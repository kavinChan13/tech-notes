3.3 共享状态

面试答「future 怎么实现」：堆上共享状态 + 引用计数。set_value 加锁、写槽、置 ready、notify；get 等 ready 后返回或重抛。API 细节见 并发深入 §5。

不写策略时实现可选择 deferred，根本不并发。更大的坑：返回的 future 析构会等任务结束。两个临时对象 = 两次隐式 join = 串行。

std::async(std::launch::async, work1);
std::async(std::launch::async, work2);
// ✅ auto f1 = async(...); auto f2 = async(...); f1.get(); f2.get();

3.5 packaged_task

把任意 callable 变成「可投递 + 自带 future」。不可拷贝，所以线程池用 shared_ptr<packaged_task> 包一层——这是 §6.2 的课，这里不重复实现。

3.6 shared_future

future 只能 get 一次。多个等待者先 .share()。典型：配置加载完成，N 个 worker 同时 get 同一份。

04

std::shared_mutex 读写锁 (C++17)

用法 · 性能 — 反直觉 · 锁升级 / 降级 — 标准不支持 · 何时不要用 shared_mutex

4.1 读并发、写独占

API 见 并发深入 §7。这里只记模式：shared_lock 多读者并行，unique_lock 写独占。标准不提供读→写升级。

4.2 性能 — 反直觉

临界区极短时，shared_mutex 的 lock/unlock 开销会吃掉「多读并行」的收益。读一个 atomic 变量别上读写锁。

4.3 锁升级 / 降级 — 标准不支持

先放读锁再拿写锁，中间有窗口，必须重新检查条件（类似 DCLP）。两个线程同时升级会死锁。需要「先看再改」→ 一开始就拿写锁，或改成单 writer 队列。

4.4 何时不要用

  • 单变量 / 纳秒级临界区 → atomic
  • 读写接近 1:1 → mutex
  • 读极多且数据可整体替换 → §8 的 COW
  • 需要升级 → 重新设计，不要自己搓升级

5.1 std::call_once + once_flag

一次性初始化：call_once 能用，但 C++11 起函数内 static（Magic Static）更短，标准保证线程安全。异常时 static 会重试，call_once 失败则 flag 仍未置位、下次再调。

5.2 std::latch (C++20)

5.3 std::barrier (C++20)

5.4 counting_semaphore / binary_semaphore

原语语义典型场景
latch倒数一次，不能重置等 N 个 worker 就绪再开下一阶段
barrier可重复的集合点，可带完成回调多阶段迭代，每轮齐步

06

线程池 — 完整实现演化 ⭐⭐⭐

最简线程池 · 返回值 + 异常透传 · forward vs move · 关键设计要点 · 线程池大小

本页的课不是「再写一遍 mutex + cv 循环」，而是 submit：packaged_task 不可拷，必须 shared_ptr 才能进队列；异常自动进 future。

6.1 结构：队列 + worker + 停止

V1 用 function<void()> 只能扔副作用。生产级要返回值 + 异常：下面这块把两版合成 submit + worker 取任务。构造/析构按 jthread 常规写即可，不重复贴完整 class。

6.2 submit：packaged_task + shared_ptr

// packaged_task 不可拷 → shared_ptr 投递；submit 听调用方 forward，worker 里再 move
template<class F, class... Args>
auto submit(F&& f, Args&&... args)
    -> std::future<std::invoke_result_t<F, Args...>>
{
    using R = std::invoke_result_t<F, Args...>;
    auto task = std::make_shared<std::packaged_task<R()>>(
        [f = std::forward<F>(f),
         args = std::make_tuple(std::forward<Args>(args)...)]() mutable {
            return std::apply(std::move(f), std::move(args));
        });
    auto fut = task->get_future();
    { std::lock_guard lk{mu_}; tasks_.emplace([task]{ (*task)(); }); }
    cv_.notify_one();
    return fut;
}

void loop(std::stop_token st) {
    std::stop_callback cb(st, [this]{ cv_.notify_all(); });
    while (!st.stop_requested()) {
        std::move_only_function<void()> task;
        {
            std::unique_lock lk{mu_};
            cv_.wait(lk, st, [this]{ return !tasks_.empty(); });
            if (st.stop_requested() && tasks_.empty()) return;
            task = std::move(tasks_.front()); tasks_.pop();
        }
        task();   // 异常已进 future
    }
}

6.2.1 为什么这里 forward、那里 move

口诀：forward 听调用方；move 抢已拥有且确定用完的东西。

上门收件看运单才搬走（forward）；货进了你仓库、今晚必发，就无条件装车（move）。写成「暂借原件人的抽屉」（forward_as_tuple）→ 人走抽屉空 → 异步悬挂。

① 进闭包：转发引用必须 std::forward

F&& / Args&&... 是万能引用。左值拷进 tuple，右值才移。make_tuple(forward<Args>(args)...) 存值。写成 forward_as_tuple 存的是引用——submit 返回后调用方栈已结束，worker 解引用即 UAF。

一律 std::move 会掏空调用方左值。forward_as_tuple 在异步边界必悬空。

② 闭包里：具名成员是 lvalue

init-capture 之后 f / args 有名字 → lvalue。apply(f, args) 接不住 unique_ptr 形参。lambda 只跑一次，所以闭包内写 apply(std::move(f), std::move(args))。

③ [task] 拷 shared_ptr 是共享所有权

packaged_task 不可拷。队列 lambda 拷贝 shared_ptr，好让 get_future() 与 worker 同时活着。不是漏了 move。

位置写法为什么
进闭包std::forward<F>(f) / make_tuple(forward<Args>(args)...)听调用方：左值拷、右值移；存值不存引用
闭包内 applyapply(std::move(f), std::move(args))具名成员是 lvalue；lambda 只跑一次，必须抢走
投递队列[task]{ (*task)(); }拷贝 shared_ptr，共享 packaged_task 所有权

点击每道题展开参考答案（先自测，再对照）。

  1. 中级线程池 submit 里为何不能一律 std::move？

    F&& / Args&&... 是转发引用。一律 move 会把调用方的左值也掏空：pool.submit(fn, payload) 之后 payload 变成 moved-from，调用方若还要用就是逻辑 bug。

    std::forward 才是「条件移动」：左值保持左值（拷进 tuple），右值才移进 tuple。闭包里面才该无条件 move——那时对象已经是闭包的具名成员，且 lambda 只执行一次。

    口诀
    forward 听调用方；move 抢已拥有且确定用完的东西。
  2. 中级为什么这里必须 make_tuple 而不能 forward_as_tuple？

    forward_as_tuple 存的是引用（tuple<Args&&...>）。submit 返回后，调用方实参的寿命已经结束，worker 线程稍后 apply 解引用 → 悬挂 / UAF。

    make_tuple(std::forward<Args>(args)...) 把对象拷或移进 tuple 的值成员，寿命跟闭包走，这才是异步边界该做的事。

07

Producer-Consumer 模式

BoundedQueue（生产级实现） · 使用模式 · 多 Producer / 多 Consumer · Backpressure (背压) 设计

有界队列把生产和消费解耦，容量就是背压。无界队列 = 慢性 OOM。

7.1 BoundedQueue — push / pop / 停服

template<class T>
class BoundedQueue {
    std::queue<T> q_; std::mutex mu_;
    std::condition_variable not_full_, not_empty_;
    size_t cap_; bool closed_ = false;
public:
    bool push(T v) {
        std::unique_lock lk{mu_};
        not_full_.wait(lk, [this]{ return closed_ || q_.size() < cap_; });
        if (closed_) return false;
        q_.push(std::move(v)); not_empty_.notify_one();
        return true;
    }
    std::optional<T> pop() {
        std::unique_lock lk{mu_};
        not_empty_.wait(lk, [this]{ return closed_ || !q_.empty(); });
        if (q_.empty()) return std::nullopt;
        T v = std::move(q_.front()); q_.pop();
        not_full_.notify_one();
        return v;
    }
    void close() {
        std::lock_guard lk{mu_}; closed_ = true;
        not_full_.notify_all(); not_empty_.notify_all();
    }
};

7.2 使用模式

生产者 push 失败就停；最后一个生产者 close()。消费者 while (auto x = q.pop())，拿到 nullopt 就是排空且关闭。

7.3 多 Producer / 多 Consumer

mutex + 两把 cv 已经支持任意 P/C。单锁热了：SPSC → 无锁 ring；MPMC → 现成库；再热 → 分片 + §11 窃取。

7.4 背压

满了默认 Block。也可 Drop / DropOldest / Reject。没有反馈，生产长期快于消费，队列会把进程撑死。

Reader-Writer 模式 — 多种实现

经典 shared_mutex · Copy-on-Write — 极致读性能 · RCU (Read-Copy-Update) — 极端读优化 · 选型

8.1 经典 shared_mutex

读路径 shared_lock、写路径 unique_lock。锁语义见 §4，这里不重复 class。

8.2 Copy-on-Write — 配置 / 路由热更

读端只 atomic<shared_ptr<const T>>::load，几纳秒、不阻塞写。写端复制整份、原子替换。旧快照随最后一个读者的 shared_ptr 析构回收。数据集大就别整表复制，改分片。

8.3 RCU

读端几乎零开销，写端复制 + 延迟回收。标准库没有，folly / userspace-rcu 才有。实现细节见 内存模型 §14。

8.4 选型

场景方案
读多、临界区微秒级shared_mutex
读极多、表小、可整体替换COW + atomic shared_ptr
读极多、表大分片锁
单变量atomic
09

Pipeline 流水线模式

实现骨架 · 性能调优要点

阶段间用有界队列连接。吞吐 = 最慢那一段。队列堆起来的阶段就是瓶颈，给它加 worker（若可并行），别给已经空转的段加线程。

假共享：队列对象挨太近会来回踢 cache line。隔离做法见 false sharing。

9.1 实现骨架

每段：从上游 pop，失败则 out.close()；成功则 push(transform(item))。不必再贴一份完整 Stage 模板——队列课在 §7。

9.2 调优

  • 看每段队列长度，长的加 worker
  • 批量 pop，减少 cv 唤醒
  • 阶段间零拷贝：传 shared_ptr，别拷大缓冲

Work-Stealing 工作窃取

动机 · 关键设计 · 工程框架

11.1 动机

全局队列的锁会先热起来。每个 worker 一把双端队列：自己从尾进出（栈、缓存友好）；空了才从别人的头偷。

11.2 关键设计

两端冲突少：owner 只碰 tail，thief 只碰 head。生产用 TBB、folly::CPUThreadPoolExecutor，或 std::execution::par 后端。

11.3 工程框架

自写 Chase-Lev 极易在 ABA / 内存序上翻车。先用库，profile 再谈。

11B

LMAX Disruptor — 极致低延时的"机械同情"模式 ⭐

定位 · 与 MPMC 的差别 · 环 + cursor · 协议 · 误用

11b.1 定位

LMAX 用环形 buffer 做到百万级订单/秒。它不是「更快的抢任务队列」：所有消费者看见所有事件，slot 预分配复用。工作分发请用线程池 / work-stealing。

11b.2 和 MPMC 队列差在哪

MPMC 队列Disruptor
所有权pop 取走slot 复用，零分配
消费者一条消息一个广播 + barrier 依赖
同步槽上 CAS各自 cursor，隔 cache line
等待混编WaitStrategy 可插拔

11b.3 环 + cursor

11b.4 协议，不是 80 行框架

生产者 next() 等到环上最老 slot 已无读者 → 写 slot → publish。消费者 wait_for(seq) 一次拿到一段连续可读区间，批量处理。cursor 用 alignas(64) 隔开，假共享见 内存模型。

11b.5 快在哪

零 malloc、生产者不和消费者抢同一个 atomic、批量摊销屏障、BusySpin 可跳过 OS 调度。面试答「省了节点分配 + 假共享 + 逐条同步」即可。

11b.6 生态与误用

C++ 侧 Disruptor-cpp；跨进程看 Aeron。工作分发（一个任务一个 worker）用 moodycamel 或 §11，不要 Disruptor。

子不能比父活得久；取消沿链传播；when_all 一人失败则取消其余再汇总。消灭 detach / 悬空回调。

NVIDIA stdexec、libunifex、Asio experimental sender。线性流程用协程即可，不必上 S/R。

11c.9 何时上

跨 CPU/GPU/IO 的统一异步、复杂依赖图、要标准取消 → S/R。SPSC 低延迟走 Disruptor。遗留 future 在边界适配。

C++20 协程 — 异步模式新范式

与线程池/future 的关系 · 标准只提供机制 — 业务自定义 Task · 简化 Task 实现骨架 · 协程的真实开销 · 应用场景

12.1 本页只问：resume 在哪条线程

机制、帧、awaiter 见 协程深入。模式层只记一件事：co_await 回来时跑在谁 resume 了你的那条线程上，不一定是当初挂起的那条。

细节：协程 §12.1 谁来 resume。线性异步长得像同步，但不要自己搓 Task。

12.2 标准只给机制

关键字 + promise_type / handle / awaiter，没有官方 Task。用 cppcoro / folly::coro，或 C++26 sender 当底座。

12.3 不要手搓 Task

骨架课在协程篇。这里只记：挂起点活着的引用必须覆盖整个 suspend，否则 UB。

12.4 开销

帧默认堆分配；resume 约几十纳秒、不进内核。CPU 密集仍走线程池。

12.5 适合 / 不适合

适合万级挂起 IO、链式异步、generator。不适合 CPU 密集、要清晰内核栈的排障。gdb 看到的是调度器，不是协程步骤。

跨线程异常传递

std::exception_ptr — 通用桥梁 · std::future — get() 自动重抛 · packaged_task — 异常自动进 future · 多 worker 异常聚合

worker 抛的异常不会自己飞回提交方。三件工具：裸 exception_ptr、future.get() 自动重抛、packaged_task 内部已经存进 future（§6）。

13.1 exception_ptr

std::exception_ptr ep;
try { do_work(); } catch (...) { ep = std::current_exception(); }
if (ep) std::rethrow_exception(ep);   // 在提交方线程重抛

13.2 future.get 自动重抛

promise / async / packaged_task 都走共享状态。提交方 get() 即可，不必自己存 ptr。

13.3 packaged_task

callable 里 throw 会被抓住并 set_exception。这是线程池 submit 能透传异常的原因。

13.4 多 worker 聚合

逐个 get，把 current_exception() 推进 vector；一个直接 rethrow，多个包成 AggregateError。不要第一个失败就丢其余的错误。

死锁的预防与检测

6 条防御规则 · 同时锁多个 mutex 的正确写法 · 锁层次 (Lock Hierarchy) · 死锁检测工具

定位与 gdb / TSan 走 死锁调试 §2。这里只记设计侧四条，不重写 HierarchicalMutex。

14.1 6 条防御

  1. 全局锁顺序（按地址也行）
  2. 多锁一起拿：scoped_lock
  3. 锁只要数据，不锁 IO
  4. RAII 守卫，禁止裸 lock/unlock
  5. 持锁不调未知回调 / 虚函数
  6. 除 cv.wait 外，持锁不阻塞

14.2 多锁

A 然后 B、对面 B 然后 A → 死锁。C++17 scoped_lock{a,b} 内部避免。细节和案例见死锁篇。

14.3 锁层次

给每把锁一个 level，线程只能从高往低拿。实现与检测工具见 §2。

14.4 工具

TSan 抓数据竞争；已死锁用 gdb thread apply all bt。Helgrind / lockstat 补长时间等待。

问：从零实现一个线程池，要支持任意 callable + 异常透传。
