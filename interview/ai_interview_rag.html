RAG 全链路 — 3 题打地基

RAG = 七步流水线，每一步都有关键选型决策
Q1: RAG 的完整链路是什么？每一步的关键决策点？

RAG = 七步流水线，每一步都有关键选型决策。

步骤做什么关键决策
文档处理解析 PDF/Word/MarkdownPDF 表格怎么处理？要不要 OCR？
Chunking长文档切小块切多大？overlap 多少？
Embedding文本块转向量什么模型？什么维度？
检索检索最相关文本块纯向量还是混合检索？Top-K 多少？
Rerank检索结果重排序什么 Rerank 模型？候选集多大？
生成检索结果+问题喂给 LLMPrompt 怎么写？幻觉怎么约束？

面试官最烦只会说"用 LangChain 调一下"的回答。要讲清每一步为什么这么选——比如"我们选递归分块而不是固定长度，是因为技术文档有明确的标题层级结构"。

Q2: 四代 RAG 架构怎么演进的？
代际名称核心特征核心局限
第一代Naive RAG简单检索→生成检索不精确、无排序、幻觉多
第二代Advanced RAG+Query 改写+混合检索+Rerank+Chunk 优化固定 pipeline、单次检索
第三代Modular RAG模块化可插拔、路由与分支仍是预设流程
第四代Agentic RAGLLM 自主决策检索策略、多轮迭代Token 消耗高、延迟大

GraphRAG 算第几代？不是第五代，而是解决不同问题的平行路线。传统 RAG 做不好"主要角色之间有什么主题联系？"这类全局理解问题，GraphRAG 通过知识图谱+社区检测来解决。

大多数生产系统 Advanced RAG 就够了，Agentic RAG 的 Token 成本是普通 RAG 的 4-8 倍，不是每个场景都值得。

Q3: Chunk 怎么切？切大了切小了分别会怎样？

切大了信息被稀释，切小了上下文被割裂——关键是根据文档结构选策略。

策略原理适用场景核心缺陷
固定长度每 512 token 切一刀简单原型不管语义边界
递归切分按段落→句子→字符优先级递归生产首选需要调参
语义切分Embedding 计算语义断点高质量要求计算量大
滑动窗口固定窗口+重叠区域避免信息丢失索引膨胀
from langchain.text_splitter import RecursiveCharacterTextSplitter
splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=100,  # 通常设 chunk_size 的 10%-20%
    separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""]
)

不同文档类型用不同策略：Markdown 按标题层级切分，PDF 先解析表格图片再按段落，代码按函数/类切分，FAQ 每个问答对作为一个 chunk。

Late Chunking（高级加分）：传统"先分块→再编码"，每个 chunk 对全局上下文是"盲"的。Late Chunking 反过来——先编码整篇文档，再按 chunk 边界做 mean pooling。在 BeIR 基准上相对提升约 3-3.6%。

03

Embedding 与向量检索 — 3 题深水区

维度不是越高越好——1024 维是当前性价比最优，3072 维存储翻 3 倍但提升有限
Q4: Embedding 模型怎么选？维度越高越好吗？

维度不是越高越好——1024 维是当前性价比最优，3072 维存储翻 3 倍但提升有限。

模型维度特点推荐场景
bge-large-zh-v1.51024中文效果最好，开源中文生产首选
bge-m31024多语言，支持稠密+稀疏+多向量多语言场景
text-embedding-3-large3072支持 Matryoshka 降维英文高精度
text-embedding-3-small1536便宜英文成本敏感

Matryoshka Representation Learning：OpenAI 的 text-embedding-3-large 支持通过 dimensions 参数降到 1024 维，在多数企业场景下性能差异微乎其微，但存储和计算成本减少了三分之二。原理是模型训练时在不同维度层级都做对比学习，截断到低维时仍保留大部分语义信息。

高维嵌入在较小知识库中甚至可能因维度灾难反而降低检索精度。

Q5: HNSW 和 IVF 有什么区别？5 亿向量怎么处理？
维度HNSWIVF
原理多层可导航小世界图k-means 划分 Voronoi 单元，只搜最近几个簇
内存高（每向量 64-128 字节邻居指针）较低（无图结构开销）
召回率一致高取决于 nprobe 设置
适用场景需要一致高召回+严格延迟内存受限 / 超大数据集

HNSW 核心参数：

  • ef_construction：构建时的搜索范围，越大索引质量越好但建得越慢
  • M：每个节点的最大连接数，影响召回率和内存占用

5 亿向量系统设计：推荐 IVF-PQ（倒排文件+乘积量化），分 16K-65K 个 Voronoi 单元，乘积量化压缩向量，跨多台机器分片并行处理。

Q6: 余弦相似度和点积有什么区别？什么时候用哪个？

嵌入没做 L2 归一化时用余弦相似度，归一化后两者等价，此时点积更快。

  • 余弦相似度：只看方向不看长度，适合未归一化嵌入
  • 点积：嵌入已 L2 归一化时与余弦等价，计算更便宜
  • 欧氏距离：受向量模长影响，不推荐

Anthropic 真题：从余弦相似度切换到内积搜索后召回率下降 15%，为什么？答案：嵌入未归一化 → 内积偏向大模长向量而非方向最相似的向量。修复方法：索引前和查询时对所有向量做 L2 归一化。

混合检索与 Rerank — 3 题核心战场

纯向量检索三个致命问题：精确匹配差、专业术语召回低、专有名词丢失
Q7: 为什么纯向量检索不够？混合检索怎么做？

纯向量检索三个致命问题：精确匹配差、专业术语召回低、专有名词丢失。

场景还原：用户搜"RFC 7231"，纯向量搜索返回一堆"HTTP 协议"语义近似文档，但偏偏漏掉了明确提到"RFC 7231"的那篇。

混合检索流程（Hybrid Search）
查询 Query
向量搜索 · 抓语义BM25 · 抓精确匹配
RRF 合并
Reciprocal Rank Fusion
Cross-encoder 重排序
最终 Top-K 结果

RRF 公式（必须能手写）：

score(d) = Σ 1 / (k + rank_i(d))  k 通常设 60 
def rrf_merge(vector_results, bm25_results, k=60):
    scores = {}
    for rank, doc in enumerate(vector_results):
        scores[doc.id] = scores.get(doc.id, 0) + 1 / (k + rank + 1)
    for rank, doc in enumerate(bm25_results):
        scores[doc.id] = scores.get(doc.id, 0) + 1 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

RRF 的优势是不需要对两路分数做归一化，也不需要学习权重，比固定加权更稳健。混合搜索相比纯向量搜索可提升 1%-9% 的召回准确率。

Q8: Rerank 为什么是生产标配？Bi-Encoder 和 Cross-Encoder 区别？

双阶段架构是生产环境标配：Bi-Encoder 粗筛百万级文档 → Cross-Encoder 精排 Top-20~50。

维度检索（粗筛）Rerank（精排）
模型类型Bi-Encoder（query 和 doc 分别编码）Cross-Encoder（query+doc 联合编码）
速度快慢（约慢 100 倍）
精度近似精确（能建模 token 级交互）
处理量百万级仅 Top-20~50 候选
指标无 Rerank有 Rerank
Top-5 召回率71%89% (+18pp)
Top-3 准确率65%84% (+19pp)

常用 Rerank 模型：BGE-Reranker (bge-reranker-v2-m3) 中文效果好、Cohere Rerank API 调用英文好、bce-reranker-base_v1 中文轻量级。最佳实践：先检索 Top-20~50 → 精排 → 取 Top-3~5。

Q9: RAG 的幻觉怎么治？

幻觉分两种：内在幻觉（与检索结果矛盾）和外在幻觉（编造检索结果里没有的信息）。治理需要六层组合拳：

#策略效果层级
1Prompt 约束："只基于检索结果回答"基础
2温度调低：temperature 设 0.1-0.3基础
3引用标注：要求模型标注信息来源 chunk进阶
4输出自校验：生成后用 LLM 检查每条是否有依据进阶
5对齐检测：回答与检索结果相似度对比，检测偏离高级
6兜底回答：相似度低于阈值时回答"未找到相关信息"保底

实战数据：Prompt 约束+引用标注+温度 0.2 三层组合，幻觉率从约 30% 降到 12%。加输出自校验才降到 3% 以下。高风险场景幻觉率应 ≤ 1%，置信度阈值通常设 0.7-0.8。

评估体系 — 2 题硬指标

RAG 评估分三个维度，推荐用 RAGAS 框架（35+ 个指标）：
Q10: 怎么衡量 RAG 系统的好坏？核心指标有哪些？

RAG 评估分三个维度，推荐用 RAGAS 框架（35+ 个指标）：

类别核心指标评估什么
检索质量Context Precision, Context Recall检索到的东西是否相关且完整
响应忠实性Faithfulness回答是否基于检索上下文，没编造
回答质量Answer Relevancy, Answer Correctness回答是否切题、是否正确

三个核心指标算法（说清面试基本满分）：

Context Precision——检索到的上下文是否对回答有用，考虑排序位置：

AP = Σ (Precision@k × is_relevant@k) / total_relevant

Context Recall——检索是否覆盖了答案需要的所有信息：

score = 可归因到检索上下文的陈述数 / 参考答案总陈述数

Faithfulness——两步算法：(1) 把回答拆成原子陈述 (2) 用 NLI 验证每条是否被检索上下文支持：

score = 忠实陈述数 / 总陈述数
分数评级行动
≥ 0.8优秀持续监控
0.6-0.8良好可接受，优化检索或 Prompt
0.4-0.6一般需要改进分块或检索策略
< 0.4较差重新审视架构
Q11: BLEU/ROUGE 能用来评估 RAG 吗？

不能。RAG 正确答案可以有多种有效释义，n-gram 重叠低不代表错误；反过来，幻觉答案可能恰好匹配参考 token。

方案优势劣势
RAGAS 自动化评估覆盖检索+生成全链路依赖 LLM 做 Judge
LLM-as-Judge灵活、可定制维度成本高、可能有偏
BERTScore语义相似度，不依赖精确匹配对事实错误不敏感
人工黄金测试集最可靠的 ground truth构建和维护成本高

生产最佳实践：维护 100+ 条黄金测试集，CI/CD 中跑 RAGAS 自动评估，在线用用户反馈互补。每次更新分块策略或 Prompt 后跑回归测试。

生产工程 — 3 题老兵区

据 Gartner 2025 年分析，问题不在技术，在于把 RAG 当"提示工程"而非"信息…
Q12: 72% 的企业 RAG 项目第一年就失败了，为什么？

据 Gartner 2025 年分析，问题不在技术，在于把 RAG 当"提示工程"而非"信息工程"。

失败模式问题解法
单体知识库所有文档塞一个向量库 → 语义噪声+上下文溢出领域专属知识仓库+路由层
"更多向量=更好"高维嵌入成本翻倍但提升微乎其微从 768 维起步，证明需要时再升级
幻觉容忍企业场景不接受"大约"置信度阈值+来源引用+验证循环
单模型依赖OpenAI 挂了全系统瘫痪多模型路由+级联降级
"部署即完成"知识库过时、系统逐渐退化反馈循环+自动化内容管理+回归评估

实例：把知识库按业务域拆成 3 个独立索引，加一层意图分类路由，检索精度从 0.62 提升到 0.81。

Q13: RAG 系统延迟怎么优化？

分层优化——先测量，再优化数据质量，再优化检索逻辑，最后压缩 Prompt。生产级 TTFT P90 应在 2 秒以内。

层级手段效果
第 1 层：测量分阶段 Profiling（检索/Rerank/生成各自耗时）找到真正的瓶颈
第 2 层：数据质量更好的 chunk + 丰富元数据支持过滤从源头降低后续负担
第 3 层：检索优化混合检索+轻量 Reranking+Query 改写提升候选质量
第 4 层：Prompt 压缩去重+片段提取+按意图调 chunk 数量降低 LLM prefill 延迟

语义缓存——成本优化的杀手锏：

语义缓存（Semantic Cache）命中判定
新查询
生成 Embedding
在缓存中向量搜索
命中 / 未命中
  • 相似度 > 阈值返回缓存响应（<100ms）
  • 相似度 < 阈值调用 LLM API（数秒级）
指标数据
LLM API 成本削减最高 68.8%
缓存命中加速比比 LLM 调用快约 65 倍
高精度场景阈值0.90 - 0.95
通用场景阈值0.85 - 0.90
Q14: 生产环境的发布门控指标怎么设？

推荐的生产级发布门控：

grounded_answer_rate  >= 97%    # 有据回答率
citation_correctness  >= 98%    # 引用正确率
hallucination_rate    <= 1%     # 高风险幻觉率
retrieval_precision@5 >= 90%    # Top-5 检索精度

索引同步——常被忽略的坑：

策略优势劣势
定时批量重建简单可靠新鲜度差（通常 24 小时）
CDC 持续同步实时更新（亚分钟级）运维复杂度约 3 倍
混合方案兼顾历史和实时历史批量处理+实时流处理

孤立向量问题：文档删除后，孤立向量可能在索引中残留数天。需要显式的删除追踪机制和定期清理任务。

前沿方向 — 1 题加分区

场景选型判断力：
Q15: Self-RAG、CRAG、GraphRAG 分别解决什么问题？
方向核心机制解决的痛点代价
Self-RAG生成时自我反思，评估检索和生成质量模型不知道自己答错了推理成本 2-3 倍
CRAG检索后评估文档相关性，不相关→触发 Web 搜索检索到的文档不靠谱额外延迟
Adaptive RAG根据查询复杂度动态选择检索策略简单问题浪费检索资源需要意图分类器
GraphRAG知识图谱+社区检测+全局/局部搜索传统 RAG 做不好跨文档关联推理构建成本极高

场景选型判断力：

场景推荐方案
简单事实查询Advanced RAG 就够了
需要可靠性+CRAG / Self-RAG
实体密集+多跳推理GraphRAG
复杂多变的查询Agentic RAG
成本敏感Adaptive RAG（简单问题不检索）

对于 2026 年大多数企业场景，Advanced RAG（混合检索+Rerank+评估闭环）仍然是性价比最高的方案。Agentic RAG 和 GraphRAG 适合特定高价值场景，不要盲目上马。

08

6 条核心判断

  1. RAG 面试的核心不是背链路，是讲 trade-off——为什么这么切、为什么混合检索、Rerank 值不值得加、成本增加多少。
  2. 混合检索+Rerank 是 2026 年生产标配——纯向量检索的三个致命问题面试官一定追问。
  3. 评估体系是区分度最大的模块——能讲清 Context Precision/Recall/Faithfulness 的算法细节，直接拉开差距。
  4. 72% 企业 RAG 失败的五大模式是系统设计题的标准答案框架。
  5. 语义缓存是成本优化的杀手锏——最高节省 68.8% LLM 成本，缓存命中快 65 倍。
  6. 前沿方向要有判断力——说清"什么场景用什么方案"比盲目追新值钱十倍。
