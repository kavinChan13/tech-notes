01

Prompt Engineering

CoT：让模型在回答前展示推理过程（"Let's think step by step"）…
Chain-of-Thought (CoT) 和 Tree-of-Thought (ToT) 有什么区别？

CoT：让模型在回答前展示推理过程（"Let's think step by step"），单条线性推理链。适用于数学题、逻辑推理等需要逐步推导的场景。ToT：将推理过程展开为树状结构，探索多条推理路径并评估每条路径的可行性，选择最优路径。适用于需要创造性探索的问题（如写作、策略规划）。核心区别：CoT 是一条路走到黑，ToT 是同时探索多条路并回溯。实际生产中 CoT 更常用（成本低、效果好），ToT 适合对质量要求极高的场景。

Self-Consistency 是什么？它解决了 CoT 的什么问题？

Self-Consistency（自一致性）解决 CoT 单次推理可能出错的问题。方法：让模型对同一问题用 temperature>0 生成多个不同的 CoT 推理路径，然后对最终答案投票，选出现次数最多的答案。例如：5 次推理得出 3 次答案 A + 2 次答案 B → 选 A。效果：在数学和推理任务上比单次 CoT 提升 5-15% 准确率。代价：推理成本 ×N（N 为采样次数）。实践中通常 N=5~10，在成本和准确率之间权衡。

System Prompt 设计有哪些最佳实践？

核心原则：①角色定义——明确模型的角色和能力边界（"你是一个专业的客服助手，只回答产品相关问题"）；②结构化输出要求——用 JSON Schema 或明确的格式模板；③安全边界——明确拒绝策略（"如果用户要求做X，请礼貌拒绝"）；④Few-shot 示例——给出 2-3 个输入输出示例；⑤分隔符——用 XML 标签或 Markdown 分隔不同指令区块，减少指令混淆。常见错误：System Prompt 过长导致关键指令被忽略（"Lost in the Middle" 问题）；缺少安全边界导致模型被 Jailbreak。

02

防幻觉策略

三大类型：①事实性幻觉——编造不存在的事实（如虚构的论文、错误的数据）
LLM 幻觉的主要类型和成因是什么？

三大类型：①事实性幻觉——编造不存在的事实（如虚构的论文、错误的数据）；②忠实性幻觉——生成的内容与输入/上下文不一致（如摘要中添加原文没有的信息）；③逻辑幻觉——推理过程看似合理但结论错误。成因：①训练数据中的噪声和偏差；②模型的"取悦倾向"（sycophancy）——倾向生成用户期望的回答而非事实；③知识截止——模型不知道最新信息但仍会"自信地"回答；④概率采样的固有不确定性。

如何在生产系统中有效防止幻觉？

多层防御：①RAG 增强——检索外部知识库作为参考依据，让模型基于事实回答而非纯记忆；②Citation 机制——要求模型标注信息来源，无法找到来源时明确说"我不知道"；③Self-Check——让模型在回答后自我检查"以上信息是否有依据"；④Guardrails 框架——用 NeMo Guardrails 或 Guardrails AI 对输出做事实校验；⑤多模型交叉验证——用不同模型回答同一问题，结果一致则可信度高。最有效的是 RAG + Citation 组合——模型基于检索到的真实文档回答，并标注来源让用户可验证。

03

Token 成本优化

五个层面：①Prompt 压缩——去除冗余指令、用缩写替代长描述、用 Few-shot 代替…
LLM 应用中如何优化 Token 成本？

五个层面：①Prompt 压缩——去除冗余指令、用缩写替代长描述、用 Few-shot 代替 Zero-shot（更短的 prompt 但更好的效果）；②模型路由——简单问题用小模型（GPT-4o-mini），复杂问题才用大模型（GPT-4），降低平均成本 50-80%；③缓存——Semantic Cache 对相似 query 返回缓存结果，命中率可达 20-40%；④工具返回结果过滤——Tool 返回的原始数据（如 JSON）可能很长，用摘要或关键字段提取后再注入上下文；⑤Batch API——非实时场景使用 Batch API，成本降低 50%。关键指标：cost per request（每次请求成本）和 cost per useful answer（每次有效回答的成本）。

什么是 Semantic Cache？和传统缓存有什么区别？

传统缓存（Exact Match Cache）：精确匹配 key，"如何报销" 和 "怎么报销" 是不同的 key，无法命中。Semantic Cache：用 embedding 相似度匹配——"如何报销" 和 "怎么报销" 的 embedding 相似度高，可以命中同一条缓存。实现：query embedding → 在缓存向量库中搜索 → 相似度 > 阈值 → 返回缓存结果。关键参数：相似度阈值（太高则命中率低，太低则可能返回不相关的缓存结果）。命中率通常 20-40%，可将 LLM 调用成本降低 20-40%。

04

结构化输出与稳定性

三层防御体系：①输入预处理——关键字段前置提取（正则/规则），减轻模型注意力漂移
如何保证大模型输出的稳定性和可靠性？

三层防御体系：①输入预处理——关键字段前置提取（正则/规则），减轻模型注意力漂移；②模型推理层——JSON Schema 约束 + 严格枚举值 + 低温度（T=0~0.3）+ RAG 知识增强；③输出后处理——多层校验（JSON 解析→Schema→值域→逻辑一致性）+ 重试（最多2次）+ 降级兜底（转人工/规则兜底/默认安全值）。核心思维转变：从"驯服模型"到"管理模型"——将模型视为需要严格管理的"同事"。实战教训：未限定枚举值导致模型输出"十万火急"作为 priority 值。

结构化输出有哪些实现方式？

三种主流方式：①JSON Mode——模型内置的 JSON 输出模式（如 OpenAI 的 response_format），保证输出是合法 JSON 但不保证符合特定 Schema；②Function Calling / Tool Use——通过定义工具的参数 Schema 来约束输出，模型按 Schema 生成结构化参数；③Constrained Decoding（约束解码）——在 token 采样阶段强制输出符合指定 Schema（如 Outlines、llama.cpp 的 grammar），100% 保证格式正确但可能影响生成质量。推荐方案：生产环境优先用 Function Calling（灵活+可靠），对格式要求极严格的场景用 Constrained Decoding。

降级兜底策略如何设计？

完整链路：JSON 解析失败 → 重试（最多2次，退避延迟）→ Schema 校验失败 → 带修正提示重试 → 重试耗尽 → 判断优先级：高优先级 → 转人工，低优先级 → 规则引擎兜底 → 仍失败 → 返回默认安全值。关键原则：永远不要假设模型输出 100% 正确。监控指标：Schema 校验通过率（<95% 告警）、重试率（>10% 告警）、降级率（>5% 告警）。实战教训：无兜底 → 模型异常 JSON 导致下游 crash；无监控 → 错误率悄悄上升。
