AI 系统设计面试框架

AI 系统设计面试通常要求在 30-45 分钟内设计一个完整的 AI 应用系统

AI 系统设计面试通常要求在 30-45 分钟内设计一个完整的 AI 应用系统。推荐用以下框架组织回答：

AI 系统设计面试回答框架（45 分钟）
Phase 1 · 需求澄清（5 min）
  • 用户规模 / QPS / 延迟要求
  • 输入输出格式
  • 质量要求（准确率 / 召回率）
  • 非功能需求（成本、安全、可扩展）
Phase 2 · 高层架构（10 min）
  • 核心组件划分
  • 数据流向
  • 技术选型（模型、向量库、缓存）
  • 部署架构
Phase 3 · 深入关键模块（20 min）
  • 检索 / 推理核心链路
  • 质量控制（防幻觉、Guardrails）
  • 性能优化（缓存、模型路由）
  • 安全设计（输入过滤、权限控制）
Phase 4 · 扩展讨论（10 min）
  • 监控与可观测性
  • A/B 测试与迭代策略
  • 成本控制
  • 扩展性（如何从 1K → 1M 用户）

02

设计题：智能客服系统

需求分析： ①多轮对话——保持上下文连贯性
请设计一个企业级智能客服系统，支持多轮对话、工单分类和知识库问答。

需求分析：①多轮对话——保持上下文连贯性；②意图识别——自动分类用户问题（咨询/投诉/退款等）；③知识库问答——RAG 检索企业知识库；④工单自动创建——结构化提取信息创建工单；⑤人机协作——复杂问题自动转人工。 架构设计：

  • 接入层——WebSocket 长连接，支持多端（Web/App/微信）
  • 对话管理层——会话状态机 + 短期记忆（Redis 存储最近 N 轮对话）
  • 意图路由——轻量级分类器先判断意图类型，路由到不同处理链路：简单FAQ→RAG、复杂问题→Agent、投诉→工单系统
  • RAG 链路——Query Rewrite → 混合检索（BM25 + Dense）→ Reranking → LLM 生成
  • 工单系统——LLM 提取结构化信息（类别/优先级/摘要）→ JSON Schema 校验 → 写入工单系统
  • 安全层——输入过滤（Prompt 注入检测）→ 输出过滤（PII 脱敏）→ Guardrails
  • 降级策略——LLM 超时/失败 → 规则引擎兜底 → 转人工
关键设计决策：
  • 模型路由：简单FAQ 用小模型（GPT-4o-mini），复杂推理用大模型（GPT-4o），降低成本 50-80%
  • 输出稳定性：工单分类必须 JSON Schema + 枚举值约束，校验失败重试 2 次后转人工
  • 延迟控制：RAG 链路 P95 < 3s，缓存高频问答结果（命中率 ~30%）

03

设计题：企业文档问答系统

核心挑战： ①文档量大（100 万文档 × 平均 10 chunks = 1000 万向量）
请设计一个支持 100 万文档的企业知识库问答系统。

核心挑战：①文档量大（100 万文档 × 平均 10 chunks = 1000 万向量）；②权限隔离（不同部门/角色看到不同文档）；③实时更新（文档变更需及时反映到检索结果中）。 架构设计：

  • 文档处理 Pipeline——文档上传 → 格式解析（PDF/Word/HTML）→ 智能分块（语义分块 + 结构化分块）→ Embedding → 向量入库
  • 向量存储——Milvus/Qdrant 集群，支持 1000 万级向量的 ANN 检索，每个向量附带权限元数据
  • 检索层——混合检索（BM25 + Dense）→ Reranking（Cross-Encoder）→ 权限过滤（Pre-filtering 按用户角色过滤）
  • Query 处理——Query Rewrite（多路扩展）→ 意图分类 → 选择检索策略
  • 生成层——检索结果 + 用户问题 → LLM 生成回答 + Citation（标注来源）
  • 实时更新——文档变更事件 → 增量更新向量索引（不重建全量）
权限设计：
  • 文档安全分级（L0 公开 → L3 绝密）
  • Pre-filtering：向量检索时 metadata filter 按权限过滤
  • Post-filtering：检索结果二次权限校验
  • L3 文档使用独立索引（物理隔离）
性能指标：
  • 检索延迟 P95 < 200ms（1000 万向量）
  • 端到端回答延迟 P95 < 5s
  • 文档更新延迟 < 5min（增量更新）

设计题：AI 代码助手

核心功能： ①代码补全（实时，延迟 架构设计： 补全引擎 ——本地部署的代码模型（如 Sta…
请设计一个企业级 AI 代码助手，支持代码补全、代码审查和代码生成。

核心功能：①代码补全（实时，延迟 < 500ms）；②代码审查（PR 级别，分析代码质量和安全问题）；③代码生成（根据自然语言描述生成代码）。 架构设计：

  • 补全引擎——本地部署的代码模型（如 StarCoder/CodeLlama）→ KV Cache 优化 → Speculative Decoding 加速。关键：补全必须低延迟（< 500ms），使用 Speculative Decoding（小模型草稿 + 大模型验证）可加速 2-3x
  • 上下文构建——当前文件 + 相关文件 + 最近编辑历史 → FIM (Fill-in-the-Middle) 格式。上下文窗口有限，需要智能选择最相关的上下文（基于文件依赖图 + 最近修改）
  • 代码审查——PR diff → 分块分析 → LLM 审查（安全漏洞、性能问题、代码风格）→ 结构化输出（JSON 格式的审查意见）→ 发布到 PR 评论
  • 代码生成——自然语言描述 → 代码生成 → 自动测试生成 → 沙箱执行验证 → 输出代码 + 测试结果
  • 安全——代码不能发送到外部 API（本地部署）→ 生成代码需通过安全扫描（SAST）→ 不生成包含硬编码密钥的代码
关键设计决策：
  • 补全用本地小模型（低延迟），复杂生成用云端大模型（高质量）
  • KV Cache 管理：按文件/项目缓存，LRU 淘汰策略
  • 代码审查的输出必须结构化（JSON Schema），方便集成到 CI/CD 流水线

通用设计要点总结

面试官关注的维度

维度考察点加分项
架构完整性端到端链路是否完整考虑异常路径和降级策略
技术选型为什么选这个技术而不是另一个展示权衡分析能力
质量控制如何保证输出质量防幻觉 + Guardrails + A/B 测试
性能优化延迟/成本/吞吐量缓存 + 模型路由 + 异步处理
安全设计输入/输出安全Prompt 注入防御 + PII 脱敏 + 权限控制
可扩展性从 1K → 1M 用户的扩展方案水平扩展 + 分层缓存 + 异步处理
可观测性如何监控系统健康指标/日志/追踪三件套 + 告警

常见的追问方向

  • 成本控制："如果 QPS 从 100 增加到 10000，成本如何变化？"
  • 故障处理："如果 LLM 服务挂了，系统如何降级？"
  • 数据一致性："知识库更新后，多久能反映到检索结果中？"
  • 冷启动："新产品线没有历史数据，如何冷启动？"
  • A/B 测试："如何验证新模型/新策略的效果？"
系统设计面试的核心不是给出"正确答案"，而是展示结构化思维和权衡分析能力。面试官想看到你能清晰地拆解问题、分析约束、提出方案、讨论权衡。
