哈希表内核

哈希表的 O(1) 是期望、摊销、且依赖哈希函数质量的。三个限定词各自对应一类事故：碰撞攻击、rehash 停顿、哈希选错。拉链 / 开放寻址、滚动哈希、一致性哈希和布隆过滤器都以图为主，代码只留探测与哈希更新。

01

本质：用值算地址

以及那个 O(1) 的三个限定词

数组下标是 O(1)，因为地址能直接算。哈希表把这件事推广到任意键：槽 = h(key) mod 桶数。键空间远大于桶数，冲突是必然的——工程复杂度全在怎么处理冲突。

「哈希表是 O(1)」的三个限定词：
  • 期望——假设哈希均匀。不成立就退化 O(n)，攻击者可以主动制造（§7）。
  • 摊销——单次可能触发 O(n) rehash，那次停顿就是 p99（§6）。
  • 不含哈希计算——长键上 h(key) 是 O(len)，计算本身可以是瓶颈。
面试里主动说这三条，比背「平均 O(1) 最坏 O(n)」有用。
像图书馆按首字母分区：找书只去那一区。分区不均 → 一区排长龙（坏哈希）；扩馆要把书全部重上架（rehash，当天谁来都得等）；恶意捐赠同一字母的书 → 碰撞攻击。防御不是换书架，而是让分区规则每次开馆随机变化，让攻击者猜不到该捐什么。

整个数据结构的性能地基

2.1 好哈希的三个标准

哈希函数速度（长键）抗碰撞典型用途
FNV-1a慢（逐字节）否短键、代码简单优先

哈希表不要用 SHA / MD5——慢几十倍，而哈希表不需要抗第二原像。抗攻击用 SipHash（专为「密钥未知则不可构造碰撞」设计）。反过来也不要用 xxHash 做内容寻址或去重指纹，它有意不抗碰撞。选哈希的第一个问题永远是「输入是否可信」。

2.2 std::hash 的实现与陷阱

类型libstdc++ 的 std::hash问题
int / 整型恒等函数（直接返回值）零雪崩。配位掩码桶时低位倾斜的键会严重聚簇
T* 指针reinterpret 成整数低位恒为 0（对齐），同上
std::stringMurmurHash 变体（逐字节）O(len)；无随机种子 → 可被攻击
float / double按位哈希（0 特判）NaN != NaN 导致 NaN 键永远查不到
std::pair / tuple没有特化编译报错，必须自己写

libstdc++ 用素数桶，恒等哈希勉强能用；自己写 2 的幂 + 位掩码时必须加一层混淆，否则页对齐指针、按 1000 递增的 ID 都会挤成一段。absl / hashbrown 已内置这层 finalizer。

// splitmix64 finalizer：3 条指令，雪崩很好
inline uint64_t mix(uint64_t x) {
    x += 0x9E3779B97F4A7C15ULL;
    x = (x ^ (x >> 30)) * 0xBF58476D1CE4E5B9ULL;
    x = (x ^ (x >> 27)) * 0x94D049BB133111EBULL;
    return x ^ (x >> 31);
}

2.3 取模 vs 位掩码

现代实现几乎全选位掩码，因为 xxHash / wyhash 已经够快、雪崩充分，用 1 条 AND 换 20 周期的除法划算。自己造表时绝不能再配弱哈希——责任已经全部压在哈希函数上。

2.4 组合多个字段

std::hash 没有 pair / tuple 特化。异或是最常见的错法：对称（(a,b) 与 (b,a) 碰撞）且自逆（a==b 结果恒 0，所有对角元素挤进一个桶）。相加同样对称；高位拼接会丢信息。结构体整块哈希还要小心 padding 字节未定义——两个逻辑相等的对象可能因垃圾值不同而哈希不同。

template <class T>
inline void hash_combine(size_t& seed, const T& v) {
    seed ^= std::hash<T>{}(v) + 0x9E3779B97F4A7C15ULL
          + (seed << 6) + (seed >> 2);
}

捷径：absl::flat_hash_map 的 AbslHashValue，或逐字段 combine。不要对带 padding 的结构体做整块字节哈希。

2.5 滚动哈希

定长窗口从位置 i 滑到 i+1 时，不必重算 m 个字符：减掉离开的、乘基数、加上进入的。前缀哈希能 O(1) 取任意子串，比定长滚动更常用——这才是它在最长公共子串、二分判定里的价值。完整匹配与碰撞处理见 字符串匹配。

// 窗口右移 1：O(1) 更新
H = (H - s[i] * p) * B + s[i + m];   // p = B^{m-1}

拉链法

std::unordered_map 走的路，以及标准怎么把它逼出来的

3.1 unordered_map 的真实结构

3.2 标准为什么逼出这个实现

C++11 把桶接口、引用稳定性、max_load_factor > 1 写进契约，任何合规实现都只能是拉链。这是标准库设计的著名教训：接口暴露了多少实现细节，直接决定以后还能不能换内核。abseil / folly / Boost.Unordered 主动放弃引用稳定，才换得开放寻址的 2–3 倍。

标准要求后果
引用与指针在 rehash 后仍有效（只有迭代器失效）元素必须单独堆分配，不能放连续数组
bucket_count() / bucket(key) / 局部迭代器必须真有「桶」，结构被锁成拉链
负载因子可 > 1开放寻址物理上做不到
全表遍历 O(size)节点必须串成一条全局链，不能每桶独立
插入不使已有引用失效禁止 Robin Hood 这类「移动已有元素」

拉链的真实优势不是「更慢所以没人要」：引用稳定（可持有 &map[k] 跨插入）、α 可 > 1、删除无墓碑、Java 8 单桶 > 8 可转红黑树把最坏从 O(n) 收到 O(log n)。选型问的是「要不要引用稳定」，不是「谁更快」（§8）。

04

开放寻址

所有元素放在一个连续数组里

4.1 线性探测与聚簇

冲突时顺着数组找下一个空位。探测序列连续，符合 cache line 与硬件预取：探 8 个槽可能只 1 次 miss；二次 / 双重哈希每步随机跳，每步都可能 miss。所以线性探测理论聚簇最重，实测常最快——又一个「渐进相同、常数不同」。

// 线性探测：唯一保留的查找代码
int find_slot(const Key& k) {
    size_t i = hash(k) & mask;
    while (slots[i].state != EMPTY) {
        if (slots[i].state == FULL && slots[i].key == k) return i;
        i = (i + 1) & mask;
    }
    return -1;   // 碰到 EMPTY 才说明不存在
}
未命中曲线按 1/(1−α)² 恶化。以「查不到」为主的负载（缓存 miss、去重）对 α 更敏感——阈值要更低，或前面加布隆过滤器（§9.2）。

4.2 二次探测与双重哈希

探测方式第 i 次位置聚簇cache
线性h + i主聚簇最好
二次h + (i+i²)/2次聚簇中
双重哈希h1 + i·h2(k)几乎无每步随机跳
Robin Hood线性但会抢位方差极小最好

二次探测的式子必须能覆盖全部槽，否则表还没满就找不到空位——看起来能跑，高负载才爆。2 的幂桶配 h+(i+i²)/2 可以遍历全部 2^k 个槽；朴素 h+i² 只能覆盖约一半。

4.3 Robin Hood

插入时若当前占用者比自己更接近理想位置，就把它踢走、自己坐下，再为被踢者继续找位。不变式让未命中不必走到 EMPTY。代价是插入会移动已有元素，违反 unordered_map 的引用稳定，所以标准库不能用；自造表且对 p99 敏感时仍值得考虑。

4.4 删除的墓碑问题

墓碑不减少探测长度，只减少 size()。反复插删会让表看起来很空、探测却很长；极端时整表墓碑，未命中扫全表变成 O(n)。所以必须把墓碑计入 α，超阈值 rehash 清掉。写多删多的负载下拉链反而更稳——选型要问删除频率，不只读写比。

05

Swiss Table

abseil / Rust hashbrown 的做法：用 SIMD 一次探测 16 个槽

5.1 控制字节与 SIMD 探测

元数据与数据分开：每槽 1 字节控制信息，16 字节 = 一条 SIMD 寄存器。H1 定位组，H2（7 位）当指纹筛候选。

「大概率排除」和「精确确认」分两步：H1 定位组，H2（7 位）当指纹。SIMD 在连续 16 字节上一次比完，假阳性约 1/128，通常只比 1 次完整 key。与布隆过滤器同源——区别是控制字节后面就是真数据（§9.2）。传统开放寻址每探一槽都要访问槽位 + memcmp；Swiss 把探测从「大对象数组」挪到「1/4 条 cache line」。

5.2 快 2–3 倍的来源

因素std::unordered_mapabsl::flat_hash_map
内存布局节点散落（每个一次 malloc）一块连续数组
查找的 cache miss1（桶）+ N（链表跳转）通常 2（控制字节 + 槽位）
每元素额外内存next 指针 + 缓存 hash + malloc 头 ≈ 32 B1 字节控制字节
桶映射素数取模（整数除法 ~20 周期）位掩码（1 周期）
key 比较次数链表上每个节点都比SIMD 筛完通常只比 1 次
哈希函数std::hash（整型是恒等）内置混淆 + 随机种子
分配次数每次插入一次仅扩容时

2–3 倍是七项累积，不是换个 std::hash 就能拿到：连续数组、位掩码、1B 元数据、SIMD、内置混淆、仅扩容时分配、更高 α。数据量小（几百）时差距不大，甚至 unordered_map 更好（无 SIMD 开销、无扩容抖动）；随机大表才明显。必须在自己的数据上测，见 性能优化指南。

5.3 代价：迭代器与引用失效

元素在数组里，扩容会移动——&map[k] 跨一次可能 rehash 的操作就是悬垂引用。unordered_map 没有这个问题。需要稳定时用 absl::node_hash_map。迁移时这是唯一必须审查的点：全仓库搜「持有 map 元素引用跨越后续操作」，并把 ASan 挂进 CI。另外两条：value 必须可移动；迭代顺序刻意随机化，测试挂了先怀疑隐藏的顺序依赖。

负载因子与 rehash

摊销 O(1) 背后的那次停顿

6.1 探测长度曲线

实现默认 max_load_factor扩容策略
std::unordered_map（libstdc++）1.0下一个素数（约 2 倍）
absl::flat_hash_map约 0.875（7/8）2 倍
Rust HashMap（hashbrown）约 0.8752 倍
Java HashMap0.752 倍；单桶 > 8 转红黑树
Python dict约 0.66（2/3）约 3 倍（按已用槽数）

拉链 α=1 只是平均链长 1，还可以 > 1；开放寻址的探测是 1/(1−α) 量级，α=0.9 未命中约 50 次，α→1 发散。Swiss 用 0.875 是因为 SIMD 把「探 16 槽」做成「探 1 槽」的成本，于是可以承受更高占用、更省内存。

6.2 增量式 rehash

一次性 rehash 是 O(n) 停顿：分配新表、重算所有键、搬移。n 很大时是几十到几百毫秒。Redis 把它切碎：双表并存，每次增删查改顺带搬一个桶；查找先旧后新，插入只写新表，保证旧表只减不增。

总工作量不变，但没有单次 O(n)。代价是过渡期内存双份、每次操作查两张表——和增量 GC、在线 DDL、LSM compaction 同一笔交易：用平均成本换尾延迟。

6.3 尾延迟

那次 O(n) 落在哪个请求上，那个请求就是 p99。均值上的摊销完美，对低延迟服务却是抖动来源。

手段做法代价
预留容量启动时 reserve(峰值)，运行期永不扩容要能估出峰值；内存常驻
渐进式 rehash把搬移分摊到后续操作（Redis 做法）实现复杂；过渡期内存双份、常数变大
换稳定结构用红黑树（std::map）：永远 O(log n)，无抖动平均更慢
分片拆成 N 个小表，rehash 只影响 1/N跨片操作变复杂
后台 rehash另起线程建新表，切换时原子替换需要并发安全设计，内存双份

reserve(n) 保证能装 n 个而不 rehash，实现按 n / max_load_factor 算桶数——reserve(1000) 在 α=0.875 时会开到约 2048 槽。不要用 rehash(n) 代替，它的参数是桶数不是元素数。完整清单见 低延迟编程。

07

哈希碰撞 DoS

把「平均 O(1)」变成「最坏 O(n)」的攻击

7.1 2011 年的事故

2011 年 28C3 上公布：Web 框架把 POST 字段 / 查询参数 / JSON 键放进哈希表。攻击者离线算出大量哈希相同的字符串当参数名，全部落入同一桶。插入 n 个碰撞键从 O(n) 变成 O(n²)（每次都要沿链查重）。几 MB 的 POST 就能打满一核数分钟。哈希公开且确定，碰撞集成本几乎为零。教训见 复杂度与分析：平均复杂度可被攻击。

7.2 SipHash 与随机种子

修法不是换数据结构，而是让攻击者算不出碰撞：h(secret, key)，密钥在进程启动时随机。SipHash 的保证就是「密钥未知则不可构造碰撞」。

语言 / 库现在的默认
Python 3.3+SipHash-1-3 + 随机种子（PYTHONHASHSEED 可固定，仅用于调试）
Rust HashMapSipHash-1-3 + 随机种子（默认就安全）
Ruby / Perl / PHP 7+SipHash 或加盐
Java HashMap没换哈希，改成单桶超 8 个转红黑树（最坏 O(log n)）
absl::flat_hash_map内置混淆 + 进程级随机种子
std::unordered_map无随机化，std::hash 完全确定
std::hash 无随机化，是标准层面的缺口。不可信键（HTTP 参数名、JSON 键）不要直接进 unordered_map。三条修法：① 自定义带 random_device 种子的 hasher（SipHash-1-3）；② 换 absl::flat_hash_map；③ 同时限制键的个数与长度——即使哈希安全，资源也要有上界。

Java 转红黑树改的是最坏复杂度（O(n)→O(log n)）；其他语言换哈希改的是攻击可行性。可以叠加。转树对用户写的烂 hashCode 也有效。

选型按顺序问三件事：
  1. 元素有多少？几十个以内，vector 线性扫描往往打败任何哈希表。
  2. 有没有硬约束？引用稳定、有序遍历、最坏延迟、线程安全——有约束先满足约束。
  3. 键可信吗？不可信就必须带随机种子。
三个都过了才比性能。「哪个更快」是最后一个问题。

09

分布式场景

同一个哈希，换成分片的地址

「哈希 → 桶」换成「哈希 → 机器」就是分片。朴素 hash % N 在 N 从 3 变 4 时约 3/4 的键要迁移——缓存命中率瞬间归零，下游被打穿。一致性哈希把值域看成环，加节点只搬它接管的那段弧，迁移量 ≈ 1/N。

9.1 一致性哈希环

方案加/减节点的迁移量负载均衡典型使用者
取模≈ N/(N+1)完美节点数固定的场景
一致性哈希 + 虚拟节点≈ 1/N好（靠虚拟节点数）Cassandra、Dynamo、memcached 客户端
Rendezvous（HRW）哈希≈ 1/N很好实现更简单，无需维护环
Jump Consistent Hash最优完美Google；但只支持在末尾增删节点
槽位映射（slot）可控（按槽迁移）完美Redis Cluster（16384 槽）

Redis Cluster 不用环，而是把键空间固定切成 16384 槽（CRC16(key) % 16384）再分配给节点。好处是迁移粒度可观测、可暂停、可回滚——你能确切知道「槽 5000 正在从 A 迁到 B」。一致性哈希的迁移是隐式的，出问题难定位。这是「显式间接层」换可运维性。完整讨论见 存储与数据架构。

9.2 布隆过滤器

只需「存在过吗」、允许假阳性时，不必存真实键。k 个哈希把比特数组对应位置 1；查询时有一位是 0 则一定不在，全是 1 则可能在（别的键的并集碰巧盖住了）。假阳性率约 (1 − e^{−kn/m})^k，m 是位数、n 是元素数。完整展开见 缓存穿透与布隆过滤器。

Swiss Table 的控制字节是同一思想的精确版：摘要挡住无效访问，后面跟着真数据。布隆不存键，所以没有「再比一次」这条退路，假阳性必须靠把 m 开够来压。缓存场景里用它挡穿透，命中后再查真实存储。

面试题集（12 道）

按难度分三段，先自测再对照

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础哈希表的查找是 O(1) 吗？把这句话说完整。

    不完整。准确说法是：期望、摊销 O(1)，且不含哈希计算本身；最坏 O(n)。三个限定词各自对应一类真实故障。

    ① 期望（expected）
    建立在「哈希值均匀分布」的假设上。假设不成立就退化到 O(n)——而攻击者可以主动制造这个不成立（Hash-DoS）。
    ② 摊销（amortized）
    单次插入可能触发 rehash，代价 O(n)。均值上无所谓，但那次停顿落在哪个请求上，那个请求就是 p99。
    ③ 不含哈希计算
    渐进分析把 h(key) 当 O(1)，但对长字符串它是 O(len)。键很长时哈希计算本身就是瓶颈。
    和红黑树对比时该怎么说
    std::map 是确定性的 O(log n)：没有假设、没有抖动、没有攻击面。所以「哈希表比树快」只在平均意义上成立；需要稳定最坏延迟时树反而是对的选择。
    而且 n 小时（几十到几百）树常常更快——log n 只有 6~8，而哈希要算 hash + 一次随机地址访问。
  2. 基础解决哈希冲突有哪两大类方法？各自的优缺点？
    拉链法（separate chaining）开放寻址（open addressing）
    做法每桶挂一条链表/树冲突时在同一数组里找下一个空位
    负载因子可 > 1必须 < 1，且 >0.85 后急剧恶化
    引用稳定性稳定（元素单独分配）扩容会移动元素
    cache 友好差（指针追逐）好（连续内存）
    每元素额外内存≈ 32 B（指针+hash+malloc 头）0~1 B
    删除简单摘链需要墓碑
    分配次数每次插入一次 malloc仅扩容时
    谁在用
    拉链：std::unordered_map、Java HashMap（单桶超 8 个转红黑树）。
    开放寻址：absl::flat_hash_map、Rust HashMap、Python dict。
    选型判据不是「哪个快」
    先问「需不需要引用稳定性」（能否持有 &map[k] 跨插入）和「删除频繁吗」（开放寻址的墓碑会累积）。两个都不需要，再选开放寻址求性能。
  3. 基础什么是负载因子？它为什么决定了扩容时机？

    负载因子 α = 元素数 / 桶数（或槽数）。它是「有多挤」的度量，直接决定查找的期望比较次数。

    拉链法：α = 平均链长；期望比较 ≈ 1 + α/2 α=1 时约 1.5 次 → 完全可接受，α 可以 > 1 开放寻址：α = 占用率 命中　： (1 + 1/(1−α)) / 2 未命中： (1 + 1/(1−α)²) / 2 ← 恶化更快 α=0.9 未命中约 50 次 α=0.99 未命中约 5000 次（发散）
    所以阈值差别很大
    unordered_map（拉链）默认 1.0；flat_hash_map（开放寻址）约 0.875；Java 0.75；Python 约 0.66。
    「未命中恶化更快」的工程含义
    以「查不到」为主的负载——缓存 miss 检查、去重判断、存在性验证——对负载因子更敏感。这类场景该把阈值设更低，或前面加一层布隆过滤器挡掉不存在的键。
    Swiss Table 为什么敢用 0.875
    因为 SIMD 让「探测 16 个槽」的成本接近「探测 1 个槽」——它把探测长度的常数压得极低，于是能承受更高负载因子，从而省内存。这是个漂亮的连锁收益。
  4. 基础为什么 std::unordered_map 的 std::hash<int> 是恒等函数也能用？什么时候会出问题？

    因为 libstdc++ 的 unordered_map 用素数桶数取模。取模会把哈希值的高位信息「搅」进结果，所以即使哈希函数很弱（恒等），分布也还算均匀。

    出问题的场合：自己造 2 的幂 + 位掩码的表
    位掩码 h & (n-1) 只用低位。此时恒等哈希会暴露键的低位规律：
    // 键都是 1000 的倍数，桶数 1024
1000 & 0x3FF = 1000
2000 & 0x3FF = 976
3000 & 0x3FF = 952    // 步长恒定 → 聚簇成一段
    指针做键更糟——对齐让低位恒为 0。
    这是一个责任转移的取舍
    素数取模把「保证分布」的责任放在桶映射上（哈希函数可以弱），代价是每次一次整数除法（~20 周期）。
    位掩码把责任放在哈希函数上，桶映射只需 1 周期，但哈希函数必须有雪崩效应。
    现代实现全选后者——因为好的快哈希（xxHash、wyhash）已经足够。
    修法
    自己加一层混淆（splitmix64 的 finalizer，3 条指令，雪崩很好）：
    x += 0x9E3779B97F4A7C15;
x = (x ^ (x>>30)) * 0xBF58476D1CE4E5B9;
x = (x ^ (x>>27)) * 0x94D049BB133111EB;
return x ^ (x>>31);
    或者直接用 absl::flat_hash_map——它内置了这层混淆。

10.2 中级（区分熟练度）

  1. 中级为什么 std::unordered_map 必须是拉链法实现？标准做了什么约束？

    标准把太多实现细节写进了接口契约，这些要求联合起来排除了开放寻址：

    标准要求后果
    引用与指针在 rehash 后仍有效元素必须单独堆分配，不能存在连续数组里
    bucket_count() / bucket(key) / 局部迭代器 begin(n)必须真的有「桶」，暴露了拉链结构
    max_load_factor 可 > 1开放寻址的负载因子物理上不可能 > 1
    全表遍历 O(size)节点必须串成一条全局链表（否则要跳过空桶 → O(桶数)）
    插入不使已存在元素的引用失效禁止 Robin Hood 这类「移动已有元素」的方案
    这是标准库设计的一个著名教训
    C++11 定接口时把桶接口、引用稳定性、负载因子 > 1 都写进了契约，结果任何符合标准的实现都必须是拉链法，未来无法换成更快的方案。
    这就是 abseil、folly、Boost.Unordered 新版都提供不完全兼容标准接口的替代品的原因——它们主动放弃引用稳定性换 2–3 倍性能。
    「接口暴露了多少实现细节」直接决定未来的优化空间——这条经验对设计任何库都成立。
    但拉链法也有真优势
    ① 引用稳定（可安全持有 &map[k]，在缓存/对象池/图结构里很有用）；② 负载因子可 > 1（内存吃紧时不必扩容）；③ 删除简单，无墓碑；④ 可按桶退化成树——Java 8 单桶超 8 个转红黑树，把最坏从 O(n) 降到 O(log n)，这是拉链法独有的能力。
  2. 中级开放寻址的删除为什么需要「墓碑」？墓碑又带来什么问题？

    因为直接标 EMPTY 会切断探测链：

    // A→槽3, B→槽3冲突占4, C→槽3冲突占5
// 槽: [.., .., .., A, B, C, ..]
// 删 B 标 EMPTY → [.., .., .., A, _, C, ..]
// 查 C：槽3(A 不匹配) → 槽4 是 EMPTY → 判定「不存在」
// 但 C 明明在槽5！
    墓碑（三态）
    状态改为 EMPTY / FULL / DELETED：
    · 查找遇到 DELETED 继续探测（不终止）
    · 插入遇到 DELETED 可以复用该槽
    · 只有遇到 EMPTY 才判定不存在
    墓碑带来的新问题
    墓碑不减少探测长度，只减少元素个数。反复插入删除的表会不断累积墓碑，导致：
    · size() 很小但探测很长（有效负载因子被墓碑撑高）
    · 极端情况整表全是墓碑 → 任何未命中查找都要扫全表 → O(n)
    标准解法
    把墓碑计入负载因子：load = (size + tombstones) / capacity，超阈值就 rehash——rehash 会自然清掉所有墓碑。
    选型含义
    这是开放寻址在「写多删多」负载下的固有弱点。这类场景拉链法反而更稳（删除只是摘链，无残留）。
    选型时要问的不只是读写比，还有删除频率——这一点经常被忽略。
  3. 中级Swiss Table（absl::flat_hash_map）为什么比 unordered_map 快 2–3 倍？

    核心创新是元数据与数据分离：一个紧凑的「控制字节数组」（每槽 1 字节）+ 一个槽位数组。哈希值拆成两部分用：H1 定位组，H2（7 位）存进控制字节当指纹。

    m = _mm_movemask_epi8(_mm_cmpeq_epi8(ctrl, set1(H2))) 一条 SIMD 指令比较 16 个控制字节 → 得到 16 位掩码 只对掩码里的位去访问真正的槽位 H2 有 7 位 ⟹ 假阳性率约 1/128 ⟹ 通常只需比较 1 次完整 key
    关键是「探测」和「比较」解耦
    传统开放寻址每探测一个槽都要：访问槽位（可能 cache miss）+ 比较完整 key（string 要 memcmp）。
    Swiss Table 的探测发生在极小的连续元数据数组上——16 字节只占 1/4 条 cache line，一次 miss 能拿到 64 个槽的元信息。
    但 2–3 倍不来自单个技巧，是七项累积
    连续内存（vs 节点散落）、位掩码（vs 素数取模的整数除法 ~20 周期）、1 字节元数据（vs 每元素 ~32 B 额外内存）、SIMD 筛选、内置哈希混淆、仅扩容时分配、更高的负载因子。
    所以「只把 std::hash 换成 xxHash」提升有限——真正的瓶颈是内存布局和分配。
    代价：引用与迭代器失效
    元素直接存在数组里，扩容会移动元素：
    auto& v = map["a"];
map["b"] = 1;   // 可能扩容 → v 悬垂
v = 2;           // use-after-free
    需要引用稳定就用 absl::node_hash_map。迁移时唯一要审查的就是这一点——全仓库搜「持有 map 元素引用跨越后续 map 操作」，并把 ASan 挂进 CI。
    还有两个次要差异
    value 必须可移动；迭代顺序刻意随机化（防止代码依赖遍历顺序）——迁移后测试挂了，先怀疑是不是有隐藏的顺序依赖。
    同源思想
    控制字节 = 一个小的、可能假阳性的摘要，用来挡住绝大多数无效访问——这和布隆过滤器完全同源。区别只是布隆不存真实数据。
  4. 中级自己给 std::pair 写 hasher，为什么不能用异或组合？

    因为异或是对称且自逆的，会产生两类系统性碰撞：

    ① 对称 → 顺序信息丢失
    h(a) ^ h(b) == h(b) ^ h(a) ⟹ (1,2) 和 (2,1) 必然碰撞。用 pair 表示「有向边」或「坐标」时这是灾难。
    ② 自逆 → 对角线全归一桶
    a == b 时 h(a) ^ h(a) == 0 ⟹ 所有 (x, x) 挤进同一个桶。

    相加也有同样的对称问题；简单移位 (h1 << 32) | h2 在 h2 超过 32 位时冲突。

    正确写法：Boost 风格 hash_combine
    template <class T>
void hash_combine(size_t& seed, const T& v) {
    seed ^= std::hash<T>{}(v)
          + 0x9E3779B97F4A7C15ULL       // 黄金比例常数
          + (seed << 6) + (seed >> 2);   // 混入已有 seed
}
    它顺序敏感且有雪崩效应。
    两条捷径
    ① 用 absl::flat_hash_map——abseil 为 pair/tuple/容器都提供了正确的 AbslHashValue；② 逐字段拼成字节序列后整体 xxHash。
    整体字节哈希的隐藏坑
    结构体的 padding 字节内容是未定义的——两个逻辑相等的对象可能因 padding 里的垃圾值不同而哈希不同。要么 static_assert 确认无 padding，要么逐字段 combine。

10.3 高级（体现深度）

  1. 高级什么是 Hash-DoS？为什么 C++ 的 std::unordered_map 有风险，怎么修？

    2011 年 28C3 公布的攻击：Web 框架把 HTTP 参数名 / JSON 键放进哈希表，攻击者预先离线算出大量哈希相同的字符串发过去，全部落进同一桶。

    插入 n 个碰撞键的总代价：O(n) → O(n²) （每次插入都要遍历整条链查重） 当时的数字：几十 KB ~ 几 MB 的 POST 就能打满一个 CPU 核数分钟

    受影响的有 PHP、Java、Python、Ruby、ASP.NET、V8——都因为用了确定性的、算法公开的哈希函数。

    C++ 的问题在标准层面
    std::hash<std::string> 没有随机化：同一字符串在同一实现上永远返回同一值，算法还是公开的。
    所以把不可信输入（参数名、JSON 键、上传字段名）直接当键放进 std::unordered_map 是有风险的。
    修法一 · 带随机种子的 hasher
    struct SeededHash {
    static const uint64_t seed;   // 启动时从 random_device 取
    size_t operator()(std::string_view s) const {
        return siphash13(seed, s.data(), s.size());
    }
};
    SipHash 的安全性正是「密钥未知时不可构造碰撞」——这是它相对 xxHash/Murmur 的唯一优势，也是它存在的理由。
    修法二 · 换 absl（内置随机种子）
    absl::flat_hash_map 自带进程级随机种子 + 哈希混淆。
    修法三 · 限制键数量与长度（必须同时做）
    if (params.size() > kMaxParams) reject();——即使哈希安全也该做。这挡住的是一整类「资源无上界」问题，不只哈希碰撞。
    Java 的另一条路
    Java 没换哈希，而是单桶超 8 个转红黑树。这改的是「最坏复杂度」（O(n)→O(log n)，攻击仍能发生但危害可控）；换哈希改的是「攻击可行性」（最坏仍 O(n) 但构造不出来）。
    两者可叠加。转树还对非恶意的坏哈希有效（比如用户自己写了糟糕的 hashCode）。
    一般性原理
    教训不是「哈希表有 bug」，而是「平均复杂度可被攻击」。同类漏洞：ReDoS（正则回溯指数级）、快排复杂度攻击（针对三点取中构造锯齿输入）、zip bomb、递归解析爆栈。
    共同点：某个资源维度没有上界，而它由攻击者控制。写处理不可信输入的代码时，逐个资源维度问「上界在哪、谁保证」。
  2. 高级一个哈希表在线上偶发 200ms 的延迟尖刺，怎么排查和消除？

    「偶发」+「尖刺」+ 哈希表，几乎可以直接指向 rehash：单次插入触发 O(n) 的重建（分配新表 + 重算所有键的桶 + 搬移 + 释放旧表）。

    ① 确认
    尖刺频率应该随元素数呈指数递减（每翻倍一次 rehash）；用 perf 抓尖刺时的栈，会看到 _M_rehash / resize / operator new。也可以打点记录 bucket_count() 的变化时刻与尖刺时刻对齐。
    别忽略另外两个嫌疑
    ① 如果表很大且元素是单独 malloc 的节点（unordered_map），rehash 时的内存分配器行为（可能触发 mmap、页错误、甚至 THP 整理）比搬移本身更贵；② 释放旧表时的大量 free 也是一笔。用 heap profiler 确认。

    按性价比排序的消除手段：

    ① 预留容量（首选）
    启动时 reserve(峰值)，运行期永不扩容——把摊销 O(1) 变成最坏 O(1)。
    注意 reserve(n) 的参数是元素数（内部按 n / max_load_factor 算桶数），而 rehash(n) 的参数是桶数——这是高频误用。
    ② 分片
    拆成 N 个小表（shard = hash(k) % N），rehash 只影响 1/N 的数据，单次停顿降到 1/N。顺带还能降低锁竞争。代价是跨片操作（如全表遍历、批量原子操作）变复杂。
    ③ 渐进式 rehash（Redis 的做法）
    双表并存，rehashidx 逐步推进：查找/删除先查旧表再查新表，插入一律写新表（保证旧表只减不增），每次操作顺带搬 1 个桶。
    单次最坏从 O(n) 降到 O(1)+一个桶。代价：过渡期内存双份，且每次操作要查两张表（常数变大）。
    ④ 换稳定结构
    std::map 永远 O(log n)、无抖动。平均更慢，但如果需求是「p99 稳定」而不是「均值最快」，这是对的选择。
    这是一笔通用的交易
    「用平均成本换尾延迟」——渐进式 rehash、GC 的增量回收、数据库的在线 DDL、LSM 的分层 compaction，全是同一笔交易。
    做决定前先确认目标是「均值」还是「p99」：扇出 100 次的服务里，单次 p99=200ms 意味着 63% 的用户请求会撞上它（见 复杂度与分析 §8.2）。
  3. 高级你要给一个高频交易系统选 key-value 容器，怎么决策？

    高频交易的核心约束是最坏延迟（p99.9）而不是平均延迟，这会让常规的「哈希表最快」结论完全翻转。

    先排除的：默认的 unordered_map
    三个理由：① rehash 造成不可预测的停顿；② 每次插入一次 malloc——malloc 自身的尾延迟不受控（可能触发 mmap、页错误、锁竞争）；③ 指针追逐导致 cache miss 不可预测。
    ① 首选：预分配的开放寻址表
    启动时 reserve 到峰值容量，运行期零分配、零 rehash。连续内存 + 位掩码，访问模式可预测。
    如果键是稠密小整数（instrument id、order id 段），直接用 std::vector 下标——真正的 O(1)，无哈希计算，最可预测。这一条最常被跳过，但往往是最优解。
    ② 元素少时用线性扫描的数组
    几十个以内（比如订阅的合约列表），vector<pair<K,V>> + 线性查找往往打败任何哈希表：连续内存、无哈希计算、无分支预测失败、可 SIMD。先量一下真实规模再谈结构。
    ③ 需要有序（价格档位、时间序）
    不要用哈希表。价格档位这类要 lower_bound 的场景用排序数组 + 二分（比 std::map 快得多，因为连续内存），或者干脆用按价格直接下标的数组（价格离散化后值域有限）。
    ④ 别忘了内存局部性之外的约束
    NUMA：表要分配在访问它的核所在的 NUMA 节点上；大页：大表用 hugepage 减少 TLB miss；禁用 THP 的整理（可能造成停顿）；预热：启动后先跑一遍把页真正映射进来（首次触碰的页错误也是尖刺）。
    见 低延迟编程 与 NUMA 与内存。
    决策顺序（这才是答案）
    ① 量真实规模和访问模式 → 可能根本不需要哈希表；② 列出硬约束（最坏延迟、有序性、单线程还是并发）；③ 消除所有运行期动态分配；④ 在真实数据和真实延迟分布上测，看 p99.9 而不是均值。
    「哪个容器快」是最后一个问题——前三步做对了，容器选择的影响反而变小。
  4. 高级把「哈希 → 桶」换成「哈希 → 机器」，会遇到什么新问题？

    核心新问题是：桶数（机器数）会变，而变化的代价是数据迁移而不是内存重分配。

    朴素取模的灾难
    node = hash(key) % N。N 从 3 变 4 时，约 N/(N+1) 的键都要迁移——缓存场景下命中率瞬间归零，全部打到后端 → 雪崩。
    对比单机哈希表：rehash 也要重算所有键，但那只是内存操作；分布式里这是跨网络搬 TB 级数据。
    一致性哈希
    把哈希值域看成一个环，节点落在环上若干点，key 顺时针找到的第一个节点就是归属。加节点时只有它接管的那段键要迁移，迁移量 ≈ 1/N。
    虚拟节点为什么必需
    每台机器只占一个点时，N 台把环切成 N 段，段长方差很大——某台机器可能负责 3 倍于平均的键。虚拟节点（每机 100–200 个点）用大数定律把方差压下来。
    额外好处：可以按机器性能分配不同数量的虚拟节点，实现加权分片。
    方案迁移量特点
    取模≈N/(N+1)仅适合节点数固定
    一致性哈希+虚节点≈1/NCassandra、Dynamo、memcached
    Rendezvous（HRW）≈1/N实现更简单，无需维护环
    Jump Consistent Hash最优但只支持末尾增删节点
    固定槽位可控Redis Cluster（16384 槽）
    Redis Cluster 的选择值得单独学
    它不用一致性哈希，而是把键空间固定切成 16384 槽（CRC16(key) % 16384），再把槽分配给节点。
    好处是迁移的粒度和进度完全可控可观测——你能确切知道「槽 5000 正在从 A 迁到 B」，能暂停、能回滚、能监控进度。一致性哈希的迁移是隐式的，出问题很难定位。
    代价是多了一层槽→节点的映射要维护和同步。这是「显式的间接层」换「可运维性」的典型选择——在分布式系统里，可运维性常常比理论最优更值钱。
    还有两个必须处理的问题
    热点键：一致性哈希解决的是「键的数量」均衡，不解决「访问量」均衡。一个爆款商品的 key 会打爆它所在的那台机器——要靠本地缓存、key 加随机后缀分散、或单独处理热点。
    迁移期间的一致性：数据正在从 A 搬到 B 时，读写该去哪？Redis Cluster 用 ASK/MOVED 重定向，本质是让客户端参与解决。见 存储与数据架构。
