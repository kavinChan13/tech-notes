哈希表内核

哈希表是「O(1)」这个说法被滥用得最严重的地方。它的 O(1) 是期望、摊销、且依赖哈希函数质量的——三个限定词各自对应一类真实事故：碰撞攻击、rehash 停顿、哈希函数选错。这一篇把两种冲突解决方案、Swiss Table 的 SIMD 技巧、rehash 的尾延迟以及 Hash-DoS 讲清，让你知道 unordered_map 什么时候不该用。

本质：用值算地址

以及那个 O(1) 的三个限定词

数组的下标访问是 O(1)，因为地址可以直接算出来。哈希表想把这个能力推广到任意类型的键：先用哈希函数把键映射成一个整数，再用这个整数当下标。

位置 = h(key) mod 桶数 代价：键空间（几乎无限）→ 桶空间（有限）必然产生冲突 哈希表的全部工程复杂度都在「怎么处理冲突」上
「哈希表是 O(1)」的三个限定词，每一个都对应一类真实故障：
  • 期望（expected）——假设哈希值均匀分布。假设不成立时退化到 O(n)，而攻击者可以主动制造这个不成立（§7 的 Hash-DoS）。
  • 摊销（amortized）——单次操作可能触发 rehash，代价 O(n)。这是尾延迟来源（§6.3）。
  • 不含哈希计算——渐进分析把 h(key) 当成 O(1)，但对长字符串它是 O(len)。键很长时哈希计算本身就是瓶颈。
面试里能主动说出这三条，比背「平均 O(1) 最坏 O(n)」有价值得多。
哈希表像图书馆按书名首字母分区上架。要找《算法导论》，你不用扫遍全馆——直接走到「S」区（h("算法导论") = S），只在那一小片找。

三个问题也都在这个类比里：
· 分区不均：如果馆藏 80% 是「S」开头的书，S 区会挤成一条长龙，退化成线性查找。好的哈希函数就是好的分区规则。
· 扩馆：书太多要换更大的馆，得把所有书重新按新规则上架一遍——这就是 rehash，那天谁来借书都得等。
· 恶意读者：有人专门捐赠 S 开头的书把 S 区搞垮，这就是碰撞攻击。防御办法不是换书架，而是让分区规则每次开馆时随机变化，让他猜不到该捐什么。

雪崩效应为什么重要：考虑一个坏哈希 h(x) = x（恒等）。插入 1, 2, 3, …, n 时，用取模分桶尚可（均匀），但用位掩码分桶时只看低位——如果键都是 8 的倍数（比如指针、页对齐的地址），低 3 位恒为 0，所有键挤进 1/8 的桶。
而且在开放寻址下，相邻的哈希值会形成连续占用（聚簇），探测长度急剧上升。所以「均匀」不够，还要「打散」。

不要用密码学哈希（SHA、MD5）做哈希表的键映射——慢几十倍，而哈希表根本不需要「抗第二原像」这种强度。需要抗攻击时用 SipHash（专为此设计，只需抗「密钥未知时无法构造碰撞」）。
反过来也别用非抗碰撞的快哈希去做内容寻址或去重指纹——xxHash 有意不抗碰撞，攻击者能轻易构造相同指纹。「选哈希函数」的第一个问题是「输入是否可信」。

2.2 std::hash 的实现与陷阱

类型libstdc++ 的 std::hash问题
int / 整型恒等函数（直接返回值）零雪崩。配位掩码桶时低位倾斜的键会严重聚簇
T* 指针reinterpret 成整数低位恒为 0（对齐），同上
std::stringMurmurHash 变体（逐字节）O(len)；无随机种子 → 可被攻击
float / double按位哈希（0 特判）NaN != NaN 导致 NaN 键永远查不到
std::pair / tuple没有特化编译报错，必须自己写
整型的 std::hash 是恒等函数，这是个必须知道的实现细节。libstdc++ 的 unordered_map 用素数桶数取模，所以恒等哈希勉强可用。但如果你自己写一个2 的幂桶数 + 位掩码的哈希表（性能考虑，见 §2.3），再配上 std::hash<int>，那么： 
// 键都是 1000 的倍数（比如按 1000 递增的 ID）
// 桶数 = 1024，掩码 = 0x3FF
1000 & 0x3FF = 1000
2000 & 0x3FF = 976
3000 & 0x3FF = 952   // 步长恒为 -24 → 聚簇成一段
修复办法：自己加一层混淆（finalizer），把整数打散： 
// splitmix64 的 finalizer，3 条指令，雪崩效果很好
inline uint64_t mix(uint64_t x) {
    x += 0x9E3779B97F4A7C15ULL;
    x = (x ^ (x >> 30)) * 0xBF58476D1CE4E5B9ULL;
    x = (x ^ (x >> 27)) * 0x94D049BB133111EBULL;
    return x ^ (x >> 31);
}
absl::flat_hash_map 和大多数现代实现内置了这层混淆，所以直接用它们不必操心。

这是一个把复杂度从 A 转移到 B 的经典取舍：
  • 素数取模把「保证分布」的责任放在桶映射上，于是哈希函数可以很弱（甚至恒等）。代价是每次操作一次整数除法。
  • 位掩码把责任放在哈希函数上，桶映射变成 1 周期。代价是哈希函数必须够好，否则崩得很惨。
现代实现全部选后者——因为好的非密码学哈希（xxHash、wyhash）已经足够快且雪崩充分，用 1 条 AND 换 20 周期的除法明显划算。但这也意味着：自己造哈希表时，绝不能配一个弱哈希函数。

还有一种折中：Fibonacci 哈希（(h * 0x9E3779B97F4A7C15) >> (64 - log2(buckets))）——一次乘法 + 移位，用高位而不是低位，兼顾速度与打散。

2.4 组合多个字段

std::hash 没有 pair / tuple 的特化，必须自己写。而「怎么组合」有对错之分：

❌ 三种常见错法
// ① 异或：对称 → (a,b) 与 (b,a) 碰撞
return h1(p.first) ^ h2(p.second);
// 而且 a==b 时结果恒为 0！

// ② 相加：同样对称，且易碰撞
return h1(p.first) + h2(p.second);

// ③ 简单移位：高位信息丢失
return (h1(p.first) << 32) | h2(p.second);
// 若 h2 值域大于 32 位就冲突
✅ Boost 风格 hash_combine
template <class T>
inline void hash_combine(size_t& seed, const T& v) {
    seed ^= std::hash<T>{}(v)
          + 0x9E3779B97F4A7C15ULL   // 黄金比例常数
          + (seed << 6) + (seed >> 2);
}

struct PairHash {
    template <class A, class B>
    size_t operator()(const std::pair<A,B>& p) const {
        size_t seed = 0;
        hash_combine(seed, p.first);
        hash_combine(seed, p.second);
        return seed;   // 顺序敏感、有雪崩
    }
};
异或的问题值得记牢，因为它是最常见的错法：异或是对称且自逆的——h(a) ^ h(b) == h(b) ^ h(a)（(1,2) 和 (2,1) 必然碰撞），而且 a == b 时结果恒为 0（所有对角元素挤进一个桶）。
如果不想自己写，C++ 里有两条捷径：① 用 absl::flat_hash_map —— abseil 为 pair/tuple/容器都提供了正确的 AbslHashValue；② 把多字段拼成一个字符串或结构体，对其字节序列整体做 xxHash（注意结构体有 padding，要么 #pragma pack，要么逐字段拼）。
对结构体做「整体字节哈希」有个隐藏坑：padding 字节的内容是未定义的。两个逻辑相等的对象可能因为 padding 里的垃圾值不同而哈希不同。所以要么保证结构体无 padding（static_assert(sizeof(S) == 各字段之和)），要么逐字段 combine。

3.2 标准为什么逼出这个实现

C++ 标准对 unordered_map 定了几条要求，它们联合起来排除了开放寻址：

标准要求后果
引用与指针在 rehash 后仍有效（只有迭代器失效）元素必须单独分配在堆上，不能存在连续数组里（数组重分配会移动元素）
提供 bucket_count() / bucket(key) / bucket_size(n)必须真的有「桶」这个概念，暴露了拉链结构
提供局部迭代器 begin(n) / end(n)（遍历第 n 个桶）同上
max_load_factor 可设为 > 1开放寻址的负载因子不可能超过 1
全表遍历 O(size)节点必须串成一条全局链表
插入不使已存在元素的引用失效禁止 Robin Hood 这类「移动已有元素」的方案
这是标准库设计里一个著名的教训：C++11 定 unordered_map 接口时，把太多实现细节写进了契约（桶接口、引用稳定性、负载因子 > 1）。结果是任何符合标准的实现都必须是拉链法，无法换成更快的开放寻址。

这就是为什么 abseil、folly、Boost.Unordered（新版）都提供不完全兼容标准接口的替代品——它们主动放弃引用稳定性来换 2–3 倍性能。「接口暴露了多少实现细节」直接决定了未来的优化空间，这条经验对设计任何库都成立。
拉链法也有它真正的优势，不是只有劣势：
  • 引用稳定：可以安全地持有 &map[key] 跨插入操作。这在缓存、对象池、图结构里非常有用。
  • 负载因子可 > 1：内存吃紧时可以让链表长一点，不必扩容。
  • 删除简单：直接摘链，没有开放寻址的墓碑问题（§4.4）。
  • 可以按桶退化成树：Java 8 的 HashMap 在单桶超过 8 个元素时把链表转成红黑树，把最坏从 O(n) 降到 O(log n)——这是拉链法独有的能力。
所以选型不是「开放寻址总是更好」，而是「你需不需要引用稳定性」（§8）。

开放寻址

所有元素放在一个连续数组里

4.1 线性探测与聚簇

开放寻址不用链表：冲突时就顺着数组往后找下一个空位。

// 线性探测的查找（概念版）
int find_slot(const Key& k) {
    size_t i = hash(k) & mask;
    while (slots[i].state != EMPTY) {
        if (slots[i].state == FULL && slots[i].key == k) return i;
        i = (i + 1) & mask;      // 往后走一格
    }
    return -1;   // 碰到 EMPTY 说明不存在
}
为什么线性探测反而是最快的——尽管它理论上聚簇最严重：因为它的探测序列是连续地址，完全符合 cache line 和硬件预取的模式。探测 8 个槽位可能只需 1 次 cache miss；而二次探测或双重哈希的跳跃式探测，每一步都可能是一次 miss。

这是「渐进相同、常数不同」的又一个案例：理论上「聚簇更少」的方案，实测更慢。

4.2 二次探测与双重哈希

探测方式第 i 次探测位置聚簇cache 友好
线性探测h + i主聚簇（primary clustering）最好
二次探测h + i² 或 h + (i+i²)/2次聚簇（同 h 的键仍走同一序列）中
双重哈希h1 + i·h2(k)几乎无最差（每步随机跳）
Robin Hood（§4.3）线性，但会抢位线性，但方差极小最好
二次探测有个容易忽略的正确性要求：探测序列必须能覆盖所有槽位，否则表还没满就找不到空位（死循环或误判为满）。
常用做法：桶数取 2 的幂，探测式子用 h + (i + i²)/2——它能保证遍历完所有 2^k 个槽位。用朴素的 h + i² 配 2 的幂桶数只能覆盖约一半槽位。这类「看起来能跑但在高负载下出错」的 bug 极难调试。

4.3 Robin Hood

Robin Hood hashing（罗宾汉哈希）是对线性探测的一个巧妙改进：插入时如果发现「当前位置的占用者比我更接近它的理想位置」，就把它踢出来，自己占进去，然后继续为被踢者找位置。

核心不变式：定义每个元素的 probe distance（实际位置 − 理想位置）。Robin Hood 保证探测序列上的 probe distance 单调不减。

由此得到两个好处：
  • 查找可以提前终止：探测到某个槽位时，如果它的 probe distance 已经小于当前查找的距离，就说明目标不可能在后面——因为如果它在，它的距离会更大，早该出现在这里。未命中查找不必走到 EMPTY。
  • 探测长度的方差极小：它不降低平均探测长度（那由负载因子决定），但把「个别元素探测几十次」这种长尾削平了。这直接改善 p99。
名字来自「劫富济贫」：抢劫「富人」（离家近、探测距离短的元素）去帮助「穷人」（离家远的）。

总的财富（平均探测长度）不变——那是由房子有多挤（负载因子）决定的，谁也变不了。但分配变均匀了：没有人特别惨。这正是「不改善均值但削平长尾」的典型手法，和限流里的对冲请求、GC 里的增量回收是同一类思路。
Robin Hood 的代价：插入时要移动已有元素，这直接违反 C++ 标准对 unordered_map 的「引用稳定性」要求，所以标准库不能用它。Rust 的 HashMap 曾用 Robin Hood（1.36 之前），后来改成了 Swiss Table（hashbrown）。
它仍是自己造哈希表时的好选择——尤其是对 p99 敏感的场景。

4.4 删除的墓碑问题

开放寻址的删除不能简单地把槽位标成 EMPTY——那会切断探测链：

❌ 直接标 EMPTY
// 插入顺序：A→槽3, B→槽3(冲突,占4), C→槽3(冲突,占5)
// 槽：  [.., .., .., A, B, C, ..]

// 删除 B，标成 EMPTY：
// 槽：  [.., .., .., A, _, C, ..]

// 现在查找 C：从槽3开始 → A 不匹配 → 槽4 是 EMPTY
// → 判定「不存在」并返回
// 但 C 明明在槽5！探测链被切断了
✅ 墓碑（tombstone / DELETED）
// 三态：EMPTY / FULL / DELETED
// 删除 B，标成 DELETED：
// 槽：  [.., .., .., A, X, C, ..]   X=墓碑

// 查找：遇到 DELETED 继续往下探测（不终止）
// 插入：遇到 DELETED 可以复用该槽位
// 只有遇到 EMPTY 才判定「不存在」
墓碑本身又带来一个问题：墓碑不减少「探测长度」，只减少「元素个数」。一个反复插入删除的表，墓碑会不断累积，导致：
  • size() 很小但探测长度很长（有效负载因子被墓碑撑高）；
  • 极端情况下整个表变成墓碑，任何未命中查找都要扫全表 → O(n)。
标准解法：把墓碑计入负载因子（load = (size + tombstones) / capacity），超过阈值时触发 rehash——rehash 会自然清掉所有墓碑。

这也是开放寻址在「写多删多」工作负载下的固有弱点。这类场景下拉链法（删除只是摘链，无残留）反而更稳。选型时要问的不只是「读写比」，还有「删除频率」。

Swiss Table

abseil / Rust hashbrown 的做法：用 SIMD 一次探测 16 个槽

5.1 控制字节与 SIMD 探测

Swiss Table 的核心创新是把元数据和数据分开存放：一个紧凑的「控制字节数组」+ 一个「槽位数组」。

哈希值被拆成两部分用：
  • H1（高位，除 H2 外）→ 决定起始的「组」（group）位置。
  • H2（7 位）→ 存进控制字节，作为快速筛选的指纹。
这个设计的精髓在于：把「大概率排除」和「精确确认」分成两步，前者在极小的连续数组上用 SIMD 批量做，后者只对少数候选执行。

它和布隆过滤器的思路完全同源——都是用一个小的、可能假阳性的摘要挡住绝大多数无效访问。区别是布隆过滤器不存真实数据，Swiss Table 的控制字节后面就跟着真数据。

5.3 代价：迭代器与引用失效

absl::flat_hash_map 的元素直接存在数组里，所以扩容时元素会被移动——&map[key] 拿到的引用会在任何可能触发 rehash 的操作后失效。这和 std::unordered_map 的保证完全不同。 
// ❌ 在 flat_hash_map 上是悬垂引用
auto& v = map["a"];
map["b"] = 1;        // 可能扩容 → v 悬垂
v = 2;                // use-after-free

// ✅ 需要引用稳定时用 node_hash_map（abseil 的拉链版）
absl::node_hash_map<std::string, int> m;   // 引用稳定，但慢一些
迁移 unordered_map → flat_hash_map 时，这是唯一需要审查的地方：全仓库搜「持有 map 元素的引用/指针跨越后续 map 操作」的代码。ASan 能抓到这类问题（heap-use-after-free），把它挂进 CI 是必要的。
还有两个次要差异要注意：① flat_hash_map 要求 value 类型可移动（因为扩容要搬）；② 它的迭代顺序刻意随机化——abseil 故意让每次运行的顺序不同，防止代码依赖上遍历顺序（这是个好设计，但会暴露原本隐藏的顺序依赖 bug）。迁移后如果测试挂了，先怀疑是不是有代码依赖了遍历顺序。

为什么拉链法能容忍 α = 1 而开放寻址只能到 0.875：
  • 拉链法的 α 是「平均链长」。α = 1 意味着平均每桶 1 个元素，查找期望比较约 1.5 次——完全可接受，且 α 可以 > 1（链长 2、3 也还行）。
  • 开放寻址的 α 是「占用率」，探测长度是 1/(1−α) 量级。α = 0.9 时未命中要探测约 50 次，α → 1 时发散。而且 α 物理上不可能超过 1。
Swiss Table 之所以敢用 0.875（比经典建议的 0.7 高），是因为 SIMD 让「探测 16 个槽」的成本接近「探测 1 个槽」——它把探测长度的常数压得极低，于是可以承受更高的负载因子，从而省内存。这是一个漂亮的连锁收益。

6.2 增量式 rehash

一次性 rehash 是 O(n)：分配新表 + 重算所有键的桶 + 搬移。n 很大时这是几十甚至几百毫秒的停顿。Redis 的做法是把它切碎：

一次性 rehash 像搬家时请一天假、把所有东西一次搬完——那一天什么也干不了。渐进式 rehash 像每天下班顺手带一箱过去：总工作量一样，但没有哪一天被完全占用。

代价也很真实：过渡期你有两套房子的租金（内存翻倍），而且找东西要两边都翻一遍（每次操作查两张表）。这就是「用平均成本换尾延迟」的标准交易——GC 的增量回收、数据库的在线 DDL、LSM 的分层 compaction 都是同一笔交易。

6.3 尾延迟

「摊销 O(1)」在均值上完美，但那次 O(n) 的 rehash 落在哪个请求上，那个请求就是 p99。对低延迟服务这是要命的。

哈希碰撞 DoS

把「平均 O(1)」变成「最坏 O(n)」的攻击

7.1 2011 年的事故

2011 年底的 28C3 大会上，Alexander Klink 和 Julian Wälde 公布了一个影响几乎所有 Web 框架的漏洞：

攻击原理：Web 框架把 HTTP POST 的表单字段、查询参数、JSON 键放进哈希表。攻击者预先计算出大量哈希值相同的字符串，作为参数名发过去。这些键全部落进同一个桶，哈希表退化成链表：
  • 插入 n 个碰撞键的总代价从 O(n) 变成 O(n²)（每次插入都要遍历整条链查重）。
  • 当时报告的数字：几十 KB 到几 MB 的 POST 请求就能让一个 CPU 核跑满数分钟。
受影响的包括 PHP、Java（Tomcat/Jetty）、Python、Ruby、ASP.NET、V8/Node.js——因为它们都用了确定性的、公开的哈希函数。攻击者离线算好碰撞集，成本几乎为零。
这个事故的教训不在「哈希表有 bug」，而在「平均复杂度可被攻击」这个一般性原理（参见 复杂度与分析 §4.5）。同一类漏洞还有：
  • ReDoS：正则回溯的最坏是指数级，构造特定输入可打满 CPU。
  • 快排复杂度攻击：针对「三点取中」构造锯齿输入，把 O(n log n) 拖成 O(n²)。
  • zip bomb / 解压炸弹：解压比无上限。
  • 递归解析爆栈：深度嵌套的 JSON/XML（见 递归与分治）。
共同点：某个资源维度没有上界，而它由攻击者控制。写「处理不可信输入」的代码时，应该逐个资源维度问「上界在哪、谁保证」。

7.2 SipHash 与随机种子

修复方案不是换数据结构，而是让攻击者算不出碰撞：

C++ 的 std::hash 没有随机化，这是标准层面的问题：std::hash<std::string> 对同一字符串在同一实现上永远返回同一值，而算法是公开的。

所以直接把不可信输入（HTTP 参数名、JSON 键、上传的字段名）当键放进 std::unordered_map 是有风险的。三种修法：

    static const uint64_t seed;   // 进程启动时从 random_device 取
    size_t operator()(std::string_view s) const {
        return siphash13(seed, s.data(), s.size());
    }
};
std::unordered_map<std::string, V, SeededHash> m;

// ② 换 absl::flat_hash_map（内置随机种子）

// ③ 限制键的数量与长度（纵深防御，应该同时做）
if (params.size() > kMaxParams) return reject();
③ 值得单独强调：即使哈希是安全的，也应该限制参数个数——这挡住的是一整类「资源无上界」问题，不只是哈希碰撞。
Java 的选择（转红黑树）和其他语言（换哈希）代表两种不同的哲学：Java 改的是「最坏复杂度」（O(n) → O(log n)，攻击仍能发生但危害可控），其他语言改的是「攻击可行性」（最坏仍是 O(n)，但攻击者构造不出来）。
两者都有效，可以叠加。转树的额外好处是对非恶意的坏哈希也有效（比如用户自己写了个糟糕的 hashCode）。

分布式场景

同一个哈希，换成分片的地址

把「哈希 → 桶」换成「哈希 → 机器」，就得到了分布式系统的分片（sharding）。但这时朴素的取模会出大问题：

❌ 朴素取模分片
node = hash(key) % N;

// N 从 3 变成 4（加一台机器）时：
// hash=10 → 10%3=1  变成  10%4=2
// hash=11 → 11%3=2  变成  11%4=3
// ...
// 约 N/(N+1) 的键都要迁移
// 缓存场景 → 命中率瞬间归零 → 雪崩
✅ 一致性哈希
// 把 hash 值域看成一个环
// 每个节点（及其虚拟节点）落在环上若干点
// key 顺时针找到的第一个节点就是它的归属

// 加一台机器时：只有它接管的那段键要迁移
// 迁移量 ≈ 1/N，而不是 N/(N+1)

// 虚拟节点（每台机器 100~200 个）
// 用来解决环上分布不均导致的负载倾斜
虚拟节点为什么必需：如果每台机器只在环上占一个点，N 台机器把环切成 N 段，段长的方差很大——某台机器可能负责 3 倍于平均的键。虚拟节点（每台机器散布 100–200 个点）让每台机器负责很多小段，由大数定律把方差压下来。
虚拟节点还带来一个额外好处：可以按机器性能分配不同数量的虚拟节点，实现加权分片。

好处是迁移的粒度和进度完全可控可观测——你能确切知道「槽 5000 正在从 A 迁到 B」，而一致性哈希的迁移是隐式的。代价是多了一层槽到节点的映射需要维护和同步。

  1. 基础哈希表的查找是 O(1) 吗？把这句话说完整。

    不完整。准确说法是：期望、摊销 O(1)，且不含哈希计算本身；最坏 O(n)。三个限定词各自对应一类真实故障。

    ① 期望（expected）
    建立在「哈希值均匀分布」的假设上。假设不成立就退化到 O(n)——而攻击者可以主动制造这个不成立（Hash-DoS）。
    ② 摊销（amortized）
    单次插入可能触发 rehash，代价 O(n)。均值上无所谓，但那次停顿落在哪个请求上，那个请求就是 p99。
    ③ 不含哈希计算
    渐进分析把 h(key) 当 O(1)，但对长字符串它是 O(len)。键很长时哈希计算本身就是瓶颈。
    和红黑树对比时该怎么说
    std::map 是确定性的 O(log n)：没有假设、没有抖动、没有攻击面。所以「哈希表比树快」只在平均意义上成立；需要稳定最坏延迟时树反而是对的选择。
    而且 n 小时（几十到几百）树常常更快——log n 只有 6~8，而哈希要算 hash + 一次随机地址访问。
  2. 基础解决哈希冲突有哪两大类方法？各自的优缺点？

  3. 基础什么是负载因子？它为什么决定了扩容时机？

    所以阈值差别很大
    unordered_map（拉链）默认 1.0；flat_hash_map（开放寻址）约 0.875；Java 0.75；Python 约 0.66。
    「未命中恶化更快」的工程含义
    以「查不到」为主的负载——缓存 miss 检查、去重判断、存在性验证——对负载因子更敏感。这类场景该把阈值设更低，或前面加一层布隆过滤器挡掉不存在的键。
    Swiss Table 为什么敢用 0.875
    因为 SIMD 让「探测 16 个槽」的成本接近「探测 1 个槽」——它把探测长度的常数压得极低，于是能承受更高负载因子，从而省内存。这是个漂亮的连锁收益。
  4. 基础为什么 std::unordered_map 的 std::hash<int> 是恒等函数也能用？什么时候会出问题？

    因为 libstdc++ 的 unordered_map 用素数桶数取模。取模会把哈希值的高位信息「搅」进结果，所以即使哈希函数很弱（恒等），分布也还算均匀。

    出问题的场合：自己造 2 的幂 + 位掩码的表
    位掩码 h & (n-1) 只用低位。此时恒等哈希会暴露键的低位规律：
    // 键都是 1000 的倍数，桶数 1024
1000 & 0x3FF = 1000
2000 & 0x3FF = 976
3000 & 0x3FF = 952    // 步长恒定 → 聚簇成一段
    指针做键更糟——对齐让低位恒为 0。
    这是一个责任转移的取舍
    素数取模把「保证分布」的责任放在桶映射上（哈希函数可以弱），代价是每次一次整数除法（~20 周期）。
    位掩码把责任放在哈希函数上，桶映射只需 1 周期，但哈希函数必须有雪崩效应。
    现代实现全选后者——因为好的快哈希（xxHash、wyhash）已经足够。
    修法
    自己加一层混淆（splitmix64 的 finalizer，3 条指令，雪崩很好）：
    x += 0x9E3779B97F4A7C15;
x = (x ^ (x>>30)) * 0xBF58476D1CE4E5B9;
x = (x ^ (x>>27)) * 0x94D049BB133111EB;
return x ^ (x>>31);
    或者直接用 absl::flat_hash_map——它内置了这层混淆。

10.2 中级（区分熟练度）

  1. 中级为什么 std::unordered_map 必须是拉链法实现？标准做了什么约束？

    标准把太多实现细节写进了接口契约，这些要求联合起来排除了开放寻址：

    标准要求后果
    引用与指针在 rehash 后仍有效元素必须单独堆分配，不能存在连续数组里
    bucket_count() / bucket(key) / 局部迭代器 begin(n)必须真的有「桶」，暴露了拉链结构
    max_load_factor 可 > 1开放寻址的负载因子物理上不可能 > 1
    全表遍历 O(size)节点必须串成一条全局链表（否则要跳过空桶 → O(桶数)）
    插入不使已存在元素的引用失效禁止 Robin Hood 这类「移动已有元素」的方案
    这是标准库设计的一个著名教训
    C++11 定接口时把桶接口、引用稳定性、负载因子 > 1 都写进了契约，结果任何符合标准的实现都必须是拉链法，未来无法换成更快的方案。
    这就是 abseil、folly、Boost.Unordered 新版都提供不完全兼容标准接口的替代品的原因——它们主动放弃引用稳定性换 2–3 倍性能。
    「接口暴露了多少实现细节」直接决定未来的优化空间——这条经验对设计任何库都成立。
    但拉链法也有真优势
    ① 引用稳定（可安全持有 &map[k]，在缓存/对象池/图结构里很有用）；② 负载因子可 > 1（内存吃紧时不必扩容）；③ 删除简单，无墓碑；④ 可按桶退化成树——Java 8 单桶超 8 个转红黑树，把最坏从 O(n) 降到 O(log n)，这是拉链法独有的能力。
  2. 中级开放寻址的删除为什么需要「墓碑」？墓碑又带来什么问题？

    因为直接标 EMPTY 会切断探测链：

    // A→槽3, B→槽3冲突占4, C→槽3冲突占5
// 槽: [.., .., .., A, B, C, ..]
// 删 B 标 EMPTY → [.., .., .., A, _, C, ..]
// 查 C：槽3(A 不匹配) → 槽4 是 EMPTY → 判定「不存在」
// 但 C 明明在槽5！
    墓碑（三态）
    状态改为 EMPTY / FULL / DELETED：
    · 查找遇到 DELETED 继续探测（不终止）
    · 插入遇到 DELETED 可以复用该槽
    · 只有遇到 EMPTY 才判定不存在
    墓碑带来的新问题
    墓碑不减少探测长度，只减少元素个数。反复插入删除的表会不断累积墓碑，导致：
    · size() 很小但探测很长（有效负载因子被墓碑撑高）
    · 极端情况整表全是墓碑 → 任何未命中查找都要扫全表 → O(n)
    标准解法
    把墓碑计入负载因子：load = (size + tombstones) / capacity，超阈值就 rehash——rehash 会自然清掉所有墓碑。
    选型含义
    这是开放寻址在「写多删多」负载下的固有弱点。这类场景拉链法反而更稳（删除只是摘链，无残留）。
    选型时要问的不只是读写比，还有删除频率——这一点经常被忽略。
  3. 中级Swiss Table（absl::flat_hash_map）为什么比 unordered_map 快 2–3 倍？

    核心创新是元数据与数据分离：一个紧凑的「控制字节数组」（每槽 1 字节）+ 一个槽位数组。哈希值拆成两部分用：H1 定位组，H2（7 位）存进控制字节当指纹。

    m = _mm_movemask_epi8(_mm_cmpeq_epi8(ctrl, set1(H2))) 一条 SIMD 指令比较 16 个控制字节 → 得到 16 位掩码 只对掩码里的位去访问真正的槽位 H2 有 7 位 ⟹ 假阳性率约 1/128 ⟹ 通常只需比较 1 次完整 key
    关键是「探测」和「比较」解耦
    传统开放寻址每探测一个槽都要：访问槽位（可能 cache miss）+ 比较完整 key（string 要 memcmp）。
    Swiss Table 的探测发生在极小的连续元数据数组上——16 字节只占 1/4 条 cache line，一次 miss 能拿到 64 个槽的元信息。
    但 2–3 倍不来自单个技巧，是七项累积
    连续内存（vs 节点散落）、位掩码（vs 素数取模的整数除法 ~20 周期）、1 字节元数据（vs 每元素 ~32 B 额外内存）、SIMD 筛选、内置哈希混淆、仅扩容时分配、更高的负载因子。
    所以「只把 std::hash 换成 xxHash」提升有限——真正的瓶颈是内存布局和分配。
    代价：引用与迭代器失效
    元素直接存在数组里，扩容会移动元素：
    auto& v = map["a"];
map["b"] = 1;   // 可能扩容 → v 悬垂
v = 2;           // use-after-free
    需要引用稳定就用 absl::node_hash_map。迁移时唯一要审查的就是这一点——全仓库搜「持有 map 元素引用跨越后续 map 操作」，并把 ASan 挂进 CI。
    还有两个次要差异
    value 必须可移动；迭代顺序刻意随机化（防止代码依赖遍历顺序）——迁移后测试挂了，先怀疑是不是有隐藏的顺序依赖。
    同源思想
    控制字节 = 一个小的、可能假阳性的摘要，用来挡住绝大多数无效访问——这和布隆过滤器完全同源。区别只是布隆不存真实数据。
  4. 中级自己给 std::pair 写 hasher，为什么不能用异或组合？

    因为异或是对称且自逆的，会产生两类系统性碰撞：

    ① 对称 → 顺序信息丢失
    h(a) ^ h(b) == h(b) ^ h(a) ⟹ (1,2) 和 (2,1) 必然碰撞。用 pair 表示「有向边」或「坐标」时这是灾难。
    ② 自逆 → 对角线全归一桶
    a == b 时 h(a) ^ h(a) == 0 ⟹ 所有 (x, x) 挤进同一个桶。

    相加也有同样的对称问题；简单移位 (h1 << 32) | h2 在 h2 超过 32 位时冲突。

    正确写法：Boost 风格 hash_combine
    template <class T>
void hash_combine(size_t& seed, const T& v) {
    seed ^= std::hash<T>{}(v)
          + 0x9E3779B97F4A7C15ULL       // 黄金比例常数
          + (seed << 6) + (seed >> 2);   // 混入已有 seed
}
    它顺序敏感且有雪崩效应。
    两条捷径
    ① 用 absl::flat_hash_map——abseil 为 pair/tuple/容器都提供了正确的 AbslHashValue；② 逐字段拼成字节序列后整体 xxHash。
    整体字节哈希的隐藏坑
    结构体的 padding 字节内容是未定义的——两个逻辑相等的对象可能因 padding 里的垃圾值不同而哈希不同。要么 static_assert 确认无 padding，要么逐字段 combine。

10.3 高级（体现深度）

  1. 高级什么是 Hash-DoS？为什么 C++ 的 std::unordered_map 有风险，怎么修？

    2011 年 28C3 公布的攻击：Web 框架把 HTTP 参数名 / JSON 键放进哈希表，攻击者预先离线算出大量哈希相同的字符串发过去，全部落进同一桶。

    插入 n 个碰撞键的总代价：O(n) → O(n²) （每次插入都要遍历整条链查重） 当时的数字：几十 KB ~ 几 MB 的 POST 就能打满一个 CPU 核数分钟

    受影响的有 PHP、Java、Python、Ruby、ASP.NET、V8——都因为用了确定性的、算法公开的哈希函数。

    C++ 的问题在标准层面
    std::hash<std::string> 没有随机化：同一字符串在同一实现上永远返回同一值，算法还是公开的。
    所以把不可信输入（参数名、JSON 键、上传字段名）直接当键放进 std::unordered_map 是有风险的。
    修法一 · 带随机种子的 hasher
    struct SeededHash {
    static const uint64_t seed;   // 启动时从 random_device 取
    size_t operator()(std::string_view s) const {
        return siphash13(seed, s.data(), s.size());
    }
};
    SipHash 的安全性正是「密钥未知时不可构造碰撞」——这是它相对 xxHash/Murmur 的唯一优势，也是它存在的理由。
    修法二 · 换 absl（内置随机种子）
    absl::flat_hash_map 自带进程级随机种子 + 哈希混淆。
    修法三 · 限制键数量与长度（必须同时做）
    if (params.size() > kMaxParams) reject();——即使哈希安全也该做。这挡住的是一整类「资源无上界」问题，不只哈希碰撞。
    Java 的另一条路
    Java 没换哈希，而是单桶超 8 个转红黑树。这改的是「最坏复杂度」（O(n)→O(log n)，攻击仍能发生但危害可控）；换哈希改的是「攻击可行性」（最坏仍 O(n) 但构造不出来）。
    两者可叠加。转树还对非恶意的坏哈希有效（比如用户自己写了糟糕的 hashCode）。
    一般性原理
    教训不是「哈希表有 bug」，而是「平均复杂度可被攻击」。同类漏洞：ReDoS（正则回溯指数级）、快排复杂度攻击（针对三点取中构造锯齿输入）、zip bomb、递归解析爆栈。
    共同点：某个资源维度没有上界，而它由攻击者控制。写处理不可信输入的代码时，逐个资源维度问「上界在哪、谁保证」。
  2. 高级一个哈希表在线上偶发 200ms 的延迟尖刺，怎么排查和消除？

    「偶发」+「尖刺」+ 哈希表，几乎可以直接指向 rehash：单次插入触发 O(n) 的重建（分配新表 + 重算所有键的桶 + 搬移 + 释放旧表）。

    ① 确认
    尖刺频率应该随元素数呈指数递减（每翻倍一次 rehash）；用 perf 抓尖刺时的栈，会看到 _M_rehash / resize / operator new。也可以打点记录 bucket_count() 的变化时刻与尖刺时刻对齐。
    别忽略另外两个嫌疑
    ① 如果表很大且元素是单独 malloc 的节点（unordered_map），rehash 时的内存分配器行为（可能触发 mmap、页错误、甚至 THP 整理）比搬移本身更贵；② 释放旧表时的大量 free 也是一笔。用 heap profiler 确认。

    按性价比排序的消除手段：

    ① 预留容量（首选）
    启动时 reserve(峰值)，运行期永不扩容——把摊销 O(1) 变成最坏 O(1)。
    注意 reserve(n) 的参数是元素数（内部按 n / max_load_factor 算桶数），而 rehash(n) 的参数是桶数——这是高频误用。
    ② 分片
    拆成 N 个小表（shard = hash(k) % N），rehash 只影响 1/N 的数据，单次停顿降到 1/N。顺带还能降低锁竞争。代价是跨片操作（如全表遍历、批量原子操作）变复杂。
    ③ 渐进式 rehash（Redis 的做法）
    双表并存，rehashidx 逐步推进：查找/删除先查旧表再查新表，插入一律写新表（保证旧表只减不增），每次操作顺带搬 1 个桶。
    单次最坏从 O(n) 降到 O(1)+一个桶。代价：过渡期内存双份，且每次操作要查两张表（常数变大）。
    ④ 换稳定结构
    std::map 永远 O(log n)、无抖动。平均更慢，但如果需求是「p99 稳定」而不是「均值最快」，这是对的选择。
    这是一笔通用的交易
    「用平均成本换尾延迟」——渐进式 rehash、GC 的增量回收、数据库的在线 DDL、LSM 的分层 compaction，全是同一笔交易。
    做决定前先确认目标是「均值」还是「p99」：扇出 100 次的服务里，单次 p99=200ms 意味着 63% 的用户请求会撞上它（见 复杂度与分析 §8.2）。
  3. 高级你要给一个高频交易系统选 key-value 容器，怎么决策？

    高频交易的核心约束是最坏延迟（p99.9）而不是平均延迟，这会让常规的「哈希表最快」结论完全翻转。

    先排除的：默认的 unordered_map
    三个理由：① rehash 造成不可预测的停顿；② 每次插入一次 malloc——malloc 自身的尾延迟不受控（可能触发 mmap、页错误、锁竞争）；③ 指针追逐导致 cache miss 不可预测。
    ① 首选：预分配的开放寻址表
    启动时 reserve 到峰值容量，运行期零分配、零 rehash。连续内存 + 位掩码，访问模式可预测。
    如果键是稠密小整数（instrument id、order id 段），直接用 std::vector 下标——真正的 O(1)，无哈希计算，最可预测。这一条最常被跳过，但往往是最优解。
    ② 元素少时用线性扫描的数组
    几十个以内（比如订阅的合约列表），vector<pair<K,V>> + 线性查找往往打败任何哈希表：连续内存、无哈希计算、无分支预测失败、可 SIMD。先量一下真实规模再谈结构。
    ③ 需要有序（价格档位、时间序）
    不要用哈希表。价格档位这类要 lower_bound 的场景用排序数组 + 二分（比 std::map 快得多，因为连续内存），或者干脆用按价格直接下标的数组（价格离散化后值域有限）。
    ④ 别忘了内存局部性之外的约束
    NUMA：表要分配在访问它的核所在的 NUMA 节点上；大页：大表用 hugepage 减少 TLB miss；禁用 THP 的整理（可能造成停顿）；预热：启动后先跑一遍把页真正映射进来（首次触碰的页错误也是尖刺）。
    见 低延迟编程 与 NUMA 与内存。
    决策顺序（这才是答案）
    ① 量真实规模和访问模式 → 可能根本不需要哈希表；② 列出硬约束（最坏延迟、有序性、单线程还是并发）；③ 消除所有运行期动态分配；④ 在真实数据和真实延迟分布上测，看 p99.9 而不是均值。
    「哪个容器快」是最后一个问题——前三步做对了，容器选择的影响反而变小。
  4. 高级把「哈希 → 桶」换成「哈希 → 机器」，会遇到什么新问题？

    核心新问题是：桶数（机器数）会变，而变化的代价是数据迁移而不是内存重分配。

    朴素取模的灾难
    node = hash(key) % N。N 从 3 变 4 时，约 N/(N+1) 的键都要迁移——缓存场景下命中率瞬间归零，全部打到后端 → 雪崩。
    对比单机哈希表：rehash 也要重算所有键，但那只是内存操作；分布式里这是跨网络搬 TB 级数据。
    一致性哈希
    把哈希值域看成一个环，节点落在环上若干点，key 顺时针找到的第一个节点就是归属。加节点时只有它接管的那段键要迁移，迁移量 ≈ 1/N。
    虚拟节点为什么必需
    每台机器只占一个点时，N 台把环切成 N 段，段长方差很大——某台机器可能负责 3 倍于平均的键。虚拟节点（每机 100–200 个点）用大数定律把方差压下来。
    额外好处：可以按机器性能分配不同数量的虚拟节点，实现加权分片。
    方案迁移量特点
    取模≈N/(N+1)仅适合节点数固定
    一致性哈希+虚节点≈1/NCassandra、Dynamo、memcached
    Rendezvous（HRW）≈1/N实现更简单，无需维护环
    Jump Consistent Hash最优但只支持末尾增删节点
    固定槽位可控Redis Cluster（16384 槽）
    Redis Cluster 的选择值得单独学
    它不用一致性哈希，而是把键空间固定切成 16384 槽（CRC16(key) % 16384），再把槽分配给节点。
    好处是迁移的粒度和进度完全可控可观测——你能确切知道「槽 5000 正在从 A 迁到 B」，能暂停、能回滚、能监控进度。一致性哈希的迁移是隐式的，出问题很难定位。
    代价是多了一层槽→节点的映射要维护和同步。这是「显式的间接层」换「可运维性」的典型选择——在分布式系统里，可运维性常常比理论最优更值钱。
    还有两个必须处理的问题
    热点键：一致性哈希解决的是「键的数量」均衡，不解决「访问量」均衡。一个爆款商品的 key 会打爆它所在的那台机器——要靠本地缓存、key 加随机后缀分散、或单独处理热点。
    迁移期间的一致性：数据正在从 A 搬到 B 时，读写该去哪？Redis Cluster 用 ASK/MOVED 重定向，本质是让客户端参与解决。见 存储与数据架构。
