堆与 Top-K

堆是刻意做得「不够有序」的结构：它只承诺「根是最值」，放弃全序，换来 O(log n) 的插入删除和 O(1) 的取最值。理解这个取舍，就知道它什么时候够用（Top-K、调度、归并）、什么时候不够（要删任意元素、要中位数、要有序遍历）。这一篇把建堆的 Θ(n) 证明、priority_queue 的三个坑、Top-K 的四种解法，以及生产里的定时器选型讲透。

01

本质：只承诺最值

放弃全序，换来插删的 O(log n)

排序给你全序，代价是 O(n log n) 且插入新元素要 O(n)。哈希表给你 O(1) 查找，代价是完全无序。堆在两者之间：它只维护一条约束——「父节点不小于子节点」。

堆的性质（大顶堆）：一棵完全二叉树，且每个节点的值 ≥ 它所有子节点的值。

注意它没有承诺的东西：
  • 兄弟之间没有任何顺序关系（左孩子可能比右孩子大，也可能小）。
  • 第二大的元素只知道「一定是根的某个孩子」，但不知道是哪个。
  • 中序遍历不得到有序序列（这和二叉搜索树完全不同）。
正是这些「不承诺」让插入删除只需 O(log n)——只要沿一条路径调整，不必维护全局顺序。

堆像急诊室的分诊台。它不给所有病人排一个精确的一到一百的号——那太贵且没必要。它只保证一件事：下一个进诊室的一定是最危急的那个。

来了新病人？插到合适的位置，只需和上级比较几次（O(log n)），不用重排全队。
想知道「第 37 危急的是谁」？做不到——分诊台从没维护过这个信息。
某个病人自己走了要从队列里移除？也很麻烦——得先把他找出来（O(n)），因为分诊台只按危急程度组织，不按姓名索引。这正是 §6「可删除堆」要解决的问题。

2.2 上浮与下沉

template <class T, class Cmp = std::less<T>>
class BinaryHeap {
    std::vector<T> a_;
    Cmp less_;                       // less_(x, y) 为真表示 x 优先级更低

    void sift_up(size_t i) {         // 插入后用：新元素往上冒
        T v = std::move(a_[i]);
        while (i > 0) {
            size_t p = (i - 1) / 2;
            if (!less_(a_[p], v)) break;   // 父不比 v 小 → 就位
            a_[i] = std::move(a_[p]);      // 父下移（不是交换：省一半赋值）
            i = p;
        }
        a_[i] = std::move(v);
    }

    void sift_down(size_t i) {       // 删根后用：新根往下沉
        size_t n = a_.size();
        T v = std::move(a_[i]);
        while (true) {
            size_t l = 2 * i + 1;
            if (l >= n) break;
            // 挑较大的孩子
            size_t c = (l + 1 < n && less_(a_[l], a_[l + 1])) ? l + 1 : l;
            if (!less_(v, a_[c])) break;   // v 不比孩子小 → 就位
            a_[i] = std::move(a_[c]);
            i = c;
        }
        a_[i] = std::move(v);
    }

public:
    const T& top() const { return a_[0]; }
    bool empty() const { return a_.empty(); }

    void push(T v) {
        a_.push_back(std::move(v));
        sift_up(a_.size() - 1);
    }
    void pop() {
        a_[0] = std::move(a_.back());     // 末尾补到根
        a_.pop_back();
        if (!a_.empty()) sift_down(0);
    }
    void build(std::vector<T> v) {  // Θ(n) 建堆
        a_ = std::move(v);
        if (a_.size() < 2) return;
        for (size_t i = a_.size() / 2; i-- > 0; ) sift_down(i);
    }
};
注意两处细节，它们是「手写版比朴素版快」的来源：
  • 用「移动 + 一次落位」代替反复交换。朴素写法每层做一次 swap（3 次赋值）；这里先把待放的值取出来，每层只做 1 次赋值，最后一次落位。赋值次数少三分之二。
  • 下沉时先挑较大的孩子再比一次，而不是「和左比、和右比、再交换」。这样每层只需 2 次比较（挑孩子 1 次 + 判是否就位 1 次）。
这两条也是 libstdc++ 的 __push_heap / __adjust_heap 的做法。

2.3 建堆是 Θ(n) 的证明

这是堆最经典的面试陷阱题：把 n 个元素建成堆，是 O(n) 还是 O(n log n)？答案取决于怎么建。

❌ 逐个 push：Θ(n log n)
for (T x : v) heap.push(x);

// 每次 sift_up 最多爬 log(当前大小) 层
// Σ log i ≈ log(n!) ≈ n log n

// 直觉：sift_up 处理的是最深的节点，
// 而一半的节点都在最底层 → 一半的元素
// 都要爬满 log n 层 → 贵
✅ 自底向上 sift_down：Θ(n)
for (size_t i = n / 2; i-- > 0; ) sift_down(i);

// 从最后一个非叶节点开始往前
// 叶子本身已经是合法堆，不用处理

// 直觉：sift_down 处理的节点越靠底层，
// 能下沉的层数越少。
// 底层节点最多（一半），但它们几乎不动
证明 设树高 h = ⌊log₂n⌋。深度为 d 的节点有至多 2^d 个， 每个最多下沉 (h − d) 层。总代价： T(n) ≤ Σ(d=0..h) 2^d · (h − d) 换元 k = h − d： = Σ(k=0..h) 2^(h−k) · k = 2^h · Σ(k=0..h) k / 2^k ≤ 2^h · Σ(k=0..∞) k / 2^k = 2^h · 2 （这个级数收敛到 2） ≤ 2n ∎ 关键 Σ k/2^k 是收敛级数。「节点数按 2^d 增长」和 「下沉层数按 (h−d) 递减」相乘后总和有界。
两种建堆方式的差别像整理一栋楼里的员工职级。

逐个 push（自顶向下）：每来一个新人就让他从最底层往上争，直到找到合适的层级。问题是大部分员工本来就该在底层，但你让每个人都走了一遍完整的晋升流程。

自底向上 sift_down：从倒数第二层的主管开始，只问「你手下有人比你强吗？」——若有就交换。底层的普通员工根本不用处理（他们没下属，天然合法），而他们占了一半人数。真正需要走很多层的只有顶部的少数几个人。

一句话：优化要针对「数量最多的那部分」。堆里数量最多的是叶子，所以让叶子什么都不做，就赢了一个 log。
这条结论有个必须知道的边界：建堆是 Θ(n)，但堆排序仍是 Θ(n log n)。因为堆排序的第二阶段要做 n 次「取根 + sift_down」，每次 O(log n)——那部分省不掉。
所以「建堆 O(n)」不能推出「堆排序 O(n)」。这是同一道题的常见追问。

2.4 STL heap 算法族

算法作用复杂度
std::make_heap(f, l)把区间整理成堆Θ(n)（自底向上）
std::push_heap(f, l)假定 [f, l-1) 已是堆，把 *(l-1) 并入O(log n)
std::pop_heap(f, l)把最大值换到末尾，[f, l-1) 仍是堆O(log n)
std::sort_heap(f, l)对堆做堆排序 → 升序O(n log n)
std::is_heap(f, l)检查是否满足堆性质O(n)
std::pop_heap 的语义容易误解：它不删除元素，只是把堆顶和末尾交换、然后把新根下沉，让 [first, last-1) 重新成为堆。真正的删除要自己 pop_back()。
这和 std::remove 的设计同理——算法只有迭代器，改不了容器大小（见 双指针 §5.1）。

直接用这套算法而不是 priority_queue 的好处：你能拿到底层容器，可以遍历、可以 reserve、可以在必要时手动 make_heap 重建——这些 priority_queue 都不允许（§3.2）。

priority_queue 的坑

三个高频误用

3.1 比较器方向反直觉

❌ 想要小顶堆，写了 less
// 默认是大顶堆（和 std::sort 升序的直觉相反）
std::priority_queue<int> pq;              // 大顶堆

// 想要小顶堆写成这样是错的：
std::priority_queue<int, std::vector<int>,
                    std::less<int>> pq;   // 还是大顶堆！
✅ 小顶堆用 greater
std::priority_queue<int, std::vector<int>,
                    std::greater<int>> pq;  // 小顶堆

// 自定义类型：注意比较逻辑要「反着读」
auto cmp = [](const Task& a, const Task& b) {
    return a.deadline > b.deadline;   // 用 > 得到「deadline 小的先出」
};
std::priority_queue<Task, std::vector<Task>, decltype(cmp)> pq(cmp);
为什么方向是反的：priority_queue 的 Compare 语义是「a 的优先级低于 b」——即 cmp(a, b) == true 时 a 排在 b 后面出队。所以传 less（a < b 为真时 a 优先级低）意味着「小的后出」= 大顶堆。

记忆方法：「top() 返回的是在这个比较器下『最大』的元素」。传 greater 时，「最大」按 greater 定义就是数值最小的那个 → 小顶堆。
这个设计和 std::sort 的 Compare（「a 应排在 b 前」）语义相反，是 C++ 里最容易搞混的一对接口。

3.2 不能改、不能删任意元素

你想做的priority_queue 支持吗该怎么办
修改某个元素的优先级否（top() 返回 const 引用）延迟删除，或用索引堆
删除任意元素否同上，或换 multiset
遍历所有元素否（没有 begin()）用 make_heap + 裸 vector
预留容量否（无 reserve）用带初值的构造，或裸 vector
Θ(n) 批量建堆是（区间构造函数）priority_queue(v.begin(), v.end())
取出底层容器受保护（c 是 protected）继承后暴露，或干脆别用它
最后一行值得说明：priority_queue 的底层容器 c 是 protected 而非 private，所以有个「合法但丑」的技巧——继承它然后暴露 c。
但更好的选择是直接用 std::vector + heap 算法族（§2.4）：你得到完全的控制权（reserve、遍历、必要时重建），代价只是多写两行。生产代码里我倾向于后者——priority_queue 的封装只在「用法极简单」时才是净收益。
批量建堆一定要用区间构造函数而不是循环 push： 
// ✅ Θ(n)：内部调用 make_heap
std::priority_queue<int> pq(v.begin(), v.end());

// ❌ Θ(n log n)
for (int x : v) pq.push(x);
这是 §2.3 那个证明的直接应用，也是实测能差 3–5 倍的地方。

Top-K 四解法选型

最常见的堆应用，也最常选错

4.1 四种做法对照

方法时间空间前提 / 特点
① 全排序取前 kO(n log n)O(1)最直观，也最浪费
② partial_sortO(n log k)O(1)前 k 个有序
③ nth_element + 局部 sortO(n)O(1)最快；但会打乱原数组
④ size-k 最小堆O(n log k)O(k)唯一能处理流式 / 数据装不下
 
// ③ 最快：O(n)。数据全在内存且可打乱时用这个
std::nth_element(v.begin(), v.begin() + k, v.end(), std::greater<>{});
std::sort(v.begin(), v.begin() + k, std::greater<>{});   // 只排前 k 个

// ④ 流式：维护一个 size=k 的最小堆（注意是最小堆求最大 k 个）
std::priority_queue<int, std::vector<int>, std::greater<int>> pq;
for (int x : stream) {
    if ((int)pq.size() < k) pq.push(x);
    else if (x > pq.top()) { pq.pop(); pq.push(x); }   // 比最小的大才替换
}
// 堆里剩的就是最大的 k 个，空间只 O(k)
「求最大 k 个用最小堆」这个反直觉的点必须理解：堆顶是这 k 个候选里最小的，也就是「门槛」。新元素只要能超过门槛，就把门槛踢出去、自己进来。
如果用最大堆，堆顶是候选里最大的——那个信息毫无用处，因为你无法知道该踢掉谁。

推论：求最小 k 个用最大堆。「堆顶应该是最容易被淘汰的那个」。
选型判据，按顺序问：
  1. 数据能全装进内存吗？不能 → 只有 ④。
  2. 数组可以被打乱吗？不能（比如它还要保持原序给别人用）→ ② 或 ④，或者先拷一份再用 ③。
  3. 前 k 个需要有序吗？需要 → ② 或 ③+局部 sort；只要「是这 k 个」不关心顺序 → ③ 单独用就行（更快）。
  4. k 接近 n 吗？是 → 直接 sort（此时 log k ≈ log n，① 和 ② 没差别）。
n=10⁷、k=100 时，① 约 3 秒、③ 约 0.1 秒——20 倍以上的差距，而这一步经常被跳过。

4.2 分布式 Top-K

数据分布在 M 台机器上时，正确做法是各分片先出局部 Top-K，再归并这些 Top-K。

为什么这样是正确的：全局 Top-K 的每个元素，必然是它所在分片的 Top-K 之一（若它连本分片前 k 都进不去，说明本分片就有 k 个比它大的，全局更不可能）。所以不会漏。
网络传输量从 O(n) 降到 O(M × k)。
但这个结论只对「可比较的单值」成立，对「聚合后再排序」不成立——这是分布式 Top-K 最大的陷阱：
  • 「求 Top-100 热门商品（按总点击数）」：某商品在每台机器上都排第 101，但把 M 台的点击数加起来后它可能是全局第 1。各分片只报 Top-100 就漏了它。
  • 正确做法：先按 key 重分区（shuffle）让同一商品的数据聚到同一台机器，聚合完再取 Top-K。这就是 MapReduce/Spark 里 reduceByKey 必须发生在 top 之前的原因。
  • 不想 shuffle 全量数据时，用近似算法：各分片报 Top-(k×c)（c 是放大系数）加上一个误差界，或者用 Count-Min Sketch 做可合并的近似频次统计（§5.3）。
判据：「元素的最终值能否在单个分片内确定」。能（如求最大的 100 个数）→ 局部 Top-K 归并正确。不能（要跨分片聚合）→ 必须先 shuffle 或接受近似。
05

流式与在线

数据一条条来，答案要随时可取

5.1 对顶堆求中位数

「数据流的中位数」是堆最漂亮的应用：用两个堆把数据切成两半。

class MedianFinder {
    std::priority_queue<int> lo_;                                        // 大顶堆：较小的一半
    std::priority_queue<int, std::vector<int>, std::greater<int>> hi_;  // 小顶堆：较大的一半
public:
    void add(int x) {
        // 先无脑塞进 lo_，再把 lo_ 的最大值移给 hi_ → 保证不变式 ①
        lo_.push(x);
        hi_.push(lo_.top());
        lo_.pop();
        // 再平衡大小 → 保证不变式 ②（约定 lo_ 可以多一个）
        if (lo_.size() < hi_.size()) {
            lo_.push(hi_.top());
            hi_.pop();
        }
    }
    double median() const {
        if (lo_.size() > hi_.size()) return lo_.top();
        return (lo_.top() + hi_.top()) / 2.0;
    }
};
上面的 add 有个值得学的写法：不去判断 x 该进哪个堆，而是「先塞左边、再把左边最大的挪到右边、最后平衡大小」。这样三步无条件执行，不需要任何 if (x < lo_.top()) 的分类讨论——把「判断该放哪」变成「无条件走一遍流程」，消掉了一整类边界 bug（空堆时 lo_.top() 怎么办之类）。
这个「用无条件的规整操作代替分类讨论」的手法在维护多个相互约束的结构时很有用。
对顶堆还能推广到任意分位数：把两个堆的大小比例从 1:1 改成 p:(1−p)，堆顶就夹住第 p 分位。不过这样维护更麻烦，而且流式分位数在生产上通常用 t-digest 或 DDSketch——它们空间 O(log 值域)、支持合并、有相对误差保证，而对顶堆是 O(n) 空间且无法合并。「能不能合并」是流式统计结构的关键分水岭。

5.2 滑动窗口中位数

比数据流中位数难一档，因为元素会离开窗口，而堆不支持删任意元素。

方案复杂度做法
multiset + 中间迭代器O(n log k)维护一个指向中位数的迭代器，插删后按需前后移一步
对顶堆 + 延迟删除O(n log k)用哈希表记「待删元素」，堆顶若在待删表里就先弹掉
两个 multisetO(n log k)对顶堆的思路，但换成能删任意元素的容器

multiset 方案有两个必须注意的点：
  • 删除要用 erase(find(x)) 而不是 erase(x)。后者会删掉所有等于 x 的元素——窗口里有重复值时直接错。这是 multiset 最高频的误用。
  • 维护「中间迭代器」时，插入/删除后要根据「插的值在中位数左边还是右边」决定迭代器往哪边移。写起来琐碎，容易错。更稳的做法是用两个 multiset（对顶堆的思路），逻辑和数据流中位数几乎一样。

5.3 近似 heavy hitters

「找出频次最高的 K 个元素」在数据量大到无法给每个元素计数时，堆也不够了——因为你连「每个元素出现几次」都存不下。

方案空间保证
哈希表计数 + size-k 堆O(不同元素数)精确
Count-Min Sketch + 堆O(1/ε · log(1/δ))频次只会高估，误差有界
Space-Saving / Misra-GriesO(k/ε)保证找出所有频次 > εn 的元素
采样 + 精确统计O(样本量)概率保证
Count-Min Sketch 的思路：用 d 个独立哈希函数 + d×w 的计数矩阵。插入时对每个哈希函数把对应格子 +1；查询时取 d 个格子的最小值（因为碰撞只会让计数偏高，取 min 最接近真值）。
再配一个 size-k 的堆存「当前 Top-K 候选」，每次插入后用 sketch 的估计值更新堆。

这是「精确但无界 → 近似但有界」的又一个案例，和 HyperLogLog（去重计数）、t-digest（分位数）、布隆过滤器（存在性）是同一族取舍。共同点是用一个可控的误差上界，换 O(1) 或 O(log n) 的空间。
动手前必须先问「误差多少可以接受」——没这个数字就没法选。相关展开见 Redis 与缓存。

可删除堆的三条路

堆最大的短板，以及三种补法

堆不支持「删除任意元素」和「修改某元素的优先级」——因为它不知道元素在哪（要 O(n) 找）。这个短板在四类需求里必须解决：Dijkstra 的 decrease-key、天际线问题、滑动窗口极值/中位数、可取消的定时器。

6.1 延迟删除

// 最常用：不真删，取用时才丢弃已失效的堆顶
class LazyHeap {
    std::priority_queue<int> pq_;
    std::unordered_map<int, int> pending_;   // 值 → 待删次数
    int size_ = 0;

    void prune() {                          // 清掉堆顶的失效元素
        while (!pq_.empty()) {
            auto it = pending_.find(pq_.top());
            if (it == pending_.end()) break;
            if (--it->second == 0) pending_.erase(it);
            pq_.pop();
        }
    }
public:
    void push(int x) { pq_.push(x); ++size_; }
    void erase(int x) { ++pending_[x]; --size_; }   // O(1)，只登记
    int top() { prune(); return pq_.top(); }
    int size() const { return size_; }         // 逻辑大小，不是 pq_.size()
};
为什么摊销复杂度仍是 O(log n)：每个元素最多被 push 一次、被 prune 弹出一次。prune 的内层循环总执行次数 ≤ 总 push 次数。所以尽管单次 top() 可能弹很多个，总代价仍是 O(n log n)——这是势能法的又一个应用。
延迟删除有三个容易踩的坑：
  • size() 必须自己维护。pq_.size() 包含了失效元素，不是逻辑大小。这个 bug 会让「判空」逻辑全错。
  • 堆可能膨胀到 O(总插入量)。如果删除远多于查询（比如大量定时器被取消但没人 top()），失效元素会一直堆积。解法：当 pq_.size() > 2 * size_ 时整体重建（把有效元素拷出来 make_heap）。
  • 按「值」登记待删只在值唯一时安全。若有重复值而你只想删一个，需要用 (值, 唯一 id) 作为堆元素，按 id 登记。

6.2 索引堆

索引堆（indexed heap）额外维护一个「元素 → 它在堆数组中的下标」的映射，从而支持真正的 O(log n) 任意删除和 decrease-key。

// 关键：sift_up / sift_down 里每次移动元素，都要同步更新映射
class IndexedHeap {
    std::vector<std::pair<int, int>> a_;      // (key, id)
    std::unordered_map<int, size_t> pos_;    // id → 在 a_ 中的下标

    void place(size_t i, std::pair<int,int> v) {
        a_[i] = v;
        pos_[v.second] = i;                  // ← 每次落位都要更新
    }
public:
    void decrease_key(int id, int new_key) {
        size_t i = pos_.at(id);            // O(1) 定位
        a_[i].first = new_key;
        sift_up(i);                          // O(log n) 调整
    }
    void erase(int id) {
        size_t i = pos_.at(id);
        place(i, a_.back());                 // 末尾补上来
        a_.pop_back(); pos_.erase(id);
        if (i < a_.size()) { sift_up(i); sift_down(i); }  // 两边都可能要调
    }
};
两个实现细节最容易错：
  • 每次元素落位都必须更新映射。sift_up/sift_down 里的每一次赋值都要走 place()，漏掉一处映射就失效，之后的定位全乱——而且这种 bug 不会立刻崩，只会给出错误结果。
  • erase 后要同时尝试 sift_up 和 sift_down。从末尾补上来的元素可能比原位置的元素大也可能小，两个方向都得试（其中一个会立即返回）。只写一个方向是经典 bug。
索引堆的代价是常数明显变大（每次移动多一次哈希表写）和代码复杂度。所以除非真的需要 decrease-key，优先用延迟删除。

堆的变体

理论最优与实测最优往往不是同一个

7.1 d-ary 堆

把二叉堆的「每节点 2 个孩子」改成 d 个孩子，树高变成 log_d n。

树高 log_d n = log₂n / log₂d ← 变矮 sift_up O(log_d n) ← 变快（爬得少） sift_down O(d · log_d n) ← 变慢（每层要比 d 个孩子） d=4 时：高度减半，sift_down 每层比 4 个（但它们连续存放， 常在同一条 cache line 里 → 实际几乎不额外花钱）
d=4 通常是实测最优，原因是 cache：4 个孩子（4i+1 .. 4i+4）在数组里连续，一次 cache line 读取（64 B / 16 个 int）就能全部拿到。所以「每层多比 3 次」几乎不花额外的内存访问，而「树高减半」实打实省掉一半的 cache miss。

d-ary 堆对 decrease-key 密集的场景收益最大（decrease-key 只用 sift_up，纯赚），这正是 Dijkstra 的形态。

7.2 斐波那契堆与配对堆

堆insertfind-mindelete-mindecrease-key实测
二叉堆O(log n)O(1)O(log n)O(log n)很好
d-ary 堆（d=4）O(log_d n)O(1)O(d log_d n)O(log_d n)最好
斐波那契堆O(1)O(1)O(log n) 摊销O(1) 摊销很差
配对堆O(1)O(1)O(log n) 摊销o(log n) 摊销好
斐波那契堆的意义是理论的，不是实践的。它让 Dijkstra 的复杂度从 O((V+E) log V) 降到 O(E + V log V)——在稠密图（E ≈ V²）上这是渐进改进。

但它实测很差，原因是：
  • 结构是一堆链表连成的森林，每个节点有 parent / child / left / right / degree / mark 六个字段 → 内存开销大、指针追逐严重。
  • 「摊销 O(1)」的代价藏在 delete-min 里——那次要做大量的树合并（consolidate），cache 行为极差。
  • 代码复杂，容易写错。
实践上要 decrease-key 就用配对堆或 d-ary 堆；Boost.Heap 提供了这些实现，实测里配对堆通常最接近斐波那契堆的理论优势而常数小得多。
斐波那契堆像为了省一次搬运而设计的极其复杂的仓储系统：理论上每次入库只要放门口（O(1)），账面上非常漂亮。但真到出库那天，你得把散落一地的箱子重新归并整理，而且所有东西都用绳子（指针）互相连着，找任何东西都得顺着绳子走。

「渐进更优」和「实际更快」之间的差距，在这里体现得最极端——这也是 复杂度与分析 §7 那一章的最好例证。

K 路归并与败者树

外部排序里为什么不用普通堆

K 路归并（合并 K 个有序流）的标准做法是用一个 size-K 的最小堆存各路队首：

// 合并 K 个有序链表 / K 个有序文件
struct Item { int val; int src; };   // 值 + 来自哪一路
auto cmp = [](const Item& a, const Item& b) { return a.val > b.val; };
std::priority_queue<Item, std::vector<Item>, decltype(cmp)> pq(cmp);

for (int i = 0; i < K; ++i)
    if (!streams[i].empty()) pq.push({streams[i].next(), i});

while (!pq.empty()) {
    auto [v, s] = pq.top(); pq.pop();
    output(v);
    if (!streams[s].empty()) pq.push({streams[s].next(), s});
}
// 每条记录 O(log K)，总 O(N log K)，N 为总记录数
为什么外部排序更常用「败者树」（loser tree / tournament tree）：普通堆的每次「pop + push」要做两次 O(log K) 的调整（下沉 + 上浮）。败者树把它合并成一次自底向上的路径更新：
  • 它是一棵完全二叉树，内部节点存「败者」（比较中输的那一方），根之上单独存全局胜者。
  • 取出胜者后，从它原来所在的叶子往上走一条路径，逐个和路上的败者比较——只需 log K 次比较，且路径固定。
  • 普通堆是「先把末尾补到根，再一路下沉」——比较次数约是败者树的两倍（每层要先挑较大的孩子）。
在外部排序里，比较次数直接决定 CPU 开销，而 I/O 已经被缓冲优化到接近顺序读——此时 CPU 侧的常数因子就成了瓶颈，所以这一倍的差距值得。

这又是一个「同样的渐进复杂度，常数因子决定选型」的例子。外部排序的完整流程见 排序全景 §10.1。
K 路归并的两个工程要点（和算法无关但更重要）：
  • 不要写成两两归并。两两归并需要 log₂K 遍，每遍都完整读写一次全量数据 → I/O 是 K 路归并的 log₂K 倍。1 TB 数据下这是 7 倍差距。
  • K 不是越大越好。内存要在 K+1 个缓冲区之间分，K 太大则每路缓冲太小，磁盘从顺序读退化成随机读。机械盘上 K 常取几十到几百，NVMe 可以更大——这个值必须实测。

时间轮的本质是「用哈希/分桶代替排序」——它不维护全局顺序，只把任务丢进「它该到期的那个槽」。这和哈希表用值算地址是同一个思想。

分层是为了解决「时间跨度大」的问题：单层轮要支持 24 小时且精度 1 秒，需要 86400 个槽（内存浪费且推进时大量空槽）。分层后用 60+60+24 = 144 个槽就覆盖了同样的范围，代价是高层任务到期时要级联到低层（一次 O(槽内任务数) 的重新分发）。
这和数字的进位表示是同一个道理——用几个小位数表示大范围。

  • 定时器数量少（几千以内）、精度要求高、取消不频繁 → 最小堆。最简单，O(log n) 完全够用。取消用延迟删除即可。
  • 需要频繁取消（每个网络连接一个超时定时器，正常返回就取消——绝大多数都会被取消）→ 时间轮或红黑树。堆的 O(n) 查找是致命的；用索引堆也行但不如时间轮简单。
  • 海量定时器 + 精度可放宽到几十毫秒（连接超时、心跳、重试）→ 分层时间轮。这是 Netty / Kafka / 内核的选择。
  • 用现成的：Linux 上 timerfd + epoll 让内核帮你管（内核内部就是时间轮）；应用层直接用 libuv / Boost.Asio 的定时器。自己实现只在有特殊需求时才值得。

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础堆是什么结构？它承诺了什么、没有承诺什么？

    堆是一棵完全二叉树，且每个节点的值不小于（大顶堆）它所有子节点的值。因为是完全二叉树，可以直接用数组表示，无需指针：

    parent(i) = (i − 1) / 2 left(i) = 2i + 1 right(i) = 2i + 2 ← 纯算术，零额外内存、cache 友好
    承诺
    根是最值（O(1) 取），插入删除 O(log n)，建堆 Θ(n)，空间 O(1) 额外。
    没有承诺（这些才是考点）
    · 兄弟之间无任何顺序（左孩子可能比右孩子大也可能小）
    · 不知道第二大是谁（只知道「一定是根的某个孩子」）
    · 中序遍历不是有序序列（和二叉搜索树完全不同）
    · 查/删任意元素是 O(n)（不知道元素在哪）
    这些「不承诺」正是它快的原因
    堆刻意放弃全序，只维护一条约束，所以插删只需沿一条路径调整。
    对比：排序数组给全序但插入 O(n)；平衡树给全序且插删 O(log n)，但常数大（指针追逐 + 每节点一次分配）；哈希表给 O(1) 查找但完全无序。堆在「取最值」这一个维度上做到了最优的时空权衡。
  2. 基础把 n 个元素建成堆，是 O(n) 还是 O(n log n)？

    取决于怎么建——这是本题的全部考点。

    逐个 push：Θ(n log n)
    for (T x : v) heap.push(x);
// Σ log i ≈ log(n!) ≈ n log n
    自底向上 sift_down：Θ(n)
    for (size_t i = n/2; i-- > 0; ) sift_down(i);
// 从最后一个非叶节点往前
    证明 树高 h = ⌊log₂n⌋，深度 d 的节点至多 2^d 个， 每个最多下沉 (h − d) 层： T(n) ≤ Σ(d=0..h) 2^d·(h−d) = 2^h · Σ(k=0..h) k/2^k （换元 k = h−d） ≤ 2^h · 2 （Σ k/2^k 收敛到 2） ≤ 2n ∎
    直觉（比公式更该记住）
    一半的节点在最底层，而它们几乎不用动。
    · sift_up（逐个 push）处理的是最深的节点 → 一半元素都要爬满 log n 层 → 贵
    · sift_down（自底向上）处理的节点越靠底层，能下沉的层数越少 → 数量最多的那部分几乎免费
    优化要针对「数量最多的那部分」——这是可迁移的思路。
    常见追问
    「建堆 O(n)，那堆排序也是 O(n) 吗？」不是。堆排序第二阶段要做 n 次「取根 + sift_down」，每次 O(log n)，那部分省不掉，所以堆排序仍是 Θ(n log n)。
    实践对应
    std::make_heap 和 priority_queue 的区间构造函数都是 Θ(n)；循环 push 是 Θ(n log n)。实测能差 3–5 倍。
  3. 基础std::priority_queue 默认是大顶堆还是小顶堆？怎么改？

    默认大顶堆（和 std::sort 默认升序的直觉相反）。改成小顶堆要传 std::greater：

    std::priority_queue<int> maxHeap;                                       // 大顶堆
std::priority_queue<int, std::vector<int>, std::greater<int>> minHeap;  // 小顶堆
    为什么方向是反的
    Compare 的语义是「a 的优先级低于 b」——cmp(a,b)==true 时 a 排在 b 后面出队。传 less（a<b 时 a 优先级低）意味着「小的后出」= 大顶堆。
    记忆方法
    「top() 返回的是在这个比较器下『最大』的元素」。传 greater 时，按 greater 定义的「最大」就是数值最小的 → 小顶堆。
    自定义类型时也照这个读：想让 deadline 小的先出，就写 return a.deadline > b.deadline;。
    和 std::sort 的 Compare 语义相反
    std::sort 的 cmp(a,b) 是「a 应排在 b 前」；priority_queue 是「a 优先级低」。这是 C++ 里最容易搞混的一对接口，写的时候多测一个用例。
    顺带：三个不支持的操作
    不能修改元素优先级（top() 是 const 引用）、不能删任意元素、不能遍历（无 begin()）、不能 reserve。
    需要这些就直接用 std::vector + make_heap/push_heap/pop_heap——多写两行，换完全的控制权。
  4. 基础从 10 亿个数里找最大的 100 个，怎么做？

    关键先问一句：数据能全装进内存吗？10 亿个 int 是 4 GB——如果能装，用 nth_element；如果是流式或装不下，用 size-k 堆。

    方案 A · 能全装内存 → nth_element，O(n)
    std::nth_element(v.begin(), v.begin()+100, v.end(), std::greater<>{});
std::sort(v.begin(), v.begin()+100, std::greater<>{});
    最快，总 O(n)。前提是数组可以被打乱。
    方案 B · 流式 / 装不下 → size-100 的最小堆，O(n log k)、空间 O(k)
    std::priority_queue<int, std::vector<int>, std::greater<int>> pq;
for (int x : stream) {
    if (pq.size() < 100) pq.push(x);
    else if (x > pq.top()) { pq.pop(); pq.push(x); }
}
    「求最大 k 个用最小堆」必须能解释
    堆顶是这 100 个候选里最小的，也就是门槛。新元素只要超过门槛，就把门槛踢出去、自己进来。
    用最大堆的话，堆顶是候选里最大的——这个信息毫无用处，你无法知道该踢谁。
    推论：求最小 k 个用最大堆。规则是「堆顶应该是最容易被淘汰的那个」。
    别用的方案
    全排序 O(n log n) 白排了 999 999 900 个不需要的数。n=10⁹ 时这是 20 倍以上的差距——而这一步经常被跳过。
    如果是分布式
    各分片先出局部 Top-100，再归并这些 Top-100。正确性：全局 Top-K 的每个元素必然是它所在分片的 Top-K 之一。网络传输从 O(n) 降到 O(M×k)。
    但这只对「可比较的单值」成立——若是「按总点击数取 Top-100 商品」这类需要跨分片聚合的，必须先 shuffle（见高级题）。

10.2 中级（区分熟练度）

  1. 中级怎么在数据流中实时求中位数？

    对顶堆：用两个堆把数据切成两半，两个堆顶恰好夹住中位数。

    结构
    lo = 大顶堆，存较小的一半（堆顶是左半最大值）
    hi = 小顶堆，存较大的一半（堆顶是右半最小值）
    两条不变式（必须同时维持）
    ① lo 的每个元素 ≤ hi 的每个元素
    ② |lo.size() − hi.size()| ≤ 1
    void add(int x) {
    lo_.push(x);                // 先无脑塞左边
    hi_.push(lo_.top());        // 把左边最大的挪到右边 → 保证 ①
    lo_.pop();
    if (lo_.size() < hi_.size()) { lo_.push(hi_.top()); hi_.pop(); }  // 保证 ②
}
double median() {
    if (lo_.size() > hi_.size()) return lo_.top();
    return (lo_.top() + hi_.top()) / 2.0;
}

    插入 O(log n)，取中位数 O(1)。

    这个 add 的写法值得学
    它不判断 x 该进哪个堆，而是「先塞左边 → 把左边最大的挪到右边 → 平衡大小」三步无条件执行。
    这样就不需要 if (x < lo.top()) 的分类讨论，也不用处理「堆为空时 top() 怎么办」。用无条件的规整操作代替分类讨论，消掉了一整类边界 bug——维护多个相互约束的结构时都可以这么想。
    滑动窗口中位数难一档
    因为元素会离开窗口，而堆不支持删任意元素。要用：两个 multiset（对顶堆思路但能删）、或对顶堆 + 延迟删除。
    注意 multiset::erase(x) 会删所有等于 x 的元素，删一个必须 erase(find(x))。
    生产上通常不用它
    流式分位数在生产里用 t-digest 或 DDSketch：空间 O(log 值域)、支持合并（多实例的 sketch 可汇总）、有相对误差保证。对顶堆是 O(n) 空间且无法合并。
    「能不能合并」是流式统计结构的关键分水岭——决定了它能否用在分布式环境。
  2. 中级堆不支持删除任意元素，有哪几种补救办法？各自的取舍？

    三条路，按「性价比」排序：

    ① 延迟删除（最常用）
    不真删，用一个哈希表记「待删元素」；取用时先把堆顶的失效元素弹掉。
    void erase(int x) { ++pending_[x]; --size_; }   // O(1)，只登记
int top() { prune(); return pq_.top(); }
    摊销仍 O(log n)：每元素最多 push 一次、被 prune 弹出一次，prune 的总次数 ≤ 总 push 次数（势能法）。
    延迟删除的三个坑
    ① size() 必须自己维护——pq_.size() 含失效元素，用它判空会全错；② 堆可能膨胀到 O(总插入量)（删多查少时），解法是 pq_.size() > 2*size_ 时整体重建；③ 按「值」登记只在值唯一时安全，有重复值要用 (值, 唯一 id)。
    ② 索引堆（需要 decrease-key 时）
    额外维护「元素 id → 堆数组下标」的映射，支持真正 O(log n) 的任意删除和 decrease-key。
    两个实现细节最容易错：每次元素落位都要更新映射（漏一处就全乱，且不会立刻崩）；erase 后要同时尝试 sift_up 和 sift_down（末尾补上来的元素可能更大也可能更小）。
    ③ 换 multiset（能用就用它）
    标准库、代码最少、功能最全（还能 O(1) 同时取最大最小）。代价是常数大（红黑树指针追逐 + 每节点一次分配）。
    决策
    能用 multiset 就用，除非 profile 显示它的常数是瓶颈。
    需要 decrease-key 且性能敏感（稠密图 Dijkstra、大规模调度）→ 索引堆。
    只需要「删除已失效元素」（定时器取消、天际线、窗口过期）→ 延迟删除，性价比最高。
  3. 中级斐波那契堆的 decrease-key 是 O(1) 摊销，为什么实践中几乎不用？

    因为它是理论最优但实测很差的典型——渐进复杂度赢了，常数因子输得更多。

    理论优势是真的
    它让 Dijkstra 从 O((V+E) log V) 降到 O(E + V log V)。稠密图（E ≈ V²）上这是实打实的渐进改进。
    但三个实践问题
    ① 结构是一堆链表连成的森林，每节点有 parent/child/left/right/degree/mark 六个字段 → 内存开销大、指针追逐严重；② 「摊销 O(1)」的代价藏在 delete-min 里——那次要做大量树合并（consolidate），cache 行为极差；③ 代码复杂，容易写错。
    实践该用什么
    d-ary 堆（d=4）：树高 log_4 n（比二叉堆减半），而 4 个孩子在数组里连续——一次 cache line 就能全拿到，所以「每层多比 3 次」几乎不额外花钱。对 decrease-key 密集的场景收益最大（decrease-key 只用 sift_up，纯赚）。
    配对堆：实测里最接近斐波那契堆的理论优势而常数小得多，Boost.Heap 有现成实现。
    这是「渐进 vs 实测」的最极端例子
    它和 排序里「堆排序理论完美却实测最慢」、复杂度里「list 的 O(1) 插入输给 vector 的 O(n)」是同一类现象：渐进分析基于 RAM 模型（每次内存访问代价相同），而真实机器上 L1 与主存差 100 倍。
    正确的结论不是「渐进分析没用」，而是渐进分析决定 n 大时的量级（不可违抗），常数因子决定同量级内的胜负（可优化 10 倍）。
  4. 中级K 路归并用堆是 O(N log K)，为什么外部排序更常用「败者树」？

    两者渐进复杂度相同，差别在比较次数的常数——而外部排序里 I/O 已被缓冲优化到接近顺序读，CPU 侧的比较开销就成了瓶颈。

    普通堆的每次「出一个、进一个」
    把末尾补到根，然后一路下沉。每层要先「挑较大的孩子」（1 次比较）再「判是否就位」（1 次比较）→ 约 2 log K 次比较。
    败者树（loser tree / tournament tree）
    完全二叉树，内部节点存「败者」（比较中输的一方），根之上单独存全局胜者。
    取出胜者后，从它原来所在的叶子往上走一条固定路径，逐个和路上的败者比较——只需 log K 次比较。
    比较次数约是普通堆的一半，而且路径固定、访问模式可预测。
    又是「同样渐进、常数决定选型」
    和 introsort 的 cutoff、d-ary 堆的 d=4、基数排序打败 std::sort 是同一类判断：渐进分析选出候选，常数因子决定最终选择。
    但 K 路归并真正的工程要点在别处
    ① 不要写成两两归并——那需要 log₂K 遍，每遍都完整读写一次全量数据，I/O 是 K 路的 log₂K 倍。1 TB 数据下是 7 倍差距。
    ② K 不是越大越好——内存要在 K+1 个缓冲区之间分，K 太大则每路缓冲太小，磁盘从顺序读退化成随机读。机械盘上 K 常取几十到几百，NVMe 可更大，必须实测。
    算法选型（堆 vs 败者树）的影响远小于这两条。

10.3 高级（体现深度）

  1. 高级设计一个支持百万级定时器的系统，选堆还是时间轮？

    先问三个问题，答案完全由它们决定：定时器数量？精度要求？取消频率？

    最小堆红黑树分层时间轮
    添加O(log n)O(log n)O(1)
    取消O(n) 找O(log n)O(1) 链表摘除
    触发O(log n)/个O(log n)/个O(1) 摊销
    精度任意任意受槽粒度限制
    使用者libuvepoll 内部、nginx内核、Netty、Kafka
    百万级定时器场景下堆的致命问题是「取消」
    典型场景是「每个连接一个超时定时器，请求正常返回就取消」——绝大多数定时器都会被取消而不是触发。堆的 O(n) 查找完全不可接受。
    用延迟删除能缓解，但堆会膨胀到 O(总添加量)；用索引堆可以，但不如时间轮简单。
    所以选分层时间轮
    本质是「用分桶代替排序」——不维护全局顺序，只把任务丢进「它该到期的那个槽」，和哈希表用值算地址同一个思想。
    分层是为了时间跨度：单层要支持 24h × 1s 精度需要 86400 个槽；分层后 60+60+24=144 个槽覆盖同样范围，代价是高层任务到期时要级联到低层。和数字的进位表示同理——用几个小位数表示大范围。
    时间轮的代价必须接受
    精度受槽粒度限制（槽粒度 100ms 就意味着定时器最多晚 100ms 触发）。对连接超时、心跳、重试这类需求完全够用；对需要精确到微秒的场景（高频交易、音视频同步）不行，那要用堆 + timerfd。
    但真正的答案是「先别自己写」
    Linux 上 timerfd + epoll 让内核帮你管（内核内部就是时间轮）；应用层直接用 libuv / Boost.Asio。
    自己实现只在有特殊需求时才值得——比如需要百万级定时器且不想每个都占一个 fd，或者需要自定义的批量触发语义。面试时能说出「先评估现成方案」比直接开始画时间轮更能体现工程判断。
  2. 高级分布式环境下求「Top-100 热门商品（按总点击数）」，各分片先出局部 Top-100 再归并对吗？

    不对。这是分布式 Top-K 最大的陷阱，也是「局部 Top-K 归并」这个正确结论被误用的典型。

    反例
    某商品在每台机器上都排第 101，各分片的 Top-100 都不含它。但把 M 台的点击数加起来后，它可能是全局第 1。局部 Top-K 归并会完全漏掉它。
    「局部 Top-K 归并」什么时候才对
    只有当元素的最终值能在单个分片内确定时才对。比如「求最大的 100 个数」——每个数的值就是它本身，不需要跨分片聚合。
    正确性论证：全局 Top-K 的每个元素必然是它所在分片的 Top-K 之一（若它连本分片前 k 都进不去，说明本分片就有 k 个比它大的，全局更不可能）。
    需要聚合时的正确做法
    先按 key 重分区（shuffle），让同一商品的所有数据聚到同一台机器 → 聚合出该商品的全局总数 → 再取 Top-K。
    这就是 MapReduce/Spark 里 reduceByKey 必须发生在 top 之前的原因，不是随便写的顺序。
    不想 shuffle 全量数据时的两条近似路
    ① 各分片报 Top-(k×c)（c 为放大系数）并附带「本分片第 k×c 名的值」作为误差界——归并后能给出「结果最多偏差多少」的保证。
    ② 用 Count-Min Sketch：d 个哈希函数 + d×w 计数矩阵，插入时对应格子 +1，查询取 d 个格子的最小值（碰撞只会高估，取 min 最接近真值）。sketch 可以合并，所以各分片的 sketch 汇总后再配一个 size-k 堆即可。
    背后的一般判据：这个指标可加吗
    sum / count / min / max 可加 → 能预聚合、能局部归并。
    avg 要拆 → 存 sum 和 count 分别聚合，最后再除。
    distinct count 和分位数不可加 → 必须换成可合并的近似结构（HyperLogLog、t-digest）。
    「这个指标可加吗」决定了整个分布式方案的形态——这个问题应该在设计的第一步就问。
  3. 高级一个用堆做优先级调度的服务，出现了「低优先级任务永远得不到执行」的问题，怎么解决？

    这是饥饿（starvation），堆的纯优先级语义的必然结果：只要高优先级任务持续到来，低优先级任务的位置永远排在后面。这不是 bug，是需求没被表达清楚。

    先确认这真的是问题
    某些场景饥饿是正确的（比如「紧急告警必须永远优先于日报生成」）。先问业务：低优先级任务有 SLA 吗？没有 SLA 就不是问题；有 SLA 才需要下面的方案。
    ① 老化 / 动态提优（aging，最常用）
    把优先级从「静态值」改成「静态优先级 + 等待时长 × 老化系数」。等得越久，有效优先级越高，最终一定能超过新来的高优先级任务。
    实现要点：不要真去修改堆里所有元素的 key（那是 O(n)）。而是把入队时间放进比较器，effective = base_priority + (now - enqueue_time) * rate——但这会让比较器随时间变化，破坏堆的不变式。
    正确做法：改成比较 deadline = enqueue_time - base_priority / rate 这类不随时间变化的量，让堆序稳定。这是个容易写错的地方。
    ② 多级队列 + 配额（更可控）
    每个优先级一个独立队列，调度器按加权轮询取（如高:中:低 = 7:2:1）。
    好处是配额显式、可观测、可调——你能直接回答「低优先级至少能拿到 10% 的处理能力」，而 aging 方案很难给出这种保证。这也是 Linux CFS 之前的 O(1) 调度器和多数 QoS 系统的做法。
    ③ 预留通道
    固定留 N 个 worker 只处理低优先级任务，与高优先级完全隔离。最简单、最可预测，代价是资源利用率下降。「隔离优于共享 + 复杂调度」——这在故障隔离上也成立。
    别忽略：饥饿常常是容量问题的症状
    如果高优先级任务多到能持续压满所有 worker，那真正的问题是容量不足或上游没限流。这时任何调度算法都只是在决定「谁先饿死」。
    先看队列长度和积压趋势：如果队列在持续增长，调度算法救不了，要么扩容要么限流（见 限流·熔断·降级）。
    选型判据
    需要可证明的公平性保证（对外承诺 SLA）→ 多级队列 + 配额，因为它的保证是显式且可计算的。只要「最终会被执行」 → aging，实现更简单。低优先级任务很少但绝不能丢 → 预留通道。
  4. 高级一个 priority_queue 在长时间运行后内存持续增长，可能是什么原因？

    「持续增长」而不是「一次性变大」，指向三类原因，按可能性排序：

    ① 延迟删除导致的堆膨胀（最常见）
    如果代码用了延迟删除（不真删，只登记待删），而删除远多于 top() 调用——失效元素永远没机会被 prune 掉，堆会膨胀到 O(总插入量)。
    典型场景：大量定时器被取消但没人去取堆顶；或者只在特定条件下才 top()。
    修法：当 pq.size() > 2 * logical_size 时整体重建（把有效元素拷出来 make_heap）。这个阈值让重建的摊销代价保持 O(1)。
    ② 生产快于消费（真正的积压）
    入队速率持续大于出队速率。这是容量问题不是内存问题——加内存只是延后崩溃时间。
    诊断：打点记录队列长度随时间的变化。如果是单调增长的趋势线而不是波动，就是这一类。
    修法：有界队列 + 明确的溢出策略（拒绝新任务 / 丢弃最低优先级 / 阻塞生产者）。无界队列是分布式系统里最常见的设计错误之一——它把「立刻失败」变成了「几小时后 OOM」。
    ③ 元素本身持有资源
    堆里存的不是简单值，而是持有 shared_ptr、连接、缓冲区的对象。堆没膨胀，但每个元素很大，或者形成了循环引用导致资源不释放。
    诊断：heap profiler 看内存去向——如果 vector<Item> 本身不大但总内存涨，就是元素引用的对象。
    排查顺序
    ① 打点 pq.size() 和逻辑 size，看两者是否分叉（分叉 → 延迟删除膨胀）；② 看队列长度趋势（单调增 → 积压）；③ heap profiler 看内存是在 vector 本身还是在元素引用的对象上。
    三个信号能直接区分三种原因。
    设计层面的教训
    任何队列都应该有界。无界队列把背压（backpressure）问题隐藏起来，直到 OOM 才暴露——而那时故障范围已经从「部分请求失败」扩大到「整个进程死亡」。
    正确做法是让容量上限成为一个显式的、可监控的、有明确溢出行为的配置项。这和 Hash-DoS 那一类「资源维度没有上界」的问题是同一个原则（见 哈希表内核 §7）。
