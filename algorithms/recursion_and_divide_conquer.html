递归与分治

递归难，不是因为概念复杂，而是因为它要求你同时相信两件事：函数还没写完，但它已经能正确处理更小的输入。这一篇先把递归拆到栈帧层面（它为什么会崩、为什么改不成循环），再把「分治」这个最重要的递归模式讲透——从归并求逆序对到 Karatsuba，最后到生产代码里的 cutoff 与并行分治。

01

递归的一句话本质

把「怎么做」换成「假设小一号的已经做完了」

写循环时，你的思维是过程式的：维护几个变量，一步步推进，直到条件满足。写递归时，思维是归约式的：不描述过程，只描述「大问题的答案怎么由小问题的答案拼出来」，然后假设小问题已经解决了。

递归的信任契约：写 f(n) 的函数体时，你可以无条件地假设 f(n-1)（或任何规模更小的调用）已经返回了正确答案。你的唯一义务是：① 保证每次调用都让规模真的变小；② 为最小规模直接给出答案（基线条件）。满足这两条，数学归纳法就替你保证了全部正确性。
递归像公司里的层层授权。你是总监，接到「统计整个部门有多少人」的任务。你不会自己去数每个工位——你给每个下属主管发同一条指令：「统计你手下有多少人，报给我」，然后把收到的数字加起来再加 1（你自己）。

这里的关键是：你不需要知道下属是怎么统计的，你只需要相信他们会给出正确的数字，而他们也在用同样的方式授权给自己的下属。基线条件就是最底层的员工——他没有下属，直接回答「1」。规模缩小就是组织架构必须是有限层的树，不能有循环汇报，否则这条指令会无限传下去。

本文按两条主线走。第一条是机制线（§2–§4）：递归在机器上真实的样子，以及它出问题时怎么办。第二条是范式线（§5–§8）：记忆化解决重叠子问题、分治解决独立子问题，以及分治在生产代码里的两个必备改造。

02

递归的机器视角

「函数调用自己」在硬件上是什么

2.1 栈帧里到底有什么

CPU 层面没有「递归」这个概念——只有函数调用。而函数调用的全部魔法在于栈帧（stack frame）：每次调用把「这次调用的私有状态」压到栈上，返回时弹掉。递归之所以能工作，纯粹是因为同一个函数的多次调用各有一份独立的栈帧。

三个数字要记住：Linux 默认线程栈 8 MB（ulimit -s 可查，pthread 默认也是 8 MB）、每帧 32–128 字节、所以安全递归深度约 10⁴–10⁵ 层。Windows 默认主线程栈只有 1 MB，更紧。

深度上限还受两个因素影响：① 帧里有大数组时（int buf[1024] 就是 4 KB 一帧），深度会骤降到几千层；② 开了 -O2 后编译器可能内联或复用栈槽，实际深度比源码看起来的更深。所以不要靠「我测过 10 万层没问题」下结论——换个编译选项就变了。

2.2 爆栈：不是异常，是信号

栈溢出不会抛 C++ 异常，也不会返回错误码。内核在栈区末端放了一个不可访问的 guard page；栈指针越过它时触发页错误，内核判定这不是合法的栈扩展，于是给进程发 SIGSEGV。程序当场死掉，try/catch 拦不住。

❌ 递归处理长链表：必崩
// n = 10⁶ 的链表反转
Node* reverse(Node* head) {
    if (!head || !head->next) return head;
    Node* rest = reverse(head->next);  // 深度 = n
    head->next->next = head;
    head->next = nullptr;
    return rest;
}
// 10⁶ 层 × 48 B ≈ 48 MB > 8 MB → SIGSEGV
✅ 迭代版：O(1) 空间
Node* reverse(Node* head) {
    Node* prev = nullptr;
    while (head) {
        Node* next = head->next;
        head->next = prev;
        prev = head;
        head = next;
    }
    return prev;
}
// 深度 0，任意长度都安全

怎么从现场认出是爆栈而不是普通的野指针？三个特征：

线索爆栈的表现普通空指针 / 野指针
gdb 的 bt同一个函数重复上万帧，或直接报 Backtrace stopped帧数正常，栈顶是具体的业务函数
出错地址紧邻当前 rsp，且落在栈区下界通常是 0x0 附近或明显的垃圾值
ASan 报告stack-overflowSEGV on unknown address / use-after-free
生产环境里排查递归深度问题的实用技巧：给递归函数加一个 depth 参数并断言上限。assert(depth < 10000) 会在爆栈之前触发，给你一个干净的、可读的栈回溯，而不是一堆重复帧。这在处理外部输入（解析嵌套 JSON、递归下降解析器）时尤其重要——攻击者可以用深度嵌套的输入把爆栈变成 DoS。

2.3 尾调用消除为何不保证

尾调用（tail call）：函数的最后一个动作是调用另一个函数，且直接返回它的结果，中间没有任何额外运算。尾调用消除（TCO）：编译器发现这种模式后，不再压新栈帧，而是复用当前帧、把 call 换成 jmp——递归被变成了循环，栈深恒为 1。
❌ 不是尾递归
int fact(int n) {
    if (n <= 1) return 1;
    return n * fact(n - 1);
    //     ↑ 递归返回后还要做一次乘法
    // → 当前帧必须保留（要留着 n）
}
✅ 尾递归（累加器改写）
int fact(int n, int acc = 1) {
    if (n <= 1) return acc;
    return fact(n - 1, acc * n);
    //     ↑ 调用结果直接返回，无后续运算
    // → 当前帧无用，可复用
}

把「递归返回后要做的事」搬进参数（累加器），就把非尾递归变成了尾递归。GCC/Clang 在 -O2 下通常会消除右边这个递归。但这是优化，不是语言保证——这一点和 Scheme、Lua 完全不同，后者在标准层面要求必须消除尾调用。

C++ 里 TCO 会失效的常见原因：

原因为什么阻止 TCO
局部对象有析构函数析构必须在 return 之后跑，所以那个「调用」其实不在尾位置。这是 C++ 特有的、最常见的原因。
编译在 -O0 / -Og调试友好优先，不做栈帧复用
函数是虚函数 / 通过函数指针调用目标不确定（除非能去虚化）
返回大对象（走 sret 隐藏指针）调用约定要求当前帧提供返回值空间
参数需要在栈上传递且布局不同无法原地复用帧
开了 sanitizer / -fno-optimize-sibling-calls需要完整栈信息
第一行值得单独强调，因为它非常隐蔽：
int f(int n) {
    std::string tmp = make_log(n);   // ← 有析构函数
    if (n == 0) return 0;
    return f(n - 1);              // 看着是尾调用，其实不是
}                                  // tmp 的析构在这里 → 帧不能丢
结论：在 C++ 里不要把「尾递归 + 编译器优化」当成深递归的解决方案。需要 O(1) 栈深就手写循环（§4.1），需要 O(log n) 上限就用「只递归小半边」（复杂度与分析 §6）。
C++ 从未纳入 [[tail_call]] 这类强制属性，但 Clang 提供了非标准的 __attribute__((musttail))：它要求编译器做尾调用消除，做不到就编译报错。这在写解释器 dispatch 循环、协议状态机时很有用——把「优化是否生效」从运行期的玄学变成编译期的确定性。代价是不可移植。
03

写对递归的三件套

递归写不出来，通常是这三件里漏了一件

3.1 三个必要条件

要素问自己漏掉的后果
① 规模严格缩小每次递归调用的参数，是否一定比当前更接近基线？无限递归 → 爆栈
② 基线条件完备所有能到达的最小情形都覆盖了吗（含空、单元素、负数）？越过基线继续递归 → 爆栈或越界
③ 归约关系正确假设子调用返回正确答案，我拼出的结果对吗？结果错但不崩，最难查

①最容易出错的地方是「缩小」不等于「参数变了」。f(n/2) 在 n=1 时是 f(0)（缩小了），但 f(n/2) 在整数除法下当 n=1 时若写成 f((n+1)/2) 就是 f(1)——没缩小，死循环。写完递归务必手推一遍最小的两三个输入。

❌ 基线不完备
int depth(TreeNode* r) {
    // 漏了 r == nullptr
    return 1 + std::max(depth(r->left),
                        depth(r->right));
}
// 叶子节点的 left 是 nullptr
// → 解引用空指针 → SIGSEGV
✅ 基线放在最前面
int depth(TreeNode* r) {
    if (!r) return 0;      // 基线
    return 1 + std::max(depth(r->left),
                        depth(r->right));
}
// 习惯：让「空」而不是「叶子」做基线，
// 代码短一半且不会漏分支
树递归有个固定套路：基线永远选「空节点」而不是「叶子节点」。选叶子的话要写 if (!r->left && !r->right)，还得单独处理只有一个孩子的情况；选空节点则所有分支自动统一。这条规则能消掉树题里一半的边界 bug。

3.2 状态往哪里放

递归函数需要的额外状态有三个去处，各有代价：

方式写法优点代价
值参数f(node, depth)每层独立，回溯自动完成每帧一份拷贝，大对象要小心
引用参数f(node, vector& path)零拷贝，能收集结果需要手动回溯（push 后必须 pop）
捕获式 lambdaauto dfs=[&](auto&& self, int u){...}状态写在外层，签名干净C++20 前需要 self 技巧或 std::function
❌ 引用参数忘了回溯
void dfs(int u, std::vector<int>& path) {
    path.push_back(u);
    if (isLeaf(u)) { ans.push_back(path); return; }
    for (int v : g[u]) dfs(v, path);
    // ← 漏了 path.pop_back()
}
// path 只增不减，所有路径都被污染
// 而且 isLeaf 分支提前 return，更容易漏
✅ push / pop 严格配对
void dfs(int u, std::vector<int>& path) {
    path.push_back(u);
    if (isLeaf(u)) ans.push_back(path);
    else for (int v : g[u]) dfs(v, path);
    path.pop_back();          // 唯一出口，必执行
}
// 纪律：函数体内只有一个 return 点，
// pop 紧贴函数末尾 → 结构上不可能漏

右边这条纪律——「push 在函数第一行，pop 在函数最后一行，中间不许 early return」——是回溯类题目的通用防错结构。想用 early return 的话，改成 RAII 更稳：

struct PathGuard {
    std::vector<int>& p;
    PathGuard(std::vector<int>& p_, int v) : p(p_) { p.push_back(v); }
    ~PathGuard() { p.pop_back(); }        // 任何出口（含异常）都会回溯
};

void dfs(int u, std::vector<int>& path) {
    PathGuard g(path, u);
    if (isLeaf(u)) { ans.push_back(path); return; }  // 现在可以随便 return
    for (int v : g[u]) dfs(v, path);
}
注意 PathGuard 有析构函数，所以它会阻止尾调用消除（§2.3）。这是个真实的取舍：RAII 换来了正确性，代价是放弃 TCO。对于深度 O(log n) 或深度有界的递归，这个代价可以忽略；对于深度 O(n) 的递归，本来就该写成迭代。
04

递归转迭代三条路

按难度从易到难：累加器、显式栈、状态机

4.1 尾递归改写

最简单的一类：递归调用是最后一个动作（或能通过累加器变成最后一个动作）。这类直接改成 while。

递归版
int gcd(int a, int b) {
    if (b == 0) return a;
    return gcd(b, a % b);
}

int fact(int n, int acc = 1) {
    if (n <= 1) return acc;
    return fact(n - 1, acc * n);
}
机械改写：参数赋值 + while
int gcd(int a, int b) {
    while (b != 0) {
        int t = a % b; a = b; b = t;
    }
    return a;
}

int fact(int n) {
    int acc = 1;
    while (n > 1) { acc *= n; --n; }
    return acc;
}

改写规则很机械：基线条件 → 循环退出条件（取反）；递归调用的实参 → 循环末尾对参数的赋值。

4.2 显式栈

有多个递归调用、或递归后还有工作时，把编译器替你维护的栈自己写出来。以二叉树前序遍历为例：

递归（前序）
void pre(TreeNode* r) {
    if (!r) return;
    visit(r);
    pre(r->left);
    pre(r->right);
}
显式栈（注意右子先入栈）
void pre(TreeNode* r) {
    if (!r) return;
    std::vector<TreeNode*> st{r};
    while (!st.empty()) {
        TreeNode* n = st.back(); st.pop_back();
        visit(n);
        // 栈是后进先出 → 想先访问左子，右子先压
        if (n->right) st.push_back(n->right);
        if (n->left)  st.push_back(n->left);
    }
}
用 std::vector 当栈而不是 std::stack（默认底层是 deque）：vector 连续内存、cache 友好，还能 reserve。这是竞赛和高性能代码的默认选择。std::stack<T, std::vector<T>> 也可以，但直接用 vector 更直白。

4.3 状态机（后序的难点）

前序好改，因为「访问」发生在递归之前。后序遍历难改，因为一个节点要等两个子树都处理完才能访问——也就是说，同一个节点会被「回到」多次，每次处于不同阶段。这时显式栈里存的不能只是节点，还得存它走到哪一步了——这就是把编译器帮你记住的「返回地址」显式化。

// 后序遍历：栈里存 (节点, 已完成的子树数)
void post(TreeNode* r) {
    if (!r) return;
    std::vector<std::pair<TreeNode*, int>> st{{r, 0}};
    while (!st.empty()) {
        auto& [n, stage] = st.back();
        if (stage == 0) {                 // 还没进左子树
            ++stage;
            if (n->left) st.push_back({n->left, 0});
        } else if (stage == 1) {          // 左子树完成，进右子树
            ++stage;
            if (n->right) st.push_back({n->right, 0});
        } else {                          // 两边都完成 → 访问自己
            visit(n);
            st.pop_back();
        }
    }
}
这就是「递归的通用去递归化」：栈里存 (局部状态, 程序计数器)。stage 扮演的正是栈帧里那个返回地址的角色——它记录「从子调用回来后该从哪继续」。任何递归都能这样机械地改成迭代，代价是代码可读性直线下降。

C++20 协程做的事本质相同：把函数的局部状态和「执行到哪一行」打包搬到堆上，让调用栈不必保留。
工程上的取舍很明确：递归深度有 O(log n) 保证时，就用递归（可读性完胜，栈深 30 层怎么都不会崩）。深度可能达 O(n) 且 n 由外部输入决定时，必须去递归——不是为了性能，是为了防 DoS。中间地带可以用「递归 + 深度断言」先上线，再按需改写。

还有一条常被忽略的路：换算法把深度降下来。二叉树遍历有 Morris 遍历，利用叶子的空右指针临时指回后继（线索化），做到 O(1) 空间且无栈；图遍历可以用 BFS 代替 DFS，队列在堆上，天然不爆栈。这些会在批次 3 的树与图两篇里展开。

05

记忆化：从指数到线性

递归的最大浪费，和一行代码的修复

5.1 重叠子问题

朴素的 Fibonacci 递归是 O(φⁿ) ≈ O(1.618ⁿ)，慢得离谱。原因不是递归本身，而是同一个子问题被反复计算：

重叠子问题（overlapping subproblems）：递归展开时，同一个子问题在树的不同位置反复出现。这是动态规划的适用信号。
对比分治（§6）：分治的子问题互不相交（归并排序的左右两半没有重叠），所以不需要记忆化，也不需要 DP。
「子问题是否重叠」是区分「该用分治」还是「该用 DP」的唯一判据。

5.2 三种写法对照

❌ 朴素递归 O(φⁿ)
long long fib(int n) {
    if (n < 2) return n;
    return fib(n-1) + fib(n-2);
}
// n=50 要算约 2×10¹⁰ 次 → 分钟级
✅ 记忆化 O(n)
long long fib(int n, std::vector<long long>& memo) {
    if (n < 2) return n;
    if (memo[n] != -1) return memo[n];   // ← 一行
    return memo[n] = fib(n-1, memo) + fib(n-2, memo);
}
// 每个 n 只算一次 → n=50 瞬间
// 但栈深仍是 O(n)
// ✅✅ 自底向上 + 滚动变量：O(n) 时间、O(1) 空间、零栈深
long long fib(int n) {
    if (n < 2) return n;
    long long a = 0, b = 1;
    for (int i = 2; i <= n; ++i) {
        long long c = a + b;
        a = b; b = c;
    }
    return b;
}
Fibonacci 还有 O(log n) 的解法（矩阵快速幂，见 §7.3）。这里的三段递进是想说明一个通用路径：朴素递归 → 加记忆化（消掉重复）→ 改自底向上（消掉栈）→ 压缩状态（消掉空间）。这四步就是绝大多数 DP 题的优化顺序，会在批次 4 的动态规划里系统展开。

5.3 自顶向下 vs 自底向上

自顶向下（记忆化递归）自底向上（迭代 DP）
思维方式和递归定义一致，好写要先想清计算顺序（拓扑序）
栈深O(递归深度)，可能爆栈0
是否计算无用状态否，只算真正需要的是，全表都填
常数因子函数调用 + 哈希/查表开销纯循环，cache 友好
能否压缩空间难（要保留全表）容易（滚动数组）
状态空间稀疏时优势明显（用哈希表存）浪费严重

选择的判据很清晰：状态空间稠密且要全填 → 自底向上；状态空间稀疏或难以确定拓扑序 → 记忆化递归。前者是竞赛和高性能代码的默认，后者在状态是多维/离散（比如状态是一个字符串或一个集合）时几乎是唯一选择。

自顶向下像按需查族谱：你想知道某人的曾祖父是谁，就顺着往上查，查过的记在小本子上。只查你关心的那一支。
自底向上像从最早的祖先开始，把整本族谱按辈分排好。填完整本书，任何查询都是 O(1)，但如果你只关心一支，那就白填了大半本。

分治范式

子问题互不重叠时的标准骨架

6.1 三步骨架

Divide 把规模 n 的问题拆成 a 个规模 n/b 的独立子问题 Conquer 递归解决每个子问题（规模足够小时直接算） Combine 把子问题的解合并成原问题的解，代价 f(n) T(n) = a · T(n/b) + f(n)

「独立」是分治的定义性前提：子问题之间没有共享的子子问题。归并排序把数组切成左右两半，左半的排序过程完全不需要右半的任何信息——所以不需要记忆化。这一点是分治与 DP 的分界线（§5.1）。

// 通用骨架（以归并排序为例）
template <class It>
void merge_sort(It lo, It hi, std::vector<typename It::value_type>& buf) {
    auto n = hi - lo;
    if (n < 2) return;                        // ① 基线
    It mid = lo + n / 2;                        // ② Divide
    merge_sort(lo,  mid, buf);                 // ③ Conquer
    merge_sort(mid, hi,  buf);
    merge_into(lo, mid, hi, buf);             // ④ Combine：O(n)
}

四行代码里藏着分治的全部设计决策：怎么切（决定 a 和 b）、切到多小停（决定基线，也是 §8.1 的 cutoff）、合并要花多少（决定 f(n)）。这三个决策一定，复杂度就定了。

6.2 复杂度落在哪一情形

用主定理（复杂度与分析 §5.2）：算临界指数 c* = log_b a，再把 f(n) 和 n^c* 比大小。

算法abf(n)c*结果
二分查找12Θ(1)0Θ(log n)
归并排序22Θ(n)1Θ(n log n)
快速幂12Θ(1)0Θ(log n)
快速选择（理想划分）12Θ(n)0Θ(n)

看最后两行的对比就懂了分治优化的核心机制：f(n) 和 b 完全相同，只有 a 从 4 降到 3，复杂度就从 Θ(n²) 掉到 Θ(n^1.585)。在主定理情形一（叶子主导）里，降低子问题个数是唯一有效的杠杆。

设计分治算法时的思考顺序：先看能不能减少子问题个数（Karatsuba、Strassen 的路子——用更多的加减法换更少的乘法），再看能不能降低合并代价（只在情形三时有意义），最后调 cutoff（只影响常数）。顺序反了就是在错的地方使劲。

7.1 归并求逆序对

这是「在分治的合并步顺便统计」这一模式的代表。逆序对指 i < j 但 a[i] > a[j] 的数对，朴素做法 O(n²)，借归并排序可以 O(n log n)。

关键洞察：合并左右两个已排序的半段时，若从右半取出元素 a[j]，说明左半剩下的所有元素都比它大——那么左半剩余个数就是以 a[j] 为右端点的逆序对数量，一次加完。

long long merge_count(std::vector<int>& a, int lo, int hi,
                       std::vector<int>& buf) {
    if (hi - lo < 2) return 0;
    int mid = lo + (hi - lo) / 2;
    long long cnt = merge_count(a, lo, mid, buf)
                 + merge_count(a, mid, hi, buf);

    int i = lo, j = mid, k = lo;
    while (i < mid && j < hi) {
        if (a[i] <= a[j]) {
            buf[k++] = a[i++];
        } else {
            cnt += mid - i;            // ← 左半剩余全部与 a[j] 构成逆序对
            buf[k++] = a[j++];
        }
    }
    while (i < mid) buf[k++] = a[i++];
    while (j < hi)  buf[k++] = a[j++];
    std::copy(buf.begin() + lo, buf.begin() + hi, a.begin() + lo);
    return cnt;
}
注意 a[i] <= a[j] 里的等号：写成 < 会把相等元素也算成逆序对，同时破坏归并的稳定性。这是同一个符号同时决定两件事的典型例子——「相等时优先取左边」既保证稳定，也保证计数正确。

同一个模式还能解：「区间内小于 x 的元素个数」「三元逆序对」「翻转对（a[i] > 2·a[j]）」。识别信号是：要统计的东西可以在「左半 × 右半」的跨界配对上一次算清。

7.2 快速选择与 introselect

找第 k 小的元素。排序后取是 O(n log n)，但分治可以做到期望 O(n)——因为每次划分后只需要递归一边。

快排： T(n) = 2T(n/2) + Θ(n) → Θ(n log n) （两边都要） 快选： T(n) = 1T(n/2) + Θ(n) → Θ(n) （只要一边） 主定理情形三：f(n)=Θ(n) 压过 n^log₂1 = n⁰ = 1
// 期望 O(n)：随机化 pivot，只递归包含目标的那一侧
int quick_select(std::vector<int>& a, int lo, int hi, int k) {
    while (true) {
        if (hi - lo == 1) return a[lo];
        int p = partition_random(a, lo, hi);   // a[p] 就位
        if (k == p)      return a[p];
        else if (k < p)  hi = p;                // 尾递归 → 循环
        else            lo = p + 1;
    }
}

为什么期望是 O(n)？随机 pivot 时每次期望切掉常数比例（约 3/4 以内），于是代价是几何级数 n + 3n/4 + 9n/16 + … < 4n。注意这是「期望」而非「最坏」——最坏仍是 O(n²)。

方案最坏期望实测常数用在哪
随机化快选O(n²)O(n)小绝大多数场景
median-of-mediansO(n)O(n)大（约 5–10×）需要最坏保证时
introselectO(n)O(n)小std::nth_element
std::nth_element 用的是 introselect：默认走快选（常数小），但监控递归深度，超过阈值就切换到有最坏 O(n) 保证的算法（median-of-medians 或堆）。这和 std::sort 的 introsort 是同一个设计思想——快路径求常数，慢路径兜底最坏。std::sort 的完整剖析在 排序全景 §9，STL 算法接口层面的对照在 STL 算法库。

7.3 快速幂

算 a^n，朴素 O(n) 次乘法。利用 a^n = (a^(n/2))² 分治，只需 O(log n) 次。

递归版（清晰）
long long qpow(long long a, long long n, long long m) {
    if (n == 0) return 1 % m;
    long long half = qpow(a, n / 2, m);
    long long r = half * half % m;
    return (n & 1) ? r * (a % m) % m : r;
}
迭代版（生产用这个）
long long qpow(long long a, long long n, long long m) {
    long long r = 1 % m;
    a %= m;
    while (n) {
        if (n & 1) r = r * a % m;   // 该位为 1 → 乘上
        a = a * a % m;                 // a 自平方
        n >>= 1;
    }
    return r;
}

迭代版本质是按 n 的二进制位展开：a^13 = a^8 · a^4 · a^1（13 = 1101₂）。这个「二进制拆分」思路可以推广到任何满足结合律的运算：

推广对象「乘法」定义为能解什么
矩阵快速幂矩阵乘法线性递推第 n 项（Fibonacci 的 O(log n) 解法）
邻接矩阵幂（布尔）布尔矩阵乘「恰好 k 步可达」的路径存在性
(min, +) 矩阵幂min-plus 乘法恰好 k 条边的最短路
快速乘（防溢出）加法大模数下的 a*b%m
r * a % m 在 m 接近 2⁶³ 时会溢出——long long 相乘的中间结果放不下。修复方式：用 __int128（GCC/Clang 扩展）做中间运算，或者用「快速乘」（把乘法也二进制展开成加法）。这是快速幂在生产代码里最常见的 bug，而且它只在大模数时暴露，小数据测试完全测不出来。

7.4 最近点对

平面上 n 个点，找距离最小的一对。朴素 O(n²)。分治能做到 O(n log n)，而它的精妙之处全在合并步。

算法流程：① 按 x 排序后取中线切分；② 递归得左右各自的最小距离，d = min(d_L, d_R)；③ 只有横坐标落在 [mid−d, mid+d] 带内的点才可能构成更近的跨界点对；④ 把带内点按 y 排序，每个点只和 y 相邻的最多 7 个点比较。

为什么是 7 个：带内任意两点若都在同一半，它们的距离 ≥ d（由 d 的定义）。把带切成 d/2 × d/2 的小格，每格最多放 1 个点（对角线 = d/√2 < d）。目标点的 y 方向 d 范围内、x 方向 2d 范围内，共 2 列 × 4 行 = 8 格，除去自己剩 7 个。这个常数 7（有的书写 6 或 8，取决于边界如何计）不重要，重要的是它是个常数——这才让合并步是 O(n) 而不是 O(n²)。
实现上有个坑：如果在每层递归里都对带内点按 y 排序，那合并步是 O(n log n)，总复杂度变成 O(n log²n)。要真正做到 O(n log n)，得预先按 y 排一份，递归时同步维护（类似归并排序的做法，回溯时顺便把 y 序合并出来）。很多教材的示例代码是 O(n log²n) 版本——面试时能指出这个区别是加分项。

7.5 Karatsuba 大数乘法

两个 n 位大数相乘，竖式是 O(n²)。朴素分治把每个数切成高低两半：

x = x₁·B + x₀, y = y₁·B + y₀ （B = 10^(n/2) 或 2^(n/2)） x·y = x₁y₁·B² + (x₁y₀ + x₀y₁)·B + x₀y₀ 朴素：需要 4 次子乘法 → T(n) = 4T(n/2) + O(n) = O(n²) 白干

Karatsuba 的技巧是用一次额外的加减法，把 4 次乘法降到 3 次：

令 P₁ = x₁·y₁ P₂ = x₀·y₀ P₃ = (x₁+x₀)·(y₁+y₀) ← 只多算这一个 则 x₁y₀ + x₀y₁ = P₃ − P₁ − P₂ ← 中间项用减法得到，不用乘 x·y = P₁·B² + (P₃ − P₁ − P₂)·B + P₂ T(n) = 3T(n/2) + O(n) → Θ(n^log₂3) ≈ Θ(n^1.585)
// 概念示意（真实实现用位运算 + 定长 limb 数组）
BigInt karatsuba(const BigInt& x, const BigInt& y) {
    size_t n = std::max(x.size(), y.size());
    if (n <= 32) return schoolbook(x, y);   // ← cutoff：小规模切回 O(n²)

    size_t h = n / 2;
    auto [x1, x0] = split(x, h);
    auto [y1, y0] = split(y, h);

    BigInt P1 = karatsuba(x1, y1);
    BigInt P2 = karatsuba(x0, y0);
    BigInt P3 = karatsuba(x1 + x0, y1 + y0);
    BigInt mid = P3 - P1 - P2;

    return (P1 << (2 * h)) + (mid << h) + P2;
}
Karatsuba 像用两次称重代替四次。要知道 A、B 两袋各自重量和它们的交叉信息，直觉是分别称四次。但如果你称了 A、称了 B、再称「A+B 一起」，就能算出第四个数，省下一次称重。

乘法比加法贵得多（尤其在大数上），所以用加减法换乘法永远划算。Strassen 矩阵乘法（8 次子乘 → 7 次，代价是 18 次矩阵加减）是同一个交易，只是账算得更绕。

再快的算法还有 Toom-Cook（推广到切 k 份）和基于 FFT 的 Schönhage–Strassen（O(n log n log log n)）。GMP 库的实际策略是按位数分段选算法：小数走竖式、中等走 Karatsuba、更大走 Toom-Cook、超大走 FFT。这是「多算法按规模切换」的经典工程模式，和 introsort 一个道理。

8.1 cutoff：小规模切走

教科书的归并排序递归到单元素为止。生产实现都不这么做——递归到某个阈值（通常 16–32）就切换到插入排序。

为什么小规模要切走说明
递归开销占比过高n=4 时，函数调用 + 栈帧 + 边界判断的成本超过实际比较
插入排序常数极小顺序访问、零分配、分支高度可预测（近乎有序时几乎无分支误预测）
小数组整块在 L132 个 int = 128 字节，两条 cache line，全程命中
叶子占了大部分节点递归树是二叉的 → 一半的节点是叶子，优化叶子等于优化一半的调用

最后一行是最有说服力的理由：二叉递归树里，叶子节点数约等于内部节点数。所以「把最底下几层砍掉换成一个高效的小规模算法」能消掉的调用量非常可观。

// 生产版归并排序骨架
constexpr int CUTOFF = 32;

void msort(int* a, int lo, int hi, int* buf) {
    if (hi - lo <= CUTOFF) { insertion_sort(a + lo, a + hi); return; }
    int mid = lo + (hi - lo) / 2;
    msort(a, lo, mid, buf);
    msort(a, mid, hi, buf);
    if (a[mid - 1] <= a[mid]) return;   // ← 已有序，跳过合并（近乎有序数据的大杀器）
    merge_into(a, lo, mid, hi, buf);
}
上面那行 if (a[mid-1] <= a[mid]) return; 值得单独学：合并前检查两半是否已首尾有序，是则整个合并步可跳过。对已排序或近乎有序的输入，这一行把归并排序从 Θ(n log n) 变成 Θ(n)。TimSort（Python/Java 的排序）把这个思路做到了极致——它主动识别输入里天然存在的有序段（run）并直接合并，对真实世界的部分有序数据快得多。
cutoff 的具体值不要照抄，也不要凭感觉。它取决于元素大小、比较器成本、cache 大小。唯一正确的确定方式是测——用真实数据分布跑一遍 16/24/32/48/64，看曲线。libstdc++ 的 std::sort 用 16（_S_threshold），但那是为 int 这类小对象调的；比较器很贵时最优值会更小。

8.2 并行分治与任务窃取

分治天生适合并行：子问题独立，所以可以同时算。但朴素的「每层都开线程」会立刻崩溃——n=10⁶ 时会创建 10⁶ 个线程。

❌ 每层无脑开线程
void psort(int* a, int lo, int hi) {
    if (hi - lo < 2) return;
    int mid = (lo + hi) / 2;
    std::thread t1([&]{ psort(a, lo, mid); });
    std::thread t2([&]{ psort(a, mid, hi); });
    t1.join(); t2.join();
    merge_into(a, lo, mid, hi);
}
// n=10⁶ → 尝试创建 ~10⁶ 个 OS 线程
// 每个线程默认 8 MB 栈 → 立即 OOM / 创建失败
✅ 双阈值：并行 cutoff + 串行 cutoff
constexpr int PAR_CUTOFF = 1 << 15;  // 32K
constexpr int SEQ_CUTOFF = 32;

void psort(int* a, int lo, int hi, int* buf) {
    int n = hi - lo;
    if (n <= SEQ_CUTOFF) { insertion_sort(a+lo, a+hi); return; }
    int mid = lo + n / 2;
    if (n > PAR_CUTOFF) {          // 只在大块时才并行
        auto fut = std::async(std::launch::async,
                              [&]{ psort(a, lo, mid, buf); });
        psort(a, mid, hi, buf);    // 当前线程做另一半，不闲着
        fut.get();
    } else {
        psort(a, lo, mid, buf);
        psort(a, mid, hi, buf);
    }
    merge_into(a, lo, mid, hi, buf);
}

右边体现了并行分治的三条纪律：

  • 并行阈值远大于串行阈值。任务切分和同步的开销在 μs 量级，所以子任务必须大到值得（经验值：至少几万个元素，或几十 μs 的工作量）。
  • 当前线程要参与干活。「fork 两个、自己等着」浪费了一整个线程；正确做法是 fork 一个、自己做另一个（这也是 Cilk 的 spawn/sync 语义）。
  • 合并步往往是瓶颈。归并的 merge 是串行的 O(n)，按 Amdahl 定律，顶层那次 O(n) 合并单独就限制了加速比上限。真正的并行归并排序要用并行 merge（在一半里二分找另一半的划分点，把合并也切开）。
任务窃取（work stealing）：每个工作线程有自己的双端任务队列，从队尾取自己的任务（LIFO，cache 友好——刚生成的子任务数据还在 cache 里），空闲时从别人的队头偷（FIFO，偷到的是最大最老的任务，摊薄偷取开销）。
这个设计让不均衡的分治（比如快排划分不均）也能自动负载均衡，而且不需要预先知道任务大小。Cilk、Intel TBB、Java 的 ForkJoinPool、Rust 的 Rayon 都是这个模型。

C++17 起标准库提供了并行算法，不必自己写线程池：

// C++17 执行策略（libstdc++ 需要链接 TBB：-ltbb）
#include <execution>
std::sort(std::execution::par_unseq, v.begin(), v.end());
std::reduce(std::execution::par, v.begin(), v.end(), 0LL);
并行算法有三个容易踩的前提：① par_unseq 允许向量化交错执行，所以传入的可调用体不能有任何同步操作（加锁、分配内存都可能死锁）；② std::reduce 要求运算可结合且可交换——浮点加法不满足结合律，所以并行 reduce 的结果可能与 accumulate 不同（且每次运行都可能不同）；③ 元素数量不够大时，并行版本比串行版本更慢。

基线不完备空指针崩溃 / 越界树递归以「空节点」为基线；数组递归先判 lo >= hi
深度 O(n) 且 n 来自外部输入可被构造成 DoS改迭代，或加 depth 断言 + 上限拒绝
重叠子问题未记忆化指数级慢，但结果对加 memo；判据是「同一参数是否被多次调用」
引用参数忘回溯结果多出/污染，不崩push/pop 严格配对，或用 RAII guard
按值传大对象慢且吃内存，profile 里全是拷贝构造改 const&；只在确实需要每层独立副本时按值传
依赖尾调用消除-O0 或加了 RAII 后突然爆栈C++ 里不要依赖 TCO；要么手写循环，要么保证深度 O(log n)
递归里做 I/O 或加锁死锁 / 极慢递归收集，出来后统一 I/O；锁在递归外层拿（或用递归锁，但那通常是设计问题）
相互递归漏了终止isEven/isOdd 式互调无限循环把「规模缩小」的义务落在每一条调用边上
快速幂中间溢出大模数下结果错，小数据测不出__int128 中转，或用快速乘
前三条可以用工具兜住：ASan 的 stack-overflow 检测能把爆栈报成可读的诊断（而不是裸 SIGSEGV）；模糊测试（fuzzing）专门擅长找出「深度嵌套输入把递归解析器打崩」这类问题。工具用法见 Sanitizers 实战。

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础写一个正确的递归需要哪几个要素？各自漏掉会怎样？

    三个要素，缺一不可：

    ① 规模缩小
    每次递归调用的参数必须严格更接近基线。漏掉 → 无限递归 → 爆栈。常见错误是「参数变了」但没变小，比如整数除法里 f((n+1)/2) 在 n=1 时还是 f(1)。
    ② 基线完备
    所有可达的最小情形都要覆盖（空、单元素、0、负数）。漏掉 → 越过基线继续递归 → 崩溃或越界。树递归的通用技巧：以「空节点」而不是「叶子节点」做基线，这样所有分支自动统一，能消掉一半边界 bug。
    ③ 归约关系正确
    假设子调用返回正确答案，你拼出的结果必须对。漏掉 → 不崩但结果错，最难查。

    满足①②后，数学归纳法就替你保证了正确性——这也是为什么递归可以「相信自己」：基线是归纳基础，归约关系是归纳步。

    额外一条（工程）
    还要问「深度会是多少」。O(log n) 深度永远安全；O(n) 深度且 n 由外部输入决定时，这是个安全问题而不只是性能问题——攻击者可以用深度嵌套的输入把爆栈变成 DoS。
  2. 基础递归为什么会爆栈？爆栈时程序表现是什么，能被 catch 吗？

    每次函数调用都要在栈上压一个栈帧，存返回地址、保存的寄存器、参数和局部变量，典型 32–128 字节。递归深度 = 栈帧数，深度太大就超出栈空间。

    数量级
    Linux 默认线程栈 8 MB（Windows 主线程 1 MB）。按 64 B/帧算约 13 万层。所以安全深度大约 10⁴–10⁵；帧里有大数组时会骤降到几千层。
    不能 catch
    栈溢出不是 C++ 异常。内核在栈末端放了不可访问的 guard page，越过时触发页错误，内核判定不是合法栈扩展，发 SIGSEGV。程序当场死，try/catch 完全拦不住。

    怎么认出是爆栈：gdb 的 bt 里同一个函数重复上万帧（或直接 Backtrace stopped）；出错地址紧邻 rsp；ASan 报 stack-overflow 而不是 SEGV on unknown address。

    实用技巧
    给递归函数加 depth 参数并 assert(depth < N)。它在爆栈之前触发，给出干净可读的回溯，而不是一堆重复帧。处理外部输入（嵌套 JSON、递归下降解析器）时这几乎是必须的。
  3. 基础朴素 Fibonacci 递归为什么是指数级？加一行代码怎么变成 O(n)？

    因为存在重叠子问题：fib(5) 展开后 fib(3) 被算 2 次、fib(2) 被算 3 次，越往下重复越多。递归树有 O(φⁿ)≈O(1.618ⁿ) 个节点，但本质不同的子问题只有 n+1 个。

    记忆化——加一行查表：

    long long fib(int n, std::vector<long long>& memo) {
    if (n < 2) return n;
    if (memo[n] != -1) return memo[n];   // ← 这一行
    return memo[n] = fib(n-1, memo) + fib(n-2, memo);
}

    每个 n 只算一次 → O(n) 时间。但栈深仍是 O(n)，n=10⁶ 照样爆栈。

    继续优化的四步路径
    朴素递归 → 记忆化（消重复） → 自底向上迭代（消栈深） → 滚动变量（消空间，O(1)）。这四步是绝大多数 DP 题的通用优化顺序。Fibonacci 还能用矩阵快速幂做到 O(log n)。
    判据
    「子问题是否重叠」是区分该用 DP 还是该用分治的唯一标准。归并排序的左右两半完全不相交，所以不需要记忆化；Fibonacci 的两个子调用共享大量子子问题，所以必须记忆化。
  4. 基础什么是分治？它的三步是什么？举两个例子。

    分治是把规模 n 的问题拆成若干规模更小、互不重叠的子问题，递归解决后合并。

    Divide
    拆成 a 个规模 n/b 的独立子问题
    Conquer
    递归解决（规模小于 cutoff 时直接算）
    Combine
    合并子解，代价 f(n)
    T(n) = a·T(n/b) + f(n) → 用主定理求解

    例一 · 归并排序：切成左右两半（a=2, b=2），递归排序，然后 O(n) 归并 → T(n)=2T(n/2)+Θ(n) = Θ(n log n)。

    例二 · 二分查找：切成两半但只需递归一半（a=1, b=2），合并代价 Θ(1) → T(n)=T(n/2)+Θ(1) = Θ(log n)。

    分治 vs DP
    关键区别是子问题是否独立。分治的子问题不相交（左半排序不需要右半的任何信息），所以不需要记忆化。DP 的子问题重叠，必须记忆化。看到「子问题会重复出现」就该想 DP，看到「切开后互不相干」就该想分治。

10.2 中级（区分熟练度）

  1. 中级什么是尾递归？为什么在 C++ 里不能依赖尾调用消除？

    尾调用指函数的最后一个动作是调用另一个函数并直接返回其结果，中间没有任何额外运算。编译器可以复用当前栈帧、把 call 换成 jmp，递归就变成了循环，栈深恒为 1。

    不是尾递归
    return n * fact(n-1);
// 返回后还要乘 → 帧必须保留（存 n）
    是尾递归
    return fact(n-1, acc*n);
// 用累加器把「返回后的工作」搬进参数

    C++ 里不能依赖它，因为 TCO 是优化而非语言保证（Scheme、Lua 在标准层面强制要求，C++ 没有）。失效原因：

    最隐蔽的一条
    局部对象有析构函数。析构必须在 return 之后执行，所以那个调用其实不在尾位置：
    int f(int n) {
    std::string tmp = log(n);  // 有析构
    return f(n-1);          // 看着是尾调用，实际不是
}
    这是 C++ 特有的，RAII 越用得好越容易撞上。
    其他原因
    -O0/-Og、虚函数或函数指针调用（目标不确定）、返回大对象走 sret、开了 sanitizer 或 -fno-optimize-sibling-calls。
    正确做法
    需要 O(1) 栈深 → 手写循环；需要 O(log n) 上限 → 只递归小半边。Clang 的非标准 __attribute__((musttail)) 会在做不到 TCO 时编译报错，把玄学变成确定性，代价是不可移植。
  2. 中级怎么把任意递归机械地改成迭代？以二叉树后序遍历为例。

    通用方法：自己维护栈，栈里存 (局部状态, 执行到哪一步)。后者就是把编译器帮你记住的「返回地址」显式化。

    前序好改，因为访问发生在递归之前，一个节点只需被「碰」一次：

    std::vector<TreeNode*> st{r};
while (!st.empty()) {
    auto* n = st.back(); st.pop_back();
    visit(n);
    if (n->right) st.push_back(n->right);  // 右先入 → 左先出
    if (n->left)  st.push_back(n->left);
}

    后序难，因为节点要等两棵子树都完成，会被回到多次。所以栈里必须记录阶段：

    std::vector<std::pair<TreeNode*, int>> st{{r, 0}};
while (!st.empty()) {
    auto& [n, stage] = st.back();
    if (stage == 0)      { ++stage; if (n->left)  st.push_back({n->left,  0}); }
    else if (stage == 1) { ++stage; if (n->right) st.push_back({n->right, 0}); }
    else                 { visit(n); st.pop_back(); }
}
    这就是去递归化的本质
    stage 扮演的正是栈帧里那个「返回地址」。任何递归都能这样机械改写，代价是可读性直线下降。C++20 协程做的事本质相同——把局部状态和「执行到哪一行」打包搬到堆上。
    工程取舍
    深度有 O(log n) 保证时就用递归，可读性完胜。深度可能 O(n) 且 n 由外部输入决定时必须去递归（防 DoS）。还有第三条路：换算法——Morris 遍历用叶子的空右指针线索化，O(1) 空间且无栈；图遍历用 BFS 代替 DFS，队列在堆上天然不爆栈。
  3. 中级怎么用归并排序在 O(n log n) 内统计逆序对？说清关键那一步。

    把统计嵌进归并的合并步。关键洞察：合并两个已排序半段时，若从右半取出 a[j]，说明左半剩下的所有元素都比它大——那么左半剩余个数就是以 a[j] 为右端点的逆序对数，一次加完。

    int i = lo, j = mid, k = lo;
while (i < mid && j < hi) {
    if (a[i] <= a[j]) buf[k++] = a[i++];
    else {
        cnt += mid - i;          // ← 关键一行
        buf[k++] = a[j++];
    }
}

    总复杂度就是归并排序本身：T(n)=2T(n/2)+Θ(n) = Θ(n log n)。

    别写错等号
    a[i] <= a[j] 里的等号同时决定两件事：① 相等元素不被算成逆序对（正确性）；② 相等时优先取左边（稳定性）。写成 < 两者同时坏掉。
    模式识别
    这属于「在分治的合并步顺便统计跨界信息」这一类。识别信号是：要统计的东西可以在「左半 × 右半」的跨界配对上一次算清。同一套模板还能解「翻转对（a[i] > 2·a[j]）」「区间内小于 x 的个数」「三元逆序对」。
    替代解法
    树状数组（BIT）+ 离散化也是 O(n log n)，从右往左扫，每次查询「已插入的比当前小的个数」。分治版不需要离散化、常数更小；BIT 版更容易扩展成在线查询。
  4. 中级快速选择为什么是期望 O(n) 而快排是 O(n log n)？std::nth_element 怎么保证最坏 O(n)？

    差别只有一处：快排划分后两边都要递归，快选只需递归一边（第 k 小只可能在一边）。

    快排：T(n) = 2T(n/2) + Θ(n) → Θ(n log n) 快选：T(n) = 1T(n/2) + Θ(n) → Θ(n) 主定理情形三：f(n)=Θ(n) 压过 n^log₂1 = n⁰ = 1

    更直观地：随机 pivot 时每次期望切掉常数比例，代价是几何级数 n + 3n/4 + 9n/16 + … < 4n。注意是「期望」不是「最坏」——最坏（每次 pivot 都取到极值）仍是 O(n²)。

    std::nth_element 用 introselect：

    快路径
    随机化/启发式 pivot 的快速选择，常数小。
    慢路径兜底
    监控递归深度，超过阈值（约 2 log n）就切换到有最坏 O(n) 保证的算法（median-of-medians 或改用堆）。
    方案最坏实测常数
    随机化快选O(n²)小
    median-of-mediansO(n)大 5–10×
    introselectO(n)小
    这是个可复用的设计模式
    「快路径求常数，慢路径兜底最坏，用一个廉价的监控量在两者间切换」——std::sort 的 introsort 也是这个结构（超深转堆排）。它的价值在于：你既拿到了随机化算法的实测速度，又拿到了确定性算法的最坏保证，代价只是一个深度计数器。

10.3 高级（体现深度）

  1. 高级Karatsuba 为什么能把 O(n²) 降到 O(n^1.585)？这个思路的一般形式是什么？

    把 n 位数切成高低两半 x = x₁B + x₀、y = y₁B + y₀，展开得：

    x·y = x₁y₁·B² + (x₁y₀ + x₀y₁)·B + x₀y₀

    朴素分治要算 4 个子乘积 → T(n)=4T(n/2)+O(n)，c*=log₂4=2 → Θ(n²)，完全白干。

    Karatsuba 用一次额外加减把 4 次降到 3 次：

    P₁ = x₁y₁, P₂ = x₀y₀, P₃ = (x₁+x₀)(y₁+y₀) x₁y₀ + x₀y₁ = P₃ − P₁ − P₂ ← 中间项用减法得到 T(n) = 3T(n/2) + O(n) → Θ(n^log₂3) ≈ Θ(n^1.585)
    为什么降 a 这么值钱
    在主定理情形一（叶子主导）里，复杂度 = Θ(n^log_b a)，完全由 a 决定，f(n) 无关。所以 a 从 4→3 就把指数从 2 降到 1.585。优化合并步（f）在情形一里毫无收益——这是设计分治算法时最重要的一条判断。
    一般形式
    用便宜的运算换贵的运算。乘法比加减贵得多（大数上尤其），所以多做几次加减去省一次乘法总是划算。同一交易的其他实例：Strassen 矩阵乘（8 次子矩阵乘 → 7 次，代价 18 次矩阵加减，得 Θ(n^2.807)）、Toom-Cook（切 k 份，用多项式插值省乘法）、FFT 乘法（把卷积搬到频域，Schönhage–Strassen 达 O(n log n log log n)）。
    渐进不等于实用
    GMP 的策略是按位数分段选算法：小数走竖式、中等 Karatsuba、更大 Toom-Cook、超大 FFT。因为 Karatsuba 的递归 + 临时空间常数远大于竖式，交叉点在几十个 limb。同理 OpenBLAS/MKL 的 GEMM 不用 Strassen——分块 + SIMD + FMA 的常数优势有 10–20×，而且 Strassen 数值稳定性更差，这是渐进分析完全看不见的成本。
  2. 高级为什么生产级归并排序不递归到单元素？cutoff 该怎么定？

    因为小规模时递归本身的开销超过了算法优势。四条理由，最后一条最有说服力：

    递归开销占比
    n=4 时，函数调用 + 栈帧建立 + 边界判断的成本超过实际的比较与移动。
    插入排序常数极小
    顺序访问、零分配、分支高度可预测（近乎有序时几乎无分支误预测）。
    小数组整块在 L1
    32 个 int = 128 字节 = 两条 cache line，全程命中。
    叶子占一半节点
    二叉递归树里叶子数约等于内部节点数。砍掉最底几层等于消掉一半的函数调用——这是收益最大的地方。

    cutoff 怎么定：不要照抄，也不要凭感觉。它取决于元素大小、比较器成本、cache 大小。唯一正确的方式是用真实数据分布测 16/24/32/48/64 看曲线。libstdc++ 的 std::sort 用 16（_S_threshold），那是为 int 调的；比较器很贵时最优值更小。

    另一个必加的优化
    if (a[mid-1] <= a[mid]) return;  // 两半已首尾有序 → 跳过整个合并
    对已排序或近乎有序的输入，这一行把 Θ(n log n) 变成 Θ(n)。TimSort（Python/Java）把这个思路做到极致：主动识别输入里天然存在的有序段（run）并直接合并，对真实世界的部分有序数据快得多——真实数据几乎从不是均匀随机的，这是个被低估的优化方向。
  3. 高级并行化一个分治算法，你会怎么做？会踩哪些坑？

    分治天生适合并行（子问题独立），但每层无脑开线程会立刻崩——n=10⁶ 时试图创建 10⁶ 个 OS 线程，每个默认 8 MB 栈，直接 OOM。

    正确做法是双阈值 + 当前线程参与：

    if (n <= SEQ_CUTOFF)  { insertion_sort(...); return; }
if (n > PAR_CUTOFF) {                    // 只在大块时并行
    auto fut = std::async(std::launch::async, [&]{ psort(lo, mid); });
    psort(mid, hi);                      // 当前线程做另一半，不闲着
    fut.get();
} else { psort(lo, mid); psort(mid, hi); }
    坑一：粒度太细
    任务切分和同步开销在 μs 量级。PAR_CUTOFF 要远大于 SEQ_CUTOFF（经验值：子任务至少几万元素、几十 μs 工作量）。粒度不够时并行版比串行版更慢。
    坑二：fork 两个自己等着
    浪费一整个线程。正确是 fork 一个、自己做另一个（Cilk 的 spawn/sync 语义）。
    坑三：合并步是串行瓶颈
    归并的 merge 是 O(n) 串行的。按 Amdahl 定律，顶层那一次 O(n) 合并单独就把加速比压在有限值上——哪怕下面全并行了。真正的并行归并排序必须用并行 merge：在一半里二分查找另一半的划分点，把合并也切开。
    为什么用任务窃取而不是静态划分
    分治的子任务大小事先不可知（快排划分可能极不均）。任务窃取让每个线程有自己的双端队列：从队尾取自己的（LIFO，刚生成的子任务数据还在 cache 里）、空闲时从别人队头偷（FIFO，偷到最大最老的任务，摊薄偷取开销）。这样不均衡的分治也能自动负载均衡。Cilk / TBB / ForkJoinPool / Rayon 都是这个模型。
    用标准库时的三个前提
    par_unseq 允许向量化交错，可调用体不能有任何同步（加锁、分配都可能死锁）；std::reduce 要求运算可结合可交换——浮点加法不满足结合律，所以并行结果可能与 accumulate 不同，甚至每次运行都不同；libstdc++ 需要 -ltbb。
  4. 高级线上一个递归下降的配置解析器被一条请求打崩了，怎么定位和根治？

    症状（SIGSEGV、只在特定输入下复现、Debug 版可能不复现）指向栈溢出，而且是被外部输入触发的——这是个安全问题，不只是 bug。

    ① 确认是爆栈
    gdb 的 bt 里同一个 parseValue/parseObject 重复上万帧，或直接 Backtrace stopped；出错地址紧邻 rsp。用 -fsanitize=address 重跑，ASan 会明确报 stack-overflow（而不是 SEGV on unknown address）。
    ② 找触发输入
    攻击载荷通常是深度嵌套：[[[[[...]]]]] 或 {"a":{"a":{"a":...}}}。几十 KB 的请求体就能造出几万层嵌套。用 fuzzer 复现——libFuzzer/AFL 特别擅长找这类问题。

    止血（当天）：在解析入口加深度计数，超限直接拒绝请求：

    if (++depth_ > kMaxDepth) throw ParseError{"nesting too deep"};

    注意限制要在解析时逐层检查，不能只检查输入长度——短输入也能造出深嵌套。

    根治（这是真正的答案）
    光加个上限只是把崩溃换成拒绝，还有三件事要做：① 改成显式栈的迭代解析（栈在堆上，深度只受内存限制且可优雅报错），成熟 JSON 库（simdjson、RapidJSON 的迭代模式）都是这么做的；② 把「所有处理不可信输入的递归必须有显式深度上限」写进 review 清单，并搜一遍全仓库其他递归下降代码（协议解析、表达式求值、模板渲染、XML/YAML）——同类代码几乎一定不止一处；③ 把 fuzzing 挂进 CI，专门喂嵌套结构的语料，让下次回归在合并前就被拦住。
    再往上一层看
    这类事故的共性是「输入的某个维度没有上界，而代码里有个隐式的资源随它线性增长」。递归深度 vs 栈只是其中一例；同构的问题还有：数组长度字段没校验 → 一次分配 4 GB、正则回溯 → ReDoS、解压缩比没限制 → zip bomb。写「解析不可信输入」的代码时，应该逐个资源维度问「上界在哪，谁保证」。
