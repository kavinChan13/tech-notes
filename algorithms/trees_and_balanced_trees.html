树与平衡树

树结构的全部价值来自一句话：把 n 个元素组织成 log n 层，让每次操作只走一条路径。而工程上的所有分歧都在「怎么保证它真的只有 log n 层」——AVL 用严格的高度约束，红黑树用放松的颜色约束，B+ 树用变宽的节点，跳表干脆用随机数。这一篇把这四条路的取舍讲清，并说明为什么它们分别赢下了不同的战场。

01

本质：用层级换对数

以及「保证 log n 层」的四条路

线性结构里查找是 O(n)，因为你只能一个个走。树引入层级：每往下一层就排除掉一大部分候选，于是 O(n) 变成 O(树高)。

但「树高 = log n」不是免费的。一棵二叉搜索树在最坏情况下会退化成一条链（树高 n），此时它比数组还差——既是 O(n) 又有指针追逐的开销。

所以树结构的核心问题不是「怎么查找」（那很简单），而是「怎么在插入删除后仍然保证树是矮的」。历史上有四种答案：
  • 严格控制高度差（AVL）——左右子树高度差 ≤ 1，靠旋转维护。
  • 放松成颜色约束（红黑树）——用「黑高相等 + 不能有连续红节点」间接限制高度 ≤ 2log(n+1)。
  • 把节点变宽（B / B+ 树）——每节点存几百个 key，树高 log_B n 降到 3–4 层。
  • 放弃确定性，用随机（跳表）——期望层高 log n，完全不需要旋转。
四种平衡策略像四种管理组织架构的方式。

AVL 是最严格的 HR：任何两个部门的层级深度不能差超过一级，一旦超了立刻重组。查询效率最高（组织最扁），但重组太频繁。
红黑树 是务实的 HR：允许一定的不平衡，只要「从上到下经过的正式编制人数相同」且「不能有两个连续的临时编制」。查询稍慢一点，但重组次数少得多。
B+ 树 换了个思路：不减少人数，而是把每个部门做得很大。一个部门 500 人，三层就能管十亿人——因为跨部门沟通（磁盘 I/O）比部门内沟通（内存）贵一千倍。
跳表 最省事：每个人入职时掷骰子决定自己算几级。期望上层级分布正好是对数的，而且没人需要重组。

1.1 与其他章节的关系

  • 递归与分治 —— 树遍历是递归最自然的场景；Morris 遍历是「换算法消掉栈」的例子
  • 并查集与区间结构 —— 线段树、树状数组是「为区间查询而设计的树」
  • 二分查找 —— B+ 树的页内二分、跳表的层级跳跃
  • 堆与 Top-K —— 堆也是树，但它刻意不维护全序（对比 BST）

二叉树遍历

三种序、迭代统一模板、以及 O(1) 空间的 Morris

2.1 三种递归序

// 三种序的区别只在 visit(root) 那一行的位置
void preorder(Node* r)  { if (!r) return; visit(r); preorder(r->l);  preorder(r->r);  }
void inorder(Node* r)   { if (!r) return; inorder(r->l);  visit(r); inorder(r->r);   }
void postorder(Node* r) { if (!r) return; postorder(r->l); postorder(r->r); visit(r); }
序什么时候用它典型题
前序（根 → 左 → 右）信息从上往下传递序列化、路径和、深拷贝、打印目录树
中序（左 → 根 → 右）BST 上得到有序序列验证 BST、第 k 小、BST 转链表
后序（左 → 右 → 根）信息从下往上汇总求高度、删除整棵树、最近公共祖先、子树聚合
层序（BFS）按距离根的层数处理最小深度、每层最大值、锯齿遍历
选序的判据只有一条：「我需要的信息是从上往下给的，还是从下往上收的？」
  • 「从根到当前节点的路径和」→ 参数往下传 → 前序。
  • 「以当前节点为根的子树高度 / 节点数 / 是否平衡」→ 返回值往上收 → 后序。
  • 两者都要（如「求直径」：既要子树高度又要更新全局答案）→ 后序 + 一个引用参数记全局值。
这个判据比记「前中后」三个字管用得多——大多数树题的难点是选序，不是写代码。

2.2 迭代版的统一模板

前序好改（访问在递归前），后序难改（要等两个子树都完成）。有一个统一模板能覆盖三种序，代价是每个节点入栈两次：

// 统一模板：栈里存 (节点, 是否已展开)
// 改变 push 的顺序就能得到三种序
void traverse(Node* root) {
    std::vector<std::pair<Node*, bool>> st;
    if (root) st.push_back({root, false});
    while (!st.empty()) {
        auto [n, expanded] = st.back(); st.pop_back();
        if (expanded) { visit(n); continue; }   // 第二次遇到 → 真正访问

        // 第一次遇到 → 按「逆序」压入，因为栈是后进先出
        // 中序：右 → 自己 → 左
        if (n->r) st.push_back({n->r, false});
        st.push_back({n, true});
        if (n->l) st.push_back({n->l, false});
    }
}
// 前序：把 {n,true} 放最前  → 自己 → 右 → 左（压入顺序）
// 后序：把 {n,true} 放最后  → 右 → 左 → 自己
这个模板的价值是「一份代码三种序」：只需调整三行 push_back 的先后。expanded 标记扮演的正是递归转迭代里那个「程序计数器」的角色——它记录「这个节点是第一次碰到（要展开）还是第二次碰到（要访问）」。

代价是每节点入栈两次、每次多存一个 bool。如果只要前序，专用的单次入栈版本更快；需要三种序都写、或需要后序时，用这个模板最省心。

2.3 Morris 遍历

递归和显式栈都需要 O(h) 空间。Morris 遍历用 O(1) 空间完成中序遍历，办法是临时借用叶子节点的空右指针。

void morris_inorder(Node* root) {
    Node* cur = root;
    while (cur) {
        if (!cur->l) {                       // 无左子：直接访问，转右
            visit(cur);
            cur = cur->r;
        } else {
            Node* pre = cur->l;              // 找左子树最右节点（中序前驱）
            while (pre->r && pre->r != cur) pre = pre->r;
            if (!pre->r) {                   // 第一次到：建线索，下潜
                pre->r = cur;
                cur = cur->l;
            } else {                         // 第二次到：左子树已完成
                pre->r = nullptr;             // 断线索，恢复原结构
                visit(cur);
                cur = cur->r;
            }
        }
    }
}
Morris 遍历在遍历过程中修改了树的结构（虽然结束时会恢复）。这带来三个真实限制：
  • 不能并发遍历，也不能在遍历时被其他线程读到——它们会看到不一致的树。
  • 遍历中抛异常会留下损坏的树（线索没断开），之后的任何操作都可能死循环。visit 里有可能抛异常时不要用它。
  • 树必须是可写的（不能是 const）。
所以它的实际用途很窄：只在「树极深（递归会爆栈）且内存极紧」时才值得。一般情况下用显式栈（O(h) 空间，h 通常是 log n）就够了。但它是面试里体现「知道有 O(1) 方案」的好谈点。
03

二叉搜索树

简单、优雅、且随时可能退化

BST 的性质：左子树所有值 < 根 < 右子树所有值。由此得到两个推论：中序遍历是有序序列；查找就是不断二分。

「验证 BST」是高频题，最常见的错法是只比较父子： 
// ❌ 只保证局部有序，不保证全局
bool bad(Node* r) {
    if (!r) return true;
    if (r->l && r->l->val >= r->val) return false;
    if (r->r && r->r->val <= r->val) return false;
    return bad(r->l) && bad(r->r);
}
// 反例：  5
//       /   \     3 < 5 ✓，7 > 5 ✓，但 6 在左子树里却 > 5 ✗
//      3     7
//       \
//        6
正确写法有两种：① 往下传 (min, max) 区间（前序）；② 中序遍历时记住前一个值，检查严格递增（更简洁，且能处理重复值语义）。

3.1 删除的三种情形

值拷到当前节点，然后递归删除它 关键：后继/前驱最多只有一个孩子 → 递归必然落到情形一或二，不会无限展开 
Node* erase(Node* r, int key) {
    if (!r) return nullptr;
    if (key < r->val)      r->l = erase(r->l, key);
    else if (key > r->val) r->r = erase(r->r, key);
    else {
        if (!r->l) { Node* t = r->r; delete r; return t; }  // 情形一/二
        if (!r->r) { Node* t = r->l; delete r; return t; }
        // 情形三：用中序后继（右子树最左节点）的值顶替
        Node* succ = r->r;
        while (succ->l) succ = succ->l;
        r->val = succ->val;
        r->r = erase(r->r, succ->val);       // 递归删除后继（必落情形一/二）
    }
    return r;
}
用后继还是前驱都对，但总是用同一个会让树逐渐偏向一侧。有些实现会交替使用（或按子树高度选较高的那侧），以延缓退化。这个细节在朴素 BST 里意义不大（反正会退化），但在实现平衡树时会影响旋转次数。

3.2 为什么会退化

BST 的最坏情形是「按顺序插入」：插入 1,2,3,…,n 会得到一条只有右孩子的链，树高 n，所有操作退化到 O(n)。

糟糕的是「按顺序插入」在真实数据里极其常见——自增 ID、时间戳、排好序的导入文件。所以朴素 BST 在生产上基本不可用。

平均情形（随机插入顺序）下树高是 O(log n)，但这依赖输入分布假设——和快排的平均 O(n log n) 一样，可被攻击者构造（见 复杂度与分析 §4.5）。
解决思路代表保证类型
每次插删后主动调整AVL、红黑树确定性：最坏 O(log n)
随机化结构跳表、Treap期望 O(log n)（攻击者不可控）
按访问频率自适应调整Splay 树摊销 O(log n)
加宽节点降低树高B / B+ 树确定性：最坏 O(log_B n)
04

平衡的两种流派

严格 vs 放松，查询快 vs 修改快

4.1 旋转

旋转是所有平衡树的基本操作：在保持中序序列不变的前提下，改变树的形状。

// 右旋：把左孩子提为根。左旋对称
Node* rotate_right(Node* y) {
    Node* x = y->l;
    y->l = x->r;      // B 挂到 y 的左边
    x->r = y;         // y 成为 x 的右孩子
    // AVL 还要更新 x、y 的高度；红黑树还要改颜色
    return x;         // 新的子树根
}

4.2 AVL：严格平衡

AVL 的不变式：每个节点的左右子树高度差 ≤ 1（平衡因子 ∈ {−1, 0, +1}）。
由此推出树高上界 ≈ 1.44 log₂(n+2)——非常接近完美平衡的 log₂n。

四种失衡与对应的旋转：
  • LL（左子的左子过高）→ 一次右旋
  • RR（右子的右子过高）→ 一次左旋
  • LR（左子的右子过高）→ 先对左子左旋，再右旋
  • RL（右子的左子过高）→ 先对右子右旋，再左旋
记忆方法：「失衡的方向决定旋转方向，两个字母不同就要先转成相同」。

4.3 红黑树：放松平衡

红黑树不直接约束高度，而是用颜色间接约束。五条性质：

#性质它保证了什么
1每个节点是红或黑—
2根是黑规范化，简化插入的情形分析
3所有叶子（NIL）是黑规范化，让「黑高」定义清晰
4红节点的孩子必须是黑（不能有连续红）红节点最多占路径的一半
5任一节点到其所有后代叶子的黑节点数相同（黑高相等）最短路径 ≥ 黑高
高度上界的推导 设黑高为 bh。 · 由性质 5：任何路径至少有 bh 个黑节点 · 由性质 4：红节点不能相邻 ⟹ 任何路径长度 ≤ 2·bh · 黑节点构成的子树至少是完美二叉树 ⟹ n ≥ 2^bh − 1 ⟹ bh ≤ log₂(n+1) ∴ 树高 h ≤ 2·bh ≤ 2 log₂(n+1)
性质 4 和 5 的组合像「正式员工 + 实习生」的层级规则。
性质 5 说：从任何管理者往下到任何一线，经过的正式员工数量必须相同——这保证了组织不会某一支特别深。
性质 4 说：实习生下面不能再带实习生——这保证了实习生最多占掉一半层级。

两条合起来：最深的路径最多是最浅路径的两倍。这个「两倍」的松弛正是红黑树比 AVL 修改更快的原因——它容忍更多的不平衡，所以需要调整的次数少得多。

4.4 对照与选型

AVL红黑树
高度上界≈1.44 log n2 log n
查找更快（树更矮）稍慢
插入的旋转次数最多 2 次最多 2 次
删除的旋转次数最多 O(log n) 次最多 3 次
需要额外存高度（int）或平衡因子（2 bit）颜色（1 bit，常塞进指针低位）
实现复杂度较简单（四种旋转）复杂（删除有多种情形）
典型使用者数据库索引（部分）、内存数据库std::map、Java TreeMap、Linux CFS、epoll
关键差异在删除：AVL 删除后可能需要沿路径一路调整（每层一次旋转），最坏 O(log n) 次旋转；红黑树的删除修复最多 3 次旋转（其余通过改颜色解决）。

所以选型判据是读写比：
  • 读远多于写 → AVL（树矮 30%，查找更快）。
  • 读写均衡或写多 → 红黑树（修改代价更可控）。
标准库选红黑树，是因为通用容器无法预知读写比，而红黑树的「最坏修改代价」更小——这是保守但正确的默认。
05

红黑树在工程里

三个真实场景，三个不同的选它的理由

5.1 五条性质保证了什么

前面推导了高度上界。这里补一条实践角度的解读：为什么工程上愿意接受「2 log n」而不追求「1.44 log n」。

场景选红黑树的真实理由
std::map / std::set迭代器稳定性：插入不失效任何迭代器，删除只失效被删的那个。这是接口契约，比性能更重要。
Linux CFS 调度器按 vruntime 排序，需要频繁插删 + 每次取最小。红黑树的删除代价可控，且「最左节点」可以缓存成 O(1)。
epoll 的兴趣列表fd 数量大、增删频繁（连接建立/关闭），需要 O(log n) 的确定性——不能像哈希表那样偶尔 rehash 停顿。
Linux 内核的 VMA 管理需要范围查询（「这个地址落在哪个 VMA 里」），哈希表做不到。
nginx 的定时器需要「取最近到期 + 频繁取消」，红黑树的 O(log n) 删除比堆的 O(n) 查找好（见 堆与 Top-K §9）。
注意这张表里没有一个理由是「红黑树查找最快」。真实理由分三类：① 需要有序性 / 范围查询（哈希表做不到）；② 需要确定性延迟（哈希表会 rehash 抖动）；③ 需要迭代器 / 引用稳定性。
这也是选 std::map 而不是 unordered_map 的三个正当理由——如果都不需要，那就该用哈希表。

5.2 std::map / epoll / CFS

一个实现细节：libstdc++ 的 _Rb_tree 把颜色存在一个单独的枚举字段里，而不是塞进指针低位。这浪费了几个字节（对齐后可能是 8 字节），但换来了可移植性和调试友好。
Linux 内核的 rb_node 则把颜色塞进 __rb_parent_color 的最低位——因为节点必然 4 字节对齐，低 2 位一定是 0，可以借用。这是内核里常见的「指针位偷用」技巧，代价是每次访问 parent 都要 mask 一下。
同一个结构在「通用库」和「内核」两种约束下会做出不同的取舍——这类对比比单纯记算法更有价值。
红黑树在实践中的一个常见误解：「红黑树比哈希表慢」不总成立。n 较小时（几十到几百），std::map 常常比 unordered_map 快：
  • 树的上层节点常驻 cache（被反复访问），实际 miss 次数远少于 log n。
  • 哈希表要先算 hash（string 键要扫全串），再做一次随机地址访问（几乎必然 miss）。
交叉点大约在 n 几百到一千，强烈依赖 key 类型与哈希成本。小容器上先别急着换哈希表。
06

B 树与 B+ 树

当「一次比较」和「一次跳转」的代价差一千倍

6.1 又矮又胖的动机

内存里：一次节点跳转 ≈ 100 ns（cache miss） 磁盘上：一次节点跳转 ≈ 100 µs（SSD）～ 10 ms（HDD） 差 1000 倍以上 ⟹ 优化目标从「减少比较次数」变成「减少跳转次数」 ⟹ 把节点做成一个磁盘页大小（4~16 KB），每页放几百个 key 二叉搜索树：log₂(10⁹) ≈ 30 次 I/O B+ 树 (B≈500)：log₅₀₀(10⁹) ≈ 3~4 次 I/O
B+ 树的智慧是「用页内的廉价二分换掉昂贵的跨页跳转」。页内对几百个 key 做二分需要 8–10 次比较，但那全在内存里（100 ns 量级）；省下来的是 26 次磁盘 I/O（100 µs 量级）。

这是二分查找 §9.2 讲过的「两层不同代价单位」的完整版本。

6.2 B 与 B+ 的差别

B 树B+ 树
数据存哪内部节点也存数据只有叶子存数据，内部节点只存 key
每页能放多少 key较少（数据占空间）更多 → 树更矮
叶子之间无连接按序链成链表
范围扫描要回树中序遍历顺着叶子链表顺序 I/O
单点查找可能在内部节点就命中（更快）必须走到叶子（深度固定）
典型使用者部分文件系统（如 ext4 的 htree）MySQL InnoDB、PostgreSQL、几乎所有 RDBMS
B+ 树胜出的决定性理由是范围扫描。SQL 里 WHERE x BETWEEN a AND b、ORDER BY x、GROUP BY x 都是范围操作，而叶子链表让它们变成顺序 I/O——这在磁盘上比随机 I/O 快一到两个数量级。
「单点查找可能在内部节点命中」这个 B 树的优势，相比之下微不足道，而且它还让树变高了。

顺带解释了为什么数据库要「覆盖索引」：如果查询需要的所有列都在索引的叶子里，就不用回主表（回表 = 又一轮 B+ 树查找 + 随机 I/O）。完整讨论见 关系型数据库。
B+ 树在写密集负载下有个固有弱点：随机插入会导致页分裂和随机写。这就是 LSM-Tree 存在的理由——它把随机写变成顺序写（写内存表 + 顺序落盘 + 后台 compaction），代价是读放大和写放大。
「B+ 树 vs LSM」的选型本质是「读优化 vs 写优化」，见 存储与数据架构。

跳表：用随机代替旋转

同样的 O(log n)，代码只有平衡树的三分之一

跳表红黑树
复杂度保证期望 O(log n)最坏 O(log n)
实现代码量约 1/3（无旋转、无颜色）多，删除情形复杂
范围扫描最底层就是有序链表，天然支持要中序遍历
并发友好度高（局部修改，易做无锁）低（旋转影响多个节点）
空间每节点期望 1/(1−p) 个指针（p=1/2 时约 2）固定 2 个指针 + 颜色
cache 友好度低（多层指针追逐）低（也是指针追逐）

Redis 为什么用跳表而不是红黑树（作者 antirez 亲自回答过）：
  • ZSet 需要范围查询（ZRANGE、ZRANGEBYSCORE），跳表的底层就是有序链表，天然支持且是顺序访问。
  • 实现和调试简单得多——没有旋转，没有颜色，删除逻辑直白。对一个要长期维护的开源项目，这是实质性的优势。
  • 可以方便地实现「按排名查找」（在每个前进指针上记跨度 span 即可）。红黑树要做这个得额外维护子树大小。
注意「并发友好」不是 Redis 的理由（它是单线程），但那是 ConcurrentSkipListMap 和 RocksDB memtable 选它的核心理由。同一个结构在不同系统里被选中的原因可以完全不同。
08

Trie 与它的压缩形态

按「键的结构」而不是「键的比较」组织

8.1 基本结构

BST 和哈希表都把键当成一个不可分割的整体（要么比较，要么哈希）。Trie 反过来——它利用键的内部结构，把公共前缀合并成一条路径。

struct TrieNode {
    std::array<TrieNode*, 26> next{};   // 或 unordered_map<char, TrieNode*>
    bool is_end = false;
};

void insert(TrieNode* root, const std::string& w) {
    TrieNode* cur = root;
    for (char c : w) {
        int i = c - 'a';
        if (!cur->next[i]) cur->next[i] = new TrieNode();
        cur = cur->next[i];
    }
    cur->is_end = true;
}
// 查找 / 插入都是 O(len)，与 Trie 里有多少个词无关
Trie 的复杂度是 O(键长) 而不是 O(log n)，这是它和比较型结构的本质区别。当键很短而集合很大时（比如 100 万个单词，平均长 8）——O(8) 完胜 O(log 10⁶) = O(20)。

它还免费提供了两个哈希表和 BST 都做不到的能力：
  • 前缀查询：「所有以 abc 开头的词」——走到 abc 节点然后遍历子树。
  • 最长前缀匹配：「输入 abcdef，找出集合里最长的那个是它前缀的词」——一路往下走，记住最后一个 is_end。这是路由表和 IP 查找的核心操作。
朴素 Trie 的空间开销极大：每个节点 26 个指针 = 208 字节（64 位），而实际可能只用了 1–2 个。存 100 万个单词、平均长 8，节点数可能到几百万 → 几百 MB。
三种压缩手段：① 用 unordered_map 或有序小数组代替定长数组（省空间，但多一次查找）；② 路径压缩（把单链的路径合并成一个节点，即基数树）；③ 自适应节点（按孩子数量选不同的节点表示，即 ART）。

8.2 基数树与 ART

变体核心改进使用者
基数树 / Patricia trie路径压缩：只有一个孩子的连续节点合并成一个（存一段字符串而非单字符）Linux 内核的 radix_tree（页缓存索引）、IP 路由表
ART（Adaptive Radix Tree）自适应节点大小：按孩子数选 Node4 / Node16 / Node48 / Node256 四种表示；Node16 用 SIMD 一次比较 16 个 keyHyPer、DuckDB、部分内存数据库的主索引

压缩后缀 Trie见 字符串匹配 的后缀树/后缀数组生物信息、全文索引
ART 的自适应思路值得单独学：Trie 的空间问题源于「节点大小固定为字符集大小」，而实际分布是极度不均的——靠近根的节点孩子多，靠近叶子的孩子少。ART 让节点按需长大（4 → 16 → 48 → 256），既省空间又保留了 O(键长) 的查找。
而 Node16 用 SIMD 一次比较 16 个 key，思路和 Swiss Table 的控制字节完全同源——「用 SIMD 在小的连续数组上批量筛选」是现代数据结构的共同手法。

选型的一句话判据：

· 要「范围 / 有序」 → 平衡树或跳表

三者的能力是递增的，代价也是递增的。先问清需要哪种查询，再选结构。

面试题集（12 道）

按难度分三段，先自测再对照

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础前序、中序、后序分别在什么时候用？怎么快速判断该用哪个？

    三种序的代码差别只在 visit(root) 那一行的位置。选哪个取决于信息的流动方向。

    判据（比记名字管用）
    「我需要的信息是从上往下给的，还是从下往上收的？」
    · 从上往下传（参数）→ 前序：序列化、路径和、深拷贝
    · 从下往上收（返回值）→ 后序：求高度、判平衡、LCA、子树聚合
    · BST 上要有序序列 → 中序：验证 BST、第 k 小
    · 按层处理 → 层序 BFS：最小深度、每层最大值
    两者都要的情况
    比如「求二叉树直径」：既需要子树高度（往上收），又要更新全局答案。写法是后序 + 一个引用参数记全局值：
    int depth(Node* r, int& best) {
    if (!r) return 0;
    int L = depth(r->l, best), R = depth(r->r, best);
    best = std::max(best, L + R);   // 用子树信息更新全局
    return 1 + std::max(L, R);        // 往上返回自己的高度
}
    另一个通用技巧
    树递归的基线一律选「空节点」而不是「叶子节点」。选叶子要写 if (!r->l && !r->r)，还得单独处理只有一个孩子的情况；选空节点则所有分支自动统一。这条规则能消掉树题里一半的边界 bug。
  2. 基础怎么验证一棵树是不是 BST？只比较父子为什么不对？
    只比较父子的反例
        5
   / \
  3   7
   \
    6      // 3 < 5 ✓，7 > 5 ✓，6 > 3 ✓
    每对父子都合法，但 6 在 5 的左子树里却比 5 大——BST 要求的是「左子树所有值 < 根」，不是「左孩子 < 根」。
    解法一 · 往下传区间（前序）
    bool ok(Node* r, long long lo, long long hi) {
    if (!r) return true;
    if (r->val <= lo || r->val >= hi) return false;
    return ok(r->l, lo, r->val) && ok(r->r, r->val, hi);
}
// 调用：ok(root, LLONG_MIN, LLONG_MAX)
    注意用 long long——如果节点值可能是 INT_MIN/INT_MAX，用 int 边界会误判。这是本题最常见的隐藏 bug。
    解法二 · 中序遍历检查递增（更简洁）
    Node* prev = nullptr;
bool ok(Node* r) {
    if (!r) return true;
    if (!ok(r->l)) return false;
    if (prev && prev->val >= r->val) return false;
    prev = r;
    return ok(r->r);
}
    好处是避开了边界值问题，而且能灵活处理「是否允许重复值」的语义（改 >= 为 >）。
  3. 基础BST 删除一个有两个孩子的节点怎么做？为什么这样是对的？

    删除分三种情形，只有第三种需要技巧：

    情形一 · 叶子
    直接删，父指针置空。
    情形二 · 只有一个孩子
    用唯一的孩子顶替自己（整棵子树上移，仍满足 BST）。
    情形三 · 两个孩子
    找一个「能站在这个位置」的值来顶替：中序后继（右子树的最左节点）或中序前驱（左子树的最右节点）。把它的值拷到当前节点，然后递归删除它。
    Node* succ = r->r;
while (succ->l) succ = succ->l;
r->val = succ->val;
r->r = erase(r->r, succ->val);
    为什么是对的（两个理由）
    ① 后继的值确实能站在这个位置：它是「所有大于当前值的元素里最小的那个」，所以放到当前位置后，左子树全部 < 它、右子树全部 > 它，BST 性质保持。
    ② 递归不会无限展开：后继是右子树的最左节点，所以它必然没有左孩子 ⟹ 最多只有一个孩子 ⟹ 递归删除它必然落到情形一或二。
    一个细节
    总是用后继（或总是用前驱）会让树逐渐偏向一侧。有些实现交替使用，或按子树高度选较高的那侧，以延缓退化。朴素 BST 里意义不大（反正会退化），但实现平衡树时会影响旋转次数。
  4. 基础什么时候该用 std::map 而不是 unordered_map？

    三个正当理由，没有一个是「map 更快」：

    ① 需要有序性 / 范围查询
    lower_bound、upper_bound、按序遍历、找「最接近 x 的元素」——哈希表根本做不到。这是最常见的理由。
    ② 需要确定性延迟
    树永远 O(log n)，无 rehash 抖动、无攻击面。哈希表是「期望 O(1)、最坏 O(n)、且偶尔一次 O(n) 停顿」。对 p99 敏感的服务、实时系统，可预测性比平均速度值钱。
    ③ 需要迭代器 / 引用稳定性
    std::map 插入不失效任何迭代器，删除只失效被删的那个。unordered_map 的 rehash 会失效所有迭代器（引用还有效）；absl::flat_hash_map 连引用都失效。
    顺带纠正一个常见误解
    「树一定比哈希表慢」不成立。n 较小时（几十到几百）std::map 常常更快：树的上层节点常驻 cache（被反复访问），而哈希表要先算 hash（string 键要扫全串）再做一次随机地址访问（几乎必然 cache miss）。
    交叉点约在 n 几百到一千，依赖 key 类型与哈希成本。小容器上先别急着换。
    还有更好的第四选项
    如果数据只读且要有序，用排序数组 + std::lower_bound——连续内存，比红黑树快得多（无指针追逐、无每节点一次分配）。这个选项经常被忽略。

10.2 中级（区分熟练度）

  1. 中级AVL 和红黑树的区别是什么？为什么 std::map 选红黑树？
    AVL红黑树
    不变式左右子树高度差 ≤ 1黑高相等 + 无连续红节点
    高度上界≈1.44 log n2 log n
    查找更快（树矮 ~30%）稍慢
    插入旋转≤ 2 次≤ 2 次
    删除旋转最坏 O(log n) 次≤ 3 次
    额外存储高度或平衡因子1 bit 颜色
    关键差异在删除
    AVL 删除后可能需要沿整条路径一路调整（每层一次旋转）；红黑树的删除修复最多 3 次旋转，其余通过改颜色解决。
    所以 std::map 选红黑树
    通用容器无法预知读写比，而红黑树的「最坏修改代价」更小、更可控。这是保守但正确的默认。
    选型判据：读远多于写 → AVL（树矮，查找快）；读写均衡或写多 → 红黑树。
    红黑树高度上界的推导（可能追问）
    设黑高 bh： · 性质 5（黑高相等）⟹ 任何路径至少 bh 个黑节点 · 性质 4（无连续红）⟹ 任何路径长度 ≤ 2·bh · 黑节点至少构成完美二叉树 ⟹ n ≥ 2^bh − 1 ⟹ bh ≤ log₂(n+1) ∴ h ≤ 2·bh ≤ 2 log₂(n+1)
    「无连续红」保证红节点最多占一半层级，这个『两倍』的松弛正是它修改更快的原因。
  2. 中级什么是 Morris 遍历？它的代价是什么？

    Morris 遍历用 O(1) 空间完成中序遍历（递归和显式栈都要 O(h)）。办法是临时借用叶子的空右指针指回当前节点，走完再断开。

    while (cur) {
    if (!cur->l) { visit(cur); cur = cur->r; }
    else {
        Node* pre = cur->l;
        while (pre->r && pre->r != cur) pre = pre->r;  // 找中序前驱
        if (!pre->r) { pre->r = cur; cur = cur->l; }      // 建线索，下潜
        else { pre->r = nullptr; visit(cur); cur = cur->r; } // 断线索，访问
    }
}

    复杂度仍是 O(n)——每条边最多被走 3 次（下潜、找前驱、返回）。

    三个真实限制（这才是考点）
    ① 遍历中修改了树结构（虽然结束会恢复）⟹ 不能并发遍历，也不能被其他线程同时读到；② 遍历中抛异常会留下损坏的树（线索没断开），之后任何操作都可能死循环——visit 可能抛异常时不要用；③ 树必须可写（不能是 const）。
    实际用途很窄
    只在「树极深（递归会爆栈）且内存极紧」时才值得。一般用显式栈就够（O(h) 空间，h 通常是 log n）。
    但它是体现「知道有 O(1) 方案」的好谈点，也是「换算法消掉栈」这一思路的漂亮例子——对比 递归与分治 里的三条去递归路径。
  3. 中级为什么数据库索引用 B+ 树而不是红黑树？B 树和 B+ 树的区别？

    因为磁盘上「一次节点跳转」比「一次比较」贵一千倍以上，优化目标从「减少比较次数」变成「减少跳转次数」。

    内存跳转 ≈ 100 ns（cache miss） 磁盘跳转 ≈ 100 µs（SSD）～ 10 ms（HDD） 二叉搜索树：log₂(10⁹) ≈ 30 次 I/O B+ 树 (B≈500)：log₅₀₀(10⁹) ≈ 3~4 次 I/O

    做法是把节点做成一个磁盘页大小（4–16 KB），每页放几百个 key。用页内的廉价二分（8–10 次内存比较）换掉 26 次磁盘 I/O。

    B 树 vs B+ 树：

    B 树B+ 树
    数据存哪内部节点也存只有叶子存
    每页 key 数较少更多 → 树更矮
    叶子之间无连接按序链成链表
    范围扫描要回树中序遍历顺着叶子链表顺序 I/O
    B+ 胜出的决定性理由是范围扫描
    SQL 的 BETWEEN、ORDER BY、GROUP BY 都是范围操作，叶子链表让它们变成顺序 I/O——磁盘上比随机 I/O 快一到两个数量级。
    B 树「单点查找可能在内部节点命中」的优势相比之下微不足道，而且它还让树变高了。
    顺带解释了覆盖索引和 LSM
    覆盖索引：查询需要的所有列都在索引叶子里 → 不用回表（回表 = 又一轮 B+ 树查找 + 随机 I/O）。
    LSM-Tree 存在的理由：B+ 树在写密集下会页分裂 + 随机写；LSM 把随机写变成顺序写（内存表 + 顺序落盘 + 后台 compaction），代价是读放大和写放大。「B+ vs LSM」本质是「读优化 vs 写优化」。
  4. 中级Redis 的 ZSet 为什么用跳表而不是红黑树？

    作者 antirez 给过三个理由，都不是「跳表更快」：

    ① ZSet 需要范围查询
    ZRANGE、ZRANGEBYSCORE 是核心操作。跳表的最底层就是一条有序链表，范围扫描是天然的顺序访问；红黑树要做中序遍历（指针跳来跳去）。
    ② 实现和调试简单得多
    没有旋转、没有颜色、删除逻辑直白——代码量约是红黑树的 1/3。对一个要长期维护的开源项目，这是实质性优势。
    ③ 容易支持「按排名查找」
    在每个前进指针上记一个跨度（span）即可实现 ZRANK / ZRANGE by index。红黑树要做这个得额外维护子树大小。
    跳表的平衡策略：用随机代替旋转
    每个节点插入时掷硬币决定层高（p=1/2 或 1/4），期望层高 log n ⟹ 期望查找 O(log n)。完全不需要任何旋转——「保持平衡」这个难题被外包给了随机数。
    代价是保证从「最坏 O(log n)」降级成「期望 O(log n)」。
    同一个结构在不同系统里的理由可以完全不同
    Redis 选它是为了范围查询 + 实现简单（它单线程，不关心并发）。
    ConcurrentSkipListMap（Java）和 RocksDB 的 memtable 选它是为了并发友好——跳表的修改是局部的（只改几个指针），容易做无锁；而平衡树的旋转会影响多个节点，无锁化极难。
    这个对比比记「跳表 vs 红黑树谁快」有价值得多。

10.3 高级（体现深度）

  1. 高级要实现一个搜索框自动补全，用什么数据结构？怎么支持「按热度排序」和百万级词库？

    「前缀查询」这个需求直接排除哈希表和平衡树——只有 Trie 族能做。但朴素 Trie 有三个问题要解决。

    ① 基础结构：Trie
    查找 O(键长)，与词库大小无关。走到前缀节点后遍历子树收集候选。
    ② 空间问题必须解决
    朴素 Trie 每节点 26 个指针 = 208 字节（64 位），实际可能只用 1–2 个。百万词、平均长 8 → 节点数几百万 → 几百 MB。
    三种压缩：路径压缩（基数树，单链节点合并）、自适应节点（ART：Node4/16/48/256 按需长大，Node16 用 SIMD）、双数组 Trie（两个整数数组编码整棵树，最省空间且 cache 友好，中文输入法常用）。
    ③ 按热度排序：在节点上预存 Top-K
    不要「收集所有后代再排序」——热门前缀（如 a）的后代可能有几十万个。
    在每个节点上预计算并缓存「以此为前缀的 Top-10」，查询变成 O(键长) + O(1)。这是空间换时间，也是所有生产补全系统的做法。
    热度更新时只需沿路径向上更新受影响的节点（O(键长)）。
    ④ 实际系统还要什么
    拼写容错（编辑距离 ≤ 1 的候选）→ Trie 上做带剪枝的模糊搜索，或用 BK-tree / SymSpell。拼音/首字母（中文）→ 建多套索引。个性化→ 全局 Top-K 与用户历史加权融合。实时性→ 热度用滑动窗口或 EWMA 而不是全量重算。
    工程上先考虑现成方案
    Elasticsearch 的 completion suggester（基于 FST，比 Trie 更省空间）、Redis 的 ZRANGEBYLEX（有序集合按字典序范围查，可以模拟前缀）。
    自己实现只在有特殊约束时才值得——比如需要嵌入到客户端、或词库有特殊结构。面试时先说「评估现成方案」再讲自研设计，比直接开始画 Trie 更能体现工程判断。
  2. 高级ART（自适应基数树）解决了 Trie 的什么问题？它和 Swiss Table 有什么共同点？

    ART 解决的是 Trie 的空间浪费问题，而它的解法思路和 Swiss Table 同源。

    Trie 的空间问题根源
    节点大小固定为字符集大小（256 个指针 = 2 KB），而实际孩子数分布极度不均——靠近根的节点孩子多，靠近叶子的往往只有 1–2 个。绝大多数指针是空的。
    ART 的两个改进
    ① 自适应节点大小：按孩子数选四种表示——
    · Node4：4 个 key 字节 + 4 个指针（线性查找）
    · Node16：16 个 key 字节 + 16 个指针（SIMD 一次比较 16 个）
    · Node48：256 字节索引表 + 48 个指针
    · Node256：直接 256 个指针（数组下标即字节）
    节点按需长大/缩小，既省空间又保留 O(键长)。
    ② 路径压缩：单链路径合并（继承基数树）。
    与 Swiss Table 的共同点
    「用 SIMD 在一小块连续数组上批量筛选」：
    · Swiss Table：16 个控制字节（哈希高 7 位）一条 SIMD 指令比完，筛掉 127/128 的候选。
    · ART 的 Node16：16 个key 字节一条 SIMD 指令比完，直接定位孩子。
    两者都是「把元数据压缩到极小的连续数组里，让一次 cache line 读取 + 一条 SIMD 指令完成大批量筛选」。

    这是现代数据结构的共同手法，同族还有：B 树式的 cache 内索引（一个 cache line 放 16 个 key）、布隆过滤器（小摘要挡住无效访问）。识别出这个模式，你在设计新结构时就多了一个工具。
    使用者与定位
    HyPer、DuckDB、部分内存数据库的主索引。它的定位是「内存数据库里替代 B+ 树的选项」——O(键长) 而非 O(log n)，且天然支持前缀和范围。
    代价是实现复杂度高（四种节点 + 转换逻辑），且对长键不如 B+ 树（键长 100 字节时 O(100) 未必优于 O(log n)）。
  3. 高级一个用 std::map 做内存索引的服务，QPS 上不去，profile 显示时间都在 map 查找上。怎么优化？

    红黑树的性能问题几乎总是指针追逐 + 每节点一次分配造成的，而不是 log n 这个次数。按性价比排序：

    ① 先问需不需要有序
    如果只做点查，换 absl::flat_hash_map——连续内存 + SIMD，通常快 3–5 倍。
    这一步收益最大，但经常被跳过：很多代码用 map 只是因为「习惯」或「以前需要有序，现在不需要了」。
    ② 需要有序但数据只读 → 排序数组 + lower_bound
    连续内存，二分的前几步会 cache miss 但后几步全命中；没有每节点一次分配、没有指针追逐。通常比红黑树快 2–3 倍，内存也省一半以上（每元素省掉两个指针 + 颜色 + malloc 头）。
    如果偶尔要更新，可以「批量重建」（攒一批改动后重排一次）。
    ③ 需要边读边写 + 有序 → 考虑跳表或 B 树式结构
    cache 内 B 树（一个 cache line 放 16 个 key，SIMD 比较）能把树高从 log₂n 降到 log₁₆n，cache miss 次数降 4 倍。ART 也是候选。
    高并发写场景 → 跳表（局部修改，易做无锁）。
    ④ 不换结构也能改善的两件事
    自定义分配器：std::map 每个节点一次 malloc，节点散落在堆上。用 arena / pool allocator 让节点连续分配，能显著改善 cache 局部性。
    缩小 key：如果 key 是长 string，比较成本高且节点大。改成存哈希值 + 短标识，或用 string_view 指向统一的字符串池。
    但先确认 profile 没骗你
    「时间都在 map 查找上」可能有两个假象：① 实际瓶颈是 key 的构造/比较（构造临时 std::string 做查找 → 每次一次分配），改用 map 的透明比较器（C++14 的 std::less<>）或 string_view key 就能解决；② 实际是内存带宽饱和，此时任何结构都受限，得先减少数据量。
    测量方法见 性能优化指南。
  4. 高级为什么平衡树很难做无锁并发，而跳表相对容易？

    根本原因是「一次修改影响多少个节点」。

    平衡树的困难
    旋转是一个涉及多个节点的原子性变更：一次旋转要同时改 3–4 个指针，而且可能沿路径向上连锁触发（AVL 删除最坏 O(log n) 次旋转）。
    要让并发读者始终看到一致的树，就得：
    · 用读写锁（写者独占整棵树 → 并发度低），或
    · 用细粒度锁 + 严格的加锁顺序（极易死锁，且旋转要锁多个节点），或
    · 用 RCU（每次修改复制受影响的路径，读者无锁——但写放大严重，且要延迟回收旧节点）。
    跳表为什么容易
    修改是局部的：插入一个节点只需在每一层做一次「前驱的 next 指针」的 CAS，各层可以独立地、逐层完成。
    关键在于即使只完成了部分层，结构仍然是「正确但不够优」的——底层链表始终有序完整，上层只是索引。读者顺着走一定能找到，只是可能慢一点。
    这个「中间状态也是合法状态」的性质是无锁化的关键，平衡树没有（旋转中途的树是非法的）。
    实践中的方案对照
    ConcurrentSkipListMap（Java）：无锁跳表，CAS + 标记删除。
    RocksDB memtable：无锁跳表（单写多读，写者也无锁）。
    Linux 内核的 RCU + 红黑树：读无锁（RCU 保护），写加锁——因为内核里读远多于写。
    B+ 树的 latch coupling / B-link 树：数据库用的方案，靠「节点内加短锁 + 右兄弟指针」让读者能追上分裂中的节点。
    可迁移的一般原则
    「设计并发数据结构时，先问『部分完成的修改是否仍是合法状态』」。
    是 → 可以无锁化（跳表、Michael-Scott 队列、Swiss Table 的部分操作）。
    不是 → 需要锁、RCU 或整体复制。
    这也解释了为什么无锁结构常常要重新设计数据布局，而不是给现有结构加 CAS——布局本身决定了能否无锁。相关展开见 并发模式。
