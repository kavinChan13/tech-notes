树与平衡树

树的价值是把 n 个元素叠成 log n 层，每次操作只走一条路径。保矮有四条路：AVL 卡高度差、红黑树卡颜色、B+ 把节点加宽、跳表用随机层高。遍历 / BST / 旋转用图讲；AVL 与红黑不写完整实现。LCA 留倍增骨架；树形 DP 转到动态规划。

核心难度 ★★★★☆ 面试出现率 极高 阅读时长 ~30 min 前置 递归 · 复杂度
三序遍历 BST 有序 旋转 / AVL / 红黑 B 树阶 LCA 倍增 树形 DP
01

本质：用层级换对数

以及「保证 log n 层」的四条路

线性扫描是 O(n)。树引入层级：每下一层丢掉一大块候选，复杂度变成 O(树高)。「树高 = log n」不是免费的——二叉搜索树最坏会退化成链，此时比数组还差。核心问题不是查找（那很简单），而是插删之后树还矮不矮。

四种答案只争一件事：插删后如何保矮。
  • AVL：左右高度差 ≤ 1，靠旋转。
  • 红黑树：黑高相等 + 无连续红，h ≤ 2 log(n+1)。
  • B / B+：节点变宽，树高 log_B n（磁盘上 3–4 层）。
  • 跳表：随机层高，期望 log n，无旋转。
AVL 是最严的 HR：两部门层级差不能超过 1，一超就重组——查询最快、重组最勤。红黑树允许临时工，但不能连续两个，正式编制人数沿每条路相同——查询稍慢，重组少。B+ 把每个部门做到一页（几百 key），跨页沟通（磁盘）比页内贵一千倍。跳表入职掷骰子定级，期望自然是对数。
四种策略只争一件事：插删之后树还矮不矮。朴素 BST 在按序插入时会变成链，比数组还差——既是 O(n) 又有指针追逐。

1.1 与其他章节的关系

  • 递归与分治 —— 遍历是递归最自然的场景
  • 动态规划 · 树形 DP —— 后序把子树答案合并到父节点
  • 并查集与区间结构 —— 线段树、树状数组是为区间查询设计的树
  • 二分查找 —— B+ 页内二分、跳表层级跳跃
  • 堆与 Top-K —— 堆也是树，但不维护全序
  • STL 容器 —— std::map 的红黑树与迭代器失效
  • 存储与数据架构 —— B+ / LSM / 跳表在数据库里
02

二叉树遍历

三种序只差 visit 的位置；选序看信息往哪流

2.1 三种递归序

// 三种序的区别只在 visit(root) 的位置
void preorder(Node* r)  { if (!r) return; visit(r); preorder(r->l);  preorder(r->r);  }
void inorder(Node* r)   { if (!r) return; inorder(r->l);  visit(r); inorder(r->r);   }
void postorder(Node* r) { if (!r) return; postorder(r->l); postorder(r->r); visit(r); }
序信息方向典型题
前序从上往下序列化、路径和、深拷贝
中序BST 有序验证 BST、第 k 小
后序从下往上高度、LCA、子树聚合、树形 DP
层序按层最小深度、每层最大值
选序的判据只有一条：信息是从上往下给的，还是从下往上收的？路径和、序列化、深拷贝是参数往下传 → 前序。高度、是否平衡、子树节点数、LCA、树形 DP 是返回值往上收 → 后序。直径两者都要：后序收高度，再用引用记全局最大值。BST 上要有序序列才用中序。层序是 BFS，按距根的层数处理。
迭代版把递归栈显式化即可：前序一次入栈，后序每个节点入栈两次（第一次展开、第二次访问）。expanded 标记就是程序计数器。Morris 用空右指针当临时线索换 O(1) 空间，但遍历中改树——不能并发、visit 抛异常会留下坏树、树必须可写。一般用显式栈（O(h)，平衡时就是 O(log n)）。
03

二叉搜索树

左 < 根 < 右；中序即有序；按序插入会退化

3.1 插入与查找

// 查找 / 插入都只走一条路；相等则查找命中、插入为 no-op
Node* find(Node* r, int k) {
    while (r && r->val != k) r = k < r->val ? r->l : r->r;
    return r;
}
Node* insert(Node* r, int k) {
    if (!r) return new Node(k);
    if (k < r->val)      r->l = insert(r->l, k);
    else if (k > r->val) r->r = insert(r->r, k);
    return r;
}

删除三种情形：叶子直接摘；单孩子用孩子顶替（子树整体上移，仍是 BST）；双孩子不能直接拆——找中序后继（右子树最左）或前驱（左子树最右），把值拷到当前节点，再递归删它。后继没有左孩子，递归必落到前两种，不会无限展开。总用后继会让树偏向一侧；平衡树实现里常按子树高度选侧。

3.2 为什么会退化

按序插入 1,2,…,n 得到右链，所有操作变 O(n)。自增 ID、时间戳、排好序的导入都是这种输入。平均 O(log n) 依赖随机顺序，可被构造攻击（与快排平均复杂度同一类假设，见 复杂度与分析）。朴素 BST 生产上基本不可用。

思路代表保证
插删后主动调整AVL、红黑树最坏 O(log n)
随机化结构跳表、Treap期望 O(log n)
按访问频率调整Splay摊销 O(log n)
加宽节点B / B+最坏 O(log_B n)
04

平衡的两种流派

旋转保中序；AVL 卡高度差；红黑卡颜色。不写完整实现

4.1 旋转

旋转：中序序列不变，只改形状。所以旋转后仍是合法 BST。

// 右旋：把左孩子提为根。左旋对称。不是完整 AVL/红黑实现
Node* rotate_right(Node* y) {
    Node* x = y->l;
    y->l = x->r;
    x->r = y;
    return x;
}
失衡形态旋转
LL左子的左子过高一次右旋
RR右子的右子过高一次左旋
LR左子的右子过高左子先左旋，再右旋
RL右子的左子过高右子先右旋，再左旋

记法：失衡方向决定旋转方向；两个字母不同就先转成相同。LL/RR 一次转，LR/RL 先把「拐弯」转直再转。插入最多两次旋转就能复衡；删除在 AVL 里可能沿路径一路转。

4.2 AVL：严格平衡

不变式：每个节点 BF = h(左) − h(右) ∈ {−1, 0, +1}。斐波那契最坏形状给出 h ≈ 1.44 log₂(n+2)，非常接近完美平衡的 log₂ n。|BF| = 2 就按上表旋转。插入从新叶往上走，碰到第一个 |BF|=2 的节点转一次（或两次）即可，因为旋转后整条路径复衡。删除可能把失衡传到父亲，最坏一路转到根。

4.3 红黑树：放松平衡

不直接卡高度，用颜色间接卡。真正干活的是性质 4（无连续红 → 红最多占一半层级）和 5（黑高相等 → 最短路 ≥ 黑高），合起来 h ≤ 2 log₂(n+1)。性质 1–3 把根和 NIL 都定为黑，让黑高定义干净、插入情形更少。

高度上界 黑高 bh：性质 5 ⇒ 任何路径至少 bh 个黑节点；性质 4 ⇒ 路径长度 ≤ 2·bh。 黑节点至少构成完美二叉树 ⇒ n ≥ 2^bh − 1 ⇒ bh ≤ log₂(n+1)。 ∴ h ≤ 2·bh ≤ 2 log₂(n+1)
性质 4 和 5 像「正式员工 + 实习生」：每条路经过的正式编制人数必须相同（组织不会一支特别深）；实习生下面不能再带实习生（临时工最多占一半层级）。最深最多是最浅的两倍——这份松弛让红黑树少转很多圈。

4.4 对照与选型

AVL红黑树
高度≈1.44 log n2 log n
查找更快稍慢
插入旋转≤ 2≤ 2
删除旋转最坏 O(log n)≤ 3
额外存储高度或 2 bit BF1 bit 颜色
使用者读多写少的内存索引std::map、CFS、epoll

读远多于写 → AVL（树矮约 30%，查找更快）；读写均衡或写多 → 红黑（最坏修改代价更小）。标准库选红黑，因为通用容器无法预知读写比。完整插删修复不在本页展开——记住旋转表和这两条不变式，能讲清取舍即可。

05

红黑树在工程里

选它几乎从不是因为「查找最快」

5.1 五条性质保证了什么

工程愿意接受 2 log n 而不是 1.44 log n，是因为修改代价可控。这张表里没有一条理由是「查找最快」。真实理由分三类：要有序 / 范围查询（哈希做不到）；要确定性延迟（哈希会 rehash 抖）；要迭代器 / 引用稳定。三条都不需要，就该用哈希表。

场景真实理由
std::map / set插入不失效迭代器；删除只失效被删的那个
Linux CFS按 vruntime 频繁插删 + 取最小；最左节点可缓存成 O(1)
epoll 兴趣列表fd 增删频繁，要 O(log n) 确定性（哈希会 rehash 抖）
内核 VMA范围查询：「地址落在哪个 VMA」
nginx 定时器取最近到期 + 频繁取消（堆找不到任意元素）

5.2 std::map / epoll / CFS

libstdc++ 把颜色存在独立字段（可移植、好调试）；内核把颜色塞进 parent 指针最低位（节点 4 字节对齐，低 2 位必为 0）。通用库和内核的约束不同，同一结构会做出不同取舍。

n 较小时（几十到几百）map 常比哈希表快：树的上层节点被反复访问、常驻 cache；哈希要先算 hash（string 键扫全串）再做一次几乎必 miss 的随机访存。交叉点大约在 n 几百到一千，依赖 key 类型。小容器上先别急着换。如果数据只读且要有序，排序数组 + lower_bound 比任何树都快（连续内存、无每节点分配）。

06

B 树与 B+ 树

阶决定扇出；磁盘上一次跳转比一次比较贵一千倍

6.1 又矮又胖的动机

内存跳转 ~100 ns（一次 cache miss），磁盘跳转 ~100 µs（SSD）～ 10 ms（HDD），差一千倍以上。优化目标从「少比较」变成「少跳转」。节点做成一个磁盘页（4–16 KB），每页放几百个 key：页内二分 8–10 次比较全在内存里，换掉的是二十多次磁盘 I/O。BST：log₂(10⁹)≈30 次 I/O；B+（B≈500）：3–4 次。这是二分查找里「两层不同代价单位」的完整版本。

6.2 B 与 B+ 的差别

B 树B+ 树
数据内部也存只有叶子存
扇出较小更大 → 更矮
叶子无连接有序链表
范围扫描回树中序顺序 I/O

B+ 胜在 BETWEEN / ORDER BY / GROUP BY：叶子链表让范围扫描变成顺序 I/O，磁盘上比随机 I/O 快一到两个数量级。B 树「单点查找可能在内部节点命中」的优势相比之下微不足道，还让树变高了。

覆盖索引 = 查询所需列都在索引叶子里，不用回表（回表 = 又一轮 B+ 查找 + 随机 I/O）。写密集会页分裂、随机写 → LSM 把随机写变顺序写（内存表 + 顺序落盘 + 后台 compaction），代价是读放大和写放大。「B+ vs LSM」本质是读优化 vs 写优化，见 存储架构 与 关系型数据库。

07

跳表：用随机代替旋转

同样的 O(log n)，代码只有平衡树的三分之一

跳表是多层有序链表：上层稀疏、跳得远，底层是完整序列。每个节点插入时掷硬币决定层高（p=1/2 或 1/4），期望层高 log n，期望查找 O(log n)，完全不需要旋转。「保持平衡」被外包给随机数，代价是保证从「最坏 O(log n)」降成「期望 O(log n)」——攻击者控不了你的骰子，这和 Treap 是同一类思路。

跳表红黑树
保证期望 O(log n)最坏 O(log n)
代码约 1/3删除情形多
范围扫描底层就是链表中序遍历
并发局部 CAS旋转牵连多节点
使用者Redis ZSet、RocksDB memtablestd::map、内核

Redis 选跳表（antirez 亲述，都不是「更快」）：① ZRANGE / ZRANGEBYSCORE 是核心，底层链表天然顺序扫；② 无旋转无颜色，代码约红黑树 1/3，长期维护是实质优势；③ 前进指针记 span 就能按排名查（ZRANK），红黑树要额外维护子树大小。Redis 单线程，并发友好不是它的理由。

ConcurrentSkipListMap 和 RocksDB memtable 选它，却正是因为并发：插入只需在每层对「前驱的 next」做一次 CAS，各层可独立完成。即使只完成部分层，结构仍然合法（底层链表始终有序，上层只是索引）——「中间状态也是合法状态」是无锁化的关键，平衡树的旋转中途是非法树。同一个结构在不同系统里被选中的原因可以完全不同。

08

最近公共祖先

树上路径交点；静态 LCA 用倍增，O(n log n) 预处理 + O(log n) 查询

树上 u 到 v 的路径必过它们的 LCA。距离 = dep[u] + dep[v] − 2·dep[LCA]。求法很多：两次 DFS 的栈交点（在线、O(n) 每次）；Tarjan 离线 + 并查集；欧拉序转 RMQ（ST 表 O(1) 查询）。工程和竞赛里最常用的是倍增：预处理每个点的 2^k 祖先，查询先把深的抬到同一层，再一起跳。树链剖分把重链压成序列，查询跳的次数更少，但代码更长——本页只留倍增骨架。

8.1 倍增骨架

// 倍增 LCA：up[k][u] = 2^k 祖先。LOG = 20 够 n≤1e6
void dfs(int u, int p) {
    up[0][u] = p;
    for (int k = 1; k < LOG; ++k) up[k][u] = up[k-1][up[k-1][u]];
    for (int v : g[u]) if (v != p) { dep[v] = dep[u]+1; dfs(v, u); }
}
int lca(int u, int v) {
    if (dep[u] < dep[v]) std::swap(u, v);
    for (int k = LOG-1; k >= 0; --k) if (dep[up[k][u]] >= dep[v]) u = up[k][u];
    if (u == v) return u;
    for (int k = LOG-1; k >= 0; --k)
        if (up[k][u] != up[k][v]) u = up[k][u], v = up[k][v];
    return up[0][u];
}

约定根的父亲是 0，dep[0] 取 −1，避免跳到树外。树剖把轻边一刀、重链压成序列，查询沿轻边跳的次数是 O(log n)；骨架更长，路径聚合、子树修改才值得上。点分治处理路径统计，见 树形 DP 同页的「直径 / 重心」提示。

09

选型与树形 DP

按查询能力选结构；树上后序聚合转到 DP 篇

树形 DP 的状态几乎总是「子树 + 该节点的选择」。选/不选（最大独立集、打家劫舍 III）用 dp[u][0/1]；树上背包用 dp[u][j]，合并上界取 size[u] 而不是 m，实际 O(n·m)；换根要两遍 DFS（后序 down、前序 up），max 不可减时要用前缀+后缀。链状树 DFS 深度 = n，n=10⁵ 必须改迭代，否则爆栈。

朴素 Trie 每节点 26～256 个指针，空间是死穴。压缩三条路：路径压缩（基数树 / Patricia，单链合并）；自适应节点（ART 的 Node4/16/48/256，Node16 用 SIMD 一次比 16 个 key，和 Swiss Table 控制字节同源）；双数组 Trie（分词、输入法）。要前缀才用它；只要等于，哈希表更省心。多模式匹配见 字符串匹配 的 AC 自动机。

结构查找插删有序前缀范围扫描典型用途
哈希表O(1) 期望O(1) 摊销否否否点查为主
排序数组O(log n)O(n)是否最快（连续）只读索引
AVLO(log n) 最快的树O(log n)，删除旋转多是否O(n) 中序读多写少
红黑树O(log n)O(log n)，删除最多 3 转是否O(n) 中序std::map、内核
跳表O(log n) 期望O(log n) 期望是否底层链表Redis ZSet、并发场景
B+ 树O(log_B n) I/OO(log_B n)是否叶子链表顺序 I/O磁盘索引
Trie / ARTO(键长)O(键长)是是是前缀查询、路由
堆O(n)O(log n)否否否只要最值

决策顺序：① 数据在磁盘还是内存？磁盘 → B+ 族（或 LSM）。② 要什么查询？只要等于 → 哈希表；要有序/范围 → 树或跳表；要前缀 → Trie 族（唯一选择）。③ 会变吗？不变 → 排序数组 + 二分，连续内存比任何树都快。④ 高并发写 → 跳表比平衡树容易做无锁。「哪个快」是最后才问的——前三步定下来，候选通常只剩一个。

10.1 基础（必答）

  1. 基础前序、中序、后序分别在什么时候用？怎么快速判断该用哪个？

    三种序的代码差别只在 visit(root) 那一行的位置。选哪个取决于信息的流动方向。

    判据（比记名字管用）
    「我需要的信息是从上往下给的，还是从下往上收的？」
    · 从上往下传（参数）→ 前序：序列化、路径和、深拷贝
    · 从下往上收（返回值）→ 后序：求高度、判平衡、LCA、子树聚合
    · BST 上要有序序列 → 中序：验证 BST、第 k 小
    · 按层处理 → 层序 BFS：最小深度、每层最大值
    两者都要的情况
    比如「求二叉树直径」：既需要子树高度（往上收），又要更新全局答案。写法是后序 + 一个引用参数记全局值：
    int depth(Node* r, int& best) {
    if (!r) return 0;
    int L = depth(r->l, best), R = depth(r->r, best);
    best = std::max(best, L + R);   // 用子树信息更新全局
    return 1 + std::max(L, R);        // 往上返回自己的高度
}
    另一个通用技巧
    树递归的基线一律选「空节点」而不是「叶子节点」。选叶子要写 if (!r->l && !r->r)，还得单独处理只有一个孩子的情况；选空节点则所有分支自动统一。这条规则能消掉树题里一半的边界 bug。
  2. 基础怎么验证一棵树是不是 BST？只比较父子为什么不对？
    只比较父子的反例
        5
   / \
  3   7
   \
    6      // 3 < 5 ✓，7 > 5 ✓，6 > 3 ✓
    每对父子都合法，但 6 在 5 的左子树里却比 5 大——BST 要求的是「左子树所有值 < 根」，不是「左孩子 < 根」。
    解法一 · 往下传区间（前序）
    bool ok(Node* r, long long lo, long long hi) {
    if (!r) return true;
    if (r->val <= lo || r->val >= hi) return false;
    return ok(r->l, lo, r->val) && ok(r->r, r->val, hi);
}
// 调用：ok(root, LLONG_MIN, LLONG_MAX)
    注意用 long long——如果节点值可能是 INT_MIN/INT_MAX，用 int 边界会误判。这是本题最常见的隐藏 bug。
    解法二 · 中序遍历检查递增（更简洁）
    Node* prev = nullptr;
bool ok(Node* r) {
    if (!r) return true;
    if (!ok(r->l)) return false;
    if (prev && prev->val >= r->val) return false;
    prev = r;
    return ok(r->r);
}
    好处是避开了边界值问题，而且能灵活处理「是否允许重复值」的语义（改 >= 为 >）。
  3. 基础BST 删除一个有两个孩子的节点怎么做？为什么这样是对的？

    删除分三种情形，只有第三种需要技巧：

    情形一 · 叶子
    直接删，父指针置空。
    情形二 · 只有一个孩子
    用唯一的孩子顶替自己（整棵子树上移，仍满足 BST）。
    情形三 · 两个孩子
    找一个「能站在这个位置」的值来顶替：中序后继（右子树的最左节点）或中序前驱（左子树的最右节点）。把它的值拷到当前节点，然后递归删除它。
    Node* succ = r->r;
while (succ->l) succ = succ->l;
r->val = succ->val;
r->r = erase(r->r, succ->val);
    为什么是对的（两个理由）
    ① 后继的值确实能站在这个位置：它是「所有大于当前值的元素里最小的那个」，所以放到当前位置后，左子树全部 < 它、右子树全部 > 它，BST 性质保持。
    ② 递归不会无限展开：后继是右子树的最左节点，所以它必然没有左孩子 ⟹ 最多只有一个孩子 ⟹ 递归删除它必然落到情形一或二。
    一个细节
    总是用后继（或总是用前驱）会让树逐渐偏向一侧。有些实现交替使用，或按子树高度选较高的那侧，以延缓退化。朴素 BST 里意义不大（反正会退化），但实现平衡树时会影响旋转次数。
  4. 基础什么时候该用 std::map 而不是 unordered_map？

    三个正当理由，没有一个是「map 更快」：

    ① 需要有序性 / 范围查询
    lower_bound、upper_bound、按序遍历、找「最接近 x 的元素」——哈希表根本做不到。这是最常见的理由。
    ② 需要确定性延迟
    树永远 O(log n)，无 rehash 抖动、无攻击面。哈希表是「期望 O(1)、最坏 O(n)、且偶尔一次 O(n) 停顿」。对 p99 敏感的服务、实时系统，可预测性比平均速度值钱。
    ③ 需要迭代器 / 引用稳定性
    std::map 插入不失效任何迭代器，删除只失效被删的那个。unordered_map 的 rehash 会失效所有迭代器（引用还有效）；absl::flat_hash_map 连引用都失效。
    顺带纠正一个常见误解
    「树一定比哈希表慢」不成立。n 较小时（几十到几百）std::map 常常更快：树的上层节点常驻 cache（被反复访问），而哈希表要先算 hash（string 键要扫全串）再做一次随机地址访问（几乎必然 cache miss）。
    交叉点约在 n 几百到一千，依赖 key 类型与哈希成本。小容器上先别急着换。
    还有更好的第四选项
    如果数据只读且要有序，用排序数组 + std::lower_bound——连续内存，比红黑树快得多（无指针追逐、无每节点一次分配）。这个选项经常被忽略。

10.2 中级（区分熟练度）

  1. 中级AVL 和红黑树的区别是什么？为什么 std::map 选红黑树？
    AVL红黑树
    不变式左右子树高度差 ≤ 1黑高相等 + 无连续红节点
    高度上界≈1.44 log n2 log n
    查找更快（树矮 ~30%）稍慢
    插入旋转≤ 2 次≤ 2 次
    删除旋转最坏 O(log n) 次≤ 3 次
    额外存储高度或平衡因子1 bit 颜色
    关键差异在删除
    AVL 删除后可能需要沿整条路径一路调整（每层一次旋转）；红黑树的删除修复最多 3 次旋转，其余通过改颜色解决。
    所以 std::map 选红黑树
    通用容器无法预知读写比，而红黑树的「最坏修改代价」更小、更可控。这是保守但正确的默认。
    选型判据：读远多于写 → AVL（树矮，查找快）；读写均衡或写多 → 红黑树。
    红黑树高度上界的推导（可能追问）
    设黑高 bh： · 性质 5（黑高相等）⟹ 任何路径至少 bh 个黑节点 · 性质 4（无连续红）⟹ 任何路径长度 ≤ 2·bh · 黑节点至少构成完美二叉树 ⟹ n ≥ 2^bh − 1 ⟹ bh ≤ log₂(n+1) ∴ h ≤ 2·bh ≤ 2 log₂(n+1)
    「无连续红」保证红节点最多占一半层级，这个『两倍』的松弛正是它修改更快的原因。
  2. 中级什么是 Morris 遍历？它的代价是什么？

    Morris 遍历用 O(1) 空间完成中序遍历（递归和显式栈都要 O(h)）。办法是临时借用叶子的空右指针指回当前节点，走完再断开。

    while (cur) {
    if (!cur->l) { visit(cur); cur = cur->r; }
    else {
        Node* pre = cur->l;
        while (pre->r && pre->r != cur) pre = pre->r;  // 找中序前驱
        if (!pre->r) { pre->r = cur; cur = cur->l; }      // 建线索，下潜
        else { pre->r = nullptr; visit(cur); cur = cur->r; } // 断线索，访问
    }
}

    复杂度仍是 O(n)——每条边最多被走 3 次（下潜、找前驱、返回）。

    三个真实限制（这才是考点）
    ① 遍历中修改了树结构（虽然结束会恢复）⟹ 不能并发遍历，也不能被其他线程同时读到；② 遍历中抛异常会留下损坏的树（线索没断开），之后任何操作都可能死循环——visit 可能抛异常时不要用；③ 树必须可写（不能是 const）。
    实际用途很窄
    只在「树极深（递归会爆栈）且内存极紧」时才值得。一般用显式栈就够（O(h) 空间，h 通常是 log n）。
    但它是体现「知道有 O(1) 方案」的好谈点，也是「换算法消掉栈」这一思路的漂亮例子——对比 递归与分治 里的三条去递归路径。
  3. 中级为什么数据库索引用 B+ 树而不是红黑树？B 树和 B+ 树的区别？

    因为磁盘上「一次节点跳转」比「一次比较」贵一千倍以上，优化目标从「减少比较次数」变成「减少跳转次数」。

    内存跳转 ≈ 100 ns（cache miss） 磁盘跳转 ≈ 100 µs（SSD）～ 10 ms（HDD） 二叉搜索树：log₂(10⁹) ≈ 30 次 I/O B+ 树 (B≈500)：log₅₀₀(10⁹) ≈ 3~4 次 I/O

    做法是把节点做成一个磁盘页大小（4–16 KB），每页放几百个 key。用页内的廉价二分（8–10 次内存比较）换掉 26 次磁盘 I/O。

    B 树 vs B+ 树：

    B 树B+ 树
    数据存哪内部节点也存只有叶子存
    每页 key 数较少更多 → 树更矮
    叶子之间无连接按序链成链表
    范围扫描要回树中序遍历顺着叶子链表顺序 I/O
    B+ 胜出的决定性理由是范围扫描
    SQL 的 BETWEEN、ORDER BY、GROUP BY 都是范围操作，叶子链表让它们变成顺序 I/O——磁盘上比随机 I/O 快一到两个数量级。
    B 树「单点查找可能在内部节点命中」的优势相比之下微不足道，而且它还让树变高了。
    顺带解释了覆盖索引和 LSM
    覆盖索引：查询需要的所有列都在索引叶子里 → 不用回表（回表 = 又一轮 B+ 树查找 + 随机 I/O）。
    LSM-Tree 存在的理由：B+ 树在写密集下会页分裂 + 随机写；LSM 把随机写变成顺序写（内存表 + 顺序落盘 + 后台 compaction），代价是读放大和写放大。「B+ vs LSM」本质是「读优化 vs 写优化」。
  4. 中级Redis 的 ZSet 为什么用跳表而不是红黑树？

    作者 antirez 给过三个理由，都不是「跳表更快」：

    ① ZSet 需要范围查询
    ZRANGE、ZRANGEBYSCORE 是核心操作。跳表的最底层就是一条有序链表，范围扫描是天然的顺序访问；红黑树要做中序遍历（指针跳来跳去）。
    ② 实现和调试简单得多
    没有旋转、没有颜色、删除逻辑直白——代码量约是红黑树的 1/3。对一个要长期维护的开源项目，这是实质性优势。
    ③ 容易支持「按排名查找」
    在每个前进指针上记一个跨度（span）即可实现 ZRANK / ZRANGE by index。红黑树要做这个得额外维护子树大小。
    跳表的平衡策略：用随机代替旋转
    每个节点插入时掷硬币决定层高（p=1/2 或 1/4），期望层高 log n ⟹ 期望查找 O(log n)。完全不需要任何旋转——「保持平衡」这个难题被外包给了随机数。
    代价是保证从「最坏 O(log n)」降级成「期望 O(log n)」。
    同一个结构在不同系统里的理由可以完全不同
    Redis 选它是为了范围查询 + 实现简单（它单线程，不关心并发）。
    ConcurrentSkipListMap（Java）和 RocksDB 的 memtable 选它是为了并发友好——跳表的修改是局部的（只改几个指针），容易做无锁；而平衡树的旋转会影响多个节点，无锁化极难。
    这个对比比记「跳表 vs 红黑树谁快」有价值得多。

10.3 高级（体现深度）

  1. 高级要实现一个搜索框自动补全，用什么数据结构？怎么支持「按热度排序」和百万级词库？

    「前缀查询」这个需求直接排除哈希表和平衡树——只有 Trie 族能做。但朴素 Trie 有三个问题要解决。

    ① 基础结构：Trie
    查找 O(键长)，与词库大小无关。走到前缀节点后遍历子树收集候选。
    ② 空间问题必须解决
    朴素 Trie 每节点 26 个指针 = 208 字节（64 位），实际可能只用 1–2 个。百万词、平均长 8 → 节点数几百万 → 几百 MB。
    三种压缩：路径压缩（基数树，单链节点合并）、自适应节点（ART：Node4/16/48/256 按需长大，Node16 用 SIMD）、双数组 Trie（两个整数数组编码整棵树，最省空间且 cache 友好，中文输入法常用）。
    ③ 按热度排序：在节点上预存 Top-K
    不要「收集所有后代再排序」——热门前缀（如 a）的后代可能有几十万个。
    在每个节点上预计算并缓存「以此为前缀的 Top-10」，查询变成 O(键长) + O(1)。这是空间换时间，也是所有生产补全系统的做法。
    热度更新时只需沿路径向上更新受影响的节点（O(键长)）。
    ④ 实际系统还要什么
    拼写容错（编辑距离 ≤ 1 的候选）→ Trie 上做带剪枝的模糊搜索，或用 BK-tree / SymSpell。拼音/首字母（中文）→ 建多套索引。个性化→ 全局 Top-K 与用户历史加权融合。实时性→ 热度用滑动窗口或 EWMA 而不是全量重算。
    工程上先考虑现成方案
    Elasticsearch 的 completion suggester（基于 FST，比 Trie 更省空间）、Redis 的 ZRANGEBYLEX（有序集合按字典序范围查，可以模拟前缀）。
    自己实现只在有特殊约束时才值得——比如需要嵌入到客户端、或词库有特殊结构。面试时先说「评估现成方案」再讲自研设计，比直接开始画 Trie 更能体现工程判断。
  2. 高级ART（自适应基数树）解决了 Trie 的什么问题？它和 Swiss Table 有什么共同点？

    ART 解决的是 Trie 的空间浪费问题，而它的解法思路和 Swiss Table 同源。

    Trie 的空间问题根源
    节点大小固定为字符集大小（256 个指针 = 2 KB），而实际孩子数分布极度不均——靠近根的节点孩子多，靠近叶子的往往只有 1–2 个。绝大多数指针是空的。
    ART 的两个改进
    ① 自适应节点大小：按孩子数选四种表示——
    · Node4：4 个 key 字节 + 4 个指针（线性查找）
    · Node16：16 个 key 字节 + 16 个指针（SIMD 一次比较 16 个）
    · Node48：256 字节索引表 + 48 个指针
    · Node256：直接 256 个指针（数组下标即字节）
    节点按需长大/缩小，既省空间又保留 O(键长)。
    ② 路径压缩：单链路径合并（继承基数树）。
    与 Swiss Table 的共同点
    「用 SIMD 在一小块连续数组上批量筛选」：
    · Swiss Table：16 个控制字节（哈希高 7 位）一条 SIMD 指令比完，筛掉 127/128 的候选。
    · ART 的 Node16：16 个key 字节一条 SIMD 指令比完，直接定位孩子。
    两者都是「把元数据压缩到极小的连续数组里，让一次 cache line 读取 + 一条 SIMD 指令完成大批量筛选」。

    这是现代数据结构的共同手法，同族还有：B 树式的 cache 内索引（一个 cache line 放 16 个 key）、布隆过滤器（小摘要挡住无效访问）。识别出这个模式，你在设计新结构时就多了一个工具。
    使用者与定位
    HyPer、DuckDB、部分内存数据库的主索引。它的定位是「内存数据库里替代 B+ 树的选项」——O(键长) 而非 O(log n)，且天然支持前缀和范围。
    代价是实现复杂度高（四种节点 + 转换逻辑），且对长键不如 B+ 树（键长 100 字节时 O(100) 未必优于 O(log n)）。
  3. 高级一个用 std::map 做内存索引的服务，QPS 上不去，profile 显示时间都在 map 查找上。怎么优化？

    红黑树的性能问题几乎总是指针追逐 + 每节点一次分配造成的，而不是 log n 这个次数。按性价比排序：

    ① 先问需不需要有序
    如果只做点查，换 absl::flat_hash_map——连续内存 + SIMD，通常快 3–5 倍。
    这一步收益最大，但经常被跳过：很多代码用 map 只是因为「习惯」或「以前需要有序，现在不需要了」。
    ② 需要有序但数据只读 → 排序数组 + lower_bound
    连续内存，二分的前几步会 cache miss 但后几步全命中；没有每节点一次分配、没有指针追逐。通常比红黑树快 2–3 倍，内存也省一半以上（每元素省掉两个指针 + 颜色 + malloc 头）。
    如果偶尔要更新，可以「批量重建」（攒一批改动后重排一次）。
    ③ 需要边读边写 + 有序 → 考虑跳表或 B 树式结构
    cache 内 B 树（一个 cache line 放 16 个 key，SIMD 比较）能把树高从 log₂n 降到 log₁₆n，cache miss 次数降 4 倍。ART 也是候选。
    高并发写场景 → 跳表（局部修改，易做无锁）。
    ④ 不换结构也能改善的两件事
    自定义分配器：std::map 每个节点一次 malloc，节点散落在堆上。用 arena / pool allocator 让节点连续分配，能显著改善 cache 局部性。
    缩小 key：如果 key 是长 string，比较成本高且节点大。改成存哈希值 + 短标识，或用 string_view 指向统一的字符串池。
    但先确认 profile 没骗你
    「时间都在 map 查找上」可能有两个假象：① 实际瓶颈是 key 的构造/比较（构造临时 std::string 做查找 → 每次一次分配），改用 map 的透明比较器（C++14 的 std::less<>）或 string_view key 就能解决；② 实际是内存带宽饱和，此时任何结构都受限，得先减少数据量。
    测量方法见 性能优化指南。
  4. 高级为什么平衡树很难做无锁并发，而跳表相对容易？

    根本原因是「一次修改影响多少个节点」。

    平衡树的困难
    旋转是一个涉及多个节点的原子性变更：一次旋转要同时改 3–4 个指针，而且可能沿路径向上连锁触发（AVL 删除最坏 O(log n) 次旋转）。
    要让并发读者始终看到一致的树，就得：
    · 用读写锁（写者独占整棵树 → 并发度低），或
    · 用细粒度锁 + 严格的加锁顺序（极易死锁，且旋转要锁多个节点），或
    · 用 RCU（每次修改复制受影响的路径，读者无锁——但写放大严重，且要延迟回收旧节点）。
    跳表为什么容易
    修改是局部的：插入一个节点只需在每一层做一次「前驱的 next 指针」的 CAS，各层可以独立地、逐层完成。
    关键在于即使只完成了部分层，结构仍然是「正确但不够优」的——底层链表始终有序完整，上层只是索引。读者顺着走一定能找到，只是可能慢一点。
    这个「中间状态也是合法状态」的性质是无锁化的关键，平衡树没有（旋转中途的树是非法的）。
    实践中的方案对照
    ConcurrentSkipListMap（Java）：无锁跳表，CAS + 标记删除。
    RocksDB memtable：无锁跳表（单写多读，写者也无锁）。
    Linux 内核的 RCU + 红黑树：读无锁（RCU 保护），写加锁——因为内核里读远多于写。
    B+ 树的 latch coupling / B-link 树：数据库用的方案，靠「节点内加短锁 + 右兄弟指针」让读者能追上分裂中的节点。
    可迁移的一般原则
    「设计并发数据结构时，先问『部分完成的修改是否仍是合法状态』」。
    是 → 可以无锁化（跳表、Michael-Scott 队列、Swiss Table 的部分操作）。
    不是 → 需要锁、RCU 或整体复制。
    这也解释了为什么无锁结构常常要重新设计数据布局，而不是给现有结构加 CAS——布局本身决定了能否无锁。相关展开见 并发模式。
