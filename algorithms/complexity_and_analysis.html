复杂度与分析

渐进复杂度是一门把实现细节和硬件差异全部抹掉的语言，它让「哪个算法更好」变成一个可以在纸上回答的问题。但它抹掉的东西不是不存在——同样是 O(n) 的遍历，链表能比数组慢一个数量级。这一篇既要把定义、摊销、主定理讲到能证明的程度，也要讲清楚渐进符号沉默的地方藏着什么。

01

为什么需要渐进分析

从「跑得快」到「可比较」

「这个算法快不快」是个坏问题，因为答案取决于 CPU 型号、编译器版本、输入长什么样、内存里还剩多少 cache。同一份代码在两台机器上差三倍，你没法用实测数字去讨论算法本身的好坏。

渐进分析给出的解法是：只问「输入规模翻倍时，工作量怎么变」。它主动放弃两样东西——常数因子和低阶项——换来一个跨机器、跨语言都成立的结论。这个取舍是整章的主题：先理解它买到了什么（§2–§6），再理解它付出了什么（§7）。

渐进复杂度像搬家公司的报价方式。报价单不会写「李师傅搬得比王师傅快 15%」，而是写「按箱数计费」。为什么？因为师傅是谁会变、天气会变、楼层会变，但「箱子多一倍、活多一倍」这个结构不会变。O(n) 就是「按箱数线性计费」，O(n²) 是「每个箱子都要和其他所有箱子核对一遍清单」——你不用知道师傅是谁，就能断定 1000 个箱子时后者会出事。

而 §7 讲的常数因子，就是报价单上没写的那句：有电梯和没电梯，同样的箱数差十倍。

02

五个记号的严格定义

O 是上界，不是「就是」

2.1 定义与直觉

这五个记号描述的是两个函数在 n 趋于无穷时的相对增长速度。它们都带一个「存在常数 c 和阈值 n₀」的前缀，这个前缀正是「忽略常数因子、只看足够大的 n」的形式化表达。

O(g) 上界（≤） ∃ c>0, n₀ > 0, ∀ n≥n₀: 0 ≤ f(n) ≤ c·g(n) Ω(g) 下界（≥） ∃ c>0, n₀ > 0, ∀ n≥n₀: 0 ≤ c·g(n) ≤ f(n) Θ(g) 确界（=） f ∈ O(g) 且 f ∈ Ω(g) o(g) 严格上界（<） ∀ c>0, ∃ n₀, ∀ n≥n₀: f(n) < c·g(n) ω(g) 严格下界（>） ∀ c>0, ∃ n₀, ∀ n≥n₀: f(n) > c·g(n)

注意 O 和 o 的量词方向不同：O 只要存在一个 c 能撑住就行，o 要求对任意多小的 c 都最终成立。所以 n² ∈ O(n²) 成立，但 n² ∈ o(n²) 不成立；n ∈ o(n²) 成立。

把它读成「集合」而不是「等于」：严格来说 O(n²) 是一个函数集合——所有增长不快于 n² 的函数。工程界习惯写 f(n) = O(n²)，但这个等号是单向的：可以说 3n+7 = O(n²)，不能反过来说 O(n²) = 3n+7。理解成 f ∈ O(n²) 就不会出错。
四个记号像体检报告上的区间。O 是「不超过」——医生说你血压不超过 140，这话没错，哪怕你实际是 110。Ω 是「不低于」。Θ 才是「就在这个范围」。所以当面试官问「快排的复杂度」而你答「O(n²)」时，你说的是真话但没信息——就像回答「我血压不超过 300」。他真正想听的是「平均 Θ(n log n)、最坏 Θ(n²)」这种带口径的答案。

2.2 四种常见误用

❌ 说法
1. 「快排是 O(n log n)」
   —— 漏了口径。最坏是 Θ(n²)。

2. 「O(2n) 比 O(n) 慢」
   —— 两者是同一个集合。

3. 「哈希表查找是 O(1)，所以
    一定比红黑树的 O(log n) 快」
   —— 混淆了渐进与实测。

4. 「最坏 O(n²) 说明它不能用」
   —— 忽略了最坏是否可触发。
✅ 说法
1. 平均 Θ(n log n)，最坏 Θ(n²)；
   随机化 pivot 后最坏发生概率极低。

2. O(2n) = O(n)。想表达「常数大
   一倍」要说常数因子，不能用 O。

3. n=64 时 log n = 6，哈希要算
   hash + 可能 cache miss，红黑树
   常常更快。渐进只在 n 大时生效。

4. 要问「最坏输入是否可被攻击者
   构造」。可以 → 是安全问题（哈希
   碰撞 DoS）；不可以 → 通常可接受。
第 4 条在生产上最贵。2011 年的 Hash-DoS 就是这样：攻击者构造大量哈希冲突的 key，把哈希表的 O(1) 拖成 O(n)，几十 KB 的 POST 请求就能打满一个 CPU 核。修复手段不是换数据结构，而是给哈希函数加随机种子（SipHash），让攻击者算不出最坏输入。
换句话说：「最坏情形」的工程价值，取决于谁能决定输入。

2.3 增长曲线的真实差距

纸上「n² 比 n log n 差」很抽象。下面这张图把 n=1..64 的实际操作数画在对数纵轴上——注意纵轴每一格是 10 倍，所以曲线之间看起来不大的间距，实际是数量级差异。

这张图解释了一个常被忽略的事实：O(n log n) 和 O(n) 的差距远小于 O(n²) 和 O(n log n) 的差距。log n 在工程规模内几乎是个小常数（n=10⁹ 时 log n≈30），所以「把 O(n log n) 优化成 O(n)」的收益通常有限，而「把 O(n²) 干掉」几乎总是值得做的。优化精力应该按这个顺序分配。

03

怎么把代码数成复杂度

三条法则，以及循环层数骗人的地方

3.1 三条运算法则

法则形式说明
加法（顺序执行）O(f) + O(g) = O(max(f, g))先排序再遍历 = O(n log n) + O(n) = O(n log n)
乘法（嵌套）O(f) × O(g) = O(f·g)外层 n 次、内层每次 log n = O(n log n)
常数吸收O(c·f) = O(f)，c 为常数包括 O(2ⁿ⁺¹)=O(2ⁿ)，但 O(2²ⁿ)≠O(2ⁿ)

加法法则是「优化时只看瓶颈」的理论依据：一个 O(n²) 加一个 O(n) 的流水线，把 O(n) 那段优化到极致也没用。

常数吸收有个容易踩的边界：O(2ⁿ⁺¹) = O(2·2ⁿ) = O(2ⁿ) 对——常数在指数外面。但 O(2²ⁿ) = O(4ⁿ)，这不等于 O(2ⁿ)——常数在指数里面时是乘在增长率上的。同理 O(log n²) = O(2 log n) = O(log n)，而 O((log n)²) 不能化简。

3.2 循环不能只看层数

「两层循环就是 O(n²)」是初学者最容易犯的错。真正要数的是内层循环体实际执行的总次数。

看着像 O(n²)，其实是 O(n log n)
// 外层每次 i 翻倍 → 只有 log n 层
for (int i = 1; i <= n; i *= 2)
    for (int j = 0; j < n; ++j)
        work();
// 总次数 = n · log n
看着像 O(n²)，其实是 O(n)
// 双指针：j 全程只前进，不回退
int j = 0;
for (int i = 0; i < n; ++i)
    while (j < n && ok(i, j)) ++j;
// j 最多前进 n 次 → 总次数 ≤ 2n

右边这个模式极其重要，它是双指针、滑动窗口、单调栈的共同复杂度论证方式：不看单次循环的最坏长度，而看某个量在整个算法过程中的总变化量。这本质上就是 §4 的摊销思想。

调和级数：O(n log n)
for (int i = 1; i <= n; ++i)
    for (int j = i; j <= n; j += i)
        work();
// n/1 + n/2 + n/3 + ... + n/n
//   = n·H(n) ≈ n·ln n
// 埃拉托斯特尼筛的复杂度来源
隐藏在库函数里的 O(n)
for (int i = 0; i < n; ++i)
    s = s + to_string(v[i]);  // ← 拷贝整个 s
// 看着单层循环，实际 O(n²)

s.reserve(n * 8);            // 修复：
for (int i = 0; i < n; ++i)
    s += to_string(v[i]);       // O(n) 摊销
右边这类 bug 在 code review 里最难看出来，因为它藏在运算符和库调用背后。同类的坑还有：在循环里对 std::vector 做 insert(begin(), x)（每次 O(n)）、对 std::string 用 substr 切片（每次分配+拷贝）、在循环里 std::map::operator[] 反复查找同一个 key。数复杂度时，把每个函数调用都替换成它的复杂度再数。

3.3 复杂度速查

复杂度名称n=10⁶ 时约典型来源
O(1)常数1数组下标、哈希查找（摊销）、栈顶
O(log n)对数20二分查找、平衡树、堆的单次调整
O(n)线性10⁶单遍扫描、双指针、计数排序

04

摊销分析三法

为什么 push_back 是 O(1)，尽管它有时要搬走整个数组

std::vector::push_back 大多数时候只是写一个元素（O(1)），但容量满时要申请新内存、把全部 n 个元素搬过去（O(n)）。说它是「O(n)」不公平——那种情况极少发生；说它是「O(1)」又需要证明。摊销分析就是把这类「偶尔很贵」的操作分摊到整个操作序列上，给出一个诚实的平均代价。

摊销复杂度（amortized complexity）：对任意长度为 m 的操作序列，总代价不超过 m·T(n)，则称单次操作的摊销代价为 T(n)。它是关于操作序列的确定性上界，不涉及任何概率假设——这一点是它和「平均复杂度」的本质区别（见 §4.5）。

4.1 聚合法：vector 扩容

聚合法（aggregate method）最直接：算出 m 次操作的总代价，再除以 m。

设初始容量 1，每次满时容量翻倍。做 n 次 push_back，扩容发生在第 1、2、4、8、…、2^k 次（2^k < n），每次扩容搬 2^k 个元素：

搬移总量 = 1 + 2 + 4 + 8 + ... + 2^k = 2^(k+1) - 1 < 2n （因为 2^k < n） 总代价 = n 次写入 + 少于 2n 次搬移 < 3n 单次摊销 = 3n / n = O(1)

关键在于等比数列求和：公比大于 1 的等比数列，其和由最后一项主导，是最后一项的常数倍。所以「所有历史扩容加起来」不超过「最后一次扩容」的两倍——这就是翻倍策略能给出 O(1) 摊销的全部原因。

像换更大的房子。你不会每添一件家具就搬一次家，而是等塞满了一次性搬到两倍大的房子。虽然搬家那天很累（O(n)），但因为每次房子都翻倍，你一辈子搬家的总工作量不超过最后一次搬家的两倍。均摊到每件家具头上，每件家具只承担了常数次搬运。

反过来，如果每次只「加一间房」（容量 +1），那你每添一件家具就得搬一次家——总代价变成 1+2+3+…+n = O(n²)，均摊 O(n)。这就是下面 4.4 要讲的：增长必须是乘性的，不能是加性的。

4.2 记账法

记账法（accounting method）换个视角：给每次操作预收一笔固定费用，便宜的操作把余款存起来，昂贵的操作用存款付账。只要账户余额永不为负，预收的费用就是合法的摊销上界。

对 vector 扩容，我们对每次 push_back 收 3 个单位：

用途费用说明
写入自己1立刻花掉
预付「自己将来被搬一次」1存起来
预付「帮一个老元素搬一次」1存起来

为什么第三笔够用？容量从 c 翻到 2c 时，要搬 c 个元素。而这 c 个元素中，后一半（c/2 个）是上次扩容之后新加进来的，每个都存了 2 个单位（自己 + 帮一个老元素），合计 c 个单位，正好覆盖这次搬移的 c 次操作。账户永不透支，故摊销代价 = 3 = O(1)。

4.3 势能法

势能法（potential method）是三者中最通用的，也是证明并查集、斐波那契堆、splay 树复杂度的标准工具。它定义一个势能函数 Φ 度量数据结构的「紧张程度」，然后要求：

摊销代价 = 实际代价 + ΔΦ = 实际代价 + Φ(after) - Φ(before) 若 Φ(初始) = 0 且 Φ(任何时刻) ≥ 0，则 Σ 摊销代价 = Σ 实际代价 + Φ(末) - Φ(初) ≥ Σ 实际代价 → 摊销代价之和是实际总代价的合法上界

对 vector，取 Φ = 2·size − capacity（刚扩容后 size = capacity/2，Φ=0；写满时 size = capacity，Φ = capacity）：

  • 不触发扩容：实际代价 1，size+1 使 Φ 增加 2 → 摊销 = 1 + 2 = 3。
  • 触发扩容（size = capacity = c）：实际代价 c 次搬移 + 1 次写入。扩容后 capacity = 2c、size = c+1，新 Φ = 2(c+1) − 2c = 2；旧 Φ = 2c − c = c。故 ΔΦ = 2 − c。摊销 = (c+1) + (2−c) = 3。

两种情况都是 3，摊销 O(1)。势能法的威力在于：它把「贵操作」的代价提前藏进势能里，贵操作发生时势能释放，正好抵消。找到合适的 Φ 是全部难点。

并查集的 O(α(n)) 就是用势能法证的，其中 α 是反 Ackermann 函数——对任何现实的 n（哪怕 2^65536），α(n) ≤ 4。所以工程上直接当常数用。这个证明会在 并查集与区间结构（批次 3）里展开。

4.4 1.5× 还是 2×

翻倍能给出 O(1) 摊销，但增长因子具体取多少是个真实的工程取舍。libstdc++ 用 2×，MSVC 的 STL 用 1.5×，Facebook 的 folly::fbvector 用 1.5×。

维度2×1.5×
摊销搬移次数每元素约 1 次每元素约 2 次（因子越小、搬得越勤）
内存浪费上限最多浪费 50%最多浪费 33%
能否复用已释放空间不能可以
扩容次数（到 n）log₂ nlog₁.₅ n ≈ 1.7 log₂ n

「能否复用已释放空间」是 1.5× 最有意思的理由。用 2× 时，历史块的总和 1+2+4+…+2^(k−1) = 2^k − 1，永远差 1 个单位不够放下一块，所以分配器无法把前面释放的空间拼起来复用，堆会持续向高地址增长。而 1.5× 时历史块之和终会超过下一块所需，分配器有机会原地复用，长期碎片更少。

这个差异只在单一大 vector 反复增长的场景下明显；实际程序里堆上还有其他分配夹杂，效果会被稀释。所以两种因子都活得很好——这正是「渐进相同、常数不同」的典型案例：渐进分析告诉你两者都是 O(1) 摊销，剩下的选择要靠工程测量。

还有一个必须知道的实践点：reserve 能把摊销变成真正的 O(1)，代价是你要预估容量。但 reserve 之后 push_back 到超过预留量，容量仍按增长因子从当前值翻倍，不会回到「按需精确分配」。而 shrink_to_fit 是非绑定请求，标准只要求它「不增加容量」。

4.5 摊销 ≠ 平均

这是面试里最能区分理解深度的一个点。

摊销（amortized）平均（average-case）
依赖概率假设不依赖依赖输入分布假设
保证强度对任意操作序列都成立只对「典型输入」成立
能否被攻击者破坏不能能（构造最坏输入）
例子vector::push_back、并查集快排的 Θ(n log n)、哈希表在均匀哈希假设下

摊销是确定性的：不存在「运气不好」的操作序列让 n 次 push_back 超过 O(n)。而快排的平均 O(n log n) 是对输入分布求期望——存在具体输入让它退化成 O(n²)，只是随机化 pivot 后你（或攻击者）找不到它。

摊销 O(1) 并不意味着「每次都快」。单次 push_back 仍可能耗时 O(n)——这在低延迟系统里是致命的尾延迟来源。实时/低延迟场景的标准做法是启动时 reserve 到峰值，运行期绝不让容器扩容，把摊销 O(1) 换成真正的最坏 O(1)。参见 低延迟编程。

递归树与主定理

分治算法复杂度的通用解法

分治算法的复杂度天然是个递推式：T(n) = a·T(n/b) + f(n)——把问题分成 a 个规模为 n/b 的子问题，额外花 f(n) 做划分和合并。归并排序是 T(n)=2T(n/2)+Θ(n)，二分查找是 T(n)=T(n/2)+Θ(1)。本节给出两种求解工具。

5.1 递归树：把递归摊平

递归树把递推式画成一棵树，每层的代价加起来，再把所有层加起来。它不需要记公式，而且能看出复杂度由谁主导。以归并排序 T(n)=2T(n/2)+n 为例：

用递归树时问自己三个问题：① 每层总代价是多少？② 树有多高（子问题缩到 1 需要几次除以 b，即 log_b n）？③ 叶子有多少个（a^(log_b n) = n^(log_b a)）？

然后看代价集中在哪里：集中在根（每层递减）、均匀分布（每层相同）、还是集中在叶子（每层递增）。这三种情况正对应主定理的三个情形。

5.2 主定理三情形

主定理（Master Theorem）把上面的判断做成了公式。对 T(n) = a·T(n/b) + f(n)，其中 a ≥ 1、b > 1，令 临界指数 c* = log_b a（它就是叶子数的指数）：

情形一（叶子主导） f(n) = O(n^(c*−ε)) → T(n) = Θ(n^c*) 情形二（各层均匀） f(n) = Θ(n^c* · log^k n) → T(n) = Θ(n^c* · log^(k+1) n) 情形三（根部主导） f(n) = Ω(n^(c*+ε)) 且 a·f(n/b) ≤ c·f(n) → T(n) = Θ(f(n))

直觉版本：把 f(n)（合并的代价）和 n^c*（叶子的总代价）比大小，谁大听谁的；一样大就多乘一个 log n。

情形谁主导递归树形状结论
一叶子（子问题多）每层代价递增，叶子层最贵Θ(n^c*)，等于叶子总数
二势均力敌每层代价相同叶子代价 × log n
三根（合并太贵）每层代价递减，根最贵Θ(f(n))，等于根的代价
情形三多了一个「正规性条件」a·f(n/b) ≤ c·f(n)（某个 c < 1）。它保证 f 增长得足够「规矩」，各层代价确实按几何级数递减。绝大多数多项式形式的 f 都满足；反例是 f(n) = n²·sin²n 这种震荡函数——面试里几乎不会考，但知道它存在能说明你不是死背公式。

情形一像层层转包的工程。总承包商自己干的活（f(n)）无论多努力都无关大局，因为真正的成本发生在最底层的无数个小工队（叶子）身上。想省钱，唯一有效的办法是减少每级的分包数量（降低 a）——这就是 Strassen 和 Karatsuba 干的事。

情形三反过来：小工队再多也不重要，成本全在总承包商的协调工作上，优化 f 才有意义。

5.4 主定理不适用时

主定理要求子问题规模相等。三类常见的失效情况：

  • 子问题不等分，如 T(n) = T(n/3) + T(2n/3) + Θ(n)（快排某些划分）。用递归树估计：最短路径 log₃n、最长路径 log_{3/2}n，每层代价 ≤ n，得 O(n log n)。或者用 Akra–Bazzi 定理（主定理的推广）精确求解。
  • 规模是减法而非除法，如 T(n) = T(n−1) + Θ(n)（退化的快排）。直接展开：n + (n−1) + … + 1 = Θ(n²)。
  • 子问题个数随 n 变化，如 T(n) = √n · T(√n) + Θ(n)。这类要靠换元（令 n = 2^m）或直接展开。
兜底方法永远是代入法（substitution）：猜一个答案，用数学归纳法验证。猜 O(n log n) 就假设 T(k) ≤ c·k log k 对所有 k < n 成立，代进递推式看能否推出 T(n) ≤ c·n log n。猜错了归纳会卡住，卡在哪里通常就提示了正确的量级。

❌ 朴素快排：最坏栈深 O(n)
void qsort_bad(int* a, int lo, int hi) {
    if (lo >= hi) return;
    int p = partition(a, lo, hi);
    qsort_bad(a, lo, p - 1);
    qsort_bad(a, p + 1, hi);  // 两边都递归
}
// 已排序数组 + 取末位为 pivot：
// 每次只切掉一个 → 栈深 n → SIGSEGV
✅ 尾递归消除 + 先小后大：O(log n)
void qsort_ok(int* a, int lo, int hi) {
    while (lo < hi) {
        int p = partition(a, lo, hi);
        // 只对「较小的一半」递归
        if (p - lo < hi - p) {
            qsort_ok(a, lo, p - 1);
            lo = p + 1;      // 大半边转循环
        } else {
            qsort_ok(a, p + 1, hi);
            hi = p - 1;
        }
    }
}
// 递归的那半 ≤ n/2 → 栈深 ≤ log₂ n

右边这个技巧值得记住：「只递归小的一半、大的一半改成循环」把栈深从 O(n) 硬压到 O(log n)，而且与 pivot 选得好不好无关。这是无条件的保证，不依赖任何概率假设。libstdc++ 的 std::sort 就用了这个模式（细节见 排序全景 §9）。

递归栈帧的具体布局、尾调用为何在 C++ 里不保证被消除、以及爆栈时怎么从 core dump 认出来，在 递归与分治 §2 有完整展开。

渐进之外：常数因子

渐进符号沉默的地方，藏着 10 倍的性能差

前面六章都在教你怎么用渐进分析。这一章讲它什么时候会骗你——这也是把算法知识从「刷题」升级到「工程」的关键一步。

7.1 内存墙与 cache line

渐进分析隐含一个假设：每次基本操作代价相同（RAM 模型）。这个假设在 1970 年代大致成立，今天已经严重失真——一次 L1 命中约 1 ns，一次主存访问约 100 ns，差 100 倍。也就是说，「访问一个内存单元」这个被算作 O(1) 的操作，其实内部有两个数量级的浮动。

层级典型延迟换算成 CPU 周期（3 GHz）容量量级
寄存器< 0.3 ns~1几百字节
L1 cache~1 ns~432–64 KB
L2 cache~4 ns~120.5–2 MB
L3 cache~15 ns~458–64 MB
主存（DRAM）~80–100 ns~300GB 级
NVMe SSD~50–100 µs~300 000TB 级

CPU 不是按字节读内存的，而是按 cache line（x86-64 上是 64 字节）整块读。这带来两条决定性的性质：

  • 空间局部性：读了 a[0]，a[1..15]（假设 4 字节 int）已经免费在 cache 里了。顺序遍历数组时，每 16 个元素只有 1 次 miss。
  • 硬件预取：CPU 检测到顺序访问模式后会提前把后续 cache line 取进来，让 miss 延迟被计算重叠掉。这个机制只对可预测的访问模式生效——随机跳转（指针追逐）完全无效。
内存访问像去图书馆借书。cache line 是「一次借一整个书架格」——你要第 1 本，管理员把那一格 16 本全搬给你。

数组遍历：书按顺序摆，搬一次够读 16 本，而且管理员看你读得快，会主动把下一格提前搬来（预取）。
链表遍历：每本书里写着下一本在哪个楼层哪个房间。你读完一本才知道下一本在哪，管理员没法提前准备，每本都要跑一趟。哪怕总共也是 16 本书，跑腿次数差 16 倍——而渐进分析会说两者都是 O(n)。

7.2 list 的 O(1) 输给 vector 的 O(n)

教科书说：在容器中间插入，std::list 是 O(1)、std::vector 是 O(n)，所以频繁插入该用 list。实测结论恰好相反，而且不是差一点——在几万元素规模下 vector 常快 5–10 倍。

把两者的真实代价拆开看：

vector 中间插入list 中间插入

插入动作本身O(n) memmoveO(1) 改两个指针
memmove 的实际速度SIMD 批量搬，~10 GB/s—
每元素内存开销4 字节（int）24–32 字节

关键在第一行：list 的 O(1) 插入前提是「你已经有了那个位置的迭代器」。如果需要先找到位置，那 O(n) 的查找不但没省掉，还是最慢的那种 O(n)。而 vector 的 O(n) memmove 是连续内存上的 SIMD 批量搬运，每字节成本极低。

std::list 真正有优势的场景是：已持有迭代器 + 需要迭代器/引用在插删后保持有效 + splice 拼接。典型例子是 LRU 缓存——哈希表存着「key → list 迭代器」，所以移动到表头是真正的 O(1)，且不会让其他迭代器失效。这个用法在 存储与数据架构 里有完整实现。
不要把这一节读成「渐进分析没用」。正确的读法是：渐进分析决定 n 大时的量级（不可违抗），常数因子决定同量级内的胜负（可优化 10 倍）。先用渐进分析排除 O(n²)，再用测量优化常数。跳过第一步去调常数，是在给一个错误的算法抛光。

最坏 / 平均 / 期望 / 摊销

四种口径，以及为什么线上只看 p99

8.1 四种口径的区别

口径对什么取极值/平均需要什么假设典型例子
最坏 worst-case所有输入中最差的那个无归并排序 Θ(n log n)、堆排序 Θ(n log n)
平均 average-case对输入分布求期望输入分布假设快排在「所有排列等概率」下 Θ(n log n)
期望 expected对算法内部随机数求期望无输入假设，随机源可靠随机化快排、跳表、随机化哈希
摊销 amortized对操作序列求平均无vector::push_back、并查集

平均和期望的区别常被混为一谈，但工程含义完全不同。平均把不确定性放在输入上——攻击者控制输入就能稳定命中最坏。期望把不确定性放在算法自己的随机源上——攻击者不知道你的随机数，所以对任何固定输入，你都能获得好的期望性能。

随机化的真正价值：它不改善最坏复杂度（随机化快排的最坏仍是 Θ(n²)），但它把「最坏何时发生」从攻击者可控变成不可控。这是一个安全性质，不是性能性质。跳表用随机层高代替红黑树的旋转、哈希表用随机种子抵御 Hash-DoS，都是同一个思路。

8.2 为什么线上看 p99

算法课关注均值，生产系统关注尾部。原因是请求扇出会放大尾延迟：一个用户请求若并行调用 100 个下游服务并等全部返回，那么只要单个服务的 p99 是 1 秒，这个用户请求有 1 − 0.99¹⁰⁰ ≈ 63% 的概率至少碰上一个慢响应。

用户可见延迟 = max(所有扇出调用的延迟) 扇出 n 次、单次 p99 = L 时： P(至少一次超过 L) = 1 − 0.99^n n=10 → 9.6% n=100 → 63.4% n=1000 → 99.996%

这直接改变算法选型标准。摊销 O(1) 的 push_back 在均值上完美，但那次 O(n) 的扩容恰好落在某个请求上时，这个请求就成了 p99。所以低延迟系统的通用纪律是：

  • 预分配：启动时 reserve 到峰值容量，把摊销 O(1) 变成最坏 O(1)。
  • 避免不可预测的分配：用对象池 / arena，或固定容量的环形缓冲区。
  • 宁要稳定的 O(log n)，不要抖动的摊销 O(1)：这就是为什么很多实时系统用平衡树而不是哈希表——红黑树每次查找都是稳定的 log n，哈希表 rehash 时会突然停顿。
  • 分摊贵操作：增量式 rehash（Redis 的做法）、分代 GC，都是把一次长停顿切成很多次短停顿。
尾延迟的完整方法论——怎么测、怎么归因、扇出场景下的对冲请求（hedged request）——在 低延迟编程 和 限流·熔断·降级·隔离 里有系统展开。

P、NP 与工程含义

当问题本身就是难的，该怎么办

前面讨论的都是「这个算法多快」。复杂度类讨论的是另一个层次的问题：这个问题存在快算法吗。工程上它的价值是给你一个止损信号——知道某个问题是 NP-hard，你就该停止寻找精确多项式算法，转向近似或启发式。

类定义直觉例子
P存在多项式时间算法求解能高效解出来排序、最短路、最大流、线性规划
NP解的正确性可在多项式时间内验证能高效验算SAT、图着色、TSP 判定版；P ⊆ NP
NP-完全属于 NP，且 NP 中所有问题都可多项式归约到它NP 里最难的一批，彼此等价SAT、3-SAT、背包（判定版）、团、顶点覆盖
NP-hardNP 中所有问题都可归约到它（自身不必属于 NP）至少和 NP-完全一样难TSP 优化版、停机问题
P 和 NP 的区别像解数独 vs 检查数独。给你一个填好的数独，你几分钟就能验证对不对（NP：验证容易）。但从空盘开始解一个 n×n 的广义数独，没人知道有没有快算法（是否属于 P，未知）。

NP-完全再加一层：这些问题之间可以互相「翻译」。如果你找到了 SAT 的多项式算法，那么全部 NP 问题瞬间都被解决了——这就是 P vs NP 问题的分量所在。也正是这个等价性让 NP-完全成了一个实用的止损信号：几十年里最聪明的人都没能攻破其中任何一个，你手上这个大概也不会例外。

证明一个问题 NP-hard 的标准姿势是归约：找一个已知 NP-完全的问题 X，构造一个多项式时间的变换，把 X 的任意实例变成你的问题 Y 的实例。这说明「Y 能快速解 ⟹ X 也能快速解」，故 Y 至少和 X 一样难。注意归约方向——是把已知难题归约到你的问题，反过来证明的是「你的问题不比 X 难」，那是另一回事。

改问题放松约束，换成一个属于 P 的近亲不再是原问题整数规划 → 线性规划松弛后取整
工程上最实用的一条常常是「改问题」。很多所谓的 NP-hard 需求，是把业务约束抽象过头了。比如「给 1000 个任务排最优调度」是 NP-hard，但如果业务上「保证 95% 的任务在 SLA 内 + 最坏不超过 2 倍」就够用，那就变成了一个可以贪心解决的问题。在动手找算法之前，先确认需求真的要最优解。
别把 NP 读成「non-polynomial」——它是 Nondeterministic Polynomial（非确定性图灵机上的多项式时间）。而且 NP-hard 不等于「指数时间」：停机问题是 NP-hard 但根本不可判定，而 P ⊆ NP 说明 NP 里也有很多容易的问题。

按难度分三段，先自测再对照

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础O、Θ、Ω 有什么区别？为什么说「快排是 O(n log n)」不算完整回答？

    O 是上界（f 增长不快于 g），Ω 是下界，Θ 是两者同时成立即确界。三者都带「存在常数 c 和阈值 n₀」的前缀，用来忽略常数因子和小规模行为。

    「快排是 O(n log n)」有两个问题：

    缺口径
    没说是最坏、平均还是期望。快排的最坏是 Θ(n²)（例如已排序输入 + 取端点为 pivot），平均才是 Θ(n log n)。不说口径等于隐瞒了退化风险。
    用 O 而非 Θ
    O 只给上界，所以「快排是 O(n²)」也是真话——但没信息量。要表达「就是这个量级」应该用 Θ。

    完整答法：平均/期望 Θ(n log n)，最坏 Θ(n²)；随机化 pivot 或 median-of-medians 后最坏可控。

  2. 基础下面两段代码的复杂度分别是多少？为什么？ 
    // A
for (int i = 1; i <= n; i *= 2)
    for (int j = 0; j < n; ++j) work();

// B
int j = 0;
for (int i = 0; i < n; ++i)
    while (j < n && ok(i, j)) ++j;

    A 是 Θ(n log n)：外层 i 每次翻倍，只有 ⌊log₂n⌋+1 层，每层内层跑 n 次。

    B 是 Θ(n)：虽然是两层，但 j 在整个过程中只增不减，最多前进 n 次。外层 n 次 + 内层总共 n 次 = 2n。

    通用方法
    不要数循环层数，数循环体的总执行次数。B 用的是「势能/记账」思路：找一个单调变化的量（这里是 j），它的总变化量就是内层的总代价上界。双指针、滑动窗口、单调栈的 O(n) 都靠这个论证。
  3. 基础为什么 std::vector::push_back 是 O(1)，尽管它有时要搬走整个数组？

    因为它是摊销 O(1)。容量每次翻倍，所以做 n 次 push_back，扩容发生在第 1、2、4、…、2^k 次，搬移总量是等比数列：

    1 + 2 + 4 + ... + 2^k = 2^(k+1) − 1 < 2n

    总代价 < n（写入）+ 2n（搬移）= 3n，除以 n 次操作得摊销 O(1)。

    关键
    公比 > 1 的等比数列，其和是最后一项的常数倍。所以「所有历史扩容之和」不超过「最后一次扩容」的两倍。
    反例
    如果每次容量 +1（加性增长），搬移总量变成 1+2+…+n = Θ(n²)，摊销就是 O(n)。增长必须是乘性的。

    要注意摊销 O(1) 不代表每次都快——单次仍可能 O(n)，这是尾延迟来源，低延迟场景要 reserve 规避。

  4. 基础n = 10⁵ 和 n = 5000 分别提示你用什么复杂度的算法？

    基准：现代 CPU 单线程每秒约 10⁸～10⁹ 次简单操作，常见时限 1 秒。

    n可行复杂度常见算法
    10⁸～10⁹O(n)单遍扫描、双指针、计数排序
    10⁵～10⁶O(n log n)排序、堆、平衡树、线段树
    5000O(n²)双层循环 DP、Floyd 的一层、朴素最近对
    300O(n³)Floyd 全源最短路、区间 DP
    20～25O(2ⁿ)状压 DP、子集枚举
    ≤ 11O(n!)全排列枚举
    反向使用
    数据范围就是出题人给的复杂度暗示。看到 n≤20 基本是状压/回溯；看到 n≤10⁵ 但要求多次查询，大概率要预处理成 O(1)/O(log n) 查询。面试时把这个推理说出来，比直接报答案更能体现思路。

10.2 中级（区分熟练度）

  1. 中级「摊销复杂度」和「平均复杂度」的本质区别是什么？举例说明。

    摊销不依赖任何概率假设，平均依赖输入分布假设。

    摊销
    对任意长度为 m 的操作序列，总代价 ≤ m·T(n)。这是确定性上界——不存在「运气不好」的序列让 n 次 push_back 超过 O(n)。
    平均
    对输入分布求期望。快排的 Θ(n log n) 假设「所有排列等概率」；存在具体输入让它退化成 Θ(n²)，只是在假设的分布下概率很低。
    工程后果
    平均复杂度可被攻击。2011 年的 Hash-DoS 就是构造大量哈希冲突的 key，把哈希表的 O(1) 拖成 O(n)，几十 KB 请求打满一个核。修复不是换数据结构，而是给哈希函数加随机种子（SipHash），让攻击者算不出最坏输入。
    还有第三种：期望
    随机化算法的「期望 O(n log n)」把不确定性放在算法自己的随机源上，而不是输入上。所以对任意固定输入都有好的期望性能——这是安全性质。随机化快排、跳表都属于这一类。
  2. 中级用主定理分析 T(n)=2T(n/2)+n、T(n)=T(n/2)+1、T(n)=7T(n/2)+n²。

    对 T(n)=a·T(n/b)+f(n)，先算临界指数 c* = log_b a，再把 f(n) 和 n^c* 比大小。

    递推式c* = log_b af(n) vs n^c*情形结果
    2T(n/2)+nlog₂2 = 1n = n¹，相等二（k=0）Θ(n log n)
    T(n/2)+1log₂1 = 01 = n⁰，相等二（k=0）Θ(log n)
    7T(n/2)+n²log₂7 ≈ 2.807n² < n^2.807一Θ(n^log₂7) ≈ Θ(n^2.807)

    三者分别是归并排序、二分查找、Strassen 矩阵乘法。

    直觉记法
    n^c* 是叶子的总代价，f(n) 是根的代价。谁大听谁的（情形一 / 三），一样大就多乘一个 log n（情形二）。Strassen 落在情形一说明它的收益全部来自「把 8 次子乘降到 7 次」（降 a），而不是优化合并。
    情形三别忘正规性条件
    还要满足 a·f(n/b) ≤ c·f(n)（某个 c<1），保证各层代价按几何级数递减。多项式形式的 f 基本都满足。
  3. 中级递归实现的快排，为什么最坏栈深是 O(n)？怎么无条件压到 O(log n)？

    最坏 O(n) 的来源：pivot 每次都取到极值（如已排序数组取末位），划分变成「1 个元素 + n−1 个元素」，递归链长 n。Linux 默认线程栈 8 MB，n 到 10⁵ 量级就 SIGSEGV。

    修复不是「选更好的 pivot」——那只降低概率，不给保证。正确做法是两个技巧叠加：

    只递归小半边
    比较两侧长度，对较短的那半递归，较长的那半通过修改 lo/hi 转成循环（手工尾递归消除）。递归的那半必然 ≤ n/2，所以栈深 ≤ log₂n。
    while (lo < hi) {
    int p = partition(a, lo, hi);
    if (p - lo < hi - p) { qsort(a, lo, p-1); lo = p+1; }
    else                 { qsort(a, p+1, hi); hi = p-1; }
}
    为什么这是无条件保证
    它不依赖 pivot 质量。哪怕每次划分都极度不均，「较短的一半」也一定不超过一半，log 上界照样成立。这是确定性的，和随机化 pivot（概率性的）互补——工程上两个都要。

    libstdc++ 的 std::sort 同时用了这个模式和「深度超限转堆排」（introsort），后者把时间最坏也拉回 O(n log n)。

  4. 中级vector 的增长因子选 2× 还是 1.5×？各自的理由是什么？

    两者都给出摊销 O(1)（只要是乘性增长），差别在常数与内存行为。libstdc++ 用 2×，MSVC STL 和 folly::fbvector 用 1.5×。

    维度2×1.5×
    每元素摊销搬移次数约 1 次约 2 次
    内存浪费上限50%33%
    扩容次数（到 n）log₂n≈1.7 log₂n
    能否复用已释放空间不能可以
    1.5× 最有意思的理由
    用 2× 时历史块之和 1+2+4+…+2^(k−1) = 2^k − 1，永远差 1 个单位不够放下一块，所以分配器没法把前面释放的空间拼起来复用，堆持续向高地址增长。1.5× 时历史块之和最终会超过下一块所需，有机会原地复用，长期碎片更少。
    实践要点
    reserve 之后超出预留量，容量仍按增长因子从当前值翻倍，不会退回按需精确分配。shrink_to_fit 是非绑定请求，标准只要求「不增加容量」。

10.3 高级（体现深度）

  1. 高级教科书说链表中间插入是 O(1)、vector 是 O(n)，为什么实测常常 vector 快 5–10 倍？

    因为渐进分析基于 RAM 模型，假设每次内存访问代价相同。真实机器上 L1 命中约 1 ns、主存约 100 ns，差两个数量级——「访问一个内存单元」这个被算作 O(1) 的操作内部有 100 倍浮动。

    ① O(1) 的前提没成立
    list 的 O(1) 插入前提是你已经持有那个位置的迭代器。若需先找位置，那 O(n) 的指针追逐不但没省掉，还是最慢的一种 O(n)：每个节点一次 cache miss，且硬件预取完全失效（读完当前节点才知道下一个地址在哪）。
    ② 两个 O(n) 的常数差 16 倍以上
    vector 顺序访问每 64 字节 cache line 覆盖 16 个 int，miss 率 1/16，且预取器几乎全命中。list 每个节点一次 miss，miss 率约 1/1。
    ③ memmove 极快
    vector 的 O(n) 搬移是连续内存上的 SIMD 批量拷贝，带宽约 10 GB/s；而 list 每次插入还要一次 malloc，节点开销 24–32 字节 vs int 的 4 字节。
    list 真正的适用场景
    已持有迭代器 且 需要迭代器/引用在插删后保持有效 且 用得上 splice 常数时间拼接。典型是 LRU 缓存：哈希表存「key → list 迭代器」，移动到表头是真 O(1) 且不失效其他迭代器。
    正确的结论
    不是「渐进分析没用」，而是渐进分析决定 n 大时的量级（不可违抗），常数因子决定同量级内的胜负（可优化 10 倍）。先用渐进排除 O(n²)，再用测量优化常数。跳过第一步去调常数，是在给错误的算法抛光。
  2. 高级什么是势能法？用它证明 vector::push_back 的摊销 O(1)。它比聚合法强在哪？

    势能法定义一个函数 Φ 度量数据结构的「紧张程度」，把摊销代价定义为实际代价 + 势能变化：

    摊销代价 = 实际代价 + Φ(after) − Φ(before) 若 Φ(初始)=0 且 Φ(任何时刻) ≥ 0，则 Σ摊销 = Σ实际 + Φ(末) − Φ(初) ≥ Σ实际 → 合法上界

    对 vector 取 Φ = 2·size − capacity（刚扩容后 size=capacity/2 时 Φ=0，写满时 Φ=capacity）：

    不扩容
    实际代价 1；size+1 使 Φ 增加 2 → 摊销 = 1+2 = 3。
    触发扩容
    size=capacity=c。实际代价 = c 次搬移 + 1 次写入 = c+1。扩容后 capacity=2c、size=c+1，新 Φ = 2(c+1)−2c = 2；旧 Φ = 2c−c = c。ΔΦ = 2−c。摊销 = (c+1)+(2−c) = 3。

    两种情况都是常数，故摊销 O(1)。Φ 的作用是把贵操作的代价提前存起来，贵操作发生时释放势能正好抵消。

    比聚合法强在哪
    聚合法要求你能算出整个序列的总代价闭式解，只适用于操作模式规整的情况。势能法是局部论证——只需对每种操作单独验证一个不等式，不必知道操作序列长什么样。所以它能处理操作交错、类型多样的结构：并查集的 α(n)、斐波那契堆的 O(1) 摊销 decrease-key、splay 树的 O(log n) 摊销，都只能用势能法证。代价是找到合适的 Φ 是全部难点，没有机械方法。
  3. 高级为什么线上系统看 p99 而不是均值？这对算法与数据结构选型有什么具体影响？

    因为请求扇出会放大尾延迟。一个用户请求并行调用 n 个下游并等全部返回时，用户可见延迟 = max(所有调用延迟)：

    P(至少一次超过 p99 阈值) = 1 − 0.99^n n=10 → 9.6% n=100 → 63.4% n=1000 → 99.996%

    也就是说，扇出 100 次时，大多数用户请求都会撞上至少一个 p99 慢响应。均值再漂亮也没用。

    对选型的四条具体影响：

    预分配
    启动时 reserve 到峰值，把摊销 O(1) 变成最坏 O(1)。摊销 O(1) 在均值上完美，但那次 O(n) 扩容落在哪个请求上，那个请求就是 p99。
    宁要稳定 O(log n)
    很多实时系统用平衡树而非哈希表：红黑树每次查找都是稳定的 log n，哈希表 rehash 时会突然长停顿。可预测性有时比平均速度更值钱。
    分摊贵操作
    把一次长停顿切成很多次短停顿：Redis 的增量式 rehash（每次操作搬几个 bucket）、分代 GC、分批 compaction。
    消除不可预测的分配
    对象池 / arena / 固定容量环形缓冲区，让运行期零 malloc。malloc 本身的尾延迟就不受控。
    再往上一层
    算法层面压不下去时，靠架构：对冲请求（hedged request，等到 p95 还没回就向副本再发一份，取先到的）能把扇出场景的 p99 显著拉低，代价是约 5% 的额外负载。这是「用吞吐换延迟」的典型交易。
  4. 高级你负责的服务里有个需求被判定为 NP-hard，接下来怎么做？

    NP-hard 的工程价值是止损信号：停止寻找精确多项式算法。但在换算法之前，先做一件更重要的事。

    ① 先质疑需求
    很多 NP-hard 是把业务约束抽象过头的结果。「给 1000 个任务排最优调度」是 NP-hard，但业务上往往只要「95% 任务在 SLA 内 + 最坏不超过 2 倍」——那就变成一个贪心能解的问题。动手找算法之前，先确认真的需要最优解。
    ② 量一量真实输入规模
    NP-hard 说的是最坏情形随 n 增长的行为。如果生产数据里 n 常年 ≤ 30，分支限界或 ILP 求解器几毫秒就返回最优解，那这个「NP-hard」在工程上根本不是问题。先看数据，再谈复杂度类。

    确认必须放弃精确解后，按「保证强度」排序的五条出路：

    策略保证实例
    近似算法有界近似比顶点覆盖 2-近似、集合覆盖 ln n-近似
    限定参数（FPT）k 小时精确O(f(k)·poly(n))，树宽有界的图
    精确 + 剪枝最优解，时间不保证分支限界、ILP（Gurobi/CBC）、SAT 求解器
    启发式无保证模拟退火、遗传算法、贪心 + 局部搜索
    松弛改问题不再是原问题整数规划 → LP 松弛后取整
    选型的判断标准
    问「解差一点的代价是多少」。结果要对外承诺（计费、合规、资源配额）→ 用近似算法，因为你需要一个能写进文档的界。结果只影响内部效率（缓存预热顺序、任务打包）→ 启发式够用，把精力花在监控实际解质量上。离线批处理、有几小时窗口→ 直接上 ILP 求解器，通常能拿到最优或近最优，而且比自己写启发式省事得多。
    别掉进的坑
    自己从零写启发式（尤其是遗传算法这类）往往打不过成熟求解器，还留下无人能维护的代码。先试通用求解器，打不过再自己写。
