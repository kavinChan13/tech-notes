为什么一个「已经被库解决」的问题值得学透

实际工作里你几乎永远该写 std::sort，不会手写快排。但排序值得单独学一章，理由不是「以后要用」，而是它把几乎所有通用算法技巧都装在一个足够小的问题里：

学排序像学做菜时先练几道基础菜。没人指望你以后天天做番茄炒蛋——但控火、调味、下锅顺序这些能力是在这几道菜里练出来的，后面做什么都用得上。

02

三个 O(n²)

其中两个只有教学价值，第三个是工业级实现的一部分

2.1 冒泡与选择

冒泡排序：稳定，但一无是处
void bubble_sort(int* a, int n) {
    for (int i = 0; i < n - 1; ++i) {
        bool swapped = false;
        for (int j = 0; j < n - 1 - i; ++j)
            if (a[j] > a[j + 1]) {
                std::swap(a[j], a[j + 1]);
                swapped = true;
            }
        if (!swapped) break;   // 已有序，提前退出
    }
}
// 最坏/平均 Θ(n²)，最好 Θ(n)
// 交换次数 = 逆序对数量（每次交换消掉恰好 1 个）
选择排序：不稳定，但交换最少
void selection_sort(int* a, int n) {
    for (int i = 0; i < n - 1; ++i) {
        int m = i;
        for (int j = i + 1; j < n; ++j)
            if (a[j] < a[m]) m = j;
        std::swap(a[i], a[m]);
    }
}
// 任何输入都是 Θ(n²) 次比较（不自适应）
// 但只做 n-1 次交换 ← 唯一优点

两条值得记住的性质：

  • 冒泡的交换次数恰好等于逆序对数量——每次相邻交换只能消掉一个逆序对。这给了逆序对一个物理意义：它是「把数组排好所需的最少相邻交换次数」。
  • 选择排序的交换次数是 O(n)，比较次数固定 Θ(n²)。所以当「元素极大、移动极贵，而比较极便宜」时它反而有意义——比如排序一堆几 MB 的结构体且没法用索引间接排序。这个场景很罕见，但它解释了为什么这个看似最差的算法还活着。
选择排序不稳定：[2a, 2b, 1] 第一轮会把 1 和 2a 交换，得到 [1, 2b, 2a]，两个 2 的相对顺序反了。想让它稳定就得改成「插入」而不是「交换」，那就变成插入排序了。

2.2 插入排序凭什么最快

插入排序在渐进上和冒泡一样是 Θ(n²)，但它是唯一被写进工业级排序实现的 O(n²) 算法。libstdc++ 的 std::sort、Java 的 Arrays.sort、Python 的 TimSort 全都在小区间用它。

void insertion_sort(int* a, int n) {
    for (int i = 1; i < n; ++i) {
        int key = a[i];
        int j = i - 1;
        while (j >= 0 && a[j] > key) {   // > 而不是 >= → 稳定
            a[j + 1] = a[j];             // 后移而非交换：写 1 次而不是 3 次
            --j;
        }
        a[j + 1] = key;
    }
}
优点为什么对比冒泡
自适应近乎有序时内层几乎不动 → Θ(n + 逆序对数)冒泡也自适应，但常数大
写操作少后移（1 次赋值）而非交换（3 次赋值）冒泡每次都是完整交换
分支可预测内层循环通常连续「不进入」或连续「进入」冒泡的比较结果更随机
顺序访问只碰相邻元素，全程 cache 命中相同
稳定 + 原地O(1) 额外空间相同
在线可以边接收边排冒泡不行
「近乎有序时是 Θ(n + I)」（I = 逆序对数）这个性质极其有用。它意味着插入排序对「已经排好、又插入了少量新元素」的数组几乎是线性的。这正是 introsort 的收尾策略能成立的原因：快排把数组分得「块内无序但块间有序」后，整体逆序对数已经被压到 O(n × cutoff)，最后一遍插入排序就是线性的。
注意内层条件是 a[j] > key 而不是 >=。用 >= 会在遇到相等元素时继续往前移，把相等元素的相对顺序反过来——丢掉稳定性，而且白做无用的移动。这个一字之差是插入排序最常见的实现 bug。
03

希尔排序：唯一的悬案

一个渐进复杂度至今没有定论的经典算法

插入排序慢，是因为它一次只能把元素往前挪一格——一个在末尾的最小元素要挪 n 步。希尔排序（Shell sort）的想法是：先做「跨大步」的插入排序，让元素快速接近最终位置，再逐步缩小步长。

void shell_sort(int* a, int n) {
    // Knuth 序列：1, 4, 13, 40, 121, ... (3h+1)
    int h = 1;
    while (h < n / 3) h = 3 * h + 1;

    for (; h >= 1; h /= 3) {
        // 对每个「间隔为 h 的子序列」做插入排序
        for (int i = h; i < n; ++i) {
            int key = a[i], j = i - h;
            while (j >= 0 && a[j] > key) { a[j + h] = a[j]; j -= h; }
            a[j + h] = key;
        }
    }
    // h == 1 的最后一轮就是普通插入排序，
    // 但此时数组已「几乎有序」→ 那一轮接近 Θ(n)
}
希尔排序像整理一屋子散落的书。你不会一本一本挪到最终位置（那是插入排序，走的路太长），而是先粗分：把书大致按「文学 / 技术 / 杂志」丢到三堆（大步长），再在每堆里细分，最后才在每个小分类里精确排序。

每一轮都让书离目标更近，所以最后那轮精确排序时，几乎不用走远路。
增量序列已证明的复杂度备注
Shell 原始：n/2, n/4, …, 1Θ(n²)最差的选择（偶数步长互不干涉）
Knuth：(3^k−1)/2 → 1, 4, 13, 40O(n^1.5)实现最简单，实用
Hibbard：2^k−1 → 1, 3, 7, 15Θ(n^1.5)已证明的紧界
SedgewickO(n^4/3)实测最好的几个之一
Pratt：2^i·3^jΘ(n log²n)理论最好，但序列太长、常数大
最优序列未知希尔排序的平均复杂度至今是开放问题
为什么原始序列（不断除以 2）最差：所有步长都是偶数，所以在最后一轮（h=1）之前，奇数位和偶数位的元素从未互相比较过。构造一个「小的全在奇数位、大的全在偶数位」的输入，前面所有轮次都白做，最后一轮退化成完整的插入排序。
好的增量序列必须让相邻步长互质（或至少不共享因子），这样不同轮次才能真正互相帮忙。

希尔排序今天几乎不用于生产（std::sort 全面更好），但它有两个不可替代的价值：① 它是教科书里唯一渐进复杂度未定论的经典算法，说明「算法分析」本身是有难度的学问；② 它原地、无递归、代码只有几行，在极度受限的嵌入式环境（几 KB RAM、不允许递归、不能带 std）里仍是不错的选择。

04

归并排序

唯一同时做到「稳定 + 最坏 O(n log n)」的比较排序

4.1 两种递归方向

自顶向下（递归）
void msort(int* a, int lo, int hi, int* buf) {
    if (hi - lo <= 32) {          // cutoff
        insertion_sort(a + lo, hi - lo);
        return;
    }
    int mid = lo + (hi - lo) / 2;
    msort(a, lo, mid, buf);
    msort(a, mid, hi, buf);
    if (a[mid - 1] <= a[mid]) return;  // 已首尾有序 → 跳过合并
    merge_into(a, lo, mid, hi, buf);
}
// 栈深 O(log n)；好写、好加 cutoff
自底向上（迭代）
void msort_bu(int* a, int n, int* buf) {
    for (int w = 1; w < n; w *= 2)
        for (int lo = 0; lo < n - w; lo += 2 * w)
            merge_into(a, lo, lo + w,
                       std::min(lo + 2 * w, n), buf);
}
// 零栈深；宽度 1→2→4→8... 逐层合并
// 链表归并排序的首选（不用随机访问找中点）
// 合并：两个已排序段 [lo,mid) 和 [mid,hi) → buf → 回写
void merge_into(int* a, int lo, int mid, int hi, int* buf) {
    int i = lo, j = mid, k = lo;
    while (i < mid && j < hi)
        buf[k++] = (a[j] < a[i]) ? a[j++] : a[i++];   // ← 等号在这里决定稳定性
    while (i < mid) buf[k++] = a[i++];
    while (j < hi)  buf[k++] = a[j++];
    std::copy(buf + lo, buf + hi, a + lo);
}

4.2 稳定性从哪里来

归并排序的稳定性完全由合并时那一个比较的方向决定：

✅ 稳定
buf[k++] = (a[j] < a[i]) ? a[j++] : a[i++];
// 相等时（!(a[j] < a[i]) 成立）取左边 a[i]
// → 原本在前面的元素仍在前面
❌ 不稳定
buf[k++] = (a[i] > a[j]) ? a[j++] : a[i++];
// 等价，仍稳定。真正会破坏稳定的是：
buf[k++] = (a[j] <= a[i]) ? a[j++] : a[i++];
// 相等时取右边 → 相对顺序被反转
稳定（stable）：排序后，比较意义上相等的元素保持它们在输入中的相对顺序。
为什么它重要：稳定性让多关键字排序可以分步做。想按「部门升序、部门内按薪资降序」排，只需先按薪资降序排一遍，再按部门升序稳定排一遍——第二遍不会打乱第一遍的结果。这在 SQL 的 ORDER BY a, b、表格 UI 的多列点击排序里是刚需。
不稳定排序想做到同样的事，必须写一个把所有关键字合起来比较的复合 comparator。

4.3 原地归并的代价

归并排序的最大缺点是需要 O(n) 临时空间。存在「原地归并」算法，但代价很高：

方案额外空间时间实用性
标准归并（全缓冲）O(n)Θ(n log n)默认选择
只缓冲一半O(n/2)Θ(n log n)常见优化，把短的一半拷出去
旋转法原地归并O(1)Θ(n log²n)慢一个 log
块归并（Block merge）O(1)Θ(n log n)常数极大，代码复杂
链表归并O(log n)（仅栈）Θ(n log n)链表排序的最优解

最后一行值得注意：链表归并排序不需要临时缓冲，因为合并只是重接指针，不需要移动数据。这就是为什么 std::list::sort 用的是归并排序而不是快排——链表没有随机访问，快排的分区做不了，而归并在链表上反而比在数组上更省空间。

std::stable_sort 的策略是：尝试分配 n 个元素的临时缓冲（get_temporary_buffer）。分配成功走标准归并 Θ(n log n)；分配失败则退化成原地归并，变成 Θ(n log²n)。这是标准里少见的「复杂度取决于能否分配内存」的接口——所以在内存紧张的环境里，stable_sort 会静默变慢一个 log 因子。

快速排序

平均最快，也最容易写错

5.1 分区三法

快排的全部工作在分区（partition）：选一个 pivot，把数组重排成「≤ pivot 的在左、≥ pivot 的在右」。三种主流写法有实质差异。

Lomuto：好写，但有陷阱
int partition_lomuto(int* a, int lo, int hi) {
    int pivot = a[hi - 1];   // 取末位
    int i = lo;
    for (int j = lo; j < hi - 1; ++j)
        if (a[j] < pivot) std::swap(a[i++], a[j]);
    std::swap(a[i], a[hi - 1]);
    return i;
}
// ❌ 全等数组 [5,5,5,...,5]：
//    a[j] < pivot 永假 → i 不动 → 划分成 (0, n-1)
//    → Θ(n²) 且栈深 O(n)
Hoare：交换少，全等也能均分
int partition_hoare(int* a, int lo, int hi) {
    int pivot = a[lo + (hi - lo) / 2];
    int i = lo - 1, j = hi;
    while (true) {
        do { ++i; } while (a[i] < pivot);
        do { --j; } while (a[j] > pivot);
        if (i >= j) return j;
        std::swap(a[i], a[j]);
    }
}
// ✅ 全等数组：i、j 各走一步就相遇 → 中点划分
// ⚠️ 返回的 j 不是 pivot 的最终位置！
//    递归必须写 [lo, j+1) 和 [j+1, hi)
Hoare 分区最容易写错的地方：它返回的下标不是「pivot 已就位」的位置，而只是一个分界点。所以递归必须是 qsort(lo, j+1); qsort(j+1, hi);——不能像 Lomuto 那样跳过中间那个元素写成 qsort(lo, j); qsort(j+1, hi);，那会丢掉一个元素。
另外 do{++i}while(a[i]<pivot) 的哨兵依赖：pivot 必须是数组里真实存在的元素（不能取平均值之类），否则指针可能越界。

三路分区（荷兰国旗问题）在有大量重复键时是唯一正确的选择：

// 返回 [lt, gt)：这段全等于 pivot，不需要再递归
std::pair<int, int> partition3(int* a, int lo, int hi) {
    int pivot = a[lo + (hi - lo) / 2];
    int lt = lo, i = lo, gt = hi;
    while (i < gt) {
        if (a[i] < pivot)      std::swap(a[lt++], a[i++]);
        else if (a[i] > pivot) std::swap(a[i], a[--gt]);
        else                   ++i;
    }
    return {lt, gt};
}
// 只有 k 个不同值时：Θ(n log k)。全等数组 → Θ(n)
什么时候必须用三路：按枚举字段排序（状态、类型、省份）、按布尔或小整数排序、按截断后的时间戳排序。这些场景里不同值可能只有几十个，而元素有百万个。Lomuto/两路会做大量无意义的递归，三路直接把复杂度从 Θ(n log n) 降到 Θ(n log k)。

5.2 pivot 怎么选

策略最坏输入代价评价
固定取首/末位已排序 / 倒序数组0绝不要用——最坏输入太常见
取中位下标特意构造的锯齿数组0比取端点好得多，但仍可构造
随机选无（攻击者无法预测）1 次随机数简单有效；期望 O(n log n)
三点取中（首/中/末）可构造（Bentley-McIlroy 反例）3 次比较实测最好的启发式
九点取中（ninther）更难构造~13 次比较大数组时用（pdqsort、BSD qsort）
median-of-medians无，最坏 O(n)常数 5–10×只作为兜底，不作主路径
随机化的真正作用：它不改善最坏复杂度（随机化快排的最坏仍是 Θ(n²)），而是把「最坏何时发生」从攻击者可控变成不可控。这是一个安全性质而非性能性质。
对比 introsort 的做法：它用一个深度计数器检测退化并切换算法，从而把最坏真正拉回 O(n log n)。两者可以叠加，libstdc++ 就是「三点取中 + 深度超限转堆排」。
2011 年前后有一批针对「三点取中」的算法复杂度攻击：攻击者构造特定的锯齿输入，使每次三点取中都选到极值，把服务端的排序拖成 O(n²)。
这类攻击的通用防御是把随机性引入到攻击者无法预测的地方——随机 pivot（种子来自进程启动时的熵）或 introsort 的深度检测。凡是「输入由外部提供 + 算法有可构造的最坏情形」，就要把它当安全问题处理。

5.3 退化与爆栈

朴素快排有两个独立的退化维度，很多人只记得第一个：

维度症状修法是否有确定性保证
时间退化到 Θ(n²)慢，但不崩随机化 pivot（概率性）
introsort 深度检测（确定性）		只有 introsort 有

// 两个修法同时上：栈深 ≤ log₂n，时间最坏 O(n log n)
void qsort_prod(int* a, int lo, int hi, int depth_limit) {
    while (hi - lo > 16) {
        if (depth_limit-- == 0) {          // ① 退化检测 → 堆排兜底
            heap_sort(a + lo, hi - lo);
            return;
        }
        int p = partition_hoare(a, lo, hi);
        // ② 只递归小半边，大半边转循环 → 栈深 ≤ log₂n
        if (p - lo < hi - p) { qsort_prod(a, lo, p + 1, depth_limit); lo = p + 1; }
        else                 { qsort_prod(a, p + 1, hi, depth_limit); hi = p + 1; }
    }
    // ③ 小区间留给最后统一的插入排序（见 §9.1）
}

第二个修法值得强调，因为它不依赖任何概率假设：无论 pivot 选得多差，「较短的那一半」必然不超过 n/2，所以栈深上界 log₂n 是确定性的。这一点比随机化 pivot 更可靠。

堆排序：理论完美、实测最慢

最坏 O(n log n) + O(1) 空间，却几乎不被单独使用

堆排序在纸面上看几乎无懈可击：最坏 Θ(n log n)（不像快排会退化）、真正 O(1) 额外空间（不像归并要缓冲）、无递归（不会爆栈）。

// 下沉：把 a[i] 沉到正确位置，堆大小为 n
void sift_down(int* a, int i, int n) {
    while (true) {
        int l = 2 * i + 1, r = l + 1, m = i;
        if (l < n && a[l] > a[m]) m = l;
        if (r < n && a[r] > a[m]) m = r;
        if (m == i) return;
        std::swap(a[i], a[m]);
        i = m;
    }
}

void heap_sort(int* a, int n) {
    // ① 建堆：自底向上，Θ(n) 而不是 Θ(n log n)
    for (int i = n / 2 - 1; i >= 0; --i) sift_down(a, i, n);
    // ② 逐个取最大值放到末尾
    for (int end = n - 1; end > 0; --end) {
        std::swap(a[0], a[end]);
        sift_down(a, 0, end);
    }
}
建堆是 Θ(n) 而不是 Θ(n log n)：自底向上建堆时，深度为 d 的节点最多下沉 (h−d) 层，而深度 d 上有 2^d 个节点。求和：
Σ 2^d · (h−d) = n · Σ (h−d)/2^(h−d) ≤ n · Σ k/2^k = 2n
关键在于大部分节点在底层，而底层节点几乎不用下沉。反之「逐个 push 建堆」是 Θ(n log n)，因为每次 sift-up 的都是最深的节点。这是面试高频陷阱题。

那它为什么实测最慢？

问题说明
cache 极不友好下沉时访问下标 i → 2i+1 → 4i+3 …，访问步长指数增长。数组一旦超出 L2，几乎每层都是一次 cache miss，而且预取器完全无法预测。
比较和交换次数多每次下沉要比较两个孩子再决定，实测比较次数约是快排的 2 倍。
分支不可预测「左孩子大还是右孩子大」基本是随机的 → 分支误预测率接近 50%。
不稳定交换堆顶和末尾会打乱相等元素的顺序。
不自适应已排序数组也要走完整流程（甚至更慢——升序数组是最坏的建堆输入）。
堆排序的访问模式像在一栋楼里找人，但每次只能问「你的两个下属是谁」。你从顶楼开始，每往下一层就要跑到楼里完全不同的位置（下标 2i+1 是指数跳跃），电梯（预取器）根本猜不到你下一站去哪。

快排和归并则像沿着走廊一间间走——虽然总路程可能更长，但一路顺着走，电梯提前在下一层等着你。这就是为什么「操作次数更少」不等于「跑得更快」。

所以堆排序的实际定位是：作为兜底算法，而不是主算法。introsort 用它做「快排退化时的降落伞」，正是因为它最坏有保证、原地、无递归——这三条恰好补齐了快排的短板。

堆本身（作为优先队列）用途极广：Dijkstra、Top-K、定时器、任务调度、合并 K 个有序流。堆排序只是堆的一个副产品。堆的完整展开（d-ary 堆、斐波那契堆、可删除堆、流式 Top-K、堆 vs 时间轮）在批次 2 的堆与 Top-K，STL 接口层面见 STL 容器深度剖析。

Ω(n log n) 下界证明

为什么比较排序不可能更快

7.1 决策树模型

要证明「不存在更快的算法」，必须先把「所有可能的算法」形式化。决策树模型做的就是这件事：把任何只靠比较来决定行为的排序算法，抽象成一棵二叉树。

比较排序的决策树：每个内部节点是一次比较 a[i] : a[j]，两条出边对应「<」和「≥」；每个叶子是一个最终的输出排列。算法在某个输入上的执行，就是从根走到某个叶子的一条路径；路径长度 = 该输入上的比较次数，树高 = 最坏情形比较次数。
这个模型覆盖了插入、归并、快排、堆排等所有「只用比较获取信息」的算法——它们的差别只是树的形状不同。

7.2 证明

证明只有三步，每一步都很短：

第一步 叶子数 ≥ n! 算法必须能输出全部 n! 种排列（否则存在某个输入它答错）。 每个叶子只对应一个固定的输出排列，故叶子数 ≥ n!。 第二步 高度为 h 的二叉树，叶子数 ≤ 2^h 所以 2^h ≥ n! → h ≥ log₂(n!) 第三步 用 Stirling 公式展开 log₂(n!) n! ≥ (n/e)^n log₂(n!) ≥ n·log₂(n/e) = n·log₂n − n·log₂e = Θ(n log n) ∴ 任何比较排序的最坏比较次数是 Ω(n log n)。∎
这个证明的结构像二十个问题猜谜。每个是/非问题最多把候选答案减半，所以要从 N 个候选里锁定唯一答案，至少要问 log₂N 次。

排序要区分的候选是 n! 种可能的排列，而每次比较只能问一个是/非问题——所以 log₂(n!) ≈ n log n 次比较是信息论下界，跟你多聪明无关。想突破它，只能改变「问问题」的方式：不问「谁大」，而是直接问「你的值是多少」——那就是 §8 的计数与基数排序。

三个必须理解的推论：

推论含义
归并排序是渐进最优的它的 Θ(n log n) 恰好达到下界，所以在比较模型内不可能有渐进更好的算法。优化只能在常数上做。
平均情形也是 Ω(n log n)同一个证明可以改成「叶子的平均深度 ≥ log₂(n!)」——不只是最坏。所以「平均更快」的比较排序也不存在。
下界只约束「比较模型」它不约束能直接用元素值做索引/位运算的算法。这不是漏洞，而是模型边界——计数、基数、桶排序正是从这里出去的。
同一个决策树论证还能给出别的下界。例如「查找有序数组中的元素」：n 个可能答案 + 每次比较三分（<、=、>）→ 至少 log₃n 次；若只用二路比较则至少 log₂n 次——这正是二分查找为什么不可能更快。「用决策树数叶子」是证明下界的通用套路，值得掌握。
08

突破下界

不比较，直接用值做下标

Ω(n log n) 只约束「只靠比较获取信息」的算法。如果元素的值本身能直接当下标用，我们就能跳过比较，做到线性。代价是对输入加了限制。

8.1 计数排序

// 前提：键是范围已知的小整数 [0, k)
void counting_sort(std::vector<int>& a, int k) {
    std::vector<int> cnt(k, 0);
    for (int x : a) ++cnt[x];              // ① 统计
    for (int i = 1; i < k; ++i)
        cnt[i] += cnt[i - 1];               // ② 前缀和 = 每个值的结束位置

    std::vector<int> out(a.size());
    for (int i = (int)a.size() - 1; i >= 0; --i)  // ③ 倒序回填 → 稳定
        out[--cnt[a[i]]] = a[i];
    a = std::move(out);
}
// Θ(n + k) 时间，Θ(n + k) 空间
第三步必须倒序遍历才能保证稳定性。正序遍历时，相同值的元素会按倒序填入。稳定性在这里不是可选项——基数排序完全依赖计数排序的稳定性（§8.2），写成正序会让整个基数排序出错。

适用边界很清楚：k = O(n) 时是 Θ(n)，k 远大于 n 时退化。给 100 万个 32 位整数排序，k = 2³² —— 计数数组要 16 GB，完全不可行。

8.2 基数排序

计数排序的问题是值域太大。基数排序的解法是把大值域拆成若干小值域，逐位做稳定的计数排序。

LSD（从低位到高位）MSD（从高位到低位）
做法对每一位做一遍稳定计数排序，共 d 遍按高位分桶，再递归排每个桶
依赖稳定性必须（否则前面的排序被打乱）不需要
能否提前结束否，d 遍全跑能（桶内只剩 1 个元素就停）
适合定长键（整数、定长字符串）变长键（字符串前缀差异大时极快）
实现难度简单，循环即可递归 + 大量小桶，常数大
 
// LSD 基数排序：8 位一组，32 位整数 → 4 遍
void radix_sort_u32(std::vector<uint32_t>& a) {
    constexpr int BITS = 8, K = 1 << BITS, MASK = K - 1;
    std::vector<uint32_t> buf(a.size());

    for (int shift = 0; shift < 32; shift += BITS) {
        int cnt[K] = {};
        for (uint32_t x : a) ++cnt[(x >> shift) & MASK];
        for (int i = 1; i < K; ++i) cnt[i] += cnt[i - 1];
        for (int i = (int)a.size() - 1; i >= 0; --i)
            buf[--cnt[(a[i] >> shift) & MASK]] = a[i];
        a.swap(buf);                        // 双缓冲，避免拷贝
    }
}
// Θ(d · (n + K))，这里 d=4, K=256 → 实测比 std::sort 快 2~3×
基数排序对有符号整数和浮点数需要额外处理，因为按位比较和数值比较不一致：
  • 有符号整数（补码）：负数的最高位是 1，按无符号排会排到正数后面。修法：把最高位翻转（x ^ 0x80000000）。
  • IEEE 754 浮点：正数可以直接按位比较（这是 IEEE 754 的设计），但负数的位模式是倒序的。修法：正数翻符号位，负数全位取反。
漏掉这一步的 bug 很隐蔽——正数测试全过，一上负数就错。

基数排序在真实工程里用得比想象中多：列式数据库的排序、GPU 排序（cub::DeviceRadixSort）、Spark 的 shuffle 有时用它、以及所有「按定长整数 key 排百万级记录」的场景。它是唯一能在实测上明确打败 std::sort 的通用排序。

// 前提：键在 [0,1) 上近似均匀分布
void bucket_sort(std::vector<double>& a) {
    size_t n = a.size();
    std::vector<std::vector<double>> b(n);
    for (double x : a) b[(size_t)(n * x)].push_back(x);   // 散到 n 个桶

}

工业级实现比教科书多了什么

9.1 introsort 三段结构

libstdc++ 的 std::sort 是 introsort（introspective sort，Musser 1997）：快排为主，堆排兜底，插入排序收尾。它的骨架只有两个函数：

// bits/stl_algo.h（简化并加注释）
template<typename It, typename Comp>
void __sort(It first, It last, Comp comp) {
    if (first == last) return;
    __introsort_loop(first, last, __lg(last - first) * 2, comp);  // ①②
    __final_insertion_sort(first, last, comp);                    // ③
}

constexpr int _S_threshold = 16;   // 小区间阈值

template<typename It, typename Size, typename Comp>
void __introsort_loop(It first, It last, Size depth_limit, Comp comp) {
    while (last - first > _S_threshold) {          // 小区间直接留给 ③
        if (depth_limit == 0) {                   // ② 退化 → 堆排兜底
            std::__partial_sort(first, last, last, comp);
            return;
        }
        --depth_limit;
        // ① 三点取中 + Hoare 风格分区
        It cut = std::__unguarded_partition_pivot(first, last, comp);
        __introsort_loop(cut, last, depth_limit, comp);   // 递归右半
        last = cut;                                    // 左半转循环 → 栈深有界
    }
}

三处实现细节值得单独说：

细节为什么这么做
深度上限 = 2⌊log₂n⌋理想划分需要 log₂n 层，留 2 倍余量。超过说明 pivot 选择在这个输入上系统性地差，不是运气问题。
最后一遍插入排序是全局的不是对每个小块单独排。因为块间已有序，全局插入排序的逆序对总数是 O(16n)，一遍下来就是 Θ(n)——而且顺序扫描，cache 全命中。分块排反而要多次进出。
unguarded_partition「无哨兵检查」的分区：因为三点取中保证了 pivot 不是最值，指针不会跑出边界，于是内层循环省掉了边界判断。这个优化在最内层循环里，收益显著。
这个「快路径求常数 + 廉价监控量 + 慢路径兜底最坏」的结构在系统软件里到处可见：std::nth_element 的 introselect、GMP 按位数切换乘法算法、JIT 的解释执行→热点编译、TCP 的快重传→超时重传、数据库的 nested-loop join→hash join 回退。识别出这个模式，你就能在自己的系统里复用它。

9.3 严格弱序：真实事故

std::sort 要求比较器满足严格弱序（strict weak ordering）。违反它不是「结果错」，而是未定义行为——实际表现通常是数组越界写入，然后在别的地方崩溃。

严格弱序的三条要求（记 comp(a,b) 为「a 排在 b 前面」）：
  • 反自反：comp(a, a) 必须为 false。
  • 非对称 + 传递：comp(a,b) 与 comp(b,a) 不能同真；comp(a,b) && comp(b,c) ⟹ comp(a,c)。
  • 「等价」的传递性：定义 equiv(a,b) 为 !comp(a,b) && !comp(b,a)，则 equiv 必须是等价关系（可传递）。
简单说：用 < 而不是 <=，并且保证多字段比较逻辑自洽。
❌ 四种真实见过的错法
// ① 用了 <= ：违反反自反
std::sort(v.begin(), v.end(),
    [](int a, int b){ return a <= b; });

// ② 多字段写漏：a,b 互相都「小于」
[](const P& a, const P& b) {
    if (a.x < b.x) return true;
    return a.y < b.y;      // ← x 更大时也可能返回 true
}

// ③ 浮点 NaN：所有比较都是 false
[](double a, double b){ return a < b; }
// 数据含 NaN → equiv 不可传递

// ④ 比较器有状态 / 依赖外部可变量
[&](int a, int b){ return score[a]++ < score[b]; };
✅ 正确写法
// ① 严格小于
std::sort(v.begin(), v.end(),
    [](int a, int b){ return a < b; });

// ② 多字段用 tie（自动正确）
[](const P& a, const P& b) {
    return std::tie(a.x, a.y) < std::tie(b.x, b.y);
}
// 或 C++20：return a <=> b < 0;（有 operator<=> 时）

// ③ 先过滤 / 归一化 NaN
std::erase_if(v, [](double x){ return std::isnan(x); });

// ④ 比较器必须无副作用、幂等
//   需要按外部键排序时，先物化成 pair 再排
为什么违反会导致越界而不只是「顺序错」：introsort 的 __unguarded_partition 内层循环省掉了边界检查——它依赖「pivot 不是最值，所以指针一定会在某个元素处停下」这个由严格弱序保证的前提。比较器一旦不自洽，while (comp(*i, pivot)) ++i; 就可能永远为真，指针一路冲出数组，往堆上乱写。

典型症状是：排序本身没报错，但几分钟后在完全无关的代码里崩溃——因为被踩坏的是别人的数据。这也是为什么这类 bug 极难定位。
怎么防：① Debug 构建下开 -D_GLIBCXX_DEBUG（libstdc++）或 _ITERATOR_DEBUG_LEVEL=2（MSVC），它们会主动校验比较器是否满足严格弱序并给出明确报错；② 多字段比较统一用 std::tie 或 C++20 的 operator<=>，不手写 if 链；③ 把「排序前检查是否含 NaN」加进处理浮点数据的流程；④ code review 时看到 <= 出现在比较器里，一律当 bug 处理。
相关的调试手段见 Sanitizers 实战。

10.1 外部排序与多路归并

要排序 1 TB 数据但只有 16 GB 内存时，所有内存排序算法都失效。外部排序的两阶段方案是所有大数据系统的基础：

三个关键工程点：

  • K 路归并用最小堆，每条记录 O(log K)。不要写成「两两归并」——那要 log₂K 遍，每遍都完整读写一次全量数据，I/O 是 K 路的 log₂K 倍。
  • K 不是越大越好。内存要在 K+1 个缓冲区之间分，K 太大则每路缓冲太小，磁盘从顺序读退化成随机读。经典结论：机械盘上 K 通常取几十到几百，NVMe 上可以更大。
  • 置换选择（replacement selection）能让 run 更长。用一个堆持续吞吐而不是「读满一批排一批」，期望能生成 2× 内存大小的 run，从而减少 run 数量。代价是实现复杂、且对已有序输入才有明显收益。
外部排序的思想在现代系统里无处不在：LSM-Tree 的 compaction 就是多路归并（存储与数据架构）、MapReduce/Spark 的 shuffle 是「map 端分块排序 + reduce 端归并」（Spark 内核）、数据库的 ORDER BY 在结果集超过 sort_buffer_size 时也走磁盘归并。

10.2 TimSort 与 pdqsort

教科书排序假设输入是均匀随机的。真实数据几乎从不是——日志按时间近似有序、数据库结果集部分有序、多个有序流拼接后是分段有序。两个现代排序算法就是冲着这一点设计的。

· 已排好的 v 追加了一小段新数据 → 对新段单独 sort，然后 std::inplace_merge（O(n) 或 O(n log n) 视缓冲而定），而不是整体重排。
· 多个有序序列合并 → std::merge 两两合并，或用最小堆做 K 路归并。
· 只是想知道「是否已有序」→ std::is_sorted 是 O(n)，比排一遍便宜得多。

并行排序的加速比通常远低于核数，原因有三：

瓶颈说明缓解
合并步串行并行归并的顶层那次 O(n) 合并是串行的，按 Amdahl 定律单独就限制了上限并行 merge：在一半里二分找另一半的划分点，把合并也切开
内存带宽饱和排序是 memory-bound 的。8 核同时搬数据，带宽先到顶，CPU 反而在等降低数据移动量（排索引而非排对象）、用基数排序（顺序访问友好）
负载不均并行快排的划分不均时，某个线程干得远多于别人任务窃取（TBB / Rayon 的模型）
在决定并行化之前先算一笔账：排 10⁷ 个 int，std::sort 单线程约 0.6 秒。如果整个任务只需要几百毫秒，并行的收益可能被线程启动和同步吃掉。而且并行版本的内存占用更高（每个任务一份缓冲）。
更划算的优化往往在别处：① 排「索引 + key」而不是排大对象（减少数据移动）；② key 是定长整数时改用基数排序，单线程就能快 2–3 倍；③ 只要 Top-K 就用 nth_element，把 O(n log n) 降成 O(n)。先换算法，再上并行。

  1. 基础什么是稳定排序？它为什么重要？哪些常见排序是稳定的？

    稳定指排序后，比较意义上相等的元素保持它们在输入中的相对顺序。

    为什么重要
    稳定性让多关键字排序可以分步做。要按「部门升序、部门内薪资降序」排，只需先按薪资降序排一遍，再按部门升序稳定排一遍——第二遍不打乱第一遍。这在 SQL 的 ORDER BY a, b、表格 UI 的多列点击排序里是刚需。不稳定排序想做同样的事，必须写一个把所有关键字合起来的复合 comparator。
    稳定不稳定
    冒泡、插入、归并、计数、基数、TimSort选择、希尔、快排、堆排、introsort
    一个记忆线索
    凡是会做「长距离交换」的排序基本都不稳定（选择排序把远处的最小值换过来、堆排把堆顶和末尾换、快排跨区交换）。只做相邻移动或按序追加的排序才稳定。
    C++ 里的细节
    std::sort 不保证稳定；std::stable_sort 保证，但它尝试分配 O(n) 缓冲——分配失败时退化成原地归并，复杂度从 O(n log n) 变成 O(n log²n)。这是标准里罕见的「复杂度取决于能否分配内存」的接口。
  2. 基础快排、归并、堆排的复杂度与空间各是多少？各自的适用场景？
    平均最坏额外空间稳定
    快排Θ(n log n)Θ(n²)O(log n) 栈否
    归并Θ(n log n)Θ(n log n)O(n) 缓冲是
    堆排Θ(n log n)Θ(n log n)O(1)否
    快排
    常数最小、cache 友好（顺序分区），是通用默认。缺点是最坏 O(n²) 且朴素实现栈深 O(n)——所以生产实现必须配 introsort 的深度兜底 + 「只递归小半边」。
    归并
    唯一同时做到稳定 + 最坏 O(n log n)。用在：需要稳定、链表排序（不需要临时缓冲，只重接指针，所以 std::list::sort 用它）、外部排序（多路归并是唯一可行方案）。
    堆排
    纸面完美（最坏有保证 + O(1) 空间 + 无递归），但实测最慢：下沉时访问下标 i→2i+1→4i+3，步长指数增长，cache miss 严重且预取器完全失效；分支「左孩子大还是右孩子大」基本随机，误预测率近 50%。所以它的定位是兜底算法——它的三个优点恰好补齐快排的三个短板。
  3. 基础为什么插入排序是唯一被写进工业级排序库的 O(n²) 算法？

    因为它在小规模和近乎有序两种情形下都极快，而这两种情形恰好是分治排序的收尾阶段会遇到的。

    自适应
    复杂度是 Θ(n + I)（I = 逆序对数），不是固定 Θ(n²)。已有序时内层一次都不进 → Θ(n)。
    写操作少
    用后移（1 次赋值）而不是交换（3 次赋值）。这是它比冒泡快好几倍的主因。
    分支可预测 + 全程 cache 命中
    只碰相邻元素，顺序访问；内层循环通常连续「进入」或连续「不进入」，分支预测器命中率高。
    原地 + 稳定 + 在线
    O(1) 空间，可以边接收数据边排。

    在 introsort 里的角色：快排把数组分到每块 ≤ 16 后停止，此时数组「块内无序、块间有序」，每个元素离最终位置不超过 16 → 总逆序对数 O(16n) → 最后一遍全局插入排序是 Θ(n)，而且顺序扫描 cache 全命中。

    实现细节
    内层条件必须是 a[j] > key 而不是 >=。用 >= 会在相等时继续前移，既丢掉稳定性，又白做无用移动。
  4. 基础计数排序 / 基数排序为什么能做到 O(n)？它们的前提是什么？

    因为它们不通过比较获取信息，而是直接用元素的值当下标。Ω(n log n) 下界只约束「只靠比较」的算法，所以这条路径不受它限制。

    计数排序 Θ(n+k)
    统计每个值出现几次 → 求前缀和得到每个值的结束位置 → 倒序回填（倒序才稳定）。前提：键是范围 [0,k) 的整数，且 k = O(n)。给 100 万个 32 位整数排序时 k=2³²，计数数组要 16 GB → 不可行。
    基数排序 Θ(d(n+K))
    把大值域拆成 d 组小值域（如 32 位拆成 4 组 8 位），逐位做稳定的计数排序。LSD（低位到高位）完全依赖每轮的稳定性——某一轮不稳定，前面几轮的结果就被打乱了。
    基数排序的隐藏坑
    有符号整数和浮点数不能直接按位排，因为位序和数值序不一致：补码负数最高位是 1（会排到正数后面），IEEE 754 负数的位模式是倒序的。修法是先做位变换（正数翻符号位、负数全位取反）。漏掉这步的 bug 很隐蔽——正数测试全过，一上负数就错。
    桶排序
    期望 Θ(n)，但依赖「键近似均匀分布」的假设，数据一偏斜就退化 Θ(n²)。它真正的价值不是当排序用，而是「先按范围分桶再各桶独立处理」这个模式——分布式系统的 range partition 就是它。

12.2 中级（区分熟练度）

  1. 中级证明比较排序的最坏比较次数是 Ω(n log n)。

    用决策树模型：把任何只靠比较获取信息的排序算法抽象成一棵二叉树——内部节点是一次比较 a[i]:a[j]，两条出边对应两个结果，叶子是最终输出的排列。树高 = 最坏比较次数。

    ① 叶子数 ≥ n! 算法必须能输出全部 n! 种排列，每个叶子只对应一个固定排列。 ② 高度 h 的二叉树叶子数 ≤ 2^h ⟹ 2^h ≥ n! ⟹ h ≥ log₂(n!) ③ Stirling：n! ≥ (n/e)^n log₂(n!) ≥ n·log₂(n/e) = n log₂n − n log₂e = Θ(n log n) ∎
    直觉版
    像「二十个问题」猜谜：每个是/非问题最多把候选减半，要从 n! 个候选里锁定一个，至少需要 log₂(n!) ≈ n log n 次。这是信息论下界，与算法多聪明无关。

    三个推论：

    归并排序渐进最优
    它的 Θ(n log n) 恰好达到下界 → 比较模型内不存在渐进更好的算法，优化只能在常数上做。
    平均情形也是 Ω(n log n)
    同一论证可改成「叶子平均深度 ≥ log₂(n!)」，所以「平均更快」的比较排序也不存在。
    下界只约束比较模型
    它不约束能用元素值直接做索引/位运算的算法——这不是漏洞，而是模型边界。计数、基数、桶排序正是从这里出去的。「用决策树数叶子」是证明下界的通用套路：同样能证明「有序数组查找至少 log₂n 次比较」。
  2. 中级快排的三种分区方式有什么区别？给一个全部元素相等的数组，各自表现如何？
    LomutoHoare三路（荷兰国旗）
    指针单向推进双向对撞三指针 lt / i / gt
    交换次数多约少一半中等
    全等数组Θ(n²) 且栈深 O(n)中点均分，Θ(n log n)Θ(n) 一遍搞定
    边界易错度低高中
    Lomuto 为什么在全等数组上崩
    条件 a[j] < pivot 永假 → i 一直不动 → 划分成 (0, n−1)，每次只切掉一个元素。时间 Θ(n²)、栈深 O(n)。
    Hoare 为什么不会
    它的两个指针在遇到「等于 pivot」时都会停下并交换，所以全等数组时 i、j 各走一步就相遇 → 中点划分。
    Hoare 的两个坑
    ① 返回的下标不是「pivot 已就位」的位置，只是分界点 → 递归必须写 [lo, j+1) 和 [j+1, hi)，不能像 Lomuto 那样跳过中间元素；② do{++i}while(a[i]<pivot) 依赖 pivot 是数组里真实存在的元素做哨兵，取平均值之类会越界。
    什么时候必须用三路
    按枚举字段排序（状态、类型、省份）、按布尔或小整数排、按截断时间戳排——这些场景不同值可能只有几十个而元素上百万。三路把复杂度从 Θ(n log n) 降到 Θ(n log k)（k = 不同值个数），因为等于 pivot 的那一段一次到位，不再进入递归。
  3. 中级逐行讲一遍 libstdc++ 的 std::sort 做了什么，以及为什么这样设计。

    它是 introsort（Musser 1997），三段结构：

    void __sort(It first, It last, Comp comp) {
    if (first == last) return;
    __introsort_loop(first, last, __lg(last-first) * 2, comp);  // ①②
    __final_insertion_sort(first, last, comp);                // ③
}
void __introsort_loop(It first, It last, Size depth_limit, Comp comp) {
    while (last - first > 16) {              // 小区间留给 ③
        if (depth_limit == 0)                 // ② 退化 → 堆排
            { __partial_sort(first, last, last, comp); return; }
        --depth_limit;
        It cut = __unguarded_partition_pivot(first, last, comp);  // ①
        __introsort_loop(cut, last, depth_limit, comp);  // 递归右半
        last = cut;                                    // 左半转循环
    }
}
    ① 快排主路径
    三点取中选 pivot + Hoare 风格分区。常数最小，平均最快。「递归一半 + 另一半转循环」把栈深压到 O(log n)。
    ② 堆排兜底
    深度上限 2⌊log₂n⌋（理想只需 log₂n，留 2 倍余量）。超限说明 pivot 选择在这个输入上系统性地差，不是运气 → 切堆排，把最坏真正拉回 O(n log n)。
    ③ 全局插入排序
    注意是对整个数组做一遍，不是逐块排。因为块间已有序、每个元素离最终位置 ≤16 → 逆序对总数 O(16n) → 这一遍是 Θ(n) 且顺序扫描 cache 全命中。分块排反而要多次进出。
    为什么这三段能凑成一个
    它们的短板互不重叠：快排常数小但最坏 O(n²)；堆排最坏有保证、原地、无递归但 cache 差；插排小规模无敌但 O(n²)。用一个 int 计数器就把三者串起来——平均拿到快排的常数，最坏拿到 O(n log n) 保证。
    这个「快路径求常数 + 廉价监控量 + 慢路径兜底」的模式在系统软件里到处可见：nth_element 的 introselect、GMP 按位数切换乘法、JIT 的解释→热点编译、TCP 快重传→超时重传、DB 的 nested-loop→hash join 回退。
    还有一处细节
    unguarded_partition 是「无哨兵检查」的分区：三点取中保证 pivot 不是最值，指针一定会停下，于是内层循环省掉了边界判断。这在最内层循环里收益显著——但它也是下一题那个 UB 会导致越界的原因。
  4. 中级要从 10⁷ 条记录里取 Top 100，你会怎么做？为什么不直接 sort？

    sort 再取前 100 是 O(n log n)，白排了 999 万条不需要的记录。三个更好的方案：

    方案一 · nth_element + sort（最快，O(n)）
    std::nth_element(v.begin(), v.begin()+100, v.end(), cmp);  // O(n)
std::sort(v.begin(), v.begin()+100, cmp);                 // O(100 log 100)
    总共 O(n)。n=10⁷ 时比 sort 快 20 倍以上。前提是数据全在内存且可以被打乱顺序。
    方案二 · partial_sort（O(n log k)）
    std::partial_sort(v.begin(), v.begin()+100, v.end())。比方案一略慢（多了堆的 log k），但一步到位且前 100 直接有序。
    方案三 · 大小为 k 的最小堆（O(n log k)，空间 O(k)）
    唯一能处理流式数据 / 数据不能全装进内存的方案：维护一个 size=100 的最小堆，新元素比堆顶大就替换堆顶。空间只要 O(k)。
    std::priority_queue<T, std::vector<T>, std::greater<>> pq;
for (auto& x : stream) {
    if (pq.size() < 100) pq.push(x);
    else if (x > pq.top()) { pq.pop(); pq.push(x); }
}
    选型判据
    数据全在内存、可打乱 → nth_element（O(n) 最快）。流式 / 内存装不下 / 分布式各分片先出局部 Top-K → 堆。k 接近 n → 直接 sort（此时 log k ≈ log n，没有优势了）。
    分布式场景还有一层：各分片各出 Top-K，再归并这些 Top-K——这是正确的（全局 Top-K 必然是某个分片的 Top-K），而且把网络传输从 O(n) 降到 O(分片数 × k)。

12.3 高级（体现深度）

  1. 高级线上服务有个偶发崩溃，最终定位到一个 std::sort 的比较器。这是怎么发生的，怎么根治？

    比较器违反了 std::sort 要求的严格弱序，这是未定义行为——而且它的表现通常不是「顺序错」，而是数组越界写入，然后在完全无关的地方崩溃。

    为什么会越界
    introsort 的 __unguarded_partition 内层循环省掉了边界检查，它依赖「pivot 不是最值，所以指针一定会在某个元素处停下」——这个前提由严格弱序保证。比较器不自洽时 while (comp(*i, pivot)) ++i; 可能永远为真，指针一路冲出数组往堆上乱写。
    典型症状：排序本身没报错，几分钟后在别的模块崩溃，因为被踩坏的是别人的数据。这也是它极难定位的原因。

    严格弱序的三条要求（记 comp(a,b) = 「a 排在 b 前」）：反自反（comp(a,a) 必为 false）、非对称且传递、以及「等价关系」!comp(a,b) && !comp(b,a) 必须可传递。

    四种真实见过的错法：

    ① 用了 <=
    return a <= b; 违反反自反。review 里看到比较器出现 <= 一律当 bug。
    ② 多字段 if 链写漏
    if (a.x < b.x) return true;
return a.y < b.y;   // ← a.x > b.x 时也可能返回 true → a<b 且 b<a
    正确写法：return std::tie(a.x, a.y) < std::tie(b.x, b.y); 或 C++20 的 <=>。
    ③ 数据含 NaN
    NaN 与任何值比较都是 false → 「等价」不可传递（a≡NaN、NaN≡b，但 a≢b）。排序前 erase_if(isnan) 或归一化。
    ④ 比较器有副作用 / 依赖可变外部状态
    [&](int a,int b){ return score[a]++ < score[b]; }——同一对元素两次比较结果不同。比较器必须无副作用且幂等。需要按外部键排序时先物化成 pair 再排。
    根治（不是修一处）
    ① Debug 构建开 -D_GLIBCXX_DEBUG（libstdc++）或 _ITERATOR_DEBUG_LEVEL=2（MSVC），它们会主动校验严格弱序并明确报错；② 全仓库搜比较器里的 <= 和手写 if 链，统一改成 std::tie / <=>；③ 把「排序前检查 NaN」写进浮点数据处理的规范；④ 把这条加进 review 清单——这类错误几乎从不只有一处，它是习惯问题。
  2. 高级要排序 1 TB 数据但只有 16 GB 内存，怎么做？关键的工程权衡在哪？

    外部排序，两阶段：

    阶段一 · 生成有序 run
    顺序读入，每读满约 8 GB（留一半内存给缓冲和输出）就 std::sort 一遍，写出一个有序文件。1 TB → 约 128 个 run。
    阶段二 · K 路归并
    为每个 run 开一个输入缓冲区，用一个 size=K 的最小堆存各路当前队首。pop 最小值写输出，再从那一路补一个进堆。每条记录 O(log K)，全量数据只需再读写一遍。

    关键权衡都在 K 上：

    别写成两两归并
    两两归并需要 log₂K 遍，每遍都完整读写一次全量数据 → I/O 是 K 路归并的 log₂K 倍。1 TB 数据下这是 7 倍的差距。
    K 也不是越大越好
    内存要在 K+1 个缓冲区之间分。K 太大 → 每路缓冲太小 → 磁盘从顺序读退化成随机读。机械盘上 K 通常取几十到几百，NVMe 上可以更大。这个值必须实测，因为它取决于存储介质的顺序/随机性能比。
    进一步的优化
    置换选择（replacement selection）：用一个持续吞吐的堆代替「读满一批排一批」，期望能生成 2× 内存大小的 run，从而把 run 数减半。代价是实现复杂，且对已部分有序的输入收益才明显。
    还有压缩 run（用 CPU 换 I/O，通常划算）和只排 key + 偏移量（记录很大时，避免搬运整条记录）。
    这个模式无处不在
    LSM-Tree 的 compaction 就是多路归并；MapReduce / Spark 的 shuffle 是「map 端分块排序 + reduce 端归并」；数据库的 ORDER BY 在结果集超过 sort_buffer_size 时也走磁盘归并。所以外部排序的核心不是算法（归并大家都会），而是让磁盘 I/O 尽可能顺序。
  3. 高级什么是自适应排序？TimSort 和 pdqsort 各解决了什么问题？在 C++ 里怎么吃到这个红利？

    自适应排序的复杂度随输入的「无序程度」变化，而不是只看 n。常用度量：逆序对数 I、天然有序段数 R。

    动机很实际：真实数据几乎从不是均匀随机的——日志按时间近似有序、数据库结果集部分有序、多个有序流拼接后是分段有序。而 std::sort 基本不自适应。

    TimSortpdqsort
    基础 / 稳定归并 / 稳定快排 / 不稳定
    核心思想识别天然有序段（run），用栈维护并按规则合并检测坏模式并主动打破
    特色优化galloping merge：一路远大于另一路时用指数搜索跳过重复键多 → 切三路；反复不均分 → 随机打乱；近乎有序 → partial insertion sort
    已有序输入Θ(n)Θ(n)
    额外空间O(n)O(log n)
    C++ 里怎么吃到红利
    不必换排序算法，而是主动利用已知的有序性：
    · 已排好的 v 追加了一小段 → 对新段单独 sort + std::inplace_merge，而不是整体重排；
    · 多个有序序列合并 → std::merge 或最小堆做 K 路归并；
    · 只想知道是否有序 → std::is_sorted 是 O(n)，比排一遍便宜太多。
    再往上一层
    「为真实数据分布而不是最坏情形优化」是个通用思路，不只在排序里：JIT 按运行时 profile 重编译热点、压缩算法先建字典再编码、数据库的自适应哈希索引、CPU 的分支预测器。
    它们的共同代价是需要一个「检测阶段」，而检测本身有开销、也可能被对抗性输入欺骗——pdqsort 遇到反复不均分时主动随机打乱，正是为了防这种对抗。
  4. 高级一个「排序 5000 万条日志按时间戳」的接口太慢，你的优化顺序是什么？

    先换算法和数据布局，最后才考虑并行。按收益从大到小：

    ① 先问需不需要全排序
    这是最大的一笔收益，而且经常被跳过。只要最近 N 条 → partial_sort（O(n log k)）；只要中位数或某个分位 → nth_element（O(n)）；只是要分页展示前 100 条 → nth_element + 局部 sort。问清需求经常直接省掉一个 log。
    ② 减少数据移动量
    如果记录很大（比如每条日志几百字节），不要排结构体本身——排 (timestamp, index) 的 pair，或者干脆排 index 数组。这把每次交换从「拷贝几百字节」变成「拷贝 8–16 字节」。
    注意间接排序会引入一次随机访问的重排，所以要实测：记录大到一定程度才划算。
    ③ 换基数排序
    时间戳是定长无符号整数——这是基数排序的理想输入。64 位时间戳按 8 位分 8 遍（或先归一化到相对秒数压到 32 位、4 遍）。单线程常能比 std::sort 快 2–3 倍，因为它顺序访问、无比较、无分支误预测。这是唯一能明确打败 std::sort 的通用排序。
    ④ 利用已有的有序性
    日志天然按时间近似有序。先 std::is_sorted_until 探一下有序前缀有多长——如果数据是「几个有序段拼起来的」（多机日志合并的典型形态），那正确做法是K 路归并（O(n log K)）而不是重新排序（O(n log n)）。
    ⑤ 最后才是并行
    并行排序的加速比通常远低于核数：合并步串行（Amdahl 上限）、内存带宽饱和（排序是 memory-bound，多核同时搬数据会先撞带宽墙）、负载不均。而且内存占用更高。先算一笔账：5×10⁷ 个 int 单线程 std::sort 约 3 秒——如果 ②③ 已经把它压到 1 秒内，并行可能不必要。
    还有一层：能不能不在这里排
    如果这个接口反复对同一批数据排序，真正的答案可能是把有序性前移：写入时就按时间分区落盘（时序数据库的做法）、或者建一个按时间戳的索引。「反复排同一批数据」是个架构信号，不是算法问题。参见 存储与数据架构 里时序数据库那一节。
