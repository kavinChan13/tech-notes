二分查找

二分是最简单的算法，也是最多人写不对的算法。原因是大家把它记成了「在有序数组里找一个数」这个特例，于是每换一种边界要求就得重新猜一遍 < 还是 <=。这一篇换一个视角：二分的本质是在单调谓词上找分界点；理解这一点后，一个模板就能覆盖全部边界，而且每次都能证明它对。

核心难度 ★★★☆☆ 面试出现率 极高 阅读时长 ~35 min 前置 复杂度与分析
循环不变式证明 四种边界统一模板 lower_bound 实现 二分答案 旋转数组 cache 友好布局
01

本质不是「找数」

而是在单调谓词上找那条分界线

教科书把二分定义成「在有序数组中查找目标值」。这个定义太窄，它是二分的一个特例，而且是最不重要的一个特例——真实工作里你会直接用 std::lower_bound。

二分查找的一般形式：给定一个在区间 [lo, hi) 上单调的布尔谓词 P（即存在某个分界点，之前全为 false、之后全为 true），用 O(log n) 次求值找到第一个使 P 为真的位置。

「有序数组找目标值」只是取 P(i) = (a[i] >= target) 的情形。而只要你能构造出一个单调谓词，二分就适用——数组不必存在，甚至答案不必是下标。
二分像 git bisect。你有 500 个提交，某个提交引入了 bug。谓词是「这个提交上 bug 存在吗」——它是单调的（bug 一旦引入就一直存在），所以你只需 9 次编译测试就能定位到那一个提交，而不是试 500 次。

注意这里没有「有序数组」也没有「目标值」：提交历史不是排好序的数字，你要找的也不是某个值，而是状态从「好」翻转到「坏」的那个位置。这才是二分的真面目。

也顺带说明了二分的失效条件：如果 bug 是时好时坏的（flaky），谓词不单调，git bisect 就会给出错误答案——它不会报错，只是安静地骗你。

1.1 与其他章节的关系

  • 复杂度与分析 —— O(log n) 的来源，以及为什么 log n 在工程规模内是小常数
  • 排序全景 —— 二分的前置条件由排序提供；决策树论证也给出了二分的下界
  • 递归与分治 —— 二分是「只有一个子问题」的退化分治
  • STL 算法库 —— lower_bound / upper_bound / equal_range / binary_search
  • 存储与数据架构 —— B+ 树、跳表、LSM 里二分的真实用途
02

为什么大家都写错

三行代码里有四个能出错的地方

2.1 mid 溢出

这是二分最著名的 bug。2006 年 Joshua Bloch 在 Google 博客上披露：JDK 的 Arrays.binarySearch 带着这个 bug 活了九年，而它照抄自 Bentley 的《Programming Pearls》——那本书里的版本也错了二十年。

❌ 有符号整数溢出 = UB
int mid = (lo + hi) / 2;

// lo = hi = 2×10⁹ 时：
// lo + hi = 4×10⁹ > INT_MAX (≈2.1×10⁹)
// → 有符号溢出是 UB，实际常得到负数
// → a[负数] 越界读
✅ 三种正确写法
int mid = lo + (hi - lo) / 2;      // 最通用

int mid = (int)(((unsigned)lo + hi) >> 1);  // 无符号，快

// 指针/迭代器版（不能相加，只能相减）
It mid = lo + (hi - lo) / 2;
对指针和迭代器来说这不是「防御性编程」而是必须：ptr1 + ptr2 在 C++ 里根本不合法（指针相加无定义）。所以 lo + (hi - lo) / 2 是唯一写法，这也解释了为什么 STL 的实现长这样。

另一个容易忽略的点：(hi - lo) / 2 对负数会向零取整而不是向下取整。所以在处理可能为负的下标范围（或者用 >> 1 与 / 2 混用）时要格外小心——-3 / 2 == -1 但 -3 >> 1 == -2。

2.2 死循环的三种成因

死循环几乎总是「区间没有严格缩小」造成的。三种典型写法：

写法为什么死循环触发条件
while (lo < hi) + lo = midmid 向下取整，当 hi == lo+1 时 mid == lo，赋值后 lo 没变区间剩 2 个元素
while (lo <= hi) + hi = mid同理，hi 不动区间剩 1–2 个元素
混用闭区间和半开区间初始 hi = n 但循环条件写 lo <= hi → 会访问 a[n]目标大于所有元素
记住这条规律就能避开全部死循环：mid 向下取整时，hi = mid 总是安全的（因为 mid < hi 恒成立），而 lo = mid 不安全（mid 可能等于 lo），必须写成 lo = mid + 1。
如果某道题的逻辑确实需要 lo = mid，那就把 mid 改成向上取整：mid = lo + (hi - lo + 1) / 2，此时 mid > lo 恒成立，lo = mid 变安全、而 hi = mid 变不安全。取整方向和赋值方式必须配对。
03

用不变式一次写对

不靠试错，靠证明

3.1 半开区间 + 不变式

下面这个模板是本文的核心。它有一个明确的循环不变式，所有边界行为都能从不变式推出来，不需要记也不需要猜。

// 在 [0, n) 上找「第一个使 P 为真」的下标；全为假则返回 n
template <class Pred>
int lower_bound_by(int n, Pred P) {
    int lo = 0, hi = n;
    // ┌─ 不变式 ────────────────────────────────────┐
    // │ 答案 ∈ [lo, hi]                              │
    // │ 即：∀ i < lo, P(i) 为假                       │
    // │     ∀ i ≥ hi, P(i) 为真（若 i < n）            │
    // └─────────────────────────────────────────────┘
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;   // lo ≤ mid < hi
        if (P(mid)) hi = mid;            // 答案 ≤ mid，收右界
        else         lo = mid + 1;        // 答案 > mid，收左界
    }
    return lo;                          // lo == hi，区间空 → lo 就是答案
}

用它做经典的「有序数组找目标」只需给出谓词：

// 第一个 ≥ target 的位置（等价于 std::lower_bound）
int pos = lower_bound_by(n, [&](int i){ return a[i] >= target; });

// 是否存在 target
bool found = (pos < n && a[pos] == target);

3.2 正确性与终止性证明

循环不变式的用法是「三步走」：证明它初始成立、每轮保持、退出时给出答案。

① 初始化 lo = 0, hi = n 「∀ i < 0，P(i) 假」空真；「∀ i ≥ n，P(i) 真」空真。✓ ② 保持 设进入循环前不变式成立，且 lo < hi。 由 mid = lo + (hi−lo)/2 得 lo ≤ mid < hi。 · P(mid) 真 → 由单调性，∀ i ≥ mid 皆真 → 答案 ≤ mid 置 hi = mid，「∀ i ≥ hi 为真」仍成立。✓ · P(mid) 假 → 由单调性，∀ i ≤ mid 皆假 → 答案 > mid 置 lo = mid+1，「∀ i < lo 为假」仍成立。✓ ③ 终止 循环退出时 lo == hi，区间 [lo, hi) 为空。 不变式给出：∀ i < lo 假，∀ i ≥ lo 真 ⟹ lo 就是第一个使 P 为真的下标。∎ ④ 必然终止 hi = mid 时新长度 = mid − lo < hi − lo（因 mid < hi） lo = mid+1 时新长度 = hi − mid − 1 < hi − lo 两种分支都严格缩短区间 ⟹ 至多 ⌈log₂n⌉ 轮后为空。∎
为什么半开区间 [lo, hi) 比闭区间 [lo, hi] 更好用：
  • 「空区间」有唯一表示：lo == hi。闭区间的空是 lo > hi，多一种状态就多一类边界错误。
  • 区间长度就是 hi - lo，不用 ±1。
  • hi = n 天然表示「没找到」，不需要额外的哨兵值或 -1。
  • 和 STL 的 [first, last) 约定一致，能直接换成迭代器。
这也是为什么 STL 全部用半开区间——它不是审美偏好，而是能消掉一整类 off-by-one 错误。
循环不变式像装修时贴的封条。你把房子分成「已验收（全假）」「待查（区间内）」「已验收（全真）」三块，每次只检查待查区中间的一间，然后把封条往里挪一格。

不变式就是那句写在封条上的话：「封条外面的都已经确认过了」。只要每次挪封条时这句话还成立，最后待查区变空时，两道封条之间的位置就是答案——你不需要回头复查任何一间房。
04

四种边界的统一模板

不要写四个函数，只改谓词

4.1 谓词化：只写 lower_bound

常见的四种查询，用同一个 lower_bound_by 加不同谓词就能全部覆盖：

要找什么谓词 P(i)返回值含义
第一个 ≥ x（lower_bound）a[i] >= x下标，或 n
第一个 > x（upper_bound）a[i] > x下标，或 n
最后一个 < xa[i] >= x返回值 − 1（可能为 −1）
最后一个 ≤ xa[i] > x返回值 − 1（可能为 −1）

关键观察：「最后一个满足 Q」= 「第一个满足 ¬Q」减一。所以只要把「找最后一个」翻译成「找第一个不满足的」，再减 1，就不需要另写一套代码。

// 四种边界，一个模板
auto first_ge = [&](int x){ return lower_bound_by(n, [&](int i){ return a[i] >= x; }); };
auto first_gt = [&](int x){ return lower_bound_by(n, [&](int i){ return a[i] >  x; }); };
auto last_lt  = [&](int x){ return first_ge(x) - 1; };   // 可能是 -1
auto last_le  = [&](int x){ return first_gt(x) - 1; };   // 可能是 -1

// 由此还能得到：
int count_eq = first_gt(x) - first_ge(x);        // x 出现次数
bool exists  = first_ge(x) < n && a[first_ge(x)] == x;
「最后一个」这一类必须检查返回 −1 的情况：当所有元素都 ≥ x 时，first_ge(x) 返回 0，减一得 −1，表示「不存在这样的元素」。忘记检查就是越界读 a[-1]。
这是「找最后一个」比「找第一个」更容易出错的唯一原因——不是逻辑更难，而是它多了一个需要显式处理的失败返回值。

4.2 四种边界互相表达

这四个函数不是独立的，理清它们的关系能少记很多东西：

一句话记牢：lower_bound 和 upper_bound 夹出的 [lo, up) 就是所有等于 x 的元素。所以：
  • up - lo = x 的出现次数（lo == up 就是不存在）
  • lo - 1 = 最后一个 < x
  • up - 1 = 最后一个 ≤ x
  • 插入 x 而保持有序：插在 lo（前插）或 up（后插，稳定）

05

std::lower_bound 的实现

以及为什么在 set 上不能用它

5.1 源码与迭代器类别

// bits/stl_algobase.h（简化）
template<typename It, typename T, typename Comp>
It lower_bound(It first, It last, const T& val, Comp comp) {
    auto len = std::distance(first, last);
    while (len > 0) {
        auto half = len >> 1;
        It mid = first;
        std::advance(mid, half);
        if (comp(*mid, val)) {          // *mid < val → 答案在右边
            first = ++mid;
            len -= half + 1;
        } else {
            len = half;                // 答案 ≤ mid
        }
    }
    return first;
}

注意它维护 len 而不是 last。这不是风格问题——它让实现对 ForwardIterator 也成立（advance 只需能往前走），而不要求随机访问。

迭代器类别比较次数推进（迭代器移动）次数总复杂度
RandomAccess（vector、数组）O(log n)O(log n)O(log n)
Bidirectional / Forward（list、set 的迭代器）O(log n)O(n)O(n)
这是标准里一处著名的「复杂度陷阱」：std::lower_bound 保证的是 O(log n) 次比较，而不是 O(log n) 的运行时间。在非随机访问迭代器上，每次 advance(mid, half) 都要一步步走，总推进次数是 O(n)。
所以在 std::list 上调用 lower_bound 能编译、结果正确，但比线性扫描还慢（同样 O(n) 的移动，外加 log n 次比较和更差的访问模式）。

5.2 set 上为什么要用成员函数

❌ 算法版：O(n)
std::set<int> s = {1, 3, 5, 7, 9};

auto it = std::lower_bound(s.begin(),
                             s.end(), 5);
// 能编译、结果对，但 O(n)：
// set 的迭代器是 Bidirectional，
// advance 要沿着红黑树中序一步步走
✅ 成员函数：O(log n)
std::set<int> s = {1, 3, 5, 7, 9};

auto it = s.lower_bound(5);
// 真正 O(log n)：直接沿红黑树
// 从根往下走，每层一次比较

// 同理：s.find / s.upper_bound
//       s.equal_range / s.count
通用规则：容器提供了同名成员函数时，一律用成员函数。因为成员函数能利用容器的内部结构（红黑树的树形导航、哈希表的桶定位），而算法版只能通过迭代器接口，拿不到这些信息。
这条规则不只适用于 lower_bound：set::find（O(log n)）vs std::find（O(n)）、string::find vs std::search、map::count vs std::count，都是同一类差异。

5.3 全家桶对照

接口返回比较次数典型用途
lower_bound(f,l,x)第一个 不小于 x 的位置O(log n)找插入点、找第一个 ≥ x
upper_bound(f,l,x)第一个 大于 x 的位置O(log n)找区间右端、稳定插入点
equal_range(f,l,x)pair：两者一起O(log n)取全部等于 x 的区间
binary_search(f,l,x)bool：是否存在O(log n)只判断存在性，拿不到位置
partition_point(f,l,P)第一个使 P 为假的位置O(log n)谓词版二分，最接近 §3 的模板
std::partition_point（C++11）是被严重低估的一个：它就是本文 §3 的 lower_bound_by，只是谓词方向相反（它找第一个使 P 为假的位置，因为它假设输入已按 P 划分成「真…真假…假」）。凡是「有序但不是按元素值排序」的二分——比如按某个派生字段、按外部条件——用 partition_point 比硬凑一个 comparator 干净得多。
注意它要求区间已按 P 划分（partitioned），这正是「谓词单调」的另一种说法。
binary_search 只返回 bool，拿不到位置。很多代码写成「先 binary_search 判断存在，再 lower_bound 取位置」——那是二分了两次。正确写法是直接 lower_bound 一次，然后检查 it != last && *it == x。
06

二分答案

把「求最优值」变成「判定可行性」

6.1 求最优 → 判定可行

这是二分最强大的用法，也是「二分不需要数组」的最好例证。模式是：

原问题 求满足某约束的最小 / 最大值 x* （直接求往往很难） 转化 定义判定函数 feasible(x) = 「x 这个取值可行吗」 若 feasible 关于 x 单调（可行的一侧连成一片）， 则在答案的取值范围上二分，找分界点。 代价 O(log(值域) × 一次判定的代价) 收益 判定通常比求最优容易得多——判定只要贪心扫一遍， 而求最优可能要 DP 甚至枚举。
像试衣服。要找「最小的能穿进去的尺码」，你不会去测量身体的 37 个维度再解方程（求最优），而是直接试：M 号能穿吗？能 → 试 S；S 能穿吗？不能 → 答案是 M。

之所以能这样试，是因为「能穿」这个性质是单调的：M 能穿，L、XL 一定也能穿。如果某家店的尺码乱标，L 号反而比 XL 号大——单调性坏了，二分就会给出错误答案。所以每次用二分答案，都必须先确认「单调」这件事，而不是假设它成立。

6.2 三个经典例题

例一 · 分割数组的最大值最小化：把数组分成 k 个连续子数组，使各子数组和的最大值最小。

// 判定：以 limit 为「每段和的上限」，能否分成 ≤ k 段？
bool feasible(const std::vector<int>& a, long long limit, int k) {
    int segs = 1;
    long long cur = 0;
    for (int x : a) {
        if (x > limit) return false;      // 单个元素就超了
        if (cur + x > limit) { ++segs; cur = x; }   // 贪心：塞不下就开新段
        else cur += x;
    }
    return segs <= k;
}

long long split_array(const std::vector<int>& a, int k) {
    long long lo = *std::max_element(a.begin(), a.end());   // 下界：最大单元素
    long long hi = std::accumulate(a.begin(), a.end(), 0LL) + 1; // 上界：全部和
    while (lo < hi) {
        long long mid = lo + (hi - lo) / 2;
        if (feasible(a, mid, k)) hi = mid;   // 同 §3 的模板，一字未改
        else                       lo = mid + 1;
    }
    return lo;
}
// O(n log(sum))：判定是 O(n) 的贪心，比直接 DP 的 O(n²k) 好得多

例二 · 在 D 天内运完包裹的最小船载重：判定「载重 cap 能否在 D 天内运完」，同样是 O(n) 贪心（能装就装，装不下就开新的一天）。

例三 · 切木材使能得到 k 段长度 ≥ L：判定「以长度 L 切，总共能得到多少段」，把每根木头除以 L 求和即可，O(n)。

题型二分的对象feasible 的实现单调方向
分割数组最大值最小每段和的上限贪心分段，数段数上限越大越可行
船运载重船的载重贪心装货，数天数载重越大越可行
木材切割每段长度求和 Σ len_i / L长度越小越可行
第 k 小的距离对距离双指针数「≤ d 的对数」距离越大越可行
最小化最大等待时间时间上限模拟或贪心上限越大越可行
爱吃香蕉的珂珂每小时吃的数量求和 Σ ⌈pile_i / speed⌉速度越大越可行
识别「这题该用二分答案」的三个信号：① 题目要求「最小化最大值」或「最大化最小值」；② 答案是一个数值且值域已知（或容易估上下界）；③ 给定一个候选答案，验证它可行比找到它容易。三个都命中就基本确定了。

6.3 单调性的证明义务

二分答案有个隐蔽的风险：它在单调性不成立时不会报错，只会安静地给出错误答案。所以每次用它都要付一笔「证明费」。

✅ 单调性可证
// 分割数组：limit 增大 → 每段能装更多
//         → 段数不增 → 仍 ≤ k
// 形式化：limit₁ < limit₂ ⟹
//   feasible(limit₁) ⟹ feasible(limit₂)
// 因为 limit₁ 的那个分割方案在
// limit₂ 下依然合法。 ✓

// 这种「原方案在放宽约束后仍合法」
// 的论证，是二分答案单调性的标准证法
❌ 看着能二分，其实不能
// 「选恰好 k 个元素使和最接近 T」
// 二分「和的取值」？
// → 「存在和 == v 的 k 元子集」
//   这个谓词不单调：
//   v=10 可行、v=11 不可行、v=12 可行
// → 二分会随机落到某个可行点
//   而且不会报错

// 正解：DP（子集和），不是二分
怎么防止「假单调」：① 写下形式化的蕴含式 feasible(x) ⟹ feasible(x')（x' 是更宽松的一侧）并给出一句话理由——最常用的理由是「原方案在放宽约束后仍然合法」；② 用暴力解对拍：小数据下把值域全部枚举一遍，打印 feasible 序列，肉眼确认它是 FFF...FTTT...T 而不是交替的；③ 警惕带「恰好」「正好等于」的题目——「恰好 k 个」「和正好等于 T」这类约束通常破坏单调性，因为放宽资源反而可能让「恰好」失效。
07

找回单调性

数组不全局有序时，二分还能用吗

7.1 旋转有序数组

把有序数组 [0,1,2,4,5,6,7] 在某点旋转，得到 [4,5,6,7,0,1,2]。它不全局有序，但任意一次划分后，至少有一半是有序的——这就是可以二分的理由。

// 无重复元素：O(log n)
int search_rotated(const std::vector<int>& a, int target) {
    int lo = 0, hi = (int)a.size() - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] == target) return mid;
        if (a[lo] <= a[mid]) {                 // 左半 [lo, mid] 有序
            if (a[lo] <= target && target < a[mid]) hi = mid - 1;
            else                                    lo = mid + 1;
        } else {                                // 右半 [mid, hi] 有序
            if (a[mid] < target && target <= a[hi]) lo = mid + 1;
            else                                    hi = mid - 1;
        }
    }
    return -1;
}

另一个更干净的思路：先二分找到旋转点，再在对应的有序段里做标准二分。找旋转点（即最小值位置）本身就是一个漂亮的谓词二分：

// 找最小值位置 = 找第一个满足 a[i] <= a[n-1] 的位置
// 谓词 P(i) = (a[i] <= a[n-1]) 在旋转数组上单调！
int find_pivot(const std::vector<int>& a) {
    int lo = 0, hi = (int)a.size() - 1;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] <= a[hi]) hi = mid;   // 和 §3 模板同一形状
        else                 lo = mid + 1;
    }
    return lo;
}
第二种写法体现了本文的中心思想：不要为每种变体重新设计二分，而要想办法构造出一个单调谓词，然后套同一个模板。「a[i] <= a[n-1]」在旋转数组上恰好是 FFF...FTTT...T 的形状（前段是旋转前的大值、后段是小值），所以模板一字不改就能用。
有重复元素时（[1,1,1,0,1,1,1]），a[lo] == a[mid] 让你无法判断哪半有序，只能 ++lo 逐个收缩，最坏退化到 O(n)。而且这个 O(n) 是不可改善的——考虑 [1,1,...,1,0,1,...,1]，那个 0 可能在任何位置，任何算法都必须最坏看遍所有元素。面试时能说出「这是信息论下界，不是实现不够好」是加分项。

7.2 山峰数组

山峰数组先严格递增后严格递减（如 [1,3,5,7,6,4,2]），要找峰顶。它整体不单调，但「相邻元素的比较结果」是单调的：

// 谓词 P(i) = (a[i] > a[i+1])  ← 「已经开始下降」
// 在山峰数组上：上升段全为 false，下降段全为 true → 单调 ✓
int peak_index(const std::vector<int>& a) {
    int lo = 0, hi = (int)a.size() - 1;   // hi 取 n-1：保证 mid+1 合法
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] > a[mid + 1]) hi = mid;   // 已下降 → 峰在左侧（含 mid）
        else                      lo = mid + 1;
    }
    return lo;
}
这个思路的一般化：原数组不单调时，试着找一个由数组导出的单调量。常见的导出量有：
  • a[i] > a[i+1]（是否开始下降）→ 山峰、局部极值
  • a[i] <= a[n-1]（是否已过旋转点）→ 旋转数组
  • a[i] - i（是否已出现缺失）→ 「找缺失的数」「找第 k 个缺失」
  • count(≤ x)（有多少个不超过 x）→ 第 k 小、中位数类问题
最后一个尤其重要：「有多少个 ≤ x」关于 x 天然单调递增，所以任何「第 k 小」问题都可以试着二分答案。

7.3 矩阵与二维

行列都有序的矩阵（每行左→右递增，每列上→下递增）有个漂亮的 O(m+n) 解法，理解它也就理解了「什么时候二分不是最优」。

✅ 从右上角走：O(m+n)
bool search_matrix(const Matrix& m, int target) {
    int r = 0, c = m.cols - 1;   // 右上角
    while (r < m.rows && c >= 0) {
        if (m[r][c] == target) return true;
        if (m[r][c] > target) --c;   // 这一列全都太大
        else                  ++r;   // 这一行全都太小
    }
    return false;
}
// 右上角是唯一「右边更大、下边更大」的角
// → 每步能确定性地排除一整行或一整列
✅ 整体有序时可以真二分：O(log mn)
// 若矩阵「整体」有序（下一行首 > 上一行尾）
// 就是一个被折叠的一维有序数组
bool search_flat(const Matrix& m, int target) {
    int lo = 0, hi = m.rows * m.cols;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        int v = m[mid / m.cols][mid % m.cols];
        if (v >= target) hi = mid;
        else             lo = mid + 1;
    }
    return lo < m.rows * m.cols
        && m[lo / m.cols][lo % m.cols] == target;
}
左边的 O(m+n) 常优于「对每行二分」的 O(m log n)——当 m ≈ n 时前者是 O(n)、后者是 O(n log n)。这说明「能二分」不等于「该二分」：右上角走法每步排除一整行或一整列，信息利用率更高。
看到「行列有序矩阵」就条件反射写二分，是把工具当成了目的。先问「每一步能排除多少候选」，再决定用什么。
08

浮点二分

为什么固定迭代次数比 eps 更稳

❌ 用 eps 作为终止条件
while (hi - lo > 1e-9) {
    double mid = (lo + hi) / 2;
    if (ok(mid)) hi = mid; else lo = mid;
}
// 问题：
// ① 数值很大时（如 1e18），相邻 double
//    的间隔已远大于 1e-9 → 永远不满足 → 死循环
// ② eps 取多大依赖题目精度要求，容易
//    要么不够精确，要么白跑很多轮
✅ 固定迭代次数
for (int iter = 0; iter < 100; ++iter) {
    double mid = lo + (hi - lo) / 2;
    if (ok(mid)) hi = mid; else lo = mid;
}
// 每轮区间减半：100 轮后缩小 2⁻¹⁰⁰ ≈ 1e-30
// 早已超过 double 的 53 位有效精度（≈1e-16 相对）
// → 不可能死循环，且精度拉满
// 100 次浮点运算的开销可以忽略
为什么 100 轮足够：double 有 53 位有效二进制位，所以相对精度上限约 2⁻⁵³ ≈ 1.1×10⁻¹⁶。二分每轮把区间减半，大约 60 轮就已经到了 double 能表示的极限——再多轮，lo 和 hi 会变成相邻的浮点数甚至相等，区间无法再缩小。
取 100 轮是留足余量的保守选择；竞赛里常用 100，工程里 60–80 就够。关键是把循环次数变成一个与数值大小无关的常数。
坑症状修法
用 hi - lo > eps 且数值巨大死循环固定迭代次数
用 lo < hi（浮点）几乎必然死循环浮点不能用严格不等判终止
用绝对 eps 判「相等」大数上判不出，小数上过早判定用相对误差：fabs(a-b) <= eps * max(1, fabs(a))
输出精度不足答案对但被判错printf("%.10f") 或 setprecision(10)
值域上下界估错答案卡在边界上下界宁可放宽，多几轮不要紧
很多「浮点二分」的题其实可以整数化：把答案乘以 10^k 变成整数再二分（比如题目要求保留 4 位小数，就在 [0, ans_max * 10⁴] 上做整数二分）。这样既避免全部浮点陷阱，又能精确控制精度。能整数化就整数化——这是竞赛里的常规操作，工程上也同样适用（金额计算用「分」而不是浮点「元」是同一个道理）。

工程里的二分

从 git bisect 到 cache 友好的内存布局

9.1 git bisect

git bisect 是二分最日常的工程化身，也是「二分不需要数组」的最好例子。

# 已知 HEAD 有 bug，v1.2.0 没有
git bisect start
git bisect bad HEAD
git bisect good v1.2.0
# git 自动 checkout 中间那个提交，你测试后告知结果
git bisect good   # 或 bad
# ... 重复约 log₂(提交数) 次

# 全自动：写一个退出码表示好坏的脚本
git bisect run ./test.sh
# 500 个提交 → 约 9 次测试
二分的要素在 git bisect 里是什么
区间good 到 bad 之间的提交序列
谓词 P「这个提交上 bug 存在吗」
单调性前提bug 一旦引入就一直存在
一次判定的代价一次编译 + 一次测试（可能几分钟）
为什么值得判定很贵，所以把 500 次降到 9 次收益巨大
git bisect 会在单调性不成立时给出错误答案而不报错，三种常见情形：① bug 是 flaky 的（间歇性失败）→ 某次误判就把整个二分带偏；② 中间某些提交编译不过 → 要用 git bisect skip 标记，而不是随便报 good/bad；③ bug 被引入后又被临时修掉再被引入 → 谓词是 FTFT 形状，非单调。

这三条对应到一般的二分答案：判定函数必须确定（无随机性）、必须对所有输入有定义、且必须真的单调。三者缺一，二分就会安静地骗你。

9.2 B+ 树页内二分

数据库和文件系统的 B+ 树里，二分出现在两个层次上：

为什么要分成两层？因为两层的代价单位完全不同：

层次次数单次代价优化目标
树高（跨页）log_B(n)，B 是每页 key 数一次磁盘/SSD I/O，约 100 µs把 B 做大 → 树高尽量低
页内二分log₂B ≈ 8–10一次内存访问，约 100 ns次要，但页大了也不能忽略
这解释了 B+ 树为什么「又矮又胖」：把节点做成一个磁盘页大小（4–16 KB），每页能放几百个 key，于是 B ≈ 数百，log_B(10⁹) ≈ 3~4——十亿行数据只需 3–4 次 I/O 就能定位。
如果用二叉搜索树（B=2），log₂(10⁹) ≈ 30 → 30 次 I/O，慢一个数量级。B+ 树的全部智慧就是「用页内的廉价二分换掉昂贵的跨页跳转」。完整展开见 存储与数据架构。

二分在存储系统里还有几处身影：LSM-Tree 的 SSTable 用块索引 + 块内二分定位 key；跳表用多层链表模拟二分（每层跳过一半，本质是「链表上的二分」）；时序数据库按时间戳二分定位数据块；Parquet/ORC 列存用 min/max 统计做块级剪枝，再在块内二分。

9.3 cache 友好的布局

最后一个工程细节，它是「渐进相同、常数差数倍」的典型案例。标准二分在大数组上 cache 极不友好：

三种常见的优化方向：

手段思路代价 / 前提
分支消除用条件移动（cmov）代替分支：lo += (cond ? half+1 : 0)，避免 50% 的分支误预测需要编译器配合，可读性下降
eytzinger 布局按层序存放，前几层挤在同一 cache line只读索引；不能随时插入
B 树式扁平索引一个 cache line 放多个 key，用 SIMD 一次比较 8–16 个实现复杂；这正是 B+ 树的思路下移到 cache 层
插值查找数据近似均匀时按值估算位置，期望 O(log log n)分布不均时退化到 O(n)
预取提前 __builtin_prefetch 两个可能的下一步浪费一半带宽换延迟
这些优化的适用范围很窄：只有在「数组远超 L3 + 查询极频繁 + 只读」时才值得。典型场景是数据库的只读索引、搜索引擎的倒排表、游戏引擎的静态资源表。
绝大多数业务代码里，std::lower_bound 已经足够，把精力花在这里是过早优化。判断标准很简单：这段二分在 profile 里占比超过 5% 了吗？相关的测量方法见 性能优化指南。

面试题集（12 道）

按难度分三段，先自测再对照

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础手写一个二分查找，并说明 mid 为什么不能写 (lo + hi) / 2。 
    // 找第一个 >= target 的下标；没有则返回 n
int lower_bound(const int* a, int n, int target) {
    int lo = 0, hi = n;                  // 半开区间 [lo, hi)
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;   // lo ≤ mid < hi
        if (a[mid] >= target) hi = mid;
        else                  lo = mid + 1;
    }
    return lo;
}
    溢出问题
    lo + hi 在两者都接近 INT_MAX/2 以上时会有符号整数溢出——这是 UB，实际常得到负数，然后 a[负数] 越界读。
    这个 bug 在 JDK 的 Arrays.binarySearch 里活了九年（2006 年 Joshua Bloch 披露），而它照抄自《Programming Pearls》——那本书里错了二十年。
    正确写法
    lo + (hi - lo) / 2（最通用）或 (int)(((unsigned)lo + hi) >> 1)。
    对指针和迭代器来说前者是唯一写法——ptr1 + ptr2 在 C++ 里根本不合法。这也是 STL 实现长这样的原因。
    为什么用半开区间
    「空区间」有唯一表示（lo == hi），区间长度就是 hi - lo，hi = n 天然表示「没找到」，而且和 STL 的 [first, last) 一致。它能消掉一整类 off-by-one 错误，不是审美偏好。
  2. 基础二分的死循环通常怎么产生？怎么从结构上避免？

    根因只有一个：某轮循环后区间没有严格缩小。

    最常见的一种
    mid 向下取整时，如果区间只剩 2 个元素（hi == lo+1），那么 mid == lo。此时写 lo = mid 等于没变 → 永远循环。
    记住这条配对规则
    mid 向下取整时（lo + (hi-lo)/2）：hi = mid 安全（mid < hi 恒成立），lo = mid 不安全，必须写 lo = mid + 1。
    如果逻辑确实需要 lo = mid，就把 mid 改成向上取整：lo + (hi - lo + 1) / 2，此时 mid > lo 恒成立，lo = mid 变安全而 hi = mid 变不安全。取整方向和赋值方式必须配对。
    另一类：区间约定混用
    初始 hi = n（半开）但循环条件写 lo <= hi（闭区间的写法）→ 会访问 a[n] 越界。一份代码里只用一种区间约定。
    结构上的根治
    写一个循环不变式并保证每轮都成立，终止性就是自动的推论：hi = mid 时新长度 mid - lo < hi - lo；lo = mid+1 时新长度 hi - mid - 1 < hi - lo。两个分支都严格缩短 ⟹ 至多 ⌈log₂n⌉ 轮必然退出。
  3. 基础lower_bound 和 upper_bound 的区别是什么？怎么用它们数出 x 出现了几次？
    返回谓词
    lower_bound(x)第一个 不小于 x（≥ x）的位置a[i] >= x
    upper_bound(x)第一个 大于 x（> x）的位置a[i] > x

    对 [1,3,5,5,5,7,9] 查 x=5：lower_bound=2、upper_bound=5。

    一句话记牢
    两者夹出的 [lo, up) 就是所有等于 x 的元素。所以：
    · 出现次数 = up - lo（等于 0 就是不存在）
    · 最后一个 < x 的位置 = lo - 1
    · 最后一个 ≤ x 的位置 = up - 1
    · equal_range 一次同时返回两者
    auto [lo, up] = std::equal_range(v.begin(), v.end(), x);
int count = up - lo;
bool exists = (lo != up);
    「最后一个」要检查 −1
    当所有元素都 ≥ x 时 lower_bound 返回 0，减一得 −1 → 表示不存在。忘了检查就是 a[-1] 越界。这是「找最后一个」比「找第一个」更易错的唯一原因——不是逻辑更难，而是多了一个要显式处理的失败返回值。
    别二分两次
    binary_search 只返回 bool，拿不到位置。「先 binary_search 判存在再 lower_bound 取位置」是二分了两次。直接 lower_bound 一次，然后查 it != last && *it == x。
  4. 基础二分查找的前提是什么？「数组必须有序」这个说法准确吗？

    不准确，它太窄了。真正的前提是：存在一个在区间上单调的布尔谓词——即存在某个分界点，之前全假、之后全真。

    「有序数组找目标值」只是取 P(i) = (a[i] >= target) 的特例。只要能构造出单调谓词，二分就适用——数组不必存在，答案也不必是下标。

    三个「不是有序数组」但能二分的例子：

    git bisect
    提交历史不是排好序的数字，找的也不是某个值，而是「状态从好翻转到坏」的位置。谓词是「这个提交上 bug 存在吗」，单调性来自「bug 一旦引入就一直存在」。
    二分答案
    「最小的能在 D 天内运完的船载重」——根本没有数组，二分的是答案的值域。谓词是 feasible(cap)。
    山峰数组
    数组本身不单调（先增后减），但导出量 a[i] > a[i+1]（「是否已开始下降」）单调。
    这也说明了失效条件
    谓词不单调时，二分不会报错，只会安静地给出错误答案。所以每次用二分都要先确认单调性，而不是假设它成立。git bisect 遇到 flaky test 就是这么被带偏的。

10.2 中级（区分熟练度）

  1. 中级写出二分的循环不变式，并用它证明算法的正确性与终止性。

    对 [lo, hi) 半开区间模板：

    不变式 答案 ∈ [lo, hi]，即 ∀ i < lo: P(i) 为假 ∀ i ≥ hi: P(i) 为真

    三步走：

    ① 初始化
    lo=0, hi=n。「∀ i < 0 假」和「∀ i ≥ n 真」都是空真（vacuously true）。✓
    ② 保持
    由 mid = lo + (hi-lo)/2 得 lo ≤ mid < hi。
    · P(mid) 真 → 由单调性 ∀ i ≥ mid 皆真 → 答案 ≤ mid → 置 hi = mid，不变式保持。
    · P(mid) 假 → 由单调性 ∀ i ≤ mid 皆假 → 答案 > mid → 置 lo = mid+1，不变式保持。✓
    ③ 终止时给出答案
    退出时 lo == hi，不变式给出「∀ i < lo 假、∀ i ≥ lo 真」⟹ lo 就是第一个使 P 为真的下标。∎
    ④ 必然终止
    hi = mid 时新长度 mid − lo < hi − lo（因 mid < hi）；lo = mid+1 时新长度 hi − mid − 1 < hi − lo。两分支都严格缩短 ⟹ 至多 ⌈log₂n⌉ 轮。∎
    这个方法的价值
    写二分时不靠试错试出 < 还是 <=，而是先写下不变式，让边界从不变式里推出来。这样每次都能证明它对，而不是「跑几个用例看着没错」。
    循环不变式是验证任何循环的通用工具，不只用于二分——它也是 Dijkstra、并查集、Floyd 等算法正确性证明的骨架。
  2. 中级什么是「二分答案」？举一道题说明怎么把「求最优」变成「判定可行」。

    直接求最优值 x* 往往很难；但给定一个候选值判断它可行不可行，常常容易得多。如果 feasible(x) 关于 x 单调，就在答案的值域上二分找分界点。

    代价：O(log(值域) × 一次判定的代价) 收益：判定通常只要贪心扫一遍，而求最优可能要 DP 甚至枚举

    例 · 分割数组的最大值最小化：把数组分成 k 个连续子数组，使各段和的最大值最小。

    // 判定：以 limit 为「每段和上限」，能否分成 ≤ k 段？→ 贪心 O(n)
bool feasible(const std::vector<int>& a, long long limit, int k) {
    int segs = 1; long long cur = 0;
    for (int x : a) {
        if (x > limit) return false;
        if (cur + x > limit) { ++segs; cur = x; } else cur += x;
    }
    return segs <= k;
}
// 值域：[max(a), sum(a)]，套 §3 模板一字不改 → O(n log(sum))
// 对比直接 DP 的 O(n²k)
    三个识别信号
    ① 题目说「最小化最大值」或「最大化最小值」；② 答案是数值且值域已知/易估；③ 验证一个候选答案比找到它容易。三个都命中就基本确定。
    同类题
    船运载重（D 天运完）、木材切割（得 k 段长 ≥ L）、爱吃香蕉的珂珂（H 小时吃完）、第 k 小的距离对、最小化最大等待时间。判定函数几乎总是「贪心扫一遍 + 计数」。
    还有一类：二分「有多少个 ≤ x」
    「有多少个元素 ≤ x」关于 x 天然单调递增，所以任何「第 k 小」问题都可以试着二分答案 + 数个数。这在「有序矩阵第 k 小」「第 k 小的距离对」里是标准解法。
  3. 中级在旋转有序数组里查找一个数怎么做？有重复元素时会怎样？

    数组不全局有序，但任意一次划分后至少有一半是有序的——这就是可二分的依据。

    解法一 · 判断哪半有序：比较 a[lo] 与 a[mid]，然后在有序的那半里判断 target 是否落在其中。

    if (a[lo] <= a[mid]) {                     // 左半有序
    if (a[lo] <= target && target < a[mid]) hi = mid - 1;
    else                                    lo = mid + 1;
} else {                                    // 右半有序
    if (a[mid] < target && target <= a[hi]) lo = mid + 1;
    else                                    hi = mid - 1;
}
    解法二（更推荐）· 先找旋转点
    把它变成一个标准的谓词二分：谓词 P(i) = (a[i] <= a[n-1]) 在旋转数组上恰好单调（前段是旋转前的大值 → 假，后段是小值 → 真）。
    while (lo < hi) {
    int mid = lo + (hi - lo) / 2;
    if (a[mid] <= a[hi]) hi = mid; else lo = mid + 1;
}   // lo = 最小值下标
    找到旋转点后在对应的有序段做标准二分。好处是模板一字不改——这正是「构造单调谓词而不是重新设计二分」的做法。
    有重复元素时退化 O(n)
    [1,1,1,0,1,1,1] 找 0：a[lo] == a[mid] == 1，无法判断哪半有序，只能 ++lo 逐个收缩。
    而且这个 O(n) 不可改善
    考虑 [1,1,...,1,0,1,...,1]——那个 0 可能在任何位置，且任何比较都无法排除超过常数个候选。所以 O(n) 是信息论下界，不是实现不够好。面试时能指出这一点是加分项。
  4. 中级为什么在 std::set 上不该用 std::lower_bound？std::partition_point 又是什么？

    因为 std::lower_bound 保证的是 O(log n) 次比较，而不是 O(log n) 的运行时间。

    // 实现里维护 len 而不是 last，用 advance 推进
auto half = len >> 1;
It mid = first;
std::advance(mid, half);      // ← 关键
    迭代器类别比较推进总复杂度
    RandomAccess（vector）O(log n)O(log n)O(log n)
    Bidirectional（set / list）O(log n)O(n)O(n)

    在 set 上，advance 要沿红黑树中序一步步走。所以 std::lower_bound(s.begin(), s.end(), x) 能编译、结果对，但 O(n)——甚至比线性扫描更慢（同样 O(n) 移动，外加 log n 次比较）。

    正确做法
    用成员函数 s.lower_bound(x)——它直接沿红黑树从根往下走，真正 O(log n)。
    通用规则：容器提供了同名成员函数时一律用成员函数，因为它能利用内部结构而算法版只能通过迭代器接口。同类差异还有 set::find vs std::find、string::find vs std::search。
    partition_point（被低估的一个）
    C++11 的 std::partition_point(first, last, P) 返回第一个使谓词 P 为假的位置，要求区间已按 P 划分（也就是「谓词单调」的另一种说法）。
    它就是本文 §3 的谓词版模板。凡是「有序但不是按元素值排序」的二分——按某个派生字段、按外部条件——用它比硬凑一个 comparator 干净得多。

10.3 高级（体现深度）

  1. 高级你用二分答案解了一道题，但线上偶尔给出错误结果。可能是什么原因？

    二分答案最危险的性质是：单调性不成立时它不会报错，只会安静地给出错误答案。「偶尔错」这个描述指向三类问题。

    ① 谓词根本不单调
    典型是带「恰好」「正好等于」的约束。比如「选恰好 k 个元素使和等于 v」——feasible 序列可能是 F T F T，二分会随机落到某个可行点。
    放宽资源反而可能让「恰好」失效，这是单调性被破坏的最常见来源。这类题的正解通常是 DP，不是二分。
    ② 判定函数不确定（有随机性/依赖外部状态）
    如果 feasible 读了缓存、依赖当前时间、或用了浮点累加导致同一输入两次结果不同——那就是 git bisect 遇到 flaky test 的情形：一次误判会把整个二分带偏，而且表现为「偶发」。
    判定函数必须是纯函数。
    ③ 值域上下界估错
    下界比真实答案大、或上界比真实答案小，二分会返回边界值。这类错误只在数据接近极端时暴露，所以也表现为「偶尔」。上下界宁可放宽——多几轮迭代的代价可以忽略。

    怎么定位和根治：

    对拍验证单调性
    小数据下把值域全部枚举一遍，打印 feasible 序列，肉眼确认它是 FFF...FTTT...T 而不是交替的。这是最直接的验证，应该作为写二分答案的标准步骤。
    写下形式化的蕴含式
    明确写出 feasible(x) ⟹ feasible(x')（x' 是更宽松那侧）并给出一句话理由。最常用的理由是「原方案在放宽约束后仍然合法」——如果你说不出这句话，单调性很可能不成立。
    断言 + 暴力对拍进 CI
    把「小规模下二分答案 == 暴力枚举」写成一个属性测试挂进 CI。二分答案的正确性依赖一个数学性质而不是代码逻辑，所以它需要的是性质测试而不是几个用例。
  2. 高级B+ 树里二分出现在哪几个层次？为什么 B+ 树要设计成「又矮又胖」？

    两个层次，而它们的代价单位完全不同——这正是 B+ 树设计的全部动机。

    层次次数单次代价优化目标
    树高（跨页导航）log_B(n)一次磁盘/SSD I/O ≈ 100 µs把 B 做大 → 树高尽量低
    页内二分log₂B ≈ 8–10一次内存访问 ≈ 100 ns次要（差 1000 倍）
    为什么又矮又胖
    把节点做成一个磁盘页大小（4–16 KB），每页能放几百个 key，于是 B ≈ 数百：
    log_B(10⁹) ≈ 3~4 ← 十亿行只需 3~4 次 I/O log₂(10⁹) ≈ 30 ← 二叉搜索树要 30 次 I/O
    B+ 树的全部智慧就是「用页内的廉价二分（100 ns）换掉昂贵的跨页跳转（100 µs）」。
    B+ 而不是 B 的额外理由
    B+ 树把数据只放叶子、内部节点只放 key。这让内部节点能塞更多 key（B 更大 → 树更矮），而且叶子按序链成链表，范围扫描（WHERE x BETWEEN a AND b、ORDER BY）变成顺序 I/O 而不是回树遍历。
    同一思路的其他化身
    跳表：用多层链表模拟二分，每层跳过约一半——本质是「链表上的二分」，而且靠随机层高避免了红黑树的旋转（Redis ZSet 用它）。
    LSM-Tree 的 SSTable：块索引 + 块内二分，外加 Bloom 过滤器先挡掉不存在的 key。
    Parquet/ORC 列存：先用块级 min/max 统计剪枝，再在块内二分。
    cache 层的 B 树：把同一思路下移一层——一个 cache line 放多个 key，用 SIMD 一次比较 8–16 个，把「内存访问」当成新的「磁盘 I/O」来省。
    展开见 存储与数据架构。
  3. 高级一个 4 GB 的只读有序索引，二分查询是热点。怎么优化？

    标准二分在超出 cache 的大数组上渐进最优但常数很差：前几步跳跃距离是 n/2、n/4、n/8……每步一次 cache miss，而且预取器完全失效（下一步位置依赖当前比较结果，不可预测）。4 GB 数据 ≈ 10⁹ 个 int，log₂n ≈ 30 步，前约 20 步全是主存访问 → 单次查询约 2 µs 里绝大部分在等内存。

    ① 分支消除（最容易，先做这个）
    用条件移动代替分支：lo += cond ? half+1 : 0。二分的分支本质不可预测（约 50% 误预测率），每次误预测约 15–20 周期。写成 cmov 形式后能省掉这部分。
    ② eytzinger 布局（收益最大）
    把二叉搜索树按层序（BFS）压平存放：root 在下标 1，子节点在 2i / 2i+1。
    好处：前几层挤在同一条 cache line 里，头几步几乎零 miss；下标计算是纯乘法，无分支。
    代价：只适合只读索引——布局要预先构建，不支持随时插入。
    ③ B 树式扁平索引（终极方案）
    把 B+ 树的思路下移到 cache 层：一个 cache line（64 B）放 16 个 int32 key，用 SIMD 一次比较 16 个，一次 cache miss 换 4 位信息（而标准二分一次 miss 只换 1 位）。树高从 30 降到约 8。这是现代内存索引（如 ART、Masstree、FAST）的核心手段。
    ④ 插值查找（看分布）
    数据近似均匀时按值估算位置，期望 O(log log n)。但分布不均时退化到 O(n)，所以生产上要做成「插值探测几步，不收敛就退回二分」的混合形式。
    ⑤ 预取
    __builtin_prefetch 提前取两个可能的下一步。用一半带宽换延迟——只在带宽有余量时划算。
    但先问两个问题
    ① 这段二分在 profile 里真的超过 5% 了吗？如果没有，以上全是过早优化。② 能不能换掉二分？如果查询是点查且不需要范围扫描，一个哈希表就是 O(1)——比任何二分优化都强。如果查询有局部性（相邻查询的 key 接近），加一层缓存或改成从上次位置开始的指数搜索（galloping）可能比优化二分更有效。
    算法层面的选择永远排在常数优化之前。测量方法见 性能优化指南。
  4. 高级浮点二分为什么建议固定迭代次数而不是用 eps 判终止？有哪些别的坑？
    用 eps 的两个问题
    ① 大数值时死循环：while (hi - lo > 1e-9) 在 lo, hi ≈ 1e18 时，相邻 double 的间隔已远大于 1e-9 → 条件永远为真 → 挂死。
    ② eps 难定：取大了精度不够，取小了白跑（甚至不收敛）。而且它耦合了「算法」和「题目精度要求」两件事。
    固定迭代次数
    for (int it = 0; it < 100; ++it) {
    double mid = lo + (hi - lo) / 2;
    if (ok(mid)) hi = mid; else lo = mid;
}
    double 有 53 位有效位 → 相对精度上限约 2⁻⁵³ ≈ 1.1e-16，约 60 轮就已到极限（再多轮 lo/hi 会变成相邻浮点数，区间无法再缩）。100 轮是保守余量，开销可忽略。
    关键是把循环次数变成与数值大小无关的常数。

    其他坑：

    用 lo < hi 判终止
    浮点上这几乎必然死循环——mid 会变成等于 lo 或 hi，区间不再缩小但 lo != hi。浮点二分不能用严格不等式判终止。
    用绝对 eps 判「相等」
    fabs(a-b) < 1e-9 在大数上判不出、在小数上过早判定。要用相对误差：fabs(a-b) <= eps * max(1.0, fabs(a))。
    输出精度
    算对了但 cout 默认只输出 6 位有效数字。要 printf("%.10f") 或 setprecision(10)。
    最好的办法：整数化
    很多「浮点二分」的题可以乘以 10^k 变成整数二分（要求保留 4 位小数就在 [0, ans_max*10⁴] 上做整数二分）。这样既避开全部浮点陷阱，又精确控制精度。
    能整数化就整数化——和「金额用『分』而不是浮点『元』」是同一个原则。
