01

范式转移：从 Prompt Engineering 到 Context Engineering

上下文工程 （Context Engineering）是 Anthropic 提出的系统性方…

上下文工程（Context Engineering）是 Anthropic 提出的系统性方案，本质是从"写好一条提示"升级为"设计信息流动结构"。就像从"写一封好邮件"升级为"设计整个公司的信息传递系统"。

维度提示工程上下文工程
目标优化单次输入管理持续信息流
范围一条 Prompt整个信息架构
时间维度单次跨会话持续
核心动作措辞调优信息动态策划
02

上下文腐烂（Context Rot）

两大根源

  1. 注意力稀释：Transformer 的 O(n²) 注意力机制导致文本越长，每个 token 分配到的注意力权重越小
  2. 长序列学习不足：训练数据以短文本为主（平均几百 token），模型缺乏处理上万 token 长序列的经验

表现

  • 文本越长，模型回忆和推理能力越差
  • 关键信息被淹没在大量无关内容中
  • 模型"遗忘"前面提到的约束条件
03

第一性原理：最小化高信号 Token 集合

Anthropic 官方博文提出的上下文工程第一性原理：上下文工程的目标不是"塞更多信息"…

Anthropic 官方博文提出的上下文工程第一性原理：上下文工程的目标不是"塞更多信息"，而是找到最小化高信号 token 集合——让模型做出正确决策所需的最少信息量。

注意力预算有限：模型的注意力机制有固定的"预算"。每增加一个 token，其他 token 分到的注意力权重就减少。信息越多 ≠ 越好，反而可能稀释关键信息的注意力。这就是边际收益递减——上下文长度超过某个点后，新增信息带来的收益递减，甚至为负。

信息密度 vs 上下文长度

策略信息密度上下文长度效果
全量加载低（大量噪声）长（24K tokens）注意力稀释，任务完成率低
精准片段高（只含相关）短（6.8K tokens）注意力集中，任务完成率高
动态策划最高（按需注入）最短（按需变化）最优性价比

系统提示词的设计原则

Anthropic 建议从最简化开始，根据失败模式逐步添加：

  • 找到"正确的高度"：太抽象（"做一个好的助手"）= 没用，太具体（逐条规定每种情况）= 脆弱
  • 从失败中学习：每次 Agent 犯错 → 分析原因 → 在 system prompt 中添加针对性规则
  • 避免一次性塞满：system prompt 应该是一个活文档，随使用逐渐增长

五大上下文维度

上下文不只是"系统提示 + 对话历史"，而是五个维度的协同管理：

维度内容关键技术优化目标
对话上下文多轮对话历史滑动窗口 + 智能摘要保持连贯性
知识上下文RAG 检索结果向量检索 + 重排序提高相关性
系统上下文System Prompt + 工具定义分层管理 + Prompt Cache最大化缓存命中
用户上下文用户画像 + 偏好用户 ID 关联 + 持久化个性化
多模态上下文图片/音频/视频多模态 embedding + 压缩跨模态理解

工具设计原则

  • 避免臃肿工具集：工具过多 → 模型选择困难 → 注意力分散。每个工具应该有明确的职责边界
  • 返回信息节省 token：工具返回结果应该压缩为摘要，而非返回原始数据。例如搜索返回 Top-5 摘要而非全文
  • 让 Agent 自己找信息：与其预检索所有可能相关的信息，不如给 Agent 搜索工具让它按需查找（类似人类用书签）
05

Just-in-Time Context（即时上下文）

核心思想： 不要预检索所有数据，让 Agent 运行时按需加载

核心思想：不要预检索所有数据，让 Agent 运行时按需加载。就像人类不会一次性读完整本书，而是先看目录找到需要的章节，再深入阅读。

vs 传统 RAG

维度传统 RAG（预检索）Just-in-Time Context
检索时机请求前一次性检索Agent 运行时按需检索
检索内容基于用户问题预测相关文档基于 Agent 当前步骤的实际需求
信息相关性中（可能检索到不相关内容）高（Agent 自己判断需要什么）
上下文效率低（塞入大量预检索结果）高（只加载当前需要的）

实现模式

Just-in-Time Context 流程
1. 用户请求到达 → 只加载 System Prompt + 用户请求
2. Agent 分析任务 → 判断需要什么信息
3. Agent 调用搜索工具 → 获取特定信息
4. Agent 处理信息 → 生成中间结论
5. Agent 发现需要更多上下文 → 再次搜索
6. 循环直到任务完成
关键: Agent 自主决定"何时搜索"和"搜索什么" · 而非系统预判断"可能需要什么"
类比：传统 RAG 像"出门前把所有可能用到的东西塞进背包"；Just-in-Time Context 像"只带钱包，需要什么现场买"。后者更灵活，但需要 Agent 有足够的"购买力"（工具调用能力）。
06

长期任务三技术

当 Agent 执行持续数小时甚至数天的任务时，上下文窗口必然不够用

当 Agent 执行持续数小时甚至数天的任务时，上下文窗口必然不够用。Anthropic 提出三种技术解决长期任务：

技术一：上下文压缩

当上下文接近窗口限制时，对历史对话进行摘要压缩，然后"重新初始化"——用摘要替代原始历史。

压缩策略保留率信息损失适用场景
关键决策点提取~15%低（保留决策链）项目管理、代码审查
状态摘要~10%中（丢失细节）长时间对话
结构化笔记~5%较高（只保留要点）超长期任务

技术二：结构化笔记（持久化内存）

在上下文窗口外维护一个"笔记本"——Agent 可以随时写入和读取，不受窗口限制。

  • 案例：Claude 玩宝可梦 — Agent 在探索游戏世界时，把重要发现（NPC 对话、地图标记、道具位置）写入结构化笔记文件，需要时再读取
  • 实现：笔记文件（如 notes.md）存储在文件系统，Agent 通过文件读写工具操作
  • 优势：理论上无限容量，Agent 可以"记住"所有重要信息

技术三：子 Agent 架构

主 Agent 维护"干净的上下文"，把复杂子任务派发给子 Agent 执行。子 Agent 有自己的上下文窗口，完成后只返回结果摘要。

子 Agent 架构
主 Agent（干净的上下文窗口）
子 Agent A: 搜索相关文档
（独立上下文窗口，完成后返回摘要）
子 Agent B: 分析代码变更
（独立上下文窗口，完成后返回摘要）
子 Agent C: 生成测试用例
（独立上下文窗口，完成后返回摘要） · 主 Agent 只看到 3 个摘要，而非 3 次完整执行过程
三种技术的选择：短期任务（<30 分钟）→ 无需压缩；中期任务（30 分钟-2 小时）→ 上下文压缩；长期任务（>2 小时）→ 结构化笔记 + 子 Agent 架构。

生产落地建议

上下文工程通过 主动架构设计 （而非暴力扩展窗口）来平衡这对矛盾

矛盾本质

  • 需求端：Agent 需要更复杂的上下文来执行复杂任务
  • 能力端：模型存在注意力稀释和长文本处理缺陷

上下文工程通过主动架构设计（而非暴力扩展窗口）来平衡这对矛盾。

生产案例

生产数据： 某 RAG Agent 系统从全量加载迁移到上下文工程架构后，单次请求 Toke…

生产数据：某 RAG Agent 系统从全量加载迁移到上下文工程架构后，单次请求 Token 消耗从 24K 降至 6.8K（降幅 72%），Prompt Cache 命中率从 45% 提升至 91%。任务完成率在长文本场景（>8K tokens）从 58% 提升至 87%。关键：分层信息架构让核心指令常驻（系统提示 ~2K tokens），任务信息按需加载（工具调用 ~3K），参考资料检索获取（RAG ~1.8K），避免了"一股脑全塞进去"的暴力模式。

上下文工程 vs 提示工程：提示工程优化"怎么问"（单次输入措辞），上下文工程设计"看到什么"（信息流动架构）。前者是写一封好邮件，后者是设计整个信息系统。核心支柱：系统提示（常驻规则）+ 工具调用（按需获取）+ 示例管理（动态注入）。
  • 分层信息架构：核心指令常驻 + 任务信息按需 + 参考资料检索
  • 动态策划上下文（而非全量加载）
  • 关注 Prompt Cache 命中率（>90% 为目标）
  • 监控 Token 消耗趋势（持续优化信息密度）
  • 不要一股脑把所有信息塞进上下文（注意力稀释）
  • 不要混淆提示工程和上下文工程的边界
  • 不要忽略上下文腐烂（越长 ≠ 越好）
  • 不要用固定 Prompt 应对所有场景（应分层管理）
10

Q&A

Q1：上下文工程和提示工程的核心区别是什么？
提示工程优化单次输入（How to prompt），上下文工程设计信息流动结构（How to manage information flow）。前者是一次性的措辞调优，后者是持续的、跨会话的系统设计。类比：提示工程 = 写一封好邮件，上下文工程 = 设计整个公司的信息传递系统。
Q2：什么是上下文腐烂？根因是什么？
上下文腐烂（Context Rot）指文本越长模型表现越差。两大根因：①Transformer O(n²) 注意力机制导致注意力稀释——每个 token 分配到的注意力权重随长度递减；②训练数据以短文本为主（平均几百 token），模型缺乏处理上万 token 长序列的经验。表现：关键信息被淹没、模型"遗忘"前面的约束条件。
Q3：如何在工程上解决上下文腐烂问题？
三大支柱架构：系统提示（固定规则，常驻）+ 工具调用（按需获取，Function Calling）+ 示例管理（动态注入，RAG + 向量检索）。核心原则是动态策划而非全量加载——关键信息聚焦、历史状态压缩、分层信息架构。生产验证：Token 消耗从 24K 降至 6.8K，任务完成率从 58% 提升至 87%。
Q4：上下文工程的"分层信息架构"具体怎么设计？
三层分离：(1) 核心指令层（系统提示 ~2K tokens）— 不变的底层规则、角色设定、行为准则，常驻上下文；(2) 任务信息层（当前任务相关 ~3K tokens）— 用户请求、中间状态、工具调用结果，随任务动态变化；(3) 参考资料层（RAG 检索 ~1.8K tokens）— 知识库文档、历史记录，按需检索注入。关键：三层的变化频率不同（不变/常变/偶变），按频率分层管理可最大化缓存命中率。
Q5：为什么说"扩大上下文窗口"不是上下文腐烂的根本解决方案？
因为注意力稀释是 O(n²) 机制的固有特性——即使窗口扩大到 100K tokens，中间部分的注意力仍然稀疏（"Lost in the Middle"现象）。实验数据：在 128K 窗口中，模型对前 10% 和后 10% 的信息回忆准确率约 90%，但中间 50% 的信息回忆准确率降至 40-60%。上下文工程通过"不给全文，只给精准片段"的方式绕过了这个限制，本质是减少 n（输入长度）而非扩大窗口。
