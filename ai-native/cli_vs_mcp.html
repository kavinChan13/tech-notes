CLI 与 MCP 架构对比

CLI vs MCP — 本地直连 vs 协议标准化 / Token消耗降90% / 混合架构趋势

AI 工程 阅读 ~15 min 8 章
00

概览

CLI 是 Agent 的"手"——直接在本地操作系统执行命令

CLI 是 Agent 的"手"——直接在本地操作系统执行命令；MCP 是 Agent 的"电话"——通过标准化协议远程调用外部服务。两者不是竞争关系，而是本地执行层与协议连接层的互补。

01

CLI 与 MCP 的本质定位

2024–2026 年，AI Agent 与外部工具交互存在两条技术路线

2024–2026 年，AI Agent 与外部工具交互存在两条技术路线。CLI（Command Line Interface）是 Agent 直接在本地 Shell 中执行命令的方式——模型生成命令字符串，操作系统执行，返回文本输出。物理距离最短，延迟最低。而MCP（Model Context Protocol）是 Anthropic 于 2024 年 11 月发布的开放协议标准，基于 JSON-RPC 2.0，为 Agent 提供结构化的工具发现、参数传递和结果返回机制。

┌──────────── CLI 路线 ────────────┐ ┌──────────── MCP 路线 ────────────┐ │ │ │ │ │ Agent │ │ Agent │ │ │ │ │ │ │ │ ▼ │ │ ▼ │ │ 生成 Shell 命令 │ │ 生成 JSON-RPC 请求 │ │ │ │ │ │ │ │ ▼ │ │ ▼ │ │ 本地 OS 执行 │ │ MCP Client → MCP Server │ │ (git/docker/npm) │ │ │ │ │ │ │ │ ▼ │ │ ▼ │ │ 外部 API / 服务 │ │ 文本输出 → Agent 解析 │ │ │ │ │ │ │ ▼ │ │ 延迟: <10ms │ │ 结构化 JSON → Agent 解析 │ │ Token: 仅命令+输出 │ │ │ │ │ │ 延迟: 50–500ms │ └───────────────────────────────────┘ │ Token: Schema+请求+响应 │ └───────────────────────────────────┘

核心定位差异对比

维度CLI（本地直连）MCP（协议标准化）
设计目标为人类/Agent 提供本地命令行交互为 Agent 提供标准化工具调用协议
输入格式字符串命令（argv / stdin）结构化 JSON-RPC 请求
输出格式文本流（stdout / stderr），可选 JSON结构化 JSON 响应，类型明确
运行位置本地进程，短生命周期Client-Server 模型，Server 持久运行
协议层无协议（纯文本流）JSON-RPC 2.0 标准协议
认证模型继承本地 Shell 权限集中式认证、OAuth、Token 轮换

关键洞察：CLI 和 MCP 不是竞争技术，而是工具粒度的两个极端——CLI 是一个通用的、无类型的、高训练先验的工具；MCP 是多个窄的、有类型的、低训练先验的工具集合。

CLI 的本质是"Agent 直接用训练知识操作工具"，MCP 的本质是"Agent 通过协议发现并调用工具"——前者靠模型记忆，后者靠协议描述。

02

Token 经济学：CLI 的成本优势

Token 成本是 Agent 系统最直接的运营开支

Token 成本是 Agent 系统最直接的运营开支。根据 Shareuhack 的 75 次基准测试对比分析，CLI 方案在可比任务中消耗的 Token 量仅为 MCP 方案的 1/4 到 1/32。这个差距在大规模部署中会产生巨大的成本差异。

Token 消耗对比（同一任务：列出 Git 仓库的 Pull Request） CLI 路线: Agent → "gh pr list --json number,title" → 输出文本 Token: ~120 (命令) + ~300 (输出) = ~420 tokens MCP 路线: Session启动: 加载工具Schema → ~8,700 tokens (5个Server) Agent → JSON-RPC 请求 → 结构化响应 Token: ~200 (Schema分摊) + ~150 (请求) + ~300 (响应) = ~650 tokens 单次差距: ~1.5x 含启动开销: 4–32x (取决于工具数量和会话长度)

Token 消耗差异的根因分析

消耗环节CLIMCP差距倍数
Schema 注入0（无 Schema，模型用训练知识）~8,700 tokens（5 Server 懒加载后）∞ vs 0
请求构造~120 tokens（命令字符串）~150 tokens（JSON-RPC 结构体）1.25x
响应解析~300 tokens（文本输出）~300 tokens（JSON 响应）~1x
会话启动0（无握手）~500ms 连接建立 + 能力协商显著
多工具扩展线性增长（每个命令独立）超线性（Schema 随工具数增长）差距扩大

Anthropic 在 Claude Code v2.1.7 引入了MCP Tool Search（懒加载）机制：未使用的 MCP 工具仅注入名称（而非完整 Schema），首次调用时才加载完整定义。这将最坏情况的 Schema 开销从 ~55,000 tokens 降至 ~8,700 tokens，减少 85%。但即便如此，CLI 仍然保持零 Schema 开销的优势。

Token 差距的本质：CLI 让模型用"已有知识"驱动工具（零额外上下文），MCP 让模型用"即时描述"驱动工具（需注入 Schema）。知识 vs 描述，成本差了一个量级。

实测数据：在每日数百个会话、每个会话数十次工具调用的生产环境中，CLI 路线的月度 API 成本可比 MCP 路线低 60–80%。但如果需要连接 5+ 外部 SaaS 平台，MCP 的集中认证和统一管理价值会抵消 Token 成本劣势。

03

MCP 解决的核心问题：工具调用标准化

在没有 MCP 之前，每个 AI Agent 框架都需要为每个外部工具编写定制化的适配代码—…

在没有 MCP 之前，每个 AI Agent 框架都需要为每个外部工具编写定制化的适配代码——解析不同 CLI 的输出格式、处理不同 API 的认证方式、适配不同数据结构。这导致了巨大的适配开发成本。MCP 通过协议层标准化，一次性解决了这个问题。

MCP 标准化之前（逐一定制化适配） ┌────────┐ ┌─────────┐ ┌──────────┐ ┌──────────┐ │ Agent │───→│ Git适配层│───→│ git CLI │ │ 每增加一个│ │ │───→│ Docker层│───→│ docker │ │ 工具需要 │ │ │───→│ Jira适配│───→│ Jira API │ │ 一个新适配│ │ │───→│ Slack层 │───→│ Slack API│ │ N个工具 = │ └────────┘ └─────────┘ └──────────┘ │ N个适配器 │ MCP 标准化之后（协议级统一接入）: ┌────────┐ ┌──────────┐ ┌──────────────────────────┐ │ Agent │───→│MCP Client│───→│ MCP Server (Git) │ │ │ │(统一协议) │───→│ MCP Server (Docker) │ │ │ │JSON-RPC │───→│ MCP Server (Jira) │ │ │ │2.0 │───→│ MCP Server (Slack) │ └────────┘ └──────────┘ └──────────────────────────┘ 一次接入 N个工具 = N个标准Server 全部适配 适配器开发量降低 85%

MCP 协议的核心能力

能力机制效果
工具发现tools/list 动态扫描可用工具Agent 运行时自动获知可用能力
参数传递JSON Schema 定义输入参数类型和约束消除参数格式歧义，减少幻觉
结果返回结构化 JSON 响应，类型明确Agent 可直接解析，无需正则提取
认证管理Server 端集中处理 OAuth / TokenAgent 无需感知认证细节
可观测性Server 端统一记录每次调用日志企业级用量追踪和 ROI 归因

MCP 解决的不是"能不能调用工具"的问题——CLI 也能调用。MCP 解决的是"如何用统一的方式调用任意工具"的问题，就像 USB 解决的不是"能不能连接设备"，而是"能不能用同一种接口连接所有设备"。

04

技术架构分层：三层模型

2026 年行业已收敛到 三层工具架构模型 ，而非二元选择

2026 年行业已收敛到三层工具架构模型，而非二元选择。每一层解决不同层次的问题，实际系统通常混合使用三层。

三层工具架构（2026 行业收敛，非二元选择）
第一层 · Skills 技能层
工作流编排 / 决策指导 / 可复现行为；告诉 Agent "做什么"和"什么时候做"（代码审查流程、PR 模板、部署流程）
第二层 · MCP 协议层
外部连接 / 认证管理 / 结构化接口；需要 OAuth / 跨平台 / 企业可观测性（GitHub / Slack / Jira MCP）
第三层 · CLI 本地执行层
确定性本地操作 / 文件读写 / 测试执行；训练知识覆盖 / 快速迭代 / 零配置（git / docker / npm / pytest / rg）

三层架构职责划分

层级适用场景不适用场景Token 开销
Skills多步骤工作流、团队标准化流程单次工具调用中（流程描述注入）
MCP外部 SaaS、OAuth 认证、跨服务编排本地文件操作、简单命令高（Schema + 连接开销）
CLIgit/docker/npm 等确定性本地操作需要认证的外部 API低（仅命令 + 输出）

前沿模型（Claude Opus / Sonnet 4.6）能直接驱动复杂 CLI 工具（aws-cli、glab、gh），无需结构化 Schema 辅助。但较弱的模型在面对不熟悉的 CLI 工具时，MCP 的结构化 Schema 能显著降低参数幻觉率。

模型能力对工具选型的影响

工具选型的另一个关键维度是模型能力等级。前沿模型凭借训练数据中的大量 CLI 用法积累，能准确驱动复杂命令行工具；而较弱模型在面对不熟悉的 CLI 时容易产生参数幻觉。

模型等级CLI 驱动能力MCP 依赖度推荐策略
前沿（Opus 4.6 / GPT-5）强——能正确驱动 aws-cli、glab 等复杂 CLI低——Schema 补偿需求小CLI 优先，MCP 仅用于认证类服务
中端（Sonnet 4 / GPT-4o）中——常见工具准确，冷门工具偶有幻觉中——陌生工具需 Schema 辅助混合策略，按工具熟悉度动态路由
轻量（Haiku / GPT-4o-mini）弱——参数幻觉率高（~35%）高——Schema 将正确率提升至 ~92%MCP 优先，CLI 仅限最基础操作

模型能力与工具选型的关系：模型越强，越偏向 CLI（减少 Schema 开销，发挥模型训练知识）；模型越弱，越偏向 MCP（用 Schema 补偿模型能力不足）。这不是技术优劣的判断，而是能力与需求的匹配。

三层模型的精髓：核心高频操作用 CLI（性能极致），外部服务连接用 MCP（标准化），复杂流程编排用 Skills（可复现）——各司其职，不是替代关系。

AGENTS.md：声明工具优先级的实践标准

Claude Code 的 AGENTS.md（或 CLAUDE.md）文件成为声明工具优先级策略的事实标准。开发者在项目根目录中创建该文件，明确指定 Agent 在工具选择上的偏好和约束。

# AGENTS.md 工具优先级声明示例 ## Tool Priority - ALWAYS prefer CLI (bash) for: git, docker, npm, file operations - Use MCP servers for: GitHub PR/Issue, Slack notifications, Jira - NEVER use MCP for local file operations (CLI is faster) ## MCP Server Configuration - github-mcp: PR management, Issue tracking - slack-mcp: team notifications only - DO NOT load unused MCP servers (saves ~2K tokens each) ## Security Policy - Require approval for: git push, docker rm, npm publish - Deny: rm -rf, force push, credential access

通过在 AGENTS.md 中显式声明工具策略，团队可以实现：① 不同项目使用不同的工具优先级；② 安全策略的统一管控；③ 新成员入职时 Agent 行为的可预期性。这种声明式配置比在每个系统提示词中硬编码规则更灵活、更易维护。

值得注意的是，AGENTS.md 中的策略声明对模型行为的影响是显著的。Anthropic 的工具编写指南明确指出："即使是工具描述的微小改进，也能显著提升工具调用的准确性"。将工具优先级写入项目配置文件，相当于为模型提供了一个持久化的决策参考框架。

对于多模型切换场景（如团队同时使用 Claude 和 GPT），AGENTS.md 的价值更加突出——它确保不同模型在同一项目中遵循相同的工具选择策略，避免因模型差异导致的行为不一致。

选型的核心逻辑不是"哪个更好"，而是"哪个更适合当前场景"——就像你不会用电钻拧螺丝，也不会用螺丝刀打墙洞。工具的价值取决于匹配度，而非绝对能力。

未来趋势：混合架构与动态路由

2026 年中期，行业共识已明确： 混合架构 是终局形态

2026 年中期，行业共识已明确：混合架构是终局形态。核心高频工具通过 CLI 直连获得极致性能，长尾工具通过 MCP 标准化集成降低维护成本，两者由 Agent 根据任务上下文动态路由。

动态路由的实现机制

混合架构的关键在于动态路由——Agent 在每次工具调用前根据任务特征自动选择最优通道。这个过程由模型的自回归预测驱动，而非硬编码的路由规则。模型在解码时综合考量四个因素：① 用户请求的语义（本地操作 vs 外部服务）；② 已加载工具的名称和描述；③ 训练数据中对特定工具的熟悉度；④ 系统提示词中的显式策略（如 AGENTS.md 中的声明）。

关键趋势：SEP-2640 规范已将三层架构（Skills + MCP + CLI）纳入 MCP 协议官方演进路线。Claude Code 的 AGENTS.md 文件成为声明工具优先级策略的事实标准——开发者在文件中指定"优先使用 CLI，CLI 无法处理时回退到 MCP"。

混合架构的本质是"用最简单的工具解决最简单的问题，用最标准的协议解决最复杂的连接"——不是技术妥协，而是工程理性的最优解。

Q&A

CLI 方案的 Token 消耗真的能比 MCP 降低 90% 吗？这个数据怎么来的？
这个数据来源于 Shareuhack 的 75 次基准测试对比。关键在于区分"单次调用差距"和"含启动开销差距"：单次工具调用（如列出 PR），CLI 约 420 tokens，MCP 约 650 tokens，差距约 1.5 倍。但计入 MCP 的 Schema 注入开销（5 Server 约 8,700 tokens），在短会话中差距可达 4–32 倍。"降低 90%"指的是在高频、短会话场景下的综合 Token 成本对比。在长会话（100+ 次工具调用）中，Schema 开销被摊薄，差距缩小到 1.5–3 倍。
MCP 懒加载（MCP Tool Search）是怎么降低 Schema 开销的？
v2.1.7 之前的最坏情况：5 个 MCP Server 的完整 Schema 在会话启动时全部注入上下文，消耗约 55,000 tokens。懒加载机制改为：启动时只注入工具名称列表（每个工具约 5–10 tokens），Agent 首次调用某个工具时才通过 MCP Tool Search 加载该工具的完整 Schema。实测将启动 Schema 开销从 ~55K 降至 ~8.7K，减少 85%。但未使用的工具名仍然占用上下文——如果连接了 50 个 Server 各有 20 个工具，仅名称列表就占 ~2,000 tokens。
为什么弱模型更需要 MCP 而不是 CLI？
前沿模型（Claude Opus 4.6、GPT-5）在训练数据中见过大量 git/docker/npm 命令的用法，能准确构造命令字符串并解析文本输出。但较弱模型（Haiku、GPT-4o-mini）对不熟悉的 CLI 工具容易产生参数幻觉——编造不存在的 flag 或错误的参数值。MCP 的 JSON Schema 明确定义了每个参数的名称、类型、约束和可选值，相当于给模型提供了"填空题模板"而非"自由写作题"。实测 Schema 辅助能将弱模型的参数正确率从 ~65% 提升到 ~92%。
CLI 在浏览器环境中为什么受限？有什么解决方案？
浏览器安全沙箱（Sandbox）禁止网页直接执行操作系统命令——这是防止恶意网站操控用户计算机的基础安全机制。因此基于浏览器的 AI 工具（如 ChatGPT 网页版、Gemini Web）无法直接使用 CLI 路线。解决方案：① 通过远程 MCP Server 桥接——浏览器中的 Agent 通过 MCP 协议调用运行在服务端的工具；② 使用 WebAssembly 在浏览器内模拟部分 CLI 功能（性能有限）；③ 使用桌面客户端（如 Claude Code Desktop）绕过浏览器沙箱限制。
三层架构（Skills + MCP + CLI）和传统的 Function Calling 是什么关系？
Function Calling 是模型层面的能力机制——模型输出结构化的函数调用请求，框架负责执行。三层架构是框架层面的工具组织策略——决定哪些工具以什么方式暴露给模型。具体来说：CLI 工具通常以单一高权限 bash 函数的形式暴露给模型；MCP 工具以多个独立的类型化函数暴露；Skills 则通过系统提示词中的流程描述来引导模型按特定步骤使用工具。三者都依赖 Function Calling 作为底层执行机制，但在工具粒度和组织方式上完全不同。
我的团队应该如何选择？有没有简单的决策框架？
四步决策框架：① 列出团队需要连接的所有工具和服务。② 分类——本地工具（git/docker/npm/测试框架）走 CLI 路线；需要 OAuth 认证的外部 SaaS（GitHub/Jira/Slack/CRM）走 MCP 路线；多步骤流程（代码审查/CI-CD/部署）走 Skills 编排。③ 评估模型能力——如果使用前沿模型，可以偏向 CLI（减少 Schema 开销）；如果使用较弱模型或需要支持多模型切换，偏向 MCP（Schema 补偿）。④ 从 CLI 优先开始，随着需要连接的外部服务增多，逐步引入 MCP Server。不要一开始就构建完整的 MCP 基础设施。
大厂为什么倾向重度 CLI 定制而不是全面使用 MCP？
核心原因是极致的性能追求和已有工程能力。以 Anthropic Claude Code 为例：它只需要 8 个核心工具（Bash、Read、Edit、Write、Grep、Glob、Task、TodoWrite），其中 Bash 是万能适配器——模型通过 Shell 可以驱动任何本地工具。这种极简设计使 Token 消耗最低、响应速度最快。但代价是需要强大的模型能力（前沿模型才能正确驱动复杂 CLI）和专业的工程团队维护 CLI Wrapper。大厂有这两项资源，所以选择 CLI 直连是理性决策。中小团队缺乏这两项资源，MCP 的标准化和 Schema 辅助是更务实的选择。
