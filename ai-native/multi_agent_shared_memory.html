01

为什么需要共享记忆

多 Agent 协作的核心痛点：没有共享记忆，每个 Agent 只能各自获取上下文 — 成本…

多 Agent 协作的核心痛点：没有共享记忆，每个 Agent 只能各自获取上下文 — 成本翻倍、信息不一致、协作沦为空谈。

三大核心问题

  • 上下文工程：如何精准管理 Agent 间的状态传递，而不是全量广播
  • 成本控制：避免 Token 爆炸和延迟激增 — 共享 ≠ 全量复制
  • 一致性保障：多个 Agent 同时读写时，如何避免冲突和数据污染
02

共享记忆的本质与架构

共享记忆的本质是一条 持久化的公共上下文总线 — 任何 Agent 可以按需读写，但只读取自…

共享记忆的本质是一条持久化的公共上下文总线 — 任何 Agent 可以按需读写，但只读取自己需要的结论片段，而非全量上下文。

架构总览

数据流转时序

Agent A (研究) Memory Manager Agent B (分析) │ │ │ │── 1.写入精炼结论 ─────▶│ │ │ │── 2.版本校验+存储 ──▶ │ │ │ │ │ │◀── 3.按需查询 key ─────│ │ │── 4.返回结论片段 ──────▶│ │ │ │ │◀─ 5.订阅变更通知 ──────│ │ │ │── 6.Agent B 完成 ──────▶│ │ │ │── 7.写入分析结果 │ │◀─────────────────────── │

核心原则

  • 按需路由：上下文按任务需求精准分发，不做全量广播
  • 结论优先：Agent 只写入极短结论（约 100 字 JSON），不分享思考过程
  • 工具化视角：把其他 Agent 的产出当作工具返回结果来处理
03

两种正确实践方案

方案一：黑板模式 + 状态路由

  • 使用 Redis Hash 作为轻量级中间存储
  • Agent 仅写入极短 JSON 格式的结论状态（约 100 字）
  • 后续 Agent 按需读取，不分享思考过程
  • 典型技术栈：Redis Hash + 极短 JSON
# 黑板模式：Agent 写入结论
memory.set("agent_a_result", {
    "conclusion": "市场规模约 500 亿，年增 12%",
    "confidence": 0.87,
    "timestamp": "2024-01-15T10:30:00"
})
# Agent B 按需读取
result = memory.get("agent_a_result")

方案二：长期记忆的克制使用

  • 错误做法：原始记忆直接存入向量数据库，召回时拼接数十个文本块到提示词
  • 正确实践：添加压缩代理层，将原始记忆提炼成 100 字内纯结论后再存储
  • 检索时通过元数据过滤仅召回 1 条最相关记忆，避免 Token 爆炸和幻觉问题
黄金法则：共享记忆的核心不是"共享所有信息"，而是"只共享经过压缩的结论"。原始数据留在各自 Agent 的私有记忆中，共享层只存放精炼后的结果。
04

共享记忆 vs 私有记忆

共享记忆 = 团队公共白板，私有记忆 = 个人笔记本

共享记忆 = 团队公共白板，私有记忆 = 个人笔记本。白板写结论供协作，笔记本记草稿供自己用。

维度共享记忆私有记忆
本质持久化的公共上下文总线Agent 内部的工作记忆
存储内容精炼结论（~100 字 JSON）完整思考过程、中间状态
访问权限所有 Agent 可读写仅所属 Agent 可访问
存储介质Redis / 数据库 / 向量数据库Agent 上下文窗口 / 本地缓存
容量策略严格限制，定期清理随上下文窗口自然淘汰

生命周期跨会话持久化单次会话内有效
05

并发控制与一致性保障

当多个 Agent 同时读写共享记忆时，没有并发控制就像多个人同时在同一张纸上写字 — 结果…

当多个 Agent 同时读写共享记忆时，没有并发控制就像多个人同时在同一张纸上写字 — 结果必然是混乱的。

三种并发控制策略

策略原理优点缺点适用场景
悲观锁写操作前先获取排他锁，阻塞其他写入者强一致性，实现简单吞吐量低，易死锁写入频繁、一致性要求极高
乐观锁写入时检查版本号，版本不匹配则重试高吞吐，无阻塞冲突多时重试成本高读多写少、冲突概率低
CAS 操作Compare-And-Swap：原子性比较并交换无锁设计，性能优异仅适用于简单值更新状态标记、计数器等原子操作

悲观锁 vs 乐观锁实现对比

# 悲观锁：写入前先锁
with memory.lock("key"):
    data = memory.get("key")
    data["status"] = "completed"
    memory.set("key", data)

# 乐观锁：写入时检查版本
data = memory.get("key")  # 含 version 字段
data["status"] = "completed"
success = memory.set("key", data, expected_version=3)

矛盾记忆处理

当不同 Agent 对同一事件产生矛盾记忆时，工程上追求最终一致性而非完美共识 — 用轻量级裁判 Agent + 时间戳和准确率规则做简单裁决。

  • 避免方案：分布式投票算法、区块链共识机制 — 过度设计，延迟不可接受
  • 工程方案：轻量级裁判 Agent，基于时间戳（最新优先）和准确率（历史表现）做简单规则裁决

实现方式与向量数据库选型

向量数据库上线前必须解决三个工程问题： 索引预热 避免冷启动延迟、 分区策略 控制单节点负载…

三种存储方案选型

存储类型代表技术适用场景特点
Redis HashRedis, Memcached实时黑板、状态路由毫秒级读写，容量有限，适合短结论
关系/文档数据库PostgreSQL, MongoDB结构化状态持久化事务支持好，查询灵活，适合结构化数据
向量数据库Chroma, Pinecone, Milvus语义检索长期记忆支持相似度搜索，适合非结构化知识检索

向量数据库选型指南

数据库规模部署方式核心优势适用场景
Chroma百万级以下嵌入式 / 单机Python 原生，零配置，开发快原型开发、小型 Agent 系统
Pinecone千万级全托管云服务免运维，自动扩缩容中型生产环境，快速上线
Milvus十亿级分布式集群高性能，支持混合检索大规模生产，高吞吐需求
pgvector百万级PostgreSQL 插件复用现有 PG 基础设施已有 PG 的团队，结构化+向量混合查询

生产环境部署要点

向量数据库上线前必须解决三个工程问题：索引预热避免冷启动延迟、分区策略控制单节点负载、TTL 淘汰防止记忆无限膨胀。

  • 索引预热：生产环境启动时主动加载高频访问的向量索引到内存，避免首次查询出现秒级延迟
  • 分区策略：按业务域或 Agent 类型划分 Collection，避免单个 Collection 过大导致查询退化
  • TTL 淘汰机制：为每条记忆设置过期时间（如 7 天 / 30 天），过期后自动清理，控制存储成本和召回噪声
  • 监控指标：重点跟踪查询 P99 延迟、召回准确率、存储增长率三项核心 SLI

权限控制模型

  • 命名空间隔离：每个 Agent 有独立的 key 前缀，如 agent_a:*、agent_b:*
  • 读写权限矩阵：配置每个 Agent 对共享区域的读/写/管理权限
  • 容量配额：限制每个 Agent 的写入量，防止单个 Agent 占满共享空间

应用场景

共享记忆在三大场景中发挥关键作用：多轮客服（跨轮次状态传递）、多 Agent 研究（协作知识…

共享记忆在三大场景中发挥关键作用：多轮客服（跨轮次状态传递）、多 Agent 研究（协作知识汇聚）、工作流协同（流水线状态接力）。

典型应用

  • 多轮客服系统：用户意图识别 Agent 将结论写入共享记忆，后续 Agent（订单查询、退款处理、技术支持）按需读取，避免用户重复描述问题
  • 多 Agent 研究：信息收集、数据分析、报告撰写三个 Agent 各自将结论存入共享记忆，报告 Agent 按需拉取前两者的精炼结论
  • 工作流协同：流水线中每个阶段的 Agent 将处理结果写入共享记忆，下一阶段 Agent 读取并继续处理，实现无缝接力
架构师价值：专注业务编排能力，不要在模型底层重复造轮子。超长上下文窗口扩展、KV Cache 提示词缓存普及、系统层自动解决前缀共享 — 底层在演进，架构层保留扩展接口应对技术迭代。
  • 使用黑板模式：Agent 只写入极短结论（~100 字 JSON）
  • 添加压缩代理层，将原始记忆提炼后再存入共享层
  • 使用乐观锁处理并发写入，版本号校验防冲突
  • 配置命名空间隔离和读写权限矩阵
  • 向量数据库检索时通过元数据过滤仅召回 1 条最相关记忆
  • 用轻量级裁判 Agent 处理矛盾记忆，追求最终一致性
  • 不要全量共享上下文（导致 Token 爆炸）
  • 不要向量数据库无限存储（引发幻觉问题）
  • 不要追求完美一致性（分布式投票/区块链 = 过度设计）
  • 不要让 Agent 共享完整思考过程（只共享结论）
  • 不要使用悲观锁处理低冲突场景（吞吐量损失大）
  • 不要忽略容量限制（单个 Agent 可能占满共享空间）
08

Q&A

Q1：多 Agent 系统中共享记忆的本质是什么？
共享记忆 = 持久化的公共上下文总线。它不是把所有 Agent 的信息塞进同一个大上下文，而是一条精准的"结论共享管道"。每个 Agent 将自己产出的精炼结论（约 100 字 JSON）写入共享层，其他 Agent 按需读取自己需要的部分。核心理念是把其他 Agent 的产出当作工具返回结果来处理 — 上下文按需路由，边界严格控制。
Q2：黑板模式和全量共享上下文有什么区别？
本质区别在于"共享粒度"。全量共享 = 把每个 Agent 的完整思考过程、中间状态全部放入公共上下文，导致 Token 爆炸（10 个 Agent 各产生 5000 Token 上下文 → 共享后每个 Agent 看到 50000 Token）。黑板模式 = 只共享精炼结论（每个 Agent 写入 ~100 字 JSON），其他 Agent 按需读取特定 key，单个 Agent 的上下文增量控制在几百 Token 内。Token 成本差异可达 100 倍以上。
Q3：多个 Agent 同时写入共享记忆时如何保证一致性？
三种并发控制策略：(1) 悲观锁 — 写前获取排他锁，强一致但吞吐低，适合写入频繁且一致性要求极高的场景；(2) 乐观锁 — 写入时检查版本号（version field），版本不匹配则重试，高吞吐无阻塞，适合读多写少场景（Agent 系统通常如此）；(3) CAS (Compare-And-Swap) — 原子性比较并交换，无锁设计，适合简单的状态标记和计数器。实际生产中推荐乐观锁为主 + CAS 辅助，避免悲观锁带来的性能瓶颈。
Q4：向量数据库在共享记忆中扮演什么角色？怎么选？
向量数据库用于共享记忆的"语义检索"层 — 当 Agent 需要历史知识时，通过语义相似度搜索召回相关记忆。选型指南：(1) Chroma — Python 嵌入式，零配置，适合原型和小型系统（百万级以下）；(2) Pinecone — 全托管云服务，免运维，适合中型生产环境（千万级）；(3) Milvus — 分布式集群，高性能，适合大规模生产（十亿级）；(4) pgvector — PostgreSQL 插件，复用现有基础设施，适合已有 PG 的团队。关键约束：必须添加压缩代理层，将原始记忆提炼成 100 字内结论再存储；检索时通过元数据过滤仅召回 1 条最相关记忆。
Q5：共享记忆和私有记忆的边界怎么划？
核心原则：共享记忆存"结论"，私有记忆存"过程"。共享记忆 = 跨 Agent 协作所需的精炼结果（~100 字 JSON），所有 Agent 可读写，持久化存储（Redis/DB/向量库），需要并发控制。私有记忆 = Agent 自身的思考过程、中间推理步骤、临时草稿，仅所属 Agent 可访问，随上下文窗口自然淘汰，无需并发控制。判断标准：如果这个信息只有当前 Agent 在后续步骤中会用到 → 私有；如果其他 Agent 可能需要参考 → 共享（但必须先压缩）。
Q6：不同 Agent 产生矛盾记忆怎么处理？
避免过度设计（分布式投票、区块链共识），采用工程化的轻量方案：(1) 裁判 Agent — 一个专门的小型 Agent 负责裁决矛盾；(2) 简单规则 — 基于时间戳（最新优先）和历史准确率（表现好的 Agent 权重更高）做判断；(3) 最终一致性 — 不追求完美共识，允许暂时不一致，后续通过更多证据自动修正。类比：团队讨论出现分歧时，不需要全体投票，由经验最丰富的组长基于最新信息和过往记录做个快速判断即可。
Q7：共享记忆系统有哪些常见坑？
三大禁忌：(1) 全量共享上下文 — 导致 Token 爆炸，10 个 Agent 的上下文膨胀 100 倍；(2) 向量数据库无限存储 — 召回过多相似但不相关的记忆片段，引发幻觉问题；(3) 追求完美一致性 — 分布式共识算法延迟高、实现复杂，在 Agent 系统中得不偿失。核心方法论：黑板模式实现精准路由 + 极致压缩控制上下文膨胀 + 拥抱底层缓存优化机制（KV Cache、超长上下文窗口）。
Q8：共享记忆系统的监控应该关注哪些核心指标？
生产环境需要关注四类核心 SLI：(1) 查询 P99 延迟 — 衡量共享记忆读取性能的上界，向量检索的 P99 应控制在 200ms 以内；(2) 写入吞吐量 — 单位时间内完成的写入操作数，反映并发控制策略是否成为瓶颈；(3) 召回准确率 — 定期抽样评估向量检索返回结果与 Agent 实际需求的匹配度，低于 80% 需要优化 Embedding 模型或元数据过滤策略；(4) 存储增长率 — 监控共享记忆空间的膨胀速度，确保 TTL 淘汰机制正常运行，避免成本失控。
Q9：如何从单体 Agent 系统渐进迁移到共享记忆架构？
推荐三步渐进法：(1) 第一步 — 引入 Redis Hash 作为轻量级黑板，让现有 Agent 将关键结论写入共享 key，不改架构只加一层读写；(2) 第二步 — 添加压缩代理层，对写入共享层的数据做精炼（原始内容 → 100 字结论），同时配置命名空间隔离和 TTL 淘汰；(3) 第三步 — 按需引入向量数据库作为语义检索层，对接历史记忆的相似度搜索。关键原则：每一步都可以独立上线验证，不需要一次性完成全部改造。先在低风险场景（如内部工具）跑通，再推广到生产核心链路。
