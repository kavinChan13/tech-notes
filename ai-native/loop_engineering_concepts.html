01

AI 工程的四代演进

过去两年，AI 开发的重点正在不断变化：从研究如何写好提示词（Prompt），逐步发展到组织…

过去两年，AI 开发的重点正在不断变化：从研究如何写好提示词（Prompt），逐步发展到组织上下文（Context）、编排工具与流程（Harness），再到构建能够自主运行、持续交付结果的循环系统（Loop）。

Prompt Engineering → 怎么问 AI Context Engineering → 给 AI 什么信息 Harness Engineering → 如何组织 AI 的能力 Loop Engineering → 如何让 AI 持续创造结果

四代工程范式对比

工程阶段核心思想关注点输入内容AI 能力人的角色典型场景
Prompt Engineering通过设计提示词获得更好的输出怎么问问题Prompt / 指令单轮生成提问者聊天、写作、代码生成
Context Engineering组织并提供完整背景信息给 AI 什么信息知识库、历史、约束上下文理解信息组织者RAG、AI 搜索、代码助手
Harness Engineering连接模型、工具、数据形成工作流如何调用能力上下文 + API + 工具链执行任务系统设计者Agent、自动化流程、多工具协同
Loop Engineering构建目标驱动的自主闭环系统如何持续完成目标目标、状态、记忆、验证规划→执行→验证→修复→持续运行规则制定者后台 Agent、持续交付、自动运维

为什么需要从 Harness 进化到 Loop？

维度Harness（编排层）Loop（循环层）
执行模式人类触发 → 单次执行 → 等待下一个触发自主触发 → 循环迭代 → 持续运行
状态管理通常无状态（每次从外部获取上下文）有状态（记忆、进度、检查点）
失败恢复失败 → 人工干预失败 → 自动重试/降级/跳过
目标达成执行完指定步骤迭代直到满足条件
人的介入每步可能需要人确认只在关键决策点介入
核心洞见：Prompt Engineering 是「教 AI 怎么做」，Loop Engineering 是「设计一个系统，让 AI 自己持续做」。前者优化单条指令，后者优化自动决定"提示什么、什么时候提示、结果是否可接受"的整套系统。
02

Loop Engineering 的起源

Loop Engineering 的出现有一个清晰的时间节点： 2026 年 6 月

Loop Engineering 的出现有一个清晰的时间节点：2026 年 6 月。

引爆点：两句话，百万次转发

人物身份原话
Boris ChernyAnthropic Claude Code 负责人"I don't prompt Claude anymore. I have loops running. They're the ones prompting Claude and figuring out what to do. My job is to write loops."
Peter SteinbergerOpenClaw 创作者"You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents."

随后，Addy Osmani（Google 工程师）在 Substack 发表了长文，将这一实践正式命名并系统化为 Loop Engineering，使其成为独立的工程学科。

背景：AI 编程工具的三代演进

阶段代表工具工作方式瓶颈人的角色
第一代：自动补全GitHub Copilot 早期补全当前行，人类主导只能辅助，不能自主逐行审查
第二代：对话式ChatGPT、Claude.ai问一句答一句，人类手动推进人类成为瓶颈（需要不断复制粘贴）任务编排者
第三代：Agent 自主循环Claude Code、OpenAI Codex AgentAgent 自主规划、执行、验证，循环迭代如何设计让 Loop 可靠运行规则制定者
范式转变：第三代工具的出现意味着，工程师的核心竞争力从"会写提示词"变成了"会设计 Loop"。你不再是 Agent 的操作员，而是 Agent 的架构师。

五阶段详解

阶段英文名做什么典型信号来源产出
意图Intent定义目标结果：成功是什么样子，约束是什么开发者或外部系统目标定义 + 约束条件
上下文Context收集相关代码、文档、报错日志、约定规范代码库、测试输出、历史结构化上下文
行动Action编辑文件、运行命令、调用工具、草拟方案Agent 自主执行代码变更 / 工具输出
观察Observation获取测试结果、编译错误、运行时输出测试框架、CI、人工 Review反馈信号
调整Adjustment根据观察更新计划，重复循环直到完成下一轮内循环更新的上下文 / 新计划
闭环的力量：测试失败不只是一条错误消息，它是新的上下文；类型错误不只是阻断，它是一个关于错误假设的信号；Code Review 评论不只是反馈，它是驱动下一步行动的新观察。

内循环 vs 外循环

层级谁在驱动做什么频率示例
内循环（Agent 内置）Agent 自身读文件 → 修改代码 → 运行测试 → 读错误 → 再修改秒级/分钟级Claude Code 的 ReAct 循环
外循环（你来设计）你设计的系统按计划发现任务 → 分派 Agent → 验证结果 → 记录状态 → 开启下一轮分钟级/小时级/天级Cron 触发的 PR 审查

你不再坐在 Agent 旁边，为每一步打下一条指令。你在设计一套外部系统，它替你驾驶内循环，而你去做更有判断价值的事：制定规则、审查结果、优化系统。

经典 while loop 模式（Braintrust）

Claude Code 和 OpenAI Agents SDK 等成功的 Agent 共享一个简单架构：带工具的 while 循环。每次迭代传递当前状态给模型，接收决策（工具调用或文本响应），然后前进。

组件职责设计要点
System Prompt定义 Agent 角色和能力简洁、明确、避免过度约束
Tools提供可调用操作参数精简、输出格式化
Transcript维护对话状态控制长度、选择性保留
While Loop编排一切明确的终止条件
为什么简单架构胜出：复杂的框架或图结构往往在生产中被证明不可靠。能够一致工作的 Agent 通常在底层收敛到相似架构：好的提示词 + 少量干净工具 + 对话历史 + while 循环。这种模式吸收了复杂性（在工具设计和上下文工程中），同时保持核心架构足够简单，任何人都可以修改。
04

四种 Loop 类型

每个生产级 Loop 都符合以下四种模式之一

每个生产级 Loop 都符合以下四种模式之一。选择哪种取决于触发方式和停止条件。

类型触发方式停止条件适用场景示例成本特征
Heartbeat Loop短间隔持续运行（秒/分钟）永不（持续监控）监控：日志检查、服务健康、漂移扫描每 5 分钟检查错误率，>1% 则开 Issue低（每次调用简单）
Cron Loop定时调度单次运行完成批量工作：每日代码审查、依赖审计、晨会总结工作日上午 10 点审查超过 3 天的 PR中（固定频率）
Hook Loop外部事件触发单次运行完成PR 推送、CI 失败、Slack 消息、Webhookpush 后运行测试，失败则尝试修复中（事件驱动）
Goal Loop持续迭代满足成功条件重构、Bug 狩猎、迁移任务迁移所有文件到新 API 模式，直到无匹配高（迭代次数不确定）

Goal Loop 的配置要素

要素说明差示例好示例
任务描述Agent 要做什么"修复 auth bug""修复 login.spec.ts 中的 session leak"
成功条件如何判断完成（无）"连续运行测试 5 次零失败"
约束条件什么不能做（无）"不要触碰其他测试文件"
最大迭代防止无限循环（无）"最多 50 次迭代"
Token 成本警告：没有 max_iterations 的 Goal Loop 可能在一小时内烧掉 $500。始终设置上限，从 50 次迭代开始，观察成本后再增加。Goal Loop 的成本 = 单次迭代成本 × 迭代次数，迭代次数由任务复杂度和停止条件的严格程度决定。

Loop 的六大构成要素

一个能够真正独立运行的 Loop 需要六个核心组件，缺一不可：

一个能够真正独立运行的 Loop 需要六个核心组件，缺一不可：

要素概览

要素解决的问题类比关键设计决策
自动触发器（Automations）Loop 何时启动心跳起搏器Cron 表达式 vs 事件触发 vs 目标驱动
并行隔离（Worktrees）多 Agent 如何不冲突独立手术台Git worktree vs 容器 vs 临时目录
技能文件（Skills）如何减少重复推理成本操作手册哪些知识应该固化为 Skill
连接器（Connectors / MCP）如何访问外部系统API 网关权限范围、安全隔离
子 Agent（Sub-Agents）如何分离生成和评估独立审计员Maker-Checker 模式、模型层级
持久记忆（Memory）如何跨对话保持状态工作日志文件 vs 数据库、同步 vs 异步

要素一：自动触发器（Automations）

自动触发器是 Loop 的心跳。没有自动触发，Loop 就只是"你做了一次的操作"，而不是真正意义上的循环。

触发类型配置方式适用场景示例
定时触发Cron 表达式固定频率任务每天 9:00 检查 CI 失败
目标触发验证命令 + 成功标准迭代直到条件满足测试全部通过 + lint 干净
事件触发Webhook / 文件变化响应式任务PR 提交后自动审查

要素二：并行隔离（Worktrees）

当你同时运行多个 Agent 时，文件冲突是最容易出问题的地方。Git Worktree 为每个 Agent 提供独立的工作目录，共享 Git 历史但文件改动完全隔离。

隔离方式实现优势劣势
Git Worktree每个 Agent 检出独立分支共享历史、易合并、易清理需要 Git 项目
容器隔离Docker 容器完全隔离、可复现启动慢、资源消耗大
临时目录系统临时目录简单、快速无版本控制
审查瓶颈：Worktree 消除了机械性文件冲突，但你处理和批准代码变更的速度，才是决定你能并行运行多少个 Agent 的真正上限。5 个 Agent 并行 = 5 倍的审查工作量。

要素三：技能文件（Skills）

Skills 解决的是每次都在浪费的成本：每次新对话，Agent 都要从零推断你的项目规范。Skill 是一个包含 SKILL.md 文件的文件夹，写明了项目约定、构建步骤、"我们不这样做是因为那次事故"等知识。

Skill 要素内容作用
YAML Frontmattername、description、version索引层判断是否加载此 Skill
技术栈声明语言版本、框架、依赖Agent 知道用什么工具
构建命令安装、测试、构建、部署Agent 知道如何验证
核心约定编码规范、架构约束Agent 知道什么不能做
历史教训"不要这样做因为..."避免重复犯错

要素四：连接器（Connectors / MCP）

一个只能看到本地文件系统的 Loop 能做的事情非常有限。连接器（基于 MCP 协议）让 Agent 能够读取 Issue 追踪、查询数据库、调用 API、在 Slack 发消息。

连接器类型功能安全风险权限控制建议
代码托管（GitHub/GitLab）读 PR、创建 Issue、推送代码中（可能推送错误代码）只读 + 人工批准推送
通讯（Slack/Discord）发消息、读频道高（可能发送不当消息）限制频道 + 审批外发
数据库查询数据高（可能泄露数据）只读 + 审计日志
CI/CD触发构建、读取结果低允许触发
最小权限原则：必须为每个连接器配置最小权限，高风险操作（推送代码、合并 PR、发送外部通知）应当要求人工审批。一个拥有"写全部"权限的 GitHub 连接器 = 一颗定时炸弹。

要素五：子 Agent（Sub-Agents）

Loop 中最重要的架构决策之一：把写代码的 Agent 和检查代码的 Agent 分开。写了代码的模型在评分自己的作业时会过于宽容。

模式描述适用场景成本
Maker-CheckerMaker 写代码，Checker 审查代码生成、文档编写2× 模型调用
Fresh Context每个子 Agent 用全新上下文长 Loop 防上下文腐烂1× 模型调用/子任务
Model Tiering简单任务用便宜模型，复杂任务用贵模型成本优化可变
Specialist Agents不同 Agent 有不同工具集和专长多领域协作按任务分

这种"制作者-检查者"模式也被应用到了 Loop 的停止条件上：Claude Code 的 /goal 命令在每次迭代后，会用一个单独的模型来判断是否"完成"，而不是让做了工作的那个模型来判断。

要素六：持久记忆（Memory）

记忆是所有能跨对话持续运行的 Loop 的核心支柱。模型在每次对话之间会完全遗忘。解决方案极其简单：把状态写在文件里，文件放在仓库里。

记忆层级存储方式容量持久性示例
会话内内存（Context Window）128K-200K tokens会话结束即丢失当前对话历史
跨会话文件（仓库内）无硬上限Git 持久化TODO.md、PROGRESS.md
长期向量数据库 / 外部服务无限制服务持久化Honcho、mem0、Chroma
仓库记得：即使模型不记得，仓库记得。每次 Loop 触发时，Agent 读取状态文件（TODO.md、PROGRESS.md），知道昨天做了什么、哪些修复已经合并、哪些任务还在开放。状态文件应该随代码一起提交，这样团队所有人（包括未来的自己）都能看到 Agent 的工作历史。

工具设计原则（Braintrust）

当你把每个 API 参数都暴露给语言模型时，它会被无关细节淹没而犯错

当你把每个 API 参数都暴露给语言模型时，它会被无关细节淹没而犯错。相反，定义每个工具时只包含必要参数，并提供针对 Agent 任务量身定制的清晰描述。

反面案例 vs 正面案例

维度反面：通用通信 API正面：专用工具
工具名称send_messagenotify_customer
参数数量10+ 个（channel, recipient, content, subject, template, variables, priority, scheduling, tracking, metadata）2 个（customerEmail, message）
Agent 认知负担高（需要理解所有参数的语义和约束）低（只需关注核心参数）
内部复杂性暴露给 Agent封装在工具内部
出错概率高（参数组合爆炸）低（参数简单）
上下文工程洞见：在典型的 Agent 对话中，工具输出占总 token 的 67.6%，系统提示只占 3.4%。工具定义再加 10.7%。这意味着工具占据了 Agent 实际看到的近 80% 内容。设计工具输出就像设计提示词一样重要：使用简洁语言、过滤无关数据、格式化易读。

工具输出设计原则

原则反面示例正面示例
简洁返回完整 JSON（包含 query_metadata、cache_hit 等）"Found 2 users..."
过滤返回所有字段（包括内部 ID、时间戳）只返回 Agent 需要的字段
格式化原始 JSON blob人类可读的文本 + 结构化提示
引导（无提示）"Need more details? Use 'get_user_details' with the user's email."

评估作为基础

当你构建一个 Agent 时，你实际上是在构建一个可评估的系统。这意味着除了 Agent（或任务函数）本身，你还需要创建一个代表性数据集和评分库。这三个组件构成了你可以测量、基准测试和持续改进的基础。

评估步骤做什么为什么
1. 端到端评估验证 Agent 能否完成由单个用户输入驱动的雄心勃勃的任务建立基线
2. 失败模式分析从 Agent 挣扎的单个轮次构建数据集（选错工具、回复差）针对性改进
3. 远程评估在 playground 中 ad-hoc 测试 Agent 在多个输入上的表现快速迭代

模型会改变，提示会演进，工具会更新，所以你的评估需要持久。这种一致性让你能够衡量进度并在迭代 Agent 时捕获回归。

Do / Don't

  • 从窄任务开始，明确验证方式
  • 设置 max_iterations 防止 Token 失控
  • 把写代码和检查代码的 Agent 分开
  • 把状态写在文件里，文件放在仓库里
  • 为高风险操作配置人工审批
  • 先让 Loop 只写文件，你来审查 diff
  • 工具设计只包含必要参数
  • 工具输出要简洁、格式化、有引导
  • 建立持久评估数据集
  • 一开始就构建全自动多 Agent 复杂 Loop
  • 没有 max_iterations 的 Goal Loop
  • 让同一个模型既写代码又评判自己
  • 每次 Loop 触发时从零开始
  • 全自动执行推送代码、合并 PR
  • 把整个 REST API 暴露为单个工具
  • 忽视 Token 成本监控
  • 返回原始 JSON 作为工具输出
  • 没有评估就上线 Agent

Q&A

Harness 是"单次任务的编排层"——人类触发 → 执行 → 等待下一个触发
Loop Engineering 和 Harness Engineering 的核心区别是什么？

Harness 是"单次任务的编排层"——人类触发 → 执行 → 等待下一个触发。Loop 是"持续运行的闭环系统"——自主触发 → 循环迭代 → 持续运行。关键区别在于状态管理：Harness 通常无状态（每次从外部获取上下文），Loop 有状态（记忆、进度、检查点）。另一个区别是失败恢复：Harness 失败需要人工干预，Loop 可以自动重试/降级/跳过。实际项目中，Loop 通常建立在 Harness 之上——Loop 负责"何时做什么"，Harness 负责"怎么做"。

为什么需要把"写代码的 Agent"和"检查代码的 Agent"分开？

这是确认偏差（confirmation bias）的问题。当同一个模型既生成代码又评估代码时，它会倾向于为自己的决策辩护，而不是客观评估。这类似于代码 review 的最佳实践——reviewer 看 PR diff，而不是看作者的思考笔记。在 Loop 中，这体现为Maker-Checker 模式：Maker（用中端模型如 Sonnet）写代码，Checker（用强模型如 Opus）审查。Claude Code 的 /goal 命令也采用这种模式——在每次迭代后，用一个单独的模型来判断是否"完成"，而不是让做了工作的那个模型来判断。成本增加约 2×，但质量提升显著。

Skill 和传统的 Prompt 模板有什么区别？

Prompt 模板是"每次都要重复输入的背景信息"，Skill 是"按需加载的操作手册"。核心区别：①加载时机：Prompt 每次都加载（浪费 Token），Skill 只在相关时加载（渐进式披露）；②结构化：Prompt 是自由文本，Skill 有 YAML frontmatter（name、description、version）用于索引层判断；③可组合：Prompt 是单一的，多个 Skill 可以同时激活（如"项目约定" + "测试规范"）；④可演进：Prompt 是静态的，Skill 可以有 success_count 追踪和定期审查更新。Skill 的本质是"程序性记忆"——知道怎么做，而非"陈述性记忆"——知道什么（那是 RAG 的事）。

如何防止 Goal Loop 的 Token 成本失控？

五层防护：①设置 max_iterations：硬性上限，从 50 次开始，有成本数据后再增加；②使用子 Agent 隔离上下文：每次迭代用新鲜上下文，避免主 Loop 的 Context Window 不断膨胀；③模型路由：简单步骤（分类、扫描）用便宜模型（Nano），复杂步骤（审查、决策）用贵模型（Frontier），可降低 60-80% 成本；④提示缓存：重复的系统提示和工具定义跨迭代缓存，节省 40-90% 输入 Token；⑤成本监控：实时监控每次迭代的 Token 消耗，设置单次 Loop 的预算上限。一个没有 max_iterations 的 Goal Loop 可能在一小时内烧掉 $500——这是最常见的 Loop 工程事故。

为什么"把状态写在文件里"比用数据库更好？

对于编码 Agent 和大多数 Loop 场景，文件有四个关键优势：①崩溃恢复：Agent 进程死掉后重启，读文件即可恢复状态，无需额外的持久化层（文件系统有 fsync）；②人类可读可编辑：开发者可以直接查看和修改文件来干预 Agent 行为（git diff 查看变更）；③版本控制友好：天然适配 git 工作流，Agent 的行为变更有完整追踪（谁在什么时候改了什么）；④零基础设施：不需要消息队列、数据库等额外基础设施。局限：文件不适合需要毫秒级响应的实时场景（文件 I/O 比内存慢），也不适合数百个 Agent 并发写入（需要文件锁或 CAS 机制）。但对于大多数 Loop 场景，"工作区即共享内存"是最简单可靠的方案。

什么时候应该用 Loop，什么时候不应该？

用 Loop 的信号：①任务需要多步迭代（不是一次性完成）；②有明确的验证条件（测试通过、lint 干净、截图匹配）；③需要跨时间持续运行（每天/每周/事件触发）；④失败后需要自动重试或降级。不用 Loop 的信号：①简单问答或一次性生成（单次 LLM 调用足够）；②没有明确的验证条件（"让代码更好"太模糊）；③任务高度创造性（需要人类直觉和判断）；④成本敏感且任务简单（Loop 的 overhead 可能不值得）。经验法则：如果你发现自己在重复执行相同类型的任务，且每次都需要手动触发 Agent，那就应该设计一个 Loop。
