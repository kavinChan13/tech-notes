高级 RAG 的本质：给固定的"检索→生成"流水线注入判断力——让系统自己决定要不要检索、检索结果够不够好、要不要再查一轮。

01

Self-RAG：让模型学会"自我反思"

Self-RAG 的核心：在生成过程中嵌入三个"反思开关"——要不要查

Self-RAG 的核心：在生成过程中嵌入三个"反思开关"——要不要查？查到了有没有用？写出来的东西有没有依据？

Self-RAG（Self-Reflective Retrieval-Augmented Generation）由 Akari et al. 2023 提出，核心创新是在 LLM 的 SFT 训练阶段注入了三种特殊的反思 token，让模型在生成文本时同步输出对自身行为的判断。

三个反思标记

标记判断时机作用输出
Retrieve生成前当前 query 是否需要外部知识？Yes → 触发检索；No → 直接生成
ISREL检索后检索到的文档与问题相关吗？Relevant → 使用；Irrelevant → 丢弃
ISSUP生成后生成的内容有没有 context 支撑？Supported → 保留；Not Supported → 重生成

这三个标记解决了 Naive RAG 的三个核心痛点：

  • 不必要检索：不是所有问题都需要检索——"Python 是谁发明的？"这种常识问题直接回答即可，跳过检索可减少 200-500ms 延迟
  • 噪声注入：检索到的 Top-K 文档可能完全不相关，强行塞给 LLM 反而会误导生成方向
  • 幻觉检测：LLM 可能无视 context 直接"脑补"，ISSUP 标记提供了忠实性的自检机制
训练方式：Self-RAG 的反思标记不是后处理逻辑，而是作为特殊 token 训入模型权重中。训练数据格式为 [query] [Retrieve:Yes] [doc] [ISREL:Relevant] [answer] [ISSUP:Supported]，模型学会在正确的时机输出正确的判断。

Corrective RAG (CRAG)：检索质量的自动纠错

CRAG 的本质：检索完不急着用，先让"质检员"评估结果，不合格就切换到 Web 搜索作为…

CRAG 的本质：检索完不急着用，先让"质检员"评估结果，不合格就切换到 Web 搜索作为 fallback。

Corrective RAG 由 Yan et al. 2024 提出，核心思想是在检索和生成之间插入一个知识评估模块，对检索结果进行三档评级，根据评级结果动态调整后续策略。

三级评估策略

评级判断条件行动典型场景
CORRECT至少 1 篇文档高度相关直接使用检索结果知识库覆盖该主题
AMBIGUOUS部分相关但不充分检索结果 + Web 搜索合并知识库有但不完整
INCORRECT所有文档都不相关完全切换到 Web 搜索知识库未覆盖

CRAG 还有一个关键步骤——Knowledge Refinement（知识精炼）：不是把所有检索结果都塞给 LLM，而是先用一个轻量模型提取每篇文档中与 query 相关的关键句，去噪后再送入生成阶段。这一步可以将 context 的噪声比例从 40% 降低到 10% 以下。

CRAG 的核心价值：当知识库不完整或存在陈旧信息时，Web Search 作为 fallback 通道确保系统不会"硬答"。在企业场景中，知识库覆盖率通常只有 60-70%，CRAG 的 fallback 机制可以将"无法回答"的比例从 30% 降至 5% 以下。
03

Adaptive RAG：查询复杂度路由

Adaptive RAG 的本质：在检索前先给问题"分诊"——简单问题走快速通道，复杂问题走…

Adaptive RAG 的本质：在检索前先给问题"分诊"——简单问题走快速通道，复杂问题走多步通道，不浪费资源也不漏掉信息。

Adaptive RAG 由 Jeong et al. 2024 提出，核心创新是在 pipeline 入口添加一个复杂度分类器，将 query 路由到三种不同的处理策略。

三级路由策略

复杂度典型 Query处理策略延迟
Simple"Python 什么时候发布？"直接 LLM 回答（跳过检索）~200ms
Moderate"解释 RAG 的工作原理"单次检索 + 生成~800ms
Complex"比较 GraphRAG 和 Vector RAG 在多跳推理上的优劣"问题分解 + 多步检索 + 综合~2000ms

分类器的三种实现方式

方式 1：轻量级 BERT 分类器 — 用几百条标注数据 fine-tune 一个三分类模型，推理延迟 <10ms，适合生产环境。

方式 2：LLM 判断 — 用 prompt 让 GPT-4 判断复杂度，灵活但增加 300-500ms 延迟，适合原型阶段。

方式 3：规则启发式 — 关键词匹配：包含"比较/对比/分析"→ complex，包含"是什么/什么时候"→ simple。零成本但泛化能力弱。

路由准确性是关键瓶颈：误判简单问题为复杂会浪费 5 倍计算资源；误判复杂为简单会因缺少检索而答错。在实际部署中，分类器 F1 需要达到 0.85 以上才能带来正向 ROI。

Adaptive RAG 与 Self-RAG 的关系：Adaptive 是路由级自适应（整个 pipeline 的走向），Self-RAG 是token 级自适应（生成过程中逐步判断）。两者可以组合——先用 Adaptive 路由，复杂路径中再用 Self-RAG 控制质量。

RAPTOR：层次化摘要树

RAPTOR 解决的核心矛盾：查询粒度与索引粒度不匹配——宏观问题（"这篇论文的主题

RAPTOR 解决的核心矛盾：查询粒度与索引粒度不匹配——宏观问题（"这篇论文的主题？"）需要高层摘要，细节问题（"实验用了多少数据？"）需要原始分块，RAPTOR 两个都给你。

RAPTOR（Recursive Abstractive Processing for Tree-Organized Retrieval）由 Sarthi et al. 2024 提出，核心思想是构建一棵多层级摘要树，叶子节点是原始 chunks，越往上越抽象，查询时在所有层级同时检索。

RAPTOR 摘要树构建: Level 2 (最抽象): [全文档主题摘要] / \ Level 1 (中间层): [章节A摘要] [章节B摘要] / \ / \ Level 0 (叶子): [c1] [c2] [c3] [c4] ← 原始 chunks 构建过程 (自底向上): 1. Level 0: 原始分块 2. 对 Level 0 做 embedding → 聚类 (K-Means) 3. 每个簇用 LLM 生成摘要 → Level 1 4. 对 Level 1 再聚类 → 再摘要 → Level 2 5. 重复直到达到预设层数 (通常 2-3 层) 查询时: 所有层级同时检索 → 合并 → Rerank → Top-K

RAPTOR vs 普通分块 vs Parent-Child

方面普通分块Parent-ChildRAPTOR
索引层级单层固定两层多层递归（2-5层）
全局理解差（碎片化）中等好（高层摘要包含全局视角）
细节保留好好好（叶子层保留原文）
索引成本低中高（需 LLM 生成每层摘要）
适用场景通用代码/长文档多粒度查询需求
生产经验：RAPTOR 的索引构建成本是普通分块的 5-10 倍（LLM 摘要调用），但查询质量在"全局总结类"query 上提升 30-50%。适合知识库规模中等（<10万 chunks）且查询粒度多样的场景。

HyDE：假设性文档嵌入

HyDE 的反直觉之处：不用"问题"去搜"答案"，而是先让 LLM 编一个"假设性答案"，用…

HyDE 的反直觉之处：不用"问题"去搜"答案"，而是先让 LLM 编一个"假设性答案"，用这个答案的 embedding 去检索——因为答案和文档的表述方式更接近。

HyDE（Hypothetical Document Embeddings）由 Gao et al. 2022 提出，解决的痛点是 query-document 语义鸿沟：用户的 query 是短、口语化的问句（"怎么报销"），而文档是长、规范化的陈述句（"差旅费用报销流程管理办法"），两者在向量空间中的距离远大于语义上的实际相关性。

HyDE 的三步流程

Step 1：LLM 基于 query 生成一个假设性回答（不需要准确，只需要风格和文档类似）

Step 2：用假设性回答的 embedding（而非原始 query）去检索向量库

Step 3：返回最相似的 Top-K 文档作为真正的 context

HyDE 的优劣势

优势劣势
桥接 query-document 表达鸿沟LLM 生成的假设可能包含错误，误导检索方向
对短/模糊 query 效果好（提升 5-15%）增加一次 LLM 调用延迟（200-500ms）
无需 fine-tune embedding 模型对精确关键词查询反而有害（如 "torch.nn.Linear 参数"）
改进方案：生成多个（3-5 个）假设性文档，取 embedding 平均值，减少单次生成的偏差。或者用 α × query_emb + (1-α) × hyde_emb 做融合，α=0.5 通常效果最好。
06

Agentic RAG：给检索注入 Agent 灵魂

Agentic RAG = RAG + Agent：检索不再是固定流程，而是 Agent 工…

Agentic RAG = RAG + Agent：检索不再是固定流程，而是 Agent 工具箱中的一个 tool，LLM 自主决定何时检索、检索什么、什么时候够了。

Agentic RAG 将检索能力嵌入 Agent 的 ReAct（Reasoning + Acting）循环中，Agent 可以根据中间推理结果动态选择下一步行动——可能是查向量库，可能是搜互联网，可能是查数据库，也可能是直接计算。

Agentic RAG vs 普通 RAG

能力普通 RAGAgentic RAG
数据源固定单源动态选择（向量库/Web/SQL/代码）
检索次数固定一次迭代多步（根据中间结果决定）
错误恢复无可重试、换策略、换数据源
多跳推理不支持自然支持（每步推理触发新检索）
延迟可控性固定可预测不确定（需设 max_iterations）
Agentic RAG 的 ReAct 循环: Thought: "用户问的是跨领域问题，需要先查技术文档再查代码" Action: vector_search("RAG 架构设计") Observation: [检索结果...] Thought: "需要更具体的实现细节，查代码库" Action: code_search("RAG pipeline implementation") Observation: [代码结果...] Thought: "现在有足够信息，可以综合回答" Final Answer: ...
生产风险与缓解：Agentic RAG 的迭代次数不确定，可能导致延迟爆炸和成本失控。必须设置 max_iterations=5、超时机制（>10s 强制 fallback 到简单 RAG）、成本上限（每次请求最多 $0.05）。某企业部署后，5% 的请求触发了 3+ 轮迭代，P99 延迟从 800ms 飙升到 8s。
07

查询分解与多步推理

多步 RAG 的本质：把一个大问题拆成小问题，每个小问题独立检索回答，最后综合——和人类做研…

多步 RAG 的本质：把一个大问题拆成小问题，每个小问题独立检索回答，最后综合——和人类做研究的过程一样。

两种多步模式

模式 1：Query Decomposition — 先将复杂问题分解为 2-4 个子问题，逐一检索回答后综合。适合比较类（"A 和 B 的区别"）和多跳类（"X 的作者在哪工作"）问题。

模式 2：IRCoT（Interleaving Retrieval with Chain-of-Thought）— 在思维链的每一步推理中都触发检索，用新信息继续推理。这是最灵活的多步方式，但 LLM 调用次数是单次的 3-5 倍。

模式拆解方式检索次数最佳场景
Query Decomposition一次性拆成子问题2-4 次比较类、多跳类
IRCoT推理过程中按需检索3-5+ 次需要逐步推理的复杂问题
Self-AskLLM 自问自答式分解2-3 次需要中间事实的问题
成本警示：多步检索的 LLM 调用次数是单次的 3-5 倍。在 GPT-4 定价下，单次 RAG 成本约 $0.01，多步模式可达 $0.03-0.05。对简单问题使用多步反而有害——增加延迟且可能引入噪声。建议先用 Adaptive Router 判断复杂度，只对 complex query 启用多步。

生产案例：某企业知识库 RAG 升级

背景：日均 5 万次查询，Naive RAG baseline 的回答准确率 62%，"无法回答"比例 28%。

Level 1 升级：添加 Adaptive Router + HyDE，简单问题（40%）跳过检索直答，模糊 query 改写后检索。准确率 → 71%，"无法回答" → 18%。

Level 2 升级：添加 CRAG Web Fallback，知识库不足时自动切换到 Web 搜索。准确率 → 76%，"无法回答" → 8%。

Level 3 升级：对 complex query（15%）启用 Query Decomposition。准确率 → 79%，但 P95 延迟从 1.2s 升至 3.5s。

结论：Level 1+2 的 ROI 最高（准确率 +14%，延迟仅 +200ms），Level 3 的边际收益递减（+3% 但延迟 +2.3s）。最终生产环境采用 Level 2 方案。

Q&A

Self-RAG 在 SFT 阶段将反思标记（Retrieve/ISREL/ISSUP）作为…
Self-RAG 的反思标记是怎么训进模型的？和普通 fine-tuning 有什么区别？

Self-RAG 在 SFT 阶段将反思标记（Retrieve/ISREL/ISSUP）作为特殊 token 加入训练数据。训练样本格式为 [query][Retrieve:Yes][doc][ISREL:Relevant][answer][ISSUP:Supported]，模型学会在正确的时机输出正确的判断标记。和普通 fine-tuning 的区别：普通 SFT 只训"输入→输出"的映射，Self-RAG 额外训了"中间决策"的能力。这需要构造带有反思标注的训练数据，通常用强模型（如 GPT-4）生成标注，再训到小模型（如 Llama-2-7B）上。

CRAG 的 Web Search fallback 有什么风险？如何控制？

主要风险：①Web 搜索结果质量不可控（可能包含错误或低质量内容）②安全风险（恶意网页注入）③延迟不可预测（Web 搜索受网络影响）。控制措施：限制 Web 搜索结果为可信域名白名单；对 Web 结果做额外的可信度评分过滤；设置 Web 搜索超时（>3s 降级到不搜索）；Knowledge Refinement 步骤提取关键句去噪。在金融/医疗等敏感领域，通常禁用 Web fallback 或限制为特定权威来源。

RAPTOR 和 Parent-Child Chunking 有什么本质区别？

本质区别在于"摘要生成方式"和"层级数量"。Parent-Child 是固定两层结构：小块（child）用于检索，大块（parent）用于送入 LLM，两者都是原始文本，没有生成摘要。RAPTOR 是多层递归结构：每一层都通过聚类+LLM 摘要生成新的、更抽象的节点。Parent-Child 保留的是"上下文窗口"（大块文本），RAPTOR 保留的是"不同抽象级别的理解"（从细节到全局）。查询时 Parent-Child 只检索 child 层，RAPTOR 在所有层级同时检索。

HyDE 在什么场景下最有效？什么场景下会失效？

最有效场景：①短/模糊 query（如"怎么报销"），query 和文档的表达风格差异大 ②开放域问答，用户用口语提问而文档用专业术语 ③embedding 模型没有针对 query-document 不对称做过优化。失效场景：①精确关键词查询（如"torch.nn.Linear 参数列表"），HyDE 生成的假设性文档可能偏离精确术语 ②LLM 对领域完全不了解时，假设性文档质量极差 ③对延迟敏感的场景（增加 200-500ms）。改进：生成 3-5 个假设文档取 embedding 均值，或做 query-hyde 融合（α=0.5）。

如何选择适合自己场景的高级 RAG 模式？

选择框架：①先跑 Naive RAG baseline，收集 100+ bad case ②分析 bad case 类型：检索不到 → 加 HyDE/Adaptive；检索到了但答错 → 加 Self-RAG 忠实性检查；知识库不覆盖 → 加 CRAG fallback；比较/多跳问题 → 加 Query Decomposition；全局总结问题 → 加 RAPTOR/GraphRAG ③逐步升级，每个优化做 A/B 测试 ④原则：不要过度设计，每加一层复杂度都增加延迟/成本/维护负担。80% 的场景在 Level 1（Adaptive + HyDE）就够了。

Agentic RAG 在生产环境中如何防止成本失控？

三层防护：①硬限制——max_iterations=5（最多 5 轮推理+检索），超时 10s 强制 fallback 到简单 RAG ②成本预算——每次请求设定上限（如 $0.05），达到上限立即终止并返回当前最佳结果 ③智能降级——高峰期自动禁用 Agentic 模式，全部走简单 RAG；低置信度的 Agent 决策强制人工审核。监控指标：平均迭代次数（应 <3）、P99 延迟（应 <5s）、fallback 比例（应 <10%）。某企业的经验：设置 max_iterations=3 后，成本降低 60%，质量仅下降 2%。
