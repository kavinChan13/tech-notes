工具调用安全威胁全景

Function Calling 和 MCP 赋予了 LLM 与外部系统交互的能力

Function Calling 和 MCP 赋予了 LLM 与外部系统交互的能力。这既是 Agent 的核心能力，也是最大的安全风险点——一旦被攻破，攻击者可以直接操控真实世界的系统。

核心原则：永远不要信任 LLM 的工具调用决策。LLM 是概率模型，不是安全边界——它的每一个工具调用请求都必须经过独立的权限校验、参数验证和安全审计。

六大威胁类型

工具注入Prompt 注入诱导调用恶意工具极高外部系统被操纵

权限提升调用超出授权范围的工具高越权操作、数据泄露
供应链攻击MCP Server / 第三方工具被篡改极高整个 Agent 系统被控制
资源滥用诱导高频调用昂贵工具中成本失控、服务降级

沙箱执行与隔离

工具调用必须在沙箱环境中运行，尤其是涉及代码执行、文件操作、网络请求的工具。

3.1 沙箱类型选择

沙箱类型隔离级别适用场景性能开销推荐场景
进程沙箱中代码执行、脚本低轻量任务

沙箱执行生命周期

④ 执行工具（在沙箱内运行）
⑤ 输出验证
结果格式与安全检查

3.3 沙箱配置清单

配置项推荐值说明
网络策略DENY_ALL + 白名单默认禁止，按需放行
文件系统readonly + 路径限制只读 + 限定目录
权限no-new-privileges禁止提权
系统调用seccomp restricted限制系统调用
超时按工具类型配置防止长时间阻塞
核心原则：默认拒绝一切，显式允许必要。网络默认禁止、文件系统默认只读、系统调用默认限制、权限默认最低。每一个"放开"都需要明确的安全评审理由。

注入类型目标工具攻击载荷示例后果

4.2 六层参数校验流水线

参数校验流水线
LLM 输出参数
第1层：类型校验 int? string? 类型不匹配直接拒绝
第2层：范围校验 数值在 [min, max] 内？字符串长度合理？

工具类型注入特征检测策略
SQL 工具'; -- UNION DROP INSERT DELETESQL 关键词 + 特殊字符
Shell 工具; | & ` $( ../管道符 + 命令分隔符
文件工具../ \ \x00路径遍历 + 空字节
HTTP 工具内网 IP / metadata 端点SSRF 目标检测

  • 每个参数定义严格 Schema

  • 信任 LLM 生成的参数
  • 只用黑名单过滤（总有绕过）
  • 所有工具共用一套校验规则
  • 静默忽略校验失败

完整的审计是安全事件的"黑匣子"——事后追溯 + 日常异常检测。

信息层记录内容用途

5.2 六类异常模式检测

异常模式检测方法告警级别响应动作
高频调用单位时间调用超阈值中限流 + 告警
权限异常调用未授权 / 越权高拒绝 + 审计
参数异常注入检测触发高拒绝 + 审计
行为偏离偏离正常调用基线中告警 + 人工审查
链式升级只读→写入快速切换高暂停 + 确认

5.3 危险操作风险分级

风险等级操作类型处理方式附加要求
低查询类 (read)自动执行—
中创建类 (create)记录日志后执行—
高修改类 (update)展示详情，用户确认展示操作影响
极高删除 / 发送 / 支付二次确认MFA + 不可逆警告
LLM 可以建议操作，但不能自主执行高风险操作。关键原则：确认信息必须展示操作详情和潜在影响，让用户做出知情决策。

纵深防御体系总结

工具调用安全纵深防御四层架构
第1层：工具注册安全
MCP Server 认证（OAuth + mTLS） · 工具白名单（只允许已审核的工具） · 最小权限（动态工具集，按需授权） · 工具签名验证（防止工具链投毒）
第2层：调用决策安全
权限校验（RBAC + ABAC，角色 + 场景） · 参数校验（白名单 Schema + 注入检测） · 频率限制（防止资源滥用） · 危险操作门控（高风险需人工确认）
第3层：执行环境安全
沙箱隔离（容器 / WASM / VM） · 网络策略（默认禁止，白名单放行） · 文件系统（只读 + 路径限制） · 资源限制（CPU / 内存 / 超时）
第4层：运营安全
完整审计日志（调用链路全程记录） · 异常检测（行为基线 + 模式识别） · 实时监控告警 · 安全事件响应 SOP
安全层核心控制关键方法防御目标
工具注册信任边界管控OAuth / mTLS / 白名单 / 签名只允许可信工具
调用决策权限 + 参数校验RBAC / ABAC / Schema / 注入检测只允许合法调用
执行环境沙箱隔离容器 / WASM / 网络策略限制爆炸半径
运营监控审计 + 告警链路日志 / 异常检测 / SOP发现 + 响应

Q&A

FC 是 LLM 内置的工具调用机制，安全边界在应用层（参数校验、权限检查）
FC 和 MCP 工具调用的安全区别是什么？

FC 是 LLM 内置的工具调用机制，安全边界在应用层（参数校验、权限检查）。MCP 引入了独立的 Server 概念，安全挑战更复杂：①Server 身份认证（OAuth/mTLS）；②供应链攻击风险（第三方 Server）；③通信安全（加密+签名）；④能力管理（Server 声明需安全消费）。MCP 的攻击面比 FC 更大，因为引入了独立的信任边界。

如何防止 LLM 被诱导调用危险工具？

多层防御：①工具集最小化——根据任务和角色动态提供最小工具集；②权限校验——每次调用独立校验，不信任 LLM 的决策；③参数校验——白名单 Schema + 注入检测；④危险操作门控——高风险操作必须人工确认；⑤行为监控——检测异常调用模式（如从只读快速升级到写入）。核心原则：LLM 的决策只是"建议"，不是"授权"。

MCP Server 的供应链安全如何保障？

六项措施：①Server 白名单——只允许审核过的 Server 接入；②签名验证——发布时签名，加载时验证完整性；③能力声明审核——安全团队审核 Server 声明的能力；④版本管理——更新时安全扫描+回归测试；⑤运行时监控——实际行为与声明一致；⑥隔离执行——每个 Server 在独立沙箱运行。类比 npm/Docker 供应链安全——信任但验证。

沙箱执行如何设计？

核心原则"默认拒绝一切，显式允许必要"：①隔离级别——代码执行用容器，轻量工具用 WASM，不可信代码用 VM；②网络——默认禁止，白名单放行；③文件系统——默认只读，写入限指定目录；④资源限制——CPU/内存/超时设上限；⑤权限最小化——no-new-privileges + seccomp；⑥生命周期——每次创建新沙箱，用完销毁。生产推荐容器沙箱（Docker/gVisor）。

如何审计 Agent 的工具调用链路？

记录四层信息：①用户层（who + session）；②推理层（LLM reasoning + Prompt 上下文）；③调用层（工具名、参数、结果、耗时）；④安全层（权限检查、参数验证、异常分数）。审计日志必须不可篡改（append-only + 哈希链）。异常检测：建立行为基线，检测偏离（高频调用、参数异常、链式升级）。关键：审计不仅事后追溯，也要实时告警。
