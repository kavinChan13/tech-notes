01

为什么需要 Tokenization

神经网络只能处理数值张量，无法直接理解自然语言文本

文本 → 数字

神经网络只能处理数值张量，无法直接理解自然语言文本。Tokenization 的核心任务就是将原始文本拆分成离散的 token，再通过词表（vocabulary）映射为整数 ID，最终送入 Embedding 层转化为稠密向量。

"今天天气真好" → ["今天", "天气", "真", "好"] → [2456, 1893, 517, 382] → Embedding

词表大小与模型效率的权衡

词表大小优势劣势
过小（如 8K）Embedding 参数量小、训练快长文本需要更多 token，增加序列长度；罕见词被拆得碎
过大（如 256K）每个 token 承载更多语义，序列更短Embedding 层参数暴涨；低频 token 训练不充分
适中（32K–128K）在压缩率与参数效率间取得平衡，主流 LLM 选择此区间

OOV（Out-of-Vocabulary）问题

传统基于空格 / 词典的分词在遇到未登录词（如专业术语、新造词、拼写错误）时只能映射为 [UNK]，丢失信息。子词（Subword）方法通过将单词拆分成更小的有意义片段，从根本上解决了 OOV 问题——任何单词都能由子词组合而成。

  • 核心理解：Tokenization 是文本与模型之间的桥梁，决定了模型"看到"什么
  • 权衡意识：词表大小直接影响 Embedding 参数量（vocab_size × hidden_dim）和序列长度
  • OOV 方案：子词分词（BPE / WordPiece / Unigram）是当前主流解决方案
  • 压缩率：好的 Tokenizer 能用更少 token 表示相同文本，提高推理效率
02

BPE (Byte Pair Encoding)

# BPE 合并示例 初始: l o w </w> (出现 5 次) l o w e r <…

算法流程

  1. 初始化：将训练语料中的每个单词拆分为字符序列，加入词尾标记（如 </w>）
  2. 统计：统计所有相邻字符对（bigram）的出现频率
  3. 合并：将频率最高的字符对合并为新符号，加入词表
  4. 重复：重复步骤 2-3，直到达到预设词表大小
# BPE 合并示例
初始:  l o w </w>   (出现 5 次)
       l o w e r </w> (出现 2 次)
       n e w e s t </w> (出现 6 次)

第1轮: 最高频对 (e, s) → 合并为 "es"
第2轮: 最高频对 (es, t) → 合并为 "est"
第3轮: 最高频对 (l, o) → 合并为 "lo"
...逐步构建子词词表

GPT 系列使用的 BPE

GPT-2 / GPT-3 / GPT-4 均使用 BPE。GPT-2 引入了 Byte-level BPE：以字节（256 个基础 token）而非 Unicode 字符为初始单元，好处是无需预处理、不会出现 [UNK]，任何文本都能被编码。

Byte-level BPE 的优势

  • 完全无 OOV：任何字节序列都可表示，包括非文本数据
  • 语言无关：不依赖特定语言的字符集定义
  • 简洁：基础词表仅 256 个字节 token + 合并产生的子词

GPT-2 使用 ~50K 词表，GPT-4（cl100k_base）使用 ~100K 词表，大幅提升了多语言和代码的压缩效率。

  • BPE 核心：贪心地合并频率最高的相邻对，自底向上构建词表
  • Byte-level BPE：以字节为基本单元，256 个初始 token 即可覆盖一切输入
  • GPT 系列：GPT-2 起使用 Byte-level BPE，是当前最流行的分词方案之一
  • 合并规则文件：merges.txt 记录合并顺序，推理时按此顺序执行

WordPiece

WordPiece 由 Google 提出，算法结构与 BPE 类似， 关键区别在于合并策略…

WordPiece vs BPE

WordPiece 由 Google 提出，算法结构与 BPE 类似，关键区别在于合并策略：

特性BPEWordPiece
合并依据频率最高的相邻对使语言模型似然（likelihood）增加最大的相邻对
合并公式count(AB)count(AB) / (count(A) × count(B))
直觉哪对出现最多就合并合并后对语言建模收益最大
代表模型GPT 系列BERT / DistilBERT / ELECTRA
WordPiece Score = log P(AB) − log P(A) − log P(B) ≈ PMI(A, B)

## 前缀标记

WordPiece 使用 ## 前缀来标记非首位子词（即续接片段），帮助区分一个 token 是词的开头还是中间部分：

"unbelievable" → ["un", "##believ", "##able"]
"playing"      → ["play", "##ing"]

## 前缀含义：这个子词不是一个新词的开始，而是前一个 token 的延续

BERT 的 WordPiece 实现

  • 词表大小：30,522（BERT-base）
  • 包含特殊 token：[PAD], [UNK], [CLS], [SEP], [MASK]
  • 先做 BasicTokenizer（分词、大小写处理、标点分离），再用 WordPiece 细分
  • 核心区别：BPE 按频率合并，WordPiece 按语言模型似然（近似互信息 PMI）合并
  • ## 前缀：标记续接子词，区分词首和词中位置
  • BERT 绑定：WordPiece 几乎与 BERT 系列绑定使用，其他框架较少采用
  • 编码方向：WordPiece 推理时使用最长匹配（longest-match-first），与 BPE 的合并顺序不同

Unigram (SentencePiece)

与 BPE / WordPiece 自底向上 合并不同，Unigram 采用 自顶向下 的策…

基于概率的分词

与 BPE / WordPiece 自底向上合并不同，Unigram 采用自顶向下的策略：从一个大词表开始，逐步移除对整体似然损失最小的 token。

算法流程

  1. 初始化：构建一个足够大的候选词表（如所有常见子串，通常为目标大小的 10-20 倍）
  2. 期望最大化（EM）：对每个句子，用 Viterbi 算法找到当前词表下的最优分词方案
  3. 计算损失：对每个 token，计算若将其从词表中移除后整体似然的下降幅度
  4. 裁剪：移除损失最小的一批 token（通常移除 10-20%）
  5. 重复：重复步骤 2-4，直到词表缩小到目标大小
P(x) = Π P(xᵢ) → 最优分词 x* = arg max Σ log P(xᵢ)

Unigram 的独特优势

  • 概率建模：每个 token 有明确的概率值，可以给出多种分词方案及其概率
  • 正则化效果：训练时可随机采样次优分词方案（Subword Regularization），增强鲁棒性
  • 确定性解码：推理时用 Viterbi 找到最优唯一解

使用 Unigram 的主流模型

  • 方向差异：BPE/WordPiece 自底向上合并，Unigram 自顶向下裁剪
  • 概率模型：Unigram 为每个 token 赋予概率，支持多种分词方案采样
  • Subword Regularization：训练时随机采样分词方案，类似 Dropout 的正则化效果
  • LLaMA 使用：LLaMA 使用 SentencePiece 的 Unigram 模式，词表 32K

SentencePiece 工具

SentencePiece 是 Google 开源的 语言无关 分词工具，它不是一种新的分词…

SentencePiece 是什么

SentencePiece 是 Google 开源的语言无关分词工具，它不是一种新的分词算法，而是一个同时支持 BPE 和 Unigram 的实现框架。

核心设计理念

  • 直接处理原始文本：不依赖预分词（pre-tokenization），将输入视为 Unicode 字符的原始流
  • 空格视为普通字符：使用 ▁（U+2581）替换空格，使空格成为词表的一部分
  • 语言无关：不需要针对特定语言的分词规则，对中文、日文、韩文等天然友好
  • 可逆解码：编码后可完全还原原始文本，包括空格位置
# SentencePiece 处理空格
"Hello World" → ["▁Hello", "▁World"]
"你好世界"    → ["▁", "你好", "世界"]

# ▁ 标记表示"这个 token 前面有空格"

SentencePiece vs HuggingFace Tokenizers

特性SentencePieceHuggingFace Tokenizers
实现语言C++Rust
预分词不需要通常需要（可配置）
支持算法BPE、UnigramBPE、WordPiece、Unigram
空格处理▁ 替换取决于具体实现
模型文件.model + .vocabtokenizer.json
训练数据格式原始文本文件灵活（文件/迭代器）

两者的关系

HuggingFace Transformers 库可以同时加载两种格式的 tokenizer。许多模型（如 LLaMA）底层使用 SentencePiece 训练，但通过 HuggingFace 的转换工具可以导出为 tokenizer.json 格式，享受 Rust 的速度优势。

  • 框架 vs 算法：SentencePiece 是工具框架，支持 BPE 和 Unigram 两种算法
  • 语言无关：直接处理原始字节流，不需要预分词，对中日韩等语言友好
  • ▁ 符号：用 ▁ 替换空格，保证编码-解码可逆
  • 互操作：SentencePiece 模型可转换为 HuggingFace tokenizer.json 格式

中文分词的挑战

中文没有天然的空格分隔符，这对 Tokenizer 带来独特挑战：

字级 vs 词级 vs 子词级

粒度示例优势劣势
字级（Char）["今", "天", "天", "气", "真", "好"]词表小、无 OOV序列长、缺少语义单元
词级（Word）["今天", "天气", "真好"]语义完整依赖分词工具、OOV 严重
子词级（Subword）["今天", "天气", "真", "好"]兼顾压缩率与覆盖率需要大规模语料训练

中文 BPE 的特殊处理

中文没有天然的空格分隔符，这对 Tokenizer 带来独特挑战：

  • 预分词策略：GPT 系列对中文使用正则表达式将每个汉字字符单独分开，再进行 BPE 合并
  • Byte-level 处理：一个中文字符 UTF-8 编码为 3 个字节，未合并时需要 3 个 token（效率低）
  • 字符级初始化：许多中文 LLM 在 BPE 训练前，先将常见汉字加入基础词表
# GPT-2 对中文的低效编码
"你好" → [20046, 254, 25001, 121]  # 4 个 token！

# 中文优化后的模型（如 ChatGLM）
"你好" → [36474]  # 1 个 token

多语言词表设计

  • 语料配比：中文/英文/代码/其他语言的训练数据比例直接影响各语言的压缩率
  • 词表分配：需要在不同语言间合理分配词表容量
  • 效率指标：用 fertility（平均每个词产生的 token 数）衡量不同语言的编码效率
  • 实践案例：LLaMA 词表对中文 fertility 约 2-3，ChatGLM / Qwen 优化后接近 1.5
  • 中文无空格：中文没有天然分词边界，子词方法需要特殊的预分词策略
  • 编码效率：未优化的英文词表对中文编码效率极低（1 汉字 → 2-3 tokens）
  • fertility 指标：衡量 Tokenizer 对特定语言的编码效率，越低越好
  • 词表扩展：在英文预训练模型上做中文微调前，常需扩展中文词表以提升效率

Vocabulary 设计

对于 LLM，Embedding 参数通常占总参数的 2-8%

词表大小选择

词表对模型性能的影响

  • 序列压缩：更大的词表 → 更短的序列 → Attention 计算量减少（O(n²) 中 n 更小）
  • 上下文容量：同样的 context window，更短的序列意味着能"装下"更多文本
  • 推理速度：每个 token 需要一次前向传播（自回归），更少的 token = 更快的生成
  • 但：词表过大会导致低频 token 欠训练，softmax 计算变慢

Embedding 层参数量

Embedding 参数 = vocab_size × hidden_dim
配置vocab_sizehidden_dimEmbedding 参数量
BERT-base30,522768~23M
LLaMA-7B32,0004,096~131M
LLaMA-3-8B128,2564,096~525M

对于 LLM，Embedding 参数通常占总参数的 2-8%。注意 LM Head（输出层）通常与 Embedding 共享权重（tied embeddings），不增加额外参数。

  • 词表趋势：主流 LLM 词表从 32K 逐步增长到 128K-152K，以提升多语言效率
  • 参数公式：Embedding 参数 = vocab_size × hidden_dim，词表翻倍则参数翻倍
  • 权重共享：大多数模型的 Embedding 和 LM Head 共享权重（tied embeddings）
  • 序列长度：更大词表→更短序列→节省 Attention 计算和 KV Cache 空间

Chat 模板与特殊 Token

Chat 模型使用特殊 token 来标记对话结构，区分系统指令、用户消息和助手回复：

# ChatML 格式（Qwen / 许多 Chat 模型使用）
<|im_start|>system
你是一个有用的助手。<|im_end|>
<|im_start|>user
你好！<|im_end|>
<|im_start|>assistant
你好！有什么我能帮你的？<|im_end|>

# LLaMA-2 Chat 格式
<s>[INST] <<SYS>>
You are a helpful assistant.
<</SYS>>

Hello! [/INST] Hi! How can I help? </s>

# LLaMA-3 使用的新格式
<|begin_of_text|><|start_header_id|>system<|end_header_id|>
...

为什么 Chat 模板很重要

  • 训练一致性：推理时的模板必须与训练时完全一致，否则性能严重下降
  • 角色区分：模型通过特殊 token 理解"谁在说话"
  • 安全边界：系统消息的特殊标记帮助模型区分指令和用户输入（防注入）
  • HuggingFace 支持：tokenizer.apply_chat_template() 自动处理模板格式
  • [CLS] 作用：BERT 中 [CLS] 的最终隐藏状态作为整个句子的表示，用于分类
  • EOS 触发停止：自回归生成中，模型输出 EOS token 时停止解码
  • Chat 模板一致性：推理时必须使用与训练完全相同的模板格式
  • ChatML：<|im_start|>/<|im_end|> 是被广泛采用的 Chat 标记格式

Tokenizer 实践

HuggingFace 提供了两种 Tokenizer 实现：

HuggingFace tokenizers 库

HuggingFace 提供了两种 Tokenizer 实现：

  • Python Tokenizer：纯 Python 实现，方便调试但速度慢
  • Fast Tokenizer：基于 Rust 的 tokenizers 库，速度快 10-100 倍，推荐使用
# 判断是否为 Fast Tokenizer
from transformers import AutoTokenizer
tokenizer = AutoTokenizer.from_pretrained("bert-base-uncased")
print(tokenizer.is_fast)  # True → 使用的是 Fast Tokenizer

tokenize → encode → decode 流程

from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("bert-base-uncased")
text = "Tokenization is important for NLP!"

# Step 1: tokenize — 文本 → token 列表（字符串形式）
tokens = tokenizer.tokenize(text)
# ['token', '##ization', 'is', 'important', 'for', 'nl', '##p', '!']

# Step 2: encode — 文本 → token ID 列表（整数形式，含特殊 token）
ids = tokenizer.encode(text)
# [101, 19204, 3989, 2003, 2590, 2005, 17953, 2361, 999, 102]
#  ↑CLS                                                    ↑SEP

# Step 3: decode — token IDs → 文本
decoded = tokenizer.decode(ids)
# '[CLS] tokenization is important for nlp! [SEP]'

# 更常用的 __call__ 方法（一步到位）
encoding = tokenizer(text, return_tensors="pt")
# encoding.input_ids      → tensor([[101, 19204, ...]])
# encoding.attention_mask → tensor([[1, 1, 1, ...]])
# encoding.token_type_ids → tensor([[0, 0, 0, ...]])

Fast Tokenizer 特有功能

# offset_mapping: 每个 token 对应原文的字符位置
encoding = tokenizer(text, return_offsets_mapping=True)
for token, (start, end) in zip(tokens, encoding.offset_mapping[1:-1]):
    print(f"{token:15s} → '{text[start:end]}'")

# word_ids: 每个 token 对应的原始词索引（NER 任务常用）
word_ids = encoding.word_ids()
# [None, 0, 0, 1, 2, 3, 4, 4, 5, None]
# None 对应特殊 token，相同数字表示属于同一个词

训练自定义 Tokenizer

from tokenizers import Tokenizer, models, trainers, pre_tokenizers

# 创建 BPE tokenizer
tokenizer = Tokenizer(models.BPE())
tokenizer.pre_tokenizer = pre_tokenizers.ByteLevel()

trainer = trainers.BpeTrainer(
    vocab_size=32000,
    special_tokens=["<pad>", "<unk>", "<bos>", "<eos>"]
)

tokenizer.train(files=["corpus.txt"], trainer=trainer)
tokenizer.save("my_tokenizer.json")
  • 三步流程：tokenize（文本→token 字符串）→ encode（加特殊 token，转 ID）→ decode（ID→文本）
  • Fast Tokenizer：基于 Rust，支持 offset_mapping / word_ids 等高级功能
  • __call__：实际使用中最常调用 tokenizer(text)，一步返回 input_ids + attention_mask
  • 自定义训练：用 tokenizers 库可快速训练 BPE / WordPiece / Unigram Tokenizer

🎯 Q&A（Top 10）

合并策略不同 ：BPE 每次合并 频率最高 的相邻 token 对
Q1: BPE 和 WordPiece 的核心区别是什么？

合并策略不同：BPE 每次合并频率最高的相邻 token 对；WordPiece 每次合并使语言模型似然增加最大的相邻对（近似于互信息 PMI）。

直觉上，BPE 关注"哪对出现最多"，WordPiece 关注"哪对合并后对语言建模帮助最大"。实践中，BPE 被 GPT 系列采用，WordPiece 被 BERT 系列采用。两者效果差异不大，但 BPE 更流行。

Q2: 为什么 GPT-2 选择 Byte-level BPE？

Byte-level BPE 以 256 个字节为基础词表，好处有三：

  • 完全消除 OOV：任何文本甚至二进制数据都能编码，不需要 [UNK]
  • 语言无关：不需要针对特定语言设计字符集
  • 简洁统一：基础词表仅 256 个 token，合并规则决定最终词表

代价是对非 ASCII 语言（如中文），初始编码效率较低（1 汉字 = 3 字节 = 可能 3 个初始 token），但通过足够的合并步骤可以缓解。

Q3: Unigram 与 BPE 的方向为什么相反？各有什么优劣？

BPE 自底向上：从字符开始逐步合并，简单高效，但合并顺序是贪心的，可能不是全局最优。

Unigram 自顶向下：从大词表开始逐步裁剪，通过 EM 算法优化全局似然，理论上更优。Unigram 的独特优势是可以做 Subword Regularization——训练时随机采样次优分词方案，增强模型鲁棒性。缺点是训练速度稍慢。

Q4: SentencePiece 和 HuggingFace Tokenizers 的区别？

SentencePiece（C++ 实现）直接处理原始文本，不需要预分词，用 ▁ 替换空格，支持 BPE 和 Unigram 算法。LLaMA、T5 等模型使用。

HuggingFace Tokenizers（Rust 实现）是更灵活的框架，支持 BPE、WordPiece、Unigram，可配置预分词、后处理等 pipeline。GPT-2、BERT 等模型使用。

两者可以互操作：SentencePiece 训练的模型可以转换为 HuggingFace 的 tokenizer.json 格式，反之亦然。

Q5: 中文 Tokenization 有哪些特殊挑战？如何解决？

中文的核心挑战是没有天然的空格分隔符，且字符种类远多于英文。具体表现为：

  • 英文词表对中文编码效率低（高 fertility）
  • UTF-8 编码下一个汉字占 3 字节，Byte-level BPE 初始需要 3 个 token
  • 词级分词依赖外部工具（jieba 等），引入分词错误传播

解决方案：(1) 在词表中加入足够多的中文字符和常见词组；(2) 用大量中文语料训练 BPE，让常见汉字组合自然合并；(3) 扩大词表总量（如 Qwen 的 152K）。

Q6: 词表大小如何影响模型效率？32K vs 128K 怎么选？

更大词表的好处：

  • 更好的压缩率 → 更短的序列 → Attention 计算量减少（O(n²)）
  • 同一 context window 装更多文本 → 更强的上下文理解
  • 每次前向传播生成更多字符 → 推理更快

更大词表的代价：

  • Embedding 层参数增加（vocab_size × hidden_dim）
  • 低频 token 训练不充分，质量下降
  • Softmax 输出层计算变慢

趋势：从 32K（LLaMA）→ 128K（LLaMA-3），更大词表在多语言和代码场景的收益明显。但需要足够大的训练语料来支撑。

Q7: 什么是 Subword Regularization？为什么有用？

Subword Regularization 是 Unigram 分词的一个特性：训练时不总是使用最优分词方案，而是按概率随机采样次优分词方案。例如 "unbreakable" 可能被分为 ["un", "break", "able"] 或 ["un", "breakable"] 等不同方案。

好处：类似于 Dropout，增强模型对分词方式变化的鲁棒性，减少过拟合。BPE 后来也引入了类似思想（BPE-Dropout），在训练时随机跳过一些合并步骤。

Q8: Chat 模板（如 ChatML）为什么重要？格式不对会怎样？

Chat 模板定义了多轮对话的格式，模型在 SFT/RLHF 训练时学会了理解这种格式中的角色区分和对话边界。

格式不一致的后果：

  • 模型无法正确区分 system/user/assistant 角色
  • 可能忽略系统指令或混淆对话历史
  • 生成质量严重下降，出现格式混乱
  • 安全防护失效（依赖 system prompt 的防护被绕过）

因此使用 tokenizer.apply_chat_template() 非常重要，它确保格式与训练时一致。

Q9: Fast Tokenizer 比 Slow Tokenizer 快多少？有什么额外功能？

Fast Tokenizer 基于 Rust 实现的 tokenizers 库，通常比纯 Python 的 Slow Tokenizer 快 10-100 倍，在批量编码时差距更明显。

Fast Tokenizer 独有功能：

  • offset_mapping：每个 token 对应原文的字符起止位置，NER 等任务必需
  • word_ids()：每个 token 对应原始词的索引
  • overflow：长文本自动滑窗切分
  • 高效批量编码和并行处理

HuggingFace 默认优先加载 Fast Tokenizer；如果需要调试，可以传入 use_fast=False。

Q10: 如果要为新语言/领域训练 Tokenizer，有哪些关键决策？

训练自定义 Tokenizer 需要做以下关键决策：

  1. 算法选择：BPE（最流行，确定性强）/ Unigram（支持采样正则化）/ WordPiece（主要 BERT 生态）
  2. 词表大小：通用场景 32K-64K，多语言 128K+，需要在压缩率和参数量间权衡
  3. 训练语料：语料的覆盖面决定词表质量，需注意不同语言/领域的配比
  4. 特殊 token：根据下游任务设计，Chat 模型需要角色标记
  5. 预分词策略：是否用正则表达式预分词（GPT 风格）还是直接处理原始文本（SentencePiece 风格）
  6. Byte fallback：是否用 Byte-level 确保零 OOV

验证方法：计算目标语料的 fertility 和压缩率，与主流 Tokenizer 对比。
