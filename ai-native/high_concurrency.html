概览

高并发架构的核心思想：不是让每台服务器扛更多请求，而是让尽量多的请求在"上层"就被处理掉——…

高并发架构的核心思想：不是让每台服务器扛更多请求，而是让尽量多的请求在"上层"就被处理掉——缓存挡住 80%，限流挡住 10%，异步削平峰值，真正到达数据库的只有不到 10%。六层策略叠加，才能从 5,000 QPS 安全扩展到 500,000 QPS。

01

流量分层与多级缓存

高并发系统的第一道防线是 多级缓存 ，将请求逐层过滤，只有少量请求到达数据库

高并发系统的第一道防线是多级缓存，将请求逐层过滤，只有少量请求到达数据库。流量分层的本质是"用空间换时间"——在不同层级部署不同特性的缓存，逐级降低后端压力。

┌─────────────────────────────────────────────────────────────────┐ │ 多级缓存架构 │ ├─────────────────────────────────────────────────────────────────┤ │ │ │ 请求入口（100% 流量） │ │ │ │ │ ▼ │ │ ┌──────────────────┐ │ │ │ L0: CDN / 接入层 │ 静态资源直接返回，拦截 30%+ 请求 │ │ └──────┬───────────┘ │ │ ▼ 70% │ │ ┌──────────────────┐ │ │ │ L1: 本地缓存 │ Caffeine/Guava，命中率 60-70%，<1ms │ │ │ (进程内) │ 适合高频读低频写的热点数据 │ │ └──────┬───────────┘ │ │ ▼ 21% │ │ ┌──────────────────┐ │ │ │ L2: 分布式缓存 │ Redis Cluster，命中率 80-90%，1-5ms │ │ │ (Redis) │ 主缓存层，水平扩展 │ │ └──────┬───────────┘ │ │ ▼ 2-4% │ │ ┌──────────────────┐ │ │ │ L3: 数据库 │ MySQL/PostgreSQL，10-100ms │ │ │ (最终数据源) │ 只承受极少请求 │ │ └──────────────────┘ │ │ │ │ 最终到达 DB 的请求仅占总请求的 2-4% │ └─────────────────────────────────────────────────────────────────┘

各级缓存详细对比

层级缓存位置命中率延迟适用场景局限性
L0 CDN边缘节点90%+<10ms静态资源、API 响应缓存动态内容不适用
L1 本地应用进程内（Caffeine）60-70%<1ms高频读、低频写的热点数据多节点一致性差
L2 分布式Redis Cluster80-90%1-5ms大部分业务数据网络开销、宕机风险
L3 DBMySQL / PostgreSQL100%10-100ms最终数据源不可过载

L1 本地缓存适合"读多写少"的热点数据（如商品基本信息、配置字典），延迟极低但存在多节点不一致问题——数据变更后，其他节点的本地缓存可能还在用旧值。解决方案：设短 TTL（30 秒）+ 数据变更时通过 Redis Pub/Sub 广播清除。强一致性场景（如库存扣减）不应使用本地缓存，直接走 Redis + DB。

生产案例：某电商系统在促销期间 QPS 从 5,000 飙升到 50,000。多级缓存效果：L0 CDN 拦截 35%（静态资源），L1 Caffeine 拦截剩余流量的 65%，L2 Redis 拦截再剩余的 85%。最终到达数据库的 QPS 仅 2,500（总流量的 5%），P99 延迟从 800ms 降至 45ms。

限流算法深度对比

限流是高并发系统的"入口闸门"——控制进入系统的请求速率，防止系统被瞬时流量冲垮

限流是高并发系统的"入口闸门"——控制进入系统的请求速率，防止系统被瞬时流量冲垮。四种主流限流算法各有适用场景，选择错误的算法可能导致用户体验恶化或系统保护失效。

生产案例：某支付网关使用令牌桶限流（1000 token/s，桶容量 5000）。正常流量 800 QPS 平稳运行。双十一零点突发 12,000 QPS，桶内存量 5000 个 token 瞬间消耗（允许 5 秒 burst），同时以 1000/s 速率补充。峰值过后流量回归正常。对比固定窗口方案（1000/s 硬限），令牌桶在突发期间的用户体验好 6 倍（拒绝率从 92% 降至 58%），同时下游系统未被冲击（桶容量限制保护了后端）。

熔断与降级策略

熔断 （Circuit Breaker）是系统自我保护的最后一道防线——当下游服务故障时，自…

熔断（Circuit Breaker）是系统自我保护的最后一道防线——当下游服务故障时，自动切断请求，防止级联故障把整个系统拖垮。熔断器的核心思想来自电路保险丝：电流异常时自动断开，保护整个电路不被烧毁。

限流是"控制进入的人数"（入口保护），熔断是"发现厨房着火就关门不让进"（出口保护）。没有熔断的系统，一个下游服务超时就会导致上游所有线程被阻塞等待，最终线程池耗尽，整个服务不可用——这就是级联故障（Cascading Failure）。

降级策略

熔断触发后，需要降级策略来保证用户体验不完全中断。降级（Degradation）是在系统压力过大或依赖故障时，主动牺牲部分功能来保证核心服务可用。

降级策略做法用户体验适用场景
返回默认值使用预设的默认响应看到默认内容推荐列表、评论数
返回缓存数据使用上次成功的缓存结果看到稍旧的数据搜索结果、排行榜
功能裁剪关闭非核心功能，保障核心链路部分功能不可用大促时关闭评价功能
排队等待请求入队，异步处理看到"排队中"秒杀下单
生产案例：某电商平台在促销期间，下游评价服务因高负载 P99 延迟飙升至 8 秒。熔断器在检测到 50% 请求超时后自动进入 Open 状态，商品详情页降级为"不显示评价"（返回默认值），核心购买流程不受影响。故障持续 15 分钟后，熔断器进入 Half-Open 探测成功，自动恢复。整个过程用户感知：评价区域短暂显示"加载中"后消失，购买完全不受影响。

异步削峰与消息队列

高并发写场景（如秒杀下单、日志收集）的核心策略是 异步化 ：用户请求先写入消息队列立即返回"…

高并发写场景（如秒杀下单、日志收集）的核心策略是异步化：用户请求先写入消息队列立即返回"排队中"，后台消费者按自身能力匀速处理。这样瞬时 10 万 QPS 被削平为持续 1,000 QPS 的稳定处理。

┌───────────────────────────────────────────────────────────────┐ │ 异步削峰架构 │ ├───────────────────────────────────────────────────────────────┤ │ │ │ 用户请求（峰值 100,000 QPS） │ │ │ │ │ ▼ │ │ ┌────────────────────┐ │ │ │ 接入层：快速应答 │ → 立即返回"排队中，预计 30 秒" │ │ │ (写入 MQ + 返回) │ │ │ └──────┬─────────────┘ │ │ │ │ │ ▼ │ │ ┌────────────────────┐ │ │ │ 消息队列 │ Kafka / RocketMQ │ │ │ (削峰缓冲区) │ 堆积能力: 百万级消息 │ │ │ │ 持久化: 磁盘顺序写 │ │ └──────┬─────────────┘ │ │ │ │ │ ▼ │ │ ┌────────────────────┐ │ │ │ 消费者集群 │ 按自身能力匀速消费 │ │ │ (1,000 QPS) │ 自动扩容: 积压 > 阈值时加实例 │ │ └──────┬─────────────┘ │ │ │ │ │ ▼ │ │ ┌────────────────────┐ │ │ │ 数据库写入 │ 匀速写入，不承受峰值冲击 │ │ │ + 通知用户"完成" │ WebSocket / 轮询推送结果 │ │ └────────────────────┘ │ └───────────────────────────────────────────────────────────────┘

消息队列的核心价值是"时间换空间"——把瞬时的处理压力分散到一段时间内匀速消化。就像餐厅高峰期，服务员记下所有订单（写入队列）后告诉客人"请稍等"，后厨按自己的节奏一道一道做（匀速消费），而不是 100 个客人同时冲进厨房催菜。

生产案例：某电商秒杀活动，零点瞬间 10 万用户同时下单。直接同步处理：DB 瞬间收到 10 万 QPS 写入，连接池 200 个连接全部阻塞，95% 请求超时失败。异步削峰后：用户点击"立即抢购" → 写入 RocketMQ → 返回"抢购中"（< 50ms）；消费者集群以 2,000 QPS 匀速处理下单逻辑；约 50 秒后全部订单处理完毕。用户体验：点击后 1-2 秒收到"抢购成功"通知，全程无超时。
  • 消息持久化 + 至少一次投递保证
  • 消费者支持幂等处理（同一消息多次消费结果一致）
  • 设置消息 TTL 防止无限堆积
  • 监控队列积压量，超阈值自动扩容消费者
  • 死信队列处理消费失败的消息
  • 消费者不做幂等（网络抖动导致重复消费）
  • 不监控队列积压（积压过多可能导致磁盘满）
  • 消息体过大（应存引用而非完整数据）
  • 忽略消费延迟（延迟过高说明消费能力不足）
  • 使用消息队列做实时性要求极高的场景

分布式锁与并发控制

在高并发场景下，多个服务实例同时操作共享资源时，需要 分布式锁 （Distributed L…

在高并发场景下，多个服务实例同时操作共享资源时，需要分布式锁（Distributed Lock）来保证同一时刻只有一个实例能执行临界区代码。与单机锁的区别在于：分布式锁需要跨进程、跨节点协调。

分布式锁的核心挑战是 CAP 定理的取舍——你不可能同时获得强一致性、高可用性和分区容错性。Redis 锁（RedLock）偏向 AP（高可用 + 分区容错），ZooKeeper 锁偏向 CP（强一致 + 分区容错）。选哪种取决于"宁可重复执行"还是"宁可等待"。

RedLock5 个 Redis 节点多数派投票较强一致⭐⭐ 中（网络往返 × 5）高价值操作（如库存扣减）

高并发数据库优化

数据库是高并发系统中最脆弱的环节——前面所有策略（缓存、限流、异步）的目的都是尽量不让请求到…

数据库是高并发系统中最脆弱的环节——前面所有策略（缓存、限流、异步）的目的都是尽量不让请求到达数据库。但当请求必须到达数据库时（如写操作、缓存未命中），需要从多个层面优化数据库的承受能力。

Q&A

本地缓存和分布式缓存的数据不一致怎么处理？
两种策略：一是设置短过期时间（如本地缓存 30 秒过期，分布式缓存 5 分钟过期），用时间换一致性；二是数据变更时通过 Redis Pub/Sub 或消息队列广播通知所有节点清除本地缓存，实现准实时一致。强一致性场景（如库存扣减、余额变更）不应使用本地缓存，直接走分布式缓存 + 数据库。一个实用建议：本地缓存只用于"变化频率低 + 读取频率极高 + 容忍短暂不一致"的数据，如系统配置、商品分类等。
令牌桶和滑动窗口限流怎么选？
如果需要允许短时突发（如 API 调用允许偶尔 burst），用令牌桶——用户体验更好，不会因为一秒内多发了一个请求就被拒绝。如果需要严格平滑限流（如保护下游数据库不被突发冲垮），用滑动窗口。大多数 Web 服务推荐令牌桶（对用户友好），大多数基础设施保护推荐滑动窗口（对系统安全）。实际生产中两者可以组合使用：网关层用令牌桶做粗限流，服务层用滑动窗口做精限流。
熔断器的 Half-Open 状态怎么探测？具体参数怎么设？
熔断器进入 Open 状态后，设定一个探测间隔（推荐 30 秒）。间隔到达后切换到 Half-Open，放行 1-3 个请求探测下游。如果探测成功，切换到 Closed 恢复正常；如果探测失败，回到 Open 继续等待下一个探测间隔。Hystrix 和 Sentinel 等框架都内置了这个机制。关键参数：探测间隔 30s（太短下游没恢复，太长影响可用性）、探测请求数 1-3（太多给下游增加压力）、失败率阈值 50%（基于最近 20 次请求的统计窗口）。
消息队列积压了怎么办？
三种处理方式：一是扩容消费者（增加消费者实例数），最直接的解法；二是降级非核心消息（如日志消息暂时丢弃，优先处理订单消息），通过消息优先级实现；三是设置消息 TTL（超时未处理的消息自动丢弃或转入死信队列）。监控队列积压量是关键指标——积压 > 10,000 条应触发告警。长期方案：分析消费慢的根因（是消费者能力不足，还是消息处理逻辑太重），考虑消费者并行化（单实例多线程消费）或异步化处理。
分布式锁用 Redis 还是 ZooKeeper？
取决于对一致性的要求。Redis SETNX 适合大部分业务场景（性能好，ms 级延迟），但在 Redis 主从切换的极端情况下可能丢锁（主节点写入后还没来得及复制到从节点就挂了）。ZooKeeper 基于 ZAB 协议保证强一致性，不会出现丢锁，但性能较低（每次操作需要多数派确认，延迟 10-50ms）。实用建议：库存扣减等高价值操作用 RedLock（5 节点多数派）；一般业务用 Redis SETNX + 看门狗续期；对一致性要求极高的金融场景用 ZooKeeper。
什么时候该分库分表？分片键怎么选？
分库分表的触发条件：单表数据量 > 500 万行，或单表 QPS > 5,000，或单库磁盘使用率 > 70%。分片键选择原则：①选择查询条件中最常用的字段（如用户系统选 user_id）；②保证数据分布均匀（避免热点分片）；③尽量减少跨分片查询。典型方案：用户系统按 user_id % N 分片，订单系统按 user_id 分片（保证同一用户的订单在同一个分片），商品系统按 product_id 分片。跨分片查询（如搜索、统计）走 Elasticsearch 或专门的聚合库。
高并发下如何设计缓存预热方案？
缓存预热是防止"冷启动"导致缓存雪崩的关键措施。三种预热方案：①服务启动时主动加载热点数据——通过离线分析前一天的访问日志，识别 Top 10,000 热点 key，启动时批量加载到 Redis；②定时刷新——每 N 分钟检查热点数据是否即将过期，提前异步刷新（避免过期瞬间的击穿）；③渐进式预热——新实例启动时不立即接入全量流量，先接入 10% 流量让缓存逐步填充，10 分钟后升至 100%。生产建议：大促前 30 分钟执行全量预热，日常每 4 小时刷新一次热点数据。
