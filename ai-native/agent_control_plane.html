AI 控制平面：Agent 失控后谁来踩刹车？

AI Control Plane — 五大核心能力构建企业级 AI 治理基础设施，从"事后报告"到"毫秒级前置拦截"

AI 工程 阅读 ~10 min 10 章
00

概览

随着 AI 系统从简单对话框进化为自主运行智能体集群，传统点对点管理彻底失效

随着 AI 系统从简单对话框进化为自主运行智能体集群，传统点对点管理彻底失效。需要在基础设施层面建立 AI 控制平面，用交通指挥中心的思维来治理 AI 军队。三大支柱：可观测性（知道在做什么）+ 控制能力（能干预行为）+ 回滚机制（出错能恢复）。

01

五大核心能力总览

AI 控制平面五大能力
1 · 精细访问控制 精确到每个工具的调用权限
2 · 身份认证 将真实用户身份注入每次 AI 请求 · 3 · 全量可观测性 完整记录每次调用的来龙去脉 · 4 · 成本治理 Token 预算 + 超支前拦截 · 5 · 数据主权 敏感数据始终在企业内部处理
能力核心职责不做会怎样优先级
精细访问控制精确到每个工具的调用权限Agent 调用危险工具（删库、发邮件）P0
身份认证真实用户身份注入每次请求无法追溯谁触发了什么操作P0
全量可观测性完整记录调用来龙去脉出问题无法定位根因P1
成本治理Token 预算 + 超支拦截一次死循环烧掉 $10,000P0
数据主权敏感数据内部处理违反 GDPR / 等保合规P0
治理理念的根本转变：从"事后报告"到"毫秒级前置拦截"。成本控制不再是月底看账单，而是执行前估算 Token 成本，超预算直接拦截。

灵活性低（角色固定）高（动态属性）中等

03

身份认证与持证上岗

Agent 不是匿名进程——它代表某个用户在执行操作

为什么每个 Agent 必须"持证上岗"？

Agent 不是匿名进程——它代表某个用户在执行操作。如果 Agent 删了数据库，必须能追溯到是谁触发的、什么时间、什么权限。

身份注入架构

层级身份来源注入方式验证时机
用户层SSO / OAuth2 / LDAPJWT Token 注入请求头每次请求
Agent 层Agent ID + 版本号X-Agent-ID 头每次工具调用
会话层Session ID + 父 Agent IDX-Session-ID 头会话创建时
身份传递链路
用户登录 (SSO) → JWT Token
Agent 启动 → 携带 user_id + agent_id + session_id
Agent 调用工具 → 控制平面验证:
user_id 是否有权限调用此工具？ · agent_id 是否在白名单中？ · session_id 是否有效（未过期）？
审计日志记录: user_id + agent_id + tool + timestamp + result

多 Agent 协作的身份传递

当主 Agent 派发子 Agent 时，身份链不能断：

  • 主 Agent 携带 user_id + agent_id
  • 子 Agent 继承 user_id + 自己的 agent_id + parent_agent_id
  • 审计日志 记录完整的调用链：user → main_agent → sub_agent → tool

成本治理与熔断机制

三级成本防线

防线时机机制效果
执行前估算Agent 发起请求时根据任务类型 + 历史数据预估 Token 成本拦截明显超预算请求
执行中监控Agent 运行过程中实时统计已消耗 Token，达到 80% 告警提前预警
执行后审计请求完成后记录实际成本 vs 预估成本，优化估算模型持续改进

熔断阈值设计

成本熔断三级阈值
Level 1: 单次请求预算
阈值: $0.50 / 请求
达到 → 拒绝执行 + 提示用户拆分任务
可覆盖: 白名单用户可申请临时提额
Level 2: 用户日预算
阈值: $50 / 用户 / 天
达到 80% → 告警用户
达到 100% → 暂停该用户所有 Agent
恢复: 次日自动重置 / 管理员手动解锁
Level 3: 系统总预算
阈值: $10,000 / 天
达到 80% → 全局限流（降低并发）
达到 100% → 紧急熔断（只允许只读操作）
恢复: 运维团队确认后方可恢复

数据主权与 PII 识别

PII 识别：多层检测机制

检测层技术覆盖类型延迟
正则匹配正则表达式手机号、身份证号、邮箱、银行卡号<1ms
NER 模型命名实体识别（小模型）姓名、地址、公司名~5ms
上下文推理大模型辅助判断隐含敏感信息（如"我的密码是..."）~50ms

PII 处理策略

策略适用场景实现方式
脱敏替换Agent 不需要原始数据138****5678 / 张*三 / 北京市***
Token 化需要保持引用一致性手机号 → TOKEN_PHONE_001，处理完再还原
本地处理数据不能出域PII 相关操作路由到本地部署的小模型
拒绝放行高敏感操作检测到密码/密钥 → 直接拒绝 + 告警

数据主权架构

数据流向控制
用户输入（含 PII）
PII 检测层
发现 PII → 脱敏 / Token 化 · 无 PII → 直接放行
数据分类器
公开数据 → 可发送到外部模型 · 内部数据 → 仅限内部模型 · 机密数据 → 仅限本地部署 · 绝密数据 → 禁止 AI 处理
路由决策
非敏感 → 外部 API（GPT/Claude）
敏感 → 内部私有模型
高敏感 → 拒绝处理
合规红线：GDPR 要求用户数据"被遗忘权"——如果 Agent 把用户数据存储到了外部模型的上下文中，用户要求删除时无法执行。解决方案：敏感数据永远不发送到外部模型，或确保外部模型不持久化数据。

为什么现有 API 网关不够用

能力传统 API 网关AI 控制平面差距
语义理解只看 HTTP 请求体理解 Prompt 语义无法判断 Prompt 是否包含危险指令
PII 识别无多层 PII 检测无法判断请求中是否有身份证号
Token 成本按请求计费按 Token 估算 + 熔断无法做执行前成本估算
递归检测看 HTTP 状态码检测 Agent 行为模式死循环时看到的只是"正常请求"
工具权限按 API 路径控制按工具粒度控制无法控制 Agent 调用哪个具体工具
结论：未来企业需要建立私有 AI 网关层，在不改动应用代码的前提下，统一管理多模型平台和 AI Agent。这不是"加一个中间件"，而是基础设施层面的升级。

关键设计决策

  • 前置拦截优于事后审计：控制平面部署在 Agent 和 LLM 之间，所有请求必须经过
  • 异步日志优于同步审计：审计日志异步写入，不影响请求延迟（增加 <5ms）
  • 渐进式熔断优于硬阈值：先限流（降低并发），再降级（只允许只读），最后熔断
  • PII 检测前置：在数据到达 LLM 之前完成脱敏，而非在输出端检测
09

Q&A

AI 控制平面和传统 API 网关有什么本质区别？
传统网关只看 HTTP 请求（URL/Header/Body），AI 控制平面需要理解 Prompt 语义。四个核心差异：(1) 语义理解 — 判断 Prompt 是否包含危险指令；(2) PII 识别 — 检测请求中的敏感信息；(3) Token 成本 — 执行前估算 + 实时熔断；(4) 递归检测 — 识别 Agent 死循环行为模式。传统网关看到的死循环只是"正常 HTTP 请求"。
成本治理的三级防线如何配合？
执行前估算 → 拦截明显超预算请求（如预估 $50 的复杂推理任务，单次预算上限 $0.50）；执行中监控 → 实时统计 Token 消耗，达到 80% 告警用户，达到 100% 强制中断；执行后审计 → 对比预估 vs 实际成本，优化估算模型。三级防线形成闭环：估算模型越准确，拦截越精准。
PII 检测为什么不能只靠正则？
正则只能匹配格式固定的 PII（手机号、身份证号），但无法识别：(1) "我的密码是 abc123" — 密码无固定格式；(2) "我的住址在 XX 小区 3 号楼" — 地址格式多变；(3) "帮我转账给张三" — 姓名需要 NER 模型识别。所以采用三层检测：正则（快，<1ms）→ NER 模型（中，~5ms）→ 大模型辅助（慢，~50ms），平衡速度和覆盖率。
为什么治理理念要从"事后报告"转为"前置拦截"？
Agent 执行速度极快，一旦失控（如递归死循环），15 分钟内可能消耗 $10,000 Token。事后报告意味着损失已经发生。毫秒级前置拦截在每次执行前检查权限、估算成本、扫描 PII，超预算直接拒绝。生产数据：前置拦截后 Token 超支事故从 5 起/月降至 0，死循环发现时间从 15 分钟缩短至 30 秒。
多 Agent 协作时，身份链怎么保证不断？
主 Agent 携带 user_id + agent_id，派发子 Agent 时，子 Agent 继承 user_id + 自己的 agent_id + parent_agent_id。控制平面在每次工具调用时验证完整身份链。审计日志记录完整调用链：user → main_agent → sub_agent → tool。如果子 Agent 做了违规操作，可以追溯到：哪个用户 → 触发了哪个主 Agent → 派发了哪个子 Agent → 调用了哪个工具。
AI 控制平面会增加多少延迟？
设计良好的控制平面增加延迟 <10ms：权限检查 ~1ms、PII 正则扫描 ~1ms、Token 预算检查 ~1ms、审计日志异步写入 ~0ms（不阻塞主路径）。只有 PII 的 NER 模型检测（~5ms）和大模型辅助判断（~50ms）会增加显著延迟，但这两层只在正则匹配不到时才触发。实际 P95 延迟增加 <8ms。
