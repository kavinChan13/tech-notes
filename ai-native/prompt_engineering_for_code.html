为什么 prompt 仍然重要（frontier 模型时代）

3 个仍然重要的原因 · 有人说"GPT-5 / Claude 5 之后 prompt 不重要了，模型够聪明"。错。

"模型够聪明了，prompt 不重要"——错。

3 个仍然重要的原因

  1. 上下文仍稀缺：窗口标称 1M token，有效 attention 远小于此。
  2. 意图歧义不可避免："加个缓存"——哪一层？什么 eviction？key 怎么定？
  3. 验证成本不变：越强的模型，错得越微妙。

❌ 模糊描述
给我写个 reconnect 逻辑，

"顺便优化一下"最贵：它会重排成员、换掉智能指针、重写注释，全要你 review。

✅ 五层齐全

见下方完整版：写它 3 分钟，省 3 轮返工。

这份是全篇的骨架，后面几节都在改写它的某一段。# 注释标出每段作用，发送时不必带：

# ── 角色 ──────────────── 定调：用哪一套工程口味来写
你是维护这个仓库三年的 C++ 系统工程师。

# ── 上下文 ────────────── 只给真正相关的事实，不要灌整个目录
项目：C++17 网络服务，boost.asio 1.83，不上 C++20。
现有类型见 @Session.hpp，错误码枚举见 @errors.hpp（均已附）。
现状：链路断开后需要人工重启进程。

# ── 目标 ──────────────── 一句话，且自带验收口径
给 Session 加自动重连：指数退避 1s → 2s → 4s，上限 60s，
成功连上后退避计数归零。

# ── 约束 ──────────────── 这一段直接决定返工次数
（与需求冲突时先提出来，不要默默绕开）
- 不改 Session 的公开 API
- 不引入新依赖，boost 与标准库以内解决
- 移动构造与析构保持 noexcept
- 重连状态会被 IO 线程和定时器线程同时访问，必须线程安全

# ── 输出格式 ──────────── 这一段决定你 review 的成本
1. 先用 5 句话讲思路，停下来等我确认
2. 我确认后，给 git diff 格式的完整补丁
3. 末尾列 3 个 GoogleTest 用例名，各自说明断言什么

# ── 兜底 ──────────────── 把不确定性逼出来，而不是让它伪装成代码
任何你不确定是否存在的 asio API，标注「待确认」并说明依据，
不要直接写进代码。

12 个实战模式

速查表 + 三个场景的完整提示词

这是一条有回灌的链路：

最容易选错的是给不给例子：

12 个模式速查

#模式触发条件 → 做法
1Spec-then-code边界没想清 → 首轮只出 spec
2Test-first纯函数 / 算法 → 用例先过
3Explain-then-edit陌生老代码 → 先复述 invariant
4Constraint-first有强规范 → 约束前置
5Chain-of-edits> 200 行 → 每步可 ship
6Few-shot风格非主流 → 附同类文件
7Critique-then-refine初版没底 → 换 reviewer 身份
8Boundary exploration怕漏 case → 当 adversary
9Cite-sourceAPI 存疑 → 标出处与版本
10Persona layer要特定口味 → 写成可检查条目
11Diff-native基于已有代码改 → 它分得清
12Bounded search候选多个 → 列全 + 评分维度

要练的是把它们组合成一份完整提示词。

场景一 · 审查与重构

风险不是改错，是没看懂就动手——把刻意保留的怪写法当技术债删掉。对策是顺序约束：

# ── 角色与口味 ─────────── 写成可检查的条目，别写「写好一点」
资深 C++ 工程师。偏好 RAII 与 unique_ptr；错误用 expected 返回，
异常只留给不可恢复的情况；单个函数不超过 40 行。

# ── 顺序约束 ───────────── 这一段是本场景的关键，放在最前
分三步走，每一步做完停下来等我确认，不要一口气做完：

  第 1 步 · 只做解释，不写任何代码
    - @legacy_dispatcher.cpp 这个类负责什么
    - 它维持了哪些不变量（invariant）
    - 哪些看起来奇怪的写法其实是有意为之，依据是什么
      （注释、命名、git blame 都可作为依据；推断请标明是推断）

  第 2 步 · 提出重构方案，仍不写实现
    - 列 2～3 个候选方案，各自说明动了什么、风险在哪
    - 给出你推荐的一个及理由

  第 3 步 · 按确认的方案出补丁
    - 拆成每步 50～100 行的独立提交，每步都能单独编译通过
    - 每步末尾说明「这一步之后哪些测试应该仍然绿」

# ── 硬约束 ─────────────── 与需求冲突时先提出，不要默默绕开
- 不改公开头文件里的任何签名
- 不引入新依赖
- 保留现有的错误码语义（见 @errors.hpp）

# ── 自检 ───────────────── 让它换一顶帽子，比让它「认真点」有效
出补丁前，切换成 reviewer 视角，从性能、并发安全、错误处理、
可测试性四个角度各挑一个自己的问题，并在补丁里修掉。
第 1 步的产出你必须真读：复述错了没发现，后两步都在错误理解上盖楼。

场景二 · 调试

质量由你给了多少可复现的事实决定：

# ── 现象 ───────────────── 可复现才叫现象，偶发要说清频率
压测到约 3000 连接时，进程在 5～10 分钟内必崩。
QPS 低于 500 时连续跑 8 小时没问题。

# ── 报错原文 ───────────── 原样贴，不要转述、不要截断
terminate called after throwing an instance of 'std::system_error'
  what():  Resource temporarily unavailable
#4  0x00005555556a1f3c in Session::onDisconnect() at session.cpp:214
#5  0x00005555556a3b81 in Reactor::dispatch() at reactor.cpp:97

# ── 最小复现 ───────────── 越小，模型的搜索空间越小
tests/repro_reconnect.cpp（已附）：单线程起 200 个 Session，
在 onDisconnect 里立即 close 再 connect，约 20 秒必现。

# ── 已经排除的 ─────────── 把你不想再听到的答案提前划掉
- 不是 fd 耗尽：ulimit -n 已调到 65536，lsof 峰值 4100
- 不是内存：RSS 稳定在 300MB，ASan 无报告
- 换成固定 1 秒重连（去掉退避）后不复现

# ── 我的猜测 ───────────── 给方向，但别让它顺着你说
怀疑是 onDisconnect 里同步调用 connect 造成的重入。
如果你认为不是，请直接反驳并说明依据。

# ── 输出格式 ───────────── 要证据，不要一份可能性清单
按可能性排序给最多 3 个假设。每个假设必须包含：
  (a) 它如何解释「低 QPS 不复现」这一点
  (b) 一个能证伪它的具体观测（打什么日志 / 看什么计数器）
先不要给修复补丁。
最后一句是重点。不写"先不要给修复补丁"，它一定会给一个合理的 patch——而根因还没确认。修没定位的 bug，只是挪个地方。

场景三 · 结构化输出

输出要进脚本、进 CI 时，"写得对"还不够，还得能被解析：

# ── 上下文（已裁剪） ───── 明确说清你给了什么、没给什么
本次改造涉及 7 个文件，按调用深度排序：
  1. src/handler/order.cpp    ← 主目标，全文已附
  2. src/handler/order.hpp    ← 全文已附
  3. include/errors.hpp       ← 只附 enum class ErrorCode 这一段
  4~7. 四个调用方             ← 只附调用 makeOrder 的那几行及上下各 3 行
仓库另有 200 多个文件与本次改造无关，请不要假设它们的内容。

# ── 任务 ───────────────── 候选给全，让它比较后再选，而不是自由发挥
把 order.cpp 中抛异常的错误路径改为返回 expected。
错误码只能从 @errors.hpp 现有 enum 中选取，不得新增。

# ── 输出格式 ───────────── 机器要读的东西，就别让它写成散文
只输出一个 JSON 对象。不要解释性文字，不要包在 markdown 代码块里。
schema：
{
  "callsites_found": 整数,
  "changes": [
    { "file": 字符串, "unified_diff": 字符串, "risk": "low" | "medium" | "high" }
  ],
  "unsure":  [ { "file": 字符串, "why": 字符串 } ]
}

# ── 兜底 ───────────────── 没有这一段，模型会用编造来填满 schema
- 拿不准该用哪个错误码 → 放进 unsure，不要挑一个填进 changes
- unified_diff 必须能被 git apply 接受；做不到就整条放进 unsure
- 若这 7 个文件不足以完成改造，只输出 unsure 说明还缺什么

10 大反模式 + 修正

以及幻觉的四种形态

#反模式为什么烂修正
1"给我写个 X"无 context / constraint补齐五层
2多任务共用 chatcontext 污染每任务新 chat
3不读 diff 就 commit编造 API / 静默 bug逐行 review + lint + test
4"简单点" / "聪明点"主观词无法 calibrate给 metric：行数 / 延迟
5不给范例默认 mainstream 风格附同类文件（模式 6）
6一次改多文件处处浅，互相不一致拆开改（模式 5）
7测试也不 review测试会迁就错代码test-first（模式 2）
8"修下 bug"，无复现只能靠猜栈 + 最小复现 + 已排除项

10编造的 API 不验证编译过但 runtime 崩标出处 + 跑测试

工具特定技巧

Cursor · Claude (Desktop / Web) · GitHub Copilot

Cursor

  • @file / @symbol / @folder——手动 select，别靠 auto-attach
  • .cursorrules——把上图第 ① 层固化进仓库
  • Apply diff 而非 copy-paste，会与本地改动 reconcile

Claude (Desktop / Web)

  • 长 context——整个 module 丢进去 explain / refactor
  • Projects——system prompt + 参考文档跨 session 复用
  • 弱项：IDE 内 multi-file 实时编辑

GitHub Copilot

  • Tab 补全最顺手，写 hot path 时几乎无感
  • @workspace 覆盖全仓库，精度不如手动 @file
  • 合规：GitHub Enterprise 集成深，有些公司只能用它
06

多轮 vs 单次

何时切新 chat

差别在错误多久被发现：

切新 chat 的信号

  • 任务语义变了（reconnect 转去做 metrics）
  • 它引用不存在的之前内容——context 已污染
  • 同样的 prompt 输出突然变差（attention 衰减）
  • 对话超过约 20 轮 / 100k token
context 污染现场：第 1 轮给 fileA，第 5 轮改 fileB，它把 fileA 的概念套了过去。不相关的任务起新 chat。
07

验证仪式（不要 vibe ship）

分层 verification · "AI-generated label"

不读 diff 就 commit 是最大的 AI 反模式。验证要做成固定动作。

分层 verification

Layer检查项成本
L1 自动Linter / formatter / type check0，CI 自跑
L2 测试现有 + 新增测试全绿分钟级
L3 静态分析clang-tidy / SAST clean分钟级
L4 SanitizerASan / TSan / UBSan分钟级
L5 人 review逐行读 diff，理解每处改动30 sec / 行
L6 同事 review常规 PR process一次 review

L5 不可跳过：Sanitizer 抓不到业务逻辑错、版本用错和安全问题，正是第 ④ 类幻觉的落点。

团队 prompt 库

实施方法 · 例：refactor-to-expected.md

要变成团队产能，得把提示词当代码管：进仓库、有版本、能比较。

实施方法

配套三件事：.prompts/ 注入 .cursorrules；月度回顾哪些高频、哪些下架；写进 onboarding。

例：refactor-to-expected.md

# Refactor Exception → std::expected

## When
重构 throwable function 到 std::expected pattern.
Codebase 倾向 expected 而非异常（hot path / 跨 ABI / 业务可预期错误）.

## Prompt template

Context: 我们 codebase 用 tl::expected (C++17) for predictable errors.
Reserve exceptions for catastrophic only (OOM / programmer bug).

Goal: 重构 @target_function.cpp 把 throw X 改成 return std::unexpected(...).

Constraints:
- API 签名变 (return type T → expected<T, ErrorCode>)
- ErrorCode 用现有 enum class（看 @errors.hpp）
- Caller 必须更新（找 callsite）
- 所有现有测试需更新断言

Output:
1. 列 callsite 数量
2. 给 patch (function impl + caller updates)
3. 更新测试

## Limitations
- 不适用 ctor (ctor 不能 return)，那种保留异常
- 不适用 RAII dtor (无 return)
