AI 工程 阅读 ~20 min 10 章
00

概览

传统"写完再审"的模式只管代码不管产品

传统"写完再审"的模式只管代码不管产品。真正可靠的质量体系需要三个角色闭环：写代码的人、审代码的人、验产品的人——审查看的是代码 diff，验收看的是产品行为。

01

传统"写-审"模式为什么不够

传统模式只有两个角色——写代码和审代码

传统模式只有两个角色——写代码和审代码。代码可以审得很漂亮，但"写的东西是不是用户要的"这个问题，没有任何角色负责回答。

传统的软件质量保障依赖两道人墙：Writer（开发者）负责实现功能，Reviewer（审查者）负责检查代码质量。这个模式在过去几十年中被广泛使用，但它存在一个结构性盲区——没有人从"产品行为"的角度验证交付物。

传统模式能拦截什么

问题类型Writer 自查Reviewer 审查能否拦截
语法错误、类型不匹配IDE 实时提示CI lint 检查✅ 完全拦截
逻辑 Bug（空指针、越界）单元测试覆盖代码逻辑审查✅ 大部分拦截
性能问题（N+1 查询、内存泄漏）开发者经验审查者经验⚠️ 部分拦截
代码风格一致性格式化工具审查标准✅ 完全拦截

传统模式不能拦截什么

问题类型具体表现为什么漏过影响程度
需求偏差需求说"按价格降序"，代码实现了"按价格升序"代码逻辑正确，只是不符合需求严重——功能方向错误
UI 还原偏差设计稿要求 16px 间距，实际实现 12px审查者不看设计稿对比中等——用户体验降级
回归缺陷修改注册流程时意外破坏了登录功能审查者只关注 diff 范围内的改动严重——已有功能被破坏
集成问题API 返回格式与前端期望不一致代码各自正确，接口契约在运行时才暴露严重——系统级故障
边界体验空数据状态下页面显示"undefined"开发者用假数据测试，未覆盖空状态中等——边缘场景暴露
结构性盲区的根源：Writer 和 Reviewer 都在"代码层面"工作——一个写，一个审。但软件质量最终由"产品行为"决定。代码可以完美无缺，但如果产品行为和用户期望不一致，质量就是零。这个盲区只能由一个"站在产品角度验证"的角色来填补。

传统模式的成本错觉

很多团队认为"加一个 Verifier 角色太贵了"——多一个人就多一份人力成本。但 Tricentis 2025 年的质量转型报告给出了反直觉的数据：42% 的全球组织认为低质量软件每年造成超过 100 万美元的损失。这些损失包括：上线后的紧急修复（开发成本 3-5 倍）、客户流失（品牌损害）、以及团队士气下降（反复返工）。相比之下，增加一个 Verifier 角色的成本只是这些损失的零头。质量三角不是"增加成本"，而是"用前置的小成本避免后置的大损失"。

软件工程中有一个经典定律：Bug 的修复成本随发现阶段向后推移而指数级增长。需求阶段发现 → 1x 成本，编码阶段 → 5x，测试阶段 → 20x，上线后 → 100x。Verifier 的价值就在于把问题拦截在"测试阶段"（20x 以内），而不是让它滑到"上线后"（100x）。

02

三角色质量体系：Writer → Reviewer → Verifier

质量三角的核心思想是"视角分离"——Writer 从实现者角度看代码，Reviewer 从工…

质量三角的核心思想是"视角分离"——Writer 从实现者角度看代码，Reviewer 从工程师角度看逻辑，Verifier 从用户角度看产品。三个视角形成完整的验证覆盖。

三个角色的精确定义

角色职责关注对象验证方式权限范围
Writer功能实现 + 白盒测试代码逻辑、单元测试、类型安全看代码实现是否符合技术方案完全读写代码
Reviewer代码审查 + 逻辑检查代码 diff、架构一致性、安全规范逐行审查代码变更只读代码 + 评论
Verifier产品验收 + 黑盒测试产品行为、UI 还原、功能完整性像用户一样操作产品，对比需求文档执行权限（Bash），不可修改代码
三角色质量闭环工作流
需求文档 / 设计稿
Writer（写作者）
阅读需求文档，制定技术方案 · 编写功能代码 · 编写单元测试（白盒测试） · 确保 CI 通过（lint + test）
代码提交 PR
Reviewer（审查者）
审查代码 diff 的逻辑正确性 · 检查架构一致性（命名、分层、依赖方向） · 检查安全规范（SQL 注入、XSS、权限控制） · 标注问题 → 未达标则返回 Writer 修改
代码审查通过
Verifier（验收者）
启动应用，像用户一样操作 · 对照需求文档逐项验证功能行为 · 检查 UI 还原度（间距、颜色、响应式） · 执行回归测试（已有功能是否受影响） · 标注问题 → 未达标则返回 Writer 修改
验收通过
✅ 合入主分支 / 发布

Verifier 的核心设计原则

设计原则具体要求原因
只看行为不看代码Verifier 不审查代码实现细节，只验证最终产品行为避免"实现者思维"导致盲区
必须有执行权限可以运行 Bash 命令启动应用、执行测试脚本、调用 API必须能实际操作产品
只报告不修改发现问题时生成报告，但绝不直接修改代码保持验证独立性，防止"既当裁判又当运动员"
对照需求文档每一个验证项都必须关联到具体的需求条目确保验证有据可依，避免主观判断

三角色协作的信息流

三个角色之间的信息传递必须结构化，不能靠口头沟通。Writer 提交 PR 时必须附带"技术方案说明"（解释为什么这样实现），Reviewer 审查时必须在评论中引用具体代码行，Verifier 验收时必须对照需求文档中的验收标准逐项标注 PASS/FAIL。这种结构化的信息流确保了问题可以被追溯和复现——当某个 Bug 漏到生产环境时，可以回溯分析是 Writer 没有覆盖、Reviewer 没有发现、还是 Verifier 的验收清单不完整。

协作铁律：Writer 的技术方案说明、Reviewer 的审查意见、Verifier 的验收报告——这三份文档构成了质量的"可追溯链"。缺少任何一份，问题发生时都无法快速定位根因。
03

典型问题拦截：三角如何覆盖盲区

三角体系的价值不在于"多了个人看"，而在于"多了一个视角看"

三角体系的价值不在于"多了个人看"，而在于"多了一个视角看"。Writer 看实现、Reviewer 看代码、Verifier 看产品——三个视角的交集才是质量的完整覆盖。

案例一：需求偏差——排序规则错误

检查环节检查动作结果
Writer 自查编写排序函数，运行单元测试通过✅ 代码逻辑正确
Reviewer 审查审查排序算法实现，代码清晰无 bug✅ 代码质量合格
Verifier 验收打开产品页面，发现商品按价格升序排列，但需求要求降序❌ 需求偏差！打回修改

根因分析：需求文档中写的是"价格从高到低排列"，Writer 在实现时理解为"价格从小到大排列后反转"但实际只做了"从小到大"。代码逻辑本身没有错误，只是方向搞反了。这类问题只有通过"操作产品看结果"才能发现。

案例二：UI 还原偏差——间距和颜色不符

检查环节检查动作结果
Writer 自查使用设计系统的组件库，目视检查✅ 看起来差不多
Reviewer 审查审查 CSS 代码，无语法问题✅ 代码质量合格
Verifier 验收打开设计稿与产品截图对比，发现卡片间距 12px（应为 16px），按钮颜色 #3B82F6（应为 #2563EB）❌ UI 还原度不足！打回修改

案例三：回归缺陷——登录改注册

检查环节检查动作结果
Writer 自查修改注册流程代码，运行注册相关测试通过✅ 注册功能正常
Reviewer 审查审查 diff，只涉及注册模块改动✅ 改动范围合理
Verifier 验收除了验证注册功能，还执行回归测试，发现登录页面的 OAuth 回调被注册改动意外修改❌ 回归缺陷！打回修改
回归缺陷是传统模式最致命的盲区。Reviewer 只能看到 diff 中修改的代码，无法预知"这段改动是否会影响其他模块"。2025 年 CodeRabbit 的统计数据显示，AI 生成的 PR 平均包含 10.83 个问题，其中 75% 是"灰色错误"——代码能通过编译和单元测试，但违反业务逻辑。Verifier 的回归测试是唯一能在发布前拦截这类问题的手段。
04

Verifier 的配置与执行规范

Verifier 的有效性取决于"权限边界"的精确设计——必须能操作产品，但绝不能修改代码

Verifier 的有效性取决于"权限边界"的精确设计——必须能操作产品，但绝不能修改代码。这是保持验证独立性的关键。

Verifier 权限配置

权限类型是否授予具体能力原因
读取项目代码✅ 授予查看文件结构和配置需要了解项目结构以正确启动应用
执行 Bash 命令✅ 授予启动应用、运行测试、调用 curl/API必须能实际操作产品
访问数据库✅ 授予（只读）查询数据验证功能正确性验证数据是否正确写入
修改代码文件❌ 禁止不可编辑任何源代码防止"既当裁判又当运动员"
执行 Git 操作❌ 禁止不可 commit/push/merge保持验证环境的一致性
安装新依赖⚠️ 受限仅允许安装验收测试工具防止引入未审查的依赖

串行工作流：为什么必须严格有序

Writer → Reviewer → Verifier 必须串行执行，不能并行

Writer → Reviewer → Verifier 必须串行执行，不能并行。因为每一层都依赖前一层的通过——审查未通过的代码不值得验收，验收未通过的产品不值得发布。

并行 vs 串行的权衡

模式流程优点缺点适用场景
严格串行W → R → V（逐步流转）每层验证充分，质量最高总耗时最长核心功能、生产环境变更
部分并行W → (R ∥ V)（审查和验收并行）总耗时缩短 30-40%验收可能在审查未通过时白做紧急修复、小范围改动
完全并行W ∥ R ∥ V（同时进行）最快Review 和 Verify 可能基于不稳定的代码不推荐
06

质量三角的常见反模式与修正

实施质量三角最容易犯的错误不是"不做事"，而是"做错了事还以为做对了"

实施质量三角最容易犯的错误不是"不做事"，而是"做错了事还以为做对了"。以下五种反模式在团队中最常见，每种都有明确的修正方案。

反模式一：形式化审查

表现后果修正方案
Reviewer 只看代码风格不看业务逻辑代码格式完美但功能方向错误审查清单必须包含"是否符合需求意图"的检查项
Reviewer 对所有 PR 都 LGTM审查变成橡皮图章要求 Reviewer 至少提出一个有深度的问题
审查时间 < 5 分钟（对中等复杂度 PR）无法深入理解代码变更设置最低审查时间阈值，复杂 PR 要求 30 分钟以上

反模式二：Verifier 越权

表现后果修正方案
Verifier 发现问题后直接修改代码"裁判兼运动员"，验证独立性丧失严格禁止 Verifier 的代码修改权限
Verifier 跳过失败的测试项直接标记通过问题被掩盖，上线后暴露验收清单中的每项必须有截图/录屏作为证据
Verifier 只看正向流程不看边界场景边界条件下的 Bug 漏到生产验收清单必须包含空状态、错误状态、边界值场景

反模式三：需求文档缺失导致验收无据可依

核心问题：没有明确的验收标准（Acceptance Criteria），Verifier 就只能凭"感觉"判断对不对。这导致验收结果不可复现、不可审计。解决方案是在 Writer 开始编码之前，三方（Writer + Reviewer + Verifier）共同审查需求文档，将每条需求转化为可验证的 AC。

反模式四：回退流程被跳过

当 Verifier 发现问题后，Writer 直接修复并在本地验证通过就合入主分支，跳过了 Reviewer 重新审查和 Verifier 重新验收。这种"快车道"看似高效，但破坏了闭环的完整性——修复可能引入新问题，而这些问题没有任何人检查。正确的做法是：任何修改后必须重新走完整的 Writer → Reviewer → Verifier 流程，无论改动多小。

反模式五：三角色由同一人兼任

在人手不足的团队中，同一个人既写代码、又审代码、又验产品。这完全丧失了质量三角的核心设计——"视角分离"。同一个人很难在"实现者思维"和"用户思维"之间快速切换，认知偏差会导致大量盲区。即使团队只有 3 个人，也必须确保同一个 PR 至少经过两个人的不同角色检查。

反模式总结：质量三角的"五大杀手"

以上五种反模式可以归纳为质量三角的"五大杀手"：形式化审查让 Reviewer 形同虚设、Verifier 越权让独立性丧失、需求缺失让验收无据可依、回退跳过让闭环断裂、角色兼任让视角单一。任何一种反模式如果被忽视，都会让质量三角退化为传统的"写-审"模式，丧失其核心价值。

自检方法：每月统计一次"Verifier 发现的问题中有多少是 Writer 和 Reviewer 都没发现的"——如果这个比例低于 20%，说明 Verifier 的视角没有真正独立，三角体系可能已经退化。

反模式修正 Do：

  • Reviewer 使用结构化审查清单（含业务逻辑项）
  • Verifier 的每项验收结果附带截图证据
  • 需求审查会议在编码前召开
  • 修复后重新走完整三角流程

反模式警示 Don't：

  • 审查只看格式不看逻辑
  • Verifier 自行修改代码
  • 需求不明确就凭感觉验收
  • 修复后跳过审查直接合入

AI 时代的质量三角适配

当 AI 可以秒速生成代码，Writer 的效率提升了 5-10 倍，但 Reviewer…

当 AI 可以秒速生成代码，Writer 的效率提升了 5-10 倍，但 Reviewer 和 Verifier 的容量没有同步增长。质量三角在 AI 时代面临"产出速度 vs 验证速度"的结构性失衡。

AI 增强的质量三角
Writer (人类 + AI 编码助手)
AI: 生成代码框架、自动补全测试用例 · 人: 审查 AI 输出、制定技术方案
Reviewer (人类 + AI 审查工具)
AI: 自动扫描安全漏洞、检测 breaking changes · CodeRabbit/CodeGuru 做第一轮筛选 · 人: 审查架构一致性、业务逻辑合理性
Verifier (人类 + 自动化验收)
AI: 自动生成验收测试脚本、UI 截图对比 · 人: 执行探索性测试、判断边界场景
质量闭环完成

最佳实践：

  • 用 AI 审查工具做 Reviewer 的"第一轮筛选"
  • 为 Verifier 编写可复用的验收测试脚本
  • Verifier 报告中发现的高频问题反馈给 Writer 做防御性编码
  • 对 AI 生成的代码执行与人类代码相同（甚至更严格）的三角流程

常见反模式：

  • 因为"AI 写的代码应该没问题"跳过 Reviewer
  • Verifier 只做正向测试，不做边界和回归测试
  • 三个角色由同一人兼任（丧失独立性）
  • 需求文档不明确就开始 Writer 阶段

落地实施的关键注意事项

质量三角不是"加一个人看"那么简单

质量三角不是"加一个人看"那么简单。它需要明确的需求文档、工具中立的验证方法、严格的权限管控，以及团队对"验证独立性"的文化认同。

Q&A（8 题）

为什么 Verifier 不能修改代码？如果发现问题直接修不是更快吗？
直接修改看似高效，但会破坏验证的独立性和可追溯性。如果 Verifier 自行修改代码，就意味着"验收者"同时变成了"实现者"——修改后的代码由谁来审查？由谁来验收？这会形成无限递归。正确的做法是 Verifier 生成问题报告，由 Writer 修复后再走完整的 Review → Verify 流程。这确保了每一层验证都是独立的、可信赖的。在实际操作中，小问题（如文案 typo）可以通过快速修复 + 简化审查流程来处理，但功能性问题必须走完整闭环。
Reviewer 和 Verifier 的检查范围有重叠吗？
有少量重叠，但关注视角完全不同。Reviewer 从"代码实现"角度检查——逻辑是否正确、架构是否合理、安全是否到位。Verifier 从"产品行为"角度验证——功能是否符合需求、UI 是否还原、已有功能是否受影响。一个具体例子：Reviewer 看到代码中排序函数使用了正确的比较器（代码层面正确），但 Verifier 发现产品页面上的商品排列顺序与需求文档不一致（产品层面错误）。代码逻辑正确但行为不符合需求，这正是两者互补的价值所在。
在 AI 编码助手（如 Copilot/Cursor）的场景下，质量三角需要怎么调整？
核心原则不变，但需要强化两个环节。第一，Reviewer 的工作量会增加——AI 生成的代码虽然速度快，但缺陷率比人类代码高 1.7 倍（CodeRabbit 2025 数据），需要更细致的审查。建议引入 AI 审查工具（如 CodeRabbit、Amazon CodeGuru）做第一轮自动扫描，人类 Reviewer 聚焦在业务逻辑和架构层面。第二，Verifier 的价值急剧上升——75% 的 AI 生成代码失败是"灰色错误"（编译通过但违反业务逻辑），这类问题只有 Verifier 通过操作产品才能发现。三角体系从"W→R→V"变为"W(AI+人)→R(AI+人)→V(自动化+人)"。
小团队（3-5 人）如何实施质量三角？人手不够怎么办？
小团队的关键是"角色分离"而非"角色独立"——同一个人可以在不同任务中扮演不同角色，但同一个 PR 必须经过不同人的审查和验收。例如：A 写代码（Writer），B 审查代码（Reviewer），C 验收产品（Verifier）。下一个任务可以轮换角色。如果只有 3 个人，可以简化 Verifier 流程——用自动化验收测试（CI 中的 E2E 测试）替代人工验收，但必须确保测试用例覆盖了需求文档中的所有验收标准。最核心的原则是：写代码的人不能自己审查自己的代码，也不能自己验收自己的产品。
需求文档不明确时，Verifier 如何执行验收？
需求不明确时，Verifier 应该在验收开始前（而非过程中）就介入。具体做法是"三方对齐会议"——Writer、Reviewer、Verifier 一起审查需求文档，把模糊的描述转化为可验证的验收标准。例如"页面加载要快"转化为"首页 LCP ≤ 2.5 秒"，"用户体验要好"转化为"3 次点击内完成核心流程"。如果需求确实无法细化（如探索性功能），Verifier 可以采用"探索性测试"方法——不带预设期望，以用户视角自由操作产品，记录发现的任何不合理之处。但这种方式应该作为补充而非替代正式验收。
串行工作流是否会导致开发周期过长？
短期看，串行确实增加了单个 PR 的交付时间（增加约 30-50%）。但从系统整体看，三角体系反而缩短了"从代码提交到线上无 Bug"的总周期。原因是：传统模式中，很多 Bug 是在上线后才被发现的（修复成本是开发阶段的 10-100 倍），而三角体系把这些问题拦截在发布前。数据支撑：TestQuality 2026 年的报告显示，增加显式验证阶段后，Agent 任务成功率提升 15.6%，生产环境缺陷率降低 25-35%。如果担心周期过长，可以采用"分级验证"策略：核心功能走完整三角，小改动走简化流程（Writer + 自动化验证）。
Writer 自己写的白盒测试和 Verifier 的黑盒测试有什么区别？
白盒测试和黑盒测试的根本区别在于"是否了解内部实现"。Writer 的白盒测试知道代码的内部结构——知道有哪些分支、哪些边界条件、哪些数据结构，因此能精确覆盖代码路径（如分支覆盖率 100%）。Verifier 的黑盒测试不了解内部实现——只知道需求文档规定的输入和期望输出，通过实际操作产品来验证。白盒测试能发现"代码逻辑错误"（如数组越界），黑盒测试能发现"需求偏差"（如排序方向错误）。两者互补，缺一不可。
质量三角如何与 CI/CD 流程集成？
质量三角可以嵌入 CI/CD 的 Pipeline 中作为自动化 Gate。Writer 阶段对应 CI 的 Build + Unit Test 阶段；Reviewer 阶段对应 Code Review Gate（可集成 CodeRabbit/CodeGuru 做自动审查）；Verifier 阶段对应 Staging 环境的 E2E 测试 + 人工验收。具体集成方式：PR 提交触发 CI → 通过则自动请求 Review → Review 通过后自动部署到 Staging → 触发 E2E 测试套件 → 测试通过后通知 Verifier 做人工验收 → 全部通过后自动合入。每个 Gate 失败都会阻止后续流程，确保串行执行。
