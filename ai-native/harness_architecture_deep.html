Agent Harness 工程方法

Harness Engineering — Agent = Model + Harness，从概念到企业级落地的完整拆解

AI 工程 阅读 ~10 min 13 章
00

概览

核心公式：Agent = Model + Harness。Model 提供基础智能能力，Harness 将智能转化为实际工作能力。效能关键在系统整体配合，而非单一模型能力。

安全隔离与自验证
L2 · 代码层：Bash 执行环境
代码执行与工具创建
L1 · 基础层：文件系统
持久存储与协作空间

Harness 工程方法的核心思想

解决 AI 长任务执行中的逻辑断裂问题

1. 上下文重置机制

解决 AI 长任务执行中的逻辑断裂问题。将任务打包成结构化数据文件，采用接力赛模式传递任务状态。

2. 对抗性架构

角色职责
生成器负责执行
评估器负责质量把控

评估器四项硬标准：设计质量、原创性、工艺、功能性。严厉惩罚 AI 批量生产的设计模式。

3. 三智能体协作模式

三智能体协作流程
规划师 → 制定产品规格
生成器 → 编写代码
评估器 → 自动化测试 + 找 Bug
特别强调：评估器要实际操作应用

4. 动态调整策略

  • 随着模型能力增强，简化不必要的流程
  • 将工程精力转向更具挑战性的场景
  • 从"老师"角色转变为"侦察兵"角色

方案耗时成本质量

  • 克制添加：避免上下文过载
  • 渐进披露：按需加载工具
  • 智能压缩：优化上下文管理
  • 持续执行：确保任务连贯性
  • 接力赛思路解决长任务
  • 对抗性架构提升质量

05

企业级 Harness 三层架构

企业级 Harness Coding 不是让 AI 裸奔写代码

企业级 Harness Coding 不是让 AI 裸奔写代码。真正的 Harness 至少需要三层：人类需求层、工程契约层、代码执行层。

第一层：人类需求层

解决"人类到底想要什么"的问题。很多 AI Coding 失败不是模型写不出代码，而是需求从一开始就没被说清楚。

要素必须明确的内容
为什么做业务动机和目标
做什么范围边界，不做什么
输入输出接口契约和数据格式
验收标准可度量的完成条件
核心原则：人类负责想清楚方向，AI 负责把方向翻译成工程动作。如果人类自己都没想清楚，AI 只会把不确定性放大。

第二层：工程契约层

人类需求是业务语言，代码实现需要工程语言。这一层把需求翻译成可执行的"工程合同"。

  • 设计方案：改哪个模块、新增什么接口
  • 错误码定义：异常场景怎么处理
  • 测试覆盖：哪些场景必须覆盖
  • 架构约束：哪些规则不能破坏

AI 可以起草契约，但人类必须 Review——方向对不对、边界有没有漏、验收标准是否可验证。

第三层：代码执行层

只有前两层对齐后，AI 才能进入代码实现。但即使到了这里，也要拆分角色：

角色职责为什么分离
规划 Agent任务拆分、依赖分析聚焦全局视野
实现 Agent编写代码和测试聚焦局部执行
评估 Agent外部视角审查不让模型既当运动员又当裁判
06

10 步 Harness 流水线

企业级 Harness 的实际运行流程，从需求到验收的完整闭环：

企业级 Harness 的实际运行流程，从需求到验收的完整闭环：

10 步 Harness 流水线
1. 团队内部评审需求文档 → 认知对齐
2. 需求文档交给 AI → 基于文档实现
3. AI 审核需求 → 对比项目架构规范，与人类达成目标一致
4. 人类批准 → AI 生成 Spec 工程文档
5. 人类审核 Spec → 确认对齐原始需求
6. AI 开发完毕 → 自主调度 Harness Check
7. Harness Check → 测试覆盖率 ≥80%、静态扫描
不通过 → 打回重新修改 · 通过 ↓ · 8. 测试 Agent → 基于 Spec 检查是否符合验收标准 · 9. 架构 Agent → 检查是否破坏项目架构原则
10. 双 Agent 验收通过 → 人类确认 / 不通过 → 打回修复
关键设计：双 Agent 验收（测试 Agent + 架构 Agent）确保代码既满足功能需求，又不破坏架构规范。经验沉淀：打回次数过多时，AI 偏航记录自动沉淀到文档，避免同类错误再次发生。

AbstractFilesystem：可插拔文件系统

个人 Agent 用本地目录就够了，但企业级场景需要分布式存储

个人 Agent 用本地目录就够了，但企业级场景需要分布式存储。AbstractFilesystem 让同一套 Agent 逻辑在不同物理存储间无缝切换。

设计思想

对上层：Agent 调用统一的 read/write/ls/grep 接口，不关心"文件"实际落在哪。

对下层：可适配本机磁盘、远端对象存储（OSS）、KV 数据库（Redis）、沙箱文件系统，甚至通过 CompositeFilesystem 把不同路径路由到不同后端。

三种部署模式

模式物理存储适用场景
Local本机磁盘个人代理（如 OpenClaw）
Remote远端 OSS/KV企业级多副本部署
Sandbox隔离沙箱文件系统不信任输入下的安全执行
为什么重要：AgentScope Java 用这一层抽象解决了"个人助手型 Agent 和企业级 Agent 是两种工程形态"的核心矛盾——同一份 Agent 逻辑，无需修改即可适配个人开发环境与企业分布式部署。
08

企业级场景分层

不是所有 Agent 都需要完整的 Harness

不是所有 Agent 都需要完整的 Harness。根据场景复杂度选择合适的 Harness 深度：

场景典型应用核心 Harness 能力关键约束
个人代理OpenClaw、Coding Agent持续记忆、本地 Shell 执行、工作区配置单用户、本机运行
企业数据服务DataAgent、SRE Agent隔离沙箱执行、多轮沙箱状态恢复、分布式记忆共享、子 Agent 并行编排多租户、安全隔离、状态可恢复
企业在线服务交易 Agent、审批 Agent默认安全边界（不暴露 Shell）、多实例共享记忆、会话跨请求连续稳定安全、API 驱动

企业级五大痛点

痛点问题Harness 解法
多用户多副本本地目录在分布式场景崩掉AbstractFilesystem + Remote 存储
隔离执行宿主机上跑任意用户输入是安全漏洞沙箱 + 多轮状态持久化
分布式文件系统没有统一本地磁盘AbstractFilesystem 统一接口
Multi-Agent 编排代码复杂度快速上升声明式子 Agent 规格
上下文压缩压缩时机/策略/事实提取细节多双层记忆 + 后台维护
09

双层记忆沉淀机制

Harness 的记忆不是简单的"存对话历史"，而是分两层沉淀：

Harness 的记忆不是简单的"存对话历史"，而是分两层沉淀：

工作记忆（流水账）

每轮对话结束后，自动提炼本次对话的新事实，写入工作区记忆文件。这层记忆是原始记录，保留完整细节。

长期记忆（精炼）

后台周期性地将流水账合并成精炼的长期记忆。过时的、低价值的信息被丢弃，高价值的经验被保留。

层级写入时机内容容量
工作记忆每轮对话结束新事实、新发现、新偏好无硬上限
长期记忆后台周期合并提炼后的核心经验字符上限（控制 token 成本）
设计要点：工作记忆保证"不丢事实"，长期记忆保证"不爆上下文"。全文检索工具允许 Agent 从工作记忆中回捞旧事实，兼顾完整性和效率。
10

核心要点总结

Harness 工程方法核心：
  • 公式：Agent = Model + Harness，Harness 是将智能转化为工作能力的工程系统
  • 四层架构：文件系统（基础）→ Bash 执行（代码）→ 沙箱验证（安全）→ 记忆搜索（知识）
  • 三大机制：上下文重置（接力赛模式）、对抗性架构（生成器+评估器）、三智能体协作（规划/生成/评估）
  • 成本洞察：完整 Harness 6h/$200 vs 单一 Agent 20min/$9，成本差 20 倍但质量天壤之别

Q&A

Model 只提供基础智能能力，Harness 将智能转化为实际工作能力
为什么 Agent 需要 Harness 而不是直接用模型？

Model 只提供基础智能能力，Harness 将智能转化为实际工作能力。没有 Harness 的 Agent 就像没有赛道的赛车——引擎再强也跑不出成绩。Harness 提供文件系统、执行环境、安全隔离、记忆管理四大能力，确保任务的连贯性、安全性和可验证性。

对抗性架构为什么需要评估器实际操作应用？

评估器如果只看代码不实际操作，就无法发现真正的 Bug。比如 UI 渲染问题、交互逻辑错误、边界条件异常，只有实际操作应用才能发现。四项硬标准（设计质量、原创性、工艺、功能性）都需要实际体验来验证，不能只靠静态代码审查。

上下文重置机制怎么解决长任务的逻辑断裂？

长任务执行中，AI 的上下文窗口会逐渐被历史信息填满，导致逻辑断裂。上下文重置机制将任务打包成结构化数据文件，采用接力赛模式传递任务状态——每个阶段结束时，将关键状态写入文件，下一阶段从文件中恢复状态重新开始，保证任务连贯性。

Harness 的动态调整策略是什么意思？

随着模型能力增强（如从 GPT-3.5 到 GPT-4 到 Claude），之前必要的流程可能变得多余。动态调整意味着：① 简化模型已经能做好的部分，② 将工程精力转向更具挑战性的场景，③ 角色从"老师"（教模型怎么做）转变为"侦察兵"（发现模型做不好的地方并补强）。

Q5：Harness 架构的可观测性怎么做？需要监控哪些指标？

Harness 可观测性三层指标：(1) 模型层 — 每步推理延迟、Token 消耗、输出质量评分（LLM-as-Judge）；(2) Harness 层 — 循环探测触发率、工具调用成功率、上下文压缩比、护栏拦截次数；(3) 业务层 — 任务完成率、用户满意度、端到端延迟。关键告警规则：循环探测触发率 >20%（说明模型可能退化）、工具调用失败率 >5%（可能是 API 问题）、上下文压缩比 >3:1（可能丢失关键信息）。生产实践：Grafana 仪表盘 + Prometheus 指标采集 + PagerDuty 告警，故障平均发现时间 2 分钟。
