概览

上下文窗口不是"越大越好"的容器，而是一块注意力稀缺的白板

上下文窗口不是"越大越好"的容器，而是一块注意力稀缺的白板。当系统提示词、对话历史、RAG 检索结果、工具调用返回值同时争夺同一块白板时，管理这些信息的优先级和密度，比单纯扩大窗口重要 10 倍。核心结论：管理优于扩容。

01

观测与预算：32K 窗口的精细分配

上下文管理的第一步是 观测 ——你得先知道每一类信息占了多少 Token，才能做预算

上下文管理的第一步是观测——你得先知道每一类信息占了多少 Token，才能做预算。在生产系统中，一个典型的 32K 上下文窗口需要被六类信息瓜分：系统提示词、用户当前输入、对话历史、RAG 检索结果、工具调用返回值、模型预留输出空间。它们不是平等的，必须按业务优先级做硬性配额。

┌──────────────────────────────────────────────────────┐ │ 32K Token 上下文窗口预算分配 │ ├──────────────────────────────────────────────────────┤ │ │ │ ┌─────────────┐ ┌──────────┐ ┌────────────────┐ │ │ │ 系统提示词 │ │ 用户输入 │ │ 对话历史(分层) │ │ │ │ ≤ 2K │ │ ~1K │ │ ~4K │ │ │ │ [高优先级] │ │ [固定] │ │ [弹性压缩] │ │ │ └─────────────┘ └──────────┘ └────────────────┘ │ │ │ │ ┌─────────────────────────┐ ┌──────────────────┐ │ │ │ RAG 检索结果 │ │ 工具调用返回值 │ │ │ │ ~16K │ │ ~4K │ │ │ │ [最大弹性区] │ │ [中间层裁剪] │ │ │ └─────────────────────────┘ └──────────────────┘ │ │ │ │ ┌──────────────────────────────────────────────┐ │ │ │ 模型预留输出空间 ~5K │ │ │ │ [硬性保障 — 不可挤压] │ │ │ └──────────────────────────────────────────────┘ │ └──────────────────────────────────────────────────────┘

为什么需要硬性预算

没有预算的上下文就像没有预算的公司——每类信息都会无限膨胀直到挤垮其他部分。一个真实的生产场景：某客服 Agent 的 RAG 检索一次返回了 25K Token 的文档片段，直接把对话历史挤出了窗口，导致 Agent 在第 8 轮对话时突然"忘记"用户之前报的工单号，给出了完全无关的回答。

Token 预算（Token Budget）不是建议值，而是硬性上限。它确保在任何时刻，模型都能"看到"最关键的信息，同时预留足够的空间生成完整回答。预算分配的本质是在回答"如果空间不够，谁先被丢弃"。

信息类别预算比例优先级压缩策略
系统提示词≤ 6%（~2K）最高 — 不可裁剪精简冗余指令，删除重复约束
用户当前输入~3%（~1K）高 — 不可裁剪通常无需压缩
对话历史~12%（~4K）中 — 弹性压缩分层保留：近期原文 / 更早摘要
RAG 检索结果~50%（~16K）中 — 弹性最大四步优化链：召回→重排→去重→压缩
工具调用结果~12%（~4K）中低 — 按需裁剪中间层清洗，保留关键字段
模型输出空间~15%（~5K）最高 — 硬性保障不可压缩，挤压会导致截断

退化曲线：60-70% 填充率是警戒线

研究表明，当上下文填充率达到 60-70% 时，模型的长程依赖能力就开始明显下降。一个 200K 窗口的 Agent，在填充到 120-140K 时就可能出现"忘记 30 轮前的文件内容"的情况。填充到 85% 以上时，JSON 格式错误、工具调用不完整等结构化输出问题会急剧增加。这意味着有效可用窗口远小于理论上限——有效窗口（Effective Window）通常只有标称值的 70-80%。

填充率区间模型表现工程建议
0-60%正常，注意力充裕正常运行
60-70%长程依赖开始退化触发 L1 压缩（裁剪工具结果）
70-85%结构化输出质量下降触发 L2 压缩（历史摘要）
85-100%可能丢失系统指令触发 L3 压缩（全局重建）
生产案例 — 编码 Agent 的上下文崩溃：某编程 Agent 在读取 5 个源文件后，上下文被工具结果（文件内容）占用了 160K/200K Token（80%）。后续的代码修改请求因 JSON 格式错误频繁失败，成功率从 94% 降至 37%。引入三层级联压缩后（L1 裁剪旧文件内容 → L2 尾部对话修剪 → L3 全局摘要），填充率控制在 60% 以下，成功率恢复到 91%，同时每轮 Token 成本从 $0.60 降至 $0.18。
02

历史对话分层：时间维度的三级存储

对话历史是上下文中最容易失控的部分——它随轮次线性增长，但业务价值随时间急剧衰减

对话历史是上下文中最容易失控的部分——它随轮次线性增长，但业务价值随时间急剧衰减。第 1 轮的用户意图可能在第 20 轮仍然关键，但第 3 轮的一个无关闲聊则纯粹是 Token 浪费。对话分层（Conversation Tiering）的核心思想是按时间远近做三级存储，就像 CPU 的 L1/L2/L3 缓存。

┌────────────────────────────────────────────────────────────┐ │ 对话历史三级分层架构 │ ├────────────────────────────────────────────────────────────┤ │ │ │ ┌─────────────────────────────────────────────────┐ │ │ │ L1 · 热层 (最近 3-5 轮) │ │ │ │ 完整原文保留，不做任何压缩 │ │ │ │ Token 消耗: ~1.5K-3K │ │ │ │ 作用: 保持当前对话连贯性 │ │ │ └────────────────────┬────────────────────────────┘ │ │ │ 轮次推进后降级 │ │ ┌────────────────────▼────────────────────────────┐ │ │ │ L2 · 温层 (第 6-15 轮) │ │ │ │ 摘要压缩 (5000 tokens → 500 tokens) │ │ │ │ 保留: 用户意图 + 关键决策 + 未完成事项 │ │ │ │ Token 消耗: ~500-1K │ │ │ └────────────────────┬────────────────────────────┘ │ │ │ 进一步老化后归档 │ │ ┌────────────────────▼────────────────────────────┐ │ │ │ L3 · 冷层 (第 16 轮以前) │ │ │ │ 高度压缩或按需召回 │ │ │ │ 仅保留: 全局目标 + 核心约束 + 里程碑事件 │ │ │ │ Token 消耗: ~200-500 │ │ │ └─────────────────────────────────────────────────┘ │ │ │ │ 总历史 Token 预算: ≤ 4K (占 32K 窗口的 12%) │ └────────────────────────────────────────────────────────────┘

摘要压缩的工程要点

摘要不是简单的"缩短文本"，而是有选择的信息提取。一个好的摘要必须保留三类信息：用户的核心意图（"我要退掉上周的订单"）、关键决策（"已确认可退款"）、未完成事项（"等待财务审批"）。而闲聊、重复确认、工具调用的中间过程可以安全丢弃。

保留信息类型示例为什么重要
用户核心意图"用户想将套餐从 A 升级到 B"防止 Agent 丢失任务主线
关键决策与结论"已确认 B 套餐可用，差价 ¥30/月"避免重复查询相同信息
未完成事项"等待用户确认是否升级"保持任务连续性
实体与 ID"订单号 ORD-2024-78901"后续操作需要精确引用
约束条件"用户表示预算不超过 ¥100/月"约束跨轮次持续生效

摘要的经济账：用 500 Token 的输出生成一条摘要，替代 5000 Token 的原文，在后续每轮请求中节省 4500 输入 Token。如果对话还有 3 轮以上，摘要的成本就已经被回收。对于长会话（10+ 轮），摘要带来的 Token 节省可以达到 60-70%。

压缩方案压缩比信息保留率适用场景
LLM 自由摘要5:1 ~ 10:1~70%通用对话，容错率高
Schema 填表摘要8:1 ~ 15:1~85%结构化任务（客服/工单）
关键句提取3:1 ~ 5:1~60%低成本方案，不需要额外 LLM 调用
结构化状态追踪10:1 ~ 20:1~90%状态明确的任务流（下单/退款）
03

RAG 结果四步优化链：少而准胜过多多益善

RAG 检索 （Retrieval-Augmented Generation）是上下文中的最…

RAG 检索（Retrieval-Augmented Generation）是上下文中的最大弹性区——它可能占用 50% 的窗口空间，但检索结果的质量参差不齐。直接塞入 Top-K 结果是一种粗暴且低效的做法：排在前面的不一定最相关，重复内容浪费 Token，不相关的片段还会干扰模型推理。四步优化链将检索结果从"原始矿石"精炼为"高纯度燃料"。

┌─────────────────────────────────────────────────────────────────┐ │ RAG 四步优化链 │ ├─────────────────────────────────────────────────────────────────┤ │ │ │ Step 1: 多路召回 │ │ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────┐ │ │ │ 向量检索 │ │ BM25 关键词│ │ 知识图谱 │ │ 元数据过滤 │ │ │ │ Top-20 │ │ Top-20 │ │ Top-10 │ │ Top-15 │ │ │ └────┬─────┘ └────┬─────┘ └────┬─────┘ └──────┬───────┘ │ │ └─────────────┴─────────────┴──────────────┘ │ │ │ 合并候选池 (~40-60 条) │ │ ▼ │ │ Step 2: 重排序 (Reranker) │ │ ┌──────────────────────────────────────────────────────┐ │ │ │ Cross-Encoder 重排模型逐对打分 │ │ │ │ 按相关性得分降序排列，取 Top-8 │ │ │ └──────────────────────────┬───────────────────────────┘ │ │ ▼ │ │ Step 3: 去重合并 │ │ ┌──────────────────────────────────────────────────────┐ │ │ │ 语义相似度 > 0.92 的段落合并 │ │ │ │ 重叠内容消除，保留最完整的版本 │ │ │ │ 结果: 8 条 → 5 条 │ │ │ └──────────────────────────┬───────────────────────────┘ │ │ ▼ │ │ Step 4: 证据保留 │ │ ┌──────────────────────────────────────────────────────┐ │ │ │ 每条结果附加来源标记 [doc_id, page, paragraph] │ │ │ │ 截断过长段落至 500 tokens │ │ │ │ 最终: 5 条精炼结果，总计 ~3K-5K tokens │ │ │ └──────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────────┘

重排序（Reranking）是 RAG 链路中投入产出比最高的优化点。向量检索的召回准确率通常在 60-75%，而经过 Cross-Encoder 重排后，Top-5 的精确率可以从 45% 提升到 78%。它的成本极低——一次重排调用只需要几十毫秒，但能让模型看到的信息质量翻倍。

为什么"多不一定好"

这里存在一个反直觉的现象：给模型更多检索结果，回答质量反而可能下降。这被称为Lost in the Middle效应——当相关信息被大量不相关或弱相关内容包围时，模型对中间位置信息的注意力显著下降。一个 2025 年的基准测试发现，13 个支持 128K 上下文的模型中，有 11 个在 32K Token 时性能就下降到短文本基线的 50% 以下。

检索策略Top-5 精确率Token 消耗回答准确率
纯向量 Top-545%~3K62%
纯向量 Top-2038%（含噪音）~12K55%（下降！）
向量 + BM25 融合 + 重排 Top-578%~3K81%
四步完整链 Top-585%~3-5K87%
生产案例 — 企业知识库 RAG 优化：某金融企业的智能客服系统使用纯向量 Top-10 检索，每次塞入 8K Token 的检索结果。优化后采用四步链（多路召回 → BGE-Reranker 重排 → 语义去重 → 500 Token 截断），检索 Token 从 8K 降至 4K（节省 50%），同时回答准确率从 68% 提升至 84%，因为噪音减少后模型的注意力更加集中。月均 Token 成本从 $2,400 降至 $1,500。
04

工具结果裁剪：中间层清洗与压缩

工具调用（Function Calling）的返回值是上下文中最容易被忽视的 Token 黑…

工具调用（Function Calling）的返回值是上下文中最容易被忽视的 Token 黑洞。一次文件读取可能返回 10K-50K Token，一个数据库查询可能返回 5K 行的完整结果，一个 API 响应可能包含大量元数据和嵌套结构。这些原始结果直接塞入上下文，就像把一整本百科全书塞进便签纸——信息是有了，但关键内容被淹没在噪音中。

工具结果裁剪（Tool Result Trimming）的核心思想是在工具返回值进入上下文之前，经过一个中间处理层进行清洗和压缩。这个层不需要理解业务语义——它只做三件事：删除无关字段、压缩重复数据、保留关键样本和异常值。

裁剪策略分类

工具类型原始返回特征裁剪策略压缩比
文件读取完整文件内容，可能 10K+ Token保留首尾 + 搜索匹配段落，中间替换为 [文件已读取，共 450 行，已裁剪]5:1 ~ 20:1
数据库查询完整结果集，可能数百行限制返回条数（如 LIMIT 20），附加总数统计10:1 ~ 50:1
API 调用包含大量元数据的 JSON白名单字段提取，删除 headers/timing 等3:1 ~ 8:1
Shell 命令可能包含大量日志输出保留最后 N 行 + 错误行 + 统计摘要10:1 ~ 100:1
Web 搜索多个网页的完整内容保留 snippet + title + URL，不塞入全文20:1 ~ 50:1

三层级联压缩：Claude Code 的生产实践

Claude Code 的上下文管理是目前生产系统中最成熟的方案，采用三层级联策略。当上下文压力增大时，依次触发三个层级，每层解决不同粒度的问题。

┌────────────────────────────────────────────────────────────┐ │ Claude Code 三层级联压缩 │ ├────────────────────────────────────────────────────────────┤ │ │ │ 触发条件: 上下文填充率 > 60% │ │ │ │ ┌────────────────────────────────────────────────────┐ │ │ │ L1 · 工具结果裁剪 (零成本，不需要 LLM) │ │ │ │ 旧的文件读取/命令输出替换为占位符 │ │ │ │ 例: [File was read but trimmed, 2340 tokens saved] │ │ │ │ 回收: 40-60% 上下文空间 │ │ │ │ ──────── 如果仍然不够 ↓ ──────── │ │ │ ├────────────────────────────────────────────────────┤ │ │ │ L2 · 尾部对话修剪 (低成本) │ │ │ │ 从对话尾部删除旧轮次，保护缓存前缀 │ │ │ │ 关键: 保留 prompt cache 锚点，避免缓存失效 │ │ │ │ 回收: 额外 15-25% │ │ │ │ ──────── 如果仍然不够 ↓ ──────── │ │ │ ├────────────────────────────────────────────────────┤ │ │ │ L3 · 全局摘要重建 (高成本，需要 LLM) │ │ │ │ 用 LLM 对剩余对话生成结构化摘要 │ │ │ │ 摘要替换原始历史，重建精简上下文 │ │ │ │ 回收: 额外 20-40% │ │ │ │ 注意: 会破坏 prompt cache，触发全价重读 │ │ │ └────────────────────────────────────────────────────┘ │ └────────────────────────────────────────────────────────────┘

Prompt Cache 保护是级联压缩中最容易被忽视的经济因素。Anthropic 的缓存定价让缓存读取比新鲜输入便宜 90%（$0.30/MTok vs $3/MTok）。一次 L3 全局重建会破坏缓存前缀，导致后续请求全部按原价计费。如果 Agent 每分钟处理 3 个请求，缓存失效一次的额外成本约为 $0.12-0.30——看起来不多，但在日均 10000 次请求的规模下，每月额外成本可达 $360-900。

MapReduce 大任务拆分：语义边界切分与局部处理

当一个任务本身就需要处理大量文本时（如分析一份 50 页的合同、总结 200 篇论文、审查…

当一个任务本身就需要处理大量文本时（如分析一份 50 页的合同、总结 200 篇论文、审查 1000 条用户反馈），即使完美地管理上下文也无法将全部信息塞入窗口。这时候需要MapReduce策略：将大任务按语义边界切分为多个局部子任务，每个子任务独立处理后，再将结果汇总为全局结论。

┌─────────────────────────────────────────────────────────────────┐ │ MapReduce 大任务处理流程 │ ├─────────────────────────────────────────────────────────────────┤ │ │ │ 原始任务: 分析 50 页合同文档 (约 40K tokens) │ │ │ │ ┌─── 切分阶段 ──────────────────────────────────────────────┐ │ │ │ 按语义边界切分 (章节/条款/段落) │ │ │ │ 切分粒度: 每块 3K-5K tokens │ │ │ │ 关键: 不在句子中间断开，保留完整语义单元 │ │ │ └──────────────────────────┬──────────────────────────────┘ │ │ ▼ │ │ ┌─── Map 阶段 ─────────────────────────────────────────────┐ │ │ │ 每个块独立送入 LLM 处理 │ │ │ │ 提取: 关键条款 / 风险点 / 异常条款 / 金额数字 │ │ │ │ 输出: 结构化中间结果 (JSON) │ │ │ │ │ │ │ │ Block 1 → {clauses: [...], risks: [...]} │ │ │ │ Block 2 → {clauses: [...], risks: [...]} │ │ │ │ ... │ │ │ │ Block N → {clauses: [...], risks: [...]} │ │ │ └──────────────────────────┬──────────────────────────────┘ │ │ ▼ │ │ ┌─── Reduce 阶段 ──────────────────────────────────────────┐ │ │ │ 汇总所有中间结果 │ │ │ │ 去重、冲突检测、全局一致性校验 │ │ │ │ 生成最终报告 │ │ │ │ 输出: 合同分析总报告 (~3K tokens) │ │ │ └──────────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────────┘

语义边界 vs 机械切分

切分策略直接决定 MapReduce 的成败。机械切分（按固定字符数或 Token 数硬切）会破坏语义完整性，导致模型在 Map 阶段无法理解上下文。语义切分则尊重文档的内在结构。

切分策略切分依据优点缺点
固定长度切分每 2K Token 一刀实现简单，块大小均匀可能在句子/段落中间断开
章节标题切分按文档标题层级语义完整，符合人类思维章节大小不均匀
段落边界切分按空行分隔保持段落完整性粒度可能太细或太粗
滑动窗口切分固定长度 + 重叠区域减少边界信息丢失增加总处理量
语义聚类切分按主题相似度分组主题内聚性最高计算成本高，需要预分析

MapReduce 的精髓在于"分而治之"——不是把问题变小，而是把大问题拆成多个可以独立并行处理的小问题。每个 Map 调用只需要 3-5K Token 的上下文，而 Reduce 阶段汇总的是精炼后的结构化结果，通常也只有 3-5K Token。这样，即使原始文档有 40K Token，整个过程的最大单次上下文消耗也不会超过 8K。

MapReduce vs 暴力塞入：成本与质量对比

对于超大文档处理任务，MapReduce 策略与"把所有内容塞进超大窗口"的做法相比，在成本和可控性上有显著优势。以下是一个 50 页合同审查任务的对比：

维度暴力塞入（200K 窗口）MapReduce（切分 + 汇总）
单次 Token 消耗~45K input tokens~12 × 4K + 1 × 5K = 53K（分摊到多次调用）
单次 API 延迟~8-12s（长上下文推理慢）~2-3s/块（短上下文推理快）
并行处理不可并行12 个 Map 可并行，总延迟 ~5s
关键信息遗漏率~25%（Lost in the Middle）~8%（每块专注处理）
可追溯性无法定位遗漏来源每块有独立中间结果，可逐块复查
成本（按 Sonnet 价格）~$0.14/次~$0.16/次（多次调用但单次便宜）

从表面上看，MapReduce 的总 Token 消耗略高（因为每个 Map 调用都需要加载系统提示词），但它在延迟（可并行）、信息保留率（每块专注处理）、可追溯性（中间结果可审计）三个维度上全面优于暴力塞入。在合同审查这种"不能遗漏关键条款"的场景下，8% 的遗漏率远好于 25%。

适用场景判断

并非所有大文档处理都适合 MapReduce。当任务需要跨段落的深度推理时（例如"第 3 条和第 47 条之间存在矛盾"），Map 阶段的独立处理会丢失跨段信息。此时可以考虑混合策略：先用 MapReduce 提取各段关键信息，再在 Reduce 阶段用较大的上下文窗口做交叉验证。另一个判断标准是任务的"可分解性"——如果子任务之间相互独立（如逐条审查条款），MapReduce 非常合适；如果子任务高度耦合（如全文一致性检查），则需要更复杂的多阶段方案。

降级策略：按优先级裁剪的最后防线

当所有压缩手段都用尽、上下文仍然溢出时，降级策略（Degradation Strategy）是最后一道防线。它的核心逻辑很简单：给每类信息标注优先级，当空间不足时，从最低优先级的信息开始丢弃。这不是最优解，而是"最不坏的"止损方案——宁可丢失一些辅助信息，也要保证核心功能的正常运行。

降级策略的设计哲学来自航空业的紧急处置程序：当飞机遭遇多重故障时，飞行员按检查表逐项处置，优先保障飞行安全（高度和速度），其次是导航（知道往哪飞），最后才是舒适（空调和娱乐系统）。上下文降级遵循同样的逻辑——先保系统指令和用户意图，再保关键历史，最后才是辅助信息。

六级降级方案

降级级别触发条件丢弃内容影响评估
L0 正常填充率 < 60%无无影响
L1 轻度60-70%旧工具结果替换为占位符几乎无影响
L2 中度70-80%早期对话原文替换为摘要细节丢失，主线保留
L3 重度80-90%RAG 结果只保留 Top-2，删除辅助文档回答可能缺少佐证
L4 严重90-95%精简系统提示词，删除示例和附加指令输出质量明显下降
L5 紧急> 95%全局摘要重建 + 仅保留当前轮 + 核心指令上下文重置，连贯性断裂

价值分层矩阵

降级裁剪的关键是正确评估每类信息的价值。一个实用的方法是建立"价值-不可替代性"矩阵：高价值且不可替代的信息（如系统安全指令）绝不能丢弃；高价值但可替代的信息（如详细历史）可以降级为摘要；低价值且可替代的信息（如冗余 RAG 结果）优先丢弃。

信息类型价值可替代性降级策略
系统安全指令极高不可替代永不裁剪

生产案例 — 客服系统降级保护：某电商客服 Agent 在促销高峰期遭遇大量多轮复杂咨询，上下文填充率频繁突破 85%。引入五级降级机制后：L1 自动裁剪旧工具结果（触发率 40%），L2 历史摘要化（触发率 25%），L3 RAG 精简（触发率 8%），L4 以上极少触发（<1%）。系统整体 Token 成本降低 35%，而用户满意度仅下降 2.1%（从 4.2 降至 4.1 分），因为被裁剪的都是低价值信息。

实践指南

  • 在系统设计阶段就定义预算分配和降级策略
  • 用 Token 计数器实时监控各类信息的占用比例
  • 实现渐进式降级，而不是一刀切的全局摘要
  • 为每个降级级别定义明确的触发阈值和回退条件
  • 保护 Prompt Cache 前缀，避免不必要的全价重读
  • 记录降级事件日志，用于后续优化分析
  • 不要依赖"窗口够大就不需要管理"的假设
  • 不要把所有信息平等对待——必须有优先级
  • 不要一次性做全局摘要——它会破坏缓存且丢失细节
  • 不要忽略工具返回值的体积——它们是最常见的 Token 黑洞
  • 不要在降级时丢失用户的实体 ID 和核心意图
  • 不要将降级阈值设为 100%——85% 时模型已经开始退化

Q&A

E32 · 大模型上下文管理策略 | 核心结论：管理优于扩容 — 预算分配 + 分层存储 +…
上下文窗口越大越好吗？为什么 200K 的窗口还需要管理？
上下文窗口并非越大越好，存在三个核心问题。第一，成本线性增长：200K Token 的输入成本是 1K 的 200 倍，在 Agent 多轮场景下差异巨大（每轮 $0.60 vs $0.003）。第二，"Lost in the Middle"效应使模型对中间位置信息的注意力显著下降，2025 年基准测试显示 13 个 128K 模型中 11 个在 32K 时性能已降到基线的 50% 以下。第三，65% 的企业 AI 故障来自上下文漂移而非窗口耗尽。因此管理比扩容更重要。
对话历史摘要会不会丢失关键信息？如何权衡压缩比和信息保留？
摘要确实会丢失信息，但关键是丢的是哪类信息。好的摘要保留五类核心内容：用户意图、关键决策、未完成事项、实体 ID、约束条件；丢弃的是寒暄、重复确认和工具中间过程。实践中，Schema 填表式摘要在结构化任务中可以达到 15:1 的压缩比和 85% 的信息保留率。经济账也很清晰：用 500 Token 生成的摘要替代 5000 Token 原文，在后续 3 轮以上就能回本。对于长会话，摘要带来的 Token 节省可达 60-70%。
RAG 检索结果为什么不是越多越好？Top-20 比 Top-5 更差是怎么回事？
这是 "Lost in the Middle" 效应在 RAG 场景下的直接体现。当 Top-20 的检索结果塞入上下文时，大量弱相关或不相关的片段会分散模型的注意力，反而降低了对 Top-5 高质量结果的利用效率。实测数据：纯向量 Top-5 精确率 45%、回答准确率 62%；Top-20 精确率降至 38%（含噪音）、回答准确率反降至 55%。正确做法是用重排序（Reranker）从多路召回的候选池中精选 Top-5，精确率可提升至 78%、回答准确率达 81%。
Claude Code 的三层级联压缩有什么经济学考量？
Claude Code 的设计深度考虑了 Anthropic 的 Prompt Cache 定价机制。缓存读取价格（$0.30/MTok）是新鲜输入（$3/MTok）的 1/10。L1 工具裁剪和 L2 尾部修剪都是零成本操作，不触发 LLM 调用，且特意保护缓存前缀不被破坏。只有 L3 全局摘要才需要 LLM 调用，但代价是破坏缓存前缀导致后续请求全部按原价计费。在日均万级请求的场景下，一次不必要的 L3 触发每月可多花 $360-900。因此级联策略的核心经济学原则是：能不调 LLM 就不调，能不动前缀就不动。
MapReduce 切分时如何选择语义边界？机械切分有什么问题？
语义边界切分遵循文档的内在结构——按章节标题、条款编号、段落空行来切分，确保每个块是一个完整的语义单元。机械切分（如每 2K Token 一刀）的最大问题是在句子或段落中间断开，导致模型在 Map 阶段缺少完整上下文，可能误读条款或遗漏跨段引用。实践中推荐的策略优先级是：章节标题切分 > 段落边界切分 > 滑动窗口切分（有重叠区） > 固定长度切分。对于合同等结构化文档，按条款编号切分效果最佳；对于连续叙述文本，段落边界配合 10-15% 重叠窗口是较好的折中。
降级策略的触发阈值如何设定？为什么不直接设到 100%？
触发阈值必须设在 100% 之前，因为模型在 85% 填充率以上就开始出现明显退化——JSON 格式错误、工具调用不完整、指令遗忘等问题急剧增加。推荐的分层阈值是：60% 触发 L1（工具裁剪），70% 触发 L2（历史摘要），80% 触发 L3（RAG 精简），90% 触发 L4（系统提示精简）。这些阈值不是固定的，应根据具体模型和任务类型做调整。关键是建立监控仪表盘实时追踪填充率，在退化发生前主动触发降级，而不是等到窗口溢出时才被动应对。
如何在不增加 Token 的情况下提升上下文的有效利用率？
有四个高杠杆率的优化方向。第一，信息位置优化：将最关键的内容放在上下文的开头和结尾（利用 Primacy-Recency 效应），中间放辅助信息。第二，RAG 重排序：不增加检索数量，仅通过 Cross-Encoder 重排就能将 Top-5 精确率从 45% 提升到 78%。第三，工具结果清洗：在中间层删除 JSON 中的冗余字段（headers、timing 等），通常可压缩 3-8 倍。第四，Prompt Cache 利用：将系统提示词和工具定义设为缓存内容，成本降低 90% 而不影响模型可用的有效上下文。
