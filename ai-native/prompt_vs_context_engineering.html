80% Agent 失败是上下文失败

Google DeepMind 工程师 Philipp Schmid 估算： 约 80% 的…

Google DeepMind 工程师 Philipp Schmid 估算：约 80% 的 Agent 失败可追溯到上下文缺失或损坏，而非模型本身的问题。

失败类型根因归类占比
回答错误RAG 检索到过期文档Context 问题~30%
遗漏关键信息对话历史被截断Context 问题~25%
格式不一致System Prompt 格式规则被覆盖Context 问题~15%
推理链断裂CoT 提示词措辞不适合当前模型Prompt 问题~10%
幻觉缺少事实锚定的 ContextContext 问题~10%
模型能力不足任务超出模型本身能力模型问题~10%

信息过载（Information Overload）是 Context 工程的隐性杀手。当上下文窗口被无关信息填满时，模型的注意力稀释效应会导致关键信息被忽略。实测表明：在 128K 窗口中注入超过 40K tokens 的低相关文档后，模型对核心问题的回答准确率下降 23%。

结论：优化 Prompt（教模型怎么想）的 ROI 远低于优化 Context（给模型看什么）。大多数时候，模型"答错"不是因为"不会想"，而是因为"信息不够"或"信息过期"。
03

Prompt 工程的核心技术

在 GPT-4 上精心调优的 Prompt，换到 Claude 可能完全失效
  • 思维链（CoT）：引导模型逐步推理，而非直接给答案
  • 少样本示范（Few-Shot）：提供 3-5 个示例作为解题模板
  • 角色设定：定义模型身份（如"你是资深架构师"）

Prompt 脆弱性问题

在 GPT-4 上精心调优的 Prompt，换到 Claude 可能完全失效。原因：不同模型的训练数据和对齐方式不同，对相同措辞的理解有差异。

Prompt 脆弱性跨模型对照

Prompt 策略GPT-4 表现Claude 3.5 表现Gemini 1.5 表现脆弱性评级
复杂 CoT（长链推理）准确率 92%准确率 88%准确率 79%高
Few-Shot（5 示例）准确率 89%准确率 91%准确率 85%中
结构化指令（JSON 规则）准确率 95%准确率 94%准确率 93%低
自然语言微调（措辞敏感）准确率 87%准确率 68%准确率 72%极高

结构化指令是降低 Prompt 脆弱性的最有效手段。用 JSON Schema 或 Markdown 表格定义规则，比自然语言描述更"模型无关"。实测：将自然语言规则改为结构化格式后，跨模型准确率方差从 19% 降至 2%。

05

协同架构

最佳实践是 Prompt + Context 协同：

最佳实践是 Prompt + Context 协同：

  • Prompt 负责规则和格式（不变的骨架）
  • Context 负责动态信息（变化的血肉）
  • 两者通过分层架构隔离，互不干扰

Context 的核心技术包括：RAG 检索（从知识库动态注入）、对话历史管理（选择性保留 vs 摘要压缩）、工具调用结果处理。

Prompt + Context 分层协同架构图

分层架构的核心价值在于变更隔离：当 RAG 数据源更新时，只需调整 Context 层的检索策略，Prompt 层完全不受影响。当需要切换模型时，只需微调 Prompt 层的措辞，Context 层完全不受影响。这种正交设计使得系统各部分可以独立演进。

面对 Agent 回答质量问题，工程师最常遇到的困惑是：应该优化 Prompt 还是优化 Context？以下决策框架提供系统化判断方法。

A/B 归因测试法

当无法确定问题来源时，使用A/B 归因测试：

  1. 固定 Prompt，替换 Context（用完美的手动 Context 替代 RAG）→ 如果准确率大幅提升，说明是 Context 问题
  2. 固定 Context，替换 Prompt（用更详细的 CoT 替代简单指令）→ 如果准确率大幅提升，说明是 Prompt 问题
  3. 两者都替换 → 如果提升不及预期，可能是模型能力瓶颈

80/20 法则在 Agent 调优中高度适用：80% 的质量问题来自 Context（信息不够），20% 来自 Prompt（推理不对）。因此，优先优化 Context 的 ROI 几乎总是更高。只有在确认信息充足但推理仍出错时，才应深入调优 Prompt。

Q&A

Q1：Prompt 工程和 Context 工程的核心区别是什么？
Prompt 工程教模型"如何思考"（CoT/Few-Shot/角色设定），Context 工程管理模型"看到什么信息"（RAG/对话历史/工具结果）。前者定义思维模式（不变的骨架），后者控制信息输入（变化的血肉）。类比：教学生解题方法（Prompt）vs 给他合适的参考资料（Context）。
Q2：什么是 Prompt 脆弱性？怎么解决？
Prompt 脆弱性指精心调优的 Prompt 换模型就失效。根因是不同模型训练数据和对齐方式不同，对相同措辞的理解有差异。解决方案：①减少对特定措辞的依赖（用结构化指令替代自然语言微调）；②将规则和信息分离（Prompt 管规则，Context 管信息）；③建立跨模型测试套件（换模型后一键验证）。生产数据：解耦后跨模型迁移成本从 2 周降至 2 小时。
Q3：Prompt + Context 协同架构的分层设计是什么？
三层分离：(1) Prompt 层 — 不变的骨架（角色设定 + 行为规则 + 输出格式），用 CoT/Few-Shot 定义思维模式；(2) Context 层 — 变化的血肉（RAG 检索结果 + 对话历史 + 工具调用输出），按任务动态注入；(3) 隔离层 — 两者通过分层架构互不干扰（Prompt 在前，Context 在后，中间用分隔符隔开）。好处：Prompt 可以跨场景复用，Context 可以独立优化，换模型时只需微调 Prompt 而 Context 不受影响。
Q4：Few-Shot 示范放在 Prompt 层还是 Context 层？
取决于示范的性质：(1) 固定示范（不变的模板案例）→ Prompt 层，如"JSON 输出格式示例"；(2) 动态示范（根据当前任务检索的相似案例）→ Context 层，如"与当前用户问题最相似的 3 个历史回答"。判断标准：是否需要随任务变化。固定示范帮助模型理解"怎么做"（Prompt 的职责），动态示范帮助模型理解"这次该做什么"（Context 的职责）。
Q5：为什么 Context 工程对回答准确率的提升（12%）比 Prompt 工程（7%）更大？
因为大多数回答错误不是"推理方法不对"（Prompt 管的），而是"信息不够或信息错误"（Context 管的）。典型场景：(1) Agent 推理方法正确但缺少关键事实 → 需要更好的 RAG 检索（Context）；(2) Agent 推理方法错误但信息充足 → 需要更好的 CoT（Prompt）。在生产中，前者的比例约 60-70%，后者约 30-40%。所以 Context 优化的 ROI 通常更高。但这不意味着 Prompt 不重要 — 两者是乘法关系（Prompt × Context），任一为零则结果为零。
Q6：如何判断 Agent 的质量问题该优化 Prompt 还是 Context？
使用 A/B 归因测试法：(1) 固定 Prompt，用完美的手动 Context 替代 RAG 检索结果 — 如果准确率大幅提升，说明是 Context 问题（信息不够）；(2) 固定 Context，用更详细的 CoT 替代简单指令 — 如果准确率大幅提升，说明是 Prompt 问题（推理不对）。快速判断口诀：推理乱 → Prompt，信息缺 → Context，格式错 → Prompt，历史断 → Context。实践中 80% 的问题来自 Context 层。
Q7：上下文窗口越大越好吗？如何管理 Token 预算？
不是。128K 窗口不意味着应该塞满 128K tokens。研究表明存在"注意力稀释"效应 — 当低相关文档占据超过 40% 窗口时，模型对核心信息的提取准确率下降约 23%。推荐策略：(1) RAG 结果控制在窗口的 30-40%；(2) 对话历史用滑动窗口 + 摘要压缩；(3) 预留 15-20% 给输出空间；(4) 使用 Token 预算管理器动态分配。实测最优配置：128K 窗口中实际使用约 60-75K tokens 时效果最佳。
Q8：跨模型迁移时，Prompt 和 Context 各自需要多少改动？
基于多个生产系统的数据：(1) Prompt 层 — 约 15% 的措辞需要微调（主要是 CoT 推理模板和角色设定的表述方式），结构化指令（JSON Schema 等）基本无需改动；(2) Context 层 — 几乎不需要改动（RAG 检索、对话历史、工具调用都与模型无关）。整体迁移成本：解耦架构下约 2-4 小时，耦合架构下约 2-3 周。这正是分层架构的核心价值所在。
Q9：什么是"巨型 Prompt 反模式"，如何避免？
巨型 Prompt 反模式指把所有规则、示例、数据塞进一个超长 Prompt（通常 5000+ tokens）。问题：(1) 模型难以从超长指令中提取关键规则；(2) 新场景适配困难（需要修改整个 Prompt）；(3) 跨模型迁移成本极高。正确做法：拆分为 Prompt（仅包含规则 + 格式，控制在 800-1500 tokens）+ Context（动态注入数据和示例）。某团队拆分后准确率提升 14%，新场景适配时间从 3 天降至 2 小时。
