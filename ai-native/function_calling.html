Function Calling

Function Calling Protocol — 工具定义、调用协议、并行调用、结构化输出与跨厂商对比

AI 工程 阅读 ~8 min 10 章
00

概览

Function Calling 的本质：LLM 并不真正执行函数——它生成一个 JSON…

Function Calling 的本质：LLM 并不真正执行函数——它生成一个 JSON 格式的调用意图（函数名 + 参数），由应用层执行后将结果返回给 LLM。核心价值是将 LLM 的自然语言理解能力转化为结构化的 API 调用能力。

01

Function Calling 概述

Function Calling 不是让 LLM "执行函数"，而是让 LLM "描述它想调…

Function Calling 不是让 LLM "执行函数"，而是让 LLM "描述它想调用什么函数"——真正的执行在应用层。这个分离设计是 Agent 架构的基石。

调用流程

Function Calling 调用流程 (以 OpenAI 为例)
用户: "北京明天天气如何？"
LLM 分析意图，生成 tool_calls
{ · name: "get_weather", · arguments: {city: "北京"} · }
应用层执行 get_weather("北京")
结果: {temp: 28, weather: "晴"}
结果以 role:"tool" 消息回传 LLM
LLM 生成自然语言回答:
"北京明天天气晴朗，气温28°C"

Function Calling vs Prompt JSON

维度Function CallingPrompt 要求输出 JSON
格式可靠性训练内置，高度稳定依赖 LLM "按要求做"，经常出错
Schema 约束JSON Schema 校验，参数类型受约束无强制约束
工具选择LLM 从多个工具中智能选择通常只能输出一种固定格式
流程集成与 Agent Loop 原生集成需要额外解析判断
核心价值：Function Calling 是 Agent 的基础设施——没有它，Agent 无法与外部世界交互。它将 LLM 从"文本生成器"升级为"决策引擎"，让 AI 能调用搜索引擎、查询数据库、发送邮件、操作文件系统等。
02

JSON Schema 工具定义

工具描述的质量直接决定 LLM 的调用准确率——description 不是给人看的，是给…

工具描述的质量直接决定 LLM 的调用准确率——description 不是给人看的，是给 LLM 看的。好的描述让 LLM 准确判断"何时调用"和"如何传参"。

工具定义三要素

要素作用关键要点
name函数标识符snake_case，动词+名词（get_weather）
description告诉 LLM 何时调用清晰描述功能+触发时机（"当用户询问天气时调用"）
parameters约束调用参数每个参数有 description，用 enum/minimum/maximum 约束

工具描述最佳实践

原则好的示例差的示例
明确用途"查询数据库中的用户信息，按 ID 或邮箱搜索""查用户"
说明触发时机"当用户请求发送邮件时调用""邮件功能"
参数有描述"ISO 8601 日期格式，如 2024-01-15"无 description
用 enum 约束"enum": ["asc", "desc"]"type": "string"（无约束）
enum 字段极其重要：它约束了参数取值范围，大幅减少幻觉参数。例如 "unit": {"enum": ["celsius", "fahrenheit"]} 确保 LLM 不会传入 "kelvin" 或 "华氏度"。required 字段避免 LLM 遗漏关键参数——始终显式声明哪些参数必填。
03

并行 Function Calling

并行调用由 LLM 自主判断——当模型认为多个工具调用之间没有数据依赖时，会在同一个 res…

并行调用由 LLM 自主判断——当模型认为多个工具调用之间没有数据依赖时，会在同一个 response 中返回多个 tool_calls，应用层并发执行后一次性回传所有结果。

并行 vs 串行性能对比

场景串行调用并行调用加速比
2 个天气查询（各 200ms）~400ms + 2 轮 LLM~200ms + 1 轮 LLM~3x
5 个数据库查询（各 100ms）~500ms + 5 轮 LLM~100ms + 1 轮 LLM~10x
3 个有依赖关系的调用必须串行无法并行1x

每个 tool_call 有唯一的 id，对应的 tool result 必须通过 tool_call_id 匹配——这是并行调用正确工作的关键。开发者不能直接控制是否并行，但可以通过工具描述暗示依赖关系（如"需要先获取 A 才能查 B"）让 LLM 选择串行。

性能洞察：并行调用大幅减少 LLM 轮次——3 个独立查询从 3 轮变为 1 轮，不仅节省 token 还减少总延迟。典型场景：用户问"对比北京和上海天气"，LLM 自动返回两个并行 tool_calls。
04

tool_choice 控制

tool_choice 是给 Agent Loop 的"方向盘"——控制 LLM 是自主决策…

tool_choice 是给 Agent Loop 的"方向盘"——控制 LLM 是自主决策、必须调用还是直接回答。在 Agent 的不同阶段使用不同的 tool_choice 是生产环境的标准做法。

四种 tool_choice 模式

模式行为适用场景
autoLLM 自行决定是否调用工具通用 Agent，LLM 自主决策
requiredLLM 必须调用至少一个工具Agent Loop 非最终轮，防止"偷懒"直接回答
none禁止调用工具，只生成文本最终回答阶段，强制 LLM 给出结论
指定函数强制调用指定函数明确知道要调用哪个工具（如分类/路由）

Structured Output via Tool

一个重要的进阶技巧：定义一个"虚拟工具"（不真正执行），其 parameters schema 就是你想要的输出格式，再用 tool_choice 强制调用它——100% 得到符合 schema 的 JSON。这比 response_format 更灵活，支持嵌套对象、数组、enum 等复杂结构，且几乎所有支持工具的模型都兼容。

Agent Loop 最佳实践：前几轮用 auto 或 required（让 LLM 用工具获取信息），最后一轮用 none（强制生成最终答案，防止无限循环）。

错误处理与重试

错误信息回传是 Function Calling 最重要的设计——不要静默失败或抛异常，而是…

错误信息回传是 Function Calling 最重要的设计——不要静默失败或抛异常，而是把错误信息返回给 LLM，让它自我修正。这比人类程序员的 try-catch 更优雅。

常见错误与处理

错误类型原因处理方式
参数格式错误LLM 生成了不合法的 JSONJSON 修复 + 重新调用
幻觉函数名LLM 调用了不存在的工具返回错误信息 + 可用工具列表，让 LLM 重选
参数值越界数值超出 schema 约束校验后返回错误提示
工具执行失败API 超时 / 网络错误重试 + 降级 + 错误信息回传
结果过大工具返回数据超过 token 限制截断 / 摘要后回传

好的错误回传 vs 差的错误回传

维度好的回传差的回传
内容"表 'users' 不存在，可用的表有: customers, orders""Error"
建议"你可能想查询 'customers' 表"无建议
效果LLM 根据提示修正调用LLM 无法学习，可能重复犯同样错误
  • 返回有意义的错误信息（让 LLM 能自我修正）
  • 结果超 50K 字符时做截断/摘要
  • 设置合理的超时时间（30s 通用，60s 复杂操作）
  • 非幂等工具（发邮件）必须有去重机制
  • 不要静默失败——LLM 不知道发生了什么
  • 不要把 10MB SQL 结果直接塞进 context
  • 不要忽略超时——超时后返回错误让 LLM 换策略
  • 不要返回 "Error" 这种无意义的错误信息

多轮工具使用

多轮 Agent 的核心挑战是 Token 膨胀——每轮包含 assistant(tool_…

多轮 Agent 的核心挑战是 Token 膨胀——每轮包含 assistant(tool_calls) + tool(result) + assistant(response)，10 轮工具调用可能消耗 50K+ tokens，需要对大型结果做摘要压缩。

多轮对话流程

多轮 Tool 使用流程
Round 1
用户 → LLM → tool_call(查询 Q3 销售) → tool_result
Round 2
LLM → tool_call(查询 Q2 销售对比) → tool_result
Round 3
LLM → tool_call(搜索市场报告) → tool_result
Round 4
LLM 综合所有数据 → 生成分析报告（finish_reason: "stop"）
关键约束：消息顺序必须严格 assistant(tool_calls) → tool(result) → 下一轮；tool_call_id 是匹配调用与结果的唯一标识；assistant 消息带 tool_calls 时 content 可以为 null。
上下文管理策略：对超过 2000 字符的工具结果做摘要后再存入历史；超过 10 轮时考虑压缩早期工具调用记录；监控 token 使用量，接近上下文窗口限制时主动终止。

三大厂商的 Function Calling 协议核心思想相同（JSON Schema 定义 + 结构化调用 + 结果回传），但消息格式差异显著——这就是 LiteLLM/LangChain 存在的原因。

高级模式与最佳实践

工具数量直接影响 LLM 选择准确率：5 个工具约 95%，20 个约 85%，50 个约…

工具数量直接影响 LLM 选择准确率：5 个工具约 95%，20 个约 85%，50 个约 70%。超过 20 个工具时建议用分层路由。

工具数量优化

工具数量LLM 选择准确率优化策略
1-5 个~95%直接传递，无需优化
6-15 个~90%好的 description 可以维持准确率
16-30 个~80%分层路由：先选类别，再选具体工具
30+ 个~70%动态工具列表：根据上下文只传相关工具

设计 Checklist

检查项说明
函数命名snake_case，动词+名词（get_weather, search_docs）
Description清晰描述功能+触发时机，包含关键词帮助 LLM 匹配
参数 Schema每个参数有 description，用 enum/minimum/maximum 约束
Required显式列出所有必填参数
错误处理返回有意义的错误信息，不要静默失败
结果大小限制返回数据大小，必要时截断或摘要
幂等性相同参数多次调用应返回一致结果（查询类）
超时设置每个工具有合理的执行超时

生产案例：某电商客服系统

背景：日均 3 万次用户咨询，初期用 8 个工具（查订单、查物流、查退款等），LLM 选择准确率 94%。

问题：业务扩展后工具增至 35 个，选择准确率降至 71%，用户投诉"回答了不相关的内容"。

改造：引入分层路由——先让 LLM 选择工具类别（订单/物流/退款/账户），再展开该类别的 5-8 个具体工具。

效果：选择准确率恢复至 92%，平均响应延迟降低 15%（减少无效工具探索）。

  • 工具数量控制在 5-15 个，超过 20 个用分层路由
  • 开启 Strict Mode（OpenAI）保证 100% schema 合规
  • 非幂等工具（发邮件）必须有去重机制
  • 用 LiteLLM 统一跨厂商接口
  • 不要传 50 个工具给 LLM（选择准确率暴跌）
  • 不要省略参数的 description（LLM 靠它理解参数含义）
  • 不要用 "Error" 作为工具返回（LLM 无法学习）
  • 不要忽略 token 膨胀——多轮工具调用会快速占满上下文

Q&A

核心区别在三个层面：①可靠性：Function Calling 是模型训练时内置的能力，生成…
Function Calling 和直接在 prompt 中要求 LLM 输出 JSON 有什么区别？

核心区别在三个层面：①可靠性：Function Calling 是模型训练时内置的能力，生成的 JSON 格式高度稳定；prompt 方式经常输出格式不规范的 JSON。②Schema 约束：Function Calling 有 JSON Schema 校验，参数类型、枚举值、必填项都有保证。③工具选择：Function Calling 支持 LLM 从多个工具中智能选择，并决定参数。④流程集成：Function Calling 与 Agent Loop 原生集成——finish_reason 告诉你这是工具调用还是最终回答。除非用不支持 Function Calling 的模型，否则都应使用 Function Calling。

并行 Function Calling 在什么情况下会被触发？开发者能控制吗？

并行调用由 LLM 自主判断——当模型认为多个工具调用之间没有数据依赖时，会在同一个 response 中返回多个 tool_calls。典型触发场景：同类查询（"北京和上海天气"→两次 get_weather）、独立操作（"搜索新闻并查汇率"）。开发者不能直接控制是否并行，但可以通过工具描述暗示依赖关系让 LLM 选择串行。OpenAI 提供 parallel_tool_calls 参数可以完全禁用并行。并行调用时，应用层需要并发执行所有工具并一次性回传所有结果。

tool_choice 的 required 和 auto 分别适用什么场景？

auto 是默认值，适合大多数场景——LLM 自主决定是直接回答还是调用工具，适用于通用聊天 Agent。required 强制 LLM 必须调用工具，适用于：①Agent Loop 的非最终轮——确保 Agent 不会提前终止；②结构化抽取——配合虚拟工具强制输出 JSON；③分类/路由——强制调用路由函数。none 用于最终回答轮——强制 LLM 用文本回答而非继续调工具。实际 Agent 通常在 Loop 中动态切换：前几轮用 auto 或 required，最后一轮用 none。

OpenAI、Anthropic、Google 三家的 Function Calling 协议主要差异在哪？

三大差异：①消息格式——OpenAI 用 role: "tool" 回传结果；Anthropic 把 tool_result 放在 role: "user" 的 content block 中；Google 用 role: "function"。②工具定义——OpenAI 用标准 JSON Schema；Anthropic 用 input_schema；Google 用 protobuf FunctionDeclaration。③特色功能——OpenAI 独有 strict mode（100% schema 合规）；Anthropic 的 tool_use 可以夹在 text 之间（更自然的思考+调用交替）；Google 支持 code_execution 作为内置工具。用 LiteLLM 或 LangChain 统一接口屏蔽差异。

如何用 Function Calling 实现 Structured Output？和 response_format 有什么区别？

实现方式：定义一个"虚拟工具"（不真正执行），parameters schema 就是想要的输出格式；用 tool_choice 强制调用它；解析 tool_call.arguments 得到结构化 JSON。与 response_format 的区别：①灵活性——Function Calling 支持更复杂的 schema（嵌套对象、数组、enum）；②兼容性——几乎所有支持工具的模型都支持，response_format 是 OpenAI 特有；③用途——Function Calling 既做结构化输出又做真正的工具调用，response_format 只做格式约束；④控制粒度——可以定义多个虚拟工具实现多种输出 schema。建议：需要真正执行函数→用 Function Calling；只需要 JSON 输出→用 response_format（更简洁）。
