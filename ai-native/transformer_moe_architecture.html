01

MoE 核心思想

MoE 的核心洞察： 不是所有参数都需要参与每个 Token 的计算

条件计算 (Conditional Computation)

MoE 的核心洞察：不是所有参数都需要参与每个 Token 的计算。模型可以拥有巨量参数，但对每个输入只激活其中一小部分 Experts。

  • 总参数量 (Total Parameters)：模型包含的所有可学习参数数量
  • 激活参数量 (Active Parameters)：处理单个 Token 时实际参与计算的参数数量
  • 目标：用更少的计算（FLOPS）获得更大模型的能力
总参数量 ≫ 激活参数量
例：Mixtral 8x7B → 总参数 46.7B，激活参数 12.9B（约 28%）

传统 Dense 模型中，每个 Token 都会经过所有参数。MoE 通过稀疏激活打破了这个约束：

  • 增加参数量 → 增加模型容量/知识存储能力
  • 保持计算量不变 → 推理速度与小模型相当
  • 获得大模型的性能 → 因为总参数量足够大
  • MoE 的核心价值：解耦「模型容量」和「计算成本」
  • Dense 模型：参数量 ≈ 计算量（线性关系）
  • MoE 模型：参数量 ≫ 计算量（稀疏激活）
  • 关键数字：通常只有 10%~30% 的参数被激活

MoE 就像一家拥有上百位专科医生的大医院——每位患者（Token）进门后，由分诊台（Router）只指派 1~2 位最相关的医生来诊治，其余医生同时服务其他患者。医院的「总知识量」极大，但每位患者的「诊疗成本」却很低。

MoE 层结构

在标准 Transformer 中，每个 Block 包含 Self-Attention +…

替换 FFN 层

在标准 Transformer 中，每个 Block 包含 Self-Attention + FFN。MoE 架构将其中的 FFN 层替换为 MoE 层（注意：Attention 层保持不变）。

MoE 层组成

  • Router（门控网络）：决定每个 Token 分配给哪些 Expert
  • N 个 Expert FFN：每个 Expert 是一个独立的 FFN（结构相同，参数不同）
  • 每个 Token 通过 Router 选择 Top-K 个 Expert 进行计算
MoE 层：Router 选专家 → Top-K 加权求和

MoE 层公式

y = Σᵢ∈TopK g_i(x) · E_i(x)

其中：
g(x) = Softmax(W_r · x) — Router 输出门控权重
TopK = argtopk(g(x), K) — 选择权重最大的 K 个 Expert
E_i(x) — 第 i 个 Expert FFN 的输出
g_i(x) — 归一化后的门控权重（仅保留 Top-K，其余置零）
  • MoE 只替换 FFN，不替换 Attention
  • 每个 Expert 的结构完全相同（和原始 FFN 一样），只是参数不同
  • Router 通常是一个简单的线性层
  • Top-K 选择使得大部分 Expert 不参与计算 → 稀疏性

路由策略 (Routing)

最常见的路由策略

Top-K Routing

最常见的路由策略。对每个 Token，Router 计算所有 Expert 的分数，选取分数最高的 K 个：

  • K=1：每个 Token 只发给 1 个 Expert（Switch Transformer）
  • K=2：每个 Token 发给 2 个 Expert（GShard, Mixtral）
  • K 越大 → 计算量越大，但表示能力更强

Token Choice vs Expert Choice

策略Token ChoiceExpert Choice
决策方Token 选择 ExpertExpert 选择 Token
方式每个 Token 挑 Top-K 个 Expert每个 Expert 挑 Top-K 个 Token
负载均衡可能不均衡天然均衡
Token 丢弃可能（容量溢出时）无
代表模型Switch Transformer, MixtralExpert Choice (Zhou et al. 2022)

Router 的实现

# Router 实现伪代码
class Router(nn.Module):
    def __init__(self, d_model, num_experts):
        self.gate = nn.Linear(d_model, num_experts, bias=False)

    def forward(self, x):
        # x: [batch, seq_len, d_model]
        logits = self.gate(x)           # [batch, seq_len, num_experts]
        scores = F.softmax(logits, dim=-1)
        topk_scores, topk_indices = scores.topk(K, dim=-1)
        # 归一化 Top-K scores
        topk_scores = topk_scores / topk_scores.sum(dim=-1, keepdim=True)
        return topk_scores, topk_indices

路由的可微性

Top-K 选择操作本身是不可微的（argmax），但实践中通过以下方式实现梯度流动：

  • Softmax 输出的门控权重 g_i(x) 是可微的
  • 最终输出 y = Σ g_i · E_i(x) 的梯度可以回传给 Router 和被选中的 Expert
  • 未被选中的 Expert 不会收到梯度（这是训练不稳定的来源之一）
  • K=1 计算最快但可能欠拟合；K=2 是最常用的折中
  • Expert Choice 天然解决负载均衡，但实现复杂度更高
  • Router 的可微性：梯度只流向被选中的 Expert
  • 面试常问：为什么不用更大的 K？→ 计算量线性增长，收益递减

负载均衡 (Load Balancing)

训练过程中容易出现「马太效应」：

负载不均衡问题

训练过程中容易出现「马太效应」：

  • 某些 Expert 被频繁选中 → 获得更多梯度更新 → 变得更强 → 更容易被选中
  • 其他 Expert 很少被选中 → 参数几乎不更新 → 逐渐退化
  • 极端情况：所有 Token 只路由到 1-2 个 Expert → Expert 坍塌

辅助损失 (Auxiliary Loss)

在主损失之外添加负载均衡损失，鼓励 Token 均匀分配到各 Expert：

L_balance = α · N · Σᵢ (fᵢ · pᵢ)

其中：
N = Expert 数量
fᵢ = 分配到 Expert i 的 Token 比例（实际负载）
pᵢ = Router 分配给 Expert i 的平均概率
α = 辅助损失权重（通常 0.01~0.1）

理想均匀分布时：fᵢ = pᵢ = 1/N，此时 L_balance 最小

Expert Capacity（容量因子）

限制每个 Expert 最多处理多少 Token：

Expert Capacity = (tokens_per_batch / num_experts) × capacity_factor

capacity_factor 通常为 1.0~1.5
超出容量的 Token 会被丢弃（通过 residual connection 保留原始表示）

Batch Priority Routing

对于超出容量的情况，按 Router 分数排序，优先处理高分 Token：

  • 计算所有 Token 对目标 Expert 的 Router 分数
  • 按分数从高到低排序
  • 容量内的 Token 正常处理，超出的按优先级丢弃
  • 辅助损失是 MoE 训练的标配，几乎所有论文都使用
  • α 太大 → 强制均匀但损害性能；α 太小 → 均衡效果差
  • 容量因子 > 1 允许一定程度的不均衡（flexibility）
  • 面试关键：能解释「为什么会不均衡」以及「如何解决」

Switch Transformer

Google 2022 Switch Transformer 是 MoE 的里程碑工作，大幅…

Google 2022 Switch Transformer 是 MoE 的里程碑工作，大幅简化了 MoE 的设计。

核心创新：Top-1 路由

  • 每个 Token 只路由到 1 个 Expert（K=1）
  • 相比之前的 Top-2（GShard），计算量直接减半
  • 实验证明：Top-1 在相同计算预算下表现更好

为什么 Top-1 就够了？

  • 减少了通信开销（只需将 Token 发给 1 个 Expert）
  • 在相同 FLOPS 预算下，可以使用更多 Expert → 更大模型容量
  • 实验结果：Top-1 + 更多 Expert > Top-2 + 更少 Expert
  • 简单路由 + 大规模 Expert 是更好的 scaling 策略

简化的负载均衡损失

L_aux = α · N · Σᵢ₌₁ᴺ (fᵢ · Pᵢ)

fᵢ = 实际分配到 Expert i 的 Token 比例
Pᵢ = Router 给 Expert i 的平均概率（所有 Token 上取平均）
α = 0.01（默认值）

关键结果

模型总参数激活参数Expert 数相对 T5 加速
Switch-Base7.4B~220M1287x
Switch-Large26B~780M1287x
Switch-XXL395B~3B1284x
  • Switch Transformer 证明了「简单路由 + 大规模」的有效性
  • Top-1 不是「退步」，而是在计算预算约束下的最优选择
  • 128 个 Expert 是常见配置，但每个 Token 只用 1 个
  • 面试必知：Switch Transformer vs GShard 的关键区别

Mixtral (Mistral MoE)

Mistral AI 2023 Mixtral 8x7B 是开源 MoE 的代表作，展示了…

Mistral AI 2023 Mixtral 8x7B 是开源 MoE 的代表作，展示了 MoE 在实际部署中的巨大潜力。

架构设计

  • 8 个 Expert，每个 Token 选 2 个（Top-2）
  • 每个 Expert 的 FFN 大小与 Mistral 7B 相同
  • 总参数量：46.7B
  • 激活参数量：12.9B（约 28%）
  • 推理速度与 12.9B Dense 模型相当

与 Mistral 7B 的关系

对比维度Mistral 7BMixtral 8x7B
总参数7.3B46.7B
激活参数7.3B（全部）12.9B
FFN 结构1 个 FFN8 个 Expert FFN（选 2）
AttentionGQAGQA（相同）
推理 FLOPS~7.3B 参数计算~12.9B 参数计算
性能优秀匹配/超越 LLaMA 2 70B

性能亮点

  • 以 12.9B 激活参数的计算量，达到 70B Dense 模型的性能
  • 在大多数 benchmark 上超越 LLaMA 2 70B
  • 推理速度是 LLaMA 2 70B 的 ~6x
  • 证明了 MoE 在「推理效率」方面的巨大优势
  • Mixtral 的关键卖点：70B 的性能，13B 的推理速度
  • 46.7B ≠ 8×7B，因为 Attention 层是共享的，只有 FFN 是多份
  • Top-2 路由：每个 Token 激活 2/8 = 25% 的 Expert 参数
  • 知识要点：理解「总参数」和「激活参数」的区别对推理的影响

DeepSeek-MoE

DeepSeek 2024 DeepSeek-MoE 系列提出了细粒度 Expert 设计…

DeepSeek 2024 DeepSeek-MoE 系列提出了细粒度 Expert 设计，推动了 MoE 架构的进一步演进。

细粒度 Expert（Fine-grained Experts）

核心思想：与其用少量大 Expert，不如用更多更小的 Expert。

  • 传统 MoE：8 个大 Expert（如 Mixtral）
  • DeepSeek-MoE：64 个小 Expert（每个 Expert 更小）
  • 更细粒度 → 路由更灵活 → Expert 专业化程度更高
  • 类比：8 个「全科医生」vs 64 个「专科医生」

共享 Expert + 路由 Expert

DeepSeek-MoE 的另一创新：

  • 共享 Expert (Shared Experts)：所有 Token 都会经过，捕获通用知识
  • 路由 Expert (Routed Experts)：通过 Router 选择，捕获专业知识
  • 最终输出 = 共享 Expert 输出 + 路由 Expert 加权输出
y = Σⱼ₌₁ˢ E_shared_j(x) + Σᵢ∈TopK g_i(x) · E_routed_i(x)

s = 共享 Expert 数量（如 2）
TopK 从路由 Expert 中选择（如从 64 个中选 6 个）

DeepSeek-V3 的无辅助损失均衡

DeepSeek-V3 提出了不使用辅助损失的负载均衡方法：

  • 为每个 Expert 维护一个动态偏置项 (bias)
  • 负载过高的 Expert → 降低偏置 → 减少被选中的概率
  • 负载过低的 Expert → 提高偏置 → 增加被选中的概率
  • 避免了辅助损失对主损失的干扰
  • 细粒度 Expert 是 DeepSeek 的核心创新：更多更小 → 更灵活的组合
  • 共享 Expert 解决了「通用知识」需要所有 Token 都学到的问题
  • DeepSeek-V3 无辅助损失均衡是重要创新，避免了 α 调参问题
  • 面试必知：对比 Mixtral（少大 Expert）vs DeepSeek（多小 Expert）的设计哲学

训练挑战

MoE 训练需要专门的并行策略：

Expert 并行 (Expert Parallelism)

MoE 训练需要专门的并行策略：

  • 数据并行：每个 GPU 持有完整模型，处理不同数据
  • Expert 并行：不同 Expert 分布在不同 GPU 上
  • 通常与数据并行/张量并行结合使用
Expert Parallelism 示意：
GPU 0: Attention + Expert 1, 2
GPU 1: Attention + Expert 3, 4
GPU 2: Attention + Expert 5, 6
GPU 3: Attention + Expert 7, 8

每个 Token 需要被发送到对应 Expert 所在的 GPU → All-to-All 通信

All-to-All 通信开销

Expert 并行的核心瓶颈：

  • 每个 Token 计算完 Router 分数后，需要发送到目标 Expert 所在的 GPU
  • 这是一个 All-to-All 通信操作（每个 GPU 都要向所有其他 GPU 发送数据）
  • 通信量与 batch_size × hidden_dim 成正比
  • 是 MoE 训练效率的主要瓶颈

训练不稳定性

  • Router 的学习不稳定：早期训练阶段，Router 随机分配导致 Expert 学到相似表示
  • 损失尖峰 (Loss Spikes)：MoE 训练中更容易出现突发的 loss 飙升
  • 解决方案：Router z-loss（限制 Router logits 的大小）、降低学习率

Expert 坍塌问题

最严重的训练问题之一：

  • 表现：训练后只有少数 Expert 被使用，其余 Expert 的参数接近随机初始化
  • 原因：正反馈循环（强者恒强，弱者恒弱）
  • 检测：监控每个 Expert 的使用频率分布
  • 缓解：辅助损失、Expert Dropout、定期重置低使用率 Expert
  • Expert 并行是 MoE 特有的并行策略，理解 All-to-All 通信是关键
  • 训练不稳定是 MoE 的已知问题，Switch Transformer 论文详细讨论了 loss spikes
  • Expert 坍塌 = 模型退化为只有少数 Expert 的「假 MoE」
  • 面试时能解释「为什么 MoE 比 Dense 更难训练」

推理挑战

MoE 推理的最大挑战： 所有 Expert 都需要加载到内存中 ，即使每次只使用其中一小部…

内存需求

MoE 推理的最大挑战：所有 Expert 都需要加载到内存中，即使每次只使用其中一小部分。

  • Mixtral 8x7B：需要加载全部 46.7B 参数（~93GB FP16）
  • 对比：13B Dense 模型只需 ~26GB FP16
  • 内存需求 ≈ 总参数量，而非激活参数量

Expert Offloading

将不活跃的 Expert 放到 CPU 内存或磁盘，需要时再加载：

  • GPU 内存只保留当前活跃的 Expert
  • 根据 Router 预测，提前预取 (prefetch) 即将使用的 Expert
  • 代价：增加延迟（PCIe/NVLink 传输时间）
  • 适合内存受限场景（消费级 GPU）

与 Dense 模型的推理速度对比

指标MoE 模型同性能 Dense 模型同激活参数 Dense 模型
内存占用高（全部参数）高（全部参数=激活参数）低
计算 FLOPS低高相同
首 Token 延迟中高低
吞吐量高低中
Batch 推理效率可能有 load imbalance稳定稳定
MoE 推理的常见误区：「激活参数少 = 推理一定快」。实际上，内存带宽瓶颈、All-to-All 通信、Expert 负载不均衡都可能影响实际推理速度。MoE 在高吞吐场景（如 serving）优势更明显。
  • MoE 推理「计算便宜但内存贵」→ memory-bound 而非 compute-bound
  • Expert Offloading 是资源受限时的妥协方案，会增加延迟
  • Batch 推理时 MoE 优势更大（因为不同 Token 可能路由到不同 Expert）
  • 面试必知：MoE 推理的瓶颈是内存而非计算

训练 FLOPS低（同性能下）高
训练稳定性较差（需要额外技巧）较好

何时选择 MoE？

  • ✅ 需要大模型性能但计算预算有限
  • ✅ 高吞吐推理场景（serving 大量请求）
  • ✅ 有充足 GPU 内存（或可以做模型并行）
  • ✅ 愿意接受更复杂的训练流程

何时选择 Dense？

  • ✅ GPU 内存有限（如单卡部署）
  • ✅ 需要极低延迟（如实时对话）
  • ✅ 训练资源有限，需要稳定的训练
  • ✅ 模型蒸馏/量化部署场景
  • MoE 的核心 trade-off：用内存换计算效率
  • 行业趋势：越来越多顶级模型采用 MoE（GPT-4 被推测为 MoE）
  • MoE 不是万能的 → 需要根据具体场景权衡
  • 面试终极问题：如果让你设计一个新的 LLM，你会选 MoE 还是 Dense？为什么？

📝 Q&A

核心思想 ：条件计算（Conditional Computation）
Q1: MoE 的核心思想是什么？它解决了什么问题？

核心思想：条件计算（Conditional Computation）。模型拥有大量参数（大容量），但每个 Token 只激活其中一小部分参数进行计算。

解决的问题：传统 Dense 模型中，模型容量（参数量）和计算成本严格绑定。想要更好的性能就必须增加参数量，同时计算成本线性增长。MoE 解耦了这两者：

  • 总参数量决定模型容量/知识存储
  • 激活参数量决定实际计算成本
  • 结果：用 13B 的计算获得 70B 的性能
Q2: MoE 层的结构是什么？它替换了 Transformer 中的哪个组件？

MoE 层替换 Transformer Block 中的 FFN 层（Attention 层不变）。

MoE 层由两部分组成：

  • Router（门控网络）：一个线性层 + Softmax，输入 Token 表示，输出对各 Expert 的分配权重
  • N 个 Expert FFN：每个 Expert 结构相同（和原始 FFN 一样），参数独立

计算流程：Token → Router 计算分数 → 选 Top-K Expert → 加权求和输出 y = Σ g_i(x) · E_i(x)

Q3: 什么是负载均衡问题？如何解决？

问题：训练中某些 Expert 被过度使用（获得更多梯度 → 变得更强 → 更被选中），其他 Expert 闲置退化，导致 Expert 坍塌。

解决方案：

  • 辅助损失：L_balance = α · N · Σ(fᵢ · pᵢ)，鼓励均匀分配
  • Expert Capacity：限制每个 Expert 最多处理的 Token 数
  • Expert Choice：让 Expert 选择 Token（天然均衡）
  • 动态偏置（DeepSeek-V3）：无辅助损失的自适应均衡
Q4: Switch Transformer 的主要创新是什么？为什么 Top-1 就够了？

主要创新：将路由简化为 Top-1（每个 Token 只发给 1 个 Expert），相比之前的 Top-2 计算量减半。

为什么 Top-1 够了：

  • 在固定计算预算下，Top-1 允许使用更多 Expert → 模型容量更大
  • 实验证明：Top-1 + 128 Expert > Top-2 + 64 Expert
  • 减少了 All-to-All 通信（只需发送到 1 个目标 GPU）
  • 核心洞察：对于 MoE，增加 Expert 数量比增加每个 Token 使用的 Expert 数更有效
Q5: Mixtral 8x7B 的参数量为什么是 46.7B 而不是 56B (8×7B)？

因为 Attention 层是共享的，只有 FFN 层是多份：

  • 每个 Transformer Block = Attention + FFN
  • MoE 只将 FFN 复制为 8 份，Attention 保持 1 份
  • 总参数 = Attention 参数 + 8 × FFN 参数 + Embedding 参数
  • 7B 模型中 FFN 约占 2/3 参数 → 8 × (2/3 × 7B) + 1/3 × 7B ≈ 39B + 2.3B + 其他 ≈ 46.7B

激活参数 12.9B = Attention 参数 + 2 × 单个 Expert FFN 参数（Top-2 选 2 个）

Q6: DeepSeek-MoE 的「细粒度 Expert」和「共享 Expert」有什么优势？

细粒度 Expert（更多更小的 Expert）：

  • 更灵活的组合：64 个小 Expert 选 6 个 → C(64,6) 种组合 vs 8 个大 Expert 选 2 → C(8,2) = 28 种
  • 每个 Expert 更专业化：小 Expert 可以专注于更细分的知识领域
  • 路由更精准：细粒度选择更容易匹配 Token 的需求

共享 Expert：

  • 捕获所有 Token 都需要的通用知识（如语法、常识）
  • 减轻路由 Expert 的负担：路由 Expert 可以专注于专业知识
  • 提供训练稳定性：即使路由有问题，共享 Expert 保证基础能力
Q7: MoE 训练中的 Expert 坍塌是什么？如何检测和解决？

Expert 坍塌：训练后只有少数 Expert 被有效使用，其余 Expert 参数接近随机初始化，形成「假 MoE」。

原因：马太效应正反馈循环 — 被选中的 Expert 获得更多梯度更新 → 变得更强 → 更容易被选中 → ...

检测方法：

  • 监控每个 Expert 的使用频率分布（应接近均匀）
  • 计算 Expert 使用的熵（越高越均匀）
  • 观察验证 loss 是否开始停滞

解决方案：辅助损失、Expert Dropout（随机禁用热门 Expert）、定期重置低使用率 Expert、Router z-loss。

Q8: MoE 推理为什么「计算便宜但内存贵」？

计算便宜：每个 Token 只激活 Top-K 个 Expert（通常占总 Expert 的 12%~25%），FLOPS 远小于同参数量的 Dense 模型。

内存贵：推理时无法预知哪些 Expert 会被需要，所以所有 Expert 必须常驻内存。

  • 例如 Mixtral 46.7B：即使每次只用 12.9B 参数的计算量，内存仍需容纳全部 46.7B
  • 相比之下，12.9B Dense 模型只需约一半内存就能达到相同计算量

实际影响：MoE 推理通常是 memory-bandwidth-bound 而非 compute-bound，特别是在小 batch size 时。大 batch 推理（serving 场景）时 MoE 优势更明显。

Q9: Expert Parallelism 中的 All-to-All 通信是什么？为什么是瓶颈？

All-to-All 通信：在 Expert 并行中，不同 Expert 分布在不同 GPU 上。每个 Token 需要被发送到其目标 Expert 所在的 GPU，这导致所有 GPU 都需要相互发送数据。

流程：

  • 所有 GPU 并行计算 Router → 确定每个 Token 的目标 Expert
  • All-to-All 通信：Token 分发到目标 GPU（dispatch）
  • 各 GPU 上的 Expert 并行处理收到的 Token
  • All-to-All 通信：结果发回原 GPU（combine）

为什么是瓶颈：通信量 = O(batch_size × seq_len × hidden_dim)，与数据规模线性增长；跨节点通信比计算慢几个数量级；负载不均衡会导致部分 GPU 空等。

Q10: 如果让你设计一个新的大语言模型，你会选择 MoE 还是 Dense？如何决策？

这是一个开放性问题，需要根据具体约束条件回答。关键决策因素：

选择 MoE 当选择 Dense 当
目标性能要求高（如 GPT-4 级别）部署环境内存有限
有充足的 GPU 集群（训练+推理）需要单卡/少卡部署
高吞吐推理是核心需求低延迟是核心需求
训练计算预算有限但想要大模型性能需要简单可靠的训练流程
团队有 MoE 训练经验需要方便地做蒸馏/量化

推荐回答思路：先明确约束条件（性能目标、计算预算、部署环境），然后分析 trade-off，最后给出结论并说明理由。展示你理解 MoE 不是银弹，需要权衡利弊。
