02

贪心解码：速度与确定性的极致

贪心解码 = 每一步都选概率最高的 token——局部最优的极致追求，代价是可能陷入复读陷阱

贪心解码 = 每一步都选概率最高的 token——局部最优的极致追求，代价是可能陷入复读陷阱。

核心机制

在每一步 t，贪心解码选择概率最高的 token：

x_t = argmax P(x_t | x_1, ..., x_{t-1})

实现极其简单：只需一次 argmax 操作，零额外计算开销。在 HuggingFace Transformers 中，这是默认的解码策略。

贪心解码的复读困境

当上下文概率分布高度集中时，贪心解码容易陷入重复循环。例如输入"他很可爱"后，模型可能反复输出相似内容，因为前文的强信号使特定 token 的概率持续占据主导地位。

现象根因分析解决方向
连续重复同一短语上下文概率集中，局部最优 ≠ 全局最优引入重复惩罚（Repetition Penalty）
生成内容过于保守始终选最高概率，回避低概率但有价值的token切换到采样策略
长文本质量下降错误累积，一步错步步错限制生成长度或引入 Contrastive Search

生产场景：贪心解码是最佳选择

在结构化输出场景中，贪心解码的稳定性和确定性是不可替代的优势：

  • 代码生成：代码语法严格，不需要"创意"，需要精确
  • SQL 生成：SQL 有唯一正确答案，多样性反而引入错误
  • JSON Schema 输出：格式约束下，最高概率 = 最合规
  • Function Calling：工具调用参数需要精确，不需要随机性

生产建议：对于确定性任务，设置 temperature=0 或 do_sample=False。Anthropic Claude API 允许 temperature 在 0.0-1.0 范围，OpenAI 和 Gemini 允许 0.0-2.0，三者默认值均为 1.0。

03

Beam Search：全局最优的追求与时代局限

Beam Search 同时维护 K 条候选路径，最终选整体概率最高的序列——能"看到"贪心…

Beam Search 同时维护 K 条候选路径，最终选整体概率最高的序列——能"看到"贪心解码错过的更优路径，但代价是 K 倍的显存和计算。

工作原理

Beam Search (beam_width=3) 示例：

Step 1:  生成候选 → 保留 Top-3 序列
         "The" (0.4) | "A" (0.3) | "It" (0.15)

Step 2:  每条路径扩展 → 共产生 3×vocab 候选 → 保留 Top-3
         "The cat" (0.32) | "The dog" (0.28) | "A cat" (0.21)

Step 3:  继续扩展 → 保留 Top-3
         "The cat sat" (0.25) | "The dog sat" (0.22) | ...

...直到所有路径生成 EOS 或达到最大长度
最终选择：整体概率最高的完整序列

核心参数

参数含义典型值影响
num_beams同时维护的候选路径数4-8↑ 质量↑ 但显存×K
length_penalty长度惩罚系数0.6-1.0防止偏好短序列
early_stopping首个完成即停止True/False加速但可能错过更优解
no_repeat_ngram_size禁止N-gram重复2-3缓解复读问题

Beam Search 在 LLM 时代"失宠"的原因

  1. 本质矛盾：开放式生成任务没有唯一最优解，而 Beam Search 追求整体概率最高——这反而导致生成内容枯燥、缺乏多样性
  2. 显存瓶颈：需维护 K 条路径的 KV Cache，显存消耗线性增长。在 70B 模型上 beam_width=4 意味着 4 倍 KV Cache
  3. 与 Flash Attention 不兼容：Flash Attention 的 IO-aware 优化假设单次前向传播，Beam Search 的多路径并行与之冲突
  4. 吞吐量线性下降：beam_width=4 时吞吐量约为贪心的 1/4，在大模型场景下不可接受
Beam Width质量提升吞吐量代价适用场景
1（贪心）基线1x代码/结构化输出
4+5-10%~4x机器翻译
8+8-15%~8x受约束生成
16+边际递减~16x+一般不推荐

Diverse Beam Search 变体

为了缓解 Beam Search 输出过于相似的问题，Diverse Beam Search 将 beam 分成多个组，组间强制引入多样性惩罚。例如 num_beams=4, num_beam_groups=2, diversity_penalty=0.5，让不同组产出风格各异的候选。

采样策略：Temperature、Top-K、Top-P 与 Min-P

采样 = 按概率分布掷骰子

采样 = 按概率分布掷骰子。Temperature 控制骰子的"偏向程度"，Top-K/Top-P 控制"哪些候选有资格上骰子"。

Temperature：概率分布的"锐化旋钮"

Temperature 的数学公式：P(tokeni) = exp(zi/T) / Σ exp(zj/T)

Temperature 值效果分布形态推荐场景
T → 0退化为贪心解码极度尖锐，几乎只有 argmax代码生成、JSON
T = 0.2-0.5聚焦高概率 token较尖锐，少量多样性技术写作、RAG 回答
T = 0.7-1.0平衡质量与多样性原始分布通用对话、摘要
T = 1.0-1.5增强多样性扁平化，长尾token概率提升创意写作、头脑风暴
T > 1.5过度随机接近均匀分布一般不推荐

Top-K：硬截断

Top-K 只保留概率最高的 K 个 token，其余概率置零后重新归一化。优点是简单直接，缺点是 K 值是固定的——无论分布是尖锐还是平坦，都只保留 K 个候选。

Top-P（Nucleus Sampling）：动态截断

Top-P 按累计概率动态截断：保留累计概率刚好达到 P 的最小 token 集合。当分布尖锐时自动保留少量候选，分布平坦时自动扩大范围——比 Top-K 更灵活。

Top-K vs Top-P 对比（假设 P=0.9, K=5）：
场景A：分布尖锐（1个token概率0.85） · Top-K=5 → 保留5个token（含4个噪声token） · Top-P=0.9 → 保留2个token（0.85+0.06=0.91 ✓） · 场景B：分布平坦（Top-5概率分别为 0.22, 0.20, 0.18, 0.16, 0.14） · Top-K=5 → 保留5个token · Top-P=0.9 → 保留5个token（0.22+0.20+0.18+0.16+0.14=0.90 ✓）
Top-P 能根据分布自适应调整候选集大小

Min-P：2025-2026 年的新默认

Min-P 设定一个相对阈值：只保留概率 ≥ (最高概率 × min_p) 的 token。例如 min_p=0.05 意味着如果最高概率 token 为 0.8，则只保留概率 ≥ 0.04 的候选。它结合了 Top-P 的自适应性，同时避免了 Top-P 在极端分布下保留过多低质量 token 的问题。

截断策略截断方式自适应性推荐值趋势
Top-K固定数量K无20-50逐渐被替代
Top-P累计概率P有0.85-0.95仍广泛使用
Min-P相对阈值强0.05-0.12025-2026新默认
Typical-P信息熵过滤强0.9-0.95小众但有优势

现代采样管线推荐顺序（2026最佳实践）：原始 logits → 重复惩罚 → DRY → Top-K（可选）→ Top-P / Min-P → Temperature → XTC（仅创意场景）→ softmax → 采样。Temperature 放在截断之后是因为它不影响截断结果的相对排序。

推测解码：用"小模型起草+大模型验证"突破速度瓶颈

推测解码的核心思想：用小模型快速生成 N 个候选 token，大模型一次性并行验证——如果验…

推测解码的核心思想：用小模型快速生成 N 个候选 token，大模型一次性并行验证——如果验证通过，一次前向传播就能产出 N 个 token 而非 1 个，提速 2-5 倍且输出分布完全不变。

为什么自回归解码慢？

自回归解码的瓶颈不在计算，而在内存带宽。以 70B 参数模型（FP8）为例：每生成 1 个 token 需要从 HBM 读取约 70GB 权重，在 H200 GPU（~4.8 TB/s 带宽）上单 token 延迟地板约 14ms。算术强度仅约 2 ops/byte，而 GPU 需要 300+ ops/byte 才能达到计算饱和——解码阶段 95% 的时间在等内存。

推测解码流程（Draft 1B → Target 70B）
1. Draft Model 起草
小模型快速生成 N 个候选 token [tok₁…tok₄]
2. Target Model 并行验证
大模型一次前向传播，并行验证所有 N 个 token
3. 拒绝采样决定前进步数
  • 全部接受前进 N 步
  • 部分接受前进 k 步（k<N）+ 重采样
  • 全部拒绝前进 1 步 + 重采样

数学保证：输出分布完全不变

推测解码通过 拒绝采样（Rejection Sampling）保证输出分布与直接用目标模型采样完全一致。接受概率公式：

P_accept = min(1, P_target(x) / P_draft(x))

这意味着质量零损失——不是近似，而是数学上的精确等价。

Self-Consistency 与高级解码策略

Self-Consistency = 让模型用不同采样路径回答同一问题多次，然后多数投票——…

Self-Consistency = 让模型用不同采样路径回答同一问题多次，然后多数投票——用"群体智慧"对抗单次采样的不稳定性。

Self-Consistency 工作原理

Self-Consistency 流程：

问题："24 ÷ 3 + 5 × 2 = ?"

路径1 (T=0.7): "24÷3=8, 5×2=10, 8+10=18"  → 答案: 18
路径2 (T=0.8): "先算24÷3得8，再5×2得10，加起来18" → 答案: 18
路径3 (T=0.9): "24÷3=8, 然后5×2=10, 结果是18"   → 答案: 18
路径4 (T=1.0): "让我算算... 24÷3=7? 不对，=8..." → 答案: 18
路径5 (T=1.1): "24÷3=8, 5×2=10... 嗯... 20?"   → 答案: 20 ✗

多数投票：18 (4票) vs 20 (1票) → 最终答案: 18 ✓

适用场景与代价

维度Self-Consistency单次采样

推理成本N 倍（N=采样路径数，通常5-20）1x
延迟N 倍串行或并行（受限于batch size）1x
适用任务数学推理、逻辑题、代码验证通用

其他进阶策略

策略核心思想应用场景
Contrastive Search在似然度和退化度之间平衡，减少重复长文本生成
Mirostat自适应控制困惑度（perplexity），维持输出"惊喜度"创意写作
DRY（Don't Repeat Yourself）智能重复惩罚，区分"合理重复"和"病态重复"代码生成中的长序列
XTC（Exclude Top Choices）偶尔排除最高概率 token，强迫模型探索极端创意场景

2024年研究发现：采样策略的随机性结合 Self-Consistency，可以在封闭式任务上超越确定性方法——虽然单次不如 Beam Search 稳定，但多次投票后的准确率更高。这是"用随机性换多样性，用投票换可靠性"的精妙平衡。

GPU 能耗视角

2025年一项系统研究表明，不同解码策略对 GPU 能耗影响巨大。Beam Search 虽然质量可能更高，但能耗成倍增长；而合适的采样策略在质量损失极小的情况下可显著降低能耗。在绿色 AI 的趋势下，解码策略选择也需考虑能效比。

  • 按任务类型选择策略，不要一个参数打天下
  • 生产环境固定 seed 保证可复现性
  • 对 RAG 场景优先 Temperature=0.1-0.3 + Min-P=0.05
  • 大规模部署时启用推测解码（vLLM 0.7+ 默认开启）
  • 监控 Acceptance Rate 指标，<50% 需调优
  • 不要对代码生成使用高 Temperature（会产生语法错误）
  • 不要在 70B 模型上用大 beam_width（显存爆炸）
  • 不要忽略 Min-P——它是 2026 年的最佳实践默认值
  • 不要同时启用 Top-K 和 Top-P——通常只需一个
  • 不要在没有 Self-Consistency 的情况下对数学推理用高 Temperature

Q&A

贪心解码和 Beam Search 的核心区别是什么？为什么 LLM 时代 Beam Search 不再主流？
贪心解码每步只保留 1 个最优 token，Beam Search 同时维护 K 条路径最终选整体最优序列。Beam Search 在 LLM 时代失宠的三个核心原因：(1) 开放式生成没有唯一最优解，Beam 追求全局最优反而导致输出枯燥；(2) K 条路径需要 K 倍 KV Cache，在 70B 模型上显存消耗巨大；(3) 与 Flash Attention 等现代优化不兼容，吞吐量线性下降。
Temperature、Top-K、Top-P 三者如何配合？推荐的使用顺序是什么？
2026 年推荐实践：(1) 首先用 Min-P（0.05-0.1）做相对阈值截断，替代 Top-K 的硬截断；(2) 可选叠加 Top-P（0.85-0.95）做累计概率截断；(3) 最后应用 Temperature 调节分布锐度。关键原则是 Temperature 放在截断之后，因为截断只看相对排序不受 Temperature 影响，这样不同 Temperature 下截断行为更一致。
推测解码如何保证输出质量不变？实际加速比受什么因素影响？
推测解码通过拒绝采样（Rejection Sampling）保证输出分布与目标模型完全一致——接受概率 P_accept = min(1, P_target/P_draft)。当草稿模型与目标模型分布越接近，接受率越高，加速比越大。实际加速比取决于：(1) 草稿模型质量（接受率 70-85% 为健康范围）；(2) 草稿长度（通常 4-8 tokens）；(3) 任务类型（结构化文本接受率高于创意文本）。2026 年 DFlash 方法在 Blackwell GPU 上实现了最高 15 倍加速。
Self-Consistency 适用于哪些任务？成本如何控制？
Self-Consistency 最适合有"正确答案"的推理任务：数学题、逻辑推理、代码验证等。它通过多次采样（通常 5-20 条路径）+ 多数投票来提升准确率，代价是 N 倍的推理成本和延迟。成本控制方法：(1) 用较低 Temperature（0.7-1.0）减少路径发散；(2) 设置早停——如果前 5 条路径中 4 条一致就提前终止；(3) 只在高价值/高风险查询上启用。不适用于开放式生成任务（无正确答案可投票）。
Min-P 为什么被认为是 2026 年的最佳默认截断策略？
Min-P 设定相对阈值：只保留概率 ≥ (最高概率 × min_p) 的 token。相比 Top-K（固定数量）和 Top-P（累计概率），Min-P 的优势在于：(1) 自适应性强——分布尖锐时自动保留少量候选，平坦时自动扩大；(2) 避免了 Top-P 在极端分布下保留过多低质量 token 的问题；(3) 语义更直观——"至少要有最优候选的 5% 概率才值得考虑"。推荐值 min_p=0.05-0.1，几乎所有场景都适用。
如何在生产环境中为不同场景配置解码参数？
按任务类型配置：(1) 代码/JSON 生成：temperature=0, constrained generation；(2) RAG 回答：temperature=0.1-0.3, min_p=0.05, top_p=0.9；(3) 通用对话：temperature=0.7, min_p=0.05, top_p=0.9；(4) 创意写作：temperature=0.8-1.2, min_p=0.03, top_p=0.95。大规模部署时启用推测解码（vLLM 0.7+ 默认开启），监控 Acceptance Rate。生产环境务必固定 random seed 保证可复现性。
DRY 和 XTC 这些新策略分别解决什么问题？
DRY（Don't Repeat Yourself）解决长序列中的重复问题——它能区分"合理重复"（如代码中的循环结构）和"病态重复"（无意义的复读），比简单的 Repetition Penalty 更智能。XTC（Exclude Top Choices）在创意场景中偶尔排除最高概率 token，迫使模型探索更有趣的表达——适用于角色扮演和极端创意写作，但在生产环境中需谨慎使用，因为它会显著降低输出可控性。
