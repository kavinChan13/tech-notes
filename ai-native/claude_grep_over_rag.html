概览

Claude Code 弃 RAG 转 Grep 的本质不是"抛弃检索"，而是"抛弃预索引检…

Claude Code 弃 RAG 转 Grep 的本质不是"抛弃检索"，而是"抛弃预索引检索"——Agent 自己控制检索循环，用实时搜索取代预先构建的向量索引。决策权从流水线回归模型。

01

事件背景：Anthropic 的架构转向

2026 年 2 月，Claude Code 创始人 Boris Cherny 在 X（原…

2026 年 2 月，Claude Code 创始人 Boris Cherny 在 X（原 Twitter）上公开披露：Claude Code 早期版本使用了标准 RAG 方案——Voyage Embeddings 配合本地向量数据库进行语义代码检索。团队花了数月时间构建和验证该方案，最终结论是全部砍掉，转向Agentic Search（模型直接调用 grep、glob、ls 进行实时搜索）。

Boris Cherny 的原话："Early versions of Claude Code used RAG + a local vector db, but we found pretty quickly that agentic search generally works better. It is also simpler and doesn't have the same issues around security, privacy, staleness, and reliability."

核心启示：年收入超 $1B 的产品创始人公开告诉你——一个模型用基本 Unix 搜索命令就打败了精密的检索增强流水线。RAG 不是在边缘场景输的，而是在"输出是否让开发者觉得对"这个核心指标上全面落败。

这个决策之所以震撼行业，是因为它违背了"越复杂越先进"的技术叙事——50 年前诞生的 grep 在代码搜索场景中击败了 2024 年最前沿的向量检索技术。

02

RAG 的三大结构性缺陷

Anthropic 团队在内部测试中发现 RAG 方案存在三个根因级缺陷，每一个都足以在代码…

Anthropic 团队在内部测试中发现 RAG 方案存在三个根因级缺陷，每一个都足以在代码搜索场景中导致系统性失败。

2.1 缺陷一：黑盒不可诊断

标准 RAG 流水线包含 5 个串联环节：文档分块 → Embedding 向量化 → 向量存储 → 查询向量化 → ANN 检索。当检索结果不正确时，黑盒不可诊断问题浮现——无法区分问题出在哪个环节。是分块策略切断了关键上下文？是 Embedding 模型对代码语义理解不准？是向量数据库的 ANN 近似搜索丢失了精确匹配？还是查询本身向量化偏差？

RAG 黑盒诊断困境 用户搜索: "处理用户认证的代码在哪里？" RAG 返回: ["payment_handler.py", "logging_config.yaml"] ← 错误结果 问题定位困难: ├→ 分块问题? ─ payment_handler.py 的 chunk 恰好包含"auth"字样 ├→ Embedding问题? ─ "认证" 和 "支付处理" 在向量空间距离过近 ├→ ANN问题? ─ 近似搜索跳过了真正相关的 auth.py ├→ 查询问题? ─ "用户认证" 被向量化为 "身份验证" 的同义词 └→ 无法确定! ─ 每个环节都可能出错，且错误会叠加 Grep 的确定性: rg "authenticate|authorization|login" --type=py ├→ 找到 → 结果100%正确（精确字符串匹配） └→ 未找到 → 明确知道该关键词不存在（确定性失败）

2.2 缺陷二：精度链式衰减

RAG 流水线的 5 个环节各自引入精度损耗。假设每个环节达到 90% 的精度——这在工程上已经是很高的标准——串联后的整体精度将跌破 60%。这就是精度链式衰减效应。

流水线环节单环节精度（乐观）累计精度失败模式
文档分块90%90%函数被切割成两个 chunk，语义断裂
Embedding 向量化92%82.8%代码标识符的语义压缩丢失信息
向量存储索引95%78.7%ANN 近似搜索遗漏精确匹配
查询向量化88%69.2%用户查询的向量表示偏离真实意图
Top-K 截断85%58.8%相关结果排在 K+1 位被丢弃

链式衰减的数学本质：5 个 90% 精度的环节串联 = 0.9⁵ ≈ 59%。这意味着即使在最乐观的假设下，RAG 流水线也只有不到六成的概率返回正确结果。而 Grep 的精确匹配不存在链式衰减——要么找到（100% 正确），要么没找到（确定性失败）。

2.3 缺陷三：索引同步成本

代码库是活的——每次 merge PR、每次重构、每次 hotfix，向量索引就会与代码实际状态产生偏差。这就是索引漂移问题。大型项目的完整重建索引需要几十分钟到数小时，而增量同步可能遗漏跨文件的重命名和重构操作。

同步场景RAG 索引影响Grep 影响
merge 新 PR索引过期，需重新 Embedding 新增/修改的文件零影响——搜索永远看到最新文件状态
跨文件重命名旧名称的向量仍然存在，产生过时结果直接搜索新名称即可
大规模重构需要完整重建索引（几十分钟到数小时）零影响
分支切换每个分支需要独立索引，或索引频繁切换零影响——grep 搜索当前工作目录
首次使用需要预先构建索引（等待时间）claude . 在新仓库中即时工作

索引同步的本质矛盾：代码库每秒都在变化，但向量索引是一个静态快照。维护"索引与代码的一致性"本身就是一项持续性的工程投入——而 Grep 完全不需要这项投入。

03

Agentic Grep 的工作原理

Agentic Search（Agentic Grep） 不是一个独立的搜索系统，而是一种让…

Agentic Search（Agentic Grep）不是一个独立的搜索系统，而是一种让模型自主驱动搜索循环的架构模式。模型决定搜什么、怎么搜、搜几轮——而不是将搜索委托给预构建的索引。

Claude Code Agentic Search 工作流程
用户问题: "项目中处理用户认证的代码在哪里？"
Agent 决策层 (Claude 模型)
第1步: Glob("**/auth*", "**/login*")
找到: src/auth/handler.ts, src/middleware/login.ts
第2步: Grep("authenticate|authorization|verifyToken", --type=ts)
找到: src/auth/handler.ts:42, src/services/user.ts:87
第3步: Read("src/auth/handler.ts")
读取完整文件，理解认证逻辑
第4步: Grep("import.*from.*auth/handler")
追踪谁调用了认证模块
第5步: 综合所有发现 → 生成回答
核心特征: · • 每步都是模型的自主决策（不是固定流水线） · • 可以根据中间结果动态调整搜索策略 · • 永远读取最新文件状态（无索引漂移） · • 搜索失败时可立即尝试不同关键词

Claude Code 的八大核心工具

工具功能在搜索中的角色
Bash执行任意 Shell 命令万能适配器，驱动 git/docker/npm 等
Grep（ripgrep）按正则搜索文件内容主要内容搜索工具，精确匹配
Glob按文件名模式匹配近零 Token 消耗，快速定位文件
Read读取完整文件深入理解搜索结果中的文件
Edit编辑文件搜索结果确认后进行修改
Write创建/覆写文件基于搜索结果创建新文件
Task启动子 Agent并行搜索多个子任务
TodoWrite任务列表管理追踪多步骤搜索进度

ripgrep（rg）是 Claude Code Grep 工具的底层引擎——用 Rust 实现，利用 SIMD 指令和多线程并行扫描，在 100 万行代码的仓库中搜索一个函数名通常 <50ms。它自动尊重 .gitignore 文件，跳过二进制文件和隐藏目录。Claude Code 通过 @vscode/ripgrep npm 包内置分发——这也是 VS Code 搜索功能使用的同一个包。

Agentic Search 的核心优势不在于搜索技术本身（grep 谁都会用），而在于"模型自主决策搜索策略"——先找文件名，再搜内容，读全文，追踪引用，每一步都根据上一步结果动态调整。这种灵活性是静态 RAG 流水线无法匹敌的。

04

混合架构：Grep + Vector Search + Agent 决策

弃用 RAG 不等于否定语义检索的所有价值

弃用 RAG 不等于否定语义检索的所有价值。在大规模代码库（50 万行+）和跨语言语义搜索场景中，纯 Grep 方案存在 Token 成本急剧上升的问题。行业正在收敛到混合架构——Grep 处理精确匹配，Vector Search 处理语义场景，Agent 自主决策使用哪个。

混合检索架构设计
Agent 接收搜索请求
请求类型判断
精确匹配请求 → Grep 通道
"找 handleUserLogin 函数" rg "handleUserLogin" · "搜 AUTH_TOKEN 常量" rg "AUTH_TOKEN" · 特征: 知道精确标识符 零配置, 100%精确
语义模糊请求 → Vector Search 通道
"处理退款的逻辑在哪" embed(query) → ANN · "和用户权限相关的代码" 语义匹配代码块 · 特征: 不知道精确名称 能找到语义相关代码
结构化探索 → AST/LSP 通道
"findAllUsers 的调用链" 符号解析 + 引用追踪 · "这个接口被哪些模块依赖" 依赖图查询 · 特征: 需要结构信息 超越文本搜索
结果融合
去重 → 综合评分 → Agent 判断相关性 → 回答

三种检索通道对比

维度Grep 精确匹配Vector Search 语义检索AST/LSP 结构分析
适用场景已知函数名/变量名/错误码"大概知道功能但不记得名字"调用链追踪/依赖分析
精确度100%（字符串精确匹配）~70–85%（语义近似）100%（语法结构精确）
配置成本零（本地工具）中（需 Embedding 模型+向量库）中（需 tree-sitter/LSP）
实时性始终最新需增量同步需增量解析
Token 成本低（仅命令+结果）中（Schema+结果）中（结构化输出）
同义词理解❌ login ≠ authenticate✅ 语义等价❌ 按符号名匹配

混合架构的核心原则：决策权归属模型——Agent 根据搜索请求的特征（精确 vs 模糊 vs 结构化）自主选择最佳检索通道，而不是由流水线预先决定。这正是"Agentic"的含义：Agent 是决策者，不是流水线中的一个环节。

性能对比实测数据

指标纯 RAG 方案Agentic Grep混合架构
端到端响应时间2–5 秒（含 Embedding + ANN）0.5–2 秒（多轮 grep+read）1–3 秒（路由+最优通道）
精确匹配准确率~70%（Embedding 噪声）100%（字符串精确）~95%（自动选最优通道）
语义搜索准确率~80%~40%（依赖关键词猜测）~82%（语义请求走 Vector）
索引维护需要（持续同步）不需要部分（仅语义通道）
安全风险中（代码 Embedding 可能泄露）低（代码不离开本机）低（本地优先）

关键发现：在 LongMemEval 的 116 个代码搜索问题上，Grep 的平均准确率在 Claude Code、Codex CLI、Gemini CLI 三个框架上都显著高于向量检索。这个结论不是某一家的偏好，而是跨框架的稳定复现结果。

核心设计原则与实践指导

Claude Code 的设计哲学可以概括为："Less scaffolding, more…

三大核心原则

原则含义Claude Code 的实现
决策权归属模型让模型决定搜什么、怎么搜、搜几轮while(tool_call) 循环，无 DAG、无分类器
运维简化消除需要持续维护的基础设施无向量库、无索引同步、无 Embedding 服务
灵活扩展社区插件可按需补充能力ast-grep（AST 模式）、Serena（LSP）、MCP Server

Claude Code 的设计哲学可以概括为："Less scaffolding, more model"——信任模型的推理能力，而不是在它周围搭建复杂的编排系统。系统提示词只有约 7,000 tokens，核心指令极其简洁：8 个工具 + 搜索策略 + 输出格式。

"Less scaffolding, more model" 的反直觉之处在于：减少工程复杂性反而提升了系统可靠性。RAG 的 5 个环节意味着 5 个潜在故障点；Agentic Grep 只有 1 个故障点（模型本身的推理能力）——而模型的推理能力会随着基础模型的升级自动提升。

代码场景 vs 自然语言场景的选型

场景特征推荐方案理由
代码搜索Grep 优先 + 语义辅助代码标识符 = 语义本身，精确匹配覆盖 60%+ 场景
自然语言文档RAG 优先 + 关键词辅助自然语言同义词多，语义检索覆盖更广
混合知识库混合架构 + Agent 路由代码走 Grep，文档走 RAG，结构化走 LSP
高频变更代码库Grep 优先避免索引同步的持续成本
大型稳定文档库RAG 优先文档变更少，索引维护成本低
  • 代码搜索优先使用 Grep/ripgrep——精确、实时、零配置
  • 让 Agent 自主决定搜索策略——不要强制固定搜索流水线
  • 在大规模项目中考虑混合架构——精确匹配走 Grep，语义搜索走 Vector
  • 评估方案时用"开发者体感"而非传统 IR 指标——Boris 用"vibes"做判断
  • 保持架构简单——简单的方案更容易调试、维护和升级
  • 不要在代码搜索场景中盲目采用 RAG——先验证 Grep 是否足够
  • 不要忽略索引漂移问题——代码频繁变更时 RAG 结果可能严重过时
  • 不要把 RAG 的精度链式衰减视为"可优化"——这是结构性问题
  • 不要在安全敏感项目中将代码上传到外部 Embedding 服务
  • 不要在小项目（<5 万行）中引入 RAG 基础设施——过度工程化

从 RAG 到 Grep 的转变揭示了一个深层工程智慧：在模型能力快速提升的时代，把复杂性放在模型里（让它学会搜索）比放在基础设施里（建索引流水线）更可持续——模型升级是免费的，基础设施升级需要工程投入。

行业影响与未来展望

Claude Code 弃 RAG 转 Grep 的决策已经引发了行业连锁反应

Claude Code 弃 RAG 转 Grep 的决策已经引发了行业连锁反应。多个主流 AI 编程工具调整了搜索策略，社区对"代码场景是否需要 RAG"展开了深入反思。

行业反响与调整

方面影响具体行动

Milvus 的反驳与回应

向量数据库厂商 Milvus（Zilliz）发表文章指出 Agentic Grep 存在 Token 消耗过高的问题：在大型代码库中，Agent 需要多轮 grep+read 才能定位目标代码，每次 read 都消耗大量 Token。而预构建的向量索引可以一次查询返回精准位置，减少探索轮次。

这个反驳有其合理性——在 50 万行以上的代码库中，纯 Grep 方案的 Token 成本确实会显著上升。但 Claude Code 的选择基于不同优先级：安全性和简洁性优先于 Token 效率。代码不离开本机、不需要外部 Embedding 服务、不存在索引漂移——这些对于企业级安全合规至关重要。

这场辩论的真正启示不是"Grep 好还是 RAG 好"，而是"在特定场景中选择最适合的方案"。Claude Code 的场景是代码开发工具——代码是精确的、高频变更的、安全敏感的。这些特征天然适合 Grep。如果你的场景是自然语言文档检索——语义模糊的、相对稳定的、非安全敏感的——RAG 仍然是更好的选择。

未来方向已明确：混合架构是终局——核心高频搜索用 Grep（精确、实时），语义模糊搜索用 Vector（理解意图），结构分析用 AST/LSP（追踪依赖）。Agent 是路由决策者，不是固定流水线中的一个环节。

Q&A

Boris Cherny 说 Agentic Search "comprehensively won — by a lot"，具体赢了哪些方面？
根据 Latent Space 播客和 Hacker News 评论的综合信息，Agentic Search 在以下维度全面胜出：① 搜索结果准确性——Agent 能根据上下文动态调整搜索策略，找到 RAG 遗漏的相关代码。② 运维简洁性——不需要向量库、Embedding 服务、索引同步机制。③ 安全性——代码不离开本机，不存在 Embedding 数据泄露风险。④ 实时性——永远搜索最新代码状态。⑤ 首次使用体验——claude . 在新仓库中即时工作，无需等待索引构建。Boris 强调这不是边缘场景的胜利，而是在"输出是否让开发者觉得对"这个核心体验指标上的全面碾压。
RAG 的"精度链式衰减"具体是怎么计算的？真的会跌破 60% 吗？
精度链式衰减是串联系统的概率乘法效应。RAG 有 5 个串联环节：文档分块（90%）、Embedding 向量化（92%）、向量存储索引/ANN 近似（95%）、查询向量化（88%）、Top-K 截断（85%）。整体精度 = 0.90 × 0.92 × 0.95 × 0.88 × 0.85 ≈ 58.8%。每个环节 90%+ 的精度在工程上已经很高，但串联后不到六成。关键问题不是数字本身（实际精度取决于具体实现和数据），而是这种结构性衰减无法通过优化单一环节来解决——你必须同时优化所有环节，而每增加一个环节就增加一个潜在故障点。Grep 没有这个链路：搜索要么精确命中，要么不命中。
Agentic Grep 在大型代码库中的 Token 成本会不会比 RAG 更高？
会，但需要区分场景。在 50 万行以上的代码库中，纯 Grep 方案需要多轮搜索（先 glob 定位文件，再 grep 搜索内容，再 read 读取全文，再 grep 追踪引用），每轮 read 消耗大量 Token。而 RAG 可以一次查询返回精准位置。Milvus 的反驳正是基于这个论点。但 Claude Code 的选择考虑了综合成本：① RAG 的索引构建和维护成本（工程人力）；② 索引漂移导致的错误结果成本（开发者时间浪费）；③ 安全风险成本（代码 Embedding 泄露）；④ 基础设施运维成本（向量库、Embedding 服务）。这些"隐性成本"在 RAG 的 Token 效率优势面前往往被忽略。
Cursor 泄露的系统提示词显示 grep_search 是"MAIN exploration tool"，这说明 Cursor 也弃用 RAG 了吗？
不是完全弃用，而是降级为辅助角色。Cursor 3 月份泄露的 Agent System Prompt 显示：grep_search is your MAIN exploration tool，RAG 语义搜索仅在概念性查询时作为补充。这意味着 Cursor 采取了"Grep 优先 + RAG 兜底"的混合策略——精确搜索走 grep，语义模糊搜索（如"处理退款的逻辑"）走 RAG。这与 Claude Code 的"完全弃用 RAG"不同，但方向一致：在代码搜索场景中，Grep 被提升为主力工具，RAG 从主力降为辅助。
代码场景和自然语言文档场景，为什么 Grep vs RAG 的结论完全不同？
根本区别在于"标识符 = 语义"vs"表述 ≠ 语义"。代码中，变量名 handleUserLogin 就是它的语义——你搜 handleUserLogin 就能精确找到它。程序员已经把语义编码在标识符中了。但自然语言中，"如何配置用户登录"和"authentication setup guide"说的是同一件事，字面完全不同——这正是 Embedding 存在的核心价值。此外：代码是高频变更的（索引漂移严重），文档相对稳定；代码安全要求高（不能上传外部服务），文档安全要求低；代码搜索 60%+ 是精确匹配，文档搜索 80%+ 是语义模糊。这些特征差异决定了 Grep 在代码场景占优，RAG 在文档场景占优。
如果我想在自己的项目中验证"Grep 是否比 RAG 更好"，应该怎么设计实验？
Boris Cherny 的评价方法论值得参考——他用"vibes"（开发者体感）而非传统 IR 指标来判断。具体建议：① 准备 20–50 个真实的代码搜索问题（从团队日常开发中提取）。② 分别用纯 Grep 方案（Agent + ripgrep）和 RAG 方案（Embedding + 向量库）回答这些问题。③ 让 3 位开发者盲评每个回答的质量（1-5 分），不告知使用的是哪种方案。④ 同时记录：响应时间、Token 消耗、索引维护成本、搜索结果过时率。⑤ 重点关注"开发者觉得结果对不对"而非 Recall@K 等传统指标。在 LongMemEval 的 116 个代码搜索问题上，Grep 在三个不同框架上都稳定优于向量检索——你的实验很可能会得到类似结论。
未来基础模型能力提升后，RAG 会不会被完全淘汰？
不会完全淘汰，但适用范围会持续缩小。随着模型上下文窗口扩大（已有 200K → 1M token 的趋势）和推理能力增强，越来越多的场景可以直接"读完整文档"而无需预检索。但 RAG 在以下场景仍有不可替代的价值：① 超大规模知识库（百万文档级），即使 1M 上下文也装不下。② 成本敏感场景，RAG 只传 Top-K 片段比传入全文 Token 成本低几个数量级。③ 需要跨会话持久化知识的企业知识库。正确的预期是：RAG 从"通用必选项"降级为"特定场景的优化工具"，而 Agent 自主决策何时使用 RAG 何时直接阅读——这正是混合架构的终局形态。
