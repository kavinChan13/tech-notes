7 策略噪声检测

策略方法判断条件标志
① 重复文本统计同文本出现频次≥30% 页的页边区域出现is_advertisement
② 固定位置同文本+同 bbox≥30% 页同位置出现（±10px）is_advertisement
③ 页眉页脚位置 + 内容判定顶部 12% 或底部 8% + 导航特征is_header / is_footer
④ 水印字体大小 + 出现频率字体 >1.5× 正文 + ≥50% 页出现is_watermark
⑤ 遮罩/Banner绘图对象分析宽 >50% 页宽 + 半透明/深色/鲜艳is_overlay_recovered
⑥ 高频兜底同文本+同位置≥80% 页出现（前面未命中时）is_advertisement
⑦ 正文保护白名单机制CODE/TITLE/HEADING 永远清除噪声标志清除误标

页边噪声：位置只是必要条件

清洗规则：过滤与断行修复放在同一步

import re

# 前面所有检测都只打标志；真正丢弃发生在输出这一步，所以误判随时能回滚
DROP = ("is_header", "is_footer", "is_watermark", "is_advertisement")
# is_overlay_recovered 故意不在 DROP 里——那是被广告盖住的正文，必须留

HYPHEN = re.compile(r"(\w{2,})-$")
SENT_END = "。！？；：.!?)]}"

def emit(blocks, vocab):
    lines = []
    for b in blocks:
        # 白名单最后生效：CODE / TITLE / HEADING 即便被上面某条策略误标，
        # 也照样输出。宁可放过噪声，不可误删正文。
        if b.type in ("CODE", "TITLE", "HEADING") or not any(
                getattr(b, f) for f in DROP):
            lines.append(b.text)
    return rejoin(lines, vocab)

def rejoin(lines, vocab):
    """断词连字符与跨页断句在同一处修复——它们的信号是同一个：
    上一行没结束。区别只在上一行结尾有没有那个连字符。"""
    out = []
    for line in lines:
        cur, prev = line.strip(), (out[-1] if out else "")
        m = HYPHEN.search(prev)
        if m and cur[:1].islower() and m.group(1) + cur.split()[0] in vocab:
            out[-1] = prev[:-1] + cur      # asyn- + chronous → asynchronous
        elif prev and prev[-1] not in SENT_END and cur[:1].islower():
            out[-1] = prev + cur           # 跨行 / 跨页断句：直接续上
        else:
            out.append(cur)
    return out

第三条判据（拼起来在词表里）不能省：state-of-the-art 断行时前两条也成立，吃掉那个连字符，检索时就再也匹配不上原词。

  • 如何区分"广告文字"和"被广告盖住的正文"？ — 广告文字高频重复，正文唯一；位置 + 频率 + 内容联合判断

扫描版 PDF 处理

OCR 只是把文本层补出来，补出来之后必须带着「来源」和置信度往下走

OCR 处理链路

步骤操作工具
1. 图像预处理二值化、去噪、倾斜校正、分辨率增强OpenCV
2. 版面分析识别文档区域（标题/正文/表格/图片）PP-StructureV2 / DocLayout-YOLO
3. 文字识别OCR 识别 + 置信度输出PaddleOCR / Tesseract
4. 结果结构化OCR 结果包装为统一 TextBlock 格式自定义转换
5. 后续流水线进入与原生 PDF 相同的下游处理通用 pipeline

第 4 步的「统一格式」容易漏掉一半：结构统一，来源标记不能丢。置信度要一路带进 chunk 的 metadata——检索命中一段莫名其妙的内容时，才能一眼看出它是 0.62 置信度 OCR 出来的，而不是去怀疑 embedding 模型。

  • OCR 精度如何保障？ — 图像预处理（去噪 / 二值化 / 倾斜校正）+ 高 DPI 渲染 + 后处理纠错，三者缺一不可
  • PaddleOCR vs Tesseract：中文场景前者精度显著更高，后者多语言覆盖广

扫描版 PDF + 水印/广告/导航栏

广告是独立图层就还能救，已经压成像素就是信息论意义上的不可逆

四种子情况与恢复可能性

子情况物理状态恢复可能方案
A. 广告已 flatten 进位图像素覆盖，信息损毁❌ 不可逆标记 + 人工补录
B. 多个 image XObject 叠加背景图和广告是独立图层✅ 可救图像层分离，仅 OCR 底图
C. 扫描底图 + 矢量广告底图是位图，广告是矢量绘图层✅ 可救OCR 底图，矢量层不进 OCR
D. 半透明水印覆盖OCR 部分能看见底层文字⚠️ 低准确率OCR + 低置信度标记

两条处理路线

判据就一句：get_images(full=True) 返回多张图 → 分层，只返回一张 → 已 flatten。B / C 可救——按面积排序，最大的那张是底图，只把它送进 OCR，结果落在广告矩形内的标 uncertain。A 不可救——只能在像素上找高饱和大色块（HSV 阈值 + 轮廓面积占页 0.5%–50%），找到了也只知道「这里挡着东西」。

信息论限制：广告像素已 flatten 进位图时，被覆盖的原文真的丢失了。正确做法是标记缺失区域告知用户，而非用 inpainting 猜测（猜出来的 OCR 结果几乎是垃圾）。

  • 导航栏与正文的区分困难在哪？ — 目录型导航本身就含正文标题，位置、频率、内容三条必须联合判断
  • 无法恢复的区域怎么交付？ — 输出 [此处可能因遮挡丢失内容] 占位符，让读者知道缺口在哪

代码块识别与保护

技术类 PDF 中代码块容易被切碎、被噪声检测误标为广告

代码块的 6 层识别链路

层位置作用
Layer 1PDF 解析从 FontDescriptor.Flags 第 3 位读取等宽标志
Layer 2布局分类等宽字体 + 字号 ≤ 正文 → BlockType.CODE
Layer 3噪声保护代码模式（{/}/return/关键字）跳过噪声检测
Layer 4跨页合并保护CODE 块永不参与跨页段落拼接
Layer 5Markdown 重构连续 CODE 块合并为单一 ``` 围栏
Layer 6语义分块保护永不在代码围栏中间切 chunk

Layer 5 看着像格式细节，其实是分块能不能用的前提：PyMuPDF 通常把一段代码切成每行一个 block，不合并的话，20 行代码就是 20 个独立段落，分块时被撒进好几个 chunk，每一片都答不了任何问题。

  • 为什么代码容易被噪声检测误标？ — 短行（} / return 0;）在多页重复出现，正好撞上"重复 = 广告"这条启发式
  • Layer 3 的代码模式判据覆盖哪些？ — 孤立标点、注释行、含关键字的短行、以 ; / { / } 结尾的行

多栏布局与阅读顺序恢复

裸抽取按 y 排序，两栏的句子会一句一句交错焊在一起

裸抽取为什么会把两栏交错

多栏检测算法

def reading_order(page):
    """裸抽取只按 y 排，两栏就会一句一句交错。
    所以顺序必须是：先分栏 → 各栏内按 y 排 → 左栏接右栏。"""
    mid = page.width / 2
    left, right, full = [], [], []
    for b in page.blocks:
        w = b.bbox.x1 - b.bbox.x0
        if w > page.width * 0.7:                  # 跨栏标题 / 通栏图表
            full.append(b)
        elif (b.bbox.x0 + b.bbox.x1) / 2 < mid:
            left.append(b)
        else:
            right.append(b)

    left.sort(key=lambda b: b.bbox.y0)
    right.sort(key=lambda b: b.bbox.y0)
    ordered = left + right

    # 全宽块不能一股脑塞到最前或最后：它在页面上的 y
    # 决定了它属于哪一段，插错位置等于把一节的标题挂到另一节头上
    for fw in full:
        insert_by_y(ordered, fw)
    for i, b in enumerate(ordered):
        b.reading_order = i

切分边界决定了检索天花板：切错的地方，后面再好的模型也捞不回来

三种切法的代价

分块规则

规则说明目的
# 或 ## 标题遇到标题立即开启新 chunk保持主题一致性
代码块 ```永不在代码块中间切割保持代码完整性
超出最大长度在段落边界（空行）切割控制 chunk 大小

分块实现：按结构切 + 重叠窗口

class Chunker:
    """不按固定字符数硬切的理由很朴素：1500 这个数字对语料一无所知，
    它落在句子中间还是段落缝里，完全是运气。所以先认结构，
    只有「结构给不出边界」时才退回长度控制，而且只在空行处下刀。"""

    def __init__(self, max_size=1500, overlap=200):
        self.max_size, self.overlap = max_size, overlap

    def split(self, md: str) -> list:
        chunks, cur, heading, in_code = [], [], "", False
        for line in md.split("\n"):
            if line.lstrip().startswith("```"):
                in_code = not in_code
            if in_code:                       # 围栏内一律不做边界判断
                cur.append(line)
                continue
            if line.startswith(("# ", "## ")):    # 标题 = 天然边界
                if cur:
                    chunks.append(self._emit(heading, cur))
                heading, cur = line, [line]
                continue
            cur.append(line)
            if sum(map(len, cur)) > self.max_size:
                cut = self._paragraph_boundary(cur)   # 只在空行处切
                chunks.append(self._emit(heading, cur[:cut]))
                # 重叠窗口：新块带上一块末尾 overlap 字，并重挂标题——
                # 少了标题，这个 chunk 在检索结果里就是一段没有出处的话
                cur = [heading] + self._tail(cur[:cut], self.overlap) + cur[cut:]
        return chunks

def audit(doc, chunks, sample=30):
    """阈值故意设得宽：它们只负责发现「量级变了」，不负责判对错。"""
    est = doc.raw_char_count                 # 解析层数到的字符总数
    out = sum(len(c["text"]) for c in chunks)
    yield "完整度", out / est, (0.90, 1.02)   # 掉 10% 以上必查
    noisy = sum(b.is_noise for b in doc.blocks) / len(doc.blocks)
    yield "噪声率", noisy, (0.05, 0.15)       # 偏高=误标正文，偏低=根本没洗
    fences = sum(c["text"].count("```") for c in chunks)
    yield "围栏配对", fences % 2, (0, 0)      # 奇数 = 有代码被切断

    # 自动指标全绿也不能发布：下面这份清单必须有人真的读一遍。
    # 抽样不要均匀随机——专挑最容易出错的三处：
    # 跨页接缝、表格前后、带水印的页。
    for c in pick_risky(chunks, sample):
        print(c["source"], c["page"], c["heading"], c["text"][:80])

Q&A（Top 10）

先自测再展开对照
PDF 文档有文本层和扫描版两种，它们的清洗策略有何本质区别？

有文本层的 PDF 可以直接通过 API（如 PyMuPDF 的 get_text("dict")）读取字符流，文字在对象层面始终完整，即使被广告遮盖也能恢复。扫描版 PDF 整页是位图，必须先 OCR 才能得到文字，且如果广告像素直接覆盖了正文像素，信息在物理上已经损毁，无法恢复。策略差异：原生 PDF 重点在去噪和结构恢复；扫描版重点在 OCR 精度和图层分离。

广告完全盖住了正文代码，为什么还能恢复？请解释 PDF 的分层原理。

PDF 内部是分层结构：文本对象、绘图对象、图像对象各自独立存在。"广告盖住正文"在文件层面 = 一个绘图对象（半透明/深色矩形）的 z-order 在文本对象之上。用 get_text("dict") 直接读字符流时，完全绕过了绘图层的遮盖效果。关键实现：解析层读文本流（不受影响）→ 检测层从绘图层识别遮罩并打标记 → 输出层不过滤 is_overlay_recovered 的文字块。三道保险确保文字零损失。

设计一个 PDF 噪声检测系统，你会用哪些策略？如何防止误删正文？

7 策略：①重复文本检测（同文本≥30%页出现）；②固定位置检测（同文本同位置）；③页眉页脚（位置区域+导航内容特征）；④水印（超大字体+高频出现）；⑤遮罩/Banner（绘图对象的颜色/透明度/面积分析）；⑥高频兜底（≥80%页同文本同位置）；⑦正文保护（白名单+区域保护）。防误删核心：所有检测只打标志不删数据；CODE/TITLE/HEADING 块永远清除噪声标志；最后一步 _protect_body_text 兜底。宁可漏检不误删。

技术类 PDF 中代码块为什么容易被误判为噪声？如何解决？

原因：代码短行如 }、return 0; 在多页重复出现，触发"重复=广告"启发式；代码常落在页面底部，触发页脚检测。解决方案是 6 层防御：①从 PDF 字体 flag 读等宽位；②布局分类标记为 CODE；③噪声检测遇代码模式跳过；④跨页合并拒绝 CODE 参与；⑤Markdown 输出合并连续 CODE 为单一围栏；⑥分块永不在代码内切割。设计理念：层层递进，任一层出错下一层兜底。

扫描版 PDF 有广告覆盖时，什么情况可以恢复，什么情况不可以？

可恢复：①多 image XObject 叠加（广告和底图是独立图层），分离后只 OCR 底图；②扫描底图+矢量广告层，矢量层不进 OCR 输入。不可恢复：广告已 flatten 进位图（像素覆盖=信息损毁，信息论意义上不可逆）。判断方法：page.get_images() 返回多张图→可救；仅1张→已 flatten。不推荐 inpainting：填充的是"视觉合理"的像素而非真实文字，OCR 结果是乱码。最佳实践：标记缺失区域 + 让用户手动补录。

PDF 表格提取有哪些方案？各适用什么场景？

6 种方案：A.线条几何网格重建（适合完整网格表、半边框表）；B.文本 bbox 列对齐（适合无线条伪表格）；C.pdfplumber extract_tables（最划算 MVP，覆盖 70% 场景）；D.AI 版面模型+结构识别（工业级，覆盖合并单元格/嵌套表）；E.跨页表合并（检测相邻页表格连续性）；F.扫描表 OCR + PP-Structure。推荐路径：先上 pdfplumber 解决大多数场景，再按需引入 AI 模型处理复杂表格。RAG 场景建议额外做"表格平铺"：逐行转为自然语言句子，提升 embedding 效果。

启发式布局分类是如何工作的？与 AI 版面模型相比各有什么优劣？

启发式方法：统计全文档字体大小频率，最高频为正文字体；≥1.8x 正文=TITLE，≥1.4x=HEADING；等宽字体+小字号=CODE；以列表符号开头=LIST_ITEM。优点：零外部依赖、速度极快（纯 CPU 毫秒级）、完全可解释可调试。缺点：对复杂版面（杂志、混合图文）效果差，无法识别表格区域。AI 版面模型（DocLayout-YOLO/LayoutParser）能处理任意复杂版面，但需要 GPU、模型文件、推理耗时。折中方案：启发式为默认，AI 模型为可选增强。

如何设计 RAG 场景下的语义分块策略？需要考虑哪些约束？

核心策略：以标题（#/##）为自然切分点开新 chunk；代码围栏内不切割（保持完整性）；超出 max_size 在段落边界切割；过短 chunk 合并入前一个避免碎片化。约束考量：①Embedding 模型最大输入长度（通常 512-8192 tokens）；②检索精度（chunk 越小越精确但丢上下文）；③内容完整性（代码/表格不可拆）；④与索引粒度匹配。进阶优化：Parent-Child 策略（小块检索+大块返回）、chunk overlap 防信息切断、metadata 保留（heading/来源/页码）辅助过滤。

多栏 PDF 的阅读顺序如何恢复？有什么边界情况？

核心算法：按文字块 x 中心点与页面中线比较，分为左栏/右栏/全宽块；各栏内按 y 排序；全宽块按 y 坐标插入正确位置；最终合并为 左栏→右栏 的阅读序。边界情况：①跨栏标题/图片（宽度>70%页宽视为全宽）；②三栏以上版面（中线二分法失效，需 DBSCAN 聚类）；③侧边注释/脚注（位置在边栏但不是主内容流）；④表格跨栏（整个表格宽度可能横跨两栏）。当前主流开源方案大多只支持 1-2 栏，杂志级复杂版面仍需 AI 辅助。

如果让你从零设计一个面向 RAG 的 PDF 清洗系统，架构如何设计？

分层架构：①解析层：PyMuPDF 提取文本/绘图/图像三类对象，检测 is_scanned 分流；②布局层：启发式分类（默认）或 AI 版面模型（可选），输出 BlockType；③去噪层：多策略检测 + 正文保护白名单，所有操作仅打标志；④结构恢复层：阅读顺序排序 + 跨页合并 + 表格重建；⑤输出层：按标志过滤噪声，生成结构化 Markdown；⑥分块层：标题驱动+代码保护+大小控制，输出 chunks.json。工程保障：异步处理+WebSocket进度推送+原始文件不可变+编辑层隔离+Debug可视化+质量评分。技术栈：FastAPI + PyMuPDF + PaddleOCR(可选) + asyncio + 文件存储。
