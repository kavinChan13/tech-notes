PDF 数据清洗概述

PDF 是"显示格式"而非"语义格式"——它只描述"在坐标(x,y)用字体F画字符C"，没有…

为什么 PDF 清洗是 RAG 的核心难题

PDF 是"显示格式"而非"语义格式"——它只描述"在坐标(x,y)用字体F画字符C"，没有段落、标题、表格的显式语义标记。直接提取文本会丢失结构、引入噪声，导致 RAG 检索精度急剧下降。

PDF 文档的 5 种典型场景

场景特征清洗难度典型来源
常规 PDF有文本层、无干扰元素⭐Word/LaTeX 导出
PDF + 水印/广告有文本层，含遮罩/Banner/水印⭐⭐⭐网络下载的技术书
含表格的 PDF表格结构复杂，需恢复行列关系⭐⭐⭐报告、论文、规格书
扫描版 PDF整页是位图，无文本对象层⭐⭐⭐⭐扫描件、拍照件
扫描版 + 水印/广告/导航栏位图上叠加广告像素或矢量层⭐⭐⭐⭐⭐网络流传的扫描书

核心原则：宁可少提取，不引入噪声。所有清洗操作应仅打标志，不直接删除数据，保留用户手动恢复的可能性。

  • PDF 为什么比 HTML 难解析？ — PDF 是面向渲染的格式，没有 DOM 树，文字块之间无父子/兄弟关系
  • 数据清洗在 RAG Pipeline 中的位置：PDF → 清洗/去噪 → Markdown → 分块 → Embedding → 向量库
  • "文本零损失"原则：清洗只打标记不删内容，最终输出时才按标记过滤，确保误判可逆

启发式布局分类算法

1. 统计全文档所有字体大小出现次数
2. 水印过滤：出现页数 ≥ 总页数×70% AND 字体 >20pt → 排除
3. 正文字体 = 出现次数最多的非水印字体
4. 标题判定：
     ≥1.8× 正文字体 → TITLE（# 一级标题）
     ≥1.4× 正文字体 → HEADING（## 二级标题）
5. 代码块：等宽字体 OR 字体名匹配 monospace 白名单
6. 列表项：以 • - （ 数字 等起头
7. 其余 → PARAGRAPH

文字提取核心代码

import fitz

def extract_text_blocks(page: fitz.Page):
    """从 PDF 对象层直接读取文本，不受视觉遮罩影响"""
    text_dict = page.get_text("dict", flags=fitz.TEXT_PRESERVE_WHITESPACE)
    blocks = []
    for block_data in text_dict.get("blocks", []):
        if block_data.get("type") != 0:  # type 0 = text
            continue
        for line in block_data.get("lines", []):
            for span in line.get("spans", []):
                blocks.append({
                    "text": span["text"],
                    "font": span["font"],
                    "size": span["size"],
                    "bbox": span["bbox"],
                    "is_bold": "Bold" in span["font"],
                    "is_monospace": bool(span["flags"] & (1 << 3)),
                })
    return blocks
  • 为什么用 get_text("dict") 而非 get_text("text")？ — dict 模式保留字体名/大小/bbox 等元数据，是后续布局分类的基础
  • 启发式布局分类 vs AI 模型分类的 trade-off：启发式零依赖、速度快、可解释，但对复杂版面力不从心
  • 为什么正文字体定义为"出现次数最多的字体"？ — 统计假设：正文占文档绝大多数内容

PDF 内部有三类独立对象：

对象类型包含信息提取 API

④ 水印字体大小 + 出现频率字体 >1.5× 正文 + ≥50% 页出现is_watermark

  • 如何区分"广告文字"和"被广告盖住的正文"？ — 广告文字高频重复，正文唯一；结合位置+频率+内容特征综合判断

扫描版 PDF 处理

扫描版 PDF 的特征识别

def is_scanned_page(page: fitz.Page) -> bool:
    """判断页面是否为扫描版（无文本层）"""
    text_dict = page.get_text("dict")
    has_text = any(
        b.get("type") == 0 for b in text_dict.get("blocks", [])
    )
    images = page.get_images(full=True)
    return not has_text and len(images) > 0

PaddleOCR 集成示例

from paddleocr import PaddleOCR

ocr = PaddleOCR(use_angle_cls=True, lang='ch', use_gpu=False)

def ocr_page(page_image_path):
    result = ocr.ocr(page_image_path, cls=True)
    text_blocks = []
    for line in result[0]:
        bbox = line[0]  # [[x1,y1],[x2,y2],[x3,y3],[x4,y4]]
        text, confidence = line[1][0], line[1][1]
        text_blocks.append({
            "text": text,
            "bbox": [bbox[0][0], bbox[0][1], bbox[2][0], bbox[2][1]],
            "confidence": confidence,
        })
    return text_blocks
  • 如何判断一个 PDF 是扫描版？ — page.get_text() 为空 + page.get_images() 非空 → 扫描版
  • OCR 精度如何保障？ — 图像预处理（去噪/二值化/校正）+ 高 DPI 渲染 + 后处理纠错
  • 扫描版 PDF 走完 OCR 后如何与原生 PDF 统一？ — OCR 结果包装成同结构 TextBlock（含 bbox），下游逻辑不区分来源
  • PaddleOCR vs Tesseract：中文场景 PaddleOCR 精度显著更高；Tesseract 多语言覆盖广

def process_scanned_page_with_overlay(page: fitz.Page):
    images = page.get_images(full=True)
    rects = [(img, page.get_image_rects(img[0])[0]) for img in images]
    rects.sort(key=lambda x: x[1].get_area(), reverse=True)

    base_image = rects[0]       # 最大的是底图（正文）
    overlay_imgs = rects[1:]    # 其余是广告 / Logo / 横幅

    # 仅 OCR 底图
    ocr_results = ocr_provider.recognize(base_image)

    # 标记落在 overlay 区域的文本为 uncertain
    for r in ocr_results:
        for _, overlay_rect in overlay_imgs:
            if r.bbox.intersects(overlay_rect):
                r.is_overlay_obscured = True
    return ocr_results

像素级广告检测（处理子情况 A）

import cv2

def detect_ad_regions(page_image):
    """启发式：高饱和色块 + 矩形形状 + 适中面积"""
    hsv = cv2.cvtColor(page_image, cv2.COLOR_BGR2HSV)
    saturated_mask = cv2.inRange(hsv, (0, 80, 80), (180, 255, 255))
    contours, _ = cv2.findContours(
        saturated_mask, cv2.RETR_EXTERNAL, cv2.CHAIN_APPROX_SIMPLE
    )
    H, W = page_image.shape[:2]
    boxes = []
    for c in contours:
        x, y, w, h = cv2.boundingRect(c)
        area = w * h
        if 0.005 * H * W < area < 0.5 * H * W:
            boxes.append((x, y, x + w, y + h))
    return boxes

导航栏清洗

导航栏（目录栏、侧边栏）是扫描书常见噪声源，识别策略：

  • 位置启发式：固定出现在页面左侧/右侧 15% 区域，或顶部/底部 10% 区域
  • 内容特征：含 URL、页码模式（"第X页"、"Page N"）、章节目录样式
  • 频率检测：同位置同内容在 ≥80% 页面重复出现
  • 面积比：占页面面积 <15% 且位于页边

信息论限制：广告像素已 flatten 进位图时，被覆盖的原文真的丢失了。正确做法是标记缺失区域告知用户，而非用 inpainting 猜测（猜出来的 OCR 结果几乎是垃圾）。

  • 如何判断 PDF 是"多图层叠加"还是"已 flatten"？ — page.get_images(full=True) 返回多个 image → 多图层；仅 1 个 → 大概率 flatten
  • 为什么不推荐用 inpainting 恢复被覆盖文字？ — inpainting 填充的是"视觉合理"的像素，不是真实文字；OCR 识别出来是乱码
  • 导航栏与正文的区分困难在哪？ — 目录型导航可能含有正文内容的标题，需结合位置+频率+内容综合判断
  • 最佳实践：标记 + 人工确认 — 对无法恢复的区域，输出 [此处可能因遮挡丢失内容] 占位符

代码模式识别（防误删）

def looks_like_code(text: str) -> bool:
    """识别代码片段，用于噪声检测时跳过"""
    # 孤立代码标点
    if text.strip() in {'{', '}', '};', ');', '*/', '//'}:
        return True
    # C/C++ 注释
    if text.strip().startswith(('// ', '/* ', '* ')):
        return True
    # 含编程关键字的短行
    keywords = ['int ', 'return', '#include', 'class ', 'def ',
                'import ', 'for (', 'while ', 'if (', 'struct ']
    if len(text) <= 40:
        return any(kw in text for kw in keywords)
    return False

多栏检测算法

def recover_reading_order(page_data):
    """基于 x 中心点聚类检测多栏布局"""
    page_center_x = page_data.width / 2

    left_blocks, right_blocks, full_width = [], [], []
    for block in page_data.text_blocks:
        block_center_x = (block.bbox.x0 + block.bbox.x1) / 2
        block_width = block.bbox.x1 - block.bbox.x0

        if block_width > page_data.width * 0.7:
            full_width.append(block)   # 全宽块（跨栏标题等）
        elif block_center_x < page_center_x:
            left_blocks.append(block)  # 左栏
        else:
            right_blocks.append(block) # 右栏

    # 各栏内按 y 排序，然后左栏 → 右栏
    left_blocks.sort(key=lambda b: b.bbox.y0)
    right_blocks.sort(key=lambda b: b.bbox.y0)

    ordered = left_blocks + right_blocks
    # 全宽块按 y 坐标插入正确位置
    for fw in full_width:
        insert_at_correct_y_position(ordered, fw)

    for i, block in enumerate(ordered):
        block.reading_order = i

跨页文本合并

条件（同时满足才合并）：

  • 第 N 页最后一个内容块不以句号/感叹号/问号结尾
  • 第 N+1 页第一个内容块以小写字母或接续标点开头
  • 两个块均为 PARAGRAPH 类型（CODE/HEADING/TITLE 不参与）
  • 多栏检测的核心启发式是什么？ — 按文字块的 x 中心点与页面中线比较聚类
  • 全宽块（如跨栏标题）如何处理？ — 宽度 >70% 页宽视为全宽，按 y 坐标插入正确位置
  • 两栏以上（杂志三栏）的局限：简单中线二分法失效，需更复杂的 x 坐标 DBSCAN 聚类
  • 跨页合并为什么排除 CODE/HEADING？ — 代码不应跨页拼接，标题是独立语义单元

语义分块（面向 RAG）

分块规则

规则说明目的
# 或 ## 标题遇到标题立即开启新 chunk保持主题一致性
代码块 ```永不在代码块中间切割保持代码完整性
超出最大长度在段落边界（空行）切割控制 chunk 大小
过短 chunk<100字合并入前一个 chunk避免碎片化

分块实现

class SemanticChunker:
    def __init__(self, max_chunk_size=1500):
        self.max_chunk_size = max_chunk_size

    def chunk(self, markdown: str) -> list:
        chunks, current_lines, current_heading = [], [], ""
        in_code_block = False

        for line in markdown.split("\n"):
            # 跟踪代码围栏状态
            if line.strip().startswith("```"):
                in_code_block = not in_code_block
                current_lines.append(line)
                continue

            # 代码内不参与切分判断
            if in_code_block:
                current_lines.append(line)
                continue

            # 遇到标题：开启新 chunk
            if line.startswith("# ") or line.startswith("## "):
                if current_lines:
                    chunks.append(self._make_chunk(
                        current_heading, current_lines))
                current_heading = line
                current_lines = [line]
                continue

            current_lines.append(line)

            # 超出大小：在段落边界切割
            content = "\n".join(current_lines)
            if len(content) > self.max_chunk_size:
                split_point = self._find_paragraph_boundary(
                    current_lines)
                # ... 切割逻辑

        return chunks
  • 为什么用标题驱动分块？ — 标题天然是语义边界，一个标题下的内容主题一致
  • max_chunk_size 为什么设 1500 字？ — 平衡：太小丢上下文，太大降检索精度；匹配主流 Embedding 模型输入长度
  • 代码块不拆分会不会导致超大 chunk？ — 会。但半段代码无意义，宁可超限也不切碎代码
  • 这种分块策略的缺点？ — 依赖标题结构，对无标题的长文本效果差，此时应回退到语义相似度分块

Q&A（Top 10）

有文本层的 PDF 可以直接通过 API（如 PyMuPDF 的 get_text("dic…
PDF 文档有文本层和扫描版两种，它们的清洗策略有何本质区别？

有文本层的 PDF 可以直接通过 API（如 PyMuPDF 的 get_text("dict")）读取字符流，文字在对象层面始终完整，即使被广告遮盖也能恢复。扫描版 PDF 整页是位图，必须先 OCR 才能得到文字，且如果广告像素直接覆盖了正文像素，信息在物理上已经损毁，无法恢复。策略差异：原生 PDF 重点在去噪和结构恢复；扫描版重点在 OCR 精度和图层分离。

广告完全盖住了正文代码，为什么还能恢复？请解释 PDF 的分层原理。

PDF 内部是分层结构：文本对象、绘图对象、图像对象各自独立存在。"广告盖住正文"在文件层面 = 一个绘图对象（半透明/深色矩形）的 z-order 在文本对象之上。用 get_text("dict") 直接读字符流时，完全绕过了绘图层的遮盖效果。关键实现：解析层读文本流（不受影响）→ 检测层从绘图层识别遮罩并打标记 → 输出层不过滤 is_overlay_recovered 的文字块。三道保险确保文字零损失。

设计一个 PDF 噪声检测系统，你会用哪些策略？如何防止误删正文？

7 策略：①重复文本检测（同文本≥30%页出现）；②固定位置检测（同文本同位置）；③页眉页脚（位置区域+导航内容特征）；④水印（超大字体+高频出现）；⑤遮罩/Banner（绘图对象的颜色/透明度/面积分析）；⑥高频兜底（≥80%页同文本同位置）；⑦正文保护（白名单+区域保护）。防误删核心：所有检测只打标志不删数据；CODE/TITLE/HEADING 块永远清除噪声标志；最后一步 _protect_body_text 兜底。宁可漏检不误删。

技术类 PDF 中代码块为什么容易被误判为噪声？如何解决？

原因：代码短行如 }、return 0; 在多页重复出现，触发"重复=广告"启发式；代码常落在页面底部，触发页脚检测。解决方案是 6 层防御：①从 PDF 字体 flag 读等宽位；②布局分类标记为 CODE；③噪声检测遇代码模式跳过；④跨页合并拒绝 CODE 参与；⑤Markdown 输出合并连续 CODE 为单一围栏；⑥分块永不在代码内切割。设计理念：层层递进，任一层出错下一层兜底。

扫描版 PDF 有广告覆盖时，什么情况可以恢复，什么情况不可以？

可恢复：①多 image XObject 叠加（广告和底图是独立图层），分离后只 OCR 底图；②扫描底图+矢量广告层，矢量层不进 OCR 输入。不可恢复：广告已 flatten 进位图（像素覆盖=信息损毁，信息论意义上不可逆）。判断方法：page.get_images() 返回多张图→可救；仅1张→已 flatten。不推荐 inpainting：填充的是"视觉合理"的像素而非真实文字，OCR 结果是乱码。最佳实践：标记缺失区域 + 让用户手动补录。

PDF 表格提取有哪些方案？各适用什么场景？

6 种方案：A.线条几何网格重建（适合完整网格表、半边框表）；B.文本 bbox 列对齐（适合无线条伪表格）；C.pdfplumber extract_tables（最划算 MVP，覆盖 70% 场景）；D.AI 版面模型+结构识别（工业级，覆盖合并单元格/嵌套表）；E.跨页表合并（检测相邻页表格连续性）；F.扫描表 OCR + PP-Structure。推荐路径：先上 pdfplumber 解决大多数场景，再按需引入 AI 模型处理复杂表格。RAG 场景建议额外做"表格平铺"：逐行转为自然语言句子，提升 embedding 效果。

启发式布局分类是如何工作的？与 AI 版面模型相比各有什么优劣？

启发式方法：统计全文档字体大小频率，最高频为正文字体；≥1.8x 正文=TITLE，≥1.4x=HEADING；等宽字体+小字号=CODE；以列表符号开头=LIST_ITEM。优点：零外部依赖、速度极快（纯 CPU 毫秒级）、完全可解释可调试。缺点：对复杂版面（杂志、混合图文）效果差，无法识别表格区域。AI 版面模型（DocLayout-YOLO/LayoutParser）能处理任意复杂版面，但需要 GPU、模型文件、推理耗时。折中方案：启发式为默认，AI 模型为可选增强。

如何设计 RAG 场景下的语义分块策略？需要考虑哪些约束？

核心策略：以标题（#/##）为自然切分点开新 chunk；代码围栏内不切割（保持完整性）；超出 max_size 在段落边界切割；过短 chunk 合并入前一个避免碎片化。约束考量：①Embedding 模型最大输入长度（通常 512-8192 tokens）；②检索精度（chunk 越小越精确但丢上下文）；③内容完整性（代码/表格不可拆）；④与索引粒度匹配。进阶优化：Parent-Child 策略（小块检索+大块返回）、chunk overlap 防信息切断、metadata 保留（heading/来源/页码）辅助过滤。

多栏 PDF 的阅读顺序如何恢复？有什么边界情况？

核心算法：按文字块 x 中心点与页面中线比较，分为左栏/右栏/全宽块；各栏内按 y 排序；全宽块按 y 坐标插入正确位置；最终合并为 左栏→右栏 的阅读序。边界情况：①跨栏标题/图片（宽度>70%页宽视为全宽）；②三栏以上版面（中线二分法失效，需 DBSCAN 聚类）；③侧边注释/脚注（位置在边栏但不是主内容流）；④表格跨栏（整个表格宽度可能横跨两栏）。当前主流开源方案大多只支持 1-2 栏，杂志级复杂版面仍需 AI 辅助。

如果让你从零设计一个面向 RAG 的 PDF 清洗系统，架构如何设计？

分层架构：①解析层：PyMuPDF 提取文本/绘图/图像三类对象，检测 is_scanned 分流；②布局层：启发式分类（默认）或 AI 版面模型（可选），输出 BlockType；③去噪层：多策略检测 + 正文保护白名单，所有操作仅打标志；④结构恢复层：阅读顺序排序 + 跨页合并 + 表格重建；⑤输出层：按标志过滤噪声，生成结构化 Markdown；⑥分块层：标题驱动+代码保护+大小控制，输出 chunks.json。工程保障：异步处理+WebSocket进度推送+原始文件不可变+编辑层隔离+Debug可视化+质量评分。技术栈：FastAPI + PyMuPDF + PaddleOCR(可选) + asyncio + 文件存储。
