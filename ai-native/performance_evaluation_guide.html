概览

性能评测不是"跑一次 benchmark 看个数字"，而是一个四维闭环：延迟告诉你"快不快"…

性能评测不是"跑一次 benchmark 看个数字"，而是一个四维闭环：延迟告诉你"快不快"，质量告诉你"对不对"，成本告诉你"贵不贵"，稳定性告诉你"扛不扛得住"。而且每个模块（RAG / Agent / Prompt / 系统层）有独立的评测维度，不能混在一起评。

02

延迟指标与分段采集

延迟不是"一个数字"，而是一条流水线

延迟不是"一个数字"，而是一条流水线。只看端到端延迟就像只看"总用时"不看"每道工序耗时"，无法定位瓶颈。

2.1 核心延迟指标

指标全称定义关注场景
TTFTTime To First Token从请求发送到接收到第一个 Token 的时间用户感知延迟（Streaming）
TPSTokens Per Second单个请求每秒生成的 Token 数生成流畅度
E2E LatencyEnd-to-End Latency从请求到完整响应的总时间SLA 定义
P50 / P95 / P99Percentile Latency50% / 95% / 99% 的请求延迟低于此值长尾分析
ThroughputThroughput系统每秒处理的请求数（QPS/RPS）容量规划

2.2 指标关系公式

E2E Latency = TTFT + (output_tokens / TPS)
关键区分：TTFT 影响用户感知延迟（"系统有没有在响应我"），E2E Latency 影响实际吞吐（"系统能处理多少请求"）。Streaming 不能降低 E2E 延迟，但显著改善用户体验[2]。

2.3 通用分段延迟模型

任何 AI 应用的端到端延迟都可以分解为以下阶段[2]：

用户请求到达
意图路由 / 请求分发 ~5ms (0.3%)
预处理（参数解析/权限校验） ~10ms (0.5%)
核心处理链路：
检索 Retrieval ~100ms (5.0%) ← RAG 场景 · Rerank ~40ms (2.0%) ← RAG 场景 · 工具调用 ~200ms (10.0%) ← Agent 场景 · Prompt 构建 ~5ms (0.3%) · LLM 推理 ~1600ms (80.0%) ← 通用瓶颈
后处理（格式化/审计日志） ~30ms (1.5%)
响应返回
Total: ~1990ms

2.4 分段采集代码模式

import time

class LatencyTracker:
    def __init__(self):
        self.segments = {}
        self._start = None
        self._current = None

    def start(self, name):
        self._start = time.perf_counter()
        self._current = name

    def end(self):
        elapsed = (time.perf_counter() - self._start) * 1000
        self.segments[self._current] = elapsed
        return elapsed

    def report(self):
        total = sum(self.segments.values())
        for name, ms in self.segments.items():
            pct = ms / total * 100
            bar = "█" * int(pct / 2)
            print(f"  {name:20s}: {ms:7.1f}ms ({pct:5.1f}%) {bar}")
        print(f"  {'Total':20s}: {total:7.1f}ms")

# 使用示例
tracker = LatencyTracker()
tracker.start("retrieval")
# ... 检索逻辑 ...
tracker.end()
tracker.start("llm_inference")
# ... LLM 调用 ...
tracker.end()
tracker.report()

阶段占延迟比优化手段预期效果
检索 Retrieval~5%向量索引优化（IVF_PQ / HNSW）、语义缓存100ms → <40ms
Rerank~2%轻量 Reranker 模型、减少候选文档数40ms → ~15ms
工具调用~10%工具调用并行化、连接池、超时兜底200ms → ~80ms（并行）
LLM 推理~80%Prompt 缓存 / Streaming / 模型降级 / KV Cache1600ms → 400-1000ms
后处理~1.5%异步写入审计日志、流式输出边际优化
优化优先级：LLM 推理占了 80%+ 的延迟，是优化的绝对重点。提高缓存命中率（减少进入 RAG/Agent 路径的比例）比优化检索/Rerank 的收益大 10 倍以上[5]。
03

分模块评测模式

不同模块的评测维度完全不同

不同模块的评测维度完全不同。RAG 关注"检索准不准、回答忠不忠实"，Agent 关注"任务完不完成、工具用没用对"，Prompt 关注"输出稳不稳定、指令跟没跟上"，系统层关注"快不快、扛不扛得住"。混在一起评 = 什么都没评清楚。

3.1 RAG 模块评测

RAG 的评测分为两个独立阶段：检索质量和生成质量，必须分开评[6]。

检索质量指标（检索阶段）：

指标定义计算方式目标
Recall@KTop-K 中包含正确答案的比例相关文档命中数 / 总相关文档数≥ 90%
MRR第一个正确结果的排名倒数1 / 第一个相关文档的排名≥ 0.7
Precision@KTop-K 中与问题相关的比例相关文档数 / K≥ 80%
检索延迟从查询到返回 Top-K 的时间P50 / P95 / P99P95 < 200ms

生成质量指标（LLM 阶段）：

指标定义评估方法目标
Faithfulness回答是否忠实于检索到的上下文LLM-as-Judge：逐句检查每个声明是否有上下文依据≥ 85%
Answer Relevance回答是否切题LLM-as-Judge：回答是否直接回答了用户问题≥ 85%
Answer Correctness最终答案与参考答案的语义一致性与 Golden Answer 的语义相似度≥ 0.8
Hallucination Rate包含虚构/编造信息的回答比例人工标注 + LLM 交叉检测< 5%

RAG 评测实操步骤：

  1. 构建 RAG Golden Dataset：每个场景 10-20 条，包含 query + ground_truth_answer + relevant_doc_ids
  2. 检索独立评测：冻结 LLM，只测检索模块，输出 Recall/MRR/Precision
  3. 生成独立评测：固定检索结果（Golden Chunks），只测 LLM 生成质量
  4. 端到端评测：检索 + 生成全流程，测 Faithfulness + Correctness
  5. A/B 对比：修改 Chunk 策略 / Embedding 模型 / Reranker 后，用相同 Dataset 对比

"最佳实践"不一定适合你的场景：HuggingFace 团队实测发现 context-aware chunking 在核工程文档场景下不如 naive chunking（70.5% vs 63.8%），hybrid retrieval 不如 dense-only（69.2% vs 63.5%）。核心原则：The only way to know what works for you is to measure.[E4]

3.2 Agent 模块评测

Agent 的评测维度比 RAG 更复杂，因为涉及多步推理、工具调用、错误恢复[7]。

核心评测维度（四象限）：

维度指标定义目标
任务完成Task Success Rate任务成功完成的比例≥ 85%
Step Efficiency实际步骤数 / 最优步骤数≤ 1.5x
Partial Completion部分完成的比例（非全有全无）≥ 60%
工具使用Tool Accuracy选择了正确工具的比例≥ 90%
Tool Param Accuracy工具参数正确的比例≥ 85%
Redundant Calls冗余工具调用次数 / 总调用次数< 10%
推理效率Reasoning Steps推理链平均步骤数场景相关
Token per Task完成任务消耗的总 Token设红线（如 <5000）
Error Recovery Rate遇到工具失败后成功恢复的比例≥ 70%
安全性Jailbreak Resistance抵抗提示注入的成功率≥ 95%
Boundary Compliance不超出授权操作范围的比例100%

Agent 评测实操步骤：

  1. 构建 Agent 测试集：按任务难度分级（简单/中等/复杂），每级 5-10 条，包含 task_description + expected_actions + expected_outcome
  2. 单步评测：给定当前状态，检查 Agent 选择的下一步是否正确
  3. 端到端评测：完整执行任务，检查最终结果是否正确
  4. 错误注入测试：模拟工具失败、超时、返回异常，检查 Agent 恢复能力
  5. 成本审计：统计每个任务的 Token 消耗和工具调用次数，设红线
# Agent 评测数据结构示例
agent_test_case = {
    "task": "查询用户最近 3 笔交易并生成摘要",
    "difficulty": "medium",
    "expected_tools": ["get_transactions", "summarize"],
    "expected_tool_calls": 2,        # 期望调用次数
    "expected_steps": 3,             # 期望推理步数
    "token_budget": 3000,            # Token 红线
    "timeout_ms": 8000,              # 超时阈值
    "evaluation": {
        "task_success": "binary",    # 成功/失败
        "step_efficiency": "ratio",  # 实际步骤/期望步骤
        "tool_accuracy": "set_match" # 工具调用集合匹配
    }
}

3.3 Prompt 评测

Prompt 的评测核心是指令遵从度和输出稳定性。Prompt 变更是最频繁的变更类型，必须有快速评测机制[8]。

指标定义评估方法目标
指令遵从度输出是否严格遵循 Prompt 中的指令检查格式约束、字段要求、风格要求≥ 95%
输出稳定性相同输入 + 相同 Prompt 的输出一致性N 次重复，计算一致率≥ 90%
结构化输出合规率JSON/Schema 格式合规的比例Schema 校验≥ 99%
边界 Case 通过率边界输入（空、超长、乱码）的通过率预定义边界测试集≥ 90%
Token 效率Prompt Token 数 / 总 Token 数的比例统计 Prompt 膨胀率Prompt 占比 < 40%

Prompt 评测实操步骤（A/B 测试框架）：

  1. 定义变更假设："将 System Prompt 加入 Few-shot 示例后，指令遵从度从 88% 提升到 95%"
  2. 构建评测集：正常 Case 30 条 + 边界 Case 10 条 + 回归 Case 10 条（历史翻车 Case）
  3. 双版本并行评测：相同输入，分别跑 Prompt A 和 Prompt B
  4. 指标对比：逐维度对比（遵从度/稳定性/合规率/Token 效率）
  5. 回归检查：新 Prompt 在回归 Case 上不能比旧 Prompt 差
Prompt 评测黄金法则：每次 Prompt 变更必须通过三关：①新指标达标 ②回归 Case 不退化 ③边界 Case 通过。三关全过才能上线[8]。

3.4 系统层评测

系统层评测关注框架基础设施的性能，与业务逻辑无关[1]。

维度指标测量方式目标
框架开销中间件链延迟MockLLM 测路由→分发→组装全链路< 5ms
缓存性能缓存命中率 / 缓存延迟统计 Hit/Miss 比 + P99 延迟命中率 > 30%, P99 < 5ms
并发能力最大 QPS / 错误率递增并发，找拐点QPS 线性增长区间
冷启动首次请求 vs 稳态请求延迟比重启后立即请求 vs 10 次后请求冷/热比 < 5x
资源利用CPU / Memory / GPU / 连接池压测期间监控峰值 < 80%

系统层评测关键：MockLLM 双轨策略

测量方式测什么优势局限
MockLLM框架层开销（路由→路径分发→响应组装）零成本、可重复、秒级完成不包含 LLM 真实延迟
RealLLM端到端用户体验（含真实 LLM 调用）反映真实用户等待时间有成本、结果波动
为什么需要 MockLLM？框架层开销通常在 2-5ms 级别，而 LLM 调用在 500-3000ms。不用 MockLLM 隔离，根本无法区分延迟来源是框架问题还是 LLM 问题。MockLLM 零成本、秒级完成，适合每次 PR 都跑[4]。

压力测试与稳定性验证

压测不是"把并发拉到最高看崩不崩"

压测不是"把并发拉到最高看崩不崩"。科学的压测是四个递进实验：并发递增 → Burst 冲击 → 混合场景 → 持续负载，每个实验回答不同的问题。

4.1 四个实验回答的问题

实验回答的问题关注指标典型配置
并发递增系统承载力上限在哪？QPS 是否线性增长？QPS 拐点、错误率上升点1→5→10→20→50 并发
Burst 冲击突发流量下系统能否存活？错误率、恢复时间50-100 并发瞬时打入
混合场景不同路径并发时是否互相干扰？各路径延迟退化比70% 简单 + 30% 复杂
持续负载长时间运行是否有内存泄漏/资源耗尽？后半段 vs 前半段延迟退化100-1000 次连续请求

4.4 稳定性 30× 重复法

LLM 的非确定性意味着单次运行没有统计意义。通过重复执行验证稳定性[4]：

  • 20 用例 × 30 次重复 = 600 次 LLM 调用
  • 5 维度覆盖：路径一致性、意图一致性、延迟稳定性、置信度稳定性、输出长度稳定性
  • 计算变异系数（CV）= 标准差 / 均值，CV < 15% 为稳定

4.5 阈值设计原则

  • 按路径分别设定阈值，不统一标准
  • MockLLM 测框架开销，RealLLM 测用户体验
  • 阈值基于实测数据 + 业务 SLA 协商
  • P95/P99 比平均值更有意义
  • 用平均值定义 SLA（掩盖长尾问题）
  • 只用 RealLLM 做性能测试（无法区分框架 vs LLM 问题）
  • 所有路径用同一个延迟阈值
  • 忽视冷启动延迟（首次请求可能慢 5 倍）

成本度量与优化

AI 系统的成本不是"服务器月费"这么简单

AI 系统的成本不是"服务器月费"这么简单。每次请求都在按 Token 烧钱，不设红线的话，一个低效 Agent 可能一个任务花 10 块钱。

5.1 Token 成本拆解

每次请求需要统计四个成本字段[9]：

每次请求统计：
  - prompt_tokens（输入 Token 数）
  - completion_tokens（输出 Token 数）
  - cost_yuan（本次调用费用，按模型单价换算）
  - model_name（使用的模型）

日报统计：
  - 总请求数
  - 各模块占比（直接回答 / RAG / Agent / 工具调用）
  - 总 Token 消耗
  - 总成本 / 平均每请求成本 / 按模块成本占比

5.3 模型路由降本策略

不是所有请求都需要最贵的模型。通过模型路由器，将简单问题分流到轻量模型：

用户请求
简单请求（FAQ/查询/格式化）→ 轻量模型（$0.002-0.003/次）
中等请求（RAG 检索回答）→ 中档模型（$0.01-0.02/次）
复杂请求（Agent 多步推理）→ 高档模型（$0.03-0.05/次）
分层后平均成本可降低 50-70%
成本红线：为每种任务类型设定成本上限（如"信息检索任务 ≤ ¥0.1"，"复杂分析任务 ≤ ¥1.0"），超标系统直接告警且不让上线[3]。

7.2 金丝雀测试

7.5 根因定位五步法

线上监控发现指标退化后的排查流程：

  1. 看时间点 — 退化从何时开始？对应何时有代码/Prompt/模型/知识库变更？
  2. 看影响范围 — 全路径退化 vs 单路径？全路径 → 基础设施问题；单路径 → 该模块逻辑问题
  3. 看分段延迟 — 哪个阶段的延迟增加了？（定位到具体模块）
  4. 看 eval_history — 质量指标是否同步退化？（区分性能问题 vs 质量问题）
  5. 看用户反馈 — 负面反馈集中在哪类问题？（定位到具体场景）
Trace 追踪是定位利器：使用 LangFuse / LangSmith 等 Trace 系统，可以追溯单次请求的完整执行链路（每个步骤的耗时、Token 消耗、输入输出），是定位 Agent 多步推理问题的关键工具[3]。

Q&A

两者测的是不同层面：MockLLM 测框架层开销（中间件→路由→路径分发→响应组装），Rea…
MockLLM 和 RealLLM 压测到底有什么区别？能不能只用 RealLLM？

两者测的是不同层面：MockLLM 测框架层开销（中间件→路由→路径分发→响应组装），RealLLM 测端到端用户体验。只用 RealLLM 的问题：①成本高（每次 ~$0.30）；②结果波动大（LLM 延迟不稳定），难以区分是框架问题还是 LLM 问题；③无法高频运行。MockLLM 零成本、秒级完成、可重复，适合每次 PR 都跑。最佳实践是双轨并行：MockLLM 做 PR 级快速反馈，RealLLM 做定时验证[4]。

RAG 检索和生成应该一起评还是分开评？

必须分开评。混合评测时，如果最终回答质量差，你无法区分是"检索没找到好文档"还是"LLM 没用好文档"。分开评测的价值：①检索差 → 优化 Chunk 策略 / Embedding 模型 / Reranker；②生成差 → 优化 Prompt / 模型 / 后处理。先独立达标，再做端到端联调，效率远高于盲目调参[6]。

Agent 评测中"任务完成率"怎么定义？有些任务是部分完成的

建议用三级评估：①完全完成（所有步骤正确 + 最终结果正确）；②部分完成（关键步骤正确但最终结果有偏差，或完成了核心子任务）；③失败（关键步骤错误或超时）。部分完成也算有价值的输出，建议设定 Partial Completion Rate ≥ 60%。另外要追踪 Step Efficiency（实际步骤/最优步骤），防止 Agent 绕圈[7]。

为什么 SLA 要用 P95/P99 而不是平均值？

LLM 延迟呈长尾分布，P99 可能是 P50 的 5-10 倍。平均值会被大量正常请求拉低，掩盖少数用户的极端等待体验。例如：95% 请求 200ms，5% 请求 8000ms → 平均值 590ms 看起来"还行"，但那 5% 的用户等了 8 秒。P95/P99 直接告诉你"最差体验有多差"，这才是 SLA 应该保障的[2]。

LLM-as-Judge 评估靠谱吗？会不会"自己给自己打高分"？

LLM-as-Judge 有已知偏差：位置偏差（偏好更长回答）、自我增强偏差（偏好自己生成的文本）。缓解策略：①用专门的 Judge 模型（非生成模型，如 GPT-4o 做 Judge 而非评估自己的输出）；②多维度评分（准确性/完整性/相关性分开打分）；③定期与人工标注校准（至少每月 100 条人工标注对比）；④多模型交叉评估取共识分[2]。

如何在控制成本的前提下做好性能评测？

成本控制四层策略：①分层触发 — PR 级只跑 MockLLM（$0），RealLLM 仅定时任务（每日 ~$4.30）；②子集评测 — PR 级用 50 条子集，定时任务用全量；③模型降级 — 评测 Judge 用 gpt-4o-mini（成本低 10 倍）；④Mock 优先 — 能用 MockLLM 验证的就不用 RealLLM。实际日成本约 $5，月成本约 $150[4]。

线上监控发现指标退化，怎么快速定位根因？

根因定位五步法：①看时间点 — 退化从哪天开始？对应哪天有代码/Prompt/模型变更？②看影响范围 — 全路径退化还是单路径？全路径 → 基础设施问题；单路径 → 该模块逻辑问题。③看分段延迟 — 哪个阶段延迟增加了？④看 eval_history — 质量指标是否同步退化？⑤看用户反馈 — 负面反馈集中在哪类问题？Trace 系统（LangFuse/LangSmith）可以追溯单次请求的完整执行链路[3]。

"最佳实践"在我的场景下不生效怎么办？

HuggingFace 团队实测发现：几乎所有"最佳实践"都有反例。context-aware chunking 在核工程文档场景下不如 naive chunking（70.5% vs 63.8%）；hybrid retrieval 不如 dense-only（69.2% vs 63.5%）。核心原则：The only way to know what works for you is to measure. 不要盲目跟随排行榜或社区推荐，用自己的真实数据构建评测集，实测对比后做决策[E4]。

C 端项目和 B 端项目的评测重点有什么不同？

C 端更关注延迟和用户体验（TTFT 要短、流式输出要流畅、放弃率要低），用户容忍度低，3 秒无响应就流失。B 端更关注质量和准确性（忠实度、幻觉率、任务完成度），用户容忍度高但对错误零容忍。评测框架是通用的，但阈值设定不同：C 端 P95 延迟目标更严格（<2s），B 端质量指标目标更严格（幻觉率 <1%）。
