概览

Agent 架构选型的核心矛盾是"灵活性与可控性的对抗"——ReAct 最灵活但最难预测，G…

Agent 架构选型的核心矛盾是"灵活性与可控性的对抗"——ReAct 最灵活但最难预测，Graph/Workflow 最可控但最不灵活，中间的五种架构（Plan-and-Execute、Reflection、RAG+Memory、Multi-Agent、Tool Calling）各自在这条光谱上占据不同的位置。选错架构的代价远大于选错模型——一个用 Multi-Agent 解决的简单查询任务，通信成本占总计算的 60% 以上，纯属架构浪费。

01

七种核心架构全景总览

2026 年的 Agent 架构生态已经从"ReAct 一统天下"演化为七种核心架构并存的格…

2026 年的 Agent 架构生态已经从"ReAct 一统天下"演化为七种核心架构并存的格局。每种架构解决的是不同维度的问题——从简单的工具调用到复杂的多 Agent 协作，从一次性任务到需要从失败中学习的长期任务。理解它们的关键不在于记住每种架构的定义，而在于理解它们之间的"升级关系"——每种架构都是对前一种架构的某种不足的回应。

Anthropic 2024 年发布的"Building Effective Agents"指南中给出了最务实的建议："从简单提示词开始，用全面的评估来优化，只在简单方案不够用时才引入多步骤 Agent 系统。"换言之，正确的架构是"能通过你评估的最简架构"——过度设计是 Agent 工程中最常见的浪费。

02

基础认知架构：工具调用型与 ReAct

工具调用型和 ReAct 是 Agent 世界的"Hello World"——所有复杂架构都…

工具调用型和 ReAct 是 Agent 世界的"Hello World"——所有复杂架构都建立在这两种基础模式之上。工具调用型解决的是"LLM 如何与外部世界交互"的基本问题，ReAct 在此基础上增加了"推理透明度"——让 Agent 不仅做事，还能解释为什么这么做。

2.1 工具调用型（Tool Calling）：边界明确的简单任务

工具调用型是最简洁的 Agent 架构——LLM 接收用户输入，直接生成一个或多个 function_call，系统执行工具并将结果返回给 LLM 生成最终回答。没有推理链，没有循环，一次调用解决问题。这种架构适用于任务边界清晰、不需要多步推理的场景：查天气、查汇率、简单数据查询。

2.2 ReAct：推理与行动的交织循环

ReAct（Reasoning + Acting, Yao et al. 2022）是 Agent 架构的基石范式。它在每一步都插入一个显式的 Thought 阶段——LLM 先推理"为什么要做这件事"，再决定"做什么"，然后观察"结果如何"。三者形成 Thought → Action → Observation 的循环，直到任务完成。ReAct 的革命性在于将 LLM 从"文本生成器"提升为"推理-行动体"。

2.3 ReAct 的生产效率数据

2026 年 LangChain 基准测试对比显示，在一个标准的 10 步任务上，ReAct 需要约 10 次 LLM 调用（每步一次 Thought+Action），而 Plan-and-Execute 仅需 1-2 次（规划一次+执行阶段按需）。ReAct 的 Token 消耗约为 Plan-and-Execute 的 5-8 倍。但 ReAct 在探索性任务上有不可替代的优势——当"下一步该做什么"无法预先规划时（如调试未知 Bug），只有逐步推理-观察的循环才能应对。

03

规划与反思：Plan-and-Execute 与 Reflection

如果 ReAct 是"走一步看一步"的探险家，那 Plan-and-Execute 就是"先…

如果 ReAct 是"走一步看一步"的探险家，那 Plan-and-Execute 就是"先看地图再出发"的旅行者，而 Reflection 是"做完作业自己检查一遍"的好学生。这三种架构分别解决了 Agent 的三个不同痛点：探索效率（ReAct 的随机性）、全局规划（Plan-and-Execute 的前瞻性）、输出质量（Reflection 的自我纠错）。

3.1 Plan-and-Execute：完整计划 → 分步执行 → 动态重规划

Plan-and-Execute 架构将 Agent 的工作分为两个显式阶段。Planner（规划器）接收完整任务描述，输出一个有序的步骤列表——它不需要执行细节，只需要宏观规划。Executor（执行器）逐步执行 Planner 给出的步骤，每步可以是 ReAct Agent 或简单的工具调用。关键增强是Replan 机制——当某一步执行失败或结果不符预期时，Planner 根据已完成的结果重新调整后续计划。

┌─────────────────────────────────────────────────────────┐ │ Plan-and-Execute 完整流程 │ ├─────────────────────────────────────────────────────────┤ │ │ │ 任务: "写一份Q2竞品分析报告" │ │ │ │ │ ▼ │ │ ┌─────────────────────────────────────┐ │ │ │ 阶段一: Planner (规划器) │ │ │ │ 模型: GPT-4o (强推理) │ │ │ │ Prompt: 仅需任务描述, 短上下文 │ │ │ │ │ │ │ │ 输出步骤: │ │ │ │ 1. 确定竞品列表(3-5家) │ │ │ │ 2. 收集各竞品Q2产品动态 │ │ │ │ 3. 收集各竞品Q2财务数据 │ │ │ │ 4. 对比分析产品策略差异 │ │ │ │ 5. 对比分析财务表现差异 │ │ │ │ 6. 撰写综合分析报告 │ │ │ └──────────────────┬──────────────────┘ │ │ │ │ │ ▼ │ │ ┌─────────────────────────────────────┐ │ │ │ 阶段二: Executor (逐步执行) │ │ │ │ 模型: GPT-4o-mini (成本优化) │ │ │ │ │ │ │ │ Step 1: ✅ 竞品=[A公司,B公司,C公司] │ │ │ │ Step 2: ✅ 收集完成 │ │ │ │ Step 3: ⚠️ C公司Q2财报未公开 │ │ │ │ │ │ │ │ │ ▼ Replan! │ │ │ │ 调整: 用C公司Q1数据+行业均值推算 │ │ │ │ Step 3': ✅ 估算完成 │ │ │ │ Step 4: ✅ 产品对比完成 │ │ │ │ Step 5: ✅ 财务对比完成 │ │ │ │ Step 6: ✅ 报告生成完成 │ │ │ └─────────────────────────────────────┘ │ │ │ │ 效率: 规划1次 + 执行6次 = 7次LLM调用 │ │ 对比ReAct: 同等任务约需15-20次调用 │ │ 节省: ~60% 的LLM调用次数 │ └─────────────────────────────────────────────────────────┘

3.2 Reflection：生成 → 检查 → 修正闭环

Reflection（或 Reflexion, Shinn et al. 2023）在 Agent 的输出之后增加了一个"自我检查"步骤。Agent 生成初始输出后，另一个 LLM 调用（或同一个 LLM 的不同 prompt）检查输出质量，发现问题则生成修改建议，Agent 据此修正输出。这个闭环可以迭代多次，每次迭代都带着上一轮的"反思结论"——不是简单重试，而是"带教训的重试"。

3.3 Reflection 的增效数据

Reflexion 论文的关键数据：在 HumanEval 代码生成基准上，GPT-4 的 pass@1 从 80% 提升到 91%——仅通过增加 2-3 轮自我反思。这 11 个百分点的提升代价是额外的 30-50% 计算开销（每轮反思需要一次额外的 LLM 调用）。在生产环境中，这意味着用 1.3-1.5 倍的成本换取显著的质量提升——对于代码生成、法律文书、医疗报告等高质量要求的场景，这笔交易是极其划算的。

架构核心创新10步任务LLM调用Token消耗最佳场景
ReAct思考-行动循环~10-15 次高（每步推理）探索性、未知路径任务
Plan-and-Execute先规划后执行~5-8 次中（规划+执行分离）复杂多步、可预见任务

生产案例：某金融研报 Agent 从纯 ReAct 切换到 Plan-and-Execute + Reflection 后，研报质量评分（内部评审 1-10 分制）从 6.2 提升到 8.1（+30%），同时 LLM 调用成本反而降低了 22%——因为 Planner 的精准规划减少了 ReAct 中大量的"探索性浪费"（Agent 反复尝试不同方向直到找到正确路径）。Reflection 层额外增加的成本被规划层节省的成本所覆盖。

Plan-and-Execute 和 Reflection 可以无缝组合——Planner 先出计划，Executor 逐步执行，每步执行后加 Reflection 检查。这种组合在 2026 年的企业 Agent 系统中已经成为"复杂任务的标配"。Planner 解决"做什么"，Executor 解决"怎么做"，Reflection 解决"做得对不对"——三个正交的问题各自用最适合的架构来回答。

04

知识增强与协作架构：RAG+Memory 与 Multi-Agent

RAG+Memory 解决的是"Agent 知道什么"的问题——让 Agent 能够访问和利…

RAG+Memory 解决的是"Agent 知道什么"的问题——让 Agent 能够访问和利用外部知识库与历史经验。Multi-Agent 解决的是"谁来做什么"的问题——让多个专业化的 Agent 协作完成单个 Agent 无法胜任的复杂任务。两者分别代表了 Agent 系统在"知识维度"和"协作维度"的扩展。

4.1 RAG+Memory 架构：结构化知识库 + 非结构化经验

RAG+Memory 架构为 Agent 增加两层知识基础。RAG（Retrieval-Augmented Generation）层提供结构化的外部知识库——文档、数据库、API 等，通过向量检索或关键词检索获取相关知识注入 Agent 上下文。Memory 层提供非结构化的历史经验——过去的成功案例、失败教训、用户偏好等，存储在向量数据库或结构化存储中。两层知识协同工作：RAG 提供"世界知识"，Memory 提供"个人经验"。

4.2 Multi-Agent 架构：跨 Agent 通信与协作

Multi-Agent 架构将复杂任务分解给多个专业化 Agent，每个 Agent 有独立的角色定义、工具集和推理能力。关键挑战不是"如何分工"——这通常很直观——而是"如何协作"。2026 年的生产数据显示，Multi-Agent 系统中跨 Agent 通信成本占总计算量的 60% 以上——每次消息传递都需要序列化、传输、反序列化，加上接收方的理解成本。当 Agent 数量超过 5 个时，通信成本开始超过任务执行成本。

4.3 Multi-Agent 的成本真相

Multi-Agent 经常被过度使用。一个常见的错误模式是用 3-5 个 Agent 来解决一个 ReAct Agent 就能搞定的问题。生产实测数据：在一个"研报生成"任务中，3-Agent 系统（研究员+分析师+写手）的总 Token 消耗是单 Agent 的 4.2 倍，其中 62% 是通信开销（Agent 之间传递上下文、协商分工、合并结果）。只有在任务确实需要不同专业知识（如同时需要法律知识+财务知识+技术知识）时，Multi-Agent 才能证明其成本合理性。

Multi-Agent 的正确使用时机：当你发现单个 Agent 的 prompt 已经超过 5000 tokens（因为要同时扮演多个角色），或者单个 Agent 需要同时使用 10 个以上不相关的工具集，或者任务天然包含"审查-被审查"的对立角色——这些信号说明任务复杂度已经超出了单 Agent 的承载能力，是时候拆分了。

05

Graph/Workflow 架构：确定性与灵活性的统一

Graph/Workflow 架构（以 LangGraph 为代表）是 2026 年企业 A…

Graph/Workflow 架构（以 LangGraph 为代表）是 2026 年企业 Agent 系统的主流选择，因为它解决了其他所有架构都回避的核心问题：如何在保持 Agent 灵活性的同时实现流程的确定性和可观测性。它用状态图（StateGraph）将 Agent 的执行路径显式建模为节点（处理步骤）和边（状态转换），支持条件分支、循环、断点续传和时间旅行。

5.1 固定节点与动态节点的双层设计

Graph/Workflow 架构的精妙之处在于区分固定节点和动态节点。固定节点执行确定性的操作（数据校验、格式转换、API 调用），不走 LLM，行为可预测。动态节点由 LLM 驱动（推理、决策、生成），行为灵活但不确定。两种节点通过条件边连接——条件边根据当前状态决定下一步走哪个节点，可以是确定性规则（如"如果 API 返回错误 → 走错误处理节点"）或 LLM 判断（如"分析结果质量是否足够 → 走 END 或走 Reflection 节点"）。

5.2 可观测性与可回滚性

Graph/Workflow 架构相比其他架构的最大优势是可观测性和可回滚性。每个节点的输入状态、输出状态、执行耗时、Token 消耗都被完整记录。当 Agent 输出不正确时，开发者可以像查看流水线日志一样，逐个节点检查，精确定位是哪个节点出了问题。更进一步，利用 Checkpoint 机制可以"回退"到任意一个历史节点，用不同的参数重新执行——这就是所谓的"时间旅行"调试。

5.3 企业级生产案例

某保险公司的理赔 Agent 系统采用 LangGraph 构建，包含 12 个节点（4 个固定节点 + 8 个动态节点）。固定节点处理：文件格式校验、保单数据库查询、金额计算、合规检查。动态节点处理：损失评估、欺诈风险判断、理赔方案推荐、客户沟通生成。系统在上线后的前三个月内，通过 Checkpoint 回退机制处理了 347 次"Agent 判断失误"的情况——每次回退都节省了从头开始处理的成本，累计节省约 2.1 万美元的 LLM 调用费用。

Graph/Workflow 架构在 2026 年成为企业首选的根本原因是"可审计性"——金融、医疗、法律等受监管行业要求每个 AI 决策都能被追溯和解释。ReAct 的 Thought 链虽然透明，但不结构化、难以审计；Graph/Workflow 的节点日志天然结构化，可以直接对接审计系统。这是架构选择从"技术最优"转向"合规最优"的标志性转变。

6.4 ReWOO 与 Tree-of-Thoughts：两种进阶推理模式

除了前述的七种核心架构外，2026 年还涌现出两种值得关注的进阶推理模式。ReWOO（Reasoning Without Observation）是一种"规划一次、减少 LLM 调用"的效率优化模式——它先让 LLM 一次性生成完整的推理计划（包含所有工具调用），然后并行执行所有工具调用，最后只用一次 LLM 调用汇总结果。这种方式将 LLM 调用次数从 ReAct 的 N 次降低到 2-3 次，代价是失去了逐步观察和调整的能力。Tree-of-Thoughts（ToT）则是一种"搜索式推理"模式——它不是沿一条推理链前进，而是在每个决策点生成多个候选方案，评估每个方案的前景，选择最有前景的路径继续探索。ToT 适合需要创造性思维或搜索最优解的任务（如数学证明、创意生成），但计算成本是 ReAct 的 3-10 倍。

推理模式核心机制LLM 调用次数最佳场景主要限制
ReAct逐步思考-行动-观察N 次（每步 1 次）探索性、不可预测任务Token 消耗高
ReWOO一次性规划+并行执行2-3 次工具调用密集、路径可预测无法中途调整计划

6.5 不同团队规模的架构推荐

架构选型不仅取决于任务特性，还受限于团队的技术能力和维护资源。以下是针对不同团队规模的务实建议：

6.6 架构演化的三个阶段

一个典型的 Agent 系统在其生命周期中会经历三个架构演化阶段。第一阶段是"原型验证"——使用最简架构（工具调用或简单 ReAct）快速验证业务可行性，关注的是"能不能做"。第二阶段是"效率优化"——当原型验证通过后，根据实际运行数据识别瓶颈（如 LLM 调用成本过高→引入 Plan-and-Execute；输出质量不稳定→加 Reflection；知识不足→加 RAG），逐步升级架构，关注的是"做得好不好"。第三阶段是"生产加固"——引入 Graph/Workflow 实现流程可控性、Checkpoint 保障容错性、可观测性满足合规要求，关注的是"稳不稳得住"。

效率优化降低成本、提升质量+P+E / +Reflection / +RAG成本效率比、质量评分1-3 月

架构演化的核心原则是"数据驱动升级，而非直觉驱动升级"。每次架构升级都应该有明确的量化动机——"LLM 调用成本超出预算 200%"→ 引入 Plan-and-Execute；"输出错误率超过 15%"→ 加 Reflection 层；"每月有 3 次因 Agent 崩溃导致的任务丢失"→ 引入 Graph+Checkpoint。没有数据支撑的架构升级就是过度设计。

Q&A

ReAct 和 Plan-and-Execute 在什么场景下应该组合使用？
最佳组合场景是"全局可规划但局部需要探索"的任务。例如"竞品分析报告"——全局步骤可以预先规划（确定竞品→收集数据→对比分析→生成报告），但每一步内部可能需要探索（搜索竞品信息时，第一条搜索结果可能不够，需要多步搜索和筛选）。此时外层用 Plan-and-Execute 做宏观规划和 Replan，内层每个 Executor 用 ReAct 做微观探索。这种组合比纯 ReAct 节省约 60% 的 LLM 调用（规划减少了无效探索），比纯 Plan-and-Execute 更灵活（局部 ReAct 应对意外情况）。
Reflection 加多少轮才合适？会不会越反思越差？
实验数据显示 2-3 轮反思是最佳平衡点。Reflexion 论文中 GPT-4 在 HumanEval 上的 pass@1 从第 0 轮的 80% 提升到第 2 轮的 91%，但继续反思到第 5 轮仅提升到 92%——边际收益急剧递减。更严重的是"过度反思"风险：在某些场景下，LLM 的自检能力有限，可能把正确的代码"修正"成错误的（False Positive 自检）。生产建议：设定 max_reflections=3，并增加一个"信心分数"机制——如果 Agent 对自己输出的信心分数超过阈值则跳过反思，避免画蛇添足。
Multi-Agent 的通信成本占 60%+ 具体是怎么产生的？
通信成本来自四个层面。第一，序列化成本——Agent A 的输出需要格式化为 Agent B 能理解的结构化消息（通常要经过一次 LLM 调用来做格式转换）。第二，上下文注入成本——Agent B 接收消息后需要将前序 Agent 的工作成果注入自己的上下文窗口（可能很长，如一份完整分析报告）。第三，对齐成本——当 Agent 之间理解不一致时需要额外的通信轮次来"对齐语义"（如 Agent A 说的"用户留存"和 Agent B 说的"用户留存"定义不同）。第四，合并成本——最终结果需要将所有 Agent 的输出合并为一致的整体（可能需要额外的 LLM 调用来消解矛盾）。在 3-Agent 系统中，这四个层面的总 Token 消耗通常占总消耗的 55-70%。
Graph/Workflow 架构的设计复杂度会不会成为瓶颈？
会。Graph/Workflow 的前期设计成本是所有架构中最高的——需要预先定义所有节点、边、状态类型和条件逻辑。一个中等复杂度的 Graph 系统（10-15 个节点）的设计和调试周期通常在 2-4 周。但这个成本是一次性的——一旦 Graph 建立，后续的维护和扩展成本反而低于其他架构（因为结构清晰、行为可预测）。投资回报的临界点大约是"任务会被重复执行 100 次以上"——如果是只做一次的一次性任务，用 ReAct 更经济；如果是每天运行数千次的生产系统，Graph 的结构化优势会在几周内收回设计成本。
如何判断一个任务是否需要 RAG+Memory 增强？
三个判断信号。第一，任务涉及 Agent 不可能"记住"的知识——如企业内部文档、最新法规、特定领域数据，这些必须通过 RAG 实时检索。第二，任务需要跨会话的连续性——如用户上周讨论的项目进展、上次失败的解决方案，这些必须通过 Memory 层持久化。第三，Agent 的输出需要"有理有据"——如回答中需要引用具体文档段落、标注信息来源，这要求 RAG 层返回可溯源的 chunk。如果三个信号都不存在（任务是通用推理、单次会话、不需要引用），则纯 LLM 推理即可，RAG 反而会增加延迟和噪声。
七种架构中哪一种是 2026 年使用增长最快的？
Graph/Workflow 架构（以 LangGraph 为代表）是 2026 年增长最快的。驱动因素有三个：第一，企业合规需求——金融、医疗、法律等行业要求 AI 决策可审计，Graph 的节点日志天然满足这一需求；第二，生产稳定性需求——Checkpoint 和时间旅行机制让长周期任务具备了容错能力，这在其他架构中很难实现；第三，生态成熟度——LangGraph 在 2025-2026 年间建立了完整的工具链（LangSmith 可观测平台、LangGraph Cloud 部署平台、LangGraph SDK），降低了开发和运维门槛。但增长最快不等于使用最广泛——ReAct 仍然是使用最广泛的基础架构（43% 的生产系统），Graph/Workflow 主要在企业级场景快速增长。
一个生产 Agent 系统通常组合几种架构？有没有上限？
典型的生产系统组合 3-5 种架构。一个常见的配置是：Graph/Workflow（流程骨架）+ ReAct（动态推理节点）+ RAG+Memory（知识增强）+ Reflection（质量检查节点）。这四种组合覆盖了 80% 的企业 Agent 场景。架构组合的上限不是技术限制而是"复杂度预算"——每增加一种架构，系统的调试难度、维护成本、故障排查复杂度都会上升。经验法则是：如果你无法在 5 分钟内向一个新同事解释清楚整个系统的执行流程，说明架构组合已经过度了。Anthropic 的建议很务实："能通过评估的最简组合就是最佳组合。"
