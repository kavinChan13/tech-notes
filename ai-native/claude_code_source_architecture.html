01

Claude Code 到底是什么

Claude Code 不只是一个聊天框，而是一套围绕大模型构建的 开发执行系统

Claude Code 不只是一个聊天框，而是一套围绕大模型构建的开发执行系统。Claude 模型负责理解需求、分析问题并决定下一步；外层运行框架负责工具调用、状态管理、权限控制与任务编排。

关键不是"会不会生成代码"，而在于能否把"读、想、做、验"组织成一条完整流程。Agent 和 ChatBot 的区别在于：谁来构建上下文。ChatBot 靠人喂，Agent 自己搜、读、调，自己构建上下文。

多层状态系统

Claude Code 看起来像是"记住了"项目，但这种效果不是来自模型的长期记忆，而是来自…

Claude Code 看起来像是"记住了"项目，但这种效果不是来自模型的长期记忆，而是来自几种显式机制的组合：

机制谁写加载方式压缩行为
CLAUDE.md用户/团队每个 session 启动时加载不丢失，压缩后重新读取
Auto memoryClaude 自己只加载 MEMORY.md 前 200 行或 25KB详细主题文件按需读取
Session transcript系统本地 JSONL 记录支持 resume/fork/rewind
Task/Goal/Cron运行时按需注入跟踪未完成的任务状态
System ReminderHooks 触发事件粒度插入压缩后可通过 hook 重新注入
CLAUDE.md 和 auto memory 都是 context，不是 enforcement。如果某项要求必须 100% 执行，不应只写在 CLAUDE.md 里，而应使用 hook 或权限规则做强约束。这种"软规则"和"硬约束"分层，是 Claude Code 工程设计非常成熟的一面。
05

八种上下文注入方法

AI 的能力、问题和用法，本质都由上下文决定

AI 的能力、问题和用法，本质都由上下文决定。Claude Code 在常规对话外，提供了八种上下文注入方法，各有不同的生命周期和作用域。

方法核心作用加载时机上下文成本控制力度
CLAUDE.md持久规则与项目背景（事实）每 session 启动时高，常驻低，指导性
Rules特定路径的约束碰到匹配路径时才加载低到中中，path-scoped
Skills按需知识与流程描述常驻，正文按需低到中中
Subagents上下文隔离的专门工人按需 spawn主会话零成本中到高
Hooks生命周期自动化与硬约束事件触发时默认零高，确定性
Workflows大规模多代理编排按需运行脚本主会话低高，代码化
Output Styles修改 Agent "人设"注入 system prompt高，不压缩高，权重最高
System Prompt Append临时追加轻量指令CLI 参数，仅当次低低，临时性

5.1 CLAUDE.md：项目说明书

分两种加载模式：

  • 始终加载：根目录 CLAUDE.md + 本地个人偏好 CLAUDE.md，启动即加载，压缩后重新读取，全程在场
  • 按需加载：子目录 CLAUDE.md（如 app/api/CLAUDE.md），只在 Claude 读取该目录时才加载，压缩后丢失

官方建议给每个团队目录放自己的 CLAUDE.md，开发者用 claudeMdExcludes 跳过不相关团队的文件。

5.2 Rules：路径限定的约束

Rules 是 .claude/rules/ 目录下的 markdown 文件，可以加路径限定（YAML frontmatter 中的 paths:）。加了路径限定的 Rule 只在 Claude 碰到匹配路径时才加载，不浪费 token。

何时用 Rule：当一条约束是跨目录的（如所有 migration 文件只能追加），但又不需要全局生效时，path-scoped rule 是最佳选择。

5.3 Skills：按需流程包

Skill 不是提示词，本质是把一堆文件按约定结构打包。启动时只加载名字和描述（几十个 token），完整内容等到被调用时才进上下文。用完之后如果上下文满了，最旧的 skill 会被踢掉。

Skill vs CLAUDE.md：CLAUDE.md 放的是 Claude 需要随时知道的事实（构建命令、目录结构），Skill 放的是需要按步骤执行的流程（部署清单、review checklist）。

5.4 Hooks：确定性执行

Hooks 完全绕过了上下文窗口，是由 harness 在外部执行的代码。八种 hook 事件覆盖从启动到完成的全流程：

事件触发时机典型用途
PreToolUse工具执行前拦截危险命令、验证文件路径，exit code 2 直接阻止
PostToolUse工具执行后写文件后自动跑 Prettier，改代码后自动跑 linter
PermissionRequest权限对话框弹出前自动批准重复的安全操作
SessionStart会话启动时自动注入 git status、TODO 列表
PreCompact上下文压缩前把完整对话备份到文件
Stop回复完成时检查任务是否做完，返回 continue 让 Claude 继续
SubagentStopSubagent 完成时针对子代理的完成检查
UserPromptSubmit提交 prompt 时自动追加当前 sprint 信息

5.5 Output Styles：Agent 人设

位于 .claude/output-styles/，注入到 system prompt 里，权重最高但影响面也最大。注意：自定义 output style 会替换掉默认的 system prompt，除非在 frontmatter 里加 keep-coding-instructions: true。

5.6 System Prompt Append：轻量追加

通过 CLI 参数 --append-system-prompt 临时追加内容，不替换任何东西，只对当次调用生效。适合加编码规范、输出格式、语气偏好等轻量指令。

递减效应：追加的指令越多，Claude 对每条指令的遵循率越低。特别是指令之间有冲突的时候，遵循率下降得更快。

常见配置误区

错误做法为什么不对正确做法
"每次 X，必须做 Y"写在 CLAUDE.md模型选择做 vs 自动执行是两码事用 PostToolUse hook
"绝对不要做 Z"写在 CLAUDE.md提示词防护在长会话/压力下可能失效用 PreToolUse hook，exit code 2 硬护栏
30 行流程写在 CLAUDE.md流程不需要全程占 token放 Skill，CLAUDE.md 只放事实
Rule 没加路径限定跟写在 CLAUDE.md 一样全程加载加 paths: 限定作用域
个人偏好写在项目级文件污染团队共享配置放用户级本地文件
核心原则：事实放 CLAUDE.md，流程放 Skill，护栏放 Hook，隔离任务给 Subagent。不同的指令，要有不同的生命周期——需要的时候出现，不需要的时候消失。
07

SubAgent 与 Worktree

SubAgent 在自己独立的上下文窗口里跑，主会话看不到它的中间过程

7.1 SubAgent：上下文隔离

SubAgent 在自己独立的上下文窗口里跑，主会话看不到它的中间过程。一个 subagent 做了 50 轮搜索、读了 200 个文件，主会话的上下文窗口里只多了一段摘要。

Skill vs SubAgent 怎么选：需要看到每一步的中间结果？用 Skill。不需要，让它自己跑完给结论？用 SubAgent。

SubAgent 可以嵌套，最深五层。这是大规模编排的基础。

7.2 Worktree：文件隔离

当多个会话需要并行修改同一仓库时，最危险的不是"互相抢上下文"，而是"在同一个工作目录里改出冲突或覆盖"。Worktree 让每个隔离会话在独立目录和分支中推进。

组合使用：subagent 本身也支持 isolation: worktree。子代理既可以在独立上下文里思考，也可以在独立 worktree 里动手。这对大规模迁移、自动 review fix、并发实现不同模块非常有帮助。
08

Task 工具与 Goal 机制

维度Task 工具/goal
解决什么把复杂任务拆成可跟踪的子任务给整个任务设定一个明确的结束条件
关注重点还有哪些步骤没做完什么时候才算真正完成
工作方式结构化任务状态记录（TaskCreate/Update/Get/List）每轮结束后由独立 evaluator 模型检查
适合场景多步骤实现、多人要求合并、长链路修改有明确验收条件的任务（tests pass、lint clean）
工程亮点：任务是否完成的判断不完全留给正在执行的同一个模型，而是引入独立 evaluator。它基于 transcript 判断，不会自己跑命令，只检查 Claude 是否已在对话中充分展示了目标达成的证据。这鼓励用户把完成条件写成可验证的形式。
09

上下文窗口与 Compaction

Claude Code 面临的首要限制往往不是"模型不够聪明"，而是"上下文窗口会被迅速填满…

Claude Code 面临的首要限制往往不是"模型不够聪明"，而是"上下文窗口会被迅速填满"。上下文中同时存在：system prompt、auto memory、环境信息、MCP 工具名、skills 描述、CLAUDE.md、用户消息、Claude 回复、工具调用结果、hook 附加信息等。

Compaction 机制

Compaction 不是"无损压缩"，而是成本控制与可持续推进机制。重要请求和关键代码片段优先保留，但早期对话里的细粒度要求——尤其是只在聊天里出现过、没有外置到 CLAUDE.md 的规则——很可能被冲淡甚至丢失。

重要工程启示：如果重要约束只存在于对话里，而没有外置为 CLAUDE.md、hook、task list 或 goal 条件，那么随着会话变长，它们被压缩、弱化甚至遗失，是一件"正常会发生的事"。

System Reminder：中途定点纠偏

当 hook 返回 additionalContext 时，Claude Code 会把这段文本包装成 system reminder，插入到触发点附近。它不会在 UI 里显示，但 Claude 会在下一次模型请求时读到它。插入位置与生命周期事件有关：

  • SessionStart / Setup / SubagentStart：插在会话开头
  • UserPromptSubmit：插在用户 prompt 附近
  • PreToolUse / PostToolUse：插在工具结果附近
  • Stop / SubagentStop：插在回合末尾
10

Dynamic Workflows：编排代码化

当任务复杂到需要数十到数百个 agent 时，Anthropic 不再依赖 Claude 在…

当任务复杂到需要数十到数百个 agent 时，Anthropic 不再依赖 Claude 在主对话里一轮一轮地决定"下一步再开哪个 agent"，而是把 orchestration 本身代码化为 JavaScript 编排脚本。

解决三个老问题

问题表现Workflow 如何解决
偷懒（Agentic laziness）安全审查要查 50 项，查到第 35 项就宣布完成独立上下文窗口隔离，每个子任务完整执行
自我偏好（Self-preferential bias）让 Claude 检查自己写的代码，倾向于觉得没问题对抗验证：执行 agent + 验证 agent 分离
目标漂移（Goal drift）长会话中每次压缩都是有损的，边缘需求容易丢失编排逻辑代码化，不依赖对话记忆

六种编排模式

模式说明适用场景
Classify-and-act先用 classifier 判断任务类型，再分发给专用 agent任务类型明确的分类处理
Fan-out-and-synthesize拆成 N 个子任务，每个跑 subagent，最后汇总可并行的独立子任务
Adversarial verification每个执行 agent 配一个验证 agent，对抗性检查高可靠性要求的输出
TournamentN 个 agent 用不同方法做同一件事，逐对比较选最优需要多方案对比
Generate-and-filter先大量生成，再过滤去重创意生成、候选方案
Loop until done不设固定轮数，循环直到满足终止条件不确定迭代次数的任务

成本控制：提示缓存与按需加载

Claude Code 很在意"上下文成本"

Claude Code 很在意"上下文成本"。每一轮都在重新发送大量上下文，并依赖 prompt caching 来降低成本。

机制作用效果
Prompt caching缓存 system prompt 等稳定前缀避免重复计算，命中率 85-92%
按需加载Skills/Rules/子目录 CLAUDE.md 只在需要时加载减少上下文占用
SubAgent 隔离副任务在独立窗口跑，主会话零成本避免主会话被中间结果淹没
Compaction对话过长时自动摘要可持续推进，但早期细节可能丢失
Workflow 脚本化编排逻辑在脚本变量中，不回主会话大规模任务的成本控制

它不是单纯在"加功能"，而是在逐步把代理系统从一段聊天，升级成一个有运行时、有状态层、有编排层的工程系统。

四条设计心法

  1. 模块化比文件数量重要：单文件也能有清晰的架构边界
  2. 安全是设计出来的：权限分层、沙箱隔离、结果过滤三层缺一不可
  3. 上下文管理是核心竞争力：精心管理每轮对话的上下文决定了 Agent 的质量上限
  4. 简单优先：不过度工程化，保持代码可读性和可维护性

实践建议

  • 持久规则外置到 CLAUDE.md，不要只靠对话记忆
  • 软规则用 CLAUDE.md，硬约束用 Hook/Permission
  • 给 Claude 能运行的验证标准（tests/lint/screenshot）
  • 调查性副任务交给 SubAgent，避免主会话被淹没
  • 复杂流程写成 Workflow script，不要硬扛在对话里
  • 事实放 CLAUDE.md，流程放 Skill，护栏放 Hook
  • 无关任务之间及时 /clear
  • 用 path-scoped Rules 避免全局 token 浪费
  • 不要把所有说明都塞进 CLAUDE.md
  • 不要只在 CLAUDE.md 里写"永远不要做 X"
  • 不要让 SubAgent 继承主 Agent 的全部权限
  • 不要忽略中间件顺序和 Hook 事件生命周期
  • 不要忽视 Compaction 的有损性——重要约束必须外置
  • 不要一次性加载所有技能，浪费上下文窗口
  • 不要忽略追加指令的递减效应
  • 不要让编排逻辑继续留在对话里——该代码化就代码化

常见问题

📖 知识来源（三篇合并）：
Agent 和 ChatBot 的本质区别是什么？
区别在于"谁来构建上下文"。ChatBot 靠人喂，你给它什么材料它就用什么材料。Agent 会自己搜网页、读文档、调工具，把有用的内容写进上下文，发现不够还会自动回头继续找。
为什么在 CLAUDE.md 里写"永远不要做 X"不靠谱？
因为 CLAUDE.md 是 context 不是 enforcement。模型选择做一件事跟自动执行一件事完全是两码事。任何提示词防护都可能在长会话、压力大或被 prompt injection 干扰时失效。绝对性约束应该用 PreToolUse hook 做硬护栏，exit code 2 直接阻止执行。
上下文窗口管理为什么是 Agent 质量上限？
Agent 的输出质量 = f(模型能力 × 上下文质量)。即使模型再强，如果上下文混乱、信息缺失或被噪声淹没，输出质量也会大打折扣。Prompt Cache 命中率从 70% 优化到 92% 后，输出一致性评分可从 3.2/5 提升到 4.5/5。
SubAgent 和 Skill 怎么选？
需要看到每一步的中间结果？用 Skill（在主线程里执行）。不需要，让它自己跑完给你一个结论？用 SubAgent（在独立上下文窗口里跑）。一个 SubAgent 做了 50 轮搜索、读了 200 个文件，主会话只多了一段摘要。
Dynamic Workflows 解决什么问题？
解决三个老问题：偷懒（查到第 35 项就宣布完成）、自我偏好（检查自己代码倾向于觉得没问题）、目标漂移（长会话中边缘需求在压缩中丢失）。Workflow 用独立上下文窗口隔离每个子任务，编排逻辑代码化，从结构上消解这三个问题。
六种编排模式分别在什么时候用？
Classify-and-act 用于任务类型明确时；Fan-out-and-synthesize 用于可并行的独立子任务；Adversarial verification 用于高可靠性要求；Tournament 用于多方案对比；Generate-and-filter 用于创意生成；Loop until done 用于不确定迭代次数的任务。实际项目中常常组合使用。
System Reminder 为什么是长流程系统的关键能力？
它允许系统在会话中途，按事件粒度向模型追加高优先级上下文，而不混进显式聊天流。比如当 Claude 准备改一个生成文件时，hook 可以提醒"请改源文件后重新生成"；在 compaction 之后，hook 可以重新注入关键工作状态，避免摘要弱化。
