HNSW 算法详解

HNSW（Hierarchical Navigable Small World）是当前最主流…

算法原理

HNSW（Hierarchical Navigable Small World）是当前最主流的 ANN 索引算法，融合了跳表和可导航小世界图的思想。

构建过程

  1. 为新节点随机生成层级 l = floor(-ln(rand()) × mL)，其中 mL = 1/ln(M)
  2. 从最高层的入口点开始贪心搜索到第 l+1 层（仅定位）
  3. 从第 l 层到第 0 层：以 efConstruction 宽度搜索候选邻居，选择 M 个最优建立双向连接
  4. 若邻居连接数超过 M_max（底层 2M，高层 M），按距离排序裁剪

搜索过程

  1. 从最高层入口点开始
  2. 每层执行贪心搜索：跳到离 query 最近的邻居
  3. 在最底层（Layer 0）使用 efSearch 宽度的 beam search
  4. 返回 Top-K 结果

关键参数调优

参数范围影响调优建议
M8~64邻居数 → 召回率↑ 内存↑ 构建时间↑中等数据集 32，大数据集 16~24
efConstruction64~512构建搜索宽度 → 图质量↑ 构建时间↑通常 4×M ~ 8×M
efSearch16~512查询搜索宽度 → 召回率↑ 延迟↑根据 recall@K 需求动态调整

复杂度分析

  • 查询：O(log N) — 层数 ≈ log(N)/log(M)，每层贪心 O(M×efSearch)
  • 构建：O(N × log N × efConstruction)
  • 空间：原始向量 + O(N × M × 4B × avg_layers)，通常 HNSW 图结构占原始数据 10~30%
内存 ≈ N × (dim × 4B) + N × M × 4B × (1 + 1/ln(M))
  • HNSW 的核心创新是"分层 + 长短连接"：高层长跳定位区域、底层短跳精确搜索
  • efSearch 是查询时唯一的"精度-延迟"调节旋钮
  • HNSW 支持增量插入（无需重建），这是对比 IVF 的关键优势
02

IVF 与 PQ 算法

优点：内存友好（不需要图结构）、构建较快

IVF（Inverted File Index）

原理

  1. 训练阶段：用 K-Means 将向量空间聚类为 nlist 个 Voronoi 区域
  2. 索引阶段：每个向量归入最近的聚类中心，建立倒排链表
  3. 查询阶段：计算 query 与所有聚类中心的距离，选最近的 nprobe 个簇，只搜索这些簇内的向量

参数

参数典型值说明
nlist√N ~ 4√N聚类中心数，越大训练越慢但粒度越细
nprobe1 ~ nlist搜索的簇数，nprobe/nlist = 搜索比例

优点：内存友好（不需要图结构）、构建较快

缺点：边界向量召回差、需要训练、不方便增量更新

PQ（Product Quantization，乘积量化）

核心思想

  1. 将 D 维向量切分为 M 个 D/M 维子向量
  2. 对每个子空间独立训练 K 个聚类中心（码本 codebook）
  3. 每个子向量用最近聚类中心的 ID（通常 8-bit）表示
  4. 原始向量压缩为 M 个字节
1536维 float32 (6144B) → PQ96×8bit → 96 字节（压缩 64 倍）

距离计算

  • SDC（Symmetric Distance Computation）：两端都用量化码
  • ADC（Asymmetric Distance Computation）：query 用原始向量，数据用量化码，精度更高
  • 查找表预计算加速：O(K×M) 预计算 → 每个向量的距离只需 M 次查表求和

组合索引：IVF + PQ

训练：K-Means(nlist) + PQ 码本训练

查询：粗量化(选 nprobe 个簇) → PQ 距离计算 → Top-K 精排

IVFPQ 是十亿级向量搜索的经典方案，在 recall 和内存之间取得最佳平衡。

  • IVF 的本质是"分治"：先粗定位再精搜索
  • PQ 的本质是"有损压缩"：用子空间聚类 ID 替代原始浮点值
  • ADC vs SDC：ADC 精度更高（query 端不量化），是实践中的首选

距离度量与选择

当向量 L2 归一化后（‖v‖ = 1）：

常用距离度量

度量公式范围特点典型场景
余弦相似度cos(A,B) = A·B / (‖A‖‖B‖)[-1, 1]方向相关，长度无关文本语义、Embedding 对比
L2 (欧氏)√Σ(a_i - b_i)²[0, +∞)方向 + 大小图像特征、聚类
内积 (IP)Σ(a_i × b_i)(-∞, +∞)方向 + 大小推荐系统、MIPS
汉明距离不同位的数量[0, n]仅二值向量LSH、哈希检索

归一化后的等价关系

当向量 L2 归一化后（‖v‖ = 1）：

Cosine(A,B) = IP(A,B) = 1 - L2²(A,B)/2

三种度量完全等价，计算 IP 最快（省除法）。OpenAI / Cohere 的 Embedding API 输出已归一化向量，直接用 IP 即可。

选择指南

  • Embedding 模型输出已归一化 → IP（最快）或 Cosine
  • 未归一化且关注方向 → Cosine
  • 关注绝对距离（图像/聚类）→ L2
  • 训练时用什么度量，检索时就用什么度量
  • 归一化后 Cosine = IP = f(L2) 是Q&A
  • 选择度量必须与 Embedding 模型训练时一致
  • L2 和 Cosine 的转换关系：L2² = 2(1 - cos) （归一化后）

Milvus 架构

Milvus 2

整体架构

Milvus 2.x 采用存算分离的云原生微服务架构：

Proxy（接入层）→ Coord 层（Root/Query/Data/Index Coord）

Worker 层：QueryNode（查询）/ DataNode（写入）/ IndexNode（构建索引）

存储层：etcd（元数据）+ MinIO/S3（对象存储）+ Pulsar/Kafka（日志流）

核心组件

组件职责
Proxy请求路由、鉴权、负载均衡
RootCoordDDL 管理（创建/删除 Collection）
QueryCoord查询任务调度与负载均衡
DataCoord数据写入管理、Segment 分配
IndexCoord索引构建任务调度
QueryNode加载 Segment 到内存，执行向量搜索

数据模型

  • Collection → 类似表，定义 Schema（向量字段 + 标量字段）
  • Partition → Collection 的逻辑分区，加速过滤
  • Segment → 数据的物理存储单元（Sealed / Growing）
  • 支持多种索引：HNSW、IVF_FLAT、IVF_PQ、IVF_SQ8、DiskANN、GPU_IVF_FLAT
  • Milvus 的存算分离架构是面试重点 — 理解各 Coord 和 Node 的职责
  • Milvus 依赖 etcd + MinIO + Pulsar/Kafka，运维复杂度较高
  • Segment（Sealed vs Growing）是理解 Milvus 写入和查询链路的关键

Qdrant 与 Weaviate 架构

Qdrant

  • Rust 实现，高性能低内存占用
  • HNSW + 标量量化（SQ）/ 乘积量化（PQ）
  • Payload 索引：对元数据建索引，高效过滤
  • 单节点部署简单，集群通过 Raft 共识实现一致性
  • 支持 mmap 将向量数据映射到磁盘（降低内存需求）

Qdrant 独特功能

  • 多向量支持：同一 Point 存储多个 Named Vector（不同 Embedding 模型）
  • 稀疏向量：原生支持 Sparse Vector（BM25/SPLADE）
  • Quantization：Scalar（int8）/ Binary / Product Quantization

Weaviate

  • Go 实现，模块化架构
  • 内置 Vectorizer 模块：直接传入文本/图片，自动调用 Embedding 模型
  • GraphQL API + RESTful API
  • 原生 BM25 + 向量混合搜索
  • Generative Search 模块：检索后直接调用 LLM 生成

模块系统

模块类型示例
Vectorizertext2vec-openai、text2vec-cohere、multi2vec-clip
Generativegenerative-openai、generative-cohere
Rerankerreranker-cohere、reranker-transformers

三大引擎对比

维度MilvusQdrantWeaviate
语言Go + C++RustGo
索引类型HNSW/IVF/PQ/DiskANNHNSW + 量化HNSW
分布式原生分布式Raft 集群Raft 集群
过滤性能强（位图索引）强（Payload 索引）中
特色功能最全面高性能、低内存模块化、开发者友好
运维复杂度高（依赖多）低~中中
  • Qdrant 的 Rust 实现和多向量支持是其核心竞争力
  • Weaviate 的模块化设计（自动向量化 + 生成式搜索）适合快速原型
  • Milvus vs Qdrant 是面试最常见的对比题：功能全面性 vs 部署简单性

性能调优与十亿级挑战

性能调优核心维度

维度优化方向具体手段
召回率提升搜索质量增大 efSearch/nprobe、使用 HNSW、调大 M
延迟降低查询时间减小 efSearch/nprobe、向量量化、内存预加载
吞吐提升 QPS增加 QueryNode 副本、批量查询、GPU 加速
内存降低资源占用PQ/SQ 量化、mmap 映射磁盘、降维

十亿级向量的挑战

核心问题：内存

10 亿 × 1536 维 × 4B = 5.7TB 原始向量数据

解决方案

  • 量化压缩：SQ8 压缩 4x（1.4TB），PQ96 压缩 64x（89GB）
  • DiskANN：向量存磁盘，内存只保留压缩导航图（Vamana 图 + PQ 码）
  • 分布式分片：数据切片到多节点，并行搜索后合并
  • 分层索引：粗排用低精度全量索引，精排用高精度子集
  • 降维：Matryoshka Embedding（768 → 256 维，recall 损失 <2%）

DiskANN 原理

  • Microsoft 开源的磁盘友好 ANN 算法
  • 构建 Vamana 图索引 → 存储在 SSD 上
  • 查询时：PQ 码在内存中做粗排 → SSD 随机读精排
  • 内存占用可降低到原始数据的 5~10%
  • Milvus 2.x 已集成 DiskANN 索引类型
  • 十亿级向量的核心瓶颈是内存，解题思路：量化 + 磁盘索引 + 分布式
  • DiskANN 是解决大规模场景内存问题的关键技术
  • recall vs latency vs memory 是向量数据库的"不可能三角"

Q1：HNSW 和 IVF 的核心区别是什么？各自适合什么场景？

HNSW 基于多层图搜索（贪心遍历 + beam search），IVF 基于聚类分治（K-Means 划分 + 倒排搜索）。核心区别：① HNSW 查询更快 O(log N)，但内存占用大（需存图结构）；IVF 内存更友好（尤其配合 PQ），但需要训练聚类中心。② HNSW 支持增量插入（图动态更新），IVF 增量更新困难（需重训练聚类中心）。③ HNSW 适合中等规模（百万~千万级）、低延迟需求；IVF+PQ 适合超大规模（十亿级）、内存受限场景。实际生产中 HNSW 用得最多。

Q2：Product Quantization (PQ) 是如何压缩向量的？精度损失如何？

PQ 将 D 维向量切分为 M 个子空间，每个子空间独立用 K-Means 训练 K=256 个聚类中心（码本）。每个子向量用 8-bit 码本 ID 替代原始浮点值。例如 1536 维 float32 向量（6144 字节），PQ96×8bit 后只需 96 字节（64 倍压缩）。精度损失：通常 recall@10 从 99% 降到 90~95%，可通过增加 M（更细的子空间划分）和 re-ranking（用原始向量精排 Top-K×10 候选）来补偿。OPQ（Optimized PQ）通过正交旋转预处理进一步减少量化误差。

Q3：Milvus 的存算分离架构有什么优势和劣势？

优势：① 弹性伸缩 — QueryNode/DataNode/IndexNode 独立扩缩，查询峰值只需扩 QueryNode；② 存储无限 — 数据存 S3/MinIO，不受单机磁盘限制；③ 故障隔离 — 某组件挂掉不影响其他组件。劣势：① 运维复杂 — 需维护 etcd（元数据）、MinIO（存储）、Pulsar/Kafka（日志流）；② 延迟增加 — 组件间通过网络通信，比单机部署延迟高；③ 调试困难 — 分布式微服务链路长。适合大规模生产环境（百万~十亿级），小规模场景 Qdrant/pgvector 更合适。

Q4：如何处理十亿级向量的存储和检索？

核心策略组合：① 量化压缩 — SQ8（4x 压缩）或 PQ（16~64x 压缩）减少内存占用；② 磁盘索引 — DiskANN 将向量存 SSD，内存仅保留压缩导航图（5~10% 内存）；③ 分布式分片 — 数据按 hash 分布到多个节点，并行搜索后合并（如 Milvus 分片）；④ 分层搜索 — 粗排用低精度全量索引（PQ），精排用高精度原始向量（只对 Top-K×N 候选）；⑤ 降维 — Matryoshka Embedding 支持 1536 → 256 维，存储减少 6 倍。实际案例：10 亿 768 维向量，DiskANN + SQ8 方案内存约 200GB（8 节点 × 25GB），延迟 <10ms。

Q5：向量数据库中的过滤搜索（Filtered Search）为什么是难题？

难点在于 ANN 索引和标量过滤的冲突：ANN 索引（HNSW/IVF）按向量距离组织数据，与标量条件无关。Pre-filter 先过滤再搜索 — 过滤后候选集可能太小导致 ANN 索引退化为暴力搜索（高选择性时 O(N) → 很慢）。Post-filter 先搜索再过滤 — 搜出的 Top-K 可能过滤后不足 K 个（结果不够）。解决方案：① 自适应策略 — 估算选择性后动态选择 pre/post；② 位图索引 — Milvus/Qdrant 对标量字段建位图索引，在 HNSW 遍历过程中同时评估过滤条件（single-stage）；③ Partition 裁剪 — 按常用过滤字段预分区。
