00

概览

多 Agent 系统的本质是 专业化分工的分布式工程架构 ——不是"让更多 Agent 一起…

多 Agent 系统的本质是专业化分工的分布式工程架构——不是"让更多 Agent 一起干活"，而是让专业 Agent 在统一调度下通过结构化通信实现 1+1 > 2 的系统级智能涌现。2026 年业界共识：能用单 Agent+Subagent 解决的不要用平等多 Agent。

01

任务分解——从混沌到结构化 DAG

任务分解是多 Agent 协作的起点

任务分解是多 Agent 协作的起点。Supervisor（监督者）将复杂任务拆解为独立的子任务，每个子任务有明确的产出物、完成标准和依赖校验。拆解决定了整个系统的上限。

任务拆解三原则

原则定义违反后果检验方法
独立性子任务之间尽量松耦合，减少同步需求Agent 间频繁等待，并行优势消失子任务依赖图中环路数量为零
可验证性每个子任务的输出有明确验收标准下游 Agent 接收到错误输入而不自知JSON Schema 校验、单元测试覆盖
上下文闭环拆分后子任务自包含所需上下文"传话游戏"式信息丢失子任务 Prompt 中不引用其他 Agent 的中间状态
任务分解四层模型（示例：新产品竞品分析报告）
Level 0 · 原始任务
"为新产品做完整竞品分析并输出报告"
Level 1 · Supervisor 拆解为 DAG
数据采集 Agent-A ∥ 价格分析 Agent-B ∥ 趋势预测 Agent-C（并行）
Level 2 · 汇总合成
Report Writer：整合 → 交叉验证 → 终稿
Level 3 · 质量审查
Reviewer Agent：数据一致性校验
2026 年业界共识：Anthropic 和 OpenAI 的实战经验都表明，80% 的"Multi-Agent 成功案例"其实是 Subagent 模式（主从隔离），而非平等多 Agent。能用单 Agent + Subagents 解决的，不要用平等的 Multi-Agent。任务分解的粒度控制是关键：过度拆分（拆分成本 > 并行收益）和拆分不足（单 Agent 上下文溢出）都会降低系统效率。
02

角色分配——System Prompt 定义与冗余设计

每个 Agent 的角色由 System Prompt 定义三个核心要素：专业领域（知道什么…

每个 Agent 的角色由System Prompt 定义三个核心要素：专业领域（知道什么）、工作方式（怎么做）、输出格式（输出什么）。工程红线：每个关键角色至少需要 2 个 Agent 冗余，防止单点故障。

角色定义三要素

要素System Prompt 中的体现示例反例
专业领域定义 Agent 的知识边界和工具集"你是数据分析师，擅长 SQL 查询和统计建模""你是全能助手"（无边界）
工作方式定义推理链、工具调用顺序"先查询数据，再计算统计量，最后给出结论"未指定步骤（Agent 自由发挥）
输出格式JSON Schema、字段约束"输出 JSON 格式，包含 analysis 和 confidence 字段"无格式要求（下游解析困难）

上下文摘要传递

Agent 之间不能共享完整上下文（上下文窗口限制），必须通过上下文摘要传递关键信息。摘要的原则是"只传结论，不传过程"——例如数据分析 Agent 传递"价格中位数 ¥299，标准差 ¥45"而不是完整的 1000 条原始数据。

传递方式信息完整性Token 消耗适用场景
完整上下文共享高——所有信息可见极高——线性增长紧耦合任务（A↔B 频繁交互）
结构化摘要传递中——保留关键结论低——固定大小松耦合任务（A→B 单向流）
只传状态码低——仅知成功/失败极低流水线中不需要前序细节的步骤
工程红线：关键角色必须有冗余。生产系统中，每个关键 Agent 至少配置 2 个实例——当主实例超时或出错时，备用实例接管。Claude Code 的实践表明，Sync Subagent 超过配置阈值时自动转为 Async 执行，防止单点阻塞。

角色分配的核心不是模仿人类岗位，而是让每个 Agent 的上下文窗口利用率最大化。手术室里的无菌原则同样适用——只放当前手术需要的器械，多余的器械不仅占空间还增加感染风险。

三种协作模式与混合架构

协作模式决定了 Agent 间的交互拓扑

协作模式决定了 Agent 间的交互拓扑。三种基础模式各有优劣：层级式提供控制力、平行式提供多视角、流水线提供确定性。生产系统几乎总是三者的混合。

流水线A→B→C 阶段接力处理确定性强、可预测、易调试灵活性差、无法回溯LangGraph

混合架构的生产实践

真实的生产系统几乎不会只用单一模式。典型的混合架构是：整体层级式调度（Supervisor 统一管理全局状态和任务分配）+ 关键决策点用平行式辩论（如风险评估、策略选择）+ 标准化子流程用流水线（如数据采集→清洗→入库）。

Stanford HAI 研究数据：混合架构的复杂推理任务性能比单 Agent 提升 3.2 倍。但 2026 年的反直觉发现是：Anthropic Subagent（主从隔离）模式是生产环境中唯一稳定运行的多 Agent 模式。平等 Multi-Agent 在控制流复杂度、调试难度和成本可控性上都显著劣于主从模式。

协作模式的选择不是技术偏好问题，而是任务耦合度问题。紧耦合任务（需要频繁交互）适合共享上下文，松耦合任务（独立执行后汇总）适合消息传递。错误的选择会导致系统要么通信开销过大，要么信息丢失过多。

双层容错——熔断 5 秒超时 + 降级人工兜底

多 Agent 系统从 Demo 到生产的最大障碍是 稳定性

多 Agent 系统从 Demo 到生产的最大障碍是稳定性。熔断机制在 Agent 响应超过阈值时自动切换备用路径，降级策略在高级 Agent 不可用时回退到简单方案。两层保障缺一不可。

熔断机制详解

参数典型值触发条件动作
超时阈值5 秒（快速任务）/ 30 秒（复杂推理）Agent 响应时间超过阈值中止当前请求，触发降级
错误率阈值连续 3 次错误或错误率 > 30%滑动窗口内错误计数熔断该 Agent，切到备用实例
恢复探测每 30 秒发送探测请求熔断状态持续中探测成功后恢复流量

2026 年多 Agent 框架已形成三大流派：OpenAI Swarm（Handoffs 模式）、Anthropic Subagents（主从隔离）、Google A2A（跨厂商互操作）。选择框架时关注的不应该是功能丰富度，而是上下文隔离模型和成本可控性。

生产级治理——监控、审计与安全

多 Agent 系统的治理面临三重挑战： 可观测性 （谁在做什么）、 安全性 （权限最小化）…

多 Agent 系统的治理面临三重挑战：可观测性（谁在做什么）、安全性（权限最小化）、成本控制（Token 消耗追踪）。2026 年的最佳实践是将这三者整合到统一的治理看板中。

治理看板的核心指标

指标类别具体指标告警阈值采集方式
可用性Agent 响应成功率、平均延迟成功率 < 95% 或 p99 > 10s每次请求埋点
质量工具调用正确率、输出 Schema 通过率正确率 < 90%Trace 日志分析
成本单任务 Token 消耗、月度 API 费用单任务 Token > 基线 200%API 调用日志
安全权限越界尝试次数、敏感数据泄露任何权限越界告警审计日志

安全原则：最小权限

每个 Agent 只拥有完成其任务所需的最小权限集。数据采集 Agent 只有读权限，代码生成 Agent 只有写权限，部署 Agent 只有部署权限。跨 Agent 通信时，敏感字段（如 API Key）必须在传递前脱敏。

2026 年的安全教训：某企业多 Agent 系统中，一个负责搜索的 Agent 被 Prompt 注入攻击后，将搜索到的恶意内容通过共享上下文传递给了代码执行 Agent，导致远程代码执行。根因是搜索 Agent 的输出未经消毒就进入了执行 Agent 的上下文。
IoA Task Protocol（IETF 草案）：2026 年 4 月提出的跨异构 Agent 协作协议，定义了分层消息格式和会话管理。核心创新是"动态团队形成"——Agent 可以按需加入/离开协作组，通过标准化的 Task 消息实现跨设备、跨厂商的分布式协作。这代表了多 Agent 互操作的未来方向。
  • 每个 Agent 独立上下文窗口，通过结构化摘要通信
  • 关键角色配置 2+ Agent 冗余
  • 通信选择按耦合度：紧耦合用共享状态，松耦合用消息传递
  • 成本分层：简单任务用 3B 模型，关键决策用 70B+ 模型
  • 每次 Agent 输出附带 confidence 分数
  • 建立统一治理看板，监控可用性/质量/成本/安全
  • 不要让所有 Agent 共享完整上下文（上下文污染）
  • 不要在没有熔断机制的情况下部署多 Agent 系统
  • 不要用平等多 Agent 解决 Subagent 能解决的问题
  • 不要忽略 Token 成本——多 Agent 系统消耗约为单 Agent 的 15 倍
  • 不要假设 Agent 间的通信是可靠的
  • 不要在 Agent 间传递未脱敏的敏感数据

语义路由与能力发现

CERN 的 Federation of Agents （FoA）框架引入了 版本化能力向量…

CERN 的 Federation of Agents（FoA）框架引入了版本化能力向量（Versioned Capability Vectors）：每个 Agent 将自己的能力、成本、局限性编码为语义向量，通过 HNSW 索引实现高效的语义路由——任务到达时自动匹配最合适的 Agent。

传统路由 vs 语义路由

维度传统路由（关键词/规则）语义路由（向量匹配）
匹配方式精确匹配关键词或正则语义相似度（embedding 距离）
灵活性低——需要穷举所有触发词高——语义近似自动覆盖变体
扩展性Agent 增加时需手动更新规则Agent 注册时自动更新索引

ACP-A2A 合并信号：2026 年初 ACP（Agent Communication Protocol）与 A2A 的合并表明协议正在走向收敛。最终可能形成一个统一的 Agent 间通信标准，就像 HTTP 统一了 Web 通信一样。MCP 和 A2A 之所以能共存，是因为它们解决的是不同层面的问题——一个是"Agent 怎么使用工具"，一个是"Agent 怎么和其他 Agent 对话"。

场景推荐协议原因

协议选择的本质是"谁需要和谁通信"的问题。Agent→Tool 用 MCP，Agent→Agent 用 A2A，跨网络异构用 IoA。不需要一开始就全部采用——从 MCP 开始（解决工具调用），按需引入 A2A（解决 Agent 间通信），IoA 留给未来的跨组织场景。

协议演进的启示：就像互联网从 FTP → HTTP → WebSocket 的演进，Agent 协议也在从"能通信"走向"高效通信"走向"实时通信"。当前阶段 MCP + A2A 已经覆盖了绝大多数场景。

Q&A

多 Agent 系统的 Token 成本到底有多高？如何控制？
生产数据显示：单 Agent 对话为 1× 基线，单 Agent+工具约 4× 基线，多 Agent 系统约 15× 基线。成本控制的三个核心手段：（1）上下文隔离——每个 Agent 只看自己需要的信息，避免全局上下文膨胀；（2）成本分层——简单任务用 3B 模型（$0.001/次），关键决策才用 70B+ 模型（$0.10-0.50/次）；（3）摘要传递——只传结论不传过程，减少下游 Agent 的输入 Token。BrowseComp 评测发现 Token 用量解释了 80% 的性能方差，所以成本控制不是简单地"用便宜的模型"，而是在关键环节投入足够 Token。
什么时候应该用多 Agent，什么时候单 Agent 就够了？
2026 年的判断标准是：如果单 Agent 的上下文窗口装不下所有需要的信息（如需要同时处理 100+ 文件、或需要并行搜索多个数据源），或者任务需要真正的专业化分工（如同时需要安全评估和性能评估两个独立视角），才用多 Agent。Anthropic 和 OpenAI 的共识是：能用单 Agent + Subagent 解决的不要用平等多 Agent。80% 的"多 Agent 成功案例"实际上只需要 Subagent 模式。多 Agent 不是默认方案，而是单 Agent 能力不足时的升级路径。
Handoff 模式和 Subagent 模式的核心区别是什么？
核心区别在于上下文隔离程度。Handoff 是把整个对话历史交给下一个 Agent 接管——新 Agent 看到所有历史，可以继续对话，但上下文窗口会逐步膨胀。Subagent 是主 Agent 派发一个独立任务，子 Agent 在独立上下文中执行，只把精炼结论传回主 Agent——主 Agent 的上下文保持干净。实战中，Subagent 更适合需要"深度搜索但只需结论"的场景（如搜索 100 个网页但只需 3 篇关键文章的论点），Handoff 更适合"对话式接力"的场景（如客服从通用 Agent 转到专家 Agent 继续和用户对话）。
多 Agent 系统中的并发冲突如何解决？
并发冲突主要发生在多个 Agent 同时写入共享状态时。解决手段有三层：（1）时间戳仲裁——每次写入带时间戳，后写入的覆盖先写入的（或合并）；（2）分布式锁——写入前先获取锁，其他 Agent 等待或重试；（3）CRDT（无冲突复制数据类型）——允许并发写入，通过数学保证最终一致性。Claude Code 用 Git Worktree 隔离解决了文件级并发——每个 Agent 在独立的 Git Worktree 中工作，最后由主 Agent 合并。这避免了文件冲突，代价是合并时需要解决冲突。
A2A 协议和 MCP 协议是什么关系？
它们是互补关系，占据不同的协议层。MCP（Model Context Protocol）解决的是 Agent-to-Tool 的连接——让 Agent 能调用外部工具和数据源，相当于"Agent 的手和脚"。A2A（Agent-to-Agent Protocol）解决的是 Agent-to-Agent 的通信——让不同厂商的 Agent 能互相发现和协作，相当于"Agent 之间的电话线"。2026 年的趋势是 MCP + A2A 形成完整的协议栈：MCP 在下层处理工具调用，A2A 在上层处理 Agent 间协作。ACP-A2A 的合并也表明协议正在走向收敛。
Claude Code 的 git worktree 隔离是如何工作的？
当主 Agent 生成 Async Agent 或 Teammate 时，每个子 Agent 都在一个独立的 Git Worktree 中工作。这意味着每个 Agent 有自己的文件副本，修改文件不会影响其他 Agent。就像三个程序员在三台电脑上各自编码，最后通过 git merge 合并。具体流程：主 Agent 创建 worktree 分支 → 子 Agent 在分支上工作 → 子 Agent 完成后提交 → 主 Agent 审查并合并。如果两个 Agent 修改了同一个文件，合并时会产生冲突，由主 Agent 解决。这种隔离确保了并行工作不会互相干扰。
如何评估多 Agent 系统的整体质量？有没有量化指标？
MDPI 2026 年 6 月发表的综述提出了六维评估框架：（1）任务完成率——子任务是否全部完成且结果正确；（2）协调效率——Agent 间通信轮次与任务复杂度的比值；（3）容错能力——单 Agent 故障后系统恢复时间；（4）成本效率——完成同等质量任务的 Token 消耗对比；（5）可扩展性——Agent 数量增加时性能的边际变化；（6）安全合规——权限越界和敏感数据泄露事件数。生产系统建议每个维度设置基线值和告警阈值，纳入治理看板持续监控。
多 Agent 系统中的"传话游戏"问题如何解决？
传话游戏（Telephone Game）是指信息在 Agent 间传递时逐步失真。解决方案分三层：（1）结构化摘要——不传自由文本，传 JSON 格式的结构化结论，包含置信度字段，减少歧义；（2）黄金注入——关键节点注入预录的标准上下文而非依赖上游传递（类似 TrainForge 的黄金注入技术）；（3）原始数据锚定——每个 Agent 可以回溯到原始数据源验证上游结论，而非盲目信任。Anthropic Subagent 模式天然缓解了这个问题——子 Agent 只传精炼结论给主 Agent，主 Agent 的上下文不会被中间过程污染。
小团队（3-5 人）如何务实地引入多 Agent 架构？
分三步走：第一步，用单 Agent + 2-3 个 Subagent 替代当前工作流中最耗时的环节（如代码审查 + 测试生成），验证 Subagent 模式的价值。第二步，如果确实需要多视角（如安全 + 性能同时评估），引入平行式辩论，但限制在 2-3 个 Agent。第三步，建立治理看板，监控 Token 成本和可用性。全程使用成本分层（简单任务用 3B 模型），月度 API 预算控制在 $50-100 以内。关键原则是"先证明价值，再扩大规模"，不要一开始就设计 10 个 Agent 的复杂系统。
