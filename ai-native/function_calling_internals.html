Function Calling 底层揭秘

Function Calling Internals — 没有新推理模块，只有 next token prediction 的模式切换，从训练到推理的全链路拆解

AI 工程 阅读 ~10 min 8 章
00

概览

Function Calling 的底层真相：模型并没有引入任何新的「推理模块」

Function Calling 的底层真相：模型并没有引入任何新的「推理模块」。它只是通过训练学会了在特定 token（如 <tool_call>）触发后，切换到一种结构化的文本生成模式 —— 输出 JSON 而非自然语言。本质上，这仍然是 next token prediction。

01

核心机制：Next Token Prediction 的模式切换

大模型的 Function Calling 不依赖任何特殊架构改动，完全建立在 next t…

大模型的 Function Calling 不依赖任何特殊架构改动，完全建立在next token prediction之上：

普通对话模式:
  User: "今天天气怎么样？"
  Model: "让我帮你查一下..."  ← 自然语言 token 序列

Function Calling 模式:
  User: "今天天气怎么样？"
  [系统注入工具定义]
  Model: <tool_call>
{"name": "get_weather",    ← 结构化 JSON token 序列
 "arguments": {"city": "北京"}}
</tool_call>

特殊 token 作为格式切换开关

Token作用触发后行为
<tool_call>开始工具调用模型切换到 JSON 生成模式
</tool_call>结束工具调用模型回到自然语言模式
<tool_result>注入工具结果模型基于结果继续推理
关键洞察：模型「并不理解」自己在调用工具。它只是学会了：当上下文包含工具定义 + 用户意图匹配时，下一个 token 应该生成 <tool_call>，然后按 JSON 格式输出。外部系统负责解析 JSON 并执行实际调用。
02

训练两阶段

目标：让模型学会工具调用的 格式 和 三种核心能力

2.1 阶段一：监督微调（SFT）

目标：让模型学会工具调用的格式和三种核心能力。

能力含义训练数据示例
触发时机判断什么时候该调工具、什么时候直接回答「1+1=?」→ 直接回答；「北京天气？」→ 调工具
参数格式生成按 Schema 生成正确的参数 JSON{"city": "北京", "date": "2024-01-01"}
结果整合拿到工具返回后，整合成自然语言回答工具返回温度数据 → 生成「北京今天 25°C，晴」
SFT 训练数据格式:

Input:
  [System] 你有以下工具: get_weather(city, date)
  [User] 明天北京天气怎么样？

Expected Output:
  <tool_call>
  {"name": "get_weather", "arguments": {"city": "北京", "date": "tomorrow"}}
  </tool_call>

Input (with tool result):
  [Tool Result] {"temp": 22, "condition": "多云"}

Expected Output:
  明天北京多云，气温 22°C，适合出行。

2.2 阶段二：强化学习（RL）

SFT 只教了格式，RL 负责优化调用质量：

优化目标RL 奖励信号效果
工具选择准确性选对工具 +1，选错 -1减少「调错工具」的错误
参数提取精确性参数正确 +1，参数缺失/错误 -0.5减少「参数漏填」和「参数格式错误」
边界控制该调不调 -1，不该调乱调 -1减少「误触发」和「漏触发」
RL 阶段的核心价值：让模型不仅"会调工具"，还要"调得准"。SFT 解决了格式问题，RL 解决了质量问题。

失败模式与优化

3.1 三类典型失败

失败类型根因表现优化方案
调用错误训练数据覆盖不足 / 工具描述歧义选错工具、该调不调补充相似场景训练样本、优化工具描述
参数错误缺少格式示例参数缺失、类型错误在描述中明确参数范例
误触发预训练惯性过强不需要工具时乱调强化系统提示 + 增加负样本

3.2 工具描述优化示例

# 差的描述（导致参数错误）
description: "获取天气信息"
parameters:
  city: string
  date: string

# 好的描述（减少参数错误）
description: "获取指定城市的天气预报。支持查询未来7天内的天气。"
parameters:
  city: string  # 城市名称，如 "北京"、"上海"
  date: string  # 日期，格式为 YYYY-MM-DD，如 "2024-01-15"
examples:
  - {"city": "北京", "date": "2024-01-15"}  # 明确的格式范例
  - {"city": "上海", "date": "2024-01-16"}
经验法则：工具描述中每多一个具体示例，参数错误率下降约 30%。模型对 few-shot 示例的遵循度远高于对抽象描述的遵循度。

串行调用 (基础):
Model → tool_call(get_weather) → result → tool_call(get_stock) → result → final_answer · 并行调用 (进阶): · Model → tool_call(get_weather) + tool_call(get_stock) ← 一次生成两个调用

4.3 强制控制机制

通过干预 token 概率分布实现调用开关：

模式实现方式效果
强制调用将 <tool_call> token 概率设为 1.0模型必须调工具
禁止调用将 <tool_call> token 概率设为 0.0模型不能调工具
自动模式不干预，模型自主决策模型自行判断是否需要调工具
强制控制的本质：在 softmax 层直接修改特定 token 的概率。这是工程层面的 hack，不涉及模型参数修改。OpenAI 的 tool_choice: "required" 就是这个原理。

完整推理链路

完整 Function Calling 推理流程
Step 1: 构建 Prompt
System Prompt + 工具定义(JSON Schema) + 用户消息
Step 2: 模型推理
Next Token Prediction → 生成 <tool_call> · 切换到 JSON 模式 → 输出 {"name":..., "args":...}
Step 3: 外部系统执行
解析 JSON → 找到对应函数 → 执行 → 获取结果 · ⚠️ 模型不参与执行！只负责生成文本
Step 4: 结果回注
将工具结果以 <tool_result> 格式注入上下文 · 模型基于结果生成最终自然语言回答
  • 工具描述包含具体参数示例
  • 用 RL 优化调用质量（不只是格式）
  • 为相似工具增加区分性描述
  • 增加「不需要调用」的负样本
  • 监控工具调用的成功率和参数正确率
  • 不要以为模型「理解」了工具调用的含义
  • 不要只靠 SFT 不跑 RL
  • 不要用模糊的工具名称（如 "get_data"）
  • 不要忽略误触发问题（不该调时乱调）
  • 不要假设所有模型的 FC 实现方式相同

生产案例

生产验证： 某 Agent 平台对 Function Calling 内部机制的深度分析：(…

生产验证：某 Agent 平台对 Function Calling 内部机制的深度分析：(1) 工具描述的 token 占比 — 20 个工具的描述占 System Prompt 的 35%（约 4.2K tokens），工具数 >30 时该比例升至 55%，挤压任务指令空间；(2) 工具选择延迟 — 工具数 5 个时选择延迟 120ms，工具数 30 个时升至 680ms（LLM 需要更多注意力来比较工具描述）；(3) 参数幻觉率 — 当参数描述缺少示例值时，LLM 编造参数值的概率 23%（如编造不存在的 API endpoint），添加示例值后降至 3%。Structured Output（JSON Schema 强制模式）使参数格式正确率从 87% 提升至 99.7%，但语义正确率不变（仍需应用层校验）。

面试 Q&A

Function Calling 的底层原理是什么？需要改模型架构吗？
不需要改模型架构。Function Calling 完全基于 next token prediction：模型通过训练学会了在特定 token（如 <tool_call>）触发后切换到 JSON 生成模式。本质上，生成 JSON 和生成自然语言对模型来说没有区别 —— 都是预测下一个 token。特殊 token 只是格式切换开关，模型参数和推理流程完全不变。
SFT 和 RL 两个阶段分别解决什么问题？
SFT 解决「会不会」的问题 —— 让模型学会工具调用的格式（什么时候生成 <tool_call>、JSON 怎么写）。RL 解决「好不好」的问题 —— 通过奖励信号优化工具选择的准确性、参数提取的精确性和边界控制。SFT 是入门培训，RL 是技能精修。只做 SFT 的模型能调工具但经常选错或参数出错。
强制调用（tool_choice: required）的底层实现是什么？
在 softmax 层直接修改 token 概率。具体来说：当用户设置 tool_choice=required 时，推理引擎将 <tool_call> token 的 logits 设为极大值（或将非工具 token 的 logits 设为极小值），确保模型必然生成工具调用。这是工程层面的 hack，不涉及模型参数修改，推理完成后恢复正常。
为什么有时候模型会「误触发」—— 不需要工具时乱调？
三个原因：(1) 预训练惯性 —— 模型在预训练中学到了「当用户提问时应该回答」的模式，但如果 SFT 数据中工具调用占比过高，模型会形成「看到问题就调工具」的偏见；(2) 工具描述过于宽泛 —— 比如一个叫 "search" 的工具描述了「搜索任何信息」，模型会觉得所有问题都该用它；(3) 缺少负样本 —— 训练数据中没有足够的「不需要调用工具」的示例。解决方案：增加负样本 + 优化工具描述边界。
不同厂商的 Function Calling 实现有什么差异？
三个维度的差异：(1) 标记方式 —— OpenAI 用控制符+JSON Schema、Anthropic 用 XML 标签、开源模型用特殊 token 或纯文本约定；(2) 并行调用 —— 部分模型（如 GPT-4）支持单次生成多个工具调用，其他模型只能串行；(3) 强制控制 —— 各厂商提供的 tool_choice 选项不同（auto/required/none/specific_tool）。但底层原理相同：都是 next token prediction 的模式切换。
如何提升 Function Calling 的可靠性？
从模型侧和使用侧两方面优化：模型侧 —— (1) 高质量 SFT 数据覆盖多样场景；(2) RL 优化调用准确性；(3) 增加负样本减少误触发。使用侧 —— (1) 工具描述清晰且包含参数示例；(2) 避免工具功能重叠；(3) 系统提示明确何时该调、何时不该调。可靠性 = 训练数据质量 × 工具描述清晰度 × RL 优化策略。
