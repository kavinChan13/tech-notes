概览

2026 年 7 月，Anthropic Claude Code 工程师 Thariq Sh…

2026 年 7 月，Anthropic Claude Code 工程师 Thariq Shihipar 发布了《A Field Guide to Claude Fable: Finding Your Unknowns》。这不是一份 prompt 技巧文档，而是一个范式宣言——它宣告了 AI 编程的核心矛盾已经转移：当 Fable 5 将系统 prompt 缩减 80%、模型智商不再是瓶颈时，输出质量的天花板变成了开发者澄清未知的能力。代码能运行但结果合理性存疑——根因是开发者与模型之间存在未对齐的隐性标准。

01

Fable AI 核心理念：从约束到探索

Fable 5 的发布标志着 AI 编程从"约束驱动"转向"探索驱动"

Fable 5 的发布标志着 AI 编程从"约束驱动"转向"探索驱动"。传统范式的逻辑是：模型不够聪明，所以开发者需要用详尽的 prompt 约束来弥补模型的能力缺陷。Fable 5 的逻辑完全相反：模型已经足够聪明，过多的约束反而限制了它的决策空间。

┌──────────── 范式转变：约束驱动 → 探索驱动 ────────────┐ │ │ │ 传统范式（弱模型时代）： │ │ ┌─────────────────────────────────────────────────┐ │ │ │ System Prompt: 65K tokens │ │ │ │ ├─ 编码风格规则: 2000 tokens │ │ │ │ ├─ 文件操作规范: 3000 tokens │ │ │ │ ├─ 安全边界约束: 5000 tokens │ │ │ │ ├─ Few-shot 示例: 10000 tokens │ │ │ │ └─ 错误处理规范: 2000 tokens │ │ │ │ → 策略: 给约束 → 模型遵守 → 输出可控但受限 │ │ │ └─────────────────────────────────────────────────┘ │ │ │ │ 新范式（Fable 5 时代）： │ │ ┌─────────────────────────────────────────────────┐ │ │ │ System Prompt: 13K tokens (缩减 80%) │ │ │ │ ├─ 核心目标: 200 tokens │ │ │ │ ├─ 领域上下文: 5000 tokens │ │ │ │ ├─ 完成标准: 1000 tokens │ │ │ │ └─ 已知未知清单: 3000 tokens │ │ │ │ → 策略: 给目标 → 模型探索 → 输出创造性但需验证 │ │ │ └─────────────────────────────────────────────────┘ │ │ │ │ ⚠ 核心转变：从"告诉模型怎么做"到"告诉模型做什么+验收标准"│ └──────────────────────────────────────────────────────────┘

Anthropic 工程师在内部测试中发现了一个反直觉的事实：保留过多的硬性规则反而干扰了 Fable 5 的决策能力。模型会绕过更优的解决方案来遵守某条规则，或者在规则之间存在冲突时产生犹豫。松绑规则不是放松质量标准，而是将"过程约束"转化为"结果标准"——不再规定"必须用 JWT"，而是规定"认证方案必须支持无状态扩展和密钥轮换"。

维度传统范式（弱模型）新范式（Fable 5）转变原因
Prompt 策略堆叠约束 + Few-shot 示例精简约束 + 上下文 + 验收标准强模型不需要手把手教
遇到模糊按"行业最佳实践"填充或报错主动提问，将未知未知转化为已知未知模型推理能力足以质疑
人机角色人=架构师，AI=执行工人人=领域专家，AI=苏格拉底式提问者AI 能自主决策和规划
验收方式人审查代码 diffAI 生成报告 + 提问人类验收AI 能自我验证基本正确性
错误处理人发现 → 修改 prompt → 重试AI 自主发现 → 提出替代方案模型具备自我纠错能力
生产数据：Claude Code 的原始系统 prompt 达到 65K tokens，其中大量是关于编码风格、文件操作规范和安全边界的硬性规则。Fable 5 发布后，Anthropic 将这些 prompt 缩减了 80%，仅保留核心目标和完成标准。结果是：代码质量不降反升，因为模型不再为了遵守某条死板的规则而绕过更优的实现方案。Fable 5 的推理能力足以自主判断正确的操作路径，不需要硬编码的底线机制。
02

发现未知项：已知/未知矩阵

新范式的核心工具是 已知/未知矩阵 （Known/Unknown Matrix），它将所有项…

新范式的核心工具是已知/未知矩阵（Known/Unknown Matrix），它将所有项目信息分为四个象限。传统编程只关注"已知的已知"（明确的需求和技术方案），而 Fable 5 范式的关键在于系统性地发现和处理其他三个象限——尤其是"未知的未知"（你甚至不知道自己不知道什么）。

┌───────────────────── 已知/未知矩阵 ─────────────────────┐ │ │ │ 已知 未知 │ │ ┌────────────────────────┬────────────────────────┐ │ │ │ │ │ │ │ │ 🟢 已知的已知 │ 🟡 已知的未知 │ │ │ │ (Known Knowns) │ (Known Unknowns) │ │ │ │ │ │ │ │ │ 明确的需求 │ 知道需要但不确定答案 │ │ │ │ 确定的技术方案 │ "这个 API 的并发限制？" │ │ │ │ 已验证的约束 │ "数据库能支撑多大QPS？" │ │ │ │ │ │ │ │ │ 处理：直接执行 │ 处理：定向调研/测试 │ │ │ │ │ │ │ │ ├────────────────────────┼────────────────────────┤ │ │ │ │ │ │ │ │ 🔵 未知的已知 │ 🔴 未知的未知 │ │ │ │ (Unknown Knowns) │ (Unknown Unknowns) │ │ │ │ │ │ │ │ │ 直觉/经验知道但未明确 │ 完全没意识到的风险/需求 │ │ │ │ "这个方案总觉得不对" │ "时区处理会导致结算错误"│ │ │ │ "这个库以前踩过坑" │ "依赖链有许可证冲突" │ │ │ │ │ │ │ │ │ 处理：显性化→验证 │ 处理：系统性扫描/探索 │ │ │ │ │ │ │ │ └────────────────────────┴────────────────────────┘ │ │ │ │ ⚠ Fable 5 的核心能力：主动扫描🔴象限并向人类提问 │ └────────────────────────────────────────────────────────────┘

Fable 5 最革命性的能力不是"更好地执行指令"，而是"发现你不知道自己不知道什么"。在传统模式下，如果开发者没有提到时区处理，模型会默认使用 UTC 或服务器本地时间——这在 99% 的情况下工作正常，但那 1% 可能导致跨国金融系统的结算金额错误。Fable 5 会主动提出："这个系统需要处理多个时区的交易吗？如果是，日切时间和结算汇率的时点如何确定？"

象限典型内容发现方法处理策略Fable 5 的作用
已知的已知明确的功能需求、技术栈需求文档直接实现高效执行
已知的未知性能指标、兼容性边界开发者明确提问定向调研/基准测试快速搜索和原型验证
未知的已知直觉性的"不对劲"经验反思显性化后验证帮助开发者梳理直觉
未知的未知隐性依赖、边界条件系统性扫描探索 + 原型测试主动发现并提问
实践案例：Thariq 在使用 Claude Code 编辑 Fable 5 的过程中，让模型扫描项目的"未知未知"。Fable 5 在执行视频编辑任务时主动发现了色彩校正领域的知识盲区，Thariq 因此在学习色彩知识的同时完善了项目需求。这个过程展示了一个关键的模式转变：AI 不再是被动执行指令的工具，而是主动帮助开发者发现知识盲区的合作伙伴。
03

重心迁移：从编码到问题定义/验收/解释

Fable 5 范式带来的最深刻变化是 开发者工作重心的迁移

Fable 5 范式带来的最深刻变化是开发者工作重心的迁移。传统开发中，80% 的时间花在编码和调试上；新范式下，编码被 AI 承担，开发者的时间重心转移到四个更高价值的活动：问题定义（定义"做什么"）、约束澄清（明确"不能做什么"）、结果验收（判断"做得对不对"）、系统解释（向利益相关方说明"为什么这样做"）。

这种重心迁移并不意味着开发者不需要懂代码——恰恰相反，它要求开发者具备更强的代码理解能力。区别在于：传统开发者主要写代码，新范式开发者主要读代码和判断代码。写代码的时间减少了，但读代码（审查 AI 输出）和判断代码（评估架构合理性）的时间大幅增加。

Stack Overflow 2025 年开发者调查的一个有趣发现印证了这种转变：84% 的开发者使用或计划使用 AI 工具，但对 AI 的正面评价持续下降，不信任感在上升。这种"用得越多、信任越低"的现象恰恰说明：经验丰富的开发者在使用 AI 的过程中越来越清晰地认识到 AI 的局限——它能快速生成代码，但需要更多的人工审查来保证质量。这进一步证明了开发者工作重心向"审查和判断"迁移的必然性。

活动传统模式占比新范式占比核心技能变化

约束澄清3-5%15-20%从"默认约束"到"显式化所有约束"

调试15-25%5-10%从"手动调试"到"指导 AI 调试"

重心迁移的经济学逻辑：在传统模式下，编码是瓶颈（占 60% 时间），所以效率提升集中在编码加速上。但当 AI 解决了编码瓶颈后，新的瓶颈转移到了"定义"和"验收"——如果问题定义不清（给 AI 错误的方向），或者验收不严格（让 AI 的错误输出流入生产），编码再快也没有意义。这就是为什么 Fable 5 范式要求开发者在"编码之外"的能力上投入更多。

04

开发者四重新定位

开发者需要从模糊的业务需求中提炼出精确的、可执行的技术问题

4.1 问题定义专家

开发者需要从模糊的业务需求中提炼出精确的、可执行的技术问题。这不仅仅是"理解需求"，更是"发现需求中未说出口的部分"。当业务方说"做一个用户认证系统"时，问题定义专家需要追问：认证失败后的用户体验是什么？需要支持哪些合规标准？历史用户如何平滑迁移？

4.2 约束澄清者

将隐性约束显式化，将模糊约束量化。"系统要快"不是约束——"P99 延迟 < 200ms，在 1000 QPS 下"才是约束。"代码要安全"不是约束——"密码使用 Argon2id 加密，会话使用 HttpOnly+Secure Cookie"才是约束。Fable 5 需要精确的约束来做出正确的决策。

4.3 结果验收官

AI 生成的代码通过了单元测试不代表它就是正确的。结果验收需要从多个维度评估：功能正确性、性能指标、安全合规、架构一致性、可维护性、与现有系统的兼容性。验收官的核心能力是"看出 AI 代码中隐藏的假设"——这些假设在测试环境中不触发，但在生产环境中可能导致事故。

4.4 系统解释者

当 AI 生成了复杂的架构方案时，开发者需要向非技术的利益相关方（产品经理、管理层、客户）解释：为什么选择这个方案？它的风险和权衡是什么？如果出问题如何回滚？这种"翻译"能力在 AI 时代变得更加重要，因为 AI 的输出往往技术性强、缺乏业务语境。

┌────────────────── 开发者四重新定位 ──────────────────┐ │ │ │ ┌────────────────────────────────────────────────┐ │ │ │ 问题定义专家 (Problem Definer) │ │ │ │ "我们要解决什么问题？问题的边界在哪里？" │ │ │ │ 技能：需求挖掘、领域知识、提问能力 │ │ │ └────────────────────────┬───────────────────────┘ │ │ │ │ │ ┌────────────────────────▼───────────────────────┐ │ │ │ 约束澄清者 (Constraint Clarifier) │ │ │ │ "哪些条件是不可违反的？性能/安全/合规底线？" │ │ │ │ 技能：系统思维、安全审计、合规知识 │ │ │ └────────────────────────┬───────────────────────┘ │ │ │ │ │ ┌────────────────────────▼───────────────────────┐ │ │ │ 结果验收官 (Result Validator) │ │ │ │ "AI 的输出真的正确吗？隐藏了什么假设？" │ │ │ │ 技能：代码审查、测试设计、风险评估 │ │ │ └────────────────────────┬───────────────────────┘ │ │ │ │ │ ┌────────────────────────▼───────────────────────┐ │ │ │ 系统解释者 (System Explainer) │ │ │ │ "为什么这样做？风险和权衡是什么？" │ │ │ │ 技能：技术写作、利益相关方沟通、风险量化 │ │ │ └────────────────────────────────────────────────┘ │ └────────────────────────────────────────────────────────┘

四重新定位不是四个独立的角色，而是同一个开发者在不同阶段切换的四种"工作模式"。一个典型的 Fable 5 工作循环：① 以问题定义专家身份定义任务目标和边界 → ② 以约束澄清者身份将隐性约束显式化写入 CLAUDE.md → ③ 让 Fable 5 探索和实现 → ④ 以结果验收官身份多维度审查 AI 输出 → ⑤ 以系统解释者身份向团队汇报方案和决策理由。

05

六项实践指南

不同能力的模型需要不同程度的"脚手架"

5.1 动态规则管理

不同能力的模型需要不同程度的"脚手架"。弱模型（如早期的 GPT-3.5）需要详尽的规则和 Few-shot 示例来保证输出质量；强模型（如 Fable 5）则需要更少的规则、更大的探索空间。动态规则管理的核心是：根据模型能力动态调整约束密度。

5.2 未知项矩阵工作流

在项目启动时，系统性地填充已知/未知矩阵的四个象限。特别关注"未知的未知"象限——通过让 AI 扫描代码库、检查依赖关系、分析历史 Bug 模式来发现潜在盲区。每次发现新的"未知"后，将其分类为"已知未知"（需要调研）或"已解决"（已验证）。

5.3 工作流改造

传统的"需求 → 设计 → 编码 → 测试"瀑布流程需要改造为"盲区检查 → 原型+笔记 → 验收清单"的探索式流程。核心变化：在编码前先做盲区检查（发现未知），编码过程中维护原型和设计笔记（而非完整文档），完成后按预定义的验收清单逐项检查。

5.4 成本革新

Fable 5 的强大能力使得"多路线并行探索"变得经济可行。传统模式下，因为编码成本高，团队通常只选择一条技术路线深入；新范式下，AI 可以快速生成 3-5 条不同路线的原型，团队在充分对比后选择最优方案。Anthropic 的实践表明，这种方式可以将探索阶段的成本降低 80%。

5.5 渐进落地

不要试图一次性改变所有工作流程。推荐从 1-2 个高价值动作开始：① 在下一个项目中引入已知/未知矩阵；② 让 AI 在项目启动时做一次盲区扫描。验证效果后再逐步扩展到更多工作流环节。

5.6 Fable 契约

每次与 Fable 5 的重要协作都应该从一份"契约"开始。契约包含七个要素：目标（完成时应该存在什么）、领域（相关的代码库/产品区域/约束）、家规（无论如何都必须遵守的不变量）、完成标准（什么可观测证据证明工作足够好）、未知项（在计划可信之前 Fable 需要发现什么）、权限（Fable 可以自行决定什么）、审查（谁或什么在信任之前攻击结果）。

新范式的正确实践：
  • 项目开始时系统性地填充已知/未知矩阵
  • 将约束从"过程规则"转为"结果标准"
  • 让 AI 先做盲区扫描再开始编码
  • 为每次重要任务定义 Fable 契约
  • 多路线并行探索，对比后选最优
  • 从 1-2 个高价值动作开始渐进落地
新范式的常见误区：
  • 继续用 65K token 的系统 prompt 约束 Fable 5
  • 假设"模型够聪明所以不需要审查"
  • 不做未知项扫描就急于编码

"先探索再收敛"的核心理念是： 探索成本 已经被 AI 大幅降低，但 决策错误的成本 没有变…

"先探索再收敛"的核心理念是：探索成本已经被 AI 大幅降低，但决策错误的成本没有变（甚至更高，因为系统更复杂）。所以最优策略不是"快速确定方案然后执行"，而是"快速生成多个方案、充分对比、然后选择最优方案执行"。Fable 5 可以在几分钟内生成 3-5 个不同技术路线的原型，这在传统开发模式下需要数天甚至数周。

实践案例：从 Command & Conquer 到 sqlite-utils

2026 年 7 月的两个公开案例完美展示了 Fable 5 新范式在实际项目中的应用

2026 年 7 月的两个公开案例完美展示了 Fable 5 新范式在实际项目中的应用。它们不是玩具 demo，而是真实世界的复杂软件工程任务——需要理解旧代码、跨平台迁移、处理遗留系统假设、运行测试、修复 Bug。

案例一：Command & Conquer 跨平台移植

Google AI Studio 产品负责人使用 Claude Code + Fable 5 将 2003 年的 PC 游戏 Command & Conquer: Generals Zero Hour 移植到 iPhone 和 iPad。这个任务的特点：

  • 从一个旧的实时策略引擎开始，不是从零创建
  • 编译原生 ARM64 构建用于 Apple 设备
  • 处理游戏资源、触控界面适配、图形 API 差异
  • 将旧 Windows PC 时代的图形假设桥接到 Apple 平台

这个案例展示了新范式的核心价值：AI 不是在做一个"prompt-to-app"的简单生成，而是在一个复杂的遗留系统中做"读取、补丁、运行、观察、恢复"的循环工作。这正是 Fable 5 擅长的工作类型——长周期、高复杂度、需要持续探索和自主决策的任务。开发者负责定义目标和平台约束，Fable 5 负责探索实现路径。

案例二：sqlite-utils 发布工程

Simon Willison 使用 Claude Fable 将成熟的开源项目 sqlite-utils 推向 4.0 稳定版。Agent 在这个过程中：

  • 发现了发布阻塞问题，包括一个关键的 delete_where() 未提交事务的 Bug
  • 在多个文件上进行了数十次 commit
  • 工作结果由另一个模型进行了额外审查
关键洞察：这两个案例的共同点是：AI 没有替代维护者，而是给了一个谨慎的维护者更大的视野、更多的耐心、和额外的审查通道。这就是新范式的本质——不是"AI 替代人"，而是"AI 增强了人的能力边界"。NxCode 的分析将此总结为：Agentic Coding 已经从"代码生成"进入"发布工程"阶段——在一个已有的仓库中工作、尊重现有架构、运行人类会运行的检查、解释为什么一个变更是安全的。

一个实用的判断标准：如果你的团队目前仍然在用"65K token 系统 prompt + 详细 Few-shot"的传统模式，而且感觉 AI 的输出"听话但缺乏创造力"，那就是时候尝试新范式了。相反，如果你的项目有严格的安全合规要求（如 PCI DSS、HIPAA），在采用新范式前需要额外设计合规审查层——不能因为"释放模型"而放松安全底线。

新范式的长期展望

Fable 5 范式只是起点而非终点。随着模型能力的持续提升，我们可以预见以下趋势：

  • 系统 prompt 将进一步精简（可能从现在的 13K 缩减到 5K 以下），模型将更多依赖自身的推理能力而非外部约束
  • 未知扫描将从"被动发现"转向"主动预防"——模型能在代码编写阶段就预测潜在的盲区
  • 多路线并行探索将成为标准工作流的一部分，AI 将自动管理多个方案的对比评估

但无论模型如何进步，开发者的四重新定位——问题定义、约束澄清、结果验收、系统解释——仍将是不可替代的核心价值。

终极洞察：AI 编程新范式的本质不是"用更聪明的模型"，而是"重新定义人与模型的关系"。从"人指导机器"到"人与机器协作探索"，从"约束模型行为"到"释放模型能力并管理输出质量"。这个转变的深层含义是：软件开发正在从"手工编码时代"进入"人机共创时代"——在这个时代，最有价值的不是能写代码的人，也不是能生成代码的 AI，而是能让人和 AI 高效协作的工作流设计者。

Q&A（7 题）

最后一个行动建议：不要试图理解所有内容后再行动
Fable 5 缩减 80% 的系统 prompt 后，如何保证代码质量和安全性？
安全性保障从"prompt 约束"转移到了三层防线：① 模型自身的安全对齐训练——Fable 5 在训练阶段就被强化了对安全边界的认知，不需要 prompt 中的显式规则来提醒；② 外部安全分类器——Anthropic 为 Fable 5 部署了实时安全分类器，当请求接近高风险领域（网络安全、生物安全）时自动降级到 Opus 4.8；③ 人类审查——最终的代码审查和安全审计仍然由人类工程师完成。三层防线的组合使得即使 prompt 大幅精简，安全性仍然有保障。
"已知/未知矩阵"在实践中如何操作？有具体的工具或流程吗？
操作流程分三步：① 项目启动时，让 Fable 5 扫描项目 codebase 并列出它认为的"未知项"——模型会基于代码结构、依赖关系、配置文件等发现潜在盲区；② 将发现的未知项分类到矩阵的四个象限中，为每个"已知的未知"和"未知的未知"指定处理策略（调研、测试、或标记为"接受风险"）；③ 在开发过程中持续更新矩阵——每解决一个未知项就标记为"已解决"，每发现新的未知就添加到矩阵。实用工具：可以用 CLAUDE.md 中的 Unknowns 章节维护这个矩阵，让 Fable 5 在每次会话开始时自动回顾。
"重心迁移"意味着开发者不需要会写代码了吗？
恰恰相反——新范式对代码理解能力的要求更高了。区别在于：传统开发者 60% 的时间在"写"代码，新范式开发者 60% 的时间在"读"代码和"判断"代码。读代码比写代码更难——你需要在 AI 生成的 500 行代码中快速识别：哪些假设是隐含的、哪些边界条件没有被覆盖、哪些设计决策可能在未来成为技术债务。如果不懂代码，你就无法做有效的验收——你只能看到"代码通过了测试"，但看不出"代码在并发场景下会死锁"。
多路线并行探索会不会导致"分析瘫痪"（永远在探索不做决策）？
会的，如果不设置明确的收敛机制。解决方案是"时间盒"（Time Box）策略：① 为探索阶段设定硬性的时间上限（如 2 天），到期后必须做出决策；② 预先定义决策标准（如"满足 P99 < 200ms 且不需要外部依赖的方案优先"）；③ 用"可逆性"作为决策权重——优先选择可逆的方案（容易切换到其他方案），降低决策错误的代价。Fable 5 的 Fable 契约中的"Done Bar"（完成标准）就是为了防止无限探索而设计的。
新范式适合所有类型的开发团队吗？小团队也能用吗？
核心原则适合所有团队，但实施粒度需要调整。小团队（3-5 人）的实践建议：① 已知/未知矩阵可以简化为一个"风险清单"（列出 top 5 未知项）；② 多路线探索可以简化为"2 条路线对比"（而非 5 条）；③ 四重新定位可以由同一个人承担（小团队中开发者本来就是全栈角色）。大团队的额外需求：需要专门的"验收官"角色、需要标准化的 Fable 契约模板、需要跨团队的未知项知识库。核心不变的是：任何团队都应该从"约束驱动"转向"探索驱动"。
Fable 5 的"未知扫描"能力是不是只适合新项目？老项目也能用吗？
老项目反而更需要未知扫描，因为老项目的"未知的未知"更多——随着系统演化，大量隐性约束和历史包袱已经没有人记得来源。实践方法：让 Fable 5 扫描现有 codebase，重点关注：① 依赖版本锁定（为什么某个库的版本被锁死？）；② 奇怪的代码模式（为什么这个函数有一段看似多余的重试逻辑？）；③ 配置中的硬编码值（为什么超时设置为 3 秒？）。Fable 5 的考古能力（code archaeology）在老项目中特别有价值——它能从 Git 历史和代码注释中挖掘出被遗忘的决策背景。
如何将 Fable 5 范式渐进地引入现有团队？
推荐的渐进路径（3 个月）：① 第 1 周——在一个低风险项目中试用已知/未知矩阵，让团队体验"发现未知"的价值；② 第 2-4 周——在下一个项目中使用 Fable 契约，定义目标、约束和验收标准，让 AI 做探索式开发；③ 第 5-8 周——引入多路线并行探索，在一个技术选型决策中尝试 3 条路线对比；④ 第 9-12 周——基于前三阶段的经验，定制适合团队的 Fable 工作流模板。关键原则：每个阶段都先小范围验证、收集反馈、调整后再推广。不要强制全团队同时切换——让早期采用者成为内部倡导者。
总结：Fable 5 范式不是"更好的 prompt 技巧"，而是 AI 编程的根本性范式转变。核心从"约束模型"转向"释放模型 + 管理未知"。四大理念——松绑规则、发现未知项、重心迁移、边界探索——共同构成了一个新的开发者工作方式。六项实践——动态规则管理、未知项矩阵、工作流改造、成本革新、渐进落地、Fable 契约——提供了具体的操作路径。最关键的心智转变：开发者的价值不再体现在"能写多少代码"，而体现在"能发现多少未知、能定义多精确的约束、能做多准确的验收判断"。代码只是手段，判断才是核心。

最后一个行动建议：不要试图理解所有内容后再行动。选择本文中的一个实践（推荐"未知项矩阵"），在下一次使用 AI 编程时尝试它。让 AI 扫描你的项目并列出它发现的"未知项"，看看它是否能发现你没有意识到的盲区。这个简单的动作，就是踏入新范式的第一步。
