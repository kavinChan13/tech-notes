深度学习张量核心讲解

Tensor Fundamentals — 多维数组本质 / Shape+Stride+Storage / reshape vs transpose / 内存连续性

Transformer 阅读 ~15 min 9 章
00

概览

深度学习中的张量不是数学里的"张量"——它只是一个带元信息的多维数组

深度学习中的张量不是数学里的"张量"——它只是一个带元信息的多维数组。真正理解张量，不是记住它有几个维度，而是理解 Storage、Shape、Stride 三件套如何协作，让"零拷贝"操作成为可能。

01

张量的本质：多维数组 + 元信息

标量是 0 维数组，向量是 1 维数组，矩阵是 2 维数组，张量是 N 维数组

标量是 0 维数组，向量是 1 维数组，矩阵是 2 维数组，张量是 N 维数组。深度学习框架中的"张量"就是这个统一概念的泛化。

在 PyTorch 中，一个Tensor 由五个部分组成：

组成部分含义类比
Storage底层连续的一维字节数组，存放实际数据仓库里的货架
dtype元素的数据类型（float32、int64 等）货物的规格标签
Shape每个维度的元素数量清单上的行列规则
Stride每个维度上跳到下一个元素需要跨过的步数从当前箱走到下一箱跨几格
Offset张量数据在 Storage 中的起始位置从第几号货架开始取货
核心认知：多个张量可以共享同一个 Storage。当你对一个张量做 reshape 或 view 时，新张量只是换了一份 Shape/Stride 元信息，底层数据纹丝不动。这是 PyTorch 实现"零拷贝"操作的基础，也是理解后续所有操作的关键。

从标量到高阶张量的维度递进

从标量到高阶张量的维度递进：

类型维度shape示例
标量 Scalar0 维()单个数值：42
向量 Vector1 维(5,)[1, 2, 3, 4, 5]
矩阵 Matrix2 维(3, 4)3 行 × 4 列的表格

⚡ 深度学习中常见维度：

维度数量不影响张量的"本质"——它们都是连续内存 + 多维索引规则。一个 shape=(24,) 的向量和 shape=(2,3,4) 的三阶张量可能指向完全相同的 Storage，只是读取方式不同。

02

Storage + Shape + Stride：内存布局三角关系

Stride 是一个元组，长度等于张量的维度数

Stride 的精确含义

Stride 是一个元组，长度等于张量的维度数。对于 shape=(D₀, D₁, ..., Dₙ) 的张量，Stride 的计算公式为：

stride[i] = ∏(Dⱼ) (j 从 i+1 到 n-1)

例：shape = (2, 3, 4)
stride[0] = 3 × 4 = 12
stride[1] = 4
stride[2] = 1
→ stride = (12, 4, 1)
张量 Shape元素总数Stride内存布局说明
(12,)12(1,)连续一维，步长 1
(3, 4)12(4, 1)行优先：跨一行跳 4 格，同行内跳 1 格
(2, 3, 4)24(12, 4, 1)跨"页面"跳 12，跨行跳 4，同行跳 1
(2, 3, 4) 转置后 (4, 3, 2)24(1, 4, 12)维度顺序反转，步长也反转
(6, 4)24(4, 1)与 (2,3,4) 共享 Storage，重新分组

元素寻址公式

给定张量的 shape 和 stride，任意元素 [i₀, i₁, ..., iₙ] 在 Storage 中的偏移量为：

offset = storage_offset + i₀ × stride[0] + i₁ × stride[1] + ... + iₙ × stride[n]

例：shape=(2,3,4), stride=(12,4,1), storage_offset=0
元素 [1, 2, 3] 的偏移 = 0 + 1×12 + 2×4 + 3×1 = 23

Stride 的设计精妙之处在于：通过改变步长而非移动数据，就能让同一块内存呈现完全不同的"逻辑视图"。这是 transpose、切片、reshape 等操作能实现零拷贝的根本原因。

03

核心操作：reshape vs transpose vs contiguous

reshape 改 Shape 和 Stride，不动数据

reshape 改 Shape 和 Stride，不动数据；transpose 只改 Stride 的顺序，不动数据；contiguous 则是"兜底方案"——当数据在内存中不连续时，强制复制一份连续副本。

操作对比一览

操作是否拷贝数据修改什么何时失败典型用途
reshape尽量不拷贝（内部先尝试 view，不行才拷贝）Shape + Stride元素总数不匹配时改变张量的维度组织方式
view永不拷贝Shape + Stride非连续张量上调用会报错零开销变形（要求连续）
transpose永不拷贝仅 Stride（交换维度顺序）不会失败转置矩阵、交换维度
permute永不拷贝仅 Stride（任意维度重排）不会失败图像格式转换 BCHW→BHWC
contiguous不连续时拷贝，连续时不拷贝重新排列 Storage不会失败为 view 等操作铺路

reshape 的运作机制

import torch
x = torch.arange(24)          # shape=(24,), stride=(1,)
y = x.reshape(2, 3, 4)        # shape=(2,3,4), stride=(12,4,1)
# 同一块内存，只是重新组织成 2×3×4
print(x.data_ptr() == y.data_ptr())  # True（共享 Storage）

z = y.reshape(6, 4)           # shape=(6,4), stride=(4,1)
# 仍然是同一块内存，6×4 的视图

transpose 的 Stride 变化

m = torch.arange(12).reshape(3, 4)  # shape=(3,4), stride=(4,1)
t = m.transpose(0, 1)               # shape=(4,3), stride=(1,4)
# stride 从 (4,1) 变成 (1,4)：行方向步长变 1，列方向步长变 4
# 数据没动，只是"读取方向"转了 90°

print(t.is_contiguous())  # False！步长不再是 row-major 顺序
PyTorch 2026 年 PR #184957 的重要改动：官方代码库中将 .contiguous().view(shape) 替换为 .reshape(shape)，因为 reshape 只在需要时才拷贝，而 contiguous().view() 总是拷贝。这验证了 reshape 作为"智能变形"操作的最佳实践地位。

04

内存连续性：为什么 contiguous 如此重要

一个张量是 contiguous （连续）的，当且仅当它的元素在 Storage 中的排列顺…

连续性的精确判定

一个张量是contiguous（连续）的，当且仅当它的元素在 Storage 中的排列顺序与"行优先"（row-major）遍历顺序一致。数学条件为：

对于 shape = (d₀, d₁, ..., dₙ) 的张量：
contiguous ⟺ stride[i] = ∏(dⱼ) (j 从 i+1 到 n-1)

即：stride[n-1] = 1
stride[n-2] = d[n-1]
stride[n-3] = d[n-1] × d[n-2]
...以此类推
张量状态ShapeStride连续？原因
新建张量(3, 4)(4, 1)✅ 连续stride[1]=1, stride[0]=4=d[1]
reshape 后(2, 6)(6, 1)✅ 连续stride 符合行优先规则
transpose 后(4, 3)(1, 4)❌ 非连续stride[0]=1 ≠ d[1]=3
切片后 [:2, :](2, 4)(4, 1)✅ 连续行方向切片不影响连续性
切片后 [:, ::2](3, 2)(4, 2)❌ 非连续stride[1]=2 ≠ 1
contiguous 后(4, 3)(3, 1)✅ 连续数据被复制到新 Storage

非连续性导致的常见问题

正确做法：

  • transpose 后使用 .reshape()（自动处理非连续）
  • 需要 view 时先调用 .contiguous()
  • 对非连续张量使用 reshape 而非 view
  • 在训练循环中避免不必要的 contiguous() 调用

常见错误：

  • transpose 后直接调用 .view() → RuntimeError
  • 盲目在每个张量后加 .contiguous() → 性能损耗
  • 认为 reshape 永远不会拷贝数据
  • 混淆 permute 和 reshape 的用途

GPU 上的性能影响

在 NVIDIA A100 GPU 上，连续张量的矩阵乘法吞吐量约为 312 TFLOPS（FP16），而非连续张量需要先做内存重排再计算，额外引入 15-30% 的延迟。在大规模训练中（如 GPT-3 的 1750 亿参数），这意味着数小时的额外计算时间。PyTorch 的 channels_last 内存格式就是为了让卷积操作在 GPU 上保持最优内存对齐而设计的。

连续性不只是"能不能算"的问题，更是"算得快不快"的问题。GPU 的 SIMD 架构和缓存机制天然偏好连续内存访问，非连续张量会破坏缓存预取，导致大量缓存未命中。

切片的本质是"只修改 offset 和 stride，不拷贝数据"

切片的本质是"只修改 offset 和 stride，不拷贝数据"。切片得到的新张量与原张量共享同一块 Storage，但只"看到"其中一部分。

认知误区澄清与 PyTorch 实战

import torch # 1

数学张量 ≠ 深度学习张量

维度数学张量深度学习张量
定义满足特定坐标变换规则的多线性映射多维数组 + 自动微分支持

PyTorch 实战演练

import torch
# 1. 创建 + 变形
x = torch.arange(24)                    # shape=(24,)
y = x.reshape(2, 3, 4)                  # shape=(2,3,4)
print(y.stride())                       # (12, 4, 1)

# 2. 转置 → stride 变化 → 非连续
z = y.transpose(0, 2)                   # shape=(4,3,2)
print(z.stride())                       # (1, 4, 12)
print(z.is_contiguous())                # False

# 3. view 会报错，用 contiguous 修复或直接用 reshape
# z.view(-1)                            # RuntimeError!
z_flat = z.contiguous().view(-1)        # OK，先拷贝再变形
z_flat2 = z.reshape(-1)                 # OK，reshape 内部自动处理

当你理解了"transpose 只改 stride，reshape 改 shape+stride，view 要求连续"这三条规则，PyTorch 中 90% 的 shape 相关 bug 都能迎刃而解。

Shape 调试实用技巧

在实际开发中，shape 相关的 bug 往往难以定位——报错信息只说"expected shape X but got Y"，却不告诉你问题出在哪一步。以下是几个高效的调试方法：

调试黄金法则：当遇到 shape 不匹配的 RuntimeError 时，在报错位置的前 5 行代码中，逐行插入 print(tensor.shape, tensor.stride())。90% 的情况下，问题出在某个 transpose 或 permute 之后忘记调用 contiguous 或 reshape。

框架设计启示：为什么这样设计

Storage + Shape + Stride 的设计不是偶然——它用最小的元信息开销，实…

Storage + Shape + Stride 的设计不是偶然——它用最小的元信息开销，实现了最大程度的操作灵活性。这是"空间换时间"与"时间换空间"之间精妙平衡的典范。

三大设计优势

设计优势实现机制收益
内存共享多个张量指向同一 Storagereshape/view/切片零拷贝，内存使用减少 50-80%
灵活索引Stride + Offset 组合切片只修改 offset，步长切片只修改 stride
惰性求值操作只修改元信息延迟到真正需要连续数据时才拷贝

PyTorch 张量操作决策——按你的目的选算子：

改变形状（元素数不变）

  • 连续 →view()（零拷贝）
  • 不连续、可拷贝 →reshape()（智能选择）
  • 不连续、不拷贝 →contiguous() 再 view()

转置 / 交换维度

  • transpose() / permute()永远零拷贝
  • 后续要 view →先加 contiguous()

取一部分数据

  • 切片 x[a:b, c:d]零拷贝，共享 Storage
  • 要独立副本 →加 clone()

发 GPU / 矩阵乘法

  • 确保 contiguous()GPU 要求连续内存对齐

理解了 PyTorch 的张量内部结构，你就掌握了"为什么有些操作快、有些操作慢"的根本原因。这不仅是使用框架的知识，更是理解高性能计算系统设计的窗口。

Q&A（8 题）

reshape 和 view 的区别是什么？什么时候用哪个？
view 永远不拷贝数据，它要求张量在内存中是连续的（contiguous），只修改 Shape 和 Stride 元信息。reshape 是"智能版 view"：它先尝试像 view 一样零拷贝操作，如果张量不连续（例如 transpose 之后），就自动做一次 contiguous 拷贝再变形。实际开发中，如果你确定张量是连续的且追求极致性能，用 view；否则用 reshape 更安全。PyTorch 官方在 2026 年的 PR #184957 中明确推荐用 reshape 替代 contiguous().view() 的写法。
为什么 transpose 之后调用 view 会报错？
因为 transpose 只修改了 Stride（交换维度对应的步长），没有移动数据，导致张量在内存中不再连续。例如 shape=(3,4) stride=(4,1) 的张量 transpose 后变为 shape=(4,3) stride=(1,4)——行步长变成 1，列步长变成 4，这不符合 row-major 的连续排列规则。view 要求数据在内存中连续排列，无法从非连续的 stride 中构建出正确的一维视图，因此抛出 RuntimeError。解决方法是先调用 .contiguous() 让数据重新排列，再调用 view；或者直接用 reshape 代替 view。
Stride 到底是什么？它怎么影响张量操作？
Stride 是一个元组，表示在每个维度上跳到下一个元素需要跨过的内存步数。例如 shape=(2,3,4) 的张量 stride=(12,4,1)：在维度 0 上跳一步跨 12 个元素（即整个 3×4 的"页面"），在维度 1 上跳一步跨 4 个元素（即一整行），在维度 2 上跳一步跨 1 个元素（即相邻元素）。transpose 通过交换 stride 的维度顺序来改变"读取方向"而不移动数据；切片通过修改 stride 的数值来实现跳步读取。理解 stride 是理解所有张量操作的关键。
多个张量共享同一个 Storage 有什么风险？
最大风险是"意外修改"。reshape、view、transpose、切片等操作产生的新张量与原张量共享同一块内存，修改任何一个都会影响其他所有视图。例如 x = torch.arange(12).reshape(3,4)，然后 y = x[1:]，修改 y[0,0] = 99 会导致 x[1,0] 也变成 99。在训练过程中，这种隐式共享可能导致难以排查的梯度错误。当需要独立副本时，务必使用 .clone()。另一个风险是序列化：共享 storage 的张量在保存和加载时可能产生意外的文件大小或数据一致性问题。
contiguous() 会引入多大的性能开销？
取决于张量大小和调用频率。对于一个小张量（如 1000 个 float32），contiguous 的开销可忽略（<1μs）。但对于大张量（如 shape=(32, 512, 768) 的注意力矩阵，约 48MB），一次 contiguous 调用需要完整拷贝 48MB 数据，在 GPU 上约 2-5μs（HBM 带宽 ~2TB/s）。问题出在训练循环中：如果每次前向传播都调用 10 次不必要的 contiguous，100 万个 batch 就是 1000 万次额外拷贝，累计增加数分钟训练时间。最佳实践是：只在"一次性开销换长期加速"的场景（如 Attention 分头、图像格式转换）调用 contiguous，不要在循环中反复调用。
深度学习中的张量和数学中的张量有什么不同？
核心区别在于"规则"。数学中的张量是一个多线性映射，必须满足严格的坐标变换规则——在不同坐标系下，张量的分量按照特定规律变换，以保持物理量的不变性（如应力张量、曲率张量）。深度学习中的"张量"只是一个多维数组，加上自动微分和 GPU 加速支持，没有任何变换规则约束。你可以随意 reshape、transpose、切片，只要元素值正确就行。这就像"正式晚宴"和"自助餐"的区别——名字都叫"吃饭"，但规矩完全不同。深度学习借用"张量"这个名字，主要是因为多维数组是张量概念的一个特例。
为什么 GPU 对内存连续性要求更高？
GPU 的架构设计决定了它偏好连续内存访问。GPU 使用 SIMD（单指令多数据）模式，一条指令同时处理多个数据元素，要求这些数据在内存中连续排列才能高效加载到共享内存和寄存器中。NVIDIA GPU 的内存事务以 128 字节为单位，如果数据不连续，一次 128 字节的读取可能只包含几个有用元素（缓存利用率低）。此外，GPU 的 L1/L2 缓存预取机制假设数据按顺序访问，非连续访问会导致大量缓存未命中。这就是为什么 PyTorch 在将张量发送到 GPU 或执行 cuBLAS 矩阵乘法时，通常要求张量是 contiguous 的。
permute 和 transpose 有什么区别？
transpose 只能交换两个维度，例如 transpose(0, 1) 交换维度 0 和 1。permute 可以任意重排所有维度，例如 permute(2, 0, 1) 把原来的维度 2 放到第 0 位、维度 0 放到第 1 位、维度 1 放到第 2 位。对于 2 维张量，transpose(0,1) 和 permute(1,0) 效果完全相同。对于 3 维以上张量，permute 更灵活。典型用例：图像处理中把 BCHW 格式转为 BHWC，需要 permute(0, 2, 3, 1)。两者都是零拷贝操作（只修改 stride），产生的张量通常是非连续的。
