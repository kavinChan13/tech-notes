概览

大模型流式传输不是一个单独的技术问题，而是一个五层递进的工程体系：从 EventSource 三行代码起步，到断线重连的数据丢失陷阱，到断点续传的三种补救方案，再到 WebSocket 双向协议替代，最终在生产级技术栈中将心跳保活、rAF 批量渲染、Markdown 分段、本地缓存兜底融合为一套完整方案。每一层都是前一层的"缺陷补丁"。
01

第一层：EventSource 基础——三行代码与六大特性

EventSource 是浏览器原生提供的 SSE（Server-Sent Events）客…

EventSource 是浏览器原生提供的 SSE（Server-Sent Events）客户端 API。它基于 HTTP 长连接，服务端单向推送文本事件流，客户端通过 onmessage 监听数据到达。2026 年 OpenAI、Anthropic、Google 等主流大模型 API 的 stream: true 模式全部基于 SSE 协议。

最小可用实现

// 三行代码跑通流式传输
const es = new EventSource('/api/chat/stream?prompt=hello');
es.onmessage = (e) => { output.textContent += e.data; };
es.addEventListener('done', () => es.close());

这三行代码完成了：建立连接 → 监听消息 → 流结束关闭。但生产环境中，这远远不够。

EventSource 六大特性与生产限制

特性行为生产环境影响
自动重连断线后约 3 秒自动重新连接看似可靠，实则丢数据（详见第二层）
仅支持 GET标准 API 不支持 POST 方法Prompt 超过 2KB 无法放 URL，需 polyfill
纯文本传输只传输 UTF-8 文本LLM 场景足够，不需要二进制
HTTP/1.1 长连接每个 EventSource 占一个 TCP 连接同域名最多 6 个并发（HTTP/2 下无此限制）
跨域 CORS支持 withCredentials 属性需服务端配置 Access-Control 头
事件类型支持 addEventListener 监听自定义事件可区分 token / done / error 等不同事件
EventSource 的"自动重连"给了开发者虚假的安全感——断了会自动连上没错，但重连后服务端会从零开始生成。你已经看了 30 秒的内容，全部丢失。这就是为什么"三行代码"在生产中不可用。

SSE 事件流格式

SSE 协议数据格式（服务端响应体）:

  event: token              ← 自定义事件类型（可选）
  id: chunk_001             ← 事件ID（可选，用于断点续传）
  retry: 3000               ← 重连间隔毫秒（可选）
  data: {"content":"你"}    ← 数据负载（必须）
                            ← 空行 = 一条事件结束
  id: chunk_002
  data: {"content":"好"}

  id: chunk_003
  data: {"content":"，"}

  event: done
  data: [DONE]              ← 流结束标记

Fetch + ReadableStream 替代方案

由于 EventSource 不支持 POST，实际生产中大量项目使用 Fetch ReadableStream 替代原生 EventSource，以获得 POST 能力和更细粒度的控制：

// Fetch + ReadableStream：支持 POST，可自定义 Header
const resp = await fetch('/api/chat', {
  method: 'POST', headers: {'Content-Type':'application/json'},
  body: JSON.stringify({ prompt, history, stream: true })
});
const reader = resp.body.getReader();
const decoder = new TextDecoder();
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  output.textContent += decoder.decode(value, { stream: true });
}
维度原生 EventSourceFetch + ReadableStream
HTTP 方法仅 GETGET / POST / PUT 全支持
自定义 Header不支持完全支持（Authorization 等）
自动重连内置需手动实现
断点续传Last-Event-ID（非强制）完全自定义
中止控制只能 close()AbortController 精确控制
适用场景简单通知流LLM 对话流（主流选择）
实践结论：2026 年实际生产中，约 70% 的 AI 对话产品使用 Fetch + ReadableStream 而非原生 EventSource。原因很简单——LLM API 的 prompt 通常远超 2KB，必须用 POST；同时需要 Authorization header 传递 API Key。原生 EventSource 更适合轻量级通知推送场景。

第二层：断线重连陷阱——已观看 30 秒内容为何丢失

EventSource 的自动重连是 LLM 流式传输中最常被忽视的"地雷"

EventSource 的自动重连是 LLM 流式传输中最常被忽视的"地雷"。断线后浏览器确实会自动重连，但重连的行为与开发者的期望完全不同。

Last-Event-ID 的局限性

SSE 规范设计了 Last-Event-ID 机制：客户端断线重连时，自动在请求头中附带最后接收到的事件 ID。但这个机制存在严重的实际限制：

限制说明影响
非强制支持规范标注 Last-Event-ID 为"建议"而非"必须"大多数 LLM API 不实现此机制
服务端需缓存服务端必须缓存已发送的事件才能重放LLM 生成是流式的，通常不缓存
LLM 不可重现大模型每次生成结果不同（temperature > 0）即使从断点续传，内容也会不一致
仅 GET 可携带Last-Event-ID 通过 HTTP 头传递POST 场景（Fetch 方案）不触发此机制
Last-Event-ID 在传统消息队列场景（如日志推送、股票行情）中非常有效，因为服务端可以缓存消息。但在 LLM 流式场景中，服务端通常"边生成边丢弃"——它不记得已经发了哪些 token，也无法精确"从第 N 个 token 继续"。

断线频率的真实数据

网络环境断线频率典型断线时长用户影响
桌面 Wi-Fi（稳定）每 1000 次请求约 0.5 次200ms-2s偶尔闪烁
移动 4G/5G每 100 次请求约 3-8 次500ms-5s频繁中断
企业代理 / VPN每 200 次请求约 2-5 次1-10sNginx 超时切断
电梯 / 地铁 / 高铁几乎每次5-30s必须断点续传
核心矛盾：LLM 单次生成耗时 10-60 秒，而移动端断线间隔可能只有 3-5 秒。这意味着一次完整生成过程中，可能断线 3-10 次。没有断点续传机制，用户体验将是灾难级的。
03

第三层：断点续传三种方案——从"能续"到"可靠续"

断点续传 是让流式传输从"能用"到"可靠"的关键跳跃

断点续传是让流式传输从"能用"到"可靠"的关键跳跃。核心思路：客户端记录已接收进度，断线重连时告知服务端从断点继续。

方案一：接收长度续接

客户端记录已接收内容的字符数或 token 数，重连时通过 lastReceivedLength 参数告知服务端跳过前面的内容。

方案一：接收长度续接流程 Client Server | | |── POST /stream {prompt:"写一篇文章"} ──→| |←── chunk: "大模型技术" | 已接收 5 字符 |←── chunk: "正在改变" | 已接收 9 字符 | ✕✕✕ 断线 ✕✕✕ | |── POST /stream {prompt, lastLen:9} ─→| 跳过前 9 字符 |←── chunk: "世界格局" | 从第 10 字符继续 |←── chunk: "..." |
优点缺点
实现最简单大模型输出有随机性（temperature > 0 时每次不同）
客户端只需计数服务端需要"跳过前 N 字符"的能力
不需要额外存储token 和字符的映射关系不稳定
接收长度续接在 temperature=0（确定性输出）时效果尚可，但大多数 LLM 对话使用 temperature=0.7-1.0，每次生成内容不同。"跳过前 9 个字符"后接上的内容，可能和前面的逻辑完全不连贯。因此这个方案在生产中很少单独使用。

方案二：消息 ID 续接

服务端为每个发出的 chunk 分配唯一递增 ID（如 chunk_001、chunk_002），客户端记录最后收到的 ID。重连时传入 lastEventId，服务端从缓存中回放该 ID 之后的内容。

方案二：消息 ID 续接流程 Client Server（带缓存） | | |── POST /stream {prompt} ────────────→| 开始生成 + 分配 ID |←── id:chunk_001 data:"大模型" | 缓存 chunk_001 |←── id:chunk_002 data:"技术" | 缓存 chunk_002 |←── id:chunk_003 data:"正在" | 缓存 chunk_003 | ✕✕✕ 断线 ✕✕✕ | |── POST /stream {prompt,lastId:003} ─→| 从缓存回放 |←── id:chunk_003 data:"正在" (重放) | 先重放已缓存的 |←── id:chunk_004 data:"改变世界" | 然后继续新生成 |←── id:chunk_005 data:"..." |
优点缺点
精确断点续传，不丢不错服务端必须缓存已发出的 chunk（内存开销）
支持去重（相同 ID 直接跳过）需要管理缓存生命周期（生成完成后释放）
与 SSE Last-Event-ID 规范兼容实现复杂度中等
消息 ID 续接是目前最成熟的方案。Anthropic 和 OpenAI 的内部实现都基于此思路——每个 chunk 携带序列号，服务端在 Redis 或内存中缓存当前会话的完整输出，直到客户端确认收到或会话超时（通常 120 秒）。

方案三：客户端缓存 + resume_token

客户端将已接收的内容存入 localStorage 或 IndexedDB，配合服务端返回的 resume_token（会话恢复令牌），断线后完全由客户端恢复，无需服务端回放。

方案三：客户端缓存续传流程 Client (localStorage) Server | | |── POST /stream {prompt} ────────────→| |←── resume_token:"sess_abc123" | 生成会话令牌 |←── chunk:"大模型技术" | → 存入 localStorage |←── chunk:"正在改变" | → 追加到 localStorage | ✕✕✕ 断线 ✕✕✕ | | (从 localStorage 恢复已显示内容) | |── POST /stream {resume:"sess_abc123"}→| 识别会话，继续生成 |←── chunk:"世界格局" | → 追加到 localStorage |←── [DONE] | → 清除 localStorage
优点缺点
断线瞬间用户体验无损（已读内容不消失）需要管理 localStorage 容量和过期
服务端压力小（无需长期缓存）resume_token 需要安全的生成和验证机制
适合移动端弱网环境多标签页需要同步 localStorage 状态

三种方案综合对比

维度接收长度续接消息 ID 续接客户端缓存
实现复杂度低中中高
数据一致性差（随机输出时断裂）优（精确回放）良（客户端保证显示连续）
服务端开销极低中（需缓存）低（仅 token 验证）
断线瞬间体验内容可能跳变短暂空白后恢复无缝过渡
适用场景原型/Demo通用生产环境移动端/弱网环境
典型使用者个人项目OpenAI / Anthropic移动端 AI 应用
生产推荐：通用场景首选消息 ID 续接（方案二），移动端叠加客户端缓存（方案三）实现无缝体验。接收长度续接（方案一）仅适合 temperature=0 的确定性场景或快速原型验证。实际产品中常将方案二和方案三组合使用——服务端保证数据完整，客户端保证视觉连续。

第四层：高级协议替代——WebSocket 双向通信与 JSON-RPC

当 SSE 的单向推送无法满足需求时（中途取消生成、实时语音交互、多人协作编辑），需要升级到…

当 SSE 的单向推送无法满足需求时（中途取消生成、实时语音交互、多人协作编辑），需要升级到 WebSocket 双向通信协议。

WebSocket 在 LLM 场景的四大优势

优势说明对应场景
双向通信客户端可随时发送控制指令中途取消生成、暂停/恢复
Resume Offset客户端发送 {"resume": true, "offset": 1523} 精确续传断线后从精确字节位置恢复
低延迟无 HTTP 握手开销，帧头仅 2-6 字节语音 AI、实时协作
持久连接一次握手，长期保持多轮对话复用同一连接

WebSocket 流式传输实现

WebSocket 双向流式传输流程 Client Server | | |── WS 握手 ──────────────────────────→| |←── 101 Switching Protocols | | | |── {"action":"chat","prompt":"..."} ─→| 发送请求 |←── {"type":"token","seq":1,"data":"你"}| |←── {"type":"token","seq":2,"data":"好"}| | | |── {"action":"cancel"} ──────────────→| 中途取消！ |←── {"type":"cancelled","seq":2} | 立即停止 | | | ✕✕✕ 断线 ✕✕✕ | |── WS 重连 ──────────────────────────→| |── {"action":"resume","offset":2} ──→| 从 seq=3 继续 |←── {"type":"token","seq":3,"data":"，"}|

WebSocket 的代价与挑战

挑战说明解决成本
无自动重连WebSocket 断线后不会自动重连需实现指数退避重连逻辑
无原生消息 ID没有 Last-Event-ID 等内置机制需在应用层实现序列号
代理兼容性差企业防火墙常阻断 WS 协议升级需要 wss:// + 降级策略
心跳保活无活动连接会被中间件超时切断需实现 ping/pong 心跳
连接管理复杂需要处理重连、消息队列、状态同步代码量是 SSE 方案的 3-5 倍
WebSocket 的能力远超 SSE，但代价是"所有 SSE 免费提供的东西（自动重连、HTTP 兼容、Last-Event-ID），在 WebSocket 中都需要自己造轮子"。除非确实需要双向通信，否则 SSE 方案的总工程成本更低。

JSON-RPC over WebSocket：大厂方案

JSON-RPC 是一种轻量级远程过程调用协议，将其叠加在 WebSocket 上，可以在双向通信的基础上获得结构化的请求-响应语义。这是 Anthropic Claude 实时 API、Google Gemini Live API 等大厂产品的底层通信模式。

JSON-RPC over WebSocket 消息格式:

  // 客户端请求（带 method + params + id）
  {"jsonrpc":"2.0", "id":1, "method":"chat.generate",
   "params":{"prompt":"你好","stream":true}}

  // 服务端流式响应（带 id 关联）
  {"jsonrpc":"2.0", "id":1, "result":{"seq":1,"data":"你"}}
  {"jsonrpc":"2.0", "id":1, "result":{"seq":2,"data":"好"}}

  // 客户端中途取消
  {"jsonrpc":"2.0", "id":2, "method":"chat.cancel",
   "params":{"original_id":1}}

  // 服务端确认取消
  {"jsonrpc":"2.0", "id":2, "result":{"cancelled":true}}

厂商 / 产品协议双向需求备注
OpenAI Chat APISSE (Fetch+Stream)无（单向流）POST + stream:true
OpenAI Realtime APIWebSocket / WebRTC语音双向流音频输入+输出
Anthropic ClaudeSSE (Fetch+Stream)无（单向流）POST + stream:true

协议选型铁律：纯文本对话场景（Chat Completions）= SSE 足矣。涉及音频/视频/实时语音交互 = WebSocket。OpenAI 和 Anthropic 的标准对话 API 全部用 SSE，只有 Realtime/Voice API 才用 WebSocket。这说明 80% 的 AI 产品不需要 WebSocket。

组件一：心跳保活

服务端每 15-30 秒发送心跳事件（SSE 注释 : heartbeat\n\n），防止 Nginx / 负载均衡器因超时（默认 60s）切断空闲连接。

心跳保活时序（防止中间件超时切断）:

  t=0s   Server → Client: data: 第一个 token
  t=1s   Server → Client: data: 第二个 token
  ...
  t=15s  Server → Client: : heartbeat    ← 心跳（SSE注释格式）
  t=16s  Server → Client: data: 继续生成
  ...
  t=30s  Server → Client: : heartbeat    ← 第二次心跳
  ...

  若 Nginx proxy_read_timeout = 60s:
  没有心跳 → 第 60s 连接被切断 → 用户看到生成中断
  有心跳 → 连接持续存活 → 生成完整完成

组件二：requestAnimationFrame 批量 DOM 更新

LLM 每秒产生 20-50 个 token，如果每个 token 都触发一次 DOM 更新和 React 重渲染，浏览器主线程将被淹没。使用 requestAnimationFrame（rAF）将多个 token 合并到一帧内更新，是解决渲染风暴的核心手段。

rAF 批量更新 vs 逐 token 更新:
逐 token 更新（卡顿）: · token到达 → setState → render → DOM → paint (16ms) · token到达 → setState → render → DOM → paint (16ms) · token到达 → setState → render → DOM → paint (16ms)
每秒 50 次 render → 主线程阻塞 → 页面冻结
rAF 批量更新（流畅）: · token到达 → 存入 buffer · token到达 → 存入 buffer · token到达 → 存入 buffer · rAF 回调 → flush buffer → 一次 setState → 一次 render
每秒最多 60 次 render → 与屏幕刷新同步 → 流畅
渲染策略每秒 render 次数主线程占用用户体验
逐 token setState20-50 次高（80%+）明显卡顿
throttle 50ms固定 20 次中（40-60%）轻微延迟

requestAnimationFrame 的精妙之处在于它"不创造新的渲染"，而是"把已有的渲染对齐到屏幕刷新周期"。60Hz 屏幕每秒最多画 60 帧，rAF 确保你的 DOM 更新恰好发生在每一帧绘制之前——既不多（浪费性能）也不少（保证及时）。

组件三：实时 Markdown 分段渲染

LLM 输出通常包含 Markdown 格式（代码块、列表、表格等）。流式场景下不能等全部生成完再渲染，也不能每来一个字符就全量解析。分段策略：将文本分为"已完成块"（冻结，不重新解析）和"进行中的块"（增量解析）。

渲染策略原理性能（20KB 输出）复杂度

AST 打字机构建增量 AST，逐节点渲染O(n) — 150ms 流畅高

组件四：本地缓存兜底

即使网络层和续传层全部失效，客户端通过 localStorage 保底存储已接收内容，确保用户刷新页面后不丢失对话记录。

本地缓存兜底策略: 正常运行: token 到达 → 渲染到 DOM → 同时写入 localStorage [DONE] 到达 → 标记完成 → localStorage 可清理 断线时: localStorage 中已有内容 → 立即恢复显示 用户看到"网络中断，正在重连..." 重连成功 → 续传补全 重连失败 → 用户可选择"查看已接收内容" 页面刷新时: 检查 localStorage → 有未完成的流 → 恢复显示 用户可手动点击"重新生成"或"继续"

组件五：手动重试机制

当自动重连 3 次仍失败时，给用户一个显眼的"重试"按钮。这看似简单，但很多产品忘记做——用户在断线后只能无奈刷新整个页面。

组件六：AbortController 中止控制

用户点击"停止生成"时，使用 AbortController 中止 HTTP 请求，立即释放网络连接和服务器计算资源。这是 Fetch API 提供的原生能力，EventSource 不具备。

  • SSE 响应头加 X-Accel-Buffering: no

  • 提供手动重试按钮

08

常见问答

EventSource 和 Fetch+ReadableStream 在 LLM 场景中到底该选哪个？
生产中推荐 Fetch+ReadableStream。原因有三：(1) LLM 的 prompt 通常超过 2KB，必须用 POST，而原生 EventSource 仅支持 GET；(2) 需要 Authorization header 传 API Key，EventSource 不支持自定义 header；(3) Fetch 提供 AbortController 中止能力，可以随时取消生成。原生 EventSource 更适合简单的通知推送场景，如构建状态更新、日志流等。
为什么大模型的断点续传比普通文件下载复杂得多？
文件下载是确定性的——同一文件的第 1000 字节永远是同一个字节。但 LLM 生成是概率性的（temperature > 0），同一 prompt 每次生成结果不同。如果断线后服务端"从头重新生成"，续接的内容与前文逻辑可能不连贯。因此 LLM 断点续传的核心不是"从第 N 个字节继续下载"，而是"服务端必须记住这次生成进行到哪里了，并从那个位置精确继续"——这需要会话状态管理和 chunk 缓存机制。
心跳保活为什么不直接设一个很大的超时时间？
设 proxy_read_timeout=3600s 确实能避免超时切断，但会带来两个问题：(1) 真正的死连接（客户端已离开）会占用服务端资源长达一小时，在高并发场景下导致连接池耗尽；(2) 中间链路上的每一层（CDN、负载均衡、防火墙）都有自己的超时设置，你无法控制所有层。心跳是更好的方案——每 15-30 秒发一个小数据包，动态重置所有中间层的计时器，既保持连接活跃，又不会让死连接长期占用资源。
requestAnimationFrame 批量渲染会导致用户看到"跳跃式"输出吗？
不会。rAF 的回调频率与屏幕刷新率同步（通常 60Hz = 每 16.7ms 一帧），这意味着最多每 16.7ms 更新一次 DOM。人类视觉暂留约 50-100ms，完全无法感知 16.7ms 级别的更新间隔。实测表明，rAF 批量渲染的视觉体验与逐 token 渲染完全一致，但性能提升 3-10 倍。如果模型输出速度特别快（每秒 100+ token），可以额外叠加 throttle 将更新频率限制在每 30-50ms 一次。
WebSocket 比 SSE 先进，为什么大厂对话 API 不用它？
"先进"不等于"合适"。SSE 在对话场景中有三大不可替代优势：(1) 基于 HTTP/1.1，天然穿透企业防火墙、CDN、代理——WebSocket 需要协议升级，约 15% 的企业网络会阻断；(2) 内置自动重连和 Last-Event-ID——WebSocket 需要从零实现重连逻辑、心跳、消息队列；(3) 调试友好——SSE 是纯文本 HTTP 响应，用 curl 就能测试，WebSocket 需要专门工具。OpenAI 和 Anthropic 的选择证明：对话场景 SSE 是最佳方案，只有语音/视频实时交互才需要 WebSocket。
移动端弱网环境下的流式传输有什么特殊考虑？
移动端面临三大特殊挑战：(1) 网络切换——WiFi 到 4G 切换时 TCP 连接断开，需要快速重连（指数退避从 500ms 起步）；(2) 系统休眠——Android Doze 模式和 iOS 后台限制会冻结网络连接，恢复后需要 resume_token 续传；(3) 连接不稳定——地铁、电梯场景下可能每 3-5 秒断一次。推荐方案：SSE + 客户端 localStorage 缓存（保证断线瞬间内容不消失）+ resume_token（服务端识别会话继续生成）+ 指数退避重连（避免频繁重试加剧网络拥塞）。
如何监控生产环境中流式传输的健康状况？
需要监控五个关键指标：(1) TTFT（Time to First Token）——首 token 延迟，P50 应 < 300ms，P99 应 < 1s；(2) 断线率——每千次请求的断线次数，桌面 < 1 次，移动端 < 50 次；(3) 续传成功率——断线后成功续传的比例，应 > 99%；(4) 渲染帧率——rAF 回调频率，应稳定在 55-60 FPS；(5) 完成率——流式传输正常完成（收到 [DONE]）的比例，应 > 98%。建议在客户端埋点上报这些指标，配合 Grafana 仪表盘实时观察。
多标签页场景下 SSE 连接数耗尽怎么处理？
HTTP/1.1 下同域名最多 6 个 TCP 连接，每个 EventSource 占用一个。如果用户打开 7 个标签页，第 7 个的 SSE 请求会被浏览器排队等待。解决方案有四种：(1) 升级到 HTTP/2——多路复用共享单个 TCP 连接，理论连接数上限 100+；(2) 使用 SharedWorker——多个标签页共享同一个 Worker 中的 SSE 连接，通过 postMessage 分发数据；(3) 使用 BroadcastChannel API 在标签页间同步状态，只保持一个活跃连接；(4) 限制同域连接数，非活跃标签页降级为轮询。
