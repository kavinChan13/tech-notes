01

RAG 评估框架总览

RAG 系统的核心矛盾在于：检索环节的分块质量与噪音干扰，以及生成环节的幻觉问题

RAG 系统的核心矛盾在于：检索环节的分块质量与噪音干扰，以及生成环节的幻觉问题。评估的目的不是打分，而是定位瓶颈在哪一层。

三层评估体系

RAGAS（RAG Assessment）框架提出的核心理念：检索和生成要分开评估，才能定位瓶颈在哪一层。三层分别对应不同的问题和指标：

层次评估对象核心问题关键指标
检索层Retriever 返回的文档检索到的内容相关吗？Context Recall, Context Precision, Hit Rate
生成层LLM 生成的回答回答正确且忠实吗？Faithfulness, Answer Relevancy, Correctness
端到端整体系统用户满意吗？成本可控吗？Answer Quality, Latency, Cost/Q

评估的两种范式

范式方式优点缺点
Ground Truth 评估人工标注 QA 对 + 标准答案客观、可复现标注成本高、覆盖有限
LLM-as-Judge用 GPT-4 等强模型做裁判零成本扩展、灵活有偏差（长度偏好、位置偏差、自我偏好）
优先建立量化基准：在优化前需定义 Context Recall 和 Faithfulness 的基线值，避免盲目调整。没有评估基线的优化，等于在黑暗中开枪。
02

检索层：核心指标与意义

RAG 中 70% 的问题出在检索层（分块不对、embedding 不够好、query-do…

RAG 中 70% 的问题出在检索层（分块不对、embedding 不够好、query-doc 语义 gap），30% 出在生成层。检索质量决定了一切后续优化的上限。

六大检索指标

指标核心含义为什么重要
Recall@KTop-K 结果中包含相关文档的比例最重要：衡量"有没有召回"，RAG 中漏掉的信息无法恢复
Precision@KTop-K 中相关文档的占比衡量"噪声有多少"，噪声多会干扰 LLM
Hit RateTop-K 中至少有一个相关文档的查询比例简单直观的成功率指标
MRR第一个相关结果排名的倒数均值关注"排第几"，排名越靠前效果越好
NDCG@K归一化折损累积增益多级相关性（强相关/弱相关），更精细
Context Precision检索到的文档中对回答有用的比例（RAGAS）区分"相关"和"有用"，更贴近实际需求
为什么 RAG 中 Recall 比 Precision 更重要？LLM 能从噪声中提取有用信息，但漏掉的信息无法恢复。宁可多检索一些（高 Recall），让 LLM 过滤噪声，也不要漏掉关键文档。

K 值选择的三方博弈

Recall@K 中的 K 是核心调参旋钮，涉及三方平衡：

  • 检索质量：K 越大 Recall 越高，但 Precision 下降（噪声增多）
  • 成本：K 越大 context tokens 越多，LLM 费用线性增加
  • 生成质量：context 过长时 LLM 可能"迷失在中间"（Lost in the Middle），反而降低回答质量

实践建议：K=3~5 为起点；加 Reranker 时可设 K=20 先广召回再精选 Top-3~5。

03

生成层：质量维度与幻觉检测

Faithfulness 和 Answer Relevancy 是生成层最关键的两个指标 —…

Faithfulness 和 Answer Relevancy 是生成层最关键的两个指标 — 一个检测"是否在编造"，一个检测"是否答非所问"。

五大生成质量指标

指标定义评估方式问题场景
Faithfulness回答是否忠实于检索到的上下文将回答拆分为 claims，逐条验证是否有 context 支撑检测幻觉：编造了 context 中没有的信息
Answer Relevancy回答是否切题从回答反向生成问题，计算与原问的语义相似度检测答非所问
Correctness回答是否与标准答案一致与 ground truth 对比（语义相似度/LLM Judge）需要标注数据
Completeness回答是否覆盖了所有要点检查 ground truth 中的关键点是否都提到回答过于简略
Harmfulness回答是否包含有害/偏见内容安全分类器 / LLM Judge安全合规

Faithfulness vs Correctness：两个不同维度

一个回答可以 faithful 但 incorrect（context 本身是错的），也可以 correct 但不 faithful（碰巧答对但编造了理由）。Faithfulness 检测"是否编造"，Correctness 检测"是否正确"，两者独立。

Faithfulness = 有支撑的陈述数 / 总陈述数

计算步骤：①将回答拆分为独立陈述（claims）；②逐条检查每个陈述是否能从 context 中找到支撑；③取比例。例如回答"LangChain 支持 OpenAI 和 Anthropic 两种模型"，拆出 3 个 claim，如果 context 说"支持多家"，则"只支持两种"无支撑 → Faithfulness = 2/3 = 0.67。

传统 NLP 指标为何不再适用

BLEU/ROUGE 等基于词汇匹配的指标不适合评估 RAG 的开放式生成，因为自然语言表达多样性太高，同一含义有无数种表述。现代 RAG 评估已基本转向 LLM-as-Judge。

05

检索优化：五大核心策略

评估定位瓶颈后，检索层的优化有五大武器：父子分块解决信息割裂、混合检索互补关键词与语义、重排…

评估定位瓶颈后，检索层的优化有五大武器：父子分块解决信息割裂、混合检索互补关键词与语义、重排序过滤噪音、HyDE 弥合语义鸿沟、强约束 Prompt 压制幻觉。

策略一：父子分块（Parent-Child Chunking）

传统固定大小分块会导致信息割裂 — 一个完整概念被切成多个 chunk，检索只命中其中一个片段。父子分块的思路是用子块（精细单元，如 200 词）保证检索精度，命中后返回父块（完整语义，如 800 词）给 LLM，兼得精度和完整性。

策略二：混合检索（Hybrid Search）

单一检索方式各有盲区：BM25（关键词匹配）擅长精确匹配但不懂语义，向量检索（语义理解）擅长模糊匹配但可能漏掉精确关键词。混合检索将两者结合，通过 RRF（Reciprocal Rank Fusion）算法融合排序结果，提升召回率。

检索方式优势劣势适用场景
BM25 关键词精确匹配、速度快不懂同义词/语义产品名、API名、编号
向量检索语义理解、模糊匹配精确匹配弱、需 embedding概念解释、方法论
混合检索两者互补需要融合排序算法通用场景（推荐默认）

策略三：重排序（Re-ranking）

初筛（向量检索）速度快但精度有限，重排序用 Cross-Encoder 对"问题-文档"对做深度打分，过滤噪音。实测精度提升 15%-30%，代价是增加约 200ms 延迟。

用户 Query
向量检索（Bi-Encoder，快但粗）→ Top-20 候选
Cross-Encoder 重排序（慢但精）→ Top-3~5 精选
送入 LLM 生成回答

策略四：HyDE 查询改写

用户的查询往往简短模糊（如"怎么部署"），与文档的正式表述有语义鸿沟。HyDE（Hypothetical Document Embeddings）的做法是：先让 LLM 生成一个"伪答案"（假设性的完整回答），再用这个伪答案去检索。伪答案更贴近文档的表述方式，检索效果更好。

HyDE 的本质：用 LLM 把用户的模糊查询"翻译"成文档的语言，弥合 query-document 之间的语义鸿沟。代价是多一次 LLM 调用（~500ms），但对复杂查询效果提升显著。

策略五：强约束 Prompt

在生成阶段明确指令"仅基于上下文回答，不准编造"，并调低 Temperature 参数减少随机性。这是对抗幻觉最直接、成本最低的手段。配合 citation 要求（"引用具体段落"），可大幅提升 Faithfulness。

  • 先跑评估定位瓶颈，再选对应策略
  • 父子分块 + 混合检索 + 重排序组合使用
  • 对复杂查询用 HyDE 弥合语义鸿沟
  • Prompt 中强制"仅基于上下文回答"
  • 降低 Temperature 减少生成随机性
  • 没有评估基线就盲目优化
  • 只用单一检索方式（纯向量或纯 BM25）
  • K 值设太大导致 context 过长（Lost in the Middle）
  • 忽略分块策略对检索质量的根本影响
  • 用高 Temperature 生成事实性回答

07

评估驱动的优化闭环

优化 RAG 的第一步永远是"先跑评估，定位瓶颈"，而非盲目换模型

优化 RAG 的第一步永远是"先跑评估，定位瓶颈"，而非盲目换模型。Recall 低 → 检索问题；Faithfulness 低 → 生成问题。分开诊断才能精准优化。

定位瓶颈的决策树

答案质量差？
Context Recall 低 → 检索没召回正确文档
Embedding 模型不够好 → 换模型 (BGE/E5/Cohere) · 分块策略不对 → 父子分块 / 调整 chunk_size · Query 与文档表述不匹配 → HyDE 查询改写 · K 太小 → 增大检索数量
Context Precision 低 → 检索到了但噪声多
加 Reranker (Cross-Encoder) · 混合检索 (BM25 + 向量) + RRF 融合 · 减小 K + 提高相似度阈值
Faithfulness 低 → LLM 在编造（幻觉）
Prompt 加强"只根据上下文回答"约束 · 降低 Temperature · 要求 citation（引用具体段落）
Answer Relevancy 低 → 答非所问
Prompt 模板质量差 → 重写 prompt
检索结果导致 LLM 跑偏 → context compression

生产案例：某企业知识库 RAG 优化

背景：日均 5000 次查询，初期 Faithfulness 仅 0.62，Context Recall 0.55。

第一轮优化（检索层）：引入混合检索 + 父子分块 → Context Recall 从 0.55 提升至 0.78（+42%）。

第二轮优化（重排序）：加 Cross-Encoder Reranker → Context Precision 从 0.45 提升至 0.82（+82%），延迟增加 180ms。

第三轮优化（生成层）：强约束 Prompt + Temperature 0.1 → Faithfulness 从 0.62 提升至 0.89（+44%）。

最终效果：用户满意度从 3.2/5 提升至 4.5/5，追问率下降 60%。

08

Q&A

①Faithfulness：回答是否忠于 context（检测幻觉）
RAGAS 的四个核心指标分别衡量什么？如何联合诊断问题？

①Faithfulness：回答是否忠于 context（检测幻觉）；②Answer Relevancy：回答是否切题（检测答非所问）；③Context Precision：检索到的文档中有用的比例；④Context Recall：标准答案中的信息能从检索结果中找到多少。联合诊断：Recall 低 → 检索器问题（换 embedding / 调分块）；Precision 低 → 排序问题（加 Reranker）；Faithfulness 低 → LLM 幻觉（强约束 Prompt）；Relevancy 低 → prompt 或整体设计问题。四个一起看才能完整定位瓶颈。

如何判断 RAG 系统的瓶颈在检索还是在生成？

分别评估两层指标。快速诊断法：①手动检查几个 bad case 的检索结果，相关文档是否在里面；②如果在但答错了 = 生成问题；③如果不在 = 检索问题。进阶方法：给 LLM 提供完美的 context（ground truth 文档），看回答质量；如果给了完美 context 还答不好，说明生成有问题。实践中 70% 的问题出在检索层。

父子分块和传统固定大小分块有什么区别？什么时候该用？

传统固定分块（如 512 tokens）简单但会割裂完整语义 — 一个概念可能跨越两个 chunk。父子分块用小子块（如 200 词）做检索索引保证精度，命中后返回父块（如 800 词）保证语义完整性。适用场景：文档结构清晰（有章节/段落层级）、概念解释类内容较多时。不适用：文档本身很短（无需分层）、实时性要求极高（父子索引增加存储和构建成本）。

LLM-as-Judge 有哪些已知偏差？如何缓解？

已知偏差：①长度偏差：倾向给更长回答高分；②位置偏差：多选时偏好第一个选项；③自我偏好：GPT-4 偏爱 GPT-4 风格回答；④格式偏差：偏爱结构化回答；⑤权威偏差：含"研究表明"等措辞得分更高。缓解方法：①多次采样取均值；②随机化选项顺序；③多个 Judge 模型交叉验证；④设计细粒度评分标准（rubric）；⑤混入人工标注做校准。关键认知：LLM-as-Judge 适合趋势判断，不适合绝对分值。

混合检索中 BM25 和向量检索的结果如何融合？

最常用的融合算法是 RRF（Reciprocal Rank Fusion）：对每个文档，RRF 分数 = Σ 1/(k + rank_i)，其中 k 通常取 60，rank_i 是文档在第 i 个检索器中的排名。RRF 的优势是不依赖分数归一化（BM25 和向量相似度分数量纲不同，直接比较没有意义），只看排名。实践建议：先用 BM25 + 向量各取 Top-20，RRF 融合后取 Top-5 送入 LLM。如果特定领域关键词很重要（如产品名），可以给 BM25 更高权重。

HyDE 查询改写的原理和代价是什么？

原理：用户查询通常简短模糊（如"怎么部署"），与文档正式表述有语义鸿沟。HyDE 先让 LLM 生成一个"伪答案"（假设性完整回答），再用伪答案的 embedding 去检索。伪答案更贴近文档表述，检索效果更好。代价：多一次 LLM 调用（~500ms + token 成本），适合复杂查询场景。不适用：简单事实查询（直接向量检索就够了）、实时性要求极高的场景。

如何构建一个评估→优化→验证的闭环？

五步闭环：①构建评估数据集（50-100 条起步，覆盖多种难度和类型）；②跑基线评估，记录四个核心指标；③根据决策树定位瓶颈，选择对应优化策略；④在相同评估集上重新评估，对比指标变化；⑤收集 bad case 补充进评估集，持续迭代。关键原则：每次只改一个变量（如只换 embedding 模型或只调分块大小），才能归因。评估集成到 CI/CD，每次改动自动回归测试。从 bad case 反馈中不断补充评估集，形成飞轮。
