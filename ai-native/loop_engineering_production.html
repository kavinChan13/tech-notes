01

核心问题：循环在哪里运行？

所有人都在问"什么是 Loop

所有人都在问"什么是 Loop？"，但没人问"什么在运行 Loop？"

单 Agent、单会话的 /loop 和 /goal 模式可以工作。但进入生产环境后，问题完全不同：

生产需求终端 while loop持久编排引擎
Loop 监督其他 Loop❌ 无编排能力✅ 嵌套调度
按计划运行（非人类触发）❌ 需手动启动✅ cron/事件触发
进程重启后存活❌ 状态丢失✅ 从检查点继续
生成子 Agent 并等待❌ 无持久等待✅ 异步等待数小时
事后可观察❌ 黑盒✅ 完整 trace
这不是提示词问题，而是基础设施问题。终端里的 while True 无法提供这些能力。VM 或沙箱上的长运行进程也不行。

生产环境的噩梦场景

想象你在服务器上运行 Agent Loop。进程死亡或重启——部署、OOM、Spot 实例回收。Loop 重启了，但：

  • 之前在做什么？进行到哪一步了？
  • 是否已经发送了那条 Slack 消息？是否已经调用了子 Agent？
  • 你不知道。它重新开始。重新获取已有数据，重新调用 LLM 做已有决策
  • 你醒来时看到三条相同的 Slack 消息和困惑的团队
修复方案不是"更好的错误处理"——而是一个执行模型，其中每一步都被检查点化，每个决策都被持久化，恢复意味着从最后成功的步骤继续。

Agent Loop 三层架构

Van Horn 的核心主张：Agent 不是 LLM + 工具，而是 Loop + Skill + 编排。

Agent Loop 三层架构（自上而下）
Layer 3 · Orchestrator 编排器
调度 cron · 执行 steps · 管理重试 · 强制并发限制 · 存储运行历史 · 热部署不中断
Layer 2 · Skill 技能
持久工作流 · 多步骤可重试可组合 · 独立可部署 · 内置容错 · 复利增长
Layer 1 · Loop 循环
cron + 决策器 · 按计划或触发运行 · 评估状态 · 决定下一步 · 调用 Skill

三层详细对比

维度Layer 1: LoopLayer 2: SkillLayer 3: Orchestrator
角色决策循环持久工作流运行时引擎
触发方式cron / 事件被 Loop 或事件调用管理一切调度
状态管理评估当前状态step 级检查点存储所有运行历史
容错失败后下次周期重试step 级重试 + onFailure全局重试策略
部署随 Agent 部署独立可部署热部署不中断
类比定时巡检员专业维修队物业管理系统

Layer 1: Loop 的实际工作模式

以基础设施健康检查为例：

每 30 分钟触发

→
LLM 评估健康
→
正常 → 结束

关键洞见：如果进程在步骤之间重启，已完成的步骤不会重新执行。这就是 Loop——不是 LLM，而是围绕 LLM 的循环。

Layer 2: Skill 的复利效应

Skill 不是提示词，而是持久工作流。多步骤、可重试、可组合、独立可部署。系统学习的每个新 Skill 都让每个 Loop 更强大。

Skill 特性说明与传统函数对比
持久性step 级检查点，失败后从断点继续传统函数需从头重试
可组合多个 Skill 可链式调用函数嵌套无状态管理
独立部署每个 Skill 可单独更新单体部署影响全局
容错内置重试 + 失败钩子需手动实现 try-catch
可观察每个 step 有完整 trace需额外添加日志

Layer 3: 编排器——没人谈论但最基础的层

编排器职责具体实现
调度 cron按 cron 表达式定时触发函数
执行 steps按顺序执行每个 step.run()，持久化输入输出
管理重试step 级重试策略，指数退避
强制并发限制流控制（限制、键、节流、去重）
存储运行历史每次运行、每个 step 的完整 trace
热部署新函数注册不中断运行中的工作流
大多数人把 Agent 看作"LLM + 工具"。Agent Loop 架构将其重新定义为"Loop + Skill + 编排"。LLM + 工具在 Loop 内部。LLM 和工具可以交换或调整，而架构保持不变。编排使架构成为可能。

故障分类与处理策略

故障类型典型场景处理方式结果
瞬时故障API 超时、网络抖动、临时限流step 级自动重试（指数退避）透明恢复，无感

模型故障LLM 返回格式异常、拒绝回答fallback 模型 + 重试切换模型继续

Step 级检查点的成本效益

场景无检查点（从头重试）有检查点（从断点继续）
5 个 step，第 4 步失败重跑 1-4 步（含 3 次 LLM 调用）只重跑第 4 步
单次 LLM 调用成本$0.50（重复 3 次 = $1.50 浪费）$0（已检查点化）
30 个 Agent 同时运行$45/天 浪费接近 $0 浪费
月度成本影响~$1,350 额外支出~$0 额外支出
Step 级检查点不只是正确性特性，它是省钱器。LLM 调用可以被检查点化，当乘以系统中的 10 个或 30 个 Agent 时，成本差异是戏剧性的。

模型路由：降低 60-80% 成本

Agent Loop 是 Token 密集型的

Agent Loop 是 Token 密集型的。一个每日 PR 审查 Loop 生成 5 个子 Agent，每个读取 50K Token 上下文，在前端模型定价下花费真金白银。

核心策略：将每个步骤路由到合适的模型层级。

部署模式与并发控制

四种部署模式

模式适用场景特点风险
单实例开发/测试简单，无并发问题单点故障
主备切换生产环境（低风险）主实例失败时备接管切换延迟
多实例 + 去重高可用场景多实例运行，编排器去重资源浪费
分区调度大规模（30+ Agent）按资源/团队分区，独立调度跨区协调复杂

并发控制策略

策略机制解决的问题
限流（Throttle）限制同时运行的实例数防止资源耗尽
键锁定（Key Lock）同一资源的 Loop 互斥执行防止竞争条件
去重（Debounce）短时间内重复触发只执行一次防止重复执行
优先级队列关键 Loop 优先执行资源竞争时的优先级保障
并发是生产环境最容易被忽视的问题。如果两个 Loop 同时操作同一资源（如同时修改同一文件、同时发送同一通知），结果是不可预测的。必须在编排层强制并发控制。

常见 Loop 失败及如何避免

失败类型问题修复方案预防措施
Token 失控没有 max_iterations 的 Goal Loop 可能在一小时内烧掉 $500始终设置上限，从 50 次开始成本告警 + 自动熔断
上下文腐烂长期运行的 Loop 不断追加上下文，质量下降每次迭代用子 Agent（新鲜上下文）定期压缩 + 质量监控

状态遗忘Loop 忘记已处理的内容每次迭代后写入检查点外部状态存储 + 去重

Do / Don't

  • 使用 step 级检查点持久化每个决策
  • 将步骤路由到合适的模型层级（60-80% 降本）
  • 添加提示缓存减少重复 Token 成本
  • 让 Agent 构建自己的 Skill（复利增长）
  • 提供完整 trace 直到 step 级（信任层）
  • 使用 onFailure 钩子处理不可恢复错误
  • 设置并发控制防止竞争条件
  • 实施审查 Loop 让 Agent 迭代自己的 Skill
  • Maker-Checker 模式验证关键操作
  • 建立分层测试策略（Step → Skill → Loop → E2E）
  • 在终端用 while True 运行生产 Loop
  • 让所有步骤使用同一前端模型
  • 忽视瞬时错误的成本（LLM 调用昂贵）
  • 假设 Agent 编写的代码总是正确
  • 将可观察性视为事后添加
  • 从 step 中间重试整个工作流
  • 让多个 Loop 同时操作同一资源
  • 部署新函数时中断运行中工作流
  • 忽视 Gateway 层的故障转移和限流
  • 跳过 Agent Loop 的端到端测试

常见问题 Q&A

消息队列解决的是"消息传递"问题——确保消息不丢失
Q1：持久执行和传统消息队列（如 Kafka）有什么区别？

消息队列解决的是"消息传递"问题——确保消息不丢失。持久执行解决的是"执行状态"问题——确保多步骤工作流在任意中断后能从断点继续。

关键区别：消息队列不知道你的业务逻辑执行到哪一步了。持久编排引擎知道每个 step 的状态，能精确恢复。消息队列是传输层，持久执行是执行层。

Q2：Agent 自己编写的 Skill 出错了怎么办？会不会造成连锁故障？

三层防护：① Skill 有独立的重试和 onFailure 钩子，单个 Skill 失败不会影响其他 Skill；② 编排器提供并发控制和熔断机制，防止级联故障；③ 开发者可以随时读取、编辑、删除任何 Skill。

核心原则：Agent 创作了 Skill，但人类拥有它。Agent 和它的 Skill 仍然是你应该照料的花园。

Q3：模型路由会不会影响输出质量？轻量模型能胜任分类任务吗？

模型路由的关键是"任务匹配"，不是"降级"。分类、扫描、过滤等任务不需要强推理能力，用 Nano 模型（如 Gemini Flash）的准确率与前端模型差异很小（通常 <2%），但成本低 50-100 倍。

建议：先用前端模型建立基准准确率，然后逐步测试轻量模型。当准确率差异 <3% 时切换到轻量模型。保留 fallback 到前端模型的能力。

Q4：什么规模的系统才需要三层架构？小项目用 while loop 够了吗？

判断标准不是项目大小，而是"失败代价"：

  • while loop 足够：开发/测试阶段、内部工具、失败后手动重启成本可接受
  • 需要持久编排：生产环境面向客户、失败导致数据不一致或重复操作、多个 Loop 并行运行、需要审计和合规

一个实用建议：先用 while loop 验证逻辑，确认价值后再迁移到持久编排。迁移成本不高——step.run() 包装现有逻辑即可。

Q5：自我进化的 Agent 会不会写出低质量的 Skill 并不断累积？

会的，如果没有审查机制。这就是为什么需要"审查 Loop"——一个定期运行的 cron 函数，分析每个 Skill 的成功率、误报率、团队响应率，并提议优化或淘汰。

类比软件工程中的"技术债务管理"：Agent 生成的 Skill 也会产生技术债务，审查 Loop 就是自动化的债务管理工具。人类仍然有最终决定权。

Q6：如何评估一个 Agent Loop 系统的健康度？

四个核心指标：

  • 可靠性：Skill 成功率（目标 >95%）、平均恢复时间（MTTR）
  • 效率：每 Loop 平均 Token 消耗、模型路由命中率（轻任务走 Nano 的比例）
  • 价值：Skill 被团队实际采纳的比例、误报率（目标 <10%）
  • 进化：新增 Skill 数量、审查 Loop 提议的采纳率
Q7：提示缓存（Prompt Caching）具体怎么实现？

大多数 LLM 提供商（Claude、GPT、Gemini）现在支持提示缓存。原理：如果请求的前缀（系统提示 + 工具定义）与之前的请求相同，提供商会复用已计算的 KV cache，输入 Token 成本降低 90%。

在 Agent Loop 中，系统提示和工具定义通常不变，只有用户消息变化。通过保持前缀稳定，每次迭代的输入 Token 成本大幅降低。Gateway 层（如 Requesty、LiteLLM）可以自动管理缓存。
