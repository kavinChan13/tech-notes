概览

Agent 系统失败处理的核心矛盾在于：传统软件的失败是"看得见的崩溃"（异常、超时、500 错误），而 Agent 的失败更多是"看不见的偏离"——系统一切正常、没有报错，但最终结果却是错的。解决这个矛盾需要融合 LLM 的自我修正能力与确定性工程护栏，而非简单套用传统的 try-catch-retry 模式。

01

显性失败与隐性失败：两种截然不同的故障模式

显性失败是"系统知道自己失败了"——有异常堆栈、有错误码、有超时信号

显性失败是"系统知道自己失败了"——有异常堆栈、有错误码、有超时信号；隐性失败是"系统不知道自己失败了"——一切运行正常，但逻辑跑偏了。后者才是 Agent 系统最危险的故障模式。

1.1 传统软件的显性失败

传统软件的失败模式已经被充分研究：接口超时、数据库连接断开、内存溢出、权限拒绝等。这些失败都有一个共同特征——系统层面会产生明确的异常信号。工程师可以通过 try-catch 捕获异常、通过重试策略应对瞬时故障、通过熔断器防止级联崩溃。这套方法论在过去 20 年已经被打磨得非常成熟。

1.2 Agent 系统的隐性失败

Agent 系统继承了传统软件的所有显性失败，但还引入了一类全新的故障模式——隐性失败。在这类失败中，系统不会抛出任何异常，API 调用全部成功，状态码全是 200，但最终交付的结果是错误的。典型表现包括：选错了工具但调用成功、陷入死循环反复执行相同操作、方向偏离导致逻辑自洽但目标错误。用户看到的不是 "Error 500"，而是"账单炸了"。

维度显性失败隐性失败
系统信号异常堆栈、错误码、超时无任何异常，一切正常
检测方式try-catch 自动捕获需业务逻辑校验或人工发现
重试有效性瞬时故障重试通常有效盲目重试大概率重复相同错误
传统工具覆盖完善的框架和模式几乎无现成方案
典型案例API 超时、DB 连接断开选错工具、死循环、方向偏离
用户感知"系统崩了""结果不对"

根据 AgentTether 框架在 τ-bench 261 个任务上的测试数据：在 Banking 领域，83 个初始失败任务中有超过 60% 属于隐性失败——系统没有报错但轨迹偏离了正确路径。传统重试策略对这些失败的修复率不足 5%。

02

显性失败处理：错误翻译与 LLM 自我修正

Agent 处理显性失败的核心思路是：把机器能读懂的堆栈异常翻译成 LLM 能理解的自然语言…

Agent 处理显性失败的核心思路是：把机器能读懂的堆栈异常翻译成 LLM 能理解的自然语言，让模型利用其推理能力修正错误路径——而不是盲目重试同一个注定失败的操作。

2.1 错误翻译机制

传统软件的重试策略是"原样重发"——同样的请求、同样的参数，赌的是瞬时故障已经恢复。但在 Agent 系统中，如果失败原因是参数构造错误或工具选择失误，盲目重试只会重复相同的错误。更聪明的做法是将异常堆栈、错误码和上下文信息转换为自然语言描述，反馈给 LLM，让它理解"为什么失败了"并调整策略。

2.2 单步错误预算

错误翻译虽好，但 LLM 的自我修正并非 100% 可靠——它可能连续多次"修正"都走入死胡同。因此必须设置单步错误预算：限制每个步骤的最大重试次数（通常为 2 次）。超过预算后强制熔断，将控制权交给上层恢复机制，防止无限循环消耗资源。

重试策略机制适用场景风险
盲目重试原样重发相同请求网络瞬时抖动参数错误时无限循环
错误翻译 + 修正异常转自然语言，LLM 调整后重试参数构造错误、工具选择失误LLM 修正可能仍然错误
指数退避重试间隔递增重试（1s→2s→4s）速率限制、服务过载增加整体延迟
单步预算熔断限次重试，超限强制中止所有场景的兜底保护可能过早放弃可恢复的故障

生产环境建议：单步错误预算设为 2 次，全局任务级预算设为 5 次。实测数据显示，超过 2 次重试仍无法修正的错误，继续重试的成功率不到 8%，但 token 消耗会以每次约 3000 tokens 的速度累积。

2.3 错误分类与响应矩阵

在生产级 Agent 系统中，错误不应被统一处理。首先需要对错误进行分类，然后为每类错误匹配最优响应策略。瞬时错误（超时、速率限制）适合退避重试；永久性错误（参数无效、资源不存在）需要重新规划；关键错误（安全违规、数据损坏）必须立即保存状态并升级到人工。

错误类别典型错误码响应策略超时设置升级条件
瞬时故障429/503/ETIMEDOUT指数退避重试（最多3次）30s 初始，倍增3次后仍失败

2.4 幂等性保障：让重试安全

重试策略有一个常被忽视的前提条件——幂等性（Idempotency）。如果一个操作执行两次和执行一次的效果相同，那么重试是安全的。但很多工具调用天然不具备幂等性——发送一封邮件、创建一条数据库记录、发起一笔支付——重复执行会导致重复操作。生产级 Agent 系统需要为每个工具调用生成唯一的幂等键（Idempotency Key），服务端据此判断是否为重复请求并拒绝二次执行。

# 幂等键生成示例
import hashlib, time

def make_idempotency_key(task_id, step, tool, params):
    raw = f"{task_id}:{step}:{tool}:{json.dumps(params, sort_keys=True)}"
    return hashlib.sha256(raw.encode()).hexdigest()[:16]

# 每次工具调用附带幂等键
result = call_tool(
    tool="send_email",
    params={"to": "user@example.com", "body": "..."},
    idempotency_key=make_idempotency_key("task_001", 3, "send_email", params)
)

错误翻译的本质是将"机器维度的失败信号"升维到"认知维度的失败理解"——LLM 不理解 TypeError at line 42，但能理解"你传了一个列表给期望字符串的函数，应该先取出第一个元素"。而幂等性是这一切的安全网——没有幂等性，错误翻译引导的"智能重试"可能比盲目重试更危险，因为它会自信地重复执行一个有副作用的操作。

03

隐性失败的三类形态与检测策略

隐性失败是 Agent 系统最棘手的挑战——没有系统级异常可以捕获，只能通过业务层面的确定性…

隐性失败是 Agent 系统最棘手的挑战——没有系统级异常可以捕获，只能通过业务层面的确定性规则来检测。核心原则：不依赖大模型反思（成本高且不可靠），改用轻量级工程护栏进行持续监控。

3.1 死循环：反复调用同一工具或状态震荡

Agent 可能在某一步卡住，反复执行相同的工具调用，或者在两个状态之间来回震荡。例如，一个数据分析 Agent 反复调用同一个 SQL 查询却不推进到下一步。检测方法是在执行过程中维护一个滑动窗口，记录最近 N 步的动作签名（工具名 + 参数哈希），当检测到动作相似度超过阈值时强制中断。

3.2 方向偏离：逻辑自洽但目标错误

Agent 的每一步推理看起来都合理，但整体方向与任务目标越来越远。例如，被要求"分析竞品定价"的 Agent 却花了大量步骤去分析竞品的技术架构。这类失败最难检测，因为每一步都"说得通"。解决方案是在任务流程中设置关键路标校验——在关键节点检查中间输出是否仍然与原始目标对齐，偏离时用小模型或规则引擎强行拉回。

3.3 上下文溢出：历史过长导致失忆

随着任务推进，Agent 的对话历史越来越长，早期的关键信息被推出上下文窗口，导致 Agent "忘记"了重要的约束条件或用户偏好。这不是模型变笨了，而是物理上看不到了。解决方案是定期对历史进行摘要压缩，释放上下文空间，同时保留关键决策点的完整信息。

04

检查点回滚：从"从头再来"到"断点续传"

没有检查点的 Agent 就像一个不会存盘的玩家——每次失败都要从头开始

没有检查点的 Agent 就像一个不会存盘的玩家——每次失败都要从头开始。在一个需要 20 步才能完成的任务中，如果第 18 步失败了，从头开始意味着前 17 步的计算全部浪费（包括 LLM token、API 调用和等待时间）。检查点机制让 Agent 可以回滚到最近的成功状态，只重试失败的那一步。

4.1 传统缺陷：无状态重试的浪费

传统的重试机制是"全有或全无"的——要么整条链路成功，要么从头再来。对于短任务（3-5 步）这不是大问题，但对于长链路任务（15-30 步），失败概率随步骤数线性增长。假设每步成功率为 95%，20 步任务的一次性成功概率仅为 0.95^20 ≈ 36%。没有检查点意味着 64% 的情况下你需要浪费大量已完成步骤的计算资源。

4.2 Agent 优化：逐步快照与增量恢复

Agent 系统可以在每个步骤完成后保存状态快照，记录当前步骤的输入、输出、中间变量和执行上下文。当某一步失败时，系统回滚到最近的成功检查点，仅重试失败步骤及其后续步骤。这种方式将恢复成本从 O(N) 降低到 O(1)——N 是已完成步骤数。

┌─────────────────────────────────────────────────────────┐ │ 检查点回滚 vs 全量重试 │ ├─────────────────────────────────────────────────────────┤ │ │ │ 【无检查点 - 全量重试】 │ │ Step1 → Step2 → ... → Step17 → Step18(FAIL) │ │ ┌─────────────────────────────────────────┐ │ │ │ 失败！从头开始: Step1 → Step2 → ... │ │ │ │ 浪费: 17步的计算 + tokens + API调用 │ │ │ └─────────────────────────────────────────┘ │ │ │ │ 【有检查点 - 增量恢复】 │ │ Step1✓ → Step2✓ → ... → Step17✓ → Step18(FAIL) │ │ ↑ ↑ ↑ │ │ [CP1] [CP2] [CP17] │ │ ┌─────────────────────────────────────────┐ │ │ │ 回滚到 CP17, 仅重试 Step18 │ │ │ │ 节省: 前17步的全部计算成本 │ │ │ └─────────────────────────────────────────┘ │ │ │ │ 检查点内容: │ │ ┌──────────────────────────┐ │ │ │ • 当前步骤编号 │ │ │ │ • 步骤输入/输出 │ │ │ │ • 累积上下文摘要 │ │ │ │ • 工具调用状态 │ │ │ │ • 时间戳 + 执行元数据 │ │ │ └──────────────────────────┘ │ └─────────────────────────────────────────────────────────┘

4.3 事件溯源：比检查点更精细的恢复

Durable AI Agent Loop 架构提出了一种更精细的方案——事件溯源（Event Sourcing）。与检查点在每个步骤结束后保存快照不同，事件溯源将每个操作记录为不可变事件，在恢复时通过重放事件流重建状态。这种方式可以做到操作级别的原子性——如果 LLM 调用成功但工具调用失败，可以只重放工具调用而不重新调用 LLM。实测数据显示，事件溯源的恢复时间比检查点方式平均减少 40%，但实现复杂度显著更高。

恢复模型保存粒度恢复精度实现复杂度适用场景
无检查点无只能从头开始最低短任务（<5步）
检查点快照每步结束回退到最近成功步骤中等中等长度任务（5-20步）
事件溯源每个操作操作级原子恢复高长链路关键任务（20+步）

检查点的价值不仅在于节省计算成本——它更是 Agent 可靠性的基石。没有检查点的 Agent 在生产环境中就像没有事务的数据库：一次失败就可能导致不一致状态。每步成功率为 95% 的 20 步任务，有检查点时整体成功率可从 36% 提升至 90% 以上。

05

缝合交付：当恢复成本过高时的降级智慧

并非所有失败都值得无限投入去恢复

并非所有失败都值得无限投入去恢复。当数据源不可用、外部服务彻底宕机、或者恢复成本远超任务价值时，最明智的选择是返回一个"不完美但可用"的结果——标注哪些部分缺失、附加置信度，让用户自行判断。

5.1 缝合交付的核心理念

缝合交付（Stitched Delivery）是指在任务无法完整完成时，将已完成的部分结果"缝合"在一起，附带缺失数据的标注和置信度评分，交付一个降级但可用的结果。这比"要么完美交付、要么彻底失败"的二元策略更加务实。

5.2 降级策略的分层设计

生产级 Agent 系统应该设计多层次的降级策略，根据失败的严重程度和恢复成本选择不同的降级级别。从最轻微的"延迟交付"到最严重的"部分结果 + 免责声明"，每个层级都有明确的触发条件和输出格式。

降级层级触发条件输出形式用户感知
L1 - 延迟交付瞬时故障，等待可恢复完整结果 + 延迟通知"稍等片刻就好"
L2 - 部分结果部分数据源不可用已完成部分 + 缺失标注"大部分都有，缺了一块"
L3 - 降级结果关键依赖失败替代方案结果 + 置信度"用了替代方案，可信度70%"
L4 - 错误报告恢复成本远超任务价值失败原因 + 建议操作"做不了，建议你这样做"

5.3 置信度标注规范

缝合交付的关键在于让用户知道哪些部分是可靠的、哪些部分有不确定性。每个结果片段应附带置信度评分：完整数据源支撑的标注为"高置信度（≥90%）"，部分数据源支撑的标注为"中置信度（60-89%）"，推断或替代方案产生的标注为"低置信度（<60%）"。

缝合交付不是"认输"，而是工程上最诚实的选择。一个标注了"市场数据来自缓存（2小时前），置信度75%"的部分报告，远比一个"抱歉，数据源不可用，无法完成任务"的空白页面有用得多。

  • 在每个结果片段标注数据来源和置信度
  • 设计多级降级策略，不要只有"全成功"和"全失败"
  • 明确告知用户哪些部分缺失以及为什么
  • 提供"重试缺失部分"的选项让用户自主决定
  • 记录降级事件用于后续分析和系统改进
  • 不要将不完整的结果伪装成完整结果交付
  • 不要在置信度低于 40% 时仍声称结果可靠
  • 不要无限重试——设定恢复成本上限
  • 不要在降级时丢弃已完成的部分结果
  • 不要让用户自己去发现结果中缺失了什么

生产级失败处理架构：从单点到体系

一个成熟的 Agent 失败处理系统不是各种策略的堆砌，而是一个分层的架构体系：底层是错误分…

一个成熟的 Agent 失败处理系统不是各种策略的堆砌，而是一个分层的架构体系：底层是错误分类与路由，中间是恢复策略引擎，上层是可观测性与学习循环。每一层各司其职，共同构成一个自我进化的可靠性系统。

6.1 可靠性分层栈

生产环境中，Agent 的可靠性需要按照分层栈的方式组织。最底层是幂等性保障——确保重试不会导致重复操作。中间层是错误分类与策略匹配——根据错误类型选择最优响应（重试、回退、熔断、升级）。最上层是可观测性与学习循环——从每次失败中提取经验，持续改进系统。

6.2 熔断器的三级状态

借鉴微服务架构中的熔断器模式（Circuit Breaker），Agent 系统可以为每个外部依赖（工具、API、数据源）维护一个熔断器。熔断器有三个状态：关闭（正常通过）、打开（所有请求快速失败）、半开（允许少量探测请求）。当某个工具的连续失败率超过阈值（如 50%），熔断器切换到打开状态，防止更多请求涌入加剧问题。

6.3 学习循环：从失败中进化

最高级的失败处理不是"恢复"，而是"学习"。每一次失败都应该被记录、分析和分类，形成失败模式库。系统通过分析历史失败数据，可以自动调整策略参数——某个工具频繁超时，就自动增加它的超时阈值；某类错误翻译的修正成功率低，就标记该类错误为"不可自动修正"，直接走降级路径。

6.4 成本感知的恢复决策

在实际生产中，不是所有任务都值得全力恢复。一个完善的失败处理系统需要内置成本意识：评估恢复所需的时间成本、token 成本、API 调用成本，与任务本身的价值做对比。如果恢复成本超过任务价值的 50%，应该降级到缝合交付而非全力恢复。

生产环境实测：一个典型的 20 步数据分析任务，每步平均消耗 4000 tokens。在第 15 步失败时，全量重试（从头开始）需要额外 60,000 tokens，而检查点恢复仅需 4,000 tokens。但如果是第 3 步就失败了，全量重试和检查点恢复的差异就小得多（12,000 vs 4,000）。成本感知引擎会根据当前步骤位置动态选择最优恢复策略。

生产级失败处理的核心不是"消灭所有失败"——那是不可能的。核心是"让每一次失败都有预案、有边界、有降级、有学习"。好的失败处理架构让系统在故障中依然保持可用，并且每次故障后都比之前更健壮。

Q&A

Agent 系统的隐性失败为什么比显性失败更危险？
显性失败会立即触发告警，工程师可以快速定位和修复。而隐性失败没有任何系统级信号——API 调用成功、状态码正常、日志无异常——但结果却是错的。这意味着隐性失败可能持续很长时间才被发现，期间已经产生了大量错误结果。更危险的是，由于没有报错，传统的监控和告警体系对隐性失败完全无效，必须依赖业务层面的确定性规则来检测。
错误翻译机制为什么不能替代传统的重试策略？
错误翻译和传统重试解决的是不同类型的问题。传统重试（指数退避、原样重发）适合处理瞬时故障——网络抖动、速率限制、服务短暂不可用——这些问题不需要"理解"错误原因，等一会儿再试就好了。错误翻译适合处理逻辑错误——参数构造错误、工具选择不当——这类问题等再久也不会自行恢复，需要 LLM 理解错误原因后调整策略。两者是互补关系，不是替代关系。
滑动窗口检测死循环时，窗口大小和相似度阈值应该如何设置？
窗口大小通常设为 5-10 步，太小会漏掉慢速循环（每隔几步才重复一次），太大会增加检测延迟。相似度阈值建议设在 0.8-0.9 之间——低于 0.8 会产生大量误报（正常的重复操作被误判为死循环），高于 0.9 则可能漏检变体循环（每次参数微调但本质相同的操作）。具体数值需要根据业务场景调优：工具调用种类少的场景可以提高阈值，种类多的场景应降低阈值。
检查点存储应该选择什么样的后端？内存、磁盘还是分布式存储？
这取决于系统的部署模式和可靠性需求。单机部署的短任务可以用内存存储（速度最快但进程重启后丢失）。需要跨重启恢复的场景应使用本地磁盘（持久但无法跨机器访问）。分布式部署的生产级系统应使用 Redis 或 PostgreSQL 等分布式存储（支持跨机器访问和自动故障转移）。实践中推荐"计算与存储分离"——Agent 执行逻辑在一个进程，检查点存储在独立的服务中，这样即使 Agent 进程崩溃，检查点数据仍然安全。
缝合交付中的置信度应该如何计算？
置信度计算通常基于三个维度：数据源可靠性（一手数据 > 缓存数据 > 推断数据）、数据完整性（所需字段的覆盖比例）、数据时效性（实时数据 > 近期缓存 > 过期缓存）。一种实用的计算方式是加权组合：数据源权重 40%、完整性权重 35%、时效性权重 25%。例如，一份市场报告如果 80% 的数据来自实时 API（权重 1.0）、20% 来自 2 小时前的缓存（权重 0.7），其完整性为 100%，时效性综合为 0.94，最终置信度约为 88%。
事件溯源与检查点快照有什么本质区别？各自适合什么场景？
检查点快照是"拍照片"——在每个步骤结束后保存完整的状态副本，恢复时直接加载最近的照片。事件溯源是"录视频"——将每个操作记录为不可变事件流，恢复时从头重放事件来重建状态。快照的优势是恢复速度快（直接加载），劣势是粒度粗（只能回退到步骤边界）。事件溯源的优势是粒度细（可以回退到任意操作），劣势是恢复需要重放（耗时更长）。短任务用快照足够，长链路且需要精细恢复的关键任务适合事件溯源。
在多 Agent 协作系统中，失败处理策略需要哪些额外考虑？
多 Agent 系统引入了三个额外的复杂性维度。首先是级联失败——一个 Agent 的失败可能触发依赖它的其他 Agent 也失败，需要设计隔离机制防止"一个 Agent 倒下、全链路崩盘"。其次是分布式检查点——多个 Agent 的状态需要协调一致地保存和恢复，不能出现 A 回滚了但 B 没有回滚的不一致状态。最后是通信失败——Agent 之间的消息传递可能丢失或延迟，这本身就是一种隐性失败，需要额外的消息确认和超时检测机制。
