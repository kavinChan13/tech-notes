检索与重排序

从粗召回到精排序的完整检索管线 — 漏斗式架构：先快后精，兼顾速度和质量

01

检索架构全景：三种编码范式

RAG 检索的核心矛盾：速度和精度的权衡

RAG 检索的核心矛盾：速度和精度的权衡。Bi-Encoder 快但不精确，Cross-Encoder 精确但慢，生产环境用"漏斗式"架构——先用 Bi-Encoder 粗筛百万文档到 Top-20，再用 Cross-Encoder 精排到 Top-5。

检索系统的性能取决于编码器如何平衡三个维度：编码速度（能否预计算）、交互深度（能否捕捉 query-doc 的细粒度匹配）、精度（能否区分相关和不相关文档）。三种主流范式各有取舍：

特性Bi-EncoderCross-EncoderColBERT
编码方式query 和 doc 独立编码query 和 doc 拼接后一起编码独立编码但保留 token 级向量
交互程度无（单向量点积）深度（全注意力）轻量（MaxSim token 级匹配）
预计算可以（doc 向量离线存储）不可以（每个 pair 独立推理）可以（doc 多向量离线存储）
检索速度最快（ANN 搜索，ms 级）最慢（线性扫描，秒级）快（特殊索引，百 ms 级）
精度中等最高（SOTA）高（接近 Cross-Encoder）
适用场景大规模初筛小规模精排需要兼顾速度和精度的折中
02

稀疏检索（BM25 / TF-IDF）

BM25 的本质：用词频和文档频率的统计权重衡量关键词重要性

BM25 的本质：用词频和文档频率的统计权重衡量关键词重要性。虽然"古老"，但在精确术语匹配场景下仍优于向量检索，是混合检索不可或缺的一极。

从 TF-IDF 到 BM25

TF-IDF（Term Frequency - Inverse Document Frequency）通过词频（TF）和逆文档频率（IDF）的乘积衡量词对文档的重要性。高频词 + 低文档频率 = 高权重。BM25 是 TF-IDF 的进化版，加入了两个关键改进：TF 饱和函数（防止词频过高主导排名）和文档长度归一化（短文档中的匹配比长文档更有价值）。

BM25 的两个超参数通常不需要调优：k1=1.2（TF 饱和参数）和 b=0.75（长度归一化参数）在大多数场景下表现良好。BM25 的核心优势是精确关键词匹配——对于产品名（"iPhone 15 Pro Max"）、错误码（"NullPointerException"）、API 名（"torch.nn.Linear"）等专有名词，BM25 几乎不会遗漏，而向量检索可能因为语义泛化而漏掉。

稀疏检索的优缺点

优点缺点
精确关键词匹配（不遗漏包含关键词的文档）无法理解同义词 / 语义相似
无需训练、无需 GPU、可解释性强"词汇鸿沟"：query 和文档用词不同则失效
速度极快（倒排索引，ms 级）不适合长尾/口语化查询、多语言语义对齐
BM25 在 RAG 中的定位：不是替代向量检索，而是互补。混合检索（BM25 + Dense + RRF）几乎总是优于任一单一方法，实测 Recall@10 提升 10-15%。如果文档含大量专有名词/精确术语，BM25 的权重应适当提高。
  • BM25 的 k1 和 b 参数通常不需要调：默认值(1.2, 0.75)在大多数场景够好
  • 稀疏检索 + 密集检索的混合几乎总是优于任一单一方法
  • BM25 在包含特定术语/名词的检索中仍优于向量检索（如产品名、错误码）
03

密集检索（Bi-Encoder + ANN）

Bi-Encoder 的核心优势：query 和 document 独立编码，文档向量可预计…

Bi-Encoder 的核心优势：query 和 document 独立编码，文档向量可预计算并存入向量数据库，检索时只需计算 query 向量 + ANN 搜索，支持百万级文档的毫秒级检索。

Bi-Encoder 架构

Bi-Encoder 将 query 和 document 分别通过 Transformer 编码为固定维度的向量（如 768 维），通过余弦相似度或点积衡量相关性。关键优势是文档向量可以离线预计算并存入向量数据库（如 FAISS、Milvus），在线检索时只需计算 query 向量，然后通过 ANN（Approximate Nearest Neighbor）算法快速找到最相似的 Top-K 文档。

ANN 算法（近似最近邻）

精确最近邻搜索在百万级文档下太慢（需要线性扫描），ANN 算法通过牺牲少量精度换取数量级的速度提升：

算法原理特点代表实现
HNSW多层跳表图结构高召回率（>95%）、内存密集Hnswlib, Qdrant, Milvus
IVF聚类 + 只搜索近邻簇可扩展、需训练FAISS IVF
PQ乘积量化压缩省内存、精度略降FAISS PQ
ScaNNGoogle: 各向异性量化速度极快Google ScaNN
DiskANNSSD-based 图索引超大规模、低成本Microsoft DiskANN

HNSW（Hierarchical Navigable Small World）是目前最流行的 ANN 算法：通过构建多层跳表图结构，实现高召回率（Recall@10 > 95%）和低延迟（< 10ms，百万级文档）。向量检索不是精确搜索——ANN 可能遗漏少量相关文档，这是速度的代价，但通过调参（如增大 ef_search）可以在精度和速度间权衡。

密集检索的优缺点

优点缺点
语义理解（同义词/释义/口语化查询都能匹配）精确词匹配不如 BM25（专有名词/错误码）
支持跨语言检索需要 GPU 做 embedding（离线阶段）
对模糊查询鲁棒向量空间的"各向异性"可能影响精度
  • Bi-Encoder 的核心优势：query 和 doc 独立编码，支持预计算文档向量→毫秒级检索
  • HNSW 是目前最流行的 ANN 算法：Recall@10 > 95%，延迟 < 10ms（百万级）
  • 向量检索不是精确搜索——ANN 可能遗漏少量相关文档，这是速度的代价

混合检索与 RRF 融合

混合检索的本质：BM25 擅长精确关键词匹配（专有名词、错误码），Dense 擅长语义理解（…

混合检索的本质：BM25 擅长精确关键词匹配（专有名词、错误码），Dense 擅长语义理解（同义词、释义、口语化查询）。两者盲区互补——BM25 召回的 Dense 可能漏掉（关键词变化），Dense 召回的 BM25 可能漏掉（语义相近但用词不同）。

为什么需要混合检索？

稀疏检索和密集检索各有盲区：BM25 抓关键词但不懂语义，向量检索懂语义但可能漏关键词。两者互补可显著提升召回率。实测：Hybrid 的 Recall@10 通常比单一方法高 10-15%。

Reciprocal Rank Fusion (RRF)

RRF（Reciprocal Rank Fusion）是将多路检索结果融合的简单有效算法。核心思想：每个文档根据其在各路结果中的排名得分，分数加和后重新排序。

RRF 公式：score(d) = Σ 1/(ranki + k)，其中 k 通常取 60

RRF 的优势：①只看排名不看绝对分数，天然解决不同检索器分数尺度不同的问题（BM25 的分数和向量相似度的量纲不同，无法直接比较）②不需要任何训练③简单有效。论文推荐 k=60，实践中 k=20~100 差异不大。

混合检索效果对比

方法Recall@10适合查询类型
BM25 only~0.65含专有名词/精确术语
Dense only~0.72语义化/口语化查询
Hybrid (RRF)~0.82所有类型（通用最优）
权重分配：如果文档含大量专有名词/精确术语（如产品名、错误码、API 名），BM25 权重应适当提高（如 0.6:0.4）；语义化查询多则 Dense 权重高（如 0.4:0.6）。Hybrid 检索几乎没有缺点，建议作为生产环境的默认选择。
  • RRF 的优势：不需要对不同检索器的分数做归一化（只看排名不看绝对分数）
  • RRF 中 k=60 是论文推荐值，实践中 k=20~100 差异不大
  • Hybrid 检索几乎没有缺点，建议作为生产环境的默认选择

Cross-Encoder Reranker

Reranker 是 RAG 中 ROI 最高的优化——增加 ~200ms 延迟换取 10-…

Reranker 是 RAG 中 ROI 最高的优化——增加 ~200ms 延迟换取 10-20% Precision 提升。典型流程：Dense/Hybrid 检索 Top-20 → Reranker 精排 → 取 Top-3~5 给 LLM。

Bi-Encoder vs Cross-Encoder

Cross-Encoder 将 query 和 document 拼接后一起输入 Transformer（格式：[CLS] query [SEP] document [SEP]），通过全注意力机制实现深度交互。每个 query token 与每个 document token 都能看到对方，捕捉细粒度的匹配信号（如精确词匹配、否定关系、条件关系）。这种深度交互带来 SOTA 精度，但代价是无法预计算——每个 (query, document) pair 都需要独立推理，速度极慢。

因此 Cross-Encoder 不能替代检索（太慢），只能在小候选集上使用。典型用法：Bi-Encoder 或 Hybrid 检索先粗筛出 Top-20~50 候选，再用 Cross-Encoder 对每个 (query, candidate) pair 打分，取 Top-3~5 传给 LLM。这种"漏斗式"架构兼顾了速度和质量。

典型 Reranker 模型

模型机构特点
bge-reranker-v2-m3BAAI多语言，开源最强之一
bge-reranker-v2-gemmaBAAI基于 Gemma，推理能力强
Cohere Rerank v3Cohere商业 API，效果极好
ms-marco-MiniLM-L-12SBERT轻量级，速度快
Jina Reranker v2Jina AI支持长文本 rerank
  • Reranker 是 RAG 中 ROI 最高的优化——增加 ~200ms 延迟换取 10-20% Precision 提升
  • 典型流程: Dense/Hybrid 检索 Top-20 → Reranker 精排 → 取 Top-3~5 给 LLM
  • Cross-Encoder 为何更精确？— 全注意力让 query 的每个 token 与 doc 的每个 token 交互
  • Reranker 不能替代检索（太慢），只能在小候选集上使用

ColBERT 延迟交互

ColBERT 的核心创新：保留 token 级粒度的交互，同时支持文档向量预计算

ColBERT 的核心创新：保留 token 级粒度的交互，同时支持文档向量预计算。介于 Bi-Encoder 和 Cross-Encoder 之间的折中方案。

ColBERT 核心思想

ColBERT（Contextualized Late Interaction over BERT）将 query 和 document 分别编码，但不做 pooling 成单向量，而是保留每个 token 的向量。然后通过 MaxSim 操作实现轻量级交互：对每个 query token，找到 document 中最相似的 token，取最大值后求和。

ColBERT 打分：score(q, d) = Σi maxj cos_sim(qi, dj)

这种设计让 ColBERT 能捕捉精确词匹配（某个 query token 与 doc token 高度匹配）和语义匹配能力，同时文档端的多向量仍可预计算并存入特殊索引，支持高效检索。缺点是存储开销大（每个文档 N 个 token 向量），通常用量化（2-bit）压缩缓解。

ColBERT 优势

对比Bi-EncoderColBERTCross-Encoder
Doc 预计算可以（单向量）可以（多向量）不可以
精度中高（比 Bi-Encoder 高 5-10%）最高
检索速度最快快（需特殊索引）最慢
存储低（1 vec/doc）高（N vecs/doc，需量化）无需存储
BGE-M3 的多模式支持：BGE-M3 同时支持 Dense + Sparse + ColBERT 三种模式，一次编码三种用途，是生产环境中灵活切换检索策略的理想选择。
  • ColBERT 的核心创新：保留 token 级粒度的交互，同时支持文档向量预计算
  • MaxSim 操作让 ColBERT 能捕捉精确词匹配（类似 BM25）+ 语义匹配（类似 Dense）
  • 存储开销大是主要缺点：每个 doc 存 N 个 token 向量，可用量化（2-bit）缓解
  • BGE-M3 同时支持 Dense + Sparse + ColBERT 三种模式，一次编码三种用途

Query 变换技术

用户的原始 query 往往不是最优的检索输入：可能过于简短、模糊、或与文档表述不匹配

用户的原始 query 往往不是最优的检索输入：可能过于简短、模糊、或与文档表述不匹配。Query 变换在检索前优化查询，bridging query-document 语义鸿沟，提升召回率。

主要技术

技术原理效果
HyDE用 LLM 生成假设性答案，用答案做检索bridging query-doc 语义鸿沟
Multi-Query用 LLM 改写为多个不同表述的 query提高召回覆盖面
Step-Back将具体问题抽象为更高层的概念找到更全面的相关文档
Sub-Query将复杂问题分解为多个子问题multi-hop 问题的分步检索

HyDE（Hypothetical Document Embeddings）

HyDE 的核心思想：让 LLM 先"猜"一个答案，用猜测的答案去检索。原理是答案的表述方式比问题更接近文档的表述方式（减小 query-document 语义鸿沟）。例如 query 是"RAG 怎么减少幻觉？"（短、口语化），LLM 生成的假设性文档可能是"RAG 通过检索相关文档作为上下文来约束 LLM 的生成，减少模型自行编造不存在信息的概率..."（长、接近文档表述），这个假设性文档的 embedding 与实际文档的相似度更高。

HyDE 的局限：LLM 可能生成错误的假设答案 → 检索到不相关文档；增加延迟（多一次 LLM 调用）；对简单/精确的查询反而有害（"Python 3.12 changelog"这种直接 BM25 更好）。缓解方法：将 HyDE 与原始 query 的检索结果融合，而非完全替代。

Multi-Query 改写

用 LLM 将一个 query 改写为多个不同角度的表述，每个变体独立检索，合并去重结果。例如原始 query "Python 的 GIL 是什么"，改写为"Python 全局解释器锁的工作原理"、"GIL 对 Python 多线程的影响"、"为什么 Python 有 GIL"，不同变体可能检索到不同相关文档，提高召回覆盖面。Multi-Query 几乎没有副作用，是最安全的 query 增强方法。

  • HyDE 的局限：LLM 可能生成错误的假设答案 → 检索到不相关文档。对模型能力有要求
  • Multi-Query 几乎没有副作用，是最安全的 query 增强方法
  • Step-Back Prompting："Python 的 GIL" → 抽象为"编程语言的并发机制" → 检索更广泛
  • 这些技术可以组合使用：Multi-Query + HyDE + Reranker

生产级检索管线设计

生产级 RAG 的检索延迟通常控制在 200-500ms（不含 LLM 生成）

生产级 RAG 的检索延迟通常控制在 200-500ms（不含 LLM 生成）。Metadata 过滤 + 混合检索 + Reranker 是"三板斧"，缺一不可。

典型 Pipeline

一个完整的生产级检索管线包含以下组件：User Query → Query Preprocessor（意图识别/改写/扩展）→ 并行检索（BM25 Retriever K=20 + Dense Retriever K=20）→ RRF 融合 → 候选集（30-50 docs）→ Cross-Encoder Reranker（Top-30 → Top-5）→ Context Compression（去冗余/提取关键段）→ LLM Generation（with Top-5 context）。

延迟预算分配

组件典型延迟优化方式
Query Embedding5-20ms本地 GPU / 轻量模型
BM25 检索5-30msElasticsearch/Lucene
Dense 检索 (ANN)5-50msHNSW / GPU 加速
Reranker100-300ms轻量模型 / 减少候选数
LLM 生成1000-3000ms流式输出 / 小模型路由
总计1.2-3.5s

Metadata 过滤

在向量检索前/后使用 metadata 过滤缩小范围，常用 metadata 包括时间、来源、类别、权限、语言。Pre-filtering（先过滤再检索）可以减小搜索空间，Post-filtering（先检索再过滤）简单但可能浪费 K 配额。建议优先使用 Pre-filtering，向量数据库（如 Qdrant、Milvus）通常原生支持。

检索结果应添加相似度分数阈值：低于阈值（如 <0.5）的结果不传给 LLM，避免噪声干扰生成。流式输出是改善用户体验的关键——检索完成后立即开始生成第一个 token，不要等全部生成完毕再返回。
  • 混合检索（BM25 + Dense + RRF）作为默认选择
  • 加 Reranker 精排（ROI 最高）
  • 用 Metadata 过滤缩小范围
  • 设相似度阈值过滤低质量结果
  • 流式输出改善用户体验
  • 只用单一检索方式（BM25 only 或 Dense only）
  • 跳过 Reranker（精度损失大）
  • 把所有 Top-K 结果都传给 LLM（噪声多）
  • 忽略 Metadata 过滤（搜索空间大）
  • 等全部生成完毕再返回（延迟高）
  • 生产级 RAG 的检索延迟通常控制在 200-500ms（不含 LLM 生成）
  • Metadata 过滤 + 混合检索 + Reranker 是"三板斧"，缺一不可
  • 流式输出是改善用户体验的关键——检索完成后立即开始生成第一个 token
  • 检索结果应添加相似度分数阈值（如 >0.5），低于阈值的结果不传给 LLM

Q&A

Bi-Encoder 和 Cross-Encoder 有什么区别？为什么 RAG 中两者配合使用？
Bi-Encoder：query 和 document 分别独立编码为向量，通过余弦相似度排序。优点是文档向量可预计算、检索速度极快（ms 级支持百万文档）；缺点是 query-doc 无深度交互，精度有限。Cross-Encoder：将 query 和 document 拼接后一起输入 Transformer，全注意力交互。精度远高于 Bi-Encoder（SOTA），但无法预计算、每个 pair 需独立推理，速度极慢。配合使用的原因：Bi-Encoder 负责大规模粗筛（百万→Top-20~50），Cross-Encoder 负责小规模精排（Top-50→Top-5）。这是"漏斗式"检索架构：先快后精，兼顾速度和质量。
什么是 RRF？为什么混合检索几乎总是优于单一检索？
RRF（Reciprocal Rank Fusion）是将多路检索结果融合的算法。公式：对每个文档 d，score(d) = Σ 1/(rank_i + k)，其中 rank_i 是 d 在第 i 路结果中的排名，k 是常数（通常60）。然后按总分重排。RRF 的优势：①只看排名不看绝对分数，天然解决不同检索器分数尺度不同的问题②不需要任何训练③简单有效。混合检索为何更优：BM25 擅长精确关键词匹配（专有名词、错误码），Dense 擅长语义理解（同义词、释义、口语化查询）。两者盲区互补——BM25 召回的 Dense 可能漏掉（关键词变化），Dense 召回的 BM25 可能漏掉（语义相近但用词不同）。实测：Hybrid 的 Recall@10 通常比单一方法高 10-15%。
HyDE 是什么？在什么场景下有效？有什么风险？
HyDE（Hypothetical Document Embeddings）：先用 LLM 根据 query 生成一个"假设性答案"，再用这个假设答案的 embedding 去检索。原理：答案的表述方式比问题更接近文档的表述方式（减小 query-document 语义鸿沟）。有效场景：①短/模糊的 query（"GIL"→LLM 展开为完整描述）②query 和文档表述差异大的场景③不方便 fine-tune embedding 的场景。风险：①LLM 可能生成错误的假设答案→检索方向完全偏②增加延迟（多一次 LLM 调用）③对简单/精确的查询反而有害（"Python 3.12 changelog"这种直接 BM25 更好）。缓解：将 HyDE 与原始 query 的检索结果融合，而非完全替代。
ColBERT 的 Late Interaction 是什么意思？相比 Bi-Encoder 和 Cross-Encoder 有什么优势？
Late Interaction：query 和 document 分别独立编码（像 Bi-Encoder），但保留每个 token 的向量而非 pooling 成单向量。在计算相似度时通过 MaxSim 操作进行 token 级轻量交互：对每个 query token 找到 document 中最相似的 token，取最大值后求和。优势：①相比 Bi-Encoder：token 级交互捕获更精细的匹配信号（如精确词匹配），精度高 5-10%②相比 Cross-Encoder：文档端向量仍可预计算，支持高效索引，速度快几个数量级③兼具精确词匹配（某个 query token 与 doc token 高度匹配）和语义匹配能力。缺点：存储量大（每个文档 N 个 token 向量），通常用量化（2-bit）压缩。
设计一个生产级检索管线需要考虑哪些因素？
核心考量：①延迟预算：端到端通常要求 <3s，检索部分 <500ms；各组件预算分配（embedding 20ms + ANN 30ms + Reranker 200ms）②召回策略：混合检索（BM25+Dense+RRF）是默认最优；特殊场景加 ColBERT③精排：Cross-Encoder Reranker 是 ROI 最高的组件，初筛 K=20-50，精排后 Top-3~5④Metadata 过滤：时间/来源/权限/类别，pre-filter 减小搜索空间⑤Query 预处理：意图识别（需不需要检索）、Multi-query/HyDE 提升召回⑥容错机制：相似度阈值过滤低质量结果、fallback 策略（检索失败时直接用 LLM）⑦可观测性：记录每一步的中间结果（检索了什么/重排结果/最终 context），方便调试⑧缓存：语义缓存热门 query 的检索结果，减少重复计算。
BM25 在什么场景下优于密集向量检索？
BM25 优于 Dense 的场景：①精确术语/专有名词查询（产品名"iPhone 15 Pro Max"、错误码"NullPointerException"、API 名"torch.nn.Linear"）②关键词明确且文档中原样出现③新词/未登录词（embedding 模型训练时没见过的新术语）④短文档/FAQ（BM25 的文档长度归一化在短文本上效果好）⑤数据量小时（Dense 需要足够数据训练/选模型，BM25 开箱即用）。Dense 更优的场景：同义词/释义查询、口语化表述、跨语言检索、长查询。结论：不要二选一，混合检索是最优解。一个实用判断：如果 query 中有专有名词/精确术语，BM25 几乎肯定能补充 Dense 遗漏的结果。
如何评估检索质量？有哪些核心指标？
离线评估核心指标：①Recall@K：Top-K 结果中包含相关文档的比例（最重要，漏掉的文档后续无法恢复）②MRR（Mean Reciprocal Rank）：第一个相关结果的排名倒数的均值（衡量"排第几"）③NDCG@K：归一化折损累积增益（考虑排名位置，越靠前越好）④Precision@K：Top-K 中相关文档的占比。评估数据来源：用户搜索日志 + 人工标注相关文档，50-100 条即可起步。A/B 测试：改动任何检索组件后，在评估集上回归测试 Recall 和 MRR，确保没有退化。Recall 是检索层最重要的指标——漏掉的文档后续无法恢复，所以宁可多召回（高 Recall）让 Reranker 过滤，也不要漏掉关键文档。
