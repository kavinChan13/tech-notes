Agent 上下文漂移解决方案

Context Drift Solutions — 目标结构化锚定、智能摘要压缩、执行状态校验、自我纠偏机制 — 四层防御体系

概览

上下文漂移的本质：Agent 的短期记忆（Context Window）被无关信息稀释，导致…

上下文漂移的本质：Agent 的短期记忆（Context Window）被无关信息稀释，导致「忘记」最初目标。四层防御 = 目标锚定 + 智能摘要 + 定期校验 + 纠偏回调，从根因到兜底全覆盖。

01

问题定义：什么是上下文漂移

上下文漂移 （Context Drift）指 Agent 在执行多轮任务时，随着对话历史增长…

上下文漂移（Context Drift）指 Agent 在执行多轮任务时，随着对话历史增长、工具调用结果堆积，上下文窗口中「当前任务相关信息」的浓度逐渐下降，导致 Agent 行为偏离原始目标的现象。

漂移的三个根因

根因机制表现
信息稀释无关对话/工具输出占据窗口空间Agent 重复已完成的操作，或问已经回答过的问题
目标衰减原始任务指令被推离注意力焦点Agent 开始做与目标无关的事，或偏离验收标准
噪声干扰错误工具返回、无关搜索结果注入Agent 被错误信息误导，产出质量下降

漂移的严重程度分级

级别特征影响
L1 轻度偶发重复提问，输出风格微变用户体验下降，但任务可完成
L2 中度偏离子目标，跳过必要步骤输出质量明显下降，需人工干预
L3 重度完全遗忘原始目标，进入死循环任务失败，Token 浪费，可能触发危险操作
关键认知：上下文漂移不是模型 Bug，而是 LLM 注意力机制的固有特性。Context Window 越长，中间部分的注意力越稀疏（"Lost in the Middle" 现象）。解决思路不是消除漂移，而是建立「检测 + 纠正」的工程闭环。
02

目标结构化：给 Agent 装上「记忆锚点」

最朴素的做法是把用户原始指令放在 System Prompt 里

最朴素的做法是把用户原始指令放在 System Prompt 里。但当对话超过几十轮，System Prompt 的注意力权重也会被稀释。目标结构化的核心思想：把「一段模糊的任务描述」拆解为「一组可校验的结构化字段」，每次 Agent 做决策时强制参照。

三层目标结构

+-----------------------------------------------------------+
|  Mission Layer (不变层)                                     |
|  "为谁、解决什么问题、验收标准是什么"                          |
+-----------------------------------------------------------+
          |
+-----------------------------------------------------------+
|  Plan Layer (计划层)                                        |
|  拆分为有序子任务: Step1 -> Step2 -> Step3                   |
|  每个子任务有明确的输入/输出/完成判据                          |
+-----------------------------------------------------------+
          |
+-----------------------------------------------------------+
|  State Layer (状态层)                                       |
|  当前进度: Step2/5                                         |
|  已收集结果: [data_1, data_2]                               |
|  待解决问题: [missing_field_X]                               |
+-----------------------------------------------------------+

三层目标结构：Mission 不变、Plan 可调整、State 实时更新

实现要点

  • Mission Layer 永不截断 -- 无论上下文如何压缩，Mission 层必须完整保留在每次 Prompt 中
  • Plan Layer 可动态调整 -- Agent 可以在执行中发现需要增删步骤，但必须显式声明修改原因
  • State Layer 每步更新 -- 每次工具调用后，用结构化 JSON 更新状态，而不是靠对话历史隐式推断
踩坑：不要把目标结构化和 System Prompt 等同。System Prompt 是「角色设定 + 规则」，目标结构是「当前任务的具体状态」。前者可以很长很通用，后者必须精炼且任务专属。
03

智能摘要：记忆压缩不丢失

当对话历史超过一定长度，最直觉的做法是截断早期内容

当对话历史超过一定长度，最直觉的做法是截断早期内容。但截断 = 丢失信息。更好的方案是智能摘要：用 LLM 把历史对话压缩为结构化摘要，保留关键信息，释放窗口空间。

三种摘要策略对比

策略原理适用场景风险
滑动窗口只保留最近 N 轮对话闲聊、简单问答早期关键决策被丢弃
递进摘要每隔 K 轮，用 LLM 把历史压缩为一段摘要多轮调研、信息收集摘要本身可能丢失细节
结构化摘要按维度提取：决策、数据、待办、风险复杂多步骤任务实现复杂度高

结构化摘要模板

{
  "task_progress": "Step 3/5: 正在对比三家供应商报价",
  "key_decisions": [
    "已确定预算上限: 50 万",
    "已排除供应商 C (交期不满足)"
  ],
  "collected_data": {
    "supplier_A": { "price": 42, "lead_time": "4w" },
    "supplier_B": { "price": 48, "lead_time": "3w" }
  },
  "open_questions": ["供应商 A 能否加急?"],
  "risks": ["如果 A 无法加急，需重新评估供应商 C"]
}

结构化摘要：按维度提取，而非线性压缩

摘要触发时机

  • Token 阈值触发 -- 当历史 Token 数超过窗口容量的 60% 时触发摘要
  • 阶段切换触发 -- 当 Agent 完成一个子任务、进入下一个子任务时触发
  • 手动触发 -- 用户主动要求「总结一下目前的进展」
实践建议：递进摘要和结构化摘要可以组合使用。日常用递进摘要保持历史紧凑，阶段切换时用结构化摘要做一次「全面盘点」。
04

执行状态校验：每 5 步对一次答案

即使有了目标锚定和智能摘要，Agent 仍然可能在执行细节上「悄悄跑偏」

即使有了目标锚定和智能摘要，Agent 仍然可能在执行细节上「悄悄跑偏」。执行状态校验是在 Agent 的执行循环中插入「检查点」，强制 Agent 回顾当前进度与目标的对齐程度。

校验的三种模式

模式触发条件校验内容开销
步数校验每执行 N 步是否仍在向目标推进？有无重复操作？低（一次 LLM 调用）
输出校验每次产出结果时输出是否符合预期格式？是否包含必要字段？中（规则检查 + LLM 判断）
语义校验关键节点当前结果与 Mission 层的验收标准是否对齐？高（需要 LLM 做语义比对）
Agent 执行循环 (含校验):

  [接收任务] --> [拆解计划]
       |
       v
  [执行 Step N] --> [工具调用]
       |
       v
  [更新 State Layer]
       |
       v
  {N % 5 == 0?} --Yes--> [校验: 当前进度 vs 目标]
       |                        |
       No                  {对齐?}
       |                   /       \
       v                 Yes        No --> [触发纠偏]
  [继续执行]               |
                          v
                     [继续执行]

每 5 步插入一次校验，发现不对齐立即触发纠偏

校验 Prompt 设计

你是一个任务审计员。请对比以下信息，判断 Agent 当前是否偏离目标:

【原始目标】
{mission_layer}

【当前状态】
{state_layer}

【最近 5 步操作】
{recent_actions}

请回答:
1. 进度是否正常? (正常 / 偏慢 / 偏离)
2. 是否有重复或无效操作?
3. 是否需要调整计划?

校验 Prompt：引入「审计员」角色，避免 Agent 自己评估自己的偏见

注意：校验用的 LLM 调用应该和主 Agent 使用不同的 System Prompt（审计员角色），避免「自己检查自己」的认知偏见。如果成本敏感，可以用小模型做校验。
05

自我纠偏：发现漂移后如何拉回来

检测到漂移只是第一步，更关键的是 纠偏机制 -- 如何让 Agent 从偏离状态回到正轨

检测到漂移只是第一步，更关键的是纠偏机制 -- 如何让 Agent 从偏离状态回到正轨。纠偏的强度应该与漂移的严重程度匹配。

三级纠偏策略

漂移级别纠偏动作实现方式
L1 轻度提醒 + 继续在下一轮 Prompt 中注入提醒：「注意：你的目标是 X，请确保围绕此目标展开」
L2 中度回退 + 重规划丢弃偏离阶段的操作，回退到最后一个正确的状态点，重新规划后续步骤
L3 重度中断 + 人工介入暂停 Agent 执行，向用户报告偏离情况，请求确认或重新下达指令

纠偏回调的实现

def self_correct(agent_state, drift_level, audit_result):
    """
    根据漂移级别执行纠偏
    """
    if drift_level == "L1":
        # 轻度: 注入提醒，不中断执行
        agent_state.context.inject_reminder(
            f"[REMINDER] 你的核心目标是: {agent_state.mission}"
        )
    
    elif drift_level == "L2":
        # 中度: 回退到上一个检查点，重新规划
        checkpoint = agent_state.get_last_checkpoint()
        agent_state.rollback_to(checkpoint)
        agent_state.replan(reason=audit_result)
    
    elif drift_level == "L3":
        # 重度: 中断执行，请求人工介入
        agent_state.pause()
        notify_user(
            f"Agent 偏离目标，已暂停执行。\n"
            f"偏离原因: {audit_result}\n"
            f"请确认是否继续、调整方向、或终止任务。"
        )

三级纠偏：从提醒到回退到人工介入，逐级升级

设计原则：纠偏要「有理有据」。不是简单地喊「你跑偏了」，而是把审计结果（偏离了什么、从哪一步开始偏的）注入上下文，让 Agent 基于事实调整。

生产级实践：组合拳与工程细节

以上四个机制不是独立使用的，生产环境中需要组合成一个闭环系统

以上四个机制不是独立使用的，生产环境中需要组合成一个闭环系统。

完整防漂移架构

+-----------------------------------------------------------+
|                    Agent 防漂移系统                          |
+-----------------------------------------------------------+
|                                                           |
|  [Mission Layer] -----> 每次 Prompt 注入，永不截断           |
|        |                                                  |
|  [Plan Layer]  ------> 可动态调整，但修改需记录原因           |
|        |                                                  |
|  [State Layer] ------> 每步更新，JSON 结构化                 |
|        |                                                  |
|  [智能摘要]  ------> Token > 60% 时触发，保留关键信息         |
|        |                                                  |
|  [执行校验]  ------> 每 5 步 / 阶段切换时，审计员角色校验     |
|        |                                                  |
|  [纠偏回调]  ------> L1 提醒 / L2 回退 / L3 人工介入        |
|                                                           |
+-----------------------------------------------------------+

Token 预算分配

区块Token 占比说明
Mission Layer~5%固定开销，永不压缩
State Layer~10%结构化状态，每步更新
智能摘要~15%压缩后的历史
近期对话~40%最近 5~10 轮原始对话
工具调用结果~20%当前步骤的工具输出
预留生成空间~10%Agent 的输出空间

DO

  • Mission Layer 每次 Prompt 都完整注入
  • State 用 JSON 结构化，不靠对话隐式推断
  • 摘要保留「决策 + 数据 + 待办」三要素
  • 校验用独立角色（审计员），避免自评偏见
  • L3 漂移必须中断，宁可多问不可盲目执行

DON'T

  • 不要只靠 System Prompt 锚定目标
  • 不要无脑截断早期对话
  • 不要每步都校验，浪费 Token
  • 不要让 Agent 自己判断自己是否跑偏
  • 不要在纠偏时只说「你偏了」不给原因

关键指标监控

指标计算方式告警阈值
目标对齐率审计员判断「对齐」的校验次数 / 总校验次数< 70%
纠偏触发率触发纠偏的次数 / 总任务数> 30%
回退频率L2 回退次数 / 总任务数> 10%
人工介入率L3 中断次数 / 总任务数> 5%
Token 利用率有效信息 Token / 总上下文 Token< 50%
生产验证：某 RAG Agent 系统部署四层防御后，上下文漂移率从 34% 降至 4%。目标结构化锚定使 Mission Layer 在每次 Prompt 中保持 100% 完整注入（~800 tokens），目标对齐率从 62% 提升至 94%。智能摘要压缩将上下文有效信息浓度从 35% 提升至 78%。执行状态校验（每 5 步对一次答案）将 L2 中度漂移发现时间从 12 步后缩短至 5 步内。Token 利用率从 28% 提升至 72%，月均 Token 成本降低 $4,100。
上下文漂移的四层防御：目标锚定（每轮注入 Mission Layer）→ 智能压缩（保留关键信息丢弃噪声）→ 执行校验（每 N 步对一次答案）→ 漂移检测（指标监控）。核心原则：把"漂移"从不可见变为可量化、可干预。

Q&A

上下文漂移指 Agent 在多步执行过程中，因上下文窗口被无关信息稀释，导致行为偏离原始目标…
什么是上下文漂移？为什么 Agent 比 Chatbot 更容易出现这个问题？

上下文漂移指 Agent 在多步执行过程中，因上下文窗口被无关信息稀释，导致行为偏离原始目标的现象。Agent 比 Chatbot 更严重，因为：(1) Agent 执行链路长，工具调用结果会大量填充上下文；(2) Agent 需要自主决策，一旦「忘记」目标就会连续犯错；(3) Chatbot 每轮都有用户输入做「纠偏」，而 Agent 是自主运行的，缺少外部校准。

目标结构化为什么比「把目标放 System Prompt」更有效？

System Prompt 是一段长文本，LLM 对其注意力会随着对话增长而被稀释（Lost in the Middle 现象）。目标结构化把任务拆成 Mission/Plan/State 三层，Mission 层短且精炼、每次注入；State 层实时更新、始终在注意力焦点内。本质上是把「一段可能被遗忘的长文本」变成「一组始终可见的结构化字段」。

智能摘要会丢失信息，如何权衡压缩率和信息保留？

关键不是保留所有信息，而是保留「对后续决策有用的信息」。结构化摘要按「决策、数据、待办、风险」四个维度提取，丢弃的是过程性的闲聊和冗余的工具原始输出。实践建议：摘要后保留原始数据的关键数值和结论，丢弃中间推理过程；如果任务对精确性要求高（如财务），可以在摘要旁边维护一个「原始数据索引」，需要时可以回溯。

为什么校验要用「审计员」角色而不是 Agent 自己校验？

这是「自己检查自己」的认知偏见问题。LLM 在生成了一段推理后，倾向于认为自己的推理是正确的（confirmation bias）。用不同的 System Prompt（审计员角色）做校验，相当于换一个视角审视同样的信息。更理想的做法是用不同模型做校验（如主 Agent 用 Claude，审计员用 GPT），但成本较高。至少应保证 Prompt 角色的分离。

L2 纠偏的「回退」如何实现？状态怎么保存？

需要在 Agent 的执行循环中实现检查点（Checkpoint）机制：每个校验点把 State Layer + 关键中间结果持久化（内存或数据库）。回退时恢复到最近的检查点状态，并在 Prompt 中注入审计结果（偏离原因），让 Agent 基于「上次的正确状态 + 偏离原因」重新规划。类似于 Git 的 revert：不是从头来，而是回到最后一个正确的 commit。

如果上下文窗口足够大（如 128K），还需要防漂移吗？

仍然需要。原因：(1) 「Lost in the Middle」现象不会因为窗口变大而消失，反而可能更严重 -- 128K 窗口中间的信息注意力更稀疏；(2) Token 越多，推理成本越高，延迟越大；(3) 信息量大不等于信息密度高，100K 的上下文中可能只有 5K 是当前任务相关的。防漂移的本质不是「放不下」，而是「让有效信息的浓度保持高位」。
