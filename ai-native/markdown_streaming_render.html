概览

流式 Markdown 渲染的本质不是"更快地解析"，而是"少解析"——只对新增片段做解析…

流式 Markdown 渲染的本质不是"更快地解析"，而是"少解析"——只对新增片段做解析，已完成的块永不触碰，从而将复杂度从 O(n²) 压回 O(n)。

01

全量解析的 O(n²) 灾难

大模型对话场景中，服务端以 SSE （Server-Sent Events）逐 token…

大模型对话场景中，服务端以 SSE（Server-Sent Events）逐 token 推送 Markdown 文本，前端每收到一个 chunk（通常 1-5 字符）就触发一次渲染。传统方案直接把累积文本丢给 marked 或 markdown-it 做全量解析——每次都从第 1 个字符扫到最后 1 个字符。

复杂度分析

假设一次完整回复共 N 个字符、每次收到 K 个字符（即 N/K 次 chunk），那么：

总解析量 = K + 2K + 3K + ... + N = K × (1+2+...+N/K) = O(N²/K) ≈ O(N²)

当 N = 20000 字符（约 20KB 回复，典型的技术文档输出）、K = 5 字符时，全量解析共执行 4000 次解析调用，累计处理约 4000 万字符。实测数据表明，在 marked 引擎下这一过程的总耗时为 1.6-5.7 秒，且后期每次 chunk 的解析耗时呈线性增长，直接导致打字机效果从流畅逐渐退化为卡顿，最终页面冻结。

O(n²) 不是"慢一点"，而是"越长越慢"的加速恶化——20KB 的回复让主流方案直接不可用，这在长代码生成、技术文档问答场景中极为常见。

生产案例：某 AI 编程助手产品上线初期使用 react-markdown 做流式渲染。当模型输出超过 15KB 的代码解释文档时，用户反馈"打字机效果在前 30% 还正常，后半段几乎停滞，最后 5 秒才一次性刷出"。性能监控显示：第 3000 个 chunk 的解析耗时已达 42ms（远超 16ms/帧），主线程阻塞率 78%，页面 FPS 降至 4-8。切换到增量解析方案后，同场景 FPS 稳定在 58-60，格式崩溃率从 12% 降至 0.3%。
02

增量解析：O(n²) → O(n) 的核心引擎

增量解析的核心思想极其简洁： 已完成的块不再触碰，只解析新到达的片段

增量解析的核心思想极其简洁：已完成的块不再触碰，只解析新到达的片段。 Incremark 是这一方案的典型实现，它将每个顶层 Markdown 元素（段落、标题、代码块、列表）视为一个独立的 Block，并引入两态生命周期管理。

Block 两态生命周期

状态含义行为何时转换
Pending正在流式接收中，内容和类型都可能变化每次新 chunk 到达时，仅对该 Block 的文本做微解析检测到语法边界后
Completed已确认完成，后续输入不影响此 Block持久缓存，不再参与解析和重渲染流重置前永久有效

为什么需要 Pending 态？在 Markdown 中，前缀决定类型——当输入 # 时，它可能是标题的开始，也可能只是一段以 # 开头的普通文本。只有收到空格或换行后，类型才真正确定。Pending 态就是用来容纳这种"类型未决"的过渡期。

边界检测规则

边界检测（Boundary Detection）是增量解析的关键——它决定了何时可以将一个 Block 从 Pending 转为 Completed。Incremark 采用启发式规则覆盖三大类边界：

边界类型触发条件示例
简单块边界空行出现，或新标题/分隔线开始段落后遇到空行 → 段落完成
Fenced 块边界检测到匹配的闭合 fence（```）代码块在闭合 ``` 出现前保持 Pending
嵌套块边界缩进回退或引用标记消失列表项缩进减少 → 当前列表完成

引擎维护一个轻量 状态机 来追踪上下文：当前是否在 Fenced Code 中、是否在自定义容器内、嵌套列表栈、引用深度。这些信息帮助引擎在流式过程中精确判断边界。

增量解析把"每次从头读一遍书"变成了"只读新来的那一页"——复杂度与文档总长度无关，只与当前 chunk 大小线性相关。

Benchmark 数据（Incremark 官方）：在 916 行、28912 字符的长文档测试中，Incremark 总耗时 87.7ms，Streamdown 总耗时 1441.1ms（16.4 倍差距）；对比 ant-design-x 快约 7 倍，对比 markstream-vue 快约 28 倍。文档越长，增量优势越明显——100 行文档快 4-6 倍，400 行快 10 倍以上，900 行快 16-65 倍。
03

不完整语法处理：流式场景的语法修复层

流式输出的 Markdown 有一个静态文档不会遇到的问题： 语法永远是"半成品"

流式输出的 Markdown 有一个静态文档不会遇到的问题：语法永远是"半成品"。 一个代码块可能只输出了开头的 ```python 而闭合标记还没到；加粗标记 **重点 的右侧 ** 可能还在下一个 chunk 里；表格的前两行已经到了，分隔行还没来。传统解析器面对这些半截语法，要么渲染出错误的 DOM，要么直接崩溃。

Ant Design X Markdown 提供了一套完整的流式配置 API：通过 streaming.hasNextChunk 告知渲染器是否还有后续内容，incompleteMarkdownComponentMap 将不完整语法类型映射到自定义占位组件。支持的占位类型包括 link、image、heading、table、xml 五种。当 hasNextChunk 最终设为 false 时，所有占位符会被刷新为最终渲染内容。

Streamdown（Vercel 出品）则通过 parseIncompleteMarkdown 属性实现类似能力——在解析阶段就自动修复不完整的语法，例如为未闭合的代码块补上 ```，为未闭合的粗体补上 **。这种方式更激进：它不是"等一等"，而是"先补一个合理的临时版本，等真正内容到了再替换"。

不完整语法处理的核心矛盾是"立即渲染会出错" vs "等太久用户觉得卡"——最佳策略是分类处理：行内语法等一等（开销小），代码块延迟渲染（体验好），结构语法用占位符（视觉不空）。

生产案例：某客服 AI 系统在处理流式表格输出时，由于表格分隔行 |---|---| 总是比表头晚 2-3 个 chunk 到达，未做不完整语法处理的方案在前几个 chunk 时把表头渲染成了普通文本段落，分隔行到达后又突然"跳变"为表格结构，导致用户看到的界面频繁闪烁。引入 table 类型占位符后，表头阶段显示 "表格加载中" 骨架屏，分隔行到达后一次性渲染完整表格，格式跳变投诉从每周 47 件降至 2 件。

占位符设计的关键约束：hasNextChunk 必须最后一个 chunk 设为 false，否则占位符永远不会被刷新为正式内容——这是流式渲染中最常见的配置遗漏。

04

分块渲染：AST 节点级缓存与打字机效果

增量解析解决了"解析慢"的问题，但渲染层如果不做优化，依然会在每次 chunk 到达时重新…

增量解析解决了"解析慢"的问题，但渲染层如果不做优化，依然会在每次 chunk 到达时重新 diff 整棵 DOM 树。分块渲染（Chunked Rendering）的思路是将 AST 按顶层 Block 拆分为独立的渲染单元，每个 Block 维护自己的缓存，只有内容发生变化的 Block 才触发重渲染。

React 生态中的实现

在 React 中，这一机制通过 React.memo 实现：每个 Block 组件接收 AST 节点作为 prop，React 在 props 引用不变时跳过该组件的 reconciliation。由于增量解析保证了 Completed Block 的 AST 节点引用不变，这些组件在整个流式过程中只渲染一次。

Block 类型渲染策略React 缓存方式更新频率
标题 (Heading)一次性渲染memo + 引用比较仅首次
段落 (Paragraph)增量追加文本memo + 文本哈希当前段 Pending 期间
代码块 (CodeBlock)延迟渲染 + 语法高亮memo + 内容相等比较闭合后一次
列表 (List)逐项追加memo + 项数比较新项到达时
表格 (Table)整表渲染memo + 行列哈希分隔行到达后

AST 级打字机效果

BlockTransformer 是 Incremark 在 AST 和渲染层之间插入的一层"动画过滤器"。它将解析的"瞬时结果"转化为"渐进过程"：追踪哪些字符已经被"播放"过，把新增的文本节点包裹为 TextChunk，渲染层对 TextChunk 实现 fade-in CSS 动画。这就是 AST 级打字机——不是逐字符闪烁，而是在 AST 节点粒度上做平滑的逐字显现。

BlockTransformer 还支持"智能跳过"：当用户主动滚动查看历史消息时，跳过动画直接显示完整内容；对图片等非文本节点也直接显示，避免不必要的延迟。

分块渲染让 DOM 操作量从 O(总节点数) 降至 O(变化节点数)——在 10 个 Block 的文档中，如果只有 1 个 Block 在流式更新，DOM 操作量降低 90%。

当前主流的 Markdown 流式渲染方案可分为两大阵营：全量重解析阵营和增量解析阵营。以下从架构、性能、生态三个维度做横向对比。

Incremark 双引擎架构

Incremark 的一个独特设计是 双引擎架构：底层同时支持 marked（极速、流式优化）和 micromark（严格 CommonMark 兼容）两个解析引擎，上层共享同一套增量解析层，产出相同的 mdast（Markdown AST）格式。两个引擎可通过 tree-shaking 按需引入——生产环境选 marked 追求极致性能，需要严格规范兼容时切 micromark。

引擎特点最佳场景
marked（默认）极速、流式优化实时 AI 对话、性能敏感场景
micromarkCommonMark 兼容、丰富插件复杂扩展需求、严格规范合规

Ant Design X 的流式能力演进

Ant Design X Markdown 虽然底层仍基于 marked 做全量重解析（O(n²) 复杂度），但在流式体验层做了大量补偿：支持 enableAnimation 淡入动画、tail 尾部光标（默认 ▋）、debug 面板监控性能。在 Mermaid 图表流式渲染中，还修复了 id 不稳定导致的抖动问题——将模块级 uuid++ 替换为 React useId()，并将 throttle(100ms) 改为 debounce(200ms)，在语法不完整时静默跳过而非抛出错误。

选型决策树：文档通常 < 5KB → 全量方案足够且实现简单；文档经常 > 10KB（长代码/文档生成） → 增量方案是刚需，复杂度收益巨大。

Ant Design X 的 Mermaid 抖动修复是一个经典教训：流式场景中组件 id 必须稳定（useId 而非自增计数器），否则每次重渲染都会卸载旧 DOM 再挂载新 DOM，引起视觉抖动。

综合业界实践，一个生产级 Markdown 流式渲染方案通常是"增量解析 + 分块渲染 + 语法修复"三合一的组合。以下从架构决策到工程细节给出完整指引。

小程序端特殊挑战

小程序端缺乏浏览器原生的 HTML 渲染能力，流式 Markdown 渲染面临额外挑战：格式突变（语法不完整导致渲染错乱）、频繁重解析（无 DOM diff，每次全量重建 WXML 树）、性能损耗（setData 的序列化开销）。蚂蚁团队推出的 @ant-design/x-markdown-mini 专门针对小程序场景做了适配，核心思路是将 AST 转换为小程序组件树而非 HTML 字符串。

  • 对长回复启用增量解析，保证 60fps
  • 为不完整语法配置占位组件（骨架屏）
  • 代码块延迟渲染，闭合后再做语法高亮
  • Mermaid 组件使用稳定 id + debounce
  • 历史消息关闭打字机动画
  • 配置 hasNextChunk 生命周期（最终设为 false）
  • 监控 chunk 解析耗时，超过 16ms 报警
  • 不要对 15KB+ 的文档使用全量重解析
  • 不要忽略不完整语法——它会引发格式跳变
  • 不要用自增计数器做组件 id（流式场景会抖动）
  • 不要在流式过程中做语法高亮（开销大且不稳定）
  • 不要忘记最后一个 chunk 设置 hasNextChunk=false
  • 不要对所有消息都启用 fade-in 动画（影响滚动体验）
  • 不要在 debug 面板开启的情况下部署生产环境

大厂最佳实践的共识：增量解析是性能基石，不完整语法处理是体验保障，分块缓存是渲染加速——三者缺一不可，组合使用才是生产级方案。

Q&A

为什么传统的 marked 或 markdown-it 不适合流式场景？
这两个库是为静态文档设计的——它们假设输入是完整的 Markdown 文本，一次性解析为 AST 或 HTML。在流式场景中，每收到一个 chunk 就要把累积全文传给它们重新解析，导致 O(n²) 的累计复杂度。20KB 的回复在 marked 下需要 1.6-5.7 秒的总解析时间，后期每个 chunk 的解析耗时线性增长，直接导致主线程阻塞、页面冻结。它们本身没有"已完成块缓存"和"边界检测"机制，无法做到增量更新。
增量解析的边界检测会不会误判？比如把未完成的段落错误标记为 Completed？
边界检测采用保守策略——宁可延迟标记，不会提前标记。例如段落只有在遇到空行时才标记为 Completed，如果后续内容紧跟在同一行（没有空行），该段落会一直保持 Pending 态。对于代码块，必须检测到匹配的闭合 ``` 才会标记完成。这种保守策略的代价是某些 Block 的 Pending 期较长（如长代码块），但由于 Pending 态的微解析只处理当前 Block 的文本片段，性能影响极小。
Incremark 的双引擎（marked vs micromark）该怎么选？
marked 引擎是默认选项，特点是极速和流式优化，适合绝大多数 AI 对话场景。micromark 引擎严格遵循 CommonMark 规范，有丰富的插件生态，适合需要严格规范合规的场景（如文档系统、合规审查）。两者共享同一套增量解析层，产出相同的 mdast 格式，切换引擎不需要修改上层代码。通过 tree-shaking 可以只打包使用到的引擎，不会增加额外体积。
Streamdown 的 parseIncompleteMarkdown 和 Incremark 的 Pending/Completed 方案有什么区别？
两者处理不完整语法的哲学不同。Streamdown 采用"积极修复"策略——遇到不完整的语法时，自动补上合理的临时闭合标记（如为未闭合的粗体补上 **），先渲染出一个临时版本，等真正内容到了再替换。优势是用户始终能看到格式化内容，劣势是可能出现短暂的"错误格式"。Incremark 采用"等待确认"策略——不完整的语法暂存缓冲区，不渲染半成品，等语法完整后再一次性渲染。优势是格式永远正确，劣势是在语法闭合前用户看到的是原文或占位符。选择取决于你对"格式正确" vs "即时反馈"的优先级。
流式渲染中 Mermaid 图表为什么会抖动？怎么修复？
抖动的根因是组件 id 不稳定。某些实现使用模块级自增计数器（uuid++）拼接 children.length 来生成 Mermaid 容器的 DOM id。在流式场景中，每次重渲染时 children.length 都在变化，导致 id 变化，React 认为这是一个新组件——先卸载旧 DOM 再挂载新 DOM，Mermaid 创建的 SVG 节点被反复销毁重建，视觉上表现为抖动。修复方案是改用 React 的 useId() 生成稳定 id，确保同一组件实例在多次渲染中 id 不变。同时用 debounce(200ms) 替代 throttle(100ms)，等内容稳定后再渲染图表，进一步减少中间态渲染。
为什么小程序端的流式 Markdown 渲染比 Web 端更困难？
小程序端面临三个 Web 端不存在的约束。第一，缺乏原生 HTML 渲染能力——Web 端可以直接 innerHTML 或 dangerouslySetInnerHTML，小程序端必须将 AST 转换为 WXML 组件树，每次更新都涉及 setData 的序列化开销。第二，无虚拟 DOM diff——Web 端 React 可以精确知道哪些 DOM 节点需要更新，小程序端每次 setData 都是全量传输，频繁调用会导致严重的性能问题。第三，组件嵌套限制——小程序对组件嵌套层数有限制，复杂的 Markdown 结构（如嵌套列表中的代码块）可能超出限制。因此小程序端方案通常需要更激进的节流策略和组件树扁平化优化。
生产环境中如何监控流式渲染的性能？
核心监控指标包括四项。第一，单 chunk 解析耗时——超过 16ms（一帧）就应该报警，这表示解析已经跟不上帧率。第二，主线程阻塞率——通过 Performance API 的 longtask 监控，超过 50ms 的任务即为 long task。第三，FPS——流式过程中应保持在 55fps 以上。第四，内存增长——增量解析方案的内存应基本平稳，全量方案的内存会随文档长度线性增长。Ant Design X 提供了 debug 面板可实时查看这些指标，但务必在生产环境关闭，避免性能开销和信息泄露。
如何为不同长度的回复选择最优渲染策略？
实践中可以按回复长度分三档处理。短回复（<3KB，约占 AI 对话的 60%）使用 react-markdown 或 marked 全量解析即可，每次解析耗时 <5ms，完全不影响体验。中等回复（3-15KB）推荐 Ant Design X 或 Streamdown，它们的流式 API（占位符、动画、tail 光标）能提供良好体验，O(n²) 的开销在可接受范围内。长回复（15KB+，如代码生成、技术文档）必须使用 Incremark 等增量方案，否则后期卡顿不可避免。更精细的做法是动态切换：开始时用全量方案，当累积文本超过阈值时自动切换到增量方案。
