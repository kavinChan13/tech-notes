概览

Agent 死循环的本质：Observation 不够结构化，LLM 不知道是该重试还是换路…

Agent 死循环的本质：Observation 不够结构化，LLM 不知道是该重试还是换路子。修复：让工具返回结构化错误码 + retryable 字段，并通过循环探测中间件在重复行为时注入反思指令。

02

ReAct 死循环：怎么防？为什么会发生？

ReAct = Thought → Action → Observation → 循环 ，直…

ReAct = Thought → Action → Observation → 循环，直到给出最终答案。但线上真实场景中，Agent 跑着跑着就不停了——一直在调同一个工具。

防死循环三板斧

ReAct 循环控制逻辑: 1. 为每个任务设置最大步数，例如 15 步 2. 记录最近几次 Tool + Args 组合 3. 若连续 3 次调用相同动作: -> 判定为重复尝试 -> 停止继续试错 -> 基于已有 observation 做总结回答 4. 若总耗时超过任务超时: -> 立即终止 -> 进入降级或人工接管
防御手段实现说明
最大步数通常 15 步超过强制终止
重复动作检测连续 3 次相同 Tool+Args直接退出循环
整体超时任务级别 60 秒兜底保护

死循环的根因分析

面试官追问"为什么会发生死循环"——层次更深一层：

死循环根因链路:
工具持续失败
LLM 不知道是工具本身的问题
还是参数不对
不断改参数重试
死循环
根因: Observation 不够结构化 · 工具只返回 "失败" 两个字 · LLM 没法判断"该不该重试" · 修复: 结构化错误码 + retryable 字段 · {"error": "RATE_LIMIT", · "retryable": true, · "retry_after": 5}

终止后要做兜底总结——让 LLM 基于已有 Observation 给用户一个"不完美但可用"的答案，而不是抛 500 错误。

03

循环探测中间件：Harness AI 的解决方案

循环探测中间件 （Doom Loop Middleware）本质上是一个"强制中断机制"——…

循环探测中间件（Doom Loop Middleware）本质上是一个"强制中断机制"——在 Agent 和工具之间插入一层监控，当检测到重复行为时强制注入反思指令，打断死循环。

三步机制

步骤实现效果
阈值监控记录文件修改次数，超限触发中断（N=10 次）量化检测，不依赖主观判断
强制提示注入"重新审视整体架构"的强干预指令给模型一个"换思路"的机会
非强制转向仅提供反思机会，不保证模型一定改变方向保持 Agent 自主性

为什么是"非强制"转向？

  • 保护合理操作：Agent 可能确实需要修改同一文件 10+ 次来完成复杂重构
  • 尊重自主决策：Agent 可能已有正确反思，只是需要一次"提醒"而非"命令"
  • 更高成功率：生产数据显示 68% 的 Agent 在反思后自主选择正确策略，比强制转向成功率更高

阈值 N=10 怎么确定？

阈值问题后果
太小（N=3）正常迭代也会触发"假阳性"率高，打断正常工作流
太大（N=30）浪费大量 Token 才触发"假阴性"导致损失扩大
推荐（N=10）基于正常任务分布的 P9595% 正常任务不触发，只有异常才触发

生产效果

指标部署前部署后改善
死循环率12%3%↓ 75%
死循环检出率—96%—
反思后切换策略率—68%—
月均 Token 浪费$3,200$180↓ 94%
Build to Delete 设计哲学：循环探测中间件是临时支架，不是永久方案。当模型能力足够强不再陷入死循环时，这层中间件就应该被删除。GPT-5 测试中，中间件触发频率已降低 75%，说明护栏可以逐步退场。

目标漂移：Agent 越跑越偏

用户问"帮我查一下上季度销售额，然后看看同比怎么样"，Agent 查完 Q1 数据后，LLM…

真实案例

用户问"帮我查一下上季度销售额，然后看看同比怎么样"，Agent 查完 Q1 数据后，LLM 在 Observation 里看到一堆数据表，思路就跑偏了——开始自己加戏，去查"各品类明细"、"头部客户排名"，结果跑了 30 步才意识到用户只要同比。

两层治理方案

目标漂移治理:

第一层: 每步目标对齐
    系统提示词固定放 "当前目标：{original_goal}"
    每一次 Thought 前 LLM 都要复述一遍目标

第二层: 中途反思机制
    每 5 步触发一次自检:
    "我现在做的事情是否还在解决最初的问题？"
    不是 → 强制回到主线

效果:
    漂移从 30 步才发现 → 5 步内纠正

最关键的信号：当被问"踩过什么坑"时，想听的是故事+数据+解决，不是复述八股文。要能说出具体数字（Token 从多少降到多少、延迟阈值怎么定的）。

  • 错误信息包含原因+建议操作（帮助 Agent 自纠错）
  • 设置最大重试次数 + 退避策略（防死循环）
  • 部署循环探测中间件（阈值 N=10，非强制反思）
  • 终止时做兜底总结（给用户"不完美但可用"的答案）
  • 组合使用缓存/压缩/异步降低 60-80% 成本
  • Build to Delete：模型能力进步后逐步退场护栏
  • 不要只返回"失败了"（Agent 会无限重试同样操作）
  • 不要在循环内累积全量上下文（Token 爆炸）
  • 不要忽略 429 限流信号（可能被封号）
  • 不要用固定延迟重试（应指数退避 + 抖动）
  • 不要强制中断 Agent（破坏自主性，用非强制反思）
  • 不要依赖永久护栏（掩盖模型本身问题）

Q&A

Agent 为什么会陷入死循环？怎么从根本上解决？
表层防御：最大步数(15步)、重复动作检测(连续3次相同Tool+Args退出)、整体超时(60秒)。根因分析：Observation 不够结构化——工具只返回"失败"，LLM 无法判断该重试还是换路子。修复：工具错误要带结构化错误码和 retryable 字段，如 {"error": "RATE_LIMIT", "retryable": true, "retry_after": 5}。兜底：退出后让 LLM 基于已有 Observation 做总结，给用户可用答案而不是 500。
什么是循环探测中间件？和三板斧有什么区别？
循环探测中间件是 Harness AI 提出的进阶方案，在 Agent 和工具之间插入监控层。三步机制：(1) 阈值监控——记录文件修改次数，超限（N=10）触发中断；(2) 强制提示——注入"重新审视整体架构"的反思指令；(3) 非强制转向——仅提供换思路机会，不强制改变方向。与三板斧的区别：三板斧是"硬终止"（超过步数直接退出），中间件是"软干预"（注入反思但保持自主性）。生产数据：检出率 96%，68% 的 Agent 在反思后成功切换策略，Token 浪费从月均 $3,200 降至 $180（降幅 94%）。
Build to Delete 设计哲学是什么？
Build to Delete 意味着工程护栏是临时支架而非永久方案。核心逻辑：(1) 承认模型不完美，通过工程补丁提升短期成功率；(2) 模型能力在持续进步，护栏应逐步退场；(3) 过度依赖护栏会掩盖模型本身的问题。生产验证：GPT-5 测试中死循环率从 12% 降至 3%，中间件触发频率降低 75%，说明护栏可以逐步退场。
Agent 目标漂移怎么治理？
两层方案：(1) 每步目标对齐——系统提示词固定放"当前目标：{original_goal}"，每次 Thought 前 LLM 复述目标；(2) 中途反思机制——每 5 步触发自检"是否还在解决最初的问题"，偏离就强制回主线。实测从 30 步才发现漂移到 5 步内纠正。
死循环和目标漂移有什么关系？
死循环是"急性发作"——完全卡在某一步无法前进；目标漂移是"渐进式"——逐渐偏离原始目标。共同根因：上下文窗口被无关/重复信息占据，Agent 无法"跳出当前视角"重新审视全局。区别：死循环需要"打断"（注入反思），目标漂移需要"纠偏"（拉回目标）。两者的共同解决方案都依赖外部干预机制——Agent 自身无法意识到问题。
线上 Token 爆炸怎么处理？
两件事：(1) 工具输出截断——超 2000 token 的结果先做摘要再进上下文，原始数据只给 reference_id；(2) 模型路由——简单子任务（格式化金额、判断意图）用小模型，复杂推理才用 Opus。整体成本降约 60%。配合 Tracing 做监控，单请求 Token p99 超 1 万就告警。
阈值 N=10 设太小或太大会怎样？
N=10 是基于正常任务分布 P95 的经验值。太小（N=3）：正常迭代也会触发，"假阳性"率高，打断正常工作流。太大（N=30）：浪费大量 Token 才触发，"假阴性"导致损失扩大。确定方法：(1) 统计正常任务的修改次数分布；(2) 将阈值设在 P95 附近；(3) 定期根据模型能力调整（Build to Delete）。
