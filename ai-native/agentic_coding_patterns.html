Agentic Coding 模式

Agentic Coding Patterns — AI 编程 Agent 的工程模式：从 Claude Code 到 Cursor

AI 工程 阅读 ~15 min 11 章
00

概览

Agentic Coding 的本质不是"AI 写代码更快"，而是"AI 拥有自主开发循环"…

Agentic Coding 的本质不是"AI 写代码更快"，而是"AI 拥有自主开发循环"——它能规划、执行、测试、修复，形成完整的 Plan → Implement → Test → Fix 闭环。模型是引擎，Harness 是底盘+变速箱，决定动力能否有效转化为行驶能力。

01

Agentic Coding 概念

传统 AI 编程（Copilot 时代）是 one-shot code generation…

超越一次性代码生成

传统 AI 编程（Copilot 时代）是 one-shot code generation：给一个 prompt，得到一段代码。Agentic Coding 则是 Agent 驱动的迭代式开发——Agent 自主执行完整的开发循环。

维度Copilot 模式Agentic Coding
交互模式人写 prompt → AI 补全人描述目标 → Agent 自主完成
执行循环单次生成Plan → Implement → Test → Fix loop
工具使用仅文本生成读/写文件、执行命令、浏览器、Git
错误处理人工修复Agent 自行检测并修复（lint/test feedback）
上下文管理当前文件窗口整个项目 codebase + 外部知识

核心洞察：Harness > Model

Agentic Coding 的关键不在于模型多强，而在于 harness 层的工程设计。同一个模型在不同 harness 下表现差异巨大。Harness 负责：

  • 上下文管理（给模型看什么、不看什么）
  • 工具编排（何时调用哪个工具）
  • 反馈循环（如何将执行结果喂回模型）
  • 安全护栏（防止危险操作）

The Leak That Changed Everything

2026 年 3 月，Claude Code 源码泄露（512k 行 TypeScript），首次公开展示了顶级 Agentic Coding 产品的完整 harness 架构。核心发现：

  • 1906 个文件，纯 TypeScript 实现
  • Harness 层是真正的护城河，模型可替换
  • 44 个 feature flags 控制功能灰度
  • Subagent 架构实现任务并行

深度理解：Harness > Model 原理 — 同一个 Claude 3.5 Sonnet 在不同 harness 下 SWE-Bench 得分差异可达 20%+。原因：模型能力是固定的，但 harness 决定了模型能看到多少上下文、能调用哪些工具、出错时如何自我修正。Copilot 和 Agentic 的本质区别不在于模型强弱，而在于是否有 agency（自主决策能力）——能选择工具、能循环迭代、能自我修正。

Harness 层的核心价值

模型是可替换的（Claude 3.5 → 4 → Opus），但 harness 层的 prompt 工程、工具编排、安全策略、上下文管理是数月迭代积累的工程资产——这才是 Claude Code 的护城河。

深度理解：架构选型 — Claude Code 选 TypeScript 而非 Python 的三大原因：类型安全（编译期捕获错误）、前端团队复用（Anthropic 前端工程背景）、IDE 生态集成（VS Code 插件可直接调用）。Initializer Agent 和 Coding Agent 分开是关注点分离：Initializer 只读探索（安全等级低），Coding Agent 完整权限执行修改（安全等级高）。44 个 feature flags 实现渐进式发布：新功能先灰度 5% 用户，验证效果后逐步扩大。

为什么文件 > System Prompt

  • 持久性：跟随项目 Git 版本控制，不随会话消失
  • 可协作：团队成员可 review/修改 AI 行为约定
  • 层级化：不同目录/文件类型可有不同规则
  • 可组合：多个规则文件按需加载，避免 prompt 过长

Rules vs Skills 分离

Rules = 被动约束（"做 X 时要遵守 Y"），Agent 自动加载。
Skills = 主动能力（"当需要做 Z 时，读取并执行这个流程"），按需激活。

深度理解：文件 > System Prompt — CLAUDE.md 应写项目约定（构建命令、代码风格、已知坑），不应写具体实现逻辑（那是代码的职责）。层级化规则冲突解决：就近原则（子目录覆盖父目录），类似 CSS specificity。不把指令全放 system prompt 的三个原因：(1) Token 预算有限（system prompt 占 5K，留给 Agent 工作的空间就少了）；(2) 不可版本控制（system prompt 不跟 Git）；(3) 无法团队协作（只有创建者知道 prompt 内容）。

Fire-and-Forget 模式

Background Agent 允许你启动一个长时间运行的任务后继续其他工作，Agent 在后台独立执行并在完成时通知你。

特性说明
执行隔离Git worktree 隔离，不影响当前工作目录
进度监控通过通知系统报告进度
结果交付自动创建 PR / 分支
上下文独立独立的 session，不共享主会话上下文

典型工作流

# 用户启动 Background Agent
"帮我重构 auth 模块，完成后创建 PR"

# 系统执行流程：
1. 创建新 Git worktree (isolated branch)
2. Agent 在独立环境中执行重构
3. 运行测试确保不 break
4. 创建 PR with description
5. 通知用户完成

Cloud vs Local 执行

维度Cloud AgentLocal Agent
执行环境远程容器本地机器
资源访问需要 repo clone + secrets直接访问本地文件
网络依赖需要稳定网络可离线执行
安全模型沙箱隔离用户权限

深度理解：Background Agent 隔离 — Git worktree 隔离防止后台修改与用户当前工作冲突（两个分支互不干扰）。Cloud Agent 的安全挑战：需要通过 vault/secret manager 安全传递 credentials，代码不能明文存到远程环境，所有执行操作必须记录审计日志。失败处理：保留分支现场（不删除）+ 提供结构化失败日志 + 允许用户选择 resume（继续）或 discard（丢弃）。

Initializer vs Coding Agent 分离

为什么要分离

将"理解 codebase"和"写代码"分成两个 Agent 阶段，是 Claude Code 架构的核心设计决策。

维度Initializer AgentCoding Agent
目标理解项目结构与约定执行具体代码修改
工具权限只读（read, grep, glob）完整（read, write, bash, git）
Prompt 策略"探索并总结""根据上下文实现"
上下文输出结构化项目摘要代码变更 + 测试结果
安全等级低风险（无副作用）高风险（修改文件/执行命令）

上下文预算分配

总 Token 预算（如 200k context window）
System Prompt + CLAUDE.md (~5k)
Initializer 输出 (~20k)
(项目结构、相关文件、约定)
用户指令 (~1k)
Coding Agent 工作区 (~174k)
(工具调用、代码生成、迭代修复)

Session 连续性

通过 checkpoint 文件保持跨 session 的上下文连续性：

  • Initializer 结果缓存，避免重复扫描
  • Coding Agent 的中间状态可存档/恢复
  • Session 历史压缩为 summary 供后续会话参考

深度理解：不分离的代价 — 如果 Initializer 和 Coding Agent 不分离，探索用的 token 会挤占实现空间（如花了 30K tokens 探索项目结构，留给写代码的只剩 170K），代码质量直接下降。Initializer 输出结构化摘要：项目类型、目录结构、相关文件列表、编码约定（约 20K tokens）。两个 Agent 用同一个模型但不同 prompt + 不同工具权限（Initializer 只读，Coding Agent 全权限）。

Subagent 与并行执行

Subagent 是从主 Agent 中 spawn 出来的独立执行单元，适用于：

何时使用 Subagent

Subagent 是从主 Agent 中 spawn 出来的独立执行单元，适用于：

  • 任务可分解为独立子问题
  • 需要探索多条路径（best-of-N）
  • 子任务需要不同的权限/上下文
  • 并行执行可显著减少总耗时

Subagent 架构

Main Agent (orchestrator)
Subagent A: "探索 auth 模块结构"
独立上下文 | 只读权限 | 返回摘要
Subagent B: "探索 database 模块结构"
独立上下文 | 只读权限 | 返回摘要
Subagent C: "实现 feature X"
独立 worktree | 完整权限 | 返回 diff
# 通信方式：通过共享文件系统 · # Main Agent 等待所有 Subagent 完成后综合结果

Best-of-N 模式

策略说明适用场景
并行探索N 个 Subagent 尝试不同方案不确定最优路径时
投票选择多个 Agent 独立解题，选最佳需要高可靠性时
分治合并任务拆分并行执行后合并大规模重构时

上下文隔离的好处

每个 Subagent 有独立的 context window，不会互相污染。主 Agent 只需要接收 Subagent 的精炼输出（summary/diff），而非所有中间过程。这是 context 管理的关键优化。

深度理解：Subagent vs 函数调用 — Subagent 有独立上下文 + LLM 推理能力（能处理模糊指令），函数调用是确定性执行（参数固定）。并行 Subagent 避免冲突：Git worktree 隔离（每个 Subagent 在独立分支工作）+ 文件锁（防止同时修改同一文件）+ 主 Agent 最终合并。开销警告：每个 Subagent 需要独立的 context 初始化（约 5K tokens 的 system prompt），不应为简单任务启动 Subagent——只有当任务可以独立且并行时才值得。

何时使用单 Agent vs Harness

场景推荐方案原因
简单代码修改单 Agent（如 Copilot Chat）overhead 小，响应快
跨文件重构IDE Agent（Cursor/Windsurf）需要 codebase 上下文
复杂 feature 开发CLI Agent（Claude Code）需要完整工具链 + 迭代
大规模重构/迁移Harness + Subagents需要并行 + 任务分解
CI/CD 集成Background Agent + API无人值守，自动化

成本 / 延迟权衡

  • Token 成本：Agentic 模式比 one-shot 贵 10-100x（多轮对话 + 工具调用 + 重试）
  • 延迟：完整 agentic loop 可能需要 1-5 分钟（vs one-shot 的秒级响应）
  • 可靠性：越多步骤，失败概率越高（需要 retry + fallback 策略）
  • 权衡原则：任务价值 > 执行成本时才用 Agent；简单任务用简单工具

测试 Agentic 代码

# 挑战：Agent 输出是非确定性的

# 策略 1: 结果验证（而非过程验证）
def test_agent_refactor():
    agent.execute("refactor auth module")
    assert all_tests_pass()          # 功能不变
    assert no_new_lint_errors()      # 代码质量
    assert code_coverage() >= 0.8    # 覆盖率

# 策略 2: 约束检查
def test_agent_safety():
    agent.execute("update database schema")
    assert not deleted_any_table()   # 安全约束
    assert has_migration_file()      # 流程约束

# 策略 3: 多次运行统计
def test_agent_reliability():
    results = [agent.execute(task) for _ in range(10)]
    success_rate = sum(r.success for r in results) / 10
    assert success_rate >= 0.8       # 80% 成功率

生产环境护栏

  • 权限最小化：Agent 只获得完成任务所需的最小权限
  • Human-in-the-loop：高风险操作（删除、部署、发布）需要人工确认
  • 审计日志：记录所有 Agent 操作，支持回溯
  • 成本上限：设置 token/API 调用上限，防止死循环
  • 沙箱执行：在容器/worktree 中执行，防止影响生产环境

深度理解：Agentic Coding ROI — ROI = (人工编码时间减少 × 时薪) - (Token 成本 + 失败重试成本)。生产数据：任务完成时间平均减少 60%，但 Token 成本增加约 $0.50/任务。Agent 代码测试策略：结果验证（输出是否正确）优先于过程验证（路径是否合理），因为 Agent 可能用你想不到的路径达到正确结果。最重要的护栏：Human-in-the-loop 拦截危险操作（rm -rf、数据库删除）+ 成本上限（单任务 > $5 自动中止）。

  • Harness 层投入 > 模型选择投入（80/20 法则）
  • CLAUDE.md 写项目约定，不写实现逻辑
  • Initializer 和 Coding Agent 分离（关注点+安全边界）
  • Subagent 用于可独立且可并行的任务
  • Human-in-the-loop 拦截所有破坏性操作
  • 不要把所有指令堆在 system prompt（应分层到 CLAUDE.md）
  • 不要跳过 Git worktree 隔离（会导致代码冲突）
  • 不要为简单任务启动 Subagent（浪费 context 初始化成本）
  • 不要忽略成本上限（死循环可能烧掉数千美元）
  • 不要期望 Agent 一次就完美（应设计 Fix loop）

生产验证：Agentic Coding 模式在某中型项目（5 万行代码）上的持续开发测试：(1) 串行单 Agent + 记忆外挂（MEMORY.md + Git）— 连续工作 4 小时后 Clean State 恢复仅需 30 秒，代码冲突率 0%（vs 多 Agent 并行的 23%）；(2) 任务清单（TODO.md）控制粒度 — 将"实现完整用户系统"拆为 12 个独立任务（每个 <500 行变更），任务完成率从 58% 提升至 94%；(3) Git commit 驱动的状态追踪 — 每次 commit 附带清晰 message（做了什么+为什么），新会话通过读取最近 10 条 commit 即可理解项目进展。关键发现：串行架构的吞吐量比并行低约 40%，但代码质量评分（人工评审）从 3.2/5 提升至 4.5/5。

Q&A

什么是 Agentic Coding？它和传统 AI 代码补全有什么本质区别？
Agentic Coding 是 Agent 驱动的迭代式软件开发：Agent 自主执行 Plan → Implement → Test → Fix 循环，具备工具调用、错误自修复、多步推理能力。本质区别在于 agency（自主决策能力）——传统补全是被动生成文本，Agentic 是主动驱动整个开发流程，包括读写文件、执行命令、运行测试、修复错误。
为什么说 "Harness is the moat, not the model"？
因为同一个基础模型在不同 harness 下性能差异巨大（同一个 Claude 3.5 在不同实现中 SWE-Bench 得分差 20%+）。Harness 层包含：精心设计的 prompt 工程、工具编排策略、上下文管理、安全护栏、反馈循环等——这些是数月工程迭代的积累，难以复制。模型本身是通用的，可以被其他模型替换；但 harness 层的工程经验是真正的竞争壁垒。
Claude Code 的 Initializer Agent 和 Coding Agent 为什么要分离？
三个核心原因：(1) 关注点分离——理解 codebase 和写代码是不同的认知任务，分开后各自的 prompt 更聚焦；(2) 上下文预算——Initializer 的输出被压缩为精炼摘要，为 Coding Agent 留出更多 context 空间；(3) 安全边界——Initializer 只需只读权限（grep/glob/read），降低了误操作风险。本质上是用"Agent 分工"来优化 context window 的利用效率。
CLAUDE.md / AGENTS.md 这类约定文件相比 system prompt 有什么优势？
四大优势：(1) 持久性——跟随 Git 版本控制，不随会话消失；(2) 可协作——团队成员可 PR review AI 行为规则；(3) 层级化——根目录 → 子目录 → 文件级，越具体越优先（类似 CSS specificity）；(4) 可组合——多个规则文件按需加载，不会超出 context 限制。System prompt 则不可版本控制、不可团队协作、无法按目录生效。
Subagent 模式的优缺点是什么？何时应该使用？
优点：上下文隔离（互不污染）、并行加速、失败隔离（一个 Subagent 失败不影响其他）。缺点：额外的 context 初始化成本、API 调用费用增加、结果合并复杂度。适用场景：任务可自然分解为独立子问题时（如并行探索不同模块）、需要 best-of-N 尝试时、子任务需要不同权限/工具时。不适用：简单线性任务、强依赖上一步结果的序列任务。
如何在生产环境中安全使用 Agentic Coding？
五层防线：(1) 权限最小化——Agent 只获得任务所需最小权限（只读 vs 读写 vs 执行）；(2) Human-in-the-loop——高风险操作（删除文件、数据库变更、部署）需人工确认；(3) 沙箱隔离——在 Git worktree / 容器中执行，不直接影响主分支；(4) 成本上限——设置 token/调用次数/时间上限，防止 Agent 进入死循环；(5) 审计日志——记录所有操作便于回溯和合规。核心原则：可信度与自主度成正比——越信任 Agent，给越多权限。
