Skill 设计与架构：从设计到运行

Skill Design + Architecture — 从"为什么不被调用"到"渐进式披露 + 三层加载 + 双 Hook 自动激活"

AI 工程 阅读 ~6 min 12 章
00

概览

Skill 不是 Prompt，而是可组合的能力工具包

Skill 不是 Prompt，而是可组合的能力工具包。好的 Skill 需要解决三个层次：被 Agent 发现和理解（设计层）、灵活复用（架构层）、有状态执行（技术层）。本文从"怎么写"讲到"怎么运行"，覆盖 Skill 的完整生命周期。

01

为什么 Skill 不被调用

根因：开发者错误地将 Skill 当作 Prompt 编写，而非构建可组合的能力工具包

根因：开发者错误地将 Skill 当作 Prompt 编写，而非构建可组合的能力工具包。

层次问题表现解决方向
内容层Agent 无法发现和理解 SkillDescription 太泛，触发条件不明确写触发条件 + 反触发条件
结构层Skill 无法灵活复用单文件臃肿，缺少模块化文件夹式组织 + 三层加载
技术层Skill 无法有状态执行每次执行从零开始状态持久化 + 双 Hook
核心认知转变：不要教 Agent 怎么写 Python（它比你更懂），要告诉它"我们团队的数据库密码在 Vault 的 team-prod 路径下"——只补充模型不知道的 Gotchas。
02

Description 写法与反触发条件

Anthropic 官方建议：好的 Description 不仅写"什么时候用"，还要写"什…

写触发条件，不写功能摘要

错误做法（功能摘要）正确做法（触发条件）
"帮助部署 AWS 服务""用户说 deploy/babysit 时触发"
"管理数据库""当需要执行 SQL 迁移或检查表结构时使用"
"生成报告""用户要求 weekly report 或 sprint summary 时触发"

反触发条件（When NOT to use）

Anthropic 官方建议：好的 Description 不仅写"什么时候用"，还要写"什么时候不用"：

  • 触发条件："当用户要求生成 PDF 报告时"
  • 反触发条件："不要用于简单的文本输出或 Markdown 渲染"

反触发条件防止 Skill 在不相关场景被误触发，减少噪声。

03

渐进式披露 vs RAG

为什么 Skill 用渐进式披露而不是 RAG

为什么 Skill 用渐进式披露而不是 RAG？两者都是"按需加载信息"，但适用场景不同：

维度渐进式披露（Skill）RAG 检索
信息类型结构化知识（SOP/脚本/配置）非结构化文档（FAQ/知识库）
检索方式确定性加载（元数据匹配 → 加载正文）语义检索（embedding 相似度）
准确性高（精确匹配，无误召回）中（语义近似，可能召回不相关内容）
更新方式直接修改文件需重新 embedding + 索引
适用规模小规模（几十个 Skill）大规模（数万篇文档）
选择原则：团队特有的 SOP/脚本/配置 → 用 Skill（渐进式披露）；大规模知识库/FAQ → 用 RAG。两者可以互补：Skill 中引用 RAG 结果作为上下文。
04

三层加载结构

层级文件大小内容加载时机Token 成本
Level 1 元数据YAML 头部技能名称 + 用途 DescriptionAgent 启动时预加载~100 tokens
Level 2 正文Markdown 主体核心 SOP 逻辑与操作指南技能被触发时加载<5k tokens
Level 3 附录forms.md / scripts详细配置与可执行代码按引用需求实时读取理论无限
动态触发流程:
1. 用户请求 → Agent 从 Level 1 元数据匹配 Skill
2. 加载 Level 2 正文（核心 SOP）
3. 正文引用 Level 3 附录（按需读取 forms.md / 执行脚本）
4. 脚本执行 → 仅返回结果摘要
5. Agent 综合生成最终响应
关键设计：Agent 启动时只加载所有 Skill 的元数据（每个 ~100 tokens），50 个 Skill 也只需 5k tokens。只有被触发的 Skill 才加载正文。

文件夹解剖

Anthropic 官方推荐的 Skill 目录结构：

Anthropic 官方推荐的 Skill 目录结构：

my-skill/
SKILL.md # 核心指令文件（< 500 行）
scripts/ # 可执行脚本
process.py # Python 处理脚本 · validate.sh # Shell 验证脚本
references/ # 参考文档
api-docs.md # API 文档 · examples.md # 示例
assets/ # 静态资源
templates/ # 输出模板
config.json # 配置文件（渐进式配置）

三个目录的职责分离

目录内容加载方式典型用途
scripts/可执行代码Agent 调用执行数据处理、API 调用、验证
references/参考文档按需读取API 文档、编码规范、示例
assets/静态资源引用使用模板、图片、配置文件
config.json 渐进式配置：首次使用 Skill 时询问用户偏好（如输出格式、目标路径），写入 config.json，后续直接复用。避免每次都问同样的问题。

双 Hook 自动激活

Langfuse 提出的 Skill 自动激活机制：通过两个 Hook 在正确时机触发 Sk…

Langfuse 提出的 Skill 自动激活机制：通过两个 Hook 在正确时机触发 Skill：

双 Hook 架构
Hook 1: UserPromptSubmit（用户输入时触发）
扫描用户 Prompt → 匹配 Skill 的触发条件
命中 → 将 Skill 正文注入上下文
未命中 → 正常处理
Hook 2: PreToolUse（工具调用前触发）
检查即将调用的工具 → 是否有对应 Skill
命中 → 注入 Skill 的 best practices
未命中 → 正常执行
Hook触发时机作用示例
UserPromptSubmit用户发送消息时匹配并注入 Skill 正文"生成报告" → 注入报告 Skill
PreToolUse工具调用前注入工具的最佳实践调用 search → 注入搜索技巧

skill-rules.json 触发模式

通过配置文件定义触发规则，支持关键词匹配、正则匹配、意图匹配：

// skill-rules.json 示例
{
  "report-generator": {
    "triggers": ["weekly report", "sprint summary", "generate report"],
    "pattern": "/report|summary/i",
    "anti_triggers": ["markdown", "plain text"]
  },
  "deploy-helper": {
    "triggers": ["deploy", "babysit", "release"],
    "pattern": "/deploy|release|babysit/i"
  }
}
07

三级执行：block / suggest / warn

Skill 被触发后，执行级别决定 Agent 的行为自由度：

Skill 被触发后，执行级别决定 Agent 的行为自由度：

级别行为适用场景示例
block强制阻止，必须按 Skill 规则执行高危操作（部署/删除）"必须先通过 CI 才能部署"
suggest建议方案，用户可覆盖常规操作"建议使用这个 SQL 模板"
warn仅提示风险，不阻止低风险操作"注意：这会覆盖现有文件"
选择原则：不可逆操作 → block；常规操作 → suggest；低风险操作 → warn。过度使用 block 会让 Agent 变得"太保守"，用户需要反复确认。
08

认知与执行分离

Skill 设计的重要原则：将"知道什么"（认知）和"做什么"（执行）分离：

Skill 设计的重要原则：将"知道什么"（认知）和"做什么"（执行）分离：

层内容存放位置示例
认知层规则、最佳实践、GotchasSKILL.md 正文"数据库查询必须加 LIMIT"
执行层可执行脚本、API 调用scripts/ 目录process.py, validate.sh

为什么要分离？

  • 认知层变化频率低（规则稳定），执行层变化频率高（脚本迭代快）
  • 认知层可以被多个执行层共享（同一套规则，不同脚本）
  • 执行层可以独立测试（脚本单测不影响认知逻辑）
09

500 行规则与 SKILL.md 模板

Anthropic 官方建议 SKILL

Anthropic 官方建议 SKILL.md 不超过 500 行。超过时需要拆分。

标准模板

--- name: "my-skill" description: "当用户说 X/Y 时触发。不用于 Z。" --- # My Skill ## 背景 - 这个 Skill 解决什么问题 - 团队踩过的坑（Gotchas） ## 操作流程 1. Step 1: 做什么 2. Step 2: 做什么 3. Step 3: 做什么 ## 约束 - 必须遵守的规则 - 反模式（不要做什么） ## 引用 - [API 文档](references/api-docs.md) - [执行脚本](scripts/process.py)
超过 500 行的处理：将详细内容拆到 references/ 目录，SKILL.md 只保留引用链接。Agent 需要时按需读取。

Q&A

Description 为什么写触发条件而不写功能摘要？
Agent 选择 Skill 时先看 Description。功能摘要（"帮助部署 AWS"）太泛，Agent 无法判断何时触发。触发条件（"用户说 deploy/babysit 时触发"）精确告诉 Agent 匹配规则。加上反触发条件（"不用于手动部署"），进一步减少误触发。生产数据：Description 从功能摘要改为触发条件后，匹配准确率从 45% 提升至 92%。
渐进式披露和 RAG 有什么区别？什么时候用哪个？
渐进式披露是确定性加载（元数据匹配 → 加载正文），适合结构化知识（SOP/脚本/配置），准确率高但规模有限。RAG 是语义检索（embedding 相似度），适合大规模非结构化文档（FAQ/知识库），但有误召回风险。选择原则：团队特有的 SOP/脚本 → Skill；大规模知识库 → RAG。两者可互补：Skill 中引用 RAG 结果作为上下文。
三层加载结构的 Token 成本怎么控制？
Level 1（元数据）每个 Skill ~100 tokens，50 个 Skill 预加载只需 5k tokens。Level 2（正文）只有被触发的 Skill 才加载，控制在 <5k tokens。Level 3（附录）按需读取，脚本只返回结果摘要而非全文。关键：Agent 启动时只加载元数据（不是全文），触发时才加载正文（不是所有 Skill），引用时才读取附录（不是一次性加载）。
双 Hook 架构中，两个 Hook 各解决什么问题？
UserPromptSubmit 解决"用户说了什么 → 匹配哪个 Skill"，在用户发送消息时触发，扫描 Prompt 匹配触发条件。PreToolUse 解决"Agent 要调用什么工具 → 注入什么最佳实践"，在工具调用前触发。两者互补：前者在对话层面匹配 Skill，后者在执行层面注入最佳实践。例如用户说"生成报告"触发报告 Skill（UserPromptSubmit），Agent 调用 search_docs 时注入搜索技巧（PreToolUse）。
为什么 SKILL.md 要控制在 500 行以内？
三个原因：(1) Token 成本 — 每次触发 Skill 都要加载正文，500 行约 5k tokens，超出则成本过高；(2) 注意力稀释 — Agent 对长文档的注意力递减，500 行内的规则更容易被准确执行；(3) 维护性 — 超过 500 行说明 Skill 职责过多，应拆分为多个 Skill。超出部分放到 references/ 目录，Agent 按需读取。
block/suggest/warn 三级执行怎么选？
按操作风险选择：不可逆操作（部署/删除/支付）→ block（强制阻止，必须按规则执行）；常规操作（生成报告/查询数据）→ suggest（建议方案，用户可覆盖）；低风险操作（格式化/重命名）→ warn（仅提示风险）。过度使用 block 会让 Agent 变得太保守，用户需要反复确认。生产建议：80% 的操作使用 suggest，15% 使用 warn，5% 使用 block。
