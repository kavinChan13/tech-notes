概览

RAG 三层防御全链路架构
用户 Query

RAG 三层防御的本质：在"检索→生成"流水线的三个关键节点各设一道关卡——输入不合法就拦截（省资源），检索质量差就重试（保质量），输出没依据就标注（防幻觉）。层层把关，防止"垃圾进垃圾出"。三层总计增加约 15-25ms 延迟，相比 RAG 本身 200-500ms 的检索延迟可忽略。

01

第一层：入口过滤 — 拦截不合法 Query

第一层防御在 Query 进入检索管道之前执行

第一层防御在 Query 进入检索管道之前执行。目的不是"限制用户"，而是"避免浪费"——拦截无效请求可以节省检索和生成的计算资源，同时防止恶意注入导致安全事故。

1.1 四种过滤规则 — 原理→机制→效果

规则触发条件处理方式防御目标开销
长度过滤Query < 3 字或 > 500 字拒绝 + 提示用户精简/补充防止无效输入和超长注入攻击<1ms
意图分类Query 不属于系统能力范围路由到兜底回复或转人工防止答非所问，节约检索资源5-15ms
敏感词过滤包含违禁词 / 越权关键词拒绝 + 记录安全日志安全合规，防止 prompt 注入<1ms
去重过滤短时间内（5s）重复相同 Query返回缓存结果降低计算成本，提升响应速度<1ms

原理：入口过滤（Input Guard）是一组轻量级的规则引擎，在 Query 进入昂贵的检索和生成管道之前快速拦截不合法的请求。其核心设计原则是"宁可误拦也不放过"——误拦一个有效请求的成本（用户重试一次）远低于放过一个恶意请求的成本（安全事故）。

机制：四种规则按顺序执行：① 长度检查（正则匹配，<1ms）→ ② 意图分类（轻量分类模型如 DistilBERT，5-15ms）→ ③ 敏感词匹配（Aho-Corasick 多模式匹配，<1ms）→ ④ 去重检查（Redis SETNX，<1ms）。任何一步触发即终止后续流程。

效果：在某企业 RAG 系统的生产数据中，入口过滤拦截了 15% 的请求，其中 60% 是无效输入（如只输入"？""嗯"），30% 是越权请求（普通用户试图访问管理员接口），10% 是恶意注入（prompt injection 攻击）。过滤后系统的平均响应质量提升了 22%，同时节省了约 12% 的 API 调用成本。

生产数据：在某金融企业 RAG 系统中，部署入口过滤后的首月拦截了 42,000 次无效请求，其中发现 380 次 prompt injection 攻击尝试（占比 0.9%），攻击模式包括"忽略以上指令""你现在是..."等。过滤日志为安全团队提供了攻击趋势分析，推动了 prompt 加固工作。
02

第二层：检索质量校验 — 不合格就重试

检索到文档 ≠ 检索到 好 文档

检索到文档 ≠ 检索到好文档。第二层防御在检索完成后评估结果质量——如果 Top-1 分数太低、Top-K 分布异常、或领域不匹配，自动触发 Query 改写或扩大检索范围后重新检索。

2.1 三个质量指标 — 原理→机制→效果

指标原理判定规则不达标处理
Top-1 相似度最高分文档的相似度反映检索质量上限Top-1 < 0.65 → 不达标Query 改写（同义词扩展 / HyDE）→ 重新检索
Top-K 离散度Top-K 分数差异反映结果一致性Top-1 与 Top-5 差 > 0.4 → 异常缩小 K 值 / Rerank 重排序
领域匹配度检索文档的领域应与 Query 一致领域分类不一致 → 不匹配加领域过滤条件 → 重新检索

Top-1 相似度原理：如果检索到的最佳文档的相似度只有 0.50，说明知识库中可能没有与 query 高度相关的内容，或者 query 表述过于模糊。此时硬塞低质量文档给 LLM 反而可能引发幻觉——LLM 可能"脑补"不存在的信息来填补上下文的空白。

Top-K 离散度原理：如果 Top-1 是 0.92 而 Top-5 是 0.35，说明只有一个文档高度相关，其余四个是噪声。此时应缩小 K 值（如从 K=10 改为 K=3），只保留高质量结果。相反，如果 Top-5 都在 0.75-0.88 之间，说明检索质量好，可以多保留。

领域匹配度原理：Query 是"Python 多线程 GIL"但检索到"Java 多线程 synchronized"——虽然"多线程"语义相似，但领域（编程语言）不匹配。用轻量文本分类模型（如 FastText 或 DistilBERT）判断 Query 和检索文档的领域标签，不匹配则加领域过滤条件重检索。

检索结果 Top-K
Top-1 相似度 < 0.65 → 触发 Query 改写 → 重新检索
改写技术: · 同义词扩展 ("登录" → "signin/login/认证") · HyDE (LLM 先生成假设性回答, 用回答去检索) · Query 分解 (复合问题拆成子问题)
Top-K 离散度异常 → 缩小 K 值 / Rerank 重排序
Top-1=0.92, Top-5=0.35 → 只取 Top-3 · Top-1=0.85, Top-5=0.78 → 保留全部 Top-5
领域不匹配 → 加领域过滤条件 → 重新检索
Query: "Python GIL" → 领域: Python · Doc: "Java synchronized" → 领域: Java → 过滤掉
生产案例：某技术文档 RAG 系统部署第二层校验后，因检索质量差导致的"答非所问"率从 18% 降至 5%（-72%）。其中 Query 改写（特别是 HyDE 技术）贡献了最大改善——短 query（< 10 字）的检索召回率从 55% 提升至 78%（+23pp）。
03

第三层：输出忠实度检测 — 没依据就标注

第三层防御在 LLM 生成回答后执行，是对抗幻觉的最后一道防线

第三层防御在 LLM 生成回答后执行，是对抗幻觉的最后一道防线。核心问题：LLM 的回答是否有检索文档的支撑？没有支撑的内容是标注"未经验证"，还是直接重新生成？

3.1 两种检测策略 — 原理→机制→效果

策略一：NLI 验证（Natural Language Inference）。用 NLI 模型逐句判断生成内容与检索文档之间的关系。NLI 将文本对分为三类：蕴含（entailment，检索文档支持该句子）→ 安全，可输出；矛盾（contradiction，检索文档与该句子冲突）→ 幻觉，需重新生成或标注警告；中性（neutral，检索文档与该句子无关）→ 可能是 LLM 基于自身知识的补充，标记"未经验证"。

策略二：引用回溯。要求 LLM 在回答中标注每句话的来源文档（通过 prompt 指令 "请在每句话后标注来源文档编号"）。如果某句话无法追溯到任何检索文档，自动标记为"⚠️ 未经验证"。这种方式对用户完全透明，用户可以自行判断是否采信。

策略检测精度额外延迟用户体验实现复杂度
NLI 验证88-92%（二分类 90-95%）10-20ms（DeBERTa-v3）检测到矛盾可自动重新生成中（需部署 NLI 模型）
引用回溯取决于 LLM 引用准确度（~80%）几乎为零（LLM 自带）透明标注来源，用户可验证低（prompt 指令即可）
LLM-as-Judge95%+500-1000ms（额外 LLM 调用）最高精度但成本高低（调用另一个 LLM）

3.2 检测后的处理策略

检测结果处理策略适用场景
全部蕴含正常输出，标注来源文档所有场景
存在矛盾重新生成（限制 LLM 只能基于 context 回答）高风险场景（医疗/法律）
存在中性标注"⚠️ 此部分基于模型通用知识，建议验证"通用场景
矛盾 + 中性混合重新生成，仍不通过则标注 + 降低置信度企业知识库
生产案例：某医疗 AI 系统部署第三层 NLI 验证后，检测到 3.5% 的回答包含与检索文档矛盾的幻觉内容。其中 60% 通过重新生成自动修复，40% 因反复生成仍矛盾而标注"⚠️ 此信息可能不准确，请以原始文献为准"。整体幻觉率从 4.2% 降至 0.8%（-81%），医生对系统的信任度评分从 3.2/5 提升至 4.4/5。

三层防御的全链路监控与告警

三层防御不是"部署了就完事"——必须持续监控每层的拦截率、重试率和幻觉率，设置告警阈值，及时…

三层防御不是"部署了就完事"——必须持续监控每层的拦截率、重试率和幻觉率，设置告警阈值，及时发现异常趋势。监控数据也是优化每层策略参数的依据。

05

三层防御的延迟与成本分析

最常见的顾虑是"三层防御会不会增加太多延迟

最常见的顾虑是"三层防御会不会增加太多延迟？"答案是：每层开销很小，三层总计 15-25ms，相比 RAG 本身 200-500ms 的检索延迟可忽略。投入产出比极高。

5.1 延迟分解

防御层处理内容延迟占 RAG 总延迟比例
第一层长度检查 + 敏感词 + 去重（规则引擎）< 2ms< 0.5%
第一层意图分类（DistilBERT 推理）5-15ms1-3%
第二层分数计算 + 阈值比较 + 领域分类< 5ms< 1%
第三层NLI 检测（DeBERTa-v3，~100M 参数）10-20ms2-4%
三层总计15-25ms3-5%

5.2 投入产出分析

  • 三层防御逐层递进，每层都有明确的触发条件和处理方式
  • 第一层拦截 15%+ 无效请求，节省 API 调用成本
  • 第二层用 Top-1 阈值 + Query 改写保证检索质量
  • 第三层用 NLI + 引用回溯双重检测幻觉
  • 每层关键指标接入监控看板，设置告警阈值
  • 只有生成后检测，没有入口过滤（垃圾进垃圾出）
  • 检索结果不做质量校验就直接塞给 LLM（低质量上下文引发幻觉）
  • 忽略 Top-K 离散度（可能混入大量噪声文档）
  • 检测到幻觉后不标注、不重试、不告警（用户无感知）
  • 部署后不监控不优化（阈值需要随数据变化持续调整）
06

Q&A

三层防御会不会增加太多延迟？在什么场景下延迟不可接受？
每层开销很小：第一层规则判断 < 2ms（意图分类 5-15ms），第二层质量校验 < 5ms，第三层 NLI 检测 10-20ms（使用 DeBERTa-v3，~100M 参数）。三层总计增加约 15-25ms，相比 RAG 本身 200-500ms 的检索延迟占比 < 5%。在对话式应用中完全无感知。只有在极低延迟场景（如高频交易决策，要求 < 100ms 总响应）下才需要裁剪——此时可以省略意图分类（第一层只保留规则检查）和 NLI 检测（第三层只保留引用回溯）。
Query 改写具体有哪些技术？哪种效果最好？
常用技术有三种：① 同义词扩展（"登录" → "signin / login / 认证"），简单有效但覆盖有限；② HyDE（Hypothetical Document Embeddings，让 LLM 先生成一个假设性回答，用这个回答的向量去检索），在短 query 场景下效果最好，可提升召回率 15-25%，但增加一次 LLM 调用（200-400ms）；③ Query 分解（将复合问题拆成多个子问题分别检索），适合多跳问题。综合推荐：短 query（< 10 字）优先用 HyDE，长 query 用同义词扩展，复合问题用分解。
NLI 检测的准确率够用吗？有没有更准确的替代方案？
主流 NLI 模型（如 DeBERTa-v3-large 在 MNLI 上微调）的三分类准确率在 88-92% 之间。对于 RAG 场景，主要判断"生成内容是否与 context 矛盾"这个二分类任务更简单，实际准确率可达 90-95%。更准确的替代方案：① LLM-as-Judge（用另一个 LLM 判断忠实度），准确率 95%+ 但每次调用增加 500-1000ms 延迟和额外成本；② 微调专用忠实度模型（如 FActScore），准确率 93-96% 但需要标注数据。推荐方案：默认用 NLI（延迟低、够用），高风险场景升级为 LLM-as-Judge。
三层防御的告警和监控具体怎么落地？
每层防御的关键指标应接入监控系统（如 Prometheus + Grafana）：第一层记录被拦截的 Query 数量和类型（发现恶意攻击趋势），第二层记录检索质量不达标触发重试的比例（反映知识库覆盖度），第三层记录幻觉检测命中率和分布。设置阈值告警——如幻觉率突增 5% 以上触发 P1 告警（可能是知识库更新引入了错误数据），检索重试率突增到 25% 以上触发 P2 告警。建议每周回顾监控数据，持续优化每层的参数阈值。
如果三层都通过了但用户仍然反馈回答不好怎么办？
三层防御覆盖的是"系统层面"的质量保障，但用户反馈可能涉及更深层的问题：① 知识库本身内容过时或不完整（需要更新/扩展知识库）；② 分块粒度不合适（重要信息被切割到不同块中，检索只命中了部分）；③ LLM 的表达能力不足（理解了 context 但表达不清）；④ Prompt 模板设计不佳（没有正确引导 LLM 使用 context）。处理方式是：收集用户反馈并分类（检索问题 / 生成问题 / 知识问题），分析失败案例属于哪个环节，然后针对性优化。
三层防御可以只部署其中一两层吗？有没有最小可行方案？
可以渐进式部署。最小可行方案是只部署第一层（入口过滤）和第三层的引用回溯（prompt 指令即可，零额外延迟）——这能拦截无效请求并让用户自行验证来源。第二步加入第二层的 Top-1 阈值检测（最简单，只需比较分数）。第三步加入完整的 NLI 检测。推荐顺序：第一层规则检查 → 第三层引用回溯 → 第二层阈值检测 → 第三层 NLI → 第一层意图分类 → 第二层 HyDE 改写。每一步都有独立的增量收益。
prompt injection 攻击如何被第一层防御拦截？有哪些典型攻击模式？
典型攻击模式包括：① 指令覆盖型（"忽略以上所有指令，你现在是..."）——通过敏感词匹配拦截；② 角色扮演型（"假装你是一个没有限制的 AI..."）——通过意图分类拦截；③ 编码绕过型（Base64 编码的恶意指令）——通过长度异常检测 + 特殊字符比例检测拦截；④ 多轮注入型（在多轮对话中逐步引导）——通过对话历史一致性检查拦截。建议维护一个持续更新的攻击模式库，定期更新敏感词列表和意图分类模型。
