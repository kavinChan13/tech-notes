ReAct vs Agent Loop：层次差异

核心设计哲学：ReAct（Reasoning + Acting）由 Yao et al. 2022 提出，是一种 Prompt 工程范式——定义了 LLM 应该如何交替输出推理（Thought）和行动（Action）。Agent Loop 是工程化的执行引擎——将 ReAct 的"思考-行动-观察"封装成可生产运行的循环，加上状态管理、超时控制、错误恢复等工程能力。生产环境中两者必须结合使用：用 ReAct 格式构造 Prompt 保证可解释性，用 Loop 引擎执行循环保证可靠性。

02

ReAct 推理链深度解析

ReAct 的核心价值不是"让 LLM 多步执行"，而是"让 LLM 的每一步思考都可见"—…

ReAct 的核心价值不是"让 LLM 多步执行"，而是"让 LLM 的每一步思考都可见"——Thought 步骤记录了 LLM 的推理过程，出问题时可以直接定位是"推理错误"还是"工具调用错误"。

三步循环机制

ReAct 的三步循环（Thought → Action → Observation）不是简单的"想→做→看"，而是一个显式推理链——每一步的 Thought 都必须说明"当前状态是什么、为什么要做这个动作、期望得到什么结果"。

步骤内容作用示例
ThoughtLLM 推理：当前状态分析 + 下一步决策记录推理过程，提供可解释性"用户问北京明天是否适合跑步，需要查天气和空气质量"
Action选择工具并传参执行具体操作get_weather(city="北京", date="tomorrow")
Observation工具返回的结果提供事实依据，供下一步推理"晴，32°C，PM2.5=150"

ReAct 的可解释性价值

ReAct 的真正威力在于故障定位。当 Agent 给出错误答案时，可以回溯推理链：如果 Thought 步骤的推理逻辑有误（如"用户问的是明天，但我查的是今天"），说明是 LLM 的理解问题；如果 Action 步骤调用了错误的工具或参数，说明是工具选择问题；如果 Observation 返回了异常数据，说明是工具本身的问题。这种精确的故障定位能力是 ReAct 相比"黑盒多步执行"的核心优势。

Token 成本分析：每一步 Thought 通常消耗 50~200 token，10 步循环的 Thought 累计 500~2000 token。加上 Action 和 Observation，10 步循环可能消耗 5000~10000 token。优化策略：① 限制 Thought 长度（最多 100 字）；② 用简短的 Chain-of-Thought 替代详细推理；③ 对历史步骤做摘要压缩（只保留最近 3 步的完整内容，更早的步骤只保留 Action 和 Observation）。
03

Agent Loop 五大工程能力

Agent Loop 是把 ReAct 的"思考-行动-观察"封装成可生产运行的执行引擎，核…

Agent Loop 是把 ReAct 的"思考-行动-观察"封装成可生产运行的执行引擎，核心是补齐 ReAct 缺失的五大工程能力：循环控制、状态持久化、超时保护、终止条件、错误恢复。

能力一：循环控制

ReAct 本身没有循环机制——它只定义了"一次思考-行动-观察"的格式，但不告诉系统"什么时候继续循环、什么时候停止"。Agent Loop 通过代码级 while 循环实现强制控制，设最大步数（如 10 步）防止无限循环。

能力二：状态持久化

生产环境中 Agent 可能运行数分钟甚至数十分钟，期间可能因进程崩溃、网络中断等原因中断。Checkpoint 机制在每一步执行完成后将完整 state 序列化保存到数据库（Redis/PostgreSQL），崩溃重启后从最新 checkpoint 恢复，继续执行下一步。

能力三：超时保护

双重超时机制：全局超时（如总耗时不超过 300 秒）防止整个任务卡死，单步超时（如单次工具调用不超过 10 秒）防止某个工具调用阻塞整个流程。超时后自动终止并返回"超时错误"给 LLM，让 LLM 决定下一步（如换工具或降级）。

能力四：终止条件

显式终止信号（final_answer）+ 最大步数兜底。LLM 通过输出 final_answer 明确表示"任务完成"，Loop 检测到该信号后正常退出。如果 LLM 一直不输出 final_answer（陷入死循环），最大步数兜底强制终止。

能力五：错误恢复

工具调用失败时自动重试（指数退避）或降级（换备选工具）。关键细节：工具调用可能是非幂等的（如发送邮件），恢复时需要检查哪些 Action 已经执行过，避免重复执行。通过 state 中的 action_history 记录已执行的 Action，恢复时跳过已完成的步骤。

  • 用 ReAct 格式保证推理可解释性
  • 用 Loop 引擎实现循环控制和状态管理
  • 设最大步数 + 全局超时双重兜底
  • 每步保存 checkpoint，支持崩溃恢复
  • 工具调用失败时自动重试或降级
  • 记录 action_history，恢复时避免重复执行
  • 只靠 ReAct prompt 不设工程级循环控制
  • 不设最大步数（可能死循环烧 token）
  • 不保存 checkpoint（崩溃后无法恢复）
  • 不设超时保护（工具调用卡死导致整体卡住）
  • 忽略非幂等工具的重复执行风险
  • 不监控循环状态（问题发现太晚）
生产案例：某代码生成 Agent 采用 ReAct + Loop 架构后，任务完成率从 68% 提升至 89%，平均执行步数从 12 步降至 7 步。关键改进：① Loop 引擎增加"重复检测"（连续 3 次调用相同工具+参数则终止），死循环率从 15% 降至 2%；② Checkpoint 机制使崩溃恢复时间从"重新执行全部步骤"（平均 8 分钟）降至"从断点继续"（平均 30 秒）；③ 单步超时保护使工具调用卡死导致的整体超时从 23% 降至 4%。
04

终止条件与防死循环策略

Agent Loop 最常见的生产事故是"死循环"——LLM 反复调用同一个工具、或不断产生…

Agent Loop 最常见的生产事故是"死循环"——LLM 反复调用同一个工具、或不断产生新的 Thought 但永远不输出 final_answer。防御策略必须是多层级的，单一策略无法覆盖所有死循环场景。

四层防死循环机制

防御层策略实现方式触发场景行为
L1 步数限制最大步数循环超过 N 步强制终止LLM 陷入反复推理不收敛返回"达到最大步数，任务未完成"
L2 时间限制全局超时总耗时超过 T 秒强制终止某一步工具调用卡死返回"执行超时，任务未完成"
L3 重复检测动作去重连续 3 次调用相同工具+参数则终止LLM 死循环调用同一工具返回"检测到重复操作，请检查逻辑"
L4 Token 预算Token 上限累计 token 超过预算则终止上下文窗口即将溢出返回"Token 预算耗尽"

最大步数设定指南

最大步数的设定需要平衡"任务复杂度"和"资源浪费"。设得太小会导致复杂任务提前终止，设得太大可能浪费 token（LLM 绕圈子）。经验法则：

推荐步数 = 任务类型基准值 × 复杂度系数（简单=1.0，中等=1.5，复杂=2.0）
任务类型基准步数示例推荐范围
简单 FAQ3~5 步单步查询 + 直接回答3~5 步
中等复杂度8~10 步多步信息查询 + 结果整合8~12 步
复杂任务15~20 步代码生成 + 测试 + 修复循环15~25 步
探索性任务20~30 步多轮调研 + 方案对比20~35 步

重复检测算法

重复检测不是简单的"上次调用了什么"，而是"最近 N 次调用是否形成循环"。推荐算法：维护最近 5 次 Action 的哈希列表，如果最新 Action 的哈希与列表中任意一个相同（相同工具 + 相同参数），则重复计数 +1。当重复计数达到 3 时触发终止。这种方法可以检测"ABA"循环（调用 A → 调用 B → 调用 A）。

  • 四层防御机制全部启用（步数+时间+重复+Token）
  • 根据任务类型动态设置最大步数
  • 重复检测用哈希列表（可检测 ABA 循环）
  • 终止时返回明确的错误信息（便于调试）
  • 记录每次终止的原因（分析死循环模式）
  • 只设步数限制不设时间限制（工具卡死无法检测）
  • 所有任务用相同的最大步数（简单任务浪费，复杂任务不够）
  • 重复检测只看"上一次"（无法检测 ABA 循环）
  • 终止时不返回原因（无法定位问题）
  • 不记录终止日志（无法分析死循环模式）
生产案例：某客服 Agent 上线初期死循环率达到 18%（每 100 次对话有 18 次陷入死循环），主要原因是：① 用户问题模糊导致 LLM 反复查询同一数据库（占 45%）；② 工具返回空结果导致 LLM 不断重试（占 30%）；③ Prompt 设计不当导致 LLM 不输出 final_answer（占 25%）。引入四层防御后：死循环率从 18% 降至 3%，平均每次死循环的 token 浪费从 8500 降至 2100，用户等待时间从平均 4.2 分钟降至 1.1 分钟。

状态管理与 Checkpoint 机制

Agent Loop 的状态不是"当前执行到哪一步"这么简单——它包含用户原始 query…

Agent Loop 的状态不是"当前执行到哪一步"这么简单——它包含用户原始 query、完整推理链、工具调用结果、累计 token 消耗、已执行的 action 历史等多个维度。状态管理的质量直接决定了崩溃恢复的可靠性。

State 数据结构

字段类型用途持久化策略
user_querystring用户原始问题每步保存
historylist[Step]所有 Thought/Action/Observation每步追加
step_countint当前步数每步更新
token_usageint累计 token 消耗每步累加
action_historylist[Action]已执行的 Action 列表（防重复）每步追加
tool_cachedict工具调用结果缓存（避免重复调用）按需更新
error_loglist[Error]错误堆栈（用于调试）错误时追加

Checkpoint 持久化策略

Checkpoint 的保存频率需要平衡"恢复精度"和"存储成本"。推荐策略：每步保存（保证恢复精度最高）+ 增量压缩（只保存变化的字段，减少存储开销）。存储介质选择：开发环境用 SQLite（零配置），生产环境用 Redis（毫秒级读写）或 PostgreSQL（强一致性）。

崩溃恢复流程

┌────────────────────────────────────────────────────────────────┐ │ Checkpoint 崩溃恢复流程 │ ├────────────────────────────────────────────────────────────────┤ │ │ │ [进程崩溃] ──▶ [重启] ──▶ [加载最新 Checkpoint] │ │ │ │ │ ▼ │ │ [恢复 state 对象] │ │ │ │ │ ▼ │ │ [检查 action_history] │ │ │ │ │ ┌────────────┴────────────┐ │ │ ▼ ▼ │ │ [有非幂等 Action] [全是幂等 Action] │ │ │ │ │ │ ▼ ▼ │ │ [跳过已执行步骤] [从断点继续执行] │ │ [标记为"已跳过"] [无需特殊处理] │ │ │ │ │ │ └────────────┬────────────┘ │ │ ▼ │ │ [继续执行下一步] │ │ │ │ 关键：非幂等 Action（如发送邮件、创建订单）必须跳过 │ │ 幂等 Action（如查询数据库、读文件）可以安全重试 │ └────────────────────────────────────────────────────────────────┘
关键细节：崩溃恢复的最大风险是非幂等操作的重复执行。例如：Agent 在执行"发送邮件"后崩溃，恢复时如果重新执行该 Action 会导致用户收到两封相同邮件。解决方案：① 在 action_history 中记录每个 Action 的执行状态（pending/success/failed）；② 恢复时检查 action_history，已成功的非幂等 Action 标记为"已跳过"；③ 对于关键操作（如金融交易），使用事务机制（先预检、再执行、后确认）。

ReAct vs Plan-and-Execute vs 纯工具调用

ReAct 不是唯一的 Agent 推理范式——Plan-and-Execute（先规划后执…

ReAct 不是唯一的 Agent 推理范式——Plan-and-Execute（先规划后执行）和纯工具调用（无推理链）各有适用场景。选择哪种范式取决于任务的"动态性"和"可解释性需求"。

维度ReActPlan-and-Execute纯工具调用
执行模式边想边做（动态决策）先规划后执行（预定义计划）直接调用（无推理）
灵活性高（每步根据观察调整）中（按计划执行，可中途调整）低（固定流程）
效率中（可能绕圈子）高（计划明确，少浪费）最高（无推理开销）
可解释性高（每步有 Thought）中（计划可见，执行黑盒）低（无推理记录）
适用场景动态变化的探索性任务结构化的复杂任务简单确定性任务
示例"调研某个话题并写报告""生成代码→测试→修复→提交""查天气并返回结果"
选择建议：如果任务需要"边做边看结果再决定下一步"（如调研、调试）→ 用 ReAct；如果任务结构清晰、步骤可预定义（如代码生成流水线）→ 用 Plan-and-Execute；如果任务简单且确定性高（如单步查询）→ 用纯工具调用。实际生产中常混合使用：Plan-and-Execute 做整体规划，ReAct 做每一步的动态执行。
07

Q&A（8 题）

ReAct 和 Plan-and-Execute 的核心区别是什么？什么时候该用哪个？
核心区别在于"决策时机"。ReAct 是"边想边做"——每一步都根据当前观察决定下一步行动，适合动态变化的任务（如"调研某个话题，根据发现调整方向"）。Plan-and-Execute 是"先规划后执行"——先让 LLM 生成完整的执行计划（步骤 1→2→3），然后按计划逐步执行，适合结构化的复杂任务（如"生成代码→测试→修复→提交"）。Plan-and-Execute 的效率更高但灵活性更低，ReAct 更灵活但可能绕圈子。实际生产中常混合使用：Plan-and-Execute 做整体规划，ReAct 做每一步的动态执行。
Agent Loop 的状态需要保存哪些信息？为什么 action_history 很重要？
核心状态包括：用户原始 query、所有历史 Thought/Action/Observation（构成推理链）、当前步数、累计 token 消耗、工具调用结果缓存。生产环境还需要：LLM 的 API 调用日志（用于计费）、错误堆栈（用于调试）、用户中断信号（支持 human-in-the-loop）。action_history 特别重要，因为它是崩溃恢复的关键——通过记录哪些 Action 已经执行过，恢复时可以避免重复执行非幂等操作（如发送邮件、创建订单），防止副作用重复发生。
最大步数设为多少合适？不同任务类型差异大吗？
差异非常大。简单 FAQ 类任务设 3~5 步，中等复杂度任务（如多步信息查询）设 8~10 步，复杂任务（如代码生成 + 测试 + 修复循环）设 15~20 步，探索性任务（如多轮调研）设 20~30 步。设得太小会导致复杂任务提前终止，设得太大可能浪费 token（LLM 绕圈子）。建议从 10 步起步，根据实际日志调整：如果 80% 的任务在 7 步内完成，说明 10 步足够；如果 20% 的任务在 10 步时被强制终止，说明需要增加步数或优化 Prompt。
ReAct 的 Thought 步骤会消耗很多 token 吗？如何优化？
是的。每一步 Thought 通常 50~200 token，10 步循环的 Thought 累计 500~2000 token，加上 Action 和 Observation，10 步循环可能消耗 5000~10000 token。优化方式：① 限制 Thought 长度（如最多 100 字）；② 用简短的 Chain-of-Thought 替代详细推理（如"需要查天气"而非"用户问的是北京明天是否适合跑步，我需要了解天气和空气质量..."）；③ 对历史步骤做摘要压缩（只保留最近 3 步的完整内容，更早的步骤只保留 Action 和 Observation）；④ 使用更便宜的模型做 Thought（如 GPT-3.5），用贵的模型做最终决策。
Agent Loop 崩溃后如何恢复？非幂等操作怎么处理？
通过 checkpoint 机制：每步执行完成后将完整 state 序列化保存到数据库（如 Redis/PostgreSQL）。崩溃重启后，从最新的 checkpoint 恢复 state，继续执行下一步。关键细节：工具调用可能是非幂等的（如发送邮件），恢复时需要检查哪些 Action 已经执行过，避免重复执行。解决方案：① 在 action_history 中记录每个 Action 的执行状态（pending/success/failed）；② 恢复时检查 action_history，已成功的非幂等 Action 标记为"已跳过"；③ 对于关键操作（如金融交易），使用事务机制（先预检、再执行、后确认）。
重复检测算法如何设计？只看"上一次"够吗？
只看"上一次"不够，无法检测"ABA 循环"（调用 A → 调用 B → 调用 A）。推荐算法：维护最近 5 次 Action 的哈希列表（Action 名称 + 参数的哈希值），如果最新 Action 的哈希与列表中任意一个相同，则重复计数 +1。当重复计数达到 3 时触发终止。更高级的检测：使用"滑动窗口"分析最近 10 次 Action 的模式，如果检测到周期性重复（如 ABABAB），则提前终止。这种方法可以检测更复杂的死循环模式。
ReAct 推理链出问题时如何定位是"推理错误"还是"工具错误"？
ReAct 的可解释性价值正在于此。回溯推理链：① 如果 Thought 步骤的推理逻辑有误（如"用户问的是明天，但我查的是今天"），说明是 LLM 的理解问题，需要优化 Prompt 或换更强的模型；② 如果 Action 步骤调用了错误的工具或参数（如"应该查天气但查了汇率"），说明是工具选择问题，需要优化工具描述或 Few-shot 示例；③ 如果 Observation 返回了异常数据（如"天气 API 返回空结果"），说明是工具本身的问题，需要检查工具实现或增加错误处理。这种精确的故障定位能力是 ReAct 相比"黑盒多步执行"的核心优势。
Agent Loop 和 LangChain 的 AgentExecutor 是什么关系？
LangChain 的 AgentExecutor 是 Agent Loop 的一种实现——它封装了 ReAct 的循环执行、工具调用、状态管理等能力。但 AgentExecutor 是通用框架，生产环境中通常需要定制化：① 自定义终止条件（如特定业务规则）；② 自定义错误恢复策略（如特定工具的重试逻辑）；③ 自定义状态持久化（如特定数据库的 checkpoint 机制）。建议：快速原型用 AgentExecutor，生产环境用自定义 Loop 引擎（基于 AgentExecutor 的核心逻辑但增加业务定制）。
