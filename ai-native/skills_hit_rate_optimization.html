Skills 命中率优化实战

Skills Hit Rate Optimization — Skill 数量一多，Agent 的命中率怎么保证？三位一体优化策略与分层架构实践

AI 工程 阅读 ~5 min 6 章
00

概览

命中率保障需要三位一体：贴合业务的 Agent 底座 + 带正负样例的分层描述 + 先召回后…

命中率保障需要三位一体：贴合业务的 Agent 底座 + 带正负样例的分层描述 + 先召回后精排的路由机制。

01

Skill 与 Agent 的关系

Skill 是依赖上层 Agent 能力的过渡产物 —— 同一个 Skill 在不同 Age…

Skill 是依赖上层 Agent 能力的过渡产物 —— 同一个 Skill 在不同 Agent 上表现可能天差地别。

因素影响说明
Agent 上下文工程决定 Skill 能否被正确触发好的上下文 = Skill 命中率高
Agent 推理能力决定 Skill 执行质量强推理 = Skill 输出准确
Skill 描述质量决定 Agent 能否选对 Skill清晰描述 = 减少误触发
核心认知：优化 Skill 命中率不能只看 Skill 本身，必须从 Agent 底座能力出发。同样的 Skill 描述，在 GPT-4 和 GPT-3.5 上的命中率可能差 30%。
02

四大优化策略

第一层按业务大类分（研发/运营/市场），第二层细分领域（如研发下分代码生成/评审）

2.1 描述优化：写「何时用」而非「是什么」

差的描述好的描述改进点
"负责生成 PPT""当用户需要制作汇报材料时使用"包含触发场景
"数据分析工具""当用户提供 CSV/Excel 并要求分析趋势时使用"明确输入格式 + 意图
"代码生成器""当用户描述需求但没写代码，需要从零生成时使用"区分生成 vs 修改
遵循 Anthropic 官方建议：Skill 描述应包含触发场景（When to use），而不仅是功能说明（What it does）。

2.2 架构分层：Skill Tree 分层架构

Skill Tree 分层架构
第一层 (业务大类):
研发 (R&D)
代码生成 · 代码评审 · Bug 修复 · 技术文档
运营 (Ops)
数据分析 · 报告生成 · 用户运营
市场 (Marketing)
文案撰写
竞品分析
活动策划

第一层按业务大类分（研发/运营/市场），第二层细分领域（如研发下分代码生成/评审）。分层后，Agent 先定位大类再在子类中精排，搜索空间从 N 缩小到 N/K。

2.3 边界防御：负面描述

必须添加「When NOT to use」负面描述，防止 Skill 被误触发：

Skill正面描述负面描述
前端组件生成"生成 React/Vue 组件""不适用于后端接口开发"
SQL 查询"生成 SQL 查询语句""不适用于数据库设计/建表"
文案撰写"撰写营销文案""不适用于技术文档/API 文档"

2.4 路由机制：召回 + 精排

Skill 路由流程
用户请求: "帮我分析一下上个月的销售数据"
召回阶段 (轻量级检索)
关键词匹配 + Embedding 相似度 · Top 10 候选 Skill · [数据分析, 报告生成, SQL查询, ...]
精排阶段 (大模型裁决)
LLM 根据用户意图 + Skill 描述做最终判断 · 选中: 数据分析
执行 Skill
阶段方法目标延迟
召回关键词 + Embedding 相似度从 N 个 Skill 中筛出 Top 10< 50ms
精排LLM 基于意图做最终裁决从 10 个中选出最匹配的 1 个~500ms
03

三位一体核心结论

维度要求效果
Agent 底座贴合业务的上下文工程 + 推理能力Skill 被正确理解和执行
分层描述带正负样例的 Skill Tree 分层减少误触发，提高选择准确率
路由机制先召回后精排的两阶段策略兼顾效率与准确率
  • 描述写「何时用」而非「是什么」
  • 建立 Skill Tree 分层架构
  • 必须添加负面描述（When NOT to use）
  • 用「召回 + 精排」两阶段路由
  • 针对不同 Agent 底座测试 Skill 表现
  • 不要把所有 Skill 平铺在一个层级
  • 不要只写功能描述不写触发场景
  • 不要忽略负面描述（防误触发）
  • 不要让 LLM 从全部 Skill 中精排（太慢）
  • 不要假设 Skill 在所有 Agent 上表现一致

生产案例

生产验证： 某 AI 编程助手的 Skill 命中率优化：(1) 将 Description…

生产验证：某 AI 编程助手的 Skill 命中率优化：(1) 将 Description 从"这是一个代码格式化工具"改为"当用户要求格式化/美化/lint 代码时触发"，匹配准确率从 45% 提升至 92%；(2) 同义词扩展（"格式化"+"美化"+"lint"+"prettify"）后，用户口语化表达的召回率从 63% 提升至 88%；(3) Skill 数量从 42 个精简至 18 个（合并功能重叠），选择错误率从 12% 降至 3.1%。整体命中率从 47% 提升至 89%，用户满意度从 3.1/5 提升至 4.3/5。

05

Q&A

Skill 数量多了之后，命中率为什么下降？
三个原因：(1) 搜索空间增大 —— Agent 需要在更多选项中做选择，选择错误概率上升；(2) 描述冲突 —— 功能相近的 Skill 容易混淆；(3) 上下文稀释 —— 所有 Skill 描述挤在 Prompt 中，每个 Skill 获得的注意力权重下降。解决方案：分层架构缩小搜索空间 + 负面描述减少冲突 + 召回精排两阶段路由。
为什么描述要写「何时用」而非「是什么」？
因为 Agent 的决策逻辑是「用户请求匹配哪个 Skill 的触发条件」，而非「哪个 Skill 的功能最接近」。「负责生成 PPT」描述的是功能，Agent 不知道该在什么情况下触发；「当用户需要制作汇报材料时使用」描述的是触发场景，Agent 能直接匹配用户意图。本质是从「功能描述」转向「意图匹配」。
召回 + 精排的路由机制比直接让 LLM 选有什么优势？
两个优势：(1) 延迟 —— 直接让 LLM 从 N 个 Skill 中选，需要把 N 个描述都注入 Prompt，延迟随 N 线性增长；召回阶段用轻量级检索（关键词+Embedding）在 50ms 内缩小到 Top 10，精排阶段 LLM 只需看 10 个描述；(2) 准确率 —— LLM 在少量候选中做精排比在大量候选中做全量选择的准确率高 15-20%。
负面描述为什么重要？
负面描述解决「边界模糊」问题。很多 Skill 功能有重叠（如「代码生成」和「代码修改」都涉及代码），如果只写正面描述，Agent 可能在不需要生成代码时误触发代码生成 Skill。负面描述明确划定边界：「不适用于后端接口开发」「不适用于代码重构」。相当于给 Skill 加了「排除条件」，减少误触发率。
Q5：如何衡量 Skill 命中率优化的效果？有哪些关键指标？
三层指标体系：(1) 离线指标 — 在标注测试集上的 Precision@1（首选 Skill 是否正确）和 Recall@3（正确 Skill 是否在 Top 3 中）；(2) 线上指标 — 实际用户请求中 Skill 触发成功率（用户无报错/无重试即为成功），以及手动切换 Skill 的频率（越低越好）；(3) 用户体验指标 — 用户满意度评分（NPS）、任务完成率、平均交互轮数。生产数据：命中率从 47% 提升至 89% 后，用户满意度从 3.1/5 提升至 4.3/5，平均交互轮数从 4.2 降至 2.1（减少不必要的澄清对话）。
