审计回放概述

什么是审计回放

审计回放是指从存储的日志和追踪数据中，精确还原 AI 系统在特定时间点的完整行为过程，包括用户输入、模型推理、工具调用、决策路径等全链路信息。

维度传统应用调试LLM 审计回放
目标找到代码 bug还原 AI 决策过程、理解"为什么这样回答"
数据源代码 + 日志 + 堆栈对话链 + 工具调用 + 模型参数 + 检索结果
确定性可精确重现不可精确重现（LLM 非确定性），只能"回看"
复杂度线性调用栈多轮对话 + 并行工具调用 + 递归 Agent 调用
用途修复 bug合规审计 + 事件调查 + 质量分析 + 用户投诉

回放场景

场景需要回放的内容关注点
用户投诉用户发了什么 → 模型回了什么回答质量、是否存在幻觉
安全事件攻击者的完整交互序列注入手法、数据泄露范围
合规审查AI 辅助决策的完整依据链决策是否有合理依据
Agent 异常Agent 的完整工具调用链在哪一步出错、为什么走错路
模型退化特定时段的批量输出模型版本切换是否导致质量下降

审计回放的核心原则：你不能"重新运行"LLM 来得到相同结果（非确定性），所以必须在运行时记录足够多的信息以支持事后回看。这就是"记录优先"的设计哲学。

  • 审计回放 ≠ 重新执行——LLM 的非确定性意味着只能"回看记录"而非"重新运行"
  • 回放的五大场景：用户投诉、安全事件、合规审查、Agent 异常、模型退化
  • 回放质量取决于记录质量——运行时记录不完整，事后无法弥补

对话链数据模型

# 完整对话链的数据结构
class ConversationChain:
    conversation_id: str
    session_id: str
    user_id: str
    created_at: datetime
    turns: list["ConversationTurn"]

class ConversationTurn:
    turn_id: str
    turn_number: int
    timestamp: datetime

    user_message: Message
    assistant_message: Message

    model_config: dict          # temperature, model, max_tokens
    context_window: list[Message]  # 实际发送给模型的完整上下文
    retrieval_results: list[dict]  # RAG 检索到的文档
    tool_calls: list[ToolCall]     # 该轮中的工具调用

    usage: TokenUsage
    latency_ms: int
    content_filter_result: dict

# 回放时需要还原的是完整的 context_window
# 而不仅仅是 user_message 和 assistant_message
# 因为上下文截断策略会影响模型的回答质量

对话链可视化回放

# 对话链回放渲染器
class ConversationReplayer:
    def replay(self, conversation_id: str):
        chain = self.storage.load_conversation(conversation_id)

        timeline = []
        for turn in chain.turns:
            # 渲染用户消息
            timeline.append({
                "type": "user_message",
                "time": turn.timestamp,
                "content": turn.user_message.content,
                "metadata": {
                    "message_length": len(turn.user_message.content),
                    "attachments": turn.user_message.attachments
                }
            })

            # 渲染 RAG 检索（如果有）
            if turn.retrieval_results:
                timeline.append({
                    "type": "retrieval",
                    "time": turn.timestamp + timedelta(ms=50),
                    "documents": [
                        {"source": d["source"], "score": d["score"],
                         "snippet": d["content"][:200]}
                        for d in turn.retrieval_results
                    ]
                })

            # 渲染工具调用（如果有）
            for tc in turn.tool_calls:
                timeline.append({
                    "type": "tool_call",
                    "time": tc.timestamp,
                    "tool": tc.name,
                    "input": tc.arguments,
                    "output": tc.result,
                    "duration_ms": tc.duration_ms
                })

            # 渲染 AI 回复
            timeline.append({
                "type": "assistant_message",
                "time": turn.timestamp + timedelta(ms=turn.latency_ms),
                "content": turn.assistant_message.content,
                "model": turn.model_config["model"],
                "tokens": turn.usage.dict(),
                "finish_reason": turn.assistant_message.finish_reason
            })

        return ReplayTimeline(
            conversation_id=conversation_id,
            events=timeline,
            total_duration=chain.duration
        )
  • 回放必须包含完整的 context_window——不仅是最后一轮，而是模型实际"看到"的所有内容
  • RAG 检索结果也要记录——理解"模型参考了什么"对分析回答质量至关重要
  • 时间轴可视化让非技术人员（合规审计员）也能理解 AI 的行为过程

多 Agent 轨迹关联

# 多 Agent 系统的分布式追踪
class MultiAgentTracer:
    def trace_delegation(self, parent_trace, child_agent, task):
        child_trace = self.create_trace(
            parent_trace_id=parent_trace.trace_id,
            agent_type=child_agent.type,
            task=task
        )

        # 构建 Agent 调用树
        parent_trace.add_child(child_trace)

        return child_trace

# 多 Agent 轨迹树示例
# Orchestrator Agent (trace_001)
# ├── Research Agent (trace_002)
# │   ├── tool_call: web_search("AI regulations 2024")
# │   └── tool_call: read_document(doc_id=...)
# ├── Analysis Agent (trace_003)
# │   ├── tool_call: extract_data(...)
# │   └── tool_call: calculate_metrics(...)
# └── Writer Agent (trace_004)
#     └── tool_call: generate_report(...)
  • Agent 轨迹记录的核心是 Think-Act-Observe 三元组——完整记录推理、行动和观察
  • 多 Agent 系统需要分布式追踪——用 parent_trace_id 构建调用树
  • 轨迹回放是 Agent 调试的唯一手段——因为你无法"重新运行 Agent 得到相同结果"

OpenTelemetry 实现追踪

OpenTelemetry 在 LLM 中的应用

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter

# 初始化 OpenTelemetry
provider = TracerProvider()
provider.add_span_processor(
    BatchSpanProcessor(OTLPSpanExporter(endpoint="http://jaeger:4317"))
)
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("llm-application")

class TracedLLMClient:
    def complete(self, messages, **kwargs):
        with tracer.start_as_current_span("llm.completion") as span:
            span.set_attribute("llm.model", kwargs.get("model"))
            span.set_attribute("llm.temperature", kwargs.get("temperature", 1.0))
            span.set_attribute("llm.max_tokens", kwargs.get("max_tokens"))
            span.set_attribute("llm.prompt_tokens", len(str(messages)))

            response = self.client.chat.completions.create(
                messages=messages, **kwargs
            )

            span.set_attribute("llm.completion_tokens",
                             response.usage.completion_tokens)
            span.set_attribute("llm.total_tokens",
                             response.usage.total_tokens)
            span.set_attribute("llm.finish_reason",
                             response.choices[0].finish_reason)

            return response

    def agent_step(self, step_num, thought, action, observation):
        with tracer.start_as_current_span(f"agent.step.{step_num}") as span:
            span.set_attribute("agent.thought", thought)
            span.set_attribute("agent.action", action.tool_name)
            span.set_attribute("agent.action_args",
                             json.dumps(action.arguments))

            result = self.execute_action(action)

            span.set_attribute("agent.observation", str(result))
            span.set_attribute("agent.success", result.success)
            span.add_event("action_completed", {
                "duration_ms": result.duration_ms
            })

            return result

事件根因分析

LLM 事件分类与根因

事件类型表现常见根因回放关注点
幻觉回答含虚假信息检索失败、上下文不足、模型能力检索了什么文档？context_window 完整吗？
安全绕过输出有害内容Prompt 注入、系统 prompt 泄露完整的对话历史、注入点在哪一轮？
Agent 循环Agent 陷入死循环观察结果不变、工具返回错误每步的 thought 和 observation 变化
延迟飙升响应时间异常增长上下文过长、模型过载prompt_tokens 变化趋势、API 延迟
质量退化回答质量突然下降模型版本切换、系统 prompt 变更对比前后的 model_version 和 system_prompt

根因分析工作流

class RootCauseAnalyzer:
    def analyze_incident(self, incident_id: str):
        incident = self.load_incident(incident_id)

        # Step 1: 收集相关 traces
        traces = self.collect_traces(
            time_range=incident.time_range,
            filters=incident.affected_entities
        )

        # Step 2: 异常检测
        anomalies = self.detect_anomalies(traces, baselines={
            "latency_p99": 3000,
            "error_rate": 0.01,
            "token_usage_avg": 2000
        })

        # Step 3: 关联分析
        correlations = self.correlate(anomalies, events=[
            self.get_deployment_events(incident.time_range),
            self.get_config_changes(incident.time_range),
            self.get_model_version_changes(incident.time_range),
        ])

        # Step 4: 生成根因报告
        return RootCauseReport(
            incident_id=incident_id,
            timeline=self.build_timeline(traces, anomalies),
            probable_cause=correlations.most_likely,
            evidence=correlations.supporting_data,
            recommendation=self.generate_recommendation(correlations)
        )
  • 根因分析的关键是"关联"——将异常指标与部署事件、配置变更、模型版本切换关联
  • LLM 特有的根因：幻觉（检索失败）、Agent 死循环（observation 不变）、质量退化（模型切换）
  • 根因分析报告应包含：时间线、可能原因、证据数据、修复建议

回放 vs 实时调试

两种调试模式对比

维度审计回放（Post-mortem）实时调试（Live Debugging）
时机事后分析实时介入
数据来源存储的日志和 trace实时流数据
精确性取决于记录完整性完整的实时上下文
干预能力只能回看，无法修改可以断点、修改参数、重试
性能影响零影响（离线分析）可能降低服务性能
适用场景合规审计、事件调查开发调试、实时故障排查

混合调试策略

class HybridDebugger:
    def replay_and_debug(self, trace_id: str):
        """先回放历史 trace，再用实时调试验证假设"""
        # Phase 1: 回放历史数据
        replay = self.replayer.load_trace(trace_id)
        timeline = replay.get_timeline()

        # 识别可疑步骤
        suspicious = [
            step for step in timeline
            if step.anomaly_score > 0.7
        ]

        # Phase 2: 在测试环境中"重放"类似请求
        for step in suspicious:
            test_result = self.live_debugger.run_with_breakpoint(
                input=step.input,
                breakpoint_at=step.step_number,
                model=step.model_config["model"],
                temperature=0  # 降低随机性以便对比
            )

            # 对比历史结果和测试结果
            comparison = self.compare(
                original=step,
                reproduced=test_result
            )

            if comparison.divergence > 0.5:
                self.flag_as_non_reproducible(step, comparison)

    def shadow_mode_debug(self, production_trace_id):
        """影子模式：用生产流量在测试环境并行运行"""
        prod_trace = self.load_trace(production_trace_id)
        shadow_trace = self.run_shadow(
            input=prod_trace.input,
            config=prod_trace.config
        )
        return self.diff(prod_trace, shadow_trace)
  • 回放适合合规审计和事后分析，实时调试适合开发和故障排查——生产环境通常只有回放
  • 混合策略：先用回放定位可疑步骤，再在测试环境重放验证
  • 影子模式（Shadow Mode）可以在不影响生产的情况下对比新旧模型/配置的行为差异

为什么 LLM 应用的审计回放不能简单地"重新运行"来重现？

根本原因是 LLM 的非确定性：①即使使用相同的 prompt 和参数（如 temperature=0.7），模型每次生成的内容也可能不同，因为 sampling 过程本质是随机的；②模型版本可能已更新——供应商会持续迭代模型权重，一个月前的 gpt-4 和现在的 gpt-4 可能是不同版本；③上下文依赖——多轮对话中前面轮次的回答影响后续轮次，而前面轮次本身就不可精确重现；④外部状态——Agent 调用的工具（数据库查询、网页搜索）返回的结果会随时间变化。因此审计回放的正确做法是"记录优先"——在运行时完整记录 prompt、response、context_window、工具调用结果、模型版本等全量信息，事后直接回看记录而非重新运行。

如何使用 OpenTelemetry 实现 LLM 应用的分布式追踪？

实现步骤：①初始化 TracerProvider 并配置 Exporter（如 OTLP 输出到 Jaeger/Grafana Tempo）；②在 LLM 调用处创建 Span，记录模型名、temperature、token 使用量等属性（使用 gen_ai.* 语义约定）；③在 RAG 检索处创建子 Span，记录查询、结果数量、相关性分数；④在 Agent 步骤处创建子 Span，记录 thought、action、observation；⑤通过 Context Propagation 确保跨服务的 trace 关联（如 API Gateway → LLM Service → Vector DB）。关键实践：使用 BatchSpanProcessor 避免性能影响；为 LLM 调用设置 span.kind=CLIENT（外部服务调用）；在异常情况下记录 span.status=ERROR 和错误详情；使用 span events 记录时间点信息（如 "stream_first_token"）。

如何设计 Agent 行为轨迹的回放系统？

Agent 轨迹回放系统的设计要点：①数据模型——以 AgentTrajectory 为根，包含有序的 AgentStep 列表，每个 step 记录 Think（推理过程）、Act（工具调用及参数）、Observe（结果及是否成功）三元组；②多 Agent 关联——使用 parent_trace_id 构建 Agent 调用树，支持 Orchestrator → Sub-Agent 的递归追踪；③可视化——使用泳道时间线展示并行活动（推理、工具调用、子 Agent），支持缩放和钻取详情；④异常标注——自动检测异常模式如"连续 3 步 observation 相同"（死循环）、"工具调用失败但继续推理"（错误忽略）；⑤对比分析——支持两个 trace 的 side-by-side 对比，用于分析模型升级或 prompt 变更的影响。

审计回放中如何进行事件根因分析？

LLM 事件根因分析的四步法：①收集证据——获取事件时间范围内的所有相关 traces（对话链、工具调用、系统日志）；②异常检测——将指标（延迟、token 消耗、错误率）与基线对比，标记偏离超过阈值的数据点；③关联分析——将异常指标与系统事件（部署、配置变更、模型版本切换、流量变化）进行时间维度关联，找出"异常出现前最近的变更"；④根因确认——在测试环境重放类似请求验证假设。LLM 特有的根因模式：幻觉通常关联 RAG 检索失败或上下文截断；安全绕过关联特定的输入模式（Prompt 注入）；Agent 循环关联工具持续返回相同错误；质量退化关联模型版本变更。

回放系统的时间线可视化应该包含哪些信息？如何设计？

时间线可视化采用"多泳道"设计，每条泳道代表一个活动维度：①用户交互泳道——用户消息发送和接收时间点；②RAG 检索泳道——检索查询、返回文档数量和相关性分数；③Agent 推理泳道——每步的 thought 内容和持续时间；④工具调用泳道——工具名、参数、结果、耗时，用颜色区分成功/失败；⑤LLM 调用泳道——模型名、token 数量、延迟。设计原则：支持时间轴缩放（从毫秒到分钟级），点击事件可钻取查看详情（完整 prompt、返回内容），支持搜索和过滤（如只看失败的工具调用），异常事件用红色高亮。前端实现可用 vis-timeline、react-chrono 等甘特图库。关键是让非技术人员（合规审计员）也能直观理解 AI 的决策过程。
