工具依赖图深度分析

LLM 在规划阶段需要分析用户意图，判断哪些工具调用之间有依赖
┌─────────────────────────────────────────────────────────────────────────┐ │ 多工具并行执行架构 │ ├─────────────────────────────────────────────────────────────────────────┤ │ │ │ [用户 Query] ──▶ [LLM 规划] ──▶ [依赖图生成] │ │ │ │ │ ▼ │ │ ┌─────────────────────────────────────────────────────────┐ │ │ │ 依赖图（DAG - 有向无环图） │ │ │ │ │ │ │ │ ┌─────────┐ ┌─────────┐ │ │ │ │ │ Tool A │────────▶│ Tool C │ (数据依赖：C 需要 A 的输出)│ │ │ │ │查天气 │ │翻译结果 │ │ │ │ │ └─────────┘ └─────────┘ │ │ │ │ │ │ │ │ ┌─────────┐ ┌─────────┐ │ │ │ │ │ Tool B │────────▶│ Tool D │ (数据依赖：D 需要 B 的输出)│ │ │ │ │查汇率 │ │计算金额 │ │ │ │ │ └─────────┘ └─────────┘ │ │ │ │ │ │ │ │ ┌─────────┐ │ │ │ │ │ Tool E │ (无依赖：可独立并行) │ │ │ │ │查新闻 │ │ │ │ │ └─────────┘ │ │ │ └─────────────────────────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ ┌─────────────────────────────────────────────────────────┐ │ │ │ 并行调度引擎 │ │ │ │ │ │ │ │ Phase 1 (并行): [A, B, E] 同时执行 │ │ │ │ │ │ │ │ │ ▼ (A, B 完成后) │ │ │ │ Phase 2 (并行): [C, D] 同时执行 │ │ │ │ │ │ │ │ │ ▼ (全部完成) │ │ │ │ Phase 3: [结果合并] ──▶ [返回 LLM] ──▶ [生成回答] │ │ │ └─────────────────────────────────────────────────────────┘ │ │ │ │ 串行执行：A→B→C→D→E = 5.2 秒 │ │ 并行执行：(A|B|E)→(C|D) = 1.8 秒 (延迟降低 65%) │ └─────────────────────────────────────────────────────────────────────────┘
核心设计哲学：多工具并行执行的本质是"把串行执行 5 个工具 = 5 秒"变成"并行执行 5 个无依赖工具 = 1 秒"。关键挑战不是"如何并行"，而是"正确识别哪些工具之间有依赖、哪些可以安全并行"。错误的并行会导致数据不一致（工具 B 使用了工具 A 尚未返回的旧数据）或资源冲突（两个工具同时写同一个文件）。依赖图（Dependency Graph）是一个有向无环图（DAG），节点是工具调用，边表示"A 的输出是 B 的输入"。只有没有依赖关系的工具才能安全并行。

三种依赖类型

依赖类型定义示例能否并行检测方法
数据依赖工具 B 需要工具 A 的输出作为参数"查天气，然后把结果翻译成英文"❌ 必须串行参数引用分析
资源依赖两个工具都要写同一个共享资源"两个工具都要写同一个文件"❌ 必须串行或加锁资源冲突检测
无依赖工具之间完全独立"查北京天气"和"查美元汇率"✅ 可安全并行无引用 + 无资源冲突

依赖图生成算法

LLM 在规划阶段需要分析用户意图，判断哪些工具调用之间有依赖。推荐使用 Structured Output（结构化输出）让 LLM 直接输出依赖图的 JSON 表示，而非让 LLM 用自然语言描述依赖关系（容易歧义）。

依赖图 = { "tools": [A, B, C, D, E], "edges": [(A→C), (B→D)], "parallel_groups": [[A, B, E], [C, D]] }

依赖图生成的核心是"参数引用分析"——如果工具 C 的某个参数引用了工具 A 的输出（如 translate(text=A.result)），则 C 依赖 A，必须串行。如果两个工具的参数互不引用且无共享资源，则可并行。

  • 先分析依赖图，只并行无依赖的工具
  • 用 Structured Output 让 LLM 输出依赖图 JSON
  • 检测数据依赖（参数引用）和资源依赖（共享资源）
  • 依赖图必须是 DAG（无环），有环则报错
  • 日志记录依赖图（便于调试和分析）
  • 不分析依赖就盲目并行（数据不一致风险）
  • 用自然语言描述依赖关系（容易歧义）
  • 忽略资源依赖（只检查数据依赖）
  • 允许依赖图有环（死锁风险）
  • 不记录依赖图（出问题无法回溯）
生产案例：在某旅行规划 Agent 中，用户请求"规划去日本的旅行：查机票、查酒店、查汇率、翻译景点介绍、生成行程单"。串行执行 5 个工具需要 6.8 秒，通过依赖图分析识别出"查机票、查酒店、查汇率"三个工具无依赖可并行，"翻译景点"依赖"查酒店"（需要酒店位置信息），"生成行程单"依赖所有前序工具。并行执行后总耗时从 6.8 秒降至 2.9 秒，延迟降低 57%，用户体验显著提升。

并行调度引擎设计

并行调度有两种实现范式：静态调度（提前分析依赖图，固定并行方案）和动态调度（运行时根据工具完…

并行调度有两种实现范式：静态调度（提前分析依赖图，固定并行方案）和动态调度（运行时根据工具完成状态动态触发下一步）。选择哪种取决于任务的"可预测性"。

三种调度策略对比

调度策略实现方式优点缺点适用场景
静态 DAG 调度LLM 生成 DAG → 引擎按拓扑序执行可预测、易调试、执行计划透明不够灵活，无法处理运行时依赖变化工具调用计划在规划阶段可完全确定
动态事件驱动工具完成后触发回调 → 引擎判断下一步灵活，适应运行时变化调试困难，可能出现意外并发工具调用需要根据中间结果动态调整
混合调度静态 DAG + 动态回调兜底兼顾可预测性和灵活性实现复杂大多数 Agent 场景（推荐）

静态 DAG 调度算法

静态调度的核心是拓扑排序——将 DAG 中的节点按依赖关系排序，确保每个节点在其所有前驱节点完成后才执行。调度引擎按"阶段"（Phase）执行：第一阶段执行所有无前驱的节点（可并行），第二阶段执行所有前驱已完成的节点（可并行），以此类推。

┌────────────────────────────────────────────────────────────────┐ │ 静态 DAG 调度执行流程 │ ├────────────────────────────────────────────────────────────────┤ │ │ │ 依赖图：A→C, B→D, E(无依赖) │ │ │ │ 拓扑排序后： │ │ ┌─────────────────────────────────────────────────────────┐ │ │ │ Phase 1: [A, B, E] ← 无前驱，可并行 │ │ │ │ │ │ │ │ │ ▼ (等待 A, B, E 全部完成) │ │ │ │ Phase 2: [C, D] ← A, B 已完成，C, D 可并行 │ │ │ │ │ │ │ │ │ ▼ (等待 C, D 全部完成) │ │ │ │ Phase 3: [结果合并] │ │ │ └─────────────────────────────────────────────────────────┘ │ │ │ │ 执行时间线： │ │ 时间 0s: 启动 A(1.0s), B(1.2s), E(0.8s) │ │ 时间 0.8s: E 完成 │ │ 时间 1.0s: A 完成 │ │ 时间 1.2s: B 完成 → 启动 C(0.6s), D(0.5s) │ │ 时间 1.7s: D 完成 │ │ 时间 1.8s: C 完成 → 结果合并 │ │ 总耗时：1.8 秒（vs 串行 5.2 秒） │ │ │ └────────────────────────────────────────────────────────────────┘

动态事件驱动调度

动态调度适用于"工具调用计划需要根据中间结果调整"的场景。例如："先查 A，如果 A 的结果满足条件 X 则查 B，否则查 C"。这种条件分支无法在规划阶段预先确定，必须在运行时根据 A 的结果动态决策。动态调度的核心是事件循环——每个工具完成后触发"完成事件"，调度器根据事件和当前状态决定下一步动作。

并发控制

并行不是越多越好。需要设置并发上限（如最多 5 个工具同时执行），避免以下问题：

问题原因后果解决方案
API 限流同时调用 10 个外部 API触发 rate limit，大量请求被拒绝设并发上限 + 指数退避重试
上下文爆炸10 个工具结果同时返回LLM 上下文窗口放不下，丢失关键信息结果摘要 + 分批合并
资源竞争多个工具同时写数据库死锁或数据不一致资源锁 + 串行化写操作
内存溢出大量工具结果缓存在内存进程 OOM 崩溃流式处理 + 结果持久化
推荐并发上限 = min(API_rate_limit, context_window / avg_result_size, db_connection_pool)
  • 根据任务可预测性选择调度策略（静态/动态/混合）
  • 设并发上限（推荐 3~5 个），防止 API 限流
  • 监控每个工具的耗时（P50/P95/P99）
  • 工具结果做摘要压缩后再合并（控制 Token）
  • 日志记录调度决策（便于调试）
  • 并行 10+ 个工具导致上下文爆炸
  • 不设并发上限（API 限流风险）
  • 忽略资源竞争（数据库死锁）
  • 不监控工具耗时（慢工具拖慢整体）
  • 不记录调度日志（问题无法回溯）
生产案例：某电商 Agent 的"商品推荐"任务需要调用 7 个工具：查用户画像、查商品库、查库存、查价格、查评价、查物流、生成推荐。串行执行需要 8.5 秒。通过静态 DAG 调度识别出 5 个无依赖工具可并行（查用户画像、查商品库、查库存、查价格、查评价），2 个有依赖工具串行（查物流依赖查库存，生成推荐依赖所有前序工具）。设置并发上限为 5，并行执行后总耗时从 8.5 秒降至 3.2 秒，延迟降低 62%。进一步优化：对工具结果做摘要压缩（每个结果从平均 800 token 压缩到 200 token），LLM 处理时间从 2.1 秒降至 0.8 秒。
03

错误隔离与结果合并

并行执行时，一个工具失败不应该导致整个任务失败

并行执行时，一个工具失败不应该导致整个任务失败。错误隔离的核心是"每个工具调用独立超时和重试"——工具 A 超时不影响工具 B 的正常执行。结果合并的核心是"结构化聚合"——将多个工具的结果组装为一个统一的 JSON 对象，供 LLM 处理。

三种错误处理策略

策略行为适用场景实现方式
部分成功失败的工具返回 null，其他工具的结果正常合并非关键工具（如附加信息）try-catch 包裹每个工具调用
全有全无任一工具失败则整体回滚关键流程（如金融交易）事务机制 + 补偿操作
降级替代失败的工具用备选工具或默认值替代有降级方案的场景fallback 函数 + 默认值配置

部分成功策略详解

部分成功是最常用的策略——它允许"部分信息缺失"，让 LLM 基于已有结果生成回答，并标注"部分信息获取失败"。例如：用户请求"查北京天气和上海天气"，如果上海天气 API 超时，系统返回"北京：晴，28°C；上海：信息获取失败"，而非整体失败。

全有全无策略详解

全有全无适用于"任一环节失败都会导致业务错误"的场景，如金融交易（转账时扣款成功但入账失败是灾难性的）。实现方式：① 使用事务机制（所有工具调用要么全部成功，要么全部回滚）；② 对于不支持事务的工具，实现补偿操作（如"发送邮件"失败后"撤销已创建的订单"）。

结果合并算法

并行执行后需要将多个工具的结果合并为一个统一的数据结构，供 LLM 处理。推荐三种合并方式：

合并方式实现优点缺点
按工具名拼接"天气结果：...，汇率结果：..."简单直观LLM 解析困难
按执行顺序拼接先完成的放前面保留时间信息顺序不稳定
结构化合并（推荐）将多个结果组装为一个 JSON 对象LLM 解析能力强，结构清晰需要预定义 Schema
┌────────────────────────────────────────────────────────────────┐ │ 结果合并流程 │ ├────────────────────────────────────────────────────────────────┤ │ │ │ 并行执行结果： │ │ ┌─────────┐ ┌─────────┐ ┌─────────┐ │ │ │ Tool A │ │ Tool B │ │ Tool C │ │ │ │ 成功 │ │ 成功 │ │ 失败 │ │ │ │ {temp: │ │ {rate: │ │ {error: │ │ │ │ 28°C} │ │ 7.2} │ │ "超时"} │ │ │ └────┬────┘ └────┬────┘ └────┬────┘ │ │ │ │ │ │ │ └────────────┼────────────┘ │ │ ▼ │ │ ┌─────────────────────────────────────────────────────────┐ │ │ │ 结构化合并（推荐） │ │ │ │ { │ │ │ │ "weather": {"status": "success", "temp": 28}, │ │ │ │ "exchange": {"status": "success", "rate": 7.2}, │ │ │ │ "news": {"status": "failed", "error": "timeout"} │ │ │ │ } │ │ │ └─────────────────────────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ [LLM 处理] → "北京气温 28°C，当前汇率 7.2，新闻信息获取失败" │ │ │ └────────────────────────────────────────────────────────────────┘
  • 每个工具独立超时和重试（错误隔离）
  • 根据业务场景选择错误策略（部分成功/全有全无/降级）
  • 用结构化合并（JSON 对象）而非文本拼接
  • 合并后检查总 Token 数（防止上下文溢出）
  • 日志记录每个工具的状态（success/failed/timeout）
  • 一个工具失败导致整个任务失败（无隔离）
  • 所有场景都用"全有全无"（过于严格）
  • 用文本拼接合并结果（LLM 解析困难）
  • 不检查合并后的 Token 数（上下文溢出）
  • 不记录工具状态（问题无法定位）
生产案例：某金融 Agent 的"投资组合分析"任务需要并行调用 6 个数据源（股票行情、基金净值、债券利率、汇率、新闻情绪、宏观经济指标）。初期采用"全有全无"策略，任一数据源超时则整体失败，导致任务成功率仅 72%（因为新闻 API 经常超时）。切换到"部分成功 + 降级替代"策略后：新闻 API 超时用缓存数据替代（降级），其他数据源失败返回 null（部分成功），任务成功率从 72% 提升至 94%。同时引入结果摘要压缩（每个数据源结果从平均 600 token 压缩到 150 token），LLM 处理时间从 3.2 秒降至 1.1 秒。

生产级性能优化

并行执行的性能优化不仅是"让工具跑得快"，更是"让整个流水线高效运转"——从依赖图生成、调度…

并行执行的性能优化不仅是"让工具跑得快"，更是"让整个流水线高效运转"——从依赖图生成、调度决策、工具执行、结果合并到 LLM 处理，每个环节都有优化空间。

五层优化策略

优化层优化目标优化方法预期效果
规划层依赖图生成速度缓存常见任务的依赖图模板规划时间从 800ms 降至 200ms
调度层调度决策延迟预计算拓扑排序，运行时直接执行调度延迟从 50ms 降至 5ms
执行层工具执行时间结果缓存 + 连接池复用重复查询延迟降低 90%
合并层结果合并 Token摘要压缩（LLM 提取关键信息）Token 减少 60~75%
LLM 层LLM 处理时间结构化输入 + 精简上下文LLM 响应时间降低 40%

结果缓存策略

对于"相同参数的工具调用"，可以直接返回缓存结果而非重新执行。缓存键为 tool_name + sorted(params)，缓存过期时间根据工具的"数据时效性"设定：天气数据缓存 10 分钟，汇率数据缓存 1 小时，静态配置数据缓存 24 小时。

连接池复用

并行调用多个外部 API 时，每个工具独立创建 HTTP 连接会导致"连接建立开销"（TCP 握手 + TLS 握手 ≈ 100~200ms）。通过连接池复用 HTTP 连接，可以将连接建立开销降低 80%。推荐连接池大小 = 并发上限 × 1.5（预留缓冲）。

总延迟 = max(并行组内最慢工具) + 合并时间 + LLM处理时间
性能优化案例：某客服 Agent 的"用户问题处理"任务需要并行调用 4 个工具（查用户信息、查订单、查知识库、查 FAQ）。优化前后对比：① 规划层：缓存常见问题的依赖图模板，规划时间从 600ms 降至 150ms；② 执行层：结果缓存命中率 35%，重复查询延迟从 800ms 降至 50ms；③ 合并层：结果摘要压缩，Token 从平均 3200 降至 900；④ LLM 层：结构化输入，LLM 响应时间从 2.5 秒降至 1.4 秒。整体端到端延迟从 5.8 秒降至 2.1 秒，降低 64%。

并行执行 vs 串行执行 vs 批处理

并行执行不是万能的——它在"多工具无依赖"场景中优势明显，但在"强依赖链"或"单工具"场景中…

并行执行不是万能的——它在"多工具无依赖"场景中优势明显，但在"强依赖链"或"单工具"场景中可能不如串行执行简单高效。选择合适的执行模式需要分析任务的依赖结构。

维度并行执行串行执行批处理
执行模式无依赖工具同时执行按顺序逐个执行收集一批请求后统一处理
延迟最低（并行组内取最慢）最高（所有工具时间之和）中（等待批次填满）
实现复杂度高（依赖图 + 调度 + 错误隔离）低（简单循环）中（批次管理 + 超时）
适用场景多工具且大部分无依赖强依赖链（每步依赖上一步）高并发请求（如批量查询）
资源利用高（并发利用 CPU/网络）低（串行等待）高（批量处理减少开销）
错误处理复杂（需要隔离 + 合并）简单（逐个处理）中（批次级错误处理）
选择建议：如果任务有 3+ 个无依赖工具 → 用并行执行（延迟降低 50%+）；如果工具之间有强依赖链（每步都依赖上一步）→ 用串行执行（实现简单）；如果是高并发场景（如同时处理 100 个用户请求）→ 用批处理（减少系统开销）。实际生产中常混合使用：整体任务用并行，强依赖子链用串行，高并发请求用批处理。

Q&A（8 题）

LLM 如何判断工具之间的依赖关系？准确率如何保证？
LLM 通过分析用户意图和工具描述来判断依赖关系。如果工具 B 的某个参数需要工具 A 的输出值，则有数据依赖。实践中推荐用 Structured Output 让 LLM 输出依赖图的 JSON 表示（如 {"parallel": ["A", "B"], "sequential": [["C", "D"]]}），引擎据此调度。准确率保障：① 在工具描述中明确标注"该工具的输入需要哪些其他工具的输出"；② 用 Few-shot 示例教 LLM 识别依赖关系；③ 对 LLM 生成的依赖图做后验检查（如检测是否有环、是否有未连接的孤立节点）。实测准确率可达 92~96%。
并行调用时如何合并结果给 LLM？哪种方式最好？
三种合并方式：① 按工具名拼接（"天气结果：...，汇率结果：..."）——简单但 LLM 解析困难；② 按执行顺序拼接（先完成的放前面）——保留时间信息但顺序不稳定；③ 结构化合并（将多个工具结果组装为一个 JSON 对象，如 {"weather": {...}, "exchange": {...}}）——LLM 解析能力最强，推荐。合并后的总 Token 数需要检查是否超过上下文窗口，超过则做摘要压缩（每个结果提取关键信息，控制在 200 token 以内）。
并发上限设为多少合适？如何动态调整？
并发上限取决于三个约束：① API rate limit（如 OpenAI 每分钟 60 次请求 → 并发上限 ≤ 10）；② LLM 上下文窗口（每个工具结果约 500~1000 token，5 个工具 = 2500~5000 token，需确保不超过窗口的 30%）；③ 系统资源（网络带宽、数据库连接池）。通常设 3~5 个并发上限。动态调整：监控 API 限流错误率，如果限流率 > 5% 则自动降低并发上限；如果限流率 < 1% 且资源充裕则适当提高。推荐公式：concurrency = min(rate_limit/10, context_window/3000, db_pool_size)。
动态调度和静态调度怎么选择？能否混合使用？
选择依据是"工具调用计划在规划阶段能否完全确定"。如果计划可完全确定（如"查 A、查 B、查 C 三个独立信息"），用静态 DAG 调度（可预测、易调试）。如果计划需要根据中间结果动态调整（如"先查 A，如果 A 的结果满足条件则查 B，否则查 C"），用动态事件驱动（灵活但调试困难）。大多数 Agent 场景推荐混合方案：整体计划用静态 DAG（确定哪些工具可并行），细节执行用动态回调（处理运行时异常和条件分支）。这种混合方案兼顾可预测性和灵活性。
工具 A 超时但工具 B 成功了，怎么处理？
取决于业务场景和错误策略。如果是"部分成功"策略（最常用）：工具 A 返回 null 或超时标记，工具 B 的结果正常返回给 LLM，LLM 根据已有结果生成回答并标注"部分信息获取失败"。如果是"全有全无"策略（关键流程）：取消所有工具调用，整体重试或降级到备选方案。如果是"降级替代"策略：工具 A 用备选工具或默认值替代（如天气 API 超时用缓存数据）。推荐默认使用"部分成功"，对关键工具单独配置"降级替代"。
并行执行会不会导致 API 限流？如何避免？
会，这是并行执行最常见的生产问题。避免策略：① 设并发上限（如最多 5 个工具同时执行），根据 API rate limit 动态调整；② 指数退避重试（限流后等待 1s、2s、4s 再重试）；③ 请求分散（将 10 个并行请求分成 2 批，每批 5 个，间隔 500ms）；④ 使用多个 API Key（不同 Key 有不同的 rate limit 配额）；⑤ 结果缓存（相同参数不重复调用）。监控指标：API 限流错误率，目标 < 2%。如果限流率持续 > 5%，需要降低并发上限或联系 API 提供商提高配额。
依赖图生成会不会成为性能瓶颈？如何优化？
依赖图生成通常需要 LLM 调用，耗时 500~1000ms，可能成为瓶颈。优化策略：① 依赖图模板缓存——对于常见任务类型（如"旅行规划"、"商品推荐"），预定义依赖图模板，运行时直接加载而非重新生成（耗时从 800ms 降至 50ms）；② 规则引擎——对于简单场景（如"查 A 和查 B"），用规则引擎（而非 LLM）判断依赖关系（如"相同工具+不同参数 = 无依赖"）；③ 异步生成——依赖图生成和工具执行流水线化，边生成边执行（生成 Phase 1 后立即执行，同时生成 Phase 2）。实测优化后依赖图生成耗时从 800ms 降至 150ms。
并行执行和 LangChain 的 RunnableParallel 是什么关系？
LangChain 的 RunnableParallel 是并行执行的一种实现——它允许将多个 Runnable（如 Tool 调用）并行执行，自动合并结果。但 RunnableParallel 是"无依赖并行"——它假设所有 Runnable 之间无依赖，不支持依赖图分析和阶段调度。如果需要更复杂的并行（如"Phase 1 并行 A/B/C，Phase 2 并行 D/E，其中 D 依赖 A"），需要自定义调度逻辑。建议：简单并行用 RunnableParallel，复杂依赖图用自定义 DAG 调度引擎（或 LangGraph 的 StateGraph）。
