概览

相似度阈值的本质是一道"质量门禁"——高于阈值的文档进入 LLM 上下文，低于阈值的被丢弃
┌─────────── 相似度阈值在 RAG 流水线中的位置 ───────────┐ │ │ │ Query ──→ Embedding ──→ 向量库 ANN 检索 ──→ Top-K │ │ │ │ │ ▼ │ │ ┌─────────────────┐ │ │ │ 阈值过滤 (门禁) │ │ │ │ score >= θ ? │ │ │ │ ┌───┐ ┌───┐ │ │ │ │ │ ≥θ │ │ <θ │ │ │ │ │ │通过│ │丢弃│ │ │ │ │ └─┬─┘ └───┘ │ │ │ └────┼────────────┘ │ │ ▼ │ │ ┌──────────────────┐ │ │ │ Rerank 重排序 │ │ │ │ Cross-encoder 评分│ │ │ └───────┬──────────┘ │ │ ▼ │ │ 最终 Top-N 输出给 LLM │ └───────────────────────────────────────────────────────┘

相似度阈值的本质是一道"质量门禁"——高于阈值的文档进入 LLM 上下文，低于阈值的被丢弃。设得太高会漏掉相关内容（低召回），设得太低会引入噪声（低精度）。没有"万能阈值"，但有"安全起点"和"调优路径"。

01

相似度分数的计算原理

讨论阈值之前必须先确认"这个分数是怎么算出来的"——不同度量方式的分值范围和方向完全不同，不…

讨论阈值之前必须先确认"这个分数是怎么算出来的"——不同度量方式的分值范围和方向完全不同，不确认度量就设阈值等于闭眼开枪。

1.1 三种主流度量方式

度量方式公式特征分值范围方向常见默认库
余弦相似度（Cosine）两向量夹角余弦值，不受模长影响[-1, 1]，归一化后 [0, 1]越大越相似多数向量库默认
点积（Dot Product）向量内积，受模长影响无固定范围越大越相似部分模型使用
L2 距离（欧氏距离）向量间直线距离[0, +∞)越小越相似Faiss 默认

关键原理：余弦相似度只衡量两个向量的"方向"是否一致，不受向量模长影响——这意味着即使两个文档长度差异很大，只要语义方向一致，余弦相似度仍然高。点积同时考虑方向和模长，长文档（模长大）的点积可能天然偏高。L2 距离的方向与前两者相反——距离越小越相似，设阈值时应设为上限而非下限。

关键前提：讨论阈值时必须先确认两件事：① 向量库使用的是哪种度量方式；② 是否做了归一化。同样的 0.7 在余弦相似度下表示"比较相似"，在点积下可能含义完全不同（取决于向量模长），在 L2 下方向还是反的。大多数 RAG 框架（LangChain、LlamaIndex）默认使用归一化后的余弦相似度，分值范围 [0, 1]。本文后续讨论均基于此默认值。
02

阈值经验值参考（归一化余弦相似度）

没有"万能阈值"，但有"安全起点"

没有"万能阈值"，但有"安全起点"。大多数场景从 0.7 开始调，再根据业务反馈微调。以下经验值基于归一化余弦相似度——如果你的向量库使用其他度量，不能直接套用。

2.1 阈值区间与效果对照

相似度分数轴 (归一化余弦, 0→1) │ │ 0.0 0.50 0.70 0.85 1.0 │ ├─────────┼─────────┼─────────┼─────────┤ │ │ 无过滤 │ 高召回 │ 平衡区间 │ 极高精度 │ │ │ (调试用) │ 噪声较多 │ (大多数 │ 极低召回 │ │ │ │ │ 系统) │ │ │ └─────────┴──────────┴─────────┴──────────┘ │ ↑ ↑ ↑ │ 创意/研究 通用问答 法律/医疗 │ 0.50-0.65 0.70-0.80 0.85-0.90
阈值区间效果特征精度/召回适用场景
0.85+极高精度，极低召回精度 95%+ / 召回 30-50%法律合规、医疗诊断——宁可不说也不能说错
0.70-0.85精度与召回平衡精度 80-90% / 召回 60-80%通用知识问答、技术文档检索——大多数 RAG 系统默认区间
0.50-0.70高召回，噪声较多精度 50-70% / 召回 85%+创意写作辅助、开放式问题探索——宁可多看也不漏
<0.50几乎无过滤精度 <50% / 召回 ~100%仅用于调试和数据分析，不适合生产

2.2 阈值对 Precision-Recall 的影响

阈值和精度/召回之间存在经典的 trade-off：阈值升高 → 只有高相似度文档通过 → 精度升高但召回下降（漏掉相关内容）；阈值降低 → 更多文档通过 → 召回升高但精度下降（引入噪声）。最优阈值通常是 F1 分数（精度和召回的调和平均值）最高的点。

生产案例：某电商客服系统最初设阈值 0.65，用户满意度 72%，"答非所问"率高（精度不够）。调高到 0.80 后满意度升至 85%，但"答非所问"率从 3% 升至 8%（因为很多问题检索不到结果，触发了兜底话术——阈值太高导致召回不足）。最终采用动态策略：FAQ 类问题 0.82，投诉类问题 0.68，满意度稳定在 89%（+17pp）。
03

动态调参策略

固定阈值在单一场景下可能足够，但真实的 RAG 系统面对多种 query 类型

固定阈值在单一场景下可能足够，但真实的 RAG 系统面对多种 query 类型。动态调参的核心思想：根据 query 的复杂度和意图，自适应调整阈值——事实类问题严选，开放类问题宽选。

3.1 策略一：按 Query 类型分级

Query 类型示例推荐阈值原因
事实类"Python 的 GIL 是什么？"0.80有明确答案，需要精准匹配
流程类"如何部署 Kubernetes 集群？"0.72需要多步文档，适度宽选
开放类"如何设计一个好的 API？"0.60没有标准答案，需要广泛参考
探索类"有哪些前沿的 AI 应用方向？"0.55发散性搜索，宁可多召回

3.2 策略二：Top-K + 阈值双控

先按相似度排序取 Top-K（如 K=10），再在 Top-K 中用阈值过滤。这样即使阈值设得低，也不会返回大量低质量结果——Top-K 限制了数量上限，阈值保证了质量底线。这是生产环境中最常用的策略。

为什么先 Top-K 再阈值？如果先阈值过滤再 Top-K，当阈值很低时可能返回成百上千个结果，不仅浪费 LLM 的上下文窗口，还增加生成延迟。先 Top-K 再阈值确保最终输入 LLM 的文档数量可控。

3.3 策略三：基于用户反馈的自适应

收集用户反馈（点赞/点踩），统计不同阈值下的用户满意度曲线。定期（如每周）根据反馈数据微调阈值。这是一种"越用越准"的策略，但需要足够多的用户交互数据才有统计意义。建议在系统上线初期用固定阈值，积累 1000+ 次交互后开启自适应。

核心结论：生产环境推荐"Top-K + 阈值双控"作为基础策略，再叠加 Query 类型分级。具体参数：默认 Top-10 + 阈值 0.70，事实类问题自动切换到 Top-5 + 阈值 0.80，开放类问题切换到 Top-20 + 阈值 0.55。这套组合在多数场景下 F1 分数提升 10-15%。
04

业务场景适配

不同业务对"说错"和"不说"的容忍度差异巨大

不同业务对"说错"和"不说"的容忍度差异巨大。阈值设置应反映业务优先级——法律/医疗场景宁可不说也不能说错（高阈值），研究辅助宁可多看也不能漏（低阈值）。

4.1 各业务场景阈值配置表

业务场景核心诉求推荐阈值配套策略错误容忍方向
客服 FAQ精准回答，不能误导0.80-0.85高阈值 + 兜底话术宁可不答也不能答错
技术文档搜索找到相关文档即可0.70-0.75中阈值 + Rerank精度和召回平衡
研究助手尽可能多召回参考资料0.55-0.65低阈值 + Top-20宁可多看也不漏
法律/医疗零容错，必须有据可依0.85-0.90高阈值 + 人工审核宁可不答也不能答错
代码搜索找到功能相关代码0.70-0.80中阈值 + AST 验证精度优先
创意写作广泛参考灵感0.50-0.60低阈值 + Top-15宁可多召回

4.2 Rerank 与阈值的协同

推荐的完整过滤链路：向量检索 Top-K → Rerank 重排序 → 阈值过滤 → 最终 Top-N。Rerank 模型（如 Cohere Rerank、bge-reranker）对检索结果做二次排序，分数比向量相似度更准确。在 Rerank 之后再设阈值，可以更精准地过滤低质量结果。如果先阈值过滤再 Rerank，可能把"向量分数低但语义实际相关"的文档提前丢弃。

过滤顺序优点缺点推荐场景
先阈值后 Rerank减少 Rerank 的计算量可能丢弃"向量分低但实际相关"的文档性能敏感场景
先 Rerank 后阈值 ✅阈值过滤更准确（基于更准的 Rerank 分数）Rerank 计算量略大质量敏感场景（推荐）
  • 从 0.7 起步，根据业务反馈微调（±0.05 步进）
  • 用 Top-K + 阈值双控，避免极端情况（空结果或噪声泛滥）
  • 按 query 类型设置不同阈值（事实类高、开放类低）
  • 先 Rerank 后阈值过滤，利用更准确的 Rerank 分数
  • 定期用标准测试集评估 Precision@K 和 Recall@K
  • 不确认度量方式就设阈值（L2 和余弦方向相反）
  • 全场景使用同一个固定阈值（不同 query 类型需要不同阈值）
  • 阈值设太高导致检索结果为空且无兜底逻辑
  • 先阈值过滤再 Rerank（可能丢弃实际相关的文档）
  • 忽略向量库是否做了归一化（非归一化的分数范围不同）
05

阈值兜底策略：检索为空时怎么办

阈值设得再合理，也难免出现检索结果为空的情况（query 与知识库内容不相关）

阈值设得再合理，也难免出现检索结果为空的情况（query 与知识库内容不相关）。此时必须有兜底策略——否则用户会看到一个空白回复，体验极差。

5.1 三级降级策略

级别触发条件处理方式效果
L1：降低阈值重试高阈值下检索结果为空自动降低阈值（如 0.80 → 0.65）重试一次召回约 60% 的"漏网"结果
L2：放宽到 LLM WIK降低阈值后仍为空不传 context，让 LLM 用自身知识回答，标注"基于通用知识"保证用户不会看到空白
L3：预设兜底话术LLM 也无法回答返回预设话术："抱歉，暂未找到相关信息，建议咨询 XX"最后的保底方案
生产案例：某法律咨询 RAG 系统分析 3 个月的检索日志发现：15% 的请求因阈值 0.88 过高导致首次检索为空，其中 9% 通过 L1 降级（降到 0.75）成功检索到结果，5% 通过 L2 由 LLM 回答（标注"非专业法律意见"），仅 1% 触发 L3 兜底话术。三级降级使系统的"无回复率"从 15% 降到 1%。
06

Q&A

为什么不同向量库的相似度分数不能直接比较？
因为不同库使用的度量方式不同：余弦相似度范围是 [0,1]（归一化后），值越大越相似；L2 距离范围是 [0,+∞)，值越小越相似；点积没有固定范围，受向量模长影响。同样是 0.7，在余弦下表示"比较相似"，在点积下可能含义完全不同（取决于向量是否归一化）。必须先确认度量方式和是否归一化，再设定阈值。如果不确定，可以做一个简单实验：用几个已知相关的文档对计算分数，观察分布范围。
阈值设太高导致检索结果为空怎么办？
三级降级策略：L1 — 自动降低阈值重试（如从 0.80 降到 0.65），可召回约 60% 的"漏网"结果；L2 — 仍为空则不传 context，让 LLM 用自身知识回答，明确标注"基于通用知识，建议验证"；L3 — LLM 也无法回答时返回预设兜底话术。生产环境建议三级结合。另外，可以记录"检索为空"的 query 日志，分析是否知识库覆盖不足，作为知识库扩展的依据。
Top-K 和阈值应该先过滤哪个？为什么？
推荐先 Top-K 再阈值。先按相似度排序取 Top-K（如 K=10），再在 Top-K 中用阈值过滤掉低于标准的结果。原因：如果先阈值过滤再 Top-K，当阈值很低时可能返回成百上千个结果，不仅浪费 LLM 的上下文窗口（增加 token 成本和延迟），还可能引入大量低质量噪声。先 Top-K 确保数量可控（最多 K 个），再阈值确保质量达标。
如何评估当前阈值是否合理？有具体的评估方法吗？
标准评估方法：准备一个包含 50-100 个标准 query 的测试集，每个 query 标注了"应该命中的文档"。然后分别计算不同阈值下的 Precision@K（前 K 个结果中正确的比例）和 Recall@K（应该命中的文档中实际命中的比例）。选择 F1 分数最高的阈值作为最优值。进阶方法：画出 Precision-Recall 曲线，找到曲线上的"肘部"（边际收益递减点）。同时持续监控线上用户反馈数据（点赞/点踩），每周回顾是否需要微调。
Rerank 模型和阈值过滤的顺序应该怎么安排？
推荐顺序：向量检索 Top-K → Rerank 重排序 → 阈值过滤。原因：Rerank 模型（如 Cohere Rerank、bge-reranker）对检索结果做二次排序，分数比向量相似度更准确——它能发现"向量分数低但语义实际相关"的文档。在 Rerank 之后再设阈值，可以更精准地过滤真正的低质量结果。如果先阈值过滤再 Rerank，可能把一些"向量分数低但语义实际相关"的文档提前丢弃，导致 Rerank 无法挽救。
不同的 Embedding 模型对阈值选择有多大影响？
影响很大。不同模型即使都输出归一化余弦相似度，分数的分布也可能差异显著。例如 bge-large-zh 的相关文档对通常在 0.75-0.95 之间，而 text-embedding-ada-002 可能在 0.65-0.88 之间。这意味着"0.7" 在 bge 下可能过滤掉太多结果，在 ada-002 下则刚好。建议每次更换 Embedding 模型后重新跑评估测试集，重新确定最优阈值——不能直接沿用旧模型的阈值。
