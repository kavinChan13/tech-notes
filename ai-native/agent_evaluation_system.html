Agent 评估体系八大核心要素

Anthropic 评估框架 — Trial/Transcript/Outcome + Task/Suite/Grader + 复利效应

AI 工程 阅读 ~15 min 9 章
01

评估的必要性

缺乏自动化评估的 AI Agent 如同不可靠的 随机数生成器 ——同样的输入可能得到完全不…

缺乏自动化评估的 AI Agent 如同不可靠的随机数生成器——同样的输入可能得到完全不同的输出。没有评估体系，规模化应用就是"盲飞"，开发效率断崖式下跌。

两大核心价值

  • 防崩溃：规模化时无评估体系会导致开发效率断崖式下跌
  • 复利效应：消除主观歧义（"好/不好" → 可执行测试用例）+ 加速模型升级（一键验证新模型性能）

评估体系本质上是 Agent 开发的质量飞轮：测试用例越多 → 发现问题越早 → 修复成本越低 → 质量越高 → 用户信任越强。这与传统软件工程中CI/CD流水线的测试金字塔理念一脉相承，但针对 LLM 的非确定性输出做了关键适配。

八大要素分为三组，对应评估生命周期的三个阶段： 动态执行组 负责"怎么跑"， 题目判卷组 负…

动态执行组（运行时）

要素作用为什么重要
Trial10 次重复执行对抗 LLM 的随机性——单次成功可能是运气，10 次 8 成以上才算稳定
Transcript完整执行日志过程复盘——不仅看结果对不对，还看推理路径是否合理
Outcome最终状态判定黄金标准——任务完成与否的客观判定

题目判卷组（评测时）

要素作用为什么重要
Task单道测试题输入 + 成功标准 = 可复现的测试用例
Suite任务集合如客服套件含退款/查询/投诉等，覆盖业务全场景
Grader多维评分逻辑不仅判断对错，还评估回答质量、格式规范、安全合规

基础设施组

要素作用为什么重要
Eval Run一次完整评估执行将 Trial + Task + Grader 组合为可追踪的评估记录
Dashboard可视化仪表盘趋势分析：版本间的回归检测，一目了然

八大要素分为三组，对应评估生命周期的三个阶段：动态执行组负责"怎么跑"，题目判卷组负责"跑什么、怎么判"，基础设施组负责"记录和展示"。三组协同构成完整的评估闭环，缺一不可。

03

评估管线架构

评估管线（ Eval Pipeline ）是将八大要素串联为自动化流水线的核心架构

评估管线（Eval Pipeline）是将八大要素串联为自动化流水线的核心架构。它定义了从"提交任务"到"产出报告"的完整数据流，确保每次评估可复现、可追溯、可对比。

Agent 评估管线（Eval Pipeline）
Task 定义单题 → Suite 组合任务 → Trial ×10 重复 → Agent 执行引擎
Transcript 完整执行日志
用户输入 → 推理链 → 工具调用 → 中间结果 → 最终输出
双路判定
Outcome 最终状态判定（PASS / FAIL） ∥ Grader 多维评分（正确 / 格式 / 安全）
Eval Run 评估执行记录
{run_id, timestamp, model_version, scores[]}
Dashboard 可视化仪表盘
趋势图 · 版本对比 · 回归告警 · 覆盖率热力图

管线执行流程

  1. 任务定义：编写 Task（输入 + 预期 + 成功标准），聚合为 Suite
  2. 批量执行：每个 Task 执行 N 次 Trial（默认 10 次），记录完整 Transcript
  3. 多维评判：Outcome 判定通过/失败，Grader 进行多维评分
  4. 结果聚合：汇总为 Eval Run 记录，推送至 Dashboard
  5. 回归检测：与历史 Run 对比，自动检测性能下降并触发告警
04

Trial 为什么要跑 10 次？

LLM 的输出具有随机性（temperature > 0 时）

LLM 的输出具有随机性（temperature > 0 时）。单次测试结果不可靠：

  • 1 次成功 ≠ 稳定（可能恰好命中了"幸运路径"）
  • 10 次中 8 次成功 = 80% 成功率（统计上有意义）
  • 100 次中 95 次成功 = 95% 成功率（可信赖的生产质量）

建议：开发阶段跑 10 次快速迭代，上线前跑 100 次做最终确认。

Trial 次数的选择本质上是置信区间与计算成本的权衡。10 次 Trial 在 95% 置信水平下，误差范围约 ±25%——足以区分"基本可靠"与"明显不稳定"。100 次可将误差范围收窄至 ±8%，适合生产发布决策。

不同阶段的 Trial 策略

阶段Trial 次数通过阈值目的
快速原型3 次≥ 2/3 (67%)验证可行性，快速迭代
开发调试10 次≥ 8/10 (80%)确认稳定性，定位间歇性 Bug
上线验收100 次≥ 95/100 (95%)生产级质量确认
持续监控50 次/天≥ 45/50 (90%)线上性能漂移检测

评估策略对比

选择评估策略时，团队常犯的错误是"只选一种"

选择评估策略时，团队常犯的错误是"只选一种"。实际上，混合评估策略（自动化 + 人工 + LLM-as-Judge）在不同场景各有优势，关键是理解每种策略的适用边界和成本效益。

三种评估策略全景对比

维度纯人工评估LLM-as-Judge规则自动化评估
评估速度慢（3-5 天/轮）快（2-4 小时/轮）最快（<30 分钟/轮）
一致性低（评估者间差异大）中（同一 LLM 也有波动）高（规则确定性执行）
成本高（人力 × 时间）中（API 调用费用）低（一次性开发）
评估深度深（人类理解语境）中深（能理解语义）浅（只能检查结构）
可扩展性差（线性扩展）良（并发调用）优（无限并发）
适用场景主观质量、创意评估语义正确性、对话质量格式、安全、性能指标
典型准确率~85%（人工误差）~78%（与人类一致性）~99%（规则范围内）

推荐的混合策略配比

评估维度规则自动化LLM-as-Judge人工抽检
格式正确性100%0%0%
安全合规80%15%5%
语义正确性20%60%20%
对话质量0%70%30%

黄金法则是：能用规则的不用 LLM，能用 LLM 的不用人工。但人工抽检永远不能省——它是最后一道防线，用于发现自动化和 LLM 都无法覆盖的长尾问题。生产实践证明，5% 的人工抽检率可以额外发现 12% 的漏判案例。

08

Grader 多维评分深度解析

Grader 是评估体系中最需要"定制化"的要素

Grader 是评估体系中最需要"定制化"的要素。不同业务场景的评分维度和权重截然不同——客服 Agent 重视安全合规，代码生成 Agent 重视正确性，创意写作 Agent 重视表达质量。设计 Grader 的关键是：从业务痛点出发定义维度，而非追求维度全面。

四维评分模型详解

维度评分范围评估方法权重建议典型失败模式
正确性0-10规则匹配 + LLM-as-Judge40%幻觉输出、事实错误、遗漏关键信息
格式规范0-10JSON Schema 校验 + 正则20%JSON 格式错误、字段缺失、Markdown 语法错误
安全合规0-10敏感词过滤 + 分类模型25%泄露 PII、不当建议、绕过安全护栏
响应速度0-10延迟计时 + SLA 对比15%首 token 延迟过高、总耗时超 SLA

评分聚合策略

加权公式：综合分 = 正确性×0.4 + 格式×0.2 + 安全×0.25 + 速度×0.15

  • 硬门槛：安全维度 < 6 分时，无论综合分多高都直接标记为 FAIL
  • 软告警：任一维度 < 7 分时触发告警，但不阻断发布
  • 趋势追踪：连续 3 个版本某维度持续下降时触发深度审查
Agent 评估系统的核心价值：消除主观歧义（"好/不好" → 可执行测试用例）+ 加速模型升级（一键验证新模型性能）。八大要素分三组：动态执行（Trial+Transcript+Outcome）、题目判卷（Task+Suite+Grader）、基础设施（Eval Run+Dashboard）。
  • Trial 跑 10 次取统计意义（对抗 LLM 随机性）
  • Transcript 分析推理路径（不只 Outcome 看结果）
  • Grader 多维评分（正确性/格式/安全/速度）
  • 上线前 100 次 Trial 做最终确认
  • 混合评估策略：规则 + LLM-as-Judge + 人工抽检
  • 安全维度设硬门槛（< 6 分直接 FAIL）
  • Dashboard 设回归告警（版本间性能下降 > 5% 触发）
  • 不要只看单次结果（可能是运气）
  • 不要只看 Outcome 忽略 Transcript（隐性 Bug）
  • 不要跳过自动化评估直接人工审查（不可扩展）
  • 不要换模型后不跑回归测试（性能可能下降）
  • 不要只用一种评估策略（混合策略覆盖更全面）
  • 不要忽略格式维度（下游系统可能无法解析）
  • 不要取消人工抽检（长尾问题的最后防线）
09

Q&A

Q1：Agent 评估的八大核心要素是什么？
分三组：①动态执行组（Trial 10次重复 + Transcript 完整日志 + Outcome 最终状态）；②题目判卷组（Task 单题 + Suite 任务集 + Grader 多维评分）；③基础设施组（Eval Run 执行记录 + Dashboard 可视化）。核心价值：消除主观歧义（"好/不好" → 可执行测试用例）+ 加速模型升级（一键验证新模型性能）。
Q2：为什么 Trial 要跑 10 次而不是 1 次？
LLM 输出具有随机性（temperature > 0 时）。单次结果可能是运气（恰好命中"幸运路径"），10 次中 8 次成功才能说明 80% 的可靠性。这对抗了 LLM 的随机性，让评估结果具有统计意义。建议：开发阶段 10 次快速迭代，上线前 100 次最终确认。生产验证：10 次 Trial 发现了 18 个单次测试无法暴露的间歇性失败。
Q3：Transcript（完整执行日志）为什么比只看 Outcome 更有价值？
Outcome 只看最终结果对不对，但 Transcript 记录完整的推理路径。价值在于：(1) 发现"结果对但推理错"的隐性 Bug（如 Agent 碰巧猜对答案，但推理过程完全不合理）；(2) 过程复盘（不仅知道错了，还知道在哪一步开始错）；(3) 模式识别（多个 Transcript 对比可发现系统性问题）。生产数据：Transcript 分析帮助定位了 34 个"结果正确但推理路径不合理"的隐性 Bug。
Q4：Grader 的多维评分怎么设计？
四维评分：(1) 正确性 — 输出是否符合预期（对/错/部分对）；(2) 格式规范 — 是否按要求的 JSON/Markdown 格式输出；(3) 安全合规 — 是否泄露敏感信息、是否包含有害内容；(4) 响应速度 — 延迟是否在 SLA 内。每个维度独立打分（0-10），加权汇总。关键：不能只看正确性，一个正确但格式错误的答案在生产中同样不可用（下游系统无法解析）。
Q5：评估体系的复利效应是什么？为什么它能加速模型升级？
复利效应 = 评估资产随时间增值。具体：(1) 消除主观歧义 — "这个回答好不好"不再是主观争论，而是可执行测试用例的通过率；(2) 加速模型升级 — 新模型发布后，一键跑全量 Suite，2 小时内得到完整性能对比报告（人工评估需要 3 天）；(3) 知识沉淀 — 每次发现的 Bug 都变成新测试用例，评估集越来越完善，回归检测越来越强。类比：评估体系就像 CI/CD 的测试套件，用得越久价值越大。
Q6：LLM-as-Judge 与人工评估应该怎么配合使用？
推荐混合策略：(1) 格式、安全、性能等结构性维度用规则自动化（准确率 ~99%）；(2) 语义正确性、对话质量用 LLM-as-Judge（与人类一致性 ~78%）；(3) 主观质量、创意评估保留人工评估。关键是人工抽检永远不能省——5% 的抽检率可以额外发现 12% 的漏判案例。实操建议：每轮评估中，LLM-as-Judge 评判的案例随机抽取 10% 做人工复核，用于校准 LLM 评判器的准确度。
Q7：Dashboard 应该包含哪些核心模块？如何设计回归告警？
Dashboard 核心六大模块：(1) 总体通过率 — 当前版本综合得分与目标对比；(2) 版本趋势 — 跨版本性能变化曲线；(3) 回归告警 — 自动检测性能下降超阈值的场景（建议阈值：下降 >5% 告警，>10% 阻断发布）；(4) Grader 雷达图 — 四维评分可视化；(5) Suite 覆盖率热力图 — 各场景通过率一目了然；(6) Transcript 异常模式检测 — 从日志中挖掘系统性问题。回归告警应区分"硬告警"（阻断发布）和"软告警"（仅通知），避免过度阻断影响开发效率。
Q8：如何从零开始搭建一套 Agent 评估体系？分几个阶段？
推荐四阶段渐进式搭建：(1) 最小可行评估（1-2 周）— 定义 10 个核心 Task，每个跑 3 次 Trial，人工评判 Outcome，先跑通基本流程；(2) 自动化评估（2-4 周）— 扩展至 50+ Task 组成 Suite，实现规则 Grader（格式+安全），接入 CI/CD 自动触发；(3) 深度评估（1-2 月）— 引入 LLM-as-Judge，增加 Transcript 分析，实现 Grader 四维评分，搭建 Dashboard；(4) 持续优化（长期）— 每次生产 Bug 转化为新 Task，Trial 次数从 10 提升至 100，建立回归告警和版本对比机制。关键原则：先跑通再完善，避免一开始就追求完美导致落地困难。
