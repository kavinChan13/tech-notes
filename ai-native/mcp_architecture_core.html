核心设计哲学：MCP（Model Context Protocol）由 Anthropic 于 2024 年发布，是一个开放标准协议，旨在解决 LLM 应用的"工具集成碎片化"问题。其架构包含三个角色：MCP Host（用户直接交互的 LLM 应用）、MCP Client（Host 内部的协议客户端，管理与 Server 的连接）、MCP Server（提供工具/资源/提示词的服务端）。一个 Host 可以同时连接多个 Server（如同时连接 GitHub + 数据库 + 文件系统），每个 Server 独立运行、互不干扰。Client 和 Server 之间通过 JSON-RPC 2.0 协议通信，支持双向调用（Client→Server 和 Server→Client）。

JSON-RPC 2.0 协议深度解析

JSON-RPC 2

JSON-RPC 2.0 是 MCP 的"通信语言"——所有 Client 和 Server 之间的交互都通过 JSON-RPC 消息进行。它的设计哲学是"简单、双向、可扩展"，支持请求-响应和通知两种模式。

消息类型对比

消息类型方向是否需要响应用途示例
RequestClient → Server✅ 需要响应调用工具、获取资源调用 create_issue 工具
ResponseServer → Client—返回请求结果返回创建的 Issue ID
Notification双向❌ 无需响应状态更新、事件通知Server 通知"工具列表已更新"
ErrorServer → Client—返回错误信息工具执行失败，返回错误码和消息

JSON-RPC 消息结构

每个 JSON-RPC 消息都包含四个核心字段：jsonrpc（协议版本，固定为"2.0"）、method（方法名称）、params（参数，可选）、id（请求 ID，用于匹配响应）。Request 消息必须有 id，Notification 消息没有 id（因为不需要响应）。

JSON-RPC 2.0 消息流转
Client Request Server
{ · "jsonrpc": "2.0", · "method": "tools/call", · "params": { · "name": "get_weather", · "arguments": {"city": "北京"} · }, · "id": "req-123" · }
Client Response Server
{ · "jsonrpc": "2.0", · "result": { · "content": "晴，28°C" · }, · "id": "req-123" · }
Client Notification Server
{ · "jsonrpc": "2.0", · "method": "notifications/tools/list_changed" · } · （无 id，无需响应）
关键特性：JSON-RPC 2.0 的 Notification 机制是 MCP 的"实时通知通道"——Server 可以在工具列表变化、资源更新时主动通知 Client，而不需要 Client 轮询。这种"推送模式"比"轮询模式"更高效（减少无效请求）且更实时（变化立即通知）。但 Notification 是"尽力而为"的——如果 Client 断开连接，期间的通知会丢失，Client 重连后需要重新同步状态。

三大能力原语深度解析

MCP Server 通过三种原语暴露能力：Tools（工具，可执行的操作）、Resourc…

MCP Server 通过三种原语暴露能力：Tools（工具，可执行的操作）、Resources（资源，可读取的数据）、Prompts（提示词模板，可复用的 prompt）。三者组合覆盖了 LLM 与外部世界交互的所有场景——读数据（Resources）、做操作（Tools）、用模板（Prompts）。

Tools：动作原语

Tools 是最常用的原语——LLM 决定调用哪个工具、传什么参数，Server 执行后返回结果。Tools 是"动词"，代表可执行的操作（如 create_issue、run_query、send_email）。每个 Tool 都有明确的 JSON Schema 定义参数结构，LLM 根据 Schema 生成正确的参数。

Resources：数据原语

Resources 让 LLM 能"看到"外部数据（如文件内容、数据库表结构），但不会修改数据。Resources 是"名词"，代表可读取的数据源。与 Tools 的关键区别：Tools 有副作用（如创建 Issue），Resources 是只读的（如读取文件）。Resources 支持两种访问方式：直接读取（resources/read）和订阅更新（resources/subscribe）。

Prompts：模板原语

Prompts 允许 Server 提供预定义的提示词模板，Host 可以直接使用而不用每次手写 prompt。例如 GitHub Server 可以提供"代码审查"prompt 模板（接受 diff 参数），数据库 Server 可以提供"SQL 生成"prompt 模板（接受 schema 和自然语言描述）。Prompts 实现了 prompt 的标准化和复用。

原语语义方向是否有副作用示例使用频率
Tools动作（动词）Client → Server✅ 有（增删改查）create_issue、run_query、send_email最高（80%+）
Resources数据（名词）Server → Client❌ 无（只读）文件内容、数据库 schema、配置信息中（15%）
Prompts模板（句式）Server → Client❌ 无（只生成 prompt）代码审查模板、Bug 分析模板低（5%）

三大原语的协同模式

实际场景中三大原语常协同工作：① 先通过 Resources 读取数据（如数据库 schema），② 再用 Prompts 生成分析 prompt（如"根据以下 schema 生成 SQL 查询"），③ 最后用 Tools 执行操作（如 run_query 执行生成的 SQL）。这种"读数据→生成方案→执行操作"的模式覆盖了 90% 的 Agent 工作流。

  • Tools 用于有副作用的操作（创建、修改、删除）
  • Resources 用于只读数据访问（查询、读取）
  • Prompts 用于标准化常用工作流（代码审查、Bug 分析）
  • 每个 Tool 提供清晰的 JSON Schema 参数定义
  • 敏感 Tools 标记为"需要用户确认"
  • 用 Tools 做只读查询（应该用 Resources）
  • 用 Resources 做写操作（违反只读语义）
  • 把所有操作都做成 Tools（缺乏语义区分）
  • Tool 参数不用 JSON Schema（LLM 无法正确传参）
  • 敏感操作不设确认机制（安全风险）
生产案例：某企业 Agent 平台接入 MCP 后，工具集成时间从"每个工具 2~3 周"（定制 API 开发）降至"每个工具 1~2 天"（实现 MCP Server）。平台已接入 47 个 MCP Server，提供 312 个 Tools、89 个 Resources、23 个 Prompts。最活跃的 Server 是"内部知识库 Server"（日均调用 12,000 次），其次是"JIRA Server"（日均调用 8,500 次）和"数据库 Server"（日均调用 6,200 次）。

传输层设计：stdio vs SSE

MCP 支持两种传输方式：stdio（标准输入输出，用于本地）和 SSE + HTTP（用于…

MCP 支持两种传输方式：stdio（标准输入输出，用于本地）和 SSE + HTTP（用于远程）。选择哪种传输方式取决于部署场景——本地开发用 stdio（简单高效），生产环境用 SSE（支持分布式）。

两种传输方式对比

维度stdioSSE + HTTP选择建议
通信方式标准输入输出（stdin/stdout）Server-Sent Events + HTTP POST—
部署场景本地进程间通信跨机器、跨网络本地 vs 远程
性能零网络开销，延迟 < 1ms网络延迟 10~100ms性能敏感用 stdio
安全性本地进程隔离，天然安全需要 TLS 加密安全敏感用 stdio
扩展性单机单进程支持分布式部署大规模用 SSE
实现复杂度低（直接读写 stdin/stdout）中（需要 HTTP 服务器 + SSE 客户端）快速原型用 stdio

stdio 传输机制

stdio 模式下，MCP Server 作为子进程运行，Host 通过 stdin 发送 JSON-RPC 消息，通过 stdout 接收响应。每条消息以换行符分隔。优点是零网络开销、实现简单；缺点是只能单机使用、不支持多 Host 共享同一 Server。

SSE + HTTP 传输机制

SSE 模式下，Client 通过 HTTP POST 发送请求，Server 通过 SSE 推送响应和通知。SSE（Server-Sent Events）是单向推送通道（Server→Client），HTTP POST 是请求通道（Client→Server）。这种"双通道"设计支持双向实时通信。生产环境必须使用 TLS 加密（HTTPS），防止数据窃听和篡改。

选择建议：本地开发和小规模部署用 stdio（简单、高效、安全）；生产环境和分布式部署用 SSE + HTTP + TLS（支持跨网络、多 Host 共享 Server）。混合部署：核心 Server（如数据库）用 stdio 部署在 Host 同机器，外部 Server（如第三方 API）用 SSE 远程连接。

三层安全机制

MCP 的安全模型基于"最小权限原则"——每个 Server 只暴露必要的 Tools 和…

MCP 的安全模型基于"最小权限原则"——每个 Server 只暴露必要的 Tools 和 Resources，Host 可以控制哪些 Server 对 LLM 可见。敏感操作（如删除文件、发送邮件）必须设为"需要用户确认"（human-in-the-loop）。

传输层安全

本地 stdio 模式天然安全（进程隔离，无网络暴露）。远程 SSE 模式必须使用 TLS 加密（HTTPS），防止数据窃听和中间人攻击。Server 应验证 Client 的身份（如 API Key 或 OAuth Token），防止未授权的 Client 接入。

权限层安全

Host 配置 Server 白名单，只有白名单中的 Server 才能被 LLM 调用。每个 Server 只暴露最小必要的 Tools（如数据库 Server 只暴露 run_query，不暴露 drop_table）。权限配置应遵循"最小权限原则"——LLM 只能访问完成任务所需的最小工具集。

操作层安全

敏感操作（如删除文件、发送邮件、执行 SQL DDL）应设为需要用户确认（human-in-the-loop）。MCP 协议支持 Server 标记某些 Tools 为 requiresConfirmation，Host 在调用前弹出确认框。用户确认后才会执行操作，防止 LLM 自主执行危险操作。

安全层机制防护目标实现方式
传输层本地 stdio / 远程 SSE + TLS防止数据窃听和篡改进程隔离 / HTTPS 加密
权限层Host 配置 Server 白名单防止未授权的 Server 接入配置文件 + API Key 验证
操作层敏感操作需用户确认防止 LLM 自主执行危险操作requiresConfirmation 标记 + 确认框
  • 每个 Server 只暴露最小必要的 Tools
  • 敏感操作设 human-in-the-loop 确认
  • 远程 Server 用 SSE + TLS 加密传输
  • 定期审计 Server 的 Tool 调用日志
  • Server 验证 Client 身份（API Key / OAuth）
  • 一个 Server 暴露所有工具（权限过大）
  • 删除/修改操作不设确认机制
  • 远程 Server 用明文 HTTP 传输
  • 忽略 Tool 调用的频率和模式异常
  • 不验证 Client 身份（任何人可接入）
生产案例：某金融 Agent 平台在接入 MCP 后，通过三层安全机制防止了 3 次潜在安全事故：① LLM 尝试调用 drop_table 工具（未在白名单中，被权限层拦截）；② LLM 尝试删除用户数据（标记为 requiresConfirmation，用户拒绝确认）；③ 外部 Server 尝试未授权接入（API Key 验证失败，被传输层拦截）。平台已安全运行 180 天，处理 230 万次 Tool 调用，零安全事故。

MCP vs Function Calling vs 定制 API

MCP 不是唯一的工具集成方案——Function Calling（单个 LLM API 的…

MCP 不是唯一的工具集成方案——Function Calling（单个 LLM API 的特性）和定制 API（为每个工具写专用集成代码）各有适用场景。MCP 的优势在于"标准化"和"可复用"，但实施成本高于 Function Calling。

维度MCPFunction Calling定制 API
层次应用级协议（独立标准）模型级 API（LLM 特性）应用级（专用集成）
标准化✅ 开放标准，跨 LLM 通用❌ 每个 LLM API 格式不同❌ 每个工具定制开发
可复用性✅ Server 可被多个 Host 复用❌ 工具定义绑定特定 LLM❌ 集成代码绑定特定应用
实施成本中（需要实现 MCP Server）低（直接定义 JSON Schema）高（每个工具定制开发）
扩展性高（新增工具只需新增 Server）中（需要修改 LLM 配置）低（需要修改应用代码）
适用场景多工具、多 LLM 的复杂系统单 LLM、少量工具的简单应用高度定制化的专用系统
选择建议：如果你的系统需要接入 10+ 个工具且可能换 LLM → 用 MCP（标准化、可复用）；如果是单 LLM、少量工具的快速原型 → 用 Function Calling（实施快）；如果是高度定制化的专用系统且工具不会变化 → 用定制 API（性能最优）。实际生产中常组合使用：MCP 做工具集成层，MCP Server 内部使用 Function Calling 调用 LLM。
07

Q&A（8 题）

MCP 和 Function Calling 的核心区别是什么？能否一起用？
核心区别在于"层次"和"标准化"。Function Calling 是单个 LLM API 的特性（如 OpenAI 的 tools 参数），定义了 LLM 如何调用函数，但每个 LLM 的格式不同（OpenAI vs Anthropic vs Google）。MCP 是一个独立的协议标准，定义了 LLM 应用（Host）如何通过统一接口连接外部工具服务器（Server），跨 LLM 通用。MCP 更高层——它解决的是"应用级别的工具集成"问题，而 Function Calling 解决的是"模型级别的工具调用"问题。二者可以一起用：MCP Server 内部可以使用任何 LLM API 的 Function Calling 能力。
MCP 支持哪些传输方式？如何选择合适的传输方式？
两种传输方式：① stdio（标准输入输出），用于本地进程间通信，Server 作为子进程运行，通过 stdin/stdout 交换 JSON-RPC 消息，零网络开销，延迟 < 1ms，天然安全（进程隔离）。② SSE + HTTP（Server-Sent Events + HTTP POST），用于远程通信，支持跨机器、跨网络调用，延迟 10~100ms，需要 TLS 加密。选择建议：本地开发和小规模部署用 stdio（简单、高效、安全），生产环境和分布式部署用 SSE + HTTP + TLS（支持跨网络、多 Host 共享 Server）。混合部署：核心 Server 用 stdio 部署在 Host 同机器，外部 Server 用 SSE 远程连接。
如何开发一个 MCP Server？需要多少代码？
MCP 提供了 Python 和 TypeScript SDK，核心步骤：① 定义 Tools（名称、描述、参数 JSON Schema）；② 实现 Tool 处理函数；③ 启动 Server 监听连接。一个最简 Server 约 50 行代码（Python SDK）。Server 需要描述自己的 Tools（让 LLM 知道有哪些工具可用），并处理 Client 的调用请求。推荐使用官方 SDK（而非自己实现协议），SDK 已封装 JSON-RPC 通信、Tool 注册、错误处理等基础设施。
MCP Server 之间能互相调用吗？为什么？
MCP 协议本身不支持 Server 间直接通信（避免循环调用和权限传递问题）。如果需要 Server 间协作，应通过 Host 层编排：Host 调用 Server A 获取结果，再调用 Server B 使用该结果。这种"星型拓扑"（所有通信都经过 Host）保持了架构的清晰性和安全性——Host 可以控制所有交互，防止 Server 间形成不受控的调用链。如果 Server 间需要频繁协作，考虑将相关功能合并到同一个 Server 中。
MCP 的 Prompts 原语有什么实际用途？使用频率高吗？
Prompts 允许 Server 提供预定义的提示词模板，Host 可以直接使用而不用每次手写 prompt。实际用途：① GitHub Server 提供"代码审查"prompt 模板（接受 diff 参数，生成审查意见）；② 数据库 Server 提供"SQL 生成"prompt 模板（接受 schema 和自然语言描述，生成 SQL 查询）；③ 文档 Server 提供"摘要生成"prompt 模板（接受长文档，生成摘要）。使用频率相对较低（约 5%），但在标准化工作流（如代码审查、Bug 分析）中非常有价值——它确保了所有用户都使用相同的 prompt 格式，提高了一致性和可维护性。
MCP 的安全机制够吗？如何应对 LLM 自主执行危险操作？
MCP 的三层安全机制（传输层、权限层、操作层）覆盖了大部分安全场景。关键防线：① 传输层用 TLS 加密防止数据窃听；② 权限层用 Server 白名单防止未授权接入；③ 操作层用 human-in-the-loop 确认防止 LLM 自主执行危险操作。对于高风险操作（如金融交易、数据删除），建议额外增加：④ 操作审计日志（记录所有 Tool 调用）；⑤ 频率限制（防止 LLM 短时间内大量调用）；⑥ 异常检测（监控 Tool 调用模式，发现异常告警）。安全是持续的过程，需要定期审计和更新策略。
MCP Server 的性能如何？会成为瓶颈吗？
MCP Server 的性能取决于两个因素：① 协议开销（JSON-RPC 序列化/反序列化 + 网络传输），② Tool 执行时间（如数据库查询、API 调用）。协议开销很小（JSON-RPC 消息通常 < 10KB，序列化耗时 < 1ms），不是瓶颈。真正的瓶颈是 Tool 执行时间——如果某个 Tool 需要调用慢速外部 API（如 3 秒响应），该 Tool 的延迟就是 3 秒。优化策略：① 异步执行（Tool 返回任务 ID，Client 轮询结果）；② 结果缓存（相同参数不重复执行）；③ 并行调用（多个无依赖 Tool 同时执行）。生产环境监控每个 Tool 的 P95 延迟，超过 5 秒的 Tool 需要优化。
MCP 和 LangChain 的 Tool 系统是什么关系？
LangChain 的 Tool 系统是应用内部的工具抽象（定义了 Tool 的接口和调用方式），MCP 是跨应用的工具集成协议（定义了 Host 如何连接外部 Server）。二者可以互补：LangChain 应用可以作为 MCP Host，通过 MCP 协议连接外部 Server 获取工具；MCP Server 返回的 Tools 可以转换为 LangChain 的 Tool 对象，供 Agent 使用。这种组合实现了"LangChain 做 Agent 逻辑，MCP 做工具集成"——LangChain 负责推理链和状态管理，MCP 负责连接外部工具服务器。
