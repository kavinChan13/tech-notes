引言：这篇文章真正回答的问题

Claude Code 值得拆，不是因为它"功能很多"，而是因为它 很像一套已经真正在承接复…

Claude Code 值得拆，不是因为它"功能很多"，而是因为它很像一套已经真正在承接复杂度的 Agent 系统。

真正决定一个 Agent 能不能长期活下去的，往往不是模型，而是围着模型搭起来的运行时。

这篇文章回答的核心问题是：

  • 它到底怎么设计
  • 为什么要这样设计
  • 这样设计的价值是什么
  • 我们做自己的 Agent 时，哪些最值得吸收
02

入口与启动链路：别急着拉起全世界

很多系统的入口都是一个越来越胖的 main ，恨不得一上来就把全世界都拉起来

核心矛盾

很多系统的入口都是一个越来越胖的 main，恨不得一上来就把全世界都拉起来。一个成熟 Agent 往往同时要支持本地交互、headless、SDK、remote、后台 session、会话恢复。如果启动层不先把模式、边界、权限和上下文装配清楚，后面每个宿主都会偷偷长出自己的运行语义。

三段启动

① 入口分流
→
② 进程级初始化
→
③ 会话级准备
阶段职责关键细节
入口分流判断这次到底是什么启动本地交互、无界面运行、远程接入、后台会话管理、极简 fast path；很多路径用动态加载，控制启动成本
进程级初始化处理运行环境配置、telemetry、远程设置、清理回调、全局设施；刻意不碰当前会话语义
会话级准备确定当前会话制度当前工作目录、会话身份、工具面、权限模式、扩展能力、系统约束、恢复方式

进程状态 vs 交互状态

这是架构里一个非常关键的细节：

类别内容存放位置
进程状态cwd、projectRoot、sessionId、telemetry、token/cost 计数bootstrap/state 全局状态
交互状态tasks、MCP clients、plugin 状态、permission context、界面选择AppState
这个分层让系统不会把 React state 误当成整套 runtime 的唯一真相，也不会把所有状态都做成不可控的全局变量。

为什么这样好

  • 无界面运行、交互式运行、远程运行、后台运行可以共享同一套核心 runtime
  • 权限、工具、系统约束、扩展能力在第一轮请求前定型，主循环不需要一边跑一边猜
  • 系统复杂度被前置：模式判断、权限边界、宿主差异不会拖到运行中解决
  • 先分流，再装配，最后才进入会话
  • 先装配共享 session/runtime 语义，再选择宿主
  • 先区分进程状态和交互状态
  • 不要做一个"大 main 把所有东西拉起来"
  • 不要把启动模式判断拖到运行中
  • 不要把进程基础设施和会话控制面混在一起
03

会话与主循环：7 种恢复条件与 transition 字段

主循环是所有 Agent 系统最容易"变形"的地方

核心矛盾

主循环是所有 Agent 系统最容易"变形"的地方。随着需求增加，循环里会塞满各种恢复逻辑、错误处理、状态转换，最终变成一个巨大的 if-else 泥球。

QueryDeps 最小接口

query.ts 中的 QueryDeps 只有 4 个方法签名：

方法职责
callModel调用 LLM
compact上下文压缩
uuid生成唯一标识
now获取当前时间
这个最小接口在测试中可以轻松 fake，覆盖了循环触及的每一个外部依赖。transition 字段命名了每次迭代继续的原因，使得恢复路径无需检查消息内容即可测试。

7 种恢复条件

主循环通过 transition 字段显式记录每次迭代继续的原因：

  1. tool_use：工具调用后继续
  2. end_turn：正常结束
  3. max_output_tokens：升级到 64k 后重试（最多 3 次）
  4. 413 prompt_too_long：触发 collapse 和 reactive compact
  5. network error：网络错误恢复
  6. rate limit：限流恢复
  7. budget remaining：token 预算剩余，注入 nudge message

为什么这样好

  • 每种恢复条件有明确的 transition 命名，恢复逻辑不再隐藏在消息内容里
  • 最小接口使得循环可以在测试中完全脱离真实依赖运行
  • 单次恢复策略：每种错误最多尝试一次恢复，防止无限重试死循环
04

工具系统：统一接口与工具面组合

工具一多就容易互相污染：输入输出格式不统一、权限模型不一致、工具面组合逻辑散落在各处

核心矛盾

工具一多就容易互相污染：输入输出格式不统一、权限模型不一致、工具面组合逻辑散落在各处。

统一 Tool 接口

每个工具实现 Tool<Input, Output> 接口，包含：

属性作用
name工具名称
description给模型看的描述
inputSchemaZod schema 定义输入
call执行函数
isReadOnly是否只读（影响权限）
isDestructive是否破坏性（影响权限）

工具面组合

工具面（tool surface）是在启动时组装的，不是运行时动态发现的：

  • Commands、tools、permissions、skills、plugins、MCP servers 都在启动时被过滤和适配
  • 模型能看到和调用的，是这个组装步骤的产物
  • 工具面在会话开始前就定型，主循环不需要一边跑一边猜
这种设计的价值在于：工具面的边界在启动时就确定，运行时的不确定性被大幅降低。新增工具不需要修改主循环，只需要注册到工具面。
05

权限系统：分层规则与自动审批

权限系统需要同时满足两个看似矛盾的需求：安全性（严格限制）和可用性（减少打扰）

核心矛盾

权限系统需要同时满足两个看似矛盾的需求：安全性（严格限制）和可用性（减少打扰）。

分层权限模型

层级来源作用
全局权限用户设置跨项目的基础权限
项目权限项目 CLAUDE.md项目特定的权限规则
会话权限当前会话状态临时授予或拒绝的权限
工具权限工具自身声明isReadOnly / isDestructive 影响默认行为

自动审批机制

当用户多次批准某个操作后，系统可以自动提升权限：

  • 相同工具 + 相同路径模式 → 自动批准
  • 有"冷却时间"，避免误操作扩散
  • 用户可以随时撤销自动批准
关键设计判断：权限不是"模型自己决定的"，而是"系统根据规则决定的"。模型只能请求，不能绕过。这是安全性的基石。
06

上下文与压缩：三级压缩管道

上下文窗口会被迅速填满

核心矛盾

上下文窗口会被迅速填满。压缩是有损的，但如果不压缩，系统就无法持续运行。

三级压缩

级别触发条件行为损失
snip每轮自动删除最老的轮次丢失最早期对话
microcompact消息过长时压缩冗长的工具输出丢失输出细节
autocompact接近 token 上限全历史摘要丢失细粒度要求

重要约束如果只存在于对话里而没有外置到 CLAUDE.md/hook/task list，就会在压缩中丢失。这是"正常会发生的事"。

为什么这样好

  • 三级压缩是分级的，不是"要么全留要么全丢"
  • 压缩时机和策略是显式的，不是隐式的
  • 系统鼓励用户把重要信息外置，而不是依赖对话记忆
07

扩展层：Skills / Plugins / MCP / Hooks

扩展能力需要足够灵活，但又不能破坏系统的核心语义

核心矛盾

扩展能力需要足够灵活，但又不能破坏系统的核心语义。

四种扩展机制

机制核心作用加载时机对主循环的影响
Skills按需知识与流程描述常驻，正文按需零（在独立上下文）
Plugins第三方功能扩展启动时加载通过工具面间接影响
MCP连接外部系统启动时连接通过工具面间接影响
Hooks生命周期自动化事件触发时通过 system reminder 注入
关键设计判断：扩展能力通过工具面和 system reminder 间接影响主循环，而不是直接修改主循环逻辑。这使得扩展可以在不破坏核心语义的前提下增加能力。

Skills 的渐进式加载

Skills 在启动时只加载名字和描述（几十个 token），完整内容等到被调用时才进上下文。用完之后如果上下文满了，最旧的 skill 会被踢掉。

  • CLAUDE.md 放的是 Claude 需要随时知道的事实
  • Skill 放的是需要按步骤执行的流程
08

Sub-Agent 与多 Agent：5 种类型与 fork vs fresh

多 Agent 编排需要隔离上下文，但又需要共享足够的信息来协作

核心矛盾

多 Agent 编排需要隔离上下文，但又需要共享足够的信息来协作。

5 种 Agent 类型

类型上下文继承工具面用途
explore继承主 Agent只读工具调查、搜索、阅读
plan继承主 Agent只读 + 写计划制定计划
custom继承主 Agent自定义用户指定的特定任务
subagent独立上下文完整工具面独立执行，只返回结论
teammate独立上下文完整工具面持久化协作，可交互

fork vs fresh spawn

方式上下文来源适用场景
fork从主 Agent 分叉当前上下文需要主 Agent 的当前状态
fresh从 system prompt 开始全新上下文独立任务，不需要主 Agent 状态

Coordinator Mode 与 Swarm

当任务复杂到需要数十个 Agent 时，可以使用 Coordinator Mode：

  • 编排逻辑代码化为 JavaScript 脚本
  • 每个子任务在独立上下文窗口里运行
  • 中间结果保存在脚本变量中，只返回 consolidated result
Coordinator Script
→
Sub-Agent A (worktree)
+
Sub-Agent B (worktree)
+
Sub-Agent N (worktree)
→
Consolidated Result

Worktree 隔离

当多个会话需要并行修改同一仓库时，Worktree 让每个隔离会话在独立目录和分支中推进。SubAgent 支持 isolation: worktree，既在独立上下文里思考，也在独立 worktree 里动手。

关键设计判断：Sub-Agent 的价值不是"更快"，而是"更稳"。主会话的上下文不会被中间结果淹没，每个子任务在隔离环境中完整执行。

对我们的启示

哪些复杂度应该前置

  • 启动模式判断：不要拖到运行中解决
  • 权限边界：在第一轮请求前定型
  • 工具面组装：在会话开始前确定
  • 扩展能力注册：在启动时加载，不是运行时发现

哪些复杂度应该制度化

  • 上下文压缩：三级管道，显式策略
  • 权限分层：全局/项目/会话/工具四层
  • 主循环恢复：7 种 transition，每种最多尝试一次
  • 状态分层：进程状态 vs 交互状态

哪些复杂度必须通过架构收敛

  • 多 Agent 编排：5 种类型 + fork/fresh + coordinator
  • 工具面组合：启动时组装，运行时不变
  • 扩展影响：通过工具面和 system reminder 间接影响，不直接修改主循环
  • 把启动做成三段：入口分流、进程初始化、会话准备
  • 区分进程状态和交互状态
  • 用最小接口（4 个方法）隔离主循环的外部依赖
  • 用 transition 字段显式记录每次迭代继续的原因
  • 让扩展通过工具面和 system reminder 间接影响主循环
  • 鼓励用户把重要信息外置到 CLAUDE.md/hook/task
  • 不要做一个"大 main 把所有东西拉起来"
  • 不要把模式判断、权限边界拖到运行中解决
  • 不要在主循环里塞满 if-else 恢复逻辑
  • 不要让扩展直接修改主循环逻辑
  • 不要依赖对话记忆来保存重要约束
  • 不要让 Sub-Agent 继承主 Agent 的全部权限

常见问题

📖 知识来源：
为什么 Claude Code 的启动要做三段分流？
因为一个成熟 Agent 要同时支持多种运行模式（本地交互、headless、SDK、remote、后台 session）。如果启动层不先把模式、边界、权限和上下文装配清楚，后面每个宿主都会偷偷长出自己的运行语义，最终系统会裂成几套。三段分流（入口分流、进程初始化、会话准备）让这些复杂度在启动时就确定下来。
QueryDeps 为什么只有 4 个方法？
这是"最小接口"设计的典范。4 个方法（callModel、compact、uuid、now）覆盖了循环触及的每一个外部依赖。这个最小接口在测试中可以轻松 fake，使得循环可以在测试中完全脱离真实依赖运行。如果接口更大，测试成本会显著增加。
transition 字段的作用是什么？
transition 字段显式记录每次迭代继续的原因（tool_use、end_turn、max_output_tokens、413、network error、rate limit、budget remaining）。这使得恢复路径无需检查消息内容即可测试，恢复逻辑不再隐藏在消息内容里。每种恢复条件有明确的命名，系统行为更加可预测。
5 种 Agent 类型的设计逻辑是什么？
5 种类型覆盖了不同的隔离需求：explore/plan/custom 继承主 Agent 上下文，适合需要主 Agent 状态的任务；subagent/teammate 有独立上下文，适合独立执行。fork vs fresh 进一步细化：fork 从主 Agent 分叉当前状态，fresh 从 system prompt 开始全新上下文。这种分层使得系统可以选择"最便宜的 Agent 类型来完成工作"。
为什么扩展不能直接修改主循环？
直接修改主循环会破坏系统的核心语义，使得主循环越来越脏。Claude Code 的设计是让扩展通过工具面和 system reminder 间接影响主循环：Skills/MCP 通过工具面增加能力，Hooks 通过 system reminder 注入上下文。这样扩展可以在不破坏核心语义的前提下增加能力，主循环保持简洁。
上下文压缩的三级策略有什么区别？
三级压缩是分级的：snip 每轮自动删除最老轮次；microcompact 在消息过长时压缩冗长工具输出；autocompact 在接近 token 上限时对全历史做摘要。损失也是分级的：snip 丢失最早期对话，microcompact 丢失输出细节，autocompact 丢失细粒度要求。重要约束如果只存在于对话里而没有外置，就会在 autocompact 中丢失。
这篇文章和 H03、H01 有什么区别？
H03（架构进化）侧重设计哲学和演进历程；H01（架构深度解析）侧重架构模式和使用方法（五层架构、八种上下文注入、六种编排模式）；本文（H02）侧重源码实现决策，从"核心矛盾→解法→为什么这样好"的角度讲透 7 个核心模块。三者形成完整链路：为什么这样设计 → 怎么设计、怎么用 → 代码怎么实现。
