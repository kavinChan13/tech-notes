01

分块的本质与全链路影响

分块决定了信息的基本单元质量 — 如果关键信息在分块时被切断，后续任何检索和生成优化都无法弥…

分块决定了信息的基本单元质量 — 如果关键信息在分块时被切断，后续任何检索和生成优化都无法弥补源头的信息损失。分块错误是不可恢复的。

Chunking（分块）是将长文档切割为小片段的过程。每个 chunk 被独立 embedding 并存入向量数据库，因此分块质量直接决定了 RAG 检索的上限。实验证明：在同一量级 embedding 模型内，分块策略的影响往往大于 embedding 模型选择的影响 — chunk_size 从 200 调到 500 可能让 Recall@5 从 0.6 提升到 0.8，而换更好的 embedding 模型通常只提升 3-5%。

分块过大 vs 过小

维度Chunk 过大Chunk 过小
Embedding 质量语义被稀释，一个向量包含多个主题缺乏上下文，语义不完整
检索精度噪声多（包含不相关内容）碎片化信息，难以命中
LLM 利用Token 浪费，含大量无关内容信息断裂，LLM 难以理解
存储成本chunk 数少，索引小chunk 数多，索引大
黄金法则：一个 chunk 应该包含一个完整的、独立可理解的语义单元。chunk_size 应该匹配用户期望问的问题的"答案粒度"。

分块质量的连锁反应

分块质量决定 RAG 全链路（问题无法在下游修复）
好分块
精准 embedding → 高 Recall/Precision → LLM 拿到好 context → 好回答
差分块
模糊 embedding → 召回不相关/遗漏关键 → LLM 拿到噪声 → 差回答 / 幻觉
02

五大分块策略深度对比

没有"万能"的分块方式

没有"万能"的分块方式。选择取决于文档类型、查询模式和模型能力 — 递归字符分割是 80% 场景的最佳起点。

策略一：固定长度分块

按固定 token 数切割文本，简单粗暴。按 token 而非字符切割更合理，因为 embedding 模型按 token 计算限制。优点是实现简单、结果可预测；缺点是不尊重语义边界，可能把完整句子或段落切断，表格和代码块也可能被切碎。适合文本格式统一、对分块质量要求不高的快速原型场景。

策略二：递归字符分割（推荐默认）

RecursiveCharacterTextSplitter 是 LangChain 中最推荐的通用分割器。核心思想是按层级分隔符依次尝试切割：优先按双换行（段落）→ 换行 → 句号 → 空格 → 字符。如果某段太长，自动用下一级分隔符进一步分割。分隔符顺序很重要：从大粒度到小粒度，确保优先保持段落和句子完整。

中文文档的分隔符需要特别调整，在句号后加入感叹号、问号、分号、逗号等中文标点。它在固定长度的约束下尽量保持语义完整，是固定分割和语义分割之间的最佳折中。

策略三：语义分块（Semantic Chunking）

不按固定长度，而是按语义相似度决定切割点：当相邻句子的语义相似度骤降时，说明话题发生了切换，应在此处分割。需要对所有句子做 embedding 后计算相邻余弦相似度，取全文相似度分布的某百分位（如 75th percentile）作为阈值。

优点缺点
每个 chunk 是语义完整的话题单元需要额外 embedding 计算（慢）
不会在话题中间切断chunk 大小不可控（可能过大或过小）
对多话题文档效果好阈值需要调优，百万文档时需批量化和缓存

策略四：结构化分块

利用文档本身的结构标记来分块。Markdown 文档按 Header 层级（# / ## / ###）切割，每个 chunk 自动携带其所属标题层级的 metadata，可用于过滤检索。代码文件按函数/类边界切割（AST 解析），绝不在函数中间切断。HTML 文档按标签结构分块。表格建议整表保留为一个 chunk，或表头 + 每行作为独立 chunk（每行都包含表头做上下文）。

策略五：命题级分块（Proposition-level）

又称 Dense X Retrieval，将每个句子拆为独立的命题（自包含的事实陈述）进行索引。例如"LangChain 支持 OpenAI 和 Anthropic 两种模型"拆为三个命题：LangChain 支持 OpenAI、LangChain 支持 Anthropic、LangChain 支持两种模型。检索精度最高，但索引量最大，适合事实性 QA 场景。

五大策略综合对比

策略语义完整度实现复杂度计算开销适用场景
固定长度低极低极低快速原型、格式统一文本
递归字符分割中低低通用场景（推荐默认）
语义分块高中高多话题长文、论文报告
结构化分块高中低Markdown/代码/HTML
命题级分块极高高极高事实性 QA、知识库
03

Overlap 与上下文连续性

Overlap 防止关键信息恰好落在切割边界而丢失

Overlap 防止关键信息恰好落在切割边界而丢失。推荐值为 chunk_size 的 10-20%，但语义分块和 Parent-Child 策略下其重要性大幅降低。

Overlap 的作用与代价

Overlap（重叠）让切割点附近的内容同时出现在两个 chunk 中。例如 chunk_size=1000、overlap=200 时，Chunk 1 覆盖 [0, 1000]，Chunk 2 覆盖 [800, 1800]，Chunk 3 覆盖 [1600, 2600]。

如果一句话被切成两半分属两个 chunk，两边都无法形成完整语义，overlap 就是防止这种断裂的保险措施。但 overlap 也有代价：增加索引大小（每个字符被存储多次）、增加检索噪声（同一内容可能被多次检索到）。

推荐 Overlap = chunk_size × 10%~20%
例：chunk_size=500 → overlap=50~100

什么时候 Overlap 不重要

  • 语义分块时：切割发生在自然边界（话题切换处），不会在句子中间切断
  • Parent-Child 策略时：child chunk 之间不需要 overlap，parent 已提供完整上下文
  • 结构化分块时：按 Markdown Header 切割天然保持段落完整
04

Parent-Child：小块检索，大块返回

Parent-Child 解决"检索粒度 vs 生成粒度"的核心矛盾 — 检索需要小粒度（精…

Parent-Child 解决"检索粒度 vs 生成粒度"的核心矛盾 — 检索需要小粒度（精确聚焦），生成需要大粒度（上下文丰富）。

核心架构

文档先切为大的 parent chunk（如 1000 字），每个 parent 再切为小的 child chunk（如 200 字）。child chunk 做 embedding 存入向量数据库用于检索，parent chunk 存入文档存储。查询时检索到 child chunk，但返回其 parent chunk 给 LLM。

原始文档
parent_splitter (chunk_size=1000)
Parent Chunk 1 Parent Chunk 2
↓ child_splitter(200) ↓ · [C1a][C1b][C1c][C1d] [C2a][C2b]...
Child chunks → embedding → 向量数据库（检索用）
Parent chunks → 文档存储（返回给 LLM） · 查询 → 检索到 C1b → 返回 Parent Chunk 1 → LLM 生成

为什么 Parent-Child 效果好

小 chunk 检索时每个 chunk 只聚焦一个概念，embedding 语义更集中，Precision 更高。大 chunk 返回给 LLM 时提供完整的段落上下文，LLM 能更好地理解语义关系。比单一粒度分块通常提升 5-15% 的 Answer Quality。

策略索引粒度返回粒度适用场景
标准分块中 (500-1000)中通用简单场景
Parent-Child小 (100-200)大 (1000-2000)需要精确定位 + 丰富上下文
Summary 索引文档摘要全文/大块文档级检索
命题级索引单个事实原始段落事实性 QA
  • Parent-Child 是解决"检索粒度 vs 生成粒度"矛盾的经典方案
  • LangChain 中通过 ParentDocumentRetriever 一行代码即可实现
  • child chunk 的 parent_id 是关联两者的关键 metadata
05

Contextual Retrieval：给每个 Chunk 加上上下文

孤立的 chunk 丢失了"我在文档中的位置和角色"这一关键信息

孤立的 chunk 丢失了"我在文档中的位置和角色"这一关键信息。Contextual Retrieval 通过给每个 chunk 生成上下文前缀，让 embedding 更好地理解 chunk 的含义。

Anthropic 的方法

用 LLM 读取整个文档 + 当前 chunk，生成一段上下文描述前缀。例如："这段内容来自关于 RAG 架构的技术文档的第三章，主要讨论了重排序算法的实现。"加入前缀后再做 embedding，使得向量更好地表示 chunk 的语义和上下文关系。

Anthropic 实验显示可降低 49% 的检索失败率（配合 BM25 混合检索更高）。代价是需要对每个 chunk 调用一次 LLM 生成前缀，但这是离线一次性操作。

简化版：手动加 Context Header

不用 LLM，手动给每个 chunk 加上文档标题和章节标题作为前缀，也能有明显提升。例如在每个 chunk 开头加上"文档: RAG 架构设计\n章节: 检索组件\n\n"。这种方式零额外成本，适合结构化文档（有明确标题层级）。

关键洞察：embedding 模型只看到 chunk 文本本身，不知道它来自哪个文档、哪个章节。Contextual Retrieval 弥补了这个信息差 — 让同一个句子在不同文档上下文中产生不同的向量表示。
06

Chunk Size 选择指南

没有"最佳 chunk size"— 500 tokens 是好的起点，但需要根据文档类型…

没有"最佳 chunk size"— 500 tokens 是好的起点，但需要根据文档类型、查询模式和评估结果调整。

影响因素矩阵

因素倾向大 chunk倾向小 chunk
文档类型叙事性长文（论文/报告）FAQ / 技术文档 / 问答对
查询类型复杂问题（需要上下文）精确事实问题
Embedding 模型支持长输入（8K tokens）短输入限制（512 tokens）
LLM 窗口窗口大（32K+）窗口小（4K）
成本约束不在乎 token 成本严格控制成本

经验参考值

场景推荐 chunk_size
FAQ / 短问答100-300 tokens
技术文档300-500 tokens
论文 / 报告500-1000 tokens
法律合同300-500 tokens（按条款）
代码文件按函数/类，通常 500-2000 tokens
聊天记录按对话轮次或时间窗口

Embedding 模型输入限制需注意：OpenAI ada-002 支持 8191 tokens，但 BGE/E5 只有 512 tokens（建议 chunk < 450）。即使模型支持长输入，chunk 太长仍然会稀释语义。

实验确定最佳 Chunk Size

在评估集上对比不同 chunk_size 的 Recall@K、Precision@K 和 Answer Quality。通常存在一个"甜蜜点"：太小则 recall 高但 precision 低（检索到太多碎片），太大则 recall 低但 precision 高（每个 chunk 都包含很多信息但匹配不精确）。对于混合类型文档，可以按文档类型使用不同分块策略（路由器模式）。

  • 从 500 tokens 开始，用评估集实验调优
  • 尊重语义边界，不在句子/段落中间切断
  • 每个 chunk 携带来源、标题层级等 metadata
  • 加 Context Header 提升 embedding 质量
  • 分块前先清洗：去页眉页脚、水印、无意义符号
  • 盲目追求最大/最小 chunk size
  • 所有文档类型用同一分块策略
  • 忽略表格和代码的特殊处理
  • 不设 overlap 就用固定长度分块
  • 不跑评估就确定分块参数
07

策略选择矩阵与最佳实践

分块策略变更意味着全量重建索引，需要评估后谨慎决定

文档类型 → 推荐策略

文档类型推荐策略理由
纯文本 / 新闻递归字符分割通用、稳健、易实现
技术文档 (Markdown)Markdown Header + 递归尊重文档结构，保留层级信息
论文 / 长报告语义分块保持话题完整性
代码仓库代码感知分块尊重函数/类边界
FAQ / 问答对按 QA 对为单位天然的语义单元
混合文档多策略路由不同部分用不同策略

生产环境注意事项

分块策略变更意味着全量重建索引，需要评估后谨慎决定。建议保存原始文档和 chunk 的映射关系，方便后续调整和追溯。表格是 RAG 的难点：embedding 模型对表格结构理解差，建议整表保留或加自然语言描述。代码 chunk 的 embedding 建议使用专用模型（如 CodeBERT）或至少在代码上 fine-tune 过的通用模型。

08

Q&A

因为分块决定了信息的基本单元质量
为什么说分块策略比 embedding 模型选择更重要？

因为分块决定了信息的基本单元质量。如果关键信息在分块时被切断，或一个 chunk 混合了多个不相关话题，无论 embedding 模型多强大，都无法产生好的向量表示。实证：chunk_size 从 200 调到 500 时，同一 embedding 模型的 Recall@5 可能从 0.6 提升到 0.8，而换更好的 embedding 模型通常只提升 3-5%。分块错误是不可恢复的 — 检索层和生成层都无法弥补源头的信息损失。

语义分块和递归字符分割各有什么优缺点？什么时候用哪个？

递归字符分割：优点是简单快速、chunk 大小可控；缺点是不完全尊重语义边界。语义分块：优点是每个 chunk 是完整话题单元；缺点是需要额外 embedding 计算且 chunk 大小不可控。选择建议：①格式规整的文档 → 递归字符分割（快且够好）②多话题混合长文 → 语义分块 ③有 Markdown/HTML 结构 → 结构化分块 ④FAQ → 按 QA 对分。递归字符分割是 80% 场景的最佳起点。

Parent-Child 策略解决什么矛盾？实际效果如何？

解决"检索需要小粒度（精确聚焦），生成需要大粒度（上下文丰富）"的矛盾。文档先切为 parent chunk（如1000字），再切为 child chunk（如200字）。child 做 embedding 和检索，命中后返回 parent 给 LLM。效果：比单一粒度分块通常提升 5-15% 的 Answer Quality。适用场景：技术文档、论文等需要上下文才能理解的长文本。LangChain 中通过 ParentDocumentRetriever 一行代码即可实现。

Overlap 设多少合适？什么时候可以不用 Overlap？

经验值是 chunk_size 的 10-20%（如 chunk=500 则 overlap=50-100）。过小无法覆盖完整句子，过大浪费存储且增加检索噪声。可以不用 Overlap 的场景：①语义分块（在自然边界切割）②Parent-Child 策略（parent 已提供完整上下文）③结构化分块（按 Header 切割天然保持段落完整）。核心认知：Overlap 是固定长度分块的保险措施，智能分块策略下其重要性大幅降低。

Contextual Retrieval 的核心思想和效果是什么？

核心思想：embedding 模型只看到 chunk 文本，不知道它在文档中的位置和角色。Anthropic 的做法是用 LLM 为每个 chunk 生成上下文前缀（如"这段来自 RAG 文档第三章，讨论重排序算法"），加入前缀后再做 embedding。效果：降低 49% 的检索失败率（配合 BM25 混合检索更高）。简化版：不用 LLM，手动加文档标题 + 章节标题作为前缀，零额外成本也有明显提升。关键：让同一个句子在不同文档上下文中产生不同的向量表示。

如何为代码文件和表格设计分块策略？

代码分块原则：尊重语法结构，不在函数/类中间切断。用 AST 解析按函数/方法/类为单位切块，每个 chunk 加文件名和类名作为上下文。过长的函数可按逻辑块（空行分隔）二次切割。建议使用代码专用 embedding 模型（如 CodeBERT）。表格是 RAG 难点：embedding 模型对表格结构理解差，建议整表保留为一个 chunk（如不太大），或表头 + 每行作为独立 chunk（每行都包含表头做上下文）。对于超大表格，可用 LLM 先生成自然语言描述再索引。

如何通过实验确定最佳 chunk size？

系统化实验框架：①选一组 chunk_size 候选值（如 200/300/500/800/1000/1500）②对每个值分别分块、重建索引、在评估集上测试 Recall@K 和 Precision@K ③找到"甜蜜点"（太小 recall 高 precision 低，太大反之）④在最佳候选上进一步微调 overlap。关键：每次只改一个变量，使用相同的评估集和指标。对于混合文档，不同部分可能需要不同 chunk size — 此时用路由器模式按文档类型分发到不同分块策略。
