Harness 的本质是"模型的底盘 + 变速箱" — 模型提供原始算力（引擎），Harness 决定算力能否有效转化为生产力。同一模型在不同 Harness 下表现差异可达 20%+，证明工程化层比模型选择更重要。

01

什么是 Harness？

在 AI Agent 系统中， 模型（Brain） 只是"大脑"，而 Harness 是围绕…

Brain vs Harness：模型不等于系统

在 AI Agent 系统中，模型（Brain）只是"大脑"，而 Harness 是围绕大脑构建的编排层 / 执行框架。类比：模型是飞行员，Harness 是整架飞机（航电系统、自动驾驶、安全检查、黑匣子）。

维度Brain（模型）Harness（编排层）
职责推理、生成、决策调度、状态管理、工具执行、安全约束
决定了什么"想"得多好"做"得多可靠
可替换性换模型需重新测试架构不变，模型可热替换
出错时幻觉、推理偏差状态丢失、死循环、权限泄漏
2026 竞争力模型差距在缩小Harness 工程是真正的差异化

2026 核心观点：模型能力在趋同（GPT-4o / Claude / Gemini 差距不大），真正决定产品质量的是 Harness 工程——上下文管理、错误恢复、工具编排、安全约束。Harness engineering is the new moat.

Harness 的核心职责

  • 上下文构建：决定模型每次看到什么信息（system prompt + 历史 + 工具结果）
  • 工具编排：调用哪些工具、按什么顺序、结果如何流转
  • 状态管理：维护 session、处理中断恢复、持久化关键数据
  • 安全约束：权限控制、操作审计、不可逆操作拦截
  • 质量保障：输出验证、回退策略、多 Agent 评审

深度理解：Harness > Model 原理 — 2026 年模型能力趋同后，产品差异来自编排质量、可靠性和安全性。Harness 的本质 = 把不确定的模型输出变成可靠的系统行为。类比：数据库引擎（Brain）vs 事务管理+故障恢复+查询优化器（Harness）— 引擎再快，没有事务保证就是数据灾难。

02

Three-Agent Harness Pattern（Anthropic 三代理模式）

受 GAN（生成对抗网络）启发：Generator 和 Discriminator 分离

核心思想：生成者不能评估自己的工作

受 GAN（生成对抗网络）启发：Generator 和 Discriminator 分离。Anthropic 在其 Agent 系统中采用 Planner → Generator → Evaluator 三阶段模式，每个阶段由独立的模型实例处理。

Agent角色输入输出
Planner任务分解与规划用户请求 + 约束结构化计划 / 子任务列表
Generator执行具体工作单个子任务 + 工具集代码 / 文本 / 操作序列
Evaluator质量评审与反馈原始需求 + Generator 输出通过 / 拒绝 + 修改建议

上下文隔离的关键作用

每个 Agent 拿到的是全新的上下文（context reset），而非前一个 Agent 的完整对话历史。这避免了：

  • 锚定偏差：Evaluator 不会被 Generator 的推理链"说服"
  • 上下文污染：中间步骤的错误信息不会级联传播
  • Token 膨胀：每个 Agent 只接收必要信息，降低成本
Three-Agent Harness（生成-评估分离）
Planner · 任务分解
输出 [plan]；上下文：用户需求 + 约束条件
Generator · 执行工作
输出 [result]；上下文：用户需求 + plan + tools
Evaluator · 质量评审
输出 [review]；上下文：用户需求 + plan + result（不看生成过程）

深度理解：生成-评估分离 — 生成者不能评估自己的输出，因为同一上下文中的推理链会造成确认偏差（confirmation bias），模型倾向于为自己的决策辩护。GAN 类比：Generator 和 Discriminator 必须独立训练 → 生成 Agent 和评估 Agent 必须有独立上下文。上下文重置 ≠ 信息丢失：精心设计的"交接协议"传递必要信息、过滤噪音。

Brain / Hands / Session 架构（Claude Managed Agents, 2026.04）

Anthropic 在 2026 年 4 月发布的 Claude Managed Agent…

三层组件分离

Anthropic 在 2026 年 4 月发布的 Claude Managed Agents 架构中，将 Agent 系统解耦为三个独立层：

组件职责生命周期失败模式
BrainClaude 模型 + Harness 逻辑（推理、决策、规划）按需启动，stateless per call可重试、可替换模型
Hands临时沙箱 + 工具集（代码执行、文件操作、API 调用）Ephemeral，任务完成即销毁崩溃不影响 Brain/Session
Session持久化事件日志（独立于上下文窗口）Durable，跨多次交互存活可恢复、可审计
Brain / Hands / Session
Brain (无状态)
Claude 模型 · Harness 逻辑 · 可热替换（降级到小模型）
Hands (临时沙箱)
代码执行环境 · 工具集 · 任务完成即销毁
Session (持久化)
事件日志（完整历史） · 崩溃可恢复 · 独立于上下文窗口

Session ≠ Context Window

属性Session（事件日志）Context Window（上下文窗口）
大小无限制（磁盘/数据库）有限（128K–200K tokens）
持久性持久化，崩溃可恢复每次 API 调用重新构建
内容所有事件的完整记录精选的相关上下文子集
用途审计、恢复、状态同步模型推理的输入

关键区分：Session（事件日志）是完整的、持久的历史记录；Context Window（上下文窗口）是每次给模型的有限输入。Session 可以有 100 万条事件，但每次调用模型只挑选最相关的内容放入 128K 的上下文窗口。

深度理解：Brain/Hands/Session 三层分离 — 任何一层失败都不会拖垮其他层：沙箱崩溃不丢状态（Session 持久化），模型超时可重试（Brain 无状态）。Session ≠ Context Window：Session 是全量持久化日志（可达 GB），Context Window 是每次推理的有限输入（128K tokens）。Ephemeral Hands 的意义：每个工具执行都在干净沙箱中，避免环境污染（上次的 pip 包残留影响这次）和安全隐患。

04

上下文管理策略

Agent 执行多步任务时，对话历史不断增长

上下文膨胀问题

Agent 执行多步任务时，对话历史不断增长。第 N 步需要携带前 N-1 步的所有信息，导致 token 成本超线性增长、关键信息被噪音淹没。

两种核心策略

策略做法优势劣势
Context Reset（上下文重置）每个阶段/Agent 拿到全新上下文无累积偏差、成本可控信息传递需精心设计
Context Compaction（上下文压缩）定期摘要/裁剪历史保留连续性摘要可能丢失细节

上下文漂移效应

步骤累积上下文的问题Context Reset 的解法
Step 1模型做了小错误假设（如误认为用户要 Python 3.8）Planner 独立生成 plan
Step 2基于错误假设继续工作 → 错误被强化Generator 只看 plan，不看推理过程
Step 3在错误基础上构建更多代码 → 越陷越深Evaluator 只看原始需求 + 最终结果
Step N最终输出建立在层层错误假设之上每个阶段从源头重新开始

Sprint Contract 模式

借鉴敏捷开发的 Sprint 概念，每次交给 Agent 的任务都有明确的完成定义（Definition of Done）：

元素说明示例
task任务描述"实现用户登录 API"
done_criteria完成标准（可验证）"POST /api/login 接受 email+password，返回 JWT"
constraints技术约束"使用 bcrypt，纯 stateless JWT"
max_steps最大步数15
timeout超时限制"5min"

深度理解：上下文漂移与 Sprint Contract — Context Reset vs Compaction 选择：多 Agent 协作用 Reset（避免偏差传播），单 Agent 长对话用 Compaction（保持连续性）。上下文漂移（Context Drift）= 长对话中早期错误假设被后续步骤不断强化，是单 Agent 的主要失败模式。Sprint Contract 核心：把"开放式任务"变成"有明确验收标准的合约"，让 Agent 行为可预测、可验证。

CLAUDE.md / AGENTS.md 约定

在现代 Agent 系统中（特别是编码 Agent），工作区中的约定文件充当 Agent 间的通信协议和共享记忆：

文件作用读写者
CLAUDE.md项目级指令：编码规范、架构约束、禁止操作人类编写，Agent 读取
AGENTS.mdAgent 间交接协议：任务状态、上下文摘要、待办事项Agent 读写

TODO.md任务追踪和进度Agent 读写

文件系统作为共享内存的优势

优势说明对比 API/内存
崩溃恢复Agent 进程崩溃 → 重启后读取文件 → 从断点继续进程死了，状态全丢
人类可读可编辑开发者可以直接查看/修改 → 干预 Agent 行为需要额外工具才能查看中间状态

跨进程/跨机器共享多个 Agent 进程只需挂载同一文件系统需要 IPC 或消息队列

核心理念：工作区（Workspace）即共享内存。Agent 不需要复杂的消息传递基础设施，文件系统本身就是最可靠的通信介质。这也是为什么 Cursor / Claude Code 等工具都重度依赖 CLAUDE.md 和目录约定文件。

深度理解：Workspace as Shared Memory — 文件通信 vs API 通信：文件适合异步、可恢复、人类可审计（git diff 一目了然）；API 适合低延迟、高吞吐。CLAUDE.md 是"给 Agent 的 README"：定义不变量（invariants，如"不能修改 config.yaml"），而非具体指令。崩溃恢复是硬性需求：文件状态天然支持（文件系统有 fsync），内存状态需要额外持久化（Redis/SQLite）。

Hooks：墙壁而非建议（Walls Not Suggestions）

Prompt 中的指令（"不要删除文件"、"代码必须通过 lint"）是 建议 ——模型可以…

Prompt 指令 vs Hook 的本质区别

Prompt 中的指令（"不要删除文件"、"代码必须通过 lint"）是建议——模型可以选择忽略。Hook 是在 Agent 执行管道中强制插入的代码检查点——无论模型"想"什么，Hook 都会执行。

属性Prompt 指令（建议）Hook（墙壁）
执行保证模型可能忽略100% 执行，无法绕过
实现层自然语言，在模型内部代码，在模型外部
失败处理模型自行决定阻断执行 / 自动修复
可审计性难以验证是否遵守有明确的 pass/fail 日志
适用场景偏好、风格、建议安全、格式、不变量

Hook 的类型与时机

时机Hook 类型作用
pre_tool_callpermission_check, argument_validation, rate_limiter在工具调用之前执行：权限检查、参数验证、速率限制
post_tool_calloutput_sanitizer, result_validator在工具调用之后执行：清理敏感信息、验证结果格式
pre_commitlinter, type_checker, security_scanner, test_runner在 Agent 提交代码之前：lint、类型检查、安全扫描、测试
post_responsepii_detector, format_validator在 Agent 回复用户之前：检测隐私信息、输出格式校验
Hook 执行管道
用户请求
[pre_tool_call hooks] → 权限检查 → 参数验证 → 速率限制
Agent 决策 → 工具调用
[post_tool_call hooks] → 输出清理 → 结果验证
Agent 生成代码
[pre_commit hooks] → lint → 类型检查 → 安全扫描 → 测试
↓ (任一失败则阻断) · 提交代码
[post_response hooks] → PII 检测 → 格式校验
返回用户

深度理解：Walls Not Suggestions — 安全关键约束必须在代码层强制执行，不能依赖 prompt 中的自然语言指令（LLM 可能"忘记"或"创造性地绕过"规则）。类比：数据库的 CHECK CONSTRAINT 不是"建议 age > 0"，而是强制拒绝违规插入。Pre-commit Hook 是编码 Agent 最重要的质量门：lint + type check + test = 三重保障，任何一层不通过则阻止提交。

07

决策树：何时使用 Harness？

经验法则 ：如果任务可以在单次 LLM 调用中高质量完成，不要用 Harness
场景推荐方案原因
简单问答 / 一次性生成单 Agent（直接调用模型）无需编排开销
需要工具调用的任务单 Agent + ReAct 循环工具循环足够，无需多 Agent
输出质量要求高（生产级代码、文档）Generator + Evaluator（双 Agent）独立评审提升质量
复杂多步任务（跨文件重构、系统迁移）三 Agent Harness（P/G/E）需要规划 + 执行 + 验证全流程
长时间运行的异步任务Managed Agent（B/H/S 架构）需要持久化 Session、崩溃恢复
多领域协作（前端 + 后端 + 测试）多 Agent + 协调器不同 Agent 有不同工具集和专长

经验法则：如果任务可以在单次 LLM 调用中高质量完成，不要用 Harness。Harness 的价值在于可靠性而非能力——它不会让模型变聪明，但能让系统更可靠。过度工程化的 Harness 反而增加延迟和成本。

Harness 设计清单

类别检查项
上下文管理每个 Agent 的上下文是否最小化？
是否有明确的信息传递协议？
长对话是否有压缩/重置策略？
错误处理模型调用失败是否有重试/降级策略？
工具执行失败是否有回退方案？
是否设置了最大步数 / 超时限制？
安全约束敏感操作是否有 Hook 强制拦截？
工具权限是否最小化？
输出是否过滤了敏感信息？
可观测性每步决策是否有日志？
Token 消耗 / 延迟是否有监控？
失败 case 是否自动收集用于改进？

核心结论 — 不要过度设计：简单任务用单 Agent，只在需要可靠性保障时才引入多 Agent Harness。Harness 的 ROI 体现在失败率降低（70% → 95%），而非成功率提升。生产级 Harness 四根支柱：上下文管理 + 错误处理 + 安全约束 + 可观测性。

  • Harness 层投入 > 模型选择投入
  • 生成者和评估者必须独立上下文
  • Brain/Hands/Session 三层分离
  • 安全约束在代码层强制执行（Walls not suggestions）
  • 每个 Sprint 有明确验收标准（done_criteria）
  • 不要让生成者评估自己的输出（确认偏差）
  • 不要依赖 prompt 做安全约束（LLM 可能绕过）
  • 不要忽略上下文漂移（长对话中早期假设会被不断强化）
  • 不要在简单任务上过度设计（多 Agent 不是银弹）
  • 不要让 Session 和 Context Window 混淆（持久化 vs 有限输入）

生产验证：Harness 架构（Agent 的"脚手架"）在编码 Agent 中的应用：(1) 循环探测中间件 — 死循环检出率 96%，Token 浪费降 94%（月均 $3,200 → $180）；(2) 工具调用守卫 — 拦截 3,400 次越权工具调用（如 Agent 试图执行 rm -rf），零安全事故；(3) 上下文窗口管理 — 自动压缩历史对话，将有效信息浓度从 35% 提升至 78%，任务完成率提升 22%。Build to Delete 实践：随着模型能力提升（GPT-4 → GPT-5），中间件触发频率降低 75%，说明护栏可以逐步退场。核心哲学：Harness 不是替代模型能力，而是在模型不完美时提供安全网。

Q&A

Harness 和 Agent Framework（如 LangChain）有什么区别？

Harness 是一种架构模式，描述围绕模型的编排层应该怎么设计（上下文管理、多 Agent 协作、安全约束、状态持久化）。Agent Framework 是具体实现，提供构建 Harness 的工具库（LangChain/LangGraph 提供链式调用、工具绑定、图状态机等）。一个好的比喻：Harness 是建筑蓝图（设计模式），Framework 是建筑材料（钢筋水泥）。你可以用 LangGraph 实现三 Agent Harness，也可以用纯 Python 实现。关键的架构决策（用几个 Agent、上下文怎么传递、Hook 放在哪里）是 Harness 层面的，不依赖特定 Framework。

为什么说 "生成者不能评估自己的工作"？能否用同一个模型做生成和评估？

可以用同一个模型，但必须是不同的实例/上下文。问题不在于模型参数相同，而在于上下文相同。当 Generator 的推理链（"我选择方案A是因为..."）出现在 Evaluator 的上下文中时，Evaluator 会受到锚定效应（anchoring bias）影响，倾向于认同已有的推理。解法：Evaluator 只看到原始需求和最终输出，不看生成过程。这类似于代码 review 的最佳实践——reviewer 看 PR diff，而不是看作者的思考笔记。上下文隔离是关键，不是模型隔离。实际上 Anthropic 的三 Agent 模式通常用同一个 Claude 模型，只是上下文完全不同。

Brain/Hands/Session 架构中，Session 和 Context Window 有什么区别？为什么要分离？

Session 是完整的、持久化的事件日志（可以有数万条记录），存储在磁盘/数据库中，记录 Agent 所有行为的完整历史。Context Window 是每次模型调用的有限输入（128K–200K tokens），从 Session 中选择性提取相关内容构建。分离的原因：①容量：长任务的完整历史远超上下文窗口限制；②持久性：Context Window 在进程崩溃后消失，Session 持久化在磁盘上可恢复；③灵活性：不同阶段可以从同一个 Session 中提取不同的上下文子集（Planner 看全局，Generator 看局部）；④审计：Session 提供完整的行为记录，用于调试和合规审计。

什么是 "Walls Not Suggestions"？为什么 Prompt 指令不够？

"Walls Not Suggestions" 是指安全关键的约束必须在代码层（Hook）而非提示层（Prompt）实施。原因：①模型不可靠：即使 prompt 说"不要删除文件"，模型在复杂推理链中可能"忘记"这个约束，特别是上下文很长或指令冲突时；②对抗性场景：Prompt Injection 可以覆盖 prompt 中的指令，但无法绕过代码层的 Hook（Hook 在模型外部执行）；③可验证性：Prompt 遵守情况难以验证（模型内部黑箱），Hook 有明确的 pass/fail 日志。实际做法：把"偏好"放 prompt（代码风格、语气），把"不变量"放 Hook（安全扫描、lint、权限检查、测试必须通过）。

如何决定一个任务是用单 Agent 还是多 Agent Harness？

决策依据有三个维度：①任务复杂度：能否在单次 LLM 调用中高质量完成？如果是，用单 Agent；需要多步规划+执行+验证，用多 Agent。②可靠性要求：容忍偶尔出错（内部工具/草稿）→ 单 Agent；要求高可靠性（面向用户/生产级）→ 多 Agent + Evaluator。③任务持续时间：秒级完成 → 单 Agent；分钟/小时级 → 需要 Session 持久化的 Managed Agent。经验法则：从最简单的方案开始（单 Agent + ReAct），通过评估发现质量不达标的环节，再有针对性地添加 Evaluator 或 Planner。过度工程化的 Harness 增加延迟（3× LLM 调用）和成本，但如果任务的失败成本高（生产环境代码、用户数据操作），这个 overhead 是值得的。

基于文件的 Agent 间通信（CLAUDE.md / AGENTS.md）有什么优势和局限？

优势：①崩溃恢复：Agent 进程死掉后重启，读文件即可恢复状态，无需额外的持久化层；②人类可读可编辑：开发者可以直接查看和修改文件来干预 Agent 行为（git diff 查看变更）；③版本控制友好：天然适配 git 工作流，Agent 的行为变更有完整追踪；④零基础设施：不需要消息队列、数据库等额外基础设施。局限：①并发冲突：多个 Agent 同时写同一个文件可能产生竞争条件（需要文件锁或 CAS 机制）；②延迟：文件 I/O 比内存通信慢，不适合需要毫秒级响应的实时场景；③结构化弱：Markdown 文件缺乏 schema 约束，Agent 可能写出格式不一致的内容；④规模限制：数百个 Agent 共享文件系统时管理复杂度会急剧上升。适用场景：编码 Agent（Cursor / Claude Code）、异步任务、需要人类审计的场景。
