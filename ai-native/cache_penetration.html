概览

缓存三大问题的本质是同一个：缓存与数据库之间的"一致性裂缝"被流量放大

缓存三大问题的本质是同一个：缓存与数据库之间的"一致性裂缝"被流量放大。穿透是"查的数据根本不存在"，击穿是"热点数据刚好过期"，雪崩是"大量数据同时过期"。三者的触发机制不同，解决方案完全不同——混用方案等于没防御。

01

三大问题全景对比

缓存穿透、 缓存击穿 、 缓存雪崩 是缓存系统最常见的三类故障模式

缓存穿透、缓存击穿、缓存雪崩是缓存系统最常见的三类故障模式。它们的核心区别在于"缓存失效的原因"和"流量冲击的形态"不同。理解这三者的差异是选择正确防御方案的前提。

关键区分：穿透是"数据不存在"问题——无论查多少次 DB 都查不到，缓存永远建立不起来。击穿是"数据存在但缓存刚好过期"——只需要重建一次缓存就能恢复。雪崩是"大面积缓存同时过期"——是击穿的大规模版本。三者的根因不同，用错方案不仅无效，还可能引入新问题（例如用空值缓存解决击穿，会导致合法数据被空值覆盖）。
02

缓存穿透：深度解析与解决方案

缓存穿透 （Cache Penetration）指客户端持续请求查询数据库中不存在的数据

缓存穿透（Cache Penetration）指客户端持续请求查询数据库中不存在的数据。由于数据不存在，缓存永远无法命中，每次请求都会穿透缓存直达数据库。当穿透请求量足够大时，数据库会因为大量无效查询而过载。

穿透的触发机制与攻击向量

穿透攻击之所以有效，是因为缓存的设计假设是"查不到就去 DB 查"——但没有考虑"DB 也查不到"的场景。攻击者利用这个假设，用随机 ID 或已知不存在的 key 发起大量请求，每个请求都会走完"缓存 miss → 查 DB → DB 也没有 → 返回空"的完整链路，浪费 DB 资源。

穿透请求的来源通常有三种：①恶意攻击（攻击者用脚本生成随机 ID 批量查询）；②爬虫程序（无差别遍历 ID 空间）；③业务 bug（前端传了错误的参数导致查不存在的 key）。三种来源的防御策略不同，但最终都需要在缓存层面做兜底。

方案一：空值缓存（Null Value Caching）

当查询的 key 在数据库中不存在时，仍然在缓存中写入一个 空值标记（如 NULL_PLACEHOLDER），并设置较短的过期时间。下次同样的请求直接命中缓存返回空值，不再查数据库。原理简单直接，但要注意参数调优。

参数推荐值调优依据
空值标记"NULL_PH"区别于真实空字符串和 JSON null
过期时间60-300 秒太短则防御无效（攻击者等过期再打），太长则浪费内存且数据变更后无法感知
内存占用每条约 50 字节100 万空值 ≈ 50MB，可接受
容量上限最多 100 万条超过后用 LRU 淘汰，防止内存无限增长

方案二：布隆过滤器（Bloom Filter）

布隆过滤器（Bloom Filter）是一个基于多个哈希函数的概率型数据结构，能在 O(1) 时间内判断"某个元素是否可能存在"。它的核心特性是：说"不存在"一定不存在（无假阴性），说"可能存在"有一定概率误判（有假阳性）。这个特性天然适合做穿透防御的第一道防线。

┌──────────────────────────────────────────────────────┐ │ 布隆过滤器工作原理 │ ├──────────────────────────────────────────────────────┤ │ │ │ 元素 "user_123" │ │ │ │ │ ├─ Hash1("user_123") = 3 ──▶ Bit[3] = 1 │ │ ├─ Hash2("user_123") = 7 ──▶ Bit[7] = 1 │ │ └─ Hash3("user_123") = 15 ──▶ Bit[15] = 1 │ │ │ │ 查询 "user_999" │ │ │ │ │ ├─ Hash1("user_999") = 5 ──▶ Bit[5] = 0 ❌ │ │ │ 只要有一个位为 0 → 一定不存在 │ │ │ → 直接返回空，不查 DB │ │ │ │ │ 查询 "user_456" │ │ │ │ │ ├─ Hash1("user_456") = 3 ──▶ Bit[3] = 1 ✅ │ │ ├─ Hash2("user_456") = 7 ──▶ Bit[7] = 1 ✅ │ │ └─ Hash3("user_456") = 15 ──▶ Bit[15] = 1 ✅ │ │ │ 所有位都为 1 → 可能存在（误判率 ~1%） │ │ │ → 正常查缓存 → 查 DB │ │ │ │ 误判率公式: P ≈ (1 - e^(-kn/m))^k │ │ m=位数组大小 k=哈希函数数 n=元素数 │ └──────────────────────────────────────────────────────┘

双层防御组合效果

生产案例：某电商平台用户服务日均请求 500 万次，其中穿透请求约 12 万次/天（占 2.4%）。引入双层防御后：布隆过滤器（100 万元素，误判率 0.8%）拦截了 99.2% 的穿透请求，剩余 0.8%（约 960 次/天）由空值缓存兜底。最终穿透到 DB 的请求从 12 万次/天降至不到 10 次/天（降幅 99.99%），DB 慢查询减少 35%，P99 延迟从 850ms 降至 120ms。
  • 布隆过滤器做第一层拦截 + 空值缓存做第二层兜底
  • 空值过期时间设 60-300 秒，并设容量上限
  • 监控穿透率（cache miss + DB miss 的比例），超 5% 告警
  • 布隆过滤器定期全量重建（数据变更后）
  • 对高频穿透 IP 做限流（如每分钟 ≤ 60 次）
  • 只用空值缓存不设布隆过滤器（随机 ID 攻击下内存爆炸）
  • 空值过期时间设太长（数据新增后查不到新数据）
  • 忽略穿透请求监控（可能是攻击前兆的信号）
  • 布隆过滤器从不重建（数据删除后仍判断"存在"）
  • 在布隆过滤器中用标准版做删除操作（需 Counting Bloom Filter）
03

缓存击穿：热点 key 的并发风暴

缓存击穿 （Cache Breakdown）指一个被大量请求访问的热点 key，在缓存过期的…

缓存击穿（Cache Breakdown）指一个被大量请求访问的热点 key，在缓存过期的瞬间，所有并发请求同时发现缓存未命中，于是全部直接打到数据库去重建缓存。结果是数据库在极短时间内被大量相同查询淹没。

击穿的触发机制

击穿的关键在于"时间窗口"——缓存过期的那一毫秒内，如果有 1000 个并发请求同时到达，它们都会发现缓存为空，然后同时发起 1000 次相同的 DB 查询。实际上只需要 1 次 DB 查询就能重建缓存，其余 999 次完全浪费。解决方案的核心思想就是：确保只有 1 个请求去重建缓存，其余 999 个等待。

┌─────────────────────────────────────────────────────────────┐ │ 缓存击穿时序图 │ ├─────────────────────────────────────────────────────────────┤ │ │ │ 时间线 ──────────────────────────────────────▶ │ │ │ │ 缓存状态: [有效 ████████████] [过期!] [重建中...] [新缓存] │ │ ↑ │ │ 过期瞬间 │ │ │ │ │ 请求1 ─────────────────┼──────▶ 查 DB ──▶ 写缓存 │ │ 请求2 ─────────────────┼──────▶ 查 DB (重复!) │ │ 请求3 ─────────────────┼──────▶ 查 DB (重复!) │ │ ... │ │ │ 请求1000 ──────────────┘──────▶ 查 DB (重复!) │ │ │ │ 无保护: 1000 次 DB 查询 │ │ 互斥锁: 1 次 DB 查询 + 999 次等待 │ │ 逻辑过期: 0 次阻塞（后台异步重建） │ └─────────────────────────────────────────────────────────────┘

两种解决方案对比

维度互斥锁（Mutex Lock）逻辑过期（Logical Expiry）
原理只让一个线程查 DB 重建缓存，其他线程等待不设真实 TTL，在 value 中存过期时间戳，过期后后台异步重建
一致性强一致（等待期间无数据返回）弱一致（可能返回旧数据）
可用性等待期间请求被阻塞始终可用，不阻塞请求
实现复杂度⭐⭐ 低（Redis SETNX 即可）⭐⭐⭐ 中高（需后台任务 + 过期判断）
适用场景数据一致性要求高、并发量适中高并发、允许短暂返回旧数据
失败处理需设锁超时防止死锁重建失败则持续返回旧数据直到成功
生产案例：某社交平台的热搜榜单（热点 key，QPS 50,000+）使用 10 分钟 TTL 缓存。每次过期瞬间约 3,000 个并发请求同时穿透到 DB，导致 DB CPU 在 200ms 内飙升到 95%。引入互斥锁方案后，过期瞬间只有 1 个请求查 DB，其余请求等待 5-15ms 后命中新缓存，DB CPU 峰值从 95% 降至 12%。后升级为逻辑过期方案，用户请求完全不阻塞，P99 延迟从 180ms 降至 8ms。
04

缓存雪崩：大面积失效的连锁反应

缓存雪崩 （Cache Avalanche）指大量缓存 key 在同一时间集中过期，导致大面…

缓存雪崩（Cache Avalanche）指大量缓存 key 在同一时间集中过期，导致大面积缓存失效，几乎所有请求都直接打到数据库。与击穿的区别在于：击穿是单个热点 key 的问题，雪崩是大量 key 同时失效的"批量灾难"。

雪崩的触发机制与连锁效应

雪崩的经典触发场景：系统在凌晨重启缓存，所有缓存同时清空，或者所有 key 设置了相同的 TTL（如都设 1 小时），导致它们在同一时刻集体过期。雪崩的危害不仅是"DB 压力大"，更危险的是连锁反应——DB 过载后响应变慢，请求堆积在应用层，应用层线程耗尽后整个服务不可用，形成雪崩式的级联故障。

┌─────────────────────────────────────────────────────────────┐ │ 缓存雪崩级联故障链路 │ ├─────────────────────────────────────────────────────────────┤ │ │ │ 大量 key 同时过期 │ │ │ │ │ ▼ │ │ ┌──────────────┐ │ │ │ 缓存大面积 miss │ │ │ └──────┬───────┘ │ │ ▼ │ │ ┌──────────────┐ 响应变慢 │ │ │ DB 查询激增 │──────────┐ │ │ │ CPU 飙升 90%+ │ │ │ │ └──────────────┘ ▼ │ │ ┌──────────────┐ │ │ │ 应用层超时堆积 │ │ │ │ 线程池耗尽 │ │ │ └──────┬───────┘ │ │ ▼ │ │ ┌──────────────┐ │ │ │ 服务不可用 │ ← 级联故障 │ │ │ 用户全部报错 │ │ │ └──────────────┘ │ └─────────────────────────────────────────────────────────────┘

三层防御方案

防御层方案原理效果
第一层：预防TTL 加随机偏移每个 key 的过期时间 = 基础 TTL + random(0, 300s)，打散过期时间消除批量过期，DB 压力均匀分散
第二层：缓冲多级缓存L1 本地缓存（Caffeine）+ L2 分布式缓存（Redis），L2 miss 时 L1 仍可服务降低单点失效冲击
第三层：兜底熔断 + 降级DB 响应时间 > 阈值时触发熔断，返回默认值或旧数据防止级联故障
生产案例：某电商大促期间，商品缓存服务重启后 500 万个商品缓存同时清空（预热不充分），导致 DB 在 10 秒内收到 200 万次查询，CPU 飙升至 100%，服务完全不可用持续 8 分钟，影响约 15,000 笔订单。事后修复方案：①TTL 加 0-600s 随机偏移，消除批量过期；②增加本地缓存层（Caffeine，10 分钟 TTL）作为 L1；③DB 查询 P99 > 500ms 时触发熔断，返回商品默认信息。修复后模拟压测：即使 Redis 全量清空，DB 峰值 CPU 仅 25%，服务可用性 99.97%。
05

生产环境多级防御体系

单一方案无法覆盖所有缓存故障场景

单一方案无法覆盖所有缓存故障场景。生产环境需要构建多层防御体系，每一层解决不同的问题，层与层之间互为兜底。

┌─────────────────────────────────────────────────────────────────┐ │ 缓存多级防御体系 │ ├─────────────────────────────────────────────────────────────────┤ │ │ │ 请求入口 │ │ │ │ │ ▼ │ │ ┌──────────────┐ │ │ │ L0: 接入层 │ IP 限流 + 异常 key 过滤 + 布隆过滤器 │ │ └──────┬───────┘ │ │ ▼ │ │ ┌──────────────┐ │ │ │ L1: 本地缓存 │ Caffeine/Guava，TTL 5min，容量 10,000 │ │ └──────┬───────┘ │ │ ▼ miss │ │ ┌──────────────┐ │ │ │ L2: Redis │ TTL + 随机偏移，空值缓存兜底 │ │ └──────┬───────┘ │ │ ▼ miss │ │ ┌──────────────┐ │ │ │ L3: 互斥锁 │ SETNX 获取锁，只有一个线程查 DB │ │ └──────┬───────┘ │ │ ▼ │ │ ┌──────────────┐ │ │ │ L4: 数据库 │ 最终兜底 │ │ └──────┬───────┘ │ │ ▼ │ │ ┌──────────────┐ │ │ │ L5: 熔断降级 │ DB 超时 → 返回默认值 / 旧缓存数据 │ │ └──────────────┘ │ │ │ │ 监控: 穿透率 | 击穿次数 | 雪崩预警 | DB CPU | P99 延迟 │ └─────────────────────────────────────────────────────────────────┘

防御层级详细对比

层级组件解决的问题配置建议局限性
L0 接入层Nginx 限流 + 布隆过滤器穿透请求拦截IP 限 60 次/分钟，布隆误判率 < 1%无法防分布式攻击
L1 本地缓存Caffeine / Guava减少 Redis 压力TTL 5min，容量 10K，LRU 淘汰多节点一致性差
L2 RedisRedis Cluster主缓存层TTL 30min + random(0, 300s)宕机则全部穿透
L3 互斥锁Redis SETNX击穿防护锁超时 3s，获取失败返回旧数据增加请求延迟
L4 DBMySQL / PostgreSQL数据源连接池上限、查询超时不可过载
L5 熔断Sentinel / Hystrix级联故障防护P99 > 500ms 触发，恢复间隔 30s降级期间数据可能过时

多级防御的核心思想是"纵深防御"（Defense in Depth）：不依赖任何单一层来保证安全，每一层都假设上一层可能失败。布隆过滤器漏了 → 空值缓存兜底；Redis 挂了 → 本地缓存还能撑一会；DB 过载了 → 熔断器自动降级。这种冗余设计看似浪费资源，实则是生产环境稳定性的基石。

  • 至少部署 L0（限流）+ L2（Redis）+ L5（熔断）三层
  • TTL 必须加随机偏移（基础值 ± 10-20%）
  • 缓存预热：服务启动时主动加载热点数据
  • 设置完善的监控告警：穿透率、DB CPU、P99 延迟
  • 定期做故障演练：模拟 Redis 宕机和缓存清空
  • 所有 key 使用相同 TTL（制造雪崩条件）
  • 只依赖单一防御层（如只用 Redis 不做限流和熔断）
  • 不监控穿透率（穿透率突增是攻击或 bug 的信号）
  • 布隆过滤器从不重建（数据删除后判断失效）
  • 缓存服务重启后不预热（等于主动制造雪崩）
06

Agent Prompt Cache 击穿：成本崩盘的隐形杀手

传统缓存击穿影响的是数据库性能，而 Prompt Cache 击穿影响的是 Agent 产品…

传统缓存击穿影响的是数据库性能，而 Prompt Cache 击穿影响的是 Agent 产品的成本结构。Claude Code 团队将缓存命中率设为 SEV 事故级别告警——命中率掉几个点就意味着 API 成本翻倍。这不是性能问题，而是产品能否跑得起的生死问题。

Agent 是长会话系统，每次对话可能涉及数十轮交互。Prompt Cache 按前缀匹配：从第一个字节到缓存断点必须完全一致才能命中。任何前缀变动——哪怕只是 System Prompt 里塞了一个精确时间戳——都会导致后续所有缓存作废。Cache Hit 时 Token 单价仅为 Miss 时的 10%，所以命中率直接决定成本。

布隆过滤器的误判率怎么控制？具体参数怎么选？
误判率由三个参数共同决定：位数组大小 m、哈希函数个数 k、元素数量 n。公式：P ≈ (1 - e^(-kn/m))^k。实际操作建议：①确定元素数量 n（如 100 万）；②选择目标误判率（如 0.8%）；③反推 m = -n·ln(p)/(ln2)² ≈ 14.4n 位 ≈ 1.7MB/百万元素；④k = (m/n)·ln2 ≈ 7 个哈希。100 万元素用 12MB 位数组 + 7 个哈希函数，误判率约 0.8%。增大位数组到 24MB + 10 个哈希，误判率可降至 0.1%。Redis 的 RedisBloom 模块可直接使用，无需自己实现。
布隆过滤器不支持删除元素怎么办？
标准布隆过滤器不支持删除（因为不同元素可能共享位，删除一个元素会影响其他元素的判断）。三种解决方案：①定期全量重建（最常用）——每天凌晨从 DB 全量加载数据重建布隆过滤器，适合数据变更不频繁的场景；②使用 Counting Bloom Filter——每个位存储计数而非 0/1，支持删除但内存消耗翻 4-8 倍；③使用 Cuckoo Filter——支持删除且空间效率更高，但实现更复杂。大多数生产场景使用方案①即可，配合空值缓存做兜底，重建间隔内的"假阳性"不会造成穿透。
互斥锁和逻辑过期该怎么选？
选择取决于业务对一致性和可用性的优先级。互斥锁适合：数据一致性要求高（如库存、余额）、并发量适中（QPS < 10,000）、实现简单快速。逻辑过期适合：高并发场景（QPS > 10,000）、允许短暂返回旧数据（如热搜、推荐列表）、团队有能力维护后台刷新任务。一个实用判断法：如果"用户看到 3 秒前的旧数据"可以接受，就用逻辑过期；如果"必须看到最新数据"，就用互斥锁。注意互斥锁必须设超时（建议 3 秒），防止持锁线程 crash 导致死锁。
缓存穿透和恶意攻击怎么区分？怎么联动防御？
通过分析请求模式区分：正常穿透（业务 bug 导致查不存在的 key）通常 key 模式有规律（如连续 ID），频率平稳；恶意攻击的特征是大量随机 ID（UUID 或雪花 ID），高频请求，来源 IP 集中或呈分布式。监控指标：穿透率（cache miss 且 DB miss 的比例）突增 > 5% 时触发告警。联动防御：①L0 层 IP 限流（单 IP ≤ 60 次/分钟）；②L0 层异常 key 检测（短时间内同一来源查大量不存在的 key → 临时封禁）；③L2 层空值缓存兜底；④记录穿透日志用于事后分析。穿透攻击往往是 DDoS 的前奏——探测系统弱点后发动更大规模攻击。
分布式环境下布隆过滤器怎么部署和同步？
两种主流方案：①中心化部署——使用 Redis 的 RedisBloom 模块，所有应用节点共享同一个布隆过滤器。优点是数据一致、维护简单，缺点是 Redis 成为单点（可用 Redis Cluster 解决）。推荐中小规模（< 10 亿元素）使用。②本地部署 + 变更广播——每个应用节点在本地维护一个布隆过滤器，数据变更通过 Kafka/RocketMQ 广播，各节点异步更新。优点是查询延迟极低（无网络开销），缺点是短暂不一致。适合超大规模（10 亿+ 元素）和对延迟敏感的场景。大多数生产环境推荐方案①，10 亿元素在 Redis 中约占 1.2GB，完全可接受。
如何设计缓存故障的监控告警体系？
核心监控四个维度：①穿透率 = (cache miss 且 DB miss 的请求数) / 总请求数，正常 < 1%，告警阈值 5%；②DB 查询 QPS 突增比 = 当前 QPS / 基线 QPS，告警阈值 > 3 倍；③缓存命中率 = cache hit / 总请求，正常 > 95%，告警阈值 < 85%；④P99 延迟，告警阈值视业务而定（如 > 500ms）。建议用 Prometheus + Grafana 建 Dashboard，设置分级告警：P1（立即处理）——DB CPU > 90% 或穿透率 > 20%；P2（30 分钟内处理）——命中率 < 85% 持续 5 分钟；P3（下次迭代处理）——穿透率偶发 > 5%。
Prompt Cache 和 KV Cache 有什么区别？它们是同一层优化吗？
不同层次的优化。Prompt Cache 是 API 层优化——OpenAI/Anthropic 在模型服务端缓存已处理的 Prompt 前缀，后续请求如果前缀相同则跳过 Token 化 + 预填充阶段，直接复用计算结果（Token 单价降至 10%）。KV Cache 是模型推理层优化——在 GPU 显存中缓存已计算的 Key/Value 矩阵，避免自回归生成时重复计算历史 Attention。关系：Prompt Cache 节省"输入处理"成本，KV Cache 节省"输出生成"时间。两者互补：一个减少 API 调用费用，一个减少推理延迟。生产建议：两者同时启用，Prompt Cache 降低 67% 成本，KV Cache（通过 PagedAttention）提升 4x 吞吐。
为什么"切便宜模型"可能反而更贵？
因为切换模型（如从 Sonnet 切到 Haiku）需要重建 prefix，而重建 prefix 的成本可能超过使用便宜模型节省的钱。正确做法是不切模型，改用子 Agent 独立运行——子 Agent 有自己的 prefix，不影响主对话的缓存。
为什么动态调工具是反模式？
工具定义在 prompt 中是 prefix 的一部分。动态加载/卸载工具会改变 prefix，导致后续缓存全部作废。正确做法是工具集保持稳定，状态切换通过工具调用表达（如调用 EnterPlanMode 工具而非动态切换工具集）。
