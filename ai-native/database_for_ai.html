概览

AI 应用的数据库不是"选一个万能数据库"——而是按数据类别分层组合

AI 应用的数据库不是"选一个万能数据库"——而是按数据类别分层组合。MVP 阶段 PostgreSQL 一把梭（对话 + pgvector + 全文）就是最优起步方案。

01

对话存储设计

AI 对话应用的数据模型很简单： Session（会话） 和 Message（消息） ，一对…

AI 对话应用的数据模型很简单：Session（会话） 和 Message（消息），一对多关系。

核心表设计要点

字段类型设计考量
session_idUUID会话标识，关联用户
roleENUMsystem / user / assistant / tool 四种角色
contentTEXT消息正文
tool_callsJSONB函数调用请求（支持多轮工具链）
token_countINTEGER每条消息记录 Token 数，用于成本核算
latency_msINTEGER响应延迟，用于性能监控
metadataJSONB灵活存储模型参数、用户反馈、评分等

设计要点

索引策略：messages 表在 (session_id, created_at) 上建联合索引，支持快速加载对话历史。

Tool 调用链：tool_calls 存函数调用请求，tool_call_id 关联调用结果，形成 user → assistant(tool_call) → tool(result) → assistant 的完整链路。

软删除：添加 deleted_at 字段而非物理删除，支持审计和恢复。

PostgreSQL + JSONB 是 AI 应用对话存储的首选方案。JSONB 兼顾结构化和灵活性，pgvector 扩展可在同一库中支持向量检索——一个 PostgreSQL 实例覆盖对话 + 记忆 + 搜索三种需求。

03

审计日志存储

AI 应用需要记录完整的操作链路——不只是为了合规，更是为了调试和优化

AI 应用需要记录完整的操作链路——不只是为了合规，更是为了调试和优化。每次对话的输入/输出、Token 消耗、延迟、工具调用都应该有迹可查。

审计维度

审计维度记录内容用途
请求日志用户输入、模型输出、参数质量监控、安全审计
Token 用量输入/输出 Token 数、费用成本核算、配额管理
延迟指标TTFT、总延迟、排队时间性能优化
Tool 调用函数名、参数、返回值、耗时功能调试
安全事件内容过滤触发、越狱尝试安全合规

分层存储方案

数据温度时间范围存储方案查询特点
🔥 热数据最近 7 天PostgreSQL / ClickHouse实时查询、SQL 灵活
🌡️ 温数据7~30 天Elasticsearch全文搜索、Kibana 可视化
🧊 冷数据30 天以上S3 + Parquet成本最低，Athena/Trino 按需查
ClickHouse 的列式存储在"按时间范围聚合统计"场景下性能极佳——比如"最近 7 天每天的 Token 消耗和平均延迟"，比 PostgreSQL 快 10~100 倍。但中小规模（<1 亿条）用 PostgreSQL 分区表足够。
04

向量 + 全文混合搜索

向量搜索理解语义（"快乐"匹配"开心"），全文搜索精确匹配关键词（专有名词、代码）

向量搜索理解语义（"快乐"匹配"开心"），全文搜索精确匹配关键词（专有名词、代码）。两者互补，混合搜索显著提升 RAG 检索质量。

final_score = alpha × vector_score + (1 - alpha) × bm25_score

混合搜索实现方案

方案实现方式适合规模
PostgreSQL + pgvector + tsvector同一库内向量索引 + GIN 全文索引中小（千万级）
Elasticsearch + 向量插件ES 8.x 原生 dense_vector + BM25中大（亿级）
Weaviate / Qdrant原生支持 BM25 + 向量混合中等（开箱即用）
独立组合向量库 + ES 分别查询后融合大规模（灵活但复杂）

RRF 融合算法

RRF（Reciprocal Rank Fusion）是最常用的多路召回融合算法。核心思想：不看分数，只看排名——排名越高的文档得分越高。

rrf_score = 1/(k + rank_vector) + 1/(k + rank_bm25) （k 通常取 60）

RRF 的优势：不依赖分数的绝对值，只依赖相对排名。不同召回路径的分数分布不同（向量余弦 0~1 vs BM25 可能 10+），直接加权不公平，RRF 消除了这个问题。

alpha 参数的调优需要根据实际数据和查询模式做 A/B 测试。一般 alpha=0.7 偏向语义搜索是个好起点。如果查询以专有名词/代码为主，应提高 BM25 权重。

MVP 阶段一把梭

PostgreSQL + Redis 即可覆盖所有需求。确认瓶颈后再引入专用数据库，避免过早复杂度。

语义缓存降本

Redis + 向量相似度匹配，相似问题复用 LLM 答案，可降低 30~60% API 费用（最大成本项）。

过早引入复杂度

不要一开始就上 Milvus + ClickHouse + Neo4j。运维成本会吃掉开发时间，先跑通再说。

忽略数据一致性

跨库同步用 CDC（Debezium）而非双写。双写容易不一致，CDC 从日志捕获变更更可靠。

核心洞察：LLM API 调用通常是 AI 应用的最大成本项（远超数据库费用），语义缓存是最直接的降本手段。选型核心原则：按需演进——MVP 用 PostgreSQL 一站式，确认瓶颈后再引入专用数据库。

Q&A

核心表设计：users → sessions（含 model/system_prompt）→…
如何设计一个 AI 聊天应用的数据库架构？

核心表设计：users → sessions（含 model/system_prompt）→ messages（含 role/content/tool_calls/token_count）。推荐 PostgreSQL：JSONB 存储灵活的 metadata 和 tool_calls；pgvector 扩展支持记忆向量检索；完整事务保证数据一致性。索引策略：messages 表在 (session_id, created_at) 上建联合索引。扩展设计：memories 表存储跨会话长期记忆（含 embedding 列），prompt_templates 表管理 Prompt 版本，audit_logs 表记录完整调用链路。MVP 阶段一个 PostgreSQL 实例即可覆盖所有需求。

Agent 的记忆系统应该如何设计？

分层设计：短期记忆 — 当前对话消息历史，溢出时滑动窗口或摘要压缩；工作记忆 — 任务中间状态（工具结果、推理步骤），存 Redis，任务结束清理；长期记忆 — 跨会话持久化，对话结束时 LLM 提取关键信息 → Embedding → 存向量数据库。检索策略：新对话开始时用最新消息检索相关长期记忆 → 注入 System Prompt。管理策略：重要性评分 + 时间衰减 + 容量上限 + 相似记忆合并。pgvector 在 PostgreSQL 中即可实现。

向量搜索和全文搜索如何混合使用？

两者互补：向量搜索理解语义（"快乐"匹配"开心"），全文搜索精确匹配关键词。实现方式：分别执行 Top-K → RRF 融合排序：rrf_score = 1/(k+rank_vector) + 1/(k+rank_bm25)，k 通常取 60。方案选择：小规模用 PostgreSQL（pgvector + tsvector 一站式），中规模用 Weaviate/Qdrant（原生混合搜索），大规模用向量数据库 + Elasticsearch 独立部署。

AI 应用如何控制数据库成本？

成本优化策略：语义缓存（Redis + 向量匹配，降低 30~60% API 费用）、向量降维（Matryoshka Embedding 1536→256 维，存储减 6x）、分层存储（热/温/冷）、连接池（PgBouncer）、缓存高频配置到 Redis、Embedding 批量写入。核心：LLM API 是最大成本项，语义缓存是最直接的降本手段。

如何为 AI 应用选择合适的数据库组合？

按数据类别逐一匹配：对话 → PostgreSQL；向量检索 → 小规模 pgvector，大规模 Qdrant/Milvus；缓存 → Redis；搜索 → Elasticsearch；审计 → ClickHouse 或 PostgreSQL 分区表。核心原则：不要过早引入复杂度 — MVP 阶段 PostgreSQL + Redis 即可；按瓶颈演进 — 确认性能瓶颈后再引入专用数据库；运维能力匹配 — 小团队优先选托管服务；数据一致性 — 跨库同步用 CDC 而非双写。
