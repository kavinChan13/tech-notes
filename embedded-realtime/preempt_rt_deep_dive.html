为什么 mainline Linux 不能硬实时

实时 = 有界，不是快 · 不可抢占段的完整清单 · 最坏延迟的量级对比

1.1 先纠正一个几乎人人都会犯的错：实时不等于快

面试里问「什么是实时系统」，十个人有八个答「响应很快的系统」。这个答案会直接决定后面所有讨论都跑偏。实时性说的是「最坏情况下的响应时间有一个可以证明的上界」，而不是「平均响应时间很短」。一个平均 5 µs、但每小时会出现一次 40 ms 尖峰的系统，在实时语境下是不合格的；一个稳定跑在 800 µs、从不超过 1 ms 的系统，反而是合格的硬实时系统。

生活类比：出租车 vs 地铁。市区打车平均 20 分钟到公司，比地铁的 35 分钟快得多——但堵一次车就是 90 分钟，你没法拿它去赶 9 点的飞机。地铁慢，可它「最坏也就 40 分钟」。赶飞机要选地铁，不是因为它快，而是因为它的最坏情况有界。实时系统选型是同一个道理：mainline Linux 是出租车，PREEMPT_RT 是地铁，RTOS 是专线摆渡车。

由此派生出三档常见分类，工程上必须在需求阶段就定死属于哪一档，因为它决定了后面要花多少钱：

类别超时的后果典型场景常见的实现选择
硬实时（hard）一次超时即视为系统失效，可能造成人身伤害或设备损毁伺服电流环、气囊点火、刹车线控MCU + RTOS / 双内核 / 专用硬件
固实时（firm）超时的那一帧结果直接作废，但系统继续运行视觉伺服的一帧、周期性总线报文PREEMPT_RT 是主力区间
软实时（soft）超时只是体验变差，价值随延迟衰减音视频播放、HMI 刷新、遥测上传mainline Linux 调优即可

大量项目的失败根源，是把一个「固实时」的需求写成了「越快越好」，于是团队一路优化平均值，上线后被长尾打穿。需求文档里必须出现的是「周期 1 ms，抖动不超过 ±100 µs，连续 72 小时不得有一次越界」这样的句子，而不是「尽量低延迟」。

1.2 一次唤醒的延迟由哪几段构成

要谈「上界」，先要把延迟拆开。从一个外设拉高中断线，到你的用户态实时线程真正开始执行第一条业务指令，中间串联着这几段，每一段都有自己的最坏值，总的最坏延迟是它们的和（严格说不能简单相加，但工程上按和做上界估计是安全且常用的做法）：

→
handler 执行top-half 自身耗时
→
调度延迟何时能重新调度
→
抢占延迟当前任务何时可被抢
→
上下文切换换栈 + cache 冷启
  • 中断延迟：CPU 从硬件置位到真正跳进 handler。取决于当前是否处在关中断区间（local_irq_disable()、spin_lock_irqsave()），以及是否有更高优先级中断在跑。
  • handler 执行时间：mainline 上这是纯 IRQ 上下文，不可抢占。某些驱动的 top-half 会做 PHY 寄存器轮询、固件握手，能跑到几百微秒甚至毫秒。
  • 调度延迟：handler 唤醒了你的线程，但要等到下一个「可以重新调度的点」。mainline 上这个点可能很远。
  • 抢占延迟：当前占着 CPU 的那段内核代码是否允许被抢。这正是 mainline 与 RT 的分水岭。
  • 上下文切换与 cache 冷启：寄存器与页表切换只是几百纳秒，真正贵的是 L1/L2/TLB 被冲掉后重新预热，工作集大时可以是几十微秒。
在 mainline 上，前四段里没有任何一段有可证明的上界——不是因为它们慢，而是因为「最长的那个不可抢占段有多长」取决于当时恰好在跑什么驱动、什么文件系统、什么内存回收路径。这就是「Linux 不能硬实时」的完整含义。

1.3 mainline 上不可抢占的来源，逐个点名

下面这份清单是理解 PREEMPT_RT 全部设计动机的钥匙。每一条都是内核里「一旦进去，高优先级任务就得等」的区间。

① 自旋锁临界区

mainline 的 spin_lock() 在 SMP 上做两件事：关抢占，然后忙等到拿到锁。关抢占是必须的——如果持锁者被抢占下去，同核上另一个想拿同一把锁的任务会忙等到天荒地老（自己不下 CPU，持锁者也上不来），直接死锁。

/* mainline 语义（简化）*/
static inline void spin_lock(spinlock_t *lock)
{
    preempt_disable();          /* ← 从这里开始，本核不可抢占 */
    do_raw_spin_lock(lock);     /* 忙等，不睡眠 */
}

static inline void spin_unlock(spinlock_t *lock)
{
    do_raw_spin_unlock(lock);
    preempt_enable();           /* ← 到这里才恢复，并检查是否需要重新调度 */
}

于是抢占延迟的下界 = 内核里最长的那一段自旋锁临界区。而内核有数千把自旋锁，遍布 VFS、内存管理、网络栈、各种驱动。你没法枚举，更没法证明上界。更糟的是 spin_lock_irqsave()——它连中断一起关掉，此时连中断延迟都被拉长。

② 显式关中断的区间

驱动里 local_irq_save() / local_irq_restore() 包住的代码，以及所有 *_irqsave 变体的锁。这段时间内 CPU 对普通中断完全失聪。写得规矩的代码只关几十条指令，但历史包袱里有不少「顺手把一大段包进去」的写法。ftrace 的 irqsoff tracer 存在的意义就是抓这个。

③ 软中断与 tasklet

硬中断的 top-half 要求尽快返回，真正的活推给软中断（NET_RX_SOFTIRQ、TIMER_SOFTIRQ、BLOCK_SOFTIRQ 等），tasklet 也建立在软中断之上。问题在于软中断的执行时机与上下文：

  • 它默认在 irq_exit() 里就地执行，也就是「借用刚被打断的那个任务的时间」——被打断的可能正是你的实时线程。
  • 执行期间 bottom-half 被禁用、抢占被关闭，同样是不可抢占段。
  • 它有一个「跑够就交给 ksoftirqd」的退让机制（按处理轮数与时间预算判断），但退让阈值本身就是毫秒量级，对 µs 级需求毫无意义。
  • 大流量收包时 NET_RX_SOFTIRQ 可以连续吃掉很长时间，这是生产上最常见的一类毛刺源。

④ per-CPU 变量的保护区

内核大量使用 per-CPU 数据（内存分配器的 per-CPU 缓存、统计计数、页向量）。访问它们的正确姿势是 get_cpu_ptr() / this_cpu_ptr() 配合关抢占——因为一旦被抢占后迁移到别的核，手里的指针就指向了别人的数据。这类保护区数量极多、单个很短，但它们让「内核任意一处都可能短暂不可抢占」成为常态，也是 RT 化改造中最琐碎的部分（需要引入 local_lock_t 这类抽象来替代裸的关抢占）。

⑤ 内存管理路径：缺页、回收、规整、大页

这是最容易被低估的一类。一次看似普通的写内存，可能触发：

  • 缺页处理：匿名页首次写入要清零一页；文件页要走 I/O。若已经开始换出，代价是毫秒到秒级。
  • 直接回收（direct reclaim）：分配路径上没内存了，当场去扫 LRU、回写脏页。这条路径的耗时完全不可预测。
  • 内存规整（compaction）：为凑出连续大页而搬移页面，期间大量持锁。
  • 透明大页（THP）：一次缺页要清零 2 MB 而不是 4 KB，单次耗时直接放大数百倍。实时系统一律 transparent_hugepage=never。

注意这一类无法靠改内核解决——PREEMPT_RT 也不能让缺页变快。它只能靠应用侧的 mlockall() + 预分配来彻底避开，这就是后面 §4 反复强调它的原因。

⑥ RCU 宽限期与回调

RCU 读侧临界区本身极轻（在非抢占式 RCU 下就是关抢占），但宽限期结束后的回调处理默认跑在软中断里，批量释放对象时可以吃掉可观的时间。rcu_nocbs= 把回调挪到专门的内核线程，正是为此。

⑦ printk 到慢速控制台

一条 printk 如果控制台是 115200 波特率的串口，输出 80 个字符大约需要 7 ms，而且历史上这段是在关中断/持锁的情况下同步吐出去的。生产实时系统上，一个平时不触发的错误分支里的 printk，就是一颗定时炸弹。（内核社区为此长期推进 printk 的异步化改造，这也是 PREEMPT_RT 合入过程中的关键前置工作之一。）

⑧ SMI —— 操作系统完全看不见的那一层

System Management Interrupt（SMI）是这份清单里最阴险的一条，因为它根本不归操作系统管。x86 平台上，固件可以让 CPU 进入 SMM（System Management Mode）——一个优先级高于一切、连 NMI 都被屏蔽、Linux 完全无法感知也无法拒绝的模式。风扇调速、温度管理、ECC 纠错记录、USB 键盘的传统模拟、某些厂商的带外管理，都可能用 SMI 实现。

它的可怕之处在于取证困难：你的 ftrace 看到的是「时间凭空跳了 300 µs，中间什么都没发生」。所有内核侧的追踪工具在 SMM 期间都是停摆的。判据也很简单：cyclictest 报出大尖峰，但 ftrace 的时间线上找不到任何对应事件——那就是 SMI（或同类的固件级中断）。专门的检测手段见 §5 的 hwlatdetect / rtla hwlat。

mainline 本身就提供了几档抢占强度，理解它们的差别有助于判断「我到底需不需要 RT」：

看这张图要抓住的重点：99.9% 的样本都在 100 µs 以内——如果你只看均值或者 P99，会得出「这机器实时性挺好」的结论。而真正决定成败的是最右边那两行千分之一、万分之一的样本。一个 1 kHz 的控制环一小时有 360 万次循环，万分之一就是 360 次越界；对伺服驱动来说这等于一小时抖 360 下。

记住这个思维方式：实时性问题永远是「分布右尾」问题，不是「均值」问题。后面 §5 会反复强调「只看 Max，不看 Avg」，根子就在这里。
02

RT patch 的 5 大核心改动

sleeping spinlock · threaded IRQ · 优先级继承 · 软中断线程化 · hrtimer 与 tickless

PREEMPT_RT 的全部工作，可以用一句话概括：把内核里所有「不可抢占的等待」改造成「可调度的等待」。不可抢占的等待是黑箱——你无法给它排优先级，无法观测，也无法证明上界；可调度的等待是白箱——它是一个有优先级的实体，会出现在 ps 的输出里，能被更高优先级的任务抢占，也能被 tracer 记录。

生活类比：把插队改成叫号。原来的内核像一家没有叫号机的诊所——谁先挤到窗口谁先办，急诊病人只能干等前面那个人办完。RT 做的事不是让每个人办得更快，而是装了一台叫号机并给急诊发了优先号：办事窗口随时可以中断当前业务去接急诊。总吞吐反而下降了（叫号、切换都要时间），但「急诊最多等多久」第一次变成可以回答的问题。

2.1 二十年 out-of-tree，2024 年终于进主线

PREEMPT_RT 由 Ingo Molnar 与 Thomas Gleixner 在 2004 年前后发起，此后长期以 out-of-tree 补丁集的形式存在——每出一个内核版本，维护者就要把成百上千个补丁重新 rebase 一遍。这套补丁的绝大部分内容其实是分批渗入主线的：hrtimer 子系统、generic IRQ 与线程化中断框架、可睡眠的 rtmutex 与优先级继承、ftrace 及其一系列 latency tracer、无 tick 空闲与 nohz_full、以及 printk 的重写——这些今天所有 Linux 用户都在用的基础设施，最初都是为 RT 做的。

2024 年，最后一块核心拼图（主要是 x86 上的相关支持）随内核 6.12 合入主线，CONFIG_PREEMPT_RT 成为一个正式的抢占模型选项。这件事的意义不在于性能——合入前后延迟数字几乎没变——而在于工程成本：

  • 不再需要维护内核 fork，安全补丁跟随上游节奏，这对需要长期维护的车载/工业产品是决定性的。
  • 第三方驱动与 RT 的兼容性问题从「补丁作者的事」变成「上游 API 契约的事」，出问题有地方讲理。
  • 新增子系统在设计阶段就要考虑 RT 语义（比如不能在 raw_spinlock 下调用可能睡眠的函数），质量门槛前移。
需要一句保守的补充：「合入主线」不等于「所有架构、所有驱动都开箱即用」。各架构与各驱动子系统的 RT 就绪程度不同，某些驱动在 RT 下仍可能触发「在原子上下文中睡眠」的告警。上生产前必须在目标平台上实测并跑 lockdep 等自检开启的调试内核。

2.2 改造一：sleeping spinlock

这是五项里影响面最大、也最需要讲清楚的一项。RT 把内核里绝大多数 spinlock_t 的实现替换成基于 rtmutex 的可睡眠锁：拿不到锁的任务不再忙等，而是进入睡眠队列让出 CPU；持锁的任务也不再关抢占，可以被更高优先级任务抢占下去。

/* 同一份驱动代码，在两种内核下的实际语义 */

spin_lock(&dev->lock);
    /* mainline: preempt_disable() 已生效，本核在这段里绝不切换任务  */
    /* RT:       实为 rt_mutex 加锁；本段可被高优先级任务抢占，       */
    /*           抢占者若也要这把锁，会睡眠等待并把优先级继承给持锁者 */
    update_ring(dev);
spin_unlock(&dev->lock);

API 完全兼容——驱动源码一个字都不用改，重编译即可。但语义变了，于是产生了一条硬约束：在 RT 下，spin_lock() 是可能睡眠的，所以不能在真正的原子上下文里调用它。

哪些代码必须用 raw_spinlock_t

内核里总有一些地方是「不能睡的」，否则会递归死锁——比如调度器自己、rtmutex 的实现自己。这些地方保留 raw_spinlock_t，它在 RT 下仍然是老语义（忙等 + 关抢占）：

场景用哪个原因
调度器核心（rq->lock）raw_spinlock_trtmutex 的实现要调度器，调度器不能反过来依赖 rtmutex
rtmutex / futex 内部raw_spinlock_t自举问题，同上
时钟源、hrtimer 基座raw_spinlock_t处在中断进入路径上，无法睡眠
中断控制器驱动、NMI 路径raw_spinlock_t真正的原子上下文
per-CPU 数据的短暂保护local_lock_tRT 下退化为 rtmutex，非 RT 下仅关抢占，语义清晰
普通设备驱动spinlock_t让 RT 有机会把它转成可抢占的锁
驱动作者最常犯的错：为了「更快」或者「避免 RT 下的睡眠告警」而随手把 spinlock_t 改成 raw_spinlock_t。这等于在 RT 内核上人为造了一段不可抢占区，把整机的最坏延迟拉高，而且症状极难定位——因为它不报错，只是偶尔多出几十微秒。raw_spinlock_t 的正确用法是「我确实处在无法睡眠的上下文里」，不是「我觉得这里性能敏感」。

相应地，在 raw_spinlock 临界区里绝不能调用任何可能睡眠的函数——包括 RT 下的 spin_lock()、kmalloc(GFP_KERNEL)、copy_to_user()。开 CONFIG_DEBUG_ATOMIC_SLEEP 能在开发期抓到大部分违规。

换来了什么，代价是什么

收益

  • 抢占延迟的上界不再取决于「内核里最长的临界区」，而取决于极少数 raw_spinlock 段——数量可枚举、可审计。
  • 持锁任务可被抢占后，配合优先级继承，等待时间有了理论上界。

代价

  • 短临界区的开销变大：原来几十纳秒的忙等，现在可能变成一次「睡眠 + 唤醒 + 上下文切换」，代价是微秒级。
  • 上下文切换次数显著增加，cache 局部性变差。
  • 高并发吞吐型负载（数据库、大流量转发）在 RT 内核上吞吐通常有可观下降，具体幅度极依赖负载形态，需自行实测。

所以有一句很实在的经验：不要在同一台机器上既追求最高吞吐又追求最低最坏延迟。它们在架构层面就是互斥的。工程上的正解通常是拆机器，或者至少拆 CPU 核。

2.3 改造二：线程化中断（threaded IRQ）

mainline 的中断分两半：top-half 在 IRQ 上下文里跑，不可抢占；bottom-half 走软中断，同样不可抢占。RT 把这套结构改成：top-half 只做最必要的硬件应答（屏蔽中断源、清状态位），然后唤醒一个专属的内核线程，真正的处理逻辑全部在那个线程里跑。

改造之后，中断在系统里就是一个个看得见、排得动的线程：

$ ps -eo pid,cls,rtprio,comm | grep -E 'irq/|^ *PID'
  PID CLS RTPRIO COMMAND
   62 FF      50 irq/16-ahci0
   93 FF      50 irq/24-eth0-rx-0
   94 FF      50 irq/25-eth0-tx-0
  128 FF      50 irq/31-xhci_hcd

# 关键点：它们是 SCHED_FIFO 线程，优先级可以单独调整
$ sudo chrt -f -p 85 93        # 现场总线网卡的收包线程，提到控制环之上
$ sudo chrt -f -p 20 128       # USB 无关紧要，压到最低
这里有一个很能体现深度的追问：「线程化中断把延迟变低了吗？」严格说，没有——它把中断的『平均处理时延』变高了（多了一次唤醒和上下文切换），把系统的『最坏调度延迟』变低了。你交换到手的是可控性：中断从一个不可协商的打断，变成一个可以被你按优先级排队的对象。能说清这层交换关系，比背下「RT 把中断线程化了」高一个层次。

需要注意两点工程细节：

  • 并非所有中断都能线程化。驱动可以用 IRQF_NO_THREAD 声明必须留在硬中断上下文（时钟中断、IPI、某些中断控制器级联就属于这类）。所以「RT 下没有硬中断了」是错的。
  • 默认优先级是一刀切的，必须自己规划。所有中断线程出厂时通常是同一个优先级，这意味着一块跟你业务无关的网卡，和你赖以驱动控制环的现场总线卡，地位相同。不动手规划等于没享受到这项改造的好处。

2.4 改造三：优先级继承（PI）

把自旋锁变成可睡眠的锁，立刻引入一个新问题：优先级反转。

优先级反转（priority inversion）：高优先级任务 H 阻塞在一把被低优先级任务 L 持有的锁上。本应等 L 跑完释放即可，但一个不需要这把锁的中优先级任务 M 抢占了 L 并长期占着 CPU。于是 H 被 M 间接饿死——尽管 H 的优先级明明高于 M。这叫「无界优先级反转」，因为 M 可以跑任意久。

最著名的案例是 1997 年的火星探路者号：着陆后反复看门狗复位，根因正是一个高优先级的总线管理任务被中优先级的通信任务通过一把互斥锁间接阻塞。JPL 的工程师最终通过远程打开 VxWorks 上的优先级继承开关解决。

rtmutex 内建优先级继承协议：当 H 阻塞在 L 持有的 rtmutex 上时，内核临时把 L 的有效优先级提升到 H 的水平；L 释放锁后立即恢复。这样 M 抢不走 L 的 CPU，H 的等待时间就被压缩成「L 的临界区长度」——一个有界的量。

时刻无 PI有 PI
L 拿到锁L 以 P:10 运行L 以 P:10 运行
H(P:80) 来抢并阻塞在锁上L 回到 P:10 等待被调度L 被提升到 P:80
M(P:50) 就绪M 抢占 L，H 无限期等待M 优先级低于此刻的 L，抢不动
结果H 的等待时间 = M 的运行时间，无界H 的等待时间 ≈ L 的临界区长度，有界

PI 也有代价，而且是真实存在的：每次加锁/解锁都要维护「谁在等谁」的依赖链，并沿链传播优先级；链上任一环节变化都要重算。这让锁操作本身变重，也让内核多了一处需要小心处理的复杂状态机（PI 链上的死锁检测、锁的嵌套顺序都要额外考虑）。这也是为什么 mainline 不把 PI 设为普通 mutex 的默认行为。

用户态对应的是 PTHREAD_PRIO_INHERIT 属性的 pthread mutex，底层走 PI-futex，代码见 §4。

2.5 改造四：软中断线程化

光把硬中断线程化还不够——软中断仍然会「借用」被打断任务的时间片执行，且期间禁抢占。RT 的做法是让软中断也在可调度的上下文中执行：处理被推给 ksoftirqd/N 这样的 per-CPU 内核线程，而不是在 irq_exit() 里就地跑到底。

$ ps -eo pid,cls,rtprio,psr,comm | grep -E 'ksoftirqd|rcuc|rcub|ktimers'
  PID CLS RTPRIO PSR COMMAND
   14 TS       -   0 ksoftirqd/0
   22 TS       -   1 ksoftirqd/1
   15 FF       1   0 rcuc/0            # RT 下 RCU 处理也有了自己的线程
   23 FF       1   1 rcuc/1
   16 FF       1   0 ktimers/0         # 定时器软中断的承载线程
这项改造会咬人的地方：软中断线程化之后，网络吞吐能力下降是可预期的。原来收包在软中断里连续处理，cache 全热；现在要经过唤醒、调度、切换。如果同一台机器既要跑控制环又要跑千兆满速转发，你会两头不讨好。正确做法是把「实时」和「吞吐」分到不同的 CPU 核上：隔离核跑控制环，非隔离核跑网络与业务，中断亲和把收包全部赶到非隔离核（§3、§4 会给出完整配置）。

2.6 改造五：高精度定时器与 full tickless

实时任务的典型形态是「每 1 ms 醒一次」。如果定时精度只有 jiffies（CONFIG_HZ=250 时是 4 ms），这件事根本无从谈起。hrtimer 子系统让定时器直接编程到硬件时钟比较器上，精度取决于时钟源而非 tick 频率。

/* 周期任务的正确写法：绝对时间 + TIMER_ABSTIME，避免漂移 */
struct timespec next;
clock_gettime(CLOCK_MONOTONIC, &next);

for (;;) {
    next.tv_nsec += 1000000L;              /* 1 ms 周期 */
    if (next.tv_nsec >= 1000000000L) { next.tv_nsec -= 1000000000L; next.tv_sec++; }

    /* 用绝对时间睡到下一个周期点：即使本轮 do_work() 超时，
       下一轮的唤醒时刻仍然对齐在原有节拍上，误差不会累积。      */
    clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, NULL);

    do_work();
}

/* ❌ 反例：相对睡眠会累积漂移
   nanosleep(&one_ms, NULL);  // 实际周期 = 1ms + do_work() 耗时 + 唤醒误差 */

full tickless（CONFIG_NO_HZ_FULL）解决的是另一半问题：即使没有任何定时器到期，内核也会周期性地打 tick 来做时间记账、调度统计与 RCU 推进。对一个只跑单个实时线程的隔离核来说，这就是每秒几百次纯粹的干扰。nohz_full= 让这些核在「上面只有一个可运行任务」时彻底停掉周期 tick。

条件很关键：nohz_full 只在该核上恰好只有一个可运行任务时才真正停 tick。只要多出第二个可运行任务（哪怕是个短命的 kworker），tick 就会回来。所以它必须和 isolcpus、rcu_nocbs、中断亲和一起用才有效果——这也是后面反复出现的「四件套」。另外系统里至少要留一个非 nohz_full 的核来承担时间维护工作。

PREEMPT_DYNAMIC 与 PREEMPT_RT 是什么关系？这是面试常问、也常被答错的一点。
CONFIG_PREEMPT_DYNAMIC 让内核在启动时（通过 preempt=none|voluntary|full）甚至运行时在 none / voluntary / full 这三档之间切换，实现方式是静态调用打桩，几乎没有额外开销。它的价值是「一个发行版内核镜像同时服务服务器和桌面用户」。

但 PREEMPT_RT 不在这个可切换集合里。因为 RT 改变的是锁的语义（spinlock_t 到底会不会睡眠）——这决定了成千上万处代码的编译结果和合法性检查，无法在运行时翻转。所以：RT 必须在编译期决定，一台机器要么是 RT 内核要么不是，没有中间态。

以一台 8 核（0–7）工控机为例，核 0–1 做管家核（跑系统服务、中断、日志），核 2–7 留给实时任务：

# /etc/default/grub

GRUB_CMDLINE_LINUX_DEFAULT=""
GRUB_CMDLINE_LINUX="\
isolcpus=nohz,domain,managed_irq,2-7 \
nohz_full=2-7 \
rcu_nocbs=2-7 \
rcu_nocb_poll \
irqaffinity=0-1 \
intel_pstate=disable \
processor.max_cstate=1 intel_idle.max_cstate=0 \
nosmt \
transparent_hugepage=never \
nosoftlockup nmi_watchdog=0 \
audit=0 \
skew_tick=1 \

# 生成并重启
$ sudo update-grub          # Debian/Ubuntu
$ sudo grub2-mkconfig -o /boot/grub2/grub.cfg   # RHEL 系
$ sudo reboot
两点说明：
① isolcpus= 的带标志形式（nohz,domain,managed_irq,）比裸写核号更明确：domain 摘出负载均衡域，managed_irq 让内核托管的多队列中断避开这些核（对 NVMe、多队列网卡尤其重要，因为它们的中断由内核自动分配，不受 irqaffinity 完全约束）。
② console=ttyS0 在调试期很有用，但生产上要慎重——串口控制台的同步输出是毫秒级延迟源。稳定后应降低 loglevel 或移除串口控制台。

不要假设，要验证。下面这套命令建议做成开机自检脚本，因为「以为装了 RT 内核其实 grub 默认项没改」是真实发生过的事故。

# ① 内核版本字符串里必须出现 PREEMPT_RT

3.5 用现成的 RT 内核还是自己编

来源获取方式适合注意
Debian仓库里有 RT 变体的内核镜像包快速验证、实验室环境配置是通用取向，未必按低延迟优化
Ubuntu通过其订阅服务提供实时内核企业环境、要商业支持需要账号/订阅，条款以官方为准
RHEL / 兼容发行版专门的实时产品线需要长期支持与合规文档商业授权
Yocto / BuildrootPREEMPT_RT 作为内核配置片段嵌入式产品的主流做法要自己维护 .config 与 BSP 补丁的兼容性
自行编译上游make menuconfig 选 Fully Preemptible需要精确控制每一个选项要自己接安全更新，长期成本最高

选择建议很简单：产品化项目走 Yocto/Buildroot 自建，因为你迟早要为了某个 BSP 驱动改内核；纯做算法验证或先导研究，用发行版现成的 RT 内核最省事。唯一不该做的是在生产设备上长期跑一个「某人两年前手编的、没人记得配置是什么」的内核。

系统级 + 应用级调优

固件设置 · 中断亲和 · RT 限流的取舍 · 优先级规划 · mlockall 与栈预热 · PI mutex

装上 RT 内核只是拿到了「有可能做到」的资格。一个没做过应用侧改造的程序，跑在 RT 内核上和跑在普通内核上，最坏延迟可能没有区别——因为它的毛刺来自缺页、来自日志、来自动态库符号解析，而这些 RT 内核一条都管不了。这一章分两层：先把机器收拾干净（系统级），再把程序改对（应用级）。

4.1 固件层：在 BIOS 里做的事，操作系统补不回来

这一层最容易被软件工程师忽略，却常常是最坏延迟的天花板。因为 SMI 发生在 SMM 里，Linux 既看不见也拦不住——你唯一的操作界面就是固件设置界面。

固件设置项（名称随厂商而异）建议理由与代价
USB Legacy Support / USB 键盘鼠标模拟关典型的 SMI 来源：每次 USB 轮询都可能陷入 SMM。代价是 BIOS 里不能用 USB 键盘（用带外管理或 PS/2）
硬件健康监控 / 风扇智能调速 / 温度轮询关或调到最低频率周期性 SMI。代价是散热策略变成固定转速，噪音和功耗上升
内存 ECC 错误日志、PCIe AER 的 SMI 上报视安全要求决定这是一个真正的取舍：关掉能消除 SMI，但也失去了硬件故障的早期告警。功能安全项目里通常不允许关，只能改用带外方式
C-State / Package C-State / Deep Sleep关到 C1 或 C0与 processor.max_cstate=1 呼应；固件层关掉更彻底
Turbo Boost / SpeedStep关频率固定后 WCET 才可估。代价是峰值算力下降 20%~30%，需要在选型时就把这部分算进余量
Hyper-Threading / SMT关兄弟线程争抢 L1D、执行端口，抖动来源。代价是逻辑核减半
厂商的性能/电源预设选「最高性能 / 确定性」类档位部分服务器主板有专门的 low-latency 预设，能一次关掉一堆项
板子选型比调参更重要。消费级主板的固件里根本不暴露 SMI 相关开关，你连关都没得关。工业主板与服务器主板通常提供「确定性性能」预设，部分厂商还提供 SMI 计数的可观测接口。如果项目有硬实时要求，硬件选型阶段就要把「固件是否可配、厂商是否给 SMI 数据」列进评分表——等板子焊好了再发现关不掉，就只能换板子。

4.2 运行时：sysctl 与 RT 限流的取舍

# /etc/sysctl.d/99-realtime.conf

# ---- 内存：让缺页彻底不可能发生 ----
vm.swappiness = 0                  # 尽量不换出（更彻底的做法是根本不配 swap）
vm.dirty_ratio = 5                 # 压低脏页水位，避免突然的大批量回写
vm.dirty_background_ratio = 2
vm.overcommit_memory = 2           # 严格记账，宁可分配失败也不要 OOM 时才发现
vm.stat_interval = 120             # 降低 vmstat 更新频率，减少周期性内核工作

# ---- 调度 ----
kernel.sched_rt_runtime_us = 950000   # 默认值：每 1s 周期里 RT 最多占 0.95s

# ---- 减少不必要的周期性工作 ----
kernel.numa_balancing = 0          # 自动 NUMA 迁移会制造缺页与 TLB 失效
kernel.timer_migration = 0         # 不把定时器迁到别的核（保持隔离）

sched_rt_runtime_us：设不设成 -1，是一道判断题

内核默认给实时任务设了一个限流：每 sched_rt_period_us（默认 1 秒）里，实时任务最多占用 sched_rt_runtime_us（默认 950000 µs，即 95%）的 CPU 时间，剩下 5% 强制留给普通任务。这个机制的存在理由是防呆：一个写错的 SCHED_FIFO 死循环会让你连 SSH 都登不上去，只能按电源键。

设置好处风险适用
保持 950000（默认）失控的 RT 任务不会锁死整机，还能登进去救正常的 RT 任务也可能被限流，制造出周期性的、长达数十毫秒的停顿开发阶段、非隔离核
设为 -1（关闭限流）RT 任务不会被无故打断一个死循环 = 整核不可用；若绑在隔离核上尚可，若在管家核上就是整机失联生产环境 + 已隔离 + 代码经过评审
用 SCHED_DEADLINE 替代内核做准入控制，天然有带宽约束与限流需要给出可靠的 WCET周期行为明确的控制任务
如果你决定关掉限流，必须同时满足两个前提：① RT 线程被 isolcpus 钉在隔离核上，且系统至少留有一个非隔离核可供登录；② 有独立的看门狗（硬件看门狗或另一个核上的监控进程）能在 RT 线程失控时复位。只关限流不做这两件事，等于把「偶尔卡 40 ms」换成了「偶尔整机死机」——后者在现场更难交代。

4.4 应用级（一）：优先级规划

SCHED_FIFO 的优先级范围是 1–99，数字越大越优先。很多人第一反应是「我的任务最重要，设 99」——这是新手最典型的一刀，而且伤的是自己。

为什么不能把业务线程设成 99：RT 内核里有一批关键内核线程本身就是 SCHED_FIFO，比如中断线程、rcuc/*、ktimers/*、以及各种看门狗。它们的优先级通常在 1~50 这个区间，但系统里最高的那一档（接近 99）是留给迁移线程、看门狗这类「必须能跑起来否则系统失去自愈能力」的实体的。

你把业务线程设成 99 并写了个偶发死循环，结果是：连负责检测「有任务卡死」的机制都抢不到 CPU，机器彻底失去响应，日志里什么都留不下。正确的做法是给自己留出「上有内核、下有辅助」的中间区间。

一个可以直接套用的分层规划（具体数值需按你系统里实际的内核线程优先级校准，先用 ps -eo cls,rtprio,comm | sort -k2 -n 摸清现状）：

优先级区间放什么说明
99不要碰留给迁移线程、停机线程等内核自身机制
90–98硬件看门狗喂狗线程、安全监控必须比业务高，否则业务卡死时它也喂不了狗
80–89最紧的控制环（电流环、力控内环）周期最短、超时后果最严重的那一个
70–79驱动它的关键中断线程（如现场总线网卡）要略低于它服务的控制环，还是略高，取决于数据流方向，需要具体分析
60–69次级控制环（位置环、轨迹规划）周期更长，可以被内环抢占
40–59其余中断线程（默认档）保持默认或按重要性微调
10–39实时数据的搬运、状态机、通信有时限但不致命
SCHED_OTHER日志、诊断、HMI、网络服务不要给它们任何 RT 优先级

什么时候改用 SCHED_DEADLINE

SCHED_FIFO 表达的是相对优先级——它能回答「谁比谁重要」，回答不了「系统整体扛不扛得住」。SCHED_DEADLINE 让任务声明三元组 (runtime, deadline, period)，内核用 EDF 调度并在设置时做准入控制：所有 deadline 任务的带宽之和超出容量就直接拒绝。

/* SCHED_DEADLINE：声明「每 1 ms 需要 200 µs，必须在 800 µs 内完成」 */
#include <linux/sched.h>
#include <sys/syscall.h>

struct sched_attr attr = {0};
attr.size            = sizeof(attr);
attr.sched_policy    = SCHED_DEADLINE;
attr.sched_runtime   =  200000;   /* ns：WCET 估计，宁可略大  */
attr.sched_deadline  =  800000;   /* ns：相对截止时间        */
attr.sched_period    = 1000000;   /* ns：周期 1 ms           */

if (syscall(SYS_sched_setattr, 0, &attr, 0) != 0)
    perror("sched_setattr");   /* EBUSY = 准入控制拒绝：系统带宽不够 */
SCHED_FIFOSCHED_DEADLINE
表达能力相对优先级绝对时间约束
过载时低优先级任务被饿死，无人告知准入阶段就返回 EBUSY，问题前移到部署期
任务超支可以一直跑，拖垮别人被限流到下个周期，天然隔离
前置条件只需排出优先级序必须有可靠的 WCET，估小了被限流，估大了浪费带宽并挤掉别人
适合优先级关系清楚的通用实时任务行为可测的严格周期任务

4.5 应用级（二）：内存——mlockall 与栈预热

这是应用侧投入产出比最高的一项。缺页处理的耗时从几十微秒到几百毫秒不等（涉及磁盘时更糟），而且它专挑「第一次走到的代码路径」发作——也就是说，实验室里跑一万圈都不出问题的程序，上线遇到第一个异常分支时就会打穿。

/* rt_setup.c —— 实时进程的标准启动序列 */
#define _GNU_SOURCE
#include <sys/mman.h>
#include <sys/resource.h>
#include <sched.h>
#include <pthread.h>
#include <malloc.h>
#include <string.h>
#include <stdio.h>

/* 预热的栈深度：必须 ≥ 实时线程运行期可能达到的最大栈深。
   估法：用 -fstack-usage 编译看各函数栈帧，或用 valgrind 的栈测量，
   再乘 2 留余量。盲目设 8 MB 既浪费也不能证明够用。          */
#define RT_STACK_PREFAULT   (512 * 1024)
#define RT_HEAP_PREFAULT    (16 * 1024 * 1024)

static void prefault_stack(void)
{
    /* volatile 防止编译器把这段「没有可见副作用」的写入优化掉 */
    volatile char buf[RT_STACK_PREFAULT];
    memset((void *)buf, 0, sizeof(buf));
    /* 函数返回后栈指针回退，但这些页已经建立了映射并被 mlockall 锁住，
       之后线程再向下用栈就不会触发缺页。                          */
}

static void prefault_heap(void)
{
    void *p = malloc(RT_HEAP_PREFAULT);
    if (!p) { perror("malloc"); return; }
    memset(p, 0, RT_HEAP_PREFAULT);   /* 真正落页，不能只 malloc */
    free(p);
    /* free 之后这块内存仍在本进程的堆里（下面已禁止归还内核），
       后续分配会复用这些已经落页且被锁住的页。                 */
}

int rt_setup(int cpu, int prio)
{
    /* ① 锁住当前和未来的所有映射，杜绝缺页与换出。
          MCL_CURRENT：现在已映射的；MCL_FUTURE：以后新映射的。 */
    if (mlockall(MCL_CURRENT | MCL_FUTURE) != 0) {
        perror("mlockall");       /* 常见失败：RLIMIT_MEMLOCK 太小 */
        return -1;                 /* ★ 失败必须当致命错误，不要只打印 */
    }

    /* ② 让 glibc 分配器别把内存还给内核，也别用 mmap 走新映射。
          否则「归还 → 再申请」会重新触发缺页，等于白锁。      */
    mallopt(M_TRIM_THRESHOLD, -1);
    mallopt(M_MMAP_MAX, 0);

    /* ③ 预热堆与栈 */
    prefault_heap();
    prefault_stack();

    /* ④ 绑核（必须绑在隔离核上，否则前面 isolcpus 白配） */
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(cpu, &set);
    if (pthread_setaffinity_np(pthread_self(), sizeof(set), &set) != 0)
        perror("pthread_setaffinity_np");

    /* ⑤ 最后才提优先级：前面几步万一卡住，还不至于以 RT 优先级卡住 */
    struct sched_param sp = { .sched_priority = prio };
    if (sched_setscheduler(0, SCHED_FIFO, &sp) != 0) {
        perror("sched_setscheduler");   /* EPERM：检查 RLIMIT_RTPRIO / CAP_SYS_NICE */
        return -1;
    }
    return 0;
}

创建实时线程时，栈也要在创建阶段就定好并预热，不要依赖默认的 8 MB 惰性栈：

/* 为实时线程显式设置栈大小并保证它被锁住 */
pthread_attr_t attr;
pthread_attr_init(&attr);
pthread_attr_setstacksize(&attr, 1024 * 1024);          /* 按实测栈深设定 */
pthread_attr_setinheritsched(&attr, PTHREAD_EXPLICIT_SCHED);
pthread_attr_setschedpolicy(&attr, SCHED_FIFO);
struct sched_param sp = { .sched_priority = 80 };
pthread_attr_setschedparam(&attr, &sp);

pthread_t tid;
pthread_create(&tid, &attr, rt_thread_main, NULL);
pthread_attr_destroy(&attr);

/* rt_thread_main 的第一件事仍然是 prefault_stack()——
   mlockall(MCL_FUTURE) 保证新栈被锁，但「锁」不等于「已建立映射」，
   仍需主动写一遍把页真正落下来。                                  */

mlockall 的两个常见失败原因，部署脚本里要提前处理：

# ① RLIMIT_MEMLOCK 默认可能很小，导致 mlockall 返回 ENOMEM
$ ulimit -l
64                     # KB —— 远远不够

# /etc/security/limits.d/99-rt.conf
@realtime   -   memlock   unlimited
@realtime   -   rtprio    95
@realtime   -   nice      -20

验证 mlockall 是否真的起作用，不要只看返回值。跑起来之后对比这两个数：
grep -E 'VmLck|VmRSS' /proc/<pid>/status —— VmLck 应该和 VmRSS 同量级；如果 VmLck 是 0，说明 mlockall 压根没成功。
再看 /proc/<pid>/stat 的第 10、12 字段（minflt / majflt）：进程进入稳态后，这两个计数应当完全不再增长。只要还在涨，就说明还有没预热到的路径。这是一个非常干净的判据，比盯 cyclictest 直观得多。

4.6 应用级（三）：PI mutex 与线程间同步

只要实时线程和非实时线程共享一把锁，优先级反转就是必然会发生的事——区别只是多久发生一次。所有跨优先级共享的 mutex 都必须启用优先级继承。

/* 带优先级继承的 mutex —— 跨优先级共享时的唯一正确写法 */
pthread_mutexattr_t mattr;
pthread_mutexattr_init(&mattr);

/* ① 优先级继承：持锁者被临时提升到最高等待者的优先级 */
pthread_mutexattr_setprotocol(&mattr, PTHREAD_PRIO_INHERIT);

/* ② 健壮性：持锁者意外退出时，下一个 lock 返回 EOWNERDEAD 而不是永久死锁 */
pthread_mutexattr_setrobust(&mattr, PTHREAD_MUTEX_ROBUST);

pthread_mutex_t lock;
pthread_mutex_init(&lock, &mattr);
pthread_mutexattr_destroy(&mattr);

/* 使用时要处理 EOWNERDEAD */
int rc = pthread_mutex_lock(&lock);
if (rc == EOWNERDEAD) {
    /* 上一个持有者死了，共享数据可能处于不一致状态：先修复再声明可用 */
    repair_shared_state();
    pthread_mutex_consistent(&lock);
} else if (rc != 0) {
    /* 真错误 */
}
/* ... 临界区尽可能短 ... */
pthread_mutex_unlock(&lock);

另一个方案是优先级天花板（PTHREAD_PRIO_PROTECT）：拿到锁就无条件提升到预设上限，不需要维护等待链，开销更小、更可预测；代价是必须静态分析出「所有可能用这把锁的线程里最高的优先级」，一旦有人加了个更高优先级的线程忘了改天花板，保护就失效了。动态系统用 PI，静态可分析的系统可以考虑 PROTECT。

更好的做法是根本不共享锁。实时线程与非实时线程之间，优先用无锁的单生产者单消费者环形缓冲交换数据：实时侧只做「写指针推进」这一个原子操作，最坏耗时是常数，连 PI 都不需要。日志、遥测、状态上报几乎全都可以这样解耦。锁只留给真的需要互斥的少数场景。

4.7 实时线程里绝对不能做的事

禁止项为什么替代做法
任何文件 I/O（含 fopen/fwrite/fsync）可能触发块层、回写、缺页，耗时不可预测写进无锁环形缓冲，非实时线程负责落盘
printf / std::cout / 同步日志格式化本身要 malloc，写终端要走 tty 层甚至串口预格式化的二进制记录 + 异步日志后端
运行期 malloc / new / 容器扩容可能走到 mmap、触发缺页、争抢分配器锁启动期预分配 + 对象池；容器提前 reserve()
异常抛出（C++）展开表查找与 RTTI 在多数实现里要取全局锁，且耗时与栈深相关热路径用返回码；异常只用于启动/关停
首次调用动态库函数惰性绑定要走 PLT 解析、可能加载新页LD_BIND_NOW=1 或链接时 -Wl,-z,now；关键路径考虑静态链接
dlopen / 反射式加载运行期加载新的映射启动期加载完毕
无界的自旋等待在单核隔离场景下会饿死持锁者有界自旋后退化为带 PI 的阻塞
系统调用中的可阻塞变体read/write/poll 到慢速设备非阻塞 + 由非实时线程搬运

关于动态链接，值得多说一句，因为它制造的毛刺极难定位：默认的惰性绑定意味着某个库函数第一次被调用时才去解析符号，这次解析要走动态链接器、查哈希表、可能触发缺页。表现就是「程序跑了两小时，突然某个只在故障分支里用到的函数第一次被调用，那一帧超时了」。

05

延迟测量

cyclictest 参数与判读 · 为什么必须加负载 · hwlatdetect 抓 SMI · ftrace 定位来源

调优的每一步都必须有数字支撑，否则就是在拜神。这一章讲怎么产生可信的数字，以及——同样重要——怎么识别不可信的数字。行业里绝大多数「PREEMPT_RT 达标报告」都栽在后者。

先立一条铁律：在实时场景里，只有 Max 是有意义的指标，Avg 没有意义。

这不是修辞。你的控制环是否失效，取决于「有没有哪一次超时」，而不是「平均多久」。Avg 从 5 µs 优化到 3 µs，对系统行为没有任何影响；Max 从 300 µs 降到 80 µs，才是把不能用变成能用。

更要命的是这两个指标经常反向变动：某些优化（比如更激进的批处理、更大的缓存）会降低均值同时抬高长尾。如果你的验收报告首列写的是平均延迟，这份报告应当被退回。

5.1 cyclictest：参数逐个说清

cyclictest 属于 rt-tests 工具集，它的原理很简单：起若干个 SCHED_FIFO 线程，用 clock_nanosleep(TIMER_ABSTIME) 定时唤醒，然后测量「计划唤醒时刻」与「实际拿到 CPU 的时刻」之差。这个差值就是系统给实时任务的调度延迟。

$ sudo apt install rt-tests          # Debian/Ubuntu
$ sudo dnf install rt-tests          # RHEL 系
参数含义怎么选
-p 80 / --priority测量线程的 SCHED_FIFO 优先级设成与你真实业务线程相同的值。设 99 测出来好看但没有参考价值
-i 1000 / --interval唤醒周期（µs）设成你真实的控制周期。默认 1000 即 1 ms
-t 4 / --threads线程数通常等于要测的核数；配 -a 一一对应
-a 2-5 / --affinity把线程钉在指定核上必须指定为你的隔离核，否则测的是管家核
-m / --mlockall测量进程自身锁内存始终加上，否则测的是 cyclictest 自己的缺页
-h 400 / --histogram输出直方图，上限 400 µs上限要略高于预期 Max；超出上限的样本会进 overflow 计数
-D 24h / --duration运行时长见下文，短了没意义
-q / --quiet只在结束时输出配合 -h 用；否则刷屏本身就是负载
--policy=fifo调度策略默认就是 FIFO，显式写更清楚
-M / --refresh-on-max只在刷新最大值时更新显示交互观察时很好用，能看出尖峰何时出现
--secaligned把所有线程的唤醒对齐到整秒制造「多个实时线程同时醒来」的最坏情形，比默认更严格

5.2 两个决定报告是否可信的前提

前提一：必须跑够长

实时性问题的本质是右尾事件。跑 10 分钟测不到「每 6 小时发生一次」的事件，这是常识，但实践中被违反的频率高得惊人。

时长1 kHz 下的样本量能捕捉到的最低事件频率适用
5 分钟30 万分钟级事件改一个参数后的快速回归，不可作为结论
1 小时360 万十分钟级事件调优迭代中的中间验证
24 小时8640 万小时级事件（如日志轮转、定时任务、温度循环）发布前的最低要求
72 小时 ~ 一周2.6 亿 ~ 6 亿天级事件安全相关产品的验收

为什么小时级事件特别值得抓：logrotate、updatedb、证书刷新、内存碎片积累到触发规整、机房空调周期导致的温度波动——这些全都是「白天测不出来，凌晨三点炸一次」的经典角色。

前提二：必须加负载

空机跑 cyclictest 测出来的数字，只能证明「这台机器在无事可做时表现良好」，而这从来不是你要回答的问题。

最坏延迟来自「某段内核代码正好在跑」。空机时文件系统不动、网络栈不动、内存分配器不动、没有 cache 争抢——那些最长的临界区根本没有机会被执行到。于是你得到一个漂亮的两位数，上线后变成三位数，团队一脸困惑。这是这一行最常见的翻车方式，没有之一。

负载要覆盖真实场景会用到的所有内核子系统：

# 终端 1：制造调度与进程压力
$ while true; do hackbench -P -g 20 -l 2000 >/dev/null; done

# 终端 2：制造文件系统与块层压力
$ stress-ng --hdd 4 --hdd-bytes 2G --io 4 --timeout 24h

# 终端 3：制造内存压力（缺页、回收、TLB）
$ stress-ng --vm 4 --vm-bytes 75% --vm-method all --timeout 24h

# 终端 4：制造网络中断压力（从另一台机器打流）
$ iperf3 -c <target> -t 86400 -P 8

# 终端 5：制造缓存争抢（这一条最容易被忘）
$ stress-ng --cache 4 --cache-level 3 --timeout 24h

# 终端 6：这才是被测对象
$ sudo cyclictest -p 80 -i 1000 -t 4 -a 2-5 -m -h 800 -q -D 24h
加负载时有一个必须想清楚的细节：负载应该跑在哪些核上？
答案是非隔离核——这才是真实部署的样子。如果你把负载也放到隔离核上，测的是「隔离失效时有多糟」，那是另一个实验。但也别走极端：负载必须真实地争抢共享资源（LLC、内存带宽、锁），所以「把负载关在另一个 NUMA 节点上」同样会得出偏乐观的结论。

面试里能主动说出「空机测试没有意义」已经是及格线，能进一步讨论「负载放哪、争抢什么」才说明真做过。

5.3 hwlatdetect / rtla hwlat：抓操作系统看不见的那一层

当 cyclictest 报出大尖峰、而所有内核侧追踪都找不到对应事件时，嫌疑人就是 SMI 或同类的固件级中断。检测思路非常巧妙：关中断，然后在一个紧循环里反复读高精度时钟，看时间有没有「跳过去」一段。既然中断已关，任何时间上的空洞就只能是「CPU 被劫持去做了 OS 不知道的事」。

5.5 ftrace：抓住尖峰发生那一瞬间的现场

tracer测什么什么时候用
wakeup_rt最高优先级 RT 任务从被唤醒到真正运行的延迟最贴近 cyclictest 的指标，首选

5.6 rteval：把上面这些打包成一次标准化压测

rteval 是 rt-tests 生态里的综合工具：它自动起一组标准负载（内核编译、hackbench 等），同时跑 cyclictest，最后产出一份包含硬件信息、内核配置、负载描述和延迟直方图的 XML/文本报告。

# 报告里会包含：
#   - CPU 型号 / 核数 / NUMA 拓扑 / 内存大小
#   - 内核版本与 /proc/cmdline
#   - 负载配置（kcompile 的并行度等）
#   - 每核的延迟直方图与 Max

它的真正价值不是「测得更准」，而是可重复、可归档、可跨机器比较。做产品的团队应该把 rteval 报告作为每次内核升级、每次 BIOS 升级、每批新硬件的准入门槛存档——出问题时能立刻回答「上一版是多少」。

5.7 一份合格的延迟报告长什么样

验收清单

  • 写明硬件型号、BIOS 版本、内核版本与完整 /proc/cmdline——缺任何一项，数字都不可复现。
  • 写明负载构成，以及负载跑在哪些核上。
  • 写明测量时长与样本量，至少 24 小时。
  • 首要指标是 Max，附带完整直方图；Overflows 必须为 0。
  • 给出与需求的余量：「需求 1 ms，实测最坏 61 µs，余量约 16 倍」。余量小于 3 倍的系统不应该上线。
  • 说明hwlatdetect 的结果，证明固件层已排查。
  • 如果有异常样本，附上 ftrace 现场与结论。

10 个调优陷阱

每条按「现象 → 原因 → 处方」写，都是现场真出过的问题

这一章按出现频率排序，不是按技术难度。第 1 条和第 2 条占了我见过的问题的一半以上。

陷阱 1 · 空机测试数字漂亮，上线就崩

现象

实验室里 cyclictest 跑出 Max 28 µs，验收报告写得漂漂亮亮。设备到现场接上真实工况，控制环每隔几分钟丢一帧，实测最坏值 900 µs。

原因

测试时机器什么都没干。最长的那些内核临界区（ext4 日志提交、网络协议栈收包、内存回收）根本没被执行到，自然测不出来。你测的是「这台机器闲着的时候有多安静」。

处方：所有延迟测量必须带负载，且负载要覆盖真实场景用到的子系统（见 §5.2）。更进一步，负载应当包含你自己的业务——把真实应用跑起来，cyclictest 作为旁路观察者，这才是最接近生产的构型。

# 最低限度的负载组合（缺一不可）
$ stress-ng --hdd 4 --io 4 --vm 4 --vm-bytes 75% --cache 4 --timeout 24h &
$ while true; do hackbench -P -g 20 -l 2000 >/dev/null; done &
$ iperf3 -c <peer> -t 86400 -P 8 &
$ sudo cyclictest -p 80 -i 1000 -t 4 -a 2-5 -m -h 800 -q -D 24h

陷阱 2 · 忘了 mlockall，被缺页打穿

现象

绝大多数周期正常，但每隔十几分钟出现一次 2~30 ms 的超时。没有规律，重启后前几分钟特别频繁，之后变稀疏。

原因

缺页。「重启后频繁、之后变稀疏」是它的指纹——因为常走的路径逐渐被访问过一遍，剩下的都是冷路径。冷路径包括：异常分支、罕见的配置组合、第一次收到某种报文类型。

处方：mlockall(MCL_CURRENT|MCL_FUTURE) + 堆栈预热 + 关闭分配器归还（见 §4.5）。关键是验证而不是相信：

$ grep -E 'VmRSS|VmLck' /proc/$(pgrep motion_control)/status
VmRSS:     184320 kB
VmLck:     184320 kB          # ★ 两者相等才算锁住；VmLck 为 0 说明失败了

# 稳态下缺页计数必须停止增长 —— 这是最硬的判据
$ for i in 1 2 3; do awk '{print "minflt="$10" majflt="$12}' /proc/$(pgrep motion_control)/stat; sleep 60; done
minflt=48213 majflt=0
minflt=48213 majflt=0         # ★ 没涨，合格
minflt=48213 majflt=0
常见的失败原因是 RLIMIT_MEMLOCK 太小导致 mlockall 返回 ENOMEM，而代码里只 perror() 了一下就继续跑。mlockall 失败必须当作致命错误直接退出——一个没锁住内存的实时进程，还不如不启动。

陷阱 3 · 优先级设成 99，把内核线程压死了

现象

把业务线程从 80 提到 99「以求更稳」，结果系统偶尔整机失去响应，网络断连，串口也不出日志，只能断电重启。事后什么现场都没留下。

原因

RT 内核里有一批 SCHED_FIFO 的关键内核线程（中断线程、RCU 线程、定时器线程、迁移与看门狗）。业务线程占据最高档并出现哪怕短暂的忙循环，这些线程就全部拿不到 CPU——连负责「检测卡死并留下现场」的机制都一起被压死了，所以事后一片空白。

处方：按 §4.4 的分层规划留出上下空间。业务最紧的环放 80–89，把 90 以上留给看门狗与安全监控，99 谁都别碰。动手前先摸清现状：

陷阱 4 · RT throttling 被触发而不自知

现象

延迟分布非常怪：绝大部分正常，但每秒稳定出现一次 30~50 ms 的巨型停顿，周期得像时钟一样准。

原因

sched_rt_runtime_us 限流。内核默认每 1 秒周期里只给实时任务 0.95 秒，剩下 50 ms 强行留给普通任务。「每秒一次、幅度接近 50 ms」就是这个机制的签名。你的 RT 线程 CPU 占用逼近 95% 时就会触发。

处方：先确认，再决定。

# ① 内核会打印一次告警（只打一次，重启后才会再打，很容易被日志淹没）
$ dmesg | grep -i 'RT throttling'
[  842.113204] sched: RT throttling activated

# ② 看当前设置
$ cat /proc/sys/kernel/sched_rt_period_us
1000000
$ cat /proc/sys/kernel/sched_rt_runtime_us
950000

# ③ 两条路：
#    (a) 降低 RT 线程的 CPU 占用 —— 通常才是真正的解，说明你的活儿太重了
#    (b) 关掉限流（前提：已隔离 + 有独立看门狗，见 §4.2）
$ echo -1 | sudo tee /proc/sys/kernel/sched_rt_runtime_us
「每秒一次的固定大停顿」这个特征值得背下来。面试里给出这个现象，能立刻说出「先 dmesg | grep 'RT throttling'」的人不多。同时要能补一句：触发限流通常说明设计本身有问题——一个健康的实时任务不该长期占满一个核的 95%，那意味着你几乎没有余量应对负载波动。直接关限流是止痛药，不是解药。

陷阱 5 · 在实时线程里写日志

现象

平时一切正常，一旦进入故障处理分支（那个分支里有几行 printf 打印诊断信息），延迟直接飙到几十毫秒。故障本身没造成损失，诊断代码造成了损失。

原因

三重代价叠加：格式化要 malloc；写文件走块层与页缓存；如果控制台是串口，115200 波特率下每 80 字符就要 7 ms，而且是同步的。std::cout 还会额外争抢流的内部锁。

处方：实时线程只允许做「往无锁环形缓冲里塞一条二进制记录」，格式化与落盘全部交给非实时线程。

/* 实时侧：只写定长二进制记录，无分配、无格式化、无锁 */
struct LogRec {
    uint64_t ts_ns;
    uint16_t event_id;
    uint16_t cpu;
    int32_t  a, b;            /* 参数按 event_id 解释 */
};

/* SPSC 环形缓冲：实时线程是唯一生产者 */
static inline void rt_log(uint16_t id, int32_t a, int32_t b)
{
    uint32_t w = g_ring.write.load(std::memory_order_relaxed);
    if (w - g_ring.read.load(std::memory_order_acquire) >= RING_SZ) {
        g_ring.dropped++;     /* ★ 满了就丢，绝不阻塞实时线程 */
        return;
    }
    LogRec &r = g_ring.buf[w & (RING_SZ - 1)];
    r.ts_ns = now_ns(); r.event_id = id; r.a = a; r.b = b;
    g_ring.write.store(w + 1, std::memory_order_release);
}

/* 非实时线程：SCHED_OTHER，跑在管家核上，负责格式化与落盘 */
「满了就丢并计数」这个设计选择要说清楚：宁可丢日志，也不能让日志阻塞控制环。丢弃计数本身作为一条指标上报，运维看到它涨说明日志带宽不够，那是可以慢慢优化的问题；而控制环卡一次可能就是设备撞机。这个取舍在评审时要主动讲出来。

陷阱 6 · 动态库首次调用的符号解析

现象

程序运行数小时后，某一帧突然超时几百微秒。之后同样的代码路径再也不超时。极难复现，因为它每个进程生命周期里只发生一次。

原因

惰性绑定。默认情况下动态库函数的地址在第一次调用时才由动态链接器解析：走 PLT 桩、查符号哈希表、可能触发新的缺页。冷门函数（错误处理、罕见配置分支）的第一次调用可能发生在运行几小时之后。

处方：三层防御，见 §4.7 的代码。核心是 LD_BIND_NOW=1 或链接时 -Wl,-z,now，并用 readelf -d 验证标记确实写进了 ELF。关键路径可以更进一步做静态链接。

陷阱 7 · CPU 频率调节与 C-state 唤醒延迟

现象

延迟直方图呈现明显的双峰：一堆样本在 5 µs，另一堆在 40 µs。而且负载越轻，第二个峰越高——「越闲越慢」的反直觉现象。

原因

系统空闲时 CPU 进入深度 C-state，被唤醒时要重新上电、恢复缓存、重锁 PLL，这个退出延迟就是第二个峰。负载轻 → 进深睡的机会多 → 第二个峰更高。频率调节是同一类问题：低频时执行同样的代码要更久，而升频本身也需要时间。

处方：固件层关 C-state 与 turbo，内核层 processor.max_cstate=1 intel_idle.max_cstate=0，governor 设 performance。验证要用 turbostat：

$ sudo turbostat --interval 5

但不要无脑上 idle=poll。它让核 100% 忙、功耗接近满载。在散热受限的设备上会触发温度保护降频，最坏延迟反而变差。正确顺序是：先关深度 C-state 看效果；仍不够再考虑 idle=poll，并同时监控 PkgTmp 与 Bzy_MHz，确认没有热降频。

陷阱 8 · 跨 NUMA 访存

现象

双路服务器上，同一个程序每次启动后的延迟表现不一样：有时 Max 60 µs，有时 180 µs，代码和配置完全没变。

原因

内存分配在一个 NUMA 节点上，线程被调度到另一个节点的核。远端访存要走处理器互联，单次延迟高出可观比例，且带宽受限、更容易被其它流量干扰。启动时落在哪个节点是随机的，所以「每次不一样」。kernel.numa_balancing 还会在运行期搬页，制造额外缺页。

处方：CPU 与内存一起钉在同一节点，并关掉自动平衡。

陷阱 9 · 网卡中断打在隔离核上

现象

isolcpus、nohz_full、rcu_nocbs 都配了，irqaffinity 也配了，但一有网络流量，隔离核上就出现几十微秒的尖峰。/proc/interrupts 里那个核的计数在涨。

原因

多队列网卡与 NVMe 的中断是内核托管（managed IRQ）的：内核按队列数自动分配亲和，不接受用户通过 /proc/irq/N/smp_affinity 修改（写入返回 EIO）。irqaffinity= 也只影响非托管中断。很多人写了批量脚本、看到一堆报错以为是脚本问题，就忽略过去了。

处方：三选一或组合使用。

# ① 用 isolcpus 的 managed_irq 标志，明确告诉内核托管中断要避开这些核
isolcpus=nohz,domain,managed_irq,2-7

# ② 从源头减少队列：队列数 ≤ 管家核数，内核就没地方往隔离核放
$ sudo ethtool -L eth0 combined 2
$ sudo ethtool -l eth0
Current hardware settings:
Combined:  2

# ③ 逐个核确认没有中断计数增长（最终验证，必须做）
$ cat /proc/interrupts | awk 'NR==1 || $4+$5+$6+$7+$8+$9 > 0' | head
#   把列号换成你的隔离核对应的列，非零就是漏网之鱼

# 别忘了不受 irqaffinity 管的另一类：未绑定工作队列
$ cat /sys/devices/virtual/workqueue/cpumask
ffff
$ echo 3 | sudo tee /sys/devices/virtual/workqueue/cpumask   # 只允许核 0-1

陷阱 10 · 在虚拟机里追求硬实时

现象

在虚拟机里装了 RT 内核，参数照抄，cyclictest 大部分时间还不错，但会出现毫秒甚至几十毫秒的尖峰，而且 guest 内的所有追踪工具都查不到原因——ftrace 时间线上一片空白，和 SMI 的表现一模一样。

原因

vCPU 只是宿主上的一个普通线程。宿主的调度器可以在任意时刻把它换下去（steal time），宿主上的其它虚拟机、宿主自己的内核工作、迁移、快照，全都会导致 vCPU 停摆。guest 内核对此完全无感——从它的视角看就是「时间跳了一段」。只要宿主存在任何形式的超卖或共享，guest 里的一切实时保证都是幻觉。

处方：先量化偷走了多少时间，再决定架构。

# guest 里看 steal time —— 这是「我的 vCPU 被宿主抢走的时间」
$ vmstat 1
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 1  0      0 2103224  38112 411220    0    0     0     0  892 1204  3  1 94  0  2
#                                                                            ↑ st 非 0 = 宿主在抢你的 CPU，实时性无从谈起

$ cat /proc/stat | head -1
cpu  4821 0 2201 918224 118 0 44 9821 0 0
#                                 ↑ 第 8 个字段就是累计 steal（单位 jiffies）
结论要说得干脆：通用虚拟化环境下做不了硬实时。如果非要在虚拟化平台上跑，能做的是把它降级为「尽力而为的固实时」，并且宿主侧必须全部满足：
① vCPU 一对一独占绑定物理核（pin），且那些核在宿主上也被 isolcpus 隔离；
② 宿主完全不超卖，内存全部预分配并锁定（大页 + 预分配）；
③ 宿主自己也是 RT 内核，且虚拟机的 vCPU 线程被赋予 RT 优先级；
④ 关闭内存气球、KSM 页合并、动态迁移；
⑤ I/O 走直通（SR-IOV / PCIe passthrough），不走软件模拟。

满足这些之后延迟仍会比裸机差一档。更诚实的工程判断是：真有硬实时需求就用裸机或专用 MCU，把虚拟化留给非实时部分——很多车载与工业方案正是这么划分的（一颗 SoC 上，实时域跑裸的 RTOS/RT Linux，应用域跑虚拟化）。

PREEMPT_RT vs Xenomai vs RTOS

三类架构的根本差异 · 一张选型对比表 · 那个绕不开的核心取舍

选型讨论最容易跑偏的地方，是所有人都盯着「谁的延迟数字更小」。延迟只是五六个维度里的一个，而且往往不是决定性的那个——真正决定项目成败的经常是「这个方案有没有现成的驱动」「团队招不招得到人」「能不能过功能安全认证」。

7.1 三类架构的根本差异

① 打补丁的 Linux（PREEMPT_RT）

一个内核，通过改造让它自身变得几乎处处可抢占。实时任务和普通任务用同一套调度器、同一套 POSIX API，只是优先级不同。

比喻：把整栋写字楼的门都换成能随时打断会议的门，急诊医生可以直接推门进去。

② 双内核 / co-kernel（如 Xenomai Cobalt）

两个内核并存：一个微型实时内核直接接管硬件中断，Linux 降级为它的最低优先级任务。实时任务跑在实时内核上，Linux 只在没有实时活时才运行。

比喻：在写字楼旁边单建一栋急诊楼，急诊完全不受写字楼作息影响，但楼里没有写字楼的会议室和食堂。

③ 独立 RTOS

没有 Linux。FreeRTOS、Zephyr、VxWorks、QNX 这类系统从头就是为确定性设计的：调度器简单、代码量小、常常无 MMU 或使用静态内存布局。

比喻：一栋只做急诊的专科医院，流程极简、极快，但你别指望在里面办公。

关键在于「实时代码运行在谁的调度器之下」：

PREEMPT_RT双内核RTOS

中断先到谁手里Linux实时内核，Linux 拿到的是虚拟化的中断RTOS
Linux 的地位就是它自己实时内核的空闲任务不存在

那个绕不开的核心取舍，一句话说清：

双内核方案的延迟更好，但你必须用它自己的 API 写实时代码——而那套 API 之外的整个 Linux 生态，在实时路径上一概用不了。

具体意味着什么：实时线程里不能调 glibc（可能陷入 Linux 内核而丢失实时上下文），不能用标准 socket，不能直接用 ROS 2 的通信中间件，第三方库基本都要重写或包一层。设备驱动也要为实时侧单独写。你换来的那几十微秒，代价是整个软件栈的可移植性和团队的学习曲线。

而 PREEMPT_RT 的全部魅力就在于：它是同一套代码、同一套 API、同一套工具链。你的实时线程可以直接 std::vector、直接用 ROS 2、直接 gdb 调试。大多数「几十微秒够用」的项目应该选它，不是因为它最好，而是因为它最便宜。

7.3 一个实用的决策顺序

按这个顺序问，通常三步内就能定

  1. 「超时一次的后果是什么？」——人身伤害或设备损毁，进入功能安全流程，直接考虑 RTOS 或带认证的方案，Linux 顶多做非安全域。只是掉一帧数据，继续往下问。
  2. 「需要的最坏延迟是多少？」——毫秒级：mainline 调优就够，别上 RT 白白损失吞吐。几百微秒到几十微秒：PREEMPT_RT 的主场。个位数微秒：Linux 这条路基本走到头了，考虑双内核、专用 MCU 或把这部分下沉到 FPGA/硬件。
  3. 「需要 Linux 生态吗？」——需要 ROS 2、容器、机器视觉库、复杂网络协议栈：PREEMPT_RT 几乎是唯一合理选择。完全不需要：RTOS 更简单也更可靠。
  4. 「团队会什么？」——这条比前三条加起来还现实。一个纯 Linux 团队硬上 Xenomai，项目周期会翻倍，而且交付后没人敢维护。
  5. 「能不能拆？」——最常被忽略的一招。把 µs 级的那一小块下沉到独立的 MCU 或运动控制卡，主控用 PREEMPT_RT 跑逻辑与通信，这是工业界的主流架构，也是把「不可能的需求」变成「可做的工程」的标准手法。
第 5 条值得展开一句：不要试图用一个系统满足所有延迟等级。典型的机器人架构是「电流环在驱动器的 MCU 上（10 kHz+）→ 关节控制在实时主控上（1 kHz，PREEMPT_RT）→ 规划与感知在应用核上（10~100 Hz，普通 Linux）」。每一层用最适合它的技术，接口用确定性的总线（EtherCAT、CAN FD、TSN）连起来。这比在单一系统里死磕要现实得多。相关内容可参考 实时控制协议 与 TSN 深入。

真实生产案例

三个案例，每个都写清现象、定位过程、根因、处方与最终数字

下面三个案例是把多个项目中反复出现的同类问题提炼后重述的，数字为典型量级、依赖具体硬件与固件，不能当作可复现的基准。有价值的是定位过程——遇到同类现象时该按什么顺序出招。

案例一 · 运动控制的周期抖动：全栈调优的完整账本

背景：一台六轴工业机械臂的主控，1 kHz 位置环，通过 EtherCAT 下发指令。需求是「每个周期的指令必须在周期开始后 200 µs 内发出」。样机阶段用普通 Ubuntu，现场调试时发现末端有肉眼可见的规律性抖动，且负载越重越明显。

定位过程

第一步不是改配置，而是确认问题确实在调度层。在应用里给每个周期打时间戳，统计「实际唤醒时刻 − 计划唤醒时刻」，同时并行跑 cyclictest 做交叉验证：

# 应用侧自测（关键：用 CLOCK_MONOTONIC 与绝对时间基准）
周期数: 3,600,000   计划周期 1000 µs
唤醒偏差  P50:    6 µs
唤醒偏差  P99:   48 µs
唤醒偏差  P99.99: 2,140 µs
唤醒偏差  Max:  11,830 µs        ← ★ 11.8 ms，比周期本身还长一个数量级

# cyclictest 交叉验证（同样带负载）
T: 0 ( 4423) P:80 I:1000 C:3600000 Min: 3 Act: 9 Avg: 11 Max: 12104

两个数字对得上，说明不是应用代码慢，是系统不让它跑。方向确定后按「内核 → 隔离 → 应用 → 固件 → 中断」的顺序逐层推进，每一层只改一类东西并重测 4 小时。

逐阶段的账本

阶段动作cyclictest Max本阶段贡献
基线普通内核，无任何调优约 12 ms—
① 换 RT 内核CONFIG_PREEMPT_RT，其它不动约 900 µs去掉了不可抢占段这个大头
② CPU 隔离四件套isolcpus/nohz_full/rcu_nocbs/irqaffinity约 260 µs第二大收益，把「别人过来」挡住了
③ 应用改造mlockall + 栈堆预热 + 异步日志 + LD_BIND_NOW约 130 µs消掉了所有 ms 级孤立尖峰
④ 固件设置关 C-state / turbo / SMT / USB legacy约 70 µs把双峰压成单峰
⑤ 中断精修降队列数、managed_irq、限制工作队列 cpumask约 55 µs收尾，边际收益递减

结论与经验

  • 换 RT 内核只解决了大约一半的问题（12 ms → 900 µs）。剩下一半分布在隔离、应用、固件三处。「装了 RT 就完事」是最常见的误解。
  • 隔离四件套的收益仅次于换内核，而它不需要改一行代码，是投入产出比最高的一步。
  • 应用改造消灭的是「孤立大尖峰」，不是「整体水位」。看直方图能看得很清楚：第 ③ 步之后，远端那几个孤零零的样本消失了，但主峰位置几乎没动。
  • 最终 55 µs 对 200 µs 的需求，余量约 3.6 倍。这是可以接受的下限；如果只有 1.5 倍，任何一次硬件批次变化都可能让产品在现场翻车。

案例二 · 力控回路被网卡中断打断

背景：一个协作机器人的力控内环，跑在已经做过完整 RT 调优的平台上，平时最坏 60 µs 一切正常。但只要上位机开始拉取点云数据（千兆网大流量），力控环就会周期性出现 300~500 µs 的超时，表现为机器人接触工件时「顿一下」。停掉点云传输，问题立刻消失。

定位过程

现象已经强烈指向网络中断，但「已经配了 irqaffinity=0-1」让人困惑。定位分三步：

# ① 先证实中断确实打在隔离核上（核 4 是力控环所在）
$ cat /proc/interrupts | grep -E 'CPU|eth0'
            CPU0    CPU1    CPU2    CPU3    CPU4    CPU5
 128:     882134       0       0       0       0       0   PCI-MSI  eth0-TxRx-0
 129:          0  874221       0       0       0       0   PCI-MSI  eth0-TxRx-1
 130:          0       0  871003       0       0       0   PCI-MSI  eth0-TxRx-2
 132:          0       0       0       0  869447       0   PCI-MSI  eth0-TxRx-4   ← ★

# ② 试图手工改亲和 —— 失败，这是最关键的一条线索
$ echo 0-1 | sudo tee /proc/irq/132/smp_affinity_list
tee: /proc/irq/132/smp_affinity_list: Input/output error

# ③ 用 osnoise 量化到底被偷了多少
$ sudo rtla osnoise top -c 4 -d 2m
CPU Runtime   Noise  % CPU Aval  Max Noise  Max Single   HW  NMI    IRQ  Softirq  Thread
  4 120000000  391204   99.67399       4128         387    0    2 288401    91022    11779
#                                        ↑ 单次最大噪声 4.1 ms，IRQ 是主要来源

根因

网卡开了 6 个收发队列，这些是内核托管中断——内核按「每个队列一个 CPU」的策略自动分配亲和，既不理会 irqaffinity= 启动参数，也拒绝用户手工修改（写入返回 EIO）。运维当初写的批量绑核脚本对这几个中断全部报错，但脚本把错误重定向丢弃了，没人发现。

echo ... > /proc/irq/N/smp_affinity_list 返回 EIO，是「这是托管中断」的明确信号，不是脚本写错了。知道这一点能省掉几天的排查。很多批量脚本里写着 2>/dev/null，正好把这条最重要的线索吞掉了。

处方与结果

# ① 把队列数降到管家核的数量，内核就没地方往隔离核放
$ sudo ethtool -L eth0 combined 2

# ② 启动参数加 managed_irq 标志，让内核在分配托管中断时避开隔离核
isolcpus=nohz,domain,managed_irq,2-7

# ③ 顺手把未绑定工作队列也关到管家核（收包路径上的 kworker）
$ echo 3 | sudo tee /sys/devices/virtual/workqueue/cpumask

# ④ 验证：隔离核那几列必须全零
$ cat /proc/interrupts | awk '{print $1, $6}' | grep -v ' 0$'
处理前处理后
力控环最坏延迟（点云传输中）约 480 µs约 65 µs
力控环最坏延迟（空闲时）约 60 µs约 58 µs
点云吞吐约 940 Mbps约 910 Mbps

值得注意的是最后一行：队列数从 6 降到 2，吞吐只掉了约 3%。这是一个很典型的发现——多队列带来的吞吐收益在千兆量级上早已饱和，而它带来的中断分散却是实时性的直接杀手。在实时系统上，「默认的性能优化配置」经常是需要被关掉的东西。

案例三 · 实验室达标、现场不达标的固件问题

背景：同一个软件镜像、同一份内核配置。实验室的三台样机跑 72 小时，最坏 52 µs，全部达标。批量部署到客户现场的三十台设备，其中十一台在运行几小时后出现 200~400 µs 的尖峰，另外十九台完全正常。软件完全一致，硬件型号也标称一致。

定位过程

「同样的软件，部分机器有问题」几乎可以直接排除软件因素，把注意力转向硬件与固件。但要拿到证据：

# ① 先在故障机上抓 ftrace 现场 —— 结果是「什么都没有」
$ sudo cyclictest -p 80 -i 1000 -t 1 -a 4 -m -b 200 --tracemark -D 6h
# 触发后查看 trace：
   cyclictest-9021  4d..2  0us : tracing_mark_write: hit latency threshold (312 > 200)
# 时间线上除了这一条标记，前面几乎没有任何事件 ——
# 「延迟发生了，但内核视角里什么都没发生」= 固件级中断的典型签名

# ② 上 hwlatdetect 直接验证
# 故障机：
$ sudo hwlatdetect --duration=30m --threshold=10
Max Latency: 318us
Samples exceeding threshold: 43

# 正常机（同型号）：
$ sudo hwlatdetect --duration=30m --threshold=10
Max Latency: Below threshold
Samples exceeding threshold: 0

# ③ 对比两批机器的固件版本
$ sudo dmidecode -s bios-version
# 故障机：2.14b   正常机：2.17

根因

两批机器出厂时间相差半年，预装的固件版本不同。较早的那一版在温度监控逻辑上有缺陷，机箱内温度超过某个阈值后会显著提高 SMI 的触发频率。这解释了所有观察到的现象：

  • 为什么实验室测不出来——实验室有空调，机箱温度一直在阈值以下。
  • 为什么是「运行几小时后」——机器要跑热才会越过阈值。
  • 为什么只有一部分机器——固件版本不同，且现场机柜位置不同导致散热条件有差异。
  • 为什么 ftrace 什么都抓不到——SMM 期间整个内核都是停摆的。

处方与后续动作

动作结果
统一刷到 2.17 固件，并按低延迟预设配置（关 USB legacy、关 C-state、关 turbo）故障机的 hwlatdetect 降到低于阈值，端到端最坏值回到 60 µs 量级
把 hwlatdetect 加入出厂检验流程，不通过不发货后续批次零复发
把 BIOS 版本、BIOS 设置项快照纳入配置管理，与软件版本一起记录可追溯
在设备上增加机箱温度上报，与延迟指标一起进监控能提前发现散热劣化

三个案例的共同教训

可以直接带走的几条

  1. 「ftrace 抓不到」本身就是一条强证据，不是排查失败。它把嫌疑范围一下子缩到固件与虚拟化两类。
  2. 软件配置必须和固件版本、固件设置一起做配置管理。只锁软件版本而不锁 BIOS 版本，等于只锁了一半。
  3. 把诊断工具做进产线检验。hwlatdetect 跑 30 分钟就能筛掉一整类现场问题，成本远低于事后返工。
  4. 每次只改一类东西，改完重测。案例一那张账本之所以有价值，正是因为每一行都是独立测出来的；一次改十项然后发现变好了，你并不知道该保留哪几项。
  5. 延迟指标要进生产监控。设备上长期采集周期偏差的直方图并上报，退化时立刻告警——不要等客户打电话。
  6. 余量要留够。实测值与需求之间少于 3 倍的余量，在批量部署时几乎必然出事，因为硬件批次、环境温度、固件版本都会浮动。

9.1 主线化之后，实际变化在哪

2024 年随内核 6.12 完成主线化之后，最大的变化不是性能，而是工程组织方式：

主线化之前主线化之后
获取方式下载与内核版本严格对应的补丁集，自己打一个内核配置选项
版本跟进补丁集的发布滞后于主线，安全更新要等与主线同步
驱动兼容第三方驱动在 RT 下出问题，双方互相推RT 语义成为上游契约的一部分，有据可依
新子系统合入后 RT 维护者再去适配设计阶段就要考虑 RT 约束
发行版只有少数发行版提供 RT 变体提供 RT 内核的门槛显著降低

对产品团队最直接的收益是长期维护成本。一个车载或工业产品的生命周期常常是 8~15 年，期间要持续接安全补丁。以前这意味着要养一个能维护内核 fork 的团队；现在跟随发行版或上游 LTS 即可。这个变化对「能不能立项」的影响，比延迟少几微秒大得多。

需要保守地补一句：「主线支持」和「你的板子开箱即用」之间仍有距离。各架构（x86_64、arm64、riscv 等）的成熟度不同，SoC 厂商的 BSP 驱动是否遵守 RT 约束更是逐个不同。实际项目里最常见的仍然是「主线 RT + 厂商 BSP 补丁」的组合，而 BSP 里的驱动往往需要花时间修 raw_spinlock 误用、原子上下文睡眠这类问题。把这部分工作量算进项目计划。

9.2 与 SCHED_DEADLINE 的关系

两者解决的是不同层面的问题，是互补而不是替代：

  • PREEMPT_RT 解决的是「内核会不会挡着我」——它压低的是不可抢占段带来的最坏延迟。
  • SCHED_DEADLINE 解决的是「多个实时任务之间怎么分配才不会互相饿死」——它提供准入控制与带宽隔离。

只有 RT 内核而用 SCHED_FIFO：你能保证内核不挡路，但保证不了「三个周期任务加起来会不会超出这个核的能力」——那要靠人工排优先级和经验估算。只有 SCHED_DEADLINE 而没有 RT 内核：准入控制算出来的带宽是对的，但内核随时可能因为一段自旋锁临界区让你错过截止时间。两者叠加，才既有「不被挡」又有「分得清」。

实践中的采用情况仍然是 SCHED_FIFO 占绝对多数，主要障碍是 SCHED_DEADLINE 要求给出可靠的 WCET——而对跑在带 cache、带分支预测、带 DVFS 的现代 SoC 上的代码，WCET 本身就是一个难题。能给出可信 WCET 的场景（简单固定的控制律、无动态分支的信号处理），用 DEADLINE 收益明显；否则 FIFO + 充足余量更实际。

9.3 eBPF 与实时观测

eBPF 给实时系统带来的价值是长期在线的、低开销的延迟观测——过去要么用 ftrace（开销可控但配置繁琐、结论要人读），要么什么都不测然后等客户报障。

# bpftrace 一行：实时任务的运行队列等待时间直方图（长期挂着也不贵）
$ sudo bpftrace -e '
  tracepoint:sched:sched_wakeup /args->prio < 100/ { @w[args->pid] = nsecs; }
  tracepoint:sched:sched_switch /@w[args->next_pid]/ {
      @runq_us = hist((nsecs - @w[args->next_pid]) / 1000);
      delete(@w[args->next_pid]);
  }'

@runq_us:

[1]               412033 |@@@@@@                                  |
[2, 4)             18221 |                                        |
[4, 8)              1104 |                                        |
[8, 16)               31 |                                        |

但 eBPF 用在实时系统上有一条必须守的纪律：探针本身也是代码，也会在你的隔离核上执行。复杂的 eBPF 程序、大量的 map 更新、以及 map 的内存分配都可能引入额外延迟。生产环境挂长期探针之前，要先测「挂上探针后最坏延迟变化了多少」，并把这个开销计入余量。观测本身不该成为新的噪声源——这个道理和「不要在实时线程里写日志」是同一个。

9.5 值得关注的方向

  • arm64 平台的持续成熟：嵌入式与车载的主力架构，其 RT 相关支持与各 SoC 厂商 BSP 的质量仍在演进中，是选型时要重点验证的一环。
  • 容器化与 RT 的结合：目前把实时负载放进容器仍需大量手工配置（cpuset 独占、去掉 CPU limit、设备直通），且很容易踩到 cgroup 限流。这一块的工具化程度还不高。
  • 确定性网络与 RT 的配套：TSN、时间敏感通信与主机侧实时性需要端到端配合，单独优化主机没有意义。参见 TSN 深入、DetNet 指南。
  • 观测工具的成熟：rtla 这类把「噪声来源」直接量化归类的工具，正在把延迟排查从「靠经验」变成「看数据」。

🎯 全文关键结论
  • 实时 = 最坏情况有界，不是快。验收指标只有 Max，Avg 在实时语境下没有意义。
  • mainline 的不可抢占来源有十来类，PREEMPT_RT 只能解决其中约一半。缺页、固件 SMI、C-state、NUMA、虚拟化都得另想办法。
  • 五大改造各有代价：sleeping spinlock 与软中断线程化换来可抢占性，代价是吞吐与切换开销；threaded IRQ 换来可排优先级，代价是单次处理更慢。
  • 隔离四件套缺一不可：isolcpus + nohz_full + rcu_nocbs + 中断亲和。而且要用 /sys/devices/system/cpu/isolated 验证它真的生效。
  • 应用不改造，RT 内核的收益要打对折。mlockall + 预热 + 无锁日志 + LD_BIND_NOW 是最低配置。
  • 测量必须加负载、跑够 24 小时、看直方图形状。空机短跑得到的数字没有任何工程价值。
  • ftrace 抓不到 = 固件或虚拟化。这条判据能省下大量时间。
  • 数字强依赖硬件与固件。换板子、刷 BIOS 之后所有结论作废，必须重测。余量少于 3 倍不要上线。
  • 选型先问「超时的后果」，再问延迟需求，最后问团队会什么。拆分成多个延迟等级的分层架构，往往比在单一系统里死磕更现实。

11.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础什么是实时系统？「实时」和「快」的区别在哪？

    实时性指的是「最坏情况下的响应时间存在一个可以证明的上界」，与平均速度无关。一个平均 5 µs、但每小时出现一次 40 ms 尖峰的系统是不合格的；一个稳定在 800 µs、从不超过 1 ms 的系统是合格的硬实时系统。

    按超时后果分三档，这个分类要在需求阶段就定死，因为它决定了预算：

    • 硬实时：一次超时即系统失效，可能伤人毁设备（伺服电流环、气囊点火）。
    • 固实时：超时那一帧作废，系统继续（视觉伺服的一帧、周期总线报文）——这是 PREEMPT_RT 的主战场。
    • 软实时：超时只是体验下降（音视频、HMI）。

    工程含义：需求文档里要写「周期 1 ms，抖动不超过 ±100 µs，连续 72 小时无越界」，而不是「尽量低延迟」。验收报告的首要指标必须是 Max 而不是 Avg——因为决定系统成败的是「有没有哪一次超时」。

    加分：能主动指出「低延迟」（高频交易那种，追求平均更快、可接受长尾）和「实时」（追求绝不超时、可接受整体更慢）是两个不同目标，手段也不同——前者靠内核旁路与忙轮询，后者靠 PREEMPT_RT 与核隔离。

  2. 基础mainline Linux 上有哪些不可抢占的来源？为什么它做不了硬实时？

    根本原因不是「Linux 慢」，而是「最长的那个不可抢占段有多长」无法证明上界——它取决于当时恰好在跑什么驱动、什么文件系统路径。主要来源：

    • 自旋锁临界区：spin_lock() 会 preempt_disable()，内核里有数千把锁，你无法枚举最长的那一段。
    • 关中断区间：local_irq_disable() 与所有 *_irqsave 变体，期间连中断都进不来。
    • 硬中断 top-half：IRQ 上下文不可抢占，劣质驱动能跑到毫秒。
    • 软中断 / tasklet：在 irq_exit() 里就地执行，禁 BH 且关抢占，大流量收包时能连续吃掉很长时间。
    • per-CPU 变量保护区：靠关抢占防止迁移，数量极多。
    • 内存管理路径：缺页、直接回收、内存规整、透明大页——单次可达毫秒甚至更久。
    • RCU 回调批量释放、printk 到串口控制台（115200 下每 80 字符约 7 ms）。
    • SMI：固件层的中断，操作系统完全看不见也挡不住。

    关键的补充（能说出来是加分项）：PREEMPT_RT 只能解决前面五条。缺页要靠应用 mlockall，C-state 与 SMI 要靠固件，NUMA 要靠绑定。很多人上了 RT 内核发现毛刺还在，原因就在这里。

  3. 基础PREEMPT_RT 的五项核心改造分别是什么？各自的代价是什么？

    一句话概括 RT 做的事：把内核里所有「不可抢占的等待」改造成「可调度的等待」。五项改造：

    • sleeping spinlock：大多数 spinlock_t 变成基于 rtmutex 的可睡眠锁，持锁期间可被抢占。代价是短临界区从几十纳秒的忙等变成微秒级的睡眠/唤醒，上下文切换增多，吞吐下降。
    • threaded IRQ：中断处理搬到内核线程，可以赋优先级、可以被更高优先级任务抢占。代价是单次中断处理时延升高（多了唤醒和切换），且默认优先级一刀切，必须人工规划。
    • 优先级继承：rtmutex 内建 PI，解决 sleeping lock 带来的优先级反转。代价是加解锁要维护依赖链并传播优先级，开销上升。
    • 软中断线程化：软中断不再借用被打断任务的时间片就地执行。代价是网络吞吐明显下降、cache 局部性变差。
    • hrtimer + full tickless：定时精度到硬件时钟粒度，隔离核可停周期 tick。代价是配置复杂，且 nohz_full 只在核上仅有一个可运行任务时才真正生效。

    总结成一句：RT 是一笔明码标价的交易——用吞吐、能效和工程复杂度换最坏情况的确定性。没有确定性需求的系统开 RT 纯属浪费。

  4. 基础什么是优先级反转？优先级继承怎么解决它？还有别的办法吗？

    优先级反转：高优先级任务 H 阻塞在低优先级任务 L 持有的锁上，此时一个不需要这把锁的中优先级任务 M 抢占了 L 并长期占 CPU。结果 H 被 M 间接饿死，尽管 H 的优先级高于 M。这叫「无界反转」——M 可以跑任意久。经典事故是 1997 年火星探路者号的反复看门狗复位。

    优先级继承（PI）：H 阻塞在 L 持有的 rtmutex 上时，内核把 L 的有效优先级临时提升到 H 的水平；L 释放锁后恢复。这样 M 抢不走 L 的 CPU，H 的等待时间被压缩成「L 的临界区长度」——一个有界的量。

    用户态写法：

    pthread_mutexattr_t a;
pthread_mutexattr_init(&a);
pthread_mutexattr_setprotocol(&a, PTHREAD_PRIO_INHERIT);
pthread_mutexattr_setrobust(&a, PTHREAD_MUTEX_ROBUST);
pthread_mutex_init(&lock, &a);

    另一个方案是优先级天花板（PTHREAD_PRIO_PROTECT）：拿到锁就无条件提升到预设上限，不用维护等待链，开销更小更可预测；代价是必须静态分析出「所有可能用这把锁的线程里最高的优先级」，加了新线程忘了改天花板就失效。动态系统用 PI，静态可分析的系统可用 PROTECT。

    更高一层的答案：最好的办法是根本不共享锁。实时线程与非实时线程之间用无锁 SPSC 环形缓冲交换数据，实时侧只做一次原子的写指针推进，最坏耗时是常数，连 PI 都不需要。

11.2 中级（区分熟练度）

  1. 中级spinlock_t 和 raw_spinlock_t 在 RT 下有什么区别？什么时候必须用后者？

    在 RT 内核下：spinlock_t 变成基于 rtmutex 的可睡眠锁（持锁可被抢占、等锁者睡眠、带优先级继承）；raw_spinlock_t 保持原语义（忙等 + 关抢占）。API 兼容，驱动源码不用改，但语义变了。

    必须用 raw_spinlock_t 的地方，共同点是「处在真正无法睡眠的上下文里」：

    • 调度器核心（如 rq->lock）——rtmutex 的实现依赖调度器，调度器不能反过来依赖 rtmutex，否则自举死锁。
    • rtmutex / futex 自身的实现——同样的自举问题。
    • 时钟源与 hrtimer 基座、中断控制器驱动、NMI 路径——处在中断进入路径上。

    per-CPU 数据的短暂保护应该用 local_lock_t，它在 RT 下退化为 rtmutex、在非 RT 下仅关抢占，语义比裸的 preempt_disable() 清晰。

    生产视角，这才是这道题真正想问的：驱动作者最常犯的错是为了「更快」或「消掉 RT 下的睡眠告警」而把 spinlock_t 随手改成 raw_spinlock_t。这等于在 RT 内核上人为造了一段不可抢占区，把整机最坏延迟拉高，而且不报错、只是偶尔多几十微秒，极难定位。另外，raw_spinlock 临界区里绝不能调用任何可能睡眠的函数——包括 RT 下的 spin_lock()、kmalloc(GFP_KERNEL)、copy_to_user()；开发期开 CONFIG_DEBUG_ATOMIC_SLEEP 能抓到大部分违规。

  2. 中级为什么实时程序必须 mlockall？只调用它就够了吗？怎么验证它生效了？

    因为缺页处理是 PREEMPT_RT 解决不了的延迟源。一次缺页从几十微秒到几百毫秒不等（涉及换出时更糟），而且它专挑「第一次走到的代码路径」发作——实验室跑一万圈没事的程序，上线遇到第一个异常分支时就打穿。典型指纹是「重启后尖峰频繁，之后逐渐变稀疏」。

    只调 mlockall 不够，要配四件事：

    /* ① 锁住现有和未来的映射 */
mlockall(MCL_CURRENT | MCL_FUTURE);

/* ② 让分配器别把内存还给内核、别用 mmap 走新映射，
      否则「归还→再申请」会重新缺页，等于白锁         */
mallopt(M_TRIM_THRESHOLD, -1);
mallopt(M_MMAP_MAX, 0);

/* ③ 预热堆：malloc 之后必须 memset 真正落页，再 free */
void *p = malloc(N); memset(p, 0, N); free(p);

/* ④ 预热栈：volatile 防优化，深度按实测栈深乘 2 */
volatile char buf[512*1024]; memset((void*)buf, 0, sizeof buf);

    还要处理环境：RLIMIT_MEMLOCK 默认可能只有几十 KB，导致 mlockall 返回 ENOMEM；systemd 服务不走 PAM，得在 unit 里写 LimitMEMLOCK=infinity。mlockall 失败必须当致命错误退出，不能只 perror 一下继续跑。

    验证（这是加分的部分，不要只看返回值）：

    $ grep -E 'VmRSS|VmLck' /proc/<pid>/status
VmRSS:  184320 kB
VmLck:  184320 kB      # 两者同量级才算锁住

# 更硬的判据：稳态下缺页计数必须停止增长
$ awk '{print "minflt="$10" majflt="$12}' /proc/<pid>/stat

    只要 minflt 还在涨，就说明还有没预热到的路径。

  3. 中级用 cyclictest 测延迟，为什么必须加负载？负载应该跑在哪些核上？

    因为最坏延迟来自「某段长的内核代码正好在跑」。空机时文件系统不动、网络栈不动、内存分配器不动、没有 cache 争抢——那些最长的临界区根本没有机会被执行到。空机测出来的数字只证明「这台机器闲着的时候很安静」，而这从来不是要回答的问题。

    典型翻车路径：实验室 Max 28 µs 验收通过 → 现场实测 900 µs。这是这一行最常见的事故，没有之一。

    负载要覆盖真实场景会用到的所有子系统：

    $ stress-ng --hdd 4 --io 4 --vm 4 --vm-bytes 75% --cache 4 --timeout 24h &
$ while true; do hackbench -P -g 20 -l 2000 >/dev/null; done &
$ iperf3 -c <peer> -t 86400 -P 8 &
$ sudo cyclictest -p 80 -i 1000 -t 4 -a 2-5 -m -h 800 -q -D 24h

    负载放哪：应该放在非隔离核上，因为那才是真实部署的样子。但也别走极端——负载必须真实地争抢共享资源（末级缓存、内存带宽、内核锁），所以「把负载关到另一个 NUMA 节点」同样会得出偏乐观的结论。

    另外两个同等重要的前提：① 测量参数要和业务一致（-p 用你真实的优先级而不是 99，-i 用你真实的周期，-a 指向你的隔离核）；② 要跑够长——24 小时是发布前的最低要求，因为 logrotate、定时任务、内存碎片积累、机房温度循环都是「白天测不出、凌晨三点炸一次」的角色。

    最后检查 Histogram Overflows 必须为 0，否则超出 -h 上限的样本真实值你根本不知道，报告无效。

  4. 中级什么是 RT throttling？怎么发现它被触发了？该不该关掉？

    内核默认给实时任务设了限流：每 sched_rt_period_us（默认 1 秒）里，实时任务最多占用 sched_rt_runtime_us（默认 950000 µs，即 95%），剩下 5% 强制留给普通任务。目的是防呆——一个写错的 SCHED_FIFO 死循环不至于让你连 SSH 都登不上。

    它的签名非常好认：每秒稳定出现一次、幅度接近 50 ms 的巨型停顿，规律得像时钟。看到这个形状先查它。

    $ dmesg | grep -i 'RT throttling'
[  842.113204] sched: RT throttling activated
# 注意：这条只打印一次，重启后才会再打，很容易被日志淹没

$ cat /proc/sys/kernel/sched_rt_period_us    # 1000000
$ cat /proc/sys/kernel/sched_rt_runtime_us   # 950000

    该不该关，取决于你能不能满足两个前提。关掉的写法是 echo -1 > /proc/sys/kernel/sched_rt_runtime_us，但前提是：

    1. RT 线程已被 isolcpus 钉在隔离核上，且系统至少留一个非隔离核可供登录；
    2. 有独立的看门狗（硬件看门狗或另一个核上的监控进程）能在 RT 线程失控时复位。

    不满足这两条就关限流，等于把「偶尔卡 40 ms」换成「偶尔整机死机」，后者在现场更难交代。

    更重要的判断：触发限流通常说明设计本身有问题。一个健康的实时任务不该长期占满一个核的 95%——那意味着几乎没有余量应对负载波动。直接关限流是止痛药，减轻单周期工作量或换 SCHED_DEADLINE（它自带准入控制和带宽隔离）才是解药。

11.3 高级（体现深度）

  1. 高级线程化中断到底带来了什么？它把延迟变低了吗？优先级该怎么规划？

    先给一个反直觉的结论：线程化中断没有把延迟变低，它把中断的平均处理时延变高了（多了一次唤醒和上下文切换），把系统的最坏调度延迟变低了。你换到手的是可控性——中断从一个不可协商的打断，变成一个可以按优先级排队、可以用 ps 看见、可以被 tracer 记录的普通线程。

    $ ps -eo pid,cls,rtprio,comm | grep irq/
   93 FF      50 irq/24-eth0-rx-0
  128 FF      50 irq/31-xhci_hcd
$ sudo chrt -f -p 85 93     # 现场总线网卡，提到控制环之上
$ sudo chrt -f -p 20 128    # USB 无关紧要，压到最低

    两个必须知道的工程细节：

    • 并非所有中断都能线程化。驱动可以用 IRQF_NO_THREAD 声明必须留在硬中断上下文——时钟中断、IPI、某些中断控制器级联就属于这类。所以「RT 下没有硬中断了」是错的。
    • 默认优先级是一刀切的。所有中断线程出厂时通常同一个优先级，意味着一块和你业务无关的网卡，与你赖以驱动控制环的现场总线卡地位相同。不动手规划等于没享受到这项改造的好处。

    优先级规划的原则（这部分最能区分做过和没做过）：

    • 99 不要碰——留给迁移线程等内核自身机制。业务设 99 并出现忙循环，连负责检测卡死、留下现场的机制都会被压死，事后一片空白。
    • 90–98 给看门狗与安全监控（必须高于业务，否则业务卡死时它也喂不了狗）。
    • 80–89 给最紧的控制环，60–69 给次级环，中间留给驱动它们的关键中断线程。
    • 日志、诊断、HMI 一律 SCHED_OTHER，不给任何 RT 优先级。

    动手前先 ps -eo cls,rtprio,comm --sort=-rtprio 摸清系统里现有内核线程的分布，按实际情况校准，不要照抄任何一份数字。

  2. 高级PREEMPT_RT 和双内核（如 Xenomai）的核心取舍是什么？什么时候该选哪个？

    架构差异在于「实时代码运行在谁的调度器之下」：PREEMPT_RT 只有一个内核，实时任务和普通任务共用 Linux 调度器与 POSIX API；双内核方案是一个微型实时内核直接接管硬件中断，Linux 被降级成它的最低优先级任务，实时代码跑在实时内核上。

    核心取舍一句话：双内核的延迟更好（通常低一个档次），但你必须用它自己的 API 写实时代码，而那套 API 之外的整个 Linux 生态在实时路径上一概用不了。

    具体意味着：实时线程里不能调 glibc（可能陷入 Linux 内核而丢失实时上下文），不能用标准 socket，不能直接用 ROS 2 的通信中间件，第三方库基本要重写或包一层；实时路径上的设备还要写专用驱动。换来的那几十微秒，代价是整个软件栈的可移植性和团队的学习曲线。

    而 PREEMPT_RT 的全部魅力在于同一套代码、同一套 API、同一套工具链：实时线程可以直接用标准容器、直接跑 ROS 2、直接 gdb 调试、直接 perf/ftrace。

    决策顺序（比背对比表更有用）：

    1. 超时一次的后果是什么？会伤人毁设备 → 进功能安全流程，考虑带认证的 RTOS，Linux 最多做非安全域。
    2. 需要多低的最坏延迟？毫秒级 → mainline 调优就够，别白白损失吞吐；几百到几十微秒 → PREEMPT_RT 主场；个位数微秒 → Linux 这条路基本到头，考虑双内核、专用 MCU 或下沉到硬件。
    3. 要不要 Linux 生态？要 ROS 2、容器、视觉库 → PREEMPT_RT 几乎是唯一合理选择。
    4. 团队会什么？这条比前三条加起来还现实。纯 Linux 团队硬上双内核，周期翻倍且交付后没人敢维护。
    5. 能不能拆？最常被忽略的一招——把 µs 级的那一小块下沉到独立 MCU 或运动控制卡，主控用 PREEMPT_RT 跑逻辑与通信。典型机器人架构就是「电流环在驱动器 MCU（10 kHz+）→ 关节控制在 RT 主控（1 kHz）→ 规划感知在普通 Linux（10~100 Hz）」，各层用确定性总线连起来。这比在单一系统里死磕现实得多。
  3. 高级虚拟机里能做硬实时吗？怎么判断 vCPU 被宿主偷了时间？

    结论要说得干脆：通用虚拟化环境下做不了硬实时。

    原因是 vCPU 只是宿主上的一个普通线程。宿主调度器可以在任意时刻把它换下去，宿主上的其它虚拟机、宿主自身的内核工作、迁移、快照都会导致 vCPU 停摆。guest 内核对此完全无感——从它的视角看就是「时间跳了一段」。症状因此和 SMI 极为相似：cyclictest 报出毫秒级尖峰，但 guest 里所有追踪工具都查不到原因，ftrace 时间线一片空白。

    判据（steal time）：

    $ vmstat 1
 r  b   swpd   free  ...  in   cs us sy id wa st
 1  0      0 2103224  ... 892 1204  3  1 94  0  2
#                                              ↑ st 非 0 = 宿主在抢你的 CPU

$ head -1 /proc/stat
cpu 4821 0 2201 918224 118 0 44 9821 0 0
#                                ↑ 第 8 个字段是累计 steal（jiffies）

    如果非要在虚拟化平台上跑，只能把它降级成「尽力而为的固实时」，且宿主侧必须全部满足：① vCPU 一对一独占绑定物理核，且那些核在宿主上也被 isolcpus 隔离；② 宿主完全不超卖，内存预分配并锁定（大页）；③ 宿主自己也是 RT 内核，vCPU 线程被赋予 RT 优先级；④ 关闭内存气球、页合并、动态迁移；⑤ I/O 走 SR-IOV 或 PCIe 直通，不走软件模拟。

    满足这些之后延迟仍会比裸机差一档。更诚实的工程判断是：真有硬实时需求就用裸机或专用 MCU，把虚拟化留给非实时部分。很多车载与工业方案正是这么划分的——一颗 SoC 上，实时域跑裸的 RTOS 或 RT Linux，应用域跑虚拟化，两者靠硬件隔离与共享内存通信。

    加分：能指出「ftrace 抓不到就是一条强证据」——它把嫌疑范围一下子缩到固件（SMI）和虚拟化（steal）两类，而这两类的区分办法分别是 hwlatdetect 和 vmstat 的 st 列。

  4. 高级给你一台全新的机器和一个 1 ms 周期、抖动不超过 100 µs 的需求，你会怎么系统性地把最坏延迟压下来？

    按「先建立可信的测量，再从收益最大的一层开始，每次只改一类并重测」推进。顺序本身就是答案的一部分——顺序错了会浪费大量时间。

    第 0 步：先量固件底线，这决定了后面值不值得做。

    $ sudo hwlatdetect --duration=30m --threshold=10

    如果这里就报出几百微秒，说明系统最坏值不可能低于这个数，先去改固件设置（关 USB legacy、关温度轮询相关 SMI、关 C-state、关 turbo、关 SMT），改不了就换板子——继续调软件是白费力气。

    第 1 步：换 RT 内核。CONFIG_PREEMPT_RT=y，同时确认 HIGH_RES_TIMERS、NO_HZ_FULL、RCU_NOCB_CPU 开着，LOCKDEP / DEBUG_PREEMPT / KASAN 全部关掉（拿调试内核测性能是经典自伤）。验证：uname -v 里有 PREEMPT_RT、/sys/kernel/realtime 为 1。

    第 2 步：CPU 隔离四件套。这是不改一行代码就能拿到的最大收益。

    isolcpus=nohz,domain,managed_irq,2-7 nohz_full=2-7 rcu_nocbs=2-7 irqaffinity=0-1
intel_pstate=disable processor.max_cstate=1 intel_idle.max_cstate=0
nosmt transparent_hugepage=never nosoftlockup nmi_watchdog=0

    验证不能只看 /proc/cmdline——那只证明你传了参数。要看 /sys/devices/system/cpu/isolated 和 nohz_full 的实际输出，空的就说明参数没被接受。

    第 3 步：中断与内核线程精修。逐列检查 /proc/interrupts，隔离核那几列必须零增长。托管中断改不动（返回 EIO）就靠 managed_irq 标志和 ethtool -L 降队列数。别忘了 /sys/devices/virtual/workqueue/cpumask。

    第 4 步：应用改造。mlockall + 堆栈预热 + mallopt 禁归还 + 绑核 + 优先级规划（80–89，不要 99）+ PI mutex + 无锁环形缓冲替代日志 + LD_BIND_NOW。验证靠 VmLck 与 minflt 停止增长。

    第 5 步：带负载长跑并看分布形状。

    $ stress-ng --hdd 4 --io 4 --vm 4 --vm-bytes 75% --cache 4 --timeout 24h &
$ while true; do hackbench -P -g 20 -l 2000 >/dev/null; done &
$ sudo cyclictest -p 80 -i 1000 -t 4 -a 2-5 -m -h 800 -q -D 24h

    看直方图形状而不只看一个 Max：双峰 → C-state 或频率没锁死；宽平分布 → 隔离没生效；远处孤立样本 → 低频事件，用 cyclictest -b 150 --tracemark 设阈值让它自己抓现场，配合 wakeup_rt tracer 看那一刻是谁在跑。若 ftrace 什么都没抓到，回到第 0 步查固件，或确认这不是虚拟机。

    第 6 步：判定与交付。需求是 100 µs 抖动，实测最坏值应当留出至少 3 倍余量（即 30 µs 量级），少于 3 倍不要上线——硬件批次、环境温度、固件版本都会浮动。报告里必须写清硬件型号、BIOS 版本、完整 /proc/cmdline、负载构成、样本量，并附 hwlatdetect 结果，Overflows 必须为 0。

    第 7 步：进生产监控。设备上长期采集周期偏差直方图并上报，退化时告警。把 hwlatdetect 加进产线检验，把 BIOS 版本与设置快照纳入配置管理——只锁软件版本不锁固件版本，等于只锁了一半。

    贯穿全程的两条纪律：每次只改一类东西并重测（否则你不知道该保留哪几项）；所有数字都要标明「典型量级、强依赖硬件与固件」，换板子或刷 BIOS 之后结论作废，必须重测。
