为什么 mainline Linux 不能硬实时

实时 = 有界，不是快 · 不可抢占段的完整清单 · 最坏延迟的量级对比

1.1 先纠正一个几乎人人都会犯的错：实时不等于快

八成人会答「响应很快的系统」，而这个答案会让后面所有讨论都跑偏。实时性说的是「最坏情况下的响应时间有一个可以证明的上界」，不是「平均响应时间很短」。平均 5 µs、每小时尖峰 40 ms 的系统不合格；稳定 800 µs、从不超过 1 ms 的反而合格。

生活类比：出租车 vs 地铁。市区打车平均 20 分钟到公司，比地铁的 35 分钟快得多——但堵一次车就是 90 分钟，你没法拿它赶 9 点的飞机。地铁慢，可它「最坏也就 40 分钟」。赶飞机选地铁，不是因为它快，而是因为它的最坏情况有界。mainline Linux 是出租车，PREEMPT_RT 是地铁，RTOS 是专线摆渡车。

由此派生出三档分类，需求阶段就必须定死属于哪一档——它决定了后面要花多少钱：

项目失败最常见的根源，是把「固实时」的需求写成「越快越好」，团队一路优化平均值，上线后被长尾打穿。需求文档里该出现的是「周期 1 ms，抖动不超过 ±100 µs，连续 72 小时不得有一次越界」。

① 自旋锁为什么必须关抢占

持锁者若被抢占下去，同核上另一个想拿同一把锁的任务会忙等到天荒地老——自己不下 CPU，持锁者也上不来，直接死锁。所以 spin_lock() 必须先 preempt_disable()。

于是抢占延迟的下界 = 内核里最长的那一段自旋锁临界区。内核有数千把锁，遍布 VFS、内存管理、网络栈与各类驱动，你没法枚举，更没法证明上界。spin_lock_irqsave() 更糟——它连中断一起关。

② 软中断的「就地执行」

软中断默认在 irq_exit() 里借用刚被打断那个任务的时间片跑完，而被打断的可能正是你的实时线程；期间 bottom-half 被禁用、抢占被关闭。它确实有「跑够就交给 ksoftirqd」的退让机制，但退让阈值本身是毫秒量级，对 µs 级需求毫无意义。

③ 内存管理路径：改内核也解决不了

一次普通的写内存可能触发缺页清零、直接回收（当场扫 LRU、回写脏页）、内存规整（搬页且大量持锁）；开了透明大页时一次缺页要清零 2 MB 而不是 4 KB。PREEMPT_RT 不能让缺页变快——这一类只能靠应用侧 mlockall() + 预分配彻底避开，这就是 §4 反复强调它的原因。

④ SMI 最阴险，因为它根本不归操作系统管。x86 上固件可以让 CPU 进入 SMM——优先级高于一切、连 NMI 都被屏蔽、Linux 无法感知也无法拒绝。风扇调速、温度管理、ECC 记录、USB 键盘的传统模拟都可能用它实现。它的可怕之处在于取证困难：ftrace 看到的是「时间凭空跳了 300 µs，中间什么都没发生」，因为所有内核侧工具在 SMM 期间都停摆。判据正是这一点：cyclictest 报出大尖峰、而 ftrace 上找不到任何对应事件——那就是 SMI。检测手段见 §5.3。

02

RT patch 的 5 大核心改动

sleeping spinlock · threaded IRQ · 优先级继承 · 软中断线程化 · hrtimer 与 tickless

PREEMPT_RT 的全部工作可以用一句话概括：把内核里所有「不可抢占的等待」改造成「可调度的等待」。前者是黑箱，无法排优先级、无法观测、无法证明上界；后者会出现在 ps 里，能被抢占，也能被 tracer 记录。

生活类比：把插队改成叫号。原来的内核像一家没有叫号机的诊所，谁先挤到窗口谁先办，急诊只能干等。RT 做的不是让每个人办得更快，而是装了叫号机并给急诊发优先号。总吞吐反而下降了（叫号与切换都要时间），但「急诊最多等多久」第一次成了可以回答的问题。

2.1 二十年 out-of-tree，2024 年终于进主线

它自 2004 年起长期以 out-of-tree 补丁集存在，但内容早已分批渗入主线——hrtimer、线程化中断、rtmutex 与优先级继承、ftrace 系列 latency tracer、nohz_full、printk 重写，这些今天人人都在用的基础设施最初都是为 RT 做的；2024 年最后一块拼图随 6.12 合入，CONFIG_PREEMPT_RT 成为正式的抢占模型选项。意义不在性能（前后延迟几乎没变）而在不必再维护内核 fork，详见 §9.1。

2.2 改造一：sleeping spinlock

这是五项里影响面最大的一项。RT 把绝大多数 spinlock_t 换成基于 rtmutex 的可睡眠锁：拿不到锁的任务进睡眠队列让出 CPU，持锁的任务不再关抢占。

API 完全兼容——驱动源码一个字都不用改，重编译即可。但语义变了，于是产生了一条硬约束：在 RT 下 spin_lock() 是可能睡眠的，所以不能在真正的原子上下文里调用它。

哪些代码必须用 raw_spinlock_t

内核里总有一些地方「不能睡」，否则递归死锁。这些地方保留 raw_spinlock_t，它在 RT 下仍是老语义（忙等 + 关抢占）：

场景用哪个原因
调度器核心（rq->lock）、rtmutex / futex 内部raw_spinlock_t自举问题：rtmutex 的实现要调度器，调度器不能反过来依赖 rtmutex
时钟源与 hrtimer 基座、中断控制器驱动、NMI 路径raw_spinlock_t处在中断进入路径上，是真正的原子上下文
per-CPU 数据的短暂保护local_lock_tRT 下退化为 rtmutex，非 RT 下仅关抢占，语义清晰
普通设备驱动spinlock_t让 RT 有机会把它转成可抢占的锁
驱动作者最常犯的错：为了「更快」或「消掉 RT 下的睡眠告警」，随手把 spinlock_t 改成 raw_spinlock_t。这等于在 RT 内核上人为造一段不可抢占区，把整机最坏延迟拉高，而且不报错、只是偶尔多出几十微秒，极难定位。它的正确用法是「我确实处在无法睡眠的上下文里」，不是「我觉得这里性能敏感」；相应地它的临界区里也绝不能调用任何可能睡眠的函数（CONFIG_DEBUG_ATOMIC_SLEEP 能在开发期抓到大部分违规）。

换来的是：抢占延迟的上界不再取决于「内核里最长的临界区」，而取决于极少数 raw_spinlock 段——数量可枚举、可审计。代价见 §2.7 那张总账表。

「线程化中断把延迟变低了吗？」严格说没有——它把中断的平均处理时延变高了（多了一次唤醒和上下文切换），把系统的最坏调度延迟变低了。换到手的是可控性：中断从不可协商的打断变成可以按优先级排队的对象。能说清这层交换关系，比背下「RT 把中断线程化了」高一个层次。

两点工程细节：并非所有中断都能线程化——驱动可以用 IRQF_NO_THREAD 声明必须留在硬中断上下文（时钟中断、IPI），所以「RT 下没有硬中断了」是错的；默认优先级是一刀切的——一块和你业务无关的网卡与现场总线卡地位相同，不动手规划等于没享受到这项改造的好处。

2.4 改造三：优先级继承（PI）

把自旋锁变成可睡眠的锁，立刻引入一个新问题：优先级反转。

优先级反转（priority inversion）：高优先级任务 H 阻塞在低优先级任务 L 持有的锁上，本应等 L 跑完释放即可；但一个不需要这把锁的中优先级任务 M 抢占了 L 并长期占着 CPU，于是 H 被 M 间接饿死。这叫「无界优先级反转」——因为 M 可以跑任意久。最著名的案例是 1997 年的火星探路者号，着陆后反复看门狗复位，根因正是这个，JPL 最终远程打开 VxWorks 的优先级继承开关才解决。

rtmutex 内建优先级继承：H 阻塞在 L 持有的 rtmutex 上时，内核把 L 的有效优先级临时提升到 H 的水平，L 释放锁后立即恢复。

PI 的代价是真实的：每次加解锁都要维护「谁在等谁」的依赖链并沿链传播优先级，链上任一环节变化都要重算。锁操作因此变重，内核也多了一处复杂状态机（PI 链上的死锁检测、锁的嵌套顺序都要额外考虑）——这正是 mainline 不把 PI 设为普通 mutex 默认行为的原因。用户态对应的是 PTHREAD_PRIO_INHERIT 属性的 pthread mutex，底层走 PI-futex，写法见 §4.6。

2.5 改造四：软中断线程化

光把硬中断线程化还不够——软中断仍会「借用」被打断任务的时间片执行且期间禁抢占。RT 让它也在可调度的上下文中执行：推给 ksoftirqd/N 这样的 per-CPU 内核线程。RCU 处理与定时器软中断也各自有了承载线程（rcuc/N、ktimers/N），都以 SCHED_FIFO 出现在 ps 里，可以被排序、被观测。

这项改造会咬人：软中断线程化之后网络吞吐下降是可预期的。原来收包在软中断里连续处理、cache 全热，现在要经过唤醒、调度、切换。正解是把「实时」和「吞吐」分到不同的 CPU 核上：隔离核跑控制环，非隔离核跑网络与业务，中断亲和把收包全赶过去（配置见 §3、§4）。

2.6 改造五：高精度定时器与 full tickless

实时任务的典型形态是「每 1 ms 醒一次」。定时精度只有 jiffies（CONFIG_HZ=250 时是 4 ms）的话，这件事根本无从谈起。hrtimer 让定时器直接编程到硬件时钟比较器上，精度取决于时钟源而非 tick 频率。

/* ✅ 绝对时间：本轮超时也不会把误差带到下一轮 */
struct timespec next;
clock_gettime(CLOCK_MONOTONIC, &next);
for (;;) {
    next.tv_nsec += 1000000L;                          /* 1 ms 周期 */
    if (next.tv_nsec >= 1000000000L) { next.tv_nsec -= 1000000000L; next.tv_sec++; }
    clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, NULL);
    do_work();
}

/* ❌ 相对睡眠：实际周期 = 1ms + do_work() 耗时 + 唤醒误差，误差逐轮累积 */
for (;;) { nanosleep(&one_ms, NULL); do_work(); }

full tickless（CONFIG_NO_HZ_FULL）解决另一半问题：即使没有定时器到期，内核也会周期性打 tick 做时间记账、调度统计与 RCU 推进——对只跑单个实时线程的隔离核来说，这是每秒上千次纯粹的干扰。

图里那条前提就是「隔离四件套」的由来。另有一条容易漏：系统里至少要留一个非 nohz_full 的核承担时间维护，不能把所有核都写进去。

3.3 完整的 grub 配置示例

以一台 8 核（0–7）工控机为例，核 0–1 做管家核（跑系统服务、中断、日志），核 2–7 留给实时任务。配置与验证要一起看——「以为装了 RT 内核其实 grub 默认项没改」是真实发生过的事故：

3.4 验证的要点：看内核认了什么，不是看你传了什么

/proc/cmdline 里写着 isolcpus=，只能证明「你传了这个参数」，不能证明「内核接受了它」。参数拼错、核号超出实际核数、与其它参数冲突时，内核通常只在 dmesg 里嘀咕一句就继续启动。/sys/devices/system/cpu/isolated 的输出才是唯一可信的证据——它要是空的，后面所有调优都建立在沙子上。

另外两点：isolcpus= 的带标志形式比裸写核号更明确，domain 摘出负载均衡域、managed_irq 让内核托管的多队列中断避开这些核；console=ttyS0 调试期好用，但串口控制台是毫秒级延迟源，稳定后应移除。

系统级 + 应用级调优

固件设置 · 中断亲和 · RT 限流的取舍 · 优先级规划 · mlockall 与栈预热 · PI mutex

装上 RT 内核只是拿到「有可能做到」的资格。没做过应用侧改造的程序，跑在 RT 内核上和普通内核上最坏延迟可能没有区别——它的毛刺来自缺页、日志、动态库符号解析，RT 一条都管不了。本章分两层：先把机器收拾干净，再把程序改对。

4.1 固件层：在 BIOS 里做的事，操作系统补不回来

这一层最容易被软件工程师忽略，却常常是最坏延迟的天花板：SMI 唯一的操作界面就是固件设置界面（机制见 §1.3）。此外还有三个开关直接决定延迟分布的形状：

固件设置项（名称随厂商而异）建议理由与代价
USB Legacy Support / USB 键鼠模拟关典型 SMI 来源，每次轮询都可能陷入 SMM。代价是 BIOS 里不能用 USB 键盘
硬件健康监控 / 风扇调速 / 温度轮询关或调到最低频率周期性 SMI。代价是散热变成固定转速
ECC 错误日志、PCIe AER 的 SMI 上报视安全要求决定真正的取舍：关掉能消除 SMI，也失去硬件故障的早期告警。功能安全项目通常不允许关
C-State / Deep Sleep关到 C1 或 C0与 processor.max_cstate=1 呼应，固件层关更彻底
Turbo Boost / SpeedStep关频率固定后 WCET 才可估。代价是峰值算力下降两三成
Hyper-Threading / SMT关兄弟线程争抢 L1D 与执行端口。代价是逻辑核减半

4.2 运行时：sysctl 与 RT 限流的取舍

先是一组没有争议的 sysctl：vm.swappiness=0，压低 vm.dirty_ratio=5 / dirty_background_ratio=2 避免突然的大批量回写，vm.overcommit_memory=2 让分配失败发生在启动期，vm.stat_interval=120，kernel.numa_balancing=0，kernel.timer_migration=0。真正需要做判断的只有下面这一项。

sched_rt_runtime_us：设不设成 -1，是一道判断题

内核默认给实时任务设了限流：每 sched_rt_period_us（默认 1 秒）里最多占用 sched_rt_runtime_us（默认 95%），剩下 5% 强制留给普通任务。它的存在理由是防呆——一个写错的 SCHED_FIFO 死循环会让你连 SSH 都登不上去。

设置好处风险适用
保持 950000（默认）失控的 RT 任务不会锁死整机，还能登进去救正常任务也可能被限流，制造出周期性的数十毫秒停顿开发阶段、非隔离核
设为 -1（关闭限流）RT 任务不会被无故打断一个死循环 = 整核不可用；在管家核上就是整机失联生产 + 已隔离 + 代码经过评审
用 SCHED_DEADLINE 替代内核做准入控制，天然有带宽约束需要给出可靠的 WCET周期行为明确的控制任务
决定关掉限流的话，两个前提必须同时满足：① RT 线程被 isolcpus 钉在隔离核上，且至少留一个非隔离核可供登录；② 有独立看门狗（硬件的，或另一个核上的监控进程）能在 RT 线程失控时复位。只关限流不做这两件事，等于把「偶尔卡 40 ms」换成「偶尔整机死机」——后者在现场更难交代。

4.3 中断亲和：把噪声赶到管家核

irqaffinity= 只影响启动时的默认掩码，运行期新注册的设备与多队列设备的托管中断都要单独处理。上线前四个动作：cat /proc/interrupts 找出隔离核那几列里计数还在涨的行；对可改的逐个写 echo 0-1 > /proc/irq/<N>/smp_affinity_list；ethtool -L eth0 combined 2 把队列数降到管家核的数量，从源头减少中断；用不上的设备直接关掉。

批量改亲和时有一部分会写入失败并返回 EIO——那不是脚本写错了，而是「这是内核托管中断」的明确信号。多队列网卡与 NVMe 的中断由内核按队列数自动分配，既不理会 irqaffinity=，也拒绝手工修改，只能靠 isolcpus=managed_irq 或减少队列数。很多脚本写着 2>/dev/null，正好把这条最重要的线索吞掉——§6 陷阱 9 与 §8 案例二都栽在这里。
还有一类容易漏掉的「中断」：内核线程。kworker、kcompactd、khugepaged、writeback 都可能跑到隔离核上。isolcpus 挡得住大部分，echo 3 > /sys/devices/virtual/workqueue/cpumask 能把未绑定工作队列也关到管家核。上线前用 ps -eo psr,comm --sort psr 数一遍。

4.4 应用级（一）：优先级规划

先看清自己站在哪一层。Linux 的调度类严格分层：上面一层还有可运行任务，下面一层就一点 CPU 都拿不到。

SCHED_FIFO 的优先级是 1–99，数字越大越优先。很多人第一反应是「我的任务最重要，设 99」——这是新手最典型的一刀，而且伤的是自己。

为什么不能设 99：最高那一档留给迁移线程、停机线程这类「必须能跑起来、否则系统失去自愈能力」的实体。业务线程占了 99 又写出一个偶发死循环，结果是连负责检测「有任务卡死」的机制都抢不到 CPU——机器彻底失去响应，日志里什么都留不下。正确做法是给自己留出「上有内核、下有辅助」的中间区间。

一个可以直接套用的分层规划（具体数值按你系统里实际的内核线程优先级校准，先用 ps -eo cls,rtprio,comm | sort -k2 -n 摸清现状）：

优先级区间放什么说明
99不要碰留给迁移线程、停机线程等内核自身机制
90–98喂狗线程、安全监控必须比业务高，否则业务卡死时它也喂不了狗
80–89最紧的控制环（电流环、力控内环）周期最短、超时后果最严重的那一个
70–79驱动它的关键中断线程比它服务的控制环高还是低，取决于数据流方向
60–69次级控制环（位置环、轨迹规划）周期更长，可被内环抢占
40–59其余中断线程（默认档）保持默认或按重要性微调
10–39实时数据搬运、状态机、通信有时限但不致命
SCHED_OTHER日志、诊断、HMI、网络服务不要给它们任何 RT 优先级

什么时候改用 SCHED_DEADLINE

SCHED_FIFO 回答得了「谁比谁重要」，回答不了「系统整体扛不扛得住」——后者要靠 SCHED_DEADLINE 的三元组与准入控制：

/* SCHED_DEADLINE：声明「每 1 ms 需要 200 µs，必须在 800 µs 内完成」 */
#include <linux/sched.h>
#include <sys/syscall.h>

struct sched_attr attr = {0};
attr.size            = sizeof(attr);
attr.sched_policy    = SCHED_DEADLINE;
attr.sched_runtime   =  200000;   /* ns：WCET 估计，宁可略大  */
attr.sched_deadline  =  800000;   /* ns：相对截止时间        */
attr.sched_period    = 1000000;   /* ns：周期 1 ms           */

if (syscall(SYS_sched_setattr, 0, &attr, 0) != 0)
    perror("sched_setattr");   /* EBUSY = 准入控制拒绝：系统带宽不够 */
SCHED_FIFOSCHED_DEADLINE
表达能力相对优先级绝对时间约束
过载时低优先级任务被饿死，无人告知准入阶段返回 EBUSY，问题前移到部署期
任务超支可以一直跑，拖垮别人限流到下个周期，天然隔离
前置条件只需排出优先级序必须有可靠的 WCET：估小了被限流，估大了挤掉别人
适合优先级关系清楚的通用实时任务行为可测的严格周期任务

4.5 应用级（二）：内存——mlockall 与栈预热

这是应用侧投入产出比最高的一项。缺页专挑「第一次走到的代码路径」发作——实验室跑一万圈没事的程序，上线遇到第一个异常分支就会打穿：

/* 实时进程的标准启动序列：锁 → 禁归还 → 预热 → 绑核 → 最后才提优先级 */
int rt_setup(int cpu, int prio)
{
    /* ① 锁住现在(MCL_CURRENT)与将来(MCL_FUTURE)的所有映射。
          ★ 失败必须当致命错误 —— 没锁住内存的实时进程还不如不启动。
          最常见的失败是 RLIMIT_MEMLOCK 太小（默认可能只有 64 KB）：
          limits.conf 里给 memlock unlimited；systemd 不走 PAM，
          要在 unit 里写 LimitMEMLOCK=infinity。                   */
    if (mlockall(MCL_CURRENT | MCL_FUTURE) != 0) { perror("mlockall"); return -1; }

    /* ② 别把内存还给内核、别用 mmap 走新映射，
          否则「归还 → 再申请」会重新缺页，等于白锁 */
    mallopt(M_TRIM_THRESHOLD, -1);
    mallopt(M_MMAP_MAX, 0);

    /* ③ 预热堆：只 malloc 不写不会落页，必须 memset 之后再 free */
    void *p = malloc(HEAP_PREFAULT); memset(p, 0, HEAP_PREFAULT); free(p);

    /* ④ 预触碰栈：volatile 防止这段「无可见副作用」的写入被优化掉。
          深度按 -fstack-usage 实测的最大栈帧和乘 2；盲目设 8 MB
          既浪费也不能证明够用。每个实时线程入口都要做一次 ——
          MCL_FUTURE 保证新栈被锁，但「锁住」不等于「已建立映射」。 */
    { volatile char buf[STACK_PREFAULT]; memset((void *)buf, 0, sizeof buf); }

    /* ⑤ 绑到隔离核，否则前面 isolcpus 白配 */
    cpu_set_t set; CPU_ZERO(&set); CPU_SET(cpu, &set);
    pthread_setaffinity_np(pthread_self(), sizeof set, &set);

    /* ⑥ 最后才提优先级：前面几步万一卡住，还不至于以 RT 优先级卡住 */
    struct sched_param sp = { .sched_priority = prio };
    if (sched_setscheduler(0, SCHED_FIFO, &sp) != 0) {
        perror("sched_setscheduler");  /* EPERM：查 RLIMIT_RTPRIO / CAP_SYS_NICE */
        return -1;
    }
    return 0;
}
验证不要只看返回值。grep -E 'VmLck|VmRSS' /proc/<pid>/status 两者应当同量级，VmLck 为 0 说明压根没锁上；再看 /proc/<pid>/stat 的 minflt / majflt，稳态后这两个计数必须完全不再增长。这个判据比盯 cyclictest 直观得多。

4.6 应用级（三）：PI mutex 与线程间同步

只要实时线程与非实时线程共享一把锁，优先级反转就必然发生，区别只是多久一次。所有跨优先级共享的 mutex 都必须启用优先级继承。

/* 跨优先级共享的 mutex —— 唯一正确的初始化写法 */
pthread_mutexattr_t mattr;
pthread_mutexattr_init(&mattr);
pthread_mutexattr_setprotocol(&mattr, PTHREAD_PRIO_INHERIT);   /* 走 PI-futex */
pthread_mutexattr_setrobust(&mattr, PTHREAD_MUTEX_ROBUST);     /* 持锁者猝死不永久死锁 */
pthread_mutex_init(&lock, &mattr);
pthread_mutexattr_destroy(&mattr);

/* 开了 ROBUST 就必须处理 EOWNERDEAD，否则等于没开 */
int rc = pthread_mutex_lock(&lock);
if (rc == EOWNERDEAD) {
    repair_shared_state();              /* 共享数据可能停在一致性中途 */
    pthread_mutex_consistent(&lock);    /* 修好之后才声明它重新可用 */
}
/* ... 临界区尽可能短 ... */
pthread_mutex_unlock(&lock);

另一个方案是优先级天花板（PTHREAD_PRIO_PROTECT）：拿到锁就无条件提升到预设上限，不用维护等待链，开销更小更可预测；代价是必须静态分析出「所有可能用这把锁的线程里最高的优先级」，有人加了个更高优先级的线程忘了改天花板，保护就失效了。动态系统用 PI，静态可分析的系统可以考虑 PROTECT。

更好的做法是根本不共享锁。实时与非实时线程之间优先用无锁 SPSC 环形缓冲交换数据：实时侧只做「写指针推进」一个原子操作，最坏耗时是常数，连 PI 都不需要。日志、遥测、状态上报几乎全可以这样解耦。

4.7 实时线程里绝对不能做的事

禁止项为什么替代做法
任何文件 I/O（fopen/fwrite/fsync）可能触发块层、回写、缺页写进无锁环形缓冲，非实时线程落盘
printf / std::cout / 同步日志格式化要 malloc，写终端走 tty 层甚至串口二进制记录 + 异步日志后端

4.8 启动方式：把上面这些串起来

临时验证一行就够：sudo chrt -f 80 taskset -c 2 numactl --membind=0 ./motion_control。生产上写进 systemd unit，把 CPUAffinity=2 3、LimitMEMLOCK=infinity、LimitRTPRIO=95、Environment=LD_BIND_NOW=1 MALLOC_ARENA_MAX=1、OOMScoreAdjust=-1000 全部写死，避免有人手抖漏掉一项。

一个把人坑惨的组合：容器 + RT。把实时进程塞进 Docker/Kubernetes 之后，即使宿主机是 RT 内核、参数全对，仍会周期性卡住几十毫秒。根因是 cgroup 的 CPU 带宽控制（cpu.max）——它和 RT 限流是两套独立机制，症状很像但根因不同。判据：cpu.stat 里的 nr_throttled 是否在涨。处方是彻底去掉 CPU limit、改用 cpuset 独占核，unit 里也不要写 CPUQuota=。能不容器化就不容器化。

延迟测量

cyclictest 参数与判读 · 为什么必须加负载 · hwlatdetect 抓 SMI · ftrace 定位来源

调优的每一步都必须有数字支撑。这一章讲怎么产生可信的数字，以及同样重要的怎么识别不可信的数字——行业里绝大多数「PREEMPT_RT 达标报告」都栽在后者。

先立一条铁律：实时场景里只有 Max 有意义，Avg 没有意义。Avg 从 5 µs 优化到 3 µs 对系统行为没有任何影响；Max 从 300 µs 降到 80 µs 才是把不能用变成能用。更要命的是这两个指标经常反向变动——更激进的批处理、更大的缓存会降低均值同时抬高长尾。验收报告首列写平均延迟的，应当被退回。

5.1 cyclictest：参数逐个说清

cyclictest 属于 rt-tests 包，原理很简单：起若干个 SCHED_FIFO 线程，用 clock_nanosleep(TIMER_ABSTIME) 定时唤醒，测量「计划唤醒时刻」与「实际拿到 CPU 的时刻」之差——这个差值就是系统给实时任务的调度延迟。

参数含义怎么选
-p 80测量线程的 SCHED_FIFO 优先级设成与真实业务线程相同的值；设 99 测出来好看但没有参考价值
-i 1000唤醒周期（µs）设成你真实的控制周期
-t 4 / -a 2-5线程数 / 把线程钉在指定核上必须指定为你的隔离核，否则测的是管家核
-m测量进程自身锁内存始终加上，否则测的是 cyclictest 自己的缺页
-h 400输出直方图，上限 400 µs上限要略高于预期 Max，超出的样本只进 overflow 计数
-D 24h / -q运行时长 / 只在结束时输出时长见下文；不加 -q 时刷屏本身就是负载
-M只在刷新最大值时更新显示交互观察时能看出尖峰何时出现
--secaligned把所有线程的唤醒对齐到整秒制造「多个实时线程同时醒来」的最坏情形，比默认更严格

5.2 两个决定报告是否可信的前提

前提一：必须跑够长

实时性问题的本质是右尾事件。跑 10 分钟测不到「每 6 小时一次」的事件，这是常识，但实践中被违反的频率高得惊人。

时长1 kHz 下的样本量能捕捉到的最低事件频率适用
5 分钟30 万分钟级改一个参数后的快速回归，不可作为结论
1 小时360 万十分钟级调优迭代中的中间验证
24 小时8640 万小时级（日志轮转、定时任务、温度循环）发布前的最低要求
72 小时 ~ 一周2.6 亿 ~ 6 亿天级安全相关产品的验收

小时级那一行的名字都很具体：logrotate、updatedb、证书刷新、碎片积累到触发规整、机房空调周期导致的温度波动——全是「白天测不出来，凌晨三点炸一次」的角色。

前提二：必须加负载

空机跑出来的数字只能证明「这台机器无事可做时表现良好」，而这从来不是你要回答的问题。最坏延迟来自「某段内核代码正好在跑」；空机时文件系统、网络栈、分配器都不动，那些最长的临界区根本没机会被执行到。于是你得到一个漂亮的两位数，上线后变成三位数——这是这一行最常见的翻车方式。

负载要覆盖真实场景会用到的所有内核子系统，缺一类就漏一类临界区：调度与进程用 hackbench -P -g 20 -l 2000 反复跑，文件系统与块层用 stress-ng --hdd 4 --io 4，内存用 --vm 4 --vm-bytes 75% --vm-method all，缓存争抢用 --cache 4 --cache-level 3（最容易被忘的一条），网络中断从另一台机器 iperf3 -P 8 打流。最理想的负载是你自己的业务——真实应用跑起来，cyclictest 作旁路观察者。

负载应该跑在哪些核上？答案是非隔离核——那才是真实部署的样子。但也别走极端：负载必须真实地争抢共享资源（末级缓存、内存带宽、内核锁），把它关在另一个 NUMA 节点上同样会得出偏乐观的结论。能说出「空机测试没有意义」只是及格线，能讨论「负载放哪、争抢什么」才说明真做过。

5.3 hwlatdetect / rtla hwlat：抓操作系统看不见的那一层

检测思路很巧妙：关中断，在紧循环里反复读高精度时钟，看时间有没有「跳过去」一段。中断已关，任何时间空洞就只能是「CPU 被劫持去做了 OS 不知道的事」。命令两条：hwlatdetect --duration=30m --threshold=15，或较新内核上能按 CPU 分列的 rtla hwlat top -d 30m -T 15；要看的只有 Max Latency 那一行。

定性只有两种：① Max Latency 明显大于 0（几十微秒）→ 存在固件级延迟，系统最坏值不可能低于这个数，先改固件，改软件是白费力气；② 为 0 或个位数 → 固件层干净，继续用 ftrace 追。注意 hwlatdetect 运行期间会长时间关中断并占满一个核，不要在生产系统上跑。

5.4 rtla 的另外两把刀：timerlat 与 osnoise

知道「有 200 µs 的尖峰」不够，要知道「那 200 µs 里 CPU 在干什么」。ftrace 的几个 latency tracer 就是为此而生，它们的共同机制是：持续测量某类延迟，只保留历史最大值那一次的完整轨迹。

5.6 rteval：把上面这些打包成一次标准化压测

sudo rteval --duration=12h 自动起一组标准负载并同时跑 cyclictest，产出含 CPU 型号、NUMA 拓扑、内核版本、完整 /proc/cmdline、负载配置与每核直方图的报告。它的价值不是「测得更准」，而是可重复、可归档、可跨机器比较——应当作为每次内核升级、BIOS 升级、每批新硬件的准入门槛存档，出问题时能立刻回答「上一版是多少」。

5.7 一份合格的延迟报告长什么样

验收清单

  • 硬件型号、BIOS 版本、内核版本、完整 /proc/cmdline——缺任何一项都不可复现。
  • 负载构成与它跑在哪些核上；测量时长与样本量，至少 24 小时。
  • 首要指标是 Max，附完整直方图，Overflows 必须为 0。
  • 与需求的余量：「需求 1 ms，实测最坏 61 µs，余量约 16 倍」，少于 3 倍不应上线。
  • hwlatdetect 的结果，证明固件层已排查；有异常样本则附 ftrace 现场。

10 个调优陷阱

每条按「现象 → 原因 → 处方」写，都是现场真出过的问题

按出现频率排序，不是按技术难度——前两条占了实际遇到的问题的一半以上。

陷阱 1 · 空机测试数字漂亮，上线就崩

现象

实验室 Max 28 µs，验收报告漂漂亮亮。到现场接上真实工况，控制环每隔几分钟丢一帧，实测最坏 900 µs。

原因

测试时机器什么都没干，最长的那些临界区（ext4 日志提交、协议栈收包、内存回收）根本没被执行到。你测的是「这机器闲着时有多安静」。

处方：所有延迟测量必须带负载，且负载要覆盖真实场景用到的子系统（组合见 §5.2）。

陷阱 2 · 忘了 mlockall，被缺页打穿

现象

绝大多数周期正常，但每隔十几分钟出现一次 2~30 ms 的超时，没有规律；重启后前几分钟特别频繁，之后变稀疏。

原因

缺页。「重启后频繁、之后变稀疏」就是它的指纹——常走的路径逐渐被访问过一遍，剩下的都是冷路径：异常分支、罕见配置组合、第一次收到某种报文。

处方：mlockall + 堆栈预热 + 关闭分配器归还（见 §4.5）。关键是验证而不是相信——grep -E 'VmRSS|VmLck' /proc/<pid>/status 两者应当同量级，再隔一分钟取一次 /proc/<pid>/stat 的 minflt，稳态下它必须完全停止增长。

陷阱 3 · 优先级设成 99，把内核线程压死了

现象

把业务线程从 80 提到 99「以求更稳」，结果整机偶尔失去响应、网络断连、串口不出日志，只能断电重启，事后什么现场都没留下。

原因

RT 内核里有一批 SCHED_FIFO 的关键内核线程。业务占了最高档又出现哪怕短暂的忙循环，连负责「检测卡死并留下现场」的机制都被一起压死，所以事后一片空白。

处方：按 §4.4 的分层规划留出上下空间，动手前先用 ps -eo cls,rtprio,comm --sort=-rtprio 摸清这台机器上现有内核线程的分布（migration/* 通常就在 99），不要照抄任何一份数字。

陷阱 4 · RT throttling 被触发而不自知

现象

延迟分布非常怪：绝大部分正常，但每秒稳定出现一次 30~50 ms 的巨型停顿，周期得像时钟一样准。

原因

sched_rt_runtime_us 限流：内核默认每秒只给实时任务 0.95 秒，剩下 50 ms 强行留给普通任务。「每秒一次、幅度接近 50 ms」就是这个机制的签名，RT 线程 CPU 占用逼近 95% 时触发。

处方：dmesg | grep -i 'RT throttling' 能拿到那句 sched: RT throttling activated——注意它只打印一次，很容易被日志淹没。确认后两条路：降低 RT 线程的 CPU 占用，或 echo -1 > /proc/sys/kernel/sched_rt_runtime_us（前提见 §4.2）。

补一句：触发限流通常说明设计本身有问题——健康的实时任务不该长期占满一个核的 95%，那意味着几乎没有余量应对波动。关限流是止痛药，不是解药。

陷阱 5 · 在实时线程里写日志

现象

平时一切正常，一旦进入故障处理分支（那里有几行 printf 打印诊断信息），延迟直接飙到几十毫秒。故障本身没造成损失，诊断代码造成了损失。

原因

三重代价叠加：格式化要 malloc、写文件走块层与页缓存、控制台是串口时 115200 下每 80 字符就要 7 ms 且同步。std::cout 还额外争抢流的内部锁。

处方：实时线程只往 §4.6 那种无锁环形缓冲里塞一条定长二进制记录（时间戳 + 事件号 + 两个整型参数），格式化与落盘交给管家核上的 SCHED_OTHER 线程（内存序见 C++ 内存模型）。

缓冲满了要直接丢并计数，这个选择必须在评审时主动讲：宁可丢日志，也不能让日志阻塞控制环。丢弃计数作为指标上报，涨了说明日志带宽不够，那是可以慢慢优化的问题；而控制环卡一次可能就是设备撞机。

陷阱 6 · 动态库首次调用的符号解析

现象

程序运行数小时后某一帧突然超时几百微秒，之后同样的代码路径再也不超时。极难复现，因为它每个进程生命周期里只发生一次。

原因

惰性绑定：动态库函数的地址在第一次调用时才由链接器解析，要走 PLT 桩、查符号哈希表、可能触发缺页。冷门函数（错误处理、罕见配置分支）的第一次调用可能在运行几小时之后。

处方：三层防御见 §4.7。核心是 LD_BIND_NOW=1 或链接时 -Wl,-z,now，并用 readelf -d 验证标记确实写进了 ELF。

陷阱 7 · CPU 频率调节与 C-state 唤醒延迟

现象

直方图明显双峰：一堆样本在 5 µs，另一堆在 40 µs；而且负载越轻第二个峰越高——「越闲越慢」的反直觉现象。

原因

机制见 §4.1 那张图：空闲时进深度 C-state，唤醒要重新上电、恢复缓存、重锁 PLL，这个退出延迟就是第二个峰；负载轻 → 进深睡的机会多 → 峰更高。

处方：按 §3.2、§4.1 关掉 C-state 与 turbo，再用 turbostat --interval 5 看隔离核那几行的 C6% 是否为 0；不为 0 就回去检查 intel_idle 是否真被禁用，必要时逐个写 /sys/devices/system/cpu/cpuN/cpuidle/state*/disable。

不要无脑上 idle=poll（原因见 §3.2）。正确顺序是先关深度 C-state 看效果，仍不够再考虑它，并同时盯 turbostat 的 PkgTmp 与 Bzy_MHz 确认没有热降频。

陷阱 8 · 跨 NUMA 访存

现象

双路服务器上，同一个程序每次启动后的表现不一样：有时 Max 60 µs，有时 180 µs，代码和配置完全没变。

原因

内存分配在一个 NUMA 节点，线程却被调度到另一个节点的核。远端访存要走处理器互联，单次延迟高出可观比例且更易被其它流量干扰；启动时落在哪个节点是随机的，所以「每次不一样」。numa_balancing 还会在运行期搬页。

处方：CPU 与内存一起钉在同一节点——numactl --hardware 先看清 node distances（远端代价常在本地的两倍上下），再用 numactl --cpunodebind=0 --membind=0 启动，并关掉会在运行期搬页的 numa_balancing。验证看 numastat -p <pid> 的 Private 是否全落在一个节点上。

隔离核的选择也要看拓扑。把实时任务放在与网卡同一节点的核上能减少 DMA 的跨节点流量，cat /sys/class/net/eth0/device/numa_node 可以查网卡属于哪个节点。完整背景见 NUMA 与内存进阶。

陷阱 9 · 网卡中断打在隔离核上

现象

隔离四件套全配了，但一有网络流量隔离核上就出现几十微秒的尖峰，/proc/interrupts 里那个核的计数在涨。

原因

多队列网卡与 NVMe 的中断是内核托管的，写 smp_affinity 会返回 EIO，irqaffinity= 也管不着（机制见 §4.3）。很多人写了批量脚本、看到一堆报错以为是脚本问题就忽略了。

处方：三件事一起做——启动参数加 managed_irq 标志让内核分配托管中断时避开这些核；ethtool -L eth0 combined 2 从源头让内核没地方放；逐列读 /proc/interrupts 确认零增长。别忘了未绑定工作队列也不受 irqaffinity 管。

陷阱 10 · 在虚拟机里追求硬实时

现象

虚拟机里装了 RT 内核、参数照抄，大部分时间还不错，但会出现毫秒甚至几十毫秒的尖峰，且 guest 内所有追踪工具都查不到原因——ftrace 一片空白，和 SMI 一模一样。

原因

vCPU 只是宿主上的一个普通线程，宿主调度器可以在任意时刻把它换下去，而guest 内核对此完全无感，从它的视角看就是「时间跳了一段」。只要宿主存在任何形式的超卖或共享，guest 里的实时保证都是幻觉。

处方：先量化被偷走了多少时间。vmstat 1 最后一列 st 就是 steal——只要非 0，宿主就在抢你的 vCPU；head -1 /proc/stat 第 8 个字段是累计值。

结论要说得干脆：通用虚拟化环境下做不了硬实时。非要跑就只能降级成「尽力而为的固实时」，且宿主侧五条要全部满足：vCPU 一对一独占绑定物理核且那些核在宿主上也隔离、宿主完全不超卖且内存用大页预分配锁定、宿主自己也是 RT 内核、关掉内存气球与页合并与动态迁移、I/O 走 SR-IOV 直通。满足之后延迟仍比裸机差一档——更诚实的判断是：真有硬实时需求就用裸机或专用 MCU，把虚拟化留给非实时部分。

PREEMPT_RT vs Xenomai vs RTOS

三类架构的根本差异 · 一张选型对比表 · 那个绕不开的核心取舍

选型讨论最容易跑偏的地方，是所有人都盯着「谁的延迟数字更小」。延迟只是五六个维度里的一个，往往还不是决定性的那个——真正决定成败的常是「有没有现成驱动」「招不招得到人」「能不能过功能安全认证」。

差别可以归结成一句话：实时代码运行在谁的调度器之下。

7.3 一个实用的决策顺序

按这个顺序问，通常三步内就能定

  1. 超时一次的后果是什么？会伤人毁设备 → 进功能安全流程，Linux 顶多做非安全域。只是掉一帧数据，往下问。
  2. 需要多低的最坏延迟？毫秒级 → mainline 调优就够，别上 RT 白白损失吞吐；几百到几十微秒 → PREEMPT_RT 的主场；个位数微秒 → Linux 这条路基本到头，考虑双内核、专用 MCU 或下沉到硬件。
  3. 需要 Linux 生态吗？要 ROS 2、容器、视觉库 → PREEMPT_RT 几乎是唯一合理选择。
  4. 团队会什么？这条比前三条加起来还现实——纯 Linux 团队硬上双内核，周期翻倍且交付后没人敢维护。
  5. 能不能拆？最常被忽略的一招：把 µs 级的那一小块下沉到独立 MCU 或运动控制卡，主控用 PREEMPT_RT 跑逻辑与通信。
不要试图用一个系统满足所有延迟等级。工业界的主流架构是「电流环在驱动器 MCU 上（10 kHz+）→ 关节控制在实时主控上（1 kHz，PREEMPT_RT）→ 规划与感知在应用核上（10~100 Hz，普通 Linux）」，各层用确定性总线（EtherCAT、CAN FD、TSN）连起来。参考 实时控制协议 与 TSN 深入。

真实生产案例

三个案例，每个都写清现象、定位过程、根因、处方与最终数字

下面三个案例是把多个项目里反复出现的同类问题提炼后重述的，数字为典型量级、依赖具体硬件与固件，不是可复现的基准。有价值的是定位过程：遇到同类现象时该按什么顺序出招。

案例一 · 运动控制的周期抖动：全栈调优的完整账本

背景：六轴工业机械臂的主控，1 kHz 位置环，通过 EtherCAT 下发指令，需求是「每个周期的指令必须在周期开始后 200 µs 内发出」。样机用普通 Ubuntu，现场调试时末端有肉眼可见的规律性抖动，且负载越重越明显。

定位过程

第一步不是改配置，而是确认问题确实在调度层：给每个周期打时间戳统计「实际唤醒 − 计划唤醒」，同时并行跑 cyclictest 交叉验证。两边的最坏值都在 12 ms 量级（P50 只有 6 µs），说明不是应用代码慢，是系统不让它跑。之后按「内核 → 隔离 → 应用 → 固件 → 中断」逐层推进，每层只改一类东西并重测 4 小时。

逐阶段的账本

阶段动作cyclictest Max本阶段贡献
基线普通内核，无任何调优约 12 ms—
① 换 RT 内核CONFIG_PREEMPT_RT，其它不动约 900 µs去掉不可抢占段这个大头
② CPU 隔离四件套isolcpus/nohz_full/rcu_nocbs/irqaffinity约 260 µs第二大收益，挡住「别人过来」
③ 应用改造mlockall + 堆栈预热 + 异步日志 + LD_BIND_NOW约 130 µs消掉所有 ms 级孤立尖峰
④ 固件设置关 C-state / turbo / SMT / USB legacy约 70 µs把双峰压成单峰
⑤ 中断精修降队列数、managed_irq、限工作队列 cpumask约 55 µs收尾，边际收益递减

结论与经验

  • 换 RT 内核只解决了大约一半的问题（12 ms → 900 µs），剩下一半在隔离、应用、固件三处。「装了 RT 就完事」是最常见的误解。
  • 隔离四件套的收益仅次于换内核，而它不需要改一行代码，是投入产出比最高的一步。
  • 应用改造消灭的是「孤立大尖峰」，不是「整体水位」。第 ③ 步之后直方图远端那几个孤零零的样本消失了，主峰位置几乎没动。
  • 最终 55 µs 对 200 µs 的需求余量约 3.6 倍——这是可接受的下限；只有 1.5 倍的话，任何一次硬件批次变化都可能让产品在现场翻车。

案例二 · 力控回路被网卡中断打断

背景：协作机器人的力控内环，跑在已做过完整 RT 调优的平台上，平时最坏 60 µs。但上位机一开始拉取点云（千兆大流量），力控环就周期性出现 300~500 µs 超时，表现为接触工件时「顿一下」。停掉点云传输，问题立刻消失。

定位过程

现象强烈指向网络中断，但「已经配了 irqaffinity=0-1」让人困惑。定位分三步：/proc/interrupts 证实网卡第 5 个队列的中断确实打在力控环所在的核 4 上；手工改它的亲和时写入失败返回 Input/output error——这才是关键线索；rtla osnoise top -c 4 量化出单次最大噪声 4.1 ms，IRQ 列占绝对大头。

根因

网卡开了 6 个收发队列，这些是内核托管中断（机制见 §4.3）。运维写的批量绑核脚本对它们全部报错，但脚本里写着 2>/dev/null，把这条最重要的线索吞掉了。

处方与结果

三件事一起做：ethtool -L eth0 combined 2 把队列降到管家核的数量、启动参数补上 managed_irq、顺手把未绑定工作队列也关到管家核。

处理前处理后
力控环最坏延迟（点云传输中）约 480 µs约 65 µs
力控环最坏延迟（空闲时）约 60 µs约 58 µs
点云吞吐约 940 Mbps约 910 Mbps

最后一行是重点：队列数从 6 降到 2，吞吐只掉了约 3%。多队列带来的吞吐收益在千兆量级上早已饱和，而它带来的中断分散是实时性的直接杀手——在实时系统上，「默认的性能优化配置」经常正是需要被关掉的东西。

案例三 · 实验室达标、现场不达标的固件问题

背景：同一个软件镜像、同一份内核配置。实验室三台样机跑 72 小时最坏 52 µs，全部达标。批量部署到现场的三十台里，十一台在运行几小时后出现 200~400 µs 尖峰，另外十九台完全正常。软件完全一致，硬件型号也标称一致。

定位过程

「同样的软件，部分机器有问题」几乎可以直接排除软件因素。拿证据分三步：cyclictest -b 200 --tracemark 在故障机上抓现场，结果是除了那条阈值标记，时间线上什么都没有；hwlatdetect --threshold=10 在故障机上报出 Max Latency: 318us，同型号正常机全部低于阈值；dmidecode -s bios-version 一比，两批机器的固件版本不一样。

根因

两批机器出厂相差半年，预装的固件版本不同。较早那一版的温度监控逻辑有缺陷，机箱温度越过某个阈值后会显著提高 SMI 触发频率——这一条解释了全部四个现象：实验室有空调所以测不出来；机器要跑热才越过阈值，所以是「运行几小时后」；现场机柜位置导致散热差异，所以只有一部分机器；SMM 期间内核停摆，所以 ftrace 一片空白。

处方与后续动作

动作结果
统一刷新固件，并按低延迟预设配置（关 USB legacy、C-state、turbo）hwlatdetect 降到阈值以下，端到端最坏值回到 60 µs 量级
把 hwlatdetect 加入出厂检验，不通过不发货后续批次零复发

三个案例的共同教训

可以直接带走的几条

  1. 「ftrace 抓不到」本身就是一条强证据，不是排查失败——它把嫌疑范围缩到固件与虚拟化两类。
  2. 只锁软件版本而不锁固件版本，等于只锁了一半。案例三那张表里的四个后续动作都值得抄。
  3. 每次只改一类东西，改完重测。案例一那张账本之所以有价值，正因为每一行都是独立测出来的；一次改十项然后发现变好了，你并不知道该保留哪几项。
  4. 延迟指标要进生产监控，余量要留够。硬件批次、环境温度、固件版本都会浮动，余量少于 3 倍在批量部署时几乎必然出事。

新子系统合入后 RT 维护者再去适配设计阶段就要考虑 RT 约束
发行版只有少数提供 RT 变体提供 RT 内核的门槛显著降低

对产品团队最直接的收益是长期维护成本：车载或工业产品的生命周期常常是 8~15 年，期间要持续接安全补丁，以前意味着养一个能维护内核 fork 的团队，现在跟随上游 LTS 即可——这一点对「能不能立项」的影响，比延迟少几微秒大得多。

保守地补一句：「主线支持」和「你的板子开箱即用」之间仍有距离。各架构成熟度不同，SoC 厂商的 BSP 驱动是否遵守 RT 约束更是逐个不同。实际项目里最常见的仍是「主线 RT + 厂商 BSP 补丁」，而 BSP 驱动往往要花时间修 raw_spinlock 误用、原子上下文睡眠这类问题——把这部分工作量算进项目计划。

9.2 与 SCHED_DEADLINE 的关系

两者互补而不是替代：PREEMPT_RT 解决「内核会不会挡着我」，SCHED_DEADLINE 解决「多个实时任务之间怎么分配才不会互相饿死」。缺后者，没人回答得了「三个周期任务加起来这个核扛不扛得住」；缺前者，带宽算得再对，内核仍会用一段自旋锁临界区让你错过截止时间。

实践中仍是 SCHED_FIFO 占绝对多数，障碍在于 DEADLINE 要求可靠的 WCET——而对跑在带 cache、带分支预测、带 DVFS 的现代 SoC 上的代码，WCET 本身就是难题。能给出可信 WCET 的场景（固定控制律、无动态分支的信号处理）用它收益明显，否则 FIFO 加充足余量更实际。

9.3 eBPF 与实时观测

eBPF 给实时系统带来的价值是长期在线的、低开销的延迟观测：一行 bpftrace 挂在 sched_wakeup 与 sched_switch 上，就能持续采集实时任务的运行队列等待时间直方图——看的仍然是最右边那几个桶。

但 eBPF 有一条必须守的纪律：探针本身也是代码，也会在你的隔离核上执行。复杂程序、大量 map 更新、map 的内存分配都可能引入额外延迟。挂长期探针之前先测「挂上之后最坏延迟变化了多少」，并把这个开销计入余量——观测不该成为新的噪声源，道理和「不要在实时线程里写日志」是同一个。

分层自测 · 基础 / 中级 / 高级各 4 道

11.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础什么是实时系统？「实时」和「快」的区别在哪？

    实时性指的是「最坏情况下的响应时间存在一个可以证明的上界」，与平均速度无关。一个平均 5 µs、但每小时出现一次 40 ms 尖峰的系统是不合格的；一个稳定在 800 µs、从不超过 1 ms 的系统是合格的硬实时系统。

    按超时后果分三档，这个分类要在需求阶段就定死，因为它决定了预算：

    • 硬实时：一次超时即系统失效，可能伤人毁设备（伺服电流环、气囊点火）。
    • 固实时：超时那一帧作废，系统继续（视觉伺服的一帧、周期总线报文）——这是 PREEMPT_RT 的主战场。
    • 软实时：超时只是体验下降（音视频、HMI）。

    工程含义：需求文档里要写「周期 1 ms，抖动不超过 ±100 µs，连续 72 小时无越界」，而不是「尽量低延迟」。验收报告的首要指标必须是 Max 而不是 Avg——因为决定系统成败的是「有没有哪一次超时」。

    加分：能主动指出「低延迟」（高频交易那种，追求平均更快、可接受长尾）和「实时」（追求绝不超时、可接受整体更慢）是两个不同目标，手段也不同——前者靠内核旁路与忙轮询，后者靠 PREEMPT_RT 与核隔离。

  2. 基础mainline Linux 上有哪些不可抢占的来源？为什么它做不了硬实时？

    根本原因不是「Linux 慢」，而是「最长的那个不可抢占段有多长」无法证明上界——它取决于当时恰好在跑什么驱动、什么文件系统路径。主要来源：

    • 自旋锁临界区：spin_lock() 会 preempt_disable()，内核里有数千把锁，你无法枚举最长的那一段。
    • 关中断区间：local_irq_disable() 与所有 *_irqsave 变体，期间连中断都进不来。
    • 硬中断 top-half：IRQ 上下文不可抢占，劣质驱动能跑到毫秒。
    • 软中断 / tasklet：在 irq_exit() 里就地执行，禁 BH 且关抢占，大流量收包时能连续吃掉很长时间。
    • per-CPU 变量保护区：靠关抢占防止迁移，数量极多。
    • 内存管理路径：缺页、直接回收、内存规整、透明大页——单次可达毫秒甚至更久。
    • RCU 回调批量释放、printk 到串口控制台（115200 下每 80 字符约 7 ms）。
    • SMI：固件层的中断，操作系统完全看不见也挡不住。

    关键的补充（能说出来是加分项）：PREEMPT_RT 只能解决前面五条。缺页要靠应用 mlockall，C-state 与 SMI 要靠固件，NUMA 要靠绑定。很多人上了 RT 内核发现毛刺还在，原因就在这里。

  3. 基础PREEMPT_RT 的五项核心改造分别是什么？各自的代价是什么？

    一句话概括 RT 做的事：把内核里所有「不可抢占的等待」改造成「可调度的等待」。五项改造：

    • sleeping spinlock：大多数 spinlock_t 变成基于 rtmutex 的可睡眠锁，持锁期间可被抢占。代价是短临界区从几十纳秒的忙等变成微秒级的睡眠/唤醒，上下文切换增多，吞吐下降。
    • threaded IRQ：中断处理搬到内核线程，可以赋优先级、可以被更高优先级任务抢占。代价是单次中断处理时延升高（多了唤醒和切换），且默认优先级一刀切，必须人工规划。
    • 优先级继承：rtmutex 内建 PI，解决 sleeping lock 带来的优先级反转。代价是加解锁要维护依赖链并传播优先级，开销上升。
    • 软中断线程化：软中断不再借用被打断任务的时间片就地执行。代价是网络吞吐明显下降、cache 局部性变差。
    • hrtimer + full tickless：定时精度到硬件时钟粒度，隔离核可停周期 tick。代价是配置复杂，且 nohz_full 只在核上仅有一个可运行任务时才真正生效。

    总结成一句：RT 是一笔明码标价的交易——用吞吐、能效和工程复杂度换最坏情况的确定性。没有确定性需求的系统开 RT 纯属浪费。

  4. 基础什么是优先级反转？优先级继承怎么解决它？还有别的办法吗？

    优先级反转：高优先级任务 H 阻塞在低优先级任务 L 持有的锁上，此时一个不需要这把锁的中优先级任务 M 抢占了 L 并长期占 CPU。结果 H 被 M 间接饿死，尽管 H 的优先级高于 M。这叫「无界反转」——M 可以跑任意久。经典事故是 1997 年火星探路者号的反复看门狗复位。

    优先级继承（PI）：H 阻塞在 L 持有的 rtmutex 上时，内核把 L 的有效优先级临时提升到 H 的水平；L 释放锁后恢复。这样 M 抢不走 L 的 CPU，H 的等待时间被压缩成「L 的临界区长度」——一个有界的量。

    用户态写法：

    pthread_mutexattr_t a;
pthread_mutexattr_init(&a);
pthread_mutexattr_setprotocol(&a, PTHREAD_PRIO_INHERIT);
pthread_mutexattr_setrobust(&a, PTHREAD_MUTEX_ROBUST);
pthread_mutex_init(&lock, &a);

    另一个方案是优先级天花板（PTHREAD_PRIO_PROTECT）：拿到锁就无条件提升到预设上限，不用维护等待链，开销更小更可预测；代价是必须静态分析出「所有可能用这把锁的线程里最高的优先级」，加了新线程忘了改天花板就失效。动态系统用 PI，静态可分析的系统可用 PROTECT。

    更高一层的答案：最好的办法是根本不共享锁。实时线程与非实时线程之间用无锁 SPSC 环形缓冲交换数据，实时侧只做一次原子的写指针推进，最坏耗时是常数，连 PI 都不需要。

11.2 中级（区分熟练度）

  1. 中级spinlock_t 和 raw_spinlock_t 在 RT 下有什么区别？什么时候必须用后者？

    在 RT 内核下：spinlock_t 变成基于 rtmutex 的可睡眠锁（持锁可被抢占、等锁者睡眠、带优先级继承）；raw_spinlock_t 保持原语义（忙等 + 关抢占）。API 兼容，驱动源码不用改，但语义变了。

    必须用 raw_spinlock_t 的地方，共同点是「处在真正无法睡眠的上下文里」：

    • 调度器核心（如 rq->lock）——rtmutex 的实现依赖调度器，调度器不能反过来依赖 rtmutex，否则自举死锁。
    • rtmutex / futex 自身的实现——同样的自举问题。
    • 时钟源与 hrtimer 基座、中断控制器驱动、NMI 路径——处在中断进入路径上。

    per-CPU 数据的短暂保护应该用 local_lock_t，它在 RT 下退化为 rtmutex、在非 RT 下仅关抢占，语义比裸的 preempt_disable() 清晰。

    生产视角，这才是这道题真正想问的：驱动作者最常犯的错是为了「更快」或「消掉 RT 下的睡眠告警」而把 spinlock_t 随手改成 raw_spinlock_t。这等于在 RT 内核上人为造了一段不可抢占区，把整机最坏延迟拉高，而且不报错、只是偶尔多几十微秒，极难定位。另外，raw_spinlock 临界区里绝不能调用任何可能睡眠的函数——包括 RT 下的 spin_lock()、kmalloc(GFP_KERNEL)、copy_to_user()；开发期开 CONFIG_DEBUG_ATOMIC_SLEEP 能抓到大部分违规。

  2. 中级为什么实时程序必须 mlockall？只调用它就够了吗？怎么验证它生效了？

    因为缺页处理是 PREEMPT_RT 解决不了的延迟源。一次缺页从几十微秒到几百毫秒不等（涉及换出时更糟），而且它专挑「第一次走到的代码路径」发作——实验室跑一万圈没事的程序，上线遇到第一个异常分支时就打穿。典型指纹是「重启后尖峰频繁，之后逐渐变稀疏」。

    只调 mlockall 不够，要配四件事：

    /* ① 锁住现有和未来的映射 */
mlockall(MCL_CURRENT | MCL_FUTURE);

/* ② 让分配器别把内存还给内核、别用 mmap 走新映射，
      否则「归还→再申请」会重新缺页，等于白锁         */
mallopt(M_TRIM_THRESHOLD, -1);
mallopt(M_MMAP_MAX, 0);

/* ③ 预热堆：malloc 之后必须 memset 真正落页，再 free */
void *p = malloc(N); memset(p, 0, N); free(p);

/* ④ 预热栈：volatile 防优化，深度按实测栈深乘 2 */
volatile char buf[512*1024]; memset((void*)buf, 0, sizeof buf);

    还要处理环境：RLIMIT_MEMLOCK 默认可能只有几十 KB，导致 mlockall 返回 ENOMEM；systemd 服务不走 PAM，得在 unit 里写 LimitMEMLOCK=infinity。mlockall 失败必须当致命错误退出，不能只 perror 一下继续跑。

    验证（这是加分的部分，不要只看返回值）：

    $ grep -E 'VmRSS|VmLck' /proc/<pid>/status
VmRSS:  184320 kB
VmLck:  184320 kB      # 两者同量级才算锁住

# 更硬的判据：稳态下缺页计数必须停止增长
$ awk '{print "minflt="$10" majflt="$12}' /proc/<pid>/stat

    只要 minflt 还在涨，就说明还有没预热到的路径。

  3. 中级用 cyclictest 测延迟，为什么必须加负载？负载应该跑在哪些核上？

    因为最坏延迟来自「某段长的内核代码正好在跑」。空机时文件系统不动、网络栈不动、内存分配器不动、没有 cache 争抢——那些最长的临界区根本没有机会被执行到。空机测出来的数字只证明「这台机器闲着的时候很安静」，而这从来不是要回答的问题。

    典型翻车路径：实验室 Max 28 µs 验收通过 → 现场实测 900 µs。这是这一行最常见的事故，没有之一。

    负载要覆盖真实场景会用到的所有子系统：

    $ stress-ng --hdd 4 --io 4 --vm 4 --vm-bytes 75% --cache 4 --timeout 24h &
$ while true; do hackbench -P -g 20 -l 2000 >/dev/null; done &
$ iperf3 -c <peer> -t 86400 -P 8 &
$ sudo cyclictest -p 80 -i 1000 -t 4 -a 2-5 -m -h 800 -q -D 24h

    负载放哪：应该放在非隔离核上，因为那才是真实部署的样子。但也别走极端——负载必须真实地争抢共享资源（末级缓存、内存带宽、内核锁），所以「把负载关到另一个 NUMA 节点」同样会得出偏乐观的结论。

    另外两个同等重要的前提：① 测量参数要和业务一致（-p 用你真实的优先级而不是 99，-i 用你真实的周期，-a 指向你的隔离核）；② 要跑够长——24 小时是发布前的最低要求，因为 logrotate、定时任务、内存碎片积累、机房温度循环都是「白天测不出、凌晨三点炸一次」的角色。

    最后检查 Histogram Overflows 必须为 0，否则超出 -h 上限的样本真实值你根本不知道，报告无效。

  4. 中级什么是 RT throttling？怎么发现它被触发了？该不该关掉？

    内核默认给实时任务设了限流：每 sched_rt_period_us（默认 1 秒）里，实时任务最多占用 sched_rt_runtime_us（默认 950000 µs，即 95%），剩下 5% 强制留给普通任务。目的是防呆——一个写错的 SCHED_FIFO 死循环不至于让你连 SSH 都登不上。

    它的签名非常好认：每秒稳定出现一次、幅度接近 50 ms 的巨型停顿，规律得像时钟。看到这个形状先查它。

    $ dmesg | grep -i 'RT throttling'
[  842.113204] sched: RT throttling activated
# 注意：这条只打印一次，重启后才会再打，很容易被日志淹没

$ cat /proc/sys/kernel/sched_rt_period_us    # 1000000
$ cat /proc/sys/kernel/sched_rt_runtime_us   # 950000

    该不该关，取决于你能不能满足两个前提。关掉的写法是 echo -1 > /proc/sys/kernel/sched_rt_runtime_us，但前提是：

    1. RT 线程已被 isolcpus 钉在隔离核上，且系统至少留一个非隔离核可供登录；
    2. 有独立的看门狗（硬件看门狗或另一个核上的监控进程）能在 RT 线程失控时复位。

    不满足这两条就关限流，等于把「偶尔卡 40 ms」换成「偶尔整机死机」，后者在现场更难交代。

    更重要的判断：触发限流通常说明设计本身有问题。一个健康的实时任务不该长期占满一个核的 95%——那意味着几乎没有余量应对负载波动。直接关限流是止痛药，减轻单周期工作量或换 SCHED_DEADLINE（它自带准入控制和带宽隔离）才是解药。

11.3 高级（体现深度）

  1. 高级线程化中断到底带来了什么？它把延迟变低了吗？优先级该怎么规划？

    先给一个反直觉的结论：线程化中断没有把延迟变低，它把中断的平均处理时延变高了（多了一次唤醒和上下文切换），把系统的最坏调度延迟变低了。你换到手的是可控性——中断从一个不可协商的打断，变成一个可以按优先级排队、可以用 ps 看见、可以被 tracer 记录的普通线程。

    $ ps -eo pid,cls,rtprio,comm | grep irq/
   93 FF      50 irq/24-eth0-rx-0
  128 FF      50 irq/31-xhci_hcd
$ sudo chrt -f -p 85 93     # 现场总线网卡，提到控制环之上
$ sudo chrt -f -p 20 128    # USB 无关紧要，压到最低

    两个必须知道的工程细节：

    • 并非所有中断都能线程化。驱动可以用 IRQF_NO_THREAD 声明必须留在硬中断上下文——时钟中断、IPI、某些中断控制器级联就属于这类。所以「RT 下没有硬中断了」是错的。
    • 默认优先级是一刀切的。所有中断线程出厂时通常同一个优先级，意味着一块和你业务无关的网卡，与你赖以驱动控制环的现场总线卡地位相同。不动手规划等于没享受到这项改造的好处。

    优先级规划的原则（这部分最能区分做过和没做过）：

    • 99 不要碰——留给迁移线程等内核自身机制。业务设 99 并出现忙循环，连负责检测卡死、留下现场的机制都会被压死，事后一片空白。
    • 90–98 给看门狗与安全监控（必须高于业务，否则业务卡死时它也喂不了狗）。
    • 80–89 给最紧的控制环，60–69 给次级环，中间留给驱动它们的关键中断线程。
    • 日志、诊断、HMI 一律 SCHED_OTHER，不给任何 RT 优先级。

    动手前先 ps -eo cls,rtprio,comm --sort=-rtprio 摸清系统里现有内核线程的分布，按实际情况校准，不要照抄任何一份数字。

  2. 高级PREEMPT_RT 和双内核（如 Xenomai）的核心取舍是什么？什么时候该选哪个？

    架构差异在于「实时代码运行在谁的调度器之下」：PREEMPT_RT 只有一个内核，实时任务和普通任务共用 Linux 调度器与 POSIX API；双内核方案是一个微型实时内核直接接管硬件中断，Linux 被降级成它的最低优先级任务，实时代码跑在实时内核上。

    核心取舍一句话：双内核的延迟更好（通常低一个档次），但你必须用它自己的 API 写实时代码，而那套 API 之外的整个 Linux 生态在实时路径上一概用不了。

    具体意味着：实时线程里不能调 glibc（可能陷入 Linux 内核而丢失实时上下文），不能用标准 socket，不能直接用 ROS 2 的通信中间件，第三方库基本要重写或包一层；实时路径上的设备还要写专用驱动。换来的那几十微秒，代价是整个软件栈的可移植性和团队的学习曲线。

    而 PREEMPT_RT 的全部魅力在于同一套代码、同一套 API、同一套工具链：实时线程可以直接用标准容器、直接跑 ROS 2、直接 gdb 调试、直接 perf/ftrace。

    决策顺序（比背对比表更有用）：

    1. 超时一次的后果是什么？会伤人毁设备 → 进功能安全流程，考虑带认证的 RTOS，Linux 最多做非安全域。
    2. 需要多低的最坏延迟？毫秒级 → mainline 调优就够，别白白损失吞吐；几百到几十微秒 → PREEMPT_RT 主场；个位数微秒 → Linux 这条路基本到头，考虑双内核、专用 MCU 或下沉到硬件。
    3. 要不要 Linux 生态？要 ROS 2、容器、视觉库 → PREEMPT_RT 几乎是唯一合理选择。
    4. 团队会什么？这条比前三条加起来还现实。纯 Linux 团队硬上双内核，周期翻倍且交付后没人敢维护。
    5. 能不能拆？最常被忽略的一招——把 µs 级的那一小块下沉到独立 MCU 或运动控制卡，主控用 PREEMPT_RT 跑逻辑与通信。典型机器人架构就是「电流环在驱动器 MCU（10 kHz+）→ 关节控制在 RT 主控（1 kHz）→ 规划感知在普通 Linux（10~100 Hz）」，各层用确定性总线连起来。这比在单一系统里死磕现实得多。
  3. 高级虚拟机里能做硬实时吗？怎么判断 vCPU 被宿主偷了时间？

    结论要说得干脆：通用虚拟化环境下做不了硬实时。

    原因是 vCPU 只是宿主上的一个普通线程。宿主调度器可以在任意时刻把它换下去，宿主上的其它虚拟机、宿主自身的内核工作、迁移、快照都会导致 vCPU 停摆。guest 内核对此完全无感——从它的视角看就是「时间跳了一段」。症状因此和 SMI 极为相似：cyclictest 报出毫秒级尖峰，但 guest 里所有追踪工具都查不到原因，ftrace 时间线一片空白。

    判据（steal time）：

    $ vmstat 1
 r  b   swpd   free  ...  in   cs us sy id wa st
 1  0      0 2103224  ... 892 1204  3  1 94  0  2
#                                              ↑ st 非 0 = 宿主在抢你的 CPU

$ head -1 /proc/stat
cpu 4821 0 2201 918224 118 0 44 9821 0 0
#                                ↑ 第 8 个字段是累计 steal（jiffies）

    如果非要在虚拟化平台上跑，只能把它降级成「尽力而为的固实时」，且宿主侧必须全部满足：① vCPU 一对一独占绑定物理核，且那些核在宿主上也被 isolcpus 隔离；② 宿主完全不超卖，内存预分配并锁定（大页）；③ 宿主自己也是 RT 内核，vCPU 线程被赋予 RT 优先级；④ 关闭内存气球、页合并、动态迁移；⑤ I/O 走 SR-IOV 或 PCIe 直通，不走软件模拟。

    满足这些之后延迟仍会比裸机差一档。更诚实的工程判断是：真有硬实时需求就用裸机或专用 MCU，把虚拟化留给非实时部分。很多车载与工业方案正是这么划分的——一颗 SoC 上，实时域跑裸的 RTOS 或 RT Linux，应用域跑虚拟化，两者靠硬件隔离与共享内存通信。

    加分：能指出「ftrace 抓不到就是一条强证据」——它把嫌疑范围一下子缩到固件（SMI）和虚拟化（steal）两类，而这两类的区分办法分别是 hwlatdetect 和 vmstat 的 st 列。

  4. 高级给你一台全新的机器和一个 1 ms 周期、抖动不超过 100 µs 的需求，你会怎么系统性地把最坏延迟压下来？

    按「先建立可信的测量，再从收益最大的一层开始，每次只改一类并重测」推进。顺序本身就是答案的一部分——顺序错了会浪费大量时间。

    第 0 步：先量固件底线，这决定了后面值不值得做。

    $ sudo hwlatdetect --duration=30m --threshold=10

    如果这里就报出几百微秒，说明系统最坏值不可能低于这个数，先去改固件设置（关 USB legacy、关温度轮询相关 SMI、关 C-state、关 turbo、关 SMT），改不了就换板子——继续调软件是白费力气。

    第 1 步：换 RT 内核。CONFIG_PREEMPT_RT=y，同时确认 HIGH_RES_TIMERS、NO_HZ_FULL、RCU_NOCB_CPU 开着，LOCKDEP / DEBUG_PREEMPT / KASAN 全部关掉（拿调试内核测性能是经典自伤）。验证：uname -v 里有 PREEMPT_RT、/sys/kernel/realtime 为 1。

    第 2 步：CPU 隔离四件套。这是不改一行代码就能拿到的最大收益。

    isolcpus=nohz,domain,managed_irq,2-7 nohz_full=2-7 rcu_nocbs=2-7 irqaffinity=0-1
intel_pstate=disable processor.max_cstate=1 intel_idle.max_cstate=0
nosmt transparent_hugepage=never nosoftlockup nmi_watchdog=0

    验证不能只看 /proc/cmdline——那只证明你传了参数。要看 /sys/devices/system/cpu/isolated 和 nohz_full 的实际输出，空的就说明参数没被接受。

    第 3 步：中断与内核线程精修。逐列检查 /proc/interrupts，隔离核那几列必须零增长。托管中断改不动（返回 EIO）就靠 managed_irq 标志和 ethtool -L 降队列数。别忘了 /sys/devices/virtual/workqueue/cpumask。

    第 4 步：应用改造。mlockall + 堆栈预热 + mallopt 禁归还 + 绑核 + 优先级规划（80–89，不要 99）+ PI mutex + 无锁环形缓冲替代日志 + LD_BIND_NOW。验证靠 VmLck 与 minflt 停止增长。

    第 5 步：带负载长跑并看分布形状。

    $ stress-ng --hdd 4 --io 4 --vm 4 --vm-bytes 75% --cache 4 --timeout 24h &
$ while true; do hackbench -P -g 20 -l 2000 >/dev/null; done &
$ sudo cyclictest -p 80 -i 1000 -t 4 -a 2-5 -m -h 800 -q -D 24h

    看直方图形状而不只看一个 Max：双峰 → C-state 或频率没锁死；宽平分布 → 隔离没生效；远处孤立样本 → 低频事件，用 cyclictest -b 150 --tracemark 设阈值让它自己抓现场，配合 wakeup_rt tracer 看那一刻是谁在跑。若 ftrace 什么都没抓到，回到第 0 步查固件，或确认这不是虚拟机。

    第 6 步：判定与交付。需求是 100 µs 抖动，实测最坏值应当留出至少 3 倍余量（即 30 µs 量级），少于 3 倍不要上线——硬件批次、环境温度、固件版本都会浮动。报告里必须写清硬件型号、BIOS 版本、完整 /proc/cmdline、负载构成、样本量，并附 hwlatdetect 结果，Overflows 必须为 0。

    第 7 步：进生产监控。设备上长期采集周期偏差直方图并上报，退化时告警。把 hwlatdetect 加进产线检验，把 BIOS 版本与设置快照纳入配置管理——只锁软件版本不锁固件版本，等于只锁了一半。

    贯穿全程的两条纪律：每次只改一类东西并重测（否则你不知道该保留哪几项）；所有数字都要标明「典型量级、强依赖硬件与固件」，换板子或刷 BIOS 之后结论作废，必须重测。
