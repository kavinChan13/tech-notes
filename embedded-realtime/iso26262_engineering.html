01

为什么车企必须 ISO 26262

背景：从 IEC 61508 而来 · 10 大 Part 概览 · 不合规的代价

ISO 26262（Road vehicles — Functional safety）2011 年首版、2018 年第二版，是汽车电子电气（E/E）系统功能安全的行业门槛。但如果你是刚进车企的 C++ 工程师，直接从标准文本读进去几乎一定会迷路：十二个 Part、上千页，通篇是 shall 和推荐度表格，读完你依然不知道明天该干什么。

所以这一章不从标准文本讲，从钱和法律讲。理解了车企在怕什么，你才会理解为什么改一行代码要填三份表、为什么你的 std::vector 过不了评审。

功能安全（Functional Safety）的官方定义可以浓缩成一句话：不存在由 E/E 系统的失效行为（malfunctioning behaviour）导致的不合理风险。三个词都是限定语——E/E 系统（不管纯机械失效）、失效行为（不管系统正常工作时的不足）、不合理风险（不是"零风险"，风险要降到社会可接受的程度）。这三个限定语划出的边界，比定义本身更值得记。

先算一笔账：不合规的代价是什么量级

汽车行业对流程的偏执不是文化洁癖，是被赔出来的。几个公开的量级（数字取自公开报道，用于说明数量级，不作为精确引用）：

  • 丰田非预期加速事件（2009–2010）：北美召回约 900 万辆量级，2014 年与美国司法部达成 12 亿美元量级的和解，此外还有集体诉讼与单独民事赔偿。在其中一起民事诉讼（Bookout v. Toyota）中，原告方聘请的嵌入式专家出庭作证，公开报告指出被审查的电子油门控制软件存在单点故障、栈使用不可分析、以及上万处编码规范违规——丰田方对这些结论持异议，但这份证词此后成了整个行业内部培训里最常被引用的反面教材。
  • 高田气囊气体发生器：全球召回量级达到数千万至上亿个部件，公司于 2017 年破产。这是"一个部件把一家 Tier 1 巨头做没了"的教科书案例。
  • 一次普通的软件召回：即使不涉及伤亡、只是 OTA 就能修的软件缺陷，通知车主、更新记录、向监管机构报备的固定成本也在每辆车几十到几百美元量级；乘以几十万辆，就是一个部门一年的预算。
某国内 Tier 1 的 EPS（电动助力转向）项目，因为没能在定点评审时提供完整的软件安全需求追溯矩阵，被 OEM 从供应商短名单里划掉。技术方案本身没问题，代码质量在同行里也算好——输在没有证据链。这类"技术过关但证据不过关"的失败在行业里非常常见，也是新人最难理解的一点：在车规项目里，做到了但证明不了，等于没做到。

安全不是测出来的，是设计和流程保证的

这句话听起来像口号，但它有严格的数学理由。ISO 26262 给 ASIL D 的随机硬件失效目标典型在 10 FIT 量级，也就是 10⁻⁸ 次/小时。假设你想纯靠"跑车验证"来统计性地证明这个数字：

# 要以合理置信度观察到一个 10^-8 /h 量级的事件，
# 需要的累计运行小时数在 10^8 ~ 10^9 h 量级

10^8 h  ÷ (24 h/天 × 365 天)  ≈  11,400 车·年
10^9 h  ÷ (24 h/天 × 365 天)  ≈  114,000 车·年

# 换算成一支 1000 辆的测试车队、每天跑 8 小时：
10^8 h ÷ (1000 辆 × 8 h/天)  ≈  34 年
# 而且这只能验证【一个】配置、【一个】软件版本。
# 每次改一行代码，统计意义上的证据就归零。

结论很硬：这个量级的安全性在物理上无法被测试证明。既然不能"测出来"，标准只能退一步——要求你用结构化的论证替代统计证据：需求是不是完整、架构上有没有单点故障、每一条安全需求是不是都有对应的实现和验证、用的工具是不是可信。这就是 V 模型、追溯性矩阵、Safety Case 这一整套东西存在的根本原因。

类比：你没法靠"这座桥我开车压过一千次都没塌"来证明它能承重 50 吨。你得给出材料参数、受力计算、焊缝检验记录、以及第三方复核。测试是抽样，论证才是覆盖。功能安全走的是桥梁工程那条路，不是互联网 A/B 测试那条路。

三条边界：26262 明确不管什么

新人最常见的错误是把"任何跟安全沾边的事"都塞进 26262。这三条边界必须能张口就说清，面试里几乎必问：

类别典型例子归谁管为什么不是 26262
E/E 失效（26262 的范围） MCU 位翻转导致转向扭矩计算错误；CAN 报文丢失导致制动指令过期 ISO 26262 —
性能不足 / 规格不充分 摄像头在逆光下把白色货车识别成天空；AEB 对横穿的电动车反应不及 ISO 21448（SOTIF） 系统没有失效，它严格按规格工作了——问题在规格本身没覆盖这个场景
恶意攻击 通过车载娱乐系统跳到 CAN 总线上伪造制动报文 ISO/SAE 21434 + UN R155 26262 的失效模型是随机失效与系统性缺陷，不含"有智能的攻击者"这个假设
非 E/E 危害 电池热失控起火、材料毒性、锐边割伤、纯机械件断裂 其它法规与标准 不由 E/E 系统的失效行为触发
这四类在真实项目里会交叉，这才是难点。一个可被入侵的 ECU 同时是信息安全问题和功能安全问题：攻击者伪造的制动指令在 26262 的视角下就是一次"失效行为"。所以现在的做法是让 26262 的安全分析和 21434 的 TARA 互为输入，而不是两个团队各写各的文档。详见 §10。

从 IEC 61508 而来：为什么汽车要单开一本

IEC 61508（1998）是通用工业功能安全的"母标准"，用 SIL 1–4 分级。它的假设是化工厂、电梯这类低批量、有专业操作员、可以停机检修的系统。汽车完全不同：

  • 批量巨大：一个车型几十万到几百万辆，10⁻⁸/h 的失效率乘上车队规模才是真实的事故期望值；
  • 操作者不专业：所以引入了 Controllability 这个维度——同样的失效，专业司机能救回来、普通人不能，风险等级就不同。这是 61508 里没有的；
  • 不能停机：车在高速上不能"进入安全停机状态"然后等维修，所以 26262 有大量关于降级运行（degraded mode）与安全状态（safe state）的要求；
  • 成本压力极端：一个 ECU 贵 5 美元，乘 200 万辆就是 1000 万美元。这直接解释了为什么 ASIL Decomposition（§4）这么受欢迎——它是用架构换硬件成本。

同样从 61508 派生出来的行业分支还有：医疗 IEC 62304、航空 DO-178C、铁路 EN 50128、工业机械 ISO 13849。它们的骨架高度相似（分级 + V 模型 + 工具认证 + 覆盖率要求），所以做过其中任何一个，转到 26262 只需要换词汇表。

下面这个例子能让你立刻感受到差别。同一个"读取轮速传感器"的函数，两种项目里长得完全不一样：

/* ---------- 普通项目：能跑就行 ---------- */
float getWheelSpeed() {
    auto raw = sensor.read();          // 失败了怎么办？没说
    return raw * kScale;                // 超范围怎么办？没说
}

/* ---------- ASIL B 项目：同一件事 ---------- */
/**
 * @brief   读取单个轮速传感器并做合理性检查
 * @satisfies SWSR-BRK-0142   轮速信号在超出物理范围时应被标记为无效
 * @satisfies SWSR-BRK-0143   传感器读取失败应在 20 ms 内被检测
 * @asil    B
 * @wcet    18 us @ 200 MHz (measured, see TR-BRK-0087)
 */
SpeedResult getWheelSpeed(WheelId id) noexcept
{
    RawSample raw{};
    if (sensor_.read(id, raw) != Status::kOk) {
        return { 0.0F, Validity::kSensorFault };   // SWSR-BRK-0143
    }
    /* 范围检查：物理上不可能超过 350 km/h → 折算后的计数上限 */
    if (raw.ticks > kMaxPlausibleTicks) {
        return { 0.0F, Validity::kOutOfRange };   // SWSR-BRK-0142
    }
    return { static_cast<float>(raw.ticks) * kScale, Validity::kValid };
}

注意差别不在"代码写得更严谨"这个层面——差别在每一行防御性代码背后都挂着一个可追溯的编号。评审时没人会问"你为什么加了范围检查"，只会问"SWSR-BRK-0142 这条需求的测试用例在哪、覆盖率报告里这个分支覆到了吗"。

不合规的实际后果

  • 进不了供应商名单：OEM 定点评审（technical review / sourcing）会直接要求过程能力证据。这是最常见、也最"无声"的淘汰方式——你甚至不会知道自己是因为这个被刷掉的。
  • 型式认证与准入：功能安全本身在多数市场不是逐条法定强制，但它是行业公认的"state of the art"。一旦出事，法庭上"你有没有遵循行业公认实践"就是决定性问题。而信息安全（UN R155/R156）在欧盟等市场已经是法定的型式认证前置条件，与功能安全流程高度耦合。
  • 产品责任：民事赔偿之外，部分司法辖区对"明知有缺陷而未处理"存在刑事追责路径。这也是为什么 Safety Manager 的签字是个人签字、不是部门盖章。
  • 召回与品牌：见本节开头的量级。
一句话总结这一章：ISO 26262 不是一本"更严格的编码规范"，它是一套把"我们的产品足够安全"这个断言变成可审计证据链的方法论。你的日常工作变化，本质上都是在为这条证据链补齿。
02

ASIL 等级 + 推导方法

S × E × C 矩阵

ASIL（Automotive Safety Integrity Level，汽车安全完整性等级）分 A / B / C / D 四级，加上 QM（Quality Management，即"按常规质量流程做就行，没有额外的功能安全要求"）。D 最严。

先记住这一章最重要的一句话：ASIL 是「危害事件」的属性，不是零件、不是 ECU、更不是"我们团队"的属性。说"我们是 ASIL D 团队"在语义上是错的；正确的说法是"这条安全目标是 ASIL D，它被分配到了我负责的这个软件组件上"。这个区分不是咬文嚼字——它直接决定了同一块 MCU 上可以同时跑 QM 和 ASIL D 的代码（前提是做好隔离，见 §4）。

HARA：ASIL 是怎么被"算"出来的

HARA（Hazard Analysis and Risk Assessment，危害分析与风险评估）是概念阶段的核心活动，也是整个项目里唯一能凭空创造 ASIL 的地方。它的输出决定了后面几年几十个人的工作量，所以 HARA 会议通常由 Safety Manager 主持，系统、软件、硬件、整车、法务都要在场。

① Item Definition定义"这个东西是什么"
→
② 场景 × 失效行为穷举组合
→
③ 危害事件Hazardous Event
→
④ S / E / C 打分查表得 ASIL
→
⑤ 安全目标 + FTTISafety Goal

五步逐个说清：

  1. Item Definition（项目定义）：先划边界——这个"item"包含哪些 ECU、传感器、执行器，它对外的接口是什么，它依赖哪些不属于它的东西。这一步做糙了，后面所有分析都会漏。常见坑：把电源、时钟、总线当成"环境"而不写进依赖，结果整个供电失效的危害没有被分析到。
  2. 穷举「运行场景 × 失效行为」：场景维度（高速直行 / 低速泊车 / 静止 / 弯道 / 湿滑路面 / 拖挂 / 倒车），失效行为维度（功能丧失 loss、功能非预期激活 unintended activation、功能过量 too much、过少 too little、时序错误 too early/late、方向错误）。这个二维笛卡尔积是 HARA 的主要工作量，一个中等复杂度的 item 能产生几百行表格。
  3. 筛出危害事件：不是每个组合都危险。"静止时转向助力丧失"没有危害；"高速时非预期全力制动"有。留下来的每一行就是一个 hazardous event。
  4. 对每个危害事件独立打 S / E / C，查表得 ASIL。
  5. 为每个危害事件写一条安全目标（Safety Goal），继承该危害的 ASIL，并给出 FTTI（Fault Tolerant Time Interval，容错时间间隔）与安全状态。
FTTI：从故障发生到危害事件发生之间，系统还"来得及"处理的时间窗。它是留给你的预算——故障检测时间 + 故障反应时间必须小于 FTTI，并且要留裕量。制动这类场景的 FTTI 常在几十到一百多毫秒量级，转向可以更短（几十毫秒），而"电池管理慢性过温"这类可能是秒级甚至分钟级。
这个数字直接决定你的软件架构：FTTI 是 50 ms，那你的安全监控任务周期不可能是 100 ms，看门狗窗口也不能设成 200 ms。新人最容易忽略的就是——FTTI 不是"越小越安全"，它是从物理场景推出来的客观量，你的任务周期必须去适配它。

三个维度的评级

S — Severity（伤害严重度）

等级描述怎么判
S0无伤害只有财产损失或功能不可用。S0 直接判 QM，不进 ASIL 表
S1轻度至中度伤害行业普遍参照 AIS（Abbreviated Injury Scale）做映射：可恢复、不留后遗症
S2严重伤害，可能危及生命但存活概率大骨折、内脏损伤等
S3致命或危及生命（存活不确定）高速碰撞、正面撞击的典型结果

E — Exposure（暴露概率）

注意 E 评的是那个运行场景出现的概率，不是失效的概率。失效概率是硬件指标（FIT），跟 E 完全无关——这是新人第一个常犯的混淆。

等级描述常用判据（按时间占比）
E0不可思议的场景被认为无需考虑，不分配 ASIL
E1非常低典型判据：远低于 1% 的驾驶时间，或"一年少于一次"量级。如"在结冰的隧道内下坡拖挂"
E2低约 1% 以下驾驶时间 / 一年数次。如"雪地起步"
E3中约 1%–10% 驾驶时间 / 每月都会遇到。如"湿滑路面高速行驶"
E4高超过 10% 驾驶时间 / 几乎每次开车都会经历。如"平路直行"、"制动"、"转向"
标准同时给了"按时间占比"和"按发生频次"两套判据，具体门槛在 Part 3 的附录里有表。这里给的百分比是行业里常用的近似口径，正式项目请以标准原文的分类表为准，并且整个项目要用同一套口径——最怕的是不同工程师用不同标尺打分，导致 HARA 内部不自洽。

C — Controllability（可控性）

C 评的是一般司机（不是赛车手，也不是最差的司机）在该场景下能否避免伤害。这是 26262 相对 IEC 61508 最独特的维度。

等级描述常用判据
C0总体可控不构成危害，直接判 QM。如"收音机音量突然变大"
C1简单可控99% 以上的司机能避免伤害。如"助力转向轻微变重"
C2一般可控90% 以上的司机能避免。如"轻微的非预期减速"
C3难以控制或不可控不足 90% 的司机能避免。如"高速时方向盘自行转动"
C 是整个 HARA 里最容易被博弈的一格。把 C3 说成 C2，ASIL 就从 D 降到 C，项目预算立刻少几百万。所以正规做法是：C 的评级要有依据——驾驶员在环（DIL）模拟器实验、真实道路测试数据、或已发表的人因工程研究，而不是会议室里"我觉得我能踩住"。评审员和第三方评估人最爱盯的也是这一格。

三个具体例子：逐项打分

例 1 · 高速行驶中非预期的全力制动

  • 失效行为：制动功能"非预期激活"（unintended activation），而非"丧失"。
  • S = S3：120 km/h 突然全力制动，后车追尾几乎不可避免，正面/背面高速碰撞的典型后果是致命。
  • E = E4：高速公路巡航是绝大多数车辆的日常场景，远超 10% 驾驶时间。
  • C = C3：制动是瞬间发生的，司机没有任何操作可以抵消它（不能"反向踩"），后车司机也来不及反应。
  • 3 + 4 + 3 = 10 → ASIL D
  • 安全目标：应避免非预期的制动力矩输出。FTTI 在几十毫秒量级——因为一旦制动器建压，减速已经发生。

例 2 · 转向助力异常（同一个 ECU，两种失效模式，两个 ASIL）

这个例子专门用来说明"ASIL 属于危害而不属于零件"。同一个 EPS 控制器：

  • 失效模式 A：助力丧失（方向盘变重，但机械连接完好）
    S3（可能偏出车道）· E4（转向是持续行为）· C2（多数司机能靠体力把车控住，尤其中高速时所需助力反而较小）
    → 3 + 4 + 2 = 9 → ASIL C
  • 失效模式 B：非预期转向扭矩（方向盘自己往一边转）
    S3 · E4 · C3（车在主动往路肩或对向车道去，司机的反打时间窗只有几百毫秒）
    → 3 + 4 + 3 = 10 → ASIL D

结论：这个 EPS 项目的整体安全需求包含一条 ASIL D（防止非预期扭矩）和一条 ASIL C（保证助力可用性）。工程上通常按最高的那条来定架构，但两条需求的验证证据可以不同——ASIL C 的那条不需要做 MC/DC 覆盖。混在一起按 D 做，是很多项目白花钱的原因。

例 3 · 仪表盘车速显示偏低 20 km/h（边界案例）

这个例子会在 HARA 会上吵很久，正好展示评级的真实过程：

  • S：显示偏低 → 司机实际超速 → 事故严重度提高。有人主张 S3（超速事故可致命），也有人主张 S1/S2（大部分超速不会直接致命）。折中通常落在 S2，并在文档里写清理由。
  • E：车速表在任何驾驶时刻都在被使用 → E4。这一格基本没争议。
  • C：这是真正的争论点。反方认为 C3（司机没法察觉一个持续偏低 20 km/h 的示数）；正方认为 C2——司机有其它线索：发动机/风噪、导航的限速提示、周围车流速度、以及 ADAS 的限速识别。若采信 C2，则 2 + 4 + 2 = 8 → ASIL B；若采信 C3 则是 ASIL C。

行业实践里，数字仪表的安全相关指示（车速、部分警告灯、驻车/挡位显示）常见落在 ASIL A–B，而同一块屏上的导航、音乐、主题皮肤是 QM。这就是为什么现在的仪表 SoC 普遍是混合关键度架构：一个 hypervisor 或一个独立的安全 MCU 负责那几个 ASIL B 的图元，Linux/Android 负责其余部分。

见过一个真实的返工：某项目仪表软件把"挡位显示"和"主题动画"放在同一个 Qt 进程里，理由是"反正都是画图"。定点后 OEM 提出挡位显示是 ASIL B（挂着 R 档却显示 D 档，倒车时会撞人），整个渲染层必须重构——最后的方案是安全图元由独立的 ASIL B MCU 直接驱动一块叠加图层，Qt 那一层降级为 QM。这次重构花掉了大约 8 个人月，而它本可以在 HARA 阶段用两小时的会议避免。教训：软件架构必须等 HARA 结果出来再定，不能倒过来。

HARA 的输出不会直接变成代码。中间有两次转换，每一次都继承 ASIL：

03

V-Model 全生命周期

概念 → 设计 → 验证

ISO 26262 组织开发活动用的是 V 模型：左臂逐层细化（需求 → 架构 → 详细设计 → 实现），右臂逐层集成验证（单元 → 集成 → 系统 → 整车）。它的核心约定只有一句话——左臂每一层产出的规格，都必须由右臂同一层的验证活动来证明被实现了。这条横向对应关系比"先设计后测试"的时间顺序重要得多。

类比盖房子：左臂是"建筑图 → 结构图 → 施工图 → 砌墙"，右臂是"每块砖检验 → 每层验收 → 整栋结构检测 → 消防验收"。关键在于横线：结构图对应的是结构检测，不是消防验收。如果你拿消防验收报告来证明结构图被正确实现了，验收员会当场把你赶走。26262 的评审员做的是完全一样的事——他会拿着你的软件架构文档问"证明这个架构被正确实现的是哪份测试报告"，而不是接受你的整车路试记录。

左右对应关系：每一层要交什么、验收标准是什么

看这张表最实用的读法是从右往左。项目后期出问题，几乎都表现为"某一层的验证证据缺失或对不上"。而"证据对不上"的根因通常在左臂——需求写得不可验证（"系统应快速响应"这种），到了右臂就没法写出通过判据。所以一条软件安全需求写完，先自问一句：我能不能给它写出一个会失败的测试？写不出来，这条需求就不合格。

安全生命周期：V 模型只是中间那一段

V 模型覆盖的是"产品开发"，但安全生命周期比它长得多——量产之后的每一次 OTA、每一次工厂端刷写、直到车辆报废，都还在安全生命周期里：

概念阶段 产品开发（V 模型） 生产 运营与服务 退役 ───────── ──────────────────── ───────── ────────────── ──────── 相关项定义 系统 / 硬件 / 软件开发 产线刷写 现场故障监控 安全相关的 HARA 集成与验证 端到端测试 OTA 变更影响分析 报废处理要求 安全目标 安全确认 可追溯的 安全异常上报与召回决策 安全计划 Safety Case 生产记录 用户手册中的安全说明 │ │ │ │ └── 一旦有变更（新车型、新供应商、OTA 功能），都要回到起点做「变更影响分析」， 判断是"影响安全"（走完整流程）还是"不影响安全"（需要有论证，不是拍脑袋）

对软件工程师最实际的影响在运营阶段：你在量产车上推一个 OTA，需要先回答"这个改动是否影响任何安全需求"。答案是"是"，就要重跑对应层级的验证、更新 Safety Case、并让独立评审人复核；答案是"否"，你也得写一份变更影响分析来证明这个"否"。没有"这就是个小改动"这种说法。

Confirmation Measures：三种独立评审，别混为一谈

26262 不相信"自己检查自己"，于是引入了 确认措施（confirmation measures）。它是三件不同的事，新人最常把它们混在一起说：

措施检查对象回答的问题典型执行者
确认评审
Confirmation Review		 具体的工作产品（安全计划、HARA、安全概念、Safety Case、集成测试规格……） "这份文档本身合规、完整、内部自洽吗？" 项目内或跨团队的独立评审人
功能安全审核
Functional Safety Audit		 过程的执行情况 "你们是不是真的按安全计划在干活？"——抽查配置管理记录、变更单、评审记录 质量/过程职能，独立于开发团队
功能安全评估

三者的独立性要求随 ASIL 递增，标准里定义了几个档位，业内一般这样口语化地表述：

I1 · 人员独立
不是编写这份工作产品的那个人，但可以是同一个团队的同事。
I2 · 团队独立
来自不同团队——即不向同一个直接上级汇报，避免"我的经理希望这个尽快通过"。
I3 · 组织独立
来自不同部门或外部组织，且独立于该项目的资源与预算决策链。

大致趋势是：ASIL A 的很多确认措施可以不做或只要求人员独立；到了 ASIL C/D，关键工作产品的评审要求团队级独立，功能安全评估要求组织级独立。

保守表述：具体哪个 ASIL 对应哪一档独立性，标准 Part 2 里有一张明确的表，各档位在不同工作产品上并不一致（HARA 的评审要求就比集成测试规格严）。这里只给趋势，正式项目请直接查 Part 2 那张表，不要照抄任何二手总结——包括本文。

为什么强调"独立性是分档的、且要花钱买"？因为它是成本的主要来源之一。I3 意味着你要么养一个独立部门，要么按小时付钱给外部评估机构。这也解释了一个现象：很多公司会把 ASIL D 的功能通过分解降到 ASIL B（§4），省下的不只是测试工作量，还有独立评审的档位。

Safety Plan 与 Safety Case：一头一尾两份主文档

Safety Plan（安全计划）在项目启动时就要写完并通过确认评审。它规定：本项目适用哪些 26262 活动、每项活动的负责人与时间点、哪些确认措施做到哪个独立性档位、用哪些工具、裁剪了什么以及理由。它是后续"功能安全审核"的对照基准——审核员就是拿这份计划来问"你说要做的这条，做了吗"。

Safety Case（安全论证）是项目结束时的收敛物。它不是"把所有文档装订在一起"，而是一条论证链：

断言本产品功能安全可接受
←
论证所有危害已识别并被安全机制覆盖
←
证据测试报告 / 覆盖率 / 分析 / 评审记录
←
背书独立功能安全评估报告

一个中等规模 ASIL D 项目的 Safety Case 主文档通常是几十到一百多页，但它引用的证据文档是数千份。这也是为什么"追溯性"是核心交付物（§9）——Safety Case 的每一句话都要能点开看到底层证据。

04

ASIL Decomposition

高级 ASIL 拆成 redundant 低级

实际工程中 ASIL D 极难也极贵：MC/DC 覆盖、组织级独立评估、认证工具链、硬件冗余，成本是 ASIL B 的数倍。所以 ISO 26262 给了一条正规出路——ASIL Decomposition（ASIL 分解）：把一条高 ASIL 的安全需求，拆成两条互相独立的低 ASIL 需求，只要任意一条生效就能达成安全目标。

类比：银行金库要求"被撬开的概率低于百万分之一"。你可以造一把百万分之一的超级锁（相当于 ASIL D），也可以装两把千分之一的普通锁（相当于两个 ASIL B）——前提是两把锁不能被同一把万能钥匙打开。如果两把锁是同一个厂、同一个模具、同一批材料，那"两把独立的锁"这个假设就崩了，你的风险其实还是千分之一。
ASIL 分解 99% 的争议都在这句"前提"上，不在分解本身。

分解的原理与合法组合

分解的数学直觉很简单：给 ASIL 编个"分数" QM=0、A=1、B=2、C=3、D=4，那么合法的分解就是把分数拆成两个非负整数之和。以此得到全部合法组合：

原始 ASIL合法的分解结果解读
ASIL D（4） ASIL C(D) + ASIL A(D)3 + 1：一个主通道做到 C，一个轻量监控做到 A
ASIL B(D) + ASIL B(D)2 + 2：最常用，两个对等通道，成本最优
ASIL D(D) + QM(D)4 + 0：等于没分解，但 QM 那一侧仍必须证明不干扰 D 侧
ASIL C（3） ASIL B(C) + ASIL A(C)2 + 1
ASIL C(C) + QM(C)3 + 0
ASIL B（2） ASIL A(B) + ASIL A(B)1 + 1
ASIL B(B) + QM(B)2 + 0
ASIL A（1） ASIL A(A) + QM(A)1 + 0；A 不能拆成 QM + QM——那等于凭空取消了安全要求
括号记法：ASIL B(D) 读作"ASIL B，源自 D"。它同时携带两个信息：
① 方法可以按 ASIL B 来——单元测试不需要做 MC/DC，架构方法表按 B 那一列查；
② 但它承载的是一个 ASIL D 的安全目标——所以对独立性的要求、以及对分解论证本身的评审要求，仍然是 D 级的。
忽略 ② 是滥用分解最常见的形式。
分解不能降低这三件事的 ASIL，它们永远保持原始等级：
① 分解本身的论证（为什么这两个通道足以替代一个 ASIL D 需求）；
② 独立性（FFI）的证明与相关失效分析（DFA）；
③ 把两个通道结果合并/仲裁的那段逻辑，以及顶层的安全确认。
换句话说：你可以把"算力矩"和"校验力矩"降到 B，但"比较两者并决定进安全状态"的那几十行代码还是 ASIL D。见过团队把仲裁器也标成 B(D)，被评估人一票打回——这是概念性错误，不是笔误。

FFI：独立性是分解成立的唯一前提

Freedom From Interference（FFI，互不干扰）指的是：一个元件的失效不会导致另一个元件失效。ISO 26262 Part 6 把软件层面的干扰归为三个维度，这三个词要能张口就说：

① 时间与执行

一个组件抢走或阻塞了另一个组件的执行机会：死循环占死 CPU、长时间关中断、持锁不放、任务优先级设计失误、栈溢出踩到别人。

② 内存

一个组件读写了不属于它的内存：野指针、数组越界、共享的可写全局变量、栈越界、DMA 目标地址算错。

③ 信息交换

组件间传递的数据被损坏、丢失、重复、乱序、延迟、或来自错误的发送方：总线错误、缓冲区覆盖、消息串线。

对应的技术手段基本是一一映射的：

干扰维度技术手段典型实现能证明到什么程度
时间与执行 时间预算监控 / 执行时间监控 OS 的 execution budget、任务超时检测（AUTOSAR OS 的 timing protection） 强：超预算直接被 OS 掐掉
程序流监控（Program Flow Monitoring） 在关键路径上打检查点，看门狗校验序列与时间窗 强：能抓到"跳过了一段代码"
不共享阻塞资源 两个通道之间不用同一把锁、不用同一个队列、不共用中断 强，但要靠架构评审+代码审查保证
内存 MPU / MMU 内存分区 Cortex-R/M 的 MPU region、AUTOSAR OS 的 memory protection、Hypervisor 的第二级页表 最强的一种：违规访问在硬件层被拦下并触发异常
静态内存 + 只读常量段 全静态分配、共享数据只允许单写多读、常量放 .rodata 中：能消除一大类问题，但抓不住"合法地址写错值"
信息交换 E2E 保护（CRC + 计数器 + 数据 ID + 超时） AUTOSAR E2E Profile；跨 ECU、跨分区、跨核都适用 强：可量化残余错误率，是分解论证里最好写的一段
单向通道 / 消息队列隔离 每个方向一个独立缓冲区，避免共享可写区 中

三个真实的 FFI 违例

这三个例子在评审里出现频率极高，而且它们的共同点是：代码本身没有 bug，架构上却让分解论证失效了。

违例 1 · 共享一把互斥锁（时间干扰）

两个通道各自访问一个"标定参数表"，为了线程安全共用了一把 mutex。看起来标准做法，但：

/* ❌ 破坏 FFI：主通道与监控通道共享同一把锁 */
namespace {
    Mutex          g_calibMutex;      // ★ 两个通道都用它
    CalibrationSet g_calib;
}

// 主通道（ASIL B(D)）
Torque computeTorque(const Input& in) {
    LockGuard lk{g_calibMutex};
    return applyCurve(in, g_calib);
}

// 监控通道（ASIL B(D)）——本应完全独立
bool checkTorque(Torque t, const Input& in) {
    LockGuard lk{g_calibMutex};   // ★ 主通道一旦持锁不放，
    return withinEnvelope(t, in, g_calib);  //   监控通道整个饿死
}

后果：主通道任何一个"持锁期间死循环 / 持锁期间被高优先级任务无限抢占"的失效，会同时让监控通道停摆。一个失效击穿两个通道 = 相关失效，分解论证不成立。

/* ✅ 修法：每个通道持有自己的一份只读副本 */
namespace {
    // 标定数据在启动时校验 CRC 后固化，运行期只读 → 无需加锁
    extern const CalibrationSet kCalibPrimary;    // 主通道专用
    extern const CalibrationSet kCalibMonitor;    // 监控通道专用
}
// 若必须运行期可变，则用「单写多读 + 双缓冲 + 每读者独立索引」，
// 读者永不阻塞；两份缓冲各自带 CRC，读到坏的就用上一帧。

顺带说一层：让两份标定由不同的编译单元、甚至不同的数据源生成，还能顺手削弱"同一个标定错误同时毒死两个通道"这类共因失效。

违例 2 · 共享一个硬件定时器 / 共享中断（时间 + 共因）

两个通道的周期任务都挂在同一个硬件定时器的中断上，理由是"省一个外设"。这个定时器一旦时钟树配置错误、或者晶振漂移，两个通道同时慢下来——而且它们的比较结果依然一致，监控通道完全察觉不到异常。

  • 这是典型的共因失效（Common Cause Failure）：单一根因导致多个元件同时失效。
  • 正确做法：监控通道用独立的时基——独立晶振、独立 PLL 分支，或至少是外部看门狗芯片自带的时基（这是外部窗口看门狗最大的价值：它的时基不来自被监控的 MCU）。
  • 共享中断向量同理：一个通道的 ISR 里出现长时间执行或异常，会推迟同优先级另一个通道的 ISR。

违例 3 · 共享内存但没做保护（内存 + 信息交换）

ADAS 域控里常见的写法：QM 的感知进程把结果写进一块共享内存，ASIL B 的规划模块直接读结构体。

/* ❌ QM 写 / ASIL B 读，中间什么都没有 */
struct ObjectList { uint32_t count; Object items[64]; };
volatile ObjectList* shm = map_shared("/percep_out");

for (uint32_t i = 0; i < shm->count; ++i) {   // ★ count 被写坏成 5000 呢？
    plan(shm->items[i]);                       // ★ 越界读，而且是 ASIL B 侧崩
}

这里同时踩了三个雷：QM 代码能写到 ASIL B 会读的内存（内存干扰）；数据没有完整性校验（信息交换干扰）；count 未做范围检查（缺少防御性实现）。修法是三件事一起上：

/* ✅ ① MPU 让 QM 侧只能写它自己的那块；
      ② E2E 保护校验数据完整性；
      ③ 消费侧对所有外来数据做范围检查（永远不信任输入） */
constexpr uint32_t kMaxObjects = 64;

PlanResult planFromPerception(const ObjectListE2E& msg) noexcept
{
    // ② 完整性 + 新鲜度：CRC / 计数器 / 数据 ID / 超时，见 §5
    if (e2e_.check(msg) != E2EStatus::kOk) {
        return degradeToSafeTrajectory();
    }
    // ③ 范围检查：即使 CRC 过了，语义也可能不合理
    const uint32_t n = (msg.payload.count <= kMaxObjects)
                       ? msg.payload.count : 0U;
    for (uint32_t i = 0U; i < n; ++i) { plan(msg.payload.items[i]); }
    ...
}

注意 ③ 的必要性：CRC 只能证明"数据在传输中没被改坏"，不能证明发送方算出来的值是合理的。QM 侧的感知模块本来就有 bug 的权利——那是它 QM 的含义。所以消费侧必须自己兜底。

MPU 分区：内存 FFI 最硬的一道证据

在评估人眼里，内存隔离的论证强度排序是：硬件 MPU/MMU 强制 > 编译期隔离（不同段 + 链接脚本约束） > 编码约定 + 代码评审。只有第一种能在报告里写"违规访问会被硬件拦截并触发确定的异常处理"。

/* Cortex-R/M 系 MPU 分区骨架（寄存器名按具体核手册，此处示意逻辑）
 * 目标：ASIL 分区不可被 QM 分区写；共享通道只有一个方向可写 */
struct MpuRegion {
    uint32_t base;       // 起始地址（需按 size 对齐）
    uint32_t size;       // 2 的幂
    Access   priv;       // 特权态权限
    Access   user;       // 非特权态权限
    bool     executable;
};

/* 每个 OS-Application 切换上下文时重载自己的 region 表 */
constexpr MpuRegion kSafetyPartition[] = {
    /* 自己的代码：只读 + 可执行（防止代码段被改写） */
    { SAFETY_TEXT_BASE, SAFETY_TEXT_SIZE, Access::kRO, Access::kRO, true  },
    /* 自己的数据 + 栈：可读写 */
    { SAFETY_DATA_BASE, SAFETY_DATA_SIZE, Access::kRW, Access::kRW, false },
    /* ★ 来自 QM 分区的数据：【只读】——QM 写，安全侧读 */
    { SHM_QM_TO_SAFETY, 4096,          Access::kRO, Access::kRO, false },
    /* ★ 发往 QM 分区的数据：【只写】——安全侧写，QM 读 */
    { SHM_SAFETY_TO_QM, 4096,          Access::kRW, Access::kRW, false },
    /* 其余地址空间：无权限 → 越界立刻 MemManage / Data Abort */
};

/* 违规时的处理：不是打印日志就完事，必须走到安全状态 */
extern "C" void MemManage_Handler() {
    recordFaultContext();        // 冻结地址 / PC / 分区 ID 到非易失区
    enterSafeState(SafeState::kActuatorCutoff);  // FTTI 内完成
}
MPU 的三个实战要点，评审时一定会被追问：
① region 数量有限（Cortex-M/R 常见 8–16 个），分区多了就得在上下文切换时重载表，这有开销，要算进 WCET；
② 对齐约束会浪费内存——region 大小必须是 2 的幂且基址对齐，链接脚本要配合，实际 RAM 利用率下降 10%–30% 很常见；
③ 异常处理器本身必须是最高 ASIL。MPU 抓到了违规却在处理器里死掉，等于没抓。这段代码通常几十行、全静态、无循环，并且要专门做故障注入测试验证它真的能进安全状态。

典型落地：制动 ASIL D 拆成 B(D) + B(D)

要素主通道（ASIL B(D)）监控通道（ASIL B(D)）独立性依据
职责完整的制动力矩计算与仲裁只做合理性校验：力矩是否在踏板/车速/路面对应的包络内算法多样性（不同模型 → 不易同错）
规模数万行通常几百到两千行监控器小 → 可穷尽验证
执行载体主核 / 主 MCU独立核或独立小 MCU（"safety companion"）时间与执行 FFI
内存自己的 MPU 分区自己的 MPU 分区 + 独立栈内存 FFI（硬件强制）
时基主 PLL独立时基 + 外部窗口看门狗消除时钟共因
通信两通道之间只有一条E2E 保护的单向消息 + 一条硬线使能信号信息交换 FFI
仲裁ASIL D：不一致或监控通道失联 → 在 FTTI 内切断执行器使能，进安全状态分解不降低仲裁的 ASIL

这个模式在行业里有个通俗名字：3 层监控概念（3-Level Monitoring Concept）——第 1 层是功能本身，第 2 层是功能监控（合理性校验），第 3 层是控制器自身监控（看门狗 + 指令集自检 + RAM/ROM 测试）。它最早在发动机管理系统上成型，现在几乎是所有 ASIL C/D 单 MCU 方案的默认骨架。

一个被评估人打回的分解论证：某项目把主通道和监控通道放在同一颗双核 MCU 的两个核上，声称"物理核不同即独立"。评估人问了三个问题就打回了——两个核共享 L2 缓存和内存控制器（一个核的 DMA 风暴会拖慢另一个核，时间 FFI 不成立）；两个核共享同一路电源与时钟（共因）；两个核用同一份编译器和同一套标定数据（系统性共因）。最后的整改方案不是换硬件，而是：给监控通道加外部窗口看门狗提供独立时基、给内存控制器配带宽限额、监控通道的标定数据独立生成并单独校验，再补一份完整的 DFA 报告。整改花了约 4 个月。教训："物理上分开"不等于"独立"，独立性要按三个维度逐项论证，每一项都要说清失效模式和防护措施。
被问"ASIL D 怎么做"，别只答"用 ASIL D 的方法"。高分答法是：先问这条需求能不能分解，然后给出 B(D)+B(D) 的方案，并主动说清三件不能降的东西（分解论证、FFI 证明、仲裁逻辑）和 FFI 的三个维度及对应手段（MPU / 时间预算与程序流监控 / E2E）。最后补一句"分解是省成本的手段，代价是要额外交一份 DFA 和一份独立性论证，并不是免费的"——这句会让人觉得你真的做过项目而不是背过标准。
05

软件层活动

关键软件活动 · Method Requirement Tables · 典型 SW Architectural Constraints

Part 6 是软件工程师 90% 时间待的地方。它的结构与 V 模型的软件段一一对应：软件安全需求 → 软件架构设计 → 软件单元设计与实现 → 软件单元验证 → 软件集成与验证 → 软件层面安全需求验证。每一步都配一张或几张方法推荐度表，这就是 26262 对软件最主要的约束形式。

方法推荐度表怎么用（这是全篇最实用的一节）

26262 几乎不说"你必须用某个技术"，它说的是"对 ASIL X，这个方法的推荐度是 ++ / + / o"。三个符号的准确含义：

符号英文实际含义不采用会怎样
++highly recommended强烈推荐。默认就该做可以不做，但必须写出充分的理由并通过评审；评估人会重点盯这里，理由不充分就是不合格项
+recommended推荐。做了加分，不做要说明说明的门槛低一些，但仍要有记录
ono recommendation既不推荐也不反对——标准对此不表态自由选择，不需要理由
这里有一个流传极广的误解要纠正：ISO 26262 的方法表里没有"不推荐"这一档。只有 ++ / + / o 三档（IEC 61508 才有明确的"不推荐 NR"）。所以严格来说，标准从来没有"禁止动态内存"——它是通过其它要求间接把动态内存挤出去的：可用内存与执行时间要能被分析、要避免不确定行为、要满足编码规范（而 MISRA / AUTOSAR C++ 明确禁止运行期动态分配）。
这个区分在面试里能拉开差距：说"标准禁止 new"是二手知识，说"标准要求资源用量可分析，而动态分配让这件事做不到，落地到编码规范上就成了禁止"才是理解。

再有一个常被忽略的机制：可以用等效方法替代。表里列的方法不采用，你可以论证"我用了方法 Y，它达到了同等或更好的效果"。这条在实践里非常有用——比如表里推荐"半形式化验证"，你用了带前后置条件的契约式设计 + 形式化静态分析工具，完全可以论证等效。

面试里问到"你怎么用 Part 6 的表"，标准答法是三步：① 项目启动时把相关 ASIL 那一列全部抄进"方法采纳矩阵"，逐项标记"采用 / 用等效方法替代 / 不采用+理由"；② 这份矩阵进安全计划，由确认评审通过；③ 项目过程中它是自查清单，交付时它是 Safety Case 的一节。关键是说出"矩阵"这个交付物——很多人只知道有表，不知道要落成一份可评审的文档。

软件架构设计的硬约束

标准对软件架构的原则性要求（分层、限制规模与复杂度、接口明确、限制耦合等），落到 C++ 项目上是这么几条可执行的规矩：

要求典型量化门槛（项目自定，需写进编码/设计规范）底层理由
层次化结构分层清晰、禁止反向依赖（下层不得引用上层）、禁止跨层调用让变更影响分析可做。层次乱了，"改这一行会影响哪些安全需求"就无法回答
限制组件与函数规模函数常见门槛：≤ 50–100 行；单文件 ≤ 1000 行规模是可验证性的上限。100 行的函数做不到有意义的 MC/DC
限制复杂度圈复杂度（cyclomatic）常见门槛 ≤ 10（部分项目 ASIL D 收到 ≤ 8）圈复杂度直接决定分支覆盖所需的用例数量；也与缺陷密度强相关
接口规模受限函数参数 ≤ 5–7 个；避免 void* 与可变参数参数多 → 组合爆炸 → 基于需求的测试写不全
无递归直接与间接递归一律禁止（静态分析可强制）栈使用量必须能静态求出上界。递归让这个上界不可判定
循环边界确定所有循环有可静态确定的最大迭代次数WCET 分析的前提。while (!done) 这种在 WCET 工具里直接算不出来
无运行期动态内存全静态分配 / 启动期一次性分配 / 定容池三个理由叠加：分配时间不确定（时序）、可能失败且失败路径难测（可靠性）、碎片化随运行时间恶化（长期行为不可分析）
调度与时序设计显式化任务清单、周期、优先级、WCET 预算、最坏响应时间分析都要在架构文档里右臂的集成验证要拿实测值和这份预算对账
初始化顺序确定禁止依赖跨编译单元的静态初始化顺序C++ 的静态初始化顺序在跨 TU 时未定义，这是经典的"在某个编译器版本上突然崩"

"不用动态内存"在 C++ 里到底怎么写？这是新人最实际的疑问。答案是定容容器：

/* ❌ 车规项目里过不了：容量不可知、分配可能失败、时序不确定 */
std::vector<Object> filterObjects(const Input& in) {
    std::vector<Object> out;          // 堆分配
    for (auto& o : in) { if (keep(o)) out.push_back(o); }  // 可能多次重分配
    return out;
}

/* ✅ 定容容器：容量在编译期确定，无堆，溢出是显式的可测行为 */
template <typename T, std::size_t N>
class StaticVector {
public:
    /* 满了返回 false，绝不抛异常、绝不申请内存 */
    bool push_back(const T& v) noexcept {
        if (size_ >= N) { return false; }
        buf_[size_] = v;
        ++size_;
        return true;
    }
    std::size_t size() const noexcept { return size_; }
    const T& operator[](std::size_t i) const noexcept { return buf_[i]; }
private:
    T           buf_[N]{};   // 就地存储
    std::size_t size_{0U};
};

/* 用法：容量 N 不是随便填的，它必须由一条需求或一份分析支撑 */
// SWSR-PER-0031: 单帧最多处理 64 个目标（超出的按距离截断）
using ObjectBuffer = StaticVector<Object, 64>;

ObjectBuffer filterObjects(const Input& in) noexcept {
    ObjectBuffer out;
    for (std::size_t i = 0U; i < in.size(); ++i) {   // 循环上界来自 in 的定容
        if (keep(in[i]) && !out.push_back(in[i])) {
            diag_.report(Diag::kObjectBufferFull);  // ★ 溢出必须可观测
            break;
        }
    }
    return out;
}
注意 diag_.report() 那一行。"容量不够"这件事本身必须是一个可诊断、可测试的事件，而不是静悄悄截断。评审时的问法是："N=64 这个数字从哪来？超过 64 的场景真的不会出现吗？如果出现了，系统的行为是什么、这个行为安全吗？"三个问题都要有答案。

安全机制清单：这才是"安全代码"长什么样

ISO 26262 反复出现"安全机制（safety mechanism）"这个词。它不是抽象概念，就是下面这几类具体代码。一个 ASIL C/D 组件里，安全机制的代码量常占三到五成——新人第一次看车规代码库最直观的震惊往往就是这个比例。

安全机制检测什么失效覆盖的 FFI 维度典型检测时间
窗口看门狗任务卡死、跑飞、执行过快（如跳过了等待）时间与执行一个看门狗周期（常见 10–100 ms）
程序流监控执行路径异常：跳过了某段代码、顺序错乱时间与执行一个监控周期
CRC / E2E 保护数据在传输或存储中被破坏、丢失、重复、过期信息交换下一次接收（一个通信周期）
双通道比较（含多样性）计算结果错误（含系统性错误，若有算法多样性）—（这是功能监控）一个控制周期
范围检查数值超出物理/接口定义的可能范围—立即
合理性检查数值在范围内但与其它信号矛盾（物理上不可能）—立即或几个周期
RAM / ROM 自检存储器位翻转、Flash 退化内存启动时全量 + 运行期分片轮检
MPU 分区非法内存访问内存立即（硬件异常）

① 窗口看门狗 vs 程序流监控——两件不同的事

这是面试高频混淆点。普通看门狗只问"你还活着吗"；窗口看门狗还问"你的节奏对吗"；程序流监控问的是"你走的路径对吗"。三者互补，不可替代。

/* ---------- ① 窗口看门狗：喂太晚会 reset，喂太早也会 reset ---------- */

/* 为什么"太早"也算故障？考虑这个失效：
 *   周期任务本该 10 ms 跑一次，但一个循环变量被位翻转破坏，
 *   任务变成 1 ms 跑一次。功能输出仍然"看起来正常"，
 *   普通看门狗完全不会报警——因为它被喂得更勤了。
 *   窗口看门狗把喂狗时刻限制在 [t_min, t_max] 内，才能抓到它。 */

constexpr uint32_t kPeriodMs   = 10U;
constexpr uint32_t kWindowOpen  = 8U;   // 早于 8 ms 喂 → 太快
constexpr uint32_t kWindowClose = 12U;  // 晚于 12 ms 喂 → 太慢

/* 硬件窗口看门狗（内置或外部芯片）自己判窗口，
 * 软件侧要做的是【只在所有子任务都确认完成后】才喂 */
void taskMonitor10ms() noexcept
{
    /* ❌ 绝对不要这样写：喂狗放在独立的高优先级任务里、
     *    或者放在中断里无条件喂。这叫「喂狗给自己听」——
     *    功能任务全死了，看门狗照样被喂，机制形同虚设。 */

    /* ✅ 收集所有被监控任务的「本周期已完成」标记 */
    const uint32_t alive = aliveFlags_.fetchAndClear();
    if (alive == kAllTasksMask) {
        wdg_.refresh();          // 只有全员到齐才喂
    }
    /* 不喂 → 硬件在窗口关闭后触发复位或外部使能切断。
     * 注意：复位不是"安全状态"，复位期间执行器必须由硬件保持无害
     *       （常见做法：使能信号是"需要持续脉冲维持"的，MCU 一死就自动断） */
}
/* ---------- ② 程序流监控：校验执行路径的签名与时间窗 ---------- */

/* 思路：在关键路径上埋检查点，每个检查点把一个唯一值异或/累加进
 * 一个签名变量；周期末把签名和期望值比对。
 * 能抓到：跳过了一段代码、执行顺序错乱、意外的分支。 */

enum class Cp : uint32_t {   // 检查点 ID 取「汉明距离较大」的值，
    kAcquire  = 0x5A3C1E7BU,     // 避免单个位翻转恰好变成另一个合法 ID
    kValidate = 0xA5C3E184U,
    kCompute  = 0x3C5A7B1EU,
    kActuate  = 0xC3A5841EU,
};

class FlowMonitor {
public:
    void begin()             noexcept { sig_ = kSeed; t0_ = nowUs(); }
    void mark(Cp cp)         noexcept {
        sig_ = rotl(sig_, 7) ^ static_cast<uint32_t>(cp);
        /* rotl 让签名对【顺序】敏感：单纯异或的话 A→B 和 B→A 同值 */
    }
    bool end(uint32_t expected) noexcept {
        const uint32_t dt = nowUs() - t0_;
        return (sig_ == expected)          // 路径对
            && (dt >= kMinUs) && (dt <= kMaxUs);  // 且耗时在窗口内
    }
private:
    uint32_t sig_{0U};
    uint32_t t0_{0U};
};

void controlLoop() noexcept
{
    flow_.begin();
    acquire();   flow_.mark(Cp::kAcquire);
    validate();  flow_.mark(Cp::kValidate);
    compute();   flow_.mark(Cp::kCompute);
    actuate();   flow_.mark(Cp::kActuate);

    if (!flow_.end(kExpectedSignature)) {   // 期望值由构建期工具算出
        enterSafeState(SafeState::kActuatorCutoff);
    } else {
        aliveFlags_.set(kMaskControlLoop);   // 才允许参与喂狗
    }
}
更强的一种形式是问答式（challenge-response）外部看门狗：外部芯片周期性发一个随机数（challenge），MCU 必须用与被监控逻辑相关的方式算出应答（response）——比如需要遍历一遍程序流签名才能算对。这样"喂狗"这个动作本身就无法被一个失控的定时中断伪造。ASIL D 的单 MCU 方案里这几乎是标配，芯片厂的功能安全配套 PMIC 通常自带这个功能。

③ CRC 与 E2E 保护

CRC 只解决"数据有没有被改坏"。但通信链路的失效模式远不止损坏——还有丢失、重复、乱序、过期、以及"串线"（收到了本该发给别人的报文）。所以 AUTOSAR 定义了 E2E（End-to-End）保护，把四件东西打包：

要素挡住什么为什么单靠 CRC 不够
CRC比特损坏—
序列计数器丢失、重复、乱序一个"完好但过期"的旧帧 CRC 是正确的
数据 ID（参与 CRC 计算）串线 / 寻址错误另一条报文恰好长度相同、CRC 也自洽
超时监控发送方彻底静默没有报文就没有 CRC 可校验——"什么都没收到"必须被当成故障

AUTOSAR 的 E2E 规范定义了多个 profile，差别主要在 CRC 宽度、计数器宽度和数据 ID 的编码方式——例如较早的 Profile 1 用 8 位 CRC + 4 位计数器，Profile 5 用 16 位 CRC + 8 位计数器，面向大报文的 Profile 7 用更宽的 CRC 与计数器。选哪个由报文长度与目标残余错误率决定，这是要写进技术安全概念的一个论证（8 位 CRC 在长报文上的漏检率明显不够用）。

/* E2E 保护的收发骨架（逻辑与 AUTOSAR E2E 一致，接口简化） */

struct E2EHeader {
    uint16_t crc;       // 覆盖 counter + payload + dataId（dataId 不上线）
    uint8_t  counter;   // 每帧 +1，回绕
};

/* ---- 发送侧 ---- */
void sendTorqueRequest(int16_t torqueNm) noexcept
{
    Frame f{};
    f.payload.torqueNm = torqueNm;
    f.hdr.counter      = txCounter_;
    txCounter_         = static_cast<uint8_t>(txCounter_ + 1U);

    /* Data ID 参与计算但【不随报文发送】：
     * 收发双方各自用自己配置的 ID，串线时 CRC 天然对不上。 */
    f.hdr.crc = crc16(kDataIdTorqueReq, f.hdr.counter, f.payload);
    bus_.transmit(f);
}

/* ---- 接收侧 ---- */
E2EStatus receiveTorqueRequest(int16_t& out) noexcept
{
    Frame f{};
    if (!bus_.receive(f)) {
        /* ④ 超时：连续 kMaxLostFrames 帧没收到 → 判故障 */
        if (++lostFrames_ > kMaxLostFrames) { return E2EStatus::kTimeout; }
        return E2EStatus::kNoNewData;      // 还在容忍窗口内，用上一帧
    }
    lostFrames_ = 0U;

    /* ① + ③ CRC（含 Data ID）：损坏与串线一起挡 */
    if (f.hdr.crc != crc16(kDataIdTorqueReq, f.hdr.counter, f.payload)) {
        return E2EStatus::kCrcError;
    }

    /* ② 计数器：区分重复、丢帧、乱序 */
    const uint8_t delta = static_cast<uint8_t>(f.hdr.counter - rxCounter_);
    rxCounter_ = f.hdr.counter;
    if (delta == 0U)                  { return E2EStatus::kRepeated; }
    if (delta > kMaxCounterJump)     { return E2EStatus::kWrongSequence; }

    out = f.payload.torqueNm;
    return E2EStatus::kOk;
}
最常见的 E2E 实现错误：把 kNoNewData 当成 kOk 处理。"这一帧没来，我先用上一帧"在一两帧内是合理的降级，但如果不计数、不设上限，发送方彻底死掉时接收方会永远拿着一个陈旧值继续控制——而且所有 CRC 校验都是通过的，日志里干干净净。这类 bug 只能靠故障注入测试发现（§8），代码评审基本看不出来，因为每一行单独看都是对的。

④ 双通道 / 多样性冗余与比较

冗余分两种，价值完全不同：

  • 同构冗余（同一份代码跑两遍、或两颗一样的核跑同一份代码）：只能挡随机硬件失效（位翻转、瞬态干扰）。挡不住软件 bug——同样的输入，同样的 bug，两边错得一模一样。锁步核（lockstep）属于这一类。
  • 多样性冗余（不同算法、不同数据类型、不同工程师、极端情况下不同编译器）：能挡一部分系统性失效，但成本高，且"多样性到底有多大"很难量化论证。
/* 双通道 + 多样性比较：注意三个刻意的设计选择 */

class TorqueArbiter {   // ★ 这个类是 ASIL D（分解不降低仲裁的 ASIL）
public:
    Output step(const Input& in) noexcept
    {
        /* ① 多样性：主通道用查表插值（float），
         *    监控通道用保守的解析包络（定点整数）。
         *    不同数值表示 → 同一个溢出/舍入 bug 不会同时出现。 */
        const int32_t primaryNm  = primary_.computeTorque(in);
        const Envelope env    = monitor_.allowedEnvelope(in);

        /* ② 比较不是"相等"，是"落在允许包络内 + 容差 + 持续时间"。
         *    只判单次不相等会被噪声频繁误触发 → 误报比漏报更容易搞死项目。 */
        const bool ok = (primaryNm >= env.minNm - kTolNm)
                    && (primaryNm <= env.maxNm + kTolNm);

        deviationCount_ = ok ? 0U : (deviationCount_ + 1U);

        /* ③ 去抖：连续 N 个周期都超差才判故障。
         *    N × 周期 必须【明显小于 FTTI】，这是设计约束不是调参。 */
        if (deviationCount_ >= kMaxDeviationCycles) {
            enterSafeState(SafeState::kActuatorCutoff);
            return Output::safe();
        }
        /* 未判故障时输出【被包络裁剪后】的值，而不是原始值：
         * 这样即使主通道偶发偏离，输出也始终在安全包络内。 */
        return Output{ clamp(primaryNm, env.minNm, env.maxNm) };
    }
private:
    PrimaryPath primary_;
    MonitorPath monitor_;
    uint32_t    deviationCount_{0U};
};
"去抖周期数 × 任务周期 < FTTI"这条不等式是这段代码里最值得说出来的东西。它把一个看似"调参"的常量（kMaxDeviationCycles）变成了可追溯到 HARA 的设计约束：FTTI 是 60 ms、任务周期 10 ms，那么去抖最多 3–4 个周期（还要给故障反应本身留时间）。面试时能把 HARA 的 FTTI 一路推到代码里的一个整数常量，说明你真的走通过整条链路。

⑤ 范围检查 vs 合理性检查

两个词经常被混用，但它们抓的是不同的东西：范围检查看单个信号，合理性检查看信号之间的关系。

/* ---- 范围检查：这个值物理上可能吗？（看单个信号） ---- */
constexpr int16_t kMinTempC = -40;    // 传感器规格下限
constexpr int16_t kMaxTempC = 150;

if ((tempC < kMinTempC) || (tempC > kMaxTempC)) {
    return { 0, Validity::kOutOfRange };   // 传感器/线束/AD 故障
}

/* ---- 合理性检查：这几个值放在一起说得通吗？（看信号关系） ---- */

/* 例 1：四个轮速互相印证。直行时四轮速差不可能超过百分之几，
 *       转弯时按阿克曼几何有确定的关系。 */
const int32_t spread = maxOf4(ws) - minOf4(ws);
if (spread > allowedSpread(steeringAngle, vehicleSpeed)) {
    diag_.report(Diag::kWheelSpeedImplausible);
}

/* 例 2：变化率（梯度）检查——值在范围内，但跳变在物理上不可能。
 *       水温 1 个周期内涨 40 °C：传感器没坏，是信号被干扰或 AD 读错。 */
if (absDiff(tempC, lastTempC_) > kMaxTempStepPerCycle) {
    diag_.report(Diag::kTempGradientImplausible);
}

/* 例 3：跨信号一致性——踏板没踩、车速在升，却收到了制动力矩请求。
 *       每个信号单独看都合法，组合起来说明上游逻辑出了问题。 */
if ((brakeRequestNm > kNoiseNm) && (pedalPct < kPedalDeadband)
    && !adasActive && !escActive) {
    enterSafeState(SafeState::kActuatorCutoff);   // 非预期制动 → §2 例 1
}

合理性检查是监控通道的主要武器：它不需要重新实现整个功能（那就等于两份同样贵的代码），只需要用少量、简单、易验证的物理约束把主通道的输出圈在一个安全包络里。"监控器要比被监控的功能简单一个数量级"——这是这个模式能省钱的根本原因，也是评审时判断监控器设计好坏的第一直觉。

某电驱项目的监控通道最初被设计成"用另一套控制算法重算一遍力矩再比较"，代码量做到了主通道的 60%，验证成本几乎翻倍，而且两套算法在弱磁区的正常差异导致误报频发，标定组花了两个月调容差。最终重构为"基于踏板开度、车速、挡位的静态包络表 + 变化率限制"，监控通道从约 12000 行降到约 900 行，误报消失，MC/DC 覆盖也变得可行。监控器写复杂了，是这个模式最典型的失败方式。
06

Coding Guideline 强制

规则等级 · 典型 MISRA C++ 2023 规则 · 静态分析工具 · Deviation 流程

Part 6 要求源代码遵循一份编码规范（coding guideline），并且明确说该规范应覆盖若干主题：语言子集的限定、强类型、防御性实现、结构化编程、可读性与可维护性。标准本身不提供规则清单——它推荐你采用一份行业公认的规范。C++ 项目在实践中就是 MISRA 与 AUTOSAR 这两条线。

规范谱系：为什么现在是 MISRA C++:2023

MISRA C++:2008面向 C++03
→
AUTOSAR C++142017 起，面向 C++14
→
合并AUTOSAR 把规范移交 MISRA
→
MISRA C++:2023面向 C++17，两者的继任者

这条演进线值得讲清楚，因为它解释了很多项目现状：

  • MISRA C++:2008 针对 C++03。它诞生时 auto、lambda、移动语义、constexpr 都还不存在，所以里面有相当一部分规则在现代 C++ 下已经过时甚至有害（最著名的是"函数只能有单一出口"，它会逼你写出深嵌套的 if，反而更难验证）。
  • AUTOSAR C++14 编码指南（2017 年起发布，随 Adaptive Platform 迭代）填补了 C++11/14 的空白，规则数量在三百多条量级，并且每条都标注了"能否被静态分析自动检查"。它是过去几年新项目的主流选择。
  • 大约在 2021–2023 年，AUTOSAR 把 C++ 编码指南移交给 MISRA，两条线合并成 MISRA C++:2023，目标语言是 C++17。合并时删掉了大量"编译器警告或类型系统已能保证"的重复条目，也修正了 2008 版里那些过时规则。
保守表述：各版本的确切规则条数各处引用互相打架（不同来源对"规则 / 指令 / 子条款"的计数口径不同），本文不给精确数字，只给量级。同理，本文不引用具体的规则编号——MISRA C++:2008、AUTOSAR C++14、MISRA C++:2023 三套编号互不相同，凭记忆写编号是这个领域最容易出错的地方。下面一律按规则内容描述；你项目里对应的编号请查你们采用的那一版原文。

规则的分类与义务等级

类别含义能不能偏离
Mandatory（强制）违反必然是错误（多数对应明确的未定义行为）不允许偏离。发现即必须改
Required（要求）默认必须遵守允许，但要走完整的偏离（deviation）流程
Advisory（建议）推荐遵守允许，手续较轻（通常记录理由即可，项目可自定门槛）
Directive（指令）不能只看代码判定，需要结合设计文档与流程（如"所有代码应可追溯到需求"）无法完全自动检查，靠评审

另一个正交的维度是可自动化程度：Automated（工具能完全判定）/ Partially automated（工具报候选，人来确认）/ Non-automated（只能人工评审）。这个标注很实用——它直接告诉你哪些规则可以进 CI 门禁，哪些必须列进代码评审的 checklist。

八组「违规 ❌ / 合规 ✅」对照，以及每条禁令的真实理由

下面每一组都先给理由再给代码。如果你只记住"标准说不行"，那么遇到规范没覆盖的新写法你就不知道该怎么判断了。

① 禁运行期动态内存

四个理由，一个比一个硬：

  1. 分配时间不可预测：分配器要遍历空闲链表，耗时取决于堆的历史状态。WCET 分析对它给不出有意义的上界。
  2. 失败路径难以验证：new 失败要么抛 std::bad_alloc（异常也被禁），要么返回 nullptr——这条路径在实验室里几乎测不到，却是最危险的路径。
  3. 碎片化是时间的函数：一个 ECU 可能连续运行几周不重启，车辆生命周期是 10–15 年。碎片化在实验室的 8 小时测试里根本不会显现。
  4. 堆是全局共享资源，直接破坏 FFI：一个 QM 组件泄漏内存，会让同进程里的 ASIL 组件分配失败。这一条最少被提起，但在评审里杀伤力最大——它把一个"性能问题"变成了"分解论证不成立"。
/* ❌ 违规：运行期分配 + 隐式分配（std::string / std::function 都会分配） */
class DiagLogger {
    std::string                 prefix_;      // 可能堆分配（超过 SSO 阈值时）
    std::function<void(int)>   sink_;        // 捕获过大时堆分配
public:
    void log(const std::string& msg) {          // 每次调用都可能分配
        buffer_.push_back(prefix_ + msg);        // 拼接 + vector 扩容
    }
    std::vector<std::string> buffer_;
};

/* ✅ 合规：容量编译期确定、无隐式分配、溢出可诊断 */
template <std::size_t N>
using FixedString = StaticVector<char, N>;

class DiagLogger {
    static constexpr std::size_t kMaxMsg  = 64U;
    static constexpr std::size_t kRingSize = 32U;

    FixedString<kMaxMsg> ring_[kRingSize]{};
    std::size_t          head_{0U};
    uint32_t             dropped_{0U};   // ★ 丢弃计数是可观测的诊断量

public:
    /* 传 span 而不是 string：调用方不需要分配，被调方也不需要 */
    void log(Span<const char> msg) noexcept {
        if (msg.size() > kMaxMsg) { ++dropped_; return; }
        copyInto(ring_[head_], msg);
        head_ = (head_ + 1U) % kRingSize;   // 环形覆盖，永不增长
    }
};
常见误区：以为"我不写 new 就没有动态内存"。std::string、std::vector、std::function、std::shared_ptr、std::map、以及某些实现里的 std::sort（会为 introsort 的栈准备空间）都可能分配。正确做法是在链接期堵死：把 operator new / malloc 定义成一个直接进安全状态的桩，或者用链接脚本让引用它们的符号解析失败——这样"不小心引入了分配"会在构建时暴露，而不是在路试时。

② 禁异常

理由也不是"异常慢"（正常路径上零成本实现确实几乎没开销），而是：

  • 抛出路径的时间不可预测：栈展开要查 unwind 表、逐帧调用析构函数，耗时取决于调用深度和对象数量。WCET 给不出上界。
  • 控制流不可见：任何一个可能抛出的调用都是一条隐藏的分支。这直接和"结构覆盖率"打架——你的分支覆盖率报告里根本看不到这些边。
  • 实现依赖运行期支持：unwinder、类型信息、异常表都要被信任。这些是运行时库的一部分，在工具认证里是额外负担。
  • 和禁动态内存冲突：某些实现分配异常对象需要堆。
/* ❌ 违规：错误通过异常传播 */
Torque computeTorque(const Input& in) {
    if (!in.valid()) { throw InvalidInput{}; }   // 隐藏控制流
    return lookup(in);                             // lookup 也可能抛
}

/* ✅ 合规：显式返回值 + noexcept + [[nodiscard]]，错误不能被忽略 */
enum class TorqueError : uint8_t { kNone, kInvalidInput, kOutOfRange };

struct TorqueResult {
    Torque      value;
    TorqueError error;
    constexpr bool ok() const noexcept { return error == TorqueError::kNone; }
};

[[nodiscard]] TorqueResult computeTorque(const Input& in) noexcept
{
    if (!in.valid()) { return { Torque{}, TorqueError::kInvalidInput }; }
    const Torque t = lookup(in);
    if (!inRange(t))  { return { Torque{}, TorqueError::kOutOfRange   }; }
    return { t, TorqueError::kNone };
}

/* 构建侧一起堵死：-fno-exceptions -fno-rtti
 * 顺带说清一个副作用：禁异常后，构造函数不能报错，
 * 所以车规代码普遍用「两段式初始化」——构造函数只做不会失败的事，
 * 真正的初始化放在返回错误码的 init() 里。 */

③ 禁 RTTI 与 dynamic_cast

dynamic_cast 的执行时间取决于继承图的形状（多重继承时要走类型图搜索），不是常数时间；typeid 需要在镜像里保留类型信息，增大 Flash 占用。更本质的问题是：需要在运行期问"你到底是什么类型"，说明系统的行为没有被静态确定——这与"可分析"的总要求冲突。

/* ❌ 违规：运行期类型查询 */
void handle(Sensor* s) {
    if (auto* w = dynamic_cast<WheelSensor*>(s)) { useWheel(w); }
    else if (auto* y = dynamic_cast<YawSensor*>(s)) { useYaw(y); }
    // 漏了某个派生类？编译器不会告诉你。
}

/* ✅ 合规 A：把分支交给虚函数——多态本来就是干这个的 */
class Sensor {
public:
    virtual void accept(Handler& h) const noexcept = 0;
    virtual ~Sensor() noexcept = default;
};

/* ✅ 合规 B（更常见）：闭集类型用带标签的联合，
 *   switch 上没有 default，漏掉新枚举值会被 -Werror=switch 挡下 */
enum class SensorKind : uint8_t { kWheel, kYaw, kSteerAngle };

void handle(const SensorView& s) noexcept {
    switch (s.kind) {
        case SensorKind::kWheel:      useWheel(s.wheel);   break;
        case SensorKind::kYaw:        useYaw(s.yaw);       break;
        case SensorKind::kSteerAngle: useSteer(s.steer);   break;
        /* 编译期穷尽 > 运行期查询：新增一种传感器 → 编译失败 → 不可能漏 */
    }
}

④ 限制模板（不是禁止）

模板在 AUTOSAR C++14 与 MISRA C++:2023 里都是允许但受约束的。约束的理由：

  • 代码膨胀：每个实例化产生一份代码。Flash 与栈预算是硬约束，一个不小心的 template<int N> 能生成几十份。
  • 覆盖率与追溯的对应关系变复杂：覆盖率报告里一行源码对应多个实例化，"这一行覆盖了吗"这个问题不再有唯一答案——工具得按实例化分别统计，而不同工具做法不同。
  • SFINAE / 复杂偏特化让"实际调用的是哪一份"难以静态确定，评审时人也读不出来。
/* ❌ 违规倾向：非类型模板参数 + 复杂 SFINAE，膨胀且不可读 */
template <int Gain, typename T,
          typename = std::enable_if_t<std::is_arithmetic<T>::value>>
T scale(T v) { return v * Gain; }
// scale<3>, scale<5>, scale<7>… 每个 Gain 一份代码

/* ✅ 合规：类型参数化保留（这是模板的价值），
 *   数值参数改成普通函数参数（避免按值膨胀），
 *   约束用简单明确的 static_assert（错误信息人能看懂） */
template <typename T>
constexpr T scale(T v, T gain) noexcept {
    static_assert(std::is_integral<T>::value,
                  "scale() 仅用于整型：浮点在本项目需走定点接口");
    return v * gain;
}
/* 项目规范里常见的量化门槛：模板嵌套深度 ≤ 3、
   禁止递归模板实例化、禁止在安全相关路径上用可变参数模板 */

⑤ 限制多重继承

菱形继承带来虚基类，虚基类带来复杂的对象布局、构造顺序和指针调整。多数车规规范的落地形式是：最多继承一个"实现基类"，其余基类必须是纯接口（无数据成员、只有纯虚函数）。

/* ❌ 违规：两个都带状态的基类 → 菱形 + 布局复杂 + 构造顺序陷阱 */
class Timer   { uint32_t tick_; public: void start(); };
class Logger  { Buffer   buf_;  public: void log();   };
class Monitor : public Timer, public Logger { };   // ★ 两个实现基类

/* ✅ 合规：一个实现基类 + 若干纯接口；状态用组合而非继承 */
class ITickable {                  // 纯接口：无数据成员
public:
    virtual void onTick() noexcept = 0;
    virtual ~ITickable() noexcept = default;
};
class IDiagnosable {               // 纯接口
public:
    virtual DiagStatus status() const noexcept = 0;
    virtual ~IDiagnosable() noexcept = default;
};

class Monitor final : public ITickable, public IDiagnosable {
    Timer  timer_;    // ★ 组合，不是继承
    Logger logger_;
public:
    void onTick() noexcept override;              // override 是强制要求
    DiagStatus status() const noexcept override;
};
/* 顺带：类不再被继承就标 final，虚函数一律 override —— 
   这两条几乎所有车规规范都是 required，因为它们把
   「我以为我覆写了但其实新建了一个函数」这类错误变成编译错误。 */

⑥ 禁 C 风格强制转换与危险的类型双关

/* ❌ 违规：C 风格 cast 掩盖了到底发生了什么 */
void parse(uint8_t* raw) {
    Header* h = (Header*)raw;      // reinterpret + 可能去 const + 对齐 UB
    int v = (int)h->value;         // 窄化，可能丢位
}

/* ✅ 合规：显式意图 + 显式复制，不做类型双关 */
void parse(Span<const uint8_t> raw) noexcept {
    if (raw.size() < sizeof(Header)) { return; }   // 先查长度

    Header h{};
    /* 用 memcpy 做字节复制：不违反严格别名、不依赖对齐，
       优化后通常和一次加载指令等价 —— 零成本且合规 */
    std::memcpy(&h, raw.data(), sizeof(h));

    /* 窄化必须显式，并且先检查值域 */
    if (h.value > std::numeric_limits<int16_t>::max()) { return; }
    const auto v = static_cast<int16_t>(h.value);
}

⑦ 禁隐式转换与"裸"基本类型

整型提升与隐式转换是嵌入式里最阴的一类 bug：它不报错、不崩溃，只是算错。

/* ❌ 违规：混合有无符号 + 依赖隐式提升 */
uint16_t a = 40000U;
uint16_t b = 30000U;
uint16_t sum = a + b;          // a+b 提升为 int(70000) 再截断成 4464

int n = -1;
if (n < buf.size()) { ... }     // size() 是无符号 → n 变成巨大正数 → 条件为假

void setTorque(int nm);
setTorque(rpm);                // 参数传错也照样编译通过

/* ✅ 合规：固定宽度类型 + 显式转换 + 强类型包装 */
constexpr uint32_t sum = static_cast<uint32_t>(a)
                       + static_cast<uint32_t>(b);   // 意图明确

for (std::size_t i = 0U; i < buf.size(); ++i) { ... }  // 同类型比较

/* 强类型：单位/物理量不同的值不能互相赋值 —— 
   这是标准里「strong typing」那一条在 C++ 里最有价值的落地形式 */
template <typename Tag>
class Quantity {
    int32_t v_;
public:
    explicit constexpr Quantity(int32_t v) noexcept : v_{v} {}
    constexpr int32_t raw() const noexcept { return v_; }
};
using TorqueNm = Quantity<struct TorqueTag>;
using SpeedRpm = Quantity<struct SpeedTag>;

void setTorque(TorqueNm nm) noexcept;
// setTorque(rpm);            ← 编译错误，单位混用被类型系统挡下

⑧ 禁递归 / 禁无界循环

/* ❌ 违规：递归 → 栈深度不可静态求解 */
uint32_t crcTree(const Node* n) {
    if (n == nullptr) { return 0U; }
    return n->crc ^ crcTree(n->left) ^ crcTree(n->right);
}

/* ❌ 违规：无界循环 → WCET 工具算不出上界 */
while (!deviceReady()) { }          // 设备不 ready 就永远卡在这

/* ✅ 合规：显式栈 + 编译期容量；循环带确定上界与超时 */
uint32_t crcTree(const Node* root) noexcept {
    constexpr std::size_t kMaxDepth = 16U;   // 由数据结构设计保证
    StaticVector<const Node*, kMaxDepth> stack;
    uint32_t acc = 0U;

    if (root != nullptr) { static_cast<void>(stack.push_back(root)); }
    while (stack.size() > 0U) {                 // 上界 = 节点总数（有限）
        const Node* n = stack.popBack();
        acc ^= n->crc;
        if ((n->left  != nullptr) && !stack.push_back(n->left)) {
            return kCrcDepthExceeded;            // 溢出是显式错误
        }
        ...
    }
    return acc;
}

/* 忙等一律带超时，并且超时是一条【有需求支撑】的行为 */
for (uint32_t i = 0U; i < kReadyPollMax; ++i) {   // kReadyPollMax × 轮询间隔 < FTTI
    if (deviceReady()) { return Status::kOk; }
    delayUs(kPollUs);
}
return Status::kDeviceTimeout;
这八条的共同结构值得点出来，面试时说一句就能显出层次：它们全都是在把"运行期的不确定性"搬到"编译期或构建期"。动态内存 → 编译期容量；异常 → 显式返回类型；RTTI → 编译期穷尽的 switch；隐式转换 → 强类型；递归 → 显式有界栈。理解了这个共同点，遇到规范没写到的新特性（协程、std::variant、反射）你也能自己判断——问一句"它把什么留到了运行期、那部分能不能被静态分析出上界"。

偏离（Deviation）：什么时候可以违规，要走什么手续

规范不可能永远对。真实项目里合理的偏离场景有三类：

  • 硬件寄存器访问：必须做地址到指针的转换、必须用 volatile、必须做位操作。这几乎是每个项目都有的一批偏离。
  • 第三方 / 供应商代码：芯片厂的 MCAL 驱动、协议栈往往不完全合规。通常的处理是把它们隔离成独立模块，整体走一次"复用论证"而不是逐条偏离。
  • 规则本身在此处适得其反：例如"单一出口"规则会让本可以早返回的函数变成五层嵌套，可读性和可验证性都更差。

手续大致是这五步，每一步都要留下记录：

  1. 提出：写明违反哪条规则、代码位置、为什么必须这么写、有没有合规的替代方案（"没想到别的写法"不是理由，"合规写法会引入更大的风险"才是）。
  2. 风险分析：这条规则本来是为了防什么？在这个具体场景下那个风险有多大？
  3. 补偿措施：既然不合规，用什么别的手段把风险压回去——额外的评审、额外的单元测试、静态断言、运行期检查、形式化验证。这一步是偏离能否被接受的关键。
  4. 批准：安全经理签字；ASIL 高的项目还需要独立评审人参与。
  5. 登记：进偏离台账，并在 Safety Case 中汇总。代码里同步加机器可读的抑制标记，让工具不再重复报。
/* 偏离在代码里的样子：注释不是给人看的，是给审计看的。
   四要素缺一不可：偏离编号、规则、理由、补偿措施。 */

/* DEV-0037: 偏离「禁止整数到指针的转换」
 * 理由    : 访问 MCU 外设寄存器，无合规替代方案
 * 补偿    : ① 地址常量由芯片头文件生成并做 static_assert 校验

static_assert(kAdcBase >= kPeripheralLow && kAdcBase < kPeripheralHigh,
              "ADC 基址不在外设区间内");

// PRQA S 0303 --
最常见的滥用：把抑制标记当成"消警告"的手段。有人为了让 CI 变绿，批量加抑制注释而不走偏离流程。这在功能安全审核里是过程违规，比代码里有几个真实违规严重得多——因为它说明整个流程失效了。正确的门禁设计是：抑制标记必须引用一个存在于偏离台账里的编号，CI 里用脚本交叉校验，引用不存在的编号直接构建失败。
量级参考（经验值，各家差异大）：一个几十万行的 ASIL B/D 代码库，正式登记的偏离通常在几百到几千条量级，但其中绝大多数是同一类偏离的批量实例（寄存器访问、MCAL 复用），真正需要逐条论证的独立偏离往往只有几十条。每条独立偏离从提出到批准的耗时经验上在一到三人天（含评审）。把同类偏离归并成"偏离类别"再批量批准，是控制这块成本最有效的做法——见过项目因为逐条走流程，光偏离评审就吃掉两个月。

工具链认证

Tool Confidence Level (TCL)

这一节回答一个新人几乎必然会问的问题：凭什么我不能把项目的 GCC 从 9 升到 13？答案的完整版就是工具认证。

ISO 26262 Part 8 里有一章专门讲"对软件工具使用的置信度"。它的出发点很朴素：你的安全论证建立在"代码正确"之上，但你交付的是编译器生成的机器码，用的是静态分析工具给出的结论。如果工具会出错，你的整条证据链就有一个未经检验的假设。

类比：法庭上你拿 DNA 报告做证据，对方律师第一件事不是质疑 DNA 理论，而是问"你这台测序仪校准过吗、上次校准是什么时候、校准记录在哪"。仪器未经校准，报告就没有证据效力。编译器和静态分析工具就是功能安全项目里的测序仪。

TI × TD → TCL：一张两行的表

对项目里用到的每一个工具，都要做两个判断：

TI · Tool Impact（工具影响）

  • TI1：这个工具不可能在安全相关产出里引入错误，也不可能漏掉本该检出的错误。
  • TI2：除此以外的所有情况——只要存在可能性就是 TI2。

判 TI1 的门槛比直觉高得多。"我们的编辑器不会改代码"——那自动格式化、自动补全算不算？凡是拿不准的，正规做法是判 TI2 再往下走。

TD · Tool error Detection（工具错误的可检出度）

  • TD1：有高度置信认为工具的失效会被后续活动发现或阻止。
  • TD2：中等置信。
  • TD3：其余情况（低置信）。

注意 TD 说的不是工具本身有多可靠，而是你的流程能不能兜住它。这个区别是本节最有价值的一句话。

TD1（易检出）TD2（中）TD3（难检出）
TI1（无影响）TCL1TCL1TCL1
TI2（有影响）TCL1TCL2TCL3
TCL要求实际负担
TCL1无需额外的工具认证措施只需记录分类理由（TI/TD 的判定依据）
TCL2需要认证；可用的方法有几种，推荐度随 ASIL 变化中等：通常靠供应商的认证包 + 自己补一份使用说明
TCL3需要认证，且对方法的要求最严重：认证版工具 + 完整证据包，或自己做工具确认
这张表里藏着整个工具认证策略的关键：TI2 + TD1 = TCL1，也就是"不需要认证"。而 TI 你改不了（工具就是会影响产出），TD 是你唯一能施加影响的变量。所以行业里真正的做法不是"给所有工具买认证"，而是用流程措施把 TD 推高：
· 编译器可能优化错？→ 目标码级覆盖率、关键模块的生成汇编评审、双编译器交叉比对、HIL 上的黑盒回归。
· 静态分析工具可能漏报？→ 再叠一个不同原理的工具（数据流 + 抽象解释），并用注入已知缺陷的样本集验证它真能报出来。
能把这层说清楚，就说明你理解的是"工具认证的目的"而不是"工具认证的手续"。

四种认证方法

当一个工具落在 TCL2/TCL3，标准给了几条可选路径（推荐度随 ASIL 与 TCL 组合变化，具体请查 Part 8 的表）：

为什么编译器必须被评估：一个具体例子

很多人以为"编译器 bug"很罕见，所以这一条是形式主义。但真正的风险不是编译器有 bug，而是编译器完全按标准行事，却把你的安全检查合法地删掉了：

/* 看起来无懈可击的溢出检查 —— 在 -O2 下这个检查会被整段删除 */
bool willOverflow(int a, int b) {
    return (a + b) < a;          // ★ a + b 已经是有符号溢出 = UB
}                                //   编译器据此推断 a+b >= a 恒成立
                                 //   于是这个函数被优化成 return false;

# 用生成的汇编验证（这是评审时真该做的动作）
$ arm-none-eabi-g++ -O2 -S -o - overflow.cpp | grep -A3 willOverflow
_Z12willOverflowii:
        movs    r0, #0          ← 直接返回 0，检查消失了
        bx      lr

/* ✅ 合规写法：先判条件，不产生溢出 */
bool willOverflow(int32_t a, int32_t b) noexcept {
    if (b > 0) { return a > (std::numeric_limits<int32_t>::max() - b); }
    return a < (std::numeric_limits<int32_t>::min() - b);
}
/* 或者用编译器内建：__builtin_add_overflow（但它是实现扩展，
   要走偏离流程并论证该内建在认证版工具里的行为已被确认） */

这个例子说明三件事：① 源码级评审看不出问题（每一行都"对"）；② 只有目标码级的验证（汇编评审或目标码覆盖率）才能发现；③ 换一个优化等级或换一个编译器版本，行为可能不同——这就是为什么"版本 + 选项"必须被锁定成认证范围的一部分。

Qualified 编译器和普通编译器的差别在哪

差别不在于代码生成质量——认证版编译器生成的代码未必更快更小。差别在它带什么材料：

交付物普通 GCC / Clang认证版编译器
二进制本体✅ 免费✅

市面上常见的认证版工具链包括 Green Hills 的 MULTI/编译器、IAR 的功能安全版、TASKING、Wind River Diab，以及一些基于 GCC / LLVM 做商业化与认证的供应商（例如 HighTec）。Ada 生态里 AdaCore 的 GNAT Pro Assurance 走的也是同一条路。价格量级：单席位每年数千到上万美元，加上认证包与支持，一个团队的年成本容易到几万到十几万美元。（经验量级，各家报价差异很大。）

保守表述：各厂商的认证包叫法不统一——"Tool Qualification Kit"、"Qualification Support Kit"、"Functional Safety Package"、"Safety Manual + Certificate" 都有。本文统称"工具认证包"。选型时要确认的不是名字，而是三件具体内容：覆盖哪个 ASIL、覆盖哪个版本与目标平台、以及安全手册里的使用约束你能不能接受（最后一条最容易被忽略：有些认证只在 -O1 下有效）。

为什么不能随便升级 GCC

把上面所有线索串起来，答案就很清楚了。工具认证的对象不是"GCC"，而是"GCC 12.2.0 + 这一组编译选项 + 这个目标核 + 这份安全手册"。升级版本会同时打破好几件事：

  1. 认证范围失效：证书写的是具体版本号。换版本 = 没有认证。
  2. 安全手册里的约束可能变了：新版本可能引入新的优化 pass，旧手册没有覆盖它的失效模式。
  3. 已知问题清单要重做：新版修了旧 bug，也会引入新 bug。规避措施清单必须重新梳理。
  4. 触发变更影响分析：编译器变了，意味着所有目标码都变了。严格来说这要求重跑全部单元测试、集成测试与目标码覆盖率，并重新出静态分析报告。
  5. WCET 与资源用量基线失效：新版本的内联与展开策略不同，栈用量和执行时间都会变。时序论证要重做。

所以行业做法是工具链冻结（toolchain freeze）：在项目某个里程碑之后锁死版本，直到量产。升级只在两种情况下发生：安全相关的已知缺陷必须修，或者项目周期长到不得不换。无论哪种，它都是一个季度级的独立小项目，要单独排期与预算。

冻结在工程上要落成"可复现构建"，而不是靠口头约定：

测试 + 验证

Coverage / Fault Injection / 形式化验证

先纠正一个根深蒂固的误解：26262 的测试目标不是"找 bug"，而是"生成证据"。这两件事的方法论完全不同。找 bug 追求性价比（哪里最可能有问题就测哪里），生成证据追求可论证的完备性（每一条需求都有对应用例、每一行代码都被解释）。理解这一点，才能理解为什么车规项目的测试量级如此夸张。

两条正交的线：基于需求的测试 + 结构覆盖率

① 基于需求的测试（是主线）

用例从需求推导，不是从代码推导。每条需求至少要有：正常值、边界值、超范围值、以及错误路径的用例。用例文档里必须写明它验证的是哪条需求 ID。

这是唯一能证明"功能被正确实现"的东西。

② 结构覆盖率（是完备性检查）

把①的用例跑一遍，测量代码被执行的程度。覆盖率的作用是反过来暴露①的漏洞——某段代码没被覆盖，说明要么需求漏了、要么测试漏了、要么这段代码本来就不该存在。

最常见的堕落方式：为了凑覆盖率而写测试。工程师看到某个分支没覆盖，就直接构造一组输入把它跑过去，用例里不写验证任何输出、也不关联任何需求。覆盖率报告变绿了，但它什么都没证明——你只是执行了代码，没有检查行为。评审里这类"覆盖率用例"一眼就能看出来（断言少、无需求追溯），是过程失效的强信号。
正确顺序永远是：先按需求写用例 → 测量覆盖率 → 分析未覆盖的原因 → 补需求或补用例（或删代码）。

软件架构层面另有一组（函数覆盖、函数调用覆盖），推荐度大致是 ASIL A/B 为 +、C/D 为 ++。

很多人第一次看这张表会疑惑：为什么语句覆盖在 ASIL C/D 上反而只是 +？不是要求降低了——而是分支覆盖蕴含语句覆盖，MC/DC 蕴含分支覆盖。高 ASIL 已经被更强的指标约束了，再单独强调弱指标没有意义。这个"包含关系"是理解这张表的钥匙，也是面试里能直接拉分的细节。

MC/DC 到底是什么，为什么它比分支覆盖严格

MC/DC（Modified Condition/Decision Coverage，修正条件/判定覆盖）要求同时满足四条：
① 每个入口与出口都被执行过；
② 每个判定（decision）都取过真和假；
③ 每个条件（condition，即判定里的每个原子布尔子表达式）都取过真和假；
④ 每个条件都被证明能独立地影响判定的结果——即存在一对用例，它们只有这一个条件不同，且判定结果不同。
第 ④ 条是 MC/DC 的全部难度所在。前三条加起来只是"条件覆盖 + 判定覆盖"，那是弱得多的指标。

用一个具体表达式看清楚差别。假设需求是"只有在系统使能、且（踏板被踩下或 ADAS 请求）时，才允许输出制动力矩"：

/* 判定 D，包含 3 个条件 A / B / C */
if (enabled && (pedalPressed || adasRequest)) {
//   ^^^A^^^      ^^^^^B^^^^^     ^^^^C^^^^^ */
    applyBrake();
}

分支覆盖只要 2 个用例就能到 100%：一个让 D 为真、一个为假。比如：

用例A enabledB pedalPressedC adasRequestD 结果
TC-x真真假真
TC-y假真假假

分支覆盖 100%、语句覆盖 100%。但看这两个用例：adasRequest 从头到尾都是假。如果 adasRequest 这个变量拼错了、读的是另一个信号、或者永远为假，这两个用例永远发现不了——而它对应的正是"ADAS 请求制动"这条核心功能。这就是分支覆盖的盲区：它只关心整个判定的真假，不关心判定内部每个条件有没有真正起作用。

MC/DC 要求为每个条件找到一对"只有它不同、结果也不同"的用例。对这个表达式，最少需要 4 个用例（N 个条件通常需要 N+1 个）：

用例ABCD它证明了谁的独立影响
TC1真真假真—（基准）
TC2真假假假B：与 TC1 只差 B，结果翻转
TC3真假真真C：与 TC2 只差 C，结果翻转
TC4假真假假A：与 TC1 只差 A，结果翻转

现在 adasRequest 在 TC3 里是唯一让判定为真的原因——它坏了，TC3 必然失败。这就是 MC/DC 买到的东西：它保证每个条件都"真的在起作用"，而不只是"被执行过"。

/* 这 4 个用例写成代码的样子。注意每个用例都：
   ① 关联一条需求；② 有真正的断言；③ 注释写清它证明哪个条件的独立性 */

// @verifies SWSR-BRK-0211  仅在使能且（踏板或 ADAS 请求）时输出制动力矩
TEST(BrakeGate, EnabledAndPedal_Applies) {          // TC1 基准
    EXPECT_TRUE(brakeGate(true,  true,  false));
}
TEST(BrakeGate, PedalIndependence) {                 // TC2：B 独立影响
    EXPECT_FALSE(brakeGate(true, false, false));
}
TEST(BrakeGate, AdasIndependence) {                  // TC3：C 独立影响
    EXPECT_TRUE(brakeGate(true,  false, true));
}
TEST(BrakeGate, EnableIndependence) {                // TC4：A 独立影响
    EXPECT_FALSE(brakeGate(false, true,  false));
}
三个能显出深度的补充点：
① 用例数是 N+1 而不是 2^N。这正是 MC/DC 的设计目的——它想要接近"多条件覆盖"（2^N，完全测不动）的检错能力，但把成本压到线性。10 个条件：多条件覆盖要 1024 个用例，MC/DC 只要 11 个。
② 短路求值让事情变复杂。C++ 的 && / || 会短路，enabled 为假时后面根本不求值。于是业界有两种口径：unique-cause MC/DC（严格要求"只有一个条件变化"）和 masking MC/DC（允许其它条件变化，只要能论证它们被逻辑屏蔽了）。含 &&/|| 的表达式通常只能用 masking 口径。项目必须明确采用哪一种并写进测试策略，否则不同工具算出的覆盖率对不上。
③ MC/DC 会反向压迫设计。一个 8 条件的判定要 9 个用例且极难构造，于是工程师会主动把它拆成几个命名清晰的中间布尔量。这是 MC/DC 最被低估的收益——它让代码变简单了。

故障注入用例的数量常被严重低估。一个中等规模 ASIL D 的 ECU，仅通信与时序两类的故障注入用例就能到数百条量级；加上电气故障，HIL 上跑一轮完整回归要十几到几十小时。所以 HIL 台架永远是稀缺资源，排期冲突是车规项目最典型的进度风险之一。务实做法：把能在 SIL 上做的注入（接口值、时序、通信协议层）尽量前移，HIL 只留真正需要真实硬件的那部分（电气、时钟、ECC）。见过项目因为把所有注入都堆在 HIL 上，台架排期直接决定了项目关键路径。

形式化方法：证明"不会发生"，而不是"没测出来"

测试只能证明存在性（这条路径是对的），证明不了普遍性（所有输入都不会溢出）。形式化方法能给出后者，这是它在 ASIL C/D 上被推荐的原因。

工具技术路线能证明什么代价

务实的用法不是"全项目形式化"（成本失控），而是挑几个小而关键的模块：仲裁逻辑、E2E 校验、状态机、CRC 实现——这些模块通常只有几百行、无动态行为、输入值域清晰，恰好是形式化工具最擅长的形状。而它们又恰好是分解论证里不能降 ASIL 的那部分（§4），投入产出比很高。

被问"测试和形式化验证怎么选"，别答"都要做"。有区分度的答法是按模块形状选：输入值域封闭、无动态内存、循环有界、几百行以内 → 形式化的性价比最高；涉及硬件时序、外设、并发调度 → 只能靠 HIL 与故障注入。再补一句"形式化的主要成本不在跑工具，在给外部接口标值域（stubbing），这部分做不好 Orange 会淹没结论"——这句只有真跑过的人说得出来。

额外成本从哪来：五块

ISO 26262 项目相对同功能的普通项目，多出来的成本可以清楚地分成五块。理解这个分解比记住一个总倍数有用得多，因为只有第一块和第五块是随代码量线性增长的，其余三块有很强的固定成本性质——这直接决定了"小项目做 ASIL 特别不划算"。

成本块具体内容随规模变化经验占比（额外成本中）
① 文档与追溯 安全需求、架构与单元设计文档、测试规格、覆盖率与静态分析报告、追溯矩阵、Safety Case 线性 ~30%–40%
② 评审与确认措施 确认评审、功能安全审核、功能安全评估；独立评审人的工时 半固定（次数与工作产品数相关） ~15%–25%
③ 工具与台架 认证工具链、静态分析、覆盖率工具、HIL 台架、故障注入设备 基本固定（可跨项目摊销） ~15%–25%
④ 外部认证 第三方评估机构的评估费；出证与后续维护 固定 ~5%–15%
⑤ 额外的验证活动 MC/DC 用例、故障注入、back-to-back 测试、形式化验证 线性（且随 ASIL 陡增） ~20%–30%

换成"总工作量是普通项目的几倍"这个更直观的口径（经验倍数，同功能同代码量对比）：

ASIL工作量倍数（相对 QM）主要增量来自哪
QM1.0（基准）—
A约 1.2 – 1.5需求追溯 + 编码规范 + 语句/分支覆盖
B约 1.5 – 2.2+ 分支覆盖强化、防御性实现、确认评审
C约 2.2 – 3.2+ 独立性档位提高、功能安全审核、更强的架构约束

这张倍数表最有价值的用法是反过来用：如果一条 ASIL D 需求可以分解成 B(D) + B(D)（§4），成本从 3–5 倍降到大约 2 × 1.5–2.2 ≈ 3–4.4 倍——看起来省得不多。真正的节省来自监控通道通常只有主通道的十分之一大小：1 × 1.8（主通道，几万行）+ 0.1 × 1.8（监控通道，几百行）≈ 2 倍。
所以"分解为什么省钱"的准确回答不是"两个 B 比一个 D 便宜"，而是"分解让你只需要把一小块代码做到高标准，而不是把整个功能都做到高标准"。面试时能算这笔账，比背 ASIL 分解表有说服力得多。

追溯性矩阵：为什么它是核心交付物

如果只能保住一份交付物，保追溯矩阵。理由有四条，每一条都对应一个具体的项目场景：

  1. 它是 Safety Case 的骨架。安全论证的每一句话都要能点开看到证据；矩阵就是那些超链接。
  2. 它让变更影响分析成为可能。"改这个函数会影响哪些安全需求、要重跑哪些测试"——没有矩阵，这个问题只能靠人的记忆回答，而人会离职。
  3. 它是"多余实现"的探测器。代码里有一段不对应任何需求的逻辑，说明软件行为没有被完整规定（见 §3.4 的四类断链）。
  4. 它是评审员的入口。评估人不会通读你的代码，他会抽样三五条需求，顺着矩阵往下走，看每一环是否闭合。矩阵烂，抽样必挂。

四个最常见的项目管理陷阱

陷阱 1 · 追溯性断链，而且是慢慢断的

没有人会一次性把追溯搞坏。它是这样烂掉的：需求评审后重新编号，代码里的标签没跟着改；某个功能被砍掉，需求删了但代码留着；紧急修 bug 时"先改了再补需求"，然后忘了补。三个月后矩阵里 15% 的链是坏的，而没有人知道。

处方：把追溯校验做成 CI 门禁（见 §3.4 的脚本），断链即构建失败。这条门禁必须在项目第一天就上——等有了 500 条需求再上，第一次运行会报出几百个错误，团队的第一反应会是"把这个门禁关掉"。

陷阱 2 · 变更影响分析缺失

表现是：一个"看起来无害"的重构合并进去，三周后 HIL 上发现某个安全机制不再触发。或者更糟——它触发了，但反应时间从 18 ms 涨到 65 ms，超出了 FTTI，而没有任何测试在盯这个数字。

处方：每个改动必须回答三个问题（可以做成 PR 模板，几分钟就填完）：碰到了哪些安全需求？哪些测试要重跑？资源与时序基线是否变化？并把它自动化到能自动化的程度：

# PR 里自动跑的变更影响分析
$ ./tools/change_impact.py --base main --head HEAD

注意栈峰值那一行。"改了一行代码导致栈超预算"是车规项目里非常真实的事故来源——多一个局部变量、多一层内联，就可能踩到相邻分区。这类基线必须在 PR 级别被盯住，而不是等集成测试。

陷阱 3 · 把安全活动堆到项目末期

这是最致命也最普遍的一个。团队先按熟悉的方式做完功能，打算"最后统一补文档、补覆盖率、走评审"。结果是三重灾难同时发生：

  • 补不出需求：代码已经写完，只能反向编造需求来匹配代码（业内叫 reverse engineering requirements）。这种需求写出来一眼就能看出是倒推的——它们和代码结构一模一样，而真正的需求应该独立于实现。评估人对这个模式极其敏感。
  • 架构改不动：等到分解论证阶段才发现两个通道共享了资源（§4.3 的三类违例），此时重构成本已经是当初的十倍。
  • 覆盖率上不去：为了达标只能写"覆盖率用例"，然后在评审中被识破。

处方就是那句老话 shift safety left，但要落到具体动作上：安全需求与用例在同一个 sprint 内完成（需求、代码、测试、追溯是一个 ticket 的四个交付项，不是四个 ticket）；正式静态分析工具第一天进 CI；评估机构在概念阶段就介入第一次。

陷阱 4 · 把安全团队当成审批部门

组织形态上的陷阱：安全工程师坐在流程末端，开发提交，安全审批。后果是安全团队变成瓶颈与"敌人"，开发学会的是"怎么让文档看起来合规"而不是"怎么把系统做安全"。

处方：安全工程师嵌进开发团队参与设计评审（这与"确认措施需要独立性"不冲突——嵌入的是安全工程支持角色，独立评审人是另一批人）。判断一个组织健康与否有个简单指标：安全相关的设计决策，是在设计讨论里做出的，还是在评审会上被否决后返工做出的。

新人第一周实务清单

如果你明天入职一个 26262 项目，按这个顺序走，比读标准原文快得多：

Day 1–2 · 搞清"我在整条链的哪个位置"
  1. 找到项目的 Item Definition 与 HARA 报告，读你负责的那个功能对应的危害事件。记住它的 ASIL、安全目标、FTTI 和安全状态定义。这四个数字会解释你之后遇到的所有奇怪约束。
  2. 找到 Safety Plan，翻到"方法采纳矩阵"和"确认措施与独立性"两节。前者告诉你项目采纳了哪些方法，后者告诉你谁有权签字。
  3. 问清楚：我负责的模块是什么 ASIL？它是分解出来的吗（有没有括号标记）？它的独立性伙伴是谁？
Day 3–4 · 把工具链跑通，而不是把代码读完
  1. 本地完整构建一次，确认工具版本校验能过（§7.5）。看一眼 tool_inventory，知道自己在用什么、允许哪些编译选项。
  2. 跑一次静态分析（认证工具那个，不是 clang-tidy），看看当前基线有多少违规、偏离台账长什么样。
  3. 跑一次覆盖率，看你的模块要求哪一档（语句/分支/MC-DC），当前差多少。
  4. 提一个最小的 PR（改个注释也行），走完整个流程：追溯校验、变更影响分析、评审。第一周就摸清流程的形状，比第三周才发现"原来每个 PR 要填这个"好得多。
Day 5 · 读三份文档，问三个问题
  1. 读你模块的软件安全需求（不是代码）。逐条问自己："我能为它写出一个会失败的测试吗？"写不出来的条目，去问需求作者。
  2. 读软件架构文档的时序那一节：任务清单、周期、优先级、WCET 与栈预算。把你模块的预算数字记下来。
  3. 读偏离台账。它会告诉你这个项目在哪些地方妥协过、为什么妥协——这是最快理解项目历史的方式。
  4. 三个必问的问题：① 我改代码时哪些基线会被自动检查（栈、WCET、覆盖率、违规数）？② 我模块的安全机制有哪些、故障注入用例在哪？③ 下一次确认评审/评估是什么时候、需要我交什么？
心态上的一条建议：不要把流程当障碍去绕。26262 项目里最快的路径恰恰是"第一次就按流程做完整"——因为返工的代价包含重新评审、重新出报告、重新更新 Safety Case，通常是首次成本的三到五倍。"先写完再补文档"在这里不是省时间，是借高利贷。
见过一个团队在项目中期做过一次很聪明的投资：花两周把"需求 → 代码 → 测试 → 覆盖率"的追溯完全自动化（标签 + CI 校验 + 报告生成）。当时被质疑"这两周不产出功能"。后来的效果是：每次里程碑前准备评审材料的时间从约两周降到半天，一年里发生了四次里程碑，还额外避免了两次因为追溯断链导致的评审不通过。在功能安全项目里，自动化证据生成是投入产出比最高的工程投资，没有第二个。

SOTIF + Cybersecurity 配套

ISO 21448 SOTIF · ISO/SAE 21434 Cybersecurity · 实施现状

ISO 26262 的失效模型有一个很硬的边界：它假设"系统按规格工作"就是安全的，于是只去管"系统没按规格工作"（失效）。这个假设在制动、转向这类功能上完全成立——规格说"踏板踩到底就出最大制动力"，照做就是对的。

但到了 ADAS 与自动驾驶，这个假设塌了：规格本身可能是不充分的。"识别前方行人"这条规格，无论怎么写都无法穷尽真实世界的光照、遮挡、异形物体。系统完全按规格工作，仍然可能撞人。这就是 SOTIF 要解决的问题。

ISO 21448（SOTIF）：系统没坏，但行为不安全

SOTIF（Safety Of The Intended Functionality，预期功能安全，ISO 21448:2022）关注的是在没有故障的前提下，由功能不足（functional insufficiency）和触发条件（triggering condition）共同导致的危害。
· 功能不足：算法/传感器的固有性能局限，例如毫米波雷达对静止金属物的分辨能力、摄像头的动态范围。
· 触发条件：把这个局限暴露出来的具体场景，例如"逆光 + 白色车厢 + 高速接近"。
两者必须同时出现才构成危害——这也是 SOTIF 分析的基本结构。

SOTIF 的方法论核心是一张"四象限"图，理解了它就理解了整个标准在干什么：

安全不安全
已知场景 区域 1：已知且安全
目标：尽量扩大		 区域 2：已知的不安全场景
目标：通过改进功能或限制 ODD 转成区域 1
未知场景 区域 4：未知但恰好安全 区域 3：未知的不安全场景
目标：通过大量场景探索把它挖出来，变成区域 2 再消除

区域 3 是 SOTIF 的全部难点——你要证明"我不知道的危险场景已经足够少了"。这在方法论上和功能安全完全不同：功能安全靠"分析失效模式 + 加安全机制"，SOTIF 只能靠大规模场景收集、仿真、真实路测里程、以及统计论证。这也是为什么自动驾驶公司要跑几千万公里、要建场景库、要做影子模式（shadow mode）。

维度ISO 26262（功能安全）ISO 21448（SOTIF）
触发原因E/E 系统失效（随机硬件失效 + 系统性缺陷）功能不足 + 触发条件；系统无失效

两者在同一个功能上是叠加而非二选一。以 AEB 为例：
· "本该刹车时因为 MCU 故障没刹" → 26262，用双通道 + 看门狗解决；
· "本该刹车但感知没识别出目标" → SOTIF，用传感器融合 + 场景库解决；
· "不该刹车却误刹（井盖、桥下阴影）" → 两者都要看：如果是失效导致的误触发归 26262，如果是感知误识别归 SOTIF。
能把同一个功能按这三种方式切开，说明你真的分清了边界。

SOTIF 落到代码上最典型的形态，是把"我不确定"变成一等公民：

/* ❌ 典型的"只有功能安全思维"的接口：结果要么有效要么无效 */
struct Detection {
    float distanceM;
    bool  valid;      // 只区分"传感器好不好"，不区分"识别准不准"
};

/* ✅ SOTIF 视角：区分【失效】与【性能不足】，并暴露 ODD 状态 */
struct Detection {
    float      distanceM;
    Validity   validity;      // kValid / kSensorFault / kOutOfRange → 26262 侧
    uint8_t    confidence;    // 0..100，识别置信度      → SOTIF 侧
    OddStatus  odd;           // 当前环境是否在运行设计域内
};

enum class OddStatus : uint8_t {
    kInside,          // 在 ODD 内，功能按标称性能工作
    kDegraded,        // 边界：能见度下降 / 强逆光 / 大雨 → 降级但仍可用
    kOutside,         // 已出 ODD（如未标线的施工路段）→ 必须移交驾驶员
};

PlanResult planWithSotif(const Detection& d) noexcept
{
    /* ① 功能安全侧：失效 → 进安全状态（这是 26262 的活） */
    if (d.validity != Validity::kValid) {
        return enterSafeState(SafeState::kHandoverWithFallback);
    }

    /* ② SOTIF 侧：没有失效，但性能不足以支撑这个决策
     *    ——不能进"安全状态"，因为系统没坏；要做的是【降级 + 移交】 */
    switch (d.odd) {
        case OddStatus::kOutside:
            return requestDriverTakeover(Urgency::kImmediate);
        case OddStatus::kDegraded:
            /* 降低功能上限而不是关闭功能：限速、拉大跟车距离、
               提前提示驾驶员。这类"优雅降级"是 SOTIF 的主要产出。 */
            return planConservative(d, speedCap(d.confidence));
        case OddStatus::kInside:
            break;
    }

    /* ③ 置信度门限本身是一条【可追溯到 SOTIF 分析】的参数，
     *    不是调参调出来的魔数：它来自误检率/漏检率的场景统计。 */
    if (d.confidence < kMinConfidenceForBraking) {
        return planConservative(d, speedCap(d.confidence));
    }
    return planNominal(d);
}
这段代码里最值得说的一句是：SOTIF 问题不能用"进安全状态"来解决。系统没坏，你不能因为"雨有点大"就切断转向助力——那本身制造了一个新的危害。SOTIF 的处方是优雅降级与人机移交：限制功能上限、扩大安全裕度、提前把控制权交回驾驶员，并且移交本身要有足够的提前量（这又是一个可以被量化和验证的要求）。
顺带一提，ISO/PAS 8800（2024 年发布，面向车辆中 AI 系统的安全）是这条线上更新的一份文件，专门处理机器学习组件的安全论证。提到它能显出你在跟进领域进展。

ISO/SAE 21434 与 UN R155/R156：信息安全

ISO/SAE 21434:2021（Road vehicles — Cybersecurity engineering）在结构上刻意模仿 26262，学过一个就很容易上手另一个：

ASIL A–D风险值 1–5；另有 CAL（网络安全保障等级）作为附录中的信息性概念注意：CAL 不像 ASIL 那样是规范性的强制分级，引用时要说清这一点

法规侧是真正的强制力所在：

  • UN R155：要求整车厂建立并通过认证的 CSMS（网络安全管理体系），并对每个车型做型式认证。在欧盟等采纳该法规的市场，没有 CSMS 证书就拿不到型式认证，车不能卖。生效节奏大致是：新车型自 2022 年年中起、所有新车自 2024 年年中起（各市场略有差异）。
  • UN R156：对应软件更新，要求 SUMS（软件更新管理体系）。它引入了 RXSWIN（软件识别号）——与型式认证相关的软件必须有可追溯的版本标识，OTA 更新如果改变了受认证影响的软件，需要走相应的认证变更流程。这直接约束了车企的 OTA 自由度。
  • ISO 24089（2023）进一步给出了车辆软件更新工程的具体要求，是 R156 落地的工程参考。

安全与信息安全的交叉：为什么必须一起做

核心命题只有一句：一个可被入侵的 ECU，同时是一个功能安全问题。攻击者伪造的制动指令，在 26262 的视角下就是一次"非预期激活"——和位翻转造成的后果完全一样，只是原因不同。

但两个体系的失效模型不同，这导致防护手段不能互相替代。最清晰的例子就是 CRC 与 MAC：

E2E 保护（CRC + 计数器）SecOC（消息认证码 + 新鲜度值）
防的是随机错误：噪声、位翻转、丢帧有意的伪造与重放
攻击者模型无（自然界不会挑弱点）有：知道算法、能读总线、能构造报文
密钥无有，需要密钥管理与安全存储（HSM）
能否互相替代不能。CRC 是公开算法，攻击者能轻易算出正确的 CRC；反过来 MAC 虽然也能挡住随机错误，但它的开销（计算 + 报文长度 + 密钥管理）远高于 CRC，全量替代不现实
 
/* 同一条制动指令，两层保护叠加：E2E 挡随机错误，SecOC 挡伪造 */

struct SecuredBrakeFrame {
    BrakePayload payload;
    /* ---- E2E 层（ISO 26262）---- */
    uint16_t     e2eCrc;        // 覆盖 payload + counter + dataId
    uint8_t      e2eCounter;
    /* ---- SecOC 层（ISO/SAE 21434）---- */
    uint8_t      freshness[4];  // 新鲜度值（截断传输）：挡重放
    uint8_t      mac[8];        // 截断的 MAC：挡伪造
};

Status receiveSecuredBrake(const SecuredBrakeFrame& f) noexcept
{
    /* ① 先验 MAC：伪造的帧连解析都不该被解析
     *    密钥在 HSM 里，MAC 计算也在 HSM 里做——
     *    密钥【绝不能】出现在应用核的内存里 */
    if (hsm_.verifyMac(f) != HsmStatus::kOk) {
        secLog_.report(SecEvent::kMacFailure);   // → 上报到车厂 SOC/VSOC
        return Status::kAuthFailed;
    }
    /* ② 新鲜度：挡重放。注意它和 E2E 计数器是两回事——
     *    E2E 计数器只有 8 位、会回绕，攻击者可以等它绕回来重放 */
    if (!freshness_.isNewer(f.freshness)) {
        secLog_.report(SecEvent::kReplayDetected);
        return Status::kReplay;
    }
    /* ③ 再走 E2E：随机错误 */
    if (e2e_.check(f) != E2EStatus::kOk) { return Status::kIntegrity; }

    /* ④ 【依然】要做合理性检查：认证过的发送方也可能算错。
     *    认证解决"是不是他发的"，不解决"他发的对不对"。 */
    return applyIfPlausible(f.payload);
}
上面第 ④ 步是最容易被跳过的一步。"消息通过了认证"不等于"消息内容是安全的"——发送方 ECU 自己有 bug、或者发送方已经被攻陷但密钥还有效，认证都会通过。功能安全的合理性检查是最后一道、也是唯一不依赖任何密码学假设的防线。
反过来的错误同样常见：把 E2E 的 CRC 当作安全措施写进 Cybersecurity Case。CRC 的算法和多项式是公开的，攻击者构造一个 CRC 正确的伪造帧只需要几行代码。这两个方向的混淆在联合评审里都会被当场指出。

三套体系怎么在一个项目里共存

现在的 ADAS / 自动驾驶项目基本都要同时满足这三套（外加 R155/R156 的法规要求）。实践中的组织方式有几条经验：

  • 分析要互为输入，不能各写各的。TARA 识别出的"攻击可能导致的损害场景"，要回灌进 HARA 作为新的危害事件来源；HARA 识别出的高 ASIL 资产，要作为 TARA 的重点保护对象。两份文档各写各的，就一定会出现"安全侧假设网关是可信的、安全侧假设网关是攻击面"这种自相矛盾。
  • 共用一套需求管理与追溯基础设施。安全需求、SOTIF 需求、网络安全需求都进同一个需求库，用属性区分。§9.3 的那套追溯自动化对三者同样适用——这是三标合一里投入产出比最高的复用。
  • 成本不是简单相加。经验上叠加 SOTIF 与信息安全后，总成本相对只做 26262 会明显上升（量级参考：+30%–50%，视 ADAS 复杂度差异很大），但流程基础设施（配置管理、变更管理、追溯、评审机制）是复用的，边际成本低于第一套。
  • 量产后的工作量分布完全不同。26262 在 SOP 之后主要是变更影响分析；信息安全在 SOP 之后才刚开始——漏洞监控、补丁、事件响应要持续整个车辆生命周期（十年以上）。这部分的长期人力经常在立项时被完全忽略。

如果你的项目跑在 Adaptive Platform 上，这些机制（E2E、SecOC、身份与访问管理、更新与配置管理）在平台层都有对应的服务与规范，可以参考本目录的 AUTOSAR Adaptive Platform 深入；车载网络侧的时间确定性与冗余可参考 车载网络 与 TSN 深入。

🎯 关键 take-aways
  • 安全不是测出来的：10⁻⁸/h 量级的目标在物理上无法用测试统计证明，只能用结构化论证 + 证据链替代。这是整套流程存在的根本原因。
  • 三条边界：26262 管 E/E 失效；SOTIF（21448）管规格不充分与性能局限；21434 + R155/R156 管恶意攻击。三者在同一个功能上叠加。
  • ASIL 属于危害事件，不属于零件。S+E+C 相加：≤6 → QM，7 → A，8 → B，9 → C，10 → D。
  • V 模型的重点是横线：每一层规格都要有同层的验证证据。评审员的固定问法是"这份规格对应的证据在哪"。
  • ASIL 分解的前提是 FFI，三个维度：时间与执行 / 内存 / 信息交换，对应时间预算与程序流监控 / MPU / E2E。分解不降低分解论证、FFI 证明与仲裁逻辑的 ASIL。
  • 编码规范的每条禁令都在把运行期不确定性搬到编译期：动态内存 → 定容；异常 → 显式返回；RTTI → 编译期穷尽；递归 → 有界显式栈。
  • 工具认证的杠杆在 TD 不在 TI：TI2 + TD1 = TCL1（无需认证）。所以"能不能用开源工具链"取决于你的验证活动够不够强。
  • MC/DC 要求每个条件独立影响判定结果，N 个条件需 N+1 个用例；它抓的正是分支覆盖的盲区。
  • 追溯性矩阵是最该自动化的交付物；四类断链要能张口说出：需求→代码、需求→测试、代码→需求（多余实现）、测试→需求（孤立测试）。
  • 成本经验倍数：ASIL A 约 1.2–1.5×，D 约 3–5×（相对 QM）。分解省钱的真正原因是"只有一小块代码需要做到高标准"。

  1. 基础功能安全、SOTIF、信息安全三者的边界在哪？举例说明

    边界由"危害是怎么产生的"划分，不是由"危害有多严重"划分。

    • ISO 26262（功能安全）：危害来自 E/E 系统的失效行为——随机硬件失效（位翻转、器件老化）与系统性缺陷（软件 bug、设计错误）。
    • ISO 21448（SOTIF）：系统没有失效，严格按规格工作，但规格本身不充分——功能的固有性能局限遇上特定触发条件。
    • ISO/SAE 21434 + UN R155/R156（信息安全）：危害来自有智能的攻击者。26262 的失效模型里没有"攻击者"这个假设。

    用同一个 AEB 功能切三刀，是最能说明理解的答法：

    • "该刹车时 MCU 故障导致没刹" → 26262，处方是双通道 + 看门狗 + 进安全状态。
    • "该刹车但感知没识别出目标（逆光下的白色车厢）" → SOTIF，处方是传感器融合、场景库、限制 ODD、优雅降级。
    • "攻击者从车机跳到总线上伪造制动报文" → 21434，处方是 SecOC 的消息认证 + 新鲜度值 + 安全启动。

    加分的两层：① 三者会交叉——被伪造的制动指令在 26262 视角下就是一次"非预期激活"，所以信息安全失效同时是功能安全问题，两边的分析要互为输入；② SOTIF 问题不能用"进安全状态"解决，因为系统没坏，切断功能本身会制造新危害；它的处方是降级与人机移交。

    还有一条常被忽略：26262 也不管非 E/E 危害（电池热失控的化学过程本身、材料毒性、纯机械件断裂），那些归别的法规。

  2. 基础ASIL 是怎么推导出来的？完整讲一遍

    ASIL 是 HARA（危害分析与风险评估）的输出，流程五步：

    1. 相关项定义：划清边界——包含哪些 ECU/传感器/执行器，依赖哪些外部要素（电源、时钟、总线一定要写进去，漏掉是常见坑）。
    2. 穷举「运行场景 × 失效行为」。场景维度：高速直行、泊车、静止、弯道、湿滑、拖挂……失效行为维度：功能丧失、非预期激活、过量、过少、时序过早/过晚、方向错误。
    3. 筛出危害事件：不是每个组合都危险（"静止时转向助力丧失"没危害）。
    4. 对每个危害事件打 S / E / C：
      · S（Severity）伤害严重度 S0–S3；
      · E（Exposure）该运行场景出现的概率 E0–E4——注意不是失效概率；
      · C（Controllability）一般司机能否避免伤害 C0–C3。
    5. 查表得 ASIL，并为每个危害事件写一条安全目标，附 FTTI（容错时间间隔）与安全状态定义。

    查表可以用一条口诀代替背表：把三个数字相加——和 ≤6 → QM，7 → A，8 → B，9 → C，10 → D。另外 S0 或 C0 直接是 QM，E0 不分配 ASIL。当场推一个：高速非预期全力制动 S3 + E4 + C3 = 10 → ASIL D。

    生产视角：C 是最容易被博弈的一格（C3 降成 C2 就少一级 ASIL，预算差几百万），所以正规项目要求 C 的评级有依据——驾驶员在环实验、路测数据或已发表的人因研究，不是会议室里的"我觉得我能踩住"。评审员和评估人最爱盯这一格。

    还要能说清 FTTI 的工程意义：它是给你的时间预算，"故障检测时间 + 故障反应时间 < FTTI"，直接决定了你的监控任务周期和看门狗窗口能设多大。FTTI 是从物理场景推出来的客观量，不是"越小越好"的调参。

  3. 基础ASIL 是零件的属性还是别的什么的属性？为什么这个区分重要

    ASIL 是「危害事件」的属性，经安全目标传递给安全需求，再由架构分配到具体元件上。所以"我们是 ASIL D 团队""这颗 MCU 是 ASIL D"在语义上都不严格；准确说法是"这条安全目标是 ASIL D，它被分配到了这个组件上"。

    这个区分有三个直接的工程后果：

    • 同一个零件可以承载不同 ASIL 的需求。一个 EPS 控制器上，"防止非预期转向扭矩"是 S3·E4·C3 = ASIL D，"保证助力可用性"是 S3·E4·C2 = ASIL C。两条需求的验证证据要求不同——ASIL C 那条不需要做 MC/DC。混在一起统统按 D 做，是很多项目白花钱的原因。
    • 同一块芯片可以混合关键度。数字仪表的挡位/车速显示是 ASIL A–B，同屏的导航和主题皮肤是 QM。前提是做好隔离（MPU 分区 / hypervisor），并证明 QM 部分不干扰安全部分（FFI）。
    • 软件架构必须等 HARA 出结果再定。反过来做几乎一定返工——见过项目把挡位显示和主题动画放在同一个渲染进程里，定点后才知道挡位显示是 ASIL B，整个渲染层重构掉了约 8 个人月。

    加分：能顺带说清括号记法。ASIL B(D) 是"ASIL B，源自 D"——方法按 B 做，但对独立性和分解论证的要求仍是 D 级。这正是"ASIL 跟着危害走"的直接体现。

  4. 基础车规 C++ 为什么禁止运行期动态内存？给出真实理由

    先纠正一个前提：ISO 26262 本身没有一条"禁止 new"的规则。它要求的是资源用量与执行时间可分析、避免不确定行为；落到 MISRA / AUTOSAR C++ 编码规范上，才成了明确的禁止。能说清这条传导链，说明你理解的是要求而不是二手结论。

    四个真实理由，按分量排序：

    1. 分配时间不可预测：分配器要遍历空闲链表，耗时取决于堆的历史状态。WCET 分析对它给不出有意义的上界，而你的控制环有硬性周期。
    2. 堆是全局共享资源，直接破坏 FFI：一个 QM 组件泄漏内存，会让同进程里的 ASIL 组件分配失败。这一条最少被提到但杀伤力最大——它把一个"性能问题"升级成"ASIL 分解论证不成立"。
    3. 失败路径几乎无法验证：new 失败要么抛 std::bad_alloc（异常也被禁），要么返回空。这条路径在实验室里测不到，却是最危险的路径。
    4. 碎片化是时间的函数：ECU 可能连续运行数周不重启，车辆寿命 10–15 年。碎片化在 8 小时的台架测试里根本不会显现。

    怎么替代：定容容器（编译期确定容量、满了返回 false、绝不抛异常）、启动期一次性分配的内存池、环形缓冲区。关键是容量常数必须有需求或分析支撑，并且"容量不够"要是一个可诊断、可测试的事件，不能静悄悄截断。

    生产陷阱：以为"不写 new 就没有动态内存"。std::string、std::vector、std::function、std::shared_ptr、有序容器都可能分配。可靠做法是在链接期堵死——把 operator new / malloc 换成直接进安全状态的桩，或者让引用它们的符号解析失败，这样"不小心引入了分配"在构建时就暴露，而不是在路试时。

11.2 中级（区分熟练度）

  1. 中级V 模型的左右两臂是怎么对应的？Confirmation Measures 是什么

    V 模型的重点不是时间顺序，而是横向对应：左臂每一层产出的规格，必须由右臂同一层的验证活动来证明被实现了。

    左臂（规格）右臂（验证）
    相关项定义 + HARA（安全目标）车辆层面安全确认
    功能安全概念（FSR）系统集成与验证（含故障注入）
    技术安全概念 + 系统架构（TSR、HSI）硬件-软件集成测试（HIL）
    软件架构设计软件集成与验证（接口、资源用量、函数/调用覆盖）
    软件单元设计软件单元验证（基于需求的测试 + 结构覆盖率）

    评审员的固定问法就是这条横线："这份规格对应的验证证据在哪？"拿整车路试报告去证明软件架构被正确实现，会被直接驳回。

    Confirmation Measures（确认措施）是三件不同的事，混为一谈是常见减分点：

    • 确认评审：检查具体的工作产品（安全计划、HARA、安全概念、Safety Case）是否合规、完整、自洽。
    • 功能安全审核：检查过程执行情况——"你们是不是真按安全计划在干活"，抽查配置管理、变更单、评审记录。
    • 功能安全评估：对最终达成的功能安全作综合判断，给出放行建议。

    三者的独立性要求随 ASIL 递增，业内口语化地分成三档：人员独立（不是作者本人）、团队独立（不向同一直接上级汇报）、组织独立（不同部门或外部机构，独立于项目的资源与预算决策）。大致趋势是 ASIL C/D 的关键工作产品要团队级独立、功能安全评估要组织级独立。具体哪个 ASIL 对应哪一档、不同工作产品还不一样，要查 Part 2 那张表，不要凭记忆答。

    生产视角：独立性是主要成本来源之一（组织独立意味着养一个独立部门或按小时付外部机构）。所以"把 ASIL D 分解成 B(D)+B(D)"省下的不只是测试量，还有独立评审的档位。

  2. 中级ASIL 分解是什么？FFI 为什么是它的前提，怎么证明

    分解是把一条高 ASIL 的安全需求拆成两条互相独立的低 ASIL 需求。合法组合可以用一条加法规则记住（QM=0, A=1, B=2, C=3, D=4，拆成两个非负整数之和）：

    • D → C(D)+A(D)、B(D)+B(D)（最常用）、D(D)+QM(D)
    • C → B(C)+A(C)、C(C)+QM(C)
    • B → A(B)+A(B)、B(B)+QM(B)
    • A → A(A)+QM(A)。A 不能拆成 QM+QM，那等于凭空取消安全要求。

    三件东西不能被分解降低，这是最容易答漏的部分：① 分解本身的论证；② 独立性（FFI）的证明与相关失效分析；③ 把两通道结果合并/仲裁的那段逻辑。见过团队把仲裁器也标成 B(D)，被评估人一票打回。

    FFI（Freedom From Interference）是分解成立的唯一前提，三个维度必须能张口说出，并配上技术手段：

    维度干扰形式技术手段
    时间与执行死循环占死 CPU、长时间关中断、持锁不放、共享中断OS 执行时间预算、程序流监控、不共享阻塞资源
    内存野指针、越界、共享可写全局量、DMA 目标算错MPU/MMU 分区（硬件强制，论证强度最高）、静态分配、只读段
    信息交换数据损坏、丢失、重复、乱序、过期、串线E2E 保护（CRC + 计数器 + 数据 ID + 超时）、单向通道

    三个真实的 FFI 违例（代码本身没 bug，但让分解论证失效）：

    • 共享一把互斥锁：主通道持锁期间卡死，监控通道跟着饿死——一个失效击穿两个通道。修法是每通道一份只读副本，或单写多读双缓冲。
    • 共享硬件定时器 / 共享中断：时钟树配置错误让两个通道同时变慢，而比较结果依然一致，监控完全察觉不到。这是共因失效，修法是给监控通道独立时基（外部窗口看门狗的最大价值就在这）。
    • 共享内存不做保护：QM 侧写、ASIL 侧读，没有 MPU、没有 E2E、没有范围检查。三个雷一起踩。

    生产视角："物理上分开"不等于"独立"。把两通道放在同一颗双核 MCU 的两个核上就声称独立，评估人三个问题就能打回：共享 L2 与内存控制器（时间 FFI 不成立）、共享电源与时钟（共因）、同一份编译器和标定数据（系统性共因）。整改往往是加外部看门狗提供独立时基、给内存控制器配带宽限额、标定数据独立生成，再补完整的 DFA 报告。

  3. 中级为什么车规 C++ 禁异常？禁了以后错误怎么处理

    理由不是"异常慢"——正常路径上的零成本实现确实几乎没有开销。真正的四个理由：

    1. 抛出路径的执行时间不可预测：栈展开要查 unwind 表、逐帧调用析构函数，耗时取决于调用深度与对象数量。WCET 给不出上界。
    2. 控制流不可见：任何一个可能抛出的调用都是一条隐藏的分支。这直接和结构覆盖率打架——你的分支覆盖率报告里根本看不到这些边，MC/DC 更无从谈起。
    3. 依赖运行期支持：unwinder、类型信息表、异常表都要被信任，在工具认证里是额外负担；某些 freestanding 环境下 unwinder 甚至不可用。
    4. 和禁动态内存冲突：某些实现分配异常对象需要堆。

    替代方案：显式返回值 + noexcept + [[nodiscard]]，让错误无法被静默忽略。

    enum class TorqueError : uint8_t { kNone, kInvalidInput, kOutOfRange };
struct TorqueResult { Torque value; TorqueError error; };

[[nodiscard]] TorqueResult computeTorque(const Input&) noexcept;

    能说出这个副作用会显得很有经验：禁异常后构造函数不能报错，于是车规代码普遍用两段式初始化——构造函数只做绝不会失败的事，真正的初始化放在返回错误码的 init() 里。这也解释了为什么车规代码库里很少看到 RAII 式的"构造即获取资源"。

    构建侧要一起堵死：-fno-exceptions -fno-rtti。只在编码规范里写"不要用异常"而编译选项不设，迟早会有第三方头文件把它带进来。

  4. 中级MC/DC 是什么？它比分支覆盖严格在哪？用一个表达式说明

    MC/DC（Modified Condition/Decision Coverage）要求四条：每个入口出口被执行；每个判定取过真假；每个条件取过真假；每个条件被证明能独立影响判定结果——即存在一对用例，只有这一个条件不同，且判定结果不同。第四条是全部难度所在，前三条只是"条件覆盖 + 判定覆盖"，弱得多。

    用 if (enabled && (pedalPressed || adasRequest)) 说明（记为 A && (B || C)）。

    分支覆盖只要 2 个用例就到 100%：(A,B,C)=(真,真,假)→真，(假,真,假)→假。但注意 C 从头到尾都是假——如果 adasRequest 拼错了变量名、读了错误信号、或永远为假，这两个用例永远发现不了，而它对应的正是"ADAS 请求制动"这条核心功能。这就是分支覆盖的盲区：只关心判定整体的真假，不关心内部每个条件有没有真正起作用。

    MC/DC 需要 4 个用例（N 个条件通常 N+1 个）：

    用例ABC结果证明谁独立
    TC1真真假真基准
    TC2真假假假B（与 TC1 只差 B）
    TC3真假真真C（与 TC2 只差 C）
    TC4假真假假A（与 TC1 只差 A）

    现在 TC3 里 adasRequest 是判定为真的唯一原因，它坏了 TC3 必然失败。

    三个加分点：

    • 为什么是 N+1 而不是 2^N：MC/DC 的设计目的就是逼近多条件覆盖的检错能力，但把成本从指数压到线性。10 个条件：多条件覆盖要 1024 个用例，MC/DC 只要 11 个。
    • 短路求值带来两种口径：&& / || 会短路，严格的 unique-cause MC/DC（只允许一个条件变化）往往构造不出来，于是有 masking MC/DC（允许其它条件变化，只要论证它们被逻辑屏蔽）。项目必须在测试策略里明确采用哪一种，否则不同工具算出的覆盖率对不上。
    • 它反向压迫设计：8 条件的判定要 9 个用例且极难构造，工程师自然会把它拆成命名清晰的中间布尔量。MC/DC 最被低估的收益是让代码变简单了。

    ASIL 对应：MC/DC 在 ASIL D 是 ++（强烈推荐），A/B/C 是 +。工具侧，Clang 18 起支持 -fcoverage-mcdc 原生测量；正式证据通常用 VectorCAST / LDRA / Tessy 这类带工具认证包的商业工具。

11.3 高级（体现深度）

  1. 高级什么是工具认证与 TCL？为什么车企不能随便升级 GCC 版本

    出发点：你的安全论证建立在"代码正确"上，但交付的是编译器生成的机器码、依赖的是静态分析工具给出的结论。工具会出错，整条证据链就有一个未经检验的假设。

    TCL 的推导：对每个工具做两个判断——

    • TI（Tool Impact）：TI1 = 不可能在安全相关产出里引入错误、也不可能漏掉本该检出的错误；TI2 = 其余全部情况。
    • TD（Tool error Detection）：工具的失效被后续活动发现或阻止的置信度，TD1 高 / TD2 中 / TD3 低。注意 TD 说的不是工具本身多可靠，而是你的流程能不能兜住它。

    组合：TI1 → 一律 TCL1；TI2+TD1 → TCL1；TI2+TD2 → TCL2；TI2+TD3 → TCL3。TCL1 无需额外认证措施，TCL2/3 需要认证。

    这里藏着整个策略的关键：TI 你改不了（工具就是会影响产出），TD 是唯一能施加影响的变量。所以行业里的真实做法不是给所有工具买认证，而是用验证活动把 TD 推高：目标码级覆盖率、关键模块生成汇编的评审、双编译器交叉比对、HIL 黑盒回归——把编译器做到 TI2+TD1 = TCL1。静态分析工具则相反（漏报很难被别的活动发现，TD3），所以它通常必须用供应商的认证包。

    为什么不能升 GCC：认证的对象不是"GCC"，而是"GCC 12.2.0 + 这一组编译选项 + 这个目标核 + 这份安全手册"。升级同时打破五件事：① 证书写的是具体版本，换版本即失效；② 安全手册里的使用约束可能变了（新优化 pass 的失效模式未覆盖）；③ 已知问题与规避清单要重做；④ 所有目标码都变了，严格说要重跑全部单元/集成测试与目标码覆盖率、重出静态分析报告；⑤ 内联与展开策略变化会让栈用量与 WCET 基线失效，时序论证要重做。

    所以行业做法是工具链冻结：某个里程碑后锁死版本直到量产。真要升级，它是一个季度级的独立小项目，要单独排期与预算。工程上要落成构建门禁——版本、二进制哈希、编译选项白名单三道锁，任何一项不符直接构建失败。见过项目为了赶性能指标在本地开 -O3（安全手册只确认到 -O2），到评估阶段才发现整份时序论证的基线不对。

    能补上这个例子会很出彩：编译器风险的真正形态不是"编译器有 bug"，而是"编译器完全按标准行事，却把你的安全检查合法地删掉了"。比如 return (a + b) < a; 这种溢出检查——a+b 本身已是有符号溢出（UB），编译器据此推断条件恒假，-O2 下整个函数被优化成 return false;。源码级评审看不出来，只有目标码级验证能发现。这也顺带解释了为什么"双编译器交叉比对"性价比高：它抓出来的绝大多数差异其实是自己代码里的 UB，而不是编译器 bug。

  2. 高级追溯性为什么是核心交付物？断链有哪几类，怎么防

    四条理由，每条对应一个真实场景：

    1. 它是 Safety Case 的骨架。安全论证的每一句话都要能点开看到底层证据，追溯矩阵就是那些超链接。
    2. 它让变更影响分析成为可能。"改这个函数会影响哪些安全需求、要重跑哪些测试"——没有矩阵，这个问题只能靠人的记忆回答，而人会离职。
    3. 它是"多余实现"的探测器。代码里有一段不对应任何需求的逻辑，意味着软件行为没有被完整规定，在 ASIL C/D 上是硬伤。
    4. 它是评审员的入口。评估人不会通读代码，他会抽样三五条需求顺着矩阵往下走，看每一环是否闭合。矩阵烂，抽样必挂。

    四类断链（第三类最容易被答漏）：

    • 需求 → 代码：有需求没实现。
    • 需求 → 测试：有需求没验证。
    • 代码 → 需求：多余实现——写了没人要求的功能。这一类在评审里杀伤力最大。
    • 测试 → 需求：孤立测试——不坏，但它不能作为任何需求的证据。

    怎么烂掉的：没人会一次性把追溯搞坏。需求评审后重新编号、代码标签没跟着改；功能砍掉、需求删了代码留着；紧急修 bug 时"先改了再补需求"然后忘了补。三个月后 15% 的链是坏的，而没有人知道是什么时候坏的。

    处方：机检 + 门禁。代码里用 @satisfies 标签、测试里用 @verifies 标签，CI 里生成矩阵并校验四个方向，断链即构建失败。而且这条门禁必须在项目第一天就上——等有了 500 条需求再上，第一次运行会报几百个错误，团队的第一反应会是"把这个门禁关掉"。

    生产视角：追溯矩阵必须由工具生成，不能手工维护；源码位置要用标签做锚点、行号由工具填（行号会漂）；ASIL 列要参与校验（B(D) 的行不查 MC/DC 列，D 的行必须有）。
    见过一个团队花两周把"需求 → 代码 → 测试 → 覆盖率"完全自动化，当时被质疑"不产出功能"；之后每次里程碑准备评审材料的时间从约两周降到半天，一年四次里程碑，还避免了两次因断链导致的评审不通过。在功能安全项目里，自动化证据生成是投入产出比最高的工程投资。

  3. 高级举三个安全机制并说清它们各自抓什么失效：看门狗 / E2E / 双通道比较

    ① 窗口看门狗与程序流监控——两件不同的事

    普通看门狗只问"你还活着吗"；窗口看门狗还问"你的节奏对吗"；程序流监控问"你走的路径对吗"。

    为什么"喂太早"也算故障？考虑这个失效：周期任务本该 10 ms 跑一次，一个循环变量被位翻转破坏，变成 1 ms 跑一次。功能输出看起来还正常，普通看门狗完全不会报警——它被喂得更勤了。窗口看门狗把喂狗时刻限制在 [t_min, t_max] 才能抓到它。

    程序流监控则在关键路径上埋检查点，每点把一个唯一值带顺序地混入签名（用旋转异或而非单纯异或，否则 A→B 和 B→A 同值），周期末比对签名与耗时窗口。它抓的是"跳过了一段代码 / 顺序错乱"。

    两个实现要点：喂狗绝不能放在独立的高优先级任务或定时中断里无条件执行——那叫"喂狗给自己听"，功能任务全死了狗照样被喂。正确做法是收集所有被监控任务的"本周期已完成"标记，全员到齐才喂。更强的形式是问答式（challenge-response）外部看门狗：外部芯片发随机数，MCU 必须借助程序流签名才能算出应答，这样喂狗动作本身无法被伪造，而且外部芯片提供了独立时基（消除时钟共因）。

    ② E2E 保护——CRC 只是四件套之一

    要素挡什么为什么 CRC 单独不够
    CRC比特损坏—
    序列计数器丢失、重复、乱序一个"完好但过期"的旧帧 CRC 是正确的
    数据 ID（参与 CRC 但不上线）串线 / 寻址错误另一条同长度报文的 CRC 也可能自洽
    超时监控发送方彻底静默没有报文就没有 CRC 可校验——"什么都没收到"必须被当成故障

    最常见的实现错误：把"这一帧没来"当成"正常"处理。"先用上一帧"在一两帧内是合理降级，但不计数、不设上限的话，发送方彻底死掉时接收方会永远拿着陈旧值继续控制——所有 CRC 校验都通过，日志干干净净。这类 bug 只有故障注入能抓到，代码评审看不出来，因为每一行单独看都是对的。

    再补一层边界：E2E 的 CRC 不是信息安全措施。CRC 算法公开，攻击者构造一个 CRC 正确的伪造帧只需几行代码。防伪造要用 SecOC 的消息认证码 + 新鲜度值。

    ③ 双通道比较——同构冗余与多样性冗余的区别

    • 同构冗余（同一份代码跑两遍、锁步核）：只挡随机硬件失效。挡不住软件 bug——同样输入同样 bug，两边错得一模一样。
    • 多样性冗余（不同算法、不同数值表示、不同工程师）：能挡一部分系统性失效，但"多样性有多大"难以量化论证。

    实现上三个刻意的设计选择：① 主通道用查表插值（浮点）、监控通道用保守解析包络（定点整数），不同数值表示让同一个溢出/舍入 bug 不会同时出现；② 比较不是判"相等"，而是判"落在允许包络内 + 容差"——只判单次不等会被噪声频繁误触发，误报比漏报更容易搞死项目；③ 去抖周期数 × 任务周期必须明显小于 FTTI，这条不等式把一个看似"调参"的常量变成了可追溯到 HARA 的设计约束。

    最有价值的一条工程经验：监控器要比被监控的功能简单一个数量级。见过项目把监控通道设计成"用另一套算法重算一遍力矩"，代码量做到主通道的 60%，验证成本翻倍且误报频发；重构成"静态包络表 + 变化率限制"后从约 12000 行降到约 900 行，误报消失，MC/DC 也变得可行。监控器写复杂了，是这个模式最典型的失败方式——它同时也说明了"分解为什么省钱"：省的不是"两个 B 比一个 D 便宜"，而是你只需要把一小块代码做到高标准。

  4. 高级一个现有的 QM 功能要升级到 ASIL B，你需要做哪些事？

    这道题考的是能否把整套流程串起来。按「先补规格，再补证据，最后补组织」的顺序答，逻辑最清楚。

    第一步：先确认 ASIL B 这个结论本身（别跳过）

    • 要求看 HARA：这个功能对应哪个危害事件、S/E/C 各是多少、FTTI 和安全状态是什么。这四个数字之后会决定你所有的设计约束。
    • 问清楚：这个 ASIL B 是原生的，还是从更高 ASIL 分解来的（有没有括号标记）？如果是 B(D)，独立性要求是 D 级的，工作量完全不同。
    • 反向确认一下能不能不升：如果整车层面已有另一道独立防线（例如动力系统已有独立扭矩监控），这个功能有可能保持 QM。这是省钱最快的路径，值得先问。

    第二步：补规格（左臂）

    • 写软件安全需求，逐条编号。判据是"我能不能为它写出一个会失败的测试"——写不出来的需求不合格。注意不要从现有代码倒推需求（reverse engineering requirements），评估人对这个模式极其敏感：倒推的需求和代码结构一模一样，一眼就能看出来。
    • 补软件架构文档：分层与依赖方向、接口、任务周期与优先级、WCET 与栈预算、以及 QM 与 ASIL 部分的边界。
    • 做 FFI 分析：这个功能升到 ASIL B 后，同一个 ECU/进程里剩下的 QM 组件不能干扰它。按三个维度逐项处理——内存上加 MPU 分区或至少做到只读共享；时间上不与 QM 组件共享锁、共享中断、共享堆；信息交换上给跨边界的数据加 E2E 保护 + 消费侧范围检查。这一步通常是整个升级里最容易触发架构重构的地方。

    第三步：改实现（顶点）

    • 把代码收进编码规范的语言子集：去掉运行期动态内存（含 std::string / vector / function 这些隐式分配）、关掉异常与 RTTI（-fno-exceptions -fno-rtti）、消除递归与无界循环、显式化所有隐式转换、虚函数加 override。
    • 加安全机制：按 FTTI 反推监控周期，加范围检查与合理性检查、必要的看门狗与程序流监控参与、跨边界数据的 E2E。
    • 拆复杂函数：把圈复杂度压到项目门槛内（常见 ≤10），否则后面分支覆盖根本做不动。
    • 正式静态分析工具进 CI（不是 clang-tidy），处理基线违规：能改的改，不能改的走偏离流程并把同类偏离归并成"偏离类别"批量批准。

    第四步：补证据（右臂）

    • 基于需求的单元测试，每个用例关联需求 ID；ASIL B 的结构覆盖率要求是分支覆盖 ++（语句覆盖也是 ++，MC/DC 只是 +，所以不必强上）。未覆盖项逐条写理由。
    • 故障注入：为每个安全机制写注入用例，证明它真的触发、且检测+反应时间在 FTTI 内。能在 SIL 上做的尽量前移，HIL 只留需要真实硬件的（电气、时钟、ECC）。
    • 集成层面：接口测试、栈/CPU/内存实测与预算对账、函数与调用覆盖。
    • 建追溯矩阵并进 CI 门禁，四类断链清零。

    第五步：流程与组织

    • 更新安全计划：把这个功能纳入范围，写清方法采纳矩阵（Part 6 相关表格 ASIL B 那一列逐项标注"采用 / 等效替代 / 不采用+理由"）。
    • 工具认证分类：把用到的工具逐个做 TI/TD 判定，编译器一般走 TI2+TD1→TCL1（靠目标码验证与双编译器比对论证），静态分析工具通常需要认证包。
    • 确认措施：安排 ASIL B 要求档位的确认评审；把变更影响分析做成 PR 模板 + 自动化脚本。
    • Safety Case 补章节，并纳入下一次功能安全评估的范围。

    最后一定要说的两句（这是区分"背过流程"和"做过项目"的地方）：

    • 不要试图一次性升级整个功能。正确做法是切出真正安全相关的那一小块升到 ASIL B，其余保持 QM 并用 FFI 隔离。这和 ASIL 分解省钱的逻辑完全一致——让高标准只覆盖必要的最小范围。把整个几万行的模块统统升到 B，是最常见也最贵的错误决策。
    • 工作量量级：同代码量下 ASIL B 的经验倍数约为 QM 的 1.5–2.2 倍，但存量代码的升级通常更贵——因为要付重构成本，还要付"补写规格"的成本（而规格本该在写代码之前就有）。所以估算时不要直接套这个倍数，要单独算重构和补文档这两块。
