01

实时系统全景

实时 ≠ 快 · 硬 / 准 / 软三档 · 关键指标与 WCET · 场景对照

整个领域的第一块基石只有一句话：实时的定义是「最坏情况有界」，不是「平均很快」。3 GHz 服务器处理中断的平均时延可能只有 2 µs，比 100 MHz 的 Cortex-M4 快一个数量级；但前者的最坏值可能是 8 ms，后者是 3 µs。对一个必须每 250 µs 采样一次电流的电机控制回路，只有那个最坏值决定系统能不能用。

一句话判据：能回答「这个动作最坏要多久，上界怎么论证出来的」，你在做实时系统；只能回答「一般几微秒，偶尔慢一点」，你在做低延迟优化。两件事都值得做，但验收方式完全不同。

反直觉的根源在于：日常工程训练都在优化期望值（QPS、平均延迟、吞吐），实时工程优化分布的右端——关深度睡眠、禁动态调频、中断改线程都是用平均性能买确定性，这是整个领域反复出现的同一笔交易。

🚇 生活类比：地铁 vs 出租车。出租车平均25 分钟，地铁固定 40 分钟；但出租车遇上封路可能要 2 小时，地铁最坏 50 分钟。赶飞机的时候所有人都选地铁——要的不是「期望到达时间最短」，而是「保证在某个时刻前到」。RTOS 就是地铁：单看吞吐比不过通用 Linux，但它给你一个能写进规格书的上界，代价是少载客。

四档：区别不在时间尺度，在失效后果

分档常被误解成「µs 是硬实时、ms 是软实时」。时间尺度只是表象，真正的依据是「错过一次 deadline 会发生什么」：每 100 ms 触发一次的气囊自检是硬实时，每 1 ms 刷新一次的仪表动画是软实时。

为什么 WCET 测不准，只能给保守上界

WCET 是整个实时工程里最硬的一块骨头。直觉上「跑一百万次取最大值」就够了，但这在现代处理器上是错的：执行时间不只取决于代码，还取决于你无法完全控制的微架构状态。

所以工业界两条腿走路：静态分析工具（AbsInt aiT、Rapita RapiTime）沿控制流图算出一个保证不低于真实值的上界，再用大量实测取上包络交叉验证。上界与实测最大值之间那段「浪费」，就是确定性的价格。

被问「你们的 WCET 怎么定的」，回答「压测一周取最大值再乘 2」会立刻暴露层次。正确表述是：实测只能给出下界，上界必须来自静态分析或对硬件行为的保守假设。

Linux vs RTOS 何时用

选型受两条谱系夹住：硬件给多少算力，以及这个算力上跑得起哪种软件形态。两者之间那道真正的坎是 MMU——没有 MMU 就没有 Linux，讨论直接结束。

谱系里还夹着一档双内核（代表是 Xenomai）：Linux 旁边跑一个独立的实时微内核，实时任务完全不受 Linux 影响，代价是要用它自己的 API、维护负担高于主线的 PREEMPT_RT。自 PREEMPT_RT 进入主线，新项目选它的理由已经少很多（对比见 §3）。

这一页怎么读。本文是门户：每个主题只给到「足够做选型判断」的深度，然后转向深入篇—— 调 Linux 实时性 → PREEMPT_RT 深入； 设计高性能 ECU 架构 → AUTOSAR AP 深入； 选总线、配 TSN → 车端网络深入； 走认证流程 → ISO 26262 工程实践。

PREEMPT_RT — Linux 准实时化

解决什么 · 代价是什么 · 够用 / 不够用的判据 · 主线化这个节点

通用 Linux 的最坏调度延迟能到几百毫秒，原因不是「代码写得慢」，而是内核里存在大量不可抢占的区间：自旋锁临界区、软中断处理、硬中断上下文。高优先级实时线程就绪时如果 CPU 正在跑这些区间，它只能等——等多久取决于当时恰好在跑哪段代码，而这不可控。PREEMPT_RT 近二十年的工作就是系统性地消灭这些区间。

核心改动（概览）

五项改动一句话概括：自旋锁换成可睡眠、支持优先级继承的 RT mutex（真不能睡的地方留显式的 raw_spinlock_t）、中断主体挪进受调度器管辖的内核线程、软中断不再无条件在中断返回路径上批量执行、RCU 回调可卸载到指定核、定时器改用 hrtimer 把唤醒精度从毫秒推进到微秒。逐项实现与配置的坑见 RT patch 的 5 大核心改动。

主线化：2024 年那个节点为什么重要

约二十年分批上游化，最后一批在 Linux 6.12（2024-11，LTS）合入，CONFIG_PREEMPT_RT 成了常规配置项。意义不在延迟数字（基本没变），而在于不必再 rebase 一大摞补丁、也不必担心某次驱动改动默默破坏 RT 语义。对选型的影响就一句：「长期维护风险」这一项可以从决策表里划掉了。生态与版本现状见 PREEMPT_RT 深入 · 2026 现状。

主流 RTOS 对比

九个候选放同一张表 · 认证可得性 · 四步决策树 · 隐性成本

技术差异（调度算法、IPC 原语）没有想象中重要——所有主流 RTOS 都是固定优先级抢占式调度，都有信号量、消息队列、互斥量和优先级继承，应用代码结构大同小异。真正决定选型的是四件更「外围」的事：认证证据拿不拿得到、生态里有没有你的芯片和外设驱动、内存装不装得下、授权成本与团队熟悉度。

先把「所有 RTOS 共有的那一半」说清，差异才看得明白。第一件是抢占式调度——它是标配不是因为效率高，而是因为只有它能把响应时间与「别人正在干什么」解耦。

第二件是固定优先级，配套的分析方法叫速率单调（RM）：周期越短、优先级越高。理论上还有更优的动态方案 EDF，但它几乎不进产品，原因值得知道：

第三件是应用代码的形态。同一个「每 1 ms 采一次、算一次」的任务，三种形态下的最小写法差别不在语法，而在时基由谁提供、谁保证它按时被叫醒：

// ① 裸机：超级循环 + 定时器中断。时基就是硬件，抖动只来自 ISR 入口开销。
volatile bool tick;
void TIM2_IRQHandler(void) { TIM2->SR = 0; tick = true; }        // 1 kHz
int main() { for (;;) { if (tick) { tick = false; controlStep(); } } }
// 陷阱：controlStep 一旦超过 1 ms 就静默丢一拍，而且没有任何人告诉你。

// ② RTOS：内核提供周期唤醒与优先级，超时可以被发现。
void controlTask(void*) {
  TickType_t next = xTaskGetTickCount();
  for (;;) { vTaskDelayUntil(&next, pdMS_TO_TICKS(1)); controlStep(); }
}
// DelayUntil 而不是 Delay：基准是绝对 tick，误差不会累积（同一个道理见 §7.9）。

// ③ RT Linux：多了两件裸机 / RTOS 上根本不存在的事 ——
//    要显式声明实时属性，要显式把内存钉住，否则一次缺页就毁掉整个预算。
mlockall(MCL_CURRENT | MCL_FUTURE);                  // 锁页，见 §7.6
clock_gettime(CLOCK_MONOTONIC, &next);               // 只在循环外取一次"现在"
for (;;) {
  tsAddNs(next, 1'000'000);                         // next = 起点 + n × 1 ms
  clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, nullptr);
  controlStep();
}
// 线程本身还要设 SCHED_FIFO 并绑核（见 §7.4），漏了它就只是个普通线程。

驱动缺口

人的成本

团队熟悉一个 RTOS 要几个月才谈得上高效。已有存量代码时，换内核的收益极少能覆盖迁移与再培训成本——除非被认证或芯片支持这类硬约束逼着。

AUTOSAR CP / AP

两套平台的定位差异 · 共存关系 · 功能该放哪一侧的判据

AUTOSAR 的本质是把「应用逻辑」和「硬件 / 通信 / 基础服务」彻底解耦，让一份控制策略能在不同供应商的 ECU 上复用。关键不是背分层图，而是它诞生的产业背景：一辆车上几十上百个 ECU 来自十几家供应商，主机厂需要一套共同语言。

🔌 生活类比：插座标准。它不规定电饭煲怎么煮饭，但规定插头形状、电压和安全要求，于是任何一家的电饭煲都能插进任何一面墙。CP 像固定在墙上的强电回路：安装时就规划好每一路走哪儿、载流多少，运行时不再改；AP 像 USB-C 口：插上后协商能力、按需供电，灵活但复杂度高得多。

最本质的一条差异：静态信号 vs 面向服务

上表所有条目都能从通信模型这一行推导出来，这才是真正的分水岭。

CP：静态信号，编译期就定死

「发动机转速」在哪条 CAN 报文的第几个 bit、多少毫秒发一次、谁接收，全部由配置工具在集成阶段生成到代码里，运行时没有发现、没有协商、没有连接建立。

于是时序完全可离线分析、无动态内存、启动即可用——这是它能支撑 ASIL D 的基础。代价是改一个信号要重新生成整条链路的配置，跨 ECU 牵一发动全身。

AP：服务发现，运行时建立连接

提供方声明「我提供 RadarObjectList」，使用方声明「我需要它」，运行时通过 SOME/IP 服务发现配对再建立连接。

于是解耦：新增消费者不用改提供方，模块能独立更新与部署——这是 OTA 与「软件定义汽车」的技术前提。代价是时序不再静态可分析（发现过程、序列化、TCP/IP 栈都是变数），所以 AP 从一开始就不为硬实时闭环控制设计。

AUTOSAR AP 关键概念（够用即可，深入见专篇）

写 AP 应用基本就是在用 ARA 这套标准化 C++ 命名空间：ara::com（服务化通信）、ara::exec（执行管理）、ara::per、ara::log、ara::crypto、ara::ucm。另外三个词要有概念：Adaptive Application 是可独立部署、启停、升级的进程，接近微服务但受严格的资源与启动时序约束；Execution Management 按依赖关系拉起各应用并管理机器状态，决定「上电到功能可用」的行为，是量产项目最常出问题的一块；UCM 是 OTA 在标准里的落点。

接口长什么样、序列化怎么做见 ARA::Com 深入，状态机见 Execution Management，升级与回滚流程见 UCM，SOME/IP 报文格式与服务发现见 车端网络 · SOME-IP / DDS。

现状与实现选择

「AP 取代 CP」是流传很广但不成立的说法：CP 覆盖车身、动力、底盘与几乎所有传感器执行器，仍是量产主体；AP 只集中在智驾域控、座舱域控、中央计算这几个高算力节点上——数量少，但承载了软件价值增长最快的部分。实现侧是 Vector / Elektrobit / ETAS 等商业栈，开源可参考 vsomeip，但完整可量产的 AP 栈至今没有纯开源替代——工具链、ARXML 配置方法学与认证支持才是真正的壁垒（2026 现状）。

车端 C++ 不允许「随便写」：多个 guideline 把语言裁剪成一个可分析的子集。初接触的人常觉得这些规则是官僚主义，但几乎每条背后都有能说清的工程理由，而且理由往往指向同一件事——让程序的时间与空间行为可以被离线论证。这一节的目标是让你能对每条禁令回答「为什么」。

两条线的由来与合流

MISRA C++:2008 基于 C++03，连 auto 和 lambda 都没覆盖，而 AP 要用现代 C++ 写，于是 AUTOSAR 另出了一套 AUTOSAR C++14；后来 AUTOSAR 把 C++ 指南移交 MISRA，两条线在 MISRA C++:2023（面向 C++17）上合流。实践含义只有一句：新项目对齐 MISRA C++:2023，存量项目继续用 AUTOSAR C++14——核心禁令高度一致，迁移主要是规则编号与个别条款松紧的差异。

规则不是不可违反的，而是「违反必须留痕」。MISRA 有正式的偏差（deviation）流程：违反哪条、为什么必须违反、补偿措施是什么、由谁批准。真正的红线不是「一条都不违反」，而是每一处违反都有记录、有理由、有人签字。最常见的失控是靠 // NOLINT 随手关告警且无人审计——审核时这会变成系统性的过程缺陷，比单个技术问题严重得多。

禁令表面理由真正的工程理由替代做法
禁运行期动态内存

功能安全

跨行业的同一个家族 · ASIL 怎么推出来 · 对开发流程意味着什么

车端 / 工业 / 医疗 / 航空 / 铁路各有自己的功能安全标准，但共享同一套底层思想：先识别危害、评估风险，再按风险等级决定要付出多严格的开发过程与验证证据。它管的不是「代码有没有 bug」，而是「你凭什么说这个系统不会伤人」——要的是一条从危害到需求、设计、代码、测试的完整证据链。

🏗 生活类比：建筑审图。盖一间自家工具房没人管；盖一栋二十层的楼，要出结构计算书、材料检验报告、施工记录，还要第三方审图。不是因为大楼的砖和工具房的砖不一样，而是塌了的后果不一样。安全等级就是这里的「楼层数」：等级越高，同一行代码要附带的证据越多。

ASIL 是怎么推出来的：S × E × C

ASIL 不是拍脑袋定的，也不是给零部件定的，而是在整车层面对每条危害事件做风险评估的产物。三个维度：

S · Severity 严重度

危害发生后对人的伤害程度。
S0 无伤害 · S1 轻中度 · S2 严重但通常可存活 · S3 危及生命。

E · Exposure 暴露概率

车辆处于该危害可能发生的场景中的频度。
E1 很少 → E4 高频（「在高速上行驶」高暴露，「在洗车机里」低暴露）。

C · Controllability 可控性

驾驶员或其他交通参与者能否避免伤害。
C1 一般可控 → C3 难以或无法控制。

三者查 ISO 26262-3 的确定表得到等级。两个有用的直觉：ASIL D 必须同时是 S3 / E4 / C3（致命 + 高频暴露 + 基本不可控），所以一辆车上真正 ASIL D 的功能并不多；反过来降低任意一个维度就能降级——保证驾驶员总能接管（提高 C）、或把危害限制在低速场景（降低 S），等级就往下走一格，开发成本可能减半，这是安全设计最重要的杠杆。完整推导见 ASIL 等级 + 推导方法，把一条高等级需求拆成两条独立低等级需求的做法见 ASIL Decomposition。

「这个模块是 ASIL D 吗？」——这个问法本身就不对。ASIL 属于安全目标，通过安全需求逐层分配到架构元素上；一个模块的等级来自它所实现的安全需求，而同一个模块可能同时承载不同等级的需求。能纠正这个提问本身，比背出 ASIL D 的要求更能说明你真的参与过安全流程。

车端 / 实时实战

隔离与绑核 · 锁页预分配 · 无锁环形缓冲 · 时钟选择 · 周期任务的正确写法

这一章可以直接抄走：六件事覆盖实时应用侧九成的手法，顺序大致是收益从高到低。先看一眼三类场景各自被什么卡住。

① CPU 隔离与绑核：先把地盘清出来

把关键线程钉在某个核上只是第一步，也最容易做错：taskset 只保证「我不被搬走」，不保证「别人不搬过来」，更管不住中断。假设 8 核、4–7 留给实时任务，启动参数只有六项：isolcpus=4-7（从负载均衡摘出去）、nohz_full=4-7（停周期时钟中断）、rcu_nocbs=4-7（RCU 回调会突然占几十 µs）、irqaffinity=0-3、processor.max_cstate=1（从 C6 唤醒要上百 µs），运行时再 cpupower frequency-set -g performance 锁频。

还有一项要有意识地决定：sched_rt_runtime_us 默认每秒最多给实时任务 0.95 秒；关掉它，一个跑飞的 SCHED_FIFO 线程就会真的锁死这个核——只在有独立看门狗兜底时才关。

isolcpus 有个反直觉之处：它把核从负载均衡里摘出去，但并没有禁止任务运行在上面——任何显式把亲和性设到该核的线程照样跑过去。所以配完必须实测验证：cat /proc/cmdline 确认参数真被吃进去了（拼错不报错，只静默失效）、ps -eLo psr,comm,cls,rtprio --sort psr 看每个核上有谁、cat /proc/interrupts 确认隔离核那几列不涨。「配了参数」和「真的干净」之间通常隔着两三个意外发现。

② 中断亲和：把打扰赶到别的核上

/proc/interrupts 每一列是一个 CPU，读它就知道谁在打扰隔离核（顺便也是验证 nohz_full 的地方）。赶走某号中断：echo 0-3 > /proc/irq/42/smp_affinity_list。然后一定要关掉 irqbalance，否则它会周期性地把中断分配回来，跟你对着干。PREEMPT_RT 上中断处理本身是线程，因此也能 chrt 调优先级、taskset 绑核。

中断线程的优先级要低于它服务的实时任务吗？看依赖关系：控制线程要等这个中断送来的数据，它就必须更高，否则数据永远送不进来；和控制线程无关（比如网卡），就必须更低，否则会抢你的 CPU。按数据流依赖排，而不是按「重要程度」的主观感觉排——能说清这一点，基本说明真的调过 RT 系统。

③ 内存锁定与预分配：把缺页挡在启动阶段

一次主缺页可能是毫秒量级，足以毁掉任何实时预算。实时线程稳态时必须一次缺页都不发生，四个动作缺一个都不算做完：mlockall(MCL_CURRENT | MCL_FUTURE)；mallopt(M_TRIM_THRESHOLD, -1) 与 mallopt(M_MMAP_MAX, 0) 让 glibc 别把内存还给内核、别走惰性映射的 mmap；分配一大块再释放预热堆；最后在一个 noinline 函数里声明按 §9.4 定大小的数组并 memset，把栈也预先踩实（不加 noinline 编译器会把这个「没用」的数组优化掉）。

验收判据只有一条：稳态跑 60 秒，ps -o min_flt,maj_flt 两次读数一模一样。禁忌不止 new：printf、日志库、std::string 拼接、第一次调用某个动态库函数（PLT 解析，可用 LD_BIND_NOW 提前绑定）、甚至第一次用浮点（某些平台会惰性初始化 FPU 状态）——任何可能进内核、可能阻塞、可能分配内存的调用都要清出热路径。

④ 无锁环形缓冲：实时线程与非实时线程之间唯一安全的桥

最高频的一个需求：控制线程每 1 ms 产生一批数据，日志 / 上传线程慢慢消费，两者不能互相阻塞。用互斥量是错的——非实时线程持锁时被抢占，实时线程就得等它，这正是优先级反转的教科书场景。正确答案是单生产者单消费者（SPSC）无锁环形缓冲：生产者永不阻塞，最坏只是发现满了然后丢弃。

为什么不用别的：互斥量队列的界包含消费者的整个临界区；std::queue 会动态分配；MPMC 无锁队列能用但复杂得多——SPSC 够用时永远优先 SPSC，它的正确性可以用眼睛看明白。逐条对比见 §11.3 第 10 题，volatile 与 atomic 的区别见 C++ 内存模型。

⑤ 时间：CLOCK_MONOTONIC 与为什么不能用 CLOCK_REALTIME

CLOCK_REALTIME 是墙上时钟，它会跳：NTP 校时、管理员改时间、闰秒都能拨动它。用它算时间差，等于让控制周期依赖运维有没有在这一刻同步时间。真实后果：NTP 一次回拨让「距上次采样多久」算出负数，PID 的微分项据此给出一个巨大的值，执行器猛地动了一下。

所以所有时间差、周期任务、超时都用 CLOCK_MONOTONIC，CLOCK_REALTIME 只用来打时间戳。逐个的坑见 §11.1 第 3 题。

时钟会不会跳专门用途用错的后果
CLOCK_MONOTONIC不向后跳，只受 NTP 频率微调时间差、周期任务、超时—（默认就选它）
CLOCK_REALTIME会跳只用来打时间戳算出负的时间差
CLOCK_MONOTONIC_RAW不跳，也不被校正测硬件频偏不适合长周期定时，会累积偏差
CLOCK_BOOTTIME不跳，含挂起时间会休眠唤醒的设备与 MONOTONIC 混用则跨休眠算错
CLOCK_TAI不跳，无闰秒对齐 PTP / TSN 时间基与 UTC 差若干秒

C++ 侧是同一个坑换了名字：std::chrono::system_clock ≈ CLOCK_REALTIME（会跳），steady_clock ≈ CLOCK_MONOTONIC。测耗时永远用 steady_clock。

⑥ 周期任务：TIMER_ABSTIME 与相对 sleep 的累积误差

区分度极高的一道面试题，也是项目里极常见的 bug。doWork(); usleep(1000); 的实际周期是「工作耗时 W + 1000 µs + 唤醒延迟 L」，而且这个误差每一轮都重新累加：跑 1 小时（360 万轮），只要平均 W + L 有 80 µs 就漂了 288 秒。症状是时间戳对不上、与 PLC / 总线主站逐渐失步、采样率比标称低几个百分点。

正确写法是 clock_gettime(CLOCK_MONOTONIC, &next) 只在循环外取一次，之后每轮 next += 周期 并用 clock_nanosleep(..., TIMER_ABSTIME, &next, nullptr) 睡到那个绝对时刻。三个不能漏的细节：时钟必须与取时间那次一致；EINTR 时要 continue 继续睡到同一个时刻而不是重算；还要做超时检测并计数上报，同时明确「落后太多是追赶还是重新对齐」（通常选重新对齐）。完整实现见 §11.2 第 7 题。

为什么绝对时间能消除累积误差：相对 sleep 每轮以「现在」为基准，误差被加进下一轮起点；绝对时间的基准是一条独立于执行过程的时间轴，单轮抖动只影响那一轮，下一轮自动回到网格上。这就是抖动（有界、不累积）与漂移（单调累积）的区别。

最后是本章的样板。只看这几行就能判断一个 Linux 进程有没有真的在做实时——没有 mlockall、没有 SCHED_FIFO、没有 PTHREAD_EXPLICIT_SCHED，那它只是个普通线程，无论上面配了多少内核参数：

// ① 进程级：一次性锁页 + 预热。少了这一步，后面全都白配。
mlockall(MCL_CURRENT | MCL_FUTURE);

bool spawnRtThread(pthread_t& tid, void* (*fn)(void*), int prio, int cpu) {
  pthread_attr_t attr;
  pthread_attr_init(&attr);

  // ② 栈大小按 §9.4 的最坏栈分析来定，别用默认的 8 MB —— 锁页时会白锁 8 MB。
  pthread_attr_setstacksize(&attr, 512 * 1024);

  // ③ 不继承父线程的调度参数。忘了这一行，下面两行设置全部无效，
  //    而且不会有任何报错 —— 这是本章最常见的一个静默失败。
  pthread_attr_setinheritsched(&attr, PTHREAD_EXPLICIT_SCHED);
  pthread_attr_setschedpolicy(&attr, SCHED_FIFO);

  sched_param sp{};
  sp.sched_priority = prio;                          // 1..99，越大越高
  pthread_attr_setschedparam(&attr, &sp);

  // ④ 绑核：钉到 isolcpus 划出来的那几个核之一。
  cpu_set_t set; CPU_ZERO(&set); CPU_SET(cpu, &set);
  pthread_attr_setaffinity_np(&attr, sizeof(set), &set);

  const int rc = pthread_create(&tid, &attr, fn, nullptr);
  pthread_attr_destroy(&attr);
  return rc == 0;      // EPERM = 缺 CAP_SYS_NICE / RLIMIT_RTPRIO
}

嵌入式调试

从 printf 到 ETM 的手段谱系 · GPIO 翻转法 · 现象到工具的决策表

嵌入式调试与服务端调试最大的差别：观测行为本身会改变被观测的时序。在 1 ms 周期的控制环里加一行 printf 可能直接把周期撑爆，于是你要找的 bug 消失了，换来一个新的。核心技能因此是按侵入程度选工具。

海森堡 bug 是这个领域的常态。「加了打印就不复现，去掉又复现」几乎总意味着问题与时序或竞态有关：未加保护的共享变量、缺少的内存屏障、恰好落在中断边界上的状态更新。正确反应不是加更多打印，而是换一种零 / 低侵入的手段（GPIO 翻转、RTT、硬件 trace），把时序保持原样再看。

手段谱系：按侵入程度排序

手段侵入程度能看到什么典型场合
printf / 串口🔴 高（阻塞、格式化、可能加锁）任意变量与流程启动阶段、非时序敏感的逻辑
SEGGER RTT🟡 低（写内存环形缓冲）同 printf，但不阻塞时序敏感场景下 printf 的替代品
GPIO 翻转 + 示波器🟢 极低（一次寄存器写）精确的时间关系：中断延迟、执行窗口、抖动测时延与抖动的首选

GPIO 翻转法：朴素但最有效的时延测量

做法土到不值一提：在关心的代码前后各翻一次 GPIO，用示波器量脉冲。MCU 上一定用 BSRR 这类置位 / 清零专用寄存器，不要用 ODR ^= mask——那是读-改-写，更慢而且不原子（写法见 §11.2 第 8 题）。示波器上一次读出三个量：脉冲宽度 = 执行时间（最宽那个就是实测最坏值）、上升沿间隔 = 实际周期、触发源到上升沿 = 中断延迟；开无限余辉看边沿的「胖度」就是抖动的可视化。Linux 用户态走 GPIO 字符设备（不要再用已废弃的 sysfs），但那段路径本身有开销。

它的价值不在于「没有更好的工具」，而在于测的是物理世界里真实发生的时间。软件内部的计时都在被测系统之内，会被同样的调度延迟与缓存效应影响；示波器在系统之外，它不会撒谎。当软件说「我只用了 200 µs」而系统表现对不上时，示波器是唯一的仲裁者。

硬件接口速查

JTAG 4–5 根线、可菊花链、几乎所有 SoC 都支持；SWD 是 ARM 的两线精简版，Cortex-M 主流；SWO / ITM 是单向单线输出，把软件打点推给探针，比 UART 快且不占应用的串口；ETM 是硬件级指令流记录，需要芯片支持与专门引脚，但对「跑飞到不存在的地址」几乎是唯一手段。

调试器 + 工具

探针侧 J-Link / ST-Link / DAPLink / Black Magic Probe，trace 侧 SEGGER J-Trace、Lauterbach TRACE32，软件侧 OpenOCD 做后端配 GDB。选型时务必确认 RTOS-aware 调试可用——它让 GDB 认识 FreeRTOS / Zephyr 的内部结构，能列出所有任务并切到某个任务的栈上；没有它，多任务死锁的定位效率差一个数量级。

典型 GDB 远程调试

MCU 与 Linux 目标形态完全不同：前者调试器停整颗芯片，后者只停一个进程。

Linux 目标上：ftrace 抓一次延迟尖峰

「我的实时线程偶尔晚了 800 µs」有标准解法：让内核在延迟超阈值时自动把前后的事件流 dump 出来，而不是靠人守着。cyclictest -b 500 --tracemark 一超阈值就停掉 trace，再用 trace-cmd report 找 tracing_mark_write 往前翻——是哪个 kworker、哪个中断线程、还是一段很长的内核函数，通常一眼可见。6.x 的 rtla timerlat top 更好用且能区分 IRQ 层与线程层，rtla osnoise hist 直接量化「谁在偷 CPU、偷了多久」。

需要长期在线、统计聚合时换 eBPF（eBPF 可观测性）；升级成内核崩溃或整机卡死则是另一套方法（内核崩溃分析）；驱动层面见 Linux 设备驱动。

先说清楚：和服务器性能优化不是一回事

从服务端转来的人带着一整套成熟直觉：加缓存、加线程、加内存、多测几次取平均。这些直觉在嵌入式上有一半是错的。

栈使用分析：最坏栈深度必须是个已知的数

没有 MMU 的 MCU 上，栈溢出不会给你一个整洁的段错误，它会安静地覆盖掉相邻的变量，然后在几天后以完全无关的形式炸出来。这是嵌入式最难查的一类 bug，但完全可以预防——前提是你知道每个任务的最坏栈用量。

三种手段配合用。-fstack-usage 给出每个函数自己那一帧的大小，标 dynamic 的含 VLA 或 alloca（安全项目应直接禁止）；-fcallgraph-info=su,da 把帧大小沿调用图累加得到每条路径的最坏值，而递归与函数指针会让调用图不闭合——这正是 §5 禁它们的原因。第三种最便宜：栈涂色，启动时把整块栈填成 0xA5A5A5A5，长跑后数还有多少字没被覆盖就是实测最高水位（uxTaskGetStackHighWaterMark() 就是这个原理）。

实测水位不能直接当作栈大小的依据。它只说明「测过的路径上用了这么多」，而最坏路径可能是一条极少走到的错误处理分支——恰恰这类路径在现场偶发触发时最容易溢出。正确做法是静态分析给上界、实测水位做交叉验证，取静态上界并留裕度，同时开栈溢出检测（MPU 保护页、RTOS 溢出钩子，或至少在栈底放个哨兵值周期检查）。

DMA 与中断合并：让 CPU 别做搬运工

收益最大的改动往往不是把代码写快，而是把 CPU 从数据通路上移走。

DMA 替代 CPU 搬运

ADC 采样、SPI 收发、以太网收包由 CPU 逐字节搬，既慢又占满中断；改成 DMA 后 CPU 只在整块传输完成时被中断一次。典型配置是双缓冲：DMA 往 A 写的同时 CPU 处理 B，完成中断里交换——采集与处理完全并行且零拷贝。

陷阱是 cache 一致性：DMA 读写物理内存，CPU 看到的可能是过期的 cache 行。要么把缓冲放非缓存区，要么手动维护，而方向搞反是最常见的形态——发送前 clean（把写刷进内存），接收后 invalidate（丢弃手里的旧副本）。

中断合并（coalescing）

每秒十万个小包、每包一次中断，光中断开销就能吃掉一个核。合并就是「攒够 N 个或超时 T µs 才中断一次」。

这是一笔明确的延迟换吞吐：窗口 T 直接加到单个事件的最坏延迟上。实时路径上要么关掉它，要么把 T 设得远小于预算。同一思路的其它形态：多个软件定时器共用一个硬件定时器、一次唤醒批量处理多个队列元素。

功耗与确定性：DVFS 是一个陷阱

DVFS 在手机上是纯收益，在实时系统里是确定性的直接破坏者：它让 WCET 失去意义（1.2 GHz 下算的 200 µs 降到 400 MHz 就是 600 µs）、切换本身是额外的抖动源、而且调速器是反应式的——它看到负载上升才升频，而实时任务恰恰在「负载刚上升那一刻」最需要算力。深度 C-state 同理。标准做法是锁频 + 禁深度睡眠（§7.4），代价是功耗与发热明显上升；展开见 §11.3 第 11 题。

测量手段：没有 perf 的时候怎么办

四档逐级降级。① 有 Linux 就用 perf stat / perf record，但采样式 profiler 回答的是「时间总体花在哪」，它天然看不到「那一次特别慢」。② Cortex-M 上用 DWT->CYCCNT（先置 DEMCR 的 TRCENA），分辨率一个时钟周期，但 32 位计数器在 200 MHz 下约 21 秒绕一圈，而且一定要自己维护最大值。③ 什么都没有时回到 GPIO 打点 + 示波器（§8.6）。④ RTOS 自带的运行时统计回答「预算花在谁身上」，但时间基太粗，不适合测单次执行时间。

这一章最值得强调的一句：我们测的是最大值，不是平均值。服务端 profiler 天生面向「时间总体花在哪」，实时系统关心「最慢的那一次为什么慢」。所以 trace 优先于 profile——这是 §1 的「实时 ≠ 快」在测量层面的体现。

11.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础什么是实时系统？"实时"等于"快"吗？

    不等于。实时的定义是「最坏情况响应时间有可论证的上界」，与平均速度无关。一台 3 GHz 服务器的平均中断响应可能是 2 µs，比 100 MHz 的 MCU 快一个数量级，但它的最坏值可能是 8 ms，而 MCU 是 3 µs。对一个必须每 250 µs 完成一次采样的控制回路来说，只有那个最坏值决定系统能不能用。

    把它拆成两句更完整：① 系统必须在规定的时间内完成响应；② 这个时间上界必须是可以事先论证的，而不是"跑了一周没出问题"。

    由此推出实时工程的核心交易：用平均性能买确定性。锁定 CPU 频率、禁用深度睡眠、把中断改成线程、禁用动态内存，每一项都在牺牲吞吐或功耗，换取"最坏情况可预测"。能主动说出这笔交易，比背定义有说服力得多。

  2. 基础硬实时、软实时、准实时（firm）怎么区分？

    划分依据不是时间尺度，而是错过一次 deadline 的后果。很多人以为"µs 级是硬实时、ms 级是软实时"，这是错的——一个 100 ms 周期的气囊自检是硬实时，一个 1 ms 刷新的仪表动画是软实时。

    • 硬实时：错过即系统失效，可能造成人身伤害或设备损毁。迟到的结果比没有结果更糟（一个迟到的刹车指令会让车在错误的时刻减速）。例：ABS、气囊点火、飞控内环、电机换相。
    • 准实时 firm：错过则该次结果作废（价值直接归零），但系统继续运行。例：一帧迟到的视频画面，直接丢掉即可。
    • 软实时：错过则价值逐渐衰减，仍然可用。例：UI 动画掉帧、日志上报延迟。

    工程上的用法：写需求时先问"迟到的结果比没有结果更糟吗"。这一句能定下等级，进而决定要不要上 RTOS、要不要做 WCET 分析、要不要走认证——省掉后面大量的争论。

  3. 基础CLOCK_MONOTONIC 和 CLOCK_REALTIME 有什么区别？该用哪个？

    所有时间差计算、周期任务、超时判断都必须用 CLOCK_MONOTONIC。CLOCK_REALTIME 是墙上时钟，它会跳：NTP 校时会向前或向后拨、管理员可以直接设置它、闰秒也会影响它。

    后果不是理论上的。一次 NTP 回拨会让"距上次采样过去了多久"算出负数，PID 的微分项据此算出一个巨大的值，执行器猛动一下——这类事故在工业现场真实发生过，而且极难复现（它只在校时的那一瞬间发生）。

    其他几个时钟的分工：

    • CLOCK_MONOTONIC_RAW：完全不受 NTP 频率校正影响。适合测量硬件本身的频偏，但正因为不被校正，长时间会与真实秒有累积偏差，不适合做长周期定时。
    • CLOCK_BOOTTIME：与 MONOTONIC 类似但包含系统挂起的时间。会休眠唤醒的设备（车机、电池设备）上要特别分清这两者。
    • CLOCK_TAI：无闰秒，用于与 PTP / TSN 的时间基对齐。

    C++ 侧是同一个坑换了名字：std::chrono::system_clock 对应 REALTIME（会跳），steady_clock 对应 MONOTONIC。测耗时永远用 steady_clock。

  4. 基础为什么车端 C++ 禁止运行期动态内存？

    不是因为 malloc 慢——它其实常常很快。真正的理由有三层，而且都指向可论证性而不是性能：

    • 耗时不确定：分配时间取决于堆当前的碎片状态，是运行历史的函数，无法给出 WCET 上界。
    • 碎片会随运行时间累积：一个跑三年的 ECU 可能在第三年某天分配失败。这种失效在测试里几乎不可能复现——你没法测三年。
    • 分配可能失败：于是每个调用点都多出一条极难覆盖的错误路径，而高等级认证要求结构化覆盖率。

    替代做法是初始化阶段一次性预分配：内存池、固定容量容器（容量作为模板参数），运行期只从池里取。

    加分的一句：换成固定容量容器不等于问题消失，只是把问题挪到了显眼处。原来 vector 会默默增长，现在 push_back 返回 false，于是"满了怎么办"变成一个必须由需求回答的问题——丢最旧的？丢最新的？置故障码？这正是这条规则的价值：逼你在设计阶段面对容量上界，而不是在现场。

11.2 中级（区分熟练度）

  1. 中级WCET 为什么测不准？跑一百万次取最大值不行吗？

    不行，而且这个说法本身就搞反了方向：实测只能给出下界（证明"至少这么慢"），永远给不出上界。你测到的最大值只意味着"在测过的这些条件下没见过更慢的"。

    根本原因是执行时间不只取决于代码，还取决于你无法完全控制的微架构状态：

    • Cache：同一段代码全命中 L1 和全落 DRAM 能差十倍以上，而命中与否取决于"刚才是谁在这个核上跑"。多任务系统里这是外部输入，专门有个名词叫 cache-related preemption delay，是可调度性分析里的独立项。
    • 分支预测器与预取器：状态由历史执行路径决定，是隐藏的全局变量，厂商通常不公开替换策略，静态分析只能保守假设"全部预测失败"。
    • DVFS 与热降频：频率变了，绝对耗时跟着变。
    • DRAM 刷新、总线争用、x86 的 SMI：SMI 由固件触发，操作系统既无法屏蔽也无法观测，是很多 x86 实时平台上无法解释的毫秒级尖峰的来源。
    • 路径爆炸：循环上界不明、函数指针、递归都会让路径集合无法闭合。

    工业界的做法是两条腿：静态分析工具（AbsInt aiT、Rapita RapiTime 一类）沿控制流图算出一个保证不低于真实值的保守上界，再用大量实测取上包络做交叉验证。静态上界通常明显高于实测最大值，这部分"浪费"就是确定性的价格。

    最后一句反过来说明了 §5 那些编码规则的由来：禁递归、要求循环上界编译期可知、限制函数指针，都是为了让路径集合能够闭合，否则静态分析根本无法开始。

  2. 中级抖动（jitter）和平均延迟是什么关系？为什么报告里要看 Max 不看 Avg？

    平均延迟描述分布的中心，抖动描述分布的离散程度（工程上常用 max − min 或高分位数与中位数之差）。实时系统的成败由分布的右端决定，而平均值对右端几乎没有信息。

    一个具体的例子：cyclictest 报告 Min: 2 Avg: 5 Max: 78（µs）。Min 和 Avg 三个数字里唯一有意义的是 78。如果 deadline 是 50 µs，那么这个系统已经失败了——尽管 99.99% 的样本都在 8 µs 以内。

    三个容易被忽略的推论：

    • 空载测出来的 Max 没有参考价值。延迟尖峰几乎都由"别人在干活"引发：网卡收包风暴、磁盘回写、图形合成、内存回收。必须一边施加最恶劣的干扰一边测。
    • 测 1 小时 Max 是 78 µs，不代表跑一年不会出现 900 µs。要么把测试时间拉长到与产品寿命可比（不现实），要么去分析尖峰的成因——只有搞清"78 µs 那次是谁造成的"，才能论证不会有更差的情况。
    • 抖动和漂移是两回事。抖动是有界且不累积的随机偏差；漂移是单调累积的系统性误差（下一题）。混用这两个词会让人怀疑你的实际经验。
  3. 中级怎么写一个精确的 1 kHz 周期任务？用 usleep(1000) 有什么问题？

    usleep / 相对 sleep 的问题是误差会累积成漂移，而不只是抖动。

    // ❌ 相对 sleep：实际周期 = 工作耗时 W + 1000 µs + 唤醒延迟 L
for (;;) { doWork(); usleep(1000); }

    关键在于每一轮都以"现在"为新基准，于是 W + L 被加进下一轮的起点，误差单调累积。跑 1 小时（360 万轮），若平均 W + L 只有 80 µs，就已经漂了 288 秒——将近 5 分钟。症状是：数据时间戳与实际不符、与外部设备（PLC、总线主站）逐渐失步、实际采样率比标称低几个百分点。

    正确做法是用绝对时间：

    timespec next{};
clock_gettime(CLOCK_MONOTONIC, &next);   // 只在循环外取一次"现在"
for (;;) {
  tsAddNs(next, kPeriodNs);              // next = start + n × period
  clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, nullptr);
  doWork();
}

    TIMER_ABSTIME 表示"睡到这个绝对时刻"，而不是"从现在起睡多久"。基准是一条独立于执行过程的时间轴，单轮的抖动只影响那一轮，下一轮自动回到网格上。抖动仍然存在（有界），但漂移消失了。

    三个必须一并说到的细节，否则答案不完整：

    • 时钟必须用 CLOCK_MONOTONIC，且与 clock_gettime 保持同一个。
    • 返回 EINTR（被信号打断）时要 continue 继续睡到同一个时刻，而不是重新计算。
    • 必须做超时检测：如果 doWork 比周期还慢，next 会落到过去，clock_nanosleep 立刻返回，任务开始"追赶"。这必须被计数并上报，同时要明确"落后太多时是追赶还是重新对齐"——通常选重新对齐，因为追赶只会让系统雪上加霜。
  4. 中级怎么测一个中断的响应延迟？为什么 GPIO 翻转法比在代码里打时间戳更可信？

    做法：在 ISR 入口写一次 GPIO 拉高、出口拉低，用示波器的两个通道分别接触发源和这根调试引脚，直接量两个沿之间的时间。

    // 用 BSRR 这类"置位/清零专用寄存器"，一次写完成，开销只有几个时钟周期。
// 不要用 ODR ^= mask —— 那是读-改-写，更慢而且不原子。
void TIM2_IRQHandler(void) {
  GPIOA->BSRR = (1U << 5);        // ISR 开始
  controlStep();
  GPIOA->BSRR = (1U << 21);       // ISR 结束（高 16 位是清零域）
}

    示波器上一次读出三个量：脉冲宽度 = ISR 执行时间（游标放在最宽的那个就是实测最坏值）、上升沿间隔 = 实际周期、触发源到上升沿 = 中断延迟。开无限余辉模式看边沿的"胖度"，就是抖动的可视化。

    为什么比软件时间戳可信：任何软件内部的计时都在被测系统之内，会被同样的调度延迟、cache 效应、中断屏蔽影响；而且它测不到"从电平变化到软件第一条指令"这一段——那一段恰恰是中断延迟的主体。示波器在系统之外，它不会撒谎。当软件说"我只用了 200 µs"而系统表现对不上时，示波器是唯一的仲裁者。

    Linux 目标上的补充手段：cyclictest -b <µs> 在超阈值时自动停止内核 trace，再用 trace-cmd report 往前翻看那段时间 CPU 上在跑什么；或者用 rtla timerlat 分别给出 IRQ 层与线程层的延迟，直接定位是哪一段慢。

11.3 高级（体现深度）

  1. 高级什么时候选 RTOS，什么时候选 Linux + PREEMPT_RT？

    按硬约束优先的顺序问四个问题，能砍掉九成候选：

    1. 算力与内存：KB 级 RAM、无 MMU → 只能是 RTOS 或裸机，讨论结束。有 MMU 和几百 MB 内存才谈得上 Linux。
    2. 要不要认证：需要 ISO 26262 / IEC 61508 / DO-178C 的高完整性等级时，Linux 通常不是主路径——代码规模与开发过程难以满足证据要求。常见架构是安全功能放认证 RTOS（QNX、VxWorks、SafeRTOS），Linux 只承担 QM 或低等级部分，中间用 hypervisor 隔离。
    3. 要不要 Linux 生态：需要 TCP/IP 栈、文件系统、容器、Python/AI 框架、厂商 BSP 时，自己在 RTOS 上重造这些的成本极高。
    4. 最坏延迟指标：≥ 500 µs → PREEMPT_RT 有充足裕度；50–200 µs → 必须在目标板上实测才能定（x86 的 SMI、某些 SoC 的总线争用都可能一票否决）；< 20 µs → 不要用 Linux，它的中断路径固定开销就压不到这个量级，该回 MCU 或把这一环下沉到 FPGA。

    还要说清 PREEMPT_RT 的代价，否则答案只有一半：吞吐下降（中断密集与锁密集的负载最明显）、功耗上升（禁 C-state、锁频率）、CPU 被隔离核"浪费"、以及驱动兼容性——假设"自旋锁不会睡眠"的老驱动会直接触发 BUG: sleeping function called from invalid context，这是实际项目里最常见的卡点。

    加分：提到 2024 年 PREEMPT_RT 完成主线化（Linux 6.12 LTS）。它的意义不在于延迟数字变好（基本没变），而在于长期维护成本塌方式下降——以前每次跟内核版本都要 rebase 一大摞补丁，现在 RT 是主线的一等公民。这一项因此可以从选型的风险表里划掉了。

    还有一档中间形态：双内核（Xenomai）。实时任务由旁边一个独立的实时内核调度，完全不受 Linux 影响，代价是实时代码要用它自己的 API、跨界调用有开销、维护负担高于主线 RT。自 PREEMPT_RT 进主线后，新项目选它的理由已经少很多。

  2. 高级实时线程要把数据交给一个会阻塞的日志线程，怎么设计才安全？

    答案是单生产者单消费者（SPSC）无锁环形缓冲，并且队列满时由实时线程直接丢弃并计数。

    先说为什么不能用互斥量：非实时线程持锁时被抢占，实时线程就得等它——这是优先级反转的教科书场景。即使启用了 PTHREAD_PRIO_INHERIT，最坏情况也只是从"无界"变成"有界但不小"，那个界包含消费者的整个临界区，通常远超时间预算。

    实现要点（每一条都对应一个真实的坑）：

    • 容量取 2 的幂，取模退化成一次与运算，避免除法。
    • head_ 与 tail_ 必须 alignas(64) 分处不同 cache line。否则生产者每次写 head_ 都会让消费者所在核上缓存 tail_ 的那行失效——这就是 false sharing，实测能让吞吐掉一个数量级，而且它只在多核上出现，单核测不出来。
    • 内存序：写自己的索引用 relaxed（只有我写），读对方的索引用 acquire，发布自己的索引用 release。release 保证数据写入对看到新索引的对方一定可见。
    • 用 std::atomic 而不是 volatile。volatile 不提供任何内存序保证，编译器和 CPU 都可以重排它前后的普通访问。它的用途是访问外设寄存器（禁止合并/省略访问），不是线程同步——这是嵌入式代码里最普遍的一个错误认知。
    • 元素类型应可平凡拷贝，避免拷贝过程本身分配内存。

    最重要的一条设计原则：实时线程永不阻塞、永不重试。满了就丢，把丢弃计数上报到诊断。控制回路的时序比某一条日志重要得多；而"丢弃可见"让容量是否够用变成一个可以被数据回答的问题。

    加分：说明为什么不用 MPMC 无锁队列——能用，但实现复杂度与最坏重试次数都高得多。SPSC 能满足需求时永远优先 SPSC，因为它的正确性可以用眼睛看明白。

  3. 高级DVFS 对实时性有什么影响？为什么实时系统通常要锁定频率？

    DVFS（动态调频调压）在手机和服务器上是纯收益，在实时系统里是确定性的直接破坏者，三层原因：

    1. 让 WCET 失去意义：按 1.2 GHz 算出的 200 µs，降到 400 MHz 就变成 600 µs。除非一律按最低频率算 WCET——那等于放弃 DVFS 的全部收益。
    2. 切换本身有过渡时间，期间 CPU 可能暂停执行，是一个额外的、不易预测的抖动源。
    3. 调速器是反应式的：它看到负载上升才升频，而实时任务恰恰在"负载刚上升的那一刻"最需要算力。等它反应过来，deadline 已经过去了。

    同样的逻辑适用于深度 C-state：从深睡眠唤醒可能要几十到上百微秒，对 µs 级预算是致命的。所以标准做法是 performance 调速器锁定频率 + processor.max_cstate=1 + idle=poll，代价是功耗与发热明显上升。

    更好的答案会给出不必二选一的架构：分区——实时任务跑在锁频的隔离核上，其余核正常调频省电；或者用一颗独立的低功耗 MCU 承担实时部分，主 SoC 该睡就睡。这在电池供电又有硬实时需求的产品上是常规解法，代价是系统复杂度和跨核通信设计。

    再加一句：这与 §1 的主线是同一件事——DVFS 优化的是期望值（平均能效比），实时优化的是分布右端，两个目标在这里直接冲突，必须明确选一个。

  4. 高级给你一个新项目：1 kHz 的运动控制回路，需要以太网上报数据和一个本地触摸界面。你怎么做技术选型？

    这是综合题，考的是提问的顺序而不是最终结论。

    第一步：把需求问清楚，尤其是没写在需求文档里的那几个数。

    • 1 kHz 的抖动预算是多少？"周期 1 ms"是无意义的，"周期 1 ms 且抖动 < 50 µs"才是可验收的指标。这个数直接决定了后面所有选择。
    • 错过一次的后果是什么？工件报废（firm）还是可能伤人（hard）？后者意味着要走认证，成本结构完全不同。
    • 控制算法的计算量有多大？如果单次要 800 µs，1 kHz 就没有裕度，这时候要先谈算法而不是谈 OS。
    • 产量多少？单价敏感度决定了能不能用一颗好的 SoC，还是必须精打细算 BOM。

    第二步：先给一个架构假设，再验证。三个需求的实时性要求差三个数量级（1 kHz 控制 / 网络上报 / 触摸 UI），把它们塞进同一个执行环境是错误的起点。我会先提出分层架构：

    • 控制回路：绝不与 UI 抢资源。两个候选——(a) Linux + PREEMPT_RT，控制线程跑在隔离核上；(b) 独立 MCU 跑 RTOS 或裸机，通过 SPI / 以太网与主控通信。
    • 上报与 UI：普通 Linux 线程，通过 SPSC 无锁环形缓冲从控制侧拿数据，满了丢弃并计数。

    第三步：用实测在 (a) 和 (b) 之间做决定，而不是靠偏好。拿目标硬件跑 cyclictest，一边跑一边施加最恶劣的干扰（网络满载 + 磁盘写 + GPU 合成 + 真实业务流量），看 Max 是否在抖动预算的一半以内。如果预算是 50 µs 而实测 Max 是 120 µs，就走 (b) 的双芯片方案；如果实测 Max 是 30 µs 且能解释每一次尖峰的来源，(a) 可以省掉一颗芯片和一套通信。

    第四步：把工程配置一次做全。核隔离 + nohz_full + rcu_nocbs + 中断亲和 + 关 irqbalance + 锁频率 + 禁深度 C-state；应用侧 mlockall + 栈预热 + 启动阶段完成全部分配 + SCHED_FIFO 并按周期长短排优先级（单调速率）+ clock_nanosleep(TIMER_ABSTIME) 写周期循环。

    第五步：定义验收与长期监控。周期超时要计数上报、环形缓冲丢弃要计数上报、稳态下缺页数必须为零、长跑测试要覆盖最恶劣工况。没有这些指标，"实时性达标"就只是一句话。

    最能体现层次的一句收尾：如果 (a) 和 (b) 实测结果接近，我会选 (b) 双芯片——不是因为它性能更好，而是因为它把"确定性"和"生态"两个诉求做了物理隔离，后续加功能时不会有人不小心把一个新服务放到隔离核上，从而毁掉整个时序论证。架构选择要考虑的不只是今天能不能跑，还有三年后被别人改成什么样。
