01

实时系统全景

实时 ≠ 快 · 硬 / 准 / 软三档 · 关键指标与 WCET · 场景对照

整个领域的第一块基石只有一句话：实时的定义是「最坏情况有界」，不是「平均很快」。一台 3 GHz 的通用 Linux 服务器处理一个中断的平均时延可能只有 2 µs，比一块 100 MHz 的 Cortex-M4 快一个数量级；但前者的最坏值可能是 8 ms，后者是 3 µs。对一个必须每 250 µs 采样一次电流的电机控制回路来说，平均值毫无意义，只有那个最坏值决定系统能不能用。

一句话判据：如果你能回答「这个动作最坏要多久，以及这个上界是怎么论证出来的」，你在做实时系统；如果你只能回答「一般几微秒，偶尔会慢一点」，你在做低延迟优化。两件事都值得做，但它们不是同一件事，验收方式也完全不同。

这个区别之所以反直觉，是因为日常工程训练几乎都在优化期望值：QPS、平均响应时间、吞吐量。而实时工程优化的是分布的右端，并且愿意为此牺牲期望值——关掉 CPU 深度睡眠会多耗电、多发热，禁用动态频率会损失几十个百分点的峰值性能，把中断改成线程会增加每次中断的固定开销。这些都是在用平均性能买确定性，是整个领域反复出现的同一笔交易。

🚇 生活类比：地铁 vs 出租车。从家到公司，出租车平均25 分钟，地铁固定 40 分钟。如果只看平均，出租车完胜。但出租车遇上事故封路可能要 2 小时，而地铁最坏也就 50 分钟。赶飞机的时候所有人都选地铁——因为你要的不是「期望到达时间最短」，而是「保证在某个时刻前到」。RTOS 就是地铁：单看吞吐它比不过通用 Linux，但它给你一个能写进规格书的上界。

映射：平均通勤时间 = 平均延迟 · 最坏通勤时间 = WCET / 最坏响应时间 · 误机 = 错过 deadline · 地铁少载客 = 确定性的吞吐代价。

3 个等级：区别不在时间尺度，在失效后果

硬 / 准 / 软的划分经常被误解成「µs 是硬实时、ms 是软实时」。时间尺度只是表象，真正的分类依据是「错过一次 deadline 会发生什么」。一个每 100 ms 触发一次的安全气囊自检是硬实时（错过就是安全事件），一个每 1 ms 刷新一次的仪表盘动画是软实时（错过就是掉一帧）。

硬实时 Hard 错过 deadline = 系统失效 / 物理危害。例：飞控、ABS 刹车控制、医疗注射泵。典型延迟 deadline：µs 级，jitter 必须 < deadline。
准实时 Firm 错过 deadline = 该任务无效，但系统继续。例：视频帧抖动、音频包延迟。典型延迟：ms 级。
软实时 Soft 错过 deadline = 体验下降，可接受。例：UI 渲染、游戏帧率、网络服务 P99。典型延迟：10-100 ms。

准实时（firm）这一档最容易被忽略，但它在工业和车载里占比很高。判据是「迟到的结果比没有结果更糟吗」：一帧迟到的视频画面直接丢掉即可（firm）；但一个迟到的刹车指令会让车在错误的时刻减速，比不减速更危险（hard）。写需求时把这一句问清楚，能省掉后面大量关于「要不要上 RTOS」的争论。

为什么 WCET 测不准，只能给保守上界

WCET 是整个实时工程里最硬的一块骨头。直觉上「跑一百万次取最大值」就够了，但现代处理器上这个直觉是错的，原因是执行时间不只取决于代码，还取决于你无法完全控制的微架构状态：

  • Cache——同一段代码，全命中 L1 和全落到 DRAM 可能差 10 倍以上。而命中与否取决于「刚才是谁在这个核上跑」，这在多任务系统里是外部输入。抢占越多，cache 相关的抖动越大（这叫 cache-related preemption delay，是可调度性分析里的一个独立项）。
  • 分支预测器 / 预取器——它们的状态由历史执行路径决定，是隐藏的全局变量。厂商通常不公开替换策略细节，静态分析只能做保守假设「全部预测失败」。
  • DVFS 与热降频——CPU 频率会随负载和温度变化。同一段代码在 2.4 GHz 和降频到 800 MHz 时的绝对耗时差 3 倍。做实时时通常直接锁定频率，宁可一直烧那么多电。
  • DRAM refresh、SMI、总线争用——DRAM 刷新期间访问会被拖住；x86 上的系统管理中断（SMI）由固件触发、操作系统完全无法屏蔽也无法观测，是很多 x86 实时平台上无法解释的毫秒级尖峰的来源。
  • 路径爆炸——静态分析要枚举所有可能路径，而循环上界不明确、函数指针、递归都会让路径集合无法闭合。这正是车端 C++ 禁递归、要求所有循环有编译期可知上界的直接原因（见 §5）。

所以工业界的做法是两条腿走路：用静态分析工具（如 AbsInt aiT、Rapita RapiTime 这类）沿控制流图算出一个保证不低于真实值的上界，再用大量实测取上包络做交叉验证。静态上界通常比实测最大值高出可观的比例（具体倍数强烈依赖平台与代码，不宜一概而论），这部分「浪费」就是确定性的价格。

被问到「你们的 WCET 怎么定的」时，回答「压测一周取最大值再乘 2」会立刻暴露层次。正确的表述是：实测只能给出下界（证明至少这么慢），不能给出上界；上界必须来自静态分析或对硬件行为的保守假设。能顺带说出 cache-related preemption delay 和 SMI 这两个具体机制，基本就说明真的做过。

  • µs 级硬实时 → RTOS / bare metal
  • ms 级准实时 + 需要 Linux 生态（网络栈、文件系统、SDK）→ PREEMPT_RT
  • 10-100 ms 软实时 + 高吞吐 → 通用 Linux + 应用层 tune（cgroup / nice / SCHED_FIFO）
  • 混合需求（infotainment + safety）→ Hypervisor + 多 OS（如 QNX + Linux）

还有一档常被忽略的中间形态：双内核（dual-kernel），代表是 Xenomai。它在 Linux 旁边跑一个独立的实时微内核，实时任务由后者调度、完全不受 Linux 影响，非实时部分照常用 Linux 生态。代价是实时代码要用它自己的 API（Xenomai 的 Cobalt 内核提供了若干 skin 来兼容 POSIX 与其他 RTOS 接口），跨界调用有额外开销，且内核升级时的维护负担明显高于主线里的 PREEMPT_RT。自从 PREEMPT_RT 进入主线，新项目选双内核的理由已经比十年前少很多——除非你需要的确定性确实是 PREEMPT_RT 给不了的（见 §3 的横向对比表）。

02

PREEMPT_RT — Linux 准实时化

解决什么 · 代价是什么 · 够用 / 不够用的判据 · 主线化这个节点

通用 Linux 的最坏调度延迟能到几百毫秒，原因不是「代码写得慢」，而是内核里存在大量不可抢占的区间：自旋锁临界区、软中断处理、硬中断上下文。一个高优先级实时线程就绪时，如果 CPU 正在跑这些区间，它只能等——等多久取决于当时恰好在跑哪段代码，而这是不可控的。PREEMPT_RT（Ingo Molnar、Thomas Gleixner 等人主导了近二十年）的全部工作就是系统性地消灭这些不可抢占区间。

核心改动（概览）

  • 自旋锁 → 可睡眠的 RT mutex：内核里绝大多数 spinlock_t 在 RT 下变成支持优先级继承的睡眠锁，持锁期间可以被抢占。真正不能睡的地方改用显式的 raw_spinlock_t。
  • 中断处理线程化：硬中断上下文只做最小的确认动作，主体逻辑跑在一个普通的内核线程里（irq/N-<name>），于是它受调度器管辖——可以设优先级、可以绑核、可以被更重要的实时线程抢占。
  • 优先级继承：低优先级线程持有高优先级线程要的锁时，临时把它的优先级提上来，避免优先级反转（1997 年火星探路者号反复重启就是这个问题的经典案例）。原理见 内核同步机制。
  • 软中断与 RCU 的处理：软中断不再无条件在中断返回路径上批量执行，RCU 回调可以卸载到指定的核（rcu_nocbs），避免它们在关键核上突然占用长时间。
  • 高精度定时器：基于 hrtimer 而非 jiffies 节拍，让周期任务的唤醒精度从毫秒级进到微秒级。

逐条的实现细节、每一项各自消掉多少延迟、以及配置时的坑，在 PREEMPT_RT 深入 里展开，这里不重复。

代价：吞吐换确定性

选型时最该问但最少被问的一句是「开了 RT 会损失什么」。答案是明确的：

主线化：2024 年那个节点为什么重要

  • PREEMPT_RT 的核心部分经过约二十年的分批上游化，最后剩余的部分在 Linux 6.12（2024 年 11 月发布，LTS）合入主线，CONFIG_PREEMPT_RT 成为常规内核配置项。
  • 这件事的工程意义不在于性能变好了（延迟数字和之前的 out-of-tree patch 基本一致），而在于维护成本塌方式下降：以前每次跟内核版本都要重新 rebase 一大摞 patch，驱动改动可能默默破坏 RT 语义；现在 RT 是主线的一等公民，新代码在合入时就要考虑 RT 语义。
  • 对选型的直接影响：以前「要不要上 RT Linux」要额外评估一份长期维护风险，现在这一项基本可以从决策表里划掉了。

需要 ISO 26262 / IEC 61508 / DO-178C 认证❌ Linux 通常不是主路径Linux 的代码规模与开发过程难以满足高完整性等级的证据要求。常见做法是安全功能放认证 RTOS，Linux 只承担 QM 或低等级部分，中间用 hypervisor 隔离（见 ISO 26262 工程实践）
只是想让服务的 P99 好看一点❌ 别上 RT这是低延迟问题不是实时问题。绑核、避免动态分配、调 cgroup 就能拿到大部分收益，而且不用承担 RT 的吞吐与维护代价

九个候选放同一张表 · 认证可得性 · 四步决策树 · 隐性成本

选型决策树：按这个顺序问，能砍掉九成候选

顺序很重要——先问硬约束（装不装得下、要不要认证），再问软偏好（生态、熟悉度）。倒过来问会花大量时间在最后被一条硬约束否掉的方案上。

三个容易被漏算的隐性成本

驱动缺口

选型评审时看的是内核特性，量产时卡住的往往是「这块 PHY / 这个 CAN 控制器 / 这颗 eMMC 没有现成驱动」。先把 BOM 上的每颗外设在候选 RTOS 里搜一遍，比比较调度算法有用得多。

工具链与调试

RTOS-aware 调试（能在 GDB 里列出所有任务、切换到某个任务的栈）不是所有组合都开箱可用。没有它，多任务死锁的定位效率会差一个数量级。见 §8。

人的成本

团队熟悉一个 RTOS 通常要几个月才谈得上高效。已有存量代码时，换内核带来的收益极少能覆盖迁移与再培训的成本——除非是被认证或芯片支持这类硬约束逼的。

面试里问「你为什么选 X」，标准的差答案是罗列特性。好答案是给出被否掉的候选和否掉的理由：「我们最初想用 Zephyr，因为要 BLE Mesh；但项目要过 IEC 61508 SIL 2，评估下来当时能直接拿到证据包的只有商业内核，加上主控只有 64 KB RAM，最后选了 SafeRTOS，蓝牙功能移到一颗独立的模组上。」——这个回答同时展示了硬约束意识、成本意识和架构拆分能力。

AUTOSAR CP / AP

两套平台的定位差异 · 共存关系 · 功能该放哪一侧的判据

AUTOSAR（AUTomotive Open System ARchitecture）是车企与供应商联盟主导的标准，本质是把「应用逻辑」和「硬件 / 通信 / 基础服务」彻底解耦，让一份控制策略能在不同供应商的 ECU 上复用。理解它的关键不是背分层图，而是理解它诞生的产业背景：一辆车上有几十上百个 ECU，来自十几家供应商，主机厂需要一套共同语言来集成它们。

🔌 生活类比：插座标准。AUTOSAR 之于车载软件，相当于国标插座之于家电。它并不规定电饭煲怎么煮饭（应用逻辑还是各家自己写），但规定了插头形状、电压和安全要求，于是任何一家的电饭煲都能插进任何一面墙。CP 像是固定在墙上的强电回路——安装时就规划好每一路走哪儿、载流多少，运行时不再改；AP 像是 USB-C 口——设备插上后协商能力、按需供电，灵活但复杂度高得多。

标准分成两个分支，它们不是新旧替代关系，而是面向两类完全不同的 ECU：

最本质的一条差异：静态信号 vs 面向服务

上表里所有条目都可以从通信模型这一行推导出来，这才是两个平台的分水岭。

CP：静态信号，编译期就定死

「发动机转速」这个信号在哪条 CAN 报文的第几个 bit、多少毫秒发一次、谁接收，全部在集成阶段由配置工具生成到代码里。运行时没有发现、没有协商、没有连接建立。

好处直接而巨大：时序完全可分析（可以离线算出总线负载和最坏传输延迟）、无动态内存、启动即可用。这是它能支撑 ASIL D 的基础。

代价是：改一个信号要重新生成整条链路的配置并重新集成，跨 ECU 的改动是"牵一发动全身"。

AP：服务发现，运行时建立连接

提供方声明「我提供 RadarObjectList 服务」，使用方声明「我需要它」，运行时通过 SOME/IP 服务发现（基于多播）配对上，然后建立连接收发数据。

好处是解耦：新增一个消费者不需要改提供方；一个软件模块可以独立更新甚至独立部署，这是 OTA 与「软件定义汽车」的技术前提。

代价是时序不再静态可分析：发现过程、序列化、TCP/IP 协议栈都引入了变数。所以 AP 的定位从一开始就不是硬实时闭环控制。

AUTOSAR AP 关键概念（够用即可，深入见专篇）

  • ARA（AUTOSAR Runtime for Adaptive Applications）——一组标准化 C++ API 命名空间：ara::com（通信）、ara::log（日志）、ara::per（持久化）、ara::exec（执行管理）、ara::crypto、ara::ucm（更新与配置管理）等。写 AP 应用主要就是在用这套 API。
  • Adaptive Application——一个可独立部署、独立启停、独立升级的进程，概念上接近后端的微服务，但受严格的资源与启动时序约束。
  • Execution Management——负责按依赖关系拉起各个应用、管理机器状态与功能组状态。它决定了「上电到功能可用」这段时间的行为，是量产项目里最常出问题的一块。
  • SOME/IP——车端的服务化通信协议，跑在以太网 UDP/TCP 上，包含服务发现（SOME/IP-SD）与序列化规则。协议细节与报文格式见 车端网络深入。
  • UCM（Update and Configuration Management）——标准化的软件包安装 / 回滚流程，是 OTA 在标准里的落点。

这几块的接口长什么样、状态机怎么转、以及实际开发中的坑，在 AUTOSAR AP 深入 里逐个展开。

实际车型里 CP 和 AP 不是二选一，而是分层共存。典型的新一代整车电子电气架构（中央计算 + 区域控制器）大致是这样分工的：

→

两侧之间通过网关或信号-服务转换打通：AP 侧的服务调用最终会被翻译成 CP 侧的 CAN 信号，反之亦然。这一层转换是集成时的重灾区——语义映射（枚举值、单位、失效值）、时序（服务调用是异步的，信号是周期的）、以及安全等级的跨越（QM 的数据不能直接驱动 ASIL D 的执行器，必须有独立的校验与降级机制）都要逐条设计。

「自动紧急制动（AEB）放哪一侧？」——这是个陷阱题，答案是拆开放。感知与决策（识别前方障碍、判断是否需要制动）算力需求大、算法迭代快，放 AP；而最终的制动执行、以及「无论上层说什么都不能超过安全边界」的仲裁逻辑，放 CP 的高 ASIL 路径上。这个拆分模式（高算力低安全等级的"大脑" + 低算力高安全等级的"守门人"）在 ADAS 里非常普遍，本质上是 ISO 26262 里 ASIL 分解思想的工程化。

现状与实现选择

  • CP 仍然是量产 ECU 的绝对主体。它覆盖了车上绝大多数节点——车身、动力、底盘、几乎所有传感器与执行器节点。「AP 取代 CP」是一个流传很广但不成立的说法。
  • AP 集中在少数几个高算力节点：智驾域控、座舱域控、中央计算单元、车联网单元。数量少，但承载了软件价值增长最快的部分。
  • 商业栈的主要供应商是 Vector、Elektrobit、ETAS 等；国内也有若干厂商提供 CP/AP 栈。开源侧可参考的实现有 COVESA 的 vsomeip（SOME/IP 通信）等，但一个完整可量产的 AP 栈至今没有成熟的纯开源替代——工具链、配置方法学（ARXML）和认证支持才是商业栈的真正壁垒。

两条线的由来与合流

MISRA 起家于 1990 年代的英国汽车工业，最早只做 C（MISRA C:1998），后来才有 MISRA C++:2008，基于当时的 C++03。而 AUTOSAR 在 2017 年前后推出 AUTOSAR C++14 Coding Guidelines，原因很直接：AP 要用现代 C++ 写，而 MISRA C++:2008 连 auto、lambda、右值引用都没覆盖，规则里甚至有大量针对 C++03 缺陷的条款在 C++11 之后已经过时。

于是业界一度陷入尴尬：两套部分重叠、部分冲突的规则集，供应商要同时应付。后来 AUTOSAR 将其 C++ 指南的后续维护移交给 MISRA，两条线在 MISRA C++:2023（面向 C++17）上合流。实践上的意义是：新项目直接对齐 MISRA C++:2023；存量项目仍大量使用 AUTOSAR C++14，两者的核心禁令高度一致，迁移主要是规则编号与个别条款松紧的差异。

规则不是不可违反的，而是「违反必须留痕」。MISRA 体系里有正式的偏差（deviation）流程：说明违反哪条规则、为什么必须违反、采取了什么补偿措施（额外评审、额外测试、运行时检查）、由谁批准。工程上真正的红线不是「一条都不违反」，而是每一处违反都有记录、有理由、有人签字。团队里最常见的失控形态，是靠 // NOLINT 随手关告警且无人审计——审核时这会变成系统性的过程缺陷，比单个技术问题严重得多。

典型限制：每条禁令的真实理由

禁令表面理由真正的工程理由替代做法
禁运行期动态内存
（new / malloc）		 "慢" 三层：① 分配耗时不确定，取决于堆的碎片状态，WCET 无法给界；② 碎片化会随运行时间累积，一个跑三年的 ECU 可能在第三年某天分配失败，而这在测试里几乎不可能复现；③ 分配可能失败，于是每个调用点都多一条极难测试覆盖的错误路径 初始化阶段一次性预分配的内存池 / 固定容量容器；容量写进设计文档并静态校验

禁 RTTI / dynamic_cast "有运行时开销" dynamic_cast 的耗时取决于继承层次的形状，不是常数，而且实现细节因编译器而异，无法给出可移植的上界；type_info 结构还会把类名字符串带进固件，增加体积。此外「需要向下转型」通常本身就是设计信号——类型层次没设计对 把类型信息显式建模（枚举 tag + switch）、访问者模式、或干脆用 std::variant
禁递归 "可能栈溢出" 准确说是最坏栈深度不可静态确定。安全项目必须给出每个任务的最坏栈用量并据此设定栈大小（见 §9），递归让这个分析直接失效。注意这条对间接递归同样成立，而间接递归靠人眼很难发现——需要工具做调用图分析 显式栈 + 循环；或用有明确上界的迭代算法
所有循环必须有可知上界 "防死循环" WCET 分析的直接前提：循环次数未知则整个函数的时间上界无法计算。while (!flag) 这种等硬件的写法在真实故障下会变成永久阻塞 循环上界写成编译期常量；等硬件必须带超时计数并在超时后进入定义好的失效处理
限制多重继承 "菱形问题" 虚继承下对象布局和成员访问路径变复杂，代码与数据的可追溯性下降，静态分析工具支持参差。规则通常允许「至多一个有实现的基类 + 若干纯接口」这种受限形态 组合优于继承；接口用纯抽象类
限制模板复杂度 "编译慢" 核心问题是可追溯性：一个模板实例化出几十份代码，需求到代码的追溯关系、覆盖率统计、代码评审都变得困难；深度元编程还可能触发编译器自身的缺陷（而编译器在安全项目里也是要做工具认证的） 用模板做类型安全的薄封装是鼓励的；避免复杂的编译期计算与深递归实例化
禁裸 new 出来的裸指针所有权 "容易泄漏" 所有权不明确导致重复释放 / 悬垂指针，这类缺陷在长期运行的 ECU 上表现为随机的、无法复现的故障。用类型系统把所有权表达出来，等于把一类运行时缺陷提前到编译期 对象生命周期静态化（全局 / 成员）；需要传递时用引用或 std::span 表达"借用而不拥有"
这一节最能拉开差距的一句话是：这些规则不是为了让程序更快，而是为了让程序的行为可以被离线论证。动态内存被禁不是因为 malloc 慢（它其实常常很快），而是因为它的最坏耗时和长期行为无法论证。能把「性能」和「可论证性」这两件事分开讲，是资深与非资深的一条清晰分界。

六组「违规 ❌ / 合规 ✅」对照

① 动态容器 → 固定容量容器

// ❌ 违规：std::vector 在 push_back 时可能重新分配，耗时不可预期
class ObstacleList {
  std::vector<Obstacle> items_;      // 容量无上界，堆分配
public:
  void add(const Obstacle& o) { items_.push_back(o); }  // 可能 realloc + 拷贝全部元素
};
// ✅ 合规：容量是类型的一部分，全部存储在对象内部，零堆分配
template <typename T, std::size_t N>
class StaticVector {
  alignas(T) std::byte storage_[N * sizeof(T)];
  std::size_t size_{0};
public:
  // 满了返回 false，而不是抛异常或悄悄增长 —— 失败是显式的、可测试的
  [[nodiscard]] bool push_back(const T& v) noexcept {
    if (size_ >= N) { return false; }
    ::new (&storage_[size_ * sizeof(T)]) T(v);   // placement new，不碰堆
    ++size_;
    return true;
  }
  [[nodiscard]] std::size_t size()  const noexcept { return size_; }
  [[nodiscard]] bool        empty() const noexcept { return size_ == 0; }
  // 调用前必须确认非空 —— 越界是 UB，不要在这里加运行时检查再"容错"，
  // 那只会掩盖调用方的逻辑错误。
  T pop_back() noexcept { --size_; return *std::launder(reinterpret_cast<T*>(&storage_[size_ * sizeof(T)])); }
  static constexpr std::size_t capacity() noexcept { return N; }
};

// 容量上界来自需求："雷达一帧最多上报 64 个目标"，这句话必须在设计文档里有出处
using ObstacleList = StaticVector<Obstacle, 64>;
换成固定容量容器不等于问题消失了，只是把问题挪到了显眼处：原来 vector 会默默增长，现在 push_back 会返回 false。「满了怎么办」是一个必须由需求回答的问题——丢最旧的？丢最新的？置故障码？不同答案对应完全不同的系统行为。这正是这条规则的价值：它逼你在设计阶段就面对容量上界，而不是等到现场。

② 异常 → expected 风格的返回值

// ❌ 违规：抛出路径的耗时与栈深度相关，且控制流是隐式的
Speed parseSpeed(Frame const& f) {
  if (f.dlc() < 2) { throw MalformedFrame{}; }   // 调用者看代码看不出这里会跳走
  return Speed{f.u16(0)};
}
// ✅ 合规：错误进入返回类型，控制流显式，且 [[nodiscard]] 保证不会被忽略
enum class ParseError : std::uint8_t { kTooShort, kOutOfRange, kChecksum };

[[nodiscard]] std::expected<Speed, ParseError>
parseSpeed(Frame const& f) noexcept {
  if (f.dlc() < 2) { return std::unexpected(ParseError::kTooShort); }
  const auto raw = f.u16(0);
  if (raw > kSpeedRawMax) { return std::unexpected(ParseError::kOutOfRange); }
  return Speed{raw};
}

// 调用侧：每条错误路径都在源码里看得见，覆盖率工具也数得清
const auto r = parseSpeed(frame);

applySpeed(*r);

std::expected 是 C++23 才进标准的；C++14/17 的项目里普遍使用等价的自研模板或第三方实现（接口大同小异）。关键不在于用哪个实现，而在于「错误是值、不是跳转」这个语义。

③ 运行期多态 → 编译期多态（热路径上）

// ❌ 在硬实时热路径上不理想：虚调用无法内联，且具体走哪个实现要看运行时类型
struct IFilter {
  virtual float step(float x) = 0;
  virtual ~IFilter() = default;
};
void controlLoop(IFilter& f) {         // WCET 必须按最慢的那个派生类算
  for (...) { y = f.step(x); }
}
// ✅ 编译期确定：可内联，WCET 针对这一个实例化精确分析
template <typename Filter>
void controlLoop(Filter& f) noexcept {
  for (std::size_t i = 0; i < kSamplesPerCycle; ++i) {   // 上界是编译期常量
    y[i] = f.step(x[i]);                                // 可完全内联
  }
}
// 或者当实现集合是封闭且已知的时候，用 variant + visit：
using AnyFilter = std::variant<Pid, Butterworth, Kalman>;
std::visit([&](auto& f){ y = f.step(x); }, filter);
不要过度解读这一条。虚函数在车端 C++ 里并不是被禁止的，AP 的整个接口体系都建立在抽象类之上；被禁的是 RTTI 与 dynamic_cast。上面的对照说的是硬实时热路径上的取舍：静态多态让 WCET 分析更精确、允许内联。在非热路径上，为了可扩展性用虚函数完全正当——而且用模板换掉所有虚函数会带来代码膨胀，那对只读段紧张的 MCU 反而是更糟的交易。

④ 递归 → 显式栈迭代

// ❌ 违规：最坏栈深度取决于树的形状，静态分析给不出界
void traverse(Node* n) {
  if (n == nullptr) { return; }
  visit(n);
  traverse(n->left);
  traverse(n->right);
}
// ✅ 合规：栈是一个固定容量的成员，最坏深度 = kMaxDepth，写死且可校验
bool traverse(Node* root) noexcept {
  StaticVector<Node*, kMaxDepth> stack;
  if (root != nullptr && !stack.push_back(root)) { return false; }
  while (!stack.empty()) {
    Node* n = stack.pop_back();
    visit(n);
    // 深度超限时明确失败，而不是踩栈 —— 踩栈的后果是随机的，返回 false 是可测的
    if (n->right && !stack.push_back(n->right)) { return false; }
    if (n->left  && !stack.push_back(n->left))  { return false; }
  }
  return true;
}

⑤ 无界等待 → 带超时的有界循环

// ❌ 违规：硬件不响应时永久阻塞，且看门狗喂不到会引发整机复位
while ((SPI->SR & SPI_SR_TXE) == 0) { }        // 循环次数无上界
SPI->DR = data;
// ✅ 合规：上界是编译期常量，超时进入定义好的失效处理
// kSpiTxTimeoutIters 由「最坏等待时间 / 单次循环耗时」算出，并留裕度；
// 这个数字要写进设计文档，不能是拍脑袋的 10000。
bool spiSend(std::uint8_t data) noexcept {
  for (std::uint32_t i = 0; i < kSpiTxTimeoutIters; ++i) {
    if ((SPI->SR & SPI_SR_TXE) != 0) {
      SPI->DR = data;
      return true;
    }
  }
  diag_.report(Dtc::kSpiTimeout);      // 失效是被观测到的，不是静默的
  return false;
}

⑥ 隐式转换与"魔法数" → 强类型单位

// ❌ 违规：单位靠注释和记忆维持，隐式转换让编译器无法帮你
void setTorque(float t);       // Nm 还是 mNm？

class MilliNewtonMetre {
  std::int32_t v_;
public:
  explicit constexpr MilliNewtonMetre(std::int32_t v) noexcept : v_{v} {}

功能安全

跨行业的同一个家族 · ASIL 怎么推出来 · 对开发流程意味着什么

车端 / 工业 / 医疗 / 航空 / 铁路都有各自的功能安全标准，但它们共享同一套底层思想：先识别危害、评估风险，再按风险等级决定要付出多严格的开发过程与验证证据。换句话说，功能安全管的不是「代码有没有 bug」，而是「你凭什么说这个系统不会伤人」——它要的是一条从危害到需求、到设计、到代码、到测试用例的完整证据链。

🏗 生活类比：建筑审图。盖一间自家工具房没人管你；盖一栋二十层的楼，要出结构计算书、材料检验报告、施工记录，还要第三方审图和验收。不是因为大楼的砖和工具房的砖不一样，而是塌了的后果不一样。功能安全等级就是这里的"楼层数"：等级越高，同一行代码需要附带的证据越多。

ASIL 是怎么推出来的：S × E × C

ASIL 不是拍脑袋定的，也不是给零部件定的，而是在整车层面对每一条危害事件（hazard，如"行驶中意外全力制动"）做风险评估的产物。三个维度：

S · Severity 严重度

危害发生后对人的伤害程度。
S0 无伤害 · S1 轻中度 · S2 严重但通常可存活 · S3 危及生命 / 致命。

E · Exposure 暴露概率

车辆处于该危害可能发生的运行场景中的频度。
E1 很少 → E4 高频（例如"在高速公路上行驶"是高暴露，"在洗车机里"是低暴露）。

C · Controllability 可控性

驾驶员或其他交通参与者能否避免伤害。
C1 一般可控 → C3 难以或无法控制。

读这张表能得到两个很有用的直觉：

  • 降低任意一个维度就能降级。这是安全设计最重要的杠杆：如果能通过设计保证驾驶员总能接管（提高 C），或者把危害限制在低速场景（降低 S），等级就能往下走一格，对应的开发成本可能减半。ASIL 分解（把一条高等级需求拆成两条独立的低等级需求）是同一思路的另一种用法。
「这个模块是 ASIL D 吗？」——严格来说这个问法就不对。ASIL 属于安全目标（safety goal），通过安全需求逐层分配到架构元素上。一个模块的等级来自它所实现的安全需求，而同一个模块可能同时承载不同等级的需求。能纠正这个提问本身，比背出 ASIL D 的要求更能说明你真的参与过安全流程。

对开发流程意味着什么

  • V 模型与双向可追溯：左边每一层（安全目标 → 功能安全需求 → 技术安全需求 → 软件需求 → 设计 → 代码）都要能向下追到实现、向上追到来源；右边每一层测试都要能追到它验证的那条需求。「这行代码为什么存在」必须有答案。
  • 文档与评审的比重远超编码：安全计划、危害分析（HARA）、安全概念、FMEA / FTA、安全分析、验证计划与报告、安全案例（safety case）。工程师第一次进入这类项目时最大的不适应是：写代码的时间可能只占个人工时的两三成。
  • 工具也要过关：编译器、静态分析、测试框架都要做工具置信度评估（tool qualification）——如果一个工具的缺陷可能导致安全缺陷漏检，就要么用已认证版本，要么自己提供论证。「随便升个 GCC 版本」在这类项目里是需要变更评审的动作。
  • 独立性要求：等级越高，验证方与开发方越需要组织上的独立，最高等级下可能要求不同部门甚至第三方。
  • 变更成本非线性上升：改一行代码可能牵动需求、设计文档、单元测试、集成测试与回归报告。这就是为什么安全项目"不敢重构"——不是技术上不敢，是流程成本太高。
横向经验：电信设备虽然不走 ASIL，但运营商入网测试、NEBS、行业审计的结构非常相似——文档、可追溯性、第三方测试才是真正占时间的部分，编码只是其中一小块。做过任意一种高合规行业的人，切换到功能安全的适应期会短很多，因为难的不是标准条文，而是接受"证据和代码同等重要"这件事。

完整的 V 模型活动、HARA 怎么做、ASIL 分解的独立性论证、工具认证、以及真实项目的成本结构，见 ISO 26262 功能安全工程实践；与之配套的信息安全（ISO/SAE 21434）与预期功能安全（SOTIF / ISO 21448）也在那一篇里。

① CPU 隔离与绑核：先把地盘清出来

把关键线程钉在某个核上只是第一步，也是最容易做错的一步：taskset 只保证「我不被搬走」，完全不保证「别人不搬过来」，更管不住中断。要真正独占一个核，需要内核参数与运行时配置配合。

# ---- 启动参数（GRUB / 设备树 bootargs），假设 8 核，把 4-7 留给实时任务 ----

rcu_nocbs=4-7             # RCU 回调不在这些核上执行（否则会突然占用几十 µs）

intel_idle.max_cstate=0   # x86 上还要另外关掉 intel_idle 驱动的深度状态

$ cat /proc/cmdline                 # 确认参数真的被内核吃进去了（拼错不会报错，只会静默失效）

③ 内存锁定与预分配：把缺页挡在启动阶段

一次主缺页（major fault，需要从存储读页）可能是毫秒量级，足以毁掉任何实时预算；即使是次缺页也有几微秒。实时线程在稳态运行时必须一次缺页都不发生，做法是启动阶段把该碰的内存全碰一遍并锁住。

#include <sys/mman.h>
#include <malloc.h>
#include <cstring>

constexpr std::size_t kMaxSafeStack = 512 * 1024;   // 按 §9 的栈分析结果来定

// 必须 noinline，否则编译器可能把这个"没用"的数组优化掉
__attribute__((noinline)) static void prefaultStack() {
  volatile unsigned char dummy[kMaxSafeStack];
  std::memset(const_cast<unsigned char*>(dummy), 0, sizeof(dummy));
}

bool lockDownMemory() {
  // MCL_CURRENT：锁住当前已映射的全部页；MCL_FUTURE：以后新映射的也自动锁
  if (mlockall(MCL_CURRENT | MCL_FUTURE) != 0) { return false; }

  // 让 glibc 不要把释放的内存还给内核 —— 还回去意味着下次分配要重新缺页
  mallopt(M_TRIM_THRESHOLD, -1);
  mallopt(M_MMAP_MAX, 0);      // 大块分配不走 mmap（mmap 的页是惰性映射的）

  // 预热堆：先分配再释放，让 glibc 把 arena 扩到足够大并保持
  void* warm = std::malloc(8 * 1024 * 1024);
  if (warm != nullptr) { std::memset(warm, 0, 8 * 1024 * 1024); std::free(warm); }

  prefaultStack();
  return true;
}

④ 无锁环形缓冲：实时线程与非实时线程之间唯一安全的桥

这是实时系统里最高频的一个需求：控制线程每 1 ms 产生一批数据，日志 / 上传 / 显示线程慢慢消费，两者不能互相阻塞。用互斥量是错的——非实时线程持锁时被抢占，实时线程就得等它，这就是优先级反转的教科书场景（即使有优先级继承，也只是把最坏情况从"无界"变成"有界但不小"）。正确答案是单生产者单消费者（SPSC）无锁环形缓冲：生产者永不阻塞，最坏情况只是发现队列满了然后丢弃。

#include <atomic>
#include <array>
#include <cstddef>
#include <new>

// 单生产者 / 单消费者无锁环形缓冲。
// 前提：恰好一个线程调用 push，恰好一个线程调用 pop。多生产者会直接坏掉。
template <typename T, std::size_t N>
class SpscRing {
  static_assert((N & (N - 1)) == 0, "N 必须是 2 的幂，这样取模能退化成一次与运算");
  static_assert(std::is_trivially_copyable_v<T>, "元素应可平凡拷贝，避免拷贝时分配内存");

  static constexpr std::size_t kLine = 64;   // 常见 cache line 大小；不同平台需确认

  // head_ 与 tail_ 必须分处不同 cache line。否则生产者每次写 head_ 都会让
  // 消费者所在核上缓存了 tail_ 的那行失效 —— 这就是 false sharing，
  // 实测能让吞吐掉一个数量级，而且它只在多核上出现，单核测不出来。
  alignas(kLine) std::atomic<std::size_t> head_{0};   // 只有生产者写
  alignas(kLine) std::atomic<std::size_t> tail_{0};   // 只有消费者写
  alignas(kLine) std::array<T, N> buf_{};

public:
  // 生产者侧：由实时线程调用。无锁、无系统调用、无分配，耗时是常数。
  [[nodiscard]] bool push(const T& v) noexcept {
    const auto h = head_.load(std::memory_order_relaxed);   // 只有我写，relaxed 足够
    const auto next = (h + 1) & (N - 1);
    // acquire：确保读到的 tail_ 之前，消费者对该槽位的读取已经完成
    if (next == tail_.load(std::memory_order_acquire)) {
      return false;                    // 满了。实时线程绝不在这里等。
    }
    buf_[h] = v;
    // release：保证上面那次写入对看到新 head_ 的消费者一定可见
    head_.store(next, std::memory_order_release);
    return true;
  }

  // 消费者侧：由普通线程调用
  [[nodiscard]] bool pop(T& out) noexcept {
    const auto t = tail_.load(std::memory_order_relaxed);
    if (t == head_.load(std::memory_order_acquire)) {
      return false;                    // 空
    }
    out = buf_[t];
    tail_.store((t + 1) & (N - 1), std::memory_order_release);
    return true;
  }
};
// 使用：注意"满了怎么办"必须是一个有意识的决定，不能忽略返回值
struct Sample { std::uint64_t t_ns; std::int32_t current_ma; std::int32_t pos; };

SpscRing<Sample, 4096> g_ring;                 // 全局，启动阶段就存在，零动态分配
std::atomic<std::uint64_t> g_dropped{0};        // 丢弃必须被计数并上报

void controlIsrThread() {                      // 1 kHz，SCHED_FIFO
  Sample s = sampleHardware();
  if (!g_ring.push(s)) {
    // 关键：丢数据，不阻塞。控制回路的时序比这一条日志重要得多。
    g_dropped.fetch_add(1, std::memory_order_relaxed);
  }
}

void loggerThread() {                           // 普通优先级，可以随便阻塞
  Sample s;
  while (running) {
    if (g_ring.pop(s)) { writeToDisk(s); }
    else { std::this_thread::sleep_for(1ms); }   // 空转时让出 CPU
  }
}
为什么不用……问题
std::mutex 保护的队列实时线程可能阻塞在消费者手里。即使用 PTHREAD_PRIO_INHERIT 把最坏情况变成有界，这个界仍然包含消费者的整个临界区，通常远大于预算
std::queue / std::deque会动态分配。push 的最坏耗时不可控
无锁 MPMC 队列能用，但实现复杂度和最坏重试次数都高得多。SPSC 能满足需求时永远优先 SPSC——它的正确性可以用眼睛看明白
volatile 而不是 std::atomicvolatile 不提供任何内存序保证，编译器和 CPU 都可以重排它前后的普通访问。这是嵌入式代码里最普遍的一个错误认知：volatile 的用途是访问外设寄存器（禁止编译器合并/省略访问），不是线程同步。原理见 C++ 内存模型
还能再快一点：让生产者缓存一份 tail_ 的旧值，只有当它显示"满了"时才真去读一次对方的原子变量（消费者对称处理 head_）。稳态下两个核几乎不再互相读对方的 cache line，跨核流量大幅下降。代价是代码复杂度上升，在 1 kHz 这种量级完全没必要——先测，再决定要不要上这个优化。

⑤ 时间：CLOCK_MONOTONIC 与为什么不能用 CLOCK_REALTIME

CLOCK_REALTIME 是"墙上时钟"，它会跳：NTP 校时会把它往前或往后拨，管理员改系统时间会把它拨到任意值，闰秒也会影响它。用它做时间差计算，意味着你的控制周期依赖于运维有没有在这一刻同步时间。见过的真实后果包括：NTP 一次回拨让"距上次采样的时间差"变成负数，进而让 PID 的微分项算出一个巨大的值，执行器猛地动了一下。

时钟会跳吗用途注意
CLOCK_MONOTONIC不会向后跳；受 NTP 的频率微调（adjtime）影响，即快慢会被缓慢校正所有时间差计算、周期任务、超时默认选它。起点是不确定的（通常是启动时刻），不要用它表示日期
CLOCK_MONOTONIC_RAW完全不受 NTP 影响需要测量硬件本身频率偏差时因为不被校正，长时间会与真实秒有累积偏差，不适合做长周期定时
CLOCK_REALTIME会，可被任意设置只用于打时间戳、和外部系统对齐日期绝不用于计算时间差
CLOCK_BOOTTIME不会跳，且包含系统挂起的时间需要感知"真实流逝了多久"（含休眠）车机这类会休眠唤醒的设备上要特别注意与 MONOTONIC 的区别
CLOCK_TAI不跳、无闰秒与 PTP / TSN 时间基对齐网络同步场景见 TSN 深入
 
// C++ 侧的对应关系，同样的坑换了个名字：
std::chrono::system_clock::now();    // ≈ CLOCK_REALTIME —— 会跳！
std::chrono::steady_clock::now();    // ≈ CLOCK_MONOTONIC —— 用这个

// ❌ 常见错误：用 system_clock 算耗时
auto t0 = std::chrono::system_clock::now();
doWork();
auto dt = std::chrono::system_clock::now() - t0;   // NTP 一跳，dt 可以是负的

// ✅ 正确
auto t0 = std::chrono::steady_clock::now();
doWork();
auto dt = std::chrono::steady_clock::now() - t0;

⑥ 周期任务：TIMER_ABSTIME 与相对 sleep 的累积误差

这是嵌入式面试里区分度极高的一道题，也是实际项目里极常见的一个 bug。

// ❌ 错误写法：相对 sleep。周期会持续变长，而且误差会累积。
for (;;) {
  doWork();                       // 耗时 W，且每次都不一样
  usleep(1000);                  // 睡 1 ms
}
// 实际周期 = W + 1000 µs + 唤醒延迟 L，而不是 1000 µs。
// 更糟的是这个误差是"每一轮都重新累加"的：
//   跑 1 小时（360 万轮），若平均 W+L = 80 µs，就漂了 288 秒 —— 将近 5 分钟。
// 症状：数据时间戳与实际不符、与外部设备（PLC / 总线）逐渐失步、
//       采样率比标称低几个百分点。
#include <time.h>
#include <cstdint>

constexpr long kPeriodNs = 1'000'000;      // 1 ms → 1 kHz
constexpr long kNsPerSec  = 1'000'000'000;

static inline void tsAddNs(timespec& t, long ns) {
  t.tv_nsec += ns;
  while (t.tv_nsec >= kNsPerSec) { t.tv_nsec -= kNsPerSec; ++t.tv_sec; }
}

void periodicTask() {
  timespec next{};
  clock_gettime(CLOCK_MONOTONIC, &next);   // 只在这里取一次"现在"
  uint64_t overruns = 0;

  for (;;) {
    tsAddNs(next, kPeriodNs);              // 下一次的绝对唤醒时刻

    // TIMER_ABSTIME：睡到这个绝对时刻，而不是"从现在起睡多久"。
    // 于是 doWork() 的耗时和唤醒延迟都被"吸收"进这一觉里，不会累积。
    // 用同一个 CLOCK_MONOTONIC，与上面取时间的时钟保持一致。
    int rc = clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, nullptr);
    if (rc == EINTR) { continue; }        // 被信号打断，继续睡到同一个时刻
    if (rc != 0)     { handleFatal(rc); return; }

    // 超时检测：如果 doWork 比周期还慢，next 会落到过去，
    // clock_nanosleep 立刻返回，任务开始"追赶"。这必须被发现并上报。
    timespec now{};
    clock_gettime(CLOCK_MONOTONIC, &now);
    if (tsLater(now, next, kPeriodNs / 2)) {   // 迟到超过半个周期
      ++overruns;
      reportOverrun(overruns);
      // 落后太多时的策略要明确：这里选择重新对齐到当前时刻，
      // 放弃追赶已经错过的那些周期（追赶会让系统雪上加霜）。
      next = now;
    }

    doWork();
  }
}
为什么绝对时间能消除累积误差：相对 sleep 每轮都以"现在"为基准，于是每轮的执行耗时和唤醒延迟都被加进下一轮的起点，误差单调累积；绝对时间的基准是一条独立于执行过程的时间轴（next = start + n × period），单轮的抖动只影响那一轮，下一轮自动回到网格上。这就是抖动（有界、不累积）与漂移（单调累积）的区别——面试里能把这两个词分清，这道题就答满分了。

把线程本身配置好的完整样板（优先级、绑核、栈大小）：

#include <pthread.h>
#include <sched.h>

bool spawnRtThread(pthread_t& tid, void* (*fn)(void*), int prio, int cpu) {
  pthread_attr_t attr;
  pthread_attr_init(&attr);

  // 1) 栈大小按 §9 的最坏栈分析来定，别用默认的 8 MB（锁页时会白锁 8 MB）
  pthread_attr_setstacksize(&attr, 512 * 1024);

  // 2) 不继承父线程的调度参数 —— 忘了这一步，下面两行设置全部无效，
  //    而且不会有任何报错。这是最常见的一个静默失败。
  pthread_attr_setinheritsched(&attr, PTHREAD_EXPLICIT_SCHED);
  pthread_attr_setschedpolicy(&attr, SCHED_FIFO);

  sched_param sp{};
  sp.sched_priority = prio;                // 1..99，越大越高
  pthread_attr_setschedparam(&attr, &sp);

  // 3) 绑核
  cpu_set_t set;
  CPU_ZERO(&set);
  CPU_SET(cpu, &set);
  pthread_attr_setaffinity_np(&attr, sizeof(set), &set);

  const int rc = pthread_create(&tid, &attr, fn, nullptr);
  pthread_attr_destroy(&attr);
  return rc == 0;    // EPERM 说明没有 CAP_SYS_NICE / RLIMIT_RTPRIO 权限
}

// 不要把所有实时线程都设成 99 —— 那等于没有优先级，

嵌入式调试

从 printf 到 ETM 的手段谱系 · GPIO 翻转法 · 现象到工具的决策表

嵌入式调试和服务端调试最大的差别是：观测行为本身会改变被观测的时序。在服务端加一行日志基本无害；在一个 1 ms 周期的控制环里加一行 printf，可能直接把周期撑爆，于是你要找的 bug 消失了，换来一个新的。所以嵌入式调试的核心技能是按侵入程度选工具——能用非侵入手段就绝不用侵入式的。

海森堡 bug 是这个领域的常态。「加了打印就不复现，去掉打印又复现」几乎总意味着问题与时序或竞态有关：一个未加保护的共享变量、一处缺少内存屏障、一个恰好在中断边界上的状态更新。遇到这种现象时，正确反应不是加更多打印，而是换一种零/低侵入的观测手段（GPIO 翻转、RTT、硬件 trace），把时序保持原样再看。

手段谱系：按侵入程度排序

手段侵入程度能看到什么需要什么典型场合
printf / 串口🔴 高（阻塞、格式化耗时、可能加锁）任意变量与流程一根 UART启动阶段、非时序敏感的逻辑
SEGGER RTT🟡 低（写内存环形缓冲，调试器后台搬走）同 printf，但不阻塞SEGGER 探针 + 目标内存里一小块缓冲时序敏感场景下 printf 的直接替代品
GPIO 翻转 + 示波器🟢 极低（一次寄存器写，通常几个时钟周期）精确的时间关系：中断延迟、任务执行窗口、抖动一根空闲 IO + 示波器 / 逻辑分析仪测时延与抖动的首选，见下

GPIO 翻转法：朴素但最有效的时延测量

这是嵌入式工程师的基本功，也是唯一能直接测到"从电平变化到软件响应"这段全链路时间的方法——因为它把测量点放在了软件之外。做法简单到有点土：在关心的代码前后各翻一次 GPIO，用示波器或逻辑分析仪量脉冲。

// MCU 上：直接写寄存器，开销通常只有几个时钟周期。
// 关键是用 BSRR 这类"置位/清零专用寄存器"（一次写完成），
// 不要用 ODR ^= mask 那种读-改-写 —— 它更慢，而且不是原子的。
#define DBG_PIN_HIGH()  (GPIOA->BSRR = (1U << 5))
#define DBG_PIN_LOW()   (GPIOA->BSRR = (1U << (5 + 16)))

void TIM2_IRQHandler(void) {
  DBG_PIN_HIGH();        // ← 上升沿：ISR 开始
  controlStep();
  DBG_PIN_LOW();         // ← 下降沿：ISR 结束
}
// 示波器上直接读出三件事：
//   脉冲宽度      = ISR 执行时间（把游标放在最宽的那一个 → 实测的最坏值）
//   脉冲上升沿间隔 = 实际周期（用无限余辉模式看边沿的"胖度" = 抖动）
//   触发源到上升沿 = 中断延迟（外部信号触发，需要两个通道）
// Linux 用户态上的等价做法：走 GPIO 字符设备（新接口，不要再用已废弃的 sysfs）。
// 注意用户态到 GPIO 的路径本身有开销，测出的是"含这段开销"的时间；
// 如果要测得更准，把打点做进内核模块或用 ftrace。
#include <linux/gpio.h>
#include <sys/ioctl.h>
#include <fcntl.h>

int fd = open("/dev/gpiochip0", O_RDWR);
gpiohandle_request req{};
req.lineoffsets[0] = 17;
req.lines = 1;
req.flags = GPIOHANDLE_REQUEST_OUTPUT;
ioctl(fd, GPIO_GET_LINEHANDLE_IOCTL, &req);   // req.fd 就是操作句柄

gpiohandle_data data{};
data.values[0] = 1;
ioctl(req.fd, GPIOHANDLE_SET_LINE_VALUES_IOCTL, &data);   // 拉高
doWork();
data.values[0] = 0;
ioctl(req.fd, GPIOHANDLE_SET_LINE_VALUES_IOCTL, &data);   // 拉低
GPIO 翻转法的价值不在于"没有更好的工具"，而在于它测的是物理世界里真实发生的时间。任何软件内部的计时（clock_gettime、周期计数器）都在被测系统之内，会被同样的调度延迟、缓存效应影响；示波器在系统之外，它不会撒谎。当软件说"我只用了 200 µs"而系统表现却对不上时，示波器是唯一的仲裁者。面试里能主动提到这一点，通常意味着真的在实验室里调过硬件。

硬件接口速查

  • JTAG——老牌标准，通常 4–5 根信号线，可菊花链多个器件，几乎所有 SoC 都支持。
  • SWD（Serial Wire Debug）——ARM 的两线精简版（SWDIO + SWCLK），Cortex-M 的主流，省引脚。
  • SWO / ITM——单向的单线输出通道，把软件打点和事件推给探针，比 UART 快且不占用应用的串口。
  • ETM / 嵌入式 trace——硬件级的指令流记录，可以离线重放"崩溃前执行了哪些指令"。需要芯片支持、需要专门的引脚，探针也贵得多，但对"跑飞到不存在的地址"这类问题几乎是唯一手段。

调试器 + 工具

  • Debug probe：J-Link（SEGGER 商业，强大）/ ST-Link / DAPLink（开源 CMSIS）/ Black Magic Probe（开源）
  • OpenOCD——开源 debugger backend，pair with GDB
  • SEGGER J-Trace / Lauterbach TRACE32——商业 trace 工具
  • RTOS-aware debug——GDB / OpenOCD 知道 FreeRTOS / Zephyr 等的内部数据结构，能列 task / 切换 stack

Linux 目标上：ftrace 抓一次延迟尖峰

在有 Linux 的目标上，「我的实时线程偶尔晚了 800 µs」这个问题有标准解法：让内核在延迟超阈值时自动把前后的事件流 dump 出来，而不是靠人守在那里。

# 方法一：让 cyclictest 自己触发 trace 停止 —— 最省事的一招
# -b 500 表示"一旦某次延迟超过 500 µs 就立刻停止内核 trace 并退出"
sudo trace-cmd start -e sched -e irq -e timer
sudo cyclictest -m -p 80 -t 1 -i 1000 -b 500 --tracemark
sudo trace-cmd stop
sudo trace-cmd extract && trace-cmd report | less
# 在报告里找 tracing_mark_write 那一行（cyclictest 打的标记），
# 往前翻 500 µs，看这段时间 CPU 上到底在跑什么 —— 答案通常一眼可见：
#   某个 kworker、某个中断线程、或者一段很长的内核函数。

# 方法二：内核自带的 wakeup_rt tracer，专测"最高优先级 RT 任务的唤醒延迟"
cd /sys/kernel/tracing
echo wakeup_rt | sudo tee current_tracer
echo 0 | sudo tee tracing_max_latency      # 清零，开始记录新高
#   ...跑负载...
cat tracing_max_latency                    # 迄今观察到的最大值（µs）
cat trace | head -40                       # 创下这个记录的那一次的完整调用序列

# 方法三：6.x 内核的 rtla，把上面这些包装成了更好用的形态
sudo rtla timerlat top -d 60s           # 分别给出 IRQ 层和线程层的延迟，能区分是哪一段慢
sudo rtla osnoise hist -d 60s          # 量化"操作系统噪声"：谁在偷 CPU、偷了多久

eBPF 适合需要长期在线、需要统计聚合的场景——比如「把运行队列等待时间做成直方图，连续观察一周」。它比 ftrace 更灵活但学习曲线更陡，工具与写法见 eBPF 可观测性。如果问题已经升级成内核崩溃或系统卡死，那是另一套方法（vmcore、崩溃转储分析），见 内核崩溃分析。驱动层面的调试（探针、DMA、中断注册）见 Linux 设备驱动。

先说清楚：和服务器性能优化不是一回事

从服务端转来的工程师带着一整套成熟的直觉：加缓存、加线程、加内存、多测几次取平均。这些直觉在嵌入式上有一半是错的，因为三个前提变了。

维度服务器嵌入式 / 实时直觉失效的地方
优化目标吞吐、平均延迟、成本/QPS最坏情况的确定性"加缓存"在服务器上是纯赚；在实时系统里它增大了最好与最坏之间的差距，命中时快、未命中时更慢，让 WCET 分析更难
资源内存与算力基本可以买RAM 以 KB 计、Flash 以 KB/MB 计，且成本对单价敏感（量产百万台，每台省一块钱就是一百万）"用空间换时间"经常没有空间可换；反过来"用时间换空间"倒是常见
功耗与热基本不是应用层要管的事硬约束：电池容量、无风扇散热能力、车规温度范围"跑满 CPU 更快完成"在服务器上成立；在嵌入式上可能导致降频，反而更慢，甚至触发热保护
可观测性随便挂 profiler、随便加日志可能没有 perf、没有 MMU、连串口都要抢"先 profile 再优化"这条黄金法则依然对，但profile 的手段要自己搭（见 §9.5）
失败代价重启一个实例可能召回、可能伤人"先上线看看"不存在
有一条规则在两边都成立而且最重要：先测量，再优化。区别只在于嵌入式上"测量"这件事本身要花更多力气搭。不要凭猜测优化——见过太多人花两周手写汇编优化一个函数，最后发现整个循环 80% 的时间花在一次没必要的 DMA 等待上。

栈使用分析：最坏栈深度必须是个已知的数

没有 MMU 的 MCU 上，栈溢出不会给你一个整洁的段错误，它会安静地覆盖掉相邻的变量，然后在几分钟或几天后以完全无关的形式炸出来。这是嵌入式领域最难查的一类 bug，而它完全可以被预防——前提是你知道每个任务的最坏栈用量。

# 方法一：编译器给出每个函数的栈帧大小（不含被调用者）
$ gcc -fstack-usage -c control.c
$ cat control.su
control.c:42:6:controlStep    128     static
control.c:87:5:pidUpdate       48     static
control.c:103:6:logSample    1064     dynamic,bounded   # ← 1 KB 的局部缓冲，可疑
# "static" 表示编译期确定；"dynamic" 表示含 VLA 或 alloca —— 安全项目里应当禁止

# 方法二：把栈帧大小沿调用图累加，得到每条路径的最坏值
$ gcc -fcallgraph-info=su,da -c control.c
# 递归和函数指针会让调用图不闭合 —— 这正是 §5 禁递归、限制函数指针的原因。
# 认证项目通常用商业工具（如 AbsInt StackAnalyzer）做这一步，因为要出正式报告。

# 方法三：运行时"栈涂色"（stack painting）—— 最实用，成本最低
#   启动时把整块栈填成 0xA5A5A5A5，长跑后看还有多少没被覆盖，
#   就得到了实测最高水位。FreeRTOS 的 uxTaskGetStackHighWaterMark()、
#   Zephyr 的 CONFIG_THREAD_ANALYZER 都是这个原理。
// 栈涂色的手写版本，任何 RTOS 上都能用
constexpr std::uint32_t kPattern = 0xA5A5A5A5;

void paintStack(std::uint32_t* base, std::size_t words) {
  for (std::size_t i = 0; i < words; ++i) { base[i] = kPattern; }
}

// 长跑之后调用：返回"从未被写过的字数"，越接近 0 越危险
std::size_t stackHeadroom(const std::uint32_t* base, std::size_t words) {
  std::size_t untouched = 0;
  while (untouched < words && base[untouched] == kPattern) { ++untouched; }
  return untouched;
}
实测水位不能直接当作栈大小的依据。它只告诉你"在测过的这些路径上用了这么多"，而最坏路径可能是一条极少走到的错误处理分支——恰恰是这类路径在现场偶发触发时最容易溢出。正确做法是两者结合：静态分析给上界、实测水位做交叉验证，最终栈大小取静态上界并留裕度（裕度比例应由项目的安全要求决定，不要随手拍一个数）。此外一定要开栈溢出检测机制——MPU 保护页、RTOS 的栈溢出钩子、或至少在栈底放一个哨兵值并周期检查。

DMA 与中断合并：让 CPU 别做搬运工

嵌入式性能优化里收益最大的一类改动，往往不是把代码写快，而是把 CPU 从数据通路上移走。

DMA 替代 CPU 搬运

ADC 采样、SPI 收发、以太网收包，如果由 CPU 逐字节搬，既慢又占满中断。改成 DMA 后 CPU 只在整块传输完成时被中断一次。

典型配置是双缓冲 / 乒乓：DMA 往缓冲 A 写的同时，CPU 处理缓冲 B，传输完成中断里交换两者。采集与处理完全并行，且没有任何拷贝。

陷阱是 cache 一致性。有数据 cache 的平台上，DMA 直接读写物理内存，CPU 看到的可能是过期的 cache 行。要么把 DMA 缓冲放在非缓存区域，要么手动维护——方向搞反是这类 bug 最常见的形态：发送前要 clean（把 CPU 的写刷进内存），接收后要 invalidate（丢弃 CPU 手里的旧副本）。

中断合并（coalescing）

每秒十万个小包、每包一次中断，光中断开销就能吃掉一个核。合并的做法是「攒够 N 个或超时 T 微秒才中断一次」。

这是一笔明确的延迟换吞吐：合并窗口 T 直接加到了单个事件的最坏延迟上。所以实时路径上要么关掉合并，要么把 T 设得远小于时间预算。

同一思路的其它形态：多个软件定时器共用一个硬件定时器、一次唤醒批量处理队列里的多个元素而不是逐个唤醒。

功耗与确定性：DVFS 是一个陷阱

动态调频调压（DVFS）在手机和服务器上是纯收益：负载低就降频省电，负载高就升频。在实时系统里它是确定性的直接破坏者，原因有三层：

  1. 频率变化让 WCET 失去意义。按 1.2 GHz 算出来的 200 µs，在降到 400 MHz 时会变成 600 µs。除非一律按最低频率算 WCET——那等于放弃了 DVFS 的全部收益。
  2. 频率切换本身有过渡时间，期间 CPU 可能暂停执行。时间通常不长，但它是一个额外的、不易预测的抖动源。
  3. 调速器是反应式的：它看到负载上升才升频，而实时任务恰恰在"负载刚上升的那一刻"最需要算力。等它反应过来，deadline 已经过去了。

同样的道理适用于深度 C-state：从深睡眠唤醒可能要几十甚至上百微秒，对 µs 级预算是致命的。所以实时系统的标准做法是锁定频率、禁用深度睡眠（见 §7 的启动参数），代价是功耗与发热明显上升。

如果你的约束是……做法代价
纯实时，不在乎功耗（车载有电、工业有市电）锁定频率，禁掉所有省电特性发热与散热设计成本
电池供电但有硬实时需求分区：实时任务跑在锁频的核上，其余核正常调频；或用一颗独立的低功耗 MCU 承担实时部分，主 SoC 该睡就睡系统复杂度、跨核通信设计
软实时 + 强功耗约束可以用 DVFS，但要按最坏频率验证时序，而不是按标称频率额外的时序验证工作
周期唤醒、大部分时间空闲可以用深度睡眠，但把唤醒延迟计入时间预算并实测（实测值往往大于数据手册）唤醒延迟占掉一部分预算

# ① 有 Linux 的目标：perf 依然是首选
$ perf stat -e cycles,instructions,cache-misses,branch-misses ./ctrl
$ perf record -F 997 -g -- ./ctrl && perf report
# 注意：采样式 profiler 给的是"时间总体花在哪"的统计，
# 它天然看不到"那一次特别慢"的单次事件 —— 长尾要靠 trace，不是靠 profile。
// ② Cortex-M 上：DWT 周期计数器，分辨率是 1 个 CPU 时钟周期。
//    调试器连接时 trace 单元通常已使能；独立运行时要自己打开。
CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
DWT->CYCCNT = 0;
DWT->CTRL  |= DWT_CTRL_CYCCNTENA_Msk;

const uint32_t t0 = DWT->CYCCNT;
controlStep();
const uint32_t dt = DWT->CYCCNT - t0;      // 无符号相减，自动处理一次回绕

// 关键：不要只看本次值，要维护最大值 —— 我们要的是最坏情况
static uint32_t s_worst = 0;
if (dt > s_worst) { s_worst = dt; }
// dt 除以 CPU 频率得到耗时。CYCCNT 是 32 位，200 MHz 下约 21 秒回绕一次，
// 测更长的间隔要自己处理多次回绕。
// ③ 什么都没有的时候：GPIO 打点 + 示波器（见 §8）。
//    这是唯一不依赖目标上任何软件设施、也是唯一能测到
//    "从外部事件到软件响应"这段全链路时间的方法。

// ④ RTOS 自带的运行时统计（如 FreeRTOS 的 vTaskGetRunTimeStats）
//    给出各任务占 CPU 的比例，适合回答"预算花在谁身上"，
//    但时间基通常较粗，不适合测单次执行时间。
这一章最值得强调的一句：我们测的是最大值，不是平均值。服务端的 profiler 天生面向"时间总体花在哪"这个统计问题，而实时系统关心的是"最慢的那一次为什么慢"。所以工具优先级是 trace（记录每个事件）优先于 profile（采样统计），记录 max 优先于记录 avg。这与 §1 的「实时 ≠ 快」是同一件事在测量层面的体现。

11.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础什么是实时系统？"实时"等于"快"吗？

    不等于。实时的定义是「最坏情况响应时间有可论证的上界」，与平均速度无关。一台 3 GHz 服务器的平均中断响应可能是 2 µs，比 100 MHz 的 MCU 快一个数量级，但它的最坏值可能是 8 ms，而 MCU 是 3 µs。对一个必须每 250 µs 完成一次采样的控制回路来说，只有那个最坏值决定系统能不能用。

    把它拆成两句更完整：① 系统必须在规定的时间内完成响应；② 这个时间上界必须是可以事先论证的，而不是"跑了一周没出问题"。

    由此推出实时工程的核心交易：用平均性能买确定性。锁定 CPU 频率、禁用深度睡眠、把中断改成线程、禁用动态内存，每一项都在牺牲吞吐或功耗，换取"最坏情况可预测"。能主动说出这笔交易，比背定义有说服力得多。

  2. 基础硬实时、软实时、准实时（firm）怎么区分？

    划分依据不是时间尺度，而是错过一次 deadline 的后果。很多人以为"µs 级是硬实时、ms 级是软实时"，这是错的——一个 100 ms 周期的气囊自检是硬实时，一个 1 ms 刷新的仪表动画是软实时。

    • 硬实时：错过即系统失效，可能造成人身伤害或设备损毁。迟到的结果比没有结果更糟（一个迟到的刹车指令会让车在错误的时刻减速）。例：ABS、气囊点火、飞控内环、电机换相。
    • 准实时 firm：错过则该次结果作废（价值直接归零），但系统继续运行。例：一帧迟到的视频画面，直接丢掉即可。
    • 软实时：错过则价值逐渐衰减，仍然可用。例：UI 动画掉帧、日志上报延迟。

    工程上的用法：写需求时先问"迟到的结果比没有结果更糟吗"。这一句能定下等级，进而决定要不要上 RTOS、要不要做 WCET 分析、要不要走认证——省掉后面大量的争论。

  3. 基础CLOCK_MONOTONIC 和 CLOCK_REALTIME 有什么区别？该用哪个？

    所有时间差计算、周期任务、超时判断都必须用 CLOCK_MONOTONIC。CLOCK_REALTIME 是墙上时钟，它会跳：NTP 校时会向前或向后拨、管理员可以直接设置它、闰秒也会影响它。

    后果不是理论上的。一次 NTP 回拨会让"距上次采样过去了多久"算出负数，PID 的微分项据此算出一个巨大的值，执行器猛动一下——这类事故在工业现场真实发生过，而且极难复现（它只在校时的那一瞬间发生）。

    其他几个时钟的分工：

    • CLOCK_MONOTONIC_RAW：完全不受 NTP 频率校正影响。适合测量硬件本身的频偏，但正因为不被校正，长时间会与真实秒有累积偏差，不适合做长周期定时。
    • CLOCK_BOOTTIME：与 MONOTONIC 类似但包含系统挂起的时间。会休眠唤醒的设备（车机、电池设备）上要特别分清这两者。
    • CLOCK_TAI：无闰秒，用于与 PTP / TSN 的时间基对齐。

    C++ 侧是同一个坑换了名字：std::chrono::system_clock 对应 REALTIME（会跳），steady_clock 对应 MONOTONIC。测耗时永远用 steady_clock。

  4. 基础为什么车端 C++ 禁止运行期动态内存？

    不是因为 malloc 慢——它其实常常很快。真正的理由有三层，而且都指向可论证性而不是性能：

    • 耗时不确定：分配时间取决于堆当前的碎片状态，是运行历史的函数，无法给出 WCET 上界。
    • 碎片会随运行时间累积：一个跑三年的 ECU 可能在第三年某天分配失败。这种失效在测试里几乎不可能复现——你没法测三年。
    • 分配可能失败：于是每个调用点都多出一条极难覆盖的错误路径，而高等级认证要求结构化覆盖率。

    替代做法是初始化阶段一次性预分配：内存池、固定容量容器（容量作为模板参数），运行期只从池里取。

    加分的一句：换成固定容量容器不等于问题消失，只是把问题挪到了显眼处。原来 vector 会默默增长，现在 push_back 返回 false，于是"满了怎么办"变成一个必须由需求回答的问题——丢最旧的？丢最新的？置故障码？这正是这条规则的价值：逼你在设计阶段面对容量上界，而不是在现场。

11.2 中级（区分熟练度）

  1. 中级WCET 为什么测不准？跑一百万次取最大值不行吗？

    不行，而且这个说法本身就搞反了方向：实测只能给出下界（证明"至少这么慢"），永远给不出上界。你测到的最大值只意味着"在测过的这些条件下没见过更慢的"。

    根本原因是执行时间不只取决于代码，还取决于你无法完全控制的微架构状态：

    • Cache：同一段代码全命中 L1 和全落 DRAM 能差十倍以上，而命中与否取决于"刚才是谁在这个核上跑"。多任务系统里这是外部输入，专门有个名词叫 cache-related preemption delay，是可调度性分析里的独立项。
    • 分支预测器与预取器：状态由历史执行路径决定，是隐藏的全局变量，厂商通常不公开替换策略，静态分析只能保守假设"全部预测失败"。
    • DVFS 与热降频：频率变了，绝对耗时跟着变。
    • DRAM 刷新、总线争用、x86 的 SMI：SMI 由固件触发，操作系统既无法屏蔽也无法观测，是很多 x86 实时平台上无法解释的毫秒级尖峰的来源。
    • 路径爆炸：循环上界不明、函数指针、递归都会让路径集合无法闭合。

    工业界的做法是两条腿：静态分析工具（AbsInt aiT、Rapita RapiTime 一类）沿控制流图算出一个保证不低于真实值的保守上界，再用大量实测取上包络做交叉验证。静态上界通常明显高于实测最大值，这部分"浪费"就是确定性的价格。

    最后一句反过来说明了 §5 那些编码规则的由来：禁递归、要求循环上界编译期可知、限制函数指针，都是为了让路径集合能够闭合，否则静态分析根本无法开始。

  2. 中级抖动（jitter）和平均延迟是什么关系？为什么报告里要看 Max 不看 Avg？

    平均延迟描述分布的中心，抖动描述分布的离散程度（工程上常用 max − min 或高分位数与中位数之差）。实时系统的成败由分布的右端决定，而平均值对右端几乎没有信息。

    一个具体的例子：cyclictest 报告 Min: 2 Avg: 5 Max: 78（µs）。Min 和 Avg 三个数字里唯一有意义的是 78。如果 deadline 是 50 µs，那么这个系统已经失败了——尽管 99.99% 的样本都在 8 µs 以内。

    三个容易被忽略的推论：

    • 空载测出来的 Max 没有参考价值。延迟尖峰几乎都由"别人在干活"引发：网卡收包风暴、磁盘回写、图形合成、内存回收。必须一边施加最恶劣的干扰一边测。
    • 测 1 小时 Max 是 78 µs，不代表跑一年不会出现 900 µs。要么把测试时间拉长到与产品寿命可比（不现实），要么去分析尖峰的成因——只有搞清"78 µs 那次是谁造成的"，才能论证不会有更差的情况。
    • 抖动和漂移是两回事。抖动是有界且不累积的随机偏差；漂移是单调累积的系统性误差（下一题）。混用这两个词会让人怀疑你的实际经验。
  3. 中级怎么写一个精确的 1 kHz 周期任务？用 usleep(1000) 有什么问题？

    usleep / 相对 sleep 的问题是误差会累积成漂移，而不只是抖动。

    // ❌ 相对 sleep：实际周期 = 工作耗时 W + 1000 µs + 唤醒延迟 L
for (;;) { doWork(); usleep(1000); }

    关键在于每一轮都以"现在"为新基准，于是 W + L 被加进下一轮的起点，误差单调累积。跑 1 小时（360 万轮），若平均 W + L 只有 80 µs，就已经漂了 288 秒——将近 5 分钟。症状是：数据时间戳与实际不符、与外部设备（PLC、总线主站）逐渐失步、实际采样率比标称低几个百分点。

    正确做法是用绝对时间：

    timespec next{};
clock_gettime(CLOCK_MONOTONIC, &next);   // 只在循环外取一次"现在"
for (;;) {
  tsAddNs(next, kPeriodNs);              // next = start + n × period
  clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, nullptr);
  doWork();
}

    TIMER_ABSTIME 表示"睡到这个绝对时刻"，而不是"从现在起睡多久"。基准是一条独立于执行过程的时间轴，单轮的抖动只影响那一轮，下一轮自动回到网格上。抖动仍然存在（有界），但漂移消失了。

    三个必须一并说到的细节，否则答案不完整：

    • 时钟必须用 CLOCK_MONOTONIC，且与 clock_gettime 保持同一个。
    • 返回 EINTR（被信号打断）时要 continue 继续睡到同一个时刻，而不是重新计算。
    • 必须做超时检测：如果 doWork 比周期还慢，next 会落到过去，clock_nanosleep 立刻返回，任务开始"追赶"。这必须被计数并上报，同时要明确"落后太多时是追赶还是重新对齐"——通常选重新对齐，因为追赶只会让系统雪上加霜。
  4. 中级怎么测一个中断的响应延迟？为什么 GPIO 翻转法比在代码里打时间戳更可信？

    做法：在 ISR 入口写一次 GPIO 拉高、出口拉低，用示波器的两个通道分别接触发源和这根调试引脚，直接量两个沿之间的时间。

    // 用 BSRR 这类"置位/清零专用寄存器"，一次写完成，开销只有几个时钟周期。
// 不要用 ODR ^= mask —— 那是读-改-写，更慢而且不原子。
void TIM2_IRQHandler(void) {
  GPIOA->BSRR = (1U << 5);        // ISR 开始
  controlStep();
  GPIOA->BSRR = (1U << 21);       // ISR 结束（高 16 位是清零域）
}

    示波器上一次读出三个量：脉冲宽度 = ISR 执行时间（游标放在最宽的那个就是实测最坏值）、上升沿间隔 = 实际周期、触发源到上升沿 = 中断延迟。开无限余辉模式看边沿的"胖度"，就是抖动的可视化。

    为什么比软件时间戳可信：任何软件内部的计时都在被测系统之内，会被同样的调度延迟、cache 效应、中断屏蔽影响；而且它测不到"从电平变化到软件第一条指令"这一段——那一段恰恰是中断延迟的主体。示波器在系统之外，它不会撒谎。当软件说"我只用了 200 µs"而系统表现对不上时，示波器是唯一的仲裁者。

    Linux 目标上的补充手段：cyclictest -b <µs> 在超阈值时自动停止内核 trace，再用 trace-cmd report 往前翻看那段时间 CPU 上在跑什么；或者用 rtla timerlat 分别给出 IRQ 层与线程层的延迟，直接定位是哪一段慢。

11.3 高级（体现深度）

  1. 高级什么时候选 RTOS，什么时候选 Linux + PREEMPT_RT？

    按硬约束优先的顺序问四个问题，能砍掉九成候选：

    1. 算力与内存：KB 级 RAM、无 MMU → 只能是 RTOS 或裸机，讨论结束。有 MMU 和几百 MB 内存才谈得上 Linux。
    2. 要不要认证：需要 ISO 26262 / IEC 61508 / DO-178C 的高完整性等级时，Linux 通常不是主路径——代码规模与开发过程难以满足证据要求。常见架构是安全功能放认证 RTOS（QNX、VxWorks、SafeRTOS），Linux 只承担 QM 或低等级部分，中间用 hypervisor 隔离。
    3. 要不要 Linux 生态：需要 TCP/IP 栈、文件系统、容器、Python/AI 框架、厂商 BSP 时，自己在 RTOS 上重造这些的成本极高。
    4. 最坏延迟指标：≥ 500 µs → PREEMPT_RT 有充足裕度；50–200 µs → 必须在目标板上实测才能定（x86 的 SMI、某些 SoC 的总线争用都可能一票否决）；< 20 µs → 不要用 Linux，它的中断路径固定开销就压不到这个量级，该回 MCU 或把这一环下沉到 FPGA。

    还要说清 PREEMPT_RT 的代价，否则答案只有一半：吞吐下降（中断密集与锁密集的负载最明显）、功耗上升（禁 C-state、锁频率）、CPU 被隔离核"浪费"、以及驱动兼容性——假设"自旋锁不会睡眠"的老驱动会直接触发 BUG: sleeping function called from invalid context，这是实际项目里最常见的卡点。

    加分：提到 2024 年 PREEMPT_RT 完成主线化（Linux 6.12 LTS）。它的意义不在于延迟数字变好（基本没变），而在于长期维护成本塌方式下降——以前每次跟内核版本都要 rebase 一大摞补丁，现在 RT 是主线的一等公民。这一项因此可以从选型的风险表里划掉了。

    还有一档中间形态：双内核（Xenomai）。实时任务由旁边一个独立的实时内核调度，完全不受 Linux 影响，代价是实时代码要用它自己的 API、跨界调用有开销、维护负担高于主线 RT。自 PREEMPT_RT 进主线后，新项目选它的理由已经少很多。

  2. 高级实时线程要把数据交给一个会阻塞的日志线程，怎么设计才安全？

    答案是单生产者单消费者（SPSC）无锁环形缓冲，并且队列满时由实时线程直接丢弃并计数。

    先说为什么不能用互斥量：非实时线程持锁时被抢占，实时线程就得等它——这是优先级反转的教科书场景。即使启用了 PTHREAD_PRIO_INHERIT，最坏情况也只是从"无界"变成"有界但不小"，那个界包含消费者的整个临界区，通常远超时间预算。

    实现要点（每一条都对应一个真实的坑）：

    • 容量取 2 的幂，取模退化成一次与运算，避免除法。
    • head_ 与 tail_ 必须 alignas(64) 分处不同 cache line。否则生产者每次写 head_ 都会让消费者所在核上缓存 tail_ 的那行失效——这就是 false sharing，实测能让吞吐掉一个数量级，而且它只在多核上出现，单核测不出来。
    • 内存序：写自己的索引用 relaxed（只有我写），读对方的索引用 acquire，发布自己的索引用 release。release 保证数据写入对看到新索引的对方一定可见。
    • 用 std::atomic 而不是 volatile。volatile 不提供任何内存序保证，编译器和 CPU 都可以重排它前后的普通访问。它的用途是访问外设寄存器（禁止合并/省略访问），不是线程同步——这是嵌入式代码里最普遍的一个错误认知。
    • 元素类型应可平凡拷贝，避免拷贝过程本身分配内存。

    最重要的一条设计原则：实时线程永不阻塞、永不重试。满了就丢，把丢弃计数上报到诊断。控制回路的时序比某一条日志重要得多；而"丢弃可见"让容量是否够用变成一个可以被数据回答的问题。

    加分：说明为什么不用 MPMC 无锁队列——能用，但实现复杂度与最坏重试次数都高得多。SPSC 能满足需求时永远优先 SPSC，因为它的正确性可以用眼睛看明白。

  3. 高级DVFS 对实时性有什么影响？为什么实时系统通常要锁定频率？

    DVFS（动态调频调压）在手机和服务器上是纯收益，在实时系统里是确定性的直接破坏者，三层原因：

    1. 让 WCET 失去意义：按 1.2 GHz 算出的 200 µs，降到 400 MHz 就变成 600 µs。除非一律按最低频率算 WCET——那等于放弃 DVFS 的全部收益。
    2. 切换本身有过渡时间，期间 CPU 可能暂停执行，是一个额外的、不易预测的抖动源。
    3. 调速器是反应式的：它看到负载上升才升频，而实时任务恰恰在"负载刚上升的那一刻"最需要算力。等它反应过来，deadline 已经过去了。

    同样的逻辑适用于深度 C-state：从深睡眠唤醒可能要几十到上百微秒，对 µs 级预算是致命的。所以标准做法是 performance 调速器锁定频率 + processor.max_cstate=1 + idle=poll，代价是功耗与发热明显上升。

    更好的答案会给出不必二选一的架构：分区——实时任务跑在锁频的隔离核上，其余核正常调频省电；或者用一颗独立的低功耗 MCU 承担实时部分，主 SoC 该睡就睡。这在电池供电又有硬实时需求的产品上是常规解法，代价是系统复杂度和跨核通信设计。

    再加一句：这与 §1 的主线是同一件事——DVFS 优化的是期望值（平均能效比），实时优化的是分布右端，两个目标在这里直接冲突，必须明确选一个。

  4. 高级给你一个新项目：1 kHz 的运动控制回路，需要以太网上报数据和一个本地触摸界面。你怎么做技术选型？

    这是综合题，考的是提问的顺序而不是最终结论。

    第一步：把需求问清楚，尤其是没写在需求文档里的那几个数。

    • 1 kHz 的抖动预算是多少？"周期 1 ms"是无意义的，"周期 1 ms 且抖动 < 50 µs"才是可验收的指标。这个数直接决定了后面所有选择。
    • 错过一次的后果是什么？工件报废（firm）还是可能伤人（hard）？后者意味着要走认证，成本结构完全不同。
    • 控制算法的计算量有多大？如果单次要 800 µs，1 kHz 就没有裕度，这时候要先谈算法而不是谈 OS。
    • 产量多少？单价敏感度决定了能不能用一颗好的 SoC，还是必须精打细算 BOM。

    第二步：先给一个架构假设，再验证。三个需求的实时性要求差三个数量级（1 kHz 控制 / 网络上报 / 触摸 UI），把它们塞进同一个执行环境是错误的起点。我会先提出分层架构：

    • 控制回路：绝不与 UI 抢资源。两个候选——(a) Linux + PREEMPT_RT，控制线程跑在隔离核上；(b) 独立 MCU 跑 RTOS 或裸机，通过 SPI / 以太网与主控通信。
    • 上报与 UI：普通 Linux 线程，通过 SPSC 无锁环形缓冲从控制侧拿数据，满了丢弃并计数。

    第三步：用实测在 (a) 和 (b) 之间做决定，而不是靠偏好。拿目标硬件跑 cyclictest，一边跑一边施加最恶劣的干扰（网络满载 + 磁盘写 + GPU 合成 + 真实业务流量），看 Max 是否在抖动预算的一半以内。如果预算是 50 µs 而实测 Max 是 120 µs，就走 (b) 的双芯片方案；如果实测 Max 是 30 µs 且能解释每一次尖峰的来源，(a) 可以省掉一颗芯片和一套通信。

    第四步：把工程配置一次做全。核隔离 + nohz_full + rcu_nocbs + 中断亲和 + 关 irqbalance + 锁频率 + 禁深度 C-state；应用侧 mlockall + 栈预热 + 启动阶段完成全部分配 + SCHED_FIFO 并按周期长短排优先级（单调速率）+ clock_nanosleep(TIMER_ABSTIME) 写周期循环。

    第五步：定义验收与长期监控。周期超时要计数上报、环形缓冲丢弃要计数上报、稳态下缺页数必须为零、长跑测试要覆盖最恶劣工况。没有这些指标，"实时性达标"就只是一句话。

    最能体现层次的一句收尾：如果 (a) 和 (b) 实测结果接近，我会选 (b) 双芯片——不是因为它性能更好，而是因为它把"确定性"和"生态"两个诉求做了物理隔离，后续加功能时不会有人不小心把一个新服务放到隔离核上，从而毁掉整个时序论证。架构选择要考虑的不只是今天能不能跑，还有三年后被别人改成什么样。
