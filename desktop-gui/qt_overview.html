01

Qt 到底是什么

一句话定义，再拆成三层

Qt（读作 "cute"）是一套用 C++ 写的跨平台应用开发框架：一份源码，编译后能在 Windows / Linux / macOS / 嵌入式屏幕上跑出界面一致的原生程序。1991 年诞生于挪威 Trolltech，现由 The Qt Company 维护，当前主线是 Qt 6.x。

初学者最容易形成的误解是「Qt = C++ 的界面库」。界面只是 Qt 的一个模块。把它拆开看，Qt 实际上是三层东西叠在一起：

层它提供什么为什么当年需要它
① 跨平台基础设施层 字符串 QString、容器 QList/QHash、文件与路径、线程、进程、定时器、网络、JSON/XML、配置存储、插件加载、国际化 1990 年代到 2010 年代，标准库既没有线程也没有网络、文件系统、正则、UTF-16 字符串。Qt 把这些一次补齐，且三大平台行为一致
② 自建运行时层（最独特） 元对象系统：运行时反射、信号槽（对象间松耦合通信）、属性系统、按名字动态创建对象与调用方法 C++ 没有反射。而 GUI 天生需要「按钮被点了，通知所有关心的人」这种运行时动态绑定。Qt 用一个代码生成器 moc 把反射能力补上了
③ UI 工具箱层 Qt Widgets（传统控件、CPU 绘制、桌面原生观感）与 Qt Quick / QML（声明式、GPU 加速、适合动效与触摸） 控件、布局、无障碍、输入法、高 DPI、主题——每一项自己实现都是巨量工作
把操作系统看成一座城市的市政系统（供水、供电、道路），那 Qt 就是建在其上的一整套商场运营系统：事件循环是前台的呼叫队列（谁按了铃就排队、按顺序处理）；对象树是租户隶属关系（一个区域撤柜，它下面的摊位一并清退，不用你逐个去谈）；信号槽是内部广播线路（广播一响，订阅了这条线的部门自己反应，广播方根本不需要认识它们）。你写业务代码 = 在这套运营规范下开店；好处是拎包入住，代价是必须守它的规矩——用纯 C++ 的习惯去动 Qt 的结构（比如自己 delete 一个有 parent 的控件、在别的线程里改界面），就是崩溃的主要来源。

顺手澄清几个「Qt 不是什么」

  • 不是即时模式的绘图库。Dear ImGui 那种「每帧重画整个界面」的模型和 Qt 完全不同：Qt 是保留模式——控件是长期存在的对象，只在需要时重绘。
  • 不是必须写 QML。用 Qt Widgets 可以全程只写 C++，一行 QML 都不碰，这也是绝大多数工业软件的做法。
  • 不排斥标准库。std::vector、std::unique_ptr、算法库在 Qt 项目里完全可以正常用，两套容器可以共存（只在 API 边界上做转换）。
  • 不只做桌面。嵌入式屏（无窗口系统，直接画到 framebuffer 或 EGL）、车机、医疗仪器面板都是 Qt 的重要战场。
许可这件事必须一开始就知道：Qt 是双许可。LGPLv3 允许闭源商业产品使用，但要求动态链接 Qt 并允许终端用户替换 Qt 库；商业许可才可以静态链接（单文件固件的嵌入式项目常被迫走这条）；另有个别模块只给 GPL，用了会传染。选型阶段就要逐模块确认，细节见 核心机制篇 §1 与 工程化篇。
02

没有 Qt 会怎样

理解一个框架，先看它替你挡掉了什么

假设不用任何框架，要在三个平台上开出一个能显示按钮的窗口。你会面对三套思路相似、细节完全不同的原生 API：

平台窗口与消息语言 / 特点控件
WindowsCreateWindowEx + GetMessage/DispatchMessage 消息循环 + WndProc 回调C API，字符串 UTF-16（wchar_t）系统自带一批（Common Controls），风格随系统版本变
Linux (X11/Wayland)XCB/Wayland 协议事件 + 自己写事件循环（poll 连接 fd）C API，字符串 UTF-8系统不提供控件，按钮、输入框都要自己画、自己处理键盘与输入法
macOSNSApplication + NSRunLoop + 委托对象Objective-C / Swift，需要混编Cocoa 控件，但 API 风格与前两者毫无相似

共同点是三者都遵循「事件循环 + 回调」这个 GUI 编程的普适模型；差异在于 API、字符编码、坐标与 DPI 规则、剪贴板、输入法、字体渲染、线程约束。Qt 把这些差异关进了一层插件里：

这张图不是纯理论，它直接对应一个部署阶段人人都会遇到的报错：This application failed to start because no Qt platform plugin could be initialized。含义就是最下面那层插件（Windows 上是 plugins/platforms/qwindows.dll，Linux 上是 libqxcb.so）没有随程序一起拷过去。把 exe 单独复制到另一台机器就跑不起来，根因即此，解法见 工程化与部署篇。

除了窗口，Qt 还统一了这些日常琐事

问题不用框架时Qt 的答案
中文乱码Windows 是 UTF-16、Linux 是 UTF-8，编码转换到处写QString 内部统一 UTF-16，边界处 toUtf8()/fromUtf8() 显式转换
路径分隔符\ 与 / 分头处理API 内部一律 /，QDir::toNativeSeparators() 只在给外部程序时用
配置存储Windows 注册表、macOS plist、Linux 配置文件各写一遍QSettings 一套 API，后端自动映射
多语言自己搞一套字符串表tr("开始") + Qt Linguist 的 .ts/.qm 流程
高 DPI 缩放各平台缩放模型不同，界面在 4K 屏上或糊或小Qt 6 默认开启高 DPI 缩放，逻辑像素与物理像素分离
定时器与异步 IO平台各自的 timer / select / IOCPQTimer、QTcpSocket 等统一挂在同一个事件循环上

换个角度说，Qt 的价值 =「跨平台一致性」+「补齐 C++ 缺失的运行时能力」+「一个成熟的控件与工具生态」。这三点也解释了它的代价：你必须接受它的对象模型和线程规则，而这套规则正是本系列后面四篇要讲透的东西。

05

第一个程序，逐行拆解

从 main() 到窗口出现在屏幕上

下面这 20 行是一个完整可运行的 Qt 程序：一个标签 + 一个按钮，点一次计数加一。每一行都藏着一个 Qt 概念，我们逐个拆。

// main.cpp
#include <QApplication>
#include <QWidget>
#include <QLabel>
#include <QPushButton>
#include <QVBoxLayout>

int main(int argc, char* argv[]) {
    QApplication app(argc, argv);                    // ① 应用对象，必须最先建、放栈上

    QWidget window;                                  // ② 顶层窗口（没有 parent）
    window.setWindowTitle(QObject::tr("计数器"));   // ③ tr() 为将来翻译留口子

    auto* label  = new QLabel("点击次数：0");       // ④ 堆上 new，但不写 delete
    auto* button = new QPushButton("点我");

    auto* layout = new QVBoxLayout(&window);      // ⑤ 布局，构造时即挂到 window
    layout->addWidget(label);                        //    addWidget 会 setParent(window)
    layout->addWidget(button);

    int count = 0;
    QObject::connect(button, &QPushButton::clicked,  // ⑥ 信号 → 槽（这里是 lambda）
                     label, [label, count]() mutable {
        label->setText(QString("点击次数：%1").arg(++count));
    });

    window.resize(280, 120);
    window.show();                                   // ⑦ 只是"标记为可见"，此刻还没画
    return app.exec();                               // ⑧ 进入事件循环，程序在这里"活着"
}

八个要点

①→QApplication 一个进程只能有一个，且必须在任何界面对象之前构造。它在构造时加载 QPA 平台插件、初始化字体与样式、解析 -platform 等命令行参数。放在栈上是为了让它最后才析构（先于它析构的窗口才能正常清理）。纯后台程序（没界面）用 QCoreApplication，只用 Qt Gui 不用 Widgets 时用 QGuiApplication。
②→没有 parent 的 QWidget 就是顶层窗口，Qt 会向系统申请一个真实窗口；有 parent 的控件只是父窗口里的一块区域。「窗口」和「控件」在 Qt 里是同一个类，区别只在有没有父亲。
③→所有给用户看的字符串都套 tr()。现在没成本，将来要出英文版时，工具能自动扫出全部待翻译文本。事后补 tr() 是最没意义的加班之一。
④⑤→new 了却不 delete，这不是内存泄漏：addWidget 内部会把控件的 parent 设为 window；window 析构时会递归 delete 所有子对象。这就是 Qt 的对象树所有权模型。反过来，如果你把控件建在栈上再交给布局，程序退出时会 double free——父对象要 delete 一个栈地址。
⑥→connect 把「按钮被点击」这个信号接到一段代码上。按钮完全不知道谁在监听，也不需要包含你的头文件——这就是解耦。第三个参数 label 是 context object：它一析构，这条连接自动失效，避免野回调。习惯：用 lambda 当槽时，总是传 context。
⑦→show() 不画界面。它只设置可见标记并投递 QShowEvent/QPaintEvent 到事件队列。真正的绘制发生在 exec() 之后、事件循环取出 paint 事件时。所以经典新手现象是：show() 后面紧跟一个耗时循环 → 窗口是一片空白甚至假死。
⑧→exec() 才是程序的主循环，概念上就是 while (!quit) { 取一个事件; 分发给目标对象; }。它一直不返回，直到 quit()/最后一个窗口关闭；返回值成为进程退出码。所有槽函数、定时器、网络回调都是被这个循环调用的——它们跑在同一个线程、排在同一条队上。

▶ 亲眼看「界面冻结」

下面的转圈由 JS 逐帧驱动，等价于「界面重绘」。点第一个按钮：本页主线程被同步占住 1.5 秒——和 Qt 里「槽函数里做耗时计算」完全同一种病，转圈会明显停住、刷新率掉到 0。点第二个按钮：同样 1.5 秒的工作量被切片交还给事件循环，转圈全程流畅。

状态：空闲
刷新率：-- fps
这是 Qt 的第一条铁律：界面对象只能在主线程创建和访问，槽函数必须尽快返回。耗时的事情交给工作线程或切片调度（QTimer::singleShot(0, ...)），完成后用信号把结果送回主线程。不要用 QApplication::processEvents() 硬撑着刷新界面——它会在你的调用栈中间重新分发事件，导致槽函数重入甚至 this 被删除后继续访问。原理与替代方案见 线程与并发篇。
06

构建链：moc / uic / rcc

Qt 项目多出来的三个代码生成器

Qt 项目的编译过程比普通 C++ 项目多一步：在编译器动手之前，先有三个工具扫过你的源码，生成额外的 .cpp/.h 一起参与编译。不知道它们存在，就会被一类奇怪的报错困住。

工具输入输出解决什么
moc
Meta-Object Compiler		含 Q_OBJECT 宏的头文件moc_xxx.cppC++ 没有反射。moc 生成类的元信息表、信号函数的实现体、以及「按索引调用某个成员函数」的分派代码，信号槽才能在运行时工作
uic
UI Compiler		Qt Designer 拖出来的 xxx.ui（XML）ui_xxx.h把可视化设计的界面翻译成「一堆 new 控件 + 设置属性 + 布局」的 C++ 代码
rcc
Resource Compiler		xxx.qrc 清单 + 图标/qss/翻译文件qrc_xxx.cpp把资源文件编进可执行文件，用 ":/icons/play.png" 访问，发布时不用带一堆散图

最小 CMake 工程

# CMakeLists.txt
cmake_minimum_required(VERSION 3.19)
project(counter LANGUAGES CXX)

find_package(Qt6 REQUIRED COMPONENTS Widgets)
qt_standard_project_setup()          # Qt 6.3+：自动打开 AUTOMOC / AUTOUIC 等常用开关

qt_add_executable(counter
    main.cpp
    mainwindow.cpp mainwindow.h      # 头文件也要列出来，AUTOMOC 才会扫到它
    mainwindow.ui                    # .ui 交给 AUTOUIC
)
target_link_libraries(counter PRIVATE Qt6::Widgets)
qt_add_resources(counter "res" PREFIX "/" FILES icons/play.png)
配置时如果报「找不到 Qt6」，是因为 CMake 不知道 Qt 装在哪。传一个前缀即可：cmake -B build -DCMAKE_PREFIX_PATH=D:/Qt/6.8.0/msvc2022_64。用 Qt Creator 打开工程时它会自动带上这个参数，这也是新手推荐用 Qt Creator 起步的原因之一。

三个「一看就懂根因」的经典报错

报错根因解法
undefined reference to vtable for MyClass类里写了 Q_OBJECT 但 moc 没为它生成代码（头文件没进源码列表 / 加宏后没重新配置构建）把头文件加入 qt_add_executable；重新跑 CMake，必要时清一次构建目录
自定义信号 undefined reference信号只有声明——它的函数体本来就该由 moc 生成，你却漏了 Q_OBJECT补上 Q_OBJECT（必须在类体第一行区域，且类必须直接或间接继承 QObject）
在 .cpp 里定义带 Q_OBJECT 的类，链接失败AUTOMOC 对 .cpp 内的类生成 xxx.moc，但需要你自己包含它在该 .cpp 末尾加 #include "xxx.moc"

看到「vtable」「no such signal」这类词就条件反射想到 moc，能省掉入门期最多的无效搜索。moc 究竟生成了什么代码、emit 展开后长什么样，在 核心机制篇 §4 有逐行反汇编级别的拆解。

07

五大核心概念速览

先建立正确直觉，深水区留给后面四篇

下面五个概念构成了「会写 Qt」的最小知识集。每个给一句话定义、一个类比、一段最小代码，以及新手最容易在这里犯的错。

7.1 对象树：谁负责 delete

每个 QObject 可以有一个 parent 和任意多个 children。parent 析构时会自动 delete 全部 children，递归向下。GUI 里一个窗口动辄几十上百个控件，这套机制把「逐个管理生命周期」变成了「管好根节点」。

像公司的组织架构：部门撤销时，下属岗位一并撤销，不需要 HR 逐个发通知。但如果某个岗位同时挂在两个部门下（对象树 + shared_ptr 双重所有权），撤销时就会有两边都来「清理」同一个人的荒诞场面——这正是 double free。
❌ 栈对象交给对象树
QWidget window;
QLabel label("hi");
layout->addWidget(&label);   // parent = window
// window 析构时 delete 一个栈地址 → 崩溃
✅ 堆对象 + 明确的 parent
QWidget window;
auto* label = new QLabel("hi");
layout->addWidget(label);    // 树接管所有权
// 不写 delete；需要弱引用时用 QPointer

7.2 信号槽：对象之间怎么通话

信号 = 「某件事发生了」的声明（只有声明，实现由 moc 生成）；槽 = 一个普通成员函数或 lambda。connect 把两者接起来，双方都不需要认识对方的类型。

class Device : public QObject {
    Q_OBJECT                                  // 必写：moc 的标记
public:
    void poll() { emit valueChanged(readSensor()); }
signals:
    void valueChanged(double v);            // 无函数体
};

// 连接：函数指针语法，编译期检查签名
connect(device, &Device::valueChanged, gauge, &Gauge::setValue);
// 一个信号可连多个槽；接收者析构时连接自动断开
信号槽的三个高价值特性，也是它相对裸回调的意义：① 一对多、运行时可增删；② 接收者析构自动断连，不会留野指针回调；③ 跨线程时自动切换执行线程——工作线程 emit，主线程的槽照样安全地在主线程执行。代价是需要继承 QObject、引入 moc 步骤，单次调用比直接函数调用慢几十纳秒（热路径按帧按像素的循环里别用）。

7.3 事件循环：程序的心跳

鼠标键盘、重绘请求、定时器到期、socket 可读、跨线程信号，最终都变成事件排进同一个队列，由 exec() 里的循环逐个取出分发。一个线程一个事件循环（要跑 exec() 才有）。

QTimer — 挂在事件循环上的定时器。QTimer::singleShot(0, obj, func) 是一个很实用的技巧：把一段代码「推到下一轮循环再执行」，用来切分长任务、或者避免在信号处理中直接销毁自己。同理，deleteLater() 也是投递一个删除事件——它依赖事件循环，没有循环的线程里对象永远不会被删。

7.4 布局系统：不要写死坐标

Qt 用布局管理器（QVBoxLayout / QHBoxLayout / QGridLayout / QFormLayout）自动计算控件几何。控件通过 sizeHint 报告理想尺寸、通过 sizePolicy 声明伸缩意愿，布局据此分配空间。

新手常用 setGeometry(10, 20, 80, 24) 手摆坐标，在自己机器上看着挺好，然后在三个地方崩塌：① 用户拉伸窗口，控件不动；② 换 4K 高 DPI 屏，一切错位；③ 界面翻译成德语，按钮文字被截断。布局系统正是为这三件事存在的——只在自定义绘制的画布里才该谈像素坐标。

7.5 模型 / 视图：数据多了必须换写法

Qt 提供两套路子显示列表和表格：便捷类（QTableWidget/QListWidget，逐个 item 塞数据）和模型视图（自己实现 QAbstractTableModel，视图按需向模型取数）。

QTableWidget（便捷类）QTableView + 自定义 Model
数据存在哪控件内部，每格一个 QTableWidgetItem 对象你自己的容器（std::vector 都行），视图不持有数据
1 万行 × 10 列10 万个堆对象，构造慢、内存高只为可见的几十行调用 data()
适合配置页那种几十行的固定表日志、采集数据、数据库结果集
代价—要实现 rowCount/columnCount/data/headerData，增删要正确发 beginInsertRows 等信号

判断标准很简单：数据行数由外部输入决定（可能上万）就用模型视图，否则用便捷类省事。大数据量表格与图像显示的性能细节在 工程化篇。

还有两个「早知道早省事」的小机制

  • 资源系统（qrc）：图标、样式表、翻译文件通过 .qrc 编进 exe，用 ":/icons/play.png" 这样的路径访问。避免了「换台机器图标全丢」。
  • 样式表（QSS）：类 CSS 的语法调整控件外观，QPushButton:hover { background: #2d6cdf; }。适合做主题；但大量复杂 QSS 会拖慢绘制，且与原生观感冲突，工业软件里通常只做克制的定制。
08

实战：采集 → 显示架构

一个真实小项目该怎么分层

需求 — 一台设备通过 TCP（或串口）以 100 Hz 上报数据帧；界面要实时画曲线、显示连接状态、支持开始/停止记录，记录写入本地文件；断线要自动重连。这几乎是所有工业上位机的最小骨架。

新手最常见的写法是：把 socket 建在 MainWindow 里，readyRead 槽里解析数据、更新曲线、顺手写文件。能跑，但三个月后没人敢改：界面代码里混着协议解析和文件 IO，写盘一卡界面就掉帧，换成串口要重写一遍，想加个自动化测试无从下手。

正确的做法是按职责切开，用信号槽做层间唯一的通信方式：

线程怎么分

组件线程为什么
所有界面对象必须主线程Qt 的硬约束，别的线程碰界面就是未定义行为
AcquisitionController主线程它只做状态机和转发，几乎不耗时；放主线程省掉一堆同步问题
TcpLink / SerialLink工作线程 A协议解析、大包拼接可能耗时；且它内部有自己的事件循环处理 socket 事件
Recorder工作线程 B磁盘 IO 会不定时卡住几十毫秒，绝不能挡住采集或界面

把对象搬到工作线程的标准装配代码——注意注释里的三个坑：

// AcquisitionController::start()
m_thread = new QThread(this);
m_link   = new TcpLink;              // ① 不能给它 parent，否则 moveToThread 失败
m_link->moveToThread(m_thread);

// 线程启动后，在新线程里执行 open()
connect(m_thread, &QThread::started, m_link, &TcpLink::open);
// 数据回传：跨线程，Qt 自动用 Queued 连接（参数会被拷贝）
connect(m_link, &DeviceLink::frameReady, this, &AcquisitionController::onFrame);
connect(m_link, &DeviceLink::stateChanged, this, &AcquisitionController::onState);
// ② 退出顺序：先删对象，再让线程结束，最后删线程
connect(m_thread, &QThread::finished, m_link, &QObject::deleteLater);

m_thread->start();                    // ③ 这里之后就不要再直接调 m_link 的普通函数了
//    要触发它做事，一律通过信号或 QMetaObject::invokeMethod
数据帧用值类型跨线程传 — struct Frame { qint64 tsNs; QVector<double> ch; }; 配 Q_DECLARE_METATYPE(Frame) + 启动时 qRegisterMetaType<Frame>()。不要传裸指针：接收方不知道谁负责释放，也无法保证发送方不在同时改它。QVector 是写时复制的，按值传的成本比想象中低；100 Hz 这个量级完全不用担心拷贝开销。忘了注册元类型的症状很隐蔽——槽静默不执行，只有一行控制台 warning。

UI 刷新必须与数据速率解耦

100 Hz 的数据不代表要 100 Hz 重绘界面。人眼看不出 30 Hz 以上的差别，而每帧都触发一次曲线重绘会把主线程吃光。

❌ 每帧直接更新界面
void ChartPanel::onFrame(const Frame& f) {
    m_series->append(f.tsNs, f.ch[0]);
    m_label->setText(fmt(f));
    chart()->update();      // 每 10 ms 一次全量重绘
}
// 数据越快界面越卡；点数无上限，内存持续涨
✅ 环形缓冲 + 定时合并刷新
// 采集侧：只写缓冲，不碰界面
void ChartPanel::onFrame(const Frame& f) { m_ring.push(f); }

// 构造时启动一个 33 ms 定时器
connect(&m_timer, &QTimer::timeout, this, [this]{
    if (m_ring.empty()) return;
    m_series->replace(m_ring.snapshot());  // 一次性换整条曲线
    m_label->setText(fmt(m_ring.back()));
});
m_timer.start(33);         // ≈30 fps，与数据速率无关

建议的目录结构

src/
  main.cpp
  ui/        mainwindow.{h,cpp,ui}  chartpanel.{h,cpp}   // 只做显示与交互
  core/      acquisition_controller.{h,cpp}  frame.h  ring_buffer.h
  device/    device_link.h  tcp_link.{h,cpp}  serial_link.{h,cpp}
  storage/   recorder.{h,cpp}
  CMakeLists.txt
tests/       test_protocol.cpp   // 协议解析可以脱离界面单独测
这套分层的实际收益，在需求变化时才显现：换成串口 → 只加一个 SerialLink 实现 DeviceLink 接口，上面三层不动；加录制格式 → 只改 Recorder；要写自动化测试 → 协议解析和状态机都不依赖 UI，可以直接喂字节流断言输出；要做无界面的采集服务 → 去掉 ui 层，换 QCoreApplication 就能跑。判断分层是否成功有个简单标准：业务层与设备层的代码里不应该出现任何 QWidget 头文件。

其中的每个环节都有更深的坑：TCP 的粘包半包与重连状态机在 网络与 IPC 篇，moveToThread 的线程亲和性与死锁案例在 线程与并发篇。

Widgets 还是 QML

入门期唯一必须做的选型

两套 UI 技术共存在同一个框架里，是 Qt 让新人最困惑的地方。它们不是新旧关系，而是面向不同场景，且都在持续维护。

Qt WidgetsQt Quick / QML
怎么写纯 C++（可配 Designer 拖界面）QML 声明式脚本 + C++ 后端，两种语言
渲染CPU 绘制（QPainter）场景图 + GPU 合成，独立渲染线程
观感贴近系统原生自定义外观，跨平台一致
擅长控件密集的表单、大表格、多窗口 / 多文档、菜单与快捷键、无障碍动画转场、手势触摸、非矩形与自由布局、多分辨率适配
不擅长复杂动效写起来啰嗦密集表格与复杂桌面交互要自己造轮子；C++ 与 QML 边界容易失控
硬件要求低，虚拟机 / 远程桌面都稳依赖 GPU 与驱动
一个真实的工程坑：QML 默认需要可用的 GPU 加速。而工业现场大量存在「集显工控机 + 远程桌面（RDP/VNC）运维」的组合——这种环境下 QML 可能退化到软件渲染（QT_QUICK_BACKEND=software）后严重掉帧，甚至因驱动问题起不来。如果你的软件要靠远程桌面运维，这一条几乎可以直接定下选 Widgets。

三句话判断

  • 做桌面工具 / 工业上位机、界面以表单表格为主、团队是 C++ 背景、要跑在杂七杂八的工控机上 → Widgets。
  • 做触摸屏 / 车机 / 消费级产品 HMI、有设计师参与、要动效和多分辨率、硬件 GPU 有保障 → QML。
  • 两者可以混用：Widgets 主框架里用 QQuickWidget 嵌一块 QML 做仪表盘或动效区，是常见的折中。但混用会同时承担两套心智负担，除非确有需要。
本系列后续四篇讲的都是 Qt Core 层的机制——对象树、信号槽、线程、事件循环、网络。这些内容对 Widgets 和 QML 完全通用，所以你不必先纠结选型再开始学。选型的更细致对比（含性能与团队协作角度）在 工程化篇。

新手十二坑 · 学习顺序

按症状查根因

这十二条覆盖了绝大多数 Qt 入门期的「莫名其妙」。建议扫一遍留个印象，真遇到时能直接对上。

#症状根因正解
1程序退出时崩溃栈上的控件被交给了布局 / 设了 parent，父对象去 delete 栈地址交给对象树的控件一律 new；顶层窗口可以放栈上
2控制台：Cannot move object with a parent给准备 moveToThread 的对象设了 parent工作对象不设 parent，用 deleteLater 管理生命周期
3继承 QThread，但槽还是卡界面QThread 对象本身属于创建它的线程，它的槽默认在原线程执行；只有 run() 里的代码在新线程用「普通 QObject + moveToThread」，不要继承 QThread
4点了按钮界面就假死、变白槽函数里长时间不返回，事件循环停转耗时任务挪线程，或用 QTimer::singleShot(0,…) 切片
5加了 processEvents() 后偶发崩溃事件在调用栈中间被重新分发 → 槽重入、this 已被删不用它；必须用时配 QPointer 守卫 + 禁用输入事件
6工作线程里更新界面，随机崩溃界面对象只允许主线程访问线程里 emit 信号，让主线程的槽去改界面
7跨线程信号「不触发」，程序不崩参数是自定义类型且未注册元类型，事件被静默丢弃Q_DECLARE_METATYPE + qRegisterMetaType；用 qInstallMessageHandler 把 Qt warning 收进日志
8undefined reference to vtable漏写 Q_OBJECT，或加了宏后 moc 没重跑补宏、把头文件列进构建目标、必要时清构建目录
9.cpp 里定义的 QObject 类链接不过AUTOMOC 生成了 xxx.moc 但没人包含该 .cpp 末尾 #include "xxx.moc"
10TCP 收到的数据时多时少、解析错乱把 readyRead 当成「一帧到齐」，忽略了粘包 / 半包累积到缓冲区，按「长度前缀 / 定界符」循环切帧，并校验长度上限
11换 4K 屏或翻译后界面错位、文字截断写死像素坐标与固定宽度一律用布局；宽度靠 sizePolicy 与 minimumSizeHint
12exe 拷到别的机器起不来缺 Qt 运行库与 平台插件（platforms/qwindows.dll）用 windeployqt / linuxdeployqt 打包；把「干净虚拟机启动测试」列入发布清单

建议的学习顺序

第 1 步→装 Qt Creator（自带调试器与 Designer，最省事的起点），照 §5 敲一遍计数器，再用 Designer 拖一个界面感受 uic。目标：能独立建工程、能打断点。
第 2 步→读 Qt 核心机制：对象树、信号槽与 moc、事件循环。这是全系列的地基，也是面试主战场。
第 3 步→读 线程与并发，然后动手把 §5 的计数器改成「后台线程算 1000 万次求和 + 进度条」。目标：moveToThread 装配代码能自己写出来。
第 4 步→读 网络与本机 IPC，实现 §8 那个采集显示小项目（可以先用一个假的数据源模拟 100 Hz）。目标：粘包处理与重连状态机。
第 5 步→读 工程化与陷阱，把项目用 CMake 组织好、打包到一台干净机器上跑起来。目标：能交付，不只是能跑。

面试题集（12 道）

入门层面最常被问到的那些

11.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础Qt 是一个 GUI 库吗？Qt Core 和 Qt Widgets 是什么关系？

    不准确。Qt 是跨平台应用框架，GUI 只是其中一部分。它由三层组成：跨平台基础设施（字符串、容器、文件、线程、网络、国际化）、自建运行时（元对象系统、信号槽、属性）、UI 工具箱（Widgets 与 Quick）。

    QtCore 是地基，提供 QObject、对象树、信号槽、事件循环，不含任何界面类；QtWidgets 建立在 QtCore+QtGui 之上，提供控件与布局。所以写一个没有界面的命令行工具或服务，也完全可以只用 QtCore（配 QCoreApplication）。

    延伸
    三个 Application 类的区别：QCoreApplication（无界面）→ QGuiApplication（用 Qt Gui / QML）→ QApplication（用 Widgets）。选错会在运行时报缺少某些初始化。
  2. 基础main() 里 show() 之后为什么必须 app.exec()？exec() 到底在做什么？

    show() 并不绘制窗口，它只是设置可见标记并投递 Show / Paint 事件到事件队列。exec() 进入事件循环，概念上是 while (!quit) { 取事件; 分发; }——只有循环转起来，那些事件才会被取出执行，窗口才真正画出来。

    不调 exec() 的话，main 直接返回、对象析构、进程退出，用户可能只看到窗口闪一下或什么都看不到。exec() 的返回值是退出码，通常由 QApplication::quit() 或最后一个窗口关闭触发返回。

    追问
    「exec 之前 emit 的跨线程信号会丢吗？」不会。Queued 连接是把调用打包成事件入队，exec() 开始后会照序执行。反之，一个不跑事件循环的线程里，Queued 信号和 deleteLater() 永远不会被处理。
  3. 基础Qt 里的控件是谁负责 delete 的？为什么 new 了不写 delete 不算泄漏？

    parent 负责。每个 QObject 有一个 parent 和一组 children，parent 析构时递归 delete 所有 children。把控件 addWidget 给布局、或构造时传入 parent，所有权就交给了这棵对象树，因此不写 delete 是正确写法。

    两个必须记住的边界：① 交给对象树的对象必须是堆对象——栈对象会导致父类去 delete 栈地址；② 不要和 shared_ptr 混用，那等于两套所有权同时释放。需要「对象死后指针自动置空」时用 QPointer。

  4. 基础为什么在槽函数里做耗时计算会让界面卡死？正确做法是什么？

    因为重绘、鼠标、键盘事件都排在主线程同一个事件队列里，靠事件循环逐个取出分发；槽函数是被这个循环同步调用的。槽不返回，循环就取不到下一个事件，重绘请求得不到处理，界面就是冻住的（系统还可能标记为「无响应」）。

    正确做法：耗时工作交给工作线程（QObject + moveToThread，或 QtConcurrent::run），用信号回传进度与结果；或者把长任务切成小块，用 QTimer::singleShot(0, …) 分片，让每片之间回到事件循环。

    反面教材
    用 processEvents() 强行刷新界面。它在当前调用栈中间重新分发事件，会导致槽重入、容器迭代器失效，甚至用户关窗口后 this 已释放却继续被访问。

11.2 中级（区分熟练度）

  1. 中级moc 是什么？为什么 C++ 需要它，它在构建流程的哪一步？

    moc（Meta-Object Compiler）是一个代码生成器。它在编译之前扫描带 Q_OBJECT 宏的头文件，生成 moc_xxx.cpp，内容包括：类的元信息表（类名、信号槽签名、属性）、信号函数的实现体、以及一个能「按索引调用某个成员函数」的静态分派函数。

    需要它的根本原因是C++ 没有反射：connect 要在运行时把一个信号和一个槽关联起来、跨线程时还要按索引找到函数并传参，标准 C++ 做不到。Qt 选择用代码生成补上这个能力，而不是靠宏黑魔法或运行时解析。

    流程位置
    CMake 打开 AUTOMOC 后：moc / uic / rcc 先跑，产物与你的 .cpp 一起进编译。所以 undefined reference to vtable、自定义信号「未定义」这类链接错误，通常不是代码逻辑问题，而是moc 没跑到这个类。
  2. 中级新项目该选 Qt Widgets 还是 Qt Quick / QML？说出你的判据。

    不是新旧之争，而是场景之分。Widgets：纯 C++、CPU 绘制、贴近原生观感，擅长控件密集的表单、大表格、多窗口、菜单快捷键与无障碍，对硬件要求低。QML：声明式 + GPU 场景图，擅长动效、手势触摸、自由布局与多分辨率适配，设计师可参与。

    • 工业上位机 / 桌面工具 + C++ 团队 + 杂牌工控机 → Widgets。
    • 车机 / 消费级触摸 HMI + 有 GPU 保障 + 有设计资源 → QML。
    • 可混用（QQuickWidget 嵌一块动效区），但要承担两套心智负担。
    现场经验
    如果软件要靠远程桌面运维或跑在集显工控机上，QML 可能退化为软件渲染而严重掉帧——这一条常常直接决定选 Widgets。
  3. 中级程序在别人机器上报「could not load the Qt platform plugin」，怎么排？这反映了什么设计？

    它反映的是 QPA（Qt Platform Abstraction）这层设计：Qt 把 Win32 / XCB / Wayland / Cocoa / eglfs 的差异关进平台插件，同一份上层代码换平台只换插件。代价是插件必须随程序一起部署，且路径要能被找到。

    • 确认目标目录下有 platforms/qwindows.dll（Linux 为 platforms/libqxcb.so）——用 windeployqt / linuxdeployqt 打包，而不是手工拷 dll。
    • 用 QT_DEBUG_PLUGINS=1 启动，日志会打印它尝试了哪些路径、为什么加载失败。
    • Linux 上常见是插件本身缺依赖（ldd libqxcb.so 看缺哪个 so），而不是插件不存在。
    • 发布流程里必须包含干净机器 / 干净容器的启动测试，开发机永远测不出这类问题。
  4. 中级一个 100 Hz 数据采集的界面，如何保证曲线不掉帧？

    核心思路是把「数据速率」和「刷新速率」解耦，三件事：

    • 采集不碰界面：设备层在工作线程收包解析，通过 Queued 信号把值类型的数据帧送到主线程（自定义类型记得注册元类型）。
    • 写入环形缓冲：主线程的槽只把数据放进固定容量的环形缓冲，不触发重绘；这样点数有上限，内存不会无限涨。
    • 定时合并刷新：用一个 30 fps 左右的 QTimer 一次性取快照、整体替换曲线数据。数据再快，重绘频率不变。
    配套
    磁盘记录放独立线程并批量落盘（攒够 N 帧或 200 ms 写一次），避免 IO 抖动传导到采集与界面。大数据量表格同理：用模型视图按需取数，而不是把几万行塞进 QTableWidget。

11.3 高级（体现深度）

  1. 高级跨线程发信号时，参数是怎么传到另一个线程的槽里的？

    跨线程连接（Auto 判定为 Queued）时，emit 并不会直接调用槽，而是：把每个参数深拷贝一份、连同「要调用哪个槽」的索引打包成一个 QMetaCallEvent，postEvent 到接收者所在线程的事件队列；等那个线程的事件循环取出该事件，才执行真正的槽调用。

    拷贝参数需要 Qt 知道该类型如何构造 / 拷贝 / 析构，这靠元类型系统。自定义类型没 Q_DECLARE_METATYPE + qRegisterMetaType 时，Qt 只打一行 warning 然后静默丢弃这次调用——槽不执行、程序不崩，是最难查的一类问题。

    两个推论
    ① AutoConnection 的方向判定发生在 emit 时刻（比较当前线程与接收者线程），不是 connect 时刻，所以 moveToThread 后已有连接会自动改变行为；② 接收者线程若没有事件循环，Queued 信号永远不会执行。
  2. 高级Qt 的事件循环底层用的是什么多路复用机制？这对架构选择意味着什么？

    是 poll(2)，不是 epoll——Qt 自带的 QEventDispatcherUNIX 用 poll，桌面 Linux 默认的 GLib 派发器底层同样是 poll。因此 Qt 的 IO 多路复用复杂度是 O(n) 于 fd 数量：每轮都把整个 fd 数组交给内核，返回后线性扫描。

    这对客户端场景完全够用（fd 少、事件类型杂：GUI + 定时器 + socket 混在一起，还要与窗口系统集成）；但不适合上万连接的服务端，会在 poll 上烧掉大量 CPU。

    架构结论
    如果一个 Qt 应用确实要扛大量连接，常见做法是把网络层独立出来用 epoll / io_uring / Asio 实现，只通过 Queued 信号把结果送回 UI 线程；界面与高并发 IO 各用擅长的机制，而不是勉强让事件循环兼任。
  3. 高级Qt 的 LGPL 许可会怎样影响架构与交付方式？

    LGPLv3 允许闭源商业产品使用 Qt，但要求 动态链接，并让终端用户能够替换 Qt 库（提供必要的链接材料与说明）。这带来几个实际约束：

    • 不能静态链接成单文件。嵌入式固件、想「一个 exe 走天下」的诉求会与之冲突——那条路要买商业许可。
    • 交付物必须包含 Qt 动态库与平台插件，部署体积和打包流程都要按此设计（并写进发布清单）。
    • 对 Qt 源码做了修改（打补丁）时，修改部分需按 LGPL 要求提供。
    • 逐模块确认许可：个别模块在开源渠道下只给 GPL（历史上 Qt Charts 就是典型），一旦链上就会传染到整个产品。
    工程习惯
    把「依赖清单 + 每个依赖的许可」纳入 CI 检查，升级 Qt 大版本时重新核对一次（Qt 6 拆分了部分模块的归属）。合规问题发现得越晚，代价越高。
  4. 高级要显示一张 10 万行的日志表格，怎么做到不卡？

    关键是不要让控件持有数据：

    • 放弃 QTableWidget（每格一个堆对象，10 万行 × 10 列 = 百万对象，构造慢、内存爆）；改用 QTableView + 自己实现的 QAbstractTableModel，数据留在你自己的容器里。
    • 视图只对可见区域调用 data()，滚动到哪取哪；data() 里不要做格式化以外的重活（更不要查数据库）。
    • 数据来自远端或数据库时用 canFetchMore/fetchMore 分页增量加载，而不是一次性拉全。
    • 批量增删务必配对发出 beginInsertRows/endInsertRows；漏发或错发行号会让视图与模型不一致，表现为空白行或崩溃。
    • 刷新要合并：高频追加日志时先入缓冲，定时（如 100 ms）批量插入一次，避免每条都触发一轮布局与重绘。
    再往深一层
    如果列宽是自适应的，视图可能为了算宽度去遍历所有行，此时行数一大立刻卡住——解法是固定列宽或只按可见行采样（setResizeContentsPrecision）。这类「模型视图的隐藏 O(n)」在工程化篇有更完整的清单。
