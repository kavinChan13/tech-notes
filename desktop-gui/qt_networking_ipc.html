01

Qt 的网络模型

异步在哪，边界在哪

Qt 的网络 API 是「事件循环驱动的异步 IO」：socket 的文件描述符被注册进当前线程的事件分发器，可读时事件循环发出 readyRead() 信号，你在槽里取数据。没有独立的 IO 线程——它和你的 UI 事件共用同一个循环。
裸 socket 是自己守着电话：不停问「有人打来吗」（poll），或干脆守在话筒边（阻塞 recv）。Qt 是装了台答录机：来电时响铃通知你。方便，但答录机和门铃、闹钟共用同一个「你」——接一通长电话，门铃就没人应。
维度Qt Network裸 socket + epoll / Asio
底层多路复用poll(2)（Linux 上经 GLib 的 GMainContext）epoll / io_uring / IOCP
复杂度O(n) 于 fd 数量O(1) 就绪通知
适用连接数几十到几百（客户端、小型服务）上万（C10K+）
与 GUI 集成天然，同一循环需要跨线程桥接
写法信号槽，无回调地狱回调 / 协程
TLS内置 QSslSocket自己接 OpenSSL
选型结论：连几台设备用 Qt Network；要扛上万连接用 Asio 或裸 epoll，见 C++ 异步网络框架完全指南、I/O 多路复用。
waitForReadyRead() / waitForConnected() 在 UI 线程里是禁区，理由见上图。它们唯一的合法用途：在没有 GUI 的工作线程里写同步风格的协议交互。

信号时序与必调的几个选项

客户端：信号时序与三条错误分支

选项作用什么时候必须设
LowDelayOption（TCP_NODELAY）关闭 Nagle 算法，小包立即发送几乎总是：控制指令、心跳、请求-响应式协议
KeepAliveOption启用 TCP keepalive 探测长连接。但默认间隔是系统级的 2 小时，太慢，必须配应用层心跳
ReceiveBufferSizeSocketOption

03

分帧：粘包与半包

TCP 是字节流，不是消息流

粘包 / 半包：TCP 只保证「字节按序到达」，不保证消息边界。发送方连发 3 条 10 字节消息，接收方可能一次 readyRead 收到 30 字节（粘包），也可能分 5 次分别收到 7/8/6/4/5 字节（半包）。readyRead 只是说「有数据了」，从不承诺「有一条完整消息了」。
TCP 像传送带上的散装货：放上去的是三个包裹，传送带只保证「按顺序过来」，中间的空隙早就没了。想还原成包裹，必须自己贴标签——每件货前写清「我有多长」（长度前缀）。
❌ 假设一次收到一条完整消息
void onReadyRead() {
    QByteArray data = m_sock->readAll();
    Msg m = parse(data);        // 半包 → 解析失败
    handle(m);                  // 粘包 → 只处理了第一条
}
// 症状：局域网测试一切正常，
// 现场跨交换机 / 大数据量时随机丢消息
✅ 累积缓冲 + 循环解析
void onReadyRead() {
    m_buf += m_sock->readAll();       // 先攒
    for (;;) {
        if (m_buf.size() < 4) break;    // 头都不够
        quint32 len = qFromBigEndian<quint32>(
            reinterpret_cast<const uchar*>(m_buf.constData()));
        if (len > kMaxFrame) {         // 防御：长度字段被污染
            m_sock->abort(); return;
        }
        if (m_buf.size() < 4 + len) break; // body 还没齐
        handle(m_buf.mid(4, len));      // 整帧到手
        m_buf.remove(0, 4 + len);       // 消费掉
    }
}
if (len > kMaxFrame) abort(); 不是可选的。长度前缀直接来自网络，对端发一个 0xFFFFFFFF 你就会去分配 4 GB——轻则 OOM，重则成为 DoS 入口。任何从网络读来的长度字段都要先做上界检查，见 C++ 安全与硬化指南。

HTTP：QNetworkAccessManager

调 REST 接口的标准姿势

// nam 是全应用唯一的那一个实例，不要在这里 new
QNetworkRequest req{QUrl("https://api.example.com/v1/inspections")};
req.setHeader(QNetworkRequest::ContentTypeHeader, "application/json");
req.setAttribute(QNetworkRequest::RedirectPolicyAttribute,
                 QNetworkRequest::NoLessSafeRedirectPolicy);   // 跟随重定向，但不降级到 http
req.setTransferTimeout(10000);                              // Qt 5.15+，必设

QNetworkReply* reply = nam->post(req, QJsonDocument(body).toJson());
connect(reply, &QNetworkReply::finished, this, [reply, this]{
    reply->deleteLater();                                     // ① 第一行
    if (reply->error() != QNetworkReply::NoError) {            // ② 传输层
        emit failed(reply->errorString()); return;
    }
    const int code = reply->attribute(                        // ③ 业务层
        QNetworkRequest::HttpStatusCodeAttribute).toInt();
    if (code < 200 || code >= 300) { emit failed(QString("HTTP %1").arg(code)); return; }
    emit succeeded(QJsonDocument::fromJson(reply->readAll()));
});
坑后果正确做法
每次请求 new 一个 QNAM连接池失效，每次重建 TCP + TLS 握手全应用一个实例
reply 生存期没管好不删 → 稳定泄漏（reply 没有 parent）；用 delete → 在自己信号里删自己，崩溃finished 第一行 deleteLater()
不设超时Qt 5.15 之前没有默认超时，网络黑洞时永久挂起setTransferTimeout()；老版本用 QTimer + abort()
跨线程使用 QNAMreply 与 manager 必须同线程，否则 UB每个线程一个，或统一在一个线程用
协议本身（keep-alive、chunked、HTTP/2 多路复用、QUIC）见 HTTP / HTTPS 协议完全指南；接口怎么设计见 API 设计。

TLS 与证书校验

最容易被「先跑通再说」毁掉的一节

写法实际含义能不能进主干
ignoreSslErrors() 无参放过一切，包括未来 Qt 新增的错误类型❌ 一旦写进去几乎没人再删
ignoreSslErrors(errs) 带参只放过你逐条 if 判断过的那一批⚠️ 可接受，前提是真的逐条判了
自签 CA 进 caCertificates + VerifyPeer校验流程不变，只是多了一个信任根✅ 内网设备的标准解法
setLocalCertificate + setPrivateKey双向认证（mTLS），服务端也校验你✅ 高安全要求场景
部署时确认目标机器上有 OpenSSL 运行库。QSslSocket::supportsSsl() 返回 false 是现场「HTTPS 全挂、HTTP 正常」的典型原因，Windows 上通常是漏拷 libssl-*.dll / libcrypto-*.dll。
握手细节、证书链验证、SNI/ALPN 见 TLS / SSH / 证书；这里只讲 Qt 侧的 API 陷阱。

本机 IPC：进程 / 管道 / 共享内存

Qt 对操作系统 IPC 的封装

Qt 类底层机制消息边界适合传什么主要坑
QProcessfork+exec，管道接 stdio无调外部工具拿结果不读输出会把子进程卡死
QLocalSocket / QLocalServerUnix domain socket / 命名管道无，要自己分帧本机的控制消息§3 的坑一个不少
QSharedMemory共享内存 / 文件映射无（就是一块内存）大块数据（图像帧）无跨进程同步；崩溃后残留
QSystemSemaphorePOSIX/SysV 信号量—跨进程互斥 / 计数同样崩溃残留
TCP over localhost回环 socket无，要自己分帧将来可能跨机器比 UDS 慢，代码完全一致

QProcess 的两条红线

永远不要用字符串拼接构造命令行。start("tool " + userInput) 在 Windows 上会被 shell 语义解析，输入里的 &、|、> 就成了命令注入。用 setProgram() + setArguments(QStringList)，参数以数组交给 OS，不经过 shell——就是 system() vs execv() 那个区别。
不读 stdout/stderr 会把子进程卡死。管道缓冲（Linux 上约 64 KB）写满后子进程的 write 阻塞，而你在等 finished——双方互等。要么持续读，要么重定向到 QProcess::nullDevice()。

本机 IPC 的标准形态：控制面 + 数据面分开

// 数据面：崩溃残留清理 + 跨进程加锁，是 QSharedMemory 唯一容易写错的两处
QSharedMemory shm("vision_frame_buffer");
if (!shm.create(kSlotBytes * kSlots) && shm.error() == QSharedMemory::AlreadyExists) {
    shm.attach(); shm.detach();          // 让内核引用计数归零（上次崩溃留下的段）
    shm.create(kSlotBytes * kSlots);
}
QSystemSemaphore sem("vision_frame_sem", 1, QSystemSemaphore::Create);
sem.acquire();                            // ★ 不是 shm.lock()：那个只锁本进程
memcpy(static_cast<uchar*>(shm.data()) + slot * kSlotBytes, frame.bits(), kSlotBytes);
sem.release();
数据量其实不大（几 KB 的结果 JSON）时，共享内存的复杂度完全不值得，直接走 QLocalSocket。操作系统层面的 IPC 全景见 Linux 多进程与 IPC 完全指南。

实战：设备长连接状态机

把前面的东西拼成一个能上产线的东西

设备重启、交换机抖动、网线被叉车碾过——「连上就一直连着」的假设必然失败，连接本身必须建模成状态机。

动手感受：断线重连与指数退避

观察退避间隔如何翻倍到上限，以及连接恢复后计数如何被重置。

Disconnected Connecting Connected Backoff 
// 整个状态机里真正值得抄的就这四处；其余是样板代码
void DeviceLink::doConnect() {
    setState(State::Connecting);
    m_sock->abort();                                   // 清掉上次的残留状态
    m_sock->connectToHost(m_host, m_port);
    m_connectTimer.start(kConnectTimeoutMs);           // ④ 系统栈的超时可能几十秒
}

void DeviceLink::onConnected() {
    m_connectTimer.stop();
    m_sock->setSocketOption(QAbstractSocket::LowDelayOption, 1);
    m_backoffMs = kBaseBackoff;                        // ① 成功后重置退避
    m_missedBeat = 0;
    m_hbTimer.start(kHeartbeatMs);
}

void DeviceLink::onDisconnected() {
    m_hbTimer.stop();
    if (m_closing) { setState(State::Disconnected); return; }  // ③ 主动停不重连
    setState(State::Backoff);
    const int jitter = QRandomGenerator::global()->bounded(m_backoffMs / 4 + 1);
    m_retryTimer.start(m_backoffMs + jitter);          // ② 抖动，避免惊群
    m_backoffMs = qMin(m_backoffMs * 2, kMaxBackoff);
}
这四处标号正是面试时该主动讲的四点，展开见 §9.3 第 10 题。
心跳判定用「连续 N 次未应答」，不是「一次超时就断」——偶发丢包很正常，单次就重连会让连接反复抖动。典型参数：2 秒一次、连续 3 次判死。另外 QTimer 精度依赖事件循环，UI 卡顿时会延迟，所以判定要基于时间戳差值而非回调次数。

面试题集（12 道）

按难度分层，先自测再对照

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础什么是 TCP 粘包？readyRead 触发时能假设收到了一条完整消息吗？

    不能。TCP 是字节流协议，只保证字节按序、不丢不重，不保证消息边界。发送方三次 write 的数据，接收方可能一次全收到（粘包），也可能分多次收到半条（半包）。

    readyRead 的语义只是「缓冲区里有新数据了」。正确处理方式是累积缓冲 + 循环解析：把新数据追加到成员缓冲区，然后在循环里反复尝试「够不够一个完整帧」，够就取走一帧继续，不够就退出等下次。

    为什么本地测试发现不了
    本地回环、小数据量时，一次 write 通常就对应一次 readyRead，错误代码「看起来能跑」。一到现场跨交换机、数据量上来，问题立刻暴露。
  2. 基础为什么不能在 UI 线程调用 waitForReadyRead()？

    因为它内部会跑一个局部的 QEventLoop直到条件满足或超时。两个后果：

    • 它会阻塞你的函数——期间界面不响应，网络慢就是卡死几秒。
    • 更隐蔽的是它继续分发其它事件，带来和 processEvents() 相同的重入与 use-after-free 风险：用户可能在这期间关闭了窗口，函数返回后你继续访问成员变量。

    UI 线程里应该用信号槽的异步写法。waitForXxx 的合法用途是在没有 GUI 的工作线程里写同步风格的协议交互。

  3. 基础用 QNetworkAccessManager 发请求，有哪几件事必须做？
    • 全应用共用一个 QNAM 实例——它内部维护连接池，每次 new 一个就等于每次重建 TCP + TLS 握手。
    • 在 finished 槽里 reply->deleteLater()——reply 没有 parent，不删就泄漏；而且必须用 deleteLater 不能用 delete（正在自己的信号里删自己会崩）。
    • 设超时——Qt 5.15 之前 QNAM 没有默认超时，遇到网络黑洞会永久挂起。用 setTransferTimeout()，老版本用 QTimer + abort()。
    • 既判 error() 也判 HTTP 状态码——只看 error 会漏掉需要区分处理的 4xx/5xx 语义。
    • QNAM 和它创建的 reply 必须在同一线程。
  4. 基础ignoreSslErrors() 有什么危害？内网自签证书应该怎么处理？

    无参的 ignoreSslErrors() 会忽略一切证书错误，包括「证书不是可信 CA 签发的」「域名不匹配」「证书已过期」。结果是：加密还在，但身份认证没了——任何中间人出示一张自签证书就能冒充服务器，客户端照单全收。这比明文 HTTP 更危险，因为它给人一种「已经加密了」的虚假安全感。

    正确做法：把设备/内网服务的自签 CA 证书打进程序资源，加入 QSslConfiguration 的信任列表，并保持 VerifyPeer：

    cfg.setCaCertificates(cfg.caCertificates()
    + QSslCertificate::fromPath(":/certs/company-ca.pem"));
cfg.setPeerVerifyMode(QSslSocket::VerifyPeer);

    实在要忽略，也只能用带参版本忽略你逐条检查过的那一批错误。

9.2 中级（区分熟练度）

  1. 中级设计一个二进制协议的分帧方案，说明要防御哪些异常输入。

    方案：4 字节大端长度前缀 + 变长 body。可选再加 2 字节魔数用于重同步、2 字节版本号、末尾 4 字节 CRC。

    接收侧算法：新数据追加到缓冲 → 循环｛缓冲不足 4 字节则退出；读长度；长度超上限则断链；缓冲不足 4+len 则退出；取出整帧、消费掉、继续｝。

    必须防御的输入：

    超大长度字段
    攻击者发 0xFFFFFFFF，你若直接按它分配就是 4 GB 内存申请，OOM 或 DoS。必须有 kMaxFrame 上界检查。
    长度为 0
    若代码里有「消费 4+len 字节」的逻辑而 len 可以为 0，配合某些写法会导致死循环空转。
    缓冲无限增长
    对端只发头不发 body，你的累积缓冲会一直涨。要给缓冲总量也设上限。
    字节序与对齐
    不要直接 reinterpret_cast 成结构体读——对齐和字节序都不可移植。用 qFromBigEndian 逐字段读。
  2. 中级使用 QDataStream 做网络序列化，有什么必须注意的兼容性问题？

    必须显式调用 setVersion()。QDataStream 的默认版本随 Qt 版本变化，而不同版本对 QString、容器、QVariant 的编码格式并不相同。上位机用 Qt 5.15、设备固件用 Qt 5.9，不钉版本就是两边各说各话——表现往往是「大部分字段正确，某个字符串偶尔乱码」，极难排查。

    其它注意点：默认字节序是大端（网络序），与主机序不同要心里有数；浮点精度默认是双精度，可用 setFloatingPointPrecision 控制；读完后要检查 in.status() 是否为 Ok，损坏数据不会抛异常只会设状态位。

    选型边界
    QDataStream 是 Qt 私有格式，Python/C# 侧无法解析。跨语言、跨团队、需要长期演进的协议应该用 Protobuf 或明确定义的字节布局；它的甜蜜区是「两端都是自己写的 Qt 程序」。
  3. 中级为什么处理 newConnection 时要用 while 循环取连接？

    因为一次 newConnection 信号可能对应多个待处理连接。Qt 在一轮事件分发里如果 accept 到了若干连接，不会为每个都单独发一次信号（信号可能被合并）。只调用一次 nextPendingConnection()，剩下的连接就留在队列里，直到下一个连接到来才被处理。

    后果是高负载时连接堆积、客户端超时——低负载测试完全正常，压测才暴露。同样的道理适用于 QUdpSocket：要用 while (hasPendingDatagrams()) 把 datagram 取干净。

  4. 中级用 QProcess 调外部程序时，为什么会出现「子进程单独跑很快，被程序调用就卡住」？

    因为没有读 stdout/stderr。子进程的输出写进管道，管道缓冲区（Linux 上通常 64 KB）写满后子进程的 write 会阻塞；而父进程在等 finished 信号——双方互等，永久卡死。

    解决：连上 readyReadStandardOutput / readyReadStandardError 持续读走；或者明确不需要输出时把通道重定向到 QProcess::nullDevice()。

    另一个常见错误
    用字符串拼接构造命令行（start("tool " + userInput)）会引入命令注入。应该用 setProgram() + setArguments(QStringList)，参数以数组传给 OS，不经过 shell。

9.3 高级（体现深度）

  1. 高级Qt 的网络 IO 适合做高并发服务端吗？如果一个 Qt 应用必须扛上万连接，架构怎么设计？

    不适合。Qt 的事件分发底层是 poll(2)（Linux 桌面上走 GLib 的 GMainContext，同样基于 poll），复杂度是 O(n) 于 fd 数量：每轮都要把整个 fd 数组交给内核、返回后线性扫描。几百个连接没问题，上万就会在 poll 上耗掉大量 CPU。而且网络事件与 GUI 事件共用一个循环，任何一个慢槽都会拖累全部。

    架构方案：把网络层从 Qt 事件循环里剥出来——独立线程跑 Asio / 裸 epoll / io_uring，用自己的线程池处理业务；只在需要更新界面时，通过 QMetaObject::invokeMethod 或 Queued 信号把结果送回 UI 线程。这样 GUI 与网络各自用最适合的模型，边界清晰。

    边界判断
    连接数在几百以内、且每个连接流量不大时，Qt 自带的够用且省事；一旦要考虑 C10K，就不该在 Qt 的循环里解决。详见 异步网络框架指南。
  2. 高级设计一个能抗住现场断网的设备长连接，说明状态机和关键参数。

    五个状态：Disconnected / Connecting / Connected / Backoff / Closing。Closing 必须与 Disconnected 分开——否则「用户点退出」会被当成意外断开而触发重连，程序关不掉。

    四个关键设计：

    应用层心跳
    TCP keepalive 默认 2 小时，且探测不到「进程假死但 TCP 栈还活着」。必须自己发心跳，典型 2 秒一次，连续 3 次无应答才判定断线（单次超时就断会导致连接反复抖动）。
    指数退避 + 抖动
    1s → 2s → 4s …封顶 30s，并加随机抖动。抖动很重要：多台上位机同时重连会把刚恢复的设备再次打挂（惊群）。
    成功后重置退避
    忘了重置的话，一次长时间断网之后即使网络恢复，也要等满 30 秒才连上。
    自己的连接超时
    系统 TCP 连接超时可能数十秒（SYN 重传），必须自己起一个 QTimer，超时就 abort() 转入退避。
    时间判定
    心跳超时判定要基于时间戳差值而非回调次数——QTimer 精度依赖事件循环，UI 卡顿时定时器会延迟，按次数算会误判。
  3. 高级本机两个进程要传大图像帧，你会怎么选 IPC 方案？

    数据面用共享内存，控制面用消息通道——这是大数据量 IPC 的通用模式：

    • 共享内存（QSharedMemory 或直接 shm_open + mmap）放像素数据，避免几十 MB 的拷贝。做成 N 个槽位的环形缓冲，生产者写槽位、消费者读槽位。
    • QLocalSocket（Unix domain socket / 命名管道）只传「第 k 号槽位已就绪、尺寸格式如下」这样的小消息。它天然有序、有连接语义、对端崩溃时能感知。
    • 同步用 QSystemSemaphore 或共享内存里的 pthread 进程间互斥量。QSharedMemory::lock() 只是本进程内的互斥，不能跨进程用。
    崩溃残留
    Unix 上共享内存段和信号量是内核持久的：进程崩溃后不会自动释放。要有清理逻辑（attach() 后 detach() 让引用计数归零），或者启动时用固定 key 主动清理一次。
    什么时候不该用共享内存
    如果数据量其实不大（几 KB 的结果 JSON），共享内存的复杂度完全不值得——直接走 QLocalSocket 就行。共享内存的适用前提是「拷贝开销确实成为瓶颈」，先测量再上。IPC 机制的完整对比见 Linux 多进程与 IPC 指南。
  4. 高级Qt 客户端出现「偶尔收不到设备数据」，你会怎么排查？

    按从外到内的顺序切割，每一步都要有证据而不是猜测：

    1. 先确认包到没到主机：tcpdump -i any port 5000 -w cap.pcap，用 Wireshark 看。如果抓不到，问题在设备侧或网络（交换机、VLAN、多网卡路由）——不要在应用代码里找。
    2. 包到了但应用没收到：查 socket 接收缓冲是否溢出（ss -tmi 看 Recv-Q）。缓冲堆积说明应用读得太慢——多半是 UI 线程被某个耗时槽占住了。
    3. 应用收到了但没处理：这就是分帧 bug。在 onReadyRead 里打印 bytesAvailable() 和累积缓冲长度，看是不是缓冲在持续增长（说明解析条件永远不满足，比如长度字段字节序搞反了）。
    4. 解析对了但槽没跑：跨线程时检查是否漏了 qRegisterMetaType——自定义类型未注册时 Qt 只打一行 warning 然后静默丢弃。把 Qt 的 warning 接进日志系统，或临时设 QT_FATAL_WARNINGS=1 让它直接 abort 到调试器。
    埋点先行
    这类「偶发」问题事后排查成本极高。上线前就应该有三个指标：每秒收帧数、解析失败计数、累积缓冲峰值。有了这三个数，问题出现时看一眼监控就能定位到上面四层中的哪一层。参见 C++ 可观测性完全指南。
