Qt 网络与本机 IPC 完全指南

Qt 的网络 API 把 socket 包成了信号槽，写起来比裸 recv 舒服得多——代价是很多人从此不知道底下发生了什么，于是照样写出粘包 bug、照样在 UI 线程里 waitForReadyRead 把界面冻住。本篇从「Qt 的异步模型到底异步在哪」讲起，覆盖 TCP 分帧、HTTP 客户端、TLS 校验、本机 IPC，最后落到一个能抗住现场断网的设备长连接状态机。

核心难度 ★★★★☆ 工程实用度 极高 阅读时长 ~30 min 前置 TCP/IP · Qt 事件循环
QTcpSocket · 分帧 QNetworkAccessManager QSslSocket · 证书 QProcess · 共享内存

01

Qt 的网络模型

异步在哪，边界在哪

Qt 的网络 API 是「事件循环驱动的异步 IO」：socket 的文件描述符被注册进当前线程的事件分发器，可读时事件循环发出 readyRead() 信号，你在槽里取数据。没有独立的 IO 线程——它和你的 UI 事件共用同一个循环。
裸 socket 编程像自己守着电话：得不停地问「有人打来吗」（poll/epoll），或者干脆守在话筒边（阻塞 recv）。Qt 则是装了一台答录机：来电话时它响铃通知你（readyRead 信号），你去接就行。方便，但答录机和门铃、闹钟共用同一个「你」——你在接一通长电话时，门铃就没人应了。
维度Qt Network裸 socket + epoll / Asio
底层多路复用poll(2)（Linux 上经 GLib 的 GMainContext）epoll / io_uring / IOCP
复杂度O(n) 于 fd 数量O(1) 就绪通知
适用连接数几十到几百（客户端、小型服务）上万（C10K+）
与 GUI 集成天然，同一循环需要跨线程桥接
写法信号槽，无回调地狱回调 / 协程
TLS内置 QSslSocket自己接 OpenSSL
选型结论：Qt 客户端连几台设备、几个服务——用 Qt Network，省心。要做能扛上万连接的服务端——用 Asio 或裸 epoll，见 C++ 异步网络框架完全指南。中间形态（Qt 界面 + 高并发网络）的标准做法是网络层独立线程用 Asio 跑，只通过 Queued 信号把结果送回 UI 线程。
waitForReadyRead() / waitForConnected() 这类同步 API 在 UI 线程里是禁区。它们的实现是「跑一个局部的 QEventLoop 直到条件满足或超时」——所以它不仅阻塞你的函数，还会在阻塞期间继续分发其它事件，带来和 processEvents() 一模一样的重入与 UAF 风险。它们的合法用途只有一个：在没有 GUI 的工作线程里写同步风格的协议交互。
02

QTcpSocket / QTcpServer

最小可用骨架 + 必调的几个选项

客户端

class DeviceLink : public QObject {
    Q_OBJECT
public:
    explicit DeviceLink(QObject* p = nullptr) : QObject(p), m_sock(new QTcpSocket(this)) {
        connect(m_sock, &QTcpSocket::connected,    this, &DeviceLink::onConnected);
        connect(m_sock, &QTcpSocket::readyRead,    this, &DeviceLink::onReadyRead);
        connect(m_sock, &QTcpSocket::disconnected, this, &DeviceLink::onDisconnected);
        connect(m_sock, &QAbstractSocket::errorOccurred, this, &DeviceLink::onError);
    }
    void open(const QString& host, quint16 port) {
        m_sock->connectToHost(host, port);   // 立即返回，异步
    }
private slots:
    void onConnected() {
        // 工业控制场景几乎一定要关 Nagle：小指令包不能被攒着
        m_sock->setSocketOption(QAbstractSocket::LowDelayOption, 1);   // TCP_NODELAY
        m_sock->setSocketOption(QAbstractSocket::KeepAliveOption, 1);
        emit ready();
    }
    void onReadyRead();     // 见 §3 分帧
    void onDisconnected() { emit lost(); }
    void onError(QAbstractSocket::SocketError e) {
        qWarning() << "socket error" << e << m_sock->errorString();
    }
private:
    QTcpSocket* m_sock;
    QByteArray  m_buf;      // 累积缓冲，见 §3
};
选项作用什么时候必须设
LowDelayOption（TCP_NODELAY）关闭 Nagle 算法，小包立即发送几乎总是：控制指令、心跳、请求-响应式协议
KeepAliveOption启用 TCP keepalive 探测长连接。但默认间隔是系统级的 2 小时，太慢，必须配应用层心跳
ReceiveBufferSizeSocketOption接收缓冲大小高吞吐（图像流）场景调大，避免内核丢包
setReadBufferSize()Qt 层的读缓冲上限，0 = 无限做背压：设成有限值后，读慢了会让 TCP 窗口收缩，反压到对端
TCP keepalive 不是应用层心跳的替代品。Linux 默认 tcp_keepalive_time 是 7200 秒——设备断电两小时后你才知道。而且 keepalive 只能探测「TCP 连接是否还在」，探测不到「对端进程假死但 TCP 栈还活着」。工业现场必须有应用层心跳，间隔通常 1–5 秒，连续 N 次无响应就判定断线。

服务端

class Server : public QTcpServer {
    Q_OBJECT
protected:
    // 方式一：重写 incomingConnection，拿到裸 fd 自行分发到工作线程
    void incomingConnection(qintptr fd) override {
        auto* h = new ConnHandler(fd);   // 无 parent
        h->moveToThread(pickWorkerThread());
        QMetaObject::invokeMethod(h, &ConnHandler::setup, Qt::QueuedConnection);
        // ⚠️ QTcpSocket 必须在它所属线程里 setSocketDescriptor()
    }
};

// 方式二：单线程够用时，直接用信号
connect(server, &QTcpServer::newConnection, this, [this]{
    while (QTcpSocket* s = server->nextPendingConnection()) {   // 循环取干净
        connect(s, &QTcpSocket::disconnected, s, &QObject::deleteLater);
        m_clients.append(s);
    }
});
newConnection 信号可能在一次事件循环里对应多个待处理连接（Qt 会合并），所以取连接时要用 while 循环调 nextPendingConnection() 直到返回 nullptr。只取一次会导致高负载时连接堆积、客户端超时——这是 Qt 服务端最经典的一个漏写。
03

分帧：粘包与半包

TCP 是字节流，不是消息流

粘包 / 半包：TCP 只保证「字节按序到达」，不保证消息边界。发送方连发 3 条 10 字节消息，接收方可能一次 readyRead 收到 30 字节（粘包），也可能分 5 次分别收到 7/8/6/4/5 字节（半包）。readyRead 只是说「有数据了」，从不承诺「有一条完整消息了」。
TCP 像传送带上的散装货：你放上去的是三个包裹，但传送带只保证「东西按顺序过来」，中间的空隙早就没了。想还原成包裹，必须自己在货物上贴标签——要么每件货前面写清「我有多长」（长度前缀），要么在货之间放一张明显的分隔卡（分隔符）。
❌ 假设一次收到一条完整消息
void onReadyRead() {
    QByteArray data = m_sock->readAll();
    Msg m = parse(data);        // 半包 → 解析失败
    handle(m);                  // 粘包 → 只处理了第一条
}
// 症状：局域网测试一切正常，
// 现场跨交换机 / 大数据量时随机丢消息
✅ 累积缓冲 + 循环解析
void onReadyRead() {
    m_buf += m_sock->readAll();       // 先攒
    for (;;) {
        if (m_buf.size() < 4) break;    // 头都不够
        quint32 len = qFromBigEndian<quint32>(
            reinterpret_cast<const uchar*>(m_buf.constData()));
        if (len > kMaxFrame) {         // 防御：长度字段被污染
            m_sock->abort(); return;
        }
        if (m_buf.size() < 4 + len) break; // body 还没齐
        handle(m_buf.mid(4, len));      // 整帧到手
        m_buf.remove(0, 4 + len);       // 消费掉
    }
}
if (len > kMaxFrame) abort(); 这一行不是可选的。长度前缀直接来自网络，攻击者（或者一个 bug 满满的设备固件）发一个 0xFFFFFFFF，你的程序就会尝试分配 4 GB 缓冲——轻则 OOM 崩溃，重则成为拒绝服务的入口。任何从网络读来的长度字段都必须先做上界检查，这是协议解析代码的第一条安全红线，详见 C++ 安全与硬化指南。

用 QDataStream 做序列化

// —— 发送 ——
QByteArray payload;
{
    QDataStream out(&payload, QIODevice::WriteOnly);
    out.setVersion(QDataStream::Qt_5_15);   // ⚠️ 必写！见下方警告
    out << quint16(cmdId) << deviceName << threshold;
}
QByteArray frame;
{
    QDataStream hdr(&frame, QIODevice::WriteOnly);
    hdr.setVersion(QDataStream::Qt_5_15);
    hdr << quint32(payload.size());         // 默认大端 = 网络序
}
m_sock->write(frame + payload);

// —— 接收（拿到整帧之后）——
QDataStream in(body);
in.setVersion(QDataStream::Qt_5_15);
quint16 cmd; QString name; double th;
in >> cmd >> name >> th;
if (in.status() != QDataStream::Ok) { /* 数据损坏，丢弃并重同步 */ }
忘了 setVersion() 是 Qt 网络协议里最隐蔽的兼容性炸弹。QDataStream 的默认版本跟着 Qt 版本走，而不同版本对 QString、容器、QVariant 的编码格式并不相同。上位机用 Qt 5.15 编译、设备端固件用 Qt 5.9——不设版本就是两边各说各话，表现为「大部分字段对，某个字符串偶尔乱码」。协议两端必须显式钉死同一个版本号。
跨语言、跨团队的协议不要用 QDataStream——它是 Qt 私有格式，Python/C# 侧无法直接解析。那种场景应该用 Protobuf、FlatBuffers 或明确定义的二进制布局，取舍见 二进制协议设计。QDataStream 的甜蜜区是「两端都是自己写的 Qt 程序」。

UDP 与设备发现

工业现场的「找设备」环节

// 广播发现：上位机喊一嗓子，设备各自应答
auto* udp = new QUdpSocket(this);
udp->bind(QHostAddress::AnyIPv4, 0, QUdpSocket::ShareAddress);
connect(udp, &QUdpSocket::readyRead, this, [udp, this]{
    while (udp->hasPendingDatagrams()) {         // 同样要 while
        QNetworkDatagram dg = udp->receiveDatagram();
        onDeviceReply(dg.senderAddress(), dg.data());
    }
});
udp->writeDatagram("DISCOVER", QHostAddress::Broadcast, 9999);

// 组播（多网段、更规范）
udp->bind(QHostAddress::AnyIPv4, 9999, QUdpSocket::ShareAddress);
udp->joinMulticastGroup(QHostAddress("239.255.0.1"));
  • UDP 一个 datagram 对应一次 receiveDatagram()，没有粘包问题——但有丢包和乱序。发现协议要能容忍：客户端重发 3 次、设备端对重复请求幂等。
  • 多网卡机器（工业上位机常见：一张网卡连相机、一张连 PLC、一张连办公网）广播会从「默认路由」那张网卡出去，不一定是你想要的。要用 QNetworkInterface::allInterfaces() 遍历，对每张网卡分别 bind + 发送。这是现场「设备明明在线却发现不了」的头号原因。
  • 组播要显式指定出接口：udp->setMulticastInterface(iface)。

HTTP：QNetworkAccessManager

调 REST 接口的标准姿势

// QNAM 是重量级对象：整个应用共用一个实例（它内部做连接池与复用）
QNetworkAccessManager* nam = qApp->property("nam").value<QNetworkAccessManager*>();

QNetworkRequest req{QUrl("https://api.example.com/v1/inspections")};
req.setHeader(QNetworkRequest::ContentTypeHeader, "application/json");
req.setRawHeader("Authorization", "Bearer " + token);
req.setAttribute(QNetworkRequest::RedirectPolicyAttribute,
                 QNetworkRequest::NoLessSafeRedirectPolicy);   // 允许重定向但不降级到 http
req.setTransferTimeout(10000);                              // Qt 5.15+：必设

QNetworkReply* reply = nam->post(req, QJsonDocument(body).toJson());

connect(reply, &QNetworkReply::finished, this, [reply, this]{
    reply->deleteLater();                     // ⚠️ 必须，而且用 deleteLater 不是 delete
    if (reply->error() != QNetworkReply::NoError) {
        emit failed(reply->errorString());
        return;
    }
    const int code = reply->attribute(
        QNetworkRequest::HttpStatusCodeAttribute).toInt();
    if (code < 200 || code >= 300) {         // 4xx/5xx 也算 error，但要看具体码
        emit failed(QString("HTTP %1").arg(code));
        return;
    }
    emit succeeded(QJsonDocument::fromJson(reply->readAll()));
});
坑后果正确做法
每次请求 new 一个 QNAM连接池失效，每次重建 TCP + TLS 握手，慢且耗资源全应用一个实例
忘记 reply->deleteLater()内存持续泄漏（reply 没有 parent）finished 槽第一行就写
在 finished 槽里 delete reply正在自己的信号里删自己 → 崩溃用 deleteLater()
不设超时Qt 5.15 之前没有默认超时，网络黑洞时请求永久挂起setTransferTimeout()，老版本用 QTimer + abort()
跨线程使用 QNAMreply 与 manager 必须同线程，否则未定义行为每个线程一个 QNAM，或统一在一个线程用
只判 error() 不看状态码把 404 当成功处理同时检查 HttpStatusCodeAttribute
HTTP 协议本身（1.1 的 keep-alive 与 chunked、2 的多路复用与 HPACK、3 的 QUIC）不在本篇展开，见 HTTP / HTTPS 协议完全指南。REST 接口该怎么设计（资源建模、幂等、分页、版本演进）见 API 设计。

TLS 与证书校验

最容易被「先跑通再说」毁掉的一节

❌ 忽略所有 SSL 错误
connect(sock, &QSslSocket::sslErrors,
        sock, [sock](const QList<QSslError>&){
    sock->ignoreSslErrors();     // "先跑通"
});
// 后果：加密还在，但【身份认证没了】。
// 任何中间人都能出示自签证书冒充服务器，
// 你的客户端照单全收 —— 等于裸奔加了层雾。
// 这行代码一旦进主干，几乎不会有人再删掉。
✅ 把自己的 CA 加进信任链
QSslConfiguration cfg = QSslConfiguration::defaultConfiguration();
QList<QSslCertificate> ca = QSslCertificate::fromPath(
        ":/certs/company-ca.pem");   // 打进资源
cfg.setCaCertificates(cfg.caCertificates() + ca);
cfg.setPeerVerifyMode(QSslSocket::VerifyPeer);
cfg.setProtocol(QSsl::TlsV1_2OrLater);
sock->setSslConfiguration(cfg);
sock->connectToHostEncrypted(host, port);

// 只在确实无法避免时，精确忽略【单一一类】错误：
connect(sock, &QSslSocket::sslErrors, sock,
        [sock](const QList<QSslError>& errs){
    for (const auto& e : errs)
        if (e.error() != QSslError::HostNameMismatch) return;
    sock->ignoreSslErrors(errs);   // 传参版本，只忽略这一批
});
  • 无参的 ignoreSslErrors() 忽略一切，包括未来出现的新错误；带参版本只忽略你检查过的那一批。两者的安全含义天差地别。
  • 部署时要确认目标机器上有 OpenSSL 运行库。QSslSocket::supportsSsl() 返回 false 是现场「HTTPS 全挂、HTTP 正常」的典型原因；Windows 上通常是漏拷 libssl-*.dll / libcrypto-*.dll。
  • 内网设备常用自签证书。正确做法不是关校验，而是把设备的自签 CA 打进程序资源并加入信任列表，同时校验 CN/SAN。
  • 需要双向认证（mTLS）时用 cfg.setLocalCertificate() + setPrivateKey()。
TLS 握手细节、证书链验证、SNI/ALPN 的完整讲解见 TLS / SSH / 证书。这里只强调 Qt 侧的 API 陷阱。

本机 IPC：进程 / 管道 / 共享内存

Qt 对操作系统 IPC 的封装

Qt 类底层机制适合传什么注意
QProcessfork+exec / CreateProcess，管道接 stdio调用外部工具，收其输出要处理退出码、stderr、超时、僵尸
QLocalSocket / QLocalServerUnix domain socket / Windows 命名管道本机进程间的消息通信同样要自己分帧（是流式的）
QSharedMemoryPOSIX/SysV 共享内存 / 文件映射大块数据（图像帧）无内建同步，必须配信号量；崩溃后可能残留
QSystemSemaphorePOSIX/SysV 信号量跨进程互斥 / 计数同样有崩溃残留问题
TCP over localhost回环 socket跨机器可迁移的方案比 UDS 慢，但代码与远程完全一致

QProcess：调外部工具的完整写法

auto* proc = new QProcess(this);
proc->setProgram("/opt/vision/calibrate");
proc->setArguments({"--config", cfgPath});
proc->setProcessChannelMode(QProcess::SeparateChannels);  // stdout / stderr 分开

connect(proc, &QProcess::readyReadStandardOutput, this, [proc]{
    qInfo().noquote() << proc->readAllStandardOutput();
});
connect(proc, &QProcess::readyReadStandardError, this, [proc]{
    qWarning().noquote() << proc->readAllStandardError();
});
connect(proc, qOverload<int, QProcess::ExitStatus>(&QProcess::finished),
        this, [proc, this](int code, QProcess::ExitStatus st){
    proc->deleteLater();
    if (st == QProcess::CrashExit) { emit failed("子进程崩溃"); return; }
    if (code != 0)                  { emit failed(QString("exit %1").arg(code)); return; }
    emit succeeded();
});
proc->start();
永远不要用字符串拼接来构造命令行。QProcess::start("tool " + userInput) 在 Windows 上会被 shell 语义解析，用户输入里的 &、|、> 就成了命令注入。用 setProgram() + setArguments(QStringList)，参数以数组形式传给操作系统，不经过 shell。这与 C 里 system() vs execv() 的区别是同一回事。
不读 stdout/stderr 会把子进程卡死。管道缓冲区（Linux 上通常 64 KB）写满后，子进程的 write 会阻塞，而你在等它 finished——双方互等。所以要么持续读，要么把通道重定向到 QProcess::nullDevice()。这是「子进程单独跑很快、被程序调用就卡住」的经典原因。

QSharedMemory 的两个真实陷阱

// 用途：把大图像帧零拷贝地交给另一个进程
QSharedMemory shm("vision_frame_buffer");
if (!shm.create(width * height * 3)) {
    if (shm.error() == QSharedMemory::AlreadyExists) {
        // 陷阱 ①：Linux/Unix 上，上一次进程【崩溃】时共享内存段不会释放。
        // 标准清理手法：attach 一下再 detach，让内核的引用计数归零。
        shm.attach();
        shm.detach();
        shm.create(width * height * 3);
    }
}

// 陷阱 ②：QSharedMemory 自带的 lock() 只是【本进程内的】互斥，
// 跨进程同步必须配 QSystemSemaphore。
QSystemSemaphore sem("vision_frame_sem", 1, QSystemSemaphore::Create);
sem.acquire();
memcpy(shm.data(), frame.bits(), frame.sizeInBytes());
sem.release();
「只允许运行一个实例」不要用 QSharedMemory 实现。常见写法是「create 成功 = 首个实例」，但程序崩溃后共享内存段残留，下次启动就永远认为「已经有实例在跑」，用户只能重启机器。更可靠的是 QLocalServer：尝试 listen(name)，成功即首个实例；失败说明已有实例，就通过 QLocalSocket 连过去让它把窗口置顶。进程崩溃时操作系统会自动回收 socket，没有残留问题。
操作系统层面的 IPC 全景——fork/exec 的完整语义、管道 vs 消息队列 vs 信号量的取舍、Unix domain socket 传文件描述符、信号处理的 async-signal-safe 约束——见 Linux 多进程与 IPC 完全指南。

实战：设备长连接状态机

把前面的东西拼成一个能上产线的东西

工业现场的网络环境远比办公室恶劣：设备重启、交换机抖动、网线被叉车碾过。「连上就一直连着」的假设必然失败，必须把连接本身建模成一个状态机。

动手感受：断线重连与指数退避

模拟现场断网。观察退避间隔如何从 1s 翻倍到上限，以及连接恢复后计数如何被重置。

Disconnected Connecting Connected Backoff 
class DeviceLink : public QObject {
    Q_OBJECT
public:
    enum class State { Disconnected, Connecting, Connected, Backoff, Closing };

    void open() { m_closing = false; m_backoffMs = kBaseBackoff; doConnect(); }
    void close() {
        m_closing = true;            // 关键：区分主动停与意外断
        m_retryTimer.stop();
        m_hbTimer.stop();
        m_sock->abort();
        setState(State::Closing);
    }

private:
    void doConnect() {
        setState(State::Connecting);
        m_sock->abort();                              // 清掉上次的残留状态
        m_sock->connectToHost(m_host, m_port);
        // Qt 自身的连接超时依赖系统栈（可能几十秒），自己加一个
        m_connectTimer.start(kConnectTimeoutMs);
    }

    void onConnected() {
        m_connectTimer.stop();
        m_sock->setSocketOption(QAbstractSocket::LowDelayOption, 1);
        m_backoffMs  = kBaseBackoff;                  // ★ 成功后重置退避
        m_missedBeat = 0;
        m_hbTimer.start(kHeartbeatMs);
        setState(State::Connected);
    }

    void onHeartbeatTick() {
        if (++m_missedBeat > kMaxMissed) {           // 连续 N 次没应答
            qWarning() << "heartbeat lost, treat as disconnected";
            m_sock->abort();                          // 触发 onDisconnected
            return;
        }
        send(makeHeartbeat());
    }
    void onHeartbeatAck() { m_missedBeat = 0; }

    void onDisconnected() {
        m_hbTimer.stop();
        if (m_closing) { setState(State::Disconnected); return; }  // 主动停，不重连
        scheduleRetry();
    }

    void scheduleRetry() {
        setState(State::Backoff);
        // 指数退避 + 抖动，避免多台上位机同时重连打垮刚恢复的设备
        const int jitter = QRandomGenerator::global()->bounded(m_backoffMs / 4 + 1);
        m_retryTimer.start(m_backoffMs + jitter);
        m_backoffMs = qMin(m_backoffMs * 2, kMaxBackoff);   // 翻倍并封顶
    }

    QTcpSocket* m_sock;
    QTimer m_hbTimer, m_retryTimer, m_connectTimer;
    int  m_backoffMs  = kBaseBackoff;
    int  m_missedBeat = 0;
    bool m_closing    = false;
};
这段代码里有四个细节能体现工程经验，面试时值得主动讲：① 成功连接后重置退避计数（否则一次长时间断网后，恢复了也要等 30 秒）；② 退避加随机抖动（避免多台上位机同步重连，把刚启动的设备再打挂）；③ m_closing 标志区分主动关闭与意外断开（否则退出程序时会触发重连，永远关不掉）；④ 自己加连接超时定时器（系统 TCP 连接超时可能长达数十秒，用户早就以为程序死了）。
心跳的判定要用「连续 N 次未应答」而不是「一次超时就断」。工业现场偶发一次丢包很正常，单次超时就重连会导致连接反复抖动，反而更不稳定。典型参数：心跳 2 秒一次，连续 3 次无应答（即 6 秒）判定断线。同时要注意 QTimer 的精度依赖事件循环——如果 UI 线程偶尔被占住 1 秒，心跳会跟着延迟，所以判定要基于时间戳差值，而不是回调次数。

面试题集（12 道）

按难度分层，先自测再对照

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础什么是 TCP 粘包？readyRead 触发时能假设收到了一条完整消息吗？

    不能。TCP 是字节流协议，只保证字节按序、不丢不重，不保证消息边界。发送方三次 write 的数据，接收方可能一次全收到（粘包），也可能分多次收到半条（半包）。

    readyRead 的语义只是「缓冲区里有新数据了」。正确处理方式是累积缓冲 + 循环解析：把新数据追加到成员缓冲区，然后在循环里反复尝试「够不够一个完整帧」，够就取走一帧继续，不够就退出等下次。

    为什么本地测试发现不了
    本地回环、小数据量时，一次 write 通常就对应一次 readyRead，错误代码「看起来能跑」。一到现场跨交换机、数据量上来，问题立刻暴露。
  2. 基础为什么不能在 UI 线程调用 waitForReadyRead()？

    因为它内部会跑一个局部的 QEventLoop直到条件满足或超时。两个后果：

    • 它会阻塞你的函数——期间界面不响应，网络慢就是卡死几秒。
    • 更隐蔽的是它继续分发其它事件，带来和 processEvents() 相同的重入与 use-after-free 风险：用户可能在这期间关闭了窗口，函数返回后你继续访问成员变量。

    UI 线程里应该用信号槽的异步写法。waitForXxx 的合法用途是在没有 GUI 的工作线程里写同步风格的协议交互。

  3. 基础用 QNetworkAccessManager 发请求，有哪几件事必须做？
    • 全应用共用一个 QNAM 实例——它内部维护连接池，每次 new 一个就等于每次重建 TCP + TLS 握手。
    • 在 finished 槽里 reply->deleteLater()——reply 没有 parent，不删就泄漏；而且必须用 deleteLater 不能用 delete（正在自己的信号里删自己会崩）。
    • 设超时——Qt 5.15 之前 QNAM 没有默认超时，遇到网络黑洞会永久挂起。用 setTransferTimeout()，老版本用 QTimer + abort()。
    • 既判 error() 也判 HTTP 状态码——只看 error 会漏掉需要区分处理的 4xx/5xx 语义。
    • QNAM 和它创建的 reply 必须在同一线程。
  4. 基础ignoreSslErrors() 有什么危害？内网自签证书应该怎么处理？

    无参的 ignoreSslErrors() 会忽略一切证书错误，包括「证书不是可信 CA 签发的」「域名不匹配」「证书已过期」。结果是：加密还在，但身份认证没了——任何中间人出示一张自签证书就能冒充服务器，客户端照单全收。这比明文 HTTP 更危险，因为它给人一种「已经加密了」的虚假安全感。

    正确做法：把设备/内网服务的自签 CA 证书打进程序资源，加入 QSslConfiguration 的信任列表，并保持 VerifyPeer：

    cfg.setCaCertificates(cfg.caCertificates()
    + QSslCertificate::fromPath(":/certs/company-ca.pem"));
cfg.setPeerVerifyMode(QSslSocket::VerifyPeer);

    实在要忽略，也只能用带参版本忽略你逐条检查过的那一批错误。

9.2 中级（区分熟练度）

  1. 中级设计一个二进制协议的分帧方案，说明要防御哪些异常输入。

    方案：4 字节大端长度前缀 + 变长 body。可选再加 2 字节魔数用于重同步、2 字节版本号、末尾 4 字节 CRC。

    接收侧算法：新数据追加到缓冲 → 循环｛缓冲不足 4 字节则退出；读长度；长度超上限则断链；缓冲不足 4+len 则退出；取出整帧、消费掉、继续｝。

    必须防御的输入：

    超大长度字段
    攻击者发 0xFFFFFFFF，你若直接按它分配就是 4 GB 内存申请，OOM 或 DoS。必须有 kMaxFrame 上界检查。
    长度为 0
    若代码里有「消费 4+len 字节」的逻辑而 len 可以为 0，配合某些写法会导致死循环空转。
    缓冲无限增长
    对端只发头不发 body，你的累积缓冲会一直涨。要给缓冲总量也设上限。
    字节序与对齐
    不要直接 reinterpret_cast 成结构体读——对齐和字节序都不可移植。用 qFromBigEndian 逐字段读。
  2. 中级使用 QDataStream 做网络序列化，有什么必须注意的兼容性问题？

    必须显式调用 setVersion()。QDataStream 的默认版本随 Qt 版本变化，而不同版本对 QString、容器、QVariant 的编码格式并不相同。上位机用 Qt 5.15、设备固件用 Qt 5.9，不钉版本就是两边各说各话——表现往往是「大部分字段正确，某个字符串偶尔乱码」，极难排查。

    其它注意点：默认字节序是大端（网络序），与主机序不同要心里有数；浮点精度默认是双精度，可用 setFloatingPointPrecision 控制；读完后要检查 in.status() 是否为 Ok，损坏数据不会抛异常只会设状态位。

    选型边界
    QDataStream 是 Qt 私有格式，Python/C# 侧无法解析。跨语言、跨团队、需要长期演进的协议应该用 Protobuf 或明确定义的字节布局；它的甜蜜区是「两端都是自己写的 Qt 程序」。
  3. 中级为什么处理 newConnection 时要用 while 循环取连接？

    因为一次 newConnection 信号可能对应多个待处理连接。Qt 在一轮事件分发里如果 accept 到了若干连接，不会为每个都单独发一次信号（信号可能被合并）。只调用一次 nextPendingConnection()，剩下的连接就留在队列里，直到下一个连接到来才被处理。

    后果是高负载时连接堆积、客户端超时——低负载测试完全正常，压测才暴露。同样的道理适用于 QUdpSocket：要用 while (hasPendingDatagrams()) 把 datagram 取干净。

  4. 中级用 QProcess 调外部程序时，为什么会出现「子进程单独跑很快，被程序调用就卡住」？

    因为没有读 stdout/stderr。子进程的输出写进管道，管道缓冲区（Linux 上通常 64 KB）写满后子进程的 write 会阻塞；而父进程在等 finished 信号——双方互等，永久卡死。

    解决：连上 readyReadStandardOutput / readyReadStandardError 持续读走；或者明确不需要输出时把通道重定向到 QProcess::nullDevice()。

    另一个常见错误
    用字符串拼接构造命令行（start("tool " + userInput)）会引入命令注入。应该用 setProgram() + setArguments(QStringList)，参数以数组传给 OS，不经过 shell。

9.3 高级（体现深度）

  1. 高级Qt 的网络 IO 适合做高并发服务端吗？如果一个 Qt 应用必须扛上万连接，架构怎么设计？

    不适合。Qt 的事件分发底层是 poll(2)（Linux 桌面上走 GLib 的 GMainContext，同样基于 poll），复杂度是 O(n) 于 fd 数量：每轮都要把整个 fd 数组交给内核、返回后线性扫描。几百个连接没问题，上万就会在 poll 上耗掉大量 CPU。而且网络事件与 GUI 事件共用一个循环，任何一个慢槽都会拖累全部。

    架构方案：把网络层从 Qt 事件循环里剥出来——独立线程跑 Asio / 裸 epoll / io_uring，用自己的线程池处理业务；只在需要更新界面时，通过 QMetaObject::invokeMethod 或 Queued 信号把结果送回 UI 线程。这样 GUI 与网络各自用最适合的模型，边界清晰。

    边界判断
    连接数在几百以内、且每个连接流量不大时，Qt 自带的够用且省事；一旦要考虑 C10K，就不该在 Qt 的循环里解决。详见 异步网络框架指南。
  2. 高级设计一个能抗住现场断网的设备长连接，说明状态机和关键参数。

    五个状态：Disconnected / Connecting / Connected / Backoff / Closing。Closing 必须与 Disconnected 分开——否则「用户点退出」会被当成意外断开而触发重连，程序关不掉。

    四个关键设计：

    应用层心跳
    TCP keepalive 默认 2 小时，且探测不到「进程假死但 TCP 栈还活着」。必须自己发心跳，典型 2 秒一次，连续 3 次无应答才判定断线（单次超时就断会导致连接反复抖动）。
    指数退避 + 抖动
    1s → 2s → 4s …封顶 30s，并加随机抖动。抖动很重要：多台上位机同时重连会把刚恢复的设备再次打挂（惊群）。
    成功后重置退避
    忘了重置的话，一次长时间断网之后即使网络恢复，也要等满 30 秒才连上。
    自己的连接超时
    系统 TCP 连接超时可能数十秒（SYN 重传），必须自己起一个 QTimer，超时就 abort() 转入退避。
    时间判定
    心跳超时判定要基于时间戳差值而非回调次数——QTimer 精度依赖事件循环，UI 卡顿时定时器会延迟，按次数算会误判。
  3. 高级本机两个进程要传大图像帧，你会怎么选 IPC 方案？

    数据面用共享内存，控制面用消息通道——这是大数据量 IPC 的通用模式：

    • 共享内存（QSharedMemory 或直接 shm_open + mmap）放像素数据，避免几十 MB 的拷贝。做成 N 个槽位的环形缓冲，生产者写槽位、消费者读槽位。
    • QLocalSocket（Unix domain socket / 命名管道）只传「第 k 号槽位已就绪、尺寸格式如下」这样的小消息。它天然有序、有连接语义、对端崩溃时能感知。
    • 同步用 QSystemSemaphore 或共享内存里的 pthread 进程间互斥量。QSharedMemory::lock() 只是本进程内的互斥，不能跨进程用。
    崩溃残留
    Unix 上共享内存段和信号量是内核持久的：进程崩溃后不会自动释放。要有清理逻辑（attach() 后 detach() 让引用计数归零），或者启动时用固定 key 主动清理一次。
    什么时候不该用共享内存
    如果数据量其实不大（几 KB 的结果 JSON），共享内存的复杂度完全不值得——直接走 QLocalSocket 就行。共享内存的适用前提是「拷贝开销确实成为瓶颈」，先测量再上。IPC 机制的完整对比见 Linux 多进程与 IPC 指南。
  4. 高级Qt 客户端出现「偶尔收不到设备数据」，你会怎么排查？

    按从外到内的顺序切割，每一步都要有证据而不是猜测：

    1. 先确认包到没到主机：tcpdump -i any port 5000 -w cap.pcap，用 Wireshark 看。如果抓不到，问题在设备侧或网络（交换机、VLAN、多网卡路由）——不要在应用代码里找。
    2. 包到了但应用没收到：查 socket 接收缓冲是否溢出（ss -tmi 看 Recv-Q）。缓冲堆积说明应用读得太慢——多半是 UI 线程被某个耗时槽占住了。
    3. 应用收到了但没处理：这就是分帧 bug。在 onReadyRead 里打印 bytesAvailable() 和累积缓冲长度，看是不是缓冲在持续增长（说明解析条件永远不满足，比如长度字段字节序搞反了）。
    4. 解析对了但槽没跑：跨线程时检查是否漏了 qRegisterMetaType——自定义类型未注册时 Qt 只打一行 warning 然后静默丢弃。把 Qt 的 warning 接进日志系统，或临时设 QT_FATAL_WARNINGS=1 让它直接 abort 到调试器。
    埋点先行
    这类「偶发」问题事后排查成本极高。上线前就应该有三个指标：每秒收帧数、解析失败计数、累积缓冲峰值。有了这三个数，问题出现时看一眼监控就能定位到上面四层中的哪一层。参见 C++ 可观测性完全指南。
