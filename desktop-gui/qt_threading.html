Qt 并发与跨线程完全指南

Qt 多线程的坑几乎全部来自同一个误解：把 QThread 当成「线程」。它其实是「线程的遥控器」，自己住在创建它的线程里。理解了这一点，moveToThread 为什么是推荐写法、为什么子类化后槽跑在了主线程、为什么 deleteLater 会泄漏，全部迎刃而解。本篇从对象的线程归属讲起，一路到 QtConcurrent、GUI 线程铁律与死锁排查。

核心难度 ★★★★★ 面试出现率 极高 阅读时长 ~25 min 前置 Qt 核心机制 · std::thread
QThread · moveToThread 线程亲和性 QtConcurrent · QFuture 死锁排查
没写过 Qt？先读 Qt 零基础全景入门 建立全景，再读 Qt 核心机制 打好对象树与信号槽的地基——本篇默认你已经知道「事件循环是什么」。
01

QThread 不是线程

纠正这一个误解，八成的坑就没了

QThread：一个管理操作系统线程的 QObject。start() 创建 OS 线程并在其中执行 run()；但 QThread 对象本身仍然属于创建它的那个线程（通常是主线程）。所以它的槽函数、它的 deleteLater，默认都在主线程执行。
把 QThread 想成工地的对讲机，不是工人本身。你在办公室（主线程）拿着对讲机，按下 start() 把工人派出去干活。对讲机一直在你手上——你对着它说话（调它的槽），声音是在办公室里响的，不是在工地上。想让工人听见，得通过无线电（跨线程信号槽）传过去。

这个区分直接解释了三个常见困惑：

  • 「我在 QThread 子类里加了槽，为什么它在主线程执行？」——因为槽属于 QThread 对象，而对象住在主线程。只有 run() 的函数体在新线程。
  • 「为什么推荐 moveToThread？」——因为要让「干活的对象」住到新线程去，而不是让「遥控器」去干活。
  • 「为什么我的 worker 收不到信号？」——多半是 run() 被重写后没调 exec()，那个线程压根没有事件循环，Queued 信号无处投递。
02

两种用法与官方推荐

moveToThread 为主，子类化为辅

写法 A：moveToThread（推荐，适合事件驱动型任务）

class Worker : public QObject {
    Q_OBJECT
public slots:
    void process(const QString& path) {      // 在工作线程执行
        for (int i = 0; i <= 100; ++i) {
            if (m_abort.loadRelaxed()) { emit canceled(); return; }
            heavyStep(i);
            emit progress(i);                // 自动 Queued 回主线程
        }
        emit finished();
    }
    void abort() { m_abort.storeRelaxed(1); }  // 注意：这个槽也在工作线程排队
signals:
    void progress(int);
    void finished();
    void canceled();
private:
    QAtomicInt m_abort{0};
};

// —— 装配（在主线程）——
auto* th = new QThread(this);
auto* w  = new Worker;          // ⚠️ 必须无 parent，否则 moveToThread 失败
w->moveToThread(th);

connect(th, &QThread::started,  w,  &Worker::process);
connect(w,  &Worker::progress,  this, &MainWindow::onProgress);
connect(w,  &Worker::finished,  th, &QThread::quit);        // 停事件循环
connect(w,  &Worker::finished,  w,  &QObject::deleteLater); // 删 worker
connect(th, &QThread::finished, th, &QObject::deleteLater); // 删 thread 对象
th->start();
那四条 connect 的顺序不是随便写的，而是一条严格的关闭链：finished → 让线程的事件循环退出（quit）；finished → worker 自删（此时它还在工作线程，DeferredDelete 会在事件循环退出前被处理）；QThread::finished（线程真正结束时发出，在主线程投递）→ 删 QThread 对象。少任何一条都会泄漏，顺序反了会崩。
moveToThread 有两条硬约束：① 对象不能有 parent，否则调用失败并打印 Cannot move objects with a parent——因为对象树必须整体属于同一线程；② 只能「推」不能「拉」，即必须在对象当前所属线程里调用 moveToThread（把自己推出去），不能从别的线程把它拽过来。移动时该对象的所有 children 会跟着一起走。

写法 B：子类化 QThread（适合一条道跑到黑的计算任务）

class ScanThread : public QThread {
    Q_OBJECT
protected:
    void run() override {                 // 这里面才是新线程
        while (!isInterruptionRequested()) {
            Frame f = camera.grabBlocking();  // 阻塞式循环，不需要事件循环
            emit frameReady(f);            // emit 可以跨线程
        }
        // 若这里不调 exec()，本线程就没有事件循环：
        //   · 本线程内创建的 QObject 收不到 Queued 信号
        //   · QTimer 不会触发
        //   · deleteLater() 永远不执行 → 泄漏
    }
signals:
    void frameReady(Frame);
};
moveToThread（写法 A）子类化 run()（写法 B）
适合事件驱动：要接收多种请求、可随时调度新任务单一长任务：阻塞式采集循环、纯计算
事件循环默认有（run() 的默认实现就是 exec()）你不调 exec() 就没有
能否接收 Queued 信号能不调 exec 则不能
常见错误忘了「worker 不能有 parent」误以为子类的槽在新线程（其实在主线程）
取消机制原子标志位 / requestInterruptionrequestInterruption + isInterruptionRequested
被问「QThread 的两种用法哪个更好」时，不要答「官方推荐 moveToThread 所以用它」。正确回答是分场景：需要事件循环、要能随时接新任务的用 moveToThread；只是把一段阻塞循环搬到后台、不需要接收消息的，子类化 run() 反而更直白。真正的红线只有一条——不要给 QThread 子类加槽然后以为它在新线程执行。

线程的销毁：必须 quit + wait

// ❌ 直接析构还在跑的线程
// QThread: Destroyed while thread is still running
// → Qt 随后调用 terminate()，线程在任意位置被打断：
//   锁不释放、析构不执行、缓冲区写一半 → 数据损坏或死锁

// ✅ 标准关闭序列
MainWindow::~MainWindow() {
    if (m_thread && m_thread->isRunning()) {
        m_thread->requestInterruption();   // 通知业务循环退出
        m_thread->quit();                  // 让事件循环 exec() 返回
        if (!m_thread->wait(3000))            // 给一个上限，别无限等
            qWarning() << "worker thread did not exit in 3s";
    }
}
quit() 只让事件循环退出，对「run() 里在跑 while 循环」的子类化线程毫无作用——那种情况必须靠 requestInterruption() 或自己的原子标志位。terminate() 在任何情况下都不该出现在生产代码里，它是最后的止损手段，不是关闭手段。
03

线程亲和性与跨线程信号槽

「这个对象属于哪个线程」是 Qt 多线程的中心问题

线程亲和性（Thread Affinity）：每个 QObject 都记录自己「属于」哪个线程，可用 obj->thread() 查询。默认是创建它的那个线程。这个归属决定了三件事：它的槽在哪执行（Queued 时）、它的定时器在哪计时、它的 deleteLater 由谁处理。

跨线程调用的三种正确姿势

// ① 信号槽（首选）——自动 Queued，参数深拷贝
connect(worker, &Worker::progress, this, &MainWindow::onProgress);

// ② invokeMethod 传 lambda（Qt5.10+）——把一段代码扔到目标对象所属线程执行
QMetaObject::invokeMethod(worker, [worker, path]{
    worker->process(path);            // 在 worker 所属线程运行
}, Qt::QueuedConnection);

// ③ 需要返回值时用 BlockingQueued（谨慎）
int result = 0;
QMetaObject::invokeMethod(worker, "compute", Qt::BlockingQueuedConnection,
                          Q_RETURN_ARG(int, result), Q_ARG(int, 42));
// ⚠️ 调用方会阻塞；若 worker 与调用方同线程 → 立即死锁
❌ 直接调另一个线程对象的方法
// 主线程里：
worker->process(path);
// 这是普通函数调用，会在【主线程】执行！
// 结果：① UI 照样卡死
//       ② 同时 worker 内部状态被两个线程碰 → race

// 变体：worker 里 new 一个 QTimer
void Worker::setup() {
    m_timer = new QTimer(this);
    m_timer->start(100);
}
// 若 setup() 是在主线程直接调的，
// timer 归主线程，永远不会在工作线程触发
✅ 经由信号 / invokeMethod
QMetaObject::invokeMethod(worker, [worker, path]{
    worker->process(path);   // 工作线程执行
}, Qt::QueuedConnection);

// 需要在工作线程里创建对象，就在工作线程里创建：
connect(th, &QThread::started, worker, [worker]{
    worker->setup();   // 此时已在工作线程
});

// 断言归属，把问题挡在开发期
void Worker::process(const QString& p) {
    Q_ASSERT(QThread::currentThread() == this->thread());
    ...
}
给每个 worker 的入口槽加一句 Q_ASSERT(QThread::currentThread() == thread())，成本几乎为零，却能在 debug 构建里立刻抓出「以为是跨线程、其实是直接调用」的错误。同理，UI 侧的关键函数可以加 Q_ASSERT(QThread::currentThread() == qApp->thread())。

QTimer 的线程规则

  • 定时器必须在拥有它的线程里 start()，否则 Qt 报 Timers can only be used with threads started with QThread 或者干脆不触发。
  • 定时器精度依赖该线程事件循环的响应速度。如果那个线程正在执行一个耗时槽，定时器就会延迟——所以 QTimer 在负载高时不是硬实时的，做心跳/超时判断要用时间戳比较而不是「回调次数 × 间隔」。
  • QTimer::singleShot(0, obj, ...) 是「让出一次事件循环、下一轮再执行」的惯用法，常用于把长任务切片，避免 processEvents 的重入风险。
04

QtConcurrent 与 QFuture

不需要事件循环的那一半：任务并行

QThread 解决的是「把一个长期运行的角色搬到后台」；QtConcurrent 解决的是「把一批短任务并行跑完」。两者是不同的抽象层次，不要互相替代。

// ① 跑一个任务，拿 future
QFuture<int> f = QtConcurrent::run([]{ return heavyCompute(); });

// ② 数据并行：对容器每个元素并行处理
QList<QImage> imgs = load();
QFuture<void> g = QtConcurrent::map(imgs, [](QImage& im){ denoise(im); });

// ③ map-reduce
QFuture<int> total = QtConcurrent::mappedReduced(files, countDefects, sumUp);

// ④ Qt6：continuation，不阻塞 UI 线程
QtConcurrent::run([]{ return inspect(); })
    .then(qApp, [](Result r){ showResult(r); });   // then 的 context 决定回调线程

// ⑤ 进度反馈 + 取消（Qt6 的 QPromise）
QFuture<void> job = QtConcurrent::run([](QPromise<void>& promise){
    promise.setProgressRange(0, 100);
    for (int i = 0; i <= 100; ++i) {
        if (promise.isCanceled()) return;    // 协作式取消
        step(i);
        promise.setProgressValue(i);
    }
});
QFutureWatcher<void>* watcher = new QFutureWatcher<void>(this);
connect(watcher, &QFutureWatcherBase::progressValueChanged,
        ui->bar, &QProgressBar::setValue);          // 自动回到 UI 线程
watcher->setFuture(job);
不要在 QtConcurrent::run 里做阻塞等待。它默认用全局线程池（QThreadPool::globalInstance()），线程数约等于 CPU 核数。如果池里的任务互相等待（任务 A 等任务 B 的结果，而 B 还排在队列里），池被占满就整体死锁——现象是程序不崩不报错，只是永远卡住。做法：阻塞型 IO 用独立的 QThreadPool（setMaxThreadCount 调大），或者用 QThread + 事件循环；计算型才交给全局池。
需求推荐工具理由
长期后台角色（相机采集、串口收发、后台服务）QThread + moveToThread需要常驻 + 事件循环接收指令
一批独立短任务（批量图像处理）QtConcurrent::map自动利用多核，写法最短
一次性的耗时计算，要拿结果QtConcurrent::run().then()continuation 风格，不阻塞 UI
需要进度条与取消QPromise + QFutureWatcher进度信号自动回到 UI 线程
自定义线程池策略（优先级、限流）QThreadPool + QRunnable可控性最高
纯计算、与 Qt 无关的库代码std::thread / std::async不引入 Qt 依赖，便于单测
QFuture::waitForFinished() 在 UI 线程调用 = 界面卡死，和直接同步执行没有区别。要么用 QFutureWatcher 的信号，要么用 Qt6 的 .then()。这是「用了异步框架但写成了同步」的典型反例，和 C++ 多线程编程模式 里 std::future::get() 的坑是同一个。

同步原语：Qt vs 标准库

现在该用哪一套

Qt标准库对应今天该用哪个
QMutex / QRecursiveMutexstd::mutex / std::recursive_mutex标准库（除非要 tryLock(ms) 这种带超时的接口）
QMutexLockerstd::lock_guard / std::unique_lock标准库
QReadWriteLockstd::shared_mutex标准库
QWaitConditionstd::condition_variable标准库
QSemaphorestd::counting_semaphore（C++20）看编译器支持
QAtomicInt / QAtomicPointerstd::atomic<T>标准库，内存序语义更清晰
信号槽 Queued（无对应）Qt——这是 Qt 真正不可替代的部分
QThreadStoragethread_local标准库
结论很清楚：C++11 之后，Qt 的同步原语已经没有技术优势，它们存在只是历史原因（Qt4 时代标准库还没有线程）。新代码用标准库，语义与内存序更精确、可移植、便于单元测试。唯独跨线程信号槽和事件循环没有标准替代品——那才是 Qt 并发模型的价值所在。内存序细节见 C++ 内存模型详解。
一个例外值得注意：Qt 的隐式共享容器（QString、QByteArray、QImage、Qt6 的 QList）内部用原子引用计数，「拷贝到别的线程」是安全的，但「两个线程同时操作同一个实例」不安全。跨线程传大对象时靠这个 COW 特性可以避免深拷贝——但一旦有一方调用非 const 方法触发分离（detach），语义就变了。传值给信号槽是安全用法；共享一个成员变量再各自改，不是。
06

GUI 线程铁律

工业检测项目里最实用的一节

只有主线程能碰 QWidget 及其派生类。这不是「建议」，是 Qt 的硬性约束——窗口系统的句柄、绘制后端、样式引擎都不是线程安全的。在工作线程里调 label->setText() 可能表现为：偶发花屏、断言失败、随机崩溃，甚至在开发机上「看起来一直没问题」而在客户现场每天崩一次。

哪些图形类可以在工作线程用

类工作线程可用？说明
QImage可以纯内存位图，后端无关。图像算法应该全程用它
QPainter 绘到 QImage可以离屏渲染在工作线程完全合法
QPixmap不可以可能是窗口系统的资源（X11 Pixmap / GDI 对象）
QWidget 及派生不可以包括 setText、update、show 一切操作
QFont / QColor / QPen可以纯值类型
QML 的 QQuickItem不可以但 Quick 的渲染本身在独立的渲染线程
工业检测的典型流水线：采集线程从相机 SDK 拿到裸数据 → 包成 QImage（零拷贝构造，指定 stride）→ 算法线程用 OpenCV/Halcon 处理，结果仍然是 QImage + 一组缺陷框 → 通过 Queued 信号把 QImage 传回 UI 线程（QImage 是隐式共享，跨线程传递只加引用计数）→ UI 线程再 QPixmap::fromImage() 并显示。QPixmap 的转换必须放在最后一步、在 UI 线程做，这是这条流水线唯一容易搞错的地方。

UI 更新的频率控制

把工作线程的每一帧结果都 emit 回 UI，会出现一个反直觉的问题：信号的产生速度超过 UI 的消费速度时，事件队列会无限增长——内存持续上涨，界面反而越来越卡（因为它在处理几秒钟以前的旧帧）。

  • 限频：UI 侧用一个 QTimer（比如 30 Hz）主动去取「最新一帧」，工作线程只更新一个受锁保护的「最新结果」变量，不发信号。这是显示类场景的标准做法。
  • 背压：工作线程发之前检查一个原子计数，UI 处理完再减；超过阈值就丢弃中间帧。
  • 合并：进度类信号用「变化超过 1% 才 emit」，避免每次循环都发。
「工作线程算得比 UI 画得快，怎么办」是个很能体现工程经验的问题。答「加锁保护最新结果 + UI 定时拉取」比答「用队列缓冲」更好——后者只是把无界增长推迟了。这本质上是背压与过载保护问题在 GUI 场景的具体形态。

与 std::thread 混用

现实项目里两套一定会共存

算法库、第三方 SDK、公司自己的基础库，往往用的是 std::thread / std::async，不可能全改成 QThread。好消息是两者可以共存，需要注意的只有几点。

// ① std::thread 里 emit 信号 —— 可以，但目标对象必须有事件循环
std::thread t([this]{
    auto r = thirdPartySdk::run();
    // this 属于主线程 → 自动 Queued，安全
    emit resultReady(r);
});
t.detach();   // ⚠️ detach 之后无法等待，析构顺序不可控，慎用

// ② 更安全：不 emit，用 invokeMethod 显式指定目标
std::thread t2([this]{
    auto r = thirdPartySdk::run();
    QMetaObject::invokeMethod(this, [this, r]{ onResult(r); }, Qt::QueuedConnection);
});

// ③ 不要在非 Qt 线程里 new QObject 然后指望它有事件循环
//    Qt 会用 QAdoptedThread 包装这个线程，QThread::currentThread() 可用，
//    但它没有 exec()，所以该线程内的 QObject 收不到 Queued 信号。
场景选择理由
需要接收 Qt 信号 / 用 QTimer / deleteLaterQThread必须有 Qt 事件循环
纯计算、无 Qt 交互、想做单元测试std::thread / std::jthread不引入 Qt 依赖
需要 stop_token 式协作取消std::jthread（C++20）Qt 侧只有 requestInterruption，粒度更粗
要跨线程返回值 + 异常传播std::future 或 QFuture信号槽不能传异常，只能传错误码/消息
信号槽不能跨线程传播 C++ 异常。在槽里抛出的异常如果穿过事件循环，Qt 的行为是未定义的（Qt6 会直接 std::terminate）。所以工作线程的槽必须自己 catch 住所有异常，转成一个 errorOccurred(int code, QString msg) 信号发出去。这与 std::future 能自动搬运 exception_ptr 形成鲜明对比——需要异常语义时应该用 future，见 跨线程异常传递。

死锁与卡顿案例集

按现场出现频率排序

#症状根因处理
1点某个按钮后整个程序卡死BlockingQueuedConnection 的收发双方在同一线程改 Queued；确实要返回值就重构成「请求 + 回调信号」
2程序退出时崩溃 / 卡住不退QThread 析构时线程还在跑，被 terminaterequestInterruption + quit + wait(timeout)
3worker 的槽从不执行子类化 run() 没调 exec()，或对象没 moveToThread核对 worker->thread()；补 exec()
4内存持续上涨，界面越来越卡信号产生快于消费，事件队列无界增长限频 / 背压 / 合并（见 §6）
5并行任务永久挂起，CPU 占用 0QtConcurrent 全局池被阻塞任务占满阻塞任务用独立池或 QThread

8数据偶尔算错，无法稳定复现写死了 DirectConnection，moveToThread 后成了跨线程直调去掉硬编码的连接类型，交给 Auto；用 TSan 复检

排查工具链

  • ThreadSanitizer：抓 data race 最有效，能直接指出「哪两个线程在哪两行访问了同一地址」。Qt 程序可以跑 TSan，注意屏蔽 Qt 内部的已知误报。用法见 Sanitizer 全家桶完全指南。
  • GDB 多线程调试：卡死时 thread apply all bt 一次性打印所有线程栈，两个线程互相等在 QWaitCondition::wait 或 pthread_cond_wait 上就是死锁现场。见 GDB 多线程调试与 死锁定位实战。
  • Qt 自带的诊断：qputenv("QT_FATAL_WARNINGS", "1") 让 Qt 的 warning 直接 abort，配合调试器能在「Cannot queue arguments」「Timers can only be used with…」发生的第一现场停下。
  • 日志打线程 ID：qSetMessagePattern("%{time} [%{threadid}] %{message}")，几乎零成本，却能让 80% 的线程问题一眼可见。

面试题集（12 道）

按难度分层，先自测再对照

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础QThread 对象属于哪个线程？它的槽函数在哪个线程执行？

    QThread 对象属于创建它的线程（通常是主线程），只有 run() 的函数体运行在新创建的 OS 线程里。

    因此它的槽函数默认在主线程执行。这就是「给 QThread 子类加槽，以为它在后台跑」这个经典错误的根源。

    记忆锚点
    QThread 是「线程的遥控器」，不是线程本身。遥控器在你手上，工人在工地上。
  2. 基础为什么不能在工作线程里直接操作 QWidget？

    因为 Qt 的 GUI 层不是线程安全的：窗口句柄、绘制后端、样式引擎、布局系统都假设只有一个线程在访问；很多平台的窗口 API 本身也要求在创建窗口的线程调用。

    违反的表现不一定是立刻崩溃，更常见的是偶发花屏、断言失败、在客户现场每天崩一次——这才是它危险的地方。

    正确做法
    工作线程只处理数据（QImage 可以在工作线程用），结果通过 Queued 信号发回主线程，由主线程更新界面。
  3. 基础写出 moveToThread 的标准装配代码，并说明每条 connect 的作用。 
    auto* th = new QThread(this);
auto* w  = new Worker;        // 无 parent
w->moveToThread(th);
connect(th, &QThread::started,  w,  &Worker::process);
connect(w,  &Worker::finished,  th, &QThread::quit);
connect(w,  &Worker::finished,  w,  &QObject::deleteLater);
connect(th, &QThread::finished, th, &QObject::deleteLater);
th->start();
    • started → process：线程一起来就开工（此时已在工作线程）。
    • finished → quit：活干完，让工作线程的事件循环退出。
    • finished → deleteLater（worker）：worker 自删，DeferredDelete 在事件循环退出前被处理。
    • QThread::finished → deleteLater（thread）：线程真正结束后，删掉 QThread 对象本身。
    易错
    worker 必须没有 parent，否则 moveToThread 失败并打印 Cannot move objects with a parent。
  4. 基础Qt 的 QMutex 和标准库的 std::mutex，新项目该用哪个？

    用 std::mutex。Qt 的同步原语诞生于 C++11 之前，当时标准库还没有线程支持；今天它们相对标准库没有技术优势，反而带来 Qt 依赖，不利于把核心逻辑抽成可单测的纯 C++ 库。

    唯一还值得用 Qt 版本的情况是需要 QMutex::tryLock(int timeout) 这类带超时的接口（C++ 里要用 std::timed_mutex），或者代码库已经全用 Qt 风格、保持一致更重要。

    真正不可替代的
    Qt 并发模型的价值不在互斥量，而在跨线程信号槽 + 事件循环——标准库至今没有对应物。

9.2 中级（区分熟练度）

  1. 中级子类化 QThread 时如果不调 exec()，会失去什么？

    QThread::run() 的默认实现就是调用 exec() 启动事件循环。重写 run() 而不调 exec()，这个线程就没有事件循环，随之失去三样能力：

    • 该线程内的 QObject 收不到 Queued 信号（事件没人取）。
    • QTimer 不会触发。
    • deleteLater() 投递的 DeferredDelete 事件永远不被处理 → 对象泄漏。

    这不一定是错——如果 run() 里就是一个「阻塞采集 → emit」的死循环，本来就不需要事件循环。关键是知道自己放弃了什么。

  2. 中级quit()、terminate()、requestInterruption() 三者有什么区别？
    quit()
    请求事件循环退出（等价于 exit(0)）。对「run() 里跑 while 循环、没有 exec()」的线程完全无效。
    requestInterruption()
    只是设置一个标志位，需要 run() 里主动用 isInterruptionRequested() 轮询。协作式取消，安全。
    terminate()
    强杀线程，在任意指令处打断：锁不释放、析构不执行、缓冲区可能写了一半。生产代码里不应该出现。

    标准关闭序列是三者配合：requestInterruption()（让业务循环退出）→ quit()（让事件循环退出）→ wait(timeout)（等它真的结束，并设上限）。

  3. 中级工作线程算得比 UI 画得快，怎么处理？

    直接每帧 emit 会导致事件队列无界增长：内存持续上涨，界面反而越来越卡，因为它在渲染几秒钟以前的旧帧。三种处理方式：

    限频（首选）
    工作线程只更新一个受锁保护的「最新结果」变量，不发信号；UI 侧用 30 Hz 的 QTimer 主动去拉。天然丢弃中间帧，队列长度恒定。
    背压
    用原子计数记录「已发未处理」数量，超阈值就跳过本次 emit。
    合并
    进度类信号加「变化超过 1% 才发」的门限，避免高频无意义更新。

    「加个更大的队列缓冲」不是答案——它只是把无界增长推迟了，本质上是过载保护问题。

  4. 中级QtConcurrent::run 里做阻塞 IO 有什么风险？

    它默认使用全局线程池，线程数大约等于 CPU 核数。阻塞任务会长期占住池中的线程，导致两个后果：

    • 吞吐塌陷：几个阻塞任务就把池占满，后面的计算任务全部排队。
    • 整体死锁：如果池里的任务 A 在等待任务 B 的结果，而 B 还排在队列里等空闲线程——线程全被 A 这类任务占着，B 永远轮不到。现象是程序不崩不报错，CPU 占用 0，永久挂起。
    正确做法
    阻塞型 IO 用独立的 QThreadPool（setMaxThreadCount 按并发数调大）或者 QThread + 事件循环；全局池只留给 CPU 密集的短任务。这与标准库里「不要在 std::async 的默认策略下做阻塞等待」是同一类问题。

9.3 高级（体现深度）

  1. 高级BlockingQueuedConnection 在什么情况下会死锁？为什么它仍然存在？

    两种死锁：

    • 同线程使用：发送方阻塞等待槽执行，而槽的调用事件排在同一个线程的队列里——线程正在阻塞，取不出事件，永久互等。Qt 对这种情况会直接 qFatal，但只在它能检测到时。
    • 跨线程成环：A 阻塞等 B 的槽，B 的槽里又用 Blocking 调回 A 的槽。两边都在等对方，构成环。这种 Qt 检测不出来。

    为什么保留它：有些场景确实需要「跨线程同步取值」，比如从工作线程读一个只有 UI 线程能提供的状态、或者在关闭流程中必须确认对方已经处理完。它是把跨线程调用退化成同步调用的逃生舱。

    替代方案
    优先重构成「请求信号 + 结果信号」的异步两段式，或者把需要的状态提前缓存成原子变量。真要同步取值时，至少确认调用链上不存在反向的 Blocking 调用。
  2. 高级一个对象 moveToThread 之后，它此前建立的连接会发生什么变化？

    取决于连接类型：

    AutoConnection（默认）
    自动适配。因为 Auto 的判定发生在 emit 时刻——用 QThread::currentThread() 与 receiver->thread() 比较。对象换了线程，下次 emit 时判定结果就变了，无需重连。
    写死的 DirectConnection
    不会变。moveToThread 之后，这条连接就成了「在发送方线程直接调用一个属于别的线程的对象的成员函数」——data race，而且是最难复现的那种：功能看起来正常，只是数据偶尔算错。

    另外，对象的 children 会跟着一起移动；它拥有的定时器会被重新注册到新线程（Qt 内部处理），但如果定时器是在旧线程 start() 的且移动时机不当，可能出现「定时器不再触发」。

    工程结论
    除非有明确理由，不要手写连接类型，让 Auto 去判断。手写 Direct 的唯一合理场景是「明确要求同步执行且确信同线程」，并且要在代码旁写清楚为什么。
  3. 高级Qt 信号槽能跨线程传播异常吗？如果不能，工作线程的错误该怎么上报？

    不能。Queued 连接下，槽是由接收方线程的事件循环调用的，与 emit 方已经不在同一个调用栈上——异常没有地方可以传回去。异常如果穿过事件循环，Qt 的行为未定义，Qt6 下通常直接 std::terminate。

    正确做法：工作线程的每个入口槽都用 try-catch 包住，把异常转成错误信号：

    void Worker::process() {
    try {
        doWork();
        emit finished();
    } catch (const std::exception& e) {
        emit errorOccurred(ErrCode::Internal, QString::fromUtf8(e.what()));
    } catch (...) {
        emit errorOccurred(ErrCode::Unknown, "unknown exception");
    }
}
    对比
    std::future/QFuture 能自动搬运 std::exception_ptr，get() 时在调用方重新抛出。需要异常语义时应该选 future 而不是信号槽——这是两种并发模型的一个实质差异，不只是风格问题。
  4. 高级设计一条工业相机的采集-处理-显示流水线，说明线程划分、对象归属与数据传递方式。

    三线程划分：

    1. 采集线程：子类化 QThread，run() 里是「阻塞等相机 SDK 回调 → 包装成 QImage」的死循环。不需要事件循环，因为它只产出不接收。用 requestInterruption 停止。
    2. 处理线程：Worker + moveToThread，需要事件循环，因为要接收「换算法参数」「暂停」等指令。算法全程操作 QImage（可以在非 UI 线程用），不碰 QPixmap。
    3. UI 线程：只负责显示与交互，收到结果后 QPixmap::fromImage() 再画。

    数据传递：帧数据用 QImage 经 Queued 信号传递——它是隐式共享的，跨线程「拷贝」只是原子加引用计数，不会深拷贝几十 MB 的像素。自定义的结果结构体（缺陷框列表等）需要 Q_DECLARE_METATYPE + qRegisterMetaType。

    背压：相机是恒定帧率的生产者，处理和显示都可能跟不上。采集→处理之间用有界队列，满了丢最旧帧（检测场景通常「最新的帧最有价值」）；处理→UI 之间用「最新结果变量 + UI 定时拉取」，不发高频信号。

    关闭顺序
    必须自上游向下游停：先停采集（requestInterruption + wait），再停处理（quit + wait），最后才析构 UI。反过来会出现「上游还在往已析构的下游发信号」——虽然 Qt 会在 receiver 析构时断开连接，但正在队列里的事件仍可能引用已释放的数据。
    可观测性
    三处埋点：采集帧率、处理耗时分布（p50/p99）、丢帧计数。没有这三个数，线上「偶尔卡一下」的问题无法定位。参见 C++ 可观测性完全指南。
