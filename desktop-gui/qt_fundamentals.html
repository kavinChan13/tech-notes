Qt 核心机制完全指南

Qt 让人上手极快，也让人栽跟头极快——因为它在标准 C++ 之上加了三样东西：对象树（谁来 delete）、元对象系统（运行时反射与信号槽）、事件循环（谁在调度）。本篇把这三样从「怎么用」一路讲到「moc 生成了什么、QMetaObject::activate 干了什么、事件分发在哪一层落到 poll(2)」，让你既能写对，也能在崩溃时说得出为什么。

01

为什么是 Qt · 选型坐标

先搞清楚它到底是什么，再谈怎么用

很多人以为 Qt 是「一个 GUI 库」。更准确的说法是：Qt 是一套在 C++ 之上自建了运行时的应用框架，GUI 只是其中一个模块。它提供了标准库当年没有（部分现在也仍然没有）的东西：跨平台的线程/文件/网络/进程抽象、字符串与容器、序列化、插件加载、国际化、以及最核心的——对象间松耦合通信（信号槽）与运行时反射（元对象）。

把标准 C++ 想成毛坯房：水电结构齐全，但没有门窗家具。Qt 是一套精装方案，连同一套「自己的施工规范」（对象树谁负责拆、信号线怎么走、总闸在哪）。好处是拎包入住，代价是你必须按它的规范施工——用标准 C++ 的习惯去动 Qt 的结构，往往就是崩溃的来源。

工业检测、机器视觉这类场景几乎是 Qt 的主场，原因很实在：算法侧是 C++（OpenCV / Halcon / 相机 SDK 全是 C++ 接口），界面如果换语言就要跨语言封装一层；同时设备端要跑 Linux、开发机是 Windows，跨平台是硬需求；再加上高频刷新的图像显示对 GC 语言不友好。Qt 把这三点一次解决。

Qt 的许可，一句话讲清

  • LGPLv3：可用于闭源商业产品，但必须动态链接 Qt，并允许最终用户替换 Qt 库（提供 .o 文件或动态库 + 相应说明）。绝大多数公司走这条路。
  • GPLv3：部分模块（如 Qt Charts 在 Qt5 时代、部分工具）只给 GPL，用了就要开源。选型时必须逐模块确认，这是真实项目里最容易踩的合规坑。
  • 商业许可：可静态链接、不受传染，按开发者席位收费。嵌入式设备（单文件固件）通常被迫走这条。

03

QObject 与对象树

Qt 的第一套内存管理规范

对象树（Object Tree）：每个 QObject 可以有一个 parent 和任意多个 children。构造时把自己登记到 parent 的孩子列表；parent 析构时会依次 delete 所有 children；child 先于 parent 析构时会自动把自己从 parent 的列表里摘掉。这就是 Qt 在智能指针普及之前给出的所有权答案。
对象树像公司的组织架构：部门（parent）撤销时，下属岗位（children）一并撤销，不需要 HR 一个个通知；员工提前离职（child 先析构）也会自动从花名册里除名，不会留下幽灵工号。麻烦在于——如果一个人同时被登记在编制内（有 parent）又被你私下签了合同（栈对象 / unique_ptr），就会被「裁员」两次。

三条必须记住的规则

  1. 有 parent 的堆对象，不要自己 delete。交给 parent。
  2. 栈对象不要设 parent（除非你能保证它一定比 parent 先析构，而这通常不成立）。
  3. QObject 不可拷贝。拷贝构造和赋值都是 delete 的——因为身份（对象名、连接、父子关系）本身不可复制。想要值语义就用普通结构体，别继承 QObject。
❌ 栈对象混进对象树
void setup(QWidget* parent) {
    QLabel label("状态", parent);  // 挂到 parent
}   // label 在这里析构，从树里摘掉——看似没事

// 真正的坑是顺序反过来：
QWidget w;
QLabel label("x", &w);   // label 后声明 → 先析构，没问题
// 但若写成：
QLabel label2("y");
QWidget w2;
label2.setParent(&w2);      // w2 后声明 → 先析构
// w2 析构时 delete label2（栈地址）→ UB
✅ 堆对象交给对象树
void setup(QWidget* parent) {
    auto* label = new QLabel("状态", parent);
    label->setObjectName("statusLabel");
    // 不写 delete：parent 负责
}

// 没有合适 parent 时，用 Qt 自己的智能指针
std::unique_ptr<QWidget> detached{new QWidget};
// 或者需要"对象死了指针自动置空"时：
QPointer<QLabel> weak = label;
if (weak) weak->setText("ok");  // 安全

对象树 vs 智能指针：怎么共存

工具语义什么时候用
parent-child父独占子，父死子死默认选择：所有挂在窗口下的控件、属于某个管理对象的定时器/socket
std::unique_ptr作用域独占顶层窗口、没有自然 parent 的对象、工厂返回值
QPointer<T>弱引用，对象析构后自动变 nullptr缓存的「可能已经被别人删掉」的 QObject 指针；跨模块持有
QScopedPointerQt 版 unique_ptr（无移动）PIMPL 的 d_ptr，见工程化篇
std::shared_ptr<QObject>共享所有权基本别用：与对象树语义冲突，parent 会在 shared_ptr 还活着时 delete 掉对象
不要把有 parent 的 QObject 塞进 shared_ptr。两套所有权会同时认为自己负责释放：parent 析构先 delete，随后 shared_ptr 引用计数归零再 delete 一次。这类 double free 在 release 构建里常表现为「关闭窗口时随机崩溃」，堆栈还落在完全无关的地方——用 ASan 才看得清，参见 Crash 定位实战。

信号槽：从用法到 moc

C++ 里没有的东西，Qt 是怎么造出来的

信号槽（Signal & Slot）：一种发布-订阅式的对象间通信机制。发送方 emit 一个信号，完全不知道谁在接收；接收方把自己的成员函数（槽）连到该信号上。连接是运行时建立的，可动态增删，且类型在编译期检查（新语法下）。
信号槽像小区广播：广播站喊「快递到了」，不关心几户人在听；住户自己决定订不订这个频道，也可以随时退订。对比之下，传统回调是互相留手机号——发送方必须持有接收方的指针，两边就耦合死了。

基本写法：优先用新语法

class Camera : public QObject {
    Q_OBJECT                       // ← 必须：告诉 moc 处理这个类
public:
    explicit Camera(QObject* parent = nullptr) : QObject(parent) {}
    void grab() {
        QImage img = doGrab();
        emit frameReady(img);       // emit 只是个空宏，纯粹为了可读性
    }
signals:                           // signals 展开为 public（Qt6 起）
    void frameReady(const QImage& img);
    void errorOccurred(int code, const QString& msg);
};

// —— 连接 ——
// ✅ Qt5 新语法：函数指针，编译期检查签名，支持 lambda
connect(camera, &Camera::frameReady, viewer, &Viewer::render);

// ❌ Qt4 老语法：字符串，拼错只在运行时给一句 warning
connect(camera, SIGNAL(frameReady(QImage)), viewer, SLOT(render(QImage)));
对比项SIGNAL/SLOT 宏（老）函数指针（新，Qt5+）
错误发现时机运行时，仅打印一行 warning编译期报错
参数类型字符串必须逐字匹配（QImage 与 const QImage& 视为同一个，但 Camera::Mode 与 Mode 不是）支持隐式转换（int → double）
连 lambda不行可以
连普通函数 / 静态函数不行可以
重载信号天然支持（字符串带签名）要写 qOverload<int>(&Cls::sig) 消歧
槽必须声明在 slots: 下是否，任意成员函数都行
唯一还需要老语法的场景是重载信号且嫌 qOverload 啰嗦，以及 QML/脚本侧按名字动态连接。新代码一律用函数指针语法。

moc 到底做了什么

C++ 没有反射，而信号槽需要「运行时按名字/索引找到某个成员函数并调用」。Qt 的解法不是宏黑魔法，而是加一个代码生成步骤：moc（Meta-Object Compiler）扫描带 Q_OBJECT 的头文件，生成一个 moc_xxx.cpp 参与编译。

生成的信号函数体，去掉细节后长这样：

// moc_camera.cpp（简化示意）
void Camera::frameReady(const QImage& _t1) {
    void* _a[] = { nullptr, const_cast<void*>(static_cast<const void*>(&_t1)) };
    QMetaObject::activate(this, &staticMetaObject, 0, _a);
    //                                              ↑ 信号索引
}

所以「emit 一个信号」本质上就是把参数打包成 void* 数组，调用 QMetaObject::activate。activate 拿着信号索引去查该对象的连接列表，逐个决定：直接调用，还是打包成事件投递到别的线程。

性能：信号槽到底慢不慢

常见的说法是「信号槽比直接调用慢 10 倍」。这个数量级大致对：Direct connection 下一次 emit 的开销主要是读锁 + 遍历连接列表 + 一次间接分派，在现代 CPU 上是几十纳秒量级。

  • UI 交互、状态通知、每秒几千次以内的事件：完全不用考虑，可读性收益远大于开销。
  • 每帧每像素、每个数据包都 emit：会成为热点。做法是批量化——不要「每收到一帧 emit 一次」，而是「攒够 N 帧或到时间片再 emit 一次」，或者热路径直接用函数指针/std::function 回调，只在边界处发信号。
  • Queued connection 额外要付参数深拷贝 + 一次堆分配（QMetaCallEvent）+ 队列锁，比 Direct 贵一个量级。跨线程传大图像时要传隐式共享的类型（QImage/QByteArray 自带 COW，拷贝只是加引用计数）或者传智能指针，不要传 std::vector<uchar> 这种真拷贝的类型。
被问到「信号槽的开销」时，别只答「有点慢」。正确的回答结构是：Direct 连接的成本 = 锁 + 列表遍历 + 间接调用，几十纳秒；Queued 连接额外有参数拷贝和堆分配，量级更高。所以判断标准不是「信号槽慢不慢」，而是「这条路径的调用频率乘以单次开销，占不占预算」。再补一句工程做法：热路径批量化、跨线程传 COW 类型。
05

连接类型与线程语义

五个枚举值，决定了槽在哪个线程、什么时候跑

连接类型槽在哪个线程执行同步/异步典型用途 / 风险
AutoConnection（默认）同线程 → 发送方；跨线程 → 接收方视情况默认就够用。注意判定在 emit 时刻做
DirectConnection发送方线程（就是普通函数调用）同步强制同步；跨线程用它 = 在错误的线程里跑槽，data race
QueuedConnection接收方线程（经事件队列）异步跨线程通信标准手段；要求参数类型已注册
BlockingQueuedConnection接收方线程，发送方阻塞等待同步需要拿返回值的跨线程调用；同线程用它必死锁
UniqueConnection（标志位，可与上面按位或）——同一对 sender/signal/receiver/slot 只连一次，防重复连接导致槽执行两遍
AutoConnection 的判定时机是 emit 的那一刻，用 QThread::currentThread() 与 receiver->thread() 比较——不是 connect 的时刻。所以一个对象 moveToThread() 之后，之前建立的连接会自动从 Direct 变成 Queued，不需要重连。反过来说，如果你曾经手动写死 DirectConnection，moveToThread 之后它不会变，就成了跨线程直接调用——这是 Qt 多线程里最隐蔽的一类竞态。

QueuedConnection 的参数注册

Queued 连接要把参数存起来跨线程传递，所以 Qt 必须知道怎么拷贝和销毁这个类型。内置类型（int、QString、QImage…）已经注册好；自定义类型必须手动注册，否则运行时只给一行 warning，槽静默不执行——这个「不报错也不工作」的表现每年坑一批人。

❌ 自定义类型未注册
struct InspectResult { int id; double score; };

signals:
    void done(InspectResult r);

// 跨线程 emit → 控制台：
// QObject::connect: Cannot queue arguments
//   of type 'InspectResult'
// 槽根本不会被调用，程序不崩，静默丢事件
✅ 注册元类型
struct InspectResult { int id; double score; };
Q_DECLARE_METATYPE(InspectResult)   // 头文件里，命名空间外

int main(int argc, char** argv) {
    qRegisterMetaType<InspectResult>();   // main 里注册一次
    ...
}
// 类型必须：可默认构造、可拷贝构造、可析构

lambda 连接的悬垂陷阱

新语法允许把 lambda 当槽，非常方便，但lambda 不是 QObject，没有生命周期。连接只在 sender 析构时才自动断开——如果 lambda 捕获了别的对象而那个对象先死了，emit 时就是访问已释放内存。

❌ 没有 context object
connect(timer, &QTimer::timeout, [viewer]{
    viewer->refresh();   // viewer 可能已经 delete
});
// timer 活着 → 连接一直有效
// viewer 死了 → 每次 timeout 都是 UAF
✅ 传 context object
connect(timer, &QTimer::timeout, viewer, [viewer]{
    viewer->refresh();
});
// 第三个参数 = context：
//   ① viewer 析构时连接自动断开
//   ② lambda 在 viewer 所属线程执行

// 捕获非 QObject 时，用 QPointer 兜底
QPointer<Viewer> guard = viewer;
connect(timer, &QTimer::timeout, viewer, [guard]{
    if (guard) guard->refresh();
});
「connect 的第三个参数有什么用」是一道很好的分水岭题。只知道「可以省略」的是初学者；答得出「它是 context object，决定连接的生命周期和 lambda 的执行线程」的，才是真写过 Qt 多线程代码的人。

断开连接与 RAII

// connect 返回一个句柄，可用来精确断开
QMetaObject::Connection c = connect(camera, &Camera::frameReady,
                                    viewer,  &Viewer::render);
disconnect(c);

// 需要"作用域结束自动断开"时用 QScopedConnection 语义的包装：
struct ScopedConn {
    QMetaObject::Connection c;
    explicit ScopedConn(QMetaObject::Connection c_) : c(c_) {}
    ~ScopedConn() { QObject::disconnect(c); }
    ScopedConn(const ScopedConn&) = delete;
    ScopedConn& operator=(const ScopedConn&) = delete;
};

// 防重复连接：每次 connect 都带 UniqueConnection
connect(camera, &Camera::frameReady, viewer, &Viewer::render,
        Qt::UniqueConnection);
「点一次按钮，槽跑了三遍」几乎总是重复 connect。典型场景：在 showEvent、setModel、或某个「初始化」函数里 connect，而那个函数被调用了多次。排查手法：给槽加日志打 sender() 和调用次数，或者干脆在所有可能重入的地方统一加 Qt::UniqueConnection。

元对象系统与属性

C++ 的运行时反射，Qt 自己补上了

元对象系统（Meta-Object System）：由 Q_OBJECT 宏 + moc 生成的 QMetaObject 构成的运行时类型信息体系。它让你能在运行时问出这些问题：这个对象是什么类？有哪些属性、信号、方法？把名字为 "start" 的方法调一下。这是信号槽、QML 绑定、Qt Designer、序列化、脚本化的共同地基。
class Inspector : public QObject {
    Q_OBJECT
    Q_PROPERTY(double threshold READ threshold WRITE setThreshold NOTIFY thresholdChanged)
    Q_PROPERTY(QString deviceId READ deviceId CONSTANT)
public:
    double threshold() const { return m_threshold; }
    void setThreshold(double v) {
        if (qFuzzyCompare(v, m_threshold)) return;   // 必写：防止信号风暴
        m_threshold = v;
        emit thresholdChanged(v);
    }
    Q_INVOKABLE void reset();      // 可被 QML / invokeMethod 调用
signals:
    void thresholdChanged(double);
private:
    double m_threshold = 0.85;
};

// —— 运行时用法 ——
Inspector ins;
const QMetaObject* mo = ins.metaObject();
qDebug() << mo->className();                       // "Inspector"
ins.setProperty("threshold", 0.9);                  // 按名字写属性
qDebug() << ins.property("threshold").toDouble(); // 按名字读

// 按名字调方法（线程安全的跨线程调用也靠它）
QMetaObject::invokeMethod(&ins, "reset", Qt::QueuedConnection);

属性系统的三个真实用途

  • QML 数据绑定：QML 里写 text: inspector.threshold，能自动更新全靠 NOTIFY 信号。没写 NOTIFY 的属性在 QML 里是「读一次就不动」的死值。
  • 样式表选择器：QPushButton[status="error"] { color: red; }，配合 setProperty("status","error") + style()->polish(w) 做状态化换肤，比手写 setStyleSheet 干净得多。
  • 配置持久化与自动化测试：遍历 metaObject()->propertyCount() 就能把一个对象的全部可读写属性 dump 成 JSON，无需为每个类手写序列化。
qobject_cast 与 dynamic_cast 的区别：qobject_cast 沿着 staticMetaObject 的 superdata 链比较类名，不依赖 RTTI——所以在 -fno-rtti 编译、或者跨动态库边界（不同 so 里 typeinfo 可能不共享）时依然可靠，而且更快。代价是只能用于 QObject 派生类。C++ 侧各种 cast 的完整对比见 C++ 类型转换深度指南。
忘了 Q_OBJECT 宏的症状很有辨识度：编译通过、连接时 Qt 打印「no such signal」或者信号槽干脆不工作，metaObject()->className() 返回的是基类名。原因是没有 Q_OBJECT 就不生成 moc 文件，该类沿用基类的元对象。另一个变体是加了 Q_OBJECT 但构建系统没重跑 moc，表现为链接期 undefined reference to vtable for Camera——清一次构建目录即可。
07

事件系统与事件循环

Qt 程序的心脏

事件循环（Event Loop）：一个「取事件 → 分发 → 执行」的无限循环。QCoreApplication::exec() 启动它之后，鼠标点击、定时器到期、socket 可读、跨线程的槽调用，全都变成事件排队进来，由循环逐个取出交给目标对象处理。每个线程最多有一个事件循环，没有事件循环的线程收不到 Queued 信号、跑不了 QTimer。
事件循环像前台接待：所有访客（鼠标、键盘、网络数据、定时提醒）都到前台排队登记，接待员按顺序叫号，把人领到对应的办公室（目标 QObject）。如果某间办公室谈了 10 分钟（槽函数耗时），后面所有人都在大厅干等——这就是界面卡死的本质。

从 exec() 到 poll()

很多资料会说「Qt 在 Linux 上用 epoll」——不准确。Qt 自带的 QEventDispatcherUNIX 用的是 poll(2)；桌面 Linux 上默认启用的是 QEventDispatcherGlib，走 GLib 的 GMainContext，底层同样是 poll。这意味着 Qt 的事件分发是 O(n) 于 fd 数量的，管理成千上万个 socket 时会成为瓶颈——这类高并发服务端场景本来也不该用 Qt 的事件循环，该用 Asio/epoll，见 C++ 异步网络框架指南。

事件 vs 信号：两套机制，别搞混

事件（QEvent）信号（Signal）
方向发给某个对象（有明确接收者）对象发出的通知（不知道谁收）
来源多数由系统/框架产生（鼠标、绘制、定时器）多数由业务代码 emit
拦截可被 eventFilter 拦截、可 ignore() 后向父控件冒泡不可拦截，连上就会调
处理方式重写 event() 或具体的 xxxEvent()connect 一个槽
典型用途自定义控件行为、全局快捷键、输入法业务状态变化通知

两者也有交汇点：Queued connection 就是用事件实现的——跨线程 emit 时，Qt 把「调用哪个槽 + 参数副本」打包成一个 QMetaCallEvent，postEvent 到接收者线程的事件队列，由那边的事件循环取出后执行。

动手感受：sendEvent 与 postEvent 的区别

点按钮模拟不同的投递方式，看执行顺序。sendEvent 立即同步调用，postEvent 排队等事件循环下一轮。

耗时槽 = 界面冻结

UI 线程的事件循环被你的槽函数占住的每一毫秒，都是界面不响应的一毫秒。Windows 上超过 5 秒还会被系统标成「无响应」并给窗口蒙灰。

❌ 用 processEvents 硬撑
void Widget::onStart() {
    for (int i = 0; i < 100000; ++i) {
        heavyStep(i);
        // "让界面刷新一下"
        qApp->processEvents();
    }
}
// 问题：processEvents 会分发所有事件，
// 包括再次点击 Start → onStart 重入；
// 用户点关闭 → this 被 delete，
// 循环回来继续用 this → UAF
✅ 挪到工作线程
void Widget::onStart() {
    ui->startBtn->setEnabled(false);
    auto* w = new Worker;          // 无 parent
    auto* th = new QThread(this);
    w->moveToThread(th);
    connect(th, &QThread::started, w, &Worker::run);
    connect(w, &Worker::progress, this, &Widget::onProgress);
    connect(w, &Worker::finished, th, &QThread::quit);
    connect(w, &Worker::finished, w,  &QObject::deleteLater);
    connect(th, &QThread::finished, th, &QObject::deleteLater);
    th->start();
}
// 细节见「Qt 并发与跨线程」篇
processEvents() 是 Qt 里最危险的便利函数。它会在你的调用栈中间重新进入事件分发，导致三类问题：① 重入（同一个槽被再次触发）；② this 被删（用户在此期间关闭了窗口，返回后继续访问成员就是 UAF）；③ 状态不一致（函数执行到一半，外部改了你正在遍历的容器）。真要用，至少加 QEventLoop::ExcludeUserInputEvents 挡掉用户输入，并配合 QPointer 在返回后检查 this 是否还活着。正确做法始终是把耗时活儿挪出 UI 线程。

生命周期陷阱清单

线上崩溃的常客，按出现频率排序

#陷阱症状正确做法

deleteLater 的正确心智模型

// deleteLater 不是"稍后删"，而是：
//   往对象所在线程的事件队列投一个 DeferredDelete 事件，
//   等控制权回到那个线程的事件循环时才真正 delete。

void Session::onError() {
    emit failed();
    deleteLater();          // ✅ 安全：当前调用栈完整退出后才析构
    // delete this;         // ❌ 返回到 activate() 时对象已没了
}
deleteLater() 依赖事件循环。如果对象所在的线程没有跑事件循环（比如一个只做计算的 std::thread，或者 QThread 子类里 run() 没调 exec()），DeferredDelete 事件永远不会被处理，对象泄漏。这类泄漏用 Valgrind 能直接看到——排查手法见 C++ 内存泄漏体系化指南。
调试对象树的两个实用手段：QObject::dumpObjectTree() 打印以某对象为根的整棵树；dumpObjectInfo() 打印该对象的所有信号槽连接。定位「这个信号到底连了几个槽」时比断点快得多。给关键对象都 setObjectName()，输出才有可读性。

面试题集（12 道）

按难度分层，先自测再对照

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础信号槽和普通回调函数相比，优势和代价分别是什么？

    优势：发送方与接收方完全解耦——发送方不需要持有接收方的指针，也不需要知道对方的类型；一个信号可以连多个槽，一个槽也可以接多个信号；连接可以在运行时动态增删；接收方析构时连接自动断开，不会留下野回调。

    代价：需要继承 QObject、写 Q_OBJECT、引入 moc 这个额外的构建步骤；单次调用比直接函数调用慢一个量级（几十纳秒）；跨线程连接还有参数拷贝和堆分配开销。

    选型判断
    高频热路径（每帧每像素）用回调或直接调用；模块边界、状态通知、UI 交互用信号槽。
  2. 基础QObject 的父子关系（对象树）解决了什么问题？有 parent 的对象需要手动 delete 吗？

    解决的是 GUI 场景下大量小对象的所有权问题：一个窗口下有几十上百个控件，逐个管理生命周期既啰嗦又易错。对象树让 parent 在析构时自动 delete 全部 children，递归向下。

    不需要手动 delete，而且不应该——手动 delete 之后 child 会自动从 parent 的列表中摘除，所以单次手动 delete 不会 double free；但一旦和 shared_ptr 或栈对象混用，就会出现两套所有权同时释放的问题。

  3. 基础Q_OBJECT 宏做了什么？漏写会发生什么？

    它声明了元对象相关的成员：staticMetaObject、虚函数 metaObject()、qt_metacast()、qt_metacall()，并且是给 moc 的标记——moc 扫到它才会为这个类生成 moc_xxx.cpp（里面有元信息表、信号函数体、静态分派函数）。

    漏写的症状：编译能过，但该类没有自己的元对象，metaObject()->className() 返回基类名；自定义信号没有实现体，链接期报 undefined reference；用老语法 connect 时运行期报「no such signal」。

    变体
    加了宏但构建系统没重跑 moc，会报 undefined reference to vtable for X。清一次构建目录即可，不是代码问题。
  4. 基础为什么在槽函数里做耗时计算会让界面卡死？

    因为 GUI 事件（重绘、鼠标、键盘）都排在主线程的事件循环里，靠循环逐个取出分发。槽函数是被这个循环同步调用的——槽没返回，循环就取不到下一个事件，重绘请求得不到处理，界面就是冻住的。

    正确做法是把耗时工作交给工作线程（QThread + moveToThread、或 QtConcurrent::run），通过信号把进度和结果回传主线程。不要用 processEvents() 硬撑，它会引发重入和 UAF。

9.2 中级（区分熟练度）

  1. 中级五种连接类型分别是什么语义？AutoConnection 的判定发生在什么时候？
    • DirectConnection：在发送方线程同步调用，等价于普通函数调用。
    • QueuedConnection：打包成事件投递到接收方线程的队列，异步执行。
    • BlockingQueuedConnection：同上，但发送方阻塞等到槽执行完。同线程使用必然死锁。
    • AutoConnection（默认）：同线程走 Direct，跨线程走 Queued。
    • UniqueConnection：是个标志位，与上面按位或使用，保证同一组 sender/signal/receiver/slot 只连一次。
    关键细节
    Auto 的判定在 emit 时刻，用 QThread::currentThread() 与 receiver->thread() 比较，不是 connect 时刻。所以 moveToThread() 之后已有连接会自动改变行为，无需重连；反过来，写死 DirectConnection 的连接不会变，moveToThread 之后就变成了跨线程直接调用，是隐蔽的竞态源。
  2. 中级跨线程用信号槽传自定义结构体，为什么槽不执行？

    因为 Queued 连接需要把参数拷贝一份存进事件，Qt 必须通过元类型系统知道这个类型怎么构造、拷贝、析构。自定义类型没注册时，Qt 只在控制台打一行 QObject::connect: Cannot queue arguments of type 'X'，然后静默丢弃这次调用——不崩溃、不抛异常，所以特别难查。

    解决：头文件里 Q_DECLARE_METATYPE(X)（放在命名空间外），程序启动时 qRegisterMetaType<X>()。类型必须可默认构造、可拷贝构造、可析构。

    工程建议
    用 qInstallMessageHandler 把 Qt 的 warning 接进项目日志系统。很多「莫名其妙不工作」的 Qt 问题，答案就在那几行被忽略的 warning 里。
  3. 中级connect 用 lambda 时，第三个参数（context object）有什么用？不传会怎样？

    context object 有两个作用：① 生命周期绑定——context 析构时该连接自动断开；② 线程归属——lambda 在 context 所属的线程执行（配合 Auto 连接类型）。

    不传的话，连接只跟 sender 绑定。如果 lambda 捕获了别的对象而那个对象先析构，之后每次 emit 都是访问已释放内存；如果是跨线程 emit，lambda 还会在发送方线程执行，可能在工作线程里碰了 UI。

    写法
    connect(sender, &S::sig, receiver, [receiver]{ ... }); —— 只要 lambda 里用到了某个 QObject，就把它作为 context 传进去。
  4. 中级事件（QEvent）和信号（Signal）有什么本质区别？Queued 连接和事件是什么关系？

    方向不同：事件是「发给某个特定对象」的，有明确接收者，由事件循环分发；信号是「对象发出的通知」，发送方不知道谁在接收。

    可拦截性不同：事件可以被 eventFilter 拦下、可以 ignore() 后向父控件冒泡、可以重写 event() 统一处理；信号一旦连上就一定会调，无法拦截。

    关系：Queued connection 正是用事件实现的——跨线程 emit 时 Qt 把「槽 + 参数副本」打包成 QMetaCallEvent，postEvent 到接收者线程队列。所以「接收者线程没有事件循环」时，Queued 信号永远不会被执行。

9.3 高级（体现深度）

  1. 高级从 emit 到槽被调用，中间经过了哪些环节？moc 在其中扮演什么角色？
    1. emit 只是个空宏，展开后就是普通函数调用 frameReady(img)。
    2. 这个函数的实现体是 moc 生成的（你只写了声明）。它把参数地址装进一个 void* _a[] 数组，调用 QMetaObject::activate(this, &staticMetaObject, signalIndex, _a)。
    3. activate 加读锁，取出该对象在这个信号索引上的连接列表。
    4. 对每条连接判断连接类型（Auto 时比较线程）：Direct 就通过 qt_static_metacall 按槽索引 switch 到真实成员函数并传参；Queued 就深拷贝参数、构造 QMetaCallEvent、postEvent 到接收者线程。
    5. Queued 的那条路径，最终由接收者线程的事件循环取出事件，再执行同样的 qt_static_metacall 分派。
    moc 的角色
    C++ 没有反射，而信号槽需要「运行时按索引找到并调用一个成员函数」。moc 通过生成一张静态元信息表 + 一个 switch 分派函数把反射能力补上——本质是用代码生成换取运行时能力，而不是用宏或模板黑魔法。
  2. 高级qobject_cast 与 dynamic_cast 有什么区别？为什么 Qt 要自己造一个？

    dynamic_cast 依赖编译器生成的 RTTI（typeinfo），沿虚表指针找类型信息。qobject_cast 走的是 Qt 自己的元对象链：从对象的 metaObject() 出发，沿 superdata 指针逐级比较类名字符串。

    dynamic_castqobject_cast
    依赖 RTTI是否，-fno-rtti 也能用
    跨动态库可能失败（不同 so 的 typeinfo 未必合并）可靠
    适用类型任意多态类型仅 QObject 派生且带 Q_OBJECT
    速度较慢更快（简单的链表遍历）
    动机
    Qt 要支持插件化（跨 so 边界传对象）、要支持关掉 RTTI 的嵌入式构建，还要在热路径上频繁做类型判断（事件分发、样式系统）。这三点 dynamic_cast 都不理想，所以顺手用已有的元对象链自己实现了一个。
  3. 高级processEvents() 为什么危险？如果必须用，怎么用才相对安全？

    它在你的调用栈中间重新进入事件分发，等于把一段本该原子的逻辑劈成两半，中间插入了任意的用户操作。三类后果：

    重入
    用户再点一次按钮，同一个槽被递归触发，状态机被打乱。
    this 被删
    用户在这期间关闭窗口，processEvents 返回后你继续访问成员变量，就是 use-after-free。
    状态不一致
    你正在遍历的容器被另一个槽修改，迭代器失效。

    相对安全的用法：传 QEventLoop::ExcludeUserInputEvents 挡掉鼠标键盘；进入前用 QPointer<QObject> guard(this)，返回后先判 if (!guard) return;；把可能重入的按钮先 setEnabled(false)。

    但这些都是补丁。根治方案是把耗时逻辑挪出 UI 线程，或者把长任务切成小块用 QTimer::singleShot(0, ...) 分片调度——后者天然回到事件循环，不会重入当前栈帧。

  4. 高级Qt 的事件循环在 Linux 上底层用的是什么？它适合做高并发网络服务端吗？

    Qt 自带的 QEventDispatcherUNIX 用 poll(2)；桌面 Linux 上默认启用的是 QEventDispatcherGlib，走 GLib 的 GMainContext，底层同样是 poll。不是 epoll——这是一个常见的误答。

    因此 Qt 的 IO 多路复用是 O(n) 于 fd 数量：每轮都要把整个 fd 数组交给内核、返回后再线性扫描。几十上百个连接完全没问题（这正是客户端场景），但要管理上万连接就会在 poll 上耗掉大量 CPU。

    结论与替代
    Qt 的事件循环是为桌面/嵌入式客户端设计的：fd 少、事件类型杂（GUI + 定时器 + IO 混在一起）、需要与窗口系统集成。高并发服务端应该用 epoll/io_uring 或 Asio，见 异步网络框架指南。如果一个 Qt 应用确实要扛大量连接，常见架构是把网络层放到独立线程用 Asio/裸 epoll 跑，只通过 Queued 信号把结果送回 UI 线程。
