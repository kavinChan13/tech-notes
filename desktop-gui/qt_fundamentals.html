Qt 核心机制完全指南

Qt 让人上手极快，也让人栽跟头极快——因为它在标准 C++ 之上加了三样东西：对象树（谁来 delete）、元对象系统（运行时反射与信号槽）、事件循环（谁在调度）。本篇把这三样从「怎么用」一路讲到「moc 生成了什么、activate 干了什么、事件分发在哪一层落到 poll(2)」。

QObject 对象树 信号槽 · moc 元对象与属性 事件循环

01

为什么是 Qt · 选型坐标

先搞清楚它到底是什么，再谈怎么用

很多人以为 Qt 是「一个 GUI 库」。更准确的说法是：Qt 是一套在 C++ 之上自建了运行时的应用框架，GUI 只是其中一个模块。它补上了标准库当年没有（部分至今仍没有）的东西：跨平台的线程/文件/网络抽象、序列化、插件加载、国际化，以及最核心的——对象间松耦合通信（信号槽）与运行时反射（元对象）。

把标准 C++ 想成毛坯房：水电齐全，但没有门窗家具。Qt 是一套精装方案，附带「自己的施工规范」——对象树谁负责拆、信号线怎么走、总闸在哪。好处是拎包入住，代价是必须按它的规范施工：用标准 C++ 的习惯去动 Qt 的结构，往往就是崩溃的来源。

工业检测、机器视觉几乎是 Qt 的主场：算法侧本来就是 C++（OpenCV / Halcon / 相机 SDK 全是 C++ 接口），换语言就要多封装一层；设备端跑 Linux、开发机是 Windows；高频刷新的图像显示又对 GC 语言不友好。Qt 把这三点一次解决。

Qt 的许可，一句话讲清

  • LGPLv3：可用于闭源商业产品，但必须动态链接并允许最终用户替换 Qt 库。绝大多数公司走这条路。
  • GPLv3：部分模块与工具只给 GPL，用了就要开源。选型时必须逐模块确认，这是真实项目里最容易踩的合规坑。
  • 商业许可：可静态链接、不受传染，按席位收费。单文件固件的嵌入式设备通常被迫走这条。

03

QObject 与对象树

Qt 的第一套内存管理规范

对象树（Object Tree）：每个 QObject 可以有一个 parent 和任意多个 children，构造时自动登记进 parent 的孩子列表。parent 析构时会依次 delete 所有 children；child 先死则自动从列表里摘掉。这就是 Qt 在智能指针普及之前给出的所有权答案。
对象树像公司的组织架构：部门撤销时下属岗位一并撤销，不用 HR 一个个通知；员工提前离职也会自动从花名册除名。麻烦在于——一个人同时在编制内又被你私下签了合同，就会被「裁员」两次。

谁 delete 谁：最短示例

void setup(QWidget* parent) {
    auto* label = new QLabel("状态", parent);
    // ✅ 不写 delete：parent 析构时会 delete 它
}

// ❌ 经典坑：栈对象被设了 parent，析构顺序反过来
QLabel label("y");          // 先声明 → 后析构
QWidget w;                   // 后声明 → 先析构
label.setParent(&w);
// w 析构 → 对一个栈地址执行 delete → UB
// 反过来写（w 在前、label 在后）恰好能跑，但这是靠声明顺序活着

// QObject 不可拷贝：拷贝构造与赋值都是 = delete 的，
// 因为身份（对象名、连接、父子关系）本身复制不了。
// 想要值语义就用普通 struct，别继承 QObject。

工具语义什么时候用

信号槽：从用法到 moc

C++ 里没有的东西，Qt 是怎么造出来的

信号槽（Signal & Slot）：发布-订阅式的对象间通信。发送方 emit 信号，完全不知道谁在接收；接收方把自己的成员函数连上去。连接运行时建立、可动态增删，而签名在编译期检查（新语法下）。
信号槽像小区广播：广播站喊「快递到了」，不关心几户人在听，住户自己决定订不订、随时可退订。传统回调则是互相留手机号——发送方必须持有接收方的指针，两边耦合死。

四种连接写法，一次看完

class Camera : public QObject {
    Q_OBJECT                       // ← 必须：告诉 moc 处理这个类
signals:                           // signals 展开为 public（Qt6 起）
    void frameReady(const QImage& img);   // 只声明，实现由 moc 生成
};

// ① ❌ Qt4 老语法：签名是字符串，拼错只在运行时给一行 warning
connect(camera, SIGNAL(frameReady(QImage)), viewer, SLOT(render(QImage)));

// ② ✅ 函数指针：编译期检查签名，槽不必声明在 slots: 下
connect(camera, &Camera::frameReady, viewer, &Viewer::render);

// ③ ⚠️ 裸 lambda：只跟 sender 绑生命周期
connect(camera, &Camera::frameReady, [viewer](const QImage& im) {
    viewer->render(im);          // viewer 先死 → 每次 emit 都是 UAF
});

// ④ ✅ lambda + context object（第三个参数）——默认就该这么写
connect(camera, &Camera::frameReady, viewer, [viewer](const QImage& im) {
    viewer->render(im);
});
// context 同时决定两件事：viewer 析构 → 连接自动断开；
//                        lambda 在 viewer 所属线程执行。

// 重载信号在 ②③④ 下要消歧：qOverload<int>(&Cls::sig)
对比项SIGNAL/SLOT 宏（老）函数指针（新，Qt5+）
错误发现时机运行时，仅打印一行 warning编译期报错
参数类型字符串逐字匹配（Camera::Mode 与 Mode 不是同一个）支持隐式转换（int → double）
可连接的目标只能是 slots: 下的成员函数任意成员函数、普通函数、静态函数、lambda
重载信号天然支持（字符串自带签名）要写 qOverload<int>(&Cls::sig) 消歧
唯一还需要老语法的场景是 QML/脚本侧按名字动态连接。新代码一律用函数指针语法。

moc 到底做了什么

C++ 没有反射，而信号槽需要「运行时按索引找到某个成员函数并调用」。Qt 的解法不是宏黑魔法，而是加一个代码生成步骤：moc 扫描带 Q_OBJECT 的头文件，生成一个 moc_xxx.cpp 参与编译。构建侧怎么接线见 工程化 · CMake + AUTOMOC。

性能：信号槽到底慢不慢

「比直接调用慢 10 倍」这个数量级大致对，但它不是判断依据。正确的判据是「这条路径的调用频率 × 单次开销，占不占预算」：

  • Direct = 读锁 + 遍历连接列表 + 一次间接分派，现代 CPU 上几十纳秒。UI 交互、状态通知这类每秒几千次以内的路径完全不用考虑。
  • Queued 额外付参数深拷贝 + 一次堆分配 + 队列锁，比 Direct 贵一个量级。
  • 真成了热点就批量化：攒够 N 帧或到时间片再发，热路径内部用裸回调，只在模块边界发信号。跨线程传大图像要用 QImage/QByteArray 这类隐式共享（COW）类型，拷贝只是加引用计数。

连接类型与线程语义

五个枚举值，决定了槽在哪个线程、什么时候跑

默认的 AutoConnection 覆盖绝大多数场景，另外四个各解决一件具体的事：强制同步、强制异步、拿跨线程返回值、防重复连接。

判定发生在 emit 的那一刻，不是 connect 的时刻。所以 moveToThread() 之后，已有的 Auto 连接会自动从 Direct 变成 Queued；而你手动写死的 DirectConnection 不会变，就成了跨线程直接调用——Qt 多线程里最隐蔽的一类竞态。详见 Qt 并发与跨线程 · 线程亲和性。

Queued 连接为什么要注册元类型

跨线程直接改 UI：最常见的一类崩溃

❌ 在工作线程里碰 QWidget
void Worker::run() {
    for (auto& f : frames) {
        process(f);
        m_label->setText(tr("已处理 %1").arg(f.id));
        // ↑ QWidget 只能在 GUI 线程碰
        // 症状：偶发花屏 / 断言 / 崩在 QPainter 里
    }
}
✅ 发信号回主线程
void Worker::run() {
    for (auto& f : frames) {
        process(f);
        emit progress(f.id);   // 跨线程 → Auto 走 Queued
    }
}
// 主线程侧：label 的更新回到 GUI 线程的事件循环里做
connect(worker, &Worker::progress, label, [label](int id) {
    label->setText(QStringLiteral("已处理 %1").arg(id));
});
「点一次按钮，槽跑了三遍」几乎总是重复 connect。典型场景是在 showEvent、setModel 这种会被调多次的函数里连接。要么只在唯一入口连，要么统一加 Qt::UniqueConnection；需要精确断开就存下 connect 的返回值 QMetaObject::Connection。

元对象系统与属性

C++ 的运行时反射，Qt 自己补上了

元对象系统（Meta-Object System）：由 Q_OBJECT 宏 + moc 生成的 QMetaObject 构成的运行时类型信息体系。它让程序能在运行时问出「这个对象是什么类、有哪些属性和方法、把叫 start 的那个调一下」——信号槽、QML 绑定、Designer、序列化都建在它上面。

声明一个属性只要一行宏，剩下的全由 moc 填进元信息表——于是这个成员变量同时具备了「按名字读写」「QML 可绑定」「样式表可选择」三种能力：

class Inspector : public QObject {
    Q_OBJECT
    Q_PROPERTY(double threshold READ threshold WRITE setThreshold NOTIFY thresholdChanged)
    Q_PROPERTY(QString deviceId READ deviceId CONSTANT)   // 无 NOTIFY = 绑定不了
public:
    double threshold() const { return m_threshold; }
    void setThreshold(double v) {
        if (qFuzzyCompare(v, m_threshold)) return;   // 必写：防止信号风暴
        m_threshold = v;
        emit thresholdChanged(v);
    }
    Q_INVOKABLE void reset();      // 可被 QML / invokeMethod 按名字调用
signals:
    void thresholdChanged(double);
private:
    double m_threshold = 0.85;
};

// moc 把上面这些登记进 staticMetaObject，于是运行时可以：
ins.setProperty("threshold", 0.9);                     // 按名字写
ins.property("threshold").toDouble();                  // 按名字读
QMetaObject::invokeMethod(&ins, "reset", Qt::QueuedConnection);
qobject_cast 为什么不用 dynamic_cast：它沿 superdata 链比较类名，不依赖 RTTI，因此在 -fno-rtti 编译、跨动态库边界时依然可靠，而且更快。各种 cast 的对比见 C++ 类型转换深度指南。
忘了 Q_OBJECT 的症状很有辨识度：编译通过，但 className() 返回基类名、信号槽不工作——没有这个宏就不生成 moc 文件。变体是加了宏却没重跑 moc，报 undefined reference to vtable，清一次构建目录即可。

事件系统与事件循环

Qt 程序的心脏

事件循环（Event Loop）：一个「取事件 → 分发 → 执行」的无限循环。exec() 启动它之后，鼠标点击、定时器到期、socket 可读、跨线程槽调用全都变成事件排队进来。每个线程最多一个事件循环，没有它的线程收不到 Queued 信号、也跑不了 QTimer。
事件循环像前台接待：访客（鼠标、键盘、网络数据、定时提醒）都到前台排队，接待员按顺序叫号，领到对应的办公室（目标 QObject）。某间办公室谈了 10 分钟，后面所有人都在大厅干等——这就是界面卡死的本质。

从 exec() 到 poll()

「Qt 在 Linux 上用 epoll」是误传：QEventDispatcherUNIX 与桌面默认的 QEventDispatcherGlib 底层都是 poll(2)，也就是 O(n) 于 fd 数量。上万连接的服务端本来也该用 Asio/epoll，见 C++ 异步网络框架指南。

一个事件被送到目标手上，要过几道关

事件过滤器是 Qt 里性价比最高的一招：不继承、不改源码，就能改掉任意控件的行为。最短实现只有一个虚函数：

// 让某个 QLineEdit 吃掉回车键，改成"回车即提交"
bool Form::eventFilter(QObject* obj, QEvent* ev) {
    if (obj == m_edit && ev->type() == QEvent::KeyPress) {
        auto* k = static_cast<QKeyEvent*>(ev);
        if (k->key() == Qt::Key_Return) {
            submit();
            return true;      // 吃掉：QLineEdit 收不到这个键
        }
    }
    return QWidget::eventFilter(obj, ev);   // 其余交还给基类
}
// 安装：m_edit->installEventFilter(this);
// 装到 qApp 上就是全局过滤器，能看到程序里每一个事件。

事件 vs 信号：两套机制，别搞混

动手感受：sendEvent 与 postEvent 的区别

点按钮模拟不同的投递方式，看执行顺序。sendEvent 立即同步调用，postEvent 排队等事件循环下一轮。

耗时槽 = 界面冻结

槽函数是被事件循环同步调用的。槽没返回，循环就取不到下一个事件，重绘请求排在队里没人处理——界面于是冻住。Windows 上超过 5 秒还会被系统标成「无响应」并给窗口蒙灰。

别用 processEvents() 硬撑刷新，它是 Qt 里最危险的便利函数。它在你的调用栈中间重新进入事件分发，等于把一段本该原子的逻辑劈成两半、中间插入任意用户操作——重入、this 被删、容器被改，三样都可能。正确做法始终是把耗时活儿挪出 UI 线程，见 Qt 并发与跨线程 · moveToThread。

生命周期陷阱清单

线上崩溃的常客，按出现频率排序

#陷阱症状正确做法
1有 parent 的对象又被手动 delete / 放进 shared_ptr关窗口时随机崩溃，堆栈无关所有权二选一；QPointer 做弱引用
2栈对象 setParent出作用域后 parent 再 delete 一次栈对象不进对象树
3lambda 槽没传 context object对象死后 emit → UAF永远传第三个参数
4在槽里 delete this 或 delete sender返回 activate 继续遍历 → 崩用 deleteLater()
5重复 connect槽执行 N 次，数据被处理多遍Qt::UniqueConnection
6自定义类型未 qRegisterMetaType跨线程槽静默不执行注册 + 把 Qt warning 接进日志
7在非 UI 线程碰 QWidget偶发花屏 / 断言用信号回主线程再动 UI
8QObject 在 A 线程 new、在 B 线程用定时器不触发、Queued 走错线程moveToThread 明确归属
9循环 connect（A→B→A）信号无限递归，栈溢出setter 里先比较再 emit
10忘写 Q_OBJECT 或 moc 未重跑信号不工作 / vtable 未定义加宏 + 清构建目录

为什么槽里只能 deleteLater

只做计算的 std::thread、或者 run() 里没调 exec() 的 QThread 子类，都属于「没有事件循环」——在那种线程上 deleteLater() 等于泄漏。这类泄漏 Valgrind 能直接看到，排查手法见 C++ 内存泄漏体系化指南。
调试对象树的两个实用手段：dumpObjectTree() 打印以某对象为根的整棵树，dumpObjectInfo() 打印该对象的所有信号槽连接。定位「这个信号到底连了几个槽」比下断点快得多。前提是给关键对象都 setObjectName()，否则输出全是 QWidget 认不出来。

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础信号槽和普通回调函数相比，优势和代价分别是什么？

    优势：发送方与接收方完全解耦——发送方不需要持有接收方的指针，也不需要知道对方的类型；一个信号可以连多个槽，一个槽也可以接多个信号；连接可以在运行时动态增删；接收方析构时连接自动断开，不会留下野回调。

    代价：需要继承 QObject、写 Q_OBJECT、引入 moc 这个额外的构建步骤；单次调用比直接函数调用慢一个量级（几十纳秒）；跨线程连接还有参数拷贝和堆分配开销。

    选型判断
    高频热路径（每帧每像素）用回调或直接调用；模块边界、状态通知、UI 交互用信号槽。
  2. 基础QObject 的父子关系（对象树）解决了什么问题？有 parent 的对象需要手动 delete 吗？

    解决的是 GUI 场景下大量小对象的所有权问题：一个窗口下有几十上百个控件，逐个管理生命周期既啰嗦又易错。对象树让 parent 在析构时自动 delete 全部 children，递归向下。

    不需要手动 delete，而且不应该——手动 delete 之后 child 会自动从 parent 的列表中摘除，所以单次手动 delete 不会 double free；但一旦和 shared_ptr 或栈对象混用，就会出现两套所有权同时释放的问题。

  3. 基础Q_OBJECT 宏做了什么？漏写会发生什么？

    它声明了元对象相关的成员：staticMetaObject、虚函数 metaObject()、qt_metacast()、qt_metacall()，并且是给 moc 的标记——moc 扫到它才会为这个类生成 moc_xxx.cpp（里面有元信息表、信号函数体、静态分派函数）。

    漏写的症状：编译能过，但该类没有自己的元对象，metaObject()->className() 返回基类名；自定义信号没有实现体，链接期报 undefined reference；用老语法 connect 时运行期报「no such signal」。

    变体
    加了宏但构建系统没重跑 moc，会报 undefined reference to vtable for X。清一次构建目录即可，不是代码问题。
  4. 基础为什么在槽函数里做耗时计算会让界面卡死？

    因为 GUI 事件（重绘、鼠标、键盘）都排在主线程的事件循环里，靠循环逐个取出分发。槽函数是被这个循环同步调用的——槽没返回，循环就取不到下一个事件，重绘请求得不到处理，界面就是冻住的。

    正确做法是把耗时工作交给工作线程（QThread + moveToThread、或 QtConcurrent::run），通过信号把进度和结果回传主线程。不要用 processEvents() 硬撑，它会引发重入和 UAF。

9.2 中级（区分熟练度）

  1. 中级五种连接类型分别是什么语义？AutoConnection 的判定发生在什么时候？
    • DirectConnection：在发送方线程同步调用，等价于普通函数调用。
    • QueuedConnection：打包成事件投递到接收方线程的队列，异步执行。
    • BlockingQueuedConnection：同上，但发送方阻塞等到槽执行完。同线程使用必然死锁。
    • AutoConnection（默认）：同线程走 Direct，跨线程走 Queued。
    • UniqueConnection：是个标志位，与上面按位或使用，保证同一组 sender/signal/receiver/slot 只连一次。
    关键细节
    Auto 的判定在 emit 时刻，用 QThread::currentThread() 与 receiver->thread() 比较，不是 connect 时刻。所以 moveToThread() 之后已有连接会自动改变行为，无需重连；反过来，写死 DirectConnection 的连接不会变，moveToThread 之后就变成了跨线程直接调用，是隐蔽的竞态源。
  2. 中级跨线程用信号槽传自定义结构体，为什么槽不执行？

    因为 Queued 连接需要把参数拷贝一份存进事件，Qt 必须通过元类型系统知道这个类型怎么构造、拷贝、析构。自定义类型没注册时，Qt 只在控制台打一行 QObject::connect: Cannot queue arguments of type 'X'，然后静默丢弃这次调用——不崩溃、不抛异常，所以特别难查。

    解决：头文件里 Q_DECLARE_METATYPE(X)（放在命名空间外），程序启动时 qRegisterMetaType<X>()。类型必须可默认构造、可拷贝构造、可析构。

    工程建议
    用 qInstallMessageHandler 把 Qt 的 warning 接进项目日志系统。很多「莫名其妙不工作」的 Qt 问题，答案就在那几行被忽略的 warning 里。
  3. 中级connect 用 lambda 时，第三个参数（context object）有什么用？不传会怎样？

    context object 有两个作用：① 生命周期绑定——context 析构时该连接自动断开；② 线程归属——lambda 在 context 所属的线程执行（配合 Auto 连接类型）。

    不传的话，连接只跟 sender 绑定。如果 lambda 捕获了别的对象而那个对象先析构，之后每次 emit 都是访问已释放内存；如果是跨线程 emit，lambda 还会在发送方线程执行，可能在工作线程里碰了 UI。

    写法
    connect(sender, &S::sig, receiver, [receiver]{ ... }); —— 只要 lambda 里用到了某个 QObject，就把它作为 context 传进去。
  4. 中级事件（QEvent）和信号（Signal）有什么本质区别？Queued 连接和事件是什么关系？

    方向不同：事件是「发给某个特定对象」的，有明确接收者，由事件循环分发；信号是「对象发出的通知」，发送方不知道谁在接收。

    可拦截性不同：事件可以被 eventFilter 拦下、可以 ignore() 后向父控件冒泡、可以重写 event() 统一处理；信号一旦连上就一定会调，无法拦截。

    关系：Queued connection 正是用事件实现的——跨线程 emit 时 Qt 把「槽 + 参数副本」打包成 QMetaCallEvent，postEvent 到接收者线程队列。所以「接收者线程没有事件循环」时，Queued 信号永远不会被执行。

9.3 高级（体现深度）

  1. 高级从 emit 到槽被调用，中间经过了哪些环节？moc 在其中扮演什么角色？
    1. emit 只是个空宏，展开后就是普通函数调用 frameReady(img)。
    2. 这个函数的实现体是 moc 生成的（你只写了声明）。它把参数地址装进一个 void* _a[] 数组，调用 QMetaObject::activate(this, &staticMetaObject, signalIndex, _a)。
    3. activate 加读锁，取出该对象在这个信号索引上的连接列表。
    4. 对每条连接判断连接类型（Auto 时比较线程）：Direct 就通过 qt_static_metacall 按槽索引 switch 到真实成员函数并传参；Queued 就深拷贝参数、构造 QMetaCallEvent、postEvent 到接收者线程。
    5. Queued 的那条路径，最终由接收者线程的事件循环取出事件，再执行同样的 qt_static_metacall 分派。
    moc 的角色
    C++ 没有反射，而信号槽需要「运行时按索引找到并调用一个成员函数」。moc 通过生成一张静态元信息表 + 一个 switch 分派函数把反射能力补上——本质是用代码生成换取运行时能力，而不是用宏或模板黑魔法。
  2. 高级qobject_cast 与 dynamic_cast 有什么区别？为什么 Qt 要自己造一个？

    dynamic_cast 依赖编译器生成的 RTTI（typeinfo），沿虚表指针找类型信息。qobject_cast 走的是 Qt 自己的元对象链：从对象的 metaObject() 出发，沿 superdata 指针逐级比较类名字符串。

    dynamic_castqobject_cast
    依赖 RTTI是否，-fno-rtti 也能用
    跨动态库可能失败（不同 so 的 typeinfo 未必合并）可靠
    适用类型任意多态类型仅 QObject 派生且带 Q_OBJECT
    速度较慢更快（简单的链表遍历）
    动机
    Qt 要支持插件化（跨 so 边界传对象）、要支持关掉 RTTI 的嵌入式构建，还要在热路径上频繁做类型判断（事件分发、样式系统）。这三点 dynamic_cast 都不理想，所以顺手用已有的元对象链自己实现了一个。
  3. 高级processEvents() 为什么危险？如果必须用，怎么用才相对安全？

    它在你的调用栈中间重新进入事件分发，等于把一段本该原子的逻辑劈成两半，中间插入了任意的用户操作。三类后果：

    重入
    用户再点一次按钮，同一个槽被递归触发，状态机被打乱。
    this 被删
    用户在这期间关闭窗口，processEvents 返回后你继续访问成员变量，就是 use-after-free。
    状态不一致
    你正在遍历的容器被另一个槽修改，迭代器失效。

    相对安全的用法：传 QEventLoop::ExcludeUserInputEvents 挡掉鼠标键盘；进入前用 QPointer<QObject> guard(this)，返回后先判 if (!guard) return;；把可能重入的按钮先 setEnabled(false)。

    但这些都是补丁。根治方案是把耗时逻辑挪出 UI 线程，或者把长任务切成小块用 QTimer::singleShot(0, ...) 分片调度——后者天然回到事件循环，不会重入当前栈帧。

  4. 高级Qt 的事件循环在 Linux 上底层用的是什么？它适合做高并发网络服务端吗？

    Qt 自带的 QEventDispatcherUNIX 用 poll(2)；桌面 Linux 上默认启用的是 QEventDispatcherGlib，走 GLib 的 GMainContext，底层同样是 poll。不是 epoll——这是一个常见的误答。

    因此 Qt 的 IO 多路复用是 O(n) 于 fd 数量：每轮都要把整个 fd 数组交给内核、返回后再线性扫描。几十上百个连接完全没问题（这正是客户端场景），但要管理上万连接就会在 poll 上耗掉大量 CPU。

    结论与替代
    Qt 的事件循环是为桌面/嵌入式客户端设计的：fd 少、事件类型杂（GUI + 定时器 + IO 混在一起）、需要与窗口系统集成。高并发服务端应该用 epoll/io_uring 或 Asio，见 异步网络框架指南。如果一个 Qt 应用确实要扛大量连接，常见架构是把网络层放到独立线程用 Asio/裸 epoll 跑，只通过 Queued 信号把结果送回 UI 线程。
