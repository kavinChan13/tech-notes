01

CMake + AUTOMOC 构建

Qt6 之后的唯一正解

AUTOMOC / AUTOUIC / AUTORCC：CMake 的三个开关，让它自动帮你跑 Qt 的三个代码生成器——moc（处理 Q_OBJECT）、uic（把 Designer 的 .ui 转成头文件）、rcc（把资源打进二进制）。开了之后你不需要在 CMakeLists 里手写任何生成规则。
cmake_minimum_required(VERSION 3.21)
project(vision_inspector LANGUAGES CXX)

# Qt6 强制 C++17；用 20 也可以
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# 三个自动化开关（Qt6 也可用 qt_standard_project_setup() 一次性打开）
set(CMAKE_AUTOMOC ON)
set(CMAKE_AUTOUIC ON)
set(CMAKE_AUTORCC ON)

# 同时支持 Qt5 / Qt6 的写法
find_package(QT NAMES Qt6 Qt5 REQUIRED COMPONENTS Widgets Network Concurrent)
find_package(Qt${QT_VERSION_MAJOR} REQUIRED COMPONENTS Widgets Network Concurrent)

qt_add_executable(vision_inspector          # Qt6 的封装，会处理部署相关的额外步骤
    src/main.cpp
    src/mainwindow.cpp src/mainwindow.h src/mainwindow.ui
    resources/app.qrc
)
target_link_libraries(vision_inspector PRIVATE
    Qt${QT_VERSION_MAJOR}::Widgets
    Qt${QT_VERSION_MAJOR}::Network
    Qt${QT_VERSION_MAJOR}::Concurrent
)
# Windows 下不弹控制台；macOS 生成 .app
set_target_properties(vision_inspector PROPERTIES
    WIN32_EXECUTABLE ON
    MACOSX_BUNDLE ON
)
问题原因处理
undefined reference to vtable for X加了 Q_OBJECT 但 moc 没跑（头文件不在 target 的源文件列表里）把 .h 也列进 qt_add_executable，AUTOMOC 只扫描 target 里列出的文件
改一个头文件全项目重编公共头文件里塞了太多东西 / 没用 PIMPL见 §5；另外 CMAKE_UNITY_BUILD 与 ccache 都能显著提速
moc 生成的文件找不到CMAKE_INCLUDE_CURRENT_DIR 没开（Qt5 时代常见）Qt6 的 qt_add_executable 已处理；Qt5 手动 set(CMAKE_INCLUDE_CURRENT_DIR ON)
把 moc_x.cpp 手动 #include 进 cpp老代码遗留习惯用 AUTOMOC 后不要再手动 include，会重复定义。例外：类定义写在 .cpp 里时，末尾要 #include "x.moc"
为什么把类定义写在 .cpp 里就要手动 #include "x.moc"？因为 AUTOMOC 对头文件生成的是 moc_x.cpp（自动加入构建），对源文件里发现的 Q_OBJECT 生成的是 x.moc（不会自动加入构建，需要你在该 cpp 末尾 include）。这是 Qt 构建里最容易卡住新人半小时的一个规则。CMake 本身的现代写法见 Modern CMake 深入。
qmake 不要在新项目里用了。Qt6 官方主推 CMake，qmake 仅保留兼容且已停止演进。存量 .pro 项目迁移时注意：SOURCES/HEADERS/FORMS 直接映射到 qt_add_executable 的文件列表；QT += widgets network 映射到 find_package 的 COMPONENTS 与 target_link_libraries；DEFINES 映射到 target_compile_definitions。真正麻烦的是自定义的 QMAKE_EXTRA_COMPILERS，要改写成 add_custom_command。
02

Widgets 与 QML 选型

一个影响三年的决定

Widgets 像装修好的标准间：桌椅床柜都是现成的，摆一摆就能住，风格跟着酒店（操作系统）走。QML 像毛坯 loft + 设计师：想做什么造型都行，动效随便加，但家具得自己设计，而且要通水电（GPU 驱动）。
维度Qt WidgetsQt Quick / QML
典型场景工业软件、仪器上位机、CAD、数据密集型表单车机 HMI、触摸屏、移动端、动效重的产品
复杂表格 / 树成熟：QTableView + 模型视图，几十万行没问题TableView 相对年轻，复杂交互要自己补
动效要手写 QPropertyAnimation，做复杂了很累一等公民，几行声明搞定
GPU 依赖无（软件光栅化）有——老工控机、远程桌面、虚拟机上可能降级或黑屏
与 C++ 的边界没有边界，全是 C++要设计 C++ 与 QML 的接口（属性、Q_INVOKABLE、模型暴露）
调试普通 C++ 调试QML 侧是解释执行，错误多在运行时才暴露
团队要求C++ 工程师即可需要有人熟 QML/JS，否则容易写成「JS 里塞业务逻辑」
无障碍 / 输入法成熟较弱
工业检测这类场景，默认选 Widgets。三条理由值得在面试时讲出来：① 界面主体是图像显示 + 参数表格 + 结果列表，Widgets 的模型视图体系正好对口；② 工控机显卡驱动往往老旧，还经常通过远程桌面操作，GPU 渲染是可靠性风险而不是收益；③ 团队大概率是 C++ 背景，引入 QML 等于引入第二套语言与调试链。反过来，如果产品是带触摸屏的一体机、要做酷炫动效，QML 才是对的。
两者可以混用：QQuickWidget 把 QML 场景嵌进 Widgets 窗口，QWidget::createWindowContainer 反过来嵌。但混用意味着两套渲染路径共存，层叠、缩放、输入法都会有边界问题，不到必要不要开这个口子。

模型视图与大数据量

十万行表格为什么卡，怎么不卡

模型/视图（Model/View）：Qt 把「数据」与「显示」分开——QAbstractItemModel 提供数据，QTableView/QListView/QTreeView 负责显示，QItemDelegate 负责单元格的绘制与编辑。视图只向模型索取当前可见的那些格子，这就是它能扛大数据量的根本原因。
QTableWidget 像把整本书全部打印出来铺在桌上——十万行就是十万个 widget 对象。QTableView + 模型像电子阅读器：书还在存储里，屏幕上只渲染当前这一页，翻到哪读到哪。

动手感受：全量渲染 vs 按需渲染

同样是 5 万行数据。「全量」会真的创建 5 万个 DOM 节点（等价于 QTableWidget 的做法），点击后能明显感到卡顿；「按需」只渲染可视区域的约 8 行（等价于 QTableView + 模型），瞬间完成。注意看创建节点数与耗时。

模式：按需渲染 · 已创建节点 0 · 耗时 0 ms

自定义模型的最小实现

class DefectModel : public QAbstractTableModel {
    Q_OBJECT
public:
    int rowCount(const QModelIndex& p = {}) const override {
        return p.isValid() ? 0 : m_rows.size();     // 表格模型：父索引有效时返回 0
    }
    int columnCount(const QModelIndex& = {}) const override { return 5; }

    QVariant data(const QModelIndex& ix, int role) const override {
        if (!ix.isValid()) return {};
        const Defect& d = m_rows[ix.row()];
        switch (role) {
        case Qt::DisplayRole:   return displayFor(d, ix.column());
        case Qt::ForegroundRole: return d.critical ? QColor(Qt::red) : QVariant{};
        case Qt::UserRole:      return d.id;    // 给代码用的原始值
        default: return {};
        }
    }
    // ★ 批量追加：必须用 begin/end 包住，否则视图状态错乱
    void append(const QVector<Defect>& batch) {
        if (batch.isEmpty()) return;
        beginInsertRows({}, m_rows.size(), m_rows.size() + batch.size() - 1);
        m_rows += batch;
        endInsertRows();
    }
private:
    QVector<Defect> m_rows;
};
症状根因处理
几万行就卡到不能用用了 QTableWidget（每格一个 widget 对象）换 QTableView + 自定义模型
加载时 UI 冻结几秒一次性 insertRow 几万次，每次都触发视图更新批量 beginInsertRows 一次包住；或用 QSortFilterProxyModel 的 setDynamicSortFilter(false) 临时关排序
滚动时掉帧data() 里做了昂贵计算（格式化、查数据库）data() 必须是 O(1) 且无 IO；预计算好放在内存里
列宽自适应导致卡顿resizeColumnsToContents() 要遍历所有行用 setSectionResizeMode(QHeaderView::Interactive) 或只按可见行估算
行高不一致时滚动条乱跳视图需要遍历全部行算总高setUniformRowHeights(true)（QTreeView）/ 固定行高
增量刷新后选中项丢失用了 reset() 而不是精确的 insert/remove 信号用 beginInsertRows/dataChanged 精确通知
data() 是性能的绝对热点。视图每次重绘、每次滚动、每个可见格子、每个 role 都会调它——一屏 200 个格子 × 5 个 role = 1000 次调用，每秒 60 帧就是 6 万次。在里面做字符串格式化（QString::number、arg()）都可能成为瓶颈，做数据库查询更是灾难。规则：data() 里只能查表和返回，任何计算都提前做好。

图像显示的性能路径

机器视觉上位机的核心问题

工业检测的界面主体往往是「一张几千万像素的图 + 叠加的缺陷标注 + 实时刷新」。这条路径上有三个容易踩的坑。

坑一：在 paintEvent 里缩放原图

❌ 每帧缩放全图
void ImageView::paintEvent(QPaintEvent*) {
    QPainter p(this);
    // 5000×4000 的图缩到 800×600，每帧都算一次
    p.drawPixmap(rect(), m_pixmap);
}
// 20 MPix 的双线性缩放 ≈ 几十 ms，
// 直接把帧率压到个位数
✅ 缓存缩放结果
void ImageView::setImage(const QImage& img) {
    m_src = img;
    m_cacheDirty = true;
    update();
}
void ImageView::paintEvent(QPaintEvent*) {
    if (m_cacheDirty || m_cache.size() != size()) {
        m_cache = QPixmap::fromImage(
            m_src.scaled(size(), Qt::KeepAspectRatio,
                         Qt::FastTransformation));  // 预览用快速插值
        m_cacheDirty = false;
    }
    QPainter p(this);
    p.drawPixmap(0, 0, m_cache);
    drawOverlays(p);   // 标注画在缓存之上，标注变化不需要重缩放
}

坑二：QImage 与 QPixmap 用反了

QImageQPixmap
存储纯内存位图，格式明确可能是窗口系统资源（X11 Pixmap / GDI）
线程可在任意线程使用只能主线程
像素访问bits() / scanLine() 直接改不能直接访问
绘制到屏幕较慢（可能要转换）快，为显示优化
该用在算法处理、跨线程传递、文件读写最终显示那一步
正确的分工：工作线程全程用 QImage 做算法；通过 Queued 信号传回 UI 线程（QImage 隐式共享，跨线程传递只是原子加引用计数，不会深拷贝几十 MB）；UI 线程再 QPixmap::fromImage() 一次并缓存。另外要注意像素格式：QImage::Format_RGB32 / Format_ARGB32_Premultiplied 与屏幕格式一致时绘制最快，用 Format_RGB888 每次绘制都要转换。

坑三：全量重绘而不是脏区重绘

// ❌ 任何变化都重画整个控件
update();

// ✅ 只重画变化的那块
update(defectRect.adjusted(-2, -2, 2, 2));   // 留出边框宽度

// paintEvent 里也要利用脏区裁剪
void ImageView::paintEvent(QPaintEvent* e) {
    QPainter p(this);
    p.setClipRegion(e->region());          // 只画需要的部分
    for (const auto& d : m_defects)
        if (e->region().intersects(d.rect))  // 跳过不可见的标注
            drawDefect(p, d);
}
性能问题不要靠猜。Qt 侧可以用 QElapsedTimer 直接量 paintEvent 耗时并打日志；系统侧用 perf 火焰图看热点函数——大多数「界面卡」最后都定位到 QImage::scaled、QPainter::drawText（大量小文本）或者模型的 data()。方法论见 C++ 性能优化方法论。

D-Pointer 与 ABI 治理

Qt 自己怎么做到二十年不破坏 ABI

D-Pointer（PIMPL）：把类的所有数据成员搬到一个前向声明的私有实现类里，公开类只保留一个指向它的指针。公开类的大小与内存布局从此固定，往实现类里增删成员不会改变 ABI，动态库可以只换 .so 不重编译调用方。
D-Pointer 像公司前台：外面的人只认识前台一个人（指针），后面办公室怎么增减工位、部门怎么重组，访客完全无感。如果没有前台，每次内部调整都得给所有合作方发通知「我们的门牌号变了」——那就是 ABI 破坏。
// camera.h —— 对外头文件，不暴露任何实现细节
class CameraPrivate;                       // 前向声明即可

class VISION_EXPORT Camera : public QObject {
    Q_OBJECT
public:
    explicit Camera(QObject* parent = nullptr);
    ~Camera() override;                     // ★ 必须在 .cpp 里定义
    bool open(const QString& id);
private:
    QScopedPointer<CameraPrivate> d;       // Qt 风格；std::unique_ptr 也可以
    Q_DECLARE_PRIVATE(Camera)              // 生成 d_func() 便捷访问
};

// camera.cpp
class CameraPrivate {
public:
    QString  id;
    QTimer   poll;
    int      retries = 0;      // 随便加，不影响 ABI
};
Camera::Camera(QObject* p) : QObject(p), d(new CameraPrivate) {}
Camera::~Camera() = default;         // 此处 CameraPrivate 已是完整类型
析构函数必须在 .cpp 里定义。如果在头文件里写 ~Camera() = default;，编译器会在调用方的翻译单元生成析构代码——而那里 CameraPrivate 只有前向声明，是不完整类型。unique_ptr 会报 invalid application of 'sizeof' to an incomplete type；更糟的是某些编译器只给一个警告，然后生成「delete 不完整类型」的代码——不调用析构函数，静默泄漏。同样的规则适用于移动构造/移动赋值。

什么时候值得用，什么时候是过度设计

场景用 D-Pointer？理由
对外发布的动态库 / SDK值得ABI 稳定是核心诉求，客户不可能陪你重编译
插件接口值得插件与宿主可能用不同版本编译
大型项目里被上百个文件 include 的公共头值得不为 ABI，为编译速度：改实现不再触发全量重编
应用内部的普通类不值得整个应用一起编译，没有 ABI 问题；平白多一层间接和堆分配
性能热点上的小对象不要额外的指针跳转会破坏缓存局部性
Qt 自己几乎所有公开类都用了 D-Pointer，这是它能在 Qt5 整个大版本内保持二进制兼容的关键。C++ ABI 的完整规则——哪些改动会破坏 ABI、内联函数的陷阱、符号可见性控制——见 C++ ABI 兼容性完全指南与 大型 C++ 工程化与 API/ABI 治理。

部署与打包

「我这儿好好的」的终结者

# Windows：把 Qt 依赖收集到 exe 旁边
windeployqt --release --no-translations --compiler-runtime build/vision_inspector.exe

# Linux：linuxdeployqt 或 CQtDeployer（Qt 官方对 Linux 支持较弱）
linuxdeployqt build/vision_inspector -appimage -qmake=/opt/Qt/6.5/gcc_64/bin/qmake

# macOS
macdeployqt build/vision_inspector.app -dmg
现场症状缺什么处理
启动即报 could not find or load the Qt platform plugin "windows"/"xcb"缺 platforms/ 目录下的平台插件这是最经典的部署错误。插件必须放在 exe 旁的 platforms/ 子目录，不能只放 exe 同级
界面能开，但所有 JPG/PNG 图标不显示缺 imageformats/ 插件windeployqt 通常会带，手动打包时容易漏
HTTPS 全部失败，HTTP 正常缺 OpenSSL 运行库拷 libssl-*.dll / libcrypto-*.dll；用 QSslSocket::supportsSsl() 在启动时自检
中文变方块缺字体 / 缺 QT_QPA_FONTDIR（嵌入式）嵌入式 Linux 上把字体打进 rootfs 或程序资源
数据库连不上缺 sqldrivers/ 插件同上，插件目录结构不能改
换台机器就崩，堆栈全是问号混用了不同 Qt 版本或不同编译器的库Qt 库、第三方库、你的程序必须同一套工具链；MSVC 与 MinGW 的库绝不能混
交付前用干净的虚拟机（全新系统、没装过 Qt、没装 VC++ 运行库）跑一遍安装包，这是唯一可靠的验证方式。开发机上装了 Qt、装了各种运行库，程序会「意外地」找到它们，掩盖掉打包缺失。有条件的话把这一步做进 CI：容器里装最小系统，跑安装 + 启动 + 截图。CI 实践见 现代 CMake + 包管理 + CI 完全指南。
许可合规不是法务的事，是选型时就要定的事。LGPLv3 要求动态链接并允许最终用户替换 Qt 库——所以静态链接 Qt 做单文件 exe，除非买了商业许可，否则是违规的。另外部分模块（历史上的 Qt Charts、Qt Data Visualization 等）只提供 GPL，用了就要开源整个产品。项目启动时就应该逐模块确认许可，等产品要发布了才发现用了 GPL 模块，代价极高。

高 DPI · i18n · 样式

交付质量的三个细节维度

高 DPI

  • Qt 6 默认启用高 DPI 缩放，Qt 5 需要 QApplication::setAttribute(Qt::AA_EnableHighDpiScaling)（5.6+）。
  • 不要写死像素。用布局（QLayout）而不是绝对坐标；确实需要固定尺寸时，用 fontMetrics().height() 或 logicalDpiX() 换算。
  • 图标要提供 @2x 版本，或者直接用 SVG（QIcon 支持 SVG，自动按 DPI 渲染），这是最省事的做法。
  • 工业现场常见「一台 4K 主屏 + 一台 1080p 副屏」，窗口在两屏间拖动时 DPI 会变——测试时一定要覆盖这个场景。

国际化

// ✅ 所有面向用户的字符串都包 tr()
ui->statusLabel->setText(tr("检测完成，共 %1 个缺陷").arg(count));

// ❌ 用字符串拼接，翻译时语序无法调整
ui->statusLabel->setText(tr("检测完成，共 ") + QString::number(count) + tr(" 个缺陷"));

// 需要区分单复数时用 tr 的第三个参数
tr("%n defect(s) found", "", count);
tr() 的参数必须是字面量——lupdate 是静态扫描源码提取字符串的，tr(someVariable) 提取不到。动态字符串要用 QT_TR_NOOP 标记 + 运行时 tr() 查表。另外 %1 占位符的写法允许翻译者调整语序，这正是不能用拼接的原因。

样式表的性能陷阱

QSS（Qt Style Sheet）好用但不便宜。给一个控件设 setStyleSheet() 会导致它和所有子控件重新解析样式、重新计算；在 paintEvent 或高频信号里调 setStyleSheet 是性能灾难。正确做法是「设一次样式，用属性切状态」。
// 启动时设一次
qApp->setStyleSheet("QLabel[level=\"error\"] { color: red; font-weight: bold; }");

// 运行时只改属性 + 触发重新 polish
label->setProperty("level", "error");
label->style()->unpolish(label);
label->style()->polish(label);

这比反复 setStyleSheet 快一个数量级，而且样式集中在一处，可维护性也更好。

陷阱总清单

四篇 Qt 内容的速查索引

类别陷阱一句话对策

面试题集（12 道）

按难度分层，先自测再对照

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础QTableWidget 和 QTableView 有什么区别？几万行数据该用哪个？

    QTableWidget 是「便利类」：数据直接存在视图里，每个单元格是一个 QTableWidgetItem 对象。几万行 × 几列就是几十万个对象，内存和构造耗时都不可接受。

    QTableView 是模型/视图架构：数据在你自己的 QAbstractTableModel 里，视图只向模型索取当前可见的那些格子。滚动到哪取到哪，行数对性能几乎没有影响。

    选择标准
    几十行的固定配置表用 QTableWidget 省事；数据量不确定或超过几百行，一律用 QTableView + 自定义模型。
  2. 基础QImage 和 QPixmap 该怎么选？

    QImage 是纯内存位图，格式明确、可以直接访问像素、可以在任意线程使用。QPixmap 是为显示优化的图像，可能是窗口系统的资源（X11 Pixmap、GDI 对象），只能在主线程使用，但绘制到屏幕更快。

    标准分工
    算法处理、跨线程传递、文件读写用 QImage；最终显示那一步再 QPixmap::fromImage()，并且这一步必须在 UI 线程。
    性能细节
    像素格式与屏幕不一致时每次绘制都要转换。显示路径上优先用 Format_RGB32 或 Format_ARGB32_Premultiplied。
  3. 基础什么是 AUTOMOC？为什么会出现 undefined reference to vtable？

    CMAKE_AUTOMOC 让 CMake 自动扫描 target 的源文件，发现 Q_OBJECT 就调用 moc 生成 moc_xxx.cpp 并加入编译，省去手写生成规则。

    undefined reference to vtable for X 的典型原因是 moc 没有对这个类跑——最常见的是头文件没有列进 qt_add_executable / add_library 的文件列表（AUTOMOC 只扫描 target 里列出的文件）。另一种情况是刚加上 Q_OBJECT 但构建缓存没刷新，清一次构建目录即可。

    特殊规则
    如果类定义写在 .cpp 里，AUTOMOC 生成的是 x.moc 而不会自动加入构建，需要你在该 cpp 末尾写 #include "x.moc"。
  4. 基础程序在开发机上正常，装到客户机上启动就报 could not find the Qt platform plugin，为什么？

    缺少平台插件（Windows 上是 qwindows.dll，Linux 上是 libqxcb.so）。Qt 的窗口系统对接是通过插件（QPA）实现的，没有它连窗口都创建不出来。

    关键在于目录结构：插件必须放在可执行文件旁边的 platforms/ 子目录里，只把 dll 拷到 exe 同级是不行的。用 windeployqt / linuxdeployqt 自动收集可以避免手工出错。

    验证方法
    用全新的干净虚拟机跑一遍安装包。开发机装过 Qt，程序会通过环境变量意外找到插件，掩盖打包缺失。

9.2 中级（区分熟练度）

  1. 中级Widgets 和 QML 怎么选？给一个工业检测上位机的项目，你选哪个，为什么？

    本质差异：Widgets 是 CPU 光栅化 + 全程在 GUI 线程；Quick/QML 是 GPU 场景图 + 独立渲染线程。

    工业检测选 Widgets，三条理由：

    功能对口
    界面主体是图像显示 + 参数表格 + 结果列表，Widgets 的模型/视图体系成熟，几十万行表格没问题；QML 的 TableView 相对年轻。
    可靠性
    工控机显卡驱动往往老旧，还经常通过远程桌面操作。GPU 渲染在这里是风险不是收益——可能降级到软件 OpenGL 反而更慢，甚至黑屏。
    团队成本
    团队是 C++ 背景，引入 QML 等于引入第二套语言、第二套调试链，而且 QML 是解释执行，很多错误运行时才暴露。

    反过来，如果是带触摸屏的一体机、要做流畅动效、有专门的前端同学，QML 才是对的选择。

  2. 中级自定义 QAbstractItemModel 时，为什么 data() 里不能做复杂计算？

    因为 data() 是绝对热点。视图每次重绘、每次滚动都会对每个可见格子的每个 role 调用它——一屏 200 个格子 × 5 个 role（Display / Foreground / Background / ToolTip / Alignment）= 1000 次，60 帧就是每秒 6 万次。

    在里面做字符串格式化（QString::arg）都可能成为瓶颈，做数据库查询或文件 IO 更是直接卡死。

    规则
    data() 里只允许查表和返回，任何计算、格式化、IO 都要在数据进入模型时提前做好，存成可以直接返回的形式。
    配套问题
    批量插入必须用 beginInsertRows/endInsertRows 一次包住整批，逐行插入会触发 N 次视图更新；resizeColumnsToContents() 要遍历所有行，大数据量下不能用。
  3. 中级什么是 D-Pointer（PIMPL）？为什么 Qt 到处都在用？

    把类的所有数据成员搬进一个只在 .cpp 里定义的私有实现类，公开类只保留一个指向它的指针。这样公开类的大小和内存布局永远不变。

    Qt 用它是为了 ABI 稳定：往私有类里增删成员不会改变公开类的 sizeof，动态库可以只替换 .so/.dll 而不要求调用方重新编译。这是 Qt5 能在整个大版本内保持二进制兼容的关键。

    次要收益是编译速度：实现细节不在头文件里，改实现不会触发所有 include 者重编译。

    代价
    一次额外的指针跳转（破坏缓存局部性）+ 一次堆分配。应用内部的普通类不该用——整个应用一起编译，没有 ABI 问题，纯粹是过度设计。
  4. 中级Qt5 迁移到 Qt6，有哪些破坏性变化要注意？
    • 强制 C++17：GCC 7 以下、MSVC 2017 以下的工具链直接出局。
    • 构建系统改用 CMake：qmake 仅保留兼容，不再演进。
    • QList 语义变了——见下方，这是最容易翻车的一条。
    • 渲染改为 RHI 抽象层：自定义 OpenGL 渲染代码需要适配。
    • 部分模块移出主包：依赖清单和许可要重新核对。
    QList 的坑
    Qt5 的 QList<T> 对大对象是「指针数组」，插入删除不会让已有元素的指针/引用失效；Qt6 改成连续存储（等同 QVector/std::vector）后，任何持有元素引用再插入的老代码都变成了悬垂访问——而且不一定立刻崩。迁移时务必用 ASan 跑一遍完整回归。

9.3 高级（体现深度）

  1. 高级用 D-Pointer 时，为什么析构函数必须定义在 .cpp 里？

    因为析构 unique_ptr<Private> / QScopedPointer<Private> 需要 Private 是完整类型（要知道怎么调它的析构函数、它多大）。

    如果在头文件里写 ~Camera() = default;，编译器会在每个包含这个头文件的翻译单元里生成析构代码——而那里 CameraPrivate 只有前向声明。

    后果
    std::unique_ptr 会触发 static_assert 报 invalid application of 'sizeof' to an incomplete type，编译失败还算好的。某些实现（历史上的 QScopedPointer、裸指针写法）只给一个警告然后生成「delete 不完整类型」的代码——不调用析构函数，静默泄漏，这才是真正危险的情况。

    把 Camera::~Camera() = default; 放在 .cpp 里，此处 CameraPrivate 已完整定义，问题消失。同样的规则适用于移动构造和移动赋值——它们也需要完整类型。

  2. 高级一个显示 5000×4000 图像、带实时缺陷标注的界面很卡，你怎么优化？

    先测量再优化：用 QElapsedTimer 量 paintEvent 耗时，用 perf 火焰图看热点。经验上瓶颈通常在这三处：

    ① 每帧缩放全图
    20 MPix 的双线性缩放要几十毫秒。缓存缩放结果，只有源图或控件尺寸变化时才重算；预览阶段用 Qt::FastTransformation，用户停止操作后再用高质量插值重算一次。
    ② 全量重绘
    标注变化时只 update(dirtyRect) 而不是 update()；paintEvent 里用 e->region() 裁剪，跳过不在脏区里的标注。
    ③ 格式转换
    像素格式与屏幕不一致时每次绘制都要转换。统一成 Format_ARGB32_Premultiplied，QPixmap::fromImage 只做一次并缓存。
    再往上一层
    如果图远大于视口，正确做法是分块（tile）+ 多分辨率金字塔——只解码/缩放当前视口覆盖的瓦片，缩放级别切换时用预生成的低分辨率层。这也是所有地图和大图查看器的标准做法。到这个量级还可以考虑用 QOpenGLWidget 把纹理上传 GPU，让缩放平移由 GPU 完成。
  3. 高级你负责一个要长期维护的 Qt SDK，怎么保证升级时不破坏客户的二进制兼容？
    1. 所有公开类用 D-Pointer，公开头文件里不出现任何数据成员，保证 sizeof 恒定。
    2. 不在头文件里内联非平凡函数。内联代码会被编译进调用方的二进制，改了实现也不会生效，还会造成新旧行为混用。
    3. 虚函数表布局要冻结：不能在已有虚函数中间插入新的虚函数（会改变后面所有函数的 vtable 索引），只能追加到末尾——更稳妥的做法是干脆不在公开类里加新虚函数，用非虚接口 + d 指针里的策略对象。
    4. 控制符号可见性：-fvisibility=hidden + 显式的 EXPORT 宏，减少导出面就是减少被依赖的面。
    5. 版本化与自检：提供 libVersion()，头文件里编译期常量与运行时返回值不匹配就报错，防止头文件与库版本错配。
    6. CI 里跑 ABI 检查工具（abi-compliance-checker / abidiff），把兼容性从「靠人记住」变成「机器拦截」。
    还要考虑的
    Qt 类型出现在公开接口上会把你的 ABI 和 Qt 的 ABI 绑定——客户必须用同一个 Qt 大版本。如果要解耦，公开接口应该只用基础类型和自己定义的 POD，把 Qt 类型藏在实现里。完整规则见 C++ ABI 兼容性指南。
  4. 高级Qt 的许可模式对产品架构有什么实际影响？

    LGPLv3（大多数公司走的路）：可以用于闭源商业产品，但有两条硬约束——必须动态链接 Qt，并且必须允许最终用户替换 Qt 库（提供替换说明，或提供可重新链接的目标文件）。

    对架构的实际影响：

    不能静态链接
    想做「单文件 exe」的产品形态，在 LGPL 下不合规。嵌入式设备（固件是单个镜像）几乎必然要买商业许可。
    逐模块确认
    部分模块只提供 GPL（历史上的 Qt Charts、Qt Data Visualization、部分工具）。用了 GPL 模块就要开源整个产品。这必须在项目启动、技术选型时就确认，等到发布前才发现代价极高。
    替代路径
    需要图表功能但不想碰 GPL 模块，可以用 QCustomPlot（GPL/商业双许可，也要看）或者自己基于 QPainter 画——很多团队最后选了后者。

    结论：许可不是发布前的合规检查项，而是选型阶段的架构约束。它直接决定了链接方式、产品形态和可用模块清单。
