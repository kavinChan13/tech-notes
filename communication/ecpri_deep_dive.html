01

eCPRI 到底跑在什么上

先破除最大的误解

本篇是整条前传链路里最偏报文与实现的一篇：只讲 eCPRI 协议本身——怎么被承载、Common Header 有哪些字段、有哪些消息类型、一个 IQ 报文从以太网头到 IQ payload 逐字节长什么样。前传为什么会演进成今天这样，见 CPRI/eCPRI 演进；C/U/S/M 各平面在时间上怎么互相配合，见 O-RAN 平面；这段以太网在整张传输网里处于什么位置，见 前传/中传/回传。这三块本篇只引用、不重复。

先回顾一个关键区分：协议 ≠ 传输机制。eCPRI 是协议——它定义前传消息的格式与语义（这一段字节是 IQ 还是控制、属于哪条流、第几号）。但它自己不负责把字节搬到对端，那是传输机制的事。eCPRI 规范为此定义了两种承载方式：

① eCPRI over Ethernet（主流）

eCPRI 消息直接封装在以太网帧的 payload 里，用 EtherType 0xAEFE 标识。没有 IP、没有 TCP/UDP。这是 O-RAN 7-2x 前传最常用的方式——时延最低、开销最小、转发路径最短。

② eCPRI over UDP/IP（可选）

需要跨三层路由时，可把 eCPRI 封装在 UDP/IP 里。注意：即便走了 IP，传输层也是 UDP 而非 TCP——前传要低时延与确定性，不要重传。

1.1 以太网直承：一个前传帧的最外层

「直承」的意思非常字面：以太网帧头之后紧接着就是 eCPRI 的第一个字节，中间没有任何一层。EtherType 字段填 0xAEFE，这是 IEEE 给 eCPRI 分配的类型值，作用是告诉接收方「payload 请按 eCPRI 解析」——网卡的分类器、交换机的 ACL、Wireshark 的解析器都靠它。

① eCPRI over Ethernet（L2 直承，前传主流）

 |<----------------------- 以太网帧（计入 FCS） ---------------------->|
 +--------+--------+--------+--------+-----------+---------------+-----+
 | 前导码 |  目的  |   源   |  VLAN  | EtherType |  eCPRI 消息   | FCS |
 | +SFD   |  MAC   |  MAC   |  Tag   |  0xAEFE   | Common Header |     |
 | (8 B)  | (6 B)  | (6 B)  | (4 B)  |  (2 B)    |  + payload    |(4B) |
 +--------+--------+--------+--------+-----------+---------------+-----+
  不计入帧长                  可选，但前传几乎必带
                             （含 3 bit PCP 优先级，见第 7 章）
  帧间隔 IFG 12 B 同样不计入帧长，但要占线路时间

② eCPRI over UDP/IP（需要跨三层路由时）

 +--------+-----+------+-----------+------------+-------------+-----+
 | 前导码 | MAC | VLAN | EtherType | IPv4 (20B) | UDP  (8 B)  |     |
 | +SFD   | ×2  | Tag  |  0x0800   | src/dst IP |src/dst port | ... |
 +--------+-----+------+-----------+------------+-------------+-----+
                                                       |
                                                       v
                                       eCPRI 消息（Common Header 完全一样）

 每帧多出 IPv4 20 + UDP 8 = 28 字节；用 IPv6 是 40 + 8 = 48 字节

为什么二层这么受偏爱，本质上是省掉了每一跳的「查路由 + 改包头」：交换机按「目的 MAC + VLAN」查一次 CAM 表就能转发，典型端口到端口时延在亚微秒到几微秒量级；而三层转发要查最长前缀匹配、减 TTL、重算校验和，还多一层排队。前传的单向预算通常只有百微秒量级（具体由 O-RAN 定义的 T2a / Ta3 / Ta4 等窗口决定，以所用配置为准），每一跳省下的几微秒都是实打实的。

另一个常被忽略的收益是RU 侧的简化：U 面走纯二层的话，RU 的数据通道不需要 IP 协议栈、不需要 ARP、不需要处理分片重组，可以做成一条硬件流水。RU 上真正需要 IP 的只有 M 面（NETCONF over SSH/TLS）和 S 面的部分部署形态。

1.2 开销算一遍：为什么前传一定开 Jumbo Frame

「开销小」不是形容词，可以算出来。下面这笔账同时解释了另一件事：为什么前传网络几乎都要求端到端支持巨帧。

场景：NR 100 MHz、30 kHz SCS → 273 个 PRB；IQ 用 BFP 压到 9 bit

  每个 PRB 的 IQ 数据
      = 12 子载波 × 2 (I,Q) × 9 bit = 216 bit = 27 B
      + 1 B 块指数（BFP exponent）        = 28 B
  一个 OFDM 符号、一条 eAxC 流的 IQ
      = 273 × 28 B ≈ 7 644 B

每个报文的固定头开销：
  线路层：以太网头 14 + VLAN 4 + FCS 4 + 前导 8 + IFG 12 = 42 B
  eCPRI ：Common Header 4 + PC_ID 2 + SEQ_ID 2           =  8 B
  O-RAN ：无线应用头 4 + 数据段头 4 + udCompHdr/保留 2    = 10 B
                                              每报文合计 ≈ 60 B

MTU = 9000（巨帧）
  一个符号一条流 = 一帧          开销 60 / 7644         ≈ 0.8%

MTU = 1500（普通以太网）
  payload 只装得下约 50 个 PRB   → 一个符号要拆成 6 帧
                                 开销 6 × 60 / 7644     ≈ 4.7%
                                                        ^^^^^ 差 6 倍

再叠加 UDP/IP 的 28 B：
  巨帧      +28 / 7644       ≈ +0.4%（几乎白送）
  MTU 1500  +6 × 28 / 7644   ≈ +2.2%（要额外买 2% 带宽）
4.7% 听起来不多，但请把它换算成钱：一个 100 MHz、8 流的小区 U 面裸速率约 13 Gbit/s（每流 3276 子载波 × 2 × 9 bit × 14 符号 × 2000 时隙/s ≈ 1.65 Gbit/s），4.7% 就是 600 Mbit/s 的纯包头。一个 25 GbE 口本来能带 1 个这样的小区还有余量，多站点汇聚时这些百分点会直接决定「一根 25G 够不够」。所以前传链路上「MTU 有没有端到端开到 9000」是开站清单里的必查项——中间任何一跳没开，要么分片、要么直接丢大包。

1.3 UDP/IP 承载：换来什么，代价是什么

既然二层这么好，为什么规范还留了 UDP/IP？因为二层的前提是「DU 和 RU 在同一个广播域里」。这个前提在下面几种情况会破：DU 集中放在边缘机房、RU 分散在几公里外的楼顶，中间要过一段已经三层化的共享传输网；或者一张前传网要同时服务多个厂商、多个租户，运维上必须靠 IP 划分边界；再或者只是实验/仿真台架，DU 是一台普通服务器，直接用 socket 收发更方便。

维度over Ethernet（L2）over UDP/IP（L3）
网络前提DU/RU 同广播域，中间只能是交换机可跨路由器、跨子网、跨机房
寻址目的 MAC + VLANIP + UDP 端口（更好管理、可做 ACL/策略）
每帧额外开销0IPv4 +28 B / IPv6 +48 B

分片风险无（MTU 不足直接丢，问题暴露得早）有，见下方警告
同步（S 面）PTP 二层 profile，边界时钟部署直接路由器必须支持 BC/TC，时间预算更难守

UDP/IP 承载最阴的一个坑是分片。IQ 报文本来就贴着 MTU 走，只要路径上有一跳的 MTU 比两端小（隧道、VLAN 叠加、某台设备默认 1500），IP 就会分片。后果有三重：① 分片重组需要缓存与定时器，时延确定性没了；② UDP 分片丢一片等于整个报文全废，一个符号的 IQ 全丢而不是丢一小段；③ 很多硬件加速路径不处理分片，会直接软件兜底，CPU 占用突然翻几倍。正确做法是端到端把 MTU 对齐（并留出 VLAN/隧道的余量），让「装不下」表现为「明确丢包 + 计数器增长」，而不是「悄悄分片」。

另外，eCPRI 规范没有为它申请一个固定的知名 UDP 端口，端口号靠两端配置约定。这在工程上有两个直接影响：抓包时 Wireshark 不会自动认出来（要手工 Decode As → eCPRI），以及做 ACL/QoS 分类时不能照抄别人的端口号，必须查本项目的配置。

1.4 两种承载都不走 TCP

这是最高频的误解，所以要说得很死：eCPRI 的两种承载方式里都没有 TCP。L2 直承时连传输层都没有；over IP 时用的是 UDP。原因不是「TCP 慢」这种笼统印象，而是 TCP 的每一项核心机制都和前传的需求正面冲突：

  • 重传对实时 IQ 毫无意义。一个 OFDM 符号在 30 kHz SCS 下只占约 35.7 µs，L1 必须在它的处理窗口内拿到数据。等一个 RTT 之后重传回来的符号，接收窗口早就关了——它不是「迟到的数据」，是垃圾，还白占了一份带宽和一次内存拷贝。
  • 拥塞控制会摧毁确定性。TCP 的发送速率由拥塞窗口决定，而窗口随丢包/时延反馈动态涨缩。可前传的码流速率是物理常量：空口每 500 µs 就产生一个时隙的 IQ，你不能因为网络觉得挤就少发。让 TCP 来「调速」的结果是数据在发送缓冲里堆积，时延一路飙升，然后整条链路崩掉。
  • 队头阻塞。TCP 是有序字节流，前面一个段没到，后面已经收到的段也不能交给上层。前传恰恰相反：丢了第 100 号报文，第 101 号该立刻交给 L1 处理，因为它属于另一段 PRB、另一个符号。
  • 字节流与消息边界不匹配。eCPRI 消息是定长头 + 明确长度的独立消息，天然是「数据报」语义。放到字节流上还得自己做一遍分帧，纯属多此一举。
  • 连接状态成本。一个 RU 上并行几百条 eAxC 流，若每条都要连接、ACK 时钟、重传定时器，RU 的硬件流水就没法做了。
所以那个经典问题的标准答案是：eCPRI 通常直接跑在以太网上（L2，EtherType 0xAEFE），不经过 IP；需要跨三层时可选 UDP/IP，但两种方式都绝不会用 TCP。能再补一句「因为前传的正确策略是宁丢不等——丢掉的那点 IQ 由空口的 HARQ 去兜，而不是由传输层重传去兜」，就说到根上了（详见第 6 章）。
02

eCPRI Common Header 结构

4 字节，简洁到极致

每个 eCPRI 消息都以一个固定的 Common Header（4 字节） 开头。整个 eCPRI 协议的「公共部分」就只有这 4 个字节，剩下的一切都由 Message Type 决定怎么解析：

eCPRI Common Header（4 字节）

  byte 0                byte 1        byte 2        byte 3
 +-----------------+  +-----------+  +---------------------------+
 |7 6 5 4|3 2 1|0  |  | 7 ... 0   |  |     15 .......... 0       |
 +-------+-----+---+  +-----------+  +---------------------------+
 |protRev| rsvd| C |  |  msgType  |  |     payloadSize (BE)      |
 +-------+-----+---+  +-----------+  +---------------------------+
   4 bit  3 bit 1bit      8 bit                 16 bit

  protRev     协议版本，当前规范里为 0x1
  rsvd        保留位，发送置 0、接收忽略
  C           Concatenation：1 = 本帧里后面还拼着下一个 eCPRI 消息
  msgType     消息类型，决定 payload 的结构（见第 3 章）
  payloadSize 本消息 payload 的字节数，大端序，★不含这 4 字节头本身★

2.1 四个字段逐条讲清

字节 · 位字段宽度含义与工程注意点
0 · bit 7–4protocolRevision4 bit协议版本。当前规范里取 0x1（以所用版本为准）。收到不认识的版本号应当计数并丢弃，不要「尽力解析」——字段可能整体挪位。
0 · bit 3–1reserved3 bit发送必须置 0，接收必须忽略。不要拿它当私有扩展位，未来版本可能启用，届时你的设备和别家就互通不了。
0 · bit 0C（Concatenation）1 bit1 = 本以太网帧里紧接着还有一个 eCPRI 消息。这是唯一的「后面还有」指示，没有消息计数字段。
1 · bit 7–0ecpriMessage（Message Type）8 bit类型分发的依据。8 bit 的空间里目前只用掉了很小一部分，未定义的值应丢弃并计数。
2–3ecpriPayloadSize16 bit本消息 payload 长度，大端序，不含 Common Header。理论上限 65535 B，实际被 MTU 卡住。
Concatenation（拼接）：把多个独立的 eCPRI 消息塞进同一个以太网帧，用第一个字节的 C 位串成链。动机很朴素——一帧的固定开销（以太网头 + FCS + 前导 + IFG）有 42 字节，如果每个 40 字节的实时控制消息都单独发一帧，效率不到一半。拼接之后这 42 字节被多个消息分摊。

拼接有一条容易漏掉的规则：除最后一个消息外，每个被拼接的消息都要补齐到 4 字节边界（以所用规范版本为准），填充字节不计入 payloadSize。这条规则的存在理由是硬件友好——接收侧的解析流水希望每个消息头都落在 32 位对齐的位置上。

一个以太网帧里拼接三个 eCPRI 消息

 [ Ethernet 头 ... EtherType = AE FE ]
 |
 ├─ msg#1   11 02 00 26 | <38 B payload> | 00 00
 |          ^^                             ^^^^^  38 不是 4 的倍数 → 补 2 B
 |          C=1，protRev=1                        （填充不计入 0x0026）
 |
 ├─ msg#2   11 02 00 26 | <38 B payload> | 00 00      C=1，还有下一个
 |
 └─ msg#3   10 00 05 86 | <1414 B payload>
            ^^                                       C=0，本帧最后一个
            10 = protRev 1 + C 0                     最后一个不需要填充
 [ FCS ]

 效率对比（以 38 B 的控制消息为例）
   各发一帧：  (42 + 4 + 38) × 3 = 252 B 线路占用
   拼接一帧：  42 + (4+38+2) × 2 + (4+38) = 42 + 88 + 42 = 172 B
   省下约 32%

2.2 一个 Common Header 的十六进制逐字节拆解

下面这 4 个字节取自本篇后面要完整拆解的那个下行 IQ 报文（第 5 章会把整帧铺开）：

       10   00   05   86
       ^^   ^^   ^^^^^^^^
       |    |    |
       |    |    └─ payloadSize = 0x0586 = 1414 字节
       |    |         = PC_ID 2 + SEQ_ID 2 + O-RAN 应用头 4
       |    |           + 数据段头 4 + udCompHdr/保留 2 + IQ 1400
       |    |         ★ 不含这 4 字节 Common Header
       |    |         ★ 大端：先 05 后 86，x86 上必须 ntohs
       |    |
       |    └─ msgType = 0x00 = IQ Data（用户面）
       |
       └─ 0x10 = 0001 000 0
                 ^^^^ ^^^ ^
                 |    |   └─ C = 0，本帧到这个消息就结束
                 |    └───── reserved = 000
                 └────────── protocolRevision = 0x1

       11 02 00 26   →  protRev=1, C=1, Type=2(实时控制), payload=38 B
       ^^ 末位 1 = 后面还有

2.3 解析这 4 个字节时踩过的坑

这个头简单到几乎不可能写错，但真实代码里翻车的地方非常固定，全都不在「读字段」这一步：

❌ 拿以太网帧长当消息长度

以太网有 60 字节最小帧（不含 FCS）的规定。一个 Type 6（Remote Reset）之类的短消息，payload 可能只有几字节，网卡会自动填充到 60 字节。如果你按帧长去切 payload，就会把填充字节当业务数据读进来。永远信 payloadSize，不要信帧长。

✅ 双向校验后再用

既要检查 payloadSize 是否超出实际收到的字节数（防越界读），也要在 C=0 时检查是否有「多余的尾巴」（可能是填充，也可能是你漏解析了一个消息）。两个方向都要有计数器。

// eCPRI Common Header 解析：遍历一帧里所有拼接的消息
// 关键点全在边界检查上，不在字段读取上
#include <cstdint>
#include <cstddef>
#include <cstring>
#include <arpa/inet.h>   // ntohs

struct EcpriHdr {          // 就 4 字节，别加 #pragma pack 之外的任何东西
  uint8_t  b0;              // protRev(4) | rsvd(3) | C(1)
  uint8_t  msg_type;
  uint16_t payload_size_be;  // 大端，别直接用
};
static_assert(sizeof(EcpriHdr) == 4, "no padding allowed");

constexpr uint8_t kProtoRev = 0x1;

void parse_frame(const uint8_t* p, size_t len, Stats& st) {
  // len 必须是「EtherType 之后的有效字节数」，不能是网卡给的帧长，
  // 否则 60 字节最小帧的填充会被当成下一个消息。
  for (;;) {
    if (len < sizeof(EcpriHdr)) { if (len) ++st.trailing_bytes; return; }

    EcpriHdr h;
    std::memcpy(&h, p, sizeof h);   // 别做 reinterpret_cast，对齐没保证

    const uint8_t  rev  = h.b0 >> 4;
    const bool     conc = h.b0 & 0x01;
    const uint16_t psz  = ntohs(h.payload_size_be);

    if (rev != kProtoRev) { ++st.bad_rev; return; }   // 版本不认识就整帧放弃
    if (psz > len - sizeof(EcpriHdr)) { ++st.trunc; return; } // ★防越界读

    dispatch(h.msg_type, p + sizeof(EcpriHdr), psz, st);

    if (!conc) {                       // C=0：本帧结束
      size_t rest = len - sizeof(EcpriHdr) - psz;
      if (rest) st.trailing_bytes += rest;   // 可能是填充，也可能是漏解析
      return;
    }
    // C=1：跳到下一个消息，注意要补到 4 字节边界
    size_t step = (sizeof(EcpriHdr) + psz + 3) & ~size_t{3};
    if (step >= len) { ++st.trunc; return; }
    p += step; len -= step;
  }
}
if (psz > len - sizeof(EcpriHdr)) 这一行是安全边界而不是健壮性锦上添花。payloadSize 是一个 16 bit 的、完全由对端控制的长度字段，前面又刚检查过 len >= 4，所以这个减法不会下溢。少了这一行，一个损坏或恶意构造的报文就能让你越界读到几十 KB 之外——而前传网络上确实会出现比特翻转造成的畸形长度（FCS 只保护到网卡那一层，DMA 之后的内存错误它管不着）。
这个头是紧凑二进制协议的教科书样本，值得拿去和自己设计的协议对照：版本（protocolRevision，留了升级余地）、类型分发（msgType，8 bit 够用几十年）、显式长度（payloadSize，不依赖分隔符也不依赖底层帧长）、批量指示（C 位，摊薄固定开销）、对齐规则（4 字节边界，为硬件流水服务）。四字节做到这个信息密度，靠的是每一位都有明确归属、没有一个「以后再说」的字段。

3.1 Type 5：单向时延测量，最实用也最常被忽略

先说清它解决什么问题。前传的时延预算是单向的：DU 必须保证 IQ 在 RU 的接收窗口内到达，晚了这个符号就废了。可我们平时手上的工具——ping、TWAMP、iperf——量的都是往返时延，然后除以 2。这个「除以 2」在前传上是错的：光纤路由去回不同长、交换机两个方向的队列深度不同、甚至上下行走了不同的波长/纤芯，都会让链路不对称。往返 80 µs 有可能是 40/40，也可能是 55/25。

eCPRI Type 5 就是为此而生：它直接量单向时延，靠的是发送方把自己的发送时刻写进报文，接收方用自己的时钟记下接收时刻，两者相减。

3.3 用 Type 5 验证前传预算：怎么测才算数

Type 5 的价值在开站验收和故障复盘时最大，但要测对，有四个坑：

❌ 只在空闲时测

空网上量到的基本只有光纤传播时延 + 串行化时延（单模光纤约 5 µs/km；1400 字节在 25 GbE 上串行化约 0.45 µs）。真正会吃掉预算的是队列，而队列只在满载、多站汇聚、M 面同时在下载固件的时候才出现。必须带载测。

✅ 看分位数，不看平均

前传是硬窗口，一个符号晚到就废。平均 45 µs 而 P99.99 是 130 µs 的链路，是坏链路。要连续测足够长的时间并统计高分位，最好同时记录最大值出现的时刻，好和别的事件（固件下载、邻站开站）对齐。

❌ 用小报文测

不填 Dummy bytes 的测量帧只有几十字节，它在交换机里的排队行为和 1400 字节的 IQ 报文不是一回事：短帧插队快、不会被大帧的串行化挡住。规范之所以留 Dummy 字段，就是让你把测量帧撑到 U 面报文的典型大小。

✅ 两个方向都测

用 Action 0x03（Remote Request）拿到反方向读数，把两个方向和不对称量一起记录。不对称量是一个会漂移的量（换光缆、改路由、加一跳都会变），值得进例行巡检。

如果 Type 5 算出来是负数，不要去找「负时延」的解释——那是时钟没对齐。公式 t2 - t1 - tCV 里 t1 和 t2 来自两个不同设备的时钟，两端偏差多少，读数就偏多少。所以负值（或者比光纤长度算出的下限还小的正值）唯一的含义是 S 面没锁定 / 正在收敛 / GM 切换过。同理，读数出现一个恒定偏置（比如每次都恰好多 3.2 µs）几乎一定是 Compensation Value 没配——两端的内部固定时延（光模块、SerDes、FPGA 流水）没有被扣掉。判读顺序永远是：先确认 PTP 锁定与 GM 稳定，再看 Type 5 的数。

4.1 eAxC ID：16 位里塞进四层含义

先说为什么需要它。一个 32T32R 的 RU、4 个载波、3 个扇区，同一根光纤上同时流着几百条互不相干的 IQ 流：第 3 扇区第 2 载波第 17 根天线的上行采样，和第 1 扇区第 1 载波第 4 层的下行采样，除了共享一条链路之外没有任何关系。接收端必须能在拿到报文的第一个纳秒就判断「这属于哪条流、该送到哪个处理单元/哪块内存」——这个判断不能查表遍历、不能解析深层字段，必须是几个移位和掩码。所以 eAxC ID 被放在 eCPRI 头后紧接着的位置，并且被切成有层次的位域：

子字段典型位宽含义谁在用它
DU_Port_ID2–4 bit区分 DU 侧的处理单元 / 端口。多个 DU、多张网卡、多个 L1 实例共用同一个 RU 时靠它分流DU 侧的收包分发
BandSector_ID3–6 bit频段 + 扇区的组合标识RU 侧定位到哪一组射频通道
CC_ID3–4 bit载波（Component Carrier）编号两侧的载波级处理

这四段的位宽是可配置的，四段加起来必须正好 16 bit，而且两端必须配成完全一样。这是 O-RAN 前传最经典的一类互通问题：M 面下发的配置里位宽写错一位，DU 编出来的 ID 和 RU 解出来的 ID 就整体错位。后果是 RU 解出一个没有配置过的组合，然后按规范静默丢弃——链路 up、PTP 锁定、C 面可能还通，就是没有业务。查这类问题一定要两边同时把 16 bit 的原始值打出来，而不是各自打印「DU_Port=1, CC=0」这种已经解码过的字段：两边的解码规则本来就不一样，打出来自然都「对」。
// eAxC ID 的编解码：位宽来自 M 面配置，不能写死
struct EaxcLayout {          // 从 M 面（NETCONF/YANG）读到的位宽
  uint8_t du_bits;             // 高位在前：DU | Band | CC | RU
  uint8_t band_bits;
  uint8_t cc_bits;
  uint8_t ru_bits;
  bool valid() const {          // ★ 启动时就要断言，别等到丢包才发现
    return du_bits + band_bits + cc_bits + ru_bits == 16;
  }
};

struct Eaxc { uint16_t du, band, cc, ru; };

inline Eaxc eaxc_decode(uint16_t id, const EaxcLayout& L) {
  Eaxc e;
  int sh = 16;
  sh -= L.du_bits;   e.du   = (id >> sh) & ((1u << L.du_bits)   - 1);
  sh -= L.band_bits; e.band = (id >> sh) & ((1u << L.band_bits) - 1);
  sh -= L.cc_bits;   e.cc   = (id >> sh) & ((1u << L.cc_bits)   - 1);
  sh -= L.ru_bits;   e.ru   = (id >> sh) & ((1u << L.ru_bits)   - 1);
  return e;                     // sh 此时必然为 0
}

4.2 一个站点到底有多少条 eAxC 流

这是个很好的面试题，因为它逼你说清一件事：下行的流数不等于天线数。取决于「谁做波束赋形（预编码）」，同一副 32T32R 天面上的前传流数可以差 8 倍。

Category A：预编码在 DU

DU 算完预编码，把每根物理天线的 IQ 分别送给 RU，RU 只做上变频/放大。于是 下行 eAxC 数 = 物理天线数（32T → 32 条）。RU 简单便宜，代价是前传带宽按天线数线性膨胀。

Category B：预编码在 RU

DU 只送每个空间层的 IQ 加上波束权值（权值走 C 面），RU 自己做预编码展开到 32 根天线。下行 eAxC 数 = 层数（4 层 → 4 条）。前传带宽省 8 倍，代价是 RU 变复杂、DU/RU 之间的接口耦合更深。

上行方向通常没有这个自由度：RU 一般把每根接收天线的采样都送上去让 DU 做合并/均衡，所以 上行 eAxC 数 ≈ 接收天线数。这就造成了 Category B 下一个反直觉的现象——上行的前传流数和带宽反而比下行大得多。

16 bit 的 eAxC ID 空间是 65536，看上面这张表就知道为什么够用、又为什么不能太浪费：单站几百条是常态，但一个 DU 可能挂十几个 RU，而 DU_Port_ID 还要从这 16 bit 里分走几位。被问「eAxC 流数怎么估」时，答题骨架是：(下行层数 或 发射天线数，取决于 Cat A/B) × 载波数 × 扇区数 + 上行接收天线数 × 载波数 × 扇区数 + PRACH/SRS 等专用通道，然后指出 Cat A/B 的区别是这里最大的变量。
PRACH 的 eAxC 漏配是一个非常有辨识度的故障。PRACH（随机接入）通常占用独立的 RU_Port_ID 取值，而且它的采样率、带宽和普通 PUSCH 不同，配置项也是分开的。漏配的现象是：已经接入的用户一切正常、吞吐正常、切换正常，但新用户接不进来。KPI 上表现为「随机接入成功率」跳水，而 RRC、核心网、传输侧的指标全绿——非常容易被误判成核心网或者终端问题，实际只是前传上少配了几条流。

4.3 SEQ_ID：两个字节干两件事

eCPRI 只说 SEQ_ID 是 2 字节的序号。O-RAN 把它进一步切成两半，因为它要同时解决丢包检测和报文分片两个问题：

eCPRI SEQ_ID（2 字节）在 O-RAN CUS-Plane 里的拆分

  byte 0                    byte 1
 +---------------------+  +-----+---------------------+
 |     seqId (8 bit)   |  |  E  |  subSeqId (7 bit)   |
 +---------------------+  +-----+---------------------+
   每条 eAxC 独立的计数器    |        分片序号
   逐报文 +1，到 255 回绕    |        （不分片时为 0）
                            |
                            E = 1 表示这是本次分片序列的最后一片
                            E = 0 表示后面还有

 为什么需要 subSeqId：一个符号一条流的 IQ 有 7 KB 量级，
 MTU 1500 时装不下，必须拆成多个报文。这是「无线传输层分片」，
 由 O-RAN 自己做，★不是 IP 分片★——所以走二层承载时也一样要分片。

丢包检测的逻辑本身很简单，难点全在回绕上：8 bit 计数器只有 256 个值。算一下它能覆盖多长时间——

MTU 1500、100 MHz、30 kHz SCS 的一条下行 eAxC：
  每符号 6 个报文 × 14 符号/时隙 × 2000 时隙/s = 168 000 报文/s
  256 个序号 ÷ 168 000 /s ≈ 1.52 ms 就绕一圈

 推论一：连续丢超过 256 个报文（≈1.5 ms），gap 会「绕回来」，
         统计上看起来正常。★所以 SEQ_ID 统计能发现零星丢包，
         但发现不了长时间中断★——中断要靠「报文完全停了」来判。

 推论二：把 MTU 开到 9000、一个符号一个报文之后，
         速率降到 28 000 报文/s，回绕周期变成 ≈9.1 ms，
         可观测窗口反而宽了 6 倍。开巨帧的附带收益。
// 每条 eAxC 一份状态，收包路径上执行；只做统计，不做恢复
struct SeqState {
  uint8_t  next = 0;
  bool     primed = false;    // 第一个包只用来对齐，不算丢
  uint64_t rx = 0, lost = 0, late_or_dup = 0;
};

inline void on_upl_pkt(SeqState& s, uint8_t seq) {
  ++s.rx;
  if (!s.primed) { s.primed = true; s.next = seq + 1; return; }

  uint8_t gap = uint8_t(seq - s.next);   // 模 256 差值，回绕天然正确

  if (gap == 0) {                          // 正常
  } else if (gap < 128) {                  // 前面漏了 gap 个
    s.lost += gap;
  } else {                                 // gap >= 128：这是个旧包
    ++s.late_or_dup;                       // 乱序 / 重复 / ID 冲突
    return;                                // ★别更新 next，否则会误报一大片丢包
  }
  s.next = seq + 1;
}

// 判读口径：
//   lost 缓慢线性增长        → 稳定的低速丢包，看 QoS / 队列 / 光功率
//   lost 一簇一簇地跳        → 突发拥塞，找同时刻的大流量事件
//   late_or_dup 大量出现     → ★首先怀疑两条流用了同一个 eAxC ID★，
//                              其次怀疑 LAG/ECMP 把一条流散到了多条路径
//   只有个别 eAxC 有问题     → 配置或映射问题，不是链路拥塞
//   所有 eAxC 一起有问题     → 链路 / 队列 / 时钟层面的公共原因
「late_or_dup 暴涨」这条判据很能体现有没有真在现场查过问题。两条不同的流被配成同一个 eAxC ID 时，接收端看到的是两个独立递增的计数器交织在一起——现象酷似严重乱序加疯狂丢包，但链路其实好得很。这类问题在「新开一个载波」「加一个扇区」之后出现的概率最高，因为配置模板复制粘贴时最容易忘改 CC_ID 或 BandSector_ID。判据是：丢包/乱序计数几乎对称地出现在两条流上，而且这两条流的 ID 一模一样。

4.4 为什么前传丢包不重传

第 1 章说了「重传对实时 IQ 没意义」，这里补上另一半、也是更重要的一半：重传机制其实已经存在，只是在正确的那一层。

U 面报文
→

也就是说，空口本来就有一套为「无线信道会出错」而设计的重传机制（HARQ），它的时间尺度（若干个时隙）和反馈路径都是为此优化过的。前传丢包最终会被它兜住。如果再在前传上叠一层重传，会得到三个坏处而没有好处：重传回来的数据已过期、DU 要为所有已发数据保留缓冲、重传引起的突发让本就拥塞的链路更堵。

所以前传的策略是把丢包率压到「HARQ 兜得住」的水平，然后彻底不管它。工程上对 U 面帧丢失率的要求通常在 10⁻⁷ 量级或更严（具体指标以所用 O-RAN 传输需求文档与运营商规范为准）。达到这个量级靠的是：专用或严格 QoS 隔离的链路、足够的带宽余量、以及不让 M 面的大流量和 U 面抢队列——而不是靠协议层的可靠性机制。

4.5 IQ 压缩：块浮点与位宽选择

前传带宽昂贵，而未压缩的 IQ 非常浪费：16 bit 定点的动态范围是为「整个小区任意时刻任意功率」准备的，可同一个 PRB 内 12 个相邻子载波的幅度其实很接近。块浮点（Block Floating Point, BFP）正是吃这个冗余——一组样本共享一个指数，各自只存低位尾数。

BFP 把一个 PRB（12 子载波 × I/Q = 24 个 16 bit 样本）压到 9 bit

原始（16 bit 有符号，节选）
  I0 = +2623 (0x0A3F)   Q0 = -2241   I1 = +786   Q1 = +1502  ...
  本块内最大绝对值 = 2623

① 选指数：9 bit 有符号的表示范围是 -256 .. +255
     2623 >> 3 = 327   > 255，放不下
     2623 >> 4 = 163   放得下   →  exponent = 4

② 编码：每个样本右移 4 bit，取 9 bit 有符号存放
     I0: +2623 >> 4 = +163
     Q0: -2241 >> 4 = -141
     I1:  +786 >> 4 =  +49
     ...
     块头写 exponent = 4（O-RAN 里放在 udCompParam，1 字节/块）

③ 解码：尾数 << 4，回到 16 bit 定点域
     I0: 163 << 4 = 2608     原值 2623，量化误差 15（约 0.6%）

字节账（每 PRB）
  未压缩    24 × 16 bit               = 48 B
  BFP 9bit  24 ×  9 bit + 1 B 指数    = 27 + 1 = 28 B
  压缩比    48 / 28 ≈ 1.71×

硬件视角：整个编码只需要「求块内最大值 → 前导零计数 → 移位」，
没有乘法、没有查表、没有反馈环路，一条组合逻辑流水就能做完。
★这是 BFP 胜出的真正原因，不是压缩比最高，而是代价最低。★
BFP 的误差由「块内最大值」决定，这是它的软肋。指数是全块共享的，所以一个特别强的子载波会把整块的移位量顶上去，块里那些幅度小的子载波就被压得只剩几个有效位。OFDM 信号在一个 PRB 内通常幅度接近，所以平常没事；但在强频率选择性衰落、窄带干扰、或者一个 PRB 内同时有强参考信号和弱数据的场景下，弱分量的相对量化噪声会明显恶化。表现是：整体 EVM 指标看着还行，但特定终端（处在深衰落频点上的那个）解调质量莫名其妙地差。
压缩方法原理特点与代价
不压缩16 bit 定点直传基准。带宽最大，但没有额外量化噪声，用于实验室、校准、以及对 EVM 要求最苛刻的场景
BFP（块浮点）块内共享一个 2 的幂次指数 + 定点尾数工程上的默认选择。硬件极简、压缩比可预测、误差行为容易分析
Block Scaling块内共享一个任意缩放因子（不限于 2 的幂）比 BFP 略精细，代价是解码要做乘法而不是移位
μ-law非均匀量化，小信号给更多量化级改善小信号精度，但实现复杂、误差分析更难
Modulation Compression利用「发出去的星座点是已知有限集合」这一先验压缩比可以很高，但强依赖调制信息，本质上是下行专用
BFP + 选择性 RE在 BFP 之上，干脆不发空的 RE / 空的 PRB低负载时省得最多，但报文长度随负载浮动，带宽规划变难
udCompMeth 的具体编码值与可选方法集合以所用 O-RAN CUS-Plane 版本为准，常见的是 0 = 无压缩、1 = BFP。位宽字段 udIqWidth 是 4 bit，其中 0 通常表示 16 bit（因为 4 bit 装不下「16」这个数），其余值就是位宽本身。
udIqWidth每 PRB 字节数相对未压缩量化噪底（粗略）典型取舍
16（字段值 0）481.00×最低校准、实验室、最高阶调制验证
1236 + 1 = 371.30×低对 EVM 敏感、追求高阶调制且带宽有余量
927 + 1 = 281.71×够用多数实现的默认值，带宽与质量的平衡点
824 + 1 = 251.92×偏高带宽极度紧张、以低阶调制为主的覆盖场景

怎么定位宽？关键是理解压缩噪声只是 EVM 预算里的一小项。基站发射的 EVM 上限由 3GPP 按调制阶数规定（阶数越高越严，256QAM 已经是个位数百分比量级，1024QAM 更严；具体数值查 TS 38.104 对应版本的表格），而这份预算要分给：功放非线性与 DPD 残差、本振相噪、通道校准误差、数字前端的定点误差，最后才轮到 IQ 压缩。所以压缩通常只被允许占用总 EVM 预算的很小一部分——这就是「9 bit 常见、8 bit 要谨慎、想上 1024QAM 就得考虑 12 bit」的由来。

被问到「压缩率和 EVM 怎么权衡」时，一个很好的回答方式是反过来推：先看这个小区要不要支持 256QAM/1024QAM（决定 EVM 上限）→ 扣掉射频链路已经吃掉的部分 → 剩给压缩的裕量决定位宽下限 → 位宽乘以流数乘以载波数得出带宽 → 对比链路能力。如果算下来带宽不够，正确的动作往往不是继续压位宽（那会直接砍掉高阶调制的可用性，得不偿失），而是换 Category B 把下行流数降下来，或者升级链路速率。

「位打包」这一条值得单独记住。9 bit 的样本在字节流里是连续位打包的，第 2 个样本从第 1 个字节的第 7 位开始，所以解析 IQ 不能用「取第 N 个字节」，必须做跨字节的移位拼接。这也是为什么工程上偏爱 8 / 16 bit 之外还偏爱 12 bit（两个样本正好 3 字节，每 3 字节一个周期）——9 bit 的周期是 9 字节（8 个样本），SIMD 展开时的分支和查表比 12 bit 复杂得多。带宽算下来 9 bit 更省，但解码侧的 CPU/FPGA 代价更高，这是一个真实存在但很少被提起的取舍。

巨帧不是没有代价：单帧串行化时延变长（2.4 µs vs 0.46 µs），一个正在发送的巨帧会挡住排在后面的高优先级报文，这个「阻塞时间」直接进入 C 面和 S 面的时延预算。这就是为什么前传交换机通常要开基于 PCP 的严格优先级队列，某些场景还会用到帧抢占（IEEE 802.1Qbu / 802.3br 一类的机制）。取舍是：巨帧省带宽、省 pps，代价是给高优先级流量引入一个有界但非零的阻塞时延——而这个代价通常远小于它省下来的队列时延。
对照最开始那句话：eCPRI 就是被以太网直接承载的「应用层协议」。整帧里没有 TCP，也没有 IP（over UDP/IP 时才在 EtherType 之后多出 IP + UDP 两层，并把 EtherType 换成 0x0800/0x86DD）。这就是 eCPRI 能把单向时延压在百微秒以内的结构性原因。

「TCP 不适合前传」不该只是一句结论。把 TCP 的每一项核心机制拿出来，问「它为什么存在」和「放到前传上会发生什么」，答案就变得不可辩驳：

6.2 「宁丢不等」到底在权衡什么

这句口号背后是一个可以量化的取舍：丢掉一个报文损失多少 vs 等一次重传损失多少。

丢一个报文（本篇的样本帧：50 PRB，一条 eAxC，一个符号）

  损失范围 = 273 个 PRB 里的 50 个 = 该符号该流的 ≈18% 的资源单元
  时间范围 = 一个 OFDM 符号 ≈ 35.7 µs = 一个时隙的 1/14
  后果     = 这些 RE 的软信息按「擦除」处理
             → 信道编码（LDPC）本来就有冗余，很可能纠回来
             → 纠不回来才 CRC 失败 → 空口 HARQ 重传（本来就有的机制）
  代价     = 一次可能的 HARQ 重传，占用几个时隙的调度机会

等一次重传（假想在前传上做）

  发现丢包   ≥ 1 个报文间隔（要等后一个报文来才知道前一个没到）
  发出请求   ≥ 1 个单向时延  ≈  50 µs
  重发到达   ≥ 1 个单向时延  ≈  50 µs
  合计       > 100 µs，而且这只是理论下限
  后果     = 这个符号的接收窗口已经关了，数据仍然没用
             + 白占一份带宽 + DU 要为所有已发数据保留重传缓冲
             + 重传造成突发，让本就拥塞的链路更堵

结论：丢包的代价是「一次可能的 HARQ 重传」，
      等待的代价是「同样丢掉这个符号，外加三重额外开销」。
      ★所以不重传不是妥协，是唯一正确的选择。★

那可靠性到哪里去了？答案是被推到了物理层和工程余量上，这是一个很典型的「把责任放到代价最低的那一层」的设计：

  • 物理层 FEC：25G/100G 以太网自带 RS-FEC，链路上的随机比特错误在这一层就被纠掉了，根本到不了 eCPRI。这是「免费」的可靠性——它不引入不确定的时延，只引入一个固定的编解码时延。
  • QoS 隔离：用 VLAN + PCP 把 U 面和其他流量分到不同队列，严格优先级保证 U 面不被 M 面的固件下载挤掉（见第 7 章）。
  • 带宽余量：前传链路通常不按「刚好够」规划，而是留出可观余量，让队列几乎不排队。
  • 空口 HARQ：真的漏过去了，由空口这一层兜——它本来就是为「无线信道会出错」设计的。
这条思路值得推广：可靠性应该放在「代价最低、时间尺度最匹配」的那一层。物理层 FEC 的代价是固定时延（可预算），HARQ 的代价是调度机会（本来就有），而传输层重传的代价是不确定的时延——恰恰是前传最不能付的那种代价。同一个道理也解释了为什么实时音视频用 UDP + 应用层 FEC/NACK 而不是 TCP。
07

CUS 平面与同步

前传上并行的三/四类流量

在 O-RAN 7-2x 前传里，DU↔RU 之间同时流动着几类流量（常称 CUS 平面）：

  • U-Plane（用户面）：IQ 数据，占绝大部分带宽。
  • C-Plane（控制面）：调度/波束等实时控制，必须比对应 U-Plane 数据略早到达。
  • S-Plane（同步面）：PTP/SyncE 报文，负责频率+相位同步。
  • M-Plane（管理面）：NETCONF/YANG 配置 RU（见 NETCONF/YANG）。
这些平面共享同一张前传以太网，靠 VLAN + QoS 优先级 严格隔离：S 面 / C 面优先级最高（时间与控制不能晚），U 面次之，M 面最低。四个平面在时间上如何互相配合（C 面要早于 U 面多久、T2a/Ta3/Ta4 窗口怎么算）是另一篇的主题，见 O-RAN 平面；本章只讲与报文直接相关的那一半：优先级具体写在帧的哪一位、配错会怎样、怎么抓包验证。

7.1 优先级到底写在哪一位

回到第 5 章那个帧的偏移 0x000e。这两个字节是 802.1Q 标签的 TCI（Tag Control Information），前传的 QoS 全靠它前 3 位：

VLAN 标签（4 字节）的内部结构

  0x000c        0x000e
 +-----------+ +---------------------------------------+
 | TPID      | | PCP | DEI |        VID (12 bit)       |
 | 0x8100    | | 3b  | 1b  |                          |
 +-----------+ +---------------------------------------+

 本篇样本帧：81 00 a0 64
                   ^^^^^
                   a0 64 = 1010 0000 0110 0100
                           ^^^                        PCP = 5  ← U 面
                              ^                       DEI = 0
                                ^^^^ ^^^^ ^^^^        VID = 100

 ★ 整个前传 QoS 体系压在这 3 个 bit 上。
   交换机看这 3 bit 决定进哪个出口队列，队列决定排队多久，
   排队多久决定 IQ 能不能在窗口内到达。
   ——所以「PCP 配错」这个听起来很小的错误，后果是业务级的。
PCP典型分配（示例）承载什么为什么给这个优先级
7S 面PTP Sync / Follow_Up / Announce / Delay_Req时间报文的抖动会直接变成相位误差，一旦排队就没法补救
5–6C 面eCPRI Type 2（调度、波束权值、PRB 分配）必须早于对应的 U 面数据到达，否则 RU 不知道该怎么处理即将到来的 IQ
4–5U 面eCPRI Type 0（IQ 数据）带宽大户，有硬窗口但比 C/S 面稍宽
2M 面NETCONF、告警、固件文件下载可以等秒级，但流量可以很大——所以必须被压在最低
0best-effort其余管理/调试流量兜底
上表是示例：具体 PCP 取值由项目 / 运营商规划决定，不同厂商与不同部署形态的取值不一样。真正要守住的原则只有三条：S 面严格最高、C 面不低于 U 面、M 面严格最低且必须限速。而且光在 RU/DU 上打对 PCP 是不够的——中间每一台交换机都要把 PCP 映射到真正独立的出口队列并配成严格优先级，否则标签打了也白打。
最阴的一种 PCP 故障是「标签打了，但中途被重写」。交换机上常见的默认行为包括：untagged 入口按端口默认 PCP 打标、信任域边界处 remark、以及某些设备默认「不信任接入端口的 CoS」而一律置 0。结果是 DU 侧抓包看 PCP=5、RU 侧抓包看 PCP=0，中间那一跳把它改了。所以验证 QoS 必须在链路两端各抓一次包做对比，只在一端抓等于没验。

7.2 前传抓包为什么这么难

「抓个包看看」在前传上不是一句轻松的话。先看数量级：

25 GbE 前传口，满载、帧长 1436 B（本篇样本帧）

  线路占用/帧 = 1436 + FCS 4 + 前导 8 + IFG 12 = 1460 B = 11 680 bit
  报文速率    = 25 Gbit/s ÷ 11 680 bit ≈ 2.14 Mpps
  写盘速率    = 25 Gbit/s ≈ 3.1 GB/s        ← 需要 NVMe 阵列
  抓 1 分钟   ≈ 187 GB

 ★ 救命的一招：只抓头部
   我们需要的字段全部落在前 0x24 = 36 字节里
   （以太网 18 + eCPRI 8 + O-RAN 应用头 4 + 段头 6）
   -s 64 → 数据量降到 64/1460 ≈ 1/23
   写盘速率变成 ≈ 137 MB/s，普通 SSD 就能吃下
   代价：看不到 IQ 内容。但排障 99% 的时候你要的是头，不是 IQ。
# ① 网卡在内核驱动下（RU 调试口、或 DU 未启用 DPDK 时）
#    注意带 VLAN 标签时，内层 EtherType 在偏移 16 而不是 12
sudo tcpdump -i ens1f0 -s 64 -w fh.pcap 'ether[16:2] == 0xaefe'

# 不带 VLAN 时：
sudo tcpdump -i ens1f0 -s 64 -w fh.pcap 'ether proto 0xaefe'

# ② 只抓一条 eAxC（PC_ID 在偏移 22，本篇样本是 0x1205）
#    ★ 定向抓包是把数据量再降两三个数量级的关键
sudo tcpdump -i ens1f0 -s 64 \
  'ether[16:2] == 0xaefe and ether[22:2] == 0x1205'

# ③ 只抓 Type 5 时延测量（msgType 在偏移 19）
sudo tcpdump -i ens1f0 'ether[16:2] == 0xaefe and ether[19] == 5'

# ④ 环形缓冲 + 事件触发：长时间挂着，出问题时才留证据
sudo tcpdump -i ens1f0 -s 64 -W 20 -C 200 -w fh.pcap \
  'ether[16:2] == 0xaefe'
#    -W 20 -C 200 → 20 个 200 MB 文件循环覆盖，最多占 4 GB

# ⑤ 先确认网卡到底在谁手里 —— 这一步经常被跳过
ethtool -i ens1f0                 # driver: ice / mlx5_core → 内核在管
dpdk-devbind.py --status          # 出现在 "DPDK-bound" 段 → 内核看不到包
「tcpdump 一个包都抓不到」在 DU 上十有八九不是配置错，而是网卡根本不在内核手里。DU 的 U 面收发几乎必然走 DPDK 之类的用户态轮询驱动：网卡被绑到 vfio-pci，报文由 PMD 直接 DMA 到用户态内存，完全绕过内核网络栈，AF_PACKET/tcpdump 自然什么都看不见。这时的出路是：① 用 DPDK 自己的抓包机制（rte_pdump / dpdk-pdump）；② 在交换机上做端口镜像；③ 上无源光分路器。先跑一次 ethtool -i 再决定用哪条路，能省掉半天。
抓包手段优点代价与陷阱
主机上 tcpdump零成本、随时可用DPDK 场景下完全无效；有效时也只能看到「本机收发到的」，看不到线上真实时序
dpdk-pdump / rte_pdump能看到 PMD 收发的报文要 DU 应用编译时就启用支持；抓包本身会挤占 DU 的 CPU 与内存带宽，可能反过来造成丢包
交换机端口镜像（SPAN）不动业务设备，配置快超订就静默丢——把一个 25G 口镜像到 10G 分析口，丢掉的那部分不会告诉你；镜像本身也消耗交换芯片资源
无源光分路器（TAP）对链路完全透明、时序最真实分光要吃掉光功率（70/30 或 50/50），插上去前必须核对光功率预算，否则你会亲手制造出正在追查的那种误码
专用采集卡 / 采集仪能线速抓、带硬件时间戳贵；且要能接进现网拓扑
DU/RU 内置统计与 trace免费、随时有、按 eAxC 聚合粒度粗、看不到字节。但它应该是第一步——见下面的排障顺序
正确的排障顺序是「先统计、后抓包」，而不是反过来。SEQ_ID 丢包计数、Type 5 时延读数、交换机队列丢包计数这些都是免费且一直在采的，它们能立刻回答最关键的那个分叉问题：是所有 eAxC 一起出问题（公共原因：链路、队列、时钟），还是只有个别流出问题（配置、映射）？这个答案决定了后面要不要抓包、在哪抓、抓哪条流。反过来先上抓包，往往是花两天搭好采集环境，抓回 200 GB，然后发现问题在配置里。

修复分两层：短期补齐 RU 侧的 PCP 配置；长期在前传交换机上按 VLAN 强制 remark，让「RU 侧配漏了」不再能造成业务影响。这个案例里最省时间的一步是最开始那次免费的 SEQ_ID 统计——它把搜索空间从「整张前传网」缩到了「4 条流共同经过的那个队列」。

分层自测

8.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础eCPRI 为什么不走 TCP？

    因为 TCP 的每一项核心机制都和前传的需求正面冲突，而不只是「TCP 慢」：

    • 重传对实时 IQ 没有意义。一个 OFDM 符号在 30 kHz SCS 下只占约 35.7 µs，L1 必须在处理窗口内拿到数据。等一个来回之后重传回来的符号不是「迟到的数据」，是垃圾，还白占了本该给新符号的带宽。
    • 拥塞控制会摧毁确定性。IQ 的码率是物理常量——空口每 500 µs 就产生一个时隙的采样，不能因为网络觉得挤就少发。降速的唯一效果是数据在发送缓冲堆积，时延单调上升直到崩掉。
    • 队头阻塞。TCP 是有序字节流，第 100 号段没到、已经收到的第 101 号也交不上去；可它属于另一段 PRB，本该立刻处理。
    • 连接状态成本。一个 RU 上并行几百条 eAxC 流，若每条都要握手、ACK 时钟、重传定时器，RU 就没法做成硬件流水了。

    量化一下最有说服力的那条：Linux 的 TCP_RTO_MIN 就有 200 ms 量级，而前传单向预算是 100 µs 量级，差三个数量级。退一步说，哪怕重传延迟能压到理论下限——发现丢包至少要等下一个报文到达，再走一个来回——也已经是 2 个单向时延，符号窗口早关了。

    加分收尾：正确的策略是「宁丢不等」。前传丢一个报文只损失一个符号里一段 PRB 的资源单元，信道编码有机会纠回来，纠不回来则由空口 HARQ 重传兜住——重传机制本来就存在，只是在正确的那一层。可靠性则被推给了物理层（25G/100G 以太网的 RS-FEC）、QoS 隔离和带宽余量。

  2. 基础eCPRI 有哪两种承载方式？怎么选？

    ① over Ethernet（L2 直承）：以太网头之后紧接着就是 eCPRI 的第一个字节，用 EtherType 0xAEFE 标识，没有 IP、没有传输层。② over UDP/IP：把 eCPRI 消息装进 UDP 载荷。两种都不用 TCP。

    取舍：

    • L2 的优势是省与快：每帧零额外开销；交换机只查一次「目的 MAC + VLAN」，端口到端口时延在亚微秒到几微秒量级；RU 的数据通道不需要 IP 栈、不需要 ARP、不需要分片重组，可以做成硬件流水。
    • L3 换来的是可路由：DU 与 RU 不在同一广播域时（集中式 DU、跨机房、共享三层传输网、多厂商/多租户要用 IP 划边界）只能走这条路；IP + 端口也比 MAC 好管理。
    • L3 的代价：IPv4 每帧多 28 字节（IPv6 多 48）；逐跳要查路由、减 TTL、重算校验和，队列更深、抖动更难约束；PTP 走三层要求路由器支持边界/透明时钟；eCPRI 没有固定知名 UDP 端口，抓包和做 ACL 都得先查项目配置。

    最阴的坑是分片：IQ 报文本来就贴着 MTU 走，路径上任何一跳 MTU 偏小就会分片，而 UDP 分片丢一片等于整个报文全废，还会掉出硬件加速路径。所以必须端到端对齐 MTU，让「装不下」表现为明确的丢包与计数增长，而不是悄悄分片。

    结论：O-RAN 7-2x 生产网上绝大多数是 L2 直承；UDP/IP 多见于跨域/共享传输、实验台架，或时延要求较宽的分割点。

  3. 基础EtherType 0xAEFE 是什么？它在帧里的什么位置？

    它是分配给 eCPRI 的以太网类型值，作用是告诉接收方「这一帧的 payload 请按 eCPRI 解析」。用到它的有三方：网卡的流分类器（把 eCPRI 送到指定队列）、交换机的 ACL / QoS 规则、以及抓包工具的协议解析器。

    位置要说准，因为它会随 VLAN 标签浮动：

    • 不带 VLAN 时：EtherType 在偏移 12（目的 MAC 6 + 源 MAC 6 之后）。
    • 带一层 802.1Q 标签时：偏移 12 是 TPID 0x8100，偏移 14–15 是 TCI（PCP/DEI/VID），真正的 0xAEFE 落在偏移 16。

    这就是为什么 tcpdump 'ether proto 0xaefe' 在前传上经常抓不到东西——前传帧几乎必带 VLAN，得写 'ether[16:2] == 0xaefe'。同理，走 UDP/IP 承载时 EtherType 变成 0x0800/0x86DD，0xAEFE 根本不出现。

    加分：能顺口说出「0xAEFE 之后就是 eCPRI Common Header 的第一个字节，中间没有任何一层，这正是 eCPRI 低时延的结构性原因」。

  4. 基础eCPRI Common Header 有哪几个字段？各自什么作用？

    固定 4 字节，四个字段：

    字段宽度作用
    protocolRevisionbyte0 bit 7–4协议版本，当前规范取 0x1。不认识的版本应计数并丢弃
    reservedbyte0 bit 3–1发 0、收忽略。不要拿来做私有扩展
    C（Concatenation）byte0 bit 01 = 本以太网帧里后面还拼着下一个 eCPRI 消息
    ecpriMessagebyte1消息类型，决定 payload 怎么解析
    ecpriPayloadSizebyte2–3payload 字节数，大端，不含这 4 字节头

    能补上下面这几条细节会明显加分：

    • 拼接的对齐规则：C=1 时，除最后一个消息外每个消息要补齐到 4 字节边界，填充不计入 payloadSize——目的是让接收侧硬件流水的每个消息头都落在 32 位对齐处。
    • 不能用帧长代替 payloadSize：以太网有 60 字节最小帧，短消息会被网卡填充，按帧长切会把填充读成业务数据。
    • payloadSize 必须做边界检查：它是完全由对端控制的 16 bit 长度字段，不检查就是一个越界读漏洞。

    最后一句可以升华：这个头是紧凑二进制协议的教科书样本——版本、类型分发、显式长度、批量指示、对齐规则，四个字节里没有一个「以后再说」的字段。

8.2 中级（区分熟练度）

  1. 中级eCPRI 定义了哪些消息类型？现网真正常用的是哪几种？

    按重要性回答而不是按编号背诵，效果好得多。

    现网真正在跑的只有三种：

    • Type 0（IQ Data）——承载基带 IQ，O-RAN 的 U 面，占前传带宽 95% 以上。
    • Type 2（Real-Time Control Data）——O-RAN 的 C 面，送调度信息、波束权值、PRB 分配，必须早于对应的 U 面数据到达。
    • Type 5（One-Way Delay Measurement）——测单向时延，工程上很有用但常被忽略。

    规范里还有但前传基本用不上的：Type 1（Bit Sequence，对应比特域的分割点）、Type 3（Generic Data Transfer，语义留给厂商）、Type 4（Remote Memory Access，远程读写寄存器，多用于厂商调试工具）、Type 6（Remote Reset）、Type 7（Event Indication）。Type 8 及以上是与传统 CPRI 互通的 IWF 相关类型，只在混合组网/改造期出现。

    关键补充：Type 6/7 用不上是有原因的——在 O-RAN 架构里，复位和告警都走 M 面的 NETCONF/YANG（复位是 RPC，告警是 notification），没必要再用一条实时通道。

    还要能说清一个常被混的点：eCPRI 的消息类型是格式分类，O-RAN 的 C/U/S/M 是功能分面，两者不等同——S 面用的是 PTP/SyncE，不是 eCPRI 消息；M 面用的是 NETCONF，也不是。

  2. 中级Type 5 单向时延测量是干什么用的？它和 PTP 有什么区别？

    它解决的问题：前传的时延预算是单向的，但 ping / TWAMP 这类工具量的是往返再除以 2。这个「除以 2」在前传上是错的——去回光纤不同长、两个方向的队列深度不同，往返 80 µs 可能是 40/40，也可能是 55/25。Type 5 直接量单向：发送方把发送时刻 t1 写进报文，接收方用自己的时钟记下 t2，单向时延 = t2 - t1 - tCV（tCV 是已知内部固定时延的补偿值）。用 Action Type 0x03（Remote Request）让对端发起反向测量，就能拿到两个方向并算出不对称量。

    和 PTP 的区别（这是重点）：

    • 目的相反：PTP 是建立共同时间基准；Type 5 是使用这个基准去量传输时延。所以 Type 5 的前提是 PTP 已锁定，反过来不成立。
    • 对称性假设：PTP 默认假设路径对称，把往返取一半当单向；路径实际不对称多少，恢复出来的相位就偏一半。Type 5 能分方向量，直接把 PTP 掩盖掉的不对称暴露出来。举例：18.6 µs 的不对称会造成约 9 µs 的相位误差，而 TDD 的空口时间对齐要求通常在 1.5 µs 量级——早就超了，表现是某个方向吞吐莫名其妙差、邻站互干扰。
    • 打时间戳的位置与走的队列不同：PTP 是硬件在 MAC/PHY 打戳、走 S 面最高优先级的小报文，它刻意绕开的正是 U 面要经历的那条路（网卡队列、交换机 U 面队列、协议栈）。Type 5 可以配成和 U 面同一个 VLAN/PCP，还能用 Dummy bytes 撑到 IQ 报文的典型大小，于是量到的是 IQ 真实的体验。

    所以两者是互相验证：PTP 锁定但 Type 5 超标 ⟹ 时钟没问题、传输路径有问题（多了一跳、队列堵了、光缆改绕了）；PTP 没锁而 Type 5 读数离谱 ⟹ 先修 S 面，别去查网络。

    加分陷阱：读数为负一定是时钟没对齐，不是「负时延」；恒定偏置几乎一定是 Compensation Value 没配；空网测出来的只有传播 + 串行化时延，必须带载测并看高分位（平均 45 µs 而 P99.99 是 130 µs 的链路是坏链路）。

  3. 中级eAxC ID 是什么？它是怎么编码的？配错会怎样？

    是什么：eAxC（extended Antenna-Carrier）是「一条空间流 × 一个载波」这种数据流的标识，装在 eCPRI 的 PC_ID（U 面）/ RTC_ID（C 面）字段里，共 16 bit。它是前传上给成百上千条并行 IQ 流分流的门牌号。

    为什么需要它：同一根光纤上同时流着几百条互不相干的流（第 3 扇区第 2 载波第 17 根天线的上行采样，和第 1 扇区第 1 载波第 4 层的下行采样毫无关系）。接收端必须在拿到报文的第一个纳秒就判断「这属于哪条流、送到哪块内存」——这个判断只能是几个移位和掩码，不能遍历查找。所以它被放在 eCPRI 头之后紧接着的位置。

    怎么编码：16 bit 从高位到低位切成四段——DU_Port_ID（区分 DU 侧处理单元/端口）、BandSector_ID（频段+扇区）、CC_ID（载波）、RU_Port_ID（RU 侧空间流/天线端口，PRACH 等专用通道通常占独立取值）。四段的位宽是 M 面可配置的，加起来必须正好 16，而且两端必须配成完全一样。

    配错的后果，按辨识度排：

    • 位宽两端不一致 → 整体错位 → RU 解出一个没配置过的组合 → 按规范静默丢弃 → 链路 up、PTP 锁定、C 面可能还通，就是没业务。
    • CC_ID 错 → IQ 进了错误载波 → 该载波 EVM 差、邻频干扰，而两个载波都「有数据」，看不出缺失。
    • RU_Port_ID 映射错 → 天线顺序错 → 波束指向错、MIMO 秩下降。单天线测试全过，只有多流才暴露。
    • PRACH 的 eAxC 漏配 → 老用户全正常，新用户接不进，KPI 上只有随机接入成功率跳水，极易被误判成核心网问题。
    • 两条流用了同一个 ID → 接收端看到两个独立计数器交织 → 现象酷似严重乱序 + 疯狂丢包，链路其实好得很。

    排障要点：查这类问题必须两端同时打印 16 bit 的原始值，不能各自打印解码后的 DU_Port=1, CC=0——两边解码规则本来就不一样，打出来自然都「对」。

  4. 中级SEQ_ID 有什么用？它能发现哪些问题、发现不了哪些？

    eCPRI 只说 SEQ_ID 是 2 字节序号；O-RAN 把它切成两半，同时干两件事：

    • seqId（8 bit）：每条 eAxC 独立的计数器，逐报文 +1，用于丢包与乱序检测。
    • E 位（1 bit）+ subSeqId（7 bit）：无线传输层分片。一个符号一条流的 IQ 有 7 KB 量级，MTU 1500 装不下必须拆；E=1 表示这是最后一片。注意这不是 IP 分片，所以走二层承载时也一样要分。

    它发现不了什么——这是区分度所在。seqId 只有 8 bit，256 个值。算一下：MTU 1500、100 MHz、30 kHz SCS 时一条下行 eAxC 是 6 报文/符号 × 14 符号 × 2000 时隙/s = 168 kpps，256 ÷ 168 k ≈ 1.52 ms 就回绕一圈。所以：

    • 能可靠发现零星丢包；
    • 发现不了长时间中断——连续丢超过 256 个报文，gap 会绕回来看着正常。中断得靠「报文完全停了」来判。
    • 顺带一个巨帧的隐性收益：MTU 9000 后降到 28 kpps，回绕周期变成约 9.1 ms，可观测窗口宽了 6 倍。

    实现要点：用 uint8_t gap = seq - expected 让回绕天然正确；gap < 128 算丢包，gap >= 128 是旧包（乱序/重复），此时千万不要更新 expected，否则会误报一大片丢包。

    判读口径：缓慢线性增长 → 稳定低速丢包，查 QoS/队列/光功率；一簇一簇跳 → 突发拥塞，找同时刻的大流量事件；只有个别 eAxC 有问题 → 配置或映射问题；所有 eAxC 一起 → 公共原因（链路/队列/时钟）。「乱序/重复」计数暴涨则首先怀疑两条流撞了同一个 eAxC ID，其次怀疑 LAG/ECMP 把一条流散到了多条路径。

8.3 高级（体现深度）

  1. 高级一个站点上有多少条 eAxC 流？怎么估？

    骨架公式：

    总流数 ≈ 下行流数 × 载波数 × 扇区数 + 上行流数 × 载波数 × 扇区数 + PRACH/SRS 等专用通道

    关键在于「下行流数」不等于天线数，它取决于谁做预编码——这是这道题最大的变量，也是区分度所在：

    • Category A（预编码在 DU）：DU 算完预编码，把每根物理天线的 IQ 送给 RU，RU 只做上变频与放大。下行 eAxC 数 = 物理天线数（32T → 32 条）。RU 简单便宜，代价是前传带宽按天线数线性膨胀。
    • Category B（预编码在 RU）：DU 只送每个空间层的 IQ，波束权值走 C 面，RU 自己展开到 32 根天线。下行 eAxC 数 = 层数（4 层 → 4 条），带宽省 8 倍，代价是 RU 变复杂、接口耦合更深。

    上行通常没有这个自由度：RU 一般把每根接收天线的采样都送上去让 DU 做合并与均衡，所以上行 eAxC 数 ≈ 接收天线数。于是 Category B 下会出现一个反直觉的现象——上行的流数和带宽反而远大于下行。

    几个量级（含 PRACH 等专用通道）：

    • Cat A、32T32R、1 载波 1 扇区：32 + 32 + 几条 ≈ 68
    • Cat B、32T32R、4 层、1 载波 1 扇区：4 + 32 + 几条 ≈ 40
    • Cat B、32T32R、8 层、2 载波 3 扇区：48 + 192 + 十几条 ≈ 250~270
    • Cat A、32T32R、4 载波 3 扇区：384 + 384 + 几十条 ≈ 800+

    这也解释了 16 bit 的 ID 空间（65536）为什么够用又不能浪费：单站几百条是常态，但一个 DU 可能挂十几个 RU，而 DU_Port_ID 还要从这 16 bit 里先分走几位。

    别忘了 PRACH：它通常占独立的 RU_Port_ID 取值，采样率和带宽都与 PUSCH 不同，配置项也是分开的——漏配的现象就是前面那道题里说的「老用户正常、新用户接不进」。

  2. 高级前传丢包为什么不重传？那可靠性从哪来？

    把两边的代价算出来对比，结论就不需要争论了。

    丢一个报文的代价（以 50 PRB / 报文为例）：损失 273 个 PRB 里的 50 个，即该符号该流约 18% 的资源单元，时间跨度是一个符号约 35.7 µs（一个时隙的 1/14）。这些 RE 的软信息按「擦除」处理，LDPC 本来就有冗余，很可能纠回来；纠不回来才 CRC 失败，然后由空口 HARQ 重传——一个本来就存在、且时间尺度与反馈路径都为此优化过的机制。

    在前传上重传的代价：发现丢包要等下一个报文到达，请求要一个单向时延，重发到达再一个单向时延，合计 > 100 µs，而这只是理论下限。结果是：这个符号的接收窗口照样关了，数据仍然没用，外加三重额外开销——白占一份带宽、DU 要为所有已发数据保留重传缓冲、重传造成的突发让本就拥塞的链路更堵。

    所以不重传不是妥协，是唯一正确的选择：丢包的代价是「一次可能的 HARQ 重传」，等待的代价是「同样丢掉这个符号，外加三重开销」。

    可靠性被推到了代价最低的那几层：

    • 物理层 FEC：25G/100G 以太网自带 RS-FEC，链路上的随机比特错误在这一层就纠掉，根本到不了 eCPRI。它引入的是固定时延（可预算），而不是不确定时延。
    • QoS 隔离：VLAN + PCP 把 U 面和 M 面的大流量分到不同队列并配严格优先级。
    • 带宽余量：前传不按「刚好够」规划，留余量让队列几乎不排队。
    • 空口 HARQ：真漏过去了由它兜——它本来就是为「无线信道会出错」设计的。

    工程上对 U 面帧丢失率的要求通常在 10⁻⁷ 量级或更严（具体指标以所用 O-RAN 传输需求文档与运营商规范为准）。协议层完全不做可靠性，只用 SEQ_ID 做感知。

    可以升华的一句：可靠性应该放在「代价最低、时间尺度最匹配」的那一层。传输层重传的代价是不确定的时延——恰恰是前传最不能付的那一种。同一逻辑也解释了实时音视频为什么用 UDP + 应用层 FEC/NACK 而不是 TCP。

  3. 高级IQ 压缩怎么权衡压缩率和 EVM？为什么 BFP 最常用？

    BFP（块浮点）的原理：一组样本（通常一个 PRB，12 子载波 × I/Q = 24 个样本）共享一个 2 的幂次指数，各自只存低位尾数。编码就是「求块内最大绝对值 → 决定移位量 → 全体右移 → 存尾数 + 1 字节指数」。压到 9 bit 时每 PRB 从 48 B 降到 27 + 1 = 28 B，压缩比约 1.71×。

    BFP 胜出的真正原因不是压缩比最高，而是硬件代价最低：整个编码只要「求最大值 + 前导零计数 + 移位」，没有乘法、没有查表、没有反馈环路，一条组合逻辑流水就能做完。Block Scaling 精细一点但解码要做乘法；μ-law 小信号精度更好但实现复杂、误差难分析；Modulation Compression 压缩比高但强依赖调制信息、本质是下行专用。

    BFP 的软肋：误差由块内最大值决定。一个特别强的子载波会把整块的移位量顶上去，块内幅度小的子载波就被压得只剩几个有效位。OFDM 在一个 PRB 内幅度通常接近，所以平常没事；但在强频率选择性衰落、窄带干扰、或一个 PRB 内同时有强参考信号和弱数据时，弱分量的相对量化噪声明显恶化。现象是整体 EVM 看着还行，但处在深衰落频点上的那个终端解调质量莫名其妙地差。

    位宽怎么定——关键是理解压缩噪声只是 EVM 预算里的一小项。3GPP 对基站发射 EVM 按调制阶数规定上限（阶数越高越严，256QAM 已是个位数百分比量级，1024QAM 更严；具体数值查 TS 38.104 对应版本的表格），而这份预算要分给功放非线性与 DPD 残差、本振相噪、通道校准误差、数字前端定点误差，最后才轮到压缩。所以正确的推导方向是反过来：

    1. 这个小区要不要支持 256QAM / 1024QAM → 决定 EVM 上限；
    2. 扣掉射频链路已经吃掉的部分 → 剩给压缩的裕量决定位宽下限；
    3. 位宽 × 流数 × 载波数 → 带宽需求，对比链路能力。

    典型结论：9 bit 是多数实现的默认值（1.71×）；8 bit（1.92×）要谨慎，适合带宽极紧、以低阶调制为主的覆盖场景；想稳上高阶调制就得考虑 12 bit（1.30×）或不压缩。如果算下来带宽不够，正确的动作往往不是继续压位宽（那会直接砍掉高阶调制的可用性），而是换 Category B 把下行流数降下来，或者升级链路速率。

    一个很少被提起的实现代价：9 bit 不是字节对齐的，样本在字节流里连续位打包，周期是 9 字节（8 个样本），SIMD 展开时的分支与查表比 12 bit（两个样本正好 3 字节）复杂得多。带宽上 9 bit 更省，解码侧的 CPU/FPGA 代价更高。

  4. 高级某站点前传误码率突然升高、RU 报 U 面丢包告警，你怎么定位？

    核心方法论：先用免费的统计把搜索空间劈成两半，再决定要不要抓包。反过来做（先搭采集环境抓 200 GB）常常是花两天验证「问题在配置里」。

    第 1 步：分清「全网 vs 单流」——这一步决定后面所有方向。让 DU 导出按 eAxC 聚合的 SEQ_ID 丢包/乱序计数：

    • 所有 eAxC 一起丢 → 公共原因：链路误码、队列拥塞、时钟异常。
    • 只有部分 eAxC 丢 → 配置、映射、或这几条流共同经过的某个队列。
    • 「乱序/重复」而不是「丢」在涨 → 优先怀疑两条流撞了同一个 eAxC ID，其次是 LAG/ECMP 把一条流散到多条路径。

    第 2 步：确认时间基准，别在错误的前提上排查。看 PTP 是否锁定、有没有发生 GM 切换，再读 Type 5 的单向时延（两个方向都要）。顺序不能反：PTP 没锁时 Type 5 的读数没有意义（负值或明显偏小就是这个原因）；读数带恒定偏置则是 Compensation Value 没配。PTP 锁定而 Type 5 超标，说明时钟没问题、传输路径有问题——多了一跳、队列堵了、光缆改绕了。

    第 3 步：分层排除物理层。看光功率是否在预算内、光模块温度、以及网卡/交换机的 FEC 纠错计数与不可纠错计数、rx_crc_errors。CRC 与 FEC 不可纠错计数在增长 = 物理层问题（光衰、脏连接器、坏模块、温漂），软件再烂也造不出 CRC 错误；反过来 CRC 为 0 而队列丢包在涨，就别去动光缆。

    第 4 步：查 QoS 是否真的生效。丢包时刻和什么事件重合？如果总在做 M 面操作（固件下载、性能数据批量上报）时出现，就查 PCP：在链路两端各抓一次包比对 vlan.priority——只在一端抓等于没验，因为中间那一跳很可能重写了它（untagged 端口默认打标、信任域边界 remark、「不信任接入端口 CoS」一律置 0）。同时查交换机各出口队列的丢包计数，确认 PCP 真的映射到了独立队列并配成严格优先级。

    第 5 步：确认容量与 MTU。链路利用率、巨帧是否端到端开到位（大包不通小包通 = 某跳 MTU 不足）、over UDP/IP 时有没有发生 IP 分片。

    第 6 步：真需要抓包时，注意三件事。① 先跑 ethtool -i：DU 的 U 面网卡多半被 DPDK 绑到 vfio-pci，tcpdump 什么都看不见，得改用 dpdk-pdump、交换机镜像或无源光分路器（插分路器前必须核对光功率预算，否则会亲手制造出正在追查的误码）。② 一定加 -s 64：需要的字段全在前 36 字节里，数据量降到 1/23，25 GbE 满载从 3.1 GB/s 变成 137 MB/s。③ 用 ether[16:2] == 0xaefe（带 VLAN 时 EtherType 在偏移 16）并按 ether[22:2] 锁定具体 eAxC，再配 -W/-C 环形缓冲长时间挂着等复现。

    一个真实案例的收束：某站点上行吞吐周期性掉坑，SEQ_ID 统计显示 380 条 eAxC 里只有 4 条在丢，且属于同一个 BandSector_ID + CC_ID，每隔十几秒一簇。「部分流 + 周期性成簇」直接排掉了链路误码（会全流一起且与光功率相关）、时钟（PTP 与 Type 5 均正常）和带宽（利用率不到 60%），指向队列。两端抓包对比发现 DU 侧 PCP=5、RU 侧变成 0：RU 一个后加载波的 VLAN 子接口配置模板漏填 PCP，交换机按默认策略重打为 0，这 4 条流掉进了和 M 面共用的 best-effort 队列，而网管每十几秒一次的性能数据上报正好打满它。修复分两层：短期补配置，长期在交换机上按 VLAN 强制 remark，让「RU 侧漏配」不再能影响业务。
