eCPRI：消息、IQ Data、Control 与 Synchronization

上一篇讲了 eCPRI"为什么"出现。这一篇彻底拆开它：一个 eCPRI 包由哪些字段组成？它到底是不是跑在 TCP/UDP 上？它和以太网是什么关系？我们会把一个 eCPRI 帧从以太网头一直剖到 IQ payload，回答这些高频而又常被搞错的问题。

协议深潜 ★★★★☆ Module 04 阅读 ~28 min
01

eCPRI 到底跑在什么上

先破除最大的误解

回顾 Module 01 的关键区分：协议 ≠ 传输机制。eCPRI 是协议（定义前传消息格式），它需要一个传输机制来搬运。eCPRI 规范定义了两种承载方式：

① eCPRI over Ethernet（主流）

eCPRI 消息直接封装在以太网帧的 payload 里，用 EtherType 0xAEFE 标识。没有 IP、没有 TCP/UDP。这是 O-RAN 前传最常用的方式——延迟最低、开销最小。

② eCPRI over UDP/IP（可选）

需要跨三层路由时，可把 eCPRI 封装在 UDP/IP 里。注意：即便走 IP，也是 UDP 而非 TCP——前传要低时延、不要重传。

所以那个经典问题的答案是：eCPRI 通常直接跑在以太网上（L2），不经过 TCP/IP；需要时可选 UDP/IP，但绝不会用 TCP。原因：TCP 的握手、重传、拥塞控制引入的时延和不确定性，对 ~100µs 级的前传是灾难。前传宁可丢也不能等。
02

eCPRI Common Header 结构

4 字节，简洁到极致

每个 eCPRI 消息都以一个固定的 Common Header（4 字节） 开头：

eCPRI Common Header（4 字节）
+--------+--------+----------------+
| byte0  | byte1  |    byte2-3     |
+--------+--------+----------------+
 byte0:  bit7-4 协议版本(Protocol Rev)
         bit3-1 保留(Reserved)
         bit0   C位(Concatenation, 是否有后续拼接消息)
 byte1:  Message Type（消息类型，0~63）
 byte2-3: Payload Size（本消息 payload 字节数, 大端)
  • Message Type 是关键：它决定后面 payload 怎么解析（是 IQ 数据？还是控制？还是同步测量？）。
  • Payload Size 就是 Module 01 讲的"长度前缀"——eCPRI 用它做消息分帧。
  • C 位：一个以太网帧里可以拼接多个 eCPRI 消息（concatenation），C=1 表示后面还有，提升带宽效率。
看，这就是 Module 01"协议 6 要素"的活教材：版本（Protocol Rev）、语义分类（Message Type）、分界（Payload Size）、拼接（C 位）。学过二进制协议设计的话，你会发现 eCPRI header 就是一个教科书式的紧凑二进制头。
03

四类主要消息

Message Type 家族

eCPRI 定义了多种 Message Type，最常用的可归为四类：

类别典型 Message Type作用
User Data / IQType 0：IQ Data传输用户面基带 IQ 采样（前传主力流量）
ControlType 2：Real-Time Control Data与 IQ 关联的实时控制（波束、调度参数等）
SynchronizationType 5：One-way Delay Measurement测量单向时延，辅助同步/时延管理
Management/其他Type 3/4/6/7…远程复位、事件指示、通用数据传输等
注意区分：eCPRI 自身的这几类消息（IQ/Control/Sync）主要对应前传的用户面与相关控制/同步测量。而 O-RAN 语境下的"CUS 平面"（Control/User/Sync）是更完整的前传分面框架——两者相关但不完全等同，见本篇最后一节与 O-RAN 三平面。
04

IQ Data 报文剖析

前传里 99% 的流量长这样

一个 IQ Data 消息（Type 0）在 Common Header 之后，还有 eCPRI 自己的定位字段，再接真正的 IQ 采样：

IQ Data Message
+---------------------+  eCPRI Common Header (4B, Type=0)
| PC_ID (2B)          |  实时上下文标识（关联到某个数据流/天线端口）
| SEQ_ID (2B)         |  序号（检测丢包/乱序）
+---------------------+
|     IQ Samples ...  |  频域 IQ 采样（I/Q 各若干 bit，可压缩）
+---------------------+
  • PC_ID（Real-Time Control / eAxC ID）：标识这段 IQ 属于哪个"天线-载波"数据流（eAxC）。一个小区有很多这样的流。
  • SEQ_ID：序号，接收端据此发现丢包/乱序（前传不重传，但要能感知质量）。
  • IQ Samples：真正的负载——频域 IQ，位宽可配置（如 9/12/14 bit），常配合块浮点压缩进一步省带宽。
eAxC（extended Antenna-Carrier）：O-RAN 前传里对"一个天线端口 × 一个载波"数据流的标识。前传上并行流动着成百上千个 eAxC 流，PC_ID/eAxC ID 就是给它们分流的"门牌"。
05

一个完整前传帧长什么样

从最外层以太网头剖到 IQ

以太网头 (14B+)目的/源 MAC + 可选 VLAN 标签(含 QoS PCP) + EtherType 0xAEFE
eCPRI Common Hdr (4B)版本 / Message Type=0(IQ) / Payload Size / C 位
eCPRI IQ 字段PC_ID(eAxC) + SEQ_ID
O-RAN U-Plane 头（O-RAN 7-2x 场景）时频定位：frameId / subframeId / slotId / symbolId + section 信息
IQ Payload频域 IQ 采样（含压缩头 + 压缩后的 I/Q 比特）
以太网 FCS (4B)帧校验
对照 Module 01 的封装图：eCPRI 就是"应用层协议"，被以太网这个"传输机制"直接承载。中间没有 TCP/IP 这两层（over UDP/IP 时才有 IP+UDP）。这就是为什么 eCPRI 能做到极低时延。
06

eCPRI 与 IP/TCP/UDP 的关系

一张对照表终结困惑

问题答案
eCPRI 跑在 TCP 上吗？不。TCP 的重传/拥塞控制不符合前传低时延确定性要求
eCPRI 一定要 IP 吗？不。主流是直接 over Ethernet（L2）；跨三层时才用 UDP/IP
eCPRI 是"更快的 TCP"吗？不。它是前传协议，与 TCP 不在一个维度（协议 vs 传输机制）
eCPRI 和以太网是什么关系？以太网是 eCPRI 的承载/传输机制；eCPRI 是被以太网搬运的协议
丢包了怎么办？前传不重传；靠 SEQ_ID 感知、靠 QoS/工程保障低丢包，宁丢不等
07

CUS 平面与同步

前传上并行的三/四类流量

在 O-RAN 7-2x 前传里，DU↔RU 之间同时流动着几类流量（常称 CUS 平面）：

  • U-Plane（用户面）：IQ 数据，占绝大部分带宽。
  • C-Plane（控制面）：调度/波束等实时控制，必须比对应 U-Plane 数据略早到达。
  • S-Plane（同步面）：PTP/SyncE 报文，负责频率+相位同步。
  • M-Plane（管理面）：NETCONF/YANG 配置 RU（见 NETCONF/YANG）。
这些平面共享同一张前传以太网，靠 VLAN + QoS 优先级 严格隔离：S-Plane/C-Plane 优先级最高（时间/控制不能晚），U-Plane 次之，M-Plane 最低。这正是 Module 01 的 VLAN/QoS 机制在前传的关键应用。完整的三平面框架见 O-RAN 三平面。
🎯 本篇要点回顾
  • eCPRI 主流直接 over Ethernet（EtherType 0xAEFE），可选 over UDP/IP，绝不用 TCP
  • Common Header 4 字节：版本 / Message Type / Payload Size / C 位（拼接）
  • 四类消息：IQ Data / Real-Time Control / Sync（时延测量）/ 其他
  • IQ Data 含 PC_ID(eAxC) + SEQ_ID + 频域 IQ 采样（可压缩），不重传靠 SEQ_ID 感知
  • 前传 CUS(+M) 多平面共网，靠 VLAN+QoS 隔离，S/C 面优先级最高
