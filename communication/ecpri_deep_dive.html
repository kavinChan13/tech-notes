eCPRI：消息、IQ Data、Control 与 Synchronization

上一篇讲了 eCPRI"为什么"出现。这一篇彻底拆开它：一个 eCPRI 包由哪些字段组成？它到底是不是跑在 TCP/UDP 上？它和以太网是什么关系？我们会把一个 eCPRI 帧从以太网头一直剖到 IQ payload，回答这些高频而又常被搞错的问题。

01

eCPRI 到底跑在什么上

先破除最大的误解

本篇只讲 eCPRI 协议本身：怎么被承载、Common Header 有哪些字段、有哪些消息类型、一个 IQ 报文从以太网头到 payload 逐字节长什么样。前传为什么演进成今天这样见 CPRI/eCPRI 演进；C/U/S/M 在时间上怎么配合见 O-RAN 平面；这段以太网在传输网里的位置见 前传/中传/回传。这三块只引用、不重复。
切分点的完整取舍见 3GPP Functional Split；本篇之后一律假定 Option 7-2x。

再回顾一个关键区分：协议 ≠ 传输机制。eCPRI 是协议——它定义前传消息的格式与语义（这一段字节是 IQ 还是控制、属于哪条流、第几号），但不负责把字节搬到对端。搬运的活儿交给两种承载方式：

1.1 以太网直承：一个前传帧的最外层

① over Ethernet（主流）把 eCPRI 消息直接放进以太网帧的 payload，用 EtherType 0xAEFE 标识，没有 IP、没有 TCP/UDP；② over UDP/IP（可选）用于跨三层路由，但传输层仍是 UDP。「直承」的意思非常字面：以太网帧头之后紧接着就是 eCPRI 的第一个字节，中间没有任何一层。0xAEFE 是 IEEE 给 eCPRI 分配的类型值，作用是告诉接收方「payload 请按 eCPRI 解析」——网卡分类器、交换机 ACL、Wireshark 解析器都靠它。

二层受偏爱，本质上是省掉了每一跳的「查路由 + 改包头」：交换机按「目的 MAC + VLAN」查一次 CAM 表就转发，端口到端口时延在亚微秒到几微秒量级；三层转发要查最长前缀匹配、减 TTL、重算校验和，还多一层排队。前传单向预算只有百微秒量级（由 O-RAN 的 T2a / Ta3 / Ta4 等窗口决定，以所用配置为准），每跳省下的几微秒都是实打实的。附带收益是RU 侧的简化：U 面走纯二层，RU 的数据通道不需要 IP 栈、ARP、分片重组，可以做成一条硬件流水——RU 上真正需要 IP 的只有 M 面和 S 面的部分部署形态。

1.2 开销算一遍：为什么前传一定开 Jumbo Frame

「开销小」不是形容词，可以算出来——这笔账同时解释了为什么前传几乎都要求端到端支持巨帧。

把 4.7% 换算成钱：一个 100 MHz、8 流的小区 U 面裸速率约 13 Gbit/s，4.7% 就是 600 Mbit/s 的纯包头，汇聚时直接决定「一根 25G 够不够」。所以「MTU 有没有端到端开到 9000」是开站清单里的必查项——任何一跳没开，要么分片、要么直接丢大包。

1.3 UDP/IP 承载：换来什么，代价是什么

既然二层这么好，为什么规范还留了 UDP/IP？因为二层的前提是「DU 和 RU 在同一个广播域里」，而这个前提会被三种情况打破：中间要过一段已三层化的共享传输网；一张前传网要服务多厂商/多租户、必须靠 IP 划边界；或者只是实验台架，DU 就是一台普通服务器。

维度over Ethernet（L2）over UDP/IP（L3）
网络前提DU/RU 同广播域，中间只能是交换机可跨路由器、跨子网、跨机房
寻址目的 MAC + VLANIP + UDP 端口（更好管理、可做 ACL/策略）
时延抖动小、可预测取决于中间路由器的队列，更难约束
分片风险无（MTU 不足直接丢，问题暴露得早）有，见下方警告
同步（S 面）PTP 二层 profile，边界时钟部署直接路由器必须支持 BC/TC，时间预算更难守
典型用法O-RAN 7-2x 生产网，绝大多数跨域/共享传输、实验台架、时延要求较宽的分割点
UDP/IP 承载最阴的坑是分片。IQ 报文本来就贴着 MTU 走，路径上任何一跳 MTU 偏小（隧道、VLAN 叠加、某台设备默认 1500）就会分片，后果三重：重组需要缓存与定时器，时延确定性没了；UDP 分片丢一片等于整个报文全废；很多硬件加速路径不处理分片，软件兜底让 CPU 占用翻几倍。正确做法是端到端对齐 MTU（并留出隧道余量），让「装不下」表现为明确丢包 + 计数器增长，而不是悄悄分片。

另外 eCPRI 没有固定的知名 UDP 端口，端口靠两端约定。后果：抓包要手工 Decode As → eCPRI，做 ACL/QoS 分类时不能照抄别人的端口号。

1.4 两种承载都不走 TCP

这是最高频的误解，所以要说得很死：eCPRI 的两种承载方式里都没有 TCP。L2 直承时连传输层都没有；over IP 时用的是 UDP。原因不是「TCP 慢」这种笼统印象，而是 TCP 的每一项核心机制都和前传的需求正面冲突——握手与连接状态、累积 ACK 与重传、拥塞窗口、慢启动、有序交付、Nagle、滑动窗口，逐条拿到前传上试的结果见 §6.1 那张表，那里也有杀伤力最大的一个数字（RTO 下限差三个数量级）。

经典问题的标准答案：eCPRI 通常直接跑在以太网上（L2，EtherType 0xAEFE），不经过 IP；需要跨三层时可选 UDP/IP，但两种方式都绝不会用 TCP。再补一句「前传的正确策略是宁丢不等——丢掉的那点 IQ 由空口 HARQ 去兜，而不是由传输层重传去兜」，就说到根上了。
02

eCPRI Common Header 结构

4 字节，简洁到极致

每个 eCPRI 消息都以一个固定的 Common Header（4 字节） 开头。整个 eCPRI 协议的「公共部分」就只有这 4 个字节，剩下的一切都由 Message Type 决定怎么解析：

2.1 四个字段逐条讲清

Concatenation（拼接）：把多个独立的 eCPRI 消息塞进同一个以太网帧，用第一个字节的 C 位串成链。动机很朴素——一帧的固定开销（以太网头 + FCS + 前导 + IFG）有 42 字节，如果每个 40 字节的实时控制消息都单独发一帧，效率不到一半。拼接之后这 42 字节被多个消息分摊。

拼接有一条容易漏掉的规则：除最后一个消息外，每个被拼接的消息都要补齐到 4 字节边界（以所用规范版本为准），填充字节不计入 payloadSize。理由是硬件友好——接收侧的解析流水希望每个消息头都落在 32 位对齐的位置上。

算一下收益：三个 38 B 的控制消息各发一帧要占 (42+4+38)×3 = 252 B 线路时间，拼接成一帧只占 42 + (4+38+2)×2 + (4+38) = 172 B，省约 32%。另外 C 位是唯一的「后面还有」指示，没有消息计数字段——解析必须循环到 C=0，且每一步都要重新做边界检查。

2.2 一个 Common Header 的十六进制逐字节拆解

下面这 4 个字节取自本篇后面要完整拆解的那个下行 IQ 报文（第 5 章会把整帧铺开）：

2.3 解析这 4 个字节时踩过的坑

这个头简单到几乎不可能写错，但真实代码里翻车的地方非常固定，全都不在「读字段」这一步。最常见的一个是拿以太网帧长当消息长度：以太网有 60 字节最小帧的规定，Type 6 之类的短消息会被网卡自动填充，按帧长去切 payload 就会把填充字节当业务数据读进来。永远信 payloadSize，不要信帧长。

解析循环里的每一步必须做的检查漏了会怎样
取头之前剩余字节 ≥ 4越界读；剩余非 0 但不足 4 应计入「尾巴」计数器
读 protRev等于本实现支持的版本字段可能整体挪位，「尽力解析」会得到垃圾
读 payloadSizentohs 转序，且 ≤ 剩余字节 − 4越界读几十 KB，见下方警告
C=1 跳下一个步长按 (4 + psz + 3) & ~3 补齐，且 < 剩余解析错位或死循环
C=0 收尾剩余字节应为 0，否则计数要么是最小帧填充，要么是你漏解析了一个消息
「payloadSize ≤ 剩余字节 − 4」是安全边界，不是健壮性锦上添花。它是一个 16 bit、完全由对端控制的长度字段；少了这个检查，一个损坏或恶意构造的报文就能让你越界读到几十 KB 之外。而前传网络上确实会出现比特翻转造成的畸形长度——FCS 只保护到网卡那一层，DMA 之后的内存错误它管不着。另外 len 必须是「EtherType 之后的有效字节数」，不能直接用网卡给的帧长。
这个头是紧凑二进制协议的教科书样本，值得和自己设计的协议对照：版本（留升级余地）、类型分发（8 bit 够用几十年）、显式长度（不依赖分隔符也不依赖底层帧长）、批量指示（C 位摊薄固定开销）、对齐规则（4 字节边界，为硬件流水服务）。四字节做到这个信息密度，靠的是没有一个「以后再说」的字段。

四类主要消息

Message Type 家族

eCPRI 定义的 Message Type 按用途可归为四类：用户数据、实时控制、同步测量、管理与其他。但「规范定义了」和「现网真的在跑」是两件很不一样的事：

被问到「eCPRI 有哪些消息类型」时，按重要性回答而不是按编号背诵：先说现网真跑的三种，再说其余的规范里有但管理与告警都走 M 面。这样既覆盖全表，又说明你见过真实的前传。

3.1 Type 5：单向时延测量，最实用也最常被忽略

它解决的问题是：前传的时延预算是单向的（IQ 必须在 RU 的接收窗口内到达），可 ping / TWAMP / iperf 量的都是往返再除以 2。这个「除以 2」在前传上是错的——去回光纤不同长、两个方向队列深度不同，往返 80 µs 可能是 40/40，也可能是 55/25。Type 5 直接量单向：发送方把发送时刻写进报文，接收方用自己的时钟记下接收时刻，相减。

eCPRI Type 5（One-Way Delay Measurement）payload 与算式

 偏移  字段                长度   作用
 ----  ------------------  -----  ---------------------------------------
 +0    Measurement ID       1 B   本次测量的标识；Response / Follow_Up
                                  靠它和对应的 Request 配对
 +1    Action Type          1 B   请求 / 响应 / 跟随 / 反向请求（见下表）

 单向时延算式（一步法）
   DU 在报文离开 MAC 的瞬间写入  t1
   RU 在报文到达 MAC 的瞬间记下  t2
   单向时延 = t2 - t1 - tCV

 例：t1 = 1234567890.500000000    t2 = 1234567890.500042700   tCV = 0
     → 42 700 ns = 42.7 µs

 ★ t1 与 t2 来自★两个不同设备的时钟★，所以这个算式的前提是 S 面已锁定。
   tCV 留空（全 0）时读数会带一个恒定偏置——那是光模块 + SerDes + FPGA
   流水的内部固定时延没被扣掉，不是链路真的变长了。
 ★ 只有 24 字节的测量帧会被以太网填充到 60 字节最小帧，量到的是「短帧」
   的排队行为；要量 IQ 的真实体验，必须用 Dummy 撑到 1400 字节量级。

Action Type名称它在测量流程里干什么
0x00Request发起方发出，TimeStamp 里就带着 t1（一步法，需要硬件在发送瞬间填戳）
0x01Request with Follow_Up两步法第一步：先把报文发出去，TimeStamp 留空

0x03Remote Request「请你来测我」——让对端发起反方向测量，这是量不对称性的关键
0x04Remote Request with Follow_Up同上，但要求对端用两步法
一步法 vs 两步法：一步法要求硬件能在报文正在离开 MAC 的那一刻把时间戳写进已经组装好的字节流里（还要顺手修正校验和）。做不到的实现就用两步法：先发报文、事后读出硬件记录的发送时刻、再用一个 Follow_Up 报文送过去。这和 IEEE 1588 的 one-step / two-step Sync 是完全同一个工程权衡——一步法精度高、不占额外报文，但要硬件支持。

18.6 µs 的不对称是个大事：PTP 的时间恢复默认假设路径对称，它测往返、取一半当单向，所以路径不对称多少，恢复出来的相位就偏掉约一半。超相位的后果是上下行时隙互相踩、邻站互干扰，表现出来是「某个方向的吞吐无缘无故差」。

3.2 Type 5 和 PTP：不是替代关系，是互相验证

维度PTP（IEEE 1588，S 面）eCPRI Type 5
目的建立共同时间基准（频率 + 相位）使用已有的时间基准去量传输时延
前置条件无（它就是提供时间的那一方）必须先有 PTP/SyncE 锁定，否则结果无意义
对称性默认假设路径对称，不对称就变成相位误差能分别测两个方向，不对称直接暴露
打时间戳的位置硬件，MAC/PHY 边界（刻意绕开协议栈与队列）取决于实现；若在 eCPRI 处理层打戳，就包含了网卡队列、DMA、协议栈的时间
走哪条队列S 面 VLAN/PCP，通常配成最高优先级可以配成和 U 面同一个 VLAN/PCP，于是量到的就是 IQ 真实排的那条队
报文大小很小（几十字节）可用 Dummy bytes 撑到和 IQ 报文一样大
回答的问题「两端的时钟对齐了吗？」「IQ 报文实际花了多久？两个方向一样吗？」
「PTP 已经在测时延了，为什么还要 Type 5？」两者是互相验证：PTP 锁定但 Type 5 超标 ⟹ 时钟没问题、传输路径有问题（多了一跳、队列堵了、光缆改绕了）；PTP 没锁而 Type 5 读数离谱 ⟹ 先修 S 面，别去查网络。S 面本身的机制见 PTP 与 SyncE。

先看清 Type 5 量的是整条预算里的哪一段：

Type 5 的价值在开站验收和故障复盘时最大，但要测对，有四个坑：

❌ 只在空闲时测

空网上量到的只有传播 + 串行化，也就是上图里动不了的那两项。真正吃掉预算的队列只在满载、多站汇聚时才出现。必须带载测。

✅ 看分位数，不看平均

前传是硬窗口。平均 45 µs 而 P99.99 是 130 µs 的链路是坏链路。要记录最大值出现的时刻，好和固件下载、邻站开站对齐。

❌ 用小报文测

短帧插队快、不会被大帧的串行化挡住，排队行为和 1400 字节的 IQ 报文不是一回事。Dummy 字段存在的意义就是撑到 U 面报文的典型大小。

✅ 两个方向都测

用 Action 0x03 拿到反方向读数。不对称量会漂移（换光缆、改路由、加一跳都会变），值得进例行巡检。

Type 5 算出来是负数，不要去找「负时延」的解释——那是时钟没对齐。t1 和 t2 来自两个不同设备的时钟，两端偏差多少读数就偏多少，所以负值（或比光纤长度算出的下限还小的正值）唯一的含义是 S 面没锁定 / 正在收敛 / GM 切换过。判读顺序永远是：先确认 PTP 锁定与 GM 稳定，再看 Type 5 的数。

eAxC（extended Antenna-Carrier）：O-RAN 前传里对「一条空间流 × 一个载波」这种数据流的标识。前传上并行流动着成百上千条这样的流，PC_ID（U 面）/ RTC_ID（C 面）里装的就是 eAxC ID，它是给这些流分流的门牌号。

4.1 eAxC ID：16 位里塞进四层含义

为什么需要它：同一根光纤上同时流着几百条互不相干的 IQ 流（第 3 扇区第 2 载波第 17 根天线的上行采样，和第 1 扇区第 1 载波第 4 层的下行采样毫无关系）。接收端必须在拿到报文的第一个纳秒就判断「这属于哪条流、送到哪块内存」——这个判断只能是几个移位和掩码，不能遍历查找。所以它被放在 eCPRI 头之后紧接着的位置，并被切成有层次的位域：

四段位宽可配置、加起来必须正好 16 bit、而且两端必须配成完全一样。这是 O-RAN 前传最经典的一类互通问题：M 面配置里位宽写错一位，DU 编出来的 ID 和 RU 解出来的就整体错位，RU 解出一个没有配置过的组合并按规范静默丢弃——链路 up、PTP 锁定、C 面可能还通，就是没有业务。查这类问题一定要两边同时打印 16 bit 的原始值，而不是各自打印「DU_Port=1, CC=0」这种解码后的字段：两边解码规则本来就不一样，打出来自然都「对」。位宽之和不等于 16 应当在启动时就断言失败，别等到丢包才发现。

4.2 一个站点到底有多少条 eAxC 流

这是个很好的面试题，因为它逼你说清一件事：下行的流数不等于天线数。取决于「谁做波束赋形（预编码）」，同一副 32T32R 天面上的前传流数可以差 8 倍。

Category A：预编码在 DU

DU 算完预编码，把每根物理天线的 IQ 分别送给 RU，RU 只做上变频/放大 → 下行 eAxC 数 = 物理天线数（32T → 32 条）。

Category B：预编码在 RU

DU 只送每个空间层的 IQ，波束权值走 C 面，RU 自己展开到 32 根天线 → 下行 eAxC 数 = 层数（4 层 → 4 条），代价是 RU 变复杂、接口耦合更深。

上行通常没有这个自由度：RU 一般把每根接收天线的采样都送上去让 DU 做合并/均衡，所以 上行 eAxC 数 ≈ 接收天线数。

4.4 为什么前传丢包不重传

第 1 章说了「重传对实时 IQ 没意义」，这里补上更重要的另一半：重传机制其实已经存在，只是在正确的那一层——就是上图最后那条链（定量对比见 §6.2）。所以前传的策略是把丢包率压到「HARQ 兜得住」的水平，然后彻底不管它。工程上对 U 面帧丢失率的要求通常在 10⁻⁷ 量级或更严（具体以所用 O-RAN 传输需求文档与运营商规范为准），达到这个量级靠的是严格 QoS 隔离、足够的带宽余量、不让 M 面大流量和 U 面抢队列——而不是协议层的可靠性机制。

4.5 IQ 压缩：块浮点与位宽选择

前传带宽昂贵，而未压缩的 IQ 非常浪费：16 bit 定点的动态范围是为「整个小区任意时刻任意功率」准备的，可同一个 PRB 内 12 个相邻子载波的幅度其实很接近。块浮点（Block Floating Point, BFP）正是吃这个冗余——一组样本共享一个指数，各自只存低位尾数。

BFP 的误差由「块内最大值」决定，这是它的软肋。指数全块共享，一个特别强的子载波会把整块的移位量顶上去，块里幅度小的子载波就被压得只剩几个有效位。OFDM 在一个 PRB 内幅度通常接近，所以平常没事；但在强频率选择性衰落、窄带干扰、或一个 PRB 内同时有强参考信号和弱数据时，弱分量的相对量化噪声明显恶化。表现是：整体 EVM 看着还行，但处在深衰落频点上的那个终端解调质量莫名其妙地差。

怎么定位宽？关键是理解压缩噪声只是 EVM 预算里的一小项。3GPP 按调制阶数规定发射 EVM 上限（阶数越高越严，具体数值查 TS 38.104 对应版本的表格），而这份预算要先分给功放非线性与 DPD 残差、本振相噪、通道校准误差、数字前端定点误差，最后才轮到压缩。所以正确的推导是反过来：要不要支持 256QAM/1024QAM → 决定 EVM 上限 → 扣掉射频链路吃掉的部分 → 剩下的裕量决定位宽下限。这就是「9 bit 常见、8 bit 要谨慎、想上 1024QAM 得考虑 12 bit」的由来。

时间一个 OFDM 符号 ≈ 35.7 µs（时隙的 1/14）发现丢包 ≥ 1 个报文间隔 + 请求 50 µs + 重发 50 µs > 100 µs，且这只是理论下限
后果RE 按「擦除」处理 → LDPC 有冗余，很可能纠回来 → 纠不回来才 CRC 失败白占一份带宽 + DU 要为所有已发数据保留重传缓冲 + 突发让本就拥塞的链路更堵
净代价一次可能的 HARQ 重传（本来就有的机制，占几个时隙的调度机会）三重额外开销，换不回任何东西
所以不重传不是妥协，是唯一正确的选择。那可靠性到哪去了？被推到了代价最低的几层：物理层 FEC（25G/100G 以太网自带 RS-FEC，比特错误在这层就纠掉，且只引入固定时延）、QoS 隔离、带宽余量、空口 HARQ。

这条思路值得推广：可靠性应该放在「代价最低、时间尺度最匹配」的那一层。传输层重传的代价是不确定的时延——恰恰是前传最不能付的那种。同一逻辑也解释了实时音视频为什么用 UDP + 应用层 FEC/NACK 而不是 TCP。
07

CUS 平面与同步

前传上并行的三/四类流量

在 O-RAN 7-2x 前传里，DU↔RU 之间同时流动着四类流量（常称 CUS 平面）：U 面的 IQ 数据、C 面的实时控制、S 面的 PTP/SyncE、M 面的 NETCONF/YANG。它们共享同一张以太网，靠 VLAN + QoS 优先级 严格隔离。

四个平面在时间上如何互相配合（C 面要早于 U 面多久、T2a/Ta3/Ta4 窗口怎么算）是另一篇的主题，见 O-RAN 平面。本章只讲与报文直接相关的那一半：优先级具体写在帧的哪一位、配错会怎样、怎么抓包验证。

7.1 优先级到底写在哪一位

回到第 5 章那个帧的偏移 0x000e。这两个字节是 802.1Q 标签的 TCI（Tag Control Information），而整个前传 QoS 体系就压在它前 3 位上：

PCP典型分配（示例）承载什么为什么给这个优先级
7S 面PTP Sync / Follow_Up / Announce / Delay_Req时间报文的抖动会直接变成相位误差，一旦排队就没法补救
5–6C 面eCPRI Type 2（调度、波束权值、PRB 分配）必须早于对应的 U 面数据到达，否则 RU 不知道该怎么处理即将到来的 IQ
4–5U 面eCPRI Type 0（IQ 数据）带宽大户，有硬窗口但比 C/S 面稍宽
2M 面NETCONF、告警、固件文件下载可以等秒级，但流量可以很大——所以必须被压在最低
0best-effort其余管理/调试流量兜底
上表是示例，具体取值由项目/运营商规划决定；要守住的原则就是图里那三条相对次序。而且光在 RU/DU 上打对 PCP 不够——中间每一台交换机都要把 PCP 映射到真正独立的出口队列并配成严格优先级，否则标签打了也白打。
最阴的一种 PCP 故障是「标签打了，但中途被重写」：untagged 入口按端口默认 PCP 打标、信任域边界处 remark、某些设备默认「不信任接入端口的 CoS」而一律置 0。结果是 DU 侧抓包看 PCP=5、RU 侧看 PCP=0。所以验证 QoS 必须在链路两端各抓一次包做对比，只在一端抓等于没验。

7.3 Wireshark 里怎么看 eCPRI

较新的 Wireshark 自带 eCPRI 与 O-RAN 前传 CUS 解析器。常用显示过滤器（字段名以所用版本为准）：ecpri 全部、ecpri.type == 0 U 面 IQ、== 2 C 面、== 5 时延测量、vlan.priority == 5 ★验证优先级打对没有、ptp S 面（和前者对照看队列是否真的分开）。

「IQ 解出来是乱码」几乎从来不是抓包错了，而是解析器不知道该按几位切：eAxC 四段位宽、udIqWidth、udCompMeth 这三组值里任何一个和现网不符，后面的位打包数据就全错位。抓包之前先把这三组值从 M 面配置里抄下来，比抓完再猜省事得多。（over UDP/IP 时还要手工 Decode As，见 §1.3。）

面试题（12 道）

分层自测

8.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础eCPRI 为什么不走 TCP？

    因为 TCP 的每一项核心机制都和前传的需求正面冲突，而不只是「TCP 慢」：

    • 重传对实时 IQ 没有意义。一个 OFDM 符号在 30 kHz SCS 下只占约 35.7 µs，L1 必须在处理窗口内拿到数据。等一个来回之后重传回来的符号不是「迟到的数据」，是垃圾，还白占了本该给新符号的带宽。
    • 拥塞控制会摧毁确定性。IQ 的码率是物理常量——空口每 500 µs 就产生一个时隙的采样，不能因为网络觉得挤就少发。降速的唯一效果是数据在发送缓冲堆积，时延单调上升直到崩掉。
    • 队头阻塞。TCP 是有序字节流，第 100 号段没到、已经收到的第 101 号也交不上去；可它属于另一段 PRB，本该立刻处理。
    • 连接状态成本。一个 RU 上并行几百条 eAxC 流，若每条都要握手、ACK 时钟、重传定时器，RU 就没法做成硬件流水了。

    量化一下最有说服力的那条：Linux 的 TCP_RTO_MIN 就有 200 ms 量级，而前传单向预算是 100 µs 量级，差三个数量级。退一步说，哪怕重传延迟能压到理论下限——发现丢包至少要等下一个报文到达，再走一个来回——也已经是 2 个单向时延，符号窗口早关了。

    加分收尾：正确的策略是「宁丢不等」。前传丢一个报文只损失一个符号里一段 PRB 的资源单元，信道编码有机会纠回来，纠不回来则由空口 HARQ 重传兜住——重传机制本来就存在，只是在正确的那一层。可靠性则被推给了物理层（25G/100G 以太网的 RS-FEC）、QoS 隔离和带宽余量。

  2. 基础eCPRI 有哪两种承载方式？怎么选？

    ① over Ethernet（L2 直承）：以太网头之后紧接着就是 eCPRI 的第一个字节，用 EtherType 0xAEFE 标识，没有 IP、没有传输层。② over UDP/IP：把 eCPRI 消息装进 UDP 载荷。两种都不用 TCP。

    取舍：

    • L2 的优势是省与快：每帧零额外开销；交换机只查一次「目的 MAC + VLAN」，端口到端口时延在亚微秒到几微秒量级；RU 的数据通道不需要 IP 栈、不需要 ARP、不需要分片重组，可以做成硬件流水。
    • L3 换来的是可路由：DU 与 RU 不在同一广播域时（集中式 DU、跨机房、共享三层传输网、多厂商/多租户要用 IP 划边界）只能走这条路；IP + 端口也比 MAC 好管理。
    • L3 的代价：IPv4 每帧多 28 字节（IPv6 多 48）；逐跳要查路由、减 TTL、重算校验和，队列更深、抖动更难约束；PTP 走三层要求路由器支持边界/透明时钟；eCPRI 没有固定知名 UDP 端口，抓包和做 ACL 都得先查项目配置。

    最阴的坑是分片：IQ 报文本来就贴着 MTU 走，路径上任何一跳 MTU 偏小就会分片，而 UDP 分片丢一片等于整个报文全废，还会掉出硬件加速路径。所以必须端到端对齐 MTU，让「装不下」表现为明确的丢包与计数增长，而不是悄悄分片。

    结论：O-RAN 7-2x 生产网上绝大多数是 L2 直承；UDP/IP 多见于跨域/共享传输、实验台架，或时延要求较宽的分割点。

  3. 基础EtherType 0xAEFE 是什么？它在帧里的什么位置？

    它是分配给 eCPRI 的以太网类型值，作用是告诉接收方「这一帧的 payload 请按 eCPRI 解析」。用到它的有三方：网卡的流分类器（把 eCPRI 送到指定队列）、交换机的 ACL / QoS 规则、以及抓包工具的协议解析器。

    位置要说准，因为它会随 VLAN 标签浮动：

    • 不带 VLAN 时：EtherType 在偏移 12（目的 MAC 6 + 源 MAC 6 之后）。
    • 带一层 802.1Q 标签时：偏移 12 是 TPID 0x8100，偏移 14–15 是 TCI（PCP/DEI/VID），真正的 0xAEFE 落在偏移 16。

    这就是为什么 tcpdump 'ether proto 0xaefe' 在前传上经常抓不到东西——前传帧几乎必带 VLAN，得写 'ether[16:2] == 0xaefe'。同理，走 UDP/IP 承载时 EtherType 变成 0x0800/0x86DD，0xAEFE 根本不出现。

    加分：能顺口说出「0xAEFE 之后就是 eCPRI Common Header 的第一个字节，中间没有任何一层，这正是 eCPRI 低时延的结构性原因」。

  4. 基础eCPRI Common Header 有哪几个字段？各自什么作用？

    固定 4 字节，四个字段：

    字段宽度作用
    protocolRevisionbyte0 bit 7–4协议版本，当前规范取 0x1。不认识的版本应计数并丢弃
    reservedbyte0 bit 3–1发 0、收忽略。不要拿来做私有扩展
    C（Concatenation）byte0 bit 01 = 本以太网帧里后面还拼着下一个 eCPRI 消息
    ecpriMessagebyte1消息类型，决定 payload 怎么解析
    ecpriPayloadSizebyte2–3payload 字节数，大端，不含这 4 字节头

    能补上下面这几条细节会明显加分：

    • 拼接的对齐规则：C=1 时，除最后一个消息外每个消息要补齐到 4 字节边界，填充不计入 payloadSize——目的是让接收侧硬件流水的每个消息头都落在 32 位对齐处。
    • 不能用帧长代替 payloadSize：以太网有 60 字节最小帧，短消息会被网卡填充，按帧长切会把填充读成业务数据。
    • payloadSize 必须做边界检查：它是完全由对端控制的 16 bit 长度字段，不检查就是一个越界读漏洞。

    最后一句可以升华：这个头是紧凑二进制协议的教科书样本——版本、类型分发、显式长度、批量指示、对齐规则，四个字节里没有一个「以后再说」的字段。

8.2 中级（区分熟练度）

  1. 中级eCPRI 定义了哪些消息类型？现网真正常用的是哪几种？

    按重要性回答而不是按编号背诵，效果好得多。

    现网真正在跑的只有三种：

    • Type 0（IQ Data）——承载基带 IQ，O-RAN 的 U 面，占前传带宽 95% 以上。
    • Type 2（Real-Time Control Data）——O-RAN 的 C 面，送调度信息、波束权值、PRB 分配，必须早于对应的 U 面数据到达。
    • Type 5（One-Way Delay Measurement）——测单向时延，工程上很有用但常被忽略。

    规范里还有但前传基本用不上的：Type 1（Bit Sequence，对应比特域的分割点）、Type 3（Generic Data Transfer，语义留给厂商）、Type 4（Remote Memory Access，远程读写寄存器，多用于厂商调试工具）、Type 6（Remote Reset）、Type 7（Event Indication）。Type 8 及以上是与传统 CPRI 互通的 IWF 相关类型，只在混合组网/改造期出现。

    关键补充：Type 6/7 用不上是有原因的——在 O-RAN 架构里，复位和告警都走 M 面的 NETCONF/YANG（复位是 RPC，告警是 notification），没必要再用一条实时通道。

    还要能说清一个常被混的点：eCPRI 的消息类型是格式分类，O-RAN 的 C/U/S/M 是功能分面，两者不等同——S 面用的是 PTP/SyncE，不是 eCPRI 消息；M 面用的是 NETCONF，也不是。

  2. 中级Type 5 单向时延测量是干什么用的？它和 PTP 有什么区别？

    它解决的问题：前传的时延预算是单向的，但 ping / TWAMP 这类工具量的是往返再除以 2。这个「除以 2」在前传上是错的——去回光纤不同长、两个方向的队列深度不同，往返 80 µs 可能是 40/40，也可能是 55/25。Type 5 直接量单向：发送方把发送时刻 t1 写进报文，接收方用自己的时钟记下 t2，单向时延 = t2 - t1 - tCV（tCV 是已知内部固定时延的补偿值）。用 Action Type 0x03（Remote Request）让对端发起反向测量，就能拿到两个方向并算出不对称量。

    和 PTP 的区别（这是重点）：

    • 目的相反：PTP 是建立共同时间基准；Type 5 是使用这个基准去量传输时延。所以 Type 5 的前提是 PTP 已锁定，反过来不成立。
    • 对称性假设：PTP 默认假设路径对称，把往返取一半当单向；路径实际不对称多少，恢复出来的相位就偏一半。Type 5 能分方向量，直接把 PTP 掩盖掉的不对称暴露出来。举例：18.6 µs 的不对称会造成约 9 µs 的相位误差，而 TDD 的空口时间对齐要求通常在 1.5 µs 量级——早就超了，表现是某个方向吞吐莫名其妙差、邻站互干扰。
    • 打时间戳的位置与走的队列不同：PTP 是硬件在 MAC/PHY 打戳、走 S 面最高优先级的小报文，它刻意绕开的正是 U 面要经历的那条路（网卡队列、交换机 U 面队列、协议栈）。Type 5 可以配成和 U 面同一个 VLAN/PCP，还能用 Dummy bytes 撑到 IQ 报文的典型大小，于是量到的是 IQ 真实的体验。

    所以两者是互相验证：PTP 锁定但 Type 5 超标 ⟹ 时钟没问题、传输路径有问题（多了一跳、队列堵了、光缆改绕了）；PTP 没锁而 Type 5 读数离谱 ⟹ 先修 S 面，别去查网络。

    加分陷阱：读数为负一定是时钟没对齐，不是「负时延」；恒定偏置几乎一定是 Compensation Value 没配；空网测出来的只有传播 + 串行化时延，必须带载测并看高分位（平均 45 µs 而 P99.99 是 130 µs 的链路是坏链路）。

  3. 中级eAxC ID 是什么？它是怎么编码的？配错会怎样？

    是什么：eAxC（extended Antenna-Carrier）是「一条空间流 × 一个载波」这种数据流的标识，装在 eCPRI 的 PC_ID（U 面）/ RTC_ID（C 面）字段里，共 16 bit。它是前传上给成百上千条并行 IQ 流分流的门牌号。

    为什么需要它：同一根光纤上同时流着几百条互不相干的流（第 3 扇区第 2 载波第 17 根天线的上行采样，和第 1 扇区第 1 载波第 4 层的下行采样毫无关系）。接收端必须在拿到报文的第一个纳秒就判断「这属于哪条流、送到哪块内存」——这个判断只能是几个移位和掩码，不能遍历查找。所以它被放在 eCPRI 头之后紧接着的位置。

    怎么编码：16 bit 从高位到低位切成四段——DU_Port_ID（区分 DU 侧处理单元/端口）、BandSector_ID（频段+扇区）、CC_ID（载波）、RU_Port_ID（RU 侧空间流/天线端口，PRACH 等专用通道通常占独立取值）。四段的位宽是 M 面可配置的，加起来必须正好 16，而且两端必须配成完全一样。

    配错的后果，按辨识度排：

    • 位宽两端不一致 → 整体错位 → RU 解出一个没配置过的组合 → 按规范静默丢弃 → 链路 up、PTP 锁定、C 面可能还通，就是没业务。
    • CC_ID 错 → IQ 进了错误载波 → 该载波 EVM 差、邻频干扰，而两个载波都「有数据」，看不出缺失。
    • RU_Port_ID 映射错 → 天线顺序错 → 波束指向错、MIMO 秩下降。单天线测试全过，只有多流才暴露。
    • PRACH 的 eAxC 漏配 → 老用户全正常，新用户接不进，KPI 上只有随机接入成功率跳水，极易被误判成核心网问题。
    • 两条流用了同一个 ID → 接收端看到两个独立计数器交织 → 现象酷似严重乱序 + 疯狂丢包，链路其实好得很。

    排障要点：查这类问题必须两端同时打印 16 bit 的原始值，不能各自打印解码后的 DU_Port=1, CC=0——两边解码规则本来就不一样，打出来自然都「对」。

  4. 中级SEQ_ID 有什么用？它能发现哪些问题、发现不了哪些？

    eCPRI 只说 SEQ_ID 是 2 字节序号；O-RAN 把它切成两半，同时干两件事：

    • seqId（8 bit）：每条 eAxC 独立的计数器，逐报文 +1，用于丢包与乱序检测。
    • E 位（1 bit）+ subSeqId（7 bit）：无线传输层分片。一个符号一条流的 IQ 有 7 KB 量级，MTU 1500 装不下必须拆；E=1 表示这是最后一片。注意这不是 IP 分片，所以走二层承载时也一样要分。

    它发现不了什么——这是区分度所在。seqId 只有 8 bit，256 个值。算一下：MTU 1500、100 MHz、30 kHz SCS 时一条下行 eAxC 是 6 报文/符号 × 14 符号 × 2000 时隙/s = 168 kpps，256 ÷ 168 k ≈ 1.52 ms 就回绕一圈。所以：

    • 能可靠发现零星丢包；
    • 发现不了长时间中断——连续丢超过 256 个报文，gap 会绕回来看着正常。中断得靠「报文完全停了」来判。
    • 顺带一个巨帧的隐性收益：MTU 9000 后降到 28 kpps，回绕周期变成约 9.1 ms，可观测窗口宽了 6 倍。

    实现要点：用 uint8_t gap = seq - expected 让回绕天然正确；gap < 128 算丢包，gap >= 128 是旧包（乱序/重复），此时千万不要更新 expected，否则会误报一大片丢包。

    判读口径：缓慢线性增长 → 稳定低速丢包，查 QoS/队列/光功率；一簇一簇跳 → 突发拥塞，找同时刻的大流量事件；只有个别 eAxC 有问题 → 配置或映射问题；所有 eAxC 一起 → 公共原因（链路/队列/时钟）。「乱序/重复」计数暴涨则首先怀疑两条流撞了同一个 eAxC ID，其次怀疑 LAG/ECMP 把一条流散到了多条路径。

8.3 高级（体现深度）

  1. 高级一个站点上有多少条 eAxC 流？怎么估？

    骨架公式：

    总流数 ≈ 下行流数 × 载波数 × 扇区数 + 上行流数 × 载波数 × 扇区数 + PRACH/SRS 等专用通道

    关键在于「下行流数」不等于天线数，它取决于谁做预编码——这是这道题最大的变量，也是区分度所在：

    • Category A（预编码在 DU）：DU 算完预编码，把每根物理天线的 IQ 送给 RU，RU 只做上变频与放大。下行 eAxC 数 = 物理天线数（32T → 32 条）。RU 简单便宜，代价是前传带宽按天线数线性膨胀。
    • Category B（预编码在 RU）：DU 只送每个空间层的 IQ，波束权值走 C 面，RU 自己展开到 32 根天线。下行 eAxC 数 = 层数（4 层 → 4 条），带宽省 8 倍，代价是 RU 变复杂、接口耦合更深。

    上行通常没有这个自由度：RU 一般把每根接收天线的采样都送上去让 DU 做合并与均衡，所以上行 eAxC 数 ≈ 接收天线数。于是 Category B 下会出现一个反直觉的现象——上行的流数和带宽反而远大于下行。

    几个量级（含 PRACH 等专用通道）：

    • Cat A、32T32R、1 载波 1 扇区：32 + 32 + 几条 ≈ 68
    • Cat B、32T32R、4 层、1 载波 1 扇区：4 + 32 + 几条 ≈ 40
    • Cat B、32T32R、8 层、2 载波 3 扇区：48 + 192 + 十几条 ≈ 250~270
    • Cat A、32T32R、4 载波 3 扇区：384 + 384 + 几十条 ≈ 800+

    这也解释了 16 bit 的 ID 空间（65536）为什么够用又不能浪费：单站几百条是常态，但一个 DU 可能挂十几个 RU，而 DU_Port_ID 还要从这 16 bit 里先分走几位。

    别忘了 PRACH：它通常占独立的 RU_Port_ID 取值，采样率和带宽都与 PUSCH 不同，配置项也是分开的——漏配的现象就是前面那道题里说的「老用户正常、新用户接不进」。

  2. 高级前传丢包为什么不重传？那可靠性从哪来？

    把两边的代价算出来对比，结论就不需要争论了。

    丢一个报文的代价（以 50 PRB / 报文为例）：损失 273 个 PRB 里的 50 个，即该符号该流约 18% 的资源单元，时间跨度是一个符号约 35.7 µs（一个时隙的 1/14）。这些 RE 的软信息按「擦除」处理，LDPC 本来就有冗余，很可能纠回来；纠不回来才 CRC 失败，然后由空口 HARQ 重传——一个本来就存在、且时间尺度与反馈路径都为此优化过的机制。

    在前传上重传的代价：发现丢包要等下一个报文到达，请求要一个单向时延，重发到达再一个单向时延，合计 > 100 µs，而这只是理论下限。结果是：这个符号的接收窗口照样关了，数据仍然没用，外加三重额外开销——白占一份带宽、DU 要为所有已发数据保留重传缓冲、重传造成的突发让本就拥塞的链路更堵。

    所以不重传不是妥协，是唯一正确的选择：丢包的代价是「一次可能的 HARQ 重传」，等待的代价是「同样丢掉这个符号，外加三重开销」。

    可靠性被推到了代价最低的那几层：

    • 物理层 FEC：25G/100G 以太网自带 RS-FEC，链路上的随机比特错误在这一层就纠掉，根本到不了 eCPRI。它引入的是固定时延（可预算），而不是不确定时延。
    • QoS 隔离：VLAN + PCP 把 U 面和 M 面的大流量分到不同队列并配严格优先级。
    • 带宽余量：前传不按「刚好够」规划，留余量让队列几乎不排队。
    • 空口 HARQ：真漏过去了由它兜——它本来就是为「无线信道会出错」设计的。

    工程上对 U 面帧丢失率的要求通常在 10⁻⁷ 量级或更严（具体指标以所用 O-RAN 传输需求文档与运营商规范为准）。协议层完全不做可靠性，只用 SEQ_ID 做感知。

    可以升华的一句：可靠性应该放在「代价最低、时间尺度最匹配」的那一层。传输层重传的代价是不确定的时延——恰恰是前传最不能付的那一种。同一逻辑也解释了实时音视频为什么用 UDP + 应用层 FEC/NACK 而不是 TCP。

  3. 高级IQ 压缩怎么权衡压缩率和 EVM？为什么 BFP 最常用？

    BFP（块浮点）的原理：一组样本（通常一个 PRB，12 子载波 × I/Q = 24 个样本）共享一个 2 的幂次指数，各自只存低位尾数。编码就是「求块内最大绝对值 → 决定移位量 → 全体右移 → 存尾数 + 1 字节指数」。压到 9 bit 时每 PRB 从 48 B 降到 27 + 1 = 28 B，压缩比约 1.71×。

    BFP 胜出的真正原因不是压缩比最高，而是硬件代价最低：整个编码只要「求最大值 + 前导零计数 + 移位」，没有乘法、没有查表、没有反馈环路，一条组合逻辑流水就能做完。Block Scaling 精细一点但解码要做乘法；μ-law 小信号精度更好但实现复杂、误差难分析；Modulation Compression 压缩比高但强依赖调制信息、本质是下行专用。

    BFP 的软肋：误差由块内最大值决定。一个特别强的子载波会把整块的移位量顶上去，块内幅度小的子载波就被压得只剩几个有效位。OFDM 在一个 PRB 内幅度通常接近，所以平常没事；但在强频率选择性衰落、窄带干扰、或一个 PRB 内同时有强参考信号和弱数据时，弱分量的相对量化噪声明显恶化。现象是整体 EVM 看着还行，但处在深衰落频点上的那个终端解调质量莫名其妙地差。

    位宽怎么定——关键是理解压缩噪声只是 EVM 预算里的一小项。3GPP 对基站发射 EVM 按调制阶数规定上限（阶数越高越严，256QAM 已是个位数百分比量级，1024QAM 更严；具体数值查 TS 38.104 对应版本的表格），而这份预算要分给功放非线性与 DPD 残差、本振相噪、通道校准误差、数字前端定点误差，最后才轮到压缩。所以正确的推导方向是反过来：

    1. 这个小区要不要支持 256QAM / 1024QAM → 决定 EVM 上限；
    2. 扣掉射频链路已经吃掉的部分 → 剩给压缩的裕量决定位宽下限；
    3. 位宽 × 流数 × 载波数 → 带宽需求，对比链路能力。

    典型结论：9 bit 是多数实现的默认值（1.71×）；8 bit（1.92×）要谨慎，适合带宽极紧、以低阶调制为主的覆盖场景；想稳上高阶调制就得考虑 12 bit（1.30×）或不压缩。如果算下来带宽不够，正确的动作往往不是继续压位宽（那会直接砍掉高阶调制的可用性），而是换 Category B 把下行流数降下来，或者升级链路速率。

    一个很少被提起的实现代价：9 bit 不是字节对齐的，样本在字节流里连续位打包，周期是 9 字节（8 个样本），SIMD 展开时的分支与查表比 12 bit（两个样本正好 3 字节）复杂得多。带宽上 9 bit 更省，解码侧的 CPU/FPGA 代价更高。

  4. 高级某站点前传误码率突然升高、RU 报 U 面丢包告警，你怎么定位？

    核心方法论：先用免费的统计把搜索空间劈成两半，再决定要不要抓包。反过来做（先搭采集环境抓 200 GB）常常是花两天验证「问题在配置里」。

    第 1 步：分清「全网 vs 单流」——这一步决定后面所有方向。让 DU 导出按 eAxC 聚合的 SEQ_ID 丢包/乱序计数：

    • 所有 eAxC 一起丢 → 公共原因：链路误码、队列拥塞、时钟异常。
    • 只有部分 eAxC 丢 → 配置、映射、或这几条流共同经过的某个队列。
    • 「乱序/重复」而不是「丢」在涨 → 优先怀疑两条流撞了同一个 eAxC ID，其次是 LAG/ECMP 把一条流散到多条路径。

    第 2 步：确认时间基准，别在错误的前提上排查。看 PTP 是否锁定、有没有发生 GM 切换，再读 Type 5 的单向时延（两个方向都要）。顺序不能反：PTP 没锁时 Type 5 的读数没有意义（负值或明显偏小就是这个原因）；读数带恒定偏置则是 Compensation Value 没配。PTP 锁定而 Type 5 超标，说明时钟没问题、传输路径有问题——多了一跳、队列堵了、光缆改绕了。

    第 3 步：分层排除物理层。看光功率是否在预算内、光模块温度、以及网卡/交换机的 FEC 纠错计数与不可纠错计数、rx_crc_errors。CRC 与 FEC 不可纠错计数在增长 = 物理层问题（光衰、脏连接器、坏模块、温漂），软件再烂也造不出 CRC 错误；反过来 CRC 为 0 而队列丢包在涨，就别去动光缆。

    第 4 步：查 QoS 是否真的生效。丢包时刻和什么事件重合？如果总在做 M 面操作（固件下载、性能数据批量上报）时出现，就查 PCP：在链路两端各抓一次包比对 vlan.priority——只在一端抓等于没验，因为中间那一跳很可能重写了它（untagged 端口默认打标、信任域边界 remark、「不信任接入端口 CoS」一律置 0）。同时查交换机各出口队列的丢包计数，确认 PCP 真的映射到了独立队列并配成严格优先级。

    第 5 步：确认容量与 MTU。链路利用率、巨帧是否端到端开到位（大包不通小包通 = 某跳 MTU 不足）、over UDP/IP 时有没有发生 IP 分片。

    第 6 步：真需要抓包时，注意三件事。① 先跑 ethtool -i：DU 的 U 面网卡多半被 DPDK 绑到 vfio-pci，tcpdump 什么都看不见，得改用 dpdk-pdump、交换机镜像或无源光分路器（插分路器前必须核对光功率预算，否则会亲手制造出正在追查的误码）。② 一定加 -s 64：需要的字段全在前 36 字节里，数据量降到 1/23，25 GbE 满载从 3.1 GB/s 变成 137 MB/s。③ 用 ether[16:2] == 0xaefe（带 VLAN 时 EtherType 在偏移 16）并按 ether[22:2] 锁定具体 eAxC，再配 -W/-C 环形缓冲长时间挂着等复现。

    一个真实案例的收束：某站点上行吞吐周期性掉坑，SEQ_ID 统计显示 380 条 eAxC 里只有 4 条在丢，且属于同一个 BandSector_ID + CC_ID，每隔十几秒一簇。「部分流 + 周期性成簇」直接排掉了链路误码（会全流一起且与光功率相关）、时钟（PTP 与 Type 5 均正常）和带宽（利用率不到 60%），指向队列。两端抓包对比发现 DU 侧 PCP=5、RU 侧变成 0：RU 一个后加载波的 VLAN 子接口配置模板漏填 PCP，交换机按默认策略重打为 0，这 4 条流掉进了和 M 面共用的 best-effort 队列，而网管每十几秒一次的性能数据上报正好打满它。修复分两层：短期补配置，长期在交换机上按 VLAN 强制 remark，让「RU 侧漏配」不再能影响业务。
