TLS / SSH / Certificate：通信系统安全基础

前面 NETCONF「跑在 SSH/TLS 上」——但 SSH 和 TLS 到底是什么、有何区别？本篇把通信安全的三块基石（加密/认证/完整性）、证书与 CA 信任链、TLS 握手、mTLS、SSH 讲清楚，最后回到 NETCONF 与 O-RAN M 平面的实际落地。

Module 08 阅读 ~24 min TLS vs SSH
01

为什么需要安全传输

明文的三大风险

TCP/IP 本身不提供任何安全保证：数据明文在网络上传输，任何中间节点都能看、能改、能冒充。管理面（配置设备）尤其致命——攻击者若能篡改配置，整个基站/网络就沦陷了。

窃听 Eavesdropping

明文被中间人看到（密码、配置泄露）→ 需要加密。

冒充 Spoofing

假服务器/假客户端骗你 → 需要认证。

篡改 Tampering

报文被偷偷改动 → 需要完整性校验。

02

三块基石：加密 / 认证 / 完整性

安全协议都在解决这三件事

对称加密：双方用同一把密钥加解密（AES），快，但密钥怎么安全交换是难题。
非对称加密：公钥加密/私钥解密（RSA、ECDSA），慢，但解决了密钥交换与身份认证。
实战组合：用非对称"协商出"一把对称会话密钥，之后用对称加密传数据——兼顾安全与性能。TLS/SSH 都这么干。
完整性：用 HMAC / AEAD（如 AES-GCM）确保报文没被改，改一位就校验失败。
03

证书与 CA / 信任链

怎么相信"这个公钥真是对方的"

光有公钥不够——你怎么知道拿到的公钥不是攻击者的？答案是数字证书：由可信第三方 CA（Certificate Authority）用它的私钥签名，把"某公钥属于某身份"这件事背书。

证书（X.509）：包含 主体身份 + 公钥 + CA 签名 + 有效期。
信任链：设备证书 ← 中间 CA ← 根 CA。你只要信任根 CA（放在 truststore 里），就能验证整条链。
O-RAN 前传 M 平面里，O-RU 和 O-DU/SMO 就是靠各自证书 + 共同信任的 CA 来互相认证的，这正是 NETCONF over TLS 中 truststore / cert-to-name 的基础。
04

TLS：握手与 1.2 / 1.3

HTTPS / NETCONF-over-TLS 的底座

TLS（Transport Layer Security，前身 SSL）在 TCP 之上加一层安全：先握手（认证 + 协商会话密钥），之后所有应用数据都加密传输。

维度TLS 1.2TLS 1.3
握手 RTT2-RTT1-RTT（0-RTT 可选）
算法套件多、含老旧不安全项精简、只留安全的 AEAD
前向保密可选强制（ECDHE）
安全性/速度较好更好更快
新系统优先 TLS 1.3；1.2 仍广泛存在需兼容。禁用 SSLv3/TLS1.0/1.1。
05

mTLS 双向认证

不只是客户端验服务器

普通 HTTPS 只验服务器（单向）。mTLS（mutual TLS）让服务器也验客户端证书——双方都出示证书、都验证。设备管理场景（O-RAN M 平面）几乎必用 mTLS：确保只有合法 SMO 才能配置 O-RU，也确保 O-RU 连的是真 SMO。

cert-to-name：从客户端证书里提取字段（如 subject/指纹）映射到一个 NETCONF 用户名，实现"证书即身份"，免密登录又安全。
06

SSH 是什么

安全远程登录/传输

SSH（Secure Shell）最初为安全远程登录而生，也提供加密通道、端口转发、文件传输（SCP/SFTP）。它同样走"非对称认证 + 对称加密"，但认证方式更灵活：密码、公钥（authorized_keys）、主机密钥。

NETCONF over SSH（830 端口）复用了 SSH 的安全通道 + 子系统机制，是 NETCONF 最常见的承载方式。

07

TLS vs SSH

高频面试题

维度TLSSSH
初衷保护应用协议（HTTP 等）安全远程登录/管理
身份认证主要靠 证书 / CA公钥(authorized_keys)/密码/主机密钥
信任模型CA 信任链（PKI）首次连接记录主机指纹(TOFU)
典型端口443(HTTPS)/6513(NETCONF)22 / 830(NETCONF)
常见用途HTTPS、gRPC、NETCONF/TLS登录、SFTP、NETCONF/SSH
面试："TLS 和 SSH 有什么区别？"
答：都提供加密通道且都用"非对称协商对称密钥"，但定位不同——TLS 通用地保护应用层协议、身份认证基于 PKI 证书/CA 信任链；SSH 面向安全远程管理、认证多用公钥或密码、信任模型是首次连接记录主机指纹(TOFU)。NETCONF 两者都能承载（830=SSH，6513=TLS）。

在 NETCONF / O-RAN 中的落地

把安全接回主线

NETCONF管理操作（YANG 数据）
SSH / TLS加密 + 认证 + 完整性（本篇主题）
TCP可靠传输
IP寻址路由
Ethernet链路
  • O-RAN M 平面（O1 + 前传管理）强制安全：mTLS + 证书 + truststore，防止未授权配置。
  • 为什么管理面对安全要求远高于用户面？因为配置错误/被篡改会导致整站失效，而用户面更在意实时性。
🎯 本篇要点回顾
  • 安全 = 加密 + 认证 + 完整性；实战用非对称协商对称密钥
  • 证书靠 CA 签名背书，truststore 存信任的根，形成信任链
  • TLS 1.3 比 1.2 更快更安全（1-RTT、强制前向保密）
  • mTLS 双向认证是设备管理必备；cert-to-name 证书即身份
  • TLS(PKI/证书) vs SSH(公钥/TOFU)：定位不同，NETCONF 都能承载
