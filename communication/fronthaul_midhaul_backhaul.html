前传、中传、后传：Fronthaul / Midhaul / Backhaul

上一篇把基站拆成了 CU / DU / RU，它们之间用网络连接。这三段连接各有名字、各有截然不同的性能要求：前传（DU↔RU）、中传（CU↔DU）、后传（RAN↔Core）。理解它们的差异，尤其"为什么前传对延迟/抖动/带宽/同步如此苛刻"，是打开 CPRI/eCPRI 与 O-RAN 的钥匙。

01

三段承载全景

把 CU/DU/RU 之间的"线"命名

名字里的 "haul" 就是"搬运/牵引"。三段搬的东西完全不同——越靠近天线，搬的越是"贴近无线物理层的实时数据"，要求也越极端。这句话读起来像口号，但它背后是一条可以量化的因果链，本篇要做的就是把每一环的数字摊开。

承载网（Transport Network）：无线接入网各功能单元之间、以及接入网与核心网之间的传输网络。它不产生业务，只搬运业务，但它的时延、抖动、同步能力会直接决定无线侧能不能工作——这是承载网与普通企业网最大的区别。

三段不是凭空冒出来的

"前传"这个词在 2G/3G 时代并不存在。当年基站是一个铁柜子，射频与基带都在里面，机柜到天线之间是馈线（粗同轴电缆），传的是模拟射频信号。真正把"基站内部的一根线"变成"一段需要规划的网络"，经历了三次结构性变化：

阶段物理形态产生了哪一段驱动力
2G / 早期 3G一体化基站 + 馈线到天线只有回传（E1/T1、后来是 IP）无
3G 后期 / 4G 初期BBU + RRU 分离，RRU 上塔诞生前传（CPRI 光纤，几百米）把功放搬到天线边，省掉馈线 3 dB 损耗
4G C-RAN多个 BBU 集中到一个机房前传拉长到 km 量级，成为真正的网络机房集中降本、协作化调度（CoMP）
5G NRBBU 再拆成 CU + DU诞生中传（F1）CU 上云、集中做移动性管理；DU 靠近站点保实时

注意第二行那个"3 dB"。馈线在 2 GHz 上每 100 m 损耗可达数 dB，把功放搬上塔等于凭空多出几个 dB 的链路预算——这是 RRU 分离最初的纯物理动机，跟云化、虚拟化毫无关系。前传网络是这个物理决策的副产品，而这个副产品后来变成了整个 5G 承载网里最难啃的一块。

面试里被问"为什么要有前传"时，如果只答"为了 C-RAN 集中化"，说明只知道 2015 年之后的故事。正确的因果顺序是：先有 RRU 上塔（省馈线损耗）→ 才有 CPRI 光纤 → 再有 C-RAN 把这根光纤拉长 → 前传才成为一个网络问题。

三段在物理上未必真的是三段

逻辑上是 RU–DU–CU–Core 四个节点三段链路，但现网里这四个功能经常合并同址，某一段就退化成机内背板甚至一根短跳纤：

常见部署形态（同一张网里可以并存）

① D-RAN 传统分布式站
   RU（塔上）── 前传 100 m ──> DU+CU 一体（塔下机柜）── 回传 ──> 5GC
   中传不存在（CU/DU 在同一块单板 / 同一台服务器内）

② C-RAN 集中式
   RU ×N（各站点）── 前传 1~10 km（光纤/WDM）──> DU 池（区域机房）
   DU 池 ── 中传 10~50 km ──> CU（边缘 DC）── 回传 ──> 5GC
   三段齐全，前传是纤芯消耗大户

③ vRAN / O-RAN 云化
   O-RU ── Open FH 7-2x ──> O-DU（COTS 服务器 + 加速卡，边缘机房）
   O-DU ── F1 ──> O-CU（区域 DC，容器化）── NG ──> 5GC
   三段齐全，且三段都跑在通用以太网上

④ 室分 / 微站
   一体化小基站（RU+DU+CU 全在一个盒子里）── 回传 ──> 5GC
   前传中传都不存在

这四种形态里，只有 ② 和 ③ 需要真正规划前传网络。这也解释了一个常见困惑：为什么运营商内部说"我们 60% 的站是 D-RAN"，同时又说"前传是最大的投资瓶颈"——因为剩下那 40% 的 C-RAN 站点吃掉了绝大部分光纤资源。

下文如果不特别说明，都以 ② / ③ 这种三段齐全的形态为讨论对象。功能拆分本身（为什么切在 Option 2 和 7-2x）不在本篇展开，见 CU/DU/RU 功能拆分。
02

Backhaul 后传（RAN ↔ Core）

最"普通"的一段，就是常规 IP 承载

后传（更常见的中文译名是回传）连接基站（5G 里是 CU）与核心网，搬运的是用户业务数据 + 核心网信令——本质就是 IP 包。它是三段里最"像普通互联网"的一段，所以我们从它讲起：把最简单的那段先立成基准，后面两段的"苛刻"才有参照物。

NG 接口其实是两个接口

5G 里 gNB 与 5GC 之间的接口叫 NG，但它在传输上是泾渭分明的两条流，走不同的传输层协议、不同的对端网元、不同的端口：

NG-C（控制面）NG-U（用户面）
应用层协议NGAP（3GPP TS 38.413）GTP-U（3GPP TS 29.281）
传输层SCTPUDP
端口SCTP 38412（TS 38.412）UDP 2152
对端网元AMFUPF
流量占比< 1%（信令）> 99%（业务）
丢包容忍极低，SCTP 自己重传由上层 TCP/QUIC 负责
典型规划要求可靠性优先，双归属 AMF带宽优先，可统计复用

这个"控制面走 SCTP、用户面走 UDP"的分工在 3GPP 里非常稳定：Xn 接口是 XnAP/SCTP 38422 + GTP-U，F1 是 F1AP/SCTP 38472 + GTP-U，E1 是 E1AP/SCTP 38462。记住这条规律，比背端口号有用——信令要求不丢不乱序且要多流并行，正是 SCTP 的设计目标；用户面已经有端到端的 TCP/QUIC 兜底，再加一层重传只会放大时延。

被追问"为什么信令用 SCTP 不用 TCP"时，答三点：① 多流（multi-streaming）避免队头阻塞——一个 UE 的信令卡住不会拖累其他 UE；② 多归属（multi-homing）——一条 SCTP association 可以绑多个 IP，链路断了不用重建；③ 消息边界保留——NGAP 是面向消息的，用 TCP 还得自己做分帧。

GTP-U：回传上真正在跑的那层封装

回传链路上抓包，看到的绝大部分是这样一个"洋葱"：

以太网帧
└─ Ethernet (14 B) [+ VLAN 4 B]
   └─ IP (20 B v4 / 40 B v6)          ← 传输网看到的、用来路由的外层 IP
      └─ UDP (8 B), dport = 2152
         └─ GTP-U (8 B 最小)          ← TEID 标识这是哪个 UE 的哪条 QoS 流
            └─ IP (20/40 B)           ← 用户真正的 IP 包（内层）
               └─ TCP/QUIC/…
                  └─ 用户数据

GTP-U 的最小头只有 8 字节，拆开看：

30 ff 05 78  00 00 12 34
│  │  └─┬─┘  └────┬────┘
│  │    │         └─ TEID = 0x00001234（Tunnel Endpoint Identifier）
│  │    └─ Length = 0x0578 = 1400，指 GTP 头之后的净荷长度
│  └─ Message Type = 0xFF = G-PDU（承载用户数据；其余如 0x01 Echo Request）
└─ Flags = 0x30 = 0b0011_0000
     version=001 (GTPv1)、PT=1 (GTP 而非 GTP')
     E=0 S=0 PN=0 → 没有扩展头/序列号/N-PDU 号，头就是 8 字节

若 E=1，头后追加 4 字节扩展头，5G 常用 PDU Session Container
（携带 QFI，即 QoS Flow Identifier）——此时头变成 12 字节甚至更长。
TEID：32 位隧道端点标识。它是接收方本地分配的，也就是说上下行两个方向的 TEID 完全无关。排查"上行通下行不通"这类问题时，第一步就是确认双方各自 assign 的 TEID 有没有对上，而不是去看是不是同一个值。

对承载网工程师来说，这层封装带来两个实际后果：

  • MTU 被吃掉约 36–60 字节。外层 IPv4+UDP+GTP-U = 20+8+8 = 36 B，IPv6 则是 56 B，再叠 VLAN、可能的 IPsec。如果传输网 MTU 只有 1500，用户内层 MTU 就得压到 1400 上下，否则要么分片、要么触发 PMTUD 黑洞。回传网普遍配置 jumbo frame（1600 或 9000）正是为了避免动用户的 MTU。
  • 传输网看不见用户流。所有 UE 的流量被塞进同一组外层五元组，传统基于五元组的 ECMP 哈希会把整条隧道压在一条等价路径上。解决办法是让设备支持基于 TEID 或内层头的哈希（很多厂商称 "GTP-aware load balancing"）。

$ sudo tcpdump -i ens1f0 -nn 'udp port 2152' -c 5
10:22:41.113402 IP 10.20.4.11.2152 > 10.30.1.9.2152: UDP, length 1408
10:22:41.113570 IP 10.30.1.9.2152 > 10.20.4.11.2152: UDP, length 132
10:22:41.114011 IP 10.20.4.11.2152 > 10.30.1.9.2152: UDP, length 1408
...

# 怎么判读
#  · length 1408 ≈ 1400 用户净荷 + 8 GTP 头 → 说明内层 MTU 被设到 1400，正常
#  · 若大量 length 很小（几十字节）的包 → 用户面多为小包业务（IoT/信令类），
#    此时瓶颈是 pps 而不是 bps，规划带宽会严重误判
#  · 只看到单向 → 先查对端 TEID 分配与 UPF 侧路由，不要先怀疑物理链路

# 常见误判：把 Echo Request/Response 当业务流量
#  Message Type=0x01/0x02 是 GTP-U 的心跳，每 60 s 一次，不代表用户面通

回传的带宽怎么规划：统计复用是这一段的特权

回传是三段里唯一可以放心做统计复用的一段。原因很直白：它搬的是用户业务流量，而用户流量有两个统计特性——突发（一个人刷完一段视频就停）和独立（不同用户的峰值不同时到来）。把足够多的用户汇聚起来，总流量的峰均比会显著下降。

回传带宽的两种算法，结果能差 3~5 倍

【错误算法：按空口峰值堆】
  单小区峰值（100 MHz, 4 层 DL）  ≈ 1.6 Gbps
  × 3 扇区                        ≈ 4.8 Gbps
  × 20 个站挂在同一个 CU 下        ≈ 96 Gbps      ← 要上 100GE
  这个数字永远不会出现：20 个站不可能同时打满峰值

【工程算法：忙时均值 + 峰值保底】
  max( Σ 各站忙时均值 × 过载系数,  单站峰值 × 并发系数 )
  = max( 20 × 0.35 Gbps × 1.3,     4.8 Gbps × 2.5 )
  = max( 9.1 Gbps,                 12 Gbps )
  ≈ 12 Gbps                                      ← 一条 25GE 绰绰有余

  · 忙时均值来自实际话统（PM 计数器），不是拍脑袋
  · 过载系数覆盖话务波动；并发系数保证少数用户能真的跑出峰值体验
  · 两项取 max 而不是相加：前者管"平均别拥塞"，后者管"峰值别封顶"
某地市回传扩容评审时，规划方按"单小区峰值 × 小区数"算出需要 400 Gbps，采购预算被直接打回。重新拉了三个月的 PM 计数器发现：全网忙时利用率的 P95 只有链路容量的 18%，真正的瓶颈根本不在带宽，而在某两个环上的微波跳段——那两跳在雨衰时会自适应降速到 400 Mbps，导致该区域忙时丢包。最终方案是不扩容主环，只把那两跳微波改成光纤，成本不到原方案的 5%。教训：回传的问题九成不是总带宽不够，而是某个局部瓶颈或某条路径异常。先看话统，再谈扩容。

回传的时延要求为什么"最宽松"，以及它宽松到什么程度

说回传时延宽松，是相对前传而言，不等于随便。准确的说法是：回传时延不参与无线侧的硬实时闭环，它只影响用户体验指标。拆开看：

回传时延影响什么机制敏感度
TCP / QUIC 吞吐吞吐 ≈ 窗口 / RTT，RTT 变大直接压低单流吞吐高：回传多 10 ms，单 TCP 流吞吐可掉三成以上
网页首屏、API 响应叠加在用户感知 RTT 上中：几 ms 用户无感，几十 ms 明显
URLLC / 边缘业务端到端预算被回传吃掉极高：这正是 MEC 把 UPF 下沉的动因
NGAP 信令流程接入、切换的流程时长低：几 ms 相对于流程的几十 ms 不显著
无线调度、HARQ完全不影响——这些闭环在 DU 内部就闭合了无

最后一行是关键，也是很多人第一次接触时的认知拐点：无线侧所有微秒~毫秒级的硬实时闭环（HARQ、调度、AGC、功控）全部发生在 DU 与 RU 之间，回传根本不在环内。所以回传断了，通话会掉、上网会停，但基站的物理层不会"乱掉"；前传抖动几微秒，物理层就直接崩。这就是两段要求天差地别的根因。

回传的工程重点是带宽、可靠性、成本，而不是极限低时延。它和普通运营商 IP 承载网没有本质区别，成熟的 IP/MPLS、SR-MPLS、SRv6 都能直接用，这也是它最便宜的原因。
03

Midhaul 中传（CU ↔ DU）

承载 F1 接口，介于前传与后传之间

中传连接 CU 与 DU，承载 3GPP 定义的 F1 接口（对应 Option 2 拆分，切在 PDCP/RLC 之间）。此时数据已经是较高层的 RAN 协议数据（PDCP PDU），不再是原始基带采样。

F1 的协议栈：和 NG 长得几乎一样

如果你已经看懂了上一章的 NG，F1 几乎不用重新学——3GPP 在接口设计上高度自我复用：

F1-C（控制面）F1-U（用户面）
应用层协议F1AP（TS 38.473）NR 用户面协议（TS 38.425）
承载于SCTP，端口 38472（TS 38.472）GTP-U / UDP 2152
搬什么UE 上下文建立、承载配置、DU 配置更新、寻呼PDCP PDU + 下行数据递送状态反馈
带宽占比< 1%> 99%
断链后果DU 无法接纳新 UE，存量 UE 逐步释放业务立即中断

值得单拎出来的是 F1-U 里那层 NR 用户面协议（TS 38.425）。它坐在 GTP-U 的扩展头里，定义了两类 PDU：

PDU Type 0 · DL USER DATA
  CU → DU，携带 PDCP 序列号等信息，告诉 DU 这个包在 PDCP 序列里的位置

PDU Type 1 · DL DATA DELIVERY STATUS（DDDS）
  DU → CU，是整条链路的"流控回执"，关键字段：
    · Highest Successfully Delivered PDCP SN   已成功送达 UE 的最高序号
    · Desired Buffer Size for the data radio bearer  DU 还想再要多少字节
    · Lost NR-U Sequence Number range          丢了哪些
    · (可选) Desired Data Rate                  期望速率

  语义：DU 根据自己 RLC 缓冲区的水位，反过来向 CU 要数据。
        这是一个 CU↔DU 之间的闭环流控。
DDDS（Downlink Data Delivery Status）：DU 周期性或事件触发地把"我这边缓冲了多少、送达到哪了、还想要多少"上报给 CU，CU 据此决定往下灌多少数据。它的作用相当于 TCP 的接收窗口，只不过运行在 CU 与 DU 之间。

为什么这个细节对承载网工程师重要？因为 DDDS 让中传的时延变成了一个吞吐问题，而不只是体验问题。这个闭环的响应速度受中传 RTT 制约：中传 RTT 越大，CU 就必须在 DU 侧缓存更多数据才能把管道填满（经典的带宽时延积），而 DU 的缓冲区是有限的物理内存。

# 中传 RTT 与 DU 缓冲需求的关系（带宽时延积）
#
#   需要的缓冲 ≈ 单 UE 峰值速率 × 中传 RTT
#
#   RTT = 0.2 ms（同机房）  , 1 Gbps → 25 KB   轻松
#   RTT = 2 ms  （同城 20km）, 1 Gbps → 250 KB  正常
#   RTT = 10 ms （跨城）     , 1 Gbps → 1.25 MB 单 UE！
#                                       × 数百 UE = GB 级缓冲，DU 内存扛不住
#
# 后果不是"慢一点"，而是：CU 灌不满 → DU 空口有资源却没数据发
#                        → 用户实测速率上不去，但所有 KPI 看着都正常
#
# 这类问题最难查，因为空口侧一切正常、传输侧丢包为 0、
# 唯一的线索是 DDDS 上报的 Desired Buffer Size 一直处于高位。
"中传能拉多远"这个问题的正确答法不是背一个 km 数，而是：中传没有硬性的物理层时序约束（那是前传的事），它的距离上限由三个软约束决定——① F1-U 流控闭环的带宽时延积 vs DU 内存；② 切换与重配置流程的时长预算；③ 端到端时延预算里留给中传的那一份。典型规划值是单向几 ms，对应几十到一百多公里，但真正拍板前要看 DU 的缓冲能力。

中传带宽 ≈ 用户面吞吐 + 开销，就这么简单

这是中传与前传最本质的差别：中传的带宽是"业务量驱动"的，前传的带宽是"配置驱动"的。小区没人用，中传上就几乎没流量；而前传即使一个用户都没有，只要小区开着，IQ 数据流的速率也基本恒定（7-2x 下会随占用的 PRB 有所变化，但规划仍按峰值）。

算中传带宽只需要一个乘法：

中传带宽 = 小区峰值吞吐 × 扇区数 × (1 + 封装开销) × 并发/过载系数

【封装开销拆解】以 1400 B 的 PDCP PDU 为例
  Ethernet 头        14 B
  VLAN               4 B
  IPv4               20 B
  UDP                8 B
  GTP-U（含扩展头）  12 B
  NR-U PDU Type 0    ~6 B
  ───────────────────────
  合计               64 B  → 64 / 1400 ≈ 4.6%
  再算上前导码+帧间隙 20 B  → 约 6%

  若是小包（如 128 B 的 VoIP/信令），开销比冲到 50% 以上
  → 所以规划要看 pps，不能只看 bps

【一个 100 MHz / 64T64R 三扇区站】
  单小区 DL 峰值（4 层，256QAM）    ≈ 1.6 Gbps
  三扇区                            ≈ 4.8 Gbps

"前传是中传的十几倍"这个比值，就是 Option 2 拆分点带来的全部价值。越往协议栈上方切，传的东西离用户数据越近、离物理层采样越远，带宽就越省。代价是 DU 要承担更多实时处理，从而无法离站点太远——这正是拆分点选择的核心权衡。

中传之所以"没那么苛刻"，正是因为 Option 2 把拆分点放得较高——高层数据经过头压缩、调度聚合，带宽和时延压力都远小于"切在 PHY 里"的前传。这体现了 功能拆分 的核心权衡：拆得越高，传输越省心，但集中化带来的收益（协作调度、资源池化）也越少。

第三行那个坑很隐蔽：F1-C 和 F1-U 在传输网眼里是完全不同的两条流（一个 SCTP 一个 UDP，五元组不同），ECMP 完全可能把它们哈希到时延差好几毫秒的两条路径上。信令说"数据已经切过去了"而数据还堵在旧路径上，就会表现为切换期间的丢包。规划时应当把同一 DU 的 F1-C 与 F1-U 绑定到同一条转发路径（用同一个 DSCP + 策略路由，或在 SR 里显式指定 path）。

还有一个规划层面的问题值得先想清楚：中传要不要单独建一张网？绝大多数情况下答案是不要。中传的指标（ms 级时延、无硬性相位同步要求、Gbps 量级带宽）和回传高度重叠，而回传网通常早就存在且有富余容量，把 F1 和 NG 一起放在同一张 IP-RAN 上、用不同的 VPN 实例或 SR 策略隔离即可。单独建中传网只有一种理由：CU 与 DU 之间的时延被某个具体业务压到了很低（例如需要严格控制端到端预算的 URLLC 场景），此时才值得为它付出一张独立网络的建设与运维成本。这与前传形成鲜明对比——前传几乎必然要独立组网，因为它的指标和任何既有网络都不兼容。

04

Fronthaul 前传（DU ↔ RU）

整个通信系统里最"变态"的一段

前传连接 DU 与 RU（Option 7-2x 拆分，切在 PHY 内部）。它搬运的是贴近无线物理层的实时数据——频域 IQ 采样。这段承载的要求堪称极端：

带宽巨大

Massive MIMO（64/128 天线）+ 大带宽 + 高采样率 → 前传要搬的 IQ 数据量惊人。传统 CPRI 下一个 100MHz 64T64R 小区前传可达几十甚至上百 Gbps。

延迟极低

无线的 HARQ 重传、调度有硬性时间预算。前传单向时延通常要求 ~100 µs 级（O-RAN 定义了 Category A/B 的时延窗口），远严于普通网络。

抖动极小

IQ 数据是"按时间刻度对齐"的，抖动会直接破坏信号。前传对包到达时间的抖动容忍度极小。

同步极严

DU 和 RU 必须频率 + 相位/时间都精确对齐（TDD 尤甚），靠 PTP/SyncE 达到 ns 级同步。

IQ 数据：无线信号用同相（I）和正交（Q）两路采样表示的复数基带样本。前传搬的就是这些采样（传统 CPRI 传时域 IQ，eCPRI/7-2x 传频域 IQ + 部分处理下沉到 RU 以省带宽）。IQ 与 eCPRI 报文格式的细节见 eCPRI 深入，本篇只关心它对承载网提出了什么要求。

时延：100 µs 是怎么来的，以及它意味着什么

3GPP TR 38.801 在评估各拆分选项时，给 Option 7 一类的拆分标注的单向时延指标在 100 µs 量级；O-RAN WG4 则把它落成了更具体的收发窗口。这个数字之所以吓人，是因为要和熟悉的量级对比一下：

抖动：比时延更致命的那个指标

时延大，可以通过把接收窗口整体往后挪来补偿——代价是牺牲一点空口时延预算，但至少能工作。抖动不行，因为它没法补偿：

  关键结论：
    传输网的时延可以大但必须"稳"。
    100 µs ± 1 µs  → 可用
    30 µs ± 50 µs  → 不可用（平均值更好，但会大面积丢包）
这是前传与所有其他网络最反直觉的一点：平均时延更低的链路可能完全不能用。把前传交给一台"平均转发时延 8 µs、但拥塞时能排队到 200 µs"的通用交换机，比交给一条"固定 60 µs 的裸光纤"要糟糕得多。确定性 > 低时延——这条原则贯穿整个前传工程。

正因为如此，前传网络上的以太网交换机不能是随便一台交换机。它至少要满足：严格优先级队列（前传流最高优先，且不与其他业务混跑）、直通转发或极浅缓冲、以及支持 IEEE 1588v2 的透明时钟或边界时钟。很多厂商为此专门做了"前传交换机"这一品类。

同步：前传是唯一一段"同步比数据还重要"的网络

TDD 系统里，相邻基站必须在同一个时刻从收切到发。切换时刻若不一致，一个站还在发下行，邻站已经开始收上行——邻站收到的全是自己隔壁的下行功率，也就是基站互干扰。这个后果不是"性能下降"，是整片区域的上行直接瘫痪。

3GPP TS 38.133 对小区相位同步精度的要求是优于 3 µs（覆盖重叠的小区之间），对应到 ITU-T G.8271.1 的网络限值是端到端 |TE| ≤ 1.5 µs。1.5 µs 要在整条同步链上分摊，于是每一跳只剩几十纳秒：

  • 金融网追求低时延，但它不要求相位同步到纳秒，也不介意为了低时延牺牲带宽利用率；

  • TSN 追求确定性，做法是时间感知整形（TAS）预留时隙，但它的时间粒度是微秒到毫秒，比前传宽松一到两个数量级；
  • 而前传要在几十 Gbps 的恒定速率下，同时做到 µs 级确定性、ns 级同步、10⁻⁷ 丢包——并且不能靠反压、不能靠重传、不能靠统计复用这三种常规手段中的任何一种。

把这三个"不能"连起来看，就明白了：前传把网络工程师平时用来解决问题的整个工具箱几乎全部没收了。剩下能用的只有"刚性预留带宽 + 缩短物理距离 + 减少中间跳数 + 把同步做扎实"这几招，而这几招全都指向物理规划而非协议设计。这就是为什么前传的难点最终落在了光纤、机房、纤芯这些看起来很"土"的地方。

为什么前传最苛刻

根因是"它离无线物理层最近"

把因果链理清楚：拆分点越往下（越靠近 RF）→ 传的越是"未加工的物理层实时数据" → 数据量越大、时间越敏感 → 带宽/时延/抖动/同步要求越极端。

拆分点位置        传什么              代价
Option 2 (中传)  高层分组(压缩过)     省带宽、时延宽松
Option 7-2x(前传) 频域 IQ(部分下沉)   带宽大、时延µs级
Option 8 (旧CPRI) 时域 IQ(几乎原始)   带宽爆炸

但"因为它离物理层近"只是定性的答案。真正让前传时延预算被压到 100 µs 的，是空口本身的时序是硬编码在标准里的——它不会因为你把 DU 搬远了就宽容一点。下面把这条预算链拆开。

端到端时延预算：从空口一路扣到核心网

3GPP TS 22.261 给出的用户面时延目标是：eMBB 4 ms、URLLC 0.5 ms（单向，上下行各自计）。这个预算要被下面这一串环节瓜分：

把它写成一张可以逐项核算的表：

被问"URLLC 1 ms 的端到端时延怎么保证"时，不要只答"用 mini-slot"。要给出完整的预算表并指出两个真正的杠杆：① 把 UPF 下沉到边缘（砍掉第 7 行的几毫秒，这是最大的一块）；② 免调度/预调度（砍掉第 1 行里的调度请求往返）。前传和 DU 处理这两项即使做到极致也只有几十微秒的空间，动它们性价比最低。

5 µs/km：一个改不了的物理常数

前传距离的上限不是运营商定的，是光速定的。推导只有两步：

【光在单模光纤里的传播速度】
  真空光速          c = 299 792 458 m/s
  单模光纤群折射率  n ≈ 1.468（1550 nm 附近的典型值，G.652 光纤）

  v = c / n = 299792458 / 1.468 ≈ 2.042 × 10⁸ m/s

【每公里时延】
  t = 1000 m / (2.042 × 10⁸ m/s)
    = 4.897 × 10⁻⁶ s
    ≈ 4.9 µs/km   → 工程上一律记作 5 µs/km

  往返（RTT）则是 10 µs/km。

【为什么是 1.468 而不是 1.5 或 1.46】
  n 随波长与光纤类型微变（1310 nm 略高，1550 nm 略低），
  不同资料给 4.8~5.0 µs/km 都对。做规划时用 5 µs/km 取整，
  留出的那点余量正好覆盖跳纤、熔接盘里绕的那几十米。

【注意：这只是传播时延，不含】
  · 光模块的收发处理（每端约 0.1~1 µs）
  · 交换机 / WDM 有源设备的转发（每跳 1~30 µs）
  · FEC 编解码（OTN 场景可达数 µs ~ 十几 µs）

"5 µs/km"这个常数值得像背 sizeof(void*) 一样刻进脑子里，因为它把一个抽象的时延预算直接翻译成了地图上的一个半径：

规划时最容易犯的错误是拿直线距离当光纤距离。光纤要沿管道走、要绕过河流和铁路、要在每个接头盒里留几十米余长。实际光纤长度通常是直线距离的 1.3 ~ 2 倍，市区因为管道路由曲折甚至更多。一个"图上量出来 8 km"的站点，实际纤长完全可能是 14 km——正好卡在预算边缘。规划一律以 OTDR 实测的纤长为准，不看地图。

承载技术选择

每段该用什么"搬运工"

先给一句结论式的分工：

  • 前传：对时延/同步最敏感 → 传统用 CPRI（专线式），5G/O-RAN 用 eCPRI over Ethernet（分组化、灵活、可用通用交换机），配合 VLAN + 严格优先级 QoS + PTP/SyncE 同步。
  • 中传：以太网 / IP 承载 F1，QoS 适中，常与回传共用一张 IP-RAN。
  • 回传：成熟 IP/MPLS、SR-MPLS、SRv6，重带宽与可靠性。

但这只回答了"用什么协议"。真正的工程选型问题是"这段光纤上放什么设备"——同样是 eCPRI over Ethernet，跑在裸光纤上、无源波分上、还是 OTN 上，是四种完全不同的成本结构与运维模型。

四类承载方案

① 暗光纤直连（Dark Fiber）

一对光纤从 DU 直通 RU，中间除了接头盒什么都没有。时延最低、抖动接近零、同步天然透传，因为链路上根本没有会引入排队的有源器件。代价是每个小区吃一对纤芯——一个三扇区站就是 3 对，20 站的 C-RAN hub 就是 60 对。

② 无源 WDM（CWDM / DWDM）

两端各放一个不带电的合分波器，把多个波长复用进同一对纤。本质上还是"光直连"，只是共享了纤芯。时延只增加合分波器的插损对应的极短光程（可忽略），同步照样透传。用它把纤芯需求压到 1/8 ~ 1/40。

③ 有源承载（OTN / SPN / PTN）

链路上放带电的传输设备，做电层的复用、交叉、保护倒换、性能监测。纤芯利用率最高、运维能力最强（有告警、有环回、有性能计数），但每一跳都引入时延与抖动，而且必须逐跳支持 T-BC 才能透传同步。

④ 以太网 / IP 交换

用交换机组网，前传流打 VLAN + 最高优先级。最灵活、设备最便宜，但普通交换机的存储转发与共享缓冲会带来不可控抖动。前传场景必须用支持 1588 边界时钟/透明时钟 + 严格优先级 + 浅缓冲的专用型号。

最后一列才是决定因素：时间同步能不能透传

选型表里前面五列（时延、成本、运维……）都是连续量——差一点可以用钱或者妥协换回来。只有最后一列是离散的 0/1：同步透不过去，这条链路就不能承载 TDD 前传，别的指标再漂亮也没用。这就是为什么它常常是选型的第一道筛子，而不是最后一道。

同步透传：PTP（IEEE 1588v2）靠"记录发送时刻 t1、接收时刻 t2、反向 t3/t4"来计算时钟偏差与链路时延。它的两个前提是——① 中间设备不能让时间戳的意义失真；② 往返链路时延必须对称。任何破坏这两条的设备，都会把误差直接注入相位。

设备自身的恒定误差 cTE时间戳打点位置与真实收发时刻之间的固定偏差，每跳累积每跳 10 ~ 50 ns（G.8273.2 Class C/A）控制跳数；选高等级 T-BC；必要时做逐跳校准
链路不对称去程与回程的物理时延不相等，PTP 无法察觉，把差值的一半当成时钟偏差见下，可达 ns ~ µs双纤同长；避免单纤双向异波长；必要时人工输入补偿值

第三项最阴险，因为它完全无法被 PTP 自己发现——协议的数学模型里假设了对称，不对称就变成一个"看不见的常数偏移"，所有告警都是绿的，只有空口的邻区干扰在悄悄变差。前传上制造不对称的最常见来源有两个：

【来源 1：单纤双向（BiDi）用了两个不同波长】
  BiDi 光模块用一根纤跑双向，典型配对是 1310 nm 发 / 1550 nm 收。
  单模光纤的群折射率随波长变化（色散），两个方向的传播速度不同：

    1310 nm 与 1550 nm 之间的群时延差 ≈ 1~2 ns/km（量级估算，
    随光纤型号与实际波长而变，精确值需查光纤色散参数）

    10 km 链路 → 往返时延差 10~20 ns
    PTP 把它的一半当成时钟偏差 → 5~10 ns 的固定相位误差

  这一项就吃掉了 G.8273.2 Class C（10 ns）的整条预算。

  ✅ 对策：前传优先用【双纤单向 + 同波长】，两根纤长度尽量一致。
     实在只有一根纤，用同波长的双向方案，或在设备上配置不对称补偿值。

【来源 2：保护倒换后走了不同长度的路径】
  主用 8 km、备用 14 km。倒换瞬间 PTP 看到链路时延突变 6 km × 4.9 = 29 µs，
  相位跳变约 14.7 µs —— 远超 1.5 µs 网络限值。

  现象：倒换后一段时间内该片区上行底噪抬升、邻区干扰告警，
        等 PTP 重新收敛（可能几分钟）才恢复。

  ✅ 对策：主备路径长度差纳入规划约束（常见要求：差值 < 1~2 km）；
     或让 PTP 在倒换时进入保持态而不是立刻跟踪新路径。

看这张图要抓住一点：无源 WDM 改变的只有"这段光走在哪根纤里"，没有改变"这段光要走多远"。合分波器是纯光学器件，光进去、按波长分开、光出来，整个过程不做光电转换、不排队、不重新打时间戳。这既是它时延几乎为零、同步天然透传的原因，也是它无法缩短距离、无法提供任何监控的原因——同一个物理特性的一体两面。

前传网的 QoS 与保护：两个反直觉的结论

如果前传跑在共享的以太网上（O-RAN 场景很常见），有两件事和常规网络工程的直觉相反。

结论一：前传流不能只是"优先级最高"，最好是"根本不和别人共队列"。

常规做法（不够）：给前传流打最高 PCP/DSCP，走严格优先级队列
  问题：严格优先级只保证"前传排在别人前面"，
        但一旦有一个大包正在发送，前传包仍要等它发完——
        这叫【存储转发的头阻塞】。

  10 GbE 上一个 1518 B 的包发送耗时 ≈ 1518 × 8 / 10e9 ≈ 1.2 µs
  9000 B 巨帧 ≈ 7.2 µs
  1 GbE 上 9000 B 巨帧 ≈ 72 µs   ← 这一下就吃掉大半条前传预算

  正确做法（三选一，按效果排序）：
    ① 物理隔离：前传独占端口 / 独占波长 / 独占纤芯（最稳，也最贵）
    ② 帧抢占（IEEE 802.1Qbu / 802.3br）：允许高优先帧打断正在发送的低优先帧
    ③ 若必须共享，则限制同端口其他业务的最大帧长（如限到 1518 B），
       把最坏头阻塞从 72 µs 压到 12 µs

  ⚠ 只配 QoS 优先级、不管最大帧长与链路速率，
    是前传抖动问题最常见的根因。

结论二：前传的保护倒换，弊可能大于利。

常规承载网的思路是"关键链路必须有备份"，但前传上做保护要面对一个尴尬：主备路径长度不一样，倒换会导致同步相位跳变（§7.3 已经算过：6 km 的路径差 = 约 14.7 µs 的相位跳变，是 1.5 µs 网络限值的十倍）。倒换本身"成功"了，业务却因为同步失准而恶化，还会波及邻区。

保护方案业务连续性对同步的影响适用性
不做保护，坏了就修差：单点故障即小区退服无影响密集城区（邻站可临时补覆盖）常见的务实选择
主备路径 + 严格约束长度差（< 1~2 km）好倒换后相位跳变可控在预算内推荐，但对光纤资源要求高
主备路径不约束长度好倒换即相位失准，可能几分钟才收敛不建议用于 TDD 前传
RU 侧加 GNSS 兜底（LLS-C4）与保护无关倒换时同步不依赖前传链路可作为长度差无法约束时的补偿手段
"前传要不要做保护"没有标准答案，但能说出"保护倒换会引入同步相位跳变，所以主备路径长度差必须纳入规划约束"，就能明显区别于只会背"关键链路要冗余"的候选人。这也是承载网与普通 IP 网思维方式差异最集中的一个点：在前传上，可用性和确定性是会打架的，不是天然一致的。

工程现实：光纤与机房

理论拓扑很美，现实是有什么光纤用什么

前面七章讲的是"应该怎么建"。这一章讲"实际上怎么建"，两者之间的差距，是从教科书走向现网最大的一道坎。

规划一段前传，纸面上的流程是：确定 RU 位置 → 确定 DU 位置 → 算距离 → 选技术。现实中的流程恰好是倒过来的：先查这一片有哪些光纤资源、哪些机房还有空间和电 → 反推 DU 只能放在哪 → 看看这个位置的前传距离能不能达标 → 不达标再想办法。

光纤资源：四种来源，四种约束

获取方式成本结构可控性典型约束什么时候选它
自建管道 + 自敷光缆一次性投入极高（市区每公里管道开挖成本可达数十万元量级），之后近乎零边际成本最高：芯数、路由、维护全自己说了算路权审批周期以月甚至年计；市区开挖常年受限长期高价值路由（核心环、大型 C-RAN hub 的进出局）
租用暗光纤按纤芯 × 公里 × 年计费中：物理层自己用，但路由由出租方决定合同期结束可能涨价或不续；出租方检修不受你控制最常见的前传方案，尤其是新建站点
租用波长（Lambda）按波长 × 带宽 × 年计费，比租纤便宜低：光层是别人的能不能透传 PTP 完全取决于出租方的设备；不对称量你无从测量回传/中传可以；前传要极其谨慎
共享 / 共建（与同行或铁塔公司）分摊，最省最低：变更要协调芯数分配、故障责任划分、扩容优先级都要谈成本压力大、且路由确实重合时

第三行值得多说一句。租波长在前传上是个陷阱：你拿到的是一个"看起来像光纤"的通道，但对端的光层设备、走的什么路由、主备路径差多少、有没有做电中继，你统统不知道。而这些恰恰是决定同步能不能透过去的全部因素。真要租，合同里必须明确写入单向时延上限、往返不对称量上限、以及 PTP 透传能力三项指标，并要求提供测试报告。

机房：比光纤更难解决的约束

DU 要放在机房里，而机房这个东西不是想有就有的。一个能放 DU 池的 C-RAN 机房要同时满足：

C-RAN 机房的准入条件（缺一不可）

  ① 位置    在目标覆盖区的几何中心附近（决定所有 RU 的前传距离）
  ② 光纤    有足够纤芯出局，且能通到每个 RU 站点
  ③ 电力    DU 池是耗电大户；一个满配 DU 机架可达数千瓦量级，
            还要配 UPS 与油机后备
  ④ 空调    电力几乎全部变成热，制冷容量要匹配
  ⑤ 承重    机架 + 电池组对楼板承重有要求，老楼常常不达标
  ⑥ 空间    不只是机架位，还要有维护通道与走线空间
  ⑦ 产权    租期要足够长（DU 一旦入驻，搬迁成本极高）
  ⑧ 安全    防水、防火、门禁、动环监控

  现实：同时满足 ①~⑧ 的候选点，在一个区里可能只有 2~3 个。
        于是 DU 位置几乎是被【选出来的】而不是【规划出来的】，
        前传拓扑随之被动确定。

  ⚠ 最常见的失败模式：找到了完美的几何中心机房，
    但那栋楼的光缆只有 12 芯且已经用满 → 方案作废。
    所以【纤芯普查】要和【机房勘察】同步做，不能分两步。
面试里被问"你怎么给一片区域规划 C-RAN"时，如果上来就画一个完美的星型拓扑，会被认为没做过工程。正确的开场是先问约束：这片区有哪些现存机房？纤芯普查做了吗？是自有光纤还是租的？有没有历史遗留的 D-RAN 站要保留？—— 这些问完，拓扑基本就只剩一两种可能了。

当距离超限时：四张牌

最常见的困境是：机房位置定死了，实测纤长超出前传预算。手上一共只有四张牌，按代价从小到大排：

手段做法能省多少代价
① 减少中间跳数把级联的交换机改成直连，或换直通转发的前传交换机每跳 5~30 µs，两三跳就是几十 µs最小，常常只是调整组网
② 换更短的光纤路由重新协调一条更直的管道路由视具体路由，可能省 30%+协调周期长，未必有资源
③ 把 DU 挪近放弃这个 DU 池，就近找次优机房，或者干脆退回 D-RAN可以彻底解决失去集中化收益；要新建/改造机房
④ 调整拆分点该站不做 7-2x，改成 Option 2 直连（把 DU 放回站点，只把 CU 集中）时延约束从 100 µs 放宽到 ms 级，距离限制基本消失该站失去 DU 集中化收益；网络出现两种形态，运维复杂度上升

注意这四张牌里没有"用 WDM 缩短距离"——这是个常见误解。WDM 解决的是纤芯不够，不是距离超限。无源 WDM 几乎不增加时延，所以它也几乎不减少时延；光是从暗纤换成 WDM，距离一米都不会短。

某新建城区规划了一个 C-RAN hub，覆盖半径内 18 个站。勘察阶段两个问题同时爆出来：（a） 出局光缆只有 48 芯，而 18 站 × 3 扇区 × 双纤 = 108 芯，缺口一倍多；（b） 其中最远的 3 个站，OTDR 实测纤长 15.8 / 16.4 / 18.1 km（图上直线距离才 9~11 km，管道绕行系数约 1.7），单向传播时延已达 77~89 µs，加上光模块与一跳汇聚交换机后逼近甚至超出 100 µs 预算。

最终是两个手段各解一题：纤芯缺口用无源 CWDM 解决——每个站点侧放一个 8 波合分波器，把 3 个扇区 + 备用波长复用到 1 对纤上，108 芯需求压到 36 芯，48 芯出局还留了余量；三个超距站单独处理——先把汇聚交换机那一跳去掉改为直连 hub（省下约 12 µs），15.8 km 的那个站压回预算内；剩下两个 16.4 / 18.1 km 的站怎么算都不够，改为该站保留本地 DU、只把 CU 集中（即从"前传 + 中传"退化成"只有中传"），中传的 ms 级预算下 18 km 毫无压力。

三点教训：① 纤芯普查和距离实测必须在方案立项前做，不能等到开工；② 管道绕行系数按 1.5~2 倍估，图上距离没有参考价值；③ 一张网里允许有两种形态——为了三个站把整个 hub 的方案推翻，才是真的不划算。

C-RAN 到底给承载网压了多少

最后把 C-RAN 的代价量化一下，这也是"集中化是否值得"这个决策的核心输入：

【D-RAN】每站独立
  前传：站内 100 m，DU 就在塔下 → 光纤成本近似为 0
  回传：每站一条 1~10 Gbps 链路
  承载压力：低

【C-RAN】20 个站汇聚到一个 hub
  前传：20 站 × 3 扇区 × 25 Gbps = 1.5 Tbps 进 hub
        纤芯需求（暗纤方案）= 20 × 3 × 2 = 120 芯
        或（无源 8 波 CWDM）= 20 × 2 = 40 芯
  中传：hub 出去约 20 × 5 Gbps = 100 Gbps（且可统计复用到更小）
  承载压力：前传是中传的 15 倍，且全部集中在 hub 的进局段

  → 结论：C-RAN 把"分散的无线设备成本"换成了
          "集中的光纤与机房成本"。
          这笔账在纤芯便宜的地方划算（自有管道、新建城区），
          在纤芯昂贵的地方不划算（老城区、租纤）。

【一个反直觉的推论】
  C-RAN 的收益（协作调度增益、资源池化、机房集约）
  与它的成本（前传纤芯与机房）在不同区域的相对大小完全不同，
  所以【全网统一做 C-RAN】和【全网统一做 D-RAN】都是错的答案。
  现网必然是混合的，而混合带来的运维复杂度本身也是一项成本。

验收：交付前必须实测的五项

承载网最容易出的事故不是"建错了"，而是"建完没测，问题在割接后才暴露"。前传尤其如此——它的失效模式里有好几种不产生任何告警。一条前传链路交付前，下面五项必须有实测数据，缺一项都不算交付：

#测什么怎么测判据不测的后果
1光纤实际长度OTDR 双向测量与设计一致；× 4.9 µs/km 后仍在时延预算内图纸距离和实际差 30~70% 很常见，方案可能根本不成立
2光功率预算光功率计测收端光功率高于模块接收灵敏度且留 3 dB 以上余量刚好够用的链路会在温度变化或器件老化后随机误码
3端到端单向时延设备自带的前传时延测量，或专用测试仪在 O-RAN 收发窗内，且留余量超窗表现为随机丢包，会被误判成"光纤有问题"
4时延抖动 / 包时延变化长时间（≥15 min）打流并统计 PDV 分布看 P99.99 与最大值，不看平均值平均值漂亮而尾部超标，割接后偶发误块，最难查
5同步性能 |TE|时间误差测试仪对比本地 PRTC，连续测 ≥15 minmax |TE| 在分配给该段的预算内；offset 无恒定偏移不对称误差不报警，只会让邻区干扰慢慢变差

第 4 项和第 5 项是最容易被跳过的，也正是最容易埋雷的。它们的共同特征是：短时间抽测一定是好的，问题只在长时间统计里露头。15 分钟是最低要求，条件允许应当测 24 小时以覆盖话务潮汐与昼夜温差。

面试题（12 道）

分层自测

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础前传、中传、回传分别连接谁、走什么接口、搬什么数据？

    三段对应关系是固定的：

    • 前传（Fronthaul）：DU ↔ RU，接口是 Open Fronthaul（Option 7-2x），搬频域 IQ 采样加波束权值与调度控制信息。
    • 中传（Midhaul）：CU ↔ DU，接口是 F1（Option 2 拆分），分 F1-C（F1AP over SCTP 38472）与 F1-U（GTP-U over UDP 2152），搬 PDCP PDU。
    • 回传（Backhaul）：CU ↔ 5GC，接口是 NG，分 NG-C（NGAP over SCTP 38412，对 AMF）与 NG-U（GTP-U over UDP 2152，对 UPF），搬用户 IP 包与核心网信令。

    加分的补充：注意 3GPP 的接口设计有高度一致的模式——控制面一律 XxAP over SCTP（NGAP/38412、XnAP/38422、F1AP/38472、E1AP/38462），用户面一律 GTP-U over UDP 2152。记住这个模式比背端口号有用。

    还要点出：逻辑上是三段，物理上未必。D-RAN 站点 CU/DU 一体，中传退化成机内背板；室分一体化小站三个功能全在一个盒子里，前传中传都不存在。

  2. 基础为什么前传的要求比另外两段严得多？

    一句话根因：前传处在无线物理层的硬实时闭环之内，另外两段不在。

    展开成因果链：拆分点越靠近射频 → 传的越是未经加工的物理层实时数据 → ① 数据量大（IQ 采样正比于带宽 × 天线数，与有没有用户无关）；② 时间敏感（每个 OFDM 符号必须在确定时刻从天线发出）；③ 必须相位同步（TDD 收发切换要全网对齐）。

    具体到数字：单向时延预算约 100 µs（TR 38.801 对 Option 7 类拆分给出的量级），抖动窗口 µs 级，同步要求 ns 级，丢包容忍 10⁻⁷ 量级。对比之下中传是 ms 级软约束、回传是几 ms 到几十 ms 且只影响体验。

    最能体现理解深度的一点：HARQ、调度、功控这些微秒到毫秒级的闭环全部在 DU 与 RU 之间闭合，回传根本不在环内。所以回传断了业务会停，但物理层不会"乱掉"；前传抖动几微秒，物理层直接出错。

  3. 基础中传和回传的带宽差多少？为什么？

    单站看，两者是同一个量级——它们搬的是同一批用户数据，只是中传搬的是 PDCP PDU、回传搬的是 PDCP 处理完之后的用户 IP 包，封装开销略有差别（都在 5% 上下）。

    真正的差别在两处：

    • 汇聚层级不同：一个 CU 下面挂 N 个 DU，所以 CU 出去的那条回传链路承载 N 个站的流量，是全网最粗的单链路。说"回传带宽最大"指的是这个，不是单站对比。
    • 统计复用能力不同：回传汇聚的用户越多，峰均比越低，统计复用增益越显著（工程上常见 3~5 倍）。中传只能在同站的几个扇区间复用，增益有限。

    给个参照数：100 MHz/64T64R 三扇区站，中传峰值约 5 Gbps（1.6 Gbps × 3 × 1.06 封装开销）；20 个这样的站汇聚后，回传按峰值堆是 96 Gbps，但按忙时话统算通常 12 Gbps 就够——这个差距正是统计复用。

  4. 基础光纤里的传播时延是多少？这个常数怎么限制前传距离？

    约 5 µs/km（单向），10 µs/km（往返）。

    推导两步：单模光纤群折射率 n ≈ 1.468，光速 v = c/n = 299792458 / 1.468 ≈ 2.04×10⁸ m/s；1 km ÷ 2.04×10⁸ m/s ≈ 4.9 µs，工程上取整成 5。

    它怎么限制前传：前传单向预算约 100 µs，100 ÷ 5 = 20 km —— 这就是常被引用的前传距离理论上限。但这个 20 km 是"传播时延吃光整条预算"的极限值，实际还要扣掉光模块收发、每跳交换机转发（5~30 µs）、以及两端设备处理，所以多数运营商的规划半径在 10 km 以内。

    最容易被忽略的一点：要用实际纤长，不是地图直线距离。光纤沿管道走、绕障碍、每个接头盒留余长，实际长度通常是直线距离的 1.3~2 倍。一个"图上 9 km"的站点实测 16 km 是很常见的事，而这直接决定方案成不成立。所以规划一律以 OTDR 实测为准。

9.2 中级（区分熟练度）

  1. 中级端到端时延预算怎么逐段分配？哪一段是硬约束？

    以 3GPP TS 22.261 给的用户面目标（eMBB 4 ms、URLLC 0.5 ms，单向）为总盘子，逐段扣：

    环节典型单向耗时性质
    空口 Uu（含调度等待与 HARQ 重传）0.5~2 ms占大头，不可压缩
    RU 处理数十 µs设备实现
    前传≤100 µs硬 deadline
    DU 处理数百 µs设备实现
    中传0.1~2 ms软约束
    CU 处理数十~数百 µs设备实现
    回传1~10 ms软约束，最大的一块可优化空间
    UPF 转发数十~数百 µs软约束

    关键洞察：前传的绝对数值最小，却是唯一超了就直接失效的一段。其他各段超预算只是"慢一点"，前传超预算是包落在 RU 接收窗之外被直接丢弃，那批 PRB 的 IQ 缺失、符号出错。这类约束是 hard deadline，不能和其他 soft budget 放在一起做加减法互相借用。

    如果面试官接着问"URLLC 1 ms 怎么保证"，正确的两个杠杆是：① UPF 下沉到边缘（砍掉回传那几毫秒，收益最大）；② 免调度 / 预调度（砍掉调度请求往返）。优化前传和 DU 处理只有几十微秒空间，性价比最低。

  2. 中级WDM 在承载网里解决什么问题？它能缩短前传距离吗？

    WDM 解决的是纤芯不够，不是距离超限。这是最常见的误解，值得先把结论摆出来。

    它的作用是把多路信号用不同波长复用到同一对光纤上。典型收益：一个 20 站的 C-RAN hub，暗纤方案需要 20 × 3 扇区 × 2 = 120 芯；用 8 波无源 CWDM，站点侧一个合分波器把 3 个扇区加备用波长复用到 1 对纤，需求压到 40 芯。在市区纤芯紧张、租纤按芯 × 公里计费的场景，这直接决定方案成不成立。

    两个标准要分清：CWDM（ITU-T G.694.2）18 个波、20 nm 间隔、覆盖 1271~1611 nm，器件便宜、无需温控；DWDM（ITU-T G.694.1）C 波段 50/100 GHz 间隔，波数多得多，但彩光模块贵、需要波长规划。

    为什么它不缩短距离：无源 WDM 只是合分波，光走的还是那根纤、那段距离，几乎不增加也不减少传播时延。时延由物理距离决定，换承载技术改变不了距离。

    加分点：CWDM 在前传上有个坑——如果用单纤双向配不同波长，色散会导致两个方向群时延不等，引入 ns 级的 PTP 不对称误差。CWDM 波长间隔大（20 nm），这个问题比 DWDM 严重。

  3. 中级有源和无源承载方案怎么取舍？

    判据是"你更缺什么"，三者不可兼得：

    • 缺纤芯 → 无源 WDM。用波长换纤芯，器件不耗电、不占机房、成本最低。
    • 缺运维手段 → 有源（OTN / SPN / PTN）。无源方案最大的问题是没有任何监控：某个波长坏了不会告警，只能派人扛着 OTDR 到现场逐波测。一个大网上百个站这样搞是运维灾难。有源设备有完善的告警、环回、性能计数、保护倒换。
    • 缺时延预算 → 暗纤或无源。有源设备每跳 5~20 µs（OTN 还要算 FEC 编解码），级联两三跳就吃掉小半条前传预算。

    还要加一条同步：有源设备必须逐跳实现 T-BC 才能透传 PTP，纯电层映射会打断同步链。无源器件对 PTP 天然透明。SPN/MTN 是个例外——它基于 66B 码块交叉、不解析包，时延确定且设计上就考虑了高精度时间传送。

    现网的真实答案是混合：密集城区纤芯紧张用无源 WDM，郊区长距用有源，站内短距直接暗纤。统一用一种方案的网络基本不存在。

  4. 中级GTP-U 在回传上起什么作用？它给传输网带来什么麻烦？

    作用：GTP-U（TS 29.281）是用户面的隧道封装，把用户的 IP 包装进一个外层 IP/UDP/GTP-U 里，靠 32 位的 TEID 区分是哪个 UE 的哪条 QoS 流。这样一来：① 用户的私网 IP 与传输网路由完全解耦，UE 移动时外层地址变而内层不变；② 移动性管理只需改隧道端点，不用动用户 IP。5G 里还会用 GTP-U 扩展头（PDU Session Container）携带 QFI。

    最小头 8 字节：Flags(1) + Message Type(1) + Length(2) + TEID(4)。典型 30 ff xx xx | TEID，其中 0x30 表示 GTPv1、无扩展头/序列号，0xFF 是 G-PDU（承载用户数据）。

    给传输网的两个麻烦：

    • 吃 MTU：外层 IPv4+UDP+GTP-U = 36 字节，IPv6 是 56，再叠 VLAN 和可能的 IPsec。1500 的传输 MTU 会把用户内层压到 1400 上下，否则分片或 PMTUD 黑洞。所以回传网普遍配 jumbo frame。
    • 破坏负载分担：所有 UE 的流量共用同一组外层五元组，传统 ECMP 哈希会把整条隧道压在一条路径上。需要设备支持基于 TEID 或内层头的哈希（"GTP-aware load balancing"）。

    排障加分点：TEID 是接收方各自分配的，上下行两个方向的 TEID 完全无关。查"上行通下行不通"时，别去核对两边是不是同一个 TEID 值。

9.3 高级（体现深度）

  1. 高级为什么说"时间同步能不能透传"是承载选型的决定因素？

    因为选型表里其他所有列（时延、带宽、成本、运维）都是连续量——差一点可以用钱或妥协换回来；只有同步透传是离散的 0/1：透不过去，这条链路就不能承载 TDD 前传，其他指标再漂亮都没用。所以它是第一道筛子，不是最后一道。

    约束从哪来：TDD 系统里相邻基站必须在同一时刻从收切到发，否则一个站的下行功率会直接砸进邻站的上行接收——不是性能下降，是整片区域上行瘫痪。TS 38.133 要求小区间相位同步优于 3 µs，对应 ITU-T G.8271.1 的端到端 |TE| ≤ 1.5 µs。

    1.5 µs 要在整条链上分摊，于是每跳只剩几十纳秒：PRTC 本身约 100 ns，每台 T-BC 按 G.8273.2 分 Class A ≤50 ns / Class B ≤20 ns / Class C ≤10 ns（前传通常要求 Class C），RU 自身还要占几十到几百 ns。预算这么紧的直接后果是：链路上多一台不支持 T-BC 的设备，整条预算立刻崩。

    破坏方式只有三种：① 排队时延波动（PTP 报文和业务同队列，时间戳被排队污染，误差 µs 到数百 µs，直接爆表）；② 设备恒定误差 cTE（每跳 10~50 ns 累积）；③ 链路不对称（往返时延不等，PTP 把差值的一半当成时钟偏差）。

    最后一项最值得讲，因为它完全无法被 PTP 自己发现——协议的数学模型假设了对称，不对称就变成一个看不见的常数偏移：所有告警都是绿的，ptp4l 也显示锁定（s2），只有空口的邻区干扰在悄悄变差。这是唯一不报警的失效模式，也是为什么租波长做前传很危险——你无从测量出租方链路的不对称量。

  2. 高级链路不对称是怎么产生的？前传上具体有哪些来源，各是什么量级？

    PTP 用 t1~t4 四个时间戳算时钟偏差，公式里隐含假设"去程时延 = 回程时延"。真实链路不满足时，误差 = 不对称量 / 2，且这个误差是常数偏移，不随时间收敛。

    前传上的三个主要来源：

    • 单纤双向（BiDi）用不同波长。典型配对 1310 nm 发 / 1550 nm 收。单模光纤的群折射率随波长变化（色散），两个方向传播速度不同，群时延差在 1~2 ns/km 量级（具体值取决于光纤色散参数与实际波长，需查光纤规格）。10 km 链路就是 10~20 ns 的往返差、5~10 ns 的相位误差——这一项就吃掉 G.8273.2 Class C 的整条预算。对策是前传优先用双纤单向 + 同波长，两根纤长度尽量一致；只有一根纤时用同波长双向方案，或在设备上配置不对称补偿值。
    • 保护倒换后走了不同长度的路径。主用 8 km、备用 14 km，倒换瞬间链路时延突变 6 × 4.9 ≈ 29 µs，相位跳变约 14.7 µs，远超 1.5 µs 网络限值。现象是倒换后该片区上行底噪抬升、邻区干扰告警，等 PTP 重新收敛（可能几分钟）才恢复。对策是把主备路径长度差纳入规划约束（常见要求差值 < 1~2 km），或让 PTP 在倒换时进入保持态而不是立刻跟踪新路径。
    • 设备内部收发通道时延不等。光模块、PHY、时间戳打点位置的差异，这部分体现在设备的 cTE 指标里，靠选高等级 T-BC 控制。

    怎么发现：看 ptp4l 的输出，如果 path delay 非常稳定但 master offset 存在恒定偏移，这是不对称的典型特征——而它本身不会报任何错。别看到状态 s2 就以为万事大吉，s2 只说明"跟上了主时钟"，不说明"跟上的那个时刻是对的"。

  3. 高级为什么统计复用在回传可行、在前传不可行？

    统计复用要成立需要两个前提：① 各路流量是突发的（峰均比高）；② 各路峰值不同时到来（相互独立）；此外还隐含 ③ 偶尔的排队/丢包可以被上层吸收。

    回传三条全满足：用户流量天然突发（刷完一段视频就停），不同用户之间独立，且端到端有 TCP/QUIC 兜底。汇聚的用户越多，总流量越平滑，工程上常见 3~5 倍复用增益。所以回传按"忙时均值 × 过载系数"规划，而不是按峰值堆——两者能差 3~5 倍。

    前传三条全不满足：

    • 速率是配置驱动、近似恒定的。CPRI 完全恒定，与用户数、调度、MIMO 层数都无关，只取决于天线数与采样率；7-2x 会随占用的 PRB 有所变化，但规划仍必须按峰值——因为小区随时可能被打满。峰均比接近 1，没有可复用的空间。
    • 同一 DU 下各小区的忙时高度相关（同一片区域的话务潮汐同步），不满足独立性。
    • 丢包不可吸收。IQ 包没有重传机制，丢一个包就是一批 PRB 的采样缺失，直接表现为符号出错、底噪抬升。丢包容忍在 10⁻⁷ 量级。

    所以前传必须按峰值刚性预留带宽，也不能和其他业务混跑抢队列。这也解释了为什么前传是三段里单位比特成本最高的一段——它没法用统计复用摊薄。

  4. 高级要新建一个覆盖 20 个站的区域，你怎么规划这三段承载？

    这是综合题，考的是顺序而不是知识点。上来就画星型拓扑会被认为没做过工程——正确的开场是先问约束。

    第一步：摸清资源，不做任何设计。

    • 纤芯普查：这一片有哪些管道、每条多少芯、已用多少、是自有还是租的、租期多久。
    • 机房勘察：候选机房的位置、电力容量、制冷、承重、空间、产权租期、出局纤芯数。纤芯普查和机房勘察必须同步做——找到完美几何中心却发现那栋楼只有 12 芯且用满，方案就作废了。
    • 历史存量：有没有要保留的 D-RAN 站、既有 BBU 机房能否复用。

    第二步：定 DU 位置。现实中 DU 位置是被"选出来"而不是"规划出来"的——同时满足位置、光纤、电力、空调、承重、空间、产权、安全八项的候选点，一个区里可能只有两三个。选定后，对每一个 RU 站点做 OTDR 实测纤长，绝不用地图直线距离（管道绕行系数按 1.5~2 倍估）。

    第三步：核算前传预算，逐站判定。实测纤长 × 4.9 µs/km + 光模块 + 每跳交换（5~30 µs）≤ 100 µs。超限的站单独拎出来。

    第四步：算纤芯需求，决定要不要 WDM。暗纤方案 20 站 × 3 扇区 × 2 = 120 芯；出局只有 48 芯就上无源 CWDM，站点侧一个 8 波合分波器把 3 扇区 + 备用复用到 1 对纤，压到 40 芯。记住 WDM 解决纤芯不解决距离。

    第五步：处理超距站，按代价从小到大出牌。① 减少中间跳数（改直连，每跳省 5~30 µs）；② 换更短的光纤路由；③ 把 DU 挪近或退回 D-RAN；④ 该站调整拆分点——保留本地 DU、只集中 CU，前传消失、只剩 ms 级预算的中传，18 km 也毫无压力。为了两三个站推翻整个 hub 方案才是真的不划算，一张网里允许有两种形态。

    第六步：同步方案。确认整条前传链路逐跳能透传 PTP（有源设备必须是 T-BC，前传通常要 G.8273.2 Class C）；主备路径长度差纳入约束；避免单纤双向异波长。

    第七步：中传与回传。中传按峰值算（20 站 × 5 Gbps，可与回传共用 IP-RAN），注意把同一 DU 的 F1-C 与 F1-U 绑到同一条转发路径，避免 ECMP 把信令与数据散到时延差几毫秒的两条路上导致切换丢包。回传按忙时话统（不是峰值堆叠）算，取"Σ 忙时均值 × 过载系数"与"单站峰值 × 并发系数"的较大者。

    最后交付的不是一张拓扑图，是一张逐站的核算表：站名、实测纤长、传播时延、跳数、总时延、余量、纤芯占用、承载方式、同步配置。有余量为负的行，就有对应的处置方案。
