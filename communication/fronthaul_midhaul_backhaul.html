前传、中传、后传：Fronthaul / Midhaul / Backhaul

上一篇把基站拆成了 CU / DU / RU，它们之间用网络连接。这三段连接各有名字、各有截然不同的性能要求：前传（DU↔RU）、中传（CU↔DU）、后传（RAN↔Core）。理解它们的差异，尤其"为什么前传对延迟/抖动/带宽/同步如此苛刻"，是打开 CPRI/eCPRI 与 O-RAN 的钥匙。

01

三段承载全景

把 CU/DU/RU 之间的"线"命名

名字里的 "haul" 就是"搬运/牵引"。图里那句结论背后是一条可以量化的因果链，本篇要做的就是把每一环的数字摊开。

承载网（Transport Network）：连接无线接入网各功能单元、以及接入网与核心网的传输网络。它不产生业务只搬运业务，但它的时延、抖动、同步能力会直接决定无线侧能不能工作——这是它与普通企业网最大的区别。

三段不是凭空冒出来的

"前传"这个词在 2G/3G 时代并不存在。当年基站是一个铁柜子，射频与基带都在里面，机柜到天线之间是馈线（粗同轴电缆），传的是模拟射频信号。真正把"基站内部的一根线"变成"一段需要规划的网络"，经历了三次结构性变化：

阶段物理形态产生了哪一段驱动力
2G / 早期 3G一体化基站 + 馈线到天线只有回传（E1/T1，后来是 IP）无
3G 后期 / 4G 初期BBU + RRU 分离，RRU 上塔诞生前传（CPRI，几百米）功放搬到天线边，省掉馈线 3 dB 损耗
4G C-RAN多个 BBU 集中到一个机房前传拉长到 km 量级机房集中降本、协作化调度
5G NRBBU 再拆成 CU + DU诞生中传（F1）CU 上云集中管移动性，DU 靠近站点保实时
被问"为什么要有前传"时只答"为了 C-RAN 集中化"，说明只知道 2015 年之后的故事。正确的因果顺序是：先有 RRU 上塔（省馈线损耗）→ 才有 CPRI 光纤 → 再有 C-RAN 把它拉长 → 前传才成为一个网络问题。

三段在物理上未必真的是三段

逻辑上是 RU–DU–CU–Core 四个节点三段链路，但现网里这四个功能经常合并同址，某一段就退化成机内背板甚至一根短跳纤：

这也解释了一个常见困惑：运营商一边说"六成的站是 D-RAN"，一边说"前传是最大的投资瓶颈"——剩下四成 C-RAN 站点占了纤芯消耗的绝大头。

下文如果不特别说明，都以 ② / ③ 这种三段齐全的形态为讨论对象。功能拆分本身（为什么切在 Option 2 和 7-2x）不在本篇展开，见 CU/DU/RU 功能拆分。
02

Backhaul 后传（RAN ↔ Core）

最"普通"的一段，就是常规 IP 承载

后传（更常见的译名是回传）连接 CU 与核心网，搬的是用户业务数据 + 核心网信令，本质就是 IP 包。它是三段里最"像普通互联网"的一段，先把它立成基准，后面两段的"苛刻"才有参照物。

NG 接口其实是两个接口

gNB 与 5GC 之间的接口叫 NG，但它在传输上是泾渭分明的两条流：

NG-C（控制面）NG-U（用户面）
应用层协议NGAP（3GPP TS 38.413）GTP-U（3GPP TS 29.281）
传输层SCTPUDP
端口SCTP 38412（TS 38.412）UDP 2152
对端网元AMFUPF
流量占比< 1%（信令）> 99%（业务）
丢包容忍极低，SCTP 自己重传由上层 TCP/QUIC 负责
典型规划要求可靠性优先，双归属 AMF带宽优先，可统计复用

"控制面走 SCTP、用户面走 UDP"这个分工在 3GPP 里非常稳定：Xn 是 XnAP/SCTP 38422、F1 是 F1AP/SCTP 38472、E1 是 E1AP/SCTP 38462，用户面一律 GTP-U/UDP 2152。记住这条规律比背端口号有用。

被追问"为什么信令用 SCTP 不用 TCP"，答三点：① 多流避免队头阻塞，一个 UE 的信令卡住不拖累其他 UE；② 多归属，一条 association 绑多个 IP，链路断了不用重建；③ 保留消息边界，NGAP 面向消息，用 TCP 还得自己分帧。而用户面已有端到端 TCP/QUIC 兜底，再加一层重传只会放大时延。

GTP-U：回传上真正在跑的那层封装

回传上抓包看到的绝大部分是下面这个"洋葱"，洋葱心那 8 个字节就是 GTP-U 头：

对承载网工程师来说，这层封装带来三个实际后果：

  • MTU 被吃掉 36–60 字节。传输网 MTU 若只有 1500，用户内层就得压到 1400 上下，否则分片或触发 PMTUD 黑洞。回传普遍配 jumbo frame正是为了不动用户的 MTU。
  • 传输网看不见用户流。所有 UE 共用同一组外层五元组，传统 ECMP 会把整条隧道压在一条路径上。需要设备支持基于 TEID 或内层头的哈希（"GTP-aware load balancing"）。
  • 抓包要看包长分布，不能只看速率。tcpdump -nn 'udp port 2152' 若多是几十字节的小包，说明用户面以 IoT/信令类为主，瓶颈是 pps 而不是 bps。

回传的带宽怎么规划：统计复用是这一段的特权

回传是三段里唯一可以放心做统计复用的一段：它搬的是用户业务流量，而用户流量既突发（刷完一段视频就停）又独立（不同用户的峰值不同时到来）。汇聚的用户越多，总流量的峰均比越低。

回传带宽的工程算法：忙时均值与峰值保底取 max

  BW = max( Σ 各站忙时均值 × 过载系数,  单站峰值 × 并发系数 )
     = max( 20 × 0.35 Gbps × 1.3,      4.8 Gbps × 2.5 )
     = max( 9.1 Gbps,                  12 Gbps )
     ≈ 12 Gbps

  · 忙时均值来自实际话统（PM 计数器），不是拍脑袋
  · 过载系数覆盖话务波动；并发系数保证少数用户能真的跑出峰值体验
  · 取 max 而不是相加：前者管"平均别拥塞"，后者管"峰值别封顶"
某地市按"单小区峰值 × 小区数"算出回传要扩到 400 Gbps，预算被打回。重拉三个月 PM 计数器才发现：忙时利用率 P95 只有容量的 18%，真正的瓶颈是两个环上的微波跳段（雨衰时降速到 400 Mbps）。最终只把那两跳改成光纤，花费不到原方案的 5%。回传的问题九成不是总带宽不够，而是局部瓶颈——先看话统，再谈扩容。

回传的时延要求为什么"最宽松"，以及它宽松到什么程度

说宽松是相对前传而言，不等于随便。准确的说法是：回传时延不参与无线侧的硬实时闭环，只影响用户体验指标。

回传时延影响什么机制敏感度
TCP / QUIC 吞吐吞吐 ≈ 窗口 / RTT高：多 10 ms，单流吞吐可掉三成以上
网页首屏、API 响应叠加在用户感知 RTT 上中：几 ms 无感，几十 ms 明显
URLLC / 边缘业务端到端预算被回传吃掉极高：这正是 MEC 把 UPF 下沉的动因
NGAP 信令流程接入、切换的流程时长低
无线调度、HARQ完全不影响——闭环在 DU 内部就闭合了无

最后一行是关键：无线侧所有微秒~毫秒级的硬实时闭环（HARQ、调度、AGC、功控）全部在 DU 与 RU 之间闭合，回传根本不在环内。所以回传断了通话会掉、上网会停，但物理层不会"乱掉"；前传抖动几微秒，物理层直接崩。这就是两段要求天差地别的根因。

回传的工程重点是带宽、可靠性、成本，而不是极限低时延。它和普通运营商 IP 承载网没有本质区别，IP/MPLS、SR-MPLS、SRv6 都能直接用——这也是它最便宜的原因。
03

Midhaul 中传（CU ↔ DU）

承载 F1 接口，介于前传与后传之间

中传连接 CU 与 DU，承载 F1 接口（Option 2 拆分，切在 PDCP/RLC 之间）。此时数据已是较高层的 RAN 协议数据（PDCP PDU），不再是原始基带采样。

F1 的协议栈：和 NG 长得几乎一样

看懂了上一章的 NG，F1 几乎不用重新学——3GPP 在接口设计上高度自我复用：

F1-C（控制面）F1-U（用户面）
应用层协议F1AP（TS 38.473）NR 用户面协议（TS 38.425）
承载于SCTP 38472GTP-U / UDP 2152
搬什么UE 上下文、承载配置、DU 配置更新、寻呼PDCP PDU + 下行递送状态反馈
带宽占比< 1%> 99%
断链后果无法接纳新 UE，存量逐步释放业务立即中断

中传之所以比前传宽松一个量级，全部来自拆分点的位置——同一个站，两段搬的东西完全不是一回事：

F1-U 里还坐着一层容易被忽略的 NR 用户面协议（TS 38.425），它藏在 GTP-U 扩展头里，定义了 CU→DU 的 DL USER DATA 和 DU→CU 的 DDDS 两类 PDU。

DDDS（Downlink Data Delivery Status）：DU 把"已送达到哪个 PDCP SN、丢了哪些、还想再要多少字节（Desired Buffer Size）"周期或事件触发地上报给 CU，CU 据此决定往下灌多少。作用相当于 TCP 的接收窗口，只不过运行在 CU 与 DU 之间。

它让中传时延变成一个吞吐问题，而不只是体验问题：需要的 DU 缓冲 ≈ 单 UE 峰值速率 × 中传 RTT。1 Gbps 下，同机房 0.2 ms 只要 25 KB，跨城 10 ms 单 UE 就要 1.25 MB——乘上几百个 UE 就是 GB 级，DU 内存扛不住。后果不是"慢一点"，而是 CU 灌不满、DU 空口有资源却没数据发：实测速率上不去，而所有 KPI 与传输侧丢包都正常，唯一线索是 DDDS 的 Desired Buffer Size 长期贴顶。

"中传能拉多远"这个问题的正确答法不是背一个 km 数，而是：中传没有硬性的物理层时序约束（那是前传的事），它的距离上限由三个软约束决定——① F1-U 流控闭环的带宽时延积 vs DU 内存；② 切换与重配置流程的时长预算；③ 端到端时延预算里留给中传的那一份。典型规划值是单向几 ms，对应几十到一百多公里，但真正拍板前要看 DU 的缓冲能力。

中传带宽 ≈ 用户面吞吐 + 开销，就这么简单

算中传带宽只需要一个乘法，唯一需要留神的是封装开销随包长剧烈变化：

中传带宽 = 小区峰值吞吐 × 扇区数 × (1 + 封装开销) × 并发/过载系数

【封装开销】以 1400 B 的 PDCP PDU 为例
  Ethernet 14 + VLAN 4 + IPv4 20 + UDP 8
  + GTP-U(含扩展头) 12 + NR-U PDU Type 0 ~6   = 64 B
  64 / 1400 ≈ 4.6%，再算前导码+帧间隙 20 B → 约 6%

  ⚠ 若是 128 B 的 VoIP/信令小包，开销比冲到 50% 以上
    → 规划要看 pps，不能只看 bps

【100 MHz / 64T64R 三扇区站】
  1.6 Gbps（单小区 DL 峰值，4 层 256QAM）× 3 × 1.06 ≈ 5.1 Gbps
  → 一条 10GE 中传口足够，还有余量给 UL 与信令
拆分点的权衡是双向的：拆得越高传输越省心，但集中化收益（协作调度、资源池化）也越少。详见 CU/DU/RU 功能拆分。

中传常见的三个坑

接入成功率忽高忽低（SCTP association 反复重建）、单用户速率上不去（F1-U 流控被 RTT 压制）、切换成功率偏低——三者的现象与查法汇总在 §5.2 的倒推表里。这里只展开最隐蔽的第三个：

F1-C 与 F1-U 在传输网眼里是完全不同的两条流（一个 SCTP 一个 UDP），ECMP 可能把它们散到时延差好几毫秒的两条路径上——信令说"数据已经切过去了"而数据还堵在旧路径，表现出来就是切换期丢包。规划时要把同一 DU 的 F1-C 与 F1-U 绑到同一条转发路径（同一个 DSCP + 策略路由，或在 SR 里显式指定 path）。

最后是个组网层面的判断：中传绝大多数情况下不必单独建网。它的指标（ms 级时延、无硬性相位要求、Gbps 带宽）和回传高度重叠，把 F1 与 NG 一起放在既有 IP-RAN 上、用不同 VPN 实例或 SR 策略隔离即可。单独建网只有一种理由：CU–DU 时延被某个 URLLC 业务压得很低。这与前传形成鲜明对比——前传几乎必然要独立组网，因为它的指标和任何既有网络都不兼容。

04

Fronthaul 前传（DU ↔ RU）

整个通信系统里最"变态"的一段

前传连接 DU 与 RU（Option 7-2x，切在 PHY 内部），搬的是频域 IQ 采样。要求堪称极端：

带宽巨大

IQ 数据量正比于天线数 × 带宽 × 采样率，单小区可达几十到上百 Gbps。

延迟极低

单向 ~100 µs 级，因为 HARQ 与调度有硬性时间预算。

抖动极小

IQ 按时间刻度对齐，包到达时间一抖就直接破坏信号。

同步极严

频率 + 相位都要 ns 级对齐（TDD 尤甚），靠 PTP/SyncE。

IQ 数据：无线信号用同相（I）与正交（Q）两路采样表示的复数基带样本。CPRI 传时域 IQ，eCPRI/7-2x 传频域 IQ 并把部分处理下沉到 RU 以省带宽。报文格式细节见 eCPRI 深入，本篇只关心它对承载网提了什么要求。

把前传带宽算出来

7-2x 传的是频域 IQ，带宽正比于"每秒有多少个资源单元（RE）要传"，而这个数只取决于配置，与用户多少无关：

【第一步：每秒多少个 RE（每层）】
  100 MHz @ SCS 30 kHz → N_RB = 273
  子载波数   = 273 × 12          = 3276
  每 slot 符号数                  = 14
  slot 时长（30 kHz）             = 0.5 ms  → 每毫秒 2 个 slot
  每毫秒符号数 = 14 × 2           = 28
  ────────────────────────────────────────
  RE 速率 = 3276 × 28 × 1000      = 91.7 M RE/s（每层）

【第二步：每个 RE 多少比特】
  未压缩 16 bit I + 16 bit Q                   = 32 bit/RE
  块浮点压缩 BFP-9（9 bit 尾数 ×2 + 共享指数） ≈ 18.5 bit/RE
  ────────────────────────────────────────
  每层速率：未压缩 91.7M × 32   ≈ 2.94 Gbps
            BFP-9   91.7M × 18.5 ≈ 1.70 Gbps

CPRI 那一栏还有个致命属性：它的速率与有没有用户、调度多少、MIMO 几层全都无关，只取决于天线数与采样率。这个恒定速率特性一路继承到了 7-2x，也是前传无法统计复用的根源。

面试里算前传带宽，评委想听的是你知道哪些量决定它：载波带宽、SCS、流数（Cat A 看天线端口、Cat B 看层数）、量化位宽与压缩方式。能讲清"为什么 Cat B 省一个量级"，比背出 25 Gbps 有价值得多。

时延：100 µs 是怎么来的，以及它意味着什么

3GPP TR 38.801 给 Option 7 一类拆分标注的单向时延在 100 µs 量级，O-RAN WG4 把它落成了具体的收发窗。这个数字要和熟悉的量级比一下才吓人：

对比对象量级相对前传预算
前传单向预算100 µs1×（基准）
光在 20 km 光纤里跑一趟~98 µs吃掉整条预算
普通以太网交换机存储转发5~30 µs（随排队波动）一跳就 5~30%
回传的典型单向时延1~10 ms10~100 倍于整条预算
跨城 ping 的 RTT10~30 ms100~300 倍

换句话说：前传的整条时延预算，还不够一个普通 IP 网络做完一次路由查找加一次排队。这不是"要求高"，是"根本不能按 IP 网络的思路来建"。

抖动：比时延更致命的那个指标

时延大，可以通过把接收窗口整体往后挪来补偿——代价是牺牲一点空口时延预算，但至少能工作。抖动不行，因为它没法补偿：

丢一个包不是"少一点数据"，而是那一批 PRB 的 IQ 整体缺失，直接表现为该符号底噪抬升或误块。

最反直觉的一点：平均时延更低的链路可能完全不能用。一台"平均转发 8 µs、拥塞时排队到 200 µs"的通用交换机，比一条"固定 60 µs 的裸光纤"糟糕得多。确定性 > 低时延——这条原则贯穿整个前传工程，也决定了前传上的交换机必须严格优先级 + 直通转发或极浅缓冲 + 支持 1588v2 的透明/边界时钟，很多厂商为此专门做了"前传交换机"这一品类。

同步：前传是唯一一段"同步比数据还重要"的网络

TDD 系统里相邻基站必须在同一个时刻从收切到发。切换时刻不一致，一个站还在发下行、邻站已经开始收上行，收到的全是隔壁的下行功率——基站互干扰，后果不是"性能下降"而是整片区域的上行瘫痪。

为什么前传最苛刻

根因是"它离无线物理层最近"

因果链本身很短：拆分点越往下 → 传的越是未加工的物理层实时数据 → 数据量越大、时间越敏感（§4.1 的对数轴图已量化过）。但"离物理层近"只是定性答案。真正把预算压到 100 µs 的，是空口时序被硬编码在标准里——它不会因为你把 DU 搬远了就宽容一点。

5 µs/km：一个改不了的物理常数

前传距离的上限不是运营商定的，是光速定的。推导只有两步：

【光在单模光纤里的传播速度】
  真空光速 c = 299 792 458 m/s
  单模光纤群折射率 n ≈ 1.468（1550 nm，G.652）
  v = c / n ≈ 2.042 × 10⁸ m/s

【每公里时延】
  t = 1000 / 2.042e8 = 4.897 µs ≈ 4.9 µs/km
  → 工程上取整记作 5 µs/km，往返 10 µs/km

  取整留出的余量正好覆盖跳纤与熔接盘里绕的那几十米。
  n 随波长微变，不同资料给 4.8~5.0 µs/km 都对。

⚠ 这只是传播时延，不含光模块收发（每端 0.1~1 µs）、
  设备转发（每跳 1~30 µs）、FEC 编解码（OTN 数 µs ~ 十几 µs）。

前传网的 QoS 与保护：两个反直觉的结论

前传跑在共享以太网上时（O-RAN 场景很常见），有两件事和常规网络工程的直觉相反。

结论一：前传流不能只是"优先级最高"，最好是"根本不和别人共队列"。严格优先级只保证前传排在别人前面，可一旦有个大包正在发送，前传包仍要等它发完——这就是存储转发的头阻塞：10 GbE 上 9000 B 巨帧要 7.2 µs，同样的帧在 1 GbE 上是 72 µs，一下吃掉大半条预算。三种做法按效果排：① 物理隔离（独占端口/波长/纤芯）；② 帧抢占（802.1Qbu / 802.3br，高优先帧可打断低优先帧）；③ 必须共享时限制同端口其他业务的最大帧长，把最坏头阻塞压到 12 µs。只配优先级、不管帧长与链路速率，是前传抖动最常见的根因。

结论二：前传的保护倒换，弊可能大于利。主备路径长度不一样，倒换就会导致相位跳变（§7.3 算过：6 km 路径差 ≈ 14.7 µs，是网络限值的十倍）。倒换本身"成功"了，业务却因同步失准而恶化，还波及邻区。三段的保护粒度因此完全不同：

"前传要不要做保护"没有标准答案，但能说出"保护倒换会引入同步相位跳变，所以主备路径长度差必须纳入规划约束"，就能明显区别于只会背"关键链路要冗余"的候选人。这也是承载网与普通 IP 网思维方式差异最集中的一个点：在前传上，可用性和确定性是会打架的，不是天然一致的。

工程现实：光纤与机房

理论拓扑很美，现实是有什么光纤用什么

纸面上的流程是：定 RU 位置 → 定 DU 位置 → 算距离 → 选技术。现实中恰好倒过来：先查这片有哪些光纤资源、哪些机房还有空间和电 → 反推 DU 只能放在哪 → 看前传距离能不能达标 → 不达标再想办法。拓扑也是这么被决定的：

光纤资源：四种来源，四种约束

获取方式成本结构可控性典型约束什么时候选它
自建管道 + 自敷光缆一次性投入极高，之后近乎零边际成本最高：芯数、路由、维护全自己说了算路权审批以月甚至年计；市区开挖常年受限长期高价值路由（核心环、hub 进出局）

租波长在前传上是个陷阱：你拿到的是一个"看起来像光纤"的通道，但对端设备、路由、主备路径差、有没有电中继统统不知道——而这些恰恰是同步能否透过去的全部因素。真要租，合同里必须写入单向时延上限、往返不对称量上限、PTP 透传能力三项并要求测试报告。

机房：比光纤更难解决的约束

一个能放 DU 池的 C-RAN 机房要同时满足八项，缺一不可：位置在覆盖区几何中心附近（它决定所有 RU 的前传距离）、光纤有足够纤芯出局、电力够（满配机架数千瓦，还要 UPS 与油机）、空调制冷匹配、承重扛得住机架与电池组、空间含维护通道、产权租期足够长、安全有防水防火与动环监控。

同时满足八项的候选点一个区里往往只有两三个，于是DU 位置几乎是被"选出来"而不是"规划出来"的。最常见的失败模式：找到了完美的几何中心机房，但那栋楼的光缆只有 12 芯且已用满——所以纤芯普查必须和机房勘察同步做。

被问"你怎么给一片区域规划 C-RAN"时，上来就画一个完美星型拓扑会被认为没做过工程。正确的开场是先问约束：有哪些现存机房？纤芯普查做了吗？自有还是租的？有没有要保留的 D-RAN 站？问完这些，拓扑基本只剩一两种可能。

当距离超限时：四张牌

机房位置定死、实测纤长又超预算时，手上只有四张牌，按代价从小到大排：

手段做法能省多少代价
① 减少跳数级联交换改直连，或换直通转发的前传交换机每跳 5~30 µs最小，常只是调整组网
② 换更短路由重新协调一条更直的管道可能省 30%+协调周期长，未必有资源
③ 把 DU 挪近就近找次优机房，或退回 D-RAN彻底解决失去集中化收益；要建/改机房
④ 调整拆分点该站改 Option 2：DU 放回站点，只集中 CU约束从 100 µs 放宽到 ms 级该站失去 DU 集中化收益；全网出现两种形态

注意四张牌里没有"用 WDM 缩短距离"——WDM 解决纤芯不够，不解决距离超限：它几乎不增加时延，所以也几乎不减少时延。

某新建城区的 18 站 C-RAN hub，勘察阶段两个问题同时爆出来：出局光缆只有 48 芯而需求 108 芯；最远的 3 个站 OTDR 实测 15.8 / 16.4 / 18.1 km（图上才 9~11 km，绕行系数约 1.7），传播时延已 77~89 µs。

两个手段各解一题：纤芯缺口用站点侧 8 波无源 CWDM 压到 36 芯；超距站里，15.8 km 那个去掉汇聚交换那一跳、直连 hub 省下约 12 µs 压回预算，剩下两个怎么算都不够，改为保留本地 DU、只集中 CU——退化成只有中传，ms 级预算下 18 km 毫无压力。

三点教训：① 纤芯普查与距离实测必须在立项前做；② 绕行系数按 1.5~2 倍估，图上距离没有参考价值；③ 一张网里允许有两种形态——为三个站推翻整个 hub 方案才是真不划算。

C-RAN 到底给承载网压了多少

D-RAN 侧这笔账接近零：DU 就在塔下，前传是站内 100 m。换成 20 站汇聚一个 hub，1.5 Tbps（20 × 3 × 25 Gbps）全压在进局段，暗纤要 120 芯、上 8 波无源 CWDM 后 40 芯；而 hub 出去的中传只有约 100 Gbps，还能再统计复用。

所以 C-RAN 的本质是把"分散的无线设备成本"换成"集中的光纤与机房成本"：自有管道、新建城区划算，老城区与租纤不划算。推论有点反直觉——既然这笔账逐区不同，"全网统一做 C-RAN"和"全网统一做 D-RAN"就都是错的答案，而混合本身的运维复杂度也是一项成本。

面试题（12 道）

分层自测

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础前传、中传、回传分别连接谁、走什么接口、搬什么数据？

    三段对应关系是固定的：

    • 前传（Fronthaul）：DU ↔ RU，接口是 Open Fronthaul（Option 7-2x），搬频域 IQ 采样加波束权值与调度控制信息。
    • 中传（Midhaul）：CU ↔ DU，接口是 F1（Option 2 拆分），分 F1-C（F1AP over SCTP 38472）与 F1-U（GTP-U over UDP 2152），搬 PDCP PDU。
    • 回传（Backhaul）：CU ↔ 5GC，接口是 NG，分 NG-C（NGAP over SCTP 38412，对 AMF）与 NG-U（GTP-U over UDP 2152，对 UPF），搬用户 IP 包与核心网信令。

    加分的补充：注意 3GPP 的接口设计有高度一致的模式——控制面一律 XxAP over SCTP（NGAP/38412、XnAP/38422、F1AP/38472、E1AP/38462），用户面一律 GTP-U over UDP 2152。记住这个模式比背端口号有用。

    还要点出：逻辑上是三段，物理上未必。D-RAN 站点 CU/DU 一体，中传退化成机内背板；室分一体化小站三个功能全在一个盒子里，前传中传都不存在。

  2. 基础为什么前传的要求比另外两段严得多？

    一句话根因：前传处在无线物理层的硬实时闭环之内，另外两段不在。

    展开成因果链：拆分点越靠近射频 → 传的越是未经加工的物理层实时数据 → ① 数据量大（IQ 采样正比于带宽 × 天线数，与有没有用户无关）；② 时间敏感（每个 OFDM 符号必须在确定时刻从天线发出）；③ 必须相位同步（TDD 收发切换要全网对齐）。

    具体到数字：单向时延预算约 100 µs（TR 38.801 对 Option 7 类拆分给出的量级），抖动窗口 µs 级，同步要求 ns 级，丢包容忍 10⁻⁷ 量级。对比之下中传是 ms 级软约束、回传是几 ms 到几十 ms 且只影响体验。

    最能体现理解深度的一点：HARQ、调度、功控这些微秒到毫秒级的闭环全部在 DU 与 RU 之间闭合，回传根本不在环内。所以回传断了业务会停，但物理层不会"乱掉"；前传抖动几微秒，物理层直接出错。

  3. 基础中传和回传的带宽差多少？为什么？

    单站看，两者是同一个量级——它们搬的是同一批用户数据，只是中传搬的是 PDCP PDU、回传搬的是 PDCP 处理完之后的用户 IP 包，封装开销略有差别（都在 5% 上下）。

    真正的差别在两处：

    • 汇聚层级不同：一个 CU 下面挂 N 个 DU，所以 CU 出去的那条回传链路承载 N 个站的流量，是全网最粗的单链路。说"回传带宽最大"指的是这个，不是单站对比。
    • 统计复用能力不同：回传汇聚的用户越多，峰均比越低，统计复用增益越显著（工程上常见 3~5 倍）。中传只能在同站的几个扇区间复用，增益有限。

    给个参照数：100 MHz/64T64R 三扇区站，中传峰值约 5 Gbps（1.6 Gbps × 3 × 1.06 封装开销）；20 个这样的站汇聚后，回传按峰值堆是 96 Gbps，但按忙时话统算通常 12 Gbps 就够——这个差距正是统计复用。

  4. 基础光纤里的传播时延是多少？这个常数怎么限制前传距离？

    约 5 µs/km（单向），10 µs/km（往返）。

    推导两步：单模光纤群折射率 n ≈ 1.468，光速 v = c/n = 299792458 / 1.468 ≈ 2.04×10⁸ m/s；1 km ÷ 2.04×10⁸ m/s ≈ 4.9 µs，工程上取整成 5。

    它怎么限制前传：前传单向预算约 100 µs，100 ÷ 5 = 20 km —— 这就是常被引用的前传距离理论上限。但这个 20 km 是"传播时延吃光整条预算"的极限值，实际还要扣掉光模块收发、每跳交换机转发（5~30 µs）、以及两端设备处理，所以多数运营商的规划半径在 10 km 以内。

    最容易被忽略的一点：要用实际纤长，不是地图直线距离。光纤沿管道走、绕障碍、每个接头盒留余长，实际长度通常是直线距离的 1.3~2 倍。一个"图上 9 km"的站点实测 16 km 是很常见的事，而这直接决定方案成不成立。所以规划一律以 OTDR 实测为准。

9.2 中级（区分熟练度）

  1. 中级端到端时延预算怎么逐段分配？哪一段是硬约束？

    以 3GPP TS 22.261 给的用户面目标（eMBB 4 ms、URLLC 0.5 ms，单向）为总盘子，逐段扣：

    环节典型单向耗时性质
    空口 Uu（含调度等待与 HARQ 重传）0.5~2 ms占大头，不可压缩
    RU 处理数十 µs设备实现
    前传≤100 µs硬 deadline
    DU 处理数百 µs设备实现
    中传0.1~2 ms软约束
    CU 处理数十~数百 µs设备实现
    回传1~10 ms软约束，最大的一块可优化空间
    UPF 转发数十~数百 µs软约束

    关键洞察：前传的绝对数值最小，却是唯一超了就直接失效的一段。其他各段超预算只是"慢一点"，前传超预算是包落在 RU 接收窗之外被直接丢弃，那批 PRB 的 IQ 缺失、符号出错。这类约束是 hard deadline，不能和其他 soft budget 放在一起做加减法互相借用。

    如果面试官接着问"URLLC 1 ms 怎么保证"，正确的两个杠杆是：① UPF 下沉到边缘（砍掉回传那几毫秒，收益最大）；② 免调度 / 预调度（砍掉调度请求往返）。优化前传和 DU 处理只有几十微秒空间，性价比最低。

  2. 中级WDM 在承载网里解决什么问题？它能缩短前传距离吗？

    WDM 解决的是纤芯不够，不是距离超限。这是最常见的误解，值得先把结论摆出来。

    它的作用是把多路信号用不同波长复用到同一对光纤上。典型收益：一个 20 站的 C-RAN hub，暗纤方案需要 20 × 3 扇区 × 2 = 120 芯；用 8 波无源 CWDM，站点侧一个合分波器把 3 个扇区加备用波长复用到 1 对纤，需求压到 40 芯。在市区纤芯紧张、租纤按芯 × 公里计费的场景，这直接决定方案成不成立。

    两个标准要分清：CWDM（ITU-T G.694.2）18 个波、20 nm 间隔、覆盖 1271~1611 nm，器件便宜、无需温控；DWDM（ITU-T G.694.1）C 波段 50/100 GHz 间隔，波数多得多，但彩光模块贵、需要波长规划。

    为什么它不缩短距离：无源 WDM 只是合分波，光走的还是那根纤、那段距离，几乎不增加也不减少传播时延。时延由物理距离决定，换承载技术改变不了距离。

    加分点：CWDM 在前传上有个坑——如果用单纤双向配不同波长，色散会导致两个方向群时延不等，引入 ns 级的 PTP 不对称误差。CWDM 波长间隔大（20 nm），这个问题比 DWDM 严重。

  3. 中级有源和无源承载方案怎么取舍？

    判据是"你更缺什么"，三者不可兼得：

    • 缺纤芯 → 无源 WDM。用波长换纤芯，器件不耗电、不占机房、成本最低。
    • 缺运维手段 → 有源（OTN / SPN / PTN）。无源方案最大的问题是没有任何监控：某个波长坏了不会告警，只能派人扛着 OTDR 到现场逐波测。一个大网上百个站这样搞是运维灾难。有源设备有完善的告警、环回、性能计数、保护倒换。
    • 缺时延预算 → 暗纤或无源。有源设备每跳 5~20 µs（OTN 还要算 FEC 编解码），级联两三跳就吃掉小半条前传预算。

    还要加一条同步：有源设备必须逐跳实现 T-BC 才能透传 PTP，纯电层映射会打断同步链。无源器件对 PTP 天然透明。SPN/MTN 是个例外——它基于 66B 码块交叉、不解析包，时延确定且设计上就考虑了高精度时间传送。

    现网的真实答案是混合：密集城区纤芯紧张用无源 WDM，郊区长距用有源，站内短距直接暗纤。统一用一种方案的网络基本不存在。

  4. 中级GTP-U 在回传上起什么作用？它给传输网带来什么麻烦？

    作用：GTP-U（TS 29.281）是用户面的隧道封装，把用户的 IP 包装进一个外层 IP/UDP/GTP-U 里，靠 32 位的 TEID 区分是哪个 UE 的哪条 QoS 流。这样一来：① 用户的私网 IP 与传输网路由完全解耦，UE 移动时外层地址变而内层不变；② 移动性管理只需改隧道端点，不用动用户 IP。5G 里还会用 GTP-U 扩展头（PDU Session Container）携带 QFI。

    最小头 8 字节：Flags(1) + Message Type(1) + Length(2) + TEID(4)。典型 30 ff xx xx | TEID，其中 0x30 表示 GTPv1、无扩展头/序列号，0xFF 是 G-PDU（承载用户数据）。

    给传输网的两个麻烦：

    • 吃 MTU：外层 IPv4+UDP+GTP-U = 36 字节，IPv6 是 56，再叠 VLAN 和可能的 IPsec。1500 的传输 MTU 会把用户内层压到 1400 上下，否则分片或 PMTUD 黑洞。所以回传网普遍配 jumbo frame。
    • 破坏负载分担：所有 UE 的流量共用同一组外层五元组，传统 ECMP 哈希会把整条隧道压在一条路径上。需要设备支持基于 TEID 或内层头的哈希（"GTP-aware load balancing"）。

    排障加分点：TEID 是接收方各自分配的，上下行两个方向的 TEID 完全无关。查"上行通下行不通"时，别去核对两边是不是同一个 TEID 值。

9.3 高级（体现深度）

  1. 高级为什么说"时间同步能不能透传"是承载选型的决定因素？

    因为选型表里其他所有列（时延、带宽、成本、运维）都是连续量——差一点可以用钱或妥协换回来；只有同步透传是离散的 0/1：透不过去，这条链路就不能承载 TDD 前传，其他指标再漂亮都没用。所以它是第一道筛子，不是最后一道。

    约束从哪来：TDD 系统里相邻基站必须在同一时刻从收切到发，否则一个站的下行功率会直接砸进邻站的上行接收——不是性能下降，是整片区域上行瘫痪。TS 38.133 要求小区间相位同步优于 3 µs，对应 ITU-T G.8271.1 的端到端 |TE| ≤ 1.5 µs。

    1.5 µs 要在整条链上分摊，于是每跳只剩几十纳秒：PRTC 本身约 100 ns，每台 T-BC 按 G.8273.2 分 Class A ≤50 ns / Class B ≤20 ns / Class C ≤10 ns（前传通常要求 Class C），RU 自身还要占几十到几百 ns。预算这么紧的直接后果是：链路上多一台不支持 T-BC 的设备，整条预算立刻崩。

    破坏方式只有三种：① 排队时延波动（PTP 报文和业务同队列，时间戳被排队污染，误差 µs 到数百 µs，直接爆表）；② 设备恒定误差 cTE（每跳 10~50 ns 累积）；③ 链路不对称（往返时延不等，PTP 把差值的一半当成时钟偏差）。

    最后一项最值得讲，因为它完全无法被 PTP 自己发现——协议的数学模型假设了对称，不对称就变成一个看不见的常数偏移：所有告警都是绿的，ptp4l 也显示锁定（s2），只有空口的邻区干扰在悄悄变差。这是唯一不报警的失效模式，也是为什么租波长做前传很危险——你无从测量出租方链路的不对称量。

  2. 高级链路不对称是怎么产生的？前传上具体有哪些来源，各是什么量级？

    PTP 用 t1~t4 四个时间戳算时钟偏差，公式里隐含假设"去程时延 = 回程时延"。真实链路不满足时，误差 = 不对称量 / 2，且这个误差是常数偏移，不随时间收敛。

    前传上的三个主要来源：

    • 单纤双向（BiDi）用不同波长。典型配对 1310 nm 发 / 1550 nm 收。单模光纤的群折射率随波长变化（色散），两个方向传播速度不同，群时延差在 1~2 ns/km 量级（具体值取决于光纤色散参数与实际波长，需查光纤规格）。10 km 链路就是 10~20 ns 的往返差、5~10 ns 的相位误差——这一项就吃掉 G.8273.2 Class C 的整条预算。对策是前传优先用双纤单向 + 同波长，两根纤长度尽量一致；只有一根纤时用同波长双向方案，或在设备上配置不对称补偿值。
    • 保护倒换后走了不同长度的路径。主用 8 km、备用 14 km，倒换瞬间链路时延突变 6 × 4.9 ≈ 29 µs，相位跳变约 14.7 µs，远超 1.5 µs 网络限值。现象是倒换后该片区上行底噪抬升、邻区干扰告警，等 PTP 重新收敛（可能几分钟）才恢复。对策是把主备路径长度差纳入规划约束（常见要求差值 < 1~2 km），或让 PTP 在倒换时进入保持态而不是立刻跟踪新路径。
    • 设备内部收发通道时延不等。光模块、PHY、时间戳打点位置的差异，这部分体现在设备的 cTE 指标里，靠选高等级 T-BC 控制。

    怎么发现：看 ptp4l 的输出，如果 path delay 非常稳定但 master offset 存在恒定偏移，这是不对称的典型特征——而它本身不会报任何错。别看到状态 s2 就以为万事大吉，s2 只说明"跟上了主时钟"，不说明"跟上的那个时刻是对的"。

  3. 高级为什么统计复用在回传可行、在前传不可行？

    统计复用要成立需要两个前提：① 各路流量是突发的（峰均比高）；② 各路峰值不同时到来（相互独立）；此外还隐含 ③ 偶尔的排队/丢包可以被上层吸收。

    回传三条全满足：用户流量天然突发（刷完一段视频就停），不同用户之间独立，且端到端有 TCP/QUIC 兜底。汇聚的用户越多，总流量越平滑，工程上常见 3~5 倍复用增益。所以回传按"忙时均值 × 过载系数"规划，而不是按峰值堆——两者能差 3~5 倍。

    前传三条全不满足：

    • 速率是配置驱动、近似恒定的。CPRI 完全恒定，与用户数、调度、MIMO 层数都无关，只取决于天线数与采样率；7-2x 会随占用的 PRB 有所变化，但规划仍必须按峰值——因为小区随时可能被打满。峰均比接近 1，没有可复用的空间。
    • 同一 DU 下各小区的忙时高度相关（同一片区域的话务潮汐同步），不满足独立性。
    • 丢包不可吸收。IQ 包没有重传机制，丢一个包就是一批 PRB 的采样缺失，直接表现为符号出错、底噪抬升。丢包容忍在 10⁻⁷ 量级。

    所以前传必须按峰值刚性预留带宽，也不能和其他业务混跑抢队列。这也解释了为什么前传是三段里单位比特成本最高的一段——它没法用统计复用摊薄。

  4. 高级要新建一个覆盖 20 个站的区域，你怎么规划这三段承载？

    这是综合题，考的是顺序而不是知识点。上来就画星型拓扑会被认为没做过工程——正确的开场是先问约束。

    第一步：摸清资源，不做任何设计。

    • 纤芯普查：这一片有哪些管道、每条多少芯、已用多少、是自有还是租的、租期多久。
    • 机房勘察：候选机房的位置、电力容量、制冷、承重、空间、产权租期、出局纤芯数。纤芯普查和机房勘察必须同步做——找到完美几何中心却发现那栋楼只有 12 芯且用满，方案就作废了。
    • 历史存量：有没有要保留的 D-RAN 站、既有 BBU 机房能否复用。

    第二步：定 DU 位置。现实中 DU 位置是被"选出来"而不是"规划出来"的——同时满足位置、光纤、电力、空调、承重、空间、产权、安全八项的候选点，一个区里可能只有两三个。选定后，对每一个 RU 站点做 OTDR 实测纤长，绝不用地图直线距离（管道绕行系数按 1.5~2 倍估）。

    第三步：核算前传预算，逐站判定。实测纤长 × 4.9 µs/km + 光模块 + 每跳交换（5~30 µs）≤ 100 µs。超限的站单独拎出来。

    第四步：算纤芯需求，决定要不要 WDM。暗纤方案 20 站 × 3 扇区 × 2 = 120 芯；出局只有 48 芯就上无源 CWDM，站点侧一个 8 波合分波器把 3 扇区 + 备用复用到 1 对纤，压到 40 芯。记住 WDM 解决纤芯不解决距离。

    第五步：处理超距站，按代价从小到大出牌。① 减少中间跳数（改直连，每跳省 5~30 µs）；② 换更短的光纤路由；③ 把 DU 挪近或退回 D-RAN；④ 该站调整拆分点——保留本地 DU、只集中 CU，前传消失、只剩 ms 级预算的中传，18 km 也毫无压力。为了两三个站推翻整个 hub 方案才是真的不划算，一张网里允许有两种形态。

    第六步：同步方案。确认整条前传链路逐跳能透传 PTP（有源设备必须是 T-BC，前传通常要 G.8273.2 Class C）；主备路径长度差纳入约束；避免单纤双向异波长。

    第七步：中传与回传。中传按峰值算（20 站 × 5 Gbps，可与回传共用 IP-RAN），注意把同一 DU 的 F1-C 与 F1-U 绑到同一条转发路径，避免 ECMP 把信令与数据散到时延差几毫秒的两条路上导致切换丢包。回传按忙时话统（不是峰值堆叠）算，取"Σ 忙时均值 × 过载系数"与"单站峰值 × 并发系数"的较大者。

    最后交付的不是一张拓扑图，是一张逐站的核算表：站名、实测纤长、传播时延、跳数、总时延、余量、纤芯占用、承载方式、同步配置。有余量为负的行，就有对应的处置方案。
