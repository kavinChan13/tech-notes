一个完整通信系统案例：从管理到数据传输

这是整个主题的总复习。我们用一个 5G O-RAN 基站的开站与运行过程，把前面所有知识——NETCONF/YANG、O-RAN、Fronthaul、eCPRI、PTP/SyncE、TLS、协议栈——串成一条完整的因果链，回答"一个现代通信系统到底是怎么组成、怎么跑起来的"。

全景系统图

一张图看懂整条链

这一篇是整个主题的总复习，刻意不引入新知识：每个概念都在专篇里讲透了，本篇只把它们按一台真实基站从上电到承载业务的顺序串起来，让你看清每个知识点在链路上的位置。

怎么用这一篇。具体机制与数值一律链到专篇而不重述——同一个数字写两遍，迟早会写出两个版本。先在这里建立顺序感，卡住了点进专篇补完，再回来接着走。
生活类比 · 一家新开的连锁餐厅
总部（SMO）先发工牌与门禁卡（证书），店长才有资格接总部电话（O1 安全连接）；然后下发菜单（配置）、核对菜单版本（软件协商）。开门营业之前必须先对表——这家店和邻店共用一条街，谁在哪个时段占哪一段人行道是排好班的（TDD 时隙），表对不上就撞车（PTP / SyncE）。之后后厨（O-DU）与前台（O-RU）靠传菜口不停搬运（eCPRI 送 IQ），传菜口有一个硬窗口：早了台面放不下，晚了菜就凉。
要点是顺序不能颠倒。本篇每一章都在回答「为什么这一步必须在那一步之后」。

一张图：网元、接口、四条线索

四条线索：管理面（O1 上的 NETCONF/YANG）、控制面（RRC / F1AP / NGAP，以及前传上的 C 面调度信息）、用户面（IQ 与用户数据，eCPRI / GTP-U）、同步面（PTP / SyncE）。本篇的核心论点：它们的就绪顺序被物理约束钉死了——管理面必须先于同步面，同步面必须先于用户面。

这个网元跑在什么硬件上、失效了影响多大

架构图告诉你「谁连谁」，工程上更要紧的是「落在哪层硬件上、坏了多严重」——这两件事其实是同一件：

网元失效后果爆炸半径
O-RU该扇区立刻退服1 个扇区
O-DU（见 电信云原生）下挂的所有小区退服1 个站 ~ 若干站
O-CU新接入全失败，已有连接随 RRC 定时器瓦解几十 ~ 几百个 DU
AMF / SMF（见 核心网演进）不能注册、不能建会话；已建会话不受影响整个注册区
UPF其上所有 PDU 会话的数据面中断整个 UPF 服务域
Near-RT RIC回退内置算法，不应导致退服优化范围内的小区
SMO / Non-RT RIC看不见、改不了、部署不了全网可观测性
时间源（GNSS + PRTC）下游进 holdover，撑不住之后 TDD 小区必须关整条同步链下游
面试加分：被问「最脆弱的一环是哪个」，答 O-DU 或 O-CU 只是中规中矩。有分量的回答是「时间源」：它的失效同时具备渐进、静默、异地三个特征（失锁瞬间一切正常，几十分钟后邻区底噪才抬升），而其他网元失效都是「立刻、可见、就地」的。能指出这三个特征，比背哪个网元更重要有说服力。

四条线索的时间尺度：为什么不能共用一套 SLA

把五种流量摊在同一根对数轴上，整条链的工程画风就清楚了：

平面典型承载断了 30 秒会怎样本篇对应章节
管理面 MO1 与前传 M 面：NETCONF/YANG over TLS/SSH看不到告警、改不了配置；已运行的小区照跑s2
同步面 SPTP（IEEE 1588 / G.8275.1）+ SyncE进 holdover。看起来一切正常，实际相位在漂s3
用户面 U前传 eCPRI Type 0；中传 / 回传 GTP-U小区立刻退服 / 数据面中断s4
控制面 C前传 eCPRI Type 2；上层 RRC / F1AP / NGAP前传 C 面断即退服；上层信令断则新接入失败s5
智能控制回路E2（RIC ↔ CU/DU）、A1（Non-RT → Near-RT）回退内置算法；业务无恙O-RAN 架构篇
这四个平面就是 O-RAN 前传上的 CUS-M；它们如何按时间配对见 O-RAN 中的 User / Control / Management Plane，本篇只用「就绪顺序」这一个结论。
02

管理面：开站配置

一切从配置开始

新基站上电，第一件事不是发数据，而是被配置。这背后是一条顺序不能乱的依赖链：跳过任何一步，后面那步不是「效果差一点」，而是根本执行不下去。

完整顺序：从上电到能承载业务

Call Home（RFC 8071）：TCP 连接方向反过来由设备主动发起，但协议角色不变——设备仍是 SSH/TLS 与 NETCONF 服务端。它一次解决三件事：可达性（O-RU 常在 NAT 后、IP 动态）、发现（网管不必维护清单）、时序（设备何时 ready 只有它自己知道）。见 NETCONF 工程实践。

配置为什么走 NETCONF/YANG，而不是私有协议

因为 O1 与前传 M 面要解决「多厂商、大规模、可自动化」的配置问题，而这正是 NETCONF/YANG 被设计出来解决的问题。三个特性缺一不可：

① 模型即契约

YANG 把可配项、类型与约束写成机器可读的模型，于是「两端 revision 是否一致」变成开站前能用工具比对的事，而不是等现场报错。

② 事务语义

candidate 里改、校验通过再 commit，配错了整批回退。开站要下几百个节点，「一半生效一半没生效」是最糟的状态。见 NETCONF / YANG。

③ 传输与授权解耦

认证结果统一经 cert-to-name 收敛成用户名，再套同一份 NACM——授权只写一遍。

SSH 还是 TLS 是真实取舍：SSH 运维简单，但主机指纹要逐台维护，规模化成本 O(N)；mTLS 靠一个 CA 背书全网，代价是先得有 PKI。前传 M 面偏向 TLS 的直接动机是 O-RU 的物理安全性远低于机房设备——被拆走一台，SSH 公钥模型下没有标准手段让全网「忘掉」那把钥匙。见 TLS / SSH / Certificate。

O-RU 由谁管：一个必须在设计阶段拍板的选择

开站流程里有个岔路口经常被跳过：O-RU 的管理面连到谁？两种模型的代价不在技术上，而在多厂商协作上：

层级模型（Hierarchical）混合模型（Hybrid）
谁直连 O-RU 的 NETCONF只有 O-DU；SMO 的操作经 O-DU 中转SMO 与 O-DU 都有连接
换 O-DU 厂商的影响O-RU 的纳管跟着一起换不影响
软件升级、证书轮换要 O-DU 厂商实现代理SMO 可直接做
主要风险O-DU 厂商成为必经之路争 candidate，谁后提交谁生效
判据只有一条：你打算不打算换 O-DU 厂商。上混合模型就必须在设计文档里逐个 YANG 模块写清由谁写（典型划法：C/U 面归 O-DU，设备级的软件、证书、日志、硬件清单归 SMO），并用 NACM 把这条线固化到设备上。
真实场景 · 「配置下发成功，小区就是起不来」
开站阶段频率最高的一类现象，排查顺序是固定的：① commit 是真成功了，还是只写进了 candidate；② 比对两端的 YANG revision 与 capability——节点名对但语义变了不会报错，只会不生效；③ 看同步状态；④ 最后才怀疑前传参数。这个顺序按「命中率 × 排查成本」排：前两步敲两条命令就能确认，后两步要上现场或抓包。
03

同步面：先对表

数据传输的前提

配置下完之后，开站流程会停在一个「等」上：等时钟锁定。这是整条链上唯一不由软件推进、只能等物理过程收敛的环节，也最容易被现场以「先开起来看看」的心态跳过。

三种同步，递进关系：频率同步（每秒的长度一样，靠 SyncE 在物理层传递）→ 相位同步（每一秒的起点对齐）→ 时间同步（还知道「现在几点」，可溯源 UTC）。关键算术：频率误差在时间上积分就是相位误差——它同时解释了「SyncE 为什么能帮 PTP」和「holdover 能撑多久」。见 PTP / SyncE。

为什么必须在开小区之前

原因不是「不同步数据会错」，而是 TDD 把时间本身当成了资源：同一频点靠时间分割上下行，这个划分只有在所有站点共用同一时间基准时才成立。相位一偏，下图里的事情就会发生。

排障推论：看到一片区域的上行指标同时劣化，不要只查这些站——要去查它们共同的同步上游，以及邻区里有没有 clockClass 已经变了的。

时钟没锁定时，设备处于什么状态

时钟不是「锁定 / 没锁定」两态，而是一个四状态的小状态机：

状态能开小区吗怎么看出来
FREERUN不能伺服状态未收敛；clockClass 处于未溯源的降级档
ACQUIRING不能ptp4l 从 LISTENING → UNCALIBRATED；servo 处于收敛档
LOCKED✅ 可以状态停在 SLAVE、servo 已锁定；clockClass 表示「已溯源 PRTC」
HOLDOVER⚠️ 暂时可以，有时限clockClass 跳到「holdover 仍在规格内」那一档——这是唯一的信号
PTP / SyncE 里有个案例：底噪抬升比 clockClass 变化滞后了约 40 分钟——那正是白送给你的修复窗口，前提是你对 clockClass 建了告警。

「多久之后必须关小区」：这是工程决策，不是标准条款

标准只告诉你相位误差的上限，「超了怎么办」是运营商的运维策略。两个选项都会伤人：

选择代价影响范围什么时候合理
继续开着一旦漂出预算就开始干扰邻区，把单站故障扩散成一片本站 + 所有邻区余量还足，且已确认上游会在余量内恢复（如计划割接）
主动关小区本站用户立刻掉线，靠邻区覆盖兜住仅本站余量即将耗尽，或上游恢复时间未知

所以要提前做成一条自动策略，而不是等出事时人工判断，三个要点：

  • 阈值设在「余量的某个比例」而不是「超标时」——超标那一刻已经在伤邻区了。
  • 分级动作：进 holdover 立刻告警 → 余量过半时禁止新接入 / 降功率 → 余量将尽时关闭 TDD 小区。FDD 对相位不敏感，可以留着。
  • 恢复也要有策略：伺服重新收敛期间相位还在动，要等稳定一段时间再解除限制，否则会「关了又开」地振荡。
面试加分：分水岭是能不能说出「关小区是为了保护邻区，不是为了保护本站」——类比一辆刹车失灵的车主动靠边停，不是为了车上的人，是为了路上的其他车。再补一句「只关 TDD、FDD 留着」，就说明你分得清相位同步约束的是什么。
真实场景 · 一次「GNSS 被遮挡」的连锁反应
某汇聚站的 GNSS 天线被新建楼宇遮挡，缓慢失锁。设备正确地进入 holdover 并改了 clockClass，但监控只对「同步告警」建了规则，于是没人知道。下游十几个站跟着一起漂，而它们的本地伺服全都显示「已锁定」——因为确实锁在了上游那个正在漂的时钟上。教训是：「本地已锁定」只说明这一跳的伺服收敛了，不代表溯源到了可信时间源。判读方法见 PTP / SyncE。
04

数据面：IQ 传输

真正的无线数据流

时钟锁定、小区激活之后，前传链路上就开始跑一条永不停歇的等时流。本章跟着一个下行时隙走完 O-DU 到天线口这一段，重点是：为什么这里是整条链上唯一「超时就丢、不许重传」的地方。

先把三个词的层次分清：Open Fronthaul 是 O-RAN 定义的接口与规范（Option 7-2x、四个平面、收发窗参数）；eCPRI 是它 C/U 面上的报文格式；以太网是承载。即 O-RAN ⊃ Open Fronthaul ⊃ eCPRI/Ethernet。注意 S 面走 PTP/SyncE、M 面走 NETCONF，都不是 eCPRI 消息。

前传单向预算通常按 100 µs 量级规划：它来自 3GPP 对 Option 7 一类拆分给出的单向时延量级指标，O-RAN WG4 把它落成了更具体的收发窗口参数，具体取值以所用版本的规范为准。预算怎么花，决定了 O-DU 能放多远：

光纤传播不能只能缩短距离，或改用 Option 2 把 DU 放回站点按图纸距离规划，实测纤长多出 30~70%
交换机转发能减少跳数；暗纤直连；开严格优先级队列汇聚层多挂几个站，排队时延吃掉余量
排队 抖动能，但最难带宽留大余量、U/C 面与 M 面分队列、PCP 强制 remark抖动比时延更致命——时延大可整体挪窗补偿，抖动不能
串行化能用巨帧降低开销与 pps巨帧阻塞后面的高优先级报文，要进 C/S 面预算
设备处理看厂商选型时就要问换一版 RU 固件，贴着上限的站开始丢包
前传最反直觉的一点：平均时延更低的链路可能完全不能用。「平均转发 8 µs、拥塞时排队到 200 µs」的通用交换机，比「固定 60 µs 的裸光纤」糟糕得多——超窗的报文直接被丢弃，不是「慢一点到」。确定性 > 低时延，这条原则贯穿整个前传工程。详见 前传、中传、后传。

带宽：为什么前传比用户吞吐大两个数量级

因为前传跑的不是用户数据，是基带 IQ 采样——量级由采样率、流数、量化位宽决定，和「有多少用户」关系不大。算式见 前传技术演进 与 eCPRI 深入，这里只给两个决定量级的开关：

开关Category ACategory B
预编码 / 波束加权做在哪O-DUO-RU
下行前传流数（eAxC 数）= 物理天线数= 层数
大规模 MIMO 下的带宽随天线数线性膨胀，很快撑不住只随层数增长，省得非常明显
O-RU 复杂度 / 成本低高（要有矩阵运算能力）

一个容易漏掉的不对称：上行通常没有这个自由度——O-RU 一般把每根接收天线的采样都送上去让 O-DU 做合并，所以上行 eAxC 数约等于接收天线数。于是 Category B 下上行的前传带宽反而比下行大得多，规划容量要按上行算。
真实场景 · 「已接入的用户全都正常，新用户就是接不进来」
根因是PRACH 的 eAxC 漏配：PRACH 占用独立的 RU_Port_ID 取值，采样率与带宽也和业务信道不同，配置项是分开的。漏配之后已连接用户 KPI 全绿，只有新用户进不来；指标上是「随机接入成功率」跳水，而 RRC、核心网、传输侧全都看不出问题。
它示范了一个通用判据：「老用户正常、新用户失败」一定指向只有接入流程才用到的资源；反过来「所有用户一起劣化」才指向带宽、时钟、光功率这类共享资源。

一次完整的通话

端到端串起来

前面三章把基站自己准备好了。这一章换视角：一个用户按下开机键，到他的数据包真正流出去，中间发生了什么。

主线是五个递进的问题：「这里有基站吗」（小区搜索）→「让我说句话」（随机接入）→「给我一条信令通道」（RRC 建立）→「我是谁」（注册与鉴权）→「给我一条通往数据网的管子」（PDU 会话）。答案分别由小区级广播、O-DU 的 MAC、O-CU-CP 的 RRC、核心网的 AMF/SMF 给出——记住「哪一步该找谁」，排障时就不会从头查到尾。

时序图：从开机到能上网

逐步拆解：每一步涉及谁、走哪个接口、大致多久

时间列一律只给量级：它们受 numerology、TDD 配比、核心网位置、UE 实现影响极大，同一套流程在不同网络里差几倍是正常的。正确的看法是比较相邻两行的比例关系，而不是当指标用。

步骤涉及网元接口 / 协议耗时量级解决什么问题
1 · 小区搜索与同步UE（单方面接收）Uu：SSB（PSS/SSS/PBCH）+ SIB1几十毫秒 ~ 数秒「这里有基站吗、在哪个频点」
2 · 随机接入UE ↔ O-RU ↔ O-DU 的 MAC空口 + 前传（PRACH 有独立 eAxC）毫秒 ~ 数十毫秒上行同步（TA）+ 临时标识 + 上行授权
3 · RRC 连接建立UE ↔ O-DU ↔ O-CU-CP空口 + F1-C（F1AP over SCTP）十毫秒量级建 SRB1，UE 进 RRC_CONNECTED
4 · 注册与鉴权UE ↔ O-CU-CP ↔ AMF ↔ AUSF / UDMN1（NAS，端到端）在 N2 里透传百毫秒量级双向鉴权、安全上下文、分配 5G-GUTI
5 · PDU 会话建立UE ↔ AMF ↔ SMF ↔ UPF；同时 CP ↔ UP ↔ DUN1 / N2 / N4（PFCP） / E1 / F1-C百毫秒量级拼出 DRB + F1-U + N3 三段隧道
6 · 数据收发全链路Uu → eCPRI → F1-U → N3 → N6见 承载篇真正干活

四个最容易答糊的点

① 随机接入到底解决什么

不是「建立连接」，而是上行同步 + 多用户竞争。UE 收 SSB 只完成了下行同步，它不知道自己离基站多远，Msg2 里的定时提前（TA）就是在告诉它该提前多久发。而 PRACH 是共享资源，所以要有 Msg3/Msg4 的竞争解决。

② 为什么 O-DU 看不懂 RRC

Option 2 把 RRC 与 PDCP 放在 O-CU，所以 RRC 消息在 F1 上是以容器（八位字节串）透传的。抓 F1 的包能看到 F1AP 结构，但 O-DU 自己不需要解析 RRC 的能力。反过来，O-DU 要产生 MAC/RLC/物理层的配置片段交给 O-CU 拼装。

③ 注册 ≠ 能上网

注册解决身份，会话解决通路。4G 的 attach 顺带建默认承载，所以感觉是一步；5G 明确分开，UE 可以只注册不建会话。现场意义：看到「已注册但上不了网」，去查 PDU 会话与 UPF。

④ NAS 是端到端的

NAS 消息在 UE 与 AMF 之间端到端跑（N1），基站只在 N2 上做容器搬运，它甚至没有解密的密钥，所以「鉴权失败」抓基站的包基本没用。这个分层是刻意的——它让基站不必被信任就能承载信令。

面试加分：把七步背出来是及格线，加分点是指出三个「不对称」：① 下行同步是单方面收广播、上行同步必须靠 Msg2 给的 TA，所以随机接入不可省；② 注册归 AMF、会话归 SMF，失败现象完全不同；③ 三段隧道的端点都是「两端各自分配、再互相告知」，所以流程里必然出现「先建、再改」，日志里看到这个不是重试。
真实场景 · 「按平面分段」怎么救回一个通宵
接入失败类问题最怕「从 UE 一路查到 UPF」——链上七个网元、五个接口，逐个看要一整晚。有效做法是先用现象把范围切成一段：各分支指向哪里见 s7-2 的反向索引表。关键在于每个分支的判定都只用「现象」，不需要抓包、不需要上现场。

两个报文的一生

逐跳追踪，看清每一层加了什么

前面五章是「按流程」串的，这一章换成协议栈视角：挑两个报文逐跳跟一遍，每跳标出加了什么、减了什么。两个刻意来自不同平面——控制面的 RRCSetup 与用户面的下行数据包。它们穿过几乎完全不同的协议栈，这正是「平面要分离」最好的例证。

报文一 · 控制面：一条 RRCSetup 从 O-CU-CP 到 UE

# 场景：UE 的 Msg3（RRCSetupRequest）已经到了 O-CU-CP，
#       CP 决定接纳它，于是生成一条 RRCSetup 往回送。

跳 1 · O-CU-CP · RRC 层
  产生 RRCSetup 消息，用 ASN.1 编成一串八位字节。
  ⚠ RRCSetup 走 SRB0（CCCH）：此时安全上下文还没建立，
    所以这条消息既不加密也不做完整性保护 —— 它是整条链上少数明文的信令之一。
  ＋ 加：RRC 消息本身

跳 2 · O-CU-CP · F1AP 封装
  塞进 F1AP 的 DL RRC Message Transfer，作为一个 RRC-Container（八位字节串）。
  同时带上两个 UE 标识（CU 侧分配的 + DU 侧分配的），DU 才知道这是哪个上下文。
  ＋ 加：F1AP 消息头与 IE（ASN.1 PER 编码）

跳 3 · 中传传输层
  ＋ 加：SCTP（端口 38472）→ IP → 以太网
  # 选 SCTP 而不是 TCP 的理由（多流避免队头阻塞、多归属、消息边界）见 oran_interfaces.html

跳 4 · O-DU · 剥到容器就停手
  − 减：以太网 / IP / SCTP / F1AP 外壳
  ⚠ O-DU 不解析 RRC-Container 里面是什么 —— Option 2 下 RRC 在 CU，
    DU 只负责把这串字节交给对应的信令承载。这是「配置由谁生成、消息由谁封装」的分工。

跳 5 · O-DU · RLC
  SRB0 用 RLC 透明模式（TM）：不分段、不编号、不重传。
  # 对比：后面的 RRCReconfiguration 走 SRB1，那时才有 PDCP 与 RLC 的完整机制。
  ＋ 加：（TM 下几乎不加东西）

跳 6 · O-DU · MAC
  ＋ 加：MAC 子头，复用进一个 MAC PDU（可能和其它逻辑信道拼在一起）
  调度器给它分配 PDSCH 上的资源，并生成对应的下行控制信息

跳 7 · O-DU · High-PHY
  ＋ 加：LDPC 编码冗余 → 调制 → 层映射 → 资源元素映射
  ⟹ 产出频域 IQ —— 到这一步，「消息」已经变成「信号」了

跳 8 · 前传封装
  ＋ 加：块浮点压缩 → O-RAN 无线应用头（帧/子帧/时隙/符号号）
        → eCPRI Common Header（Type 0）+ PC_ID/SEQ_ID
        → 以太网（EtherType 0xAEFE，带 VLAN PCP）
  ⚠ 在它之前，O-DU 已经先发过一条 eCPRI Type 2（C 面）
    告诉 O-RU「等下这堆 IQ 该怎么摆」。C 面迟到 = U 面白发。

跳 9 · O-RU
  − 减：以太网 / eCPRI / O-RAN 头 → 解压
  ＋ 加：（Category B 还要做预编码与波束加权）→ iFFT → 循环前缀 CP
  → DAC → 上变频 → 功放 → 天线发射

跳 10 · UE
  把上面每一层按相反顺序全部剥掉，最后 RRC 层拿到那条 RRCSetup。

# ★ 一条控制面消息穿过了：RRC → F1AP → SCTP → IP → Ethernet
#                        → RLC → MAC → PHY → eCPRI → Ethernet → 空口
#   十层封装，两次「协议 → 信号」的转换。
#   而这一切只为了把一条「我接纳你」的消息送到手机上。

报文二 · 用户面：一个下行数据包从 Internet 到 UE

# 场景：某个网站给这台手机回了一个 TCP 数据包。
#       UE 的 IP 是核心网分配的，属于 UPF 后面的地址段。

跳 1 · N6 口进入 UPF
  一个普通 IP 包，目的地址 = UE 的 IP。此时它还没有任何隧道封装。

跳 2 · UPF · 规则匹配与封装
  查 PDR 匹配到这条会话 → 应用 QER（限速）与 URR（用量统计/计费）
  → 按 FAR 指定的动作封装
  ＋ 加：GTP-U 头（含 TEID） → UDP（端口 2152）→ 外层 IP → 以太网
  # PDR/FAR/QER/URR 这四张规则表是 SMF 在会话建立时经 N4/PFCP 下发的（见 s5 第 5 步）。
  ⚠ 为什么必须封隧道：不封的话，这个包在回传网上就是一个「源地址可疑」的普通 IP 包，
    而且网络不知道该把它送到哪个基站 —— UE 是会移动的。
    TEID 建立了「这条会话 ↔ 当前服务基站」的映射，切换时只改映射，
    UE 的 IP 与上层 TCP 连接毫发无损。

跳 3 · 回传网络（N3）
  按外层 IP 转发。跨机房时这一段通常还要再套 IPsec 或走 MPLS/SR。
  # 此时链路上是：Ethernet | IP | UDP | GTP-U | IP(UE) | TCP | 数据  —— 两层 IP。

跳 4 · O-CU-UP
  − 减：N3 的 GTP-U / UDP / 外层 IP
  ＋ 加：SDAP 头 —— 按 QFI 把这个 QoS Flow 映射到某条 DRB
  ＋ 加：PDCP 头 —— 编号、加密、（按配置）完整性保护、头压缩
  ＋ 加：F1-U 的 GTP-U 头（另一个 TEID，由 O-DU 侧分配）→ UDP → IP → 以太网
  ⚠ 注意这里出现了第二条隧道：N3 与 F1-U 是两条独立的 GTP-U 隧道，
    TEID 不同、端点不同。「三段拼一条通路」的中间那一段就是它。

跳 5 · O-DU · RLC
  − 减：F1-U 的 GTP-U / UDP / IP
  ＋ 加：RLC 头 —— 编号、按授权大小分段；AM 模式下还要维护 ARQ 窗口

跳 6 · O-DU · MAC
  ＋ 加：MAC 子头，与其它逻辑信道复用
  交给 HARQ 进程，缓存一份副本等 ACK/NACK
  # ★ HARQ 实体在这里，而收发在 O-RU —— 前传因此被夹在 HARQ 环路正中间，
  #   这才是前传时延预算被压到百微秒量级的真正原因（见 ran_cu_du_ru.html）。

跳 7 · O-DU · High-PHY → 前传 → O-RU → 天线
  与报文一的跳 7~9 完全相同：编码调制 → 频域 IQ → eCPRI/以太网 → iFFT → 射频。
  # ★ 到了这一层，控制面和用户面的报文已经无法区分了 —— 
  #   它们都只是这一时隙里某些资源元素上的 IQ 采样。

跳 8 · UE
  PHY → MAC → RLC 重组 → PDCP 解密 + 重排序 → SDAP 去头
  → 交给 IP 栈 → TCP → 应用。

# ★ 数一下这个包一路上被套了几层「网络」：
#   ① 它自己的 IP/TCP（端到端，UE 与网站之间）
#   ② N3 的 GTP-U/UDP/IP（UPF 与 O-CU-UP 之间）
#   ③ F1-U 的 GTP-U/UDP/IP（O-CU-UP 与 O-DU 之间）
#   ④ 前传的 eCPRI/Ethernet（O-DU 与 O-RU 之间）
#   —— 四层「网络中的网络」，每一层解决的问题都不同。

eCPRI IQ 报文（U 面）F1AP 信令（C 面）NETCONF 请求（M 面）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础一台新基站从上电到能承载业务，正确的顺序是什么？为什么顺序不能乱？

    顺序可以答十步，但面试真正想听的是「哪两处是硬顺序」。先给顺序：

    1. 上电、链路 up；
    2. DHCP/SLAAC 拿 IP，并通过 DHCP 厂商选项或预置 FQDN 知道「网管在哪」；
    3. 建立安全的管理通道：设备主动向网管的 Call Home 端口发起连接，用出厂预置证书做双向认证；
    4. NETCONF hello 交换 capability，网管读硬件与软件清单；
    5. 软件版本协商与升级（不符则下载、校验、激活、重启）；
    6. 下发运营商域工作证书、账号权限、订阅；
    7. 下发业务配置：接口与 VLAN → 同步配置 → 载波与小区参数 → eAxC 流映射 → 前传时延窗；
    8. 等时钟锁定；
    9. 激活小区；
    10. 建立通知订阅、PM 周期与监督心跳。

    两处硬顺序（这是答案的核心）：

    ③ 之前必须有证书
    密码学约束：mTLS 要求双方都出示可被对端信任链验证的证书。没有证书就建不了安全连接——这不是「效果差一点」，是根本建不起来。
    ⑨ 之前必须有时钟
    物理约束：TDD 靠全网共同的时间基准划分上下行时隙。时钟没锁就开小区，会在邻区还在下行发射时切到上行接收，把一个站的故障扩散成一片区域的干扰。

    其余步骤是「强建议」而非「不可能」，但违反了都有具体代价：先下配置再升软件会遇到 YANG 模型随版本演进导致配置失效或语义漂移，症状是最难查的「下发成功但不生效」；载波配置排在同步配置之前会因为 YANG 的 leafref/must 约束引用不到同步节点而 commit 被拒。

    加分点：指出「证书校验依赖系统时间，而时间要靠同步拿到」是一个真实的循环依赖。一台 RTC 电池耗尽、时间停在出厂日期的设备会因「证书尚未生效」而纳管不上。破解方式有三种（出厂证书 notBefore 设得足够早、纳管阶段先只校验证书链、或先用 NTP/DHCP 选项拿粗略时间），必须在设计阶段选定，留给现场就是两天工期。

  2. 基础时钟没锁定为什么不能开小区？会出现什么现象？

    因为 TDD 把时间本身当成了资源。TDD 小区在同一个频点上靠时间分割上下行：这一段时隙全网都在下发，那一段时隙全网都在上收。这个划分只有在所有站点共用同一个时间基准时才成立。

    某个站相位跑偏之后，它会在邻区还在下行发射的时候切到上行接收——而邻区基站的下行功率比远处 UE 的上行功率高出好几个数量级。于是：

    • 肇事者本站几乎看不出问题：它自己的收发是自洽的，KPI 可能只是略降，告警里可能什么都没有；
    • 受害者是邻区：上行底噪被淹掉，表现为「上行覆盖突然缩了」「随机接入成功率下降」，而邻区自己的时钟完全正常。

    「肇事者与受害者分离」是同步类故障最恶劣的性质——所有其他故障都是「谁坏了谁报警」，只有同步是「A 站坏了、B 站报警」。这直接决定了排障方法：看到一片区域上行指标同时劣化，不要只查这些站，要查它们共同的同步上游。

    加分点：把指标换算成覆盖半径。相位误差要靠保护间隔吸收，而保护间隔本来是留给传播时延的——同步误差吃掉多少保护间隔，就等于从小区半径里扣掉对应的距离（按光速换算，注意往返关系要除以 2）。具体数值与算式见 PTP / SyncE。能这样答，说明理解了这个指标为什么长这样，而不是背下来的。

    再补一点：FDD 对相位不敏感。同步失效时可以只关 TDD 小区、留着 FDD——这个差别经常被忽略。

  3. 基础O1、A1、E2、F1 各自的职责是什么？它们的本质区别在哪？

    先给一句话职责，再给区别——区别比职责更能体现理解深度。

    接口两端职责时间尺度断了会怎样
    O1SMO ↔ 各网元FCAPS：配置、性能、告警、软件管理。承载是 NETCONF/YANG（加事件上报）秒 ~ 小时看不见、改不了；业务无恙
    A1Non-RT RIC ↔ Near-RT RIC下发策略（目标 + 约束 + 授权）、提供富化信息与模型管理秒 ~ 分钟xApp 沿用旧策略
    E2Near-RT RIC ↔ O-CU / O-DU订阅事件、上报指标、下发近实时控制10 ms ~ 1 s优化停止，网元回退内置算法
    F1O-CU ↔ O-DU（中传）F1-C 走 F1AP over SCTP（信令）；F1-U 走 GTP-U over UDP（用户数据）毫秒级新接入失败、数据面中断

    三组本质区别：

    O1 vs A1
    命令式 vs 声明式。O1 下发确定的参数值（「这个小区功率设为 X」）；A1 下发目标与约束（「这个切片的时延目标是 Y，允许你抢占 eMBB 资源，自己想办法达到」）。
    A1 vs E2
    层级不同。A1 是「上层给下层下策略」（RIC 之间），E2 是「下层去动网元」（RIC 到 CU/DU）。方向和作用对象都不一样。
    F1 vs 其余三个
    F1 在数据通路上，其余三个不在。这一条决定了它们的可用性要求、冗余设计与告警级别完全不同——判据是「断 30 秒会怎样」：F1 断了用户立刻掉话，E2/A1 断了只是「优化停了」，O1 断了运维界面没数据但网络无恙。把它们混在一张 SLA 里是很多现场的第一个坑。

    加分点：指出 O1 与 E2 两条路都能改网络，所以作用域必须显式划分。不划分的现场后果很具体——运维通过 O1 改了一个参数，过一会儿发现被改回去了，报「配置下发失败」，而真正原因是某个 xApp 在按 A1 策略正常工作。

  4. 基础随机接入解决什么问题？为什么它不能被省掉？

    它不是「建立连接」——建立连接是后面 RRC 的事。随机接入解决的是两件更底层的事：

    ① 上行同步
    UE 通过接收 SSB 只完成了下行同步：它知道基站的时序，但不知道自己离基站多远，因此不知道该提前多久发才能让信号正好落在基站的接收窗里。Msg2（随机接入响应）里的定时提前（TA）就是在告诉它这个提前量。这一步无论如何省不掉——它是几何决定的。
    ② 多用户竞争
    PRACH 是共享资源，多个 UE 可能同时选到同一个前导。所以需要 Msg3/Msg4 的竞争解决：Msg3 里带上 UE 自己的标识，Msg4 回来时确认「我说的是你」。没赢的 UE 退避后重试。

    四步的分工：Msg1 前导（此时 UE 还没有任何身份）→ Msg2 随机接入响应（给 TA + 临时标识 + 第一份上行授权）→ Msg3 RRCSetupRequest（第一条真正携带 UE 意图的消息）→ Msg4 RRCSetup + 竞争解决。

    涉及的网元：UE ↔ O-RU ↔ O-DU 的 MAC。注意随机接入完全在 O-DU 里闭环，不需要 O-CU 参与——直到 Msg3 里那个 RRC 容器需要送上去。

    工程加分点：PRACH 通常占用独立的 RU_Port_ID 取值，采样率与带宽也和普通业务信道不同，前传上是单独配置的。漏配之后的现象非常有辨识度——已接入的用户一切正常，只有新用户接不进来，KPI 上表现为随机接入成功率跳水，而 RRC、核心网、传输侧全绿，极易误判成核心网或终端问题。能说出这个案例，比背四步流程有分量。

8.2 中级（区分熟练度）

  1. 中级时钟失锁后 holdover 能撑多久？什么时候必须关小区？

    先讲清 holdover 是什么状态。时钟不是「锁定 / 没锁定」两态，而是四态：FREERUN（从未锁定）、ACQUIRING（正在收敛）、LOCKED（已锁定到可溯源时间源）、HOLDOVER（曾经锁定过，现在参考丢了，靠本地振荡器维持）。只有 LOCKED 与「仍在规格内的 HOLDOVER」允许带业务。

    HOLDOVER 是整套系统里最危险的状态，因为它的外在表现和 LOCKED 完全一样——本地伺服显示「已锁定」、告警不响、业务与 KPI 都正常。唯一变化的是 clockClass 这一个数值。所以监控上有一条硬要求：把 clockClass 从「已锁定」变为任何其它值直接设成告警项，而不是等相位超标或邻区报底噪。

    能撑多久：由本地频率源的准确度决定，因为频率误差在时间上积分就是相位误差。把相位预算除以频率偏差就是时长，量级差异很大（口径与算式见 PTP / SyncE）：

    • 只有板载 TCXO（约 1 ppm）→ 秒级，等于没有 holdover 能力；
    • SyncE 仍在（频率由物理层锁住，EEC 量级约 10 ppb）→ 分钟级，够撑过一次链路保护倒换或上游设备重启；
    • 本站有 OCXO → 小时量级，够运维赶到现场；
    • 本站有铷钟 → 天量级，用于关键汇聚节点。

    所以 SyncE 不是「锦上添花」，它是 PTP 的保险丝：把失效后的劣化速度降低两个数量级。第二个作用是让 PTP 伺服环能用更窄的带宽滤波，抗抖动能力更强。

    什么时候关小区：这是运维策略，不是标准条款。标准只告诉你误差上限，「超了怎么办」要自己定。两个选项都伤人——继续开着，一旦漂出预算就开始干扰邻区，把单站故障扩散成一片；主动关小区，本站用户立刻掉线但影响仅限本站。工程做法是提前做成自动策略：

    • 阈值设在「余量的某个比例」而不是「超标时」——超标那一刻已经在伤邻区了，而余量是可以算出来的；
    • 分级动作：进 holdover 立刻告警 → 余量过半时禁止新接入或降功率 → 余量将尽时关闭 TDD 小区（FDD 可以留着）；
    • 必须可自动执行——指望运维在半夜的窗口内响应等于没有策略；
    • 恢复也要有策略：伺服重新收敛期间相位还在动，要等状态稳定一段时间再解除限制，否则会「关了又开、开了又关」地振荡。

    加分点：一句话点明「关小区是为了保护邻区，不是为了保护本站」——类比一辆刹车失灵的车主动靠边停，不是为了车上的人，是为了路上的其他车。

  2. 中级eCPRI 在整条链路上处于什么位置？它跑在 TCP 还是 UDP 上？

    先把三个词的层次分清（这是最常见的混淆点）：Open Fronthaul 是 O-RAN 定义的接口与规范（切分点 Option 7-2x、四个平面、收发窗参数）；eCPRI 是它 C/U 面上用的报文格式；以太网是承载。包含关系是 O-RAN ⊃ Open Fronthaul ⊃ eCPRI/Ethernet。

    位置：它只存在于 O-DU ↔ O-RU 这一段（前传），承载的是频域 IQ 采样而不是用户数据。往上走的中传 F1-U 和回传 N3 用的是 GTP-U，不是 eCPRI。

    四个平面里 eCPRI 只覆盖两个：U 面用 eCPRI Type 0（IQ Data，占带宽绝大部分），C 面用 eCPRI Type 2（逐符号的调度与波束信息）；而 S 面走 PTP/SyncE、M 面走 NETCONF——这两个都不是 eCPRI 消息。另外 Type 5 用于单向时延测量。

    传输层：主流直接跑在以太网上（L2，EtherType 0xAEFE，没有 IP、没有传输层）；需要跨三层时可选 over UDP/IP；两种方式都绝不用 TCP。

    为什么不用 TCP（这是答案的重点，不要只说「TCP 慢」）：

    重传毫无意义
    等一个 RTT 之后回来的符号，O-RU 的接收窗早就关了——它不是「迟到的数据」而是垃圾，还白占一份带宽和一次内存拷贝，同时 O-DU 还得为所有已发数据保留重传缓冲。
    量级根本对不上
    Linux 的 TCP_RTO_MIN 是百毫秒量级，而前传单向预算是百微秒量级——差三个数量级。就算把下限调到理论最小，一次「发现丢包 + 请求 + 重发」也要两个以上单向时延，已经超预算。
    正确策略是「宁丢不等」
    把丢包率压到 HARQ 兜得住的水平（工程上对 U 面帧丢失率的要求通常在极低的量级，具体指标以所用规范与运营商要求为准），然后彻底不管它。靠的是专用或严格 QoS 隔离的链路、足够的带宽余量、以及不让 M 面大流量和 U 面抢队列。

    加分点：指出 C 面必须早于对应的 U 面到达——O-RU 要先知道「等下这堆 IQ 该怎么摆」。C 面迟到等于 U 面白发，这是前传的命门，也是「链路 up、告警全绿但小区起不来」的常见根因之一。

  3. 中级RRC 连接建立的关键步骤有哪些？为什么 O-DU 看不懂 RRC 消息？

    关键步骤（接在随机接入之后）：

    1. Msg3 = RRCSetupRequest：UE 在拿到上行授权后发出的第一条 RRC 消息，走 SRB0（CCCH）。
    2. O-DU → O-CU-CP：F1AP Initial UL RRC Message Transfer，把 RRC 消息作为容器上报，同时带上 C-RNTI 与 O-DU 侧分配的 UE 标识。
    3. O-CU-CP 决策并回 RRCSetup（Msg4）：经 F1AP 下发，O-DU 转成空口消息发出。这一步同时完成竞争解决，UE 拿到 C-RNTI 与 SRB1。
    4. UE 回 RRCSetupComplete：里面装着 NAS 的 Registration Request——这是控制面从 RAN 交棒给核心网的那一刻。

    这一步之后 UE 进入 RRC_CONNECTED，有了一条可靠的信令通道（SRB1），但还没有任何数据通路。

    为什么 O-DU 看不懂 RRC：因为 Split Option 2 把 RRC 与 PDCP 放在 O-CU、RLC 及以下放在 O-DU。所以 RRC 消息在 F1 上是以容器（八位字节串）的形式透传的，O-DU 只负责把它交给对应的信令承载发出去。

    两个推论值得说出来：

    • 抓 F1 的包能看到 F1AP 的结构，但 O-DU 自己不需要解析 RRC 的能力。抓包工具能解出内容是因为它内置了解码器主动往里钻，这和网元的实现需求是两回事。
    • 反过来，O-DU 确实要产生一部分 RRC 片段——MAC/RLC/物理层的配置。它把这部分交给 O-CU，由 O-CU 拼进完整的 RRC 消息。这就是「配置由谁生成、消息由谁封装」的分工。

    细节加分点：RRCSetup 走 SRB0，而 SRB0 既不加密也不做完整性保护——因为此时安全上下文还没建立。它是整条链上少数明文的信令之一。SRB0 还用 RLC 透明模式（TM）：不分段、不编号、不重传。到后面的 RRCReconfiguration 走 SRB1 时，才有 PDCP 与 RLC 的完整机制。能分清 SRB0 与 SRB1 的差别，说明是真读过流程而不是背过名字。

  4. 中级注册与鉴权是怎么完成的？为什么「注册成功」不等于「能上网」？

    流程骨架：UE 的 Registration Request 装在 RRCSetupComplete 里上来 → O-CU-CP 通过 NGAP Initial UE Message 转给 AMF → AMF 向 AUSF / UDM 取鉴权向量并读签约数据（5G-AKA）→ 经基站透传下发 Authentication Request，UE 用 SIM 里的密钥算出响应回上去（可能多次往返）→ 双向鉴权成立后建立安全上下文（Security Mode）→ AMF 回 Registration Accept 并分配 5G-GUTI。

    关键结构：NAS 是端到端的。鉴权、注册、会话请求这些 NAS 消息在 UE 与 AMF 之间端到端跑（N1），基站只是在 N2/NGAP 上做容器搬运，看不到里面的内容——它甚至没有解密的密钥。

    这个分层的现场意义
    一个「鉴权失败」的问题，抓基站的包基本没用，要在核心网侧看。这个设计是刻意的：它让基站不必被信任就能承载信令——注意基站在物理上是暴露的（O-RU 就挂在外面）。

    为什么注册 ≠ 能上网：这是 5G 明确切开的一刀。注册解决「你是谁、允许你接入」，会话解决「给你一条通往数据网的管子」。4G 里 attach 会顺带建默认承载，所以感觉是一步；5G 里 UE 完全可以只注册不建会话（例如仅接收寻呼与短信）。

    现场意义很直接：看到「UE 显示已注册但上不了网」，要去查 PDU 会话、SMF、N4 规则与 UPF，不要再回头查鉴权。反过来，「连不上、反复重试」才可能是鉴权或注册侧的问题。

    加分点：注册完成后 UE 处于 RM-REGISTERED 状态，这时它可被寻呼、可收短信，但没有任何用户面隧道。把「状态」和「通路」分开描述，比笼统说「注册好了」清楚得多。核心网侧的完整展开见 核心网演进：从 EPC 到 5GC。

8.3 高级（体现深度）

  1. 高级PDU 会话是怎么建起来的？UPF 在里面做什么？为什么必须封 GTP-U 隧道？

    流程：UE 发 NAS PDU Session Establishment Request（带 DNN 与 S-NSSAI）→ AMF 选一个 SMF 并调 Nsmf_PDUSession_CreateSMContext → SMF 从 PCF 取策略（5QI、会话级 AMBR）→ SMF 经 N4/PFCP 给 UPF 下发四张规则表并拿到 UPF 侧的 N3 地址 + TEID → 经 AMF 用 N2 PDU Session Resource Setup 把 QoS Flow 交给 gNB → O-CU-CP 经 E1 让 O-CU-UP 建承载上下文、经 F1-C 让 O-DU 建资源 → RRC Reconfiguration 建立 DRB → 各侧把自己分配的隧道端点回报，隧道两端才都知道对方。

    UPF 做的四件事，对应 N4 下发的四张表：

    PDR
    包检测规则：判断「这个包属于哪条会话、哪条 QoS Flow」。
    FAR
    转发动作规则：往哪儿转、要不要封装/解封装、丢弃还是缓存。
    QER
    QoS 执行规则：限速、标记。
    URR
    用量上报规则：计费与统计的数据来源。

    为什么必须封隧道（这是这道题的深度所在）：UE 的 IP 是核心网分配的，属于 UPF 后面的地址段。不封装的话有两个问题——① 这个包在回传网上就是一个「源地址可疑」的普通 IP 包，会被路由策略丢掉；② 更要紧的是，网络不知道该把下行包送到哪个基站，而 UE 是会移动的。GTP-U 用 TEID 建立了「这条会话 ↔ 当前服务基站」的映射，切换时只改这个映射，UE 的 IP 与上层 TCP 连接毫发无损。

    再深一层：一条通路是三段拼出来的——空口的 DRB + 中传 F1-U（GTP-U）+ 回传 N3（GTP-U）。N3 与 F1-U 是两条独立的隧道，TEID 不同、端点不同。而每段隧道的端点都是「两端各自分配、再互相告知」，所以流程里必然出现「先建、再改」（例如 E1 上先 Bearer Context Setup、拿到 F1 侧端点后再 Modification）。日志里看到「建了又改」是正常流程，不是重试——这一点能省下不少误判。

    失败模式加分点：这条流程里任何一步超时都会留下「半建立」状态——SMF 有 SM 上下文、UPF 有规则、gNB 没有资源。必须靠定时器 + 显式清理流程兜底，否则大规模信令风暴后会残留大量僵尸会话，占着 IP 池和 UPF 规则表不放。这类「事务补偿」逻辑是核心网软件复杂度的主要来源之一。

  2. 高级一个下行数据包从 Internet 到手机，完整路径与逐跳封装是什么？

    按跳走一遍，重点是每一跳加了什么、减了什么：

    1. N6 进入 UPF：一个普通 IP 包，目的地址是 UE 的 IP，此时没有任何隧道封装。
    2. UPF：查 PDR 匹配 → 应用 QER/URR → 按 FAR ＋ 加 GTP-U 头（含 TEID）+ UDP + 外层 IP + 以太网。此时链路上有两层 IP。
    3. N3 回传：按外层 IP 转发，跨机房时通常还要再套 IPsec 或走 MPLS/SR。
    4. O-CU-UP：− 剥 N3 的 GTP-U/UDP/IP → ＋ SDAP 头（按 QFI 映射到某条 DRB）→ ＋ PDCP 头（编号、加密、按配置做完整性保护、头压缩）→ ＋ F1-U 的 GTP-U 头（另一个 TEID）+ UDP + IP。
    5. O-DU · RLC：− 剥 F1-U 隧道 → ＋ RLC 头（编号、按授权大小分段，AM 模式还要维护 ARQ 窗口）。
    6. O-DU · MAC：＋ MAC 子头，与其它逻辑信道复用；交给 HARQ 进程并缓存副本等 ACK/NACK。
    7. O-DU · High-PHY：LDPC 编码 → 调制 → 层映射 → 资源元素映射 ⟹ 频域 IQ。
    8. 前传：块浮点压缩 → O-RAN 无线应用头（帧/子帧/时隙/符号号）→ eCPRI Type 0 → 以太网 0xAEFE。之前已先发过 C 面 Type 2。
    9. O-RU：解压 →（Cat B 还要做预编码/波束加权）→ iFFT → 加 CP → DAC → 上变频 → 天线。
    10. UE：PHY → MAC → RLC 重组 → PDCP 解密 + 重排序 → SDAP 去头 → IP → TCP → 应用。

    三个能体现深度的观察：

    四层「网络中的网络」
    ① 包自己的 IP/TCP（UE 与网站端到端）；② N3 的 GTP-U/UDP/IP；③ F1-U 的 GTP-U/UDP/IP；④ 前传的 eCPRI/Ethernet。每一层解决的问题都不同：②③ 解决移动性与寻址，④ 解决「信号怎么搬」。
    加密发生在 O-CU-UP
    PDCP 在 CU-UP，所以O-DU 与 O-RU 看到的用户数据都是密文。这也解释了为什么用户面密钥必须由 CP 经 E1 下发给 UP——E1 跨机房时那条链路就是密钥传输通道，必须上 IPsec 或 MACsec。
    三级重传，各管一个时间尺度
    HARQ（O-DU，最快，攒信噪比）→ RLC ARQ（较慢，补 HARQ 兜不住的）→ 端到端 TCP（最慢）。而前传上没有任何重传——它的策略是宁丢不等，丢掉的由 HARQ 兜。能把「哪一层负责哪个时间尺度的丢失」讲清楚，是这道题的天花板。

    最后一个观察：到了 PHY 与前传这一层，控制面和用户面的报文已经无法区分了——它们都只是这一时隙里某些资源元素上的 IQ 采样。平面的区分只存在于 MAC 以上。

  3. 高级故障定位时怎么「按平面分段」排查？这个方法为什么有效？

    核心思想：先用现象把范围切成一段，再决定去哪一段抓包。因为这条链上有七个网元、五个接口，逐个查要一整晚；而下面每个分支的判定只需要看现象，不需要抓包、不需要上现场。

    第一层：按平面分（判据是「断了会怎样」）：

    • 业务立刻中断 → 数据通路：前传 C/U 面、F1、N3；
    • 业务正常但优化停了 → 控制回路：E2、A1；
    • 业务正常但看不见/改不了 → 管理面：O1、前传 M 面；
    • 一切正常但在缓慢劣化 → 同步面。这一类最阴险，因为没有任何立即可见的信号。

    第二层：按现象分支（这是真正省时间的一步）：

    现象指向
    所有 UE 都接不进来，且已有连接也断小区级：同步、前传 C/U 面
    已有连接正常，只有新用户失败只有接入流程才用到的资源：PRACH 的前传流、随机接入相关的 C 面段类型、F1-C 信令通道
    能建 RRC 连接但注册失败越过了空口与 F1，问题在 N2 之后：SCTP 关联、PLMN/TAC/切片配置、鉴权数据
    注册成功但上不了网会话侧：SMF、N4 规则、UPF 转发、QoS Flow → DRB 映射
    能上网但速率/时延不达标不再是「通不通」：带宽与时延预算的分配
    一片区域上行指标同时劣化它们共同的同步上游，以及邻区的 clockClass
    随机 CRC 错误、误块率无规律上升前传时延/抖动超窗，或光功率余量不足

    为什么这个方法有效：因为它利用的是「哪些资源被哪些流程独占」这个结构信息，而这个信息是架构给定的、不需要现场数据。「老用户正常、新用户失败」必然指向只有接入才用的资源；「所有用户一起劣化」必然指向共享资源（带宽、时钟、光功率）。一个二分法就能把搜索空间砍一半。

    两个必须强调的方法论要点：

    先做免费的检查
    网管侧敲两条命令能确认的（commit 是否真执行、模型 revision 是否一致、clockClass 是多少），永远排在需要上现场或抓包的动作之前。按「命中率 × 排查成本」排序，而不是按「我最熟哪个」排序。
    「已锁定」不等于「对齐」
    「PTP 已锁定」只说明这一跳的伺服收敛了，不代表溯源到了可信时间源、也不代表端到端误差满足要求。要看溯源等级而不是锁定标志，并且要实测。这是排障里最常见的一个假绿灯。
  4. 高级综合题：「基站起不来」，你怎么按顺序查？

    这道题考的不是知识点，而是「你有没有一条不会漏、不会绕的顺序」。正确的顺序是沿着开站的依赖链从下往上走——因为下层不成立时，上层的所有检查都是无意义的。

    1. 先问清「起不来」是哪一种。这一步不能跳：是设备纳管不上？是配置下不去？是小区激活失败？还是小区显示已激活但没有 UE 能接入？这四种的排查路径完全不同，把它们混成一句「起不来」是最大的时间浪费。
    2. 物理层与链路：光模块识别、链路 up、光功率在余量内、纤长实测与设计一致。OTDR 实测纤长比图纸多 30~70% 是常见的，超距的话方案本身就不成立。
    3. 管理面（M）：设备纳管上了吗？—— 证书是否有效、系统时间是否离谱（证书校验依赖它）、Call Home 目标地址对不对。纳管上了之后，确认 commit 真的执行了、两端的 YANG 模型 revision 与 capability 一致。
    4. 同步面（S）：看溯源等级而不是看「已锁定」。clockClass 是多少？是锁在 PRTC 上，还是锁在一个正在 holdover 的上游时钟上？端到端时间误差实测过吗？这一步是最容易被假绿灯骗过去的一步。
    5. 前传控制面（C）：C 面报文有没有按时到达 O-RU？收发窗内比例、窗外丢弃计数是多少？C 面迟到 = U 面白发。
    6. 前传用户面（U）：eAxC 映射齐不齐（特别是 PRACH 那几条，它有独立的 RU_Port_ID）？压缩方法与位宽两端一致吗？Category A/B 匹配吗？
    7. 中传与上层信令：F1-C 的 SCTP 关联建起来了吗？NG Setup 成功了吗？—— NG Setup 失败的原因高度集中在 TAC/PLMN/切片配置不一致、SCTP 被防火墙拦、以及 Global gNB ID 冲突或未登记这三处，而失败消息里的 Cause 值是有意义的，不要看到「失败」就去重启。
    8. 平台侧（如果是云化 DU）：CPU 隔离四件套齐不齐、大页够不够、VF 是否绑到了用户态驱动、NUMA 是否对齐、硬件时钟有没有透传进容器。这些配置的失效方式是「静默降级」——Pod 照样起来、小流量压测照样过，只是抖动悄悄回来了。所以要看运行时状态而不是配置文件。

    这个顺序的三条设计原则（说出来会明显加分）：

    ① 沿依赖链走，不跳步
    S 面不成立时去查 U 面是浪费——时钟没对齐，C/U 面的窗判决本身就是错的。开站顺序就是排查顺序。
    ② 免费的检查排在前面
    第 3、4 步在网管侧敲命令就能做完；第 5、6 步要抓包或上现场。把免费的做完再动手。
    ③ 多厂商场景下，先怀疑「合规范围内的不同选项」
    两端都通过了一致性测试、链路 up、告警全绿，小区就是起不来——这类问题的共同特征是两端都没错，只是各自在合规范围内选了不同的可选项（模型版本、压缩位宽、section type 集合、Category）。它不是靠调试解决的，是靠开站前那张对接参数表逐行核对解决的。一小时的纸面工作能省下几天现场时间。

    最后一句加分：指出「基站起不来」里有一类根本不在基站上——是时间源、是传输、是机房条件。能主动说「第 2 步和第 4 步我要去问传输和同步专业」，比给出一份漂亮的自查清单更像做过现网的人。
