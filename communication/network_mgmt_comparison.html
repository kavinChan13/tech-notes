网络管理协议对比：NETCONF / RESTCONF / SNMP / gNMI

管理面不止 NETCONF。做横向比较：SNMP（老监控王）、NETCONF（配置强、事务化）、RESTCONF（NETCONF 的 REST 化）、gNMI（gRPC 流式遥测）。重点是它们在配置/状态/数据模型/实时性/可编程性/场景上的取舍，而非每个协议的所有细节。

01

四个协议一句话

先建立第一印象

这个题目最容易被讲成「四个协议各自的 API 手册」，读完还是不知道该用哪个。本篇要给的是判据：凭哪几个特征就能判断一个需求该落到哪个协议上，以及为什么这四个会在同一张网里长期并存而不是互相取代。先把「网络管理」拆开——设备对外要提供的能力只有三类，任何管理协议都是在这三类上做取舍：

① 配置（config）

把意图写进设备：加一个 VLAN、改一条路由策略、开一个小区。特征是低频、高风险、要求原子性——半套配置生效比不生效更糟。

② 状态（state）

把设备当前实际情况读出来：接口是 up 还是 down、收发了多少字节、光功率多少。特征是高频、只读、允许少量丢失。

③ 事件（event）

设备主动告诉你出事了：链路断了、板卡拔了、门限越限。特征是稀疏但不能漏、必须低时延。

摊开就能看清一件事：三类需求对协议的要求互相冲突。配置要「宁慢勿错」，于是需要两阶段提交、锁、校验、回滚——每一个机制都在增加往返与状态；采集要「多快好省」，一秒几万个数值，任何一次握手、任何一个可省的字节都是成本；事件要「设备主动推」，而前两者天然是「管理侧主动拉」。一个协议同时把三件事做到最优是不可能的，每一次协议更迭本质都是在某一类需求上做专门优化。

生活类比：和装修队沟通的三种方式。「把主卧墙面改成哑光白」这种施工变更你会写进合同附件、双方签字、约定不满意可以恢复原样——慢、正式、可追溯，这是配置（NETCONF 的事务）。「今天干到哪儿了」这种进度你不会天天签合同，而是让工头每天下班发张照片过来——高频、单向、丢一天也不致命，这是遥测（gNMI 的 Subscribe）。「水管爆了」这种突发必须工头立刻打电话，不能等你下次去工地才发现——这是告警（SNMP trap）。把三件事塞进同一种沟通方式，要么变成天天签合同，要么变成水管爆了写进周报。

SNMP

90 年代的经典监控协议。擅长读监控（get/trap）、拙于复杂配置。用 MIB 建模，UDP 承载。今天的定位：存量设备的最小公约数。

NETCONF

配置强、事务化（candidate/commit），YANG 建模，XML/RPC，SSH/TLS。运营商/电信主流。今天的定位：有风险的写操作的默认答案。

RESTCONF

把 NETCONF 的能力用 REST/HTTP + JSON/XML 暴露，对 Web/自动化友好，复用 YANG。今天的定位：集成成本最低的那条路。

gNMI

Google 主导，gRPC + Protobuf，强在高频流式遥测（streaming telemetry），云原生/大规模数据中心常用。今天的定位：规模化状态采集的唯一现实选择。

再补上第五种：CLI + expect 脚本。它至今仍是覆盖率最高的「管理方式」，因为它是设备一定有的；但它的输出是为人眼排版的，没有 schema、随软件版本改格式。它的失效方式是静默的——设备升级后正则匹配不到，脚本「什么都没做」也返回成功。所有现代网管协议的第一条设计目标都是「摆脱 screen scraping」。把五种方式按能力摊开，选型的可行域就已经画出来了：

还有一种常被单列的形态：gRPC 遥测 dial-out——设备主动连到采集器再推数据（IOS-XR、Junos 部分版本），编码可为 GPB / JSON。它和 gNMI Subscribe 解决同一件事，区别只在谁发起 TCP 连接；在 NAT 后或不想让设备开监听端口时更好用。把它理解成 gNMI Subscribe 的「反向拨号」变体即可，不必单列一种范式。

数据模型的三档：无模型 / MIB / YANG

模型驱动管理（model-driven management）：设备把自己「有哪些可配置项、每项的类型与取值范围、项与项之间的依赖」用机器可读的模型（YANG 文件）声明出来；管理侧据此自动生成数据结构、校验逻辑甚至 UI，而不是靠人读文档写正则。
关键洞察：它们大多共享 YANG 数据模型，区别主要在「传输 + 编码 + 交互范式」。这句话直接推出两个结论：① 换协议不需要重写数据模型；② 反过来，协议换了但设备的 YANG 模型实现得差，问题一个也解决不了（第 7 章的真实案例正是踩在这一点上）。
02

SNMP

监控之王，配置之短

  • 建模：MIB（OID 树）。承载：UDP（161 查询 / 162 trap）。
  • 强：读状态、告警 trap，设备普遍支持，轻量。
  • 弱：写配置能力差、无事务、安全较弱（v1/v2c 明文，v3 才加密）、大规模数据低效。

它是唯一一个你躲不开的网管协议——不是因为它好，而是因为过去三十年卖出去的每一台交换机、UPS、机房空调上都跑着一个 SNMP agent。而「它为什么统治了监控二十年」和「它为什么从来没能统治配置」是同一个问题的两面：它的设计取舍在读的场景上全部是优点，在写的场景上全部是缺点。

MIB 与 OID：一棵全球唯一的编号树

OID（Object Identifier）：一串点分十进制数字，如 1.3.6.1.2.1.2.2.1.10.3，标识一棵全球注册树上的一个节点。MIB（Management Information Base）：用 SMIv2（RFC 2578）语法写的文本文件，描述这棵树上每个节点的名字、类型、访问权限、语义。关系类比：OID 是「邮政编码」，MIB 是「邮编对照表」——设备只发编码，翻译成人能看懂的名字全靠管理侧本地装了对应的 MIB 文件。

为什么 SNMP 不能用来做配置：四个层次的原因

这是最高频、也最容易答浅的一道题。「安全性差」只是最表层的原因，v3 已经解决了。真正致命的是下面三条，而且它们至今没有任何补救方案：

① MIB 的表达力撑不起配置语义

SMIv2 只有「标量」和「表」两种结构，且表不能嵌套表。而真实配置天生是深层嵌套的：接口 → 子接口 → IP 地址 → VRF → 路由策略 → 规则。用 MIB 表达只能拆成一堆靠「人工约定的索引列」互相引用的平表——等于把外键约束交给管理侧靠文档去维护。加上 §1.2 那张图里的第三行（约束表达力为零），结论就是：MIB 能描述「设备有哪些旋钮」，描述不了「哪些旋钮组合是合法的」。

② SET 没有事务，而配置的本质就是事务

规范上同一个 SET PDU 内的多个 varbind 要求原子生效（RFC 1905 有 undoFailed 错误码，正是描述「部分生效后回滚失败」），但这个原子性的作用范围只有一个 PDU，而 UDP 报文装不下一次真实变更——跨 PDU 之间没有任何事务边界：没有 candidate、没有 validate、没有 commit/rollback、没有 confirmed-commit。第 3 章那张对比图画的就是这个后果：5 个 SET 里第 3 个失败，前两个已经生效，设备停在一个你没设计过的中间状态；而它可能刚好切断你自己的管理通道，或让路由策略半套生效导致流量黑洞。

③ 建行、删行要靠 RowStatus 这种补丁式约定

MIB 的表本来没有「创建一行」这个操作——SET 只能写已有的格子。RFC 2579 用一个叫 RowStatus 的特殊列打了个补丁：往一个不存在的行索引上写 createAndGo(4) 表示「建行并立即激活」，写 createAndWait(5) 表示「建行但先别生效，我还要填其他列」，填完再写 active(1)，删行则写 destroy(6)。

这套约定能用，但它把状态机塞进了一个整数字段：createAndWait 之后如果管理侧崩了，设备上就永久留着一行 notReady(3) 的僵尸配置，没有超时清理机制。而 NETCONF 里同一件事就是 <interface nc:operation="create"> 一个属性，失败就整体回滚。「配置操作要靠数据字段来编码」这件事本身，就说明协议层缺了一个抽象。

补一句常被忽略的第四层：SNMP 没有「读回你刚写下去的意图」这个能力。SNMP 只有一个数据视图——设备当前的实际值。而配置管理必须区分意图（intended config）与实际（operational state）：我配了接口 admin-up，但光模块没插所以 oper-down，这两个值必须都能读到才能做故障判断。SNMP 在 IF-MIB 里靠 ifAdminStatus / ifOperStatus 两个列手工模拟了这个区分，但这只在接口这一处做了；其他地方一律混在一起。YANG 用 config true/false 从建模层面解决了它。

UDP 承载与轮询模型：规模瓶颈在哪里

SNMP 跑在 UDP 上（agent 161，通知 162）。这在 1990 年是明确的优点：agent 不必维护连接状态，一台内存几百 KB 的接入交换机也扛得住几十个网管同时来问。但同一个选择放到千台规模上，成本链条与负载分布都成了问题：

真实案例形态：一走 SNMP 全表 walk，设备转发面就抖。停止 walk 立刻恢复，而请求速率只有几十 pps——所以根因不是带宽。真正的原因是该实现的 SNMP agent 与控制面协议栈跑在同一个核上，且 MIB 遍历是持锁的线性扫描，walk 期间 agent 长时间占 CPU，控制面报文处理被拖慢。判读线索：抖动与 walk 的起止时刻严格相关；设备 CPU 在 walk 期间抬升而流量没变；只采少量关键 OID 后症状消失。处置顺序：全表 walk 改成白名单 GetBulk → 加 jitter → 间隔从 30 s 放到 300 s → 再考虑迁流式遥测。

那它凭什么活到今天

那为什么 2026 年了它还在几乎每一个生产监控系统里？四条硬道理——覆盖率压倒性（机房里的 UPS、精密空调、光配线传感器支持 gNMI 的是零，支持 SNMP 的是全部）；只读用法的风险等级完全不同（致命缺陷全在写路径上，而九成现网用法是只读 + trap，一个只读 v3 账号的最坏后果是信息泄露而非断网）；生态是二十年的沉没成本（迁移成本不在协议，在告警规则、报表模板、值班手册这套积累）；agent 资源占用极低（几百 KB 内存、无需 TLS 栈与连接状态，受限设备跑不了 gRPC）。

怎么表述 SNMP 的现状才算专业？不要说「过时了、该淘汰」——这在面试和真实项目里都是减分的。准确说法是：「它在只读监控与告警上仍是覆盖率最高的方案，缺陷集中在写路径与规模化采集；所以现代做法是按能力分工——配置走 NETCONF/RESTCONF，高频指标走 gNMI，只有 SNMP 的设备与场景继续走 SNMP，并把三路数据在采集侧归一化。」能主动说出「归一化」，说明你想过并存期的工程问题，而不只是背对比表。
03

NETCONF

配置管理的电信主力

  • 建模：YANG。承载：XML/RPC over SSH(830)/TLS。
  • 强：复杂配置、事务（candidate/commit/confirmed-commit）、锁、校验、丰富操作、安全。
  • 弱：XML 相对冗长；高频遥测不是它的强项。
  • 场景：运营商网络、O-RAN O1 与前传 M 平面。

协议细节与 YANG 语法属于 NETCONF 与 YANG §4，工程落地属于 NETCONF 工程实践。这里只讲一件事：在与其他三个协议的对比中，NETCONF 独有的价值是什么。答案只有一个词——事务。

candidate + validate + commit：把配置变更做成数据库事务

SNMP 的写模型是「一格一格改，改一格立即生效」。NETCONF 的写模型是「先攒好整套改动，整体校验，一次性生效，出错整体撤销」。这个区别的价值不在方便，而在它消除了「中间状态」这个类别的故障。

生活类比：改合同 vs 现场涂改。SNMP SET 像是拿笔在正在执行的合同上直接涂改——改到第三条时发现和第一条矛盾了，前两条的涂改已经在那儿了，而且对方可能已经照着执行了。NETCONF 的 candidate 是「先在副本上把所有条款改完，双方通读一遍确认无矛盾（validate），然后签字换页（commit）」。如果通读时发现问题，撕掉副本即可，正本一个字没动过。confirmed-commit 更进一步：签完字先试运行 10 分钟，双方都没喊停才算最终生效，否则自动恢复原版。

validate（:validate 能力）提交前做整体一致性校验（引用完整性、must/when 约束）只能靠 commit 去试，失败了才知道

confirmed-commit（:confirmed-commit）提交后启动确认定时器，超时未确认自动回滚把自己关在门外（lockout）后只能派人去现场
lock / unlock独占 datastore，防止多方并发改同一处两个自动化系统同时下发，结果不可预测
rollback-on-error（:rollback-on-error）单次 edit-config 内出错即整体撤销半套配置留在 candidate 里，还要自己清理

把两种写模型的最小骨架并排放，差别就是「有没有一个可以撕掉的草稿」：

# SNMP：没有草稿，第 3 条失败时前 2 条已经在生产上了
snmpset -v3 … ifAdminStatus.3 i 1        → 立即生效
snmpset -v3 … ifMtu.3          i 9000    → 立即生效
snmpset -v3 … ipAdEntNetMask…  a …       → 失败，无法撤销前两条

# NETCONF：改动先落草稿区，整体校验通过才一次生效
<lock><target><candidate/></target></lock>
<edit-config><target><candidate/></target>
  <error-option>rollback-on-error</error-option> …</edit-config>
<validate><source><candidate/></source></validate>
<commit><confirmed/><confirm-timeout>600</confirm-timeout></commit>
<commit/>   ← 再连上来发这一条才算落定，否则 600 s 后自动回滚
confirmed-commit 解决的是一个 SNMP / RESTCONF / gNMI 都解决不了的问题：管理通道自锁（lockout）。远程改管理口 ACL 或路由，配置语法合法、校验通过、commit 成功——然后你的 SSH 断了。事务模型此时救不了你，因为事务是成功的，错的是配置的语义。confirmed-commit 把判据换成了「你能不能再连上来」：连不上就没人确认，设备自己恢复。它比任何外部看护脚本都可靠，因为它跑在设备自己身上，不依赖任何外部系统还活着。完整的时序、五个超时参数与没有 candidate 时的替代做法，见 NETCONF 工程实践 §4.3。

RESTCONF

NETCONF 的 REST 化身

  • 建模：同样 YANG。承载：HTTP(S) + JSON/XML，用 URL 定位数据节点，用 HTTP 动词（GET/POST/PUT/PATCH/DELETE）对应操作。
  • 强：对 Web/DevOps 工具链友好（curl 就能玩）、易集成。
  • 弱：没有 NETCONF 那么完整的事务/锁语义（简化版）。

RESTCONF 由 RFC 8040 定义，设计目标写得很直白：让「已经会用 HTTP API 的人」不必学 NETCONF 就能操作同一份 YANG 数据。理解它的关键是一句话——它不是「NETCONF 的简化版协议」，而是「YANG 数据树的一种 HTTP 映射规则」。数据模型完全一样，变的只是寻址方式与操作动词。

资源路径是怎么构成的

这是 RESTCONF 最需要一次看清的地方，因为路径写错时的报错信息通常毫无帮助。左边是 YANG 树，右边是它逐级映射出来的 URL：

HTTP 方法怎么映射到 NETCONF 操作

HTTP 方法作用大致对应的 NETCONF 语义要点
GET读资源（配置或状态）get-config / get用 ?content=config|nonconfig|all 区分只读配置还是含状态
HEAD只取响应头—拿 ETag / Last-Modified 做变更检测，不传正文
OPTIONS查询该资源支持哪些方法—判断某节点是否可写（是不是 config false）的便捷手段
POST在父资源下创建子资源；或在 /operations 下调用 RPCedit-config operation="create"；<rpc>目标已存在返回 409 Conflict，这是「创建」语义的体现
PUT整体替换（不存在则创建）operation="replace"幂等；未出现在请求体里的兄弟节点会被删掉，这一点最容易误伤
PATCH合并（plain patch）operation="merge"只改提到的部分；配 RFC 8072 的 YANG Patch 可做「有序的多操作列表」

PUT 与 PATCH 的区别在网管场景里是会出事故的级别。PUT 是「这个资源现在就是请求体描述的样子」——请求体里没写 enabled，设备就会把 enabled 恢复成 YANG 里的默认值或直接删掉。真实事故形态：自动化脚本用 PUT 去「改一下 MTU」，请求体里只带了 name 和 mtu，结果把该接口的 IP 地址、描述、VRF 绑定全清了。判据很简单：「我要的是替换还是修改？」——除了「以这份配置为准，多余的都删掉」这种明确的声明式下发，其余一律用 PATCH。而 NETCONF 里同一个区别是显式的 operation="replace" vs "merge"，写的人会警觉；HTTP 的 PUT 因为太熟悉反而容易失去警觉。

相对 NETCONF，RESTCONF 丢了什么

RFC 8040 是有意做减法的——不是能力不足，而是为了让「映射到 HTTP」这件事成立而主动放弃了一些语义。丢掉四样：

NETCONF 有RESTCONF 的情况实际后果
<candidate> 草稿区 + 多次编辑后一次 commitRFC 8040 没有定义 candidate 的访问方式；每个请求各自是一个独立事务，立即生效跨多个资源的变更无法原子化。要改 3 个接口 + 1 条路由，就是 4 个请求、4 次生效，中间状态真实存在于设备上
lock / unlock 显式独占没有锁 RPC，只有基于 ETag / Last-Modified + If-Match / If-Unmodified-Since 的乐观并发能检测到「我读之后别人改过」并拒绝（412），但无法阻止别人在我的多步操作中间插入变更。多系统并发下发时需要外部协调
confirmed-commit + 超时自动回滚标准里没有对应机制没有 lockout 保护——改错管理通道就是现场处理。这是 RESTCONF 做高风险变更最大的顾虑
validate 单独校验、test-option=test-only 干跑没有标准的「只校验不生效」入口只能发出去看返回码，校验与生效是同一个动作
公平地说它也拿到了三样 NETCONF 没有的东西：集成成本趋近于零（任何 HTTP 客户端 / API 网关 / CI 里的 curl 都能用，浏览器打开路径就看到 JSON）、复用整套 HTTP 基础设施（反代、OAuth/JWT、限流、审计、ETag 条件请求、可观测性——NETCONF over SSH 在这些方面基本一片空白）、细粒度寻址天然便宜（读一个叶子就是一个 URL，配 fields / depth 裁剪，比构造 subtree filter 轻）。
所以判据是：写操作的风险等级决定要不要 NETCONF。查状态、下发单个低风险参数、给业务系统开自助接口 → RESTCONF 足够且更省；一次改动横跨多个子系统、改错断业务、要审计与回滚 → 必须 NETCONF。
05

gNMI

为流式遥测而生

  • 建模：YANG（用 OpenConfig 模型居多）。承载：gRPC + Protobuf（HTTP/2）。
  • 强：Subscribe 流式遥测（设备按周期/变化持续推指标）——比 SNMP 轮询高效得多；二进制编码紧凑、性能好。
  • 操作：Get / Set / Subscribe / Capabilities。
  • 场景：大规模数据中心、云原生网元、高频监控。

gNMI（gRPC Network Management Interface）是 OpenConfig 社区的规范，不是 IETF RFC——这一点值得主动说明，因为它解释了 gNMI 的两个特征：迭代快，以及厂商实现差异比 IETF 协议大得多（没有 RFC 那种严格的 MUST/SHOULD 约束与互操作测试传统）。它跑在 gRPC over HTTP/2 上，通常强制 TLS；IANA 为 gNMI/gNOI 登记的端口是 9339，但现网厂商常用别的端口（如 57400），以设备文档为准。

四个 RPC：整个协议就这么大

RPC方向 / 流式做什么对应到别的协议
Capabilities一问一答返回设备支持的 YANG 模型列表（名字+版本+组织）、支持的编码、gNMI 版本≈ NETCONF <hello> 的能力交换；≈ RESTCONF 的 yang-library
Get一问一答按 path 取一次数据。可指定 type = ALL / CONFIG / STATE / OPERATIONAL≈ NETCONF get / RESTCONF GET
Set一问一答一次请求里带 delete / replace / update 三个列表，规范要求整体作为一个事务生效，顺序是删→替→更≈ NETCONF 单次 edit-config（但没有 candidate 与 confirmed-commit）
Subscribe双向流设备持续推送数据变化或周期采样，一条连接承载多个订阅没有对等物——这是 gNMI 独有的价值
「gNMI 的 Set 有事务吗？」是一道很好的分辨题，答案是「单请求内部有原子性，但没有跨请求的事务框架」：规范要求 target 把一个 SetRequest 里的所有操作当作一个事务，但没有 candidate（无法分多次攒改动）、没有 validate（无法只校验不生效）、也没有 confirmed-commit（无法超时自动回滚）。所以它的配置能力大致等于「NETCONF 的一次 edit-config + 立即 commit」——够用于声明式整体下发，不够用于需要人工确认窗口的高风险变更。这就是决策树里「需要事务性配置」指向 NETCONF 而不是 gNMI 的原因。

Path 与编码：省下来的字节来自四处

gNMI 的 Path 不是字符串，而是结构化的 elem 列表（Protobuf message）；人手书写时用 XPath 风格的简写 /interfaces/interface[name=eth0]/state/counters/in-octets，工具再转成结构。这个设计加上 §3.2 那张编码对比图里的四点，就是「差一个数量级」的全部来源：① 字段是编号而不是名字（<in-octets>847…</in-octets> 是 37 字节，Protobuf 的「字段号 + varint」不到 10 字节）；② prefix 把公共路径提出来只发一次——一次推 200 个接口计数器时，/interfaces/interface[name=X] 这段只写一遍，而路径字符串在遥测数据里往往比数值本身还长；③ 连接复用，上行除 TCP ACK 与 HTTP/2 窗口更新什么都不发；④ HPACK 头压缩 + 可选 gzip，对重复性极高的遥测流格外有效。此外每条 notification 都带一个设备侧打的纳秒时间戳——这一项后面会证明比省下的字节更值钱。

编码（encoding）选项：Capabilities 返回设备支持哪些编码，常见的有 JSON、JSON_IETF（按 RFC 7951 规则序列化 YANG 数据的 JSON）、PROTO（用 TypedValue 直接承载标量，最省）、BYTES、ASCII。Subscribe 场景应当优先选 PROTO；Get/Set 用 JSON_IETF 便于调试与跨实现互通。一个高频坑：某些实现只在 Get 上支持 JSON_IETF，Subscribe 只支持 PROTO，先跑 Capabilities 确认再写代码。

Subscribe 的三种模式：这才是杀手锏

订阅的模式分两层，这个两层结构是最容易搞混的地方：

SAMPLE 与 ON_CHANGE 怎么选

这是 gNMI 落地时最实际的一道选择题，判据是数据的性质而不是「想省多少带宽」：

数据性质例子该用理由
单调递增的计数器in-octets in-errors in-pktsSAMPLE计数器几乎每毫秒都在变，ON_CHANGE 等于「变了就推」= 无限高频。而且你要的是速率，速率必须由两个等间隔的样本求差——不等间隔的样本算速率误差很大
离散状态 / 枚举oper-status admin-status BGP session-state LACP 成员状态ON_CHANGE平时完全不变，一年可能只跳两次。SAMPLE 是在白推同一个值几百万次；更重要的是 SAMPLE 抓不到短于采样间隔的抖动（10 秒间隔看不见一次 300 ms 的 flap，而这恰恰是你最想知道的）
缓变的模拟量温度、光功率、电压、CPU 使用率SAMPLE（间隔可放宽）浮点值会持续微幅抖动，ON_CHANGE 相当于全速推送；这类数据要的是趋势，30–60 秒一个点足够

除了「必配 heartbeat」，ON_CHANGE 还有两个更隐蔽的陷阱，都只能靠实测发现：① 厂商对「什么算变化」的判定不一致——严格实现是「值不同才推」，宽松实现是「底层数据结构被更新过就推」，后者对一个每秒被刷新的字段等于全速推送。suppress_redundant 标志正是为此，但不是所有实现都遵守。上线前订一个稳定不变的 path，看一小时内到底收到几条。② 支持范围因设备而异——规范允许 target 对不支持的 path 返回错误，但有的实现会静默降级成 SAMPLE、甚至静默接受后什么都不发。这就是第 7 章案例里「订阅成功但没数据」的一类根因。

一条正确的订阅长什么样

流式遥测是 gNMI 相对其它三者的核心增量，所以这一块值得原样记住——两个订阅、两种触发方式，是生产上的标准配法：

# 计数器：SAMPLE 10 s（速率要靠等间隔样本求差，所以不能用 ON_CHANGE）
$ gnmic -a 10.0.3.11:57400 -u admin --tls-ca ca.pem subscribe \
    --mode stream --stream-mode sample --sample-interval 10s -e proto \
    --path '/interfaces/interface[name=*]/state/counters/in-octets'
# → 先推一遍初始全量，以 sync_response:true 收尾；此后每 10 s 自动来一条，
#   采集器全程什么都不用发

# 离散状态：ON_CHANGE + 心跳（心跳不是可选项）
$ gnmic -a 10.0.3.11:57400 -u admin --tls-ca ca.pem subscribe \
    --mode stream --stream-mode on-change --heartbeat-interval 60s \
    --path '/interfaces/interface[name=*]/state/oper-status'
# → 平时静默；跳变时立刻来一条，timestamp 是设备打的跳变时刻（纳秒）；
#   即使一直不变也每 60 s 来一条，证明订阅还活着

# ⚠ 不要用 --skip-verify：gNMI 的 Set 有写权限，中间人能改写你的配置下发
安全上有一处必须自己补：gNMI 规范本身不定义授权模型。「哪个用户能读写哪些 path」由实现自己决定（部分实现映射到 NACM / RFC 8341）。所以不能假设它有 VACM 那样的标准视图机制，必须逐个设备确认授权粒度到底是「全有全无」还是「按 path」——一个能 Set 的账号造成的最坏后果，比一个只读 SNMP 账号泄露严重得多。传输侧的证书校验、CA 固定与到期问题见 TLS/SSH/证书 §5。
关于 sync_response 这个容易被忽略的细节：Subscribe 建立后，设备会先把订阅路径下的当前全量值推一遍，推完发一条 sync_response: true 的消息，此后才是增量。采集器必须处理这个边界——在收到 sync_response 之前，你手里的是一份正在填充的不完整快照，不该拿去算「有多少接口 down 了」这类需要全量的判断。反过来，updates_only 这个请求标志可以要求设备跳过初始全量，只发后续变化，用于重连后不想再收一遍全量的场景。

模型与协议解耦：同一份 YANG 被三种协议承载

四个协议里三个用同一种建模语言，只有 SNMP 用自己的 MIB。这不是巧合，而是 2000 年代那一轮反思的直接结果：SNMP 把「数据长什么样」和「怎么传数据」焊死在一起了，想改传输就必须重新建模，二十年的 MIB 资产一分钱都带不走。

生活类比：菜谱与快递。YANG 是菜谱——写清一道菜有哪些配料、每样多少克、哪两样不能同时放。NETCONF / RESTCONF / gNMI 是三家快递公司：一家用木箱装（XML，结实但重）、一家用纸箱（JSON，通用好拆）、一家用真空压缩袋（Protobuf，最省体积）。菜谱一份就够，换快递公司不用重写菜谱。而 SNMP 的问题是「菜谱是印在木箱内壁上的」——想换纸箱，菜谱就没了。

这一节值得逐字看的只有一样东西：「读同一个接口的 MTU」这件事，四种协议各自长什么样。这个对照本身就是全篇的课——三者指向同一棵 YANG 树上的同一个叶子，只有 SNMP 是另一套地址空间。

## SNMP —— 独立的 OID 编号空间，MIB 与协议绑死
$ snmpget -v3 … 10.0.3.11 1.3.6.1.2.1.2.2.1.4.3
IF-MIB::ifMtu.3 = INTEGER: 1500          ← 列 .4 + 行索引 .3，与 YANG 无关

## NETCONF —— subtree filter（XML），指向 YANG 树
<get-config><source><running/></source><filter>
  <interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
    <interface><name>eth0</name><mtu/></interface></interfaces>
</filter></get-config>

## RESTCONF —— 同一棵树，URL 寻址
GET /restconf/data/ietf-interfaces:interfaces/interface=eth0/mtu
Accept: application/yang-data+json

## gNMI —— 同一棵树，结构化 path（elem 列表的简写形式）
$ gnmic … get --path '/interfaces/interface[name=eth0]/mtu' --type CONFIG

# 后三者的模型定义、类型约束、默认值、config/state 划分 —— 完全一样。
# 换协议要改的是客户端的寻址与序列化代码，不是数据建模。

这个解耦带来三项具体收益：校验逻辑可复用（用 pyang / yanglint 从 YANG 生成校验器，无论走哪个协议，发之前本地就能判定合法）；代码可生成（YANG → 语言类型 / gNMI path 常量 / 数据库 schema）；迁移不用重建资产（加一路 gNMI 遥测时写的是新采集器，不是新数据字典，两路数据能落到同一张表里——这一条是第 7 章能否平滑并存的关键）。

「大家都用 YANG」不等于「大家能互通」。deviation（合法声明「标准模型里这部分我不支持」）、augment（挂私有扩展，解析代码对未知节点不宽容就换厂商即失败）、if-feature（可选特性可以不实现）三个机制会让同名模型的实际行为不同——这三者的语法与用法见 NETCONF 与 YANG §3.5。实操结论：不要相信文档说的「支持 OpenConfig」，跑 Capabilities 拿真实的模型+版本清单，再对关键 path 逐个实测；版本号也要盯——OpenConfig 的大版本变更改过路径结构，而失败形态往往是「静默返回空」而不是报错。

决策树：从需求走到协议

真正做选型时是一串条件判断，而顺序很重要——先问「这是写还是读」，再问风险与规模，最后才问集成成本。把顺序颠倒（先看「哪个好接」）是最常见的选型错误。

并存而不是替代：一张网里的实际分工

「新协议取代老协议」是技术博客的叙事，不是现网的样子。四者长期并存是合理的稳态，理由有三层：能力互补而非重叠（confirmed-commit 与 ON_CHANGE 都没有替代品，一张网既要高风险变更又要秒级观测，就必然要两个协议）；设备支持永远是分批到位的（协议统一的前提是设备统一，而设备永远不会统一）；迁移成本落在采集侧（协议改造是一周的工作，下游一致性验证是三个月的工作）。所以真实的架构长这样：

并存带来的真正工作量是「归一化」。SNMP 的 IF-MIB::ifHCInOctets.3 与 gNMI 的 …/state/counters/in-octets 是同一个物理含义，但名字、层级、类型、时间戳语义全不同（SNMP 的时间戳是采集器收到的时刻，含网络与排队抖动；gNMI 是设备打的）。不做归一化，两路数据落进时序库就是两条互不相干的曲线，告警规则要写两套，切换时无法对比验证。
真实案例形态：约 1200 台设备从 SNMP 30 秒轮询迁到 gNMI 流式。
动机：采集器 CPU 常态 70%，且业务侧反复投诉「链路 flap 在监控上看不到」——flap 时长普遍在数秒，落在两个采样点之间。
收益：① 状态跳变从「30 秒内某个时刻」变成带纳秒时间戳的精确时刻，跨设备的 flap 因果链第一次能排出顺序，这是最大的收益；② 采集器报文处理量降约一个数量级，CPU 70% → 20% 以下，腾出的余量直接把计数器间隔从 30 s 缩到 10 s；③ 设备侧周期性的 MIB 全表遍历消失。
踩的坑，按代价从大到小：
① 模型不一致（最贵）。三个厂商都声称支持 OpenConfig，但一家把光模块功率挂在 openconfig-platform 组件树下、一家挂在自己 augment 的私有分支里，同一个 oper-status 的枚举大小写还不统一。处置：先跑 Capabilities，再逐型号实测关键 path，把差异收进一张映射表——这张表的维护成本被严重低估，它是项目里最持久的技术债。
② 设备实现参差。有型号声明支持 ON_CHANGE 却对某些 path 静默降级成 SAMPLE；有型号用通配符 [name=*] 时只返回第一个实例；有型号升级后路径结构变了，采集静默变空。处置：把「每个订阅的消息速率」本身做成监控指标并告警。不监控采集链路本身，是这类迁移最容易犯的错。
③ 订阅风暴。一次机房断电恢复，1200 台设备在几秒内同时重连并各自推初始全量，入口瞬时流量是稳态的几十倍，直接 OOM，重启后再被打一遍形成崩溃循环。根因是「初始同步的全量」这笔成本在容量规划里被完全忽略——稳态很省，冷启动很贵。处置三条：重连退避 + 抖动（绝不允许同时重连）、分片与限流（限并发订阅建立数与入口速率，超出先落盘）、用 updates_only 跳过重连后的全量；另外订阅拆细到叶子级，初始全量直接小一个量级。
最终形态：SNMP 没有下线，环境设备与两个老型号仍走它，trap 继续作为兜底告警通道。这个「并存 + 归一化」的结果不是妥协，而是当初就应该定的目标。
🎯 本篇要点回顾
  • 配置 / 状态 / 事件三类能力对协议的要求互相冲突，所以不存在全能协议；每次协议更迭都是对某一类需求的专门优化。
  • 后三者共享 YANG，区别在传输 + 编码 + 交互范式；SNMP 的 MIB 与协议绑死，这是它无法被平滑迁移的根因。
  • SNMP 做不了配置有四层原因：MIB 无嵌套无约束、SET 无跨 PDU 事务、建行靠 RowStatus 补丁、无「意图 vs 实际」的区分。安全只是最表层那一层，v3 已解决——而 v3 也只解决了安全。
  • confirmed-commit 与 ON_CHANGE 是全篇唯一两处没有替代品的能力：前者用「能否再次通信」作判据、防管理通道自锁；后者让状态跳变被设备以纳秒精度记录。
  • RESTCONF 丢了四样：candidate、lock RPC（只剩 ETag + If-Match 的乐观并发）、confirmed-commit、独立 validate；换来趋近于零的集成成本与整套 HTTP 基础设施。PUT 会清掉请求体里没提到的兄弟节点，除声明式整体下发外一律用 PATCH。
  • Subscribe 两层模式：先选 ONCE / POLL / STREAM，STREAM 下每个订阅再选 SAMPLE / ON_CHANGE / TARGET_DEFINED。计数器 SAMPLE，离散状态 ON_CHANGE 且必配 heartbeat。
  • 流式的真正价值不是省带宽，而是「让原本不可观测的现象变得可观测」——采样间隔决定了能观察到的最快现象，30 秒间隔对一次 2 秒的 flap 是完全不知情。
  • 「大家都用 YANG」≠「能互通」：deviation / augment / if-feature 让同名模型行为不同，上线前跑 Capabilities 并逐 path 实测。
  • 选型顺序是先分能力、后看成本：配置事务→NETCONF，Web 集成→RESTCONF，遥测→gNMI，兜底→SNMP。并存是稳态而非过渡态，真正的工作量在归一化那一层。

  1. 基础为什么 SNMP 适合做监控，却不适合做配置？

    因为 SNMP 的设计取舍在读路径上全部是优点，在写路径上全部是缺点。「安全性差」只是最表层的原因，而且 SNMPv3 已经解决了。真正致命的有四层：

    MIB 表达力不够
    SMIv2 只有标量和平表两种结构，表不能嵌套表；而真实配置天生是深层嵌套的（接口→子接口→地址→VRF→路由策略）。更关键的是 MIB 没有约束表达能力：没法声明「字段 A 只在字段 B 等于某值时有意义」（YANG 的 when）、「这两个字段必须同配」（must）、「这个字段引用另一张表的行」（leafref）。所以 MIB 能描述「有哪些旋钮」，描述不了「哪些旋钮组合合法」。
    SET 没有跨 PDU 的事务
    规范上同一个 SET PDU 内的多个 varbind 要求原子生效（RFC 1905 有 undoFailed 错误码正是描述部分生效后回滚失败），但这个原子性的作用范围只有一个 PDU，而 UDP 报文装不下一次真实变更。跨 PDU 之间没有 candidate、没有 validate、没有 commit/rollback、没有 confirmed-commit。5 个 SET 里第 3 个失败 → 前两个已生效，设备处在你没设计过的中间状态，而且因为 UDP 你甚至不能确定前两个到底成不成功。
    建行删行靠 RowStatus 打补丁
    MIB 的表本来没有「创建一行」这个操作。RFC 2579 用一个整数列 RowStatus 模拟：写 createAndGo(4) 建行并激活、createAndWait(5) 先建后填、active(1) 激活、destroy(6) 删除。把状态机塞进一个数据字段——管理侧在 createAndWait 后崩掉，设备上就永久留一行 notReady 的僵尸配置，没有超时清理。
    没有「意图 vs 实际」的区分
    SNMP 只有一个数据视图：设备当前的实际值。而配置管理必须能同时读到「我配的」和「实际生效的」（我配了 admin-up 但光模块没插所以 oper-down）。IF-MIB 靠 ifAdminStatus/ifOperStatus 两列在接口这一处手工模拟了，其他地方一律混在一起。YANG 用 config true/false 从建模层面解决了它。

    反过来说读路径：UDP 无连接状态所以 agent 极轻、一次往返就完事、覆盖率压倒性、只读账号的最坏后果是信息泄露而不是断网——这些正是它统治监控二十年的原因。

  2. 基础SNMPv3 解决了什么、没解决什么？

    解决了（全部集中在安全这一件事上）：

    • USM（User-based Security Model）：凭证从明文 community 变成「用户名 + 认证密钥 + 加密密钥」，认证用 HMAC-MD5/SHA 系列，加密用 DES / AES（RFC 3826 起）。凭证与内容都不再明文过网。
    • VACM（View-based Access Control Model）：授权从「读 community / 写 community」二选一，变成「用户 → 组 → 视图」的三级映射，视图可以精确到 OID 子树——只读账号真的读不到敏感的私有分支。
    • 重放防护：用 engineID + engineBoots + engineTime 构成时间窗，超窗的报文被丢弃。

    没解决（这部分才是加分项）：

    配置能力一点没变
    SET 还是那个 SET，MIB 还是那个 MIB。上一题的四层原因里，v3 一条都没碰。「SNMP 不适合配置」这个结论在 v3 之后完全不变。
    密钥管理自成一套
    不接 PKI、不接 RADIUS/TACACS+、没有证书吊销机制。密钥要在每台设备上单独配置，几千台设备轮换一次密钥是一个项目而不是一条命令。对比 gNMI 直接用 TLS 证书体系。
    engineID 本地化的运维坑
    USM 密钥要与设备的 engineID 做本地化（localization）。设备换主控或重置后 engineID 变了，之前配好的所有用户全部失效——现象是「设备好着呢，但网管突然采不到了」，而且看起来像网络问题。
    复杂度导致降级使用
    -l 有三档：noAuthNoPriv（只有用户名，等于白开 v3）、authNoPriv（验身份但内容仍可抓包读）、authPriv（生产唯一可接受）。现网大量「配了 v3 但用 noAuthNoPriv」——复杂度全付了，安全收益为零。
  3. 基础NETCONF 的事务模型由哪几件东西组成？价值在哪？

    组成部分与各自作用：

    • <candidate> datastore：可反复编辑的草稿区，改多少次都不影响转发面。
    • lock / unlock：独占 datastore，防止两个自动化系统同时改同一处。
    • validate：提交前做整体一致性校验（引用完整性、must / when 约束），失败就不用 commit。
    • commit：candidate 原子性地整体落到 <running>。
    • rollback-on-error（error-option）：单次 edit-config 内部出错即整体撤销，不留半套改动在 candidate 里。
    • confirmed-commit + confirm-timeout：提交后启动定时器，超时未收到第二次 commit 就自动回滚。

    价值不在「方便」，而在它消除了「中间状态」这一整类故障。SNMP 的写模型是「一格一格改、改一格立即生效」，所以一次多步变更中途失败必然留下一个你没设计过的设备状态；NETCONF 把整套改动做成一次原子跃迁，要么完整生效，要么一个字节都没变。

    加分：把 confirmed-commit 单独拎出来讲管理通道自锁（lockout）。远程改管理口 ACL 或路由，配置语法合法、校验通过、commit 成功，然后你的 SSH 断了——事务模型此时救不了你，因为事务是成功的，错的是配置的语义。confirmed-commit 的思想是「用能否再次通信作为变更成功的判据」：连不上来就意味着没人来确认，设备自己恢复旧配置。它比任何外部看护脚本都可靠，因为它跑在设备自己身上，不依赖任何外部系统还活着。

  4. 基础RESTCONF 相对 NETCONF 丢掉了什么？

    RFC 8040 是有意做减法的——不是能力不足，而是为了让「映射到 HTTP」这件事成立。丢掉四样：

    丢掉的RESTCONF 的替代实际后果
    <candidate> + 多次编辑一次 commit没有；每个 HTTP 请求各自是一个独立事务，立即生效跨多个资源的变更无法原子化。改 3 个接口 + 1 条路由 = 4 次请求 4 次生效，中间状态真实存在
    lock / unlock 显式独占乐观并发：ETag / Last-Modified + If-Match / If-Unmodified-Since，冲突返回 412能检测「我读之后别人改过」，但无法阻止别人在我的多步操作中间插入变更
    confirmed-commit没有没有 lockout 保护，改错管理通道就是现场处理
    独立的 validate / test-only 干跑没有标准入口校验与生效是同一个动作，只能发出去看返回码

    公平地讲也拿到了三样：① 集成成本趋近于零（任何 HTTP 客户端、API 网关、CI 里的 curl 都能用）；② 复用整套 HTTP 基础设施（反代、OAuth/JWT、限流、审计、ETag 条件请求、可观测性）；③ 细粒度寻址天然便宜（读一个叶子就是一个 URL，配 fields / depth 裁剪，比构造 NETCONF 的 subtree filter 轻）。

    判据：写操作的风险等级决定要不要 NETCONF。查状态、下发单个低风险参数、给业务系统开自助接口 → RESTCONF；一次改动横跨多个子系统、改错断业务、要审计与回滚 → 必须 NETCONF。

8.2 中级（区分熟练度）

  1. 中级gNMI 有哪四个 RPC？它的 Set 有事务性吗？
    • Capabilities（一问一答）：返回设备支持的 YANG 模型清单（名字+版本+组织）、支持的编码、gNMI 版本。任何 gNMI 集成的第一步都应该是它——文档说的和设备实际支持的经常不一致。
    • Get（一问一答）：按 path 取一次数据，可用 type 指定 ALL / CONFIG / STATE / OPERATIONAL。
    • Set（一问一答）：一个请求里带 delete / replace / update 三个列表，执行顺序是删 → 替 → 更。
    • Subscribe（双向流）：设备持续推送，一条连接承载多个订阅。这是四个里唯一没有对等物的。

    Set 的事务性：单请求内部有原子性，但没有跨请求的事务框架。规范要求 target 把一个 SetRequest 里的所有操作当作一个事务——要么全成要么全不成，SetResponse 里逐操作返回结果。但它没有 candidate（无法分多次攒改动）、没有 validate（无法只校验不生效）、也没有 confirmed-commit（无法超时自动回滚）。

    所以 gNMI 的配置能力大致等于「NETCONF 的一次 edit-config + 立即 commit」：够用于声明式的整体下发（把目标状态一次 replace 进去，这也是数据中心 leaf/spine 的常见用法），不够用于需要人工确认窗口的高风险变更。这就是选型决策树里「需要事务性配置」指向 NETCONF 而不是 gNMI 的原因。

    再加一句：gNMI 规范本身不定义授权模型——「哪个用户能读写哪些 path」由实现决定（部分实现映射到 NACM / RFC 8341）。做安全设计时不能假设它有 VACM 那样的标准视图机制，必须逐设备确认授权粒度是「全有全无」还是「按 path」。

  2. 中级Subscribe 的模式怎么分层？ON_CHANGE 与 SAMPLE 各用在什么数据上？

    模式分两层，这是最容易搞混的地方：

    • 第一层 SubscriptionList.mode（整个订阅列表的性质）：ONCE（发一次全量快照后关流，等价于流式的 Get，适合巡检与 CI 断言）/ POLL（连接保持但设备不主动发，客户端每发一个 PollRequest 才回一次）/ STREAM（设备主动持续推，真正的流式遥测）。
    • 第二层（仅 STREAM 时，每个 Subscription 各自选）：SAMPLE（按 sample_interval 周期上报）/ ON_CHANGE（只在值变化时上报）/ TARGET_DEFINED（交给设备自行决定，实现差异最大，生产建议显式指定）。

    选择判据是数据的性质，不是「想省多少带宽」：

    数据性质例子用理由
    单调递增计数器in-octets in-errorsSAMPLE计数器几乎每毫秒都在变，ON_CHANGE 等于无限高频；而且你要的是速率，速率必须由等间隔样本求差
    离散状态 / 枚举oper-status、BGP session-stateON_CHANGE平时完全不变，SAMPLE 是白推同一个值几百万次；更重要的是 SAMPLE 抓不到短于采样间隔的抖动（10 s 间隔看不见 300 ms 的 flap，而那恰恰是你最想知道的）
    缓变模拟量温度、光功率、CPU 使用率SAMPLE（间隔放宽）浮点值持续微幅抖动，ON_CHANGE 等于全速推；这类数据要的是趋势
    配置类数据接口描述、VLAN 成员ON_CHANGE只在有人下发时才变，最理想的 ON_CHANGE 对象，可据此做配置漂移检测
    大列表增删MAC 表、ARP 表看规模小表 ON_CHANGE；几十万条的表在震荡时会直接打爆采集器，改 SAMPLE 或只订聚合计数

    ON_CHANGE 的三个陷阱（加分点）：① 「没数据」和「没变化」在协议上长得一样——三天没消息既可能是一切正常，也可能是订阅早挂了；必须配 heartbeat_interval，不配心跳的 ON_CHANGE 订阅在生产上不可接受。② 厂商对「什么算变化」判定不一——严格实现是值不同才推，宽松实现是底层被更新过就推；suppress_redundant 标志正是为此，但不是所有实现都遵守，上线前要实测「订一个稳定不变的 path，一小时收到几条」。③ 支持范围因设备而异，有实现会静默降级成 SAMPLE、甚至静默接受后什么都不发。

  3. 中级为什么流式遥测比轮询强一个数量级？请算给我看。

    取标准场景：1000 台设备 × 200 计数器 × 10 秒间隔。目标数据量固定：20 000 数值/秒。差别全在「为了送达这 2 万个数值各自付多少」。

    SNMP GetBulk（max-repetitions=25）：每台每周期 8 次请求 → 1000 × 8 / 10 = 800 req/s，加响应共 1600 pps。单 varbind 线上体积约 25–40 B（OID 12–14 B + 类型长度 + 值），总计约 0.75 MB/s ≈ 6 Mbps，另有每秒 800 次 agent 侧 MIB 树查找。

    gNMI STREAM/SAMPLE（PROTO 编码）：1000 条长连接，请求速率 0（订阅只发一次）。prefix 提取了公共路径，单个 update 约 8–15 B，总计约 0.25 MB/s ≈ 2 Mbps；每台每周期打包成 1–2 个 Notification → 报文速率 100–200 pps。

    关键是要指出：字节数只差约 3 倍，但带宽从来不是瓶颈——瓶颈在报文数与设备 CPU，而这两项差一个数量级以上。三个层面：

    往返次数 800/s → 0
    每次 GetBulk 都要 agent 在收到请求时才去内部结构里找「比这个 OID 大的下一个实例」，很多实现是持锁线性扫描；gNMI 是设备按自己的定时器批量导出，可走内部高效路径、可流水线化、不与管理侧往返耦合。
    尖峰 → 均匀流
    轮询天然把负载压在采集周期边界（不加 jitter 时一千台同时被查）；流式是各设备按自己的相位推，天然打散。
    失败模式反了过来
    轮询在设备繁忙时采集成功率下降（越需要数据越拿不到），重试还会加压形成正反馈；流式最坏只是推送延迟，而且管理侧不施加任何额外负载。
    真正的价值（这句最重要）
    轮询有一个信息论限制：采样间隔决定了能观察到的最快现象。30 秒轮询对一次 2 秒的 flap、一次 500 ms 的队列爆满，不是「看不准」，而是完全不知道它发生过——而这恰恰是最难排查的故障。ON_CHANGE 把这个限制拿掉了：跳变由设备在发生的那一纳秒记录并主动上报。所以「为什么迁 gNMI」的正确答案是「让原本不可观测的现象变得可观测」，省带宽只是顺带的。
  4. 中级同一份 YANG 怎么被 NETCONF / RESTCONF / gNMI 三个协议复用？

    因为 YANG 是建模语言，不是协议——它只描述「数据长什么样」，不规定「怎么传」。三个协议各自定义了一套寻址与序列化规则，把同一棵 YANG 数据树映射到自己的表达形式：

    协议寻址方式序列化
    NETCONFsubtree filter 或 XPath（XML 结构本身就是路径）XML
    RESTCONFURL 路径：/restconf/data/<module>:<node>/<list>=<key>/<leaf>JSON（RFC 7951 规则）或 XML
    gNMI结构化 Path（elem 列表 + key map），书写时用 /a/b[k=v]/c 简写Protobuf（或 JSON_IETF）

    关键：三者的模型定义、类型约束、默认值、config true/false 划分完全一样。换协议要改的是客户端的寻址与序列化代码，不是数据建模。这个解耦带来三个具体收益：校验逻辑可复用（用 pyang/yanglint 从 YANG 生成校验器，发之前本地就能判定合法）；代码可生成（YANG → 语言类型 / path 常量 / 数据库 schema）；迁移不用重建资产（加一路 gNMI 遥测时要写的是新采集器，不是新数据字典，两路数据能落到同一张表里）。

    对比 SNMP 就能看出这个设计的价值：SNMP 把「数据长什么样」和「怎么传」焊死在一起了——MIB 是 SNMP 自带的建模方式，两者绑死。想换传输就必须重新建模，二十年的 MIB 资产一分钱都带不走。这也是为什么 SNMP 到 YANG 世界的迁移只能重写而不能映射。

    加分：指出 gNMI 的路径省略了模块名前缀（/interfaces/interface[name=eth0]），而 RESTCONF 的第一个节点必须带（ietf-interfaces:interfaces）。gNMI 用 origin 字段来处理模块/命名空间消歧，实践中多数实现默认单一 origin，所以在同时支持标准模型与私有模型的设备上路径可能撞车——这是跨厂商采集的一个隐坑。

8.3 高级（体现深度）

  1. 高级OpenConfig 与 IETF 标准模型、厂商私有模型是什么关系？「都用 YANG」就能互通吗？

    三套模型是互补的三层，不是竞争关系：

    • IETF 标准模型：IETF 工作组走 RFC 流程产出（ietf-interfaces RFC 8343、ietf-ip 8344、ietf-routing 8349、ietf-system 7317、ietf-netconf-acm 8341）。权威稳定、变更慢，覆盖偏基础层，高层业务能力覆盖有限。
    • OpenConfig：运营商与大型网络运营者主导的社区（不是标准组织）。迭代快、贴近实际运维需求，是 gNMI 遥测的事实标准模型。版本演进比 IETF 快，也更可能引入不兼容变更。
    • 厂商私有（native）：覆盖最全，通常与 CLI 一一对应，能配的都能配；但完全不可移植，换厂商等于重写。用于标准模型覆盖不到的功能。

    OpenConfig 有一个值得单独讲的设计：/config 与 /state 双子树。IETF 的做法是在同一棵树上用 config false 标注只读叶子；OpenConfig 把同名叶子在两个子树下各放一份——.../config/mtu 是「我要求的」，.../state/mtu 是「实际生效的」。好处是「意图 vs 实际」的对比退化成一次纯路径比较，配置漂移检测极其简单；代价是模型体积近乎翻倍，且订阅时必须想清要哪一边（订错了会得到「配置改了但指标没动」的困惑）。

    「都用 YANG」绝不等于「能互通」，三个机制让同名模型行为不同：

    deviation
    厂商用它合法地声明「标准模型里这一部分我不支持」——不支持某叶子、缩小取值范围、把可写改成只读。所以设备声明支持 openconfig-bgp 6.1.0，不代表该模型里每个节点都能用。
    augment
    厂商往标准模型里挂私有扩展。你的解析代码如果对未知节点不宽容，换个厂商就失败。RESTCONF 路径里这还会带来一个额外坑：被 augment 进来的子节点，那一节路径要带上它自己的模块名。
    if-feature
    模型里声明为可选特性的部分，设备可以选择不实现。

    实操结论：不要相信文档说的「支持 OpenConfig」，要跑 Capabilities 拿到真实的模型+版本清单，再对关键 path 逐个实测。版本号也要盯——OpenConfig 的大版本变更改过路径结构，同一段采集代码在同型号设备的两个软件版本上取不到数据，是很常见的现场问题，而且失败形态往往是「静默返回空」而不是报错。

  2. 高级为什么真实网络里四个协议是并存的稳态，而不是逐步替代？

    「新协议取代老协议」是技术博客的叙事。并存是合理的稳态，理由有三层，从强到弱：

    ① 能力上互补而非重叠（最硬的理由）
    NETCONF 的 confirmed-commit 与 gNMI 的 ON_CHANGE 都没有替代品。前者是唯一能防管理通道自锁的协议级机制，后者是唯一能精确记录状态跳变时刻的手段。一张网既要做高风险变更、又要做秒级观测，就必然要两个协议——这不是历史包袱，是需求本身决定的。
    ② 设备侧的支持永远是分批到位的
    同一张网里的设备来自不同厂商、年代、产品线。核心路由器可能三个协议全支持，老接入交换机只有 SNMP + CLI，机房 UPS / PDU / 精密空调 / 光配线传感器只有 SNMP。协议统一的前提是设备统一，而设备永远不会统一。
    ③ 迁移成本落在采集侧而不是协议侧
    告警规则、报表模板、值班手册、容量模型全绑在现有指标名字上。把一个指标从 SNMP 换成 gNMI，协议改造是一周的工作，下游一致性验证是三个月的工作。所以理智的做法是并行采集、对比数据、逐指标切换。

    典型的现网分工：核心路由器 → NETCONF 配置 + gNMI 采集 + RESTCONF 对外只读查询 + SNMP trap 兜底；数据中心 leaf/spine → gNMI Set 声明式下发 + gNMI 订阅；老接入交换机 → CLI/SNMP；O-RAN 网元 → NETCONF（O1 与前传 M 平面）+ VES 报事件与 PM 文件；环境类设备 → 只有 SNMP。

    加分点：并存带来的真正工作量是「归一化」。SNMP 给你 IF-MIB::ifHCInOctets.3，gNMI 给你 /interfaces/interface[name=eth1]/state/counters/in-octets——同一个物理含义，但名字、层级、类型、时间戳语义全不同（SNMP 的时间戳是采集器收到的时刻，含网络与排队抖动；gNMI 是设备打的纳秒时间戳）。不做归一化，两路数据落进时序库就是两条互不相干的曲线，告警规则要写两套，切换时无法对比验证。推荐做法是定义一层内部规范化指标名（以 OpenConfig 路径为蓝本，因为它最贴近 YANG），SNMP 侧写映射表转过来——这样每台设备从 SNMP 切到 gNMI 时，下游一行都不用改。

  3. 高级什么是订阅风暴？怎么防？

    订阅风暴（subscription storm）指的是大量 gNMI 订阅在短时间内同时建立或重建，导致采集侧瞬时负载远超稳态而崩溃。根因是一笔容量规划里最常被忽略的成本：每条 Subscribe 建立后，设备会先把订阅路径下的当前全量值推一遍（推完发 sync_response: true），然后才是增量。稳态很省，冷启动很贵。

    典型触发场景（都是真实会发生的）：

    • 机房断电恢复：上千台设备在几秒内同时上线并推初始全量，入口流量是稳态的几十倍。
    • 采集器自身重启/升级：所有订阅同时重建——而且如果采集器因此再次 OOM，就形成崩溃循环，这是最危险的形态。
    • 网络分区恢复：一批设备的连接同时超时重连。
    • 订阅粒度过粗：一个订阅把整棵 /interfaces 订下来，初始全量里包含大量根本不用的叶子，体积大一个量级。
    • 大列表的 ON_CHANGE：几十万条的 MAC/ARP 表在震荡时，ON_CHANGE 会把每一条增删都推出来。

    防护手段，按有效性排序：

    重连退避 + 抖动
    采集器侧对每台设备的连接建立做随机延迟 + 指数退避，绝不允许同时重连。这是成本最低、收益最大的一条。
    分片 + 限流
    按设备分片到多个采集实例；每个实例限制并发订阅建立数（不只是限入口速率——瓶颈常在建立阶段）与入口消息速率，超出的先落盘缓冲而不是丢弃或崩溃。
    updates_only 跳过初始全量
    这个请求标志让设备不推初始快照，只发后续变化。对已有基线的订阅在重连后特别有用——直接把冷启动最贵的那一笔省掉。
    订阅拆细，只订要用的叶子
    不要用一个订阅把整棵子树订下来。订到叶子级别，初始全量体积直接小一个量级，而且出问题时定位范围也小。
    把采集链路本身做成监控指标
    监控「每个订阅的消息速率」：一个 ON_CHANGE 订阅长期零消息、或一个 SAMPLE 订阅的速率与预期不符，都要告警。不监控采集链路本身，是这类系统最容易犯的错——你会在完全不知情的情况下丢数据好几周。
    保留一条不依赖订阅的兜底通道
    SNMP trap 或 NETCONF notification 继续作为关键告警的第二条路。订阅挂了的时候，你需要一个不经过订阅的方式知道这件事。
  4. 高级给一个新的网管系统做协议选型，你怎么决策？

    这是综合题，考的是判断顺序而不是结论。我会按下面的顺序走，关键是先分能力、后看成本——反过来（先看「哪个好接」）是最常见的选型错误。

    第 0 步：先摸设备，不要先选协议
    列出所有要纳管的设备类型（含 UPS、PDU、空调、光配线传感器这些容易被忘的），逐型号跑 Capabilities / <hello> 拿到真实支持的协议与模型清单，不要相信规格书。这一步的产出决定了后面所有选择的可行域——如果 40% 的设备只有 SNMP，那「统一到 gNMI」这个方案在第一天就是不可行的。
    第 1 步：按「配置 / 状态 / 事件」把需求分成三堆
    不要按「功能模块」分。这三类对协议的要求互相冲突，必须分开选。
    第 2 步：配置那一堆，按「改错的后果」分级
    会中断业务、需要审计与回滚、需要变更窗口确认 → NETCONF（candidate + validate + commit + confirmed-commit 防自锁，这是不可替代的）。
    低风险、要让别的系统方便接进来 → RESTCONF（注意用 PATCH 而不是 PUT；PUT 会把请求体里没提到的兄弟节点清掉，这是真实事故形态）。
    已在用 gNMI 采集、且是声明式整体下发 → gNMI Set 可以复用同一条通道，但要接受它没有 confirmed-commit。
    第 3 步：状态那一堆，按「时间分辨率」分
    秒级 / 要看跳变时刻 / 千台以上 → gNMI Subscribe（计数器 SAMPLE、离散状态 ON_CHANGE + 必配 heartbeat）。
    只是低频巡检 → NETCONF get 或 RESTCONF GET 就够，不必为此引入一整套流式管道。
    设备只有 SNMP → SNMP GetBulk，但要做对三件事：用 ifHC* 64 位计数器（32 位在万兆口上 3.4 秒回绕）、每次带 sysUpTime 判重启（否则每次重启画一根冲天尖峰）、给采集加 jitter 打散。
    第 4 步：事件那一堆，一定要有两条路
    主路走 gNMI ON_CHANGE（时间戳精确）或 NETCONF notification；兜底保留 SNMP trap。理由很实在：订阅挂了的时候，你需要一个不经过订阅的方式知道这件事。
    第 5 步：设计归一化层（这一步最容易被跳过，代价最大）
    定义一层内部规范化指标名（以 OpenConfig 路径为蓝本），各协议的采集器负责转换。好处是下游（告警、报表、容量模型）完全不感知数据来自哪个协议，后续每台设备切换协议时下游一行都不用改。跳过这一步的系统，在第一次协议切换时会发现下游要改三个月。
    第 6 步：把采集链路本身纳入监控
    每个订阅的消息速率、每个 SNMP 目标的成功率、每个 NETCONF 会话的存活——这些指标的缺失会让你在完全不知情的情况下丢数据。

    最后要主动说出的结论：目标不是「统一到一个协议」，而是「按能力分工 + 数据归一化」。并存是稳态而不是过渡态——因为 confirmed-commit 与 ON_CHANGE 各自不可替代，而设备永远不会统一。把「三年内全部迁到 gNMI」写进方案的选型，是没有摸过现网设备清单的选型。
