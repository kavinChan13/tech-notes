网络管理协议对比：NETCONF / RESTCONF / SNMP / gNMI

管理面不止 NETCONF。做横向比较：SNMP（老监控王）、NETCONF（配置强、事务化）、RESTCONF（NETCONF 的 REST 化）、gNMI（gRPC 流式遥测）。重点是它们在配置/状态/数据模型/实时性/可编程性/场景上的取舍，而非每个协议的所有细节。

01

四个协议一句话

先建立第一印象

网管协议这个题目最容易被讲成「四个协议各自的 API 手册」，读完还是不知道该用哪个。本篇要给的不是手册，而是判据：面对一个具体需求，凭哪几个特征就能判断该落到哪个协议上，以及为什么在同一张网里这四个会长期并存而不是互相取代。

先把「网络管理」这件事拆开。设备对外要提供的能力只有三类，任何管理协议都是在这三类上做取舍：

① 配置（config）

把意图写进设备：加一个 VLAN、改一条路由策略、开一个小区。特征是低频、高风险、要求原子性——半套配置生效比不生效更糟。

② 状态（state）

把设备当前实际情况读出来：接口是 up 还是 down、收发了多少字节、光功率多少。特征是高频、只读、允许少量丢失。

③ 事件（event）

设备主动告诉你出事了：链路断了、板卡拔了、门限越限。特征是稀疏但不能漏、必须低时延。

把这三类摊开就能看清一件事：它们对协议的要求是互相冲突的。配置要的是「宁慢勿错」，所以需要两阶段提交、锁、校验、回滚——这些机制每一个都在增加往返次数与状态。状态采集要的是「多快好省」，一秒钟推几万个数值，任何一次握手、任何一个可省略的字节都是成本。事件要的是「设备主动推」，而配置和状态天然是「管理侧主动拉」。一个协议同时把三件事做到最优是不可能的，历史上的每一次协议更迭，本质都是在某一类需求上做专门优化。

生活类比：和装修队沟通的三种方式。「把主卧墙面改成哑光白」这种施工变更你会写进合同附件、双方签字、约定不满意可以恢复原样——慢、正式、可追溯，这是配置（NETCONF 的事务）。「今天干到哪儿了」这种进度你不会天天签合同，而是让工头每天下班发张照片过来——高频、单向、丢一天也不致命，这是遥测（gNMI 的 Subscribe）。「水管爆了」这种突发必须工头立刻打电话，不能等你下次去工地才发现——这是告警（SNMP trap）。把三件事塞进同一种沟通方式，要么变成天天签合同，要么变成水管爆了写进周报。

SNMP

90 年代的经典监控协议。擅长读监控（get/trap）、拙于复杂配置。用 MIB 建模，UDP 承载。今天的定位：存量设备的最小公约数。

NETCONF

配置强、事务化（candidate/commit），YANG 建模，XML/RPC，SSH/TLS。运营商/电信主流。今天的定位：有风险的写操作的默认答案。

RESTCONF

把 NETCONF 的能力用 REST/HTTP + JSON/XML 暴露，对 Web/自动化友好，复用 YANG。今天的定位：集成成本最低的那条路。

gNMI

Google 主导，gRPC + Protobuf，强在高频流式遥测（streaming telemetry），云原生/大规模数据中心常用。今天的定位：规模化状态采集的唯一现实选择。

另外两个必须提一句、但不该被当成「协议」的东西：

  • CLI + expect 脚本：至今仍是覆盖率最高的「管理协议」，因为它是设备一定有的。但它的输出是为人眼排版的，没有 schema、随软件版本改格式、错误只能靠匹配提示语判断。用它做自动化的代价是每次设备升级都可能让你的脚本静默失效——不是报错，而是正则匹配不到、于是「什么都没做」也返回成功。所有现代网管协议的第一条设计目标都是「摆脱 screen scraping」。
  • gRPC 遥测（dial-out）：部分厂商（如 IOS-XR、Junos 的某些版本）提供「设备主动连到采集器再推数据」的模式，编码可以是 GPB / JSON。它和 gNMI Subscribe 解决的是同一件事，区别只在谁发起 TCP 连接；在 NAT 后、或者不想让设备开监听端口时更好用。OpenConfig 侧也有独立的 gNMI Dial-out 规范。把它理解成 gNMI Subscribe 的「反向拨号」变体，不必单列一种范式。

02

SNMP

监控之王，配置之短

  • 建模：MIB（OID 树）。承载：UDP（161 查询 / 162 trap）。
  • 强：读状态、告警 trap，设备普遍支持，轻量。
  • 弱：写配置能力差、无事务、安全较弱（v1/v2c 明文，v3 才加密）、大规模数据低效。
  • 现状：监控存量仍广泛，但新配置管理已让位给 NETCONF/gNMI。

上面四行是结论，但 SNMP 值得比这更认真地对待。它是唯一一个你在职业生涯里躲不开的网管协议——不是因为它好，而是因为过去三十年卖出去的每一台交换机、路由器、UPS、PDU、机房空调、光模块托盘上都跑着一个 SNMP agent。理解「它为什么统治了监控二十年」和「它为什么从来没能统治配置」是同一个问题的两面：它的设计取舍在读的场景上全部是优点，在写的场景上全部是缺点。

MIB 与 OID：一棵全球唯一的编号树

OID（Object Identifier）：一串点分十进制数字，如 1.3.6.1.2.1.2.2.1.10.3，标识一棵全球注册树上的一个节点。MIB（Management Information Base）：用 SMIv2（RFC 2578）语法写的文本文件，描述这棵树上每个节点的名字、类型、访问权限、语义。关系类比：OID 是「邮政编码」，MIB 是「邮编对照表」——设备只发编码，翻译成人能看懂的名字全靠管理侧本地装了对应的 MIB 文件。

OID 的前缀是有含义的，记住这一段就能看懂九成的现网 OID：

判读要点，按重要性排：

  • sysUpTime（1.3.6.1.2.1.1.3.0）是所有计数器的有效期戳。SNMP 的计数器全是单调递增且会回绕的绝对值，速率必须由管理侧做两次采样求差。如果两次采样之间设备重启了，sysUpTime 会变小——此时差值必须丢弃而不是当成速率。不做这个判断的监控系统会在每次设备重启后画出一根冲天的尖峰，然后触发一堆假告警。每次采集都顺手把 sysUpTime 带上，是 SNMP 采集器最基本的正确性要求。
  • 32 位计数器在万兆口上会秒级回绕。ifInOctets 是 Counter32，上限约 4.29×10⁹ 字节。10 Gbps 满速跑 = 1.25 GB/s，3.4 秒回绕一次；1 Gbps 也只有 34 秒。这就是 RFC 2863 补出 ifXTable 里那套 ifHC*（High Capacity，Counter64）的原因。现网仍然见到有人在万兆口上采 ifInOctets，结果流量图恒定偏低——因为两次采样之间回绕了不止一次，差值算出来是个小数字。判据：只要接口速率 ≥ 1 Gbps，一律用 ifHCInOctets。
  • ifIndex 不是稳定标识。RFC 2863 要求 ifIndex 在重初始化之间保持不变，但现网实现参差——插拔子卡、增删子接口、升级软件后重排的情况都遇到过。把「ifIndex=3」当成「GE0/0/2 的永久别名」存进数据库，是监控系统最经典的数据错位来源（一觉醒来所有接口的流量图对调了）。正确做法是每轮采集先走一遍 ifName / ifDescr 建立索引到名字的映射。
  • 看到 No Such Object available on this agent 要分清两种情况：设备不支持这个 MIB（正常，很多低端设备只实现 mib-2 的一小部分），还是 VACM 视图把它挡在了外面（v3 下的权限问题，看起来和「不支持」一模一样）。这两个的排查方向完全相反。

为什么 SNMP 不能用来做配置：四个层次的原因

这是本篇最高频的面试题，也是最容易答浅的一道。「安全性差」只是最表层的原因，而且 v3 已经解决了。真正致命的是下面三条，而且它们至今没有任何补救方案：

① MIB 的表达力撑不起配置语义

SMIv2 只有「标量」和「表」两种结构，表里只能放标量，表不能嵌套表。而真实配置天生是深层嵌套的：一个接口下面有多个子接口，每个子接口下面有多个 IP 地址，每个地址属于一个 VRF，VRF 下面挂路由策略，策略里有多条规则……用 MIB 表达这个，只能拆成一堆用「人工约定的索引列」互相引用的平表——等于把关系数据库的外键约束交给管理侧靠文档去维护。

更要命的是 MIB 没有约束表达能力：没法声明「这个字段只有当那个字段等于某值时才有意义」（YANG 的 when）、没法声明「这两个字段必须同时配」（must）、没法声明「这个字段引用另一张表里已存在的行」（leafref）。所有这些依赖只能写在 MIB 的 DESCRIPTION 注释里给人看。结果是：MIB 能描述「设备有哪些旋钮」，但描述不了「哪些旋钮组合是合法的」。

② SET 没有事务，而配置的本质就是事务

规范上，同一个 SET PDU 里的多个 varbind 要求原子生效（RFC 1905 定义了 undoFailed 这个错误码，正是为了描述「部分生效后回滚失败」这种情况）。但这个原子性的作用范围仅限一个 PDU，而 UDP 报文装不下一次真实的配置变更——跨 PDU 之间没有任何事务边界：没有 candidate（改动先落到一个草稿区）、没有 validate（提交前整体校验）、没有 commit/rollback、没有 confirmed-commit（改完等确认，超时自动恢复）。

后果很具体：一次改动需要 5 个 SET，第 3 个失败了——前两个已经生效，设备处在一个你没设计过的中间状态。这个中间状态可能刚好把你自己的管理通道切断（改了管理口的 ACL 之后才发现下一条 SET 发不出去了），也可能让路由策略半套生效导致流量黑洞。而管理侧甚至无法可靠地知道「究竟前两个成功了没有」——因为 UDP 的响应可能只是丢了。

③ 建行、删行要靠 RowStatus 这种补丁式约定

MIB 的表本来没有「创建一行」这个操作——SET 只能写已有的格子。RFC 2579 用一个叫 RowStatus 的特殊列打了个补丁：往一个不存在的行索引上写 createAndGo(4) 表示「建行并立即激活」，写 createAndWait(5) 表示「建行但先别生效，我还要填其他列」，填完再写 active(1)，删行则写 destroy(6)。

这套约定能用，但它把状态机塞进了一个整数字段：createAndWait 之后如果管理侧崩了，设备上就永久留着一行 notReady(3) 的僵尸配置，没有超时清理机制。而 NETCONF 里同一件事就是 <interface nc:operation="create"> 一个属性，失败就整体回滚。「配置操作要靠数据字段来编码」这件事本身，就说明协议层缺了一个抽象。

补一句常被忽略的第四层：SNMP 没有「读回你刚写下去的意图」这个能力。SNMP 只有一个数据视图——设备当前的实际值。而配置管理必须区分意图（intended config）与实际（operational state）：我配了接口 admin-up，但光模块没插所以 oper-down，这两个值必须都能读到才能做故障判断。SNMP 在 IF-MIB 里靠 ifAdminStatus / ifOperStatus 两个列手工模拟了这个区分，但这只在接口这一处做了；其他地方一律混在一起。YANG 用 config true/false 从建模层面解决了它。

解决了：凭证不再明文过网、报文可加密、有重放防护、授权可以按 OID 子树收窄（只读账号真的读不到 enterprises 下的敏感分支）。
没解决：① 配置能力一点没变——SET 还是那个 SET，MIB 还是那个 MIB，事务问题原封不动；② 密钥管理是自己一套，不接 PKI、不接 RADIUS/TACACS+、没有证书吊销，密钥要在每台设备上单独配，几千台设备轮换一次密钥是个项目；③ engineID 本地化带来的运维坑——USM 密钥要与设备的 engineID 做本地化（localization），设备更换主控或重置后 engineID 变了，之前配好的用户全部失效，现象是「设备好着呢但网管突然采不到了」；④ 复杂度导致的降级使用：现网大量「配了 v3 但用 noAuthNoPriv」的情况，安全收益为零而复杂度全付了。

UDP 承载与轮询模型：规模瓶颈在哪里

SNMP 跑在 UDP 上（agent 161，通知 162）。这在 1990 年是明确的优点：agent 不需要维护连接状态，一台内存只有几百 KB 的接入交换机也扛得住几十个网管同时来问；单次查询一个来回就完事，没有握手成本。但同一个选择在今天带来三个必须处理的问题：

  • 丢包等于数据洞，且无法区分「丢了」与「设备忙」。UDP 没有重传，超时重试是管理侧自己实现的。而超时的原因可能是：网络丢包、agent 进程被高优先级任务抢占、设备 CPU 打满（常常正是你最需要数据的时候）。所以 SNMP 监控有一个讽刺的特性：设备越出问题，采集成功率越低。重试还会放大压力，形成正反馈。
  • 报文尺寸受限，超了就 tooBig。规范要求所有实现至少支持 484 字节的报文，实际多数支持到接近一个 MTU（1472 字节负载）。GetBulk 的 max-repetitions 设大了，响应装不下就返回 tooBig 错误——而且是整个响应作废，不是截断。采集器必须实现「遇到 tooBig 就把 max-repetitions 减半重试」的退避逻辑。这个值的最优取值随设备与 OID 而变，工程上常见落在 10–50 之间。
  • 轮询是 O(设备数 × OID 数 / 间隔) 的请求风暴。而且负载完全落在固定的时刻——如果采集器不做打散（jitter），一千台设备会在每个 10 秒边界同时被查，管理网络与采集器的瞬时负载是平均值的若干倍。「监控系统自己把网压垮」在大规模 SNMP 部署里是真实发生过的事。

把轮询模型的成本量化一下（这也是第 6 章要与 gNMI 对比的基线）：

# 轮询一台设备的一张接口表，成本从哪来
设备有 48 个物理口 + 200 个子接口 = 248 行
要采 8 个计数器列                    = 1984 个 varbind

GetBulk(max-repetitions=25) 一次约取 25 个 varbind
  → 每列需 248/25 ≈ 10 次往返，8 列 ≈ 80 次请求-响应
  → 每次往返含一次 agent 侧的 MIB 树查找

关键代价不在字节数，而在 往返次数 与 agent 的按需计算：
  agent 收到 GetNext/GetBulk 时才去内部数据结构里
  「找到比这个 OID 大的下一个存在的实例」——
  很多实现是线性扫描，OID 越靠后越慢。
真实案例形态：一走 SNMP 表设备就丢包。某接入设备在被网管全表 walk 时，转发面出现毫秒级抖动甚至丢包，停止 walk 立刻恢复。根因不是带宽——请求速率只有几十 pps。真正的原因是该实现的 SNMP agent 与控制面协议栈跑在同一个核上，且 MIB 遍历是持锁的线性扫描；全表 walk 期间 agent 长时间占用 CPU，导致控制面报文处理延迟，进而影响了转发表的更新。判读线索有三个：① 抖动与 walk 的起止时刻严格相关；② 设备 CPU 曲线在 walk 期间抬升明显（而流量没变）；③ 换成只采少量关键 OID 后症状消失。处置顺序：先把全表 walk 改成按需的 GetBulk 白名单、给采集加 jitter 打散、把采集间隔从 30 秒放到 300 秒，再考虑迁到流式遥测。这类问题的普适教训是：SNMP 的开销主要不在网络，而在 agent 的 CPU——而这一项在容量规划里几乎从不被计入。

那它凭什么活到今天

说完这么多缺点，必须诚实回答一个问题：为什么 2026 年了，SNMP 还在几乎每一个生产监控系统里？这不是惰性，是有硬道理的：

① 覆盖率是压倒性的

SNMP 是唯一一个跨厂商、跨设备类型、跨年代都能指望的接口。你的机房里有交换机、路由器、防火墙、负载均衡、UPS、PDU、精密空调、存储阵列、KVM、光配线架传感器——它们里面支持 gNMI 的可能是零，但支持 SNMP 的是全部。做统一监控时，最小公约数的价值极高。

② 只读监控的风险模型完全不同

SNMP 的致命缺陷（无事务、无回滚）全都在写路径上。而 90% 的现网 SNMP 用法是纯只读 + trap。一个只读的 v3 账号能造成的最坏后果是信息泄露，不是网络中断——这个风险等级，和「为了换协议去升级三千台设备的软件」比起来，绝大多数运维团队会选择维持现状。

③ 生态与人力的沉没成本

Zabbix / Nagios / LibreNMS / Cacti / 商业网管，二十年的告警规则、报表模板、值班手册、以及「一看到这个 OID 就知道是什么」的运维直觉，全都是 SNMP 形态的。迁移的成本不在协议，在这套积累。而它换来的收益（采集间隔从 30 秒变成 10 秒）对很多业务并不构成价值。

④ agent 的资源占用极低

一个精简的 SNMP agent 可以做到几百 KB 内存、不需要 TLS 栈、不需要维护连接。对嵌入式设备、传感器、老旧单板来说，跑 gRPC + Protobuf + TLS 是不现实的。凡是「设备侧资源极其受限」的场合，SNMP 依然是唯一能落地的选项。

怎么表述 SNMP 的现状才算专业？不要说「SNMP 过时了、应该淘汰」——这在面试和真实项目里都是减分的。准确的说法是：「SNMP 在只读监控与告警上仍然是覆盖率最高的方案，缺陷集中在写路径与规模化采集这两点上；所以现代做法是按能力分工——配置走 NETCONF/RESTCONF，高频指标走 gNMI，剩下那些只有 SNMP 的设备与只有 SNMP 的场景（如 UPS、环境传感器）继续走 SNMP，并把三路数据在采集侧归一化。」能说出「归一化」这三个字，说明你想过并存期的工程问题，而不只是背协议对比表。
03

NETCONF

配置管理的电信主力

  • 建模：YANG。承载：XML/RPC over SSH(830)/TLS。
  • 强：复杂配置、事务（candidate/commit/confirmed-commit）、锁、校验、丰富操作、安全。
  • 弱：XML 相对冗长；高频遥测不是它的强项。
  • 场景：运营商网络、O-RAN O1、前传 M 平面。详见 NETCONF 工程实践。

本篇不重复 NETCONF 的协议细节与 YANG 语法（那属于 NETCONF 与 YANG），也不展开它的工程落地（那属于 NETCONF 工程实践）。这里只讲一件事：在与其他三个协议的对比中，NETCONF 独有的价值是什么。答案只有一个词——事务。

candidate + validate + commit：把配置变更做成数据库事务

SNMP 的写模型是「一格一格改，改一格立即生效」。NETCONF 的写模型是「先攒好整套改动，整体校验，一次性生效，出错整体撤销」。这个区别的价值不在方便，而在它消除了「中间状态」这个类别的故障。

生活类比：改合同 vs 现场涂改。SNMP SET 像是拿笔在正在执行的合同上直接涂改——改到第三条时发现和第一条矛盾了，前两条的涂改已经在那儿了，而且对方可能已经照着执行了。NETCONF 的 candidate 是「先在副本上把所有条款改完，双方通读一遍确认无矛盾（validate），然后签字换页（commit）」。如果通读时发现问题，撕掉副本即可，正本一个字没动过。confirmed-commit 更进一步：签完字先试运行 10 分钟，双方都没喊停才算最终生效，否则自动恢复原版。

datastore / 能力作用没有它会怎样
<running>当前生效的配置—（必有）
<candidate>（:candidate 能力）可反复编辑的草稿区，不影响转发每一次 edit-config 都立即生效，中间状态暴露在生产上
<startup>（:startup 能力）下次重启加载的配置改了 running 但没存盘，重启回退（经典事故）
validate（:validate 能力）提交前做整体一致性校验（引用完整性、must/when 约束）只能靠 commit 去试，失败了才知道
commitcandidate 原子性地落到 running无原子性
confirmed-commit（:confirmed-commit）提交后启动确认定时器，超时未确认自动回滚把自己关在门外（lockout）后只能派人去现场
lock / unlock独占 datastore，防止多方并发改同一处两个自动化系统同时下发，结果不可预测
rollback-on-error（:rollback-on-error）单次 edit-config 内出错即整体撤销半套配置留在 candidate 里，还要自己清理

<!-- ① 锁住 candidate，防止别的会话同时改 -->
<rpc message-id="1" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <lock><target><candidate/></target></lock>
</rpc>

<!-- ② 往 candidate 里写改动；error-option 保证本次编辑本身也是原子的 -->
<rpc message-id="2" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <edit-config>
    <target><candidate/></target>
    <default-operation>merge</default-operation>
    <error-option>rollback-on-error</error-option>
    <config>
      <interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
        <interface>
          <name>eth0</name>
          <enabled>true</enabled>
          <mtu>9000</mtu>
        </interface>
      </interfaces>
    </config>
  </edit-config>
</rpc>

<!-- ③ 提交前整体校验：引用是否存在、must/when 约束是否满足 -->
<rpc message-id="3" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <validate><source><candidate/></source></validate>
</rpc>

<!-- ④ 带确认的提交：600 秒内不发第二次 commit 就自动回滚 -->
<rpc message-id="4" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <commit>
    <confirmed/>
    <confirm-timeout>600</confirm-timeout>
  </commit>
</rpc>

<!-- ⑤ 管理侧验证业务正常后，发一个不带 confirmed 的 commit 落定 -->
<rpc message-id="5" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <commit/>
</rpc>
confirmed-commit 是 NETCONF 最值得单独讲的一个能力，而且它解决的是一个 SNMP / RESTCONF / gNMI 都解决不了的问题：管理通道自锁（lockout）。
设想你远程改一台机房设备的管理口 ACL 或路由，配置语法完全合法、校验通过、commit 成功——然后你的 SSH 断了，再也连不上。此时事务模型帮不了你，因为事务是成功的，错的是配置的语义。confirmed-commit 的设计恰恰针对这一点：新配置先生效，但设备内部起一个定时器；如果管理侧在超时前没能再连上来发第二个 commit（这个动作本身就证明了通道还活着），设备自动恢复到旧配置。这是「用能否再次通信作为变更成功的判据」这一思想的协议级实现，比任何外部看护脚本都可靠——因为它跑在设备自己身上，不依赖任何外部系统还活着。面试里能主动举出 lockout 这个场景，说明你真的远程改过设备。

XML 的代价：具体贵多少

NETCONF 的短板同样要说清楚，而且要给量级而不是「比较冗长」。三笔成本：

  • 字节膨胀。同一份数据用 XML 表达，相比 JSON 通常大一档，相比 Protobuf 差距更大——原因是每个叶子都要写两遍标签名（开+闭），加上命名空间声明。工程上的量级感：一个只有几十字节数值的接口状态，包成 NETCONF XML 后往往是几百字节。这对配置（低频）无所谓，对遥测（每秒几万条）就是决定性的。
  • 解析成本。XML 解析要处理命名空间、实体、属性、混合内容；即便用流式解析器（SAX 类），单条消息的 CPU 成本仍明显高于 Protobuf 的定长/变长字段解码。设备侧（往往是较弱的控制面 CPU）的瓶颈通常出现在这里而不是网络。
  • 会话建立成本高。NETCONF over SSH 要走完 SSH 的密钥交换与认证，再交换 <hello> 里的能力列表——而能力列表在支持大量 YANG 模型的设备上可以是几百 KB 甚至更多（每个模型一条 capability URI）。这意味着「建一次会话读一个值」的用法极其低效，NETCONF 的正确用法是长连接复用。
推论：NETCONF 的通知（notification）能不能当遥测用？协议上可以——RFC 5277 定义了 create-subscription 与事件流，RFC 8639/8641 的 subscribed notifications 与 YANG Push 更进一步支持了「按周期或按变化推送数据树的一部分」。但编码还是 XML，成本没变。所以它适合承载「事件」（稀疏、重要，如告警、状态跳变），不适合承载「指标」（密集、每秒万条）。这正是 gNMI 存在的理由，也是 O-RAN 的 O1 接口选择「NETCONF 管配置 + VES 走 HTTP/JSON 报事件与性能文件」这种分工的原因（见 O-RAN 接口）。
04

RESTCONF

NETCONF 的 REST 化身

  • 建模：同样 YANG。承载：HTTP(S) + JSON/XML，用 URL 定位数据节点，用 HTTP 动词（GET/POST/PUT/PATCH/DELETE）对应操作。
  • 强：对 Web/DevOps 工具链友好（curl 就能玩）、易集成。
  • 弱：没有 NETCONF 那么完整的事务/锁语义（简化版）。
# RESTCONF 读一个接口配置（对比 NETCONF 的 XML RPC）
GET /restconf/data/example-interfaces:interfaces/interface=eth0
Accept: application/yang-data+json

RESTCONF 由 RFC 8040 定义。它的设计目标写得很直白：让「已经会用 HTTP API 的人」不必学 NETCONF 就能操作同一份 YANG 数据。理解它的关键是搞清一件事——RESTCONF 不是「NETCONF 的简化版协议」，而是「YANG 数据树的一种 HTTP 映射规则」。数据模型完全一样，变的只是寻址方式与操作动词。

资源路径是怎么构成的

这是 RESTCONF 最需要一次讲透的地方，因为路径写错的报错信息通常毫无帮助。规则只有四条：

# 完整形状
{+restconf}/data/<module-name>:<top-node>/<child>/<list>=<key>/<leaf>
   │           │        │             │                    │
   │           │        │             │                    └─ 列表用 = 跟主键值，不是 /
   │           │        │             └─ 同模块内的子节点不再写模块名
   │           │        └─ 第一个节点必须带 module-name: 前缀（消歧）
   │           └─ /data 是配置+状态的统一数据树；/operations 是 RPC；
   │              /yang-library-version 报告 YANG 库版本
   └─ 根路径由 /.well-known/host-meta 发现，习惯上是 /restconf

# 例子逐级展开（用 IETF 标准模型 ietf-interfaces / RFC 8343）
/restconf/data                                        整棵树
/restconf/data/ietf-interfaces:interfaces              接口容器
/restconf/data/ietf-interfaces:interfaces/interface=eth0        一个列表项
/restconf/data/ietf-interfaces:interfaces/interface=eth0/mtu    一个叶子

# 多主键：按 YANG 里 key 语句的顺序，用逗号分隔
/restconf/data/ex:routes/route=10.0.0.0,24

# 主键值里有 / : = , 等字符时必须百分号转义 —— 高频踩坑点
#   接口名 GigabitEthernet0/0/1 →  GigabitEthernet0%2F0%2F1
/restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet0%2F0%2F1
三个几乎人人踩过的路径坑：① 列表项用 = 而不是 /——写成 /interface/eth0 会被解析成「interface 容器下有个叫 eth0 的子节点」，返回 400 而不是 404，报错完全不提示真实原因。② 只有路径的第一个节点带模块名，后面的子节点不带；但如果某个子节点是别的模块 augment 进来的，那一节又要带上它自己的模块名——这一条最容易漏。③ 接口名里的斜杠必须转义，而且有些实现对已转义的 %2F 在反代理层会被二次解码，导致「本地 curl 能通、走网关不通」。

HTTP 方法怎么映射到 NETCONF 操作

HTTP 方法作用大致对应的 NETCONF 语义要点
GET读资源（配置或状态）get-config / get用 ?content=config|nonconfig|all 区分只读配置还是含状态
HEAD只取响应头—拿 ETag / Last-Modified 做变更检测，不传正文
OPTIONS查询该资源支持哪些方法—判断某节点是否可写（是不是 config false）的便捷手段
POST在父资源下创建子资源；或在 /operations 下调用 RPCedit-config operation="create"；<rpc>目标已存在返回 409 Conflict，这是「创建」语义的体现
PUT整体替换（不存在则创建）operation="replace"幂等；未出现在请求体里的兄弟节点会被删掉，这一点最容易误伤
PATCH合并（plain patch）operation="merge"只改提到的部分；配 RFC 8072 的 YANG Patch 可做「有序的多操作列表」
DELETE删除资源operation="delete"不存在时返回 404（对比 remove 的「不存在也算成功」）

PUT 与 PATCH 的区别在网管场景里是会出事故的级别。PUT 是「这个资源现在就是请求体描述的样子」——请求体里没写 enabled，设备就会把 enabled 恢复成 YANG 里的默认值或直接删掉。真实事故形态：自动化脚本用 PUT 去「改一下 MTU」，请求体里只带了 name 和 mtu，结果把该接口的 IP 地址、描述、VRF 绑定全清了。判据很简单：「我要的是替换还是修改？」——除了「以这份配置为准，多余的都删掉」这种明确的声明式下发，其余一律用 PATCH。而 NETCONF 里同一个区别是显式的 operation="replace" vs "merge"，写的人会警觉；HTTP 的 PUT 因为太熟悉反而容易失去警觉。

相对 NETCONF，RESTCONF 丢了什么

这是选型时真正要判断的部分。RFC 8040 是有意做减法的——它不是能力不足，而是为了让映射到 HTTP 这件事成立而主动放弃了一些语义。丢掉的东西有四样：

NETCONF 有RESTCONF 的情况实际后果
<candidate> 草稿区 + 多次编辑后一次 commitRFC 8040 没有定义 candidate 的访问方式；每个请求各自是一个独立事务，立即生效跨多个资源的变更无法原子化。要改 3 个接口 + 1 条路由，就是 4 个请求、4 次生效，中间状态真实存在于设备上
lock / unlock 显式独占没有锁 RPC，只有基于 ETag / Last-Modified + If-Match / If-Unmodified-Since 的乐观并发能检测到「我读之后别人改过」并拒绝（412），但无法阻止别人在我的多步操作中间插入变更。多系统并发下发时需要外部协调
confirmed-commit + 超时自动回滚标准里没有对应机制没有 lockout 保护——改错管理通道就是现场处理。这是 RESTCONF 做高风险变更最大的顾虑
validate 单独校验、test-option=test-only 干跑没有标准的「只校验不生效」入口只能发出去看返回码，校验与生效是同一个动作
公平地说，RESTCONF 也拿到了三样 NETCONF 没有的东西，别只讲它丢了什么：
① 集成成本趋近于零——任何语言的 HTTP 客户端、任何 API 网关、任何 CI 流水线里的 curl 都能用；调试时浏览器直接打开路径就能看到 JSON。
② 复用整套 HTTP 基础设施——反向代理、OAuth/JWT 认证、限流、审计日志、缓存（ETag 天然支持条件请求）、可观测性工具全都现成。NETCONF over SSH 在这些方面基本是一片空白。
③ 细粒度寻址天然便宜——「只读某一个叶子」在 RESTCONF 里就是一个 URL，在 NETCONF 里要构造一段 subtree filter 或 XPath。配合 fields / depth 查询参数，读小块数据比 NETCONF 轻。
所以判据是：写操作的风险等级决定要不要 NETCONF。「查询状态、下发单个低风险参数、给业务系统开一个自助接口」→ RESTCONF 足够且更省；「一次改动横跨多个子系统、改错会断业务、需要审计与回滚」→ 必须 NETCONF。

gNMI

为流式遥测而生

  • 建模：YANG（用 OpenConfig 模型居多）。承载：gRPC + Protobuf（HTTP/2）。
  • 强：Subscribe 流式遥测（设备按周期/变化持续推指标）——比 SNMP 轮询高效得多；二进制编码紧凑、性能好。
  • 操作：Get / Set / Subscribe / Capabilities。
  • 场景：大规模数据中心、云原生网络、需要高频监控的场合。
gNMI 的 Subscribe 是它相对 NETCONF/SNMP 的杀手锏：几万台设备每秒推一次关键指标，用 gRPC 流比逐个 poll 高效得多。

gNMI（gRPC Network Management Interface）是 OpenConfig 社区的规范，不是 IETF RFC——这一点在面试里值得主动说明，因为它解释了 gNMI 的两个特征：迭代快（版本号一直在走）、以及厂商实现差异比 IETF 协议大得多（没有 RFC 那种严格的 MUST/SHOULD 约束与互操作测试传统）。它跑在 gRPC over HTTP/2 上，通常强制 TLS；IANA 为 gNMI/gNOI 登记的端口是 9339，但现网厂商常用别的端口（如 57400），以设备文档为准。

四个 RPC：整个协议就这么大

RPC方向 / 流式做什么对应到别的协议
Capabilities一问一答返回设备支持的 YANG 模型列表（名字+版本+组织）、支持的编码、gNMI 版本≈ NETCONF <hello> 的能力交换；≈ RESTCONF 的 yang-library
Get一问一答按 path 取一次数据。可指定 type = ALL / CONFIG / STATE / OPERATIONAL≈ NETCONF get / RESTCONF GET
Set一问一答一次请求里带 delete / replace / update 三个列表，规范要求整体作为一个事务生效，顺序是删→替→更≈ NETCONF 单次 edit-config（但没有 candidate 与 confirmed-commit）
Subscribe双向流设备持续推送数据变化或周期采样，一条连接承载多个订阅没有对等物——这是 gNMI 独有的价值
「gNMI 的 Set 有事务吗？」这是一道很好的分辨题。答案是「单次 Set 请求内部有原子性，但没有跨请求的事务框架」。规范要求 target 把一个 SetRequest 里的所有 delete/replace/update 当作一个事务处理——要么全成要么全不成，失败时返回的 SetResponse 里逐个操作带结果。但它没有 candidate 草稿区（无法分多次攒改动）、没有 validate（无法只校验不生效）、也没有 confirmed-commit（无法超时自动回滚）。所以 gNMI 的配置能力大致相当于「NETCONF 的一次 edit-config + 立即 commit」——够用于声明式的整体下发（把设备的目标状态一次性 replace 进去），不够用于需要人工确认窗口的高风险变更。这也是为什么第 7 章的决策树里，「需要事务性配置」那一支指向 NETCONF 而不是 gNMI。

Path 与编码：为什么它比 XML 省这么多

# gNMI 的 Path 不是字符串，是结构化的 elem 列表（Protobuf message）
path: {
  elem: { name: "interfaces" }
  elem: { name: "interface"  key: { key: "name" value: "eth0" } }
  elem: { name: "state" }
  elem: { name: "counters" }
  elem: { name: "in-octets" }
}
# 人类书写时用 XPath 风格的简写，工具会转成上面的结构：
/interfaces/interface[name=eth0]/state/counters/in-octets

# 关键优化：prefix 只发一次，后续 update 只带相对路径
notification: {
  timestamp: 1773296420123456789      ← 纳秒级 Unix 时间戳，设备侧打的
  prefix: { elem:{name:"interfaces"} elem:{name:"interface" key:{key:"name" value:"eth0"}} }
  update: { path:{elem:{name:"state"} elem:{name:"counters"} elem:{name:"in-octets"}}
            val:{ uint_val: 84719203411 } }
  update: { path:{elem:{name:"state"} elem:{name:"counters"} elem:{name:"out-octets"}}
            val:{ uint_val: 61203998172 } }
  update: { path:{elem:{name:"state"} elem:{name:"oper-status"}}
            val:{ string_val: "UP" } }
}

省下来的字节来自四处，值得逐条看清——因为这解释了「为什么差一个数量级」不是营销话术：

  • Protobuf 的字段是编号而不是名字。XML/JSON 每条数据都要重复写一遍 key 的字符串；Protobuf 写的是一个 varint 标签号。<in-octets>84719203411</in-octets> 是 37 字节，同样的信息在 Protobuf 里是「字段号 + varint 值」不到 10 字节。
  • prefix 提取了公共路径。一台设备一次推 200 个接口计数器，路径的前半段 /interfaces/interface[name=X] 只写一次。路径字符串在遥测数据里往往比数值本身还长，这一项的节省非常可观。
  • 连接复用，没有请求报文。SNMP 的每个数值背后都有一个请求 PDU + 一个响应 PDU + 各自的 UDP/IP 头。gNMI Subscribe 建立一次连接后，上行方向除了 TCP ACK 与 HTTP/2 的窗口更新，什么都不发。
  • HTTP/2 层还有 HPACK 头压缩与可选的 gRPC 消息压缩（gzip），对重复性极高的遥测流特别有效。
编码（encoding）选项：Capabilities 返回设备支持哪些编码，常见的有 JSON、JSON_IETF（按 RFC 7951 规则序列化 YANG 数据的 JSON）、PROTO（用 TypedValue 直接承载标量，最省）、BYTES、ASCII。Subscribe 场景应当优先选 PROTO；Get/Set 用 JSON_IETF 便于调试与跨实现互通。一个高频坑：某些实现只在 Get 上支持 JSON_IETF，Subscribe 只支持 PROTO，先跑 Capabilities 确认再写代码。

Subscribe 的三种模式：这才是杀手锏

订阅的模式分两层，这个两层结构是初学者最容易搞混的地方：

# 第一层：SubscriptionList.mode —— 整个订阅列表的性质
ONCE    发一次全量快照，然后服务端关闭这条流。
        用途：一次性巡检、拉基线、CI 里做断言。等价于一个"流式的 Get"。

POLL    保持连接不断，但设备不主动发；客户端每发一个 PollRequest，
        设备就回一次当前值。用途：客户端想自己控制节奏、
        或采集周期不规则（比如只在人点开 dashboard 时才取）。

STREAM  设备主动持续推送。真正的流式遥测就是这一档。

# 第二层：仅当 mode=STREAM 时，每个 Subscription 各自再选一种
SAMPLE          按 sample_interval（纳秒）周期上报，不管有没有变化。
ON_CHANGE       只在值发生变化时上报；不变就一个字节都不发。
TARGET_DEFINED  把选择权交给设备——由设备按该 path 的性质自行决定用
                SAMPLE 还是 ON_CHANGE。（实现差异最大的一档，生产建议显式指定）

SAMPLE 与 ON_CHANGE 怎么选

这是 gNMI 落地时最实际的一道选择题，判据是数据的性质而不是「想省多少带宽」：

数据性质例子该用理由
单调递增的计数器in-octets in-errors in-pktsSAMPLE计数器几乎每毫秒都在变，ON_CHANGE 等于「变了就推」= 无限高频。而且你要的是速率，速率必须由两个等间隔的样本求差——不等间隔的样本算速率误差很大
离散状态 / 枚举oper-status admin-status BGP session-state LACP 成员状态ON_CHANGE平时完全不变，一年可能只跳两次。SAMPLE 是在白推同一个值几百万次；更重要的是 SAMPLE 抓不到短于采样间隔的抖动（10 秒间隔看不见一次 300 ms 的 flap，而这恰恰是你最想知道的）
缓变的模拟量温度、光功率、电压、CPU 使用率SAMPLE（间隔可放宽）浮点值会持续微幅抖动，ON_CHANGE 相当于全速推送；这类数据要的是趋势，30–60 秒一个点足够
配置类数据接口描述、路由策略、VLAN 成员ON_CHANGE只在有人下发配置时才变，是 ON_CHANGE 最理想的对象；可以据此做「配置漂移检测」
列表的增删邻居表、MAC 表、ARP 表条目看规模小表用 ON_CHANGE；大表（几十万条 MAC）用 ON_CHANGE 会在表震荡时直接打爆采集器，要么 SAMPLE 要么只订阅聚合计数
ON_CHANGE 的三个陷阱，一个比一个隐蔽：
① 「没数据」和「没变化」在协议上长得一样。一个订阅了 oper-status 的 ON_CHANGE 流，可能三天没有任何消息——这既可能是「一切正常」，也可能是「设备的订阅早挂了」。解决办法是必须配 heartbeat_interval：即使值没变，也强制每 N 秒推一次当前值，作为「我还活着」的心跳。不配心跳的 ON_CHANGE 订阅在生产上是不可接受的。
② 厂商对「什么算变化」的判定不一致。严格实现是「值不同才推」，宽松实现是「底层数据结构被更新过就推」——后者对一个每秒被刷新的字段等于全速推送。suppress_redundant 这个标志正是为了让客户端要求「重复值不要推」，但不是所有实现都遵守它。上线前必须实测：订一个稳定不变的 path，看一小时内到底收到几条消息。
③ ON_CHANGE 支持范围因设备而异。规范允许 target 对不支持 ON_CHANGE 的 path 返回错误，但有的实现会静默降级成 SAMPLE、甚至静默接受后什么都不发。这就是第 7 章案例里「订阅成功但没数据」的一类根因。

关于 sync_response 这个容易被忽略的细节：Subscribe 建立后，设备会先把订阅路径下的当前全量值推一遍，推完发一条 sync_response: true 的消息，此后才是增量。采集器必须处理这个边界——在收到 sync_response 之前，你手里的是一份正在填充的不完整快照，不该拿去算「有多少接口 down 了」这类需要全量的判断。反过来，updates_only 这个请求标志可以要求设备跳过初始全量，只发后续变化，用于重连后不想再收一遍全量的场景。

模型与协议解耦：同一份 YANG 被三种协议承载

第 1 章埋下的那条线索现在可以展开了。四个协议里，三个用同一种建模语言（YANG），只有 SNMP 用自己的 MIB。这不是巧合，而是 2000 年代那一轮反思的直接结果：SNMP 把「数据长什么样」和「怎么传数据」焊死在一起了，导致想改传输就必须重新建模，二十年的 MIB 资产一分钱都带不走。

生活类比：菜谱与快递。YANG 是菜谱——写清一道菜有哪些配料、每样多少克、哪两样不能同时放。NETCONF / RESTCONF / gNMI 是三家快递公司：一家用木箱装（XML，结实但重）、一家用纸箱（JSON，通用好拆）、一家用真空压缩袋（Protobuf，最省体积）。菜谱一份就够，换快递公司不用重写菜谱。而 SNMP 的问题是「菜谱是印在木箱内壁上的」——想换纸箱，菜谱就没了。

/* 同一份 YANG 定义（片段，简化自 ietf-interfaces / RFC 8343） */
module ietf-interfaces {
  container interfaces {
    list interface {
      key "name";
      leaf name    { type string; }
      leaf enabled { type boolean; default "true"; }
      leaf mtu     { type uint16; }
      leaf oper-status {
        type enumeration { enum up; enum down; enum testing; }
        config false;      /* ← 这一句就是"状态 vs 配置"的分界 */

    }
  }
}

这个解耦带来的实际收益是具体的：

  • 校验逻辑可以复用。管理侧用 pyang / yanglint 从 YANG 生成校验器，无论下发走哪个协议，发之前本地就能判定合法。SNMP 时代这一步只能靠「发下去看设备报不报错」。
  • 代码可以生成。YANG → Python/Go 类、YANG → gNMI path 常量、YANG → 数据库 schema，都是成熟做法。这是「模型驱动」能省人力的根本原因。
  • 迁移不用重建资产。从 NETCONF 加一路 gNMI 遥测时，你要写的是新的采集器，不是新的数据字典。指标名字、层级、语义全都对得上，两路数据能落到同一张表里。这一条在第 7 章的迁移案例里是能不能平滑并存的关键。

OpenConfig 的 /config 与 /state 双子树是个值得单独理解的设计。IETF 的做法是在同一棵树上用 config false 标注哪些叶子是只读的；OpenConfig 的做法是把同名的叶子在 /config 和 /state 下各放一份——/interfaces/interface[name=eth0]/config/mtu 是「我要求的 MTU」，/interfaces/interface[name=eth0]/state/mtu 是「设备实际生效的 MTU」。好处是「意图 vs 实际」的对比变成了一次纯粹的路径比较，配置漂移检测极其简单；代价是模型体积几乎翻倍，而且订阅时必须想清楚你要的是哪一边（订错了会得到「配置改了但指标没动」的困惑）。
「大家都用 YANG」不等于「大家能互通」——这是模型驱动最大的一个认知陷阱。三个机制会让同名模型的实际行为不同：
① deviation：厂商用它合法地声明「标准模型里的这一部分我不支持」（不支持某叶子、缩小取值范围、改成只读）。所以设备声明支持 openconfig-bgp 6.1.0，不代表这个模型里的每个节点都能用。
② augment：厂商往标准模型里挂私有扩展。你的代码如果对未知节点不宽容，换个厂商就解析失败。
③ feature / if-feature：模型里声明为可选特性的部分，设备可以选择不实现。
实操结论：不要相信文档说的「支持 OpenConfig」，要跑 Capabilities 拿到真实的模型+版本清单，再对关键 path 逐个实测。版本号也要盯——OpenConfig 的大版本变更改过路径结构，同一段采集代码在两个软件版本的同型号设备上取不到数据，是很常见的现场问题。

遥测规模的量化：轮询 vs 流式差在哪

「流式比轮询高效一个数量级」这句话要能算出来才有说服力。取一个标准场景：1000 台设备 × 每台 200 个计数器 × 10 秒采集间隔。目标数据量是固定的：1000 × 200 / 10 = 20 000 个数值/秒。差别全在「为了送达这 2 万个数值，各自要付多少」。

上面的字节数只差 3 倍，为什么说「强一个数量级」？因为带宽从来不是 SNMP 轮询的瓶颈——瓶颈在报文数与设备 CPU，而这两项差的正是一个数量级以上。三个层面：
① 往返次数从 800/s 降到 0。每一次 GetBulk 都要 agent 在收到请求时才去内部数据结构里做「找比这个 OID 大的下一个实例」，很多实现是持锁的线性扫描；而 gNMI 是设备按自己的定时器批量导出，可以走内部的高效路径、可以流水线化、不与管理侧的往返耦合。
② 负载从「瞬时尖峰」变成「均匀流」。轮询天然把负载压在采集周期的边界上；流式是设备各自按自己的相位往外推，天然打散。
③ 失败模式反了过来。轮询在设备繁忙时采集成功率下降（越需要数据越拿不到），且重试会加压；流式在设备繁忙时最坏也只是推送延迟，而且管理侧不施加任何额外负载。

最后一行才是流式遥测真正的价值所在，而它经常被「省带宽」这个说法掩盖。轮询模型有一个无法绕过的信息论限制：采样间隔决定了你能观察到的最快现象。30 秒轮询的监控系统，对一次 2 秒的链路 flap、一次 500 ms 的队列爆满、一次瞬时的 CPU 打满，不是「看得不准」，而是完全不知道它发生过——而这些恰恰是最难排查的故障。ON_CHANGE 把这个限制拿掉了：状态跳变由设备在发生的那一纳秒记录并主动上报。
所以「为什么要迁 gNMI」的正确答案不是「省带宽」（省下的几 Mbps 在今天几乎不值钱），而是「让原本不可观测的现象变得可观测」。带宽和 CPU 的节省只是顺带的。

并存而不是替代：一张网里的实际分工

「新协议取代老协议」是技术博客的叙事，不是现网的样子。真实网络里四者长期并存，而且这是合理的稳态，不是没来得及迁移的历史包袱。原因有三层：

  • 能力上互补而非重叠。前面已经论证过：NETCONF 的 confirmed-commit 与 gNMI 的 ON_CHANGE 都没有替代品。一张网既要做高风险变更、又要做秒级观测，就必然要两个协议。
  • 设备侧的支持是分批到位的。同一个网络里的设备来自不同厂商、不同年代、不同产品线。核心路由器可能三个协议全支持，接入交换机只有 SNMP + CLI，机房 UPS 只有 SNMP。协议统一的前提是设备统一，而设备永远不会统一。
  • 迁移的成本落在采集侧而不是协议侧。告警规则、报表、值班手册、容量模型全都绑在现有指标名字上。把一个指标从 SNMP 换成 gNMI，协议改造是一周的工作，下游一致性验证是三个月的工作。所以理智的做法是并行采集、对比数据、逐指标切换。

并存带来的真正工作量是「归一化」。SNMP 给你 IF-MIB::ifHCInOctets.3，gNMI 给你 /interfaces/interface[name=eth1]/state/counters/in-octets——是同一个物理含义，但名字、层级、类型、时间戳语义全不同（SNMP 的时间戳是采集器收到的时刻，gNMI 是设备打的）。不做归一化，两路数据落进时序库就是两条互不相干的曲线，告警规则要写两套，切换时无法对比验证。推荐做法：定义一层内部的规范化指标名（以 OpenConfig 的路径为蓝本，因为它最贴近 YANG），SNMP 侧写映射表转过来。这样后续每台设备从 SNMP 切到 gNMI 时，下游一行都不用改。
真实案例形态：某网管系统从 SNMP 轮询迁到 gNMI 流式。
动机：约 1200 台设备、30 秒 SNMP 轮询间隔，采集器 CPU 常态 70%，且业务侧反复投诉「链路 flap 在监控上看不到」——因为 flap 时长普遍在数秒，落在两个采样点之间。目标是把接口与 BGP 状态改成 ON_CHANGE、计数器改成 10 秒 SAMPLE。
收益（切换完成后实测量级）：① 状态跳变从「30 秒内某个时刻」变成带纳秒时间戳的精确时刻，跨设备的 flap 因果链第一次能排出顺序，这是最大的收益；② 采集器的报文处理量下降约一个数量级，CPU 从 70% 降到 20% 以下，腾出的余量直接用来把计数器间隔从 30 秒缩到 10 秒；③ 设备侧 CPU 在采集时段的抬升消失（不再有周期性的 MIB 全表遍历）。
踩的坑，按代价从大到小：
① 模型不一致（最贵）。三个厂商都声称支持 OpenConfig，但路径细节有差：一家把光模块功率挂在 openconfig-platform 的组件树下，一家挂在自己 augment 出来的私有分支里；同一个 oper-status 的枚举取值大小写不统一。处置：先跑 Capabilities 拿到真实模型清单，再对每个关键 path 逐设备型号实测，把差异收进一张映射表——这张表的维护成本被严重低估了，它是这个项目里最持久的技术债。
② 设备实现参差。有型号声明支持 ON_CHANGE 但对某些 path 静默降级成 SAMPLE；有型号在订阅路径用通配符（[name=*]）时只返回第一个实例；有型号软件版本升级后路径结构变了，采集静默变空。处置：把「每个订阅的消息速率」本身做成监控指标——一个 ON_CHANGE 订阅长期零消息、或一个 SAMPLE 订阅的消息速率与预期不符，都要告警。不监控采集链路本身，是这类迁移最容易犯的错。
③ 订阅风暴。一次机房断电恢复，1200 台设备在几秒内同时重连并各自推送初始全量快照，采集器入口瞬时流量是稳态的几十倍，直接 OOM；重启后又被打一遍，形成崩溃循环。根因是「初始同步的全量」这一笔成本在容量规划里被完全忽略了——稳态很省，冷启动很贵。
处置（这三条是通用的防护手段）：(a) 重连退避 + 抖动，采集器侧对每台设备的连接建立做随机延迟与指数退避，绝不允许同时重连；(b) 分片与限流，按设备分片到多个采集实例，每个实例限制并发订阅建立数与入口消息速率，超出先落盘缓冲；(c) 用 updates_only 跳过不必要的全量，对已有基线的订阅重连后只要增量。另外把订阅拆细也有帮助——不要用一个订阅把整棵 /interfaces 订下来，只订真正要用的叶子，初始全量的体积直接小一个量级。
最终形态：SNMP 没有下线。UPS、空调、以及两个老型号接入交换机仍走 SNMP；SNMP trap 继续作为 gNMI 的兜底告警通道（订阅挂了时它还在）。两路数据在采集侧归一化成同一套指标名，下游完全不感知数据来自哪个协议。这个「并存 + 归一化」的结果不是妥协，而是当初就应该定的目标。
面试："NETCONF vs SNMP 有什么区别？"
答：SNMP 强于监控轮询、弱于配置、无事务、安全弱、MIB 建模；NETCONF 用 YANG 建模、强于复杂配置、有事务(candidate/commit)、走 SSH/TLS 更安全。现代网络配置管理已从 SNMP 转向 NETCONF/gNMI，SNMP 主要留在存量监控。

  1. 基础为什么 SNMP 适合做监控，却不适合做配置？

    因为 SNMP 的设计取舍在读路径上全部是优点，在写路径上全部是缺点。「安全性差」只是最表层的原因，而且 SNMPv3 已经解决了。真正致命的有四层：

    MIB 表达力不够
    SMIv2 只有标量和平表两种结构，表不能嵌套表；而真实配置天生是深层嵌套的（接口→子接口→地址→VRF→路由策略）。更关键的是 MIB 没有约束表达能力：没法声明「字段 A 只在字段 B 等于某值时有意义」（YANG 的 when）、「这两个字段必须同配」（must）、「这个字段引用另一张表的行」（leafref）。所以 MIB 能描述「有哪些旋钮」，描述不了「哪些旋钮组合合法」。
    SET 没有跨 PDU 的事务
    规范上同一个 SET PDU 内的多个 varbind 要求原子生效（RFC 1905 有 undoFailed 错误码正是描述部分生效后回滚失败），但这个原子性的作用范围只有一个 PDU，而 UDP 报文装不下一次真实变更。跨 PDU 之间没有 candidate、没有 validate、没有 commit/rollback、没有 confirmed-commit。5 个 SET 里第 3 个失败 → 前两个已生效，设备处在你没设计过的中间状态，而且因为 UDP 你甚至不能确定前两个到底成不成功。
    建行删行靠 RowStatus 打补丁
    MIB 的表本来没有「创建一行」这个操作。RFC 2579 用一个整数列 RowStatus 模拟：写 createAndGo(4) 建行并激活、createAndWait(5) 先建后填、active(1) 激活、destroy(6) 删除。把状态机塞进一个数据字段——管理侧在 createAndWait 后崩掉，设备上就永久留一行 notReady 的僵尸配置，没有超时清理。
    没有「意图 vs 实际」的区分
    SNMP 只有一个数据视图：设备当前的实际值。而配置管理必须能同时读到「我配的」和「实际生效的」（我配了 admin-up 但光模块没插所以 oper-down）。IF-MIB 靠 ifAdminStatus/ifOperStatus 两列在接口这一处手工模拟了，其他地方一律混在一起。YANG 用 config true/false 从建模层面解决了它。

    反过来说读路径：UDP 无连接状态所以 agent 极轻、一次往返就完事、覆盖率压倒性、只读账号的最坏后果是信息泄露而不是断网——这些正是它统治监控二十年的原因。

  2. 基础SNMPv3 解决了什么、没解决什么？

    解决了（全部集中在安全这一件事上）：

    • USM（User-based Security Model）：凭证从明文 community 变成「用户名 + 认证密钥 + 加密密钥」，认证用 HMAC-MD5/SHA 系列，加密用 DES / AES（RFC 3826 起）。凭证与内容都不再明文过网。
    • VACM（View-based Access Control Model）：授权从「读 community / 写 community」二选一，变成「用户 → 组 → 视图」的三级映射，视图可以精确到 OID 子树——只读账号真的读不到敏感的私有分支。
    • 重放防护：用 engineID + engineBoots + engineTime 构成时间窗，超窗的报文被丢弃。

    没解决（这部分才是加分项）：

    配置能力一点没变
    SET 还是那个 SET，MIB 还是那个 MIB。上一题的四层原因里，v3 一条都没碰。「SNMP 不适合配置」这个结论在 v3 之后完全不变。
    密钥管理自成一套
    不接 PKI、不接 RADIUS/TACACS+、没有证书吊销机制。密钥要在每台设备上单独配置，几千台设备轮换一次密钥是一个项目而不是一条命令。对比 gNMI 直接用 TLS 证书体系。
    engineID 本地化的运维坑
    USM 密钥要与设备的 engineID 做本地化（localization）。设备换主控或重置后 engineID 变了，之前配好的所有用户全部失效——现象是「设备好着呢，但网管突然采不到了」，而且看起来像网络问题。
    复杂度导致降级使用
    -l 有三档：noAuthNoPriv（只有用户名，等于白开 v3）、authNoPriv（验身份但内容仍可抓包读）、authPriv（生产唯一可接受）。现网大量「配了 v3 但用 noAuthNoPriv」——复杂度全付了，安全收益为零。
  3. 基础NETCONF 的事务模型由哪几件东西组成？价值在哪？

    组成部分与各自作用：

    • <candidate> datastore：可反复编辑的草稿区，改多少次都不影响转发面。
    • lock / unlock：独占 datastore，防止两个自动化系统同时改同一处。
    • validate：提交前做整体一致性校验（引用完整性、must / when 约束），失败就不用 commit。
    • commit：candidate 原子性地整体落到 <running>。
    • rollback-on-error（error-option）：单次 edit-config 内部出错即整体撤销，不留半套改动在 candidate 里。
    • confirmed-commit + confirm-timeout：提交后启动定时器，超时未收到第二次 commit 就自动回滚。

    价值不在「方便」，而在它消除了「中间状态」这一整类故障。SNMP 的写模型是「一格一格改、改一格立即生效」，所以一次多步变更中途失败必然留下一个你没设计过的设备状态；NETCONF 把整套改动做成一次原子跃迁，要么完整生效，要么一个字节都没变。

    加分：把 confirmed-commit 单独拎出来讲管理通道自锁（lockout）。远程改管理口 ACL 或路由，配置语法合法、校验通过、commit 成功，然后你的 SSH 断了——事务模型此时救不了你，因为事务是成功的，错的是配置的语义。confirmed-commit 的思想是「用能否再次通信作为变更成功的判据」：连不上来就意味着没人来确认，设备自己恢复旧配置。它比任何外部看护脚本都可靠，因为它跑在设备自己身上，不依赖任何外部系统还活着。

  4. 基础RESTCONF 相对 NETCONF 丢掉了什么？

    RFC 8040 是有意做减法的——不是能力不足，而是为了让「映射到 HTTP」这件事成立。丢掉四样：

    丢掉的RESTCONF 的替代实际后果
    <candidate> + 多次编辑一次 commit没有；每个 HTTP 请求各自是一个独立事务，立即生效跨多个资源的变更无法原子化。改 3 个接口 + 1 条路由 = 4 次请求 4 次生效，中间状态真实存在
    lock / unlock 显式独占乐观并发：ETag / Last-Modified + If-Match / If-Unmodified-Since，冲突返回 412能检测「我读之后别人改过」，但无法阻止别人在我的多步操作中间插入变更
    confirmed-commit没有没有 lockout 保护，改错管理通道就是现场处理
    独立的 validate / test-only 干跑没有标准入口校验与生效是同一个动作，只能发出去看返回码

    公平地讲也拿到了三样：① 集成成本趋近于零（任何 HTTP 客户端、API 网关、CI 里的 curl 都能用）；② 复用整套 HTTP 基础设施（反代、OAuth/JWT、限流、审计、ETag 条件请求、可观测性）；③ 细粒度寻址天然便宜（读一个叶子就是一个 URL，配 fields / depth 裁剪，比构造 NETCONF 的 subtree filter 轻）。

    判据：写操作的风险等级决定要不要 NETCONF。查状态、下发单个低风险参数、给业务系统开自助接口 → RESTCONF；一次改动横跨多个子系统、改错断业务、要审计与回滚 → 必须 NETCONF。

8.2 中级（区分熟练度）

  1. 中级gNMI 有哪四个 RPC？它的 Set 有事务性吗？
    • Capabilities（一问一答）：返回设备支持的 YANG 模型清单（名字+版本+组织）、支持的编码、gNMI 版本。任何 gNMI 集成的第一步都应该是它——文档说的和设备实际支持的经常不一致。
    • Get（一问一答）：按 path 取一次数据，可用 type 指定 ALL / CONFIG / STATE / OPERATIONAL。
    • Set（一问一答）：一个请求里带 delete / replace / update 三个列表，执行顺序是删 → 替 → 更。
    • Subscribe（双向流）：设备持续推送，一条连接承载多个订阅。这是四个里唯一没有对等物的。

    Set 的事务性：单请求内部有原子性，但没有跨请求的事务框架。规范要求 target 把一个 SetRequest 里的所有操作当作一个事务——要么全成要么全不成，SetResponse 里逐操作返回结果。但它没有 candidate（无法分多次攒改动）、没有 validate（无法只校验不生效）、也没有 confirmed-commit（无法超时自动回滚）。

    所以 gNMI 的配置能力大致等于「NETCONF 的一次 edit-config + 立即 commit」：够用于声明式的整体下发（把目标状态一次 replace 进去，这也是数据中心 leaf/spine 的常见用法），不够用于需要人工确认窗口的高风险变更。这就是选型决策树里「需要事务性配置」指向 NETCONF 而不是 gNMI 的原因。

    再加一句：gNMI 规范本身不定义授权模型——「哪个用户能读写哪些 path」由实现决定（部分实现映射到 NACM / RFC 8341）。做安全设计时不能假设它有 VACM 那样的标准视图机制，必须逐设备确认授权粒度是「全有全无」还是「按 path」。

  2. 中级Subscribe 的模式怎么分层？ON_CHANGE 与 SAMPLE 各用在什么数据上？

    模式分两层，这是最容易搞混的地方：

    • 第一层 SubscriptionList.mode（整个订阅列表的性质）：ONCE（发一次全量快照后关流，等价于流式的 Get，适合巡检与 CI 断言）/ POLL（连接保持但设备不主动发，客户端每发一个 PollRequest 才回一次）/ STREAM（设备主动持续推，真正的流式遥测）。
    • 第二层（仅 STREAM 时，每个 Subscription 各自选）：SAMPLE（按 sample_interval 周期上报）/ ON_CHANGE（只在值变化时上报）/ TARGET_DEFINED（交给设备自行决定，实现差异最大，生产建议显式指定）。

    选择判据是数据的性质，不是「想省多少带宽」：

    数据性质例子用理由
    单调递增计数器in-octets in-errorsSAMPLE计数器几乎每毫秒都在变，ON_CHANGE 等于无限高频；而且你要的是速率，速率必须由等间隔样本求差
    离散状态 / 枚举oper-status、BGP session-stateON_CHANGE平时完全不变，SAMPLE 是白推同一个值几百万次；更重要的是 SAMPLE 抓不到短于采样间隔的抖动（10 s 间隔看不见 300 ms 的 flap，而那恰恰是你最想知道的）
    缓变模拟量温度、光功率、CPU 使用率SAMPLE（间隔放宽）浮点值持续微幅抖动，ON_CHANGE 等于全速推；这类数据要的是趋势
    配置类数据接口描述、VLAN 成员ON_CHANGE只在有人下发时才变，最理想的 ON_CHANGE 对象，可据此做配置漂移检测
    大列表增删MAC 表、ARP 表看规模小表 ON_CHANGE；几十万条的表在震荡时会直接打爆采集器，改 SAMPLE 或只订聚合计数

    ON_CHANGE 的三个陷阱（加分点）：① 「没数据」和「没变化」在协议上长得一样——三天没消息既可能是一切正常，也可能是订阅早挂了；必须配 heartbeat_interval，不配心跳的 ON_CHANGE 订阅在生产上不可接受。② 厂商对「什么算变化」判定不一——严格实现是值不同才推，宽松实现是底层被更新过就推；suppress_redundant 标志正是为此，但不是所有实现都遵守，上线前要实测「订一个稳定不变的 path，一小时收到几条」。③ 支持范围因设备而异，有实现会静默降级成 SAMPLE、甚至静默接受后什么都不发。

  3. 中级为什么流式遥测比轮询强一个数量级？请算给我看。

    取标准场景：1000 台设备 × 200 计数器 × 10 秒间隔。目标数据量固定：20 000 数值/秒。差别全在「为了送达这 2 万个数值各自付多少」。

    SNMP GetBulk（max-repetitions=25）：每台每周期 8 次请求 → 1000 × 8 / 10 = 800 req/s，加响应共 1600 pps。单 varbind 线上体积约 25–40 B（OID 12–14 B + 类型长度 + 值），总计约 0.75 MB/s ≈ 6 Mbps，另有每秒 800 次 agent 侧 MIB 树查找。

    gNMI STREAM/SAMPLE（PROTO 编码）：1000 条长连接，请求速率 0（订阅只发一次）。prefix 提取了公共路径，单个 update 约 8–15 B，总计约 0.25 MB/s ≈ 2 Mbps；每台每周期打包成 1–2 个 Notification → 报文速率 100–200 pps。

    关键是要指出：字节数只差约 3 倍，但带宽从来不是瓶颈——瓶颈在报文数与设备 CPU，而这两项差一个数量级以上。三个层面：

    往返次数 800/s → 0
    每次 GetBulk 都要 agent 在收到请求时才去内部结构里找「比这个 OID 大的下一个实例」，很多实现是持锁线性扫描；gNMI 是设备按自己的定时器批量导出，可走内部高效路径、可流水线化、不与管理侧往返耦合。
    尖峰 → 均匀流
    轮询天然把负载压在采集周期边界（不加 jitter 时一千台同时被查）；流式是各设备按自己的相位推，天然打散。
    失败模式反了过来
    轮询在设备繁忙时采集成功率下降（越需要数据越拿不到），重试还会加压形成正反馈；流式最坏只是推送延迟，而且管理侧不施加任何额外负载。
    真正的价值（这句最重要）
    轮询有一个信息论限制：采样间隔决定了能观察到的最快现象。30 秒轮询对一次 2 秒的 flap、一次 500 ms 的队列爆满，不是「看不准」，而是完全不知道它发生过——而这恰恰是最难排查的故障。ON_CHANGE 把这个限制拿掉了：跳变由设备在发生的那一纳秒记录并主动上报。所以「为什么迁 gNMI」的正确答案是「让原本不可观测的现象变得可观测」，省带宽只是顺带的。
  4. 中级同一份 YANG 怎么被 NETCONF / RESTCONF / gNMI 三个协议复用？

    因为 YANG 是建模语言，不是协议——它只描述「数据长什么样」，不规定「怎么传」。三个协议各自定义了一套寻址与序列化规则，把同一棵 YANG 数据树映射到自己的表达形式：

    协议寻址方式序列化
    NETCONFsubtree filter 或 XPath（XML 结构本身就是路径）XML
    RESTCONFURL 路径：/restconf/data/<module>:<node>/<list>=<key>/<leaf>JSON（RFC 7951 规则）或 XML
    gNMI结构化 Path（elem 列表 + key map），书写时用 /a/b[k=v]/c 简写Protobuf（或 JSON_IETF）

    关键：三者的模型定义、类型约束、默认值、config true/false 划分完全一样。换协议要改的是客户端的寻址与序列化代码，不是数据建模。这个解耦带来三个具体收益：校验逻辑可复用（用 pyang/yanglint 从 YANG 生成校验器，发之前本地就能判定合法）；代码可生成（YANG → 语言类型 / path 常量 / 数据库 schema）；迁移不用重建资产（加一路 gNMI 遥测时要写的是新采集器，不是新数据字典，两路数据能落到同一张表里）。

    对比 SNMP 就能看出这个设计的价值：SNMP 把「数据长什么样」和「怎么传」焊死在一起了——MIB 是 SNMP 自带的建模方式，两者绑死。想换传输就必须重新建模，二十年的 MIB 资产一分钱都带不走。这也是为什么 SNMP 到 YANG 世界的迁移只能重写而不能映射。

    加分：指出 gNMI 的路径省略了模块名前缀（/interfaces/interface[name=eth0]），而 RESTCONF 的第一个节点必须带（ietf-interfaces:interfaces）。gNMI 用 origin 字段来处理模块/命名空间消歧，实践中多数实现默认单一 origin，所以在同时支持标准模型与私有模型的设备上路径可能撞车——这是跨厂商采集的一个隐坑。

8.3 高级（体现深度）

  1. 高级OpenConfig 与 IETF 标准模型、厂商私有模型是什么关系？「都用 YANG」就能互通吗？

    三套模型是互补的三层，不是竞争关系：

    • IETF 标准模型：IETF 工作组走 RFC 流程产出（ietf-interfaces RFC 8343、ietf-ip 8344、ietf-routing 8349、ietf-system 7317、ietf-netconf-acm 8341）。权威稳定、变更慢，覆盖偏基础层，高层业务能力覆盖有限。
    • OpenConfig：运营商与大型网络运营者主导的社区（不是标准组织）。迭代快、贴近实际运维需求，是 gNMI 遥测的事实标准模型。版本演进比 IETF 快，也更可能引入不兼容变更。
    • 厂商私有（native）：覆盖最全，通常与 CLI 一一对应，能配的都能配；但完全不可移植，换厂商等于重写。用于标准模型覆盖不到的功能。

    OpenConfig 有一个值得单独讲的设计：/config 与 /state 双子树。IETF 的做法是在同一棵树上用 config false 标注只读叶子；OpenConfig 把同名叶子在两个子树下各放一份——.../config/mtu 是「我要求的」，.../state/mtu 是「实际生效的」。好处是「意图 vs 实际」的对比退化成一次纯路径比较，配置漂移检测极其简单；代价是模型体积近乎翻倍，且订阅时必须想清要哪一边（订错了会得到「配置改了但指标没动」的困惑）。

    「都用 YANG」绝不等于「能互通」，三个机制让同名模型行为不同：

    deviation
    厂商用它合法地声明「标准模型里这一部分我不支持」——不支持某叶子、缩小取值范围、把可写改成只读。所以设备声明支持 openconfig-bgp 6.1.0，不代表该模型里每个节点都能用。
    augment
    厂商往标准模型里挂私有扩展。你的解析代码如果对未知节点不宽容，换个厂商就失败。RESTCONF 路径里这还会带来一个额外坑：被 augment 进来的子节点，那一节路径要带上它自己的模块名。
    if-feature
    模型里声明为可选特性的部分，设备可以选择不实现。

    实操结论：不要相信文档说的「支持 OpenConfig」，要跑 Capabilities 拿到真实的模型+版本清单，再对关键 path 逐个实测。版本号也要盯——OpenConfig 的大版本变更改过路径结构，同一段采集代码在同型号设备的两个软件版本上取不到数据，是很常见的现场问题，而且失败形态往往是「静默返回空」而不是报错。

  2. 高级为什么真实网络里四个协议是并存的稳态，而不是逐步替代？

    「新协议取代老协议」是技术博客的叙事。并存是合理的稳态，理由有三层，从强到弱：

    ① 能力上互补而非重叠（最硬的理由）
    NETCONF 的 confirmed-commit 与 gNMI 的 ON_CHANGE 都没有替代品。前者是唯一能防管理通道自锁的协议级机制，后者是唯一能精确记录状态跳变时刻的手段。一张网既要做高风险变更、又要做秒级观测，就必然要两个协议——这不是历史包袱，是需求本身决定的。
    ② 设备侧的支持永远是分批到位的
    同一张网里的设备来自不同厂商、年代、产品线。核心路由器可能三个协议全支持，老接入交换机只有 SNMP + CLI，机房 UPS / PDU / 精密空调 / 光配线传感器只有 SNMP。协议统一的前提是设备统一，而设备永远不会统一。
    ③ 迁移成本落在采集侧而不是协议侧
    告警规则、报表模板、值班手册、容量模型全绑在现有指标名字上。把一个指标从 SNMP 换成 gNMI，协议改造是一周的工作，下游一致性验证是三个月的工作。所以理智的做法是并行采集、对比数据、逐指标切换。

    典型的现网分工：核心路由器 → NETCONF 配置 + gNMI 采集 + RESTCONF 对外只读查询 + SNMP trap 兜底；数据中心 leaf/spine → gNMI Set 声明式下发 + gNMI 订阅；老接入交换机 → CLI/SNMP；O-RAN 网元 → NETCONF（O1 与前传 M 平面）+ VES 报事件与 PM 文件；环境类设备 → 只有 SNMP。

    加分点：并存带来的真正工作量是「归一化」。SNMP 给你 IF-MIB::ifHCInOctets.3，gNMI 给你 /interfaces/interface[name=eth1]/state/counters/in-octets——同一个物理含义，但名字、层级、类型、时间戳语义全不同（SNMP 的时间戳是采集器收到的时刻，含网络与排队抖动；gNMI 是设备打的纳秒时间戳）。不做归一化，两路数据落进时序库就是两条互不相干的曲线，告警规则要写两套，切换时无法对比验证。推荐做法是定义一层内部规范化指标名（以 OpenConfig 路径为蓝本，因为它最贴近 YANG），SNMP 侧写映射表转过来——这样每台设备从 SNMP 切到 gNMI 时，下游一行都不用改。

  3. 高级什么是订阅风暴？怎么防？

    订阅风暴（subscription storm）指的是大量 gNMI 订阅在短时间内同时建立或重建，导致采集侧瞬时负载远超稳态而崩溃。根因是一笔容量规划里最常被忽略的成本：每条 Subscribe 建立后，设备会先把订阅路径下的当前全量值推一遍（推完发 sync_response: true），然后才是增量。稳态很省，冷启动很贵。

    典型触发场景（都是真实会发生的）：

    • 机房断电恢复：上千台设备在几秒内同时上线并推初始全量，入口流量是稳态的几十倍。
    • 采集器自身重启/升级：所有订阅同时重建——而且如果采集器因此再次 OOM，就形成崩溃循环，这是最危险的形态。
    • 网络分区恢复：一批设备的连接同时超时重连。
    • 订阅粒度过粗：一个订阅把整棵 /interfaces 订下来，初始全量里包含大量根本不用的叶子，体积大一个量级。
    • 大列表的 ON_CHANGE：几十万条的 MAC/ARP 表在震荡时，ON_CHANGE 会把每一条增删都推出来。

    防护手段，按有效性排序：

    重连退避 + 抖动
    采集器侧对每台设备的连接建立做随机延迟 + 指数退避，绝不允许同时重连。这是成本最低、收益最大的一条。
    分片 + 限流
    按设备分片到多个采集实例；每个实例限制并发订阅建立数（不只是限入口速率——瓶颈常在建立阶段）与入口消息速率，超出的先落盘缓冲而不是丢弃或崩溃。
    updates_only 跳过初始全量
    这个请求标志让设备不推初始快照，只发后续变化。对已有基线的订阅在重连后特别有用——直接把冷启动最贵的那一笔省掉。
    订阅拆细，只订要用的叶子
    不要用一个订阅把整棵子树订下来。订到叶子级别，初始全量体积直接小一个量级，而且出问题时定位范围也小。
    把采集链路本身做成监控指标
    监控「每个订阅的消息速率」：一个 ON_CHANGE 订阅长期零消息、或一个 SAMPLE 订阅的速率与预期不符，都要告警。不监控采集链路本身，是这类系统最容易犯的错——你会在完全不知情的情况下丢数据好几周。
    保留一条不依赖订阅的兜底通道
    SNMP trap 或 NETCONF notification 继续作为关键告警的第二条路。订阅挂了的时候，你需要一个不经过订阅的方式知道这件事。
  4. 高级给一个新的网管系统做协议选型，你怎么决策？

    这是综合题，考的是判断顺序而不是结论。我会按下面的顺序走，关键是先分能力、后看成本——反过来（先看「哪个好接」）是最常见的选型错误。

    第 0 步：先摸设备，不要先选协议
    列出所有要纳管的设备类型（含 UPS、PDU、空调、光配线传感器这些容易被忘的），逐型号跑 Capabilities / <hello> 拿到真实支持的协议与模型清单，不要相信规格书。这一步的产出决定了后面所有选择的可行域——如果 40% 的设备只有 SNMP，那「统一到 gNMI」这个方案在第一天就是不可行的。
    第 1 步：按「配置 / 状态 / 事件」把需求分成三堆
    不要按「功能模块」分。这三类对协议的要求互相冲突，必须分开选。
    第 2 步：配置那一堆，按「改错的后果」分级
    会中断业务、需要审计与回滚、需要变更窗口确认 → NETCONF（candidate + validate + commit + confirmed-commit 防自锁，这是不可替代的）。
    低风险、要让别的系统方便接进来 → RESTCONF（注意用 PATCH 而不是 PUT；PUT 会把请求体里没提到的兄弟节点清掉，这是真实事故形态）。
    已在用 gNMI 采集、且是声明式整体下发 → gNMI Set 可以复用同一条通道，但要接受它没有 confirmed-commit。
    第 3 步：状态那一堆，按「时间分辨率」分
    秒级 / 要看跳变时刻 / 千台以上 → gNMI Subscribe（计数器 SAMPLE、离散状态 ON_CHANGE + 必配 heartbeat）。
    只是低频巡检 → NETCONF get 或 RESTCONF GET 就够，不必为此引入一整套流式管道。
    设备只有 SNMP → SNMP GetBulk，但要做对三件事：用 ifHC* 64 位计数器（32 位在万兆口上 3.4 秒回绕）、每次带 sysUpTime 判重启（否则每次重启画一根冲天尖峰）、给采集加 jitter 打散。
    第 4 步：事件那一堆，一定要有两条路
    主路走 gNMI ON_CHANGE（时间戳精确）或 NETCONF notification；兜底保留 SNMP trap。理由很实在：订阅挂了的时候，你需要一个不经过订阅的方式知道这件事。
    第 5 步：设计归一化层（这一步最容易被跳过，代价最大）
    定义一层内部规范化指标名（以 OpenConfig 路径为蓝本），各协议的采集器负责转换。好处是下游（告警、报表、容量模型）完全不感知数据来自哪个协议，后续每台设备切换协议时下游一行都不用改。跳过这一步的系统，在第一次协议切换时会发现下游要改三个月。
    第 6 步：把采集链路本身纳入监控
    每个订阅的消息速率、每个 SNMP 目标的成功率、每个 NETCONF 会话的存活——这些指标的缺失会让你在完全不知情的情况下丢数据。

    最后要主动说出的结论：目标不是「统一到一个协议」，而是「按能力分工 + 数据归一化」。并存是稳态而不是过渡态——因为 confirmed-commit 与 ON_CHANGE 各自不可替代，而设备永远不会统一。把「三年内全部迁到 gNMI」写进方案的选型，是没有摸过现网设备清单的选型。
