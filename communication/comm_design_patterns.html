通信软件设计模式：Reactor / Proactor / Active Object / Pipeline

GoF 那 23 个模式解决的是"对象怎么组织"，通信软件的问题是"事件从哪来、谁来处理、谁持有状态、慢的那个怎么不拖死快的"。这类问题有自己一套沉淀了三十年的模式语言。本篇讲它们在协议栈里的具体落点、取舍，以及四个高发反模式。

Module 09 阅读 ~20 min POSA2 家族
01

为什么通信软件有自己一套模式

POSA2 家族的由来

三条边界，先划清。GoF 23 个模式的本体（意图、类图、C++ 实现）见 设计模式（C++ 视角）；线程池、Actor、future/promise 这类通用并发模式见 并发模式指南；epoll / io_uring 的内核机制见 异步网络编程 与 Linux I/O 内核。本篇只讲这些东西在通信协议栈里怎么组合、组合错了会怎样。

90 年代末，Douglas Schmidt 等人把当时电信与中间件系统（ACE 框架、CORBA 实现）里反复出现的结构整理成了 POSA2（Pattern-Oriented Software Architecture, Vol.2: Patterns for Concurrent and Networked Objects）。这套模式语言之所以独立于 GoF 存在，是因为它回答的是另一层问题：

事件从哪来Reactor / Proactor：谁在等 IO、就绪之后谁被调用。
连接怎么建Acceptor-Connector：把"建立连接"从"用它做业务"里剥出去。
线程怎么分工Half-Sync/Half-Async、Leader/Followers：快慢分离。
谁持有状态Active Object / Monitor Object：加锁还是排队。
处理怎么分级Pipeline / Stage：把长处理切段，各段独立调优。
🍜 类比：这五个问题就是开一家面馆要回答的。事件从哪来——门口是站个迎宾（Reactor：客人到了叫你）还是装个取号机（Proactor：号排好了通知你）；连接怎么建——迎宾只管带位，绝不兼职炒菜；线程怎么分工——前台点单（快、不能堵）和后厨出餐（慢）必须分开，否则一桌点菜慢会让整队人堵在门口；谁持有状态——每张桌子的账单是"谁都能改但要抢一支笔"（加锁），还是"只有这桌的服务员能改、别人要改就跟他说"（Active Object）；处理怎么分级——切菜、下锅、装盘分工站位（Pipeline）。
GoF 关心的是"炒锅这个对象怎么设计"，POSA2 关心的是"整个店怎么排布才不会堵在门口"。
02

Reactor vs Proactor

"能读了叫我" vs "读完了叫我"

Reactor：就绪通知模型。事件分离器（epoll_wait）返回"这些 fd 可读了"，然后由你自己发起 read()。缓冲区由应用在读之前准备，读多少由应用决定。Linux 上的 epoll、BSD 的 kqueue 都是这个模型。
Proactor：完成通知模型。你预先把缓冲区交给内核并发起"读 N 字节"的异步操作，内核完成后通知你"已经读好 M 字节，在你给的那块内存里"。Windows IOCP 是经典实现，Linux 上是 io_uring。

两者的差别远不止"通知时机不同"。真正影响架构的是下面这张表里的后四行——它们决定了你的代码要处理哪些边界情况：

维度Reactor（epoll）Proactor（io_uring / IOCP）
通知语义"可以读了""已经读完了"
系统调用次数每次就绪至少一次 read（ET 下还要读到 EAGAIN）批量提交 + 批量收割，可做到零 syscall（轮询模式）
缓冲区所有权应用随时拥有：可以按需分配、可以复用同一块临时缓冲提交后到完成前归内核：每个在飞的读都要占一块独立缓冲，取消也不能立即回收
内存占用与活跃连接数相关（一个 worker 一块读缓冲即可）与在飞操作数相关：10 万连接各挂一个读 = 10 万块缓冲同时驻留
错误处理错误在你自己的 read 返回值/errno 上，处理点集中错误随完成事件返回（CQE 里的负 errno），要按操作 ID 关联回上下文，处理点分散
背压天然：处理不过来就不去读，数据积在内核缓冲，TCP 窗口自动收缩，压力传回对端要显式做：不提交新的读请求。已提交的读会继续完成并堆在你的完成队列里
取消语义简单：不再关注这个 fd 即可复杂：要发取消请求，还要等取消的完成事件，期间缓冲不能释放
可观测性好：tcpdump / strace / ss 都直接可用差一些：strace 看不到逐个 IO，需要 io_uring 专门的追踪
最关键的一行是"背压"。Reactor 有一个巨大的隐性优势：不读就是背压。上层处理不过来时你只要停止 read，数据自然积压在内核接收缓冲里，接收窗口缩小，对端被迫减速——整条链路的流控由 TCP 免费提供。Proactor 里"读"是提前发出的，数据会被源源不断搬进你的用户态缓冲，压力只会体现为你的内存增长，一路涨到 OOM。所以选 Proactor 的系统必须自己实现有界的在飞操作数控制，这不是可选项。面试被问 Reactor 与 Proactor 的区别，答到缓冲区所有权和背压才算答到位。

2.1 epoll 的 LT 与 ET：一个具体的取舍

⚠️ ET（边缘触发）：漏读就永久失联
// ET 只在"状态发生变化"时通知一次
void on_readable(int fd) {
  char buf[4096];
  ssize_t n = ::read(fd, buf, sizeof buf);
  if (n > 0) process(buf, n);
  // ⚠️ 只读了一次！内核里还有剩余数据时，
  // 不会再有新的 EPOLLIN → 这个连接永远静默
}
// 症状：大报文场景下偶发"连接卡住"，小报文测试不出来
✅ ET 必须读到 EAGAIN，且要防饿死
void on_readable(int fd) {
  for (int i = 0; i < kMaxBatch; ++i) {      // 有上限：防单连接饿死别人
    ssize_t n = ::read(fd, buf, sizeof buf);
    if (n > 0)               { process(buf, n); continue; }
    if (n == 0)              { close_peer(fd); return; }   // EOF
    if (errno == EINTR)      { continue; }
    if (errno == EAGAIN)     { return; }      // 读干净了
    close_with_error(fd); return;
  }
  // 达到批次上限但可能还有数据 → 自己补一个待处理标记，
  // 下轮事件循环继续，而不是死循环占着这个线程
  mark_pending(fd);
}
LT 与 ET 怎么选。LT（水平触发）是默认且不易错：只要还有数据就一直通知，漏读只是下轮再来。代价是同一 fd 可能被反复通知，唤醒次数多。ET 唤醒次数最少（高并发下省 CPU），但把"读干净"的责任交给了你，并且引入"单连接批次上限"这个新的调优点。
建议：管理面/信令面用 LT（连接数不多，正确性优先，少一类 bug）；数据面高并发用 ET（唤醒开销值得省），但必须配套写好上面那个循环，并且给它专门的单元测试（构造"分多次到达的大报文"）。
03

Acceptor-Connector

把"建立连接"和"用连接做事"彻底分开

Acceptor-Connector：用专门的组件负责被动接受（Acceptor）与主动发起（Connector）连接，连接建立成功后创建一个 Service Handler 并把 fd 交给它，此后 Acceptor/Connector 与业务再无关系。核心价值是让业务逻辑不关心自己是主动方还是被动方——同一份 Service Handler 代码在 client 和 server 侧都能用。

这个模式在通信软件里的价值比在普通服务器上大得多，因为通信设备经常两种角色都要扮演。最典型的例子是 O-RAN 的 NETCONF Call Home：正常 NETCONF 是管理站主动连设备（设备是被动方），而 Call Home 反过来——O-RU 上电后主动连出到 SMO（设备变主动方），因为设备可能在 NAT 后面、或者 IP 是动态分配的。有了 Acceptor-Connector，NETCONF 会话状态机那一大坨代码两种模式共用，只换一个建链组件。

三个必须在这一层解决的工程问题：

重连退避Connector 负责重试，业务无感。必须指数退避 + 上限 + 随机抖动——一个 SMO 下挂几千个 O-RU，SMO 重启后如果所有 O-RU 同时以固定 1 秒间隔重连，SMO 会被自己的客户端打死。抖动不是可选优化，是必需品。
半开连接检测TCP 的一端崩溃或链路中断（拔网线）时，另一端可能永远不知道：没有 FIN、没有 RST，socket 看起来完好，只是永远没有数据。必须靠应用层心跳（NETCONF 的 keepalive、SCTP 的 HEARTBEAT）或 TCP_KEEPALIVE 检测。默认的 TCP keepalive 是 2 小时后才开始探测，对通信设备毫无意义，必须显式调小（如 10s 探测、3 次失败判死）。
连接与会话解耦TCP 连接断了不等于会话要销毁。断线重连后能否恢复会话（SCTP 的 restart、NETCONF 重连后的配置对账）是协议层决策，Acceptor-Connector 只报告"连接状态变了"，由上层状态机决定是恢复还是重建。混淆这两层是常见设计错误。
半开连接是通信软件排障里最阴的一类问题。现场表现是"设备显示在线但不响应任何操作"，重启设备就好了——于是被归档为"偶发异常"。根因往往就是某一侧持有半开连接、心跳没配或者心跳走了同一条卡死的 TCP 连接（心跳报文也发不出去，但发送缓冲没满，send() 照样返回成功）。心跳必须能检测"发出去但没回应"，而不只是"能不能调用 send"。
04

线程模型两种流派

Half-Sync/Half-Async 与 Leader/Followers

Half-Sync/Half-Async：把系统切成异步层（IO 线程，只做收包、分帧、入队，绝不阻塞）和同步层（worker 线程，用直白的顺序代码处理业务，可以阻塞），中间用有界队列连接。这是通信软件最主流的骨架。
Leader/Followers：一组线程轮流当"leader"去等事件，leader 拿到事件后先把领导权移交给某个 follower，然后自己就地处理这个事件。没有专门的分发线程，也没有队列——事件从不在线程间传递。
怎么选。业务处理时长差异大（有的查库、有的纯计算）→ Half-Sync/Half-Async，队列吸收抖动，慢请求不会占着 IO 线程。业务处理短且均匀、追求最低时延 → Leader/Followers，省掉入队与跨核搬运。
真实的通信软件常常两者并存：前传/转发面用 Leader/Followers 或干脆 per-core shared-nothing（见 高并发那篇），管理面/信令面用 Half-Sync/Half-Async。判断依据是"这条路径上最慢的处理有多慢"。
05

Active Object / Monitor Object

把"每会话一把锁"换成"每会话一个消息队列"

Monitor Object：对象自带一把锁，所有公有方法进来先加锁。这是最直觉的做法，也是绝大多数代码的现状。Active Object：对象自带一个消息队列和一个执行上下文；调用它的方法不是直接执行，而是把请求入队，由它自己的循环串行执行。调用方立刻返回（要结果就拿一个 future）。

用一个真实改造来看差别。NETCONF agent 的会话对象要被三个来源并发访问：IO 线程（收到 RPC）、定时器线程（会话/commit 超时）、通知线程（数据变更要推送 notification）。

❌ Monitor Object：一把锁保护一切
class NcSession {
 public:
  void on_rpc(Rpc r) {
    std::lock_guard lk(mu_);
    auto reply = handle(r);      // 可能很慢：校验整棵配置树
    send(reply);                 // 持锁做 IO ⚠️
  }
  void on_timeout() {
    std::lock_guard lk(mu_);     // 与 on_rpc 争锁
    rollback_candidate();
  }
  void on_notify(Event e) {
    std::lock_guard lk(mu_);
    if (subscribed_) send(encode(e));   // 又一个持锁 IO
  }
 private:
  std::mutex mu_;
  ...
};
// 已知问题清单：
// 1. 持锁做 IO → 对端慢会把整个会话卡住
// 2. handle() 里回调业务代码，可能反过来碰这把锁 → 死锁
// 3. 加了 SessionManager 的锁之后出现锁序问题
// 4. 忘加锁的新方法 = 一个静默的数据竞争
✅ Active Object：无锁，因为无共享
class NcSession {
 public:
  // 三个入口都只是入队，立即返回
  void post_rpc(Rpc r)      { mbox_.push(Msg{Rpc_{std::move(r)}}); }
  void post_timeout()       { mbox_.push(Msg{Timeout_{}}); }
  void post_notify(Event e) { mbox_.push(Msg{Notify_{std::move(e)}}); }

  // 唯一的执行者：由所属 worker 调用，天然串行
  void drain() {
    Msg m;
    while (mbox_.try_pop(m))
      std::visit(*this, m.body);     // 无需任何锁
  }

  void operator()(Rpc_& r)     { send(handle(r.v)); }
  void operator()(Timeout_&)   { rollback_candidate(); }
  void operator()(Notify_& n)  { if (subscribed_) send(encode(n.v)); }

 private:
  Mailbox mbox_;   // 有界；满了对上游背压
  // 没有 mutex —— 状态只被 drain() 所在的那个线程碰
};
// 上面 4 个问题一次性消失：
// 1&2. 不持锁，也就无所谓持锁 IO / 回调死锁
// 3.  无锁 → 无锁序
// 4.  新方法只要遵守"只 post 不直接改状态"就自动安全
这就是"结构性消除一类 bug"的典范。Monitor Object 的正确性依赖"每个方法都记得加锁、临界区里不做危险的事、多把锁的顺序一致"——三条都靠人。Active Object 把它换成一条可机械检查的规则：状态只被自己的执行上下文碰。违反它需要显式写出跨线程访问，code review 一眼看得见。这也顺便解决了 协议状态机那篇讲的 run-to-completion 与"定时器回调悬垂 this"——定时器到期变成投给自己邮箱的一条消息，回调根本不在别的线程执行。
代价要认清，别当银弹。① 时延多一次入队与唤醒（几百纳秒到几微秒），单会话极致低时延的路径上要衡量。② 跨会话操作变麻烦：原来"锁住 A 和 B 然后搬数据"变成"给 A 发消息，A 再给 B 发消息，B 回消息"，代码从同步变异步，可读性下降。③ 邮箱必须有界，否则背压消失、内存无界增长。④ 调试栈变短：崩溃时的调用栈只到 drain()，看不到"谁投递了这条消息"，所以消息里要带来源标识与关联 ID。
06

Pipeline / Stage

解析 → 校验 → 路由 → 处理 → 编码

把报文处理切成有序的若干段，每段职责单一、可独立替换与调优。通信软件里的经典切法：

① 分帧 Framing从字节流里切出完整消息（长度前缀 / 分隔符 / 固定长度）。唯一关心 TCP 粘包拆包的地方。
② 解析 Parsing字节 → 结构化视图（零拷贝解析）。只做结构，不判语义。
③ 校验 Validation长度、CRC、版本、必填字段、取值范围。这一段是安全边界——所有"不可信输入"的假设在这里终结，后面各段可以信任数据。
④ 路由 Routing按会话 ID / 小区 ID 找到目标状态机，或按 opcode 找到 handler。
⑤ 处理 Handling业务逻辑，通常就是喂给某个状态机。
⑥ 编码 Encoding结果 → 字节，写回。
③ 的位置是这条流水线最重要的设计决策。校验必须集中在一段并且在业务逻辑之前完成。散落式校验（每个 handler 自己检查一点）的后果是：一定会有某个 handler 忘了检查某个字段，而它恰好是攻击面。集中校验还带来一个额外收益——可以对这一段单独做模糊测试，输入随机字节、断言"要么返回明确错误、要么产出结构合法的对象"，覆盖率非常高。这与 内存与竞态排查那篇讲的解析器 fuzz 是同一件事。

6.1 批处理与流水线气泡

把每段做成"一次处理一批"而不是"一次处理一个"，收益来自三处：分摊每次调用的固定开销、指令缓存命中率提升（同一段代码连续跑 N 次）、数据缓存的预取更有效。这是 io_uring 与 DPDK 都强调批处理的原因。

但批处理和低时延是直接冲突的。攒批意味着第一个包要等最后一个包到齐。轻载时批攒不满，就会出现两种糟糕情况：要么等到超时才处理（时延突增），要么按 1 个包一批处理（批处理收益归零，只剩下开销）。
标准做法是"自适应批"：设置批上限 N 和等待上限 T，任一先到就处理；轻载时 T 主导（时延可控），重载时 N 主导（吞吐最优）。这个 T 通常取百微秒量级——它直接决定了轻载时延的下界，是最需要按业务实测的参数。
分段 ≠ 分线程。Pipeline 是逻辑分段，默认应该在同一个线程里顺序跑完（缓存最热、无同步开销）。只有当某一段明显是瓶颈且能并行时（如加解密、FEC）才把它拆到独立线程或卸载到加速卡。一上手就"每段一个线程"是典型的过度设计：报文要跨 5 次线程边界，每次都是一次队列 + 唤醒 + 缓存失效，总时延往往比单线程跑完更差。
07

GoF 在通信里的落点

不重讲模式，只说"用在哪、为什么是它"

GoF 模式通信里的落点为什么非它不可
Strategy编解码器：同一份消息结构，按对端能力选 XML / JSON / ASN.1 / 自定义二进制协议协商的结果是运行期才知道的（hello 交换之后），必须能运行期换实现
Factory消息工厂：opcode → 具体消息对象；YANG 模型 → 节点对象反序列化时"该建哪个类型"由数据决定，这是工厂的本职
Observer告警与通知订阅：NETCONF notification、状态变更推送、性能计数器采集一个事件多个订阅者、订阅关系动态变化，这正是 O1 管理面的形状
Chain of Responsibility报文过滤链：ACL → 限速 → 去重 → 解密 → 业务每一环都可能"到此为止"，而且顺序可配置（不同部署开不同的环）
PIMPL / Type Erasure插件式协议栈：主程序与协议插件之间保持 ABI 稳定厂商要独立发布协议插件而不重编主程序——见 ABI 兼容性：暴露的头文件里不能有会变的成员布局
State协议状态机（见 专篇）每状态行为差异大且各有私有数据时，比 switch 更局部化
CommandActive Object 的消息、配置事务的操作项（可撤销）把"要做什么"对象化之后才能排队、重放、回滚
唯一需要展开讲的是 PIMPL / Type Erasure，因为它解决的是通信特有的约束。电信软件的生命周期以十年计，主程序和协议插件常常由不同团队、不同发布节奏交付。一旦对外头文件里暴露了类的数据成员，任何字段增删都会改变对象大小与布局，插件必须重编——这就是 ABI 断裂。用 PIMPL（头文件里只有一个 std::unique_ptr<Impl>）或纯虚接口 + 工厂函数，把布局关进 .so 里，才能做到"升级主程序，插件不重编"。这不是洁癖，是交付模型决定的硬需求。
08

反模式

四个在通信代码库里高频出现的结构

① 上帝 Manager 类
SessionManager 里有 8000 行：管理会话生命周期、路由消息、维护定时器、统计计数、处理配置变更、做 HA 同步。症状是任何改动都要碰它，两个人同时改必然冲突，而且它持有一把大锁（见 ④）。
成因不是懒，而是"新功能不知道放哪，Manager 显然能拿到所有东西"。解法：把它拆成"注册表（只管 ID → 对象映射）+ 路由器（只管投递）+ 生命周期控制器（只管创建销毁）"，各自可以独立测试。判断标准很简单：如果一个类的名字里有 Manager 而你说不出它不负责什么，它就是这个反模式。
② 跨层回调地狱
传输层拿到数据回调协议层，协议层回调业务层，业务层在回调里又调传输层发送，发送失败再回调错误处理……最终形成一个跨 5 层、深度 20 的调用栈。
后果：栈溢出风险（递归发送）、异常穿过 C 回调边界导致 UB、崩溃时看不出真正的触发点、以及最麻烦的——持锁状态在栈上层层叠加，锁序完全失控。
解法：层间用消息而不是回调（回到 Active Object），或者至少保证回调是"通知型"（只标记状态，不触发新动作），真正的动作留给下一轮事件循环。
③ 一把大锁保护整张会话表
std::mutex + unordered_map<SessionId, Session>，所有操作先锁整张表。单核时代能跑，多核时它就是吞吐天花板——所有 worker 在这一点串行化，加核数不涨吞吐（Amdahl 的具体形态）。
三级解法：a) 分片锁（按 ID 哈希成 N 个桶，各自一把锁，N 取核数的几倍）；b) 会话对象自己持锁，表锁只保护"查找"这一瞬间（查到就取 shared_ptr 然后放表锁）；c) 最彻底——会话按哈希固定绑到某个 worker，表本身变成每个 worker 私有，锁彻底消失（见 高并发那篇的分片模型）。
④ 在回调里做同步 IO
IO 线程的回调里写日志到磁盘、查 DNS、读配置文件、发同步 RPC 等回应。一次几十毫秒的磁盘抖动就会让这个 IO 线程上的所有连接一起卡住——包括心跳，于是对端判定你死了，触发不必要的倒换。
这个反模式的隐蔽性在于平时完全正常：磁盘不忙、DNS 有缓存、下游很快，测试全过。它只在依赖变慢时爆发，而那时通常已经是故障处理现场（日志量暴增 → 磁盘变慢 → IO 线程被卡 → 心跳丢失 → 倒换 → 更多日志），形成正反馈。解法：IO 线程上的一切操作必须是非阻塞的；日志走无锁队列交给专门线程落盘；任何外部依赖调用一律异步化。

案例：重画 O-DU 软件视图

把前面所有模式装进一张图

通信软件架构那篇给了 O-DU 的功能视图（三平面怎么映射到模块）。这里换一个视角：同一个 O-DU，用本篇的模式语言重画一遍——每个框标注它用了什么模式、为什么是这个模式。

这张图的中心结论：模式选择由时限预算决定，不由"哪个模式更先进"决定。用户面 500 µs 的窗口容不下一次队列唤醒（几微秒还行，但一次锁等待或一次分配抖动就可能超时），所以走 shared-nothing、连 Reactor 的队列都省掉；控制面有毫秒级预算，Half-Sync/Half-Async + Active Object 的入队开销完全可以接受，换来的可推理性非常值；管理面有秒级预算，可以放心用最重、最容易写对的结构。在同一个进程里对三个平面用三套模式，这不是不一致，这才是对的。
🎯 本篇要点回顾
  • POSA2 回答的五个问题：事件从哪来、连接怎么建、线程怎么分工、谁持有状态、处理怎么分级
  • Reactor vs Proactor 的关键差别不是通知时机，而是缓冲区所有权与背压：Reactor 里"不读就是背压"，Proactor 必须自己限制在飞操作数
  • epoll LT 用于信令面（正确性优先），ET 用于数据面（必须读到 EAGAIN + 批次上限）
  • Acceptor-Connector 让同一份会话代码支持主动/被动两种角色（NETCONF Call Home）；重连退避必须带随机抖动，心跳必须能检测"发出去没回应"
  • Half-Sync/Half-Async 用队列吸收处理时长差异；Leader/Followers 无队列、时延最低但无背压观测点
  • Active Object 把"每会话一把锁"换成"每会话一个邮箱"，结构性消除持锁 IO、回调死锁、锁序、定时器悬垂四类问题
  • Pipeline 的校验段是安全边界，必须集中且可 fuzz；批处理与低时延冲突，用自适应批（N 或 T 先到）；分段 ≠ 分线程
  • 四个反模式：上帝 Manager、跨层回调地狱、一把大锁保护会话表、在回调里做同步 IO
  • 模式选择由时限预算决定：µs 级 shared-nothing、ms 级消息传递、s 级随便写对就好
