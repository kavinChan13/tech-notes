考点地图与四层模型

先把坐标系建起来

NETCONF/YANG 的面试有一个明显特征：题目看起来很碎，但绝大多数答案都收敛到同一套坐标系上。「get 和 get-config 有什么区别」考的是 Content 层的 config true/false；「为什么要 lock」考的是 Operations 层的事务边界；「chunked framing 解决什么问题」考的是 Messages 层的分帧；「SSH 还是 TLS」考的是 Transport 层的身份模型。只要先把四层模型摆出来，后面每一道题都能落到一个格子里，答起来不会散。

另一个特征是：面试官往往不是在考协议本身，而是在考「你有没有真的用它管过设备」。协议条文谁都能背，但「candidate 被别人锁住了怎么办」「下发返回 ok 但配置没生效」「一万台 O-RU 的 NETCONF 连接怎么维持」这类问题只有踩过坑的人答得出来。所以本页的答案统一按「结论 → 机制 → 生产视角」三段写，最后一段才是拉开差距的地方。

这一页是题集。协议与建模的系统性讲解在 NETCONF/YANG，服务端实现与调试在 NETCONF 工程实践，与 SNMP/RESTCONF/gNMI 的横向选型在 网络管理协议对比。答案里会链过去，但每一条都写成可以独立读懂。

四层模型：所有问题的坐标系

RFC 6241 把 NETCONF 分成四层。这个分层不是文档编排上的方便，而是真实的可替换边界：换掉 Transport 层（SSH → TLS）上面三层一行不改；换掉 Messages 层（XML/RPC → gRPC）就变成了 gNMI；只保留 Content 层（YANG）而换掉其余三层，就是 RESTCONF。理解这一点，「NETCONF / RESTCONF / gNMI 怎么选」这类题就有了统一的回答框架。

把这张图背下来还不够，要能顺着它把「每一层解决什么问题、不解决什么问题」说清楚：

层它负责什么它不负责什么典型面试题落点
Content数据长什么样：树形结构、类型、约束、默认值、config true/false不关心怎么传、怎么改augment/deviation、config false、模型版本兼容
Operations对数据能做什么：读、改、锁、校验、提交、回滚不关心数据的具体语义get vs get-config、五种 operation、事务与 confirmed-commit
Messages一次调用怎么封装：请求/应答配对（message-id）、异步通知、消息边界不关心操作语义chunked framing、]]>]]> 的历史包袱、notification 与 interleave
Secure Transport加密、完整性、对端身份、会话生命周期不关心上面传的是什么SSH vs TLS、cert-to-name、Call Home、端口
面试加分：被问「NETCONF 和 YANG 的关系」时，不要只答「一个是协议一个是建模语言」——那是所有人都会答的。加一句：「YANG 是 Content 层的规范，NETCONF 是 Operations + Messages + Transport 三层的规范，它们在 RFC 里就是分开的两份文档（RFC 6241 与 RFC 7950），正交到可以各自替换。」然后马上给出证据：RESTCONF 用同一套 YANG 模型但换掉了下三层，gNMI 用 OpenConfig 的 YANG 模型但换成了 gRPC。这一句就把「背过定义」和「理解分层」区分开了。

很多候选人能分别说清 lock、edit-config、commit，但串不成一条完整的流程。下面这条时间线值得背熟——面试里画出它，等于一次性回答了「事务」「锁」「校验」「回滚」四个问题：

2.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础NETCONF 和 YANG 分别是什么？NETCONF 的四层模型怎么分？

    YANG 是数据建模语言，NETCONF 是管理协议；前者规定「数据长什么样」，后者规定「怎么读写这些数据」。用点菜打比方：YANG 是菜单的排版规范（有哪些菜、每道菜有哪些可选项、哪些搭配互斥），NETCONF 是点菜、改单、下单、退单这一整套流程。两者是正交的——它们在标准里就是两份独立文档：NETCONF 是 RFC 6241，YANG 1.1 是 RFC 7950。

    NETCONF 自身分四层，自上而下：

    • Content（内容层）：YANG 模型描述的配置数据与状态数据，也就是那棵数据树。
    • Operations（操作层）：<get>、<get-config>、<edit-config>、<copy-config>、<delete-config>、<lock>/<unlock>、<commit>、<validate>、<close-session>/<kill-session> 这些标准 RPC。
    • Messages（消息层）：把操作封装成 <rpc> / <rpc-reply> 请求应答对（靠 message-id 配对），以及单向的 <notification>；还负责消息分帧。
    • Secure Transport（安全传输层）：SSH（TCP 830）或 TLS（TCP 6513）。

    为什么这样分层值得多说一句：这四层是真实的可替换边界，不是文档编排。保留 Content 层的 YANG、把下三层换成 HTTP + JSON 就是 RESTCONF（RFC 8040）；换成 gRPC + Protobuf 就是 gNMI。所以「用同一套 YANG 模型，跑三种协议」在工程上是成立的，这也是后面协议选型题的基础。

    最常见的两个失分点：① 把 YANG 说成「协议」——它不传输任何东西，编译出来的产物是校验规则和代码骨架；② 反过来把 NETCONF 说成「只是个 XML 传输通道」——它自带事务语义（candidate/commit/rollback），这恰恰是 RESTCONF 和 gNMI 都没有的东西。

  2. 基础一个 NETCONF 会话是怎么建立起来的？<hello> 里协商了什么？

    结论：TCP 连接 + SSH/TLS 握手之后，双方各发一条 <hello> 通告自己支持的 capability，取交集作为本次会话的能力集；其中最关键的一项是协议版本 base:1.0 还是 base:1.1，因为它决定后续用哪种分帧方式。

    <hello> 是单向通告，不是请求应答——双方同时发，谁也不等谁。服务端的 <hello> 里必须带 <session-id>，客户端的则不能带。

    <!-- 客户端 → 服务端 -->
<hello xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <capabilities>
    <capability>urn:ietf:params:netconf:base:1.0</capability>
    <capability>urn:ietf:params:netconf:base:1.1</capability>
  </capabilities>
</hello>

<!-- 服务端 → 客户端 -->
<hello xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <capabilities>
    <capability>urn:ietf:params:netconf:base:1.1</capability>
    <capability>urn:ietf:params:netconf:capability:candidate:1.0</capability>
    <capability>urn:ietf:params:netconf:capability:confirmed-commit:1.1</capability>
    <capability>urn:ietf:params:netconf:capability:validate:1.1</capability>
    <capability>urn:ietf:params:netconf:capability:xpath:1.0</capability>
    <capability>urn:ietf:params:netconf:capability:notification:1.0</capability>
    <!-- 支持的 YANG 模块也以 capability 形式通告 -->
    <capability>http://example.com/ns/if?module=example-if&amp;revision=2024-03-01</capability>
  </capabilities>
  <session-id>4711</session-id>
</hello>

    capability 分三类，答题时分开说会显得更有条理：

    • 协议版本：base:1.0 / base:1.1。取交集里最高的一个。
    • 可选特性：:candidate、:confirmed-commit:1.1、:rollback-on-error、:validate:1.1、:startup、:writable-running、:xpath、:url、:notification、:interleave、:with-defaults。客户端必须先看再用——设备不支持 :candidate 时你只能直接改 running。
    • YANG 模块：早期把每个模块及其 revision、feature、deviation 都塞进 capability 列表里，一台大设备能有上千条、几十 KB。后来的做法是只通告一条 yang-library capability，客户端再通过读 ietf-yang-library 拿完整清单，把握手报文压回可控大小。
    生产陷阱
    握手失败最常见的原因不在 NETCONF 层，而在下面的 SSH/TLS：证书过期、系统时间不同步（TLS 握手直接失败）、SSH 算法套件太旧被新版 OpenSSH 拒绝。看到「连接建立后立刻断开、连 <hello> 都没交换」，先怀疑传输层而不是协议实现。
  3. 基础NETCONF 的消息是怎么分帧的？chunked framing 解决了什么问题？

    结论：base:1.0 用特殊字符串 ]]>]]> 作为消息结束标记，base:1.1（RFC 6242）改成了带长度前缀的 chunked framing。改动的原因是前者不安全也不健壮——那个分隔符可能合法地出现在 XML 内容里。

    先看 1.0 的问题：如果某条配置的值本身就包含 ]]>]]>（比如一段描述文本、一条正则、一个 base64 证书的巧合片段），接收方会在数据中间把消息切断，剩下的部分被当成下一条消息去解析，直接导致会话错乱。这不只是理论问题，还是一条可被构造的注入面。

    1.1 的 chunked framing 用「长度前缀」彻底绕开了这个问题：每个 chunk 以 \n# 加十进制字节数开头，消息以 \n##\n 结束。解析器只按字节数读，完全不看内容。

    # base:1.0 —— 靠分隔符，内容里出现同样的字符串就崩
<rpc message-id="101" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get-config><source><running/></source></get-config>
</rpc>]]>]]>

# base:1.1 —— 长度前缀，内容再怎么写都不影响分帧
\n#121\n
<rpc message-id="101" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get-config><source><running/></source></get-config>
</rpc>
\n##\n

    额外的好处是可以流式发送。一条 <get> 的应答动辄几 MB（大设备的完整状态树能到几十 MB），1.0 下发送方必须先把整份 XML 拼完才知道在哪加分隔符；1.1 下可以边序列化边发，每凑够一个缓冲区就发一个 chunk。这对内存受限的嵌入式网元很关键——基站侧的 NETCONF server 常常只有几十 MB 可用堆。

    容易被追问
    「为什么 <hello> 本身不用 chunked framing？」因为分帧方式正是 <hello> 协商出来的，鸡生蛋问题。所以 <hello> 永远用 1.0 的 ]]>]]> 结尾，从下一条消息开始才切换到协商结果。抓包时看到第一条消息用旧分帧、后面用新分帧，是正常的。
  4. 基础<get> 和 <get-config> 有什么区别？各自什么时候用？

    一句话：<get-config> 只返回配置数据（YANG 里 config true 的节点），且可以指定读哪个 datastore；<get> 返回配置数据 + 状态数据（config false），且固定读 running，没有 <source> 参数。

    <get-config><get>
    返回内容仅 config trueconfig true + config false
    可选 datastore有 <source>：running / candidate / startup无，固定 running
    数据来源配置库（存储）配置库 + 设备实时采样
    典型开销小，可预期大且不可预期：要遍历所有状态节点
    典型用途配置备份、差异比对、审计查看链路状态、告警、统计计数
     
    <!-- 只要配置：备份 running -->
<rpc message-id="7" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get-config>
    <source><running/></source>
    <filter type="subtree">
      <interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces"/>
    </filter>
  </get-config>
</rpc>

<!-- 要状态：看某个口现在通不通 -->
<rpc message-id="8" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get>
    <filter type="subtree">
      <interfaces-state xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
        <interface><name>eth0</name><oper-status/></interface>
      </interfaces-state>
    </filter>
  </get>
</rpc>
    最常见的生产事故
    不带 <filter> 直接发 <get>。这等于要求设备把整棵状态树都序列化出来——所有接口的所有计数器、所有小区的所有测量量。在一台负载中的基站上，这一条命令可能要几十秒、占掉几百 MB 内存、并把管理面 CPU 打满。见过的现场故障：监控系统每 30 秒对全网做一次无 filter 的 <get>，把网元管理进程活活拖垮，表现却是「设备随机失联」，查了两周才定位到监控自己。规矩很简单：<get> 必须带 filter，且采集周期要大于单次采集耗时的若干倍。

    加分点：提一句这两个 RPC 在 NMDA（RFC 8342）之后有了统一的继任者 <get-data>（RFC 8526），它把「读哪个 datastore」变成显式参数，可以直接读 operational，从而干净地解决「配置写下去了但还没生效」的可见性问题。这一点在高级题里会展开。

  5. 基础running / candidate / startup 三个 datastore 有什么区别？

    结论：running 是「正在生效的」，candidate 是「还没生效的草稿」，startup 是「下次重启要加载的」。三者都是配置库，区别只在生命周期与生效时机。

    datastore含义是否必选怎么写入掉电后
    running设备当前生效的配置必选支持 :writable-running 时可直接 edit-config；否则只能由 commit 写入视实现，可能丢失
    candidate草稿区，改了不生效可选（:candidate）edit-config 多次累积，commit 一次生效，discard-changes 丢弃通常清空
    startup启动时加载的配置可选（:startup）只能 copy-config 从 running 复制持久保存

    为什么需要 candidate：一次业务变更往往要改几十上百个节点，而这些节点之间有约束依赖。没有 candidate 时，你只能一条条改 running——中间的每一个瞬间设备都处于「改了一半」的非法状态，可能瞬断业务，出错也没法整体回退。candidate 提供的是事务边界：先在草稿上把该改的都改完，validate 一次性校验，commit 原子生效。

    startup 常被忽略的一点：commit 只把 candidate 写进 running，不会自动写 startup。改完配置忘记 <copy-config> 到 startup，设备下次重启就回到旧配置——这是现网非常常见的「配置无故丢失」的真相。部分厂商实现了「commit 时自动同步 startup」，但那是私有行为，不能默认。

    <!-- 变更落盘：running → startup -->
<rpc message-id="31" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <copy-config>
    <target><startup/></target>
    <source><running/></source>
  </copy-config>
</rpc>

    还有一种设备不支持 :candidate（很多嵌入式网元为省内存就是这样），此时只能靠 :writable-running 直接改 running。这种设备上要拿到「原子性」，只能退而求其次用 <edit-config> 的 error-option = rollback-on-error，把一次 RPC 内部做成全成或全败。

  6. 基础NETCONF over SSH 和 over TLS 有什么区别？完整协议栈是什么？怎么选？

    完整协议栈自上而下：NETCONF（Content/Operations/Messages）→ SSH 或 TLS → TCP → IP → Ethernet。传输层必须面向连接、可靠、有序，所以不可能是 UDP——这也是 NETCONF 与 SNMP 最根本的分野之一。

    NETCONF over SSH（RFC 6242）NETCONF over TLS（RFC 7589）
    默认端口TCP 830TCP 6513
    标准地位强制实现，任何 NETCONF 设备都得支持可选
    身份认证口令 / SSH 公钥 / 键盘交互双向 X.509 证书（mTLS），强制客户端证书
    用户名从哪来SSH 认证时直接给出由 cert-to-name 从证书字段映射
    凭据轮换口令/密钥要逐台推，规模化难走 PKI，签发/吊销/续期有现成体系（CRL、OCSP）
    调试友好度高，ssh -s host -p 830 netconf 就能手连低，要准备证书链
    典型场景人工运维、实验室、传统网管大规模自动化、零接触部署、O-RAN 前传 M 平面
     
    # 用 SSH 手连一台设备（把 netconf 当 SSH subsystem 起）
ssh -s admin@10.1.2.3 -p 830 netconf

# 用 TLS 连（需要客户端证书 + CA），常用 openssl 先验证握手
openssl s_client -connect 10.1.2.3:6513 \
        -cert client.pem -key client.key -CAfile ca.pem

    怎么选，判据只有一条：凭据怎么管。几十台设备、有人工运维界面 → SSH，简单直接。几千上万台、要零接触上电自动纳管 → TLS，因为证书天然携带身份且可被自动签发与吊销，而给一万台设备轮换 SSH 口令是运维噩梦。

    两个必须说清的配套概念：

    • truststore：本地保存的受信 CA 证书集合，用来验证对端证书链。它回答的是「我该不该相信这张证书」。
    • cert-to-name：把已验证通过的客户端证书的某个字段（常用 subject DN、Subject Alternative Name 里的某一项，或证书指纹）按规则映射成一个 NETCONF 用户名。它回答的是「这张证书对应系统里的哪个账号」。有了它，后续的 NACM 访问控制（RFC 8341）才有主体可依据——不然验证通过之后你不知道该给它什么权限。
    时间是隐藏依赖
    TLS 握手会校验证书的有效期，所以设备时间不对，NETCONF 就连不上。而基站上电时往往还没同步到 NTP/PTP，时间可能停在 1970 或出厂日期。现场典型症状：设备重启后一直纳管不上，日志里是 certificate is not yet valid。解决办法是上电流程里保证「先对时、再建管理通道」，或者给引导阶段留一条时间容忍策略。

2.2 中级（区分熟练度）

  1. 中级<edit-config> 的五种 operation 是什么？它和 default-operation 怎么配合？

    operation 是打在具体节点上的属性，default-operation 是这次 RPC 里没被显式标注的节点的默认行为。两者是「局部」与「全局」的关系。

    五种 operation（属性写在 urn:ietf:params:xml:ns:netconf:base:1.0 命名空间下）：

    operation语义目标已存在目标不存在
    merge合并，只动提到的子节点（默认值）更新创建
    replace整棵子树替换，没提到的子节点会被删掉整体覆盖创建
    create只创建报错 data-exists创建
    delete删除，要求必须存在删除报错 data-missing
    remove删除，不存在也算成功（幂等）删除静默成功

    default-operation 有三个取值：merge（默认）、replace（把整个目标 datastore 换成报文里给的内容，等于全量下发）、none（不做任何隐式操作，只执行显式标了 operation 的节点）。

    <rpc message-id="55" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <edit-config>
    <target><candidate/></target>
    <default-operation>none</default-operation>      <!-- 关键：路径节点只当"路标" -->
    <error-option>rollback-on-error</error-option>
    <config>
      <interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
        <interface>
          <name>eth1</name>
          <description xc:operation="replace"
                       xmlns:xc="urn:ietf:params:xml:ns:netconf:base:1.0">uplink-to-core</description>
        </interface>
        <interface xc:operation="delete"
                   xmlns:xc="urn:ietf:params:xml:ns:netconf:base:1.0">
          <name>eth9</name>
        </interface>
      </interfaces>
    </config>
  </edit-config>
</rpc>

    default-operation=none 是生产环境的推荐写法，理由值得讲清楚：默认的 merge 会把报文里出现的每一个路径节点都当成「要确保它存在」的指令。你只是想改 eth1 的 description，却顺手「创建」了 interfaces 容器和 eth1 这个 list 条目——如果 eth1 本来不存在，你就凭空造出了一个残缺的接口条目，而校验可能因为缺必填字段直接失败，或者更糟：创建成功但配置不完整。用 none 之后，路径节点纯粹是定位用的路标，只有显式标注的节点会被执行。

    最贵的一个坑：replace 的删除语义
    replace 不是「更新这几个字段」，而是「这棵子树以后就长成我给的样子」。报文里没写的兄弟节点全部消失。常见事故：想给某个小区加一条邻区关系，用了 replace 下发只含新邻区的 neighbors 容器，结果原有的几十条邻区被一次性清空，小区瞬间失去所有切换目标。修改用 merge，只有在确实想做全量同步（意图式配置、以控制器为准）时才用 replace。

    另外两个配套参数也应该顺带提到：test-option（test-then-set 先校验再生效，是 :validate:1.1 下的默认；set 不校验直接set；test-only 只校验不生效，很适合做发布前的 dry-run）与 error-option（stop-on-error 默认，continue-on-error，rollback-on-error 需要 :rollback-on-error capability）。在不支持 candidate 的设备上，rollback-on-error 是唯一能拿到「单次 RPC 原子性」的手段。

  2. 中级讲讲 candidate/commit 的事务模型。confirmed-commit 解决什么问题？

    事务模型的核心是把「编辑」和「生效」分开：edit-config 只动 candidate，可以做任意多次；commit 把 candidate 整体原子地搬到 running。中间随时可以 <discard-changes> 把 candidate 恢复成 running 的副本，等于事务回滚。

    这条链路上有三个校验时机，面试时能分清就很加分：

    • 语法/类型校验：edit-config 当场做（类型、range、pattern、枚举值）。
    • 语义/约束校验：<validate> 或 commit 时做（must、when、leafref 引用完整性、unique、mandatory）。这些约束是跨节点的，只有在一份完整的候选配置上才有意义——这正是为什么它们不能在 edit-config 阶段做。
    • 业务可行性：协议层管不了。「配置合法但业务跑不通」只能靠下一段的 confirmed-commit 兜。

    confirmed-commit（capability :confirmed-commit:1.1）解决的是一个非常具体、也非常致命的问题：你通过管理通道下发的配置，可能把管理通道自己切断。改错一条 VLAN、ACL、路由或管理口地址，配置在设备上完全合法地生效了，然后你就再也连不上这台设备——只能派人到站点接串口线。基站在铁塔上、在地下室、在几百公里外的乡镇，一次上站的成本是几千块和半天时间。

    <!-- 第一步：带确认超时的提交，配置立刻生效但进入"待确认" -->
<rpc message-id="90" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <commit>
    <confirmed/>
    <confirm-timeout>120</confirm-timeout>   <!-- 秒；不写则默认 600 -->
    <persist>IZ-2026-0904-A</persist>         <!-- 允许换一个会话来确认 -->
  </commit>
</rpc>

<!-- 中间：验证业务。ping 得通、告警没涨、管理通道还在 -->

<!-- 第二步：确认。超时前没发这条，服务端自动回滚到提交前的 running -->
<rpc message-id="91" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <commit><persist-id>IZ-2026-0904-A</persist-id></commit>
</rpc>

    关键在于回滚的触发条件是「服务端没等到确认」，而不是「客户端主动要求回滚」。所以哪怕客户端已经完全失联，回滚照样发生——这是一个不依赖客户端存活的安全网。<persist> 参数则解决另一个问题：默认情况下会话一断就立即回滚，而有了 persist-id，你可以用一条新会话来确认，甚至换一台控制器来确认。

    怎么定超时
    太短来不及验证，太长则故障窗口拉长。工程上常用「预计验证耗时 × 3」并留出连接重建的时间：改管理面相关配置时 120–300 秒是常见档位，因为你可能需要重新建立 NETCONF 会话才能发确认。灰度批次也应该按这个节奏切——先一台、验证、确认，再放量。
  3. 中级为什么需要 <lock>？不加锁会怎样？加了锁又有什么风险？

    因为 NETCONF 的事务边界只覆盖「一次 commit」，覆盖不了「我读出来、算一算、再写回去」这个更长的过程。而现网一台设备同时被多个客户端连着是常态：网管平台、自动化脚本、值班人员的 CLI、告警系统的自愈动作。

    不加锁的典型丢失更新（lost update）：

    时刻   会话 A（网管）                    会话 B（自愈脚本）
 t0    get-config candidate            
 t1                                     get-config candidate      ← 拿到同一份基线
 t2    edit-config 改 cell-3 功率
 t3                                     edit-config 改 cell-3 邻区
 t4    commit                                                     ← A 的改动生效
 t5                                     commit                    ← B 基于旧基线覆盖，A 的改动没了

    更隐蔽的是 candidate 的共享语义：多数实现里 candidate 是全局共享的，不是每会话一份。于是 B 的 commit 可能把 A 还没写完的半成品一起提交上去——这比丢失更新更危险，因为提交的是一份谁都没打算生效的中间状态。

    <!-- 拿不到锁时的应答 -->
<rpc-reply message-id="12" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <rpc-error>
    <error-type>protocol</error-type>
    <error-tag>lock-denied</error-tag>
    <error-severity>error</error-severity>
    <error-info><session-id>4711</session-id></error-info>   <!-- 谁占着 -->
  </rpc-error>
</rpc-reply>

    锁的风险有三个，能主动说出来才算答完整：

    • 粒度太粗。标准 <lock> 锁的是整个 datastore，不是某棵子树。一个只想改小区 3 的脚本会把整台设备的配置面挡住。RFC 5717 定义了 <partial-lock>（按 XPath 锁子树），但支持它的设备不多，不能想当然。
    • 持锁者失联。规范规定会话终止时锁自动释放，这在正常断开时没问题；但 TCP 半开（对端进程被 kill -9、网络中断而没发 RST）时，服务端要等 keepalive 超时才认为会话死了，这期间锁一直挂着。所以服务端必须开 SSH/TCP keepalive 或者会话空闲超时，否则一次客户端崩溃能把设备的配置面锁住几十分钟。真被卡住时的应急手段是 <kill-session> 强杀持锁会话，但要先确认它真的死了。
    • candidate 的锁有额外前提。如果 candidate 里已经有未提交的改动，锁请求会被拒绝——因为你锁住一份带着别人半成品的草稿毫无意义。规范化的做法是「lock 成功之后立刻 discard-changes」，确保自己从一份干净的基线开始。
    推荐流程
    lock candidate → discard-changes → 若干次 edit-config → validate → commit（confirmed）→ 验证 → commit 确认 → unlock。并且把 unlock 写进异常路径——C++ 里就用 RAII 守卫，Python 里用 with，绝不要让 unlock 只出现在成功分支上。
  4. 中级YANG 里的 augment 和 deviation 有什么区别？各自什么时候用？

    方向相反：augment 是「我给标准模型加东西」，deviation 是「我声明自己做不到标准模型的某一部分」。前者是扩展，后者是认错。

    augmentdeviation
    作用往已有模型的某个路径下插入新节点声明本设备对某路径的实现与标准不一致
    谁写标准组织或厂商，写在自己的模块里只能是设备实现方
    对客户端多出可用的字段，不破坏原有交互必须读，否则会下发注定失败的配置
    典型子句augment "/if:interfaces/if:interface" { leaf ... }not-supported / add / replace / delete
     
    // augment：在标准 ietf-interfaces 上挂厂商私有的光模块信息
module vendor-if-ext {
  namespace "http://example.com/ns/if-ext";
  prefix vifx;
  import ietf-interfaces { prefix if; }

  augment "/if:interfaces/if:interface" {
    leaf optical-tx-power-dbm { type decimal64 { fraction-digits 2; } config false; }
    leaf laser-enable        { type boolean; default true; }
  }
}

// deviation：这台低端设备不支持标准里的某个特性
module vendor-if-dev {
  import ietf-interfaces { prefix if; }

  deviation "/if:interfaces/if:interface/if:link-up-down-trap-enable" {
    deviate not-supported;                 // 整个节点不实现
  }
  deviation "/if:interfaces/if:interface/if:description" {
    deviate replace { type string { length "0..31"; } }   // 只支持 31 字节
  }
}

    为什么 deviation 这个机制必须存在：标准 YANG 模型是按「理想设备」写的，而真实设备总有做不到的地方——芯片不支持、内存放不下、这一代硬件没有这个功能。如果没有 deviation，设备只有两条路：谎称支持然后在运行时报错（客户端无法预知），或者干脆不声明支持这个模型（那就完全失去了标准化的好处）。deviation 提供了第三条路：把「不一致」本身变成机器可读的声明，让客户端在下发之前就知道边界在哪。

    工程上的真实姿态
    多厂商场景里，控制器必须先把每台设备的完整模型集（含 deviation）拉下来编译成该设备专属的校验器，而不是拿一份标准模型去校验所有设备。设备侧通过 ietf-yang-library 通告自己实现了哪些模块、哪些 revision、启用了哪些 feature、应用了哪些 deviation；控制器用 <get-schema>（ietf-netconf-monitoring，RFC 6022）把模型文本取回来。跳过这一步是「实验室能通、现网各种报错」的头号原因——因为实验室里往往只有一款设备。
  5. 中级config false 是什么意思？它对读取、下发、校验分别意味着什么？

    YANG 里每个数据节点都有 config 属性，默认继承父节点、根为 true。config true 是配置数据（你写进去的意图），config false 是状态数据（设备算出来或测出来的事实）。

    container interfaces {
  list interface {
    key name;
    leaf name    { type string; }                // config true（继承）
    leaf enabled { type boolean; default true; }  // config true —— 我"要求"它起来

    leaf oper-status {                            // config false —— 它"实际"起没起来
      type enumeration { enum up; enum down; enum testing; }
      config false;
    }
    container statistics {                         // 整个子树都是 config false
      config false;
      leaf in-octets  { type yang:counter64; }
      leaf out-errors { type yang:counter64; }
    }
  }
}

    这个标记会连锁影响四件事：

    影响面config trueconfig false
    <get-config>返回不返回
    <get>返回返回
    <edit-config>可写不可写，写了报 invalid-value 或直接被拒
    存放位置（NMDA）candidate / running / intended只在 operational
    能否做 key / leafref 目标可以受限：config true 的 leafref 不能指向 config false 节点

    最后一条约束是建模时最容易撞墙的地方，也值得展开讲：配置必须能在设备状态之外独立成立。如果允许一条配置引用一个状态值，那么「把这份配置原样恢复到另一台设备」就不再可行了——因为目标设备的那个状态值可能不存在。这条规则本质上是在保证配置的可移植性与可重放性。

    「意图 vs 事实」这个二分还解释了一个高频困惑：为什么 enabled=true 但 oper-status=down？因为前者是你的意图（管理状态），后者是物理事实（光纤没插、对端没开）。同理，<get-config> 读回来的一定是你写下去的原样，而 <get> 读到的可能包含设备自己补的默认值和系统生成的条目——这也是为什么做配置比对（config diff）时必须用 <get-config> 而不是 <get>，否则每次比对都会看到一堆假差异。

    再深一层：with-defaults
    即使都用 <get-config>，默认值的处理方式仍可能造成假差异。RFC 6243 定义了 with-defaults 的四种模式：report-all（把默认值也吐出来）、trim（等于默认值的一律不吐）、explicit（只吐显式设置过的，最常用作基线）、report-all-tagged（吐出来但打上 default 标记）。做配置基线比对时应该固定用同一种模式，并优先选 explicit。
  6. 中级NETCONF / RESTCONF / gNMI 怎么选？它们的能力边界在哪？

    三者的 Content 层可以是同一套 YANG，差别全在下面三层。所以选型问题等价于：你更需要事务，还是更需要 Web 集成，还是更需要高频遥测。

    NETCONFRESTCONFgNMI
    规范RFC 6241 / 6242RFC 8040OpenConfig（非 IETF）
    传输SSH 830 / TLS 6513，长连接HTTP/1.1 或 HTTP/2 over TLSgRPC over HTTP/2 + TLS
    编码XMLJSON 或 XMLProtobuf / JSON_IETF
    操作get / get-config / edit-config / lock / commit …GET / POST / PUT / PATCH / DELETE（+ RFC 8072 yang-patch）Capabilities / Get / Set / Subscribe
    多次编辑一次提交有（candidate + commit）无（每次请求即一次独立变更）Set 内部可多操作原子，但没有跨请求事务
    datastore 概念完整（running/candidate/startup/…）简化（对应 running，另有 operational 视图）用 path prefix 表达，非 IETF 语义
    推送 / 遥测<notification>（RFC 5277）、YANG-Push（RFC 8641）SSE 事件流原生强项：sample / on-change 订阅，秒级到亚秒级
    典型场景电信设备配置、O1/M 平面、需要回滚的变更控制器北向、CI/CD 脚本、Web 集成数据中心大规模状态采集

    判据可以压成三句话：① 要事务、要回滚、要多步变更原子生效 → NETCONF。这是另外两个都补不上的能力，也是电信设备坚持用它的根本原因。② 只是想让一段 Python/CI 脚本读写几个字段、和现有 HTTP 体系打通 → RESTCONF。它的最大价值是「不需要专门的 NETCONF 客户端库」。③ 要从几千台设备上每秒收几万个指标 → gNMI。Protobuf 的编解码开销比 XML 低一个数量级以上，且 on-change 订阅避免了轮询。

    那 SNMP 呢？这是必然的追问，值得单独答一段。SNMP 与上面三者不是同一代人：它用 MIB（ASN.1/SMI）建模而不是 YANG，跑在无连接的 UDP 上，强项是 get/trap 这种轻量的监控与告警，弱点集中在配置侧——没有事务、没有回滚、没有锁，set 一次只能改一个变量且失败了没人帮你收拾；安全性到 v3 才补上认证与加密，而现网大量存量还停在 v2c 的社区名（community string，明文口令）上。

    所以现在的格局是：配置管理已经基本从 SNMP 迁走（转向 NETCONF 或 gNMI），SNMP 留在存量设备的监控告警上，短期内也不会消失——因为几十万台老设备只支持它，而且「收个 trap、查个接口流量」它确实够用且便宜。答这道题时不要说「SNMP 过时了」，要说清楚「它在配置侧被替代，在监控侧仍有存量价值」，这才是现网的真实状态。更细的横向对比见 网络管理协议对比。

    现实里几种协议常常并存，这是一个很好的收尾回答：一张网上，配置走 NETCONF（要事务与回滚），遥测走 gNMI（要频率与规模），控制器北向暴露 RESTCONF（要给上层业务系统一个 HTTP 接口），存量老设备继续用 SNMP 收告警。前三条路复用同一套 YANG 模型，所以模型才是真正的资产，协议只是搬运工。

    别把 gNMI 说成"更现代所以更好"
    gNMI 不是 IETF 标准而是 OpenConfig 的规范，且没有 candidate/commit 语义。用它做复杂配置变更时，「改到一半失败」的收拾工作要由控制器自己承担——你得自己实现比对、重试和补偿。在需要审计与回滚的电信场景，这是实打实的倒退。

2.3 高级（体现深度）

  1. 高级O1 接口和 NETCONF 是什么关系？NETCONF 在 O-RAN 里具体承担了哪些活？

    先纠正一个常见的口误：O1 不是「一个协议」，而是 SMO 与被管网元之间的一组管理服务；NETCONF/YANG 只是其中配置管理（CM）那一块的承载方式。把 O1 和 NETCONF 划等号，是这道题最典型的失分点。

    O1 上的管理服务承载方式典型内容
    配置管理（CM）NETCONF + YANG小区参数、传输参数、邻区关系；需要事务与回滚
    故障管理（FM）VES 事件上报（HTTPS + JSON）告警产生/清除，要求低时延推送
    性能管理（PM）批量文件上报 + VES15 分钟粒度的计数器文件，量大、可容忍延迟
    软件与文件管理NETCONF RPC 触发 + 文件传输版本下载、激活、回退

    为什么 CM 选 NETCONF 而 FM/PM 不选，这是能体现判断力的地方：CM 的诉求是「几十个参数要么一起生效、要么一起不生效，出问题能退回去」——这正是 candidate/commit 提供的。FM 的诉求是「一条告警要在秒级内推到 SMO」，PM 的诉求是「每 15 分钟搬运几十 MB 的计数器」，这两者都不需要事务，却都需要高吞吐或低时延的单向管道，用 HTTP/JSON 的 VES 更合适。用对的工具做对的事，而不是全都塞进一个协议。

    NETCONF 在 O-RAN 里其实出现在两个位置，这一点很多人只说了一半：

    • O1：SMO ↔ O-CU / O-DU / O-RU / Near-RT RIC，管的是网元级的 FCAPS。
    • 前传 M 平面：O-DU（和/或 SMO）↔ O-RU。O-RU 是一个资源极其受限的设备，它只做 NETCONF server，模型由 O-RAN WG4 定义（天线阵、载波、时延管理、S 平面的 PTP 配置等）。

    值得多说一句的工程现实：O-RU 侧的 NETCONF 实现是整条链路上最脆弱的一环。它跑在一颗算力有限的 SoC 上，堆内存可能只有几十 MB，却要承载完整的 XML 解析、YANG 校验和数据树。所以 O-RU 的模型往往做了大量 deviation（不支持某些节点、字符串长度受限、list 条目数上限），并且对并发会话数、单次报文大小都有硬限制。多厂商互操作时，「O-DU 侧下发的 XML 太大把 O-RU 的解析器打爆」是真实存在的失败模式，表现是 O-RU 无响应或直接重启。

    面试加分：把「谁是 client 谁是 server」这条线理清楚。被管的一方永远是 NETCONF server——O-RU 是 server，O-DU 或 SMO 是 client；O-DU 自己在 O1 上又是 server，SMO 是 client。所以 O-DU 需要同时实现 server（面向 SMO）和 client（面向 O-RU）两套角色，这是它管理面代码量远大于 O-RU 的原因，也是很多人没想到的一点。想看 O1 在整套 O-RAN 接口里的位置，见 O-RAN 接口全景。
  2. 高级O-RAN 前传 M 平面的 hierarchical 与 hybrid 模式有什么区别？各自的取舍是什么？

    区别只有一句：O-RU 上究竟挂着几个 NETCONF 客户端。hierarchical 模式下只有 O-DU 一个；hybrid 模式下 O-DU 和 SMO/网管都能直接连到 O-RU。

    Hierarchical（层级式）Hybrid（混合式）
    谁连 O-RU只有 O-DUO-DU + SMO/网管，多条并存的会话
    SMO 视角看不到 O-RU，只看到 O-DU；O-RU 的信息由 O-DU 代理上报可以直接读写 O-RU
    O-DU 的职责重：要做 O-RU 的全部管理代理，含告警、软件升级、模型透传轻：只管无线业务必需的那部分
    并发写冲突不存在（单一写者）存在：要靠 lock + NACM 划分可写子树
    多厂商解耦差：换一款 O-RU，O-DU 的代理层要跟着适配好：SMO 可以直接按 O-RU 厂商模型操作
    O-RU 资源开销低（一条会话）高（多条会话、多份订阅）

    取舍的本质是「代理」与「直连」的老问题。hierarchical 的收益是接口面收敛——SMO 只需要和 O-DU 说话，整网的管理拓扑是一棵干净的树；代价是 O-DU 变成了瓶颈与耦合点，任何 O-RU 侧的新能力都要 O-DU 先支持才能用上，而 O-DU 与 O-RU 常常来自不同厂商，这个「先支持」可能要等一个版本周期。

    hybrid 的收益是解耦——O-RU 的软件升级、证书更新、告警订阅可以由 SMO 直接做，不必等 O-DU 开发；代价是你必须认真回答「两个客户端同时写同一个节点会发生什么」。工程上的标准答案是两条一起上：① 用 <lock> 保证同一时刻只有一个写者；② 用 NACM（RFC 8341） 按角色把可写子树切开——比如 O-DU 只能写载波与时延相关的子树，SMO 只能写软件与证书相关的子树，从模型层面消除重叠。只答 lock 不答 NACM 是不完整的，因为 lock 是互斥，NACM 才是职责划分。

    还有一个被忽略的维度：告警去重
    hybrid 下 O-RU 的同一条告警可能既经 O-DU 代理上报到 SMO，又由 SMO 直接订阅收到，于是同一个故障在网管上出现两次、清除时间还不一致。设计时要明确「告警的权威来源只有一个」，另一条通道要么关掉订阅、要么在 SMO 侧按告警标识做归并。

    关于 O-RU 怎么被发现：O-RU 上电后并不知道谁来管它，所以链路建立方向通常是反过来的——O-RU 先通过 DHCP 等手段拿到管理网参数与 NETCONF 客户端地址，再用 Call Home（RFC 8071）主动向 O-DU/SMO 发起 TCP 连接，然后在这条连接上由对方扮演 NETCONF 客户端。具体的发现步骤各版本规范有差异，答题时讲清「方向是反的、原因是 O-RU 不知道对端」即可，不必背条款。

  3. 高级用 C/C++ 做一个 NETCONF server，libyang / libnetconf2 / sysrepo / netopeer2 各负责什么？

    这四个库是一条清晰的分层，各自对应 NETCONF 四层模型里的不同位置，边界划得相当干净：

    组件层次职责大致对应
    libyangContent解析 .yang 文件、构建模型树；解析/序列化 XML/JSON 数据；执行类型、must、when、leafref 等全部校验；提供 XPath 求值「懂 YANG 的那个大脑」
    libnetconf2Messages + Transport会话管理、<hello> 协商、分帧、<rpc>/<rpc-reply> 收发、通知投递；SSH（经 libssh）与 TLS（经 OpenSSL）「协议管道」
    sysrepoOperations + 存储datastore 的实际实现（running/candidate/startup/operational）、事务与提交、变更订阅与回调、NACM 访问控制、模块安装管理「配置数据库 + 事务引擎」
    netopeer2组装把上面三者粘起来的可运行 NETCONF server 进程，实现标准 RPC 的默认行为「成品服务端」

    一次 edit-config 在这条链上的流转，能讲清楚这个就说明真的用过：

    SSH/TLS 报文
   │
   ├─ libnetconf2：解分帧 → 得到一条完整的 <rpc> XML
   │
   ├─ libyang：解析 XML → 校验类型/约束 → 生成内存数据树（lyd_node）
   │
   ├─ sysrepo：写入 candidate → NACM 鉴权 → <commit> 时开启事务
   │            ├─ 阶段 1：通知所有订阅者"要变了"，任一订阅者拒绝则整体中止
   │            ├─ 阶段 2：写入 running（持久化）
   │            └─ 阶段 3：通知订阅者"已生效"，由业务进程真正下发到硬件
   │
   └─ libnetconf2：把 <ok/> 或 <rpc-error> 封帧回送

    最关键的设计点是 sysrepo 的两阶段变更通知。业务进程（真正操心硬件的那一方）以订阅者身份注册在某棵子树上，在阶段 1 拿到「即将变更」的回调时可以做业务层面的可行性检查——比如「这块板卡当前不支持这个带宽组合」——并返回错误让整个事务中止。这样一来，「配置写进了数据库但硬件配不下去」这种不一致就被挡在提交之前。如果只在提交之后才通知业务，你就只能事后补偿，那是完全不同的复杂度。

    # 装模型（含 deviation 与 feature 开关）
sysrepoctl -i ./o-ran-uplane-conf.yang -s ./yang-deps -p 600
sysrepoctl -c o-ran-uplane-conf -e ENABLE-SOME-FEATURE

# 看装了哪些模块、什么 revision、启用了哪些 feature
sysrepoctl -l

# 直接读写 datastore，绕过 NETCONF，排查时非常有用
sysrepocfg -X -d running -f xml -m ietf-interfaces
sysrepocfg --edit=patch.xml -d candidate -m ietf-interfaces

# 起服务端并把日志开到最大
netopeer2-server -d -v 3
    生产陷阱
    ① 模型版本不匹配：客户端按 revision A 生成报文，设备装的是 revision B，多一个节点就整条 RPC 校验失败。规范做法是客户端启动时读 ietf-yang-library，按设备实际模型集编译校验器，而不是硬编码一份。② 大配置的性能：libyang 的数据树是全内存的，一份几万节点的配置在树里可能占几十上百 MB，嵌入式设备上要控制单次事务的规模、分批下发。③ 订阅回调阻塞：阶段 1 的回调是同步的，业务进程在里面做了慢操作（等硬件、等锁）会把整个 commit 拖住甚至超时，回调里只该做校验，真正的下发放到阶段 3 或异步做。更完整的实现细节见 NETCONF 工程实践。
  4. 高级要纳管上万台设备，NETCONF 的连接策略怎么设计？

    核心矛盾：NETCONF 是长连接协议，而长连接的数量、方向和保活成本都不随设备数线性缩放。一万台设备意味着一万条常驻 TCP + SSH/TLS 会话，每条都占着控制器的文件描述符、加密上下文和内存，还要各自保活。这道题考的就是你有没有想过这件事。

    第一个问题：连接方向。默认模型是控制器主动连设备，但现网设备大量在 NAT 之后、在私网里、或者上电时地址由 DHCP 动态分配——控制器根本不知道往哪连。解决办法是 Call Home（RFC 8071）：设备开机后主动向预置的控制器地址发起 TCP 连接，连上之后角色反转——发起连接的设备扮演 NETCONF server，接受连接的控制器扮演 client。它为此登记了两个端口：netconf-ch-ssh 4334 与 netconf-ch-tls 4335。

    # 常规方向：控制器 → 设备
控制器 ──TCP connect──> 设备:830      设备是 server

# Call Home：设备 → 控制器（穿 NAT、免预知地址）
设备 ──TCP connect──> 控制器:4334     设备仍是 server，控制器是 client
      └─ 上电流程：DHCP 拿地址与控制器位置 → 对时 → 取/验证证书 → Call Home

    第二个问题：连接要不要一直留着。两种策略各有适用面：

    常驻长连接按需短连接
    下发时延低，省掉每次的握手（SSH/TLS 握手在弱网上可达数百毫秒到秒级）高
    能否收 notification能，告警可即时推送不能，只能轮询
    控制器资源高：fd、内存、保活流量都乘以设备数低
    雪崩风险大：控制器重启后上万台同时重连小
    适用需要实时告警的核心网元只做周期性巡检/备份的边缘设备

    第三个问题：怎么防雪崩。这是最能体现工程经验的一点。控制器重启或链路恢复的瞬间，所有设备会同时重连，一万次并发的 TLS 握手足以把控制器的 CPU 打满，于是握手超时、设备重试、进一步加剧拥塞——典型的重连风暴。三件套是必须的：指数退避 + 随机抖动（jitter）+ 控制器侧的并发准入限流。抖动尤其关键，纯指数退避会让所有设备在同一批时间点上齐步重试，退避曲线只是把冲击往后推而没有摊平。

    第四个问题：采集怎么做。轮询 <get> 是最省事也最贵的方案（前面基础题里那个「监控把网元拖垮」的案例就是这么来的）。可选的替代：

    • 订阅通知：RFC 5277 的 <create-subscription>，配合 :interleave capability 可以在同一条会话上边收通知边发 RPC，不必再开一条。
    • YANG-Push（RFC 8641，基于 RFC 8639 的订阅框架）：按周期或按 on-change 推送数据子树的变化，把「控制器反复问」变成「设备主动说」。on-change 对状态稀疏变化的场景（接口 up/down、告警）能把流量降一两个数量级。
    • 大批量性能数据不要走 NETCONF：15 分钟粒度的 PM 计数器用文件批量上报（O1 上就是这么做的），或者上 gNMI 的流式订阅。让 NETCONF 专注在它擅长的配置事务上。
    分层收敛
    真到几万台的规模，单个控制器无论如何都扛不住。通行做法是分层：区域控制器负责一片设备的长连接与采集，中心控制器只和区域控制器打交道。这也正是 O-RAN 前传 hierarchical 模式的思路——O-DU 就是那个区域收敛点，SMO 不必直连成千上万个 O-RU。
  5. 高级NMDA 是怎么回事？intended 和 operational 有什么区别？

    NMDA（Network Management Datastore Architecture，RFC 8342）解决的是一个老问题：原始 NETCONF 只有 running/candidate/startup 三个配置库，而「配置实际生效成了什么样」在协议里没有位置。结果就是 <get> 把配置和状态混在一起返回，而配置那部分究竟是「你写下去的」还是「设备实际在用的」，说不清楚。

    NMDA 把 datastore 重新切了一遍：

    datastore内容写者回答的问题
    candidate草稿配置客户端我打算改成什么
    running当前生效的配置commit我要求它是什么
    intendedrunning 经模板展开、去掉 inactive 节点、校验通过后的结果系统，只读系统打算让它是什么
    operational实际生效的配置 + 全部状态数据系统，只读它现在实际是什么

    intended 与 running 的差别来自那些「配置里写了但不直接生效」的机制：模板/profile 展开（写一行引用，展开成几十行）、被标记为 inactive 的节点、条件生效的分支。running 是你写的原文，intended 是展开求值之后系统真正要去实现的那份。

    operational 与 intended 的差别才是真正有价值的那一个，它同时包含三类内容：① 已经落到硬件上的配置；② 系统自己生成的配置（比如自动创建的默认路由、协议协商出来的参数）；③ 传统意义上的状态数据。于是

    intended 有、operational 没有的节点 = 「下发了但没生效」；
    operational 有、intended 没有的节点 = 「系统自己加的或学来的」。

    这两句话把「配置是否真的生效」从一个靠经验猜的问题变成了一次可编程的集合运算。配套的读取 RPC 是 <get-data>（ietf-netconf-nmda，RFC 8526），它把「读哪个 datastore」变成了显式参数：

    <rpc message-id="200" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get-data xmlns="urn:ietf:params:xml:ns:yang:ietf-netconf-nmda">
    <datastore xmlns:ds="urn:ietf:params:xml:ns:yang:ietf-datastores">
      ds:operational
    </datastore>
    <subtree-filter>
      <interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces"/>
    </subtree-filter>
    <with-origin/>              <!-- 要求逐节点标注这个值是哪来的 -->
  </get-data>
</rpc>

    <with-origin/> 是 NMDA 里被低估的一项能力：它让服务端给 operational 里的每个节点打上来源标记（配置下发的、系统生成的、协议学来的、取的默认值等）。有了它，「这条路由到底是我配的还是 OSPF 学来的」不再需要人去翻文档判断——数据自己带着答案。

    对建模的连锁影响
    NMDA 之前，YANG 模型为了同时表达配置和状态，习惯写成两棵并列的树：/interfaces（config）和 /interfaces-state（state），字段大面积重复。NMDA 之后这种双树是多余的——同一棵树在 intended 里读到配置、在 operational 里读到实际值就够了。所以新版模型（含 ietf-interfaces 的较新 revision）把 -state 分支标为 deprecated。这也解释了一个现实困扰：同一份模型在支持 NMDA 与不支持 NMDA 的设备上，正确的读取路径不一样，客户端必须先看设备通告的 capability 再决定走哪条路。
  6. 高级综合题：一条配置下发失败了，或者返回 ok 却没生效，你怎么定位？

    先分清是哪一类失败，两类的排查路径完全不同：「返回 <rpc-error>」是协议或校验层面的问题，信息都在报文里；「返回 <ok/> 但业务不对」是生效层面的问题，报文里什么都看不出来，必须去比对 datastore。

    第一类：拿到了 <rpc-error>。NETCONF 的错误结构是相当完整的，先把它读懂再动手：

    <rpc-reply message-id="101" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <rpc-error>
    <error-type>application</error-type>        <!-- transport/rpc/protocol/application -->
    <error-tag>invalid-value</error-tag>        <!-- 机器可读的分类 -->
    <error-severity>error</error-severity>
    <error-path xmlns:if="urn:ietf:params:xml:ns:yang:ietf-interfaces">
      /if:interfaces/if:interface[if:name='eth1']/if:mtu
    </error-path>                               <!-- 精确到出错节点，最有用的一行 -->
    <error-message xml:lang="en">
      value 65536 is out of range 68..9216
    </error-message>
  </rpc-error>
</rpc-reply>

    <error-type> 直接告诉你该去哪一层查，<error-path> 给出精确到节点的 XPath。常见 error-tag 与它们指向的根因：

    error-tag含义八成是什么原因
    unknown-element / unknown-namespace节点或命名空间不认识模型版本不匹配，或客户端用了设备 deviate 掉的节点
    invalid-value值不合法超出 range/length/pattern；设备通过 deviation 收窄了取值范围
    missing-element缺必填节点mandatory true 或 list 的 key 没给
    data-exists / data-missing目标已存在 / 不存在误用了 create / delete，换 merge / remove
    access-denied无权限NACM 规则挡住了，或 cert-to-name 映射到了错误的用户
    lock-denied拿不到锁另一会话持锁；error-info 里有它的 session-id
    operation-not-supported操作不支持用了设备没通告的 capability（典型：设备没有 :candidate）
    resource-denied资源不足报文太大、条目数超限、设备内存不够

    第二类：返回 <ok/> 但业务没变化。这类问题的排查顺序应该是沿着数据的流向逐段夹逼，每一步都要有明确的判定动作：

    1. 写进 candidate 了吗：<get-config> 读 candidate 比对。若没有，说明报文的路径/命名空间写错了——最常见的是 namespace 前缀对了但 URI 错了，服务端把整个子树当未知内容忽略。
    2. 提交到 running 了吗：<get-config> 读 running。忘记发 <commit> 是排名第一的原因，脚本里尤其容易漏。
    3. 是不是被 confirmed-commit 回滚了：如果用了 <confirmed/> 而确认那一步失败或超时，配置会在 timeout 之后自己退回去。现象非常迷惑：下发后立刻查是对的，几分钟后再查就变回去了。
    4. 生效到硬件了吗：设备支持 NMDA 就读 operational 与 intended 比对；不支持就用 <get> 读对应的状态节点。差异存在，说明卡在业务进程的下发环节。
    5. 被 startup 覆盖了吗：如果是「重启后配置丢失」，那就是没做 <copy-config> 到 startup。
    6. 被别人改回去了吗：读 ietf-netconf-monitoring 的会话与统计，看还有谁连着、谁在写。多客户端场景下「A 刚配完 B 就用旧基线覆盖」非常常见。
    # 看当前有哪些会话连着设备、各自发了多少 RPC
<get><filter type="subtree">
  <netconf-state xmlns="urn:ietf:params:xml:ns:yang:ietf-netconf-monitoring">
    <sessions/><statistics/>
  </netconf-state>
</filter></get>

# 服务端侧：直接读数据库，绕开协议层，判断"是协议问题还是业务问题"
sysrepocfg -X -d candidate   -f xml -m <module>
sysrepocfg -X -d running     -f xml -m <module>
sysrepocfg -X -d operational -f xml -m <module>
    真实案例：某站点批量下发小区参数，控制器全部返回成功，但现场统计显示参数没变。逐段夹逼下来：candidate 有、running 有、operational 里没有。于是问题落在业务进程的下发环节。查下去发现该批次下发使用了 default-operation 的默认值 merge，在报文的路径节点上「顺手创建」了一个本不该存在的 list 条目；业务进程在阶段 3 的回调里对这个残缺条目取属性时抛了异常并被吞掉，导致后半段的真实变更全部没有执行，而 sysrepo 侧的事务已经提交。修复是两条：报文改用 default-operation=none，以及把阶段 3 回调里的异常改为显式记录并触发告警，不再静默吞掉。这个案例的普适教训是：「数据库写成功」和「硬件生效」是两件事，只有 operational 能区分它们。

面试前扫一眼

capability 速查

capability 是 NETCONF 里「能力发现」的唯一机制，客户端所有的行为分支都由它决定。下面这些是最可能被问到的：

capability没有它会怎样
:candidate:1.0没有草稿区，只能直接改 running，失去多步变更的事务性
:writable-running:1.0running 不可直接写，必须走 candidate + commit
:confirmed-commit:1.1提交后无法自动回滚，改错管理面配置只能上站
:rollback-on-error:1.0edit-config 的 error-option 不能用 rollback，一次 RPC 内做不到全成全败
:validate:1.1不能单独校验；test-option 的 dry-run 也用不了
:startup:1.0没有独立 startup，重启行为由厂商私有逻辑决定
:xpath:1.0<filter> 只能用 subtree，不能用 XPath 表达复杂条件
:notification:1.0 / :interleave:1.0收不到异步通知；没有 interleave 时收通知的会话不能同时发 RPC，得再开一条
:with-defaults:1.0无法控制默认值是否返回，配置基线比对会出现大量假差异
:url:1.0不能用 URL 作为 config 的源/目标，大配置只能走报文
一条通用建议：客户端的正确姿势永远是「先读 <hello> 与 ietf-yang-library，再决定怎么操作」，而不是假设设备支持什么。面试里被问到任何「怎么做 X」时，如果 X 依赖某个可选能力，主动补一句「前提是设备通告了对应 capability，否则要降级成 Y」，这句话的分量往往比 X 本身还高。

面试前 10 分钟自检

下面每一条都应该能不看资料讲出 30 秒。讲不出来的，回到对应题目再看一遍：

  • 四层模型分别是什么，每一层换掉会变成哪个协议。
  • <hello> 协商了什么，为什么它自己不能用 chunked framing。
  • ]]>]]> 有什么问题，chunked framing 怎么解决，顺带带来了什么好处。
  • <get> 为什么必须带 filter。
  • 五种 operation 里哪一种会「删掉你没提到的东西」。
  • default-operation=none 为什么是生产推荐值。
  • confirmed-commit 防的是哪一类事故，为什么它不依赖客户端存活。
  • 锁的三个风险：粒度、持锁者失联、candidate 有脏数据时拿不到锁。
  • augment 和 deviation 的方向相反在哪里。
  • config false 为什么不能被 config true 的 leafref 指向。
  • NETCONF 比 RESTCONF/gNMI 多的那一样东西是什么（答案：跨请求的事务）。
  • O1 不等于 NETCONF，FM/PM 走的是什么。
  • hierarchical 与 hybrid 的差别只有一句话：O-RU 上挂几个客户端。
  • sysrepo 的两阶段变更通知为什么重要。
  • 大规模纳管的三件套：Call Home、退避加抖动、订阅代替轮询。
  • intended 减 operational 等于什么。
最后一个通用技巧：NETCONF 的题目几乎都可以用「它保护的是哪一类失败」来收尾。candidate 保护的是「改到一半」，confirmed-commit 保护的是「把自己关在门外」，lock 保护的是「两个人同时改」，deviation 保护的是「下发注定失败的配置」，NMDA 保护的是「以为生效了其实没有」。把机制和它对应的事故绑定起来讲，比复述规范条文有说服力得多——因为那正是这些机制被写进标准的原因。
