01

NETCONF vs YANG

Q1NETCONF 和 YANG 分别是什么？两者关系？
P0必考
要点
  • YANG：数据建模语言，定义配置/状态数据的结构、类型、约束（"菜单"）。
  • NETCONF：管理协议，用 XML/RPC 对这些数据做操作与传输（"点菜"）。
  • 关系：YANG 定义模型，NETCONF 按模型读写。二者正交——数据模型 vs 传输操作。
陷阱

别把 YANG 说成"协议"。它是建模语言，本身不传输任何东西。

Q2为什么需要 YANG？没有它会怎样？
P1概念
要点

没有统一模型，各厂商设备配置结构五花八门，自动化/多厂商管理极难。YANG 提供标准化、可校验、机器可读的模型，让工具自动生成校验与 API，是网络可编程的基础。

02

Datastore 与操作

Q3running / candidate / startup 三个 datastore 有什么区别？
P0高频
要点
  • running：当前生效的配置。
  • candidate：草稿区，可多次编辑后一次性 commit 到 running（支持事务）。
  • startup：重启后加载的配置（需 copy-config 保存）。
追问

confirmed-commit 做什么？——提交后若超时未确认自动回滚，防止改错配置把管理通道自己切断。

Q4get / get-config / edit-config 的区别？
P1操作
要点
  • get-config：只读配置数据（可指定 datastore）。
  • get：读配置 + 运行状态数据。
  • edit-config：修改配置（merge/replace/create/delete 等操作）。
Q5NETCONF 的四层模型是什么？
P1结构
要点

Content(YANG 数据) / Operations(get/edit-config 等) / Messages(rpc/rpc-reply/notification) / Secure Transport(SSH/TLS)。自上而下，最终落到安全传输。

03

安全传输

Q6NETCONF over SSH 和 over TLS 有什么区别？完整协议栈？
P0高频
要点
  • 协议栈：NETCONF → SSH/TLS → TCP → IP → Ethernet。
  • SSH(默认 830)：常用密码/公钥认证，部署简单。
  • TLS(6513)：基于 X.509 证书，天然支持 mTLS + cert-to-name（证书即身份），适合大规模自动化/O-RAN。
Q7cert-to-name 和 truststore 是干什么的？
P1工程
要点

truststore 存放信任的 CA 证书，用于验证对端证书链。cert-to-name 把客户端证书的字段映射到一个 NETCONF 用户名，实现基于证书的免密身份认证。

04

O1 与 O-RAN

Q8NETCONF/YANG 为什么出现在 O-RAN 里？和 O1 什么关系？
P0综合
要点

O-RAN 需要标准化、多厂商的管理面。O1 接口(SMO↔网元)就用 NETCONF/YANG 承载配置/故障/性能管理；前传的 M 平面(SMO/O-DU↔O-RU 管理)同样用 NETCONF over TLS/SSH。这就是它出现在 O-RAN 的原因。

05

协议横向对比

Q9NETCONF vs SNMP 有什么区别？
P0高频
要点
  • SNMP：MIB 建模、UDP、擅长监控/告警(get/trap)、配置弱、无事务、安全弱(v3才好)。
  • NETCONF：YANG 建模、SSH/TLS、擅长复杂配置、有事务(candidate/commit)、安全强。
  • 趋势：配置管理从 SNMP 转向 NETCONF/gNMI；SNMP 留在存量监控。
Q10NETCONF / RESTCONF / gNMI 怎么选？
P1对比
要点
  • 都可用 YANG。NETCONF：复杂配置+事务(电信/O1)；RESTCONF：REST/JSON，Web 自动化友好；gNMI：gRPC/Protobuf，强在高频流式遥测。
  • 选型看场景：事务配置→NETCONF，简单集成→RESTCONF，大规模遥测→gNMI。
06

工程实现

Q11用 C 实现 NETCONF 会用到哪些库？各负责什么？
P1实战
要点
  • libyang：解析/校验 YANG 模型与数据。
  • libnetconf2：NETCONF 协议栈(会话/RPC/SSH/TLS)。
  • sysrepo：datastore(配置存储/订阅/通知)。
  • netopeer2：基于上述的 NETCONF server 实现。
陷阱

常见坑：client/server YANG 模型版本不匹配导致校验失败；大配置的性能；证书/系统时间依赖(时间不对 TLS 握手失败)。
