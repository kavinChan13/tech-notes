通信系统与通信协议概览

这是「通信系统与通信协议」主题的总入口。先建立一张全局地图：什么是协议、协议为什么要分层、OSI 与 TCP/IP 到底在说什么，以及一段数据从你的应用程序走到网卡上到底经历了什么。理解这些，后面的 5G RAN、eCPRI、O-RAN、NETCONF/YANG 才不会变成一堆孤立的名词。

主题总纲 阅读 ~28 min 零基础可读 Why · What · How
01

通信、通信系统、通信协议

三个最基础、却最容易混为一谈的概念

通信（Communication）的本质，是把信息从一个地方准确地搬到另一个地方。人打电话、程序发消息、基站给手机推数据，本质都是同一件事：发送方把信息编码成信号，经过某种介质传播，接收方再解码还原。

🌉 生活类比：跨国寄一件易碎品

你要把一个花瓶从北京寄到慕尼黑。你不会把花瓶直接扔进邮筒——你会：装进气泡膜（编码/封装）、写上地址（寻址）、选顺丰还是海运（传输机制）、贴上"易碎/此面向上"（控制信息）。收件人拆开时按相反顺序还原。通信协议就是收发双方对"怎么装、怎么写地址、坏了怎么办"的一整套事先约定。

通信系统（Communication System）

为了完成通信而搭起来的软硬件整体：终端、传输介质、交换/路由设备、协议软件、管理系统……都是它的一部分。一个 4G/5G 网络就是一个巨大的通信系统。

通信协议（Protocol）

收发双方对数据格式 + 交互规则的约定。它规定"一个消息长什么样、字段怎么排、谁先说话、出错怎么办"。协议是通信系统里的"共同语言 + 交通规则"。

一句话记住三者关系：通信是目标，通信系统是达成目标的整套装置，通信协议是让装置里各方能对上话的规则。本主题主要沿着"协议 + 系统架构"这条线展开。
02

协议到底解决什么问题

没有协议会怎样，有了协议解决了哪些"麻烦"

如果双方没有事先约定，收到一串二进制 0x48 0x49 ... 根本无法解释：这是文字？图片？从哪开始算一条消息？谁是发送者？丢了一段怎么办？协议就是把这些"没法猜"的问题变成"事先约定好"的问题。

要解决的问题协议里对应的机制典型例子
语法：一条消息长什么样报文格式 / 字段布局 / 编码IP 头 20 字节、HTTP 的 \r\n 分隔
寻址：发给谁、谁发的地址字段（MAC / IP / Port）目的 IP + 目的端口
分界：一条消息到哪结束长度字段 / 分隔符 / 定长TCP 之上要自己做 framing
可靠：丢了/错了怎么办序号 / 确认 / 重传 / 校验TCP 的 ACK 与重传
时序：谁先说、状态怎么变状态机 / 握手 / 流程TCP 三次握手、TLS 握手
流控/拥塞：别把对方/网络压垮窗口 / 背压 / 拥塞算法TCP 滑动窗口、拥塞控制
把这张表记牢：后面每学一个协议（TCP、eCPRI、NETCONF…），都可以拿这 6 个问题去"套"——它是怎么定义报文的？怎么寻址的？怎么分界的？可靠性谁负责？状态机长什么样？如何做流控？这样学协议就不再是背 API。
03

为什么协议必须分层

分层不是学院派的洁癖，而是工程上的"解耦"

想象一下：如果每个应用都要自己处理"电信号怎么调制、比特怎么纠错、包怎么路由、丢了怎么重传、数据怎么加密"，那写一个聊天软件的复杂度将不可承受。分层的核心思想是：每一层只解决一类问题，并向上层提供一个"干净的抽象"，向下层依赖一个"稳定的接口"。

✅ 分层带来的好处

  • 关注点分离：应用层不关心是光纤还是 Wi-Fi
  • 可替换：把网卡从以太网换成 4G，上层代码不改
  • 可复用：TCP 之上可以跑 HTTP、也可以跑 MQTT
  • 可演进：IPv4 → IPv6，传输层基本不动

⚠️ 分层的代价

  • 每层都加头部 → 协议开销（overhead）
  • 层层拷贝 / 处理 → 延迟增加
  • 严格分层有时性能不够 → 出现跨层优化（如 eCPRI 直接跑在以太网上，绕开 TCP/IP）
为什么 5G 前传的 eCPRI 不走 TCP/IP，而是直接压在以太网上？
提示：因为分层的"延迟代价"在前传场景里无法接受——这正是理解本主题后半段（CPRI/eCPRI、Open Fronthaul）的关键。答案在 eCPRI 深入 一篇。
04

OSI 与 TCP/IP 模型

一个是"教学参考模型"，一个是"实际在跑的模型"

OSI 七层是国际标准化组织给出的理论参考模型，用来"讲清楚每层干嘛"；TCP/IP 四层是互联网真正在用的工程模型。学习时用 OSI 建立概念，做工程时按 TCP/IP 思考。

OSI vs TCP/IP 对比

维度OSI 七层TCP/IP 四层
定位理论参考 / 教学实际工程 / 互联网
层数7 层，划分更细4 层，更贴近实现
诞生先有模型后有实现（偏理论）先有实现后有模型（偏实践）
会话/表示层独立成层并入应用层（由 app 自己处理）
典型价值沟通时"对齐在第几层"排障/编程时的真实心智模型
面试高频："请把 OSI 和 TCP/IP 对应起来。"记住映射：OSI 5/6/7 → TCP/IP 应用层；OSI 4 → 传输层；OSI 3 → 网络层；OSI 1/2 → 网络接口层。
05

协议栈：数据从应用到网卡经历了什么

封装（encapsulation）与解封装，是整个网络的心跳

你在应用里调用 send("hello")，这几个字节要变成物理线上的信号，中间被逐层加上头部（封装）；到了对端再逐层剥掉头部（解封装）交给应用。这就是"协议栈"在做的事。

应用层你的数据：hello。应用协议决定它的含义（HTTP 请求？一条 NETCONF RPC？）
+ TCP/UDP 头加上源/目的端口、序号、校验 → 变成 Segment（TCP）/ Datagram（UDP）。解决"到了主机后，交给哪个进程"
+ IP 头加上源/目的 IP → 变成 Packet。解决"跨网络怎么找到目标主机（路由）"
+ 以太网头加上源/目的 MAC + 尾部 CRC → 变成 Frame。解决"在这一段链路上，交给哪块网卡"
物理层Frame 被编码成电/光/电磁信号，通过网线/光纤/空口发出去

数据单位随层次变化，这几个术语要分清：

层数据单位（PDU）关键地址
应用层Message / Data—（靠 URL、名字等）
传输层Segment (TCP) / Datagram (UDP)端口 Port
网络层Packet（分组）IP 地址
链路层Frame（帧）MAC 地址
物理层Bit（比特/信号）—
封装的顺序永远是"越往下头越多"，解封装时反过来。理解这一点，你就能看懂后面 eCPRI 帧（"以太网头 + eCPRI 头 + IQ 数据"）为什么长那样，也能看懂一个 NETCONF 请求是怎样"NETCONF over SSH over TCP over IP over Ethernet"层层封装出去的。
06

关键澄清：协议 ≠ 传输机制

这是初学者最容易混淆、也是本主题反复强调的一点

很多人会把"协议"和"传输机制"当成一回事，其实它们是两个正交的概念：

协议（Protocol）= 约定

规定数据长什么样、交互规则是什么。它是一份"契约"，本身不搬运数据。
例：eCPRI 规定了前传消息的格式；NETCONF 规定了配置操作的 RPC 语义。

传输机制（Transport）= 搬运

负责真正把字节从 A 送到 B：可靠还是尽力而为？面向连接还是无连接？
例：TCP、UDP、以太网都是"搬运工"。同一份数据可以选不同搬运工。

经典对照：eCPRI 是"协议"，以太网是"传输机制"——eCPRI 定义了要传什么、字段怎么排，以太网负责把这些帧真正送到对端。同理，NETCONF 是"协议"，SSH/TLS + TCP 是"传输机制"。区分开这两者，"eCPRI 到底跑在 TCP 上吗""NETCONF 为什么要 over SSH"这类问题就迎刃而解。
下面哪句对？(a) "eCPRI 是一种更快的 TCP"　(b) "eCPRI 是一种前传协议，通常直接承载在以太网上"。
答案：(b)。(a) 混淆了"协议"与"传输机制"——eCPRI 不是 TCP 的替代品，它是被以太网这个传输机制"搬运"的一种协议。
