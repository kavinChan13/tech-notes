核心网演进：从 EPC 到 5GC 服务化架构

前面几个模块把 UE → RU → DU → CU 讲透了，但那条链的右端一直写着一个模糊的方框「核心网」。本篇把这个方框拆开：4G EPC 有哪些网元、为什么控制面和用户面必须分离、5GC 的服务化架构（SBA）到底改了什么、一部手机开机注册和建立一条数据连接分别经过哪些网元。

Module 03 阅读 ~30 min EPC → 5GC
01

核心网到底在干什么

RAN 负责空口，核心网负责"这个人是谁、能上什么网、算多少钱"

很多人对核心网的印象是"基站后面那一坨服务器"。这个印象不算错，但没解释它为什么存在。换一个角度：无线接入网（RAN）解决的是"怎么把比特通过空气送出去"这个物理问题；而核心网解决的是"这些比特属于谁、要不要放行、按什么优先级走、最后送到哪里"这个业务与策略问题。

📦 类比：RAN 是最后一公里的快递员，只管把包裹从站点送到你手上；核心网是分拣中心 + 收费站 + 户籍处——它知道你是谁（户籍：鉴权与签约）、你的包裹该走哪条通道（分拣：会话与路由）、这趟运费怎么算（收费站：策略与计费），还负责在你换城市时把地址簿改掉（移动性管理）。快递员换一家公司无所谓，户籍处的记录不能丢。

把这句话展开，任何一代蜂窝核心网都在干五件事：

移动性管理 MobilityUE 在哪个小区、哪个跟踪区；换区时更新位置、维持连接不断；空闲态如何被寻呼。
会话管理 Session建立/修改/释放一条到数据网的隧道，分配 IP，决定这条隧道经过哪个转发节点。
鉴权与安全 AuthSIM 卡里的密钥与网络侧签约数据做双向认证，派生加密与完整性保护密钥。
策略与计费 Policy这个套餐能跑多少带宽、哪些业务免流、超量后限速还是断网；产生计费记录。
对外出口 Gateway作为移动网络与 Internet / IMS / 企业专网之间的边界，做 NAT、防火墙、DPI。
控制面 vs 用户面：核心网内部一条铁律般的划分。控制面（Control Plane）处理信令——注册、鉴权、建立会话、切换，报文少但逻辑复杂、状态多；用户面（User Plane）只做一件事：按控制面下发的规则转发用户数据包，逻辑简单但吞吐巨大。这两者的性能曲线完全不同，这就是后面 CUPS 拆分的根本动机。
02

4G EPC：网元与接口

先看清一个"能跑但耦合"的设计

EPC（Evolved Packet Core）是 4G LTE 的核心网。它的一个历史性进步是全 IP、纯分组——2G/3G 时代还残留电路域，EPC 把语音也推向 IMS/VoLTE，核心网只做分组转发。EPC 由五个主要网元组成：

网元全称职责面
MMEMobility Management EntityUE 的信令大脑：附着/去附着、鉴权（向 HSS 取向量）、跟踪区更新、寻呼、承载管理、切换控制、NAS 加密与完整性保护控制面
S-GWServing Gateway本地锚点：UE 在基站间移动时，隧道的一端固定在 S-GW，把移动性对 P-GW 屏蔽掉；空闲态缓存下行包并触发寻呼用户面（+少量控制）
P-GWPDN Gateway出口锚点：分配 UE 的 IP、连接外部数据网、执行 QoS 与计费规则、DPI/NAT/防火墙用户面（+少量控制）
HSSHome Subscriber Server签约数据库：用户身份、密钥 K、允许的 APN、QoS 上限；生成鉴权向量数据层
PCRFPolicy and Charging Rules Function策略决策：按套餐/业务/时段下发 QoS 与计费规则给 P-GW 执行控制面
GTP（GPRS Tunnelling Protocol）：3GPP 自家的隧道协议。GTP-U 跑在 UDP/2152 上，在用户 IP 包外面加一层 GTP 头，用 TEID（Tunnel Endpoint Identifier）标识"这是哪个 UE 的哪条承载"。这样 UE 换基站时，只要把隧道的一端重指向新基站，UE 的 IP 完全不用变——这就是移动性的实现基础。GTP-C 是配套的控制协议，负责隧道的增删改。

2.1 为什么"控制面与用户面耦合"变成了瓶颈

EPC 的设计缺陷不在功能，而在形状。S-GW 和 P-GW 是"控制逻辑 + 转发引擎"揉在一个网元里的盒子：同一台设备既要维护会话状态、跑 GTP-C 状态机，又要以线速转发 GTP-U 报文。这带来三个现实问题：

  • 扩容维度绑死。视频业务爆发时需要的是转发能力（Gbps、Mpps），而信令量几乎没涨；但因为控制与转发同体，只能整台扩，买回来的控制面算力全是浪费。反过来，物联网海量小连接场景信令暴涨、流量很小，同样浪费转发芯片。
  • 无法按时延下沉。想把出口放到离用户更近的地方（降低时延），就必须把整个 P-GW 搬下去，连带把策略、计费、签约交互也搬到边缘——运维和一致性代价高得离谱。
  • 点对点接口固化。S11、S5、Gx、S6a 每条都是专用协议栈（GTP-C、Diameter），新增一个功能往往要动多条接口的标准，迭代周期以年计。
"EPC 有什么问题，为什么要演进到 5GC？"
答：功能上没问题，问题是形状。控制面与用户面在同一网元里，导致扩容维度绑死、转发面无法独立下沉到边缘、接口是点对点专用协议难以演进。5GC 的两个核心动作正是针对这三点：CUPS 把面拆开，SBA 把点对点接口换成服务化调用。
03

CUPS 与 5GC 的拆分

一个网元拆成一堆网络功能

CUPS（Control and User Plane Separation）：3GPP R14 先在 EPC 上做的过渡方案——把 S-GW / P-GW 各自拆成 S-GW-C / S-GW-U、P-GW-C / P-GW-U，中间用 Sx 接口 + PFCP 协议通信。5GC 把这个思路做彻底：控制面只剩若干"网络功能"，用户面只剩一个 UPF。

5GC 的控制面被切成职责单一的网络功能（NF, Network Function）：

NF全称它接管了 EPC 里的什么
AMFAccess and Mobility Management FunctionMME 的接入与移动性部分：NAS 信令终结点、注册管理、连接管理、寻呼、接入侧安全
SMFSession Management FunctionMME 的会话管理部分 + S-GW-C/P-GW-C：分配 UE IP、选择 UPF、通过 N4 下发转发规则
UPFUser Plane FunctionS-GW-U + P-GW-U：唯一的转发面，做 GTP-U 封解封、QoS 执行、用量统计、分流
AUSFAuthentication Server FunctionHSS 的鉴权服务部分：执行 5G-AKA / EAP-AKA′ 鉴权流程
UDM / UDRUnified Data Management / RepositoryHSS 的签约数据部分；UDM 是逻辑，UDR 是后端存储（数据与逻辑也拆开了）
PCFPolicy Control FunctionPCRF：策略决策，下发给 SMF 执行
NRFNetwork Repository FunctionEPC 没有对应物：NF 的注册中心与服务发现
NSSFNetwork Slice Selection FunctionEPC 没有对应物：为 UE 选择网络切片实例
NEFNetwork Exposure Function把网络能力（位置、QoS 调整、事件订阅）以 API 形式安全暴露给第三方
不要背成一一对应。最常见的错误是"AMF = MME"。真相是 MME ≈ AMF + SMF 的一部分 + 一点 AUSF 的编排逻辑：MME 既管接入移动性，也管承载/会话，还负责去 HSS 取鉴权向量。5GC 按"职责"重切了刀，切线和 EPC 的网元边界并不平行。同理 P-GW ≈ SMF（控制） + UPF（转发），你没法说 P-GW 等于哪一个。

3.1 EPC ↔ 5GC 网元对照表

能力4G EPC5GC关键差异
接入与移动性信令MMEAMFAMF 不再管会话；一个 AMF 可服务多个切片
会话管理MME + S-GW-C + P-GW-CSMF会话逻辑收敛到一个 NF，可按切片/DNN 部署多实例
用户面转发S-GW-U + P-GW-UUPF合并为一种网元，可级联（N9）、可下沉边缘

3.2 N 系列参考点速查

5GC 不再用 S1/S5/S11 这种编号，改用 N1–N9 参考点（reference point）。注意"参考点"和"服务化接口"是两种视角：N 系列描述谁和谁之间有交互，SBI（Nxxx 服务）描述通过什么 API 调用。

参考点两端承载什么协议
N1UE ↔ AMFNAS 信令（注册、会话请求、鉴权）。对 gNB 透明——gNB 只是转发容器NAS over RRC/NGAP
N2gNB ↔ AMF接入侧控制：UE 上下文建立、切换、PDU 会话资源建立（含 QoS Flow 参数）NGAP / SCTP
N3gNB ↔ UPF用户数据（相当于 4G 的 S1-U）GTP-U / UDP
N4SMF ↔ UPF转发规则下发：PDR / FAR / QER / URRPFCP / UDP
N6UPF ↔ 数据网出口流量（相当于 4G 的 SGi）IP
N9UPF ↔ UPFUPF 级联：I-UPF（中间）到 PSA-UPF（锚点），漫游与边缘分流用GTP-U
N11AMF ↔ SMF会话管理请求转发（AMF 只是 NAS SM 消息的邮差）HTTP/2 (Nsmf)
N12/N13AMF↔AUSF / AUSF↔UDM鉴权流程HTTP/2
PFCP（Packet Forwarding Control Protocol）：N4 上 SMF 指挥 UPF 的协议。它下发四类规则：PDR（Packet Detection Rule，怎么识别这个包属于哪条会话）、FAR（Forwarding Action Rule，转发/丢弃/缓存到哪里）、QER（QoS Enforcement Rule，限速与标记）、URR（Usage Reporting Rule，用量上报触发条件）。理解 PFCP 就理解了"控制面到底怎么控制转发面"——它不是转发数据，而是下发一张表。
NAS（Non-Access Stratum）：UE 与核心网之间的信令层，跳过接入网直接对话。分 5GMM（移动性管理：注册、鉴权、服务请求）和 5GSM（会话管理：PDU 会话建立/修改/释放）。NAS 消息在空口被 RRC 承载、在 N2 被 NGAP 承载，中间的 gNB 看不懂也不需要看懂 NAS 内容（它是加密的）。这是"接入网与核心网解耦"的具体体现。
04

SBA：服务化架构

从"专线电话"到"注册中心 + HTTP 调用"

SBA（Service Based Architecture）是 5GC 相对 EPC 最像"软件架构升级"的一步。EPC 的接口是点对点专用协议：MME 要和 HSS 说话就得实现 Diameter S6a，要和 S-GW 说话就得实现 GTP-C S11。每加一个交互就是一套新协议栈、一份新标准。

SBA 把这些全换成同一套技术底座：

传输TCP + TLS
应用协议HTTP/2（多路复用、头压缩、服务端推送用于 Notification）
风格RESTful + 少量自定义方法，资源与操作在 3GPP TS 29.5xx 里逐个定义
编码JSON（OpenAPI 描述），二进制附件用 multipart
发现NRF 注册 + 查询，返回候选实例列表与优先级

于是每个 NF 既是服务生产者又是消费者。SMF 要取策略就调 Npcf_SMPolicyControl_Create，要通知 AMF 就调 Namf_Communication。接口名统一形如 N<nf>_<Service>_<Operation>。

4.1 和互联网微服务的异同

如果你熟悉 微服务架构，SBA 会让你有强烈的既视感——服务注册发现、松耦合、独立伸缩、API 版本化，思想完全一致，这里不重复讲这些通用能力。真正值得琢磨的是差异：

维度互联网微服务5GC SBA
接口定义权团队自治，内部约定即可，可随时重构3GPP 强标准化：OpenAPI 由标准给定，多厂商必须互通，不能随意改字段
可用性目标99.9%~99.95% 常见，降级可接受99.999%：一年不可用 5 分钟；且"降级"要有明确的标准行为而非随手兜底
状态处理常见做法是服务内存态 + 会话粘性要求状态外置（UDSF / 共享存储），任一实例宕掉后 UE 上下文必须可被接管
时延预算用户可感知的是百毫秒级信令流程有明确预算（如切换中断 < 数十 ms），URLLC 场景更严
失败语义重试 + 幂等，最终一致信令流程多为有状态事务：半建立的会话必须能被清理，否则泄漏"僵尸会话"
版本演进灰度发布，快速迭代R15/R16/R17 版本共存，需要长期向后兼容与能力协商
"5GC 就是把核心网写成微服务？"——方向对，但有两点必须补上：① 接口不是你定的，是 3GPP 定的，跨厂商互通是硬约束，这决定了你不能靠"改协议"解决问题，只能在实现内做优化；② 可用性要求高两个数量级，逼出了状态外置、无状态 NF、N+1 冗余这套做法，而不是靠"挂了就重试"。
05

两条关键流程

开机注册 + 建立数据连接，走一遍就把网元关系记住了

核心网的网元表背下来没用，把两条主流程走通才算懂。这两条流程也是面试里出现频率最高的题。

5.1 注册流程 Registration

注册 ≠ 能上网。这是初学者最容易忽略的一刀切分：注册解决"你是谁、允许你接入"，会话解决"给你一条通往数据网的管子"。4G 里 attach 会顺带建默认承载所以感觉是一步；5G 明确把两者分开，UE 可以只注册不建会话（比如仅接收短信/寻呼）。

5.2 PDU 会话建立

PDU Session：UE 与某个数据网（由 DNN, Data Network Name 标识，相当于 4G 的 APN）之间的一条逻辑连接。它有类型（IPv4 / IPv6 / IPv4v6 / Ethernet / Unstructured）、有 SSC 模式（会话连续性策略），内部再切分成多条 QoS Flow。一个 UE 可以同时有多条 PDU 会话，分别落在不同切片、不同 UPF 上。
GTP-U 隧道为什么必须存在：UE 的 IP 是核心网分配的，属于 UPF 后面的地址段。如果不封装，UE 发出的包在回传网上会被当成来源伪造的普通 IP 包路由掉，而且基站换了之后网络也不知道该把下行包送到哪。GTP-U 用 TEID 建立了"UE 的这条会话 ↔ 当前服务基站"的映射，切换时只改这个映射，UE 的 IP 和上层 TCP 连接都不受影响。
失败模式提醒：这条流程里任何一步超时都会留下"半建立"状态——SMF 有 SM 上下文、UPF 有规则、gNB 没有资源。5GC 必须靠定时器 + 显式清理流程兜底，否则大规模信令风暴后会残留大量僵尸会话，占着 IP 池和 UPF 规则表不放。这类"事务补偿"逻辑是核心网软件复杂度的主要来源之一，和 协议状态机那篇讲的定时器治理是同一类问题。
06

NSA vs SA

为什么运营商先上 NSA，以及它对 RAN 软件意味着什么

5G 部署有一堆 3GPP "Option" 编号，实际落地的只有两种：

NSA（Option 3x）SA（Option 2）
核心网沿用 EPC（升级支持 5G 承载）5GC
控制面锚点LTE eNB（主节点 MN）gNB 自己
gNB 角色辅节点 SN，只加数据速率，不承载 NAS完整节点，承载 NAS 与所有信令
用户面Option 3x：分流点在 gNB，S1-U 直连 gNB 再分给 eNBgNB → UPF (N3)
UE 要求必须同时连 LTE 和 NR（EN-DC 双连接）只连 NR
能力只有大带宽；没有切片、URLLC、边缘分流全部 5G 特性
投资复用现网 EPC 与 LTE 覆盖，最快见效要新建 5GC，投资大、周期长
EN-DC（E-UTRA NR Dual Connectivity）：UE 同时和一个 LTE 基站（主）与一个 NR 基站（辅）保持连接。控制信令走 LTE 保证覆盖与稳定，用户数据可以在两边同时跑或全部走 NR。这就是 NSA 的技术本质——5G 当成 LTE 的一个大带宽载波。

运营商先上 NSA 的原因很实际：5G 高频段覆盖差，如果控制面也放在 NR 上，UE 一走到边缘就掉网；而 NSA 让控制面留在覆盖好的 LTE 上，NR 只在信号好的时候贡献速率，用户体验反而更稳。加上不用新建核心网，能在两三年内把"5G 商用"这件事做出来。

对 RAN 侧软件的三个具体影响：① gNB 要实现 X2/Xn 双连接的辅节点角色（承载分离、SN 添加/修改/释放流程），复杂度不比独立组网低；② gNB 的 PDCP 要支持分流与重排序——数据在两条无线链路上乱序到达，重组逻辑是真实的踩坑点；③ 因为没有 5GC，所有切片、边缘分流、URLLC QoS 相关代码在 NSA 上都跑不起来，同一份软件要能在两种组网下降级运行，配置分支会显著变多。
07

接回整张图 + 三组易混

把核心网嵌进本主题的主线

UE ↔ RAN空口 + 前传/中传，见 CU / DU / RU 功能拆分、前传中传后传
RAN ↔ 核心网回传承载 N2（NGAP/SCTP，控制）与 N3（GTP-U，数据）——两者跑在同一张 IP 回传网上，靠 QoS/VLAN 隔离
核心网内部控制面 SBI（HTTP/2）+ 用户面 N4/N9，本篇主体
核心网 ↔ 数据网N6，出口策略、NAT、防火墙
管理面核心网自己的 OAM（配置、性能、告警），与 O-RAN O1 是不同的管理面

下面三组混淆在面试和实际排障里都常见，值得单独钉住：

① GTP-U ≠ eCPRI
两者层次完全不同。eCPRI 是前传协议，搬运的是 DU↔RU 之间的 IQ 采样/时频数据，直接跑在以太网上、时延预算是几十微秒；GTP-U 是回传/核心网隧道，搬运的是已经解调完成的用户 IP 包，跑在 UDP/IP 上。一个在物理层与高层之间，一个在网络层之上。它们在协议栈上甚至不在同一段链路。
② 核心网 OAM ≠ O-RAN O1
O1 是 O-RAN 定义的 SMO ↔ O-RAN 网元管理接口，用 NETCONF/YANG，管的是 O-DU/O-CU/O-RU。5GC 的网元管理走的是 3GPP 定义的管理服务（TS 28.5xx，常见实现是 RESTful 的 MnS 管理服务，或厂商自有 EMS）。两者都是"管理面"，但归属不同标准组织、模型和协议都不一样。把 5GC 网元接到 O1 上是行不通的。
③ UPF 才是转发面，不是 SMF
SMF 名字里有 "Session"，容易被误解为"用户数据经过它"。SMF 一个用户数据包都不碰，它只是通过 N4/PFCP 下发规则表。这个区分很重要：优化用户面吞吐要动 UPF（DPDK、SR-IOV、硬件卸载），优化信令能力要动 SMF（并发上下文数、状态存储）。压测时把两者混在一个指标里是常见错误。
08

工程视角：规模与状态

核心网软件难在哪

8.1 状态量的数量级

一个中等规模的 AMF 实例要维护数百万 UE 的上下文：每个 UE 有身份标识、安全上下文（密钥集）、位置（TAI list）、注册状态、活跃的 PDU 会话列表、各种定时器。SMF 侧每条 PDU 会话有 QoS Flow 列表、UPF 绑定、用量计数器。粗算下来单实例常驻内存是几十 GB 量级，而且这些状态不能丢。

这直接决定了几件事：

  • 数据结构选择极其敏感。上下文查找在信令热路径上，哈希表的负载因子、每个上下文的内存布局、指针 vs 索引，都会直接反映在容量指标上。这里的取舍思路和 高性能通信那篇讲的是一套。
  • 定时器规模是设计约束。数百万 UE × 每 UE 若干定时器 = 千万级定时器，用最小堆会被插入删除拖死，必须用时间轮；这部分见 协议状态机。
  • 状态必须能外置。为了做到实例无状态（挂了能被接管），上下文要写到共享存储（UDSF 或分布式 KV），于是"写多少、多久写一次、丢多少可接受"变成核心权衡——详见 电信云原生。

8.2 信令风暴与拥塞控制

核心网最典型的雪崩场景：一个区域断电恢复，几十万 UE 同时重新注册。峰值信令可能是正常值的数十倍。如果没有保护，AMF 的 CPU 打满 → 处理变慢 → UE 超时重发 → 信令量再翻倍 → 彻底不可用。这是一个正反馈环。

标准与实现层面的应对手段是分层的：

层次手段代价
空口RACH 接入前缀 / 接入类别限制（Access Barring）：直接不让部分 UE 发起接入被限的用户完全无服务，但保住了整网
RAN↔核心网AMF 通过 N2 下发过载指示（Overload Start/Stop），gNB 按比例丢弃或延迟转发信令部分 UE 注册变慢
NAS回退定时器（Back-off Timer）：拒绝时告诉 UE "T 秒后再试"，T 带随机化打散重试需要 UE 实现正确，老终端可能不遵守
NF 内部有界队列 + 优先级（紧急呼叫、切换优于首次注册）+ 快速拒绝要提前区分消息优先级，逻辑复杂
SBI 之间NF 之间的过载控制与熔断，避免下游慢拖垮上游与 限流熔断同一套思路，但要符合 3GPP 定义的拒绝原因码
关键洞见：这些手段的共同点是把过载推到边缘、尽早拒绝。最糟糕的设计是"来者不拒地排队"——请求在队列里排到超时，UE 已经重发了，服务器还在处理过期请求，做的全是无效工作。这就是背压的核心，和 通信系统可靠性那篇讲的是同一条原则。

8.3 五个 9 从哪来

99.999% 意味着一年不可用时间 < 5.26 分钟。这个数字不可能靠"单机很稳"达到，只能靠结构：

  • N+1 / N+M 冗余 + 无状态实例：任一实例宕掉，其他实例从共享存储接管上下文；对 UE 而言最多是一次重试。
  • 地理冗余：整个机房级故障时，UE 通过 NRF 发现另一个站点的 NF 实例（跨站点注册）。
  • 故障域隔离：切片之间、DNN 之间、UPF 之间不共享故障域，避免一个业务把整网拖下水。
  • 滚动升级不中断：这是电信云原生的硬骨头——升级时长连接（SCTP 偶联、NETCONF 会话）会被打断，必须有连接排空与优雅退出策略。
  • MTTR 优先于 MTBF：与其追求"永不故障"，不如把检测 + 切换压到秒级。这决定了健康检查、心跳、故障判定阈值的设计比冗余数量更关键。
