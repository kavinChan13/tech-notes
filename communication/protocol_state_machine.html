协议状态机：从 TCP / RRC / NETCONF 到可维护的 FSM

通信软件架构的 §03 提到"控制面就是一堆状态机"，本篇把它展开：协议状态机在真实协议里长什么样、四种实现手法各自适合什么规模、定时器怎么管才不悬垂、以及怎么让状态机变成可测试、可观测的东西而不是一坨 switch。

Module 09 阅读 ~28 min 含交互演示
01

为什么通信软件到处是状态机

协议的定义本身就是一台状态机

翻开任何一份协议规范，核心内容几乎总是这四样东西：有哪些状态、会收到哪些事件、什么状态收到什么事件迁移到哪、各状态下哪些定时器在跑。换句话说：

协议 = 状态 × 事件 × 迁移 × 定时器。这四个维度缺一个都不成立：没有状态就无法表达"握手做到哪一步了"；没有事件就无法响应对端；没有明确的迁移就会对同一消息做出不一致的反应；没有定时器，任何一次对端不回应都会让你永远卡住——分布式系统里"对端沉默"和"对端很慢"无法区分，只能靠超时来判定。
🚇 类比：地铁闸机。状态只有"关闭 / 已验票待通过 / 开启"，事件是"刷卡 / 通过感应 / 超时"。你刷了卡但不走，5 秒后闸机自己关回去（定时器）；你在闸机关闭时硬挤，它不理你（非法事件被拒绝）。它绝不会"因为你刷了两次卡就开两倍宽"——状态机的价值就是把"系统在任意时刻只能处于一个明确状态、且只接受该状态允许的输入"这件事变成结构而不是靠人记住。通信协议之所以离不开它，是因为对端是不可信的：畸形的、乱序的、重复的、恶意的消息都会来，你需要一个能对任何输入给出确定反应的东西。

反过来说，通信软件里凡是"用一堆 bool 标志位表达进度"的地方，几乎都是一个没被识别出来的状态机。is_connected、hello_sent、auth_done、closing 四个标志位理论上表达 16 种组合，其中合法的可能只有 5 种——剩下 11 种是"不该出现但代码里可以出现"的状态，也就是 bug 的藏身处。把它们收敐成一个显式的枚举状态，非法组合在类型层面就消失了。

面试里怎么答"你怎么判断该不该引入状态机"：数一数表达"进度"的布尔标志位。超过两个、并且它们之间存在"A 为真时 B 必须为假"这类隐含约束，就该换成显式状态机。这个判据比"代码行数"或"看起来复杂"都靠得住。
02

四个真实状态机

从最经典的到最工程化的

2.1 TCP 连接状态机

最经典的例子。它值得看的不是"有 11 个状态"，而是为什么需要 TIME_WAIT 这个看似多余的状态——那是状态机设计里"为不可靠网络留余量"的典范。

2.2 5G RRC：IDLE / INACTIVE / CONNECTED

RRC 状态机只有三个状态，但它体现了一个 TCP 没有的设计动机：用中间状态换功耗与信令量。

RRC 的 INACTIVE 是"状态机换成本"的教科书案例：加一个状态、加一套上下文保留与 RAN 寻呼机制，换来的是海量间歇性小流量终端（IoT、后台推送）不必反复付完整建立的信令代价。设计状态机时值得反复问的问题就是这个——加一个状态，能省下什么？

2.3 NETCONF 会话

上图下半部分。它形状简单（近似线性），难点在失败清理：会话在"持有 candidate 配置 + 持有 datastore 锁 + 有活跃通知订阅"的状态下断开，这三样都必须被回收。NETCONF 工程实践讲了 datastore 与 commit 语义；这里要强调的是状态机视角：每个"已获取的资源"都应该绑定到某个状态的进入/退出动作上，而不是散落在各个消息处理函数里靠人配平。

2.4 O-RU M-plane 启动流程

这是一个"工程化到不像教科书"的状态机：O-RAN 接口里 O-RU 上电到可服务的完整过程。它的特点是状态多、每步都可能失败、失败后的退避与重试策略各不相同。

① 上电自检硬件自检、加载固件。失败 → 点告警灯，不重试（需人工）。
② 获取管理 IPDHCP 或静态。失败 → 持续重试并指数退避，因为网络可能还没就绪。
③ 发现控制器通过 DHCP 选项 / mDNS 找到 SMO/NETCONF 客户端的地址。这一步的超时值直接决定"网络慢时能不能起来"。
④ 建立 NETCONF 会话Call Home（O-RU 主动连出）+ SSH/TLS。证书不匹配 → 明确的告警而不是无声重试。
⑤ 能力与模型协商交换 hello、比对 YANG 模型版本。不兼容 → 上报并停在此状态，别硬着头皮往下走。
⑥ 接受配置SMO 下发载波、天线、C/U 平面参数。事务性：部分失败要整体回滚。
⑦ 同步锁定等 PTP 达到要求的时钟类别。没锁定绝不能开始发射——这是硬性前置条件，也是最常见的"卡在这一步"现场。
⑧ 载波激活 / 服务中开始收发 eCPRI 用户面。之后任何一步的前置条件破坏（PTP 失锁）都要退回相应状态。
这个例子最值得学的一点：状态机必须能"往回走"。⑦ 里 PTP 失锁之后，正确行为是停止发射并退回等同步状态，而不是继续发射错误的信号（那会干扰邻区）。很多真实 bug 就是只实现了前进路径，忘了实现"前置条件被破坏时的回退"。写状态机时的自查方法：对每个状态，列出它成立所依赖的前置条件，再确认每个条件失效时都有对应的退出迁移。

怎么选（这是面试高频题）：状态 ≤ 5 且逻辑简单 → switch，别过度设计；状态 5–20、规范里本来就有一张迁移表 → 状态转移表，这是通信软件里性价比最高的选择；每个状态有大量独有行为与私有数据 → State 模式；希望"非法的(状态,事件)组合根本无法编译" → variant FSM。核心判据不是性能（四者在信令面差别可忽略），而是规范演进时改动的局部性。

3.1 状态转移表：通信软件的默认选择

// 表的每一行就是规范里的一行，评审时可以逐行对照
enum class St : uint8_t { Idle, Inactive, Connected, N };
enum class Ev : uint8_t { Setup, Suspend, Resume, Release, T310, N };

struct Tr { St next; void (*action)(Ctx&); };
constexpr Tr kNo{St::N, nullptr};                 // 非法迁移

constexpr Tr kTable[(int)St::N][(int)Ev::N] = {
/*            Setup            Suspend  Resume                Release          T310   */
/*Idle     */{{St::Connected,&do_setup}, kNo, kNo, kNo, kNo},
/*Inactive */{kNo, kNo, {St::Connected,&do_resume}, {St::Idle,&do_rel}, kNo},
/*Connected*/{kNo, {St::Inactive,&do_susp}, kNo, {St::Idle,&do_rel}, {St::Idle,&do_rlf}},
};

void Fsm::feed(Ev e, Ctx& c) {
  const Tr& t = kTable[(int)st_][(int)e];
  if (t.next == St::N) {                          // 统一处理非法事件
    ++stats_.illegal[(int)st_][(int)e];           // 打点，别静默丢
    return;
  }
  if (t.action) t.action(c);
  log_transition(st_, e, t.next);                 // 一处埋点覆盖全部迁移
  st_ = t.next;
}
转移表的隐藏收益：横切关注点只写一遍。非法事件计数、迁移日志、进入/退出动作、状态驻留时间统计——在 switch 实现里这些要在每个 case 里重复；在表驱动实现里只在 feed() 里写一次。通信软件的可观测性需求很重（现场排障全靠迁移日志），这一点的价值往往超过性能考虑。

3.2 variant FSM：让非法组合无法编译

完整的可编译小例子。核心思路：状态是不同的类型（而不是同一个枚举的不同取值），迁移函数按 (状态类型, 事件类型) 重载，std::visit 做双分派。

// ---- 状态：每个状态携带自己的数据，别的状态访问不到 ----
struct Idle      { };
struct Inactive  { std::uint32_t i_rnti; std::chrono::steady_clock::time_point since; };
struct Connected { std::uint32_t c_rnti; int drb_count; };
using State = std::variant<Idle, Inactive, Connected>;

// ---- 事件 ----
struct Setup   { std::uint32_t rnti; };
struct Suspend { std::uint32_t i_rnti; };
struct Resume  { std::uint32_t i_rnti; };
struct Release { };
struct T310    { };                       // 无线链路失败
using Event = std::variant<Setup, Suspend, Resume, Release, T310>;

// ---- 迁移：只为合法组合写重载 ----
struct Transition {
  Log& log;

  State operator()(Idle,            const Setup& e) const {
    log.info("Idle -> Connected");  return Connected{e.rnti, 0};
  }
  State operator()(const Connected& s, const Suspend& e) const {
    log.info("Connected -> Inactive"); (void)s;
    return Inactive{e.i_rnti, std::chrono::steady_clock::now()};
  }
  State operator()(const Inactive& s, const Resume&) const {
    log.info("Inactive -> Connected"); return Connected{s.i_rnti, 0};
  }
  State operator()(const Connected&, const Release&) const { return Idle{}; }
  State operator()(const Inactive&,  const Release&) const { return Idle{}; }
  State operator()(const Connected&, const T310&)    const {
    log.warn("radio link failure"); return Idle{};
  }

  // 兜底：所有未列出的 (状态,事件) 组合走这里 —— 非法事件
  template <class S, class E>
  State operator()(const S& s, const E&) const {
    log.warn("illegal event in current state");  // 打点 + 保持原状态
    return s;
  }
};

// ---- 驱动 ----
class Fsm {
 public:
  void feed(const Event& ev) {
    st_ = std::visit(Transition{log_}, st_, ev);   // 双分派
  }
  bool connected() const { return std::holds_alternative<Connected>(st_); }
 private:
  State st_{Idle{}};
  Log   log_;
};
这个写法的三个真实好处。① 状态数据被状态本身守住：c_rnti 只存在于 Connected 里，处于 Idle 时代码根本拿不到它——这消灭了"用了一个当前状态下无意义的字段"这一整类 bug（在枚举 + 大结构体的写法里非常常见）。② 迁移是纯函数：输入 (状态, 事件)，输出新状态，没有隐藏的副作用，单元测试可以直接构造任意状态。③ 删掉兜底模板，非法组合就变成编译错误——如果你的协议要求穷尽处理，这是最强的保证。
代价也要说清：编译期变长、错误信息难读、双分派的跳转表在每包热路径上要实测。它属于"控制面首选、数据面慎用"。
04

定时器与超时

状态机一半的复杂度在这里

最小堆（priority_queue）时间轮（timing wheel）
插入O(log n)O(1)
取消O(log n)（或懒删除，堆会膨胀）O(1)（从槽链表摘除）
取最早O(1) 查看，O(log n) 弹出O(1) 推进指针
精度任意精度受槽粒度限制（如 1 ms/槽）
长时限天然支持需分层轮（秒轮/分轮/时轮）
适合定时器少、时限跨度大、需要高精度海量同类定时器（每连接/每会话，时限相近）
为什么通信软件几乎都用时间轮：核心网那篇算过，百万级 UE × 每 UE 若干定时器 = 千万级定时器，而且绝大多数定时器会被取消而不是到期（收到回应就取消重传定时器）。最小堆在这种"高频插入 + 高频取消"的模式下会被 O(log n) 和懒删除导致的堆膨胀拖死；时间轮的插入与取消都是 O(1)，且时限集中在几个固定值上（协议规定的 T300/T310 等），正好落进少量槽里。这不是"时间轮更高级"，而是负载特征决定的选择。

4.1 经典竞态：定时器回调触发时对象已析构

这是通信软件里最高发的 UAF（use-after-free）来源，没有例外。

❌ 定时器捕获裸 this
class Session {
  void arm_retransmit() {
    timer_.after(500ms, [this] {   // ⚠️ 裸 this
      this->retransmit();
    });
  }
  ~Session() { }                   // 忘了 / 无法可靠取消
};

// 时序：
// t0  会话 arm 了 500ms 重传定时器
// t1  对端发来 Release，会话对象被销毁
// t2  定时器线程到期，回调执行 → 悬垂 this → UAF
// 即使在析构里调 timer_.cancel()，仍有窗口：
// 回调已被定时器线程取出、正要执行，cancel 已经来不及
✅ weak_ptr 提升 / 取消令牌
class Session : public std::enable_shared_from_this<Session> {
  void arm_retransmit() {
    timer_.after(500ms,
      [w = weak_from_this()] {
        if (auto self = w.lock())  // 对象还活着才执行
          self->retransmit();
        // 否则什么都不做：竞态被结构性消除
      });
  }
};

// 另一种：取消令牌（不想引入 shared_ptr 时）
struct Token { std::atomic<bool> cancelled{false}; };

timer_.after(500ms, [tok = tok_, this] {
  if (tok->cancelled.load(std::memory_order_acquire)) return;
  retransmit();          // 前提：回调与析构在同一线程/同一 actor
});
~Session() { tok_->cancelled.store(true, std::memory_order_release); }
注意两种方案的适用前提不同，这一点常被忽略。weak_ptr 方案本身就线程安全（lock() 是原子的），代价是会话必须由 shared_ptr 管理、且回调期间对象被延长生命周期。取消令牌方案只有在"回调执行与对象析构发生在同一线程（或同一 actor 的消息循环）"时才安全——否则"检查 cancelled 为 false"和"执行 retransmit"之间仍有窗口，对象可能在这个窗口里被析构。跨线程场景请用 weak_ptr，或者干脆把定时器到期也做成一个投递给该会话的消息（见第 6、7 节），这样根本不存在跨线程回调。shared_ptr/weak_ptr 的所有权语义细节见 智能指针深入。

重传与指数退避：协议定时器几乎都要退避。三个容易写错的地方——① 必须有上限（不然退避到几分钟，故障恢复后要等很久）；② 必须加随机抖动（否则一次网络闪断后所有会话在同一毫秒重试，制造自己的信令风暴）；③ 退避计数要在成功后重置，忘了重置会导致长期运行的连接越来越迟钝。

05

分层状态机 HSM

治理状态爆炸

扁平状态机的状态数会乘性爆炸。举个真实例子：一个会话有"连接状态"（3 种）× "配置事务状态"（4 种）× "同步状态"（2 种），扁平展开是 24 个状态，而且大量迁移是重复的（"任何状态下收到 Release 都回 Idle"这条规则要写 24 遍）。

HSM（Hierarchical State Machine）：状态可以嵌套。子状态未处理的事件会冒泡到父状态处理。于是"任何连接子状态下收到 Release 都断开"这条规则只在父状态 Connected 里写一次，所有子状态自动继承。这就是把 24 条重复迁移压缩成 1 条的机制。
正交区域不是免费的。它成立的前提是各区域之间真的正交。一旦出现"同步失锁时不允许提交配置"这种跨区域约束，就必须显式建模成"区域间的守卫条件（guard）"，否则约束会变成散落在各处的 if (ptp_locked_) 检查，退化成最初那堆布尔标志位的问题。实践建议：区域数量控制在 3 个以内，跨区域约束集中写在一处并列成表。
06

事件队列与可重入

run-to-completion 是不可谈判的

Run-to-completion（RTC）语义：状态机处理一个事件必须完整执行完（包括退出动作、迁移、进入动作）之后，才能开始处理下一个事件。这是所有状态机形式化模型的基础假设。违反它的直接后果是：迁移过程中状态变量处于中间态，此时若被重入，你会观察到一个"不存在于状态图上的状态"。
❌ 迁移动作里直接递归投喂事件
void Fsm::feed(Ev e) {
  ...
  st_ = next;
  action(ctx);            // action 内部：
}

void do_setup(Ctx& c) {
  c.fsm.feed(Ev::Ready);  // ⚠️ 递归重入
  // 回来时 st_ 已被内层改过，外层后续逻辑基于过期假设
  c.notify_upper();
}
// 症状：迁移日志里出现不可能的顺序；栈深不可控；
// 严重时无限递归爆栈
✅ 内部事件入队，由同一个循环串行消费
void Fsm::post(Ev e) { q_.push_back(e); }   // 只入队

void Fsm::run() {
  if (running_) return;         // 防重入闸门
  running_ = true;
  while (!q_.empty()) {
    Ev e = q_.front(); q_.pop_front();
    step(e);                    // 一次完整迁移
  }
  running_ = false;
}

void do_setup(Ctx& c) {
  c.fsm.post(Ev::Ready);        // 排到当前事件之后
  c.notify_upper();             // 本次迁移正常收尾
}
三条配套规则。
① 迁移里绝不做阻塞 IO。同步读文件、同步 DNS 查询、同步等锁都会把整个状态机（乃至整个事件循环上的所有会话）停住。要访问外部资源就发起异步请求 + 迁移到 Waiting 状态 + 挂一个超时定时器，回来时作为一个新事件。
② 队列必须有界。内部事件可以由外部事件产生，无界队列在过载时会吃光内存。满了要有明确策略（丢弃低优先级、拒绝新连接），这与 背压设计是同一件事。
③ 区分内部事件与外部事件的优先级。内部事件（迁移产生的后继动作）通常应优先于新的外部事件，否则会话会长期停在中间状态。实现上用两个队列，内部队列先清空。
07

并发与状态机

"单线程持有状态 + 消息传递" vs "共享加锁"

维度共享状态 + 加锁单线程持有 + 消息传递
竞态风险高：每个成员都可能被并发访问，靠人配平锁结构性消除：状态只被一个线程碰
RTC 语义要靠锁 + 防重入标志手工保证天然成立（消息串行消费）
定时器悬垂要 weak_ptr / 令牌定时器到期也是消息，投递到同一队列即可，悬垂问题消失
吞吐锁竞争随核数增加而恶化按会话分片可线性扩展
单会话时延可能更低（无入队开销）多一次入队 + 唤醒（几百纳秒到几微秒）
跨会话操作直接加两把锁（有锁序风险）更麻烦：要设计请求-应答消息，异步化
调试难：需要重现线程交织易：消息序列可录制回放
通信软件的主流答案是后者，理由不是性能而是可推理性。状态机的正确性论证依赖 RTC；共享加锁的实现里 RTC 靠人保证，而"人保证"在几十万行代码和多年迭代之后必然失效。把状态机做成 Actor（一个会话 = 一个邮箱 + 一个状态机 + 一个拥有它的线程），RTC 和"定时器回调悬垂"两个问题同时消失。代价是跨会话操作必须异步化，这需要在架构早期就想清楚。Actor / 线程池等通用并发模式见 并发模式指南；在通信软件里的具体落法（Active Object 改造）见 通信软件设计模式。
08

可测试与可观测

状态机是最容易做到"现场可诊断"的组件

迁移日志每次迁移打一行 (会话ID, 旧状态, 事件, 新状态, 耗时)。这是现场排障的第一手材料，且成本可控（信令面每秒几万行是可承受的，必要时按会话采样）。
状态快照提供一个"dump 所有会话当前状态的直方图"的运维接口。"3000 个会话卡在 Committing"这一个数字往往比几个小时的日志分析更快定位问题。
非法迁移断言开发/测试构建下断言并中止；生产构建下计数 + 采样日志。千万不要静默丢弃——非法事件计数的突增通常意味着对端版本不匹配或有攻击。
状态驻留时间每个状态的驻留时长直方图。中间状态（Committing、Waiting）的 P99 驻留时间是最灵敏的健康指标，比 CPU 使用率有用得多。
模糊测试状态机的输入是"事件序列"，天生适合 fuzz：随机生成畸形/乱序/重复的事件序列，断言"不崩溃、不泄漏、最终能回到 Idle"。这比对单个报文做 fuzz 更能找出状态相关的 bug。
从代码导出状态图转移表实现的额外红利：写十几行代码把 kTable 导出成 DOT/Mermaid，就得到一张永远和代码一致的状态图。手工维护的架构图三个月后一定是错的，自动生成的不会。
录制回放是状态机最强的调试武器。因为迁移是纯函数（第 3.2 节）、事件是串行消费的（第 6 节），你可以把现场的事件序列录下来，在开发机上完全确定性地重放，得到一模一样的迁移轨迹。这把"偶发的现场问题"变成"可重复的本地问题"——这一步做到了，剩下的调试就是常规工作。这也是为什么值得为 RTC 语义和消息传递付那点入队开销。
🎯 本篇要点回顾
  • 协议 = 状态 × 事件 × 迁移 × 定时器；两个以上互相约束的布尔标志位就该换成显式状态机
  • 四个真实例子的启示：TCP 的 TIME_WAIT（为不可靠留余量）、RRC 的 INACTIVE（加状态换成本）、NETCONF 的失败清理（资源绑定到状态）、O-RU 启动（必须能往回走）
  • 实现手法选型看"规范演进时改动的局部性"：≤5 状态用 switch，5–20 用转移表（通信软件默认），状态有大量独有行为用 State 模式，要编译期穷尽用 variant FSM
  • 转移表的隐藏收益是横切关注点只写一遍：非法计数、迁移日志、驻留统计
  • 定时器用时间轮不是因为更高级，而是"高频插入 + 高频取消 + 时限集中"的负载特征决定的
  • 定时器悬垂 this：weak_ptr 跨线程安全，取消令牌只在同线程/同 actor 下安全
  • HSM 用事件冒泡消除重复迁移，正交区域把乘法变加法，但跨区域约束必须显式集中管理
  • RTC 不可谈判：内部事件入队而非递归，迁移里不做阻塞 IO，队列必须有界
  • 单线程持有 + 消息传递的价值是可推理性，顺带消灭定时器悬垂；代价是跨会话操作要异步化
