二进制通信协议设计与解析

eCPRI、NETCONF 底层的报文、私有设备协议……本质都是"双方约定的字节格式 + 交互规则"。本篇手把手设计一个简单二进制协议，讲透 Header/Length/Magic/TLV、字节序、消息分帧与解析状态机——让你能读懂也能写出健壮的协议解析器。

Module 08 阅读 ~24 min TLV / 分帧
01

协议 = 格式 + 交互规则

回到本质

通信协议本质是两部分：① 数据格式（每个字节代表什么）+ ② 状态/交互规则（谁先发、怎么应答、超时怎么办）。前面所有协议——从 TCP 到 eCPRI 到 NETCONF——都逃不出这个框架。

本篇聚焦"格式"这一半，也简单带到交互规则。掌握它，你看任何协议的 RFC/规范都能抓住重点。

02

设计一个简单协议

从需求到报文布局

假设我们要在两个服务间传消息，设计一个定长头 + 变长体的协议：

Magic2B
0xCAFE
Version1B
Type1B
Seq4B
Length4B
(payload长度)
PayloadN B
CRC4B
  • Magic：魔数，快速识别/校验这是本协议的包（也便于错位后重新对齐）。
  • Version：协议版本，兼容演进。
  • Type：消息类型（请求/响应/心跳…）。
  • Seq：序列号，用于匹配请求-响应、检测丢失。
  • Length：Payload 字节数——分帧的关键。
  • CRC：完整性校验。
// C 结构体（注意对齐/pack）
#pragma pack(push, 1)
struct MsgHeader {
    uint16_t magic;    // 0xCAFE
    uint8_t  version;
    uint8_t  type;
    uint32_t seq;
    uint32_t length;   // payload 长度
};
#pragma pack(pop)
⚠️ #pragma pack(1) 很重要：不加，编译器会为对齐插入填充字节，导致收发双方结构体大小不一致。
03

字节序 Endianness

大端 / 小端

大端(Big-Endian)：高位字节在前。网络字节序就是大端。小端(Little-Endian)：低位在前，x86/ARM 常用。

多字节字段（uint16/32/64）跨机器传输必须约定字节序，否则 0x0001 在一端读成 0x0100。惯例用网络序（大端）。

uint32_t seq_host = 12345;
uint32_t seq_net  = htonl(seq_host);   // 发送前转网络序
memcpy(buf + 4, &seq_net, 4);
// 接收端
uint32_t seq = ntohl(*(uint32_t*)(buf + 4));
eCPRI/以太网头都用大端；很多私有协议直接沿用网络序省心。单字节字段无字节序问题。
04

消息分帧 Framing

TCP 字节流怎么切成消息

TCP 没有消息边界（Module 02 讲的"粘包/拆包"），三种经典分帧法：

方法做法适用
定长每条消息固定字节数字段固定的简单场景
分隔符用特殊字节结束（如 \n）文本协议(HTTP行/Redis)
长度前缀头里带 Length，先读头再读体二进制协议首选
 
// 长度前缀分帧：先收满头，再按 length 收满体
bool read_n(int fd, void* buf, size_t n) {   // 循环收满 n 字节
    size_t got = 0; char* p = (char*)buf;
    while (got < n) {
        ssize_t r = recv(fd, p + got, n - got, 0);
        if (r <= 0) return false;            // 断连/错误
        got += r;
    }
    return true;
}
struct MsgHeader h;
read_n(fd, &h, sizeof(h));                    // 1) 收满定长头
uint32_t len = ntohl(h.length);
if (ntohs(h.magic) != 0xCAFE || len > MAX) { /* 丢弃/断连 */ }
std::vector<char> body(len);
read_n(fd, body.data(), len);                 // 2) 按长度收满体
05

TLV：可扩展的秘诀

Type-Length-Value

TLV：把每个字段编码成 类型(Type) + 长度(Length) + 值(Value)。解析器遇到不认识的 Type 可以按 Length 跳过——天然向前兼容、可选字段友好。
Type1-2B
Length2B
ValueL B
Type...
Length...
Value...

很多协议（RADIUS、Diameter、部分 3GPP 信令）用 TLV 就是为了扩展性。缺点：比紧凑定长格式多占几个字节、解析稍复杂。

06

Parser 状态机

健壮解析器的核心

真实收包不会一次到齐——数据是流式、分片到达的。解析器应设计成状态机，把收到的字节喂进去，攒够一个阶段就推进：

// 累积缓冲 + 状态机（伪代码）
enum State { WAIT_HEADER, WAIT_BODY };
State st = WAIT_HEADER; Buffer acc;

void on_data(const char* data, size_t n) {
    acc.append(data, n);
    for (;;) {
        if (st == WAIT_HEADER) {
            if (acc.size() < sizeof(MsgHeader)) return;  // 头还没齐
            parse_header(acc);
            st = WAIT_BODY;
        }
        if (st == WAIT_BODY) {
            if (acc.size() < sizeof(MsgHeader) + body_len) return; // 体没齐
            dispatch(one_full_message);       // 交付完整消息
            acc.consume(sizeof(MsgHeader) + body_len);
            st = WAIT_HEADER;                 // 继续下一条(可能已粘在后面)
        }
    }
}
这个"累积缓冲 + 循环切分"模式适用所有长度前缀协议，也是网络框架里 codec 的标准写法。
07

设计权衡与陷阱

工程视角

  • Length 上限校验：不校验会被恶意超大 length 撑爆内存（安全 + 稳定）。
  • 版本字段：预留才能平滑升级；不预留后期难改。
  • 对齐 & pack：结构体收发必须 pack(1)，否则跨平台/编译器崩。
  • 紧凑 vs 可扩展：定长省带宽、快；TLV 灵活、可选字段友好——按场景选。
  • 心跳/超时：交互规则的一部分，检测半死连接。
🎯 本篇要点回顾
  • 协议 = 数据格式 + 交互规则
  • 典型头：Magic/Version/Type/Seq/Length/CRC
  • 多字节字段必须约定字节序（网络序=大端）
  • TCP 分帧首选长度前缀；TLV 换取可扩展性
  • 解析器用累积缓冲 + 状态机，务必校验 length 上限
