01

Socket 是什么

应用与内核网络栈的门

Socket：操作系统给应用提供的网络通信端点抽象。你对它 read/write，内核负责底下的 TCP/IP/Ethernet。一个 socket 由 (协议, 本地IP:端口, 远端IP:端口) 唯一标识——Module 01 讲的分层封装/解封装全部藏在内核里。

📮 生活类比：楼下的快递柜

send() 不是"把包裹送到对方手上"，而是"把包裹塞进楼下的快递柜"。柜子满了就塞不进去（阻塞模式下你站着等，非阻塞模式下转身就走并得到一个 EAGAIN）；塞进去之后快递员什么时候来收、路上会不会丢、对方什么时候取，都不在这次调用的返回值里。recv() 同理——柜子里有 3 件就给你 3 件，不会因为你说"我要 10 件"就等齐才给。短写、短读、EAGAIN、close() 之后数据还在飞，全都能从"两个柜子"推出来。

socket 就是一个文件描述符，但不只是文件描述符

socket() 返回的是普通 fd，遵守所有 fd 的规则——受 RLIMIT_NOFILE 限制、fork() 后被继承、引用计数归零才真正释放。三个常见现象由此而来：fd 泄漏时 accept() 开始返回 EMFILE；fork() 后父进程 close() 了连接、对端却收不到 FIN；exec() 前不用 SOCK_CLOEXEC，子程序会莫名持有一堆连接。

但它比普通文件多了一个协议控制块（TCP 状态机、序号、窗口、重传定时器都挂这里）和一对内核缓冲区。所以 read/write 能用在 socket 上，而 send/recv 不能用在普通文件上——后者多的那个 flags（MSG_NOSIGNAL、MSG_PEEK、MSG_WAITALL）只有网络端点才讲得通。

两个内核缓冲区：本篇最重要的一张图

面试里问"send() 返回成功意味着什么"，标准答案是"n 个字节已被拷贝进本机内核发送缓冲区，此外什么都不意味着"。加分补充：此刻数据可能一个比特都还没上线（Nagle 攒着、拥塞窗口不允许、网卡队列排着）；即使对端 ACK 了也只代表进了对端的接收缓冲区；所以"对端已处理"只能由应用层协议自己给——NETCONF 的 rpc-reply、HTTP 的响应码都要一来一回，正是这个原因。

02

TCP 服务端 / 客户端流程

经典调用序列

服务端

socket() → bind() → listen() → accept()（阻塞等连接）→ recv()/send() → close()

客户端

socket() → connect()（触发三次握手）→ send()/recv() → close()

逐个调用：它在内核里到底做了什么

调用序列人人会背，拉开差距的是"这一步之后内核的状态变成了什么"。下表把实际效果和最常见的误解并排放着。

调用内核里真正发生的事之后的 socket 状态常见误解
socket()分配协议控制块 + fd，还没有任何地址CLOSED以为它会占用端口——不会，此时四元组全空
bind()把本地 IP:port 写进控制块并登记到端口哈希表仍是 CLOSED以为客户端必须 bind——不必，connect() 自动挑临时端口
listen()转为被动打开，并创建两个队列LISTEN以为 backlog 是"最大并发连接数"——它只是等待被 accept 的队列长度
accept()从全连接队列头部摘一条已完成握手的连接，为它新建 fd新 fd 是 ESTABLISHED；监听 fd 不变以为握手发生在 accept 里——握手是内核自动完成的，accept 只是"取货"
connect()挑临时端口、发 SYN、驱动握手SYN_SENT → ESTABLISHED以为返回 0 代表"服务端已经 accept 了"——只代表握手完成、连接躺在对方队列里
send()/recv()只在用户缓冲区和内核缓冲区之间搬字节不变以为"发一次就收一次"——字节流没有这种对应关系（§1.2、§3.3）
close()fd 引用计数减一；归零时按情况发 FIN 或 RSTFIN_WAIT_1 → … → TIME_WAIT以为一定立刻断开——缓冲区里还有数据时内核会后台发完再发 FIN
最值得单独记住的是 connect() 那一行：返回成功只说明握手完成，服务端进程可能压根还没 accept()，甚至已经假死。内核照样替它完成握手、把连接堆进全连接队列，客户端一路成功，然后在第一个 recv() 上超时。所以只测端口通不通是无效的健康检查，必须做到应用层一问一答。

listen 的 backlog：两个队列，不是一个

backlog 是最容易被讲错的参数——它管的只是后一个队列，而且会被 somaxconn 静默截断：写 listen(fd, 4096) 而 somaxconn 是 128 时，实际上限就是 128，没有任何报错。

现象完全不同、根因是同一个，所以排查必须直接读队列计数，不要靠现象猜：

命令看什么判据
ss -lnt '( sport = :9000 )'LISTEN 行的 Recv-Q / Send-QRecv-Q = 堆积的连接数，Send-Q = 队列上限；两者相等即堆满
nstat -az TcpExtListenOverflows TcpExtListenDrops溢出次数累计值，两次采样做差才有意义；持续增长即全连接队列在溢出
ss -ant '( sport = :9000 )'ESTABLISHED 行的 Recv-Q这里是字节数（没被应用读走的），与上面不是一回事
同一栏两种含义，看错就会把"accept 慢"误判成"读得慢"。另外 ListenOverflows 在涨时加大 backlog 只是把问题往后推——真正的原因通常是 accept 循环被业务逻辑阻塞了。半连接队列溢出是另一回事（多为 SYN flood），由 tcp_syncookies 兜底。

accept 的三个坑

  • ECONNABORTED 必须容忍。连接在握手完成之后、被 accept 之前，客户端可能已经发了 RST（用户按了 Ctrl+C，或是端口扫描器）。正确处理是 continue 而不是退出循环——见过太多服务因为"accept 失败就 break"而被一次端口扫描扫死。
  • EMFILE 会让事件循环空转。fd 用尽时 accept() 返回 EMFILE，但那条连接仍躺在全连接队列里，epoll 立刻又报一次可读，CPU 打满。经典解法是启动时先 open("/dev/null") 占一个备用 fd：遇到 EMFILE 就关掉它，用腾出的名额 accept() 再立刻 close() 把连接从队列清掉，然后重新占回备用 fd。
  • 用 accept4() 而不是 accept()。新 fd 不会继承监听 fd 的 O_NONBLOCK（POSIX 明确规定，也是最常见的"我明明设了非阻塞"事故来源）；accept4(lfd, ..., SOCK_NONBLOCK | SOCK_CLOEXEC) 一次搞定，且没有竞态窗口。

地址别硬编码：getaddrinfo()

inet_pton(AF_INET, "127.0.0.1", ...) 只能用在教学示例里。生产代码要接受主机名、要同时支持 IPv4/IPv6，标准做法是 getaddrinfo()——它返回一个候选地址链表，依次尝试直到有一个成功（这也是 Happy Eyeballs 的基础）。完整写法见 §3.2 的客户端。

两个容易漏的细节：getaddrinfo() 的返回码不是 errno，要用 gai_strerror() 翻译（strerror(errno) 打出来的是上一次无关调用留下的错误，极其误导）；循环里失败的 fd 必须 close()，否则一个连不上的域名解析出 8 个地址就泄漏 8 个 fd。

TCP 代码骨架

最小可运行示例（Linux/C）

本章只留两份代码：服务端的关键几行和一份完整可编译的客户端。错误分支全部写出来是有意为之——真实事故几乎全部藏在平时被 // 省略错误处理 一笔带过的那几行里。

服务端：bind / listen / accept4 的关键几行

/* 建监听 socket。每个错误分支都对应一类真实事故，不是装饰。 */
static int make_listener(uint16_t port, int backlog)
{
    int lfd = socket(AF_INET, SOCK_STREAM | SOCK_CLOEXEC, 0);
    if (lfd < 0) { perror("socket"); return -1; }

    int on = 1;
    /* 少了这一句，重启服务时 bind 会因旧连接处于 TIME_WAIT 而失败（§3.8）。
       它影响正确性，所以失败要退出——TCP_NODELAY 那类只记日志。 */
    if (setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof(on)) < 0) {
        perror("setsockopt(SO_REUSEADDR)"); close(lfd); return -1;
    }

    struct sockaddr_in addr;
    memset(&addr, 0, sizeof(addr));
    addr.sin_family      = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);
    addr.sin_port        = htons(port);      /* 主机序 → 网络序（大端） */

    if (bind(lfd, (struct sockaddr *)&addr, sizeof(addr)) < 0) {
        fprintf(stderr, "bind :%u: %s\n", port, strerror(errno));
        close(lfd); return -1;
    }
    /* backlog 被 min(backlog, net.core.somaxconn) 静默截断（§2.2） */
    if (listen(lfd, backlog) < 0) { perror("listen"); close(lfd); return -1; }
    return lfd;
}

/* main 里的 accept 循环。三类 errno 都不该让服务退出（§2.3）；
   前提是 main 开头已经 signal(SIGPIPE, SIG_IGN)，见 §3.6。 */
for (;;) {
    struct sockaddr_in cli;
    socklen_t clilen = sizeof(cli);   /* 值-结果参数，每轮都要重置 */
    int cfd = accept4(lfd, (struct sockaddr *)&cli, &clilen, SOCK_CLOEXEC);
    if (cfd < 0) {
        if (errno == EINTR || errno == ECONNABORTED) continue;
        if (errno == EMFILE || errno == ENFILE) {
            sleep(1);                    /* 不退让就是 100% CPU 空转 */
            continue;
        }
        perror("accept4");
        break;                          /* 只有真没救了才退出循环 */
    }
    int one = 1;                        /* 只影响性能，失败仅记日志 */
    setsockopt(cfd, IPPROTO_TCP, TCP_NODELAY, &one, sizeof(one));
    serve_one(cfd);                     /* 阻塞式：一次一条，并发见第 6 章 */
    close(cfd);
}
serve_one() 就是"recv 到多少就 send_all 回去，直到 recv 返回 0"，三个返回分支见 §3.5 那张表。这里刻意一次只服务一条连接——先把单连接的错误处理讲透，第 6 章再换成 epoll 并发骨架。

完整可编译的客户端

完整文件，cc -Wall -Wextra -O2 -o tcp_echo_client tcp_echo_client.c 就能跑。四样必须有的东西全在里面：getaddrinfo 逐个候选地址试、短写循环、EINTR 原地重试、recv() 返回 0 判结束。

/* tcp_echo_client.c —— 完整可编译的阻塞式 TCP 客户端 */
#define _GNU_SOURCE        /* SOCK_CLOEXEC / MSG_NOSIGNAL 需要 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <signal.h>
#include <unistd.h>
#include <netdb.h>
#include <sys/socket.h>

/* 按主机名/服务名连接：IPv4 / IPv6 无关，依次试所有候选地址（§2.4）。 */
static int tcp_connect(const char *host, const char *serv)
{
    struct addrinfo hints, *res, *rp;
    memset(&hints, 0, sizeof(hints));
    hints.ai_family   = AF_UNSPEC;          /* v4 / v6 都要 */
    hints.ai_socktype = SOCK_STREAM;

    int rc = getaddrinfo(host, serv, &hints, &res);
    if (rc != 0) {                          /* 它不走 errno！ */
        fprintf(stderr, "getaddrinfo: %s\n", gai_strerror(rc));
        return -1;
    }

    int fd = -1;
    for (rp = res; rp != NULL; rp = rp->ai_next) {
        fd = socket(rp->ai_family, rp->ai_socktype | SOCK_CLOEXEC,
                    rp->ai_protocol);
        if (fd < 0) continue;                /* 本机没有这个协议族 */
        if (connect(fd, rp->ai_addr, rp->ai_addrlen) == 0) break;
        close(fd);                              /* 失败的 fd 必须关，否则泄漏 */
        fd = -1;
    }
    freeaddrinfo(res);                         /* 无论成败都要释放 */
    if (fd < 0)
        fprintf(stderr, "connect %s:%s: %s\n", host, serv, strerror(errno));
    return fd;
}

/* 循环写：send 可能短写，必须把 n 字节全部交出去才算成功。 */
static int send_all(int fd, const void *buf, size_t n)
{
    const char *p = buf;
    size_t left = n;
    while (left > 0) {
        ssize_t w = send(fd, p, left, MSG_NOSIGNAL);
        if (w > 0) { p += w; left -= (size_t)w; continue; }
        if (errno == EINTR) continue;          /* 信号打断，原地重试 */
        return -1;   /* EPIPE / ECONNRESET…；阻塞 fd 上不会有 EAGAIN */
    }
    return 0;
}

/* 循环读满 n 字节。三种结果调用方必须分开处理：
 *   0 = 读满；1 = 对端在读满前就 FIN 了（半条消息）；-1 = 出错。 */
static int recv_exact(int fd, void *buf, size_t n)
{
    char *p = buf;
    size_t left = n;
    while (left > 0) {
        ssize_t r = recv(fd, p, left, 0);
        if (r > 0) { p += r; left -= (size_t)r; continue; }
        if (r == 0) return 1;                  /* EOF：短了一截 */
        if (errno == EINTR) continue;
        return -1;
    }
    return 0;
}

int main(int argc, char **argv)
{
    const char *host = (argc > 1) ? argv[1] : "127.0.0.1";
    const char *serv = (argc > 2) ? argv[2] : "9000";
    const char *msg  = (argc > 3) ? argv[3] : "hello socket";

    signal(SIGPIPE, SIG_IGN);   /* 不做这一步，第二次 send 会杀掉进程 */

    int fd = tcp_connect(host, serv);
    if (fd < 0) return 1;

    size_t len = strlen(msg);
    if (send_all(fd, msg, len) < 0) {
        fprintf(stderr, "send: %s\n", strerror(errno));
        close(fd); return 1;
    }

    char *echo = malloc(len + 1);
    if (!echo) { close(fd); return 1; }

    /* echo 服务会原样回同样多的字节，所以这里能用 recv_exact；
       真实协议要先读定长头拿到长度，再读变长体，见 §3.4 */
    int rc = recv_exact(fd, echo, len);
    if (rc < 0)      fprintf(stderr, "recv: %s\n", strerror(errno));
    else if (rc == 1) fprintf(stderr, "server closed early\n");
    else { echo[len] = '\0'; printf("echo: %s\n", echo); }

    free(echo);
    /* 先半关闭发方向，让服务端的 recv 干净地拿到 0，再关整个 fd（§3.7） */
    shutdown(fd, SHUT_WR);
    close(fd);
    return rc == 0 ? 0 : 1;
}

最容易错的一件事：TCP 是字节流，不是消息

短读（short read）：recv(fd, buf, 1000, 0) 返回 300——接收缓冲区当时只有 300 字节，内核不会替你等齐。
短写（short write）：send(fd, buf, 1000, 0) 返回 300——发送缓冲区只剩 300 字节空位。

TCP 提供的是"一条有序、无重复、无丢失的字节流"，它不保证一次 send 对应对方一次 recv。切分位置由 Nagle 合并、MSS 分段、窗口限制、网卡 GRO/TSO 共同决定；而且同一段代码在回环上跑一万次都不出错，一上真实网络就露馅——这是短读类 bug 最恶劣的性质。

所以"粘包"是个很坏的叫法：它暗示这是异常，而这恰恰是 TCP 唯一的正常行为。正确的心智模型是——TCP 从来就没有"包"，是你的协议给它划了包。

反方向的短写同理，只是原因换成了"缓冲区没有那么多空位"：

长度前缀分帧：把 recv_exact 用对

最常用的分帧方式是定长头 + 变长体。下面这段有两个要点：长度字段走网络字节序；拿到长度后必须先做上限校验再分配内存——不校验就等于给了对端一个"发一个 0xFFFFFFFF 让你 OOM"的开关，这是真实存在的攻击面。

/* 线上格式：[4 字节大端长度 N][N 字节负载]，N ≤ MAX_MSG
 * 返回 0 成功（*out 由调用方 free）；1 = 对端正常关闭；-1 = 出错/协议错  */
#define MAX_MSG (1u << 20)   /* 1 MiB 上限，必须有 */

static int recv_message(int fd, char **out, uint32_t *out_len)
{
    uint32_t be_len;
    int rc = recv_exact(fd, &be_len, sizeof(be_len));
    if (rc != 0) return rc;                 /* 头都没读全：EOF 或出错 */

    uint32_t len = ntohl(be_len);
    if (len > MAX_MSG) {                     /* 先校验，再分配！ */
        fprintf(stderr, "frame too large: %u\n", len);
        errno = EPROTO;
        return -1;                           /* 协议已错乱，只能断连 */
    }

    char *body = malloc(len ? len : 1);
    if (!body) return -1;

    rc = recv_exact(fd, body, len);
    if (rc != 0) {                          /* 头读到了、体没读全 = 半条消息 */
        free(body);
        if (rc == 1) {                     /* EOF 落在半条消息中间 */
            fprintf(stderr, "truncated frame\n");
            errno = EPROTO;
        }
        return -1;                          /* 两种都当协议错，断连 */
    }
    *out = body; *out_len = len;
    return 0;
}

/* 短写之后把 iovec 数组整体前移 n 字节：整项写完的直接丢弃，
 * 停在中间的那一项削掉已写出的部分。注意 iov_base 是 void *，
 * 必须先转成 char * 再做指针算术——对 void * 加减是 GCC 扩展，
 * -pedantic 下会报警告。*/
static void advance_iov(struct msghdr *mh, size_t n)
{
    while (n > 0 && mh->msg_iovlen > 0) {
        struct iovec *v = mh->msg_iov;
        if (n < v->iov_len) {                /* 这一项只写出去一部分 */
            v->iov_base = (char *)v->iov_base + n;
            v->iov_len -= n;
            return;
        }
        n -= v->iov_len;                     /* 整项写完，丢弃后看下一项 */
        mh->msg_iov++;
        mh->msg_iovlen--;
    }
}

static int send_message(int fd, const void *body, uint32_t len)
{
    uint32_t be_len = htonl(len);
    struct iovec iov[2] = {
        { .iov_base = &be_len,          .iov_len = sizeof(be_len) },
        { .iov_base = (void *)body,   .iov_len = len            },
    };
    struct msghdr mh;
    memset(&mh, 0, sizeof(mh));
    mh.msg_iov = iov; mh.msg_iovlen = 2;

    size_t total = sizeof(be_len) + len, done = 0;
    while (done < total) {
        ssize_t w = sendmsg(fd, &mh, MSG_NOSIGNAL);
        if (w < 0) {
            if (errno == EINTR) continue;
            return -1;
        }
        done += (size_t)w;
        if (done < total)                    /* 短写：把 iovec 往前推 w 字节 */
            advance_iov(&mh, (size_t)w);      /* 见上 */
    }
    return 0;
}
sendmsg / writev 的短写比 send 更容易写错：重试时不能原样再调一次，必须把 iovec 数组按已写字节数往前推。上面的 advance_iov() 平淡无奇，却是 iovec 类代码出 bug 频率最高的一个函数。不想自己维护就退回"把头和体拼进同一个缓冲区再 send_all"：多一次内存拷贝，换一份不会错的代码。真要抠这次拷贝见 高性能网络编程；协议格式怎么设计见 二进制协议设计与解析。

recv 的返回值：三个分支必须分开处理

返回值含义正确动作写错的后果
> 0读到 n 字节，n 可能远小于请求处理这 n 字节，继续循环当成"读满了"→ 解析错乱
== 0对端已关闭发送方向（收到 FIN）。TCP 上这是唯一含义不会再有数据；发完剩余出站数据后关闭当成错误 → 正常断连被记成故障；当成"再试一次"→ 死循环空转
< 0 + EINTR被信号打断，一个字节都没传原地重试当成错误 → 偶发失败，只在有定时器/信号时复现
< 0 + EAGAIN/EWOULDBLOCK非阻塞下"现在没数据"，不是错误回事件循环等下次可读当成错误 → 连接被无故关闭
< 0 + ECONNRESET对端发了 RST（进程崩了 / 收到发往已关闭连接的数据）立即清理，不要重试重试 → 又一次 RST，日志刷屏
< 0 + 其它真错误记日志并关闭—
把 n == 0 和 n < 0 合并成 if (n <= 0) { 出错 } 是能跑的，合并成 if (n <= 0) { continue; } 会烧掉一个 CPU 核。对端断开后 recv 稳定返回 0，循环永不退出，监控上表现为"某个线程 CPU 恒定 100%，但没有任何流量"。判读特征是 strace 里刷屏的 recvfrom(9, "", 4096, 0, NULL, NULL) = 0——同一个 fd、同一个返回值、每秒几十万次。

EINTR 还有一条容易踩的：很多人以为设了 SA_RESTART 就不用管它，这在 socket 上不成立。signal(7) 明确写着，socket 一旦设了 SO_RCVTIMEO / SO_SNDTIMEO，被信号打断时即使有 SA_RESTART 也会返回 EINTR——而设收发超时恰恰很常见。所以所有阻塞式 socket 调用都要显式处理 EINTR。

SIGPIPE：默认会直接杀死你的进程

向一个对端已完全关闭的连接写数据，内核会发 SIGPIPE，默认动作是终止进程——不是返回错误，是进程没了。时序值得记住：对端 close() 后第一次 send 通常成功（FIN 只表示对方不再发），对方 TCP 回一个 RST，第二次 send 才触发 EPIPE + SIGPIPE——这就是这类事故总是"偶发、重现不了"的原因。三种处理方式选一种，别都不做：

方式粒度可移植性适用
sigaction(SIGPIPE, {SIG_IGN}, NULL)整个进程POSIX，处处可用应用程序的默认选择；比 signal() 少一层实现差异
send(fd, p, n, MSG_NOSIGNAL)单次调用Linux 有；macOS 没有库代码：不该替宿主进程做全局决定
setsockopt(SO_NOSIGPIPE)单个 socketmacOS/BSD 有；Linux 没有跨平台库里与上一条用 #ifdef 互补
三者共同的效果只是"把信号换成返回值"：之后 send 返回 −1 且 errno == EPIPE，你仍然必须检查它，否则只是把"进程猝死"换成了"数据悄悄丢了"。这就是 send_all() 里那句 return -1 不能省的原因。

TIME_WAIT 与 SO_REUSEADDR：为什么重启服务会 bind 失败

现象人人见过：Ctrl+C 掉服务立刻重启，得到 bind: Address already in use，等一两分钟又好了。原因不是"端口没释放干净"这种玄学，而是四次挥手把 TIME_WAIT 精确地留在了某一侧——留在谁身上，决定了这个错误会不会出现：

TIME_WAIT 的两个理由都很实在：① 最后那个 ACK 丢了时，对端重传的 FIN 还能被应答；② 让本次连接的迷路报文彻底消亡，不被后来复用同一四元组的新连接错收。SO_REUSEADDR 正是对"不许 bind 被 TIME_WAIT 占着的地址"这一条的豁免，而且不牺牲安全性。

两个常被误用的旋钮：tcp_tw_reuse 只作用于主动发起连接的一侧（复用 TIME_WAIT 的本地临时端口连出去），对服务端监听端口毫无帮助；tcp_tw_recycle 已在 Linux 4.12 删除，它在 NAT 后面会让大量连接被莫名丢弃，网上流传的"设它解决 TIME_WAIT 过多"是过时且有害的建议。
短读导致的协议解析错乱：只在跨机房出现的"报文校验失败"。一个设备管理通道用自定义二进制协议（4 字节长度 + 负载），同机房联调三个月零故障，切到跨机房后每天几十次"magic 校验失败，断开重连"，而抓包看到线上字节完全正确。根因是接收端写成了 n = recv(fd, buf, 4, 0); if (n != 4) 报错;——RTT 0.1 ms 时一个报文就到齐，recv 永远返回 4；跨机房且中间做过 MSS 收缩后，长度字段偶尔被切在两个 TCP 段里，recv 返回 2，代码判错断连，重连后剩下那 2 字节被当成下一条消息的开头，错乱一路传染。判读要点：抓包正确 + 应用报错，几乎一定是接收侧分帧写错了。修法是换成 recv_exact()，并把 tc qdisc ... netem delay 30ms loss 0.5% 加进回归测试。

UDP 代码骨架

无连接，收发即用

UDP 的编程模型比 TCP 简单得多——但简单的是 API，不是工程。TCP 帮你做的那些事（重传、排序、去重、流控）一件都不会消失，只是从内核搬到了你的代码里。

收发骨架：两个必踩的坑都在这几行里

/* 建立过程与 TCP 只差两步：没有 listen，也没有 accept。
   socket(AF_INET, SOCK_DGRAM | SOCK_CLOEXEC, 0) + bind() 之后直接收发。 */
for (;;) {
        char buf[2048];
        struct sockaddr_in cli;
        socklen_t clilen = sizeof(cli);   /* ① 值-结果参数，每轮都要重置！ */

        /* ② MSG_TRUNC 让返回值给出「数据报的真实长度」，即使它比 buf 还大。
              不加的话超长数据报被静默截断，你根本不知道。 */
        ssize_t n = recvfrom(fd, buf, sizeof(buf), MSG_TRUNC,
                             (struct sockaddr *)&cli, &clilen);
        if (n < 0) {
            if (errno == EINTR) continue;
            /* connect 过的 UDP socket 才会在这里看到 ECONNREFUSED（§4.2） */
            fprintf(stderr, "recvfrom: %s\n", strerror(errno));
            continue;              /* UDP 的错误几乎都不该终止服务 */
        }
        /* n == 0 表示「收到一个长度为 0 的数据报」，
           绝不是「对端关闭」——UDP 根本没有连接可关。 */
        if ((size_t)n > sizeof(buf)) {
            fprintf(stderr, "datagram truncated: %zd, dropped\n", n);
            continue;              /* 半个数据报没有任何价值 */
        }

        /* sendto 失败（ENOBUFS / EMSGSIZE / 被防火墙 EPERM）
           只该丢弃这一个包，不该影响后续。 */
        if (sendto(fd, buf, (size_t)n, 0,
                   (struct sockaddr *)&cli, clilen) < 0)
            fprintf(stderr, "sendto: %s\n", strerror(errno));
}
① clilen 必须在每次 recvfrom 前重新赋值。它是值-结果参数，调用后会被改成实际地址长度；放在循环外只初始化一次，第二轮开始传进去的就是个偏小的值，IPv6 场景下直接导致地址被截断。② 不加 MSG_TRUNC 时超长数据报被静默截断——recvfrom 返回 sizeof(buf)，多出来的部分丢弃且没有任何提示，你会得到一条"看起来完整但内容不对"的消息。

UDP 上的 connect()：无连接，但值得连

"UDP 是无连接的所以不能 connect"是个流传很广的误解。connect() 在 UDP socket 上完全合法，它不产生任何网络报文，只是在内核里登记一个默认对端——之后 send/recv 就能用，不必每次填地址。三条收益里第二条几乎是必须的：

收益机制注意
能用 send/recv/write/read默认对端已登记；顺带缓存路由查找结果，省掉每次 sendto 的临时查找省下的量级取决于内核版本与路由表规模，要测了才知道
能收到 ICMP 错误对端端口无人监听会回 ICMP port unreachable，但未 connect 的 socket 默认收不到（内核无法确定投给谁）；connect 后下一次 send/recv 返回 ECONNREFUSED"UDP 发到没人听的端口毫无反应"就是这么来的
内核替你过滤来源只投递来自那个对端的数据报不要当安全机制——源地址可以伪造
这是个很好的分层面试题。答"能"只是及格，答出"不产生报文、只绑定默认对端"算合格，说出"最大的收益是开始接收 ICMP 错误"就明显在生产里踩过。再补一句"不 connect 也想拿到 ICMP 错误，就开 IP_RECVERR，用 recvmsg(..., MSG_ERRQUEUE) 从错误队列里读"就很扎实。反向操作也要知道：connect 到 AF_UNSPEC 可解除绑定。

UDP 与 TCP 在 API 语义上的六处不同

阻塞 / 非阻塞与 I/O 多路复用

从一个连接到十万连接

从一线程一连接走到一个线程管几万条连接，只需要两样东西：非阻塞 fd，和一个问"现在哪些 fd 就绪"的机制。二者相加就是 Reactor——nginx、Redis 以及绝大多数高性能网络框架的骨架。

O_NONBLOCK 到底改变了什么

非阻塞不是"变快"，而是"不等待"：本来会让线程睡下去的调用，改为立刻返回 −1 并把 errno 设为 EAGAIN（在 Linux 上 EWOULDBLOCK 与它是同一个值，但为可移植性习惯上两个都判）。EAGAIN 是"现在没得干"，不是错误。
调用阻塞模式非阻塞模式
accept()没有连接就一直等队列为空 → −1/EAGAIN
connect()等到握手完成或失败立刻 −1/EINPROGRESS，握手在后台继续
recv()缓冲区空就等，有 1 字节就返回缓冲区空 → −1/EAGAIN
send()缓冲区满就等，通常写完全部写多少算多少；一个字节都写不下才 −1/EAGAIN
close()立即返回（除非设了 SO_LINGER）同左；SO_LINGER + 非阻塞的组合依平台而异，不要依赖
① 阻塞模式下也会短读短写：阻塞 recv 的语义是"至少读到 1 字节就返回"；阻塞 send 通常写完，但传了一部分后被信号打断也会短写。所以 send_all/recv_exact 在阻塞模式下同样必须写。② 非阻塞不会让单个调用更快，它只是把"等"的决定权交还给你——单连接场景用它只会白白多写几百行状态机。

四步流程里最后一步是绝大多数人漏掉的——而漏掉它的代码在本机测试永远正确（回环一定连得上），上线遇到对端没起来就会"成功连上"，然后在第一次 send 时莫名其妙 EPIPE，排查方向被彻底带偏：

有了结果，不说明结果是成功 ① 设 O_NONBLOCK 建 socket 时带 SOCK_NONBLOCK 更好 ② connect() −1 / EINPROGRESS 这是正常的，不是错误 ③ 等可写事件 poll POLLOUT / epoll EPOLLOUT 握手成功 → fd 可写 SO_ERROR == 0 被 RST 拒绝 / 超时 → 也可写 ECONNREFUSED / ETIMEDOUT ④ getsockopt(fd, SOL_SOCKET, SO_ERROR, &err, &len)：err == 0 才算连上 读取的同时会清除这个挂起错误，所以只能读一次；漏掉这一步 = 把失败当成功 
/* 带超时的非阻塞 connect。成功返回 0；失败返回 -1（errno 已置为真正的原因）。
 * fd 必须是已创建但未连接的 socket；sa/salen 来自 getaddrinfo。          */
static int set_nonblock(int fd)
{
    int fl = fcntl(fd, F_GETFL, 0);
    if (fl < 0) return -1;
    /* 必须「先取回再或上」，直接 F_SETFL O_NONBLOCK 会清掉其它标志 */
    return fcntl(fd, F_SETFL, fl | O_NONBLOCK);
}

static int connect_timeout(int fd, const struct sockaddr *sa,
                           socklen_t salen, int timeout_ms)
{
    if (set_nonblock(fd) < 0) return -1;

    if (connect(fd, sa, salen) == 0)
        return 0;                       /* 回环地址常常一次就成功 */
    if (errno != EINPROGRESS)
        return -1;                      /* 这才是真失败 */

    /* ③ 等可写。注意：失败时 fd 也会变可写，所以这里还不能下结论 */
    struct pollfd pfd;
    pfd.fd = fd; pfd.events = POLLOUT; pfd.revents = 0;
    for (;;) {
        int n = poll(&pfd, 1, timeout_ms);
        if (n > 0) break;
        if (n == 0) { errno = ETIMEDOUT; return -1; }
        if (errno == EINTR) continue;   /* 严谨实现应扣减已耗时间 */
        return -1;
    }

    /* ④ 唯一可信的判据：取出并清除挂起错误 */
    int err = 0;
    socklen_t len = sizeof(err);
    if (getsockopt(fd, SOL_SOCKET, SO_ERROR, &err, &len) < 0)
        return -1;
    if (err != 0) {          /* ECONNREFUSED / ETIMEDOUT / EHOSTUNREACH … */
        errno = err;         /* getsockopt 本身成功了，错误在 err 里 */
        return -1;
    }
    return 0;
}
除了上图那条主线，再补两点就很完整：① connect 只能对同一个 fd 调用一次，失败后必须 close 掉重新 socket()；② 用应用层超时，不要等内核默认超时——SYN 重传耗尽默认要一分钟以上（tcp_syn_retries），业务等不起，要么像上面用 poll 计时，要么设 TCP_SYNCNT。

关键差别只有一句：select/poll 每次调用都要把"我关心哪些 fd"重新告诉内核一遍，内核也要重新扫一遍；epoll 把这份关注列表常驻内核，只在增删时通信，就绪时由回调直接挂进就绪链表。于是成本从"随总连接数增长"变成"随活跃连接数增长"——在"1 万条连接、50 条活跃"这种典型场景下是数量级差别，而不是"epoll 更快"这么一句。

FD_SETSIZE 常被误解成"最多 1024 个连接"。准确说法是：fd 的数值不能 ≥ FD_SETSIZE。一个只监听 3 个 fd 的进程，若那 3 个 fd 的编号恰好在 2000 附近，FD_SET 就会越界写坏栈上的内存——不报错，只是随机崩溃。这是"新代码一律别用 select"最硬的理由。epoll 的内核数据结构与唤醒路径见 Linux I/O 与内核。

LT 与 ET：区别在"什么时候通知"

LT（Level Triggered，水平触发，默认）：只要 fd 处于就绪状态，每次 epoll_wait 都会报告它。
ET（Edge Triggered，边沿触发，加 EPOLLET）：只在状态发生变化的那一刻报告一次——比如"缓冲区从空变成有数据"。

生活类比：门铃与信箱。LT 是只要信箱里有信就一直响的铃——取一封剩两封它还响，直到取空为止。ET 是邮差按门铃：送信时按一下，之后不管你取没取都不会再按。所以 ET 下听到铃声就必须把信箱一次性掏空；剩一封在里面，邮差不会为它再来一次，那封信就永远躺在那儿了。

LT（默认）ET（EPOLLET）
必须用非阻塞 fd 吗不强制（但推荐）必须：否则循环读的最后一次会永久阻塞
一次事件读多少 / accept 几条随意，读不完下次还通知都必须循环到 EAGAIN
EPOLLOUT 怎么管写不完才注册，写完立刻取消，否则空转可常驻注册：不满就不再触发
写错的后果CPU 空转（监控能发现）连接静默挂死（很难发现，只在高负载下出现）
建议默认选它，逻辑简单、出错代价小确有性能证据、团队对状态机很熟时再上

ET 下必须读到 EAGAIN，是因为它的通知条件是"内核收到新数据"这个事件，而不是"缓冲区里有数据"这个状态。所以读到 EAGAIN 的本质是重新武装（re-arm）那个边沿；accept 同理——两条连接在同一瞬间进入全连接队列只算一次边沿。

最小事件循环：非阻塞 + 读到 EAGAIN

这份骨架能长成生产代码：非阻塞、有出站缓冲、按需开关 EPOLLOUT、循环读到 EAGAIN（LT 和 ET 都正确）。make_listener 同 §3.1，set_nonblock 同 §6.2。

/* 省略：MAX_EVENTS / MAX_FD / OUT_LIMIT（单连接出站缓冲上限 4 MiB）三个宏，
   以及 conn_add() 建连接对象、conn_queue() 追加、conn_flush() 尽量写出、
   conn_close() 摘除并释放这四个直白的辅助函数。
   出站缓冲必须有上限——否则慢客户端会把它撑爆。 */
struct conn { int fd; char *out; size_t len, cap; };
static struct conn *g_conns[MAX_FD];   /* 用 fd 直接索引，最简单也最快 */

static int ep_mod(int ep, int fd, int want_out)
{
    struct epoll_event ev;
    memset(&ev, 0, sizeof(ev));
    ev.data.fd = fd;
    /* EPOLLOUT 只在「确实还有数据没写完」时注册；
       LT 下常驻注册会每轮都触发，CPU 直接跑满。 */
    ev.events  = EPOLLIN | (want_out ? EPOLLOUT : 0);
    return epoll_ctl(ep, EPOLL_CTL_MOD, fd, &ev);
}

int main(void)
{
    signal(SIGPIPE, SIG_IGN);

    int lfd = make_listener(9000, 1024);
    if (lfd < 0 || set_nonblock(lfd) < 0) return 1;

    int ep = epoll_create1(EPOLL_CLOEXEC);
    if (ep < 0) { perror("epoll_create1"); return 1; }

    struct epoll_event ev, evs[MAX_EVENTS];
    memset(&ev, 0, sizeof(ev));
    ev.events = EPOLLIN; ev.data.fd = lfd;   /* 加 | EPOLLET 即为 ET 模式 */
    if (epoll_ctl(ep, EPOLL_CTL_ADD, lfd, &ev) < 0) { perror("epoll_ctl"); return 1; }

    for (;;) {
        int n = epoll_wait(ep, evs, MAX_EVENTS, -1);
        if (n < 0) {
            if (errno == EINTR) continue;   /* 漏了这句 = 收个信号服务就退 */
            perror("epoll_wait"); break;
        }
        for (int i = 0; i < n; i++) {
            int fd = evs[i].data.fd;
            uint32_t e = evs[i].events;

            if (fd == lfd) {
                /* 循环 accept 到 EAGAIN：ET 下是必须的（同一瞬间到达的多条
                   连接只算一次边沿），LT 下也能少几次 epoll_wait。 */
                for (;;) {
                    int cfd = accept4(lfd, NULL, NULL,
                                       SOCK_NONBLOCK | SOCK_CLOEXEC);
                    if (cfd < 0) {
                        if (errno == EAGAIN || errno == EWOULDBLOCK) break;
                        if (errno == EINTR || errno == ECONNABORTED) continue;
                        perror("accept4"); break;   /* EMFILE 见 §2.3 */
                    }
                    if (conn_add(ep, cfd) < 0) close(cfd);
                }
                continue;
            }

            struct conn *c = g_conns[fd];
            if (!c) continue;

            /* EPOLLERR / EPOLLHUP 不注册也会上报，不处理就会在一个已经
               出错的 fd 上无限收到事件。 */
            if (e & (EPOLLHUP | EPOLLERR)) { conn_close(ep, fd); continue; }

            if (e & EPOLLIN) {
                char buf[16384];
                for (;;) {                       /* 一路读到 EAGAIN */
                    ssize_t r = recv(fd, buf, sizeof(buf), 0);
                    if (r > 0) {
                        if (conn_queue(c, buf, (size_t)r) < 0) {
                            conn_close(ep, fd); goto next;
                        }
                        continue;
                    }
                    if (r == 0) {                /* 对端 FIN */
                        conn_close(ep, fd); goto next;
                    }
                    if (errno == EINTR) continue;
                    if (errno == EAGAIN || errno == EWOULDBLOCK) break;
                    conn_close(ep, fd); goto next;   /* ECONNRESET… */
                }
            }
            if (conn_flush(ep, c) < 0) { conn_close(ep, fd); continue; }
        next: ;
        }
    }
    close(ep); close(lfd);
    return 0;
}
四个"少写一行就出事"的地方：① epoll_wait 的 EINTR 要 continue，否则挂个 SIGWINCH 都能把服务弄退出；② EPOLLOUT 必须按需开关，LT 下常驻注册会每轮触发，CPU 直接 100%；③ 出站缓冲必须有上限，否则一个只连不收的慢客户端就能吃光内存（经典的 slowloris 类资源耗尽）；④ EPOLLERR/EPOLLHUP 不注册也会上报。
多线程用 epoll 有三种形态：① 一个 epoll、多个线程 epoll_wait——必须配 EPOLLONESHOT（事件报给一个线程后自动失效，处理完手工 re-arm），否则同一个 fd 会被两个线程同时处理，而且这种架构有惊群；② 每线程一个 epoll，监听 fd 用 SO_REUSEPORT 各自 bind（§7.2）；③ 单线程 accept + 分发。取舍与协程/Proactor 见 异步网络编程。

缓冲区大小：多数情况下最好的做法是别动它

Linux 的 TCP 接收缓冲区默认自动调优（tcp_rmem 给 min/default/max，tcp_moderate_rcvbuf 打开自适应）。而你一旦显式调了 setsockopt(SO_RCVBUF)，这个 socket 的自动调优就被关掉——你设的值从此就是天花板。很多"照抄调优文章"的代码设成 256 KB，结果在长肥管道上反而限制了吞吐，因为自动调优本来能涨到几 MB。三个细节：

  • Linux 会把你设的值翻倍（一半留给 sk_buff 记账），getsockopt 读回来是两倍，不是 bug。
  • 上限受 rmem_max/wmem_max 约束，超出部分被静默截断——setsockopt 返回 0 但值没生效，设完一定要读回来确认。
  • 要在 connect()/listen() 之前设：窗口缩放因子在握手的 SYN 里就协商完了。监听 socket 上的值会被 accept 出的连接继承。
什么时候真的该手工设？两种：① 明确知道带宽时延积、又要求确定性行为（固定拓扑的传输设备）；② 反过来，为了限制单连接占用的内存——几万条连接时缓冲区是内存大头，把 SO_RCVBUF 压小是有效的容量控制。除此之外交给内核。

第四行值得展开：SO_RCVTIMEO 超时时若已收到一部分数据，recv 返回的是已读字节数而不是 −1。于是 recv_exact 会悄悄退化成"读了一半就返回"——把"返回值 > 0"当成成功，就会拿半条消息去解析。

还有几件小事，但都真的出过事故

  • close() 的返回值要检查，但绝对不能重试。Linux 上它即使返回 EINTR，fd 也已经被释放了；再关一次，关掉的可能是另一个线程刚 accept 到的同号 fd——症状是"随机某条连接被莫名关掉"，几乎无法定位。
  • 临时端口会耗尽。每建一条连接占一个临时端口（ip_local_port_range 默认约 28k），加上 60 秒 TIME_WAIT，短连接压测很容易撞到 connect: Cannot assign requested address。这时候该改连接模型，不是继续调内核参数。
  • fd 泄漏比内存泄漏更致命——后者几天才出事，前者在 ulimit -n 1024 下几分钟就让服务不可用。ls /proc/<pid>/fd | wc -l 定时采样只涨不跌就是泄漏，再用 ss -anp 按 socket:[inode] 反查是哪条连接。
  • setsockopt 都要判返回值，但不都要致命：影响正确性的（SO_REUSEADDR）失败就退出，只影响性能的只记日志——目标系统上不存在的选项返回 ENOPROTOOPT，为它退出进程毫无道理。
  • 用 strace 看真相。strace -f -e trace=network -T -p <pid> 打出每个调用的参数、返回值与耗时；-T 能立刻区分"卡在 recv"和"卡在业务逻辑"（两次系统调用之间的空档）。
忘记处理 SIGPIPE，导致管理进程"无日志退出"。基站上的管理代理每隔几天消失一次，日志最后一行永远是正常业务输出，没有异常栈也没有 coredump。突破口是 systemd 的退出记录 code=killed, status=13/PIPE——13 号信号就是 SIGPIPE。根因是代理会主动向网管推送告警，而那条连接空闲后被中间的防火墙静默回收；下次推送时第一次 send 成功并收到 RST，第二次 send 触发 SIGPIPE，连打日志的机会都没有。修法是 §3.6 那三件事一起做，再加 TCP_USER_TIMEOUT 与应用层心跳。判读要点：进程无日志消失时先看退出信号号——退出码 141（128+13）与 status=13/PIPE 是同一个指纹。
🎯 本篇要点回顾
  • send/recv 的边界只到内核缓冲区——成功不代表发出去了，更不代表对端读到了
  • TCP 是字节流不是消息：短读短写是常态，必须 send_all/recv_exact + 应用层分帧
  • recv 三个分支分开处理：>0、==0（对端关闭）、<0 再分 EAGAIN/EINTR/真错误
  • SIGPIPE 默认杀进程，三种处理方式选一种必须做
  • 非阻塞 connect 的第四步 getsockopt(SO_ERROR) 不能漏；epoll 默认用 LT
  • 监听 socket 标配 SO_REUSEADDR；缓冲区交给内核；保活要 keepalive 三参数 + TCP_USER_TIMEOUT 一起上
用现代 C++ 写这些会好很多：收发缓冲用 std::span 而不是裸 char* + len、超时用 chrono::steady_clock（有 PTP 的设备上 system_clock 会被授时跳变打乱）、返回码加 [[nodiscard]] 防漏检——落点与事故案例见 现代 C++（14/17）在通信协议栈中的实战；Reactor 还是 Proactor 见 通信软件设计模式 §02。

  1. 基础TCP 是字节流还是消息流？所谓的"粘包"该怎么解决？

    TCP 是字节流。它保证的是"一条有序、无重复、无丢失的字节序列"，唯独不保证你的一次 send 对应对方的一次 recv。发送方三次 send 各 10 字节，接收方可能一次读到 30 字节，也可能读到 7 / 13 / 10 三次，切分位置由 Nagle 合并、MSS 分段、拥塞窗口、网卡 GRO/TSO 共同决定，与消息边界毫无关系。

    所以"粘包"这个词本身就误导人：它暗示这是一种异常，而这恰恰是 TCP 唯一的、正常的行为。把它当 bug 去修，就会写出"加个 sleep 让包分开"这类在压测下必然崩的代码。正确的心智模型是"TCP 从来没有包，是你的协议给它划了包"。

    解决办法只有三种，且必须选一种：

    • 定长消息：最简单，但只适合字段固定的场景。
    • 长度前缀（最常用）：定长头里放负载长度，先读头再按长度读体。
    • 分隔符（如 \r\n）：文本协议常用，代价是负载里出现分隔符时要转义。

    加分：指出这类 bug 在本机和同机房几乎测不出来——RTT 很低时一条消息通常一个报文就到齐，recv 永远"恰好"读满。一上跨机房或中间 MSS 收缩就开始偶发。因此"加延迟 + 加丢包"必须进回归测试（tc qdisc ... netem delay 30ms loss 0.5%）。反过来 UDP 天然有消息边界，一次 recvfrom 就是一个完整数据报，不需要分帧。

  2. 基础什么是短读和短写？正确的循环写法长什么样？

    短读：recv(fd, buf, 1000, 0) 返回 300，因为接收缓冲区当时只有 300 字节，内核不会替你等齐。短写：send(fd, buf, 1000, 0) 返回 300，因为发送缓冲区只剩 300 字节空位。

    关键是阻塞模式下同样会发生——这一点很多人答错。阻塞 recv 的语义是"至少读到 1 字节就返回"，不是"读满才返回"；阻塞 send 通常会写完，但在传输了一部分之后被信号打断时也会返回短写。所以 send_all / recv_exact 不是"非阻塞才需要的东西"。

    循环里必须处理三件事：推进指针、扣减剩余长度、区分 EINTR（原地重试）与真错误。写循环读时还要把返回 0（对端提前关闭）单独作为一种结果返回给调用方——它既不是成功也不是 errno 错误，混进任何一边都会让上层判断失真。

    加分点两个：① writev/sendmsg 的短写更难处理，重试时不能原样再调一次，必须把 iovec 数组按已写字节数往前推（跳过写完的项、把当前项的 iov_base/iov_len 调整），这是 iovec 类代码出 bug 频率最高的地方；② 设了 SO_RCVTIMEO 时，超时且已经收到部分数据的 recv 返回的是已读字节数而不是 −1，于是 recv_exact 会悄悄退化成"读了一半就返回"，必须自己区分"完全没读到"和"读了一半"。

  3. 基础recv 返回 0 和返回 −1 分别意味着什么？

    TCP 上返回 0 只有一个含义：对端已经关闭了发送方向（你收到了 FIN）。这是有序关闭，不是错误——之后这条连接上再也不会有数据到来，但你仍然可以继续 send（对方可能只是做了半关闭）。

    返回 −1 才是"这次调用没成功"，必须再看 errno 分四类：

    • EAGAIN/EWOULDBLOCK——非阻塞下"现在没数据"，不是错误，回事件循环等下一次可读；
    • EINTR——被信号打断且一个字节都没传，原地重试；
    • ECONNRESET——对端发了 RST（进程崩了、或收到了发往已关闭连接的数据），立即清理，不要重试；
    • 其它——真错误，记日志并关闭。

    最经典的写错方式是把 0 和 −1 合并：if (n <= 0) continue; 会在对端断开后烧掉一整个 CPU 核——recv 稳定返回 0，循环永不退出。判读特征是 strace 里刷屏的 recvfrom(9, "", 4096, 0, NULL, NULL) = 0，同一个 fd 每秒几十万次，而监控上表现为"某进程 CPU 恒定 100% 但完全没有流量"。

    加分：UDP 上返回 0 是"收到了一个长度为 0 的数据报"，不是关闭——UDP 根本没有连接可关。把 TCP 的 if (n == 0) 断开 照抄到 UDP 代码里，对方发个空包就能把你踢下线。

  4. 基础EAGAIN 和 EINTR 有什么区别？分别怎么处理？

    EAGAIN（= EWOULDBLOCK，Linux 上同值）意思是"现在没得干"：非阻塞 socket 上缓冲区空（读）或满（写）。处理方式是把控制权交回事件循环，等下一次可读/可写事件，不要原地忙等重试——那会退化成自旋。

    EINTR 意思是"被信号打断了，而且一个字节都还没传"。处理方式相反：原地重试同一个调用，因为什么都没发生，重试是完全安全的。

    把两者搞混的后果对称地糟糕：把 EAGAIN 当错误 → 连接被无故关闭；把 EINTR 当错误 → 偶发失败，而且只在有定时器或信号的环境下复现，本地一跑就好。

    加分点是"设了 SA_RESTART 就不用管 EINTR 了"这个说法在 socket 上不成立：Linux 的 signal(7) 明确写着，如果 socket 设了 SO_RCVTIMEO 或 SO_SNDTIMEO，被信号打断时即使有 SA_RESTART 也会返回 EINTR。而设收发超时恰恰很常见。所以结论是：所有阻塞式 socket 调用都要显式处理 EINTR，不要依赖 SA_RESTART。另外注意 connect 被 EINTR 打断时不能简单重试——握手仍在后台进行，正确做法是转成等可写 + getsockopt(SO_ERROR)。

8.2 中级（区分熟练度）

  1. 中级SIGPIPE 是怎么产生的？有哪三种处理方式，各自适合什么场合？

    向一个对端已经完全关闭的 TCP 连接写数据，内核会发 SIGPIPE，默认动作是终止进程——不是返回错误，是进程直接没了，连打日志的机会都没有。

    时序要说清楚，这是这道题的分水岭：对端 close() 之后你的第一次 send 通常是成功的（FIN 只表示对方不再发送，你的数据照样被它的 TCP 收下），对方的 TCP 发现连接已经关闭于是回一个 RST，你的第二次 send 才触发 EPIPE + SIGPIPE。这解释了为什么这类事故总是"偶发、重现不了"。

    方式粒度可移植性适合
    signal/sigaction(SIGPIPE, SIG_IGN)整个进程POSIX，处处可用应用程序的默认选择
    send(..., MSG_NOSIGNAL)单次调用Linux 有，macOS 没有库代码：不该替宿主进程改全局信号处置
    setsockopt(SO_NOSIGPIPE)单个 socketmacOS/BSD 有，Linux 没有跨平台库里与上一条用 #ifdef 互补

    加分：指出三种方式的效果都只是"把信号换成返回值"——之后 send 返回 −1 且 errno == EPIPE，你仍然必须检查这个返回值，否则只是把"进程猝死"换成了"数据悄悄丢了"。再补一条排障经验：进程无日志消失时先看退出信号，systemd 里的 status=13/PIPE、或 shell 里的退出码 141（128+13）都是同一个指纹。

  2. 中级非阻塞 connect 的正确写法是什么？为什么必须查 SO_ERROR？

    四步：① 设 O_NONBLOCK（或建 socket 时带 SOCK_NONBLOCK）→ ② 调 connect()，返回 −1 且 errno == EINPROGRESS 是正常的 → ③ 用 poll/epoll 等这个 fd 变为可写 → ④ getsockopt(fd, SOL_SOCKET, SO_ERROR, &err, &len)，err == 0 才算连上。

    第四步是这道题真正考的东西。直觉是"可写就说明连上了"，但事实是连接失败时 fd 同样会变成可写（POSIX 规定出错时 select 会同时报可读与可写）。所以"可写"只表示"连接尝试有了最终结果"，成功还是被 RST 拒绝，只有 SO_ERROR 知道。

    漏掉这一步的代码在本机测试永远正确（回环一定连得上），上线后遇到对端服务没起来，就会"成功连上"然后在第一次 send 时莫名其妙 EPIPE，排查方向被彻底带偏。

    三个加分细节：① getsockopt(SO_ERROR) 读取的同时会清除这个挂起错误，只能读一次；② 同一个 fd 上 connect 失败后不能原地重试，必须 close 掉重新 socket()；③ 要用应用层超时而不是等内核默认超时——SYN 重传耗尽默认要一分钟以上（受 tcp_syn_retries 控制），业务通常等不起，所以要么在 poll 上给毫秒级超时，要么设 TCP_SYNCNT 减少重传次数。

  3. 中级select / poll / epoll 的差别在哪？为什么高并发要用 epoll？

    一句话概括：select/poll 每次调用都要把"我关心哪些 fd"重新告诉内核一遍、内核也要重新扫一遍；epoll 把这份关注列表常驻在内核里，只在增删时通信，就绪时由回调直接挂进就绪链表。

    差别在"1 万条连接、其中 50 条活跃"这种典型长连接场景下是数量级的：poll 每次都要拷贝并扫描 1 万个条目才找出那 50 个，epoll_wait 直接返回 50 个。成本从"随总连接数增长"变成"随活跃连接数增长"——这才是 epoll 的本质优势，而不是"epoll 更快"这种说法。

    加分：把 FD_SETSIZE 说准。它不是"最多 1024 个连接"，而是"fd 的数值不能 ≥ 1024"——一个只监听 3 个 fd 的进程，若那 3 个 fd 编号恰好是 2000 附近，FD_SET 就会越界写坏栈内存，不报错、只是随机崩溃。这是"新代码一律别用 select"最硬的理由。另外要知道 epoll 是 Linux 专有的，跨平台要抽象一层（BSD 用 kqueue、Windows 用 IOCP），这也是 libevent/libuv/Asio 存在的理由。

  4. 中级shutdown 和 close 有什么区别？半关闭有什么用？

    close 作用于文件描述符，shutdown 作用于连接本身。这是所有差别的根源：

    close(fd)shutdown(fd, how)
    做什么fd 引用计数减一直接操作连接，不看引用计数
    一定发 FIN 吗否——还有别的 fd 指向它时什么都不发是，SHUT_WR 立即发 FIN
    方向两个方向一起关可只关一个（SHUT_RD/SHUT_WR/SHUT_RDWR）
    之后还能读吗不能，fd 已失效SHUT_WR 后仍可继续 recv
    回收 fd 吗会不会，之后仍需 close

    半关闭就是 shutdown(fd, SHUT_WR)：告诉对端"我说完了，但我还在听"。典型场景是"请求可能很长、且以流结束作为请求边界"——客户端发完全部请求后 SHUT_WR，服务端 recv 到 0 就知道请求完整了，开始计算并把结果发回，客户端此时仍能收。close 做不到，它把接收方向一起关了，对端后续发来的数据会触发 RST。

    加分：举 fork 多进程服务的经典 bug——父进程 accept 后必须 close(cfd)，子进程必须 close(lfd)，否则引用计数永不归零，子进程 close 时对端收不到 FIN。症状是"连接数只涨不跌，而且两端都显示 ESTABLISHED"，非常迷惑人。这正好说明了"close 关的是 fd 不是连接"。

8.3 高级（体现深度）

  1. 高级epoll 的 LT 与 ET 有什么区别？工程上该选哪个？

    LT（水平触发，默认）关注的是状态：只要 fd 处于就绪状态，每次 epoll_wait 都报告它。ET（边沿触发）关注的是事件：只在状态发生变化的那一刻报告一次，比如"接收缓冲区从空变成非空"。

    类比：LT 是只要信箱里有信就一直响的铃，取空为止；ET 是邮差按门铃，他送完就走，之后不管你取没取都不会再按。

    LTET
    必须非阻塞 fd不强制必须，否则循环读的最后一次会永久阻塞
    一次事件读多少随意，读不完下次还报必须循环到 EAGAIN
    accept一次一条也行必须循环 accept 到 EAGAIN
    EPOLLOUT写不完才注册、写完立刻取消，否则空转可常驻注册
    写错的后果CPU 空转（监控能发现）连接静默挂死（很难发现，且只在高负载下出现）

    工程上默认选 LT。理由不是性能，而是出错代价不对称：LT 写错了顶多多几次系统调用或 CPU 空转，监控立刻能看到；ET 写错了是连接悄无声息地卡住，而且只在数据量大到一次读不完时才发生——测试环境的小报文永远触发不了。ET 的收益（少一些 epoll_wait 返回）在绝大多数业务里被 TLS、序列化、业务逻辑的开销完全淹没。确有性能证据、且团队对状态机很熟时再上 ET。

    加分：指出 LT 下用 EPOLLOUT 是有讲究的——常驻注册可写事件会导致每轮都触发（发送缓冲区通常都是可写的），CPU 直接 100%。正确做法是"只在还有数据没写完时才 EPOLL_CTL_MOD 加上 EPOLLOUT，写完立刻去掉"。ET 反而没这个问题，这是 ET 少有的、真正省事的地方。

  2. 高级ET 模式下为什么必须循环读到 EAGAIN？只读一次会发生什么？

    因为 ET 的通知条件是"内核收到了新数据"这个事件，而不是"缓冲区里有数据"这个状态。假设缓冲区里有 5000 字节，你只读走 2000，缓冲区从"有 5000"变成"有 3000"——这中间没有发生任何"新数据到达"的边沿，于是 epoll_wait 永远不会再提这个 fd。剩下 3000 字节就此长眠，连接表现为"卡住了但没断开"。

    换个角度说：读到 EAGAIN 的本质是"重新武装（re-arm）那个边沿"。只有确认了内核缓冲区确实空了，才能保证"下一个字节到达时一定会给我新事件"。所以正确写法是 while ((n = recv(...)) > 0) { 处理 } ，直到 n < 0 && errno == EAGAIN 才退出。

    同一个道理适用于 accept：两条连接在同一瞬间进入全连接队列只算一次边沿，只 accept 一条，另一条会一直躺在队列里，直到下一条新连接到来才被顺带取走。症状是"高并发建连时部分客户端连接建立特别慢"，而且负载越高越明显。

    三个加分点：① ET 必须配非阻塞 fd——阻塞 fd 上循环读，最后那次没数据的 recv 会把整个事件循环线程挂死，这是比漏读更严重的事故；② 循环读要有公平性上限，一条连接持续高速灌数据时，死读到 EAGAIN 会饿死其它连接，成熟框架会设一个单次最大读取字节数，读满就先记住"这个 fd 还没读完"、下一轮继续；③ ET + 多线程通常还要配 EPOLLONESHOT，否则同一个 fd 可能被两个线程同时处理。

  3. 高级SO_REUSEADDR 与 SO_REUSEPORT 有什么区别？各自解决什么问题？

    名字像，作用完全不同。

    • SO_REUSEADDR 解决的是"重启服务时绕开 TIME_WAIT"：允许 bind 到一个仅被 TIME_WAIT 连接占用的本地地址。它不允许两个 socket 同时 LISTEN 同一个 IP:port——真有别的进程在监听，bind 照样失败。所以它不削弱安全性，服务端监听 socket 应当无条件设它，这是标准写法而不是调优。
    • SO_REUSEPORT（Linux 3.9+）解决的是"多个进程/线程同时监听同一个端口"：每个 worker 各自 socket + bind + listen，内核按四元组哈希把新连接分发给其中一个。所有参与的 socket 都必须设这个选项，且要求同一 UID（防止别的用户劫持端口）。

    SO_REUSEPORT 相比传统方案的收益：比"父进程 accept 后分发给 worker"少一次跨线程传递，负载均衡在建连时就由内核做完了；比"多进程共享一个监听 fd 一起 accept"好在没有惊群——每条连接只唤醒一个进程。

    加分要说出它的代价与坑：① 分发按四元组哈希，不看各 worker 的实际负载，某个 worker 恰好拿到几条重连接时会不均衡，需要按负载分发就得回到应用层调度；② 滚动重启时，正在旧进程 accept 队列里排队的连接可能被丢弃（具体行为随内核版本而变，必须在目标内核上实测），所以优雅退出要先停止接受新连接、等队列排空再退。另外提一句 EPOLLEXCLUSIVE（Linux 4.5+）是解决惊群的另一条路，适合"共享一个监听 fd"的架构。

  4. 高级服务重启后 bind 失败报 Address already in use，你会怎么分析？

    这是道综合题，好的回答应该先分诊再给方案，而不是直接甩一个 SO_REUSEADDR。第一步永远是看那个端口现在到底是什么状态：

    • ss -lntp '( sport = :9000 )'——有 LISTEN 行说明真有进程在监听，是旧进程没退干净（或者你启了两份），SO_REUSEADDR 救不了，得先把它停掉；
    • ss -ant state time-wait '( sport = :9000 )'——只有 TIME_WAIT，这才是本题的典型场景。

    为什么会有 TIME_WAIT：主动关闭的一方（谁先发 FIN 谁就是）在四次挥手结束后进入 TIME_WAIT，停留 2×MSL（Linux 上固定 60 秒）。你 Ctrl+C 掉服务端时是服务端先发 FIN，所以处于 TIME_WAIT 的正是服务端自己的 0.0.0.0:9000，默认规则不允许 bind 一个还被 TIME_WAIT 占着的本地地址。

    TIME_WAIT 存在的两个理由都很实在，能说出来就说明不是死记：① 保证最后那个 ACK 丢失时，对端重传的 FIN 还能被应答，让对端干净地关闭；② 让本次连接的迷路报文在网络中彻底消亡，避免被后来复用同样四元组的新连接错收。

    正解：监听 socket 在 bind 之前设 SO_REUSEADDR。它正是对这条规则的豁免，且不牺牲安全性。

    加分是把常见的错误答案一一排掉：

    • net.ipv4.tcp_tw_reuse 没用——它只作用于主动发起连接的一侧（复用本地临时端口去连出去），对服务端的监听端口毫无帮助；
    • tcp_tw_recycle 已在 Linux 4.12 删除，它在 NAT 后面会导致大量连接被莫名丢弃，网上流传的"设它解决 TIME_WAIT"是过时且有害的建议；
    • SO_LINGER(1,0) 是危险的偏方——它没有 TIME_WAIT 是因为它根本没正常关闭，而是发了 RST：发送缓冲区里的数据被丢弃，对端 recv 拿到 ECONNRESET。只有"这条连接的数据本来就不要了"时才该用；
    • 如果是"服务端 TIME_WAIT 有几万条"这种容量问题，那说明是服务端在主动关连接。如果协议允许，把主动关闭改到客户端一侧，比调任何内核参数都有效——TIME_WAIT 落到客户端后，每个客户端只需承担自己那一份。再往后才是长连接化、扩大 ip_local_port_range。
