通信系统的性能、可靠性与高可用

通信系统为什么比普通业务系统更"斤斤计较"实时性、确定性与故障恢复？本篇讲清性能指标、可用性(几个9)、容错冗余、重试/超时/背压、负载均衡与扩展性，并给出故障处理的工程心法。

Module 10 阅读 ~22 min HA / 容错
01

为什么通信系统更严苛

和普通业务系统的差别

  • 实时性/确定性：前传有 µs 级窗口，晚到的数据等于没到（不像网页慢点没事）。
  • 不可中断：基站宕几秒就是大面积掉话/断网，可用性要求极高（电信级 99.999%）。
  • 规模：一个核心网要扛海量并发用户与信令。
  • 故障必现：链路抖动、丢包、硬件失效是常态而非例外，必须设计成"故障可恢复"。
🏥 类比：普通业务系统像餐厅——慢一点、偶尔关门可接受；通信系统像医院急诊/供电——必须 7×24 不间断、响应有硬时限，出问题要能立即切备用。
02

性能指标：延迟 / 吞吐 / 抖动 / 丢包

四个核心度量

指标含义为何关键
Latency 延迟单程/往返耗时前传/URLLC 有硬上限
Throughput 吞吐单位时间处理量(bps/pps)决定容量
Jitter 抖动延迟的波动实时流最怕抖动(比平均延迟更致命)
Packet Loss 丢包丢失比例影响质量/触发重传
尾延迟(p99/p999)比平均延迟更重要：平均 1ms 但 p999 达 50ms，对实时系统仍是灾难。通信系统盯的是最坏情况的确定性，不是平均值。
03

可用性与几个 9

电信级 = 99.999%

可用性年停机时间级别
99%~3.65 天普通
99.9%~8.77 小时较好
99.99%~52.6 分钟高可用
99.999%(5个9)~5.26 分钟电信级
可用性 = MTBF / (MTBF + MTTR)。提高它要么让故障更少(MTBF↑)、要么让恢复更快(MTTR↓)。通信系统两手抓，尤其靠冗余把 MTTR 降到秒级。
04

容错与冗余

故障不可避免，切换要无感

  • 冗余：主备(1+1)、N+1、双活。硬件、链路、进程都可冗余。
  • 故障检测：心跳/健康检查，快速发现挂掉的节点。
  • 快速切换 Failover：主挂了备立即接管，会话/状态尽量不丢。
  • 状态复制：主备同步状态(或用共享存储)，实现热备而非冷启。
  • 优雅降级：部分故障时保住核心功能，而非整体崩溃。
05

Retry / Timeout / Backpressure

面对拥塞与失败

Timeout 超时：任何等待都要有上限，否则一个卡死拖垮全局。是可靠性的第一道防线。
Retry 重试：瞬时失败可重试，但必须指数退避 + 上限 + 幂等，否则重试风暴会雪上加霜。
Backpressure 背压：下游处理不过来时，向上游反馈"慢点发"，而不是无限堆积导致内存爆掉/延迟飙升。队列有界 + 拒绝/丢弃策略是关键。
⚠️ 常见事故：无界队列 + 无超时 + 无退避重试 = 一点抖动就级联雪崩。三者要一起设计。
06

负载均衡与可扩展

从单机到集群

  • 负载均衡：把流量/会话分散到多个实例，避免单点过载。
  • 水平扩展：加机器就能加容量(无状态或状态可分区最容易扩)。
  • 分区/分片：按用户/小区把状态切开，各自独立扩展。
  • 云原生 O-RAN：CU/DU 软件化后可在通用服务器上弹性伸缩，这也是 O-RAN 的动机之一。
"弹性伸缩"在电信负载上并不像互联网服务那样自动成立：独占 CPU、大页、SR-IOV 直通会让可调度节点集缩到个位数，滚动升级还会打断 SCTP 偶联与 NETCONF 会话。5 个 9 靠的是无状态化 + 状态外置（UDSF）+ 主动引导对端迁移，而不是"挂了就重启"。这些取舍见 Module 03 电信云原生：NFV → CNF、5GC 与 O-Cloud 的容器化；横向扩展与会话粘性的实现手法见 Module 09 通信服务的高并发。
07

故障处理心法

设计原则

  • 假设一切会失败：链路会断、进程会挂、包会丢——为故障而设计。
  • 快速失败 + 快速恢复：早发现、早切换，把 MTTR 压到最小。
  • 隔离爆炸半径：故障局部化，别让一个模块拖垮全系统(舱壁/熔断)。
  • 可观测：完善的指标/日志/告警，故障时能秒级定位。
  • 确定性优先：宁可稳定的稍慢，不要偶发的极快。
🎯 本篇要点回顾
  • 通信系统重实时性/确定性/不中断，盯尾延迟而非平均
  • 四指标：延迟/吞吐/抖动/丢包；抖动对实时流最致命
  • 电信级 = 5个9；可用性=MTBF/(MTBF+MTTR)
  • 冗余+故障检测+快速切换实现 HA
  • 超时+退避重试+背压 三件套防雪崩
