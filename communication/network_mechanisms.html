主线：一个包怎么走完全程

先看全景，再逐个机制拆解

主机 A（192.168.1.10）访问另一个网段的服务器 B（10.0.0.5）。这个包不是"直达"的，而是被一台台设备接力：

全篇最重要的直觉：IP 是"最终送到哪"，全程不变；MAC 是"这一跳交给谁"，每过一台路由器就被改写。
🚚 生活类比：跨省快递。面单上的收件地址从交寄到签收全程不变，这是 IP；包裹实际一段段接力，每段的"下一站是谁"被反复重写，这是 MAC。面单上那栏"已中转次数"超限就当寄丢销毁——这是 TTL。

1.3 那些"IP 全程不变"的例外

这是极好用的一阶近似，但真实网络有四类合法例外——不知道它们，抓包结果会完全对不上模型：

NAT / NAPT

边界设备改写源 IP 与端口，用会话表把回包翻译回来。代价是有状态：表满了新连接建不起来，设备重启表就丢，长连接被无声中断。

隧道 / 封装

GRE、VXLAN、5G 的 GTP-U：原包整体塞进新 IP 包的载荷，外层逐段变化、内层才是业务地址。代价：每层封装吃掉 MTU（第 6 章），沿途设备看不到内层五元组。

Anycast

同一个 IP 被多地同时宣告，路由把用户导向"最近"的一个。代价：路由一抖就可能切到另一个实例，对有状态服务是灾难。

负载均衡器 / 代理

四层 LB 做 DNAT；七层代理干脆终结连接再新建一条，后端看到的源 IP 是 LB 的，真实客户端 IP 得靠 X-Forwarded-For 单独带。

"用户面通了，但下载只有几 Mbps。"抓包发现 GTP-U 外层是 基站IP → UPF IP，中间承载网有一段做了 ECMP。所有用户面流量的外层五元组完全相同（UDP 2152，同一对 IP），哈希把它们全压在一条链路上，那条先打满、另外三条空着。解法是让承载网参与内层哈希，或在外层 UDP 源端口上做熵（VXLAN 正是这么做的，GTP-U 不带熵字段）。ECMP 分不分得开，取决于设备能看到多少变化的字节。
02

ARP：从 IP 找 MAC

L3 地址与 L2 地址之间的桥

主机知道要发给某个 IP，但链路层投递需要 MAC 地址。把"IP → MAC"翻译出来的就是 ARP。

ARP（Address Resolution Protocol，RFC 826）：在本地链路上广播"谁是 192.168.1.1？把 MAC 告诉我"，持有该 IP 的设备单播回复，结果缓存进邻居表。
目标在同网段就 ARP 目标本身；不同网段则 ARP 默认网关。这就是"目的 MAC 逐跳改写"的直接来源——A 发给跨网段的 B 时，帧上写的其实是网关的 MAC。

2.2 Linux 邻居表：六个状态，和一个会咬人的阈值

老教材说的"ARP 缓存"在 Linux 里叫邻居表，IPv4 的 ARP 与 IPv6 的 NDP 共用同一套状态机。arp -a 只是简化视图，做设备的人应该用 ip neigh：

$ ip -s neigh show dev eth0
192.168.1.1   lladdr 00:1a:2b:cc:dd:ee  ref 3 used 0/0/0   REACHABLE
192.168.1.23  lladdr 00:1a:2b:44:55:66  ref 1 used 92/92/8  STALE
192.168.1.77                            ref 1 used 2/2/2    INCOMPLETE
192.168.1.99  lladdr 00:1a:2b:77:88:99  ref 1 used 5/5/5    FAILED
STALE 不是问题，一屏 STALE 也不需要"修"。Linux 的设计意图正是只在有流量时才验证可达性——静默的邻居不值得花一次广播去探测。REACHABLE 的默认基准 30 s，实际超时在 0.5~1.5 倍间随机化以避免全网同步刷新。真正要警觉的只有 INCOMPLETE（对端没响应：不在线、ARP 被挡、或 VLAN 配错导致压根不在一个广播域）和 FAILED。

接下来是真正会咬人的东西——邻居表不是无限大的：

参数（net.ipv4.neigh.default.*）默认行为常见误判
gc_thresh1 / gc_thresh2128 / 512低于 1 完全不回收；超过 2 在 5 秒后开始激进回收回收把还在用的条目清掉，表现为"偶尔要重新 ARP 一次"

一台做汇聚的 x86 转发节点，二层域里约 1500 台设备共处一个大 VLAN。业务表现是随机、短暂、无规律的丢包：ping 大部分正常但偶尔连续几个不通，重启后好一阵又复发，不针对特定目标也没有时间规律。gc_thresh3 还是默认的 1024，而邻居数早已超过它。决定性线索只有 dmesg 里那句 neighbor table overflow。应急是把阈值提到邻居数的 2 倍以上，真正的解法是拆小二层域——上千台设备挤一个广播域，ARP 广播本身就是一笔可观的固定开销。

2.3 三个必须知道的 ARP 变体

代理 ARP（Proxy ARP）

路由器替不在本网段的主机回答 ARP，让主机误以为"目标就在隔壁"。现在主要出现在某些无线/接入网关和点对点链路上。陷阱：它让"谁负责这个 IP"变得不透明，抓包会看到多个 IP 指向同一个 MAC，极易误判成 ARP 欺骗。除非明确知道为什么要开，否则保持关闭。

IPv6 没有 ARP

IPv6 用 NDP（RFC 4861）取代 ARP，跑在 ICMPv6 上（NS / NA 报文），并用组播而不是广播——只有被请求节点组播地址匹配的少数节点会被打扰，这对大二层域是实质改进。代价是它依赖 ICMPv6，详见 7.2。

03

路由：跨网段转发

路由器如何决定"往哪个口送"

路由器的核心工作是查路由表：按目的 IP 用"最长前缀匹配"找到下一跳和出接口。交换机在网段内按 MAC 转发，路由器连接不同网段、按 IP 转发；小网静态配，大网用 OSPF / BGP 自动学习拓扑。

3.1 最长前缀匹配：为什么必须是"最长"

最长前缀匹配（LPM, Longest Prefix Match）：多条路由都能覆盖目的 IP 时，选前缀最长（掩码位数最多、覆盖范围最小）的那条。
📮 生活类比：邮局按地址的"精确程度"分拣。写"中国"的信归国际部，写"中国浙江杭州西湖区"的归西湖区投递员——越具体的规则越优先，不然所有信都被"中国"这条最粗的规则吃掉。默认路由就是那条前缀长度为 0、永远最后才轮到的兜底规则。
这也是"我明明配了默认路由，为什么流量不走它"的答案——一定有更长的前缀先命中了。别肉眼比对掩码，让内核直接给结论：
$ ip route get 10.1.2.3
10.1.2.3 via 192.0.2.9 dev eth3 src 192.0.2.10 uid 0

硬件 FIB 容量是一堵会突然爆的墙。接入 / 汇聚交换机的转发表往往只能装几万到十几万条前缀。BGP 全表越过这条线时设备不报错，而是把溢出的前缀退回 CPU 软转发——那部分流量从线速掉到每秒几万包，同时 CPU 打满、路由协议超时、引发全局震荡。特征是只有部分目的地址慢 / 丢包，而且越来越糟，所以 TCAM 使用率应纳入常规巡检。

3.3 内核不止一张表：策略路由与 ECMP

"查路由表"其实是"先查规则、再查表"。策略路由让选表本身依赖源地址、fwmark 或入接口：

ip rule 里的一行含义常见误判
0: from all lookup local本机地址，优先级最高动了它会让本机地址不可达
100: from 10.9.0.0/24 lookup mgmt按源网段选表规则命中但该表没路由时会继续往下匹配，看起来像"规则没生效"
200: fwmark 0x64 lookup ptp按 nft 打的标记选表标记打在错误的 hook 上，规则永远不命中
32766: from all lookup main常规表，ip route show 就是它以为"只有这一张表"，于是找不到流量为什么走别处
策略路由是多网口设备的标准工具：管理面走 eth1、用户面走 eth0、同步面走 eth2，各有各的默认路由。用一张 main 表硬塞配不出来——一张表里只能有一条默认路由。

ECMP（等价多路径）是同一前缀有多个等价下一跳时的负载分担。关键是它按流哈希而不是逐包轮转：

net.ipv4.fib_multipath_hash_policy哈希依据什么时候必须调
0（默认）仅 L3：源 IP + 目的 IP一对主机间的多条 TCP 连接会全压在一条链路上
1L4：加上源 / 目的端口多连接场景立竿见影，最常用的一档
2L3 + 隧道内层GTP-U / VXLAN：外层五元组相同，只有看内层才分得开
面试爱问"ECMP 为什么不逐包轮转，那样不是更均匀吗？"为了不打乱包序：两条路径时延几乎不可能相同，逐包轮转会让同一条 TCP 流乱序到达，接收端把乱序当丢包信号、触发重传并压低窗口，吞吐反而崩掉。代价是粒度粗——只有几条大流时会严重不均，这就是"大象流"问题。

3.5 反向路径过滤：一个常被忽略的静默丢包点

包能进来、路由也有，内核就是不收——很多时候是 rp_filter：它检查"从这个入接口收到的源 IP，回包时是不是也走这个接口"，不一致就丢。

04

VLAN：在一根线上切分广播域

逻辑隔离，不用为每个网络单独拉线

一台交换机下的所有口默认同属一个广播域，广播风暴与安全隔离都成问题。VLAN 用一个 12 位的 VLAN ID 把物理交换机逻辑切分成多个互不相通的网络，代价只是帧里多出 4 个字节：

VLAN 解决什么

  • 隔离：不同 VLAN 默认不能直接通信，要经三层
  • 缩小广播域：抑制广播风暴与 ARP 开销
  • 灵活：按业务 / 租户划分，不受物理位置限制

通信系统里的应用

  • 把管理面 / 用户面 / 同步流量隔离在不同虚网
  • O-RAN 前传用 VLAN + PCP 区分 C/U/S/M 四个平面，见 O-RAN 三平面
VLAN ID规范含义工程上意味着什么
0"优先级标签"：不指定 VLAN，只带 PCP设备支持得不一致，跨厂商互通尽量避免
1多数设备的默认 / 原生 VLAN不要用它承载业务：误配的汇集地，且常有厂商私有控制协议
2 – 4093可自由使用正常业务范围（部分设备保留 1002–1005 给令牌环遗留用途）
4095保留不可使用；Linux 桥 / 某些芯片用它表示"任意 VLAN"
承载 VLAN 的中转口 MTU 至少要设到 1504（"baby giant"），否则带标签的满长帧会被当超长帧丢掉——现象是小包全通、大包不通：ping 默认包长正常，ping -s 1472 就断。回传 / 汇聚这类不追求微秒级确定性的段落干脆直接开 Jumbo，但前传不能这么办（理由见 5.3）。

4.3 VLAN 的边界：什么时候它不够用

4096 这个上限

VID 只有 12 位，一张网最多 4094 个可用 VLAN。对园区够用，对多租户云或大规模切片不够——VXLAN（24 位 VNI，约 1670 万）由此而来。而 QinQ（802.1ad，两层标签）不解决规模问题，它解决的是客户 VLAN 与运营商 VLAN 撞号。

VLAN 仍然是二层

再多 VLAN 也改不了一件事：每个 VLAN 内部还是一个广播域，ARP 广播、未知单播泛洪、STP 收敛的代价照旧。把一个 VLAN 做到上千成员，2.2 那个邻居表溢出的案例就会找上门。

05

QoS：拥塞时谁先走

带宽有限，就得排优先级

QoS（Quality of Service）是一组"网络拥塞时按重要性区别对待流量"的机制。没有它，语音包和下载包平等排队，语音就会卡。优先级在两层各有一个字段：

层次标记字段作用范围
L2（以太网）802.1p PCP（3 位，在 VLAN 标签里）只在带标签的二层链路上有效，0~7
L3（IP）DSCP（6 位，在 IP 头 TOS 字节高位）DiffServ，跨路由器端到端有效
🏥 生活类比：急诊分诊。医院不是先来先看，而是先分诊、给一个手环颜色（标记）、按颜色排不同的队（调度），同时限制"每小时最多接多少非急诊"（限速）。而候诊椅太多反而是坏事：所有人都能坐下等，于是没人发现系统已过载，等待时间悄悄涨到四小时——这就是 5.5 的 bufferbloat。
前传网上同时跑着 eCPRI 用户面、PTP 同步和管理面，三者的时延容忍度差三个数量级，必须靠 VLAN + QoS 严格隔离（O-RAN 三平面）。注意本节是传输网视角；3GPP 另有一套还管空口资源保障的 5QI / QoS Flow / DRB 模型，两套标签必须对齐（QoS、网络切片与边缘）。

5.1 DSCP 码点：不要自己发明数字

DSCP 是 TOS 字节的高 6 位（低 2 位归 ECN，见 5.6）。64 个码点理论上随便用，但 RFC 4594 给了一套业界普遍遵循的建议——跨域互通按它填，才不用逐条协商：

DSCP 名十进制期望的转发行为（PHB）典型业务
CS7 / CS656 / 48网络控制，最高运营商自己的关键控制；路由协议（OSPF / BGP）、PTP 同步
EF46加速转发：低时延、低抖动、低丢包，必须限速语音（VoIP / VoNR）、eCPRI 用户面
AF41–AF4334 / 36 / 38保障转发第 4 类，三档丢弃优先级互动视频、会议
AF31–AF3326 / 28 / 30保障转发第 3 类信令、流媒体
AF21–AF1318 – 22 / 10 – 14保障转发第 2、1 类数据事务；批量但有时限的数据
DF (BE)0尽力而为其它一切；也是被清零后的下场
EF 必须配限速，这不是可选项。它的语义是"你先走"，若不限制带宽占比（常见做法是不超过链路的 30%~50%），EF 流量一旦超过链路容量就会把其它队列饿死，包括路由协议和管理面——设备"业务还在跑但完全失联"，连改配置救回来都做不到。严格优先级的队列一定要成对配置：优先级 + 上限。

PCP 只有 3 位，所以 DSCP → PCP 必然是多对一的有损压缩（默认取高 3 位，即 CS 值）。CS7/CS6/EF 压过去无损，但 AF41/42/43 高 3 位相同、全落到 PCP 4——三档丢弃优先级在二层被合并成一档。跨 L2 / L3 边界时要逐条确认两侧的映射表。

DSCP 是"信任"问题而不是"配置"问题。任何人都能在自己的包上写 DSCP 46，所以每个网络在信任域边界都要选择：信任对方的标记，还是重新分类打标。默认几乎都是不信任、清零——这正是"应用里设了 EF 却依然不优先"最常见的答案。验证很直接：两端同时抓包比对 TOS 字节。

5.5 队列管理：bufferbloat 与 AQM

前面讲的都是"谁先出队"。还有一个更根本的问题被长期忽略：队列本身该有多长？直觉是"越大越不丢包"，这个直觉错得很贵。

Bufferbloat（缓冲区膨胀）：设备配了远超需要的缓冲区，拥塞时包不被丢弃、而是排在队里等。吞吐没掉，但排队时延暴涨到几百毫秒甚至几秒。对交互业务这比丢包糟得多——丢包可以重传，时延无法追回。

把长度换算成时间，问题立刻直观。同一个 128 包的 FIFO（老家用路由器的默认值）满队时：

链路速率128 × 1500 B 满队的排队时延体感
1 Gbps1.5 ms可以接受
100 Mbps15 ms开始影响交互
10 Mbps154 ms语音明显卡
1 Mbps1536 ms一秒半——网页点了没反应

同一个"合理"的长度在不同速率下时延差 1000 倍——队列不能按包数配，要按时间配。而时延之所以会一路涨到把缓冲区填满，是因为基于丢包的拥塞控制只认丢包这一个信号：发送方持续加速，直到队列溢出才退让：

AQM（主动队列管理）的思路是：不等队列溢出，提前、少量地丢包或打 ECN 标记，主动把拥塞信号送回发送方。三代方案的演进思路很值得体会：

算法判断依据解决了什么遗留问题
Tail Drop队列满了才丢（基线）时延失控；全局同步——多条流一起退让又一起加速
RED（1993）平均队列长度超阈值后按概率丢提前预警、打散全局同步参数极难调，换个场景就要重调——它部署率低的直接原因
CoDel（RFC 8289）包在队列里的驻留时间是否持续超过 target（5 ms）无需调参；能区分短暂突发与持续积压单队列，挡不住大流挤占交互流
FQ-CoDel（RFC 8290）按流哈希分成上千个子队列，各跑一份 CoDel流间隔离：大下载压不住语音流哈希碰撞；隧道流量看不到内层
CAKEFQ-CoDel + 内建整形 + DSCP 感知三件事打包成一条命令CPU 开销更高；需要准确告知链路速率
CoDel 最关键的洞见：它测的是时延，不是队列长度。"多长的队列算太长"没有普适答案，取决于速率、流数、包长分布；而"包在队里等了多久算太久"有：5 ms，对任何速率都成立。把控制目标从一个依赖环境的量换成一个不依赖环境的量，参数就自然消失了——这个思路在系统设计里非常通用。

队列该配多大？经典结论 缓冲区 ≈ 1 × BDP（如 1 Gbps × 10 ms = 1.25 MB）只对一条流成立；实际修正是 BDP / √n（n 为并发长流数），n = 100 时只需 BDP/10——这解释了核心路由器的缓冲区为何远小于经典规则、利用率却依然接近满。按时间给上限，超出部分交给 AQM：

5.6 ECN：不丢包也能通知拥塞

AQM 靠丢包传信号，但丢包本身有代价——被丢的那份要重传，对短连接尤其伤（只有几个包的请求丢一个可能要等一次超时）。ECN（RFC 3168）把信号从"丢一个包"改成"在包上做个标记"：

要素怎么配 / 怎么看不到位会怎样
端点协商net.ipv4.tcp_ecn：0 不用，1 主动发起也接受，2 只被动接受（多数发行版默认）包被标成 Not-ECT，退回丢包信号
瓶颈处的队列tc qdisc replace dev eth0 root fq_codel ecn队列只丢包，不打 CE 标记
验证标记真的发生tc -s qdisc 里的 ecn_mark；抓包 tcpdump 'ip[1] & 0x03 != 0'一直是 0 = 这条路上根本没在用 ECN
沿途所有设备必须不破坏这两个 bit见下面那条部署难题
ECN 的部署史是一部"中间设备把好意撞碎"的历史，三种破坏方式危害不同：① 早期有防火墙 / 负载均衡看到 SYN 里的 ECN 协商位就丢弃该 SYN，开了 ECN 的主机连不上某些站点——最致命，因为表现是"完全打不开"而不是"慢一点"，tcp_ecn 默认取 2 正由此而来；② 有设备把整个 TOS 字节清零，只是失去收益；③ 最危险的是只清 CE 不清 ECT，信号被吞掉而两端都以为 ECN 在工作，比不开更糟。可控网络里结论相反：数据中心（DCTCP）与自管承载网上每一跳都是自己的，很值得开。近年的 L4S（RFC 9330 系列）用 ECT(1) 承载更高频的信号，部署仍在早期。
06

MTU 与分片

一个帧最多能装多少，装不下怎么办

MTU（Maximum Transmission Unit）：链路层一帧能承载的最大载荷，标准以太网 1500 字节。IP 包超过下一跳 MTU 就要分片，TCP 则用 MSS 协商每段最大数据量，PMTUD 负责探出端到端路径上最小的那个 MTU。
「移动承载网都开 Jumbo」是个常见的误记，前传恰恰相反。回传（backhaul）确实普遍配 9000~9600 的大帧——那里外层 GTP-U 封装要吃掉 36~56 字节，不开大帧就得把用户内层 MTU 压到 1400 上下（见 前传/中传/后传）。但前传（fronthaul）通常宁可放弃 Jumbo：9000 字节帧在 1 Gbps 上的非抢占阻塞是 72 µs，对百微秒级的前传预算是硬伤（推导见 5.3）。前传上既要大帧又要确定性，靠的是帧抢占（802.1Qbu / 802.3br）或提高线速，而不是直接开 Jumbo。

6.1 把这几个名字彻底分清

术语混用是排障时最常见的沟通成本来源。先把账算清楚——1500 字节 MTU 上到底能装多少应用数据：

名字指的是以太网 + IPv4 + TCP 的典型值
MTU链路层载荷的最大字节数（不含以太网头 / CRC）1500
线上帧长MTU + 以太网头 14 + CRC 41518（每层 VLAN 再 +4）
帧间开销前导码 7 + SFD 1 + 帧间隙 12+20（算线速利用率时不能忘）

带时间戳选项的 MSSTCP 选项占 12 字节（时间戳 10 + 对齐 2）有效载荷降到 1448

"为什么抓包看到的 TCP 载荷经常是 1448 而不是 1460？"——时间戳选项（RFC 7323）占了 12 字节。1448 是判断"段是不是满长"的基准：远小于它就要考虑是应用写得碎（见 Socket 编程）还是被 MSS 钳制了。

6.3 PMTUD 黑洞：教科书级的静默故障

Path MTU Discovery（RFC 1191 / IPv6 的 RFC 8201）：发送方给包打 DF，装不下的那一跳丢弃并回一个带着下一跳 MTU 的 ICMP "Fragmentation Needed"，发送方据此调小。问题在于——它的正确性完全依赖那个 ICMP 能回来：

图里最后那条症状值得单独记住：HTTPS 打不开而 HTTP 能开——TLS 握手的证书链报文往往正好是几 KB 的大包，而 HTTP 的小请求不受影响。ICMP Type 3 Code 4（IPv4）与 ICMPv6 Type 2（Packet Too Big）是网络的必需品，不是可选的调试工具。

确认路径 MTU 只需要两条命令，它们也是判断"是不是黑洞"的分界线：

$ ping -M do -s 1472 -c 2 10.0.0.5      # -M do 设 DF；1472 + 8 ICMP + 20 IP = 1500
2 packets transmitted, 0 received, 100% packet loss       ← 不通

$ ping -M do -s 1420 -c 2 10.0.0.5
1428 bytes from 10.0.0.5: icmp_seq=1 ttl=61 time=8.2 ms   ← 通了，继续二分

$ ip route get 10.0.0.5
10.0.0.5 via 192.0.2.1 dev eth0 src 192.0.2.10 mtu 1400
    cache expires 597sec mtu 1400
# 出现 mtu 1400 = 路径回了 ICMP，PMTUD 正常；黑洞的特征恰恰是这里【什么都没有】
处置命令适用与边界
应急：钉死路由 MTUip route change 10.0.0.0/8 via 192.0.2.1 dev eth0 mtu 1400只影响这一条路由，立刻生效；治标
通用：MSS 钳制iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu改写 TCP SYN 里的 MSS，让两端一开始就不发大包，不依赖 ICMP——网关上的标准做法。隧道口开销固定时改用 -o gre1 … --set-mss 1360 更可控
根治：放行 ICMPICMP Type 3 Code 4 与 ICMPv6 Type 2唯一能同时救 TCP 与 UDP 的做法。nstat -az | grep -i IcmpInDestUnreachs 长期为 0 就非常可疑
MSS 钳制只救 TCP，救不了 UDP——它靠改写 TCP SYN 生效，而 UDP 没有握手也没有 MSS。所以 QUIC、GTP-U、eCPRI、DNS over UDP 必须自己处理路径 MTU：要么保守取值（QUIC 规定初始至少支持 1200 字节载荷），要么实现 PLPMTUD（RFC 8899），在传输层自己用探测包试出来。这就是"现代协议都在自己做 MTU 探测"的原因。

GTP-U 承载的用户面业务，少数网站页面能开、图片加载不出来：隧道内层 MTU 是 1464，而 UE 按 1500 发满长包并带 DF，路径上那一跳丢弃它、回程 ICMP 又被防火墙拦掉——小的 HTML 请求走得通，图片这种大响应走不通。处置要双管：① 在 5G 侧通过 PCO 把 MTU 下发给 UE（3GPP 在 PDU 会话建立时提供了这个机制）；② 在边界做 --clamp-mss-to-pmtu 兜住不听话的终端。只做②不做①，QUIC、视频这类 UDP 业务依然会踩坑。

6.5 Jumbo Frame：收益、代价与"两端必须一致"

Jumbo 的收益来自固定开销占比下降，但真正的收益不在带宽而在包率：

1 Gbps 满速发送标准帧（载荷 1500）Jumbo（载荷 9000）
线上总占用（含头 14 + CRC 4 + 前导与间隙 20）1538 B9038 B
有效载荷占比97.5%99.6%（只多 2 个百分点）
每秒包数≈ 81 274 pps≈ 13 830 pps（降到 1/6）
真正的收益每个包都要过一次协议栈、一次中断合并、一次 DMA 描述符——包率降 6 倍就是这部分 CPU 开销降 6 倍，在 10G/25G 上是决定性的

什么时候值得开

存储网络（iSCSI / NFS / Ceph）、数据中心东西向流量，以及任何"CPU 先于带宽成为瓶颈"的场景。判断依据：top 里 si 占比高、包率大而字节率没打满。

什么时候不该开

需要微秒级确定性的链路（5.3 的 72 µs 非抢占阻塞）；以及路径上有任何一跳不受你控制时——公网上开 Jumbo 只会制造黑洞。

Jumbo 最大的坑是"两端 MTU 不一致"，表现是不对称的静默丢包。A 端设 9000、B 端仍是 1500：A 发的大帧到 B 被当超长帧丢掉，B 发给 A 的小帧却一切正常，于是单向不通、或"能连上但传大文件就断"，而且错误计数长在对端（B 的 rx_length_errors 在涨）。验证三步：ip link show eth0、ping -M do -s 8972、ethtool -S eth0 | grep -iE 'length|over|jabber'。必须逐跳确认——中间交换机的端口 MTU 经常是被漏掉的那一环。

7.1 "头部简化"到底简化了什么

IPv6 头是固定 40 字节，比 IPv4 的最小 20 字节还大一倍——"简化"不是变小，而是变得可预测。这个区别对硬件转发面是决定性的：

IPv4 的设计IPv6 的改动为什么这么改
头长可变，靠 IHL 字段固定 40 字节，选项移到扩展头转发芯片不必先读 IHL 再算偏移，可并行取出关键字段

分片字段在基本头里移到分片扩展头，只有源端能用把例外路径从快速路径里挪走
TTL / Protocol改名 Hop Limit / Next Header后者既可能指上层协议，也可能指下一个扩展头
UDP 校验和可为 0UDP 校验和强制基本头没有校验和了，必须有人兜底
高频面试点：IPv6 上 UDP 校验和是强制的，因为 IP 头不再有校验和。工程后果是隧道封装（VXLAN、GTP-U）在 IPv6 上不能把外层 UDP 校验和置 0 来省 CPU，而这在 IPv4 上是常规优化。RFC 6935/6936 为隧道开了个受限的例外，但要显式满足条件——做隧道开发时这条会直接影响性能测试的结论。
扩展头是"设计很美、部署很痛"的典型。中间设备要判断 L4 端口就必须遍历整条扩展头链，长度不定、可以嵌套，对硬件流水线极不友好。结果是大量运营商与云厂商直接丢弃带扩展头的 IPv6 包（RFC 7872 实测过，丢弃率相当可观）。不要在生产流量上依赖扩展头能穿越公网，把它当受控网络内部才可用的能力。

7.2 NDP 取代 ARP：组播代替广播

报文Request / ReplyNS（Neighbor Solicitation）/ NA（Neighbor Advertisement）

"禁 ICMP"这个 IPv4 时代的安全习惯，搬到 IPv6 上等于自断经脉。IPv6 把三件必需的事都放在 ICMPv6 上：邻居发现、路由器发现、以及 Packet Too Big（PMTUD 的唯一途径，而 IPv6 路由器不分片，所以比 IPv4 更关键）。全禁的结果不是"更安全"，而是IPv6 完全不工作。防火墙策略应按 RFC 4890 写。

"IPv6 明明配好了，业务流量还是全走 IPv4。"根因是 gai.conf 的地址选择策略（RFC 6724）：本机 IPv6 源地址是临时地址而目标只有一条不太优的路由时，策略表把 IPv4 排在了前面。getent ahosts <域名> 直接看解析顺序比在应用里加日志快得多。教训：双栈下"用哪个栈"的决定权在客户端，不在服务端。

把所有机制放回同一个故事

把本篇机制串成一个完整故事——A（192.168.1.10）访问 B（10.0.0.5）：

  1. A 发现 B 不在本网段 → ARP 出默认网关的 MAC，封装帧：目的 IP = B，目的 MAC = 网关；走 VLAN 就打上标签 + PCP。
  2. 交换机按 MAC 把帧送到网关口。

分层自测

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础一个包从 A 走到 B，哪些字段变了、哪些没变？为什么这么设计？

    不变：源/目的 IP（NAT、隧道、Anycast 除外）、端口、载荷。每跳都变：源/目的 MAC、TTL（减 1）、IPv4 头校验和（因为 TTL 变了必须重算）、以太网 CRC。可能变：VLAN 标签（打上/剥掉/改写）、DSCP（信任域边界会重写或清零）。

    设计理由是职责分层：IP 回答"最终送到哪"，是端到端的语义，任何中间设备都无权改动；MAC 回答"这一段交给谁"，是纯局部的、逐跳协商的结果。这种分离让 L2 技术可以随意演进（以太网、PPP、无线）而完全不影响 L3。

    加分点：解释 TTL 为什么存在——它是路由环路的兜底。路由协议收敛过程中难免短暂成环，没有 TTL 的话一个包会永久占用带宽。它同时是 traceroute 的实现原理（故意发 TTL=1,2,3… 的包，收集每跳回的 ICMP Time Exceeded）。另一个加分点是指出校验和覆盖范围的差异：IPv4 头校验和只覆盖头部，所以逐跳重算很便宜；TCP/UDP 校验和覆盖载荷 + 含 IP 地址的伪首部，所以NAT 改 IP 就必须同步修 TCP/UDP 校验和——这是 NAT 真正的工作量。

  2. 基础ARP 的完整过程是什么？跨网段访问时，主机 ARP 的是谁？

    主机要发帧但只知道对方 IP，于是在本链路广播一个 ARP 请求（"谁是 192.168.1.1？"），持有该 IP 的设备单播回复自己的 MAC，结果缓存进邻居表。

    跨网段时 ARP 的是默认网关，不是目标主机。因为 ARP 报文直接跑在以太网上、没有 IP 头，天生无法跨越广播域——所以"问不到"隔壁网段的主机。主机先用目的 IP 与自己的掩码判断目标是否同网段：同网段就 ARP 目标本身，不同网段就 ARP 网关，把帧交给网关去接力。这正是"目的 MAC 逐跳改写"的直接原因。

    加分点一：ARP 请求虽然是广播，收到它的所有主机都会顺便学习"发送方 IP → 发送方 MAC"（RFC 826 允许），因为提问者显然是活着的。这既是免费 ARP 能生效的机制基础，也是 ARP 欺骗成本极低的原因——攻击者不需要等谁来问，直接广播"网关是我"即可。

    加分点二：IPv6 里没有 ARP，对应机制是 NDP（RFC 4861），跑在 ICMPv6 上并且用被请求节点组播而非广播，只打扰少数节点——这对大二层域是实质改进。代价是它依赖 ICMPv6，按 IPv4 习惯"禁掉所有 ICMP"会让 IPv6 直接不通。

  3. 基础VLAN 解决什么问题？802.1Q 那 4 个字节里装了什么？

    解决三件事：① 缩小广播域（抑制广播风暴与 ARP 广播开销）；② 逻辑隔离（不同 VLAN 默认不能直接通信，必须过三层）；③ 摆脱物理位置约束（按业务/租户划分，不用为每个网络单独拉线）。

    4 字节的构成：TPID 16 位（0x8100 表示 802.1Q；QinQ 外层用 0x88A8）+ PCP 3 位（优先级 0–7，衔接 QoS）+ DEI 1 位（可丢弃指示，原 CFI）+ VID 12 位（VLAN ID，理论 4096 个，实际可用 2–4093）。

    加分点一：标签会吃掉 MTU。1500 字节载荷的帧从 1514 变成 1518（QinQ 1522），中转口 MTU 若按 1514 设，满长的带标签帧会被当超长帧丢弃——现象是"小包通、大包不通"。所以承载 VLAN 的中转口至少设到 1504。

    加分点二：VID 只有 12 位是 VXLAN 出现的直接原因（24 位 VNI，约 1670 万），而 QinQ 解决的是"客户 VLAN 与运营商 VLAN 撞号"，不是规模问题。

    加分点三：VLAN 1 不要承载业务——它是各种误配的汇集地，且常有厂商私有控制协议在上面。

  4. 基础MTU、MSS 和分片是什么关系？1500 的 MTU 下为什么常看到 1448 的 TCP 载荷？

    MTU 是链路层能承载的最大载荷（以太网 1500，不含 14 字节以太网头和 4 字节 CRC）。MSS 是 TCP 单个段的最大数据量 = MTU − IP 头 − TCP 头 = 1500 − 20 − 20 = 1460。IP 包超过下一跳 MTU 时就要分片（IPv4 沿途路由器可做，IPv6 只有源端可做）。

    1448 的来源是 TCP 时间戳选项（RFC 7323）：它占 10 字节，加 2 字节对齐 = 12 字节，1460 − 12 = 1448。这个数字很实用——抓包看到 1448 就知道发送方在全速发满长段，明显小于它就要考虑是应用写得碎还是被 MSS 钳制了。IPv6 上对应的值是 1500 − 40 − 20 = 1440。

    加分点：MSS 是两端在握手时各自声明"我最多能收多大"，取双方的较小值，而它反映的是本地接口 MTU——两端都不知道中间那一跳更窄，这正是需要 PMTUD 的原因。另外要点明分片是有害的而不只是"有开销"：n 片中任一片丢失就整包报废，有效丢包率 1−(1−p)ⁿ，p=1% 切 5 片就接近 5%；而且只有首片带端口号，后续片让防火墙、ECMP 哈希、负载均衡全部失效，很多设备干脆丢弃非首片。

9.2 中级（区分熟练度）

  1. 中级什么是最长前缀匹配？RIB 和 FIB 有什么区别，排障时该看哪个？

    最长前缀匹配：多条路由都覆盖目的 IP 时，选掩码位数最多、覆盖范围最小的那条。10.1.2.0/24 会击败 10.1.0.0/16、10.0.0.0/8 和默认路由 0.0.0.0/0。它与"路由优先级/管理距离"是两个层次：LPM 先决定哪些条目可比，同前缀长度之间才轮到优先级和度量值。

    非常实用的推论：要临时引走一小段流量，不必删任何现有路由，加一条更长的前缀即可（/32 一定赢）。反过来这也是"配了默认路由但流量不走它"的答案——一定有更长的前缀先命中。

    RIB（Routing Information Base）在控制面，保存各协议学到的全部候选路由，带协议来源、AS 路径、度量值；BGP 抖动时每秒可能变更数千次。FIB（Forwarding Information Base）在转发面，只留选路后胜出的那一条，结构为查找速度优化，数据包每包查一次、从不碰 RIB。

    排障对应：问"为什么这条路由没被选中"看 RIB（show ip route）；问"这个包实际会往哪走"看 FIB，而且不要自己肉眼比对掩码，直接 ip route get <目的IP> 让内核给结论。

    加分点：硬件 FIB 容量是一个会突然爆的墙。接入/汇聚设备的转发表往往只有几万到十几万条前缀，BGP 全表增长越过这条线时，设备不报错，而是把溢出前缀退回 CPU 软转发——那部分流量从线速掉到每秒几万包，同时 CPU 打满、路由协议超时、引发全局震荡。特征是"只有部分目的地址慢/丢包，而且越来越糟"，所以 TCAM 使用率应该纳入常规巡检。

  2. 中级Linux 邻居表有哪些状态？看到一屏 STALE 要不要处理？gc_thresh 是什么？

    六个状态：INCOMPLETE（已发请求未收回复，报文排队等待）→ REACHABLE（近期确认可达）→ STALE（条目还在但可达性已过期）→ DELAY（等一小会儿看上层有无隐式确认）→ PROBE（正在单播探测）→ FAILED（探测无响应）。

    STALE 不需要处理，它是正常状态。Linux 的设计意图是只在有流量时才验证可达性——静默的邻居不值得花广播去探测，所以 STALE 条目会被照常使用、不阻塞转发，只有真有流量时才转入 DELAY 去确认。而 DELAY 阶段如果上层（比如 TCP 的 ACK）能证明对端活着，就直接回到 REACHABLE，连探测都省了。真正需要警觉的是 INCOMPLETE（对端没响应：不在线、ARP 被挡、或 VLAN 配错导致根本不在一个广播域）和 FAILED。

    gc_thresh1/2/3 是邻居表的垃圾回收阈值，默认 128 / 512 / 1024：低于 1 完全不回收；超过 2 在 5 秒后开始激进回收；超过 3 就直接拒绝创建新条目。

    加分点（这是本题真正的区分度）：描述 gc_thresh3 溢出的故障形态——大二层域里邻居数超过 1024 时，症状是随机、短暂、无规律的丢包，不针对特定目标、也没有时间规律，重启后好一阵又复发，从业务侧几乎无法定位。决定性证据只有 dmesg 里的 neighbour: arp_cache: neighbor table overflow。应急是把阈值提到邻居数的 2 倍以上，但真正的解法是拆小二层域——上千台设备挤一个广播域，ARP 广播本身就是可观的固定开销。

  3. 中级DSCP 和 PCP 是什么关系？为什么应用里设了 EF 却依然不优先？

    DSCP 是 IP 头 TOS 字节的高 6 位（低 2 位归 ECN），三层端到端有效；PCP 是 802.1Q 标签里的 3 位，只在带标签的二层链路上有效。两者是同一个意图在不同层的表达，DSCP → PCP 是多对一的有损压缩（6 位压到 3 位，默认取高 3 位），比如 AF41/AF42/AF43 高 3 位相同，压到 PCP 后三档丢弃优先级的信息就丢了。

    "设了 EF 却不优先"最常见的原因是：出主机第一跳就被清零了。DSCP 本质是信任问题而不是配置问题——任何人都能在自己的包上写 46，所以每个网络在信任域边界必须做决策：信任对方标记（trust dscp），还是按自己的策略重新分类打标（remark）。默认几乎都是不信任、清零。验证方法很直接：在链路两端同时抓包，比对 IP 头的 TOS 字节（tcpdump -v 里的 tos 0xb8 就是 DSCP 46；看到 tos 0x0 说明被清了）。

    其它可能原因：② 出接口根本没配多队列调度，标记了也只有一个队列；③ 瓶颈不在你标记的这一跳（QoS 只在拥塞点生效，不拥塞时标记完全无效果——这也解释了"压测时才看得出差别"）；④ 跨 L2/L3 边界时映射表两侧不一致。

    加分点：EF 必须配限速，这不是可选项。EF 语义是"你先走"，若不限制它的带宽占比（常见做法是不超过链路的 30%–50%），EF 流量一旦超过链路容量就会把其它队列全部饿死，包括路由协议和管理面——后果是设备"业务还在跑但完全失联"，连改配置救回来都做不到。严格优先级队列一定要成对配置：优先级 + 上限。

  4. 中级什么是 PMTUD 黑洞？怎么确认、怎么处置？为什么它常表现为"HTTP 能开、HTTPS 打不开"？

    PMTUD 的机制是给包打 DF 标志，路径上装不下的那一跳丢弃它并回 ICMP "Fragmentation Needed"（IPv4 Type 3 Code 4 / IPv6 Packet Too Big），报文里带下一跳 MTU，发送方据此调小。黑洞就是这个 ICMP 回不来（几乎总是因为有人"为了安全"把 ICMP 全禁了）——发送方永远不知道要调小，大包永远发不出去。

    症状组合非常有辨识度：① TCP 三次握手成功（SYN 只有几十字节）；② 小请求正常，大数据一发就卡死然后超时；③ ping 正常（默认 56 字节载荷）但 ping -M do -s 1472 不通；④ HTTP 能开、HTTPS 打不开——因为 TLS 握手要传证书链，那往往正好是几 KB 的大包，而 HTTP 的小请求不受影响。

    确认：ping -M do -s N 二分找出真实路径 MTU；ip route get <IP> 看有没有学到 mtu（学到了说明 PMTUD 正常，黑洞的特征恰恰是这里什么都没有）；nstat -az | grep -i icmp 看 IcmpInDestUnreachs 是否长期为 0。

    处置：① 应急在路由上钉死 ip route change … mtu 1400；② 通用做法是在网关/隧道口做 MSS 钳制（iptables -t mangle … TCPMSS --clamp-mss-to-pmtu），改写经过的 TCP SYN 里的 MSS，让两端一开始就不发大包，从而完全不依赖 ICMP；③ 根治是放行 ICMP Type 3 Code 4 与 ICMPv6 Type 2。

    加分点：MSS 钳制救不了 UDP——它靠改写 TCP SYN 生效，而 UDP 没有握手也没有 MSS。所以 QUIC、GTP-U、eCPRI、DNS over UDP 必须自己处理路径 MTU：要么保守取值（QUIC 要求初始至少支持 1200 字节载荷），要么实现 PLPMTUD（RFC 8899）在传输层自己用探测包试出来。这正是现代协议都在自己做 MTU 探测的原因。另外指出 IPv6 下这件事更严重：路由器根本不分片，PMTUD 不是优化而是必需品。

9.3 高级（体现深度）

  1. 高级什么是 bufferbloat？为什么缓冲区大反而害人？AQM 怎么解决它，CoDel 的关键设计是什么？

    bufferbloat：设备配了远超需要的缓冲区，于是拥塞时包不被丢弃、而是排在队里等。吞吐没掉，但排队时延暴涨到几百毫秒甚至几秒。对交互业务这比丢包糟得多——丢包可以重传，时延无法追回。这也是它长期没被发现的原因：所有吞吐类指标都是正常的。

    为什么大缓冲区有害：基于丢包的拥塞控制只认丢包一个信号，发送方会持续加速直到队列溢出才退让。缓冲区越大，"发现拥塞"就被推迟得越久，稳态下队列一直接近满。把队列长度换算成时间就很直观：一个 128 包的 FIFO 在 1 Gbps 上只有 1.5 ms，在 1 Mbps 上是 1.5 秒——同一个"合理"的队列长度在不同速率下时延差 1000 倍。结论：队列长度不能按包数配，要按时间配。

    AQM 的思路是不等溢出，提前、少量地丢包或打 ECN 标记，主动把拥塞信号送回发送方，从而把队列压在很短的长度上。三代演进：Tail Drop（满了才丢，还会造成全局同步——多条流同时被丢、一起退让又一起加速）→ RED（1993，按平均队列长度概率丢，打散了同步但参数极难调，这是它部署率低的直接原因）→ CoDel（RFC 8289）→ FQ-CoDel（RFC 8290，先按流哈希分上千个子队列，各跑一份 CoDel，实现流间隔离，一条大下载再也压不住语音流）。

    CoDel 的关键设计，也是本题最能体现深度的一点：它测的是包在队列里的驻留时间，而不是队列长度。RED 难调正是因为"多长的队列算太长"没有普适答案——取决于速率、流数、包长分布；而"包在队里等了多久算太久"有普适答案：5 ms，对任何速率都成立。把控制变量从一个依赖环境的量（长度）换成不依赖环境的量（时间），参数就自然消失了。CoDel 还能区分"good queue"（短暂突发，正常）与"bad queue"（持续积压，要干预），只有持续超过 target 才开始丢。

    怎么在 Linux 上确认：tc -s qdisc show dev eth0 看 backlog，用 backlog字节 / 链路速率 换算成毫秒——持续几十毫秒就是 bufferbloat。drop_overlimit 非零说明撞到队列上限、AQM 来不及生效。处置：换成 fq_codel 或 cake，且整形速率要略低于真实链路速率，否则瓶颈仍在运营商侧那个你管不到的队列上，本地 AQM 完全失效。真实效果：10 Mbps 上行线路从 pfifo_fast 换成 cake bandwidth 9.5Mbit，上传期间的 ping 从 1400 ms 回到 12 ms，吞吐只降 2%。

  2. 高级严格优先级和 DWRR 各适合什么？高优先级队列的最坏时延怎么算？这和 TSN 有什么关系？

    严格优先级（SP）：高优先级队列非空就先发它。优点是高优先级的时延最小且可计算；缺点是会饿死低优先级，所以必须成对配"优先级 + 带宽上限"。适合语音、同步、eCPRI 用户面这类"时延预算硬"的流量。

    DWRR（差额加权轮转）：每轮给每个队列一个字节配额，用不完累积到下一轮。它相对 WRR 的关键改进是按字节而不是按包数公平——WRR 按包轮转会让大包流量实际拿到更多带宽。DWRR 是 O(1) 的、硬件友好，是设备上的主流选择。适合需要按比例分配带宽、又不能饿死任何一类的场景。

    实际设备上的标准做法是混合：一两个 SP 队列（同步、语音）+ 其余走 DWRR。

    最坏时延的计算（这是本题的核心）：最坏出口时延 ≈ 非抢占阻塞 + 同优先级排队。

    • 非抢占阻塞 = 最大帧长 / 链路速率。以太网不能中断一个正在发送的帧，所以哪怕你是最高优先级，也得等当前那个低优先级帧发完。1500 B 帧在 1 Gbps 上是 12 µs，在 10 Gbps 上是 1.2 µs；9000 B 的 Jumbo 帧在 1 Gbps 上是 72 µs。
    • 同优先级排队 = 前面 k 个同优先级包的发送时间之和。
    • 每一跳都要加一次这两项，20 跳的累积抖动就是单跳的 20 倍。

    这段计算直接支撑两个工程决策：① Jumbo Frame 不是免费的——它把 1 Gbps 上的非抢占阻塞从 12 µs 抬到 72 µs，所以需要微秒级确定性的前传/TSN/工业网络往往宁可放弃 Jumbo，或靠提高线速把阻塞压回去。② 这正是 TSN 里"帧抢占"（802.1Qbu / 802.3br）存在的理由：它允许把正在发送的低优先级帧切断，让高优先级帧插进去，从而直接消掉非抢占阻塞这一项。TSN 的其它工具（802.1Qbv 时间感知整形、802.1Qav 信用整形）同样是在攻击这个时延界的不同项。

    加分点：指出 QoS 只在拥塞点生效。不拥塞时所有队列都是空的，调度算法无从发挥——这解释了为什么 QoS 配置的效果"只有压测时才看得出来"，也解释了为什么排障要先用 tc -s qdisc 的 backlog 找到真正的瓶颈口，而不是在每个接口上都堆一套 QoS。

  3. 高级ECN 是怎么做到"不丢包也能通知拥塞"的？为什么标准化二十多年了还没成为默认？

    机制：IP 头 TOS 字节的低 2 位是 ECN 字段，四种取值——00 Not-ECT（不支持，只能丢包）、10 ECT(0) 与 01 ECT(1)（支持，请用标记代替丢包）、11 CE（Congestion Experienced，路径上某个队列把它标成"我拥塞了"）。

    关键在于标记方与感知方是分开的：中间设备只把 ECT 改写成 CE，它不认识也不需要认识传输层。信号必须由接收端反馈给发送端——TCP 用头里的 ECE（回声）与 CWR（已减窗，确认收到回声）完成这一回合，发送方随后像遇到丢包一样降速，但没有任何一个包真的丢了。收益对短连接尤其明显：一个只有几个包的请求丢一个，可能要等一次超时才恢复。

    为什么部署不了——问题全在路径中间，而且三种破坏方式的危害程度不同：

    • 最致命的：早期有防火墙/负载均衡看到 TCP SYN 里的 ECN 协商位就直接丢弃该 SYN，导致开了 ECN 的主机连不上某些站点。故障表现是"完全打不开"而不是"慢一点"，代价高到没人敢默认开启——这正是 Linux net.ipv4.tcp_ecn 默认取 2（只被动接受，不主动发起）的由来。
    • 有设备无条件把整个 TOS 字节清零（顺手把 DSCP 也清了），ECN 信号无声消失，退回丢包信号——只是失去收益，不至于坏事。
    • 最危险的：只清 CE 不清 ECT。拥塞信号被吞掉，而两端都以为 ECN 在正常工作、不再期待丢包信号，结果比不开 ECN 更糟。

    但在可控网络里结论完全相反：数据中心内部（DCTCP）和运营商自管的承载网上，路径上每台设备都是自己的，ECN 非常值得开——它把拥塞控制的信号从"事后丢包"变成"事前提示"，队列时延与重传率能同时下降。配置上要两侧都到位：端点 tcp_ecn=1，瓶颈处的 AQM 加 ecn 选项（tc … fq_codel ecn），然后用 tc -s qdisc 里的 ecn_mark 计数器验证标记真的在发生。

    加分点：提 L4S（RFC 9330 系列）——它用 ECT(1) 承载更高频的拥塞信号，目标是把公网排队时延压到毫秒级，是 bufferbloat 问题在标准层面的最新回应，但部署仍在早期。

  4. 高级综合题：一条链路"业务时延忽高忽低、偶发丢包"，给你 root 权限，你怎么定位？

    先说方法论，再说命令——面试官考的是有没有结构，而不是记住多少工具。核心是连续做二分：本地 / 远端 → 控制面 / 数据面 → 通不通 / 通但质量差。不做二分而直接抓包是效率最低的做法：一屏包看不出"本该有什么却没有"，二分法才能告诉你去哪一段抓。

    第一步：把"不通"和"质量差"分开。本题症状是"偶发"，属于质量问题，所以不要一头扎进路由配置。先量化：ping -i 0.2 -c 500 或 mtr 跑一段，看时延分布和丢包集中在哪一跳。注意 traceroute/mtr 的经典误判：中间某跳全是 * 或时延很高，往往只是那台设备不回/限速 ICMP，转发本身完全正常；判据是"后面的跳是否正常回应"。

    第二步：先排除自己这一端（最便宜，且最常中）：

    • ethtool eth0 看 Speed/Duplex——协商成半双工或降速会让性能莫名极差；ethtool -S eth0 看 rx_crc_errors（线路/光模块问题）、rx_length_errors（MTU 不一致）、rx_missed/over_errors（收不过来）。
    • ip -s link、nstat -az | grep -vE ' 0 +0.0$'——只看非零计数器，重点是 *Drop*、*Error*、InMartianSrc（rp_filter 在丢包）、Frag*。
    • dmesg——找 neighbor table overflow（邻居表溢出会造成正是本题这种"随机、无规律"的丢包）。
    • top 看 si（软中断）占比、cat /proc/interrupts 看中断是否都压在一个核上。

    第三步：判断是不是排队问题（"时延忽高忽低"的最高频原因）：tc -s qdisc show dev eth0，看 backlog 并换算成毫秒；drop_overlimit 非零说明撞到队列上限。同时做一个决定性的对照实验：空闲时 ping 和满载时 ping 的差值——如果空闲 8 ms、满载 800 ms，那就是 bufferbloat，与丢包、路由、对端都无关，换 fq_codel/cake 即可。

    第四步：排除 MTU 这条静默通道。症状里若含"小包正常、大包异常"就直接怀疑它：ping -M do -s 1472 二分；ip route get 看有没有学到 mtu；确认路径上的 VLAN/隧道开销与两端 MTU 是否一致。

    第五步：检查 QoS 是否真的生效。两端同时抓包比对 TOS 字节是否被清零；确认瓶颈口是否真的配了多队列调度。注意 QoS 只在拥塞时才有效果，所以要在加压状态下验证。

    第六步：路径的稳定性。"忽高忽低"也可能是路由在两条不等长路径间抖动，或 ECMP 把一条大流和其它流哈希到了同一条链路（fib_multipath_hash_policy；隧道流量因为外层五元组相同而熵不足，是个高频陷阱）。mtr 长跑能看出路径变化。

    最后一条，也是最重要的一条纪律：不要抄 sysctl 大礼包。网上那一长串调优参数是别人在别人的负载和内核版本上试出来的，照抄的典型后果是把 rmem/wmem 一律拉大、制造出主机侧自己的 bufferbloat，或覆盖掉发行版默认的 fq_codel 退回 pfifo_fast、反而让时延变差。正确顺序永远是：先测量 → 定位到具体瓶颈 → 只改一个参数 → 复测。改完没有复测数据的调优等于没做。
