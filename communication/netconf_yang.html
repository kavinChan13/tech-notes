NETCONF / YANG：网络设备如何被配置和管理

管理面的主角来了。O-RAN 的 O1 接口和前传 M 平面都用 NETCONF/YANG——它俩到底谁干什么？这一篇讲建模语言与协议本身：YANG 的类型系统、数据树、约束与版本演进，以及 NETCONF 的四层分层与操作语义。YANG 定义"数据长什么样"，NETCONF 定义"怎么操作和传输这些数据"。工程落地在 NETCONF 工程实践。

01

先讲清一件事

NETCONF 和 YANG 的分工

🍽 生活类比：餐厅点菜

YANG = 菜单的"格式规范"：规定菜单该有哪些字段（菜名、规格、可选配料、价格范围、哪些是必选）。NETCONF = 你和服务员的"交互协议"：怎么点菜（下单）、怎么查看当前订单、怎么改单、怎么确认。菜单定义结构（YANG），点菜流程操作数据（NETCONF）。

YANG：数据建模语言——定义设备的配置/状态数据有哪些字段、层级、类型、约束。
NETCONF：网络管理协议——定义如何获取、修改、提交、传输这些数据（一套基于 XML 的 RPC）。

这两个名字几乎总是连在一起出现（"O1 用 NETCONF/YANG"、"M 平面用 NETCONF/YANG"），久而久之很多人把它当成一个东西的两半，甚至以为 YANG 是 NETCONF 的某种"配置文件格式"。它们其实处在完全不同的时间轴上：YANG 属于设计期，厂商在设备出厂前就把模型写好、编译好、发布出去；NETCONF 属于运行期，真正跑在 TCP 连接上搬运数据的是它。你拿到 .yang 文件时设备还没上电，你抓到 <rpc> 报文时模型早就固化在两端了。

三条判据，看一眼就能分清

你看到的东西它属于理由
container / list / leaf / type uint16YANG这是模型语言的关键字，描述"字段与约束"，本身不是数据
<rpc> / <rpc-reply> / <edit-config> / <commit>NETCONF协议自己的操作词汇，定义在 urn:ietf:params:xml:ns:netconf:base:1.0 命名空间里
<interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">两者的交界XML 的骨架由 NETCONF 定义，装在 <config> 里的这一坨由 YANG 定义；命名空间就是分界线

最后一行是这一篇最值得记住的一句：一个 NETCONF 报文里其实混着两套命名空间，分界线就在 <config> 这一层（§3.8 有图）。调试时先分清「报错发生在哪一层」能省掉一半时间——外层报错是协议用错了，内层报错是模型用错了。

两者并不互相绑死

  • 同一份 YANG 模型可以被多种协议承载：NETCONF 用 XML，RESTCONF 用 JSON 或 XML，gNMI 用 protobuf。换协议不用换模型——这正是"把数据模型独立出来"的最大红利。
  • NETCONF 理论上不强制用 YANG：最早的 NETCONF（RFC 4741，2006）发布时 YANG 还不存在。但今天没有任何一个严肃实现不用 YANG——没有 schema 就没有类型检查、没有代码生成、没有跨厂商一致性，NETCONF 会退化成"用 XML 包起来的私有 CLI"。
本篇的边界。这里讲建模语言与协议本身：YANG 的类型系统、数据树、约束、版本演进，以及 NETCONF 的分层与操作语义。工程落地（SSH/TLS 怎么配、事务与失败处理、大规模下发、libnetconf2、O-RAN O1 与 Call Home）在 NETCONF 工程实践；横向取舍（SNMP / RESTCONF / gNMI）在 管理协议对比；SSH / TLS 的原理在 TLS / SSH / 证书。
02

为什么需要 YANG

从 SNMP/CLI 的痛点说起

在 YANG 之前，网络设备管理有两大老办法，各有硬伤：CLI 对人友好，但机器难解析、各厂商语法不同、无标准结构；SNMP + MIB 有结构，但擅长"读监控"而不擅长"复杂配置"，事务性弱、写操作差。

YANG 让"配置"从"一堆命令字符串"变成一棵有类型、有约束、可校验的结构化数据树。厂商用 YANG 发布自己设备的模型，管理系统据此自动生成与校验配置——这是网络可编程化的地基。

把痛点落到一个具体任务上

抽象地说"CLI 不好自动化"没有说服力。换成一个具体任务：给 200 个接口把 MTU 从 1500 改成 9000，要么全成、要么全不成，改完能验证。三种方式的差别立刻就出来了：

环节CLI + expect 脚本SNMP SETNETCONF + YANG
怎么表达"eth3 的 MTU"一串命令文本，各厂商语法不同一个 OID + 索引（ifMtu.3）/interfaces/interface[name='eth3']/mtu，跨厂商一致
非法值怎么办回一行报错，脚本靠正则猜返回 wrongValue，不告诉你合法范围模型里写着 range "68..9000"，客户端本地就能拦下
200 条改动的原子性没有。第 137 条失败时前 136 条已生效只有单个 PDU 内原子，跨 PDU 无事务candidate → validate → commit，一次原子提交
失败怎么回滚自己写反向脚本，它本身也可能失败自己记录旧值再 SET 回去discard-changes 或 rollback-on-error
改完怎么确认再 show 一遍，解析文本再 GET 一遍get-config 拿回结构化数据，可直接做树比对
换个厂商的设备脚本基本重写私有 MIB 部分要重写标准模型部分不动，只处理 deviation 差异

生活类比：报销。CLI 像手写便条交给财务：每人格式都不一样，交上去也没法撤回。SNMP MIB 像按编号排的电话簿：查号很快，但没法用它"下单"，更没法"下十单再一起确认"。YANG + NETCONF 像带校验规则的在线报销系统：字段类型是死的、必填漏了当场提示、可以先存草稿、提交是一次性的、驳回整单退回不会只退一半。

这些需求不是 IETF 拍脑袋想的

NETCONF 与 YANG 的需求清单来自运营商本人：IAB 在 2002 年办过一次网络管理研讨会，会后的 RFC 3535 把运营商实际抱怨的问题整理成需求列表，其中四条直接长成了后来的语言特性——配置与状态必须能分开（→ config true/false）、要有配置事务（→ candidate / commit）、配置要能整体导出与恢复（→ <copy-config>）、要区分「谁下发的」与「设备实际在跑的」（这一条拖了十几年才由 NMDA 补上，见 §6.5）。

"为什么不用 SNMP 做配置"，答"写操作弱"只能拿基础分。三个结构性缺陷才是根因：① 没有事务边界——SNMP 的原子性只覆盖单个 PDU 内的变量绑定列表，一次大配置必然拆成多个 PDU，中途失败就是半套配置；② 没有配置/状态之分——MIB 里 ifMtu（可写）和 ifInOctets（只读计数）平级摆着，"备份配置"无从下手；③ SMIv2 的类型系统太弱——表达不了"这个字段只在另一个字段为 true 时才有意义"（YANG 的 when）或"这两个值不能同时配"（must），约束只能写在 DESCRIPTION 的自然语言里，机器读不了。"UDP 不适合大配置"只是表象。横向对比见 管理协议对比。
03

YANG：数据建模语言

看一个真实的 YANG 片段

YANG 用 container / list / leaf / leaf-list 把数据组织成一棵树，并给每个字段定类型和约束。它的形态更像一门 IDL 而不是配置文件格式：有类型系统、有命名空间、有 import、有版本、有可复用的片段，甚至有基于 XPath 的跨字段约束。

模块的六类组成，与一份最小可用的模块

一份 .yang 文件里的语句按作用分成六类。分清这六类，读任何厂商模块都不会迷路——因为只有其中一类会真正变成线上报文：

下面是一份麻雀虽小的完整模块，只有模块头 + 数据树两部分，但已足够被设备加载、被客户端编译成代码：

module example-interfaces {
  yang-version 1.1;                                              // 不写默认是 1.0
  namespace "urn:example:params:xml:ns:yang:example-interfaces"; // 全球唯一，报文里的 xmlns
  prefix exif;                                                   // 短前缀，本模块内与被引用时用

  import ietf-yang-types { prefix yang; }   // 用别人的类型必须先 import（RFC 6991）
  revision 2026-03-01 { description "首版。"; }

  container interfaces {          // 非 presence 容器：只是分组，本身不携带信息
    list interface {
      key "name";                 // 主键：隐式 mandatory，且在整个 list 里必须唯一

      leaf name { type string { pattern "[a-zA-Z][a-zA-Z0-9./-]*"; } }
      leaf type {
        type enumeration { enum ethernet; enum loopback; }
        mandatory true;           // 必填。与 default 互斥，同时写编译器直接报错
      }
      leaf mtu { type uint16 { range "68..9216"; } units "bytes"; default 1500; }

      leaf oper-status {          // config false：状态数据，get 看得到、get-config 看不到
        config false;
        type enumeration { enum up; enum down; }
      }
      container statistics {
        config false;
        leaf in-octets { type yang:counter64; }   // 前缀 yang 来自上面的 import
      }
    }
  }
}

为什么 list 一定要有 key，从这张图就能看出来：没有主键，"改第二个接口的 MTU"这句话在协议里根本无法表达，你只能整表覆盖。这也解释了另一条规则：config false 的 list 可以没有 key，config true 的必须有。

不要用会变的字段做 key（比如用 IP 地址而不是接口名）。改一次 key 在协议语义上等于"删掉旧的一行、加进新的一行"，这一行下面挂的整棵子树会跟着被清掉——统计、子接口、ACL 绑定，全没了。
拿到一份陌生模块别从第一行读起。pyang -f tree foo.yang 直接把它打印成一棵树，一眼看到的就是上图第 4 类——数据树的形状，也就是你真正要下发的东西；碰到不认识的类型名再回头翻 typedef。

节点四件套：container / list / leaf / leaf-list

选哪个节点类型只有两个问题：装的是一个值还是一棵子树？只有一个还是可以有多个？两两组合正好四种：

语句相当于关键点常见误用
container结构体 / 目录默认非 presence：存在与否不携带信息。加 presence "..." 才变成"存在本身就是配置"（如 <dhcp-relay/> 表示开启中继）把开关做成非 presence 容器——客户端删不掉它，因为它本来就不算数据
list数据库表config true 时必须有 key；可加 unique、min-elements / max-elements、ordered-by user|system用一个会变的字段做 key（见上面那条 tip）
leaf字段必须有 type；可有 default、mandatory、unitsmandatory true 又写 default——两者互斥，编译器直接报错
leaf-list数组同类型多个值。1.1 起允许 default（可给多个）需要"每项带多个属性"时还硬用它——那应该是 list
choice / casetagged union本身不出现在数据里；设置另一个 case 的节点会自动删掉当前 case 的全部节点以为 choice 会在 XML 里生成一层元素——不会，它是纯 schema 概念
anydata / anyxmlany装"结构未知"的数据。anydata（1.1）要求内容仍是合法 YANG 数据树，anyxml 是任意 XML拿它当逃生舱口塞私有配置——等于放弃 YANG 的全部好处

类型系统：内置类型、typedef、以及三种"引用型"类型

13 类内置类型加四种约束语句，绝大多数字段都能表达得很精确，而"精确"换来的好处很具体：客户端拿到模型就能在本地把非法值拦下来，不用发到设备再等报错。类型的演化方向永远是收窄：

内置类型可加的约束说明与工程注意
int8/16/32/64、uint8/16/32/64rangerange 支持多段与 min/max：range "1..4094 | 4096..8191"
decimal64fraction-digits（必填 1–18）、range定点数不是浮点。用它表达功率、经纬度，避免二进制浮点的舍入争议
stringlength、pattern（可多条，取交集）pattern 用的是 W3C XSD 正则，不是 POSIX ERE——默认整串锚定，写 ^...$ 反而当字面量匹配
boolean / binary后者可加 lengthboolean 在 XML 里是文本、JSON 里是原生布尔；binary 两边都是 base64（证书、密钥走它）
enumerationenum（可指定 value）封闭集合，加一个新枚举值就是不兼容变更
bitsbit（可指定 position）位标志集合。线上表示是空格分隔的名字，不是数字
empty—没有值，存在与否就是全部信息。不能有 default，也不能进 leaf-list
union多个成员类型按声明顺序逐个匹配，第一个匹配上的胜出——把 string 放第一位会吃掉后面所有类型
leafrefpath（必填）、require-instance外键。默认 require-instance true：指向不存在的实例会校验失败
identityrefbase指向一个 identity。可扩展的枚举，见下图
instance-identifierrequire-instance指向数据树某节点的 XPath 字符串，常用于告警里指明"哪个对象出的问题"

IETF 的 ietf-interfaces 把接口类型做成 identityref 而不是枚举，正是为了这一点——厂商能自己派生 my-vendor:custom-tunnel，而不用等 IETF 改标准。反过来，在自己的模块里给一个已发布的 enumeration 加值，是最容易被忽略的不兼容变更：编译能过、revision 检查能过，只有老客户端在运行时解码到那个新值时才炸。

约束：must / when / mandatory / default / config

能把约束写进模型、交给机器去查，是 YANG 相对别的建模语言最实用的一处优势（SMIv2 只能把约束写在 DESCRIPTION 的自然语言里）。全部约束语句凑起来也就这么长：

typedef mtu-size {                     // ① 派生类型：约束 + 单位 + 默认值集中一处
  type uint16 { range "68..9216"; }    //    range 支持多段："1..4094 | 4096..8191"
  units "bytes";
  default 1500;
}

leaf name {
  type string {
    length  "1..63";
    pattern "[a-zA-Z][a-zA-Z0-9./-]*";  // ② W3C XSD 正则，不是 POSIX ERE
  }                                     //    默认整串锚定，写 ^…$ 反而当字面量匹配
}

leaf vlan-id {
  when "../type = 'ethernet'";         // ③ 条件为假 → 这个节点在数据树里【根本不存在】
  type uint16 { range "1..4094"; }
}

leaf parent-interface {
  type leafref { path "../../interface/name"; }  // ④ 外键，默认 require-instance true
}

must "not(vlan-id) or mtu <= /exif:interfaces/exif:interface"
   + "[exif:name = current()/exif:parent-interface]/exif:mtu" {
  error-message "VLAN 子接口的 MTU 不能大于父接口的 MTU。";  // ⑤ 违反 → commit 被打回
}

这五个语句加上 mandatory / config 最容易被混为一谈，但它们回答的是四个完全不同的问题：

语句回答的问题什么时候求值违反时的后果
when "XPath"这个节点存不存在？随时。条件为假时，该节点连同子树在数据树里根本不存在不算"违反"——服务器会自动删掉这个子树，不报错
must "XPath"这份数据合不合法？<validate> 与 <commit> 时（整棵树）返回 <rpc-error>，error-app-tag 默认是 must-violation，可用 error-message 自定义提示
mandatory true这个节点必须被填吗？校验时缺了就报 missing-element
default X没填的时候按什么算？读取与校验时不会报错。注意默认值不一定出现在 get-config 的回复里（见 with-defaults）
config false这是配置还是状态？编译期往 config false 节点写数据会被拒（invalid-value 或 unknown-element）

其中 when 与 must 的差别最值得记，也是现场最常见的"配了但没生效"来源。区别不在写法，而在求值时机与失败方式：

还有一条 config 的硬规则容易被忽略：config false 节点的所有子孙自动也是 config false，翻不回 true——配置树不可能长在状态树下面。

复用与扩展：grouping / uses / augment / deviation

这四个语句解决"别重复写"和"别改别人的模块"两件事，但作用方向不同：

写在哪作用典型场景
grouping + uses自己的模块里（也可跨模块 uses 别人的）把一组节点定义一次、在多处原地展开。uses 内可 refine 微调，也可 augment 往展开结果里加节点地址族配置、认证参数这类在多处长得一样的字段块
augment自己的模块里，往别人的树上挂「我给标准模型加东西」。挂上去的节点属于你自己的命名空间，可带 when 条件挂载厂商在 ietf-interfaces 下加私有的 storm-control
deviation单独的 deviation 模块里「我这台设备做不到标准模型的这部分」。四种 deviate，见下图设备 MTU 只到 1500，就把 range 收紧
feature + if-feature模块里定义，设备在运行时声明支持哪些「这块内容可选，看设备支不支持」。不支持时相关节点整体不存在同一份标准模型覆盖高低端两条产品线

剩下两个最容易混：augment 是模型作者的加法，deviation 是设备实现者的减法（或修正）。前者会进数据树、客户端可正常读写；后者唯一的目的是诚实地告诉客户端「标准模型的这部分我对不上」。

// ① augment：厂商往 IETF 标准接口模型上挂私有节点
module vendor-if-ext {
  yang-version 1.1;
  namespace "urn:vendor:if-ext";
  prefix vext;
  import ietf-interfaces { prefix if; }
  import iana-if-type    { prefix ianaift; }   // 用到别人的前缀就必须 import

  augment "/if:interfaces/if:interface" {
    when "if:type = 'ianaift:ethernetCsmacd'";   // 只挂在以太口上
    container storm-control {
      leaf broadcast-pps { type uint32; }
      leaf multicast-pps { type uint32; }
    }
  }
}

// ② deviation：这台设备的实际能力与标准模型的差异，单独一个模块
module vendor-if-deviations {
  …模块头同上，import ietf-interfaces { prefix if; }…

  deviation "/if:interfaces/if:interface/if:link-up-down-trap-enable" {
    deviate not-supported;                                // 我没实现，别下发
  }
  deviation "/if:interfaces/if:interface/if:description" {
    deviate replace { type string { length "0..63"; } }   // 标准允许更长，我只到 63
  }
  deviation "/if:interfaces/if:interface/if:enabled" {
    deviate add { must "../if:type != 'ianaift:softwareLoopback' or . = 'true'"; }
  }
}
真实案例形态：照着 IETF 官网的 ietf-interfaces.yang 写代码，上设备就 unknown-element。根因几乎总是三选一：revision 与你手上那份不同、节点被 deviate not-supported 掉了、或相关 feature 没开。正确做法是把设备当成模型的唯一真相来源——用 <get-schema>（RFC 6022）把模块正文拉下来编译客户端。排查路径见 工程实践 §7.4。

module / submodule 与 revision：版本怎么演进

一个模块大到几千行时会拆成 submodule，它和 import 完全不是一回事：import 引用另一个模块，对方有自己的 namespace，引用时必须带前缀（inet:ipv4-address）——这是"跨模块协作"；include + submodule + belongs-to 则是把同一个模块拆到多个文件里，submodule 没有自己的 namespace 和 prefix，借用主模块的，编译后等价于把内容原地粘回去——这是"单纯的文件切分"。

版本演进的规则（RFC 7950 第 11 节）比想象中严格，核心思想只有一句：同一个模块名 + 同一个 namespace 的所有 revision，必须能让老客户端继续工作。要判断某个改动兼不兼容，不必背清单——只看值空间朝哪个方向变：

对照封装思想：NETCONF over SSH over TCP over IP over Ethernet——这与 eCPRI 的"薄封装、直接 over 以太网"形成鲜明对比。管理面要可靠、安全、有事务，每层开销都值；前传要确定性低时延，所以连 IP 层都省了。「时延预算决定协议栈厚度」这条判据在 O-RAN 的九个接口上一路适用（见 O-RAN 接口）。

SSH / TLS 给的是一条字节流，NETCONF 要在上面切出一条条独立的 XML 消息——和 TCP 上跑任何应用协议遇到的粘包/半包是同一回事。前后用过两套方案：base:1.0 的 end-of-message（RFC 6242 §4.1，消息尾部追加 6 字节的 ]]>]]>）和 base:1.1 的 chunked（§4.2，\n#<字节数>\n<数据> 重复若干次，以 \n##\n 结束）。字节级对照图见 工程实践 §1.3。

实现者踩得最多的一个坑：<hello> 本身永远用 ]]>]]> 分帧。因为分帧方式是靠 hello 协商出来的，协商完成之前双方还不知道该用哪种，所以 RFC 6242 规定 hello 固定用 end-of-message，从它之后的第一条消息起才切换到 chunked。忘了切换的症状是会话静默挂死——不报错、没有任何回复（服务端在等 chunk header），比报错还难查。同源的另一个坑是"小的能过、大的挂住"：客户端只实现了"一条消息 = 一个 chunk"，遇到多 chunk 的大响应就永远等不到结束标记。工程实践 §7.4 给了这类症状的排查入口。

两个操作都可带 <filter>，两种写法：subtree 用「数据的形状」描述你要什么（带值的元素是内容匹配，空元素是选择节点），所有设备都支持；xpath 能表达 [mtu > 1500] 这类条件，但需要 :xpath。有一条两者都成立：list 的 key 总会被带回来，即使你没选它——否则回复里那一行无法寻址。

subtree filter 最反直觉的一点：写错了不报错，只是返回空。命名空间打错一个字母、revision 换了导致节点改名、或请求了一个被 deviate not-supported 掉的节点——服务端的行为都是「这个过滤器什么都没匹配上」，于是回一个空的 <data/>，完全符合规范，没有任何错误。所以「查不到数据」这个现象里，「设备上真没有」和「你问错了」是分不出来的。判读方法：先发一个不带 filter 的 get-config，确认那棵子树确实存在、命名空间确实是你以为的那个，再逐层往下收窄。

<edit-config>：改配置

整篇 NETCONF 里最容易出事的就是这一个 RPC，不是因为它复杂，而是因为它有两套互相作用的开关：每个节点可带 operation 属性，整条 RPC 又有一个 default-operation，再加上 test-option 与 error-option。完整报文见 工程实践 §4.1，这里只讲语义。

第一个坑就在 xmlns:nc 上。operation 属性属于 NETCONF base 命名空间，而它所在的元素在模型的命名空间里。XML 的规则是：无前缀的属性不属于任何命名空间——它不会像元素那样继承默认 xmlns。所以 <interface operation="delete"> 是错的：严格的服务端报 unknown-attribute，宽松的服务端直接忽略这个属性，于是你的 delete 退化成默认的 merge——你想删一个接口，结果只是把它的 key 又写了一遍，commit 返回 <ok/>，接口纹丝不动。这是"操作成功但什么都没发生"最常见的单一原因。

delete 与 remove 的取舍，本质是"你要不要用报错来做一致性检查"。幂等脚本（"确保这条配置不存在"）用 remove，重跑一百遍结果都一样；一次性运维动作（"把这个用户删掉"）用 delete——如果它已经不在了，说明你对设备状态的认知有偏差，这时候报错是好事。create 与 merge 是同一逻辑的镜像。兼容点：remove 是 RFC 6241（2011）才加的，很老的设备可能不认识，而这一条 hello 里看不出来。

还有一条容易忽略的语义：作为节点属性的 replace，作用范围只是它自己那个节点的子树，兄弟节点毫发无损——与下一节的 <default-operation>replace</default-operation> 是完全不同的两件事，名字一样，威力差几个数量级。

default-operation / test-option / error-option

default-operation没标 operation 的节点怎么处理危险度什么时候用
merge
（默认值）		列出的写进去，没列出的不动低绝大多数增量修改。缺点是它永远删不掉东西
replace⚠ 用 <config> 的内容完整替换整个目标 datastore，没出现在这次请求里的配置一律删除极高唯一正当用途：把一份完整的配置备份灌回去
none什么都不做，这些节点纯粹作为定位路径；只有显式带 operation 的节点才生效低，且最精确外科手术式的改动，尤其是删除
default-operation=replace 是这整篇里最危险的一个字段，没有之一。它的语义不是"替换你写的这部分"，而是"用你这次发来的 <config> 替换掉整个 datastore"。你只想改 eth0 的 MTU、请求体里只写了一个接口，这个字段手滑填了 replace——commit 之后设备上只剩下 eth0 一个接口，路由、ACL、用户、其它 200 个接口全部消失，而且完全合法，设备回一个 <ok/>。防护三条见 工程实践 §4.2。

none 存在的理由值得单说：删一个 description 时，请求里 <interface><name>eth2</name> 这两层在 merge 下本身就是"要被合并进去的配置"——万一 eth2 不存在，你这一发就顺手把它创建出来了。用 none 时它们只是路径，而且规范特意规定：层级在目标库里不存在就返回 data-missing，正好把"我的假设错了"暴露出来。

另外两个开关一句话说完：test-option 决定校不校验（test-then-set 默认 / set 不校验 / test-only 只校验不写，dry-run 的正规手段，需 :validate:1.1）；error-option 决定出错后失败点之前的改动留不留（stop-on-error 默认，留下半套配置 / continue-on-error / rollback-on-error 整条撤回）。

rollback-on-error 是"没有 candidate 的设备"唯一的原子性来源，但边界要说准：它只覆盖一条 edit-config RPC，不是跨多条 RPC 的事务。变更需要三次 edit-config 时，第二次成功、第三次失败，前两次的改动照样留在设备上。真正的多步事务只能靠 candidate + commit。推论有点反直觉：把改动拆成很多小的 edit-config"方便调试"，恰恰是在放弃仅有的那点原子性。

lock / unlock / validate / copy-config

<lock> 锁的是整个 datastore，不是某个子树（子树级的部分锁是 RFC 5717 的可选扩展，现网支持度不高）。规范里写死了三种拒绝授予的情形，每一种都在防一类事故：

  • 锁已被任何会话（或其它管理实体，比如正在敲 CLI 的人）持有——返回 lock-denied，<error-info> 里带上持有者的 <session-id>，那就是你决定要不要 <kill-session> 的依据。
  • 目标是 candidate 且它已有未提交的改动——防的正是"你锁上 candidate，却发现里面躺着别人半小时前写了一半又忘了的东西"。
  • 目标是 running 且别的会话正在做确认式提交——那个 commit 随时可能超时回滚，此刻 running 不稳定。

锁在 <unlock> 时释放，或者在会话终止时由服务端自动释放——也就是说锁的生命周期挂在 TCP 连接上，而 TCP 连接的死亡未必被及时发现。僵尸会话与抢锁退避见 工程实践 §4.4。

「commit 了就会一直生效」是个非常昂贵的误会。<commit> 只把 candidate 提交到 running，而 running 在多数设备上是内存里的运行态。设备支持 :startup 时，你必须再显式 copy-config running → startup，配置才能扛过一次重启——现场表现就是那句经典的"改完好好的，机房断电重启之后全变回去了"。反过来，不声明 :startup 的设备 running 本身就持久化，多做一次反而报 invalid-value。所以这一步做不做，必须由 hello 决定，不能写死在脚本里。

<rpc-error>：失败长什么样

一条 <rpc-reply> 要么带 <ok/> 或 <data>，要么带一个或多个 <rpc-error>。读懂 error-tag 就能定位到问题类别，比读 error-message 里那句厂商自由发挥的英文靠谱得多：

error-tag含义八成是你哪里错了
unknown-namespace / unknown-element命名空间或元素设备不认识模型 revision 对不上、命名空间打错、或该节点被 deviate not-supported
unknown-attribute属性不认识十有八九是 operation 忘了带 nc: 前缀
missing-element缺必填节点漏了 mandatory true 的 leaf，或漏了 list 的 key
bad-element / invalid-value值不合法越界、不匹配 pattern、枚举值不认识、往 config false 节点写数据

operation-not-supported这个操作我不支持没先看 hello 的 capability 列表

Datastore 与通知

配置的"三个抽屉" + 主动上报

running

当前正在生效的配置，唯一必选的库。能不能直接写它取决于 :writable-running。

candidate

草稿：先改这里，commit 后才生效。可选。默认是全设备共享一份，不是每会话一份——最大的坑。

startup

开机加载的配置（掉电保存）。可选。commit 不会自动更新它，要显式 copy-config。

为什么要 candidate + commit？复杂配置往往要"一批改动一起生效"，中途的半套配置会让设备异常。candidate 让你先改草稿、校验无误再原子提交。

完整的事务流程：从编辑到落盘

规范的变更序列是 lock → discard-changes → edit-config ×N → validate → commit → unlock（视情况再 copy-config → startup）。每一步都在防一类具体事故，逐步报文与"省掉它会怎样"见 工程实践 §4.1。这里只说最反直觉的那条前提：

candidate 默认是「整台设备共享一份」，不是「每个会话一份」——这条几乎所有人第一次都会想错。后果是：会话 A 往 candidate 里写了几条改动就去开会了，会话 B 进来接着写自己的，B 一发 <commit>——A 和 B 的改动被一起提交到 running 了，而 B 完全不知道自己捎带了什么。这不是 bug，是 RFC 6241 定义的行为。防护就是开头那两步：先 lock，紧接着 discard-changes。规范还配了一条很妙的规则：candidate 里已有未提交改动时 lock 会被拒绝——于是你在第一步就能发现"里面有人"，而不是 commit 之后才发现。discard-changes 之所以要在 lock 之后：拿到锁之前清理，清完立刻可能又被别人写进去。

confirmed-commit：给远程配置留一条退路

远程配置最恐怖的场景不是"配错了"（那有 validate 和 must），而是"配错的那一下正好把你自己连进来的这条路切断了"——改错管理口 IP、ACL 把自己拒之门外、路由改崩。这时设备工作得好好的，只是你再也够不着它。机制是 <commit><confirmed/><confirm-timeout>300</confirm-timeout></commit>：配置立即生效，同时压上一个回滚定时器（默认 600 秒）。窗口内再发一个 <commit> 就确认，<cancel-commit> 立即回滚，什么都不做则自动还原。

它最精妙的地方是把"什么都不做"设计成了安全的那一侧。凡是需要人主动补救的机制，真出事时都指望不上——因为出事时你恰恰联系不上设备。confirmed-commit 反过来要求你主动确认"我还活着"，做不到就自动退回；而且回滚逻辑跑在设备自己身上，不依赖客户端还活着、也不依赖网络还通。<persist>（:1.1）是"能不能真的救你"的分水岭：不带它时会话一终止就立即回滚，可最常见的场景恰恰是你改的就是管理网，改完链路必然抖一下，于是一次本来会成功的变更被判了死刑。另外 :confirmed-commit:1.1 只能在同时声明 :candidate 的设备上宣告——没有草稿库的设备，标准里就没有这个安全网。四条时间线的图解见 工程实践 §4.3。

没有 candidate 的设备怎么办

相当一部分设备（嵌入式网元、白盒设备、早期实现）只声明 :writable-running，于是三样东西一起失去：多步事务、提交前 review、标准的 confirmed-commit。能补回来的只有近似方案——把整批改动塞进一条 edit-config 配 rollback-on-error、用 test-only 做 dry-run、变更前后各做一次全量 get-config 算 diff、以及客户端侧自建"定时器 + 探活"的确认窗口。最后这条的致命弱点必须认清：它依赖客户端还活着、且到设备的路还通——而这恰恰是 confirmed-commit 唯一不依赖的两件事。逐条取舍见 工程实践 §4.5。

NMDA：intended 与 operational

传统三库有一个从 2003 年就提出、却拖到 2018 年才补上的缺口：你无法区分"我要求的配置"和"设备实际在跑的配置"。四种情形都表达不出来——给一块还没插上的板卡配了接口（running 里有，设备上没这个口）；设备自己生成的配置（在跑但不在 running 里）；值来自 YANG default 的 leaf（running 里看不到，设备确实在按它工作）；配置正在逐个下发的过程中（running 已是新的，硬件还是旧的）。RFC 8342 为此把 datastore 这个概念重新定义了一遍，加了两个只读库：

datastore可写内容回答的问题
candidate / running / startup是客户端下发的配置（config true）「我提交了什么」
<intended>否running 经"配置变换"（模板展开、失活配置剔除）后的结果，且必须有效「我打算让它变成什么样」
<operational>否已生效的配置 + 系统自建配置 + 学到的数据 + 生效的默认值 + 全部状态数据「它现在实际是什么样」

配套的协议扩展在 RFC 8526：新增 <get-data> / <edit-data>，带一个 datastore 参数，于是"读哪个库"从"用哪个 RPC"变成了"填哪个参数"。<get-data> 还支持 with-origin，给 operational 里每个值标注来源——排查"这个值到底是谁配的"时，这一个标注抵得上半天翻日志。

用一句话说清它的价值：「NMDA 把『配置是否真的生效』从一个靠猜的问题，变成了一个可以直接查询的问题——intended 与 operational 的差集就是答案。」在这之前，一致性校验只能做成"把 running 拉回来和期望比对"，而这只验证了设备记住了我的话，没验证设备做到了我的话。现实是落地进度参差不齐，客户端要能同时兼容两种模型。

Notification：设备主动上报

客户端用 <create-subscription>（RFC 5277，需 :notification）订阅一个事件流，此后设备在故障/状态变化时主动推送 <notification>——这就是管理面"监控/告警"的来源。模型侧的声明方式见 §3.7 那张图；协议侧有三个点决定你的客户端架构：

  • <notification> 不是 <rpc-reply>，它没有 message-id，也不对应任何请求。收包循环必须能处理"这条消息不是我在等的那个响应"，否则一发订阅，后续所有 RPC 的响应配对就全乱了。
  • 没有 :interleave 的设备，订阅之后这条会话就只能收通知。所以稳妥的做法是永远为通知单开一条会话，顺带也隔离了"订阅会话被事件刷爆"对配置通道的影响。
  • <startTime> 能重放历史事件（需设备支持），是客户端重启后补齐断连期间事件的正规手段。但嵌入式设备的 replay 缓冲往往很小甚至没有，所以重连后还得再做一次全量状态同步，见 工程实践 §5.7。

面试题（12 道）

分层自测

8.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础YANG 和 NETCONF 是什么关系？

    YANG 是数据建模语言，NETCONF 是网络管理协议。前者定义"数据长什么样"——有哪些字段、什么层级、什么类型、什么约束；后者定义"怎么操作和搬运这些数据"——一套基于 XML 的 RPC。

    更能体现理解深度的说法是它们处在不同的时间轴上：YANG 属于设计期，厂商在设备出厂前就把 .yang 模型写好、编译好、发布出去；NETCONF 属于运行期，真正跑在 TCP 连接上一来一回的是它。

    一个很好用的具象化：一个 NETCONF 报文里混着两套命名空间。外层的 <rpc><edit-config><target><config> 全部来自 urn:ietf:params:xml:ns:netconf:base:1.0，所有设备都一样；一进到 <config> 内部，命名空间就切换成某个 YANG 模块的 namespace，这部分才是设备特有的。排查时先判断"报错在外层还是内层"——外层是协议用错了，内层是模型用错了。

    加分：指出两者并不互相绑死。同一份 YANG 模型可以被 NETCONF（XML）、RESTCONF（JSON，RFC 7951）、gNMI（protobuf）分别承载，换协议不换模型；反过来 NETCONF 在规范上也不强制用 YANG（RFC 4741 发布时 YANG 还不存在），只是没有 schema 的 NETCONF 会退化成"用 XML 包起来的私有 CLI"，失去全部价值。

  2. 基础NETCONF 的四层模型是哪四层？各自负责什么？

    自上而下：

    • Content（内容层）：配置数据、状态数据、通知内容。结构完全由 YANG 决定（RFC 7950），NETCONF 本身不关心里面装的是什么。
    • Operations（操作层）：协议的动词——get / get-config / edit-config / copy-config / delete-config / lock / unlock / commit / discard-changes / validate，加上 close-session / kill-session。定义在 RFC 6241 第 7 节。
    • Messages（消息层）：<hello> / <rpc> / <rpc-reply> / <rpc-error> / <notification> 这套信封，message-id 的配对规则，以及消息分帧（RFC 6242 第 4 节）。通知的定义在 RFC 5277。
    • Secure Transport（安全传输层）：SSH（RFC 6242，tcp/830，强制实现）或 TLS（RFC 7589，tcp/6513），Call Home 是 RFC 8071 的 tcp/4334。再往下是 TCP / IP / 以太网。

    要答出分层的意义而不只是罗列：这四层是"换一层不影响其它层"的解耦承诺。真实例证——NMDA 给操作层加了 <get-data> / <edit-data>（RFC 8526），消息层与传输层一个字节没改；base:1.0 升到 1.1 换了分帧方式，操作层完全不受影响；O-RAN 前传 M 平面用 TLS 而 O1 更多用 SSH，上面三层一模一样。

    加分：指出传输层的要求是"能力"而不是"某个具体协议"——面向连接、可靠有序、已认证、已加密。这也解释了为什么 UDP 从一开始就被排除：message-id 配对、分帧、以及 datastore 锁的生命周期全都建立在"会话"这个概念上。

  3. 基础<get> 和 <get-config> 有什么区别？

    三个差别，每一个都有实际后果：

    • 返回内容不同。get-config 只返回 config true 的节点；get 返回 config true + config false，即配置与状态混在同一棵树里。
    • 能不能选库。get-config 有 <source> 参数，可以读 running / candidate / startup；get 没有 source 参数，它固定读 running。这一点很多人记不住。
    • 结果能不能回灌。get-config 的输出是"干净"的，可以原样 edit-config 回去——配置备份与灾难恢复就靠这个性质。get 的输出里混着只读节点，回灌必然报错。

    再补一句量级：不加 filter 的 <get/> 在一台满配设备上可能返回比 get-config 大一个数量级的数据（计数器是逐接口逐队列的），它实际上是一次压测，生产环境里不该出现在轮询循环里。

    加分：把它上升到设计层面——"配置数据与状态数据必须能分开"是 RFC 3535 那份运营商需求清单里的第一条，YANG 的 config 标志 + 这两个操作就是它的落地。SNMP 的 MIB 里 ifMtu（可写）和 ifInOctets（只读计数）平级摆着，正因为分不开，"备份配置"这件事在 SNMP 上根本无从下手。

  4. 基础YANG 里的 config false 是什么意思？

    config false 标记这个节点是「状态数据」而不是「配置数据」：它由设备自己产生，客户端只能读、不能写。典型的是计数器（in-octets）、运行状态（oper-status）、协商结果、邻居表。默认值是 config true，所以模型里绝大多数节点不写这一句。

    直接后果：

    • 它不会出现在 <get-config> 的结果里，只有 <get> 能拿到；
    • 往它写数据会被拒（invalid-value 或 unknown-element）；
    • 它不参与配置备份与比对——这正是配置备份能干净回灌的原因。

    两条容易被追问的硬规则：① config false 节点的所有子孙自动也是 config false，不能再翻回 true（配置树不可能长在状态树下面）；② config true 的 list 必须有 key，config false 的 list 可以没有——因为状态数据不需要被寻址修改。第二条解释了为什么很多计数器表在模型里看不到主键。

    加分：指出这个二分法在 NMDA（RFC 8342）里被进一步细化了。config 标志区分的是"节点的性质"，而 NMDA 用 <intended> 与 <operational> 两个 datastore 区分"我打算要的配置"与"实际在跑的配置 + 状态"。在 <operational> 里，config true 的节点照样会出现——但那是「已经生效的值」，可能和你在 running 里写的不一样（比如给一块没插上的板卡配的接口，running 里有、operational 里没有）。

8.2 中级（区分熟练度）

  1. 中级<hello> 里的 capability 协商起什么作用？

    会话一建立（SSH/TLS 认证通过后），双方各自立刻发出一个 <hello>，列出自己支持的能力。注意它不是请求/响应——两边都不等对方，所以严格说是"双向单播的能力宣告"而不是握手。协商规则极简单：取交集，某个能力必须在双方列表里都出现才算可用。

    它决定了这条会话上"什么能做、什么不能做"，关键的几条：

    • :base:1.1 → 决定用 chunked framing 还是 ]]>]]>；
    • :writable-running → edit-config 的 target 能不能填 running；
    • :candidate → 有没有草稿库，也就是有没有多步事务；
    • :validate / :rollback-on-error / :confirmed-commit → 三层安全网各有没有；
    • :startup → 要不要额外做 copy-config running → startup 才能扛过重启；
    • :notification / :interleave → 能不能订阅事件，订阅之后还能不能在同一条会话上发 RPC；
    • :xpath / :url / :with-defaults / :yang-library → 过滤方式、大配置传输方式、默认值行为、模型清单来源。

    另外 服务端的 <hello> 里有 <session-id>，客户端的禁止有。这个 id 不只是流水号——它是 <kill-session> 的入参，也是 lock-denied 错误的 <error-info> 里告诉你"锁在谁手上"的那个值。

    工程上的加分点：集成一台新设备时第一件事是把服务端 <hello> 完整存档。它回答了"这台设备到底能做什么"的九成问题。后面每次"这个操作为什么不行"，都该先回到这份存档看一眼，而不是去翻 RFC。只在自己 mock 服务器上测过的客户端往往默认所有能力都在，上真设备第一天就会被 operation-not-supported 教做人。

  2. 中级为什么 chunked framing 取代了 ]]>]]>？

    因为 ]]>]]> 这种分隔符式分帧把"边界标记"和"数据"塞进了同一个字节空间，却没有提供任何转义机制。RFC 6241 只能靠一条纪律兜底：内容里禁止出现这六个字节。可 NETCONF 的内容是任意 YANG 数据——一个 description 字符串、一段脚本、一个 XML 注释都可能凑出它。

    而后果不是丢一条消息，是整条会话此后所有消息的边界全部错位：接收端在半截 XML 处切了一刀，之后每条消息都是上一条的尾巴加下一条的头。现场表现是"跑了几个月好好的，某天配了一条带特殊字符的描述之后，这台设备的管理通道再也起不来了"。

    除了正确性，还有三个工程问题：① 必须逐字节扫描找分隔符，无法零拷贝、无法预分配缓冲；② 读完才知道消息多大，也就无法在读之前做"消息过大直接拒绝"的 DoS 防护；③ 大响应必须在内存里拼成一整块才能发。

    chunked framing（RFC 6242 §4.2）用长度前缀把这些一次性解决：\n#<size>\n<data> 重复若干次，以 \n##\n 结束。接收端不需要理解内容的任何一个字节，只需要数够 N 个，于是内容对分帧完全透明。这是所有二进制协议早就学会的一课（HTTP 的 Content-Length、SCTP 的消息边界都是同一个道理）。

    两个必答的实现细节：

    • <hello> 本身永远用 ]]>]]> 分帧。因为分帧方式是靠 hello 协商出来的，协商完成之前双方还不知道该用哪种。从 hello 之后的第一条消息起才切换到 chunked（前提是双方都声明了 base:1.1）。忘了切换的症状是会话静默挂死——不报错、没回复，因为服务端在等 chunk header。
    • chunk 边界与 XML 结构毫无关系。RFC 里的例子第一个 chunk 只有 4 个字节 <rpc，把标签都切断了，这完全合法。所以接收端必须先按 chunk 拼出完整字节流，再交给 XML 解析器，不能边拆边解析。只处理"一条消息 = 一个 chunk"的实现，会在"小的能过、大的挂住"上翻车。
  3. 中级edit-config 的 operation 属性有哪五个值？分别什么语义？

    按"目标已存在 / 不存在"两种情况说，才算讲清楚：

    • merge（默认）：逐层合并——列出的 leaf 覆盖值，未列出的保留；目标不存在则创建。merge 只增不减，想删东西它帮不上忙。
    • replace：整棵子树被替换，未列出的子节点全部删除；不存在则创建。这是"把这个对象配成我说的这个样子"的幂等下发姿势。
    • create：已存在则报 data-exists；不存在则创建。
    • delete：不存在则报 data-missing；存在则删除。
    • remove：存在就删，不存在则静默成功。

    两个高频追问点：

    ① delete 与 remove 怎么选？本质是"你要不要用报错来做一致性检查"。幂等脚本（"确保这条配置不存在"）用 remove，重跑一百遍结果都一样；一次性运维动作（"把这个用户删掉"）用 delete——如果它已经不在了，说明你对设备状态的认知有偏差，这时候报错是好事。顺带一个兼容点：remove 是 RFC 6241（2011）才加的，RFC 4741 时代没有，很老的设备可能不认识。

    ② replace 作用在哪一层？作为节点属性时，它只重塑带这个属性的那个节点的子树，兄弟节点毫发无损。这和 <default-operation>replace</default-operation> 是完全不同的两件事——后者会用你这次发的 <config> 替换掉整个 datastore。名字一样，威力差几个数量级。

    最后一个几乎必踩的实现坑：operation 属性属于 NETCONF base 命名空间，必须带前缀写成 nc:operation="delete"。XML 里无前缀的属性不属于任何命名空间（不像元素那样继承默认 xmlns）。写成 operation="delete" 时，严格的服务端报 unknown-attribute，宽松的服务端直接忽略这个属性，于是你的 delete 退化成默认的 merge——返回 <ok/>，接口纹丝不动。这是"操作成功但什么都没发生"最常见的单一原因。

  4. 中级augment 和 deviation 有什么区别？

    一句话：augment 是模型作者的加法，deviation 是设备实现者的减法（或修正）。

    • augment：在自己的模块里，往别人的数据树上挂新节点。"标准模型没有我要的字段，我加一个。"挂上去的节点属于你自己的命名空间，可以带 when 做条件挂载。典型场景：厂商在 ietf-interfaces 的 interface 下加私有的 storm-control。它会进数据树，客户端可以正常读写。
    • deviation：写在一份单独的 <vendor>-deviations.yang 里，声明这台设备与标准模型的偏差。"标准模型的这部分我做不到 / 我做得不一样。"四种 deviate：not-supported（这个节点我根本没实现）、replace（换个类型或收紧范围，比如标准允许 MTU 到 9216 而我只到 1500）、add（加个 must 或 default）、delete。它的唯一目的是诚实地告诉客户端"别对我抱这个期望"，让客户端提前调整，而不是等下发失败再猜。

    一个非常容易答错的细节值得主动说：augment 进来的节点属于「写 augment 的那个模块」的命名空间，不是被 augment 的模块。写实例数据时必须切 xmlns——把 storm-control 直接写在 ietf-interfaces 的默认命名空间下，设备会报 unknown-element 或直接忽略。这一条几乎人人都会想错一次。

    顺带把相关的第三个机制补上：feature + if-feature 表达的是"这块内容可选，看设备支不支持"，由设备在运行时声明支持哪些。它和 deviation 的分工是：feature 是模型作者预见到的可选性（写在标准模块里），deviation 是设备实现者事后声明的偏差（写在自己的模块里）。

    工程结论：集成时必须把 deviation 和 feature 一起读进来。途径是 ietf-yang-library（RFC 8525），它同时给出模块清单、revision、启用的 feature 和 生效的 deviation。只按 IETF 官网那份标准模型写代码，然后在设备上遇到 unknown-element，绝大多数就是漏了这一步。

8.3 高级（体现深度）

  1. 高级default-operation 有哪三个取值？它的坑在哪？

    三个取值决定"<config> 里没有显式标 operation 的那些节点该怎么处理"：

    • merge（默认值）：按 merge 处理。低风险，覆盖绝大多数增量修改。
    • replace：用 <config> 的内容完整替换整个目标 datastore，凡是没出现在这次请求里的配置一律删除。
    • none：什么都不做，这些节点纯粹作为定位路径；只有显式带 operation 的节点才生效。

    最大的坑是 replace 的作用域被严重低估。很多人以为它是"替换我写的这部分"，实际是"替换整个库"。想象你只想改 eth0 的 MTU，请求体里就写了一个接口，default-operation 手滑填了 replace——commit 之后设备上只剩下 eth0 这一个接口，路由、ACL、用户、其它 200 个接口全部消失。而且这完全合法，设备回一个 <ok/>。它唯一的正当用途是把一份完整的配置备份灌回去。

    防护三条，缺一不可：① 客户端代码里把它做成需要显式开关才能触发的"危险模式"，不要让它成为某个封装函数的一个可选参数；② 永远先在 candidate 上做，commit 前用 get-config candidate 把结果整棵拉回来看一眼；③ 配 confirmed-commit，给自己留退路。

    第二个坑在反方向：none 太安全，安全到"什么都没发生也不报错"。如果 <config> 里一个 operation 属性都没写，服务端老老实实什么都不做，返回 <ok/>。这与"属性忘了带 nc: 前缀"叠加时特别难查——你以为写了 operation，服务端认为你没写。

    说清 none 为什么存在能体现深度：假设要删 /interfaces/interface[name='eth2']/description。用默认的 merge 时，请求里的 <interfaces> 和 <interface><name>eth2</name> 这两层本身就是要被合并进去的配置——万一 eth2 其实不存在，你这一发就顺手把它创建出来了，然后删掉一个本来就没有的字段。用 none 就不会，而且 RFC 6241 特意规定：如果 <config> 里的层级在目标库中不存在，返回 data-missing——正好把"我对设备状态的假设错了"暴露出来。

    最后把它和另外两个开关串起来：test-option（test-then-set 默认 / set / test-only）决定校不校验，error-option（stop-on-error 默认 / continue-on-error / rollback-on-error）决定出错后失败点之前的改动留不留。stop-on-error 是默认值，也就是说默认行为会留下半套配置——这一点必须知道。

  2. 高级candidate 与 running 的事务模型是怎样的？完整的变更流程有哪几步？

    running 是正在生效的配置（唯一必选的库）；candidate 是草稿区（可选能力 :candidate）。模型是：所有 edit-config 打到 candidate，中途随便改、随便验，<commit> 时一次性原子地刷进 running；不想要了就 <discard-changes>，candidate 还原成 running 的内容。

    完整的六步，每一步都在防一类具体事故：

    1. <lock><candidate/> —— 防别人同时改同一份草稿
    2. <discard-changes/> —— 清掉前一个会话留下的残渣
    3. <edit-config> ×N
    4. <validate><source><candidate/> —— 抓 must / leafref / unique 这类跨节点约束
    5. <commit>（建议带 <confirmed/>）
    6. <unlock>；若设备声明 :startup，再 copy-config running → startup

    第 1、2 步为什么不能省，是这道题真正的考点：candidate 默认是「整台设备共享一份」，不是「每个会话一份」。后果是：会话 A 写了几条改动就去开会了，会话 B 进来接着写自己的，B 一发 <commit>——A 和 B 的改动被一起提交了，而 B 完全不知道自己捎带了什么。这不是 bug，是 RFC 6241 定义的行为。规范还有一条很妙的配套规则：candidate 里如果已有未提交的改动，lock 会被拒绝——所以你在第 1 步就能发现"里面有人"，而不是 commit 之后才发现。（另外两条拒绝规则：锁已被任何会话或其它实体持有；目标是 running 且别人正在做确认式提交。）

    第 6 步也常被漏：<commit> 只写到 running，而 running 在多数设备上是内存里的运行态。不做 copy-config → startup，一次重启就全变回去了。反过来，不声明 :startup 的设备 running 本身就持久化，多做这一步反而报 invalid-value。所以这一步做不做，必须由 hello 里有没有 :startup 决定，不能写死在脚本里。

    加分：指出比锁泄漏更隐蔽的是"脏 candidate"。会话异常终止时锁会被自动释放，但 candidate 里写了一半的内容不会，它就静静躺着等下一个不做 discard-changes 的人。锁泄漏至少会报 lock-denied，脏草稿是彻底静默的。

  3. 高级confirmed-commit 解决什么问题？<persist> 有什么用？

    它解决的不是"配置写错了"（那有 validate 和 must），而是"配置本身完全合法，但生效之后正好把你自己连进来的这条路切断了"——改错管理口 IP、ACL 把自己拒之门外、路由改崩、VLAN 划错。这时设备工作得好好的，只是你再也够不着它，除非有人开车去机房插串口线。

    机制：<commit><confirmed/><confirm-timeout>300</confirm-timeout></commit>。配置立即生效，同时压上一个回滚定时器（不写 timeout 默认 600 秒）。在窗口内：再发一个 <commit> 就确认，配置永久生效；发 <cancel-commit> 就立即回滚；什么都不做，超时后设备自动还原成提交前的样子。

    它最精妙的地方是把"什么都不做"设计成了安全的那一侧。所有需要人主动补救的机制，在真出事的时候都指望不上——因为出事时你恰恰联系不上设备。confirmed-commit 反过来要求你主动确认"我还活着、一切正常"，做不到这一点就自动退回。而且这个回滚逻辑跑在设备自己身上，不依赖客户端还活着、也不依赖网络还通——这是任何客户端侧的"自建确认窗口"方案都无法替代的。

    <persist>（:confirmed-commit:1.1）是"能不能真的救你"的分水岭。不带它时，规范行为是会话一终止就立即回滚。听起来安全，但现实中最常见的场景恰恰相反：你改的就是管理网的配置，改完管理链路必然会短暂抖一下，SSH 会话被断开——于是一次本来会成功的变更被判了死刑，还得从头再来。带上 persist 之后，会话断了不要紧，倒计时继续走，你重连上来（甚至换一条会话）发一个带 <persist-id> 的 commit 就确认；真连不上，超时后它自己回滚。两种失败都被覆盖，这才是完整的。

    几个能显出真做过的细节：① 确认用的那个 commit 如果自己也带 <confirmed/>，会重置倒计时——可以边验证边"续期"；② 确认式提交进行中时，其它会话无法 lock running，因为此刻 running 随时可能变回去；③ RFC 6241 规定 :confirmed-commit:1.1 只能在同时声明 :candidate 的设备上宣告——没有草稿库的设备，标准里就没有这个安全网，只能退回到"变更前全量 get-config 备份 + 客户端侧定时探活回灌"，而那个方案恰恰依赖客户端和网络都还活着。

  4. 高级一次配置下发失败了，你怎么定位？

    先把"失败"分成三种，因为它们的排查路径完全不同：（A）报了 <rpc-error>；（B）返回 <ok/> 但配置没生效；（C）没有任何响应，挂住或超时。问清是哪一种，是这道题的第一个得分点——很多人上来就讲抓包。

    （A）有 <rpc-error>：从 error-tag 入手，它比 error-message 里那句厂商自由发挥的英文靠谱。

    • unknown-element / unknown-namespace → 模型对不上。跳到下面的"模型三连查"。
    • unknown-attribute → 十有八九是 operation 忘了带 nc: 前缀。
    • data-exists / data-missing → 对设备当前状态的假设错了。先 get-config 看真实状态；想要幂等就把 create/delete 换成 merge/remove。
    • invalid-value / bad-element → 越界、不匹配 pattern、或往 config false 节点写数据。
    • lock-denied → 看 <error-info> 里的 session-id，再读 ietf-netconf-monitoring 的会话表判断是不是僵尸会话。
    • access-denied → NACM（RFC 8341）挡了。注意 NACM 也能配成"隐藏"而非"拒绝"，那时症状变成（B）或空数据。
    • operation-not-supported → 回去看 hello 的 capability 列表。
    • rollback-failed → 最坏情况，设备处于既非改前也非改后的中间态，停止自动化、人工介入。

    另外 <error-path> 会给出指到出错节点的 XPath（含 list 的 key 谓词），能直接告诉你 200 个接口里是第几个出的问题。填得不完整的实现，就配 continue-on-error 让它一次报全，或者二分定位。

    （B）返回 <ok/> 但配置没生效——最难查的一类，按可能性从高到低：

    1. operation 属性没带 nc: 前缀，被宽松的服务端忽略，delete 退化成 merge。
    2. 只 commit 到 running，没有 copy-config → startup——症状是"改完好好的，重启后全变回去"。
    3. YANG 的 when 条件为假，服务端静默地把节点删掉了。这是设计使然、不报错。回头 get-config 会发现那个 leaf 根本不在。
    4. 命名空间写错，尤其是 augment 进来的节点用了父节点的命名空间。
    5. default-operation=none 但一个 operation 都没标，服务端确实什么都没做。
    6. 配置进了 running 但没在硬件上生效（板卡没插、资源不足、驱动失败）。这一条正是 NMDA 要解决的：设备支持的话，用 <get-data> 比较 <intended> 与 <operational>，差集就是"要求了但没落地"的部分；配上 with-origin 还能看出每个值的来源。不支持 NMDA 就只能拿 <get> 的状态节点和期望值人工比对。

    （C）挂住 / 超时：先分清是协议层还是处理层。协议层看分帧——典型症状是"小的能过、大的挂住"，而且连接还活着、没有任何错误（服务端在等 chunk header，客户端在等结束标记）；排查入口是在传输层把原始字节 dump 出来数 chunk，而不是看 XML 解析日志（那一层根本没收到东西）。处理层则是设备真的还在算：大配置的 must / leafref 校验成本随规模超线性增长，1000 个接口可能比 100 个慢 100 倍。这时千万不要盲目重发——重连后先读会话表，看上一条会话在不在、锁在谁手上，再决定等待、kill 还是重来。

    「模型三连查」（A 类里 unknown-* 的标准动作）：① 读 ietf-yang-library，拿模块 + revision + 启用的 feature + 生效的 deviation 四份清单；② 用 <get-schema>（RFC 6022）把设备上的 .yang 正文拉下来，和你手上那份 diff；③ 用 test-option=test-only 缩到最小复现，只发一个 leaf。

    最后给一条工程结论，比具体步骤更值钱：不要相信任何本地的模型副本，把设备当成模型的唯一真相来源。正确的集成流程是连上设备 → 读 yang-library → get-schema 下载全部模块 → 用这份"设备自述"编译客户端绑定。这样 feature、deviation、revision 差异在编译期就暴露，而不是在凌晨的变更窗口里以 unknown-element 的形式暴露。
