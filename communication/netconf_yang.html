NETCONF / YANG：网络设备如何被配置和管理

管理面的主角来了。O-RAN 的 O1 接口和前传 M 平面都用 NETCONF/YANG——它俩到底谁干什么？这一篇把最容易混淆的一对概念讲透：YANG 定义"数据长什么样"，NETCONF 定义"怎么操作和传输这些数据"，并配上真实的 XML/RPC 例子。

Module 07 阅读 ~90 min 管理面核心
01

先讲清一件事

NETCONF 和 YANG 的分工

🍽 生活类比：餐厅点菜

YANG = 菜单的"格式规范"：规定菜单该有哪些字段（菜名、规格、可选配料、价格范围、哪些是必选）。NETCONF = 你和服务员的"交互协议"：怎么点菜（下单）、怎么查看当前订单、怎么改单、怎么确认。菜单定义结构（YANG），点菜流程操作数据（NETCONF）。

YANG：数据建模语言——定义设备的配置/状态数据有哪些字段、层级、类型、约束。
NETCONF：网络管理协议——定义如何获取、修改、提交、传输这些数据（一套基于 XML 的 RPC）。
核心关系：YANG → 定义数据模型（schema）；NETCONF → 操作并传输符合该模型的数据（instance）。二者是"schema 与 protocol"的关系，缺一不可。

这两个名字几乎总是连在一起出现（"O1 用 NETCONF/YANG"、"M 平面用 NETCONF/YANG"），久而久之很多人把它当成一个东西的两半，甚至以为 YANG 是 NETCONF 的某种"配置文件格式"。它们其实处在完全不同的时间轴上：YANG 属于设计期——厂商在发布设备之前就把模型写好、编译好、发布出去；NETCONF 属于运行期——真正跑在 TCP 连接上、一来一回搬运数据的是它。你手上拿到一份 .yang 文件时设备还没上电，而你抓到一个 <rpc> 报文时模型早就固化在两端了。

三条判据，看一眼就能分清

你看到的东西它属于理由
container / list / leaf / type uint16YANG这是模型语言的关键字，描述"字段与约束"，本身不是数据
<rpc> / <rpc-reply> / <edit-config> / <commit>NETCONF协议自己的操作词汇，定义在 urn:ietf:params:xml:ns:netconf:base:1.0 命名空间里
<interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">两者的交界XML 的骨架由 NETCONF 定义，装在 <config> 里的这一坨由 YANG 定义；命名空间就是分界线

最后一行是这一篇最值得记住的一句：一个 NETCONF 报文里其实混着两套命名空间。外层的 <rpc><edit-config><target><config> 全部来自 NETCONF 自己的 base 命名空间，是所有设备都一样的；一旦进到 <config> 内部，命名空间立刻切换成某个 YANG 模块的 namespace，这部分才是设备特有的。调试时把「报错发生在哪一层命名空间」分清楚，能省掉一半时间——外层报错是协议用错了，内层报错是模型用错了。

两者并不互相绑死

  • 同一份 YANG 模型可以被多种协议承载：NETCONF 用 XML 编码（RFC 6241），RESTCONF 用 JSON 或 XML 编码（RFC 8040 + RFC 7951），gNMI 用 protobuf。换协议不用换模型——这正是"把数据模型独立出来"的最大红利。
  • NETCONF 理论上不强制用 YANG：RFC 6241 只规定了协议操作与消息格式，<config> 里装什么 XML 它并不关心；最早的 NETCONF（RFC 4741，2006）发布时 YANG 甚至还不存在（RFC 6020 是 2010 年）。但今天现实里没有任何一个严肃实现不用 YANG——没有 schema 就没有类型检查、没有自动生成代码、没有跨厂商一致性，NETCONF 会退化成一个"用 XML 包起来的私有 CLI"。
本篇的边界，先说清楚免得你找错地方。这一篇讲的是协议与语言本身：分层、报文、操作语义、datastore 模型、YANG 语法。想看怎么在真实工程里落地（SSH/TLS 怎么配、libnetconf2 怎么用、O-RAN O1 怎么接）去 NETCONF 工程实践；想看它和 SNMP / RESTCONF / gNMI 的横向取舍去 管理协议对比；想看 SSH / TLS 本身的原理去 TLS / SSH / 证书。
02

为什么需要 YANG

从 SNMP/CLI 的痛点说起

在 YANG 之前，网络设备管理有两大老办法，各有硬伤：

  • CLI（命令行）：人友好，但机器难解析、各厂商语法不同、无标准结构，自动化困难。
  • SNMP + MIB：有结构（MIB），但擅长"读监控"、不擅长"复杂配置"，事务性弱、写操作差。

网络自动化时代需要的是：结构化、强类型、有约束、跨厂商一致、机器可读、支持复杂配置和校验的数据模型。这正是 YANG 的设计目标。

YANG 让"配置"从"一堆命令字符串"变成"一棵有类型、有约束、可校验的结构化数据树"。厂商用 YANG 发布自己设备的模型，管理系统据此自动生成/校验配置——这是网络可编程化的地基。

把痛点落到一个具体任务上

抽象地说"CLI 不好自动化"没有说服力。换成一个再普通不过的运维任务：给 200 个接口把 MTU 从 1500 改成 9000，要求要么全成、要么全不成，改完能验证。三种方式的差别立刻就出来了：

环节CLI + expect 脚本SNMP SETNETCONF + YANG
怎么表达"接口 eth3 的 MTU"一串命令文本，各厂商语法不同一个 OID + 索引（ifMtu.3）模型路径 /interfaces/interface[name='eth3']/mtu，跨厂商一致
非法值怎么办设备回一行中文/英文报错，脚本靠正则猜返回 wrongValue，不告诉你合法范围模型里写着 range "68..9000"，客户端本地就能拦下，不用先打到设备
200 条改动的原子性没有。第 137 条失败时前 136 条已经生效只有单个 PDU 内的变量是原子的，跨 PDU 无事务写 candidate → validate → commit，一次原子提交
失败怎么回滚自己写反向脚本，且反向脚本本身也可能失败自己记录旧值再 SET 回去discard-changes，或 error-option=rollback-on-error
改完怎么确认再 show 一遍，解析文本再 GET 一遍get-config 拿回结构化数据，可直接与期望值做树比对
换个厂商的设备脚本基本重写私有 MIB 部分要重写标准模型部分不动，只处理 deviation 差异

生活类比：报销。CLI 像是手写便条交给财务——每个人格式都不一样，财务得逐张辨认字迹，写错了只能划掉重写，而且交上去就没法撤回。SNMP MIB 像是一本按编号排的电话簿——查号很快（读监控很在行），但你没法用它"下单"，更没法"下十单然后一起确认"。YANG + NETCONF 像是带校验规则的在线报销系统：字段类型是死的（金额填不了汉字）、必填项漏了当场提示、整单可以先存草稿、提交前能试算、提交是一次性的、驳回了整单退回不会只退一半。

这些需求不是 IETF 拍脑袋想的

值得知道的一段背景：NETCONF 与 YANG 的需求清单来自运营商本人。IAB 在 2002 年办过一次网络管理研讨会，会后的 RFC 3535 把运营商实际抱怨的问题整理成了一份需求列表，其中几条直接塑造了后来的设计：

  • 配置数据与状态数据必须能分开——运维想要"把设备 A 的配置原样搬到设备 B"，而计数器、链路状态这类东西搬过去毫无意义。这一条后来变成了 YANG 的 config true/false 和 NETCONF 的 <get-config> vs <get>。
  • 要有配置事务，而且最好能跨设备——变成了 candidate / commit / confirmed-commit。
  • 配置要能整体导出、整体恢复、能做文本 diff——变成了 <copy-config> 与"整棵树可序列化"的设计。
  • 要区分「谁下发的」与「设备实际在跑的」——这一条当时没做完，十几年后才由 NMDA（RFC 8342）的 intended / operational 补上（见第 6 章）。
面试里聊到"为什么不用 SNMP 做配置"，很多人只答"SNMP 写操作弱"。更有分量的回答是指出三个结构性缺陷：① 没有事务边界，SNMP 的原子性只覆盖单个 PDU 里的变量绑定列表，一次大配置必然拆成多个 PDU，中途失败就是半套配置；② 没有配置/状态之分，MIB 里 ifMtu（可写配置）和 ifInOctets（只读计数）平级摆着，导致"备份配置"这件事根本无从下手；③ SMIv2 的类型系统太弱，表达不了"这个字段只在另一个字段为 true 时才有意义"（YANG 的 when）或"这两个值不能同时配"（must），约束只能写在 DESCRIPTION 的自然语言里，机器读不了。至于"UDP 承载不适合大配置"只是表象，不是根因。详细的横向对比见 管理协议对比。
03

YANG：数据建模语言

看一个真实的 YANG 片段

YANG 用 container / list / leaf / leaf-list 等语句把数据组织成一棵树，并给每个字段定类型和约束。它的形态更像一门 IDL（接口定义语言）而不是配置文件格式：有类型系统、有命名空间、有 import、有版本、有可复用的片段，甚至有基于 XPath 的跨字段约束。下面先看一份麻雀虽小五脏俱全的完整模块，再逐块拆开讲。

一份完整的 YANG 模块（先通读，再逐段拆）

// ─────────── ① 模块头：身份、版本、依赖 ───────────
module example-interfaces {
  yang-version 1.1;                          // 不写默认是 1.0；用 1.1 特性必须显式声明
  namespace "urn:example:params:xml:ns:yang:example-interfaces";
  prefix exif;                               // 本模块内部以及被别人 import 时的短前缀

  import ietf-yang-types { prefix yang; }    // RFC 6991：counter64 / date-and-time 等
  import ietf-inet-types { prefix inet; }    // RFC 6991：ipv4-address / port-number 等

  organization "Kavin Tech Notes";
  description  "演示用的简化接口配置模型。";

  // ─────────── ② 版本历史：最新的放最上面 ───────────
  revision 2026-03-01 { description "新增 vlan-id 与 loopback 类型（向后兼容）。"; }
  revision 2025-06-15 { description "首版。"; }

  // ─────────── ③ feature：可选能力开关 ───────────
  feature vlan-support {
    description "设备支持在物理口上创建 VLAN 子接口。不支持的设备不会暴露 vlan-id。";
  }

  // ─────────── ④ identity：可扩展的枚举 ───────────
  identity interface-type { description "接口类型基类。"; }
  identity ethernet { base interface-type; }
  identity loopback { base interface-type; }

  // ─────────── ⑤ typedef：给类型起名字，带约束与默认值 ───────────
  typedef mtu-size {
    type uint16 { range "68..9216"; }
    units "bytes";
    default 1500;
    description "以太网 MTU。下界 68 来自 IPv4 最小重组缓冲的要求。";
  }

  // ─────────── ⑥ grouping：可复用的字段组合（本身不生成任何节点） ───────────
  grouping admin-state {
    leaf enabled     { type boolean; default true; }
    leaf description { type string { length "0..255"; } }
  }

  // ─────────── ⑦ 数据树主体 ───────────
  container interfaces {                     // 非 presence 容器：只是个分组，本身不携带信息
    description "接口配置与状态的根。";

    list interface {
      key    "name";                         // 主键，隐式 mandatory 且必须唯一
      unique "parent-interface vlan-id";     // 组合唯一约束：同一父口下 VLAN 不重复

      leaf name {
        type string { pattern "[a-zA-Z][a-zA-Z0-9./-]*"; }
      }
      leaf type {
        type identityref { base interface-type; }
        mandatory true;                      // 没有 default 的必填项
      }

      uses admin-state;                      // 把 grouping 里的两个 leaf 原地展开

      leaf mtu { type mtu-size; }            // 复用 typedef，连 default 1500 一起继承

      leaf-list ipv4-address {
        type inet:ipv4-address;              // 跨模块引用：前缀 inet 来自 import
        ordered-by user;                     // 顺序由客户端决定，不是系统排序
      }

      // ⑧ when + if-feature：这个节点「什么时候才存在」
      leaf vlan-id {
        if-feature vlan-support;             // 设备没声明这个 feature，整个节点不存在
        when "derived-from-or-self(../type, 'exif:ethernet')";
        type uint16 { range "1..4094"; }
      }
      leaf parent-interface {
        when "../vlan-id";
        type leafref { path "../../interface/name"; }   // 外键：必须指向已存在的接口
      }

      // ⑨ must：跨节点的语义约束，违反了 validate/commit 会失败
      must "not(vlan-id) or "
         + "mtu <= /exif:interfaces/exif:interface[exif:name = current()/exif:parent-interface]/exif:mtu" {
        error-message "VLAN 子接口的 MTU 不能大于父接口的 MTU。";
      }

      // ⑩ choice：互斥的几组配置，同一时刻只能存在一组
      choice bandwidth-spec {
        case fixed { leaf speed { type uint32; units "Mbps"; } }
        case auto  { leaf auto-negotiate { type empty; } }   // empty：存在与否即是信息
      }

      // ⑪ config false：状态数据，只读，get 能看到、get-config 看不到
      leaf oper-status {
        config false;
        type enumeration { enum up; enum down; enum testing; }
      }
      container statistics {
        config false;
        leaf in-octets   { type yang:counter64; }
        leaf out-octets  { type yang:counter64; }
        leaf last-change { type yang:date-and-time; }
      }

      // ⑫ action（YANG 1.1）：绑在具体接口上的操作，1.0 里做不到
      action reset-counters {
        output { leaf reset-time { type yang:date-and-time; } }
      }
    }
  }

  // ⑬ 顶层 rpc 与 notification
  rpc clear-all-counters {
    input  { leaf force { type boolean; default false; } }
    output { leaf cleared-count { type uint32; } }
  }
  notification link-state-change {
    leaf if-name   { type leafref { path "/exif:interfaces/exif:interface/exif:name"; } }
    leaf new-state { type string; }
  }
}
读 YANG 模块的顺序建议是 ⑦ → ⑤⑥ → ①：先看 container 里的数据树长什么样（这是你实际要下发的东西），碰到不认识的类型名再回头看 typedef / grouping，最后才关心 import 和 revision。反过来从第一行读起，很容易被一堆 identity 和 typedef 劝退，而它们其实只是"辅助定义"。pyang -f tree example-interfaces.yang 可以直接把整个模块打印成一棵树，比读源码快十倍。

节点四件套：container / list / leaf / leaf-list

语句相当于关键点常见误用
container结构体 / 目录默认是非 presence 容器：它存在与否不携带任何信息，只是给子节点做分组。加了 presence "..." 才变成"存在本身就是配置"（例如 <dhcp-relay/> 表示开启中继）把开关做成非 presence 容器——客户端删不掉它，因为它本来就不算数据
list数据库表必须有 key（config true 时），key 隐式 mandatory 且不可重复；可加 unique、min-elements / max-elements、ordered-by user|system用一个会变的字段做 key（比如 IP 地址）——改一次 key 等于删一条加一条，会把子树全清掉
leaf字段一个值，必须有 type；可有 default、mandatory、units（default 与 mandatory true 互斥）给 mandatory true 的 leaf 又写 default，编译器直接报错
leaf-list数组同类型的多个值。YANG 1.1 起允许 default（可给多个）需要"每项带多个属性"时还硬用 leaf-list——那应该是 list
choice / casetagged unionchoice 与 case 本身不出现在数据里，实例里只看得到某个 case 下的节点。设置另一个 case 的节点会自动删掉当前 case 的所有节点以为 choice 会在 XML 里生成一层元素——不会，它是纯 schema 概念
anydata / anyxmlany装"结构未知"的数据。anydata（1.1 新增）要求内容仍是合法的 YANG 数据树，anyxml 则是任意 XML拿它当逃生舱口塞私有配置——等于放弃了 YANG 的全部好处

类型系统：内置类型、typedef、以及三种"引用型"类型

YANG 的类型系统是它和 SNMP 的 SMIv2 拉开距离的地方。13 类内置类型加上四种约束语句，绝大多数字段都能表达得很精确，客户端拿到模型后可以在本地就把非法值拦下来，根本不用发到设备再等报错。

内置类型可加的约束说明与工程注意
int8/16/32/64、uint8/16/32/64rangerange 支持多段与 min/max：range "1..4094 | 4096..8191"
decimal64fraction-digits（必填 1–18）、range定点数，不是浮点。用它表达功率、经纬度，避免二进制浮点的舍入争议
stringlength、pattern（可多条，取交集）pattern 用的是 W3C XSD 正则，不是 POSIX ERE——它默认整串锚定，不需要写 ^...$，写了反而当字面量匹配
boolean—XML 里是 true/false 文本，JSON 里是原生布尔
enumerationenum（可指定 value）封闭集合，加一个新枚举值就是不兼容变更——老客户端不认识它
bitsbit（可指定 position）位标志集合。线上表示是空格分隔的名字，不是数字
binarylengthXML/JSON 里都编码成 base64。证书、密钥走这个类型
empty—没有值，存在与否就是全部信息。不能有 default，也不能出现在 leaf-list 里
union多个成员类型按声明顺序逐个尝试匹配，第一个匹配上的胜出——把 string 放在第一位会吃掉后面所有类型
leafrefpath（必填）、require-instance外键。默认 require-instance true：指向不存在的实例会校验失败
identityrefbase指向一个 identity。可扩展的枚举：别的模块能从你的 identity 派生新值，而不用改你的模块
instance-identifierrequire-instance一条指向数据树某个节点的 XPath 字符串，常用于告警里指明"哪个对象出的问题"
enumeration 与 identityref 的取舍是一个很能看出经验的点。两者在数据里长得很像（都是一个名字），但演进性质完全相反：enumeration 是封闭的，值集合钉死在定义它的模块里，加一个值就是 breaking change；identityref 是开放的，任何模块都能 import 你的基 identity 再派生新值，你的模块一个字节都不用改。所以经验规则是：值集合注定要被第三方扩展的（接口类型、加密算法、告警类别）一律用 identity；确实封闭的（up/down/testing、enabled/disabled）才用 enumeration。IETF 的 ietf-interfaces 把接口类型做成 identityref 而不是枚举，就是这个原因——厂商可以自己派生 my-vendor:custom-tunnel。

typedef 的价值不在少打几个字，而在把约束和语义集中到一处。上面模块里的 mtu-size 一旦定义好，所有用到 MTU 的地方自动带上 68..9216 的范围、bytes 的单位和 1500 的默认值；哪天设备支持 9600 了，改一行即可。反过来，如果在十个 leaf 里各写一遍 uint16 { range "68..9216"; }，改的时候一定会漏。

约束：must / when / mandatory / default / config

这五个语句最容易被混为一谈，但它们回答的是四个完全不同的问题：

语句回答的问题什么时候求值违反时的后果
when "XPath"这个节点存不存在？随时。条件为假时，该节点连同子树在数据树里根本不存在不算"违反"——服务器会自动删掉这个子树，不报错
must "XPath"这份数据合不合法？<validate> 与 <commit> 时（整棵树）返回 <rpc-error>，error-app-tag 默认是 must-violation，可用 error-message 自定义提示
mandatory true这个节点必须被填吗？校验时缺了就报 missing-element
default X没填的时候按什么算？读取与校验时不会报错。注意默认值不一定出现在 get-config 的回复里（见 with-defaults）
config false这是配置还是状态？编译期往 config false 节点写数据会被拒（invalid-value 或 unknown-element）
when 与 must 的差别是这一节最值得记的一条，也是现场最常见的"配了但没生效"来源。when 为假时服务器静默地把节点删掉——你 edit-config 下发了 vlan-id 100，因为 type 不是 ethernet，commit 成功了，回头 get-config 却发现 vlan-id 不见了，而且全程没有任何错误。must 则相反，它会明明白白地把 commit 打回来。所以：能用 must 表达的约束就不要用 when——前者失败可见，后者失败无声。when 只应该用在"这个节点在这种场景下确实不该存在"的场合（比如某个 feature 关掉时）。

config false 还有两条硬规则值得记住：① config false 的节点其所有子孙自动也是 config false，不能再翻回 true（配置树不可能长在状态树下面）；② config true 的 list 必须有 key，config false 的 list 可以没有（状态数据不需要被寻址修改）。第二条解释了为什么很多计数器表在模型里看不到主键。

复用与扩展：grouping / uses / augment / deviation

这四个语句解决的是"别重复写"和"别改别人的模块"两件事，但作用方向不同：

写在哪作用典型场景
grouping + uses自己的模块里（也可跨模块 uses 别人的）把一组节点定义一次、在多处原地展开。uses 内可用 refine 微调（改 default、加 mandatory、改 description）、也可用 augment 往展开结果里加节点地址族配置、认证参数这类在多个地方长得一样的字段块
augment自己的模块里，往别人的树上挂「我给标准模型加东西」。挂上去的节点属于你自己的命名空间，可带 when 做条件挂载厂商在 ietf-interfaces 的 interface 下加私有的 flow-control、storm-control
deviation单独的 deviation 模块里，声明设备的偏差「我这台设备做不到标准模型的这部分」。deviate not-supported / add / replace / delete设备只支持 MTU 到 1500，就 deviate replace { type uint16 { range "68..1500"; } }
feature + if-feature模块里定义，设备在运行时声明支持哪些「这块内容可选，看设备支不支持」。不支持时相关节点整体不存在同一份标准模型覆盖高低端两条产品线

用一句话区分最容易混的那两个：augment 是模型作者的加法，deviation 是设备实现者的减法（或修正）。augment 写在正常模块里、会进数据树、客户端可以正常使用；deviation 写在一份专门的 <vendor>-deviations.yang 里，它的唯一目的是诚实地告诉客户端「标准模型的这部分我对不上」，让客户端提前调整，而不是等下发失败再猜。

// ① augment：厂商往 IETF 标准接口模型上挂私有节点
module vendor-if-ext {
  yang-version 1.1;
  namespace "urn:vendor:if-ext";
  prefix vext;
  import ietf-interfaces { prefix if; }
  import iana-if-type    { prefix ianaift; }   // 用到别人的前缀就必须 import

  augment "/if:interfaces/if:interface" {
    when "if:type = 'ianaift:ethernetCsmacd'";   // 只挂在以太口上
    container storm-control {
      leaf broadcast-pps { type uint32; }
      leaf multicast-pps { type uint32; }
    }
  }
}

// ② deviation：这台设备的实际能力与标准模型的差异，单独一个模块
module vendor-if-deviations {
  yang-version 1.1;
  namespace "urn:vendor:if-deviations";
  prefix vdev;
  import ietf-interfaces { prefix if; }
  import iana-if-type    { prefix ianaift; }

  deviation "/if:interfaces/if:interface/if:link-up-down-trap-enable" {
    deviate not-supported;            // 这个节点我根本没实现，别下发
  }
  deviation "/if:interfaces/if:interface/if:description" {
    deviate replace { type string { length "0..63"; } }   // 标准允许更长，我只支持 63
  }
  deviation "/if:interfaces/if:interface/if:enabled" {
    deviate add { must "../if:type != 'ianaift:softwareLoopback' or . = 'true'"; }
  }
}
真实案例形态：照着 IETF 官网的 ietf-interfaces.yang 写代码，上设备就报错。现象是 edit-config 返回 unknown-element，或者干脆 commit 成功但字段没生效。根因几乎总是三选一：① 设备用的 revision 比你手上那份旧（或新），字段名/层级变了；② 设备发布了 deviation，你用的那个节点被 deviate not-supported 掉了；③ 相关 feature 没开，整棵子树在这台设备上不存在。正确做法是不要相信任何"标准模型"的本地副本，而是从设备本身把模型取回来：先读 ietf-yang-library（RFC 8525）拿到模块、revision、启用的 feature 与 deviation 三份清单，再用 RFC 6022 的 <get-schema> 把模块正文一个个下载下来，用这份"设备自述"去编译客户端。这一步做与不做，是集成一天搞定还是排查一周的分水岭。

module / submodule 与 revision：版本怎么演进

一个 YANG 模块大到几千行时会拆成 submodule。它和 import 不是一回事：

  • import：引用另一个模块。对方有自己的 namespace，引用时必须带前缀（inet:ipv4-address）。这是"跨模块协作"。
  • include + submodule + belongs-to：把同一个模块的定义拆到多个文件里。submodule 没有自己的 namespace 和 prefix，它借用主模块的；编译后等价于把内容原地粘回主模块。这是"单纯的文件切分"。
// main.yang
module example-interfaces {
  yang-version 1.1;
  namespace "urn:example:params:xml:ns:yang:example-interfaces";
  prefix exif;
  include example-interfaces-statistics;    // 把统计部分拆出去
  revision 2026-03-01;
}

// example-interfaces-statistics.yang
submodule example-interfaces-statistics {
  yang-version 1.1;
  belongs-to example-interfaces { prefix exif; }   // 借用主模块的前缀
  // 这里定义的节点，命名空间仍然是主模块的那个 URN
}

版本演进的规则（RFC 7950 第 11 节）比想象中严格，核心思想是：同一个模块名 + 同一个 namespace 的所有 revision，必须能让老客户端继续工作。允许与不允许的清单：

变更兼容？为什么
新增非必填节点（有 default 或可缺省）✅ 允许老客户端不发它，设备按默认值走
新增 mandatory true 的节点❌ 禁止老客户端下发的配置会突然变成非法
新增 enumeration 的枚举值 / bits 的位❌ 禁止老客户端不认识新值，解码会失败
放宽 range / length（值空间变超集）✅ 允许原来合法的值现在仍然合法
收紧 range / length / 加 pattern❌ 禁止原来合法的配置现在会被拒
删除节点、改名、改 key、改 config true↔false❌ 禁止直接把老配置打成废纸
把节点标为 status deprecated / obsolete✅ 允许这正是"想删但不能删"的正规退场通道
改 description / reference✅ 允许不影响数据

真要做不兼容变更，唯一正当的做法是换模块名 + 换 namespace（业界惯例是加版本后缀，例如 ietf-foo → ietf-foo-2），让新旧两份模型在设备上共存一段时间。偷偷在原模块里做不兼容改动、只是 bump 一个 revision 日期，是所有 NETCONF 集成事故里最难查的一类——客户端的 revision 检查会通过，运行时才在某个具体字段上炸。

YANG 1.0（RFC 6020）与 1.1（RFC 7950）

1.1 是 2016 年发布的修订版，不是推倒重来，而是补齐了 1.0 用起来发现缺的东西。判断一份模块是哪个版本只看一行：有 yang-version 1.1; 就是 1.1，没有这一行（或写着 1）就是 1.0。

NETCONF：操作与传输

基于 XML 的 RPC over 安全传输

NETCONF 是一套基于 XML 的 RPC 协议：客户端（管理端/SMO）发 <rpc>，服务端（设备）回 <rpc-reply>。RFC 6241 把它切成四层，这个分层不是文档编排上的装饰——它是「换一层不影响其它层」的解耦承诺：换传输（SSH → TLS）不动操作层，换模型（厂商私有 → IETF 标准）不动消息层。

四层模型：每层负责什么、由哪份 RFC 规定

层它决定什么它不决定什么换掉这一层的现实例子
Content字段名、层级、类型、约束、命名空间字段怎么被读写、走什么连接同一台设备既支持 ietf-interfaces 又支持厂商私有模型，协议层完全不变
Operations有哪些动词、每个动词的参数与语义、作用在哪个 datastore数据本身长什么样（那是 YANG 的事）NMDA 加了 <get-data> / <edit-data>（RFC 8526），消息层与传输层一个字节没改
MessagesRPC 的信封、message-id 的配对规则、通知怎么推、一条消息到哪里结束信封里装什么操作base:1.0 → base:1.1 换了分帧方式，操作层完全不受影响
Secure Transport认证、加密、完整性、连接可靠性与顺序任何 NETCONF 语义O-RAN 前传 M 平面用 TLS + 证书，而 O1 更多用 SSH；上面三层一模一样

值得注意的是传输层的要求是"能力"而不是"某个具体协议"：RFC 6241 只要求承载必须是面向连接、可靠有序、已认证、已加密的。SSH 是强制实现的那一个（RFC 6242），TLS 是可选替代（RFC 7589）。反过来说，UDP 这类无连接承载在 NETCONF 里从一开始就被排除了——因为消息层的 message-id 配对、分帧、以及 datastore 锁的生命周期全都建立在"会话"这个概念上，会话没了，锁的归属和事务的边界就无从谈起。SSH / TLS 本身的原理见 TLS / SSH / 证书，工程配置见 NETCONF 工程实践。

对照封装思想：NETCONF over SSH over TCP over IP over Ethernet——这与 eCPRI 的"薄封装、直接 over 以太网"形成鲜明对比。管理面要的是可靠、安全、有事务，为此付出的每层开销都是值得的；前传要的是确定性低时延，所以连 IP 层都省了。「时延预算决定协议栈厚度」这条判据在 O-RAN 的九个接口上一路适用（见 O-RAN 接口）。

:rollback-on-erroredit-config 可用 error-option=rollback-on-error出错只能 stop-on-error，失败点之前的改动已经落在 target 里
:confirmed-commit<commit> 支持 <confirmed/> + 超时自动回滚把自己配断网就只能派人去现场——远程配置的第一大风险
:notification支持 <create-subscription> 订阅事件流（RFC 5277）状态变化只能靠轮询 <get>，实时性与开销都差一档
:interleave订阅通知的同时还能在这条会话上发别的 RPC订阅之后这条会话就"只收不发"了，得另开一条会话做配置
:xpath<filter type="xpath">只能用 subtree filter，表达不了"筛选 mtu 大于 1500 的接口"这类条件
:url<config> 可换成 <url>，从 FTP/SFTP/file 取配置整机配置只能塞进 RPC 消息体传输
:with-defaults可指定回复里"要不要带默认值"（RFC 6243）不同设备对"默认值出不出现在 get-config 里"的行为不一致，配置比对会大量误报
:yang-library模块清单改由 ietf-yang-library 数据提供，含 feature 与 deviation只能读 hello 里那一长串 ?module=，且它不含 deviation 的完整信息
集成一台新设备时，第一件事永远是把它的 <hello> 完整存档。这一坨文本回答了"这台设备到底能做什么"的九成问题：能不能直接写 running、有没有 candidate、能不能 confirmed-commit、支不支持 xpath 过滤、模型是哪个 revision、开了哪些 feature。后面每一次"这个操作为什么不行"的排查，都应该先回到这份存档看一眼，而不是去翻 RFC。反过来，一个只在自己的 mock 服务器上测过的客户端，通常会默认所有能力都在——上真设备第一天就会被 operation-not-supported 教做人。

消息分帧：为什么 ]]>]]> 被 chunked framing 取代

SSH / TLS 给的是一条字节流，NETCONF 需要在上面切出一条条独立的 XML 消息。这就是分帧问题——和 TCP 上跑任何应用协议时遇到的粘包/半包是同一回事。NETCONF 前后用过两套方案：

# ① end-of-message framing（RFC 6242 §4.1）——base:1.0 时代
# 规则：一条消息之后追加 6 个字节的分隔符 ]]>]]>

<?xml version="1.0" encoding="UTF-8"?>
<rpc message-id="105" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <close-session/>
</rpc>
]]>]]>

# 字节层面：  ... 3C 2F 72 70 63 3E 0A   5D 5D 3E 5D 5D 3E
#             ^ "</rpc>\n"              ^ "]]>]]>"  ← 只能靠逐字节扫描找到它
# ② chunked framing（RFC 6242 §4.2）——双方都声明 base:1.1 时启用
# 语法：  chunk      = LF '#' chunk-size LF chunk-data
#         结束标记   = LF '#' '#' LF
#         chunk-size = 十进制，1 .. 4294967295（字节数，不含 header 本身）

\n#4\n
<rpc
\n#18\n
 message-id="102"\n
\n#79\n
    xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <close-session/>
</rpc>
\n##\n

# 关键：一条消息可以拆成任意多个 chunk，chunk 边界与 XML 结构【毫无关系】——
# 上例第一个 chunk 只有 4 个字节 "<rpc"，把一个标签都切断了，这完全合法。
# 接收端必须先按 chunk 拼出完整字节流，【再】交给 XML 解析器，不能边拆边解析。
end-of-message（]]>]]>）chunked framing
启用条件默认；只要有一方不支持 base:1.1双方 hello 里都出现 base:1.1
怎么找边界逐字节扫描 6 字节序列读定长 header 拿到长度，直接 read(n)
内容能不能包含任意字节不能——出现 ]]>]]> 就废，而且没有转义机制能——长度前缀天然对内容透明
能否预知消息大小不能，读完才知道每个 chunk 的大小提前已知
超大消息防护只能边读边累计，发现超限时已经收了一大堆读到 chunk header 就能判断并拒绝
实现复杂度看着简单，但错一次就永久失步稍复杂，出错可定位（chunk-size 非法可立即报 malformed-message）
这是 NETCONF 实现者踩得最多的一个坑，值得单独说清楚：<hello> 消息本身永远用 ]]>]]> 分帧。原因很直白——分帧方式是靠 hello 协商出来的，协商完成之前双方还不知道该用哪种，所以 RFC 6242 规定：hello 交换固定用 end-of-message framing，从 hello 之后的第一条消息开始才切换到 chunked（前提是双方都声明了 base:1.1）。自己写客户端时最典型的两种翻车姿势：① 一上来就用 chunked 发 hello，服务端读到 \n#4\n 当成 XML 内容，报 malformed-message 或直接断连；② hello 之后忘了切换，继续用 ]]>]]> 发第一条 <rpc>，服务端在等 chunk header，于是会话静默挂死——不报错，就是没有任何回复，比报错还难查。

那么，]]>]]> 到底错在哪里？根本问题是它把"分隔符"和"数据"放进了同一个字节空间，却没有提供转义手段。RFC 6241 只能靠一条纪律来兜底：内容里禁止出现这个序列。可 NETCONF 的内容是任意 YANG 数据——一个 description 字符串、一段脚本、一份 base64 之外的私有文本、甚至一个 XML 注释，都有可能凑出这六个字节。而它一旦出现，后果不是丢一条消息，是整条会话此后所有消息的边界全部错位：接收端在半截 XML 处切了一刀，之后每一条消息都是上一条的尾巴加下一条的头。这类故障的现场表现是"跑了几个月好好的，某天配了一条带特殊字符的描述之后，这台设备的管理通道就再也起不来了"。

长度前缀把这个问题从根上消掉了：接收端不需要理解内容的任何一个字节，只需要数够 N 个。顺带还得到三个好处——可以预分配缓冲、可以在读到 header 时就拒绝超大消息（DoS 防护）、以及大响应可以流式分块发送而不必先在内存里拼成一整块。这是所有二进制协议早就学会的一课（HTTP/1.1 的 Content-Length 与 Transfer-Encoding: chunked、SCTP 的消息边界都是同一个道理），NETCONF 只是在 2011 年的 RFC 6242 里补上了这一课。

真实案例形态：换了个 NETCONF 客户端库之后，同一台设备"偶尔"回不了大响应。小的 get-config 一切正常，一旦请求整机配置就超时。抓包看到设备确实在发数据，但客户端始终不认为消息结束了。根因是客户端实现只处理了"一条消息 = 一个 chunk"的简单情况，遇到设备把大响应切成多个 chunk 时，读完第一个 chunk 就去找结束标记 \n##\n，没找到于是一直等。判读要点：分帧问题的典型症状是"小的能过、大的挂住"，而且挂住时连接还活着、没有任何错误——因为在协议看来双方都在正常等待。排查入口是在传输层把原始字节 dump 出来数 chunk 个数，而不是去看 XML 解析日志（那一层根本没收到东西）。

看真实报文

RFC 6241 定义的操作只有九个基础动词加两个会话管理动词，数量比想象中少得多。先看全表，再挑最容易出事的展开。

<get-config>：读配置

先把最常被问的一对辨析清楚：

<get-config><get>
返回什么只有 config true 的节点config true + config false，即配置与状态混在一棵树里
能选库吗能：running / candidate / startup / url不能，固定读 running
典型用途配置备份、配置比对、"我下发的东西存进去没有"看运行状态、读计数器、"这个口现在到底 up 没 up"
幂等与可回灌结果可以原样 edit-config 回去不行——里面混着只读节点，回灌必然报错
开销整机配置通常几百 KB 到几 MB可能大一个数量级（计数器是逐接口逐队列的），不加 filter 直接 <get/> 是压测级操作

"配置与状态可分离"是 RFC 3535 那份运营商需求清单里的第一条，config 标志 + 这两个操作就是它的落地。能做配置备份与灾难恢复，全靠 get-config 的输出是"干净可回灌"的——这一点 SNMP 从来没做到过。

<!-- ① subtree filter：用「数据的形状」描述你要什么，最通用，所有设备都支持 -->
<rpc message-id="1" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get-config>
    <source><running/></source>
    <filter type="subtree">
      <interfaces xmlns="urn:example:params:xml:ns:yang:example-interfaces">
        <interface>
          <name>eth0</name>   <!-- 内容匹配节点：带了值 ⇒ 按这个值筛 -->
          <mtu/>               <!-- 选择节点：空元素 ⇒ 我只要这个字段 -->
        </interface>
      </interfaces>
    </filter>
  </get-config>
</rpc>

<!-- 回复 -->
<rpc-reply message-id="1" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <data>
    <interfaces xmlns="urn:example:params:xml:ns:yang:example-interfaces">
      <interface>
        <name>eth0</name>    <!-- key 总是会被带回来，即使你没选它 -->
        <mtu>9000</mtu>
      </interface>
    </interfaces>
  </data>
</rpc-reply>
<!-- ② XPath filter：能表达条件，但需要设备声明 :xpath capability -->
<rpc message-id="2" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get-config>
    <source><running/></source>
    <filter type="xpath"
            xmlns:exif="urn:example:params:xml:ns:yang:example-interfaces"
            select="/exif:interfaces/exif:interface[exif:mtu &gt; 1500]/exif:name"/>
  </get-config>
</rpc>

<!-- ③ <get>：注意【没有 source】，且能拿到 config false 的状态节点 -->
<rpc message-id="3" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get>
    <filter type="subtree">
      <interfaces xmlns="urn:example:params:xml:ns:yang:example-interfaces">
        <interface>
          <name>eth0</name>
          <oper-status/>    <!-- config false：get-config 里【永远】拿不到 -->
          <statistics/>
        </interface>
      </interfaces>
    </filter>
  </get>
</rpc>
subtree filter 最反直觉的一点：写错了不报错，只是返回空。命名空间打错一个字母、模块 revision 换了导致节点改名、或者请求了一个被 deviate not-supported 掉的节点——这些情况下服务端的行为都是「这个过滤器什么都没匹配上」，于是老老实实回一个空的 <data/>，完全符合规范，没有任何错误。所以「查不到数据」这个现象里，「设备上真没有」和「你问错了」是分不出来的。判读方法：先发一个不带 filter 的 get-config（或只到顶层容器），确认那棵子树确实存在、命名空间确实是你以为的那个，再逐层往下收窄。这个习惯能省掉大量"设备是不是有问题"的无谓争论。

<edit-config>：改配置

整篇 NETCONF 里最容易出事的就是这一个 RPC。原因不在于它复杂，而在于它有两套互相作用的开关：每个节点上可以带 operation 属性，整条 RPC 又有一个 default-operation；再加上 test-option 与 error-option，组合出来的语义空间足够让人踩上好几年。先看一个把这些开关都用上的完整请求：

<rpc message-id="10" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <edit-config>
    <target><candidate/></target>

    <default-operation>none</default-operation>      <!-- 没标 operation 的节点纯导航 -->
    <test-option>test-then-set</test-option>         <!-- 先校验，通过了才写 -->
    <error-option>rollback-on-error</error-option>   <!-- 出错整条撤回 -->

    <!-- operation 属性属于 NETCONF base 命名空间，【必须带前缀】 -->
    <config xmlns:nc="urn:ietf:params:xml:ns:netconf:base:1.0">
      <interfaces xmlns="urn:example:params:xml:ns:yang:example-interfaces"
                  xmlns:exif="urn:example:params:xml:ns:yang:example-interfaces">

        <interface nc:operation="merge">      <!-- 只改 mtu，其它字段原样保留 -->
          <name>eth0</name>
          <mtu>9000</mtu>
        </interface>

        <interface nc:operation="create">     <!-- 已存在则报 data-exists -->
          <name>eth1</name>
          <type>exif:ethernet</type>
          <mtu>1500</mtu>
        </interface>

        <interface nc:operation="delete">     <!-- 不存在则报 data-missing -->
          <name>eth2</name>                  <!-- 删 list 条目只需给 key -->
        </interface>

        <interface nc:operation="replace">    <!-- ⚠ 这条 interface 下【没列出的字段全部消失】 -->
          <name>eth3</name>
          <type>exif:ethernet</type>
          <mtu>1500</mtu>
        </interface>

        <interface>
          <name>eth4</name>
          <ipv4-address nc:operation="remove">10.0.0.9</ipv4-address>  <!-- 不存在也不报错 -->
        </interface>
      </interfaces>
    </config>
  </edit-config>
</rpc>

<!-- 成功：-->
<rpc-reply message-id="10" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0"><ok/></rpc-reply>
第一个坑就在 xmlns:nc 上。operation 属性属于 NETCONF base 命名空间，而它所在的元素在模型的命名空间里。XML 的规则是：无前缀的属性不属于任何命名空间（它不会像元素那样继承默认 xmlns）。所以写成 <interface operation="delete"> 是错的——严格的服务端会报 unknown-attribute，宽松的服务端则直接把它当成一个不认识的属性忽略掉，于是你的 delete 变成了默认的 merge：你想删一个接口，结果只是把它的 key 又写了一遍，commit 返回 <ok/>，接口纹丝不动。这是"操作成功但什么都没发生"最常见的单一原因。

operation 属性：五个值，五种语义

operation目标已存在时目标不存在时会不会删掉"没列出的东西"典型用途
merge
（默认）		逐层合并：列出的 leaf 覆盖值，未列出的保留创建不会——merge 只增不减日常增量改配置。90% 的场景用它
replace整棵子树被替换：未列出的子节点全部删除创建会，仅限该节点的子树内「把这个接口配成我说的这个样子」——幂等下发的正确姿势
create❌ 报 data-exists创建不会要求"必须是新建"的场景，用报错来防止误覆盖
delete删除❌ 报 data-missing—要求"必须存在"的删除，用报错来发现状态不一致
remove删除静默成功，不报错—幂等清理。批量脚本里几乎总该用它而不是 delete
delete 与 remove 的取舍，本质是"你要不要用报错来做一致性检查"。remove 是 RFC 6241（2011）才加进来的，RFC 4741 时代只有 delete——所以很老的设备可能不认识 remove，这是个需要在 hello 之外单独试探的兼容点。选择规则：幂等脚本（"确保这条配置不存在"）用 remove，重跑一百遍结果都一样；一次性运维动作（"把这个用户删掉"）用 delete，因为如果它已经不在了，说明你对设备状态的认知出了偏差，这时候报错是好事，静默成功反而会把问题藏起来。同理，create 与 merge 的取舍也是这个逻辑的镜像。

还有一条容易忽略的语义：replace 的作用范围是"带这个属性的那个节点的子树"，不是整个库。上例里 <interface nc:operation="replace"> 只会重塑 eth3 这一条，eth0/eth1 毫发无损。这与下一节的 <default-operation>replace</default-operation> 是完全不同的两件事，名字一样，威力差了几个数量级。

default-operation / test-option / error-option

default-operation没标 operation 的节点怎么处理危险度什么时候用
merge
（默认值）		按 merge 处理：列出的写进去，没列出的不动低绝大多数增量修改。缺点是它永远删不掉东西——想删必须显式标 delete/remove
replace⚠ <config> 的内容完整替换整个目标 datastore。凡是没出现在这次请求里的配置，一律删除。极高只有一个正当用途：把一份完整的配置备份灌回去。任何"我只是想改个 MTU"的场景用它都是灾难
none什么都不做，这些节点纯粹作为定位路径存在；只有显式带 operation 的节点才生效低，且最精确外科手术式的改动。特别是删除——避免"为了删一个叶子，反而把它的父层级凭空创建出来"
default-operation=replace 是这整篇里最危险的一个字段，没有之一。它的语义不是"替换你写的这部分"，而是"用你这次发来的 <config> 替换掉整个 datastore"。想象一下：你只想改 eth0 的 MTU，请求体里就写了一个接口，default-operation 手滑填了 replace——commit 之后设备上只剩下 eth0 这一个接口，路由、ACL、用户、SNMP 团体字、其它 200 个接口，全部消失。而且这个操作完全合法，设备会老老实实回一个 <ok/>。防护措施只有三条，缺一不可：① 客户端代码里把 replace 设成需要显式开关才能用的"危险模式"，不要让它成为某个封装函数的可选参数；② 永远先在 candidate 上做，commit 之前用 get-config candidate 把结果整棵拉回来看一眼；③ 真要用，就配 confirmed-commit（见第 6 章），给自己留一条退路。

none 值得单独说一句它存在的理由。假设你要删掉 /interfaces/interface[name='eth2']/description。如果用默认的 merge，请求里的 <interfaces> 和 <interface><name>eth2</name> 这两层本身就是"要被合并进去的配置"——万一 eth2 其实不存在，你这一发就顺手把它创建出来了，然后删掉它下面一个本来就没有的字段。用 none 就不会：这两层只是路径，RFC 6241 还特意规定，如果 <config> 里的层级在目标库里根本不存在，服务端返回 data-missing——正好把"我对设备状态的假设错了"这件事暴露出来。

test-option行为备注
test-then-set
（默认）		先跑一遍校验，通过了才真正写入安全默认值。代价是校验一次、写入一次，大配置下耗时翻倍
set不校验，直接写只在"上游已经校验过、且追求速度"时用。写进 candidate 的非法数据会在 commit 时才爆
test-only只校验，绝不写入需要 :validate:1.1。做「预检 / dry-run」的正规手段，比自己实现一套本地校验靠谱
error-option出错时失败点之前的改动需要
stop-on-error
（默认）		立即停止处理，返回 <rpc-error>留在 target 里——这就是"半套配置"的来源—
continue-on-error记录错误、继续处理后面的内容，最后统一回错能成功的都生效了—
rollback-on-error停止处理，并把 target 恢复到本次 edit-config 开始之前的完整状态全部撤销，单条 RPC 变成原子操作:rollback-on-error
rollback-on-error 是"没有 candidate 的设备"唯一的原子性来源，这个点很值得记。它的边界要说准：它只覆盖一条 edit-config RPC 的范围，不是一个跨多条 RPC 的事务。如果你的变更需要三次 edit-config，那第二次成功、第三次失败时，第一二次的改动照样留在设备上——rollback-on-error 帮不了你。真正的多步事务只能靠 candidate + commit。所以工程结论是：设备有 candidate 就用 candidate；没有 candidate，就想办法把整批改动塞进一条 edit-config，再配上 rollback-on-error。把改动拆成很多小的 edit-config"方便调试"，恰恰是在放弃仅有的那点原子性。

lock / unlock / validate / copy-config

<lock> 锁的是整个 datastore，不是某个子树（子树级的部分锁是 RFC 5717 的可选扩展，现网支持度不高）。三条规范里明确写死、但很多人不知道的规则：

  • 已被任何会话（或任何其它管理实体，比如 CLI 用户）持有时，锁不予授予，返回 lock-denied，并在 <error-info> 里带上持有者的 <session-id>。这个 session-id 就是你决定要不要 <kill-session> 时的依据。
  • 目标是 candidate 且它已经有未提交的改动时，锁不予授予。这条设计得很妙——它防的正是"你锁上 candidate，却发现里面躺着别人半小时前写了一半又忘了的东西"。
  • 目标是 running 且另一个会话正在进行确认式提交（confirmed commit）时，锁不予授予。因为那个 commit 随时可能超时回滚，此刻 running 的内容不稳定。

锁在 <unlock> 时释放，或者在会话终止时由服务端自动释放。后半句是关键——它意味着锁的生命周期挂在 TCP 连接上，而 TCP 连接的死亡未必及时被发现（见第 7 章「锁没释放」那一节）。

<rpc message-id="20"><lock><target><candidate/></target></lock></rpc>
<rpc message-id="21"><discard-changes/></rpc>      <!-- 清掉前人可能留下的残渣 -->
<rpc message-id="22"><edit-config>…</edit-config></rpc>
<rpc message-id="23"><validate><source><candidate/></source></validate></rpc>
<rpc message-id="24"><commit/></rpc>
<rpc message-id="25"><unlock><target><candidate/></target></unlock></rpc>

<!-- 拿不到锁时的响应：error-info 告诉你锁在谁手上 -->
<rpc-reply message-id="20" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <rpc-error>
    <error-type>protocol</error-type>
    <error-tag>lock-denied</error-tag>
    <error-severity>error</error-severity>
    <error-message>Lock failed, lock is already held</error-message>
    <error-info><session-id>4198</session-id></error-info>
  </rpc-error>
</rpc-reply>

<!-- 把 running 存成开机配置：commit 【不会】自动做这一步 -->
<rpc message-id="30" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <copy-config>
    <target><startup/></target>
    <source><running/></source>
  </copy-config>
</rpc>
「commit 了就会一直生效」是个非常昂贵的误会。<commit> 把 candidate 提交到 running，而 running 在多数设备上是内存里的运行态。设备支持 :startup 时，你必须再显式做一次 copy-config running → startup，配置才能扛过一次重启。现场表现就是那句经典的"改完好好的，机房断电重启之后全变回去了"。反过来，有些设备不声明 :startup——它们的 running 本身就是持久化的，多做一次 copy-config 反而会报 invalid-value。所以这一步必须由 hello 里有没有 :startup 来决定，不能写死在脚本里。

<rpc-error>：失败长什么样

一条 <rpc-reply> 要么带 <ok/> 或 <data>，要么带一个或多个 <rpc-error>。读懂 error-tag 基本就能定位到问题类别，比读 error-message 里那句厂商自由发挥的英文靠谱得多：

error-tag含义八成是你哪里错了
unknown-namespace / unknown-element命名空间或元素设备不认识模型 revision 对不上、命名空间打错、或该节点被 deviate not-supported
unknown-attribute属性不认识十有八九是 operation 忘了带 nc: 前缀
missing-element缺必填节点漏了 mandatory true 的 leaf，或漏了 list 的 key
bad-element / invalid-value值不合法越界、不匹配 pattern、枚举值不认识、往 config false 节点写数据
data-existscreate 时目标已存在你以为是新建，实际上设备上已经有了
data-missingdelete 时目标不存在；或 default-operation=none 时路径层级不存在对设备当前状态的假设错了。想幂等就改用 remove
operation-not-supported这个操作我不支持没先看 hello 的 capability 列表
lock-denied拿不到锁看 error-info 里的 session-id；可能是别人的僵尸会话
in-use资源正被占用典型如"这个接口正被某业务引用，不能删"
access-denied权限不足NACM（RFC 8341）规则挡下了。注意 NACM 也可以配成"隐藏"而不是"拒绝"，那时你看到的是空数据而不是这个错
resource-denied / too-big设备顶不住一次发太多，拆批
rollback-failed回滚本身失败了最坏的情况：设备现在处于既非改前也非改后的中间态，必须人工介入
malformed-message消息解析不了分帧错了（见第 4 章的消息分帧）、XML 不合法、或尖括号没转义

<error-path> 是排查时最有价值的字段：它给出一条指到出错节点的 XPath，包括 list 的 key 谓词，能直接告诉你"200 个接口里是第几个出的问题"。可惜不是所有实现都填得完整——填了的，先看它；没填的，只能配合 continue-on-error 二分法定位。

06

Datastore 与通知

配置的"三个抽屉" + 主动上报

running

当前正在生效的配置。唯一必选的库，每台 NETCONF 设备都有。能不能直接写它，取决于 :writable-running。

candidate

草稿：先改这里，commit 后才生效。可选（:candidate）。默认是全设备共享的一份，不是每会话一份——这是最大的坑。

startup

开机加载的配置（掉电保存）。可选（:startup）。commit 不会自动更新它，要显式 copy-config。

为什么要 candidate + commit？因为复杂配置往往要"一批改动一起生效"，中途半套配置可能让设备异常。candidate 让你先改草稿、校验无误再原子提交；还可配合 confirmed-commit（超时未确认自动回滚），避免把自己"配断网"。

完整的事务流程：从编辑到落盘

一次规范的变更由六步组成，每一步都在防一类具体的事故：

步操作它防住了什么省掉它的后果
1<lock><candidate/>别人同时在改同一份草稿你 commit 的时候，把别人写了一半的东西一起提交上去了
2<discard-changes/>草稿里躺着前一个会话留下的残渣同上，而且更隐蔽——残渣可能是几小时前留下的
3<edit-config> ×N——
4<validate><source><candidate/>跨节点约束（must / leafref / unique）违规错误推迟到 commit 时才暴露，而 commit 的失败处理比 validate 复杂得多
5<commit>（建议带 <confirmed/>）配置本身合法，但会把管理通道切断设备失联，只能派人去现场接串口
6<unlock> + 视情况 copy-config → startup锁泄漏；重启后配置回退别人再也拿不到锁；断电一次全白改
candidate 默认是「整台设备共享一份」，不是「每个会话一份」——这条几乎所有人第一次都会想错。它的直接后果是：会话 A 往 candidate 里写了几条改动就去开会了，会话 B 进来接着写自己的，然后 B 发了一个 <commit>——A 和 B 的改动被一起提交到 running 了，而 B 完全不知道自己捎带了什么。这不是 bug，是 RFC 6241 定义的行为。防护就是第 1、2 两步：先 lock candidate，紧接着 discard-changes。规范还很贴心地加了一条配套规则：candidate 里如果已经有未提交的改动，lock 会被拒绝——所以你在第 1 步就能发现"有人在里面"，而不是等 commit 之后才发现多提交了东西。至于 discard-changes 为什么要在 lock 之后：拿到锁之前清理，清完立刻可能又被别人写进去。

confirmed-commit：给远程配置留一条退路

远程配置最恐怖的场景不是"配错了"，而是"配错的那一下正好把你自己连进来的这条路切断了"——改错管理口 IP、错误的 ACL 把自己拒之门外、路由改崩、VLAN 划错。这时候设备工作得好好的，只是你再也够不着它，除非有人开车去机房插串口线。confirmed-commit 就是为这一类事故设计的。

<!-- ① 确认式提交：先生效，但给自己压一个 300 秒的死亡倒计时 -->
<rpc message-id="40" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <commit>
    <confirmed/>
    <confirm-timeout>300</confirm-timeout>   <!-- 不写的话默认 600 秒 -->
    <persist>change-ticket-8842</persist>     <!-- 可选：让它扛过会话断开 -->
  </commit>
</rpc>

<!-- ② 这 300 秒里你要做的事：验证管理通道还通、业务还正常 -->
<!--    比如再发一个 get 看看，或者从别的路径 ping 一下 -->

<!-- ③ 确认：再发一个 commit，倒计时解除，配置永久生效 -->
<rpc message-id="41" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <commit><persist-id>change-ticket-8842</persist-id></commit>
</rpc>

<!-- ③' 或者：发现不对，主动立刻回滚，不用干等超时 -->
<rpc message-id="42" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <cancel-commit><persist-id>change-ticket-8842</persist-id></cancel-commit>
</rpc>

<!-- ③'' 或者：什么都不做。300 秒后设备自动把 running 还原成提交前的样子。 -->
<!--      「什么都不做」是【安全】的那一侧，这才是这个机制的精髓。 -->
参数 / 行为说明
<confirmed/>标记这是一次待确认的提交。配置立即生效，但带着一个回滚定时器
<confirm-timeout>秒数，默认 600。太短来不及验证，太长则故障窗口拉大——变更窗口里 120–300 秒是常见取值
确认动作再发一个 <commit> 即可。若这个确认 commit 自己也带 <confirmed/>，则重置倒计时——可以用来"续期"，边验证边延长
<persist>（:1.1）给这次确认式提交起个名字。没有它，会话一断就立即回滚；有了它，即使 SSH 连接掉了，倒计时照常走，你可以重新连上来、甚至换一条会话去确认
<persist-id>在别的会话里确认或取消时，用它指明是哪一次
<cancel-commit>（:1.1）不等超时，立即回滚
期间的限制确认式提交进行中时，其它会话无法 lock running——因为此刻 running 的内容随时可能变回去
<persist> 加不加，是这个机制"能不能真的救你"的分水岭，值得想清楚。不带 persist 时，规范的行为是会话一终止就立即回滚。听起来很安全——"我被踢下线了，说明配置有问题，赶紧回滚"——但现实中最常见的场景恰恰相反：你改的就是管理网的配置，改完管理链路必然会短暂抖一下，SSH 会话被断开。这时候不带 persist 的行为是"立即回滚"，于是一次本来会成功的变更被判了死刑，而且你还得从头再来一遍。带上 persist 之后，会话断了不要紧，倒计时继续走，你重连上来发一个带 persist-id 的 commit 就确认了；真连不上，300 秒后它自己回滚。两种失败都被覆盖，这才是完整的。另外别忘了：RFC 6241 规定 :confirmed-commit:1.1 只能在同时声明 :candidate 的设备上宣告——没有草稿库的设备，标准里就没有这个安全网。

没有 candidate 的设备怎么办

相当一部分设备（尤其是嵌入式网元、白盒设备、以及一些早期实现）只声明 :writable-running 而没有 :candidate。这意味着你失去了三样东西：多步事务、提交前 review、以及标准的 confirmed-commit。按重要性排序的替代方案：

  • ① 把整批改动塞进「一条」edit-config，配 error-option=rollback-on-error。这是唯一还剩下的原子性来源。注意这与"为了好调试而拆成多条小 RPC"的直觉是相反的——拆开就等于放弃原子性。规模大到一条 RPC 装不下时，退而求其次是按"业务上可独立回滚的单元"分批，而不是按字段分批。
  • ② 先 lock running，改完再 unlock。没有 candidate，running 就是你的工作区，锁的窗口从"编辑期间"扩大到"整个变更期间"，对别人的影响更大——所以更要控制变更时长。
  • ③ 用 test-option=test-only 做 dry-run。设备声明 :validate:1.1 时，可以先发一份 test-only 的 edit-config，把 must / leafref / 类型错误全筛一遍，再发真正的那一发。这近似地补回了"提交前 review"。
  • ④ 变更前后各做一次全量 get-config，自己算 diff。既是回滚素材（真出事就把改前那份用 copy-config 灌回去），也是"改动是否符合预期"的证据。这一步应该是自动化的一部分，而不是出事时才想起来。
  • ⑤ 自建"确认窗口"。标准的 confirmed-commit 用不了，但可以在客户端侧实现：改完启动一个定时器 + 一个探活（从另一条路径 ping 管理口 / 发个 <get>），超时未通过就自动用第 ④ 步的备份灌回去。这个方案的致命弱点必须认清：它依赖客户端还活着、且到设备的路还通。而 confirmed-commit 的回滚逻辑跑在设备自己身上，恰恰不依赖这两点——这就是为什么它无可替代。
许多厂商在标准之外提供了等价能力（各种 rollback timer / commit confirmed / 配置归档回滚）。能用当然要用，但要在设计上把它隔离成一个可插拔的适配层，不要让"某厂商有这个私有 RPC"的假设渗透进主流程——否则你的自动化系统就和这一家绑死了，而"不被单一厂商绑死"正是当初选 NETCONF/YANG 的初衷。

NMDA：intended 与 operational

传统三库有一个从 2003 年就被提出、却拖到 2018 年才补上的缺口：你无法区分"我要求的配置"和"设备实际在跑的配置"。举几个具体的例子——

  • 你给一块还没插上的板卡配了接口：配置在 running 里躺得好好的，设备上却根本没有这个口。
  • 设备自己生成了一些配置（管理口的默认地址、自动发现的邻居、系统预置的 VRF）：它们在跑，但不在 running 里。
  • 某个 leaf 的值来自 YANG 的 default：running 里看不到它，但设备确实在按这个值工作。
  • 配置正在生效的过程中（几百个接口逐个下发）：running 已经是新的，硬件还是旧的。

在 NMDA 之前，<get> 返回的是"running 配置 + 状态数据"的拼盘，上面这四种情况全都表达不出来。RFC 8342 把 datastore 这个概念本身重新定义了一遍，加了两个只读的库：

datastore可写内容回答的问题
candidate / running / startup是客户端下发的配置（config true）「我提交了什么」
<intended>否running 经过"配置变换"（模板展开、失活配置剔除等）之后的结果，且必须是有效的「我打算让它变成什么样」
<operational>否已经生效的配置 + 系统自建配置 + 学到的数据 + 生效的默认值 + 全部状态数据（config false）「它现在实际是什么样」

配套的协议扩展在 RFC 8526：新增 <get-data> 与 <edit-data>，带一个 datastore 参数，于是"读哪个库"从"用哪个 RPC"变成了"填哪个参数"。<get-data> 还支持 with-origin，让每个 operational 里的值都标注它的来源（来自 intended、系统生成、学习得到、还是默认值）——排查"这个值到底是谁配的"时，这一个标注抵得上半天翻日志。

面试里能把 NMDA 的价值用一句话说清楚，是很强的信号：「它把『配置是否真的生效』从一个靠猜的问题，变成了一个可以直接查询的问题——比较 intended 与 operational 的差集就是答案。」在这之前，配置一致性校验只能做成"把 running 拉回来和我的期望比对"，而这只验证了设备记住了我的话，完全没有验证设备做到了我的话。O-RAN、大规模数据中心自动化这些场景里，"下发成功但没生效"的静默故障占比很高，NMDA 是标准侧对它的正面回应。要补一句现实：NMDA 的落地进度参差不齐，很多在网设备仍是传统三库模型，客户端要能同时兼容两种（看 hello 里有没有 :yang-library:1.1、以及设备支不支持 <get-data>）。

Notification：设备主动上报

<!-- ① 客户端订阅事件流（RFC 5277，需要 :notification capability） -->
<rpc message-id="50" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <create-subscription xmlns="urn:ietf:params:xml:ns:netconf:notification:1.0">
    <stream>NETCONF</stream>      <!-- 默认流；设备可自定义别的流 -->
    <filter type="subtree">
      <link-state-change xmlns="urn:example:params:xml:ns:yang:example-interfaces"/>
    </filter>
    <startTime>2026-09-04T06:00:00Z</startTime>  <!-- 可选：重放历史事件 -->
  </create-subscription>
</rpc>

<!-- ② 之后设备主动推送，注意它【不是】 rpc-reply，没有 message-id -->
<notification xmlns="urn:ietf:params:xml:ns:netconf:notification:1.0">
  <eventTime>2026-09-04T06:12:33.412Z</eventTime>
  <link-state-change xmlns="urn:example:params:xml:ns:yang:example-interfaces">
    <if-name>eth0</if-name>
    <new-state>down</new-state>
  </link-state-change>
</notification>

客户端可订阅事件流，设备在故障/状态变化时主动推送 notification——这就是管理面"监控/告警"的来源（O-RAN O1 里配合 VES 遥测）。三个容易踩的点：

  • <notification> 不是 <rpc-reply>，它没有 message-id，也不对应任何请求。客户端的收包循环必须能处理"这条消息不是我在等的那个响应"，否则最典型的表现是：一发订阅，后续所有 RPC 的响应配对全乱了。
  • 没有 :interleave 的设备，订阅之后这条会话就只能收通知、不能再发别的 RPC。所以稳妥的做法是永远为通知单开一条会话，配置会话和通知会话分开——这样也顺带隔离了"订阅会话被大量事件刷爆"对配置通道的影响。
  • <startTime> 能重放历史事件（需要设备支持事件重放），这是客户端重启后补齐断连期间事件的正规手段。不用它就得接受"重连窗口内的告警永远丢了"。

面试题（12 道）

分层自测

8.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础YANG 和 NETCONF 是什么关系？

    YANG 是数据建模语言，NETCONF 是网络管理协议。前者定义"数据长什么样"——有哪些字段、什么层级、什么类型、什么约束；后者定义"怎么操作和搬运这些数据"——一套基于 XML 的 RPC。

    更能体现理解深度的说法是它们处在不同的时间轴上：YANG 属于设计期，厂商在设备出厂前就把 .yang 模型写好、编译好、发布出去；NETCONF 属于运行期，真正跑在 TCP 连接上一来一回的是它。

    一个很好用的具象化：一个 NETCONF 报文里混着两套命名空间。外层的 <rpc><edit-config><target><config> 全部来自 urn:ietf:params:xml:ns:netconf:base:1.0，所有设备都一样；一进到 <config> 内部，命名空间就切换成某个 YANG 模块的 namespace，这部分才是设备特有的。排查时先判断"报错在外层还是内层"——外层是协议用错了，内层是模型用错了。

    加分：指出两者并不互相绑死。同一份 YANG 模型可以被 NETCONF（XML）、RESTCONF（JSON，RFC 7951）、gNMI（protobuf）分别承载，换协议不换模型；反过来 NETCONF 在规范上也不强制用 YANG（RFC 4741 发布时 YANG 还不存在），只是没有 schema 的 NETCONF 会退化成"用 XML 包起来的私有 CLI"，失去全部价值。

  2. 基础NETCONF 的四层模型是哪四层？各自负责什么？

    自上而下：

    • Content（内容层）：配置数据、状态数据、通知内容。结构完全由 YANG 决定（RFC 7950），NETCONF 本身不关心里面装的是什么。
    • Operations（操作层）：协议的动词——get / get-config / edit-config / copy-config / delete-config / lock / unlock / commit / discard-changes / validate，加上 close-session / kill-session。定义在 RFC 6241 第 7 节。
    • Messages（消息层）：<hello> / <rpc> / <rpc-reply> / <rpc-error> / <notification> 这套信封，message-id 的配对规则，以及消息分帧（RFC 6242 第 4 节）。通知的定义在 RFC 5277。
    • Secure Transport（安全传输层）：SSH（RFC 6242，tcp/830，强制实现）或 TLS（RFC 7589，tcp/6513），Call Home 是 RFC 8071 的 tcp/4334。再往下是 TCP / IP / 以太网。

    要答出分层的意义而不只是罗列：这四层是"换一层不影响其它层"的解耦承诺。真实例证——NMDA 给操作层加了 <get-data> / <edit-data>（RFC 8526），消息层与传输层一个字节没改；base:1.0 升到 1.1 换了分帧方式，操作层完全不受影响；O-RAN 前传 M 平面用 TLS 而 O1 更多用 SSH，上面三层一模一样。

    加分：指出传输层的要求是"能力"而不是"某个具体协议"——面向连接、可靠有序、已认证、已加密。这也解释了为什么 UDP 从一开始就被排除：message-id 配对、分帧、以及 datastore 锁的生命周期全都建立在"会话"这个概念上。

  3. 基础<get> 和 <get-config> 有什么区别？

    三个差别，每一个都有实际后果：

    • 返回内容不同。get-config 只返回 config true 的节点；get 返回 config true + config false，即配置与状态混在同一棵树里。
    • 能不能选库。get-config 有 <source> 参数，可以读 running / candidate / startup；get 没有 source 参数，它固定读 running。这一点很多人记不住。
    • 结果能不能回灌。get-config 的输出是"干净"的，可以原样 edit-config 回去——配置备份与灾难恢复就靠这个性质。get 的输出里混着只读节点，回灌必然报错。

    再补一句量级：不加 filter 的 <get/> 在一台满配设备上可能返回比 get-config 大一个数量级的数据（计数器是逐接口逐队列的），它实际上是一次压测，生产环境里不该出现在轮询循环里。

    加分：把它上升到设计层面——"配置数据与状态数据必须能分开"是 RFC 3535 那份运营商需求清单里的第一条，YANG 的 config 标志 + 这两个操作就是它的落地。SNMP 的 MIB 里 ifMtu（可写）和 ifInOctets（只读计数）平级摆着，正因为分不开，"备份配置"这件事在 SNMP 上根本无从下手。

  4. 基础YANG 里的 config false 是什么意思？

    config false 标记这个节点是「状态数据」而不是「配置数据」：它由设备自己产生，客户端只能读、不能写。典型的是计数器（in-octets）、运行状态（oper-status）、协商结果、邻居表。默认值是 config true，所以模型里绝大多数节点不写这一句。

    直接后果：

    • 它不会出现在 <get-config> 的结果里，只有 <get> 能拿到；
    • 往它写数据会被拒（invalid-value 或 unknown-element）；
    • 它不参与配置备份与比对——这正是配置备份能干净回灌的原因。

    两条容易被追问的硬规则：① config false 节点的所有子孙自动也是 config false，不能再翻回 true（配置树不可能长在状态树下面）；② config true 的 list 必须有 key，config false 的 list 可以没有——因为状态数据不需要被寻址修改。第二条解释了为什么很多计数器表在模型里看不到主键。

    加分：指出这个二分法在 NMDA（RFC 8342）里被进一步细化了。config 标志区分的是"节点的性质"，而 NMDA 用 <intended> 与 <operational> 两个 datastore 区分"我打算要的配置"与"实际在跑的配置 + 状态"。在 <operational> 里，config true 的节点照样会出现——但那是「已经生效的值」，可能和你在 running 里写的不一样（比如给一块没插上的板卡配的接口，running 里有、operational 里没有）。

8.2 中级（区分熟练度）

  1. 中级<hello> 里的 capability 协商起什么作用？

    会话一建立（SSH/TLS 认证通过后），双方各自立刻发出一个 <hello>，列出自己支持的能力。注意它不是请求/响应——两边都不等对方，所以严格说是"双向单播的能力宣告"而不是握手。协商规则极简单：取交集，某个能力必须在双方列表里都出现才算可用。

    它决定了这条会话上"什么能做、什么不能做"，关键的几条：

    • :base:1.1 → 决定用 chunked framing 还是 ]]>]]>；
    • :writable-running → edit-config 的 target 能不能填 running；
    • :candidate → 有没有草稿库，也就是有没有多步事务；
    • :validate / :rollback-on-error / :confirmed-commit → 三层安全网各有没有；
    • :startup → 要不要额外做 copy-config running → startup 才能扛过重启；
    • :notification / :interleave → 能不能订阅事件，订阅之后还能不能在同一条会话上发 RPC；
    • :xpath / :url / :with-defaults / :yang-library → 过滤方式、大配置传输方式、默认值行为、模型清单来源。

    另外 服务端的 <hello> 里有 <session-id>，客户端的禁止有。这个 id 不只是流水号——它是 <kill-session> 的入参，也是 lock-denied 错误的 <error-info> 里告诉你"锁在谁手上"的那个值。

    工程上的加分点：集成一台新设备时第一件事是把服务端 <hello> 完整存档。它回答了"这台设备到底能做什么"的九成问题。后面每次"这个操作为什么不行"，都该先回到这份存档看一眼，而不是去翻 RFC。只在自己 mock 服务器上测过的客户端往往默认所有能力都在，上真设备第一天就会被 operation-not-supported 教做人。

  2. 中级为什么 chunked framing 取代了 ]]>]]>？

    因为 ]]>]]> 这种分隔符式分帧把"边界标记"和"数据"塞进了同一个字节空间，却没有提供任何转义机制。RFC 6241 只能靠一条纪律兜底：内容里禁止出现这六个字节。可 NETCONF 的内容是任意 YANG 数据——一个 description 字符串、一段脚本、一个 XML 注释都可能凑出它。

    而后果不是丢一条消息，是整条会话此后所有消息的边界全部错位：接收端在半截 XML 处切了一刀，之后每条消息都是上一条的尾巴加下一条的头。现场表现是"跑了几个月好好的，某天配了一条带特殊字符的描述之后，这台设备的管理通道再也起不来了"。

    除了正确性，还有三个工程问题：① 必须逐字节扫描找分隔符，无法零拷贝、无法预分配缓冲；② 读完才知道消息多大，也就无法在读之前做"消息过大直接拒绝"的 DoS 防护；③ 大响应必须在内存里拼成一整块才能发。

    chunked framing（RFC 6242 §4.2）用长度前缀把这些一次性解决：\n#<size>\n<data> 重复若干次，以 \n##\n 结束。接收端不需要理解内容的任何一个字节，只需要数够 N 个，于是内容对分帧完全透明。这是所有二进制协议早就学会的一课（HTTP 的 Content-Length、SCTP 的消息边界都是同一个道理）。

    两个必答的实现细节：

    • <hello> 本身永远用 ]]>]]> 分帧。因为分帧方式是靠 hello 协商出来的，协商完成之前双方还不知道该用哪种。从 hello 之后的第一条消息起才切换到 chunked（前提是双方都声明了 base:1.1）。忘了切换的症状是会话静默挂死——不报错、没回复，因为服务端在等 chunk header。
    • chunk 边界与 XML 结构毫无关系。RFC 里的例子第一个 chunk 只有 4 个字节 <rpc，把标签都切断了，这完全合法。所以接收端必须先按 chunk 拼出完整字节流，再交给 XML 解析器，不能边拆边解析。只处理"一条消息 = 一个 chunk"的实现，会在"小的能过、大的挂住"上翻车。
  3. 中级edit-config 的 operation 属性有哪五个值？分别什么语义？

    按"目标已存在 / 不存在"两种情况说，才算讲清楚：

    • merge（默认）：逐层合并——列出的 leaf 覆盖值，未列出的保留；目标不存在则创建。merge 只增不减，想删东西它帮不上忙。
    • replace：整棵子树被替换，未列出的子节点全部删除；不存在则创建。这是"把这个对象配成我说的这个样子"的幂等下发姿势。
    • create：已存在则报 data-exists；不存在则创建。
    • delete：不存在则报 data-missing；存在则删除。
    • remove：存在就删，不存在则静默成功。

    两个高频追问点：

    ① delete 与 remove 怎么选？本质是"你要不要用报错来做一致性检查"。幂等脚本（"确保这条配置不存在"）用 remove，重跑一百遍结果都一样；一次性运维动作（"把这个用户删掉"）用 delete——如果它已经不在了，说明你对设备状态的认知有偏差，这时候报错是好事。顺带一个兼容点：remove 是 RFC 6241（2011）才加的，RFC 4741 时代没有，很老的设备可能不认识。

    ② replace 作用在哪一层？作为节点属性时，它只重塑带这个属性的那个节点的子树，兄弟节点毫发无损。这和 <default-operation>replace</default-operation> 是完全不同的两件事——后者会用你这次发的 <config> 替换掉整个 datastore。名字一样，威力差几个数量级。

    最后一个几乎必踩的实现坑：operation 属性属于 NETCONF base 命名空间，必须带前缀写成 nc:operation="delete"。XML 里无前缀的属性不属于任何命名空间（不像元素那样继承默认 xmlns）。写成 operation="delete" 时，严格的服务端报 unknown-attribute，宽松的服务端直接忽略这个属性，于是你的 delete 退化成默认的 merge——返回 <ok/>，接口纹丝不动。这是"操作成功但什么都没发生"最常见的单一原因。

  4. 中级augment 和 deviation 有什么区别？

    一句话：augment 是模型作者的加法，deviation 是设备实现者的减法（或修正）。

    • augment：在自己的模块里，往别人的数据树上挂新节点。"标准模型没有我要的字段，我加一个。"挂上去的节点属于你自己的命名空间，可以带 when 做条件挂载。典型场景：厂商在 ietf-interfaces 的 interface 下加私有的 storm-control。它会进数据树，客户端可以正常读写。
    • deviation：写在一份单独的 <vendor>-deviations.yang 里，声明这台设备与标准模型的偏差。"标准模型的这部分我做不到 / 我做得不一样。"四种 deviate：not-supported（这个节点我根本没实现）、replace（换个类型或收紧范围，比如标准允许 MTU 到 9216 而我只到 1500）、add（加个 must 或 default）、delete。它的唯一目的是诚实地告诉客户端"别对我抱这个期望"，让客户端提前调整，而不是等下发失败再猜。

    一个非常容易答错的细节值得主动说：augment 进来的节点属于「写 augment 的那个模块」的命名空间，不是被 augment 的模块。写实例数据时必须切 xmlns——把 storm-control 直接写在 ietf-interfaces 的默认命名空间下，设备会报 unknown-element 或直接忽略。这一条几乎人人都会想错一次。

    顺带把相关的第三个机制补上：feature + if-feature 表达的是"这块内容可选，看设备支不支持"，由设备在运行时声明支持哪些。它和 deviation 的分工是：feature 是模型作者预见到的可选性（写在标准模块里），deviation 是设备实现者事后声明的偏差（写在自己的模块里）。

    工程结论：集成时必须把 deviation 和 feature 一起读进来。途径是 ietf-yang-library（RFC 8525），它同时给出模块清单、revision、启用的 feature 和 生效的 deviation。只按 IETF 官网那份标准模型写代码，然后在设备上遇到 unknown-element，绝大多数就是漏了这一步。

8.3 高级（体现深度）

  1. 高级default-operation 有哪三个取值？它的坑在哪？

    三个取值决定"<config> 里没有显式标 operation 的那些节点该怎么处理"：

    • merge（默认值）：按 merge 处理。低风险，覆盖绝大多数增量修改。
    • replace：用 <config> 的内容完整替换整个目标 datastore，凡是没出现在这次请求里的配置一律删除。
    • none：什么都不做，这些节点纯粹作为定位路径；只有显式带 operation 的节点才生效。

    最大的坑是 replace 的作用域被严重低估。很多人以为它是"替换我写的这部分"，实际是"替换整个库"。想象你只想改 eth0 的 MTU，请求体里就写了一个接口，default-operation 手滑填了 replace——commit 之后设备上只剩下 eth0 这一个接口，路由、ACL、用户、其它 200 个接口全部消失。而且这完全合法，设备回一个 <ok/>。它唯一的正当用途是把一份完整的配置备份灌回去。

    防护三条，缺一不可：① 客户端代码里把它做成需要显式开关才能触发的"危险模式"，不要让它成为某个封装函数的一个可选参数；② 永远先在 candidate 上做，commit 前用 get-config candidate 把结果整棵拉回来看一眼；③ 配 confirmed-commit，给自己留退路。

    第二个坑在反方向：none 太安全，安全到"什么都没发生也不报错"。如果 <config> 里一个 operation 属性都没写，服务端老老实实什么都不做，返回 <ok/>。这与"属性忘了带 nc: 前缀"叠加时特别难查——你以为写了 operation，服务端认为你没写。

    说清 none 为什么存在能体现深度：假设要删 /interfaces/interface[name='eth2']/description。用默认的 merge 时，请求里的 <interfaces> 和 <interface><name>eth2</name> 这两层本身就是要被合并进去的配置——万一 eth2 其实不存在，你这一发就顺手把它创建出来了，然后删掉一个本来就没有的字段。用 none 就不会，而且 RFC 6241 特意规定：如果 <config> 里的层级在目标库中不存在，返回 data-missing——正好把"我对设备状态的假设错了"暴露出来。

    最后把它和另外两个开关串起来：test-option（test-then-set 默认 / set / test-only）决定校不校验，error-option（stop-on-error 默认 / continue-on-error / rollback-on-error）决定出错后失败点之前的改动留不留。stop-on-error 是默认值，也就是说默认行为会留下半套配置——这一点必须知道。

  2. 高级candidate 与 running 的事务模型是怎样的？完整的变更流程有哪几步？

    running 是正在生效的配置（唯一必选的库）；candidate 是草稿区（可选能力 :candidate）。模型是：所有 edit-config 打到 candidate，中途随便改、随便验，<commit> 时一次性原子地刷进 running；不想要了就 <discard-changes>，candidate 还原成 running 的内容。

    完整的六步，每一步都在防一类具体事故：

    1. <lock><candidate/> —— 防别人同时改同一份草稿
    2. <discard-changes/> —— 清掉前一个会话留下的残渣
    3. <edit-config> ×N
    4. <validate><source><candidate/> —— 抓 must / leafref / unique 这类跨节点约束
    5. <commit>（建议带 <confirmed/>）
    6. <unlock>；若设备声明 :startup，再 copy-config running → startup

    第 1、2 步为什么不能省，是这道题真正的考点：candidate 默认是「整台设备共享一份」，不是「每个会话一份」。后果是：会话 A 写了几条改动就去开会了，会话 B 进来接着写自己的，B 一发 <commit>——A 和 B 的改动被一起提交了，而 B 完全不知道自己捎带了什么。这不是 bug，是 RFC 6241 定义的行为。规范还有一条很妙的配套规则：candidate 里如果已有未提交的改动，lock 会被拒绝——所以你在第 1 步就能发现"里面有人"，而不是 commit 之后才发现。（另外两条拒绝规则：锁已被任何会话或其它实体持有；目标是 running 且别人正在做确认式提交。）

    第 6 步也常被漏：<commit> 只写到 running，而 running 在多数设备上是内存里的运行态。不做 copy-config → startup，一次重启就全变回去了。反过来，不声明 :startup 的设备 running 本身就持久化，多做这一步反而报 invalid-value。所以这一步做不做，必须由 hello 里有没有 :startup 决定，不能写死在脚本里。

    加分：指出比锁泄漏更隐蔽的是"脏 candidate"。会话异常终止时锁会被自动释放，但 candidate 里写了一半的内容不会，它就静静躺着等下一个不做 discard-changes 的人。锁泄漏至少会报 lock-denied，脏草稿是彻底静默的。

  3. 高级confirmed-commit 解决什么问题？<persist> 有什么用？

    它解决的不是"配置写错了"（那有 validate 和 must），而是"配置本身完全合法，但生效之后正好把你自己连进来的这条路切断了"——改错管理口 IP、ACL 把自己拒之门外、路由改崩、VLAN 划错。这时设备工作得好好的，只是你再也够不着它，除非有人开车去机房插串口线。

    机制：<commit><confirmed/><confirm-timeout>300</confirm-timeout></commit>。配置立即生效，同时压上一个回滚定时器（不写 timeout 默认 600 秒）。在窗口内：再发一个 <commit> 就确认，配置永久生效；发 <cancel-commit> 就立即回滚；什么都不做，超时后设备自动还原成提交前的样子。

    它最精妙的地方是把"什么都不做"设计成了安全的那一侧。所有需要人主动补救的机制，在真出事的时候都指望不上——因为出事时你恰恰联系不上设备。confirmed-commit 反过来要求你主动确认"我还活着、一切正常"，做不到这一点就自动退回。而且这个回滚逻辑跑在设备自己身上，不依赖客户端还活着、也不依赖网络还通——这是任何客户端侧的"自建确认窗口"方案都无法替代的。

    <persist>（:confirmed-commit:1.1）是"能不能真的救你"的分水岭。不带它时，规范行为是会话一终止就立即回滚。听起来安全，但现实中最常见的场景恰恰相反：你改的就是管理网的配置，改完管理链路必然会短暂抖一下，SSH 会话被断开——于是一次本来会成功的变更被判了死刑，还得从头再来。带上 persist 之后，会话断了不要紧，倒计时继续走，你重连上来（甚至换一条会话）发一个带 <persist-id> 的 commit 就确认；真连不上，超时后它自己回滚。两种失败都被覆盖，这才是完整的。

    几个能显出真做过的细节：① 确认用的那个 commit 如果自己也带 <confirmed/>，会重置倒计时——可以边验证边"续期"；② 确认式提交进行中时，其它会话无法 lock running，因为此刻 running 随时可能变回去；③ RFC 6241 规定 :confirmed-commit:1.1 只能在同时声明 :candidate 的设备上宣告——没有草稿库的设备，标准里就没有这个安全网，只能退回到"变更前全量 get-config 备份 + 客户端侧定时探活回灌"，而那个方案恰恰依赖客户端和网络都还活着。

  4. 高级一次配置下发失败了，你怎么定位？

    先把"失败"分成三种，因为它们的排查路径完全不同：（A）报了 <rpc-error>；（B）返回 <ok/> 但配置没生效；（C）没有任何响应，挂住或超时。问清是哪一种，是这道题的第一个得分点——很多人上来就讲抓包。

    （A）有 <rpc-error>：从 error-tag 入手，它比 error-message 里那句厂商自由发挥的英文靠谱。

    • unknown-element / unknown-namespace → 模型对不上。跳到下面的"模型三连查"。
    • unknown-attribute → 十有八九是 operation 忘了带 nc: 前缀。
    • data-exists / data-missing → 对设备当前状态的假设错了。先 get-config 看真实状态；想要幂等就把 create/delete 换成 merge/remove。
    • invalid-value / bad-element → 越界、不匹配 pattern、或往 config false 节点写数据。
    • lock-denied → 看 <error-info> 里的 session-id，再读 ietf-netconf-monitoring 的会话表判断是不是僵尸会话。
    • access-denied → NACM（RFC 8341）挡了。注意 NACM 也能配成"隐藏"而非"拒绝"，那时症状变成（B）或空数据。
    • operation-not-supported → 回去看 hello 的 capability 列表。
    • rollback-failed → 最坏情况，设备处于既非改前也非改后的中间态，停止自动化、人工介入。

    另外 <error-path> 会给出指到出错节点的 XPath（含 list 的 key 谓词），能直接告诉你 200 个接口里是第几个出的问题。填得不完整的实现，就配 continue-on-error 让它一次报全，或者二分定位。

    （B）返回 <ok/> 但配置没生效——最难查的一类，按可能性从高到低：

    1. operation 属性没带 nc: 前缀，被宽松的服务端忽略，delete 退化成 merge。
    2. 只 commit 到 running，没有 copy-config → startup——症状是"改完好好的，重启后全变回去"。
    3. YANG 的 when 条件为假，服务端静默地把节点删掉了。这是设计使然、不报错。回头 get-config 会发现那个 leaf 根本不在。
    4. 命名空间写错，尤其是 augment 进来的节点用了父节点的命名空间。
    5. default-operation=none 但一个 operation 都没标，服务端确实什么都没做。
    6. 配置进了 running 但没在硬件上生效（板卡没插、资源不足、驱动失败）。这一条正是 NMDA 要解决的：设备支持的话，用 <get-data> 比较 <intended> 与 <operational>，差集就是"要求了但没落地"的部分；配上 with-origin 还能看出每个值的来源。不支持 NMDA 就只能拿 <get> 的状态节点和期望值人工比对。

    （C）挂住 / 超时：先分清是协议层还是处理层。协议层看分帧——典型症状是"小的能过、大的挂住"，而且连接还活着、没有任何错误（服务端在等 chunk header，客户端在等结束标记）；排查入口是在传输层把原始字节 dump 出来数 chunk，而不是看 XML 解析日志（那一层根本没收到东西）。处理层则是设备真的还在算：大配置的 must / leafref 校验成本随规模超线性增长，1000 个接口可能比 100 个慢 100 倍。这时千万不要盲目重发——重连后先读会话表，看上一条会话在不在、锁在谁手上，再决定等待、kill 还是重来。

    「模型三连查」（A 类里 unknown-* 的标准动作）：① 读 ietf-yang-library，拿模块 + revision + 启用的 feature + 生效的 deviation 四份清单；② 用 <get-schema>（RFC 6022）把设备上的 .yang 正文拉下来，和你手上那份 diff；③ 用 test-option=test-only 缩到最小复现，只发一个 leaf。

    最后给一条工程结论，比具体步骤更值钱：不要相信任何本地的模型副本，把设备当成模型的唯一真相来源。正确的集成流程是连上设备 → 读 yang-library → get-schema 下载全部模块 → 用这份"设备自述"编译客户端绑定。这样 feature、deviation、revision 差异在编译期就暴露，而不是在凌晨的变更窗口里以 unknown-element 的形式暴露。
