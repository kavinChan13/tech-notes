01

协议栈：从 NETCONF 到以太网

管理面的完整封装

NETCONF<rpc>/<rpc-reply> XML（承载符合 YANG 的数据）
SSH / TLS加密 + 认证（保护配置数据不被窃听/篡改/冒充）
TCP可靠、有序字节流（配置绝不能丢/乱）
IP网络寻址
Ethernet链路投递
对比 eCPRI（Module 05）的"薄封装 over 以太网"：NETCONF 是"厚封装"——多了 SSH/TLS + TCP。这不是浪费，而是管理面对可靠性/安全性的刚需。传输机制永远服务于业务特性：管理面要稳要安全 → TCP+TLS/SSH；用户面(前传)要快 → eCPRI/以太网。
本篇的边界。NETCONF 的协议分层、操作语义与 YANG 语法在 NETCONF / YANG 里讲过了；NETCONF 与 RESTCONF / SNMP / gNMI 的横向取舍在 管理协议对比。这一篇只回答一个问题：把 NETCONF 真正跑起来、并且在几百上千台设备上跑稳，工程上要做哪些事、会撞上哪些墙。所以后面出现的都是库、命令、代码骨架、超时参数和故障现象。

一条会话的完整生命周期

先把整条时间线摆出来。工程上 90% 的"连不上"问题，都能定位到下面这七步里的某一步——而每一步失败时看到的错误信息完全不同，这是排障能不能快的关键。

# ── 一次 NETCONF over SSH 会话，从零到能下发配置 ─────────────
① TCP 三次握手           → 目标端口 830        失败：Connection refused / timeout
② SSH 传输层握手         → 密钥交换、算法协商   失败：no matching key exchange method
③ SSH 认证               → publickey / password 失败：Permission denied
④ 打开 subsystem         → 名字固定为 "netconf" 失败：subsystem request failed
⑤ 双方各发一条 <hello>   → 交换 capability     失败：会话建立后立刻被关
⑥ N 条 <rpc> / <rpc-reply>（可穿插 <notification>）
⑦ <close-session> 或 TCP 断开

# 关键点：①~④ 是纯 SSH 的事，NETCONF 一个字节都还没出现。
# 所以 ①~④ 的问题不要去翻 NETCONF 日志，要去翻 sshd 的日志。
这条分界线值得单独记住：SSH 层的失败在 NETCONF 服务端往往是"无感"的——netopeer2 的日志里可能一行都没有，因为会话根本没有交到它手上。反过来，第 ⑤ 步之后的问题在 sshd 日志里也看不出名堂。先判断卡在哪一侧，再决定看哪份日志，比一上来就开 debug 级日志有效得多。

hello 与 capability：开场 5 毫秒决定后面能干什么

会话建立后，双方各自无条件发出一条 <hello>（不是请求-应答，是两条独立的单向消息），列出自己支持的能力集。服务端的 hello 里还多一个 <session-id>。

<!-- 客户端 → 服务端 -->
<hello xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <capabilities>
    <capability>urn:ietf:params:netconf:base:1.0</capability>
    <capability>urn:ietf:params:netconf:base:1.1</capability>
  </capabilities>
</hello>]]>]]>

<!-- 服务端 → 客户端（真实设备上这条常有几百行） -->
<hello xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <capabilities>
    <capability>urn:ietf:params:netconf:base:1.0</capability>
    <capability>urn:ietf:params:netconf:base:1.1</capability>
    <capability>urn:ietf:params:netconf:capability:candidate:1.0</capability>
    <capability>urn:ietf:params:netconf:capability:confirmed-commit:1.1</capability>
    <capability>urn:ietf:params:netconf:capability:validate:1.1</capability>
    <capability>urn:ietf:params:netconf:capability:notification:1.0</capability>
    <capability>urn:ietf:params:netconf:capability:interleave:1.0</capability>
    <!-- 随后是每一个已加载 YANG 模块的 URI，带 revision 与 features -->
    <capability>http://example.com/yang/vendor-radio?module=vendor-radio&amp;revision=2024-03-11&amp;features=beamforming</capability>
  </capabilities>
  <session-id>41</session-id>
</hello>]]>]]>

这条消息在工程上有三重价值，很多人只用到第一重：

能力 URI（省略 urn:ietf:params:netconf: 前缀）缺了它会怎样客户端必须做的降级
base:1.1只能用 ]]>]]> 分帧不能发含该序列的内容；大消息更容易踩解析坑
capability:candidate:1.0没有草稿库，改一条生效一条退化成"直接写 running"，必须自己保证顺序与幂等
capability:writable-running:1.0running 只读必须走 candidate；两者都没有基本无法配置
capability:validate:1.1不能单独校验只能靠 commit 自己报错，出错点更靠后
capability:confirmed-commit:1.1没有自动回滚护栏远程改网络配置前必须自己准备带外恢复手段
capability:rollback-on-error:1.0edit-config 出错时可能"改了一半"只能用 stop-on-error + 自己反向补偿
capability:startup:1.0没有独立 startup 库running 即持久，或需厂商私有 RPC 保存
capability:notification:1.0收不到告警/事件只能改成轮询（代价见第 06 章）
capability:interleave:1.0订阅后同一会话不能再发 RPC必须开第二条会话专门收通知
capability:xpath:1.0过滤只能用 subtree复杂条件要拉回本地过滤，流量放大
capability:with-defaults:1.0不能控制默认值是否回显两端对"缺省即默认"的理解可能不一致

第二重价值是模块清单：hello 后半段列出的每一个 ?module=&revision=&features= 就是这台设备的"能被配置什么"的完整声明。自动化脚本应该在连上的第一时间把它存档——设备升级后模块 revision 变了、某个 feature 被关掉了，都能靠比对这份清单立刻发现，而不是等某条 edit-config 被拒才知道。

第三重价值最容易被忽略：hello 是判断"服务端活着"的第一个也是最廉价的探针。TCP 通、SSH 认证过、subsystem 开了，但 hello 迟迟不来，说明服务端进程虽然在，但主循环卡住了（常见于上一条大 edit-config 的回调还没返回）。libnetconf2 为此有一个 hello 超时，默认量级是几十秒；把它调小到 5~10 秒，能让"服务端假死"这类故障从"客户端挂很久"变成"快速失败并重连"。

capability 的存在不等于实现是对的。见过不止一次：设备宣告了 confirmed-commit:1.1，但超时后并不真的回滚；宣告了 validate:1.1，但 <validate> 只检查语法不检查 must/leafref。把每一条你依赖的 capability 在实验室里实测一遍，写进设备准入清单——尤其是那些"出事时才会被用到"的能力，因为它们在日常流程里永远不会被触发。

分帧：为什么会有两套，以及混用会怎样

SSH 给的是无边界的字节流，而 NETCONF 是一条一条的 XML 消息。谁来告诉接收方"这条消息到此为止"？这就是 RFC 6242 的分帧（framing）要解决的问题，它给了两套机制。

End-of-Message 分帧（base:1.0）：在每条消息后面追加特殊序列 ]]>]]>。Chunked 分帧（base:1.1）：每条消息切成若干块，每块前面写明字节数，消息结束用 \n##\n 标记。
# base:1.0 —— End-of-Message
<rpc message-id="1" ...>...</rpc>]]>]]>

# base:1.1 —— Chunked（\n 是真实的换行符）
\n#312\n
<rpc message-id="1" ...>...(恰好 312 字节)...</rpc>
\n#57\n
...(再 57 字节)...
\n##\n                       ← 消息结束

为什么要换掉 ]]>]]>？因为它是一个可能合法出现在 XML 内容里的序列——CDATA 段的结束标记就是 ]]>，而某些配置值（正则表达式、脚本片段、证书之外的 base64 变体、日志文本）也可能凑出这串字符。一旦出现，接收方会在消息中间误判结束，剩下的半截被当成下一条消息的开头，后果是会话从此永久错位：每条回复都对不上请求，而错误信息通常只是一句无头无脑的 "XML parse error"。chunked 分帧靠长度前缀，内容里出现什么字节都无所谓。

维度]]>]]>（base:1.0）chunked（base:1.1）
边界判定扫描特殊序列读长度前缀
内容透明性不透明：内容不能含该序列完全透明
接收端能否预分配缓冲不能，只能边收边找能，按 chunk 大小分配
能否边收边解析可以但要处理跨界匹配可以，天然按块
对超大消息的友好度差：整条读完才知道多大好：可以流式喂给 XML 解析器
协商条件默认双方都宣告 base:1.1 才启用
唯一的例外：<hello> 本身永远用 ]]>]]> 结束。逻辑上没有别的选择——分帧方式要靠 hello 协商出来，那么 hello 自己就不能用协商结果。自己手写客户端时这是最经典的坑：hello 发对了、后面的 rpc 用了 chunked，或者反过来 hello 用了 chunked，两种情况都会让对端在解析上直接卡死，而且因为对端也在等你的数据，表现是"连上了但什么都不发生"，比报错更难查。

还有一个量级问题：chunk 的大小上限允许到 232-1 字节，但真实实现会有自己的消息大小上限。一次拉全量配置的 <get-config> 在一台配置饱满的设备上做到几 MB 到几十 MB 很正常，如果服务端的单消息上限设得比它小，你会拿到一个含糊的错误或者被直接断链。这就是第 07 章"大配置"那一节要处理的第一件事。

02

NETCONF over SSH（默认）

标准端口 830

NETCONF 默认走 SSH，端口 830（RFC 6242）。SSH 提供加密通道 + 客户端/服务端认证。会话在 SSH 之上用特殊分帧（旧的 ]]>]]> 或新的 chunked framing）传 XML。

# 用命令行连一个 NETCONF server（示意）
ssh -s -p 830 admin@ru-device netconf
# 或用 netopeer2-cli（libnetconf2 配套客户端）
netopeer2-cli
> connect --host ru-device --port 830 --login admin
> get-config --source running
  • 认证方式：密码 或 SSH 公钥。生产环境优先公钥/证书，避免明文密码。
  • 优点：部署简单、运维熟悉、默认选项。

subsystem 到底是什么机制

这是理解 NETCONF over SSH 的关键，也是最常被跳过的一环。SSH 连上之后，客户端要告诉服务端"我这条通道要干什么"，一共三种请求：

SSH channel request服务端做什么典型用途
shell起一个交互式 shell，接上伪终端ssh user@host 登进去敲命令
exec起一个进程执行指定命令行ssh user@host "ls -l"
subsystem按名字查表，起预先注册好的那个程序，不给伪终端sftp、netconf
SSH subsystem：一种"具名服务"机制。服务端在配置里把一个名字（如 netconf）绑定到一个处理程序，客户端用 ssh -s host netconf 按名字请求。它与 exec 的本质区别是名字由服务端定义、客户端无法指定任意命令行——这既是安全边界，也意味着"名字没注册就一定连不上"。

为什么 NETCONF 要用 subsystem 而不是 exec？三个理由，都很实际：

  • 不分配伪终端（PTY）。PTY 会做行规程处理：把 \n 变成 \r\n、拦截 Ctrl-C、对某些字节做转义。XML 是二进制敏感的字节流，被 PTY 改一个字节整条消息就废了。subsystem 天然是裸管道。
  • 不经过登录 shell。不会执行 .bashrc，不会有欢迎横幅（banner）、motd、fortune 之类的输出混进流里。"某台设备的 NETCONF 连上就解析失败，别的设备都正常"，十有八九是它的 shell 启动脚本往 stdout 打了东西——这个坑在用 exec 自己拼命令行时几乎必踩。
  • 可以独立做授权。可以给一个账号只开 netconf subsystem、不开 shell，做到"能配置设备但登不进操作系统"。
# 服务端：OpenSSH 复用 22 端口时，在 sshd_config 里注册
Subsystem netconf /usr/bin/netopeer2-server-wrapper
# 更常见的做法是让 NETCONF 服务端自己监听 830，内置 SSH 服务器
（netopeer2 走这条路，用 libssh 自己实现 SSH 服务端，不依赖 sshd）

# 客户端：三种等价写法
ssh -s -p 830 admin@ru-device netconf          # -s = 请求 subsystem
ssh -p 830 -N -o "Subsystem netconf" ...        # 不常用
netopeer2-cli                                   # 交互式，推荐调试用

# 判断"是 SSH 的问题还是 NETCONF 的问题"的一条命令：
ssh -vvv -s -p 830 admin@ru-device netconf 2>&1 | tail -40
#   看到 "Requesting subsystem netconf" 之后立刻 exit → 名字没注册 / 账号无权限
#   看到 <hello ...>]]>]]> 打出来        → SSH 侧完全正常，问题在 NETCONF 层
上面最后那条命令是本篇最值得记住的一行。它用纯 SSH 客户端把 NETCONF 会话的前五步走完，把 hello 原样打在屏幕上。能看到 hello，说明端口、认证、subsystem、服务端进程全部正常，剩下的问题一定在你的客户端代码或模型层——排障范围一下砍掉一半，而且不需要在设备上装任何工具。

端口 830 与复用 22 之争

RFC 6242 给 NETCONF 分了独立端口 830，但也允许在 22 上跑（靠 subsystem 名字区分）。实践中怎么选：

方案好处代价什么场景选它
独立 830防火墙/ACL 里能按端口区分管理流量；NETCONF 服务端进程独立，崩了不影响 SSH 登录；能单独限速、单独统计多一个端口要在所有中间设备上放通网元设备的默认选择，O-RAN 场景基本都是它
复用 22不用额外开洞；沿用现有 sshd 的认证与审计NETCONF 与运维登录共享连接数与资源；sshd 重启会一起断；ACL 无法区分通用服务器、已有严格端口管控的环境

还有一个容易被忽略的差别：如果 NETCONF 服务端自带 SSH 实现（netopeer2 用 libssh），它和系统 sshd 是两套独立的算法策略、两套主机密钥、两套认证配置。安全扫描要求"禁用某个弱算法"时，改了 /etc/ssh/sshd_config 对 830 端口毫无作用——这是安全整改时反复出现的返工点。

认证：公钥、密码，以及主机密钥校验这件麻烦事

客户端认证服务端、服务端认证客户端，是两个独立的方向，工程上难度完全不对称。

服务端认客户端相对简单：公钥认证。把客户端公钥灌进设备的 authorized_keys（在 YANG 化的设备上是 ietf-netconf-server 或厂商模块里的一个 list）。密码认证在生产上应当关掉，理由不只是"明文"（SSH 里其实是加密的），而是密码没法做到"一机一密"，一旦泄露波及全网。

客户端认服务端才是真麻烦：SSH 靠 主机密钥指纹（known_hosts），第一次连接时提示 "The authenticity of host ... can't be established"。在自动化场景里这一步没有人来点"yes"，于是几乎所有脚本都写成了：

# ❌ 生产上最常见的一行错误代码
m = manager.connect(host=ip, port=830, username=u,
                    hostkey_verify=False)   # 等于关掉服务端身份校验

# ✅ 预置 known_hosts：设备出厂/开站时把主机公钥录入资产库
ssh-keyscan -p 830 -t ed25519 ru-device >> ~/.ssh/known_hosts_netconf
m = manager.connect(host=ip, port=830, username=u,
                    key_filename="/etc/smo/id_ed25519",
                    hostkey_verify=True,
                    device_params={'name': 'default'})
hostkey_verify=False 把 SSH 降级成"只加密不认证"：链路上的中间人可以完整地代理这条会话，读到你下发的每一条配置，还能篡改。它之所以到处都是，是因为不关它自动化就跑不起来——而"跑不起来"是立刻可见的，"能被中间人"是永远不可见的。这正是 O-RAN 前传 M 平面选择 TLS + 证书的直接动机：证书体系天然解决了"我怎么知道对面是不是那台设备"，而不需要为每台设备手工维护一条指纹记录。

SSH 层的三个参数会直接决定运维体感

参数作用配小了配大了建议量级
TCP keepalive / SSH keepalive探测对端是否还在抖动时误断连设备重启后旧会话残留，占着锁不放探测间隔 30~60 s，3 次失败判死
hello 超时等对端 hello 的上限慢启动设备连不上服务端假死时客户端长时间挂住5~15 s
会话空闲超时（idle timeout）多久没消息就回收会话长事务中途被踢僵死会话堆积，吃满并发上限看用途：长连接监控设 0/很大，脚本会话设 5~15 min

"设备重启后旧会话残留"值得展开：TCP 连接的一端掉电时，另一端在没有数据要发的情况下是察觉不到的——它会一直以为连接还在。如果这条僵死会话上还锁着 candidate 库，那么设备重启回来后新会话去 <lock> 会被拒（服务端认为锁还被那个 session-id 持有），直到空闲超时把它清掉。这就是"设备刚重启完反而配不了"的典型成因，而它看起来完全不像一个网络问题。keepalive 与 idle timeout 就是用来给这个状态兜底的。

03

NETCONF over TLS 与 cert-to-name

O-RAN 前传 M 平面偏爱 TLS

NETCONF 也可走 TLS（RFC 7589，端口 6513）。O-RAN 前传 M 平面常用 TLS + 双向认证（mTLS）：不仅客户端验设备，设备也验客户端证书。

cert-to-name：TLS 里客户端出示的是证书，但 NETCONF 的授权（NACM）是基于用户名的。cert-to-name 就是一张"证书 → 用户名"的映射规则（依据证书指纹或 subject 字段），把 TLS 认证到的身份映射成 NETCONF 用户，再套用户的访问控制。

证书体系关键词

  • CA：签发/背书证书的权威
  • truststore：我信任的 CA/证书集合
  • keystore：我自己的私钥+证书
  • mTLS：双向证书认证

SSH vs TLS 选择

  • SSH：运维简单、默认；适合传统网管
  • TLS+mTLS：证书体系、可扩展、自动化友好；O-RAN M 平面常用

🏨 生活类比：门禁卡 vs 身份证

SSH 公钥像一栋楼自己发的门禁卡：每栋楼的前台各自登记一份"谁的卡能进"。楼少的时候很好用；等你管一千栋楼，某个人离职要收回权限，你得跑一千个前台。TLS 证书像公安发的身份证：每栋楼只需要认"公安局的章"（信任 CA），谁能进由随身携带的证件说了算，作废也只要发一份挂失名单（CRL）。代价是你得先有一个公安局——PKI 的搭建与运营成本，正是 TLS 在小规模场景里显得笨重的原因。

cert-to-name：证书与 NACM 之间那道必须存在的胶水

TLS 握手结束时，服务端手里只有一张证书。而 NETCONF 的访问控制（NACM，RFC 8341）是按用户名和用户组授权的：哪个组能读哪条 XPath、哪个组能调哪个 RPC。中间必须有人把证书翻译成用户名——这就是 cert-to-name。

标准做法来自 ietf-x509-cert-to-name（RFC 7407 定义的 grouping，被 ietf-netconf-server 复用）。它是一张按优先级排序的规则表，每条规则含三部分：证书指纹、映射方式、以及（部分方式下的）用户名模板。

指纹字段可以填叶子证书的指纹，也可以填签发它的 CA 的指纹。这两种用法的规模化差别巨大：

  • 填叶子证书指纹：等价于白名单。每加一个客户端、每换一次证书，都要去每台设备上改配置——这就把 TLS 退化回了 SSH authorized_keys 的运维模型，白搭了 PKI。
  • 填 CA 指纹 + san-dns-name：任何由这个 CA 签发、SAN 里带合法名字的客户端都能自动落到对应用户上。新增一个网管节点不需要碰任何一台设备。这才是 TLS 在大规模场景下的价值所在。
面试里这道题的分水岭在于能不能说清"为什么不能直接拿证书做授权"。答案是：NETCONF 的授权模型（NACM）早于、且独立于传输层，它认的是 user-name 与 group；如果让 TLS 层直接决定权限，就等于每套传输各自实现一份 ACL，SSH 一套、TLS 一套、Call Home 又一套。cert-to-name 的设计意图是"把所有传输的认证结果收敛成同一种身份表示"，从而让授权只写一遍。这是一个典型的"加一层间接解决 N×M 问题"的工程决策。

第三行是最硬的一条。O-RU 的物理安全性远低于机房设备——它就挂在外面。一台被拆走的 O-RU，里面的私钥就在攻击者手上；如果用的是 SSH 公钥模型，你没有任何标准手段让全网"忘掉"这把钥匙，只能挨台去删。而证书体系里，把它的序列号加进 CRL 就完事了。

但 CRL/OCSP 在嵌入式设备上是有代价的，别想当然。O-RU 要校验客户端证书是否被撤销，就得能拿到 CRL——而 CRL 分发点通常是一个 HTTP URL，这要求 O-RU 在还没被纳管、可能还没有完整路由的时候就能访问外网，这在前传隔离网里常常不成立。现实中的折中有三种：① 把 CRL 通过 M 平面自身下发（先信任、后收紧）；② 用短有效期证书（几天到几周）代替撤销，靠自动续签兜底；③ 只校验证书链与有效期，撤销靠改设备上的 truststore。三种都不完美，选哪种要在设计阶段定，不要留给现场。

证书的生命周期才是长期运维成本的大头

TLS 上线那天最顺利，第 365 天最痛苦。把生命周期上的事提前想清楚：

阶段要解决的问题常见做法典型坑

其中"CA 轮换"是最容易被推迟到不可收拾的一件事。根 CA 的有效期通常十年二十年，上线时没人会去想；但一旦发生私钥泄露或算法淘汰，就得在不能通过管理面登录设备的前提下更换设备信任的 CA——这是个鸡生蛋问题。唯一的解法是从第一天起就让 truststore 支持"同时信任多个 CA"，并且把"往 truststore 里加一个 CA"做成一个例行可执行的操作，而不是等到需要时才发现流程根本不存在。

04

Datastore 与 commit 工作流

安全地改一批配置

生产里改配置的标准姿势（避免"配一半生效"或"把自己配断"）：

1. <lock> candidate            # 锁库，防并发
2. <edit-config> → candidate   # 把一批改动写入草稿
3.（可选）<validate> candidate  # 校验是否符合 YANG 约束/依赖
4. <commit>                     # 原子提交到 running（一起生效）
5. <unlock> candidate
confirmed-commit（保命技能）：<commit> 带 confirmed + timeout，若在超时内没收到二次确认，设备自动回滚到提交前状态。远程改 O-RU 网络配置时若不慎把自己"配失联"，它能自动救回——这是运维远端设备的必备护栏。

五步链路的完整报文

上面五步每一步的实际报文长这样。注意 message-id 是客户端自己维护的、单调递增的编号，回复靠它对上请求——这是 NETCONF 允许在一条会话上并发发多个 RPC（pipelining）的基础。

<!-- ① 锁 candidate。锁的粒度是"整个 datastore"，不是某个子树 -->
<rpc message-id="101" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <lock><target><candidate/></target></lock>
</rpc>

<!-- ② 写草稿。default-operation 与 error-option 是两个必须显式指定的参数 -->
<rpc message-id="102" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <edit-config>
    <target><candidate/></target>
    <default-operation>merge</default-operation>
    <error-option>rollback-on-error</error-option>
    <config>
      <interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
        <interface>
          <name>eth0</name>
          <mtu nc:operation="replace"
               xmlns:nc="urn:ietf:params:xml:ns:netconf:base:1.0">9000</mtu>
        </interface>
      </interfaces>
    </config>
  </edit-config>
</rpc>

<!-- ③ 校验：跑一遍 must / when / leafref / unique，但不生效 -->
<rpc message-id="103" ...><validate><source><candidate/></source></validate></rpc>

<!-- ④ 带确认的提交：600 秒内没有二次 commit 就自动回滚 -->
<rpc message-id="104" ...>
  <commit>
    <confirmed/>
    <confirm-timeout>600</confirm-timeout>
    <persist>batch-2026-0904-A</persist>   <!-- 允许换一条会话来确认 -->
  </commit>
</rpc>

<!-- ④' 业务验证通过后，二次提交确认（不带 confirmed） -->
<rpc message-id="105" ...><commit><persist-id>batch-2026-0904-A</persist-id></commit></rpc>

<!-- ⑤ 解锁 -->
<rpc message-id="106" ...><unlock><target><candidate/></target></unlock></rpc>

两个被默认值坑过很多人的参数

<edit-config> 上有两个参数，不写就走默认值，而默认值在批量场景下几乎总是错的。

参数取值含义什么时候用
default-operation
（默认 merge）		merge把发过来的树合并进目标库，没提到的保持不变增量修改，绝大多数场景
replace发过来的树整体替换对应子树，没提到的被删"我要把这个设备配成完全这个样子"的声明式下发
none不做隐式操作，只执行显式标了 operation 的节点精确删除：想删一项时必须用它，否则父节点会被 merge 出来
error-option
（默认 stop-on-error）		stop-on-error遇错停下，已经改的部分留在 candidate 里单条修改；批量时是灾难
continue-on-error跳过错的继续做几乎不该用：结果不可预测
rollback-on-error任一处出错整条 edit-config 全部撤回批量下发的唯一正确选择（需 rollback-on-error:1.0 能力）
默认组合 merge + stop-on-error 的后果是：一条包含 200 个节点的 edit-config，在第 137 个节点上因为一个 must 约束失败，前 136 个改动留在了 candidate 里。如果这时候有人（或你的重试逻辑）执行了 <commit>，设备就进入了一个"配了一部分"的状态——而这个状态从任何一份配置文件里都推导不出来。所以批量脚本里 error-option 必须显式写 rollback-on-error，并且失败路径上必须 <discard-changes>。

还有一个不在参数里、但同样重要的动作：拿到 candidate 锁之后的第一件事应该是 <discard-changes>。candidate 是全局共享的一份草稿，不是"你这条会话的草稿"。上一个客户端异常退出、锁被超时释放，它留在 candidate 里的半截改动会原封不动地等着——你 commit 的时候会把别人的半成品一起提交上去。

confirmed-commit：不只是"超时回滚"

confirmed-commit 的完整语义比大多数人以为的丰富。RFC 4741/6241 定义的 :confirmed-commit:1.1 里有三件事值得单独讲：

<persist> / <persist-id>

不带 persist 时，发起 confirmed-commit 的那条会话一断，立刻触发回滚——不等超时。这在"改网络配置把自己配断"的场景下正是想要的。但如果你是想改完之后换一条会话来确认（比如让另一个流程去做业务验证），就必须带 persist 起个名字，确认时用 persist-id 认领。

可以续期，也可以主动放弃

超时内再发一条带 <confirmed/> 的 commit，会刷新超时计时器而不是确认——适合验证时间不确定的场景，每 5 分钟续一次。想立刻回滚不必等超时，直接 <cancel-commit>。

超时时间怎么定？这是个被低估的决策：

场景建议超时理由
改管理网 IP / VLAN / 路由60~120 s连通性验证很快就有结论；配断了要尽快回来
改载波/射频参数300~600 s需要等小区重建、UE 重新接入才能判断好坏
批量下发（几十台）600~1800 s + persist要等整批都下完再统一确认，否则先做的等不及后做的
confirmed-commit 回滚的是配置，不是世界。它把 running 恢复到提交前的内容，但你的应用因为那次配置已经做过的副作用不会撤销：重启过的进程不会回到重启前、发出去的告警不会收回、写进外部数据库的记录还在。所以订阅回调（第 05 章）里做的事情必须是可重入、可反向执行的——sysrepo 之所以专门给一个 ABORT 事件，就是为了让你有地方写这段撤销逻辑。

并发变更：三种冲突与各自的处理

真实系统里同时想改一台设备的往往不止一个：SMO 的编排流程、值班工程师的手工操作、自动优化算法、以及厂商的巡检脚本。冲突分三类，处理方式完全不同。

冲突类型表现NETCONF 提供的手段正确处理
① 抢锁<lock> 返回 lock-denied，error-info 里带持锁的 session-id<lock> 的原子性带抖动的退避重试；重试若干次后上报人工，不要无限等
② 覆盖（lost update）A 读了配置、算出改动、写回；期间 B 改过同一处，A 的写把 B 覆盖了无内建乐观锁用 merge + 只写自己负责的最小子树；或读取时记下关键值，写时用 test-option=test-then-set 前先复核
③ 语义冲突两边各自合法，合起来违反 must/unique（如两个流程各分配了同一个 VLAN）<validate> 与 commit 时的模型校验把分配类资源收敛到单一权威（SMO 侧的资源池），设备侧校验只当最后一道网

关于 ① 有个反直觉的建议：不要为了"稳"而把锁的持有时间拉长。锁的作用范围是整个 candidate 库，持锁期间别人一条配置都下不了。一个持锁 10 分钟做业务验证的流程，会让同一台设备上所有其它自动化全部超时失败，而它们的日志里只会写"lock-denied"，没人知道是谁占着。正确做法是：锁只覆盖 edit + validate + commit 这几秒，验证放在 commit 之后、靠 confirmed-commit 兜底。

# 一个健壮的加锁重试（伪码，量级参数是实测出来的经验值）
for attempt in range(5):
    try:
        m.lock('candidate')
        break
    except RPCError as e:
        if e.tag != 'lock-denied':
            raise                       # 别的错误不该重试
        holder = e.info                       # 里面有 session-id，记进日志
        time.sleep(min(2 ** attempt, 16) * (0.5 + random.random()))
else:
    raise Timeout(f"candidate 被 session {holder} 长期占用，需人工介入")
抖动（jitter）那一项不是装饰。SMO 对一批设备并行下发时，如果每个 worker 都用同样的退避序列，它们会在同一时刻一起重试、一起失败、再一起重试——形成稳定的活锁。乘一个 0.5 + random() 的随机因子就能把它们打散。这个坑在单机测试时永远不出现，只在规模上去之后出现。

没有 candidate 的设备怎么办

不是所有设备都支持 candidate——尤其是资源受限的嵌入式设备，可能只宣告 :writable-running:1.0。这时候上面那条链路要退化：

有 candidate只有 writable-running
原子性整批 commit 一起生效每条 edit-config 内部原子，批次之间不原子
失败回退discard-changes，零成本必须自己发反向 edit-config 补偿
护栏confirmed-commit 自动回滚没有；只能靠外部看门狗 + 带外通道
并发保护lock candidatelock running（代价更大：锁住的是生效配置）
工程建议照标准五步走把一次变更压进一条 edit-config，靠 rollback-on-error 拿到批内原子性

最后一行是关键技巧：在没有 candidate 的设备上，"一条 edit-config" 就是你能拿到的最大事务边界。所以要把本该分成五条的改动拼成一条大的，宁可 XML 长一点，也不要拆成多条——拆开就等于放弃了原子性。

C 语言实现 NETCONF 的事实标准库

四个组件，四件不同的事

这套栈最值得先弄清的是职责边界。很多人把它们当成"一个大黑盒"，结果排障时不知道该看谁的日志、性能瓶颈也定位不到层。

组件它负责什么它不负责什么出问题时的典型症状
libyang把 .yang 编译成 schema；构造、校验、序列化数据树不碰网络、不碰存储模块加载失败、must 校验报错、命名空间不匹配
libnetconf2SSH/TLS 服务端与客户端、会话、分帧、RPC 编解码不理解任何业务语义，不存数据连不上、hello 超时、分帧解析错、会话数打满
sysrepodatastore 存储与差分、订阅分发、两阶段提交、操作数据聚合不做 SSH，不做 NACMcommit 卡住（某个订阅者不返回）、模块未安装、共享内存/权限问题
netopeer2-server把标准 RPC 接到 sysrepo；NACM；会话管理；通知转发不实现具体业务配置RPC 返回 access-denied、operation-not-supported
你的应用订阅回调里把配置写进硬件；提供 operational 数据；产告警—配置"提交成功"但硬件没变——回调里吞了错误
这张分层表本身就是一道好面试题的答案。加分点是指出厂商自研栈几乎必然是同一个分层：不管用不用开源实现，"协议/会话层""事务/datastore 层""模型/校验层""业务生效层"这四件事都必须有人做，而且必须分开做。理由是它们的变化频率完全不同——协议层十年不动，模型层每个版本都在扩，业务层随硬件改。把它们糅在一起的实现，最终都会因为"改一个 YANG 字段要动网络代码"而重构。

从零把服务端跑起来：模块安装与启动

模块升级不要用"卸载再安装"。sysrepoctl -u（uninstall）会连同该模块在所有 datastore 里的配置数据一起删掉，重装后设备回到空配置——在现场设备上这等于一次业务中断。原地升级（-U）会尝试把旧数据迁移到新 revision，只有在模型做了不兼容变更时才会失败。软件包升级流程里必须显式区分这两条路径，这是 O-RU 远程升级最容易翻车的一处。

订阅配置变更：两阶段提交与那三个事件

这是服务端实现里唯一真正需要你写代码的地方。sysrepo 的模型是：你声明关心哪个模块的哪棵子树，当有人 commit 时，sysrepo 会分阶段回调你。

两阶段提交：sysrepo 先用 CHANGE 事件问所有订阅者"这份改动你能接受吗"，任何一个返回错误就整体作废，已经答应过的订阅者会收到 ABORT 让它们撤销；全部答应才发 DONE，此时改动已经写进 running，不能再拒绝。
事件什么时候到你在这里应该做什么返回错误的后果
SR_EV_UPDATE校验之前需要修改本次变更（补默认值、联动字段）时用；可以往 session 里写数据整个变更失败
SR_EV_CHANGE校验通过后、生效前只做检查与预留资源：参数合不合理、硬件当前状态允不允许、内存够不够整批回滚，客户端收到你填的 error message
SR_EV_DONE已经写进 running 之后真正把配置作用到硬件；这里的失败无法阻止提交无法回滚，只能自己产告警 / 触发自愈
SR_EV_ABORT别人否决了本次变更释放你在 CHANGE 阶段预留的资源忽略
SR_EV_ENABLED订阅刚建立时（带该选项）拿到当前已有配置，做初始化同步订阅失败

CHANGE 与 DONE 的分工是整套机制的核心，也是最常写错的地方。把"写硬件"放在 CHANGE 里，看起来能"失败就拒绝"，实际上是灾难：如果同一次 commit 涉及三个模块，你在 CHANGE 里已经改了硬件，而第三个模块的订阅者否决了，sysrepo 会告诉客户端"提交失败、配置未变更"——但你的硬件已经变了，软件配置与硬件状态从此分叉。

/* sysrepo 2.x 订阅骨架（1.x 回调签名没有 sub_id 参数） */
#include <sysrepo.h>

static int radio_change_cb(sr_session_ctx_t *sess, uint32_t sub_id,
                           const char *module, const char *xpath,
                           sr_event_t event, uint32_t request_id, void *priv)
{
    sr_change_iter_t *it = NULL;
    sr_change_oper_t op;
    const struct lyd_node *node;
    const char *prev_val;
    int rc;

    /* 只在这两个阶段遍历差分；ABORT 走另一条撤销路径 */
    if (event != SR_EV_CHANGE && event != SR_EV_DONE) {
        if (event == SR_EV_ABORT) release_reserved(priv);
        return SR_ERR_OK;
    }

    /* "//." 表示这棵子树下的所有节点，含被删除的 */
    rc = sr_get_changes_iter(sess, "/vendor-radio:carriers//.", &it);
    if (rc != SR_ERR_OK) return rc;

    while (sr_get_change_tree_next(sess, it, &op, &node,
                                  &prev_val, NULL, NULL) == SR_ERR_OK) {
        if (event == SR_EV_CHANGE) {
            /* 阶段一：只校验 + 预留，绝不碰硬件 */
            if (!carrier_params_acceptable(node)) {
                sr_session_set_error_message(sess,
                    "carrier %s: bandwidth exceeds RF capability",
                    node_key(node));
                sr_free_change_iter(it);
                return SR_ERR_VALIDATION_FAILED;   /* → 整批回滚 */
            }
            reserve_dsp_resources(node);
        } else {
            /* 阶段二：已成定局，把它作用到硬件 */
            switch (op) {
            case SR_OP_CREATED:  hw_carrier_add(node);            break;
            case SR_OP_MODIFIED: hw_carrier_update(node, prev_val); break;
            case SR_OP_DELETED:  hw_carrier_del(node);            break;
            case SR_OP_MOVED:    hw_carrier_reorder(node);        break;
            }
        }
    }
    sr_free_change_iter(it);
    return SR_ERR_OK;
}

int main(void)
{
    sr_conn_ctx_t *conn;  sr_session_ctx_t *sess;  sr_subscription_ctx_t *sub = NULL;

    sr_connect(0, &conn);
    sr_session_start(conn, SR_DS_RUNNING, &sess);

    /* SR_SUBSCR_ENABLED：订阅时先拿一遍当前配置，避免重启后与硬件不同步 */
    sr_module_change_subscribe(sess, "vendor-radio", "/vendor-radio:carriers",
                               radio_change_cb, NULL, 0,
                               SR_SUBSCR_ENABLED, &sub);

    /* 提供 operational 数据（只读状态，如实测发射功率） */
    sr_oper_get_subscribe(sess, "vendor-radio", "/vendor-radio:carriers/carrier/measured-power",
                          oper_power_cb, NULL, 0, &sub);

    while (!stop) pause();
    sr_disconnect(conn);                       /* 会一并释放 sub */
    return 0;
}
回调是在 commit 的关键路径上同步执行的。你在回调里睡 30 秒，客户端的 <commit> 就阻塞 30 秒；你在回调里死锁，这台设备的所有配置操作从此全部超时——而客户端看到的只是一个笼统的 timeout，完全指不到你。硬性纪律：DONE 回调里只做"把参数塞进队列/写寄存器"这种确定性短操作，凡是可能长耗时的（等硬件锁定、重建小区、等外部服务）必须异步化，用 operational 数据或通知回报结果。sysrepo 有回调超时机制，超时后整批变更被判失败——量级是秒级，可配，别指望它很宽松。

关于订阅优先级（sr_module_change_subscribe 的 priority 参数）：同一模块多个订阅者时，数值大的先被回调。这在有依赖顺序的场景下必要，比如"先建端口、再建端口上的载波"。但要警惕：依赖优先级排序等于把模块间的耦合藏进了两个整数里，代码里看不出来。能靠模型的 leafref/must 表达的依赖就交给模型，实在不行再用 priority，并且在代码里写清楚为什么是这个数。

Python 侧：ncclient 的一个完整可跑脚本

自动化侧几乎没人手写 C 客户端。ncclient（Python）是事实标准，下面这段是把第 04 章那条完整链路真正实现出来的样子，可以直接改改地址跑：

#!/usr/bin/env python3
# pip install ncclient  (0.6+)
import random, sys, time
from ncclient import manager
from ncclient.operations import RPCError, TimeoutExpiredError

HOST, PORT, USER, KEY = "ru-device", 830, "smo-operator", "/etc/smo/id_ed25519"

CFG = """
<config xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
    <interface>
      <name>eth0</name>
      <type xmlns:ianaift="urn:ietf:params:xml:ns:yang:iana-if-type"
            >ianaift:ethernetCsmacd</type>
      <mtu>9000</mtu>
    </interface>
  </interfaces>
</config>"""


def acquire_lock(m, target="candidate", tries=5):
    for i in range(tries):
        try:
            m.lock(target)
            return
        except RPCError as e:
            if e.tag != "lock-denied":
                raise
            time.sleep(min(2 ** i, 16) * (0.5 + random.random()))
    raise RuntimeError("candidate 长期被占用")


with manager.connect(
        host=HOST, port=PORT, username=USER, key_filename=KEY,
        hostkey_verify=True,              # 生产必须 True，见第 02 章
        device_params={"name": "default"},  # 标准 NETCONF 设备
        timeout=120,                      # 单条 RPC 的超时，不是连接超时
        allow_agent=False, look_for_keys=False) as m:

    # ── 0. 先看它到底支持什么，别假设 ──────────────────────
    caps = {c.split("?")[0] for c in m.server_capabilities}
    has = lambda s: any(s in c for c in caps)
    if not has("candidate:1.0"):
        sys.exit("该设备无 candidate，需走 writable-running 分支")
    use_confirm = has("confirmed-commit")

    # ── 1. 只读需要的子树，别整树拉 ────────────────────────
    flt = """<interfaces xmlns="urn:ietf:params:xml:ns:yang:ietf-interfaces">
                 <interface><name>eth0</name></interface></interfaces>"""
    before = m.get_config(source="running", filter=("subtree", flt))

    # ── 2. 事务：锁 → 清残留 → 改 → 校验 → 提交 ────────────
    acquire_lock(m)
    try:
        m.discard_changes()               # candidate 是全局共享的，先清干净
        m.edit_config(target="candidate", config=CFG,
                      default_operation="merge",
                      error_option="rollback-on-error")
        if has("validate"):
            m.validate(source="candidate")

        if use_confirm:
            m.commit(confirmed=True, timeout="120",
                     persist="batch-A")          # 允许换会话确认
        else:
            m.commit()
    except (RPCError, TimeoutExpiredError) as e:
        m.discard_changes()               # 失败路径必须清 candidate
        raise
    finally:
        m.unlock("candidate")              # 无论如何都要解锁

    # ── 3. 业务验证：确认设备还活着、参数真的生效了 ────────
    after = m.get_config(source="running", filter=("subtree", flt))
    ok = "<mtu>9000</mtu>" in str(after)

    # ── 4. 确认 or 让它自动回滚 ────────────────────────────
    if use_confirm:
        if ok:
            m.commit(persist_id="batch-A")    # 二次提交 = 落定
        else:
            m.cancel_commit(persist_id="batch-A")  # 立刻回滚，不等超时

    # ── 5. 需要掉电保持时才写 startup ─────────────────────
    if ok and has("startup:1.0"):
        m.copy_config(source="running", target="startup")

这段代码里有四个"看起来多余、其实必要"的地方，也是评审别人脚本时该重点看的：

写法省掉它会怎样
开头查 server_capabilities在不支持 candidate 的设备上，脚本会在 lock 那一步报一个含义模糊的错，而不是给出可读的原因
拿到锁后 discard_changes()把上一个异常退出的会话留在 candidate 里的半截改动一起提交上去
finally: unlock()异常路径漏解锁，这台设备被挂住直到 idle timeout（可能是几十分钟）
失败时 cancel_commit 而不是干等设备要多带着坏配置跑满整个 confirm-timeout，白白延长故障时间
manager.connect() 的 timeout 是单条 RPC 的等待上限，不是 TCP 连接超时。默认值（30 s 量级）对 get-config 拉全量或者对慢设备的 commit 常常不够，超时后 ncclient 抛异常、但设备那边可能还在老老实实地执行——于是脚本以为失败去重试，设备上就出现了两次同样的操作。这是第 07 章真实案例的直接成因之一。凡是可能长耗时的 RPC，宁可把 timeout 设大到 5~10 分钟，也不要让客户端先放弃。

通知订阅：RFC 5277 的模型与它的两个限制

NETCONF 的事件通知走 RFC 5277：客户端发一条 <create-subscription>，之后服务端在同一条会话上单向推送 <notification>，直到会话关闭。没有取消订阅的 RPC——想停就断会话。

<!-- 订阅：可选 stream / filter / startTime / stopTime -->
<rpc message-id="201" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <create-subscription xmlns="urn:ietf:params:xml:ns:netconf:notification:1.0">
    <stream>NETCONF</stream>
    <filter type="subtree">
      <alarm-notif xmlns="urn:o-ran:fm:1.0"/>   <!-- 命名空间以所用模型为准 -->
    </filter>
    <startTime>2026-09-04T06:00:00Z</startTime> <!-- 有 replay 才有效 -->
  </create-subscription>
</rpc>

<!-- 之后服务端单向推送，注意它不是 rpc-reply，没有 message-id -->
<notification xmlns="urn:ietf:params:xml:ns:netconf:notification:1.0">
  <eventTime>2026-09-04T06:14:22.371Z</eventTime>
  <netconf-config-change xmlns="urn:ietf:params:xml:ns:yang:ietf-netconf-notifications">
    <changed-by><username>smo-operator</username><session-id>41</session-id></changed-by>
    <datastore>running</datastore>
    <edit><target>/if:interfaces/if:interface[if:name='eth0']</target>
          <operation>merge</operation></edit>
  </netconf-config-change>
</notification>

    while True:

        if n is None:

            continue
        handle(n.event_time, n.notification_xml)

标准里有两个流是基本可以指望的：NETCONF（默认流，RFC 5277 规定必须存在）承载通用事件；RFC 6470 又在其上定义了一组基础通知——netconf-config-change（谁在什么时候改了哪条路径，这就是免费的配置审计日志）、netconf-session-start/-end、netconf-capability-change、netconf-confirmed-commit。厂商与 O-RAN 会另外定义自己的流。

能不能补收断连期间漏掉的事件，取决于设备是否支持 replay。查 /netconf-state/streams 里该流的 replaySupport，支持才可以用 startTime 回放。嵌入式设备上 replay 缓冲通常很小（几百到几千条），或者干脆不支持——所以不能把"通知一定不会丢"写进设计假设，恢复连接后必须有一次全量状态同步（重新 <get> 当前告警列表）来对齐。

interleave 能力决定了你要开几条会话。RFC 5277 规定：如果服务端不支持 :interleave:1.0，那么一条会话在 create-subscription 之后不能再发任何其它 RPC。很多嵌入式实现确实不支持。所以规模化架构里的标准做法是两条会话：一条长连接专门收通知，一条按需连接做配置——顺带还有个好处，配置会话卡住时不影响告警上报。

与 O-RAN O1 的联系

这一切为什么和无线扯上关系

回到 O-RAN 接口：SMO 通过 O1 接口用 NETCONF/YANG 管理 O-CU/O-DU/O-RU；O-RU 还通过前传 M 平面被 NETCONF/YANG 直接管理。所以一个 O-RU 里往往就跑着一个基于 libnetconf2 的 NETCONF server，加载 O-RAN 定义的 o-ran-* YANG 模型。

所以"网络管理协议 NETCONF 为什么出现在无线 RAN 里"就完全说通了：O-RAN 把设备管理开放化，选用了成熟、结构化、可编程的 NETCONF/YANG 作为 O1 与前传 M 平面的管理协议。

先分清 O1 和前传 M 平面

两者都用 NETCONF/YANG，但它们是不同的接口、不同的对端、不同的模型族，混为一谈会让后面所有讨论都错位。

O1 接口前传 M 平面（Open Fronthaul M-Plane）
两端是谁SMO ↔ O-CU / O-DU（以及 hybrid 下的 O-RU）O-DU 和/或 NMS ↔ O-RU
规范归属O-RAN WG10（O1 接口规范）O-RAN WG4（M-Plane 规范）
模型族3GPP NRM 相关 + o-ran-* 管理模型o-ran-* 前传设备模型

设备形态通常是服务器/云化网元，资源充裕嵌入式，资源受限：CPU/内存/存储都紧

"资源受限"这一行决定了 M 平面上所有工程决策的基调：O-RU 上的 NETCONF 服务端往往只能撑个位数的并发会话、单条消息有明确的大小上限、通知缓冲很小、XML 解析本身就是一笔可观的 CPU 开销。拿管服务器的思路去管 O-RU，几乎一定会撞墙。

hierarchical 与 hybrid：谁有权管 O-RU

O-RAN WG4 定义了两种 M 平面架构模型，差别只有一件事：O-RU 上有几个 NETCONF client 连着。

O-RU 上加载的模型是 IETF 通用模型 + O-RAN 前传模型两部分。按用途大致可以分成六类（具体模块名、revision 与 feature 以所用 O-RAN WG4 M-Plane 版本发布的模型包为准，各版本之间有增删；判断设备实际支持什么，用第 05 章的 get-schema）：

最后一类里的"监督心跳"值得单独记住。M 平面上有一个 watchdog 机制：O-RU 期待 NETCONF client 周期性地调用一个复位监督定时器的 RPC，超时未收到就认为 M 平面连接已失效，进而触发重连/Call Home 流程。它解决的正是第 05 章提到的那个问题——TCP 层察觉不到对端已死。设计客户端时必须实现这个心跳，而且它的周期要短于 O-RU 侧配置的超时；"设备莫名其妙自己断开重连"最常见的原因就是心跳漏发或被慢 RPC 挤掉了。

O-RU 上电后是怎么被纳管的：Call Home

传统 NETCONF 是"网管去连设备"，这在前传场景下有三个硬伤：① O-RU 的 IP 是 DHCP 动态分配的，网管不知道它是多少；② O-RU 常在 NAT 或私网后面，网管连不进去；③ 一台从未配置过的新设备，网管压根不知道它存在。

Call Home（RFC 8071）：把 TCP 连接方向反过来——由设备主动向网管发起 TCP 连接。但连上之后协议角色不变：设备仍然是 SSH/TLS 服务端、仍然是 NETCONF 服务端，网管仍然是客户端。端口用专门分配的 4334（over SSH）/ 4335（over TLS），网管在这两个端口上监听。

"发起连接的一方却是服务端"这个反直觉设计是有意的：它让认证与授权模型完全不用改。设备照样出示服务端证书、照样校验客户端证书、照样跑同一套 cert-to-name 与 NACM，一行都不用为 Call Home 特殊处理。变的只是谁先拨号。

# 一台出厂 O-RU 从上电到被纳管，典型流程
① 上电，链路 up
② 获取 IP：DHCP（v4）或 SLAAC/DHCPv6（v6）
③ 获取"网管在哪里"：DHCP 厂商特定选项 / 预置 FQDN / 本地静态配置
④ 向 4334 或 4335 发起 TCP 连接（失败则按退避策略重试）
⑤ SSH/TLS 握手：O-RU 是服务端，出示出厂预置证书；
   网管出示自己的证书，O-RU 用 truststore 校验 → 双向认证成立
⑥ hello 交换 → 网管拿到模块清单与能力
⑦ 网管读硬件/软件清单，判断"这是谁"，与规划数据匹配
⑧ 下发运营商域工作证书、账号权限、软件包（如需升级）
⑨ 下发业务配置：接口 → 同步 → 载波 → eAxC → 时延窗
⑩ 建立通知订阅 + 启动监督心跳 → 进入常态运维
被问"Call Home 解决什么问题"时，只说"设备在 NAT 后面"是不完整的。完整的答案是它同时解决了三件事：可达性（NAT/私网/动态 IP 下网管连不进来）、发现（网管不需要维护一份"有哪些设备、IP 是多少"的清单，也不需要扫段）、以及时序（设备什么时候真正 ready 只有它自己知道，主动上报比网管轮询探测既快又省）。再补一句"协议角色不变、认证模型完全复用"，就说明你读过 RFC 而不只是听说过这个词。注意方向反转也带来新的攻击面：任何能连上 4334/4335 的东西都能声称自己是设备，所以网管侧的客户端证书校验必须严格，不能因为"是设备主动来的"就放松。

告警与 PM：NETCONF 通知能干什么，不能干什么

M 平面上主要有两类上行数据，它们的传输方式完全不同，这个区别经常被忽略：

故障管理（FM / 告警）性能管理（PM / 计数）
触发事件驱动：状态跳变时立刻发周期驱动：按测量周期汇总
典型周期 / 时延秒级上报粒度常见 15 min（也有 1 min / 5 min 档）
数据量小，一条告警几百字节大：几百到几千个计数器 × 每个测量对象
传输方式NETCONF Notification常见做法是设备生成文件、通过文件传输取走，NETCONF 只发"文件已就绪"的通知
丢了怎么办重连后全量 <get> 当前告警列表对齐文件还在设备上，可以补取

为什么 PM 要走文件而不是直接用通知？因为量级差了两三个数量级。一个测量周期内的计数器如果逐条封装成 XML 通知推出来，光 XML 标签的开销就能比数据本身大好几倍，而且要在一条会话上串行推送几千条——O-RU 那点 CPU 会被 XML 序列化吃掉。打包成文件（常见是压缩后的 XML/CSV）再一次性取走，是用"少量大传输"换掉"大量小传输"，这是所有网管系统在 PM 上的共同选择。

NETCONF 通知不适合高频遥测，原因是叠加的，不是单一的。① 编码开销：XML 冗长，同样的数值比二进制编码大数倍。② 单条会话串行：所有通知挤在一条 TCP 流上，一个慢消费者就会造成背压，进而阻塞服务端。③ 没有流控与背压语义：RFC 5277 没定义"我处理不过来了"怎么表达。④ 缺少可靠的补发：replay 支持与缓冲深度都靠不住。⑤ 推的是事件而不是数据流：想要"每 100 ms 一个采样"，标准里根本没有对应的订阅语义。
这些正是 gNMI（gRPC + Protobuf + 流式订阅）出现的动机，也是 IETF 用 RFC 8639 / 8641（Subscribed Notifications 与 YANG-Push）补齐 NETCONF 侧周期/变更订阅的原因。横向取舍见 管理协议对比，本篇不展开。

工程陷阱

真实项目里的坑

  • YANG 模型版本/依赖不匹配：client 与 server 支持的模型/revision 不一致 → RPC 被拒。上线前对齐 capabilities。
  • 大配置的性能：整树 get 慢且占内存，善用 subtree/xpath filter 只取需要的子树。
  • candidate 未 unlock：异常路径忘了 unlock 会挡住后续会话。
  • 证书/时间：TLS 证书校验依赖系统时间——设备没同步好时间会导致证书"未生效/已过期"误判（又和 时间同步 扯上关系）。
  • NACM 权限：基于 YANG 路径的访问控制配置不当，会导致"能连上但改不动"或"权限过大"。
还有一类坑不在协议里，在会话对象的并发结构上。一个 NETCONF 会话会被三个来源并发访问：IO 线程（收到 RPC）、定时器线程（会话/confirmed-commit 超时）、通知线程（数据变更要推 notification）。最直觉的做法是给会话加一把锁，于是必然踩到「持锁做 IO，对端读得慢就把整个会话卡住」和「edit-config 校验里回调业务代码、业务代码又碰这把锁 → 死锁」。
把它改成 Active Object（每会话一个邮箱、三个入口只投递不执行）能一次性消掉这一整类竞态，连"定时器到期时会话已销毁"的悬垂问题都顺带解决。改造前后的完整代码对照见 通信软件设计模式 §05；Call Home 下"设备变主动方"如何与被动方共用同一份会话代码见同篇 §03 Acceptor-Connector。

规模化：一千台设备的连接怎么管

单台设备跑通和一千台跑稳，是两个问题。核心矛盾是：设备侧能承受的并发会话数是个位数到几十，而 SMO 侧想同时对几百台做操作。

策略长连接（常驻）按需连接（用完就断）混合（推荐）
建连开销只付一次每次操作都要付（O-RU 上是秒级）只在配置时付
设备侧资源占用N 台 × 常驻会话，吃内存与会话槽位接近 01 条常驻/台
能否收通知能不能（会话断了就没有推送）能
故障感知连接断即知（配合心跳）下次操作才知道即时
SMO 侧资源N 个 socket + N 个线程/协程只占用峰值并发数N 个轻量 socket + 有限的配置 worker
设备重启后需要重连逻辑与退避无感需要重连逻辑

实践中收敛出来的架构基本是同一套：

  • 每台设备一条常驻"通知会话"：只做 create-subscription + 心跳，不发配置 RPC。它很轻（几乎不消耗 CPU），但换来了实时告警与"设备是否在线"的即时判断。这也正好绕开了 interleave 不支持的问题。
  • 一个受限并发的"配置会话池"：需要下发时才建连，用完立刻断。池的大小是全局限流阀门——它决定了同时有多少台设备在被改，也决定了 SMO 自己的 CPU/内存上限。
  • 批量作业分批 + 抖动：一千台不要一起下，切成每批几十台，批与批之间留间隔，并给每台的起始时刻加随机抖动。理由和第 04 章的重试抖动一样：同步化的批量操作会在共享环节（DNS、证书服务、日志后端、SMO 自己的数据库）上制造周期性尖峰。
  • 每台设备一把本地互斥：SMO 内部要保证同一台设备同时只有一个配置作业在跑。指望设备侧的 lock 来串行化是不够的——那只会把冲突变成一堆 lock-denied 重试。
面试里聊到这里，值得主动提一句反向的规模化手段：Call Home 让"连接管理"从推模型变成拉模型。设备主动来连，SMO 侧就不需要维护"有哪些设备、IP 是多少、现在通不通"这份状态，也不需要扫段探测；设备重启后自己会回来，退避重试的逻辑在设备侧而不是 SMO 侧。在几千台规模上，这个方向的改变比任何连接池调优都更有效。

真实案例：批量下发在部分设备上静默失败

现象。某次例行变更，SMO 向 420 台 O-RU 批量下发同一份参数调整。作业报告显示 391 台成功、29 台失败。失败的 29 台里，报告给出的原因有两种：17 台是 "RPC timeout"，12 台是 lock-denied。运维按流程重跑失败清单，第二轮又变成 8 台失败——失败集合每次都不一样，于是被判定为"网络抖动"，计划第三轮重跑。

第一个不对劲的地方：抽查发现"成功"的也不一定成功。随机挑了 20 台报告成功的设备读回配置，其中 3 台的目标参数根本没变。这一下把问题性质变了：不是"部分失败需要重试"，而是"作业报告不可信"。在这种情况下继续重跑是危险的——你不知道自己在往什么状态上叠加操作。作业被立刻叫停。

第一步：把三类失败分开，不要合并统计。把 29 台按型号、软件版本、所属 O-DU、所在批次列了一张表，立刻看出分布不是随机的：12 台 lock-denied 全部集中在 3 个站点，而 17 台 timeout 全部是同一个厂商同一个软件版本。加上那 3 台"假成功"——这是三个独立的问题，被一次批量作业同时暴露出来。合在一起看永远看不出规律。

问题一：lock-denied —— 两个 client 在抢。那 3 个站点是 hybrid 模型部署，O-DU 和 SMO 都直连 O-RU 的 M 平面。读 ietf-netconf-monitoring 的会话列表，发现持锁的 session-id 属于 O-DU：它的巡检任务每 15 分钟会锁一次 candidate 读写一小段配置。批量作业恰好和巡检窗口重叠。SMO 的重试逻辑退避到 16 秒就放弃了，而 O-DU 的巡检持锁约 20 秒——差一点点。第二轮重跑时错开了窗口，所以"好了"，这正是失败集合每次不同的原因。

问题二：17 台 timeout —— 客户端先放弃，设备还在干。在实验室复现：同一份配置在这个版本上耗时 90~110 秒，而其它厂商的设备只要 8~15 秒。SMO 侧的 RPC 超时是全局统一的 60 秒。所以客户端在 60 秒抛出 timeout、把这台标记为失败，而设备在第 95 秒老老实实地提交成功了。作业报告里的"失败"是假的——这批设备其实都配上了。更糟的是，如果第二轮重跑赶在第一次 commit 完成之前发起，就会撞上 lock-denied，把两个问题搅在一起。
继续追这 90 秒花在哪：在设备上直接 sysrepocfg --import 灌同一份配置，仍然要 80 多秒——排除了网络和 NETCONF 层。最后定位到该版本的模型里有一条 must 表达式，XPath 里用了对一个大列表的全局遍历，节点一多就退化成平方复杂度。厂商在下个版本改掉了这条约束，耗时回到 12 秒。

问题三：3 台"假成功" —— deviation 把字段悄悄变成了只读。这三台是同型号但更老的硬件批次。用 get-schema 把它们实际加载的模型拉下来对比，发现厂商为这个硬件批次发布了一份 deviation，把我们要改的那个叶子标成了 not-supported。关键在于设备的行为：它接受了 edit-config、接受了 commit、返回了 <ok/>，但那个节点根本没有被写进去——从客户端看不出任何异常。这是本案里最隐蔽的一个，因为它连错误码都没有。

为什么三个问题会同时暴露。它们平时都不出现：单台操作不会撞上巡检窗口；慢设备单独测时没人卡表；deviation 影响的三台从来没人回读过配置。批量作业的价值不只是省事，它同时还是一次覆盖全网的一致性测试——把平时藏在长尾里的差异一次性抖出来。

处置与沉淀（五条，都写进了作业框架）。
① 写后必读：每次变更结束后回读关键字段做比对，比对不通过才算失败。不要相信 <ok/>——它只保证"设备接受了这次请求"，不保证"你想改的东西真的变了"。
② 超时按设备画像分档，不用全局统一值；并且超时后的第一个动作是"回读状态"而不是"重试"。
③ 锁重试的总时长必须大于对端已知的最长持锁时间；hybrid 部署要把对端（O-DU）的周期性任务窗口当成已知参数写进配置，而不是靠试。
④ 首次纳管时用 get-schema 拉全量模型存档，并在每次软件升级后重新拉一次做 diff。deviation、revision 变化、feature 开关，这三样任何一样变了都会静默改变行为。
⑤ 作业报告要区分"确认失败"和"结果未知"。原来的框架把 timeout 归为失败，这是错的——timeout 的语义是不知道，它需要的是一次状态查询，而不是一次重试。这一条改动带来的收益最大：它让后续所有批量作业的报告第一次变得可信。

分层自测

8.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础830 和 6513 分别是什么端口？两种承载除了加密层，还有什么不同？

    830 是 NETCONF over SSH（RFC 6242）的默认端口，6513 是 NETCONF over TLS（RFC 7589）的默认端口。另外 Call Home（RFC 8071）有自己的两个端口：4334（over SSH）、4335（over TLS），由网管侧监听。

    只答端口号是基础分。要说清的是两者相同的部分和不同的部分：

    • 完全相同的是分帧。TLS 承载沿用 RFC 6242 定义的同一套分帧（]]>]]> 或 chunked），也沿用同样的 hello 协商。所以上层 NETCONF 代码一行都不用改，换传输只是换一个连接函数。
    • 不同的是身份怎么建立。SSH 里认证结果本身就是用户名；TLS 里拿到的是一张 X.509 证书，需要 cert-to-name 映射成用户名才能交给 NACM。
    • RFC 7589 强制双向认证：客户端必须出示证书。SSH 侧虽然也能做服务端认证（known_hosts），但自动化场景里经常被 hostkey_verify=False 关掉。
    • TLS 依赖系统时间（证书有效期），SSH 不依赖。这是 TLS 引入的一个全新失败模式。

    还可以补一句部署层面的差别：用独立端口（而不是复用 22）的好处是防火墙能按端口区分管理流量、NETCONF 进程崩了不影响运维登录、能单独限速统计。而且如果服务端自带 SSH 实现（netopeer2 用 libssh），它和系统 sshd 是两套独立配置——安全整改改了 sshd_config 对 830 毫无作用。

  2. 基础libnetconf2、netopeer2-server、sysrepo、libyang 各自负责什么？

    四个组件对应四件互不重叠的事，按"一条 edit-config 从网口走到硬件"的顺序：

    • libnetconf2 — 管"线"：SSH/TLS 服务端与客户端、会话生命周期、hello 协商、RFC 6242 分帧、RPC 的收发与编解码。它不理解任何业务字段，对它来说 edit-config 和 get 只是两个不同的 XML 结构。
    • netopeer2-server — 管"骨架"：把标准 RPC 翻译成 sysrepo 调用，实现 NACM 访问控制，管理会话与通知转发。它是"服务端框架"，不实现具体业务配置。
    • sysrepo — 管"状态"：running / candidate / startup / operational 的存储与差分，把变更按模块和 XPath 分发给订阅者，驱动 CHANGE → DONE / ABORT 的两阶段提交。
    • libyang — 管"规则"：编译 .yang，构造与校验数据树，执行 must/when/leafref/unique。上面三层全都建立在它的数据树之上。
    • 你的应用：订阅感兴趣的子树，在回调里把配置真正作用到硬件，并提供 operational 数据。

    加分点：厂商自研栈几乎必然是同一个分层。不管用不用开源实现，"协议/会话""事务/datastore""模型/校验""业务生效"这四件事都必须有人做、而且必须分开做——因为它们的变化频率完全不同：协议层十年不动，模型层每个版本都在扩，业务层随硬件改。糅在一起的实现最终都会因为"改一个 YANG 字段要动网络代码"而重构。

    这个分层在排障时也很有用：连不上、hello 超时、分帧错 → libnetconf2；access-denied/operation-not-supported → netopeer2；commit 卡住、模块没装 → sysrepo；must 校验失败、命名空间不对 → libyang；"提交成功但硬件没变" → 你自己的回调。

  3. 基础改配置为什么要先 <lock>？它有什么风险？

    为什么需要：candidate 是设备上全局共享的一份草稿，不是每条会话各有一份。没有锁的话，A 会话写了一半、B 会话执行 commit，就会把 A 的半成品一起提交上去；或者 A、B 交替写入，最终 candidate 里是两份改动的任意交织。锁保证的是"从 edit 到 commit 这段时间里，candidate 只归我"。

    三个风险：

    • 粒度太粗。锁的对象是整个 datastore，不是某棵子树。一个流程持锁，这台设备上所有其它自动化全部 lock-denied。（RFC 5717 定义了 partial-lock，但支持的设备不多。）
    • 忘了解锁。异常路径漏 unlock，这台设备被挂住直到空闲超时——可能是几十分钟。所以 unlock 必须写在 finally 里。
    • 僵死会话占锁。持锁的一端掉电时，TCP 另一端在没有数据要发的情况下察觉不到，锁会一直挂着。这正是"设备刚重启完反而配不了"的典型成因，需要 keepalive 与 idle timeout 来兜底。

    两条实践纪律：① 锁只覆盖 edit + validate + commit 这几秒，业务验证放到 commit 之后靠 confirmed-commit 兜底，不要持锁做长时间验证；② 拿到锁后的第一件事是 <discard-changes>，清掉上一个异常退出的会话留在 candidate 里的残留。

  4. 基础什么是 cert-to-name？为什么 TLS 承载必须有这一层？

    cert-to-name 是一张"X.509 证书 → NETCONF 用户名"的映射规则表，来自 ietf-x509-cert-to-name（RFC 7407 定义的 grouping，被 ietf-netconf-server 复用）。每条规则含优先级 id、证书或 CA 的 fingerprint、map-type，以及部分方式下的用户名。

    为什么必须有：TLS 握手结束后服务端手里只有一张证书，而 NETCONF 的访问控制 NACM（RFC 8341）是按用户名和用户组授权的。中间必须有人把证书翻译成用户名。

    更好的答法是讲设计意图：NACM 早于、也独立于传输层而存在。如果让 TLS 层直接决定权限，就等于每套传输各实现一份 ACL——SSH 一套、TLS 一套、Call Home 再一套。cert-to-name 的作用是把所有传输的认证结果收敛成同一种身份表示，从而让授权只写一遍，是典型的"加一层间接解决 N×M 问题"。

    常见 map-type：specified（规则里直接写死名字）、san-dns-name、san-rfc822-name、san-ip-address、san-any、common-name。

    工程上最关键的一点：fingerprint 既可以填叶子证书的指纹，也可以填签发它的 CA 的指纹。填叶子指纹等于白名单，每加一个客户端、每换一次证书都要去每台设备改配置——那就把 TLS 退化回了 SSH authorized_keys 的运维模型，白搭了 PKI。填 CA 指纹 + san-dns-name，才能做到"新增一个网管节点不需要碰任何一台设备"。

8.2 中级（区分熟练度）

  1. 中级SSH 还是 TLS？O-RAN 前传 M 平面为什么偏好 TLS + 双向认证？

    先给判据，再讲 O-RAN 的特殊性。决定因素不是加密强度（两者都够），而是身份管理的规模化成本。

    SSHTLS + mTLS
    服务端身份主机指纹，逐台维护 known_hosts服务端证书，一个 CA 背书全网
    客户端身份公钥，逐台灌 authorized_keys客户端证书，CA 签发
    撤销无标准机制，只能挨台删CRL / OCSP / 短周期证书
    N 台设备的轮换成本O(N) 手工可自动化
    前置投入几乎为零要先有一套 PKI

    所以小规模、设备在可信机房里、运维熟悉 SSH → 用 SSH 完全合理。TLS 的价值只有在规模上来之后才兑现。

    O-RAN 前传的四个场景条件把结论逼向了 TLS：

    • 一个网络里几百到几千台 O-RU 且持续新增，新设备接入不能要求逐台手工登记；
    • 多厂商混合组网，信任关系需要跨厂商统一治理；
    • O-RU 物理不可信——它挂在杆上、楼顶、室内分布点。设备被拆走后必须能远程作废其身份，而 SSH 公钥模型没有任何标准手段做到这一点；
    • O-RU 主动 Call Home，此时更需要确认"对面是不是真网管"，而设备侧维护网管指纹同样是 O(N)。

    加分：主动说出 TLS 的代价。① 依赖系统时间——设备时间没同步好会误判证书"未生效"，而前传恰好还没配好 PTP 时最容易踩；② CRL/OCSP 在嵌入式设备上未必可用：CRL 分发点通常是 HTTP URL，要求 O-RU 在还没被纳管、可能还没有完整路由时就能访问外网，前传隔离网里常常不成立，现实中要在"CRL 经 M 平面下发""短有效期证书自动续签""只校验链与有效期"之间选一个；③ CA 轮换必须从第一天就设计，truststore 要支持同时信任多个 CA，否则根 CA 出事时会全网失联。

  2. 中级sysrepo 的配置变更回调怎么写？CHANGE 和 DONE 有什么区别？

    用 sr_module_change_subscribe(session, module, xpath, cb, priv, priority, opts, &sub) 订阅一棵子树，回调里用 sr_get_changes_iter() + sr_get_change_tree_next() 遍历差分，拿到每个节点的操作类型（CREATED/MODIFIED/DELETED/MOVED）。

    关键是事件分阶段，这是两阶段提交：

    • SR_EV_UPDATE：校验之前，用来修改本次变更（补默认值、联动字段）。
    • SR_EV_CHANGE：校验通过、生效之前。这里只做检查与资源预留，返回错误会让整批变更回滚，客户端收到你填的错误消息。
    • SR_EV_DONE：已经写进 running 之后。这里才真正把配置作用到硬件，此时无法再拒绝。
    • SR_EV_ABORT：别人否决了本次变更，用来释放你在 CHANGE 阶段预留的资源。
    • SR_EV_ENABLED：订阅建立时先给一遍当前配置，用于重启后与硬件对齐。

    为什么不能把"写硬件"放在 CHANGE 里：如果一次 commit 涉及三个模块，你在 CHANGE 里已经改了硬件，而第三个模块的订阅者否决了，sysrepo 会告诉客户端"提交失败、配置未变更"——但你的硬件已经变了，软件配置与硬件状态从此分叉，而且没有任何地方记录这件事。

    三条必须说出来的纪律：

    • 回调在 commit 的关键路径上同步执行。你睡 30 秒，客户端的 commit 就阻塞 30 秒；你死锁，这台设备的所有配置操作从此全部超时。凡是可能长耗时的（等硬件锁定、重建小区、调外部服务）必须异步化，用 operational 数据或通知回报结果。sysrepo 有秒级的回调超时，超时即判整批失败。
    • DONE 里的失败无法回滚，只能自己产告警或触发自愈——所以 DONE 里的动作应该是"确定能成功"的那种。
    • confirmed-commit 回滚的是配置，不是副作用。你重启过的进程、发出去的告警、写进外部库的记录都不会撤销。ABORT 事件的存在就是给你写这段撤销逻辑的地方。

    关于 priority：数值大的先回调，用于有依赖顺序的场景（先建端口再建载波）。但要提醒它把模块间耦合藏进了两个整数里，代码上看不出来——能用 leafref/must 在模型里表达的依赖优先交给模型。

  3. 中级confirmed-commit 怎么用？超时该设多少？

    机制：<commit> 带 <confirmed/> 和 <confirm-timeout>，配置立刻生效但处于"待确认"状态；超时内没有收到第二条不带 confirmed 的 <commit>，设备自动回滚到提交前。用于远程改配置时防止"把自己配失联"。能力标识是 :confirmed-commit:1.1。

    三个细节，答出来才算真用过：

    • <persist> / <persist-id>：不带 persist 时，发起会话一断就立刻回滚，不等超时——这在"配断了自己"的场景下正是想要的行为。但如果要换一条会话来确认（让另一个流程做业务验证），就必须带 persist 起个名字，确认时用 persist-id 认领。
    • 可以续期：超时内再发一条带 <confirmed/> 的 commit 是刷新计时器而不是确认，适合验证时长不确定的场景。
    • 可以主动放弃：<cancel-commit> 立刻回滚，不用干等超时。验证失败时应该主动 cancel，而不是让设备多带着坏配置跑满整个超时。

    超时怎么定——判据是"多久能得出这次变更好不好的结论"：改管理网 IP/VLAN/路由 60~120 s（连通性很快有结论）；改载波/射频参数 300~600 s（要等小区重建、UE 重新接入）；批量下发几十台 600~1800 s + persist（要等整批下完再统一确认）。

    两条重要的限制：① 它只回滚配置，不撤销你的应用已经产生的副作用；② capability 宣告了不等于实现是对的——见过设备宣告 confirmed-commit:1.1 但超时后并不真回滚。这类"只在出事时才会被用到"的能力，日常流程永远不会触发它，必须在实验室实测一遍并写进设备准入清单。

  4. 中级NETCONF Notification 为什么不适合高频遥测？

    先说清它是什么：RFC 5277 的模型是客户端发一条 <create-subscription>（可带 stream / filter / startTime），之后服务端在同一条会话上单向推送 <notification>，直到会话关闭——没有取消订阅的 RPC。

    不适合高频遥测的原因是叠加的，不是单一的：

    • 编码开销：XML 冗长，同样的数值比二进制编码大数倍；序列化本身在嵌入式设备上就是可观的 CPU 开销。
    • 单条会话串行：所有通知挤在一条 TCP 流上，一个慢消费者造成背压就会阻塞服务端。
    • 没有流控与背压语义：RFC 5277 没定义"我处理不过来了"该怎么表达。
    • 补发不可靠：能不能补收断连期间的事件取决于 replaySupport，嵌入式设备上缓冲通常只有几百到几千条，或者干脆不支持。
    • 语义不对：它推的是事件，不是数据流。"每 100 ms 采一个值"这种订阅在标准里根本没有对应表达。

    那它适合什么：秒级、低频、事件驱动的东西——告警（FM）、配置变更审计（RFC 6470 的 netconf-config-change 会告诉你谁在什么时候改了哪条 XPath，这是免费的审计日志）、会话与能力变化、confirmed-commit 事件。性能计数（PM）的常见做法不是推通知，而是设备生成文件、NETCONF 只发一条"文件已就绪"，再通过文件传输取走——用"少量大传输"换掉"大量小传输"。

    业界的两条演进路径：IETF 侧用 RFC 8639 / 8641（Subscribed Notifications 与 YANG-Push）补齐了周期订阅与 on-change 订阅；另一条是 gNMI（gRPC + Protobuf + 流式订阅），从编码到传输整体换掉。横向取舍见管理协议对比篇。

    再补一个实现细节会显得你真部署过：:interleave:1.0 能力决定了架构。不支持它的服务端上，一条会话 create-subscription 之后不能再发任何其它 RPC，而很多嵌入式实现确实不支持。所以规模化的标准做法是两条会话：一条常驻收通知，一条按需做配置；顺带的好处是配置会话卡住时不影响告警上报。

8.3 高级（体现深度）

  1. 高级Call Home 解决了什么问题？它为什么把连接方向反过来却不改协议角色？

    Call Home（RFC 8071）：由设备主动向网管发起 TCP 连接，端口 4334（over SSH）/ 4335（over TLS），网管在这两个端口上监听。

    它同时解决三件事，只说"设备在 NAT 后面"是不完整的：

    • 可达性：O-RU 的 IP 是 DHCP 动态分配的，还常在 NAT 或私网后面，网管连不进去。
    • 发现：网管不需要维护一份"有哪些设备、IP 是多少"的清单，也不需要扫段探测。一台从未配置过的新设备，网管压根不知道它存在——只能由它自己来报到。
    • 时序：设备什么时候真正 ready 只有它自己知道，主动上报比网管轮询探测既快又省。

    为什么协议角色不变：连上之后，设备仍然是 SSH/TLS 服务端、仍然是 NETCONF 服务端，网管仍然是客户端。这个看起来别扭的设计是有意的——它让认证与授权模型完全不用改：设备照样出示服务端证书、照样校验客户端证书、照样跑同一套 cert-to-name 与 NACM。变的只是"谁先拨号"这一件事。如果连角色也一起反转，就要为 Call Home 单独设计一套认证与权限，那才是真正的复杂度。

    一台出厂 O-RU 的纳管流程：上电 → DHCP/SLAAC 拿 IP → 从 DHCP 厂商特定选项或预置 FQDN 得知网管在哪 → 连 4334/4335（失败按退避重试）→ SSH/TLS 握手，出示出厂预置证书，双向认证 → hello 交换拿到模块清单 → 网管读硬件/软件清单与规划数据匹配 → 下发运营商域工作证书、账号、软件包 → 下发业务配置（接口 → 同步 → 载波 → eAxC → 时延窗）→ 建立通知订阅 + 启动监督心跳。

    三个加分点：① 方向反转带来新的攻击面——任何能连上 4334/4335 的东西都能声称自己是设备，网管侧的客户端证书校验必须严格，不能因为"是设备主动来的"就放松；② 初始信任是个鸡生蛋问题，靠出厂预置的厂商 IDevID 证书破局，前提是运营商愿意信任厂商 CA；③ 在几千台规模上，Call Home 把"连接管理"从推模型变成拉模型，设备重启后自己会回来，退避重试逻辑在设备侧——这个方向的改变比任何连接池调优都更有效。

  2. 高级SMO 要管上千台设备，连接怎么管？长连接还是按需连接？

    核心矛盾要先点出来：设备侧能承受的并发会话数是个位数到几十（O-RU 是资源受限的嵌入式设备），而 SMO 侧想同时对几百台做操作。所以这不是"选一种"的问题，答"长连接"或"按需"都只能得一半分。

    长连接按需连接
    建连开销只付一次每次操作都付（O-RU 上是秒级，密钥交换很贵）
    设备侧资源吃内存与会话槽位接近 0
    能否收通知能不能
    故障感知即时下次操作才知道

    实践中收敛出来的是混合架构，四个组成部分：

    • 每台设备一条常驻"通知会话"：只做 create-subscription + 心跳，不发配置 RPC。它几乎不消耗 CPU，换来实时告警和"设备是否在线"的即时判断，同时天然绕开了 interleave 不支持的问题。
    • 一个受限并发的"配置会话池"：需要下发时才建连、用完立刻断。池的大小就是全局限流阀门，它决定了同时有多少台设备在被改，也决定了 SMO 自己的资源上限。
    • 批量作业分批 + 抖动：一千台切成每批几十台，批间留间隔，每台起始时刻加随机抖动。同步化的批量操作会在共享环节（DNS、证书服务、日志后端、SMO 数据库）上制造周期性尖峰；重试退避同样要加抖动，否则一批 worker 会形成稳定活锁——这个坑单机测试永远不出现。
    • 每台设备一把 SMO 侧的本地互斥：保证同一台设备同时只有一个配置作业。指望设备侧的 lock 来串行化是不够的，那只会把冲突变成一堆 lock-denied 重试。

    还要说超时分档：全局统一的 RPC 超时在异构设备群里必然出事——快设备 8 秒、慢设备 100 秒，取任何一个统一值都错。超时要按设备画像分档，而且必须满足"客户端超时 > 设备最长处理时间"，否则会制造"客户端认为失败、设备其实成功"的不一致状态。

    最高层的加分：如果设备支持 Call Home，就把连接管理从推模型改成拉模型——SMO 不再需要维护设备清单与可达性状态，设备重启后自己回来。在几千台规模上这是收益最大的一个架构决策。

  3. 高级NETCONF 全程加密，抓包看不到明文，怎么排障？

    先摆正方法论：NETCONF 排障靠"分层排除"，不靠"抓包看真相"。SSH 承载下的报文内容是不可解密的（SSH 没有类似 TLS 的会话密钥导出的通行做法），所以抓包只用来回答"包有没有到、TCP 层有没有异常"。

    第一步是把故障定位到分界线的哪一侧。一条命令就够：

    ssh -vvv -s -p 830 admin@device netconf

    它用纯 SSH 客户端把会话的前五步（TCP → SSH 握手 → 认证 → subsystem → hello）全部走完，把服务端的 <hello> 原样打在屏幕上。能看到 hello，说明端口、认证、subsystem、服务端进程全部正常，问题一定在你的客户端代码或模型层——排障范围一下砍掉一半，而且不需要在设备上装任何工具。反之在哪一步停下，就对应哪一类原因。

    分层看日志：SSH 层的失败在 NETCONF 服务端往往完全无感（会话根本没交到它手上），要看 sshd / libssh 的日志；hello 之后的问题在 sshd 日志里又看不出名堂，要看 netopeer2（-v3）与你自己的订阅进程。先判断卡在哪一侧，再决定看哪份日志。

    抓包还能干什么：TCP 重传、RST、零窗口、MTU 黑洞这类问题抓包完全可见，而且只有抓包能看见；TLS 承载下还能看到完整证书链与 TLS 告警码，排"证书未生效/CA 不匹配"非常直接。想看 TLS 里的明文，可以用 SSLKEYLOGFILE 把会话密钥导给 Wireshark。

    比抓包更有价值的三个信息源：① ncclient 的 DEBUG 日志会打印完整 XML，客户端侧的"我到底发了什么"一目了然；② ietf-netconf-monitoring 能读到当前会话列表（排 lock-denied 时直接看是谁持锁）与全部 schema；③ RFC 6470 的 netconf-config-change 通知记录了谁在什么时候改了哪条 XPath，是现成的审计线索。

    再给一条判据：现象是"提交成功但硬件没变"时，去比对 running 与 operational 两个 datastore——不一致就说明问题在订阅回调里被吞掉了，跟传输一点关系都没有。

    最后一句是设备准入建议：要求设备能打出足够细的 NETCONF 日志，并且能在不重启的情况下动态调整日志级别。现场故障往往不可复现，"重启一下开 debug 再看"等于放弃这次机会。

  4. 高级批量配置下发到一半失败了，设备处于什么状态？怎么恢复？

    这道题的关键是先拒绝笼统作答——"失败"至少有五种，各自的设备状态完全不同，恢复动作也不同。上来就说"回滚"的，说明没在生产上处理过。

    失败发生在设备实际状态正确恢复动作
    edit-config 报错，且用了 rollback-on-errorcandidate 干净，running 未动修正内容重试即可，无残留
    edit-config 报错，用的是默认 stop-on-errorcandidate 里留着改了一半的内容，running 未动必须 discard-changes，否则下一个 commit 会把半成品提交上去
    commit 报错running 未动（commit 是原子的）discard-changes + 查错误信息
    客户端 RPC 超时未知：设备可能还在执行，也可能已经成功回读状态，不要重试
    DONE 回调里硬件操作失败running 已变，硬件没变——软硬件分叉读 operational 比对；靠告警/自愈，配置层面回滚也救不回副作用

    第四行是最重要的一条：timeout 的语义是"不知道"，不是"失败"。客户端超时后设备很可能还在老老实实地执行，此时重试会撞上 lock-denied，或者在一个未知状态上叠加第二次操作。超时后的第一个动作必须是重新读一遍实际状态。

    "批量"还会多出一层不原子：单台设备内部有 commit 的原子性，但"420 台设备"这个层面没有任何事务语义。跨设备的一致性只能靠编排层自己实现——记录每台的实际结果、支持从断点续做、以及必要时的反向补偿。

    恢复的通用流程（顺序不能变）：

    1. 停止一切重试。状态未知时继续操作只会让它更不可知。
    2. 回读真实状态：get-config running 看配置，get / operational 看硬件实际生效值。两者不一致本身就是一条重要线索。
    3. 清残留：discard-changes；确认没有僵死会话占着锁（读 ietf-netconf-monitoring 的会话列表）。
    4. 按回读结果重新分类成"已生效/未生效/部分生效"，只对真正未生效的重做。
    5. 部分生效的最麻烦：如果有 startup 备份或变更前的完整配置快照，用 copy-config 整体恢复到已知基线再重来，比逐条补偿可靠得多。所以变更前抓一份配置快照是必须动作。

    预防才是这道题真正想听的：① error-option 显式写 rollback-on-error，失败路径必 discard-changes；② 远程改关键配置用 confirmed-commit，验证失败主动 cancel-commit；③ 写后必读——不要相信 <ok/>，它只保证"设备接受了请求"，不保证"你想改的字段真的变了"（模型 deviation 把字段标成 not-supported 时，设备会返回 <ok/> 但静默丢弃）；④ 超时按设备画像分档，保证客户端超时大于设备最长处理时间；⑤ 作业报告必须区分"确认失败"和"结果未知"，这是让报告变得可信的关键一步。
