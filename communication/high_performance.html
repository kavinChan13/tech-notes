1.2 把预算算出来：为什么这些纳秒真的重要

上面那些数字看起来都很小。让它们变得可怕的，是每包预算——把线速换算成「每个包允许花多少纳秒」之后，一切都变了。

这就是通信数据面和普通业务代码最本质的区别：业务代码的单位是毫秒，数据面的单位是纳秒。所以数据面的写法不是「优化」，而是一整套「不许做什么」的纪律：不许在包路径上分配内存、不许在包路径上进内核、不许在包路径上碰别的核在写的 cache line。

「我们的系统能跑满 10 G」在没说包长分布之前是没有信息量的——所以压测时的包长分布必须贴近真实流量，这一条在 7.2 还会再强调一次。

02

Ring Buffer 环形缓冲

生产者-消费者的基石

Ring Buffer：固定大小的数组，用读/写两个下标（head/tail）循环使用。写到末尾就绕回开头。预分配、无需动态内存、天然生产者-消费者。
生活类比：环形缓冲就像流水线上的传送带——带子长度固定，工位 A 在一头往上放零件，工位 B 在另一头取。两人不需要打招呼（不需要锁），只要各自看一眼「还有没有空位 / 还有没有零件」。真正巧妙的地方在于：A 只推进自己那一端，B 只推进自己那一端，两人永远不会去改对方的那个数——这就是它能不用锁的全部秘密。

这个结构在通信栈里无处不在：网卡驱动的 RX/TX ring、DPDK 的 rte_ring、io_uring 的 SQ/CQ 都是它。下面从最简单也最重要的形态——单生产者单消费者（SPSC）——开始讲透。

2.1 SPSC 为什么能不用锁

锁存在的意义是保护一段不能被并发打断的读-改-写。SPSC ring 恰好把所有的读-改-写都变成了单线程独占：

状态谁写谁读是否需要互斥
tail（写下标）只有生产者生产者 + 消费者不需要——单一写者，没有「两个人同时改」这回事
head（读下标）只有消费者生产者 + 消费者同上
buf[i] 的每个槽位生产者（写入时）消费者（取出时）不需要——两个下标保证了同一时刻只有一方在碰某个槽位
被问「SPSC 为什么能无锁」，只答「用了原子变量」不及格。原子变量在这里的作用不是提供互斥，而是提供可见性与顺序——下一节就讲这个。

2.2 逐行读内存序：acquire/release 在这里保证了什么

两个下标一律采用「单调递增的无界计数器，只在索引数组时才取掩码」这一约定（2.3 会讲为什么不能和另一种约定混用）：

// 单生产者单消费者 (SPSC) 环形队列 —— 完整可编译版本
#include <atomic>
#include <cstddef>

template<typename T, size_t N>  // N 必须是 2 的幂，见 2.3
class RingSPSC {
    static_assert((N & (N - 1)) == 0, "N must be a power of two");

    static constexpr size_t kLine = 64;   // x86-64 / 多数 ARM64 的 cache line

    // 三块内容各占独立的 cache line，理由见 2.4（伪共享）
    alignas(kLine) std::atomic<size_t> tail_{0};   // 只有生产者写
    alignas(kLine) std::atomic<size_t> head_{0};   // 只有消费者写
    alignas(kLine) T buf_[N];

  public:
    // ---------------- 生产者线程独占调用 ----------------
    bool push(const T& v) {
        // ① relaxed：tail_ 只有本线程会写，读到的必定是自己上次写的值。
        const size_t t = tail_.load(std::memory_order_relaxed);

        // ② acquire：与消费者的 head_.store(release) 配对，保证「消费者对
        //    buf_[h] 的读取」先于「本线程接下来的覆写」——防止把消费者
        //    还没读完的槽位提前写掉。这个方向最容易被漏掉。
        if (t - head_.load(std::memory_order_acquire) == N)
            return false;                       // 满：无界计数器的差值就是元素个数

        buf_[t & (N - 1)] = v;                  // ③ 普通写，不需要原子

        // ④ release：这是「发布」动作，保证 ③ 的数据写入不会被重排到
        //    这条 store 之后。少了它，消费者可能读到半个对象。
        tail_.store(t + 1, std::memory_order_release);
        return true;
    }

    // ---------------- 消费者线程独占调用 ----------------
    bool pop(T& out) {
        const size_t h = head_.load(std::memory_order_relaxed);   // 同 ①

        // acquire 与生产者的 release 配对：看到新 tail_ ⟹ 看到完整数据。
        if (h == tail_.load(std::memory_order_acquire))
            return false;                       // 空

        out = buf_[h & (N - 1)];

        // release：告诉生产者「这个槽位我读完了，可以覆写」。
        head_.store(h + 1, std::memory_order_release);
        return true;
    }
};

四处内存序建立的是一条单向的因果链，而不是「互斥」：

位置内存序它保证了什么去掉会怎样
读自己的下标relaxed什么都不保证，也不需要——本线程是唯一写者换成 acquire 也对，只是白付一个屏障
读对方的下标acquire与对方的 release store 配对：看到新下标 ⟹ 看到该下标之前的所有数据写入换成 relaxed：可能看到新 tail_ 却读到旧的或半写的槽位。x86 上几乎测不出来，ARM/POWER 上随机错乱——最阴的一类 bug
写自己的下标release把数据写入「钉」在下标推进之前，构成一次完整的发布换成 relaxed：tail_++ 可以被提到数据写入之前，对方读到空洞
写数据槽位普通写不需要原子性：同一时刻只有一方碰它（见 2.1）用 atomic 反而白付开销

为什么不用 seq_cst

① 实现代价（看得见的那层）

x86-64 上 acquire load 与 release store 都编译成普通 mov（TSO 天然满足），而 seq_cst 的 store 必须用 xchg 或 mov + mfence——一条全屏障，几十个周期，还会阻止 store buffer 合并写入。
AArch64 上不同：两者用的都是 LDAR/STLR，差别很小；额外代价主要出现在 RMW 与需要全序的场景。

② 语义不匹配（更本质的那层）

seq_cst 额外提供的是所有 seq_cst 操作存在一个全局单一顺序，用来解决「多个变量之间的相对顺序要被所有线程一致观察」这类问题（如 IRIW）。SPSC 需要的不是全序，而是上图那条单向因果链，这正好就是 release/acquire 配对的定义。用 seq_cst 不是「更安全」，是买了一个用不上的更强保证。

relaxed 不等于「不原子」：它仍保证不会撕裂，放弃的只是与其它变量之间的顺序保证。所以下标必须是 std::atomic，不能是裸 volatile size_t——volatile 在 C++ 里不提供任何跨线程顺序语义。内存模型本体见 C++ 内存模型。

2.3 容量为什么取 2 的幂

标准答案是「用位与代替取模」，但它只对了一半。三层理由，最后一层才是硬约束：

层次内容实际差距
① N 是运行期变量i % n 生成 div（20~40 周期且不能流水），i & (n-1) 是 1 周期。DPDK 的 rte_ring 大小是运行期参数，所以它强制要求 2 的幂约 30 周期 ≈ 10 ns，占 67 ns 预算的 15%——这一层是实打实的
② N 是编译期常量编译器会做强度削减，把 % 100 变成乘法+移位+减法，并不会真的用 div缩到 4 周期左右——还有差距但不惊人。能主动指出这一点，说明真的想过
③ 无界计数器回绕（真正的硬约束）N = 1024 时 2^64 能被 N 整除，SIZE_MAX & 1023 = 1023 而下一个 0 & 1023 = 0，序列连续；N = 1000 时 SIZE_MAX % 1000 = 615 而下一个是 0，环上凭空错位一次不是性能问题，是正确性问题。差值判满同样依赖无符号模 2^64 运算
这里有一个手写 ring 时最高频的错误：「掩码」有两种自洽的约定，混用就会出 bug。① 无界计数器约定（本文与 DPDK/folly 的做法）：下标一直递增，只在索引时取掩码，判满 tail - head == N——好处是 N 个槽位全部可用，且「已入队总数」白送。② 掩码下标约定：存回去的下标本身就在 [0, N)，判满只能写 ((t+1) & (N-1)) == head，代价是必须浪费一个槽位来区分满和空。
把「①的存法」和「②的判法」混在一起，在计数器还小于 N 时完全正常、跑过所有单元测试，然后在下标越过 N 之后开始随机判错——现象是「压测跑几秒后开始丢数据或卡死」。选定一种约定，然后在满、空、索引三处都严格遵守它。

2.4 伪共享：head/tail 必须分开放

伪共享（False Sharing）：两个线程各自读写逻辑上无关的变量，但它们恰好落在同一个 cache line（x86-64 与多数 ARM64 上 64 字节）里。缓存一致性协议的粒度是整行、不是字节——所以一方的写会让另一方持有的整行失效。逻辑上没有共享，物理上却在疯狂互相打断。
生活类比：两个人合用一张写字板，A 只写左上角、B 只写右下角，互不干扰。但规矩是「谁要写字，得先把整块板子拿到自己手上」。于是两人不停互相抢板子。解决办法不是协调他们，而是给每人一块自己的板子。

head_ 和 tail_ 各 8 字节，紧挨着声明必然同行；而它们的访问模式是最坏情况——每一次入队和每一次出队都会让对方那一行失效，没有任何间歇：

再往前一步是缓存对方的下标（folly、DPDK 都这么做）：既然对方的下标只会朝「对我更有利」的方向走，就可以拿一个陈旧的本地副本先用，只在副本显示满/空时才真正去读那条共享行——稳定流动时几十次操作才付一次跨核传输。

三个容易漏掉的伪共享位置：
① buf_ 的第一个元素——buf_ 紧跟 tail_ 而没对齐时，buf_[0] 会和 tail_ 共享一行。
② 队列对象本身在数组里——RingSPSC<T,N> queues[8] 时若单个对象大小不是 64 的倍数，相邻两个队列的头尾会互相干扰（类里用了 alignas(64) 时编译器会把类的对齐与大小都提到 64，自动解决；手工填充时要自己检查 sizeof）。
③ 「顺手放在一起」的统计计数器——把 push_count、drop_count 塞在下标旁边，等于把两个热写变量绑在一行。第 7 章的真实案例就是这么栽的。

2.5 批量出队：把同步开销摊薄

即使做了对齐和本地缓存，每次 pop 仍要付一次 release store，还要走一遍函数调用与边界判断。批量接口把这些固定开销摊到 k 个元素上——acquire 读一次 tail_、搬 k 个元素（环上可能分两段拷）、release 写一次 head_。

批大小每元素的同步开销额外收益额外代价
1（逐个 pop）1 次 acquire + 1 次 release时延最低固定开销占比最高
81/8循环体可被向量化；分支预测更稳第一个元素多等 7 个元素的到达时间
321/32典型的甜点区（DPDK 默认 burst 就在 32 附近）；可以在处理第 i 个时预取第 i+4 个（见 §6.3）批内元素总大小要能装进 L1/L2，否则前面处理的已被挤出 cache
2561/256吞吐几乎见顶——同步开销已经不是瓶颈了时延明显恶化；批数据超出 L2 后 cache miss 反噬，吞吐可能反而下降
批量化的收益是次线性且很快饱和的：从 1 到 8，每元素同步开销降 87.5%；从 32 到 256，只再降 3%，却把时延放大了 8 倍。所以「批越大越好」是错的，批大小应该按「同步开销降到总开销的 5% 以下」来定，通常落在 16~64。批处理的时延代价与双阈值折中见 §6.2。
03

Lock-Free 无锁队列

用原子操作代替锁

上一章的 SPSC ring 已经是无锁的——但它之所以简单，是因为「单一写者」这个前提把所有难点都消掉了。一旦有多个生产者要抢同一个 tail_，就必须引入读-改-写的原子性，而这才是无锁编程真正复杂的地方。

Lock-Free：无论任何一个线程在任何时刻被挂起或杀掉，其余线程仍能在有限步内完成操作。这是一个进度保证（progress guarantee），不是性能承诺。三档强弱：Obstruction-free < Lock-free < Wait-free（每个线程都在有界步数内完成）。SPSC ring 的 push/pop 其实是 wait-free 的——没有任何重试循环。
「lock-free 就是不用 mutex」是个有害的简化。准确定义里根本没提锁，提的是「一个线程停摆不会阻塞其他线程」。一段用了 while (!cas(...)) 的代码不用 mutex，但如果它在某种交错下会一直失败，它就不是 lock-free；反过来 §3.3 会看到 DPDK 的多生产者入队没有 mutex 但也不是 lock-free。

3.1 CAS 的基本用法：以 Treiber 栈为例

CAS（Compare-And-Swap）：cas(addr, &expected, desired) 原子地做「若 *addr == expected 就写入 desired 并返回 true；否则把当前值写回 expected 并返回 false」。它把「读一个值、算一个新值、写回去」变成一次不可分割的操作，并且在被抢先时告诉你被抢了。
生活类比：CAS 就像共享文档上的乐观并发编辑——你基于版本 7 改好内容，提交时说「如果现在还是版本 7，就存成版本 8」。别人先提交了，你被拒绝并被告知「现在是版本 8」，于是基于新版本重算一遍再提交。这个「重算-重试」循环就是无锁编程的基本形状，也是它的主要代价来源。
// Treiber 栈：最经典的 CAS 结构，用来展示重试循环的形状。
template<typename T>
class TreiberStack {
    struct Node { T value; Node* next; };
    std::atomic<Node*> top_{nullptr};

  public:
    // push 是安全的：新节点是本线程私有的，别人看不到它。
    void push(Node* n) {
        Node* old = top_.load(std::memory_order_relaxed);
        do {
            n->next = old;                    // 基于当前看到的栈顶算出新状态
        } while (!top_.compare_exchange_weak(
                    old, n,
                    std::memory_order_release,   // 成功：发布 n 及其 next
                    std::memory_order_relaxed)); // 失败：old 被刷新，下轮重算
        // CAS 失败时 old 被自动更新，所以循环体不需要重新 load。
    }

    // ❌ pop 的教科书版本 —— 看起来对，实际有 ABA（见 3.2）
    Node* pop_unsafe() {
        Node* old = top_.load(std::memory_order_acquire);
        while (old != nullptr) {
            Node* next = old->next;           // ⚠️ 此刻 old 可能已被别人 pop 并释放
            if (top_.compare_exchange_weak(old, next,
                    std::memory_order_acquire, std::memory_order_acquire))
                return old;
        }
        return nullptr;
    }
};

push 和 pop 的不对称是理解 ABA 的钥匙：push 里被解引用的是本线程刚造出来、还没发布的私有节点，绝对安全；pop 里被解引用的是从共享结构读到的指针，读完到 CAS 之前的这段窗口里，别的线程完全有可能已经把它摘走并 free 掉了。无锁结构的所有内存安全问题都出在这个窗口里。

3.2 ABA 问题：为什么「值没变」不等于「状态没变」

ABA 问题：线程读到某位置的值是 A，准备 CAS 时该位置已经历 A → B → A。CAS 只比较「值是不是还等于 A」，于是成功了——但线程基于的是第一个 A 时的世界状态，而那个状态早已不成立。根源是：指针的数值不足以标识对象的身份，因为内存会被回收再分配。
生活类比：你把车停在 3 号车位，回来看到 3 号位上还是一辆同款同色的车，于是开走了——中间这辆车被开走、另一个人把他的同款车停了进来。「车位号 + 车的外观」不足以确认身份，需要车牌号（版本号）。

被问「ABA 怎么解决」时，先说根因再说手段最能体现理解：根因不是 CAS 有缺陷，而是「内存复用让指针失去了唯一身份」。所有解法本质上都在给身份加上时间维度——版本号是给指针加时间戳，hazard pointer 是让读者宣告「这段时间我在用」，epoch 是让回收者等到「所有人都翻过页了」。
再补一句更实用的：工程上最省事的是最后一行——用索引 + 代数替代指针，从池里取节点。它同时解决 ABA、内存回收和分配抖动三个问题，而且和 §5 的内存池是同一套基础设施。

3.3 MPMC 为什么难写：建议用成熟库

SPSC 到 MPMC 不是「多加几个 CAS」这么简单，至少有四个新问题一起冒出来：

① 「预定」与「填好」必须分开

多个生产者用 CAS 抢 tail_ 各自拿到槽位号，然后并发地往各自的槽位写。此时 tail_ 已经推进了但槽位可能还没写完——消费者不能只看 tail_ 就取数据。必须给每个槽位加状态标记（Vyukov 的有界 MPMC 给每个 cell 加一个 sequence 字段）。

② 提交顺序 vs 预定顺序

A 抢到槽 5、B 抢到槽 6。若 B 先写完，队列里就出现「6 好了但 5 还没好」的空洞。要么消费者支持乱序取（破坏 FIFO），要么后面的生产者必须等前面的提交——而这就引入了阻塞。

③ 重试循环的活性

高竞争下 CAS 失败率飙升。lock-free 只承诺「总有一个线程成功」，但某个具体线程可能长期失败（饥饿）。表现在分位数上：P50 很好、P99.99 极差。

④ ABA 与内存回收

就是 §3.2 那一整套。有界数组式的 MPMC（Vyukov 型）能规避它——槽位预分配、用序号而非指针。这也是为什么数据面几乎都用有界数组环。

DPDK 的 rte_ring 处理②的方式值得看：生产者先用 CAS 抢下 [prod_head, prod_next) 这段独占的预定区间，各自往槽位里写（互不干扰、无需同步），最后提交时自旋等到 prod.tail 等于自己的 prod_head 才推进。这意味着一个在写数据阶段被抢占的生产者会挡住所有排在它后面的生产者，所以严格意义上 MP 模式不是 lock-free。

DPDK 敢这样设计，是因为它的工作线程 pinned 到独占核、跑轮询模式、不会被抢占——「写数据阶段耗时有上界」这个前提在它的部署模型里成立。把 rte_ring 搬到会被调度器抢占的普通线程上，这个前提就没了，表现是偶发的长尾时延（一个线程被抢占 4 ms，整条流水线停 4 ms）。DPDK 后来加的 RTS / HTS 模式正是为了缓解它。

在挑库之前，先问一个能省掉整个问题的问题：这里真的需要 MPMC 吗？大多数场景可以改成 N 个 SPSC 队列——每个生产者一条专线，消费者轮流扫。代价是消费者要轮询 N 个队列（N 小时可忽略），换来的是没有 CAS、没有竞争、每条队列都是 wait-free，还顺带获得天然的公平性与可观测性（能看出是哪个生产者在堆积）。「消除共享」永远优于「优化共享」，这是 §3.4 的主题。

3.4 无锁不等于更快：这一条必须讲透

「把锁换成无锁队列」是性能优化里最常见的错误动作之一，它常常没有效果，甚至更慢。原因有三层，一层比一层反直觉。

第一层：无竞争的锁其实很便宜

回看 §1.1：无竞争的 mutex lock+unlock ≈ 20 ns。glibc 在无竞争时就是一次用户态 CAS，根本不进内核——「加锁要陷入内核」是 futex 出现之前的旧知识。而一次无竞争的原子 RMW 本身也要 10~20 ns。所以低竞争下两者差距只有个位数纳秒，你以为省下的那几百纳秒从来不存在。

第二层：高竞争下，无锁的失败重试会主动烧钱

关键在于失败的 CAS 不是免费的——它同样要把 cache line 以独占态（RFO）拉到本核，同样让其他核的副本失效：

缓解手段是退让（backoff）：CAS 失败后指数退避（x86 的 _mm_pause() / ARM 的 yield），重试若干次后干脆 sched_yield()。但请注意这意味着什么——「加了退避的无锁」在行为上正在向「锁」收敛，这本身就说明两者差别没有直觉中那么大。（另外退避的指数必须设上限，无上限的指数退避会把时延尾巴拉得非常长。）

第三层：正确的第一步是消除共享，不是优化共享

把前两层合起来：锁和无锁的差距（几十纳秒）远小于「有没有共享写热点」的差距（几百纳秒 × 每次 × 随核数恶化）。所以优化顺序应该是：

优先级动作典型收益说明
1（最优）彻底消除共享：每核一份数据结构，只在上报时聚合共享开销归零，扩展性线性统计计数器、内存池的 per-core cache、per-core 定时器都属于这一类。唯一能真正线性扩展的做法

「无锁一定更快吗」是一道很好的筛人题。第一层：不一定——无竞争时锁只要 ~20 ns；高竞争时无锁的失败重试会持续抢 cache line、干扰赢家，吞吐可能随核数上升而下降。第二层（更能体现深度）：无锁真正的价值不是「更快」，而是三条确定性保证——① 没有优先级反转（实时系统的硬需求）；② 持有者被杀/被换出不会导致全局停摆；③ 不会死锁。所以选无锁的正确理由是「我需要进度保证」，而不是「我想更快」。
无锁代码的隐性成本也要算进决策里：极难测试（bug 依赖特定的指令交错，在 x86 上跑一万小时不出错的代码换到 ARM 上五分钟就崩，上生产前必须用 ThreadSanitizer 并在目标架构上压测）、难以调试（破坏点和崩溃点相隔很远，见 §3.2）、难以维护（一个不熟悉内存模型的同事加一行「顺手的」统计代码就可能破坏正确性）。这些是真实的工程成本，不该为了几十纳秒去付。

Zero Copy 零拷贝

别搬数据

Zero Copy：减少或消除数据在内核态与用户态、各缓冲区之间的 CPU 拷贝。注意「零」指的是零次 CPU 参与的搬运——DMA 依然要把字节从内存搬到网卡，那是设备干的活，不占 CPU 周期也不算进来。

零拷贝是这一批技术里最容易被当成万灵药的一个。要用对它，必须先回答一个具体得多的问题：在我这条路径上，拷贝到底发生在哪几处、每一处多少字节？

4.1 先搞清楚拷贝发生在哪几处

再建立一个数量级感觉：1500 B 的 memcpy 约 50~100 ns。放到 §1.2 的每包预算里看，该不该上零拷贝一算就清楚：

场景每包预算一次 1500 B 拷贝的占比结论

4.2 内核内的手段：避免用户态往返

这一类手段的共同思路是：数据本来就在内核的页里，那就别把它拿到用户态再送回去，直接在内核内部传页的「引用」。代价是用户态碰不到数据——所以它们只适用于「纯搬运、不需要看内容」的路径。

/* sendfile：文件 → socket。offset 是传入传出的，内核会更新它 */
ssize_t send_file_all(int sock, int filefd, off_t offset, size_t count) {
    size_t left = count;
    while (left > 0) {
        ssize_t n = sendfile(sock, filefd, &offset, left);
        if (n > 0) { left -= (size_t)n; continue; }
        if (n < 0 && errno == EINTR) continue;
        if (n < 0 && (errno == EAGAIN || errno == EWOULDBLOCK))
            return (ssize_t)(count - left);   /* 非阻塞：等可写再来 */
        return -1;
    }
    return (ssize_t)count;
}

/* splice：socket → socket 的零拷贝转发，必须借一个 pipe 当页容器 */
ssize_t relay_once(int from, int to, int pipefd[2]) {
    /* 建 pipe 时：pipe2(pipefd, O_NONBLOCK) 并用
       fcntl(pipefd[1], F_SETPIPE_SZ, 1 << 20) 放大容量 ——
       默认只有 64 KB，是 splice 代理吞吐上不去的头号原因。 */
    ssize_t in = splice(from, NULL, pipefd[1], NULL,
                        1 << 16, SPLICE_F_MOVE | SPLICE_F_NONBLOCK);
    if (in <= 0) return in;                /* 0 = 对端关闭 */

    ssize_t done = 0;
    while (done < in) {                     /* 短写循环 */
        ssize_t out = splice(pipefd[0], NULL, to, NULL,
                             (size_t)(in - done),
                             SPLICE_F_MOVE | SPLICE_F_MORE | SPLICE_F_NONBLOCK);
        if (out > 0) { done += out; continue; }
        if (out < 0 && errno == EINTR) continue;
        /* ⚠️ 数据已经在 pipe 里了，不能丢：EAGAIN 时必须记住
           「pipe 里还剩多少」，等 to 可写再继续，不能重新从 from 读。
           这是 splice 代理最常写错的地方。 */
        break;
    }
    return done;
}
mmap + write 不是零拷贝，只省掉了一半。它把「page cache → 用户 buf」换成了「把 page cache 直接映射进地址空间」，这一次拷贝确实没了；但后面的 write(sock, ...) 照样要把数据拷进 skb——所以是 1 次 CPU 拷贝，不是 0 次。而它引入的新代价常被低估：① 每页首次访问要走一次缺页中断（~1~3 µs/页，搬 1 MB 就是 256 次缺页 ≈ 数百 µs，可用 MAP_POPULATE 缓解）；② TLB 压力；③ munmap 要做 TLB shootdown（给所有相关核发 IPI）；④ 文件被别的进程 truncate 时，访问已消失的页会收到 SIGBUS，而不是一个可以处理的错误码。所以 mmap 适合「反复随机访问同一份大数据」，不适合「一次性顺序搬运」——后者用 sendfile/splice。

4.3 MSG_ZEROCOPY：发送侧零拷贝，以及它真实的代价

MSG_ZEROCOPY（TCP 自 Linux 4.14、UDP 自 5.0）让网卡直接 DMA 用户态缓冲区，省掉「用户 buf → skb」那一次拷贝。它是本章最值得细讲的一个，因为它的代价不在于难用，而在于它悄悄改变了缓冲区的生命周期契约：

代价具体是什么后果
页要被锁住get_user_pages 把缓冲区涉及的页 pin 住，发完再解锁按页计费的固定开销，与数据量不成正比。受 RLIMIT_MEMLOCK 限制，超了返回 ENOBUFS——必须回退到普通 send而不是重试（重试会死等）
完成通知是异步的必须再做一次 recvmsg(MSG_ERRQUEUE) 才知道哪些缓冲可回收① 多一次系统调用；② 缓冲生命周期变长且不确定——应用必须持有「在飞缓冲」池并容忍它涨大（新的抖动来源）；③ 忘了监听 EPOLLERR 就会泄漏缓冲
小包反而更慢页锁定 + 额外 syscall + 记账是固定成本；省下的是与长度成正比的 memcpy存在盈亏平衡点。内核文档给的经验值是 10 KB 量级以上才划算。MTU 大小的单包发送几乎肯定是负收益。
内核可能悄悄退化成拷贝常见触发：数据太小、需要软件校验和、要加密/分段而设备不支持、走了 veth/bridge、经过某些 netfilter 路径你以为在跑零拷贝，其实付了零拷贝 + 拷贝两份成本。必须把 SO_EE_CODE_ZEROCOPY_COPIED 做成监控指标
缓冲区不可变通知到达之前修改 buf，发出去的就是被改后的内容与「复用一个发送缓冲」的常见写法直接冲突。要么换成缓冲池 + 引用计数，要么别用
接收侧没有对称方案得用 TCP_ZEROCOPY_RECEIVE（4.18+，对齐条件苛刻）或 AF_XDP「上了 MSG_ZEROCOPY 就零拷贝了」是错的，那只是发送方向的一半
最常见的误用是「发完就复用缓冲区」。在小数据、或内核退化成拷贝时，行为看起来和普通 send 完全一样（数据正确、没有报错），所以这个 bug 能在测试环境里完全隐身。一旦流量上来、缓冲变大、零拷贝真的生效，就开始出现「偶发的报文内容错乱」——收到的包是下一条消息的内容或两条的拼接。极难定位，因为抓包看到的确实是错的，而发送侧日志打印的却是对的（日志读的是内存后来的值）。

4.4 用户态直通：DPDK 与 RDMA

前面几种都是「在内核的规则内减少拷贝」。DPDK 和 RDMA 走的是另一条路：把网卡的收发队列直接映射到用户态，让内核完全不参与数据面。

DPDK（内核旁路 + 轮询）

网卡通过 vfio-pci 从内核驱动解绑，交给用户态的 PMD；描述符环与 mbuf 都在用户态大页内存里，网卡 DMA 直接读写。拷贝、系统调用、中断全部 0 次。
代价：网卡被独占（内核栈用不了）；要一个核 100% 空转（电费、散热、容器 CPU 配额都是真实成本）；大页/IOMMU/绑核/NUMA 全要配对；协议栈要自备（F-Stack、VPP）；tcpdump 看不到任何东西，排障方式全部要换。

RDMA（远程直接内存访问）

应用把一块内存注册给网卡（pin 住并交出地址翻译表），之后网卡可直接读写它；单边操作连对端 CPU 都不参与。
代价：内存注册很贵（µs~ms 量级，必须启动时做完并复用）；编程模型完全不同（QP、CQ、WR）；RoCEv2 需要无损网络，PFC 配错会引发全网 head-of-line blocking 甚至死锁；硬件与驱动版本敏感。
适合存储、HPC、AI 参数同步；转发面用得少，因为它优化的是「大块数据的远程搬运」而不是「小包的逐包处理」。

还有一个常被忽略的中间选项：AF_XDP。它把一块用户态内存（UMEM）与网卡队列绑定，实现收发双向零拷贝，但网卡仍归内核管——可以只把一部分队列（通过 XDP 程序分流）给用户态，其余流量照常走内核栈。相比 DPDK 吞吐略低，但不需要独占网卡、不需要大页、ethtool/ip 照常可用。内核侧实现见 Linux I/O 与内核。

05

Memory Pool 内存池

预分配复用

Memory Pool：启动时一次性分配一大块内存，切成固定大小的块，运行期从池里「借还」而非 malloc/free。目标不是「让分配更快」，而是把分配的耗时从「不确定」变成「确定」。
生活类比：malloc 像去仓库领料——大多数时候柜台上就有现货（几十纳秒），偶尔要去库房找（加锁排队），偶尔库房也没有、要现场下单（mmap + 缺页，几微秒）。平均等待很短，但你永远不知道下一次会不会是那个「偶尔」。内存池的做法是开工前把当天的料全部领出来堆在工位上——每一次取料都一样快。
内存池在架构层面的落点，可以看 IoT 接入网关 · 每连接预算：那里 30 万条长连接的读缓冲从「每条常驻 64 KB」改成「每核一小组缓冲块、借用即还」，单实例内存从 37 GB 降到 3 GB。同一个技术，在那里不是为了降低延迟抖动，而是为了让单机能放下 30 万连接——同一个手段服务的质量属性可以完全不同。

5.1 为什么运行期 malloc 是延迟抖动的主要来源

问题不是「malloc 慢」——快路径只要 15~30 ns。问题是它的耗时分布有一条很长的尾巴，而这条尾巴恰好就是你的 P99.9：

路径发生条件典型耗时为什么
tcache 命中尺寸桶里有本线程缓存的块~15~30 ns纯用户态、无锁，从单链表摘头。压测时量到的基本都是这一档
tcache 空 → 走 arena本线程缓存耗尽（默认每桶只缓存 7 个块）~50~200 ns要拿 arena 的锁。线程多于 arena 时必然共享
跨线程 free在 B 线程释放 A 线程分配的块~100~300 ns块归属 A 的 arena，B 必须去锁它。「生产者分配、消费者释放」这个最常见的流水线模式恰好触发它
需要向 OS 要内存arena 也不够；大于 M_MMAP_THRESHOLD（128 KB）直接走 mmap~1~5 µs一次系统调用，还要改页表
首次 touch 新页mmap 只建了映射，物理页等第一次访问才分配~1~3 µs 每页minor page fault。1 MB 就是 256 次缺页 ≈ 数百 µs——最凶的一档
归还后又要回来超过 M_TRIM_THRESHOLD 时 glibc 把内存还给 OS，下次再要又得重来反复 µs 级「颠簸」：流量在阈值附近波动时反复归还-索取，表现为吞吐正常但时延周期性尖峰
碎片化后长期运行、尺寸混杂逐渐变差bin 搜索路径变长；更糟的是 RSS 只涨不跌（像泄漏但不是）
THP 相关停顿透明大页设为 always，内核尝试整理/压缩可达 ms 级低延迟系统通常设 madvise/never，改用显式大页
还有一个与性能无关但同样重要的理由：数据面必须有界。用 malloc 意味着「缓冲用量没有上限」——流量突增时队列会一直涨，涨到 OOM 或涨出巨大的排队时延（bufferbloat）。内存池天生有界：池空了就是明确的「拿不到缓冲」，此时可以主动丢包并计数——它把「隐性的时延恶化」变成了「显性的丢包数字」，是数据面最有价值的监控指标之一。过载时怎么优雅劣化见 通信服务的高并发。

5.2 固定大小块池：实现骨架

核心技巧是侵入式空闲链表——空闲块里反正没有有效数据，就把「下一个空闲块」的指针写在块的头几个字节里。于是元数据开销为零，分配和释放都是 O(1) 的摘头/插头。

// 固定大小块内存池：单线程版（per-core 使用，数据面最常见的形态）
class FixedPool {
    static constexpr size_t kLine = 64;
    uint8_t* base_      = nullptr;
    size_t   region_    = 0;
    void*    free_list_ = nullptr;   // 侵入式空闲链表头
    size_t   block_ = 0, capacity_ = 0, in_use_ = 0;
    size_t   fail_cnt_  = 0;         // ★ 池空次数：必须暴露成监控指标

    static size_t round_up(size_t v, size_t a) { return (v + a - 1) & ~(a - 1); }

  public:
    bool init(size_t block_size, size_t n, bool use_hugepage = true) {
        // ① 块大小对齐到 cache line：避免两个块共享一行（伪共享，见 2.4）。
        block_ = round_up(block_size < sizeof(void*) ? sizeof(void*) : block_size, kLine);

        // ② ⚠️ 反直觉的一步：block_ 恰好是 4096 这类「漂亮」的 2 的幂时，
        //    所有块的起始地址会映射到 cache 的同一组（set），明明总量装得下
        //    L1 却疯狂互相驱逐。多加一个 cache line 让地址错开。
        if ((block_ & (block_ - 1)) == 0 && block_ >= 512) block_ += kLine;

        region_ = round_up(block_ * n, 1 << 21);   // 向上取到 2 MB 边界
        int flags = MAP_PRIVATE | MAP_ANONYMOUS
                  | MAP_POPULATE;                   // ③ 立即建立物理映射 = 预热（见 5.3）
        if (use_hugepage) flags |= MAP_HUGETLB;

        void* p = mmap(nullptr, region_, PROT_READ | PROT_WRITE, flags, -1, 0);
        if (p == MAP_FAILED && use_hugepage) {
            // 大页不够时优雅退化 —— 但要记日志，
            // 否则你会以为在用大页而其实没有。
            flags &= ~MAP_HUGETLB;
            p = mmap(nullptr, region_, PROT_READ | PROT_WRITE, flags, -1, 0);
        }
        if (p == MAP_FAILED) return false;

        base_     = static_cast<uint8_t*>(p);
        capacity_ = region_ / block_;

        // ④ 倒序串成空闲链表，让先分配出去的是低地址 —— 顺序分配时
        //    地址递增，对硬件预取更友好。
        free_list_ = nullptr;
        for (size_t i = capacity_; i-- > 0; ) {
            void* blk = base_ + i * block_;
            *reinterpret_cast<void**>(blk) = free_list_;  // 指针存在块内，零元数据
            free_list_ = blk;
        }
        return true;
    }

    // 分配：摘链表头。~5~10 ns，且每次都一样 —— 这才是重点。
    void* alloc() {
        void* blk = free_list_;
        if (__builtin_expect(blk == nullptr, 0)) { ++fail_cnt_; return nullptr; }
        free_list_ = *reinterpret_cast<void**>(blk);
        ++in_use_;
        return blk;
    }

    // 释放：插链表头。刚归还的块还在 L1 里，下次 alloc 立刻拿回它 ——
    // LIFO 顺序是有意选的，对 cache 最友好。
    void free(void* blk) {
        if (!blk) return;
        *reinterpret_cast<void**>(blk) = free_list_;
        free_list_ = blk;
        --in_use_;
    }

    size_t exhausted() const { return fail_cnt_; }   // ★ 上监控
    ~FixedPool() { if (base_) munmap(base_, region_); }
};

多线程要用时，不要给上面这个池加一把锁——那会把 §3.4 的共享写热点重新引进来。正确做法是两级结构，这也是 tcmalloc、jemalloc、DPDK mempool 共同的形状：

耗时的最坏情况~100 µs+（缺页风暴、THP 整理）就是快路径——没有慢路径可走
确定性无上界有上界，这是选它的唯一真正理由

5.3 预热：别把缺页留到运行期

这是内存池最容易被漏掉的一半。mmap 成功返回不等于内存已经存在——Linux 默认惰性分配：mmap 只在页表里登记了「这段虚拟地址将来可用」，真正的物理页要等第一次访问时由缺页中断分配。

手段解决什么代价
MAP_POPULATE（mmap 标志）建立映射时就分配物理页，把缺页从运行期挪到启动期启动变慢（1 GB 约 0.3~0.8 s）；最省事的一档，优先用它
手工 touch 每页 / 把池跑一遍同上，且顺带热了空闲链表与 TLB必须写而不是读——只读会命中共享零页，等于没预热；用 volatile 做读-改-写防止被优化掉
显式大页（MAP_HUGETLB）2 MB 页把缺页次数与 TLB 项需求都降到 1/512要预留 vm.nr_hugepages；不可换出；启动时可能因碎片失败，必须准备退化路径并记日志
mlockall防止被换出（换入是 ms 级）需要 RLIMIT_MEMLOCK 或 CAP_IPC_LOCK——容器里最常见的失败点，不能静默忽略
mallopt(M_TRIM_THRESHOLD, -1) + M_MMAP_MAX=0防止 glibc 把内存还给 OS 又要回来（颠簸）RSS 保持峰值不降——这是有意的，但要向运维解释清楚
THP 设 madvise 或 never避免内核在缺页路径上做内存压缩（可达数十 ms 停顿）失去 THP 的自动收益，改用显式大页
启动后跑一段自流量再放行热掉的不只是内存，还有指令 cache、分支预测器、各级 TLB、惰性符号解析发布流程变复杂，但这是唯一能覆盖「非内存类冷启动」的手段
内存池没预热，上线首分钟 P99.9 尖峰
某转发服务改造后引入了内存池（约 1.2 GB，4 KB 普通页），稳态压测非常漂亮：P50 18 µs、P99 41 µs、P99.9 58 µs。上线后监控却显示，每个实例在滚动发布后的头 40~70 秒里 P99.9 在 2~6 ms 之间跳，之后自动恢复到 58 µs 再也不复现。
误判过程：因为「一段时间后自愈」，团队第一反应是「连接建立阶段的开销」或「路由表还没收敛」，查了两天都排除了。
转折点是有人注意到这个现象与流量无关，而且持续时长和实例的内存大小成正比。于是去看 /proc/<pid>/status：进程刚起来时 VmRSS 只有 60 MB，之后在一分钟内爬到 1.3 GB。perf stat -e page-faults 确认这一分钟里有约 30 万次 minor fault，正好是 1.2 GB / 4 KB。
修复：① 池的 mmap 加 MAP_POPULATE；② 改用 2 MB 显式大页，缺页次数从 30 万降到约 600；③ 启动时把池整个借出-归还一遍，并把这一步放进健康检查——预热没完成就不上报 ready。改完首分钟 P99.9 与稳态一致。
两条教训：① 「一段时间后自愈」的性能问题，第一个该怀疑的就是各种冷启动效应（内存页、cache、TLB、连接、JIT），而不是业务逻辑。② 压测必须包含冷启动阶段——把预热期从报告里丢掉，等于把这一类问题系统性地屏蔽掉。

侵入式空闲链表底层是一个 rte_ring用环而不是链表是为了支持批量取还——链表摘 32 个要走 32 次指针跳跃（每次可能一个 miss），环上取 32 个是一段连续内存
（无）cache_size：per-lcore 本地缓存就是 §5.2 的两级结构。配大了会「假耗尽」，配小了失去摊薄效果
块大小对齐到 cache line对象错位（channel spreading）不只对齐，还主动错开对象起始地址，让连续的 mbuf 落在不同 cache set 与不同内存通道上
裸内存块rte_mbuf：headroom + data + tailroom + 元数据headroom（默认 128 B）是关键设计：封装外层协议头时只把数据指针往前挪，不搬动 payload——这是「零拷贝」在应用层的落地方式
（无）refcnt + rte_pktmbuf_clone多播/镜像时共享同一份 payload，只复制元数据；减到 0 才真的回池
（无）mbuf 链（next + nb_segs）大包用多个 mbuf 串起来，配合 SG-DMA，避免为巨帧准备巨大的定长块
fail_cnt_rte_mempool_avail_count / rx_nombuf同一个概念：池空是必须监控的一等指标。rx_nombuf 增长意味着「网卡收到包但没有缓冲可放」，这是最典型的过载信号
被问「内存池怎么设计」时，能把这七条说出来就很扎实：① 侵入式空闲链表让元数据开销为零；② LIFO 归还顺序是刻意的（刚还的块还在 L1 里）；③ per-core 缓存 + 批量取还 + 高低双水位；④ headroom 是为了封装时不搬 payload；⑤ 块大小要对齐 cache line 但不能是漂亮的 2 的幂（否则所有块撞同一组 cache set）；⑥ 必须在使用它的那个核上预热（first-touch 决定 NUMA 归属）；⑦ 池空计数器要上监控。
最后一句最重要：选内存池的理由不是「更快」，而是「确定」——快路径上它只比 malloc 快一点点，但它没有慢路径。

Batch & Cache 友好

摊薄开销 + 榨干 CPU

前面五章处理的是「别做那些贵的事」。这一章处理剩下那些必须做的事，怎么做得便宜：把固定开销摊到一批上（批处理），以及让内存访问尽量落在快的那一档（cache 与 NUMA）。

6.1 recvmmsg / sendmmsg：一次系统调用收发一批

逐包 recvmsg 的问题不在函数本身，而在每包都要付一次内核态往返（几百纳秒到 1 µs）。一次 syscall 摊到 32 个报文上就是 10~30 ns/包——在 67 ns 的预算里，这是从「占 100%~150%」降到「占 15%~45%」的差别。还有一笔隐性收益：批内的代码路径重复执行 32 遍，指令 cache 与分支预测器都处在最热的状态，实测收益常常大于单纯的 syscall 摊薄。

/* recvmmsg / sendmmsg：批量收发 UDP（前传、GTP-U、SIP 这类都用得上） */
#define BATCH   32          /* 甜点区通常 16~64，见 6.2 */
#define BUFSZ   2048

struct RxBatch {
    struct mmsghdr      msgs[BATCH];
    struct iovec        iov [BATCH];
    struct sockaddr_in6 addr[BATCH];   /* 用 in6 以便同时容纳 v4-mapped */
    char                buf [BATCH][BUFSZ];
};

/* 只需在启动时做一次：这些结构整批复用，不要每次循环重建 */
void rx_batch_init(struct RxBatch* b) {
    memset(b->msgs, 0, sizeof b->msgs);
    for (int i = 0; i < BATCH; ++i) {
        b->iov[i].iov_base = b->buf[i];
        b->iov[i].iov_len  = BUFSZ;
        b->msgs[i].msg_hdr.msg_iov    = &b->iov[i];
        b->msgs[i].msg_hdr.msg_iovlen = 1;
        b->msgs[i].msg_hdr.msg_name   = &b->addr[i];
    }
}

int rx_batch_recv(int sock, struct RxBatch* b) {
    /* ⚠️ msg_namelen 是「传入传出」的：内核会把它改成实际地址长度。
       批量复用时必须每轮重置，否则第二轮之后拿不到完整的源地址 ——
       现象是「回包发到了错误的地址」。这是 recvmmsg 最常见的 bug。 */
    for (int i = 0; i < BATCH; ++i) {
        b->msgs[i].msg_hdr.msg_namelen = sizeof b->addr[i];
        b->msgs[i].msg_hdr.msg_flags   = 0;
        b->msgs[i].msg_len             = 0;
    }

    /* ⚠️ 不要用最后那个 timeout 参数来控制时延：内核只在「已经收到至少
       一个报文之后、报文之间」检查它。正确做法是非阻塞 + MSG_DONTWAIT，
       超时交给 epoll。 */
    int n = recvmmsg(sock, b->msgs, BATCH, MSG_DONTWAIT, NULL);
    if (n < 0) return (errno == EAGAIN || errno == EINTR) ? 0 : -1;

    for (int i = 0; i < n; ++i) {
        /* ⚠️ msg_len 是「本来的长度」而不是「拿到的长度」：报文比 BUFSZ
           大时内核会截断并置 MSG_TRUNC。不查就会解析到半个包。 */
        if (b->msgs[i].msg_hdr.msg_flags & MSG_TRUNC) { ++g_trunc; continue; }
        handle_packet(b->buf[i], b->msgs[i].msg_len, &b->addr[i]);
    }
    return n;
}

/* 发送侧：短写循环 —— sendmmsg 的部分成功是常态，不是异常 */
int tx_batch_send(int sock, struct mmsghdr* msgs, unsigned cnt) {
    unsigned sent = 0;
    while (sent < cnt) {
        int n = sendmmsg(sock, msgs + sent, cnt - sent, MSG_DONTWAIT);
        if (n > 0) {
            /* ⚠️ 返回值是「成功发出的报文数」，不是字节数。
               必须记住进度，绝不能整批重发 —— 那会造成重复报文。 */
            sent += (unsigned)n;
            continue;
        }
        if (n < 0 && errno == EINTR) continue;
        if (n < 0 && (errno == EAGAIN || errno == EWOULDBLOCK))
            break;              /* 等 EPOLLOUT，剩下的下次再发 */
        return -1;
    }
    return (int)sent;
}

6.2 批处理的代价：时延与吞吐的取舍

批处理不是免费的吞吐提升，它是一笔明确的交易：用首包时延换吞吐。理解这笔交易的关键是看清「批要攒满」这件事在低负载下意味着什么：

批策略吞吐低负载时延高负载时延适用
不批（逐包）差——每包一次 syscall最优差（过载时更差，固定开销吃掉处理能力）极低速率的控制面消息
只按数量（B=32）最优无上界，可能永远不发好基本不要单独用
只按时间（T=100 µs）中等≤ T中等（批大小不受控）速率稳定、对时延上界有硬要求
双阈值（B=32, T=50 µs）接近最优≤ T好默认选它
双阈值 + 过载时放大 B最优≤ T最优过载时优先保吞吐（不雪崩）而容忍时延恶化
T 怎么定，以及三个常见的配错：T 应该来自端到端时延预算的分配——先写下总预算（前传百微秒量级、交易系统微秒量级、普通 RPC 毫秒量级），再决定分给批处理多少（通常 5%~20%）。
三个真实的配错：① T 比总预算还大——预算 100 µs 却把 T 配成 1 ms，等于把时延交给了批处理决定。② 忘了让 epoll_wait 的超时跟随批的剩余寿命——T 配 50 µs 但 epoll_wait 写死 1 ms，那么没有新包到达时冲刷最坏被推迟到 1 ms，配置里写的 50 µs 完全没生效。③ 用粗粒度定时器驱动冲刷——挂在 1 ms 周期定时器上，时延尾巴就固定有一个 1 ms 的台阶，而且它在监控里长得很像「网络抖动」。
三个错的共同点是：配置项看起来是对的，实际生效的值完全不是它。验证方法只有一个——量出来的 P99 时延要和 T 对得上。
同一笔交易在硬件层也存在，判据完全一样：网卡中断合并（ethtool -C eth0 rx-usecs 50 rx-frames 32）就是 NIC 版的双阈值。rx-usecs 0 是逐包中断（时延最低、CPU 开销最高，高 PPS 下会中断风暴），值调大则吞吐好、时延差。两层各配 50 µs 时，最坏时延是叠加的 100 µs 而不是 50 µs——调优时必须一起算。NAPI 与软中断的实现机制见 Linux I/O 与内核。

6.3 结构体布局与预取

热冷分离：让 fast path 只碰一行

Cache 的搬运单位是 64 字节的行，不是字节。所以「读一个 4 字节字段」的真实代价是「把包含它的那 64 字节整行搬进来」——于是布局决定了 fast path 要付几次 cache miss，更决定了整个热工作集能不能装进某一级 cache：

顺序访问 vs 随机访问的量级差别同样值得单独记住：

访问模式每元素有效耗时为什么
数组顺序遍历~1~2 ns硬件预取器识别出线性模式，提前把后续行拉进来；一行 64 B 还能覆盖多个元素
数组固定步长（步长 < 2 KB）~2~10 ns预取器也能识别固定步长；但每行只用到一部分，带宽利用率下降
链表 / 指针跳跃~80~100 ns下一个地址要等当前访问返回才知道——预取器无从预测，而且这些延迟无法重叠（串行依赖链）。50~100 倍的差距
哈希表查找（随机桶）~80~100 ns / 次探测同上。所以开放地址法通常快于链地址法——冲突时的下一次探测在同一行或相邻行

结论：数据面里能用数组就别用链表，能用索引就别用指针。「链表 O(1) 插入」在纸上成立，但一次插入要付一次 ~80 ns 的随机访问，而数组尾插只要 ~1 ns。

预取：什么时候有用，什么时候是负担

批量取出之后「接下来要处理哪些包」是已知的，于是可以在处理第 i 个时用 __builtin_prefetch(pkts[i + PD]->data, 0, 3) 把第 i+PD 个的包头拉进 L1（DPDK 的标准写法）。rw 给 1 会以独占态拉行、省掉之后写入的 RFO；locality 给 0 是非临时访问（用完就丢、不污染 cache），适合「只扫一遍不回头」的大数据流。

预取有用的场景预取是负担的场景
访问模式地址提前已知但硬件预取器猜不到：批量包的包头（指针数组）、哈希表桶、树节点的下一层候选数组顺序遍历——硬件预取器早就在做了，手写纯属浪费指令槽
提前距离取「miss 延迟 ÷ 每元素耗时」，通常 3~8 个太近（数据还没到就要用）；太远（预取来的行在用之前就被挤出去了）
工作集热数据放不进 cache，miss 无法避免，只能把延迟藏起来工作集本来就装得下——那就不该有 miss，该去查为什么有
核心判据预取不减少 cache miss 的次数，它只是把 miss 的等待时间藏到别的计算后面。所以它只在「有事可做」时有用；处理逻辑极短（只改一个字段）时根本没有时间可以藏
预取是最容易「优化出负收益」的手段，因为它有三种失败方式而且都不报错：① 无效预取（距离不对，等于白付指令）；② cache 污染（挤掉了正在用的数据，反而制造新的 miss）；③ 带宽浪费（预取了最终没用到的行，在带宽已饱和的系统上直接拖慢整体）。所以预取必须「加了之后量一遍」：看 LLC-load-misses 和 IPC 有没有真的改善，而不是看代码有没有变「更优化」。距离参数必须实测扫一遍 2/4/8。

6.4 绑核与 NUMA 本地

前面所有优化都假设「线程一直在同一个核上跑、内存就在本地」。这两个假设默认都不成立，得自己去建立：

// 绑核 + NUMA 本地：顺序很重要（链接 -lnuma）
int bind_to_core(int core) {
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(core, &set);
    int rc = pthread_setaffinity_np(pthread_self(), sizeof set, &set);
    if (rc != 0) { fprintf(stderr, "setaffinity core %d: %d\n", core, rc); return -1; }
    // 验证：不要假设它成功了
    if (sched_getcpu() != core)
        fprintf(stderr, "warning: still on core %d\n", sched_getcpu());
    return 0;
}

// ★ 网卡挂在哪个 NUMA 节点上，决定了轮询线程该放哪个 socket。
//   放错的代价：每个包的描述符和数据都要跨 socket 互连搬一趟。
int nic_numa_node(const char* ifname) {
    char path[256];
    snprintf(path, sizeof path, "/sys/class/net/%s/device/numa_node", ifname);
    FILE* f = fopen(path, "r");
    if (!f) return -1;
    int node = -1;
    if (fscanf(f, "%d", &node) != 1) node = -1;
    fclose(f);
    return node;   // -1 = 单节点机器或 BIOS 没报
}

void setup_worker(const char* ifname, int core) {
    bind_to_core(core);                          // ① 先绑核

    if (numa_available() >= 0) {                 // ② 内存分配策略钉在本地节点
        int node = numa_node_of_cpu(core);
        numa_set_localalloc();
        numa_set_strict(1);                      // 本地不够时报错，而不是悄悄跨节点

        int nic_node = nic_numa_node(ifname);
        if (nic_node >= 0 && nic_node != node)
            fprintf(stderr, "warning: core %d on node %d but NIC on node %d "
                            "-- every packet will cross the interconnect\n",
                    core, node, nic_node);
    }

    // ③ 最后才分配并预热 —— first-touch 把物理页放在「第一次写它的
    //    CPU」所属的节点上。在主线程里预热完再交给 worker，等于把内存
    //    全放在主线程的节点，worker 从此每次访问都跨 NUMA。
    my_pool.init(2048, 8192);
    warm_pool(my_pool);

7.1 流水线全景

把前六章的手段按「在这条流水线的哪一段起作用」重排一遍，就能看出它们不是六个独立技巧，而是一套互相依赖的组合：

流水线位置用到的手段它依赖前面的什么省掉了什么
网卡 DMA → RX ring零拷贝（§4）+ 内存池（§5）缓冲必须预先存在且地址固定——网卡 DMA 不能等你 malloc收方向 1 次 CPU 拷贝 + 每包分配开销
轮询 / 中断 → 批量取描述符批处理（§6.1）+ 预取（§6.3）批量取出后「接下来处理谁」已知，预取才有意义每包 syscall / 中断开销；把 miss 等待藏起来
解析分帧热冷分离（§6.3）+ 消除应用层拷贝（§4.1）缓冲带 headroom（§5.4）才能「改头不搬 payload」多余的 memcpy 与 cache miss
跨线程交接SPSC ring（§2）或分片（§3.4）对齐（§2.4）+ 批量出队（§2.5）锁竞争、跨核弹跳、线程唤醒
Worker 处理绑核 + NUMA 本地（§6.4）内存池必须在这个核上预热（§5.3），否则 first-touch 把页放错节点跨 NUMA 访问、迁核导致的 cache 全冷
TX ring → 网卡批量发送（§6.1）+ 双阈值（§6.2）—每包 syscall；把时延上界钉在 T
全程不 malloc、不加锁、不进内核以上全部整条时延分布的长尾
最值得说的是「依赖」那一列——这些手段不能单点引入：① 想做零拷贝，先得有内存池；② 想做预取，先得有批处理；③ 想做 NUMA 本地，先得让内存池在正确的核上预热。反过来，「只上了一半」经常是负收益：引入内存池但没预热（§5.3）、绑了核但没做核隔离（§6.4）、开了 MSG_ZEROCOPY 但还在复用发送缓冲（§4.3）。所以真正的经验不是「知道这六个手段」，而是知道它们的前置条件。

7.2 怎么测：别凭感觉优化

前面所有手段都有明确的代价，所以「用不用」必须由测量决定。凭感觉优化的典型下场是：花两周把一个占 3% 的环节改快了 10 倍（整体改善 2.7%），同时引入了一个每月复现一次的并发 bug。

第一步：先分段归因，别先优化

端到端时延由四段构成，而它们能不能优化、该用什么手段完全不同。不先分段就动手，最常见的结果是优化了占比最小的那一段：

第二步：perf stat 判断瓶颈的性质

一条 perf stat -e cycles,instructions,LLC-load-misses,page-faults,context-switches -p <pid> -- sleep 10 同时回答「忙不忙」和「忙在哪」。判读的顺序很重要：

指标怎么算不健康时说明什么
IPC（每周期退休指令数）instructions / cycles，x86 上限约 4> 2 是计算受限；1~2 正常；< 1 是内存受限——优化方向应该是布局与访问模式而不是「减少指令数」。这一条能立刻否掉一半的错误方向
LLC-load-misses必须除以包数：绝对值毫无信息量健康的转发路径每包应在个位数次。几十次说明有一张放不进 cache 的表在被随机访问——该做的是缩小热工作集（§6.3），不是加预取
context-switches除以采样秒数绑了核还在切换 → 有阻塞操作（锁、条件变量、日志落盘、没关的 sleep），或没做核隔离，别的任务还在这个核上跑
page-faults看稳态是否持续增长持续增长 → 内存池没预热，或热路径还在 malloc（§5.3）
dTLB-load-misses同样除以包数偏高说明工作集跨了太多页 → 考虑显式大页

第三步：「加核数吞吐不涨」→ 直接上 perf c2c

伪共享是本篇里最隐蔽的问题：代码看起来完全正确，逻辑上也没有共享，只有「加核数吞吐不升反降」这一个症状。perf c2c record -a + perf c2c report --stdio 统计 HITM 事件（读到的行处于另一个核的 Modified 状态，必须从对方核搬过来），并精确告出是哪一条 cache line、行内哪几个偏移、哪两个核、哪两行代码。

perf c2c 报告的形状本身就是答案：「同一条 cache line、不同 offset、不同 CPU、同一行代码」= 教科书级的伪共享，解法是加 alignas(64)；「同一条 line、同一个 offset、不同 CPU」= 真共享，解法是消除共享或分片（§3.4）。两者解法完全不同，一定要先分清。另外：offset 相差 8 字节说明是一个 8 字节元素的数组被不同核各自写，拿地址去符号表查就找到了；RmtHitm 高则还跨了 socket，代价再大 3~4 倍。

第四步：时延必须看分位数，不能看均值

均值会被海量的快路径拉平，而 SLA 是被尾巴决定的——§5.1 那张分布图就是例子：均值 25 ns，P99.99 是 100 µs，差 4000 倍。

指标它回答什么问题陷阱
均值「总共花了多少 CPU」——容量规划有用对用户体验几乎没有信息量。「均值 20 µs」可能是稳定 20 µs，也可能是 99% 的 2 µs 加 1% 的 2 ms
P50（中位数）「典型情况」好看，但改善 P50 通常对用户无感
P99「1% 的请求有多糟」一个页面要发 100 个请求时，P99 意味着几乎每个页面都会碰到一次
P99.9 / P99.99「尾巴到底有多长」低延迟系统真正要守的指标。测准 P99.99 至少需要百万量级样本
Max「最坏情况的上界」单个离群点就能主导它；但确定性系统必须看它——「有没有上界」就是确定性的定义
标准差 / 均值±3σ（基本没用）时延分布不是正态的，它重尾且多峰，「3σ 覆盖 99.7%」在这里完全不成立

记录分位数不能靠「存下所有样本再排序」（1000 万个样本就是 80 MB，且记录本身会干扰被测系统）。标准做法是 HdrHistogram 式的对数-线性分桶：把 v 写成 2^e × (1 + f)，e 选指数桶、f 的高 7 位选子桶——相对精度恒定在约 0.8%、内存只要 30 KB、记录路径只有几条位运算（无除法、无分支）。

直方图必须每线程一份，绝不共享。共享一个直方图加一把锁，会让「测量」本身成为最大的竞争点——你测到的将是锁的时延，不是业务的时延。
同样的道理适用于打点开销：clock_gettime 约 22 ns、rdtsc 约 6~20 ns、一次直方图记录约 3~5 ns。一个包打两个点加一次记录，clock_gettime 版是 ~48 ns——在 67 ns 的预算里占 72%，全量打点会把被测系统改造成另一个系统（观测者效应）。应对按推荐顺序：① 采样（每 64/256 个包一次，必须固定或随机间隔、不能按内容筛，否则会系统性漏掉某类慢包，而那恰好是你要找的）；② 用 rdtsc（先确认 constant_tsc + nonstop_tsc）；③ 网卡硬件时间戳（开销在网卡上，且测的是「线上的时间」而不是「代码里的时间」）；④ 分段打点只在排障时开。

第五步：压测必须加真实负载

「实验室 3 µs、上线 300 µs」几乎总是压测失真，不是代码问题。五个失真源，每一个都能让结果好上一个量级：
① 流数太少——1 条流时连接状态、FIB、加密上下文全部常驻 L1；真实系统有几万到几百万条流，工作集根本装不进 cache。这一个往往单独就能解释一个量级。
② 表太小——100 条路由的 FIB 在 L1 里查表 ~1 ns，100 万条在 DRAM 里 ~80 ns/次探测。
③ 包长分布不真实——真实流量通常双峰（小 ACK + 大数据段），而小包的每包预算是大包的 1/18。
④ 没有背景噪声——生产上同时在跑日志落盘、监控采集、配置下发和别的容器，它们抢 cache、抢带宽、抢核。
⑤ 闭环压测的「协调遗漏」（coordinated omission）——客户端等上一个响应才发下一个时，系统卡顿期间它不发请求，那段时间的慢样本根本没被采集，尾部被系统性低估几个数量级。必须用固定速率的开环压测。

7.3 一个真实案例

伪共享导致多核扩展性为负：8 个 worker 比 4 个还慢
现象：一个 UDP 转发服务（GTP-U，包长以 1400 B 为主），worker 从 4 加到 8 之后总吞吐从 2.4 Mpps 掉到 1.9 Mpps，加到 16 个时掉到 1.1 Mpps。每个 worker 的 CPU 都是 100%，看起来满负荷，但产出反而少了。
先排除了什么：不是锁（fast path 一把锁都没有，每个 worker 有自己的 RX 队列、内存池、连接表分片）；不是 NUMA（核和网卡都在 node 0，other_node 基本为零）；不是网卡（各队列均衡、rx_missed 为 0）。
转折点：perf stat 显示 IPC 只有 0.31，而单 worker 时是 1.8。「加了核之后 IPC 崩掉」基本只指向核之间在争抢什么东西。于是跑 perf c2c，第一条 cache line 占了 41% 的 HITM，Pareto 显示同一条 line 上有 8 个不同偏移（0x0…0x38）、来自 8 个不同 CPU，而且都指向同一行代码。
根因：几个月前有人加了一组 per-worker 计数器，写法是最自然的那种——struct { uint64_t rx, tx, drop; } stats[MAX_WORKERS];。每个元素 24 字节，于是相邻 2~3 个 worker 的计数器落在同一条 cache line 里；每包都要 stats[id].rx++，逻辑上各写各的，物理上 8 个核在争抢 3~4 条行，每次都要把行以独占态抢过来（~60 ns）。worker 越多，争抢者越多，所以扩展性为负。
修复：struct alignas(64) WorkerStats {...}; 并用 static_assert(sizeof(WorkerStats) == 64) 钉住。改动两行、多花 320 字节，8 worker 从 1.9 升到 4.6 Mpps（2.4 倍），IPC 回到 1.7。
三条教训：① 「加核数吞吐下降」本身就是伪共享的强信号，直接上 perf c2c，不要先去翻锁。② 元凶往往不是核心数据结构，而是「顺手加的」统计、日志、调试计数器——它们不在任何人的性能审查视野里，却在最热的路径上每包执行。③ 数组化的 per-thread 数据是伪共享最高发的形态，因为「按索引分开」在逻辑上看起来已经隔离了。
这个案例适合作为整篇的收束：数据面的性能问题，绝大多数不是「算法不够好」，而是「无意中制造了共享」。共享有明的（锁、原子变量）也有暗的（伪共享、跨 NUMA 的页、共享的 L3、共享的内存带宽、共享的中断线）。暗的那些不会出现在代码评审里，只会出现在 perf c2c 和「加核数不涨」的曲线里。
🎯 本篇要点回顾
  • 数量级直觉是地基：L1 ~1 ns、DRAM ~80 ns、跨核搬一行 ~40~100 ns、有竞争的原子与 syscall ~几百 ns、线程唤醒与缺页 ~µs。10 GbE 小包的每包预算只有 67 ns。
  • Ring Buffer：SPSC 能无锁是因为「每个变量单一写者 + 误差方向保守」；acquire/release 提供的是可见性与顺序而非互斥；容量取 2 的幂更是为了计数器回绕时下标序列保持连续；head/tail 必须 alignas(64)。
  • Lock-Free：是进度保证不是性能承诺；ABA 的根因是「内存复用让指针失去唯一身份」；MPMC 别自己写；正确的第一步是消除共享而不是优化共享。
  • Zero Copy：应用层的多余拷贝通常比内核拷贝更多；它把「与长度成正比的 memcpy」换成「与长度无关的固定开销」，所以小包更慢；MSG_ZEROCOPY 的真实代价是页锁定 + 异步通知 + 缓冲区在通知前不可修改。
  • Memory Pool：选它的理由是确定性（没有慢路径）；per-core 缓存 + 批量取还 + 高低双水位；必须在使用它的那个核上预热（first-touch）；池空计数器要上监控。
  • Batch & Cache：批处理是用首包时延换吞吐，用双阈值触发（并让 epoll_wait 超时跟随批的剩余寿命）；布局优化的第一目标是把热工作集缩进某一级 cache；绑核之外还要做核隔离与网卡同 NUMA。
  • 怎么测：先用硬件时间戳分段归因；perf stat 看 IPC；perf c2c 定位伪共享；看 P99.9/P99.99 不看均值；压测必须有真实流数、真实表大小、真实包长分布、背景噪声与开环发包。

8.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础从 L1 命中到一次线程唤醒，各类操作的耗时大概是什么量级？为什么要记住它们？

    以 3 GHz 级 x86 为参考（1 周期 ≈ 0.33 ns）。绝对值随微架构差 2~3 倍，但比例关系稳定：

    • 访存阶梯：L1 ~1 ns → L2 ~4 ns → L3 ~15~40 ns → 本地 DRAM ~70~100 ns → 跨 NUMA ~120~200 ns。
    • 一致性传输：跨核搬一行 ~40~100 ns，跨 socket ~150~400 ns——后者比读本地 DRAM 还贵。
    • 同步：无竞争原子 RMW ~10~20 ns，有竞争 ~100~500 ns；无竞争 mutex ~20 ns（不进内核），有竞争 ~1~10 µs。
    • 内核与调度：空 syscall ~50 ns ~ 1 µs（跨度大是因为 KPTI/IBPB 影响很大）；线程唤醒与上下文切换 µs 级；minor page fault ~1~3 µs/页。
    • 其它：malloc 快路径 ~15~30 ns 但走 mmap + 缺页是 µs 级；memcpy 1500 B ~50~100 ns；clock_gettime ~20~25 ns。

    为什么必须记住：要拿它们和每包预算做对比。10 GbE 线速小包每包 67 ns，25 GbE 27 ns，100 GbE 6.7 ns。于是一次伪共享（+60 ns）就把 10 GbE 的预算打满，一次逐包 syscall 超支 5 倍，一次 malloc 走 mmap 超支 45 倍。

    三条最有杀伤力的对比：① 有竞争的原子操作 ≈ 几千条指令，所以「换成原子变量」不自动变快；② 一次线程唤醒 ≈ 一万次 L1 命中，所以低延迟系统宁可让一个核 100% 空转；③ 跨 socket 搬一行比读本地内存还贵，所以「有没有共享写热点」比「下面挂什么数据结构」重要得多。

  2. 基础SPSC 环形队列为什么可以不用锁？

    只答「用了原子变量」不及格——原子变量提供的是可见性，不是互斥。要答两层：

    第一层：每个共享变量都只有一个写者。锁存在的意义是保护「读-改-写」不被并发打断，而 SPSC 把所有读-改-写都变成了单线程独占（tail 只有生产者写、head 只有消费者写），于是没有需要互斥的临界区。

    第二层：双方读到对方的陈旧值时，误差方向永远是保守的。两段区间不重叠，而且各自的边界只由对方推进——对方只会让你的可用区变大，绝不会变小。所以陈旧的 head 只会让生产者以为更满（少放一个），陈旧的 tail 只会让消费者以为更空（少取一个）。过时但保守，永不越界。

    再补两句：SPSC 的 push/pop 其实是 wait-free 的（比 lock-free 更强，因为没有任何重试循环），这也解释了它为什么比必须靠 CAS 重试的 MPMC 快得多。反过来，这套推理一旦有第二个生产者就整体失效——所以正确性依赖「真的只有一个生产者」，代码里最好用 assert 或线程 ID 检查钉住。

  3. 基础环形队列的容量为什么通常取 2 的幂？

    标准答案是「位与代替取模」，但它只对了一半。三层：

    第一层（对，但有条件）：省掉 div。i % N 在 N 是运行期变量时会生成 div（20~40 周期且不能流水），而 i & (N-1) 是 1 周期。DPDK 的 rte_ring 大小是运行期参数，所以它强制要求 2 的幂——这一层是实打实的。

    第二层（最容易答错）：N 是编译期常量时差距远没那么大。编译器会做强度削减，把 % 100 变成乘法+移位+减法（约 5 周期），并不会真的用 div，差距从 30 周期缩到 4 周期左右。能主动指出这一点，说明真的想过而不是背的。

    第三层（真正的硬约束）：无界计数器回绕时，只有 2 的幂能保持下标序列连续。若 N 是 2 的幂，2^64 能被 N 整除，回绕毫无影响（SIZE_MAX & 1023 = 1023，下一个 0 & 1023 = 0）；若 N = 1000，SIZE_MAX % 1000 = 615 而下一个是 0——环上凭空错位一次，中间槽位被跳过、0 号被重复使用。同理 tail - head 判满也依赖无符号模 2^64 运算。

  4. 基础什么是伪共享？为什么 ring buffer 的 head/tail 要 alignas(64)？不做的代价有多大？

    定义：两个线程各自读写逻辑上无关的变量，但它们恰好落在同一个 cache line（x86-64 与多数 ARM64 上 64 字节）里。一致性协议的粒度是整行而不是字节，所以一方的写会让另一方持有的整行失效。逻辑上没有共享，物理上在疯狂互相打断。

    为什么 ring buffer 是最坏情况：两个下标各 8 字节，紧挨着声明必然同行；而生产者每次 push 都写 tail、读 head，消费者每次 pop 都写 head、读 tail——每一次入队和出队都会让对方那一行失效，没有任何间歇。

    代价量级：每次操作可能付一次跨核传输（同 socket ~40~100 ns，跨 socket ~150~400 ns），而命中本核 L1 的下标更新只要 ~1 ns，所以吞吐差距通常是 3~10 倍。加一个 alignas(64)、不改一行逻辑，是整个数据面投入产出比最高的一处修改。

    更进一步（加分）：除了对齐还可以缓存对方的下标——拿一个陈旧的本地副本先用，只在副本显示满/空时才真正读共享行，稳定流动时几十次操作才付一次跨核传输。folly 和 DPDK 都这么做。另外要能说出三个容易漏掉的位置（buf[0]、队列对象放进数组时的 sizeof、以及「顺手放在一起」的统计计数器）和怎么确认（perf c2c：同行不同偏移 = 伪共享，同偏移 = 真共享）。

8.2 中级

  1. 中级SPSC ring 里的 acquire / release 各保证了什么？为什么不用默认的 seq_cst？

    四个位置：读自己的下标用 relaxed（本线程是唯一写者）；读对方的下标用 acquire、写自己的下标用 release，两者配对建立 happens-before——看到新下标 ⟹ 看到该下标之前的所有数据写入；写数据槽位是普通写（同一时刻只有一方碰它，用 atomic 反而白付开销）。

    两个方向都要有 acquire，这一点最容易被漏掉：消费者的 tail.load(acquire) 保证「看到新 tail ⟹ 看到完整数据」；生产者的 head.load(acquire) 保证「消费者对该槽位的读取」先于「本线程接下来的覆写」，防止把消费者还没读完的槽位提前写掉。

    把 acquire 换成 relaxed 会怎样——这个追问很能区分人：x86 上几乎测不出来（TSO 天然不重排 load-load），代码能跑几个月；换到 ARM/POWER 上就是随机的数据错乱。这也是「无锁代码必须在目标架构上压测」的原因。

    为什么不用 seq_cst——两层：① 实现代价。x86-64 上 acquire load 与 release store 都编译成普通 mov，而 seq_cst 的 store 必须用 xchg 或 mov + mfence（全屏障，几十周期，还阻止 store buffer 合并写入）。但 AArch64 上不同：两者用的都是 LDAR/STLR，差别很小——能指出这个架构差异是加分点。② 语义不匹配（更本质）。seq_cst 额外提供的是「所有 seq_cst 操作存在全局单一顺序」，用来解决 IRIW 那类「多变量相对顺序要被所有线程一致观察」的问题；而 SPSC 需要的只是一条单向因果链，这正好就是 release/acquire 配对的定义。用 seq_cst 不是「更安全」，是买了一个用不上的更强保证。

    一个常见误解：relaxed 不等于「不原子」，它仍保证不会撕裂，放弃的只是与其它变量之间的顺序保证。所以下标必须是 std::atomic，不能用裸 volatile size_t——volatile 在 C++ 里不提供任何跨线程顺序语义。

  2. 中级什么是 ABA 问题？它是怎么产生的，有哪些解法？

    定义：线程读到某位置的值是 A，准备 CAS 时该位置已经历 A → B → A。CAS 只比较「值是不是还等于 A」，于是成功了——但线程基于的是第一个 A 时的世界状态。根因（这句最重要）：指针的数值不足以标识对象的身份，因为内存会被回收再分配。

    具体交错（Treiber 栈，初始 A→B→C）：T1 读到 top = A 与 A->next = B 后被抢占；T2 依次 pop 掉 A 和 B（都被 free），再 push 一个新节点，而 malloc 恰好把刚 free 的那块地址返回，于是新栈顶地址等于 A 但 next = C；T1 恢复后 CAS(top, A, B) 比较成功——而 B 已经被 free 了，之后任何 pop 都是 use-after-free。malloc 返回同一地址不是巧合：刚 free 的块在 tcache/fastbin 头部，下次同尺寸分配优先返回它，所以 ABA 的概率比直觉高得多。

    四种解法，本质都是「给身份加上时间维度」：

    • 带版本号的指针：把「指针 + 单调递增版本号」一起 CAS，读侧零额外开销；但 std::atomic<16B> 可能不是 is_always_lock_free，塞高位越来越危险（5 级页表、Intel LAM、ARM TBI 都在改变高位语义），版本号位数少时它自己也会回绕。
    • Hazard Pointer：读之前把指针写进本线程的公示槽并加屏障，回收方 free 前扫描所有槽。读侧要付一次 store + 屏障。用 folly::hazptr 或 C++26 的 std::hazard_pointer，不要自己写。
    • Epoch / RCU 式回收：读侧几乎零开销，但一个卡住的线程会无限期阻塞回收、内存无界增长——要求「临界区极短且不会被长时间挂起」，这恰好是内核 RCU 与 DPDK 轮询线程成立的前提。
    • 绕过它（工程上最省事）：节点从预分配的固定池里取，索引 + 代数打包进 uint64_t 做单宽 CAS。一次同时解决 ABA、内存回收、分配抖动三个问题。

    一个反问值得准备：为什么 push 没有 ABA 而 pop 有？因为 push 解引用的是本线程刚造出来、还没发布的私有节点；pop 解引用的是从共享结构读到的指针，读完到 CAS 之间的窗口里它可能已被别人摘走并释放。无锁结构的所有内存安全问题都出在这个窗口里。

  3. 中级零拷贝到底省掉了哪次拷贝？sendfile / splice / mmap 各省哪一次？

    先纠一个常见的混淆：「零拷贝」的经典语境是文件 → 网络，那里确实有 2 次 CPU 拷贝（page cache → 用户 buf → skb）；但通信设备上更常见的是网络 → 处理 → 网络，那里每方向只有 1 次内核拷贝。转发路径上根本没有 sendfile 能省的那两次，拿它去优化是无的放矢。

    • mmap + write：省掉「page cache → 用户 buf」这一次。但 write 照样要拷进 skb，所以剩 1 次不是 0 次——「mmap 是零拷贝」是错的。新代价：每页首次访问一次缺页、TLB 压力、munmap 的 TLB shootdown、以及文件被 truncate 时会收到 SIGBUS 而不是错误码。适合反复随机访问同一份大数据，不适合一次性顺序搬运。
    • sendfile：两次都省——网卡支持 SG-DMA 与校验和卸载时，内核把页引用直接挂进 skb。代价是数据完全不进用户态：不能改、不能算校验、不能加密；源必须是普通文件、目的必须是 socket。
    • splice：同样 0 次且不限于文件源，代价是至少一端必须是 pipe。两个实操坑：默认 pipe 容量只有 64 KB；EAGAIN 时 pipe 里的残留必须自己记账，不能重新从源读，写错就丢数据。

    但最该先做的是第四件事：数清自己代码里的拷贝。真实收包路径常常是——recvmsg 到栈上数组、memcpy 进 vector 保存、解析时 memcpy 出字段、转发前重新序列化、日志再拷一份、入队时深拷贝。内核那 1 次是必要的，应用这 5 次是白搬的，而消除它们几乎没有代价。

    该不该上零拷贝，用每包预算算：1500 B 拷贝约 50~100 ns。10 GbE 大包预算 1.23 µs → 占 6%，不是瓶颈；100 GbE 大包预算 123 ns → 占 60%，必须零拷贝；10 GbE 小包 64 B 只需 ~5 ns → 小包的瓶颈从来不是拷贝而是每包固定开销。

  4. 中级内存池为什么要预热？不预热会观察到什么现象？

    因为 mmap 成功返回不等于内存已经存在。Linux 默认惰性分配：mmap 只在页表里登记「这段虚拟地址将来可用」，真正的物理页要等第一次访问时由缺页中断分配，每次 ~1~3 µs。

    现象（一个 1 GB 池、4 KB 页）：启动时 mmap 只花 ~20 µs，VSZ = 1 GB 而 RSS ≈ 0，健康检查全部通过。上线后每碰到新页就一次缺页——262 144 次、合计 0.26~0.79 秒，随机撒在头一分钟里。于是：吞吐正常（平均下来看不出来）、P99.9 在头一分钟里比稳态高 10~100 倍、每次重启/扩容都重现然后自动「痊愈」，而稳态压测怎么也复现不出来——被当成「预热期」丢掉的那一段正是问题本身。更糟的两种情况：内存有压力时缺页可能触发页面回收（kswapd），单次从 µs 跳到 ms；THP 设为 always 时可能触发内存压缩，停顿可达数十 ms。

    怎么预热（按推荐顺序）：

    • mmap 加 MAP_POPULATE——最省事，把缺页从运行期挪到启动期（1 GB 约 0.3~0.8 s）。
    • 手工 touch 每页 / 把池整个借出-归还一遍。⚠️ 必须「写」而不是「读」——只读匿名页会命中共享的零页，物理页并没有真正分配。
    • 显式大页（MAP_HUGETLB）——把缺页次数与 TLB 项需求都降到 1/512。启动时可能因碎片失败，必须准备退化路径并记日志。
    • mlockall 防止被换出（换入是 ms 级）——容器里最常见的失败点，不能静默忽略。
    • mallopt(M_TRIM_THRESHOLD, -1) + M_MMAP_MAX=0 防止 glibc 把内存还给 OS 又要回来（副作用是 RSS 保持峰值不降，要和运维说清楚）。
    • 把预热放进健康检查：没完成就不上报 ready，负载均衡不会把流量打进来。

    两个容易漏掉的关键点：① 预热必须在「将来使用这块内存的那个线程」上做，且要在绑核之后。Linux 的 first-touch 策略把物理页放在「第一次写它的 CPU」所属的节点上——在主线程里预热完再交给 worker，等于把内存全放在主线程的节点。正确顺序：绑核 → 分配 → 预热 → 进包循环。② 要热的不只是内存页，还有指令 cache、分支预测器、各级 TLB、惰性符号解析——只能靠「启动后跑一段自流量再放行」。

8.3 高级（体现深度）

  1. 高级无锁一定比加锁更快吗？什么时候反而该用锁？

    不一定，而且高竞争下常常更慢。理由有三层，一层比一层反直觉。

    第一层：无竞争的锁其实很便宜。glibc 的 pthread_mutex_lock 在无竞争时就是一次用户态 CAS，根本不进内核——「加锁要陷入内核」是 futex 之前的旧知识。无竞争的 lock+unlock 约 20 ns，而无竞争的原子 RMW 本身也要 10~20 ns，所以低竞争下两者差距只有个位数纳秒。

    第二层（关键）：高竞争下，无锁的失败重试会主动烧钱。失败的 CAS 不是免费的——它同样要以独占态（RFO）把 cache line 拉到本核。于是锁的输家会让出核、停止产生总线流量，赢家独占那条 line 连续操作（吞吐随核数持平）；而朴素无锁的输家持续把行抢回自己核、干扰赢家，行在核间弹跳，吞吐随核数下降——同一个计数器自增，8 线程只有单线程的 1/20。这不是「无锁写得不好」，而是「多核共享一个写热点」的固有代价，换成 mutex 也快不了多少。缓解手段是退让（指数退避，必须设上限）——但「加了退避的无锁」正在向「锁」收敛。

    第三层：正确的第一步是消除共享。优化顺序：① 彻底消除共享（每核一份，只在上报时聚合）→ ② 分片 → ③ 改成 N 条 SPSC 专线 → ④ 批量化（与前三条正交）→ ⑤ 最后才考虑换无锁结构。

    那什么时候该选无锁？——当你要的是确定性而不是速度：① 没有优先级反转（实时系统的硬需求）；② 持有者被杀或被换出不会导致全局停摆；③ 不会死锁。

    反过来该用锁的场景：临界区较长（锁的固定开销占比小，而无锁的重试代价随临界区长度线性放大）；操作涉及多个数据结构需要原子地一起改；竞争本来就低；以及团队维护能力有限——bug 依赖特定指令交错（x86 的 TSO 会掩盖大量内存序错误，换到 ARM 上五分钟就崩）、破坏点与崩溃点相隔很远、一个不熟悉内存模型的同事加一行「顺手的」统计就可能破坏正确性。

  2. 高级MSG_ZEROCOPY 的代价是什么？什么情况下它反而更慢？

    MSG_ZEROCOPY（TCP 自 Linux 4.14、UDP 自 5.0）让网卡直接 DMA 用户态缓冲，省掉「用户 buf → skb」那次拷贝。它的代价不在于难用，而在于它悄悄改变了缓冲区的生命周期契约。六项代价：

    • 页要被锁住：get_user_pages 把涉及的页 pin 住，是按页计费、与数据量不成正比的固定开销。超了 RLIMIT_MEMLOCK 返回 ENOBUFS——必须回退到普通 send 而不是重试（重试会死等）。
    • 完成通知是异步的：必须再做一次 recvmsg(MSG_ERRQUEUE)，从 sock_extended_err（ee_origin == SO_EE_ORIGIN_ZEROCOPY）里取出「已完成的 ID 闭区间」。三重后果：多一次系统调用；缓冲生命周期变长且不确定（TCP 重传可能让通知延迟几百毫秒）；epoll 要监听 EPOLLERR，忘了就泄漏缓冲。
    • 内核可能悄悄退化成拷贝：通知里带 SO_EE_CODE_ZEROCOPY_COPIED（数据太小、需要软件校验和、走了 veth/bridge 等都会触发）。此时你付了零拷贝 + 拷贝两份成本，必须把这个标志做成监控指标。
    • 缓冲区在通知前不可修改：改了，发出去的就是改后的内容（对 TCP 重传尤其致命——重传的是内存当前的值）。
    • 接收侧没有对称方案：得用 TCP_ZEROCOPY_RECEIVE（对齐条件苛刻）或 AF_XDP。
    • 忘了 setsockopt(SO_ZEROCOPY)：不开的话标志会被静默当成普通发送。

    什么时候更慢——机理要说清：它把「一次与长度成正比的 memcpy」换成「一组与长度无关的固定开销」，所以存在盈亏平衡点，数据越小越亏。内核文档给的经验值是 10 KB 量级以上才划算，MTU 大小的单包发送几乎肯定是负收益——这也解释了它对「小包高 PPS」的转发面基本没用。

    最常见的误用与它为什么能躲过测试：「发完就复用缓冲区」。在小数据、或内核退化成拷贝时，行为和普通 send 完全一样，所以这个 bug 在测试环境里能完全隐身。一旦流量上来、零拷贝真的生效，就出现「偶发的报文内容错乱」——收到的是下一条消息的内容或两条的拼接。极难定位，因为抓包看到的确实是错的，而发送侧日志打印的却是对的（日志读的是内存后来的值）。

  3. 高级批处理的时延与吞吐怎么取舍？双阈值该怎么配？

    先把交易说清楚：批处理不是免费的吞吐提升，它是用首包时延换吞吐。收益是把每包的固定开销（一次 syscall 300 ns~1 µs、一次同步）摊到 B 个包上；代价是批里第一个包必须等到批被触发。

    收益次线性且很快饱和——这决定了 B 不该很大：从 1 到 8，每包同步开销降 87.5%；从 32 到 256，只再降 3% 却把时延放大 8 倍。所以「批越大越好」是错的，B 应按「同步开销降到总开销 5% 以下」来定，通常落在 16~64。还有一个上限：批内数据总量必须装得进 L1/L2。

    为什么必须是双阈值：只按数量在 100 pps 时攒满 32 个要 320 ms，空载时前 31 个包永远发不出去——最阴的是曲线形状：负载越低，时延越大，满负载压测一切正常，上线后夜间低峰时延爆炸。只按时间则时延有了上界，但批大小不受控、低负载下摊薄完全失效。双阈值高负载数量先到（批满、吞吐最优）、低负载时间先到（时延有上界 T），真正的优越之处是自带自适应：批大小随负载自动伸缩，不需要额外的调节逻辑。

    T 怎么定：来自端到端时延预算的分配——先写下总预算（前传百微秒量级、交易系统微秒量级、普通 RPC 毫秒量级），再分给批处理 5%~20%。

    三个真实的配错，共同点是「配置项看起来对，实际生效的值完全不是它」：① T 比总预算还大；② 忘了让 epoll_wait 的超时跟随批的剩余寿命——T 配 50 µs 但 epoll_wait 写死 1 ms，没有新包时冲刷最坏被推迟到 1 ms，配置里的 50 µs 完全没生效；③ 用粗粒度定时器驱动冲刷——时延尾巴固定有一个 1 ms 的台阶，而且在监控里长得很像「网络抖动」。另外「时间阈值」要靠事件循环每一轮都检查一次才生效，包括没有新包到达的那些轮；只在入队时检查等于形同虚设。

    还要把硬件层一起看：网卡中断合并（ethtool -C eth0 rx-usecs 50 rx-frames 32）就是 NIC 版的双阈值。两层各配 50 µs 时，最坏时延是叠加的 100 µs。

    怎么验证配对了：量出来的 P99 要和 T 对得上。对不上就说明有别的东西在决定时延，去把它找出来——而不是继续调 T。

  4. 高级一个转发服务 P99 时延抖动很大，你怎么查？

    核心方法论：先用免费的统计把搜索空间劈成两半，再决定要不要上重工具。反过来做（先挂 perf record 采一小时）常常是花两天验证「问题在配置里」。另外一开始就要问一个决定方向的问题——抖动是「持续的」还是「有起止的」：有起止（启动后一分钟、每小时一次、发布后消失）几乎都是冷启动效应或周期性任务，不是代码热路径。

    第 0 步：先确认「P99 抖动」这个观测本身是真的。① 采样是否足够（测准 P99.99 需要百万量级样本）；② 压测客户端是不是闭环的——闭环有协调遗漏，尾部会被系统性低估几个数量级，必须换成固定速率的开环发包；③ 打点开销是否已经改变了被测系统（一个包打两个 clock_gettime 就 44 ns，在 67 ns 的预算里占 66%）。

    第 1 步：分段定位。用网卡硬件时间戳（SO_TIMESTAMPING）对比应用收到的时刻：两者相差很大就说明问题在内核/调度，不在你的代码——这一步能立刻排掉一半方向。同时看 ethtool -S、nstat、以及应用自己的队列满/池空计数。

    第 2 步：perf stat 判断瓶颈性质。IPC > 2 是计算受限、< 1 是内存受限（优化方向是布局与访问模式，不是减少指令数）；LLC-load-misses 除以包数健康值是个位数；context-switches 绑了核还在切换 → 有阻塞调用或没做核隔离；page-faults 稳态持续增长 → 内存池没预热或热路径还在 malloc。

    第 3 步：「加核数吞吐不涨甚至下降」→ 直接上 perf c2c。这个症状本身就是伪共享的强信号，不要先去翻锁。「同一行、不同偏移、不同 CPU、同一行代码」= 伪共享（加 alignas(64)）；「同一行、同一偏移、不同 CPU」= 真共享（要消除共享或分片）。RmtHitm 高则还跨了 socket。元凶往往是「顺手加的」统计/日志/调试计数器，尤其是写成 xxx[thread_id] 的数组。

    第 4 步：排查抖动的经典来源（按命中率排）：

    • 热路径上的内存分配：malloc 快路径 20 ns 但走 mmap + 缺页是 µs 级，THP 整理可达 ms 级。查 page-faults，内存池加 MAP_POPULATE + 大页 + mlockall。
    • 没做核隔离 / 中断落在业务核上：查 context-switches、/proc/interrupts、irqbalance 有没有把中断亲和改回去。
    • NUMA 放错：numastat 看 other_node；特别要查网卡的 numa_node 与轮询核是否同 socket；也要检查内存池是不是在 worker 线程、绑核之后才预热。
    • 批处理/定时器配错：P99 与配置的 T 对不上，就说明有别的东西在决定时延。
    • 动态调频与深度 C-state：唤醒要几十 µs，频率爬升期性能只有标称一半，低负载时最明显。
    • 超线程兄弟互相抢：查 thread_siblings_list。
    • 队列积压：时延随负载单调上升而 CPU 没满，那是排队而不是处理慢——去看队列深度，而不是优化处理逻辑。

    第 5 步：确认是内存受限时，优化方向是缩小热工作集。512 B × 10 万连接 = 51 MB 远超 L3，每次访问都是 DRAM（~80 ns）；热冷分离后 6.4 MB 装进 L3（~20 ns）。这个收益远大于「2 次 miss 变 1 次」。配套：字段收窄、static_assert 钉住布局、数组代替链表。

    第 6 步：实验室好、生产差，怀疑压测失真而不是代码。五个失真源：① 流数太少（这一个往往就能解释一个量级）；② 表太小；③ 包长分布不真实；④ 没有背景噪声；⑤ 闭环压测的协调遗漏。

    最后一条最实用的经验：最好的排查方式是「上线前就有指标」，而不是「出问题后再装工具」——生产环境往往不允许现场跑 perf c2c。把关键计数器做成常驻指标：池空次数、队列满次数、SO_EE_CODE_ZEROCOPY_COPIED、每包 LLC miss、IPC、P99.9/Max；直方图必须每线程一份。
