O-RAN 中的 User / Control / Management Plane

通信系统里到处是"平面（Plane）"：用户面、控制面、管理面、同步面……初学者常被绕晕。这一篇专门解决一个问题——为什么通信系统要分这么多 Plane？并把每个平面和它用的具体技术（eCPRI / O1 / NETCONF / PTP）对应起来。

Module 06 阅读 ~85 min 概念收口
01

为什么有这么多 Plane

按"职责 + 时间尺度"分离关注点

"平面"是一种逻辑分类：把流经系统的流量按用途分开——哪些是真正的业务数据、哪些是控制信令、哪些是配置管理、哪些是时间同步。为什么要分？因为它们的性能要求、可靠性要求、安全域、变化频率完全不同，混在一起既难保障又难管理。

🏢 生活类比：一栋写字楼的四套系统

用户面=员工进出办公（主营业务，量最大）；控制面=门禁/电梯调度（指挥业务怎么走）；管理面=物业配置楼宇（改规则、查报表，慢但关键）；同步面=全楼统一时钟（大家步调一致）。四套系统各走各的线路、各有优先级，坏了一套不至于全瘫——这就是"分平面"。

平面（Plane）：按流量用途划分的逻辑通道。经典三平面 = User（数据）/ Control（控制）/ Management（管理）；在前传等对时间敏感的场景再加 Sync（同步）平面。它们常常物理上共享同一张网络，靠 VLAN + QoS 隔离与优先级保障。
本篇讲的是 Open Fronthaul（O-DU ↔ O-RU，7-2x 拆分）上并行流动的 C / U / S / M 四个平面：各自传什么、时序上怎么咬合、配置与故障如何互相传染。eCPRI 报文头的逐字段拆解在 eCPRI 深入，O-RAN 其它接口（E2 / A1 / O1 / F1）在 O-RAN 接口，PTP/SyncE 的时钟原理在 PTP 与 SyncE，前传/中传/回传的分段与承载在 前传中传回传。本篇只引用它们，不重复展开。

分平面的四条硬理由

"分开关注点"是软件工程里的套话，但在前传上它是有硬约束支撑的。四条理由按重要性排：

① 时间尺度差了九个数量级。S 面的误差预算是纳秒，U 面的调度粒度是几十微秒，M 面的配置变更以天计。要为纳秒级抖动做设计（硬件时间戳、专用 PLL、逐跳边界时钟），代价极高；如果把配置下发也塞进同一条通路，就得为它付同样的代价，而它根本不需要。分平面本质上是"把昂贵的保障只花在真正需要的流量上"。

平面一次"动作"的时间尺度谁在驱动实现它需要的最贵的那个东西
Sns ~ 百 ns（误差预算）硬件时间戳单元、PLL逐跳边界时钟 / SyncE 的物理层时钟链
Cμs（提前量窗口）~ 数百 μs（时隙周期）O-DU 调度器实时线程确定性的发包时刻（时间触发发送 / TSN 整形）
U约 35.7 μs（30 kHz SCS 一个符号）O-DU L1 / 加速卡10 ~ 25 Gbps 的无损转发 + 零丢包缓存
M秒（告警）~ 天（配置）运维人员 / SMO 编排事务语义与回滚（NETCONF candidate + commit）

② 失效后果的"半径"完全不同。U 面丢一个包，损失是一个 PRB 在一个符号上的数据，上层 HARQ 重传就补回来了；S 面丢锁，整个小区的 TDD 收发切换点漂移，不但自己发不出去，还会干扰邻区。后果半径差这么大的东西，不能共用同一套保护与告警策略。

③ 安全域不同。M 面能改配置、能刷软件——拿到 M 面等于拿到基站，所以它必须做双向证书认证、必须有操作审计。U 面是海量 IQ 采样，逐包加密会把时延预算吃光。两者对"安全"的定义是冲突的，只能分开。

④ 变化频率不同，因而演进节奏不同。M 面的 YANG 模型每个 O-RAN 版本都在扩充，U 面的 IQ 格式一旦定下来就不能轻易动（涉及 FPGA/ASIC）。分平面让快变的部分和慢变的部分解耦，各自按自己的节奏升级。

CPRI 时代没有"平面"这回事

理解四平面为什么长这样，最快的路径是看它的前身。传统 CPRI 是一条恒定速率的同步串行链路：整条链路被切成固定的字节位置，控制字（Control Word）占哪些位置、IQ 数据占哪些位置，都是按规范写死的时分复用。

能力CPRI（恒定比特率）eCPRI / Open Fronthaul（分组化）
用户数据时域 IQ，占满固定时隙，无话可讲也照样发满频域 IQ，按实际调度的 PRB 发，空载几乎不占带宽
控制信息控制字里的固定字段，与数据同一条流独立的 C 面报文，需要显式的时序约定
同步内建：链路本身是同步的，从比特流里就能恢复时钟与帧头必须补一个 S 面：以太网是异步的，时间要靠 PTP 重新分发
管理厂商私有的 L1 inband 通道 / 慢速链路独立的 M 面：NETCONF/YANG，标准化、可多厂商互通
带宽随小区负载不变（与负载无关）随负载变化，可统计复用
能不能过交换机不能（点到点专用链路）能（标准以太网，可组环、可汇聚）

所以"四平面"不是谁凭空设计出来的分类学，而是把 CPRI 里原本捆在一起、由物理层免费提供的四件事，在以太网上重新显式地建出来的结果。分组化换来了统计复用和多厂商互通，代价就是：时间要自己同步（S 面）、时序要自己约定（C 面的提前量窗口）、设备要自己管（M 面）。本篇后面讲的所有陷阱，几乎都源自"以太网不再免费提供这三样"。

被问"为什么 eCPRI 要分四个平面"时，答"职责分离"只能得基础分。加分答法是把它讲成一次技术债的显式化：CPRI 用恒定速率同步链路把同步、时序、管理三件事隐含在物理层里；改成以太网后这三件事没有消失，只是从"免费"变成"要自己付费"，于是各自长成了一个平面。这也解释了为什么前传的故障里，时序类问题占比远高于带宽类问题——带宽是花钱能买的，时序不是。
02

User Plane（用户面 / 数据面）

真正搬运业务数据的那一面

  • 是什么：承载最终用户的业务数据（上网、视频、语音的实际字节；前传里就是 IQ 数据）。
  • 特点：流量最大、要求高吞吐/低时延；讲究"快"。
  • 对应技术：前传 U 平面用 eCPRI over Ethernet；核心网用面用 GTP-U。
口诀：User Plane = "干活的"。它只管把数据高效搬过去，不管为什么搬、按什么规则搬（那是控制面的事）。

前传上流的不是"用户数据"，是频域 IQ

这是最容易被误解的一点。前传的 U 面虽然叫 User Plane，但它不含任何 IP 报文、不含任何可识别的业务内容。7-2x 拆分把 iFFT/FFT、CP 添加/去除、数字波束成形放在 O-RU 侧，O-DU 侧做完调制、层映射、预编码之后，交给前传的就是一格一格的频域采样点。

RE（Resource Element）：NR 时频栅格上最小的一格 = 1 个子载波 × 1 个 OFDM 符号。每个 RE 上承载一个复数（I 分量 + Q 分量），代表这一格上的星座点。前传 U 面搬的就是这些复数。12 个连续子载波构成 1 个 PRB（Physical Resource Block）。

📊 生活类比：传"照片"还是传"每个像素的颜色值"

回传（backhaul）上流动的是 IP 报文，好比传一张 JPEG 照片——有格式、有语义、丢一张可以重发。前传 U 面流动的是频域 IQ，好比把照片拆成每个像素的 RGB 数值，按扫描顺序一行一行发过去：数据量大出一两个数量级，没有语义可言，而且某个像素来晚了就只能丢，等它没有意义——因为下一行已经该出屏了。

维度时域 IQ（CPRI / 拆分 8）频域 IQ（eCPRI / 拆分 7-2x）
采样对象整个载波带宽的时域波形每个已调度 RE 的复数
带宽是否随负载变化不变变：只发被调度到的 PRB
O-RU 需要做什么只做 DAC/ADC + 上下变频还要做 iFFT/FFT、CP、（Cat B 时）波束成形
与调度信息的耦合无（波形自带一切）强：必须由 C 面告诉 O-RU 这批 RE 放在哪
压缩空间有限（波形动态范围大）较大（同一 PRB 内幅度接近，适合分块浮点）

最后一行是关键：频域 IQ 之所以能压缩，正因为同一个 PRB 内 12 个 RE 的幅度量级接近（它们经历的信道衰落几乎相同）。这就是分块浮点能奏效的物理前提。

先算一笔带宽账：压缩不是优化，是前提

拿最常见的一档配置——100 MHz NR TDD、SCS 30 kHz——手算一遍，就能明白为什么压缩是必选项而不是可选项：

# 一、栅格参数（TS 38.104：100 MHz @ 30 kHz SCS → 273 PRB）
每 PRB          = 12 RE
时隙长度         = 0.5 ms（30 kHz SCS），每时隙 14 个 OFDM 符号
每毫秒符号数     = 14 × 2 = 28
每符号时长       = 0.5 ms / 14 ≈ 35.7 us      # U 面的"心跳"就是这个数

# 二、一条 eAxC 流（= 1 天线端口 × 1 载波 × 1 方向）每毫秒的 RE 数
273 × 12 × 28   = 91,728 RE/ms

# 三、未压缩：I、Q 各 16 bit → 32 bit/RE
91,728 × 32 bit = 2,935,296 bit/ms = 2.94 Gbps   # 仅一条流！

# 四、9-bit 分块浮点（BFP）压缩后
每 PRB 载荷 = 12 × 2 × 9 bit + 8 bit 指数 = 224 bit = 28 B
压缩比      = 28 B / 48 B ≈ 0.583
一条流       ≈ 2.94 × 0.583 ≈ 1.71 Gbps

# 五、放大到 8 层 MIMO（8 个下行 eAxC），单载波单方向
未压缩      ≈ 23.5 Gbps   ← 25GbE 加上开销直接撑爆
9-bit BFP  ≈ 13.7 Gbps   ← 25GbE 可承载，且给上行和 C/S/M 留出余量

结论很直接：不压缩的话，一个 8 层的 100 MHz 小区单方向就要吃掉 23.5 Gbps，25GbE 连一个小区都装不下；压缩之后同一根光纤还能留下十几 G 给上行与其它平面。压缩不是"省点钱"，而是"这套架构能不能成立"。

顺带算一下包速率——这是选 MTU 的依据

# 一个符号、一条 eAxC 的载荷（9-bit BFP，全带宽调度）
273 PRB × 28 B = 7,644 B

# 用 1500 B 标准 MTU：一个符号要切成 6 个包
6 × 28,000 符号/s = 168,000 pkt/s  # 每 eAxC
× 8 eAxC          ≈ 1.34 Mpps      # 仅下行，仅一个载波

# 用 9000 B jumbo：一个符号一个包就装下了
1 × 28,000 × 8    ≈ 224 kpps       # 包速率降到 1/6
这就是前传必须开 jumbo frame的量化理由：包速率降到六分之一，交换机的 pps 压力、O-RU 网卡的中断/轮询开销、以及每包 38 字节以太网开销（前导+FCS+IFG+VLAN）带来的带宽浪费都同步下降。常见的部署要求是全链路 MTU ≥ 9000（含所有中间交换机），而"某一跳的 MTU 没配够"是前传上线阶段最常见的低级故障之一——症状是大包被丢、小包正常，看起来像"随机丢包"。

分块浮点：用一个共享指数换掉一半带宽

O-RAN WG4 定义了若干压缩方法，字段 udCompMeth 标识用哪一种，udIqWidth 标识压缩后每个分量的位宽，两者合起来在报文里叫 udCompHdr。工程上用得最多的是分块浮点（Block Floating Point, BFP）。

压缩方法原理一句话典型用途 / 特点
不压缩16-bit I + 16-bit Q 原样发调试、低带宽小区、或需要绝对保真的测试场景
分块浮点 BFP一个块（常为 1 个 PRB）共享一个指数，各 RE 只存尾数事实上的主流：实现简单、无查表、压缩比稳定可预测
块缩放 Block Scaling共享一个缩放因子（乘法）而非 2 的幂指数精度略优于 BFP，但需要乘法器，硬件代价更高
μ-law非均匀量化，小信号给更多量化级动态范围大的场景更友好；需要查表，实现更重
调制压缩不发 IQ，发"这是哪个星座点"的索引压缩比最高，但要求 O-RU 知道调制方式，与 C 面耦合更深

具体的 udCompMeth 取值编码，以及"压缩 + selective RE sending"这类组合方法，以所用 O-RAN WG4 CUS 版本的取值表为准，这里不逐个列码点。

BFP 的载荷排布长这样（以 1 PRB 为一个压缩块、udIqWidth = 9 为例）：

# 未压缩：每 RE 固定 32 bit，共 48 B/PRB
[ I0(16) Q0(16) ][ I1(16) Q1(16) ] ... [ I11(16) Q11(16) ]
 <--- 4 B --->                          共 12 组 = 48 B

# 9-bit BFP：1 B 共享指数 + 12 组 9-bit 尾数对，共 28 B/PRB
[ exp(8) ][ I0(9) Q0(9) ][ I1(9) Q1(9) ] ... [ I11(9) Q11(9) ]
 udCompParam   <-- 18 bit -->              共 12 组 = 27 B

# 还原：value = mantissa << exp（定点左移，无需乘法器）
# 指数由块内幅度最大的那个 RE 决定 —— 这是精度损失的来源

注意最后一行注释：指数是块内共享的，由幅度最大的 RE 决定。于是同一个 PRB 里那些幅度小的 RE 就损失了有效尾数位。这不是缺陷而是设计意图——EVM 是相对于整体信号功率的指标，块内最强的那个 RE 精度得到保证，误差功率就被压在了可接受的范围内。

位宽与 EVM 的权衡：省带宽和保调制阶数的对赌

压缩位宽 udIqWidth 是前传上唯一一个"直接用带宽换信号质量"的旋钮，也是容量吃紧时最先被动的参数。定量地看：

udIqWidth每 PRB 字节数（BFP）相对未压缩对 EVM 的影响（量级）典型定位
16（不压缩）48 B100%可忽略测试基线
1443 B≈ 90%可忽略省不了多少，少见
1237 B≈ 77%很小，留足余量高阶调制 / 保守配置
928 B≈ 58%小，仍能支撑 256QAM业界最常用的折中点
825 B≈ 52%开始明显，需实测确认带宽紧张时的选项
619 B≈ 40%较大，高阶调制风险高低阶调制 / 特殊场景

要把这张表和 3GPP 的指标对上，需要一个参照系。TS 38.104 对基站发射的 EVM 有分调制阶数的限值，量级上大致是：QPSK 约 17.5%、16QAM 约 12.5%、64QAM 约 8%、256QAM 约 3.5%（1024QAM 更严）。关键在于——

压缩只是整条链路 EVM 预算里的一项，而且是最不该占大头的那一项。同一个预算里还有：功放非线性（DPD 之后的残余）、本振相位噪声、DAC/ADC 量化与时钟抖动、滤波器带内平坦度、天线通道间不一致性。所以不能拿"9-bit BFP 的量化误差小于 3.5%"就断定 256QAM 没问题——要留余量给其它项。工程上的做法是：压缩带来的 EVM 贡献控制在总预算的一小部分，并在实验室用矢量信号分析仪实测确认，而不是纸上算。

还有两条容易忽略的边界：

  • 上下行可以配不同的位宽。上行的动态范围问题更突出（近点用户与远点用户同时存在），有些实现会给上行更宽的位宽或不同的压缩方法。具体支持哪些组合由 O-RU 通过 M 面的能力上报（o-ran-module-cap 一类模块）声明，O-DU 只能在交集里选。
  • 压缩比不是恒定的，取决于块大小。指数是按块共享的，块越大（比如把多个 PRB 合成一个块）指数开销摊薄得越多、带宽越省，但块内幅度差异变大、精度损失变大。把"块 = 1 PRB"当默认理解是安全的。

eAxC：前传上成百上千条流的"门牌号"

eAxC（extended Antenna-Carrier）：Open Fronthaul 上一条独立 IQ 数据流的标识，粒度是一个天线端口（或空间流） × 一个载波 × 一个方向。eCPRI 报文头里的 ecpriPcid 字段（也叫 eAxC ID）就是这个门牌号，O-RU 靠它把收到的 IQ 分派到正确的处理通道。

eAxC ID 是 16 bit，但它不是一个扁平的编号——它被切成几个子字段，切法由 M 面配置：

# eAxC ID（16 bit）的典型子字段划分（各字段位宽由 M 面配置）
 15                                                          0
+-------------+---------------+---------+---------------------+
| DU_Port_ID  | BandSector_ID | CC_ID   |     RU_Port_ID      |
+-------------+---------------+---------+---------------------+
  哪个 DU/          哪个频段/     哪个载波     哪个天线端口 /
  哪条处理链         哪个扇区     (Component  哪个空间流
                              Carrier)

# 关键：位宽的划分是【配置项】，不是规范写死的常量。
# O-DU 与 O-RU 必须对同一套划分达成一致，否则同一个 16-bit 值
# 会被两端解读成完全不同的"载波+天线"组合 —— 流被送错通道。
这是 M 面污染 U 面的头号案例。O-DU 认为低 4 bit 是 RU_Port_ID、O-RU 认为低 6 bit 是 RU_Port_ID，两边都"配置成功、无告警"，但 IQ 数据会被 O-RU 分派到错误的天线通道或直接落到未配置的通道上被丢弃。症状是：某几个天线口没有输出、或者天线口之间的信号张冠李戴（波束打错方向）。而抓包看到的报文完全合法——只有把两端的 eAxC 划分配置拉出来逐字段比对才能发现。

eAxC 数量怎么算：为什么会"暴涨"

eAxC 的数量决定了前传的流数、带宽和 O-RU 的处理通道数，它是几个因子的乘积，所以增长很快：

eAxC 数 = 空间流数 × 载波数 × 方向数（DL / UL）

# 场景 A：单载波 4 层，Cat A O-RU
4 × 1 × 2 = 8 个 eAxC
带宽 ≈ 4 × 1.71 + 4 × 1.71 ≈ 13.7 Gbps   # 25GbE 舒适

# 场景 B：单载波 8 层
8 × 1 × 2 = 16 个 eAxC
带宽 ≈ 27.4 Gbps                          # 25GbE 已不够

# 场景 C：3 载波（100M + 100M + 60M）× 8 层
8 × 3 × 2 = 48 个 eAxC
带宽 ≈ 70 Gbps 量级                       # 必须 100GbE

# 场景 D：Cat A O-RU + 64T64R（预编码在 O-DU，逐物理天线送）
64 × 1 × 2 = 128 个 eAxC
带宽 ≈ 220 Gbps 量级                      # 前传直接不成立 —— 见下

场景 D 暴露了 Massive MIMO 与 7-2x 拆分的根本矛盾：如果按物理天线数发 IQ，64T64R 的前传带宽会突破任何现实的光模块。O-RAN 用 O-RU 分类来解这个问题：

O-RU 类别下行预编码 / 波束成形在哪eAxC 数量取决于前传带宽C 面负担
Category A在 O-DU 侧完成，O-RU 只做 iFFT/CP物理天线端口数随天线数线性暴涨轻（不需要传波束权重）
Category B在 O-RU 侧完成空间层数（远小于天线数）被层数封顶，可控重：波束权重要经 C 面下发或预置

所以 Massive MIMO 场景基本只能用 Category B：把"64 个天线"这件事关在 O-RU 内部，前传上只走 8 层左右的数据流。代价是波束权重（BFW）成了新的负担——它可以经 C 面实时下发（带宽压力大，但灵活），也可以预先经 M 面配置成波束库、C 面只发一个索引（带宽小，但灵活性受限）。这个选择直接决定了 C 面的带宽占比是 1% 还是 30%，是容量规划里最容易漏算的一项。

U 面的四个生产陷阱

① 丢包不重传，序列号只用来"知道自己丢了"。eCPRI 报文头里的 ecpriSeqid 是给接收端做丢包/乱序检测的，没有任何重传机制——重传回来的 IQ 早就过了它该出现的符号，毫无意义。所以前传网络的设计目标是零丢包，不是"低丢包率"。序列号的价值在可观测性：它让你能把"丢了多少"变成一个可监控的计数器（见第 06 章）。

② 早到和晚到都算丢。O-RU 对每条 eAxC 都有一个接收窗口，落在窗口外的报文一律丢弃。这意味着把网络做"快"也可能出问题——一条链路换成更短的光纤、或者去掉一级交换机，报文可能变成"太早到"。这是运维直觉最容易翻车的地方，细节见第 03 章。

③ 微突发（microburst）比平均带宽更致命。U 面的流量不是平滑的：每 35.7 μs 到来一批，同一时刻所有 eAxC 一起发。平均 13.7 Gbps 的负载，瞬时可能以线速冲进交换机。用"平均带宽 < 端口速率"来判断容量是不够的，要看交换机的缓存深度和是否配了优先级队列。典型症状是交换机的输出队列丢包计数缓慢增长，而端口利用率看起来只有 60%。

④ 空载不等于零流量。频域 IQ 只发被调度的 PRB，所以空载小区的 U 面带宽确实会掉下来——但 C 面仍然按时隙节奏在发（哪怕内容是"这个时隙什么都不发"，即 Section Type 0 那类空闲/保护描述），S 面也照旧。所以"半夜没人用了，前传应该很空"这个假设只对 U 面成立。

面试时被问"前传带宽怎么估"，能把 273 × 12 × 28 × 32 bit ≈ 2.94 Gbps/流 这条式子当场推出来，再乘上层数、载波数、方向数，并主动补上"压缩比 0.58、以太网开销 3~5%、C 面另算、微突发要留 buffer"这四个修正项，深度就到位了。只说"100 MHz 大概 10 个 G"是背结论，说不出中间任何一步。
03

Control Plane（控制面）

决定数据"怎么走"的信令

  • 是什么：承载控制信令——建立/释放连接、调度、切换、波束/资源分配等"指挥"信息。
  • 特点：数据量小但极其关键、常有实时性要求（前传 C 平面必须比对应 U 平面数据略早到）。
  • 对应技术：前传 C 平面（调度/波束控制，与 U 平面配套）；RAN 内 E2（近实时控制）、F1-C；核心网 NGAP 等。
User vs Control 的经典比喻：控制面是"点菜和下单"，用户面是"上菜"。先有控制信令决定"怎么传、用哪些资源"，用户面才据此把数据搬过去。

C 面传的是"section 描述"：这批 RE 放在哪、用哪个波束

把 U 面理解成"一车货"，C 面就是随车的提货单：这车货属于第几帧第几时隙、从第几个符号开始、占哪些 PRB、哪些 RE 有效、用哪个波束打出去。O-RU 收到 U 面 IQ 之后并不知道该把它们放进时频栅格的哪个位置——这个信息只在 C 面里。

Section（段）：C 面消息的基本单元，描述"一段连续的时频资源 + 它的属性"。一条 C 面消息可以携带多个 section（numberOfSections），因为一个时隙里往往有多块不连续的 PRB 分给不同 UE、用不同波束。

C 与 U 的时序配对：本篇最关键的一节

前面说 C 面是"提货单"，但真正的工程难点不在内容，在时间：

C 面报文必须先于对应的 U 面报文到达 O-RU，而且两者都必须落在各自的接收窗口内。早到、晚到、只到一个，结果都是——那个时隙不发射。O-RU 不会等、不会缓存、不会重传，因为空口的发射时刻是由 S 面钉死的绝对时间，过了就过了。

先看图。图里从左到右是时间，最右边那条红线是由 S 面确定的绝对发射时刻（某帧某时隙的符号 0），所有时序都以它为参考点向前倒推：

图里有三件事必须读出来：

  • 所有时刻都是相对"参考时刻"倒推的提前量，不是相对彼此。O-DU 与 O-RU 都由 S 面对齐到同一时间基准，才可能谈"提前 200 μs"这种话——S 面一丢，整个时序体系立刻失去意义。
  • 接收窗是 O-RU 的能力，发送提前量是 O-DU 的选择。窗口宽度是 O-RU 硬件（缓存深度、流水线设计）决定的，通过 M 面上报；O-DU 要在这个窗口和实测网络时延之间解出一个可行的发送提前量。
  • C 面还要额外早于 U 面一段（图中黄色的 tcp_adv_dl），因为 O-RU 需要先拿到 section 描述、把接收通道准备好，才能正确解析随后到来的 IQ。

C/U 失配会发生什么：一张症状对照表

C/U 失配的所有后果都可以归到一句话：O-RU 拿不到完整且及时的"描述 + 数据"配对，于是放弃这一份资源。但从外面看到的现象差别很大，容易误判成网络问题：

失配类型根因常在哪O-RU 行为你观察到的现象怎么确认
C 面太早到（早于 T2a_min_cp_dl）提前量配大了；或链路变短 / 减少了一级交换机丢弃该 C 面消息该时隙整段不发；改造后突然出问题O-RU 的 C 面 "early" 类接收窗计数增长
C 面太晚到提前量配小了；网络拥塞；O-DU 调度线程被抢占丢弃时隙随机不发，吞吐忽高忽低C 面 "late" 类计数增长
C 面根本没到VLAN 不通、MAC/IP 配错、eAxC 划分不一致什么也不做整个小区完全不发射，但 M 面一切正常C 面总接收计数为 0
U 面到了但没有对应 C 面tcp_adv_dl 未满足；sectionId 对不上丢弃 U 面（不知道放哪）发不出，或频谱上出现空洞U 面 "on time" 计数正常但 C 面异常

udCompHdr 两端不一致M 面配的压缩方法/位宽与实际发的不符按错误位宽解压 → 得到噪声发得出去但全是噪声，EVM 极差，UE 完全接不上抓包看 U 面 udIqWidth 与 M 面配置是否一致
注意倒数第二行和最后一行的区别，这是判断"配置问题还是网络问题"的分水岭：如果症状是"完全不发"或"固定位置的空洞"，几乎一定是配置/时序问题；如果症状是"发得出去但质量差、随负载变化"，才要去查网络。反过来把配置问题当网络问题查，会在交换机上白折腾很久——因为交换机确实一切正常。

C 面的容量与拥塞：小包多、带宽小，但优先级最敏感

C 面的流量画像和 U 面完全相反：报文很小（典型百字节量级）、数量很多、带宽占比低。这带来三个工程后果：

① 以太网开销占比高。一个 100 字节的 C 面报文，加上前导码、FCS、帧间隙、VLAN 标签，链路上实际要占约 140 字节——近三成是开销。U 面用 jumbo 帧时开销不到 0.5%。所以 C 面的"链路占用"要比"载荷带宽"算出来的大不少。

② 波束权重是决定 C 面量级的分水岭。如果采用 Category B O-RU 并把波束权重（BFW）经 C 面实时下发，C 面报文就不再是百字节量级——每个 section 要携带每个天线的复数权重，报文长度会膨胀一两个数量级，C 面带宽可以做到与 U 面同阶。两种做法的对比：

波束权重下发方式C 面带宽灵活性典型适用风险
C 面实时携带 BFW大幅上升，可与 U 面同阶最高：每时隙可换任意权重需要精细波束跟踪的场景容量规划漏算 C 面 → 上线后随机丢包
M 面预置波束库，C 面只发 beamId很小（beamId 只 15 bit）受限于波束库大小覆盖型场景、固定波束栅格波束库改动要走 M 面，无法快速响应

③ C 面对优先级最敏感。C 面带宽小，很容易在容量规划里被当作"可以忽略"，于是和 U 面共用一个队列。这在轻载时没问题，一旦 U 面出现微突发，C 面的小包就排在几十个 9000 字节巨帧后面——按 25 Gbps 算，每个巨帧约 2.9 μs，排 30 个就是 87 μs 的额外时延，足够把 C 面顶出接收窗。症状就是典型的"随机丢包"：忙时掉、闲时好、抓包抓不到、换光纤没用。

因此四平面的优先级必须显式规划，不能靠默认值。常见的做法是用 VLAN 的 PCP（802.1p）区分，S 面最高、C 面次之、U 面再次、M 面最低，并在每一跳交换机上都配严格优先级队列。"每一跳"三个字是重点——链路上只要有一台交换机没配，整条链的时延抖动就由它决定。
04

Management Plane（管理面）

配置、监控、运维的那一面

  • 是什么：设备的配置下发、性能/故障监控、软件升级（FCAPS）。改的是"设备的长期行为规则"，而非某条业务流。
  • 特点：变化慢、可靠性要求高、安全要求高（能改配置=能改一切）；讲究"稳、可追溯、安全"。
  • 对应技术：NETCONF/YANG（O-RAN O1 接口、前传 M 平面），走 SSH/TLS 保护，用 TCP 保证可靠。
这正是为什么管理面用 TCP + NETCONF，而用户面（前传）用 eCPRI over Ethernet：管理面要"可靠、事务化、安全"（TCP/TLS/SSH 完美契合），用户面要"极低时延确定性"（TCP 反而是负担）。同一系统里，不同平面按需选择不同"传输机制"——回扣了 Module 01 的核心思想。

前传 M 面的具体形态：O-RU 是 NETCONF 服务器

前传 M 面的角色分配和直觉相反：O-RU 是 NETCONF Server，O-DU / SMO 是 NETCONF Client。被管的那一方跑服务器，管别人的那一方是客户端。协议本身的原理（NETCONF 的 RPC 模型、datastore、YANG 建模、SSH/TLS 承载）见 NETCONF 工程实践，这里只讲前传场景特有的部分。

第一个特有之处是启动阶段的自发现。一台刚上电的 O-RU 挂在光纤上，它不知道自己的 IP、不知道 VLAN 是多少、不知道谁该来管它。O-RAN 定义了一套逐步收敛的流程：

# O-RU 上电到 M 面可用（各步失败点都很典型）
1. 链路 up
   └─ 光模块识别、自协商速率
      ✗ 常见失败：光模块型号不在 O-RU 白名单里 → 链路起不来

2. VLAN 发现
   └─ O-RU 在候选 VLAN 上尝试（含无标签 / 预置 VLAN 列表）
      ✗ 常见失败：交换机端口没配成 trunk，或没放通 M 面 VLAN

3. 获取 IP
   └─ DHCPv4 / DHCPv6，或 IPv6 SLAAC（前传 M 面常用 IPv6）
      ✗ 常见失败：DHCP 中继没配，O-RU 拿不到地址，现场只能看灯

4. 发现 NETCONF Client
   └─ 通过 DHCP 选项下发的 client 地址，或 mDNS/DNS-SD
      ✗ 常见失败：DHCP 选项配了但 O-RU 版本不支持该选项号

5. Call Home（RFC 8071）
   └─ O-RU 主动向 client 发起 TCP 连接
      netconf-ch-ssh: TCP 4334   netconf-ch-tls: TCP 4335
      # 注意方向是反的：不是 client 连 server，而是 server 来敲门。
      # 这样 O-RU 就不需要一个可路由、可预知的固定地址。
      ✗ 常见失败：防火墙只放通了 830，没放通 4334/4335

6. SSH/TLS 建立 + hello 交换能力
      ✗ 常见失败：双向证书未预置 / 证书过期 / 时间没同步导致证书判为无效

7. Client 读能力 → 下发配置 → 启动 supervision 看门狗

第 5 步的 Call Home 方向反转是前传 M 面最值得记住的设计。常规 NETCONF 是客户端连服务器的 830 端口，前提是服务器有已知地址。但一个站点几十台 O-RU，逐台规划地址不现实，所以改成 O-RU 拿到地址后主动"来敲门"。副作用是排障时的思维要跟着反过来：M 面连不上，先查 O-RU 有没有拿到 IP、有没有发出 SYN，而不是先去 ping O-RU。

另一个坑在第 6 步：TLS 证书校验依赖系统时间，而 O-RU 刚上电时时间还没同步。这会形成一个"鸡生蛋"——需要 M 面配好才能同步，需要时间正确才能建 M 面。实现上通常靠 O-RU 的 RTC 或宽松的初始时间校验绕过，但现场如果 O-RU 断电很久、RTC 电池耗尽，就会撞上这个问题，症状是"新装的 RU 连不上，老的都正常"。

Hierarchical 与 Hybrid：O-RU 被谁管

M 面有两种架构模型，差别只在一件事：O-RU 身上有几条 NETCONF 连接。

维度Hierarchical（层级）Hybrid（混合）
O-RU 上的 NETCONF 连接数1 条（只来自 O-DU）≥ 2 条（O-DU + SMO）
SMO 怎么看到 O-RU通过 O-DU 代理 / 聚合上报既可经 O-DU，也可直连
配置权归属清晰：只有 O-DU 能改需要划分：谁能改哪些子树要事先约定
O-RU 网络可达性要求只需与 O-DU 互通还要与 SMO 互通（跨网段、跨安全域）

Hybrid 模式最容易踩的坑是两个 client 都以为自己是唯一的配置者。NETCONF 本身没有内置的"配置权划分"机制（lock 只保护一次事务，不表达长期归属），所以必须在运维流程上约定：时序与载波参数（o-ran-uplane-conf、o-ran-delay-management）只由 O-DU 写，软件包与证书只由 SMO 写。约定被打破时的症状极难查——配置会"自己变回去"，因为另一个 client 在按它的意图周期性纠偏。

Supervision 看门狗：M 面断了怎么被发现

NETCONF 跑在 TCP 上，而 TCP 连接可以在中间设备重启、路由切换后静默失效——两端都以为连接还在，直到下一次写操作才报错。对基站来说这不能接受：M 面断了却不知道，等于失去了对 O-RU 的全部观测。

所以 o-ran-supervision 定义了一个看门狗：Client 必须周期性调用 RPC 重置 O-RU 侧的监督定时器，超时未喂狗，O-RU 就认定 M 面已失联，并按预设策略动作（上报、或释放 M 面会话等待重新 Call Home）。

# Client（O-DU）周期性"喂狗"，示意
<rpc message-id="1017" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <supervision-watchdog-reset xmlns="urn:o-ran:supervision:1.0">
    <supervision-notification-interval>60</supervision-notification-interval>
    <guard-timer-overhead>10</guard-timer-overhead>
  </supervision-watchdog-reset>
</rpc>

# O-RU 回一个下次期望被喂狗的时间点
<rpc-reply message-id="1017">
  <next-update-at>2026-09-04T05:31:07Z</next-update-at>
</rpc-reply>

# 关键工程点：
# 超时 = interval + overhead。overhead 给的是网络抖动与
# client 侧 GC/调度延迟的余量。配得太小 → M 面被误判断开、
# 会话反复重建（"M 面抖动"）；配得太大 → 真断了也发现得慢。
M 面断开不一定影响业务。这是前传运维里一个反直觉但很重要的事实：C/U/S 面完全不依赖 M 面在线，M 面掉了小区照样发射。所以"M 面告警"的紧急程度低于"同步告警"——但它的危险性在于失去了观测能力：接下来任何故障你都只能靠 O-DU 侧的间接指标去猜。所以处理顺序上它不紧急，但不能积压。
05

Sync Plane（同步面）

让所有设备"对时"

  • 是什么：分发精确的频率 + 相位/时间，让 DU/RU 步调一致。
  • 特点：优先级最高（时间不能晚、不能抖）。
  • 对应技术：PTP（IEEE 1588）+ SyncE。
同步面在前传尤为关键（TDD、载波聚合、Massive MIMO 都要求 ns 级相位对齐）。它是 eCPRI 以太网化之后必须补上的一块（CPRI 时代同步内建，不需单独一面）。

为什么必须做到 ns 级：三个互相独立的理由

"同步"这个词常被含糊地一带而过，但前传的同步需求其实来自三个完全独立的物理原因，各自的精度要求差了一两个数量级。搞混它们会导致选型时过度设计或严重欠设计。

① TDD 收发切换：微秒级，管的是"别互相干扰"。TDD 下上下行共用一个频率，靠时间分开。如果相邻两个基站的时隙边界错开了，A 站还在发下行的时候 B 站已经切到接收上行——A 的下行大功率信号就直接灌进 B 的上行接收机。基站的发射功率比 UE 高几十 dB，这种干扰是毁灭性的，而且受害者是邻站，自己看不出来。

② MIMO / 发射分集的相位一致：几十纳秒级，管的是"波束能不能成形"。多个天线口要合成一个指向性波束，靠的是各路信号之间精确的相位关系。时间偏差直接变成相位偏差，波束就歪了或者散了。

③ 载波聚合：百纳秒级，管的是"UE 能不能把多个载波拼起来"。UE 需要在多个载波上同时接收，载波之间的时间偏差超出容限，UE 的接收窗就对不齐。

需求来源指标典型量级不满足时的症状
TDD 小区间相位同步任意两站之间的时间偏差≤ 3 μs（即相对公共基准 ±1.5 μs）邻区上行底噪抬升、上行吞吐塌陷；受害者不是自己
MIMO / 发射分集同一载波内天线口间的 TAE≈ 65 ns波束指向偏、增益下降、MIMO 秩上不去
带内连续载波聚合载波间 TAE≈ 130 nsCA 建立失败或吞吐不达标
带内非连续 / 跨带载波聚合载波间 TAE≈ 260 ns同上

上表的 TAE 数值是 3GPP TS 38.104 对基站时间对齐误差的量级要求，具体条款与数值以所用版本为准；3 μs 的小区相位同步要求来自 TDD 共存约束。

再看这 1.5 μs 的预算怎么花掉——这才是工程上真正吃紧的地方。ITU-T G.8271.1 给出的典型划分是：从 PRTC 到最后一个网元的网络部分约 1.1 μs，末端应用（这里就是 O-RU 内部到天线口）约 0.4 μs。而这 1.1 μs 要分给链路上每一跳：

# 端到端时间误差预算（典型划分，量级示意）
总预算（PRTC → 天线口）                     1500 ns
├─ 末端应用（O-RU 内部到天线口）              400 ns
└─ 网络部分                                 1100 ns
   ├─ PRTC / T-GM 自身                        ~100 ns
   ├─ 每一跳边界时钟（T-BC）的噪声累积      每跳几十 ns
   │  # 所以跳数是硬约束：10 跳就吃掉几百 ns
   └─ 链路收发时延不对称                 ★ 最容易被忽略
      # PTP 假设收发路径对称，用往返时延的一半估单程。
      # 不对称量 Δ 会直接产生 Δ/2 的固定相位误差，
      # 而且【PTP 自己发现不了】—— 它没有任何手段测出不对称。

# 不对称的三个常见来源：
1. 单纤双向（BiDi）光模块：收发用不同波长，折射率不同
   → 不对称量约每公里数纳秒量级，10 km 链路就可能有几十 ns
2. 收发走了不同长度的光纤（双纤方案里布线长度不一致）
   → 1 m 光纤差 ≈ 4.9 ns 单程 → 相位误差 ≈ 2.5 ns
3. 中间设备的收发处理路径不对称（非 T-BC 的普通交换机尤甚）
"不对称"是同步类问题里最难查的一类，值得单独记住：PTP 的整个数学基础是"往返路径对称"，一旦不成立，它会算出一个稳定、平滑、看起来毫无问题的偏差——而这个偏差是错的。监控界面上 offset 一直是几纳秒，path delay 也很稳定，但天线口的实际相位偏了几十纳秒。唯一的发现手段是用外部时间源在天线口实测（GNSS 参考 + 时间间隔分析仪），或者对已知的不对称量做静态补偿配置。用 BiDi 光模块的站点，这个补偿值必须配，而它经常被漏掉。

PTP 和 SyncE 各给什么：为什么要两个都上

这是 S 面最常见的困惑：既然 PTP 能给时间，为什么还要 SyncE？答案是它们给的东西不一样，而且失效模式互补。原理细节见 PTP 与 SyncE，这里只讲前传场景下的分工：

维度SyncE（ITU-T G.8262 / G.8264）PTP（IEEE 1588 / G.8275.1）
提供什么频率（每秒有多长）相位 + 时间（现在几点、秒边界在哪）
工作在哪一层物理层：从收到的比特流里恢复时钟报文层：靠带时间戳的报文往返计算
受排队 / 拥塞影响吗不受——比特流一直在，与队列无关受：报文时延变化（PDV）直接变成噪声
能单独满足前传吗不能：没有相位信息，TDD 切换点无从确定理论上能，但对网络质量要求高
丢源之后频率慢慢漂（本地晶振品质决定）相位快速漂（因为频率也在漂）
需要网络设备支持吗需要：每跳都要能恢复并再生时钟需要：每跳最好是 T-BC（边界时钟），带硬件时间戳

组合起来的价值在于保持（holdover）能力：

⌚ 生活类比：报时的人和秒表

PTP 像一个每隔一会儿喊一次"现在是 12 点 00 分 00 秒"的人——他给你绝对时刻，但如果房间里很吵（网络拥塞），你可能听错几次。SyncE 像一只走得极准的秒表——它不知道现在几点，但能保证"一秒就是一秒"。两个一起用：靠喊话对准绝对时刻，靠秒表在喊话听不清或中断的时候继续稳稳地走。只有秒表，你不知道该几点开始发；只有喊话的人，房间一吵你就乱了。

具体地说：PTP 报文在拥塞时会经历 PDV，PTP 从算法上要把这些抖动滤掉，而滤波器要区分"网络抖动"和"本地晶振真的漂了"是很困难的。有了 SyncE 提供的物理层频率，PTP 的从时钟只需要跟踪相位，不需要同时跟踪频率，环路带宽可以做得很窄，对 PDV 的抑制能力大幅提高。反过来，PTP 源短暂中断时，SyncE 保住频率，相位漂移速率能慢一两个数量级，把保持时间从分钟级拉长到小时级。

LLS-C1 ~ C4：四种同步拓扑

O-RAN 定义了四种前传同步拓扑配置，差别就一件事：O-RU 的时间从哪儿来。

配置O-RU 的时钟源对前传网络的要求优点代价 / 风险典型适用

同步状态怎么读：三层证据

同步问题的排查要分三层看，不要只看一层就下结论：

第一层：O-RU 自己怎么认为（M 面读 o-ran-sync）。这是"官方口径"，也是排障的起点：

    <sources>
      <local-port-number>1</local-port-number>
      <state>SLAVE</state>
    </sources>
  </ptp-status>
  <synce-status>
    <lock-state>LOCKED</lock-state>
  </synce-status>

# 判读要点：
# · sync-state = HOLDOVER → 源丢了但本地还在撑，业务可能仍正常。
#   这是【最需要立刻处理】的状态，因为它有过期时间。
# · sync-state = LOCKED 但 clock-class = 7 → 自己锁上了，
#   但【上游的 PRTC 已经失去 GNSS】。整条链在慢慢漂，
#   而每台 O-RU 都显示 LOCKED —— 最容易漏判的一种情况。
上面注释里的第二条值得单独强调：sync-state = LOCKED 不等于"同步没问题"。它只说明"我跟上了我的上游"，不说明"我的上游是对的"。整条时钟链一起漂的时候，每一级都是 LOCKED。判断"链条源头健不健康"要看 clockClass，不是看 lock-state。这也是为什么监控必须把 clockClass 收上来告警，而很多现场只监控了 lock-state。

第二层：O-DU / 服务器侧的 PTP 协议栈（linuxptp）。这一层给的是量化数据：

第三层：天线口实测。前两层都无法发现路径不对称，只有把外部时间源接到天线口实测才能。这一层通常只在开站验收和疑难故障时做，但一旦怀疑不对称，前两层的数据全都不能作为证据。

丢锁之后：HOLDOVER 是一个有过期时间的状态

S 面故障的时间演进有明确的三个阶段，理解它能解释很多"故障为什么隔了半小时才爆发"的现象：

阶段状态典型持续业务表现该做什么
①LOCKED—正常监控 clockClass 与 delay 阶跃
②HOLDOVER分钟 ~ 小时（有 SyncE 保频率则长得多）完全正常，看不出任何异常这是唯一的处理窗口，必须在这个阶段修好
③相位漂出容限—先是邻区上行底噪抬升，然后 UE 大面积掉线，最后 O-RU 可能主动停发已经出事故了
④FREERUN—小区静默恢复时钟源，注意重锁可能有相位跳变

阶段 ② 的"完全正常"是 S 面运维的核心难点：同步告警出现的时刻，业务还是好的；业务出问题的时刻，往往已经过了几十分钟。所以同步告警绝对不能按"业务是否受影响"来定优先级——它必须按"保持时间还剩多少"来定。这也解释了为什么成熟的现场会把 HOLDOVER 直接定为高级别告警，哪怕此刻一切指标都绿。

还有一个容易忽略的细节：重新锁定时可能出现相位跳变。如果 O-RU 在保持期间已经漂了几百纳秒，重锁时把相位"拽回来"的那一瞬间，对空口是一次不连续。所以有些实现会选择缓慢牵引而不是直接跳变，代价是恢复时间更长。

为什么前传抓包这么难

"抓个包看看"在前传上不是一句轻松的话。三个硬约束：

# ① 速率：25 Gbps 双向 = 6.25 GB/s
#    tcpdump / libpcap 走内核协议栈 + 单线程写盘，必丢包。
#    而【丢掉的恰好是你要找的那个突发】—— 抓到的"正常"是假的。
#    13.7 Gbps 全量落盘 = 1.7 GB/s = 约 100 GB/分钟。

# ② 时间戳精度：判断"早到/晚到"要跟 us 级窗口比
#    软件时间戳误差就有几十 us，比接收窗还大 → 结论必然错。
#    必须用带【硬件时间戳】的网卡或采集卡，且它自己要同步到
#    同一个时间源上（否则你在拿两个不同的钟做减法）。

# ③ 取包点：镜像口把双向 25G 塞进一个 25G 口
#    单方向利用率过半就开始丢，重载时的镜像结论不可信。
#    光分路器（TAP）+ 采集卡是唯一在满载下可信的方式。

# ── 实务：先靠"只抓头部"把数据量压下来 ──────────────

# 只抓 eCPRI（裸以太网承载），每包只留前 128 字节
# 头部信息全在前 30 字节内，IQ 载荷对排障没用
$ tcpdump -i ens1f0 -s 128 -w fh.pcap 'ether proto 0xaefe'
#            ↑ 这一条把 1.7 GB/s 降到约 0.4 GB/s，仍需 NVMe

# 无 VLAN 时 eCPRI 头从第 14 字节开始：
#   ether[14]=版本/C位  ether[15]=msgType
#   ether[16:2]=payloadSize  ether[18:2]=pcid/rtcid(eAxC)
$ tcpdump -i ens1f0 'ether proto 0xaefe and ether[15] == 2'          # 只抓 C 面
$ tcpdump -i ens1f0 'ether proto 0xaefe and ether[18:2] == 0x0002'   # 只抓 eAxC=2

# 带 VLAN（前传常态）：整体后移 4 字节，写死绝对偏移最稳妥
$ tcpdump -i ens1f0 'ether[16:2] == 0xaefe and ether[19] == 2'

# S 面报文量小，可以长期抓 —— 性价比最高的一条
$ tcpdump -i ens1f0 -w ptp.pcap 'ether proto 0x88f7'

# 离线分析：Wireshark 有 eCPRI 与 O-RAN 前传解析器，
# 但要先在首选项里填入 eAxC 各 bitmask 的位宽，
# 否则它切分出的 CC_ID / RU_Port_ID 是错的。
$ tshark -r fh.pcap -Y 'ecpri' -T fields \
    -e frame.time_relative -e ecpri.msg.type -e ecpri.pcid
抓包在前传的正确定位是"用来验证一个已经成型的假设"，不是"用来找线索"。因为抓包窗口很短（几秒就几十 GB）、代价很高（要停业务插 TAP），漫无目的地抓几乎一定白干。正确的顺序是：先用 O-RU 的接收窗计数和同步状态把范围缩到"某一条 eAxC 的 C 面晚到"，再去抓包确认。这也是下一章排障顺序存在的理由。

接收窗计数：C/U 面时序问题唯一的直接证据

O-RU 侧对每条 eAxC 都维护一组接收窗计数（在 o-ran-performance-management 一类模块里，字段名随版本演进），语义是把收到的报文按"落在窗内 / 太早 / 太晚 / 损坏 / 重复"分类计数。这组计数是整个前传排障体系里性价比最高的东西——不用抓包、不用停业务、15 分钟粒度自动上报：

# 4) 占比 218,558 / 25,200,000 ≈ 0.87%
#    看着小，但 U 面【没有重传】：0.87% 的符号级丢失会让
#    该层的 MCS 被下压几档，表现为"吞吐上不去但不掉线"。

与之配套的是 ecpriSeqid：它让接收端能算出丢了多少、乱序了多少。注意它只提供"感知"不提供"恢复"——序列号跳变说明中间丢了包，但那些 IQ 已经永久失去意义。把 SEQ_ID 推出的丢包率做成常态监控指标，比事后抓包有用得多。

被问"前传出问题你怎么定位"时，答"抓包看看"是扣分的——面试官想听的是你知道抓包在这里有多贵。加分答法是给出按代价递增的证据链：① 读 o-ran-sync（免费、一秒钟）→ ② 读接收窗计数与 SEQ_ID 丢包（免费、已在上报）→ ③ 比对两端 M 面配置（免费）→ ④ 交换机队列丢包计数（免费）→ ⑤ 才是 TAP + 硬件时间戳抓包（要停业务、要设备）。能把"什么时候才该抓包"讲清楚，比会写 BPF 表达式更能体现工程判断力。

一次"配置到数据"的贯穿

四平面如何协同

  1. 管理面（M / O1）：SMO 用 NETCONF/YANG 把小区参数配置到 O-DU / O-RU。
  2. 同步面（S）：PTP/SyncE 让 O-DU 与 O-RU 对齐到同一时间基准。
  3. 控制面（C）：O-DU 通过 eCPRI 控制消息告诉 O-RU"下一个时隙怎么发（波束、资源）"。
  4. 用户面（U）：O-DU 通过 eCPRI 把 IQ 数据发给 O-RU，O-RU 转成射频经天线发给 UE。
这条链正是下一步"完整通信系统案例"的雏形：管理面先把系统配好，同步面对齐时间，控制面指挥，用户面搬数据。四个平面各司其职、缺一不可。完整贯穿见 通信系统案例。

排障判定顺序：S → M → C → U

基于上面的传染路径，前传排障有一个固定的推进顺序。这个顺序不是按"哪个平面更可能出问题"排的（论概率 M 面最高），而是按"排除它的代价最低、且它的故障会污染后面所有观测"排的：

① S 面同步锁了吗
② M 面配置到底是什么
③ C 面命令到了吗、准时吗
④ U 面数据准时吗、丢了多少
⑤ 网络 / 光路最后才轮到它

为什么是这个顺序，三条理由：

  • S 面放第一，因为它一旦有问题，后面所有观测都不可信。同步不对时，接收窗计数里的"早到/晚到"全是同步偏差的投影，你会得出完全错误的时序结论。而排除它只需要读一次 sync-state 加 clockClass——代价接近零，收益是让后面的所有数据变得可信。
  • M 面放第二，因为它是根因概率最高、且验证成本最低的。C/U 面的全部时序与格式参数都从 M 面来，而验证方法只是"把两端的配置读出来逐字段比"。不要相信"配置应该是对的"——读出来看。
  • 网络放最后，因为它是最贵、最容易被冤枉的。上一节表里有五行的误判都指向"网络/光纤/光模块"。在前面四步没做完之前去查网络，通常的结果是"网络一切正常"，然后损失两天。

真实案例一：新开站，O-RU 完全不发射

现象。某站新开一个 100 MHz TDD 小区。O-DU 侧显示小区已激活、无告警；M 面连接正常；用频谱仪在天线口测，完全没有信号，底噪都是干净的。现场第一反应是"O-RU 是坏的"，已经在申请备件。

① S 面（2 分钟）。读 o-ran-sync：sync-state = LOCKED，clockClass = 6，ptp4l 的 rms 在 10 ns 上下。同步没问题，而且这个结论让后面的时序数据变得可信。

② M 面（5 分钟）。读 tx-array-carriers：active = ACTIVE，state = READY。这一条很关键——O-RU 认为自己已经准备好发射了。所以问题不是"发不出去"，而是"没有内容可发"。射频通路、功放、载波配置全部可以排除，怀疑范围一下缩到 C/U 面。

③ C 面（3 分钟）。拉接收窗计数：U 面的 RX_TOTAL 是满的（25,200,000/15 min），RX_ON_TIME 也是满的——U 面的 IQ 一直在准时到达。但 C 面的总接收计数是 0。一个 C 面报文都没收到。

关键的一次推理。U 面能到、C 面到不了，而两者走的是同一根光纤、同一个 VLAN。所以可以排除：链路不通、VLAN 没放通、MTU 不够、光模块故障——这些原因都会同时影响 U 面。剩下的可能只有两个：O-DU 根本没发 C 面，或者 C 面被发到了别的地方。

④ 在 O-DU 网卡上抓包（C 面量小，几秒即可）。tcpdump 'ether proto 0xaefe and ether[15] == 2' —— C 面报文确实在稳定地发出，rtcid 也是对的。所以是"发到了别的地方"。

⑤ 根因。读 o-ran-processing-element：C 面和 U 面各自配了独立的传输端点，U 面端点的目的 MAC 是对的，C 面端点的目的 MAC 是另一个站点 O-RU 的地址——开站时复制了隔壁站的配置模板，改了一处没改另一处。于是 C 面报文进到交换机后按未知单播泛洪，到达这台 O-RU 的网口时因目的 MAC 不匹配被网卡直接丢掉，连计数器都不会加。

为什么没有任何告警。这是这个案例最值得记住的地方：O-RAN 前传没有"C 面没收到"这种告警。因为 O-RU 无法区分"这个 eAxC 我配了但对端没发"和"这个 eAxC 本来就还没启用"——两者在它看来完全一样。所以它只提供计数器，不提供告警。不主动去读计数，这个故障可以静默存在到有人拿频谱仪去量。

沉淀。把"C 面总接收计数 > 0"和"U 面 RX_ON_TIME 占比 > 99.9%"写进开站脚本的准出门槛，与"载波 state = READY"并列。这三条加起来能在开站阶段拦掉绝大多数 C/U 配置类问题，成本是一次 NETCONF get。

真实案例二：上行底噪每天定时抬升

现象。某片区若干小区的上行干扰功率（底噪）每天在大致相同的时段抬升 10 dB 以上，持续一两小时后自行恢复；上行吞吐在此期间塌陷，下行完全正常。受影响小区分布在几个不同的站点。第一反应是"外部干扰"，已经安排了扫频。

第一条线索：只有上行坏，下行好。这个不对称非常有信息量。如果是带宽、丢包、配置类问题，下行通常先出问题（下行数据量大得多）。"只有上行受影响"强烈指向 TDD 相位同步——因为上行接收窗一旦与邻区的下行发射时间重叠，基站就会在自己的接收窗里收到邻区的大功率下行信号，而这在下行侧不会有任何表现。

第二条线索：受害者与肇事者不是同一个。TDD 干扰是相对的：漂掉的那个小区污染的是邻区的上行，它自己的指标可能一切正常。所以不能只看告警小区，要把该片区所有小区的同步状态一起拉出来。

差点被排除掉的一步。读所有相关 O-RU 的 o-ran-sync：全部 sync-state = LOCKED。按常见流程，同步到这里就被排除了。但进一步读 clockClass，发现其中一片区域的 O-RU 报的是 7——它们自己确实锁定了，但锁定到了一个已经失去 GNSS、正在保持中的上游 PRTC。整条时钟链一起漂，每一级都显示 LOCKED。

为什么会漂到互相干扰。该片区有两条独立的时钟链。链 A 正常，链 B 的 PRTC 失去 GNSS 后进入保持并缓慢漂移。挂在链 A 和链 B 上的小区之间，相对相位偏差随时间累积，超出 3 μs 容限后边界处开始互相干扰。同一条链上的小区之间反而没有问题——它们一起漂，相对关系不变。这解释了为什么受影响的小区呈现出"按地理片区分布"的奇怪规律。

时段性的来源。把 PRTC 的可见卫星数与 clockClass 的变化时刻对齐，与底噪抬升时刻对照，发现三者高度相关，但底噪抬升比 clockClass 变化晚了约 40 分钟。这 40 分钟正是第 05 章讲的"阶段 ②"：进入保持后还没漂出容限的那段时间，业务完全正常。正是这个滞后，让运维在很长时间里没能把两件事联系起来——底噪告警响的时候，同步告警已经响了 40 分钟，被当成两个独立事件分给了两个组。至于每天定时，是站点旁新装的设备遮挡了 GNSS 天线的一部分天空视野，卫星在特定时段落入遮挡方向后可见数不足。

处置。短期：给链 B 的 PRTC 增加一路备份时钟源（从链 A 引 PTP，靠 clockClass 优选自动切换），使 GNSS 失锁时不再进入保持。长期：移动 GNSS 天线位置恢复天空视野。

沉淀（三条，比修复本身更有价值）。① clockClass 必须进常态告警，不能只监控 lock-state——本案里 lock-state 全程正常。② "进入 HOLDOVER 已持续多久"要作为独立指标，因为它才是"还剩多少时间"的直接度量。③ 上行底噪类告警的排查流程第一步改为"查本片区所有小区的同步状态"，扫频降到第三步。

  1. 基础Open Fronthaul 上的四个平面各自传什么？

    四个平面共享同一张前传以太网，靠 VLAN + PCP 隔离：

    • U 面（User）：频域 IQ 采样——每个 RE 上的复数。走 eCPRI Message Type 0。占前传带宽的 95% 以上，每个 OFDM 符号一批（30 kHz SCS 下约 35.7 μs）。
    • C 面（Control）：section 描述——哪个帧/时隙/符号、哪些 PRB、哪些 RE 有效、用哪个波束。走 eCPRI Message Type 2。带宽小（典型是 U 面的几个百分点）但时序最敏感。
    • S 面（Sync）：时间、相位、频率基准。PTP（IEEE 1588，前传常用 G.8275.1）+ SyncE。带宽可以忽略，但优先级最高。
    • M 面（Management）：配置、告警、性能计数、软件包。NETCONF/YANG over SSH 或 TLS。无实时要求，但它下发的参数决定了 C/U 面能不能正常工作。

    一个关键澄清：U 面虽然叫 User Plane，但它不含任何 IP 报文或可识别的业务内容——它是纯粹的频域采样。前传上看不到"用户在访问什么"。

  2. 基础为什么要把前传流量分成四个平面？CPRI 时代为什么没有这个概念？

    分平面的直接理由是这四类流量的时间尺度、失效后果、安全域、变化频率差异极大：S 面的误差预算是纳秒，M 面的配置变更以天计；U 面丢一个包由 HARQ 补回来，S 面丢锁会让整个小区静默还干扰邻区；M 面能改配置所以必须强认证，U 面逐包加密会吃掉时延预算。分平面本质上是"把昂贵的保障只花在真正需要的流量上"。

    更有洞见的答法是把它讲成一次技术债的显式化：CPRI 是恒定速率的同步串行链路，同步（从比特流恢复时钟）、时序（固定的时分复用位置）、管理（私有 inband 通道）这三件事由物理层"免费"提供，所以不需要独立的平面。改成以太网之后，以太网是异步的、分组的、best-effort 的，这三件事没有消失，只是从免费变成了要自己付费——于是各自长成了 S 面、C 面的提前量窗口、M 面。

    这也解释了一个现象：前传故障里时序类问题的占比远高于带宽类问题。带宽是花钱能买的，时序不是。

  3. 基础C 面和 U 面的时序关系是什么？失配会怎样？

    三层关系，缺一不可：

    • C 面必须先于对应的 U 面到达 O-RU，且至少早 tcp_adv_dl 这么多（O-RU 通过 M 面上报的能力）。因为 O-RU 需要先拿到 section 描述才知道随后的 IQ 该放进时频栅格的哪个位置。
    • 两者都必须落在各自的接收窗内：C 面在 [T2a_min_cp_dl, T2a_max_cp_dl]，U 面在 [T2a_min_up, T2a_max_up]。窗口是相对"空口发射时刻"倒推的提前量。
    • 所有时刻都以 S 面确定的绝对时间为参考，不是相对彼此。

    失配的后果统一是：O-RU 丢弃，那个时隙不发射。它不等、不缓存、不重传，因为空口的发射时刻是钉死的绝对时间，过了就没有意义了。注意早到也算失配——这最反直觉：把链路改短、去掉一级交换机，反而可能让报文变成"太早到"而被丢。

    从外面看到的症状差别很大：C 面完全没到 → 整个小区不发射；C 面偶发晚到 → 时隙随机不发，表现成"随机丢包、吞吐忽高忽低"；U 面晚到 → 误码率上升、EVM 恶化但不掉线。判据："完全不发"或"固定位置的空洞"是配置/时序问题；"随负载变化的零星异常"才去查网络。

  4. 基础什么是 eAxC？它的数量怎么算？

    eAxC（extended Antenna-Carrier）是前传上一条独立 IQ 数据流的标识，粒度是一个天线端口（或空间流）× 一个载波 × 一个方向。eCPRI 头里的 ecpriPcid（U 面）/ ecpriRtcid（C 面）就是这个 16-bit 的门牌号，O-RU 靠它把流分派到正确的处理通道。

    数量是乘积关系，所以增长很快：

    eAxC 数 = 空间流数 × 载波数 × 方向数(DL/UL)

单载波 4 层   → 4 × 1 × 2 = 8      ≈ 13.7 Gbps（9-bit BFP）
单载波 8 层   → 8 × 1 × 2 = 16     ≈ 27.4 Gbps
3 载波 8 层   → 8 × 3 × 2 = 48     ≈ 70 Gbps 量级

    还有一个容易漏的要点：16-bit eAxC ID 不是扁平编号，它被切成 DU_Port_ID / BandSector_ID / CC_ID / RU_Port_ID 几个子字段，而各字段的位宽由 M 面配置（o-ran-uplane-conf 里的几个 bitmask）。两端配的位宽不一致时，同一个 16-bit 值会被解读成不同的"载波+天线"组合，流被送错通道——而两端都显示"配置成功、无告警"，抓包看到的报文也完全合法。

8.2 中级（区分熟练度）

  1. 中级前传 IQ 为什么必须压缩？位宽怎么权衡？

    先给量化理由，这比讲道理有说服力。100 MHz / SCS 30 kHz → 273 PRB，每毫秒 28 个符号：

    一条 eAxC 每毫秒的 RE 数 = 273 × 12 × 28 = 91,728
未压缩（16-bit I + 16-bit Q）= 91,728 × 32 bit ≈ 2.94 Gbps / 流
8 层单方向未压缩 ≈ 23.5 Gbps  → 25GbE 装不下一个小区
9-bit BFP 后    ≈ 13.7 Gbps  → 还能给上行和 C/S/M 留余量

    所以压缩不是优化，是这套架构能不能成立的前提。

    为什么频域 IQ 压得动：同一个 PRB 内 12 个 RE 经历的信道衰落几乎相同，幅度量级接近，适合共享一个指数。这就是分块浮点（BFP）的物理前提。9-bit BFP 下每 PRB = 1 B 指数 + 12×2×9 bit = 28 B，相对未压缩 48 B 约 0.58 倍。指数由块内幅度最大的 RE 决定，小幅度的 RE 损失有效尾数位——这是精度损失的来源，但因为 EVM 是相对整体功率的指标，所以可以接受。

    权衡：位宽越小越省带宽，但量化误差越大、EVM 越差，能支撑的最高调制阶数越低。TS 38.104 对基站 EVM 的限值量级大致是 QPSK 17.5% / 16QAM 12.5% / 64QAM 8% / 256QAM 3.5%。9 bit 是业界最常用的折中点。

    最容易答漏的一点：不能拿"9-bit 的量化误差小于 3.5%"就断定 256QAM 没问题。压缩只是整条 EVM 预算里的一项，同一个预算里还有功放非线性残余、本振相位噪声、DAC/ADC 量化与时钟抖动、滤波器平坦度、通道间不一致性。压缩应该只占总预算的一小部分，且必须实测确认，不能纸上算。

  2. 中级S 面为什么要做到 ns 级？3 μs、65 ns、130 ns 这几个数字分别对应什么？

    关键是要说清这是三个互相独立的物理原因，精度要求差一两个数量级，混在一起谈会导致选型时欠设计或过度设计：

    • ≈ 3 μs：TDD 小区间相位同步。TDD 上下行共用频率靠时间分开。相邻站的时隙边界错开时，A 站还在发下行、B 站已切到收上行，A 的大功率下行直接灌进 B 的上行接收机（基站功率比 UE 高几十 dB）。要点：受害者是邻区，肇事者自己一切正常。
    • ≈ 65 ns：MIMO / 发射分集的天线口间 TAE。多天线合成指向性波束靠精确的相位关系，时间偏差直接变成相位偏差，波束就歪了或散了。
    • ≈ 130 ns（带内连续 CA）/ 260 ns（带内非连续、跨带 CA）：载波间 TAE。UE 要同时在多个载波上接收，载波间偏差超容限就对不齐接收窗。

    （TAE 数值是 TS 38.104 的量级要求，具体以所用版本为准。）

    预算怎么花掉也要能说：G.8271.1 的典型划分是总 1.5 μs 里网络部分约 1.1 μs、末端应用约 0.4 μs。1.1 μs 要分给 PRTC 自身、每一跳 T-BC 的噪声累积（所以跳数是硬约束），以及最容易被忽略的链路收发不对称——PTP 假设收发对称、用往返时延的一半估单程，不对称量 Δ 会产生 Δ/2 的固定相位误差，而 PTP 自己完全发现不了。BiDi 单纤双向光模块收发波长不同，不对称量在每公里数纳秒量级，必须做静态补偿配置，而这一项经常被漏掉。

  3. 中级LLS-C1 ~ C4 有什么区别？怎么选？

    四种配置的差别只有一件事：O-RU 的时间从哪儿来。

    配置O-RU 的时钟源对前传网络的要求主要代价
    C1O-DU，点到点直连无中间设备不能经交换网络；O-DU 需自带 PRTC
    C2O-DU，经交换网络每一跳都必须是 T-BC跳数吃时间预算；O-DU 成为时钟单点
    C3前传网络中独立的 T-GM（常配 GNSS）每跳 T-BC + 建时钟网络要单独规划部署监控一套时钟网络
    C4O-RU 本地 PRTC（GNSS）无同步要求每站一套 GNSS：成本、天空视野、抗干扰/防欺骗

    选型判断顺序：① 前传中间有交换设备吗？没有 → C1 最省事。② 有，但能不能全部换成 T-BC？不能 → 只剩 C4。③ 能 → 时钟源放 O-DU 是 C2、放网络里是 C3。

    规模稍大就选 C3，理由是它是唯一让"时钟"成为一个可独立冗余、独立监控、独立演进的子系统的方案：可以做 1+1 冗余、可以独立升级、O-DU 换厂商不影响同步。C2 看起来省了一套设备，但它把 O-DU 变成单点——O-DU 升级重启，挂在它下面的所有 O-RU 一起进保持。

  4. 中级M 面的 hierarchical 与 hybrid 模式有什么区别？各自的风险是什么？

    先说共同点：O-RU 是 NETCONF Server，O-DU / SMO 是 Client（被管的那一方跑服务器）。两种模式的差别只在 O-RU 身上有几条 NETCONF 连接：

    • Hierarchical（层级）：只有 1 条，来自 O-DU。SMO 想看/改 O-RU 必须经 O-DU 代理。配置权归属清晰，运维简单，O-RU 只需与 O-DU 互通。风险是 O-DU 成为唯一通道：O-DU 故障时 O-RU 完全"看不见"；O-RU 的特有功能受限于 O-DU 是否支持对应的 YANG 模块，多厂商解耦较弱。
    • Hybrid（混合）：≥ 2 条，O-DU 一条 + SMO 直连一条。SMO 可以直接做软件升级、证书管理，不依赖 O-DU 支持，多厂商解耦更强。代价是 O-RU 还要与 SMO 互通（跨网段、跨安全域），网络规划更复杂。

    Hybrid 最大的风险是双主写冲突。NETCONF 没有内置的"配置权长期归属"机制（lock 只保护一次事务），两个 client 都可能以为自己是唯一的配置者。症状极难查——配置会"自己变回去"，因为另一个 client 在按它的意图周期性纠偏。所以必须在运维流程上硬性约定子树归属，典型的划分是：时序与载波参数（o-ran-uplane-conf、o-ran-delay-management）只由 O-DU 写，软件包与证书只由 SMO 写。

    加分点：前传 M 面用 NETCONF Call Home（RFC 8071，TCP 4334/4335），方向是 O-RU 主动去连 client，而不是常规的 client 连服务器 830 端口。因为一个站点几十台 O-RU 逐台规划地址不现实。副作用是排障思维要反过来：M 面连不上，先查 O-RU 有没有拿到 IP、有没有发出 SYN，而不是先去 ping O-RU。

8.3 高级（体现深度）

  1. 高级同步丢失后，业务上会看到什么？为什么"看到"的时刻往往晚很多？

    S 面故障有明确的四个阶段，理解它能解释很多"故障为什么隔了半小时才爆发"：

    1. LOCKED：正常。
    2. HOLDOVER：源丢了，本地时钟还在撑。持续分钟到小时（有 SyncE 保住频率则长得多）。业务完全正常，看不出任何异常。
    3. 相位漂出容限：先是邻区上行底噪抬升、上行吞吐塌陷，然后 UE 大面积掉线，最后 O-RU 可能主动停发。
    4. FREERUN：小区静默。

    滞后就来自阶段 ②。同步告警响的时候业务是好的，业务出问题时同步告警已经响了几十分钟——如果这两类告警分给了两个组，就很可能被当成两个独立事件。所以：同步告警的优先级不能按"业务是否受影响"定，必须按"保持时间还剩多少"定。成熟的现场会把 HOLDOVER 直接定为高级别告警，哪怕此刻所有指标都绿。

    两个必须补上的深度点：

    LOCKED ≠ 没问题
    sync-state = LOCKED 只说明"我跟上了我的上游"，不说明"我的上游是对的"。整条时钟链一起漂时，每一级都是 LOCKED。判断链条源头健不健康要看 clockClass（6 = 锁定到 PRTC，7 = 上游 PRTC 进入保持，248 = 自由运行），而很多现场只监控了 lock-state。
    重锁时的相位跳变
    保持期间已经漂了几百纳秒，重新锁定时把相位"拽回来"的瞬间对空口是一次不连续。有些实现会选择缓慢牵引而不是直接跳变，代价是恢复时间更长。
  2. 高级前传排障为什么是 S → M → C → U 的顺序？为什么不按故障概率排？

    因为这个顺序是按"排除它的代价"和"它的故障会不会污染后续观测"排的，不是按概率排的。论概率 M 面根因最多，但它不该放第一。

    • S 面第一：它一旦有问题，后面所有观测都不可信。同步不对时，接收窗计数里的"早到/晚到"全是同步偏差的投影，你会得出完全错误的时序结论。而排除它只要读一次 sync-state + clockClass——代价接近零，收益是让后面所有数据变得可信。
    • M 面第二：根因概率最高，验证成本最低。C/U 的全部时序与格式参数都从 M 面来，验证方法只是把两端配置读出来逐字段比。关键心态是不要相信"配置应该是对的"，读出来看。
    • C 面第三、U 面第四：靠接收窗计数，不靠抓包。C 面总接收计数为 0 → 一个都没到，查 VLAN/MAC/eAxC；RX_LATE > 0 → 查优先级队列与提前量；RX_EARLY > 0 → 提前量配大了或链路变短了。
    • 网络最后：最贵、最容易被冤枉。前传故障里指向"网络/光纤/光模块"的误判特别多，而在前四步做完之前去查网络，通常结果是"网络一切正常"，然后损失两天。

    一个能体现工程判断的补充：先用免费证据把范围缩窄，再决定是否付费。证据链按代价递增是：读 o-ran-sync（一秒）→ 读接收窗计数与 SEQ_ID 丢包（已在上报）→ 比对两端 M 面配置 → 交换机队列丢包计数 → 最后才是 TAP + 硬件时间戳抓包（要停业务、要设备）。

  3. 高级前传抓包有哪些困难？该怎么做？

    三个硬约束，缺一个结论就不可信：

    速率
    25 Gbps 双向 = 6.25 GB/s。tcpdump/libpcap 走内核协议栈 + 单线程写盘必丢包，而丢掉的恰好是你要找的那个突发——抓到的"正常"是假的。13.7 Gbps 全量落盘 = 1.7 GB/s ≈ 100 GB/分钟。
    时间戳精度
    判断"早到/晚到"要和 μs 级的接收窗比，软件时间戳的误差就有几十 μs，比窗口还大，结论必然错。必须用带硬件时间戳的网卡或采集卡，而且它自己要同步到同一个时间源——否则你在拿两个不同的钟做减法。
    取包点
    交换机镜像口把双向 25G 塞进一个 25G 口，单向利用率过半就开始丢，重载时的镜像结论不可信。光分路器（TAP）+ 采集卡是唯一在满载下可信的方式。

    可行的做法：先靠"只抓头部"把数据量压下来——头部信息全在前 30 字节内，IQ 载荷对排障毫无用处：

    $ tcpdump -i ens1f0 -s 128 -w fh.pcap 'ether proto 0xaefe'
# 无 VLAN 时 eCPRI 头从第 14 字节起：ether[15]=msgType
#   ether[18:2]=pcid/rtcid(eAxC)
$ tcpdump -i ens1f0 'ether proto 0xaefe and ether[15] == 2'   # 只抓 C 面
# 带 VLAN（前传常态）：整体后移 4 字节，写死绝对偏移最稳妥
$ tcpdump -i ens1f0 'ether[16:2] == 0xaefe and ether[19] == 2'
# S 面量小，可长期抓 —— 性价比最高的一条
$ tcpdump -i ens1f0 -w ptp.pcap 'ether proto 0x88f7'

    另外 Wireshark 有 eCPRI 与 O-RAN 前传解析器，但要先在首选项里填入 eAxC 各 bitmask 的位宽，否则它切分出的 CC_ID / RU_Port_ID 是错的。

    最该表达的判断：抓包在前传的定位是"验证一个已经成型的假设"，不是"用来找线索"。因为窗口很短、代价很高（要停业务插 TAP），漫无目的地抓几乎一定白干。正确顺序是先用 O-RU 的接收窗计数把范围缩到"某一条 eAxC 的 C 面晚到"，再去抓包确认。

  4. 高级某个 O-RU 突然不发射了，M 面正常、无告警。你怎么查？

    严格按 S → M → C → U 推进，每一步都有明确的"通过/停止"判据。

    ① S 面（2 分钟）。读 o-ran-sync：sync-state 是否 LOCKED、clockClass 是否为 6（不能只看 lock-state）；读 ptp4l：rms 是否在几十 ns 内、delay 最近有没有阶跃跳变（跳变意味着路径变了，不对称补偿已失效）、freq 是否在持续单向漂。任一项异常就停在这里——不然后面的时序数据全部不可信。

    ② M 面（5 分钟），最有信息量的一次读取。读 o-ran-uplane-conf 的 tx-array-carriers，看 active（rw，你的意图）与 state（ro，实际结果）这一对：

    • active=ACTIVE 但 state 停在 DISABLED/BUSY → 问题在 O-RU 内部（同步没锁、频率不支持、射频/功放故障），不必再查 C/U 面。
    • state=READY → O-RU 认为自己已准备好发射，所以问题不是"发不出去"而是"没有内容可发"，射频通路和载波配置可以整体排除，范围一下缩到 C/U 面。

    顺便比对四项两端一致性：载波中心频率/带宽、压缩位宽与方法、eAxC 四个 bitmask 的位宽、以及 O-DU 用的延迟参数是 O-RU 上报的值还是模板默认值。

    ③ C 面（3 分钟）。拉接收窗计数。最典型的一种结果是：U 面 RX_TOTAL / RX_ON_TIME 都是满的，而 C 面总接收计数为 0。这时有一次关键推理：U 面能到、C 面到不了，而两者走同一根光纤、同一个 VLAN——所以链路不通、VLAN 没放通、MTU 不够、光模块故障全部可以排除（它们会同时影响 U 面）。剩下只有两种可能：O-DU 没发，或 C 面被发到了别的地方。

    ④ 定位到具体配置。在 O-DU 网卡上抓 C 面（量小，几秒够）确认它确实在发；然后读 o-ran-processing-element 比对 C 面与 U 面各自的 VLAN 和目的 MAC。实战中最常见的根因就是这里：开站复制了别站的配置模板，U 面的 MAC 改了、C 面的没改，于是 C 面报文被泛洪后在 O-RU 网口因目的 MAC 不匹配被直接丢弃，连计数器都不加。

    为什么全程没有告警——这是这道题真正想考的：O-RAN 前传没有"C 面没收到"这种告警，因为 O-RU 无法区分"这个 eAxC 我配了但对端没发"和"这个 eAxC 本来就还没启用"。它只提供计数器。所以不主动去读计数，这个故障可以静默存在到有人拿频谱仪去量。

    沉淀：把"C 面总接收计数 > 0"和"U 面 RX_ON_TIME 占比 > 99.9%"写进开站脚本的准出门槛，与"载波 state = READY"并列。成本是一次 NETCONF get，能在开站阶段拦掉绝大多数 C/U 配置类问题。
