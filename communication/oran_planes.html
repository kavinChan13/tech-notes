O-RAN 中的 User / Control / Management Plane

通信系统里到处是"平面（Plane）"：用户面、控制面、管理面、同步面……初学者常被绕晕。这一篇专门解决一个问题——为什么通信系统要分这么多 Plane？并把每个平面和它用的具体技术（eCPRI / O1 / NETCONF / PTP）对应起来。

Module 06 阅读 ~60 min 概念收口
01

为什么有这么多 Plane

按"职责 + 时间尺度"分离关注点

"平面"是一种逻辑分类：把流经系统的流量按用途分开——业务数据、控制信令、配置管理、时间同步。要分开是因为它们的性能要求、可靠性要求、安全域、变化频率完全不同，混在一起既难保障又难管理。

🏢 生活类比：一栋写字楼的四套系统

用户面=员工进出办公（主营业务，量最大）；控制面=门禁/电梯调度（指挥业务怎么走）；管理面=物业配置楼宇（改规则、查报表，慢但关键）；同步面=全楼统一时钟（大家步调一致）。四套系统各走各的线路、各有优先级，坏了一套不至于全瘫——这就是"分平面"。

平面（Plane）：按流量用途划分的逻辑通道。经典三平面 = User（数据）/ Control（控制）/ Management（管理）；在前传等对时间敏感的场景再加 Sync（同步）平面。它们常常物理上共享同一张网络，靠 VLAN + QoS 隔离与优先级保障。
本篇讲 Open Fronthaul（O-DU ↔ O-RU，7-2x 拆分）上并行流动的 C / U / S / M 四个平面：各自传什么、时序上怎么咬合、配置与故障如何互相传染。以下四篇只引用不重复：eCPRI 深入（报文头逐字段）、O-RAN 接口（E2 / A1 / O1 / F1）、PTP 与 SyncE（时钟原理）、前传中传回传（分段与承载）。

分平面的四条硬理由

① 时间尺度差了九个数量级。下面这条对数时间轴是分平面最硬的理由：为纳秒级抖动做设计（硬件时间戳、专用 PLL、逐跳边界时钟）代价极高，而配置下发根本不需要这份代价。分平面本质上是"把昂贵的保障只花在真正需要的流量上"。

② 失效后果的"半径"完全不同。U 面丢一个包，上层 HARQ 重传就补回来了；S 面丢锁，整个小区的 TDD 收发切换点漂移，不但自己发不出去，还会干扰邻区。后果半径差这么大的东西，不能共用同一套保护与告警策略——分平面同时也是在划故障域：

③ 安全域不同。拿到 M 面等于拿到基站，它必须双向证书认证、必须有操作审计；U 面是海量 IQ，逐包加密会把时延预算吃光。两者对"安全"的定义是冲突的。④ 变化频率不同。M 面的 YANG 模型每版都在扩充，U 面的 IQ 格式一旦定下就不能轻易动（涉及 FPGA/ASIC）——分平面让快变与慢变解耦，各自按自己的节奏升级。

CPRI 时代没有"平面"这回事

传统 CPRI 是一条恒定速率的同步串行链路：控制字占哪些字节位置、IQ 数据占哪些位置，都是按规范写死的时分复用——不需要"平面"这个概念。

能力CPRI（恒定比特率）eCPRI / Open Fronthaul（分组化）
用户数据时域 IQ，占满固定时隙，无话可讲也照样发满频域 IQ，按实际调度的 PRB 发，空载几乎不占带宽
控制信息控制字里的固定字段，与数据同一条流独立的 C 面报文，需要显式的时序约定
同步内建：链路本身是同步的，从比特流里就能恢复时钟与帧头必须补一个 S 面：以太网是异步的，时间要靠 PTP 重新分发
管理厂商私有的 L1 inband 通道 / 慢速链路独立的 M 面：NETCONF/YANG，标准化、可多厂商互通
带宽随小区负载不变（与负载无关）随负载变化，可统计复用
能不能过交换机不能（点到点专用链路）能（标准以太网，可组环、可汇聚）

所以"四平面"不是凭空设计出来的分类学，而是把 CPRI 里由物理层免费提供的三件事，在以太网上重新显式地建出来：时间要自己同步（S 面）、时序要自己约定（C 面的提前量窗口）、设备要自己管（M 面）。本篇后面讲的所有陷阱，几乎都源自这一句。

把分平面讲成一次技术债的显式化，比答"职责分离"深一层。它还顺带解释了一个现象：前传故障里时序类问题的占比远高于带宽类——带宽是花钱能买的，时序不是。
02

User Plane（用户面 / 数据面）

真正搬运业务数据的那一面

口诀：User Plane = "干活的"——只管把数据高效搬过去，不管为什么搬、按什么规则搬（那是控制面的事）。它流量最大、讲究"快"，前传上用 eCPRI over Ethernet，核心网侧则是 GTP-U。

前传上流的不是"用户数据"，是频域 IQ

7-2x 拆分把 iFFT/FFT、CP、数字波束成形放在 O-RU 侧，O-DU 交给前传的就是一格一格的频域采样点。

RE（Resource Element）：NR 时频栅格上最小的一格 = 1 个子载波 × 1 个 OFDM 符号，承载一个复数（I + Q），代表这一格上的星座点。前传 U 面搬的就是这些复数。12 个连续子载波构成 1 个 PRB。

📊 生活类比：传"照片"还是传"每个像素的颜色值"

回传上是 IP 报文，好比传一张 JPEG 照片。前传 U 面是频域 IQ，好比把照片拆成每个像素的 RGB 数值，按扫描顺序一行一行发过去：数据量大出一两个数量级，而且某个像素来晚了就只能丢——因为下一行已经该出屏了。

维度时域 IQ（CPRI / 拆分 8）频域 IQ（eCPRI / 拆分 7-2x）
采样对象整个载波带宽的时域波形每个已调度 RE 的复数
带宽是否随负载变化不变变：只发被调度到的 PRB
O-RU 需要做什么只做 DAC/ADC + 上下变频还要做 iFFT/FFT、CP、（Cat B 时）波束成形
与调度信息的耦合无（波形自带一切）强：必须由 C 面告诉 O-RU 这批 RE 放在哪
压缩空间有限（波形动态范围大）较大（同一 PRB 内幅度接近，适合分块浮点）

最后一行是关键：频域 IQ 能压缩，正因为同一个 PRB 内 12 个 RE 经历的信道衰落几乎相同、幅度量级接近——这就是分块浮点能奏效的物理前提。

先算一笔带宽账：压缩不是优化，是前提

不压缩的话，一个 8 层的 100 MHz 小区单方向就要吃掉 23.5 Gbps，25GbE 连一个小区都装不下。所以压缩不是"省点钱"，而是"这套架构能不能成立"。

部署要求是全链路 MTU ≥ 9000，含所有中间交换机。"某一跳的 MTU 没配够"是前传上线阶段最常见的低级故障之一——症状是大包被丢、小包正常，看起来像"随机丢包"。

分块浮点：用一个共享指数换掉一半带宽

O-RAN WG4 定义了若干压缩方法，字段 udCompMeth 标识用哪一种，udIqWidth 标识压缩后每个分量的位宽，两者合起来在报文里叫 udCompHdr。工程上用得最多的是分块浮点（Block Floating Point, BFP）。

压缩方法原理一句话典型用途 / 特点

压缩只是整条链路 EVM 预算里的一项，而且是最不该占大头的那一项。同一个预算里还有功放非线性残余、本振相位噪声、DAC/ADC 量化与时钟抖动、滤波器带内平坦度、通道间不一致性。所以不能拿"9-bit BFP 的量化误差小于 3.5%"就断定 256QAM 没问题——必须实测确认，不能纸上算。另外上下行可以配不同位宽（上行动态范围问题更突出），具体组合由 O-RU 经 o-ran-module-cap 上报，O-DU 只能在交集里选。

eAxC：前传上成百上千条流的"门牌号"

eAxC（extended Antenna-Carrier）：前传上一条独立 IQ 流的标识，粒度是一个天线端口（或空间流） × 一个载波 × 一个方向。eCPRI 头里的 ecpriPcid 就是这个门牌号，O-RU 靠它把 IQ 分派到正确的处理通道（位域细节见 eCPRI 深入 §4.1）。

U 面的四个生产陷阱

  • 丢包不重传。ecpriSeqid 只用于丢包/乱序检测——重传回来的 IQ 早就过了它该出现的符号。所以前传的设计目标是零丢包，不是"低丢包率"；序列号的价值全在可观测性（见 eCPRI 深入 §4.3）。
  • 早到和晚到都算丢。落在 O-RU 接收窗外的报文一律丢弃，所以把网络做"快"也可能出问题——换更短的光纤、去掉一级交换机，报文可能变成"太早到"。这是运维直觉最容易翻车的地方，细节见 §3.2。
  • 微突发比平均带宽更致命。每 35.7 μs 所有 eAxC 一起发，平均 13.7 Gbps 的负载瞬时按线速冲。典型症状是交换机输出队列丢包计数缓慢增长，而端口利用率看起来只有 60%。
  • 空载不等于零流量。U 面只发被调度的 PRB，但 C 面仍按时隙节奏在发、S 面照旧。"半夜没人用了前传应该很空"这个假设只对 U 面成立。
03

Control Plane（控制面）

决定数据"怎么走"的信令

经典比喻：控制面是"点菜下单"，用户面是"上菜"——先有控制信令决定用哪些资源，用户面才据此把数据搬过去。它数据量小但极其关键，前传上承载调度与波束控制，RAN 内还有 E2 与 F1-C、核心网有 NGAP。

C 面传的是"section 描述"：这批 RE 放在哪、用哪个波束

把 U 面理解成"一车货"，C 面就是随车的提货单：这车货属于第几帧第几时隙、占哪些 PRB、用哪个波束打出去。O-RU 收到 IQ 之后并不知道该把它们放进时频栅格的哪个位置——这个信息只在 C 面里。

Section（段）：C 面消息的基本单元，描述"一段连续的时频资源 + 它的属性"。一条 C 面消息可携带多个 section（numberOfSections），因为一个时隙里往往有多块不连续的 PRB 分给不同 UE、用不同波束。

C 面走 Message Type 2，O-RAN 应用层这部分才是"C 与 U 如何配对"的载体（eCPRI 公共头的逐字段拆解见 eCPRI 深入 §2.1）：

C 与 U 的时序配对：本篇最关键的一节

C 面报文必须先于对应的 U 面报文到达 O-RU，而且两者都必须落在各自的接收窗口内。早到、晚到、只到一个，结果都是——那个时隙不发射。O-RU 不会等、不会缓存、不会重传，因为空口的发射时刻是由 S 面钉死的绝对时间，过了就过了。

04

Management Plane（管理面）

配置、监控、运维的那一面

  • 是什么：设备的配置下发、性能/故障监控、软件升级（FCAPS）。改的是"设备的长期行为规则"，而非某条业务流。
  • 特点：变化慢、可靠性要求高、安全要求高（能改配置=能改一切）；讲究"稳、可追溯、安全"。
  • 对应技术：NETCONF/YANG（O-RAN O1 接口、前传 M 平面），走 SSH/TLS 保护，用 TCP 保证可靠。
这解释了为什么管理面用 TCP + NETCONF，而前传用户面用 eCPRI over Ethernet：前者要"可靠、事务化、安全"（TCP/TLS/SSH 完美契合），后者要"极低时延确定性"（TCP 反而是负担）。同一系统里，不同平面按需选择不同的传输机制。

前传 M 面的具体形态：O-RU 是 NETCONF 服务器

前传 M 面的角色分配和直觉相反：O-RU 是 NETCONF Server，O-DU / SMO 是 Client——被管的那一方跑服务器。协议本身的原理见 NETCONF 工程实践 §3.3，这里只讲前传特有的部分：一台刚上电的 O-RU 不知道自己的 IP、不知道 VLAN、不知道谁该来管它，得靠一套逐步收敛的流程把 M 面建起来。

Call Home 的方向反转是前传 M 面最值得记住的设计：一个站点几十台 O-RU，逐台规划可路由地址不现实，所以改成 O-RU 拿到地址后主动"来敲门"。副作用是排障思维也要跟着反过来——M 面连不上，先查 O-RU 有没有拿到 IP、有没有发出 SYN，而不是先去 ping O-RU。

第 ⑥ 步还藏着一个"鸡生蛋"：TLS 证书校验依赖系统时间，而 O-RU 刚上电时时间还没同步。实现上靠 RTC 或宽松的初始时间校验绕过，但 O-RU 断电很久、RTC 电池耗尽就会撞上，症状是"新装的 RU 连不上，老的都正常"。

Supervision 看门狗：M 面断了怎么被发现

TCP 连接会在中间设备重启、路由切换后静默失效：两端都以为连接还在，直到下一次写操作才报错。所以 o-ran-supervision 定义了一个看门狗——Client 周期性调用 supervision-watchdog-reset 重置 O-RU 侧的监督定时器，O-RU 在 rpc-reply 里回一个下次期望被喂狗的时间点。超时 = supervision-notification-interval + guard-timer-overhead，后者是留给网络抖动与 client 侧 GC/调度延迟的余量：配小了 M 面会被误判断开、会话反复重建；配大了真断了也发现得慢。

M 面断开不一定影响业务——C/U/S 面完全不依赖 M 面在线，M 面掉了小区照样发射。所以它的紧急程度低于同步告警，但危险在于失去了观测能力：接下来任何故障都只能靠 O-DU 侧的间接指标去猜。不紧急，但不能积压。

Sync Plane（同步面）

让所有设备"对时"

同步面分发精确的频率 + 相位/时间（PTP + SyncE），优先级最高：时间不能晚、不能抖。它是 eCPRI 以太网化之后必须补上的一块——CPRI 时代同步内建在链路里，不需要单独一个平面。

为什么必须做到 ns 级：三个互相独立的理由

前传的同步需求来自三个完全独立的物理原因，各自的精度要求差一两个数量级——搞混它们会导致选型时过度设计或严重欠设计。① TDD 收发切换（μs 级）管的是"别互相干扰"：相邻两站的时隙边界一错开，A 站还在发下行、B 站已切到收上行，A 的大功率下行直接灌进 B 的上行接收机。② MIMO 相位一致（几十 ns）管的是波束能不能成形：时间偏差直接变成相位偏差。③ 载波聚合（百 ns）管的是 UE 能不能把多个载波拼起来。

MIMO / 发射分集同一载波内天线口间的 TAE≈ 65 ns波束指向偏、增益下降、MIMO 秩上不去

PTP 和 SyncE 各给什么：为什么要两个都上

既然 PTP 能给时间，为什么还要 SyncE？因为它们给的东西不一样，而且失效模式互补（原理见 PTP 与 SyncE）：

维度SyncE（ITU-T G.8262 / G.8264）PTP（IEEE 1588 / G.8275.1）
提供什么频率（每秒有多长）相位 + 时间（现在几点、秒边界在哪）
工作在哪一层物理层：从收到的比特流里恢复时钟报文层：靠带时间戳的报文往返计算
受排队 / 拥塞影响吗不受——比特流一直在，与队列无关受：报文时延变化（PDV）直接变成噪声
能单独满足前传吗不能：没有相位信息，TDD 切换点无从确定理论上能，但对网络质量要求高

需要网络设备支持吗需要：每跳都要能恢复并再生时钟需要：每跳最好是 T-BC（边界时钟），带硬件时间戳

组合起来的价值在于保持（holdover）能力：

⌚ 生活类比：报时的人和秒表

PTP 像一个每隔一会儿喊一次"现在是 12 点 00 分 00 秒"的人——他给你绝对时刻，但如果房间里很吵（网络拥塞），你可能听错几次。SyncE 像一只走得极准的秒表——它不知道现在几点，但能保证"一秒就是一秒"。两个一起用：靠喊话对准绝对时刻，靠秒表在喊话听不清或中断的时候继续稳稳地走。只有秒表，你不知道该几点开始发；只有喊话的人，房间一吵你就乱了。

工程上的收益有两处：有了 SyncE 的物理层频率，PTP 从时钟只需跟踪相位、不必同时跟踪频率，环路带宽可以做得很窄，对 PDV 的抑制能力大幅提高；反过来 PTP 源短暂中断时，SyncE 保住频率，相位漂移速率慢一两个数量级，把保持时间从分钟级拉长到小时级。

第一层是"官方口径"：M 面读 o-ran-sync，一次 get，也是整个排障流程的起点。

sync-state = LOCKED 不等于"同步没问题"：它只说明"我跟上了我的上游"，不说明"我的上游是对的"。整条时钟链一起漂时，每一级都是 LOCKED。判断链条源头健不健康要看 clockClass。很多现场只监控了 lock-state，这是同步类漏判的头号原因。

第二层是量化数据：O-DU 侧的 linuxptp。三个量分别指向不同的根因，其中最容易被忽略的是 delay：

指标正常量级异常时指向

ptp4l 的 freq（ppb）稳定在某个值附近持续单向漂 → 本地晶振老化，或 SyncE 源丢了
ptp4l 的 delay（ns）恒定阶跃跳变 → 路径变了（改接 / 保护倒换 / 路由切换），意味着不对称补偿值已失效——offset 看着正常，实际相位已经偏了
pmc 的 stepsRemoved越小越好距 GM 的跳数，直接对应误差累积
pmc 的 grandmasterClockClass6真正该进告警的那个字段（见上）

第三层是天线口实测。前两层都发现不了路径不对称，只有接外部时间源实测才能。通常只在开站验收和疑难故障时做，但一旦怀疑不对称，前两层的数据全都不能作为证据。

丢锁之后：HOLDOVER 是一个有过期时间的状态

S 面故障的时间演进有四个阶段，理解它能解释"故障为什么隔了半小时才爆发"：

阶段状态典型持续业务表现该做什么
①LOCKED—正常监控 clockClass 与 delay 阶跃
②HOLDOVER分钟 ~ 小时（有 SyncE 保频率则长得多）完全正常，看不出任何异常这是唯一的处理窗口，必须在这个阶段修好
③相位漂出容限—先是邻区上行底噪抬升，然后 UE 大面积掉线，最后 O-RU 可能主动停发已经出事故了
④FREERUN—小区静默恢复时钟源，注意重锁可能有相位跳变
阶段 ② 的"完全正常"是 S 面运维的核心难点：同步告警出现时业务还是好的，业务出问题时往往已经过了几十分钟。所以同步告警不能按"业务是否受影响"定优先级，只能按"保持时间还剩多少"定——成熟的现场会把 HOLDOVER 直接定为高级别告警，哪怕此刻一切指标都绿。另有一个细节：重锁时可能出现相位跳变，保持期间漂了几百纳秒，把相位"拽回来"的瞬间对空口是一次不连续，所以有些实现选择缓慢牵引，代价是恢复更慢（见 PTP 与 SyncE §5.1）。

与之配套的是 ecpriSeqid：它只提供"感知"不提供"恢复"——序列号跳变说明中间丢了包，但那些 IQ 已经永久失去意义。把 SEQ_ID 推出的丢包率做成常态监控指标，比事后抓包有用得多——因为前传抓包很贵：25 Gbps 双向落盘约 100 GB/分钟，软件时间戳的几十 μs 误差比接收窗还大，镜像口在重载时自己就会丢包。三条约束的细节与可用的 BPF 表达式见 eCPRI 深入 §7.2。

排障判定顺序：S → M → C → U

基于上面的传染路径，前传排障有一个固定的推进顺序。这个顺序不是按"哪个平面更可能出问题"排的（论概率 M 面最高），而是按"排除它的代价最低、且它的故障会污染后面所有观测"排的：

① S 面同步锁了吗
② M 面配置到底是什么
③ C 面命令到了吗、准时吗
④ U 面数据准时吗、丢了多少
⑤ 网络 / 光路最后才轮到它

三条理由：S 面放第一，因为它一旦有问题后面所有观测都不可信——同步不对时，接收窗计数里的"早到/晚到"全是同步偏差的投影；而排除它只要读一次 sync-state + clockClass，代价接近零。M 面放第二，因为根因概率最高、验证成本最低，方法只是把两端配置读出来逐字段比——不要相信"配置应该是对的"，读出来看。网络放最后，因为它最贵也最容易被冤枉：上一节表里有五行的误判都指向"网络/光纤/光模块"。

真实案例一：新开站，O-RU 完全不发射

现象。某站新开一个 100 MHz TDD 小区。O-DU 侧显示小区已激活、无告警，M 面连接正常，但频谱仪在天线口完全测不到信号。现场第一反应是"O-RU 坏了"，已经在申请备件。

① S 面 2 分钟。sync-state = LOCKED、clockClass = 6、rms 在 10 ns 上下——同步没问题，后面的时序数据可信。

② M 面 5 分钟。tx-array-carriers 是 active = ACTIVE 且 state = READY：O-RU 认为自己已经准备好发射了。所以问题不是"发不出去"而是"没有内容可发"——射频通路、功放、载波配置一次性排除，范围缩到 C/U 面。

③ C 面 3 分钟。U 面 RX_TOTAL 与 RX_ON_TIME 都是满的，而 C 面总接收计数是 0。

关键的一次推理。U 面能到、C 面到不了，而两者走同一根光纤、同一个 VLAN——所以链路不通、VLAN 没放通、MTU 不够、光模块故障全部可以排除（它们会同时影响 U 面）。剩下只有两种可能：O-DU 没发，或 C 面发到了别的地方。在 O-DU 网卡上抓几秒 C 面，确认它在稳定发出，于是只剩后者。

根因。读 o-ran-processing-element：U 面端点的目的 MAC 是对的，C 面端点的目的 MAC 是另一个站点 O-RU 的地址——开站时复制了隔壁站的模板，改了一处没改另一处。C 面报文进交换机后按未知单播泛洪，到这台 O-RU 网口时因目的 MAC 不匹配被网卡直接丢掉，连计数器都不会加。

为什么全程没有告警——这是本案最值得记住的一点：O-RAN 前传没有"C 面没收到"这种告警，因为 O-RU 无法区分"这个 eAxC 配了但对端没发"和"这个 eAxC 本来就还没启用"。它只提供计数器。不主动去读，这个故障可以静默存在到有人拿频谱仪去量。

沉淀。把"C 面总接收计数 > 0"和"U 面 RX_ON_TIME > 99.9%"写进开站脚本的准出门槛，与"载波 state = READY"并列——成本是一次 NETCONF get。

真实案例二：上行底噪每天定时抬升

现象。某片区若干小区的上行底噪每天在大致相同时段抬升 10 dB 以上，持续一两小时后自行恢复，上行吞吐同步塌陷，下行完全正常。受影响小区分布在几个不同站点。第一反应是"外部干扰"，扫频已经安排上了。

第一条线索：只有上行坏。带宽、丢包、配置类问题通常先打下行（数据量大得多）。"只有上行受影响"强烈指向 TDD 相位同步——上行接收窗一旦与邻区的下行发射时间重叠，基站就会在自己的接收窗里收到邻区的大功率下行，而这在下行侧毫无表现。

第二条线索：受害者与肇事者不是同一个。漂掉的那个小区污染的是邻区的上行，它自己一切正常。所以不能只看告警小区，要把整片区的同步状态一起拉出来。

差点被排除掉的一步。所有 O-RU 的 sync-state 全是 LOCKED——按常见流程同步到这里就被排除了。但进一步读 clockClass，其中一片区域报的是 7：它们确实锁定了，但锁定到了一个已经失去 GNSS、正在保持中的上游 PRTC。

为什么会漂到互相干扰。该片区有两条独立时钟链，链 B 的 PRTC 进入保持后缓慢漂移，与链 A 之间的相对相位偏差随时间累积，超出 3 μs 容限后边界处开始互扰。同一条链上的小区反而没事——它们一起漂，相对关系不变，这解释了"按地理片区分布"的奇怪规律。

时段性与那 40 分钟的滞后。把可见卫星数、clockClass 变化时刻与底噪抬升时刻对齐，三者高度相关，但底噪抬升比 clockClass 变化晚了约 40 分钟——正是 §5.5 的阶段 ②。就是这个滞后让两件事被当成了两个独立事件，分给了两个组。至于"每天定时"，是站点旁新装的设备遮挡了 GNSS 天线的一部分天空视野。处置上短期给链 B 的 PRTC 加一路备份时钟源（从链 A 引 PTP，靠 clockClass 优选自动切换），长期移动天线恢复视野。

沉淀三条，比修复本身更有价值。① clockClass 必须进常态告警——本案里 lock-state 全程正常。② "进入 HOLDOVER 已持续多久"要作为独立指标，它才是"还剩多少时间"的直接度量。③ 上行底噪类告警的第一步改为"查本片区所有小区的同步状态"，扫频降到第三步。

面试题（12 道）

分层自测

8.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础Open Fronthaul 上的四个平面各自传什么？

    四个平面共享同一张前传以太网，靠 VLAN + PCP 隔离：

    • U 面（User）：频域 IQ 采样——每个 RE 上的复数。走 eCPRI Message Type 0。占前传带宽的 95% 以上，每个 OFDM 符号一批（30 kHz SCS 下约 35.7 μs）。
    • C 面（Control）：section 描述——哪个帧/时隙/符号、哪些 PRB、哪些 RE 有效、用哪个波束。走 eCPRI Message Type 2。带宽小（典型是 U 面的几个百分点）但时序最敏感。
    • S 面（Sync）：时间、相位、频率基准。PTP（IEEE 1588，前传常用 G.8275.1）+ SyncE。带宽可以忽略，但优先级最高。
    • M 面（Management）：配置、告警、性能计数、软件包。NETCONF/YANG over SSH 或 TLS。无实时要求，但它下发的参数决定了 C/U 面能不能正常工作。

    一个关键澄清：U 面虽然叫 User Plane，但它不含任何 IP 报文或可识别的业务内容——它是纯粹的频域采样。前传上看不到"用户在访问什么"。

  2. 基础为什么要把前传流量分成四个平面？CPRI 时代为什么没有这个概念？

    分平面的直接理由是这四类流量的时间尺度、失效后果、安全域、变化频率差异极大：S 面的误差预算是纳秒，M 面的配置变更以天计；U 面丢一个包由 HARQ 补回来，S 面丢锁会让整个小区静默还干扰邻区；M 面能改配置所以必须强认证，U 面逐包加密会吃掉时延预算。分平面本质上是"把昂贵的保障只花在真正需要的流量上"。

    更有洞见的答法是把它讲成一次技术债的显式化：CPRI 是恒定速率的同步串行链路，同步（从比特流恢复时钟）、时序（固定的时分复用位置）、管理（私有 inband 通道）这三件事由物理层"免费"提供，所以不需要独立的平面。改成以太网之后，以太网是异步的、分组的、best-effort 的，这三件事没有消失，只是从免费变成了要自己付费——于是各自长成了 S 面、C 面的提前量窗口、M 面。

    这也解释了一个现象：前传故障里时序类问题的占比远高于带宽类问题。带宽是花钱能买的，时序不是。

  3. 基础C 面和 U 面的时序关系是什么？失配会怎样？

    三层关系，缺一不可：

    • C 面必须先于对应的 U 面到达 O-RU，且至少早 tcp_adv_dl 这么多（O-RU 通过 M 面上报的能力）。因为 O-RU 需要先拿到 section 描述才知道随后的 IQ 该放进时频栅格的哪个位置。
    • 两者都必须落在各自的接收窗内：C 面在 [T2a_min_cp_dl, T2a_max_cp_dl]，U 面在 [T2a_min_up, T2a_max_up]。窗口是相对"空口发射时刻"倒推的提前量。
    • 所有时刻都以 S 面确定的绝对时间为参考，不是相对彼此。

    失配的后果统一是：O-RU 丢弃，那个时隙不发射。它不等、不缓存、不重传，因为空口的发射时刻是钉死的绝对时间，过了就没有意义了。注意早到也算失配——这最反直觉：把链路改短、去掉一级交换机，反而可能让报文变成"太早到"而被丢。

    从外面看到的症状差别很大：C 面完全没到 → 整个小区不发射；C 面偶发晚到 → 时隙随机不发，表现成"随机丢包、吞吐忽高忽低"；U 面晚到 → 误码率上升、EVM 恶化但不掉线。判据："完全不发"或"固定位置的空洞"是配置/时序问题；"随负载变化的零星异常"才去查网络。

  4. 基础什么是 eAxC？它的数量怎么算？

    eAxC（extended Antenna-Carrier）是前传上一条独立 IQ 数据流的标识，粒度是一个天线端口（或空间流）× 一个载波 × 一个方向。eCPRI 头里的 ecpriPcid（U 面）/ ecpriRtcid（C 面）就是这个 16-bit 的门牌号，O-RU 靠它把流分派到正确的处理通道。

    数量是乘积关系，所以增长很快：

    eAxC 数 = 空间流数 × 载波数 × 方向数(DL/UL)

单载波 4 层   → 4 × 1 × 2 = 8      ≈ 13.7 Gbps（9-bit BFP）
单载波 8 层   → 8 × 1 × 2 = 16     ≈ 27.4 Gbps
3 载波 8 层   → 8 × 3 × 2 = 48     ≈ 70 Gbps 量级

    还有一个容易漏的要点：16-bit eAxC ID 不是扁平编号，它被切成 DU_Port_ID / BandSector_ID / CC_ID / RU_Port_ID 几个子字段，而各字段的位宽由 M 面配置（o-ran-uplane-conf 里的几个 bitmask）。两端配的位宽不一致时，同一个 16-bit 值会被解读成不同的"载波+天线"组合，流被送错通道——而两端都显示"配置成功、无告警"，抓包看到的报文也完全合法。

8.2 中级（区分熟练度）

  1. 中级前传 IQ 为什么必须压缩？位宽怎么权衡？

    先给量化理由，这比讲道理有说服力。100 MHz / SCS 30 kHz → 273 PRB，每毫秒 28 个符号：

    一条 eAxC 每毫秒的 RE 数 = 273 × 12 × 28 = 91,728
未压缩（16-bit I + 16-bit Q）= 91,728 × 32 bit ≈ 2.94 Gbps / 流
8 层单方向未压缩 ≈ 23.5 Gbps  → 25GbE 装不下一个小区
9-bit BFP 后    ≈ 13.7 Gbps  → 还能给上行和 C/S/M 留余量

    所以压缩不是优化，是这套架构能不能成立的前提。

    为什么频域 IQ 压得动：同一个 PRB 内 12 个 RE 经历的信道衰落几乎相同，幅度量级接近，适合共享一个指数。这就是分块浮点（BFP）的物理前提。9-bit BFP 下每 PRB = 1 B 指数 + 12×2×9 bit = 28 B，相对未压缩 48 B 约 0.58 倍。指数由块内幅度最大的 RE 决定，小幅度的 RE 损失有效尾数位——这是精度损失的来源，但因为 EVM 是相对整体功率的指标，所以可以接受。

    权衡：位宽越小越省带宽，但量化误差越大、EVM 越差，能支撑的最高调制阶数越低。TS 38.104 对基站 EVM 的限值量级大致是 QPSK 17.5% / 16QAM 12.5% / 64QAM 8% / 256QAM 3.5%。9 bit 是业界最常用的折中点。

    最容易答漏的一点：不能拿"9-bit 的量化误差小于 3.5%"就断定 256QAM 没问题。压缩只是整条 EVM 预算里的一项，同一个预算里还有功放非线性残余、本振相位噪声、DAC/ADC 量化与时钟抖动、滤波器平坦度、通道间不一致性。压缩应该只占总预算的一小部分，且必须实测确认，不能纸上算。

  2. 中级S 面为什么要做到 ns 级？3 μs、65 ns、130 ns 这几个数字分别对应什么？

    关键是要说清这是三个互相独立的物理原因，精度要求差一两个数量级，混在一起谈会导致选型时欠设计或过度设计：

    • ≈ 3 μs：TDD 小区间相位同步。TDD 上下行共用频率靠时间分开。相邻站的时隙边界错开时，A 站还在发下行、B 站已切到收上行，A 的大功率下行直接灌进 B 的上行接收机（基站功率比 UE 高几十 dB）。要点：受害者是邻区，肇事者自己一切正常。
    • ≈ 65 ns：MIMO / 发射分集的天线口间 TAE。多天线合成指向性波束靠精确的相位关系，时间偏差直接变成相位偏差，波束就歪了或散了。
    • ≈ 130 ns（带内连续 CA）/ 260 ns（带内非连续、跨带 CA）：载波间 TAE。UE 要同时在多个载波上接收，载波间偏差超容限就对不齐接收窗。

    （TAE 数值是 TS 38.104 的量级要求，具体以所用版本为准。）

    预算怎么花掉也要能说：G.8271.1 的典型划分是总 1.5 μs 里网络部分约 1.1 μs、末端应用约 0.4 μs。1.1 μs 要分给 PRTC 自身、每一跳 T-BC 的噪声累积（所以跳数是硬约束），以及最容易被忽略的链路收发不对称——PTP 假设收发对称、用往返时延的一半估单程，不对称量 Δ 会产生 Δ/2 的固定相位误差，而 PTP 自己完全发现不了。BiDi 单纤双向光模块收发波长不同，不对称量在每公里数纳秒量级，必须做静态补偿配置，而这一项经常被漏掉。

  3. 中级LLS-C1 ~ C4 有什么区别？怎么选？

    四种配置的差别只有一件事：O-RU 的时间从哪儿来。

    配置O-RU 的时钟源对前传网络的要求主要代价
    C1O-DU，点到点直连无中间设备不能经交换网络；O-DU 需自带 PRTC
    C2O-DU，经交换网络每一跳都必须是 T-BC跳数吃时间预算；O-DU 成为时钟单点
    C3前传网络中独立的 T-GM（常配 GNSS）每跳 T-BC + 建时钟网络要单独规划部署监控一套时钟网络
    C4O-RU 本地 PRTC（GNSS）无同步要求每站一套 GNSS：成本、天空视野、抗干扰/防欺骗

    选型判断顺序：① 前传中间有交换设备吗？没有 → C1 最省事。② 有，但能不能全部换成 T-BC？不能 → 只剩 C4。③ 能 → 时钟源放 O-DU 是 C2、放网络里是 C3。

    规模稍大就选 C3，理由是它是唯一让"时钟"成为一个可独立冗余、独立监控、独立演进的子系统的方案：可以做 1+1 冗余、可以独立升级、O-DU 换厂商不影响同步。C2 看起来省了一套设备，但它把 O-DU 变成单点——O-DU 升级重启，挂在它下面的所有 O-RU 一起进保持。

  4. 中级M 面的 hierarchical 与 hybrid 模式有什么区别？各自的风险是什么？

    先说共同点：O-RU 是 NETCONF Server，O-DU / SMO 是 Client（被管的那一方跑服务器）。两种模式的差别只在 O-RU 身上有几条 NETCONF 连接：

    • Hierarchical（层级）：只有 1 条，来自 O-DU。SMO 想看/改 O-RU 必须经 O-DU 代理。配置权归属清晰，运维简单，O-RU 只需与 O-DU 互通。风险是 O-DU 成为唯一通道：O-DU 故障时 O-RU 完全"看不见"；O-RU 的特有功能受限于 O-DU 是否支持对应的 YANG 模块，多厂商解耦较弱。
    • Hybrid（混合）：≥ 2 条，O-DU 一条 + SMO 直连一条。SMO 可以直接做软件升级、证书管理，不依赖 O-DU 支持，多厂商解耦更强。代价是 O-RU 还要与 SMO 互通（跨网段、跨安全域），网络规划更复杂。

    Hybrid 最大的风险是双主写冲突。NETCONF 没有内置的"配置权长期归属"机制（lock 只保护一次事务），两个 client 都可能以为自己是唯一的配置者。症状极难查——配置会"自己变回去"，因为另一个 client 在按它的意图周期性纠偏。所以必须在运维流程上硬性约定子树归属，典型的划分是：时序与载波参数（o-ran-uplane-conf、o-ran-delay-management）只由 O-DU 写，软件包与证书只由 SMO 写。

    加分点：前传 M 面用 NETCONF Call Home（RFC 8071，TCP 4334/4335），方向是 O-RU 主动去连 client，而不是常规的 client 连服务器 830 端口。因为一个站点几十台 O-RU 逐台规划地址不现实。副作用是排障思维要反过来：M 面连不上，先查 O-RU 有没有拿到 IP、有没有发出 SYN，而不是先去 ping O-RU。

8.3 高级（体现深度）

  1. 高级同步丢失后，业务上会看到什么？为什么"看到"的时刻往往晚很多？

    S 面故障有明确的四个阶段，理解它能解释很多"故障为什么隔了半小时才爆发"：

    1. LOCKED：正常。
    2. HOLDOVER：源丢了，本地时钟还在撑。持续分钟到小时（有 SyncE 保住频率则长得多）。业务完全正常，看不出任何异常。
    3. 相位漂出容限：先是邻区上行底噪抬升、上行吞吐塌陷，然后 UE 大面积掉线，最后 O-RU 可能主动停发。
    4. FREERUN：小区静默。

    滞后就来自阶段 ②。同步告警响的时候业务是好的，业务出问题时同步告警已经响了几十分钟——如果这两类告警分给了两个组，就很可能被当成两个独立事件。所以：同步告警的优先级不能按"业务是否受影响"定，必须按"保持时间还剩多少"定。成熟的现场会把 HOLDOVER 直接定为高级别告警，哪怕此刻所有指标都绿。

    两个必须补上的深度点：

    LOCKED ≠ 没问题
    sync-state = LOCKED 只说明"我跟上了我的上游"，不说明"我的上游是对的"。整条时钟链一起漂时，每一级都是 LOCKED。判断链条源头健不健康要看 clockClass（6 = 锁定到 PRTC，7 = 上游 PRTC 进入保持，248 = 自由运行），而很多现场只监控了 lock-state。
    重锁时的相位跳变
    保持期间已经漂了几百纳秒，重新锁定时把相位"拽回来"的瞬间对空口是一次不连续。有些实现会选择缓慢牵引而不是直接跳变，代价是恢复时间更长。
  2. 高级前传排障为什么是 S → M → C → U 的顺序？为什么不按故障概率排？

    因为这个顺序是按"排除它的代价"和"它的故障会不会污染后续观测"排的，不是按概率排的。论概率 M 面根因最多，但它不该放第一。

    • S 面第一：它一旦有问题，后面所有观测都不可信。同步不对时，接收窗计数里的"早到/晚到"全是同步偏差的投影，你会得出完全错误的时序结论。而排除它只要读一次 sync-state + clockClass——代价接近零，收益是让后面所有数据变得可信。
    • M 面第二：根因概率最高，验证成本最低。C/U 的全部时序与格式参数都从 M 面来，验证方法只是把两端配置读出来逐字段比。关键心态是不要相信"配置应该是对的"，读出来看。
    • C 面第三、U 面第四：靠接收窗计数，不靠抓包。C 面总接收计数为 0 → 一个都没到，查 VLAN/MAC/eAxC；RX_LATE > 0 → 查优先级队列与提前量；RX_EARLY > 0 → 提前量配大了或链路变短了。
    • 网络最后：最贵、最容易被冤枉。前传故障里指向"网络/光纤/光模块"的误判特别多，而在前四步做完之前去查网络，通常结果是"网络一切正常"，然后损失两天。

    一个能体现工程判断的补充：先用免费证据把范围缩窄，再决定是否付费。证据链按代价递增是：读 o-ran-sync（一秒）→ 读接收窗计数与 SEQ_ID 丢包（已在上报）→ 比对两端 M 面配置 → 交换机队列丢包计数 → 最后才是 TAP + 硬件时间戳抓包（要停业务、要设备）。

  3. 高级前传抓包有哪些困难？该怎么做？

    三个硬约束，缺一个结论就不可信：

    速率
    25 Gbps 双向 = 6.25 GB/s。tcpdump/libpcap 走内核协议栈 + 单线程写盘必丢包，而丢掉的恰好是你要找的那个突发——抓到的"正常"是假的。13.7 Gbps 全量落盘 = 1.7 GB/s ≈ 100 GB/分钟。
    时间戳精度
    判断"早到/晚到"要和 μs 级的接收窗比，软件时间戳的误差就有几十 μs，比窗口还大，结论必然错。必须用带硬件时间戳的网卡或采集卡，而且它自己要同步到同一个时间源——否则你在拿两个不同的钟做减法。
    取包点
    交换机镜像口把双向 25G 塞进一个 25G 口，单向利用率过半就开始丢，重载时的镜像结论不可信。光分路器（TAP）+ 采集卡是唯一在满载下可信的方式。

    可行的做法：先靠"只抓头部"把数据量压下来——头部信息全在前 30 字节内，IQ 载荷对排障毫无用处：

    $ tcpdump -i ens1f0 -s 128 -w fh.pcap 'ether proto 0xaefe'
# 无 VLAN 时 eCPRI 头从第 14 字节起：ether[15]=msgType
#   ether[18:2]=pcid/rtcid(eAxC)
$ tcpdump -i ens1f0 'ether proto 0xaefe and ether[15] == 2'   # 只抓 C 面
# 带 VLAN（前传常态）：整体后移 4 字节，写死绝对偏移最稳妥
$ tcpdump -i ens1f0 'ether[16:2] == 0xaefe and ether[19] == 2'
# S 面量小，可长期抓 —— 性价比最高的一条
$ tcpdump -i ens1f0 -w ptp.pcap 'ether proto 0x88f7'

    另外 Wireshark 有 eCPRI 与 O-RAN 前传解析器，但要先在首选项里填入 eAxC 各 bitmask 的位宽，否则它切分出的 CC_ID / RU_Port_ID 是错的。

    最该表达的判断：抓包在前传的定位是"验证一个已经成型的假设"，不是"用来找线索"。因为窗口很短、代价很高（要停业务插 TAP），漫无目的地抓几乎一定白干。正确顺序是先用 O-RU 的接收窗计数把范围缩到"某一条 eAxC 的 C 面晚到"，再去抓包确认。

  4. 高级某个 O-RU 突然不发射了，M 面正常、无告警。你怎么查？

    严格按 S → M → C → U 推进，每一步都有明确的"通过/停止"判据。

    ① S 面（2 分钟）。读 o-ran-sync：sync-state 是否 LOCKED、clockClass 是否为 6（不能只看 lock-state）；读 ptp4l：rms 是否在几十 ns 内、delay 最近有没有阶跃跳变（跳变意味着路径变了，不对称补偿已失效）、freq 是否在持续单向漂。任一项异常就停在这里——不然后面的时序数据全部不可信。

    ② M 面（5 分钟），最有信息量的一次读取。读 o-ran-uplane-conf 的 tx-array-carriers，看 active（rw，你的意图）与 state（ro，实际结果）这一对：

    • active=ACTIVE 但 state 停在 DISABLED/BUSY → 问题在 O-RU 内部（同步没锁、频率不支持、射频/功放故障），不必再查 C/U 面。
    • state=READY → O-RU 认为自己已准备好发射，所以问题不是"发不出去"而是"没有内容可发"，射频通路和载波配置可以整体排除，范围一下缩到 C/U 面。

    顺便比对四项两端一致性：载波中心频率/带宽、压缩位宽与方法、eAxC 四个 bitmask 的位宽、以及 O-DU 用的延迟参数是 O-RU 上报的值还是模板默认值。

    ③ C 面（3 分钟）。拉接收窗计数。最典型的一种结果是：U 面 RX_TOTAL / RX_ON_TIME 都是满的，而 C 面总接收计数为 0。这时有一次关键推理：U 面能到、C 面到不了，而两者走同一根光纤、同一个 VLAN——所以链路不通、VLAN 没放通、MTU 不够、光模块故障全部可以排除（它们会同时影响 U 面）。剩下只有两种可能：O-DU 没发，或 C 面被发到了别的地方。

    ④ 定位到具体配置。在 O-DU 网卡上抓 C 面（量小，几秒够）确认它确实在发；然后读 o-ran-processing-element 比对 C 面与 U 面各自的 VLAN 和目的 MAC。实战中最常见的根因就是这里：开站复制了别站的配置模板，U 面的 MAC 改了、C 面的没改，于是 C 面报文被泛洪后在 O-RU 网口因目的 MAC 不匹配被直接丢弃，连计数器都不加。

    为什么全程没有告警——这是这道题真正想考的：O-RAN 前传没有"C 面没收到"这种告警，因为 O-RU 无法区分"这个 eAxC 我配了但对端没发"和"这个 eAxC 本来就还没启用"。它只提供计数器。所以不主动去读计数，这个故障可以静默存在到有人拿频谱仪去量。

    沉淀：把"C 面总接收计数 > 0"和"U 面 RX_ON_TIME 占比 > 99.9%"写进开站脚本的准出门槛，与"载波 state = READY"并列。成本是一次 NETCONF get，能在开站阶段拦掉绝大多数 C/U 配置类问题。
