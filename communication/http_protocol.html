HTTP / HTTPS 协议完全指南

HTTP 看起来只是「一行请求行加几个头」，但它三十年的演进史其实是一部和延迟死磕的历史：从每次请求都重连、到复用连接、到二进制多路复用、再到干脆换掉 TCP。这篇把每一次演进解决了什么、又留下了什么讲清楚，并给出 C++ 侧的选型与排错方法。

核心难度 ★★★☆☆ 面试必考 阅读时长 ~30 min 前置 TCP/IP 基础
报文与语义 队头阻塞 · 多路复用 TLS · 证书链 缓存 · CORS · 排错
01

报文结构与无状态

先把地基打牢

HTTP 报文就是一封标准格式的信：第一行写「我要干什么、找谁」（请求行），接下来是信封上的一堆标签（头部：寄件人、内容类型、有效期），空一行之后才是信的正文（body）。服务器回信格式一样，只是第一行换成「办成了没有」（状态码）。
── 请求 ──────────────────────────────────
POST /api/v1/inspect HTTP/1.1        ← 方法 路径 版本
Host: vision.example.com             ← ★ HTTP/1.1 强制，虚拟主机靠它区分
Content-Type: application/json
Content-Length: 42                   ← ★ 接收方靠它知道 body 到哪结束
Authorization: Bearer eyJhbGci...
Accept-Encoding: gzip, br
                                     ← ★ 空行：头部结束的唯一标志
{"image_id":"f001","threshold":0.85}

── 响应 ──────────────────────────────────
HTTP/1.1 200 OK                      ← 版本 状态码 原因短语
Content-Type: application/json
Transfer-Encoding: chunked           ← 长度未知时用分块，与 Content-Length 互斥
Cache-Control: no-store
                                     ← 空行
2a
{"defects":[],"elapsed_ms":37}
0
                                     ← chunked 以长度 0 的块结尾
无状态（stateless）：服务器不为某个客户端保留任何请求间的上下文。每个请求都必须自带全部信息，服务器处理完就忘。这是 HTTP 能横向扩展的根本原因——任何一台服务器都能处理任何一个请求，加机器就能加容量。
「无状态」不等于「无法保持登录」。状态是存在的，只是不存在协议层——它被塞进 Cookie（客户端存）或者 Session ID + 后端存储（Redis 里存）。这个设计决定了后端架构：只要状态不在进程内存里，服务就是无状态的，可以随意扩缩容和滚动重启。反过来，把 session 存进本地内存的服务只能靠会话保持（sticky session）苟住，一重启就掉线，这是很多老系统扩容困难的根源。
方法语义安全*幂等†常见误用
GET获取资源✅✅用 GET 做删除或修改——会被爬虫、预取、CDN 意外触发
POST提交，语义由服务端定❌❌把一切都做成 POST，丢掉缓存和重试能力
PUT整体替换资源❌✅当成 POST 用，做部分更新（那是 PATCH）
DELETE删除资源❌✅删第二次返回 404 而不是 204——破坏幂等语义
PATCH部分更新❌❌没定义清楚 patch 格式（JSON Patch / Merge Patch）
HEAD只要响应头✅✅忘了实现，导致某些客户端探测失败
OPTIONS查询能力 / CORS 预检✅✅被鉴权中间件拦掉，导致跨域全挂（§7）

* 安全 = 不改变服务端状态；† 幂等 = 执行 N 次和执行 1 次效果相同。幂等性直接决定了「超时后能不能自动重试」——这是网关和 SDK 设计里最实际的一条。

状态码：记分类比记数字重要

类别含义高频码
1xx信息，处理中100 Continue（大 body 前先问一句）、101（切换到 WebSocket）
2xx成功200、201 Created、204 No Content、206（断点续传）
3xx重定向301 永久 / 302 临时 / 304 Not Modified（协商缓存命中） / 307/308（保持方法不变）
4xx客户端错，重试无用400、401（没认证）、403（认证了但没权限）、404、409（冲突）、429（限流）
5xx服务端错，可能值得重试500、502（网关上游挂）、503（暂时不可用，配 Retry-After）、504（上游超时）
4xx / 5xx 的分界是重试策略的分界线：4xx 说明请求本身有问题，重试一万次还是错，应该直接失败并上报；5xx 是服务端问题，配合指数退避重试往往能成功。429 是个特例——它是 4xx 但应该重试，按 Retry-After 指示的时间等待。SDK 里把这三类分开处理，能省掉大量线上问题。
02

1.0 → 1.1：连接复用

第一次和延迟死磕

特性解决的问题说明
持久连接 keep-alive每请求一次三次握手 + 慢启动1.1 默认开启。省掉的不只是 1 个 RTT，还有 TCP 慢启动重新爬升的时间
Host 头（强制）一个 IP 只能放一个网站虚拟主机的基础。这也是后来 TLS 需要 SNI 扩展的原因——加密后服务器看不到 Host 了
分块传输 chunked动态内容长度事先不知道边生成边发，不用先缓存整个响应。流式接口的基础
范围请求 Range大文件断点续传配 206 Partial Content；多线程下载器的原理
缓存控制 Cache-Control1.0 的 Expires 依赖时钟同步见 §6
管线化 pipelining请求必须一问一答事实上已废弃：响应仍须按序返回，队头阻塞没解决，且代理实现混乱。浏览器全部默认关闭
队头阻塞（Head-of-Line Blocking）：排在前面的东西被卡住，后面明明已经就绪的也只能干等。HTTP 有两层队头阻塞——HTTP/1.1 是应用层的（一条连接上响应必须按序），TCP 是传输层的（丢一个包，后面已到达的数据也不能交给应用）。HTTP/2 解决了前者，HTTP/3 才解决后者。
HTTP/1.1 的队头阻塞像单车道收费站：前面那辆车司机在翻钱包，后面十辆车全部动不了，哪怕它们都办了 ETC。浏览器的应对是「多开几个收费站」——对同一域名并发建 6 条 TCP 连接。这治标不治本，而且连接数一多，每条连接各自慢启动，反而更占带宽。
「域名分片」（把静态资源分散到 img1.x.com、img2.x.com）是 HTTP/1.1 时代绕开 6 连接上限的经典优化。但在 HTTP/2 下它反而有害——2 的多路复用希望所有请求走一条连接以共享拥塞控制和头部压缩表，分片会强制建立多条连接，把优势抵消掉。升级到 HTTP/2 时记得把这类老优化撤掉，包括雪碧图和资源内联。
03

HTTP/2：二进制分帧

一条连接跑并发

HTTP/2 没有改变 HTTP 的语义——方法、状态码、头部含义全都一样。它改的是传输方式：把文本报文换成二进制帧，在一条 TCP 连接上并发跑多个逻辑流。

动手对比：串行 vs 多路复用

6 个请求，其中第 2 个特别慢（模拟一个卡住的接口）。HTTP/1.1 模式下后面的请求必须排队等它；HTTP/2 模式下 6 个流并发推进，慢的那个不影响其他。看右侧总耗时的差别。

点击按钮开始

四个核心机制

二进制分帧
所有内容切成带长度前缀的二进制帧（HEADERS / DATA / SETTINGS / WINDOW_UPDATE / RST_STREAM…）。相比文本解析，解析确定、不用处理各种空白与大小写歧义、不会有请求走私（request smuggling）那类攻击。
多路复用
一条连接上并发跑多个流，帧交错传输，靠 Stream ID 归位。彻底解决了 HTTP 层的队头阻塞，也让「6 连接上限」和域名分片成为历史。
HPACK 头部压缩
HTTP 头部重复率极高——每个请求都带一遍相同的 User-Agent、Cookie、Accept，可能几百字节。HPACK 用静态表（61 个预定义常见头）+ 动态表（连接内已出现过的头）+ 霍夫曼编码，把重复头压成 1–2 字节的索引。典型压缩率 80–90%，对头部远大于 body 的 API 调用效果尤其明显。
流优先级与流控
客户端可以声明「先给我 CSS 再给图片」；每个流和整个连接各有一个滑动窗口（WINDOW_UPDATE）防止快的发送方压垮慢的接收方。实践中优先级的实现质量参差不齐，HTTP/3 里做了简化。
HTTP/2 没有解决 TCP 层的队头阻塞，而且还放大了它。所有流跑在同一条 TCP 连接上，一旦某个 TCP 包丢失，内核必须等它重传到位才能把后续数据交给应用——此时全部流一起卡住。HTTP/1.1 用 6 条连接时，丢包只影响其中一条。所以在高丢包网络（弱网移动、跨国链路）下，HTTP/2 有时反而比 1.1 慢。这个问题在 TCP 层无解，必须换传输层——于是有了 QUIC。
服务端推送（Server Push）是个失败的特性。设计意图是「服务器预判客户端接下来要什么，主动推过去」，但实际上服务器无法知道客户端缓存里已经有什么，推送经常是纯浪费带宽；配置复杂、收益难以衡量。Chrome 已在 2022 年默认禁用，规范上也基本被 103 Early Hints（提前告诉客户端「你可以先去预加载这几个 URL」）取代。面试被问到时，能说清「为什么它失败了」比能说清「它是什么」更有价值。
04

HTTP/3 与 QUIC

把传输层也换掉

QUIC：Google 提出、IETF 标准化的传输协议，跑在 UDP 之上，在用户态实现了 TCP 的可靠传输、拥塞控制，并内建 TLS 1.3。HTTP/3 就是「HTTP 语义 + QUIC 传输」。
TCP 像一整条流水线传送带：中间掉了一个箱子，整条带子停下来等它补上，后面的箱子明明到了也不许卸。QUIC 像并排的多条独立传送带：某条带子掉了箱子只停那一条，其他照常卸货。代价是——传送带的调度逻辑得自己造（用户态实现），不能白用工厂现成的（内核 TCP 栈）。
能力TCP + TLS 1.3（HTTP/2）QUIC（HTTP/3）
建连 RTTTCP 1 RTT + TLS 1 RTT = 2 RTT1 RTT；重连 0-RTT（带上次的票据直接发数据）
队头阻塞TCP 层仍有：丢一个包卡住全部流彻底消除：每个流独立重传，互不影响
连接标识四元组——换网络 = 断线重连Connection ID——Wi-Fi 切 5G 连接不断
加密范围TCP 头明文（序号、标志位可被中间设备读改）几乎全部加密，中间设备无法窥探或篡改
实现位置内核，成熟、有硬件卸载用户态，可快速迭代，但 CPU 开销更高
协议僵化中间盒子（NAT、防火墙）对 TCP 有各种假设，新特性推不动加密使中间盒子无法干预，可持续演进
部署阻力无部分企业网络封禁 UDP；必须保留 HTTP/2 回退
连接迁移是被低估的一项
手机从 Wi-Fi 切到 5G，IP 变了，TCP 四元组失效，所有连接必须重建——视频卡一下、上传中断、要重新握手和认证。QUIC 用与 IP 无关的 Connection ID 标识连接，换网络时连接原样存活。对移动端体验的提升比多路复用还明显。
0-RTT 的重放风险
0-RTT 数据是用上次会话的密钥加密的，没有新鲜性保证——攻击者录下这段数据可以重放。所以 0-RTT 只能用于幂等请求（GET），不能用来提交订单或转账。协议层面允许，但应用层必须自己把关，服务端也应对 0-RTT 请求做方法白名单。
作为服务端工程师，现在该怎么做？HTTP/3 在 CDN 和网关层（Nginx 1.25+、Cloudflare、各云厂商 LB）打开一个开关就能用，源站到网关之间继续用 HTTP/1.1 或 2 完全没问题——收益主要在「最后一公里」的弱网和移动场景。自己用 C++ 实现 QUIC 客户端要谨慎：可用的库有 quiche（Cloudflare，Rust + C API）、msquic（微软）、nghttp3+ngtcp2，都比 TCP 客户端复杂一个量级，除非确有需求否则不值得。
05

HTTPS 与证书链

加密之外，更重要的是身份

HTTPS = HTTP over TLS。它提供三件事：机密性（内容加密）、完整性（篡改可检测）、身份认证（你连的确实是那个域名）。最容易被忽略的恰恰是第三件——只加密不验身份的 HTTPS 毫无意义，中间人可以用自己的密钥和你建立一个「加密良好」的连接。

证书链像身份证的信任传递：你不认识这个人，但你认识发证机关（根 CA），发证机关的公章能验证「省厅」（中间 CA）的资格，省厅的章又能验证这张身份证。根 CA 的公钥是预装在你操作系统/浏览器里的——这是整条信任链的起点，也是它唯一的假设。
浏览器报错真实原因怎么查
ERR_CERT_AUTHORITY_INVALID自签证书，或服务器没发中间证书openssl s_client -connect host:443 -showcerts 看返回了几张证书
ERR_CERT_COMMON_NAME_INVALID域名不在证书的 SAN 列表里现代客户端只看 SAN 不看 CN，老证书只填 CN 会失败
ERR_CERT_DATE_INVALID过期，或客户端时钟错了嵌入式设备没有 RTC、开机时间是 1970，这个很常见
握手直接失败无详细信息协议版本或密码套件不匹配老设备只支持 TLS 1.0/1.1，服务端已禁用
curl 能通、程序不通程序用的 CA 包路径不对容器里常见——ca-certificates 没装
永远不要用「忽略证书错误」来解决问题。curl -k、verify=False、ignoreSslErrors()、InsecureSkipVerify: true——这些一旦写进代码就基本不会被删掉，而且它关掉的是身份认证，中间人可以完整地劫持流量并且你毫无察觉，加密变成了自我安慰。正确做法是把自签 CA 加进信任库（SSL_CTX_load_verify_locations / 系统 CA 目录 / 容器里 COPY ca.crt /usr/local/share/ca-certificates/），一次配置永久解决。
TLS 的密钥交换细节、前向保密、会话复用、双向认证（mTLS）、证书吊销（CRL/OCSP/OCSP Stapling）等内容，在 TLS / SSH / 证书体系里有完整展开，这里不重复。
06

缓存机制

最便宜的性能优化

指令含义典型用法
max-age=31536000, immutable一年内直接用本地副本，且保证不会变带内容哈希的静态资源（app.a1b2c3.js）
no-cache可以存，但每次用前必须去问HTML 入口页——内容会变，但大多数时候没变，靠 304 省流量
no-store完全不许存，任何地方都不许含敏感信息的响应（个人数据、支付页）
private / public只有浏览器能存 / CDN 也能存带用户身份的响应必须 private，否则 CDN 会把 A 的数据发给 B
s-maxage=60给共享缓存（CDN）单独设的时间CDN 存 60 秒，浏览器按 max-age 走
stale-while-revalidate=30过期后 30 秒内先返回旧的，后台悄悄更新消除缓存过期时的延迟毛刺，性价比很高
ETag / If-None-Match内容指纹比对比 Last-Modified 精确（后者只到秒，且内容没变但重新生成时会误判）
最经典的一套配置：HTML 入口页 Cache-Control: no-cache（每次校验，靠 ETag 拿 304）；带内容哈希的 JS/CSS/图片 max-age=31536000, immutable（永不过期，改了内容文件名就变了）。这套组合让「发新版本立刻生效」和「静态资源零请求」同时成立——因为版本更新会改变 HTML 里引用的文件名，而 HTML 本身每次都校验。这是所有现代前端构建工具默认产出的模式。
CDN 缓存了带用户身份的响应是一类严重的生产事故——A 用户看到了 B 用户的个人信息。触发条件很简单：响应没设 private/no-store，且 URL 不含用户标识（身份在 Cookie 或 Authorization 头里）。CDN 只按 URL 做键，自然就串了。规则：只要响应内容随身份变化，必须显式 Cache-Control: private 或 no-store，并配合 Vary: Authorization。这条建议写进网关的默认响应头里，而不是指望每个业务开发记得。

Cookie · CORS · 安全头

浏览器语境下的三件事

Cookie 的四个关键属性

Set-Cookie: sid=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
             │           │         │       │
             │           │         │       └─ 跨站请求时是否携带（防 CSRF）
             │           │         └───────── 只在 HTTPS 下发送
             │           └─────────────────── ★ JS 读不到 —— XSS 也偷不走
             └─────────────────────────────── 会话标识
属性作用不设的后果
HttpOnly禁止 JS 通过 document.cookie 访问一个 XSS 就能偷走会话，直接冒充用户
Secure只在 HTTPS 连接上发送混合内容或降级攻击下明文泄露
SameSiteStrict 完全不跨站发 / Lax（现代浏览器默认）顶层导航的 GET 才发 / None 都发但必须配 SecureCSRF：恶意站点让你的浏览器带着 Cookie 去发请求
Domain控制发送范围设成父域会泄漏到所有子域，包括不受控的那些

CORS：不是服务器在限制你，是浏览器

同源策略：浏览器的安全基石——来自 a.com 的脚本默认不能读取 b.com 的响应内容。CORS 是服务器主动放行的机制：通过响应头告诉浏览器「我允许这个源读我」。
最重要的一点认知：CORS 限制的是「浏览器里的 JS 能不能读到响应」，不是「请求能不能到达服务器」。对于简单请求，请求已经发出去了，服务器也已经执行了——只是浏览器拦住不给 JS 看结果。所以 CORS 不是安全机制，不能拿它防任何东西；用 curl、Postman、任何非浏览器客户端都完全不受 CORS 影响。真正的防护是鉴权和 CSRF Token。

排查 CORS 的三个高频原因
① 鉴权中间件把 OPTIONS 请求也拦了——预检不带凭证，返回 401，浏览器直接报 CORS 失败（错误信息很有误导性）。② Allow-Credentials: true 时 Allow-Origin 不能是 *，必须回显具体来源。③ 自定义响应头默认不暴露给 JS，要用 Access-Control-Expose-Headers 显式列出（分页总数、请求 ID 这类头经常栽在这）。

面试题集（12 道）

按难度分层，先自测再对照

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础HTTP 报文由哪几部分组成？接收方怎么知道 body 到哪里结束？

    起始行 + 头部 + 空行 + body。请求的起始行是「方法 路径 版本」，响应是「版本 状态码 原因短语」。空行是头部结束的唯一标志。

    判断 body 边界有三种方式，按优先级：

    • Transfer-Encoding: chunked——分块传输，每块前有长度，以长度为 0 的块结尾。
    • Content-Length: N——固定长度，读 N 字节。
    • 都没有——读到连接关闭为止（HTTP/1.0 的做法，无法区分「正常结束」和「连接断了」）。
    安全相关
    两者不能同时出现。如果同时出现且前后端处理优先级不一致，就产生请求走私（HTTP Request Smuggling）——攻击者可以把一个请求「藏」在另一个请求的 body 里绕过前置的安全检查。HTTP/2 的二进制分帧从根本上消除了这类攻击。
  2. 基础GET 和 POST 有什么区别？

    本质区别在语义，不在技术细节：GET 是安全的（不改变服务端状态）且幂等的，POST 两者都不是。

    由这个语义差异派生出的实际后果：

    • GET 响应可以被缓存（浏览器、CDN、代理），POST 默认不缓存。
    • GET 可以被安全地自动重试，POST 超时后不敢重试（可能重复下单）。
    • GET 会被爬虫、浏览器预取、链接预加载意外触发——所以「用 GET 做删除」是经典事故。
    • GET 参数在 URL 里，会进浏览器历史、服务器访问日志、Referer 头，不能放敏感信息。
    常见的错误说法
    「GET 有长度限制 2048 字节」——规范没有这个限制，是浏览器和服务器的实现限制（各家不同）。「GET 不安全因为参数可见」——POST body 同样是明文，抓包一样能看，安全靠的是 HTTPS 而不是方法。
  3. 基础301 和 302、403 和 404、502 和 504 分别有什么区别？
    301 vs 302
    301 永久重定向——浏览器会缓存这个跳转，下次直接去新地址，搜索引擎会转移权重。误发 301 很难挽回，用户浏览器里存着，你改回来他也不请求你了。302 临时，每次都会先来问。不确定就用 302。另外 307/308 是它们的「严格版」——保证重定向后不改变请求方法（301/302 历史上会把 POST 变成 GET）。
    403 vs 404
    401 = 你没证明你是谁（该带 token 没带，或 token 过期）；403 = 我知道你是谁，但你没这个权限；404 = 资源不存在。安全实践上，有时会故意把 403 报成 404——避免泄露「这个资源存在」这一信息。
    502 vs 504
    都发生在网关/代理上。502 Bad Gateway = 上游给了无效响应或直接拒绝连接（后端挂了、端口不通、返回了乱七八糟的东西）；504 Gateway Timeout = 上游连上了但在超时时间内没回复（后端卡住了、慢查询、死锁）。502 查后端存活，504 查后端性能——这个分工能省一半排查时间。
  4. 基础HTTP 和 HTTPS 的区别是什么？HTTPS 慢在哪？

    HTTPS = HTTP over TLS，多提供三样东西：机密性（加密）、完整性（篡改可检测）、身份认证（确认对方是那个域名）。默认端口 443（HTTP 是 80）。

    慢在哪：

    • 握手 RTT：TLS 1.2 需要额外 2 个 RTT，TLS 1.3 降到 1 个，会话复用可以 0-RTT。这是主要开销。
    • 非对称加密的 CPU 开销：只在握手时用一次。现代 CPU 有 AES-NI 指令，对称加密阶段的开销可以忽略。
    • 证书链验证：可能触发 OCSP 查询（额外网络请求），用 OCSP Stapling 可以消除。
    结论
    「HTTPS 很慢」是过时的印象。开启 TLS 1.3 + 会话复用 + HTTP/2 之后，HTTPS 往往比明文 HTTP/1.1 还快——因为多路复用带来的收益远大于握手成本。而且很多性能特性（HTTP/2、HTTP/3、Brotli 的浏览器支持）实际上只在 HTTPS 下可用。

9.2 中级（区分熟练度）

  1. 中级什么是队头阻塞？HTTP/1.1、HTTP/2、HTTP/3 各自处于什么状态？

    队头阻塞：排在前面的被卡住，后面已就绪的也只能等。HTTP 场景下有两层：

    HTTP/1.1
    两层都有。应用层：一条连接上响应必须按请求顺序返回，前一个慢后面全等（管线化想解决但失败了）。传输层：TCP 本身的按序交付。浏览器的对策是对同域名开 6 条连接，治标不治本。
    HTTP/2
    解决了应用层，传输层反而更严重。二进制分帧 + 多路复用让多个流在一条连接上并发，应用层不再排队。但所有流跑在同一条 TCP 连接上，丢一个包，内核等重传期间全部流一起卡住——比 HTTP/1.1 的 6 条连接（丢包只影响一条）影响面更大。所以弱网下 HTTP/2 有时反而更慢。
    HTTP/3
    两层都解决。QUIC 在 UDP 上自己实现可靠传输，每个流独立管理序号和重传，一个流丢包不影响其他流。这是必须换掉 TCP 的根本原因——TCP 的按序交付语义在内核里，改不了。
  2. 中级HTTP/2 相比 1.1 做了哪些改进？服务端推送为什么被废弃了？

    四项核心改进：

    • 二进制分帧——解析确定，无文本歧义，顺带消灭了请求走私类攻击。
    • 多路复用——一条连接并发多个流，消除应用层队头阻塞，也让域名分片、雪碧图这些老优化过时。
    • HPACK 头部压缩——静态表（61 个常见头）+ 动态表（本连接出现过的）+ 霍夫曼编码，重复头压成 1–2 字节索引，典型压缩率 80–90%。对头部比 body 还大的 API 调用收益巨大。
    • 流优先级与流控——可以声明先要 CSS 后要图片；每流和整连接各有滑动窗口。
    服务端推送为什么失败
    核心问题是服务器不知道客户端缓存里已经有什么。推送一个用户早就缓存了的 CSS 纯属浪费带宽，而这种情况占多数。加上配置复杂、与缓存交互混乱、收益难以量化，Chrome 在 2022 年默认禁用。替代方案是 103 Early Hints——服务器在正式响应前先回一个 103，告诉客户端「你可以先去预加载这几个 URL」，由客户端决定要不要拿（它知道自己缓存里有什么）。把决策权交回客户端，这是设计上的关键修正。
  3. 中级强缓存和协商缓存有什么区别？一套完整的缓存策略该怎么配？

    强缓存：本地副本在有效期内（Cache-Control: max-age），一次网络请求都不发，直接用。最快。

    协商缓存：本地有副本但不确定是否过期，发一个条件请求（If-None-Match: "etag" 或 If-Modified-Since）去问服务器。没变返回 304 Not Modified（无 body），变了返回 200 + 新内容。省的是流量，不省 RTT。

    经典配置
    HTML 入口页：Cache-Control: no-cache + ETag——每次都校验，大多数时候拿 304。带内容哈希的静态资源（app.a1b2c3.js）：max-age=31536000, immutable——永不过期。
    这套组合让「发版立刻生效」和「静态资源零请求」同时成立：版本更新会改变 HTML 里引用的文件名，而 HTML 本身每次都校验。
    加分项
    ETag 比 Last-Modified 精确（后者只到秒，且内容没变但文件重新生成时会误判）。stale-while-revalidate=30 让过期后 30 秒内先返回旧内容、后台悄悄更新，消除缓存过期瞬间的延迟毛刺，性价比很高。共享缓存用 s-maxage 单独控制 CDN。
  4. 中级解释 CORS 的完整流程。为什么有时会多出一个 OPTIONS 请求？

    浏览器的同源策略默认不允许页面脚本读取跨源响应。CORS 是服务器主动放行的机制。

    简单请求（GET/HEAD/POST + 有限的几个头 + Content-Type 是 text/plain/form-urlencoded/multipart）：浏览器直接发，然后检查响应里的 Access-Control-Allow-Origin 决定是否把结果交给 JS。

    非简单请求（PUT/DELETE、自定义头如 Authorization、Content-Type: application/json）：浏览器先自动发一个 OPTIONS 预检，问服务器「我能用 PUT 带 authorization 头吗」，服务器同意了才发真实请求。这就是那个多出来的 OPTIONS。用 Access-Control-Max-Age 可以缓存预检结果，避免每次都问。

    最关键的认知
    CORS 限制的是「JS 能不能读到响应」，不是「请求能不能到服务器」。简单请求早就发出去了，服务器也已经执行了，只是浏览器不给 JS 看结果。所以 CORS 不是安全机制——curl、Postman、任何非浏览器客户端完全不受影响。防护要靠鉴权和 CSRF Token。
    三个高频坑
    ① 鉴权中间件把 OPTIONS 也拦了（预检不带凭证 → 401 → 浏览器报 CORS 错误，信息很误导）；② Allow-Credentials: true 时 Allow-Origin 不能是 *；③ 自定义响应头要用 Expose-Headers 才能被 JS 读到。

9.3 高级（体现深度）

  1. 高级QUIC 为什么选择建在 UDP 上而不是直接做一个新的传输层协议？

    技术上完全可以设计一个新的 IP 协议号，但它永远部署不上去——这是协议僵化（ossification）问题。

    中间盒子的阻碍
    互联网上遍布 NAT、防火墙、负载均衡、运营商设备，它们只认识 TCP（6）和 UDP（17），其他协议号的包会被直接丢弃。SCTP 就是活生生的例子：技术优秀、标准化多年，但在公网上基本用不了。UDP 是唯一能穿透现有网络的「通用容器」。
    用户态实现的价值
    TCP 在内核里，改一次要等操作系统升级，服务器还好，客户端要等用户升级手机系统，周期以年计。QUIC 在用户态，跟着应用/浏览器发版就能更新——Chrome 可以两周迭代一次拥塞控制算法。这个迭代速度差异是决定性的。
    加密作为「防僵化」手段
    QUIC 把包头也加密了，中间设备读不懂也就改不了，无法基于内部字段做任何假设。这是刻意的设计——TCP 之所以僵化，正是因为中间盒子对它的每个字段都建立了依赖（比如很多设备会重写窗口大小、丢弃带未知选项的包）。加密从根本上保证了 QUIC 未来还能继续演进。

    代价：UDP 在用户态收发，CPU 开销明显高于内核 TCP（缺少 GSO/GRO 等卸载优化，虽然在逐步补上）；部分企业网络封禁 UDP，必须保留 HTTP/2 回退路径。

  2. 高级HPACK 是怎么工作的？它带来了什么安全问题？

    三层机制：静态表（61 个预定义的常见头，如 :method: GET，直接用索引 2 表示）；动态表（本连接内出现过的头，双方各维护一份同步的表，后续出现只发索引）；霍夫曼编码（表里没有的字面值也压一遍）。效果是把几百字节的重复头压到 1–2 字节。

    CRIME / BREACH 类攻击
    压缩率泄露了内容的相似性：如果攻击者能让浏览器发出包含自己可控内容的请求，通过观察压缩后的长度变化，可以逐字节猜出同一请求里的 Cookie。HPACK 的对策：不像通用 gzip 那样跨字段压缩，而是用「索引表 + 逐字段霍夫曼」，并允许把敏感头标记为「永不索引」（never-indexed literal），这样它不进动态表也不参与共享压缩上下文。
    状态同步的脆弱性
    动态表是连接级的共享状态，收发双方必须严格同步。一旦不一致，后续所有头部都解错，只能断开连接。这也意味着代理不能简单地转发帧——它必须完整解压再重新压缩，这是 HTTP/2 代理比 HTTP/1.1 代理复杂得多的原因之一。
    HTTP/3 的 QPACK
    HTTP/3 不能直接用 HPACK：QUIC 的流之间没有全局顺序，而动态表更新必须按序才能保持同步。QPACK 的解法是把表更新放在单独的单向流上，并允许请求引用「已确认的表项」，在压缩率和队头阻塞之间提供可调的权衡。
  3. 高级一个 HTTPS 接口偶发 3 秒延迟，你怎么定位？

    第一步永远是把耗时分段，否则就是瞎猜：

    curl -o /dev/null -s -w \
 "dns:%{time_namelookup} tcp:%{time_connect} tls:%{time_appconnect} \
ttfb:%{time_starttransfer} total:%{time_total}\n" https://api.x.com/v1/y

    五段各自指向完全不同的问题：

    DNS 慢
    解析服务器不可达导致超时重试（典型 5 秒整）、没有本地缓存、容器里 ndots 配置导致多次无谓查询。「偶发恰好 5 秒」几乎一定是 DNS 超时重试。
    TCP 连接慢
    后端 accept 队列满（ss -ltn 看 Send-Q）、SYN 被丢弃后重传（初始重传超时 1 秒，指数退避 → 1s / 3s / 7s 这类整数延迟是 SYN 重传的指纹）、中间有防火墙限速。
    TLS 慢且每次都慢
    连接没有复用——每次请求都重新握手。检查客户端是否复用 handle/连接池；也可能是 OCSP 查询阻塞（开 OCSP Stapling 解决）。
    TTFB 慢
    后端处理慢。这时候问题已经不在 HTTP 层，转去看服务端的链路追踪、慢查询日志、GC 日志。
    TTFB 快但 total 慢
    响应体传输慢：内容太大没压缩、带宽受限、或者服务端是流式输出而中间某段生成得慢。
    偶发问题的额外手段
    单次 curl 未必复现。在客户端把这五段时间打进日志/指标，看 p99 落在哪一段，比蹲守复现有效得多。抓包时用 tcpdump -w 持续录、环形缓冲，出问题后回溯；HTTPS 明文可以靠 SSLKEYLOGFILE 导出密钥让 Wireshark 解密。还要排除连接池打满导致请求排队——这种排队时间在 curl 单发时完全看不到，只有在应用侧埋点才能发现。
  4. 高级设计一个对外的 HTTP API，你会在协议层面做哪些约定？
    幂等与重试
    明确每个接口的幂等性。非幂等的写接口必须支持幂等键（客户端生成 Idempotency-Key 头，服务端在一定窗口内去重）——否则客户端超时后不敢重试，网络抖动就变成业务失败。这是支付类 API 的标配。
    版本与演进
    URL 版本（/v1/）最直观，也可以用 Accept: application/vnd.x.v2+json。更重要的是约定「什么改动算兼容」：加字段兼容、删字段不兼容、改字段含义最危险。客户端必须忽略未知字段，这条要写进 SDK 和文档。
    错误格式统一
    HTTP 状态码表达大类，body 里给机器可读的错误码 + 人可读的消息 + 请求 ID。别让客户端去解析错误消息文本——那会让你的错误文案变成 API 契约，再也改不了。
    限流与背压
    429 + Retry-After + X-RateLimit-Remaining。明确告诉客户端什么时候可以再来，比直接拒绝更能避免雪崩式重试。服务端过载时返回 503 + Retry-After 而不是让请求排队到超时。
    缓存语义
    读接口给 ETag，支持 If-None-Match；任何带用户身份的响应必须 Cache-Control: private，否则 CDN 会把 A 的数据发给 B——这是真实发生过的严重事故。
    分页与超时
    大结果集用游标分页而不是 offset（offset 在数据变动时会漏/重，深翻页还会打爆数据库）。文档里明确服务端超时时间，让客户端的超时设置能对齐——客户端超时短于服务端会导致「客户端认为失败但服务端已执行」。
    可观测性
    每个响应回请求 ID（并在日志里可检索），支持 traceparent 头透传。用户报障时能凭一个 ID 拉出完整链路，这一项的排查效率提升比前面所有加起来还大。
