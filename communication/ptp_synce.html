01

为什么无线要"对表"

不同步会怎样

本篇讲的是时间与频率同步本身的原理与工程：为什么需要、PTP 怎么算出时间、SyncE 补什么、电信剖面怎么选、现场怎么测怎么排障。前传网络里"时钟源放在哪一级"的拓扑选型（LLS-C1 ~ C4）属于部署形态，在 O-RAN 四平面的 Sync Plane 一节；分段承载见 前传/中传/回传，报文格式见 eCPRI 深入。

"时钟不同步"在有线和无线里，后果完全不是一个量级。点到点的有线链路上，两端快慢不一致只是让收端缓冲区慢慢填满或抽空，隔一阵发生一次滑码——局部、可观测、可恢复，上层重传一下就过去了。

无线不一样。空口是共享介质，靠"谁在什么时刻用哪段频率"这套约定分开几十个基站和成千上万个终端，而约定成立的前提就是所有参与者对"现在几点"看法一致。某个基站时间偏了，不是"自己出错"，而是把信号发进了别人正在接收的时间窗。这种干扰有三个很坏的性质：持续（不是偶发丢包）、单向（肇事者自己看不到）、重传修不好（重传的报文照样撞）。

不同步的表现物理原因需要哪种同步谁是受害者
邻区上行底噪抬升、上行吞吐塌陷、UE 反复功率冲顶TDD 上下行时隙边界错位，本站下行落进邻站的上行接收窗相位邻站（本站各项指标全绿）
波束指向偏、MIMO 秩上不去、增益不达标同一载波多个天线口之间的时间偏差 → 相位偏差 → 波束合成错误相位（更严）本站
载波聚合建立失败或吞吐不达标载波之间时间对齐误差（TAE）超容限，UE 的接收窗对不齐相位（更严）本站的 CA 用户
载频偏移、UE 解调误码上升、切换成功率下降本地振荡器频率不准，发射载频偏离标称值频率本站
定位精度差、时间戳类业务对不上设备之间不知道共同的绝对时刻时间业务层

TDD 为什么必须相位同步：3 μs 是从保护间隔里抠出来的

TDD（时分双工）上下行共用同一段频率，靠时间切开。一个典型的 5G TDD 时隙图样（如 DDDSU）里，下行与上行时隙之间夹着一段保护间隔 GP（Guard Period）。GP 不是白留的空档，它要同时覆盖三件事——而其中只有一件由同步网络决定：

为什么后果这么重？功率不对称：宏站下行是几十瓦（46 dBm 量级），要接收的 UE 上行到达接收机时只有 −110 dBm 量级。哪怕 A、B 隔着几公里、路损上百 dB，A 漏过来的信号仍远高于 B 期望收到的有用信号。结果不是"略有下降"，而是 B 站在那几个符号里彻底聋掉。

TDD 同步问题最刁钻的地方是肇事者与受害者分离：跑偏的是 A 站，而 A 站的 KPI、告警、同步状态可能全绿（它锁在了一个错误的源上，自认为锁得很好）；底噪抬升、上行吞吐塌陷的是 B 站。所以看到"一片区域底噪同时抬升，但每个站自己都没告警"，就该去查那片区域周边的站，而不是查报障的站。
🎻 类比：一支交响乐团，每个乐手都要跟着同一个指挥的节拍。频率同步=大家节拍快慢一致（每小节都是 4 拍、每拍一样长）；相位同步=大家在同一拍子的同一瞬间落弓；时间同步=大家还知道"现在是第 137 小节"。只快慢一致但落弓错开半拍，听起来比乱拉还难受——这就是频率同步了但相位没同步的 TDD 网络。
02

三种同步：频率 / 相位 / 时间

先分清概念

"同步"这个词被用得太随意，很多讨论从一开始就在鸡同鸭讲。它其实指三件严格递进的事——后一个必然包含前一个，反之不成立。把这张图看懂，选型时就不会既欠设计又过度设计：

频率同步 Frequency Synchronization（也叫同频 syntonization）：两个时钟"走得一样快"——单位时间的长度相同，频率之比恒等于 1。不要求它们指向同一个刻度。物理上对应的是本地振荡器的频率准确度，指标单位是 ppb（10−9）或 ppm。
相位同步 Phase Synchronization：走得一样快，而且秒边沿（1PPS 的上升沿）对齐——同时"跳秒"，但可以对"现在是第几秒"有不同看法。指标单位是时间（ns / μs）。
时间同步 Time Synchronization：在相位同步之上再加共同的时间刻度与纪元，都知道"现在是 UTC 的某年某月某日某时某分某秒"。需要额外传 currentUtcOffset（TAI 与 UTC 的闰秒差）与时标标识。
递进关系是时间 ⊃ 相位 ⊃ 频率，反过来不成立：相位对齐的两个钟必然频率一致（否则边沿会越走越开），但频率一致的两个钟可以永远差着固定的 37 ms 而毫不自知。

频率误差怎么变成时间误差：一个必须会算的换算

三者不是孤立的：频率误差在时间上积分，就是相位/时间误差。这是理解 holdover、理解"SyncE 为什么能帮 PTP"的算术基础，全篇会反复用到。

# 定义：频率偏差 y = (f_local − f_ref) / f_ref  （无量纲，常写成 ppb = 10^-9）
# 恒定频率偏差下，累积的时间误差：

    ΔT(t) = y × t

# 代几个数（这些数值值得背下来）：
y = 1 ppb  (1×10^-9)  → 1 秒累积 1 ns   → 累积到 1.5 μs 需要  1500 s ≈ 25 分钟
y = 10 ppb (1×10^-8)  → 1 秒累积 10 ns  → 累积到 1.5 μs 需要   150 s ≈ 2.5 分钟
y = 50 ppb            → 累积到 1.5 μs 需要 30 s
y = 1 ppm  (1×10^-6)  → 累积到 1.5 μs 需要 1.5 秒   # 普通 TCXO 的量级

# 如果频率本身还在漂（老化率 D，单位"每天多少"），从零偏差起算：
    ΔT(t) = ½ × (D / 86400) × t²

# 结论一：任何"只有频率同步"的方案，相位误差都会线性发散。
#         频率同步永远替代不了相位同步。
# 结论二：反过来，频率越准，相位漂得越慢 —— 这就是 SyncE 对
#         PTP holdover 的全部价值（见第 5 章）。

3GPP 对基站载频准确度的要求也落在这个尺度上：宏基站（Wide Area BS）量级为 ±0.05 ppm，本地/中程与家庭基站逐级放宽（数值以 TS 38.104 所用版本为准）。这就是为什么 FDD 网络只要频率同步就能跑：它的同步需求只来自载频准确度和切换，不涉及时隙边界对齐。

表中 TAE 与相位精度数值是 3GPP TS 38.104 / TS 38.133 的量级要求，用于建立数量级直觉；具体条款号与限值以所用版本为准。前传场景下这些指标怎么进一步分解到每一跳，见 O-RAN 四平面的 Sync Plane 一节与本篇第 6 章。

一个很实用的判据："这个业务需要知道『现在几点』吗？"不需要、只要步调一致 → 频率（FDD、SDH）；需要"同时开始"但不关心几点 → 相位（TDD 时隙边界）；需要跨系统对时间戳或算绝对到达时刻 → 时间（定位、TSN、日志取证）。每往上走一档，成本与对网络的要求都是数量级增加，所以不要习惯性地全都上时间同步。
03

SyncE：物理层频率同步

从以太网时钟提频率

SyncE（Synchronous Ethernet，ITU-T G.8261 / G.8262 / G.8264）让频率信息沿以太网物理层逐跳传递：每台设备从收到的以太网信号里恢复出发送方的时钟，用它驱动自己的发送时钟，一级级传下去，最终都溯源到同一个高精度基准。

普通以太网为什么天生不同步

标准以太网是异步的：每个网口用板上那颗晶振产生发送时钟，标称 125 MHz（千兆）但允许 ±100 ppm。收端的 CDR 虽然从信号里提取了发送方的时钟，却只拿它采样、不用它驱动本端发送；两端速率差靠帧间隙（IPG）伸缩吸收。对数据传输完全够用，代价是链路上没有任何频率信息能被下游继承——SyncE 的全部改动就是把这条路打通。

SyncE 的本质：把网口的发送时钟从「本地自由振荡的晶振」改成「由某个选定的参考源（可以是某个收端口恢复出的时钟）驱动的 DPLL 输出」。数据面一个比特都没改，改的是时钟从哪来。所以它对上层完全透明，也完全不受排队、拥塞、负载影响——这是它相对 PTP 最大的优势。

ESMC 与 QL：选源和防环靠它

光有物理层时钟还不够，还剩两个问题：设备有多个上联口，该选哪个；以及万一 A 跟着 B、B 又跟着 A，就成了时钟环路。ESMC（Ethernet Synchronization Messaging Channel）同时解决这两件事——它用以太网 Slow Protocol（和 LACP 同一族，组播 01-80-C2-00-00-02，EtherType 0x8809）在每个 SyncE 端口周期通告一个 QL（Quality Level）：「顺着我这个口往上追，最终能追到什么等级的基准」。

QL（SSM 码，Option I / 欧洲体系）含义频率准确度量级典型来源
QL-PRC（Primary Reference Clock）一级基准时钟1×10−11铯钟；或 PRTC（GNSS 驯服）
QL-SSU-A转接局同步供给单元优于 EEC局端 SSU / BITS 设备
QL-SSU-B本地局同步供给单元介于两者之间下级 SSU
QL-EEC1（Ethernet Equipment Clock）普通网元自身的时钟±4.6 ppm（自由振荡上限）交换机/路由器板载 DPLL
QL-DNU（Do Not Use）不要用我这一路—防环专用，见下

SSM 码值在 ITU-T G.781 的不同 Option（Option I 欧洲 / Option II 北美 / Option III）下编码与名称不同（北美体系里对应的是 PRS / ST2 / ST3E 等）。同一张网必须全程使用同一个 Option，混用会导致等级被误解释——这是跨厂商组网的经典坑。

回发 DNU 是配置项，不是自动行为。它经常在多厂商拼接或人工改配后被漏掉，而漏掉之后没有任何告警——环里的两台设备都认为自己锁在 PRC 上。所以割接后要专门核对一遍「选中口的 TX QL 是不是 DNU」，别等业务出问题再回头找。

EEC：网元自己的时钟质量

沿途每台设备的 DPLL 都不理想，它的带宽、抖动传递与保持能力被 ITU-T G.8262 定义为 EEC（Ethernet Equipment Clock），更严的相位场景还有 G.8262.1 的 eEEC。下图并排放着两件最要紧的事：QL 等级的高低顺序，以及为什么串接跳数不能无限加。

04

PTP / IEEE 1588：时间 / 相位

用报文交换算出精确时刻

PTP（Precision Time Protocol，IEEE 1588）通过主从之间交换带硬件时间戳的报文，同时解出「我和主时钟差多少」和「这条链路单向要走多久」，从而达到亚微秒甚至纳秒级的时间 / 相位同步。

公式推导：两个未知数，两个方程

从时钟面对两个未知量：偏移 θ 和单向传播时延 d。一次往返恰好给出两个方程——但「能解」是有前提的，那个前提比公式本身更重要。

# 四个时间戳（t1、t4 用主时钟的表；t2、t3 用从时钟的表）
  t1 = Master 发出 Sync 的时刻          （主时钟读数）
  t2 = Slave  收到 Sync 的时刻          （从时钟读数）
  t3 = Slave  发出 Delay_Req 的时刻     （从时钟读数）
  t4 = Master 收到 Delay_Req 的时刻     （主时钟读数）

# 设：θ = 从钟 − 主钟（从钟快则 θ > 0）
#     d_ms = 主→从 单向时延    d_sm = 从→主 单向时延

  t2 = t1 + d_ms + θ        →   t2 − t1 = d_ms + θ      … ①
  t4 = t3 + d_sm − θ        →   t4 − t3 = d_sm − θ      … ②

# 两个方程、三个未知数（θ、d_ms、d_sm）—— 解不出来。
# 必须再加一个假设，这就是 PTP 的命门：

  ★ 对称性假设： d_ms = d_sm = d

# 有了它，① + ② 与 ① − ② 分别给出：

  d = [ (t2 − t1) + (t4 − t3) ] / 2        # 单向时延
  θ = [ (t2 − t1) − (t4 − t3) ] / 2        # 时钟偏移

# 从钟把自己的时间减去 θ，就对齐了主钟。
对称性假设是 PTP 全部误差的来源。设真实不对称量 d_ms − d_sm = Δ，代入上式直接得到算出的 θ 偏离真值 Δ/2——1 μs 的不对称换来 0.5 μs 的固定误差，而且多测几次、做平均、加滤波都消不掉：它是系统性偏差，不是噪声。PTP 的滤波算法能对付抖动，对付不了不对称（§7.1 有图）。

报文族与两种时延测量机制

报文类别作用备注
SyncEvent（要打戳）主→从，产生 t1 / t2周期发送，速率可配（典型 16/s）
Follow_UpGeneral携带精确的 t1仅 two-step 模式需要
Delay_ReqEvent从→主，产生 t3 / t4E2E 机制
Delay_RespGeneral把 t4 告诉从时钟E2E 机制
Pdelay_Req / Pdelay_Resp（+ _Follow_Up）Event / General测相邻两跳之间的链路时延P2P 机制，配合 P2P TC 使用

Management / SignalingGeneral管理查询、单播协商pmc 工具走的就是它

E2E（端到端）时延机制

从时钟直接和主时钟做 Delay_Req / Delay_Resp，测的是整条路径的时延。中间设备如果是 TC，就把自己的驻留时间累加进修正域。适合链状拓扑，是电信网络的主流。

P2P（点到点）时延机制

每一跳各自用 Pdelay 测自己到邻居的链路时延，逐段累加。拓扑变化时收敛更快（换路径不用重测全程），常见于工业以太网与 802.1AS。

E2E 与 P2P 不能在同一个 PTP 域里混用——它们对中间设备的行为要求不同。组网前必须统一，这是多厂商互通时的常见踩坑点。

one-step 与 two-step

问题很实际：Sync 里要写「我发出的时刻 t1」，可真正的发出时刻要等报文已经在发才知道。two-step 先把 Sync 发出去、硬件记下真实时刻，再用 Follow_Up 补发精确的 t1——实现简单，代价是报文量翻倍；one-step 让硬件在报文飞出去的过程中实时改写时间戳并重算校验和，省掉 Follow_Up，但要求网卡/PHY 具备这个能力。两者协议上互通（从时钟看 twoStepFlag），选哪个由硬件能力决定。

BMCA：谁当主时钟

PTP 域里的时钟通过 Announce 报文互相通告自己的属性，每个节点独立运行 BMCA（Best Master Clock Algorithm），按固定优先级逐项比较，选出最好的那个当主。比较顺序是：

# BMCA 数据集比较顺序（前面的字段分出胜负就不再看后面的）
  1. priority1          # 人工优先级，越小越优先。运维手动干预的主要旋钮
  2. clockClass         # 时钟等级，反映溯源质量（见下表）
  3. clockAccuracy      # 精度枚举
  4. offsetScaledLogVariance  # 稳定度
  5. priority2          # 第二人工优先级，用于同等条件下分高下
  6. clockIdentity      # 最后靠 ID 大小决胜，保证结果唯一且确定

# 几个常见的 clockClass（G.8275.1 语境）：
   6  = 溯源到 PRTC 且当前锁定（GNSS 正常）
   7  = 曾溯源到 PRTC，当前处于 holdover，仍在规格内
  140 / 150 / 160 = holdover 已超出规格、或未溯源到 PRTC 的各档降级状态
  248 = 默认值（自由振荡，没有可信来源）
  255 = slave-only 节点
clockClass = 7 是运维里最值得盯的一个值：它表示「GNSS 已经丢了，正在靠本地振荡器硬撑」。此时 PTP 一切正常、下游全部 LOCKED、没有任何同步告警——但时间正在缓慢漂移，业务劣化会在几十分钟甚至几小时后才显现。把 clockClass 从 6 变 7 这件事本身设成告警，比等相位超标再告警要早一个数量级。这条经验在面试里很能体现实战经历。

硬件时间戳：为什么软件打戳根本不够

PTP 的精度上限，取决于「记录 t1~t4 这四个时刻」有多准。打戳点到线路之间的那一段，全部变成误差——所以越靠近物理层越准：

BC 与 TC：中间设备必须参与

PTP 报文穿过一台普通交换机时会在队列里排队——排队时间随机、上下行还不一样，直接违反对称性假设，而且违反的量随负载变化。所以电信级 PTP 网络里，路径上每一台设备都必须是 PTP 感知的。两种做法的差别在下图：

ITU-T 剖面：G.8275.1 与 G.8275.2

IEEE 1588 只是个框架：报文速率、承载方式、BMCA 行为、时钟属性取值全都可配，两台都"符合 1588"的设备完全可能互通不了。所以各行业要在它之上定义剖面（profile）收紧这些自由度。电信用的是 ITU-T 这一族：

G.8275.1G.8275.2G.8265.1
同步内容相位 / 时间相位 / 时间仅频率
俗称FTS（Full Timing Support）PTS / APTS（Partial / Assisted PTS）频率剖面
对网络的要求路径上每一跳都必须是 T-BC允许中间存在不支持 PTP 的网段无特殊要求
承载以太网组播（L2，逐跳终结）IPv4/IPv6 单播（可路由、可跨网段）IP 单播

面试最爱追问「为什么 .1 非要用二层组播」。答案不是"二层更快"，而是组播 + 逐跳终结这个组合，从机制上强制了「每一跳都必须参与」——它把「有没有全程支持」这件事变成了可观测的，而 .2 把它变成了不可观测的。

网络限值与设备等级：预算是怎么分下去的

「前传要 ns 级同步」这句话要落到工程上，得回答两个问题：端到端总共允许差多少，以及每一跳允许贡献多少。ITU-T 把这两件事分别标准化了：

  • G.8271.1 定义网络限值：对相位/时间同步网络，端到端到空口的时间误差预算量级为 1.5 μs（对应 3GPP 的 3 μs 小区间要求，两站各占一半）。这个总预算还要在网络与末端设备之间再分配。
  • G.8273.2 定义 T-BC / T-TSC 的设备等级（Class A / B / C，更严的等级面向高密度组网）。等级越高，同一条链上能串的跳数越多。
引用 G.8273.2 的等级数值时，必须说清是哪一个指标——它同时规定了两组限值，数字完全不同，混用会让人以为两份资料互相矛盾：
指标Class AClass BClass C含义
cTE（恒定时间误差）±50 ns±20 ns±10 ns设备引入的固定偏差，可校准、会逐跳累加
max|TE|（最大绝对时间误差）100 ns70 ns30 ns含随机分量在内的总上限，做预算用这个
本篇下面的预算核算用 max|TE|（保守口径）；前传/中传/回传那篇按 cTE 逐跳累加来讲承载网选型，两者不冲突，看的是同一件事的两个侧面。

数值用于建立数量级直觉，各档限值以所用 ITU-T 版本为准；真实工程要用同步规划工具按实际拓扑核算。O-RAN 定义的 LLS-C1 ~ C4 本质都是这套 PTP + SyncE 的部署拓扑变体，四种的差别与选型见 四平面的 LLS-C1 ~ C4 一节。

GNSS 与 holdover：链条的头和尾

整条同步链最终要溯源到一个物理基准，绝大多数情况下是 GNSS（GPS/北斗/Galileo）。它便宜、精度高（ns 级）、全球可得，但它有三个绕不开的弱点：

风险表现缓解手段
干扰 / 压制（jamming）信噪比下降、可见星数骤减、失锁天线选址避开干扰源、抗干扰天线、监测可见星数与 C/N0
欺骗（spoofing）时间被缓慢牵引到错误值，而设备显示"已锁定"多星座交叉校验、与网络 PTP 互为参照、对时间跳变设阈值告警
安装与环境室内/隧道/密集城区收不到；天线进水、雷击改用网络侧 PTP 分发（这正是 G.8275.1 存在的意义）
系统性依赖全网都靠 GNSS → 单一故障源核心节点配高等级振荡器 + 网络 PTP 作为互备
欺骗比干扰更危险：干扰导致失锁，设备会进 holdover 并告警，你知道出事了；欺骗是让设备"锁在一个错的时间上"，clockClass 仍然是 6、状态灯全绿，而整个区域的相位在慢慢跑偏——§1 的「肇事者与受害者分离」在这里被放大到全网尺度。关键节点不能只信 GNSS 一个源。

GNSS 一旦失锁，本站就靠本地振荡器 holdover顶着，能顶多久完全取决于振荡器等级（§5.1 那张图的另一种读法）：

振荡器频率稳定度量级撑到 1.5 μs 的时长量级成本 / 体积 / 功耗
TCXO（温补晶振）~1 ppm秒级最低
OCXO（恒温晶振）~1–10 ppb（短稳更好）小时量级中；需要预热时间
Rb（铷原子钟）~0.01 ppb 量级天量级高；体积功耗都大

holdover 时长强烈依赖温度稳定性与老化，上表只给数量级。规划时的正确做法是先定「要撑多久」（比如"够运维赶到现场"或"够撑过一次计划割接"），再倒推振荡器等级与是否需要网络侧 PTP 互备。

工程与陷阱

落地要注意

头号敌人：路径不对称

§4.1 已经推过结论，这里把它画出来——为什么 Δ 的不对称必然换来 Δ/2 的固定误差，以及为什么滤波和平均都救不了：

不对称来源量级能否补偿做法
单纤双向（BiDi）光模块：收发用不同波长（如 1310/1490），光纤色散使两个波长群速度不同每公里数纳秒量级能，但要按实际纤长与波长算在设备上配置固定的不对称补偿值
收发走不同物理路由（保护倒换后尤其常见）可达数微秒，取决于路由长度差难——路由会变规划阶段就要求收发同路由；倒换后重新评估同步
设备内部收发处理路径不等ns ~ 数十 ns能，出厂校准厂商标定，通常已含在设备指标里
双纤方案里两根纤长度不同每米约 5 ns能测量实际纤长差并配置补偿
中间存在不支持 PTP 的设备随负载变化，不固定不能只能换设备或改用 FTS 逐跳 BC

现场怎么测：ptp4l / phc2sys 的输出判读

Linux 上的事实标准是 linuxptp：ptp4l 跑协议、把网卡 PHC（PTP Hardware Clock）对齐到主时钟，phc2sys 再把 PHC 与系统时钟对齐。两者缺一不可——只跑 ptp4l，网卡时间准了但系统时间照样飘。配置侧要点只有四条：time_stamping hardware、network_transport L2（G.8275.1 走二层）、delay_mechanism E2E、logSyncInterval -4（每秒 16 个 Sync）。真正要练的是读输出：

$ sudo ptp4l -f /etc/ptp4l.conf -m
ptp4l[21.480]: master offset      -8241 s0 freq  -12043 path delay     41230
ptp4l[23.480]: master offset        -33 s2 freq  -10871 path delay     41231
ptp4l[25.480]: master offset         -7 s2 freq  -10861 path delay     41230

# 四个字段各回答一个不同的问题：
#  master offset  与主钟差多少（ns）。稳态应在几十 ns 内小幅抖动。
#                 ★ 稳定偏在非零值 = 路径不对称；围绕零大幅跳 = 抖动。
#  s0 / s1 / s2   伺服状态：未锁 / 首次调整 / 已锁定。
#                 ★ 只有持续 s2 才算真锁；反复回落说明报文在丢。
#  freq           对本地振荡器的频率修正量（ppb），应当稳定。
#                 ★ 持续朝一个方向爬 = 本地晶振在漂，或 SyncE 没配好。
#  path delay     算出的单向时延（ns）。41230 ns ≈ 8.4 km 光纤，合理。
#                 ★ 大幅波动 = 中间有非 PTP 设备在排队；
#                   突然阶跃 = 路由变了（保护倒换？），不对称补偿值已失效。
$ sudo phc2sys -s eno1 -w -m
phc2sys[62.5]: CLOCK_REALTIME rms    9 max   21 freq  -8452 +/-  12 delay  1180 +/-  40
#  rms 长期均方根，个位数到几十 ns 算好；
#  ★ max 才是实时业务真正在乎的那个数，不是 rms。

$ sudo pmc -u -b 0 'GET PARENT_DATA_SET'
        grandmasterIdentity       001b19.fffe.3a2c01
        grandmasterClockClass     6     ← ★ 6=锁定 PRTC；7=holdover 正在漂（§4.4）
        gmPresent                 true

两种反直觉的现场情况

同步告警，但业务正常

常见于刚进 holdover 的短时间内：clockClass 已变 7、告警已响，但本地振荡器还没漂出预算，空口一切正常。

处置：这是预警而不是故障，价值在于留出了修复窗口——按 §6.3 的表估「还能撑多久」，据此决定立刻派人还是等窗口期。最糟的做法是因为"业务没事"就把告警屏蔽掉。

业务异常，但同步显示正常

三种典型成因：① 本站锁在了错误的源上（GNSS 欺骗，或选源配错追到了一个降级时钟），自己认为很好；② 问题在邻站——本站是受害者（§1 的功率不对称）；③ 存在固定不对称，offset 显示接近 0 是因为它被算进了"链路时延"里。

处置：拿独立的外部基准（便携 GNSS 接收机 / 时间测试仪）到现场测 1PPS 相位差，不要只信设备自己的读数。

某室内覆盖场景，一批 O-RU 每天凌晨到清晨上行底噪抬升、白天恢复，持续两周没定位到。所有 O-RU 同步状态都是 LOCKED、无同步告警，最初根本没往时钟上想；直到注意到抬升时段与机房空调的夜间节能模式高度重合，才用 pmc 查出 grandmasterClockClass 夜间从 6 变成 7——GNSS 馈线接头进水，低温下接触电阻变化导致失锁，白天回温又锁上。

两个关键点：一是 holdover 期间除了 clockClass 这个值，其它一切都显示正常；二是底噪抬升比 clockClass 变化滞后约 40 分钟——正是本地 OCXO 漂出预算所需的时间，这个滞后就是当初没人把两件事联系起来的原因。处方：修接头，并把「clockClass 从 6 变为非 6」直接设成告警项。

面试题（12 道）

分层自测

8.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础频率同步、相位同步、时间同步有什么区别？

    三者是严格递进的关系：时间同步 ⊃ 相位同步 ⊃ 频率同步。

    • 频率同步：两个时钟走得一样快，单位时间长度相同。不要求指向同一刻度。指标单位是 ppb/ppm。
    • 相位同步：在频率一致的基础上，秒边沿（1PPS 上升沿）对齐——同时跳秒，但可以对"现在是第几秒"看法不同。指标单位是 ns/μs。
    • 时间同步：再加上共同的时间刻度与纪元，都知道现在是 UTC 的具体时刻，需要额外传 UTC offset 等信息。

    反过来不成立：相位对齐必然频率一致（否则边沿会越走越开），但频率一致的两个钟可以永远差着固定的 37 ms 而毫不自知。

    实用判据：「这个业务需要知道『现在几点』吗？」不需要、只要步调一致 → 频率（FDD、SDH）；需要"同时开始"但不关心几点 → 相位（TDD 时隙边界）；需要跨系统对时间戳或算绝对到达时刻 → 时间（定位、TSN）。

  2. 基础为什么 TDD 必须相位同步，而 FDD 只要频率同步？

    因为 TDD 上下行共用同一段频率、靠时间切开，而 FDD 上下行分在不同频率上，物理上不会撞车。

    TDD 的下行与上行时隙之间夹着保护间隔 GP，GP 要同时覆盖三件事：① 最远 UE 的往返传播时延（10 km 小区约 66.7 μs，这是大头）；② 收发切换时间；③ 相邻基站之间的相位同步误差。

    同步误差一旦把 GP 吃穿，A 站还在发下行的时段就和 B 站已经切到接收上行的时段重叠了。而基站下行功率（宏站 46 dBm 量级）比它要接收的 UE 上行信号（−110 dBm 量级）高出百分贝以上，就算隔着几公里，漏过去的信号仍然远高于有用信号——B 站在那几个符号里彻底聋掉。

    3GPP 对 TDD 小区相位同步的要求是 ≤ 3 μs（各站相对公共基准 ±1.5 μs）。换算一下：1.5 μs × 光速 ÷ 2 = 225 m 的小区半径——同步每差 1.5 μs，等于白扔掉 225 m 覆盖。

  3. 基础PTP 是怎么用四个时间戳算出时钟偏移的？

    从时钟面对两个未知量：偏移 θ 和单向时延 d。一次往返给出两个方程：

    t2 − t1 = d_ms + θ    … ①  （Sync：主→从）
t4 − t3 = d_sm − θ    … ②  （Delay_Req：从→主）

    两个方程、三个未知数解不出来，必须补一个对称性假设 d_ms = d_sm = d。有了它：

    d = [ (t2 − t1) + (t4 − t3) ] / 2
θ = [ (t2 − t1) − (t4 − t3) ] / 2

    从时钟把自己的时间减去 θ 就对齐了。

    回答时一定要主动点出对称性假设——它是 PTP 全部误差的来源，也是面试官接着要追问的点。

  4. 基础SyncE 和 PTP 各解决什么问题？

    SyncE（ITU-T G.8261/8262/8264）在物理层传频率：设备把某个收端口 CDR 恢复出的时钟送进 DPLL，用它驱动自己所有发送口，一级级传下去。因为在物理层，完全不受排队、拥塞、负载影响，也不受路径不对称影响。但它不携带任何"几点"的信息。

    PTP（IEEE 1588）用带硬件时间戳的报文交换算出时间与相位。能给出绝对时刻，但精度直接受网络抖动和路径不对称影响。

    一句话对照：SyncE 稳但不知道几点，PTP 知道几点但不够稳。所以电信网络两个都要。

8.2 中级（区分熟练度）

  1. 中级路径不对称会带来多大误差？为什么滤波消不掉？

    设真实往返不对称量为 Δ = d_ms − d_sm，代入 PTP 的求解公式可以直接得到：算出的 θ 偏离真值 Δ/2。也就是 1 μs 的路径不对称 = 0.5 μs 的固定时间误差。

    消不掉的原因：它是系统性偏差而不是随机噪声。滤波、多次测量取平均、卡尔曼这些手段都是在压制零均值的随机分量；而不对称带来的偏差每一次测量都朝同一个方向、同样大小，平均多少次都还在那儿。

    常见来源与能否补偿：

    • BiDi 单纤双向光模块（收发用不同波长，色散导致群速度不同）：每公里数纳秒量级，能补偿，按实际纤长配固定值。
    • 收发走不同物理路由（保护倒换后常见）：可达数微秒，很难——路由会变，只能在规划阶段要求同路由。
    • 双纤长度不同：每米约 5 ns，能测量后补偿。
    • 中间有非 PTP 设备：随负载变化，完全不能补偿，只能换设备。

    现场区分技巧：看 ptp4l 的 offset 稳定偏在非零值就是不对称，围绕零大幅跳动就是抖动，两者处方完全不同。

  2. 中级为什么 PTP 必须用硬件时间戳？

    因为 PTP 的精度上限取决于「记录 t1~t4 四个时刻」有多准，而打戳位置越靠近物理层越准：

    打戳位置误差量级可达同步精度
    用户态数十 μs ~ ms毫秒级
    内核软件时间戳μs 量级几十 μs
    网卡 MAC 硬件戳数十 ns亚微秒
    PHY 层时间戳个位数 nsns 级

    软件打戳要穿过协议栈、中断、调度，这些延迟不但大而且抖动大且上下行不对称——正好踩中 PTP 最怕的两件事。而 TDD 需要 μs 级、MIMO/CA 需要几十到几百 ns，软件戳差了一到两个数量级。

    实操上第一步就是 ethtool -T <iface>：要看到 hardware-transmit / hardware-receive 且 PTP Hardware Clock 不是 none。如果只有 software-*，这块网卡做不了电信级 PTP，换卡，不要试图调参数补救。

  3. 中级BC 和 TC 有什么区别？为什么电信网络更常用 BC？

    两者都是为了解决「普通交换机的排队时延破坏对称性假设」这个问题，做法不同：

    • BC（边界时钟）：在上游口当从、下游口当主，逐段重新做一次完整的 PTP。每跳重新定时，上游的抖动不会原样传下去；代价是每跳自身会引入一点误差。
    • TC（透明时钟）：不做主从，只测量报文在自己内部的驻留时间并累加进 correctionField，让最终从时钟扣掉。实现更轻。

    电信更常用 BC 的原因：① ITU-T G.8275.1（FTS 剖面）就是建立在逐跳 T-BC 之上的，并由 G.8273.2 给 T-BC 分了 Class A/B/C 等级，误差可以逐跳量化、预算可以逐跳分配；② BC 参与 BMCA，拓扑管理、倒换、状态可观测性都更好；③ TC 的 correctionField 逐跳累加，跳数多时精度不如逐跳重新定时。

    补充加分：E2E 与 P2P 时延机制不能在同一个 PTP 域里混用，它们对中间设备的行为要求不同，组网前必须统一。

  4. 中级SyncE 靠什么选源和防环？

    靠 ESMC（Ethernet Synchronization Messaging Channel）承载的 QL（质量等级）。

    ESMC 是以太网 Slow Protocol（组播 01-80-C2-00-00-02，EtherType 0x8809），周期性在每个 SyncE 端口通告一个 QL，表示「顺着我这个口往上追能追到什么等级的基准」。常见等级从高到低：QL-PRC（一级基准，1×10⁻¹¹）→ SSU-A → SSU-B → QL-EEC1（网元自身时钟，±4.6 ppm）。设备据此选择最优的参考端口。

    防环靠 QL-DNU（Do Not Use）：设备一旦选定从端口 X 收时钟，必须朝 X 口回发 DNU，告诉上游别再从我这取。漏了这一步，A 和 B 就可能互选形成时钟环路——两边 DPLL 都显示 LOCKED、QL 都显示 PRC，但整个环已脱离真基准自由漂移。这类故障所有状态灯都是绿的，只能拿外部基准比对才能发现。

    还有一个跨厂商的坑：SSM 码值在 G.781 的 Option I（欧洲）/ Option II（北美）下编码与名称都不同，同一张网必须全程用同一个 Option。

8.3 高级（体现深度）

  1. 高级G.8275.1 与 G.8275.2 怎么选？为什么前者要用二层组播？

    G.8275.1（FTS，Full Timing Support）：要求路径上每一跳都是 T-BC，走以太网组播，精度最高，是 5G 前传与 TDD 承载网的主流。

    G.8275.2（PTS/APTS，部分支持）：走 IP 单播，允许中间存在不支持 PTP 的网段，精度明显更差且强依赖那段网络的对称性。通常作为过渡方案；APTS 变体是在本站加 GNSS、PTP 只作备份。

    为什么 .1 用二层组播——这是最容易被追问的点，答案不是"二层更快"，而是机制上的强制性：组播地址是链路本地的，报文走不出一跳。中间设备要么作为 T-BC 处理并重新生成报文，要么这条同步链就在那里断掉、下游立刻能发现。

    反观 G.8275.2 的单播 IP：报文可以悄悄穿过一段不支持 PTP 的网络到达对端，看起来是通的，精度却已经被那段网络的排队抖动毁掉，而且没有任何机制会告诉你。这既是它精度差的原因，也是它难排查的原因。

    另外还有 G.8265.1 是频率剖面，只做频率同步，对应 FDD 时代的需求。

  2. 高级SyncE 对 PTP 的 holdover 有多大帮助？能不能算给我听？

    能，而且这是理解"为什么两个都要装"的关键。基础公式是频率误差在时间上积分就是相位误差：ΔT(t) = y × t。

    场景：PTP 链路中断，从时钟进入 holdover，只能靠本地频率源维持相位。问多久突破 1.5 μs：

    • 没有 SyncE：板载 TCXO 自由振荡，实际频率偏差约 1 ppm。t = 1.5e-6 / 1e-6 = 1.5 秒。等于没有 holdover 能力。
    • 有 SyncE：频率仍由物理层锁在 PRC 上，偏差可压到 ~10 ppb。t = 1.5e-6 / 1e-8 = 150 秒。从秒级变成分钟级，够撑过一次链路倒换或设备重启。
    • 本站高等级振荡器：OCXO 可到小时量级，铷钟可到天量级，代价是成本、体积、功耗与预热时间。

    第二个作用常被忽略：频率被物理层稳住之后，PTP 从时钟的伺服环可以把带宽设得很窄，只需慢慢修正相位，于是能对报文时延抖动做很强的滤波。没有 SyncE 的 PTP 必须同时跟频率和相位，滤波带宽被迫放宽，抗抖动能力显著下降。

    所以标准里管这种配置叫「频率辅助（frequency-assisted）的 PTP」，而不是简单的"两个都装上"。

  3. 高级前传的同步预算是怎么逐跳分下去的？

    分两层标准：G.8271.1 定网络限值（端到端到空口的时间误差预算量级 1.5 μs，对应 3GPP 的 3 μs 小区间要求、两站各占一半）；G.8273.2 定设备等级（Class A / B / C）。引用数值时必须说清指标：cTE（恒定时间误差）是 ±50 / ±20 / ±10 ns，max|TE|（含随机分量的总上限）是 100 / 70 / 30 ns——两组数都出自这份建议书，混用就会显得自相矛盾。做端到端预算用 max|TE| 这个保守口径。

    一条链的粗略核算（量级示意）：

    端到端预算                        1500 ns
├─ PRTC/T-GM 自身                −  100 ns
├─ 6 跳 Class B（70 ns/跳）      −  420 ns
├─ 末端 T-TSC（O-RU 从时钟）     −  150 ns
├─ 链路不对称残余                −  300 ns   ← 常常是最大一块
└─ 余量                            ≈  530 ns

    两个结论：① 跳数不能随便加，Class B 下每 6 跳吃掉近三分之一预算，所以前传拓扑要"扁"；② 不对称残余往往比所有设备误差加起来还大，把钱花在校准不对称上通常比升级设备等级更划算。

    加分：具体限值与划分方式以所用 ITU-T 版本为准，真实工程要用规划工具按实际拓扑核算，不能照抄示例。

  4. 高级一片区域的基站上行底噪同时抬升，但每个站自己都没有同步告警。你怎么查？

    这是 TDD 同步故障的典型特征，关键认知是肇事者与受害者是分离的：时钟跑偏的站自己各项指标可能全绿（它锁在了一个错误的源上，自认为锁得很好），出问题的是它的邻站。所以不要只查告警的站，要查那片区域周边的站。

    排查顺序：

    1. 先看 clockClass 而不是看告警。用 pmc -u -b 0 'GET PARENT_DATA_SET' 查周边站的 grandmaster 状态：6 = 锁定 PRTC，7 = 已进 holdover 正在漂。7 的时候设备一切显示正常、没有同步告警，但时间在缓慢跑偏——这是最常见的"隐形"故障。
    2. 看 ptp4l 的三个量：offset 是稳定偏移（不对称）还是围绕零跳动（抖动）；path delay 是否恒定（波动=中间有非 PTP 设备，阶跃=路由变了）；freq 是否持续单向爬（本地晶振在漂，或 SyncE 没配好）。
    3. 检查是否锁在错误的源上：GNSS 欺骗、或选源配错追到了降级时钟。判据是拿独立的外部基准（便携 GNSS/时间测试仪）到现场实测 1PPS 相位差，不要只信设备自己的读数。
    4. 检查 SyncE 时钟环路：如果整网都显示 PRC 但时间集体偏了，查 ESMC 的 DNU 是否正确回发。
    5. 看时间相关性：故障是否与温度、负载、割接、保护倒换等外部事件相关——这往往比看日志更快定位。

    加分点：主动提出把 clockClass 从 6 变为非 6 直接设成告警项，而不是等相位超标才告警。前者能提前几十分钟甚至几小时发现问题——因为本地振荡器从进入 holdover 到漂出预算之间有一段缓冲，这段时间正是修复窗口。
