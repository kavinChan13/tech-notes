1.1 从协议平面到代码模块

核心洞察：不同平面对"好"的定义不同——数据面要快、管理面要稳、控制面要对，所以线程模型、错误处理、数据结构都不该用同一套。

1.2 真正的分界线：三个平面的时间尺度差三到六个数量级

「按平面分层」常被写成一条组织原则，仿佛是为了代码好看。它其实是被物理约束逼出来的——把三个平面的时限预算画在同一根对数轴上，理由就自己跳出来了：

时限预算（deadline budget）：一次处理从触发到必须完成之间允许消耗的时间。它不是「平均耗时」而是「不能超过的上界」——超过之后发生的不是变慢，而是功能错误（丢帧、掉话、链路复位）。架构决策的依据是预算，不是平均值。
平面单次处理的时限预算触发频率（一个中等规模 DU 的量级）超时的后果
数据面（用户面收发、eCPRI IQ 搬运）亚微秒 ~ 数微秒每秒百万级到千万级丢帧、误块率上升；前传超出接收窗口被 RU 丢弃
控制面（调度决策、信令状态机、切换）数百微秒 ~ 数十毫秒每秒千级到万级调度错过时隙、信令超时重试、切换失败掉话
管理面（配置下发、告警、性能统计）数百毫秒 ~ 数十秒每分钟几次到每小时几次网管界面转圈、配置生效慢；不影响正在跑的业务
生活类比：把三个平面塞进同一套线程模型，像是让手术室、门诊和医院财务共用一份排班表。财务月底做账拖两天没人受伤；门诊病人等半小时会抱怨；手术台上的麻醉师晚三十秒就是事故。医院从来不会用一份排班表管三边——通信设备也一样。

轮询线程即使一个包都没有也在满载空转，所以数据面真正的负载指标是「每轮循环处理了几个包」和「空轮占比」（§2.4），不是 CPU 使用率。三个平面为什么是三个进程，见 §5.3。

一条被写错的 chrt
某设备把统计线程也提到了 SCHED_FIFO 优先级 80，却没给它绑核，于是它偶尔落到隔离核上。两个同优先级的 FIFO 线程在同一个核上时，后来的那个要等前一个主动让出 CPU——而轮询 worker 永远不会让出。统计线程因此被饿死几十秒；当它恰好持有一把和 worker 共享的锁时，就是实时环境下的死锁。
教训：优先级和 CPU 亲和必须成对设计——在隔离核上，任何与轮询线程同优先级的线程都等同于「永不被调度」。

1.5 为什么不能「先做成一个进程，将来再拆」

这是骨架期最常见的决定，也是最贵的一个。问题在于：三个平面共用一个进程时，代码会自发地长出无法拆开的依赖，而且长出来的过程完全无感。

❌ 合进程后会自发长出的三种耦合

  • 共享一个全局配置对象。管理面改一个字段、数据面直接读，省掉了消息定义与序列化。等到要拆才发现这种「顺手」的读取有几百处，一部分还在包路径上（于是还得顺带解决数据面的配置无锁读，见 §4.3）。
  • 控制面直接调用数据面的函数。同进程里一次调用只要几纳秒，所以没人会想去定义一条消息。而这条调用一旦发生在控制面线程上，数据面的数据结构就同时被两个线程碰了，于是被迫加锁——锁进包路径，确定性就没了。
  • 共用一套异常与内存分配。数据面无法用 -fno-exceptions 编译，也无法用自定义分配器接管堆。

✅ 一开始就分进程，得到的是

  • 耦合被编译器强制。跨进程唯一的通信方式是显式消息，「顺手读一下」在语法上就做不到——比任何代码规范都管用。
  • 故障隔离是白送的。管理面解析一条畸形 XML 崩了，数据面一个包都不会丢。
  • 编译选项与语言可以分开选：数据面 -fno-exceptions -fno-rtti，管理面正常 C++ 甚至 Python。
  • 升级粒度变细：改一条告警规则只需重启管理面，业务零中断（§7.4）。

代价是跨进程要付序列化与 IPC 开销（§5.4 给了量级）、调试要同时看三个进程。但这些代价是线性的、可预估的；而「合了再拆」的代价是指数的，且只有在拆的时候才会被发现。

02

Data Plane 设计

一整套「不许做什么」的纪律

数据面的设计原则可以浓缩成一句：它不是「写得更快的普通代码」，而是「一段被剥夺了大部分语言特性的代码」。下面先看执行模型，再看「禁止清单」，最后回答最实际的问题——不许打日志、不许分配内存，那出问题时怎么查。

RX→Parse→Lookup→Modify→TX

2.1 run-to-completion 与轮询：为什么一个包不换手

run-to-completion（RTC，一跑到底）：一个包从收进来到发出去的全部处理都在同一个线程、同一次调用栈里完成，中途不入队、不移交、不等待。相对的是 pipeline（流水线）：把处理切成若干级，每级一个线程，级间用队列传递。
生活类比：RTC 是一个厨师从洗菜到装盘全做完；pipeline 是流水线上四个人各做一步、用传送带传递。流水线看起来更「专业化」，但每传一次都要放下、拿起、重新看清这是什么菜——在做一道菜只要 60 纳秒的场景下，传递本身比做菜还贵。
维度run-to-completionpipeline（多级 + 队列）
每包额外开销≈ 0每级入队+出队 ≈ 20~50 ns（无竞争 SPSC，需批量摊薄）
Cache 局部性✅ 全程留在本核 L1/L2❌ 每跨一级要从上一个核搬 cache line（40~100 ns/行）
扩展方式横向复制：加一个核 = 加一条完整流水线纵向切分：加核要重新切分级并平衡各级耗时
木桶效应没有——一个核慢只影响自己那份流量有——吞吐等于最慢那一级，且会随流量特征漂移
时延分布紧凑，抖动小每级排队都贡献抖动，尾延迟明显更差
适合什么绝大多数转发型数据面；逻辑同质、每包耗时相近某一级必须绑在特定核上（加密卡、专用加速器），或耗时远超其它级且需单独扩容

RTC 与「轮询」是一对孪生兄弟：既然一个包全程不换手，「等包」这件事就只能由 worker 自己做——而在微秒预算下，唯一可选的等法是空转。

// 数据面 worker 的骨架 —— 这段代码的形状本身就是设计
void worker_loop(WorkerCtx* ctx) {
    constexpr unsigned BURST = 32;
    Packet* bufs[BURST];

    while (__builtin_expect(!ctx->stop_flag.load(std::memory_order_relaxed), 1)) {
        // ① 批量收：一次 syscall/一次 ring 访问取回最多 32 个包
        unsigned n = rx_burst(ctx->rx_queue, bufs, BURST);

        if (n == 0) {
            ++ctx->stat.empty_polls;      // ← 空轮计数：数据面真正的负载指标
            cpu_relax();                  // x86: _mm_pause() / ARM: __yield()
            continue;                     // 注意：不 sleep、不 epoll_wait、不让出 CPU
        }

        // ② 预取下一批的包头，把 DRAM 延迟藏进本批处理时间里
        for (unsigned i = 0; i < n; ++i) __builtin_prefetch(bufs[i]->data);

        // ③ run-to-completion：解析→查表→改写，全在本线程本栈上完成
        unsigned tx_n = 0;
        for (unsigned i = 0; i < n; ++i) {
            Verdict v = process_one(ctx, bufs[i]);   // 无分配、无锁、无日志、无 syscall
            if (v == Verdict::FORWARD) bufs[tx_n++] = bufs[i];
            else                          drop(ctx, bufs[i], v); // drop 也只是「计数 + 还池」
        }

        // ④ 批量发；发不出去的立刻还池，不重试、不缓存
        unsigned sent = tx_burst(ctx->tx_queue, bufs, tx_n);
        ctx->stat.tx_drop += (tx_n - sent);
        for (unsigned i = sent; i < tx_n; ++i) free_to_pool(ctx->pool, bufs[i]);

        // ⑤ 每 N 轮做一次「非包路径」的杂活：定时器到期、统计快照、命令检查
        if (__builtin_expect(++ctx->round % 1024 == 0, 0)) housekeeping(ctx);
    }
}
第 ⑤ 步最容易漏。定时器扫描、统计快照、配置检查必须由 worker 自己在两批包之间做，否则别的线程闯进来碰它的数据结构就要加锁。代价是这份耗时直接叠加到那一轮的时延上，所以它自己也必须有界：「每轮最多处理 8 个到期定时器」优于「处理完所有到期定时器」——后者在定时器雪崩时是一次几百微秒的停顿。

2.2 禁止清单：为什么这四件事在包路径上是红线

「数据面不许 malloc / 加锁 / 打日志 / 进内核」流传很广，但只有把每一条的代价和它对应的现象说清楚，它才从口号变成纪律：

禁止项为什么（代价与机理）生产上的现象替代做法
动态内存分配
malloc / new / std::vector 扩容 / std::string		 快路径（tcache 命中）15~30 ns 已吃掉小包预算一小半；真正的问题是长尾——不命中要走 arena（可能抢锁）、可能触发 mmap、新页首次写缺页（1~3 µs）。长期运行还会碎片化。 P50 完美、P99.9 高出一两个数量级；重启后头一分钟尤其差；RSS 爬升被误判为泄漏 启动时预分配定长对象池，运行期只「取 / 还」；池空了就丢包并计数，不临时扩容
加锁
任何 mutex、甚至「看起来很轻」的自旋锁		 无竞争的 mutex 只要 ~20 ns，问题不是锁本身，是竞争：一旦竞争，要么走 futex 睡醒一趟（µs 级，超预算几十倍），要么 cache line 在核间来回弹（40~400 ns/次）。更致命的是时延变得不可预测，预算模型彻底失效。 加核数吞吐不升反降；perf c2c 里某条 cache line 的 HITM 极高；时延分布双峰 消除共享：每核一份数据，按会话哈希分片到固定核；跨核只用 SPSC 队列传消息
打日志
printf / syslog / 任何格式化输出		 三重代价叠加：格式化本身几百纳秒到微秒（%f 尤其慢）；写文件/socket 是系统调用；多线程共用日志器时那把互斥锁成了全局串行点。而且日志在出问题时最密集——正好在最需要吞吐的时候把系统压垮。 「一告警就雪崩」：错误率升高 → 日志暴涨 → 数据面被拖垮 → 错误率继续升高，正反馈 包路径上只递增计数器；需要细节时写定长二进制事件到每核环形缓冲，由旁路线程格式化（§2.4）
系统调用
含 clock_gettime 之外的一切		 空 syscall 在开了 Spectre/Meltdown 缓解（KPTI、IBPB）之后可能到微秒量级。逐包一次就等于把预算翻几倍。 top 里 sy 占比高；perf 火焰图上内核入口函数很热 用户态直通（DPDK / AF_XDP）；必须调用时批量化（recvmmsg/sendmmsg）；取时间用 vDSO 的 clock_gettime（~20 ns，不进内核）或 TSC
C++ 异常
throw / 会抛的标准库调用		 不抛时零开销，但一旦抛出，栈展开要读 .eh_frame、可能触发 malloc、首次抛出还要拿全局锁查异常表——微秒到毫秒，完全不可预测。 某类畸形报文一来，时延瞬间尖刺，甚至像「卡死」 数据面用 -fno-exceptions -fno-rtti 编译；错误用返回值 / Verdict 枚举表达
虚函数与间接跳转（次要） 单次只是一次间接跳转，但目标频繁变化时预测失败率高，一次错误预测 15~20 周期，且会打断预取。 IPC 偏低，perf stat 里 branch-misses 占比明显 热路径用模板 / switch 把分发变成编译期已知；或把同类包聚在一起连续处理
三个「隐形违规」，在代码里根本看不出来是禁止项：std::function 捕获过大时会堆分配；map::operator[] 在 key 不存在时会插入，一次「查询」变成一次分配；首次调用动态库函数的惰性符号解析会拿全局锁，单次可达微秒级——它的特征是「只有第一次慢」，压测时会被当成预热而丢掉。

2.4 不许打日志，那怎么观测？

数据面纪律带来一个真实困境：最需要观测的那一段，恰好是最不能被观测打扰的那一段。解法不是「少观测」，而是把观测的成本从包路径上挪走。三个层次：

层次一：per-core 计数器（每包都能付得起）

包路径上唯一可以无限用的观测手段是递增一个本核私有的普通变量——注意是普通变量，不是 atomic：

    uint64_t tx_pkts, tx_drop;
    uint64_t empty_polls, rounds;

03

Control Plane 与状态机

为什么通信代码里到处是显式状态机

翻开任何一份通信设备的控制面代码，你都会看到成片的 enum State、on_event()、start_timer()。这不是编码风格，而是问题域强加的结构。这一节先说清「为什么必须是状态机」，再给实现骨架，最后讲两个真正会咬人的问题：状态爆炸和重入。

3.1 为什么必须是显式状态机

两个理由，缺一个都还能用 if 硬扛，两个凑齐就只能上状态机：

① 协议规范本身就是状态机

TCP 的十一个状态（RFC 793 / 9293）、NETCONF 会话、RRC 的 IDLE / INACTIVE / CONNECTED——标准里画的就是状态转移图。实现写成一堆布尔标志，等于每次对照规范排查都要在脑子里翻译一次，而这个翻译正是 bug 的产地：规范说「只有在 X 状态收到 Y 才合法」，代码写成 if (flag_a && !flag_b && timer_running)，两者是否等价，没人能一眼看出来。

② 必须处理超时与乱序

通信是异步 + 不可靠的：对端可能不回、回得很晚、在你放弃之后才回、或者顺序颠倒。于是每个「等待」都要配定时器，每个状态都要回答「在这里收到那条迟到的消息怎么办」。用 if 写，这些异常分支散落在几十个函数里；用状态机写，它们是转移表里一行行明确的条目——空着的格子本身就是待办清单。

本章最值得记住的一句：状态机的价值不在于表达合法路径，而在于把「非法路径」变成可枚举、可审查的东西。展开见 §8.1 第 4 题。
生活类比：办签证。「状态」是「已提交材料 / 已面签 / 补件中 / 已出签」，「事件」是「使馆来信 / 补件寄出 / 超过 30 天没消息」。关键在于：使馆的回信可能丢、可能晚两个月才到、也可能在你已经重新提交之后才到。所以每个状态都得想清楚「这封迟到的信来了怎么办」。通信协议一模一样，只是时间尺度从月变成了毫秒。

3.2 实现骨架：表驱动 vs switch

用「会话建立」这个最常见的场景看一遍。先看它的状态图，再看这张图在代码里长什么样：

// ---- fsm.h : 表驱动状态机骨架（C++17）----
// 各 a_xxx 动作函数与 Msg 的定义在别处；这里给的是「结构」而不是完整程序。
#include <cstdint>
#include <array>

enum class St  : uint8_t { IDLE, WAIT_SETUP_RSP, ACTIVE, WAIT_REL_CFM, N };
enum class Ev  : uint8_t { SETUP_REQ, SETUP_RSP, SETUP_REJ, REL_REQ, REL_CFM,
                                T_SETUP_EXPIRE, T_REL_EXPIRE, PEER_DOWN, N };

struct Session;                                   // 前向声明：上下文
struct Msg;
using Action = void (*)(Session&, const Msg&);   // 裸函数指针，无堆分配

struct Trans { St next; Action act; };

// 转移表：行=当前状态，列=事件。next==St::N 表示「此格非法」。
// ⚠ 这张表的价值一半在于「填了什么」，一半在于「哪些格子是空的」——
//    每个空格都是一次「这里收到这个事件该怎么办」的显式决定。
static constexpr Trans kTable[(size_t)St::N][(size_t)Ev::N] = {
/*                 SETUP_REQ              SETUP_RSP                SETUP_REJ              REL_REQ                REL_CFM                T_SETUP_EXPIRE         T_REL_EXPIRE           PEER_DOWN            */
/* IDLE       */ {{St::WAIT_SETUP_RSP,a_send_setup}, {St::N,nullptr},     {St::N,nullptr},     {St::N,nullptr},   {St::N,nullptr},   {St::N,nullptr},           {St::N,nullptr},   {St::IDLE,a_nop}      },
/* WAIT_RSP   */ {{St::N,a_reject_dup},          {St::ACTIVE,a_activate},{St::IDLE,a_cleanup},{St::IDLE,a_abort},{St::N,nullptr},   {St::IDLE,a_setup_timeout},{St::N,nullptr},   {St::IDLE,a_cleanup}  },
/* ACTIVE     */ {{St::N,a_reject_dup},          {St::ACTIVE,a_late_rsp},{St::N,nullptr},     {St::WAIT_REL_CFM,a_send_rel},{St::N,nullptr},{St::N,nullptr},    {St::N,nullptr},   {St::IDLE,a_cleanup}  },
/* WAIT_REL   */ {{St::N,nullptr},               {St::N,nullptr},      {St::N,nullptr},     {St::WAIT_REL_CFM,a_nop},{St::IDLE,a_released},{St::N,nullptr},   {St::IDLE,a_force_rel},{St::IDLE,a_cleanup} },
};

注意 ACTIVE 行的 SETUP_RSP 格子指向 a_late_rsp 而不是 nullptr——那就是上图里那条虚线。驱动部分同样只有一个入口：

// ---- 事件分发：整个控制面的心脏 ----
void Session::dispatch(Ev e, const Msg& m) {
    const Trans& t = kTable[(size_t)state_][(size_t)e];

    // ① 非法迁移：记录 + 计数，绝不 assert、绝不崩溃。
    //    对端可能是别家实现、可能有 bug、也可能是攻击流量。
    if (t.next == St::N && t.act == nullptr) {
        log_illegal(id_, state_, e);
        ++stat_.illegal[(size_t)state_][(size_t)e];
        return;                                // 状态保持不变
    }

    St from = state_;

    // ② 关键：先改状态，再执行动作。
    //    动作里可能同步产生新事件（见 §3.6 重入），
    //    此时状态必须已经是「转移后」的值，否则新事件会按旧状态处理。
    if (t.next != St::N) state_ = t.next;

    // ③ 动作只做三类事：起停定时器、发消息、改上下文。
    //    绝不在这里递归调用 dispatch()，见 §3.6。
    if (t.act) t.act(*this, m);

    trace_transition(id_, from, e, state_);   // 一行 32 字节的定长记录
}

3.3 事件队列：控制面的 run-to-completion

状态机不能被随便调用。必须有且只有一个线程驱动一个状态机实例，一次只处理一个事件、处理完才取下一个——这就是控制面版本的 run-to-completion，收益是决定性的：状态机内部不需要任何锁。

3.4 定时器：为什么是 timing wheel

控制面定时器的负载画像很特殊：数量巨大（每个会话每个流程都有一两个）、绝大多数在到期前就被取消、精度要求不高（毫秒级够用）。这三条一起，决定了通用的定时器结构并不合适。

Timing Wheel（时间轮）：把时间切成固定长度的槽（tick）排成一个环，定时器按「还有多少个 tick 到期」挂到对应槽的链表上；指针每 tick 前进一格，只处理当前槽里的链表。超出一圈的定时器有两种办法：记「还要转几圈」（hashed wheel），或用多级轮进位（hierarchical wheel，像时钟的时分秒三根针）。由 Varghese 与 Lauck 于 1987 年提出，Linux 内核与多数协议栈都采用它。
结构添加取消取最早到期推进一 tick适合

最小堆 / timerfd + 堆O(log n)O(log n)，或惰性删除变 O(1) 但堆会膨胀✅ O(1)—（事件驱动，不需要 tick）定时器不多、但精度要求高；需要精确知道「下一个什么时候到期」

判断该用哪个，问一句：「这两个维度会不会同时变化，且变化互不影响？」会 → 正交区域；不会，只是几个状态碰巧对某事件反应相同 → 分层。选错的代价都是「重构一次比重写还贵」。

3.6 重入：「在回调里改自己状态」这个经典坑

这是状态机里最难查的一类 bug，几乎总是以「顺手」的形式被引入：动作函数里发现「建立期间用户已经请求释放了」，于是就地递归调用了一次 dispatch()。看起来毫无问题，实际是一颗定时炸弹：

层次发生了什么症状
① 动作在错误的状态下继续执行递归返回后 state_ 已是 WAIT_REL_CFM，而外层还在往下跑上层看到「先 ACTIVE 后 RELEASING」的乱序通知，或一个已释放会话的激活事件
② 迁移顺序被倒置trace 里内层先打印、外层后打印，和实际语义相反复盘时得出完全错误的结论——比 bug 本身更浪费时间
③ 对象在自己的栈帧里被销毁内层最终走到「释放会话」，返回外层后是 use-after-free随机崩溃，栈里看不到 dispatch，压测跑几小时才复现一次
一次「偶发的会话泄漏」
某网元的会话数运行几天后缓慢爬升到耗尽资源池，但每一条释放路径的代码都写得对。靠「非法迁移计数器」定位到：WAIT_REL_CFM 下收到 REL_CFM 的次数比进入该状态的次数少了千分之几。根因正是动作函数里同步调用了 dispatch()——内层又投递了一次 REL_REQ，会话被重新推进 WAIT_REL_CFM，而这一次的确认永远不会来（对端早已释放完），兜底定时器也在第一次释放时被取消了。
① 非法迁移和重入都要有计数器，它们是唯一的线索；② 每个「等待对端」的状态必须有兜底定时器，且只能在离开该状态时取消；③ 各状态的会话数分布要做成常态指标——那条缓慢单调上升的曲线比任何日志都先告诉你出事了。

Management Plane

事务性、两份配置、异步生效窗口

管理面是三个平面里唯一「慢到可以慢慢来」的，难点从来不是性能，而是正确性的定义变了：数据面的正确性是「这个包处理对了」，管理面的正确性是「这一批改动要么全生效要么全不生效，且无论中间发生什么都不能停在半路」。

  • 对接 NETCONF/YANG：配置校验 → 事务提交 → 生效，出错能回滚（candidate/commit）。
  • 维护配置库（running）、上报状态/告警/遥测给 SMO。
  • 慢变、低频，但要高可靠、可审计、强安全（mTLS）——和数据面完全不同的取向。

4.1 配置的事务性：要么全生效，要么全回滚

配置事务：一组配置改动被当作不可分割的单元——全部成功才生效，任何一项失败则整体撤销。它借用数据库的 ACID 思想，但难点不同：数据库的「生效」是写一条记录，网元的「生效」意味着改硬件表项、重配 DSP、通知对端——这些动作有些做不到原子，有些甚至撤销不了。
生活类比：给餐厅换菜单。「事务性」不是「把新菜单打印好」，而是「所有服务员、后厨、收银系统同一刻切到新菜单」。做不到同步切换，就会出现「客人按新菜单点、后厨按旧菜单做、收银按新价格收」的混乱——这个混乱窗口的存在与否，正是配置管理的核心问题（§4.3）。

为什么非要事务？「建小区 + 配三个承载 + 开射频」的第二步失败了，没有事务时设备就停在「小区已建、承载没配、射频未开」这个规范里根本不存在的状态。后果不是「这次配置没成功」，而是网管视图与设备实际状态永久不一致，下一次配置在这个不一致上继续叠加——最终只能重启。

① 语法/模型校验XML/JSON 解析、YANG 模型约束（类型、range、pattern、mandatory）直接拒绝，返回 rpc-error，设备一点没动✅ 随便失败，代价为零
② 语义/一致性校验跨节点约束（must/when/leafref）与业务规则（「频点必须在许可的频段内」）同上，整体拒绝✅ 要尽量把失败都挤到这一阶段
③ 预留资源（prepare）向各模块申请但不启用：分配 ID、占住内存/表项/硬件通道已成功的模块逐个 abort，释放预留⚠️ 可以失败，但撤销必须保证成功
④ 提交（commit）让预留真正生效：切换指针、下发硬件表项、通知对端最麻烦——部分已生效。要么重试到成功，要么反向配置回滚，要么判定不可恢复并重启该进程❌ 设计目标是让它不会失败——可能失败的事都必须在 ③ 之前做完

落到代码上最有信息量的一处是 commit() 的返回类型：它是 void，在类型层面宣告「这一步不允许失败」。

// 两阶段提交的骨架：注意 commit() 的返回类型是 void —— 它不允许失败
class ConfigTxn {
    std::vector<Participant*> prepared_;   // 已 prepare 成功的模块，用于回滚
public:
    Status run(const ConfigDelta& d) {
        // ①② 校验：失败零代价
        if (Status s = validate_model(d); !s.ok()) return s;
        if (Status s = validate_semantics(d); !s.ok()) return s;

        // ③ prepare：允许失败，失败则逐个 abort（逆序，与资源依赖相反）
        for (auto* p : participants_) {
            if (Status s = p->prepare(d); !s.ok()) { rollback(); return s; }
            prepared_.push_back(p);
        }

        // ④ commit：不允许失败。凡是能失败的都已经在 prepare 里做过了，
        //    这里只剩「把预备好的东西挂上去」。
        for (auto* p : prepared_) p->commit();

        persist_running(d);       // 落盘：先写临时文件 + fsync + rename，保证掉电原子
        audit_log(d);             // 谁、什么时候、改了什么、结果如何
        return Status::Ok();
    }
    void rollback() {
        // 逆序 abort：后 prepare 的可能依赖先 prepare 的资源
        for (auto it = prepared_.rbegin(); it != prepared_.rend(); ++it)
            (*it)->abort();       // abort 也不允许失败，否则无路可退
        prepared_.clear();
    }
};
这个「两阶段」结构是整节的骨架：prepare 阶段的失败是廉价的（还没有任何东西生效，撤销就是释放预留），commit 阶段的失败是昂贵的（部分生效，且回滚本身也可能失败）。完整展开见 §8.2 第 7 题。

4.2 running / candidate：为什么需要两份配置

NETCONF（RFC 6241）定义了多个配置数据存储（datastore）。它们的关系常被误解为「草稿箱和正式版」，真正的价值要具体一点：

datastore含义可写掉电是否保留解决什么问题
running当前正在生效的配置取决于设备能力；支持 :candidate 时通常不允许直接改不一定（很多实现下它在内存，掉电看 startup）「设备现在是什么样」的唯一真值
candidate待提交的配置副本，可反复编辑✅ 可写（<edit-config> 目标）否（通常掉电丢弃）① 多次编辑攒成一次原子提交；② 提交前可整体校验；③ 反悔只要 <discard-changes>
startup下次启动时加载的配置✅（<copy-config>）✅ 是把「本次生效」和「永久保存」解耦——改错了不 copy，重启即恢复

关键收益在 candidate 那一行的第一条：把「多次编辑」和「一次生效」分开。建一个小区往往要改十几个节点，若每次 <edit-config> 都立刻生效，这十几步之间的每个中间态都是「不完整的配置」，设备可能在任何一个瞬间尝试按半成品运行。

confirmed commit（RFC 6241 §8.4）是「改配置把自己关在门外」这个经典事故的标准解法。它对远程站点（基站、边缘节点）尤其重要——一次现场维护的成本可能是几千块和一整天。

「窗口很短，可以忽略」数据面侧是微秒级，但端到端要算上管理面解析、控制面状态机、硬件表项下发，可能到几十毫秒甚至更久把「配置未生效」误判成「配置下错了」，重复下发把问题变复杂
「版本号 + 回执」是配置系统里性价比最高的一个设计：网管能显示「下发中 / 已生效」，自动化测试能据此等待而不是 sleep(1)，运维能一眼看出是哪个模块卡住了。

手段做法解决哪一类风暴代价 / 坑
去抖 / 保持时间（hold-off）条件成立后先等 N 秒，仍然成立才上报；恢复同理等 M 秒抖动型：链路快速起落（flapping）产生的成对告警发现时间推迟 N 秒；N 要按级别分档（严重告警 N 小）

抑制规则本身成了故障

① 关联抑制只能覆盖已知的故障模式，所以限速 + 溢出摘要这层兜底不能省，它不依赖任何领域知识。② 根因型告警必须定成高级别——判据是「它能不能解释别的告警」，而不是「它自己有多严重」。③ 被抑制的告警要本地留存可查。

05

线程 / 队列 / IPC 模型

模块怎么串起来

  • 线程分工：数据面独占核轮询，控制面/管理面用事件循环。
  • 队列解耦：模块间传消息，避免直接调用带来的耦合与锁。
  • IPC：进程间用共享内存、Unix socket；跨机用网络。
Message Passing 架构：每个模块是一个"处理消息的黑盒"，只通过队列收发消息。天然可测试、可扩展、易并行——telecom 软件的常见范式（类 Actor 模型）。

5.1 三种线程模型：适用与代价

「该开多少线程、怎么分工」只有三个有意义的答案。它们不是「新旧优劣」的关系，而是分别针对三类完全不同的负载：

维度① 每连接一线程② 线程池 + 事件循环③ 分片 shared-nothing
结构来一个连接 pthread_create 一个，阻塞式读写N 个线程各跑一个 epoll 循环；或一个 acceptor + 一个工作池按会话键哈希固定分到 M 个 worker，各自独占自己那份状态
代码可读性✅ 最好——逻辑是顺序的，不用手写状态机⚠️ 一切变成回调，逻辑被切碎（这正是 §3 的用武之地）⚠️ 同②，还要考虑分片键
连接规模上限❌ 几千——每线程默认 8 MB 栈，加上调度器压力✅ 十万级以上✅ 十万级以上
每连接内存❌ 栈 + TLS，常在几十 KB 到 MB 量级✅ 只有会话对象，几百字节到几 KB✅ 同②
多核扩展性⚠️ 靠调度器，负载不均且切换多⚠️ 取决于共享了什么——共享会话表就退化成锁竞争✅ 近线性，只要哈希不倾斜
尾延迟❌ 差——线程数远超核数时一次调度延迟就是毫秒⚠️ 中等——一个慢回调阻塞该线程上所有连接（队头阻塞）✅ 好——本核只服务本片
阻塞操作友好度✅ 随便阻塞，唯一的杀手锏❌ 一次同步 IO 就毁掉整个循环❌ 同②，且更严格
典型用武之地连接数少、每连接逻辑复杂且必然阻塞——管理面的 NETCONF 会话连接数大、逻辑以 IO 为主——控制面信令、南北向接口包速率高、每包耗时短、状态可按键切分——数据面转发

第三种模型还要补一句：分片键的选择决定成败。按五元组哈希保证同一条流永远落在同一个 worker 上，「连接状态」天然无需共享；但要小心倾斜（一条大象流打满某个核）和重分片（worker 数变化时会话被搬到别的核，搬迁期间的一致性是个真问题）。见 通信服务的高并发。

5.2 队列：模块之间只传消息

模块之间只有两种连接方式：直接函数调用（纳秒级）或队列传消息（几十纳秒到微秒级）。跨平面、跨线程的边界上队列几乎总是唯一正确的选择，理由不是性能而是时间尺度隔离：

❌ 直接调用把两个时间尺度焊死了

控制面线程调用数据面的函数，意味着数据面的数据结构现在被两个线程碰了——要么加锁（毁掉确定性），要么祈祷。
反方向更糟：数据面在包路径上调用控制面的函数，只要那个函数里有一次日志、分配或锁，67 ns 的预算就被毁掉了。而这条调用链会在演进中变长——今天很轻，三个月后有人加了一行 log()。

✅ 队列把「谁在什么时间尺度上跑」变成显式的

入队的耗时可预测且有上界，且与消费者做什么完全无关——消费者慢，队列会积压（可观测），但生产者的时延不受影响。
更重要的是：队列长度是一个天然的指标，它直接告诉你「这两个模块的处理能力是否匹配」，而函数调用什么都不会告诉你。§7.1 的背压完全建立在这一点上。

队列类型入队+出队开销（无竞争，量级）用在哪注意
SPSC 无锁环~20~50 ns（批量摊薄后更低）数据面 worker ↔ 旁路统计线程最快也最简单，但「只有一个生产者」这个前提要用 assert 钉住
MPSC 无锁环~50~150 ns（随生产者数恶化）多个控制面模块 → 一个上报线程生产者侧要 CAS，竞争激烈时明显变慢
MPMC 无锁环~100~300 ns，竞争下更差通用工作队列能拆成 N 条 SPSC 就别用它——消除竞争比结构优化有效得多
互斥锁 + 条件变量队列无竞争 ~50 ns；需要唤醒时 1~10 µs管理面、任何 ms 尺度的模块毫秒尺度上完全够用，而且比无锁队列好写好调试十倍
选队列的顺序是：先问时间尺度，再问几个生产者几个消费者，最后才考虑无锁。控制面与管理面之间用一把普通的 mutex + condition_variable 就好，换成无锁环唯一的收获是「省了几微秒」，而那两个模块的预算是几十毫秒。无锁队列的成本主要不是性能，是维护性：内存序写错的 bug 在 x86 上能潜伏几个月，换到 ARM 上五分钟就崩（见 高性能通信）。

5.3 为什么电信设备偏爱多进程而不是多线程

多线程共享地址空间，通信便宜、开发方便，为什么电信设备普遍走多进程？把「一个野指针」这件事在两种架构下的后果画出来，答案就有了：

维度多线程（单进程）多进程对电信设备意味着什么
故障隔离❌ 一个线程段错误，整个进程死；野指针能写坏任何模块的数据，破坏点与崩溃点可能隔几分钟✅ 崩溃被地址空间挡住直接决定可用性等级。「管理面的 bug 不能影响业务」这条要求，多线程从架构上就做不到
独立重启❌ 要么全重启，要么「线程重建」——但地址空间已被污染，重建的线程跑在不可信的堆上✅ 单独重启一个进程，由守护进程拉起把「重启恢复」这条最可靠的兜底手段从「全网元中断」降级为「某个功能短暂不可用」
灰度升级❌ 换二进制 = 换整个进程 = 业务中断✅ 可以只升级管理面；也可新旧并存再切换（§7.4）决定「打一个补丁要不要申请业务割接窗口」——运营商最在意的事之一
资源约束⚠️ 只能靠自律✅ 每进程单独设 cgroup 内存上限、CPU 配额、RLIMIT_*管理面泄漏时被 OOM killer 干掉的是管理面，不牵连数据面
安全边界❌ 整个进程一套权限✅ 按最小权限分别降权：只有管理面需要读证书私钥一个被攻破的对外接口不等于「设备被完全控制」
编译选项 / 语言❌ 全进程统一✅ 数据面 -fno-exceptions + 自定义分配器，管理面正常 C++ 甚至 Python让 §2.2 的纪律被编译器强制，而不是靠代码评审
通信成本✅ 一次函数调用，纳秒级❌ 要走 IPC（§5.4）；共享内存能压到接近线程，但要自己管序列化与生命周期多进程唯一的实质代价，也是共享内存在电信设备里如此普遍的原因
调试复杂度✅ 一个 gdb 看全部❌ 要同时 attach 多个进程；core dump 也是多份用统一 trace ID 贯穿各进程（§7.3）可大幅缓解
共享内存是这个取舍的折中——保留地址空间隔离（野指针写不到对方的堆），只在一块显式映射的区域里共享数据，把「意外共享」压缩成「有意共享」。

「裸指针不能跨进程」在代码评审里极难发现：用 MAP_FIXED 强行映射到同一地址时它能正常工作，直到某天开了 ASLR 或换了机器。共享区里只能存相对段起点的偏移。
这些做法都有名字。"传消息不共享内存"就是 Active Object（替代"每会话一把锁"的 Monitor Object）；"收包线程 + 业务线程 + 中间队列"就是 Half-Sync/Half-Async（另一条路是无队列的 Leader/Followers）。
模式取舍、Reactor 与 Proactor 的本质差异、四个高发反模式 → 通信软件设计模式；分片、背压、横向扩展 → 通信服务的高并发。

① 时间尺度在一次动作里跨了六个数量级

第 8 步是微秒，第 6 步是秒——这就是 §1.2 那个结论的实证：任何用一套同步调用把这十步串起来的设计，都会被最慢的那一步（等 RU 应答几秒）逼着让最快的那一步也等几秒。
所以这条链必须是异步的，而异步就意味着「中间态」，中间态就意味着「必须有状态机」（§3）和「必须有超时」。

② 失败的代价随步骤单调递增

实用的检查方法：逐行问「这一步失败了会怎样」。答不出来的行就是架构里的黑洞——真实事故几乎总发生在这些行上。

07

架构原则

四条会在生产上兑现的规则

五条概括：按平面分治、解耦（消息队列隔离模块）、热路径极简、显式状态机（覆盖超时与异常）、可观测（日志与追踪放在非热路径）。下面四节展开的是真正会在生产上兑现代价的四条——每一条都有一个「看起来做了、实际没做」的常见版本。

7.1 背压必须端到端

背压（backpressure）：下游处理不过来时，把「慢」这个信号反向传播给上游，让上游减速或明确丢弃，而不是让数据在中间无限堆积。它的反面不是「不减速」，而是「在某个看不见的地方悄悄堆积，直到内存耗尽或时延爆炸」。
生活类比：高速公路收费站堵了。没有背压：车辆继续从各入口涌入，整条高速变成停车场。局部背压：只在收费站前放一个「前方拥堵」的牌子，入口照常放行——车流只是堵在更靠前的位置，总量没变。端到端背压：一直传到入口匝道的红绿灯，源头就限流。
关键洞见在中间那种：只在一个环节加背压，等于把队列推到别处，而不是消除它。
背压手段怎么工作适合的边界坑
阻塞写入队列满时生产者阻塞，直到有空位管理面内部——阻塞几毫秒无所谓❌ 绝不能用在数据面和控制面：一阻塞就是把上游的时限预算交给下游支配，且极易死锁（A 等 B 的队列，B 等 A 的队列）
返回失败 + 上游决策队列满时立即返回 EAGAIN，由上游决定丢弃还是缓存控制面之间；数据面首选上游必须真的处理这个返回值。「返回值被忽略」是背压失效最常见的原因，而编译器不会警告
信用/窗口（credit）下游告诉上游「我还能收 N 个」，上游用完就停跨进程、跨设备边界信用回收消息丢失会永久停摆，必须有超时重新同步
准入控制（admission）在入口就限流：超阈值直接拒绝新会话，而不是接进来再慢慢死系统最上游——唯一真正解决问题的那一层阈值要按「能稳定服务的容量」定，不是按「峰值扛得住的容量」
队列水位 + 优先级丢弃超过高水位开始丢低优先级，超过更高水位才丢高优先级数据面要留迟滞（高低水位不同），否则会在阈值附近抖动
无界队列是架构里最危险的默认值。一个 std::queue 天生无界，写的时候感觉「很安全，不会丢东西」，实际是把「丢弃」这个决定推迟给了 OOM killer——而它的决定是「杀掉整个进程」。所有跨模块队列都必须有容量上限，满了之后的行为必须被显式设计过，并同时观测当前深度与历史最高水位——只看当前深度会漏掉「瞬时冲到 95% 又回落」这种最危险的情况。

7.2 优雅降级：过载时保住最重要的那部分

背压回答「压力怎么传」，降级回答「压力传到源头之后，砍掉什么」。核心问题是：过载时的行为必须是设计出来的，而不是「自然发生」的。

过载时的行为没有设计过的版本（自然发生）设计过的版本
丢什么先到先服务，队列满了丢最新的——紧急信令和普通数据一视同仁按优先级：保信令、保已建立会话，丢新建请求、统计上报、低优先级数据
时延随队列长度线性增长，可以涨到几秒——此时处理出去的包早就没有意义了队列有上界 ⟹ 时延有上界；超过「有效期」的报文主动丢弃
吞吐曲线过载后吞吐反而下降（忙于处理已超时的请求、重试、打日志）——拥塞崩溃过载后吞吐保持在平台值，多出来的负载被明确拒绝
恢复负载降回来却恢复不了——积压要几分钟消化，期间还在超时重试丢弃是即时的，队列不积压，负载一降立刻恢复
可见性只能从「时延变高」间接推断有明确的「降级中」状态与告警
「处理一个已经超时的请求，比丢弃它更糟。」排队 5 秒的信令，对端早就重发了，处理它没有价值还占用了本可服务新请求的资源——这正是拥塞崩溃的机理：系统 100% 忙碌，有效吞吐接近零。入队打时间戳、出队检查有效期，是过载防护里性价比最高的几行代码。

7.3 可观测性必须设计进去

「先做功能，上线后再补监控」是通信软件里最贵的技术债之一。原因很具体：事后能补的只有「进程外能看到的东西」——CPU、内存、网卡计数。而排查真正的问题需要「进程内的状态」，那些数据结构如果没预留出口，事后就只能靠改代码 + 重启 + 等复现，而生产事故等不起。

层次内容成本什么时候必须有
计数器（metrics）收/发/丢按原因分桶；各状态的会话数分布；队列深度与历史高水位；配置版本号包路径上 ~1 ns（§2.4）永远开着。唯一能持续采集的一层
状态迁移轨迹每次 FSM 迁移一条 32 字节定长记录，写每核环形缓冲~5~10 ns控制面永远开着——排查状态机问题的唯一线索
分布式追踪（trace ID）动作从管理面进来时生成 ID，随消息穿过所有进程每条消息多 8~16 字节多进程架构下必须有，否则 §6 那十步的日志散在三个进程里拼不起来
结构化日志非热路径上的事件日志，带 trace ID 与结构化字段微秒级控制面/管理面开着；数据面包路径上禁止（§2.2）
按需抓包 / 采样条件触发的报文镜像正常包 ≈ 0，异常包一次拷贝常态开「异常触发」那一档
最实用的一条经验：「计数器要成对，并且要能配平。」旁路线程里定期核对 进入次数 == 离开次数 + 当前数量。它能发现「你根本没想到会发生」的那类问题：§3.6 的会话泄漏、§2.4 的漏计丢包，都是靠等式对不上而不是靠日志发现的——成本几乎为零，覆盖的却是「未知的未知」。

7.4 升级与回滚：热重启与状态迁移

电信设备的可用性常以「年不可用时间」计。这个量级下「升级要重启、重启中断 30 秒」是不可接受的——一年升级 12 次就是 6 分钟，光升级一项就吃掉大部分预算。所以升级方式本身就是架构的一部分：

方式做法中断时间状态怎么办回滚适合
整机重启停服务、换二进制、起服务数十秒到几分钟全丢，从配置重建换回旧二进制再重启有冗余保护、或允许割接窗口时
进程级重启只重启一个平面的进程，守护进程拉起该平面几百毫秒，其它零中断从配置和对端重建同上，但影响面小得多管理面升级的默认做法——它本来就状态可重建
进程热重启（优雅交接）新进程启动 → 迁移状态 → 迁移监听 fd（SCM_RIGHTS）或共享内存所有权 → 旧进程退出毫秒级甚至零显式序列化后交接——全部难点所在新进程起不来 → 旧进程继续跑，零影响控制面；有连接状态但状态量可控时
主备切换备板已同步状态，切流量过去，再升级原主亚秒到数秒，取决于同步方式靠持续的主备状态同步切回去核心网元；成本最高，可用性也最高
就地代码热补丁运行期替换函数（livepatch 类机制）接近零完全保留卸载补丁紧急修复单个函数；不能改数据结构布局，适用面很窄

热重启听起来最美，但它把复杂度全部压到了「状态迁移」这一步上：

状态快照就是一种和「未来的自己」通信的协议，约束和协议演进一模一样：格式带版本号；新增字段一律可选且有默认值；绝不复用或改变已有字段的含义；遇到不认识的字段要能安全跳过（见 二进制协议设计）。也正因为这笔代价真实存在，很多产品只对关键状态做热重启。
主备同步、故障检测与切换判据、可用性指标怎么算 → 通信系统的性能、可靠性与高可用；容器化环境下的滚动升级与就绪探针 → 电信云原生。
🎯 本篇要点回顾
  • 三个平面的时间尺度差三到六个数量级（µs / ms / s）——连「等待」这个动作都不能共用一种实现，这才是「必须分层」的真正理由
  • 数据面是一段被剥夺了语言特性的代码：run-to-completion + 轮询，禁止分配/加锁/日志/系统调用，观测只能靠 per-core 计数器与旁路采样
  • 控制面到处是状态机：表驱动的价值在于让「漏掉的格子」可见；状态爆炸用分层治重复、用正交区域治相乘
  • 管理面的核心是事务性：两阶段提交把失败挤到 prepare 阶段；commit 返回 ≠ 数据面已生效，要用版本号回执把窗口变可观测
  • 电信设备偏爱多进程——故障隔离、独立重启、灰度升级三条都直接对应可用性指标；代价只有 IPC
  • 背压必须端到端，且终点必须是一个「有权拒绝」的地方

从平面划分到开放式架构设计

8.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础数据面、控制面、管理面的时间尺度分别是什么量级？这个差异为什么会直接决定软件架构？

    量级：数据面 亚微秒 ~ 数微秒（每秒百万级到千万级触发）；控制面 数百微秒 ~ 数十毫秒（每秒千级到万级）；管理面 数百毫秒 ~ 数十秒（每分钟几次）。首尾差三到六个数量级。

    为什么它决定架构——关键是「等待」这个最基本的动作不能共用一种实现：

    数据面只能轮询
    一次线程唤醒是 1~10 µs，而它的全部预算也就几微秒。所以宁可让一个核 100% 空转，也不能付这一趟。
    管理面必须阻塞
    它可能要等一次数据库查询或对端应答几秒钟。用轮询等于白烧一个核换来毫无意义的响应速度提升。
    推导链
    「等待方式不可调和」⟹「线程模型不可共用」⟹「调度策略、内存策略、错误处理都得分开」⟹「干脆分进程」。顺序反过来讲（先说职责清晰再说性能）就是背书。

    其它跟着分叉的维度：调度策略（SCHED_FIFO 独占隔离核 / SCHED_FIFO 中优先级 / SCHED_OTHER）、内存策略（启动全预分配+mlockall / 对象池 / 随便 new）、错误处理（计数丢弃 / 状态机重试 / 事务回滚）、失败影响半径（本核流量 / 进行中的信令 / 只影响网管可见性）。

  2. 基础数据面为什么禁止动态内存分配？「malloc 很慢」这个说法准确吗？

    先纠正那个说法：malloc 的快路径并不慢——glibc tcache 命中时只要 15~30 ns。所以「因为慢」是个不准确的理由，真正的理由是它有不可预测的长尾：

    • tcache 不命中 → 走 arena，多线程时可能抢锁；
    • arena 不够 → 走 brk/mmap，变成系统调用；
    • 新拿到的页首次写 → minor page fault，1~3 µs；
    • 长期运行 → 碎片化，让上面几条越来越容易发生。

    放到预算里看：10 GbE 线速小包（14.88 Mpps）的每包预算是 67 ns。一次走 mmap + 缺页的分配是 3 µs，等于把 45 个包的预算一次烧光（超支 4500%）。

    现象
    P50 完美而 P99.9 高一两个数量级；重启后头一分钟尤其差；RSS 缓慢爬升被误判成内存泄漏。稳态压测复现不出来——因为被当成「预热期」丢掉的那一段正是问题本身。
    替代做法
    启动时预分配定长对象池 + 预热（MAP_POPULATE 或手工写每页）+ mlockall；运行期只做「取/还」；池空了就丢包并计数，绝不临时扩容。

    加分点是指出三个隐形违规：std::function 捕获过大时会堆分配；std::map::operator[] 在 key 不存在时会插入（一次「查询」变成一次分配）；首次调用动态库函数时的惰性符号解析会拿全局锁（用 -Wl,-z,now 或静态链接解决，这个坑的特征是「只有第一次慢」）。

  3. 基础什么是 run-to-completion？数据面为什么默认选它而不是流水线？

    定义：一个包从收进来到发出去的全部处理，都在同一个线程、同一次调用栈里完成，中途不入队、不移交、不等待。对立面是 pipeline——把处理切成若干级，每级一个线程，级间用队列传递。

    选它的四个理由（按重要性排序）：

    Cache 局部性
    包头、会话上下文、查表结果全程留在本核 L1/L2。流水线每跨一级就要把 cache line 从上一个核搬过来，40~100 ns/行——而每包预算可能只有 67 ns。
    没有木桶效应
    流水线的整体吞吐等于最慢那一级，配平极难且会随流量特征漂移。RTC 下每个核是完整独立的一条链，一个核慢只影响自己那份流量。
    扩展方式更简单
    加一个核 = 复制一条完整流水线（shared-nothing 横向扩展），不需要重新切分级。
    时延分布更紧凑
    没有级间排队，抖动源少。

    什么时候反而该用流水线：某一级必须绑定到不可移动的硬件资源（加密卡、专用加速器在特定 NUMA 节点），或某一级耗时远大于其它级且需要单独扩容。判据是「这一级能不能搬到本核来做」——能，就别切。

    还要补一句 RTC 的配套要求：既然一个包全程不换手，「等包」也只能由 worker 自己做，所以 RTC 天然意味着轮询。而轮询意味着 CPU 恒定 100%，此时「CPU 使用率」不再是负载指标——真正的指标是「每轮循环处理了几个包」和「空轮占比」。

  4. 基础为什么通信代码里到处是显式状态机？用一堆布尔标志不行吗？

    两个理由，缺一个都还能用 if 硬扛，凑齐就只能上状态机：

    ① 协议规范本身就是状态机
    TCP 的十一个状态、NETCONF 会话、RRC 的 IDLE/INACTIVE/CONNECTED——标准里画的就是状态转移图。实现写成布尔标志，等于每次对照规范排查都要在脑子里做一次翻译，而这个翻译过程正是 bug 的产地：规范说「只有 X 状态收到 Y 才合法」，代码写成 if (a && !b && timer_running)——两者是否等价，没人能一眼看出来。
    ② 必须处理超时与乱序
    通信是异步 + 不可靠的：对端可能不回、回得很晚、在你放弃之后才回、或者顺序颠倒。于是每个「等待」都要配定时器，每个状态都要回答「在这里收到那条迟到的消息怎么办」。

    但最本质的一句是：状态机的价值不在于表达合法路径，而在于把「非法路径」变成可枚举、可审查的东西。一个 6 状态 × 10 事件的转移表有 60 个格子，你可以逐个问「这里收到这个事件该怎么办」；同样的逻辑写成 if，你连「一共有多少种情况」都数不出来。

    具体到布尔标志的问题：N 个标志意味着 2^N 种组合，其中绝大多数是非法组合，但代码里没有任何地方声明过哪些非法。于是「connecting=true 且 closed=true」这种不该存在的状态可以静默出现，而且没人知道它出现过。状态机用一个枚举把状态空间从 2^N 压到 N，非法状态在类型层面就不存在了。

8.2 中级

  1. 中级状态机的状态爆炸怎么控制？分层状态机和正交区域分别治什么？

    先说爆炸的机理：状态数随「正交的关注点」个数指数增长。一个 4 状态的会话机，加上「加密（3 态）× 链路（2 态）× 配置更新（2 态）」，天真做法是把它们乘进状态名 → 4×3×2×2 = 48 个状态，转移表 48×8 = 384 格，其中绝大多数是复制粘贴。

    分层状态机（HSM）—— 治「重复」
    症状：好几个状态对同一个事件反应完全一样（PEER_DOWN 在任何状态下都要清理回 IDLE），同一段逻辑被复制了 N 遍。
    做法：给状态加父子关系，事件先给当前状态处理，它不处理就交给父状态（行为继承）。把 PEER_DOWN 放在根状态上，48 个格子塌缩成 1 个。
    代价：进入/退出要沿层级链依次执行 exit/entry 动作，顺序容易写错；「事件被谁处理了」不再一眼可见——所以 HSM 必须打印「事件在第几层被消费」，否则调试成本反而上升。
    正交区域 —— 治「相乘」
    症状：几个关注点互相独立，却被硬乘进一个状态空间。
    做法：拆成几个并存的小状态机各自独立收事件。4+3+2 = 9 个状态，而不是 4×3×2 = 24。
    代价：区域之间总有少量真实耦合（「必须加密完成才能进 ACTIVE」），这部分要用显式的守卫或区域间事件表达，不能偷偷读对方的状态变量——那会让两个机悄悄变回一个机，还是隐式的那种。

    判据：问一句「这两个维度会不会同时变化，且变化互不影响？」——会 → 正交区域；不会，只是几个状态碰巧对某事件反应相同 → 分层。选错的代价是「重构一次比重写还贵」。

    最被低估的第三招
    把「数据」从「状态」里赶出去。「重试了几次」应该是 retry_count 字段而不是 WAIT_RETRY_1/_2/_3 三个状态。判据：如果两个「状态」之间没有不同的转移行为，只是携带的信息不同，那它们就不该是两个状态。
  2. 中级timing wheel 解决什么问题？为什么控制面用它而不是最小堆？

    先看控制面定时器的负载画像，这决定了一切：① 数量巨大（每个会话每个流程都挂一两个，几万到几十万）；② 绝大多数在到期前就被取消（发出去的请求 99% 以上会在超时前收到应答）；③ 精度要求不高（毫秒级够用）。

    结构添加取消取最早到期
    有序链表O(n)O(1)O(1)
    最小堆O(log n)O(log n)✅ O(1)
    Hashed timing wheel✅ O(1)✅ O(1)❌ 要扫描找下一个非空槽

    关键在「取消」这一列：既然定时器的正常归宿是被取消而不是到期，那么取消的复杂度就是主导成本。时间轮的取消只是侵入式链表的一次摘除（O(1) 且无分配），最小堆则是一次 O(log n) 的堆调整。

    最小堆什么时候更好：定时器数量不多、但需要精确知道「下一个什么时候到期」——因为事件循环要用它来设置 epoll_wait 的超时。时间轮在这一点上是弱项（要扫描）。所以实践中常见的组合是：海量的会话级保护定时器用轮，少量的高精度定时器用堆或 timerfd。

    三个实现坑
    ① 到期回调只能入队，不能直接 dispatch()——直接调等于在遍历链表时执行任意用户代码，而那段代码可能取消或新增定时器，正在遍历的链表被就地修改。
    ② 用时间差值补 tick，不要依赖「每毫秒被调用一次」——线程被抢占 200 ms 是常态，依赖调用频率会让所有定时器集体漂移且再也追不回来。
    ③ 精度是「向上取整到一个 tick」，所以定时器时长必须显著大于 tick；用 1 ms 轮实现 2 ms 超时，误差可达 50%。
  3. 中级配置为什么要有事务性？两阶段提交在网元上怎么落地？

    为什么要：没有事务时，一次「建小区 + 配三个承载 + 开射频」在第二步失败，设备会停在「小区已建、承载没配、射频未开」这个规范里根本不存在的状态。后果不是「这次配置没成功」，而是网管视图与设备实际状态永久不一致，下一次配置在这个不一致上继续叠加，最终只能重启。

    四个阶段，失败代价单调递增：

    • ① 语法/模型校验（YANG 类型、range、mandatory）→ 失败零代价，设备一点没动；
    • ② 语义校验（must/when/leafref、业务规则）→ 同样零代价，要尽量把失败都挤到这一阶段；
    • ③ prepare：各模块「预留但不启用」（分配 ID、占住表项/内存/硬件通道），返回「我能做到」→ 失败则逆序 abort；
    • ④ commit：让预留真正生效（切指针、下发硬件表项）→ 这里失败最麻烦，部分已生效。
    核心设计原则
    把所有可能失败的操作都挪到 prepare 阶段，让 commit 只剩下不会失败的动作（切一个指针、翻一个标志位）。因为 prepare 的失败是廉价的（还没生效，撤销就是释放预留），commit 的失败是昂贵的（部分生效，且回滚本身也可能失败）。
    不能保证 commit 不失败时
    必须准备「重启该进程恢复到已知状态」这条兜底路径。很多电信设备确实是这么做的——这也解释了为什么要把管理面单独放一个进程：重启它不影响业务。
    最常被漏掉的：落盘的原子性
    内存里的事务做得再漂亮，如果持久化是「打开 → 写 → 关闭」，写到一半掉电就会留下半个配置文件，设备起不来且现场无线索。正确写法：写临时文件 → fsync(fd) → rename() → fsync(dir_fd)。rename 在同一文件系统内是原子的；最后那次对目录的 fsync 同样不能省。

    补充一个实用机制：confirmed commit（RFC 6241 §8.4）——带超时地提交，N 秒内没有再次确认就自动回滚。它是「远程改配置把自己关在门外」这个经典事故的标准解法。要点是回滚定时器必须在设备本地（不能依赖网管，因为「网管连不上」恰恰是它要解决的场景），且回滚要回到提交前的完整快照而不是反向执行变更。

  4. 中级「配置下发成功」和「数据面已生效」之间为什么有窗口？怎么处理？

    窗口的来源是数据面的纪律：数据面不许加锁（§2.2），所以管理面改配置时不能直接改数据面正在用的结构，只能「发布一份新的，让 worker 自己在安全点切换」：

    • 管理面构造全新的 Config 对象，用一次 atomic exchange 发布指针；
    • 每个 worker 在自己下一轮循环开头做一次 acquire load，读到新指针；
    • 整批包用同一份配置（保证批内一致）；
    • 旧配置不能立刻释放，要等所有 worker 都经历过一次静默期（RCU / epoch / hazard pointer）。

    于是产生四个必须纠正的误解：

    「commit 返回成功 = 已生效」
    它只表示管理面把新版本发布出去了。数据面要到下一轮循环才读到，控制面可能还要走一遍状态机。现象：自动化测试「配置完立刻验证」间歇失败。
    「所有 worker 同时切换」
    不会。16 个核各自在自己的循环边界切换，彼此相差一轮（微秒到几十微秒）。大多数场景无害，但「先分类后计费」这类跨包一致性要求高的场景会出错。
    「旧配置可以立刻 delete」
    绝对不行——use-after-free，且崩溃点离释放点很远，极难定位。
    「窗口很短可以忽略」
    数据面侧确实是微秒级，但端到端要算上管理面解析、控制面状态机、硬件表项下发，可能到几十毫秒甚至更久。
    正解：把窗口变成可观测、可等待的东西
    给每份配置一个单调递增的版本号，每个消费方（每个 worker、每个模块）上报「我当前生效的版本」。于是「是否已全网生效」变成一个可直接查询的条件：min(所有消费方的生效版本) >= 目标版本。网管可以显示「下发中/已生效」，自动化测试可以等待而不是 sleep(1)，运维能一眼看出是哪个模块卡住。成本极低，收益贯穿整个生命周期。

8.3 高级

  1. 高级电信设备为什么偏爱多进程而不是多线程？代价是什么？

    高分答案的第一句应该是：「隔离」和「共享」是同一件事的两面。多线程之所以通信便宜，正是因为它没有隔离；多进程之所以有隔离，正是因为它没有共享。所以问题不是「哪个更好」，而是「在这条边界上，我更需要哪一个」。

    六条收益，每一条都直接对应可用性指标：

    • 故障隔离：一个线程段错误整个进程死，而且野指针能写坏任何模块的数据、破坏点与崩溃点可能隔几分钟。分进程后，管理面解析畸形 XML 崩了，数据面一个包不丢。「管理面的 bug 不能影响业务」这条要求，多线程从架构上就做不到。
    • 独立重启：把「重启恢复」这条最可靠的兜底手段，从「全网元中断」降级为「某个功能短暂不可用」。
    • 灰度升级：可以只升级管理面而数据面完全不动——直接决定「打一个补丁要不要申请业务割接窗口」。
    • 资源约束：每个进程单独设 cgroup 内存上限，管理面泄漏时被 OOM killer 干掉的是管理面，不牵连数据面。
    • 安全边界：按最小权限分别降权——只有管理面需要读证书私钥。
    • 编译选项分离：数据面 -fno-exceptions -fno-rtti + 自定义分配器，管理面正常 C++ 甚至 Python。让 §2.2 的纪律被编译器强制，而不是靠代码评审。
    代价
    只有一条实质代价：通信要走 IPC。其余是调试复杂度（要 attach 多个进程、core dump 多份，用统一 trace ID 可大幅缓解）和部署脚本更复杂。
    结论要给出粒度
    平面之间要隔离（分进程），平面内部要共享（多线程）。典型网元是「3~5 个进程，每个进程内部若干线程」，不是「一个进程几十个线程」，也不是「几十个微进程」。
    再补一句会更完整：共享内存是这个取舍的折中——保留地址空间隔离（野指针写不到对方的堆），只在一块显式映射的区域共享，把「意外共享」压缩成「有意共享」。
  2. 高级进程间通信选共享内存还是 socket？判据是什么？共享内存有哪些隐性成本？

    三个判据，按顺序问：

    ① 时间尺度够不够
    预算微秒级 → 只能共享内存（socket 一次往返就吃掉预算）。预算毫秒级及以上 → 直接 socket，省下的几微秒对你毫无意义。
    ② 数据量大不大
    大块数据（IQ 采样、抓包缓冲）→ 共享内存，socket 要拷两次。小控制消息（几十到几百字节）→ socket，拷贝可忽略。
    混合做法最常见：数据放共享内存，通过 socket / eventfd 传一个「偏移 + 长度」的句柄。
    ③ 需不需要天生的流控与故障检测
    这是共享内存最大的隐性成本。socket 白送你「对端慢了我会阻塞」「对端死了我会知道」；共享内存两样都要自己写，而这两样恰恰最容易写错、最难测试。所以默认选 socket，只在被时延或数据量逼到墙角时才上共享内存。

    量级参考（单向，随机器差异很大）：共享内存 + 轮询 ~100~300 ns；共享内存 + eventfd 唤醒 几微秒（唤醒成本主导）；Unix 域套接字 几微秒到十几微秒；回环 TCP 十几到几十微秒。

    共享内存最容易被低估的三笔账：

    生命周期
    写端崩溃时共享内存段不会消失（POSIX shm 的生命周期跟着文件系统而非进程），里面可能停在写到一半的状态。读端必须能识别「这份数据不完整」——靠序列号双写校验，不能靠祈祷。
    没有 EOF
    对端死了，你的轮询循环永远读到空，看起来和「对端很闲」一模一样。必须配心跳字段（写端周期更新时间戳，读端检查它有没有停止增长），否则故障以「莫名其妙不工作了」的形式出现。
    指针不能跨进程
    两个进程映射同一段共享内存的虚拟地址通常不同，里面绝不能存裸指针，只能存相对段起点的偏移。这一条在评审里极难发现——用 MAP_FIXED 时它能正常工作，直到某天开了 ASLR 或换了机器。

    顺带一个 Unix socket 的优势值得知道：它能用 SCM_RIGHTS 传递文件描述符，这是进程热重启时交接监听套接字的标准手段（§7.4）。

  3. 高级为什么说背压必须端到端？只在一个环节加背压会怎样？

    因为局部背压不消除队列，只是把队列推到别处。看一条典型链路 网卡 RX ring → worker 队列 → 编码队列 → 发送队列 → 网卡 TX ring，当发送侧变慢时：

    只在「发送队列」加背压
    发送队列有界不涨（看起来解决了）→ 编码队列开始堆积 → worker 队列跟着堆积 → RX ring 溢出，网卡丢包。
    结果：内存涨、时延涨、最后还是丢包，而且丢在最不该丢的地方——网卡不认识业务优先级，它把紧急信令和普通数据一起丢了。
    端到端背压
    压力一路传到入口的准入判断，在那里按优先级丢弃低优先级流量、保住信令，并递增明确的丢弃计数。结果：内存有界、时延有界、丢弃是受控且可解释的。

    真正拉开差距的一层是：背压的终点必须是一个「有权拒绝」的地方。如果链路上每一环都只会把压力传给上一环，而最上游那一环没有拒绝的权力（比如它是一张网卡，只会溢出丢包），那整条背压链只是把队列搬了个家。所以设计背压的第一步不是加队列水位，而是先回答「谁有权说不」——通常是准入控制或限流器。找不到这个点，说明架构里缺了一层。

    机制选择要看边界
    阻塞写入只能用在管理面内部——用在数据面/控制面就是把上游的时限预算交给下游支配，且极易死锁（A 等 B 的队列，B 等 A 的队列）。返回失败让上游决策是数据面首选，但「返回值被忽略」是背压失效最常见的原因，而编译器不会警告。跨进程/跨设备边界用信用（credit），注意信用回收消息丢失会导致永久停摆，必须有超时重新同步。
    无界队列是架构里最危险的默认值
    一个 std::queue 天生无界，写的时候感觉「很安全，不会丢东西」，实际是把「丢弃」这个决定推迟给了 OOM killer——而它的决定是杀掉整个进程。所有跨模块队列都必须有容量上限，且满了之后的行为必须是被显式设计过的。
    配套两个指标：当前深度（看趋势）和历史最高水位（看是否接近上限）。只看当前深度会漏掉「瞬时冲到 95% 又回落」这种最危险的情况。

    最后补一条与降级的衔接：「处理一个已经超时的请求，比丢弃它更糟。」排队 5 秒的信令，对端早就重发了，处理它不但没价值还占用了本可服务新请求的资源——这正是拥塞崩溃的机理：系统 100% 忙碌，有效吞吐接近零。入队打时间戳、出队检查有效期，是过载防护里性价比最高的几行代码。

  4. 高级设计一个基站（如 O-DU）的软件架构，你怎么分进程？说清依据、边界机制和升级策略。

    这是开放题，考的是有没有一条从约束推到方案的完整链条。建议按下面的顺序讲，不要一上来就画框图。

    第一步：先说约束，不说方案
    三个平面的时限预算是 µs / ms / s，差三到六个数量级；可用性要求高到「升级不能要求业务割接」；管理面要处理来自外部的不可信输入（XML/JSON 解析历来是漏洞高发区）。方案必须从这三条推出来，而不是从「业界都这么分」推出来。
    第二步：给进程划分与依据
    ① 数据面进程（du_fastpath）：每核一个 worker 线程，绑 isolcpus 隔离核，SCHED_FIFO 高优先级，run-to-completion + 轮询。启动时全部预分配 + mlockall，-fno-exceptions 编译。
    ② 控制面进程（du_ctrl）：少量线程 + 事件循环 + 表驱动状态机 + timing wheel，绑几个非隔离核，SCHED_FIFO 中优先级。
    ③ 管理面进程（du_mgmt）：SCHED_OTHER，不绑核，NETCONF 会话可以每会话一线程（连接数只有个位数，这个模型在这里是最优解）。
    ④ 守护/监控进程：拉起与看门狗，本身极简、几乎不可能崩。
    依据一句话：平面之间要隔离所以分进程，平面内部要共享所以多线程。不要分成几十个微进程——那只是把 IPC 成本乘以进程数，收益不再增加。
    第三步：说清每条边界用什么机制
    控制面 ↔ 数据面：共享内存环 + eventfd（µs 级预算，且要传大块数据）；配置切换用「原子发布指针 + worker 在循环边界读 + RCU 式延迟回收」。
    管理面 ↔ 控制面：Unix 域套接字，请求-应答带超时（ms 级预算，白送流控和 EOF 检测，好调试）。
    所有边界都要有：有界队列 + 明确的满时行为、心跳/看门狗、以及贯穿全链路的 trace ID。
    第四步：升级与故障策略
    管理面 → 进程级重启（它本来就状态可重建，重启几百毫秒，业务零影响）；
    控制面 → 热重启 + 状态迁移（版本化快照，新进程就绪确认接管后旧进程才退出，起不来就放弃升级、零影响）；
    数据面 → 尽量不重启；必须换版本时靠板级冗余或割接窗口。
    兼容性要双向：新版本能读旧快照（升级），旧版本也要能读新版本写出来的（回滚）——后者最常被忽略，结果是「能升级但不能回滚」，而回滚恰恰是出问题时唯一的救命手段。
    第五步：主动说出取舍与不做什么
    这一步最加分。① 分进程的代价是 IPC 与调试复杂度，我用共享内存 + 统一 trace ID 来对冲。② 数据面用 shared-nothing 分片，代价是要处理哈希倾斜与重分片，但我不打算支持运行期动态改 worker 数——那个复杂度不值得，改并发度就重启数据面进程。③ 状态机用表驱动而不是 HSM，因为本场景状态数可控，可审查性比表达力更重要。④ 不追求「零中断升级」的全覆盖，只对控制面做热重启——把有限的工程预算花在收益最大的一处。

    最后给一个自检工具（也是 §6 的方法）：拿任意一个跨模块动作（比如一次小区建立）画出「步骤 × 边界 × 机制 × 时间尺度 × 回滚责任」五列。「回滚责任」栏写着「不确定」的行，就是架构里的黑洞；相邻两步时间尺度差三个数量级却用了同步调用的，将来一定超时。这比画一张漂亮的模块框图能发现的问题多得多。
