O-RAN 架构：O-CU / O-DU / O-RU / SMO / RIC

把上一篇的四大理念落成具体网元。O-RAN 在 3GPP 的 CU/DU/RU 之外，新增了两个关键角色：SMO（管理编排） 与 RIC（智能控制器，分 Non-RT / Near-RT）。这一篇建立完整架构图，把每个网元的职责和时间尺度讲清楚。

整体架构图

先看全貌，再拆网元

产业动机在为什么要有 O-RAN，接口的协议栈细节在 O-RAN 接口，前传的四个平面在 三平面（CUS-M）。这一篇只回答：O-RAN 把一个基站拆成了哪几个逻辑网元、每个放在哪里、怎么拼回一个能工作的网络。

生活类比 · 城市交通指挥体系
O-RU 是路口的信号灯与地感线圈（必须在现场、必须实时）；O-DU 是路口的信号机控制器（按秒级配时驱动信号灯）；O-CU 是区域交通控制中心（管「一辆车从 A 到 B 走哪条路」这种会话级的事）；Near-RT RIC 是值班调度员（看着实时路况改配时方案）；Non-RT RIC / SMO 是交通规划院加运维总部；O-Cloud 是这些指挥中心租用的通用机房与服务器。
类比里最关键的一条是：越靠近现场，时间尺度越紧、越挪不走；越靠上，时间尺度越松、越可以集中。整篇的网元切分与部署选择都是这一条的推论。

一句话判据（按「断 30 秒会怎样」分类）：用户立刻掉话 → 数据通路（Open Fronthaul、F1、NG）；只是「优化停了」→ 控制回路（E2、A1）；运维界面看不到数据但业务无恙 → 管理面（O1、O2）。三条线的可用性要求、冗余设计与告警级别完全不同，混在一张 SLA 里是很多现场的第一个坑。

逻辑网元 ≠ 物理盒子

逻辑网元（Logical Node）：标准定义的是「一组功能 + 一组对外接口」，不是一个机箱。O-RAN 与 3GPP 都只规定「O-CU-CP 必须通过 E1 向 O-CU-UP 提供什么、通过 F1-C 向 O-DU 提供什么」，不规定它是不是一个独立的进程、容器、服务器或机柜。只要对外接口行为符合规范，把两个逻辑网元合成一个二进制也是合规的。

02

O-CU / O-DU / O-RU

就是 O-RAN 化的 CU/DU/RU

这三者本质就是 CU/DU/RU，冠以 "O-" 强调它们遵循 O-RAN 开放接口。但「都是 CU/DU/RU」这句话说完就没了，真正的骨架是——四个逻辑网元各自背着哪几层协议、被什么时间尺度绑住、因此只能放在哪里。

先看两个切点：Option 2 与 Option 7-2x

一个 gNB 的协议栈从上到下是 RRC / SDAP / PDCP / RLC / MAC / PHY / RF，四个网元就是在这条栈上切了两刀。Option 2（PDCP 与 RLC 之间）是 3GPP 定义的 CU/DU 切分点，O-RAN 只是沿用；Option 7-2x（PHY 内部、频域侧）是 O-RAN WG4 选定的 DU/RU 切分点，也是相对 3GPP 的实质增量——3GPP 从未规定 DU 以下怎么切。切分选项的完整谱系见 CU/DU/RU · 3GPP Functional Split。

为什么 7-2x 切在频域而不是切在 iFFT 之后？iFFT 之后是时域采样流，速率只由采样率决定，和这一时隙实际有多少 UE、占了多少 PRB 完全无关——半夜没人用也照样跑满，这正是老 CPRI 前传贵得离谱的原因。切在频域侧之后，前传上跑的是「实际占用的资源元素」，随负载起伏，还能做块浮点压缩。具体带宽算式见 三平面 · User Plane，压缩格式见 eCPRI · IQ 压缩。

O-CU-CP：整个基站的状态机所在地

O-CU-CP 对应 3GPP 的 gNB-CU-CP，承载 RRC 与 PDCP-C，是整个基站「记事」的地方：每个 UE 处在哪个 RRC 状态、配了哪些测量、用了哪套安全算法、下一步该切到哪个小区，全在这里。

时间尺度：事件驱动，十毫秒到几百毫秒。一次 RRC 重配、一次切换准备涉及多轮跨网元信令，没有任何一步被时隙对齐——这正是它最容易集中、最容易云化的原因：搬到几十公里外的中心机房，用户只会多感知到中传那点往返。

但它的可用性要求是全网最高的一档。一个 O-CU-CP 常常挂着几十到几百个 O-DU，它挂了这些小区全部无法接入新用户、已有连接也会随 RRC 定时器超时逐步瓦解。所以云化 CU-CP 的重点从来不是性能，而是状态的持久化与主备接管：几万个 UE 上下文重启后恢复不了，就意味着全体重新接入，而接入风暴会把刚起来的实例再压死一次。

O-CU-UP：唯一按「吞吐」而不是按「事件」设计的网元

O-CU-UP 对应 gNB-CU-UP，承载 SDAP（QoS Flow → DRB 映射、QFI 标记）与 PDCP-U（序列号、加密、按需完整性保护、重排序与重复检测、头压缩 ROHC/EHC、以及双连接下的 PDCP 复制）。

时间尺度：毫秒级的吞吐型负载，没有硬期限，但要每秒处理几百万个包并逐包加解密。所以它和 CU-CP 的工程画风完全不同：CU-CP 敏感于单核性能与状态存储，CU-UP 敏感于报文收发路径、cache 命中与加密指令集。

为什么 CU-UP 云化必须动网络栈？内核网络栈处理一个包的开销在微秒量级，每核每秒几十万包就跑满了；而一个 CU-UP 实例常要做到每秒几百万到上千万包。所以生产上的 CU-UP 几乎一定是 DPDK/VPP 用户态转发 + SR-IOV 直通网卡，加密走 AES-NI 或专门卸载。「跑在标准 CNI 的 veth 上」在实验室能通、在现网必然打不住量——展开见 电信云原生 · 电信负载的独特要求。

CU-CP 与 CU-UP 为什么要拆开：E1 的价值与代价

3GPP 在 TS 38.401 里明确允许一个 gNB 由 一个 gNB-CU-CP + 一个或多个 gNB-CU-UP + 一个或多个 gNB-DU 组成，CP 与 UP 之间的接口叫 E1（一般性描述见 TS 38.460，应用协议 E1AP 见 TS 38.463）。拆开之后，控制与用户面走的是两条完全分开的路：

① 两种负载的扩缩容曲线完全不同

控制面压力来自用户数与移动性事件数，用户面压力来自吞吐量。演唱会是「人多、不动、流量不大」，固定无线接入恰好相反。合在一个网元里，只能按两者的最坏情况一起买算力。

② 用户面可以单独下沉

用户面时延直接等于用户感知，控制面时延只影响接入与切换。UP 下到边缘与 UPF 同址做本地分流能砍掉回传那段 RTT，而 CP 留在中心继续池化几百个站。

③ 故障域与升级节奏解耦

控制面升级要动 RRC 状态机，风险高、窗口紧；用户面更像换一个转发进程。拆开后各自灰度，也能做「用户面滚动重启而控制面不动」。

④ 切片与多归属

一个 CU-CP 带多个 CU-UP，按切片 / 位置 / 业务类型把承载分到不同 UP 上——见上图右侧。

O-DU：四个网元里工程难度最高的一个

O-DU 承载 RLC + MAC + High-PHY，其中 MAC 里的空口调度器是整个基站的心脏：每个时隙都要决定「频域资源分给哪些 UE、用什么 MCS、几层、什么波束」。这件事的期限是硬的——错过这个时隙，资源就永久浪费掉了。而期限有多硬，由子载波间隔直接决定：

SCS 120 kHz (μ=3):  slot =  125 µs,  symbol ≈  8.9 µs   ← 毫米波

# 生成 C-plane 报文 → 编码调制产出频域 IQ → 按发送窗（T1a 一族）送上前传。
# 早了 O-RU 缓存放不下，晚了 O-RU 来不及发，两侧都是硬边界。

这张表解释了一个常被误解的现象：O-DU 的 CPU 占用率经常看着不高，但已经在丢时隙。瓶颈是「最坏情况的期限」而不是「平均吞吐」——一次几十微秒的调度抖动就足以让某个时隙迟到，而这在利用率曲线上几乎看不出来。判读它的健康度要看时隙迟到/丢弃计数与前传收发的窗内比例，而不是 top。云化之后怎么把这条期限守住，见 §3.4。

O-RU：唯一必须是专用硬件的网元

O-RU 承载 Low-PHY + RF，是 O-RAN 里唯一 3GPP 没有对应逻辑节点的网元——3GPP 的 gNB-DU 以下就没再切了，是 O-RAN 把这一段单独定义出来并规定了开放接口，这才有了「A 家 O-RU 配 B 家 O-DU」的可能。

时间尺度：符号级，数十微秒。拿到频域 IQ 后必须在这个符号该发射的时刻之前完成 iFFT 与上变频，没有任何缓冲余量。这也正是它必须是专用硬件的原因：定点数、固定流水、强时序的信号处理，用 FPGA/ASIC 才划算，跑通用 CPU 上既没有确定性也没有功耗优势。

O-RAN 把 O-RU 分成两类，分界点只有一个——预编码 / 波束加权做在哪，而它直接决定了前传上要跑几条流：

      ≈ 70 µs  →  最大光纤长度 ≈ 70 / 5 ≈ 14 km

# ★ 这就是「C-RAN 集中半径 20 km 量级」这个常被引用的数字的来处。
#   它不是光纤能传多远的问题（光纤跑 80 km 毫无压力），
#   而是 HARQ 与前传发送窗的时序容不容得下这个往返的问题。
#   注意实际工程里还要扣掉：光纤路由不是直线（绕行系数常按 1.3~1.6 算）、
#   中间可能有 WDM 设备、以及保护倒换后路径变长。

四个网元汇总

把前面几节压成一条因果链，整个架构就只剩一句话：时间尺度决定了可搬移距离，可搬移距离决定了部署位置。

面试加分：被问「为什么是这三刀（CU/UP 分离、CU/DU、DU/RU）」时，能用同一条逻辑串起来会明显加分：每一刀都切在「时间尺度」的台阶上，而时间尺度决定了这一段能被搬多远。RRC 是会话级 → 能搬几百公里；PDCP-U 是吞吐型 → 搬远了只损时延不损功能，所以按业务需要选；MAC/High-PHY 是时隙级 → 只能搬到光纤往返装得进 HARQ 时序的范围内（十几公里）；Low-PHY/RF 是符号级 → 一步都搬不了。把「时间尺度 → 可搬移距离 → 部署形态」这条因果链讲通，比背四个网元的协议层要有分量得多。

部署形态：D-RAN、C-RAN，以及 O-RAN 下的自由组合

上面那条因果链落到实际网络里，就是几种典型的部署形态。注意 D-RAN / C-RAN 描述的是「网元放在哪」，不是「用不用 O-RAN」——O-RAN 的贡献是让这几种形态能用同一套标准接口拼出来。

所以「一刀切」在真实网络里从不成立。O-RAN 的价值恰恰在于：这三四种形态用的是同一套接口和同一套管理面，而不必买三套不同的产品。

生产陷阱一：网元一多，兼容矩阵先爆

架构图上四个方块看着很清爽，但每个方块背后都是一条可独立演进的版本轴。互通的真正难点不是「接口有没有实现」，而是「接口上的可选项有没有选到同一个」。

兼容维度不一致的典型表现怎么提前发现
前传 M 平面的 YANG 模型版本配置里带了对端不认识的节点，NETCONF 直接报错；或节点名对但语义变了、配下去不生效入网前导出双方模型清单与版本，逐个对齐
C/U 平面的 section type 集合普通业务通，但特殊信道不工作 → 「能建站但接入失败」按信道逐项验证，不要只测吞吐
IQ 压缩方法与位宽两端支持集合不交叉，或默认位宽不同 → 星座图糊掉写进对接参数表，作为开站必填项
Category A / B 与波束能力一端按天线端口数据发、另一端按层数据加权重期待，完全对不上选型阶段锁定类别；混用时管理面要能自动识别
同步方式与拓扑O-RU 期望从前传口拿 PTP 却只给了 SyncE，或时间源等级不够 → 间歇性时序告警与邻区干扰方案写进设计文档，开站实测时间误差而非只看「已锁定」
F1 / E1 的可选 IE 与过程正常流程没问题，异常恢复流程走不通专门测异常路径：重启、断链、Reset、超时
网元与 O-Cloud 的版本依赖DU 依赖特定内核、驱动或加速卡固件，平台升级后起不来把「网元 ↔ 平台」支持矩阵维护成一张表，升级前查表

O-RAN 的应对是互通测试规范里的「测试档位（IOT profile）」：把一堆可选项固化成几组预先商定的组合，两端各自声明支持哪一档，从而把 n 维可选项的笛卡尔积压成几个已验证的组合——和 USB、PCIe 生态里的一致性档位是同一个套路。

真实场景 · 一次「都合规但接不上」的开站
O-RU 与 O-DU 各自都通过了一致性测试，链路 up、管理面读得到告警、PTP 显示已锁定，但小区就是起不来。排查顺序几乎是固定的：① M 平面的 YANG 模型版本与能力集（占比最高）→ ② 压缩方法与位宽（星座图糊掉一定是这一层）→ ③ C 平面的 section type 与波束配置 → ④ 最后才怀疑同步。
共同特征是两端都没有「错」，只是选了合规范围内的不同可选项——所以它不是靠调试解决的，而是靠开站前那张对接参数表逐行核对解决的。一小时的纸面工作能省下几天现场时间。

生产陷阱二：架构图很漂亮，集成很痛

「架构图很清晰，为什么现网集成这么难」的答案不在架构本身，而在解耦之后，原来被厂商内部消化掉的那些工作暴露出来了：

  • 责任边界变成了排障边界。一体化基站里「接入失败」是厂商自己的事；拆成四个网元三个厂商之后，同一个现象需要三方同时在线、各出日志、时钟还要对得上。集成成本的大头是协作成本，不是技术难度。
  • 时序类问题的可观测性天然很差。「时隙偶尔迟到」在应用层只表现为「吞吐比预期低 5%」，告警里可能什么都没有——要看见它得靠网元上报细粒度的窗内/窗外计数，而这类计数的定义在不同实现里差别很大。
  • 升级从一件事变成一个有依赖顺序的编排。O-Cloud、DU、CU、RU、SMO 各有版本，顺序错了就起不来。一体化交付时厂商给你一个包，开放之后这张依赖图归你维护。
  • 「测试通过」被稀释了。一致性测试证明「对着规范没错」，互通测试证明「这两个型号能配」，而现网还有第三件事：在你的容量、你的同步方案、你的机房温度下能不能长期稳定跑。前两件有规范可依，第三件只能靠试点。
常见的错误表述是「O-RAN 增加了复杂度」。准确的说法是：它没有增加系统的复杂度，而是把原本隐藏在单厂商内部的复杂度显式化了，并把消化这部分复杂度的责任从设备商转移给了运营商或集成方。这既是它最大的价值（接口从此可被审视、可被替换），也是它最大的落地阻力（需要一支原来不必存在的集成团队）。产业背景见 为什么需要 O-RAN · 落地现状与选型。
03

SMO：管理与编排

整个 O-RAN 的"大管家"

SMO（Service Management and Orchestration）：负责对整个 RAN 的管理、编排、自动化——配置下发、性能/故障监控（FCAPS）、软件生命周期、O-Cloud 资源编排。它通过 O1 接口管理 O-CU/O-DU/O-RU，通过 O2 接口管理 O-Cloud。Non-RT RIC 通常作为 SMO 的一部分。

SMO 是整个架构里唯一不在数据通路上的网元：它挂掉网络照常跑，但你既看不见网络、也改不了网络、更部署不了新网元。一句话概括——SMO 掌管的是「网络的形态」，不是「网络的流量」。

SMO 的四块工作

SMO 更像一个功能域的统称而非单一产品：摊开看是四件性质不同的事，现实中常由不同系统（甚至不同厂商）承担。

职能块具体做什么走哪条接口时间尺度

性能管理：计数器与 KPI 采集，通常按周期生成文件后上传O115 分钟粒度常见

O1 的具体承载是 NETCONF/YANG（配置与状态）加 VES/HTTP 一类的事件上报——这就是 NETCONF 出现在 O-RAN 里的原因，工程细节见 NETCONF 工程实践，接口层面的分解见 O-RAN 接口。

一个容易被忽略的架构选择：O-RU 由谁管

看架构图时会冒出一个自然的问题：O-RU 的管理面到底连到谁？这不是实现细节，而是设计阶段必须拍板的架构选择。O-RAN 给了两种模型——层级模型（SMO 把 O-RU 当作 O-DU 的一部分，配置与告警全部经 O-DU 中转）与混合模型（SMO 另有一条直达 O-RU 的管理连接，O-DU 只管与实时行为强相关的那部分）。两者的连线画法见 三平面 · Management Plane。

架构层面只需要记住选型判据：「你打算不打算换 O-DU 厂商」。同一家供货且短期不拆 → 层级模型省事得多，SMO 侧看到的网元数量少一个数量级。O-RU 独立采购、要保留替换 O-DU 的能力 → 只能上混合模型，代价是同一个 O-RU 有了两个管理者，必须在设计文档里逐个 YANG 模块写清楚由谁写——不要指望「运行时协商」能解决配置互相覆盖。

O-Cloud：跑 RAN 网元的那朵云

O-Cloud：承载可虚拟化 RAN 网元（Near-RT RIC、O-CU-CP、O-CU-UP、O-DU）的云平台，含物理基础设施、虚拟化/容器化层，以及向 SMO 暴露的管理能力。关键点：O-Cloud 是「被管理的对象」，SMO 是「管理者」，两者之间的接口是 O2。它不是一朵云，而是分层的多朵——中心、区域、边缘各一套，规格差异很大。

为什么要专门给它一个名字？因为 RAN 网元对承载平台的要求和普通 IT 负载差得太远，泛泛地说「跑在 Kubernetes 上」没有任何约束力。O-Cloud 的意义在于把这些要求标准化成一组平台必须提供的能力，从而让「网元」和「平台」可以分别采购：

O-Cloud 层次典型规模承载什么特殊要求
中心（Regional / Central）标准数据中心，几十到几百节点O-CU-CP、Near-RT RIC、部分 O-CU-UP与普通 IT 云差别不大，重点在状态持久化与高可用
区域 / 边缘（Edge）小机房，数节点到十几节点O-CU-UP、O-DU、Near-RT RIC需要高精度时钟、SR-IOV/DPDK、CPU 隔离；机房条件受限
站点（Far Edge / Cell Site）1 ~ 2 台服务器，甚至无人值守机柜O-DU（有时含 O-CU）最苛刻：实时内核、时钟直连、宽温、远程零接触部署、断电重启自愈

O2 接口的角色：分成「管资源」和「管部署」两件事

上图右侧那两条分支值得单独说一句。O2 把两类完全不同的操作分开了：基础设施管理（IMS）管 O-Cloud 本身的资源——清点节点/CPU/加速卡/网卡、查容量与拓扑、订阅硬件告警，相当于「云管平台」；部署管理（DMS）管跑在上面的网元实例——实例化、扩容、滚动升级、回退、删除，相当于「应用编排」。

为什么必须分开？两件事的变更节奏和责任人完全不同：基础设施半年一动（换硬件、扩机柜），网元部署可能一周一动（版本灰度）。合在一个接口里，等于要求「换网卡」和「升级 DU」走同一套审批和同一套工具。分开之后，平台团队负责 IMS 侧的资源供给，网元团队负责 DMS 侧的实例编排，中间用「资源已就绪」作为交接契约。

还要澄清一个常见混淆：O1 和 O2 管的不是同一层东西。O1 管「网元的业务配置」（这个小区功率多少、邻区是谁），O2 管「网元的存在与形态」（这个 O-DU 实例跑在哪台机器上、什么版本、给了多少核）。同一个 O-DU 被两条接口同时管着，但维度不重叠。把这两条搞混的直接后果是：出问题时不知道该找平台团队还是无线团队。

生产陷阱：把 O-DU 跑在通用服务器上，要解决的到底是什么

核心矛盾一句话就能说清：O-DU 有 500 µs 的硬期限，而通用服务器和通用 Linux 从设计目标上就是为「平均吞吐」而不是「最坏时延」优化的。默认配置下，一台服务器上能让线程停顿几十甚至几百微秒的机制多达十几种。下表是必须逐项落实的清单——这些不是调优建议，是功能前提，少任何一条，表现都是「大部分时候好，偶尔丢时隙」：

$ cat /proc/cmdline | tr ' ' '\n'
BOOT_IMAGE=/vmlinuz-...
isolcpus=managed_irq,domain,2-21   # 2-21 摘出负载均衡域，并接管这些核的托管中断
nohz_full=2-21                     # 免掉周期时钟中断（单任务运行时）
rcu_nocbs=2-21                     # RCU 回调挪到 0-1 上执行
irqaffinity=0,1                    # 所有可迁移中断赶到 0-1
intel_pstate=disable               # 或 passive + performance governor
processor.max_cstate=1
intel_idle.max_cstate=0            # 禁掉深睡眠，避免唤醒时延
default_hugepagesz=1G hugepagesz=1G hugepages=32

nosoftlockup skew_tick=1 tsc=reliable

# ★ 判读要点：
#   isolcpus 只做了「别人不许过来」，nohz_full / rcu_nocbs / irqaffinity 才是
#   「打扰源也搬走」。四件套缺一件都不算隔离——最常见的漏项就是 irqaffinity，
#   因为不配它系统照样能跑，只是每来一个中断就赌一次期限。
#   注意 nohz_full 只在「该核上恰好只有一个可运行任务」时才真的免中断，

但配置写对了不等于生效了。下面这组命令才是真正定界「这台机器到底给没给 O-DU 独占核」的判据——验证的是运行时事实，不是配置文件：

# ① 实时线程有没有真正拿到独占 CPU
$ ps -eLo pid,tid,psr,cls,rtprio,comm | grep -E 'l1_|fh_'
  4211  4213    6  FF     90 l1_dl_worker    # psr=6 固定，SCHED_FIFO 90
  4211  4215    8  FF     89 fh_tx_poll      # 前传发送轮询线程
#   判据：cls 必须是 FF/RR（出现 TS = 在和别人抢 CPU，必然抖动）；
#   psr 必须落在 isolcpus 隔离出来的核里，且一核一线程；
#   rtprio 留在 99 以下，最高档让给内核 migration/watchdog。

# ② 这些核上有没有别人来串门
$ cat /sys/devices/system/cpu/cpu6/cpufreq/scaling_governor
performance                       # 不能是 powersave/schedutil：降频 = 抖动
$ awk '/i40e|ice|mlx/' /proc/interrupts | cut -c1-90
#   判据：实时核那几列的中断计数增量必须为 0。落上去一个，就是一次期限风险。

# ③ NUMA 是不是真的对齐了（最容易在「看起来都配了」时漏掉）
$ cat /sys/class/net/ens5f0/device/numa_node
1                                 # 前传网卡在 node 1
$ grep Cpus_allowed_list /proc/4213/status
Cpus_allowed_list:  6             # ✗ 核在 node 0 → 每个报文跨一趟 UPI
#   现象：「同样的镜像、同样的配置，这台机器就是比那台抖」。
#   所以 Topology Manager 必须是 single-numa-node，不能是 best-effort。

时钟这一块要特别提醒：O-RAN 的前传同步规范给出了多种同步拓扑（LLS-C1 ~ LLS-C4，区别在于时间源接在哪、经过几级边界时钟）以及若干时间对齐误差等级——拓扑画法与预算分配见 三平面 · Sync Plane。架构层面只需记住一条：「PTP 已锁定」≠「时间对齐误差满足空口要求」。前者只说明这一跳的伺服收敛了，后者是从时间源一路累积到 O-RU 天面的端到端预算，必须靠设计核算加实测确认。

最后把这些要求映射到容器编排上。下面是概念示意，各家 CNF 的实际字段名以其文档为准：

# 概念示意：O-DU 的 Pod 里哪些字段是「功能前提」而不是「调优项」
apiVersion: v1
kind: Pod
metadata:
  name: o-du-cell-01
  annotations:
    k8s.v1.cni.cncf.io/networks: fh-cus-net, fh-mgmt-net   # 前传与管理分开
spec:
  nodeSelector: { node-role/o-du: "true" }   # 只调度到调优过的节点
  containers:
  - name: du
    resources:
      requests:                     # ★ requests 必须与 limits 完全相等，
        cpu: "16"                   #   否则拿不到 Guaranteed QoS，
        memory: 32Gi                #   拿不到 Guaranteed 就拿不到独占核
        hugepages-1Gi: 16Gi
      limits:
        cpu: "16"                   # 必须是整数；小数会退回共享核池
        memory: 32Gi
        hugepages-1Gi: 16Gi
        vendor.example/fh_vf: "2"   # SR-IOV VF：前传收发
        vendor.example/fec: "1"     # FEC 加速卡（如有）
    securityContext:
      capabilities: { add: ["IPC_LOCK", "SYS_NICE"] }  # 锁页 / 设实时优先级
    volumeMounts:
    - { name: phc, mountPath: /dev/ptp1 }   # 硬件时钟透传

# ★ 节点侧还必须配套（不在 Pod 里，最容易被忘）：CPU Manager = static、
#   Topology Manager = single-numa-node、reserved CPU 要和 isolcpus 的补集对上。
#   Pod 写得再对，节点没配这三项，独占核根本不会发生。
最坑的一点：这些配置的失效方式是「静默降级」。CPU Manager 没开成 static，Pod 照样起来、业务照样通、小流量压测也没问题——只是那 16 个核变成了共享核，抖动悄悄回来了。所以每一项都要有对应的「运行时验证动作」而不是「配置检查」，也就是上面那组命令。这是云化 RAN 与传统专用硬件最大的心智差异，平台侧的完整讨论见 电信云原生 · O-RAN O-Cloud。
真实场景 · 「上线三周后开始偶发丢时隙」
典型剧本：一套 O-DU 在实验室和试点都很稳，扩到几十个节点、跑了几周之后开始零星上报时隙迟到，每天几次，找不到规律。根因分布高度集中在少数几处：①新加入的节点漏了内核启动参数（批量部署模板改过版本）；②某台机器 BIOS 是出厂默认，节能没关，低负载时核在打瞌睡；③监控采集这类「无害」的 DaemonSet 被调度到了实时核上；④网卡驱动版本不一致，中断合并默认值不同。
共同点是：全都不是 O-DU 软件的问题，而是「这台机器和那台机器不一样」。所以云化 RAN 的第一件基础设施工作不是调优，而是把节点状态做成可断言、可漂移检测的。
04

RIC：RAN 智能控制器

O-RAN 最有"新意"的部分

RIC（RAN Intelligent Controller）：把无线网络的优化从"厂商内置的固定算法"变成"可编程、数据驱动、可由第三方注入 App"的闭环控制平台。分两级：Non-RT RIC（非实时）与 Near-RT RIC（近实时）。

为什么要分两级？因为无线优化有两种时间尺度：「策略与训练」（慢，秒级以上）和「实时闭环控制」（快，10 ms ~ 1 s）。这个理由值得再挖一层，因为它同时解释了 RIC 的架构和部署位置——闭环周期决定了它需要什么数据、能承受多大时延、以及出错时后果有多严重：

闭环周期需要什么数据能做什么优化出错的后果放在哪
时隙级（< 1 ms）每时隙的信道与缓冲状态PRB 分配、MCS 选择、HARQ——这是 MAC 调度器的活，RIC 碰不了丢时隙、吞吐直接下降必须在 O-DU 内部
近实时（10 ms ~ 1 s）UE 级的测量、切换事件、小区级负载流量引导、切换参数微调、准入控制、干扰协调用户体验波动、极端情况下乒乓切换Near-RT RIC（区域或边缘 DC）
非实时（≥ 1 s，到天）长周期 KPI、地理与业务画像、历史趋势参数模板、覆盖与容量规划、能效策略、模型训练策略偏差，但有时间纠正Non-RT RIC / SMO（中心 DC）
第一行最重要，也最容易被吹过头。「RIC 让 AI 接管无线调度」这种说法是不成立的——时隙级调度永远在 O-DU 里，RIC 的最快尺度是 10 ms 量级，比一个时隙慢一到两个数量级。RIC 能做的是「改变调度器的目标与约束」（比如给某个切片更高的权重、把某个 UE 引导到另一个小区），而不是「替调度器决定这一时隙给谁多少 PRB」。把这条边界说清楚，是判断一个人是否真的理解 RIC 的分水岭。

Near-RT RIC 内部有什么

Near-RT RIC 不只是「跑 xApp 的地方」。要让第三方 App 安全地控制生产网络，平台侧必须先解决一堆问题，这些就构成了它的内部组件：

上图里每个平台组件都对应一种「没有它就会发生」的故障：没有订阅合并，重复上报把 E2 链路和网元 CPU 打满；没有共享数据层，各 xApp 视图不一致且重启即失忆；没有 A1 策略终结，两级 RIC 各干各的；没有生命周期与鉴权，一个第三方 App 就能改全网参数。

而冲突消解是其中最被低估的一个。设想两个 xApp：一个做负载均衡（倾向把 UE 从拥塞小区推走），一个做覆盖优化（倾向把 UE 拉回信号最好的小区）。各自都是对的，但作用在同一批 UE 的同一组切换参数上，结果是参数以闭环周期为节拍来回摆动，用户体验比不装任何 xApp 更差。这类问题在单个 xApp 的测试里绝对暴露不出来，只有组合部署时才出现。所以「装了几个 xApp」不是能力指标，「几个 xApp 组合起来验证过」才是。

Near-RT RIC 放在哪：一个被时间尺度松开的约束

因为闭环是 10 ms ~ 1 s，而 E2 上跑的是指标与控制命令（不是用户数据），Near-RT RIC 的部署位置比 O-DU 宽松得多：几十公里的传输时延对一个 100 ms 的闭环完全可以接受。所以现实中它通常和 O-CU 同址，在区域或边缘 DC。两个容易踩的坑：

  • E2 的规模效应。一个 Near-RT RIC 可能连着成百上千个 E2 节点。订阅粒度设错，上报流量能轻松打到 Gbps 量级，同时吃掉网元可观的一块 CPU。所以订阅设计（上报什么、多久一次、按 UE 还是按小区聚合）是容量规划的一部分，不是 xApp 作者自己随便定的事。
  • 故障隔离方向。Near-RT RIC 挂掉不能让小区退服，网元必须能在 E2 断链后回退内置算法。但「回退」本身要设计和测试：回退瞬间参数会跳变吗？RIC 恢复后会不会又跳回来？把「E2 断链」做成常规演练项。

SMO 与 RIC 到底是什么关系

这是面试里最容易答糊的一处。三者的关系可以这样理清：

关系说明
Non-RT RIC ⊂ SMONon-RT RIC 是 SMO 内部的一个功能，不是与 SMO 并列的网元。它复用 SMO 的数据采集（O1 来的 KPI）、拓扑与配置视图
SMO 管 Near-RT RICNear-RT RIC 自身也是被管网元：部署走 O2、配置与告警走 O1。所以两者之间同时存在「管理关系」（O1/O2）与「策略关系」（经 Non-RT RIC 的 A1）
A1 是策略，不是配置O1 下发确定的参数值（「这个小区功率设为 X」），A1 下发目标与约束（「切片时延目标是 Y，你自己想办法达到」）。前者命令式，后者声明式
两条路都能改网络，要防打架同一个参数既可能被 O1 配置、也可能被 xApp 经 E2 改动。必须事先划清哪些归 O1、哪些交给 RIC 闭环，否则运维改一次、xApp 又改回去，运维会认为「配置下发失败」
面试加分：被问「SMO 和 RIC 的关系」时，最有分量的回答不是背包含关系，而是指出「O1 是命令式的配置，A1 是声明式的策略，而两者的作用域必须显式划分」。再补一句现场后果——「不划分的话，运维会看到配置被莫名改回去，而根因是某个 xApp 在按策略工作」——立刻能显出是做过现网的人。

记忆法：Non-RT RIC 是"慢思考"（训练模型、定策略），Near-RT RIC 是"快反应"（毫秒级闭环执行）。A1 是"慢→快"传策略的接口，E2 是"快 RIC → CU/DU"实施控制的接口。

把一个闭环完整走一遍

用一个具体目标串一遍最能说明分工：「保障某个 URLLC 切片的用户面时延不超过目标值」。三层各答一个问题，任何一层单独都做不到：

  • 「为什么会拥塞、什么时候会拥塞」→ 需要历史与全局 → 非实时层。rApp 从 O1 收来的若干天 KPI 里找出规律（「工作日 9-11 点 A 片区三个小区拥塞，而相邻 B 片区有余量」），训练预测模型，再经 A1 把「时延目标 + 允许抢占 eMBB + 优先引导到 B 片区」交下去。
  • 「现在拥塞了，先动谁」→ 需要当前状态 → 近实时层。xApp 经 E2 订阅这三个小区的 PRB 利用率与切片队列长度，每 100 ms 评估一次；逼近目标就提高该切片的调度权重、把若干 eMBB UE 的切换参数调偏、必要时限制新会话准入。
  • 「这一时隙的 PRB 怎么切」→ 需要时隙精度 → O-DU。MAC 调度器按新权重逐时隙分配 PRB 与 MCS。RIC 从来没有、也不可能替它做这一步。

消息级的闭环时序（E2 订阅、Indication、Control）见 O-RAN 接口 · E2（近实时控制）。

两级之间的边界怎么划

实际项目里经常纠结「这个功能该做成 rApp 还是 xApp」，四个判据基本够用：

判据倾向 rApp（非实时）倾向 xApp（近实时）
需要的数据窗口需要历史、跨小区、跨时段的全局视图只需要当前几百毫秒的局部状态
决策的时效性晚几分钟没关系晚 1 秒就没意义了
计算复杂度可以很重（模型训练、全网优化求解）必须很轻（每周期都要跑完）
出错的可挽回性有时间发现并回退可能在被发现前已经影响大量用户

一个实用经验：把「训练模型」放在 rApp，把「用模型输出做快速决策」放在 xApp。训练在非实时层（有数据、有算力、失败无害），结果以策略或轻量模型的形式经 A1 下到近实时层执行——既拿到了 AI 的能力，又没把重计算塞进 100 ms 的闭环。

rApp / xApp

RAN 上的"App Store"

rApp（跑在 Non-RT RIC）

非实时应用：如网络规划、能效优化、异常检测、训练供 xApp 使用的模型，再通过 A1 下发策略。它访问平台数据与服务用的是标准化的 R1 接口。

xApp（跑在 Near-RT RIC）

近实时应用：如流量引导、切换优化、干扰管理、准入控制、切片资源保障——通过 E2 直接影响 O-CU/O-DU 的行为。

rApp/xApp 可由第三方开发，这正是 O-RAN "智能化 + 开放生态"的落地形态——类似给 RAN 装了一个可编程的 App 平台，打破了"优化算法只能来自设备商"的格局。

为什么需要 R1 这条接口

xApp 有 E2 可用（那是它控制网元的通道），但 rApp 并不直接连网元，它需要的是「访问平台的数据与服务」。这一层不标准化，每个 rApp 就得针对某一家的 Non-RT RIC 实现写一遍，「第三方生态」于是退化成「某家的插件生态」——这就是 R1 的意义：把服务注册、发现、数据订阅、A1 策略管理标准化，让 rApp 能在不同厂商的框架上运行。

三条接口的分工可以这样记：R1 是「App 找平台要东西」，A1 是「上层给下层下策略」，E2 是「下层去动网元」。方向和层级都不一样。

生产陷阱：App 生态的现实门槛

  • 权限模型必须先于 App 存在。能读 UE 级测量报告就意味着能看到用户的位置与行为特征，能改切换参数就意味着能影响服务质量。「哪个 xApp 能订阅什么、能下发什么」必须由平台强制，而不是靠 App 自律。这件事没做，多厂商 App 就上不了生产网。
  • 组合验证的成本是乘法关系。单个 xApp 的测试很便宜，n 个的组合是 2ⁿ 量级。现实做法是限定同时生效的数量、并按「作用域是否重叠」分组——重叠的一起验证，不重叠的独立上线。
  • E2 服务模型的支持程度决定 App 的可移植性。网元只实现了指标上报类而没实现 RAN 控制类，这台网元上就只能跑「监控型」xApp。采购时没把需要的服务模型写进要求，后面装了 RIC 也用不上（E2SM 的分层见 O-RAN 接口 · E2）。
  • 「谁负责」在多厂商组合里是空白。xApp、RIC、网元来自三家，出了问题三方都能证明自己合规。这不是技术问题，却是 App 生态目前最大的实际阻力——也是现网里跑的 xApp 大多仍与 RIC 同厂商的原因。

室内分布系统DU 集中在楼内机房，Cat A O-RU前传极短、天线数不多，Cat A 足够且便宜
大规模 MIMO 宏站Cat B O-RU + DU 就近天线数远大于层数，Cat B 压得下前传带宽

🎯 本篇要点回顾
  • 网元清单：O-CU-CP / O-CU-UP / O-DU / O-RU（数据通路）+ Near-RT RIC / Non-RT RIC / SMO（智能与管理）+ O-Cloud（承载平台）。两个切点是 Option 2 与 Option 7-2x。
  • 一条贯穿的因果链：时间尺度 → 可搬移距离 → 部署位置。符号级搬不动，时隙级最多十几公里，会话级可以搬几百公里。
  • CP/UP 分离的价值是「两种负载独立扩缩 + 用户面可下沉」，接口是 E1；代价是两份状态要对账、UP 选择要设计、排障要看三份日志。
  • 部署形态由光纤和机房条件决定，不由架构偏好决定；一张现网通常同时跑着 D-RAN、C-RAN 与 UP 下沉三种。
  • SMO 与 O-Cloud：O1 管网元的业务配置、O2 管云平台资源（IMS）与网元部署（DMS）；O-Cloud 是被管对象而非管理者。
  • RIC 的边界：时隙级调度永远在 O-DU 里；Near-RT RIC 最快 10 ms 量级，改的是调度器的目标与约束，不是每时隙的分配。
  • 最痛的地方：O-Cloud 上跑 O-DU 的实时性配置是功能前提而非调优项，且失效方式是静默降级——所以要有运行时验证，不能只查配置。

面试题（12 道）

分层自测：先自己答一遍，再展开对照

8.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础O-RAN 有哪些逻辑网元？每个网元承载哪些协议层？

    分两组答，条理会清楚很多。

    数据通路上的四个（自上而下）：

    • O-CU-CP：RRC + PDCP-C。UE 状态机、连接管理、移动性决策、安全模式。
    • O-CU-UP：SDAP + PDCP-U。QoS Flow 到 DRB 的映射、加密、重排序、头压缩。
    • O-DU：RLC + MAC + High-PHY。空口调度器、HARQ、LDPC 编解码、调制与资源映射。
    • O-RU：Low-PHY + RF。iFFT/FFT、CP 添加去除、数字前端、射频与天线。

    智能与管理侧的三个：Near-RT RIC（近实时闭环，跑 xApp）、Non-RT RIC（长周期策略与模型训练，跑 rApp，是 SMO 的一部分）、SMO（编排 + FCAPS）。再加上承载平台 O-Cloud。

    补充加分：两个切点要说得出来——CU 与 DU 之间是 3GPP 的 Split Option 2（切在 PDCP 与 RLC 之间），DU 与 RU 之间是 O-RAN 选定的 Option 7-2x（切在 PHY 内部的频域侧）。前者是 3GPP 的成果，O-RAN 只是沿用；后者才是 O-RAN 相对 3GPP 的实质增量，因为 3GPP 从没规定 DU 以下怎么切。

  2. 基础O-DU 和 O-RU 的实时性要求差在哪？为什么 O-RU 必须是专用硬件？

    差一个数量级，而且性质不同。

    O-DU 是时隙级硬期限。30 kHz 子载波间隔下时隙是 500 µs，它必须在这 500 µs 内收完上一时隙的反馈、跑完调度器、做完编码调制、并按前传发送窗把报文送出去。错过就是这一时隙的空口资源永久浪费。所以 O-DU 的指标是「最坏情况」而不是「平均值」——平均 200 µs 但每万次有一次 600 µs，就是每 5 秒丢一个时隙。

    O-RU 是符号级，数十微秒。30 kHz 下一个符号约 35.7 µs，它拿到频域 IQ 后必须在这个符号该发射的时刻之前完成 iFFT 与上变频，几乎没有缓冲余量。

    O-RU 必须是专用硬件有三条理由：① 这一段是定点数、固定流水、强时序的信号处理，FPGA/ASIC 的能效比通用 CPU 高一两个数量级；② 它必须紧挨射频前端与天线，物理上没有搬走的可能；③ 它包含 DAC/ADC、变频、功放这些本来就是模拟/射频器件的部分。而 O-DU 那一段虽然实时性也很紧，但它是浮点/整数的通用计算，用通用 CPU 加加速卡可以做——这正是 O-DU 能云化、O-RU 不能的分界。

  3. 基础SMO、Non-RT RIC、Near-RT RIC 三者是什么关系？O1 和 A1 的本质区别是什么？

    关系有三层：

    • Non-RT RIC 属于 SMO，是 SMO 内部的一个功能，不是与它并列的网元。它复用 SMO 从 O1 收来的 KPI、拓扑与配置视图。
    • Near-RT RIC 是独立网元，同时被 SMO 管理：部署走 O2，配置与告警走 O1。
    • Non-RT RIC 通过 A1 向 Near-RT RIC 下策略，Near-RT RIC 通过 E2 去动 O-CU/O-DU。

    O1 与 A1 的本质区别是命令式 vs 声明式：O1 下发的是确定的参数值（「这个小区功率设为 X」），A1 下发的是目标与约束（「这个切片的时延目标是 Y，允许你抢占 eMBB 的资源，自己想办法达到」）。

    加分点：指出这两条路都能改网络，所以作用域必须显式划分。不划分的现场后果很具体——运维通过 O1 改了一个参数，过一会儿发现被改回去了，于是报「配置下发失败」，而真正的原因是某个 xApp 正在按 A1 策略正常工作。能说出这个现象，说明是做过现网的。

  4. 基础O-Cloud 是什么？O2 接口管什么？它和 O1 管的是同一层东西吗？

    O-Cloud 是承载可虚拟化 RAN 网元的云平台——包含物理基础设施（服务器、网卡、加速卡）、虚拟化/容器化层，以及向 SMO 暴露的管理能力。它承载 Near-RT RIC、O-CU-CP、O-CU-UP、O-DU；不承载 O-RU（专用硬件），也不承载 SMO 自己（SMO 是它的管理者）。实际网络里 O-Cloud 是分层的多套——中心、区域、边缘规格差别很大，站点级那一套最苛刻。

    O2 是 SMO 与 O-Cloud 之间的接口，分成两类服务：

    • 基础设施管理（IMS）：清点资源、查容量与拓扑、订阅硬件告警——相当于云管平台。
    • 部署管理（DMS）：实例化网元、扩缩容、升级、回退、删除——相当于应用编排。

    分开的理由是两者变更节奏与责任人不同：基础设施半年一动，网元部署可能一周一动。

    O1 和 O2 管的不是同一层。O1 管「网元的业务配置」（这个小区功率多少、邻区是谁），O2 管「网元的存在与形态」（这个 O-DU 实例在哪台机器、什么版本、给了多少核）。同一个 O-DU 被两条接口同时管，但维度不重叠。混淆的直接后果是：出问题时不知道该找平台团队还是无线团队。

8.2 中级（区分熟练度）

  1. 中级为什么要把 CU 拆成 CU-CP 和 CU-UP？E1 承载什么？拆开之后多了哪些麻烦？

    拆的理由有四条，前两条最重要：

    • 两种负载的扩缩容曲线完全不同。控制面压力来自用户数与移动性事件率，用户面压力来自吞吐量。演唱会场景是「人多、不动、流量不大」（控制面重、用户面轻），固定无线接入恰好相反。合在一个网元里只能按两者的最坏情况一起买算力。
    • 用户面可以单独下沉。用户面时延直接等于用户感知，控制面时延只影响接入与切换。把 CU-UP 和 UPF 摆到边缘做本地分流能砍掉回传那一段 RTT，而 CU-CP 留在中心继续池化几百个站。
    • 故障域与升级节奏解耦：控制面升级动 RRC 状态机、风险高；用户面更像换一个转发进程。
    • 切片与多归属：一个 CP 可带多个 UP，能按切片、位置、业务类型把承载分流到不同 UP。

    E1 是纯控制接口，上面不跑用户数据。核心是让 CP 在 UP 上创建并维护「承载上下文」：Bearer Context 的建立/修改/释放、用户面密钥下发、GTP-U 隧道端点交换、无活动通知（供 CP 决定是否把 UE 转 INACTIVE 省电）、用量上报（供计费）、以及异常后的 Reset。一般性描述见 TS 38.460，应用协议 E1AP 见 TS 38.463。

    多出来的麻烦（这部分最能区分熟练度）：① 两份状态要对账，超时或重启会留下「CP 以为释放了、UP 还占着隧道」的幽灵承载，表现为资源缓慢泄漏；② 一个 CP 带多个 UP 时要设计 UP 选择算法，写歪了会负载严重不均；③ 用户面密钥要经 E1 下发，E1 跨机房时这就是密钥传输通道，必须上 IPsec/MACsec；④ 一次接入失败要看 DU、CP、UP 三份日志，没有统一的 UE 级关联标识和时钟同步就拼不起来；⑤ 原来的进程内调用变成两条网络接口，时延叠加到接入与切换指标上。

    细节加分：一次 UE 接入会触碰 E1 两次——先 Bearer Context Setup 拿到 UP 侧隧道端点，再在 F1 UE Context Setup 回来后用 Bearer Context Modification 把 DU 侧端点告知 UP。看到日志里「建了又改」是正常流程，不是重试。

  2. 中级D-RAN 和 C-RAN 怎么选？限制 C-RAN 集中半径的到底是什么？

    先纠一个常见误解：限制不是光纤能传多远。光纤跑 80 km 毫无压力。真正的限制是HARQ 时序与前传发送窗容不容得下这个往返——O-DU 必须在 O-RU 该发射的时刻之前把数据送到，上行也必须在 HARQ 反馈时刻之前解完码。

    算一下就清楚了：单模光纤里传播速度约 204 000 km/s，单向约 4.9 µs/km（工程按 5 µs/km 估）。若前传单向时延预算取百微秒量级，扣掉中间交换转发（两跳、每跳数微秒）与成帧抖动余量（约 20 µs），留给传播的大约 70 µs，对应约 14 km 光纤。再考虑光纤路由不是直线（绕行系数常按 1.3~1.6）、可能有波分设备、保护倒换后路径会变长，所以工程上常报「10 ~ 20 km」这个量级。

    怎么选：

    • 有满足预算的直连光纤 + 机房条件达标 → C-RAN。收益是算力池化、便于小区间协同（CoMP、干扰协调）、升级不用逐站上站。
    • 光纤拉不到或机房不达标 → D-RAN。代价是每站一套算力、利用率低、运维成本随站点数线性增长。

    加分点两条：① 逐站判断，不要整片区一刀切——光纤分布是历史造成的，同一个城市里三种形态并存是常态；② 机房条件常常比光纤更致命，电、空调、承重、防尘、时间源与备份任一项不达标就该退回 D-RAN，哪怕光纤很好。这一步被跳过的次数最多，代价在夏天高温和雨季集中爆发。

  3. 中级部署形态怎么影响前传预算？为什么 O-RAN 选 Option 7-2x 而不是切在 iFFT 之后？

    切点决定了前传上跑的是什么信号，而信号的性质决定了带宽随什么变化。

    切在 iFFT 之后（Option 8，也就是传统 CPRI 那一档），前传上是时域采样流：速率只由采样率、天线数、量化位宽决定，和这一时隙实际有多少 UE、占了多少 PRB 完全无关。半夜一个用户都没有，链路照样跑满。这正是老 CPRI 前传贵得离谱、且完全无法优化的根源。

    切在 Option 7-2x（PHY 内部的频域侧），前传上是频域 IQ：只传实际占用的资源元素，带宽随负载起伏，还能做块浮点之类的压缩。同一个 100 MHz 小区，两种切点的前传带宽可以差好几倍。

    部署形态的影响体现在三处：

    • 集中度决定条数。D-RAN 下前传是站内几十米，成本可忽略；C-RAN 下每个 O-RU 都要一条前传拉到边缘机房，「条数 × 每条带宽」直接变成那个机房的接入容量需求，这经常是 C-RAN 方案真正的瓶颈。
    • Category A/B 决定每条带宽。Cat A 的 O-RU 在 O-DU 做预编码，前传流数等于天线端口数；Cat B 在 O-RU 做预编码，前传流数等于层数。大规模 MIMO（32T32R、64T64R）下层数远小于天线数，Cat B 省得非常明显，这时候几乎只能选 B。
    • 集中半径决定时延预算怎么分。拉得越远，留给交换、成帧、处理的余量越少，对中间传输设备的确定性要求越高。

    具体的带宽算式与四个平面各自怎么跑，属于前传专题的内容。

  4. 中级Category A 和 Category B O-RU 有什么区别？什么时候必须用 B？

    唯一的本质区别是预编码 / 波束加权做在哪：

    • Category A：预编码在 O-DU。前传上传的是每个天线端口的、已完成预编码的 IQ，所以前传流数 = 天线端口数。O-RU 简单、便宜、互通容易。
    • Category B：预编码在 O-RU。前传上传的是每个空间层的 IQ 加上波束加权信息，所以前传流数 = 层数。O-RU 要有矩阵运算能力，更贵，互通也更难（波束加权的表达方式与能力协商都更复杂）。

    什么时候必须用 B：当天线数远大于层数时。典型是 32T32R、64T64R 的大规模 MIMO 宏站——Cat A 下前传带宽随天线数线性增长，很快就撑不住；Cat B 只随层数增长（常见 4~16 层），差距是数倍。反过来，4T4R / 8T8R 的中低配站型和室分场景，Cat A 足够且成本与互通风险都低。

    工程提醒：类别必须在选型阶段就锁定，而且这是个高频的对接故障点。O-DU 按 Cat A 发（已预编码的天线端口数据）、O-RU 按 Cat B 期待（层数据 + 权重），两边完全对不上，现象是链路 up、管理面正常，但小区就是起不来。混用不同类别的 O-RU 时，管理面必须能自动识别并按类别配置。

8.3 高级（体现深度）

  1. 高级把 O-DU 跑在通用服务器上，要解决哪些问题？

    核心矛盾一句话：O-DU 有几百微秒的硬期限，而通用服务器和通用 Linux 都是为「平均吞吐」优化的，不是为「最坏时延」优化的。默认配置下，能让一个线程停顿几十甚至几百微秒的机制有十几种。要解决的是这些：

    • CPU 隔离四件套：isolcpus（摘出负载均衡域）+ nohz_full（免周期时钟中断）+ rcu_nocbs（RCU 回调挪走）+ irqaffinity（中断赶走）。最常漏的是最后一条——不配它系统照样跑，只是每来一个中断就赌一次期限。而 nohz_full 只在「该核上恰好只有一个可运行任务」时才真的免中断，所以必须和「一核一实时线程」的规划配套。
    • 大页：1 GiB 大页，避免 TLB miss 与页表遍历带来的不确定停顿；DPDK 的内存池也依赖它。
    • SR-IOV + DPDK：前传报文不能走内核网络栈或虚拟交换机。VF 直通给容器，用户态轮询收发，轮询线程独占核。
    • NUMA 对齐：CPU、大页、网卡 VF、加速卡必须在同一个 NUMA 节点。这是最容易在「看起来都配了」的情况下漏掉的一环，现象是「同样的镜像，这台机器就是比那台抖」。
    • 频率与 C-state：governor 设 performance、限制最大 C-state。反直觉的一点是低负载时反而更容易抖，因为核在打瞌睡，唤醒要几十微秒。
    • 时钟透传：O-DU 必须拿到网卡的硬件时钟（PHC），不能用系统软件时钟；PHC 设备要透传进容器。
    • FEC 加速：LDPC 编解码在高吞吐下吃掉大量 CPU，通常用加速卡（内联或旁挂两种形态）。
    • 容器编排侧：requests 必须与 limits 完全相等且 CPU 是整数（否则拿不到 Guaranteed QoS 就拿不到独占核）；节点上 kubelet 的 CPU Manager 要是 static 策略、Topology Manager 要是 single-numa-node。

    最能体现深度的一点：这些配置的失效方式是「静默降级」。CPU Manager 没开成 static，Pod 照样起来、业务照样通、小流量压测也没问题——只是那些核变成了共享核，抖动悄悄回来了。所以每一项都要有「运行时验证动作」而不是「配置检查」：看容器实际拿到的 cpuset、看实时线程的 psr 是否落在隔离核里、看 /proc/interrupts 在实时核上的增量是否为零。配置文件写对了不等于生效了。

    再补一句排障经验：这类问题上线几周后才偶发，根因高度集中在「这台机器和那台机器不一样」——漏了内核参数的新节点、BIOS 是出厂默认的机器、被调度到实时核上的监控 DaemonSet、驱动版本不一致导致中断合并默认值不同。所以第一件基础设施工作不是调优，而是把节点状态做成可断言、可漂移检测的。

  2. 高级给一个新建网络，你怎么划分各网元的部署位置？

    关键是顺序：从约束出发，而不是从「我想用什么架构」出发。按下面六步走，答案自然就出来了。

    1. 列出不可协商的约束：O-RU 必须在天面；O-DU 到 O-RU 的单向时延必须落在前传预算内（十几公里量级）；每个放 O-DU 的位置都必须能拿到满足要求的时间源。
    2. 看光纤——决定 O-DU 能不能集中。有到候选边缘机房的直连/波分光纤、且按绕行系数折算后仍在预算内，才有 C-RAN 的可能；否则只能 D-RAN。逐站判断，不要整片区一刀切。
    3. 看业务——决定 O-CU-UP 要不要下沉。有 URLLC、本地分流、数据不出园区的需求，就把 UP 和 UPF 下到边缘、CP 留中心；没有就 CP+UP 一起放区域 DC，别自找麻烦。
    4. 看规模——决定 O-CU-CP 集中到什么程度。几十个站，CU 与 DU 同址即可，池化收益不值那条中传；几百个以上，集中到区域 DC 收益明显。同时核算故障域：一个 CU-CP 带多少 DU 是可接受的爆炸半径。
    5. 看机房条件——这一步会否决前面的结论。电、空调、承重、防尘、进出通道，以及时间源与其备份（GNSS 天面位置、上游 PTP 路径、保持能力），任一项不满足就退回 D-RAN，哪怕光纤条件很好。
    6. 反过来验算三份预算：带宽（前传条数 × 每条带宽 → 边缘机房接入容量够不够）、时延（F1 时延加到接入时延与切换中断时间上是否还满足指标）、同步（从时间源到最远那个 O-RU，逐跳累加误差是否还在预算内）。

    RIC 与 SMO 的位置是顺带的结论：Near-RT RIC 与 O-CU 同址（10 ms 闭环不需要更近），SMO / Non-RT RIC 放中心 DC 或 IT 云，一套管全网。

    这道题真正考的东西：第 2 步和第 5 步都不是无线专业能独立回答的问题。能主动说出「这两步我要去问传输和基建」，比给出一个漂亮的架构图更有说服力——因为从架构偏好倒推的方案，几乎一定在这两步崩掉。另外要敢于说「同一张现网会同时跑三四种形态」，这是实话，也是 O-RAN 的价值所在：几种形态用的是同一套接口和同一套管理面。

  3. 高级多厂商的 O-DU 与 O-RU 都通过了一致性测试，却接不上。你怎么排查？

    先把问题的性质说清楚：这类故障的共同特征是「两端都没有错，只是在合规范围内选了不同的可选项」。所以它不是靠调试解决的，而是靠开站前那张对接参数表解决的。

    排查顺序（按命中率从高到低）：

    1. 管理面的 YANG 模型版本与能力集是否一致——这里出问题占比最高。表现是下发的配置里带了对端不认识的节点导致 NETCONF 报错，或者节点名对但语义变了、配下去不生效。
    2. IQ 压缩方法与位宽是否一致——块浮点、块缩放、µ-law、不压缩，两端支持集合不交叉，或都支持块浮点但默认位宽不同。星座图糊掉一定是这一层。
    3. C 平面的 section type 支持集合与波束配置——表现是「能建站但接入失败」，因为普通业务用的那类支持了，随机接入之类的特殊信道那一类没支持。
    4. Category A / B 是否匹配——一端按已预编码的天线端口数据发，另一端按层数据加权重期待，完全对不上。
    5. 最后才怀疑同步——而且要注意「PTP 已锁定」不等于「时间对齐误差满足空口要求」。前者只说明这一跳的伺服收敛了，后者是从时间源一路累积到 O-RU 天面的端到端预算，必须实测。

    兼容矩阵的维度（这是这道题的深度所在）：前传管理面的 YANG 模型版本、C/U 平面的 section type 集合、压缩方法与位宽、Category 与波束能力、同步方式与拓扑、F1/E1 的可选 IE 与异常恢复过程、以及「网元 ↔ O-Cloud 平台」的版本依赖（DU 常依赖特定内核、驱动或加速卡固件版本）。这些维度之间是笛卡尔积关系——厂商一体化交付时它们被「同一个团队的默认值」自动对齐了，开放之后每一个默认值都得显式约定。

    加分点：指出 O-RAN 自己的应对思路是互通测试规范里的「测试档位」概念——把一堆可选项固化成几组预先商定的组合，两端声明支持哪一档，从而把 n 维可选项的笛卡尔积压成几个已验证的组合。这和 USB、PCIe 生态里的一致性档位是同一个套路。

    还可以补一句结论性的判断：O-RAN 并没有增加系统的复杂度，它把原本隐藏在单厂商内部的复杂度显式化了，并把消化这部分复杂度的责任从设备商转移给了运营商或系统集成方。这既是它最大的价值，也是它最大的落地阻力。

  4. 高级Near-RT RIC 的能力边界在哪？两个 xApp 打架怎么办？E2 断链时网元该做什么？

    边界：Near-RT RIC 的最快闭环是 10 ms 量级，比一个时隙（125 ~ 1000 µs）慢一到两个数量级。所以「RIC 让 AI 接管无线调度」这种说法是不成立的——时隙级的 PRB 分配、MCS 选择、HARQ 永远在 O-DU 的 MAC 调度器里。RIC 能做的是改变调度器的目标与约束（提高某个切片的权重、把某个 UE 引导到别的小区、对新会话做准入限制），而不是替调度器决定这一时隙给谁多少 PRB。把这条边界说清楚是判断一个人是否真懂 RIC 的分水岭。

    xApp 冲突：这是 RIC 最被低估的风险。举个具体例子——一个 xApp 做负载均衡（倾向把 UE 从拥塞小区推走），一个做覆盖优化（倾向把 UE 拉回信号最好的小区）。两个各自都对，但作用在同一批 UE 的同一组切换参数上，结果是参数以闭环周期为节拍来回摆动，用户体验比不装任何 xApp 更差。这类问题在单 xApp 测试里绝对暴露不出来。

    应对是三层：① 平台侧必须有冲突消解机制，决定同时想改同一参数时谁生效；② 权限模型要先于 App 存在——哪个 xApp 能订阅什么、能下发什么控制，由平台强制而不靠 App 自律；③ 按「作用域是否重叠」分组验证，重叠的必须一起测，不重叠的可独立上线。所以「装了几个 xApp」不是能力指标，「几个 xApp 组合起来验证过」才是。

    E2 断链：网元必须能回退到内置算法继续工作，绝不能让小区退服。但「回退」本身是需要设计和测试的，有两个具体问题要回答：回退瞬间参数会不会跳变（跳变会造成一次可感知的体验波动）？RIC 恢复后会不会又跳回来（形成第二次波动）？把「E2 断链」做成常规演练项，比事后处理有效得多。

    最后补一个容量视角的深度点：一个 Near-RT RIC 可能连着成百上千个 E2 节点，订阅粒度设错，上报流量能轻松打到 Gbps 量级，同时吃掉网元可观的一块 CPU。所以订阅设计（上报什么、多久一次、按 UE 还是按小区聚合）是容量规划的一部分，不是 xApp 作者能自己随便定的事——这一点在方案评审时经常被漏掉。
