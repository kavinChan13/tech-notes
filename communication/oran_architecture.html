O-RAN 架构：O-CU / O-DU / O-RU / SMO / RIC

把上一篇的四大理念落成具体网元。O-RAN 在 3GPP 的 CU/DU/RU 之外，新增了两个关键角色：SMO（管理编排） 与 RIC（智能控制器，分 Non-RT / Near-RT）。这一篇建立完整架构图，把每个网元的职责和时间尺度讲清楚。

01

整体架构图

先看全貌，再拆网元

上一篇讲的是为什么要有 O-RAN——那是产业动机层面的事。这一篇只回答一个问题：O-RAN 把一个基站拆成了哪几个逻辑网元，每个网元放在哪里，它们怎么拼回一个能工作的网络。接口的协议栈细节留给 O-RAN 接口，前传的四个平面留给 三平面（CUS-M）；本篇只在「谁连谁、为什么这么连」的粒度上停留。

生活类比 · 城市交通指挥体系
把一个 5G 网络想成一座城市的交通指挥体系，O-RAN 的分层几乎是一一对应的：O-RU 是路口的信号灯与地感线圈——必须装在现场，必须实时响应；O-DU 是路口的信号机控制器，按秒级配时驱动信号灯，可以放在路口箱体里也可以放在附近的小机房；O-CU 是区域交通控制中心，管的是「一辆车从 A 到 B 走哪条路」这种会话级的事，放在城里任何一个机房都行；Near-RT RIC 是值班调度员，看着实时路况在几十秒内改配时方案；Non-RT RIC / SMO 是交通规划院加运维总部，做长周期模型、定策略、管设备台账与版本升级；O-Cloud 则是这些指挥中心租用的通用机房与服务器——不是厂家的专用机柜。
这个类比里最重要的一点是：越靠近现场的环节，时间尺度越紧、越不能挪走；越靠上的环节，时间尺度越松、越可以集中。整个 O-RAN 的网元切分与部署选择，本质上都是这一条约束的推论。

这张图有三条主线，分开看才不乱

初学者看 O-RAN 架构图容易一团糊，因为图上同时叠了三种性质完全不同的流量。把它们分开看，图就立刻清楚了：

  • 数据通路（纵向，右侧那一串）：UE 的比特从空口进来，经 O-RU → O-DU → O-CU-UP → UPF 一路往上。这条链是每个符号、每个时隙都在跑的，时间尺度从微秒到毫秒，任何一环卡住，用户立刻感知。
  • 控制回路（横向的 A1 / E2）：Non-RT RIC 通过 A1 把「策略」交给 Near-RT RIC，Near-RT RIC 通过 E2 从 CU/DU 收指标、往 CU/DU 下控制。这条链是事件与周期驱动的，时间尺度 10 ms 到分钟，断了网络照样跑，只是不再被优化。
  • 管理编排（O1 / O2）：SMO 通过 O1 对每个网元做 FCAPS，通过 O2 对云平台做资源与部署管理。这条链是人或流水线驱动的，时间尺度秒到小时。
一句话判据：如果一条接口断了 30 秒，用户立刻掉话——那是数据通路（Open Fronthaul、F1、NG）；如果断了 30 秒只是「优化停了」——那是控制回路（E2、A1）；如果断了 30 秒运维界面看不到数据但网络无恙——那是管理面（O1、O2）。三条线的可用性要求、冗余设计、告警级别完全不同，把它们混在一张 SLA 里是很多现场的第一个坑。

逻辑网元 ≠ 物理盒子

逻辑网元（Logical Node）：标准定义的是「一组功能 + 一组对外接口」，不是一个机箱。O-RAN 与 3GPP 都只规定「O-CU-CP 必须通过 E1 向 O-CU-UP 提供什么、通过 F1-C 向 O-DU 提供什么」，不规定它是不是一个独立的进程、容器、服务器或机柜。只要对外接口行为符合规范，把两个逻辑网元合成一个二进制也是合规的。

这一点是读架构图时最容易误解的地方。同一张图，在现实里至少有三种截然不同的打包方式：

# ① 一体化站点（D-RAN 风格）：CU+DU 合在一个服务器里，接口内部化
[ 站点机柜 ]
  └─ 一台服务器
       ├─ O-CU-CP  ┐
       ├─ O-CU-UP  ├─ E1/F1 变成进程内函数调用或本机 socket
       └─ O-DU     ┘
  └─ O-RU（塔上，Open Fronthaul 走光纤）

# ② 分层部署（典型 C-RAN + 边缘）：只有 F1 跨机房，前传仍在站点侧
[ 区域 DC ]  O-CU-CP + O-CU-UP + Near-RT RIC
     │ F1-C / F1-U（中传，跨几十公里）
[ 边缘机房 ]  O-DU（若干个，集中放置）
     │ Open Fronthaul（前传，≤ 约 20 km）
[ 站点 ]     O-RU

# ③ 用户面下沉（低时延业务）：CP 集中、UP 跟着 UPF 下到边缘
[ 中心 DC ]  O-CU-CP + SMO + Non-RT RIC
     │ E1（信令，可容忍较长时延）
[ 边缘 DC ]  O-CU-UP + UPF + O-DU + Near-RT RIC
     │ Open Fronthaul
[ 站点 ]     O-RU

# ★ 三种打包对应的接口全都是同一套标准。
#   区别只在「哪条接口跨了机房」——而这决定了它的时延预算、
#   要不要加密（跨机房链路通常要 IPsec/MACsec）、要不要独立监控。

所以看到一张 O-RAN 架构图时，正确的问法不是「这有几个盒子」，而是「这几条接口里，哪几条是跨机房的」。跨机房的那几条决定了整个方案的时延预算、光纤成本、安全边界和排障难度；没跨机房的那几条在工程上几乎是免费的。

02

O-CU / O-DU / O-RU

就是 O-RAN 化的 CU/DU/RU

这三者本质就是 CU/DU/RU，冠以 "O-"（O-RAN 符合性）强调它们遵循 O-RAN 开放接口。但「都是 CU/DU/RU」这句话说完就没了，恰恰是这一篇要展开的地方——四个逻辑网元各自背着哪几层协议、被什么时间尺度绑住、因此只能放在哪里，才是整个架构真正的骨架。

先看两个切点：Option 2 与 Option 7-2x

一个 gNB 的协议栈从上到下是 RRC / SDAP / PDCP / RLC / MAC / PHY / RF。O-RAN 的四个网元，就是在这条栈上切了两刀：

  • Option 2（PDCP 与 RLC 之间）——3GPP 定义的 CU/DU 切分点，把「与时隙无关的会话级处理」和「与时隙强绑定的实时处理」分开。这一刀是 3GPP 的功劳，O-RAN 只是沿用。
  • Option 7-2x（PHY 内部，频域侧）——O-RAN WG4 选定的 DU/RU 切分点，把「计算密集但可通用化的高层 PHY」和「必须贴着射频的低层 PHY」分开。这一刀是 O-RAN 相对 3GPP 的实质增量，因为 3GPP 从未规定 DU 以下怎么切。

  ┌───────────┐
  │  O-CU-CP  │  RRC         ← 连接管理、移动性决策、安全模式、测量配置
  │           │  PDCP-C      ← SRB（信令承载）的加密与完整性保护
  └───────────┘
  ┌───────────┐
  │  O-CU-UP  │  SDAP        ← QoS Flow → DRB 映射、QFI 标记
  │           │  PDCP-U      ← DRB 加密、重排序、复制、头压缩（ROHC/EHC）
  └───────────┘

  │           │  MAC         ← 调度器、HARQ、复用、随机接入

  │           │  RF          ← DAC/ADC、上下变频、功放与低噪放、天线
  └───────────┘

# ★ 记住两刀的性质差异：
#   Option 2 切的是「时间尺度」：上面是会话级（毫秒~秒），下面是时隙级（微秒）。
#   Option 7-2x 切的是「信号域」：上面是频域 IQ（带宽随负载变化、可压缩），
#                                 下面是时域采样（带宽只随采样率，压不动）。
为什么 7-2x 切在频域而不是切在 iFFT 之后？因为 iFFT 之后是时域采样流，它的速率只由采样率决定，和这一时隙实际有多少 UE、占了多少 PRB 完全无关——半夜没人用也照样跑满，这正是老 CPRI 前传贵得离谱的原因。切在频域侧之后，前传上跑的是「实际占用的资源元素」，可以随负载起伏，还能做块浮点压缩。同一个 100 MHz 小区，Option 8（CPRI）和 Option 7-2x 的前传带宽可以差好几倍，具体算式见 三平面 那一篇。

O-CU-CP：整个基站的状态机所在地

O-CU-CP 对应 3GPP 的 gNB-CU-CP。它承载 RRC 与 PDCP-C，是整个基站「记事」的地方：每个 UE 处于 IDLE / INACTIVE / CONNECTED 的哪个状态、配了哪些测量、用了哪套安全算法、下一步该切到哪个小区，全在这里。

它对外有四条接口，这四条接口基本就定义了它的工作内容：

  • NG-C（对 AMF）：透传 NAS 消息、接受核心网的 PDU 会话建立请求、上报 UE 上下文。
  • F1-C（对 O-DU）：小区级管理（激活/去激活）、UE 上下文的建立与修改、承载在 DU 侧的配置。
  • E1（对 O-CU-UP）：指挥 UP 建立/修改/释放承载上下文，并把用户面密钥交下去。
  • Xn-C（对邻站）：切换准备、双连接的辅站添加。

时间尺度：事件驱动，量级在十毫秒到几百毫秒。一次 RRC 重配、一次切换准备涉及多轮跨网元信令，天然是毫秒级的事，没有任何一步被时隙对齐。这正是它最容易集中、最容易云化的原因——把它放到几十公里外的中心机房，用户几乎感知不到，只有切换时延和接入时延会多出中传的往返。

但它的可用性要求是全网最高的一档。一个 O-CU-CP 常常挂着几十到几百个 O-DU，它挂了，这些小区全部无法接入新用户、已有连接也会随着 RRC 定时器超时逐步瓦解。所以云化 CU-CP 的重点从来不是性能，而是状态的持久化与主备接管：几万个 UE 上下文在实例重启后能不能恢复，恢复不了就意味着全体重新接入，接入风暴又会把刚起来的实例再压死。

O-CU-UP：唯一按「吞吐」而不是按「事件」设计的网元

O-CU-UP 对应 3GPP 的 gNB-CU-UP，承载 SDAP 与 PDCP-U。它做的事很单一但很重：

  • SDAP：把核心网侧的 QoS Flow 映射到空口侧的 DRB，并在下行给包打上 QFI 标记。
  • PDCP-U：序列号维护、加密（NEA0/NEA1/NEA2/NEA3 一族算法）、按需的完整性保护、重排序与重复检测、头压缩（ROHC，R16 起还有以太网头压缩 EHC）、以及 PDCP 复制（双连接/载波聚合下的冗余传输）。

时间尺度：毫秒级的吞吐型负载。它没有「500 µs 硬期限」这种东西，但它要在每秒处理几百万个包，并且对每个包做加解密。这让它的工程画风和 CU-CP 完全不同——CU-CP 是状态机与信令解析（对 CPU 单核性能与内存一致性敏感），CU-UP 是数据平面转发（对报文收发路径、cache 命中、加密指令集敏感）。

为什么 CU-UP 云化必须动网络栈？内核网络栈处理一个包的开销在微秒量级，按每核每秒几十万包算已经跑满；而一个 CU-UP 实例常常要做到每秒几百万到上千万包。所以生产上的 CU-UP 几乎一定是 DPDK / VPP 这类用户态转发 + SR-IOV 直通网卡，加密走 AES-NI 或专门的加解密卸载。「把 CU-UP 跑在标准 CNI 的 veth 上」这种方案在实验室能通、在现网必然打不住量——这是 电信云原生 那一篇要展开的主线。

CU-CP 与 CU-UP 为什么要拆开：E1 的价值与代价

3GPP 在 TS 38.401 里明确允许一个 gNB 由 一个 gNB-CU-CP + 一个或多个 gNB-CU-UP + 一个或多个 gNB-DU 组成，CP 与 UP 之间的接口叫 E1（一般性描述见 TS 38.460，应用协议 E1AP 见 TS 38.463）。这一刀切得比 CU/DU 那一刀更「云原生」，理由有三条：

① 两种负载的扩缩容曲线完全不同

控制面的压力来自用户数与移动性事件数（接入、切换、寻呼）；用户面的压力来自吞吐量。一个演唱会场景是「用户数暴涨但人不动、每人流量不大」——控制面压力大、用户面压力小；一个固定无线接入（FWA）场景恰好相反。合在一个网元里，就只能按两者的最坏情况一起买算力。

② 用户面可以单独下沉

用户面时延直接等于用户感知，控制面时延只影响接入与切换。把 CU-UP 放到边缘、和 UPF 摆在一起做本地分流，能把业务 RTT 砍掉中心回传的那一段；而 CU-CP 留在中心，仍然可以池化服务几百个站。这是 CP/UP 分离最有商业价值的一条。

③ 故障域与升级节奏解耦

控制面升级要动 RRC 状态机，风险高、窗口紧；用户面升级更像换一个转发进程。拆开之后可以各自按自己的节奏灰度，也能做「用户面滚动重启而控制面不动」。

④ 切片与多归属

一个 CU-CP 可以带多个 CU-UP，于是能按 S-NSSAI（切片）、地理位置、业务类型把不同承载放到不同 CU-UP 上——eMBB 走大吞吐那台，URLLC 走边缘那台。单一网元做不到这种分流。

E1 到底承载什么

E1 是一条纯控制接口，上面不跑用户数据。它的核心是让 CP 在 UP 上创建并维护「承载上下文（Bearer Context）」：

O-DU：四个网元里工程难度最高的一个

O-DU 承载 RLC + MAC + High-PHY，其中 MAC 里的空口调度器是整个基站的心脏：它每个时隙都要决定「这一时隙的频域资源分给哪些 UE、用什么 MCS、几层、什么波束」。这件事的期限是硬的——错过这个时隙，这一时隙的资源就永久浪费掉了。

# NR 的时隙长度：slot = 1 ms / 2^μ，SCS = 15 × 2^μ kHz（普通 CP，14 符号/时隙）
SCS  15 kHz (μ=0):  slot = 1000 µs,  symbol ≈ 71.4 µs
SCS  30 kHz (μ=1):  slot =  500 µs,  symbol ≈ 35.7 µs   ← Sub-6G TDD 最常用
SCS  60 kHz (μ=2):  slot =  250 µs,  symbol ≈ 17.9 µs
SCS 120 kHz (μ=3):  slot =  125 µs,  symbol ≈  8.9 µs   ← 毫米波

# 30 kHz 下，O-DU 每 500 µs 必须完整跑一轮：
#   ① 收上一时隙的 HARQ 反馈、CSI 与 SR/BSR 上报
#   ② 跑调度器：分 PRB、定 MCS、定层数与波束
#   ③ 生成 C-plane 报文，告诉 O-RU 这一时隙的资源与波束信息
#   ④ 做下行编码 / 调制 / 层映射 / 资源元素映射，产出频域 IQ
#   ⑤ 按 O-RAN 定义的发送窗（T1a 一族参数）提前把报文送上前传
#      —— 早了 O-RU 缓存放不下，晚了 O-RU 就来不及发，两侧都是硬边界

# ★ 所以 O-DU 的性能指标从来不是「平均处理时间」，而是
#   「在 500 µs 期限内完成的比例」以及「最坏情况用了多久」。
#   平均 200 µs 但每一万次有一次 600 µs，就是每 5 秒丢一个时隙。
O-DU 内部环节期限性质典型量级做不到会怎样
MAC 调度器决策每时隙硬期限必须在时隙时间的一小部分内完成（30 kHz 下留给它的通常是几十到一两百微秒）时隙空转，吞吐直接掉
下行 LDPC 编码 + 调制每时隙硬期限与 CPU/加速卡能力强相关，重负载下是最大头发送窗迟到，O-RU 丢包
上行 LDPC 解码受 HARQ 时序约束必须在 HARQ 反馈时刻之前完成反馈变 NACK，无谓重传
前传收发（U-plane）符号级轮询线程，抖动要控制在个位数微秒抖动超窗，O-RU 判为迟到丢弃
RLC ARQ 与重组软期限毫秒级时延上升，但不会丢时隙
O1 管理与统计上报无期限秒级只影响可观测性

这张表解释了一个常被误解的现象：O-DU 的 CPU 占用率经常看着不高，但已经在丢时隙。因为它的瓶颈是「最坏情况的期限」而不是「平均吞吐」——一次几十微秒的调度抖动就能让某个时隙迟到，而这在利用率曲线上几乎看不出来。判读 O-DU 的健康度，要看的是它自己上报的时隙迟到/丢弃计数、前传收发的窗内比例，而不是 top。

O-RU：唯一必须是专用硬件的网元

O-RU 承载 Low-PHY + RF：iFFT/FFT、CP 添加与去除、数字前端，以及 DAC/ADC、变频、功放、天线。它是 O-RAN 里唯一 3GPP 没有对应逻辑节点的网元——3GPP 的 gNB-DU 以下就没再切了，是 O-RAN 把这一段单独定义出来并规定了开放接口，这才有了「A 家 O-RU 配 B 家 O-DU」的可能。

时间尺度：符号级，数十微秒。它拿到 O-DU 送来的频域 IQ 之后必须在这个符号该发射的时刻之前完成 iFFT 与上变频，没有任何缓冲余量可言。这也是它必须是专用硬件的原因：这一段是定点数、固定流水、强时序的信号处理，用 FPGA/ASIC 做才划算，跑在通用 CPU 上既做不到确定性也做不到功耗。

部署形态：D-RAN、C-RAN，以及 O-RAN 下的自由组合

上面那条因果链落到实际网络里，就是几种典型的部署形态。要注意 D-RAN / C-RAN 是描述「网元放在哪」的，不是描述「用不用 O-RAN」的——O-RAN 的贡献是让这几种形态可以用同一套标准接口拼出来，而不是只能买厂商预设的那一种。

为什么「一刀切」在真实网络里从不成立：决定形态的是光纤，而光纤的分布是历史造成的，不是规划出来的。同一个城市里，老城区可能有富余的直连光纤（适合 C-RAN），新开发区只有环网（前传拉不到，只能 D-RAN），而工业园区客户要求数据不出园区（必须 UP 下沉）。所以一张现网通常同时跑着三四种形态——O-RAN 的价值恰恰在于这几种形态用的是同一套接口和同一套管理面，而不必买三套不同的产品。

生产陷阱一：网元一多，兼容矩阵先爆

架构图上四个方块看着很清爽，但每个方块背后都是一个可独立演进的版本轴。互通的真正难点不是「接口有没有实现」，而是「接口上的可选项有没有选到同一个」。O-RAN 的接口规范里有大量可选能力，两端各自合规但选择不同，结果就是接不上。

兼容维度不一致的典型表现怎么提前发现
Open Fronthaul 管理面的 YANG 模型版本O-DU 或 SMO 下发的配置里带了 O-RU 不认识的节点，NETCONF 直接报错；或者节点名对但语义变了，配下去不生效入网前做模型比对：把双方支持的模型清单与版本导出，逐个对齐
C/U 平面的 section type 支持集合普通业务通，但某些特殊信道（如随机接入相关的那一类）不工作，表现为「能建站但接入失败」按信道逐项验证，不要只测吞吐
IQ 压缩方法与位宽块浮点、块缩放、µ-law、不压缩，两端支持集合不交叉；或都支持块浮点但默认位宽不同，表现为解出来的星座图糊掉把压缩方法与位宽写进对接参数表，作为开站必填项
Category A / B 与波束能力O-DU 按 Cat A 发（已预编码的天线端口数据），O-RU 按 Cat B 期待（层数据 + 权重），完全对不上选型阶段就锁定类别；混用不同类别的 O-RU 时管理面要能自动识别
同步方式与同步拓扑O-RU 期望从前传口拿 PTP，现场却只给了 SyncE；或时间源等级不满足，表现为间歇性的时序告警与邻区干扰把同步方案与所选拓扑写进设计文档，开站时实测时间误差而不是只看「PTP 已锁定」
F1 / E1 的可选 IE 与过程某个可选过程一端支持一端不支持，正常流程没问题，异常恢复流程走不通专门测异常路径：重启、断链、Reset、超时
O-Cloud 与网元的版本依赖DU 依赖特定内核版本、特定网卡驱动或特定加速卡固件，O-Cloud 升级后 DU 起不来把「网元 ↔ 平台」的支持矩阵显式维护成一张表，升级前查表

O-RAN 自己也意识到了这个问题，所以在互通测试规范里引入了「测试档位（IOT profile）」的思路：把一堆可选项固化成几组预先商定的组合，两端都声明自己支持哪一档，从而把「n 维可选项的笛卡尔积」压成「几个已验证的组合」。这个思路和 USB、PCIe 那些成熟生态里的「一致性档位」是同一个套路。

真实场景 · 一次「都合规但接不上」的开站
多厂商前传对接里最典型的一类问题长这样：O-RU 与 O-DU 都通过了各自的一致性测试，链路 up、管理面能读到告警、PTP 显示已锁定，但小区就是起不来，或者起来了没有 UE 能接入。排查顺序几乎是固定的：①先确认管理面的 YANG 模型版本与能力集是否一致（这里出问题占比最高）；②再确认压缩方法与位宽是否一致，星座图糊掉一定是这一层；③再看 C-plane 的 section type 与波束配置是否被对端接受；④最后才怀疑同步——但「PTP 已锁定」不等于时间误差满足要求，要实测。
这类问题的共同特征是：两端都没有「错」，只是选了合规范围内的不同可选项。所以它不是靠调试解决的，而是靠开站前那张对接参数表解决的——把双方每一个可选项的取值列出来逐行核对，一小时的纸面工作能省下几天的现场时间。

生产陷阱二：架构图很漂亮，集成很痛

「O-RAN 架构图很清晰，为什么现网集成这么难」是个非常值得想清楚的问题。原因不在架构本身，而在架构解耦之后，原来被厂商内部消化掉的那些工作暴露出来了：

  • 责任边界变成了排障边界。一体化基站里，一个「接入失败」是厂商自己的事，他们能一路看到底。拆成四个网元三个厂商之后，同一个现象需要三方同时在线、各出日志、还要时钟对得上，才能定位。集成成本的大头不是技术难度，是协作成本。
  • 可选项的组合空间是乘法关系。上一节那张表里每一行都是一个维度，维度之间是笛卡尔积。厂商一体化交付时这些维度是被「同一个团队的默认值」自动对齐的；开放之后，每一个默认值都得显式约定。
  • 时序类问题的可观测性天然很差。「时隙偶尔迟到」这种问题在应用层的表现是「吞吐比预期低 5%」，在告警里可能什么都没有。要看到它需要网元上报细粒度的窗内/窗外计数，而这类计数的定义与颗粒度在不同实现里差别很大。
  • 升级不再是一件事，而是一个有依赖顺序的编排。O-Cloud 平台、DU、CU、RU、SMO 各有版本，升级顺序错了就起不来。一体化交付时厂商给你一个包，开放之后你要自己维护这张依赖图。
  • 「测试通过」的含义被稀释了。一致性测试证明的是「对着规范没错」，互通测试证明的是「这两个具体型号能配」，而现网还有第三件事：这两个型号在你的容量、你的同步方案、你的机房温度下能不能长期稳定跑。前两件事有规范可依，第三件事只能靠试点。
把这件事说反了会很吃亏。常见的错误表述是「O-RAN 增加了复杂度」——这不准确。准确的说法是：O-RAN 没有增加系统的复杂度，它把原本隐藏在单厂商内部的复杂度显式化了，并把消化这部分复杂度的责任从设备商转移给了运营商（或系统集成方）。这既是它最大的价值（这些接口从此可被审视、可被替换），也是它最大的落地阻力（需要一支原来不需要存在的集成团队）。这一层取舍的产业背景在 为什么需要 O-RAN 那一篇。
03

SMO：管理与编排

整个 O-RAN 的"大管家"

SMO（Service Management and Orchestration）：负责对整个 RAN 的管理、编排、自动化——配置下发、性能/故障监控（FCAPS）、软件生命周期、O-Cloud 资源编排。它通过 O1 接口管理 O-CU/O-DU/O-RU，通过 O2 接口管理 O-Cloud。Non-RT RIC 通常作为 SMO 的一部分。

SMO 是整个 O-RAN 架构里唯一不在数据通路上的网元。它挂掉，网络照常跑；但它挂掉之后，你既看不见网络，也改不了网络，更部署不了新网元。用一句话概括它的定位：SMO 掌管的是「网络的形态」，而不是「网络的流量」。

SMO 的四块工作

把 SMO 的职能摊开，其实是四件性质不同的事挤在一个名字下面。区分清楚很重要，因为现实中这四块常常由不同的系统承担（甚至来自不同厂商），SMO 更像一个功能域的统称而非单一产品：

职能块具体做什么走哪条接口时间尺度
① FCAPS 网元管理配置管理：网元参数、小区参数、邻区关系、切片配置O1秒 ~ 分钟
性能管理：计数器与 KPI 采集，通常按周期生成文件后上传O115 分钟粒度常见
故障管理：告警上报与订阅、告警清除与同步O1秒级
软件管理：版本下载、校验、激活、回退O1分钟 ~ 小时
② 云平台与网元编排清点与监控 O-Cloud 的资源（节点、CPU、加速卡、网卡、存储）O2（IMS 类服务）分钟
网元的生命周期：实例化、扩缩容、升级、迁移、删除O2（DMS 类服务）分钟 ~ 小时
③ 非实时智能作为 Non-RT RIC 的宿主：rApp 平台、模型训练与管理、通过 A1 下发策略内部 + R1 + A1秒 ~ 天
④ O-RU 的管理面按所选管理模型，直接管 O-RU 或经 O-DU 中转Open Fronthaul M 平面秒 ~ 分钟

O1 的具体承载是 NETCONF/YANG（配置与状态）加 VES/HTTP 一类的事件上报——这就是 NETCONF 出现在 O-RAN 里的原因，工程细节见 NETCONF 工程实践，接口层面的分解见 O-RAN 接口。

一个容易被忽略的架构选择：O-RU 由谁管

看架构图时会冒出一个自然的问题：O-RU 的管理面到底连到谁？这不是实现细节，而是一个需要在设计阶段拍板的架构选择，O-RAN 给了两种模型：

层级模型（Hierarchical）

SMO 不直接管 O-RU，而是把 O-RU 当作 O-DU 的一部分来管：所有对 O-RU 的配置与告警都经 O-DU 中转。好处是 SMO 侧看到的网元数量少一个数量级，且 O-DU 天然知道 O-RU 的实时状态，能做一致性校验。代价是 O-DU 厂商变成了 O-RU 管理的必经之路，多厂商混搭时这里就是摩擦点。

混合模型（Hybrid）

SMO 有一条直达 O-RU 的管理面连接，同时 O-DU 也管 O-RU 的一部分（尤其是与实时行为强相关的部分）。好处是运营商对 O-RU 有直接控制权，换 O-DU 厂商不影响 O-RU 的纳管。代价是同一个 O-RU 有两个管理者，「谁说了算」必须事先划清，否则会出现配置互相覆盖。

选哪个？判据是「你打算不打算换 O-DU 厂商」。如果 O-DU 与 O-RU 来自同一家、且短期不打算拆，层级模型省事得多；如果 O-RU 是独立采购、要保留替换 O-DU 的能力，那就得上混合模型，并且在设计文档里逐个 YANG 模块写清楚由谁写——不要指望「运行时协商」能解决这个问题。

O-Cloud：跑 RAN 网元的那朵云

O-Cloud：O-RAN 定义的云平台，用来承载可虚拟化的 RAN 网元（Near-RT RIC、O-CU-CP、O-CU-UP、O-DU）。它包含物理基础设施（服务器、加速卡、网卡、交换）、虚拟化/容器化层，以及向 SMO 暴露的管理能力。关键点：O-Cloud 是「被管理的对象」，SMO 是「管理者」，两者之间的接口是 O2。O-Cloud 不是一朵云，而是分层的多朵——中心、区域、边缘各有一套，规格差异很大。

为什么要专门给它一个名字？因为 RAN 网元对承载平台的要求和普通 IT 负载差得太远，泛泛地说「跑在 Kubernetes 上」没有任何约束力。O-Cloud 的意义在于把这些要求标准化成一组平台必须提供的能力，从而让「网元」和「平台」可以分别采购：

O-Cloud 层次典型规模承载什么特殊要求
中心（Regional / Central）标准数据中心，几十到几百节点O-CU-CP、Near-RT RIC、部分 O-CU-UP与普通 IT 云差别不大，重点在状态持久化与高可用
区域 / 边缘（Edge）小机房，数节点到十几节点O-CU-UP、O-DU、Near-RT RIC需要高精度时钟、SR-IOV/DPDK、CPU 隔离；机房条件受限
站点（Far Edge / Cell Site）1 ~ 2 台服务器，甚至无人值守机柜O-DU（有时含 O-CU）最苛刻：实时内核、时钟直连、宽温、远程零接触部署、断电重启自愈

O2 接口的角色：分成「管资源」和「管部署」两件事

O2 是 SMO 与 O-Cloud 之间的接口，它把两类完全不同的操作分开了——这个分法很重要，因为它对应现实中两个不同的团队：

O2 的两类服务管什么典型操作类比
基础设施管理服务（IMS，常写作 O2ims）O-Cloud 本身的资源清点有哪些节点/CPU/加速卡/网卡；查询容量与拓扑；订阅资源变更与硬件告警；申请或释放资源池相当于「云管平台」：机器有多少、坏没坏、还剩多少
部署管理服务（DMS，常写作 O2dms）跑在 O-Cloud 上的网元实例实例化一个 O-DU；给它扩容；滚动升级；回退；删除并回收资源相当于「应用编排」：把哪个网元、哪个版本、放到哪一块资源上
为什么必须分开？因为这两件事的变更节奏和责任人完全不同。基础设施半年一动（换硬件、扩机柜），网元部署可能一周一动（版本灰度）。合在一个接口里，等于要求「换网卡」和「升级 DU」走同一套审批和同一套工具。分开之后，平台团队负责 IMS 侧的资源供给，网元团队负责 DMS 侧的实例编排，中间用「资源已就绪」作为交接契约。这也解释了 O2 为什么在时间尺度那张表里是「分钟到小时」——它天生不是一个高频接口。

还要澄清一个常见混淆：O1 和 O2 管的不是同一层东西。O1 管的是「网元的业务配置」（这个小区的功率是多少、邻区是谁），O2 管的是「网元的存在与形态」（这个 O-DU 实例跑在哪台机器上、什么版本、给了多少核）。同一个 O-DU 同时被两条接口管着，但管的维度不重叠。把这两条搞混的直接后果是：出问题时不知道该找平台团队还是无线团队。

生产陷阱：把 O-DU 跑在通用服务器上，要解决的到底是什么

这是整个 O-RAN 落地里技术含量最高、也最容易低估的一块。核心矛盾一句话就能说清：O-DU 有 500 µs 的硬期限，而通用服务器和通用 Linux 从设计目标上就是为「平均吞吐」优化的，不是为「最坏时延」优化的。默认配置下，一台服务器上能让一个线程停顿几十甚至几百微秒的机制多达十几种。

最坑的一点：这些配置的失效方式是「静默降级」。CPU Manager 策略没开成 static，Pod 照样起来、业务照样通、压测小流量也没问题——只是那 16 个核变成了共享核，抖动悄悄回来了。所以每一项都要有对应的「运行时验证动作」而不是「配置检查」：看 /sys/fs/cgroup 下这个容器实际拿到的 cpuset、看实时线程的 psr 是否落在隔离核里、看 /proc/interrupts 在实时核上的增量是否为零。配置文件写对了不等于生效了，这是云化 RAN 与传统专用硬件最大的心智差异。平台侧的完整讨论见 电信云原生。
真实场景 · 「上线三周后开始偶发丢时隙」
这类问题的典型剧本是：一套 O-DU 在实验室和试点都很稳，扩容到几十个节点、跑了几周之后开始零星上报时隙迟到，每天几次，找不到规律。而这类问题的根因分布高度集中在少数几处：①有个新加入的节点漏了内核启动参数（批量部署的模板改过版本）；②某台机器的 BIOS 是出厂默认，节能没关，低负载时核在打瞌睡；③监控/日志采集这类「无害」的 DaemonSet 被调度到了实时核上；④网卡固件或驱动版本与其他节点不一致，中断合并参数默认值不同。
共同点是：全都不是 O-DU 软件的问题，全都是「这台机器和那台机器不一样」。所以云化 RAN 的第一件基础设施工作不是调优，而是把节点状态做成可断言、可漂移检测的——用一份基线清单在每个节点上定期跑，比出问题再去逐台 diff 有效得多。
04

RIC：RAN 智能控制器

O-RAN 最有"新意"的部分

RIC（RAN Intelligent Controller）：把无线网络的优化从"厂商内置的固定算法"变成"可编程、数据驱动、可由第三方注入 App"的闭环控制平台。分两级：Non-RT RIC（非实时）与 Near-RT RIC（近实时）。

为什么要分两级？因为无线优化有两种时间尺度：一种是"策略/训练"（慢，秒级以上），一种是"实时闭环控制"（快，10ms~1s）。硬把它们放一起既不高效也不安全，所以拆成两层。

这个理由值得再往下挖一层，因为它同时解释了 RIC 的架构和它的部署位置。一个闭环的周期决定了它需要什么数据、能承受多大的时延、以及它出错时的后果有多严重：

闭环周期需要什么数据能做什么优化出错的后果放在哪
时隙级（< 1 ms）每时隙的信道与缓冲状态PRB 分配、MCS 选择、HARQ——这是 MAC 调度器的活，RIC 碰不了丢时隙、吞吐直接下降必须在 O-DU 内部
近实时（10 ms ~ 1 s）UE 级的测量、切换事件、小区级负载流量引导、切换参数微调、准入控制、干扰协调用户体验波动、极端情况下乒乓切换Near-RT RIC（区域或边缘 DC）
非实时（≥ 1 s，到天）长周期 KPI、地理与业务画像、历史趋势参数模板、覆盖与容量规划、能效策略、模型训练策略偏差，但有时间纠正Non-RT RIC / SMO（中心 DC）
第一行最重要，也最容易被吹过头。「RIC 让 AI 接管无线调度」这种说法是不成立的——时隙级调度永远在 O-DU 里，RIC 的最快尺度是 10 ms 量级，比一个时隙慢一到两个数量级。RIC 能做的是「改变调度器的目标与约束」（比如给某个切片更高的权重、把某个 UE 引导到另一个小区），而不是「替调度器决定这一时隙给谁多少 PRB」。把这条边界说清楚，是判断一个人是否真的理解 RIC 的分水岭。

Near-RT RIC 内部有什么

Near-RT RIC 不只是「跑 xApp 的地方」。要让第三方 App 能安全地控制生产网络，平台侧必须先解决一堆问题，这些就构成了它的内部组件：

平台组件解决什么问题没有它会怎样
E2 终结与订阅管理维护到各 E2 节点的连接，把多个 xApp 的订阅需求合并后下发每个 xApp 各自订阅，重复上报把 E2 链路和网元 CPU 打满
共享数据层给 xApp 提供统一的 UE/小区状态视图与持久化每个 xApp 自己维护一份状态，视图不一致，且重启即失忆
冲突消解两个 xApp 同时想改同一个参数时决定谁生效最危险的一类故障：两个 App 反复互相覆盖，参数持续振荡
xApp 生命周期与鉴权部署、升级、下线；限定每个 xApp 能读什么、能改什么一个第三方 App 就能改全网参数，没有任何护栏
A1 策略终结接收 Non-RT RIC 的策略并翻译成对 xApp 的约束上层策略无法落地，两级 RIC 各干各的
消息路由与订阅总线xApp 之间、xApp 与平台之间的解耦通信xApp 之间硬耦合，无法独立升级
冲突消解是 RIC 最被低估的部分。设想两个 xApp：一个做负载均衡（倾向把 UE 从拥塞小区推走），一个做覆盖优化（倾向把 UE 拉回信号最好的小区）。它们各自都是对的，但作用在同一批 UE 的同一组切换参数上，结果是参数以闭环周期为节拍来回摆动，用户体验比不装任何 xApp 更差。这类问题在单个 xApp 的测试里绝对暴露不出来，只有在组合部署时才出现。所以「装了几个 xApp」不是能力指标，「几个 xApp 组合起来验证过」才是。

Near-RT RIC 放在哪：一个被时间尺度松开的约束

因为 Near-RT RIC 的闭环是 10 ms ~ 1 s，而 E2 上跑的是指标上报与控制命令（不是用户数据），它的部署位置比 O-DU 宽松得多：几十公里的传输时延对一个 100 ms 的闭环来说完全可以接受。所以现实中它通常和 O-CU 放在一起，在区域或边缘 DC，而不是下到站点。

但这里有两个容易踩的坑：

  • E2 的规模效应。一个 Near-RT RIC 可能连着成百上千个 E2 节点，每个节点按订阅周期上报指标。订阅粒度设错，上报流量能轻松打到 Gbps 量级，同时把网元的 CPU 吃掉可观的一块。所以订阅设计（上报什么、多久一次、按 UE 还是按小区聚合）是容量规划的一部分，不是 xApp 作者自己随便定的事。
  • 故障隔离方向要想清楚。Near-RT RIC 挂掉不能让小区退服——网元必须能在 E2 断链后回退到内置算法继续工作。这一点听起来显然，但「回退」本身是需要设计和测试的：回退瞬间参数会跳变吗？RIC 恢复后会不会又跳回来？把「E2 断链」作为常规演练项，比事后处理有效得多。

SMO 与 RIC 到底是什么关系

这是面试里最容易答糊的一处。三者的关系可以这样理清：

关系说明
Non-RT RIC ⊂ SMONon-RT RIC 是 SMO 内部的一个功能，不是与 SMO 并列的网元。它复用 SMO 的数据采集（O1 来的 KPI）、拓扑与配置视图
SMO 管 Near-RT RICNear-RT RIC 自身也是一个被管理的网元：它的部署走 O2，它的配置与告警走 O1。所以 SMO 与 Near-RT RIC 之间同时存在「管理关系」（O1/O2）和「策略关系」（经 Non-RT RIC 的 A1）
A1 是策略，不是配置O1 下发的是确定的参数值（「这个小区功率设为 X」）；A1 下发的是目标与约束（「这个切片的时延目标是 Y，你自己想办法达到」）。前者是命令式，后者是声明式——这是两条接口最本质的区别
两条路都能改网络，要防打架同一个参数既可能被 O1 配置，也可能被 xApp 通过 E2 改动。必须事先划清哪些参数由 O1 管、哪些交给 RIC 闭环，否则运维改一次、xApp 又改回去，运维会认为「配置下发失败」
面试加分：被问「SMO 和 RIC 的关系」时，最有分量的回答不是背包含关系，而是指出「O1 是命令式的配置，A1 是声明式的策略，而两者的作用域必须显式划分」。再补一句现场后果——「不划分的话，运维会看到配置被莫名改回去，而根因是某个 xApp 在按策略工作」——立刻能显出是做过现网的人。

把一个闭环完整走一遍

抽象的分工看完了，用一个具体目标串一遍最能说明问题：「保障某个 URLLC 切片的用户面时延不超过目标值」。这件事必须两级 RIC 配合，任何一级单独都做不到：

# ┌─ 非实时层（Non-RT RIC / SMO），周期：小时 ~ 天 ─────────────────┐
① SMO 通过 O1 收集过去若干天的 KPI：
     各小区的时延分布、切片占用、拥塞时段、切换成功率
② rApp 分析出规律：
     "工作日 9-11 点、17-19 点，A 片区的 3 个小区会拥塞，
      URLLC 时延在这些时段超标；而相邻 B 片区有余量"
③ rApp 训练/更新一个预测模型：给定当前负载 → 预测未来 5 分钟是否将超标
④ rApp 通过 A1 下发策略给 Near-RT RIC：
     "切片 S 的时延目标 = T；允许你为它抢占 eMBB 的资源；
      A 片区这 3 个小区在这些时段优先把 eMBB 用户引导到 B 片区"
   # ★ 注意：这里下发的是「目标 + 授权 + 倾向」，不是具体参数值。
# └────────────────────────────────────────────────────────────────┘
                              │  A1
                              ▼
# ┌─ 近实时层（Near-RT RIC），周期：100 ms ~ 1 s ───────────────────┐
⑤ xApp 通过 E2 订阅这 3 个小区的近实时指标：
     PRB 利用率、切片队列长度、UE 级测量报告
⑥ 每个周期评估：切片 S 的当前时延是否逼近目标 T？
⑦ 逼近了 → 通过 E2 下控制：
     • 提高切片 S 在调度器里的权重；
     • 把若干 eMBB UE 的切换参数调偏，引导它们去 B 片区；
     • 必要时对新的 eMBB 会话做准入限制。
⑧ 下个周期再看效果，形成闭环。
# └────────────────────────────────────────────────────────────────┘
                              │  E2
                              ▼
# ┌─ 时隙级（O-DU 的 MAC 调度器），周期：500 µs ────────────────────┐
⑨ 调度器按 xApp 给的新权重，逐时隙分配 PRB 与 MCS。
   # ★ RIC 从来没有、也不可能替它做这一步。
# └────────────────────────────────────────────────────────────────┘

# ★ 三层的分工判据：
#   "为什么会拥塞、什么时候会拥塞" → 需要历史与全局 → 非实时层
#   "现在拥塞了，先动谁"           → 需要当前状态   → 近实时层
#   "这一时隙的 PRB 怎么切"        → 需要时隙精度   → O-DU
这个例子里最值得注意的是「授权」二字。第 ④ 步里 Non-RT RIC 不只给了目标，还给了「允许你抢占 eMBB 资源」这个许可。没有这层授权，xApp 就成了一个可以任意牺牲其他业务的黑箱——它为了达成自己的时延目标，完全可能把整片区域的 eMBB 体验搞垮。所以 A1 策略不仅是「告诉你目标」，同时也是「划定你的行动边界」。这是两级 RIC 分层最本质的安全价值，比「时间尺度不同」这个表面理由更重要。

两级之间的边界怎么划

实际项目里经常纠结「这个功能该做成 rApp 还是 xApp」。三个判据基本够用：

判据倾向 rApp（非实时）倾向 xApp（近实时）
需要的数据窗口需要历史、跨小区、跨时段的全局视图只需要当前几百毫秒的局部状态
决策的时效性晚几分钟没关系晚 1 秒就没意义了
计算复杂度可以很重（模型训练、全网优化求解）必须很轻（每周期都要跑完）
出错的可挽回性有时间发现并回退可能在被发现前已经影响大量用户

一个实用经验：把「学习/推理模型」放在 rApp，把「用模型的输出做快速决策」放在 xApp。训练在非实时层（有数据、有算力、失败无害），推理结果以策略或轻量模型的形式经 A1 下到近实时层执行。这样既拿到了 AI 的能力，又没有把重计算塞进 100 ms 的闭环里。

06

rApp / xApp

RAN 上的"App Store"

rApp（跑在 Non-RT RIC）

非实时应用：如网络规划、能效优化、异常检测、训练供 xApp 使用的模型，再通过 A1 下发策略。它访问平台数据与服务用的是标准化的 R1 接口。

xApp（跑在 Near-RT RIC）

近实时应用：如流量引导、切换优化、干扰管理、准入控制、切片资源保障——通过 E2 直接影响 O-CU/O-DU 的行为。

rApp/xApp 可由第三方开发，这正是 O-RAN "智能化 + 开放生态"的落地形态——类似给 RAN 装了一个可编程的 App 平台，打破了"优化算法只能来自设备商"的格局。

为什么需要 R1 这条接口

xApp 有 E2 可用（那是它控制网元的通道），但 rApp 并不直接连网元——它跑在 Non-RT RIC 里，需要的是「访问平台的数据与服务」。如果这一层不标准化，每个 rApp 就得针对具体某家的 Non-RT RIC 实现写一遍，「第三方生态」就退化成「某家的插件生态」。这就是 R1 接口的意义：把 rApp 与 Non-RT RIC 框架之间的服务注册、发现、数据订阅、A1 策略管理等能力标准化，让 rApp 可以在不同厂商的 Non-RT RIC 上运行。

三条接口的分工可以这样记：R1 是「App 找平台要东西」，A1 是「上层给下层下策略」，E2 是「下层去动网元」。方向和层级都不一样，不要混为一谈。

生产陷阱：App 生态的现实门槛

  • 权限模型必须先于 App 存在。一个 xApp 能读到 UE 级的测量报告，就意味着它能看到用户的位置与行为特征；能改切换参数，就意味着它能影响服务质量。「哪个 xApp 能订阅什么、能下发什么控制」必须由平台强制，而不是靠 App 自律。这件事没做，多厂商 App 就上不了生产网。
  • 组合验证的成本是乘法关系。单个 xApp 的测试很便宜，但 n 个 xApp 的组合是 2ⁿ 量级。现实做法是限定同时生效的 xApp 数量、并按「作用域是否重叠」分组——重叠的必须一起验证，不重叠的可以独立上线。
  • E2 服务模型的支持程度决定了 App 的可移植性。xApp 要通过 E2 做事，得依赖网元支持相应的 E2 服务模型（指标上报类、RAN 控制类等）。网元只实现了指标上报而没实现控制类，那么这台网元上只能跑「监控型」xApp。采购网元时如果没把需要的服务模型写进要求，后面装了 RIC 也用不上。
  • 「谁负责」在多厂商组合里是空白。xApp 来自 A 家、Near-RT RIC 来自 B 家、网元来自 C 家，出了问题三方都能证明自己合规。这不是技术问题，但它是 App 生态目前最大的实际阻力——也是为什么现网里跑的 xApp 大多还是与 RIC 同厂商的。

综合题：给一个新建网络，怎么划分网元部署位置

这是本篇所有内容的收敛点，也是这个方向最常被问的综合题。关键在于顺序——从约束出发，而不是从「我想用什么架构」出发。

# 给一个新建网络划分网元部署位置：一条可执行的决策顺序

第 0 步 · 先把不可协商的约束列出来（这些不是选择题）
  ├─ O-RU 必须在天面，没有例外。
  ├─ O-DU 到 O-RU 的光纤单向时延必须落在前传预算内（十几公里量级）。
  └─ 每个放 O-DU 的位置都必须能拿到满足要求的时间源。

第 1 步 · 看光纤：这决定了 O-DU 能不能集中
  有到候选边缘机房的直连/波分光纤，且按绕行系数折算后仍在预算内？
    ├─ 是 → 候选 C-RAN：O-DU 集中到边缘机房
    └─ 否 → 只能 D-RAN：O-DU 留在站点
  ★ 逐站判断，不要整片区一刀切。同一个城市三种形态并存是常态。

第 2 步 · 看业务：这决定了 O-CU-UP 要不要下沉
  有 URLLC / 本地分流 / 数据不出园区的需求？
    ├─ 是 → O-CU-UP 与 UPF 一起下到边缘，O-CU-CP 留中心（CP/UP 分离部署）
    └─ 否 → CP 与 UP 一起放区域 DC，运维最简单，别自找麻烦

第 3 步 · 看规模：这决定了 O-CU-CP 集中到什么程度
  站点数少（几十个）  → CU 与 DU 同址即可，池化收益不值那条中传
  站点数多（几百以上）→ CU 集中到区域 DC，池化收益明显
  ★ 但要核算故障域：一个 CU-CP 带多少个 DU 是可接受的爆炸半径？

第 4 步 · 看机房条件：这一步会否决前面的结论
  候选边缘机房有没有：足够的电、空调、承重、防尘、可维护的进出通道？
  有没有可靠的时间源与备份（GNSS 天面位置、上游 PTP 路径、保持能力）？
    └─ 任一项不满足 → 退回 D-RAN，哪怕光纤条件很好
  ★ 这一步被跳过的次数最多，代价也最大：机房不达标的站点会在夏天高温、
     雨季进水、市电波动时集中出问题，而那时已经没有便宜的补救办法了。

第 5 步 · 放 RIC 与 SMO
  Near-RT RIC     → 与 O-CU 同址（区域/边缘 DC）；10 ms 闭环不需要更近
  SMO / Non-RT RIC → 中心 DC 或运营商 IT 云，一套管全网

第 6 步 · 反过来验算三份预算
  带宽：前传条数 × 每条带宽 → 边缘机房的接入与上行容量够不够？
  时延：F1 时延加到接入时延与切换中断时间上，还满足指标吗？
  同步：从时间源到最远那个 O-RU，逐跳累加的误差还在预算内吗？

# ★ 顺序不能颠倒：约束 → 传输 → 业务 → 规模 → 机房 → 验算。
#   从「我想用哪种架构」倒推的方案，几乎一定在第 1 步或第 4 步崩掉。
#   而这两步都不是无线专业能独立回答的问题——所以这道题真正考的是
#   「你知不知道该去问传输和基建」。
场景推荐形态为什么
密集城区，光纤资源好C-RAN（DU 集中）+ CU 区域集中站点密、需要小区间协同、机房条件相对好，池化收益最大
郊区 / 农村宏站D-RAN（CU+DU 在站点）站点稀疏、光纤匮乏、集中的传输成本超过省下的算力成本

室内分布系统DU 集中在楼内机房，Cat A O-RU前传距离极短，天线数不多，Cat A 足够且成本低

🎯 本篇要点回顾
  • 网元清单：O-CU-CP / O-CU-UP / O-DU / O-RU（数据通路）+ Near-RT RIC / Non-RT RIC / SMO（智能与管理）+ O-Cloud（承载平台）。
  • 协议层归属：O-CU-CP 管 RRC + PDCP-C，O-CU-UP 管 SDAP + PDCP-U，O-DU 管 RLC + MAC + High-PHY，O-RU 管 Low-PHY + RF。两个切点是 Option 2 与 Option 7-2x。
  • 一条贯穿的因果链：时间尺度 → 可搬移距离 → 部署位置。符号级搬不动，时隙级最多十几公里，会话级可以搬几百公里。
  • CP/UP 分离的价值是「两种负载独立扩缩 + 用户面可下沉」，接口是 E1；代价是两份状态要对账、UP 选择要设计、排障要看三份日志。
  • 部署形态由光纤和机房条件决定，不由架构偏好决定；一张现网通常同时跑着 D-RAN、C-RAN 与 UP 下沉三种形态。
  • SMO 与 O-Cloud：SMO 通过 O1 管网元业务配置、通过 O2 管云平台资源（IMS）与网元部署（DMS）；O-Cloud 是被管对象而非管理者。
  • RIC 的边界：时隙级调度永远在 O-DU 里；Near-RT RIC 最快是 10 ms 量级，它改的是调度器的目标与约束，不是每时隙的分配。
  • 最痛的地方：O-Cloud 上跑 O-DU 的实时性配置（隔离四件套、大页、SR-IOV/DPDK、NUMA 对齐、时钟透传）是功能前提而非调优项，且失效方式是静默降级。

8.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础O-RAN 有哪些逻辑网元？每个网元承载哪些协议层？

    分两组答，条理会清楚很多。

    数据通路上的四个（自上而下）：

    • O-CU-CP：RRC + PDCP-C。UE 状态机、连接管理、移动性决策、安全模式。
    • O-CU-UP：SDAP + PDCP-U。QoS Flow 到 DRB 的映射、加密、重排序、头压缩。
    • O-DU：RLC + MAC + High-PHY。空口调度器、HARQ、LDPC 编解码、调制与资源映射。
    • O-RU：Low-PHY + RF。iFFT/FFT、CP 添加去除、数字前端、射频与天线。

    智能与管理侧的三个：Near-RT RIC（近实时闭环，跑 xApp）、Non-RT RIC（长周期策略与模型训练，跑 rApp，是 SMO 的一部分）、SMO（编排 + FCAPS）。再加上承载平台 O-Cloud。

    补充加分：两个切点要说得出来——CU 与 DU 之间是 3GPP 的 Split Option 2（切在 PDCP 与 RLC 之间），DU 与 RU 之间是 O-RAN 选定的 Option 7-2x（切在 PHY 内部的频域侧）。前者是 3GPP 的成果，O-RAN 只是沿用；后者才是 O-RAN 相对 3GPP 的实质增量，因为 3GPP 从没规定 DU 以下怎么切。

  2. 基础O-DU 和 O-RU 的实时性要求差在哪？为什么 O-RU 必须是专用硬件？

    差一个数量级，而且性质不同。

    O-DU 是时隙级硬期限。30 kHz 子载波间隔下时隙是 500 µs，它必须在这 500 µs 内收完上一时隙的反馈、跑完调度器、做完编码调制、并按前传发送窗把报文送出去。错过就是这一时隙的空口资源永久浪费。所以 O-DU 的指标是「最坏情况」而不是「平均值」——平均 200 µs 但每万次有一次 600 µs，就是每 5 秒丢一个时隙。

    O-RU 是符号级，数十微秒。30 kHz 下一个符号约 35.7 µs，它拿到频域 IQ 后必须在这个符号该发射的时刻之前完成 iFFT 与上变频，几乎没有缓冲余量。

    O-RU 必须是专用硬件有三条理由：① 这一段是定点数、固定流水、强时序的信号处理，FPGA/ASIC 的能效比通用 CPU 高一两个数量级；② 它必须紧挨射频前端与天线，物理上没有搬走的可能；③ 它包含 DAC/ADC、变频、功放这些本来就是模拟/射频器件的部分。而 O-DU 那一段虽然实时性也很紧，但它是浮点/整数的通用计算，用通用 CPU 加加速卡可以做——这正是 O-DU 能云化、O-RU 不能的分界。

  3. 基础SMO、Non-RT RIC、Near-RT RIC 三者是什么关系？O1 和 A1 的本质区别是什么？

    关系有三层：

    • Non-RT RIC 属于 SMO，是 SMO 内部的一个功能，不是与它并列的网元。它复用 SMO 从 O1 收来的 KPI、拓扑与配置视图。
    • Near-RT RIC 是独立网元，同时被 SMO 管理：部署走 O2，配置与告警走 O1。
    • Non-RT RIC 通过 A1 向 Near-RT RIC 下策略，Near-RT RIC 通过 E2 去动 O-CU/O-DU。

    O1 与 A1 的本质区别是命令式 vs 声明式：O1 下发的是确定的参数值（「这个小区功率设为 X」），A1 下发的是目标与约束（「这个切片的时延目标是 Y，允许你抢占 eMBB 的资源，自己想办法达到」）。

    加分点：指出这两条路都能改网络，所以作用域必须显式划分。不划分的现场后果很具体——运维通过 O1 改了一个参数，过一会儿发现被改回去了，于是报「配置下发失败」，而真正的原因是某个 xApp 正在按 A1 策略正常工作。能说出这个现象，说明是做过现网的。

  4. 基础O-Cloud 是什么？O2 接口管什么？它和 O1 管的是同一层东西吗？

    O-Cloud 是承载可虚拟化 RAN 网元的云平台——包含物理基础设施（服务器、网卡、加速卡）、虚拟化/容器化层，以及向 SMO 暴露的管理能力。它承载 Near-RT RIC、O-CU-CP、O-CU-UP、O-DU；不承载 O-RU（专用硬件），也不承载 SMO 自己（SMO 是它的管理者）。实际网络里 O-Cloud 是分层的多套——中心、区域、边缘规格差别很大，站点级那一套最苛刻。

    O2 是 SMO 与 O-Cloud 之间的接口，分成两类服务：

    • 基础设施管理（IMS）：清点资源、查容量与拓扑、订阅硬件告警——相当于云管平台。
    • 部署管理（DMS）：实例化网元、扩缩容、升级、回退、删除——相当于应用编排。

    分开的理由是两者变更节奏与责任人不同：基础设施半年一动，网元部署可能一周一动。

    O1 和 O2 管的不是同一层。O1 管「网元的业务配置」（这个小区功率多少、邻区是谁），O2 管「网元的存在与形态」（这个 O-DU 实例在哪台机器、什么版本、给了多少核）。同一个 O-DU 被两条接口同时管，但维度不重叠。混淆的直接后果是：出问题时不知道该找平台团队还是无线团队。

8.2 中级（区分熟练度）

  1. 中级为什么要把 CU 拆成 CU-CP 和 CU-UP？E1 承载什么？拆开之后多了哪些麻烦？

    拆的理由有四条，前两条最重要：

    • 两种负载的扩缩容曲线完全不同。控制面压力来自用户数与移动性事件率，用户面压力来自吞吐量。演唱会场景是「人多、不动、流量不大」（控制面重、用户面轻），固定无线接入恰好相反。合在一个网元里只能按两者的最坏情况一起买算力。
    • 用户面可以单独下沉。用户面时延直接等于用户感知，控制面时延只影响接入与切换。把 CU-UP 和 UPF 摆到边缘做本地分流能砍掉回传那一段 RTT，而 CU-CP 留在中心继续池化几百个站。
    • 故障域与升级节奏解耦：控制面升级动 RRC 状态机、风险高；用户面更像换一个转发进程。
    • 切片与多归属：一个 CP 可带多个 UP，能按切片、位置、业务类型把承载分流到不同 UP。

    E1 是纯控制接口，上面不跑用户数据。核心是让 CP 在 UP 上创建并维护「承载上下文」：Bearer Context 的建立/修改/释放、用户面密钥下发、GTP-U 隧道端点交换、无活动通知（供 CP 决定是否把 UE 转 INACTIVE 省电）、用量上报（供计费）、以及异常后的 Reset。一般性描述见 TS 38.460，应用协议 E1AP 见 TS 38.463。

    多出来的麻烦（这部分最能区分熟练度）：① 两份状态要对账，超时或重启会留下「CP 以为释放了、UP 还占着隧道」的幽灵承载，表现为资源缓慢泄漏；② 一个 CP 带多个 UP 时要设计 UP 选择算法，写歪了会负载严重不均；③ 用户面密钥要经 E1 下发，E1 跨机房时这就是密钥传输通道，必须上 IPsec/MACsec；④ 一次接入失败要看 DU、CP、UP 三份日志，没有统一的 UE 级关联标识和时钟同步就拼不起来；⑤ 原来的进程内调用变成两条网络接口，时延叠加到接入与切换指标上。

    细节加分：一次 UE 接入会触碰 E1 两次——先 Bearer Context Setup 拿到 UP 侧隧道端点，再在 F1 UE Context Setup 回来后用 Bearer Context Modification 把 DU 侧端点告知 UP。看到日志里「建了又改」是正常流程，不是重试。

  2. 中级D-RAN 和 C-RAN 怎么选？限制 C-RAN 集中半径的到底是什么？

    先纠一个常见误解：限制不是光纤能传多远。光纤跑 80 km 毫无压力。真正的限制是HARQ 时序与前传发送窗容不容得下这个往返——O-DU 必须在 O-RU 该发射的时刻之前把数据送到，上行也必须在 HARQ 反馈时刻之前解完码。

    算一下就清楚了：单模光纤里传播速度约 204 000 km/s，单向约 4.9 µs/km（工程按 5 µs/km 估）。若前传单向时延预算取百微秒量级，扣掉中间交换转发（两跳、每跳数微秒）与成帧抖动余量（约 20 µs），留给传播的大约 70 µs，对应约 14 km 光纤。再考虑光纤路由不是直线（绕行系数常按 1.3~1.6）、可能有波分设备、保护倒换后路径会变长，所以工程上常报「10 ~ 20 km」这个量级。

    怎么选：

    • 有满足预算的直连光纤 + 机房条件达标 → C-RAN。收益是算力池化、便于小区间协同（CoMP、干扰协调）、升级不用逐站上站。
    • 光纤拉不到或机房不达标 → D-RAN。代价是每站一套算力、利用率低、运维成本随站点数线性增长。

    加分点两条：① 逐站判断，不要整片区一刀切——光纤分布是历史造成的，同一个城市里三种形态并存是常态；② 机房条件常常比光纤更致命，电、空调、承重、防尘、时间源与备份任一项不达标就该退回 D-RAN，哪怕光纤很好。这一步被跳过的次数最多，代价在夏天高温和雨季集中爆发。

  3. 中级部署形态怎么影响前传预算？为什么 O-RAN 选 Option 7-2x 而不是切在 iFFT 之后？

    切点决定了前传上跑的是什么信号，而信号的性质决定了带宽随什么变化。

    切在 iFFT 之后（Option 8，也就是传统 CPRI 那一档），前传上是时域采样流：速率只由采样率、天线数、量化位宽决定，和这一时隙实际有多少 UE、占了多少 PRB 完全无关。半夜一个用户都没有，链路照样跑满。这正是老 CPRI 前传贵得离谱、且完全无法优化的根源。

    切在 Option 7-2x（PHY 内部的频域侧），前传上是频域 IQ：只传实际占用的资源元素，带宽随负载起伏，还能做块浮点之类的压缩。同一个 100 MHz 小区，两种切点的前传带宽可以差好几倍。

    部署形态的影响体现在三处：

    • 集中度决定条数。D-RAN 下前传是站内几十米，成本可忽略；C-RAN 下每个 O-RU 都要一条前传拉到边缘机房，「条数 × 每条带宽」直接变成那个机房的接入容量需求，这经常是 C-RAN 方案真正的瓶颈。
    • Category A/B 决定每条带宽。Cat A 的 O-RU 在 O-DU 做预编码，前传流数等于天线端口数；Cat B 在 O-RU 做预编码，前传流数等于层数。大规模 MIMO（32T32R、64T64R）下层数远小于天线数，Cat B 省得非常明显，这时候几乎只能选 B。
    • 集中半径决定时延预算怎么分。拉得越远，留给交换、成帧、处理的余量越少，对中间传输设备的确定性要求越高。

    具体的带宽算式与四个平面各自怎么跑，属于前传专题的内容。

  4. 中级Category A 和 Category B O-RU 有什么区别？什么时候必须用 B？

    唯一的本质区别是预编码 / 波束加权做在哪：

    • Category A：预编码在 O-DU。前传上传的是每个天线端口的、已完成预编码的 IQ，所以前传流数 = 天线端口数。O-RU 简单、便宜、互通容易。
    • Category B：预编码在 O-RU。前传上传的是每个空间层的 IQ 加上波束加权信息，所以前传流数 = 层数。O-RU 要有矩阵运算能力，更贵，互通也更难（波束加权的表达方式与能力协商都更复杂）。

    什么时候必须用 B：当天线数远大于层数时。典型是 32T32R、64T64R 的大规模 MIMO 宏站——Cat A 下前传带宽随天线数线性增长，很快就撑不住；Cat B 只随层数增长（常见 4~16 层），差距是数倍。反过来，4T4R / 8T8R 的中低配站型和室分场景，Cat A 足够且成本与互通风险都低。

    工程提醒：类别必须在选型阶段就锁定，而且这是个高频的对接故障点。O-DU 按 Cat A 发（已预编码的天线端口数据）、O-RU 按 Cat B 期待（层数据 + 权重），两边完全对不上，现象是链路 up、管理面正常，但小区就是起不来。混用不同类别的 O-RU 时，管理面必须能自动识别并按类别配置。

8.3 高级（体现深度）

  1. 高级把 O-DU 跑在通用服务器上，要解决哪些问题？

    核心矛盾一句话：O-DU 有几百微秒的硬期限，而通用服务器和通用 Linux 都是为「平均吞吐」优化的，不是为「最坏时延」优化的。默认配置下，能让一个线程停顿几十甚至几百微秒的机制有十几种。要解决的是这些：

    • CPU 隔离四件套：isolcpus（摘出负载均衡域）+ nohz_full（免周期时钟中断）+ rcu_nocbs（RCU 回调挪走）+ irqaffinity（中断赶走）。最常漏的是最后一条——不配它系统照样跑，只是每来一个中断就赌一次期限。而 nohz_full 只在「该核上恰好只有一个可运行任务」时才真的免中断，所以必须和「一核一实时线程」的规划配套。
    • 大页：1 GiB 大页，避免 TLB miss 与页表遍历带来的不确定停顿；DPDK 的内存池也依赖它。
    • SR-IOV + DPDK：前传报文不能走内核网络栈或虚拟交换机。VF 直通给容器，用户态轮询收发，轮询线程独占核。
    • NUMA 对齐：CPU、大页、网卡 VF、加速卡必须在同一个 NUMA 节点。这是最容易在「看起来都配了」的情况下漏掉的一环，现象是「同样的镜像，这台机器就是比那台抖」。
    • 频率与 C-state：governor 设 performance、限制最大 C-state。反直觉的一点是低负载时反而更容易抖，因为核在打瞌睡，唤醒要几十微秒。
    • 时钟透传：O-DU 必须拿到网卡的硬件时钟（PHC），不能用系统软件时钟；PHC 设备要透传进容器。
    • FEC 加速：LDPC 编解码在高吞吐下吃掉大量 CPU，通常用加速卡（内联或旁挂两种形态）。
    • 容器编排侧：requests 必须与 limits 完全相等且 CPU 是整数（否则拿不到 Guaranteed QoS 就拿不到独占核）；节点上 kubelet 的 CPU Manager 要是 static 策略、Topology Manager 要是 single-numa-node。

    最能体现深度的一点：这些配置的失效方式是「静默降级」。CPU Manager 没开成 static，Pod 照样起来、业务照样通、小流量压测也没问题——只是那些核变成了共享核，抖动悄悄回来了。所以每一项都要有「运行时验证动作」而不是「配置检查」：看容器实际拿到的 cpuset、看实时线程的 psr 是否落在隔离核里、看 /proc/interrupts 在实时核上的增量是否为零。配置文件写对了不等于生效了。

    再补一句排障经验：这类问题上线几周后才偶发，根因高度集中在「这台机器和那台机器不一样」——漏了内核参数的新节点、BIOS 是出厂默认的机器、被调度到实时核上的监控 DaemonSet、驱动版本不一致导致中断合并默认值不同。所以第一件基础设施工作不是调优，而是把节点状态做成可断言、可漂移检测的。

  2. 高级给一个新建网络，你怎么划分各网元的部署位置？

    关键是顺序：从约束出发，而不是从「我想用什么架构」出发。按下面六步走，答案自然就出来了。

    1. 列出不可协商的约束：O-RU 必须在天面；O-DU 到 O-RU 的单向时延必须落在前传预算内（十几公里量级）；每个放 O-DU 的位置都必须能拿到满足要求的时间源。
    2. 看光纤——决定 O-DU 能不能集中。有到候选边缘机房的直连/波分光纤、且按绕行系数折算后仍在预算内，才有 C-RAN 的可能；否则只能 D-RAN。逐站判断，不要整片区一刀切。
    3. 看业务——决定 O-CU-UP 要不要下沉。有 URLLC、本地分流、数据不出园区的需求，就把 UP 和 UPF 下到边缘、CP 留中心；没有就 CP+UP 一起放区域 DC，别自找麻烦。
    4. 看规模——决定 O-CU-CP 集中到什么程度。几十个站，CU 与 DU 同址即可，池化收益不值那条中传；几百个以上，集中到区域 DC 收益明显。同时核算故障域：一个 CU-CP 带多少 DU 是可接受的爆炸半径。
    5. 看机房条件——这一步会否决前面的结论。电、空调、承重、防尘、进出通道，以及时间源与其备份（GNSS 天面位置、上游 PTP 路径、保持能力），任一项不满足就退回 D-RAN，哪怕光纤条件很好。
    6. 反过来验算三份预算：带宽（前传条数 × 每条带宽 → 边缘机房接入容量够不够）、时延（F1 时延加到接入时延与切换中断时间上是否还满足指标）、同步（从时间源到最远那个 O-RU，逐跳累加误差是否还在预算内）。

    RIC 与 SMO 的位置是顺带的结论：Near-RT RIC 与 O-CU 同址（10 ms 闭环不需要更近），SMO / Non-RT RIC 放中心 DC 或 IT 云，一套管全网。

    这道题真正考的东西：第 2 步和第 5 步都不是无线专业能独立回答的问题。能主动说出「这两步我要去问传输和基建」，比给出一个漂亮的架构图更有说服力——因为从架构偏好倒推的方案，几乎一定在这两步崩掉。另外要敢于说「同一张现网会同时跑三四种形态」，这是实话，也是 O-RAN 的价值所在：几种形态用的是同一套接口和同一套管理面。

  3. 高级多厂商的 O-DU 与 O-RU 都通过了一致性测试，却接不上。你怎么排查？

    先把问题的性质说清楚：这类故障的共同特征是「两端都没有错，只是在合规范围内选了不同的可选项」。所以它不是靠调试解决的，而是靠开站前那张对接参数表解决的。

    排查顺序（按命中率从高到低）：

    1. 管理面的 YANG 模型版本与能力集是否一致——这里出问题占比最高。表现是下发的配置里带了对端不认识的节点导致 NETCONF 报错，或者节点名对但语义变了、配下去不生效。
    2. IQ 压缩方法与位宽是否一致——块浮点、块缩放、µ-law、不压缩，两端支持集合不交叉，或都支持块浮点但默认位宽不同。星座图糊掉一定是这一层。
    3. C 平面的 section type 支持集合与波束配置——表现是「能建站但接入失败」，因为普通业务用的那类支持了，随机接入之类的特殊信道那一类没支持。
    4. Category A / B 是否匹配——一端按已预编码的天线端口数据发，另一端按层数据加权重期待，完全对不上。
    5. 最后才怀疑同步——而且要注意「PTP 已锁定」不等于「时间对齐误差满足空口要求」。前者只说明这一跳的伺服收敛了，后者是从时间源一路累积到 O-RU 天面的端到端预算，必须实测。

    兼容矩阵的维度（这是这道题的深度所在）：前传管理面的 YANG 模型版本、C/U 平面的 section type 集合、压缩方法与位宽、Category 与波束能力、同步方式与拓扑、F1/E1 的可选 IE 与异常恢复过程、以及「网元 ↔ O-Cloud 平台」的版本依赖（DU 常依赖特定内核、驱动或加速卡固件版本）。这些维度之间是笛卡尔积关系——厂商一体化交付时它们被「同一个团队的默认值」自动对齐了，开放之后每一个默认值都得显式约定。

    加分点：指出 O-RAN 自己的应对思路是互通测试规范里的「测试档位」概念——把一堆可选项固化成几组预先商定的组合，两端声明支持哪一档，从而把 n 维可选项的笛卡尔积压成几个已验证的组合。这和 USB、PCIe 生态里的一致性档位是同一个套路。

    还可以补一句结论性的判断：O-RAN 并没有增加系统的复杂度，它把原本隐藏在单厂商内部的复杂度显式化了，并把消化这部分复杂度的责任从设备商转移给了运营商或系统集成方。这既是它最大的价值，也是它最大的落地阻力。

  4. 高级Near-RT RIC 的能力边界在哪？两个 xApp 打架怎么办？E2 断链时网元该做什么？

    边界：Near-RT RIC 的最快闭环是 10 ms 量级，比一个时隙（125 ~ 1000 µs）慢一到两个数量级。所以「RIC 让 AI 接管无线调度」这种说法是不成立的——时隙级的 PRB 分配、MCS 选择、HARQ 永远在 O-DU 的 MAC 调度器里。RIC 能做的是改变调度器的目标与约束（提高某个切片的权重、把某个 UE 引导到别的小区、对新会话做准入限制），而不是替调度器决定这一时隙给谁多少 PRB。把这条边界说清楚是判断一个人是否真懂 RIC 的分水岭。

    xApp 冲突：这是 RIC 最被低估的风险。举个具体例子——一个 xApp 做负载均衡（倾向把 UE 从拥塞小区推走），一个做覆盖优化（倾向把 UE 拉回信号最好的小区）。两个各自都对，但作用在同一批 UE 的同一组切换参数上，结果是参数以闭环周期为节拍来回摆动，用户体验比不装任何 xApp 更差。这类问题在单 xApp 测试里绝对暴露不出来。

    应对是三层：① 平台侧必须有冲突消解机制，决定同时想改同一参数时谁生效；② 权限模型要先于 App 存在——哪个 xApp 能订阅什么、能下发什么控制，由平台强制而不靠 App 自律；③ 按「作用域是否重叠」分组验证，重叠的必须一起测，不重叠的可独立上线。所以「装了几个 xApp」不是能力指标，「几个 xApp 组合起来验证过」才是。

    E2 断链：网元必须能回退到内置算法继续工作，绝不能让小区退服。但「回退」本身是需要设计和测试的，有两个具体问题要回答：回退瞬间参数会不会跳变（跳变会造成一次可感知的体验波动）？RIC 恢复后会不会又跳回来（形成第二次波动）？把「E2 断链」做成常规演练项，比事后处理有效得多。

    最后补一个容量视角的深度点：一个 Near-RT RIC 可能连着成百上千个 E2 节点，订阅粒度设错，上报流量能轻松打到 Gbps 量级，同时吃掉网元可观的一块 CPU。所以订阅设计（上报什么、多久一次、按 UE 还是按小区聚合）是容量规划的一部分，不是 xApp 作者能自己随便定的事——这一点在方案评审时经常被漏掉。
