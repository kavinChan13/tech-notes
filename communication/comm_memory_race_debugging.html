通信软件的内存与竞态排查实战

通信软件的缺陷分布很有特色：畸形报文打的是解析器，会话销毁撞的是工作线程回调，7×24 长稳照的是每连接泄漏，多把锁换来的是死锁。本篇不重讲工具用法，只讲通信场景里怎么选工具、能不能在设备上跑、以及三个从报告读到根因的完整复盘。

01

四类高发缺陷

通信软件的缺陷分布不是随机的

边界。Memcheck / Helgrind / Massif 的完整用法见 Valgrind 全套指南；Sanitizer 的选项与内部实现见 Sanitizers 指南 与 Sanitizer 内部原理；泄漏治理、死锁调试、崩溃调试的通用方法见 内存泄漏治理、死锁调试、崩溃调试。本篇只讲通信场景特有的部分：设备上能不能跑、时序约束怎么绕、以及这四类 bug 的固定形状。
① 畸形报文 → 解析越界长度字段没校验就当偏移用、TLV 嵌套没限深度、可选字段缺失时仍按固定偏移读。唯一一类既是稳定性问题又是安全漏洞的缺陷，因为输入完全由外部控制。
② 会话销毁 vs 回调 → UAF会话 teardown 时，定时器回调、工作线程、通知推送可能仍持有裸指针。表现为悬垂 this。触发条件是"正好在这个时刻断链"，所以永远是偶发。
③ 每连接泄漏 → 长稳 RSS 上扬单次泄漏几 KB，功能测试完全看不见；7×24 跑一周、几十万次连接后 RSS 涨几个 G，被 OOM killer 收走或触发倒换。
④ 锁序不一致 → 死锁会话锁与管理器锁的加锁顺序在不同路径上相反。通信软件里尤其容易，因为"从会话找管理器"和"从管理器遍历会话"两个方向都天然存在。
🏗️ 类比：这四类缺陷像建筑的四种病。① 解析越界是大门没验票——任何人递张假票就能进后台，是唯一会被人主动攻击的一类。② UAF 是拆房时还有人在里面——拆迁队和住户各按自己的时间表行动，平时错开，偶尔撞上就是事故。③ 泄漏是每天掉一点墙皮——今天看不出来，一年后地下室堆满。④ 死锁是两条单行道对开——路修好那天就注定了，只是要等两辆车恰好同时来。
四种病要用四种不同的检查手段，用错了就是"体检全过但楼在塌"。
为什么强调"分布不是随机的"？因为它决定了资源该往哪投。通信软件的输入是不可信的字节流、生命周期是并发拆除的会话、运行时长以年计——这三件事直接生成了前三类缺陷，而普通业务软件（输入受控、对象生命周期由请求边界界定、进程天天重启）对它们的敏感度低得多。所以通信项目的质量投入应当集中在：解析器 fuzz、会话生命周期的所有权模型、长稳趋势告警。把力气均摊到所有代码上是低效的。
02

工具选型矩阵

开销量级决定了它能跑在哪

工具抓什么速度损耗内存开销能上带实时/同步约束的节点？CI 里怎么排
ASan堆/栈越界、UAF、double-free~2x~2–3x（红区 + 隔离区）⚠️ 实验室节点降速可行；生产不建议必备门禁：单测 + 集成测试全跑
TSan数据竞争、锁序问题~5–15x~5–10x（影子内存）❌ 基本不可能必备门禁：并发相关测试专跑一轮
UBSan未定义行为（非对齐、溢出、无效枚举）~1.2x可忽略✅ 开销最小，可长期开着全量开，成本几乎为零
LSan内存泄漏（进程退出时快照）~1x（含在 ASan 里）低✅ 但要能正常退出才出报告随 ASan 一起；注意"退出前清理"要真做
Memcheck越界、UAF、未初始化读、泄漏（最全）10–50x高❌ 绝对不能（见 §03）夜间任务跑关键模块单测
Helgrind数据竞争 + 锁序（含 happens-before）20–100x很高❌只跑抽出来的小规模复现用例
DRD数据竞争（比 Helgrind 轻，报告更少噪声）~20x中❌Helgrind 噪声太大时的替代
Massif堆使用快照曲线（谁占的内存）~5–20x中❌ 但可在实验室低负载跑长稳后分析用，不适合门禁
Callgrind指令级 profile / 调用图~50x中❌不进 CI，人工分析用
heaptrack / tcmalloc-prof堆分配来源与增长趋势~1.1–1.5x中✅ 可以上生产长稳环境常开，定期导快照
选型口诀：先按"能跑在哪"筛，再按"抓什么"选。通信软件的现实约束是：大部分 bug 只在真实负载、真实对端、真实时序下才出现，而能承受真实负载的工具只有 UBSan、heaptrack 这一档（1–1.5x）；ASan（2x）在实验室降速环境勉强可用；TSan 与 Valgrind 全家只能跑"抽出来的模块 + 构造的用例"。
所以正确的工作流是：把可疑模块从设备里抽出来，在 x86 开发机上用最狠的工具（TSan + Memcheck）跑构造的用例，而不是想办法把 Valgrind 塞进设备。"抽得出来"本身就是一项架构要求——解析器、状态机、会话表都应该能脱离硬件独立编译与测试。
ASan 与 TSan 不能同时开（影子内存布局冲突），必须跑两轮。CI 里的推荐排布：① 每次提交：普通构建 + UBSan 全量单测（几乎不加时间）；② 每次 PR：ASan 一轮（单测 + 集成）；③ 每晚：TSan 一轮（并发测试，跑够时长与并发度）+ 解析器 fuzz 增量；④ 每周：Memcheck 跑核心模块 + 7 天长稳的趋势复核。具体流水线写法见 CMake / CI 指南。
03

为什么实时节点不能上 Valgrind

它不只是"慢"，它会掩盖真 bug 并制造假 bug

Valgrind 的工作方式：它是一个动态二进制翻译框架——把你的机器码翻译成中间表示、插入检查、再重新生成执行。所以它不是采样、也不是插桩后原速运行，而是整个程序都在解释执行。这决定了它的两个特性：检查极其彻底（连未初始化读都能抓），以及时序被整体拉长 10–50 倍且不均匀。

"不均匀"是关键。ASan 的 2x 开销大致均匀分布，程序的相对时序基本保持；Valgrind 的开销集中在访存与分支密集处，不同代码路径被拉长的倍数完全不同。对通信软件来说，这会造成三类后果：

制造假 bug协议超时被击穿：对端 200 ms 没收到回应就重传/断链，于是你看到的是"一堆重传与断链"，而不是原本要查的问题。心跳丢失 → 对端判死 → 触发倒换 → 会话重建，整个测试变成在观测超时机制而不是原 bug。更糟的是看门狗复位：带硬实时约束的设备（O-DU 的 slot 处理）有硬件看门狗，喂狗线程被拖慢就直接重启，你连日志都拿不到。
掩盖真 bug竞态的触发窗口通常是几十到几百纳秒。Valgrind 下所有操作都变慢，但相对时序被打乱——原本"恰好同时"的两个操作现在被拉开了，竞态不再复现。你跑了三天 Memcheck 干干净净，回到原速环境 bug 依旧。这是最浪费时间的一种情形。
与同步机制冲突带 PTP 的节点上，ptp4l / phc2sys 靠精确的收发时间戳做伺服。整个进程被拖慢会让时间戳质量崩坏，PTP 状态机可能判定失锁并进入 holdover——这时候设备的所有时序行为都变了，测出来的东西没有参考价值。
这是"观测行为改变被观测对象"的教科书案例，而通信软件对它格外敏感，因为通信软件的正确性大量依赖时间（超时、重传、心跳、slot 边界、PTP 伺服）。一个纯计算程序放慢 50 倍只是慢，一个协议栈放慢 50 倍就是换了一套完全不同的运行条件。

3.1 四条可行的替代路径

① 抓包离线重放首选。在生产/实验室用 tcpdump / 端口镜像抓下故障时段的报文，然后在开发机上把这段 pcap 喂给抽出来的协议栈模块，此时可以随便上 Memcheck / ASan / TSan。优点是输入完全真实且可重复——这是排查解析类 bug 的最快路径。前提是模块能脱离硬件运行（回到 §02 那句架构要求）。
② 模块抽出做单测把解析器、状态机、会话表做成不依赖硬件与网络的库，用构造的用例（含畸形报文、乱序事件、并发 teardown）跑最狠的工具。竞态类 bug 要在单测里主动加压：多线程反复"建会话—发消息—拆会话"几百万次，配 TSan。
③ 实验室降速跑如果必须在设备上跑：把负载降到 1/50、同步把所有协议超时按同样倍数放大（这一步最常被漏掉——只降负载不改超时，一样会被超时机制淹没）、关掉看门狗、把 PTP 相关测试单独隔离。能查泄漏与越界，查不了竞态。
④ 上低开销工具非要在真实负载下观测：UBSan（1.2x，可长期开）+ heaptrack / tcmalloc profiling（1.1–1.5x）+ eBPF 动态追踪（几乎零侵入，见 §06）。这一档不能抓竞态，但能抓泄漏与 UB，而且是唯一能在真实时序下工作的。
04

三个复盘案例

从报告读到根因的完整路径

案例 1 · TLV 长度字段未校验 → 堆越界读 越界 / 安全

现象：某型对端设备接入后，管理面进程每隔几十分钟崩一次；换回原厂对端就正常。core dump 的栈在解析函数里，但每次崩的位置不同，有时甚至栈都是坏的。

第一步：把它变成可重复的。崩溃随机说明读到的内容不确定——典型的越界。先在故障时段抓包（tcpdump -s0 -w），拿到 pcap 后写一个 20 行的重放程序把报文逐个喂给解析器，在开发机上用 ASan 编译运行。第三个报文就炸了：

==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x60300000f0e8
READ of size 4 at 0x60300000f0e8 thread T0
    #0 parse_tlv(const uint8_t*, size_t) tlv.cc:47
    #1 handle_msg(Session&, Buf&)       session.cc:212
    #2 replay_main()                    replay.cc:31

0x60300000f0e8 is located 8 bytes to the right of 96-byte region [0x60300000f080,0x60300000f0e0)
allocated by thread T0 here:
    #0 operator new(unsigned long)
    #1 Buf::Buf(size_t)                 buf.cc:14

怎么读这份报告——三行关键信息，缺一不可：

  • READ of size 4：读 4 字节 → 在读一个 uint32_t，符合"读长度字段/读 value"。
  • 8 bytes to the right of 96-byte region：这是最有价值的一行。缓冲只有 96 字节，而访问落在结束后 8 字节处 → 偏移算到了 104。说明偏移来自报文里的某个字段，而那个字段没有和缓冲长度比对过。
  • allocated by ... Buf::Buf：确认越界的对象就是 recv buffer 本身，不是别的结构被踩。

根因代码：

❌ 长度字段直接当偏移用
while (off + 4 <= len) {          // 只检查了 T+L 这 4 字节
  uint16_t type, vlen;
  std::memcpy(&type, p + off,     2);
  std::memcpy(&vlen, p + off + 2, 2);
  type = ntohs(type); vlen = ntohs(vlen);

  handle_value(p + off + 4, vlen);  // ⚠️ vlen 完全来自对端！
  off += 4 + vlen;                  // ⚠️ 还可能溢出回绕
}
// 对端把 vlen 填成 100，实际只剩 8 字节 → 越界读 92 字节
// 这不是对端"坏"：它可能只是用了不同的可选字段组合，
// 而我们从没验证过这条路径。
✅ 先校验再解析 + span 边界
std::span<const std::byte> buf{p, len};
size_t off = 0;
while (off + 4 <= buf.size()) {
  auto type = read_be<uint16_t>(buf.data() + off);
  auto vlen = read_be<uint16_t>(buf.data() + off + 2);

  // ① 剩余空间检查（用减法，避免 off+4+vlen 溢出回绕）
  if (vlen > buf.size() - off - 4) return Err::kTruncated;
  // ② 语义检查：这个 type 允许的长度范围
  if (!len_ok(type, vlen))         return Err::kBadLength;

  // ③ 传子 span，被调用方拿不到越界的能力
  if (auto e = handle_value(type, buf.subspan(off + 4, vlen)); e)
    return e;
  off += 4u + vlen;
}
if (off != buf.size()) return Err::kTrailingGarbage;  // ④ 不容忍尾部残留
return Err::kOk;
三条可复用的教训。① 剩余空间检查一律用减法（vlen > size - off - 4）而不是加法（off + 4 + vlen > size）——后者在 size_t 上会因溢出回绕而把检查变成恒真。② 传 span 而不是"指针 + 长度"：被调用方从类型上就拿不到越界能力，这是把"约定"变成"编译期保证"（见 现代 C++ 那篇）。③ 这个 bug 本该被 fuzz 在第一天抓到：随机变异 vlen 字段是 libFuzzer 最容易发现的模式之一（见 §07）。它能活到现场，说明解析器从来没被 fuzz 过。

顺带说明为什么 Memcheck 在这里不如 ASan：Memcheck 也能报这个越界，但它对堆块之间的越界依赖红区大小，小幅越界（比如只越 4 字节且落在同一个 chunk 的 padding 里）可能漏报；ASan 的红区是明确插入的且报告直接给出"距离哪个对象右侧多少字节"，定位效率高得多。而且 ASan 只有 2x 开销，能直接跑集成测试。越界类问题优先 ASan，Memcheck 留给"未初始化读"这类 ASan 抓不到的。

案例 2 · 会话 teardown 与定时器回调竞态 → UAF 竞态 / 悬垂

现象：链路抖动频繁的现场，进程每天崩 1–2 次。栈有时在定时器线程、有时在工作线程，崩的对象是会话结构。加了日志之后不复现了（典型的 Heisenbug——日志把时序拉开了）。

第一步：判断是竞态还是纯逻辑错误。"加日志就不复现"+"崩的位置随机"+"与链路抖动强相关"三条同时成立，基本可以定性为销毁与使用的竞态。链路抖动 = 频繁断链 = 频繁 teardown，正好是触发窗口。

第二步：构造复现。不要指望在设备上抓。把会话管理抽成单测，开 8 个线程反复做「建会话 → 挂 10 ms 定时器 → 立即 teardown」，跑 TSan：

WARNING: ThreadSanitizer: heap-use-after-free (pid=8123)
  Read of size 8 at 0x7b0400001040 by thread T3:
    #0 Session::on_timer()        session.cc:301
    #1 TimerWheel::tick()         timer.cc:88

  Previous write of size 8 at 0x7b0400001040 by thread T1:
    #0 operator delete(void*)
    #1 SessionMgr::teardown()     mgr.cc:145

  Location is heap block of size 512 at 0x7b0400001040 freed by thread T1

报告的读法：TSan 直接给出了两个线程 + 两条栈——T3 在读，T1 已经 free 了。这比 core dump 强的地方在于它同时给出了释放方的栈，根因一眼可见：teardown() 删了会话，但时间轮里还挂着指向它的回调。

❌ 裸指针回调 + "取消定时器"不可靠
void SessionMgr::teardown(SessionId id) {
  auto* s = map_[id];
  timer_.cancel(s->timer_id);   // ⚠️ 看似取消了
  map_.erase(id);
  delete s;                     // ⚠️ 但回调可能已经在跑
}
// 竞态窗口：tick() 已经从时间轮取出这个回调、
// 正准备调用（或已进入 on_timer 但还没读成员），
// 此时 cancel() 找不到东西可取消，delete 照常执行。
// → on_timer 里的 this 悬垂。
// 窗口只有几十纳秒，但一天几万次 teardown 就够了。
// ⚠️ 关键认识："取消"永远无法覆盖"已取出待调用"，
// 除非取消与调用在同一个串行上下文里。
✅ weak_ptr：让回调自己判断对象还在不在
// 会话由 shared_ptr 持有，定时器只持 weak_ptr
void SessionMgr::arm(std::shared_ptr<Session> s) {
  std::weak_ptr<Session> w = s;
  timer_.after(10ms, [w] {
    if (auto sp = w.lock()) sp->on_timer();   // ✅ 提升成功才用
    // 提升失败 = 会话已销毁 = 什么都不做，正确且无竞态
  });
}
void SessionMgr::teardown(SessionId id) {
  map_.erase(id);      // 引用计数归零时才真正析构；
                       // 若回调正持有 sp，析构推迟到回调结束
}
三种修法，按推荐度排序。① Active Object / 单一执行上下文（最彻底）：定时器到期只是往会话邮箱投一条消息，与 teardown 消息在同一个队列里串行——竞态从结构上不存在，连引用计数都不需要。见 设计模式 §05。② shared_ptr + weak_ptr（上面的代码，改动最小）：适合已有大量裸指针回调的存量代码，代价是每次回调一次原子引用计数操作。③ 取消令牌（cancellation token）：回调闭包持有一个 shared_ptr<atomic<bool>>，teardown 时置位，回调进门先检查。比 weak_ptr 轻，但要自己保证"检查后到使用前对象不会被销毁"——通常还是要配引用计数，所以只在极热路径上才值得。

为什么 Helgrind 在这里不如 TSan：Helgrind 能报同样的问题，但它的报告噪声大得多（对无锁原语与自定义同步的误报率高，通信代码里这两样都不少），而且 20–100x 的开销让"跑几百万次 teardown"这种加压方式变得不现实——而竞态类 bug 恰恰需要大量迭代才能命中。TSan 的 5–15x 让你能在几分钟里跑完百万次循环，这是它的决定性优势。Helgrind 的价值在于不需要重新编译（对付只有二进制的第三方库时有用）。

案例 3 · 每连接残留 5 KB → 7 天长稳 RSS 上扬 泄漏 / 长稳

现象：功能测试全过，短时压测（1 小时）内存平稳。7 天长稳跑到第 4 天 RSS 从 1.2 G 涨到 3.8 G，趋势线笔直向上，第 6 天被 OOM killer 收走。

第一步：先确认是"泄漏"还是"缓存增长"或"碎片"——这三者的处理完全不同，搞错方向会白费几天：

  • 看 RSS 与堆使用量的差：malloc_info / tcmalloc 的统计显示"应用持有的堆"只有 1.3 G，而 RSS 3.8 G → 偏向碎片或分配器不归还。
  • 反之若两者一起涨 → 真的有对象没释放，是泄漏或无界缓存。本例是这一种。
  • 关掉某个功能后趋势是否消失：这是最便宜的二分法。本例关掉"待确认消息重传"后曲线立刻变平——范围一下缩到一个模块。

第二步：定位到具体分配点。LSan 在这里帮不上忙——它只在进程退出时报告，而长稳进程根本不退出，而且这些内存"仍被 pending 表可达"，从 LSan 的定义看不算泄漏。要用的是"堆增长归因"类工具：

  • heaptrack（开销 ~1.1–1.5x，可在长稳环境常开）：直接给出"从 T1 到 T2 之间净增长的分配来自哪些调用栈"，这正是本例需要的。
  • Massif（Valgrind 家族）：快照曲线很直观，但开销让它只能在实验室低负载跑，而低负载下增长慢、要等很久。
  • tcmalloc / jemalloc 的 heap profiler：开销极低，可以在生产上按需 dump，是最实用的一档。

本例的 heaptrack 报告显示，净增长的 87% 来自一个调用栈：

2.4G  net increase (over 72h)
  └─ 87%  PendingMap::insert(SessionId, PendingEntry)   pending.cc:63
       └─ Session::send_with_ack(Msg&&)                 session.cc:418
            └─ ...

# 对照：PendingMap 的条目数从 0 单调涨到 480 万，从未下降
# 而同期活跃会话数一直稳定在 ~2000

根因：send_with_ack() 把待确认消息记进 PendingMap，收到 ack 时删除。但会话异常断开时没有清理它自己的 pending 条目——ack 永远不会来，条目永久驻留。每条约 5 KB（含消息副本），链路抖动频繁的现场每天几十万次断链，一周就是几个 G。

❌ 只在正常路径上清理
void Session::send_with_ack(Msg&& m) {
  pending_map_.insert(id_, PendingEntry{std::move(m), now()});
  transport_.send(...);
}
void Session::on_ack(SeqNo s) {
  pending_map_.erase(id_, s);      // ✅ 正常路径清理了
}
// ❌ 但 ~Session() 里什么都没做
// ❌ 也没有任何条目级的超时清理
// 于是：断链 = 一批条目永久留下
// 而且这些内存是可达的 —— LSan/Memcheck
// 都不会报"泄漏"，只有增长归因工具能看见。
✅ 所有权明确 + 兜底超时
class Session {
  // ① 让 pending 表属于会话：析构自动清理，
  //    不依赖任何人"记得"调用清理函数
  PendingTable pending_;
 public:
  ~Session() = default;            // pending_ 随之析构
};

// ② 即使所有权正确，仍要有条目级兜底超时 —— 
//    防止"会话活着但对端永不 ack"这一类
void PendingTable::gc(steady_clock::time_point now) {
  erase_if(map_, [&](auto& kv) {
    if (now - kv.second.ts < kAckTimeout) return false;
    ++stats_.expired;              // ③ 打点：能上监控的指标
    return true;
  });
}
// ④ 硬上限：条目数超阈值就拒绝新的 send_with_ack
//    并告警 —— 把"无界增长"变成"明确拒绝"
本例最重要的一条教训：这类问题不是"泄漏"，标准泄漏检测工具全都报不出来。内存仍然可达（PendingMap 持有它），从 Memcheck / LSan 的定义看完全合法。它是"逻辑泄漏"或"无界缓存"，只能靠三件事发现：① 长稳测试的 RSS 趋势告警（见 §05）；② 关键容器的 size 打点（本例中 PendingMap 的条目数与活跃会话数的比值，稳态下应该有界——4.8M vs 2000 是明显异常，而这个指标一秒钟就能看出问题）；③ 增长归因工具（heaptrack / tcmalloc profiler）。
推论：所有长期存活的容器都必须导出 size 指标。这条规则的成本是几行代码，收益是把"一周后 OOM"变成"十分钟内看见"。
05

长稳测试怎么设计

soak 测试的价值在趋势，不在通过与否

长稳（soak）测试：在接近生产的负载下连续运行数天到数周，目的不是验证功能，而是暴露只在时间尺度上显现的缺陷：泄漏、句柄耗尽、计数器回绕、碎片累积、日志打满磁盘、证书过期、定时器堆积。通信设备的验收几乎都包含这一项，因为它的运行周期以年计。
负载模型关键是包含生命周期变化，而不只是稳态打流。必须有：连续的会话建立/拆除（这是最容易泄漏的路径）、周期性的配置变更、注入的链路抖动与断链、异常报文比例（1% 畸形）。只跑稳态转发的长稳测试几乎抓不到东西——案例 3 那个 bug 就在拆除路径上。
基线指标跑之前先记录稳态基线：RSS、虚拟内存、FD 数、线程数、各队列水位、关键容器 size、CPU、时延分位数。没有基线，第 4 天看到 3.8 G 你也不知道它是不是正常。
趋势告警判据不是"有没有崩"，而是斜率：任何本该有界的指标出现单调上升就是缺陷，哪怕绝对值还很低。RSS 每小时涨 10 MB 看着无害，30 天就是 7 G。用线性拟合的斜率做告警，不要用阈值——阈值只会在快撞墙时才响。
容器 size 打点承接案例 3 的推论：每一个长期存活的 map / list / 队列都要导出条目数，并给出"稳态下它应该与什么成正比"的注释（如 pending 表 ≈ 活跃会话数 × 每会话在飞消息数）。比值异常比绝对值异常更早、更明确。
周期性效应专门检查跨天/跨周的边界：日志轮转、证书与令牌刷新（TLS 证书过期是长稳测试的经典发现）、闰秒与授时跳变（会毁掉用 system_clock 算超时的代码——这也是为什么必须用 steady_clock）、计数器 32 位回绕。
长稳测试最容易被浪费的方式是"跑完看有没有崩"。它真正的产出是一整套指标的时间序列。所以在设计上要保证：指标采集从第一秒就开着、采样间隔够密（分钟级）、数据能保留到测试后分析、并且每次长稳结束都把曲线和上一版对比。
很多缺陷是渐变的——这一版比上一版每小时多涨 3 MB，两个版本各自都"通过"了，但趋势对比能立刻指出是哪次提交引入的。这比事后从几万行 diff 里考古便宜太多。完整的泄漏治理流程见 内存泄漏治理。
06

不能上工具时的生产手段

现场只给你一次机会

core dump + 符号服务生产二进制必须是 带符号但 strip 过的：发布时把 .debug 分离存档（objcopy --only-keep-debug），设备上跑 strip 版本，出 core 后用归档的符号解析。⚠️ 三件必配：ulimit -c unlimited、kernel.core_pattern 指向有足够空间的分区（几 G 的 core 写满 / 会二次故障）、以及 build-id 与版本号入库——现场跑的到底是哪次构建，这个问题在多版本并存时会卡住整个分析。
分配器 profiling链上 tcmalloc / jemalloc，通过环境变量或信号触发 heap dump。开销 < 5%，可以长期开着。这是生产环境定位内存增长唯一实用的手段（案例 3 那类"可达的逻辑泄漏"只有它能看见）。jemalloc 还能顺带给出碎片率，用来区分"泄漏"与"碎片"。
eBPF 动态追踪不改代码、不重启进程，动态挂探针看函数调用频率、参数、时延分布、以及内核侧的丢包与队列。排查"某个路径是不是被走到了""慢在哪一层"极其高效。⚠️ 注意 uprobe 会带来实际开销（每次命中一次陷入），高频函数上要用采样或聚合而不是逐次打印。用法见 eBPF 可观测性。
结构化日志 + 关联 ID每条日志带 session-id / 关联 ID，输出成可检索的键值对而不是自由文本。这样"把某个 UE 的完整生命周期捞出来"是一次查询而不是一场 grep 考古。⚠️ 日志本身是抖动源与磁盘炸弹：热路径用无锁队列交给专门线程落盘（绝不在 IO 线程里同步写盘，见 反模式 ④），并且带限速与采样。
状态快照与迁移日志承接 状态机那篇：把状态迁移与非法事件计数常态化打点。现场排障时，"这个会话在 12:03:41 从 CONNECTED 迁到 IDLE，触发事件是 T310 超时"这一行信息，价值超过一小时的猜测。可观测性是设计出来的，不是出事之后加的。
07

把排查前移

最便宜的排查是根本不用排查

模糊测试（fuzzing）：用变异或生成的输入反复调用目标函数，配合 Sanitizer 检测崩溃与 UB。覆盖率引导的 fuzzer（libFuzzer、AFL++）会根据"哪些输入触发了新的代码路径"来指导变异，因此能自动钻进人写不出来的边角分支。协议解析器是 fuzz 的最佳目标：输入就是字节串、无需环境、单次调用极快（每秒几十万次）。
基础版：随机字节
// 20 行就能挂上，第一天就能抓一批越界
extern "C" int LLVMFuzzerTestOneInput(
    const uint8_t* d, size_t n) {
  Parser p;
  p.parse({reinterpret_cast<const std::byte*>(d), n});
  return 0;   // 崩溃/UB 由 ASan+UBSan 报告
}
// 编译：
// clang++ -fsanitize=fuzzer,address,undefined ...

// 局限：纯随机字节很难通过 magic 与
// 校验和检查，绝大多数输入在头几个
// 字节就被拒 —— 深层解析逻辑覆盖不到。
✅ 工程版：真实语料 + 修正校验和
extern "C" int LLVMFuzzerTestOneInput(
    const uint8_t* d, size_t n) {
  if (n < kMinFrame) return 0;
  // ① 用变异数据构帧，但重算 magic 与 CRC，
  //    让 fuzzer 的力气花在字段语义而不是校验和上
  auto frame = build_frame(d, n);
  fix_magic(frame); fix_crc(frame);

  Parser p;
  if (auto msg = p.parse(frame)) {
    // ② 断言不变量，不只是"没崩"
    assert(msg->tlv_count() <= kMaxTlv);
    assert(msg->total_len() == frame.size());
    // ③ 往下喂状态机，抓深层问题
    fsm_.feed(*msg);
  }
  return 0;
}
// 语料库种子 = 生产抓包的 pcap 拆出的真实报文
// → 起点就在深处，覆盖率爬升快得多
语料库怎么来最有效的种子是生产抓包：把 pcap 里的应用层报文逐条拆出来当初始语料。这让 fuzzer 从"合法且复杂"的输入开始变异，而不是从零学会构造合法帧。语料库要入库并持续积累（每次发现新崩溃的输入都加进去做回归）。
断言不变量只检查"没崩"会浪费一大半价值。在 fuzz target 里断言协议不变量（解析出的长度与输入一致、TLV 数量有上限、状态机不进入非法状态），能把"没崩但解析错了"这类沉默缺陷也抓出来。
状态机也能 fuzz把事件序列当输入：让 fuzzer 生成随机的事件序列喂给状态机，断言"不会进入未定义状态、不会泄漏资源、非法事件都被计数而不是崩溃"。这是抓状态爆炸类缺陷最有效的手段（见 状态机那篇的可测试性一节）。
静态分析-Wall -Wextra -Werror 是底线；再加 clang-tidy（尤其 bugprone-*、cppcoreguidelines-*）与 clang --analyze。它们抓不到并发问题，但对"忘检返回值""可疑的类型转换""越界的常量下标"这类命中率不低，而且零运行成本。
CI 门禁把 ASan / UBSan / TSan 做成阻塞合并的门禁而不是"参考信息"。关键在于必须零容忍：一旦允许"这个告警先忽略"，报告很快会积累到没人看的程度，工具就等于没有。发现历史遗留太多时，用抑制列表（suppression）冻结存量、对新代码严格执行，然后逐步清理存量。
把本篇倒过来读，就是一份优先级清单。最贵的排查是现场偶发（案例 2 那种，一天崩两次、加日志就消失）；便宜一点的是长稳趋势（案例 3，一周才看出来，但至少确定可复现）；再便宜的是 CI 里的 Sanitizer 报告（几分钟，且直接给出两条栈）；最便宜的是 fuzz 在提交前就把畸形报文挡住（案例 1 本该死在这一关）。
四类缺陷对应四道防线：解析越界 → fuzz + span；UAF → 所有权模型（Active Object / weak_ptr）+ TSan；逻辑泄漏 → 容器 size 打点 + 长稳趋势；死锁 → 锁序约定 + TSan。每一道防线的成本都比它下游的排查便宜一到两个数量级，这就是"把排查前移"的全部理由。
🎯 本篇要点回顾
  • 通信软件四类高发缺陷：畸形报文越界、会话销毁与回调竞态（UAF）、每连接逻辑泄漏、锁序死锁——分布由"输入不可信 + 并发拆除 + 运行以年计"决定
  • 工具选型先按"能跑在哪"筛：UBSan/heaptrack（~1.2x，可上真实负载）→ ASan（2x，实验室）→ TSan（5–15x，单测）→ Valgrind 家族（10–100x，抽出来的模块）
  • Valgrind 不能上带 PTP / 实时约束的节点：不只是慢，它会制造假 bug（超时击穿、看门狗复位、PTP 失锁）并掩盖真竞态（相对时序被打乱）
  • 替代路径优先级：抓包离线重放 > 模块抽出单测 > 降速（负载与超时同步放大）> 上低开销工具
  • 案例 1：ASan 报告里"距对象右侧 N 字节"直接指向未校验的长度字段；剩余空间检查用减法防溢出回绕，传 span 把约定变成编译期保证
  • 案例 2：TSan 同时给出读方与释放方两条栈；"cancel 定时器"永远无法覆盖"已取出待调用"，修法优先 Active Object，其次 weak_ptr
  • 案例 3：可达的"逻辑泄漏"标准泄漏工具全都报不出来——靠长稳 RSS 趋势 + 容器 size 打点 + heaptrack 增长归因
  • 长稳测试的产出是指标时间序列而非"有没有崩"；判据是斜率不是阈值；负载模型必须含会话建立/拆除与异常注入
  • 生产手段：分离符号的 core dump（含 build-id 入库）、tcmalloc/jemalloc profiling、eBPF 动态追踪、带关联 ID 的结构化日志、常态化的状态迁移打点
  • fuzz 解析器要修正校验和 + 用生产 pcap 做种子 + 断言不变量；事件序列 fuzz 可以抓状态机缺陷；CI 门禁必须零容忍，存量用抑制列表冻结
