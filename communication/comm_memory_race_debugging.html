通信软件的内存与竞态排查实战

通信软件的缺陷分布很有特色：畸形报文打的是解析器，会话销毁撞的是工作线程回调，7×24 长稳照的是每连接泄漏，多把锁换来的是死锁。本篇不重讲工具用法，只讲通信场景里怎么选工具、能不能在设备上跑、以及三个从报告读到根因的完整复盘。

01

四类高发缺陷

通信软件的缺陷分布不是随机的

边界。工具的完整用法一律不在本篇：Valgrind 全套指南、Sanitizers 指南、Sanitizer 内部原理、内存泄漏治理、死锁调试、崩溃调试。本篇的增量是通信场景特有的四件事：竞态的三种固定形态、设备上能不能跑、时序约束怎么绕、生产上不能开工具怎么办。
① 畸形报文 → 解析越界长度字段没校验就当偏移用、TLV 嵌套不限深度。唯一一类既是稳定性问题又是安全漏洞的缺陷——输入完全由外部控制。
② 会话销毁 vs 回调 → UAFteardown 时定时器回调、工作线程仍持有裸指针，表现为悬垂 this。触发条件是"正好在此刻断链"，所以永远偶发。
③ 每连接泄漏 → RSS 上扬单次几 KB，功能测试看不见；跑一周、几十万次连接后涨几个 G，被 OOM killer 收走或触发倒换。
④ 锁序不一致 → 死锁会话锁与管理器锁在不同路径上顺序相反。通信软件尤其容易，因为"从会话找管理器"和"从管理器遍历会话"两个方向天然都存在。
🏗️ 类比：建筑的四种病。解析越界是大门没验票；UAF 是拆房时还有人在里面，拆迁队与住户各按自己的时间表，平时错开、偶尔撞上；泄漏是每天掉一点墙皮；死锁是两条单行道对开，路修好那天就注定了。四种病要四种检查手段，用错了就是"体检全过但楼在塌"。
"分布不是随机的"决定了资源该往哪投。输入是不可信的字节流、生命周期是并发拆除的会话、运行时长以年计——这三件事直接生成了前三类缺陷。质量投入应集中在解析器 fuzz、会话所有权模型、长稳趋势告警三处，均摊到所有代码上是低效的。

1.1 通信软件里竞态的三种形态

数据竞争的定义与内存模型见 C++ 内存模型，判据只有三条，缺一条就不成立：

这三条在任何并发程序里都一样。通信软件的增量在于它把竞态压进了三个固定形态：缓冲区所有权、定时器与业务线程的时序、多核计数器的可见性。本篇后面所有工具选择都是为了抓它们。

形态一：包路径上的缓冲区所有权

收包线程从网卡取出缓冲、投给处理线程，然后把缓冲还回池子——最常见也最常写错的一次所有权移交。错法永远相同：投递之后收包线程还认为自己是所有者。

最短复现——把窗口从纳秒放大到必然命中，只要在归还前加一次让出：

Buf* b = pool.alloc();
recv(fd, b->data, b->cap, 0);
queue.push(b);                 // 所有权已交给 worker
std::this_thread::yield();     // ← 只为把窗口撑开，便于必然命中
pool.free(b);                  // ❌ 已经不是我的了

// worker 侧：parse(b->data, b->len) 读到的是下一个包
// ✅ 正确写法只有两种，都是"让类型表达所有权"：
//   ① push(std::move(owner))  —— 独占移交，RX 侧不再持有句柄
//   ② push(shared_ptr<Buf>)   —— 共享，最后一个放手的人归还
// 判据：push 之后 RX 侧若还能写出 b->，这行代码就是错的
为什么这类 bug 靠 review 抓不到。归还与读取通常隔着好几层调用——pool.free() 藏在 RX 循环末尾的 RAII 析构里，parse() 在另一个文件，两处单独看都完全正确。只有把两条线程的时序摆在一起才看得出问题，而这正是 TSan 做的事：它给两条栈，不是一个崩溃点。

形态二：定时器线程与业务线程

协议栈里几乎每个会话都挂着定时器（重传、心跳、T3xx 系列），由独立线程或时间轮驱动，到期时刻与业务线程的处理时刻完全无关——第二个稳定的竞态来源。

形态三：多核计数器的可见性与伪共享

第三种形态不会崩，只会慢，因此最容易漏到现场：每线程统计计数器排在同一个数组里，落进同一条缓存行——逻辑上互不相干，硬件上却在互相抢。

完整原理与测量方法见 C++ 内存模型 · False sharing；ARM 上缓存行与原子指令的差异见 ARM 平台 §04；缓存行布局见 高性能通信 §06。本篇只强调一件事：它不在任何 sanitizer 的抓取范围内，只能靠 perf 与"加核不加吞吐"这个现象发现。
02

工具选型矩阵

开销量级决定了它能跑在哪

工具抓什么开销（速度 / 内存）能上生产？判据：什么时候选它
UBSan未定义行为（非对齐、溢出、无效枚举）~1.2x / 可忽略✅ 可长期开全量常开，没有理由不开
heaptrack / tcmalloc-prof堆分配来源与增长趋势~1.1–1.5x / 中✅ 可以内存单调上升，且需要真实负载
ASan堆/栈越界、UAF、double-free~2x / 2–3x⚠️ 实验室可，生产不建议崩点随机 → 越界；PR 门禁
LSan泄漏（进程退出时快照）含在 ASan 里 / 低✅ 但要能正常退出只对"不可达"的泄漏有效，长稳进程不适用
TSan数据竞争、锁序问题~5–15x / 5–10x❌加日志就不复现 → 竞态；夜间门禁
Memcheck越界、UAF、未初始化读、泄漏（最全）10–50x / 高❌ 绝对不能（§03）只在怀疑未初始化读时有独占价值
Helgrind / DRD数据竞争 + 锁序20–100x / 很高❌只在无法重新编译时用
Massif / Callgrind堆快照曲线 / 指令级 profile5–50x / 中❌事后人工分析，不进门禁
选型口诀：先按"能跑在哪"筛，再按"抓什么"选。现实约束是大部分 bug 只在真实负载、真实对端、真实时序下才出现，而能承受真实负载的只有 UBSan / heaptrack 这一档。所以正确的工作流是把可疑模块抽出来，在开发机上用最狠的工具跑构造的用例，而不是想办法把 Valgrind 塞进设备。"抽得出来"本身就是一项架构要求（模块边界怎么切见 通信软件架构）。

2.1 两种影子内存：为什么 ASan 和 TSan 不能同时开

两者名字都带 Sanitizer，内部机制却完全不同——这点解释了"为什么 ASan 报不出竞态""为什么 TSan 贵得多"。原理细节见 ASan 原理 与 TSan 原理，这里只给能直接用于读报告的那一层。

影子内存布局互相冲突，两者不能同时开，必须跑两轮。CI 排布：每次提交 UBSan 全量单测；每次 PR ASan 一轮；每晚 TSan 一轮（并发测试跑够时长与并发度）+ fuzz 增量；每周 Memcheck 核心模块。见 Sanitizers §10 组合与冲突 与 CMake / CI 指南。

2.2 从现象到工具

现场给你的永远是"现象"，选错工具就是几天时间。这张树只用不需要任何工具就能观察到的判据分叉。

03

为什么实时节点不能上 Valgrind

它不只是"慢"，它会掩盖真 bug 并制造假 bug

Valgrind 的工作方式：动态二进制翻译——把机器码翻成中间表示、插入检查、再重新生成执行，也就是整个程序都在解释执行，既不是采样也不是插桩后原速跑。由此得到两个特性：检查极其彻底（连未初始化读都能抓），以及时序被整体拉长 10–50 倍，而且不均匀。用法见 Valgrind 全套指南。

"不均匀"是关键：ASan 的 2x 大致均匀，相对时序基本保持；Valgrind 的开销集中在访存与分支密集处，不同路径被拉长的倍数完全不同。对依赖时间判定正确性的协议栈，这三件事同时发生：

"观测行为改变被观测对象"的教科书案例，通信软件对它格外敏感——正确性大量依赖时间（超时、重传、心跳、slot 边界、PTP 伺服）。纯计算程序放慢 50 倍只是慢，协议栈放慢 50 倍是换了一套运行条件。

3.1 隔离核与实时线程：连"停下来看一眼"都不允许

上面讲的是慢，还有一类更硬的约束：isolcpus 隔离核上的 SCHED_FIFO 线程（O-DU 的 slot 处理、DPDK 的 poll-mode 收包）。每个周期都有硬截止时间，常规调试动作里一半是被禁止的。

隔离核、中断亲和与 PMU 的配置见 ARM 平台 §07 实时与隔离；无锁环形缓冲的实现见 高性能通信 §02；线程模型与分片见 高并发与扩展 §03。

3.2 四条可行的替代路径

① 抓包离线重放首选。抓下故障时段报文，在开发机上把 pcap 喂给抽出来的模块，此时可以随便上最狠的工具。输入真实且可重复，排查解析类 bug 最快。
② 模块抽出做单测用构造的用例（畸形报文、乱序事件、并发 teardown）跑 TSan。竞态要主动加压：多线程反复"建会话—发消息—拆会话"几百万次。
③ 实验室降速跑负载降到 1/50、同步把所有协议超时按同样倍数放大（最常被漏的一步）、关看门狗、隔离 PTP 测试。能查泄漏与越界，查不了竞态。
④ 上低开销工具UBSan + heaptrack + eBPF（见 §06）。抓不到竞态，但能抓泄漏与 UB，且是唯一在真实时序下工作的一档。
04

三个复盘案例

从报告读到根因的完整路径

案例 1 · TLV 长度字段未校验 → 堆越界读 越界 / 安全

现象：某型对端设备接入后，管理面进程每隔几十分钟崩一次，换回原厂对端就正常。栈在解析函数里，但每次崩的位置不同，有时栈本身就是坏的。

第一步：变成可重复的。按 §2.2 那棵树走——崩点随机就是抓包 + 开发机 ASan 重放。tcpdump -s0 -w 抓下故障时段，20 行程序把报文逐个喂给解析器，第三个就炸了：

==12345==ERROR: AddressSanitizer: heap-buffer-overflow
READ of size 4 at 0x60300000f0e8 thread T0
    #0 parse_tlv(const uint8_t*, size_t)  tlv.cc:47
    #1 handle_msg(Session&, Buf&)         session.cc:212

0x60300000f0e8 is located 8 bytes to the right of
              96-byte region [0x60300000f080,0x60300000f0e0)
allocated by thread T0 here:
    #1 Buf::Buf(size_t)                   buf.cc:14

# 判据一：READ of size 4 → 在读一个 uint32_t，符合"读长度字段/读 value"
# 判据二：8 bytes to the right of 96-byte region ← 最有价值的一行。
#         缓冲 96 字节，访问落在结束后 8 字节 → 偏移算到了 104。
#         偏移比缓冲大 = 偏移来自报文里某个字段，而它没和缓冲长度比对过。
# 判据三：allocated by Buf::Buf → 越界的就是 recv buffer 本身，
#         不是别的结构被踩 —— 排除了"内存已被破坏"这条更麻烦的岔路。

根因：parse_tlv 只检查了 T+L 这 4 字节够不够，之后直接 handle_value(p + off + 4, vlen)，而 vlen 完全来自对端——它填 100、实际只剩 8 字节。这不是对端"坏"，它可能只是用了一种我们从没验证过的可选字段组合。

两条可复用的教训。① 传 span 而不是"指针 + 长度"，把边界约定变成编译期保证（见 现代 C++ 在通信软件里）。② 这个 bug 本该被 fuzz 在第一天抓到——变异长度字段是 libFuzzer 最容易命中的模式（§07）。它能活到现场，说明解析器从没被 fuzz 过。
案例 2 · 会话 teardown 与定时器回调竞态 → UAF 竞态 / 悬垂

现象：链路抖动频繁的现场，进程每天崩 1–2 次，栈有时在定时器线程、有时在工作线程，崩的对象是会话结构。加了日志之后不复现了——典型 Heisenbug。

第一步：定性。"加日志就不复现" + "崩点随机" + "与链路抖动强相关"三条同时成立，可判为销毁与使用的竞态：抖动 = 频繁断链 = 频繁 teardown，正是触发窗口。至于为什么崩得如此随机——

第二步：构造复现。把会话管理抽成单测，开 8 个线程反复做「建会话 → 挂 10 ms 定时器 → 立即 teardown」，跑 TSan：

WARNING: ThreadSanitizer: heap-use-after-free (pid=8123)
  Read of size 8 at 0x7b0400001040 by thread T3:
    #0 Session::on_timer()        session.cc:301
    #1 TimerWheel::tick()         timer.cc:88

  Previous write of size 8 at 0x7b0400001040 by thread T1:
    #0 operator delete(void*)
    #1 SessionMgr::teardown()     mgr.cc:145

  Location is heap block of size 512 freed by thread T1

# 怎么读：只要回答"哪两条线程的哪两次访问"这一个问题
#   T3 的这次访问：Read，来自 on_timer ← 时间轮线程
#   T1 的那次访问：operator delete，来自 teardown ← 业务线程
#   两者之间没有任何同步 → 根因在这两行的交叉处
# 判据：TSan 比 core dump 强的唯一关键点是它给出了释放方的栈。
#       core dump 只有 T3 那半边，你永远不知道是谁 free 的。

根因就是 §1.1 形态二那张图：teardown() 删了会话，但时间轮里还挂着指向它的回调。

❌ 裸指针回调 + "取消定时器"不可靠
void SessionMgr::teardown(SessionId id) {
  auto* s = map_[id];
  timer_.cancel(s->timer_id);   // ⚠️ 看似取消了
  map_.erase(id);
  delete s;                     // ⚠️ 但回调可能已经在跑
}
// 竞态窗口：tick() 已经从时间轮取出这个回调、
// 正准备调用（或已进入 on_timer 但还没读成员），
// 此时 cancel() 找不到东西可取消，delete 照常执行。
// → on_timer 里的 this 悬垂。
// 窗口只有几十纳秒，但一天几万次 teardown 就够了。
// ⚠️ 关键认识："取消"永远无法覆盖"已取出待调用"，
// 除非取消与调用在同一个串行上下文里。
✅ weak_ptr：让回调自己判断对象还在不在
// 会话由 shared_ptr 持有，定时器只持 weak_ptr
void SessionMgr::arm(std::shared_ptr<Session> s) {
  std::weak_ptr<Session> w = s;
  timer_.after(10ms, [w] {
    if (auto sp = w.lock()) sp->on_timer();   // ✅ 提升成功才用
    // 提升失败 = 会话已销毁 = 什么都不做，正确且无竞态
  });
}
void SessionMgr::teardown(SessionId id) {
  map_.erase(id);      // 引用计数归零时才真正析构；
                       // 若回调正持有 sp，析构推迟到回调结束
}
修法做法代价适用
① Active Object
（最彻底）		到期只往会话邮箱投一条消息，与 teardown 消息在同一队列里串行要有消息循环；单会话吞吐受单线程限制新模块首选——竞态从结构上不存在，连引用计数都不需要。见 设计模式 §05
② weak_ptr
（改动最小）		上面那段代码：回调只捕获 weak_ptr，用前 lock()每次回调一次原子引用计数已有大量裸指针回调的存量代码
③ 取消令牌闭包持 shared_ptr<atomic<bool>>，teardown 置位，回调进门先查要自己保证"查完到用完之间对象不被销毁"，通常仍需引用计数只在极热路径上值得

为什么不用 Helgrind：20–100x 的开销让"跑几百万次 teardown"不现实，而竞态恰恰需要大量迭代才命中。它的独占价值只有一条：不需要重新编译，适合只有二进制的第三方库。

案例 3 · 每连接残留 5 KB → 7 天长稳 RSS 上扬 泄漏 / 长稳

现象：功能测试全过，1 小时压测内存平稳。7 天长稳跑到第 4 天 RSS 从 1.2 G 涨到 3.8 G，趋势线笔直向上，第 6 天被 OOM killer 收走。

第一步：分清"泄漏 / 无界缓存 / 碎片"——三者处理完全不同，搞错方向白费几天。判据只需要两个已有的数字：

RSS 与堆统计的关系归类下一步
RSS 涨，malloc_info / tcmalloc 报的"应用持有堆"不涨碎片或分配器不归还调 arena / MALLOC_TRIM_THRESHOLD_；不要去找"漏掉的 free"
两者一起涨　←　本例泄漏或无界缓存做增长归因，定位到分配栈
关掉某个功能后趋势立刻变平范围已缩到一个模块最便宜的二分法，先做这个。本例关掉"待确认消息重传"后曲线就平了

第二步：定位分配点。LSan 帮不上忙——它只在进程退出时报告，而这些内存仍被 pending 表可达，按它的定义压根不算泄漏。要用的是"堆增长归因"：heaptrack 或 tcmalloc / jemalloc 的 heap profiler。本例净增长的 87% 落在一个调用栈上：

2.4G  net increase (over 72h)
  └─ 87%  PendingMap::insert(SessionId, PendingEntry)   pending.cc:63
       └─ Session::send_with_ack(Msg&&)                 session.cc:418

# 判据一：看的是"两个时刻之间的净增长"，不是总分配量。
#         总分配量最大的调用栈通常是收包路径 —— 它分配得多但也全还了，
#         按总量排序会一直把你引到错的地方。
# 判据二：拿容器条目数交叉验证，一秒钟定性：
#         PendingMap 条目数 0 → 480 万，单调，从未下降
#         同期活跃会话数稳定在 ~2000 → 比值应该有界，却差了三个数量级

根因：send_with_ack() 把待确认消息记进 PendingMap，收到 ack 时删除；但会话异常断开时没人清理它自己的条目——ack 永远不会来，条目永久驻留。每条约 5 KB，抖动频繁的现场每天几十万次断链，一周几个 G。修法是四层，缺一层就会以另一种形式复发：

① 所有权归位让 pending 表属于会话（成员而不是全局 map），析构自动清理，不依赖任何人"记得"调清理函数。这一层修掉本例。
② 条目级超时即使所有权正确仍要有兜底 GC——防"会话活着但对端永不 ack"。用 steady_clock 判超时，顺手 ++stats_.expired。
③ size 打点条目数导出成监控指标。唯一能把"一周后 OOM"变成"十分钟内看见"的一层，成本是几行代码。
④ 硬上限超阈值就拒绝新的 send_with_ack 并告警——把"无界增长"变成"明确拒绝"。背压做法见 高并发与扩展 §05。
最重要的一条：这类问题不是"泄漏"，标准泄漏工具全都报不出来。内存仍然可达（PendingMap 持有它），按 LSan / Memcheck 的定义完全合法。它是逻辑泄漏 / 无界缓存，只有三件事能发现：长稳 RSS 趋势（§05）、关键容器 size 打点、增长归因工具。推论：所有长期存活的容器都必须导出 size 指标。
05

长稳测试怎么设计

soak 测试的价值在趋势，不在通过与否

长稳（soak）测试：在接近生产的负载下连续跑数天到数周，目的不是验证功能，而是暴露只在时间尺度上显现的缺陷：泄漏、句柄耗尽、计数器回绕、碎片累积、证书过期、定时器堆积。

它最容易被浪费的方式是"跑完看有没有崩"。真正的产出是一整套指标的时间序列，读法是看斜率而不是绝对值：

负载模型关键是包含生命周期变化而不只是稳态打流：连续的会话建立/拆除、周期性配置变更、注入的抖动与断链、1% 畸形报文。只跑稳态转发几乎抓不到东西——案例 3 那个 bug 就在拆除路径上。
基线与打点先记稳态基线：RSS、FD 数、线程数、队列水位、CPU、时延分位数，以及每个长期存活容器的条目数并注明"稳态下应与什么成正比"（pending 表 ≈ 活跃会话数 × 每会话在飞消息数）。比值异常比绝对值异常更早。
周期性效应专查跨天/跨周边界：日志轮转、TLS 证书与令牌刷新、闰秒与授时跳变（会毁掉用 system_clock 算超时的代码，这就是必须用 steady_clock 的理由）、32 位计数器回绕。
版本间对比很多缺陷是渐变的：这一版比上一版每小时多涨 3 MB，两版各自都"通过"，但曲线对比能立刻指出是哪次提交引入的。
06

不能上工具时的生产手段

现场只给你一次机会

现场不能停机、不能重新编译、不能拖慢时序，可用手段因此排成一个漏斗：越靠前越便宜、越该常态开着；越靠后诊断力越强、代价也越大。按顺序用。

手段怎么开判据 / 必配的坑
核心转储 + 符号服务objcopy --only-keep-debug 分离 .debug 存档，设备只跑 strip 版三件必配：ulimit -c unlimited、core_pattern 指向有足够空间的分区（几 G 的 core 写满 / 会二次故障）、build-id 入库
分配器 profiling链上 tcmalloc / jemalloc，环境变量或信号触发 heap dump< 5%，可长期开。案例 3 那类可达的逻辑泄漏只有它能看见
eBPF 动态追踪不改代码、不重启进程挂探针，看调用频率、参数、时延分布与内核侧丢包⚠️ uprobe 每次命中一次陷入，高频函数上必须采样或在内核内聚合。见 eBPF 可观测性
结构化日志 + 关联 ID每条日志带 session-id，输出键值对而非自由文本"捞出某个 UE 的完整生命周期"应是一次查询而不是一场 grep 考古。⚠️ 热路径用无锁队列交给专门线程落盘（见 反模式 ④）
状态迁移打点每次迁移与每个非法事件都计数并留时间戳"该会话 12:03:41 从 CONNECTED 迁到 IDLE，触发 T310 超时"胜过一小时猜测。见 协议状态机
可观测性是设计出来的，不是出事之后加的。漏斗前两层必须在故障发生之前就在跑，否则出事时你手里什么都没有，只能等它再来一次。
07

把排查前移

最便宜的排查是根本不用排查

模糊测试（fuzzing）：用变异输入反复调用目标函数，配合 Sanitizer 检测崩溃与 UB。覆盖率引导的 fuzzer 按"哪些输入触发了新代码路径"指导变异，能钻进人写不出来的边角分支。协议解析器是最佳目标：输入就是字节串、无需环境、单次调用极快。用法见 Sanitizers §13；事件序列 fuzz 见 协议状态机。
共同前提：做成阻塞合并的门禁，并且零容忍。一旦允许"这个告警先忽略"，报告很快积累到没人看，工具就等于没有；存量太多时用抑制列表冻结存量、对新代码严格执行。再往前一格是零成本的 -Wall -Wextra -Werror 与 clang-tidy——抓不到并发问题，但对"忘检返回值""可疑类型转换"命中率不低。
把本篇倒过来读就是一份优先级清单：最贵的是现场偶发（案例 2），其次长稳趋势（案例 3），再次 CI 里的 Sanitizer 报告，最便宜的是 fuzz 在提交前挡住畸形报文（案例 1 本该死在这一关）。四类缺陷对应四道防线：解析越界 → fuzz + span；UAF → 所有权模型 + TSan；逻辑泄漏 → 容器 size 打点 + 长稳趋势；死锁 → 锁序约定 + TSan（见 死锁调试）。每道防线都比它下游的排查便宜一到两个数量级。
🎯 本篇要点回顾
  • 通信软件把竞态压进三个固定形态：缓冲区所有权（push 之后还能写 b-> 就是错的）、定时器线程 vs 业务线程（cancel 覆盖不到"已取出待调用"）、多核计数器伪共享（不崩只慢，没有 sanitizer 能抓）
  • 选型先按"能跑在哪"筛：UBSan / heaptrack（~1.2x，真实负载）→ ASan（2x，实验室）→ TSan（5–15x，单测加压）→ Valgrind 家族（10–100x，只能跑抽出来的模块）
  • ASan 靠红区 + 隔离区，完全不看线程关系；TSan 靠向量时钟 + 4 格影子内存，只判实际执行过的两次访问。影子布局冲突，必须跑两轮
  • Valgrind 不能上带 PTP / 实时约束的节点：它制造假 bug（超时击穿、看门狗复位、PTP 失锁）并掩盖真竞态；隔离核上的 SCHED_FIFO 线程更是连断点、加锁、打印都不允许
  • 三条读报告的判据：ASan 的"距对象右侧 N 字节"指向未校验的长度字段；TSan 的价值是给出释放方的栈；heaptrack 要看净增长而不是总分配量
  • 可达的"逻辑泄漏"标准工具全都报不出来——只有长稳趋势、容器 size 打点、增长归因能发现；判据是斜率：斜率第 1 天就响，阈值要等到第 6 天
  • 生产手段排成漏斗：常态打点与结构化日志 → 分离符号的 core dump → 分配器 profiling → eBPF → 最后才是灰度开 sanitizer。前两层必须在故障之前就在跑
