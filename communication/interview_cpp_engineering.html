01

Socket / TCP/UDP

Q1recv 返回 0、-1 分别意味着什么？如何正确收满 N 字节？
P0必考
要点
  • 返回 0：对端正常关闭连接(EOF)。返回 -1：出错(检查 errno；EAGAIN/EWOULDBLOCK 表示非阻塞下暂无数据；EINTR 被信号中断可重试)。
  • >0：实际读到的字节数(可能少于请求)。要循环调用累积到 N。
Q2高并发服务器为什么用 epoll 而不是 select？Reactor 是什么？
P0高频
要点
  • select/poll 每次要遍历所有 fd(O(n))、有数量限制；epoll 用事件就绪列表(O(就绪数))、无硬限制，适合海量连接。
  • Reactor：epoll 事件循环 + 回调分发，是高性能网络框架的骨架。
  • ET(边缘触发) vs LT(水平触发)：ET 需一次读干净否则漏事件，效率高但易错。
Q3TCP_NODELAY 和 Nagle 算法的关系？何时关闭？
P1工程
要点

Nagle 算法把小包攒起来一起发以省带宽，但会增加延迟。实时/低延迟场景(交互、控制面)用 TCP_NODELAY 关闭 Nagle，让小包立即发出。

02

二进制协议 / TLV / 字节序

Q4什么是字节序？跨机通信如何处理？
P0必考
要点

大端(高位在前)/小端(低位在前)。x86 是小端，网络序是大端。多字节字段发送前 htons/htonl 转网络序，接收后 ntohs/ntohl 转回。单字节无字节序问题。不处理会导致数值错乱。

Q5设计一个二进制协议要考虑哪些字段？如何做消息分帧？
P0高频
要点
  • 典型头：Magic(识别/对齐)、Version(兼容)、Type、Seq、Length、Checksum/CRC。
  • 分帧首选长度前缀：先收满定长头，读出 length，再收满 body。
  • 务必校验 length 上限，防止超大值撑爆内存。
  • 结构体收发用 #pragma pack(1) 避免对齐填充导致两端不一致。
Q6TLV 编码的优缺点？什么场景用？
P1设计
要点

TLV(Type-Length-Value)：遇到不认识的 Type 可按 Length 跳过 → 向前兼容、可选字段友好。缺点：比紧凑定长多占字节、解析稍复杂。适合需要扩展性的信令协议。

03

高性能：Ring / Lock-Free / Zero Copy

Q7Ring Buffer 为什么高效？如何实现无锁 SPSC？
P0高频
要点
  • 预分配固定数组、无动态内存、缓存友好、天然生产者-消费者。容量取 2 的幂用位与取模。
  • SPSC 无锁：生产者只写 tail、消费者只读 head，用 atomic + acquire/release 内存序保证可见性，无需互斥锁。
  • 把 head/tail 放不同 cache line 避免伪共享。
Q8什么是 Zero Copy？列举实现手段。
P0高频
要点
  • 减少内核态/用户态间及缓冲区间的数据拷贝。
  • 手段：sendfile/splice/mmap；用户态传指针+引用计数；DPDK/RDMA 内核旁路直接 DMA 到用户态大页。
  • 前传/转发面为极致吞吐常用 DPDK：旁路内核 + 轮询 + 大页 + 零拷贝。
Q9为什么用内存池？和批处理如何配合？
P1工程
要点

内存池预分配固定块，运行期借还代替 malloc/free，消除分配延迟抖动与碎片。配合 Ring Buffer：包缓冲从池取、处理完归还。批处理一次收发多个包，摊薄 syscall/同步开销。

04

多线程与并发

Q10通信软件里模块之间为什么倾向"传消息"而非共享内存？
P1架构
要点

消息传递(队列)解耦模块、减少共享状态与锁竞争、易测试易并行(类 Actor)。共享内存快但竞态难控。必须共享时用无锁结构或按数据分区避免争用。数据面线程常绑核减少切换。

Q11数据面热路径上有哪些操作要避免？
P0低延迟
要点

热路径避免：动态内存分配、加锁、打日志、抛异常、系统调用、跨 NUMA 访问、cache 不友好的随机访问。追求确定性延迟：预分配、无锁、绑核、批处理、预取。

05

性能与高可用

Q12为什么通信系统更关注尾延迟(p99)而非平均延迟？
P0高频
要点

实时系统有硬时限，偶发的高延迟(尾延迟)会导致丢帧/掉话/超时，比平均值更能反映用户体验与确定性。所以盯 p99/p999 并优化最坏情况，而非只看均值。

Q13超时、重试、背压为什么要一起设计？
P0可靠性
要点
  • 超时：任何等待有上限，防止卡死拖垮全局。
  • 重试：需指数退避 + 上限 + 幂等，否则重试风暴放大故障。
  • 背压：队列有界，下游忙时让上游减速/丢弃，防止堆积雪崩。
  • 三者缺一：无界队列+无超时+无退避 = 一点抖动就级联崩溃。
Q14如何实现电信级高可用(5个9)？
P1HA
要点

冗余(主备/N+1/双活) + 心跳故障检测 + 快速 failover + 状态复制(热备) + 优雅降级 + 隔离爆炸半径(熔断/舱壁)。可用性=MTBF/(MTBF+MTTR)，重点靠冗余把 MTTR 压到秒级。

现代 C++ / 状态机 / 高并发 / ARM / 排错

12 道，对应 Module 09 与 Module 11 的四篇工程实践

点击每道题展开参考答案（先自测，再对照）。

  1. 基础用 string_view / span 做零拷贝报文解析，最容易踩什么坑？

    悬垂视图。视图只是"指针 + 长度"，不持有内存。典型事故：解析函数返回一个指向 recv buffer 的 string_view，而这块 buffer 在本轮处理结束后就被归还到缓冲池给下一个报文用了 —— 后续代码读到的是别人的数据。

    症状很难查：功能测试单报文场景全过；只有在高报文率、缓冲复用频繁时才偶发内容错乱，而且看起来像"协议解析错误"而不是内存问题。

    约定：视图不过帧边界。任何要活过本帧处理周期的数据必须拷贝一份（存进会话状态）。工程上可以把它变成可检查的规则：解析结果结构体里只允许放视图，且该结构体标记为不可存储（[[nodiscard]] + 命名约定 XxxView），要留存就必须显式调用 materialize()。详见 现代 C++ 在通信协议栈中的实战。

  2. 中级为什么用 variant + visit 表达消息族，比裸 union + tag 好？
    • 类型安全：裸 union + tag 的"tag 与实际内容不一致"是纯靠人保证的；variant 由编译器保证，取错类型是异常/UB 明确的行为而不是静默读到垃圾。
    • 穷尽性检查：visit 配合无 auto 兜底的重载集，漏处理某个消息类型编译不过。协议加一种新消息时，所有需要更新的地方会被编译器逐个指出来 —— 这在裸 union 里只能靠 review。
    • 生命周期：非平凡类型（含 std::string、容器的消息体）在 union 里要手工调构造/析构，极易漏；variant 自动处理。

    代价要说清楚才完整：variant 的大小是最大成员 + 判别标签（消息体大小差异大时浪费内存，可用 variant<小消息..., unique_ptr<大消息>> 缓解）；visit 在类型数多时可能生成跳转表，热路径上要看生成代码确认没有意外开销。数据面每包必经的路径上，表驱动的 opcode 派发可能仍然更快。

  3. 高级shared_mutex 保护读多写少的路由表，怎么会死锁？

    持读锁时回调业务代码，而业务代码又想拿写锁（或拿了另一把锁）。

    {
  std::shared_lock rd(route_mu_);        // 持读锁
  auto& entry = table_.at(key);
  entry.on_hit(ctx);                     // ⚠️ 回调业务代码
  //    业务代码里若调用 update_route() → 请求写锁
  //    → 同一线程持读锁等写锁 = 自锁死
}

    即使不是同一线程，也有写者饥饿 + 读者递归的经典问题：线程 A 持读锁、线程 B 在等写锁（多数实现会阻塞后续读者以防写者饿死）、线程 A 的回调里又请求读锁 → A 等 B，B 等 A。

    三条规则：① 临界区内绝不调用不受控的代码（回调、虚函数、业务逻辑）；② 需要的数据在锁内拷出来或取 shared_ptr，出锁后再用；③ 读多写极少的配置表用 copy-on-write + 原子换指针（RCU 风格），读侧完全无锁，比 shared_mutex 更快也更不容易出错。

  4. 基础为什么通信软件算超时必须用 steady_clock 而不是 system_clock？

    system_clock 是墙上时钟，可以被向前或向后调整（NTP 校准、PTP 授时、运维手工改时间、闰秒）。steady_clock 单调不回退，专门用来测量时间间隔。

    用 system_clock 算超时的具体后果：时钟被往前跳 1 小时 → 所有在飞的定时器立即全部到期（大量误判超时、误重传、误断链）；往后跳 → 定时器永远不到期（会话永久挂死、资源永不回收）。

    在通信设备上这不是罕见事件而是常态：带 PTP 的节点在同步建立、失锁恢复、主时钟切换时都会调整系统时间，而且设备刚上电时系统时间往往是错的（1970 或上次关机时刻），同步上之后会有一次大跳变。所以规则是：所有"间隔/超时"用 steady_clock，只有"给人看的时间戳、日志、证书有效期"才用 system_clock。

  5. 中级协议状态机的四种实现（switch / 转移表 / State 模式 / variant+visit），怎么取舍？
    实现优势短板适用
    switch-case零框架、直观、性能好状态多了就是嵌套地狱；横切逻辑（日志/计数）要在每个 case 重复状态 ≤ 4–5、迁移少
    转移表横切关注点只写一遍（非法事件计数、迁移日志、驻留时长统计都在 feed() 里）；表本身可读性接近状态图动作只能是函数指针，携带复杂上下文时不便；表随状态×事件平方增长通信协议的默认选择
    GoF State每状态一个类，私有数据局部化；扩展新状态不改老代码类数量膨胀、跳转要看多个文件、有虚调用开销各状态行为差异极大且各有大量私有状态
    variant + visit类型安全（状态的数据与状态本身绑定）、编译期穷尽检查、无虚调用编译期依赖强、报错信息难读、状态多时编译变慢状态带各自不同的数据、追求编译期保证

    关键判断依据是可观测性需求：通信软件的现场排障几乎全靠迁移日志，而"横切逻辑只写一遍"这一点让转移表在真实项目里的价值经常超过性能考虑。详见 协议状态机。

  6. 高级"定时器回调触发时对象已析构"这个竞态怎么修？为什么"取消定时器"不够？

    因为"取消"永远无法覆盖"已经从定时器队列取出、正准备调用"这个窗口。cancel() 在队列里找不到东西可删，于是照常 delete，而回调随后进入并读到悬垂 this。窗口只有几十纳秒，但每天几万次 teardown 就足够命中。

    三种修法，按推荐度：

    • ① Active Object / 单一执行上下文（最彻底）：定时器到期只是往对象的邮箱投一条消息，与 teardown 消息在同一队列里串行执行 —— 竞态从结构上不存在，连引用计数都不需要。
    • ② shared_ptr + weak_ptr（改动最小）：回调闭包只持 weak_ptr，进门 lock()；提升失败说明对象已销毁，什么都不做即为正确。提升成功则引用计数保证对象在回调期间存活。
    • ③ 取消令牌：闭包持一个 shared_ptr<atomic<bool>>，teardown 置位、回调先检查。比 weak_ptr 轻，但仍需保证"检查后到使用前对象不被销毁"，通常还是要配引用计数，只在极热路径上才值得。

    抓这个 bug 的工具是 TSan：它会同时给出读方与释放方两条栈，根因一眼可见。复现方法是把会话管理抽出来做单测，多线程反复"建—挂定时器—立即 teardown"跑几百万次。见 内存与竞态排查 §04 案例 2。

  7. 中级Reactor 与 Proactor 的本质差异是什么？只答"就绪通知 vs 完成通知"够不够？

    不够。通知时机只是表象，真正影响架构的是两点：

    • 缓冲区所有权：Reactor 里缓冲始终归应用，可以按需分配、可以多个连接复用同一块临时缓冲 —— 内存占用与活跃连接数相关。Proactor 里缓冲在提交后到完成前归内核，每个在飞的读都要独占一块，内存占用与在飞操作数相关：10 万连接各挂一个读 = 10 万块缓冲同时驻留。
    • 背压：Reactor 天然有背压 —— 处理不过来就不去读，数据积在内核缓冲，TCP 接收窗口自动收缩，压力免费传回对端。Proactor 的读是提前发出的，数据会源源不断被搬进用户态，过载时压力只体现为内存增长直到 OOM，必须自己限制在飞操作数。

    次要但也要知道：错误处理（Reactor 集中在自己的 read 返回值，Proactor 分散在完成事件里、要按操作 ID 关联上下文）、取消语义（Proactor 要发取消请求并等取消的完成事件，期间缓冲不能释放）。见 通信软件设计模式 §02。

  8. 高级Active Object 相比"每会话一把锁"，为什么能消灭一整类竞态？

    因为它把正确性依据从"人的纪律"换成了可机械检查的结构约束。

    Monitor Object（每会话一把锁）的正确性依赖三条全靠人保证的规则：每个方法都记得加锁、临界区里不做危险的事（IO、回调）、多把锁的顺序一致。任何一条被违反就是一个 bug，而且是偶发的。

    Active Object 只有一条规则：状态只被自己的执行上下文碰。别人要改状态必须投消息。违反它需要显式写出跨线程访问，review 一眼看得见。于是四类问题同时消失：

    • 持锁做 IO：没有锁，无从谈起。
    • 回调导致的锁升级/递归死锁：同上。
    • 锁序不一致：无锁则无锁序。
    • 定时器回调悬垂：到期变成投给自己的一条消息，回调不在别的线程执行。

    代价：多一次入队与唤醒（几百纳秒到几微秒，极致低时延路径要衡量）；跨会话操作从同步变异步（可读性下降）；邮箱必须有界（否则背压消失）；崩溃栈只到 drain()，所以消息里要带来源标识与关联 ID。见 设计模式 §05。

  9. 中级SO_REUSEPORT 解决什么问题？它和"同会话有序性"是什么关系？

    SO_REUSEPORT 让多个 worker 各自 listen 同一个端口，内核按四元组哈希把新连接分发给其中一个。收益：无惊群（不用 EPOLLEXCLUSIVE）、无跨线程的连接分配、可以逐个 worker 灰度重启升级。代价：长连接场景下分配可能长期不均（内核只在建连时哈希，之后不会再平衡）。

    它保证的是"连接级"的固定，不是"会话级"的有序。两者的区别是本题考点：如果一个逻辑会话的消息可能来自不同的连接（如 UDP、或多条 TCP 承载同一 UE），SO_REUSEPORT 就保证不了同会话串行。

    要保证同会话有序，必须按会话键哈希分片到固定 worker。反例的后果很具体：一个 UE 的 RRC Setup 与紧随的 RRC Release 被两个 worker 并行处理，Release 先完成、Setup 后完成 → 已释放的 UE 又变成 CONNECTED，成为永远清不掉的僵尸会话。注意"给会话加锁"只保证互斥、不保证顺序，谁先抢到锁谁先执行，乱序依旧。见 高并发 §03。

  10. 高级"在 x86 跑了三年，换 ARM 就偶发"最常见的根因是什么？举一个具体例子。

    缺失的 release/acquire 内存序。x86-TSO 只允许 StoreLoad 一种重排，而 ARM 四种全允许 —— 所以漏写同步的代码在 x86 上"恰好正确"，在 ARM 上会真实地重排。

    具体例子：自己写的 SPSC 环形队列。生产者先写数据槽、再递增 tail。这两步之间是 StoreStore：x86 禁止重排，所以一直是对的；ARM 允许 tail 的写先对消费者可见，于是消费者过了"非空"检查后，读到一个还没写进去的槽位。修法是 tail_.store(t+1, memory_order_release) 配 tail_.load(memory_order_acquire)。

    最有说服力的补充：写对内存序几乎是免费的 —— x86 上 release store / acquire load 编译出来就是普通 mov（TSO 本来就提供这些保证），ARM 上是单条 STLR/LDAR，远比 DMB 全屏障便宜。所以用 relaxed 换不到任何性能，只换到"在 ARM 上会坏"。

    另一个经典受害者是手写双重检查锁（构造对象的写与指针赋值之间的 StoreStore），直接用函数内 static 即可避免。提前发现的手段是在 x86 上跑 TSan（它检测的是"缺少同步"而非"重排发生了"，所以在 x86 上也有效）；QEMU 模拟抓不到这类问题。见 ARM 平台 §03。

  11. 高级为什么不能在带 PTP / 实时约束的节点上跑 Valgrind？该怎么替代？

    不只是慢，它会制造假 bug 并掩盖真 bug。Valgrind 是动态二进制翻译（整个程序解释执行），10–50x 开销且各代码路径被拉长的倍数不同：

    • 制造假 bug：协议超时被击穿 → 满屏重传与断链；心跳丢失 → 对端判死 → 触发倒换；带硬件看门狗的设备直接复位，连日志都拿不到。
    • 掩盖真 bug：竞态窗口是几十到几百纳秒，相对时序被打乱后不再复现 —— 跑三天干干净净，回到原速 bug 依旧。
    • 与同步机制冲突：ptp4l / phc2sys 依赖精确时间戳做伺服，进程被拖慢会导致 PTP 失锁进 holdover，此时设备的所有时序行为都变了，测出来的东西没有参考价值。

    替代路径（按优先级）：① 抓包离线重放 —— 把故障时段的 pcap 喂给抽出来的协议栈模块，在开发机上随便上 ASan/TSan/Memcheck，输入真实且可重复；② 模块抽出做单测并主动加压；③ 实验室降速：负载降到 1/50 的同时把所有协议超时按同样倍数放大（这一步最常被漏掉），关看门狗，隔离 PTP 相关测试；④ 真实负载下只用低开销工具：UBSan（~1.2x）+ heaptrack/tcmalloc profiling（~1.1–1.5x）+ eBPF。见 排查实战 §03。

  12. 高级长稳跑一周 RSS 从 1.2 G 涨到 3.8 G，怎么定位？为什么 LSan / Memcheck 可能什么都报不出？

    先分清三种可能，方向搞错会白费几天：比较"RSS"与"应用持有的堆"（malloc_info / tcmalloc 统计）。两者差距大 → 碎片或分配器不归还；一起涨 → 真有对象没释放。另外用最便宜的二分法：关掉某个功能看趋势是否变平，能一下把范围缩到一个模块。

    为什么标准泄漏工具报不出：最常见的形态是"逻辑泄漏 / 无界缓存" —— 内存仍然可达（某个 pending 表、缓存、索引还持有它），从 LSan / Memcheck 的定义看完全合法。而且 LSan 只在进程退出时报告，长稳进程根本不退出。

    典型场景：待确认消息记进 PendingMap，收到 ack 时删除；但会话异常断开时没清理自己的条目，ack 永远不来 → 条目永久驻留。链路抖动频繁的现场每天几十万次断链，一周就是几个 G。

    定位与预防：① heaptrack（~1.1–1.5x，可在长稳环境常开）直接给出"T1 到 T2 之间净增长来自哪些调用栈"；② tcmalloc/jemalloc heap profiler（开销 < 5%，可上生产，按需 dump）；③ 最有效的预防是给每个长期存活的容器导出 size 指标 —— 本例中 PendingMap 条目数 480 万 vs 活跃会话 2000，这个比值一秒钟就能看出异常，而 heaptrack 分析要几小时。④ 修法：让 pending 表属于会话（析构自动清理，不依赖谁"记得"调清理函数）+ 条目级兜底超时 + 条目数硬上限（把"无界增长"变成"明确拒绝并告警"）。见 排查实战 §04 案例 3。
