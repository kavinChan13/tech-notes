Ethernet / IP / TCP / UDP：现代网络通信基础

一条数据的四层旅程

Ethernet → IP → TCP/UDP → Application 的配合

应用数据被 TCP/UDP 加上端口、被 IP 加上地址、被以太网加上 MAC，最后变成线上的信号。四个协议各司其职、层层嵌套：

Application决定数据"是什么意思"（HTTP、DNS、NETCONF…）
TCP / UDP用端口区分进程；TCP 额外负责可靠、有序、流控
IP用IP 地址做跨网络寻址与路由
Ethernet用MAC 地址在一段链路内投递帧

生活类比：寄一份合同。街道地址 = IP，快递公司靠它决定往哪个方向转运；"张三 · 法务部" = 端口，到了楼里前台靠它决定交给谁；每一段运输的车牌号 = MAC，只在这一段有意义，换车就换车牌。全程街道地址不变、车牌每一跳都换——这就是"IP 端到端、MAC 逐跳"的全部含义。

四层各自在解决什么

真正要记住的不是一串名字，而是每一层引入了什么能力、为此付了什么代价——工程上的每个选择（要不要 VLAN、走 TCP 还是 UDP、MTU 设多大）都是在这张表的某一行上做交易。

Ethernet 与 MAC：链路层的投递

帧格式、MAC 地址、广播域

以太网是今天最主流的有线链路层技术，数据中心与 5G 前传都在用。它工作在一段"链路"内，用 48 位 MAC 地址标识网卡。

MAC 地址：网卡出厂即固化的 48 位硬件地址。它是"物理身份证"，只在本地链路内有意义；跨网段投递靠 IP，不靠 MAC。

48 位里有结构：前 24 位是 OUI（IEEE 分配给厂商），后 24 位厂商自己保证唯一。更实用的是第一个字节里的两个位——bit 0 是 I/G 位（1 = 组播或广播，所以首字节为奇数的地址如 01:00:5e:…、ff:ff:ff:ff:ff:ff 一眼可辨，交换机会往整个广播域泛洪而不查 MAC 表）；bit 1 是 U/L 位（1 = 本地管理，虚拟机、容器、bond 口、VRRP 虚拟 MAC 都用它，因为没有 OUI 可用）。

两个映射规则抓包时天天用到：IPv4 组播映射到 01:00:5e + 组播 IP 的低 23 位（32 个组播地址会撞同一个 MAC，收上来还要软件二次过滤）；IPv6 组播映射到 33:33 + 目的地址低 32 位，而 IPv6 邻居发现全靠组播，所以正常主机上会看到大量 33:33:ff:xx:xx:xx。

64 与 1500：两个数字的来历，以及巨帧

最小帧 64 字节：让冲突"来得及被发现"

来自最初的 CSMA/CD：发送方必须在自己还在发的时候就检测到冲突，否则会误以为发成功。10 Mbps 以太网最大网络直径对应的往返传播时延约 51.2 µs，正好是 512 位 = 64 字节的发送时间。

今天全双工交换式以太网根本没有冲突，下限却因兼容性与硬件流水线简单而保留：载荷不足 46 字节时必须填充，小于 64 字节的帧叫 runt，直接丢并计入 rx_length_errors。

最大 1500 字节：早期缓存太贵

1980 年代网卡缓存以字节计价，帧越大越贵；同时帧越大，一个比特错误导致的重传浪费越多。这个折中写进标准后就成了整个互联网的默认值。

算术要分清：MTU 1500 是载荷上限，整帧上限 1518（14+1500+4），带一层 VLAN 是 1522。超 1518 但 FCS 正确的帧叫 baby giant——运营商网络必须把中间设备 MTU 调大以容纳标签开销，否则"加了 VLAN 就通不了大包"。

巨帧（Jumbo Frame）把载荷放大到 9000 字节左右，是数据中心与存储网络的标配。它不属于 IEEE 802.3 标准（标准至今只到 1500），纯属厂商事实约定，所以没有"标准巨帧尺寸"：常见 MTU 9000，交换机侧帧上限常写 9216 或 9600（给标签留余量）。

ARP：从"知道 IP"到"能发帧"缺的那一步

内核要发一个目的 IP 是 192.168.1.23 的包，得填帧的目的 MAC——可它只知道 IP，而两者之间没有任何计算关系，只能问。这就是 ARP（RFC 826）。

生活类比：在一栋没有门牌的大楼里找人。你要找"财务部张三"（IP）但不知道他在哪个房间（MAC），于是站在走廊里大喊"财务部张三在哪儿？我在 305！"（广播请求）；张三听到后直接走到你面前说"我在 712"（单播应答）；你记在便签上（缓存），便签会过期（老化）。弱点一目了然：没有人核验回话的是不是张三——任何人都能抢答"我是张三，我在 999"。

解释清 STALE 不是错误。Linux 的设计是"先用旧地址把包发出去，同时异步验证"，所以一屏 STALE 完全正常，真正要担心的是 FAILED 与长期 INCOMPLETE。再加一层：内核会把 TCP 的 ACK 当成邻居可达的隐式证据（这正是 DELAY 状态存在的理由），所以持续有流量的连接几乎不触发 ARP 探测——邻居表的活跃度和业务流量是耦合的。

一个 /16 大二层网段，业务每天固定时段偶发连接失败。失败随机、重试就好、ping 也通，应用与防火墙全查过没结果。最后 dmesg 里出现 neighbor table overflow——这个网段活跃主机超过 1000 台，撞上了默认的 gc_thresh3=1024。内核回收表项时，恰好被回收的那个邻居的下一个包直接返回 EHOSTUNREACH，重试时又重新解析成功，于是表现为"随机、重试就好"。默认值是为"一台机器面对几十个邻居"设计的，大二层与容器网络必须显式上调。

免费 ARP：主备切换的关键一环

免费 ARP（Gratuitous ARP）：没人问，主动发的 ARP 报文，特征是发送方 IP（SPA）与目标 IP（TPA）相同，且以广播发出。它不是为了查询，而是为了宣告"这个 IP 现在归我这个 MAC"，让整个网段刷新缓存。

它有三个真实用途，且都不可替代：

用途怎么发不发会怎样
① IP 冲突检测（ACD，RFC 5227）接口刚起来时发 ARP 探测：请求包，SPA = 0.0.0.0、TPA = 想用的地址两台机器同用一个 IP，流量在两者间随机跳，症状是"时通时不通"且极难定位
② 主备切换刷新邻居表新主抢到 VIP 后立刻广播若干个免费 ARP，宣告 VIP → 新 MAC见上图左半：客户端缓存还指向旧主，包全打到已停的旧主上直到缓存老化
③ 更新交换机 MAC 表同一个广播包顺便让交换机学到"这个 MAC 在这个端口"交换机继续往旧端口转发，客户端知道新 MAC 也没用

手工发用 arping -U（请求形式）或 -A（应答形式）。VRRP 的虚拟 MAC 是固定格式 00:00:5e:00:01:<VRID>，抓 vrrp or arp 时看到"通告 + 紧跟一串免费 ARP"才算切换动作完整，只看到 VRRP 通告不算。还有一个容易忽略的内核开关：net.ipv4.conf.all.arp_accept 默认 0 = 免费 ARP 只更新已有表项、不新建，所以别指望它能给"从没通信过的客户端"建表项；开成 1 会让 ARP 欺骗更容易，非必要不开。

免费 ARP 是高可用切换里最容易漏的一步，而且测试环境测不出来——测试机缓存本来是空的，第一次通信自然会解析；只有"客户端已和旧主通信过一段时间"的生产环境才暴露。三条可靠做法：①抢到 VIP 后连发 3~5 个、间隔 100~200 ms；②验证要在客户端侧 ip neigh 确认 MAC 已更新，不能只看"VIP 配上了"；③优先用 VRRP 虚拟 MAC——切换时 MAC 根本不变，客户端缓存无需更新。见 可靠性与高可用。

03

IP 与端口 Port

跨网络寻址 + 进程多路复用

IP（网络层）解决"如何跨越许多段链路把包送到目标主机"。它是无连接、尽力而为的——不保证送达与顺序，可靠性留给上层。

两种地址与一个端口号

IP 地址：主机的网络身份

IPv4 32 位、IPv6 128 位。路由器按目的 IP 逐跳转发，IP 只管"送到哪台主机"。

端口 Port：进程的门牌号

16 位。包到了主机后靠端口决定交给哪个进程；IP+Port 合起来叫 Socket 地址。

Socket：操作系统提供的网络编程抽象，一个 socket ≈ (协议, 本地 IP:Port, 远端 IP:Port)，也就是 send()/recv() 的对象。一条 TCP 连接由五元组唯一确定。
面试常问"两个客户端连到同一个端口 80，服务器怎么区分"，答案是靠五元组：目的 IP:Port 相同但源 IP:Port 不同。Socket 编程细节见 Socket 网络编程 与 Linux 网络编程。

DSCP 与 ECN：一个字节撑起整个 QoS 体系

IPv4 头第 2 个字节曾叫 TOS，RFC 2474 把它重新划分成 6 位 DSCP + 2 位 ECN。这是电信设备里最常打交道的 QoS 入口：所有"语音优先于下载""信令绝不能丢"的策略最终都落在这 6 个比特上。

DSCP（Differentiated Services Code Point）：6 位、64 个取值的分类标记。它本身不提供任何保障，只是一个标签；差异化来自路径上每台设备读到标签后把包放进哪个队列、用什么调度策略。所以 DSCP 是"承诺的语言"，不是"承诺本身"。

AF 类的编码有规律：AFxy = 8x + 2y，x 是类别（1~4，决定进哪个队列），y 是丢弃优先级（1~3，同队列内拥塞时先丢 y 大的）。所以 AF11/12/13 进同一个队列，只是拥塞时的生存顺序不同——这个"同队列内分级丢弃"常被忽略，却正是 WRED 起作用的地方。

几个关键事实：

  • 队列是"出口方向"的资源，而队列数远少于 DSCP 取值。拥塞只发生在出口，所以每一跳都要重新经历②③④；64 个值挤进典型的 8 个队列，两个"看起来不同优先级"的标记落进同一队列是常态，要查设备的映射表而不是想当然。
  • 信任边界最容易出问题。运营商接入端口默认 untrust，会把客户打的 DSCP 清零或重标记。"应用里标了 EF 但对端收到是 0"绝大多数是这个原因，不是代码 bug。
  • 打标时 DSCP 必须左移 2 位。IP_TOS（IPv6 是 IPV6_TCLASS）拿的是整个 8 位字段，低 2 位属于 ECN，所以要写 val = dscp << 2。直接写 tos = 46 是最常见的错误——那等于 DSCP=11 + ECN=10。
  • 纯二层链路没有 DSCP。eCPRI over Ethernet 根本没有 IP 头，只能用 VLAN 标签里的 PCP（3 位、8 级）——这是前传 QoS 与承载网 QoS 用不同字段的根本原因，见 eCPRI 深入 与 核心网 QoS 与切片。

验证要在接收侧抓一次和发送侧对比，只在发送侧看到 EF 说明不了链路认这个标记。tcpdump -nn -v 打印的 tos 0x48 是整字节，右移 2 位才是 DSCP（0x48 → 18 = AF21）；按 DSCP 过滤要记得掩掉 ECN 两位，写 'ip[1] & 0xfc == 0xb8'（0xb8 = 46 左移 2 位），否则 ECN 一置位就匹配不上。Wireshark 侧直接用 ip.dsfield.dscp / ip.dsfield.ecn，不要用旧的 ip.tos 比整字节。

ECN：让拥塞"被通告"而不是"被丢包"

ECN（RFC 3168）用那 2 位解决一个朴素的问题：路由器想告诉发送方"我快堵了"，唯一手段却是丢包，而丢包的代价是一次 RTT 以上的恢复时延。ECN 让它改成"打个标记继续转发"：

分片：能不分就别分

一个 4000 字节的 IPv4 数据报要走过 MTU 1500 的链路时，IPv4 允许路径上的路由器把它切开（只要 DF=0）：

IPv6 在这件事上做了个明确的决断：路由器一律不分片。链路 MTU 不够就丢包 + 回 ICMPv6 "Packet Too Big"，要分只能源端自己分（加分片扩展头）。同时规定所有 IPv6 链路的 MTU 至少 1280 字节，给了一个"永远安全"的下界。

为什么说分片有害——六条理由，从最直观到最隐蔽：

  1. 丢包率被放大。单片丢包 1%、切成 3 片，数据报失败率就是 1−0.99³ ≈ 2.97%，切 10 片是 9.6%——线性的丢包变成指数的失败。
  2. 后续分片没有传输层头（上图 ①）：ACL 匹配不了、负载均衡的哈希算不出来、连接跟踪也对不上。
  3. 防火墙只有两个糟糕的选择：自己重组（耗内存、加时延、成为攻击面），或丢弃非首片（业务莫名不通）。默认策略多偏向丢弃。
  4. 重组是状态开销，也是攻击面：要为"等其余分片"保留缓冲直到超时（默认 30 s），历史上有一整个家族的攻击建立在这上面。
  5. 16 位 Identification 在高速下会绕回，旧分片可能被拼进错误的数据报而校验和未必能发现（RFC 4963）。
  6. 硬件卸载全部失效。TSO/GRO/LRO、RSS、校验和卸载都不处理分片，一出现就掉到软件慢路径。

PMTUD 与 MSS clamping：为什么"理论上完美"的机制经常失效

PMTUD（Path MTU Discovery，RFC 1191 / 8201）：发送方给所有包置上 DF 位，遇到 MTU 不够的链路时那台路由器丢包并回一个 ICMP，报文里带着下一跳的 MTU，发送方据此下调估计并重发。整个过程是"故意撞墙，靠回音测距"。

查 MTU 有三条命令。ip route get <对端> 输出里的 mtu 是内核已经学到的路径 MTU（没有这个字段不代表就是 1500，也可能只是还没学到）；tracepath 会指出哪一跳打印了更小的 pmtu，末行 Resume: pmtu N 是结论，而 traceroute 根本不报 MTU；ping -M do -s N 里 -M do 才是强制置 DF，N 是载荷（IPv4 下 N+28 = 待测 MTU），失败会打印 message too long, mtu=…——用默认 ping 去验 MTU 结果一定是"通"，什么也验不出来。

它为什么经常失效？整个机制建立在"那个 ICMP 一定能回到发送方"这个假设上，而这个假设在真实互联网里非常脆弱：

失效原因为什么会发生症状
ICMP 被防火墙一刀切"禁用 ICMP 提升安全性"是流传极广的错误建议，deny icmp any any 把 Type 3 Code 4 一并挡了最常见。小包通、大包死
无状态设备找不到会话ICMP 差错的源地址是中途某台路由器，不属于任何已建立会话，容易被当成意外流量丢弃同上，且更难说服对方"这不是攻击"
ECMP / Anycast 让 ICMP 走错机器多台服务器共享一个 IP，ICMP 回到哈希算出来的某一台，而发大包的是另一台——收到的那台根本没有这条连接大规模 CDN / LB 的典型故障，只影响一部分用户
隧道端点不透传 ICMPGRE / IPsec / VXLAN 加了外层头使内层 MTU 变小，ICMP 打给隧道端点，端点要能翻译成内层的 ICMP——很多实现做不到或没配"VPN 里打不开某些网页"的经典成因
源地址被 uRPF 挡掉ICMP 的源是路由器接口地址，可能是私网或不在路由表里的地址偶发、难以复现
非对称路径去程与回程走不同路径，两侧瓶颈 MTU 不同单方向卡死，另一方向正常
判据很简单：如果"小请求秒回、大响应必挂"，先怀疑 MTU，不要去查应用。快速验证就是 ping -M do -s <递减尺寸> 的二分。这里的"大响应"可以是 scp 一个文件、HTTP 返回一个大页面、NETCONF 下发一份完整配置。

MSS clamping：不问路径，直接把两端的期望改小

既然 ICMP 不可靠，主流补救是绕开它：在路径上的设备（通常是隧道端点或 NAT 网关）拦下 TCP 的 SYN 报文并直接改写里面的 MSS 选项，让两端一开始就协商出一个小到能过的段大小。Linux 上是 iptables -t mangle … -j TCPMSS --clamp-mss-to-pmtu，或 --set-mss N 写死（如 GRE over IPv4 开销 24 B，隧道内 MSS = 1500−24−40 = 1436）。

匹配条件写 --tcp-flags SYN,RST SYN 而不是只写 SYN，是这条规则最容易抄错的地方。它的含义是"SYN=1 且 RST=0"，因此同时命中 SYN 和 SYN+ACK——MSS 是各自单向通告的，两个方向都要改，只改一个没用。

但 MSS clamping 不是万能药，边界必须清楚：

手段覆盖范围要求局限
MSS clamping只有 TCP必须部署在数据路径上，且能看到明文 SYN对 UDP / QUIC / ESP / eCPRI 完全无效；只在建连时生效，中途路径变化不跟随
PLPMTUD（RFC 4821 / 8899）TCP、QUIC、SCTP协议栈支持不依赖 ICMP，靠"发探测包看有没有确认"二分。Linux 上 tcp_mtu_probing=1（检测到黑洞才启用）/ =2（一直启用），代价是收敛要几个 RTT
静态调小接口 MTU所有协议能改两端主机最粗暴也最可靠，但全局降低效率，路径变好也不会自动调回
按路由设 MTU所有协议，粒度更细ip route add … mtu 1400要维护，路径变化时会失准
应用层自己保守UDP 类协议唯一可靠的办法应用改代码如 DNS 把 EDNS0 缓冲降到 1232、QUIC 初始包限制在 1200 字节内。"不产生大包"永远比"让大包能过"可靠
光说"ICMP 被墙了"只能得一半分。加分的两点：① 指出结构性缺陷——PMTUD 让一个端到端的机制去依赖第三方主动发起的反向通知，这在有 anycast、ECMP、无状态防火墙、隧道翻译的现代网络里天然不可靠；② 给出方向正确的解法：改成"不依赖别人帮忙"，也就是 PLPMTUD——自己发探测、自己看确认、自己二分。这也解释了为什么 QUIC 从一开始就内建 PMTU 探测而不用 ICMP。

名字只差三个字母，作用毫不相干。一句话区分：SO_REUSEADDR 解决"重启时 bind 不上"，SO_REUSEPORT 解决"多进程一起监听同一个端口"。

int listen_reuseport(const char *port, int backlog)
{
    int on = 1, off = 0;
    int fd = socket(AF_INET6, SOCK_STREAM | SOCK_CLOEXEC, 0);
    if (fd < 0) { perror("socket"); return -1; }

    /* ① 重启时不被残留的 TIME_WAIT 卡住 */
    if (setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof on) < 0) goto fail;
    /* ② 允许多个进程同时 listen 同一端口 */
    if (setsockopt(fd, SOL_SOCKET, SO_REUSEPORT, &on, sizeof on) < 0) goto fail;
    /* ③ 双栈：一个 socket 同时收 v4 与 v6。失败不致命 */
    setsockopt(fd, IPPROTO_IPV6, IPV6_V6ONLY, &off, sizeof off);

    /* ⚠ 上面三个 setsockopt 必须在 bind 之前。
         bind 之后再设不生效，而且不报错 —— 这是
         "我明明设了但没用"的头号成因。 */
    struct sockaddr_in6 a = { .sin6_family = AF_INET6,
                              .sin6_addr   = in6addr_any,
                              .sin6_port   = htons(atoi(port)) };
    if (bind(fd, (struct sockaddr *)&a, sizeof a) < 0) goto fail;
    if (listen(fd, backlog) < 0) goto fail;
    return fd;
fail:
    perror("listen_reuseport"); close(fd); return -1;
}

/* 每个 worker 进程各自调一次，内核按四元组哈希分流。
   不要 fork 之后共享同一个 fd —— 那是另一种模型（共享 accept 队列）。 */
SO_REUSEPORT 的两个坑都在"缩容"这一侧。① 关闭组内某个 listen socket 时，它 accept 队列里"已完成握手但还没被 accept"的连接会被丢弃，客户端看到连接建立后立刻被 RST。较新内核能迁移到组内其它 socket（需开 net.ipv4.tcp_migrate_req），但不能假定线上都有；稳妥做法是滚动重启时先让新进程加入组、跑一会儿再关旧的。② 哈希按四元组算不按负载算，上游只有几台代理时分布会严重不均——"某个 worker CPU 100%、其它闲着"就是这个原因，需要自定义分发可以挂 eBPF。

TCP：为什么可靠

连接、序号、确认、重传、流控、拥塞控制

TCP 在"不可靠的 IP"之上，用一整套机制造出一条"可靠、有序的字节流"管道。它的可靠不是魔法，而是这几件事叠加：

机制解决什么怎么做
连接管理双方建立 / 释放共识三次握手、四次挥手
序号 + 确认(ACK)知道哪些到了、哪些丢了每个字节有序号，接收方回 ACK
超时 / 快速重传丢包恢复没收到 ACK 就重发
校验和检测损坏校验错的段丢弃并重传
滑动窗口 / 拥塞控制别压垮接收方 / 别压垮网络接收方通告可用缓冲；慢启动、拥塞避免、BBR 等

三次握手 & 四次挥手（一图记住）

为什么建连要三次而不是两次？
答：核心不是"确认三次"，而是要同步两个方向的初始序号；每个方向都需要"发出 + 被确认"，共四个动作，第②步合并了两件事才压成三个报文。
TIME_WAIT 是干嘛的？
答：主动关闭方等 2MSL，一是保证最后那个 ACK 能到（丢了要能再回一次），二是让旧连接的迷途报文消散，免得污染复用同一五元组的新连接。

TCP 头逐字段

TCP 头基本 20 字节，带选项最多 60 字节。它比 IP 头更值得逐字段看懂，因为抓包排障时几乎每个字段都会用到：

字段位宽作用排障时怎么用
Source / Dest Port16 + 16连接的两个端点与 IP 一起构成五元组，是内核查连接表的键

窗口缩放有一个非常隐蔽的失败模式。路径上若有"半智能"中间设备把 SYN 里不认识的选项剥掉了而 SYN-ACK 的选项完好，两端对"要不要缩放"的理解就不一致：一端认为对方窗口有 8 MB、实际只有 64 KB，猛发数据 → 对端缓冲溢出 → 大量丢包重传，吞吐反而极低。症状是"连接能建、小数据没问题、大流量一塌糊涂"，而且两端抓包各自看起来都自洽，必须同时在两端抓、对比 SYN 与 SYN-ACK 的选项才能发现。这类"中间设备篡改握手"也是 QUIC 选择把握手全部加密的动机之一。

握手的每一步在解决什么问题

"为什么是三次"这道题几乎必问，而"因为要确认双方都能收发"这个答案只对了一半。把三步逐个拆开看，每一步都在解决一个具体的、可命名的问题：

步骤报文做到了什么还差什么
① 客户端 → 服务端SYN, seq=x声明"我要建连"并告知初始序号 x，同时通告 MSS、窗口缩放、SACK 能力服务端不知道这个 SYN 是刚发的还是迟到的旧包；客户端也不知道服务端在不在
② 服务端 → 客户端SYN+ACK, seq=y, ack=x+1一个报文干两件事：确认收到 x，并告知自己的初始序号 y仍不知道客户端收到了 y——反方向还没被确认
③ 客户端 → 服务端ACK, ack=y+1确认收到 y，两个方向都完成"发出→被确认"的闭环可以发数据了
两次握手为什么不行——要举具体的坏后果，而不是说"不够可靠"。省掉第三步的话：①一个很久以前被放弃的旧 SYN 迟到了，服务端会为它建连、分配缓冲、甚至通知应用"来了个新客户"，而客户端根本不认——资源泄漏加状态不一致，这也是 RFC 793 的原始理由；②伪造源地址的单个 SYN 就能让它分配完整连接资源。第三步的本质是"让服务端拿到客户端确实在线的证据，再决定投入资源"。

顺带说清一对常被混为一谈的队列——服务端收到 SYN 时并非零开销，会在半连接队列留一个轻量表项，这正是 SYN 洪泛的着力点：

挥手为什么是四次，以及完整的状态机

答案的关键在一个词：TCP 是全双工的，一条连接其实是两条独立的单向字节流。FIN 的语义不是"关闭连接"，而是"我这个方向不再发数据了"——所以关闭必须两个方向各来一次、每次都要被确认（时序见 §4.1 那张图）。发出 FIN 的一方仍然可以继续接收，这就是"半关闭"（shutdown(fd, SHUT_WR)）。

状态在等什么堆积起来说明什么
SYN_SENT等 SYN+ACK对端不可达、端口没开、SYN 被静默丢弃。大量堆积 = 网络或防火墙问题，不是应用问题
SYN_RECV等第三次 ACK正常停留极短。大量堆积 = SYN 洪泛，或回程路径不通
ESTABLISHED在传数据或空闲数量应与业务量匹配，只增不减 = 连接泄漏
FIN_WAIT_1等对方 ACK 我的 FIN停留久 = 对端不响应或网络断了
FIN_WAIT_2等对方的 FIN对端应用忘了 close()；Linux 用 tcp_fin_timeout（默认 60 s）兜底
CLOSE_WAIT等本端应用调 close()几乎 100% 是自己的 bug：读到 EOF 却没关 fd，见下面的框
LAST_ACK等对方 ACK 我的 FIN短暂正常，堆积说明对端已消失
TIME_WAIT等 2MSL 到时正常现象，但数量受临时端口数限制，见 §4.6
大量 CLOSE_WAIT 与大量 TIME_WAIT 性质完全不同，千万别一起处理。
TIME_WAIT 多是"设计的结果"：出现在主动关闭一方，说明服务在大量主动关连接，机制本身没问题，只是可能撞上端口上限。
CLOSE_WAIT 多是"代码的 bug"：出现在被动关闭一方，含义精确到无可辩驳——对端已经关了、内核也通知了你（read 返回 0 / EPOLLRDHUP），而你的代码没有调 close(fd)。它永远不会自动消失，只会涨到 fd 耗尽。常见成因是把 read()==0 当成"没数据"而不是"对端关闭"。排查一步到位：看 /proc/<pid>/fd 的数量是否单调增长。

TIME_WAIT 的两个理由，与 2MSL 的来历

MSL（Maximum Segment Lifetime）：一个 TCP 段在网络中能存活的最长时间。它不是测出来的，是约定的——RFC 793 建议 2 分钟。实践中由 IP 的 TTL 上限间接保证（跳数有限、每跳耗时有限）。Linux 把它固定实现为 30 秒，因此 TIME_WAIT = 2×30 = 60 秒。

为什么要等，而不是发完最后一个 ACK 就直接关掉？两个理由，缺一不可：

理由一：保证最后那个 ACK 能到

第四次挥手的 ACK 没有人会确认它（否则无穷递归）。它丢了的话，被动方会停在 LAST_ACK 并重传自己的 FIN，这时主动方必须还"活着"才能再回一次。

不等就关闭的话：主动方已 CLOSED，收到重传的 FIN 会回 RST，被动方于是认为连接异常终止并可能报错——而实际上数据全都传完了。这是"连接明明正常结束却报错"的一个真实来源。2MSL 正好覆盖最坏情况：一个 MSL 让 ACK 走过去，一个让对端可能重传的 FIN 走回来。

理由二：让旧连接的"幽灵包"消散

五元组可以复用。若连接刚关就用同一个五元组建了新连接，网络里还漂着的旧数据段五元组完全匹配新连接。

唯一防线是序号随机化，旧包大概率落在窗口外被丢弃。但"大概率"不等于"一定"——32 位序号在高速连接上会绕回，旧包恰好落进新窗口是可能的，结果是把陌生数据静默混进应用的字节流。等 2MSL 就是用时间把这个可能性抹掉：所有旧段都已超过生存期，物理上不可能再出现。

排查的标准动作是用 ss -tan 按状态计数（CLOSE-WAIT 只要不是 0 就值得看一眼代码）。三个相关 sysctl 的适用面差别很大，抄错方向完全没用：

tcp_fin_timeoutFIN_WAIT_2 的兜底超时，默认 60 s以为它能缩短 TIME_WAIT——完全无关。Linux 的 TIME_WAIT 时长写死在内核（TCP_TIMEWAIT_LEN），没有任何 sysctl 能改
tcp_tw_reuse允许把 TIME_WAIT 的四元组重新用于新发起的出向连接；依赖 tcp_timestamps=1 靠时间戳区分新旧包。取值 0 关 / 1 开 / 2 仅 loopback（较新内核默认）指望它能救服务端——它只帮"作为客户端主动连出去"的场景，对监听侧无效

TIME_WAIT 真正的工程解法不是"缩短它"，而是"少产生它"：①改用长连接 / 连接池——它与"关连接的次数"成正比，能直接降两三个数量级还顺带省掉握手 RTT；②让对端做主动关闭方；③确实需要海量短连接时扩五元组空间，而不是去调超时。

UDP：为什么低开销

无连接、不可靠、但快而简单

UDP 几乎是"在 IP 上薄薄加了个端口"：8 字节头，无连接、无握手、不保证送达与顺序、不做流控。正因为"什么都不管"，它开销极小、延迟极低——对比 TCP 至少 20 字节头 + 握手往返 + 状态维护。

UDP 的优势

  • 无握手 → 零 RTT 起步延迟
  • 头小、无状态 → 省带宽、省内存
  • 应用可自定义可靠性策略

UDP 的代价

  • 可能丢包、乱序、重复
  • 无流控/拥塞控制 → 需应用自己节制
  • 可靠性要自己在应用层实现
为什么实时数据爱用 UDP？语音/视频/游戏里"迟到的数据"比"丢一点数据"更糟——一帧旧画面重传过来已经没用了。宁可丢、不可等，所以选 UDP 并在应用层做补偿；5G 前传的 eCPRI 用户面同样是"实时优先"。

选型口诀："数据不能错、可以稍慢"→ TCP；"数据要快、旧了就丢"→ UDP。本主题里，NETCONF 管理面走 TCP（要可靠配置），而 eCPRI 用户面/实时遥测偏向无连接（要低延迟确定性）——这正是"协议选择服务于业务特性"的典型例子。

四个判据，按顺序问就能定下来

口诀好记但不够用。真做决策时按四个问题依次问，任何一个答"是"就基本定了：

  1. "迟到的数据还有用吗？"——没用（当前语音帧、当前 IQ 采样）就用 UDP。这一条最有决定性，因为它让"可靠交付"本身变成负担：TCP 为了保序会把后到的新数据压在队头等重传，而你要的恰恰是"跳过旧的，给我最新的"。
  2. "消息之间有依赖吗？"——配置下发、状态机推进这类丢一条后面全错的场景用 TCP；每条消息独立可解释才适合 UDP。
  3. "有多少个对端？"——一对多、组播、广播只能 UDP，TCP 天生点对点。
  4. "我愿意自己写多少传输层代码？"——§5.3 那张表的九项能力你打算实现几项？答案若是"大部分都要"，就用 TCP，或用一个已经做完这些事的库（QUIC / DTLS / RTP+RTCP），而不是自己从头造。
业务选择决定性理由
NETCONF 配置下发TCP（over SSH/TLS）配置有事务语义，少一个字节就是错的；对时延不敏感
eCPRI 用户面（IQ 数据）无连接承载下一个采样周期几十微秒后就来了，重传毫无意义；见 eCPRI 深入
PTP 时间同步UDP 或纯 L2需要组播 + 时间戳精度，重传会破坏时间语义；见 PTP / SyncE
性能计数上报UDP（可加应用层确认）丢一个采样点可接受，但要注意 §1.2 的小包开销
告警 / 软件升级 / 日志回传TCP告警丢了就是事故，宁可延迟也不能丢；大文件同样要完整性
核心网信令（部分接口）SCTP需要多流避免队头阻塞 + 多归属做链路冗余，这两点 TCP 都给不了
今天的答案其实是三选一，不是二选一。QUIC（RFC 9000）跑在 UDP 上，却把可靠、有序、拥塞控制、加密全在用户态实现了一遍，并解决了 TCP 的两个结构性问题：①多个流互相独立，一个流丢包不阻塞其它流；②握手全部加密，中间设备无法篡改选项（§4.3 那个坑在 QUIC 上不存在）。所以"要可靠但也要低延迟"的新项目，默认答案往往是 QUIC——代价是成熟度与可观测性。设备内部的私有协议另说：链路可控、时延预算紧，自定义 UDP 往往更合适。

TCP 粘包 / 拆包与 message framing

初学者最常踩的坑，也是二进制协议设计的起点

很多人以为 send() 一次、对端 recv() 一次就能拿到"一条完整消息"。错。TCP 是字节流，没有"消息边界"的概念。你发的 3 条消息，可能被合并成一次收到（粘包），也可能一条消息被拆成两次收到（拆包）。

解决办法是message framing（消息分帧），三种经典做法：定长（简单但浪费）、分隔符（文本协议常用，但正文不能含分隔符）、长度前缀 TLV/LV（消息头里放"后面还有多少字节"，二进制协议的主流做法）。下一节逐项对比。

UDP 不存在粘包问题——它保留消息边界（一个 sendto 对应一个 recvfrom），只是每个数据报有大小上限。粘包本质是"TCP 是流不是消息"。如何设计带长度前缀的二进制协议，见 二进制通信协议设计与解析。

"粘包"这个词其实误导人

它让人以为发生了某种意外的合并。真相是：TCP 从来就没有"包"这个概念，粘包不是异常而是常态。关键在于 send() 并不发送任何东西——它只是把字节拷进内核发送缓冲区就返回（返回值可能小于你要求的），之后由内核按当前 MSS、拥塞窗口、对端窗口决定怎么切分。接收端把段按序号拼进缓冲区，边界信息在这一步彻底消失。

三个必须放弃的错误假设，各自都造成过真实故障：① "send() 一次对应 recv() 一次"——这就是粘包的全部内容；② "send() 返回就是发出去了"——它只是进了缓冲区，对端可能永远收不到而你完全不知道；③ "PSH 标志代表消息边界"——危害最大。PSH 由内核在"发送缓冲即将空"等条件下自动置位，和应用的消息结构毫无关系，靠它切分的代码在开发机上好好的、一上生产就随机错乱。

三种分帧方案，各自的适用边界

定长分隔符长度前缀（LV / TLV）
怎么切每 N 字节一条扫描到分隔符为止（如 \r\n）先读固定长度的头，从头里取出后续长度
解析成本最低要逐字节扫描，跨读入边界还要保留状态低：一次读头 + 一次读体
内容限制无，但要填充正文不能出现分隔符，否则要转义（又引入转义的转义）无限制，二进制安全
空间开销浪费（短消息也占 N 字节）小（1~2 字节）小（2~4 字节）
能否预分配能不能，读完才知道多长，只能边读边扩容能，这是它最大的实际优势
抗错能力一旦错位永远错位较好，丢弃到下一个分隔符就能重新同步差：长度字段被破坏就读到荒谬的长度，必须靠魔数 + 长度上限自保
典型用户固定格式遥测帧、硬件寄存器镜像HTTP/1.1 头、Redis、SMTP 等行协议绝大多数二进制协议：HTTP/2 帧、gRPC、NETCONF 1.1、eCPRI

工程上最常见的组合是"魔数 + 版本 + 类型 + 长度"的固定头 + 变长体。魔数不是装饰——它是长度前缀方案唯一的自救手段：一旦解析错位，靠魔数才能重新找到帧边界。

一个正确的读循环

下面这段是阻塞模式下的完整实现。它短，但每一处错误处理都对应一个真实踩过的坑：

#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <arpa/inet.h>

#define FRAME_MAGIC   0x4B54        /* "KT"，用于错位后重新同步 */
#define FRAME_MAX_LEN 1048576       /* 1 MB。这个上限不是可选项，见下 */

/* 帧头：8 字节，全部网络字节序 */
struct frame_hdr {
    uint16_t magic;      /* 0x4B54 */
    uint8_t  version;    /* 协议版本 */
    uint8_t  type;       /* 消息类型 */
    uint32_t len;        /* 后续 body 的字节数，不含本头 */
};

/* 读满 n 字节。这是整段代码的核心：
     返回 n  → 读满了
     返回 0  → 对端在帧边界上正常关闭（这是唯一合法的 EOF 位置）
     返回 -1 → 出错，或读到半条消息就 EOF（协议错误，不能当正常关闭处理） */
static ssize_t read_full(int fd, void *buf, size_t n)
{
    size_t got = 0;
    while (got < n) {
        ssize_t r = read(fd, (char *)buf + got, n - got);
        if (r > 0) { got += (size_t)r; continue; }
        if (r == 0) {
            /* EOF。读了一半才 EOF 说明对端中途死了，必须区别对待 */
            if (got == 0) return 0;
            errno = EPROTO;
            return -1;
        }
        if (errno == EINTR) continue;   /* 被信号打断，重试而不是报错 */
        return -1;
    }
    return (ssize_t)n;
}

/* 收一帧。返回 1 成功（*body 由调用方 free），0 正常结束，-1 错误 */
int recv_frame(int fd, struct frame_hdr *hdr, void **body)
{
    uint8_t raw[8];
    ssize_t r = read_full(fd, raw, sizeof raw);
    if (r <= 0) return (int)r;          /* 0 或 -1 直接透传 */

    /* 手工解字段，不要直接 memcpy 到结构体上 —— 结构体有对齐填充，
       在不同编译器/架构上布局可能不同。这是跨平台协议的基本纪律。 */
    hdr->magic   = (uint16_t)((raw[0] << 8) | raw[1]);
    hdr->version = raw[2];
    hdr->type    = raw[3];
    memcpy(&hdr->len, raw + 4, 4);
    hdr->len     = ntohl(hdr->len);

    if (hdr->magic != FRAME_MAGIC) {
        fprintf(stderr, "魔数不对（0x%04x），流已错位\n", hdr->magic);
        errno = EPROTO;
        return -1;                        /* 断连重来比"尝试恢复"更安全 */
    }
    /* ⚠ 最关键的一行：长度必须校验上限。
       少了这一行，对端（或攻击者）发一个 len=0xFFFFFFFF 的头，
       你就会 malloc 4 GB —— 一个报文打死一个进程。 */
    if (hdr->len > FRAME_MAX_LEN) {
        fprintf(stderr, "帧长 %u 超过上限\n", hdr->len);
        errno = EMSGSIZE;
        return -1;
    }
    if (hdr->len == 0) { *body = NULL; return 1; }   /* 允许空体 */

    void *buf = malloc(hdr->len);
    if (buf == NULL) return -1;
    if (read_full(fd, buf, hdr->len) != (ssize_t)hdr->len) {
        free(buf);
        return -1;
    }
    *body = buf;
    return 1;
}

四个要点按重要性排：①长度上限校验是安全边界不是优化——缺了它，一个 8 字节的恶意头就能让你 malloc 4 GB；②"读到一半 EOF"必须与"正常关闭"区分，混在一起会把对端崩溃当成正常结束；③不要 memcpy 到结构体上，结构体有对齐填充，逐字段解析是唯一可靠的做法；④EINTR 要重试，当成错误会导致偶发连接中断。

非阻塞 / epoll 下这段代码不能直接用：read_full 的循环在非阻塞 fd 上会因 EAGAIN 立刻失败，而"数据还没到齐"完全正常。正确做法是每条连接维护一个持久缓冲区 + 一个解析状态（在等头 / 在等体 / 还差多少字节），每次 EPOLLIN 把能读的全读进缓冲，再循环解出尽可能多的完整帧——一次可读事件可能带来 0 条或十几条消息。见 Socket 网络编程。

Nagle 与延迟 ACK：那个诡异的 40 毫秒

分帧讲完，还有一个和"小写入"密切相关的经典陷阱，因为它的症状常被误判成"网络慢"。

Nagle 算法（发送侧）

规则很简单：如果已经有未被确认的小段在途，就先不发新的小段，攒着，等 ACK 回来或者攒够一个 MSS 再发。目的是防止应用逐字节写入时产生海量的"41 字节帧运 1 字节数据"（telnet 时代的真实问题）。

关掉它：setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &on, sizeof on)。

延迟 ACK（接收侧）

接收方收到数据后不立刻回 ACK，而是等一会儿（Linux 上典型 40 ms，可从 ss -i 的 ato:40 看到），希望能把 ACK 搭在自己的响应数据上一起发，省一个报文。

目的同样合理：减少纯 ACK 报文数量。

两个各自合理的优化叠在一起就死锁了。触发条件是"写-写-读"模式，也就是把一条逻辑消息分成两次 write()（很自然的写法：先写头，再写体）：

这道题的正确答案不是"关掉 Nagle"。TCP_NODELAY 能让症状消失，但它治的是症：真正的毛病是把一条逻辑消息拆成了多次系统调用。更好的修法是用 writev() 一次把头和体写出去——既没有 40 ms，还少一次系统调用、少一个报文。什么时候该真开 TCP_NODELAY？请求-应答型的低时延交互；批量传输不要开，那里 Nagle 的合并是有价值的。还有一个方向相反的 TCP_CORK：主动堵住发送缓冲直到解除或攒满一个 MSS。能说清这两个是一对相反的工具，是本题的加分点。
一个 RPC 客户端的 P99 时延死死卡在 41 ms。同机房调用，ping 0.25 ms、服务端自报处理 1.2 ms，客户端却测到 41 ms，而且P50 与 P99 几乎一样——这个"没有抖动"就是最大的线索。抓包看到每次请求都是两个 TCP 段（先 12 字节头，40 ms 后跟上 300 字节体），中间夹一个纯 ACK。改成一次 writev() 后时延变成 1.5 ms。判据：时延恰是 40 ms 整数倍且分布极窄，先怀疑 Nagle 与延迟 ACK，不要去查网络。

延迟 / 吞吐 / 抖动 / 带宽

评价一个通信系统好坏的四个核心指标

这四个词在通信系统里几乎无处不在（尤其 5G 前传对它们极其敏感），必须分清：

指标含义类比单位
带宽 Bandwidth链路理论最大传输能力马路有几车道bps（Gbps…）
吞吐 Throughput实际达到的传输速率实际每秒过多少车bps
延迟 Latency一个包从发到收的时间一辆车走完全程用时ms / µs
抖动 Jitter延迟的波动（不稳定程度）每辆车用时忽长忽短ms / µs

带宽 ≠ 吞吐

10 Gbps 的链路实际吞吐可能只有 6 Gbps——受协议开销、丢包重传、拥塞、对端处理能力限制。带宽是上限，吞吐是现实。

低延迟 ≠ 高吞吐

批量攒一波再发能提升吞吐却增加延迟，一有数据就发延迟低却牺牲吞吐。通信系统设计常在两者间取舍。

为什么这四个指标对 5G 前传是"生死线"？前传（DU↔RU）传的是无线基带实时 IQ 数据，延迟要求低到 ~100 µs 级、抖动要极小、带宽需求又极大（Massive MIMO）。这正是 CPRI 带宽压力、eCPRI 出现与 PTP/SyncE 时间同步的根本动因，见 前传/中传/后传 与 PTP/SyncE。

带宽时延积：为什么"带宽够却传不快"

BDP（Bandwidth-Delay Product，带宽时延积）= 带宽 × RTT。它的物理含义是"这条路径上最多能同时装多少字节还没被确认的数据"——像一根管子的容积。要把带宽跑满，发送方的在途数据量必须至少等于 BDP；而在途数据量的上限由窗口决定。

要调的是 net.ipv4.tcp_rmem / tcp_wmem 的第三个值（最大值），min 与 default 不要动；net.core.rmem_max / wmem_max 同步上调。默认的 6 MB 在 100 ms RTT 上只支撑约 480 Mbps，跑不满千兆。改完用 ss -tin 确认 wscale 确实变大了。

调大缓冲之前，先确认瓶颈真的是窗口。判据很清晰：cwnd 远小于 BDP/MSS 时瓶颈是拥塞控制（说明路径上有丢包）；cwnd 已经很大而吞吐上不去、且对端通告窗口很小时，瓶颈才是接收缓冲。两者解法完全相反：前者要查丢包、换拥塞控制算法（BBR 在有丢包的长路径上通常明显好于 CUBIC），后者才是调 tcp_rmem。盲目调大缓冲的副作用是 bufferbloat——时延变差而吞吐没变好。深入讨论见 网络常见机制。

抖动怎么量化：常用包时延变化（PDV）。单向时延需要两端时钟同步，否则测出来的是"时延 + 时钟偏差"——这就是精确抖动测量绕不开 PTP 的原因（见 PTP / SyncE）。接收侧对抗抖动靠抖动缓冲：牺牲一点固定时延把到达间隔熨平，缓冲越大越平滑但总时延越高，这是实时通信最核心的取舍。

抓包位置：你抓到的包，可能线上并不存在

这是整章最反直觉的一节，也是把"会用 tcpdump"和"懂抓包"区分开的地方。根源在挂钩位置：tcpdump 通过 AF_PACKET 挂在网络设备层——发送方向是内核把 skb 交给驱动之前，接收方向是驱动把 skb 交给协议栈之后，而现代网卡的大量工作发生在这两点之外：

你在抓包里看到的线上真实情况怎么确认 / 怎么绕开
length 65160 的"超大包"不存在这样的帧。这是 TSO/GSO 的一个大 skb，硬件会切成几十个 ≤MTU 的段ethtool -k 查 segmentation；要看真实分段就临时关掉 tso/gso
接收侧也有超大包GRO/LRO 把多个帧合并了，包数、到达间隔、时间戳全部失真关掉 gro/lro。研究乱序、重复、微突发时必须关
"checksum incorrect"警告校验和由网卡在钩子之后填，发送方向抓包里它本来就是空的，这是假警报只在发送侧本机抓包时出现；接收侧或镜像抓包里的校验和错才是真的
看不到 VLAN 标签网卡把标签剥到 skb 元数据里了，链路上确实带着标签ethtool -k 查 vlan-offload；过滤时仍要注意 vlan 关键字会把偏移整体 +4
时间戳"很准"内核软件打的，与包真正上线的时刻有几微秒到几十微秒偏差且会抖要微秒级精度必须用硬件时间戳（SO_TIMESTAMPING / 网卡 PTP），见 PTP / SyncE
本机没丢包可能是 tcpdump 自己丢了退出时那三行统计每次都要看

当前开了哪些卸载用 ethtool -k eth0 查（关注 tcp-segmentation-offload、generic-receive-offload、rx-vlan-offload）；要看真实分段就 ethtool -K eth0 tso off gso off gro off，查完记得开回来。但要注意关卸载本身就是观察者效应——关掉之后 CPU 开销、吞吐、时延特征都变了，你测的已经不是原来那个系统。所以顺序很重要：先在开着卸载的状态下判断"是不是这一类问题"，确定需要时才关，而且只关必要的那一项。

完整答案有三个层次，能答到第三层就很难得。①位置——tcpdump 挂在设备层、TSO 之前 GRO 之后，看到的是"内核视角的包"；本机抓包物理上不可能看到网卡之后的丢弃。②内容与时间——校验和可能还没填、VLAN 可能已被剥、时间戳是软件打的且带抖动，所以抓包适合回答"发生了什么"，不适合回答"精确什么时候发生"。③观察行为本身会改变系统——抓包抢 CPU、可能自己丢包，关掉卸载又改变了被测系统的性能特征。一句话收尾：抓包不是"网络的照片"，而是"内核在某个特定位置的记账"。
两台机器之间"丢包率 3%"，查了两周查不出来。本机抓包显示发出 100 个包、对端只收到 97 个，而两侧网卡计数器都是零错误零丢弃。转折点是注意到发送侧抓到的包长度都是几万字节——那是 TSO 的大 skb，"发出 100 个包"这个前提本身就是错的，线上实际是几千个帧。关掉 tso/gso 重抓后才看清丢的是同一个大 skb 切出来的尾部若干段，进一步指向对端网卡接收环形缓冲在微突发下溢出。教训：在弄清"抓包里的一个包"对应线上几个帧之前，任何按包计数的推理都是空中楼阁。

  • 以太网帧最小 64 字节、载荷上限 1500，线上还要算前导码与帧间隔；小包场景下开销占比可以超过 70%，而且 pps 才是瓶颈

  • TCP 是字节流会粘包/拆包，必须自己做 framing（长度前缀最常用，且必须校验长度上限）

面试题（12 道）

按难度分三组，覆盖帧格式、IP 头、分片、TCP 状态机与抓包判读

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础以太网最小帧为什么是 64 字节？今天还有意义吗？

    它来自最初的 CSMA/CD 冲突检测：发送方必须在自己还在发送时就检测到冲突，否则会误以为成功而不去重发。10 Mbps 以太网最大网络直径对应的往返传播时延约 51.2 µs，恰好是 512 位 = 64 字节的发送时间。算术上还要说清它包含什么：6+6+2+46+4 = 64，不含前导码、SFD 与帧间隔（线上最小占用是 84 字节），因此最小载荷 46 字节、不足要填充。

    今天全双工交换式以太网根本没有冲突，下限却因兼容性与硬件流水线简单而保留，后果有两个：①小包效率极低——24 字节载荷被撑到线上 84 字节，有效占比不到 30%，按载荷估带宽会低估 2~4 倍；②pps 成为独立瓶颈——1 Gbps 下最小帧约 1.488 M pps，很多软件转发路径远达不到，此时限制你的是包速率而不是比特率。

    加分点：小于 64 字节的帧叫 runt，直接丢弃并计入长度错误；再能说出"填充字节必须显式置零"，说明你理解填充不只是凑数。

  2. 基础EtherType 是什么？加了 VLAN 标签之后它在哪里？

    EtherType 是以太网头里的 2 字节字段，告诉接收方"载荷是什么协议"，是链路层与网络层之间的唯一接口（常见值见 §2.1）。一个容易忽略的历史细节：这两个字节在老 802.3 格式里是长度字段，判据是数值——≤ 1500 当长度，≥ 0x0600 当类型，这个二义性正是"以太网帧有两种格式"的来源。

    加 VLAN 后的变化是"插入"而不是"替换"：TPID 占了偏移 12~13、TCI 占 14~15，真正的 EtherType 被推到 16~17，QinQ 则被推到偏移 20。

    真正的考点是解析代码怎么写。把偏移写死成 12 是最经典的 bug：遇到 VLAN 读到 0x8100，代码要么判未知协议丢包，要么按偏移 14 当 IP 头解析、读出荒谬的"IP 版本"。正确做法是循环剥离并给循环设层数上限——不设上限就是可被恶意报文触发的 DoS 点。

    再加一句体现实战：网卡的 VLAN 卸载常把标签剥到 skb 元数据里，导致抓包"看不见 VLAN"；而 tcpdump 的 vlan 关键字会把后续偏移整体 +4，必须写在过滤表达式最前面。

  3. 基础ARP 解决什么问题？免费 ARP 是什么，用在哪里？

    ARP 填补的是"知道目的 IP"到"能填帧的目的 MAC"之间的空白——两者没有任何计算关系，只能问。流程是请求广播、应答单播。最需要强调的是 STALE 不是故障：它表示"地址旧了但照常使用"，内核在下次发包时并行验证（先进 DELAY 等 5 秒看有没有隐式确认，比如 TCP 的 ACK）；真正要警惕的是 FAILED 与长期 INCOMPLETE。

    免费 ARP 是"没人问、主动发"的 ARP，特征是发送方 IP 与目标 IP 相同。它不是查询，而是宣告"这个 IP 现在归我这个 MAC"，用于 IP 冲突检测、主备切换刷新客户端邻居表、以及顺带更新交换机 MAC 表。

    最有价值的一句是指出它是高可用切换里最容易漏的一步，而且这个 bug 在测试环境测不出来（测试机缓存本来是空的），只有"客户端已和旧主通信过一段时间"的生产环境才暴露，症状是切换后中断几十秒然后自愈。可靠做法：连发 3~5 个并在客户端侧用 ip neigh 验证，或更彻底地改用 VRRP 虚拟 MAC——切换时 MAC 根本不变。

  4. 基础TCP 为什么是三次握手？两次不行、四次多余，分别为什么？

    先给结构性答案：TCP 全双工，要同步两个方向的初始序号；每个方向都需要"发出"和"被确认"两个动作，共四个，而第二个报文把"服务端的 SYN"与"对客户端 SYN 的 ACK"合并成一个。三次是四个必要动作能压缩到的最少报文数——这同时回答了"为什么不是四次"。

    两次为什么不行——要举具体的坏后果：①旧的重复 SYN 会造成半开连接，服务端为一个早已被放弃的 SYN 建连、分配缓冲、通知应用，而客户端根本不认，这是资源泄漏加状态不一致，也是 RFC 793 的原始理由；②服务端的初始序号从未被确认，SYN-ACK 丢了它却以为连接可用并开始发数据；③攻击面更大。所以第三步的本质是让服务端拿到一份"客户端确实在线"的证据，再决定投入资源。

    加分点：服务端收到 SYN 时并非零开销——会在半连接队列留一个轻量表项，这正是 SYN 洪泛的着力点，也是 SYN cookie 的用武之地。再能区分半连接队列与全连接队列、说出后者溢出的证据是 Recv-Q 贴住上限与 ListenOverflows 增长，就相当完整了。

9.2 中级（区分熟练度）

  1. 中级IP 头里的 DSCP 和 ECN 各自干什么？DSCP 是怎么变成"队列"的？

    两者共用 IPv4 头的第 2 个字节：高 6 位 DSCP、低 2 位 ECN（IPv6 对应 Traffic Class）。第一个考点就是这个共用——把整字节当 TOS 去比较，ECN 一置位判断就失败。

    DSCP 本身不提供任何保障，它只是一个标签。差异化来自路径上每台设备读到标签后把包放进哪个队列、用什么调度；完整链条是打标 → 信任边界 → 映射 → 调度四步，每一步都可能断。打标时 DSCP 要左移 2 位，写 tos=46 是错的；EF(46) 必须配限速，否则严格优先队列会饿死其它队列。

    "我标了 EF 但对端收到是 0"绝大多数是信任边界问题，不是代码 bug——运营商接入端口默认 untrust。另一个加分点：纯二层链路没有 DSCP，eCPRI over Ethernet 根本没有 IP 头，只能用 VLAN 里的 PCP，这就是前传 QoS 与承载网 QoS 用不同字段的根本原因。

    ECN 解决另一个问题：路由器想说"我快堵了"，唯一手段却是丢包。ECN 让它改成打标记继续转发（11 是 CE，拥塞已发生），闭环还要 TCP 配合——接收方看到 CE 就在 ACK 里置 ECE，发送方像遇到丢包一样降窗并用 CWR 确认。所以 ECN 是三方协作，缺一环就退化成普通丢包，这也是它推广缓慢的原因。

  2. 中级UDP 校验和为什么 IPv4 下可选、IPv6 下必需？关掉它能提性能吗？

    区别的根源是 IPv6 把 IP 头校验和整个删掉了。IPv4 下可选（全 0 表示"未计算"），因为 IPv4 头自己有校验和、关键区域至少还有一层保护。IPv6 下必需：IPv6 头没有任何校验和，UDP 也不校验的话整条路径上没有任何机制能发现地址被翻转了一位，包会被静默投递给错误的主机。细节：算出来正好是 0 时必须发 0xFFFF，以区别于"未计算"。

    顺势讲清伪首部能显出深度：它让传输层能自己验证"这个包确实是发给我的"而不是盲目信任 IP 层。直接后果：NAT 改了 IP 就必须重算传输层校验和——这正是"NAT 必须理解传输层"的根本原因，也解释了 IPsec ESP 加密后 NAT 会失效。

    "关掉能提性能吗"的答案是不能，而这道反问才是真正的考点。校验和早由网卡硬件卸载，关掉只丢掉唯一一层端到端保护、换不来任何东西。而这层保护不多余——真实网络存在链路层 CRC 检不出来的错误（中间设备内存位翻转，发生在两段链路的 CRC 之间）。结论：IPv4 下也永远算；自己设计 UDP 协议时还应在应用层再加一层 CRC32。

  3. 中级TIME_WAIT 存在的两个理由是什么？服务器上 TIME_WAIT 太多该怎么处理？

    两个理由缺一不可，只答一个是这道题最常见的失分点。①保证第四次挥手的那个 ACK 能到——它没有人会确认，丢了的话被动方会停在 LAST_ACK 重传 FIN，此时主动方必须还"活着"才能再回一次；不等就关闭的话它会回 RST，被动方于是认为连接异常终止，而实际上数据全都传完了。②让旧连接的迷途报文消散——五元组可以复用，网络里漂着的旧数据段五元组完全匹配新连接，而 32 位序号会绕回，旧包恰好落进新窗口是可能的，结果是把陌生数据静默混进字节流，这种损坏比丢包严重得多，因为它不报错。

    时长：Linux 把 MSL 固定实现为 30 秒，所以 TIME_WAIT 是 60 秒，而且没有任何 sysctl 能改；顺便纠正一个极常见的误解——tcp_fin_timeout 管的是 FIN_WAIT_2，与它无关。

    怎么处理——先纠正问题本身：限制不是"端口用完"而是五元组用完。按优先级是改长连接 / 连接池 → 让对端做主动关闭方 → 扩五元组空间（加后端 IP 是乘法，比调 ip_local_port_range 这个加法有效得多）。

    还要点出不该用的"快解"：tcp_tw_recycle 已在 Linux 4.12 移除；SO_LINGER(0) 的代价是未发出的数据被直接丢弃；而 tcp_tw_reuse 只帮"主动连出去"的场景、对监听侧无效。

  4. 中级SO_REUSEADDR 与 SO_REUSEPORT 有什么区别？

    一句话：SO_REUSEADDR 解决"重启时 bind 不上"，SO_REUSEPORT 解决"多进程一起监听同一个端口"。名字只差三个字母，作用毫不相干。

    SO_REUSEADDR 解决的是"旧连接的 TIME_WAIT 还占着 addr:port，bind() 返回 EADDRINUSE"；它不能让两个 socket 同时 listen 同一 addr:port。SO_REUSEPORT（Linux 3.9）才能，由内核按四元组哈希决定给谁——TCP 在收到 SYN 时决定，UDP 按每个包决定。它还要求组内每一个 socket 都设这个选项且 effective UID 相同（防止别人"抢监听"你的端口）。逐项对比见 §3.8。

    对两者都成立的坑：必须在 bind() 之前设置。bind 之后再设不生效而且不报错，这是"我设了但没用"的头号成因。

    真正拉开差距的是说出 SO_REUSEPORT 的两个陷阱，都在缩容一侧：①关闭组内某个 listen socket 时，它 accept 队列里"已完成握手但还没被 accept"的连接会被丢弃，客户端看到连接建立后立刻被 RST（较新内核能迁移，但不能假定线上都有）；②哈希按四元组算不按负载算，上游只有几台代理时分布会严重不均，这就是"某个 worker CPU 100%、其它闲着"的原因。

9.3 高级（体现深度）

  1. 高级IPv6 头为什么敢去掉校验和？它还砍了什么、加了什么？

    去掉校验和有三条理由叠加，缺一条都不足以支撑这个决定：

    1. 下面有更强的保护。链路层 CRC-32 的检错能力远强于 16 位一的补码和。
    2. 上面有强制的保护。IPv6 强制要求传输层校验和，而它通过伪首部覆盖了 IP 地址，所以"地址被改坏"仍然会被发现。这是最关键的一条——如果 UDP 校验和也可选，删 IP 校验和就不可接受。
    3. 它在 IPv4 里是纯转发开销。TTL 每跳都减 1，所以每台路由器都必须重算，而换来的保护又和上下两层重复。

    还砍掉了 IHL、分片三字段、头内变长 Options（见 §3.4），加了 Flow Label（20 位）让转发设备不解析传输层就能做流级哈希；另外 Total Length 改成 Payload Length，两个字段口径不同，换算时容易差 40 字节。

    加分点是指出这套简化的工程代价：扩展头链把"找到传输层头在哪"从一次加法变成遍历链表——网卡的硬件卸载遇到扩展头就放弃，防火墙要匹配端口必须走完整条链，恶意报文可以叠很多层把设备拖进慢路径。所以遍历扩展头链必须设层数与总长度上限，否则就是一个可被远程触发的 CPU 消耗点。

  2. 高级为什么说 IP 分片有害？IPv4 与 IPv6 在这件事上有什么根本差别？

    六条理由见 §3.5，答题时至少要说出最有分量的三条：①丢包率被指数放大——单片丢包 1%、切 3 片，数据报失败率就是 1−0.99³ ≈ 2.97%；②后续分片没有传输层头，于是 ACL 匹配不了、负载均衡的哈希算不出来（可能把同一数据报的分片发到不同后端）；③硬件卸载全部失效，一出现分片就掉到软件慢路径。

    根本差别是"谁有权分片"：IPv4 下源端和路径上任何路由器都能分（DF=0 时）；IPv6 下只有源端能分，路由器一律丢包并回 ICMPv6 Type 2，配套还有所有链路 MTU 至少 1280 字节作为"永远安全"的下界。

    这个改变把责任放回了唯一有能力承担它的一方。路由器分片时对这条流一无所知；源端却知道自己在发什么、能做 PMTU 探测、能选择"改小消息"而不是"切开消息"。本质是"让错误尽早暴露给能修它的人"，代价是源端必须正确实现 PMTU 发现。

    加分点：netstat -s 里持续增长的 packet reassembles failed 是硬证据；根治方向是"不产生大包"而不是"让大包能过"——DNS 把 EDNS0 缓冲降到 1232、QUIC 把初始包限制在 1200 字节内，都是这个思路。

  3. 高级PMTUD 的原理是什么？它为什么在真实网络里经常失效，怎么补救？

    原理：发送方给所有包置上 DF 位，遇到 MTU 不够的链路时那台路由器丢包并回一个 ICMP，报文里带着下一跳 MTU，发送方据此下调估计并重发。本质是"故意撞墙，靠回音测距"。

    为什么经常失效——先给结构性原因，再举场景。结构性缺陷是：PMTUD 让一个端到端的机制去依赖第三方主动发起的反向通知，在有 anycast、ECMP、无状态防火墙和隧道翻译的现代网络里天然不可靠。最常见的场景是 deny icmp any any 一刀切；最能体现深度的是 ECMP / Anycast 让 ICMP 走错机器——多台服务器共享一个 IP，ICMP 回到哈希算出的某一台而发大包的是另一台，收到的那台根本没有这条连接。完整清单见 §3.6。

    症状叫"MTU 黑洞"，欺骗性在于"看起来一切正常"：ping、DNS、握手、SSH 全通，一旦传大数据就彻底挂住，不报错也不断连。判据：小请求秒回、大响应必挂，先怀疑 MTU 不要查应用。

    补救手段要点出各自的边界：MSS clamping 只管 TCP，对 UDP/QUIC/ESP 完全无效；PLPMTUD 不依赖 ICMP，靠"发探测包看有没有被确认"来二分，方向最正确。收尾一句：把机制从"依赖别人帮忙"改成"自己探测"才是根治方向，这正是 QUIC 一开始就内建 PMTU 探测的原因。

  4. 高级你在服务器上抓到的包，和线上真实的包为什么可能不一样？

    完整答案有三个层次，能答到第三层就说明真的排查过难题。

    ① 位置：抓包钩子不在线路上。tcpdump 挂在网络设备层——发送方向在内核把 skb 交给驱动之前、接收方向在驱动把 skb 交给协议栈之后，而网卡的大量工作恰好在这两点之外：TSO/GSO 让发送侧看到"超大包"而线上根本不存在这样的帧，GRO/LRO 让接收侧的包数、到达间隔、时序全部失真。此外网卡之后的一切只能靠端口镜像，被 XDP 更早丢弃的报文根本到不了 tcpdump。

    ② 内容与时间：抓包时间戳不是上线时刻。它是内核软件打的，与包真正上线有几微秒到几十微秒偏差而且会抖——所以抓包适合回答"发生了什么"，不适合回答"精确什么时候发生"。

    ③ 观察行为本身会改变系统。高流量下 tcpdump 自己会丢包，此时"抓包里没看到"不能作为"网络里没有"的证据；而关掉 tso/gso/gro 之后吞吐与时延特征都变了，你测的已经不是原来那个系统。

    结论：抓包不是"网络的照片"，而是"内核在某个特定位置的记账"。可以用 §8.4 那个真实场景收尾——"发出 100 个包"这个前提本身就是错的。
