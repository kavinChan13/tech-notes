核心网 / 电信云原生 20 问

按难度分三段，先自测再对照

点击每道题展开参考答案（先自测，再对照）。

1.1 基础（必答）

  1. 基础核心网到底负责什么？用一句话说清它和 RAN 的分工。

    RAN 负责"最后一公里的无线连接"，核心网负责"连接之上的一切管理与转发"。五大职责：

    • 移动性管理：UE 在哪、切换到哪、寻呼怎么发（4G 的 MME / 5G 的 AMF）。
    • 会话管理：建立/修改/释放数据通道（PDU 会话），分配 IP（4G 的 P-GW / 5G 的 SMF）。
    • 鉴权与安全：确认这张卡是真的、协商密钥（HSS / AUSF+UDM）。
    • 策略与计费：这个用户能用多少带宽、怎么算钱（PCRF / PCF）。
    • 对外出口：把用户流量转发到 Internet / IMS / 企业网（P-GW / UPF）。

    一个常见的加分补充：RAN 是"每个基站管一片区域"，核心网是"集中管理整网用户"，所以核心网的规模瓶颈是状态量（几千万 UE 上下文）而不是带宽。

  2. 基础4G EPC 有哪几个主要网元，各管什么？
    • MME（Mobility Management Entity）：控制面核心。NAS 信令终结点、移动性管理、承载管理、鉴权流程编排、寻呼。
    • S-GW（Serving Gateway）：用户面锚点，处理基站间切换时的数据转发，是 3GPP 内的移动性锚点。
    • P-GW（PDN Gateway）：对外出口。分配 UE 的 IP、执行 QoS 与计费、连接外部数据网。
    • HSS（Home Subscriber Server）：用户签约数据库 + 鉴权向量来源。
    • PCRF：策略与计费规则决策。

    关键接口：S1-MME（eNB↔MME，控制面）、S1-U（eNB↔S-GW，用户面 GTP-U）、S11（MME↔S-GW）、S5/S8（S-GW↔P-GW）、S6a（MME↔HSS，Diameter）。

  3. 基础GTP-C 与 GTP-U 分别干什么？为什么用隧道？

    GTP-U 是用户面隧道：把 UE 的原始 IP 包整包封装在 UDP/IP 里（加一个 GTP 头带 TEID 隧道标识）传输。GTP-C 是控制面信令：建立/修改/删除这些隧道（4G 里 S11/S5 用它，5G 的 N4 换成了 PFCP）。

    为什么必须用隧道——两个理由：

    • 移动性：UE 的 IP 由 P-GW/UPF 分配且在移动中保持不变。UE 从基站 A 切到基站 B，如果按原生 IP 路由，路径就变了、IP 就得换。隧道把"UE 的 IP"与"承载它的网络路径"解耦——换基站只是换隧道端点，UE 的 IP 不动，上层 TCP 连接不断。
    • 逐用户策略：TEID 让网络能按用户/按承载识别流量，从而做 QoS、计费、合法监听。裸 IP 转发做不到这种粒度。
  4. 基础5GC 的主要网元有哪些？AMF 是不是就是 MME？

    控制面：AMF（接入与移动性管理）、SMF（会话管理）、AUSF（鉴权服务）、UDM（统一数据管理）、PCF（策略控制）、NRF（网络存储/服务发现）、NSSF（切片选择）。用户面只有 UPF。

    AMF ≠ MME，不能一一对应。MME 是"移动性 + 会话管理 + 承载控制"打包在一起的胖网元；5GC 把它拆开了：移动性与 NAS 终结留给 AMF，会话管理独立成 SMF，鉴权逻辑拆到 AUSF + UDM。所以正确说法是"MME 的职责被 AMF、SMF、AUSF 三者分担"。

    大致对照：MME → AMF + SMF（+ AUSF 部分）；S-GW/P-GW 的控制面 → SMF，用户面 → UPF；HSS → UDM + UDR + AUSF；PCRF → PCF。

  5. 基础N1 / N2 / N3 / N4 / N6 / N9 各连接谁、跑什么协议？
    接口两端协议 / 内容
    N1UE ↔ AMFNAS 信令（注册、会话请求、鉴权）。逻辑接口——物理上透明穿过 gNB
    N2gNB ↔ AMFNGAP（RAN 控制面：UE 上下文、切换、QoS Flow 下发）
    N3gNB ↔ UPFGTP-U（用户数据隧道）
    N4SMF ↔ UPFPFCP（下发包检测/转发/QoS 规则）
    N6UPF ↔ 数据网普通 IP（这里才是"出口"）
    N9UPF ↔ UPFGTP-U（多 UPF 级联，如 I-UPF + PSA-UPF）

    记忆要点：N1 是逻辑的（UE 和 AMF"直接对话"，gNB 只搬运），这与 4G 里 NAS 也透传的做法一致；带数据的只有 N3/N6/N9。

  6. 基础什么是 CUPS？5GC 为什么必须做控制面与用户面分离？

    CUPS（Control and User Plane Separation）：把网元的控制逻辑与转发逻辑拆成可独立部署、独立扩容的两部分。4G 后期已在 S-GW/P-GW 上引入，5GC 从设计之初就是 SMF（控制）+ UPF（转发）。

    三个必须分离的理由：

    • 扩容维度不同：转发能力的需求随流量涨（视频流量翻倍），控制信令的需求随用户数与移动行为涨。耦合在一起时，为了扛流量必须整体扩容，白买一堆控制面能力。
    • 部署位置不同：低时延业务要求 UPF 下沉到边缘（离用户几十公里），而控制面适合集中在少数大机房（便于运维与状态一致性）。耦合就没法这么放。
    • 技术栈不同：转发面要 DPDK / SR-IOV / 硬件加速，控制面要的是 HTTP/2 微服务与数据库。分开才能各用最合适的实现。
  7. 基础NSA 与 SA 有什么区别？为什么运营商先上 NSA？

    NSA（Non-Standalone，典型是 Option 3x）：核心网仍是 EPC，gNB 作为辅站挂在 LTE eNB 之下，控制面走 LTE（4G 锚定），用户面可以从 5G 走。SA（Standalone，Option 2）：gNB 直连 5GC，控制面与用户面都是 5G。

    先上 NSA 的原因：只需新建基站、复用现有 EPC，投资小、上线快，能最快拿出"5G 速率"的市场宣传点。

    代价（也是 SA 的价值）：NSA 拿不到 5G 的能力——网络切片、URLLC 的低时延（控制面还在 4G，时延下不来）、边缘 UPF 下沉、SBA 的敏捷性，全都要 SA 才有。所以 NSA 是"更快的 4G"，SA 才是"5G"。

    对 RAN 软件的影响：NSA 要求 gNB 支持与 eNB 的双连接（EN-DC）、X2/Xn 协同、以及两套核心网接口（S1 与 NG）——软件复杂度反而比纯 SA 更高，这是 NSA 常被忽略的成本。

1.2 中级（区分熟练度）

  1. 中级说一遍 UE 注册（Registration）流程，NAS 与 N1/N2 是什么关系？

    主干流程：

    1. UE 通过 RRC 与 gNB 建立无线连接，把 Registration Request（NAS 消息）放在 RRC 消息里发出。
    2. gNB 不解析 NAS，把它装进 N2（NGAP）的 Initial UE Message 转给 AMF。
    3. AMF 向 AUSF 请求鉴权，AUSF 从 UDM 取鉴权向量，与 UE 完成挑战-应答（5G-AKA）。
    4. 鉴权通过后协商 NAS 安全上下文（加密 + 完整性保护），后续 NAS 消息受保护。
    5. AMF 从 UDM 取签约数据、（若涉及切片）向 NSSF 请求允许的 S-NSSAI 集合。
    6. AMF 回 Registration Accept，带上分配的 5G-GUTI 与允许的切片列表。

    NAS 与 N1/N2 的关系是本题的考点：NAS 是 UE 与 AMF 之间的端到端协议，对应逻辑接口 N1；但它没有自己的传输通道，而是被 RRC 与 NGAP 分段承载（UE↔gNB 段在 RRC 里，gNB↔AMF 段在 N2 里）。gNB 只是搬运工，看不到 NAS 内容（也解不开，因为 NAS 安全的密钥在 UE 与 AMF 手里）。这正是"N1 是逻辑接口"的含义。

  2. 中级PDU 会话建立时，N4/PFCP 与 N2 各做了什么？
    1. UE 发 PDU Session Establishment Request（NAS，经 N1 到 AMF）。
    2. AMF 按 S-NSSAI 与 DNN 选一个 SMF，把请求转过去。
    3. SMF 向 PCF 取策略（QoS 规则、计费规则），选一个合适的 UPF（考虑位置、负载、是否需要下沉）。
    4. N4 / PFCP：SMF 向 UPF 下发转发规则四件套——PDR（包检测规则：什么样的包属于这个会话/这条流）、FAR（转发动作）、QER（QoS 执行：限速/标记）、URR（用量上报，用于计费）。UPF 回隧道端点信息（TEID + IP）。
    5. N2：SMF 经 AMF 把 QoS Flow 的参数（QFI、5QI、GBR/MBR）+ UPF 侧隧道信息下发给 gNB。
    6. gNB 据此建立 DRB，把 QoS Flow 映射到 DRB（这是空口侧的动作），并通过 RRC 重配置告知 UE。
    7. gNB 把自己侧的隧道端点回给 SMF，SMF 再经 N4 更新 UPF —— 至此 N3 隧道两端打通，数据可通。

    一句话总结分工：N4 告诉 UPF"怎么转"，N2 告诉 gNB"怎么调度"，两边各自建好隧道端点后互相告知，隧道才算通。注意 SMF 自己不碰任何用户数据——它只是下规则的。

  3. 中级SBA 服务化架构和互联网微服务有什么相同、有什么不同？

    相同：都是细粒度服务 + 服务注册发现（NRF ≈ 注册中心）+ HTTP/2 + JSON 的 RESTful 风格接口（SBI）+ 松耦合、独立升级。

    不同（这才是答题重点）：

    • 接口是强标准化的：3GPP 把每个服务的 API（Nsmf、Namf…）定死，多厂商必须互通。互联网微服务的接口是团队内部约定，想改就改。
    • 可用性要求高一到两个数量级：电信级 5 个 9（年停机 < 5 分钟），而且是"注册用户不能掉线"级别，不是"重试一下就好"。
    • 状态外置是硬要求：网元必须能做到"任意实例接管任意用户"，所以 UE 上下文要放 UDSF / 外部存储（见后面 UDSF 那题）。互联网服务通常可以接受"会话粘性 + 丢了重登录"。
    • 用户面完全不走这一套：SBA 只覆盖控制面。UPF 的转发面是 DPDK / 硬件加速，与 HTTP/2 毫无关系。把"5GC 是微服务"理解成"整个核心网都是 HTTP"是常见错误。
  4. 中级5QI → QoS Flow → DRB 的映射链是怎样的？谁做哪一步？

    四段链条，每段的执行者不同：

    1. SDF → QoS Flow：PCF 给出策略，SMF 把业务数据流（按五元组等特征识别）绑定到一个 QoS Flow，标上 QFI 与对应的 5QI。UPF 按 PDR 识别包并打上 QFI。
    2. QoS Flow 参数下发：经 N2 送到 gNB（QFI、5QI、GBR/MBR、优先级）。
    3. QoS Flow → DRB：gNB 决定。可以多个 QoS Flow 映射到同一个 DRB（省 DRB 资源），也可以一对一（隔离更好）。这一步是 RAN 的自主权，标准不规定映射策略——这是本题最容易漏的考点。
    4. DRB → 空口调度：MAC 调度器按 DRB 的优先级、时延预算、GBR 需求分配 PRB。

    QoS Flow 是 5G QoS 的最细粒度（4G 是 EPS Bearer），一个 PDU 会话内最多 64 个 QoS Flow。补充加分点：端到端还要把 5QI 对齐到传输网的 DSCP / VLAN PCP，否则空口调度对了、承载网上照样被排到后面（见 网络机制）。

  5. 中级GTP-U、eCPRI、Open Fronthaul 三者是什么关系？

    它们在完全不同的层次上，不是可替换的选项。这道题是通信岗高频送分/送命题。

    GTP-UeCPRIOpen Fronthaul
    位置gNB ↔ UPF（N3，回传）O-DU ↔ O-RU（前传）同前传，是规范集合
    载荷UE 的完整 IP 包IQ 采样数据（基带信号）含 eCPRI + C/U/S/M 四平面定义
    时延要求毫秒级百微秒级硬时限同 eCPRI
    层次关系Open Fronthaul 使用 eCPRI 作为传输封装；GTP-U 与两者毫无关系

    一句话：GTP-U 搬的是"用户的数据包"，eCPRI 搬的是"天线的信号采样"。前者在基站之上（面向核心网），后者在基站之内（O-DU 与 O-RU 之间）。另外 Open Fronthaul 是 O-RAN 联盟的规范（规定了 eCPRI 之上的 C/U/S/M 平面细节与 7-2x 拆分），eCPRI 只是其中的传输层——所以"用 eCPRI 就等于 Open Fronthaul"也是错的。

  6. 中级网络切片是怎么落地的？S-NSSAI 与 NSSF 各起什么作用？

    S-NSSAI = SST（Slice/Service Type，标准值如 1=eMBB、2=URLLC、3=MIoT）+ 可选的 SD（Slice Differentiator，区分同类型的不同租户）。它是切片的标识。

    NSSF 在注册与会话建立时决定"这个 UE 允许用哪些切片、这次请求落到哪个切片实例"，并帮 AMF 找到该切片对应的 SMF/UPF 集合。

    落地要三段都做，缺一段就是"假切片"：

    • 核心网：按切片部署独立的 SMF/UPF 实例（或共享但逻辑隔离）。
    • RAN：两种做法——PRB 预留（硬隔离，保证但浪费）或调度权重（软隔离，高效但过载时无保证）。这是切片最难也最容易被跳过的一段。
    • 传输网：FlexE / VPN / 软切片，保证承载段不被别的切片挤占。

    取舍：切片数量爆炸的运维成本是真实的——每个切片都有独立的配置、监控、SLA 与故障定位路径。业界的普遍做法是少量粗粒度切片（个位数）而不是"每个客户一个切片"。

1.3 高级（体现深度）

  1. 高级URLLC 承诺的"1 ms"具体由谁分摊？这个预算现实吗？

    先澄清一个常见误解：3GPP 的 1 ms 指的是"用户面时延"，而且通常是单向、空口段的目标，不是"应用到服务器的往返"。把它当端到端 RTT 是答错的起点。

    一个典型的预算拆分（数量级，非标准值）：

    • 空口：调度 + 传输 + HARQ 一次重传 ≈ 几百微秒。这需要短 TTI（mini-slot）、预调度（免调度请求）、更保守的编码（牺牲频谱效率换一次成功）。
    • 前传：O-RU↔O-DU 单向 ≈ 几十微秒（受光纤长度约束，每公里约 5 µs，这是物理下限——所以 URLLC 站点的 O-DU 不能放太远）。
    • 传输 + UPF：几十到几百微秒，取决于 UPF 离得多远。

    结论与工程含义：1 ms 只能在"UPF 下沉到边缘 + 应用也在边缘（MEC）"的前提下成立。如果流量还要绕回中心机房，光是往返传播时延就吃掉全部预算。所以 URLLC 不是一个"开关"，而是一整套部署要求——这也是为什么它落地远慢于 eMBB。反过来说，面试里能主动指出"这个指标依赖 UPF 下沉"，就说明理解了 CUPS 的真正价值。

  2. 高级ULCL / Branching Point 是什么？为什么低时延业务要把 UPF 下沉到边缘？

    ULCL（Uplink Classifier）：在一条 PDU 会话里，UPF 按目的地址/域名分流——去本地 MEC 应用的流量就地转出（走本地 N6），去公网的流量继续经 N9 送到中心的 PSA-UPF。Branching Point 是它在 IPv6 多归属场景下的对应机制。

    关键点是"同一条会话、同一个 UE IP"：UE 完全不知道有分流发生，应用无需改动，也不用建第二条会话。这是 ULCL 相对"给 MEC 单独建一条会话"的核心优势。

    为什么必须下沉：传播时延是物理常数（光纤约 5 µs/km）。UPF 在 300 km 外的中心机房，仅单向传播就 1.5 ms，往返 3 ms——任何 1 ms 级的承诺都不可能成立。下沉是唯一手段，不是优化选项。

    与 Near-RT RIC 的边界（常见追问）：RIC 管的是无线资源的优化决策（调度策略、切换参数、频谱效率），控制回路在 10 ms–1 s 量级，通过 E2 影响 RAN；UPF 下沉管的是数据走哪条路，属于转发面部署。两者都为低时延服务，但一个调"空口怎么用"，一个调"包往哪走"，互不替代。见 O-RAN 架构。

  3. 高级VNF 与 CNF 的本质区别是什么？CNF 和普通微服务又差在哪？

    VNF vs CNF：VNF 是"把网元装进虚拟机"——独占内核、隔离性强、启动分钟级、镜像几个 G，管理靠 ETSI MANO（NFVO/VNFM/VIM）。CNF 是"把网元拆成容器"——共享宿主内核、启动秒级、镜像百兆级、管理靠 K8s。核心取舍是「隔离性与确定性」换「解耦度与迭代速度」。

    CNF vs 普通微服务——差在四处，这才是本题的深度所在：

    • 网络：普通微服务一个 eth0 + kube-proxy 就够；CNF 要 Multus 多网卡（信令面/媒体面/管理面物理隔离）、SR-IOV / DPDK 用户态直通（绕过内核协议栈），还要 SCTP（K8s Service 对 SCTP 支持长期不完整）。
    • 性能确定性：要 HugePages、CPU Manager static 策略 + isolcpus 独占核、NUMA Topology Manager 对齐 CPU/内存/网卡，甚至 PREEMPT_RT。普通微服务只要 CPU limit。
    • 状态：会话状态不能随 Pod 一起消失，要靠 UDSF / 外部存储（见下题）。
    • 升级：滚动升级会杀长连接（NETCONF 会话、SCTP 偶联），需要连接排空与优雅退出，不能靠"反正客户端会重试"。

    一句话回答"到底差在哪"：普通微服务假设网络是抽象的、时延是尽力而为的、连接是短的、状态可以丢；CNF 这四条假设全都不成立。

  4. 高级为什么电信容器必须要 SR-IOV / HugePages / CPU pinning？各解决什么问题？
    • SR-IOV（+ DPDK/VPP）：把物理网卡虚拟成多个 VF 直通给 Pod，绕过内核协议栈与虚拟交换。解决的是"每包固定开销"——内核路径下 Mpps 级转发根本达不到，而且 softirq 带来的抖动无法控制。代价是失去 K8s 的网络抽象（Service、NetworkPolicy 都不管用了），IP 管理要自己做。
    • HugePages（2 MB / 1 GB）：减少 TLB miss 与页表层级。转发面的报文缓冲池动辄几个 G，4 KB 页会让 TLB 完全失效，随机访问缓冲池时每次都是页表走查。同时避免了缺页中断这个抖动源。
    • CPU pinning（CPU Manager static + isolcpus + NUMA Topology Manager）：让轮询线程独占物理核，不被 CFS 抢占、不被其他 Pod 干扰。DPDK 的 PMD 是忙轮询的——被抢占一次就是一次可观的时延尖峰。NUMA 对齐则保证 CPU、内存、网卡在同一个 socket，否则跨 NUMA 访问的额外 100–200 ns 会直接吃掉预算。

    共同点：三者都是为了把"尽力而为"变成"确定性"。代价也是共同的——Pod 变得与硬件强耦合，失去了云原生的可移植性与弹性调度能力。这正是"电信云原生"这个词内在矛盾的地方：它要的不是云的弹性，而是云的运维模型 + 裸机的性能。

  5. 高级5GC 网元"无状态化"是什么意思？UDSF 解决什么问题？AMF 重启后 UE 上下文怎么保住？

    "无状态化"不是"没有状态"，而是"状态不驻留在特定实例的内存里"。UE 上下文、会话上下文被写到外部的 UDSF（Unstructured Data Storage Function）或等效的分布式存储，实例本身只做处理。

    解决的问题：① 任意实例可以处理任意 UE 的请求 → 负载均衡自由、扩缩容无需迁移会话；② 实例故障或升级重启，UE 不掉线（新实例从 UDSF 读回上下文继续服务）；③ 这才是"5 个 9"与"云原生弹性"能同时成立的前提。

    AMF 重启的具体过程：重启后的 AMF（或接管的另一个 AMF 实例）从 UDSF 取回 UE 上下文（安全上下文、注册状态、已建立的 PDU 会话列表）；UE 侧无感知，因为它的 5G-GUTI 与 NAS 安全上下文仍然有效。若上下文取不回来，UE 才需要重新注册。

    代价与边界（加分点）：每次处理多一次外部访问（几百微秒到毫秒），UDSF 本身成了新的关键路径与瓶颈，且它自己必须做到极高可用（否则单点风险从网元转移到了存储）。所以这条路只有控制面走得通，用户面绝对不能——UPF 每个包查一次远端表是不可想象的，因此 UPF 的转发规则必须由 SMF 经 N4/PFCP 预先下发并驻留本地内存。
    "控制面状态外置、用户面状态本地化"这条 5GC 设计原则，是被时延预算逼出来的，不是架构偏好。

  6. 高级O-DU / O-CU 上 O-Cloud 有哪三个硬难点？为什么比 5GC 上云难得多？

    5GC 控制面上云相对容易（毫秒级时延预算、状态可外置）。O-DU 难得多，因为它有百微秒级的硬时限：

    • ① 硬实时调度：O-DU 的 slot 处理有绝对截止时间（错过就掉帧）。容器共享内核，CFS 调度、其他 Pod 的干扰、内核的 softirq 都可能造成超时。需要 CPU 独占 + isolcpus + PREEMPT_RT + 关闭一切可能抢占的东西——而这些配置一层层削掉了容器化的意义。
    • ② PTP 时钟穿透容器：O-DU 需要纳秒级同步（见 PTP/SyncE）。时钟设备（PHC）是宿主级资源，容器里的进程要访问 /dev/ptp* 并使用硬件时间戳，权限、设备直通、以及"多个 Pod 共享一个时钟源"的一致性都要专门设计。K8s 原生没有"时钟"这个资源概念。
    • ③ 加速卡直通：FEC / 前向纠错卸载卡、L1 加速器要通过 Device Plugin 直通给 Pod，还要与 CPU/内存做 NUMA 对齐。设备的固件版本、驱动与容器镜像的匹配是持续的运维负担。

    O2 与 SMO 的关系：O2 是 SMO 与 O-Cloud 之间的接口，负责基础设施管理（IMS：节点、资源池）与部署管理（DMS：部署/升级 O-DU 等网络功能）。它与 O1 的分工要说清——O2 管"云平台和部署"，O1 管"网络功能自身的配置与性能/告警"。见 O-RAN 接口。

  7. 高级核心网软件的可用性"5 个 9"从哪里来？信令风暴是怎么产生的、怎么防？

    5 个 9（年停机 < 5.26 分钟）不来自单点可靠，而来自四层叠加：

    • 冗余：N+M 实例、跨机房/跨 AZ 部署，单实例故障不影响服务。
    • 状态外置：故障实例的用户能被别的实例接管（见 UDSF 那题）——这是"故障不等于掉线"的关键。
    • 快速检测与倒换：健康检查 + 服务发现摘除，秒级完成。⚠️ 探针配置不当反而是故障放大器：过于敏感会在负载高峰误杀正在正常处理信令的实例。
    • 过载保护：这一层最容易被忽略，但它决定了故障是"局部"还是"全网"。

    信令风暴的产生机制：某个事件（大面积断电恢复、传输中断恢复、一个 AMF 实例故障）导致海量 UE 同时重新注册。瞬时信令量可能是稳态的几十倍。若无保护：核心网过载 → 响应变慢 → UE 超时 → 重试放大 → 负载再翻倍 → 雪崩。这是正反馈，一旦进入就很难自行恢复——即使原始故障已修复，重试洪流仍会持续压死系统。

    防御手段（分层）：

    • 终端侧退避：NAS 层的 back-off timer（网络在拒绝消息里告诉 UE 等多久再来）+ 随机抖动。这是最有效的一层，因为它从源头削峰。
    • 接入准入限速：核心网侧限制每秒接受的注册数，超出的明确拒绝并带退避时长——宁可让一部分 UE 晚几十秒接入，也不要全部超时后一起重试。
    • RAN 侧的接入控制：ACB（Access Class Barring）在无线侧就挡住一部分尝试，让信令根本不进核心网。
    • 有界队列 + 优先级：紧急呼叫与已有会话的维持信令优先于新注册。

    核心洞察：过载时的目标不是"全都处理完"，而是"以可预测的方式劣化"——保住一部分完整服务，明确拒绝其余并引导它们错峰重来。这与 高并发那篇讲的背压原则是同一件事，只是在 3GPP 里被标准化成了协议字段。

02

三组高频易混

答错这三组，前面答得再好也会被扣分

① GTP-U ≠ eCPRI。GTP-U 在基站与核心网之间（N3/回传），载荷是用户的 IP 包，毫秒级时延要求。eCPRI 在基站内部（O-DU↔O-RU/前传），载荷是IQ 采样，百微秒级硬时限。两者层次完全不同，不存在"用哪个"的选择。而 Open Fronthaul 是规范集合，它使用 eCPRI 作为传输——"eCPRI = Open Fronthaul"同样是错的。
② 核心网 OAM ≠ O-RAN O1。核心网网元的管理走各厂商/3GPP 的 OAM 体系（越来越多用 SBI + 云原生的监控栈）。O1 是 O-RAN 定义的、SMO 管理 RAN 网络功能（O-CU/O-DU/O-RU）的接口，基于 NETCONF/YANG。两者管的对象不同、协议栈不同、由不同标准组织定义。顺带：O2 管的是 O-Cloud 这个"云平台"本身与部署，也不要和 O1 混。
③ SMF 不是转发面，UPF 才是。SMF 只做会话管理与规则决策，通过 N4/PFCP 把 PDR/FAR/QER/URR 下发给 UPF；它从不接触任何一个用户数据包。同理 AMF 也不碰用户数据。5GC 里唯一的用户面网元就是 UPF——记住"控制面下规则、用户面执行规则"这条分界，很多题都能推出来。
答核心网题的通用框架：先说层次，再说职责，最后说取舍。被问到任何一个网元或接口，先定位它在"UE → RAN → 核心网控制面/用户面 → 数据网"这条链上的哪一段（这一步就避开了上面三组易混），再说它负责什么，最后给一个工程取舍（为什么这么设计、代价是什么）。能主动给出取舍的回答，和只能背出名词的回答，区分度极大。
