通信服务的高并发：连接模型、线程模型与横向扩展

"支持高并发"这句需求本身是个陷阱——海量连接、高报文率、低尾延迟是三个不同的问题，优化手段还常常互相打架。本篇先把三者拆开定位，再逐层给连接模型、线程模型、尾延迟、背压、横向扩展的取舍，最后用一个可拖动的实验台看吞吐-时延曲线为什么会有拐点。

Module 09 阅读 ~25 min 含交互实验台
01

"高并发"其实是三个问题

先定位，再选手段——不然一定会优化错方向

边界。ring buffer、zero-copy、无锁队列的实现细节见本模块的 高性能通信编程（那篇讲数据结构，本篇讲模型）；memory_order 的原理见 C++ 内存模型 与 并发深入；epoll / io_uring 的内核机制见 异步网络编程；Reactor / Active Object 等模式本体见 通信软件设计模式。

关键在于第一列与第二列之间的冲突。把三行的"主要手段"横着看就会发现：批处理是高报文率的头号手段，也是低尾延迟的头号敌人（攒批就是主动引入等待）；缩小每连接内存（海量连接）意味着收发缓冲要小，而小缓冲在高报文率下会频繁触发窗口收缩；独占核（低尾延迟）把核锁死，正好和海量连接想要的"高密度部署"相反。
所以"这个服务要高并发"是一句没有信息量的需求。必须先问清是三行里的哪一行，因为按另外两行优化不仅无效，还会主动伤害目标指标。
🏥 类比：三个不同的医院。海量连接像社区门诊挂号系统——一万个人都"挂着号"，但同时看病的只有几十个，关键是每个号占的档案柜要小。高报文率像流水线体检——每天必须过一万人，关键是每人的固定环节能不能批量做（十个人一起排队抽血，比一个个叫进来快得多）。低尾延迟像急诊室——不在乎一天看多少人，只在乎最差的那个病人等了多久，所以宁可空着医生也不许他去帮忙做体检。
让急诊室去做批量体检，或者让体检中心承诺"最差 5 分钟"，都是把手段用错了地方。
02

连接模型演进

从"每连接一线程"到 io_uring，每一步解决了什么

惊群（thundering herd）：多个线程阻塞在同一个事件源上，一个事件到达却把所有线程都唤醒，最终只有一个抢到活干，其余白白唤醒又睡回去。表现为 CPU 上升但吞吐不涨。accept 的惊群早已被内核修掉（只唤醒一个），但多个线程 epoll 同一个 listen fd 仍会惊群——除非用 EPOLLEXCLUSIVE（内核 4.5+）或干脆用 SO_REUSEPORT 让每个线程有自己的 listen fd。
选型建议。管理面 / 信令面（连接数千级、逻辑复杂）→ 主从 Reactor，成熟、易调试、连接分配可控。数据面 / 网关（连接十万级、逻辑简单）→ SO_REUSEPORT + per-core，彻底消除跨核，还能做到"逐个 worker 灰度重启"。io_uring 目前更适合存储与文件型 IO；网络侧要用它，必须先想清楚在飞操作数的上界与背压怎么做，否则过载时的失效模式非常难看（内存一路涨到 OOM，而不是优雅地丢包）。
C10M 的真正瓶颈几乎从不是 epoll，而是每连接内存。粗算一下：内核侧一个 TCP 连接（sock + 收发缓冲最小值）≈ 4–10 KB，应用侧一个会话对象（状态机 + 定时器 + 统计 + 收发缓冲）随手就是 4–8 KB。一千万连接 × 10 KB = 100 GB。所以做海量连接的第一件事不是换 IO 模型，是逐字节审计会话对象：收发缓冲改成按需分配（空闲连接不占）、定时器改成时间轮里的一个槽位引用而不是独立对象、统计计数按需惰性创建、能用 uint16_t 就别用 int。这件事的收益比任何 IO 模型切换都大一个量级。
03

线程模型与分片

shared-nothing vs 共享队列，以及"同会话有序性"这条硬约束

per-core shared-nothing（Seastar / DPDK 风格）：每个核一个线程、一份数据、一个事件循环，核之间不共享任何可变状态，需要协作时发消息（无锁 SPSC 环）。锁完全消失，缓存亲和最好。代价是负载均衡只能靠"分片键选得好"，某一片热了没法让别的核来帮忙。
维度per-core shared-nothing共享队列 + 线程池
同步开销零锁（跨核才发消息）每次取任务一次竞争；高核数下队列本身成瓶颈
缓存亲和极好：会话数据始终在同一个核的 L1/L2差：同一会话可能被不同核处理，每次都是跨核搬运
负载均衡差：分片不均就有核闲着看别的核忙死好：天然工作窃取，谁空谁干
尾延迟好（无锁等待、无排队不确定性）差（队列排队 + 锁等待都进入 P99.9）
同会话有序性免费：同一分片必然串行要额外机制（见下）
编程难度高：所有跨核协作都要显式异步化低：写同步代码即可
适用UPF / 前传 / 网关：分片键均匀、处理时长均匀信令面 / 管理面：请求成本差异大、连接数不多

3.1 同会话有序性：一条容易被忽略的硬约束

通信协议几乎都要求同一会话内的消息按序处理。举个立刻出事的例子：一个 UE 的 RRC Setup 和紧随其后的 RRC Release 被分给两个 worker 并行处理，Release 先跑完，Setup 后跑完——结果一个已经释放的 UE 又变成 CONNECTED，成了永远清不掉的"僵尸会话"，占着资源直到设备重启。

❌ 全局队列 + 谁空谁抢
// 吞吐最优，但同会话消息会被并行处理
void worker_loop() {
  Msg m;
  while (global_q.pop(m))
    dispatch(m);          // ⚠️ 同一 UE 的两条消息可能同时在这里
}
// 补救办法通常是给会话加锁：
//   std::lock_guard lk(session_of(m)->mu);
// 但这只保证互斥，不保证顺序 —— 谁先抢到锁
// 谁先执行，乱序问题依然存在。
✅ 按会话哈希固定分片
// 同一会话永远落在同一个 worker → 天然有序、天然互斥
inline unsigned shard_of(SessionId id) {
  return hash_mix(id) & (kShards - 1);   // kShards 取 2 的幂
}

void on_packet(Packet p) {
  auto id = parse_session_id(p);
  shards_[shard_of(id)].mbox.push(std::move(p));   // 只入队
}

void worker_loop(unsigned s) {
  Packet p;
  while (shards_[s].mbox.pop(p))
    dispatch(p);          // 无锁：这一片的会话只有我碰
}
// 顺带得到：无锁、缓存热、可按片统计与限流
分片的三个实践要点。① 分片数取核数的整数倍且是 2 的幂（用位与代替取模），通常 = 核数或 2× 核数；多于核数便于将来迁移分片而不改哈希。② 哈希前先做 mix：会话 ID 常常是自增或带结构的（同一小区的 UE ID 连号），直接取低位会严重倾斜。③ 必须能观测每片水位：分片模型的典型故障是"总体 CPU 才 40% 但服务已经在丢包"——因为某一片满了。没有 per-shard 的队列深度指标，这个故障根本查不出来。
跨核通信的真实代价，值得记住量级。同核内函数调用 ~1 ns；同 L3 的两个核之间传一条 cache line ≈ 40–80 ns；跨 NUMA 节点 ≈ 100–200 ns；一次线程唤醒（futex + 调度）≈ 1–5 µs。
换算一下就知道分片的价值：一个包如果要跨 3 次线程边界，光唤醒就是几微秒，而 100 Gbps 下一个 64 字节小包的时间预算只有 约 6.7 ns。这就是为什么高报文率场景必须 shared-nothing——不是为了优雅，是因为跨核这一下就已经超预算几百倍了。相关的 NUMA 与网卡队列绑定见 NUMA 与内存进阶。
04

尾延迟工程

P99.9 不是"平均值大一点"，是另一个物理量

平均时延由正常路径决定，尾延迟由抖动源决定——两者的优化手段几乎没有交集。把尾延迟压下来的工作，本质上是逐个消灭抖动源：

调度抖动被 CFS 抢占、被别的进程挤走、被内核线程插队。手段：isolcpus + nohz_full 隔核，线程绑核（sched_setaffinity），必要时上 PREEMPT_RT。只绑核不隔核收益有限——别的任务照样能被调度到这个核上。
分配抖动malloc 大多数时候几十纳秒，但触发 arena 扩展或 mmap 时可能几十微秒。手段：热路径零分配——预分配对象池、per-connection 的 monotonic_buffer_resource（见 现代 C++ 在通信中的实战）。
缺页抖动第一次访问触发 page fault，几微秒；换页更糟。手段：启动时预触碰（touch）全部内存 + mlockall()，用 HugePages 把 TLB miss 与页表层级一起降下来。
中断抖动网卡中断、时钟中断打在业务核上。手段：irqbalance 关掉后手工设置 smp_affinity，把网卡队列中断绑到与处理该队列的线程同一个核（或至少同一 NUMA 节点）。
锁等待抖动平时 100 ns，偶尔一次持锁者被抢占就是几十微秒（锁持有者抢占问题）。手段：热路径消除共享（分片）；不得不用锁时用自适应自旋而不是直接睡。
攒批抖动低负载时批攒不满就要等超时。手段：自适应批（N 个或 T 微秒先到先处理），T 直接就是轻载时延的下界，必须实测调。
定时器抖动成千上万个定时器同一时刻到期（同步化的心跳/重传）造成周期性尖峰。手段：定时器加随机抖动打散，时间轮而非最小堆（O(1) 摊还，无堆调整尖峰）。
尾延迟工程的方法论，一句话：不要优化平均值，要去找并消灭最差情况的成因。做法是记录每个请求的时延直方图（HdrHistogram 式的对数分桶，代价只有几纳秒），然后专门去看最慢的那 0.1%——它们通常高度聚集在某个特征上：都在整秒时刻（定时器同步）、都在同一个核（某个核被别的东西干扰）、都是同一类请求（某条路径上有分配或锁）、或者都在某次 GC/rehash 之后（unordered_map 扩容是个经典尖峰源）。找到聚集特征，根因基本就出来了。通用方法论见 低延迟系统指南 与 性能优化方法论。
05

背压与过载保护

过载时的目标不是"处理完"，是"以可预测的方式劣化"

背压（backpressure）：下游处理不过来时，把"慢"这个信号逆流传回上游，让上游主动减速或拒绝，而不是让请求无限堆积。没有背压的系统在过载时不是"变慢"，是雪崩：队列无界增长 → 内存耗尽 / 时延涨到全部超时 → 上游全部重试 → 负载再翻倍。
第一原则：所有队列必须有界。一个无界队列就足以让整个系统失去过载时的可预测性。有界队列满了之后必须有明确策略，而不是阻塞了事：拒绝（返回明确的忙错误，让上游退避）、丢弃（数据面常用，丢最新的还是最旧的要按业务定）、降级（跳过可选处理，如详细统计、非必要日志）。
⚠️ 阻塞入队是最差的选择：它把背压变成了"上游线程被卡住"，如果上游是 IO 线程，那就等于整条链路一起停摆，还顺带触发心跳丢失和不必要的倒换。
❌ 丢最旧的：过载时全是无效工作
// 队列满 → 丢队头（最旧的）
// 直觉上"先来先服务"很公平，但过载时：
// 队列深度 = 10000，处理速率 = 1 万/s
// → 队头那条已经等了 1 秒
// → 对端早就超时重传了
// 结果：CPU 100% 忙着处理没人要的旧请求，
// 而新到的、还有意义的请求排在最后。
// 这就是 goodput（有效吞吐）归零，
// 但监控上 CPU 和吞吐都很"健康"。
✅ 带截止时间 + LIFO 降级
struct Req { steady_clock::time_point deadline; ... };

void handle(Req& r) {
  if (steady_clock::now() > r.deadline) {   // 进门先看还有没有意义
    ++stats_.dropped_expired;              // 打点，别静默
    return;                                // 已过期，不做无效工作
  }
  process(r);
}

// 进一步：过载时切到 LIFO（后进先出）
// 反直觉但有效 —— 保证"一部分请求快速成功"
// 优于"所有请求一起慢到全部超时"。
// 前提：调用方有超时与重试，被牺牲的那部分
// 会被明确拒绝而不是无限等待。
队头阻塞（head-of-line blocking）在通信软件里有三个层次，容易只治了一层。① TCP 层：一个丢包会挡住它后面所有已到达的数据（这也是 HTTP/3 换 QUIC 的原因）。② 应用队列层：一个慢请求挡住它后面所有请求——分片能缓解（只挡住同片），但同片内依然存在。③ 慢连接层：某个对端接收慢，导致你的发送缓冲堆积、内存被它吃掉；必须给每连接的待发数据设上限，超了就断开这个连接，而不是让它拖垮整个进程。第三点最常被漏掉——一个恶意或故障的慢客户端就足以把网关打爆。
限流、熔断、舱壁隔离的完整套路见 弹性模式；通信侧的可靠性与 HA 见 可靠性与高可用。
06

协程做会话管理

把回调地狱写回顺序代码，代价是什么

通信会话的逻辑天然是"多步等待"：发请求 → 等回应（可能超时）→ 再发 → 再等 → 收尾。用回调写出来就是 设计模式那篇说的跨层回调地狱：状态被拆散在若干个回调函数里，"这一步之后该干什么"要靠状态字段推断。协程能把它写回顺序形式：

❌ 回调：状态散落在四处
void start_setup(Ses* s) {
  send_req(s, kSetup);
  s->stage = kWaitSetupAck;      // 手工记录"我在哪一步"
  arm_timer(s, 200ms, on_timeout);
}
void on_setup_ack(Ses* s, Msg m) {
  if (s->stage != kWaitSetupAck) return;   // 每个回调都要防错序
  cancel_timer(s);
  send_req(s, kConfig);
  s->stage = kWaitConfigAck;
  arm_timer(s, 200ms, on_timeout);
}
void on_config_ack(Ses* s, Msg m) { ... }  // 还有三个
void on_timeout(Ses* s) {
  switch (s->stage) { ... }                 // 每一步的超时处理都在这儿
}
// 流程被切成 5 个函数，读代码看不出先后；
// 错误处理与资源释放要在每个回调里重复。
✅ 协程：顺序、异常安全
Task<void> setup_session(Ses& s) {
  co_await send(s, kSetup);
  auto ack = co_await recv(s, kSetupAck, 200ms);   // 超时抛/返错
  if (!ack) co_return fail(s, "setup timeout");

  co_await send(s, kConfig);
  auto cfg = co_await recv(s, kConfigAck, 200ms);
  if (!cfg) co_return fail(s, "config timeout");

  s.state = kActive;
  // 流程一眼看到底；RAII 保证任何路径都清理干净；
  // 局部变量替代手工 stage 字段
}
协程不是免费的，三笔账要算清。① 内存：每个协程帧要保存局部变量与挂起点。C++ 无栈协程的帧通常几十到几百字节（比线程 8 KB 栈小得多），但十万会话 × 200 B = 20 MB，且默认在堆上分配——热路径要考虑自定义 operator new 或用池。② 调度开销：一次恢复约几十纳秒，比线程唤醒（µs 级）便宜两个数量级，但比直接函数调用贵；每包都跑一次协程恢复的转发面要慎用。③ 可观测性变差：崩溃时的调用栈只到调度器，看不出"这个协程在哪一步挂起、谁恢复了它"——必须自己在协程帧里带上会话 ID 与步骤标记，否则线上排障会非常痛苦。
协程的语言机制、帧布局与自定义分配器见 C++ 协程深入。
务实的分工：协程用在"多步流程"，不用在"每包处理"。会话建立、配置事务、O-RU 启动序列、软件升级流程——这些步骤多、超时多、错误路径复杂，协程收益巨大。而数据面的"收包→查表→改头→发包"是单步无等待的，用协程只是白付一次恢复开销。同一个进程里两种风格并存是正常的，判断标准就是"这段逻辑里有没有等待点"。
07

扩展到多机

单机调到头之后，状态往哪放

单机优化的终点是"加核不再涨吞吐"或"内存到顶"。往多机走时，通信服务遇到的核心难题只有一个：会话状态是有的，请求必须找到持有它的那台机器。三种做法：

做法怎么工作优点代价典型用处
会话粘性
(sticky)		负载均衡器按会话键把同一会话固定路由到同一实例实现简单；状态留在本地内存，访问最快扩缩容 / 实例故障时该实例的会话全丢；负载可能长期不均短会话、可重建的会话
一致性哈希会话键哈希到环上，顺时针找到负责节点；增删节点只影响相邻区间扩缩容时只迁移 1/N 的会话而非全部重排仍会迁移；需要虚拟节点解决倾斜；节点视图要一致（否则路由分裂）网关、缓存层、分布式会话表
状态外置实例完全无状态，会话数据放外部存储（Redis / UDSF）任意实例可处理任意请求；扩缩容与重启零影响每次处理多一次网络往返（几百 µs ~ ms）；存储成了新的单点与瓶颈5GC 控制面网元（见 电信云原生的 UDSF）
3GPP 在 5GC 上选的是"状态外置"，而这个选择的代价正好说明了取舍的本质。AMF 把 UE 上下文写到 UDSF，换来的是"任意 AMF 实例可以接管任意 UE、实例重启不掉会话"——这是电信级可用性和云原生弹性的前提。代价是每次信令处理多一次外部访问，所以控制面能这么做，用户面绝对不能：UPF 每个包都查一次远端表是不可想象的，所以 UPF 的转发规则必须由 SMF 通过 N4/PFCP 预先下发并驻留本地。
这就是"控制面状态外置、用户面状态本地化"这条 5GC 设计原则的由来——它不是架构偏好，是被时延预算逼出来的。
横向扩展的隐藏成本：连接建立速率往往先撞墙。容量规划时大家都算"能撑多少并发连接"，却忘了算"每秒能建多少新连接"。TLS 握手是 CPU 密集的（一次 ECDHE + 证书验签在几百微秒到毫秒量级），一个基站群同时上电、或者一次网络闪断后所有终端同时重连，瞬时建连速率可能是稳态的几十倍——这就是信令风暴。
三道防线：客户端侧的重连退避加随机抖动（最有效，见 Acceptor-Connector）、服务端侧的建连准入限速（宁可让一部分排队，也不要全部握手失败后一起重试）、以及 TLS 会话复用（session ticket 把重连的握手成本降一个数量级）。

perf / bpftrace观测找瓶颈在哪：cache miss、锁、syscall、软中断压测和观测要同时做，否则只知道"慢"不知道"哪慢"
协调遗漏（coordinated omission）：让无数压测报告失真的一个坑。闭环压测器（发一个等一个回，如默认的 wrk）在服务端变慢时会自动减速——它在等回应，发不出下一个请求。结果服务端卡了 1 秒这件事，只会被记为"1 个请求耗时 1 秒"，而不是"这 1 秒里本该发出的 1 万个请求都被延迟了"。于是报告出来 P99 很漂亮，上线一压就崩。
正确做法：用固定发送速率的压测器（wrk2、TRex 的 CPS 模式），并按预期发送时刻而不是实际发送时刻计算时延。这一条不注意，前面所有尾延迟工作的测量都是假的。

8.1 怎么读那条曲线

标准做法是：固定并发/速率跑一段，记录吞吐与时延分布，逐档加压，画出 (吞吐, P50/P99/P99.9) 曲线。这条曲线一定是三段，每一段告诉你不同的事：

① 线性段加压吞吐同比涨，时延基本平坦。系统还有余量，队列基本是空的，时延 ≈ 纯处理时间。
② 拐点吞吐开始涨不动，时延开始明显上翘。这里就是容量——某个资源（核、锁、带宽）开始饱和，队列出现稳定积压。容量规划应该取拐点的 50%~70% 作为额定负载，留出突发余量。
③ 饱和/崩溃段吞吐持平甚至下降，时延指数上升。下降是危险信号——说明系统在做无效工作（处理已超时的请求、重试放大、锁竞争加剧）。设计良好的系统在这一段应该是吞吐持平 + 明确拒绝，而不是吞吐倒退。
拐点之后吞吐下降，几乎必然是背压做得不对。健康系统过载时应该"吃到额定量、其余明确拒绝"，曲线走平；吞吐倒退意味着资源被浪费在了不会被使用的结果上——回到第 05 节的截止时间检查与有界队列。把压测跑到崩溃段并观察形状，比只测额定负载有价值得多：它检验的是过载保护，而过载正是真实故障发生的时刻。

实验台想让你亲手确认的四件事。① 批大小是纯粹的取舍：调大→吞吐上限升、轻载 P50 也跟着升（攒批等待是白等的）。② 线程数有最优值不是越多越好：把"共享会话表"打开，你会看到线程数超过某个点后吞吐反而下降——同步开销吃掉了并行收益；切回分片模式，这个下降基本消失。③ 拐点前后是两个世界：利用率 70% 以下时 P99.9 和 P50 贴得很近，越过拐点后 P99.9 会陡直上翘——这就是"容量规划留 30% 余量"的量化依据。④ P99.9 永远比 P50 先恶化：当 P50 还很漂亮时，P99.9 可能已经翻了几倍，所以SLA 必须写在尾分位上，写平均值等于没写。
🎯 本篇要点回顾
  • "高并发"是三个不同问题：海量连接（瓶颈是每连接内存）、高报文率（瓶颈是每包固定开销）、低尾延迟（瓶颈是抖动源）；手段互相冲突，必须先定位
  • 连接模型每一代都在削掉"与总连接数成正比"的开销；epoll 让开销 = O(活跃数)，io_uring 再削掉 syscall，但要自己做背压
  • C10M 的墙是内存不是 epoll：一千万连接 × 10 KB = 100 GB，先审计会话对象
  • SO_REUSEPORT 无惊群、可逐个 worker 灰度重启，代价是长连接下分配可能长期不均
  • 按会话哈希分片同时买到：无锁、缓存热、同会话有序性；必须有 per-shard 水位指标（否则"总 CPU 40% 却在丢包"查不出来）
  • 跨核 40–200 ns、线程唤醒 1–5 µs，而 100 G 下 64 B 小包预算约 6.7 ns —— 这就是数据面必须 shared-nothing 的算术原因
  • 尾延迟 = 逐个消灭抖动源（调度/分配/缺页/中断/锁/攒批/定时器）；方法是看时延直方图最慢 0.1% 的聚集特征
  • 所有队列必须有界；满了要拒绝/丢弃/降级，不要阻塞入队；带截止时间检查避免做无效工作
  • 协程用在"多步流程"（会话建立、配置事务），不用在"每包处理"；注意帧分配与栈可观测性
  • 控制面状态外置（UDSF）、用户面状态本地化（PFCP 预下发）—— 时延预算决定的，不是架构偏好
  • 压测必须用固定速率工具避开协调遗漏；容量取拐点的 50%~70%；拐点后吞吐倒退 = 背压没做对
