电信云原生：NFV → CNF、5GC 与 O-Cloud 的容器化

核心网演进那篇把 5GC 拆成一堆网络功能，但没说这些 NF 跑在什么之上。本篇回答这个问题，并且只回答"电信负载和普通互联网负载有什么不一样"——这是电信云原生真正难的部分。

Module 03 阅读 ~30 min VNF → CNF
01

为什么电信要云原生

三代演进，以及 NFV MANO 与 K8s 的对应关系

本篇的边界，先声明清楚。容器与镜像、Pod / Deployment / Service、声明式 API 与控制器模式、服务发现、Operator、K8s 的调度与网络模型这些通用能力，本站已有专篇：云原生与 Kubernetes 讲原则与生态，容器底层原理 讲 namespace / cgroup v2 / OverlayFS / runc 的实现机制。本篇不重复这些内容，只讲电信负载在这套体系上"哪里对不上、怎么补"。如果你对 K8s 还不熟，建议先读那两篇再回来。

电信设备的形态经历了三代，每一代都是被成本和迭代速度逼出来的：

🏠 类比：专用硬件像自建独栋别墅——地基墙体全按自己需求造，住得最舒服，但想改个格局要重新盖。VNF 像整层公寓——楼是别人的，你租一整层自己装修，搬进搬出还是要几天。CNF 像共享办公工位——十分钟就能进驻、按人头付费，代价是隔音差：隔壁开会吵到你（噪声邻居抢 CPU/缓存），而电信业务恰恰是那个"在打电话不能被吵到"的人。所以电信版的共享办公必须额外装隔音间——那就是 CPU 独占、大页、网卡直通这一整套。

1.1 ETSI NFV MANO 与 K8s 生态的对应

NFV 时代 ETSI 定义了一套编排管理框架（MANO）。到了容器时代，这套框架并没有作废，而是被映射到 K8s 生态上。理解这张对应表，才能看懂运营商招标文档里的术语：

ETSI NFV 概念职责K8s 世界的对应物差异要点
NFVO Orchestrator跨站点的网络服务编排、生命周期、资源许可上层编排器（ONAP、厂商 SMO）+ GitOps 流水线K8s 本身没有"网络服务"概念，跨站点编排仍需外部系统
VNFM VNF Manager单个网络功能的实例化、扩缩容、升级、愈合Operator + Helm + HPAOperator 是最自然的落点：把厂商的运维知识写成控制器
VIM Virtualised Infra Manager管理计算/存储/网络资源池K8s 控制面本身（+ CNI / CSI / Device Plugin）CISM（Container Infra Service Mgmt）是 ETSI 给 K8s 的新名字
VNFD 描述符声明这个 NF 要什么资源、有哪些组件Helm Chart / CRDVNFD 是 TOSCA/YAML 标准，Chart 是事实标准，两者常需转换
EM Element Manager网元级 FCAPS 管理无对应；仍由厂商 EMS 或 SMO 承担K8s 只管"容器活着"，不管"网元业务是否正常"
最容易被低估的一行是最后一行。K8s 的健康检查只知道"进程在跑、端口能连"，它不知道"这个 AMF 是否还能正常处理注册"。电信侧必须自己把业务健康度（信令成功率、上下文数、队列水位）翻译成探针语义，否则会出现"Pod 全绿但网络不可用"。这是从互联网运维习惯迁移过来时最常踩的坑。
02

电信负载的额外要求

默认 K8s 缺的那几块

普通 Web 服务对 K8s 的诉求是"给我 CPU、内存、一个 Service 地址"。电信 NF 的诉求要长得多，逐条来看。

2.1 多网卡：Multus

K8s 默认给 Pod 一张网卡（eth0）。但一个 UPF 至少需要三张：N3（面向 gNB）、N6（面向数据网）、N4（面向 SMF），而且这几张通常在不同的 VLAN、不同的物理网卡，还要各自有独立的路由表。这不是"多个端口"能解决的，必须是多个网络接口。

Multus CNI：一个"元 CNI"（meta-plugin）。它先调用默认 CNI 给 Pod 建管理网卡，再按 Pod 注解 k8s.v1.cni.cncf.io/networks 追加若干张二级网卡，每张可以来自不同 CNI（macvlan、SR-IOV、host-device）。电信 CNF 几乎都依赖它。代价是网络拓扑不再由 K8s 统一表达——Service / NetworkPolicy 只作用于主网卡，二级网卡的连通性和策略要靠底层网络自己保证，可观测性明显变差。

2.2 用户态转发：SR-IOV / DPDK / VPP

UPF 要做的事是"每秒转发几百万个包并且抖动可控"。走内核网络栈做不到——每个包要经过中断、软中断、协议栈、多次拷贝，单核几十万 pps 就是上限，而且尾延迟不可控。电信数据面的标准答案是绕过内核：

手段做什么换来什么付出什么
SR-IOV物理网卡虚拟出多个 VF，直通给 Pod 独占接近裸机的收发性能，隔离性好VF 数量有限、Pod 与具体网卡硬绑定 → 调度自由度大幅下降、迁移困难
DPDK用户态轮询驱动 + 大页 + 无锁队列，完全接管网卡Mpps 级吞吐、微秒级确定性时延轮询线程 100% 占核（CPU 账单按核算而非按利用率）、失去内核工具链（tcpdump/iptables 全部失效）
VPP基于 DPDK 的向量化包处理框架，一次处理一批包更好的指令与数据缓存命中率自成一套转发平面与配置模型，学习与运维成本高
eBPF/XDP在内核驱动最早期挂钩处理包不占满核、保留内核可观测性能力受限（复杂状态处理难）、内核版本敏感
DPDK 与 K8s 的资源模型天然冲突。K8s 的 CPU request/limit 基于 CFS 配额（时间片），而 DPDK 轮询线程要的是"这个核完全归我、永不被抢"。用 CFS limit 去限制轮询线程会导致周期性节流（throttling）→ 丢包。正确做法是 cpuManagerPolicy=static + Guaranteed QoS（整数核）+ 宿主 isolcpus，把核从内核调度器手里彻底拿走。这条链上任何一环没配对，症状都是"平时好、偶发丢包"，极难定位。

2.3 内存与 CPU：HugePages / CPU Manager / NUMA

HugePages2 MB / 1 GB 大页减少 TLB miss。DPDK 的内存池必须建在大页上。K8s 通过 hugepages-2Mi 资源声明，需要宿主预先在启动参数里预留——运行时无法动态扩。
CPU Manager static让 Guaranteed Pod 独占整数个逻辑核，其他 Pod 不会被调度到这些核上。这是数据面确定性的前提。
isolcpus / nohz_full内核启动参数，把核从调度域移除并关闭周期性时钟中断，进一步消除抖动来源。
Topology Manager保证 CPU 核、大页、SR-IOV VF 来自同一个 NUMA 节点（single-numa-node 策略）。跨 NUMA 访问网卡 DMA 缓冲区会让吞吐直接掉一大截，原理见 NUMA 与内存进阶。
中断亲和把网卡中断、内核线程赶到管理核上，别落在业务核。K8s 不管这件事，要靠 tuned profile 或节点初始化脚本。
这五项必须一起配才有效果，这是最常见的失败模式：配了 static CPU Manager 但没配 isolcpus，内核线程照样跑在业务核上；配了大页但 Topology Manager 是 none，大页和 CPU 落在不同 NUMA 节点。任何一环缺失，测出来的时延分布都会有长尾，而各项配置单独看都"没问题"。写节点配置时把这五项当成一个不可分割的套件。

2.4 协议支持缺口

SCTP
N2（NGAP）与 4G 的 S1-MME 都跑在 SCTP 上。K8s 的 Service / kube-proxy 对 SCTP 支持长期是"能用但不完整"：多归属（multi-homing，SCTP 的核心特性之一，一个偶联绑多个 IP 做冗余）在 NAT/LB 后面基本无法工作。实际做法是绕开 Service——用 SR-IOV 或 macvlan 二级网卡让 Pod 直接持有可路由 IP，SCTP 端点直接暴露。这也意味着放弃了 K8s 的服务发现与负载均衡。
UDP 类型 Service 与会话保持
GTP-U（N3）是 UDP，且必须保证"同一条会话的包永远送到同一个 UPF 实例"（因为规则表在实例本地）。kube-proxy 的 UDP 负载均衡没有会话亲和语义。解决办法通常是把选择权交给控制面：SMF 直接选定某个 UPF 实例的 IP 下发给 gNB，根本不经过 K8s 的 LB。
实时性
O-DU 的 L1/L2 处理有硬性时限（每个 slot 500 µs / 250 µs 内必须完成），标准内核的调度延迟无法保证。需要 PREEMPT_RT 实时内核（那篇讲清了抢占模型、优先级继承与延迟来源），并且容器里的线程要能设 SCHED_FIFO——这需要 Pod 具备相应 capability，与"最小权限"的容器安全原则直接冲突。
03

有状态 vs 无状态

AMF 重启后，UE 上下文怎么保住

K8s 的核心假设是"Pod 是牲畜不是宠物"——随时可以被杀掉重建。但 核心网演进那篇算过：一个 AMF 实例持有数百万 UE 上下文，几十 GB 内存。这些状态如果随 Pod 消失，一次滚动升级就等于全网用户掉线。

5GC 标准的答案是无状态化 + 状态外置：

UDSF（Unstructured Data Storage Function）：3GPP 定义的、供 NF 存放非结构化状态的共享存储服务。NF 把 UE 上下文序列化后写进 UDSF，本地只保留缓存。实例宕掉后，接管实例凭 UE 标识从 UDSF 取回上下文继续服务。工程上 UDSF 常由内存数据库（Redis 集群、专用 IMDB）实现，因为它在信令热路径上。

听起来干净，但引入了一组新的权衡，这才是真正的工程内容：

决策点选项 A选项 B怎么选
写入时机同步写：每次状态变更都写 UDSF 后才回响应异步/批量写：先回响应，后台落库同步写保证零丢失但每条信令多一次 RTT（信令时延翻倍）；异步写快但故障瞬间会丢最近状态。多数实现选"关键节点同步、中间态异步"
写入粒度整个上下文增量字段整体写简单但流量大（几十 KB × 百万次）；增量写省带宽但要处理版本冲突
本地缓存不缓存，每次读 UDSF缓存 + 失效策略不缓存会让 UDSF 成为瓶颈；缓存则要面对"两个实例同时认为自己拥有这个 UE"的一致性问题
故障接管任意实例可接管（真无状态）主备实例接管（半状态）真无状态的运维最简单，但每次请求都要查存储；主备切换快，但备机要持续同步
存储自身可用性UDSF 三副本强一致UDSF 主从异步复制强一致写延迟高；异步复制在存储故障切换时会丢数据。UDSF 本身成了新的单点，需要独立的可用性设计
"无状态"是个相对说法。状态没有消失，只是从 NF 内存搬到了 UDSF——你把可用性问题从"NF 会不会挂"变成了"UDSF 会不会挂"，同时新增了一跳网络延迟。这个交换在信令面是划算的（信令时延预算有几十毫秒，容得下一次 KV 访问），在用户面完全不划算（UPF 的规则表必须在本地，不可能每个包去查存储）。所以真实系统里 UPF 依然是有状态的，它的高可用靠 N4 会话重建、而不是靠状态外置。这个区分是理解电信云原生 HA 设计的关键，进一步的可用性权衡见 通信系统的性能、可靠性与高可用。
StatefulSet 不等于解决方案：K8s 的 StatefulSet 提供稳定的网络标识与持久卷，适合"实例身份重要"的场景（如数据库）。但它解决的是存储挂载与命名，不解决"上下文能被别的实例接管"。5GC 的无状态化目标是让实例身份不重要，所以大多数控制面 NF 反而用 Deployment + 外部 UDSF，而不是 StatefulSet。
04

O-RAN O-Cloud

RAN 上云比核心网上云难一个量级

O-Cloud：O-RAN 定义的云平台抽象——承载 O-DU / O-CU（以及部分 RIC）的虚拟化基础设施。它通过 O2 接口接受 SMO 的管理：O2ims 负责基础设施资源的清单与生命周期（节点、加速卡、镜像仓库），O2dms 负责在其上部署与管理网络功能实例。这与 O1 是两层：O1 管"网元的业务配置"，O2 管"承载网元的云平台"。

核心网上云已经量产多年，RAN 上云仍在艰难推进。三个难点：

4.1 硬实时调度

O-DU 的 L1（如果不卸载）和 L2 高层要在每个 slot 的时限内完成处理。5G NR 常用 30 kHz 子载波间隔时，一个 slot 是 500 µs；再考虑前传时延预算，留给 DU 处理的窗口只有一两百微秒。这个量级的确定性要求意味着：

  • 业务线程必须 SCHED_FIFO 跑在独占核上，内核必须是 PREEMPT_RT，任何一次几百微秒的调度延迟就是一个丢帧。
  • 容器不能有"冷启动"行为：首次访问触发的缺页、JIT、动态库延迟加载都可能超时。启动阶段要预热并锁定内存（mlockall）。
  • 宿主机上的任何"背景噪音"都要清理：内核线程迁移、定时器、监控 agent 的周期采集，都可能抢到业务核上。这类问题的定位方法和 低延迟工程里讲的抖动排查是同一套。

4.2 PTP 时钟穿透容器

PTP / SyncE 那篇讲清了为什么前传需要纳秒级同步。上云之后这件事变棘手：

  • 时钟是宿主级资源。PHC（PTP Hardware Clock）设备属于某张网卡，ptp4l / phc2sys 在宿主上跑，把系统时钟同步到 PHC。容器共享宿主时钟（time namespace 不隔离 CLOCK_REALTIME 的同步源），所以"同步"这件事本身是宿主的责任，不是 CNF 的。
  • 但 CNF 需要读取同步状态：时钟类别、锁定状态、偏移量——这些要通过 O1/M-plane 上报给 SMO。于是容器需要访问 /dev/ptp* 或宿主的状态接口，又一次与容器隔离原则冲突。
  • 如果 O-DU 用 SR-IOV VF 收发前传报文，硬件时间戳能力必须在 VF 上可用，而不是所有网卡的 VF 都支持。这是选型时的硬约束，不是软件能弥补的。
一句话总结这个难点：同步是"物理事实"，而容器化的本质是"抽象掉物理"。两者天然对立，只能靠"把宿主能力有选择地暴露进容器"来妥协——每一次暴露都是隔离性的让步，也是运维复杂度的增加。

4.3 加速卡直通

L1 的 FEC 编解码（LDPC）算力需求极大，通常卸载到硬件——inline 加速卡（网卡上直接做）或 look-aside 加速器（如 FPGA / eASIC）。容器要使用它们，依赖 Device Plugin 把设备注册成可调度资源，配合 SR-IOV / VFIO 直通。带来的现实问题：

  • 调度自由度归零。Pod 只能落在有该型号加速卡的节点上，节点异构导致调度器可选集极小，"云"的弹性优势被大幅削弱。
  • 驱动与镜像耦合。容器内的用户态驱动版本必须匹配宿主内核模块版本，升级要两侧协同——这是"容器让部署解耦"承诺的一个明显例外。
  • 故障隔离弱。加速卡挂了或状态异常，往往需要重置整卡，影响同卡上的其他实例。
05

发布与运维的坑

滚动升级对长连接的杀伤

互联网服务的滚动升级之所以"无感"，靠的是一个隐含前提：请求是短的、无状态的、可重试的。HTTP 请求打断了重发一次就行。电信信令面完全不满足这个前提。

连接类型升级时发生什么业务后果缓解手段
SCTP 偶联（N2/S1-MME）Pod 终止 → 偶联断链，gNB 侧感知为 AMF 不可用该 gNB 下所有 UE 的信令中断，可能触发大规模重注册（= 自制信令风暴）NG Setup 前先做 AMF 卸载流程（Overload/Configuration Update 引导 gNB 迁移）；一次只升一个实例并留足观察期
NETCONF 会话（O1/M-plane）会话断开，未提交的 candidate 配置丢失，订阅的通知流中断SMO 侧配置事务失败，需要重连并重新拉取全量状态对齐升级前主动 close-session；实现会话恢复与配置对账（见 NETCONF 工程实践）
PFCP 关联（N4）SMF↔UPF 关联丢失已有会话规则可能被清空 → 用户面中断，比信令中断更可感知PFCP Association 支持恢复标识（Recovery Time Stamp）；实现"关联重建后规则重下发"而非清空
HTTP/2 SBI连接断开，进行中的事务失败影响较小（可重试），但半完成的会话事务需要清理优雅退出：先从 NRF 注销 → 停止接新请求 → 等在途事务完成 → 退出
连接排空（connection draining）与优雅退出：正确的退出顺序是四步——① 从注册中心/负载均衡摘除自己（不再有新请求进来）；② 拒绝新会话但继续处理已有会话；③ 主动引导对端迁移（这是电信特有的一步：通过协议告诉 gNB/SMF "请转到别的实例"）；④ 在途事务完成或超时后退出。K8s 侧对应 preStop 钩子 + 足够长的 terminationGracePeriodSeconds——默认 30 秒对电信场景往往远远不够。
探针的两个反直觉坑。① Liveness 探针配得太敏感是灾难：信令风暴时 NF 本来就慢，探针超时 → K8s 重启 Pod → 上下文重建 → 负载更高 → 下一个实例也被重启，形成升级版的雪崩。信令面的 liveness 应该只检测"真死"（死锁、线程全挂），不要用业务时延做判据。② Readiness 必须包含业务就绪：进程起来但还没从 UDSF 加载完上下文、还没建立 SCTP 偶联，此时被标记 Ready 就会收到流量并失败。业务就绪的判据要由 NF 自己给。

金丝雀发布在电信场景也需要重新定义。互联网的金丝雀按请求比例切流；电信信令的自然切分维度是网元/区域——先升级一个城市的一个 AMF、观察该区域的注册成功率与切换成功率，再推下一个。按请求比例切在这里没有意义，因为一个 UE 的信令必须始终由同一个实例处理（否则上下文不一致）。

06

裸机 / 虚机 / 容器取舍

不是"容器最好"，而是"哪段用哪个"

维度裸机 PNF虚拟机 VNF容器 CNF
时延与抖动最优，可做硬实时中：hypervisor 引入额外抖动（VM exit、vCPU 调度）接近裸机（共享内核，无 VM exit），但需 static CPU + isolcpus 才能达到
部署密度低：一台机器一个功能中：每 VM 一份 Guest OS 开销（GB 级内存 + 分钟级启动）高：共享内核，镜像 MB 级，秒级启动

真实网络是混合的，而且长期会是混合的。常见组合：5GC 控制面全容器（收益最大——弹性、迭代快、状态可外置）；UPF 容器化但配满 SR-IOV/DPDK/大页/独占核（拿容器的部署便利，不要容器的资源共享）；O-DU 容器化 + 实时内核 + 加速卡（最难，仍在爬坡）；O-RU 保持专用硬件（成本与功耗决定，短期不会变）。把"容器化"当成目标而不是手段，就会在 O-DU 上撞墙。
07

CNF 到底差在哪

一句话回答

CNF 和普通微服务，差在"它必须同时是云原生的和确定性的"。普通微服务通过放弃对底层的假设换取弹性——不关心跑在哪台机器、哪个核、哪张网卡上。CNF 做不到这个放弃：它需要独占的核、特定 NUMA 上的大页、直通的网卡 VF、宿主的 PTP 时钟、实时内核的调度保证。于是电信云原生的全部工程量，就是在一个以"抽象掉硬件"为设计目标的平台上，把硬件细节有选择地重新暴露出来，同时尽量不丢掉声明式、自愈、滚动升级这些好处。

展开成可操作的四条判断：

  • 调度约束多一个量级。普通微服务的调度约束是 CPU/内存；CNF 还要 NUMA 对齐、设备可用性、内核版本、大页数量、网卡型号。可行节点集常常只有个位数，"弹性"更多体现在升级便利而非自动扩缩。
  • 网络不走 Service。多网卡 + 直通 IP + 控制面自己选实例，K8s 的服务发现与负载均衡在数据面基本用不上。这意味着可观测性要自己建，不能指望 service mesh。
  • "重启一下"不是兜底手段。重启意味着上下文重建、偶联断链、可能引发重注册风暴。自愈策略要比互联网服务保守得多。
  • 协议决定运维流程。优雅退出、金丝雀维度、探针语义都由 3GPP/O-RAN 的协议行为决定，而不是由平台惯例决定。不读协议就配不对运维参数。
🎯 本篇要点回顾
  • 三代演进（PNF → VNF → CNF）每一步都在用确定性换解耦度；电信云原生的工作就是把确定性补回来
  • ETSI MANO 映射到 K8s：VNFM ≈ Operator、VIM ≈ K8s 控制面，但 EM（网元业务健康）没有对应物，必须自己补
  • 额外要求套件：Multus 多网卡 + SR-IOV/DPDK + HugePages + CPU Manager static + isolcpus + Topology Manager，五项缺一就有长尾
  • 协议缺口：SCTP 多归属、UDP 会话亲和在 K8s Service 上无法满足 → 绕开 Service，用直通 IP + 控制面选实例
  • 无状态化 = 状态搬到 UDSF，可用性问题也随之转移；用户面（UPF）依然有状态，靠 N4 会话重建而非状态外置
  • O-Cloud 三难：硬实时调度、PTP 时钟穿透容器、加速卡直通——都是"抽象掉硬件"与"依赖硬件"的正面冲突
  • 滚动升级对 SCTP/NETCONF/PFCP 长连接是硬伤；要主动引导对端迁移，金丝雀按网元/区域而非请求比例
  • 裸机/虚机/容器长期混合共存；把容器化当目标而非手段就会在 O-DU 上撞墙
