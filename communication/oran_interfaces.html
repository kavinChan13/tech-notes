O-RAN 接口：Open Fronthaul / O1 / E2 / A1 / F1

把接口集中讲，避免一个接口一篇造成碎片化。每个接口只需回答四问：谁连谁？解决什么？属于哪个平面？和 3GPP 是什么关系？特别澄清一个高频误区：Open Fronthaul ≠ eCPRI。

01

接口全景

一张连线图定位所有接口

基站被拆成 O-CU / O-DU / O-RU 三块、再挂上 RIC 和 SMO 之后，真正决定这套系统能不能多厂商拼装的，不是网元本身，而是网元之间那些接口。一个网元内部怎么实现是厂商私事，但只要它对外的接口行为与规范一致，别人就能替换掉它。所以「O-RAN 是什么」这个问题，最终会归约成「O-RAN 定义了哪些接口，每个接口约束了什么」。

生活类比：公司之间的合同。一家公司内部怎么开会、用什么 ERP，外人管不着；但它和上游供应商之间的合同——交付什么、什么格式、多久之内、验收标准是什么、谁负责——一旦写死，供应商就是可替换的。接口就是网元之间的合同。CPRI 时代的问题不是「没有合同」，而是每家的合同都是自己写的，条款还不公开，于是你买了谁的 DU 就只能买谁的 RU。

本篇把 9 个接口摊开逐个讲清四件事：连接哪两个网元、承载什么内容、协议栈怎么分层、由谁定义。判断一个接口的「性格」有一条很好用的经验规则：看它的时延预算。100 µs 级的接口一定是硬件/FPGA 参与的以太网直连，秒级的接口一定是 HTTP/JSON 加数据库。时延预算差 4 个数量级，技术选型就没有任何共同点。

全景图：谁连谁，谁定义的

图里 E2 节点那个虚线框是有讲究的：E2 不是「RIC 连到基站」这么笼统，而是分别与 O-CU-CP、O-CU-UP、O-DU 各建一条 E2 关联（还可以包含 O-eNB）。每条关联独立声明自己支持哪些 RAN Function——O-DU 报得出 MAC 层调度与 PRB 占用，O-CU-CP 报得出 RRC 连接数与切换事件，两者不能互相替代。

命名规律：为什么有的接口带 -C / -U 后缀

3GPP 的习惯是一个接口名 + 平面后缀：控制面加 -C、用户面加 -U。两个后缀不只是命名区分，它们在实际网络里是两条完全独立的 IP 流，可以走不同的 VLAN、不同的 QoS、不同的物理路径，甚至在故障时表现出「信令通但数据不通」这种典型症状。O-RAN 新增的接口则不带后缀，因为它们各自只有单一用途。

3GPP 侧：接口名 + 平面后缀，两条独立的 IP 流

      └─ F1-U   用户面   UDP  / GTP-U    ← O-CU-UP ↔ O-DU
  NG ─┬─ NG-C   控制面   SCTP / NGAP     ← O-CU-CP ↔ AMF

这条命名规律有一个非常实用的排障推论：「注册成功但没有流量」几乎一定是 -U 面的问题，「完全接不上」才是 -C 面的问题。UE 能进 RRC_CONNECTED、核心网侧看到会话建立，说明 F1-C / NG-C / E1 全通；此时数据不走，就去查 F1-U / NG-U 的 GTP-U 路径——最常见的三个原因是 MTU 不够导致隧道内分片被丢、TEID 配错或对端未开、以及承载 -U 面的 VLAN 没打通。

02

Open Fronthaul（前传接口）

O-RAN 最标志性的开放接口

Open Fronthaul：O-RAN 定义的 O-DU ↔ O-RU 之间的开放前传接口规范（基于 3GPP 7-2x 拆分）。它规定了前传上的 C/U/S/M 四个平面：Control、User、Sync、Management，其中 C/U 平面承载用 eCPRI（over Ethernet）。
关键澄清：Open Fronthaul ≠ eCPRI。
• Open Fronthaul 是 接口规范（规定 O-DU 和 O-RU 之间该有哪些平面、消息、时序、管理模型）。
• eCPRI 是 Open Fronthaul C/U 平面所使用的承载协议之一。
• 层次关系：O-RAN → Open Fronthaul(接口) → eCPRI / Ethernet(承载)。
Open Fronthaul 还额外定义了 eCPRI 之外的东西：S 平面（PTP/SyncE 同步 profile）、M 平面（NETCONF/YANG 管理 O-RU）、以及 U/C 平面之上的 O-RAN 专有 section 扩展。
  • 谁连谁：O-DU ↔ O-RU。
  • 解决什么：让不同厂商的 DU 和 RU 能在前传上互通（打破私有 CPRI）。
  • 平面：数据面(U) + 控制面(C) + 同步面(S) + 管理面(M)。
  • 与 3GPP：落地 3GPP 7-2x 拆分点，补齐可互操作的细节。

协议栈：唯一一个不跑在 IP 上的接口

把 Open Fronthaul 的协议栈画出来，会发现它和本篇其它所有接口都不一样：C/U 平面默认没有 IP 层，也没有 TCP/UDP。eCPRI 直接坐在以太网帧上（EtherType 0xAEFE），靠 VLAN 标签和 PCP 优先级做隔离与调度。

规范上 eCPRI 也允许 UDP/IP 承载，O-RAN 还并列允许 IEEE 1914.3 (RoE)；
实际部署几乎清一色是「eCPRI over Ethernet」——多一层 IP 就多一份处理时延与抖动。
「为什么前传不用 IP」是个好问题。三个理由：① 时延预算不允许——单向只有百微秒量级，IP 转发与可能的分片重组会吃掉相当比例；② 不需要路由——O-DU 与 O-RU 之间是点到点或经一台前传交换机，没有多跳选路的需求；③ 硬件友好——eCPRI 头只有 4 字节固定字段，FPGA/ASIC 可以在线速下用固定偏移直接解析，不必处理 IP 的可变头长与选项。前传是本站里少数几个「软件根本来不及、必须硬件参与」的场景。

时延预算：100 µs 这个数是怎么来的

前传时延要求常被引用为「单向 100 µs 量级」，它不是拍出来的，而是从空口 HARQ 时序倒推的。UE 收到下行数据后要在规定的 slot 里回 HARQ 反馈，而处理这个反馈的 MAC 调度器在 O-DU 里——于是「O-DU 发出调度命令 → O-RU 发射 → UE 处理 → UE 回传 → O-RU 收 → O-DU 拿到」这一整圈必须塞进 HARQ 的时间预算，前传占掉的那两段（下行 + 上行）就被挤到了百微秒量级。

互操作的真实难点：Category 与 section 扩展

「有了规范就能互通」是最大的误解。Open Fronthaul 规范里有大量可选能力，两端支持的子集不一致就是配不通。最典型的两处：

可选点含义不匹配的后果
O-RU Category（A / B）Category A 的 O-RU 不做预编码，O-DU 送下来的就是天线端口数据；Category B 的 O-RU 内部承担一部分预编码，接口上传的是层数据DU 按 B 发、RU 只支持 A（或反之），波束赋形完全错乱；这不是「性能差一点」，是根本跑不起来
Section 扩展与压缩方式IQ 的位宽与压缩方法（如块浮点）、以及各类 section extension 的支持度都是可选的协商失败或解出乱码；带宽估算也会全错（压缩比直接决定前传带宽）
M 平面管理架构Hierarchical：只有 O-DU 通过 M 平面管 O-RU；Hybrid：SMO 也可以直接经 NETCONF 管 O-RU两端预期不一致时，O-RU 可能拒绝第二个 NETCONF 会话，或出现两个主体同时改配置
时钟拓扑（LLS-C1..C4）O-RU 从哪里取时钟O-RU 一直处于 HOLDOVER/FREERUN，小区起不来
真实案例形态：DU 与 RU「握手成功但没有空口」。现场表现是 M 平面 NETCONF 会话正常、O-RU 状态上报 OK、告警栏干净，但小区始终没有 UE 接入。排查顺序应当是：① 先看 O-RU 的 PTP 状态——是 LOCKED 还是 HOLDOVER？没锁上就不用往下查了；② 再看 O-RU 侧的 C/U 平面统计计数器——收到的 eCPRI 报文数是 0（VLAN/PCP 没打通、或 PC_ID 与 O-DU 配置的 eAxC 编号对不上），还是有报文但全被判为 late（时延超窗）；③ 最后才怀疑 Category / 压缩配置。这个顺序的依据是「从下层往上层排」：时钟不对，一切统计都不可信。
面试里被问「Open Fronthaul 和 CPRI 的本质区别」时，别停在「一个开放一个私有」。要答出数据形态变了：CPRI 传的是时域采样，带宽只跟采样率与天线数相关，与实际有没有用户完全无关（空载也满带宽）；7-2x 之后传的是频域采样，只传实际被调度的 PRB，带宽随负载变化，还能做压缩。这一个改变才是前传带宽从「几十 Gbps 固定」降到「可统计复用」的根本原因，也顺带解释了为什么 7-2x 之后前传网络可以用以太网交换机做汇聚。

F1（中传接口）

这是 3GPP 的接口，O-RAN 复用

  • 谁连谁：O-CU ↔ O-DU（对应 Option 2 拆分）。
  • 解决什么：承载 CU 与 DU 之间的控制面(F1-C)与用户面(F1-U)。
  • 平面：含控制面与用户面（RAN 内部）。
  • 与 3GPP：F1 是 3GPP 定义的，O-RAN 直接复用（不是 O-RAN 新造）。承载在 Midhaul 上。
辨析：F1 属于"3GPP 原生接口"，Open Fronthaul / O1 / E2 / A1 才是 O-RAN 重点新增或开放化的接口。面试里能指出"F1 是 3GPP 的、E2/A1/O1 是 O-RAN 的"是个加分点。

这一章除了 F1，还把另外三个 3GPP 原生接口一起讲完——E1、NG、Xn。把它们放在一起是因为它们共享同一套「工程语言」：控制面一律是 ASN.1 编码的应用协议跑在 SCTP 上，用户面一律是 GTP-U 隧道跑在 UDP 上。学会读一个，剩下三个就只是消息名不同。本章后半段专门拆这两条共性：为什么信令面选 SCTP 与 GTP-U 为什么要多套一层隧道。

F1AP 的典型过程

F1AP 的消息分两类，这个二分法是读懂所有 3GPP 应用协议的钥匙：

  • 非 UE 关联（non-UE-associated）：与某个具体终端无关的，比如接口建立、小区激活、系统消息更新。这类信令固定走同一条流（实现上普遍是 stream 0），以保证接口级过程之间的顺序；具体规定见对应接口的信令传输规范（F1 见 TS 38.472、NG 见 TS 38.412）。
  • UE 关联（UE-associated）：针对某一个终端的，靠一对 ID 定位上下文——gNB-CU UE F1AP ID（CU 侧分配）与 gNB-DU UE F1AP ID（DU 侧分配）。两端各自分配、各自维护映射表，任何一条消息都要同时带上两个 ID，接收方才知道自己这边是哪个上下文。

E1：CU 内部的那条线

E1：3GPP 定义的 gNB-CU-CP ↔ gNB-CU-UP 接口，应用协议是 E1AP（TS 38.463），跑在 SCTP 上（端口 38462）。E1 是纯控制面接口，永远不承载用户数据——它的唯一职责是让 CU-CP 去指挥 CU-UP 建立、修改、释放承载上下文。

E1 存在的理由是 CU 的控制面与用户面要独立扩容。控制面的负载正比于「信令事件数」（接入、切换、寻呼），用户面的负载正比于「比特数」。这两者的比例在不同场景下差好几个数量级：一个物联网小区可能有海量连接但吞吐极低（CP 重、UP 轻），一个热点小区可能只有几十个用户但跑满带宽（UP 重、CP 轻）。把它们做成两个可以分别部署、分别扩容的网元，是云化 RAN 的前提；而拆开就必须有接口，E1 就是这个接口。

另一个常被忽略的动力是用户面下沉：CU-UP 可以部署在靠近基站的边缘机房以降低时延（MEC 场景），而 CU-CP 集中在区域中心。这只有在 CP/UP 分离之后才做得到。

NG：连到 5GC 的那两条线

NG（也常按核心网侧的叫法称 N2 / N3）是 RAN 与 5G 核心网之间的接口。在分离架构里，NG 终结在 CU 上，DU 与 RU 完全看不到它——这是 Option 2 拆分的直接结果：NG-C 承载的是 NAS 与会话级信令，需要 RRC 上下文；NG-U 承载的是 PDCP 之上的用户 IP 包。

Xn：基站之间的横向连接

Xn：3GPP 定义的 gNB ↔ gNB 接口（TS 38.420 系列）。Xn-C 跑 XnAP（TS 38.423）over SCTP（端口 38422），Xn-U 跑 GTP-U。在分离架构里 Xn 同样终结在 CU 上。

Xn 切换源站直接向目标站发 HANDOVER REQUEST（含 UE 上下文与安全参数），目标站预留资源后回 ACK；切换完成后再通过 NG-C 通知 AMF 换路径退化成 NG 切换：所有信令绕 AMF 一圈，中断时间明显变长
数据前转Xn-U 上建立临时隧道，把源站缓存里还没发完的下行数据转给目标站，避免丢包切换瞬间的在途数据丢失，TCP 会看到重传甚至窗口塌陷
双连接（NR-DC / EN-DC 的 NR 侧）主节点向辅节点请求增加/修改辅小区组，协商承载分流方式无法做多站点聚合，边缘吞吐上不去
RAN 寻呼与资源协调RRC_INACTIVE 的 UE 在 RAN 通知区内被寻呼；相邻站之间协调 TDD 配置与干扰INACTIVE 态的价值大幅缩水；干扰只能靠集中式优化
Xn 与 E2 在「负载均衡」这件事上容易混。Xn 上的资源状态上报是「两个基站之间的双边协商」，粒度粗、目的是完成一次具体的切换或双连接；E2 上的上报是「多个基站向一个集中大脑汇报」，目的是让 xApp 做全局决策。前者是 3GPP 的分布式思路，后者是 O-RAN 的集中式思路，两者并存而不是互相替代。真实网络里的移动性负载均衡（MLB）常常是：xApp 经 E2 看到某小区过载，下发策略调整切换门限，实际的切换动作仍然走 Xn 完成。

为什么信令面用 SCTP 而不是 TCP

SCTP（Stream Control Transmission Protocol，RFC 4960，已由 RFC 9260 取代）：一个与 TCP 平级的可靠传输协议，IP 协议号 132。它诞生于 SIGTRAN 项目——当年要把 SS7 电话信令搬到 IP 网上，发现 TCP 的语义根本不合用，于是新设计了一个。所以 SCTP 从第一天起就是为电信信令定制的，不是通用传输协议。

3GPP 在 F1-C、E1、NG-C、Xn-C 上一律规定用 SCTP，O-RAN 的 E2 也跟着用 SCTP。这不是「历史惯性」，而是三个具体能力的组合，每一个都对应 TCP 的一个真实缺陷。

优势一：多流（multi-streaming）消除队头阻塞

TCP 是单一有序字节流。一条 SCTP 关联内部可以有多条逻辑流（stream），流与流之间的交付顺序互不相干。这一点对信令面是决定性的：

一台 O-DU 上可能同时有上千个 UE 在做接入、切换、释放。如果这些信令挤在一条 TCP 连接里，任何一个报文段丢失都会把其后所有 UE 的信令扣在接收缓冲里，直到重传补齐——一个 RTO 在 SCTP 默认参数下是秒级的，这期间所有 UE 的状态机都在等，超时后大面积失败。多流把这种耦合降到「只影响散列到同一条流的那些 UE」。

这里有个常被答错的细节，说清楚很加分：SCTP 的多流只解耦了「向上层交付的顺序」，没有解耦「拥塞控制与重传」。拥塞窗口、RTO、SACK 都是每关联一份的。所以链路真的丢包时，整条关联的发送速率都会降下来，只是接收侧不会因为等一个包而把别的流全扣住。想要连拥塞控制也隔离，就得建多条关联（或者用 QUIC 那种每流独立的设计）。

优势二：多归属（multi-homing）做传输层故障切换

一条 SCTP 关联的每一端都可以绑定多个 IP 地址。握手时双方交换全部地址，之后其中一个被选为主路径，其余作为备份路径，靠周期性的 HEARTBEAT 探活。主路径失效时，关联不断，只是切到备份地址继续发——上层应用完全不感知，UE 上下文不用重建。

TCP 做不到这一点：TCP 连接由四元组唯一标识，换 IP 就是换连接，必须重建。传统做法是在 IP 层做冗余（VRRP 浮动地址、BFD + 动态路由），但那要么依赖网络设备配合，要么收敛时间受路由协议约束。SCTP 把故障切换下沉到了传输层，不依赖任何网络侧机制。

优势三：保留消息边界（面向消息而非字节流）

SCTP 的传输单元是消息：发送方 send 一次，接收方就 recv 到完整的一条，不多不少。TCP 是字节流，应用必须自己加长度前缀、自己处理粘包与半包。

这一条对 ASN.1 编码的信令协议尤其重要：F1AP / NGAP 的 PER 编码结果本身不带长度字段（长度信息在编码里是隐式的，要解到一半才知道有多长）。如果跑在 TCP 上，就必须在协议之外额外套一层帧定界——SIGTRAN 时代的 M3UA 就是这么干的（自己定义了带长度的公共头）。SCTP 直接把这个问题消灭了。附带的能力还有：可以按消息选择「有序交付」或「无序交付」（U 位），心跳、状态查询这类消息不需要排队。

GTP-U：用户面为什么要再套一层隧道

用户数据本身就是 IP 包，UE 也已经有了 IP 地址。那为什么不直接路由，非要在外面再套一层 UDP + GTP-U？三个理由，缺一不可：

理由不套隧道会怎样
① 移动性 / 会话连续性UE 的 IP 由 SMF/UPF 分配，锚定在 UPF 上。UE 切换到另一个基站时，如果靠路由把流量引过去，就要在传输网里为每个终端注入一条主机路由并在切换时收敛——百万级终端的路由表，且收敛时间远慢于切换时间。套隧道后换基站只是换隧道端点，UE 的 IP 一位都不用变。
② 会话与 QoS 标识一个 UE 可以有多个 PDU 会话，每个会话里有多个 QoS Flow。裸 IP 包里没有任何字段能表达「这是哪个会话的哪条流」。TEID 标识隧道（≈ 会话/承载），扩展头里的 QFI 标识流，转发面据此做限速、调度、计费。
③ 地址空间隔离UE 的地址属于 N6 侧的用户地址空间（常有大量私网地址与重叠地址、多 APN/DNN 各一套），在 RAN 传输网里不可路由也不应可路由。传输网只需要知道 gNB 与 UPF 的地址，规模从「终端数」降到「网元数」。

生活类比：快递里的转寄服务。你搬家了，但不想通知所有商家改地址（那是「给每个终端注入主机路由」）。于是你在快递公司登记一个转寄：包裹先寄到老地址（UPF，你的 IP 锚点），快递公司再套一个新面单（GTP-U 头）转发到你的新住处（当前基站）。搬家只要改快递公司那一条记录，寄件人一无所知。TEID 就是那张面单上的转寄单号——它标识的是「这一路转寄关系」，而不是收件人本人。

F1-U 上那个 NR RAN Container 值得单独说，因为它是「DU 缓存爆掉」这类问题的答案所在。CU-UP 往 DU 灌数据时，并不知道 DU 侧的 RLC 缓冲还剩多少、空口是否正在被干扰。TS 38.425 定义了一对报文解决这件事：CU-UP 下发的 DL USER DATA 带 NR-U 序列号；DU 定期回 DL DATA DELIVERY STATUS，里面报「期望的缓冲区大小」、已成功交付的最高 PDCP SN、以及丢失的 PDU 区间。CU-UP 据此调节下发速率并触发 PDCP 重传。换句话说，F1-U 虽然跑在不可靠的 UDP 上，但在 GTP-U 扩展头里自带了一套逐承载的流控与反馈回路。现场如果看到 DU 侧 RLC 丢弃率高而空口质量正常，就要怀疑这条反馈链路（配置未开启、或 CU 侧未按上报值限速）。
MTU 是 GTP-U 最经典的坑，而且症状极具误导性。隧道每层都要加头：外层 IPv4 20 + UDP 8 + GTP-U 8（带扩展头再 +8）= 36~44 字节，IPv6 外层还要再多 20。如果传输网的 MTU 是标准 1500，那么 UE 侧能安全通过的 MTU 就只剩 1450 左右。

不处理的后果是「小包正常、大包全丢」：ping 通、DNS 正常、网页打开一部分就卡住、HTTPS 握手偶尔失败——因为 TLS 握手的证书报文正好是大包。更麻烦的是外层如果设了 DF 位而中间设备的 ICMP「需要分片」被防火墙丢掉，路径 MTU 发现就彻底失效（PMTUD 黑洞）。

三种处置，按优先级：① 传输网整段开 jumbo frame（推荐，从根上消除）；② 在 gNB/UPF 上通告给 UE 的 MTU 减掉隧道开销；③ 对 TCP 做 MSS clamping 兜底（只救 TCP，救不了 UDP/QUIC，所以只能算兜底）。

生产陷阱：版本协商与兼容矩阵

多厂商组网真正的成本不在「协议实现」，而在版本组合。同一个接口，两端各自实现了某个 Release，能不能互通取决于协议的可扩展性机制设计得好不好。3GPP 这方面做得相当扎实，值得单独理解。

ASN.1 的向后兼容机制：extension marker + criticality

  IE 定义里的省略号就是扩展点：
      UEContextSetupRequest ::= SEQUENCE {
          protocolIEs   ProtocolIE-Container,
          ...                 ← 未来版本可以在这里追加内容，老版本解码器能跳过
      }

  每个 IE 在容器里都带一个 **criticality**，告诉对端「你要是不认识我，该怎么办」：
      reject  → 整条消息失败，回 Failure，并在 Criticality Diagnostics 里指出是哪个 IE
      ignore  → 忽略这个 IE，继续处理消息的其余部分

SCTP 在真实网络里的三个配置坑（多归属尤其多）：
① 两个地址其实不独立。把两个 IP 配在同一块网卡、同一个 VLAN、同一台接入交换机上——形式上是多归属，实际共享全部单点。做多归属前先问：这两条路径的故障域真的分开了吗？
② 反向路径不通 / rp_filter。多归属要求任意源地址、任意目的地址的组合都可达（共 4 种组合）。工程上常见只测了主-主一条。Linux 的 rp_filter=1 会按路由表校验源地址，多网卡场景下直接丢包，表现是备份路径的 HEARTBEAT 永远收不到 ACK。
③ 中间设备不认多归属。有状态防火墙看到 INIT 里声明的地址列表之外的源地址就丢；NAT 基本不支持 SCTP 多归属；云上的四层负载均衡多数只支持 TCP/UDP。所以相当多的现网索性用单归属 SCTP + IP 层冗余（BFD + 动态路由 / VRRP），把可靠性交给网络而不是传输层。这是个正当的工程选择，不是「没做好」。
容器化部署还要再加一条：K8s 的默认 CNI 与 Service 对 SCTP 支持有限，Pod 通常只有一个 IP，多归属基本无从谈起，实践中靠 Multus 多网卡 + SR-IOV，或干脆放弃多归属。这是 O-Cloud 化过程中一个真实的能力退化，值得在方案评审时明确提出来。

O1（管理接口）

NETCONF/YANG 登场的地方

  • 谁连谁：SMO ↔ 所有 O-RAN 网元（O-CU/O-DU/O-RU，以及 Near-RT RIC）。
  • 解决什么：管理面（FCAPS）——配置、性能监控、故障、软件管理。
  • 用什么协议：NETCONF/YANG（配置/状态）+ VES（事件/遥测流）。
  • 属于：管理平面（Management Plane）。
这就是 "NETCONF/YANG 为什么出现在 O-RAN" 的答案：SMO 通过 O1 接口用 NETCONF/YANG 去配置和监控各网元。此外，O-RU 还通过 Open Fronthaul 的 M 平面被 NETCONF/YANG 直接管理。所以 NETCONF 在 O-RAN 里出现在两处：O1（对 CU/DU/RU）+ 前传 M 平面（对 RU）。详见 NETCONF 工程实践。

O1 不是一个协议，而是一组管理服务

O1 最容易被误解成「就是 NETCONF」。实际上它是按管理功能划分的一组服务，不同功能用了完全不同的协议，因为它们的数据形态与时间尺度根本不同：配置要求事务性与强一致，性能数据要求高吞吐与可批量，告警要求实时推送。用一个协议去覆盖三者是行不通的。

NETCONF Call Home 是个很好的加分细节。常规 NETCONF 是管理侧作为 SSH 客户端去连网元（网元开 830 端口）。但基站部署在站点侧，可能在 NAT 后、地址动态、且不希望对外开监听端口。Call Home 把 TCP 连接方向反转：网元上电后主动去连管理侧的 4334 端口，连上之后在这条 TCP 连接上仍然按「网元是 SSH 服务端」的角色跑 NETCONF。好处有三：网元不需要固定地址、不需要开入向端口（攻击面小）、以及「设备上电即自注册」这个即插即用体验。O-RU 的 M 平面用的就是这个模式。

<rpc message-id="103"><commit/></rpc>

上面那个 candidate → validate → commit 三步，是 O1 相对老一代管理接口（SNMP、厂商私有 CLI）最实质的改进：配置变更是一个事务，不是一串命令。老办法下「配了 5 条、第 3 条失败」会留下一个谁也说不清的中间状态；有了 candidate 库和 rollback-on-error，要么全生效要么全不生效。基站的小区参数动辄互相约束（带宽/SCS/TDD 配置/邻区），这种一致性不是锦上添花，而是自动化运维的前提——SMO 侧的意图闭环敢不敢自动下发配置，就取决于这一层保证。NETCONF 与 YANG 的机制细节看 NETCONF / YANG 基础，工程实践与踩坑看 NETCONF 工程实践。

O2：管的不是网元，是承载网元的那片云

O2：O-RAN 定义的 SMO ↔ O-Cloud 接口。O-Cloud 是承载 O-CU / O-DU（乃至 Near-RT RIC）的虚拟化/容器化基础设施——裸金属、加速卡、Kubernetes 集群。O2 被拆成两组逻辑服务：IMS（Infrastructure Management Services）管基础设施本身（资源清单、容量、告警、软件版本），DMS（Deployment Management Services）管网元的部署与生命周期（实例化、扩缩、升级、终止）。接口形态是 RESTful HTTPS。

O2 之所以必须存在，是因为解耦做到了「软硬件分离」这一层：O-DU 的软件可能来自 A 厂，跑在 B 厂的服务器 + C 厂的加速卡 + D 家的 Kubernetes 发行版上。SMO 要能自动化地问出「这片云上还有多少可用的 CPU、有没有支持某种指令集/加速卡的节点、把这个 O-DU 部到哪里」，就需要一个厂商中立的基础设施接口。这正好是 O1 覆盖不到的那一层——O1 管的是「网元里的无线参数」，O2 管的是「网元跑在什么上面」。

E2（近实时控制接口）

让 xApp 能真正"控制"RAN

  • 谁连谁：Near-RT RIC ↔ O-CU / O-DU（合称 E2 Node）。
  • 解决什么：近实时（10ms~1s）从 RAN 采集数据、并向 RAN 下发控制/策略，供 xApp 做闭环（切换、负载均衡、干扰、准入等）。
  • 机制：基于 E2 Service Model（E2SM），如 KPM（指标上报）、RC（RAN 控制）。
  • 属于：控制平面（近实时）。
  • 与 3GPP：O-RAN 新增，3GPP 没有对应接口。

E2AP 与 E2SM：为什么要分成两层

这是 E2 最重要的一个设计，也是面试里最能区分「用过」和「读过」的地方。E2 被刻意拆成两层：

E2AP（E2 Application Protocol）

信令的外壳：谁连谁、怎么建立关联、怎么发起一次订阅、怎么回一次上报、出错怎么报。它完全不理解无线语义——E2AP 里没有「PRB」「切换」这些概念。

相当于 HTTP：管请求/响应/状态码，不管你传的是图片还是 JSON。

E2SM（E2 Service Model）

装在 E2AP 消息里的载荷定义：具体上报哪些指标、控制哪个参数、事件触发条件怎么写。每个 E2SM 是一份独立规范，有自己的 OID 与版本。

相当于 HTTP 里的那个 JSON body 的 schema。

这么拆的收益是「加新功能不用改协议」：想让 xApp 控制一个新参数，只需要定义（或扩展）一个 E2SM，E2AP 一个字节都不用动，已有的关联、订阅机制全部复用。代价是多了一层版本协商——E2 节点在 E2 Setup 时声明「我支持哪些 RAN Function、每个对应哪个 E2SM 的哪个版本」，RIC 侧必须装有对应的解码器才能真正用起来。

E2SM全称 / 用途典型内容谁是 E2 节点侧的主要提供者
E2SM-KPMKey Performance Measurement：只读的指标上报PRB 利用率、吞吐、活跃 UE 数、切换成功率；支持小区级与 UE 级、周期性上报O-DU（MAC 层指标）、O-CU-CP（连接与移动性指标）
E2SM-RCRAN Control：可写的控制与策略切换控制、双连接/载波聚合配置、QoS 流映射、无线资源分配策略O-CU-CP、O-DU
E2SM-NINetwork Interface：把 RAN 接口消息本身暴露出来把 X2/Xn/F1/NG 上的消息内容作为上报载荷送给 RIC各 E2 节点
E2SM-CCCCell Configuration and Control：小区级配置的读写小区参数与配置结构的查询与修改O-DU、O-CU

POLICY下发一条持续生效的策略，之后由 RAN 自己按策略决策把策略装进本地逻辑，不再逐次上报切换门限、准入门限这类「设一次管很久」的参数

INSERT + CONTROL 的组合是 E2 最有杀伤力也最危险的能力，值得单独讲清。它把 RAN 的一个内部决策点「外包」给了 xApp：RAN 走到某个判断处停下来，把上下文发给 RIC，等 xApp 回一个决定再继续。

威力在于：不改基站软件就能替换掉一个算法。风险在于：你在实时控制路径里插进了一次网络往返 + 一个第三方程序。所以必须问三个问题——① 超时策略是什么（RIC 不回怎么办，必须能退回本地默认决策）；② 挂起期间的资源占用与并发上限是多少；③ xApp 崩溃或 E2 关联断开时，RAN 能不能干净地退化。一个连超时兜底都没有的 INSERT 型 xApp，是可以把整个小区拖垮的。这也是为什么现网里 REPORT 与 POLICY 型 xApp 遍地开花，而 INSERT 型极少见。

O1 与 E2 的职责边界：最容易混的一对

两者都能「改 RAN 的行为」，所以经常被问「为什么不用 O1 做就好」。判据有两条，缺一不可：

判据O1（管理面）E2（近实时控制面）
时间尺度秒 ~ 分钟。一次配置变更要经过事务校验、可能触发小区重配10 ms ~ 1 s。跟得上信道与负载的变化
是否持久化持久化。写进配置库，网元重启后仍然生效，是「真值」不持久化。关联断开或 xApp 下线后，行为回到配置库定义的基线
数据模型YANG 模型，声明式，描述「系统应该是什么样」E2SM，命令/事件式，描述「现在该做什么」
发起方SMO / 运维系统 / 意图闭环Near-RT RIC 里的 xApp
适合做小区规划参数、邻区关系、切片配额、告警门限逐 UE / 逐 TTI 附近的动态决策：负载均衡、干扰规避、切换目标选择
不适合做需要秒级响应的闭环——等你配置生效，负载高峰已经过去了需要长期生效的基线配置——会与配置库产生「配置漂移」
混淆边界的两个真实后果：
① 拿 O1 做实时闭环 → 追不上，还把配置库搅乱。见过的做法是 SMO 侧写个脚本，每 30 秒通过 O1 改一次切换门限。问题不只是慢：每次变更都是一次事务提交，配置库版本号疯涨，回滚基线彻底失去意义，网元侧还可能因为参数变更触发小区重配导致瞬时掉话。
② 拿 E2 做持久配置 → 「配置漂移」，故障时莫名恢复原状。xApp 通过 E2SM-RC/CCC 改了某个参数，但配置库里没有这条记录。之后任何一次网元重启、E2 关联重建、或 xApp 升级，参数就悄悄回到基线值。现象是「优化效果间歇性消失」，而运维系统里查不到任何变更记录——因为变更从来没进过配置库。

正确姿势：E2 负责在基线之上做短期偏移，O1 负责基线本身。如果某个 xApp 的偏移量长期稳定有效，应该由 SMO 侧的非实时闭环把它固化回 O1 的配置基线，而不是让它永远挂在 E2 上。O-RAN 后来定义 E2SM-CCC 让部分配置类操作也能走 E2，边界确实变模糊了——这时更要回到那两条判据（时间尺度 + 是否需要持久化）来判断。
真实案例形态：xApp 订阅成功但一条 Indication 都收不到。E2 关联 ESTABLISHED，RIC SUBSCRIPTION RESPONSE 里 Action 也在 Admitted 列表里，可就是没有数据。三个高频原因，按排查成本从低到高：① Event Trigger 的周期设得比 E2 节点支持的最小上报周期还短——有的实现会「接受订阅但静默不报」，而不是拒绝；② RAN Function ID 与 OID 对上了，但 RAN Function Definition 里声明的可用指标集合不含你请求的那几个，节点于是报了个空消息（看字节数就能发现）；③ RIC 侧路由问题——Indication 到了 RIC，但 RIC Request ID 与 xApp 注册的不一致，被 RIC 内部丢弃。判读入口是先在 E2 节点侧看「发出的 Indication 计数」：如果节点侧计数为 0，问题在订阅内容；如果节点在发而 xApp 收不到，问题在 RIC 内部路由。

A1（策略接口）

慢 RIC 给快 RIC 下策略

  • 谁连谁：Non-RT RIC（SMO 内）↔ Near-RT RIC。
  • 解决什么：Non-RT RIC 把策略/意图 + 富数据/AI 模型指导下发给 Near-RT RIC，指导 xApp 行为。
  • 时间尺度：非实时（≥1s）。
  • 属于：控制/管理平面（策略）。
  • 与 3GPP：O-RAN 新增。

A1 下的是「目标」，不是「动作」

A1 与 E2 的关键区别不在时延数字，而在语义层次：

  • E2 下发的是动作或短期策略：「把 UE-42 切到小区 7」「把这个小区的切换门限设为 −105 dBm」。
  • A1 下发的是目标与约束：「切片 S-NSSAI=0x01 的用户，P95 时延要压在 20 ms 以内」「这一批小区优先保吞吐而不是保覆盖」。怎么达成，A1 不管——由 Near-RT RIC 里的 xApp 自己去决定用什么算法、盯哪些指标、下什么 E2 控制。

生活类比：三级管理。O1 是人事与制度——岗位编制、办公场地、考勤规则，改一次要走流程（持久、慢、是真值）。A1 是季度 OKR——「本季度把客户满意度提到 90 分」，只给目标不给方法（非实时、声明式）。E2 是班组长的现场指挥——「你去接这个电话、你先处理那个投诉」（秒级以下、命令式、不留档）。三层各管一段，谁越界谁出问题：老板每 10 秒指挥一次具体动作，公司会瘫；班组长自己改编制，人事系统会乱。

A1 规范里定义了两类（另有一类曾作为研究项）服务：

判读要点：A1 的三个状态要分清 ——
  ① HTTP 状态码：请求格式/权限对不对
  ② 策略实例存在与否：RIC 有没有存下来
  ③ enforceStatus：**有没有 xApp 真的在按它工作**
  只看 ① 就以为"策略生效了"，是 A1 集成阶段最典型的误判。
「为什么要把策略与决策分成两层，而不是让一个大脑直接控制」——这是 RIC 架构的核心问题，答案有三条：
① 时间尺度不可兼得。要在 10 ms 内响应，就必须部署在靠近 RAN 的地方、用轻量逻辑、不能等外部数据；要用上历史数据与大模型做训练，就必然是分钟到小时级。把两者塞进一个组件，只能按最严的约束设计，于是复杂分析根本做不了。
② 训练与推理天然分离。非实时侧有全网数据和算力，负责训练与评估；近实时侧只做推理与执行。A1 就是这条「模型/策略投放」通道。
③ 故障域隔离。Non-RT RIC 挂了，Near-RT RIC 继续按最后一次收到的策略工作，RAN 不受影响；Near-RT RIC 挂了，RAN 退回自身基线逻辑。每一层失效都只损失一层能力，而不是整体不可用——这是把它做成三层而不是两层的真正理由。
A1 的落地陷阱集中在 policy type 的版本与归属。策略类型 ID 与它的 JSON Schema 是 Near-RT RIC 侧由 xApp 注册进来的，不是 A1 规范预先规定好的一张全局表。所以：① Non-RT RIC 下发一个没有任何 xApp 注册过的 policy type，会被直接 404；② xApp 升级时改了 schema（比如加了个必填字段），旧的策略实例会变成非法，而 enforceStatus 未必立刻反映出来；③ 多个 xApp 注册了同一个 policy type 时，谁执行、会不会互相打架，规范层面并不替你解决。所以生产环境必须有一条纪律：策略类型的 schema 变更要当作接口变更来管，走版本号而不是原地改。

另一种归类：按时间尺度排一排

按平面归类是规范的说法，但工程上更有解释力的是按时间尺度排序——因为时间尺度直接决定了技术选型，而且它解释了「为什么不能合并成一个接口」。

这张表其实回答了一个更一般的工程问题：「什么时候用二进制协议，什么时候用 JSON/REST」。分界线不是「谁更现代」，而是时延预算与消息频次。毫秒级、每秒上万条的接口用 ASN.1；秒级、每分钟几条的接口用 REST + JSON——后者省下的是人的时间（可读、可 curl、可用现成工具链），而这在运维面比 CPU 周期值钱。O-RAN 新增的四个接口正好横跨这条分界线两侧：E2 选了 ASN.1，A1/O2 选了 REST，这不是不统一，是各自选对了。

串起来：一条用户数据从 UE 到互联网穿过哪些接口

这是本篇最好的自测题。把它答完整，前面所有接口的位置关系就都对上了。

上行方向：UE 打开一个网页，数据包的完整旅程

 ① UE ──Uu 空口（3GPP）──► O-RU
      形态：射频信号。UE 的 IP 包已经被 SDAP/PDCP/RLC/MAC 层层封装并调制。

 ② O-RU ──Open Fronthaul U 平面（O-RAN）──► O-DU
      形态：**频域 IQ 采样**，装在 eCPRI over Ethernet 里。
      ⚠ 注意：这一段里**根本没有 IP 包这个概念** —— O-RU 只做 Low-PHY，
         它看到的是复数采样点，看不到"数据包"。这是最容易讲错的一环。

 ③ O-DU 内部：High-PHY 解调 → MAC 解复用 → RLC 重组
      到这里才第一次出现"一个完整的 PDCP PDU"。

 ④ O-DU ──F1-U（3GPP，GTP-U/UDP/IP）──► O-CU-UP
      形态：PDCP PDU 封在 GTP-U 隧道里，TEID 标识是哪个 DRB。
      同时 O-DU 会在 NR RAN Container 里回报送达状态（TS 38.425）。

 ⑤ O-CU-UP 内部：PDCP 解密与完整性校验 → 重排序 → SDAP 去头
      到这里才还原出 **UE 原始的那个 IP 包**。

 ⑥ O-CU-UP ──NG-U / N3（3GPP，GTP-U/UDP/IP）──► UPF
      形态：UE 的 IP 包重新封进另一条 GTP-U 隧道，
            PDU Session Container 里带 QFI 标明它属于哪条 QoS 流。

 ⑦ UPF ──N6──► 互联网
      形态：UPF 解掉 GTP-U 头，做 NAT / 计费 / 策略执行，
            **UE 的 IP 包第一次以裸包形态出现在传输网上**。

 ═══ 全程用户数据穿过的接口：Uu → Open FH → F1-U → NG-U → N6 ═══
     三段隧道/封装：eCPRI（IQ）、GTP-U（F1-U，PDCP PDU）、GTP-U（NG-U，IP 包）

   NG-C   O-CU-CP ↔ AMF      UE 注册、鉴权、PDU 会话建立，拿到 UPF 的隧道端点
   E1     O-CU-CP ↔ O-CU-UP  让 CU-UP 建 Bearer Context，拿到它的两个隧道端点
   F1-C   O-CU-CP ↔ O-DU     建 UE Context，交换 F1-U 的两个隧道端点
   Open FH C/S/M 平面        让 O-RU 有正确的时钟与载波配置，能收发这个 slot

   E2 / A1                   在这一切之上，动态优化调度与切换决策
面试里被问这道串联题时，能主动指出「Open Fronthaul 上传的不是 IP 包而是 IQ 采样」的人非常少，这一句几乎能决定这道题的评分。很多人会把前传描述成「数据包从 RU 传到 DU」，那是 CPRI/eCPRI 之上一个错误的心智模型——拆分点在 7-2x，意味着物理层是被切开的，接口上流动的是物理层中间量，不是任何一层的数据包。顺着这一点还能补一句有分量的推论：正因为传的是 IQ 而不是包，前传才没有重传、没有拥塞控制，也才必须靠时钟同步和硬时延窗口来保证正确性。
🎯 本篇要点回顾
  • 定义方分野：F1 / E1 / NG / Xn / Uu 是 3GPP 的，O-RAN 原样复用；Open FH / O1 / O2 / E2 / A1 是 O-RAN 定义的（Open FH 基于 3GPP 的 7-2x 拆分点）。
  • 命名规律：3GPP 接口带 -C / -U 后缀，是两条独立 IP 流；E1 只有控制面；O-RAN 接口不拆后缀，唯独前传一个接口内含四平面。
  • 两条共性技术：信令面清一色 ASN.1 + SCTP（多流免队头阻塞、多归属故障切换、保留消息边界）；用户面清一色 GTP-U over UDP（TEID 由接收方分配，解决移动性、会话标识、地址隔离）。
  • 时延分档：Open FH ~100 µs → F1/E1/NG/Xn 毫秒 → E2 10 ms–1 s → A1 >1 s → O1/O2 秒到分钟。分档决定技术选型（二进制 vs REST）。
  • 易混的两对：O1（持久化基线配置，慢）vs E2（不持久化的短期偏移，快）；O1（管网元）vs O2（管承载网元的云）。
  • 生产陷阱：ASN.1 的 criticality 决定跨版本兼容行为；SCTP 多归属在有状态中间设备与容器环境里常常形同虚设；GTP-U 的 MTU 开销导致「小包通大包丢」。
  • Open Fronthaul ≠ eCPRI；NETCONF/YANG 出现在 O1 + 前传 M 平面两处。

  1. 基础F1-C 与 F1-U 有什么区别？

    它们是 F1 接口的两条逻辑独立的通道，连接的网元、协议、传输层、可靠性来源全都不同。

    • F1-C：O-CU-CP ↔ O-DU，承载 F1AP（TS 38.473，ASN.1 PER 编码），跑在 SCTP 上（端口 38472）。做的是 UE 上下文管理、承载建立、以及把 RRC 消息当容器透传。每个 O-DU 与 CU-CP 之间只有一条长期保持的 SCTP 关联，所有 UE 的信令在里面按 stream 分流。
    • F1-U：O-CU-UP ↔ O-DU，承载 PDCP PDU，用 GTP-U 隧道跑在 UDP 2152 上，并在 GTP-U 扩展头里带 TS 38.425 的 NR 用户面协议做流控与送达状态反馈。每个 DRB 一对隧道，随 UE 建立与释放。

    可靠性来源的差别值得单独说：F1-C 的可靠性来自 SCTP 自身的重传与拥塞控制；F1-U 跑在不保证送达的 UDP 上，丢包由 PDCP 层的 ARQ 与重排序兜住，用户侧只表现为时延毛刺。

    加分：两条通道在分离架构里连的是不同网元（一个到 CU-CP，一个到 CU-UP），这正是需要 E1 接口的原因。而且它们通常走不同 VLAN / 不同 QoS，所以现场会出现「注册成功但没流量」这种只有一条通道坏了的症状。

  2. 基础NG-C 与 NG-U 分别连到核心网的哪个网元？
    • NG-C（也叫 N2）→ AMF（Access and Mobility Management Function）。协议是 NGAP（TS 38.413）over SCTP，端口 38412。承载 UE 注册、鉴权与 NAS 透传、PDU 会话资源建立、切换、寻呼，以及接口级的 NG Setup。
    • NG-U（也叫 N3）→ UPF（User Plane Function）。协议是 GTP-U（TS 29.281）over UDP 2152，并用 PDU Session Container 扩展头逐包携带 QFI。承载用户的 IP 报文。

    两个要点：① 在 CU/DU 分离架构里，NG 终结在 CU 上——NG-C 在 O-CU-CP，NG-U 在 O-CU-UP，DU 与 RU 完全看不到 NG。② NG-C 上的 NAS 消息对 RAN 是不透明容器，基站只负责在 RRC 与 NGAP 之间搬运，看不到鉴权向量与 NAS 加密内容——安全边界就划在这里。

    常见混淆：把 N4（SMF ↔ UPF，用 PFCP）也算进 RAN 侧接口。N4 是核心网内部接口，与基站无关。

  3. 基础Open Fronthaul 是谁定义的？它和 3GPP 是什么关系？

    Open Fronthaul 是 O-RAN 联盟（WG4）定义的，不是 3GPP 定义的，但它建立在 3GPP 的研究成果上。准确的说法是：「O-RAN 定义，基于 3GPP 的 7-2x 拆分点」。

    展开这个关系：3GPP 在 CU/DU 功能拆分的研究里列出了 Option 1~8 一系列候选拆分点（相关研究见 TR 38.816 等），但只把 Option 2（即 F1 接口）标准化成了正式接口，物理层内部的 7-2x 只停留在研究阶段——3GPP 没有为它定义可互操作的接口规范。O-RAN WG4 补上了这一块：报文结构、C/U/S/M 四个平面、时延窗口、YANG 管理模型、以及互操作测试规范。

    所以对比记忆：F1 / E1 / NG / Xn 是 3GPP 定义、O-RAN 原样复用；Open Fronthaul / O1 / O2 / E2 / A1 是 O-RAN 定义，其中只有 Open Fronthaul 与 3GPP 有这层「拆分点来自 3GPP」的渊源。

    再加一句能拉开差距的：Open Fronthaul ≠ eCPRI。Open Fronthaul 是接口规范，eCPRI（由 CPRI 合作组织定义）只是它 C/U 平面的承载协议之一；S 平面用 PTP、M 平面用 NETCONF/YANG，都不是 eCPRI。

  4. 基础O1 与 O2 有什么区别？

    都是 SMO 发起的管理接口，但管的对象层次不同：

    • O1：管网元。SMO ↔ O-CU / O-DU / O-RU / Near-RT RIC。做 FCAPS——配置（NETCONF/YANG，有事务语义）、故障与性能（VES 事件 + 批量 PM 文件）、软件与文件管理。典型动作是「把小区 3 的下行功率调低 2 dB」。
    • O2：管承载网元的那片云。SMO ↔ O-Cloud。分成 IMS（基础设施管理服务：资源清单、容量、节点与加速器、基础设施告警）与 DMS（部署管理服务：网元实例化、扩缩、升级、终止），接口形态是 RESTful HTTPS。典型动作是「在有加速卡的节点上再起两个 O-DU 实例」。

    一个好用的判据：「把网元从一台服务器迁到另一台，谁负责？」——O2。迁完之后重新下发小区参数？——O1。顺序也是这个：先 O2 把实例拉起来，再 O1 把它配成一个能提供服务的基站。

    加分：指出 O2 的存在前提是「软硬件解耦」——O-DU 软件、服务器、加速卡、Kubernetes 发行版可能来自四家厂商，SMO 需要一个厂商中立的基础设施接口。并可以补一句工程现实：O2 的资源事件与 O1 的网元告警来自两套数据模型，不做关联的话值班人员会把资源问题误判成无线故障。

8.2 中级（区分熟练度）

  1. 中级E1 接口是干什么的？为什么需要它？

    E1 是 gNB-CU-CP 与 gNB-CU-UP 之间的接口，协议是 E1AP（TS 38.463）over SCTP（端口 38462）。它是纯控制面接口，永远不承载用户数据——职责就是让 CU-CP 去指挥 CU-UP 建立、修改、释放 Bearer Context。

    为什么需要它，两条理由：

    • CP 与 UP 要独立扩容。控制面负载正比于信令事件数，用户面负载正比于比特数，两者的比例在不同场景下差好几个数量级：物联网小区是「海量连接、极低吞吐」（CP 重），热点小区是「几十用户、跑满带宽」（UP 重）。做成两个可分别部署与扩容的网元是云化 RAN 的前提，而拆开就必须有接口。
    • 用户面下沉。CU-UP 可以部署到靠近基站的边缘机房以降低时延（MEC），CU-CP 集中在区域中心。这只有 CP/UP 分离后才做得到。

    核心过程是 BEARER CONTEXT SETUP / MODIFICATION / RELEASE，另有 BEARER CONTEXT INACTIVITY NOTIFICATION（用户面发现长时间无数据，通知 CP 去做 RRC 释放或挂起）。

    加分点是把隧道端点的流转讲清楚：CU-CP 是唯一的信息中枢，自己不碰任何用户数据，但所有隧道端点都要经它转手。UPF 的端点经 NG-C 进来、经 E1 递给 CU-UP；CU-UP 的两个端点经 E1 出来，一个经 NG-C 回给 5GC、一个经 F1-C 递给 DU；DU 的端点经 F1-C 上来、经 E1 递给 CU-UP。四个网元、三个接口、六次端点交换，一处配错就是单向不通。

  2. 中级为什么 3GPP 的信令面统一用 SCTP，而不是大家更熟悉的 TCP？

    因为 TCP 的三个语义特征恰好都不适合电信信令面，而 SCTP 是为信令面定制的（它出自 SIGTRAN 项目，目标就是把 SS7 信令搬到 IP 网上）。

    • TCP 是单一有序字节流 → 队头阻塞。一台 O-DU 上可能有上千个 UE 同时在接入/切换/释放。挤在一条 TCP 连接里时，任何一个报文段丢失都会把其后所有 UE 的信令扣在接收缓冲里，而一个 RTO 是秒级的——这期间所有 UE 的状态机都在等，然后大面积超时失败。
    • TCP 连接绑死四元组 → 换 IP 就是换连接。信令面需要在一条链路/网卡失效时不中断，TCP 只能重建连接、重建上下文。
    • TCP 是字节流 → 需要额外帧定界。F1AP / NGAP 的 ASN.1 PER 编码结果本身不带长度字段，跑在 TCP 上就必须在协议之外再套一层带长度的公共头（M3UA 时代就是这么做的）。

    对应地，SCTP 用多流、多归属、面向消息三个能力把这三点都消掉了，所以 3GPP 在 F1-C、E1、NG-C、Xn-C 上一律规定用 SCTP，O-RAN 的 E2 也跟着用。

    要显得真做过，可以补一句反面：SCTP 的代价是中间设备友好度极差——NAT、有状态防火墙、云上的四层负载均衡多数不支持它，Kubernetes 的默认 CNI 与 Service 对 SCTP 支持也有限。这是它在云原生环境里最大的落地阻力。

  3. 中级用户面为什么要再套一层 GTP-U 隧道？TEID 是谁分配的？

    UE 已经有 IP 地址了，但直接路由不行，三个理由缺一不可：

    • 移动性 / 会话连续性。UE 的 IP 锚定在 UPF 上。若靠路由把流量引到当前基站，就要为每个终端在传输网里注入一条主机路由并在切换时收敛——百万级路由表，且收敛远慢于切换。套隧道后换基站只是换隧道端点，UE 的 IP 一位都不用变。
    • 会话与 QoS 标识。裸 IP 包里没有字段能表达「这属于哪个 PDU 会话的哪条 QoS 流」。TEID 标识隧道（≈ 会话/承载），扩展头里的 QFI 标识流，转发面据此做限速、调度、计费。
    • 地址空间隔离。UE 地址属于 N6 侧的用户地址空间（大量私网与重叠地址），在 RAN 传输网里不可路由也不应可路由。传输网只需知道 gNB 与 UPF 的地址，规模从「终端数」降到「网元数」。

    TEID 是 32 位，由「接收方」分配，然后通过信令告诉发送方「往这个 TEID 发」。所以一条隧道的两个方向用的是两个毫不相关的 TEID 值，各自只需在本端唯一。具体地：F1-U 上，CU-UP 的接收端点通过 F1AP 的 UL UP TNL Information 给 DU，DU 的接收端点通过 DL UP TNL Information 回给 CU；NG-U 上，UPF 的端点在 PDU SESSION RESOURCE SETUP REQUEST 里下来，CU-UP 的端点在 Response 里上去。

    加分：TEID 配反或对端未开的现象是「单向不通」，抓包能看到报文到了对端却被静默丢弃，判读入口是接收侧的「unknown TEID」计数器。另外别忘了 MTU：外层 IPv4 20 + UDP 8 + GTP-U 8（带扩展头再 +8）合计 36~44 字节，不处理就会「小包通、大包丢」（ping 通但 HTTPS 握手失败），处置优先级是传输网开 jumbo frame > 通告给 UE 的 MTU 减掉开销 > TCP MSS clamping 兜底。

  4. 中级Xn 接口用在什么场景？没有它会怎样？

    Xn 是 gNB ↔ gNB 的横向接口（TS 38.420 系列），Xn-C 跑 XnAP over SCTP（端口 38422），Xn-U 跑 GTP-U。在分离架构里同样终结在 CU 上。它的意义是让「相邻两个基站之间的事」不必绕核心网。四类用途：

    • Xn 切换：源站直接向目标站发 HANDOVER REQUEST（带 UE 上下文与安全参数），目标站预留资源后回 ACK，切换完成再通过 NG-C 通知 AMF 换路径。没有 Xn 就退化成 NG 切换——所有信令绕 AMF 一圈，中断时间明显变长。
    • 数据前转：Xn-U 上建临时隧道，把源站缓存里还没发完的下行数据转给目标站。没有它，切换瞬间的在途数据丢失，TCP 会看到重传甚至窗口塌陷。
    • 双连接（NR-DC / EN-DC 的 NR 侧）：主节点向辅节点请求增删辅小区组、协商承载分流。没有它就做不了多站点聚合。
    • RAN 寻呼与资源协调：RRC_INACTIVE 的 UE 在 RAN 通知区内被寻呼；相邻站协调 TDD 配置与干扰。

    加分：辨析 Xn 与 E2 在负载均衡上的分工。Xn 上的资源状态交换是「两个基站之间的双边协商」，为的是完成一次具体的切换或双连接；E2 上的上报是「多个基站向一个集中大脑汇报」，为的是让 xApp 做全局决策。两者并存：xApp 经 E2 看到某小区过载、下发策略调整切换门限，实际的切换动作仍然走 Xn 完成。

8.3 高级（体现深度）

  1. 高级说出 SCTP 相对 TCP 的三个优势，并说明各自的限度。

    ① 多流（multi-streaming）：一条关联内多条逻辑流，流与流之间的交付顺序互不相干。丢一个包只阻塞它所在的那条流，不会把别的流一起扣住。3GPP 各接口的用法是 非 UE 关联信令固定走一条流（实现上普遍是 stream 0），UE 关联信令按 UE 散列到其它流上——这样一个 UE 的信令卡住不会波及其它 UE，接口级过程之间又保住了顺序；流数在 INIT 里协商（OS / MIS），实际可用数是 min(本端 OS, 对端 MIS)，双向可以不对称。

    限度（这一点最能拉开差距）：多流只解耦了「向上层交付的顺序」，没有解耦「拥塞控制与重传」——拥塞窗口、RTO、SACK 都是每关联一份的。链路真丢包时整条关联的发送速率都会降，只是接收侧不会因等一个包而全扣住。想连拥塞控制也隔离，得建多条关联。另外，流数配得太少是隐性故障：协议栈会把多个 UE 挤进同一条流，多流的好处直接消失。

    ② 多归属（multi-homing）：每端可绑多个 IP，主路径失效时切到备份，关联不断。靠周期性 HEARTBEAT 探活，上层完全不感知，UE 上下文不用重建。这是把故障切换下沉到传输层，不依赖任何网络侧机制。

    限度：现网里它经常形同虚设。（a）两个地址如果配在同一块网卡/同一 VLAN/同一台接入交换机上，故障域根本没分开；（b）多归属要求四种「源地址 × 目的地址」组合都可达，工程上常只测了主-主一条，Linux 的 rp_filter=1 会按路由表校验源地址直接丢包；（c）有状态防火墙看到 INIT 声明之外的源地址就丢，NAT 基本不支持多归属，云上四层负载均衡多数只支持 TCP/UDP。所以相当多的现网索性用单归属 SCTP + IP 层冗余（BFD + 动态路由 / VRRP）——这是正当的工程选择。容器化后更严峻：Pod 通常只有一个 IP，多归属基本无从谈起。

    ③ 面向消息，保留消息边界：send 一次、recv 到完整一条，应用不用处理粘包半包。对 ASN.1 PER 尤其重要——PER 编码结果不带长度字段，跑 TCP 就必须额外套一层帧定界。附带能力是逐消息可选无序交付，心跳类消息不必排队。

    限度：消息过大时 SCTP 仍要分片，且要依赖路径 MTU 发现；PMTUD 被防火墙挡住时，大消息（比如带整份系统信息的 F1 Setup）会被静默丢弃。

    再补一个常被忘记的第四点：四次握手 + State Cookie 让服务端在验证 Cookie 之前不分配 TCB，天然抗 SYN 洪泛式攻击，这对暴露给成千上万个基站的信令面很有价值。

    最后一条工程不变式值得主动提：Association.Max.Retrans 必须明显大于 Path.Max.Retrans，否则主路径刚被判死、还没切到备份，整条关联就先 ABORT 了——花钱买的双归属一次都没生效过，现象还是「偶发接口闪断」，极难定位。

  2. 高级E2 与 A1 的时延分档分别是多少？这个分档为什么必须存在？

    E2 是 10 ms ~ 1 s（近实时），A1 是 > 1 s（非实时），再往上 O1/O2 是秒到分钟级。作为对照，另一端的 Open Fronthaul 是 ~100 µs 量级，F1/E1/NG/Xn 是毫秒量级。

    但真正要答的是「为什么不能合成一层」，理由有三条：

    • 时间尺度不可兼得。要在 10 ms 内响应，就必须部署在靠近 RAN 的地方、跑轻量逻辑、不能等外部数据；要用上全网历史数据与大模型做训练，就必然是分钟到小时级。塞进一个组件只能按最严的约束设计，于是复杂分析根本做不了。
    • 训练与推理天然分离。非实时侧有全网数据与算力，负责训练与评估；近实时侧只做推理与执行。A1 就是「策略/模型投放」这条通道。
    • 故障域隔离。Non-RT RIC 挂了，Near-RT RIC 按最后收到的策略继续工作；Near-RT RIC 挂了，RAN 退回自身基线逻辑。每层失效只损失一层能力，而不是整体不可用。

    语义层次上的差别同样要说清：A1 下发的是目标与约束（「这个切片的 P95 时延压在 20 ms 内」），怎么达成不管；E2 下发的是动作或短期策略（「把 UE-42 切到小区 7」「把切换门限设为 −105 dBm」）。

    加分点：A1 的「下发成功 ≠ 生效成功」。PUT 策略实例返回的是 202 Accepted，必须再查 status 的 enforceStatus 才知道有没有 xApp 真的在按它工作——最常见的失败就是没有任何 xApp 注册过这个 policy type。只看 HTTP 状态码就以为策略生效，是 A1 集成阶段最典型的误判。

  3. 高级E2SM 是什么？为什么要把它和 E2AP 分成两层？

    E2SM（E2 Service Model）是「装在 E2AP 消息里的载荷定义」：具体上报哪些指标、控制哪个参数、事件触发条件怎么写。每个 E2SM 是一份独立规范，有自己的 OID 与版本。而 E2AP 只管信令外壳——建立关联、发起订阅、回上报、报错——它完全不理解无线语义，里面没有「PRB」「切换」这些概念。类比：E2AP 是 HTTP，E2SM 是 body 的 schema。

    主要的 E2SM：E2SM-KPM（只读指标上报：PRB 利用率、吞吐、活跃 UE 数、切换成功率，支持小区级与 UE 级）、E2SM-RC（RAN Control，可写：切换控制、双连接/载波聚合、QoS 流映射、资源分配策略）、E2SM-NI（把 RAN 接口上的消息本身作为载荷暴露出去）、E2SM-CCC（小区配置的读写）。

    分层的收益是「加新功能不用改协议」：想让 xApp 控制一个新参数，只需定义或扩展一个 E2SM，E2AP 一个字节不动，已有的关联与订阅机制全部复用。代价是多了一层版本协商——E2 节点在 E2 SETUP REQUEST 里声明 RAN Function 列表（每项含 ranFunctionID、ranFunctionOID、以及描述可用能力的 ranFunctionDefinition），RIC 侧必须装有对应 SM 的解码器才能真正用起来。OID 或版本对不上，xApp 就订阅不了。

    再往深一层，可以讲订阅里的 Action Type：REPORT（只上报，不影响 RAN 行为）、INSERT（上报并挂起正在进行的 RAN 过程，等 RIC 发话）、POLICY（下发持续生效的策略，之后 RAN 自己决策），加上独立的 RIC CONTROL 过程。INSERT + CONTROL 是最有杀伤力也最危险的组合——它把 RAN 的一个内部决策点外包给了 xApp，威力是「不改基站软件就能替换一个算法」，风险是「你在实时控制路径里插了一次网络往返 + 一个第三方程序」。所以必须问清超时兜底、挂起并发上限、以及 xApp 崩溃时能否干净退化。没有超时兜底的 INSERT 型 xApp 可以把整个小区拖垮，这也是现网里 REPORT 与 POLICY 型遍地、INSERT 型极少见的原因。

  4. 高级一条用户数据从 UE 到互联网，要穿过哪些接口？每一段的数据形态是什么？

    按上行方向串一遍，重点是每一段的数据形态而不只是接口名：

    1. UE → O-RU：Uu 空口（3GPP）。形态是射频信号，UE 的 IP 包已经被 SDAP/PDCP/RLC/MAC 层层封装并调制。
    2. O-RU → O-DU：Open Fronthaul U 平面（O-RAN）。形态是频域 IQ 采样，装在 eCPRI over Ethernet 里。这一段根本没有「IP 包」这个概念——O-RU 只做 Low-PHY，看到的是复数采样点。
    3. O-DU 内部：High-PHY 解调 → MAC 解复用 → RLC 重组，到这里才第一次出现一个完整的 PDCP PDU。
    4. O-DU → O-CU-UP：F1-U（3GPP，GTP-U/UDP/IP）。形态是 PDCP PDU 封在 GTP-U 隧道里，TEID 标识是哪个 DRB。
    5. O-CU-UP 内部：PDCP 解密与完整性校验 → 重排序 → SDAP 去头，到这里才还原出 UE 原始的那个 IP 包。
    6. O-CU-UP → UPF：NG-U / N3（3GPP，GTP-U/UDP/IP）。UE 的 IP 包重新封进另一条 GTP-U 隧道，PDU Session Container 里带 QFI。
    7. UPF → 互联网：N6。UPF 解掉 GTP-U 头、做 NAT/计费/策略执行，UE 的 IP 包第一次以裸包形态出现在传输网上。

    所以答案是：Uu → Open Fronthaul → F1-U → NG-U → N6，中间经历三段封装：eCPRI（IQ）、GTP-U（F1-U，装 PDCP PDU）、GTP-U（NG-U，装 IP 包）。

    还要补上「这条路是怎么建起来的」——以下接口全都不承载用户数据：NG-C 完成 UE 注册与 PDU 会话建立并拿到 UPF 的隧道端点；E1 让 CU-UP 建 Bearer Context 并交出它的两个端点；F1-C 建 UE Context 并交换 F1-U 的两个端点；Open Fronthaul 的 C/S/M 平面保证 O-RU 有正确的时钟与载波配置；再往外是 O1/O2（把网元部署好配置好）与 E2/A1（动态优化）。

    这道题的评分点几乎全在第 2 步。很多人会把前传描述成「数据包从 RU 传到 DU」，那是错误的心智模型：拆分点在 7-2x 意味着物理层被切开，接口上流动的是物理层中间量，不是任何一层的数据包。顺着还能补一条有分量的推论：正因为传的是 IQ 而不是包，前传才没有重传、没有拥塞控制，也才必须靠时钟同步与硬时延窗口来保证正确性。
