O-RAN 接口：Open Fronthaul / O1 / E2 / A1 / F1

把接口集中讲，避免一个接口一篇造成碎片化。每个接口只需回答四问：谁连谁？解决什么？属于哪个平面？和 3GPP 是什么关系？特别澄清一个高频误区：Open Fronthaul ≠ eCPRI。

01

接口全景

一张连线图定位所有接口

基站被拆成 O-CU / O-DU / O-RU 三块、再挂上 RIC 与 SMO 之后，真正决定这套系统能不能多厂商拼装的不是网元本身，而是网元之间那些接口——内部怎么实现是厂商私事，只要对外行为与规范一致就能被替换。于是「O-RAN 是什么」最终归约成「它定义了哪些接口，每个接口约束了什么」。

生活类比：公司之间的合同。一家公司内部怎么开会、用什么 ERP，外人管不着；但它和上游供应商之间的合同——交付什么、什么格式、多久之内、怎么验收——一旦写死，供应商就是可替换的。接口就是网元之间的合同。CPRI 时代的问题不是没有合同，而是每家的合同都自己写、条款还不公开，于是买了谁的 DU 就只能买谁的 RU。

本篇把 9 个接口逐个讲清四件事：连接哪两个网元、承载什么、协议栈怎么分层、由谁定义。判断接口「性格」的经验规则是看时延预算：100 µs 级的一定是 FPGA 参与的以太网直连，秒级的一定是 HTTP/JSON——差 4 个数量级，选型没有共同点。

全景图：谁连谁，谁定义的

图里 E2 节点那个虚线框有讲究：E2 不是「RIC 连到基站」这么笼统，而是分别与 O-CU-CP、O-CU-UP、O-DU 各建一条关联。每条关联独立声明自己支持哪些 RAN Function——O-DU 报得出 MAC 调度与 PRB 占用，O-CU-CP 报得出 RRC 连接数与切换事件，两者不能互相替代。

命名规律：为什么有的接口带 -C / -U 后缀

3GPP 的习惯是一个接口名 + 平面后缀：控制面加 -C、用户面加 -U。这不只是命名区分——两者在实际网络里是两条完全独立的 IP 流，可以走不同的 VLAN、QoS 与物理路径。O-RAN 新增的接口不带后缀，因为各自只有单一用途。

这条规律有个非常实用的排障推论：「注册成功但没有流量」几乎一定是 -U 面的问题，「完全接不上」才是 -C 面的问题。UE 进得了 RRC_CONNECTED、核心网看得到会话建立，说明 F1-C / NG-C / E1 全通；此时数据不走就去查 GTP-U 路径——三个高频原因：MTU 不够、TEID 配错或对端未开、承载 -U 面的 VLAN 没打通。

02

Open Fronthaul（前传接口）

O-RAN 最标志性的开放接口

Open Fronthaul：O-RAN 定义的 O-DU ↔ O-RU 开放前传接口规范（基于 3GPP 7-2x 拆分），规定了前传上的 C / U / S / M 四个平面，其中 C/U 平面用 eCPRI over Ethernet 承载。
关键澄清：Open Fronthaul ≠ eCPRI。层次关系是 O-RAN → Open Fronthaul（接口规范）→ eCPRI / Ethernet（承载）：前者规定 O-DU 与 O-RU 之间该有哪些平面、消息、时序与管理模型，后者只是它 C/U 平面所用的承载协议之一。Open Fronthaul 还定义了 eCPRI 之外的东西——S 平面的同步 profile、M 平面的 YANG 模型、以及 U/C 平面之上的 O-RAN 专有 section 扩展。

协议栈：唯一一个不跑在 IP 上的接口

它的协议栈和本篇其它接口都不一样：C/U 平面默认没有 IP 层，也没有 TCP/UDP。eCPRI 直接坐在以太网帧上（EtherType 0xAEFE），靠 VLAN 标签与 PCP 优先级做隔离和调度。

规范上 eCPRI 也允许 UDP/IP 承载，O-RAN 还并列允许 IEEE 1914.3（RoE），但实际部署几乎清一色是「eCPRI over Ethernet」。为什么前传不用 IP：① 单向只有百微秒，时延预算不允许 IP 转发与可能的分片重组；② O-DU 与 O-RU 之间是点到点或经一台交换机，不需要路由；③ eCPRI 头只有 4 字节固定字段，FPGA 能按固定偏移线速解析。逐字节结构见 eCPRI Header。

时延预算：100 µs 这个数是怎么来的

「单向 100 µs 量级」不是拍出来的，而是从空口 HARQ 时序倒推的：UE 要在规定的 slot 里回 HARQ 反馈，而处理反馈的 MAC 调度器在 O-DU 里——「下命令 → 发射 → UE 处理 → 回传 → O-DU 拿到」这一整圈必须塞进 HARQ 预算，前传占掉的那两段就被挤到了百微秒。

互操作的真实难点：Category 与 section 扩展

「有了规范就能互通」是最大的误解。规范里有大量可选能力，两端支持的子集不一致就是配不通：

可选点含义不匹配的后果

被问「Open Fronthaul 和 CPRI 的本质区别」，别停在「一个开放一个私有」，要答出数据形态变了：CPRI 传时域采样，带宽只跟采样率与天线数相关，空载也占满；7-2x 之后传频域采样，只传实际被调度的 PRB，带宽随负载变化，还能压缩。这才是前传带宽从「几十 Gbps 固定」变成「可统计复用」的根本原因。
03

F1（中传接口）

这是 3GPP 的接口，O-RAN 复用

F1 连接 O-CU 与 O-DU（对应 Option 2 拆分），承载在 Midhaul 上，含 F1-C 与 F1-U。它是 3GPP 定义的，O-RAN 直接复用而不是新造——能主动指出这点是加分项。

这一章顺带把 E1、NG、Xn 一起讲完，因为它们共享同一套工程语言——控制面一律是 ASN.1 应用协议跑在 SCTP 上，用户面一律是 GTP-U 跑在 UDP 上，学会读一个，剩下三个只是消息名不同。后半段专门拆这两条共性：为什么信令面选 SCTP、GTP-U 为什么要多套一层隧道。

F1-C 与 F1-U：两条独立的通道

两者物理上可以走同一根光纤，逻辑上完全独立。数量关系先记住：F1-C 每个 O-DU 只有一条 SCTP 关联，所有 UE 的信令按 stream 分流；F1-U 每个 DRB 一对隧道，所以一台 DU 上的隧道数是「UE 数 × 平均 DRB 数」量级。

F1AP 的典型过程

F1AP 的消息分两类，这个二分法是读懂所有 3GPP 应用协议的钥匙：

  • 非 UE 关联：与具体终端无关的接口建立、小区激活、系统消息更新。这类信令固定走同一条流（实现上普遍是 stream 0），以保证接口级过程之间的顺序。
  • UE 关联：针对某一个终端，靠一对 ID 定位上下文——gNB-CU UE F1AP ID 与 gNB-DU UE F1AP ID。两端各自分配、各自维护映射表，每条消息都要同时带上两个 ID，接收方才知道自己这边是哪个上下文。

TEID 是「接收方分配、告诉发送方」的。④ 里 CU 给出的 UL UP TNL Info 是 CU-UP 自己的接收端点，意思是「上行数据发到这里来」；⑤ 里 DU 给出的 DL UP TNL Info 是 DU 自己的。这个方向很容易记反，后果非常典型：一端能通、另一端不通，抓包看到 GTP-U 报文到了对端却被静默丢弃（TEID 在对端隧道表里查不到）。判读方法是在接收侧看「unknown TEID」计数器。

E1：CU 内部的那条线

E1：3GPP 定义的 gNB-CU-CP ↔ gNB-CU-UP 接口，应用协议 E1AP（TS 38.463），跑在 SCTP 38462 上。纯控制面，永远不承载用户数据——唯一职责是让 CU-CP 指挥 CU-UP 建立、修改、释放承载上下文。

E1 存在的理由是 CU 的控制面与用户面要独立扩容：前者的负载正比于信令事件数，后者正比于比特数，两者的比例在不同场景下差好几个数量级——物联网小区海量连接却吞吐极低，热点小区几十个用户就跑满带宽。拆开就必须有接口。另一个动力是用户面下沉：CU-UP 可以放在边缘机房降时延，CU-CP 仍集中在区域中心。

E1 上的过程不多：E1 SETUP 建接口并交换 CU-UP ID 与支持的 PLMN/切片；BEARER CONTEXT SETUP / MODIFICATION 建改承载上下文，携带 PDCP 密钥、QoS Flow→DRB 映射与各段隧道端点；BEARER CONTEXT INACTIVITY NOTIFICATION 把「长时间无数据」告诉控制面去做 RRC 释放。真正难讲清的是最后一件——隧道端点怎么在四个网元之间互相喂过去：

为什么信令面用 SCTP 而不是 TCP

SCTP（RFC 4960，已由 RFC 9260 取代）：与 TCP 平级的可靠传输协议，IP 协议号 132。它诞生于 SIGTRAN 项目——当年要把 SS7 电话信令搬上 IP 网，发现 TCP 的语义根本不合用，于是新设计了一个。所以 SCTP 从第一天起就是为电信信令定制的。

F1-C、E1、NG-C、Xn-C 一律用 SCTP，O-RAN 的 E2 也跟着用。这不是历史惯性，而是三个能力的组合，每一个都对应 TCP 的一个真实缺陷。

优势一：多流（multi-streaming）消除队头阻塞

TCP 是单一有序字节流，一个报文段丢失会把其后所有已到达的数据扣在接收缓冲里。一台 O-DU 上同时有上千个 UE 在接入、切换、释放，挤在一条 TCP 连接里就意味着任何一次丢包都让所有 UE 一起等一个 RTO。SCTP 一条关联内可以有多条逻辑流，流间交付顺序互不相干：

一个常被答错、说清楚很加分的细节：SCTP 的多流只解耦了「交付顺序」，没有解耦「拥塞控制与重传」。拥塞窗口、RTO、SACK 都是每关联一份的——链路真丢包时整条关联的发送速率都会降下来，只是接收侧不会因为等一个包就把别的流全扣住。想连拥塞控制也隔离，只能建多条关联。

优势二：多归属（multi-homing）做传输层故障切换

一条关联的每一端都可以绑定多个 IP 地址，握手时交换全部地址，之后一个作主路径、其余作备份。主路径失效时关联不断，只是切到备份地址继续发，上层完全不感知，UE 上下文不用重建。TCP 做不到——连接由四元组唯一标识，换 IP 就是换连接；传统替代是 IP 层冗余（VRRP、BFD + 动态路由），但那要么依赖网络设备配合，要么收敛时间受路由协议约束。

优势三：保留消息边界（面向消息而非字节流）

SCTP 的传输单元是消息：send 一次，对端就 recv 到完整的一条。这对 ASN.1 信令协议尤其重要——F1AP / NGAP 的 PER 编码本身不带长度字段，要解到一半才知道有多长。跑在 TCP 上就得额外套一层帧定界（SIGTRAN 时代的 M3UA 正是如此），SCTP 直接消灭了这个问题，附带还能按消息选择有序或无序交付。

GTP-U：用户面为什么要再套一层隧道

用户数据本身就是 IP 包，UE 也已经有 IP 地址。为什么不直接路由，非要再套一层 UDP + GTP-U？三个理由，缺一不可：

理由不套隧道会怎样
① 移动性 / 会话连续性UE 的 IP 锚定在 UPF 上。靠路由把流量引过去，就要为每个终端注入一条主机路由并在切换时收敛——百万级路由表，且收敛远慢于切换。套隧道后换基站只是换端点，UE 的 IP 一位都不用变。
② 会话与 QoS 标识一个 UE 有多个 PDU 会话，每个会话里有多条 QoS Flow，而裸 IP 包里没有字段能表达这个。TEID 标识隧道（≈ 会话/承载），扩展头里的 QFI 标识流，转发面据此限速、调度、计费。
③ 地址空间隔离UE 地址属于 N6 侧的用户地址空间（大量私网与重叠地址），在 RAN 传输网里不可路由也不应可路由。传输网只需知道 gNB 与 UPF 的地址，规模从「终端数」降到「网元数」。

生活类比：快递里的转寄服务。你搬家了但不想通知所有商家改地址（那就是「给每个终端注入主机路由」），于是登记一个转寄：包裹先到老地址（UPF，你的 IP 锚点），快递公司再套一张新面单（GTP-U 头）转发到你的新住处（当前基站），寄件人一无所知。TEID 就是面单上的转寄单号——它标识的是「这一路转寄关系」，不是收件人本人。

按优先级三种处置：① 传输网整段开 jumbo frame；② 把通告给 UE 的 MTU 减掉隧道开销；③ 对 TCP 做 MSS clamping——第三种救不了 QUIC，只能算兜底。

SCTP 多归属在真实网络里的四个坑：
① 两个地址其实不独立。配在同一块网卡、同一个 VLAN、同一台接入交换机上，形式上是多归属，实际共享全部单点。
② 反向路径不通 / rp_filter。多归属要求任意源、任意目的地址的 4 种组合都可达，而工程上常常只测了主-主那一条；Linux 的 rp_filter=1 在多网卡场景下会直接丢包，表现为备份路径的 HEARTBEAT 永远收不到 ACK。
③ 中间设备不认多归属。有状态防火墙看到 INIT 声明之外的源地址就丢，NAT 基本不支持，云上四层负载均衡多数只支持 TCP/UDP。所以相当多现网索性用单归属 SCTP + IP 层冗余（BFD + 动态路由 / VRRP）——这是正当的工程选择，不是「没做好」。
④ 容器化后更难。K8s 默认 CNI 与 Service 对 SCTP 支持有限，Pod 通常只有一个 IP，多归属无从谈起，实践中靠 Multus + SR-IOV 或干脆放弃。这是 O-Cloud 化过程中一个真实的能力退化，值得在方案评审时明确提出来。

O1（管理接口）

NETCONF/YANG 登场的地方

这就是 「NETCONF/YANG 为什么出现在 O-RAN」的答案：SMO 经 O1 配置和监控各网元，O-RU 还额外通过前传 M 平面被直接管理——所以 NETCONF 出现在两处。详见 NETCONF 与 O-RAN O1 的联系。

O1 不是一个协议，而是一组管理服务

O1 最容易被误解成「就是 NETCONF」。它其实是按管理功能划分的一组服务，各自用了完全不同的协议——配置要事务性与强一致，性能数据要高吞吐与可批量，告警要实时推送，一个协议覆盖三者是行不通的。

O2：管的不是网元，是承载网元的那片云

O2：O-RAN 定义的 SMO ↔ O-Cloud 接口，形态是 RESTful HTTPS，拆成两组逻辑服务——IMS（Infrastructure Management Services）管基础设施本身，DMS（Deployment Management Services）管网元的部署与生命周期。

O2 必须存在，是因为解耦做到了「软硬件分离」这一层。SMO 要能自动问出「这片云上还有多少 CPU、有没有带加速卡的节点、把这个 O-DU 部到哪里」，就需要一个厂商中立的基础设施接口——这正好是 O1 覆盖不到的那一层。

O2 落地时最容易低估的一点：基础设施的故障不会自己变成无线告警。一个 O-DU Pod 因节点内存压力被驱逐，O2/IMS 侧看到「节点资源告警 + Pod 重调度」，O1 侧看到「网元失联 + 小区不可用」——两条告警来自两个接口、两套数据模型，常常还进了两个运维系统。不做关联，值班人员会按无线故障去排查一个纯资源问题。两侧至少要共享一个实例标识。

E2（近实时控制接口）

让 xApp 能真正"控制"RAN

E2 连接 Near-RT RIC 与 O-CU / O-DU（合称 E2 节点），在 10 ms ~ 1 s 的尺度上从 RAN 采数据、向 RAN 下控制，供 xApp 做切换、负载均衡、干扰规避这类闭环。3GPP 没有对应接口。

E2AP 与 E2SM：为什么要分成两层

这是 E2 最重要的设计，也最能区分「用过」和「读过」——E2 被刻意拆成了两层：

E2SM全称 / 用途典型内容谁是 E2 节点侧的主要提供者
E2SM-KPMKey Performance Measurement：只读的指标上报PRB 利用率、吞吐、活跃 UE 数、切换成功率；小区级与 UE 级O-DU（MAC 指标）、O-CU-CP（连接与移动性）
E2SM-RCRAN Control：可写的控制与策略切换控制、双连接 / 载波聚合、QoS 流映射、资源分配策略O-CU-CP、O-DU
E2SM-NINetwork Interface：把 RAN 接口消息本身暴露出来把 Xn / F1 / NG 上的消息内容作为上报载荷送给 RIC各 E2 节点
E2SM-CCCCell Configuration and Control小区参数与配置结构的查询与修改O-DU、O-CU

E2 上的四类过程与订阅模型

Action Type语义E2 节点的行为典型用途
REPORT只上报，不影响 RAN 行为触发条件满足就发 Indication，继续原有流程KPI 采集、监控、给模型喂数据
INSERT上报并挂起正在进行的 RAN 过程发出 Indication 后暂停，等 RIC Control 或超时「切换前先问一下 xApp」这类插手式控制
POLICY下发一条持续生效的策略把策略装进本地逻辑，不再逐次上报切换门限、准入门限这类「设一次管很久」的参数
CONTROL独立过程，RIC 主动下发一次具体动作执行并回 ACK / FAILURE强制某个 UE 切换、调整某条流的资源
INSERT + CONTROL 是 E2 最有杀伤力也最危险的组合。它把 RAN 的一个内部决策点「外包」给 xApp：威力在于不改基站软件就能替换掉一个算法，风险在于你在实时控制路径里插进了一次网络往返 + 一个第三方程序。三个问题必须先答：① RIC 不回时能不能退回本地默认决策；② 挂起期间的资源占用与并发上限；③ xApp 崩溃时能不能干净退化。连超时兜底都没有的 INSERT 型 xApp 可以拖垮整个小区——这就是现网里 REPORT 与 POLICY 型遍地开花、INSERT 型极少见的原因。

O1 与 E2 的职责边界：最容易混的一对

两者都能「改 RAN 的行为」，所以常被问「为什么不用 O1 做就好」。判据有两条，缺一不可：

判据O1（管理面）E2（近实时控制面）
时间尺度秒 ~ 分钟：一次变更要过事务校验，还可能触发小区重配10 ms ~ 1 s：跟得上信道与负载的变化
是否持久化持久化：写进配置库，重启后仍生效，是「真值」不持久化：关联断开或 xApp 下线后回到基线
数据模型YANG，声明式，描述「系统应该是什么样」E2SM，命令 / 事件式，描述「现在该做什么」
发起方SMO / 运维系统 / 意图闭环Near-RT RIC 里的 xApp
适合做小区规划参数、邻区关系、切片配额、告警门限逐 UE 的动态决策：负载均衡、干扰规避、切换目标选择
不适合做秒级响应的闭环——等配置生效，高峰已经过去了长期生效的基线配置——会与配置库产生「配置漂移」
混淆边界的两个真实后果：
① 拿 O1 做实时闭环 → 追不上，还把配置库搅乱。SMO 侧写个脚本每 30 秒经 O1 改一次切换门限：问题不只是慢——每次变更都是一次事务提交，配置库版本号疯涨、回滚基线失去意义，网元还可能因参数变更触发小区重配导致瞬时掉话。
② 拿 E2 做持久配置 → 配置漂移，故障后莫名恢复原状。xApp 改了参数但配置库里没有记录，之后任何一次重启、关联重建或 xApp 升级，参数就悄悄回到基线值。现象是「优化效果间歇性消失」，运维系统里却查不到任何变更记录。

正确姿势：E2 在基线之上做短期偏移，O1 负责基线本身。偏移量长期稳定有效，就该由非实时闭环固化回 O1 的配置基线。E2SM-CCC 让部分配置类操作也能走 E2、边界确实模糊了——这时更要回到那两条判据。
真实案例形态：xApp 订阅成功但一条 Indication 都收不到。关联 ESTABLISHED、Action 也在 Admitted 列表里，就是没有数据。三个高频原因：① Event Trigger 的周期比节点支持的最小上报周期还短——有的实现「接受订阅但静默不报」而不是拒绝；② Definition 里声明的可用指标不含你请求的那几个，节点于是回了个空消息（看字节数就能发现）；③ RIC 内部路由——Indication 到了 RIC，但 RIC Request ID 与 xApp 注册的不一致，被丢弃。

A1（策略接口）

慢 RIC 给快 RIC 下策略

A1 连接 Non-RT RIC 与 Near-RT RIC，把策略、意图与富数据下发给近实时侧去指导 xApp，时间尺度 ≥ 1 s，同样是 O-RAN 新增的接口。

A1 下的是「目标」，不是「动作」

A1 与 E2 的关键区别不在时延数字，而在语义层次：E2 下发动作或短期策略（「把 UE-42 切到小区 7」）；A1 下发目标与约束（「切片 0x01 的 P95 时延压在 20 ms 以内」）。怎么达成 A1 不管，由 xApp 自己决定算法与手段。

生活类比：三级管理。O1 是人事与制度——岗位编制、考勤规则，改一次要走流程（持久、慢、是真值）。A1 是季度 OKR——「把客户满意度提到 90 分」，只给目标不给方法。E2 是班组长的现场指挥——「你去接这个电话」（秒级以下、命令式、不留档）。谁越界谁出问题：老板每 10 秒指挥一次具体动作，公司会瘫；班组长自己改编制，人事系统会乱。

A1 规范里定义了两类（另有一类曾作为研究项）服务：

A1 服务方向内容为什么需要
A1-P（Policy）Non-RT RIC → Near-RT RICpolicy type 与 policy instance 的增删改查与状态查询把长周期分析得出的意图 / 目标传给近实时侧执行
A1-EI（Enrichment Information）Non-RT RIC → Near-RT RICxApp 靠 E2 拿不到的外部信息：话务历史、人流预测、天气很多好决策需要 RAN 之外的知识
ML 模型管理Non-RT RIC → Near-RT RIC模型分发与生命周期管理（能力仍在演进，以规范版本为准）模型在非实时侧训练、近实时侧推理，需要一条投放通道

「为什么要把策略与决策分成两层，而不是让一个大脑直接控制」——这是 RIC 架构的核心问题，三条理由：
① 时间尺度不可兼得。要在 10 ms 内响应就必须靠近 RAN、逻辑轻量、不等外部数据；要用历史数据做训练就必然是分钟到小时级。塞进一个组件只能按最严的约束设计，复杂分析根本做不了。
② 训练与推理天然分离。非实时侧有全网数据与算力负责训练，近实时侧只做推理与执行，A1 就是这条投放通道。
③ 故障域隔离。Non-RT RIC 挂了，Near-RT RIC 继续按最后一次收到的策略工作；Near-RT RIC 挂了，RAN 退回自身基线逻辑。每一层失效只损失一层能力——这才是做成三层的真正理由。
A1 的落地陷阱集中在 policy type 的版本与归属。既然 schema 是 xApp 注册进来的，就有三个后果：① 下发一个没有任何 xApp 注册过的 policy type 会被直接 404；② xApp 升级时改了 schema，旧策略实例会变成非法，而 enforceStatus 未必立刻反映；③ 多个 xApp 注册同一个 policy type 时谁执行、会不会打架，规范并不替你解决。纪律只有一条：schema 变更当作接口变更来管，走版本号而不是原地改。

  • 两条共性技术：信令面清一色 ASN.1 + SCTP，用户面清一色 GTP-U over UDP，TEID 由接收方分配。

分层自测

8.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础F1-C 与 F1-U 有什么区别？

    它们是 F1 接口的两条逻辑独立的通道，连接的网元、协议、传输层、可靠性来源全都不同。

    • F1-C：O-CU-CP ↔ O-DU，承载 F1AP（TS 38.473，ASN.1 PER 编码），跑在 SCTP 上（端口 38472）。做的是 UE 上下文管理、承载建立、以及把 RRC 消息当容器透传。每个 O-DU 与 CU-CP 之间只有一条长期保持的 SCTP 关联，所有 UE 的信令在里面按 stream 分流。
    • F1-U：O-CU-UP ↔ O-DU，承载 PDCP PDU，用 GTP-U 隧道跑在 UDP 2152 上，并在 GTP-U 扩展头里带 TS 38.425 的 NR 用户面协议做流控与送达状态反馈。每个 DRB 一对隧道，随 UE 建立与释放。

    可靠性来源的差别值得单独说：F1-C 的可靠性来自 SCTP 自身的重传与拥塞控制；F1-U 跑在不保证送达的 UDP 上，丢包由 PDCP 层的 ARQ 与重排序兜住，用户侧只表现为时延毛刺。

    加分：两条通道在分离架构里连的是不同网元（一个到 CU-CP，一个到 CU-UP），这正是需要 E1 接口的原因。而且它们通常走不同 VLAN / 不同 QoS，所以现场会出现「注册成功但没流量」这种只有一条通道坏了的症状。

  2. 基础NG-C 与 NG-U 分别连到核心网的哪个网元？
    • NG-C（也叫 N2）→ AMF（Access and Mobility Management Function）。协议是 NGAP（TS 38.413）over SCTP，端口 38412。承载 UE 注册、鉴权与 NAS 透传、PDU 会话资源建立、切换、寻呼，以及接口级的 NG Setup。
    • NG-U（也叫 N3）→ UPF（User Plane Function）。协议是 GTP-U（TS 29.281）over UDP 2152，并用 PDU Session Container 扩展头逐包携带 QFI。承载用户的 IP 报文。

    两个要点：① 在 CU/DU 分离架构里，NG 终结在 CU 上——NG-C 在 O-CU-CP，NG-U 在 O-CU-UP，DU 与 RU 完全看不到 NG。② NG-C 上的 NAS 消息对 RAN 是不透明容器，基站只负责在 RRC 与 NGAP 之间搬运，看不到鉴权向量与 NAS 加密内容——安全边界就划在这里。

    常见混淆：把 N4（SMF ↔ UPF，用 PFCP）也算进 RAN 侧接口。N4 是核心网内部接口，与基站无关。

  3. 基础Open Fronthaul 是谁定义的？它和 3GPP 是什么关系？

    Open Fronthaul 是 O-RAN 联盟（WG4）定义的，不是 3GPP 定义的，但它建立在 3GPP 的研究成果上。准确的说法是：「O-RAN 定义，基于 3GPP 的 7-2x 拆分点」。

    展开这个关系：3GPP 在 CU/DU 功能拆分的研究里列出了 Option 1~8 一系列候选拆分点（相关研究见 TR 38.816 等），但只把 Option 2（即 F1 接口）标准化成了正式接口，物理层内部的 7-2x 只停留在研究阶段——3GPP 没有为它定义可互操作的接口规范。O-RAN WG4 补上了这一块：报文结构、C/U/S/M 四个平面、时延窗口、YANG 管理模型、以及互操作测试规范。

    所以对比记忆：F1 / E1 / NG / Xn 是 3GPP 定义、O-RAN 原样复用；Open Fronthaul / O1 / O2 / E2 / A1 是 O-RAN 定义，其中只有 Open Fronthaul 与 3GPP 有这层「拆分点来自 3GPP」的渊源。

    再加一句能拉开差距的：Open Fronthaul ≠ eCPRI。Open Fronthaul 是接口规范，eCPRI（由 CPRI 合作组织定义）只是它 C/U 平面的承载协议之一；S 平面用 PTP、M 平面用 NETCONF/YANG，都不是 eCPRI。

  4. 基础O1 与 O2 有什么区别？

    都是 SMO 发起的管理接口，但管的对象层次不同：

    • O1：管网元。SMO ↔ O-CU / O-DU / O-RU / Near-RT RIC。做 FCAPS——配置（NETCONF/YANG，有事务语义）、故障与性能（VES 事件 + 批量 PM 文件）、软件与文件管理。典型动作是「把小区 3 的下行功率调低 2 dB」。
    • O2：管承载网元的那片云。SMO ↔ O-Cloud。分成 IMS（基础设施管理服务：资源清单、容量、节点与加速器、基础设施告警）与 DMS（部署管理服务：网元实例化、扩缩、升级、终止），接口形态是 RESTful HTTPS。典型动作是「在有加速卡的节点上再起两个 O-DU 实例」。

    一个好用的判据：「把网元从一台服务器迁到另一台，谁负责？」——O2。迁完之后重新下发小区参数？——O1。顺序也是这个：先 O2 把实例拉起来，再 O1 把它配成一个能提供服务的基站。

    加分：指出 O2 的存在前提是「软硬件解耦」——O-DU 软件、服务器、加速卡、Kubernetes 发行版可能来自四家厂商，SMO 需要一个厂商中立的基础设施接口。并可以补一句工程现实：O2 的资源事件与 O1 的网元告警来自两套数据模型，不做关联的话值班人员会把资源问题误判成无线故障。

8.2 中级（区分熟练度）

  1. 中级E1 接口是干什么的？为什么需要它？

    E1 是 gNB-CU-CP 与 gNB-CU-UP 之间的接口，协议是 E1AP（TS 38.463）over SCTP（端口 38462）。它是纯控制面接口，永远不承载用户数据——职责就是让 CU-CP 去指挥 CU-UP 建立、修改、释放 Bearer Context。

    为什么需要它，两条理由：

    • CP 与 UP 要独立扩容。控制面负载正比于信令事件数，用户面负载正比于比特数，两者的比例在不同场景下差好几个数量级：物联网小区是「海量连接、极低吞吐」（CP 重），热点小区是「几十用户、跑满带宽」（UP 重）。做成两个可分别部署与扩容的网元是云化 RAN 的前提，而拆开就必须有接口。
    • 用户面下沉。CU-UP 可以部署到靠近基站的边缘机房以降低时延（MEC），CU-CP 集中在区域中心。这只有 CP/UP 分离后才做得到。

    核心过程是 BEARER CONTEXT SETUP / MODIFICATION / RELEASE，另有 BEARER CONTEXT INACTIVITY NOTIFICATION（用户面发现长时间无数据，通知 CP 去做 RRC 释放或挂起）。

    加分点是把隧道端点的流转讲清楚：CU-CP 是唯一的信息中枢，自己不碰任何用户数据，但所有隧道端点都要经它转手。UPF 的端点经 NG-C 进来、经 E1 递给 CU-UP；CU-UP 的两个端点经 E1 出来，一个经 NG-C 回给 5GC、一个经 F1-C 递给 DU；DU 的端点经 F1-C 上来、经 E1 递给 CU-UP。四个网元、三个接口、六次端点交换，一处配错就是单向不通。

  2. 中级为什么 3GPP 的信令面统一用 SCTP，而不是大家更熟悉的 TCP？

    因为 TCP 的三个语义特征恰好都不适合电信信令面，而 SCTP 是为信令面定制的（它出自 SIGTRAN 项目，目标就是把 SS7 信令搬到 IP 网上）。

    • TCP 是单一有序字节流 → 队头阻塞。一台 O-DU 上可能有上千个 UE 同时在接入/切换/释放。挤在一条 TCP 连接里时，任何一个报文段丢失都会把其后所有 UE 的信令扣在接收缓冲里，而一个 RTO 是秒级的——这期间所有 UE 的状态机都在等，然后大面积超时失败。
    • TCP 连接绑死四元组 → 换 IP 就是换连接。信令面需要在一条链路/网卡失效时不中断，TCP 只能重建连接、重建上下文。
    • TCP 是字节流 → 需要额外帧定界。F1AP / NGAP 的 ASN.1 PER 编码结果本身不带长度字段，跑在 TCP 上就必须在协议之外再套一层带长度的公共头（M3UA 时代就是这么做的）。

    对应地，SCTP 用多流、多归属、面向消息三个能力把这三点都消掉了，所以 3GPP 在 F1-C、E1、NG-C、Xn-C 上一律规定用 SCTP，O-RAN 的 E2 也跟着用。

    要显得真做过，可以补一句反面：SCTP 的代价是中间设备友好度极差——NAT、有状态防火墙、云上的四层负载均衡多数不支持它，Kubernetes 的默认 CNI 与 Service 对 SCTP 支持也有限。这是它在云原生环境里最大的落地阻力。

  3. 中级用户面为什么要再套一层 GTP-U 隧道？TEID 是谁分配的？

    UE 已经有 IP 地址了，但直接路由不行，三个理由缺一不可：

    • 移动性 / 会话连续性。UE 的 IP 锚定在 UPF 上。若靠路由把流量引到当前基站，就要为每个终端在传输网里注入一条主机路由并在切换时收敛——百万级路由表，且收敛远慢于切换。套隧道后换基站只是换隧道端点，UE 的 IP 一位都不用变。
    • 会话与 QoS 标识。裸 IP 包里没有字段能表达「这属于哪个 PDU 会话的哪条 QoS 流」。TEID 标识隧道（≈ 会话/承载），扩展头里的 QFI 标识流，转发面据此做限速、调度、计费。
    • 地址空间隔离。UE 地址属于 N6 侧的用户地址空间（大量私网与重叠地址），在 RAN 传输网里不可路由也不应可路由。传输网只需知道 gNB 与 UPF 的地址，规模从「终端数」降到「网元数」。

    TEID 是 32 位，由「接收方」分配，然后通过信令告诉发送方「往这个 TEID 发」。所以一条隧道的两个方向用的是两个毫不相关的 TEID 值，各自只需在本端唯一。具体地：F1-U 上，CU-UP 的接收端点通过 F1AP 的 UL UP TNL Information 给 DU，DU 的接收端点通过 DL UP TNL Information 回给 CU；NG-U 上，UPF 的端点在 PDU SESSION RESOURCE SETUP REQUEST 里下来，CU-UP 的端点在 Response 里上去。

    加分：TEID 配反或对端未开的现象是「单向不通」，抓包能看到报文到了对端却被静默丢弃，判读入口是接收侧的「unknown TEID」计数器。另外别忘了 MTU：外层 IPv4 20 + UDP 8 + GTP-U 8（带扩展头再 +8）合计 36~44 字节，不处理就会「小包通、大包丢」（ping 通但 HTTPS 握手失败），处置优先级是传输网开 jumbo frame > 通告给 UE 的 MTU 减掉开销 > TCP MSS clamping 兜底。

  4. 中级Xn 接口用在什么场景？没有它会怎样？

    Xn 是 gNB ↔ gNB 的横向接口（TS 38.420 系列），Xn-C 跑 XnAP over SCTP（端口 38422），Xn-U 跑 GTP-U。在分离架构里同样终结在 CU 上。它的意义是让「相邻两个基站之间的事」不必绕核心网。四类用途：

    • Xn 切换：源站直接向目标站发 HANDOVER REQUEST（带 UE 上下文与安全参数），目标站预留资源后回 ACK，切换完成再通过 NG-C 通知 AMF 换路径。没有 Xn 就退化成 NG 切换——所有信令绕 AMF 一圈，中断时间明显变长。
    • 数据前转：Xn-U 上建临时隧道，把源站缓存里还没发完的下行数据转给目标站。没有它，切换瞬间的在途数据丢失，TCP 会看到重传甚至窗口塌陷。
    • 双连接（NR-DC / EN-DC 的 NR 侧）：主节点向辅节点请求增删辅小区组、协商承载分流。没有它就做不了多站点聚合。
    • RAN 寻呼与资源协调：RRC_INACTIVE 的 UE 在 RAN 通知区内被寻呼；相邻站协调 TDD 配置与干扰。

    加分：辨析 Xn 与 E2 在负载均衡上的分工。Xn 上的资源状态交换是「两个基站之间的双边协商」，为的是完成一次具体的切换或双连接；E2 上的上报是「多个基站向一个集中大脑汇报」，为的是让 xApp 做全局决策。两者并存：xApp 经 E2 看到某小区过载、下发策略调整切换门限，实际的切换动作仍然走 Xn 完成。

8.3 高级（体现深度）

  1. 高级说出 SCTP 相对 TCP 的三个优势，并说明各自的限度。

    ① 多流（multi-streaming）：一条关联内多条逻辑流，流与流之间的交付顺序互不相干。丢一个包只阻塞它所在的那条流，不会把别的流一起扣住。3GPP 各接口的用法是 非 UE 关联信令固定走一条流（实现上普遍是 stream 0），UE 关联信令按 UE 散列到其它流上——这样一个 UE 的信令卡住不会波及其它 UE，接口级过程之间又保住了顺序；流数在 INIT 里协商（OS / MIS），实际可用数是 min(本端 OS, 对端 MIS)，双向可以不对称。

    限度（这一点最能拉开差距）：多流只解耦了「向上层交付的顺序」，没有解耦「拥塞控制与重传」——拥塞窗口、RTO、SACK 都是每关联一份的。链路真丢包时整条关联的发送速率都会降，只是接收侧不会因等一个包而全扣住。想连拥塞控制也隔离，得建多条关联。另外，流数配得太少是隐性故障：协议栈会把多个 UE 挤进同一条流，多流的好处直接消失。

    ② 多归属（multi-homing）：每端可绑多个 IP，主路径失效时切到备份，关联不断。靠周期性 HEARTBEAT 探活，上层完全不感知，UE 上下文不用重建。这是把故障切换下沉到传输层，不依赖任何网络侧机制。

    限度：现网里它经常形同虚设。（a）两个地址如果配在同一块网卡/同一 VLAN/同一台接入交换机上，故障域根本没分开；（b）多归属要求四种「源地址 × 目的地址」组合都可达，工程上常只测了主-主一条，Linux 的 rp_filter=1 会按路由表校验源地址直接丢包；（c）有状态防火墙看到 INIT 声明之外的源地址就丢，NAT 基本不支持多归属，云上四层负载均衡多数只支持 TCP/UDP。所以相当多的现网索性用单归属 SCTP + IP 层冗余（BFD + 动态路由 / VRRP）——这是正当的工程选择。容器化后更严峻：Pod 通常只有一个 IP，多归属基本无从谈起。

    ③ 面向消息，保留消息边界：send 一次、recv 到完整一条，应用不用处理粘包半包。对 ASN.1 PER 尤其重要——PER 编码结果不带长度字段，跑 TCP 就必须额外套一层帧定界。附带能力是逐消息可选无序交付，心跳类消息不必排队。

    限度：消息过大时 SCTP 仍要分片，且要依赖路径 MTU 发现；PMTUD 被防火墙挡住时，大消息（比如带整份系统信息的 F1 Setup）会被静默丢弃。

    再补一个常被忘记的第四点：四次握手 + State Cookie 让服务端在验证 Cookie 之前不分配 TCB，天然抗 SYN 洪泛式攻击，这对暴露给成千上万个基站的信令面很有价值。

    最后一条工程不变式值得主动提：Association.Max.Retrans 必须明显大于 Path.Max.Retrans，否则主路径刚被判死、还没切到备份，整条关联就先 ABORT 了——花钱买的双归属一次都没生效过，现象还是「偶发接口闪断」，极难定位。

  2. 高级E2 与 A1 的时延分档分别是多少？这个分档为什么必须存在？

    E2 是 10 ms ~ 1 s（近实时），A1 是 > 1 s（非实时），再往上 O1/O2 是秒到分钟级。作为对照，另一端的 Open Fronthaul 是 ~100 µs 量级，F1/E1/NG/Xn 是毫秒量级。

    但真正要答的是「为什么不能合成一层」，理由有三条：

    • 时间尺度不可兼得。要在 10 ms 内响应，就必须部署在靠近 RAN 的地方、跑轻量逻辑、不能等外部数据；要用上全网历史数据与大模型做训练，就必然是分钟到小时级。塞进一个组件只能按最严的约束设计，于是复杂分析根本做不了。
    • 训练与推理天然分离。非实时侧有全网数据与算力，负责训练与评估；近实时侧只做推理与执行。A1 就是「策略/模型投放」这条通道。
    • 故障域隔离。Non-RT RIC 挂了，Near-RT RIC 按最后收到的策略继续工作；Near-RT RIC 挂了，RAN 退回自身基线逻辑。每层失效只损失一层能力，而不是整体不可用。

    语义层次上的差别同样要说清：A1 下发的是目标与约束（「这个切片的 P95 时延压在 20 ms 内」），怎么达成不管；E2 下发的是动作或短期策略（「把 UE-42 切到小区 7」「把切换门限设为 −105 dBm」）。

    加分点：A1 的「下发成功 ≠ 生效成功」。PUT 策略实例返回的是 202 Accepted，必须再查 status 的 enforceStatus 才知道有没有 xApp 真的在按它工作——最常见的失败就是没有任何 xApp 注册过这个 policy type。只看 HTTP 状态码就以为策略生效，是 A1 集成阶段最典型的误判。

  3. 高级E2SM 是什么？为什么要把它和 E2AP 分成两层？

    E2SM（E2 Service Model）是「装在 E2AP 消息里的载荷定义」：具体上报哪些指标、控制哪个参数、事件触发条件怎么写。每个 E2SM 是一份独立规范，有自己的 OID 与版本。而 E2AP 只管信令外壳——建立关联、发起订阅、回上报、报错——它完全不理解无线语义，里面没有「PRB」「切换」这些概念。类比：E2AP 是 HTTP，E2SM 是 body 的 schema。

    主要的 E2SM：E2SM-KPM（只读指标上报：PRB 利用率、吞吐、活跃 UE 数、切换成功率，支持小区级与 UE 级）、E2SM-RC（RAN Control，可写：切换控制、双连接/载波聚合、QoS 流映射、资源分配策略）、E2SM-NI（把 RAN 接口上的消息本身作为载荷暴露出去）、E2SM-CCC（小区配置的读写）。

    分层的收益是「加新功能不用改协议」：想让 xApp 控制一个新参数，只需定义或扩展一个 E2SM，E2AP 一个字节不动，已有的关联与订阅机制全部复用。代价是多了一层版本协商——E2 节点在 E2 SETUP REQUEST 里声明 RAN Function 列表（每项含 ranFunctionID、ranFunctionOID、以及描述可用能力的 ranFunctionDefinition），RIC 侧必须装有对应 SM 的解码器才能真正用起来。OID 或版本对不上，xApp 就订阅不了。

    再往深一层，可以讲订阅里的 Action Type：REPORT（只上报，不影响 RAN 行为）、INSERT（上报并挂起正在进行的 RAN 过程，等 RIC 发话）、POLICY（下发持续生效的策略，之后 RAN 自己决策），加上独立的 RIC CONTROL 过程。INSERT + CONTROL 是最有杀伤力也最危险的组合——它把 RAN 的一个内部决策点外包给了 xApp，威力是「不改基站软件就能替换一个算法」，风险是「你在实时控制路径里插了一次网络往返 + 一个第三方程序」。所以必须问清超时兜底、挂起并发上限、以及 xApp 崩溃时能否干净退化。没有超时兜底的 INSERT 型 xApp 可以把整个小区拖垮，这也是现网里 REPORT 与 POLICY 型遍地、INSERT 型极少见的原因。

  4. 高级一条用户数据从 UE 到互联网，要穿过哪些接口？每一段的数据形态是什么？

    按上行方向串一遍，重点是每一段的数据形态而不只是接口名：

    1. UE → O-RU：Uu 空口（3GPP）。形态是射频信号，UE 的 IP 包已经被 SDAP/PDCP/RLC/MAC 层层封装并调制。
    2. O-RU → O-DU：Open Fronthaul U 平面（O-RAN）。形态是频域 IQ 采样，装在 eCPRI over Ethernet 里。这一段根本没有「IP 包」这个概念——O-RU 只做 Low-PHY，看到的是复数采样点。
    3. O-DU 内部：High-PHY 解调 → MAC 解复用 → RLC 重组，到这里才第一次出现一个完整的 PDCP PDU。
    4. O-DU → O-CU-UP：F1-U（3GPP，GTP-U/UDP/IP）。形态是 PDCP PDU 封在 GTP-U 隧道里，TEID 标识是哪个 DRB。
    5. O-CU-UP 内部：PDCP 解密与完整性校验 → 重排序 → SDAP 去头，到这里才还原出 UE 原始的那个 IP 包。
    6. O-CU-UP → UPF：NG-U / N3（3GPP，GTP-U/UDP/IP）。UE 的 IP 包重新封进另一条 GTP-U 隧道，PDU Session Container 里带 QFI。
    7. UPF → 互联网：N6。UPF 解掉 GTP-U 头、做 NAT/计费/策略执行，UE 的 IP 包第一次以裸包形态出现在传输网上。

    所以答案是：Uu → Open Fronthaul → F1-U → NG-U → N6，中间经历三段封装：eCPRI（IQ）、GTP-U（F1-U，装 PDCP PDU）、GTP-U（NG-U，装 IP 包）。

    还要补上「这条路是怎么建起来的」——以下接口全都不承载用户数据：NG-C 完成 UE 注册与 PDU 会话建立并拿到 UPF 的隧道端点；E1 让 CU-UP 建 Bearer Context 并交出它的两个端点；F1-C 建 UE Context 并交换 F1-U 的两个端点；Open Fronthaul 的 C/S/M 平面保证 O-RU 有正确的时钟与载波配置；再往外是 O1/O2（把网元部署好配置好）与 E2/A1（动态优化）。

    这道题的评分点几乎全在第 2 步。很多人会把前传描述成「数据包从 RU 传到 DU」，那是错误的心智模型：拆分点在 7-2x 意味着物理层被切开，接口上流动的是物理层中间量，不是任何一层的数据包。顺着还能补一条有分量的推论：正因为传的是 IQ 而不是包，前传才没有重传、没有拥塞控制，也才必须靠时钟同步与硬时延窗口来保证正确性。
