01

分层模型

对应关系、封装开销、按层排障、跨层优化的边界

面试官问分层，想看的是你脑子里有没有一张能用来排障和选型的坐标系：遇到问题能一句话定位到第几层，做前传设计能解释为什么 eCPRI 不走 TCP/IP。

点击每道题展开参考答案（先自测，再对照）。

  1. 基础OSI 七层和 TCP/IP 四层的对应关系是什么？为什么非要分层？

    先给映射。OSI 自下而上是物理、数据链路、网络、传输、会话、表示、应用；TCP/IP 只有四层。对应关系只需两条合并规则：OSI 的 1/2 合并成网络接口层，5/6/7 合并成应用层，中间两层一一对应。

    OSITCP/IP典型协议这一层引入的新能力
    7 应用 / 6 表示 / 5 会话应用HTTP、DNS、NETCONF、eCPRI 控制面业务语义、编码、会话状态
    4 传输传输TCP、UDP、SCTP、QUIC端口多路复用；TCP 另加可靠与有序
    3 网络网络IP、ICMP、路由协议跨网段寻址与转发
    2 数据链路 / 1 物理网络接口Ethernet、Wi-Fi、5G 空口、PON相邻节点间送比特 + 检错

    解耦、独立演进、复用都只是结果。真正的原因是分层把乘法问题变成了加法问题：n 种应用协议 × m 种链路技术，没有网络层时共需 n×m 份适配，加一种新链路要改 n 个应用。IP 插了一个所有人都必须对接、三十多年基本没变的"窄腰"：上面只声明"我跑在 IP 上"，下面只声明"我能承载 IP"，总适配量降到 n+m。这就是沙漏模型。

    代价必须一起说：① 每层加自己的头，小包场景协议开销能占七成以上（下一题会算）；② 信息隐藏是双向损失——上层不知道下层的真实 MTU（于是有 PMTUD 黑洞），下层不知道上层的时延预算（于是每层各自加缓冲，端到端时延成了所有缓冲之和，即 bufferbloat）。极致性能场景因此做跨层优化：eCPRI 压在以太网上、内核旁路、QUIC 搬到用户态。

    陷阱
    OSI 是参考模型，不是实现，真实互联网跑的是 TCP/IP。混为一谈的典型症状是"在 OSI 第 5 层做会话管理"——现实里没有任何一个独立组件对应它。
    追问：为什么会话层和表示层没能独立成层？
    不是这两件事不需要做，而是它们没能被抽象成一个所有人都复用的稳定接口：会话管理被拆进了各应用协议自己（HTTP 的 Cookie、NETCONF 的 session-id）；编码与加密被 TLS、Protobuf 这些库吸收了，而库不是层。窄腰只有一个位置能成立。见 通信概览。
  2. 基础数据从应用程序到网卡经历了什么？封装开销该怎么算？

    结论：逐层加头。应用数据 → 加 TCP/UDP 头成为段 → 加 IP 头成为包 → 加以太网头与 FCS 成为帧 → 物理层变成比特流。接收端逐层剥头，每层靠上一层头里的一个"分用字段"决定交给谁：以太网靠 EtherType（0x0800 = IPv4），IP 靠 Protocol（6 = TCP，17 = UDP），TCP 靠端口号——这三个字段就是整个协议栈的分发钥匙。

    但面试真正想听的是算术，它直接决定有效带宽（1500 字节 MTU 的以太网）：

    算什么结果怎么来的
    MSS（无 TCP 选项）1460 BMTU 1500 − IPv4 头 20 − TCP 头 20；MTU 指 IP 包上限，不含以太网头
    MSS（实际连接）1448 B几乎都开 Timestamps（+10 B，对齐补 2 B NOP）→ TCP 头 32 B。抓包里的 1448 就是这么来的
    MSS（IPv6）1440 B1500 − IPv6 头 40 − TCP 头 20
    一个满载帧在线上真正占用1538 B前导码 7 + SFD 1 + 以太网头 14 + IP/TCP 40 + 载荷 1460 + FCS 4 + 帧间隔 12 → 效率 94.9%

    大包很漂亮，小包是另一个世界——这对做遥测、心跳、信令的通信软件是决定性的：

    应用载荷线上字节（IPv4+TCP+以太网+IFG）有效载荷占比1 Gbps 的包速率
    1460 B（满 MSS）1538 B94.9%≈ 81 k pps
    512 B590 B86.8%≈ 212 k pps
    100 B178 B56.2%≈ 702 k pps
    24 B（一条小遥测）102 B23.5%≈ 1.23 M pps
    ≤ 6 B84 B（被最小帧撑到 64 B 帧 + 20 B 物理开销）≤ 7.1%≈ 1.488 M pps（千兆线速上限）
    按载荷估带宽会低估 2~4 倍
    真实的坑：某基站性能计数按"每个测量项一条消息"上报，UDP、载荷 24 字节、每秒 40 万条。开发按载荷算 76.8 Mbps，认为千兆口毫无压力；上线后管理口严重丢包——每条在线上占 90 字节，真实 288 Mbps，而且管理口走 CPU 软转发，瓶颈是 pps 不是 bps。改法是攒成约 1400 字节的消息，pps 从 40 万降到 6.9 千。
    追问："协议"和"传输机制"是一回事吗？
    不是。协议是双方约定的格式与规则，传输机制是承载它的通道。NETCONF 既能 over SSH 也能 over TLS，PTP 既能 over UDP 也能直接 over Ethernet（0x88F7）——这就是"换掉一层不影响其它层"在具体协议上的体现。
  3. 中级排障时怎么判断"这是第几层的问题"？你的顺序是什么？

    结论：从下往上，每层用一个能给出"是/不是"的判据，不要跳层。层号最实用的地方就在这里——它直接决定你该敲哪个命令。跳层的代价很具体：查两天应用代码，最后发现是 MTU 配错。

    层现象判据命令看什么
    L1 物理链路 down、间歇误码ethtool eth0、ethtool -S eth0Link detected、协商速率/双工；rx_crc_errors 是否增长
    L2 链路同网段不通、ARP 解析不出来ip -s neigh、tcpdump -e -nn arp邻居表停在 INCOMPLETE/FAILED；VLAN 标签对不对
    L3 网络跨网段不通、部分目的地不通ip route get <dst>、mtr -rwzc 200实际选中的出接口与下一跳；哪一跳之后开始持续丢
    L4 传输连不上、连上就断、慢ss -tin、tcpdump 'tcp[tcpflags] & tcp-rst != 0'SYN_SENT 堆积 = 对端没听；RST 是哪侧发的；retrans/rtt
    L4+ 队列吞吐够但时延抖tc -s qdisc show dev eth0backlog 持续非零 = 这个口是瓶颈
    L7 应用能连、报文正确但业务错业务日志 + strace只有前面都排除了才轮到这里

    三个分界判据值得单独背下来：

    • ping 通但业务不通 → 往上查 L4 及以上；小包通、大包挂 → 一定是 MTU（见第 5 组）。
    • 抓包字节正确但应用报错 → 几乎一定是接收侧分帧写错了，不要查网络（见第 2 组）。
    • 部分目的地址慢/丢包且越来越糟 → 怀疑硬件转发表溢出，流量掉到了 CPU 软转发路径。
    陷阱：mtr 中间跳的丢包率不能直接采信
    某一跳 Loss% 很高但最后一跳是 0，那是路由器对打给自己的 ICMP 限速，不是真丢包。只有"这一跳之后的所有跳都在丢"才是真丢包。
  4. 高级分层既然有代价，什么时候该打破它？你怎么判断一个跨层优化值不值得做？

    结论：跨层优化的收益几乎总是真的，代价也几乎总是同一个——你用分层换来的"可替换性"换了性能。所以判断标准不是"快不快"，而是"我付得起那份锁定成本吗"。

    跨层手段跨过了哪条边界换来什么代价
    eCPRI over Ethernet整个 IP + 传输层百微秒级确定性时延只能在自己规划的二层域里跑；没有路由
    内核旁路（DPDK / XDP）内核协议栈与 socket API每包开销降一个数量级协议栈要自己实现；失去内核的可观测性（ss、抓包全失效）；绑定网卡型号
    QUIC内核 TCP 与 TLS 的分层边界消除队头阻塞、0-RTT 建连、能快速演进CPU 开销高于内核 TCP；对中间设备不透明；给 UDP 限速的网络里反而更差
    硬件卸载（TSO/GRO/校验和）协议栈与网卡的职责边界大幅降低 per-packet 成本抓包看到的不再是线上的包（见第 6 组）；遇分片就静默失效

    把最后一列读一遍就看出共性：跨层做完之后，系统被锁定在特定硬件型号、特定拓扑、特定内核版本上。所以我用三个问题判断，三个都是"是"才做：

    1. 指标是不是硬性的、写在需求里的？"百微秒内必须到"是硬指标，"越快越好"不是。
    2. 被跨过那一层的能力，我有别的办法补上吗？绕过内核栈等于放弃 ss/tcpdump 这一整套可观测性，你得自己造一套等价的，这部分工作量常被严重低估。
    3. 部署环境是我能控制的吗？自己规划的二层网、自己选的网卡 → 可以；跑在客户不确定的网络上 → 老老实实分层。
    最能体现深度的一句
    bufferbloat 就是分层信息损失的产物：没有任何一层知道端到端的时延预算，于是每层各自加缓冲，端到端时延变成所有缓冲之和——不是 bug，是分层的固有代价（第 6 组第 3 题展开）。
02

TCP / UDP

可靠性机制、选型判据、状态机与 TIME_WAIT、字节流分帧

传输层问得最细：「TCP 为什么可靠」人人能背，但「两次握手为什么不行」「TIME_WAIT 的两个理由」就开始分层了。四道题按这个梯度排。

点击每道题展开参考答案（先自测，再对照）。

  1. 基础TCP 为什么可靠？核心机制有哪些，各自防的是什么失败？

    结论：TCP 的可靠不是靠某一个机制，而是六件事各管一类失败，缺一件都不成立。答这题最好的结构是把机制和它防的失败绑起来。

    机制防的是哪一类失败不做会怎样
    序列号 + 累积确认乱序、丢失、重复无法判断数据完整，也无法重排
    超时重传 + 快速重传丢包丢了就永远丢了，等于 UDP
    校验和（含伪首部）数据损坏 + 包被送错主机链路 CRC 之间的位翻转无人发现
    滑动窗口（流量控制）淹没接收方接收缓冲溢出，数据被丢弃
    拥塞控制（慢启动/拥塞避免/快恢复）淹没网络路径队列被打爆，全网一起崩（1986 年的拥塞崩溃）
    连接管理（三次握手/四次挥手）状态不一致、旧连接干扰新连接半开连接、资源泄漏、幽灵数据

    其中流量控制和拥塞控制不是一回事，混说是最常见的失分点：前者端到端、由接收方通告窗口决定，防"对方来不及收"；后者端到网络、由发送方自己估计，防"路上塞住了"。实际发送量取两者最小值：

    校验和覆盖伪首部（含源/目的 IP 和协议号），这是一个刻意的越界设计：它让传输层能自己验证"这个包确实是发给我的"，而不是盲目信任 IP 层。直接后果是 NAT 改了 IP 就必须重算传输层校验和（见第 3 组第 1 题）。

    顺带把"可靠"的边界说清楚：TCP 承诺"字节流有序、无重复、无丢失"，它不承诺消息边界（见本组第 4 题）、不承诺时延上界、也不承诺"对端应用真的处理了这些字节"（send 返回只表示进了内核缓冲）。把"TCP 可靠"当成"业务可靠"是架构层面最常见的误解。

    追问方向
    常见三个：快速重传的触发条件（3 个重复 ACK，不必等超时）；SACK 解决了什么（累积确认表达不了中间的空洞，SACK 让发送方知道该补哪几段，否则一个窗口里丢两个包就要多花一个 RTT）；RTO 怎么算（基于 RTT 的平滑估计与偏差，指数退避，有下界）。逐字段细节见 Ethernet/IP/TCP/UDP 基础。
  2. 基础TCP 和 UDP 怎么选？UDP 为什么适合实时数据？

    结论：判据只有一句——"迟到的数据还有价值吗"。有价值就用 TCP（文件、配置、管理面），没价值就用 UDP（实时音视频、游戏、前传 IQ）。一帧语音迟到 200 ms 到达和丢了没有区别，反而占着队列害了后面的帧——这就是"宁可丢也不要等"。更完整的答法是按顺序问四个问题：

    问题倾向 TCP倾向 UDP
    ① 丢一点能不能接受？不能（配置、文件、计费）能（一帧图像、一个采样点）
    ② 时延有硬上界吗？没有有（前传百微秒级、语音几十毫秒）
    ③ 一对一长会话，还是一对多/短交互？一对一长会话组播/广播、无状态短请求（TCP 做不了组播）
    ④ 连接数与内存预算每连接有状态与缓冲，几十 KB 起几乎无状态，海量对端时省得多

    为什么 TCP 的时延不可控，要能说到机制：① 重传至少是一个 RTT，超时重传更是 RTO 起步；② 队头阻塞——第 3 段丢了，即使第 4、5 段已在接收缓冲，也必须等第 3 段补齐；③ 拥塞控制会主动降速，遇丢包窗口减半；④ Nagle 与延迟 ACK 相互作用能制造那个著名的 40 毫秒停顿。这四条在批量传输里是优点，在实时流里全是灾难。

    陷阱：选了 UDP 不等于省事，而是把活接过来了
    TCP 帮你做的每件事在 UDP 上都还得做，只是可以按业务需要挑着做：序号、重传（实时流通常改成 FEC）、拥塞控制（最容易被忽略，也最容易把网络打坏）、分片重组、保活、加密。所以正确表述是「UDP 更适合，因为我可以只保留序号和 FEC」，而不是「UDP 更简单」。
    加分点：还有第三个选项
    SCTP 提供多流（避免队头阻塞）与多归属，3GPP 的 N2/S1-MME 信令面就用它；QUIC 在 UDP 上重建了可靠传输并消除队头阻塞。"TCP 还是 UDP"在电信场景里从来不是只有两个选项。见 核心网演进。
  3. 中级为什么握手是三次、挥手是四次？TIME_WAIT 的两个理由是什么，太多了怎么办？

    三次握手的结构性答案：TCP 是全双工的，要同步两个方向的初始序号；每个方向的同步都需要"发出"和"被确认"两个动作，一共四个。第二个报文把"服务端的 SYN"和"对客户端 SYN 的 ACK"合并，四个动作压成三个报文。所以三次是四个必要动作能压缩到的最少报文数——这一句同时回答了"为什么不是四次"。

    两次为什么不行，要举具体的坏后果：

    • 旧的重复 SYN 会造成半开连接。一个很久前被放弃的 SYN 迟到了，服务端直接进入 ESTABLISHED、分配缓冲、通知应用"来了个客户"，而客户端根本不认这条连接——资源泄漏加状态不一致，RFC 793 给出的原始理由。
    • 服务端的初始序号从未被确认。SYN-ACK 丢了，服务端以为连接可用并开始发数据，客户端会把它当成来自未知连接而回 RST。
    • 攻击面更大。伪造源地址的单个 SYN 就能让服务端分配完整连接资源。

    TIME_WAIT 的两个理由缺一不可，只答一个是这道题最常见的失分点：

    1. 保证第四次挥手那个 ACK 能到。它没有人会确认（否则无穷递归）。它丢了，被动方停在 LAST_ACK 并重传 FIN，此时主动方必须还"活着"才能再回一次 ACK；若不等就关闭，主动方收到重传的 FIN 会回 RST，被动方于是认为连接异常终止——而数据其实全传完了。2MSL 正好覆盖最坏情况：一个 MSL 让 ACK 走过去，一个 MSL 让对端可能重传的 FIN 走回来。
    2. 让旧连接的迷途报文消散。刚关就用同一个五元组建新连接，而网络里还漂着旧连接的迟到数据段，它们的五元组完全匹配新连接。唯一防线是序号随机化，但 32 位序号在高速连接上会绕回——结果是把陌生数据静默混进字节流，比丢包严重得多，因为它不报错。

    时长：MSL 是约定而非测量值，RFC 793 建议 2 分钟；Linux 固定实现为 30 秒，所以 TIME_WAIT 是 60 秒，没有任何 sysctl 能改。顺便纠正一个极常见的误解：tcp_fin_timeout 管的是 FIN_WAIT_2。

    怎么处理——先纠正问题本身：限制不是"端口用完"而是五元组用完。解法按优先级：① 改长连接 / 连接池——TIME_WAIT 与"关连接的次数"成正比，短连接改长连接能直接降两三个数量级；② 让对端做主动关闭方；③ 扩五元组空间（加后端 IP、让后端多监听几个端口），这是乘法，比调 ip_local_port_range（加法）有效得多。

    两个不该用的"快解"
    tcp_tw_recycle 已在 Linux 4.12 移除：它按源 IP 记时间戳，NAT 后多台客户机的时间戳不单调，会把正常 SYN 当旧包丢掉，症状是"一部分用户完全连不上"。SO_LINGER(0) 能跳过 TIME_WAIT，代价是未发出的数据被直接丢弃且对端看到异常终止。tcp_tw_reuse 则只帮"主动连出去"的场景，对服务端监听侧无效。
    陷阱：CLOSE_WAIT 永远不会自动消失
    它会一路涨到 fd 耗尽、accept() 返回 EMFILE。一步到位的判据：ls -l /proc/<pid>/fd | wc -l 看 fd 是否单调增长。把它和 TIME_WAIT 混在一起处理，会让你朝完全错误的方向调内核参数——那边该改架构，这边该改代码。
  4. 高级什么是 TCP 粘包 / 拆包？为什么这类 bug 在本机测不出来？

    结论：「粘包」是个很坏的叫法，它暗示这是异常，而这是 TCP 唯一的、正常的行为。正确的心智模型是：TCP 从来就没有"包"，是你的协议给它划了包。它不保证你的一次 send 对应对方的一次 recv；切分位置由 Nagle 合并、当前发送窗口与拥塞窗口、MSS 切分、路径上的 MSS clamping、网卡 TSO/GRO 共同决定，没有一个是你能控制的。

    解决办法只有一句：应用层自己带边界，三选一。

    方案适用代价与边界
    定长消息字段固定的遥测、控制帧最简单最快；协议一旦要加字段就得改版本
    分隔符（\r\n）文本协议（HTTP 头、Redis）必须处理转义，否则负载里出现分隔符就切错；要扫描每个字节
    长度前缀（最常用）二进制协议要定字节序与字段宽度，且必须校验上限
    长度前缀不校验上限，等于给对端一个 OOM 开关
    正确顺序永远是"先校验上限，再分配内存"，超限就直接断连——此时协议已经错乱，继续读只会一路错下去。这是代码审查里必查的一条。

    "为什么本机测不出来"是真正的高级部分。同机房 RTT 0.1 ms、消息又小于 MSS，数据几乎总是一次到齐——于是 n = recv(fd, buf, 4, 0); if (n != 4) 报错; 能在本机稳定跑三个月零故障。切到跨机房后 RTT 30 ms、中间又做了一次 MSS 收缩，长度字段偶尔被切在两个 TCP 段里，recv 返回 2，代码判错并断连，而重连后剩下的 2 个字节被当成下一条消息的开头，错乱一路传染。

    所以要主动把这类环境做进回归测试
    一条命令就能造出跨机房的效果：tc qdisc add dev eth0 root netem delay 30ms loss 0.5%。判读要点：抓包字节完全正确 + 应用报"校验失败/协议错" → 几乎一定是接收侧分帧写错了。读循环见 Socket 编程，协议格式设计见 二进制协议设计。

Ethernet / IP

两级地址与逐跳改写、五元组与端口耗尽、免费 ARP、地址复用选项

这一组考的是"一个包在网络里到底被谁改过"。地址两级、作用域不同，这件事说清了，ARP、NAT、负载均衡、主备切换才有地方落脚。抓包源 MAC 对不上、切换后中断几十秒才自愈、重启 bind 不上——三个排障问题都在这里。

点击每道题展开参考答案（先自测，再对照）。

  1. 基础MAC 地址和 IP 地址有什么区别？一个包转发时它们各自怎么变化？

    结论：MAC 是链路层地址、作用域只有一跳；IP 是网络层地址、作用域是端到端。所以转发过程中源/目的 IP 全程基本不变，而 MAC 每一跳都被重写。

    MAC 地址IP 地址
    长度 / 层48 位，链路层32 位（IPv6 128 位），网络层
    作用域本地链路，逐跳有效端到端，全程有效
    怎么来的网卡出厂固化（前 24 位是厂商 OUI）配置或 DHCP 分配，跟拓扑位置绑定
    转发时每经一台路由器整对重写不变（NAT、隧道除外）
    谁做解析—ARP（IPv4）/ NDP（IPv6）解析成同网段的 MAC

    为什么需要两级地址？MAC 是"这根线上的哪块网卡"，不含任何位置信息，无法据此做路由聚合（48 位平坦地址空间要装几十亿条）；IP 是分层、可聚合的，一条 10.0.0.0/8 就代表 1600 万个地址，这才让全球路由表压到百万量级。IP 负责"往哪个方向走"，MAC 负责"这一步交给谁"。

    抓包里的源 MAC 只告诉你"上一跳是谁"
    不是"发起方是谁"。看到源 MAC 和你以为的服务器对不上，第一反应应该是"中间过了路由器"。目的 IP 不变也有例外：除 NAT 之外，隧道会加外层 IP 头、LB 的 DNAT 会把目的地址换成后端。
    陷阱：TTL 与头校验和也在每一跳变
    IPv4 头校验和覆盖整个头，TTL 一减就必须重算——纯粹的转发开销，也正是 IPv6 敢把头校验和整个删掉的理由之一。实战用法：收到的 TTL 能反推跳数（Linux 初值 64、Windows 128），同一个源的 TTL 突然变了说明路径变了或有人在伪造。
  2. 基础IP 定位什么、端口定位什么？为什么"端口不够用"这个说法是不准确的？

    结论：MAC 找网卡、IP 找主机、端口找进程——三级地址各管一段路。一条 TCP 连接由五元组唯一标识：协议 + 源 IP + 源端口 + 目的 IP + 目的端口。

    五元组要讲透：它是内核查找"这个包属于哪条连接"的键，也是防火墙 ACL、LB 哈希、连接跟踪表的键。由此推出两个结论：① IP 分片后第二片起没有传输层头、也就没有端口号，五元组匹配不了、LB 哈希算不出来；② IPsec ESP 加密后端口号读不到，NAT 与按端口做的 QoS 分类都会失效。

    端口范围名称用途
    0 – 1023知名端口标准服务；绑定需要特权（或 CAP_NET_BIND_SERVICE）
    1024 – 49151注册端口向 IANA 登记的应用（NETCONF over SSH 是 830）
    49152 – 65535动态 / 私有端口IANA 建议的临时端口范围
    32768 – 60999Linux 实际默认net.ipv4.ip_local_port_range，约 28232 个

    "端口不够用"为什么不准确：受限的从来不是端口，而是五元组的组合空间——同一个源端口可以同时连不同的目的地。只有连同一个 目的IP:Port（典型是反向代理连唯一后端）时上限才真的是临时端口数、约 2.8 万条。

    所以扩容的正确方向是"扩五元组空间"而不是"调端口范围"：给后端加 IP、让后端多监听几个端口，都是乘法；把 ip_local_port_range 调到 6 万只是加法，还会占用注册端口区间。

    陷阱：端口耗尽的症状不是报错，而是"偶发连不上"
    connect() 拿不到临时端口时返回 EADDRNOTAVAIL，而多数框架会把它记成一条普通的连接失败日志并重试。判据：ss -tan state time-wait | wc -l 接近临时端口数。TIME_WAIT 的五元组也占着组合空间，所以第 2 组那三条解法同样适用。
  3. 中级免费 ARP 是什么？它有什么用，为什么主备切换最容易漏掉它？

    结论：免费 ARP（Gratuitous ARP）是"没人问、主动发"的 ARP，特征是发送方 IP 与目标 IP 相同，以广播发出。它不是查询，而是宣告"这个 IP 现在归我这个 MAC"。

    作为对照：普通 ARP 之所以存在，是因为 IP 和 MAC 之间没有任何计算关系，只能问——请求以广播发出、应答以单播返回，结果缓存在邻居表里并会老化。免费 ARP 跳过"问"，直接广播答案。三个用途：

    • IP 冲突检测（RFC 5227 的 ACD）：探测包的发送方 IP 填 0.0.0.0，这是刻意的——让收到的机器不要建立缓存表项，探测本身不污染全网。
    • 主备切换刷新邻居表：新主抢到 VIP 后广播免费 ARP，让客户端把缓存改过来。这是 VRRP / keepalived 浮动 IP 能秒级生效的关键一环。
    • 更新交换机 MAC 表：同一个广播包顺便让交换机学到"这个 MAC 现在在哪个端口"。

    这个 bug 为什么特别阴：切换代码常常配了 VIP、起了服务、改了路由，唯独没发免费 ARP；而它在测试环境测不出来——测试机的 ARP 缓存本来就是空的。只有"客户端已和旧主通信过一段时间、缓存里存着旧 MAC"的生产环境才暴露，症状是切换后中断几十秒然后自愈（等到缓存老化）。ip -s neigh show dev eth0 能判断走到了哪一步：

    状态含义看到它意味着
    INCOMPLETE已发请求、没收到回复对端没响应：不在线、ARP 被挡、或 VLAN 配错导致不在一个广播域
    REACHABLE近期确认可达健康。超时在基准值 0.5~1.5 倍间随机化，避免全网同步刷新
    STALE条目还在、可达性过期完全正常，照常用、不阻塞；有流量时才转 DELAY 去确认
    DELAY等一下看有没有隐式确认上层 TCP ACK 能证明对端活着就直接回 REACHABLE
    PROBE正在单播探测DELAY 期间没等到隐式确认，开始主动问
    FAILED多次探测无响应对端确实没了，或 MAC 变了却没通告——漏发免费 ARP 的下场
    可靠的做法
    连发 3~5 个免费 ARP、间隔 100~200 ms（广播会丢），并在客户端侧用 ip neigh show <VIP> 确认 lladdr 真的换了；更彻底的是改用 VRRP 的虚拟 MAC——切换时 MAC 根本不变，客户端缓存不需要更新，问题从根上消掉。
    陷阱：有些设备默认不接受未经请求的 ARP 更新
    出于防 ARP 欺骗的考虑，部分设备会忽略免费 ARP，导致"切换完成了，但业务恢复要等半分钟"。这也提醒一件事：ARP 没有任何认证，任何人都能声称"网关是我"——免费 ARP 和 ARP 欺骗本质是同一个机制，防御在交换机侧（DAI + DHCP Snooping）。见 可靠性与高可用。
  4. 高级SO_REUSEADDR 与 SO_REUSEPORT 有什么区别？各自的陷阱在哪？

    一句话：SO_REUSEADDR 解决"重启时 bind 不上"，SO_REUSEPORT 解决"多进程一起监听同一个端口"。名字只差三个字母，作用毫不相干。

    SO_REUSEADDRSO_REUSEPORT
    解决的问题旧连接的 TIME_WAIT 还占着 addr:port，bind() 返回 EADDRINUSE单个 accept() 线程成为瓶颈；想让多个进程各自持有一个 listen socket
    能否多个 socket 同时 listen 同一 addr:port不能（组播是例外）能，由内核按四元组哈希分流
    分流时机—TCP 在收到 SYN 时定；UDP 按每个包定
    额外前提无组内每个 socket 都要设，且 effective UID 必须相同（防止别人抢你的端口）
    引入BSD 时代的老选项，各平台语义有细微差异Linux 3.9

    SO_REUSEADDR 不削弱安全性：真有另一个进程在 LISTEN 同一个 IP:port 时 bind 仍然会失败，它只豁免了"不允许 bind 一个被 TIME_WAIT 占用的本地地址"这一条。所以服务端监听 socket 应当无条件设它，这不是"调优"而是标准写法。

    对两者都成立的头号坑：必须在 bind() 之前设置
    bind 之后再设不生效而且不报错。这是"我明明设了但没用"的第一成因，而且因为没有任何错误返回，代码评审时极容易放过。

    真正拉开差距的是 SO_REUSEPORT 的两个陷阱，它们都在缩容一侧：

    • 关闭组内某个 listen socket 时，它 accept 队列里"已完成握手但还没被 accept"的连接会被丢弃，客户端看到连接建立后立刻被 RST。较新的内核能把这些请求迁移到组内其它 socket（需显式开启 sysctl），但不能假定线上内核都有。稳妥做法是滚动重启时先让新进程加入组、再关旧进程。
    • 哈希是按四元组算的，不是按负载算的。少量客户端建大量连接时分布可能严重不均——"某个 worker CPU 100%、其它闲着"就是这个原因。需要自定义分发时可以挂 eBPF 程序自己决定选哪个 socket。
    追问：那 UDP 上呢？
    UDP 的 SO_REUSEPORT 是按包哈希的，同一客户端的包会落到同一 socket（四元组不变），但客户端换了源端口就会换 worker。这对"在 worker 内保存会话状态"的设计是个隐藏前提——NAT 重绑定一旦发生，状态就找不到了。见 通信服务的高并发、Socket 编程。

Socket

调用序列与两个队列、短读短写、返回值分支与 SIGPIPE、LT 与 ET

唯一能验证"你真的写过网络代码"的一组。「backlog 管哪个队列」「recv 返回 0 怎么办」「ET 为什么必须读到 EAGAIN」答错的人非常多，线上后果分别是连接被静默丢弃、一个 CPU 核被烧掉、连接静默挂死。共同特点：写错了不报错，只在生产上以另一种面貌出现。

点击每道题展开参考答案（先自测，再对照）。

  1. 基础描述 TCP 服务端 / 客户端的 socket 调用流程。listen 的 backlog 到底管什么？

    流程本身：服务端 socket → bind → listen → accept → recv/send → close；客户端 socket → connect（触发握手）→ send/recv → close。关键是accept 返回的是一条新的已连接 socket，监听 socket 本身不承载数据。

    但真正的考点在 listen(fd, backlog)：内核侧有两个队列，不是一个。

    半连接队列（SYN queue）全连接队列（accept queue）
    装什么收到 SYN、回了 SYN-ACK，还在等最后那个 ACK握手已完成，等应用来 accept()
    连接状态SYN_RECVESTABLISHED
    大小由谁定net.ipv4.tcp_max_syn_backlogmin(backlog, net.core.somaxconn)
    溢出时丢弃 SYN（或启用 SYN cookie 把状态编进 ISN，不占内存）丢弃或回 RST，看 tcp_abort_on_overflow
    溢出的证据nstat 里 TcpExtTCPReqQFullDrop 增长ss -lnt 里 Recv-Q 贴住上限；nstat 里 ListenOverflows 持续增长

    所以 backlog 只管全连接队列，而且会被 somaxconn 截断——代码里写 listen(fd, 4096) 而系统 somaxconn 是 128 时，实际就是 128，且不会有任何警告。这是"压测时连接莫名超时"的经典原因。

$ ss -lnt

LISTEN  128     128     0.0.0.0:8080      ← 贴满了，应用 accept 不过来

# 硬证据：这个计数在涨就是全连接队列溢出
$ nstat -az | grep -E 'ListenOverflows|ListenDrops'

TcpExtListenDrops               4127
    accept 的三个坑
    ① accept 可能返回 ECONNABORTED——客户端在握手完成后、被 accept 之前发了 RST，这不是错误，应继续循环。② 要用 accept4(..., SOCK_NONBLOCK | SOCK_CLOEXEC)：新 fd 不继承监听 fd 的 O_NONBLOCK；SOCK_CLOEXEC 避免 fork+exec 时把连接泄漏给子进程。③ 多线程同时 accept 同一个 fd 会有惊群，可用 EPOLLEXCLUSIVE 或 SO_REUSEPORT 缓解。
    追问：非阻塞 connect 怎么写才对？（高频，也是高频 bug）
    四步：① 设 O_NONBLOCK；② connect() 返回 −1 且 errno == EINPROGRESS 是正常的；③ 等可写；④ getsockopt(fd, SOL_SOCKET, SO_ERROR, ...) 取挂起错误。第四步绝大多数人漏掉：连接失败时 fd 同样会变可写，"可写"只表示"握手有了最终结果"。漏掉它的代码在本机永远正确，上线遇到对端没起来就会"成功连上"然后在第一次 send 时莫名 EPIPE。另外 connect 对同一个 fd 只能调一次，且要用应用层超时（SYN 重传耗尽默认要一分钟以上）。
  2. 中级什么是短读和短写？send 返回值小于请求长度时该怎么处理？

    定义先给准：短读是 recv(fd, buf, 1000, 0) 返回 300——接收缓冲里当时只有 300 字节，内核不会替你等齐；短写是 send 返回 300——发送缓冲只剩 300 字节空位。两者都不是错误，必须靠循环补齐。

    为什么会短写：发送缓冲区有限（net.ipv4.tcp_wmem），排空速度取决于对端接收窗口 + 当前拥塞窗口 + 链路速率。阻塞模式下 send 会等到"至少写进去一部分"就返回，非阻塞模式下缓冲全满直接返回 EAGAIN。所以短写频率和消息大小直接相关——小消息几乎不会遇到，大消息必然遇到。

    场景正确写法写错的后果
    读固定长度（如 4 字节长度头）recv_exact()：循环直到读满或 EOF拿到半个长度字段就判错，断连后剩余字节污染下一条消息
    写一整条消息send_all()：循环推进偏移直到写完只发出一半，对端等不到完整消息
    sendmsg/writev 一次发头+体按已写字节数推进 iovec 数组原样重试 → 已发出的部分被重复发送，协议彻底错乱
    iovec 短写是这一类代码里出 bug 频率最高的地方
    sendmsg / writev 同样可能只写出一部分，重试时不能原样再调一次——必须跳过已写完的项，再把当前项的 iov_base += 偏移、iov_len -= 偏移（iov_base 是 void *，要先转 char * 再做指针算术）。不想自己维护就退回"把头和体拼进同一个缓冲区再 send_all"——多一次内存拷贝换一份不会错的代码。
    配套的两个必备动作
    ① 发送时带 MSG_NOSIGNAL（见下一题）；② 循环里必须处理 EINTR——被信号打断时一个字节都没传，应原地重试。不要依赖 SA_RESTART：Linux 上只要这个 socket 设了 SO_RCVTIMEO/SO_SNDTIMEO，即使有 SA_RESTART 也会返回 EINTR，而设收发超时恰恰很常见。
    追问：短写的时候该等还是缓存？
    阻塞模型里就地循环等；事件驱动模型里绝对不能等——那会卡住整个事件循环，一条慢连接拖垮所有连接。正确做法是把未发完的数据挂到该连接的出站缓冲上，注册 EPOLLOUT，可写时续发，发完立刻取消注册（LT 下不取消会空转）。出站缓冲必须有上限，超过就断连——否则对端只要不读，你的内存就会被撑爆。
  3. 中级recv 返回 0 和返回 −1 分别意味着什么？各个 errno 该怎么分支？

    结论：返回 0 不是错误，是"对端关闭了发送方向"（收到 FIN）；返回 −1 才是错误，而其中两种根本不算错误。把它们合并处理是这一组里后果最严重的写法。

    返回值含义正确动作写错的后果
    > 0读到 n 字节，n 可能远小于请求处理这 n 字节，继续循环当成"读满了" → 解析错乱
    == 0对端已关闭发送方向。TCP 上这是唯一含义把剩余出站数据发完后 close当成错误 → 正常断连记成故障；当成"再试一次" → 死循环空转
    −1 + EAGAIN/EWOULDBLOCK非阻塞下"现在没数据"，不是错误回事件循环等下次可读当成错误 → 连接被无故关闭
    −1 + EINTR被信号打断，一个字节都没传原地重试当成错误 → 偶发失败，只在有定时器时复现
    −1 + ECONNRESET对端发了 RST（进程崩了，或收到发往已关闭连接的数据）立即关闭清理，不要重试重试 → 又一次 RST，日志刷屏
    −1 + 其它真错误记日志并关闭—
    把 0 和 −1 合并成 if (n <= 0) continue; 会烧掉一个 CPU 核
    对端断开后 recv 稳定返回 0，循环永不退出。监控上的表现是"某个线程 CPU 恒定 100%，但没有任何流量"——看流量图会以为服务是空闲的。判读特征：strace 里刷屏的 recvfrom(9, "", 4096, 0, NULL, NULL) = 0，同一个 fd、每秒几十万次。合并成 if (n <= 0) { 出错 } 虽然能跑，但会把正常断连记成故障。

    SIGPIPE 必须一起答，它是"写"这一侧的对应物：向一个对端已完全关闭的连接写数据，内核会发 SIGPIPE，默认动作是终止进程——不是返回错误，是进程没了。时序值得说清：对端 close() 后你的第一次 send 通常成功（FIN 只表示对方不再发），对方的 TCP 收到这些数据后回一个 RST，第二次 send 才触发 EPIPE + SIGPIPE。这就是这类事故总是"偶发、重现不了"的原因。

    处理方式粒度可移植性适用
    sigaction(SIGPIPE, SIG_IGN)整个进程POSIX，处处可用应用程序的默认选择
    send(..., MSG_NOSIGNAL)单次调用Linux 有，macOS 没有库代码：不该替宿主进程做全局决定
    setsockopt(SO_NOSIGPIPE)单个 socketmacOS/BSD 有，Linux 没有跨平台库里与上一条 #ifdef 二选一
    三种方式的共同效果只是"换了失败的形状"
    处理掉 SIGPIPE 不等于问题消失，只是把"进程猝死"换成了"send 返回 −1 且 errno == EPIPE"——一个你必须检查的返回值。忽略信号却不检查返回值，等于把崩溃换成了更难查的静默数据丢失。
    追问：shutdown 和 close 有什么区别？
    close(fd) 作用在文件描述符上、引用计数减一，fork/dup 后还有别人持有时什么也不发；shutdown(fd, SHUT_WR) 作用在连接上，立即发 FIN，而且之后还能继续 recv——这就是"半关闭"。经典事故：多进程服务里父进程 accept 后忘了 close(cfd)，引用计数永不归零，子进程 close 时对端收不到 FIN，连接卡在 ESTABLISHED。
  4. 高级epoll 的 LT 与 ET 有什么区别？为什么 ET 下必须循环读到 EAGAIN？

    结论：LT（水平触发，默认）报告的是状态——只要 fd 就绪，每次 epoll_wait 都会报；ET（边沿触发）报告的是事件——只在状态变化的那一刻报一次。类比是门铃与信箱：LT 像"只要信箱里有信就一直响的铃"；ET 像"邮差按门铃"，送信时按一下，之后不管你取没取都不会再按——所以 ET 下听到铃声就必须把信箱一次性掏空。

    LT（默认）ET（EPOLLET）
    必须用非阻塞 fd 吗不强制（但推荐）必须：否则最后一次读会永久阻塞
    一次事件要读多少读多少都行，读不完下次还通知必须循环到 EAGAIN
    accept 怎么写一次 accept 一条也行必须循环到 EAGAIN，否则同时到达的连接会漏
    EPOLLOUT 怎么管写不完时才注册，写完立刻取消，否则空转可常驻注册：缓冲不满就不再触发
    系统调用次数多一些（每轮都报告）少一些（但每次多一次返回 EAGAIN 的读）
    写错的后果CPU 空转（能被监控发现）连接静默挂死（只在高负载下出现）
    建议默认选它：逻辑简单、出错代价小确有性能证据时再上

    核心答案落在"事件 vs 状态"上：ET 的通知条件是"内核收到新数据"这个事件，不是"缓冲区里有数据"这个状态。只读走一部分，缓冲区从"有 5000"变成"有 3000"——这中间没有发生任何"新数据到达"的事件，于是 epoll_wait 永远不会再提这个 fd，剩下那 3000 字节就此长眠，连接表现为"卡住了但没断"。读到 EAGAIN 就是"重新武装那个边沿"。同理 ET 下的 accept 也必须循环：两条连接同一瞬间入队只算一次边沿。

    ET 还有一个反直觉的公平性问题
    "必须读到 EAGAIN"和"不能让一条连接饿死其它连接"互相冲突：一条连接持续高速灌数据时你会一直读不到 EAGAIN，事件循环被它占住。工程上给单次处理设配额，但这时就不能依赖 ET 的边沿了——必须自己把这个 fd 记进"还有剩余数据"的待办集合。这一层状态机正是 ET 复杂度的真正来源。
    追问：select/poll/epoll 的本质差别是什么？
    select/poll 每次调用都要把"我关心哪些 fd"重新告诉内核，内核也要重新扫一遍；epoll 把这份关注列表常驻在内核里。所以前两者成本随总连接数上升，epoll 只随活跃连接数上升。另外 FD_SETSIZE 常被误解成"最多 1024 个连接"，准确说法是fd 的数值不能 ≥ FD_SETSIZE——FD_SET 会越界写坏栈内存，不报错、只是随机崩溃。见 通信软件设计模式。

VLAN / QoS / MTU

逻辑隔离与 PVID、DSCP 到队列的完整链条、整形与限速、分片与 PMTUD 黑洞

做通信设备的人和做互联网应用的人差别最大的一组。「我标了 EF 为什么对端收到是 0」这类问题只有在现网调过才答得上来。最后一道里的「MTU 黑洞」是教科书级的静默故障。

点击每道题展开参考答案（先自测，再对照）。

  1. 基础VLAN 解决什么问题？那 4 个字节里装了什么？QoS 又是什么？

    VLAN 解决的是"一根线上要跑多个互不干扰的网络"：在同一套物理设备上做逻辑隔离，把一个大广播域切成多个小广播域。收益三条：① 限制广播范围（ARP 广播是所有主机的公共负担）；② 安全隔离（不同 VLAN 之间必须过三层设备，于是有了施加策略的位置）；③ 省线。5G 前传的典型用法就是把 C / U / M / S 四个平面分到不同 VLAN。

    那 4 个字节是插入而不是替换——这是解析代码的头号考点：

    字段位宽作用
    TPID160x8100 = 内层 C-Tag；0x88A8 = QinQ 外层 S-Tag
    PCP3二层优先级 0~7，映射到出口队列。纯二层链路只能靠它做 QoS
    DEI1拥塞时可优先丢弃的标记
    VID12VLAN 编号 1~4094（0 与 4095 保留）

    QoS 是另一回事：对不同流量分级并差异化调度，保证关键业务的时延与带宽。"VLAN 划分谁和谁隔离，QoS 决定拥塞时谁先走"。

    解析代码里最经典的一个 bug：把 EtherType 偏移写死成 12
    链路上一出现 VLAN 标签，偏移 12 读到的是 0x8100，代码要么判"未知协议"丢包，要么按偏移 14 当 IP 头解析。正确写法是循环剥离并给循环设层数上限，不设上限就是一个可被恶意报文触发的 DoS 点。两个抓包的坑：VLAN 卸载常把标签剥到 skb 元数据里，抓包"看不见 VLAN"（ethtool -k 确认）；tcpdump 的 vlan 关键字会把后续偏移整体 +4，必须写在过滤表达式最前面。
    陷阱：PVID 不一致是 VLAN 里最经典的坑
    Access 口只属于一个 VLAN、收发都不带标签；Trunk 口带标签转发，但其中有一个 Native VLAN（PVID）是不带标签的。两端 PVID 配得不一致时，无标签帧会被塞进错误的 VLAN——症状是"某些流量莫名跑到了别的网段"，而两端配置各自看起来都对。这也是 VLAN 跳跃攻击的基础。排查：tcpdump -e 两端同时抓，比对帧上有没有标签。
  2. 中级DSCP 是怎么变成"队列"的？为什么我在应用里标了 EF，对端收到却是 0？

    结论：DSCP 本身不提供任何保障，它只是一个标签。真正的差异化来自路径上每台设备读到标签后把包放进哪个队列、用什么调度策略。「标了 EF 却收到 0」不是代码 bug，而是链条断在了中间。

    字段先说清：DSCP 是 IPv4 头第 2 个字节（原 TOS）的高 6 位，低 2 位是 ECN；IPv6 里对应 Traffic Class。第一个考点就是这个共用——把整个字节当 TOS 去比较，ECN 一置位判断就失败。抓包要按位比：tcpdump -nn 'ip[1] & 0xfc == 0xb8' 只抓 EF（0xb8 高 6 位 101110 = 46）。两端同时抓、比对这个字节，是判断"被谁清零"的唯一可靠办法。完整链条四步，每步都可能断：

    步骤做什么这一步的典型失败
    ① 打标应用 setsockopt(IP_TOS) 或设备按五元组分类忘了左移 2 位：DSCP 46 要写成 46<<2 = 0xB8
    ② 信任边界入口端口决定 trust 还是 untrust「收到 0」的头号原因：运营商接入端口默认 untrust，直接清零
    ③ 映射DSCP → 内部流量类 → 出口队列典型只有 8 个队列，64 个码点必然多对一，两侧映射表不一致就错位
    ④ 调度严格优先 / WRR / DWRR / 整形 / WRED队列分对了但没配上限或权重，等于没做（见下一题）

    常用码点按 RFC 4594 填，不要自己发明数字，跨域互通时才不用逐条协商：

    名称十进制期望行为典型业务
    CS648网络控制路由协议（OSPF/BGP）、PTP 同步
    EF46加速转发：低时延、低抖动、低丢包，必须限速语音、eCPRI 用户面
    AF41–AF4334 / 36 / 38保障转发第 4 类，三档丢弃优先级互动视频、会议
    AF31–AF3326 / 28 / 30保障转发第 3 类信令、流媒体
    DF (BE)0尽力而为其它一切；也是被清零后的下场

    两条算术能省很多查表：AFxy = 8x + 2y，x 决定进哪个队列、y 是同队列内的丢弃优先级（WRED 作用在这里）；CSn = 8n。

    陷阱：纯二层链路根本没有 DSCP
    eCPRI over Ethernet（EtherType 0xAEFE）没有 IP 头，只能用 VLAN 标签里的 PCP（3 位、8 级）。而 DSCP → PCP 必然是有损压缩：默认取 DSCP 高 3 位，于是 AF41/42/43 高 3 位相同，"丢弃优先级"这一维在二层被彻底合并。跨 L2/L3 边界时必须显式确认两侧映射表。
    追问：ECN 是干什么的？
    路由器想说"我快堵了"，唯一手段却是丢包，而丢包的恢复代价至少一个 RTT。ECN 让它改成打标记继续转发：00 Not-ECT、10/01 ECT、11 CE（拥塞已发生）。闭环还要 TCP 配合——接收方看到 CE 后在 ACK 里置 ECE，发送方像遇到丢包一样降窗并用 CWR 确认。所以 ECN 是三方协作，缺一环就退化成普通丢包，这也是它推广缓慢的原因。
  3. 中级整形和限速有什么区别？为什么严格优先级队列必须配上限？

    结论：整形（shaping）把超额流量缓存下来延后发送，限速（policing）直接丢弃或降级。前者用时延换平滑，后者不引入时延但很粗暴。

    整形 Shaping限速 Policing
    超额流量怎么办缓存，延后发送丢弃或降级重标记
    需要缓冲区 / 引入时延需要 / 会（这是它的代价）不需要 / 不会
    对 TCP 的影响友好，流量被平滑粗暴，突发被打断、触发重传
    典型位置出接口（约束自己往外发的）入接口（约束别人送进来的）
    Linux 工具tc … tbf / htb / caketc … police、nftables limit

    选择原则一句话：对自己发出的流量用整形，对别人送进来的流量用限速。整形要花缓冲区和时延去"讨好"对端，只有你控制得住的流量才值得；而入向流量的发送方不受你控制，缓存它只是把拥塞点从对方挪到自己这里，还额外制造了时延。

    "严格优先级为什么必须配上限"是这道题的核心。SP 的语义是"高优先级队列非空就先发它"，好处是高优先级时延可计算、最小；代价是低优先级会被彻底饿死。不限制 EF 队列的带宽占比，一旦 EF 流量超过链路容量，其它队列全部饿死——包括路由协议和管理面，后果是设备"业务还在跑但完全失联"。

    所以规矩是：严格优先级的队列一定要成对配置——优先级 + 上限
    常见做法是 EF 队列不超过链路的 30%~50%。这条在 O-RAN 前传里尤其致命：eCPRI 用户面本身就是大带宽的 EF 流量，没给它设上限，一次异常的重传风暴就能把同一条链路上的 M 平面（NETCONF）和 S 平面（PTP）一起打死——而 PTP 一断，整个小区的时间同步就崩了。

    调度算法也值得会一张表，被追问时能直接给出取舍：

    算法规则致命弱点
    FIFO只有一个队列语音和下载平等排队——等于没有 QoS
    SP（严格优先级）高优先级非空就先发低优先级饿死，必须配上限
    WRR（加权轮转）按包数轮转大包流量实际拿到更多带宽，不公平
    DWRR（差额加权轮转）每轮给每队一个字节配额，用不完累积时延界比 WFQ 松；但 O(1) 且硬件友好，是主流选择
    SP + DWRR 混合一两个 SP 队列 + 其余 DWRR设备上的实际标准做法
    加分点：为什么 DiffServ 能规模化而 IntServ 不能
    分类贵、标记便宜。第一跳做一次昂贵的深度分类，把结论写进 DSCP 的 6 个 bit，后面几十跳只需要读这 6 个 bit——"流状态"被压缩成包里的几个 bit，转发设备无需记住任何一条流；而 IntServ/RSVP 要求每条流沿途预留状态，在骨干上根本装不下。
  4. 高级什么是 MTU？为什么说分片有害？PMTUD 为什么在真实网络里经常失效？

    MTU 是链路层单帧能承载的最大载荷，以太网默认 1500 字节（指 IP 包上限，不含以太网头；整帧上限 1518，带一层 VLAN 是 1522）。IP 包超过路径上某段的 MTU 就要分片，或者被丢弃并回 ICMP。「分片有害」要能给出多条理由，从最直观到最隐蔽：

    1. 丢包率被放大。任意一片丢失整个数据报就报废。单片丢包 1% 时数据报失败率跳到 1−0.99³ ≈ 2.97%，切成 10 片是 9.6%——分片把线性的丢包变成了指数的失败。
    2. 后续分片没有传输层头。只有第一片带 TCP/UDP 头，片 2 之后看不到端口号：五元组 ACL 匹配不了、LB 哈希算不出来（可能把同一数据报的分片发到不同后端）。于是防火墙只有两个糟糕的选择：自己重组后再判断（耗内存、加时延、成为攻击面），或者直接丢弃非首片（业务莫名不通）。
    3. 重组是状态与内存开销，也是攻击面。目的主机必须为"等其余分片"保留缓冲直到超时（Linux 默认 30 秒）——重叠分片、只发首片占满重组队列，是一整个家族的攻击手法。
    4. 硬件卸载全部失效。TSO/GRO/LRO、RSS、校验和卸载都不处理分片，一出现分片就掉到软件慢路径。

    IPv4 与 IPv6 的根本差别是"谁有权分片"：IPv4 下源端和路径上任何路由器都能分（只要 DF=0）；IPv6 下只有源端能分，路由器一律丢包并回 ICMPv6 Type 2（Packet Too Big），同时规定所有 IPv6 链路 MTU 至少 1280 字节作为永远安全的下界。这把责任放回了唯一有能力承担它的一方——源端知道自己在发什么、可以探测、可以选择"改小消息"而不是"切开消息"。

    PMTUD 的原理是"故意撞墙，靠回音测距"：发送方给所有包置上 DF 位，遇到 MTU 不够的链路时那台路由器丢包并回一个带下一跳 MTU 的 ICMP（IPv4 是 Type 3 Code 4，IPv6 是 Type 2），发送方据此下调估计并重发。

    为什么经常失效——先给结构性原因再列场景。结构性缺陷是：PMTUD 让一个端到端的机制去依赖第三方主动发起的反向通知。在有 anycast、ECMP、无状态防火墙和隧道翻译的现代网络里，这个假设天然不可靠：

    • ICMP 被一刀切。"禁用 ICMP 提升安全性"是流传极广的错误建议，很多 ACL 直接 deny icmp any any，把 Type 3 Code 4 一并挡了。最常见的一种。
    • ECMP / Anycast 让 ICMP 走错机器。多台服务器共享一个 IP，ICMP 回到哈希算出来的某一台，而发大包的是另一台——收到 ICMP 的那台根本没有这条连接。
    • 隧道端点不透传。GRE/IPsec/VXLAN 加了外层头使内层可用 MTU 变小，ICMP 打给隧道端点，端点要能正确翻译成内层的 ICMP——很多实现做不到。这是"VPN 里打不开某些网页"的经典成因。
    症状叫「MTU 黑洞」，它的欺骗性在于"看起来一切正常"
    ping 通、DNS 通、TCP 握手通（SYN 很小）、SSH 登录也通，一旦传大数据就彻底挂住，不报错也不断连——TCP 只知道"没收到 ACK"，就按指数退避一遍遍重发同一个超大段。判据记牢：小请求秒回、大响应必挂，先怀疑 MTU 不要查应用。巨帧的"半通"（两端配 9000、中间某台还是 1500）是同一个病。
    # 验证 MTU 千万不要用默认 ping，要带 DF 位 + 指定长度二分
$ ping -M do -s 1472 <对端>      # 1472 = 1500 - 20 IP头 - 8 ICMP头
ping: local error: message too long, mtu=1500   ← 本机就挡住了

# 逐跳看 PMTU；以及确认那个 ICMP 到底有没有回来
$ tracepath <对端>
$ tcpdump -nn 'icmp[icmptype] == 3 and icmp[icmpcode] == 4'

# 分片的硬证据
$ tcpdump -nn 'ip[6:2] & 0x1fff != 0'          # 抓非首片
$ netstat -s | grep -i reassemb                # 持续增长的 reassembles failed

    补救手段与各自的边界：① MSS clamping——路径上的设备拦下 TCP SYN 改写 MSS 选项（iptables … TCPMSS --clamp-mss-to-pmtu，匹配条件写 --tcp-flags SYN,RST SYN 是为了同时命中 SYN 和 SYN+ACK）。局限很硬：只管 TCP，对 UDP/QUIC/ESP 完全无效。② PLPMTUD（RFC 4821 / 8899）——不依赖 ICMP，靠探测包二分路径 MTU，Linux 上是 tcp_mtu_probing，方向最正确，代价是收敛要几个 RTT。③ 静态调小 MTU——最粗暴最可靠，缺点是全局降效率。④ 应用层自己保守——UDP 类协议唯一可靠的办法。

    最能体现深度的一句收尾
    根治方向是"不产生大包"而不是"让大包能过"，是"自己探测"而不是"依赖别人帮忙"。DNS 社区把 EDNS0 缓冲降到 1232 字节，QUIC 把初始包限制在 1200 字节内并内建自己的 PMTU 探测。顺带说前传一般不用巨帧——9000 字节的帧在 1 Gbps 上串行化时延就是 72 µs，对百微秒级预算是硬伤。见 网络常见机制。

网络性能

四把尺子与 BDP、为什么看分位数、bufferbloat、抓包的可信边界

共同主题是"你测到的数字，和你以为它代表的东西不是一回事"：带宽够却传不快、均值好看而用户在骂、抓包里的包线上根本不存在。能算的人不少，知道"这个数字什么时候不能信"的人很少。

点击每道题展开参考答案（先自测，再对照）。

  1. 基础延迟、吞吐、抖动、带宽有什么区别？为什么实时系统最怕抖动？为什么"带宽够却传不快"？

    四把尺子先分清：带宽是链路的理论容量（有几车道）；吞吐是实际达到的速率（每秒真过多少车）；延迟是一个包从发到收的时间；抖动是延迟的波动。差距来自协议开销、丢包重传、拥塞、对端处理能力。

    时延由四部分组成，而只有一部分会抖——这张表是整道题的核心：

    组成怎么算典型量级会抖吗
    串行化时延（把帧推上线路）帧长 ÷ 链路速率1500 B @ 1 Gbps = 12 µs；9000 B = 72 µs不抖（帧长固定时）
    传播时延（信号在介质里跑）距离 ÷ 介质中光速，光纤约 5 µs/km10 km 单程 = 50 µs；1000 km = 5 ms完全不抖，是物理下限
    处理时延（查表、改头、校验）看设备实现硬件转发 < 几 µs；掉到 CPU 慢路径可到几百 µs软件路径会抖
    排队时延（在出口队列里等）队列深度 ÷ 出口速率0 到几十毫秒抖动几乎全部来自这里

    两个可以直接用的推论：① 传播时延是硬下限，任何软件优化都动不了它——两地相距 200 km 往返至少 2 ms，这就是"低时延业务必须把计算搬近"（MEC）的物理基础；② 要降抖动只能管队列，QoS、AQM、限速整形都在做同一件事：让关键流量少排队。加带宽不一定能降抖动——只要突发仍会瞬时填满队列，抖动照旧。

    为什么实时系统最怕抖动：实时流靠固定节奏播放，抖动大会让接收侧缓冲一会儿欠载（卡顿）、一会儿溢出（丢帧）。而对抗抖动的唯一手段是抖动缓冲，它用固定时延换平滑——缓冲越大越平滑、总时延越高，所以抖动直接抬高了系统的时延底线。

    "带宽够却传不快"是必然的追问，答案是 BDP——带宽 × RTT，即"这条路径上最多能同时装多少未确认数据"，窗口小于它就跑不满：

    路径BDP = 带宽 × RTT窗口不够时会发生什么
    跨洲 1 Gbps，RTT 100 ms100 Mbit = 12.5 MB窗口缩放没生效（上限 65535 B）时吞吐 = 65535 B ÷ 0.1 s ≈ 5.24 Mbps——千兆链路只跑出 5 Mbps，而且丢包率是 0。这是"链路没问题、但就是慢"最经典的成因
    同机房 10 Gbps，RTT 0.2 ms250 KB默认配置轻松覆盖，永远碰不到——BDP 只在"高带宽 × 高时延"的长肥管道上才是问题
    陷阱：调大缓冲之前先确认瓶颈真的是窗口
    ss -ti 里 cwnd 远小于 BDP/MSS → 瓶颈是拥塞控制（路径上有丢包，该查丢包或换算法，BBR 在有一定丢包的长路径上通常明显好于 CUBIC）；cwnd 已经很大但吞吐上不去、且对端通告窗口很小 → 瓶颈才是接收缓冲，这时才该调 tcp_rmem。两者解法完全相反，而盲目调大缓冲的副作用正是下一题的 bufferbloat。
  2. 中级为什么时延要看 P99 而不是均值？测 P99 有哪些坑？

    结论：均值会被海量的快路径拉平，而 SLA 是被尾巴决定的。一个真实例子：某内存分配路径 P50 是 20 ns、均值 25 ns，而 P99.99 是 100 µs——比均值差四千倍。只看均值，这条尾巴在报表上完全不存在，但用户每天都在碰它。

    指标回答什么为什么不够 / 为什么重要
    均值"总体大概多快"被快路径拉平，对长尾完全不敏感；且不可加总
    P50 / 中位数"典型请求多快"比均值抗离群点，但同样看不见尾巴
    P99"1% 的请求有多糟"看起来严格，但一个页面发 100 个请求时，几乎每个页面都会碰到一次
    P99.9 / P99.99"尾巴到底有多长"低时延系统真正要守的指标；测准 P99.99 至少要百万量级样本
    Max"最坏情况"对硬实时有意义，但单个离群点容易由环境噪声造成

    三个测量坑，能说出来就说明真的量过：

    1. 协调遗漏（coordinated omission）——最致命的一个。闭环压测客户端"发一个、等回来、再发下一个"，于是系统卡顿期间客户端根本不发请求，慢样本压根没被采集，尾部被系统性低估几个数量级。必须换成固定速率的开环发包。
    2. 打点开销本身会改变被测系统。clock_gettime 约 22 ns，一个包打两个点就 44 ns——在 67 ns 的预算里占 66%。解法是采样（固定或随机间隔，不能按内容筛，否则会系统性漏掉你要找的那类慢包）、rdtsc、或网卡硬件时间戳。
    3. 直方图必须每线程一份。多线程共享一个直方图再加锁，你测到的将是锁的时延而不是业务的时延。

    怎么记录分位数：不能"把所有样本存下来再排序"。标准做法是 HdrHistogram 式的对数-线性分桶——按最高有效位选指数桶，桶内再线性细分。这样相对精度恒定、内存有界（约 30 KB）、记录是 O(1) 的几条位运算。

    # 看单条连接的 RTT、抖动与重传 —— 业务流量的真实视角
$ ss -tin | grep -A1 203.0.113
   cubic wscale:8,8 rtt:98.7/1.2 mss:1448 cwnd:1420 retrans:0/312
#   rtt:均值/偏差 —— 偏差大就是抖；retrans 是累计值，要配合时间看增速
#   cwnd 远小于 BDP/MSS → 瓶颈在拥塞控制，不在接收缓冲

# ping 的 mdev 只能当粗略抖动指标
$ ping -c 100 -i 0.2 203.0.113.10 | tail -1
rtt min/avg/max/mdev = 0.198/0.241/1.902/0.118 ms
#   min 才是"没有排队时"的真实时延，max-min 就是最坏排队
#   ⚠ 很多设备把 ICMP 放低优先级或限速，它不能代表业务流量
    面试时最实用的一句收尾
    被问"你怎么验证一个性能优化真的有效"，答案里必须有"先量后改、改完再量同一个指标"这个闭环，再加两条：对比必须在同一份真实负载上；看分位数而不是均值，因为很多"优化"是拿尾部换均值（批处理就是典型）。见 高性能网络编程。
  3. 中级什么是 bufferbloat？为什么"缓冲区越大越好"是错的？怎么判断和处置？

    结论：bufferbloat 是"设备配了远超需要的缓冲区，于是拥塞时数据包不被丢弃、而是排在队里等"。吞吐没掉，但排队时延暴涨到几百毫秒甚至几秒。对交互业务这比丢包糟得多——丢包可以重传，时延无法追回。

    为什么"越大越好"是错的？把队列长度换算成时间就清楚了。一个 128 包的 FIFO（老家用路由器的常见默认值）满队时 192 000 字节：

    链路速率满队排队时延 = 192 000 B ÷ 速率后果
    1 Gbps1.54 ms可以接受
    100 Mbps15.4 ms开始影响交互
    10 Mbps154 ms语音明显卡
    1 Mbps1 536 ms一秒半——网页点了没反应

    同一个"合理"的队列长度，在不同速率下时延差 1000 倍——所以按【包数】设队列长度是错的，要按【时间】设。

    为什么会一路涨到把缓冲填满？因为基于丢包的拥塞控制只认丢包这一个信号。发送方持续加速，直到队列溢出才知道该退让。缓冲区越大，"发现拥塞"就被推迟得越久，稳态时队列一直接近满；而吞吐几乎不受影响——这正是 bufferbloat 长期没被发现的原因。

    AQM（主动队列管理）的思路是不等溢出，提前少量地丢包或打 ECN 标记，把队列压在一个短的长度上。三代方案的演进思路很值得体会：

    算法判断依据解决了什么遗留问题
    Tail Drop队列满了才丢（基线）时延失控；全局同步——大家一起退让又一起加速
    RED平均队列长度超阈值后按概率丢提前预警、打散全局同步参数极难调：合适的队列长度取决于速率和流数，换场景就要重调
    CoDel包在队列里的驻留时间是否持续超过 target（5 ms）无需调参，直接盯时延单队列，防不住一条大流挤占交互流
    FQ-CoDel按流哈希分成上千个子队列，各跑一份 CoDel流间隔离：大下载压不住语音流哈希碰撞时两条流互相影响；隧道流量看不到内层五元组
    CAKEFQ-CoDel + 内建整形 + DSCP 感知整形、AQM、公平打包成一条命令CPU 开销更高；需要准确告知链路速率
    CoDel 最关键的设计洞见，值得单独记住
    它测的是时延，不是队列长度。"多长的队列算太长"没有普适答案（取决于速率、流数、包长分布），而"包在队里等了多久算太久"有——5 ms，对任何速率都成立。把控制目标从一个依赖环境的量换成一个不依赖环境的量，参数就自然消失了。
    # 判断有没有 bufferbloat：backlog 是最重要的一个数
$ tc -s qdisc show dev eth0
qdisc fq_codel 8003: root refcnt 2 limit 10240p flows 1024 target 5ms interval 100ms ecn
 Sent 84930215744 bytes 61582301 pkt (dropped 4127, overlimits 0 requeues 812)
 backlog 262144b 173p requeues 812
  new_flow_count 90412 ecn_mark 51903 drop_overlimit 0
  new_flows_len 0 old_flows_len 3
    字段怎么判读
    backlog最重要的一个数。持续非零 = 这个口是瓶颈。用 backlog字节 / 链路速率 换算成时延：262144 B @ 1 Gbps ≈ 2.1 ms 尚可，几十毫秒就是 bufferbloat
    droppedfq_codel 下少量丢包是正常且必要的——那是 AQM 在工作。4127 / 6158 万 ≈ 0.007%，健康
    ecn_mark非零说明对端支持 ECN，拥塞信号在不丢包的前提下传达出去了
    drop_overlimit不该非零。非零意味着撞到队列上限、AQM 来不及生效——带宽严重不足，或 limit 配得太小
    old_flows_len个位数 + backlog 大 = 少数大流在占队列，FQ 正在保护其它流
    一个真实案例，也是最好记的处置模板
    一条 10 Mbps 上行专线，"一边上传日志一边 SSH 回显要等两三秒"。ping 空闲 8 ms、上传时涨到 1400 ms——出口 qdisc 是 pfifo_fast，1000 包的默认队列在 10 Mbps 上就是 1.2 秒。处置只有一条命令：tc qdisc replace dev eth0 root cake bandwidth 9.5Mbit。吞吐从 9.6 降到 9.4 Mbps，而上传期间的 ping 从 1400 ms 回到 12 ms。关键细节：整形速率必须略低于真实链路速率，否则瓶颈仍在运营商侧那个你管不到的队列上，本地 AQM 完全失效。
    陷阱：不要抄网上的 sysctl 大礼包
    那一长串是别人在别人的负载与内核版本上试出来的。两个典型后果：① 把 rmem/wmem 一律拉到很大，制造出主机侧自己的 bufferbloat；② 覆盖掉发行版默认的 fq_codel 退回 pfifo_fast，反而让时延变差。正确顺序永远是先测量、定位瓶颈、只改一个参数、然后复测。
  4. 高级你在服务器上抓到的包，和线上真实的包为什么可能不一样？

    结论：抓包不是"网络的照片"，而是"内核在某个特定位置的记账"。用它之前必须清楚这个位置在哪、记了什么、漏了什么。答案有三层，能答到第三层就说明真的排查过难题。

    ① 位置：抓包钩子不在线路上。tcpdump 通过 AF_PACKET 挂在网络设备层——收方向是驱动把 skb 交给协议栈之后，发方向是内核把 skb 交给驱动之前。而现代网卡的大量工作恰好在这两个点之外：

    机制抓包里看到的线上实际的
    TSO / GSO发送侧一个 length 65160 的"超大包"不存在这样的帧，硬件会切成几十个 ≤MTU 的段
    GRO / LRO接收侧少数几个大包多个帧被合并，包数、到达间隔、时序全部失真
    校验和卸载发送方向校验和还没填，Wireshark 报 "checksum incorrect"校验和是对的——那是假警报
    VLAN 卸载看不见 VLAN 标签链路上确实带着（标签被剥到 skb 元数据里）
    XDP什么都看不到报文在更早阶段就被 DROP / REDIRECT 了

    ② 时间：抓包时间戳不是上线时刻。它是内核软件打的，与包真正上线的时刻有几微秒到几十微秒的偏差而且会抖。所以抓包适合回答"发生了什么"，不适合回答"精确什么时候发生"；要微秒级精度必须用网卡硬件时间戳（SO_TIMESTAMPING / PTP）。

    ③ 观察行为本身会改变系统——这一层最少有人答到。抓包要抢 CPU，高流量下 tcpdump 自己会丢包；而为了看清真实分段去 ethtool -K eth0 tso off gso off gro off，CPU 开销、吞吐和时延特征都变了，你测的已经不是原来那个系统。正确姿势是先在开着卸载的状态下判断"是不是这一类问题"，确定要看真实分段时才关，且只关必要的那项。
