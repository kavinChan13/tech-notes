00

概览

LLM 后端不是"在模型前面套个 Web 服务器"——它需要感知 GPU 状态、管理 Tok…

LLM 后端不是"在模型前面套个 Web 服务器"——它需要感知 GPU 状态、管理 Token 配额、处理流式输出、实现智能路由。每个请求的资源消耗可能差 1000 倍，这让传统 Web 架构的经验几乎失效。

五层架构，每层职责清晰、可独立扩展——接入层接请求，网关层守门，调度层分流，推理层算模型，模型层跑 GPU。

核心设计原则

原则说明
无状态服务推理节点无状态，会话状态外存 Redis/DB，便于水平扩展
异步解耦请求入队列（Kafka），推理服务消费，避免直接耦合
可观测性每层集成 Prometheus 指标、OpenTelemetry 链路追踪和日志
优雅降级大模型不可用时自动降级至小模型或缓存兜底
推理层必须无状态设计——因为 GPU 节点随时可能 OOM 崩溃或被扩缩容替换。有状态数据（会话历史、Token 配额）全部外存到 Redis/DB，推理节点只负责"拿 Prompt 跑模型返回结果"。

API Gateway

API Gateway 是 LLM 后端的"守门人"——挡住不合法的请求，限制每个用户的用量…

API Gateway 是 LLM 后端的"守门人"——挡住不合法的请求，限制每个用户的用量，把合法请求转发给后面的推理集群。

认证鉴权

方式场景实现
API Key服务端调用、第三方集成Header Authorization: Bearer sk-xxx，网关校验后透传
OAuth 2.0用户端应用、多租户平台JWT 验签，从 Claims 提取 tenant_id、quota
mTLS内部微服务互调双向证书校验，零信任网络内认证

限流策略

LLM 场景的限流比传统 API 复杂得多——一个 10 token 的请求和一个 10000 token 的请求消耗差 1000 倍。需要多维度限流：

维度说明实现方式
RPM请求/分钟Token Bucket 算法
TPMToken/分钟Redis INCRBY + EXPIREAT 滑动窗口
日/月额度总预算控制Redis 持久化计数器

配额管理

机制说明
租户隔离每个 API Key 绑定独立配额，互不影响
预扣 + 修正请求前预估 max_tokens 扣减，完成后按实际 Token 退还差额
超额策略软限制（告警）→ 硬限制（拒绝）→ 降级（切小模型）
LLM 限流的核心是 Token 级限流而非 QPS 限流。分布式限流用 Redis + Lua 脚本保证原子性——INCRBY 增加消耗量，EXPIREAT 设置窗口过期，一条 Lua 脚本完成判断+扣减的原子操作。
03

流式输出 (SSE / WebSocket)

LLM 每生成一个 Token 就立即推送给客户端——用户 ~100ms 就能看到第一个字…

LLM 每生成一个 Token 就立即推送给客户端——用户 ~100ms 就能看到第一个字，而不是等数秒后才一次性返回全部。这就是流式输出的核心价值。

SSE vs WebSocket

维度SSEWebSocket
通信方向单向（服务端 → 客户端）双向
协议基于 HTTP，天然穿透代理/CDN独立协议，需额外配置
自动重连原生支持需自行实现
适合场景LLM 输出（绝大多数场景）中途修改方向、音频流

流式 vs 非流式对比

维度流式 (stream=true)非流式 (stream=false)
首 Token 延迟~100ms（立即看到）数秒~数十秒（全部生成后返回）
用户体验逐字打字效果长时间白屏等待
连接占用长连接短连接
适用场景聊天、实时翻译、代码补全批处理、离线摘要

流式中断处理

场景处理方式
客户端取消AbortController.abort()，后端检测连接断开后终止推理
后端超时设置 max_tokens 上限，超时自动截断
部分结果中断时已生成的 Token 保存至 DB，可展示部分结果
Nginx/CDN 代理流式响应必须关闭缓冲：proxy_buffering off，否则代理会把 Token 攒到一定量再发，破坏"逐字输出"的体验。这是最常见的流式输出踩坑。
04

多模型路由

并非所有请求都需要最强模型——"翻译一句话"用 7B 模型就行，"分析代码架构"才需要 72…

并非所有请求都需要最强模型——"翻译一句话"用 7B 模型就行，"分析代码架构"才需要 72B。智能路由可以在保证质量的同时降低 40~60% 成本。

多模型路由流程 ┌──────────┐ │ 用户请求 │ └─────┬────┘ ▼ ┌──────────────┐ │ 路由判断器 │ │ (Router) │ └──┬──────┬────┘ 简单请求 │ │ 复杂请求 ▼ ▼ ┌────────┐ ┌────────┐ │ 小模型 │ │ 大模型 │ │ 7B/14B │ │ 72B/API│ │ 成本 1x │ │ 成本 20x│ └────────┘ └────────┘

路由判断方法

方法原理延迟准确度
关键词规则正则匹配："翻译"→小模型，"分析代码"→大模型<1ms低
文本分类器BERT/FastText 判断难度等级~5ms高
意图识别NLU 引擎识别意图 + 实体，映射到模型能力~10ms最高
级联策略先用小模型生成，置信度低时升级大模型可能翻倍高质量

级联策略详解

级联策略是最实用的路由方式：先用小模型生成，检查质量分（logprob 均值），低于阈值时升级到大模型。

优势：60~70% 的请求可以用小模型满足，整体成本降低 40~60%。劣势：质量不达标的请求延迟翻倍（小模型 + 大模型两次推理）。

A/B 测试

环节做法
流量分割按用户 ID 哈希分桶，5% 流量走新路由策略
指标对比响应质量（LLM-as-Judge）、延迟 P50/P99、成本/请求
灰度发布5% → 20% → 50% → 100% 逐步放量
自动回滚质量指标低于阈值时自动切回旧策略
路由器本身的性能开销必须 <10ms——否则抵消了小模型的速度优势。关键词规则 + 轻量分类器的组合是最优方案：规则处理明确场景（0ms），分类器兜底不确定场景（5ms）。

限流与熔断

LLM 推理又慢又贵——当模型开始频繁超时或 OOM，必须快速"切断"问题链路，防止雪崩

LLM 推理又慢又贵——当模型开始频繁超时或 OOM，必须快速"切断"问题链路，防止雪崩。这就是熔断器的价值。

熔断器三状态

熔断器状态机 ┌────────┐ 失败率 < 阈值 ┌────────┐ │ CLOSED │ ──────────────▶ │ CLOSED │ 正常调用 │ (正常) │ │ (正常) │ └────┬───┘ └────────┘ │ 失败率 > 50% ▼ ┌────────┐ 超时后尝试 │ OPEN │ ──────────────▶ ┌───────────┐ │ (熔断) │ │ HALF-OPEN │ └────────┘ │ (半开探测) │ ▲ └──────┬────┘ │ 探测失败 │ 探测成功 └─────────────────────────────┘ ▼ ┌────────┐ │ CLOSED │ 恢复正常 └────────┘

熔断参数

参数推荐值说明
监控指标—推理超时率、GPU OOM 率、5xx 错误率
熔断条件失败率 > 50%最近 60s 内且请求数 > 20
熔断时间30s ~ 5min初始 30s，每次失败加倍
半开探测1 个请求成功则恢复，失败则继续熔断

多级降级策略

级别策略说明
L1 轻度缓存兜底返回语义相似问题的缓存答案
L2 中度切换小模型大模型不可用时降级为 7B 模型
L3 重度模板回复"服务繁忙，请稍后再试"
L4 极端功能关闭关闭 AI 功能，仅保留基础功能
并发控制也很关键：每个用户最多 N 个并发推理请求（信号量模式），超出排队。GPU 感知调度根据显存/算力剩余动态调整并发上限。付费用户走优先级队列，免费用户低优先级排队。

幂等性设计

LLM 推理成本高（一次请求可能消耗数千 Token），网络抖动导致的重复请求会造成重复扣费…

LLM 推理成本高（一次请求可能消耗数千 Token），网络抖动导致的重复请求会造成重复扣费、浪费 GPU 算力、会话历史污染。幂等性保证"同一请求执行一次和执行多次效果一样"。

幂等键方案

方案生成方式优缺点
客户端 UUID（推荐）Header Idempotency-Key: uuid灵活，客户端控制粒度
内容哈希sha256(user_id + model + messages_hash)自动去重，但粒度粗

幂等处理流程

幂等处理流程
请求到达
查 Redis 缓存 key = "idempotent:{idempotency_key}"
命中 未命中
直接返回
缓存结果 加分布式锁 ← 防并发重复
执行推理
结果写 Redis TTL = 24h

重试安全

策略说明
指数退避重试间隔 1s → 2s → 4s → 8s，避免雪崩
抖动 (Jitter)delay = base × 2^attempt + random(0, base)，打散重试峰值
最大重试通常 3 次，超过进入 Dead Letter Queue
可重试判断5xx 和超时可重试，4xx（参数错误）不重试
流式接口的幂等性比较特殊：首次请求建立流式连接，相同幂等键的重复请求返回已有流的读取端。幂等缓存的 TTL 应大于客户端最大重试周期，通常设 24h。

会话管理

LLM 本身是无状态的——每次调用都是独立的

LLM 本身是无状态的——每次调用都是独立的。多轮对话的上下文需要后端维护：加载历史消息 → 拼接 System Prompt → 截断超长对话 → 发送给模型。

上下文窗口管理策略

策略原理优缺点
尾部截断保留 System Prompt + 最近 N 轮简单，但丢失早期重要信息
摘要压缩用 LLM 对早期对话生成摘要替换原文保留语义，但引入额外推理成本
滑动窗口 + 摘要最近 K 轮保留原文，更早的做摘要平衡效果与成本（推荐）
RAG 增强历史对话存入向量库，检索相关片段注入适合超长会话，需向量检索基础设施
滑动窗口 + 摘要策略 上下文预算 = MAX_TOKENS - System Prompt - 输出预留 ┌──────────────────────────────────────────┐ │ System Prompt │ 早期摘要 │ 最近 K 轮原文 │ 输出预留 │ (始终保留) │ (LLM压缩) │ (完整保留) │ (20%) └──────────────────────────────────────────┘ 触发条件: 累计 Token > 窗口 70% 时，对早期消息做摘要 压缩比: 约 5:1 ~ 10:1

会话存储方案

存储场景特点
Redis活跃会话（24h 内）高性能读写，TTL 自动过期
PostgreSQL持久化 + 审计事务安全，支持全文检索
Redis + DB混合方案（推荐）Redis 热数据快速读写，异步写入 DB 持久化
Redis 会话过期后的恢复流程：从 DB 加载完整消息历史 → 检查是否需要摘要压缩 → 重建 Redis 缓存。多端同步问题（用户在手机和电脑同时对话）需要基于 session_id 共享状态，而非基于连接。

负载均衡

LLM 推理与传统 Web 服务不同——请求耗时从秒到分钟不等，资源消耗差 100 倍

LLM 推理与传统 Web 服务不同——请求耗时从秒到分钟不等，资源消耗差 100 倍。传统轮询完全不适用，需要 GPU 感知的智能调度。

负载均衡策略对比

策略原理LLM 适用性
加权轮询按权重循环分配，A100 权重高于 T4⭐⭐⭐ 简单有效
最小连接数选当前连接最少的节点⭐⭐ 不感知请求复杂度差异
GPU 感知基于 GPU 利用率 + 显存实时选择⭐⭐⭐⭐⭐ 最优
Queue-based请求入全局队列，空闲 GPU 主动拉取⭐⭐⭐⭐ 充分利用资源

GPU 感知打分

score = gpu_util × 0.4 + (memory_used / memory_total × 100) × 0.3 + queue_depth × 0.3

选 score 最低的节点——GPU 利用率 40% 权重 + 显存占用 30% 权重 + 队列深度 30% 权重。GPU 指标通过 DCGM Exporter → Prometheus → 路由器定时拉取。

Queue-based 调度

Queue-based 调度 请求 ──▶ ┌─────────────────────┐ ──▶ GPU Node 1 (空闲 → 拉取) 请求 ──▶ │ 全局任务队列 │ ──▶ GPU Node 2 (空闲 → 拉取) 请求 ──▶ │ (Redis/Kafka/NATS) │ ──▶ GPU Node 3 (忙碌 → 等待) 请求 ──▶ └─────────────────────┘ ──▶ GPU Node 4 (空闲 → 拉取)

跨区域部署

策略说明
就近接入DNS GeoDNS / Anycast 将用户路由到最近区域
区域自治每个区域独立部署完整推理栈，避免跨区调用
溢出路由本区域 GPU 满载时，溢出到其他区域或云 GPU
数据合规敏感数据不出境，特定区域使用特定模型版本
LLM 扩容速度是传统 Web 服务的痛点：传统容器秒级启动，LLM 推理节点加载 30GB+ 模型需要分钟级。解决方案：预热节点提前加载模型 + 云 GPU（按量计费）作为弹性备份。

成本控制

LLM API 是 AI 应用的最大成本项

LLM API 是 AI 应用的最大成本项。五把降本利器：语义缓存（省 20~40%）、模型路由（省 40~60%）、Prompt 精简（省 10~30%）、Batch API（省 50%）、量化部署（省 30~50%）。

Token 计量计费

环节做法
定价表每个模型配置 input/output 单价（$/1K tokens）
实时计量推理完成后记录 (model, input_tokens, output_tokens, cost)，异步写入时序数据库
预算告警50% / 80% / 95% / 100% 分别触发提醒/警告/告警/拒绝
自动策略超预算后自动降级（大模型→小模型→缓存兜底）

缓存减少重复调用

缓存类型实现方式命中率
精确缓存Prompt 完全一致时命中，Hash 做 Key低（5~15%），FAQ 场景高
语义缓存Prompt Embedding 相似度 > 0.95 时命中中（15~40%），需向量数据库
KV Cache推理引擎层面复用 Prefix 的注意力缓存高（System Prompt 接近 100%）

语义缓存原理

用户提问 → 生成 Embedding → 在向量数据库中搜索相似度 > 0.95 的历史问题 → 命中则直接返回缓存答案，跳过 LLM 推理。相似度阈值是关键参数：过高则命中率低，过低则答案不准。需要通过评估集调优。

Batch API

特点说明
成本优势OpenAI Batch API 价格为实时 API 的 50%
调度窗口24h 完成窗口，系统在低峰期执行，最大化 GPU 利用率
适用场景日报生成、批量翻译、数据标注等非实时场景
  • 语义缓存优先：最直接的降本手段。相似问题复用 LLM 答案，可降低 20~40% API 费用。用向量数据库和相似度阈值控制质量。
  • GPU 感知调度：基于实时 GPU 利用率和显存选择节点，避免部分 GPU 过载而其他空闲。DCGM Exporter + Prometheus 是常见组合。
  • 用 QPS 限流：LLM 请求消耗差异巨大，10 token 和 10000 token 的资源占用完全不是一个量级。只看 QPS 无法反映真实成本，应该做 Token 级限流。
  • 传统轮询负载均衡：LLM 推理耗时从秒到分钟不等，轮询会导致部分 GPU 严重过载。更合适的是 GPU 感知调度或基于队列的调度。
核心要点：LLM 后端与传统 Web 后端的根本区别在于"每个请求的资源消耗差异巨大"。这导致限流需要 Token 级、负载均衡需要 GPU 感知、路由需要智能分级。成本控制的核心是"用最小的模型满足需求"——语义缓存 + 模型路由 + Batch API 三板斧可降低 50~70% 总成本。

Q&A

核心功能：认证鉴权（API Key/OAuth）、多维限流（RPM/TPM/并发）、流式代理…
设计一个 LLM API Gateway，需要考虑哪些核心功能？

核心功能：认证鉴权（API Key/OAuth）、多维限流（RPM/TPM/并发）、流式代理（SSE 透传 + proxy_buffering off）、路由分发（按模型/用户等级/请求特征）、配额管理（实时 Token 计量 + 预扣修正）、可观测性（日志/链路追踪/指标）、安全防护（Prompt 注入检测/敏感内容过滤）。

SSE 和 WebSocket 在 LLM 流式输出场景下如何选择？

SSE 优先（大多数场景）：LLM 输出是单向推流，SSE 天然适合；基于 HTTP 穿透代理/CDN；自动重连。WebSocket 仅在需要双向通信（中途修改方向）、二进制传输（音频流）、高频交互（协作编辑+AI 补全）时使用。

如何设计多模型路由系统实现成本优化？

核心思路：用最小的模型满足需求。请求分级（轻量分类器 Easy/Medium/Hard）→ 模型映射（7B/14B/72B）→ 级联兜底（小模型质量不够升级大模型）。实践效果：60~70% 请求用小模型，成本降低 40~60%。关键约束：路由器判断 <10ms，否则抵消小模型速度优势。

LLM 后端如何实现 Token 级别的限流？

预估扣减：请求到达时按 input_tokens + max_tokens 预扣配额；实际修正：推理完成后按实际 output_tokens 退还差额。实现方式：Redis + Lua 脚本保证原子性，Sorted Set 实现滑动窗口。同时限制 TPM（Token/分钟）和 RPM（请求/分钟）。

如何设计 LLM 服务的熔断和降级策略？

熔断：监控推理超时率/GPU OOM 率/5xx 错误率，60s 内失败率 >50% 触发熔断，30s 后进入半开探测。多级降级：L1 缓存兜底 → L2 切小模型 → L3 模板回复 → L4 关闭 AI 功能。降级应自动化：监控指标 → 告警 → 自动降级 → 恢复后自动恢复。

LLM 场景下如何实现请求幂等性？

客户端在 Header 传递 Idempotency-Key（UUID），服务端以此为维度去重。处理流程：查 Redis 缓存 → 未命中加分布式锁 → 执行推理 → 结果写缓存（TTL 24h）→ 释放锁。流式幂等：首次建立流，重复请求返回已有流的读取端。

多轮对话中如何管理上下文窗口？

推荐滑动窗口 + 摘要混合策略：始终保留 System Prompt + 最近 3~5 轮原文，当累计 Token 超过窗口 70% 时对早期消息做摘要压缩（压缩比 5:1~10:1）。总上下文 = System Prompt + 摘要 + 最近 N 轮 + 输出预留（20%）。超长会话可结合 RAG 增强：历史对话 Embedding 存入向量库，检索相关片段补充。

LLM 推理服务的负载均衡与传统 Web 服务有何不同？

三大差异：请求耗时差异大（秒~分钟 vs 毫秒级）、资源消耗差异大（GPU 显存 vs CPU 差异小）、扩容速度慢（分钟级模型加载 vs 秒级容器启动）。推荐 GPU 感知负载均衡 + 全局队列：推理节点通过 DCGM Exporter 上报 GPU 指标，调度器基于实时指标选最空闲节点，配合 Continuous Batching 最大化吞吐。

如何设计 LLM 的成本监控和优化系统？

计量系统：每次推理记录 (model, tokens, cost, latency)，异步写入时序数据库，实时流处理计算分钟级用量。优化手段按效果排序：语义缓存（20~40%）> 模型路由（40~60%）> Prompt 精简（10~30%）> Batch API（50%）> 量化部署（30~50%）。

如何保障 LLM 后端系统的高可用性（SLA 99.9%）？

冗余部署（至少 2 个 AZ，每 AZ 至少 2 个推理节点）、深度健康检查（实际执行推理而非 ping）、自动扩缩（基于 GPU 利用率 HPA + 预热节点）、故障转移（主模型不可用自动切备用）、混合架构（自建 GPU 为主 + 云 GPU 弹性备份）、定期容灾演练（Chaos Engineering）、灰度变更（金丝雀 5% → 蓝绿切换 + 回滚版本）。
