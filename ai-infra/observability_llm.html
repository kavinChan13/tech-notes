LLM Tracing

Span 模型没变，变的是挂什么属性

Trace/Span 概念在 LLM 中的应用

Span 模型本身与普通微服务没有区别（Span 语义约定、 分布式追踪基础）。差别只在往 Span 上挂什么属性。

Prompt → Retrieval → Generation 链路追踪

Parent-Child Span

给一次调用打 Span

只有一个要点：模型、提示词版本、三种 token、成本，全部落在 Span 属性上。

from opentelemetry import trace
tracer = trace.get_tracer("llm-app")

with tracer.start_as_current_span("llm.generate") as sp:
    sp.set_attribute("gen_ai.request.model", model)
    sp.set_attribute("gen_ai.prompt.version", "qa-v7")   # 少了它，回归时说不清是谁改坏的
    rsp = client.chat.completions.create(model=model, messages=msgs)

    u = rsp.usage
    sp.set_attribute("gen_ai.usage.input_tokens",  u.prompt_tokens)
    sp.set_attribute("gen_ai.usage.output_tokens", u.completion_tokens)
    sp.set_attribute("gen_ai.usage.cached_tokens",
                     u.prompt_tokens_details.cached_tokens)  # 缓存命中另算价
    sp.set_attribute("llm.cost_usd", price(model, u))
    # ❌ 不要 sp.set_attribute("llm.prompt_text", prompt) —— 见 §6 高基数与脱敏
知识要点
  • RAG 至少要拆出 Retrieval 与 Generation 两个 Span，否则「慢在检索还是慢在生成」无法定界
  • Agent 嵌套可达 5–10 层，Span 树是发现死循环的唯一手段

Token 用量监控

三种计价 · 三层下钻 · 高基数陷阱

Token 不是一个数，是三个

⚠ 成本风险

一次失控的循环调用能在几小时内烧掉几千美元，而这期间接口全是 200。

「这次调用花了 4500 个 token」几乎没有信息量——它们按三种价目分别计费，单价差 16 倍：

成本归因 (Cost Attribution)

-- 三种 token 各按各的价目累加，再按功能下钻
SELECT feature,
       sum(input_tokens - cached_tokens) * p.in_price  / 1e6
     + sum(cached_tokens)                * p.in_price  / 4e6   -- 命中价约 1/4
     + sum(output_tokens)                * p.out_price / 1e6   AS cost_usd
FROM generations g JOIN model_price p USING (model)
WHERE ts >= now() - interval '1 day'
GROUP BY feature ORDER BY cost_usd DESC;

把 feature 换成 user_id / model，同一条语句就是下一层下钻。排查路径几乎总是这三步：

高基数陷阱：prompt 内容不能当 label

基数的一般性讨论见 label 基数警告 与 Prometheus 数据模型。

预算告警

  • 分层设阈值：日预算 → 小时速率超日均 3 倍 → 单用户单日超 $5 触发限流
  • 自动降级：Z-score > 3 时切便宜模型，先止血再排查

延迟分析

TTFT 与 TPOT 是两个数，不是一个

TTFT 与 TPOT：把「慢」拆成两个互不相干的数

指标受什么支配参考量级
TTFT排队 + 提示词长度0.2 – 2 s
TPOT模型规模 + batch 拥挤度12 – 33 ms/tok
E2E以上二者 + 输出长度2 – 30 s

流式改变的是感知，不是 E2E

流式怎么埋点

非流式一个计时器就够；流式必须在迭代器内部取两个时间点：

t0, first, n = time.perf_counter(), None, 0
for chunk in client.chat.completions.create(**kw, stream=True):
    if not chunk.choices[0].delta.content:
        continue                       # 心跳 / 空 delta 不算首 token
    if first is None:
        first = time.perf_counter()
        TTFT.observe(first - t0)       # 直方图；均值会把长尾抹平
    n += 1
    yield chunk

if first and n > 1:                    # n==1 时 TPOT 无定义，别记成 0
    TPOT.observe((time.perf_counter() - first) / (n - 1))
✅ 对症下药
  • TTFT 高：先看排队与缓存命中率，换小模型对它帮助有限
  • TPOT 高：换小模型或疏解 batch，见 Prefill-Decode 分离
  • 两者都正常、E2E 高：输出太长，查 max_tokens
知识要点
  • 分位数一律走直方图（bucket 设计与 histogram_quantile），均值会抹平长尾
  • 流式只降 TTFT 不降 E2E；SLO 写错对象会否定掉一次有效优化

质量指标

按检测成本排闸

核心质量指标体系

指标怎么算目标
幻觉率NLI 蕴含 / LLM-as-Judge< 5%
用户满意度Up / (Up + Down)> 80%
相关性评分1–5 分，判分器给≥ 4.0
有害内容率安全分类器< 0.1%
拒答率拒答数 / 总请求< 3%

三种质量信号，三种检测手段

这些指标不在一个成本量级上。按检测成本排成流水线，顺序错了钱就白花：

采样回放与打分

thumbs up / down 必须带 trace_id，否则只知道「有人不满意」。主动反馈率通常只有个位数，覆盖面靠回放补：

# 每天回放昨天 1% 的采样：规则先筛，judge 只处理剩下的
for tr in sample(yesterday_traces(), rate=0.01):
    checks = {
        "schema_ok": validate_json(tr.output, SCHEMA),
        "refused":   REFUSAL_RE.search(tr.output) is not None,
        "grounded":  nli_entailment(tr.output, tr.context) > 0.7,
    }
    if checks["schema_ok"] and not checks["refused"] and checks["grounded"]:
        continue                       # 规则能判的，不要花 judge 的钱
    checks["judge"] = llm_judge(tr.question, tr.context, tr.output)
    store_score(tr.id, checks,
                prompt_version=tr.attrs["gen_ai.prompt.version"])  # 归因靠它
⚠ LLM-as-Judge 的三种偏见
  • 长度 / 位置偏见：随机交换位置能消掉后者，前者只能靠 rubric 压
  • 自我偏见：同一家的模型评自己的输出会系统性偏高
  • 没有校准集的分数只是噪声：定期量一次它与人工标注的一致率
知识要点
  • 规则能判的绝不交给 judge，这是成本问题也是准确性问题
  • 反馈必须携带 trace_id 与 prompt_version，否则无法归因

异常类型检测规则级别响应动作

规则语法就是 Prometheus 那一套（PromQL 与告警规则、 Metric 类型）。难的是响了之后往哪儿走：

一条定界查询

「慢」这条线的第一步永远是定界：检索段与生成段的分位数并排看，后面的判断就是机械的。

histogram_quantile(0.95, sum by (le) (
  rate(llm_span_duration_seconds_bucket{span="retrieval"}[5m])))
histogram_quantile(0.95, sum by (le) (
  rate(llm_span_duration_seconds_bucket{span="generation"}[5m])))

# 判据
#  retrieval 涨、generation 平        → 向量库或重排，别去动模型
#  generation 涨、TTFT 平、TPOT 涨    → 推理侧拥挤（batch 或换了模型）
#  generation 涨、TTFT 涨、TPOT 平    → 上下文变长了，去查 ctx_tokens
#  两段都平，E2E 却涨                 → 慢在编排层：串行了本该并行的步骤

🎓 Q&A（10 题）

核心区别在于"语义层面"的不确定性：
Q1: LLM 可观测性与传统微服务可观测性的核心区别是什么？

核心区别在于"语义层面"的不确定性：

  • 输出不确定性：传统服务相同输入 → 相同输出；LLM 同一 Prompt 可能产生不同答案，需要关注输出质量的一致性
  • 错误定义模糊：传统服务有明确的错误码（500/404）；LLM 返回 200 但内容可能是幻觉、不相关或有害内容
  • 新增指标维度：Token 用量/成本、幻觉率、语义相关性评分等传统不需要的指标
  • 数据隐私挑战：Prompt 和 Response 是自然语言，可能包含 PII，日志存储需特殊处理
  • 成本关注：API 调用按 Token 计费，成本波动大，需实时监控
Q2: 如何设计一个 RAG 应用的 Tracing 方案？需要记录哪些关键信息？

RAG Tracing 设计方案：

  • Trace 粒度：一次用户请求 = 一个 Trace，包含多个 Span
  • 关键 Span： ① Query 理解 (query rewrite/expansion) — 输入原始 query，输出改写后的 query
    ② Vector Retrieval — 输入 embedding，输出 top-K chunks，记录检索耗时和数据库
    ③ Reranker — 输入 query + chunks，输出 reranked 结果，记录分数
    ④ Prompt Assembly — 记录最终拼装的完整 prompt（含 system/context/query）
    ⑤ LLM Generation — model、input/output tokens、温度、耗时
    ⑥ Post-processing — 格式化、引用提取等
  • 关键元数据：每个 Span 记录 input、output、duration、status；Generation Span 额外记录 model、token_usage、cost
  • 质量标注：在 Trace 上关联用户反馈 (thumbs up/down) 和自动评估分数
  • Session 关联：多轮对话使用同一 session_id 串联
Q3: LangSmith 和 Langfuse 如何选择？各自的优缺点是什么？

选择依据：

维度LangSmithLangfuse
适用框架LangChain 最佳，其他框架需适配框架无关，任何 LLM 应用均可
部署仅 SaaS（数据托管在 LangChain 服务器）SaaS + 自部署（Docker Compose）
评估能力内置丰富评估器 + Hub 生态Score API 灵活但需自行构建评估逻辑
数据隐私需信任 LangChain 的数据安全可完全自部署，数据不出内网
成本免费 tier 有限，大规模需付费开源免费，自部署仅基础设施成本

建议：已深度使用 LangChain → LangSmith；对数据隐私敏感或非 LangChain 项目 → Langfuse

Q4: 如何实现 LLM 应用的成本归因和预算控制？

成本归因：

  • 每次 LLM 调用记录：user_id、team、feature、model、input_tokens、output_tokens
  • 根据模型价格表自动计算 cost = (input_tokens × input_price) + (output_tokens × output_price)
  • 多维聚合：按用户/团队/功能/模型/时间维度统计

预算控制策略：

  • 前置控制：用户级 Rate Limit（QPM / 日 Token 上限）
  • 实时监控：小时级成本异常检测（> 3 倍均值告警）
  • 自动降级：当成本接近预算时自动切换到更便宜的模型
  • 后置分析：周度/月度成本报告，识别优化机会（如 Prompt 过长、无效重试）
Q5: 什么是 TTFT 和 TPS？它们分别影响什么？如何优化？

TTFT（Time to First Token）：从发送请求到收到第一个 Token 的时间。影响用户的感知延迟——TTFT 越低，用户越快看到响应开始。

TPS（Tokens per Second）：流式输出的 Token 生成速率。影响阅读体验——TPS 过低会导致输出"卡顿"。

优化手段：

  • 降低 TTFT：Streaming 输出、Prompt Caching（减少重复前缀计算）、选择低延迟模型、就近部署
  • 提升 TPS：使用更小/更快的模型（gpt-4o-mini）、限制并发以减少排队、使用 vLLM 等推理框架优化吞吐
  • 注意：Streaming 降低 TTFT 但不降低 E2E Latency；E2E = TTFT + (output_tokens / TPS)
Q6: 如何检测和监控 LLM 的幻觉？

幻觉检测方法：

  • 基于引用验证：检查 LLM 输出是否可以从提供的 context 中找到依据（Faithfulness 检测）
  • LLM-as-Judge：用一个更强的 LLM 评估输出是否包含虚构信息（如 GPT-4 评估 GPT-3.5 的输出）
  • NLI（自然语言推理）：使用 NLI 模型判断输出与 context 之间是 entailment 还是 contradiction
  • 知识库交叉验证：将关键事实与外部知识库比对
  • 用户反馈：收集 thumbs down 并人工审核是否为幻觉

监控体系：

  • 抽样评估：每日随机抽取 N% 的输出做自动幻觉检测
  • 实时检测：高风险场景（医疗/法律）对每条输出做检测
  • 趋势监控：跟踪日/周级幻觉率变化，Prompt 或模型变更后重点关注
Q7: LLM-as-Judge 方案有哪些局限性？如何改进？

核心局限：

  • 位置偏见：Judge 模型倾向于给排在前面的答案更高分
  • 长度偏见：更长、更详细的回答通常得分更高，即使简洁回答更优
  • 自我偏见：用 GPT-4 评估 GPT-4 的输出，可能偏向自己的风格
  • 知识局限：Judge 模型本身的知识可能有错，导致误判
  • 一致性问题：同一对 (question, answer) 多次评估结果可能不同

改进策略：

  • 多 Judge 投票：使用 2-3 个不同模型做 Judge，取多数意见
  • 随机化：随机交换答案位置，消除位置偏见
  • 校准集：维护人工标注的 Golden Set，定期评估 Judge 的准确性
  • 结构化评估：使用明确的评分维度和 rubric，减少主观性
  • 人工兜底：低置信度的评估交给人工复审
Q8: 生产环境中 LLM 应用应该设置哪些告警？

必设告警清单：

  • 延迟告警：P95 延迟超过 SLA 阈值（如 10s），持续 5 分钟 → P1
  • 错误率告警：5xx / API 错误率 > 5%，持续 3 分钟 → P1
  • 成本告警：小时成本超过 7 日均值 3 倍 → P2
  • Rate Limit 告警：429 响应持续出现 → P2
  • 质量告警：日幻觉率 > 10% 或用户满意度 < 70% → P3
  • Token 突增：单请求 Token 超过阈值（如 > 10K）→ 排查 Prompt 注入

关键原则：每条告警必须配 Runbook；区分 actionable 告警和 informational 告警；避免告警疲劳。

Q9: Phoenix 的 Embedding 可视化如何帮助 RAG 调优？

Phoenix 通过 UMAP 降维将 Query 和 Document 的 Embedding 映射到 2D 空间：

  • 发现检索漏洞：如果 Query 聚类远离所有 Document 聚类，说明知识库缺少相关内容
  • 检测文档漂移：新增文档的 Embedding 分布与历史文档不一致，可能是数据质量问题
  • 分析失败案例：低分 Trace 的 Query Embedding 与检索到的 Document Embedding 距离远，说明检索不准
  • 优化 Chunk 策略：如果同一文档的 Chunk Embedding 过于分散，可能需要调整 chunk size 或 overlap
  • 评估 Embedding 模型：切换 Embedding 模型后，对比可视化变化，判断检索质量是否改善

配合 NDCG@K、Precision@K 等指标量化分析，实现"可视化定位 + 定量验证"的调优循环。

Q10: 如何构建一套完整的 LLM 可观测性体系？

分层架构：

  • 数据采集层： - SDK 埋点（Langfuse/LangSmith SDK）采集 Trace/Span/Generation - Proxy 模式（Helicone）零侵入采集 API 调用 - 用户反馈采集（Thumbs Up/Down）
  • 数据存储层： - Trace 数据 → 时序数据库/ClickHouse - Prompt & Response → 对象存储（注意 PII 脱敏） - 评估结果 → 关系型数据库
  • 分析层： - 实时仪表盘（延迟 / Token / 成本 / 错误率） - 质量分析（幻觉检测 / LLM-as-Judge / 检索质量） - 成本归因（多维下钻）
  • 告警层： - 多级告警（P1-P3）+ Runbook - 异常检测（统计异常 + 趋势变化） - 自动化响应（降级 / 限流 / 切换模型）
  • 工具选型： - 开发阶段：Phoenix（本地快速迭代） - 测试阶段：LangSmith/Langfuse（评估 + 数据集管理） - 生产阶段：Langfuse（追踪）+ Helicone（成本）+ Prometheus（告警）
