GPU 架构基础

SM 是 GPU 的基本计算单元，每个 SM 包含：

Streaming Multiprocessor (SM)

SM 是 GPU 的基本计算单元，每个 SM 包含：

  • CUDA Cores — 标量浮点/整数运算单元（FP32/INT32）
  • Tensor Cores — 矩阵乘加（MMA）专用硬件
  • Warp Scheduler — 调度 32 线程为一个 Warp 执行
  • Register File — 每 SM 通常 256KB 寄存器
  • Shared Memory / L1 Cache — 可配置比例，通常合计 192-228KB

CUDA Core vs Tensor Core

每周期吞吐1 FMA / Core如 4×4×4 MMA / Core
精度FP32/FP64/INT32FP16/BF16/TF32/FP8/INT8
主要用途通用计算、图形渲染深度学习训练/推理
效率优势灵活通用矩阵运算高 10-20× 吞吐

    ↓

    ↓

    ↓

  • SM 是 GPU 并行计算的基本单位，GPU 核心数决定了并行度
  • Tensor Core 吞吐远高于 CUDA Core（矩阵运算），是深度学习的算力基础
  • 内存层次带宽逐级递减：Registers > Shared > L2 > HBM；优化核心是减少 HBM 访问
  • Warp (32 threads) 是 GPU 调度最小单位，分支发散会降低效率

Tensor Core 的核心操作：D = A × B + C

每个 Tensor Core 一次执行一个小矩阵乘法（如 4×4×4 或 16×16×16 取决于代数和精度）：

// Hopper Tensor Core (4th Gen)
// wgmma.mma_async 指令：可执行 m64n256k16 的矩阵乘法
// 一个 Warp Group (128 threads) 协作完成一次 MMA

// 等效操作:
for i in range(M):
    for j in range(N):
        for k in range(K):
            D[i][j] += A[i][k] * B[k][j]  // 一条指令完成

为什么 Transformer 训练依赖 Tensor Core

  • Attention = QK^T × V — 大量矩阵乘法，完美匹配 MMA
  • FFN = xW₁ × W₂ — 全连接层本质是 GEMM
  • Transformer 的 >99% 计算量是矩阵运算
  • Mixed Precision Training (FP16/BF16 计算 + FP32 累加) 利用 Tensor Core 获得 2-3× 加速
  • Tensor Core 的本质是硬件级矩阵乘加，一次指令完成小矩阵乘法
  • FP8 训练使 H100 相对 A100 可获得 ~6× 的有效算力提升
  • BF16 vs FP16：BF16 指数位更多（8 vs 5），训练更稳定不易溢出
  • TF32 是 A100 引入的"透明加速"——19位宽度，在 CUDA Core 上以 FP32 API 自动使用 Tensor Core

InfiniBand 网络

Remote Direct Memory Access (RDMA) — 绕过 CPU 和内…

RDMA 原理

Remote Direct Memory Access (RDMA) — 绕过 CPU 和内核协议栈，GPU/NIC 直接读写远端内存：

传统网络: GPU → CPU → Kernel → TCP/IP → NIC → ... → NIC → Kernel → CPU → GPU RDMA: GPU → NIC (GDR) ──────────────────────────→ NIC → GPU (零拷贝, 绕过 CPU 和 OS)
  • GPUDirect RDMA (GDR)：GPU 显存直接通过 NIC 发送，无需经过 CPU 内存
  • 延迟从 ~10μs (TCP) 降低到 ~1μs (RDMA)
  • CPU 开销从 100% 降低到 ~0%

为什么大规模训练必需 InfiniBand

  • AllReduce 通信量巨大：万亿参数模型每步需交换 GB~TB 级梯度
  • 训练效率对延迟敏感：通信与计算 overlap 需要低延迟
  • 尾延迟问题：千卡同步中最慢一张卡决定整体速度，IB 的稳定性至关重要
  • GPUDirect RDMA：避免 GPU→CPU→NIC 的额外拷贝，带宽利用率更高
  • 经验规则：>256 GPU 规模训练，IB 相比以太网可提升 20-40% 训练吞吐
  • RDMA 核心价值：零拷贝 + 绕过 CPU/OS = 低延迟高吞吐
  • IB vs Ethernet：IB 在大规模下更稳定（credit-based 无丢包），但成本更高
  • GPUDirect RDMA 使 GPU 显存直接通过 NIC 传输，减少一次内存拷贝
  • NDR 400Gb/s 是当前主流 LLM 训练集群标配

GPU 集群架构

DGX SuperPOD

  • 基本单元：DGX H100 节点（8× H100 + 4× NVSwitch + 8× ConnectX-7）
  • Scalable Unit：32 节点 = 256 GPU，通过 IB leaf switches 互联
  • SuperPOD：多个 Scalable Unit + Spine switches，可达 数千 GPU
  • NVIDIA Eos 超算：576 DGX H100 = 4,608 H100 GPU

网络拓扑

Fat-Tree（传统）

        [Spine Switches]
       / | | | | | | | \
  [Leaf Switches] [Leaf Switches]
   /|\              /|\
 DGX nodes        DGX nodes
  • 全二分带宽（full bisection bandwidth）
  • 任意两节点等距，AllReduce 友好
  • 缺点：spine 层交换机数量多，成本高

Rail-Optimized（新趋势）

Rail 0: GPU0 ─── Switch0 ─── GPU0 ─── Switch0 ─── GPU0 Rail 1: GPU1 ─── Switch1 ─── GPU1 ─── Switch1 ─── GPU1 ... Rail 7: GPU7 ─── Switch7 ─── GPU7 ─── Switch7 ─── GPU7
  • 每个 GPU "rail" 连接到专属 leaf switch
  • 相同编号 GPU 在同一 rail 内通信（Data Parallel 梯度同步）
  • 减少交换机数量 30-50%，降低成本
  • 适合 DP + TP 混合并行的流量模式

存储系统

  • 并行文件系统：Lustre / GPFS / WekaFS
  • 需求：数百 GB/s 聚合读带宽（数据加载不能成为瓶颈）
  • 分层：NVMe SSD 本地缓存 + 远端并行文件系统
  • Checkpoint：大模型检查点 TB 级别，需要高写入带宽
  • DGX SuperPOD 是 NVIDIA 官方参考集群架构，常被问及
  • Fat-Tree vs Rail-Optimized：后者更省成本但对流量模式有假设
  • 存储瓶颈不可忽视：数据加载和 checkpoint 都可能限制训练效率
  • 典型集群规模：512-4096 GPU 用于训练 100B+ 模型

GPU 利用率优化

MFU (Model FLOPs Utilization)

MFU = 实际模型计算 FLOPs / (GPU 峰值 FLOPs × 训练时间)

示例计算 (GPT-3 175B on 1024× A100):
- 每 token 计算量 ≈ 6 × 175B = 1.05T FLOPs (前向+反向)
- 峰值 FP16: 1024 × 312 TFLOPS = 319,488 TFLOPS
- 如果处理 1 token 花了 10ms:
  MFU = 1.05T / (319,488T × 0.01s) = 1.05T / 3,194.88T ≈ 32.8%

业界参考:
- 优秀: MFU > 50%
- 良好: MFU 40-50%
- 一般: MFU 30-40%
- PaLM (Google): ~46.2% on TPUv4
- Megatron-LM: ~50%+ on A100

提高 GPU 利用率的方法

优化方向方法效果
计算优化FlashAttention、Kernel Fusion减少内存读写，提升计算密度
通信优化Computation-Communication Overlap通信隐藏在计算后面
内存优化Activation Checkpointing、Mixed Precision允许更大 batch 或模型
数据加载多进程 DataLoader、预取消除 I/O 等待
并行策略TP/PP/DP 最优配比减少通信/气泡

常见瓶颈诊断

  • 数据加载瓶颈：GPU 利用率周期性掉零 → 增加 DataLoader workers / 使用 NVMe 缓存
  • 通信瓶颈：AllReduce 时间占比 >30% → 增大 batch / overlap / 更优拓扑
  • 内存瓶颈：OOM 导致 batch 过小 → Activation Checkpointing / ZeRO offload
  • Kernel Launch 开销：大量小 Kernel → Kernel Fusion / CUDA Graph
  • 工具：nvidia-smi, Nsight Systems, PyTorch Profiler, DCGM
  • MFU 计算公式必须会：实际 FLOPs / (峰值 FLOPs × 时间)
  • 业界 MFU 通常在 30-55% 之间，能说出原因（通信/内存/气泡）
  • FlashAttention 通过 tiling 减少 HBM 访问，是当前最重要的单点优化
  • 诊断方法论：先定位是 Compute-Bound 还是 Memory-Bound，再针对性优化

Q1: CUDA Core 和 Tensor Core 有什么区别？为什么深度学习训练主要依赖 Tensor Core？

CUDA Core 是通用标量运算单元，每周期执行一个 FMA (Fused Multiply-Add) 操作。Tensor Core 是矩阵运算专用硬件，每周期执行一个小矩阵乘加（如 4×4×4 MMA）。

深度学习依赖 Tensor Core 的原因：

  • Transformer/CNN 的 >95% 计算量是矩阵乘法（GEMM），完美匹配 Tensor Core
  • Tensor Core 支持低精度（FP16/BF16/FP8），吞吐比 FP32 CUDA Core 高 8-16×
  • Mixed Precision Training 使得精度损失可忽略，同时获得巨大加速
Q2: 解释 GPU 内存层次结构。为什么 Shared Memory 对性能很重要？

GPU 内存层次从快到慢：Register → Shared Memory → L1/L2 Cache → Global Memory (HBM)

  • Register：每线程私有，零延迟，数量有限（每 SM ~256KB）
  • Shared Memory：每 Block 共享，~20 cycles 延迟，程序员显式管理
  • L2 Cache：全局共享，~200 cycles，硬件自动管理
  • HBM：~600 cycles，带宽高（2-8 TB/s）但延迟大

Shared Memory 重要性：它是程序员可控的 on-chip 缓存，通过 tiling 策略将数据从 HBM 加载到 Shared Memory 后复用多次，大幅减少 HBM 访问（FlashAttention 的核心思想）。

Q3: NVLink 和 PCIe 有什么区别？为什么多 GPU 训练需要 NVLink？

带宽差异：NVLink 4.0 提供 900 GB/s，而 PCIe Gen5 x16 仅 64 GB/s（~14× 差距）

为什么需要 NVLink：

  • Tensor Parallelism 需要频繁的 AllReduce（每层前向/反向都通信），对带宽极其敏感
  • 8 GPU 间做 AllReduce，NVLink 可在 <1ms 完成，PCIe 则需要 >10ms
  • NVSwitch 提供全互联拓扑，任意两卡间都有高带宽直连

经验法则：Tensor Parallelism 必须在 NVLink 域内；Data Parallelism 可跨节点走 IB。

Q4: 什么是 RDMA？GPUDirect RDMA 如何工作？

RDMA (Remote Direct Memory Access)：允许一台机器直接读写另一台机器的内存，绕过双方的 CPU 和操作系统内核。

GPUDirect RDMA 进一步优化：

  • 传统路径：GPU → PCIe → CPU Memory → Kernel → NIC（两次拷贝）
  • GDR 路径：GPU → PCIe → NIC（一次 DMA，零 CPU 参与）

关键优势：延迟从 ~10μs 降至 ~1μs，CPU 完全不参与数据搬运，对千卡训练的 AllReduce 效率至关重要。

Q5: 什么是 MFU？如何计算？业界典型值是多少？

MFU (Model FLOPs Utilization) = 模型有效计算量 / (硬件峰值算力 × 实际训练时间)

计算步骤：

  1. 每 token FLOPs ≈ 6 × 参数量（前向 2N + 反向 4N）
  2. 总 FLOPs = 每 token FLOPs × tokens 数 / 训练时间
  3. MFU = 总 FLOPs / 集群峰值 TFLOPS

业界参考值：

  • PaLM (540B, 6144 TPUv4): ~46.2%
  • Megatron-LM (175B, 1024 A100): ~50-54%
  • 一般大模型训练: 30-50%

MFU < 100% 的原因：通信开销、Pipeline 气泡、内存带宽瓶颈、数据加载等待。

Q6: Fat-Tree 和 Rail-Optimized 网络拓扑有什么区别？各自优缺点？

Fat-Tree：

  • 经典 Clos 网络，提供全二分带宽（full bisection bandwidth）
  • 任意两节点通信带宽相同
  • 优点：通用性强，对任意流量模式都表现好
  • 缺点：需要大量 spine 交换机，成本高

Rail-Optimized：

  • 每 GPU 有独立 "rail"（专属网络平面）
  • 相同编号的 GPU 在同一 rail 内通信
  • 优点：交换机减少 30-50%，成本更低
  • 缺点：依赖特定流量模式（DP 梯度同步），跨 rail 通信带宽有限

选择依据：纯 DP 训练适合 Rail-Optimized；混合并行（TP+PP+DP）需评估跨 rail 通信需求。

Q7: 解释 CUDA 的 Thread/Block/Grid 层次。Warp 是什么？

CUDA 编程模型层次：

  • Thread：最小执行单位，有自己的 register 和 local memory
  • Block (Thread Block)：一组 threads（最多 1024），共享 Shared Memory，映射到一个 SM
  • Grid：所有 blocks 的集合，对应一次 kernel launch
  • Warp：32 个连续 threads，是 GPU 硬件调度的最小单位（SIMT 执行）

Warp 重要性：同一 Warp 内的 32 个线程执行相同指令；如果有分支发散（branch divergence），不同路径会串行执行，降低效率。

Q8: 训练大模型时 GPU 利用率不高，如何诊断和优化？

诊断流程：

  1. nvidia-smi：看 GPU 利用率是否周期性掉零（数据加载问题）
  2. Nsight Systems / PyTorch Profiler：timeline 分析 Kernel 执行和间隙
  3. 计算 MFU：判断是否在合理范围
  4. 区分 Compute-Bound vs Memory-Bound（Arithmetic Intensity 分析）

常见优化：

  • 数据加载慢 → 增加 workers、预取、NVMe 本地缓存
  • 通信占比高 → Overlap、增大 micro-batch、优化并行策略
  • 小 Kernel 过多 → Kernel Fusion、CUDA Graph
  • 内存不足导致 batch 小 → Activation Checkpointing、ZeRO
  • Attention 瓶颈 → FlashAttention
Q9: BF16 和 FP16 有什么区别？为什么现在训练更倾向 BF16？

格式对比：

  • FP16：1 符号位 + 5 指数位 + 10 尾数位（范围 ±65504，精度 ~3.3 位十进制）
  • BF16：1 符号位 + 8 指数位 + 7 尾数位（范围 同 FP32 ±3.4×10³⁸，精度 ~2.4 位十进制）

BF16 优势：

  • 动态范围与 FP32 相同（8 位指数），训练时不易上溢/下溢
  • 不需要 Loss Scaling（FP16 训练的一个痛点）
  • 从 FP32 转换简单：直接截断低 16 位尾数

FP16 仍有用：推理场景精度更重要、旧硬件（V100）只支持 FP16。

Q10: 如何选择云 GPU 实例？按需/预留/Spot 各适合什么场景？

选择维度：

  • GPU 型号：H100 > A100（性价比通常 H100 更优，考虑 FP8）
  • 网络：多节点训练必须选高带宽实例（Azure IB / AWS EFA）
  • 显存：推理大模型选大显存（H200 141GB）；训练可通过并行策略分摊

计费模式选择：

  • 按需：快速实验、短期项目、负载不确定
  • 预留：持续运行 >6 月、成本敏感的生产训练
  • Spot：可容忍中断、有 checkpoint 机制的训练任务（省 60-90%）

最佳实践：预留实例覆盖基线负载 + Spot 实例弹性扩展 + 按需处理突发需求。
