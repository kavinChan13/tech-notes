企业 AI 平台全景

随着大模型在企业中的广泛应用，各业务线独立集成 AI 能力会导致：

1.1 为什么需要统一 AI 平台

随着大模型在企业中的广泛应用，各业务线独立集成 AI 能力会导致：

  • 模型碎片化 — 不同团队对接不同模型提供商，接口标准不统一
  • 资源浪费 — GPU 推理资源无法共享，利用率低
  • 安全合规难 — 敏感数据无统一管控，审计缺失
  • 重复造轮子 — 每个团队自建 Prompt 管理、RAG、缓存等基础能力
  • 运维复杂度高 — 模型版本、可用性、性能无统一监控

统一 AI 平台的核心价值：能力复用、成本可控、安全合规、快速迭代。

1.2 平台能力矩阵

🧠 模型管理
⚡ 推理服务
📦 数据管理
📊 评估中心
📡 监控告警

📝 Prompt 管理

平台架构分层

AI 平台分层架构（自上而下依赖）

Chat · Agent · 知识问答 · 内容生成 · 代码助手
能力层 Capability

K8s · GPU 集群 · 对象存储 · 向量数据库 · 监控
💡 关键要点
  • 能从业务痛点出发，解释为什么需要统一平台而不是各自为战
  • 平台能力矩阵 — 至少说出 6 个核心模块及其职责
  • 分层架构 — 应用层/能力层/服务层/模型层/基础设施，各层边界清晰

多租户设计

2.1 租户隔离策略

隔离维度方案优缺点
命名空间隔离每个租户分配独立 Namespace（K8s Namespace + 逻辑 DB schema）隔离性好，运维复杂度中等
资源池隔离共享集群 + 资源配额（ResourceQuota）+ 优先级（PriorityClass）资源利用率高，需防止 noisy neighbor
API Key 隔离每个租户独立 API Key，通过 Key 映射租户配置实现简单，适合 SaaS 场景
物理隔离独立集群或独立 GPU 节点池隔离性最强，成本最高

2.3 计费模型

计费模型描述适用场景
按 Token 计费统计 input/output Token 数，按单价计算精确计量，适合内部结算
按请求计费每次 API 调用固定费用简单场景，请求复杂度相近
订阅制按月/年固定费用，含一定额度面向内部团队包月制
混合计费基础订阅 + 超额按量大多数企业生产环境
💡 关键要点
  • 多租户隔离至少知道三种方案及优缺点对比
  • 配额管理需要覆盖 Token / QPS / 并发 三个维度
  • 计费模型能说出 3 种以上，并分析各自适用场景
  • 防止 noisy neighbor 的手段：限流、资源隔离、优先级队列

3.3 版本管理与一键部署

  • 语义化版本 — major.minor.patch，大版本不兼容需迁移通知
  • 灰度发布 — 新版本先切 10% 流量，观察指标后逐步放量
  • 回滚机制 — 保留最近 N 个版本的模型权重和配置，一键回滚
  • 一键部署流程 — 选择模型 → 配置资源(GPU/副本数) → 选择量化策略 → 自动生成 K8s 资源 → 健康检查 → 上线
💡 关键要点
  • 模型卡片应包含哪些核心字段（能力、性能、定价、部署信息）
  • 内部模型 vs 外部模型的管理差异
  • 模型版本管理与灰度发布策略
  • 一键部署的关键步骤和自动化程度

4.2 版本控制与 A/B 测试

  • 版本控制 — 每次修改 Prompt 自动生成新版本，支持 diff 对比，关联性能指标变化
  • A/B 测试框架：
    • 创建实验 → 配置流量比例（如 V3:80%, V4:20%）
    • 定义评估指标（响应质量评分、用户满意度、任务完成率）
    • 自动收集数据 → 统计显著性检验 → 输出报告
    • 胜出版本一键推全量

4.3 Prompt 共享与复用

  • Prompt 仓库 — 组织内共享 Prompt 库，支持搜索、收藏、Fork
  • 模板继承 — 基础 Prompt → 业务 Prompt → 场景 Prompt 层级复用
  • 权限控制 — 私有 / 团队可见 / 组织公开 三级权限
  • 效果排行榜 — 按场景展示 Prompt 效果评分排名，促进最佳实践沉淀
💡 关键要点
  • Prompt 模板需支持变量插值和模型参数绑定
  • 版本控制参考 Git 思路：commit、diff、branch、tag
  • A/B 测试需明确流量分配、评估指标、统计检验方法
  • Prompt 共享需考虑权限和防止敏感信息泄露

5.2 多知识库路由

  • 意图识别路由 — 先识别用户问题意图，再路由到对应知识库
  • 关键词路由 — 基于关键词匹配选择知识库
  • 多库融合 — 同时检索多个知识库，合并去重后排序
  • 级联检索 — 先粗检索（BM25）→ 再精排（向量+交叉编码器 Reranker）
// 多知识库路由配置
{
  "app_id": "hr-assistant",
  "retrieval_config": {
    "knowledge_bases": [
      { "kb_id": "hr-policy", "weight": 0.5, "top_k": 5 },
      { "kb_id": "employee-handbook", "weight": 0.3, "top_k": 3 },
      { "kb_id": "faq-general", "weight": 0.2, "top_k": 3 }
    ],
    "strategy": "weighted_merge",      // weighted_merge | intent_route | cascade
    "reranker": { "model": "bge-reranker-v2", "top_n": 5 },
    "similarity_threshold": 0.65
  }
}

5.3 检索策略与权限控制

检索策略描述适用场景
向量检索基于语义相似度的 ANN 检索通用语义问答
全文检索BM25 / Elasticsearch 关键词检索精确术语匹配
混合检索向量 + 全文加权融合(RRF)兼顾语义与关键词
图检索基于知识图谱的结构化检索实体关系密集场景
权限控制要点

知识库需要实现文档级权限：不同租户/角色只能检索到授权范围内的文档。实现方式包括：元数据过滤（在向量查询中附加 tenant_id 过滤条件）、独立 Collection 隔离、行级安全(RLS)策略。

💡 关键要点
  • 分块策略（固定大小 vs 语义 vs 递归）的优缺点
  • 混合检索中 RRF（Reciprocal Rank Fusion）的原理
  • Reranker 的作用：粗排 → 精排 二阶段检索
  • 知识库权限控制的实现方案，尤其是向量数据库中的元数据过滤

6.2 各环节详解

环节核心职责可配置项

后处理敏感信息过滤、格式化、引用标注过滤规则、输出格式、引用模板
响应返回SSE 流式推送或完整响应流式/非流式、压缩、缓存

6.3 可配置化设计

// 应用级全链路配置
{
  "app_id": "legal-assistant",
  "pipeline": {
    "auth": { "required": true, "method": "api_key" },
    "rate_limit": { "qps": 30, "burst": 50 },
    "prompt": { "template_id": "legal-qa-v2", "max_context_tokens": 8000 },
    "retrieval": {
      "enabled": true,
      "knowledge_bases": ["legal-docs", "case-law"],
      "strategy": "hybrid",
      "top_k": 8,
      "reranker": true
    },
    "routing": {
      "primary": "gpt-4o",
      "fallback": ["claude-3.5-sonnet", "qwen-72b"],
      "strategy": "lowest_latency"
    },
    "inference": { "temperature": 0.2, "max_tokens": 4096, "stream": true },
    "post_process": {
      "sensitive_filter": true,
      "citation": true,
      "format": "markdown"
    },
    "cache": { "enabled": true, "ttl_seconds": 3600, "similarity_threshold": 0.95 }
  }
}
💡 关键要点
  • 能画出完整请求链路，说清每个环节的职责
  • 每个环节都应可配置 — 这是平台化的核心思想
  • Fallback 机制：主模型失败时自动切换备用模型
  • 语义缓存：相似请求命中缓存，降低成本和延迟

权限与安全

7.1 RBAC 角色权限

角色权限范围典型操作
平台管理员全局管理模型上下线、租户管理、全局配置
租户管理员租户内管理应用创建、成员管理、配额查看
应用开发者应用级操作Prompt 编辑、知识库管理、API 调用
终端用户使用级通过应用界面使用 AI 能力
审计员只读审计查看日志、用量报表、安全报告

7.2 API Key 管理

  • Key 生命周期 — 创建 → 激活 → 轮换 → 吊销，支持设置过期时间
  • 权限绑定 — 每个 Key 绑定特定模型、应用、操作范围
  • 安全存储 — Key 仅在创建时展示一次，后端使用 hash 存储
  • 调用追踪 — 每个 Key 的调用记录可追溯，异常调用自动告警

7.3 敏感信息过滤

  • 输入过滤 — 检测并脱敏用户输入中的身份证号、手机号、银行卡号等 PII 信息
  • 输出过滤 — 防止模型输出敏感内容（政治敏感、色情、暴力等）
  • Prompt 注入防护 — 检测恶意 Prompt 注入攻击，隔离系统提示与用户输入
  • 数据驻留 — 确保数据不出区域/国家，满足 GDPR / 数据安全法要求

💡 关键要点
  • RBAC 模型：角色-权限-资源 三要素，最小权限原则
  • API Key 安全：hash 存储、过期轮换、权限最小化
  • PII 脱敏的实现方式：正则 + NER 模型混合检测
  • Prompt 注入防护：输入输出双重校验，系统/用户提示隔离

可扩展性

8.1 水平扩展推理节点

  • 无状态推理服务 — 推理服务本身无状态，方便水平扩展
  • 负载均衡 — 基于 GPU 利用率、队列深度、延迟的智能负载均衡
  • 多副本部署 — 同一模型多副本，跨节点分布，单节点故障不影响服务
  • 模型并行 — 大模型使用 Tensor Parallelism 跨多卡部署

8.2 自动扩缩容 (HPA)

# Kubernetes HPA 配置示例
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: vllm-qwen-72b-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: vllm-qwen-72b
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Pods
    pods:
      metric:
        name: gpu_utilization       # 自定义 GPU 利用率指标
      target:
        type: AverageValue
        averageValue: "70"          # GPU 利用率超 70% 扩容
  - type: Pods
    pods:
      metric:
        name: request_queue_depth   # 请求队列深度
      target:
        type: AverageValue
        averageValue: "10"
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
      - type: Pods
        value: 2
        periodSeconds: 120          # 每 2 分钟最多扩 2 个 Pod
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
      - type: Pods
        value: 1
        periodSeconds: 300          # 每 5 分钟最多缩 1 个 Pod

8.3 GPU 资源调度

组件职责
NVIDIA GPU Operator自动管理 GPU 驱动、Container Toolkit、Device Plugin
GPU Device Plugin向 K8s 注册 GPU 资源，支持 nvidia.com/gpu 资源请求
GPU 共享 (MIG/MPS)将 A100 切分为多个 GPU 实例，提高利用率
调度器扩展基于 GPU 型号、显存、拓扑的智能调度
KEDA基于外部指标（如消息队列深度）的事件驱动自动扩缩
GPU 调度最佳实践
  • 大模型（70B+）使用专属 A100/H100 节点池，避免与小模型争抢
  • 小模型使用 MIG 切分或 GPU 共享，提高利用率
  • 设置合理的扩缩容窗口：扩容要快（1-2 分钟），缩容要慢（5-10 分钟），避免抖动
  • 预热池：预留少量闲置 Pod，应对突发流量，减少冷启动时间
💡 关键要点
  • HPA 自定义指标：GPU 利用率、队列深度、推理延迟
  • 扩缩容策略：扩快缩慢，防止振荡
  • GPU Operator 的作用与组件
  • MIG vs MPS 的区别：MIG 硬隔离适合生产，MPS 软共享适合开发

Q&A（10 题）

统一 AI 平台解决五大核心问题：
Q1：企业为什么需要统一 AI 平台，而不是各业务线自行对接大模型？

统一 AI 平台解决五大核心问题：

  • 能力复用 — Prompt 管理、RAG、模型路由等基础能力集中建设，避免重复造轮子
  • 成本管控 — 统一 GPU 资源池，提高利用率；统一计费，透明可控
  • 安全合规 — 统一的数据脱敏、审计日志、权限管理，满足合规要求
  • 模型管理 — 统一的模型版本管理、灰度发布、监控告警
  • 快速迭代 — 新业务接入只需配置，不需要从零搭建 AI 基础设施

类比：就像企业为什么需要统一的数据库中台、统一的消息队列，而不是每个团队自己搭 MySQL/Kafka。

Q2：多租户架构中如何防止 noisy neighbor 问题？

Noisy Neighbor 指一个租户大量消耗资源导致其他租户服务降级。防御策略：

  • 请求限流 — 每个租户独立的 QPS/并发限制（令牌桶算法），超限返回 429
  • 资源配额 — K8s ResourceQuota 限制 CPU/GPU/内存上限
  • 优先级队列 — 高优先级租户请求优先调度，低优先级在高负载时降级
  • 物理隔离 — 对 SLA 要求高的租户分配专属 GPU 节点池
  • 熔断降级 — 某租户异常请求激增时触发熔断，不影响其他租户

最佳实践是多层防护组合使用，而非依赖单一策略。

Q3：模型路由有哪些策略？如何实现 Fallback 机制？

路由策略：

  • 轮询 (Round Robin) — 简单均匀分配，适合同质模型实例
  • 加权路由 — 按模型性能/成本分配权重
  • 最低延迟 — 实时采集各模型延迟，优先发送到最快节点
  • 内容路由 — 按任务类型（代码/翻译/对话）路由到专长模型
  • 成本优先 — 优先使用低成本模型，复杂问题升级到高成本模型

Fallback 机制实现：

  1. 定义主模型和备用模型列表（有序）
  2. 主模型调用超时或返回错误时，自动切换下一个备用模型
  3. 所有模型都失败时返回降级响应
  4. 配合熔断器（如 Circuit Breaker）：连续 N 次失败自动跳过该模型一段时间
Q4：RAG 平台中如何选择分块(Chunking)策略？

三种主流分块策略对比：

策略原理优点缺点
固定大小按字符/Token 数切分，含 overlap实现简单，速度快可能切断语义
递归分块按标题/段落/句子逐层切分保留结构，效果好依赖文档格式
语义分块基于 Embedding 相似度切分语义完整性最好计算开销大

选择建议：

  • 结构化文档（Markdown/HTML）→ 递归分块
  • 纯文本长文 → 语义分块或带 overlap 的固定分块
  • 代码文件 → 按函数/类/模块分块
  • 通用默认 → 递归分块 + 256~512 Token chunk size + 20% overlap
Q5：如何设计 Prompt 的 A/B 测试框架？

完整 A/B 测试流程：

  1. 创建实验 — 定义原始版本(Control)和测试版本(Treatment)
  2. 流量分配 — 按比例随机分流（如 80/20），确保同一用户在实验期内稳定分组（基于 user_id hash）
  3. 指标收集 — 自动/人工评估指标：
    • 自动指标：延迟、Token 数、格式正确率
    • LLM 评估：使用另一个模型打分（GPT-4 as Judge）
    • 人工评估：随机抽样人工评分
    • 业务指标：用户满意度、任务完成率
  4. 统计分析 — 计算置信区间，做显著性检验（p-value < 0.05）
  5. 决策 — 胜出版本推全量，记录实验报告供后续参考
Q6：全链路中语义缓存是如何工作的？

语义缓存 vs 传统缓存：

  • 传统缓存 — 精确匹配 key（如请求 hash），命中率低
  • 语义缓存 — 将请求 Embedding 化，通过向量相似度判断是否命中

工作流程：

  1. 用户请求到达 → 计算请求文本的 Embedding 向量
  2. 在缓存向量库中搜索相似向量（cosine similarity）
  3. 若相似度 > 阈值（如 0.95）→ 命中缓存，直接返回缓存的响应
  4. 若未命中 → 正常调用模型 → 将请求向量 + 响应存入缓存

注意事项：

  • 阈值设置：太高命中率低，太低可能返回不相关答案。建议从 0.95 开始调优
  • 缓存失效：设置 TTL，知识库更新时主动清理相关缓存
  • 适用场景：FAQ 类高重复问题效果最好，开放式对话不适合缓存
  • 开源实现：GPTCache
Q7：推理服务的 GPU 资源调度有哪些关键技术？

核心技术栈：

  • NVIDIA GPU Operator — 一键部署 GPU 驱动、Container Toolkit、Device Plugin、DCGM Exporter
  • Device Plugin — 向 K8s 暴露 nvidia.com/gpu 资源，Pod 可通过 resources.limits 请求 GPU
  • MIG (Multi-Instance GPU) — A100/H100 硬件级切分，最多 7 个独立 GPU 实例，性能隔离
  • MPS (Multi-Process Service) — 软件级 GPU 共享，多进程共享 GPU，适合小模型
  • Topology-aware 调度 — 感知 NVLink/NVSwitch 拓扑，Tensor Parallel 任务分配到同一节点的 GPU

HPA 自定义指标来源：

  • DCGM Exporter → Prometheus → Prometheus Adapter → K8s Custom Metrics API → HPA
  • 常用指标：DCGM_FI_DEV_GPU_UTIL(GPU 利用率)、DCGM_FI_DEV_FB_USED(显存使用)
Q8：如何防范 Prompt 注入攻击？

Prompt 注入的三种形式：

  • 直接注入 — 用户在输入中嵌入"忽略以上指令"等指令覆盖系统 Prompt
  • 间接注入 — 攻击者在知识库文档中植入恶意指令，通过 RAG 检索注入
  • 越狱(Jailbreak) — 通过角色扮演、编码等方式绕过安全限制

防御策略：

  1. 输入检测 — 使用分类模型检测恶意输入（如 OpenAI Moderation API）
  2. Prompt 隔离 — 系统 Prompt 与用户输入使用特殊分隔符，明确角色边界
  3. 输出检测 — 对模型输出进行安全分类，过滤危险内容
  4. 权限最小化 — Function Calling / Tool Use 限制可调用的工具范围
  5. 知识库审核 — 入库文档进行安全扫描，检测嵌入的恶意指令
  6. 多层 Prompt — 在 System Prompt 末尾加入防注入指令（有限效果）
Q9：Dify 和 FastGPT 的核心区别是什么？分别适合什么场景？

Dify 核心特点：

  • 定位为 LLMOps 平台，不仅做 RAG，更强调完整 AI 应用开发
  • 可视化工作流编排（Workflow）能力强，支持条件分支、循环、HTTP 调用等
  • Agent 能力丰富，支持 ReAct / Function Calling 多种 Agent 模式
  • 生态丰富：大量插件、模型提供商接入
  • 适合：复杂 AI 应用开发，需要工作流编排、多步骤任务

FastGPT 核心特点：

  • 定位为知识库问答平台，专注 RAG 场景
  • 开箱即用，部署简单，上手快
  • 知识库管理直观，支持多种文件格式
  • 工作流相对简单，但覆盖主要问答场景
  • 适合：快速搭建知识库问答系统，团队技术能力中等

选择依据：如果需要复杂工作流和 Agent 能力选 Dify；如果只需要知识库问答且要求快速上线选 FastGPT。

Q10：如何设计推理服务的高可用架构？

高可用设计的关键要素：

  1. 多副本部署 — 每个模型至少 2 个副本，跨可用区部署
  2. 健康检查 — Liveness Probe（进程存活）+ Readiness Probe（可接收流量）+ Startup Probe（模型加载完成）
  3. Fallback 链 — 主模型 → 备用自托管模型 → 云端 API → 降级响应
  4. 熔断器 — 连续失败 N 次 → 打开熔断 → 直接走 Fallback → 定期探测恢复
  5. 优雅关停 — 下线前完成进行中的请求（drain），preStop hook 处理
  6. 模型预热 — 新 Pod 启动后先发送 warmup 请求，加载 KV Cache，再接入流量
  7. 监控告警 — P99 延迟、错误率、GPU 利用率、队列深度的多维度告警

容灾架构：

用户 → CDN/DNS → LB(多可用区)
AZ-1: vLLM Pod × 3
AZ-2: vLLM Pod × 3
Fallback: Cloud API (GPT-4o / Claude)
