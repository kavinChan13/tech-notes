DetNet 与跨域确定性

TSN 在一个二层域内能把抖动压到微秒级，但机器人的数据要跨过路由器、跨过运营商网络、跨过无线空口才能到云端调度中心——TSN 一旦出了广播域就失效了。IETF 的 DetNet 把同一套思路搬到 IP/MPLS 层，而 3GPP 的 URLLC 负责空口那一段。这篇讲清三者各自的能力边界，以及怎么把它们拼成一条端到端可证明的时延链。

TSN 的边界在哪

为什么二层方案不够用

TSN 的所有机制都建立在三个隐含前提上，而这三个前提在跨网段时全部失效：

TSN 的前提为什么跨网段失效DetNet 的应对
全网共享一个 gPTP 时间域gPTP 是纯 L2（EtherType 0x88F7），路由器不转发它；跨域要靠 PTP over UDP 或 GNSS，精度和信任模型都变了不强制要求全网同步；按机制分档：CQF 需要同步，ATS 不需要
转发标识是 (MAC, VLAN)路由器会剥掉/重写二层头，VLAN 标签和 PCP 出了广播域就没了用 MPLS 标签或 IPv6 六元组 + Flow Label 做流标识
路径是二层生成树 / 静态配的IP 路由会自己收敛、自己改路——一次 OSPF 重算就能把你精心规划的路径换掉显式路径（MPLS TE / SR Policy），把路由决策从分布式收回到控制器
TSN 像一栋楼里的内部电梯调度：楼管知道每层的人流，可以精确安排「8:00:00 到 8:00:12 这台电梯只送 3 楼的人」。但人一出楼门上了城市道路，楼管就管不着了——城市交通有自己的信号灯系统和路径规划。DetNet 就是城市级的那套方案：它不重新发明「保证准时」这个目标，而是用适合城市道路的手段（专用车道 = MPLS 标签、限行时段 = 循环排队、双路线 = PREOF）达到同样效果。
DetNet（Deterministic Networking）是 IETF 的工作组和标准族，核心架构文档是 RFC 8655（2019）。目标写得很直白：在 L2 以上的 IP/MPLS 网络中，为特定流提供有界时延、有界抖动、有界（近零）丢包，且不影响非 DetNet 流量的正常转发。注意它明确只覆盖「单一管理域」——跨运营商的端到端 DetNet 至今仍是未解决的开放问题，这一点在面试里提出来很有分量。

1.1 三个「有界」的精确含义

DetNet 的服务承诺不是「快」，而是「可证明的界」。三个界分别对应三类工程手段，理解这个映射就理解了整个 DetNet 的技术选择：

承诺威胁来源手段
有界时延排队等待随背景流量变化资源预留（准入控制）+ 排队机制（CQF / TAS / ATS）
有界抖动不同包经历的排队不同；路径切换导致时延跳变循环排队（把抖动锁定为一个周期）+ 显式路径（禁止路由自行收敛）
近零丢包缓冲溢出、链路故障预留保证不溢出 + PREOF 多路径复制消除（不靠重传）
「近零丢包」这个措辞是刻意的。DetNet 不承诺绝对零丢包——物理层的比特错误、硬件故障、软件 bug 都无法被协议消除。它承诺的是「拥塞导致的丢包为零」：只要流量符合预留的到达曲线，缓冲区数学上不会溢出。剩下的随机丢包靠 PREOF 的多路径冗余降到可忽略。这个区分很重要：如果你的应用要求真正的零丢包，网络层只能帮到「概率极低」，剩下的必须由应用层的安全逻辑兜底（超时检测 + 安全停机）。
02

RFC 8655 架构：三平面两子层

DetNet 的分层模型

RFC 8655 把 DetNet 拆成三个平面（数据 / 控制 / 管理），并把数据平面进一步分成两个子层。这个分层不是学术洁癖——它决定了「哪些功能必须在哪些设备上实现」，是选型和排障时的地图。

「Transport 必选、Service 可选」这个结论有很强的实践含义。它意味着你可以分阶段部署：第一步只做 Transport 子层（显式路径 + 资源预留 + 排队整形），就已经拿到了有界时延和抖动——这一步只需要交换机/路由器支持，不需要改动端侧。第二步再加 Service 子层的 PREOF 来对付链路故障，这一步需要在边缘设备上维护每流序号状态，成本高得多。很多项目第一阶段做完就够用了，因为链路故障的概率远低于拥塞抖动的概率。

2.1 与 TSN 的架构对照

两者的层次是一一对应的，这也是为什么它们能拼在一起：

功能TSN（IEEE 802.1）DetNet（IETF）
流标识目的 MAC + VLAN ID，或 Stream IDMPLS 标签栈，或 IPv6 六元组 + Flow Label
时间同步802.1AS 强制按机制可选（CQF 要，ATS 不要）
排队整形Qbv（TAS）· Qav（CBS）· Qcr（ATS）· Qch（CQF）复用同一套机制：CQF、TAS、ATS 都被 DetNet 引用
冗余802.1CB FRER（R-TAG）PREOF（d-CW 序号 / IPv6 扩展头）
入口保护802.1Qci PSFP入口整形 + 策略（policing）
路径控制生成树 / 静态 FDB / 802.1QcaMPLS-TE · SR Policy · PCE
配置802.1Qcc（CNC / CUC）+ YANG控制器 + YANG（RFC 9016 流规格模型）
DetNet 刻意复用了 TSN 的排队机制，只替换了「流怎么标识」和「路径怎么定」。这个设计决定意味着：芯片厂商的投入可以共享——一颗支持 CQF 的交换芯片，配上 L2 转发就是 TSN 交换机，配上 MPLS/IPv6 转发就是 DetNet 路由器。所以不要把 TSN 和 DetNet 当成竞争技术去比较优劣，它们是同一套排队理论在不同转发平面上的两次落地。面试里这么答，比逐条对比参数更能体现理解深度。
03

数据平面：MPLS 与 IPv6

两条技术路线，取舍完全不同

DetNet 定义了两套数据平面封装，对应两种网络现实。选哪条不是技术偏好问题，而是「你的网络是运营商级的还是园区级的」。

3.1 DetNet over MPLS（RFC 8964）

用 MPLS 标签栈天然表达「显式路径 + 流标识」，这是运营商网络的既有能力，改造成本最低。

── DetNet over MPLS 封装栈（自外向内）──────────
┌──────────────────────┐
│ 以太网头              │
├──────────────────────┤
│ F-Label（转发标签）   │ ← 决定下一跳，可以是 SR-MPLS 段列表
│ ...（可多层，TE 路径）│
├──────────────────────┤
│ S-Label（服务标签）   │ ← ★ 标识这是哪条 DetNet 流
├──────────────────────┤
│ d-CW（控制字，4 B）   │ ← ★ 含 28 bit 序号，PREOF 靠它去重
├──────────────────────┤
│ 原始负载（IP / 以太帧）│
└──────────────────────┘

关键点：
· S-Label 是「流」的身份，F-Label 是「路」的指令，两者解耦
· 同一条流走两条路径 = 同一个 S-Label，不同的 F-Label 栈
· d-CW 复用了伪线（PW）的控制字格式，硬件改动小
S-Label 与 F-Label 分离是 DetNet over MPLS 最精巧的设计。S-Label 回答「你是谁」（哪条流，用于 PREOF 去重和 QoS 归类），F-Label 回答「你走哪」（显式路径，可以用 SR-MPLS 的段列表表达）。这个解耦让 PREOF 的复制变得极简：复制时只换 F-Label 栈，S-Label 和 d-CW 序号保持不变，接收端按 (S-Label, 序号) 就能识别副本。如果把流身份和路径混在一起（比如只用一层标签），复制出来的两份就没法认亲了。

3.2 DetNet over IPv6（RFC 8939）

纯 IP 网络没有 MPLS，流标识只能从 IP 头本身提取：

字段作用坑
源/目的 IPv6 地址基本流标识NAT 或地址变更会打断流识别
Next Header / 协议号区分 UDP / TCP / 其他IPv6 扩展头链会让协议号位置浮动
源/目的端口细分同主机的多条流加密后不可见（IPsec ESP、QUIC 内层）
DSCPQoS 归类过域边界常被重写或清零，必须在边界重新标记
Flow Label（20 bit）无需深入解析即可做 ECMP 和流识别有些设备会重写它，需逐跳验证
IPv6 方案的致命弱点是「流标识依赖可见的五元组」。机器人到云端的链路上，只要中间有 NAT、有 IPsec 隧道、或者应用用了 QUIC（端口在加密层内），路由器就认不出这是哪条 DetNet 流，所有保证瞬间失效。实践上的对策：① 在进入 DetNet 域的边缘做一次流分类，然后在域内改用 MPLS 标签或 SRv6 SID 承载身份；② 如果必须端到端 IP，那就把 DetNet 流量放在隧道外层，用外层的 IPv6 头和 Flow Label 做标识。这也是为什么运营商级部署几乎都走 MPLS/SRv6 路线。

3.3 两条路线的对比

✅ MPLS / SRv6 路线
适合：运营商专线、园区骨干、
      5G 传输网、有 SDN 控制器

优点：
· 显式路径是原生能力
· 流身份与路径解耦，PREOF 简单
· 与 SR Policy / PCE 生态成熟
· 加密对流识别无影响（标识在外层）

代价：
· 需要 MPLS/SRv6 转发面
· 运维门槛高，要控制器
⚠️ 纯 IPv6 路线
适合：小规模园区、纯 IP 环境、
      过渡阶段验证

优点：
· 不需要 MPLS，改造成本低
· 端到端可见，排障直观

代价：
· 流标识脆弱（NAT/加密/DSCP 重写）
· 显式路径难保证——IP 路由会自己收敛
· 需要额外手段固定路径
  （策略路由 / SRv6 / 隧道）
机器人场景的现实选择：端边这一段（机器人到边缘节点）通常在自己的园区网内，跳数少、可控，用 IPv6 + 策略路由或 SRv6 就够；端云这一段（回传到远程调度中心）要跨运营商网络，此时真正的 DetNet 保证基本拿不到——跨域 DetNet 是 IETF 至今未解决的问题。务实做法是：端云段不追求确定性，而是设计成「弱实时 + 大带宽 + 优雅降级」，把硬实时需求全部收敛在端内和端边。这个判断会直接影响整个系统架构，详见 端边云一体化架构。
04

PREOF：复制 · 消除 · 排序

和 FRER 同源，但多了一个功能

PREOF 是三个功能的合称，名字本身就是缩写的拼接：

PRF · Replication

在入口或分支点把包复制成 N 份，打上相同的序号，分别送入不同路径。

PEF · Elimination

在汇聚点按序号窗口丢弃重复副本，只放行第一个到达的。

POF · Ordering

TSN 的 FRER 没有这一项。把乱序的包重排成原始顺序后再交付。

4.1 为什么 DetNet 需要排序而 TSN 不需要

这是个很好的面试切入点，答案在两者的网络特性差异：

  • TSN 域内路径极短且对称。两条冗余路径通常都在同一个机柜或同一辆车里，跳数相同、线长相近，时延差在微秒级，乱序几乎不发生。所以 FRER 只做复制和消除，接收端的位图窗口顺手就把少量乱序处理了。
  • DetNet 跨越 L3 网络。两条路径可能一条走 5 跳、一条走 8 跳，时延差可达毫秒级；再加上 ECMP 哈希、链路聚合的成员切换，乱序是常态。如果不重排就交给应用，TCP 会误判丢包触发快速重传，UDP 应用的状态机会直接乱掉。
POF 像快递驿站的分拣台：同一批货走了顺丰和邮政，两家到货时间不同，第 3 件可能比第 2 件先到。驿站不会按到货顺序直接给你，而是等齐一小段再按订单号排好。代价是「等齐」这个动作本身要花时间——排序缓冲区越大，能纠正的乱序越严重，但引入的延迟也越大。这个取舍是 POF 的全部工程内容。
POF 的缓冲区大小是个危险的旋钮。它必须 ≥「两条路径的最大时延差」，否则慢路径的包到达时排序窗口已经滑过去了，包被当成过期丢弃——冗余静默失效。但缓冲区太大会给所有包都加上额外延迟（要等可能存在的慢包），把你辛苦省下来的时延又赔回去。工程做法：① 实测两条路径的时延差分布，取 P99.99 再留余量；② 监控「因过期被丢弃的包数」和「排序缓冲区实际占用」两个指标；③ 如果时延差太大，宁可不做排序，让应用层容忍乱序（比如控制指令自带时间戳和序号，应用自己丢弃过期指令）——这往往比在网络层排序更健壮。

4.2 复制点该放在哪

PREOF 的部署位置直接决定成本和收益。三种典型放法：

放法复制点 / 消除点成本适用
端到端Talker 侧复制，Listener 侧消除全程带宽翻倍；端侧要实现 PREOF路径全程都脆弱；或端侧本来就有能力（如双网口机器人主控）
段内保护脆弱段的两端各放一对只有那一段带宽翻倍最常用。滑环、拖链、无线跳、跨楼链路
多点分支沿路多个分支点复制，多个汇聚点消除状态维护复杂，带宽开销最大大规模网络要防多点同时故障；机器人场景通常过度设计
判断依据是故障树，不是均匀撒开。把复制加在失效概率最高的环节：机器人上最容易坏的是经过旋转关节的滑环和拖链里反复弯折的线缆，这两处的年故障率可能比机柜内固定链路高两三个数量级。在这两段做段内保护，成本只是一小段的带宽翻倍，收益却覆盖了绝大部分故障概率。反过来，给机柜内两台交换机之间的固定短链路做冗余，基本是浪费——除非它们共用了同一个电源。
05

排队机制与时延界

CQF 为什么是工程首选

DetNet 直接复用 TSN 的排队机制，但在 L3 网络里各机制的可用性排序变了——因为跨域后「精确时间同步」和「知道每段链路延迟」这两个前提越来越难满足。

5.1 四种机制在 L3 的可行性

机制需要时间同步？需要每流状态？时延界L3 可行性
TAS（时间感知门控）需要，且要知道每段延迟否（按类别）最优，接近零排队差。跨域拿不到精确延迟，路径一变就崩
CQF（循环排队转发）需要（但只要周期对齐，不要求知道链路延迟）否跳数 × 周期，抖动恒为一个周期好。界与拓扑无关，配置简单
ATS（异步流量整形）不需要需要（每流令牌桶）可算，且多跳不恶化好。无同步需求是巨大优势，但硬件贵
CBS（信用整形）不需要否（按队列）可算，但多跳突发累积，界随跳数恶化一般。跳数少时够用
CQF（Cyclic Queuing and Forwarding，源自 IEEE 802.1Qch）：每个出口维护两个缓冲区乒乓交替。在周期 Tn 内收到的包全部进 buffer A，同时把 buffer B（上个周期收的）里的包发出去；周期切换时两个 buffer 角色互换。结果是每一跳恰好延迟一个周期，不多不少——于是端到端时延 = 跳数 × 周期，抖动 = 一个周期，完全不依赖链路延迟、队列深度、背景流量等任何细节。
CQF 像班车而不是出租车：不管你几点到站，都只能坐下一班车；车每 10 分钟一趟。好处是行程时间完全可预测（等车最多 10 分钟 + 车程固定），坏处是就算路上没车你也得等到发车时刻。把这个模式串成多段（换乘三次），总时间就是 3 × 10 分钟的等待上界——算起来极其简单，而且和当天路况完全无关。这就是 CQF 用「稍高的时延」换来的「极好的可预测性」。

5.2 周期怎么选

周期是 CQF 唯一的旋钮，但它同时被三个约束夹住：

  • 下界一：一个周期必须装得下这一跳所有 DetNet 流量。如果周期内到达的字节数超过一个周期能发出去的字节数，buffer 会持续增长直到溢出。所以 周期 ≥ 该跳 DetNet 流量的总帧时 / 允许占用的带宽比例。
  • 下界二：周期必须远大于时间同步误差。如果各跳时钟差 10 µs 而周期只有 20 µs，周期边界就会错乱。经验值：周期 ≥ 同步误差的 10 倍以上。这直接把跨域 CQF 的周期下限抬到几十微秒到毫秒级。
  • 上界：跳数 × 周期 ≤ 时延预算。这是应用给的硬约束。
三个约束经常打架，这时候不要硬凑。典型冲突：应用要求端到端 200 µs、路径 6 跳 → 周期必须 ≤ 33 µs；但跨域同步误差就有 5 µs → 周期至少要 50 µs。此时正确的动作不是把周期硬压到 33 µs（会因同步误差随机丢包），而是改变问题：① 减少跳数（改拓扑，让这条流少走两跳）；② 把这条流从 DetNet 域改到 TSN 域内（同步精度高一个数量级，周期可以更小）；③ 和应用方谈判放宽预算——很多「200 µs」的需求追问下去其实是「不要超过 1 ms」。第三条是 JD 里「把需求转化为技术指标」这项职责最真实的日常。
06

资源预留与控制平面

准入控制才是确定性的真正来源

这一节讲的东西常被低估：所有排队机制的时延界都有一个前提——流量符合它声明的规格。如果谁都可以往 DetNet 队列里塞流量，再精妙的整形也算不出界。所以准入控制（admission control）是确定性的真正来源，排队机制只是执行手段。

6.1 流规格：RFC 9016 的 YANG 模型

一条 DetNet 流要被接纳，必须先说清自己长什么样：

── 流规格的核心字段（对应 RFC 9016 ietf-detnet-topology / flow）──
traffic-specification:
  interval:            1000000 ns   ← 观察窗口（通常等于应用周期）
  max-packets-per-interval: 6       ← 窗口内最多几个包
  max-payload-size:    100          ← 单包最大字节
  min-payload-size:    64
  → 以上四项共同定义了「到达曲线」，是算时延界的输入

traffic-requirements:
  min-bandwidth:       4800000      ← bps，由上面推导
  max-latency:         200000 ns    ← ★ 端到端预算
  max-latency-variation: 50000 ns   ← ★ 抖动预算
  max-loss:            1e-7         ← ★ 丢包率上限
  max-consecutive-loss-tolerance: 1 ← 能容忍连丢几个

→ 控制器拿到这份规格后做三件事：
  ① 算路径（满足 max-latency 的最短/最优路径）
  ② 逐跳检查余量（这一跳还能不能再接一条流）
  ③ 算出并下发每跳的队列/整形/门控参数
→ 任一步不满足就 拒绝这条流，而不是「尽力而为」
「拒绝」是确定性网络最重要的行为，也是它和普通 QoS 最大的心理差异。传统网络的哲学是「都收下，忙的时候大家一起慢」；确定性网络的哲学是「接了就必须保证，保证不了就不接」。这意味着系统必须能处理「流被拒绝」这个返回值——机器人上多加一个传感器，如果网络算出来带不动，它就是起不来，而不是「起来了但大家都抖」。这个语义变化对上层软件的设计影响很大，必须在架构阶段就想清楚。

6.2 控制平面的三种实现

方式协议特点适用
集中式控制器PCEP（算路）+ NETCONF/gNMI（下发）+ BGP-LS（收拓扑）能做全局最优；单点故障风险；配置需事务化主流选择，与 TSN 的 CNC 同构
分布式信令RSVP-TE 扩展无中心；只能做贪心式局部决策，容易陷入次优；跨域信任问题多存量 MPLS-TE 网络的渐进演化

机器人场景其实很适合「静态配置 + 构型切换」这种务实方案。一台机器人的传感器和执行器是固定的，流集合在出厂时就确定了；不同工作模式（示教 / 高速运行 / 诊断上传）的流量特征不同，但模式数量有限（三五种）。所以完全可以离线为每种构型算好一套完整配置，运行时按模式切换整套参数，而不是搭一个动态准入控制器。这样既拿到了确定性，又避开了控制器的复杂度和单点风险。切换时用「预约未来时刻统一生效」（TSN 的 admin-base-time 思路），避免半生效状态。
不要漏掉「流的生命周期管理」。预留了资源的流如果异常终止（节点掉电、进程崩溃）而没有释放，资源就泄漏了——几次重启之后网络会拒绝接纳本该能接纳的流，现象是「重启几次就起不来了」。必须有两道防线：① 软状态 + 保活，流预留带超时，Talker 定期刷新，不刷新自动回收；② 启动时全量对账，控制器重启或节点重连时重新同步「谁预留了什么」，把孤儿预留清掉。这和分布式系统里租约（lease）的思路完全一致。
07

跨域拼接：TSN + DetNet + 5G

端到端确定性是拼出来的，不是某一个技术给的

这一节是整篇的落点。机器人的一条控制回路可能要跨过四种完全不同的网络技术，每种只在自己的域内有效。端到端的确定性等于每一段的界相加——任何一段没有界，整条链就没有界。

7.1 三个技术的能力边界

TSN（IEEE 802.1）— 一个二层广播域内

能力上限：抖动亚微秒到微秒级，时延界可精确到帧时粒度。边界：路由器一跳都跨不过去（gPTP 不被转发、VLAN/PCP 被剥离）。适用：机器人本体内部、单个机柜、单辆车、一个车间的有线骨干。

DetNet（IETF）— 一个 IP/MPLS 管理域内

能力上限：抖动一个 CQF 周期（典型几十微秒到毫秒），时延界 = 跳数 × 周期。边界：跨运营商无解（RFC 8655 明确限定单一管理域），且流标识易被 NAT/加密破坏。适用：园区骨干、企业专线、5G 传输网。

5G URLLC（3GPP）— 空口那一段

能力上限：单向1 ms 空口（理论）、可靠性 99.999%，实际端到端 5–20 ms。边界：受numerology、TDD 配比、调度授权物理限制（细节见 NR 物理层与 MAC）；容量随用户数下降。适用：移动机器人、AGV、不便布线的场景。

端侧实时 OS — 帧进出网络之前的那一段

能力上限：PREEMPT_RT 下 数十微秒调度抖动；裸 RTOS 可到微秒级。边界：普通 Linux 是数百微秒到毫秒，会直接吃掉整个网络预算。适用：所有场景——这一段最常被忽略却最常成为瓶颈，详见 PREEMPT_RT 深入。

7.2 5G-TSN Bridge：两个世界的连接器

3GPP 从 Release 16 起把整个 5G 系统建模成一个 TSN 网桥（TSN Bridge），这是跨域拼接里最巧妙的一步设计：

  • 对 TSN 侧隐藏 5G 的复杂性。TSN 的 CNC 看到的只是「一个有确定转发延迟的网桥」，它按正常的 802.1Qcc 流程给这个桥下发配置，不需要懂 5QI、PDU 会话、QoS Flow 这些概念。
  • 两侧的翻译由适配功能完成。设备侧是 DS-TT（Device-side TSN Translator），网络侧是 NW-TT（Network-side TSN Translator）。它们负责把 TSN 的流规格翻译成 5G 的 QoS Flow 参数，并把 gPTP 报文透传/桥接过 5G 系统。
  • 时间同步跨界靠 gPTP 透传。DS-TT 和 NW-TT 之间用 5G 自己的空口定时做参考，把两侧的 gPTP 域桥接起来，使得 5G 段的驻留时间可以像 TSN 交换机一样被如实上报。
5G-TSN bridge 的时延界比 TSN 交换机差两三个数量级，别抱不切实际的期待。一个 TSN 交换机的驻留时间是几微秒且抖动极小；5G 系统即使配了 URLLC，驻留时间也是毫秒级且抖动显著（受调度授权、HARQ 重传、切换影响）。所以正确的架构不是「用 5G 延长 TSN 域」，而是「把硬实时闭环完整放在 TSN/有线域内，5G 只承载可容忍毫秒级抖动的流量」。典型分法：关节伺服闭环留在本体（TSN，µs 级），路径规划和协同决策走 5G（ms 级），全局调度和数据回传走 IP 网络（100 ms 级，无保证）。

7.3 拼接处最容易断的两条链

选型：什么场景用什么

需求选择理由
抖动 < 10 µs，单机柜/本体内TSN（Qbv 逐跳错相 + 帧抢占）只有 L2 门控能到微秒级；拓扑固定，可承受逐跳规划的维护成本

移动机器人，不能布线5G URLLC 切片 + MEC，硬实时闭环留在本体空口抖动是物理限制，无法压到 TSN 水平；架构上要把闭环缩短而不是延长

整个选型逻辑像规划一趟货物运输：厂内用传送带（TSN，精确到秒但只能在厂内）、市内用专线货车（DetNet，可控但要提前报备路线）、跨省用航空（5G，快但受天气和调度影响）、出国走海运（跨域 IP，只能给个大概时间）。聪明的做法不是要求海运也精确到秒，而是把需要精确的环节全部安排在厂内完成。这就是机器人系统架构里「把硬实时闭环下沉到本体」这条铁律的由来。
最常见的架构错误：把确定性需求往上推。有人会想「让云端做统一调度，所有机器人的动作都由云控制」——这要求端云链路具备确定性，而这在跨运营商网络上根本做不到。正确方向是反过来把智能下沉：本体负责伺服闭环（µs 级、TSN）、边缘负责局部协同（ms 级、5G/Wi-Fi）、云端只做全局优化和参数下发（秒级、无保证）。判断一个机器人通信架构好不好，第一个问题就是「云端断联 10 秒会发生什么」——答案应该是「继续按上一次下发的策略安全运行」，而不是「停机」。

面试题集（12 道）

按难度分层，先自测再对照

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础DetNet 和 TSN 是什么关系？为什么有了 TSN 还需要 DetNet？

    不是竞争关系，是同一套排队理论在不同转发平面上的两次落地。TSN 是 IEEE 802.1 在二层做的，DetNet 是 IETF 在IP/MPLS 层做的。

    为什么需要 DetNet：TSN 的三个前提出了广播域就全部失效——

    • gPTP 是纯 L2（EtherType 0x88F7），路由器不转发它；
    • 流标识是 (MAC, VLAN)，路由器会剥掉/重写二层头；
    • 路径靠生成树或静态 FDB，而 IP 路由会自己收敛改路。

    DetNet 换掉了「流怎么标识」（MPLS 标签或 IPv6 六元组）和「路径怎么定」（MPLS-TE / SR Policy / PCE），但直接复用 TSN 的排队机制（CQF、TAS、ATS）。

    工程含义
    芯片投入可以共享：一颗支持 CQF 的交换芯片，配 L2 转发是 TSN 交换机，配 MPLS/IPv6 转发就是 DetNet 路由器。
  2. 基础DetNet 承诺的「三个有界」是什么？为什么是「近零丢包」而不是「零丢包」？

    有界时延、有界抖动、有界（近零）丢包，且不影响非 DetNet 流量的正常转发。三者对应三类手段：

    • 有界时延：资源预留（准入控制）+ 排队机制（CQF / TAS / ATS）。
    • 有界抖动：循环排队把抖动锁定为一个周期 + 显式路径禁止路由自行收敛。
    • 近零丢包：预留保证缓冲不溢出 + PREOF 多路径复制消除（不靠重传）。
    为什么是「近零」
    协议无法消除物理层比特错误、硬件故障、软件 bug。DetNet 承诺的是「拥塞导致的丢包为零」——只要流量符合预留的到达曲线，缓冲区数学上不会溢出。剩下的随机丢包靠 PREOF 降到可忽略。
    对上层的要求
    如果应用要求真正的零丢包，网络层只能做到「概率极低」，剩下必须由应用兜底：超时检测 + 安全停机。
  3. 基础什么是 CQF？它的时延界怎么算？

    CQF（Cyclic Queuing and Forwarding，源自 IEEE 802.1Qch）：每个出口维护两个缓冲区乒乓交替。周期 Tn 内收到的包全进 buffer A，同时把 buffer B（上周期收的）发出去；周期切换时角色互换。

    结果是每一跳恰好延迟一个周期，不多不少：

    • 端到端时延 = 跳数 × 周期
    • 抖动 = 恰好一个周期，且不随跳数累积（从第二跳起相位已被周期边界对齐）
    • 完全不依赖链路延迟、队列深度、背景流量等任何细节
    为什么工程上首选它
    它把「算 GCL」这个 NP-hard 的规划问题降级成填表。要满足 500 µs 预算、路径 5 跳，周期取 ≤ 100 µs，一步算完。代价是时延被放大——CQF 用「稍高的时延」换「极好的可预测性」。
  4. 基础DetNet 数据平面有哪两条路线？各自的适用场景？
    DetNet over MPLS（RFC 8964）
    封装栈是 以太网头 / F-Label(可多层) / S-Label / d-CW / 负载。S-Label 标识流身份，F-Label 指定路径，两者解耦；d-CW 控制字含 28 bit 序号供 PREOF 去重。适合运营商专线、园区骨干、5G 传输网。
    DetNet over IPv6（RFC 8939）
    流标识只能从 IP 头提取：源/目的地址、协议号、端口、DSCP、Flow Label。适合小规模园区、纯 IP 环境、过渡验证。
    IPv6 路线的弱点
    流标识依赖可见的五元组：一旦中间有 NAT、IPsec 隧道、或应用用 QUIC（端口在加密层内），路由器就认不出这是哪条 DetNet 流，所有保证瞬间失效。另外 DSCP 过域边界常被重写或清零，Flow Label 也可能被改。所以运营商级部署几乎都走 MPLS/SRv6。

9.2 中级（区分熟练度）

  1. 中级PREOF 和 TSN 的 FRER 有什么区别？为什么 DetNet 多了排序功能？

    PREOF = PRF（复制）+ PEF（消除）+ POF（排序）。FRER 只有前两项，没有排序。

    原因在两者的网络特性差异：

    TSN 域内
    两条冗余路径通常在同一机柜或同一辆车里，跳数相同、线长相近，时延差在微秒级，乱序几乎不发生。接收端的位图窗口顺手就处理了少量乱序。
    DetNet 跨 L3
    两条路径可能一条 5 跳一条 8 跳，时延差可达毫秒级；加上 ECMP 哈希、链路聚合成员切换，乱序是常态。不重排交给应用的后果：TCP 误判丢包触发快速重传，UDP 应用状态机乱掉。
    POF 缓冲区是个危险旋钮
    必须 ≥「两条路径最大时延差」，否则慢路径的包被当过期丢弃、冗余静默失效；但太大会给所有包加延迟（要等可能存在的慢包）。做法：实测时延差取 P99.99 再留余量；监控「过期丢弃数」和「缓冲实际占用」；时延差太大时宁可不做排序，让应用靠时间戳+序号自行丢弃过期指令。
  2. 中级为什么说「准入控制才是确定性的真正来源」？

    因为所有排队机制的时延界都有一个前提：流量符合它声明的规格。如果谁都能往 DetNet 队列里塞流量，再精妙的整形也算不出界——排队机制只是执行手段，界来自「进来的流量是受限的」这个约束。

    流规格（RFC 9016）用四项定义「到达曲线」：interval（观察窗口）、max-packets-per-interval、max-payload-size、min-payload-size；再加时延/抖动/丢包三项要求。控制器拿到后：① 算满足时延的路径；② 逐跳检查余量；③ 算出并下发每跳参数。任一步不满足就拒绝这条流。

    哲学差异
    传统 QoS 是「都收下，忙时大家一起慢」；确定性网络是「接了就必须保证，保证不了就不接」。这意味着上层软件必须能处理「流被拒绝」——多加一个传感器如果网络带不动，它就是起不来，而不是「起来了但大家都抖」。这个语义变化要在架构阶段就想清楚。
    别漏掉生命周期管理
    流异常终止而未释放预留 → 资源泄漏 → 「重启几次就起不来」。两道防线：软状态 + 保活超时回收；控制器重启时全量对账清孤儿预留。思路和分布式租约（lease）一致。
  3. 中级CQF 的周期怎么选？三个约束打架时怎么办？

    周期是 CQF 唯一的旋钮，被三个约束夹住：

    • 下界一：装得下流量。周期 ≥ 该跳 DetNet 流量总帧时 / 允许占用的带宽比例，否则 buffer 持续增长直到溢出。
    • 下界二：远大于同步误差。经验值 ≥ 同步误差的 10 倍。跨域同步误差几微秒，就把周期下限抬到几十微秒。
    • 上界：跳数 × 周期 ≤ 时延预算。应用给的硬约束。
    典型冲突
    要求端到端 200 µs、6 跳 → 周期须 ≤ 33 µs；但跨域同步误差 5 µs → 周期至少 50 µs。
    正确动作是改变问题，不是硬压周期
    ① 减少跳数（改拓扑）；② 把这条流收回 TSN 域（同步精度高一个数量级，周期可更小）；③ 和应用方谈判放宽预算——很多「200 µs」追问下去其实是「不要超过 1 ms」。第三条是「把需求转化为技术指标」这项工作最真实的日常。硬压周期的后果是因同步误差随机丢包。
  4. 中级四种排队机制（TAS / CQF / ATS / CBS）在 L3 网络的可行性排序如何？

    跨域后「精确时间同步」和「知道每段链路延迟」这两个前提越来越难满足，于是排序和 L2 里不同：

    机制需同步每流状态L3 可行性
    TAS 门控需要 + 要知道每段延迟否差：跨域拿不到精确延迟，路径一变就崩
    CQF需要（但不要求知道链路延迟）否好：界与拓扑无关
    ATS不需要需要好：无同步需求是巨大优势，但硬件贵
    CBS不需要否一般：多跳突发累积，界随跳数恶化
    ATS 的独特价值
    CBS 按队列整形，同队列多流互相影响，多跳后突发被放大（burst cascading）。ATS（802.1Qcr）按流用令牌桶整形并每跳重新整形，把突发压回原始形状，多跳后界不恶化。且完全不需要时间同步——这在跨域场景是决定性优势。代价是每流状态，硬件成本高。

9.3 高级（体现深度）

  1. 高级5G-TSN Bridge 是怎么设计的？它的能力边界在哪？

    3GPP 从 Release 16 起把整个 5G 系统建模成一个 TSN 网桥：

    • 对 TSN 侧隐藏 5G 复杂性：CNC 看到的只是「一个有确定转发延迟的网桥」，按正常 802.1Qcc 流程配置，不需要懂 5QI、PDU 会话、QoS Flow。
    • 两侧翻译由适配功能完成：设备侧 DS-TT（Device-side TSN Translator）、网络侧 NW-TT。负责把 TSN 流规格翻译成 5G QoS Flow 参数，并桥接 gPTP。
    • 时间同步跨界：DS-TT 与 NW-TT 之间以 5G 空口定时为参考，把两侧 gPTP 域桥接起来，使 5G 段驻留时间能像 TSN 交换机一样如实上报。
    能力边界：差两三个数量级
    TSN 交换机驻留时间几微秒且抖动极小；5G 系统即使配 URLLC，驻留时间也是毫秒级且抖动显著（受调度授权、HARQ 重传、切换影响）。
    正确的架构结论
    不是「用 5G 延长 TSN 域」，而是「硬实时闭环完整放在 TSN/有线域内，5G 只承载可容忍毫秒级抖动的流量」。典型分法：关节伺服闭环留本体（µs）、路径规划与协同走 5G（ms）、全局调度与数据回传走 IP 网络（100 ms，无保证）。
  2. 高级端到端跨域确定性最容易在哪两个地方断链？怎么排查？
    断链一：时间基准
    gPTP（TAI，L2）→ PTP over UDP → 5G 空口定时 → NTP，每次转换都可能丢失基准。症状：各段自己「准时」但相互错位；跨段的单向时延测量全是错的（两端时钟不同源）。对策：全链统一到 TAI；每个转换点显式记录 offset；单向时延测量必须两端同源，否则只能测 RTT/2。
    断链二：QoS 标记
    PCP → DSCP → MPLS TC → 5QI → WMM/TID，任一处映射断链，流静默退化成 Best Effort。特点是不报错——包照样通，只是没优先级了；实验室（少跳）正常、现场（多跳）失效。
    排查方法
    在每一跳的入口和出口各抓一次包，比对 PCP/DSCP 字段。常见元凶：① 运营商网络默认清零 DSCP（防客户滥用高优先级）；② VLAN 剥离时丢掉 PCP；③ 隧道封装没把内层 DSCP 拷到外层——最隐蔽，因为中间设备只看外层，必须显式选 qos-mode 的 pipe/uniform 语义。对策是在每个域边界显式重新标记并维护一张映射表，把「标记正确性」纳入自动化回归。
  3. 高级为什么跨运营商的端到端 DetNet 至今做不到？架构上应该怎么应对？

    RFC 8655 明确把 DetNet 限定在「单一管理域」内。跨域的障碍不是技术细节，而是几个结构性问题：

    • 信任与准入：确定性依赖准入控制，而准入意味着「拒绝」。运营商凭什么相信你声明的流规格？谁来仲裁超额？跨域的 SLA 违约怎么举证？
    • 资源可见性：算时延界需要知道每跳的能力和余量，但运营商不会把内部拓扑和负载暴露给你。
    • 路径控制权：显式路径要求控制器能指定每一跳，跨域时你无权指挥对方的转发面。
    • 流标识穿越：过域边界时 MPLS 标签要重新映射、DSCP 常被清零、NAT 破坏五元组。
    架构应对：把确定性需求收敛，而不是往上推
    正确方向是智能下沉：本体负责伺服闭环（µs 级、TSN）、边缘负责局部协同（ms 级、5G/Wi-Fi）、云端只做全局优化和参数下发（秒级、无保证）。端云段设计成「弱实时 + 大带宽 + 优雅降级」：QUIC + 拥塞控制 + 本地兜底。
    检验一个架构好坏的第一个问题
    「云端断联 10 秒会发生什么」——答案应该是「继续按上一次下发的策略安全运行」，而不是「停机」。如果答案是停机，说明确定性需求被错误地推到了拿不到保证的那一段上。
  4. 高级给一个多机器人协同系统做通信选型，你的决策流程是什么？

    第一步：按闭环把流量分层，而不是按业务模块分。列出所有控制回路，标注每个回路的周期、时延预算、失效后果。回路越紧、后果越严重，就必须放在越靠近本体的地方。

    第二步：按段选技术。

    段预算技术
    端内（模组间）µs 级共享内存 / DMA / EtherCAT / 板内 TSN + PREEMPT_RT
    端间（协同）ms 级有线 TSN；无线则 Wi-Fi 6/7 + TWT、5G sidelink、UWB 授时
    端边5–20 ms5G URLLC 切片 + MEC，或 DetNet over SRv6
    端云50–200 ms不追求确定性：QUIC + 优雅降级

    第三步：验证两条贯穿链。时间基准全链统一到 TAI 并记录每个转换点的 offset；QoS 标记在每个域边界显式重标并逐跳抓包验证。

    第四步：机制选型的三个判据。能否拿到精确时间同步（不能 → ATS）；拓扑是否稳定（不稳定 → CQF 而非 TAS）；跳数多不多（多且用 CBS → 注意突发累积）。

    机器人场景的一个务实简化
    一台机器人的传感器和执行器是固定的，流集合出厂即定；工作模式（示教/高速/诊断）数量有限。所以完全可以离线为每种构型算好整套配置，运行时按模式切换，而不必搭动态准入控制器——既拿到确定性，又避开控制器的复杂度和单点风险。切换时用「预约未来时刻统一生效」避免半生效状态。
