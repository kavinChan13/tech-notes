01

ROS1 到 ROS2：为什么换成 DDS

理解设计动机才能理解那些复杂性

ROS1 的通信是自研的：TCPROS/UDPROS + 一个中心化的 Master。它简单好用，但有几个致命问题，正好解释了 ROS2 为什么宁愿引入 DDS 这么重的一套标准。

问题ROS1 的表现ROS2 / DDS 的解法
单点故障roscore 挂了，新节点无法建立连接（已建立的连接还能继续）去中心化发现：节点用组播互相发现，没有 Master
无实时能力TCP 的重传和拥塞控制引入不可预测的时延；没有任何 QoS 概念QoS 策略：可选 BestEffort、可配 Deadline / Liveliness，配合实时执行器
不适合弱网TCP 断线要重连；无法表达「只要最新数据，旧的不要」UDP 之上的 RTPS + History/Durability 策略
无标准可循自研协议，无第三方实现、无认证路径OMG 国际标准，多家实现，有安全（DDS-Security）和车规认证路径
跨平台弱主要面向 Linux，Windows/嵌入式支持差DDS 实现覆盖 Linux/Windows/QNX/裸机（Micro-XRCE-DDS）
ROS1 像公司内部的一块公告板：所有人先去总台（Master）登记「我要发什么、我想看什么」，总台撮合后大家互相直连。总台一停摆，新人就进不来。ROS2/DDS 则像一个约定好频道的对讲机系统：没有总台，每个人开机后在公共频道喊一声「我在，我发 X 频道的内容」，需要的人自己记下来。代价是开机时的那一轮喊话（发现），人越多喊话越吵——这正是 §9 要解决的规模化问题。
DDS（Data Distribution Service）是 OMG 的数据分发标准，核心抽象是「全局数据空间」：参与者不是「给某个节点发消息」，而是「往某个 Topic 写数据 / 从某个 Topic 读数据」，发布者和订阅者互不知道对方存在。RTPS（Real-Time Publish-Subscribe Protocol）是 DDS 的线协议（wire protocol），规定了字节怎么在 UDP 上排布、怎么发现、怎么确认。两者关系是「API 标准」与「传输标准」——DDS 定义你写什么代码，RTPS 定义网线上跑什么字节。互操作性靠的是 RTPS。
ROS2 的复杂性有相当一部分是「DDS 通用性」的代价。DDS 设计目标是覆盖军舰作战系统、金融交易、工业 SCADA 等各种场景，所以有 20 多条 QoS 策略、复杂的发现机制、可插拔的传输层。而机器人用得上的可能只有 5–6 条。这个认知很重要：遇到问题时不要试图理解 DDS 的全部，而是搞清 ROS2 实际用到的那个子集——本文讲的就是这个子集。
02

DDS 数据中心模型

五个实体，一层层套进去

DDS 的对象模型是严格的层次结构。理解它的收益是：知道每个对象的生命周期和作用域，才能定位「为什么两个节点看不见对方」这类问题。

2.1 ROS2 概念到 DDS 概念的映射

ROS2 概念DDS 对应要注意什么
rclcpp::Node一组 Publisher/Subscriber 的封装不是 1:1 对应 DomainParticipant。默认多个 Node 共用一个 Participant（use_intra_process_comms 相关），因为 Participant 很重
Topic /scanTopic rt/scanROS2 加了前缀：话题 rt/、服务请求 rq/、响应 rr/。用原生 DDS 工具抓包时要认得
publish()DataWriter::write()返回即表示「已交给 DDS」，不代表已送达
订阅回调DataReader + Listener/WaitSet回调在哪个线程执行由 Executor 决定，见 §7
Service / Action两个 Topic（请求 + 响应）所以 Service 也受 QoS 影响；Action 是 Service + Topic 的组合，涉及更多实体
ROS_DOMAIN_IDdomain_id最常见的「互相看不见」原因。不同 domain 完全隔离，且 domain 决定 UDP 端口号
排查「两个节点互相看不见」的检查顺序：① ROS_DOMAIN_ID 是否一致（最高频）；② RMW_IMPLEMENTATION 是否一致（不同 DDS 实现之间理论上 RTPS 互通，但实际常有坑）；③ 网络是否允许组播（Docker 默认桥接网络、部分云环境、跨子网都会挡住组播，这是第二高频原因）；④ 话题名和消息类型的哈希是否完全一致（改了 .msg 没重编译就会不匹配）；⑤ QoS 是否兼容（见 §5，最隐蔽）。这五步按顺序走，九成问题在前三步解决。
03

RTPS 线协议

网线上到底跑的是什么

RTPS 是 DDS 的线协议，跑在 UDP 之上（也可跑 TCP、共享内存）。理解它的报文结构有很实际的价值：抓包排障时你得看得懂，而且发现流量的规模化问题只有从报文层面才能算清。

3.1 报文结构

── 一个 RTPS 消息 = 固定头 + 若干 Submessage ─────
┌────────────────────────────────┐
│ RTPS Header（20 B）             │
│  · 魔数 'R','T','P','S'        │
│  · 协议版本（2.2 等）           │
│  · vendorId（厂商标识）         │
│  · GuidPrefix（12 B，标识发送方）│
├────────────────────────────────┤
│ Submessage 1                   │  ← 一个 UDP 包里可以塞多个
│ Submessage 2                   │
│ ...                            │
└────────────────────────────────┘

── 关键 Submessage 类型 ────────────────────────
DATA       携带用户数据 + SequenceNumber + writerId/readerId
DATA_FRAG  大消息分片（超过 MTU 时；点云、图像常触发）
HEARTBEAT  Writer 告诉 Reader「我有 seq [firstSN, lastSN]，你缺什么？」
ACKNACK    Reader 回复「我收到到 N，缺 N+2、N+5」（位图表示）
GAP        Writer 说「seq X~Y 你不用等了，我不会发/已过期」
INFO_TS    时间戳
INFO_DST   目的 GUID（用于把组播包定向给某个 Reader）

★ GUID = GuidPrefix(12 B) + EntityId(4 B)，全局唯一标识每个实体
GAP 是最容易被忽略但很关键的一条。当 Writer 因为 History 策略（KEEP_LAST depth=1）把旧样本丢掉了，而 Reader 还在问「seq 5 呢」，Writer 就发 GAP 说「5 已经没了，别等」。没有 GAP 的话 Reader 会一直重试直到超时，白白浪费一个 Deadline 周期。这解释了一个常见现象：把 History 设成 KEEP_LAST depth=1 配合 RELIABLE 时，高速发布下会看到大量 GAP——这是正常的，不是故障。

3.2 发现机制：SPDP 与 SEDP

去中心化发现分两阶段，理解这个两阶段是理解发现流量为什么爆炸的前提：

组播是 ROS2 部署的第一大坑。SPDP 完全依赖 UDP 组播（默认 239.255.0.1），而组播在很多环境下默认不通：Docker 的默认 bridge 网络、多数公有云的 VPC、跨子网（组播不跨路由器除非配了 PIM/IGMP snooping）、某些企业交换机的默认配置。症状就是「ros2 topic list 看不到对方」。对策：① 容器用 --net=host；② 配置 DDS 的静态发现或Discovery Server（见 §9）用单播替代组播；③ 交换机上开 IGMP snooping 并确认组播组正确转发。
04

可靠传输状态机

RELIABLE 是怎么在 UDP 上实现的

DDS 的 RELIABLE 不是 TCP。它在 UDP 之上用 Heartbeat / AckNack 的显式协商实现可靠性，机制上更像「周期性对账」而不是「逐包确认」。这个差别决定了它的时延特性。

TCP 像挂号信逐封回执：每封信都要收到回执，没收到就重寄。RTPS 的 RELIABLE 像月底对账：发件人定期（Heartbeat 周期）发一份「本月我寄了 1 到 100 号」的清单，收件人核对后回复「我缺 37 和 82」，发件人只补这两封。好处是控制报文少得多（一个 Heartbeat 覆盖上百个样本），坏处是发现丢包的延迟取决于对账频率——Heartbeat 周期设成 100 ms，那么最坏要 100 ms 后才知道丢了包。

4.1 交互时序

── 正常流程 ────────────────────────────────────
Writer                                    Reader
  │── DATA seq=1 ────────────────────────────▶│  收到
  │── DATA seq=2 ─────────────✗（丢了）        │
  │── DATA seq=3 ────────────────────────────▶│  收到（但检测到缺 2）
  │                                           │
  │── HEARTBEAT [first=1, last=3] ───────────▶│  「我有 1~3」
  │◀── ACKNACK base=2, bitmap=[缺2,有3] ──────│  「我缺 2」
  │── DATA seq=2（重发）─────────────────────▶│  补齐
  │── HEARTBEAT [1,3] final ─────────────────▶│
  │◀── ACKNACK base=4（全收到）───────────────│  完成

── 关键参数（Fast DDS / Cyclone 都可配）─────────
heartbeatPeriod       Writer 多久发一次 Heartbeat   典型 100 ms ~ 3 s
nackResponseDelay     收到 ACKNACK 后延迟多久再重发  典型 0 ~ 5 ms
nackSuppressionDuration  忽略过于频繁的 ACKNACK      防止 NACK 风暴
heartbeatResponseDelay   Reader 收到 HB 后延迟回 ACKNACK  聚合多个 HB

★ 丢包恢复时延 ≈ heartbeatPeriod + RTT + nackResponseDelay
  → 默认配置下常常是 数百毫秒，对控制回路完全不可接受
这个公式是 ROS2 实时化最重要的一条。如果你用 RELIABLE 传 1 kHz 的控制指令，丢一个包的恢复要几百毫秒——那 300 个周期的指令全部作废。所以周期性控制流应该用 BEST_EFFORT + KEEP_LAST depth=1：反正下一个周期（1 ms 后）就有新数据了，重传一个 300 ms 前的旧指令毫无意义甚至有害。判断口诀：数据「过期即无用」→ BEST_EFFORT；数据「必须送到、晚点也行」→ RELIABLE。地图、参数、配置用 RELIABLE，传感器读数和控制指令用 BEST_EFFORT。

4.2 Writer 侧的历史缓存与阻塞

RELIABLE 要求 Writer 保留已发送但未被全部 Reader 确认的样本，这块内存叫 History Cache。它满了会发生什么，是个高频事故点：

❌ RELIABLE + KEEP_ALL + 慢 Reader
Writer 的 History 塞满（resource_limits）
  ↓
write() 阻塞（等 max_blocking_time）
  ↓
超时后返回 TIMEOUT，样本丢失
  ↓
如果调用方是控制线程 →
整个控制回路被一个慢订阅者拖死

典型元凶：rviz、rosbag record、
一个卡住的日志节点
✅ 正确的隔离做法
控制流：BEST_EFFORT + KEEP_LAST(1)
  → write() 永不阻塞

监控/录制流：独立的 Topic 或
  独立 Participant，RELIABLE
  + 有限 resource_limits
  → 慢消费者只影响自己

关键：不要让调试工具和控制流
共享同一条 QoS 严格的通道
「一个卡住的订阅者拖死整个机器人」是 ROS2 生产环境的经典事故。机制是：RELIABLE 的 Writer 必须等所有匹配的 Reader 确认；某个 Reader（比如远程 rviz 通过弱网连接、或一个 CPU 打满的节点）迟迟不确认；Writer 的 History 满了；publish() 从「非阻塞」变成「阻塞到超时」；如果这个 publish() 在控制线程里，控制周期直接被拉长几百毫秒。三道防线：① 控制流一律 BEST_EFFORT；② 必须 RELIABLE 时设置合理的 resource_limits 和很短的 max_blocking_time（比如 1 ms）；③ 调试/可视化流物理隔离到独立 Participant 甚至独立 domain。
05

QoS 策略与兼容性

半天调不通的元凶通常在这

DDS 有 20 多条 QoS 策略，ROS2 暴露了其中 7 条常用的。关键规则叫「Request vs Offered（RxO）兼容性」：Reader 请求的服务等级不能高于 Writer 提供的，否则静默不匹配——不报错，就是收不到数据。

5.1 七条常用策略

策略取值作用选择建议
ReliabilityRELIABLE / BEST_EFFORT是否重传丢失的样本控制/传感器 → BEST_EFFORT；地图/参数 → RELIABLE
HistoryKEEP_LAST(depth) / KEEP_ALL缓存多少个样本周期数据 → KEEP_LAST(1)；事件流 → 按需 depth；KEEP_ALL 慎用（无界内存）
DurabilityVOLATILE / TRANSIENT_LOCAL晚加入的 Reader 能否收到历史数据「latched」语义（地图、静态 TF、机器人描述）→ TRANSIENT_LOCAL
Deadline时长承诺/要求的最大样本间隔；违约触发回调周期流设成 2–3 倍周期，用于检测「对端不发了」
LivelinessAUTOMATIC / MANUAL_BY_TOPIC + lease判定 Writer 是否还活着要区分「进程活着但业务卡死」→ 用 MANUAL_BY_TOPIC
Lifespan时长样本超过此时长自动作废控制指令设成 2–3 个周期，防止积压的旧指令被执行
OwnershipSHARED / EXCLUSIVE + strength多个 Writer 写同一 Topic 时谁说话算数主备冗余控制器 → EXCLUSIVE + 不同 strength，自动主备切换
Lifespan 是机器人场景里最被低估的一条。它让样本「自动过期」——写进去 3 ms 后如果还没被读走，DDS 直接丢弃。这正好实现了 确定性保障体系 §8 里说的「不要用过期指令继续动」，而且是在中间件层实现的，不需要每个应用自己检查时间戳。配合 KEEP_LAST(1)，你得到的语义是「Reader 永远只能看到最新且新鲜的那一条」——这几乎就是周期控制流的理想语义。

5.2 兼容性矩阵

规则是「Offered ≥ Requested」：Writer 提供的等级必须不低于 Reader 请求的。

交互：QoS 兼容性判定

分别设置 Writer（Offered）和 Reader（Requested）的策略，看是否能匹配上以及为什么。这是排查「话题有数据但订阅不到」的核心工具。

Writer Reliability
Reader Reliability
Writer Durability
Reader Durability
Writer Deadline
Reader Deadline
策略兼容条件不兼容时的症状
ReliabilityWriter RELIABLE 可配任意 Reader；Writer BEST_EFFORT 只能配 Reader BEST_EFFORT完全收不到数据
DurabilityWriter TRANSIENT_LOCAL 可配任意；Writer VOLATILE 只能配 Reader VOLATILE完全收不到数据。典型场景：订阅 /map 忘了设 TRANSIENT_LOCAL，于是「地图发了但收不到」
DeadlineWriter 的 deadline ≤ Reader 的 deadline（Writer 承诺发得更勤）完全收不到数据
LivelinessWriter 的 lease_duration ≤ Reader 的；且 kind 的强度 Writer ≥ Reader完全收不到数据
History / Lifespan不参与兼容性判定（各端独立生效）不会导致不匹配，但会影响行为（丢样本、内存增长）
ROS2 提供了预置 QoS profile，优先用它们而不是手搓。rclcpp::SensorDataQoS()（BEST_EFFORT + KEEP_LAST(5)，适合传感器）、rclcpp::SystemDefaultsQoS()、rclcpp::ServicesQoS()、rclcpp::ParameterEventsQoS()。它们的组合是社区踩过坑之后定下来的。最需要手动指定的场景只有两类：① 需要 latched 语义（地图/静态 TF）→ 手动设 TRANSIENT_LOCAL；② 硬实时控制流 → 手动设 BEST_EFFORT + KEEP_LAST(1) + Lifespan。
调试 QoS 不匹配的最快方法：ros2 topic info /topic_name --verbose 会列出所有 Publisher 和 Subscriber 的完整 QoS，直接肉眼比对。另外可以订阅 rclcpp 的 QOSRequestedIncompatibleQoS 事件回调（SubscriptionOptions::event_callbacks），在代码里主动捕获不兼容事件并打日志——比事后猜测高效得多。生产系统应该默认注册这个回调，把静默失败变成显式告警。
06

rmw 层与实现选型

换一行环境变量，性能差几倍

ROS2 通过 rmw（ROS MiddleWare）抽象层把自己和具体 DDS 实现解耦。切换实现只需换一个环境变量，但行为差异相当大。

── 分层结构 ────────────────────────────────────
你的代码
   ↓
rclcpp / rclpy          ← 语言绑定，Node/Publisher/Executor 都在这层
   ↓
rcl                     ← C 语言核心，语言无关的通用逻辑
   ↓
rmw（抽象接口）           ← ★ 可替换的边界
   ↓
rmw_fastrtps_cpp / rmw_cyclonedds_cpp / rmw_zenoh_cpp / rmw_connextdds
   ↓
Fast DDS / Cyclone DDS / Zenoh / RTI Connext

── 切换方法 ────────────────────────────────────
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
# ★ 所有互相通信的节点必须用同一个实现（虽然 RTPS 理论互通，实际常有坑）
Fast DDS（eProsima）—— 默认实现

功能最全：内置 Discovery Server（单播替代组播）、共享内存传输、DDS-Security、XML 配置文件。代价是配置项极多、默认参数偏向通用性而非实时性、内存占用较大。生态和文档最好，遇到问题最容易找到答案。

Cyclone DDS（Eclipse）—— 更轻更稳

代码量小、依赖少、内存占用低，延迟更稳定（尾部分位表现通常优于 Fast DDS 默认配置）。配置通过单个 XML，选项少但够用。被很多产品化项目选中，尤其是资源受限的嵌入式平台。缺点是高级特性（如 Discovery Server 等价物）较少。

rmw_zenoh —— 不是 DDS

ROS 2 Jazzy 起提供的非 DDS 后端。用 Zenoh 协议替代 RTPS，从根上解决了发现风暴和组播依赖：默认走 router 模式（单播、可跨网段、天然穿 NAT），大规模和跨网络场景表现明显更好。代价：与原生 DDS 系统不互通、生态较新、部分 QoS 语义映射不完全对齐。

RTI Connext —— 商业

工具链（Admin Console、录制回放、监控）和认证支持（DO-178C、ISO 26262 相关）最强，适合需要功能安全认证的项目。商业授权成本高。

选型判断：① 刚起步、要文档和社区支持 → Fast DDS 默认；② 产品化、要稳定的尾部延迟和小内存 → Cyclone DDS；③ 节点数量多（> 50）、要跨网段/跨 NAT、被组播折磨 → rmw_zenoh；④ 需要功能安全认证 → Connext。最重要的一条：不管选哪个，都要在自己的负载下实测 P99.9 延迟，不要照抄别人的 benchmark——DDS 的性能对配置极其敏感，同一个实现调优前后能差三五倍。
07

Executor 与实时陷阱

回调到底在哪个线程、按什么顺序跑

DDS 负责把数据送到进程，Executor 负责决定什么时候在哪个线程调用你的回调。ROS2 实时化的大部分坑都在这一层，而不是在 DDS 里。

7.1 三种 Executor

Executor行为问题
SingleThreadedExecutor一个线程轮询所有就绪的回调，逐个执行一个慢回调阻塞所有其他回调；无法利用多核
MultiThreadedExecutor线程池并发执行不同回调组的回调回调可能并发——共享状态必须自己加锁；线程分配不可控，实时性差
StaticSingleThreadedExecutor启动时把实体集合固定下来，运行时不再重新扫描吞吐更高、开销更低，但运行时不能动态增删实体
默认 Executor 的调度顺序不是「先到先服务」，而是有固定优先级的轮询。ROS2 默认 Executor 每一轮按固定类别顺序扫描：timer → subscription → service → client → waitable，并且同类别内按注册顺序取第一个就绪的。后果是：如果一个高频 timer 一直就绪，它可能持续抢在 subscription 之前；而同一类别里注册顺序靠前的实体也天然占优。这意味着回调的执行顺序既不公平也不由业务优先级决定——是实现细节。生产系统里如果依赖某种回调顺序，那是隐藏的 bug。

7.2 回调组：控制并发的唯一手段

── 两种回调组语义 ──────────────────────────────
MutuallyExclusive   同组内的回调永不并发（组内串行）
Reentrant           同组内的回调可以并发（含同一个回调的多次调用）

── 典型实时化布局 ──────────────────────────────
class RobotNode : public rclcpp::Node {
  RobotNode() : Node("robot") {
    // ① 控制回路独占一个互斥组 —— 保证串行、不被打断语义混淆
    ctrl_group_ = create_callback_group(
        rclcpp::CallbackGroupType::MutuallyExclusive);
    // ② 慢任务（点云处理、日志）放另一个组，可并发
    slow_group_ = create_callback_group(
        rclcpp::CallbackGroupType::Reentrant);

    rclcpp::SubscriptionOptions ctrl_opt;
    ctrl_opt.callback_group = ctrl_group_;
    joint_sub_ = create_subscription<JointState>(
        "joint_states", rclcpp::SensorDataQoS(),
        [this](JointState::SharedPtr m){ on_joint(m); }, ctrl_opt);

    rclcpp::SubscriptionOptions slow_opt;
    slow_opt.callback_group = slow_group_;
    cloud_sub_ = create_subscription<PointCloud2>(
        "points", rclcpp::SensorDataQoS(),
        [this](PointCloud2::SharedPtr m){ on_cloud(m); }, slow_opt);
  }
  rclcpp::CallbackGroup::SharedPtr ctrl_group_, slow_group_;
  /* ... */
};

── ★ 关键：用两个独立 Executor + 两个线程，各自设优先级 ──
int main(int argc, char** argv) {
  rclcpp::init(argc, argv);
  auto node = std::make_shared<RobotNode>();

  rclcpp::executors::SingleThreadedExecutor ctrl_exec, slow_exec;
  ctrl_exec.add_callback_group(node->ctrl_group_, node->get_node_base_interface());
  slow_exec.add_callback_group(node->slow_group_, node->get_node_base_interface());

  std::thread ctrl_thread([&]{
      set_realtime_priority(80);          // SCHED_FIFO 80
      pin_to_cpu(2);                      // 配合 isolcpus=2
      ctrl_exec.spin();
  });
  std::thread slow_thread([&]{ slow_exec.spin(); });   // 普通优先级

  ctrl_thread.join(); slow_thread.join();
  rclcpp::shutdown();
}
「一个 Executor 一个线程一种优先级」是 ROS2 实时化的标准模式。因为 MultiThreadedExecutor 的线程池无法为不同回调设置不同的实时优先级——线程是共享的，你不知道哪个回调会跑在哪个线程上。而多个 SingleThreadedExecutor 各跑在自己的线程里，你就能精确控制「控制回路这个线程是 SCHED_FIFO 80 并绑在隔离核上，点云处理那个线程是普通优先级」。这个模式加上 PREEMPT_RT，才是 ROS2 能做实时的前提。

7.3 四个必做的实时化动作

  • 内存预分配 + 锁定。启动时 mlockall(MCL_CURRENT | MCL_FUTURE)，避免运行时页错误（一次 major fault 就是几百微秒到毫秒）。消息类型尽量用定长（避免 std::vector/string 在回调里动态分配），或者用自定义分配器 + 内存池。
  • 避免回调里做任何可能阻塞的事：文件 I/O、日志落盘（RCLCPP_INFO 在某些配置下会同步写）、锁竞争、内存分配、DNS 解析。把这些挪到低优先级线程。
  • 不要用 SharedPtr 的引用计数做热路径传递——原子操作在多核上有跨核缓存同步开销。热路径优先用 unique_ptr（触发进程内零拷贝，见 §8）。
  • 关闭不必要的中间件开销：不用的 /parameter_events、/rosout 日志话题、以及 introspection（--enable-type-description-service 之类）在高频场景下都是额外的发现和序列化成本。
最反直觉的一条：进程内通信（intra-process）不一定更快。ROS2 的 use_intra_process_comms(true) 会绕过 DDS 直接在进程内传指针，理论上零拷贝。但它有两个陷阱：① 只在发布时用 unique_ptr 且订阅端接受 unique_ptr 或 const& 时才真正零拷贝，用 SharedPtr 或值传递会退化为拷贝；② 进程内通信的队列满了会静默丢弃，行为和 DDS 的 QoS 不完全一致，容易出现「同样的代码在单进程和多进程下行为不同」。要用就要实测确认真的零拷贝了（看有没有 memcpy 的开销）。
08

零拷贝与共享内存

点云和图像的唯一出路

一帧 1080p RGB 图像是 6 MB，一帧 32 线激光点云约 200 KB。如果每次发布都做序列化 + 内存拷贝 + UDP 分片，光是拷贝和分片就吃掉几毫秒，还会把 CPU 打满。零拷贝是大数据话题的必需品，不是优化。

8.1 三个层次的零拷贝

层次机制适用范围收益
进程内ROS2 intra-process：unique_ptr 直接移交所有权同一进程内的节点（用 composition 把节点装进同一进程）完全零拷贝，只传指针
进程间共享内存DDS 的 SHM 传输（Fast DDS SHM、Cyclone 的 iceoryx psmx 插件）同一台机器的不同进程一次拷贝进共享段，多个订阅者共读不再拷贝
Loaned MessageDDS 借出一块本身就在共享内存里的缓冲，应用直接写进去同机进程间，且消息类型是 POD / 定长真正的端到端零拷贝，一次都不拷
 
── Loaned Message 用法（真零拷贝）──────────────
// 前提：消息类型必须是「plain / fixed size」——
// 不含 string、不含变长 sequence，否则会静默退化为普通拷贝路径
auto pub = create_publisher<MyPodMsg>("topic", qos);

// ① 向中间件「借」一块缓冲（它可能直接位于共享内存段里）
auto loaned = pub->borrow_loaned_message();
if (!loaned.is_valid()) { /* 该实现不支持，走普通路径 */ }

// ② 直接往里写，不经过任何中间缓冲
loaned.get().timestamp_ns = now_tai_ns();
loaned.get().joint_pos[0] = 1.234;

// ③ 归还即发布（所有权移交给中间件）
pub->publish(std::move(loaned));

── 检查是否真的零拷贝 ──────────────────────────
# Fast DDS：确认 SHM 传输已启用且在用
export FASTDDS_BUILTIN_TRANSPORTS=SHM
# 用 perf 看有没有大块 memcpy；有就是没走通
perf record -g ./your_node && perf report | grep -i memcpy
三个层次像三种交接文件的方式：进程内是「把桌上那份文件推给同办公室的同事」（只是换个人拿）；共享内存是「放到公共文件柜里，谁要谁去看」（放一次，多人共读）；Loaned Message 是「直接在公共文件柜里的纸上写」（连「放进去」这一步都省了）。而没有零拷贝的默认路径是「每个人都复印一份自己拿走」——人越多复印越多。
「消息类型必须是 POD」是 Loaned Message 最大的限制，也是设计上的一个重要提示。标准的 sensor_msgs/PointCloud2 含变长 data 字段，不满足条件，所以拿不到真零拷贝。实践中的做法是自定义定长消息：把点云按固定最大点数定义（比如 Point points[65536]; uint32 valid_count;），牺牲一点内存换零拷贝。这个取舍在高频大数据场景通常是值得的——浪费 20% 内存换来省掉 90% 的 CPU 拷贝开销。同样的思路在高性能网络编程里叫「以空间换时间的定长协议」，见 二进制协议设计。
09

规模化：发现风暴与调优

30 个节点还好，300 个就起不来了

ROS2 在十几个节点时非常顺，到几十上百个节点后会出现一类难查的问题：启动极慢、CPU 常态偏高、话题偶发丢失、重启后行为不一致。根源基本都在 §3 提到的 SEDP 的 O(N²)。

9.1 问题的量级

── 发现开销的估算 ──────────────────────────────
设：P 个 Participant，每个平均 E 个端点（Writer + Reader）

SPDP（组播）：
  每 5 s 有 P 个组播包，每个节点都要收全部 P 个 → P² 次处理 / 5 s
  
SEDP（单播）：
  两两交换端点清单 → P × (P-1) × E 条端点信息
  每条端点信息含话题名、类型名、完整 QoS（数百字节）

── 实例 ────────────────────────────────────────
P = 100, E = 20：
  SEDP 端点信息条数 ≈ 100 × 99 × 20 = 198,000
  每条 ~300 B → 启动瞬间约 59 MB 发现流量
  每个节点要做 99 × 20 = 1,980 次匹配判定 × 100 个节点
  
→ 症状：启动要几分钟；期间 CPU 满载；组播风暴可能挤掉业务流量
→ 更糟：某些节点在发现完成前就开始工作，行为不确定

9.2 五个有效的对策

对策做法效果与代价
合并进程（composition）用 rclcpp_components 把多个节点装进一个进程最有效：Participant 数量直接下降一个数量级，还顺带拿到进程内零拷贝。代价是故障隔离变差（一个节点崩溃拖累整个进程）
Discovery ServerFast DDS 的中心化发现：节点只和 server 单播交换，不再两两 SEDP发现流量从 O(N²) 降到 O(N)；不再依赖组播。代价是引入一个（可冗余的）中心组件
换 rmw_zenohRMW_IMPLEMENTATION=rmw_zenoh_cpp + 启动 zenoh router从根上不用 RTPS 发现；天然跨网段、穿 NAT。代价是与原生 DDS 不互通
静态发现XML 里写死对端的 GUID、IP、端点清单，完全跳过动态发现启动最快、流量最小、完全确定。代价是拓扑硬编码，改一个节点要改配置——但机器人的节点集合本来就是固定的，这个代价往往可以接受
Domain 分区按子系统划分不同 ROS_DOMAIN_ID，跨域用桥接节点把 N² 拆成几个小 N²。代价是跨域通信要显式桥接
对机器人产品来说，「静态发现」这条常常被低估。一台机器人的节点集合在出厂时就固定了——不会运行时冒出一个新节点。所以动态发现提供的灵活性对产品毫无价值，却让你付出了启动慢、流量大、行为不确定的全部代价。把发现配成静态之后，启动时间可以从几十秒降到一两秒，且完全确定（不会出现「有时候某个话题连不上」）。做法是导出运行时的发现信息生成 XML，纳入构建产物。开发阶段用动态发现（方便），出货用静态发现（确定），是很务实的组合。

9.3 其他常见调优项

  • 增大 socket 缓冲。默认 net.core.rmem_max 常常只有 200 KB 左右，点云突发时直接溢出丢包。调到 16–64 MB，并在 DDS 配置里设置对应的 socketBufferSize。这是「点云偶发丢帧」最常见的原因。
  • 调大 MTU 或启用分片控制。大消息走 DATA_FRAG，UDP 层再分片就是双重分片。局域网内启用 jumbo frame（MTU 9000）能显著降低分片开销和丢包放大效应。
  • 限制 History 与 resource_limits。KEEP_ALL + 无限 resource_limits 是内存泄漏式增长的配方；生产配置必须显式设上限。
  • 关掉不用的传输。如果只在本机通信，禁用 UDP 只留 SHM，能省掉大量开销和端口占用。
  • 把发现流量和业务流量分开。多网卡场景用 whitelist 指定 DDS 只用某张网卡，避免发现包跑到业务网或管理网上。
10

DDS over TSN

中间件和确定性网络怎么对接

把 TSN 和 DDS 拼起来时，最关键的问题是：DDS 的 QoS 概念和 TSN 的流概念怎么映射？两者都叫 QoS，但完全不是一个层面的东西。

维度DDS QoSTSN
作用层应用语义层：可靠性、历史、生命期链路调度层：什么时刻允许哪个队列发送
保证内容「数据会不会送到、送到几份、过期不过期」「帧最坏什么时候到」
是否保证时延不保证。Deadline 只是「违约通知」，不是「时延保证」保证，且可证明上界
粒度每个 Topic / DataWriter每个流量类别（8 个）或每条流（Qci）
DDS 的 Deadline 不提供任何时延保证——这是最常见的误解。它的语义是「如果连续两个样本的间隔超过 X，触发一个回调告诉你违约了」。它是监控机制，不是调度机制。真正的时延保证必须来自下层：TSN 的门控、DetNet 的排队、或 5G 的 5QI。所以「我配了 Deadline 10 ms 为什么还会晚到」这个问题的答案是：Deadline 从来就不管这个。

10.1 对接的三个动作

  1. 把 DDS 流量映射到正确的 socket priority。这是唯一的连接点：DDS 发出的 UDP 包要带上正确的 SO_PRIORITY，TSN 的 mqprio 才能把它放进对应的硬件队列。Fast DDS 和 Cyclone 都支持在传输配置里设置 socket 的 SO_PRIORITY 或 DSCP（IP_TOS）。不设的话所有 DDS 流量都是同一个优先级，TSN 的门控形同虚设。
  2. 把发布时刻对齐到 TSN 周期。光有优先级不够——TT 窗口只在特定时刻打开，如果应用在窗口之外调用 publish()，包要等到下一个窗口。所以发布线程要用 clock_nanosleep(CLOCK_TAI, TIMER_ABSTIME) 对齐到 GCL 周期，配合 etf qdisc 和 SO_TXTIME。
  3. 把大消息挡在 TT 通道之外。点云、图像这类大消息会产生大量 DATA_FRAG，塞进 TT 窗口会挤爆它。必须按 Topic 分优先级：控制类 Topic 走高优先级 + TT 窗口，大数据 Topic 走 CBS 或 BE 队列。
DDS 的自身控制流量也要考虑进去。Heartbeat、AckNack、SPDP、SEDP 这些报文和业务数据走同一个 socket，因此享受同样的优先级。后果是：如果把控制 Topic 设成最高优先级，那么这个 Participant 的发现流量也变成最高优先级——启动时的发现风暴会直接冲进 TT 窗口。对策是把控制流放在独立的 Participant 里（甚至独立 domain），让它的发现流量规模极小；或者用静态发现彻底消除发现流量。这个细节很容易漏，而症状是「平时正常，只在有节点重启时抖动」。
11

面试题集（12 道）

按难度分层，先自测再对照

11.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础ROS2 为什么放弃 ROS1 的自研通信改用 DDS？

    ROS1 用的是自研的 TCPROS/UDPROS + 中心化 Master，有五个结构性问题：

    • 单点故障：roscore 挂了新节点无法建连 → DDS 是去中心化发现，无 Master。
    • 无实时能力：TCP 的重传和拥塞控制带来不可预测时延，没有 QoS 概念 → DDS 有可配 QoS（BestEffort、Deadline、Liveliness）。
    • 不适合弱网：TCP 断线要重连，无法表达「只要最新数据」→ UDP 之上的 RTPS + History/Durability。
    • 无标准可循：无第三方实现、无认证路径 → OMG 国际标准，多家实现，有 DDS-Security 和车规认证路径。
    • 跨平台弱 → DDS 覆盖 Linux/Windows/QNX/裸机。
    代价
    DDS 为覆盖军工、金融、SCADA 等场景设计，有 20+ 条 QoS 和复杂发现机制，而机器人只用得上 5–6 条。遇到问题不要试图理解 DDS 全部，搞清 ROS2 实际用到的子集就够。
  2. 基础DDS 和 RTPS 是什么关系？Topic 匹配需要满足什么条件？

    DDS 是 API 标准，RTPS 是线协议标准：DDS 定义你写什么代码（DomainParticipant / Publisher / DataWriter 等对象模型），RTPS 定义网线上跑什么字节。互操作性靠 RTPS。

    Writer 与 Reader 匹配的三要素（缺一个就静默不匹配，不报错只是收不到）：

    1. 同一个 domain_id
    2. 同一个 Topic 名 + 同一个数据类型（含类型哈希）
    3. QoS 兼容
    排查「两节点看不见」的顺序
    ① ROS_DOMAIN_ID 是否一致（最高频）；② RMW_IMPLEMENTATION 是否一致；③ 网络是否允许组播（Docker 默认 bridge、公有云 VPC、跨子网都会挡住，第二高频）；④ 话题名和消息类型哈希是否一致（改了 .msg 没重编译）；⑤ QoS 是否兼容（最隐蔽）。九成问题在前三步解决。
  3. 基础ROS2 常用的 QoS 策略有哪些？控制指令该怎么配？

    七条常用策略：Reliability、History、Durability、Deadline、Liveliness、Lifespan、Ownership。

    控制指令的推荐配置：

    • BEST_EFFORT——因为丢了一个包，重传要几百毫秒（见下题），而 1 ms 后就有新指令了，重传旧指令毫无意义甚至有害。
    • KEEP_LAST(depth=1)——只保留最新的一条。
    • Lifespan 设成 2–3 个周期——让样本自动过期，防止积压的旧指令被执行。
    判断口诀
    数据「过期即无用」→ BEST_EFFORT（传感器读数、控制指令）；数据「必须送到、晚点也行」→ RELIABLE（地图、参数、配置）。
    Lifespan 被低估了
    它在中间件层实现了「不用过期数据」，不需要每个应用自己校验时间戳。配合 KEEP_LAST(1)，语义是「Reader 永远只看到最新且新鲜的那一条」——几乎就是周期控制流的理想语义。
  4. 基础什么是 Durability 的 TRANSIENT_LOCAL？什么场景需要它？

    TRANSIENT_LOCAL 让 Writer 为「晚加入的 Reader」保留历史样本，新订阅者连上后能立刻收到之前发布的数据。VOLATILE（默认）则只发给当时已连接的 Reader。

    这对应 ROS1 里的 latched publisher 语义，典型场景：

    • /map——地图只发一次，之后启动的节点也要能拿到
    • /tf_static——静态坐标变换
    • /robot_description——机器人 URDF
    • 各种「配置类」一次性下发的数据
    最经典的坑
    订阅 /map 时忘了设 TRANSIENT_LOCAL，于是「地图明明发了但订阅不到」。因为兼容规则是 Writer VOLATILE 只能配 Reader VOLATILE；反过来 Writer TRANSIENT_LOCAL 可以配任意 Reader，但如果 Reader 是 VOLATILE，它能匹配上却收不到历史数据——两端都要设才有效。

11.2 中级（区分熟练度）

  1. 中级RTPS 的 RELIABLE 是怎么实现的？和 TCP 有什么本质区别？

    RTPS 在 UDP 之上用 Heartbeat / AckNack 的显式协商实现可靠性，机制上是「周期性对账」而不是 TCP 的「逐包确认」。

    交互：Writer 周期性发 HEARTBEAT [firstSN, lastSN] 告诉 Reader「我有这些」；Reader 回 ACKNACK 带位图说「我缺 2 和 5」；Writer 只补这两个。另有 GAP 子消息表示「seq X~Y 已过期，别等了」。

    丢包恢复时延公式
    ≈ heartbeatPeriod + RTT + nackResponseDelay。默认 heartbeatPeriod 常在 100 ms ~ 3 s，所以恢复时延常常是数百毫秒。对 1 kHz 控制回路意味着300 个周期的指令全部作废——这就是控制流必须用 BEST_EFFORT 的原因。
    和 TCP 的取舍
    控制报文少得多（一个 Heartbeat 覆盖上百个样本），但发现丢包的延迟取决于对账频率。TCP 是逐包回执，发现快但控制报文多、且有拥塞控制引入的额外不确定性。
  2. 中级为什么「一个卡住的订阅者能拖死整个机器人」？怎么防？

    机制链：RELIABLE 的 Writer 必须保留未被所有 Reader 确认的样本（History Cache）→ 某个 Reader 迟迟不确认（远程 rviz 走弱网、或一个 CPU 打满的节点）→ Writer 的 History 满了 → publish() 从非阻塞变成阻塞到 max_blocking_time → 如果这个 publish() 在控制线程里，控制周期直接被拉长几百毫秒。

    典型元凶：rviz、rosbag record、一个卡住的日志节点。

    三道防线
    ① 控制流一律 BEST_EFFORT（write() 永不阻塞）；② 必须 RELIABLE 时设置合理的 resource_limits 和很短的 max_blocking_time（如 1 ms）；③ 调试/可视化流物理隔离到独立 Participant 甚至独立 domain。
    还要避开 KEEP_ALL
    RELIABLE + KEEP_ALL + 无限 resource_limits 是内存无界增长的配方。生产配置必须显式设上限。
  3. 中级ROS2 的 Executor 有哪几种？为什么实时化要用「多个单线程 Executor」？

    三种：SingleThreadedExecutor（一个线程轮询所有回调，一个慢回调阻塞全部）、MultiThreadedExecutor（线程池并发，共享状态要自己加锁）、StaticSingleThreadedExecutor（启动时固定实体集合，开销更低但不能动态增删）。

    MultiThreadedExecutor 的实时性问题
    它的线程池无法为不同回调设置不同的实时优先级——线程是共享的，你不知道哪个回调跑在哪个线程上。
    标准实时化模式：一个 Executor 一个线程一种优先级
    用 create_callback_group() 把控制回路和慢任务分到不同回调组，再用两个 SingleThreadedExecutor 各跑在自己的线程里，通过 add_callback_group() 绑定。这样能精确设置「控制线程 SCHED_FIFO 80 + 绑在 isolcpus 隔离核」、「点云线程普通优先级」。
    还有个隐藏坑：默认调度顺序
    默认 Executor 每轮按固定类别顺序扫描：timer → subscription → service → client → waitable，同类别内按注册顺序。所以高频 timer 可能持续抢在 subscription 之前。回调执行顺序既不公平也不由业务优先级决定——依赖它就是隐藏 bug。
  4. 中级点云/图像这类大消息怎么做零拷贝？有什么限制？

    三个层次：

    层次机制范围
    进程内intra-process：unique_ptr 移交所有权同进程（用 composition 装进一个进程）
    进程间 SHMDDS 共享内存传输（Fast DDS SHM、Cyclone + iceoryx）同机不同进程，多订阅者共读
    Loaned Message借出一块本身就在共享内存里的缓冲，应用直接写同机进程间，真正端到端零拷贝
    Loaned Message 的硬限制：消息必须是 POD / 定长
    不能含 string、不能含变长 sequence，否则静默退化为普通拷贝路径。标准的 sensor_msgs/PointCloud2 含变长 data 字段，拿不到真零拷贝。
    实践做法
    自定义定长消息：按固定最大点数定义（Point points[65536]; uint32 valid_count;），牺牲内存换零拷贝。浪费 20% 内存换省掉 90% CPU 拷贝，高频大数据场景通常值得。用 perf report | grep memcpy 验证是否真的走通了。
    intra-process 不一定更快
    只在「发布用 unique_ptr 且订阅端接受 unique_ptr 或 const&」时才真零拷贝，用 SharedPtr 或值传递会退化为拷贝；且进程内队列满了静默丢弃，行为与 DDS QoS 不完全一致。

11.3 高级（体现深度）

  1. 高级ROS2 系统扩到上百个节点后会出什么问题？根因和对策是什么？

    症状：启动极慢（几分钟）、CPU 常态偏高、话题偶发丢失、重启后行为不一致。

    根因是 SEDP 的 O(N²)。发现分两阶段：SPDP 周期性组播宣告参与者（O(N) 包，但每个节点都要处理全部 N 个）；SEDP 单播两两交换完整端点清单（话题名 + 类型 + 完整 QoS，数百字节/条）。

    100 个 Participant × 每个 20 个端点：100 × 99 × 20 ≈ 198,000 条端点信息，启动瞬间约 59 MB 发现流量，每个节点近 2000 次匹配判定。

    五个对策（按有效性排序）
    ① 合并进程（composition）——Participant 数降一个数量级，还顺带拿到进程内零拷贝，代价是故障隔离变差；② Discovery Server——O(N²) 降到 O(N)，不再依赖组播；③ 换 rmw_zenoh——从根上不用 RTPS 发现，天然跨网段穿 NAT；④ 静态发现；⑤ Domain 分区 + 桥接节点。
    机器人产品应该用静态发现
    节点集合出厂即固定，动态发现的灵活性对产品毫无价值，却让你付出启动慢、流量大、行为不确定的全部代价。配成静态后启动时间从几十秒降到一两秒且完全确定。务实组合：开发阶段用动态发现（方便），出货用静态发现（确定）。
  2. 高级Fast DDS / Cyclone DDS / rmw_zenoh 怎么选？
    Fast DDS（默认）
    功能最全：Discovery Server、共享内存、DDS-Security、XML 配置。生态和文档最好。代价是配置项极多、默认参数偏通用而非实时、内存占用较大。
    Cyclone DDS
    代码量小、依赖少、内存占用低，尾部延迟通常比 Fast DDS 默认配置更稳。适合资源受限的嵌入式平台和产品化项目。高级特性较少。
    rmw_zenoh（Jazzy 起，非 DDS）
    用 Zenoh 协议替代 RTPS，从根上解决发现风暴和组播依赖：默认 router 模式（单播、跨网段、穿 NAT）。代价是与原生 DDS 不互通、生态较新、部分 QoS 语义映射不完全对齐。
    RTI Connext（商业）
    工具链和功能安全认证支持最强（DO-178C、ISO 26262 相关），授权成本高。
    最重要的一条
    不管选哪个，都要在自己的负载下实测 P99.9 延迟，不要照抄别人的 benchmark——DDS 性能对配置极其敏感，同一实现调优前后能差三五倍。
  3. 高级DDS 的 QoS 和 TSN 的 QoS 是一回事吗？怎么把两者对接起来？

    完全不是一回事。

    维度DDS QoSTSN
    作用层应用语义层：可靠性、历史、生命期链路调度层：何时允许哪个队列发送
    是否保证时延不保证保证，可证明上界
    最常见的误解：Deadline ≠ 时延保证
    DDS 的 Deadline 语义是「连续两个样本间隔超过 X 就触发违约回调」——它是监控机制，不是调度机制。「我配了 Deadline 10 ms 为什么还会晚到」的答案是：Deadline 从来就不管这个。真正的时延保证必须来自下层（TSN 门控 / DetNet 排队 / 5G 的 5QI）。
    对接的三个动作
    ① 设置 socket priority / DSCP——这是唯一的连接点，DDS 发出的 UDP 包要带正确的 SO_PRIORITY，mqprio 才能放进对应硬件队列；不设的话所有 DDS 流量同优先级，TSN 门控形同虚设。② 把发布时刻对齐 GCL 周期——用 clock_nanosleep(CLOCK_TAI, TIMER_ABSTIME) + etf qdisc + SO_TXTIME。③ 把大消息挡在 TT 通道外——点云产生大量 DATA_FRAG，会挤爆 TT 窗口，必须按 Topic 分优先级。
    容易漏的细节
    DDS 自身的 Heartbeat / AckNack / SPDP / SEDP 和业务数据走同一个 socket，享受同样优先级。把控制 Topic 设成最高优先级，该 Participant 的发现流量也变成最高优先级，启动时的发现风暴直接冲进 TT 窗口。对策：控制流放独立 Participant（甚至独立 domain），或用静态发现彻底消除发现流量。症状是「平时正常，只在有节点重启时抖动」。
  4. 高级要在 ROS2 上做一个 1 kHz 的硬实时控制回路，你会怎么设计？

    先说结论：能不跨进程就不跨，能不跨网络就不跨。1 kHz 回路的理想形态是「控制逻辑和驱动在同一进程、用共享内存或直接函数调用」，ROS2 只用来做配置下发和状态上报。如果必须跨节点，按下面来。

    ① 通信层：BEST_EFFORT + KEEP_LAST(1) + Lifespan 2–3 ms；消息类型设计成定长 POD 以启用 Loaned Message；同机进程间只启用 SHM 传输、禁用 UDP。

    ② 发现层：静态发现，彻底消除发现流量与启动不确定性；控制流独占一个 Participant。

    ③ 执行层：控制回路独占一个 MutuallyExclusive 回调组 + 独立的 SingleThreadedExecutor + 独立线程，设 SCHED_FIFO 高优先级并绑到 isolcpus 隔离核；mlockall() 锁内存；回调里不做任何 I/O、日志落盘、动态内存分配、锁竞争。

    ④ 操作系统层：PREEMPT_RT 内核，关闭 CPU 频率调节与深度 C-state，中断亲和性避开隔离核。

    ⑤ 网络层（若跨设备）：TSN 门控 + 帧抢占；设置 socket priority 让 DDS 包进 TT 队列；用 clock_nanosleep(CLOCK_TAI, TIMER_ABSTIME) 对齐 GCL 周期。

    ⑥ 安全层：消息自带时间戳 + 序号，执行端校验新鲜度；分级降级（保持 → 减速 → 受控停止），带滞回和渐进恢复。

    最重要的排序认知
    按 确定性保障体系 的预算分解，1 ms 里网络只占 2%–20%。所以优先级应该是：先关掉聚合类隐藏缓冲（零成本）→ 上实时 OS（常常是最大项）→ 改中间件用零拷贝 → 最后才引入 TSN。如果端侧是普通 Linux，再好的网络也做不出 1 kHz 的确定性回路。
