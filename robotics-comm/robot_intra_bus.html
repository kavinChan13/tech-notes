机器人端内总线选型

端内是四类场景里时延要求最严、但最可控的一类：线路短、拓扑固定、没有外部干扰，所有变量都在你手里。这篇把 EtherCAT 为什么能做到 62.5 µs 周期、CAN FD 的最坏时延怎么算、共享内存为什么比任何网络都快、以及一个 20 关节机器人的控制周期预算该怎么排，讲到能直接拿去做选型决策的程度。

01

端内场景的特殊性

先想清楚该不该走网络

端内指一台机器人机身里各模组之间的通信：主控与关节驱动器、力矩传感器、视觉模块、电池管理。它有三个和其他场景截然不同的性质：

  • 拓扑固定且已知。出厂时就确定了有几个关节、几个传感器，运行时不会冒出新节点。这意味着动态发现、动态准入这些机制毫无价值，全部可以静态配置——省掉大量复杂度和不确定性。
  • 物理环境可控。线缆长度已知、没有外部干扰源、供电统一。时延的每一项都能算出来，不需要统计估计。
  • 周期极短。伺服闭环通常 1 kHz ~ 8 kHz（1 ms ~ 125 µs），力控和碰撞检测可能更快。网络往返只能占其中 10%–20%。
端内选型的第一个问题不是「用哪种总线」，而是「能不能不用总线」。如果两个模组能放在同一颗 SoC 上，用共享内存 + 无锁环形缓冲就能做到亚微秒级，比任何网络方案都快好几个数量级，而且没有协议开销、没有丢包、没有时钟同步问题。很多所谓的「确定性通信难题」，本质上是模组划分不合理造成的自找麻烦——把本该在一起的功能拆到了两颗芯片上，然后再花大力气把它们连起来。
这就像公司里两个协作极其频繁的岗位：如果他们坐在同一张桌子旁（同一颗 SoC），转个头就能沟通；如果一个在 3 楼一个在 8 楼（两颗芯片），就得走楼梯、等电梯，还要约时间。与其研究「怎么让电梯更快」，不如先问「他们为什么不坐在一起」。只有当确实必须分开时（物理位置分散、算力隔离、安全隔离），才去优化中间的传输。

端内场景有一个和其他层完全不同的特点：瓶颈几乎总在端侧，不在总线上。保障体系 §3.2 讲过那个典型的错误顺序——先花两个月调 EtherCAT 的 GCL，实测抖动 400 µs，最后才发现主控跑的是普通 Linux、控制线程被内核抢占了。正确的第一步永远是用 cyclictest 测端侧调度抖动，达不到目标就先上 PREEMPT_RT，端侧稳定到 < 20 µs 之后，再看总线这一段够不够。
02

EtherCAT：飞读飞写

工业伺服的事实标准，以及它为什么快

标准以太网连 N 个节点，就要发 N 个帧、经历 N 次存储转发。EtherCAT 的核心创新是让一个帧服务所有节点。

EtherCAT 像一列不停站的火车沿途扔包裹取包裹：火车匀速经过每个小站，站员在火车经过的瞬间把自己的包裹挂上、把给自己的包裹摘下，火车一次都不用停。而标准以太网像快递车逐站停靠：到一站、停车、卸货、装货、再出发，站数越多总时间越长。这个差别在 20 个关节的机器人上就是 62.5 µs 和 1 ms 的差别。

2.1 分布式时钟（DC）

EtherCAT 的分布式时钟（Distributed Clocks）让所有从站的动作在同一时刻发生，精度亚微秒（典型 < 100 ns）。机制：选第一个支持 DC 的从站作为参考时钟，主站测量到各从站的传播延迟（利用帧去程和回程经过每个从站的时间戳差），然后给每个从站下发偏移量。之后从站按同步信号（SYNC0）触发动作，而不是「收到帧就动」。
「收到帧就动」和「按 SYNC0 信号动」的区别，是理解伺服同步精度的关键。帧到达各从站的时刻天然不同（沿链传播有先后，20 个从站的首尾差可达几微秒）。如果每个从站收到帧就立刻执行，各关节的动作就会错开，多轴插补精度下降。DC 的做法是：帧到达后数据先缓存，等到全局同步的 SYNC0 时刻所有从站同时执行。这样通信的先后就与执行的同步性解耦了——和 端间协同的「时间戳执行」是完全一样的思想。

2.2 工程要点

要点说明
主站需独占网口EtherCAT 帧不走 IP 栈，主站直接操作网卡。该网口不能同时跑普通以太网流量
拓扑必须串联线型或环型菊花链。分支需要专门的分支从站（Junction Slave）
环形冗余把链尾接回主站的第二个口，断一处仍可从另一方向到达，切换在一个周期内完成。成本只多一根线，性价比极高
从站需 ESC 芯片飞读飞写必须由硬件完成，软件做不到。选型时要确认驱动器支持 EtherCAT 从站
主站实时性主站必须精确按周期发帧——这又回到端侧实时性问题，需要 PREEMPT_RT + 绝对时刻唤醒
过程数据映射用 PDO 映射把各从站的变量排进一个帧里；映射表在启动时配置，运行时固定
EtherCAT 的「快」有个前提常被忽略：主站必须准时发帧。飞读飞写保证了帧在网络上的传播时间极短且确定，但如果主站因为调度抖动晚发了 200 µs，那么整个周期就晚了 200 µs——总线的确定性被端侧的不确定性抵消了。所以 EtherCAT 项目的成败往往取决于主站侧的实时化做得好不好，而不是总线本身。这和 TSN 需要 etf + SO_TXTIME 是同一个道理。
03

CAN FD：仲裁与最坏时延

带宽小，但最坏时延可以算得很清楚

CAN 的设计目标和以太网完全不同：它优先考虑抗干扰、低成本、线束少、以及可预测的优先级，而不是带宽。这些特性让它在机器人本体的低速控制与状态回报上仍有一席之地。

3.1 无损仲裁：CAN 最精妙的设计

CAN 的仲裁是「无损」的（non-destructive arbitration）。所有节点可以同时开始发送，它们逐位比较自己发出的电平和总线上的实际电平：显性位（0）会覆盖隐性位（1）。某个节点发出 1 却在总线上读到 0，就知道有更高优先级的报文在发，立即退出并转为接收——注意它没有破坏那个高优先级报文，赢的那一方完全不受影响，继续发完。仲裁字段就是报文 ID，ID 数值越小优先级越高。
CAN 的仲裁像一群人同时开口说话，但约定「谁的话里先出现某个特定音节谁就继续说，其他人立刻闭嘴」。关键是闭嘴的人不会打断说话的人——赢家的整句话完好无损地传达了，输家只是白开了个头，下一轮再来。这和以太网的 CSMA/CD「一撞车大家都得重来」相比，没有浪费任何一次成功的传输，这也是 CAN 在高负载下依然稳定的原因。

3.2 最坏时延怎么算

── CAN 报文的最坏响应时间 ───────────────────────
R_i = J_i + w_i + C_i

J_i  该报文的排队抖动（任务侧产生）
C_i  报文自身的传输时间
w_i  排队等待时间，由两部分构成：

  ① 阻塞时间 B_i：一个更低优先级的报文可能刚开始发，
     必须等它发完（仲裁只在帧起始生效，发到一半不能被打断）
     B_i = max{ C_j | j 优先级低于 i }

  ② 更高优先级报文的干扰：在等待期间，
     所有比 i 优先级高的报文都会插队
     Σ ⌈(w + J_j) / T_j⌉ × C_j   （对所有 hp(i) 求和）

→ 这是一个不动点迭代，收敛后即为最坏等待
→ 与实时任务调度里的响应时间分析（RTA）完全同构

── 传输时间 C 的量级 ────────────────────────────
经典 CAN 500 kbps，8 字节数据帧（约 111 bit 含填充）：
  C ≈ 222 µs
CAN FD 500 kbps 仲裁 / 2 Mbps 数据段，64 字节：
  C ≈ 150 µs（数据段提速，但仲裁段仍是 500 kbps）
CAN 的最坏时延是「可以严格算出来」的，这是它相比 Wi-Fi 之类的巨大优势。只要你知道总线上所有报文的 ID（优先级）、周期、长度，就能用上面的迭代算出每条报文的最坏响应时间——和 TSN 用 Network Calculus 算时延界是同一类方法。这也意味着 CAN 的 ID 分配是一个需要认真规划的设计动作，不是随便编号：ID 就是优先级，分错了就会让关键报文被一堆低优先级报文挤在后面。
CAN FD 的一个陷阱：仲裁段速率没变。CAN FD 提升的是数据段的速率（可到 2–8 Mbps），但仲裁段仍然是 500 kbps 或 1 Mbps——因为仲裁需要所有节点在一个位时间内完成信号传播和比较，速率受总线长度物理限制。后果是：小数据量报文的收益有限（开销占比大），只有大载荷（32/64 字节）才能显著受益。所以从 CAN 升级到 CAN FD 时，要顺便把小报文合并成大报文，否则拿不到预期的提升。

3.3 什么时候选 CAN

✅ 适合 CAN FD
· 电池管理、温度、状态回报
· 低速执行器（夹爪、气阀）
· 强电磁干扰环境（差分信号抗扰）
· 线束成本敏感（两根线挂多个节点）
· 需要可算的最坏时延但周期在 ms 级
· 节点物理分散、布线困难
❌ 不适合 CAN FD
· 高频伺服闭环（< 1 ms 周期）
  → 带宽和最坏时延都不够
· 大数据量（视觉、点云）
  → 8 Mbps 上限，且是共享带宽
· 节点数很多且都要高频通信
  → 低优先级报文会被饿死
· 需要亚微秒级多节点同步
  → CAN 没有等价的分布式时钟

片内通道：共享内存与 DMA

最快的通信是不通信

如果两个模块在同一颗 SoC 上，就不该走任何网络协议。共享内存 + 无锁数据结构能做到亚微秒级，比 EtherCAT 快两个数量级。

4.1 无锁环形缓冲的关键点

── 单生产者单消费者（SPSC）无锁环形缓冲 ──────────
// 控制场景最常用的形态：主控写、驱动读，一对一

struct Ring {
    alignas(64) std::atomic<uint32_t> head;   // 写者独占的缓存行
    alignas(64) std::atomic<uint32_t> tail;   // 读者独占的缓存行
    alignas(64) Frame buf[N];                 // N 必须是 2 的幂
};

// 生产者
bool push(Ring& r, const Frame& f) {
    uint32_t h = r.head.load(std::memory_order_relaxed);
    uint32_t t = r.tail.load(std::memory_order_acquire);   // ★ acquire
    if (((h + 1) & (N - 1)) == t) return false;            // 满
    r.buf[h] = f;
    r.head.store((h + 1) & (N - 1), std::memory_order_release);  // ★ release
    return true;
}

★ 三个必须做对的点：
① head 和 tail 要 分处不同缓存行（alignas(64)），
   否则读写双方反复使对方的缓存行失效 —— 伪共享（false sharing），
   性能可能掉一个数量级
② 内存序必须是 acquire/release 而非 relaxed，
   否则在 ARM 这类弱内存模型上数据可能先于索引可见 → 读到半截数据
③ 容量取 2 的幂，用位与代替取模（取模在热路径上是几十个周期）
伪共享（false sharing）是共享内存 IPC 最常见的性能陷阱。CPU 缓存以「缓存行」（通常 64 字节）为单位同步。如果 head 和 tail 挤在同一个缓存行里，那么写者更新 head 会让读者的整个缓存行失效，反之亦然——两个核心不停地互相踢缓存，明明各写各的变量却产生了激烈的竞争。解法就是把它们对齐到不同缓存行（C++17 起可用 std::hardware_destructive_interference_size）。更多细节见 Ring Buffer / Zero Copy / Lock-Free。
ARM 平台上的内存序问题尤其致命，因为它「测不出来」。x86 的内存模型很强，即使写成 relaxed 通常也能正常工作，所以在开发机上测试一切正常；换到 ARM 的机器人主控上，偶发地读到半截数据——现象是「某一帧的关节角度是错的」，频率极低（可能几小时一次），几乎无法复现和定位。这类 bug 必须靠代码审查和正确的内存序来预防，不能靠测试发现。相关背景见 ARM 平台与弱内存模型。

4.2 DMA 的收益与陷阱

方面说明
收益大块数据搬运不占 CPU；外设到内存的传输可以和计算并行
缓存一致性DMA 直接操作物理内存，可能绕过 CPU 缓存。非一致性架构上必须显式 flush（写前）/ invalidate（读后），漏了就读到旧数据
中断合并DMA 完成中断如果被合并（为省 CPU），会引入额外时延且与包速率反相关——正是抖动来源的第 ⑥ 类
描述符准备开销小传输时，准备 DMA 描述符的开销可能超过直接 CPU 拷贝。小于几百字节通常不值得用 DMA
05

板内 TSN 与 PCIe

拓扑灵活性与带宽的选项

板内 TSN（千兆以太网 + Qbv/Qbu）

相比 EtherCAT 的优势是拓扑灵活（星型、树型都可以，不必串联）、带宽大（千兆起）、与外部网络同构（协议栈复用，视觉数据和控制数据可以走同一套基础设施）。代价是需要 TSN 交换芯片、需要 完整的门控配置、且时延（数十到数百 µs）通常不如 EtherCAT 的最优情况。适合模组多、拓扑会随构型变化、且有大数据流（相机/雷达）要一起承载的机器人。

PCIe

带宽极高（Gen3 x4 约 4 GB/s），适合视觉传感器、AI 加速卡这类大数据量设备。时延约 µs 级但抖动受 DMA 引擎、中断合并、以及 PCIe 链路的 ASPM 电源管理影响——追求确定性时要关掉 ASPM 和中断合并。它是板内高带宽的默认选择，但不适合做多节点的周期性控制总线（拓扑是树状点对点，没有广播语义和同步机制）。

SPI

主从同步串行，时延低（µs 级）且因为有独立时钟线所以时序确定。速率通常几十 Mbps。适合短距离、少节点的传感器读取（IMU、编码器、ADC）。缺点是每个从设备需要一根片选线，节点多了引脚不够；且不适合长距离（信号完整性差）。

I²C

两线制、可挂多设备、成本最低。但速率低（标准 100 kHz / 快速 400 kHz）、抗干扰差、且有总线锁死的经典问题（从设备异常时把 SDA 拉低不放，需要靠时钟脉冲或复位恢复）。只适合配置类、低频、非关键的场合——不要用它传控制指令。

10BASE-T1S（单对以太网）

新兴选项：单对双绞线、支持多点接入（PLCA 无冲突仲裁）、10 Mbps。目标是取代 CAN——线束同样简单，但可以直接跑以太网协议栈，与上层网络同构。速率低意味着帧抢占在这里是必需而非可选（一个 1522 B 帧要占 1.23 ms）。生态还在成长，选型时要确认器件可获得性。

板内 TSN vs EtherCAT 的选择，本质是「灵活性 vs 极致时延」。如果机器人构型固定、关节串联、追求最短周期（125 µs 以下）→ EtherCAT；如果模组多样、拓扑会变、还要同时承载视觉大数据、希望和外部网络用同一套技术栈 → 板内 TSN。不要两个都上——维护两套确定性网络的配置和时钟同步，复杂度会翻倍而收益有限。

    是 → PCIe（板内）或 千兆以太网 / 板内 TSN

Q3: 控制周期 < 500 µs 且节点串联？
    是 → EtherCAT（飞读飞写 + 分布式时钟）
    否 ↓

Q4: 拓扑会随构型变化 / 要和外部网络同构？
    是 → 板内 TSN

Q5: 低频、抗干扰优先、线束成本敏感？
    是 → CAN FD（记得规划 ID 优先级并算最坏时延）

Q6: 只是读几个近距离传感器？
    是 → SPI（配置类可用 I²C，但别传控制指令）

7.2 典型的混合架构

层次方案承载
主控内部共享内存 + 无锁队列规划线程 ↔ 控制线程 ↔ 通信线程
主控 ↔ AI 加速卡 / 相机PCIe图像、点云、推理结果
主控 ↔ 关节驱动器EtherCAT（环形冗余）周期性位置/力矩指令与反馈
主控 ↔ 辅助模组CAN FD电池管理、温度、夹爪、指示灯
板上传感器SPIIMU、编码器、ADC
安全回路独立硬件通道（STO / 安全继电器）急停 —— 不走任何软件总线
最后一行是不可妥协的。急停、力矩限制这类安全功能必须走独立的硬件回路（Safe Torque Off、安全继电器、安全 PLC），而不是软件消息。理由很简单：即使主控软件全崩、总线全断，安全链路仍然必须有效。把安全功能建在通信总线上，等于让「通信正常」成为「安全有效」的前提——这在 功能安全的框架下是不可接受的。通信总线可以承载「安全相关的状态上报」，但不能承载「安全动作的唯一触发路径」。
混合架构的隐性成本是「多套时钟」。EtherCAT 有分布式时钟、TSN 有 gPTP、主控有 CLOCK_TAI、相机有自己的帧同步——如果这些时间基准不统一，跨子系统的时间戳就对不上，融合算法会拿到相互矛盾的数据。设计时要明确指定一个「主时间源」，其他所有时钟都对齐到它，并在架构文档里画出时钟分发树。这一点在多传感器融合的机器人上尤其关键。

面试题集（12 道）

按难度分层，先自测再对照

8.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础EtherCAT 为什么能做到 62.5 µs 的控制周期？

    靠「飞读飞写」（processing on the fly）：主站发出一个大帧，这个帧依次穿过所有从站；每个从站在帧经过自己时，直接在硬件（ESC 芯片）里就地读走属于自己的字节、写入要上报的数据，帧不停顿、不重组、不排队。

    于是 N 个从站的通信只需一个帧时，而不是 N 个帧时——这是它能做到 62.5 µs 的根本原因。标准以太网则是逐站「收完整帧 → 解析 → 转发」，总时间正比于节点数。

    代价
    ① 拓扑必须串联（线型/环型），分支需要专门的 Junction Slave；② 从站必须有 ESC 专用芯片（软件做不到）；③ 主站要独占网口（不走 IP 栈）；④ 主站必须精确按周期发帧。
    性价比极高的一个附加项
    环形冗余：把链尾接回主站的第二个口，断一处仍可从另一方向到达，切换在一个周期内完成。成本只多一根线。
  2. 基础EtherCAT 的分布式时钟解决什么问题？为什么不能「收到帧就动」？

    问题：帧到达各从站的时刻天然不同（沿链传播有先后，20 个从站首尾差可达几微秒）。如果每个从站收到帧就立刻执行，各关节动作会错开，多轴插补精度下降。

    分布式时钟（DC）的做法：选第一个支持 DC 的从站作参考时钟；主站利用帧去程和回程经过每个从站的时间戳差测量传播延迟，给每个从站下发偏移量。之后帧到达时数据先缓存，等到全局同步的 SYNC0 时刻所有从站同时执行。精度典型 < 100 ns。

    核心思想
    把「通信的先后」与「执行的同步性」解耦。这和端间协同的「时间戳执行」范式、以及 TSN 的门控是完全一样的思想——用共同的时间基准替代对传输时刻的依赖。
  3. 基础CAN 的仲裁机制是怎样的？为什么说它是「无损」的？

    所有节点可以同时开始发送，逐位比较自己发出的电平与总线实际电平：显性位（0）会覆盖隐性位（1）。某节点发出 1 却读到 0，就知道有更高优先级报文在发，立即退出转为接收。仲裁字段就是报文 ID，ID 越小优先级越高。

    「无损」的含义：退出的节点没有破坏赢家的报文——赢的一方完全不受影响，继续把整帧发完。对比以太网的 CSMA/CD「一撞车大家都重来」，CAN 没有浪费任何一次成功的传输，这是它在高负载下依然稳定的原因。

    设计含义
    ID 分配是需要认真规划的设计动作，不是随便编号——ID 就是优先级，分错了关键报文会被一堆低优先级报文挤在后面。
  4. 基础端内通信选型的第一个问题应该是什么？

    不是「用哪种总线」，而是「能不能不用总线」。

    如果两个模组能放在同一颗 SoC 上，用共享内存 + 无锁环形缓冲就能做到亚微秒级，比 EtherCAT 快两个数量级，而且没有协议开销、没有丢包、没有时钟同步问题。

    分层参考
    同进程 → 函数调用/无锁队列（ns）；同 SoC 不同进程 → 共享内存（< 1 µs）；同板不同芯片 → PCIe/SPI（µs）；同机身高频周期 → EtherCAT / 板内 TSN（数十~数百 µs）；同机身低频抗干扰 → CAN FD（ms）。
    一个常被忽略的洞察
    很多「确定性通信难题」本质上是模组划分不合理造成的自找麻烦——把本该在一起的功能拆到了两颗芯片上，然后再花大力气把它们连起来。与其研究「怎么让电梯更快」，不如先问「他们为什么不坐在一起」。

8.2 中级（区分熟练度）

  1. 中级怎么计算 CAN 报文的最坏响应时间？

    R_i = J_i + w_i + C_i，其中 J_i 是排队抖动、C_i 是自身传输时间、w_i 是排队等待，由两部分构成：

    • 阻塞时间 B_i——一个更低优先级的报文可能刚开始发，必须等它发完（仲裁只在帧起始生效，发到一半不能被打断）。B_i = max{C_j | j 优先级低于 i}。
    • 更高优先级报文的干扰——等待期间所有比 i 优先级高的报文都会插队：Σ ⌈(w + J_j)/T_j⌉ × C_j。

    这是一个不动点迭代，收敛后即为最坏等待。

    它和什么同构
    和实时任务调度里的响应时间分析（RTA）完全同构，也和 TSN 用 Network Calculus 算时延界属于同一类方法——确定性的本质是「能算出可证明的上界」。
    CAN FD 的一个陷阱
    CAN FD 提升的是数据段速率（2–8 Mbps），仲裁段仍是 500 kbps/1 Mbps（仲裁需要所有节点在一个位时间内完成传播和比较，受总线长度物理限制）。所以小报文收益有限，升级时要顺便把小报文合并成大报文（32/64 字节）才能拿到预期提升。
  2. 中级实现无锁环形缓冲时，哪三个点必须做对？
    ① head 和 tail 必须分处不同缓存行
    CPU 缓存以缓存行（通常 64 字节）为单位同步。若 head 和 tail 挤在同一缓存行，写者更新 head 会让读者的整个缓存行失效，反之亦然——两个核心不停互相踢缓存，这就是伪共享（false sharing），性能可能掉一个数量级。用 alignas(64) 或 std::hardware_destructive_interference_size。
    ② 内存序必须是 acquire/release 而非 relaxed
    否则在 ARM 这类弱内存模型上，数据可能先于索引可见 → 读到半截数据。
    ③ 容量取 2 的幂
    用位与代替取模——取模在热路径上是几十个周期。
    为什么第 ② 点尤其危险
    x86 的内存模型很强，写成 relaxed 通常也能跑，开发机上测试一切正常；换到 ARM 主控上偶发读到半截数据，现象是「某一帧的关节角度是错的」，频率极低（几小时一次），几乎无法复现和定位。这类 bug 必须靠代码审查和正确的内存序预防，不能靠测试发现。
  3. 中级板内 TSN 和 EtherCAT 怎么选？

    本质是「灵活性 vs 极致时延」的取舍。

    EtherCAT板内 TSN
    典型周期62.5 µs ~ 1 ms< 100 µs ~ 数百 µs
    拓扑必须串联（线型/环型）灵活（星型/树型/网状）
    带宽100 Mbps 量级千兆起
    大数据共载不适合可以（视觉/雷达与控制同网）
    与外部网络异构，需网关同构，协议栈复用
    配置复杂度PDO 映射，相对简单需完整门控/CBS 配置
    判断
    构型固定、关节串联、追求最短周期（< 125 µs）→ EtherCAT；模组多样、拓扑会变、还要承载视觉大数据、希望和外部网络同技术栈 → 板内 TSN。不要两个都上——维护两套确定性网络的配置和时钟同步，复杂度翻倍而收益有限。
  4. 中级什么时候该用 DMA？它有哪些陷阱？

    收益：大块数据搬运不占 CPU；外设到内存的传输可与计算并行。

    四个陷阱：

    缓存一致性
    DMA 直接操作物理内存，可能绕过 CPU 缓存。非一致性架构上必须显式 flush（写前）/ invalidate（读后），漏了就读到旧数据。
    中断合并
    DMA 完成中断若被合并（为省 CPU），引入额外时延且与包速率反相关——包越少越慢。这正是「压力测试没问题、真实流量有问题」这类怪现象的来源。
    小传输不划算
    准备 DMA 描述符的开销可能超过直接 CPU 拷贝。小于几百字节通常不值得用 DMA。
    电源管理
    PCIe 的 ASPM 等省电机制会引入唤醒延迟；追求确定性时要关掉。

8.3 高级（体现深度）

  1. 高级为什么说端内场景的瓶颈通常不在总线上？

    按六段闭环分解（采集 / 序列化 / 上行 / 计算 / 下行 / 执行），总线往返通常只占总预算的 10%–20%。而端侧的调度抖动可以轻易吃掉整个预算：

    端侧 OS调度抖动量级
    裸 RTOSµs 级
    PREEMPT_RT（调好）数十 µs
    普通 Linux数百 µs ~ ms
    典型的错误顺序
    先纠结选 EtherCAT 还是 TSN → 采购昂贵的确定性交换芯片 → 花两个月调配置 → 实测抖动 400 µs，与预期差 100 倍 → 才发现主控跑的是普通 Linux，控制线程被内核抢占了。
    正确顺序
    ① 先用 cyclictest 测端侧调度抖动；② 达不到目标就先上 PREEMPT_RT，配 isolcpus / mlockall / 关频率调节；③ 端侧稳定到 < 20 µs 后，再看总线够不够；④ 不够才引入 EtherCAT/TSN。先解决最大项。
    还有一层
    即使总线本身确定，主站晚发帧 200 µs，整个周期就晚 200 µs——总线的确定性被端侧的不确定性抵消。所以 EtherCAT 项目的成败往往取决于主站侧的实时化，而非总线本身。
  2. 高级给一个 24 轴人形机器人设计端内通信，你会怎么分层？

    典型的混合架构（不会只用一种）：

    层次方案承载
    主控内部共享内存 + 无锁队列规划 ↔ 控制 ↔ 通信线程
    主控 ↔ AI 卡 / 相机PCIe图像、点云、推理结果
    主控 ↔ 关节驱动器EtherCAT（环形冗余）周期性位置/力矩指令与反馈
    主控 ↔ 辅助模组CAN FD电池管理、温度、夹爪、指示灯
    板上传感器SPIIMU、编码器、ADC
    安全回路独立硬件通道（STO）急停 —— 不走任何软件总线
    最后一行不可妥协
    急停、力矩限制必须走独立硬件回路。理由：即使主控软件全崩、总线全断，安全链路仍必须有效。把安全功能建在通信总线上，等于让「通信正常」成为「安全有效」的前提，这在功能安全框架下不可接受。总线可以承载「安全相关的状态上报」，但不能是「安全动作的唯一触发路径」。
    混合架构的隐性成本：多套时钟
    EtherCAT 有 DC、TSN 有 gPTP、主控有 CLOCK_TAI、相机有帧同步——不统一的话跨子系统时间戳对不上，融合算法拿到矛盾数据。必须明确一个「主时间源」，其他全部对齐到它，并在架构文档里画出时钟分发树。
  3. 高级24 个关节用 CAN FD 跑 1 kHz 闭环，可行吗？

    不可行，而且差得很远。算一笔账：

    CAN FD（500 kbps 仲裁 / 2 Mbps 数据段），单帧 64 字节：
  单帧传输时间 C ≈ 150 µs

24 个关节，每周期至少一收一发：
  24 × 2 × 150 µs = 7.2 ms  ≫ 1 ms 周期

    即使把多个关节的数据合并成一帧（假设能压到 8 帧）：8 × 2 × 150 µs = 2.4 ms，仍然放不下。

    更深层的问题
    ① CAN 是共享带宽，节点越多每个分到越少；② 低优先级报文的最坏时延随高优先级流量线性增长——即使平均够用，最坏情况也会超；③ CAN 没有分布式时钟，24 个关节无法做到亚微秒级同步执行，多轴插补精度上不去。
    正确方案
    关节控制走 EtherCAT（24 个从站一个帧搞定，且有 DC 同步）；CAN FD 留给低频辅助模组（电池、温度、夹爪）。这正是混合架构的意义——不同流量特征用不同总线，而不是强行统一。
  4. 高级10BASE-T1S 有什么价值？它会取代 CAN 吗？

    10BASE-T1S（单对以太网）：单对双绞线、支持多点接入（PLCA 提供无冲突仲裁）、10 Mbps。

    相对 CAN 的优势
    ① 线束同样简单（两根线挂多个节点），但速率高一个数量级；② 直接跑以太网协议栈，与上层网络同构——不需要 CAN-以太网网关，诊断工具、协议栈、TSN 机制都能复用；③ PLCA 提供无冲突的确定性仲裁（轮转令牌式），最坏时延可算。
    但速率低带来一个必然要求
    10 Mbps 下一个 1522 字节的帧要占 1.23 ms——帧抢占（802.1Qbu）在这里是必需而非可选，否则一个大帧就吃掉整个控制周期。这一点和千兆链路上「抢占是锦上添花」的情况完全不同。
    会不会取代 CAN
    方向上是的（尤其汽车电子已在推进），但不会很快：CAN 的生态、器件成本、工程师熟悉度、以及数十年的现场验证是巨大的惯性。务实的判断是：新设计可以评估 10BASE-T1S，尤其当你已经在用以太网/TSN 技术栈时（省掉网关和第二套工具链）；存量系统没有强理由不必迁移。选型时要确认器件可获得性和长期供货。
