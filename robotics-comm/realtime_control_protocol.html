实时控制协议设计与标准化

前面几篇讲的是「网络能提供什么保证」，这篇讲「协议本身该怎么设计，才能在保证失效时依然安全」。核心观点：实时控制协议的设计重心不在「高效传输」，而在三件事——让接收方能判断数据是否还新鲜、让双方能就「现在该做什么」达成一致、以及在通信中断时行为可预测。最后讲怎么把一个内部协议推成团队间的标准。

01

和普通协议有什么不同

设计重心的根本差异

如果你熟悉 二进制协议设计里的 TLV、framing、字节序那一套，那是通用协议的基础。实时控制协议在此之上有三个方向性不同的设计取向：

维度普通协议（如 RPC / HTTP）实时控制协议
可靠性确保每条消息都送到，靠重传不重传——旧指令送到反而有害；靠下一周期的新数据自然覆盖
数据有效期没有概念，消息永远有效核心概念——超过几毫秒的指令必须丢弃
消息边界变长，需要 framing尽量定长——解析确定、可零拷贝、无动态分配
失败处理返回错误码给调用方接收方自主降级——发送方可能已经失联了，没人能接收错误码
顺序需要保序只要最新——乱序到达的旧包直接丢，不需要重排
优化目标吞吐、易用性、可扩展最坏时延、可预测性、失效安全
普通协议像寄信：重要的是信一定要送到，晚几天也认。实时控制协议像交通信号灯：它每秒都在广播当前状态，你错过了这一秒的信号不要紧，下一秒还会来；但如果你看到的是十秒前的信号并据此通过路口，那就出事了。所以信号灯系统的设计重点不是「确保每个人都看到每一次变化」，而是「让人能判断自己看到的信号是不是当前的」——灯灭了（失联）比灯显示旧状态安全得多。
「宁可没有数据，不可有过期数据」是实时控制协议的第一原则。这条原则推翻了很多通用协议的设计习惯：不要重传、不要缓存队列、不要保序重排、不要「尽力送达」。因为在控制场景里，一条晚到 300 ms 的关节指令不是「迟到的好消息」，而是「会造成机械冲击的错误命令」。协议要做的是让接收方有能力识别并拒绝这类数据，而不是想方设法把它送到。
02

帧格式设计

每个字段都要有存在的理由

2.1 一个参考帧格式

── 机器人关节控制帧（定长 64 字节）─────────────────
偏移  长度  字段                说明
────  ────  ──────────────────  ──────────────────────────────
 0     2    magic               0x52C7 —— 快速识别与错帧检测
 2     1    version_major       ★ 不兼容变更时递增
 3     1    version_minor       ★ 兼容性新增时递增
 4     1    msg_type            指令 / 反馈 / 心跳 / 配置
 5     1    flags               bit0 紧急停止 bit1 降级中 …
 6     2    payload_len         即使定长也保留，便于演进
 8     4    seq                 ★ 单调递增序号（回绕需处理）
12     8    tx_timestamp_ns     ★★ 发送时刻（CLOCK_TAI）
20     8    exec_timestamp_ns   ★★ 期望执行时刻（时间戳执行）
28     2    src_id              发送方标识
30     2    dst_id              接收方标识（或组播组）
32    24    payload             6 轴 × 4 字节位置指令
56     4    reserved            ★ 预留，必须发 0、收时忽略
60     4    crc32               ★ 覆盖前 60 字节

★ 设计要点：
· 定长 → 解析无分支、可直接内存映射、无动态分配
· 字段按 8/4/2/1 字节从大到小排列 → 天然对齐，无填充空洞
· 显式指定字节序（建议小端，与主流 CPU 一致，省掉转换）
· 预留字段的语义必须写死：发送方必须置 0，接收方必须忽略
「发送方必须置 0，接收方必须忽略」这条规则是协议能演进的前提。如果接收方对预留字段做了校验（比如「不为 0 就报错」），那么未来任何想用这个字段的新版本都会被老版本接收方拒绝，向后兼容彻底失效。反过来，如果接收方忽略未知字段，新版本就可以渐进地启用预留字段而不破坏老设备。这条规则在 IETF 的协议设计里叫「be conservative in what you send, be liberal in what you accept」，在实时协议里同样适用——但注意安全相关字段是例外，那些必须严格校验。

2.2 关键字段的必要性

tx_timestamp_ns —— 不可省略

接收方判断新鲜度的唯一依据。没有它，接收方无法区分「刚发来的指令」和「网络恢复后涌进来的积压旧指令」。必须用与全网同源的时钟（CLOCK_TAI，见 TSN §9.1 的闰秒陷阱），否则比较毫无意义。

seq —— 不可省略

用于丢包检测（统计丢了几个）和乱序识别（收到比已应用序号更旧的直接丢）。时间戳解决「多旧」，序号解决「是不是重复/倒退」——两者不能互相替代。注意回绕：32 位序号在 1 kHz 下约 50 天回绕一次，比较时要用「循环序号比较」而非直接大小比较。

exec_timestamp_ns —— 协同场景必需

「时间戳执行」范式的载体：不说「现在动」，而说「在绝对时刻 T 动」。只要 T 在传输时延之外，网络抖动就完全不影响动作精度——抖动被时间戳吸收了。多机协同时这是保证动作对齐的关键（见 保障体系 §4）。

crc32 —— 不要依赖下层

以太网有 FCS、UDP 有校验和，但它们只覆盖各自的传输段。数据在协议栈内、在网关转换时、在共享内存里都可能被损坏，而下层校验对此无能为力。端到端校验是唯一可靠的——这是「端到端原则」在协议设计里的直接应用。

version_major / minor —— 早加比晚加便宜得多

协议一定会演进。第一版就留版本号，成本是 2 个字节；第二版才想加，成本是所有已部署设备的兼容性处理。major 变更表示不兼容（对端应拒绝并告警），minor 变更表示兼容性新增（老设备忽略新字段即可）。

flags —— 带外状态的通道

用于传递「我正在降级」「我检测到异常」这类与主数据正交的状态。有了它，接收方能知道对端的健康状况，而不必等超时才发现问题。预留足够的位——flags 是最容易不够用的字段。

不要用 JSON、Protobuf 之类的通用序列化做硬实时控制帧。理由不是「慢」（Protobuf 其实很快），而是不确定：变长编码意味着解析时间随内容变化、可能触发动态内存分配、序列化后的大小不固定导致无法做精确的时延预算。定长 POD 结构 + 显式字节序 + 静态断言才是硬实时的正确选择——它还顺带让 DDS 的 Loaned Message 零拷贝成为可能。配置类、非周期的消息用 Protobuf 完全没问题，关键是把「周期控制通道」和「配置管理通道」分开设计。
03

时间戳与新鲜度

协议里最重要的一段逻辑

接收方在使用一条指令前，必须回答两个问题：这条指令有多旧？它是不是比我已经执行过的更新？前者靠时间戳，后者靠序号，两者缺一不可。

── 新鲜度校验（接收侧的核心逻辑）─────────────────

bool accept_command(const Frame& f, uint64_t now_tai_ns) {
    // ① 完整性 —— 先验校验，坏帧直接丢
    if (f.magic != MAGIC)                     return false;
    if (crc32(&f, 60) != f.crc32)             return false;

    // ② 版本 —— major 不同表示不兼容
    if (f.version_major != PROTO_MAJOR)       { report_incompatible(f); return false; }

    // ③ 新鲜度 —— ★ 核心：太旧的指令必须拒绝
    int64_t age = (int64_t)(now_tai_ns - f.tx_timestamp_ns);
    if (age > MAX_AGE_NS)                     { stat_.too_old++;    return false; }
    // ★ 负 age 说明对端时钟超前 —— 是时钟问题而非数据问题，要单独告警
    if (age < -CLOCK_SKEW_TOLERANCE_NS)       { stat_.clock_skew++; return false; }

    // ④ 序号 —— ★ 只接受比已应用的更新的（处理回绕）
    if (!seq_is_newer(f.seq, last_applied_seq_)) { stat_.stale_seq++; return false; }

    // ⑤ 范围校验 —— 越界指令是最危险的一类
    if (!within_limits(f.payload))            { stat_.out_of_range++; return false; }

    last_applied_seq_ = f.seq;
    return true;
}

── 循环序号比较（回绕安全）──────────────────────
// 32 位序号在 1 kHz 下约 50 天回绕；不能用 a > b 直接比
static inline bool seq_is_newer(uint32_t a, uint32_t b) {
    return (int32_t)(a - b) > 0;   // 有符号差值判定，半个序号空间内正确
}
负 age（对端时钟超前）必须单独统计和告警，不能和「太旧」混为一谈。正常情况下 now > tx_timestamp，age 恒为正。如果出现明显的负值，说明两端时钟不同源或已经失步——这时候所有基于时间戳的判断都不可信了，包括新鲜度校验本身。把它单独报出来，能让你在几秒内定位到时钟问题；如果混在「太旧」的计数里，你会误以为是网络丢包，排查方向完全跑偏。这正是 保障体系 §2.1 里「Q4：两端时钟同源吗」那一步的具体落地。

3.1 阈值怎么定

参数建议值理由
MAX_AGE_NS2–3 个控制周期设成 1 个周期会被正常抖动误触发；设成 10 个周期又失去保护意义
CLOCK_SKEW_TOLERANCE_NS同步精度的 3–5 倍gPTP 下几微秒即可；无精确同步时要放宽到毫秒级（但那样新鲜度校验本身也不可靠了）
序号位宽32 位16 位在 1 kHz 下 65 秒就回绕，太频繁；32 位约 50 天，配合循环比较足够
把所有拒绝原因分开计数，是这段代码最有价值的部分。too_old / clock_skew / stale_seq / out_of_range / CRC 错这五个计数器，直接对应五种完全不同的故障：网络拥塞、时钟失步、乱序或重放、上游算法出错、物理层误码。把它们暴露成监控指标后，「机器人抖了一下」这类模糊报障可以在几分钟内定位到具体环节，而不是花几小时抓包。这个投入产出比在所有可观测性措施里是最高的之一。
04

看门狗与分级降级

通信断了之后的行为，才是协议设计的重点

协议的价值一半在「正常时怎么传」，另一半在「不正常时怎么办」。而后者往往被忽略——很多自研协议把正常路径做得很精致，异常路径只有一句 if (timeout) stop();。

交互：看门狗状态机

模拟连续 24 个控制周期。切换网络状况，观察状态机如何在保持 / 减速 / 停机之间迁移，以及滞回为什么必要。

网络状况
滞回
每格 = 一个控制周期；颜色 = 该周期的链路状态

4.1 四级状态机

── 控制回路的看门狗与分级降级 ──────────────────
typedef enum {
    LINK_HEALTHY,   // 连续收到新鲜指令 → 正常执行
    LINK_DEGRADED,  // 丢 1~3 个周期 → 保持上次指令
    LINK_LOST,      // 丢 4~10 个周期 → 斜坡减速到 30%
    LINK_FAILED,    // 超过 10 个周期 → 受控停止 + 抱闸
} link_state_t;

void on_control_tick(uint64_t now_tai_ns) {
    Frame f;
    bool fresh = try_recv(&f) && accept_command(f, now_tai_ns);

    if (fresh) {
        if (++good_count_ >= RECOVER_THRESHOLD) {   // ★ 滞回：连续 N 次才恢复
            miss_count_ = 0;
            state_ = LINK_HEALTHY;
        }
        apply_with_ramp(f);            // ★ 渐进恢复，不是一步跳回全速
        return;
    }

    good_count_ = 0;
    miss_count_++;
    if      (miss_count_ <= 3)  { state_ = LINK_DEGRADED; hold_last_command(); }
    else if (miss_count_ <= 10) { state_ = LINK_LOST;     ramp_down(0.3f); }
    else                        { state_ = LINK_FAILED;   controlled_stop(); engage_brake(); }

    report_metric("link_state", state_);   // ★ 降级必须可观测
}
三个容易做错的细节，都在实验室发现不了：① 新鲜度阈值不要设成一个周期——正常抖动就会误判，设 2–3 个周期；② 降级必须有滞回（RECOVER_THRESHOLD），否则在临界网络质量下会在 HEALTHY 和 DEGRADED 之间高频振荡，比稳定停在降级态更糟（反复的加速减速对机械是伤害）；③ 恢复要渐进——从 LOST 恢复不能一步跳回全速，要按斜坡加速，否则机械冲击很大。这三条在 demo 里把「滞回」关掉就能直观看到差别。
「宁可停下，不可乱动」是分级降级的设计准则。每一级的动作都要比上一级更保守，且最终状态必须是安全的。特别注意 LINK_DEGRADED 的「保持上次指令」只在很短时间内是安全的——如果上次指令是「以 1 m/s 前进」，保持 3 个周期（3 ms）没问题，保持 3 秒就会撞墙。所以「保持」这一级的时长必须足够短，且要考虑指令的物理含义（位置指令保持是安全的，速度指令保持是危险的——这也是为什么控制协议倾向于传位置而非速度）。
05

失步与重同步

恢复比中断更危险

通信恢复的瞬间是最容易出事的时刻：积压的旧数据涌入、双方对当前状态的理解不一致、控制器以为机器人还在原地而实际已经移动。协议必须显式处理这个过程。

5.1 恢复时的三个陷阱

陷阱现象协议层对策
积压涌入网络恢复后，缓冲区里几十条旧指令一次性到达，机器人做出剧烈动作新鲜度校验自动挡掉（§3）；另外接收缓冲区应该极浅（深度 1–2），而不是「尽量别丢」
状态不一致控制器按中断前的状态继续规划，但机器人已经因降级而减速/停止到别处恢复时先走一次状态同步握手：接收方上报当前实际状态，发送方据此重新规划，确认后才恢复正常指令流
抖动式恢复网络时好时坏，反复 HEALTHY↔DEGRADED，机械反复加减速滞回（§4）+ 最小停留时间（进入降级态后至少停留 N 个周期才允许恢复）
「接收缓冲区应该极浅」是个反直觉但正确的设计。通用网络编程的习惯是把缓冲区开大一点「免得丢包」，但在实时控制里，缓冲区里的每一帧都是一颗定时炸弹——它们会在恢复瞬间一起涌出来。正确做法是缓冲深度设成 1–2，新数据直接覆盖旧数据（对应 DDS 的 KEEP_LAST(1)）。丢掉旧数据不是损失，而是特性。
06

版本协商与向后兼容

协议一定会改，问题是改的时候疼不疼

机器人系统里，控制器和驱动器几乎不可能同时升级——现场有几十台设备、固件版本参差、升级窗口有限。所以协议必须从第一版就考虑混合版本共存。

6.1 兼容性规则

变更类型版本号老接收方的行为例子
兼容性新增minor +1忽略新字段，正常工作用预留字段加一个新的状态位；增加一种新的 msg_type（老设备忽略未知类型）
语义收紧minor +1，但需评估可能行为不一致把某字段的取值范围缩小——老发送方可能发出新接收方拒绝的值
不兼容变更major +1必须拒绝并告警改字段偏移/含义、改字节序、删除字段、改帧长
「新增字段用预留位、绝不改动已有字段的偏移和含义」是向后兼容的黄金法则。一旦某个字节的含义变了，所有老设备都会按旧含义解读新数据——这比直接报错危险得多，因为它静默地产生错误行为。所以宁可浪费几个预留字节，也不要复用或重排已有字段。如果确实必须做不兼容变更，就递增 major 并让双方显式拒绝——明确的失败远好于静默的错误。

6.2 协商流程

── 连接建立时的版本协商 ────────────────────────
① 双方在 HELLO 报文里宣告：
     supported_major = 2
     supported_minor_max = 5
     supported_minor_min = 0        ← 还能兼容到多老
     capability_bits = 0x00000037   ← 支持哪些可选特性

② 取双方 major 是否一致：
     不一致 → 拒绝连接并明确报错（不要试图"凑合着跑"）

③ minor 取 min(双方的 max)：
     即"按较老的一方的能力工作"

④ capability_bits 按位与：
     只启用双方都支持的可选特性

★ 协商结果要记录到日志和监控：
  "与驱动器 #7 协商为 v2.3，未启用零拷贝（对端不支持）"
  否则现场出现性能差异时无从查起
能力位（capability bits）比版本号更适合表达「可选特性」。版本号是线性的，但特性支持往往不是——设备 A 支持零拷贝但不支持新的诊断接口，设备 B 反过来。用版本号表达这种情况会导致版本号爆炸。能力位让每个特性独立协商，扩展性好得多。但要注意：能力位只用于「可选增强」，核心语义仍由 major 版本保证——不要用能力位来表达「这个设备不支持时间戳」这种基础能力，那属于不兼容。
07

安全层

加密、认证与实时性的矛盾

控制协议的安全需求和 IT 系统不同：机密性通常不是首要的（关节角度泄露危害有限），完整性和真实性才是——攻击者能篡改或伪造指令就能让机器人做出危险动作。

安全目标重要性手段实时代价
完整性 + 真实性最高每帧附 MAC/CMAC（如 AES-CMAC，8–16 字节）低——硬件加速下几微秒
防重放高MAC 覆盖序号和时间戳；接收方拒绝旧序号（§3 已有）几乎为零（复用已有字段）
机密性中/低AES-GCM 等中——数据量小时开销可接受
密钥管理高预置密钥 + 定期轮换；设备身份用证书不在热路径上
对实时控制协议，认证（MAC）的性价比远高于加密。加一个 AES-CMAC 只需要几个微秒（有硬件加速时更少）和 8–16 字节开销，就能阻止篡改和伪造这两类最危险的攻击。而全量加密带来的机密性收益在控制场景通常有限——攻击者知道关节角度并不能造成伤害，但能改写关节角度就可以。所以资源受限时的优先级是：先做认证与防重放，再考虑加密。这和 §3 的新鲜度校验是天然协同的——MAC 覆盖时间戳和序号后，重放攻击自动被新鲜度检查挡住。
安全层绝不能成为安全功能的唯一防线。即使协议做了完善的认证，急停、力矩限制这类安全功能仍必须走独立的硬件回路（STO、安全继电器）——理由和 端内总线 §7.2 一样：即使主控软件全崩、密钥泄露、总线全断，安全链路仍必须有效。软件协议层的安全措施是「防止恶意指令被执行」，硬件安全回路是「保证最后能停下来」，两者不可互相替代。
密钥轮换要设计成不中断的。常见做法是双密钥窗口：新密钥下发后，接收方在一段时间内同时接受新旧两个密钥，等确认所有设备都切换完成再废弃旧密钥。如果做成「到点同时切换」，任何一台设备切换失败就会立刻失联——在生产环境是不可接受的。这和 TSN 配置的事务性下发是同一类问题：分布式系统的配置变更必须能容忍部分节点滞后。

标准化落地流程

从内部协议到团队间标准

协议设计得再好，如果只有你自己的团队用，价值有限。把它推成跨团队（甚至跨公司）的标准，是通信架构师的核心产出之一——这也正是 JD 里「推动协议标准化落地」这项职责的实际含义。

8.1 五个阶段

阶段产出关键动作
① 需求对齐用例清单 + 接口契约草案找齐所有利益方（本体、感知、云平台、供应商）；把各自的需求转成可验收的指标
② 规范撰写协议规范文档（字段定义、状态机、错误码、时序图）用 MUST / SHOULD / MAY 明确约束强度（RFC 2119 风格）；每个字段写清「发送方必须、接收方必须」
③ 参考实现可复用的库 + 一致性测试套件规范和实现一起交付——只有文档没有代码，各团队会实现出五个不同版本
④ 一致性验证测试报告 + 互操作矩阵每个实现都跑同一套测试；两两互操作测试（A 的发送方 × B 的接收方）
⑤ 治理与演进变更流程 + 版本路线图明确谁有权批准变更；建立弃用（deprecation）周期；维护兼容性矩阵
第 ③ 步「规范和实现一起交付」是成败关键。纯文档的标准会被各团队理解成不同的样子——尤其是边界情况（序号回绕怎么处理？收到未知 msg_type 怎么办？时间戳为负怎么办？）。一份参考实现能把这些歧义固化下来，而且大多数团队会直接用它，天然保证了一致性。配套的一致性测试套件更重要：它让「符合标准」变成可验证的，而不是靠人读文档打钩。

「不适用场景」和「设计决策记录」是最容易省略也最有价值的两节。前者防止协议被误用（有人拿这个硬实时协议去传固件镜像），后者让半年后的争论有据可依——「为什么用小端？」「为什么序号是 32 位不是 64 位？」这和架构文档里的 ADR 是同一个道理：记录结论容易，记录推理才是真正的资产。

面试题集（12 道）

按难度分层，先自测再对照

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础实时控制协议和普通 RPC 协议在设计取向上有什么根本不同？
    维度普通协议实时控制协议
    可靠性确保每条都送到，靠重传不重传——旧指令送到反而有害
    数据有效期没有概念核心概念——超时的必须丢弃
    消息边界变长，需 framing尽量定长——解析确定、可零拷贝
    失败处理返回错误码给调用方接收方自主降级——发送方可能已失联
    顺序需要保序只要最新，旧包直接丢
    第一原则
    「宁可没有数据，不可有过期数据」。一条晚到 300 ms 的关节指令不是「迟到的好消息」，而是会造成机械冲击的错误命令。协议要做的是让接收方有能力识别并拒绝它，而不是想方设法把它送到。
  2. 基础控制帧里哪些字段是不能省的？为什么？
    • tx_timestamp_ns——接收方判断新鲜度的唯一依据。没有它就无法区分「刚发来的」和「网络恢复后涌进来的积压旧指令」。必须用与全网同源的时钟（CLOCK_TAI）。
    • seq——用于丢包检测和乱序识别。时间戳解决「多旧」，序号解决「是不是重复/倒退」，两者不能互相替代。
    • crc32——不要依赖下层校验。以太网 FCS、UDP 校验和只覆盖各自传输段；数据在协议栈内、网关转换时、共享内存里都可能损坏。端到端校验是唯一可靠的。
    • version_major/minor——第一版就留，成本 2 字节；第二版才想加，成本是所有已部署设备的兼容处理。
    协同场景还要加 exec_timestamp_ns
    「时间戳执行」范式的载体：不说「现在动」而说「在绝对时刻 T 动」。只要 T 在传输时延之外，网络抖动完全不影响动作精度。
  3. 基础为什么不建议用 JSON / Protobuf 做硬实时控制帧？

    理由不是「慢」（Protobuf 其实很快），而是不确定：

    • 变长编码 → 解析时间随内容变化，无法给出确定的处理时延
    • 可能触发动态内存分配——在实时线程里是大忌（见 PREEMPT_RT 的内存预分配要求）
    • 序列化后大小不固定 → 无法做精确的时延预算

    正确选择：定长 POD 结构 + 显式字节序 + 静态断言。它还顺带让 DDS 的 Loaned Message 零拷贝成为可能（那要求消息类型是 plain/fixed size）。

    但不是全盘否定
    配置类、非周期的消息用 Protobuf 完全没问题。关键是把「周期控制通道」和「配置管理通道」分开设计，各用各的合适技术。
  4. 基础什么是新鲜度校验？阈值该怎么定？

    接收方在使用指令前计算 age = now_tai_ns − tx_timestamp_ns，超过阈值就拒绝并计数，而不是执行。

    参数建议值理由
    MAX_AGE_NS2–3 个控制周期设成 1 个周期会被正常抖动误触发；设成 10 个又失去保护意义
    时钟偏差容忍同步精度的 3–5 倍gPTP 下几微秒即可
    序号位宽32 位16 位在 1 kHz 下 65 秒就回绕；32 位约 50 天
    序号比较要处理回绕
    不能用 a > b 直接比。正确写法：(int32_t)(a - b) > 0——有符号差值判定，在半个序号空间内正确。

9.2 中级（区分熟练度）

  1. 中级为什么「负 age」要单独告警，不能算作「太旧」？

    正常情况下 now > tx_timestamp，age 恒为正。明显的负值说明两端时钟不同源或已失步。

    为什么必须区分
    时钟失步时所有基于时间戳的判断都不可信了，包括新鲜度校验本身。如果把负 age 混进「太旧」的计数里，你会误以为是网络丢包，排查方向完全跑偏——去查网络、抓包、调 QoS，而根因在时钟。
    更普遍的做法：把拒绝原因分开计数
    too_old / clock_skew / stale_seq / out_of_range / CRC 错这五个计数器直接对应五种完全不同的故障：网络拥塞、时钟失步、乱序或重放、上游算法出错、物理层误码。暴露成监控指标后，「机器人抖了一下」这类模糊报障能在几分钟内定位到具体环节，而不是花几小时抓包。这是所有可观测性措施里投入产出比最高的之一。
  2. 中级看门狗分级降级怎么设计？哪三个细节最容易做错？

    四级状态机（按连续缺失周期数）：

    • HEALTHY——正常执行
    • DEGRADED（丢 1–3 个周期）——保持上次指令
    • LOST（丢 4–10 个）——斜坡减速到 30%
    • FAILED（> 10 个）——受控停止 + 抱闸
    三个易错细节（实验室发现不了）
    ① 新鲜度阈值不要设成一个周期——正常抖动就误判；② 降级必须有滞回，否则临界网络质量下在 HEALTHY/DEGRADED 间高频振荡，反复的加速减速对机械是伤害，比稳定停在降级态更糟；③ 恢复要渐进——不能一步跳回全速，要按斜坡加速。
    「保持上次指令」有个前提
    它只在很短时间内安全。如果上次指令是「以 1 m/s 前进」，保持 3 ms 没问题，保持 3 秒会撞墙。所以「保持」这一级时长必须足够短，而且要考虑指令的物理含义——位置指令保持是安全的，速度指令保持是危险的。这也是为什么控制协议倾向于传位置而非速度。
  3. 中级通信恢复时有哪些陷阱？为什么说「恢复比中断更危险」？

    中断时系统会进入已设计好的降级态，行为可预测；恢复瞬间则是多种不一致同时爆发的时刻。

    陷阱一：积压涌入
    缓冲区里几十条旧指令一次性到达，机器人做出剧烈动作。对策：新鲜度校验自动挡掉；更重要的是接收缓冲区要极浅（深度 1–2），新数据直接覆盖旧数据。
    陷阱二：状态不一致
    控制器按中断前的状态继续规划，但机器人已因降级减速/停到别处——位置跳变导致剧烈冲击。对策：恢复时先走状态同步握手（RESYNC_REQ → STATE_REPORT → 重新规划 → RESUME → 斜坡加速）。
    陷阱三：抖动式恢复
    网络时好时坏，反复迁移状态，机械反复加减速。对策：滞回 + 最小停留时间。
    一个反直觉的设计
    通用网络编程习惯把缓冲区开大「免得丢包」，但实时控制里缓冲区里的每一帧都是定时炸弹。丢掉旧数据不是损失，而是特性——对应 DDS 的 KEEP_LAST(1)。
  4. 中级协议怎么设计才能向后兼容？黄金法则是什么？

    黄金法则：新增字段用预留位，绝不改动已有字段的偏移和含义。

    因为一旦某字节含义变了，老设备会按旧含义解读新数据——这比直接报错危险得多，它静默地产生错误行为。宁可浪费几个预留字节。

    变更类型版本号老接收方
    兼容性新增minor +1忽略新字段，正常工作
    不兼容变更major +1必须拒绝并告警
    配套规则：发送方必须置 0，接收方必须忽略
    如果接收方对预留字段做校验（「不为 0 就报错」），未来任何启用该字段的新版本都会被老设备拒绝，向后兼容彻底失效。但安全相关字段是例外，那些必须严格校验。
    能力位比版本号更适合表达可选特性
    版本号是线性的，但特性支持往往不是（设备 A 支持零拷贝不支持新诊断，设备 B 反过来）。能力位让每个特性独立协商。但能力位只用于「可选增强」，核心语义仍由 major 保证。

9.3 高级（体现深度）

  1. 高级控制协议的安全层该怎么设计？为什么认证优先于加密？

    控制协议的安全需求和 IT 系统不同：机密性通常不是首要的（关节角度泄露危害有限），完整性和真实性才是——攻击者能篡改或伪造指令就能让机器人做出危险动作。

    目标重要性手段实时代价
    完整性+真实性最高每帧附 AES-CMAC（8–16 字节）低，硬件加速下几微秒
    防重放高MAC 覆盖序号和时间戳几乎为零（复用已有字段）
    机密性中/低AES-GCM中
    为什么认证优先
    几微秒 + 8–16 字节就能阻止篡改和伪造这两类最危险的攻击。而攻击者知道关节角度不能造成伤害，能改写关节角度就可以。且 MAC 覆盖时间戳和序号后，重放攻击自动被新鲜度检查挡住——两个机制天然协同。
    但安全层绝不能是唯一防线
    急停、力矩限制仍必须走独立硬件回路（STO、安全继电器）。即使密钥泄露、软件全崩、总线全断，安全链路必须有效。软件安全是「防止恶意指令被执行」，硬件安全回路是「保证最后能停下来」，不可互相替代。
    密钥轮换要不中断
    用双密钥窗口：新密钥下发后接收方一段时间内同时接受新旧两个，确认所有设备切换完成再废弃旧的。做成「到点同时切换」的话，任何一台切换失败就立刻失联。这和 TSN 配置的事务性下发是同一类问题。
  2. 高级怎么把一个内部协议推成跨团队标准？

    五个阶段：

    1. 需求对齐——找齐所有利益方（本体、感知、云平台、供应商），把各自需求转成可验收指标，产出接口契约草案。
    2. 规范撰写——用 MUST/SHOULD/MAY 明确约束强度；每个字段写清「发送方必须、接收方必须」。
    3. 参考实现——规范和实现一起交付，外加一致性测试套件。
    4. 一致性验证——每个实现跑同一套测试；做两两互操作测试（A 的发送方 × B 的接收方）。
    5. 治理与演进——明确谁有权批准变更；建立弃用周期；维护兼容性矩阵。
    第 ③ 步是成败关键
    纯文档的标准会被各团队理解成不同的样子，尤其是边界情况（序号回绕？未知 msg_type？时间戳为负？）。参考实现把这些歧义固化下来，而且多数团队会直接用它，天然保证一致性。一致性测试套件让「符合标准」变成可验证的，而不是靠人读文档打钩。
    最大阻力是沉没成本，不是技术
    各团队通常已有自己的一套。推进策略：① 先在新项目上用，积累案例再推存量；② 提供适配层而非要求重写；③ 用参考实现降低采用成本——用你的库比维护自己的更省事，采纳就是自然的；④ 把一致性测试做成 CI 门禁。技术标准的推行本质是产品问题。
  3. 高级协议规范文档里哪两节最容易省略、又最有价值？
    「不适用场景」
    明确写出这个协议不该用在哪。防止误用——比如有人拿硬实时控制协议去传固件镜像，或者拿它做非周期的请求响应。边界写清楚了，评审和答疑的成本会大幅下降。
    「设计决策记录」
    记录为什么这么定：为什么用小端？为什么序号是 32 位不是 64 位？为什么阈值是 3 个周期？没有它，半年后这些问题会被反复讨论甚至反复推翻。这和架构文档里的 ADR 是同一个道理——记录结论容易，记录推理才是真正的资产。
    还有一节也常被低估：「对下层的要求」
    协议不是凭空运行的，它对承载有假设：最大时延多少、MTU 多大、是否需要保序、是否允许重复。把这些假设显式写出来，才能在换承载（从 EtherCAT 换到 UDP over TSN）时快速判断是否可行。不写的话，这些假设会隐藏在实现里，换承载时就会踩坑。
  4. 高级从零设计一个机器人实时控制协议，你的设计清单是什么？

    先确认三个前提，它们决定后面所有选择：控制周期是多少？承载是什么（有线 TSN / EtherCAT / 无线）？是否需要多机时间对齐？

    然后按这个清单走：

    1. 帧格式——定长 POD；字段按 8/4/2/1 从大到小排列（天然对齐）；显式字节序；预留字段并写死「发送置 0、接收忽略」。
    2. 必备字段——magic、version_major/minor、seq（32 位）、tx_timestamp（CLOCK_TAI）、crc32；协同场景加 exec_timestamp；flags 留够位。
    3. 新鲜度校验——完整性 → 版本 → age（含负 age 单独告警）→ 序号（循环比较）→ 范围校验；每类拒绝分开计数。
    4. 看门狗——四级状态机，带滞回和渐进恢复；接收缓冲深度 1–2。
    5. 失步恢复——RESYNC 握手对齐双方状态，再恢复指令流。
    6. 版本演进——协商流程 + 能力位；协商结果记入日志和监控。
    7. 安全——AES-CMAC 覆盖含时间戳与序号的全帧；双密钥窗口轮换；安全功能另走硬件回路。
    8. 可观测性——所有计数器暴露为指标；状态机迁移打点。
    9. 规范与参考实现一起交付，配一致性测试套件。
    最后一条自检
    问自己：「如果对端从此不再发任何数据，我这边会发生什么？」如果答不出一个确定的、安全的行为序列，说明协议的异常路径设计还不完整——而异常路径才是实时控制协议真正的价值所在。
