01

四层参考架构

先定分层原则，再谈技术选型

架构设计的第一个决定不是「用什么技术」，而是「哪些功能放在哪一层」。这个决定一旦错了，后面所有技术选型都在为它擦屁股。

分层的唯一判据：这个控制回路断开 T 时间会有什么后果？后果越严重、T 越小，就必须放在越靠近本体的层。这条判据比「算力在哪」「数据在哪」都优先——因为算力可以搬，通信物理时延搬不动。具体地：断开 100 ms 会造成机械损坏或人身危险 → 必须在端内闭环；断开 1 s 会造成任务失败但不危险 → 可以放边缘；断开 10 s 只影响效率 → 可以放云端。

1.1 分层的三条硬规则

  • 安全回路不跨层。急停、力矩限制、碰撞检测这些必须在 L1 内闭环，而且最好是硬件回路（STO，Safe Torque Off）而非软件回路——即使主控软件全崩，安全链路仍然有效。这是 功能安全的基本要求。
  • 每一层都要能在上层失联时独立工作。L1 失去 L2 时按最后的轨迹安全停止；L2 失去 L3 时按本地规划继续；L3 失去 L4 时按缓存的任务列表继续。任何一层的存活不依赖上层在线。
  • 数据向上聚合，指令向下细化。L1 上报的是原始高频数据（本地过滤后），L4 下发的是粗粒度目标（去哪里、做什么），中间层负责翻译。不要让 L4 直接下发关节角度——那是把 L1 的职责推到了 L4。
四层架构像公司的管理层级：车间工人（L1）处理毫秒级的具体动作，班组长（L2）协调几个人配合，车间主任（L3）安排今天的生产计划，总部（L4）决定这个月生产什么。总部断联一个月，车间照样能按上个月的计划生产——这才是健康的组织。反过来，如果总部一断联工人就不知道该干什么，那是把决策全推到了最上层，任何通信中断都会瘫痪整个系统。
最常见的架构错误：为了「统一管理」把决策上移。「让云端统一调度所有机器人的动作」听起来先进，实际上要求端云链路具备确定性——而跨运营商网络物理上给不了（原因见 DetNet §8）。正确方向是智能下沉：云端只做全局优化和参数下发，本体保留完整的自主运行能力。评审架构时的第一个问题永远是「云端断联 10 分钟会发生什么」——答案必须是「继续安全工作」。
02

拓扑设计

物理连接方式决定了故障域

2.1 本体内拓扑

拓扑特点故障影响适用
线型 / 菊花链线束最省（EtherCAT 的天然形态）中间断一处，后面全掉关节串联的机械臂；配合 EtherCAT 的环形冗余可缓解
环型线型的两端接起来断一处仍可从另一方向到达（EtherCAT Cable Redundancy）对可用性有要求的机械臂；成本只多一根回环线
星型中心交换机 + 各模组独立连接单个模组断开只影响自己；中心交换机是单点模组较多、需要故障隔离的移动底盘 / 人形机器人
双星（双归属）每个模组连两台交换机任一交换机故障不影响；配合 FRER 做零丢包安全关键系统；成本翻倍
分层树核心交换机 + 若干区域交换机区域故障局部化；但跳数增加影响 gPTP 精度大型机器人；注意 802.1AS 的 7 跳约束
拓扑深度直接受时间同步精度约束。802.1AS 规定 7 跳内累积误差 < 1 µs，所以本体内的交换机层数是硬上限。这条约束经常在「为了省线束做成长链」时被违反——20 个关节串成一条 EtherCAT 链没问题（EtherCAT 有自己的分布式时钟机制），但如果是 TSN 交换机串 10 级，同步精度就崩了。设计时先画拓扑图数跳数，再选技术。

2.2 无线覆盖与漫游

移动机器人的拓扑核心问题是切换（handover / roaming）：从一个 AP/基站移动到另一个时的中断时长。

技术未优化的切换中断优化手段优化后
Wi-Fi200 ms ~ 数秒（完整重新认证）802.11r（FT 快速漫游）、802.11k（邻居报告）、802.11v；控制器辅助漫游< 50 ms
Wi-Fi（双网卡）—Make-before-break：一张网卡保持旧连接，另一张先连新 AP接近 0（代价是双份射频与带宽）
5G30 ~ 100 ms（Xn 切换）DAPS（Dual Active Protocol Stack）双活切换、条件切换（CHO）< 10 ms 甚至 0 ms 中断
AP 密度不是「越多越好」。密度过高会导致同频干扰和频繁乒乓切换（机器人在两个 AP 边界反复来回，每次都触发一次切换中断）。规划原则：① 覆盖重叠区控制在 15%–25%，保证有切换余量但不过度；② 相邻 AP 用非重叠信道（2.4 GHz 只有 1/6/11 三个）；③ 调低 AP 发射功率而不是调高——功率越大覆盖越大，但干扰范围也越大且切换点越模糊；④ 设置合理的漫游触发阈值并加入滞回，避免乒乓。
03

频谱资源分配

无线是共享介质，规划不好就是互相踩

有线网络的带宽是独占的——你买了千兆口就有千兆。无线不是：频谱是共享的公共资源，你的吞吐取决于周围有多少人在用同一段频率。所以频谱规划是无线架构里最实质的工作。

频谱像会议室里的说话声：房间（频段）的总"声音容量"是固定的，人越多每个人能说的话越少。2.4 GHz 是那个所有人都挤在里面的大厅（Wi-Fi、蓝牙、微波炉、无线鼠标都在），5/6 GHz 是分了很多小隔间的楼层，而 UWB 是用极低音量但覆盖极宽频率的耳语——它不和别人争音量，靠"铺得极宽"来传信息。

3.1 各频段的工程特性

2.4 GHz（Wi-Fi 2/4，802.11b/g/n）—— 尽量别用

只有 3 个不重叠信道（1/6/11），且与蓝牙、Zigbee、微波炉、无线摄像头共存。穿墙好但干扰严重且不可控。工业环境实测吞吐常常只有标称的 20%。结论：机器人通信不应把关键流量放在 2.4 GHz，最多用于低速遥测或作为最后的兜底链路。

5 GHz（Wi-Fi 5/6，802.11ac/ax）—— 主力频段

信道多（20 MHz 带宽下可用 20+ 个），干扰远小于 2.4 GHz。注意 DFS 频段（5.25–5.35 / 5.47–5.725 GHz）：这些信道要做雷达检测，检测到气象雷达时必须立即腾空信道，会造成秒级中断。关键流量应避开 DFS 信道，只用非 DFS 的那几个（如 36–48、149–165，具体依地区法规）。

6 GHz（Wi-Fi 6E/7，802.11ax/be）—— 干净但穿透差

频谱最宽最干净（无历史设备），支持 320 MHz 带宽和多链路（MLO）。穿透衰减大，需要更密的 AP。国内 6 GHz 的开放程度和功率限制需按当地法规确认，规划前必须查清合规边界——这是频谱工作里最容易忽略的一环。

5G 专网频段 —— 可控性最好

中频 n78（3.5 GHz）/ n79（4.9 GHz） 是国内 5G 专网主力，覆盖与容量平衡。毫米波（n257/n258，26/28 GHz）带宽极大但穿透差、需密集部署，室内工厂场景可用性有限。专网的核心优势是频谱由你独占——不与公众用户争资源，调度策略可定制，这是 Wi-Fi 无法提供的。

UWB（6–8.5 GHz，802.15.4z）—— 定位与授时专用

用 500 MHz 以上的超宽带宽 + 极低功率谱密度，因此不干扰同频段其他系统（在别人看来只是底噪抬高一点）。带宽只有几百 kbps ~ 几 Mbps，不承载数据；价值在厘米级测距（ToF/TDoA/AoA）和纳秒级授时。典型架构是「UWB 管定位授时，Wi-Fi/5G 管数据」。

3.2 分配原则

原则做法为什么
按业务分频段而非混用控制流走 5G 专网或 5 GHz 专用 SSID；视频回传走 6 GHz；遥测兜底走 2.4 GHz不同业务的干扰特性和时延要求差异巨大，混在一个频段等于让它们互相踩
避开 DFS 与已知干扰源做现场频谱扫描（spectrum survey），画出干扰热力图后再定信道纸上规划一定会漏掉现场的变频器、电焊机、既有 Wi-Fi；实测是唯一可靠的输入
降功率而非加功率AP 发射功率调到刚好覆盖目标区域功率越大干扰半径越大，反而降低整体容量；也让切换点更模糊
信道复用要留空间距离同信道 AP 之间隔至少两个 AP 的距离同频复用是容量的来源，但过近会产生共信道干扰（CCI）
预留扩容余量规划时按目标机器人数量的 1.5–2 倍算容量无线容量随用户数下降不是线性的；接近满载时时延会急剧恶化
Wi-Fi 6 的两个特性对机器人特别有价值，值得专门配置。① OFDMA：把一个信道切成多个子载波组（RU），多个设备可以在同一时刻各用一部分，而不是像以前那样轮流占满整个信道。这对「很多机器人各自发小包」的场景是决定性的——它把小包的排队时延大幅降低。② TWT（Target Wake Time）：AP 和设备约定唤醒时刻，各设备在自己的时隙里通信。这本质上是无线版的时间门控，思路和 TSN 的 Qbv 一致——用调度替代竞争，把 CSMA 的随机性去掉。要在无线上追求确定性，TWT 是必须打开的开关。
频谱合规是硬约束，不是可以「先做再说」的事。发射功率、可用频段、DFS 要求、6 GHz 的开放范围都由无线电管理法规规定，各国各地区不同。产品出货前必须做型式认证，而认证结果可能反过来限制你的架构（比如某个频段功率不够，覆盖半径达不到设计值，需要加 AP）。架构文档里必须有「频谱合规」这一节，明确列出使用的频段、功率、依据的法规条款、以及认证状态——这是评审时一定会被问到的。

QoS 端到端映射链

最容易断、断了还不报错的一环

一个控制包从机器人应用出发到边缘服务器，可能要经过五种不同的 QoS 标记体系。每次跨越技术边界都要做一次翻译，任何一处翻译失败，这个包就退化成 Best Effort——而且不会有任何错误提示。

隧道的 pipe 与 uniform 模式是必须搞清的一对概念。uniform 模式在封装时把内层的 DSCP/TC 拷到外层，解封装时再把外层的值写回内层——所以隧道内的优先级对中间设备可见，且中间的重标记会传导回内层。pipe 模式则外层用固定值，内层保持不变——隧道对中间设备呈现统一优先级，内层标记被"保护"起来。选择依据：如果你需要中间的运营商网络按你的优先级调度，用 uniform（但要接受它可能被重写）；如果你只想保证内层标记穿越后完好，用 pipe 并在外层设一个协商好的固定值。不显式配置时的默认行为各厂商不同，这正是它成为隐蔽故障点的原因。
把「标记正确性」做成自动化测试，是这一节最实用的建议。做法：在每个域边界部署一个探测点，周期性发送带已知标记的探测包，接收端校验收到的标记是否符合映射表，不符合就告警。这样标记断链从「上线后偶发的性能问题」变成「配置变更时立刻发现的红灯」。成本很低（几个脚本 + 几个探测点），收益极高——因为这类问题手工排查通常要一两天，而且往往是在生产环境出问题后才被发现。
05

容灾冗余

冗余要放在故障概率最高的地方

冗余的成本是实打实的（多一条链路、多一块网卡、多一台交换机），所以不能均匀撒。正确的方法是先做故障树，把冗余投在概率最高的环节上。

5.1 机器人系统的故障概率排序

环节相对故障率失效机理值不值得做冗余
拖链 / 弯折线缆★★★★★反复弯折导致导体疲劳断裂、屏蔽层破损非常值得。用 FRER 段内保护，或改用高柔性专用线缆 + 定期更换
旋转关节滑环★★★★★接触磨损、氧化、瞬时接触不良非常值得。段内 FRER，或改用无线/光学旋转接头
无线链路★★★★☆干扰、遮挡、切换中断、信道拥塞值得。双频/双网卡 make-before-break，或 5G + Wi-Fi 双路
连接器★★★☆☆振动导致松动、接触电阻增大视场景。优先用带锁扣的工业连接器（M12 等）而非冗余
电源模块★★★☆☆电解电容老化、过温值得。双 PSU + 冗余供电，这是共因失效的关键点
交换机 / 芯片★☆☆☆☆元件失效（MTBF 通常几十万小时）安全关键系统才需要（双星拓扑）；一般场景优先保供电
机柜内固定短链路★☆☆☆☆几乎不失效不值得。给它做冗余基本是浪费
共因失效（Common Cause Failure）分析是冗余设计的核心，而不是「有两条路径」。两条路径如果共用同一台核心交换机、同一个电源模块、同一根线槽、同一个时钟源，那么单个共因故障会让两条路径同时挂掉——冗余失效而你付了双倍成本。检查清单：物理路由是否分离（不同线槽/不同侧）、供电是否分离（不同 PSU / 不同配电回路）、时钟是否分离（双 GM）、软件是否分离（同一个固件 bug 会同时影响两条路径）。这和存储做多副本要跨机架跨可用区完全是同一个道理。

5.2 各层的冗余手段

层手段切换时间代价
L1 端内EtherCAT 环形冗余（Cable Redundancy）一个周期内一根回环线，几乎零成本
L1 端内TSN 双星 + 802.1CB FRER0（无中断）带宽翻倍 + 双份交换机
L1 端内安全回路走独立硬件通道（STO）不适用（始终有效）额外的安全继电器 / 安全 PLC
L2 端间双网卡 make-before-break（Wi-Fi）接近 0双份射频、双份带宽占用

时间同步的冗余最容易被忘，后果却最严重。Grandmaster 掉线时，全网门控会错位——这比根本不用 TSN 更糟，因为 TT 流被关在门外而 BE 流以为自己有带宽。必做三件事：① 部署冗余 GM 并实测 BMCA 切换时间（不要相信文档标称值）；② 端节点持续监控 offsetFromMaster，超阈值时主动降级到不依赖时间的策略（严格优先级）而不是继续假装同步；③ 时钟跳变时不要让 GCL 硬跟随，用平滑调整避免窗口瞬间错乱。这三条应该写进架构文档的「单点故障清单」。
06

降级矩阵

把「出问题怎么办」写成表

容量规划与演进

从 5 台到 200 台会遇到什么

架构的一个核心质量是可扩展性：5 台机器人跑得好的方案，200 台时可能完全崩掉。这一节列出规模增长时会先撞上的墙。

规模先撞上的墙原因对策
~10 台基本没有瓶颈—此阶段的方案不能作为规模化的证据
~30 台ROS2 发现流量SEDP 的 O(N²)；组播风暴合并进程（composition）、Discovery Server 或 rmw_zenoh、静态发现
~50 台无线信道容量共享介质，竞争加剧；AP 关联数上限加 AP + 信道复用、开 OFDMA/TWT、把大数据挪到 6 GHz
~100 台边缘算力与上行带宽推理请求并发数超出 GPU 容量；点云上传打满上行边缘横向扩容 + 负载均衡；本体侧加强过滤（三级过滤策略）
~200 台集中式控制器与配置管理CNC 的规划计算量、配置下发的事务规模、监控数据量分区（按车间/楼层分独立域）+ 分层控制器；监控改为分层聚合
任意规模可观测性数据量每台机器人的指标 × 采样频率 × 台数本地预聚合成直方图再上报；不要上报原始每包数据
「10 台跑通了就能上 200 台」是最危险的规模化假设。无线容量、发现流量、控制器计算量这三项都是超线性增长的，10 台时看不出任何征兆。所以规模化验证必须做压力外推：① 用流量生成器模拟 200 台的通信负载（不需要真有 200 台机器人）；② 用虚拟节点模拟 ROS2 的发现负载（几百个空节点就能压出发现风暴）；③ 按目标规模的 1.5–2 倍做容量规划，因为接近满载时时延会急剧非线性恶化。这三条应该写进架构文档的「容量与扩展性」一节，并给出各项的实测外推曲线。

8.2 ADR：把「为什么这么选」留下来

ADR（Architecture Decision Record）是一页纸记录一个关键决策。半年后有人问「为什么不用 X」时，它能直接回答，避免反复讨论同一个问题。

══ ADR-007：端边通信选用 5G 专网而非 Wi-Fi 6 ═══════

状态:      已接受（2026-08-15）
决策者:    通信架构组 / 本体团队 / IT
相关 ADR:  ADR-003（四层分层原则）· ADR-011（频谱分配）

【背景】
移动机器人需要把视觉推理卸载到边缘节点，往返预算 P99.9 < 20 ms，
覆盖范围 12000 m² 的三跨厂房，目标规模 80 台，存在大量金属货架遮挡。

【备选方案】
A. Wi-Fi 6（5 GHz + 6 GHz 双频，18 个 AP）
B. 5G 专网（n78，独立组网 SA，4 个 gNB + 本地 UPF）
C. Wi-Fi 6 承载数据 + 5G 兜底双路并发

【评估】
                  A Wi-Fi 6      B 5G 专网      C 双路
P99.9 往返         12 ms(实测)    15 ms          11 ms
满载 80 台时       48 ms(恶化严重)  18 ms          19 ms
切换中断           45 ms(802.11r) < 10 ms(DAPS)   ~0
遮挡穿透           差（需加 AP）   好             好
可控性             信道竞争不可控   调度可定制       —
初期成本           低             高（约 4 倍）    最高
运维复杂度         低             高（需专业运维）  最高

【决策】
选择 B（5G 专网）。

【理由】
1. 决定性因素是满载表现：Wi-Fi 在 80 台并发时 P99.9 恶化到 48 ms，
   超出预算 2.4 倍；5G 专网因调度可控，恶化幅度小得多。
2. 遮挡环境下 Wi-Fi 需要显著增加 AP 密度，反而带来同频干扰与乒乓切换。
3. 切换中断对协同任务影响大，DAPS 双活切换优于 802.11r。
4. C 方案的可靠性收益不足以抵消双份成本与运维复杂度；
   冗余需求改由「本地降级模型 + 限速运行」在应用层满足（见降级矩阵）。

【后果与代价】
· 需引入 5G 专网运维能力（培训 或 外部服务）
· 频谱使用需完成合规申请（见 ADR-011）
· 初期投入高，需在预算中单列
· 已接受的风险：单一接入技术，无异构冗余 —— 由应用层降级兜底

【复议条件】   ★ 什么情况下要重新讨论这个决策
· 规模缩减到 30 台以下（此时 Wi-Fi 满载表现可接受）
· Wi-Fi 7 的 MLO 实测能把满载 P99.9 压到 20 ms 以内
· 5G 专网运维成本超出预算 30%
ADR 最有价值的两节是「后果与代价」和「复议条件」，而它们恰恰最常被省略。「后果与代价」强迫你诚实地写下这个决策的负面影响——包括你主动接受的风险，这让评审讨论建立在真实权衡上而不是推销上。「复议条件」则给决策设了一个到期检查点：技术在变、规模在变，一个两年前正确的决策今天可能已经错了。写下「什么情况下该重新讨论」，让架构演进变成有触发条件的动作，而不是靠某个人某天忽然想起来。
ADR 像病历：不只记「开了什么药」，还记「当时什么症状、排除了哪些可能、为什么选这个方案、有什么副作用、什么情况下要复诊」。下一个医生（或半年后的你自己）看到病历就能接上，而不用从头重新检查一遍。没有 ADR 的架构文档只有「结论」没有「推理」，团队换人后就只能靠考古。

面试题集（12 道）

按难度分层，先自测再对照

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础端边云四层架构怎么划分？分层的判据是什么？

    分层的唯一判据：这个控制回路断开 T 时间会有什么后果？后果越严重、T 越小，就必须放在越靠近本体的层。这条判据比「算力在哪」「数据在哪」都优先，因为算力可以搬，通信物理时延搬不动。

    层预算放什么技术
    L1 端内µs 级伺服闭环、力控、碰撞检测、安全回路（STO）EtherCAT / 板内 TSN / 共享内存 + RTOS
    L2 端间ms 级协同搬运、编队、避碰协商、相对定位Wi-Fi 6/7 + TWT、5G sidelink、UWB
    L3 端边5–50 ms视觉推理卸载、SLAM、多机规划5G URLLC 切片 + MEC、DetNet
    L4 端云50–500 ms，无保证全局调度、模型下发、OTA、数字孪生QUIC / gRPC + 本地缓冲
    三条硬规则
    ① 安全回路不跨层，且最好是硬件回路（STO）而非软件；② 每层都能在上层失联时独立工作；③ 数据向上聚合、指令向下细化——不要让 L4 直接下发关节角度。
  2. 基础为什么机器人通信不应该把关键流量放在 2.4 GHz？

    三个原因叠加：

    • 只有 3 个不重叠信道（1/6/11），信道复用空间极小。
    • 与大量异构设备共存：蓝牙、Zigbee、微波炉、无线摄像头、无线鼠标都在这个频段，干扰不可控且无法协商。
    • 工业环境实测吞吐常常只有标称值的 20%。

    正确的频段分配：控制流走 5G 专网或 5 GHz 专用 SSID；视频/点云回传走 6 GHz（Wi-Fi 6E/7，频谱最宽最干净）；2.4 GHz 最多用于低速遥测或最后的兜底链路。

    5 GHz 也有坑：DFS
    5.25–5.35 / 5.47–5.725 GHz 属于 DFS 频段，要做雷达检测，检测到气象雷达时必须立即腾空信道，造成秒级中断。关键流量应避开 DFS 信道，只用非 DFS 的那几个。
  3. 基础QoS 标记要经过哪些体系？为什么容易断链？

    一个控制包可能经过五种标记体系：socket priority → 802.1p PCP（L2）→ DSCP（L3）→ 5QI/QFI（5G 空口）→ WMM/TID（Wi-Fi 空口）。每次跨技术边界都要翻译一次。

    断链的三个高频原因：

    • 运营商网络默认清零 DSCP（防客户滥用高优先级）。
    • VLAN 剥离时丢掉 PCP。
    • 隧道封装没把内层 DSCP 拷到外层——最隐蔽，因为中间设备只看外层。
    为什么难查
    断链不报错——包照样通，只是没有优先级了，静默退化成 Best Effort。症状是「实验室（少跳）正常、现场（多跳）失效」。
    对策
    在每个域边界显式重新标记并维护映射表；逐跳抓包比对；把「标记正确性」做成自动化回归（探测点周期发已知标记的包并校验）。
  4. 基础本体内有哪几种拓扑？各自的故障影响是什么？
    拓扑故障影响适用
    线型 / 菊花链中间断一处，后面全掉关节串联的机械臂（EtherCAT 天然形态），线束最省
    环型断一处可从另一方向到达同上但要可用性；成本只多一根回环线
    星型模组断开只影响自己；中心交换机是单点模组多、需故障隔离的底盘/人形
    双星（双归属）任一交换机故障不影响，配 FRER 可零丢包安全关键系统；成本翻倍
    分层树区域故障局部化；但跳数增加影响 gPTP 精度大型机器人；注意 7 跳约束
    硬约束：拓扑深度受时间同步限制
    802.1AS 规定 7 跳内累积误差 < 1 µs，所以交换机层数有硬上限。这条约束经常在「为省线束做成长链」时被违反。设计时先画拓扑图数跳数，再选技术。

9.2 中级（区分熟练度）

  1. 中级无线覆盖规划里，AP 密度和发射功率该怎么定？

    核心认知：AP 密度不是「越多越好」，功率不是「越大越好」。密度过高导致同频干扰和乒乓切换（机器人在两个 AP 边界反复来回，每次都触发一次切换中断）。

    四条规划原则：

    • 覆盖重叠区控制在 15%–25%——有切换余量但不过度。
    • 相邻 AP 用非重叠信道；同信道 AP 之间隔至少两个 AP 的距离。
    • 降功率而非加功率——功率越大干扰半径越大、切换点越模糊，反而降低整体容量。
    • 设置合理的漫游触发阈值并加滞回，避免乒乓。
    前置动作：现场频谱扫描
    纸上规划一定会漏掉现场的变频器、电焊机、既有 Wi-Fi。必须做 spectrum survey 画出干扰热力图后再定信道——实测是唯一可靠的输入。
    切换中断的量级
    Wi-Fi 未优化 200 ms ~ 数秒；开 802.11r/k/v 后 < 50 ms；双网卡 make-before-break 接近 0（代价双份射频）。5G 的 Xn 切换 30–100 ms，DAPS 双活切换可到 < 10 ms 甚至 0 中断。
  2. 中级冗余应该放在哪里？怎么判断？

    先做故障树，把冗余投在故障概率最高的环节，不能均匀撒（冗余成本是实打实的）。

    机器人系统的故障率排序：

    • ★★★★★ 拖链 / 弯折线缆（导体疲劳断裂）、旋转关节滑环（接触磨损氧化）→ 非常值得做段内 FRER 保护
    • ★★★★☆ 无线链路（干扰/遮挡/切换）→ 值得，双频双网卡或 5G+Wi-Fi 双路
    • ★★★☆☆ 电源模块（电容老化）→ 值得，且是共因失效的关键点
    • ★☆☆☆☆ 机柜内固定短链路 → 不值得，基本是浪费
    核心是共因失效分析，不是「有两条路径」
    两条路径若共用同一台核心交换机、同一个 PSU、同一根线槽、同一个时钟源，单个共因故障会让两条同时挂掉——冗余失效而你付了双倍成本。检查清单：物理路由分离、供电分离、时钟分离、软件分离（同一个固件 bug 会同时影响两条路径）。
  3. 中级什么是降级矩阵？设计时要注意什么？

    降级矩阵把「出问题怎么办」写成一张表：每一行是一个故障，列出检测方式和各层的行为、以及对外表现。它的价值是把不确定的故障响应变成确定的、可测试的行为，可以直接变成测试用例和状态机代码。

    例（控制指令超时的三级响应）：

    • 3 个周期 → 保持上次指令，无可见影响
    • 10 个周期 → 主动减速（斜坡降到 30%），动作变慢
    • > 10 个周期 → 受控停止 + 抱闸，停机（安全）
    三条设计规则
    ① 每一行都要有明确的检测方式——检测不到的故障，降级逻辑永远不会触发；② 降级要有滞回，否则临界条件下高频振荡比稳定降级更糟；③ 恢复要渐进——不能一步跳回全速，要按斜坡加速，否则机械冲击很大。
    还必须做
    矩阵里每一行都要有对应的自动化测试，定期注入故障验证行为符合预期——否则你只是「相信」它会这样降级，而不是「知道」。
  4. 中级从 10 台扩到 200 台机器人，会依次撞上哪些墙？
    规模先撞上的墙对策
    ~30 台ROS2 发现流量（SEDP 的 O(N²) + 组播风暴）合并进程（composition）、Discovery Server 或 rmw_zenoh、静态发现
    ~50 台无线信道容量（共享介质竞争、AP 关联数上限）加 AP + 信道复用、开 OFDMA/TWT、大数据挪到 6 GHz
    ~100 台边缘算力与上行带宽边缘横向扩容 + 负载均衡；本体侧三级过滤
    ~200 台集中式控制器与配置管理按车间/楼层分区 + 分层控制器；监控分层聚合
    最危险的假设：「10 台跑通了就能上 200 台」
    无线容量、发现流量、控制器计算量这三项都是超线性增长的，10 台时看不出任何征兆。
    规模化验证必须做压力外推
    ① 用流量生成器模拟 200 台的通信负载（不需要真有 200 台）；② 用虚拟节点模拟 ROS2 发现负载（几百个空节点就能压出发现风暴）；③ 按目标规模的 1.5–2 倍规划容量，因为接近满载时时延会急剧非线性恶化。

9.3 高级（体现深度）

  1. 高级隧道的 pipe 和 uniform 模式有什么区别？怎么选？
    uniform 模式
    封装时把内层的 DSCP/TC 拷到外层，解封装时再把外层的值写回内层。所以隧道内的优先级对中间设备可见，且中间的重标记会传导回内层。
    pipe 模式
    外层用固定值，内层保持不变。隧道对中间设备呈现统一优先级，内层标记被「保护」起来不受中间网络影响。
    选择依据
    需要中间的运营商网络按你的优先级调度 → 用 uniform（但要接受它可能被重写）；只想保证内层标记穿越后完好 → 用 pipe 并在外层设一个协商好的固定值。
    为什么它是隐蔽故障点
    不显式配置时的默认行为各厂商不同。你在实验室（不过隧道）测一切正常，上线后过了隧道优先级就丢了，而且不报错。所以架构文档的 QoS 映射表必须显式写明每个隧道用哪种模式。
  2. 高级Wi-Fi 6 的哪些特性对机器人确定性有实质帮助？原理是什么？
    OFDMA
    把一个信道切成多个资源单元（RU），多个设备可以在同一时刻各用一部分，而不是像以前那样轮流占满整个信道。对「很多机器人各自发小包」的场景是决定性的——它大幅降低小包的排队时延，因为不需要等别人把整个信道用完。
    TWT（Target Wake Time）
    AP 与设备约定唤醒时刻，各设备在自己的时隙里通信。本质上是无线版的时间门控——思路和 TSN 的 Qbv 完全一致：用调度替代竞争，把 CSMA 的随机性去掉。要在无线上追求确定性，TWT 是必须打开的开关。
    Wi-Fi 7 再补一项：MLO
    多链路操作（Multi-Link Operation）让设备同时在多个频段上收发。可以做成负载分担（提升吞吐）或冗余双发（一份数据同时走 5 GHz 和 6 GHz，思路等同 FRER），后者对可靠性提升显著。
    但仍有物理上限
    即使全部特性打开，无线的抖动仍是毫秒级（受干扰、竞争、重传影响），比 TSN 差两三个数量级。所以硬实时闭环不应跨无线段——这是架构铁律，不是调优能解决的。
  3. 高级一份合格的通信架构文档要包含什么？哪些章节最容易缺失？

    九个部分：引言 / 需求与约束 / 总体架构 / 详细设计 / 可靠性设计 / 容量与扩展性 / 可观测性与运维 / 验收方案 / 演进路线，附录含接口契约、配置清单、ADR 列表。

    七个最容易缺失但评审必问的：

    • 不在范围内的部分（1.2）——防需求无限扩张（「顺便把工厂 WiFi 也管一下吧」）
    • 通信需求转化表（2.2）——业务话翻译成可验收指标
    • 频谱合规（2.4）——频段、功率、法规依据、认证状态
    • 端到端时延预算分解表（3.3）——每段分多少，含余量
    • 频谱与信道规划 + QoS 映射表（4.2/4.3）
    • 共因失效分析 + 降级矩阵（5.1/5.3）
    • 单点故障清单（5.4）——评审人会直接对着它逐条问「这个坏了怎么办」
    主动写比被问出来好
    「单点故障清单」和「不在范围内的部分」是两个最有价值却最常被省略的章节。写出来体现你已经想过边界和风险；被问出来则显得没准备。
  4. 高级ADR 该怎么写？为什么它比架构图更重要？

    ADR（Architecture Decision Record）一页纸记录一个关键决策，结构是：状态 / 背景 / 备选方案 / 评估 / 决策 / 理由 / 后果与代价 / 复议条件。

    最有价值的两节，也最常被省略
    「后果与代价」强迫你诚实写下负面影响，包括你主动接受的风险——这让评审讨论建立在真实权衡上而不是推销上。「复议条件」给决策设了到期检查点：写下「什么情况下该重新讨论」（比如「规模缩到 30 台以下」「Wi-Fi 7 的 MLO 实测能达标」），让架构演进变成有触发条件的动作，而不是靠某个人忽然想起来。
    为什么比架构图重要
    架构图只表达「结论」——最终选了什么。ADR 表达「推理」——排除了哪些方案、依据什么数据、接受了什么风险。半年后有人问「为什么不用 X」，有 ADR 就能直接回答，没有就只能重新讨论一遍甚至重新做一遍评估。团队换人后，没有 ADR 的架构文档只能靠考古。
    评估要有数据，不能只有形容词
    「Wi-Fi 时延低、5G 可控性好」这种评估等于没写。要写成可比较的数字：「Wi-Fi 满载 80 台时 P99.9 恶化到 48 ms，超预算 2.4 倍；5G 专网 18 ms」。数据来自实测或有依据的估算——这一步是 ADR 里最花时间但最有价值的部分。
