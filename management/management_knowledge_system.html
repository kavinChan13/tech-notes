团队管理 · 人员管理

所有团队问题，先问一句"人对不对"，再谈机制。

1.1.1 招聘 · 把"对的人"招进来

🎯 概念解释

招错一个人的成本 = 3-9 个月薪资 + 团队污染 + 机会成本。5 人小组里有 1 个不合格成员，团队产出可能下降 30%-50% —— 这是它排第一优先级的原因。

📋 怎么做（标准流程）

阶段核心动作关键产出
① 岗位画像定义硬技能 + 软技能 + 文化匹配JD 文档（含3年成长路径）/ 面试官分工表
② 简历筛选三看：经历相关性 / 作品深度 / 稳定性每份简历看 90 秒，标"过/留/扔"
③ 多轮面试技术轮 / 管理轮 / Cross-team 轮 / Bar Raiser每轮独立打分，避免锚定效应
④ 决策与跟进三方共识（HR + Hiring Mgr + Bar Raiser），offer 后跟进入职书面决策记录 / 入职 30 天 check-in

🔥 一条铁律

找"做过类似事的人"，不找"看起来聪明的人"——每个判断点都要落到候选人讲过的具体事例上。

❌ 常见误区 1：JD 写成"全能侠"

"10 年经验、精通 5 种语言、有架构能力、懂业务、能带团队" — 没人匹配，最后只能降标准。

✓ 修正：JD 必须明确 3 个 Must-have + 3 个 Nice-to-have，其他都是干扰项。

❌ 常见误区 2：被"光环效应"绑架

看到大厂背景就高分，小厂背景就低分。结果招进来的"大厂人"水土不服。

✓ 修正：只看 "他做了什么"，不看"他在哪里做的"。

❌ 常见误区 3：只问技术不问软实力

技术轮全 A，进来发现沟通极差 / 不能合作 / 抗压差，3 个月就出问题。

✓ 修正："讲一次你和同事的冲突" 是必问题，从答案看情商和合作意识。
🎤 面试题：讲讲你最近一次招聘经历，怎么招到 / 没招到一个人？
考察意图 你是真的 Owner 过招聘，还是只在协调和约面试。 高分答法（STAR 结构）
  • S / T：缺一个 P7 后端，3 个月内到岗；我是 Hiring Manager
  • A：JD 砍到 3 个 Must-have；4 轮分工明确；最后选了一个非大厂背景但项目深度好的
  • R：入职 6 个月成为团队 Top；同时主动 reject 了一个光鲜但价值观不匹配的候选人 —— 讲一个"拒绝"的故事显著加分
追问预案
  • "为什么 reject 那个人？" → 背调听到"和同事关系紧张"，验证了面试时感到的强势
  • "入职后才发现不合适？" → 30 / 90 天 check-in，试用期内坦诚反馈，不拖到转正

1.1.2 绩效管理 · KPI vs OKR · 怎么打分

🎯 概念解释

本质：绩效管理 ≠ 打分。打分只是闭环里的一个动作，真正起作用的是目标对齐和反馈牵引。

📊 KPI vs OKR 本质区别

维度KPI Key Performance IndicatorOKR Objectives & Key Results
定位考核工具（评定结果）对齐工具（聚焦目标）
方向Top-down 强制下发双向对齐（公司O → 部门O → 团队O）
目标性质必须达成的承诺线（80-100%）挑战性目标（60-70% 完成即优秀）
与奖金挂钩强挂钩不直接挂钩（强挂钩会让人保守）
典型场景销售、客服、运营等结果可量化岗位研发、产品、创新等需要探索的岗位
典型问题员工只做被考核的事，僵化目标设得太软 / 流于形式

📅 完整的绩效管理闭环（季度循环）

阶段动作关键产出 / 注意点
① 目标设定（W1-2）1on1 协商目标，对齐到部门 OKR2-3 个 O，每个 O 配 3-5 个 KR；KR 必须可衡量
② 过程跟踪（每周）1on1 / 站会 / 周报中持续校准发现偏差立即调整，不要等到季度末
③ 自评（最后 1 周）员工先打分 + 写亮点 / 不足避免你的"主观印象"先入为主
④ 校准会（必做）同级 EM 互相校准，避免每个 manager 标准不一见下方校准图
⑤ 反馈面谈（1 小时）正式面谈，告知评分 + 原因 + 改进方向用 SBI 模型（Situation-Behavior-Impact）
⑥ 改进计划（次季）共同制定下季成长计划低绩效进入 PIP，普通成员定 IDP

Radical Candor 坦诚相对 · Kim Scott (former Google/Apple)

定义用关心个人 Care Personally × 直接挑战 Challenge Directly两维切出 4 象限。多数管理者卡在错误象限：反馈要么伤人，要么没有意义。
4 象限
低 Challenge高 Challenge
高 Care毁灭性同情 Ruinous Empathy
"怕伤感情不说真话" — 最常见的陷阱		坦诚相对 Radical Candor
✓ 目标象限
低 Care操控式假装 Manipulative Insincerity
"拍马屁 / 表面 OK 背后捅刀"		令人厌恶的攻击 Obnoxious Aggression

实操原则① 先有信任——没有 Care Personally 垫底，挑战都会被读成攻击；② 当天给，不攒到绩效面谈；③ 具体到行为（SBI），不评判人格；④ 负面反馈只当面给。
实战案例✅ "这个函数 3 处没处理空指针，线上风险会变高。我相信你能做到 0 NPE，一起看这次为什么漏——是时间紧，还是不熟悉规则？"
事实 → 影响 → 信任 → 一起找原因，缺一步就退回"还行吧下次注意"或"你怎么连 X 都不懂"。
🎤 面试题：你团队有一个低绩效员工，已经辅导半年还是不行，怎么办？
两个陷阱 说"再给他机会"立刻丢分（EM 必须敢做难决定）；直接说"开掉"也丢分（暴露你不懂流程，HR 和法务会否决）。 高分答法
  • 先复盘自己：是岗位不匹配，还是我的反馈不够清晰？自省是最高分的动作
  • 走正式 PIP：书面计划 + 30/60/90 里程碑 + 双周 check-in + HR 同步
  • 有进步但不达标 → 考虑内部转岗
  • 确实不合适 → 给体面方案，并对留下的人说明"标准是统一的"
金句

"不开除一个真正不合适的人，是对剩下 9 个人最大的不公平 —— 但开除之前我必须先问自己：是不是我没给够成长机会。"

1.1.3 人才发展 · 1on1 与成长路径

🎯 1on1 机制设计

要素设计建议
频次新员工 / 重要岗位：每周；稳定老员工：双周；规模大可月度（但不能取消）
时长固定 45-60 分钟，不要轻易缩短或取消
地点避开开放工位，找小会议室 / 咖啡区
谁主导话题员工 70% / 你 30% — 不要变成你的"工作分配会"
禁忌临时取消 / 公开场合谈 / 谈完没下文 / 变成"汇报会"

四象限之外还有一个核武器级问题："你最近有没有想离开的瞬间？"它能把离职意图提前两三个月挖出来，但只在信任建立后用——关系还浅时问只会得到"没有啊"，还会让对方从此对 1on1 设防。

GROW 教练模型 · Goal · Reality · Options · Will

定义用 4 个阶段把"模糊抱怨"引到"具体行动"。管理者不是解答者，是提问者 —— 员工自己说出的答案，执行力比你的指令高 3-5 倍。
4 步 + 话术
  1. G："半年后这次对话有效果的话，你希望看到什么？"—— 不接受"想成长"
  2. R："现在和那个理想态最大的差距是什么？"—— 只听事实，不做诊断
  3. O："还有别的方法吗？如果资源不是问题呢？"—— 至少逼出 3 个
  4. W："这周先做的一件事是？我怎么帮你？"—— 落到动作 + 时间 + 求助点
什么时候别用他缺的是信息或授权而不是想法时。那种情况下的教练式追问像在耍他，直接给答案。
实战案例下属抱怨"项目太杂、没时间提升技术"。
❌ "那你周末多看书"——把系统问题推回给个人。
✅ 走一遍 GROW，他自己识别出 2 个低价值项目，主动来找你协商砍掉。问题没变，能动性变了。

🗺️ 成长路径设计（IDP）

当前定位（技术 / 协作 / 业务 / 影响力）→ 目标定位 → 3-5 个核心 gap → 每个 gap 配一个填补动作 → 每月对照。
决定它有没有用的是"填补动作"那一栏：写"多学习"就是废纸，写"下季度 Owner 支付对账模块、我做 reviewer"才是计划。

Situational Leadership II · Hersey & Blanchard

定义成熟度（能力 × 意愿）随任务变化，风格要跟着切。同一个人，做不同事，要用不同风格。
4 种风格 × 4 类员工
员工状态特征你的风格做法
D1 热心新手不会但想做S1 指令式 Directing明确告诉做什么、怎么做、何时检查（多说少听）
D2 幻灭学习者会一点但泄气S2 教练式 Coaching解释为什么、回答问题、鼓励 — 仍主导决策
D3 谨慎贡献者会但不自信S3 支持式 Supporting少给指示、多倾听、协助决策 — 给信心
D4 自驱专家会且想做S4 授权式 Delegating放手、只看结果、避免微管理 — 给空间
最容易判错的一类新晋升的中层：原岗位是 D4，管理这件事上是 D2。按旧印象继续放手，他会在头三个月独自撞完所有墙。
实战案例A 干了 3 年（D4），B 刚从 P5 升上来（D2）。对 A 只看里程碑 demo，对 B 每周 1on1 + 教练式追问。判据不是"这个人几级"，是"这个人在这件事上第几次做"。

1.1.4 人员流动 · 保留与离职管理

🎯 离职信号识别（提前 2-3 个月看出来）

突然变安静、不接重要任务；缺席团建；更新简历 / 与行业 KOL 互动；关键会议不发言也不挑战；1on1 中变浅（只谈具体工作，不谈想法）；工作日下午请假变多。

🛡️ 保留策略 · 5R 模型

R含义具体动作
Reward报酬定期 review 薪酬竞争力，关键人提前调薪
Recognition认可公开表扬、季度奖、归功不归过
Responsibility责任给到核心项目 Owner、放权决策
Relation关系1on1 高质量 / 团队氛围 / 心理安全感
Roadmap路径明确晋升 / 成长 / 转岗的具体路径

面试金句

"等他递辞职信才知道，已经晚了 3 个月。信号刚出现时我会安排一次深度 1on1，不绕弯地问他在不在看机会，再判断是钱、平台还是关系。"

📤 体面离职的管理

挽留不了就把它做干净：按流程办、主导知识交接（文档 / Code Owner / 关键联系人）、做 Exit Interview、保持校友关系。
留下来的人全程在看你怎么对待走的人 —— 这才是体面离职真正的收益方。

02

团队管理 · 运行机制

Agile 本质 · 会议体系 · 任务拆解 · 跨角色协作

机制 ≠ 流程。机制是让事情自动发生的设计，靠人盯着的不是机制，是劳工管理。

Tuckman 团队发展 5 阶段 · Forming-Storming-Norming-Performing-Adjourning

定义团队不是"组建即可用"，而要经历 5 个可预测的阶段。
5 阶段 × 团队状态（管理者在每一阶段该做什么见下图）
阶段特征团队感受你的角色
① Forming 组建期客气、试探、不熟悉"我在哪 / 大家是谁"引导者
② Storming 风暴期冲突、争吵、质疑"凭什么听他的"调解者
③ Norming 规范期建立默契、形成规范"我们的方式是…"顾问
④ Performing 表现期自驱、高产、互信"放手让我们干"授权者
⑤ Adjourning 解散期项目结束 / 重组"下一站去哪"引荐者
实战案例新接手 8 人团队，前 2 个月很顺，第 3 个月小冲突骤增。
❌ "团队怎么变差了？是不是要换人？"
✅ 这就是 Storming，而且迟到的 Storming 更该担心——那说明分歧被压住了。开一次 conflict 复盘、重申共同目标、不站队，2-3 周后进入 Norming。

1.2.1 Scrum / Agile 进阶理解

🎯 Agile 的本质（很多 SM 都答不上）

站会、迭代都只是仪式，本质是 4 个价值观：个体和互动 > 过程和工具；可工作软件 > 详尽文档；客户协作 > 合同谈判；响应变化 > 遵循计划。每条都是"大于"而不是"取代" —— 冲突时你才知道该牺牲哪一个。

🚦 Scrum 5 大事件 · 进阶理解

事件表面目的进阶理解 / 真实价值
Sprint Planning规划本迭代要做什么真实价值：让团队对承诺达成共识。不是 PM 安排任务，是团队一起承诺。如果团队只是被动接受，已经偏了。
Daily Standup同步进度真实价值：识别风险与依赖。核心是"我卡在哪了"，不是"我昨天做了什么"。15 分钟超时立刻打住。
Sprint Review演示成果给 stakeholder真实价值：用真实反馈校准方向。不演示半成品，要演示可工作的产品。
Sprint Retro复盘改进真实价值：让团队自驱进化。没有 action 的复盘是垃圾 — 每次必出 3 个 action 并跟到下次。
Backlog Refinement梳理 backlog真实价值：让"下一个迭代"提前清晰。所有故事入 Sprint 前必须 INVEST（独立 / 可协商 / 有价值 / 可估算 / 小 / 可测）。

❌ Scrum Master 转型最大的坑：把自己定位成"流程警察"

盯着"没按时开站会、故事不符合 INVEST、复盘没出 action" —— 你越守流程，团队越觉得你阻碍他们干活。

✓ 修正：SM 的真正价值是 风险识别 + 效率提升 + 跨角色协同，面试时用这三个词包装 SM 经验。

迭代层面值得盯的四个数见 §2.3.1 的度量体系图。只补一条最容易读反的：承诺达成率长期 100% 不是好消息，说明团队在保守承诺；长期 60% 也未必是团队不行，多半是没扣掉隐性消耗（见 §1.2.3）。

1.2.2 会议体系设计

🎯 设计原则：用最少的会议达成最大的对齐

判据：一个 10 人团队，每周会议时间应 < 工作时间的 15%（约 6 小时）。

📅 健康的会议结构（10 人研发团队）

会议频次时长目的 / 出口
站会每天15 分钟同步昨天/今天/卡点，出口：识别 3 个最大风险
Sprint Planning每 2 周2 小时对本 sprint 形成承诺，出口：可执行的 backlog
Sprint Review每 2 周1 小时演示成果 + 收 stakeholder 反馈
Retrospective每 2 周1 小时出口：3 个 action + Owner + 截止日
1on1每周/双周45 分钟员工成长 + 团队感受 + 反馈
技术评审按需1 小时重大方案决策，出口：决策记录 + Owner
跨团队对齐按需30 分钟非常驻协同，必须有 agenda + 准备材料

✅ 高效会议的 7 个铁律

没有 Agenda 不开；没有决策出口不开（会前先问"开完要定什么"）；不超过 8 人；Decision Maker 必须在场，否则只是讨论；准点开始、准点结束、迟到不重述；纪要 24 小时内发出；每季度审一次。

最后一条有个便宜的判据：把一个会停掉两周，没有人来问，它就不该再开。

1.2.3 任务拆解与分配

🎯 WBS · 任务拆解的科学方法

WBS（Work Breakdown Structure）：从目标自顶向下拆分到"可执行任务"的层级树。

📐 拆解原则

拆到单人 1-3 天的粒度（再大就看不见进度，再小就是管理开销）；子任务之间MECE（不漏不重）；每个任务有明确的 DoD；整体留 20% buffer。

🧮 迭代容量估算（排期争执的唯一解药）

名义容量 = 人数 × 迭代天数
  6 人 × 10 天(两周)                                    = 60 人天

减去从来不写进计划、但一定会发生的：
  - 会议与仪式   站会/评审/复盘/1on1  约 15%           = -9
  - 事故与打断   线上问题/客服升级    约 10%（历史均值）= -6
  - 技术债偿还   20% 法则（见 §2.2.2）                  = -12
  - 请假/在职培训 按实际排班                            = -3

可承诺容量 = 60 - 30 = 30 人天   ← 真正能排需求的只有一半

再乘上估算偏差修正：
  团队历史「承诺达成率」若为 80%，则本迭代只承诺 30 × 0.8 = 24 人天

判据：如果你承诺的人天接近名义容量，不是团队高效，
      是那 30 人天被藏进了加班和延期里。

它的价值不在精度：争"这个需求做不做"永远吵不完，争"这 60 人天里哪 30 天该砍"就有得谈了。
⚠️ 事故那 10% 必须用历史均值 —— "这次应该不会出事"是最常见的乐观估算入口。

👥 分配原则 · 因人而异 · 因事而异

分配场景怎么分
关键路径任务分给最可靠的人，不要给"新人练手"
有挑战的任务分给想晋升的人 — 给机会就是给信任
常规任务轮换给所有人 — 避免知识孤岛
探索性任务分给好奇心强 + 容错能力强的人
"脏活"EM 自己先扛或公平轮换 — 永远别只给一个人

❌ 经典错误：所有重要任务都给一个"靠谱的人"

团队 90% 关键任务给到 Top 1 成员，结果他过劳要离职，其他人无成长机会。

✓ 修正：故意让"靠谱的人"带新人做关键任务，是培养梯队的最快方式。

1.2.4 跨角色协作

🎯 PRD → 联调 → 上线 全链路协同设计

每一段等待都对应一个交接界面，机制就设计在这些界面上：

阶段关键交接机制设计
需求阶段PM ↔ 研发PRD Review 会：研发提前介入，PM 答 5 个 Why；研发出技术可行性反馈

联调阶段研发 ↔ 测试提测 DoD：自测过 / 用例覆盖 / 数据准备到位
上线阶段研发 ↔ 运维 / SRE发布清单：灰度 / 回滚 / 监控 / 告警 / 应急人

🤝 处理"和产品冲突"的 4 步法

① 先认同情绪，再讨论事实——"我理解这个需求很急"比"你这个需求不合理"有效一百倍；② 把"做不了"翻译成数据——"要 5 人天，会让另一个 P0 延两周"。②是分水岭："做不了"是立场，只能靠谁嗓门大；"会挤掉 X"是信息，才谈得下去。给替代方案与共同担责见 §1.3.2。

团队管理 · 冲突与问题处理

冲突分类 · 技术 vs 产品 · 低绩效与 PIP · 需求争抢

面试官最喜欢问冲突题 —— 答案里能看到你的管理底色：怎么思考人、怎么处理利益、怎么承担难决定。

1.3.1 冲突类型识别

🎯 三类冲突 · 处理方式完全不同

类型特征处理方式典型案例
任务冲突 对"怎么做"有不同意见 鼓励、引导讨论 — 这是健康的 方案 A vs 方案 B 之争
关系冲突 对"人"有意见，情绪化 1on1 单独谈 — 解开心结，必要时调岗 "我和他没法合作"
价值观冲突 对"什么是对的"有分歧 断 — 不要妥协 — 价值观不合无法长期合作 诚信问题 / 团队精神缺失

1.3.2 处理"技术 vs 产品"冲突

本质是 "长期价值 vs 短期交付" 的权衡：要快上线 vs 要重构、要加功能 vs 要先还债。

🛠️ 4 步化解法

  1. 明确共同目标，不要变成立场之争
  2. 用数据建模 — 债不还的 3 / 6 / 12 个月分别会发生什么？延迟、故障率、人力消耗都给数字
  3. 给 3 个方案：A 全力做产品（6 个月后债爆炸）/ B 全力还债（迭代停 2 个月）/ C 拆 70:30（推荐）
  4. 共同决策 + 共同担责 — 记入纪要，爆雷时不是"我早就说过"，是"我们一起选的"

1.3.3 处理低绩效成员（深度）

🎯 PIP（Performance Improvement Plan）流程

PIP 不是"为了开人走流程"，而是"给员工一次结构化的最后机会"。

阶段时长动作
① 信号识别2-4 周1on1 中明确反馈 → 看是否能自己调整
② 启动 PIP1 周书面 PIP 计划：3-5 个具体目标 / 时间表 / 评估方式 / 失败后果
③ 改进期30-90 天双周 check-in 评估，明确"达成 / 部分达成 / 未达成"
④ 结果评估1 周三种结果：达成（脱离 PIP） / 部分（延长） / 未达成（启动退出）
⑤ 退出 / 调岗1-4 周HR / 法务 / 工会三方介入，确保程序合规和员工体面

⚖️ EM 的 3 个底线

不情绪化决定（哪怕你不喜欢他，也只看事实）；书面留痕（避免法律风险）；团队透明（不点名，但要让其他人知道"标准是统一的"）。

🗣️ 开场话术范本（这几句的措辞真的会决定谈话走向）

[结论先行 · 30 秒内说完，不要寒暄铺垫]
  "这次绩效我给的是 C。我先把依据讲清楚，然后我们聊接下来怎么办。"
  —— 绕圈子只会让对方一直在猜，猜到一半就开始防御。

[事实 · 只说可核对的事件，不用形容词]
  "Q3 你负责三件事：X 延期 3 周、Y 上线后两次 P2、Z 按期完成。
   X 的排期风险我在 8 月和 9 月的 1on1 里都提过。"
  —— 不能说"你最近状态不太好""大家反馈你沟通有问题"。

[影响 · 说对别人的影响，不评判他这个人]
  "X 延期让下游两个团队等了三周，其中一个团队的 KR 因此没达成。"

[停 · 这里必须闭嘴，等他说完]
  "这和你自己的判断一致吗？有哪些是我不知道的？"
  —— 90% 的谈崩都发生在这一步被跳过。

[出口 · 后果和时间都写明，不留模糊空间]
  "接下来 60 天走一个正式的改进计划，3 条可验证的具体产出，双周 check 一次。
   达成就回到正常轨道；不达成我们会讨论调岗或者退出。"

❌ 致命错误：长期"睁一只眼闭一只眼"

怕冲突，对低绩效装作没看见。结果团队里高绩效成员看在眼里，慢慢心冷 → 高绩效先离职 → 团队烂掉。

✓ 修正："宽以待人"是性格，"敢做难决定"才是管理者的职责。

1.3.4 处理需求冲突 · 多方都要做

🎯 资源永远不够 · 优先级是最重要的管理工具

工具用 RICE（口径见 §3.1.3）。它的作用不是算出正确答案，是把"每个人都说自己最重要"变成一张可以当众争论的表。

被砍的那一方必须看到为什么被砍，这比排序本身重要：看到了，他下次来抢资源会尊重规则；没看到，他下次直接绕过你找老板。

2.1.1 什么是技术决策（不是写代码）

🎯 定义

技术决策 = 结合业务约束、团队能力与长期演进，在多个可行方案中拍板并承担后果。

📚 5 类典型的技术决策

类型例子常见 Trade-off

❌ 工程师视角 vs 决策者视角

工程师视角

🎯 永远在权衡的 8 对经典 Trade-off

权衡典型场景

🛠️ Trade-off 决策的"显式化"技巧

失败的决策多半不是选错，而是没有显式列出代价。给 stakeholder 的永远是"A/B/C 三个方案 + 各自代价"让他挑，同时提前告诉团队这个方案会疼在哪里——半年后真疼起来，那是当初一起选的，不是 surprise。

❌ 经典错误：决策时只讲优点

"我们选了 X，因为它快、稳、好"。一旦它的缺点暴露（必然暴露），就被骂"早说啊"。

✓ 修正："任何方案我都会主动说出 3 个最大代价" — 这是资深 TL 才有的诚实。

2.1.4 推动技术方案落地

🎯 决策 ≠ 落地 · 7 步推进法

预沟通（评审前先 1on1 关键 stakeholder，避免会上突袭）→ 评审会（RFC + 决策与异议留痕）→ 指定唯一 Owner → 任务拆到 ≤ 1 周 → 周节奏同步进度与风险 → 25% / 50% / 75% 三次 demo → 上线两周内复盘。

第一步和第六步最常被省，代价也最大：会上突袭必然收到情绪化反对；没有中途 demo，偏差只会在最后一周暴露，那时只能加班。

2.2.1 拆解复杂系统

🎯 三种主流拆解思路

思路本质适用场景
分层架构按"职责粒度"切（如表现/业务/数据）所有系统起步阶段
分域架构（DDD）按"业务边界"切（限界上下文）复杂业务 / 多团队协作
服务化（微服务）按"独立部署 + 团队 Owner"切规模大 / 团队多 / 高并发

❌ 过度拆分的代价

5 人小团队上来就微服务化：运维成本爆炸、分布式事务、链路追踪，开发效率反而下降 50%。

✓ 修正：先单体跑通业务，再按需拆分。微服务是组织选择不是技术选择。

拆系统的第一问题是组织问题：拆完谁 Owner 哪块、接口怎么定、对接成本多少。Conway's Law —— 系统结构最终会反映组织结构。

C4 Model 架构图标准 · Simon Brown

定义用 4 个 Level 描述架构，每层一个抽象度，解决"人人画得不一样"的混乱。不是 UML，但比 UML 实用。
4 层缩放
  1. L1 System Context：系统在世界中的位置 —— 系统、用户、外部依赖 3 类盒子。给老板看。
  2. L2 Container：内部有哪些可独立部署单元 —— Web / App / DB / MQ。给架构师、新人看。
  3. L3 Component：容器内部的主要组件 —— Controller / Service / Repository。给同团队开发者看。
  4. L4 Code：类图，一般不画，交给 IDE。
画图规则盒子写名字 + 技术栈 + 一句话职责，箭头写动词 + 协议（"Reads from [JDBC/SSL]"）。大多数项目只画 L1 + L2。
实战案例跨部门评审会直接上 L3，老板五秒就走神。分层就是分人群——用错 Level 不是画得不好，是讲给了错的人。

DDD 领域驱动设计 · Eric Evans · Domain-Driven Design

定义当业务复杂度高于技术复杂度时，软件结构应以业务领域为中心而非以技术分层为中心。DDD 不是技术，是建模思想。
5 个核心概念
概念含义
① 限界上下文 Bounded Context同一个词在不同业务里有不同含义。如"订单"在交易系统是创建订单，在物流系统是发货单。每个上下文是一个"独立世界"
② 通用语言 Ubiquitous Language业务+技术使用同一套术语。PM 说"订单"、代码里也叫 Order，不要翻译成 Transaction
③ 聚合根 Aggregate Root一组业务相关对象的入口，外部只能通过聚合根操作内部对象。如 Order 是聚合根，OrderItem 必须通过 Order 操作
④ 领域事件 Domain Event业务上有意义的事情发生（OrderCreated / PaymentReceived）— 跨上下文通信靠事件，不靠直接调用
⑤ 防腐层 Anti-Corruption Layer当对接老系统 / 第三方时，加一层"翻译"，避免对方的模型污染你的领域
分层与依赖方向
适用场景规则多变的复杂业务，以及微服务边界设计（一个限界上下文 ≈ 一个服务）。不适合简单 CRUD——条件不成立时它只剩成本。
实战案例1000 行的 OrderService：建单、算价、扣库存、发起支付、发短信全在里面。
✅ 切出交易 / 库存 / 支付三个限界上下文，建单后发 OrderCreated 事件各自订阅：OrderService 降到 200 行，库存团队不再等交易团队排期。
DDD 一般不是开局就用，是"发现混乱之后"用来重构的。

SOLID 五大原则 · Robert C. Martin (Uncle Bob)

定义5 条 OOP 设计原则，共同目标是让代码"对修改封闭，对扩展开放"。几乎所有设计模式都是它们的应用。
5 个字母
字母原则核心问题
SSingle Responsibility
单一职责		一个类只有一个"被修改的理由"。反例： UserService 既管登录又管发邮件 — 两个 reason to change
OOpen/Closed
开闭原则		对扩展开放，对修改封闭。反例： if-else 加新分支 — 应该用多态/策略模式
LLiskov Substitution
里氏替换		子类必须能替换父类不破坏行为。反例： Square 继承 Rectangle 然后重写 setWidth — 违反 LSP
IInterface Segregation
接口隔离		不要强迫客户端依赖它不用的接口。反例： 一个大 Service 接口有 30 个方法 — 拆成多个小接口
DDependency Inversion
依赖倒置		依赖抽象，不依赖具体。反例： Service 直接 new Repository — 应该注入接口
Code Review 时的五个触发器类超过 200 行 → 查 S；又加一个 if-else 分支 → 查 O；出现 instanceof → 查 L；接口方法超过 5 个 → 查 I；直接 new 一个有副作用的类 → 查 D。这五条不读懂业务也能机械执行，适合当 review 基线。
适用场景核心业务模块的设计与重构；不适用脚本和一次性工具。
典型违反长什么样一个 createOrder() 同时做四件事：硬编码优惠分支（违反 O）、new MySQLOrderRepo()（D）、顺手发邮件（S）、再打一行 println。重构后只剩三行：跑 validators、存库、发一个事件。
判据：这个方法能不能在没有数据库和邮件服务器的机器上跑单测？

2.3.3 Code Review 机制设计

🎯 Code Review 的 3 大价值

质量、知识传播、梯队培养。后两项才是管理者该在意的 —— 只盯质量的话，把 lint 和门禁做好就够了，不需要人。

👥 Reviewer 设计原则

原则说明
至少 2 人1 人 review 容易遗漏，2 人能覆盖
必有一个 Senior至少一个 P6+ 的人参与，确保深度
跨模块轮换不同模块的人互相 review，传播知识
时效约束PR 提交后 24 小时内必有反馈
大 PR 拒绝> 400 行的 PR 直接打回拆分

📋 Review 检查清单（你的"标尺"）

正确性（边界 / 异常 / 并发）· 可读性 · 可测试性（关键路径有没有单测）· 性能（循环 / 查询 / 分配）· 安全（注入 / 敏感数据）· 设计（有没有过度设计）。

💬 反馈艺术

不好的反馈

  • "这段代码很烂" — 零信息量
  • "你应该这样写…" — 命令式
  • 大段教科书 — 让人想关掉页面

好的反馈

  • "X=null 时会 NPE，建议加判空" — 具体 + 建议
  • "用 Map 替代 List 你怎么看？" — 提问式
  • 标出"必须改 / 建议 / 只是讨论" — 分级

分级那一条最省事：不标级别的评论，作者只能全部当成必须改，于是 PR 卡住、双方都烦。

产品思维 · 需求分析

真假需求 · 三层视角 · 优先级模型

3.1.1 如何判断需求真假

🎯 用户说的 ≠ 用户要的

"如果我问用户要什么，他们会说要更快的马。"用户说的是解决方案，你要的是他背后的问题。

🔍 5Why 分析法（找真需求）

问答
"为什么你想要这个功能？"因为现在的流程太慢
"为什么慢？"因为要切到 3 个页面才能完成
"为什么要切 3 个页面？"因为信息分散，要拼凑
"为什么信息分散？"因为 3 个系统没打通
"为什么没打通？"因为是不同时期 3 个团队建的，没整合

结论：真需求不是"加快速度"，是"打通系统 / 一站式视图"。

🧪 验证真需求的 3 个方法

  1. 观察行为 — 看用户实际做什么，不要只听他说什么
  2. 反着问 — "如果这个功能不做你会怎么办？" 答得出来 = 不是核心痛点
  3. 付费意愿测试 — "这个功能你愿意付多少？" 不愿付 = 不是真需求

Design Thinking 设计思维 · IDEO / Stanford d.school

定义5 个阶段的非线性循环（可以来回跳），核心信念是 "先深度理解人，再设计方案"。
5 阶段
阶段关键问题方法
① Empathize 共情用户真的在乎什么？用户访谈 / 影子陪伴 / Empathy Map
② Define 定义核心问题到底是什么？用 POV 句式：[用户] 需要 [需求] 因为 [洞察]
③ Ideate 构思有什么解决方案？头脑风暴 / Crazy 8 / SCAMPER — 先求量再求质
④ Prototype 原型怎么用最低成本试？纸原型 / Mockup / Wizard of Oz
⑤ Test 测试用户怎么反馈？可用性测试 / A/B test / 数据验证
POV 句式（Define 阶段的核心产出）[用户角色] 需要 [具体需求]，因为 [出乎意料的洞察]
例："加班的程序员需要 10 分钟组装健康晚餐，因为他不是没钱点外卖，是想拿回一点'掌控感'。" 这个洞察决定了你做"快手菜 + 仪式感"而不是"外卖优惠 App" —— 写不出让人意外的那半句，说明 Empathize 还没做够。
适用场景0→1 新产品、老产品转型、内部工具改造。不适合成熟产品的已知问题优化——那里数据驱动便宜得多。
实战案例❌ 做"程序员效率工具"，开局列功能清单，做完没人用。
✅ 影子陪伴 8 个程序员各一天，真痛点是打断（每天 23 次）→ POV 指向"缺一个'我在专注'的信号"→ Mockup 给 5 个人看，4 个说明天就想用。

3.1.2 拆解需求（用户 vs 商业 vs 技术）

🎯 一个需求 = 3 层视角

视角问什么问题关注产出
用户视角解决了用户什么问题？提升了什么体验？用户故事 / Persona / 场景
商业视角给公司带来什么收益？提升什么指标？北极星指标 / ROI 测算
技术视角怎么实现？要多少人力？有什么风险？方案设计 / 工作量 / Trade-off

📝 User Story 与 INVEST

作为 [角色]，我希望 [完成某动作]，以便 [达到某价值] 的价值全在第三段。写不出"以便"的需求基本都是伪需求——提的人只想到了功能，没想到用它的场景。

入 Sprint 前用 INVEST 卡一遍：Independent、Negotiable、Valuable、Estimable、Small（≤ 1 个 Sprint）、Testable。
最常挂的是 I 和 E：前者说明它其实是别人的子任务，后者说明需求还没想清楚 —— 两种都该退回，而不是硬拆进迭代。

3.1.3 优先级判断

🎯 4 种主流优先级模型

四个模型解决的是不同的问题，不是四种口味：

  • RICE (Reach × Impact × Confidence) / Effort — 横向比较一堆需求。前提是有数据，否则 Reach 和 Confidence 都是编的。
  • ICE (Impact × Confidence × Ease) / 3 — 数据不足、要当场拍板时用，去掉了最难估的 Reach。
  • MoSCoW — 不排序，做范围切割。价值在 Won't 那一档：写下"这个版本不做"比排出前三名更能止住蔓延。
  • KANO — 不比价值大小，判断这个功能做了会不会被感知。

⚠️ 量化模型的通病：Effort 由研发估、Impact 由需求方估，两边都有动机往有利方向偏。所以分数只用来排出讨论顺序，不用来代替决策。

📊 KANO 模型（用户感受）

类型定义例子
基本需求没有就抱怨，有了无感支付功能稳定
期望需求越好越满意支付速度快
兴奋需求没有不抱怨，有了惊喜支付完跳出小动画 + 优惠券

KANO 的用处是止住在"基本需求"上继续投入——支付稳定性从 99.9% 做到 99.95%，用户感知为零；而一个兴奋需求可能只要三天。

🎤 面试题：现在有 5 个需求都要做，资源只够 2 个，你怎么选？
高分答法
  • 先和每个 stakeholder 聊清价值与紧急度，再用 RICE 拉到同一坐标系
  • 额外加权一项：哪个做了能解锁后续 N 个需求（RICE 本身算不出来）
  • 公开决策：带数据上桌，让所有人看到同一份 trade-off
  • 给被砍的需求一个"下个 Q 重新评估"，不是"永远不做"
陷阱

说"问老板要资源"就是甩锅。这道题考的正是你能不能在资源约束下做决定。

产品思维 · 用户思维

用户价值 · 用户分层 · 行为与漏斗

技术人转产品 / 管理最大的视角切换 — 从"代码能跑"到"用户在用"。

3.2.1 什么是用户价值

🎯 用户价值的 3 个层次

层次用户感受例子
痛点"不解决就难受"支付失败 / 数据丢失
痒点"解决了更舒服"一键登录 / 智能推荐
爽点"用了上瘾"抖音的下滑 / 多巴胺反馈

📐 用户价值公式

用户价值 =（新体验 − 旧体验）− 替换成本

滴滴：新体验 = 不用招手 + 明码标价；旧体验 = 站路边等出租；替换成本 = 下载 App + 绑卡。
技术人最常漏的是第三项。"明显更好"的内部工具推不动，多半是迁移与重学的成本超过了体验增量。

🎯 JTBD · Jobs to Be Done

不问"用户是谁"，问"用户在什么场景下要完成什么 Job"。买电钻的人要的是墙上那个洞 → 把画挂上去 → 一个温馨的家：停在"洞"只能做更好的电钻，追到"挂画"才可能做出免钉挂钩，再往上就超出你能交付的范围。选那个既换得动方案、又还是你能做的层级。

3.2.2 用户分层 · 不要把"用户"当成一类人

🎯 主流分层方法

方法分层维度典型应用
RFMRecency 最近 / Frequency 频次 / Monetary 金额电商精准营销
Persona按典型用户画像分组设计阶段 / 产品策略
漏斗分层按生命周期阶段（新→活跃→留存→流失）增长 / 运营
价值分层核心 / 重要 / 普通 / 边缘资源分配 / 服务策略

👤 Persona 模板

给每个 Persona 一个真名（"小王 · 28 岁产品经理"），填五项：背景、目标、3 个最大障碍、典型场景、一句金句。
判据：Persona 要能在评审会上被用来否掉一个功能，做不到就只是一张好看的卡片。

3.2.3 理解用户行为

🎯 AARRR 海盗指标（增长经典）

阶段含义关注指标
Acquisition获取用户渠道转化率 / CAC
Activation激活（首次价值时刻）注册转化 / 首单转化
Retention留存次日 / 7 日 / 30 日留存率
Revenue变现ARPU / LTV
Referral推荐NPS / 邀请率

🔍 漏斗分析方法

画出关键路径（登录 → 浏览 → 加购 → 下单 → 支付）→ 逐步看转化率找最大漏点 → 归因 → A/B test 验证。
归因最容易被跳过：支付环节掉 30% 可能是设计难用，也可能是某个机型上的接口超时，两者的解法毫无关系。

行为是看出来的，不是问出来的。埋点给行为真相、访谈给动机、竞品给已验证的市场答案 —— 只用一个都会盲人摸象。

HEART Framework · Google · 用户体验度量

定义5 个用户体验度量维度，每个维度用 Goal-Signal-Metric 三层定义指标。比 AARRR 更聚焦体验质量，比 NPS 更系统。
5 个维度
维度含义典型指标
H - Happiness用户的主观满意度NPS / CSAT / 满意度评分 / 应用商店评分
E - Engagement用户的参与深度DAU/MAU / 平均会话时长 / 周活跃天数
A - Adoption新功能 / 新用户的接受率新功能使用率 / 新用户注册转化
R - Retention用户的留存能力次日 / 7 日 / 30 日留存 / 流失率
T - Task Success用户完成任务的能力任务完成率 / 完成时长 / 错误率
Goal-Signal-Metric 三层以 Engagement 为例：Goal "深度使用视频功能" → Signal "每天看 ≥3 个、每个看完 50% 以上" → Metric "深度观看率 / DAU"。
中间那层的作用是不让人直接从目标跳到指标 —— 少了"什么行为算达成"，定出来的往往是最容易取到的数。
适用场景定北极星指标、季度复盘。AARRR 偏增长，HEART 更适合"已经有用户、要把它做好"的阶段。
实战案例年度健康度只报 DAU/MAU/GMV，老板反问"那用户到底喜不喜欢？"五维一起给才答得上。
单维上升不算赢：留存涨而任务成功率跌，往往意味着用户是被迫留下而不是用得顺。

产品思维 · 商业理解

ROI 四象限 · TCO · 技术人的六个盲区

技术人最容易缺的一课 — "做出来"和"赚到钱"是两回事。EM / PM 必须懂"算账"。

3.3.1 ROI 思维

🎯 公式与本质

ROI =（收益 − 成本）/ 成本 × 100%

公式谁都会写，难的是把两项拆到能填数字 —— 大部分技术人卡在下面四个格子里的隐性那一列。

📊 ROI 拆解四象限

显性隐性
收益新增收入 / 节省成本 / 提升 GMV用户体验提升 / 品牌价值 / 战略地位
成本人力 / 硬件 / 服务 / 时间机会成本 / 风险 / 复杂度 / 维护负担

💡 估算 ROI 的四条实战规则

模糊表述都要给一个数（"提升体验" → "次日留存 +2%"）；收益砍一半再看是否还成立（技术人几乎必然乐观）；永远和"不做 / 做另一件事"对比；分 1 个月 / 1 年 / 3 年三档看 —— 战略项目在一个月的尺度上一定是负的。

❌ 技术人常见 ROI 失误

"这个重构能提升性能 30%" — 然后呢？对应多少收入、多少用户、多少成本节省？没算到业务层面就是不完整的 ROI。

✓ 修正：把技术指标翻译成业务语言。性能 +30% → 首屏快 200ms → 转化率 +2% → 月收入 +100w

3.3.2 成本/收益分析

🎯 TCO · 总拥有成本（很多人只算冰山上面的）

成本类型例子
建设成本开发人力 / 设计 / 硬件采购
运维成本云服务 / 监控 / 排障 / 升级
机会成本做这件事 = 不能做另一件事
风险成本失败概率 × 失败损失
认知成本新人上手 / 文档维护 / 知识传递
切换成本后续如果要换方案的代价

⚖️ 短期 vs 长期收益

技术决策的难点常在"短期看不划算，长期看必须做"：测试自动化投 3 人月、之后每月省 5 人月；架构重构短期压慢迭代、长期撑 3x 业务量。能把这组对应关系讲给老板听，是 EM 和高级工程师的分界。

3.3.3 为什么很多技术人不会做产品

🎯 技术人转产品的 4 大盲区

❌ 盲区 1：不懂"砍需求"

需求来一个做一个，最后产品什么都有、什么都不好。

✓ 破：每次新需求先问"砍掉哪个老需求做这个？"

❌ 盲区 2：自己 = 用户

"我觉得这样设计好" — 但你不是目标用户。

✓ 破：用Persona + 真实用户访谈替代你的"感觉"。

❌ 盲区 3：不重视数据

"这个功能上了应该会涨" — 但没数据证明。

✓ 破：所有上线动作都设北极星指标 + A/B test。

❌ 盲区 4：把"竞品分析"做成"功能复制"

"竞品有 X 功能我们也要" — 没想为什么他们要。

✓ 破：竞品分析是理解策略，不是抄功能。

破这几条的动作只有一个，而且很便宜：每周固定一小时做"用户视角"的事——看埋点、看吐槽、试竞品。靠觉悟改不掉，靠日历能。

Lean Startup 精益创业 · Eric Ries · Build-Measure-Learn

定义在浪费时间打造没人要的产品之前，先用最低成本验证假设。用 Build-Measure-Learn 循环迭代，每轮只回答一个具体假设。
核心循环 · 3 步
  1. Build：MVP 不是"丑版完整产品"，是刚刚能验证假设的最小版本
  2. Measure：只认可执行指标（转化率、留存率），不看浮夸的总数
  3. Learn：三选一 —— Persevere 假设成立继续投、Pivot 假设错了转向、Kill 方向不通停掉
MVP 类型清单Landing Page（看多少人留邮箱）、Wizard of Oz（界面像自动、后台是人工）、Concierge（人工服务前 10 个客户）、视频 / PPT（Dropbox 早期一段 demo 换来 3 万个邮箱）。
共同点是都不写业务代码：一旦开始建表、拆服务，就不是 MVP 了。
实战案例"AI 写周报助手"若直接投 3 个月研发，上线没人用。
✅ 一周做个 Slack bot，后台是运营在手写。50 人里只有 10 个用过 3 次以上，但其中 5 个愿意付 30 元/月 —— 两条相反的信号：高频痛点不成立、深度用户付费意愿强 → Pivot 到企业 SaaS。

4.1.1 OKR 深度理解

🎯 OKR 的本质 · 不是 KPI 的变种

它解决三个组织问题：聚焦（3-5 个目标，不要什么都做）、对齐（上级 O = 下级 O 之和）、透明（所有人的 OKR 公开）。

📐 一个好 OKR 的结构

元素特征例子
Objective方向性、定性、激励性"成为行业内最快的支付系统"
Key Result 1可衡量、有挑战P99 延迟从 500ms 降到 100ms
Key Result 2可衡量峰值 QPS 从 5w 提升到 50w
Key Result 3可衡量故障 MTTR 从 2 小时降到 15 分钟

🚦 OKR 落地的 4 个动作

设定（季初，自下而上提案 + 自上而下对齐，公开发布）→ 每周跟进（标 On track / At risk / Off track）→ 季末复盘（评完成度 0-1，不用于绩效打分）→ 据此调整下个 Q。

❌ OKR 失败的判据

只要出现下面任一条，这套 OKR 已经死了：KR 写成"提升用户体验"（无法评估）、季度末才第一次看进度、完成度直接进绩效公式（见 §4.1.2）。

4.1.2 KPI vs OKR 本质区别

🎯 工具选择不是非此即彼

逐项对照见 §1.1.2 的 KPI vs OKR 对比表，这里只补选择判据。

问题不在"用哪个"，而在把两件事塞进同一套机制：OKR 要有挑战性（完成 60-70% 即优秀），绩效要能分档（必须可比可核）。同一份文档既定挑战目标又定考核基线，员工唯一理性的选择就是把目标设低。

做法：OKR 对齐目标与过程、每周 review；绩效单独跑一条线（校准会 + 事实证据），OKR 完成度只作为讨论输入，不进公式。

4.2.1 推动依赖团队

🎯 4 层影响力（递进）

Team Topologies 团队拓扑 · Skelton & Pais (2019)

定义研发组织由 4 种团队类型 + 3 种交互模式组成。它是 Conway's Law 的反向运用：先设计你想要的系统形状，再倒推组织形状。
4 种团队类型
类型职责例子
① Stream-aligned（流对齐团队）端到端 Owner 一个业务流，能独立交付价值。占组织的 70-80%支付团队、商品团队、订单团队
② Platform（平台团队）提供"内部产品"给流对齐团队用，降低他们的认知负担K8s 平台、CI/CD 平台、监控平台
③ Enabling（赋能团队）短期介入帮其他团队补能力，3-6 个月就撤SRE 教练、安全教练、敏捷教练
④ Complicated Subsystem（复杂子系统团队）专门管"对深度专业知识要求极高"的部分实时风控引擎、视频编解码、ML 模型
3 种交互模式
  • Collaboration 协作：两个团队短期深度合作（新产品 0→1）— 短暂、有时限
  • X-as-a-Service 即服务：消费另一个团队的产品（如平台团队的 CI/CD）— 长期、低成本
  • Facilitating 引导：Enabling 团队短期帮别人补能力 — 短暂、教练式
适用场景团队规模 50+、微服务化撞上组织瓶颈、平台战略落地时。
实战案例公司从 30 人扩到 200 人，每个团队都在自己造 CI/CD、监控、容器。给每队"加一个运维"只会让重复造轮子加倍。
✅ 抽 5 人组建平台团队，把这些能力做成有文档、有 SLA 的内部产品，再派 SRE 教练驻队 3 个月。平台团队从此有使命而不是"打杂的运维"——这决定了它招不招得到人。

面试映射 · 高频题型拆解

行为面试 / 项目复盘 / 技术管理 / 产品业务四类题

管理岗面试主要有 4 大题型，考察意图与答题结构各不相同。

🎤 题型 1：行为面试（BEI）

问法："讲一次你…" / "举一个…的例子" / "最有成就感、最失败的一次"。

结构：STAR。

加分点：有数字、有Trade-off（拒绝过什么 / 牺牲了什么）、有反思、有沉淀（机制化 / 团队成长）。

失分点：全程用"我们"。听不出你一个人做了什么，这个故事就等于没有主角。

🎤 题型 2：项目复盘

问法："这个项目你做错了什么？" / "重来一遍怎么做？" / "怎么衡量它成功？"

结构：现象 → 根因（5Why）→ 影响 → 改进 → 沉淀。考的是反思能力，P7+ 的核心分水岭。

加分点：敢承认真失败；能说出"如果当时知道 X 我会做 Y"；失败被机制化挡住；从个体问题看到系统性问题。

失分点：拿一个"其实成功了的项目"当失败讲（"唯一遗憾是没早点开始"），面试官一听就知道你没有真的复盘过。

🎤 题型 3：技术管理题

问法："怎么做技术选型 / 处理线上事故 / 衡量工程效率 / 管技术债？"

结构：先给框架，再用一个 Case 印证，最后给度量。三段缺一段都显得空。

加分点：有结构化方法（如 5 维评估）；Case 能讲到细节；有量化；有反向思考（"选了 A，同时要防 X"）。

失分点：只讲框架不给 Case —— 会被追问到底，而背来的框架经不起两层追问。

🎤 题型 4：产品 / 业务题

问法："这个业务你怎么看？" / "用户为什么不用？" / "这个项目 ROI 怎么算？"

结构：用户分层 → 价值假设 → 数据验证 → 优先级。

加分点：讲场景而不是功能列表；讲数据而不是"我觉得"；会算账（ROI / LTV / CAC）；能讲"不做什么"比能讲"做什么"更值钱。

失分点：把竞品功能清单当业务分析。

面试映射 · 答题方法论

🌟 STAR 模型 · 🚗 CAR 模型 · 🔍 5Why · 根因分析 · 📊 RICE · 优先级量化 · 💬 SBI · 给反馈 / 谈话框架

5 个万能模型 — 把你的"经历"变成"结构化叙事"。

🌟 STAR 模型

Situation · Task · Action · Result · 行为面试万能结构

SSituation 背景

哪个项目？什么阶段？团队多大？

TTask 任务

你的角色？要解决什么问题？目标和约束是什么？

AAction 行动

你具体做了什么？拒绝了什么？最关键的 2-3 个动作。

RResult 结果

量化结果 + 影响（团队 / 业务）+ 沉淀（机制 / 文档 / 成长）

避坑：不要 S+T 讲掉 80% 时间，Action 至少占 60%。

🚗 CAR 模型

Context · Action · Result · STAR 的简化版

把 S+T 压成一句背景，A 和 R 照 STAR 讲。
什么时候换成它：面试官明显在赶时间。短答不是省力，是主动把时间让给追问 —— 追问才是拿分的地方。

🔍 5Why · 根因分析

连问 5 个为什么 · 找到根因而不是表象

适用：复盘题 / 故障题 / "你最大的教训"。五连问示例见 §2.3.4 的 Postmortem 模板。
唯一的要害：不要停在"那个人做错了"，要挖到"为什么我们的机制让他这样做" —— 面试官就是在听你停在第几层。

📊 RICE · 优先级量化

Reach × Impact × Confidence ÷ Effort · 产品决策利器

四个因子与算法见 §3.1.3；适用："这两个需求先做哪个" / "资源不够怎么分"。
关键不在公式，而在算完之后怎么公开（口径见 §3.1.3）。只报分数，听起来像在用工具躲决策。

💬 SBI · 给反馈 / 谈话框架

Situation · Behavior · Impact · 让反馈对事不对人

SSituation

"在上周的客户评审会上"（明确具体场景）

BBehavior

"你打断了客户 3 次"（描述行为，不评判）

IImpact

"客户后来跟我说他感觉不被尊重"（说影响）

适用："你怎么给员工反馈 / 处理低绩效 / 1on1 谈话"，把反馈钉在行为上，避免变成"你这人怎么这样"。

MECE 原则 · Mutually Exclusive, Collectively Exhaustive · 麦肯锡咨询基础

定义把问题分解成 互不重叠（ME）+ 不遗漏（CE）的子项，是所有结构化答题的底层。
3 步法框定边界 → 选一个切分轴（混用两个必然重叠）→ 回头检验有没有重叠、盖不盖得住整个问题。
常用的轴：时间、主体（用户 / 商家 / 平台）、流程（输入 → 加工 → 输出）、层级，以及最好用的2×2 矩阵。
适用场景任何开放题先拆维度再答；文档目录设计；问题诊断。不适用：对方问的是一个具体事实时，先拆三个维度只显得在拖时间。
实战案例 · 对比答法
问题❌ 非结构化答法✅ MECE 答法
"如何提升团队效率？" "加强自动化、做好规范、提升士气..." (杂乱) 从人 / 事 / 工具 3 维拆：
① 人：招聘 / 培养 / 激励
② 事：拆任务 / 优先级 / 协同
③ 工具：CI/CD / 协作工具 / AI 辅助
"团队为什么效率低？" "沟通不畅、技术债多、人不够..." (重叠) 从输入 / 过程 / 输出 3 段拆：
① 输入端：需求质量 / 优先级清晰度
② 过程：协作 / 工具 / 技术债
③ 输出端：交付质量 / 反馈速度

金字塔原理 · Pyramid Principle · Barbara Minto (McKinsey)

定义不是"先有结论"，而是"听众先听结论"。
4 个核心原则① 结论先行；② 以上统下——上一层是下一层的总结；③ 同一层论点必须 MECE；④ 同一层要有顺序（时间 / 重要性 / 因果），否则听众记不住三个并列的点。
结构：塔尖 1 句核心论点 → 3~7 条 MECE 论据 → 每条挂数据和案例。塔尖超过一句，说明你还没想清楚要对方记住什么。
SCQA 开场（汇报 / 邮件的前 30 秒） S 情境"Q3 用户增长 20%" → C 冲突"订单转化率反而降了 5%" → Q 疑问"要不要调策略" → A 答案"我建议先做 X 实验，理由有 3 个…"。
C 是发动机：没有冲突，前面那句情境就只是废话，对方不明白你为什么占用他的时间。
适用场景周报 / 述职、决策提案、RFC、跨团队邮件 —— 凡是"对方比你忙"的沟通。

🎤 最后环节 · 你有什么问题？（3 个高质量反问）

问题背后的考察意图
"团队现在最大的挑战是什么？" 看你的"主动 ownership" — 你在了解之后能不能 hit ground running
"这个岗位入职后 6 个月，您希望我做出什么成果？" 校准期望，避免入职后才发现"误解"。也展示你目标感强

🏁 一句话总结 · 5 大象限的核心命题

  1. 团队管理 = 合适的人 + 合适的机制 + 持续校准
  2. 技术管理 = 拍板并承担后果

  4. 组织战略 = 结构服从战略
  5. 面试映射 = 每个能力配一个能讲、能量化、能追问的故事
