万级并发图片处理流水线

「同时处理 10000 张图片」这句需求本身是未定义的——按字面实现要 360 GB 内存，按正确理解只要 640 KB。这一篇从这个五个数量级的差距出发，把 C++ 高吞吐流水线的三层并发度、内存放大、分级队列、GPU 批处理和反压逐个拆开算清楚。

核心难度 ★★★★★ 端到端案例 阅读时长 ~65 min 前置 C++ 并发 · 内存管理
01

「同时处理 10000 张」是一个未定义的需求

这一章的产出不是架构，是把一句话拆成六个能验证的数字

1.1 甲方原话与四轮追问

「我们的 App 用户上传照片，要能同时处理一万张，出五档缩略图加水印。另外历史上还有一千万张老图要重刷一遍。要快，别让用户等。」

和上一篇一样，先把形容词换成数字。四轮追问，每一轮的答案都会改掉一个架构决策：

追问答案它改变了什么
图片多大、多少像素？平均 4 MB / 12 MP（4000×3000），P95 12 MB，最大允许 100 MB决定内存预算。关键不是 4 MB，是解码之后的 36 MB（§3.1）
「同时一万张」是峰值到达率还是在途数量？追问后发现是「后台积压任务数的报警阈值」，和并发处理能力根本不是一回事这是全篇最重要的一次澄清（§1.3）
「别让用户等」等的是什么？上传完能立刻看到自己的照片；五档缩略图晚几百毫秒无感意味着上传和处理可以解耦，用户等的是上传，不是处理（§4）
在线和离线批共用一套资源吗？希望共用，成本敏感决定要不要做优先级与配额隔离（§8.1）
第二个追问的价值最大。「同时处理一万张」听起来是个容量需求，追问之后发现它是运维给的一个报警阈值——「积压超过一万张就告警」。这两者对架构的要求完全相反：前者要求系统能并行处理一万个任务（几乎不可能，见 §1.3），后者只要求系统在积压一万个任务时不崩溃，并按可预期的速度消化。

「同时」「并发」「支持 N 个」这类词在需求里几乎总是有歧义的，而歧义的两端往往差几个数量级。听到就要追问，不要自己选一个理解往下做。

先做一次最粗的核算，确认这个需求在物理上成立：

峰值 CPU 需求 = 1200 张/s × 0.28 s = 336 核。

为什么不按 336 核买 6 台（利用率 87%）？因为排队论告诉我们，利用率越过 70% 之后排队延迟开始非线性上升，到 87% 时平均排队时间是空闲时的 6.7 倍——P99 800 ms 的目标会直接失守。详细推导见容量估算与背压 · 利用率与排队延迟。「按峰值需求买机器」是容量规划里最常见的一个错误，它漏掉了排队。

1.3 「同时 10000 张」的三个答案，差五个数量级

现在回到那句需求。假设真的要让一万张图「同时在系统里」，内存要多少？答案完全取决于「在系统里」是指哪一层：

所以正确的解读是：系统要能在积压一万个待办时保持稳定，而真正「在处理中」的数量应该由 CPU 核数决定，不由积压量决定。这两个数字必须解耦，而解耦它们的东西就是一个只存引用的有界队列（§2.4）。

「并发 10000」这个说法在 IO 密集场景下是成立的——一万条 TCP 连接同时挂着等数据，是上一篇的题目，那里每条连接只占几 KB。但在计算密集场景下它几乎总是错的：一万个正在跑的解码任务需要一万个执行单元，而机器只有 512 个核。多出来的 9488 个「并发」只会变成上下文切换、缓存抖动和 36 MB 一份的内存占用。
判断一个「并发 N」的需求是否合理，先问它是 IO 密集还是计算密集——两者的合理并发度分别由「等待时间」和「核数」决定，差几个数量级。

1.4 范围与非目标

本文范围

从对象存储事件到五档缩略图落库这一段：并发度定容、内存与配额、线程池分层、尾延迟、GPU 批处理、离线批调度、反压。难点是吞吐与内存。

明确的非目标

① 图像算法本身（缩放核、水印算法、感知哈希）——那是另一个领域；② CDN 与缓存策略；③ 审核与内容安全（它是流水线上的一个消费者，不改变流水线的形状）。

还有一件事要提前说清楚：本文不讨论「实时转码」这条路线（不预生成缩略图，等 CDN 回源时按需转）。它在很多场景下是更优解——省掉 80% 从没被访问过的缩略图的存储和计算——但它把问题变成了一个缓存与冷启动问题，形状完全不同。选预生成的理由是本例的访问模式：图片上传后 24 小时内会被查看的比例超过 90%，按需转码省不下多少，反而给首次访问加了几百毫秒。这个判据（首访命中率）应该在选型时算一遍，而不是照抄别人的架构。

02

三层并发度必须分开定容

把一个「并发度」拆成三个，是这条流水线的骨架

2.1 三层的资源画像完全不同

一张图从进入系统到产出缩略图，要跨过三种性质完全不同的工作：等网络、烧 CPU、等存储。它们的合理并发度分别由三个毫不相干的量决定：

很多流水线的性能问题，根源就是把这三个数字合成了一个。典型症状：把线程池调大，网络吞吐上去了但 CPU 上下文切换飙升、P99 变差；调小，CPU 打满了但一堆线程卡在等对象存储。无论怎么调都有一边不满意——这不是「没调好」，是这个旋钮本身不该只有一个。

2.2 Little's Law：每层各算一遍

三层各自要多大，用 Little's Law 算：在途数量 L = 到达率 λ × 单个任务的驻留时间 W。这个式子的价值在于它只需要两个容易测的量，就能算出一个很难直接观测的量（在途数量，而在途数量直接等于内存占用）。完整推导与它的三种用法见容量估算与背压 · Little's Law，这里直接代数：

层λ（峰值）WL = λW它决定了什么
① 接收1200 张/s拉取 4 MB ≈ 80 ms96 个在途请求 需要 96 个「等待槽」。用协程就是 96 个协程（每个几 KB）；用线程就是 96 个线程（每个 8 MB 栈 = 768 MB）
② 处理1200 张/s280 ms CPU + 排队336 个在途 但集群只有 512 核，所以 336 是并行跑着的，不是排队的。这也说明利用率 66% —— 见 §1.2
③ 写回1200 × 5 = 6000 个对象/s上传小文件 ≈ 30 ms180 个在途上传 要么 180 个协程，要么按对象存储的并发配额限速排队
第二层那个 336 是全篇的关键数字。它乘上「解码后位图 36 MB」就是集群解码内存峰值 = 336 × 36 MB ≈ 12 GB，分摊到 8 台机是 1.5 GB/台——完全可控。

而如果不设 in-flight 上限、让接收层有多少收多少，同样的 1200 张/s 在下游变慢时会在几秒内堆出上千个正在解码的任务：1000 × 36 MB = 36 GB/台，直接 OOM。Little's Law 算出来的 L 不只是一个观测值，它必须变成代码里一个真实存在的上限。

2.3 有界队列是层间唯一合法的接口

三层之间怎么连？只有一种做法是对的——有界队列。另外两种常见做法都会在某个时刻失效：

连接方式正常时下游变慢时
直接函数调用（同一线程串起来）最快，零开销三层并发度被强制相等——接收层的并发度等于处理层的，等于写回层的。§2.1 的三个数字被合并了
无界队列解耦了，看起来很美上游继续全速生产，队列无限增长直到 OOM。无界队列不是「没有背压」，是「把背压推迟到 OOM 那一刻」
有界队列解耦，且各层独立定容队列满 → 上游阻塞或拒绝 → 压力在产生的地方被感知到。这就是背压

「有界」这两个字看起来是个小配置，实际上它是整个系统唯一把「下游能力」传导回「上游速度」的机制。§9 会展开：这条链上有三个必须存在的背压点，缺任何一个，压力都会绕过去、在别的地方以看不懂的形态爆发。

2.4 ADR-001 队列里放引用，不放数据

回到 §1.3 的三个答案。队列里到底放什么，决定了「积压一万张」是 40 GB 还是 640 KB：

ADR-001层间队列只传对象存储的键与元数据，不传图片字节；队列有界且外置已接受
背景
积压量（可能上万）与在途处理量（由 Little's Law 算出为 336）必须解耦。若队列元素携带图片数据，积压 1 万张就是 40 GB 内存，且进程重启即丢失用户数据。
候选
① 进程内队列传 shared_ptr<Buffer> ② 进程内队列传对象键 ③ 外置消息队列（Kafka / SQS）传对象键
决策
选 ③ 作为跨阶段的主队列（上传事件 → 处理任务），选 ② 作为单进程内三层之间的队列。图片字节只在处理层内部存在，从拉取到写回是一条不落地的短路径。
后果
得到：积压量与内存脱钩（1 万张积压 = 640 KB）；任务可持久化、可重投、可跨进程与跨机器重新分配；worker 变成无状态的，可随意扩缩与抢占（§8.3 用到这一点）。
付出：每个任务多一次对象存储读取（约 80 ms，已计入 §2.2 的 W）；多一个外部依赖；重投意味着可能重复处理，因此下游必须幂等（§8.2）。
何时重议
若将来出现「上传后 100 ms 内必须出图」这类硬实时需求，多一次对象存储往返就不可接受，需要为这条路径单开一个「上传即处理、数据不落地」的短路——但那应该是主流水线之外的一条额外快车道，而不是把主流水线改成同步的。
03

内存放大：解码后的位图才是杀手

所有关于「4 MB 一张图」的直觉，在这一章都要作废

3.1 4 MB 的 JPEG，处理峰值 72 MB

JPEG 是压缩格式，而所有图像处理都在未压缩的位图上进行。这中间的放大倍数才是这条流水线真正的内存模型：

更要命的是这个倍数不是常数：它取决于像素数，而像素数和文件大小的关系很弱。一张 4 MB 的高压缩率照片可能是 24 MP（解码后 72 MB），一张 4 MB 的低压缩率截图可能只有 2 MP（解码后 6 MB）。也就是说光看文件大小无法预测内存占用——这直接推出下一节的结论。

极端情况有名字：解压炸弹（decompression bomb）。一个 1 MB 的 PNG 可以解码成几十 GB 的位图（全白图片的压缩率极高），这既是可用性问题也是安全问题。唯一可靠的防御是解码前先只读文件头拿到尺寸（libjpeg 的 jpeg_read_header、libpng 的 png_read_info），宽 × 高 × 通道数超限直接拒绝，一个像素都不解。§5.4 会给出更彻底的兜底。

3.2 所以配额单位必须是字节

既然文件大小预测不了内存，那么用「任务条数」做并发控制就是错的：

假设限制「最多 40 个任务并行」。
如果这 40 张恰好都是 2 MP 的截图：40 × 6 MB = 240 MB，机器闲得发慌。
如果这 40 张恰好都是 24 MP 的相机原图：40 × 72 MB = 2.9 GB，还只是解码；加上旋转的第二份就是 5.8 GB。
同一个配置，实际内存占用差 24 倍——这个配置项没有任何意义。

正确的做法是按字节配额：一个进程级的信号量，单位是字节，容量是「允许用于位图的内存上限」。任务在解码之前先读头拿到尺寸、算出需要多少字节、申请配额；申请不到就等（这就是背压点之一）。处理完归还。

// 按字节而不是按条数的配额。这是这条流水线上最重要的一个不变量：
//   任意时刻，所有正在解码/处理的位图字节数之和 <= budget_
class ByteBudget {
  const size_t budget_;
  size_t used_ = 0;
  std::mutex m_;
  std::condition_variable cv_;

 public:
  explicit ByteBudget(size_t bytes) : budget_(bytes) {}

  // 返回 false = 超时，调用方应当把任务退回队列而不是硬等 —— 硬等会让
  // 一张 900 MB 的巨图把所有 worker 都堵在这里（§6.1 的队头阻塞）。
  template <class Rep, class Period>
  bool acquire(size_t n, std::chrono::duration<Rep, Period> timeout) {
    // 单个任务就超过总预算时永远等不到 —— 必须在这里判掉，否则死等。
    if (n > budget_) return false;
    std::unique_lock lk(m_);
    if (!cv_.wait_for(lk, timeout, [&] { return used_ + n <= budget_; }))
      return false;
    used_ += n;
    return true;
  }

  void release(size_t n) {
    { std::lock_guard lk(m_); used_ -= n; }
    cv_.notify_all();   // notify_one 不行：等待者要的字节数不同，被唤醒的那个未必满足
  }
};

// 用法：先读头，再申请，最后才解码。顺序不能反 —— 这三步的顺序就是这段代码的全部价值。
ImageInfo info = peek_header(bytes);                 // 只解析头部，不碰像素
if (info.width * info.height > kMaxPixels) return reject("too large");
size_t need = size_t(info.width) * info.height * 3 * 2;  // ×2：源 + 目标（§3.1）
if (!budget.acquire(need, 200ms)) return requeue(task);   // 背压：退回队列，不硬等
BudgetGuard guard(budget, need);                       // RAII，异常路径也要归还
notify_all 那一行的注释值得展开。这不是普通的信号量——等待者请求的数量不同，所以「释放了 36 MB」并不意味着队首那个等 900 MB 的能走。用 notify_one 会出现「明明有空间，但被唤醒的那个不够用，又睡回去，而能用的那个没被叫醒」——一个典型的丢失唤醒。
代价是惊群：每次归还都叫醒所有等待者。在 worker 数量只有几十个的场景下这完全可以接受；如果等待者上千，就该改成按需求量排序的显式等待队列。「用简单实现 + 说清它什么时候不够用」，比一上来写复杂版本更有价值。

3.3 ADR-002 流式解码替代全解码

上面那套配额把内存管住了，但它管的是「同时能解多少张」。还有一条正交的路：让单张图占用的内存本身变小。

关键观察是：我们要的是最大 1600×1200 的缩略图，而源图是 4000×3000。传统流程「完整解码 36 MB → 缩放 → 编码」里，那 36 MB 有 84% 的像素解码出来就是为了被扔掉。两种成熟的规避手段：

手段做法省下多少限制
JPEG DCT 缩放解码 libjpeg-turbo 的 scale_num/scale_denom，在 DCT 域直接按 1/2、1/4、1/8 输出 1/4 缩放时位图从 36 MB 降到 2.25 MB，解码时间也降到约 1/3 只支持 N/8 这些固定比例，需要再做一次精细缩放收尾
流式 / 分块处理 libvips 的按扫描线流式管道：解码一条、缩放一条、写出一条，整图从不完整驻留 峰值内存降到几 MB 量级，与图片尺寸基本无关 只适用于能局部计算的算子；需要全局信息的（某些直方图操作）仍要全图
ADR-002用 libvips 的流式管道做主处理路径，保留 libjpeg-turbo 直调作为快路径已接受
背景
全解码路径下单张峰值 72 MB，而 84% 的解码像素最终被丢弃。内存是本流水线在线部分的主要约束（§3.1）。
候选
① ImageMagick / GraphicsMagick（全解码，生态最全）② libvips（流式，内存与尺寸解耦）③ 直接调 libjpeg-turbo + 自写缩放
决策
主路径选 ②。libvips 的按需流式模型让单张峰值内存从 72 MB 降到个位数 MB，使 §3.2 的字节配额可以设得宽松很多，进而提高并行度。对最常见的「JPEG 输入 + 等比缩放」这一条占 85% 流量的路径，另走 ③ 的 DCT 缩放快路径。
后果
得到：内存与图片尺寸基本解耦，一张 100 MB 的大图不再需要 900 MB；同样的内存预算下并行度提高一个数量级。
付出：libvips 的算子集比 ImageMagick 小，遇到不支持的格式或算子要有回退分支（分支意味着两条路径都要测）；流式模型下错误发生在管道执行时而不是调用时，错误定位比同步 API 困难。
依赖
本决策放宽了 ADR-001 之外的内存约束，但不能取代 §3.2 的字节配额——回退到全解码分支时配额仍是唯一的保护。两者是互补的，不是二选一。

3.4 缓冲池：mmap 阈值与 RSS 锯齿

就算用了流式解码，仍然有大量几 MB 到几十 MB 的缓冲要反复申请释放。这里有两个 glibc 层面的行为会直接变成性能问题和「看起来像内存泄漏」的现象。

一、大块分配走 mmap，每次都要重新缺页。glibc 的 malloc 对超过 M_MMAP_THRESHOLD（默认 128 KB）的请求直接 mmap，free 时 munmap 还给内核。mmap 返回的是未映射的虚拟地址，第一次写每一页都要触发缺页中断：

一块 36 MB 的位图缓冲 = 36 MB ÷ 4 KB = 9216 个页面。每次缺页处理约 1–2 μs（分配物理页 + 清零 + 建页表项），合计 9–18 ms。
这占单张 280 ms 处理时间的 3–6%，而且它是纯浪费——同一块内存刚刚才被释放。1200 张/s 下就是每秒 11–22 秒的 CPU 时间，接近 20 个核。

二、glibc 会自适应提高 mmap 阈值，于是 RSS 只涨不落。当你 free 一块 mmap 来的内存时，glibc 认为「这个大小以后还会用」，会把 M_MMAP_THRESHOLD 提高到这次的大小，后续同样大小的分配改从 arena 里切。这个自适应对性能是好事（避免反复 mmap），但它的副作用是那块内存不再归还给内核，RSS 曲线只涨不落——运维看到的就是一个疑似内存泄漏。

❌ 每次 new 一块

RSS 呈锯齿状剧烈波动然后单调爬升到一个高台；每张图付 9–18 ms 缺页；碎片化让高台越来越高。而且这个高台的高度是不可预测的，取决于历史上处理过的最大那批图。

✅ 分档缓冲池 + 显式配置

按 2 的幂分档（4/8/16/32/64/128 MB）预分配一组缓冲，借还复用。首次使用后页面一直是映射着的，缺页只付一次。RSS 稳定在一个可预测的高度，正是我们在 §3.2 里配额的那个数。

配套要做的两件事：启动时 touch 一遍（或者 mmap 时带 MAP_POPULATE），把缺页成本一次性付在启动阶段而不是第一个用户请求上；以及考虑透明大页（THP），2 MB 的页让 36 MB 只需要 18 次缺页而不是 9216 次，代价是可能的内存浪费和分配延迟抖动——这个取舍要实测，不要照抄结论。

换用 jemalloc 或 tcmalloc 能缓解一部分问题，但要注意它们自己的归还策略：jemalloc 的 dirty_decay_ms / muzzy_decay_ms 控制多久把空闲页还给内核，默认 10 秒。值太小会让 RSS 上下抖动并反复缺页，太大会让容器的内存 limit 被撑爆。在容器里跑时通常还要开 background_thread:true，否则归还只在分配路径上顺带发生，而空闲期恰恰没有分配。
但无论换哪个分配器，分档缓冲池仍然值得做——它解决的是「同一块内存反复缺页」，而这是分配器层面解决不了的（分配器不知道你下一次还要一块同样大的）。

摄取路径：为什么上传不走处理服务

最省钱的一条边，是让流量根本不经过你

4.1 预签名 URL 直传

朴素设计是「App → 我们的服务 → 对象存储」。算一下这条边的成本：峰值 1200 张/s × 4 MB = 4.8 GB/s 入向带宽，还要在服务里为每个上传维持一份缓冲。而这个服务在这条路径上什么也没做——它只是个搬运工。

预签名 URL 不只是省带宽，它把三件事一起解决了。限时（URL 5 分钟过期，天然限制了被滥用的窗口）、限内容（签名里可以带 Content-Length 上限和 Content-Type 约束，超限的 PUT 会被存储直接拒绝，不需要我们写一行校验）、限路径（key 由服务生成，用户无法覆盖别人的文件）。这些约束由对象存储在它自己的边界上执行，比我们在应用层校验更可靠也更省。

这是「把职责下沉到已经在链路上的组件」的典型例子。带宽、限流、大小校验、鉴权——这四件事对象存储本来就在做，让它做一遍比我们再做一遍便宜得多。架构设计里一个反复出现的问题是「这件事非我做不可吗」，而答案通常取决于链路上有没有别的组件已经在那个位置上。上一篇的 OTA（ADR-004）和这里是同一个判断。

4.2 ADR-003 事件驱动而非轮询

图片进了对象存储，处理流水线怎么知道？两条路：轮询「列出新对象」，或者由存储推事件。这个选择看起来很小，但它决定了系统的延迟下界和存储的账单：

ADR-003用对象存储的事件通知驱动流水线，不轮询；事件先进消息队列再分发已接受
背景
端到端 P99 目标 800 ms，其中留给「感知到新对象」的预算只有几十毫秒。同时对象存储的 LIST 操作在大桶上既慢又贵。
候选
① 定期 LIST 新前缀 ② 应用服务在返回预签名 URL 后自己排队（乐观地假设用户一定会上传成功）③ 对象存储事件通知 → 消息队列 → worker
决策
选 ③。事件是上传真正完成时才产生的，这一点很关键——候选 ② 会为大量「申请了 URL 但没上传」的请求生成幽灵任务，而移动端上传失败率并不低。事件不直连 worker 而是先进消息队列，是为了 ADR-001 的重投与削峰。
后果
得到：感知延迟从「轮询周期的一半」降到几十毫秒；不为未完成的上传生成任务；LIST 成本归零。
付出：事件通知是至少一次投递，同一张图可能被处理两次——所以 §8.2 的幂等是必需的，不是可选的；事件也可能丢失（各家存储的 SLA 都不是 100%），因此必须保留一条低频的对账扫描作为兜底。
何时重议
若换到不提供事件通知的存储，或者出现「同一次上传要触发多条互不相干的流水线」的需求（此时事件扇出会变复杂），应考虑在应用服务侧写一张 outbox 表，由它统一分发。
「事件可能丢」这条后果最容易被忽略，因为它很少发生。兜底的对账扫描不需要实时——每小时扫一次「过去两小时内上传但没有缩略图记录」的对象即可，成本极低。凡是依赖「异步通知」的架构都要配一条低频对账，否则丢掉的那 0.01% 会变成永远查不出原因的用户投诉。

C++ Worker：线程池分层与四个坑

§2 那三个数字，在这一章变成三个线程池

5.1 单一线程池会互相饿死

最常见的实现是一个线程池，每个任务从头做到尾：拉取 → 解码 → 处理 → 上传。线程数按核数设 64。问题在于这 64 个线程里，任意时刻有多少在真正用 CPU？

「饿死」这个词的准确含义在下半张图里：单一线程池下，对象存储变慢会让 CPU 停摆——64 个线程全堵在 read() 上，机器的 CPU 使用率掉到个位数，而任务队列在疯涨。这时候如果按「CPU 不高」去扩容，加的机器同样会堵在 IO 上，一点用没有。分层之后，外部依赖的抖动被限制在它自己那一层，表现为「IO 队列变长」而不是「整个系统停摆」。

5.2 三个池各自的定容依据

池大小依据调错了会怎样
IO 池（拉取 + 上传） 4–8 线程 / 数百协程 线程数只要够跑完成回调；在途数量由 §2.2 的 96 和 180 决定，用协程或异步 IO 承载，不是用线程 用线程承载在途数：276 个线程 × 8 MB 栈 = 2.2 GB，还有上下文切换
CPU 池（解码 + 处理 + 编码） = 物理核数 64 纯计算，多一个线程不会多算一点，只会多一次上下文切换和一份缓存污染 调大：P99 变差（每个任务都被切得更碎）；调小：核空转
GPU 提交池 2–4 线程 只负责攒批、拷贝到显存、提交 kernel、取回。GPU 的并行度在设备里，不在线程数上 调大：多个 stream 互相抢显存与 SM，吞吐反降（§7.3）
「CPU 池 = 物理核数」这条要说清一个细节：是物理核，不是逻辑核（超线程）。图像处理是典型的高 IPC、大量 SIMD、访存密集的负载，两个超线程共享同一套执行单元和 L1/L2，收益通常只有 10–20%，却会让每个任务的单张耗时翻倍——吞吐微涨、延迟明显变差。在有 P99 目标的在线路径上这是亏的；在只看吞吐的离线批上可以打开。同一台机器上，在线和离线应该用不同的线程数配置，这也是 §8.1 要做资源隔离的一个理由。

5.3 大对象分配：缺页才是成本

§3.4 已经算过这笔账：一块 36 MB 的缓冲首次写入要付 9216 次缺页、9–18 ms。这里补充两个只有在这个量级才会遇到的具体问题。

一、std::vector 会白清零一遍。std::vector<uint8_t> buf(36 * 1024 * 1024) 会值初始化——也就是 memset 36 MB。而这块内存马上就要被解码器完整覆写，这次清零是纯浪费。36 MB 的 memset 在内存带宽 10 GB/s 下约 3.6 ms，占单张处理时间的 1.3%。用缓冲池 + resize 到已有容量，或者用不做值初始化的分配器，能省掉它。注意这不是「过早优化」——在 1200 张/s 下这 3.6 ms 等于 4.3 个核。

二、内存带宽本身会成为瓶颈。处理一张图要至少完整走几遍 36 MB：解码写入、缩放读取、色彩变换。假设 4 遍，就是 144 MB 的内存流量。64 个核同时干这件事：64 × 144 MB ÷ 0.28 s ≈ 33 GB/s——已经逼近双路服务器的实际可用内存带宽。这意味着加核到某个点之后吞吐不再线性增长，因为大家在抢内存总线。USL：加核为什么会变慢讲的就是这个现象的一般形式。

这条推论直接支持了 ADR-002：流式解码不只是省内存峰值，它也省内存带宽——数据在 L2/L3 里就被消费掉了，不必往返主存。在核数多的机器上，这个收益经常比省内存本身更大，而且不会体现在任何「内存使用率」的监控图上。

5.4 超时与解码炸弹

一个任务卡住了怎么办？在这条流水线上这不是假设：

  • 恶意构造的解压炸弹（§3.1），一张图能解出几十 GB；
  • 格式损坏导致第三方库进入病态路径，某些 TIFF / WebP 的畸形文件能让解码器跑几分钟；
  • 就是单纯的大图——100 MB 的全景图合法且真实存在，处理它要几秒。

问题在于 libjpeg、libpng、libtiff 都是同步的 C 接口，没有取消点。你不能从外面「中断」一次 jpeg_finish_decompress()。可用的手段按可靠性排序：

手段能挡住什么挡不住什么
解码前读头 + 尺寸上限绝大多数解压炸弹，成本几乎为零畸形文件导致的病态循环（尺寸是合法的）
库的进度回调（libjpeg 的 progress_monitor）协作式取消，能中断长时间解码只在库愿意回调的地方生效；库内部的紧循环、以及库本身的崩溃都挡不住
线程 + 超时后放弃等待让调用方不被卡住那个线程永远回不来，它占的核和内存都收不回；跑几小时之后线程池就空了
独立进程 + 超时 kill全部：病态循环、内存爆炸（配 cgroup 限额）、段错误、库里的安全漏洞进程创建与 IPC 的开销
第三行那个陷阱值得单独记住：「起个线程做，超时就不管它了」不是超时控制，是资源泄漏。调用方确实按时返回了，但那个线程还占着一个核在死循环、还持有着 §3.2 申请的字节配额（如果配额是 RAII 释放的，那它永远不会释放）。表现是服务运行几小时后「吞吐缓慢下降」，重启就好——一个非常难查的问题，因为每一次单独看都是正常的。

5.5 ADR-004 解码放进独立进程

ADR-004图片解码在独立的沙箱子进程里执行，通过共享内存传递数据，超时即 kill已接受
背景
解码库是同步 C 接口、无取消点，且历来是内存安全漏洞的重灾区；处理的又是完全不可信的用户上传内容。超时、资源爆炸、崩溃、安全，四个问题指向同一个位置。
候选
① 同进程 + 尺寸校验 ② 同进程 + 进度回调协作式取消 ③ 独立进程池 + 共享内存 + cgroup 限额 + seccomp
决策
选 ③。维护一个常驻的解码子进程池（避免每次 fork 的开销），原始字节和输出位图通过共享内存传递（避免拷贝 36 MB），子进程用 cgroup 限住内存、用 seccomp 砍掉文件与网络系统调用。超时直接 SIGKILL，主进程回收共享内存并把任务标记为失败。
后果
得到：超时是真正可强制执行的；解码器崩溃只损失一个任务而不是整个 worker；一个 CVE 的爆炸半径被 seccomp 限制住；内存爆炸被 cgroup 挡在子进程里。
付出：一次跨进程往返（共享内存下约几百微秒，相对 280 ms 可忽略）；子进程池的生命周期管理是新增的复杂度（僵尸回收、崩溃后重建、共享内存段泄漏）；调试变难，栈跨了进程边界。
何时重议
若输入源变为完全可信（例如只处理自家管线产出的内部图片），这套隔离的收益会大幅下降，同进程方案的简单性会重新占优。判据是「输入是否可信」，不是「有没有出过事」。
这个决策的说服力不在于任何单一理由——只为了超时，或只为了安全，都不太值得付这份复杂度。它的价值在于一个手段同时解决了四个原本要分别处理的问题（超时、崩溃隔离、内存爆炸、安全漏洞）。
架构决策的性价比经常是这样体现的：与其为四个问题各打一个补丁，不如找一个位置把它们一次性挡住。找这个位置的方法是把问题列在一起看它们有没有共同的边界——这四个问题的共同边界都是「解码这段不可信代码的执行环境」。

尾延迟：P99 由最大的那张图决定

平均值完全正常，而用户在抱怨——这一章解释为什么

6.1 队头阻塞

处理时间和像素数近似成正比，而像素数的分布是重尾的：中位数 12 MP（280 ms），P99 是 50 MP（1.2 s），P99.9 是 100 MP 的全景图（2.5 s 以上）。千分之一的图，耗时是中位数的十倍。

如果所有任务共用一个 FIFO 队列，这千分之一会把它前面排着的所有人一起拖慢：

6.2 按体积分级的队列

实现上有三个要点，每一个都容易做错：

一、分级依据必须是像素数，不是文件大小。§3.1 已经说过两者关系很弱。而像素数在 §3.2 的「读头」那一步就已经拿到了，不需要额外成本。

二、慢通道要有独立的 worker，而不是共享 worker 池 + 优先级。如果只是给小图更高的优先级、共用 64 个 worker，那么当 64 个 worker 恰好都在处理大图时，小图仍然要等——优先级只影响排队顺序，不影响已经开始执行的任务。要真正隔离，必须是物理上分开的执行资源。这和 舱壁隔离是同一个道理。

三、慢通道的容量是一次业务取舍，要写下来。给慢通道 8 个 worker 意味着：大图的吞吐上限是 8 / 2.5 s = 3.2 张/s，超过这个速率大图就会积压。这个数字必须和业务对齐——如果哪天有个活动导致大量全景图上传，慢通道会堵，而这是设计时就接受的结果，不是故障。

// 分级路由：读头拿到像素数之后立刻决定走哪条通道，此后两条路完全独立。
enum class Lane { kFast, kSlow, kReject };

Lane route(const ImageInfo& info) {
  uint64_t px = uint64_t(info.width) * info.height;
  if (px > kMaxPixels)     return Lane::kReject;   // 解压炸弹与超规格，直接拒（§3.1）
  if (px > kFastLanePixels) return Lane::kSlow;    // 20 MP 分界，覆盖 99.4% 的流量走快车道
  return Lane::kFast;
}

// 两条通道各自持有独立的 worker 与独立的字节配额。
// 配额也要分开：共用一个 ByteBudget 的话，几张巨图就能把快车道的额度吃光 ——
// worker 分开了但内存没分开，隔离只做了一半，故障时依然会互相拖累。
struct LaneRuntime {
  BoundedQueue<Task> queue;
  ThreadPool          workers;
  ByteBudget          budget;
};
LaneRuntime fast{ /*queue*/ 4096, /*workers*/ 56, /*budget*/ 24_GB };
LaneRuntime slow{ /*queue*/  256, /*workers*/  8, /*budget*/  8_GB };
注释里那句「隔离只做了一半」是这类设计最常见的漏洞。做资源隔离时要把所有共享资源列一遍：线程、内存配额、连接池、限流令牌、甚至日志缓冲。只隔离最显眼的那一个（通常是线程），剩下的任何一个都足以让两条通道在故障时重新耦合起来。上一篇 §8.2 把握手线程池独立出来时，也必须同时给它独立的入口队列，是同一件事。

6.3 为什么加机器解决不了

遇到 P99 高，最直觉的反应是加机器。但队头阻塞造成的尾延迟，加机器的效果非常有限：

假设集群从 8 台加到 16 台，总 worker 从 512 到 1024。一张 100 MP 的巨图仍然占住一个 worker 2.5 秒——它不会因为集群变大而变快。
变的只是「一张巨图占住的 worker 占总量的比例」从 1/512 变成 1/1024，也就是被它挡住的小图变少了。但由于巨图的数量也是按比例增长的（流量涨了才需要加机器），这个比例并不会改善。加机器改善的是排队，改善不了「单个任务本身就慢」。

这是理解尾延迟的一个通用要点：P99 有两个来源，排队和服务时间本身，两者的解法完全不同。排队造成的尾延迟靠加容量或降利用率解决（利用率与排队延迟）；服务时间本身的长尾只能靠隔离（不让慢的拖累快的）或者让慢的变快（比如给巨图专门走 GPU 路径）。诊断的第一步是把两者分开测：在队列里的时间和在 worker 上的时间要分别打点。

GPU 批处理：吞吐与延迟的直接兑换

批大小是一个旋钮，它两端接的东西正好相反

7.1 nvJPEG 的批量曲线

GPU 解码 JPEG（nvJPEG）单张比 CPU 快一个数量级，但它的优势要靠批量才能兑现——每次提交都有固定的开销（PCIe 传输的启动延迟、kernel launch、同步），批越大越能摊薄。同时批越大，第一张图要等的时间越长：

攒批本身也有一个必须注意的点，和上一篇 §9.3 的 Kafka 攒批完全一样：必须有超时兜底。低谷期到达率可能只有 50 张/s，攒够 128 张要 2.5 秒；如果只按条数触发，这 2.5 秒会直接进入延迟。三个触发条件缺一不可——条数、字节（显存约束，见 §7.3）、超时。

// GPU 攒批。三个触发条件里，超时是唯一保证延迟上界的那个。
void BatchSubmitter::run() {
  std::vector<Task> batch;
  size_t vram_needed = 0;
  auto deadline = Clock::now() + linger_;

  while (running_) {
    Task t;
    // 注意超时用「距离 deadline 还有多久」，不是每次都等一个完整的 linger_ ——
    // 后者会让批次在持续小流量下被无限推迟，延迟上界失效。
    if (queue_.pop_until(t, deadline)) {
      batch.push_back(std::move(t));
      vram_needed += batch.back().vram_estimate();
    }
    bool full  = batch.size() >= max_batch_ || vram_needed >= vram_budget_;
    bool timed = Clock::now() >= deadline;
    if (!batch.empty() && (full || timed)) {
      submit(batch);            // H2D 拷贝 + nvjpegDecodeBatched + D2H
      batch.clear(); vram_needed = 0;
    }
    if (timed) deadline = Clock::now() + linger_;
  }
}

7.2 ADR-005 在线 batch=4，离线 batch=128

ADR-005GPU 解码按路径取不同批大小：在线 batch=4 / linger 5 ms，离线 batch=128 / linger 200 ms已接受
背景
批大小同时影响吞吐（有饱和点）与单张延迟（线性增长）。在线路径 P99 预算 800 ms，离线路径只关心 8 小时窗口内的总吞吐。
决策
两条路径用同一份代码、不同配置，各自独立的批处理器和显存配额。在线取 batch=4：吞吐拿到饱和值的 55%，而批内等待只增加约 3 ms。离线取 batch=128：吞吐拉满，200 ms 的攒批延迟在 8 小时窗口里可忽略。
后果
得到：一个旋钮服务两个目标相反的场景，不需要两套实现。
付出：两条路径要共享同一块 GPU 的显存和算力，必须做配额与优先级（见 §7.3）；离线的大批次一旦提交就占住 GPU 直到完成，在线批次要等——这会给在线路径引入一个不可抢占的延迟毛刺。这是本决策最主要的代价，缓解手段是给离线批也设一个批大小上限，让单次占用时间可控。

7.3 显存也要配额，而且它不能 swap

显存和主存有一个关键差别：它没有 swap，也没有 OOM Killer 帮你挑一个进程杀。显存不足时 CUDA 调用直接返回 cudaErrorMemoryAllocation，如果代码没处理好，通常是整个进程崩掉——而这个进程里可能还有几十个正在处理的任务。

所以 §3.2 的字节配额在 GPU 这一侧要再做一遍，而且要更保守：

  • 配额按批估算，不按单张。一批 128 张 12 MP 的图，显存需求是 128 × (压缩输入 + 解码输出) ≈ 128 × 40 MB = 5 GB。A10 有 24 GB，但要留给别的东西。
  • 在线和离线各有独立配额，理由同 §6.2：只隔离算力不隔离显存，隔离只做了一半。
  • 用显存池，不要反复 cudaMalloc。cudaMalloc 是同步的、会隐式同步整个设备，在热路径上调它会让流水线的所有 stream 停顿。启动时一次性分配，之后自己管。这和 §3.4 的主存缓冲池是同一个道理，只是后果更严重。

7.4 CPU 回退路径

GPU 路径必须有回退，理由有三个层次，越往后越现实：

为什么需要回退触发频率
nvJPEG 只支持基线和渐进式 JPEG 的一部分子集，遇到不支持的编码变体要退回 CPU经常——真实世界的图片格式远比想象中杂
PNG / WebP / HEIC / TIFF 的 GPU 解码支持远不如 JPEG 成熟取决于流量构成
GPU 故障、驱动升级、显存耗尽、机器上根本没有 GPU偶尔，但影响面大
回退路径的容量必须被算进去，否则它是个陷阱：如果按「90% 走 GPU」来配 CPU 核数，那么 GPU 一挂，100% 的流量涌向只有 10% 容量的 CPU 路径，系统立刻雪崩——一个为了提高性能而引入的组件，故障时反而成了单点。
正确做法是把 GPU 当成加速器而不是依赖：CPU 路径的容量按「能扛住全量的降级服务水平」来配（比如全量但 P99 放宽到 3 s），GPU 负责把正常情况下的延迟和成本压下去。这条判据同样适用于任何「快路径 + 慢路径」的设计。

离线批：一千万张 / 24 小时

同一套 worker，完全不同的约束

8.1 瓶颈不在 CPU，在对象存储

1000 万张、夜间 8 小时窗口，平均 347 张/s。CPU 需求 347 × 0.28 = 97 核——集群有 512 核，看起来轻松。但换个维度算：

读取带宽 = 347 张/s × 4 MB = 1.4 GB/s，八小时共读 40 TB。
这个流量打到和线上业务共用的对象存储上。即使存储扛得住，它的带宽、IOPS 和请求配额是共享的——离线批把它们吃掉，线上的图片访问就会变慢。离线批的真正约束不是「我需要多少」，是「我能占多少而不伤到别人」。

所以离线批必须自带限速，而且限速的依据是外部约束，不是自己的能力。三个层次的隔离：

存储侧限速

读取速率设一个明确上限（比如 800 MB/s），并且按时段调整：白天压到 200 MB/s，夜间放开。如果存储支持请求分级（不同 access key 不同配额），用它比自己限速更可靠。

CPU 侧优先级

离线任务的 worker 用较低的调度优先级（nice 或 cgroup 的 cpu.weight），保证在线任务突增时能立刻抢到核。注意这只在超线程关闭或核未打满时有效，真要硬隔离得用 cpuset 分核。

内存与显存配额

独立的 ByteBudget 与显存配额（§6.2、§7.3）。离线批可以用大得多的批次和更激进的并行度，但它的总额度必须是剩余量，不能挤占在线的保留额。

8.2 分片、断点续跑与幂等键

一千万个任务不能一次性塞进队列（ADR-001 算过：640 KB 的引用倒是放得下，但一次性投递会让消费顺序完全不可控，也没法中途调速）。标准做法是分片 + 游标：

分片按对象 key 的哈希前缀切成固定数量（比如 4096 片），每片是一个独立的工作单元。每片记录一个游标（处理到哪个 key）和状态。这样做的好处是片数固定、与数据量无关，扩缩 worker 只是重新分配片，不需要重新切分。

断点续跑就是游标的持久化。要注意的是游标推进的时机：必须在确认处理成功之后才推进，否则崩溃时会跳过一批。而「确认成功之后推进」意味着崩溃时会重复处理已完成但没来得及记录的那些——这就把问题推给了幂等。

幂等键是这里的关键设计。用什么做键，决定了重复处理是无害的还是有害的：

幂等键重复处理时问题
任务 ID / 消息 ID需要维护一张「已处理」表并查询这张表和任务量同量级（1000 万条），且它自己的写入也可能失败——把问题推迟了一层
源对象 key输出路径固定，第二次覆盖第一次可行，但如果处理逻辑有版本变化，无法区分「旧版本产物」和「新版本产物」
源内容哈希 + 处理版本号输出路径由它决定，重复处理产生逐字节相同的结果，覆盖与否都无所谓要读完整内容才能算哈希（但反正要读）；换处理版本会产生新产物，旧的需要清理
第三行才是真正的幂等：它不需要任何「已处理」的记录，因为重复执行的结果和执行一次完全一样。前两行是「靠查表避免重复执行」，而查表本身又需要一致性保证，是把问题往下推。
这两种思路的区别值得记住：「去重」需要状态，「幂等」不需要。能把操作设计成天然幂等（输出由输入唯一决定）时，整条链路上所有的「至少一次」投递语义都变得无害——ADR-001 的重投、ADR-003 的事件重复，一次性全部解决。上一篇 §10.2 说「把指令设计成声明目标状态而不是增量」，是同一条原则在控制面的形态。 
// 输出路径完全由「内容 + 处理逻辑版本」决定。
// 于是同一张图被处理 100 次，产出的 100 份结果逐字节相同、路径也相同 ——
// 「重复」这件事在下游根本不可观测，也就不需要任何去重表。
std::string derive_key(std::span<const uint8_t> src, Variant v) {
  // 用内容哈希而不是源 key：同一张图被不同用户重复上传时，还能顺带命中已有产物。
  std::string h = blake3_hex(src);
  return fmt("thumb/v{}/{}/{}/{}.jpg", kPipelineVersion, h.substr(0, 2), h, name_of(v));
  //               ↑ 版本号在路径里：改了缩放算法就是一批新产物，
  //                 新旧共存、可灰度、可回滚，不需要「原地更新」这种危险操作。
  //               ↑ 哈希前两位做目录分片：避免单目录下千万级对象，
  //                 也让对象存储的分区键分布均匀（很多存储按 key 前缀分区）。
}
h.substr(0, 2) 那个细节在千万级规模下很要紧。不少对象存储按 key 的字典序前缀划分内部分区，如果所有 key 都以 thumb/v3/2026-09-11/ 这类递增前缀开头，写入会全部集中到同一个分区上，形成热点——表现为写入速率莫名其妙地卡在某个值上不去。把高熵的哈希放在路径靠前的位置，是这类系统的一条常规做法。

8.3 抢占式实例与检查点

离线批对延迟不敏感、可重试、无状态（ADR-001 的红利），这三条正好是抢占式实例（Spot / 竞价实例）的适用条件，成本能降到按需实例的 20–30%。要用好它，只需要保证两件事：

一、被抢占时正在处理的任务不能丢。因为任务在队列里有「未确认」状态，worker 被杀之后消息会重新可见、被别的 worker 领走。这依赖 §8.2 的幂等——被抢占的任务很可能已经完成了一半甚至全部，只是没来得及确认。

二、抢占通知要被利用。云厂商通常给 30 秒到 2 分钟的预告。收到通知后应当：停止领新任务、尽快完成手上的、主动确认，然后退出。这能把「被抢占的浪费」从「整批任务重做」降到接近零。

抢占式实例有一个容易忽略的连锁风险：同一可用区、同一机型的抢占往往是同时发生的——不是随机掉一台，而是一批一起没。如果整个离线集群都在抢占实例上，可能瞬间从 200 个 worker 掉到 0，然后队列里几万条未确认消息同时超时重投。
两个缓解：混合部署（保底一部分按需实例，保证进度不归零）和跨机型分散（不要把所有 worker 都放在同一个机型上，它们的抢占是强相关的）。这和「不要把同一个变电站的设备放进同一个 OTA 批次」是同一类思路——识别出隐藏的相关性，然后打散它。

假设某一个环节的背压缺失（比如队列写成了无界的，或者字节配额只按条数算）。故障不会立刻发生，它会沿着一条固定的路径走完：

最后那行值得展开，因为它解释了为什么这类故障在现场特别难处理：三个最直觉的应对措施都会让情况变糟。加内存只是把 OOM 推迟几分钟；加机器会让新机器也走一遍同样的链条（而且它们启动时会一起去抢重投的任务）；重启是最糟的，因为重启后面对的是 ⑦ 那个「原流量 + 全部重投」的更高负载。唯一有效的现场措施是从入口限流——而如果架构里没有这个开关，现场就只能等它自己烧完。

9.2 三个必须存在的背压点

顺着数据流走一遍，这条流水线上有三个位置必须能说「不」。少任何一个，压力都会绕过去：

位置机制拒绝时的行为缺了它会怎样
① 领取任务 worker 只在有空闲容量时才从消息队列拉取（拉模式而非推模式） 不拉就是不拉，任务留在队列里 推模式下队列会把任务硬塞进来，worker 只能自己缓冲——无界队列就是这么出现的
② 申请解码内存 §3.2 的 ByteBudget，按字节 超时后退回队列而不是硬等（硬等会让 worker 全堵在这里） 这是最核心的一个。缺了它，内存占用与像素数直接挂钩、完全不可控
③ 写回上传 有界的上传队列 + 对下游的自适应限速 队列满时阻塞处理层，进而阻塞 ① 缺了它，下游 429 会变成无限重试，把已完成的位图一直留在内存里
三个背压点的共同点是它们都把压力挡在「产生新内存占用」之前。②之所以最关键，是因为它是唯一一个能挡住「单个任务的内存需求本身很大」这种情况的——①和③都只能控制任务的数量。
这也是设计背压时的一个通用检查：把系统里所有会显著增长内存的动作列出来，确认每一个前面都有一道闸。只在入口限流是不够的，因为入口不知道每个请求会消耗多少。

9.3 观测：看在途字节，不看任务数

监控指标的选择要和 §3.2 保持一致——既然配额单位是字节，那么告警和容量判断也必须看字节：

指标为什么是它
在途位图字节数（配额已用量 / 总量）直接对应内存风险。「32 个任务在处理」什么也说明不了，「用了 22 GB / 24 GB 配额」说明马上要限流了
配额等待时间的分位数比「队列长度」更早暴露问题：还没开始堆积时，等待时间就已经在涨了
队列时间 vs 处理时间分开打点§6.3 的诊断依据：P99 高是排队造成的还是服务时间本身长，两者解法完全不同
按通道分开的分位数（快车道 / 慢通道）混在一起算，慢通道的 2.5 s 会污染整体 P99，让 §6.2 的隔离效果完全看不出来
拒绝率与重投率背压真正生效时会体现在这里。拒绝率为零不一定是好事，可能说明背压点根本没起作用
RSS 与配额上限的差值§3.4 的分配器行为会让 RSS 高于配额，这个差值就是碎片与分配器缓存，涨得不对就该查

10.4 这套架构什么时候不适用

如果……哪个决策会失效该怎么做
吞吐 < 50 张/s 分层线程池、沙箱子进程、分级队列的复杂度全都收不回来 v1：一个线程池，一个队列，尺寸校验就够了
图片很小且尺寸一致（例如固定 512×512 的头像） §3 整章的前提（内存放大不可预测）不成立；§6 的队头阻塞也不存在 按条数配额就够，不需要字节配额；不需要分级队列
处理是同步的、用户在等结果 ADR-001 的「队列 + 重投」和 ADR-003 的事件驱动都建立在异步之上 要么改需求（让用户等的是上传，见 §1.1 第三问），要么走同步短路径并接受严格的容量上限
输入完全可信（自家管线产出） ADR-004 的沙箱隔离收益大幅下降 退回同进程 + 尺寸校验 + 进度回调，省掉一大块复杂度
要处理视频而不是图片 几乎全部。视频是流式且有时间维度：内存模型变成滑动窗口，任务粒度变成分片而不是文件，GPU 编解码器有独立的会话数上限 形状不同的问题，不要套用。可复用的只有「三层并发度分开定容」和「字节配额」这两条原则
把这五条读下来，会发现失效判据集中在两个量上：单任务资源消耗的可预测性，以及单任务耗时的分布形状。
消耗可预测（固定尺寸头像）→ 不需要字节配额；耗时分布窄（没有长尾）→ 不需要分级队列。本文之所以需要这一整套，正是因为这两个量在图片场景下都很糟：内存消耗和文件大小的相关性很弱，耗时分布是重尾的。下次遇到一个新的流水线，先测这两个分布，架构的形状基本就定了。

高频面试题 · 高吞吐流水线

12 道，按难度分三档

11.1 基础（必答）

  1. 基础需求写着「要能同时处理 10000 张图片」，你会怎么做？

    先追问，不要直接设计。「同时」这个词至少有三种含义，对应的内存需求差五个数量级（§1.3）：

    • 一万张都是已解码的位图：10000 × 36 MB = 360 GB，不可行
    • 一万张压缩态驻留在内存队列：10000 × 4 MB = 40 GB，放得下但毫无意义，且重启即丢
    • 队列里只放对象存储的键：10000 × 64 B = 640 KB，真正在处理的只有几百张
    正确解读
    它通常是「积压报警阈值」而不是「并行处理能力」。系统要能在积压一万时保持稳定并按可预期速度消化，而真正在途的数量应该由核数决定。这两个数字必须解耦，解耦它们的就是一个只存引用的有界队列。
    更一般的判据
    「并发 N」在 IO 密集场景下可能是合理的（一万条连接各占几 KB），在计算密集场景下几乎总是错的——一万个解码任务需要一万个执行单元，而机器只有几百个核。看到「并发 N」先问它是 IO 还是 CPU 密集。
  2. 基础一张 4 MB 的 JPEG，处理它要准备多少内存？

    不是 4 MB，是 36–72 MB（§3.1）。JPEG 是压缩格式，处理在未压缩的位图上进行：4000×3000×3 = 36 MB；EXIF 旋转或色彩变换需要源与目标同时驻留，峰值 72 MB。放大 18 倍。

    而且倍数不是常数
    内存取决于像素数，而像素数与文件大小的相关性很弱：4 MB 的高压缩照片可能 24 MP（72 MB），4 MB 的截图可能 2 MP（6 MB）。所以光看文件大小无法预测内存。
    推论：按条数限流是错的
    「最多 40 个任务并行」这个配置，实际内存占用可能是 240 MB 也可能是 5.8 GB，差 24 倍。配额单位必须是字节：先读头拿尺寸、算字节数、申请配额，再解码。
    加分
    提到解压炸弹：1 MB 的 PNG 能解出几十 GB。唯一可靠防御是解码前只读文件头做尺寸校验，一个像素都不解。
  3. 基础为什么图片上传不应该经过你的应用服务？

    峰值 1200 张/s × 4 MB = 4.8 GB/s 入向带宽，而服务在这条路径上什么也没做，只是搬运（§4.1）。

    预签名 URL 直传
    App 先向服务要一个预签名 URL（几百字节的往返），然后直接 PUT 到对象存储。服务的带宽降到接近零。
    它不只是省带宽
    签名里可以带 Content-Length 上限、Content-Type 约束和固定的 key，这三条校验由对象存储在它自己的边界上执行——比我们在应用层再写一遍更可靠也更省。URL 限时过期还顺便限制了滥用窗口。
    背后的原则
    「这件事非我做不可吗」——带宽、限流、大小校验、鉴权，对象存储本来就在做。把职责下沉到已经在链路上的组件。
  4. 基础为什么不能用一个线程池把「拉取 → 处理 → 上传」从头做到尾？

    因为这三段的资源画像完全不同，合理并发度由三个毫不相干的量决定（§2.1）：接收层是 IO 密集，由「等待时间 ÷ 处理时间」决定，可以上千；处理层是 CPU 密集，等于物理核数；写回层受对象存储的配额约束，是几十到几百。

    合成一个旋钮的后果
    调大：网络吞吐上去了但上下文切换飙升、P99 变差。调小：CPU 打满了但一堆线程卡在等存储。无论怎么调都有一边不满意——不是没调好，是这个旋钮本身不该只有一个。
    更严重的是故障传导
    单一线程池下，对象存储变慢会让 CPU 停摆：64 个线程全堵在 read() 上，CPU 使用率掉到个位数而队列在疯涨。这时按「CPU 不高」去扩容，加的机器同样堵在 IO 上。分层之后外部抖动被限制在它那一层，只表现为「IO 队列变长」。
    三层之间
    用有界队列连接。无界队列不是「没有背压」，是「把背压推迟到 OOM 那一刻」。

11.2 中级（区分熟练度）

  1. 中级用 Little's Law 算一下这条流水线各层要多大。

    L = λ × W：在途数量 = 到达率 × 单个任务驻留时间。它的价值在于用两个容易测的量，算出一个很难直接观测、却直接等于内存占用的量（§2.2）。

    层λWL含义
    接收1200/s80 ms9696 个等待槽。用协程是 96 × 几 KB，用线程是 96 × 8 MB 栈
    处理1200/s280 ms336× 36 MB = 12 GB 解码内存；集群 512 核 → 利用率 66%
    写回6000 对象/s30 ms180180 个在途上传
    关键一步
    算出来的 L 必须变成代码里一个真实的上限，不能只是一个观测值。不设上限的话，下游一慢，在途数会在几秒内翻十倍，内存跟着翻十倍。
    容量规划的常见错误
    按峰值 CPU 需求（336 核）买 6 台（利用率 87%）。排队论告诉我们利用率越过 70% 之后排队延迟非线性上升，87% 时平均排队时间是空闲时的 6.7 倍，P99 目标直接失守。所以买 8 台。
  2. 中级P99 是中位数的十倍，平均值却完全正常。怎么查、怎么改？

    先分清 P99 的两个来源，它们的解法完全相反（§6.3）：排队造成的，还是服务时间本身长。诊断的第一步是把「在队列里的时间」和「在 worker 上的时间」分开打点。

    本例是后者：队头阻塞
    处理时间与像素数成正比，而像素分布重尾：中位数 12 MP（280 ms），P99.9 是 100 MP（2.5 s）。单一 FIFO 下，千分之一的巨图会把排在它后面的所有小图一起拖慢——那些小图变慢的原因和它们自己毫无关系。
    解法：按体积分级
    读头拿到像素数就分流：≤20 MP 走快车道（56 worker），>20 MP 走慢通道（8 worker）。分级不是让大图变快，是不让大图拖慢小图——这是一次明确的偏袒，偏袒谁是业务决策。
    两个容易做错的地方
    ① 用文件大小分级——它和像素数相关性很弱，要用像素数。② 用「优先级 + 共享 worker 池」代替独立 worker——优先级只影响排队顺序，不影响已经开始执行的任务，64 个 worker 都在跑大图时小图照样等。
    为什么加机器没用
    一张巨图仍然占住一个 worker 2.5 秒，不会因为集群变大而变快。加机器改善排队，改善不了服务时间本身的长尾。
  3. 中级反复 new 一块 36 MB 的缓冲，会有什么问题？

    两个都跟 glibc malloc 的大块行为有关（§3.4）。

    一、每次都要重新缺页
    超过 M_MMAP_THRESHOLD（默认 128 KB）的分配直接 mmap，free 时 munmap。mmap 返回的是未映射的虚拟地址，第一次写每页都缺页：36 MB ÷ 4 KB = 9216 次缺页 × 1–2 μs = 9–18 ms，占 280 ms 处理时间的 3–6%，1200 张/s 下相当于近 20 个核在白干。
    二、RSS 只涨不落，像内存泄漏
    glibc 会在 free 时自适应提高 mmap 阈值（认为这个大小还会再用），此后同尺寸分配改从 arena 切，不再归还内核。对性能是好事，但 RSS 曲线单调爬升到一个不可预测的高台，运维会当成泄漏来查。
    解法
    按 2 的幂分档的缓冲池（4/8/16/…/128 MB），借还复用，缺页只付一次；启动时 touch 一遍或用 MAP_POPULATE，把这笔成本付在启动而不是第一个用户请求上。RSS 稳定在配额那个可预测的值。
    还有两条
    ① std::vector<uint8_t> buf(36MB) 会值初始化，白 memset 36 MB（约 3.6 ms，1200 张/s 下等于 4.3 个核）——这块内存马上就要被解码器完整覆写。② 换 jemalloc 能缓解但不能替代池化，还要调 dirty_decay_ms 并开 background_thread，否则空闲期根本不归还。
  4. 中级一个解码任务卡死了，怎么把它超时掉？

    难点在于 libjpeg / libpng / libtiff 都是同步 C 接口，没有取消点，你无法从外面中断一次 jpeg_finish_decompress()（§5.4）。

    最常见的错误答案
    「起个线程去做，超时就不等它了」。这不是超时控制，是资源泄漏：调用方按时返回了，但那个线程永远回不来，还占着一个核死循环、还持有着字节配额（RAII 也救不了，因为析构永远不会执行）。症状是服务跑几小时后吞吐缓慢下降，重启就好——极难定位。
    可用手段，按可靠性排序
    ① 解码前读头做尺寸上限——挡住绝大多数解压炸弹，成本几乎为零，但挡不住畸形文件的病态循环；② 库的进度回调做协作式取消——只在库愿意回调的地方生效；③ 独立进程 + 超时 SIGKILL——唯一能真正强制执行的。
    为什么值得上进程隔离
    不是单为了超时。一个手段同时解决四个问题：超时可强制、解码器崩溃只损失一个任务、内存爆炸被 cgroup 挡住、解码库的 CVE 被 seccomp 限制爆炸半径（处理的是完全不可信的用户上传）。四个问题的共同边界都是「解码这段不可信代码的执行环境」。
    代价
    常驻子进程池（避免每次 fork）、共享内存传数据（避免拷贝 36 MB）、僵尸回收与共享内存段泄漏的处理、以及跨进程的调试困难。输入完全可信时不值得付这份复杂度——判据是「输入是否可信」，不是「有没有出过事」。

11.3 高级（体现深度）

  1. 高级设计一个「按字节而不是按条数」的并发配额，有哪些坑？

    核心不变量是：任意时刻所有在处理的位图字节数之和 ≤ 预算（§3.2）。四个坑：

    ① 必须 notify_all，不能 notify_one
    这不是普通信号量，等待者请求的数量不同。释放 36 MB 并不意味着队首那个等 900 MB 的能走。用 notify_one 会出现「明明有空间，被唤醒的那个不够用又睡回去，而能用的那个没被叫醒」——典型的丢失唤醒。代价是惊群，等待者只有几十个时可接受。
    ② 单个请求超过总预算时要提前判掉
    否则它永远等不到，死等在那里。
    ③ 获取不到时要退回队列，不能硬等
    硬等会让一张 900 MB 的巨图把所有 worker 都堵在配额上——把内存问题变成了队头阻塞问题。
    ④ 顺序：读头 → 校验 → 申请 → 解码
    颠倒任何一步这套机制就失效了。特别是必须在解码之前申请——解码到一半才发现超预算，内存已经花掉了。
    还有一条隔离要求
    做了分级队列之后，每条通道要有独立的配额。共用一个的话，几张巨图就能把快车道的额度吃光——worker 分开了但内存没分开，隔离只做了一半。做资源隔离时要把所有共享资源列一遍：线程、内存配额、连接池、限流令牌。
  2. 高级把 GPU 加进来，批大小怎么定？

    批大小同时接着两条形状不同的曲线（§7.1）：吞吐随批大小上升但在 32 附近饱和；单张延迟从头到尾线性增长，没有拐点。所以「批越大越好」只在不看延迟时成立。

    按路径取不同的值
    在线 batch=4 / linger 5 ms：吞吐拿到饱和值的 55%，批内等待只加约 3 ms。离线 batch=128 / linger 200 ms：吞吐拉满，攒批延迟在 8 小时窗口里可忽略。同一份代码、两套配置。
    攒批必须有超时兜底
    低谷期到达率可能只有 50 张/s，攒够 128 张要 2.5 秒。只按条数触发，这 2.5 秒会直接进入延迟。三个触发条件：条数、字节（显存约束）、超时。而且超时要用「距离 deadline 还有多久」，不是每次都等一个完整的 linger——后者在持续小流量下会把批次无限推迟。
    显存和主存不一样
    显存没有 swap，也没有 OOM Killer 帮你挑进程杀，不足时 CUDA 直接返回错误，处理不好就是整个进程崩掉，带走里面几十个正在处理的任务。所以配额要更保守，而且在线/离线各自独立。另外cudaMalloc 是同步的、会隐式同步整个设备，绝不能在热路径上调，必须用显存池。
    最容易被忽略的：回退路径的容量
    nvJPEG 只支持部分 JPEG 变体，PNG/WebP/HEIC 支持也差，加上 GPU 本身会故障。如果按「90% 走 GPU」配 CPU 核数，GPU 一挂，100% 流量涌向 10% 容量的路径，立刻雪崩——为提高性能引入的组件，故障时成了单点。CPU 路径要按「能扛住全量的降级服务水平」来配。
  3. 高级下游变慢，进程被 OOM Killer 杀了，重启之后更快被杀。发生了什么？

    这是一条每一步都「正确」但合起来不收敛的因果链（§9.1）：

    下游变慢 → 队列增长（正常，本该止步于此）→ 队列无界，内存持续上涨 → OOM Killer → 在途任务全部未确认 → 消息队列重投 → 重启后负载 = 原流量 + 全部重投，比崩溃前更高 → 更快被杀。

    三个最直觉的应对都会加速它
    加内存只是把 OOM 推迟几分钟；加机器让每台都走一遍这条链，而且新机器启动时会一起去抢重投的任务；重启是最糟的，因为它直接进入「原流量 + 重投」那一步。
    唯一有效的现场措施
    从入口限流。而如果架构里没有这个开关，现场就只能等它自己烧完。
    根治：链上唯一能斩断它的位置
    「队列增长 → 内存上涨」之间加一个有界。故障就停在「队列变长、上游被拒绝」这个可观测、可告警、可自愈的状态上。这条流水线上有三个必须存在的背压点：领取任务（拉模式而非推模式）、申请解码内存（字节配额）、写回上传（有界队列 + 自适应限速）。共同点是它们都挡在「产生新内存占用」之前。
    监控上的推论
    看在途字节数而不是任务数（「32 个任务在处理」什么也说明不了，「用了 22/24 GB 配额」说明马上要限流）；看配额等待时间的分位数，它比队列长度更早暴露问题；还要注意拒绝率为零不一定是好事，可能说明背压点根本没生效。
  4. 高级一千万张图重刷，任务会重复投递，怎么保证不出错？

    重复是必然的：事件通知是至少一次（ADR-003）、队列重投是至少一次（ADR-001）、断点续跑的游标推进在确认之后（§8.2）。与其消除重复，不如让重复无害。

    「去重」方案的问题
    维护一张「已处理」表：1000 万条，和任务量同量级，而且这张表自己的写入也可能失败——只是把一致性问题往下推了一层。
    真正的幂等：输出由输入唯一决定
    产物路径 = thumb/v{版本}/{哈希前两位}/{内容哈希}/{档位}.jpg。同一张图处理 100 次，产出 100 份逐字节相同、路径也相同的结果——「重复」这件事在下游根本不可观测，不需要任何去重表。去重需要状态，幂等不需要。
    这个 key 里的两个设计
    ① 版本号在路径里：改了缩放算法就是一批新产物，新旧共存、可灰度、可回滚，避免「原地更新」这种危险操作。② 哈希前两位做目录分片：很多对象存储按 key 的字典序前缀划分内部分区，用递增日期前缀会让写入全部集中到一个分区形成热点，表现为写入速率莫名卡住。把高熵的哈希放在路径靠前的位置。
    额外收益
    用内容哈希而不是源 key，同一张图被不同用户重复上传时还能直接命中已有产物。
    这条幂等还打开了另一扇门
    因为重复无害、worker 无状态，离线批可以跑在抢占式实例上，成本降到 20–30%。但要注意抢占往往是成批发生的（同可用区同机型强相关），需要混合部署保底 + 跨机型分散。
