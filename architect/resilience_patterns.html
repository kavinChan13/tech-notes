01

雪崩：把传导过程算出来

「一个慢服务拖垮整条链路」是一句正确但没用的话，要的是数字

1.1 场景与它的五个下游

全篇用一个具体的服务做锚点：电商的下单服务 order-svc。

规模

稳态 8000 QPS，大促峰值 5 万 QPS（6 倍）。部署 40 个实例，每实例 200 个工作线程。SLA：下单成功率 ≥ 99.95%，端到端 P99 < 500 ms。

依赖

一次下单串行调五个下游：库存（20 ms）、优惠券（10 ms）、风控（15 ms）、支付预下单（30 ms）、推荐（非核心，5 ms）。加上本地逻辑，正常单次 50 ms。

生活类比：电路保险丝 + 泄洪闸

家里电流过大时，保险丝会先熔断，牺牲一路电保住整栋楼不着火（熔断）。水库水位过高时，泄洪闸主动放掉一部分水，避免大坝整体溃堤（限流 + 负载脱落）。系统的弹性组件就是这些「主动牺牲局部换取整体存活」的机制——宁可拒绝部分请求，也不要全盘崩溃。

映射：保险丝=熔断 · 泄洪=限流/脱落 · 分区断电=隔离 · 保住整栋楼=系统可用

1.2 下游 RT 涨 100 倍，你的吞吐掉 100 倍

现在库存服务出问题：不报错，只是变慢，RT 从 20 ms 涨到 2000 ms。注意它没有失败——所有请求最终都成功返回，只是慢。很多熔断配置在这种情况下不会触发（§3.2 会说明为什么）。

并发度固定时，吞吐与响应时间成反比——这是 Little's Law 的直接推论（λ = L / W）。

正常：单实例 200 线程 ÷ 0.05 s = 4000 QPS，40 实例 = 16 万 QPS，稳态 8000 QPS 只用了 5% 的容量。
库存变慢后：单次 RT 变成 2030 ms，单实例 200 ÷ 2.03 = 98 QPS，40 实例 = 3940 QPS。

流入 8000 QPS，流出 3940 QPS。本来富余 20 倍的容量，现在连稳态流量的一半都扛不住。

这个算术里有一条容易被忽略的推论：你的容量不是你自己的，它由最慢的那个依赖决定。压测时测出来的「16 万 QPS」是在所有依赖都健康的前提下得到的，它没有告诉你任何关于故障时的信息。而故障时才是你最需要知道容量的时候。

1.3 从变慢到打满，只有两秒

流入 8000/s，流出 3940/s，净积压 4060/s。线程槽位共 8000 个，正常占用约 400 个（8000 QPS × 0.05 s）。
(8000 − 400) / 4060 ≈ 1.9 秒

图里第②段那三行注释是这一节真正想说的：线程耗尽之后，你写的所有降级代码都不会被执行。因为「返回兜底结果」也是一段需要在某个线程上跑的代码，而线程已经没了。同理，熔断器也统计不到样本——请求连进入业务逻辑的机会都没有。

这条推论决定了所有弹性手段的位置：它们必须在「占用稀缺资源之前」生效，而不是在业务逻辑里。限流要在网关或线程分配之前，隔离要在拿到工作线程之前，脱载要在排队之前。一个写在 service 方法开头的「如果过载就返回兜底」，在真正过载时是执行不到的——因为它已经在稀缺资源的下游了。这是很多弹性代码看起来齐全、真出事时却完全没生效的根本原因。

1.4 四类手段各管一段

手段拦在哪一步它防的是它防不了的
限流入口，占用任何资源之前流入超过容量容量本身变小（本例就是）——阈值是按健康时的容量设的
隔离分配资源时一个依赖吃光全部资源被隔离的那个依赖自己的请求还是会失败
熔断调下游之前持续给已经挂了的下游发请求首次故障的那一批（要先攒够样本才跳闸）
降级失败之后失败直接暴露给用户核心链路——核心是不能降的

第一行的「防不了」是本例的关键：静态限流阈值挡不住「容量变小」这种故障。阈值是按 16 万 QPS 的健康容量设的，比如设在 5 万；而故障时真实容量只有 3940，8000 QPS 的正常流量在限流器看来完全合规，一个都不会被拦。这正是 §7 自适应脱载存在的理由。

02

限流：控制入口水位

四种算法的差别不在「精度」，在它们放行突发的方式

2.1 四种算法在同一波突发下的行为

四种算法的教科书描述大家都熟，但那些描述看不出它们真正的差别。把同一波流量（前 900 ms 空闲，第 900 ms 到 1100 ms 之间涌入 200 个请求）喂给四个限流器（都配置成 100 QPS），放行曲线是这样的：

算法突发行为适用别用在
固定窗口窗口交界可放行 2 倍只在乎「一小时内不超过 N 次」这类配额语义保护下游容量——那正是它会击穿的地方
滑动窗口平滑，精度由格数决定需要准确计数的场景（计费、配额）超高频路径（每个 key 要维护 N 个计数器）
漏桶完全不允许突发保护对突发极敏感的下游（老式第三方接口、写数据库）用户交互路径——空闲了很久也不给攒，体验很差
令牌桶允许可控突发绝大多数业务限流下游完全不能接受突发时

2.2 桶容量是个真正的架构参数

令牌桶有两个参数：速率 r 和桶容量 b。几乎所有人都认真设 r，然后把 b 随手设成 r × 1 秒——因为大部分库的默认值就是这样。但 b 的含义完全独立：

r 决定长期平均放行速率；b 决定单次能放行多大的突发。

r = 1000/s、b = 1000：空闲一秒后能瞬间放行 1000 个。如果下游的实际瞬时承受能力只有 300，这一下就打穿了——而限流器会告诉你「没有超限」。
r = 1000/s、b = 200：瞬时最多放 200 个，之后按 1000/s 匀速。长期吞吐一样，但瞬时冲击小 5 倍。

所以 b 的取值依据是下游能吸收的瞬时突发，而不是「一秒的量」。怎么知道下游能吸收多少？看它的队列深度和并发上限——如果下游是 40 个实例 × 200 线程，那么瞬间 8000 个请求它接得住；如果下游是一个连接池只有 50 的数据库，b 就不该超过几十。

另外，限流器本身在热路径上。8000 QPS × 40 实例意味着每秒 8000 次限流判断，如果实现里有一把锁，它就是一个跨核争抢点（同网关篇 §6.4）。令牌桶可以做成完全无锁的：

// 把「令牌数」和「上次补充时刻」打包进一个 64 位原子量，用一次 CAS 同时更新两者。
// 这样限流判断在热路径上没有锁、没有 cache line 上的写写争抢（只有失败重试时才重读）。
class TokenBucket {
  static constexpr int kTokShift = 24;          // 低 24 位放令牌（定点数，×1024）
  alignas(64) std::atomic<uint64_t> state_;      // 高 40 位放毫秒时间戳
  const uint32_t rate_per_ms_, burst_;          // r 与 b，都是定点数

 public:
  bool try_acquire(uint32_t n = 1024) noexcept {
    uint64_t now_ms = coarse_now_ms();   // CLOCK_MONOTONIC_COARSE，比精确时钟便宜一个量级
    uint64_t cur = state_.load(std::memory_order_relaxed);
    for (;;) {
      uint64_t last_ms = cur >> kTokShift;
      uint64_t tokens  = cur & ((1ull << kTokShift) - 1);
      // 按经过的时间补充令牌，但不超过桶容量 —— 这一步就是「b 限制突发」的全部实现
      tokens = std::min<uint64_t>(burst_, tokens + (now_ms - last_ms) * rate_per_ms_);
      if (tokens < n) return false;             // 拒绝路径零副作用，不写共享状态
      uint64_t next = (now_ms << kTokShift) | (tokens - n);
      if (state_.compare_exchange_weak(cur, next, std::memory_order_relaxed))
        return true;
      // CAS 失败说明有并发放行，cur 已被更新为最新值，直接重试
    }
  }
};
coarse_now_ms() 那一行值得注意：CLOCK_MONOTONIC_COARSE 直接读内核维护的一个变量，比 CLOCK_MONOTONIC 便宜一个数量级，精度是一个时钟节拍（通常 1–4 ms）。限流器不需要纳秒精度——毫秒级的补充粒度对 1000 QPS 的速率来说完全够用。在每秒调用上万次的热路径上，选对时钟源本身就是一次可观的优化。

2.3 单机 vs 分布式：三笔代价

本地令牌桶只管本实例，40 个实例各限 200 QPS 才等于全局 8000。问题是流量不均：某个实例被路由到 400 QPS 时它会拒绝一半，而别的实例还闲着。分布式限流（Redis + Lua 原子计数）能做全局配额，但要付三笔代价：

① 延迟

每个请求一次 Redis 往返，同机房约 0.3–1 ms。放进 P99 500 ms 的预算里不算多，但它在每个请求上都发生，而且 Redis 抖动会直接变成业务抖动。

② 新的单点

Redis 挂了，限流怎么办？这必须是一个显式决策（§2.4），不能等到出事时才发现代码里是抛异常。

③ 它自己会成为瓶颈

8000 QPS × 每请求 1 次 = Redis 8000 QPS，还只是这一个限流维度。按用户/租户/接口多维度限流时，请求数是乘出来的。

实践中的解法是两级：本地令牌桶按「全局配额 ÷ 实例数」分配，中心侧每隔几秒根据各实例的实际用量重新分配配额。这样热路径上没有网络调用，全局配额的准确性由低频的校正保证。

两级方案有两个必须处理的边界，它们决定了这套东西能不能真的上线：
① 实例数变化。扩缩容时配额要重分配。如果用「全局 ÷ 当前实例数」，那么滚动升级期间实例数短暂翻倍，每个实例的配额减半，可能误杀正常流量。做法是让中心侧按实际用量而不是实例数分配。
② 长尾实例的配额浪费。如果 39 个实例各用 50 QPS、1 个用 400 QPS，均分配额会让那一个被限死而全局远未达标。做法是允许实例向中心「借」配额，借不到再拒绝。

这两条一加，两级限流就不是「本地桶 + 定时同步」那么简单了。如果流量本来就均匀（前面有一个好的负载均衡），单机限流 + 稍微放宽的阈值往往是更划算的选择。

2.4 限流器自己故障时怎么办

这是分布式限流最容易被跳过的一个设计点，而它是个二选一的决策，没有中间答案：

策略Redis 挂了风险适用
fail-open（放行）限流失效，全部放行如果此时正好有流量洪峰，系统会被打垮绝大多数业务：限流是保护措施，不该比被保护的东西还脆弱
fail-close（拒绝）全部拒绝限流器的可用性直接变成业务的可用性——Redis 一抖，全站 429配额有强合规要求时（计费、外部 API 配额）

推荐 fail-open，但要配一条兜底：中心限流失效时自动退回本地令牌桶，阈值取「全局配额 ÷ 实例数 × 1.5」的宽松值。这样既不会因为限流器故障而拒绝正常流量，也不会完全裸奔。

比 fail-open / fail-close 选错更常见的，是根本没选——代码里 Redis 调用抛异常，异常往上冒，被某个 catch 块捕获后返回 500。于是限流器故障表现为「下单接口大面积 500」，排查时谁也想不到根因在限流器上。任何「保护性组件」都必须显式定义自己故障时的行为，并且写进代码注释和 ADR。
03

熔断：给故障下游喘息

配置里漏掉一项，它在最需要的时候就不会跳闸

3.1 三态状态机

下游持续失败时继续调用有三重浪费：占着自己的线程和连接、给下游雪上加霜、以及让用户等一个注定失败的结果。熔断器的作用是快速失败——不再真正发起调用，直接走降级。

🟢 Closed（关闭）

正常放行，统计失败率与慢调用率。任一超阈值且样本量足够 → 转 Open。

🔴 Open（打开）

直接快速失败（走降级），不调下游。冷却时间到 → 转 Half-Open。

🟡 Half-Open（半开）

并发限制为 N 的探测：连续成功够多 → 回 Closed；任一失败 → 立刻退回 Open。

3.2 慢调用必须计入失败率

回到 §1.2 的场景：库存服务没有失败，它只是从 20 ms 变成了 2000 ms。如果熔断器只统计「抛异常 / 返回错误码」，那么失败率是 0%，熔断器永远不会跳闸——而这恰恰是最危险的一类故障（§1.3 的两秒线程耗尽就是它造成的）。

对比两种故障对上游的伤害：
下游直接报错（RT 5 ms）：单实例吞吐 200 ÷ 0.035 = 5714 QPS。上游资源几乎不受影响，只是业务失败。
下游变慢不报错（RT 2000 ms）：单实例吞吐 98 QPS。上游被拖垮。

「慢」比「错」危险得多，因为「错」会立刻释放资源，「慢」会一直占着。而默认的熔断配置往往只看「错」。

所以熔断器必须有两个独立的触发条件，两者是「或」的关系：

  • 失败率：窗口内失败请求 ÷ 总请求 > 阈值（如 50%）
  • 慢调用率：窗口内 RT 超过「慢调用阈值」的请求占比 > 阈值（如 50%）。慢调用阈值该设多少？不是超时值，而是「明显偏离正常」的值——比如 P99 的 2 倍。本例库存正常 P99 是 50 ms，慢调用阈值设 100 ms，2000 ms 的请求会被全部计为慢。
注意慢调用阈值和超时值是两个不同的数，很容易被混为一谈。超时（比如 500 ms）决定「等多久放弃」，慢调用阈值（100 ms）决定「多慢算不健康」。后者必须明显小于前者，否则熔断器要等到请求超时才认为它慢，而那时资源已经被占了 500 ms——熔断器的响应就晚了 5 倍。

Resilience4j 和 Sentinel 都支持慢调用率，但默认是关闭的。这大概是弹性配置里最值得单独检查的一项。

3.3 错误率怎么统计才对

统计方式行为问题
累计计数（自启动以来）永不遗忘下游恢复后失败率仍然很高，熔断器迟迟回不到 Closed；跑得越久越迟钝
滑动窗口（时间或计数）只看最近 N 秒 / N 次推荐。窗口大小是个取舍：太小容易被抖动误触发，太大反应慢
指数衰减老数据权重递减平滑且省内存，但「失败率 50%」的直观含义没了，调参更靠感觉

最小样本数是另一个必须设的门槛。没有它，凌晨低峰期只有 3 个请求、错了 2 个 = 66% 失败率，熔断器跳闸——而实际上什么事都没有。样本数应该覆盖「一个窗口内的正常请求量」的下界，比如窗口 10 s、低峰 QPS 是 5，那最小样本设 20 就意味着熔断器在低峰期基本不工作（这通常是对的，低峰期本来就不需要保护）。

3.4 三个反模式

① 粒度太粗

整个下游服务共用一个熔断器。库存服务的 /query 慢了，把 /deduct 一起熔断——而后者完全健康。粒度应该到 (服务, 接口)，有分片的话还要到分片：一个分片的慢不该影响其它分片。

② 熔断了但没降级

跳闸后抛 CircuitBreakerOpenException，一路冒到最外层变成 500。用户看到的从「慢」变成「立刻报错」，体验反而更差。熔断的价值在于「省下资源去做兜底」，没有兜底就只剩下省资源。

③ 参数互相矛盾

超时 5 s、统计窗口 10 s、冷却 3 s。慢请求要 5 s 才被计入统计，窗口内攒不够样本；好不容易跳闸，3 s 冷却又到了。结果是熔断器一直在 Closed 和 Half-Open 之间抖动，从没真正保护过什么。

第三个反模式指向一个通用要求：这些参数之间有约束关系，不能各自独立地拍。大致的不等式是 慢调用阈值 < 超时 < 统计窗口 < 冷却时间 × k。§8.2 会把本例的全部参数按这个约束推一遍。

04

降级：优雅退化

大部分降级预案在真实故障时不生效，原因很一致

4.1 先分级，再谈降级

降级的前提是知道什么可以牺牲。没有分级的降级只会变成「出事时临时开会讨论关哪个功能」。把下单链路的五个依赖按「不可用时会怎样」排一遍：

依赖不可用时等级降级策略
支付预下单下单流程走不完L0 核心不可降。它挂了就是下单挂了，只能靠自身高可用
库存可能超卖L0 核心不可降。但可以换实现：主链路挂了走本地预扣库存 + 异步对账（这是容错不是降级）
风控放过一些欺诈订单L1 可有条件降按金额分档：小额放行、大额仍然强依赖。降级不是全有全无
优惠券用户少省了钱L1按原价下单 + 事后补偿。要能解释给用户，不能默默不用券
推荐页面少一个模块L2 随时可降返回静态热门榜，或直接不展示
风控那一行是这张表里最有价值的：降级不必是「用」或「不用」的二选一，它可以是一个连续谱。「小额放行、大额强依赖」把风控从一个 L0 依赖变成了 L1——代价是接受小额欺诈的损失，而这个损失是可以量化并和风控故障的损失作比较的。

很多依赖被标成「核心不可降」，只是因为没人花时间去想「部分降级」的方案。每加一条可降级路径，就少一个能让全站挂掉的单点。

4.2 兜底数据从哪来

降级要返回点什么。三个来源，各有各的过期语义，选错了会从「降级」变成「返回错误数据」：

静态默认值

推荐位返回运营配好的热门榜。永不过期、永远可用，但和用户无关。适合 L2。

本地缓存的上次结果

用上一次成功的响应。个性化保住了，但数据可能很旧——必须带上时间戳并定义「多旧就不能用了」。价格、库存这类不能用旧值。

另一个数据源

主库挂了读从库、实时算不出来读离线表。看起来最完美，但它是一条平时不跑的代码路径——真出事时大概率也是坏的。必须常态化演练（见 A3 那一篇的主题）。

无论用哪种，兜底结果都要带一个标记告诉上游「这是降级数据」。否则前端无法区分「真的没有推荐」和「推荐服务挂了」，监控也无法把降级期间的成功率单独算出来——那段时间的「成功率 99.9%」是假的，因为里面有一半返回的是兜底值。

4.3 降级开关不能依赖会一起挂的东西

最常见的失效方式：降级开关放在配置中心，而配置中心和业务服务在同一个机房、共用同一套网络或注册中心。机房网络出问题 → 业务需要降级 → 但配置中心也连不上，开关推不下去。预案写得再详细也没用。

三条要求，缺一条这套开关在真出事时就是摆设：

  • 本地有兜底副本。配置拉取成功后写本地文件，配置中心不可用时用本地最后一份。启动时也要能只靠本地文件起来——否则配置中心挂了连重启都做不到。
  • 自动降级不依赖开关。熔断触发的降级是本地判断，全程不需要外部输入。手动开关只用于「预判性降级」（大促前主动关掉非核心），是自动降级的补充而不是主路径。
  • 开关的推送路径要和业务流量路径分开。如果开关走的是同一个服务网格、同一个注册中心，那它们会一起挂。
降级开关还要考虑怎么恢复。自动降级应该能自动恢复（熔断器回到 Closed）；手动开关必须有人负责关掉——而「大促结束后忘记关掉降级开关」是个真实且常见的问题，表现为几周后有人发现某个功能一直没生效。给手动开关加一个过期时间，到期自动失效并告警，比依赖流程可靠。
05

隔离：限制爆炸半径

两种隔离方式的差别，在于能不能隔离「慢」

隔离把资源分舱，让一个依赖的故障不耗尽全局资源。回到 §1.2：如果库存调用用的是独立资源池，它变慢只会耗尽它自己那 40 个线程，剩下 160 个线程照常服务其它依赖——整体吞吐从 4000 QPS 降到 3200 QPS，而不是 98 QPS。

生活类比：轮船的水密隔舱

大船船体分成多个水密隔舱：即使一个舱破洞进水，水也被封在这个舱里，其它舱照常浮起，船不沉。系统给每个下游依赖分配独立的资源池：即使「库存服务」变慢占满它自己的池，「优惠券」的池不受影响。

映射：隔舱=独立资源池 · 一舱进水=一个依赖故障 · 船不沉=系统整体存活

5.1 线程池与信号量的本质区别

两种隔离方式经常被并列介绍成「一个重一个轻」，但它们真正的差别只有一条：调用是否在调用方的线程上执行。这一条决定了能不能隔离「慢」。

维度线程池隔离信号量隔离
能否隔离「慢」能——调用方可超时放弃不能——调用方线程被一起卡住
每次调用开销一次线程切换，约 5–10 μs一次原子操作，几十纳秒
上下文传递跨线程，ThreadLocal / trace context / 事务上下文都要手动传同线程，什么都不用管
资源开销每个依赖一个池，N 个依赖 N 组线程一个计数器
适用调用耗时长（> 1 ms）、不可信、可能卡住的远程依赖调用极快（本地缓存、内存计算）且几乎不可能卡住的

判据可以简化成一句：如果这个依赖有可能「卡住而不是失败」，就必须用线程池隔离。本例的五个下游全是远程调用，全都可能卡住，所以核心三个（库存、支付、风控）用独立线程池；推荐是 L2 且可以直接不调，用信号量足够。

在协程 / 异步模型里这个取舍会变形。C++ 协程或 io_uring 下，「等待」不占线程——一个卡住的调用只占一个协程（几 KB），不占执行单元。此时线程池隔离的主要收益消失了，因为信号量隔离已经能达到同样效果（限制并发协程数 + 超时取消）。
所以这条判据的准确表述是：「等待」是否占用稀缺的执行资源。线程模型下占，协程模型下不占。这也是网关篇选 shared-nothing + 协程之后，很多传统弹性手段可以简化的原因。

5.2 隔离要隔干净

只隔离了最显眼的那个资源（通常是线程），剩下任何一个共享资源都足以让两条通道在故障时重新耦合。这类「隔离做了一半」的问题在故障复盘里非常常见，因为它平时完全看不出来。

把所有可能共享的资源列一遍，逐个确认：

共享资源不隔离的后果
工作线程 / 协程最显眼的一个，通常会被隔离
连接池库存和优惠券共用一个 HTTP 连接池，库存把连接占满，优惠券拿不到连接——线程隔离了但连接没隔离
限流令牌 / 熔断器状态共用一个熔断器就是 §3.4 的粒度问题
本地缓存容量一个依赖的结果把缓存挤爆，另一个依赖的命中率暴跌
日志与监控缓冲最隐蔽的一个：故障依赖疯狂打错误日志，日志缓冲写满 → 阻塞所有线程（如果日志是同步的）
DNS 解析 / 名字服务客户端共用一个解析器，一个域名解析慢会拖住所有域名的解析

倒数第二行值得展开：同步日志是一个经常被忽略的全局共享点。下游故障时错误日志量可能涨几十倍，如果日志写入是同步的（或者异步但队列有界且满了会阻塞），那么所有线程都会卡在日志上——一个「隔离得很好」的系统，因为日志而整体挂掉。这也是为什么日志库的队列满时策略（阻塞 / 丢弃 / 采样）是一个弹性设计决策，不只是运维配置。

5.3 什么时候合并反而更好

隔离不是越细越好。把 40 个 worker 拆成 5 组各 8 个，每组只服务一个依赖，会带来一个反效果：统计复用消失了。

排队论里，多服务台共享一个队列的排队时间远小于同样利用率下的独立小队列（M/M/c 对比）。ρ = 85% 时，c = 8 的排队时间约 1.4×S，而 c = 40 只有 0.3×S。
拆成 5 个 8 线程的池，正常情况下的排队时间会比一个 40 线程的池差 4 倍以上——你为了防范故障，牺牲了平时的性能。

所以隔离的粒度是一次明确的取舍，判据是：

  • 这个依赖会不会独立故障？如果五个依赖其实都部署在同一个集群、共享同一个数据库，那它们会一起挂，隔离没有意义。
  • 它们的服务时间分布是否接近？接近就合并（统计复用收益大），差一个数量级就拆（同分级队列）。本例库存 20 ms 和支付 30 ms 接近，推荐 5 ms 差得远。
  • 故障时是否需要保住其中某一个？这是隔离最强的理由——核心与非核心之间必须有墙，哪怕代价是平时慢一点。
06

超时与重试

超时是所有弹性手段的地基，重试是最容易失控的那个

6.1 超时值该由什么决定

常见做法是「下游 P99 × 2 再加点 buffer」。这个做法在单跳时够用，在调用链上是错的，因为它只看了下游，没看上游。

换个角度想：超时的作用是「放弃」，所以它该由「再等下去还有没有意义」决定，而不是由下游的延迟分布决定。

如果上游给你的 deadline 只剩 200 ms，那你给下游设 500 ms 超时毫无意义——上游 200 ms 后就走了，你还在等，白占 300 ms 的资源，而且这些资源产出的结果没有任何人会用。这类「注定被丢弃的工作」在过载时会占掉可观的容量，而且完全不可见。
超时 = min( 上游剩余 deadline − 本地开销 ,   业务能接受的上限 ,   下游 P99 × k )

三项各有各的角色：第一项保证不做无用功，第二项保证用户体验（就算下游很快，某些操作也不该让用户等超过 N 秒），第三项保证不误杀正常的慢请求（k 通常取 2–3）。取三者的最小值，而不是只算第三项。

6.2 deadline 沿链路递减

// deadline 传播的最小实现：一个随请求走的绝对时刻。
// 关键是它必须是「绝对时刻」而不是「剩余毫秒数」—— 后者在每一跳都要重新计算，
// 而网络传输和排队的时间会被漏掉，越往下游误差越大。
class Deadline {
  std::chrono::steady_clock::time_point at_;   // 必须用单调时钟，不能用系统时钟

 public:
  std::chrono::milliseconds remaining() const {
    auto left = at_ - std::chrono::steady_clock::now();
    return std::max(0ms, std::chrono::duration_cast<std::chrono::milliseconds>(left));
  }

  // 调下游前算超时：三项取最小（§6.1）。reserve 是留给「拿到结果后还要做的事」。
  std::chrono::milliseconds budget_for(const DepConfig& d) const {
    auto left = remaining() - d.reserve;
    if (left <= 0ms) return 0ms;         // 已经没预算了，直接走降级，别发这个请求
    return std::min({left, d.max_timeout, d.p99 * d.k});
  }
};

// 调用点：预算为 0 就不发请求 —— 这一行是「不做无用功」的全部实现。
auto budget = deadline.budget_for(kInventory);
if (budget == 0ms) return fallback_inventory();
auto resp = inventory.call(req, budget, deadline);   // deadline 继续往下传
必须用单调时钟（steady_clock / CLOCK_MONOTONIC），不能用系统时钟。如果用 system_clock，一次 NTP 校时把时间往前调 1 秒，所有在途请求的 deadline 会瞬间「已过期」，全部被取消——表现为「某个时刻突然全站超时，几秒后自动恢复，日志里什么异常都没有」。这是分布式系统里最难查的一类问题之一。

6.3 重试与熔断谁包着谁

重试的放大是乘性的、而且恰好在过载时才启动——这部分的算术在容量篇 §6.3，这里只补一个实现层面的细节，它经常被搞反。

重试和熔断的嵌套顺序有两种写法，行为完全不同：

❌ 熔断在外，重试在内

breaker(retry(call))：熔断器只看到「重试三次后的最终结果」。三次调用只统计成一次失败，样本被稀释三倍，熔断器迟迟不跳闸；而且跳闸之前，每个请求都实实在在打了下游三次。

✅ 重试在外，熔断在内

retry(breaker(call))：每次重试都先过熔断器检查。熔断器统计到全部三次调用，跳闸更快；而且一旦跳闸，后续的重试会立刻被熔断器拒绝，重试自动停止——这正是我们想要的。

「重试在外、熔断在内」还有一个不明显的好处：它让重试预算和熔断自动配合。下游轻微抖动时熔断器不跳，重试正常发挥作用（提高成功率）；下游真的挂了熔断器跳闸，重试被立刻掐断（避免放大）。两个机制的边界由熔断器的阈值自动划定，不需要再单独调一套重试开关。

大多数弹性库（Resilience4j、Polly）的装饰器顺序是可配的，而默认顺序不一定是这个。这是一个值得在代码评审里专门看一眼的地方。
07

负载脱落与自适应

§1.4 那个「静态阈值挡不住容量变小」的洞，靠这一章补

7.1 静态阈值一周就过期

限流阈值是按「压测出来的容量」设的，而容量不是一个常数。它随着这些东西一起漂：

什么在变容量怎么变
下游 RT§1.2 已经算过：下游慢 100 倍，容量掉 100 倍。这是最剧烈的一项，而且静态阈值完全感知不到
缓存命中率命中率从 95% 掉到 80%，落库请求翻 4 倍，容量对应下降
请求组成大促时「查询」变「下单」，单请求成本涨几倍
机型与部署密度换机型、同机部署了别的服务、超卖比例变化
代码本身每次发版都可能改变单请求成本，而阈值没人跟着改

所以静态限流只能作为粗粒度的第一道门（挡住明显异常的流量洪峰），真正贴着容量走的保护必须是自适应的——不看流量有多大，看系统自己累不累。

7.2 三种反馈信号，只有一种够快

最后那句是关键：在「下游变慢」这类故障里，CPU 利用率是下降的，因为所有线程都在等 IO。用 CPU 做脱载判据，在最需要它的场景下完全不会触发。

排队时延是最好的信号，这也是 CoDel（Controlled Delay，最初为网络队列设计）的核心思想。它的精髓不是「队列多长」，而是「队列持续拥塞了多久」——短暂的排队是正常的突发吸收，持续的排队才说明容量不足：

// CoDel 式脱载：判据是「排队时延持续超过目标值」，不是「队列长度超过 N」。
// 队列长度的阈值会随扩容失效（同样长度在更大的集群上其实更安全），
// 而排队时延是自归一化的 —— 扩容之后它自然就降下来了，阈值不用改。
class CodelShedder {
  static constexpr auto kTarget   = 20ms;   // 可接受的排队时延
  static constexpr auto kInterval = 100ms;  // 观察窗口：持续这么久才算真拥塞
  TimePoint overload_since_{};                // 空 = 当前不在拥塞状态

 public:
  // 每个请求出队时调用一次。queued 是它在队列里待的时长。
  bool should_shed(Duration queued, TimePoint now) {
    if (queued < kTarget) {
      overload_since_ = {};                  // 一旦有请求等得够短，就认为已恢复
      return false;
    }
    if (overload_since_ == TimePoint{}) {
      overload_since_ = now;                 // 刚进入拥塞，先观察，不急着丢
      return false;                          // ← 这一步让突发不会被误杀
    }
    // 持续拥塞超过一个观察窗口，才开始丢 —— 这就是 CoDel 与「队列超长就丢」的全部区别
    return now - overload_since_ > kInterval;
  }
};

// 丢弃时按优先级从低到高（§7.3），并且要立刻返回明确的「过载」错误码，
// 让调用方能退避 —— 返回 500 会让它当成偶发错误立刻重试，反而放大（§6.3）。
kTarget = 20ms 这个值该怎么定？它不是「用户能忍受的延迟」，而是「排队时延占端到端预算的可接受比例」。本例 P99 预算 500 ms、正常处理 50 ms，留 20 ms 给排队意味着排队占预算的 4%——足够吸收突发，又不至于把预算吃掉。

更重要的是 kInterval：它区分了「突发」和「过载」。没有它，一次 100 ms 的正常流量尖峰就会触发丢弃；有了它，只有持续 100 ms 以上的拥塞才被认定为真过载。这个「先观察一个窗口」的设计，是 CoDel 相比「队列超长就丢」最本质的进步。

另一条路是延迟梯度探测（Netflix concurrency-limits，思路来自 TCP Vegas）：持续测量 RT，逐步提高并发上限，一旦 RT 开始上升就回退。它的好处是能自动找到并发上限而不需要任何阈值；代价是收敛需要时间，且对 RT 抖动敏感。两者可以叠加：梯度探测定并发上限，CoDel 管超出上限之后的丢弃。

7.3 优先级必须在入口就打上

脱载要丢就丢低价值的请求。但「价值」这个信息在哪一层才知道？

常见做法是在业务逻辑里判断优先级。但到那时候资源已经花掉了——请求已经占了线程、已经解析完参数、可能已经查过一次缓存。丢弃它只是止损，不能回收已花的成本。在过载时，这些「花了成本又被丢弃」的请求会占掉相当比例的容量。

正确做法是在入口就把优先级打进请求上下文，依据可以是：调用方身份（内部批量任务 < 普通用户 < VIP）、接口本身（下单 > 查询 > 埋点上报）、以及重试标记（重试请求应当比首次请求优先级更低——它已经失败过一次，而且优先丢重试能天然抑制重试放大）。

最后一条值得单独强调：过载时优先丢弃重试请求，等于把 §6.3 的重试预算变成了一个自适应的机制——系统越忙，重试越容易被丢，放大效应自动收敛。这比配一个固定的重试预算百分比更贴合实际。

脱载和限流的分工要说清，它们不重复：限流在入口按「流量有多大」挡（快、便宜、但不知道系统实际状态）；脱载在服务内按「系统有多累」挡（准、能感知容量变化、但请求已经进来了）。两道都要有——限流挡住明显异常的洪峰，脱载兜住「流量正常但容量变小」这种限流看不见的情况（§1.4）。

8.3 三条 ADR

ADR-001限流用两级（本地令牌桶 + 中心按用量校正），限流器故障时 fail-open 退回本地已接受
背景
峰值 5 万 QPS × 多个限流维度，纯中心式限流会让 Redis 成为瓶颈并在每个请求上加一次往返；纯本地限流在流量不均时会误杀。
决策
热路径只做本地无锁令牌桶（§2.2 的 CAS 实现）；中心侧每 5 s 按各实例实际用量（而非实例数）重新分配配额，并允许实例向中心借用。中心不可用时保持最后一次配额继续本地限流，即 fail-open + 本地兜底。
后果
得到：热路径零网络调用、限流器不会成为新的单点、扩缩容期间不会因实例数突变而误杀。
付出：全局配额是最终一致的，短时间内可能超出配额 10–20%（对保护性限流可接受，对计费类配额不可接受——那种场景必须用中心式 + fail-close）。
ADR-002核心依赖用线程池隔离，L2 依赖用信号量；熔断器粒度到 (服务, 接口)已接受
背景
五个下游全是远程调用，都存在「卡住而不是失败」的可能，而信号量隔离无法隔离「慢」（§5.1）。同时全部用线程池会牺牲统计复用并增加上下文传递成本（§5.3）。
决策
库存 / 支付 / 风控各一个 40 线程的专用池；优惠券与推荐用信号量（它们可以直接跳过，不需要「把线程捞回来」）。熔断器按 (服务, 接口) 建，不共用。连接池与限流令牌一并按依赖隔离，不只隔离线程（§5.2）。
后果
得到：任一核心依赖变慢，影响面限制在它自己的 40 个线程内，整体吞吐从 4000 降到 3200 而不是 98。
付出：三组线程池的排队时间比一个大池差（§5.3 的统计复用损失）；跨线程的 trace context / 事务上下文要显式传递，漏传会导致链路追踪断裂。
何时重议
若服务改造成协程 / 全异步模型，「等待」不再占用执行单元，线程池隔离的主要收益消失，应改回信号量 + 超时取消（§5.1 的提示框）。
ADR-003熔断必须同时启用慢调用率；装饰器顺序为「重试在外、熔断在内」已接受
背景
本系统最危险的故障形态是「下游变慢但不报错」（§1.2），它不会触发只看失败率的熔断器；而重试与熔断的嵌套顺序会决定熔断器能否统计到全部调用、以及跳闸后能否掐断重试（§6.3）。
决策
每个熔断器同时配置失败率与慢调用率两个阈值（「或」关系），慢调用阈值取超时的 2/3（§8.2 验证出来的约束）。装饰器组装顺序固定为 retry(breaker(call))，并在代码评审清单里列为必查项。
后果
得到：「慢而不错」的故障能在 10 秒统计窗口内跳闸；跳闸后重试自动停止，重试放大与熔断的边界由熔断阈值自动划定，不需要另配开关。
付出：慢调用阈值是一个需要随下游性能变化而复核的参数——下游优化变快之后阈值不跟着调，会变得过于敏感而误跳闸。需要纳入定期复核清单。

9.1 什么时候不要用这些模式

模式什么时候不要用为什么
限流 内部调用、单一可信调用方、流量本来就受控 限流的成本是一次判断 + 一份要维护的配置 + 误杀的风险。调用方就一个且它自己有限速时，再加一层只是增加了一个会配错的地方
熔断 ① 下游没有替代方案且没有兜底 ② 调用极低频 ① 熔断只是把「慢慢失败」变成「快速失败」，如果没有兜底，用户体验反而更差
② 低频调用永远攒不够样本，熔断器要么不工作要么误判——不如直接靠超时
重试 非幂等、下游已在过载、错误是确定性的 确定性错误（参数错、鉴权失败）重试一万次也一样；下游过载时重试是火上浇油
隔离 依赖只有一两个、服务时间相近、且会一起故障 会一起挂的依赖之间隔离没有意义；服务时间相近时合并的统计复用收益大于隔离收益（§5.3）
降级 核心链路、以及「兜底数据可能被误当成真实数据」的场景 返回一个旧的库存数或旧的价格，比返回错误更危险——错误会被处理，错误的数据会被信任
最重要的一条反向判据在模式之外：这些手段全都在「用一部分请求的失败，换整体的存活」。如果业务根本不能接受任何请求失败——金融清算、医疗、安全关键控制——那答案不是弹性模式，而是容量冗余 + 排队 + 异步化：把请求先落到一个持久队列里，慢慢处理，永不丢弃，用「延迟上升」代替「部分失败」。

换句话说，弹性模式的适用前提是「快速失败」比「慢慢完成」更可接受。这个前提在交互式业务里成立，在批处理和强一致业务里往往不成立。选模式之前先确认这一条。

9.2 一页速记

🎯 关键结论
  • 先算再配。下游 RT 涨 100 倍，你的吞吐掉 100 倍（Little's Law）；从变慢到线程池打满只有 2 秒——任何依赖人工的预案都来不及。
  • 弹性代码必须在稀缺资源之前。线程耗尽之后，你写的降级逻辑根本没机会执行。
  • 限流：算法决定的是「放行什么形状的突发」，固定窗口会在交界处放行 2 倍；桶容量 b 由下游能吸收的瞬时突发决定，不是「r × 1 秒」。
  • 熔断：必须同时启用慢调用率，否则挡不住「慢而不错」这类最危险的故障；慢调用阈值要小于超时，否则永远不生效。粒度到 (服务, 接口)。
  • 降级：先分级；降级可以是连续谱（风控按金额分档）而非全有全无；开关不能依赖会和业务一起挂的配置中心；给手动开关加过期时间。
  • 隔离：线程池能隔离「慢」，信号量不能——这是两者唯一的本质区别。隔离要把连接池、熔断器、日志缓冲一起隔离，只隔线程等于隔了一半。
  • 超时：三项取小（上游剩余预算、业务上限、下游 P99×k）；deadline 用绝对时刻 + 单调时钟沿链路传播。
  • 重试：retry(breaker(call)) 而不是反过来——熔断跳闸能自动掐断重试。
  • 脱载：用排队时延做信号，不要用 CPU（下游变慢时 CPU 反而是下降的）；CoDel 的精髓是「持续拥塞多久」而不是「队列多长」。优先丢重试请求。
  • 参数要一起推。单看每个值都合理，凑在一起常有一项是死的（§8.2 那个慢调用阈值就是）。

10.1 基础（必答）

  1. 基础一个下游变慢，为什么会拖垮上游？给出量化的解释。

    并发度固定时，吞吐与响应时间成反比——这是 Little's Law 的直接推论 λ = L / W（§1.2）。

    代入算一遍
    上游 40 实例 × 200 线程 = 8000 个并发槽位。正常单次 50 ms → 吞吐 8000 / 0.05 = 16 万 QPS。下游 RT 从 20 ms 涨到 2000 ms，单次变成 2030 ms → 吞吐 8000 / 2.03 = 3940 QPS。流入 8000，流出 3940。
    从变慢到打满有多久
    净积压 4060/s，槽位 8000 个（正常占用 400）→ (8000−400)/4060 ≈ 1.9 秒。这就是为什么弹性必须自动——人工介入的预案在这个时间尺度上完全无效。
    最容易被忽略的推论
    线程耗尽之后，你写的降级代码根本执行不了——「返回兜底结果」也需要一个线程。熔断器也统计不到样本，请求连业务逻辑都进不去。所以弹性手段必须在「占用稀缺资源之前」生效，而不是写在 service 方法开头。
    一句话
    你的容量不是你自己的，它由最慢的那个依赖决定。压测出来的容量只在所有依赖都健康时成立。
  2. 基础令牌桶和漏桶有什么区别？该怎么选？
    漏桶
    请求入桶、恒定速率流出，完全不允许突发。适合保护对突发极敏感的下游（老式第三方接口、直接写库）。缺点是空闲期的容量全部作废——空闲一小时也不给你攒，对交互式业务体验很差。
    令牌桶
    匀速产令牌、取到才放行，允许可控突发（桶里攒的令牌）。绝大多数业务限流用它。
    真正该展开的是桶容量 b
    令牌桶有两个参数：速率 r 和桶容量 b。大部分人认真设 r、把 b 随手设成 r × 1 秒（库的默认值）。但 b 决定的是「单次能放行多大突发」，它的依据是下游能吸收的瞬时冲击，和 r 无关。r=1000/b=1000 意味着空闲一秒后能瞬间放 1000 个；如果下游连接池只有 50，这一下就打穿了，而限流器会告诉你「没超限」。
    顺带提一句固定窗口
    它在窗口交界处可以放行 2 倍配额（第 0.9 s 放 100 个 + 第 1.1 s 放 100 个 = 0.2 s 内 200 个 = 瞬时 1000 QPS）。限流器本身成了突发的制造者——用它保护下游容量是错的。
  3. 基础熔断器的三个状态是什么？半开态要注意什么？

    Closed（正常放行 + 统计）→ 失败率或慢调用率超阈值且样本足够 → Open（全部快速失败，冷却计时）→ 冷却到期 → Half-Open（少量探测）→ 连续成功够多回 Closed，任一失败立刻回 Open 并重新计时。

    半开的关键细节
    那个「少量」必须是并发上限，不是「放 N 个然后关门」。后者会让 N 个请求同时打进去、同时超时——等于在下游刚要恢复时又捶了它一次。正确做法是同时最多 N 个在途，一个回来了才放下一个。
    最小样本数
    没有它，凌晨低峰只有 3 个请求错了 2 个 = 66% 失败率就跳闸了。样本数应覆盖「一个统计窗口内正常请求量」的下界。
    熔断必须配降级
    跳闸后抛异常一路冒到最外层变成 500，用户体验从「慢」变成「立刻报错」，反而更差。熔断的价值是「省下资源去做兜底」，没有兜底就只剩省资源。
  4. 基础为什么重试可能让故障更严重？

    因为放大是乘性的，而且恰好在过载时才启动。三层各重试 3 次 = 27 倍。平时成功率 99.99%，重试量可忽略；一旦下游开始超时，27 倍流量立刻砸下去，把「有点慢」变成「彻底崩」。

    四条约束
    ① 只重试幂等操作；② 指数退避 + 随机抖动（只退避不抖动的话所有客户端永远同相，一个大尖峰变成一串小尖峰，总量没变）；③ 重试预算而不是重试次数（「重试请求 ≤ 总请求的 10%」，过载时自动趋近于零）；④ 只重试可重试的错误（超时、503 可以，400 和业务错误重试一万次也一样）。
    加分：只在最外层重试
    中间层不重试、把失败如实上报，放大从 3ⁿ 变成 3。「每一层都自己重试」通常是无意中形成的——每个团队都觉得自己那层加个重试更稳。

10.2 中级（区分熟练度）

  1. 中级下游只是变慢、没有报错，熔断器为什么不跳闸？

    因为默认的熔断配置只统计失败率，而「慢」不算失败——所有请求最终都成功返回了，失败率是 0%（§3.2）。

    而「慢」比「错」危险得多
    下游直接报错（RT 5 ms）：上游单实例吞吐 200/0.035 = 5714 QPS，资源几乎不受影响。下游变慢不报错（RT 2000 ms）：吞吐 98 QPS，上游被拖垮。「错」会立刻释放资源，「慢」会一直占着。
    解法：慢调用率
    熔断器要有两个独立触发条件，「或」的关系：失败率 > 阈值，或慢调用率（RT 超过慢调用阈值的请求占比）> 阈值。Resilience4j 和 Sentinel 都支持，但默认关闭——这大概是弹性配置里最值得单独检查的一项。
    慢调用阈值怎么定
    它和超时是两个不同的数：超时决定「等多久放弃」，慢调用阈值决定「多慢算不健康」。后者必须明显小于前者（比如取超时的 2/3），否则熔断器要等请求超时才认为它慢，响应就晚了；如果慢调用阈值大于超时，这一项永远不会触发，等于白配。
  2. 中级线程池隔离和信号量隔离，本质区别是什么？

    只有一条：调用是否在调用方的线程上执行。这一条决定了能不能隔离「慢」（§5.1）。

    线程池隔离
    调用在独立线程执行，调用方线程可以超时后放弃，去服务下一个请求。慢被关在专用池里，调用方最多损失一个超时的时间。
    信号量隔离
    调用就在调用方线程上，只是限制了并发数。调用方线程仍然被卡满 2000 ms，无处可去。它省的是「不让更多线程陷进去」，不是「把陷进去的捞出来」。
    代价对比
    线程池每次调用一次线程切换（5–10 μs），而且 ThreadLocal / trace context / 事务上下文都要手动跨线程传递；信号量只是一次原子操作，什么都不用管。
    判据
    这个依赖有没有可能「卡住而不是失败」？有就必须用线程池。远程调用几乎都有可能，所以核心远程依赖用线程池，本地缓存/内存计算用信号量。
    协程模型下这条判据会变形：等待不占执行单元，线程池隔离的主要收益消失，信号量 + 超时取消就够了。准确的表述是「等待是否占用稀缺的执行资源」。
  3. 中级调用链上每一层的超时该怎么设？

    不是「下游 P99 × 2」那么简单——那只看了下游，没看上游。超时的作用是「放弃」，所以它该由「再等下去还有没有意义」决定（§6.1）。

    三项取最小
    超时 = min(上游剩余 deadline − 本地开销, 业务能接受的上限, 下游 P99 × k)。第一项保证不做无用功，第二项保证用户体验，第三项避免误杀正常的慢请求。
    各层独立设固定超时的后果
    网关 500 ms，order-svc 给五个下游各设 300 ms → 最坏 1500 ms，是上游预算的 3 倍。网关 500 ms 就走了，order-svc 还要再干 1000 ms，全是无用功——而且这些请求的监控指标是「成功」，完全看不出来。过载时它们会占掉可观容量。
    deadline 传播的两个实现要点
    ① 传绝对时刻而不是「剩余毫秒数」——后者在每一跳重算，会漏掉网络传输和排队的时间，越往下游误差越大。② 必须用单调时钟（steady_clock）。用系统时钟的话，一次 NTP 校时往前调 1 秒，所有在途请求的 deadline 瞬间「已过期」全部被取消——表现为「某一刻突然全站超时，几秒后自动恢复，日志里什么异常都没有」。
  4. 中级降级方案写得很详细，为什么真出事时没生效？

    三个高频原因，都不是「方案写得不好」：

    ① 降级开关依赖了会一起挂的东西
    开关放在配置中心，而配置中心和业务在同一机房、共用同一套网络或注册中心。机房网络出问题 → 需要降级 → 但开关推不下去。
    要求：本地有兜底副本（且启动时能只靠本地文件起来）、自动降级完全不依赖外部输入、开关推送路径与业务流量路径分开。
    ② 降级代码在稀缺资源的下游
    写在 service 方法里的「如果过载就返回兜底」，在真过载时执行不到——线程已经耗尽了（§1.3）。
    ③ 兜底路径平时不跑
    「主库挂了读从库」「实时算不出来读离线表」看起来最完美，但它是一条平时不执行的代码路径，真出事时大概率也是坏的（依赖变了、数据格式变了、权限过期了）。必须常态化演练。
    还有一个运营层面的
    大促结束后忘记关降级开关，几周后才有人发现某功能一直没生效。给手动开关加过期时间，到期自动失效并告警，比依赖流程可靠。

10.3 高级（体现深度）

  1. 高级限流阈值设了 5 万 QPS，为什么系统在 8000 QPS 时就挂了？

    因为静态限流阈值挡不住「容量变小」这类故障（§1.4、§7.1）。阈值是按健康时的容量（16 万 QPS）设的，而下游变慢后真实容量只有 3940 QPS——8000 QPS 在限流器看来完全合规，一个都不会拦。

    容量会随什么漂
    下游 RT（最剧烈，涨 100 倍容量掉 100 倍）、缓存命中率、请求组成、机型与部署密度、以及每一次发版。压测出来的阈值一周就过期。
    解法：自适应脱载
    不看流量有多大，看系统自己累不累。限流在入口按流量挡（快、便宜、但不知道内部状态），脱载在服务内按饱和度挡（准、能感知容量变化）。两道都要有，它们不重复。
    用什么信号
    排队时延最好：请求一开始等它就动了，而且自归一化（扩容后不用改阈值）。CPU 是最差的信号——它最滞后，而且在「下游变慢」这类故障里 CPU 反而是下降的（线程都在等 IO），用它做判据在最需要的场景下完全不会触发。队列长度居中，但阈值会随扩容失效。
    CoDel 的精髓
    判据是「排队时延持续超过目标值多久」，不是「队列多长」。先观察一个窗口（比如 100 ms）再开始丢，这一步让正常的突发不会被误杀——这是它相比「队列超长就丢」最本质的进步。
  2. 高级重试和熔断，装饰器的嵌套顺序有讲究吗？

    有，而且两种顺序的行为完全不同（§6.3）。

    ❌ 熔断在外，重试在内：breaker(retry(call))
    熔断器只看到「重试三次后的最终结果」，三次调用被统计成一次失败，样本稀释三倍，跳闸慢；而且跳闸之前，每个请求都实实在在打了下游三次。
    ✅ 重试在外，熔断在内：retry(breaker(call))
    每次重试都先过熔断器检查。熔断器统计到全部三次调用，跳闸更快；一旦跳闸，后续重试立刻被熔断器拒绝，重试自动停止。
    不明显的好处
    这个顺序让重试预算和熔断自动配合：下游轻微抖动时熔断器不跳，重试正常发挥作用；下游真挂了熔断器跳闸，重试被立刻掐断。两个机制的边界由熔断阈值自动划定，不需要再单独调一套重试开关。
    实践提醒
    Resilience4j、Polly 这些库的装饰器顺序是可配的，默认顺序不一定是这个。值得在代码评审清单里列为必查项。
  3. 高级每个下游都做了线程池隔离，为什么一个依赖故障还是把整个服务拖垮了？

    因为只隔离了最显眼的那个资源，剩下任何一个共享资源都足以让两条通道在故障时重新耦合（§5.2）。

    要逐个确认的共享资源
    连接池（线程隔离了但共用一个 HTTP 连接池，一个依赖把连接占满）、熔断器状态（共用一个就是粒度问题）、限流令牌、本地缓存容量、DNS 解析器（一个域名解析慢拖住所有域名）。
    最隐蔽的一个：日志
    下游故障时错误日志量可能涨几十倍。如果日志是同步写、或者异步队列有界且满了会阻塞，所有线程会一起卡在日志上——一个「隔离得很好」的系统因为日志整体挂掉。所以日志库的「队列满时策略」（阻塞/丢弃/采样）是一个弹性设计决策，不只是运维配置。
    反过来也要问：是不是隔离过头了
    把 40 个 worker 拆成 5 组各 8 个，统计复用就消失了。ρ=85% 时 c=8 的排队时间约 1.4×S，而 c=40 只有 0.3×S——为了防范故障，牺牲了平时 4 倍的排队性能。
    判据三条：这些依赖会不会独立故障（会一起挂就没必要隔离）、服务时间分布是否接近（接近则合并的复用收益更大）、故障时是否必须保住其中某一个（这是隔离最强的理由）。
  4. 高级这一整套模式，什么时候不该用？

    逐个说完之后，还有一条在所有模式之上的判据。

    逐个的反向判据
    限流：调用方单一且可信时，多一层只是多一个会配错的地方。熔断：下游没有替代也没有兜底时，它只是把「慢慢失败」变成「快速失败」，体验更差；调用极低频时永远攒不够样本。重试：非幂等、确定性错误、下游已过载。隔离：依赖会一起故障、或服务时间相近（合并的统计复用收益更大）。降级：兜底数据可能被当成真实数据时——错误会被处理，错误的数据会被信任。
    最上面那条
    这些手段全都在「用一部分请求的失败，换整体的存活」。如果业务根本不能接受任何请求失败——金融清算、医疗、安全关键控制——那答案不是弹性模式，而是容量冗余 + 持久队列 + 异步化：请求先落盘，慢慢处理，永不丢弃，用「延迟上升」代替「部分失败」。
    所以选模式之前先确认前提
    「快速失败」是不是比「慢慢完成」更可接受？这个前提在交互式业务里成立，在批处理和强一致业务里往往不成立。前提不成立时，这一整篇的模式都是错的工具。
