01

把「几十万设备」翻译成可验证的指标

架构设计的第一步不是画图，是把形容词换成数字

1.1 甲方原话与真实工况

需求方是一家做工业能源管理的公司，原话是这样的：

「我们要做一个设备接入平台，支持几十万台设备同时在线，把数据收上来，也能远程下指令和升级固件。要稳定，不能丢数据。」

这句话里没有一个词是可以直接验证的。「几十万」是 20 万还是 80 万？「同时在线」是保持长连接还是每小时来一次？「不能丢数据」是不能丢遥测还是不能丢计费？这三个问题的答案不同，架构会完全不同——所以在画任何图之前，先做四轮追问，把工况问清楚：

追问答案它改变了什么
设备是市电还是电池供电？两类都有：40 万台市电供电的能源网关，460 万台电池供电的 NB-IoT 传感器决定了要不要保持长连接——这是全篇最大的一个分叉
上报周期与单帧大小？网关 30 s 一帧、约 200 B；传感器 1 h 一帧决定瓶颈是带宽还是每包成本
下行有多少、要多快？控制指令约 500 QPS，端到端 P99 < 2 s；固件 8 MB，一批 5 万台决定下行是走网关还是走旁路
「不能丢」具体指什么？遥测可丢（30 s 后就有下一帧）；告警和计费不能丢决定 QoS 分级与反压时的丢弃策略
第四个答案是最值钱的。「不能丢数据」如果按字面落地，整条上行链路都要做端到端持久化确认，吞吐会被存储的写入速度绑死；而一旦确认「遥测可丢、告警不可丢」，就可以按 topic 分级，让 95% 的流量走廉价路径。把一句形容词拆成两类数据，比任何技术优化都省钱。

1.3 IoT 接入与 IM 网关的四个本质差异

「几十万长连接」这个描述让人第一反应是照抄 IM 网关的架构。这是个陷阱：两者在四个维度上正好相反，而这四个维度恰好决定了线程模型、内存分布和故障形态。

维度IM / 消息推送IoT 设备接入架构后果

消息大小文本 + 富媒体，几 KB 到几十 KB遥测 200 BIoT 的 payload 摊薄不了框架开销，锁与 malloc 直接暴露在热路径上（§6）

第三、四条是 IoT 独有的，而它们都不是「更难的 TCP 问题」，而是客户端行为进了架构设计的范围。设备固件的 sleep(30) 和它的重连退避策略，和服务端的线程模型一样属于这个系统的架构决策——只是那部分代码不在你的仓库里。这一点在 §7.3 会变成一个必须双方协同才能解决的问题。

1.4 范围切分与非目标

回到 §1.1 那个最大的分叉：500 万设备里只有 40 万保持长连接，另外 460 万台电池供电的传感器每小时唤醒一次、用短连接上报完就睡。很容易想当然地认为「都是设备接入，一套网关收了」。算一下就知道不行：

460 万台 ÷ 3600 s = 1278 次新建连接/s，而长连接侧稳态只有 28 次/s。两者的连接建立频率差 45 倍。由于 mTLS 完整握手要花掉约 1.1 ms 服务端 CPU（§8.1），短连接侧光是握手就需要 1.4 个核持续满载，长连接侧只要 0.03 核。

这两侧的成本结构完全不同：长连接侧的钱花在常驻内存上，短连接侧的钱花在连接建立的 CPU 上。混在一个进程里，意味着短连接的握手洪峰会直接抢走长连接的上行处理时间，而且两者的扩容依据（内存 vs CPU）互相打架，没法定一个统一的副本数。所以第一条架构决策在画图之前就产生了：两侧分开部署，各自独立扩缩。

本文范围

40 万长连接侧：接入层选型、线程模型、每连接预算、弱网活性判定、握手预算、上下行链路、滚动升级。这一侧的难点是规模与常驻资源。

明确的非目标

460 万短连接摄取侧只给判据不展开：它应该做的是 PSK / 会话票据优先、DTLS + Connection ID 保持身份、以及按到达率而不是连接数扩缩。难点是握手成本与突发，是另一篇的题目。

另外三件明确不做的事，写进文档是为了让后来者知道这不是遗漏：设备固件不在本文范围（但它的退避策略是本架构的前提，见 §7.3）；规则引擎与业务计算不放在网关里（网关必须保持薄，理由见 §12.4）；不追求强一致——本文所有决策都建立在「最终一致 + 可重试」之上，这个前提在 §10.1 会被显式用到。

02

C4 视图：连接与会话必须分开

整篇文章只有一个结构性洞见，就在这一章

这一章用 C4 模型的前两层画出系统。架构方法论 · 第 2 章讲了 C4 的记法和它为什么胜过 UML，这里不重复，直接用；要留意的是第三小节那个切分——它决定了后面从线程模型到滚动升级的所有事情。

2.1 Level 1 · 系统上下文

Level 1 只回答一个问题：这个系统和谁打交道，边界在哪里。画它的价值在于暴露那些「本来以为不用管」的外部依赖——比如运营商的 NAT 超时，它不是我们的组件，但它会直接决定我们的心跳周期（§7.2）。

很多 Level 1 图会把「运营商网络」省掉，理由是「那是网络，不是系统组件」。但它是这个架构里唯一我们无法配置、又会单方面终止连接的参与者，它的空闲回收时间是心跳周期的硬上界。凡是能单方面改变系统状态、又不受我们控制的东西，都必须画进 Level 1。

2.2 Level 2 · 容器分解

Level 2 把平台内部拆开。这里的分解原则不是按业务功能，而是按「变化频率 × 资源画像」：变化频率不同的东西要能独立发布，资源画像不同的东西要能独立扩缩。网关是最难发布的（一次重启动 30 万连接），所以它必须最薄、变得最少。

值得单独说的是「网关最薄」这条原则的具体尺度。网关只做四件事：TLS 终止、MQTT 编解码、活性维护、以及把上行转成 Kafka 消息。规则判断、告警阈值、数据转换一律不放进来。理由不是分层洁癖，而是发布成本——业务规则每周都改，网关重启一次要付 30 万连接重连的代价（§11.1）。发布代价越高的组件，允许它承载的变化就越少，这是一条可以量化的分层依据，比「高内聚低耦合」有用得多。

2.3 为什么「连接」和「会话」是两个概念

朴素实现里，一个设备就是一个 TCP 连接上的一个对象，设备在线等于连接存在。这个等价关系在 40 万规模下会连着崩三次，所以要提前把它拆开：

崩塌一 · 半开连接

设备断电了但 TCP 不知道（§7.1），连接对象还在，控制台显示在线。指令投过去、进了内核发送缓冲、write 返回成功，业务以为下发成功了。连接存在 ≠ 设备在线。

崩塌二 · 重连期间

设备换基站，断开后 3 s 重连。这 3 s 里它的会话应该还在（MQTT 有 clean_session=false 的语义），订阅关系、QoS1 待确认消息都得保留。连接消失 ≠ 会话结束。

崩塌三 · 网关重启

网关实例升级，连接全断。如果会话状态只活在这个进程里，30 万台设备的订阅关系和在途消息就一起丢了。会话不能和进程同生命周期。

拆开之后，三个概念各有归属，而且各自的一致性要求完全不同——这是后面能做出很多简化的根本原因：

概念住在哪生命周期一致性要求
连接（fd + TLS + 缓冲）网关某个实例的某个核，独占一次 TCP 连接不需要——它就是本地状态，进程没了它也该没
会话（订阅、在途消息、clean_session）会话注册中心 + 设备影子跨多次连接，按 MQTT 语义过期最终一致足够：寻址错了就重试（§10.1）
设备（身份、证书、影子状态）设备台账 + 影子服务设备的整个生命周期证书吊销要强一致（§8.4），影子状态最终一致
这张表最有用的一列是最右边。因为「连接」不需要任何一致性保证，网关才可以是完全无状态、可随意重启的；也正因为「会话」只要最终一致，会话注册中心才可以用一个分片的 Redis 而不是 Raft 集群（一致性模型对比）。先把状态按一致性要求分类，再选存储——顺序反过来就会出现「用 etcd 存 30 万连接的心跳时间」这种把强一致用在不需要的地方、然后被写入吞吐打死的设计。

「活性」这个概念也随之落地：设备在线与否不看连接是否存在，而看最近一次收到字节的时间。这个判定住在网关的时间轮里（§6.2），并且周期性地把结果同步到影子服务。§7.2 会给出这个时间窗口必须满足的不等式。

03

接入层：长连接的负载均衡是一次性的

第一个反直觉的地方：两种主流均衡策略在这里都是错的

3.1 四个候选

设备要先找到某个网关实例。这一步的候选方案在无状态 HTTP 服务里几乎不用思考——挂个 L7 网关就完事——但长连接把它变成了一个真问题。四个候选：

方案每连接开销能否感知连接数致命问题
Kubernetes Service + kube-proxy1 条 conntrack ≈ 0.3 KB，30 万连接 = 90 KB 表项 × 转发路径数否nf_conntrack 表满后静默丢包，且 SNAT 掉源 IP（§3.3）
L7 代理（Envoy / Nginx stream）代理侧再开一条连接 + 一份缓冲，内存与握手成本翻倍是，可做加权与慢启动TLS 要么在代理终止（网关拿不到设备证书身份），要么透传（代理白付一份连接成本）
L4 DSR（LVS DR / ECMP）只有入向经过，回包直接走，几乎为零否（需要控制面补）只能按四元组哈希，不感知负载；配置复杂
DNS 多 A 记录 + 设备侧选择零否缓存 TTL 不可控，摘除一个实例要等几分钟到几小时，故障切换太慢

先看一眼 L7 那一行的代价，因为它是最容易被默认选中的方案。如果在 Envoy 终止 TLS，网关就拿不到设备证书里的身份，而这个身份是本系统的授权依据（哪台设备能发哪个 topic）；要透传身份就得靠 PROXY protocol 或者把证书指纹塞进 header，等于把安全边界搬到了代理上。如果改成 TCP 透传，代理只是个搬运工，却要为 30 万连接各维护一条上游连接和一份缓冲——按 §5 的预算，那是又一个 3 GB 和又一份 fd 上限问题。为长连接付两次连接成本，是这一层最典型的浪费。

3.2 均衡了新建，不等于均衡了负载

真正的反直觉在这里。短连接服务里「负载均衡」和「流量均衡」是同一件事，因为连接活不过一个请求；长连接里一条连接能活好几天，于是负载均衡器只能均衡「新建连接」这个导数，它对存量无能为力。两种最常用的策略在这个前提下各错一半：

轮询（round-robin）：新实例永远补不齐

实例 C 重启后连接数归零，但轮询只会把新建连接的三分之一给它。稳态新建才 28 次/s，要补上 10 万连接的缺口需要 100000 / (28/3) ≈ 3 小时。这三个小时里 A、B 各多背 5 万连接。

最少连接（least-conn）：新实例被瞬间打爆

反过来，least-conn 会把所有新建连接都送给刚重启的 C，直到它追平。如果此时正赶上一次重连洪峰（§7.3），5000 次/s 全砸在一个实例上——它需要 5.6 个核纯做握手（§8.1），远超单实例预算，于是握手排队、设备超时、继续重试。

可行的做法是两个手段合起来用，缺一个都不行：

一、新实例慢启动。让实例在上线后的一段时间内以递增的权重接收新连接（Envoy 的 slow_start_config、LVS 的加权轮询配合控制面调权），把 least-conn 的尖峰削成斜坡。这解决了「被打爆」，但没解决「追平太慢」。

二、主动再平衡。既然均衡器只能作用于新建，那就人为制造新建：网关周期性（每 30 s）向控制面上报自己的连接数，控制面算出偏离目标水位最多的实例，通知它按限定速率主动断开一小批连接。设备重连时会被均衡器分到别处，缺口就补上了。

关键在于「主动断开」怎么断才不伤设备。MQTT 5.0 为此专门提供了机制：服务端发 DISCONNECT 时带上 reason code 0x9C (Use another server) 加 Server Reference 属性，设备收到后立即重连并且不触发退避——它知道这是一次调度，不是故障。MQTT 3.1.1 没有这个字段，只能直接关连接，设备会走退避逻辑（这就是 §12.3 里推动设备升级协议版本的实际动机）。

再平衡的速率不能拍脑袋，它必须小于集群剩余的握手能力。每一次主动断开都会换来一次完整 mTLS 握手（约 1.1 ms CPU），而这笔 CPU 是从上行处理里抢的。§11.3 会把这个速率算出来，滚动升级用的是同一个公式——再平衡和优雅下线在物理上是同一件事，只是触发原因不同。

04

线程模型：shared-nothing 与它的代价

选一个模型很容易，说清楚它让你付出了什么才是架构工作

4.1 三个候选与判据

网关内部怎么用 32 个物理核，有三种成熟做法。异步网络编程指南 · 第 6 章讲了它们在 Asio 里的写法与 strand 的语义，这里只讨论选型：

4.2 为什么 IoT 场景选每核一份

选 B 的理由完全来自 §1.2 的两个数字：消息小（200 B）、消息多（1.33 万/s，峰值 12 万/s）。这个组合让方案 A 的共享队列锁变成了主要成本：

处理一帧 200 B 的 MQTT PUBLISH，实际业务工作量大约是几百纳秒（解析固定头 + 变长头 + 拷贝 payload + 一次 topic 查表）。而一次跨核的锁竞争，只要发生实际争用，光是 cache line 在核之间迁移就要 100–200 ns 量级。当单条消息的处理时间和一次锁争用的时间是同一个数量级时，锁不再是「开销」，它是主要成本。

换个角度看同一件事：如果消息是 64 KB（比如 IM 的图片消息），处理一条要几十微秒，那么 200 ns 的锁开销占比不到 1%，方案 A 完全够用，还省下跨核下发的全部复杂度。所以「选哪个线程模型」的答案不是某个模型更先进，而是取决于单条消息的处理时间和一次锁争用时间的比值。这个比值越接近 1，越要往 shared-nothing 走。

第二个理由是内存局部性。方案 B 里每个核独占约 1 万个连接（30 万 ÷ 32），Session 对象被压到 64 B（§5.3）后，这 1 万个 Session 一共 640 KB——正好落在单核 L2（通常 1–2 MB）的量级里。整个核的工作集常驻自己的 L2，不和别的核共享任何可写数据，这是方案 A 无论怎么优化都做不到的。

没选方案 C 的理由要说清楚，因为它其实很接近：主从 Reactor 天然解决了 §3.2 的存量倾斜，而且把握手集中到主线程便于限速。但它的主线程是单点——按 §8.1，一次 mTLS 握手要 1.1 ms CPU，单线程做握手的上限是 900 次/s，而 §7.3 的重连洪峰要求 5000 次/s。所以 C 的主线程必须扩成一个线程池，扩完之后它和 B 的区别就只剩「分配由用户态决定还是内核决定」了。最终的方案其实是 B 加上 C 的握手池：内核负责分流已建立的连接，独立的握手线程池负责建立过程（§8.2）。

4.3 代价：跨核下发

shared-nothing 的账单在这里。控制面下发一条指令，HTTP 请求落在核 A 的线程上，而目标设备的连接在核 B 上——而且核 B 上的连接只能由核 B 自己碰，这是这个模型的立身之本，不能破。于是必须有一条跨核通道。

为什么不直接用 asio::post(other_ctx, handler)？它能工作，但有三个问题：队列无界（下游变慢时会一直堆到 OOM，背压彻底消失）、每次 post 都要把 handler 装进 std::function 从而一次堆分配、以及每次 post 都会无条件唤醒目标 io_context。第三点在 OTA 通知这种批量下发场景下最致命：给 5 万台设备发通知会产生 5 万次 write(eventfd) 系统调用和 5 万次线程唤醒。

自己写这条通道，核心是三十行：

// 跨核只传 POD：拿到 slot 后由目标核自己去查 Session，指针和引用计数都不过界
struct Mail {
  uint32_t slot;      // Session 在目标核槽位数组里的下标
  uint32_t gen;       // 槽位代号，防 ABA：槽被复用后 gen 不同，投递自然失效
  uint32_t cmd_id;    // 指令在下行池里的编号，payload 不进队列
  uint32_t deadline_ms;
};
static_assert(sizeof(Mail) == 16 && alignof(Mail) == 4);

class CoreMailbox {
  static constexpr uint32_t kCap = 8192;              // 2 的幂，取模变位与
  Mail ring_[kCap];
  alignas(64) std::atomic<uint32_t> head_{0};        // 多生产者在这里 CAS
  alignas(64) std::atomic<uint32_t> tail_{0};        // 单消费者独占，和 head 分开 line
  alignas(64) std::atomic<bool>     armed_{false};   // 唤醒信号是否已在途
  int evfd_;                                             // 注册在目标核的 epoll 上

 public:
  // 任意核可调。返回 false = 队列满 —— 这就是背压点，调用方要如实告诉上游「设备忙」
  bool post(const Mail& m) noexcept {
    uint32_t h = head_.load(std::memory_order_relaxed);
    do {
      if (h - tail_.load(std::memory_order_acquire) >= kCap) return false;
    } while (!head_.compare_exchange_weak(h, h + 1, std::memory_order_relaxed));
    ring_[h & (kCap - 1)] = m;
    std::atomic_thread_fence(std::memory_order_release);

    // 关键：唤醒信号聚合。只有第一个让队列从空变非空的人才写 eventfd，
    // 后面 8000 条搭同一趟车 —— 5 万台设备的 OTA 通知可能只产生几十次系统调用。
    if (!armed_.exchange(true, std::memory_order_acq_rel)) {
      uint64_t one = 1;
      ::write(evfd_, &one, sizeof one);
    }
    return true;
  }

  // 只有目标核会调。先解除 armed 再排空，顺序反了会漏掉排空后新入队的消息。
  template <class F> void drain(F&& fn) {
    uint64_t sink;
    ::read(evfd_, &sink, sizeof sink);
    armed_.store(false, std::memory_order_release);
    uint32_t t = tail_.load(std::memory_order_relaxed);
    for (uint32_t h = head_.load(std::memory_order_acquire); t != h; ++t)
      fn(ring_[t & (kCap - 1)]);
    tail_.store(t, std::memory_order_release);
  }
};
drain() 里「先清 armed_ 再读 head_」的顺序不能颠倒。如果先排空再清标志，那么在排空之后、清标志之前入队的消息，其生产者会看到 armed_ == true 而不写 eventfd，这条消息就永远躺在队列里等下一次唤醒——表现是「偶尔有指令延迟几十秒才到」，而且只在高并发下发时出现。这类唤醒丢失是自建通道最经典的 bug，无界队列（比如 asio::post）不会有，因为它每次都无条件唤醒。做聚合唤醒就必须付出这份小心。

队列满的时候必须如实向上返回失败，而不是阻塞等待或者扩容。这是整条下行链路唯一的背压点：post() 返回 false，控制面 API 就给调用方返回「设备忙，请重试」。如果这里选择阻塞，HTTP 线程会被拖住，压力就传到了控制面的连接池上，最终以一个完全无关的形态（API 超时）暴露出来。限流与水位讲的是同一个道理：背压点要设在压力产生的地方，而不是让它往上游漂。

4.4 SO_REUSEPORT 的两个坑

方案 B 依赖 SO_REUSEPORT 让内核按四元组哈希把新连接分给某个核的监听 socket。它省掉了用户态的分发逻辑，但有两个必须知道的行为：

坑一：加入或退出监听组会重排哈希桶。内核在 reuseport 组里按 hash % group_size 选 socket。当一个 worker 线程关闭它的监听 socket（比如线程崩溃重启、或者优雅下线时逐个关闭），group_size 变化，已经在 SYN 队列里、握手还没完成的连接可能被重新哈希到另一个 socket，导致这些 SYN 被丢弃，设备侧表现为连接超时。Linux 4.5+ 提供 SO_ATTACH_REUSEPORT_EBPF 让你自己决定分发逻辑，可以做到一致性哈希式的平滑变更；如果不想上 eBPF，工程上的做法是监听 socket 的数量在进程生命周期内固定不变——worker 线程可以退出，但它的监听 socket 交给别人接管，绝不关闭。

坑二：分布不会自愈。内核按四元组哈希，长期看新建连接是均匀的，但它不看每个 socket 现有的连接数。§3.2 的存量倾斜在核之间同样存在：某个核上的连接恰好断得少，它就一直比别人多。核间倾斜比实例间倾斜危害小（同一台机器，内存是共享的），但它会造成尾延迟——那个核的时间轮扫描更慢、上行队列更长。做法和 §3.2 一致：把「主动断连再平衡」的粒度做到核级别，让偏离最多的核先断。

5.2 37 GB → 3 GB：省下来的全在用户态

这张表最值得记住的结论和大多数人的直觉相反。「单机几十万连接」这个话题下最常见的建议是调内核参数——tcp_rmem、tcp_mem、somaxconn——但从表里能看到，内核那两行加起来只有 0.75 GB，而且基本不可压缩。34 GB 的节省全部来自我们自己写的代码。

之所以会有「调内核就能省内存」的错觉，是因为一个普遍的误解：以为 net.ipv4.tcp_rmem 的默认值（常见 128 KB）是每条连接预留的内存。它不是。这三个数字是「最小 / 初始目标 / 上限」，内核的收发队列是按实际排队的数据量动态分配 sk_buff 的；一条空闲连接的内核侧常驻只有 struct sock 和 tcp_sock 那约 2.3 KB。

这不代表 tcp_rmem 无关紧要——它决定的是上限，也就是「一条连接最坏能吃掉多少内核内存」。在 IoT 场景下，单帧 200 B、设备也不会一次灌几十 KB，所以把 SO_RCVBUF 显式设成 8 KB 是合理的：它不省常态内存，但把异常场景的爆炸半径从 30 万 × 128 KB（38 GB，足以打死整台机器）压到 30 万 × 8 KB（2.4 GB）。调内核缓冲不是为了省内存，是为了封住最坏情况。

反过来，用户态那 33.6 GB 是怎么一步步申请出来的？两行代码而已：一个 char rbuf[64 * 1024] 放在 Session 里，一个默认配置的 SSL_new()。

OpenSSL 这一笔尤其容易漏。TLS record 的最大长度是 16 KB，所以 OpenSSL 默认给每个 SSL 对象准备了一个 16 KB 的读缓冲和一个 16 KB 的写缓冲，加上会话状态、密钥材料、握手残留，实测常驻在 35–45 KB。对 40 万连接来说这就是 12 GB——比业务数据本身大四个数量级（业务侧其实只有 200 B/帧）。两个对策：

  • SSL_CTX_set_mode(ctx, SSL_MODE_RELEASE_BUFFERS)：让 OpenSSL 在 record 处理完、连接空闲时释放这两个大缓冲，下次用到再分配。IoT 场景下连接 99.9% 的时间是空闲的，这个 mode 几乎白拿。
  • SSL_CTX_set_max_send_fragment(ctx, 2048)：把发送 record 上限从 16 KB 降到 2 KB。下行指令本来就只有几百字节，用不到大 record；代价是发大块数据（比如 OTA，如果它真的走网关）时会分成更多 record，多几次加密调用——而 OTA 已经被 ADR-004 挪出网关了，所以这个代价是零。
注意最后那半句：max_send_fragment 之所以能放心调小，是因为另一个决策（OTA 走旁路）已经把大块下行从网关拿走了。这是架构决策之间典型的相互支撑——单看任何一个决策都会觉得「太激进」，放在一起才成立。ADR 的价值就在这里：它把「这个决策依赖哪些其它决策」写下来，否则半年后有人为了图省事把 OTA 挪回网关，这个 2 KB 的 record 就会变成一个查不出来的性能问题。

5.4 收发缓冲不能常驻

那个 char rbuf[64 * 1024] 是 19.2 GB 的来源。它之所以会被写出来，是因为它让代码变简单：读缓冲和连接同生命周期，不用管释放。但仔细想一下这块内存的使用率：连接 99.9% 的时间在等下一帧，缓冲区里什么都没有。30 万条连接同时有数据在读缓冲里的概率接近零。

正确的做法是把读缓冲从「per-connection 常驻」改成「per-core 池化，借用即还」：

读缓冲 · 借用即还

每个核持有一小组 16 KB 的缓冲块（比如 64 块 = 1 MB）。epoll 报告可读时从池里借一块，read() → 解析 → 处理完立刻归还。因为是 shared-nothing，这个池不需要任何同步，借还就是一次数组下标操作。

池子要多大？由「同一轮 epoll 事件里最多有多少连接可读」决定，而不是连接总数。epoll_wait 的 maxevents 设成 512，池子给 512 块就绝对够，实际远用不满。

写缓冲 · 按需 + 水位

下行只有 500 QPS，稳态下有在途数据的连接不到 200 条。所以写缓冲应该是 WBuf* wbuf 这个指针——为 nullptr 时说明这条连接没有待发数据，一个字节都不占。

真正要设计的是水位：单连接待发数据超过 256 KB 说明设备收不动了（弱网或已经半死）。此时不能无限缓存，必须选一个策略：丢弃低优先级下行、或者直接断开这条连接让它重连（§7.1 的半开连接就是这么被发现的）。

「写缓冲无上限」是长连接服务里最常见的 OOM 原因，而且它的表现极具欺骗性：内存曲线平时非常平稳，某天某个区域网络劣化，几万台设备同时收不动，写缓冲在几十秒内涨到几十 GB，进程被 OOM Killer 杀掉。然后这几十万连接重连、可能又落到同一批实例上、又收不动——一次网络劣化变成了一次雪崩。水位和丢弃策略不是优化项，它是这条链路的保险丝。

C++ 侧真正会咬人的四个点

四个都是「代码完全正确、在一千连接下完美工作」的东西

这一章的四个问题有一个共同特征：它们在开发和测试环境（几千连接）下完全看不出来，压测到十万量级才会出现，而且症状都是「CPU 高但看不出高在哪」。这也是为什么它们必须在架构阶段就被决定，而不是留给后期优化。

6.1 shared_ptr 的引用计数会在核之间弹跳

std::shared_ptr<Session> 是管理连接生命周期的标准答案：异步回调里持有它，就不用担心回调执行时对象已经被销毁。问题在于它的引用计数是一个原子变量，而原子变量的成本完全取决于有几个核在碰它。

值得强调的是：问题不是「原子操作慢」。一个只被单核访问的原子自增，cache line 一直在本核的 L1 里，成本约几个周期，可以忽略。真正贵的是争用——多个核轮流写同一条 line，每次都要把这条 line 从别人的 L1 里抢过来（RFO），跨 socket 时更要走内存或 UPI。shared_ptr 的复制在异步代码里极其频繁（每次 async_read 捕获一次、每次 post 一次），于是这条 line 就在核之间持续弹跳。

§4.2 选了 shared-nothing，所以有一个比「优化 shared_ptr」更彻底的答案：让它从热路径上消失。Session 住在本核的槽位数组里（§5.3），生命周期由本核独占管理，回调里传的是裸引用；其它核想碰这条连接只能投递 (slot, gen) 弱句柄（§4.3）。这套设计一次解决了四个问题：

  • 引用计数争抢：不存在引用计数了。
  • 跨核生命周期竞争：只有一个核能销毁 Session，不需要任何同步。
  • ABA：槽位被复用后 gen 递增，迟到的投递会因为 gen 不匹配被丢掉——这正是 weak_ptr 想解决的问题，但代价是 8 字节整数比较而不是原子加载。
  • 缓存局部性：槽位数组连续，遍历（比如时间轮扫描）是顺序访问，硬件预取器能派上用场。
这是本文里最典型的一次「架构决策消除了一类实现难题」。如果线程模型选了共享（§4.1 方案 A），那么 shared_ptr、strand、weak_ptr 提升、生命周期竞态就全都是必修课，每一项都要小心处理；一旦选了 shared-nothing，它们中的大部分不是被优化了，而是被定义掉了。这也解释了为什么 §4 那一章要花那么多篇幅在选型上——选错模型，后面每一章都会变难。

要付的代价也要说清楚：裸指针 + 槽位索引意味着编译器不再替你检查生命周期。工程上必须靠约定顶住：跨核消息里永远只有 (slot, gen)、任何函数签名里出现 Session& 就意味着「调用者保证在本核执行」、并且用一个 debug 模式下的断言检查当前线程 ID 是否等于该核的 owner。这类「靠约定而非类型系统保证」的设计，必须在 ADR 里写明，并且在代码里放断言，否则半年后一定会有人从另一个线程直接调它。

6.2 三十万个定时器

MQTT 的 keepalive 要求：如果在 1.5 倍 keepalive 周期内没收到设备的任何报文，服务端应当关闭连接。朴素实现是每个 Session 一个 asio::steady_timer，收到数据就 cancel() 再 expires_after() 重新武装。

io_context 的定时器队列是一个堆，插入和取消都是 O(log n)。n = 30 万时 log₂n ≈ 18 次比较，每次比较可能是一次 cache miss（堆节点分散在堆内存里）。
而「重置心跳」的频率不是每 45 秒一次，是每收到一帧就一次：1.33 万 msg/s × (1 次 cancel + 1 次 rearm) = 2.7 万次 O(log 30万) 堆操作/秒，峰值时 24 万次/秒。再加上每次 async_wait 一个 handler 的堆分配（§6.3）。

时间轮把这件事变成 O(1)。它的可行性来自一个业务事实：MQTT keepalive 的判定本来就允许 1.5 倍宽限，所以 ±1 秒的精度损失完全无害。用精度换复杂度，前提是业务允许——这是架构判断，不是优化技巧。

class TimerWheel {
  static constexpr uint32_t kSlots = 128;   // 2 的幂 → 取模变位与；128 s > R = 75 s
  IntrusiveList slots_[kSlots];             // 链表节点就是 Session 自己，零分配
  uint32_t now_slot_ = 0;

 public:
  // 收到任何一个字节都会调它：把 Session 从旧槽摘下，挂到 (now + timeout) 槽。
  void touch(Session& s) noexcept {
    slots_[s.wheel_slot].erase(s);                                  // O(1)
    s.wheel_slot = (now_slot_ + s.keepalive_sec * 3 / 2) & (kSlots - 1);
    slots_[s.wheel_slot].push_back(s);                              // O(1)
  }

  // 每秒调一次：只扫一个槽，链表里剩下的就是超时的。
  template <class F> void tick(F&& on_timeout) {
    now_slot_ = (now_slot_ + 1) & (kSlots - 1);
    // 先把整条链摘下来再逐个回调：on_timeout 会关连接，从而 erase 自己，
    // 边遍历边删会踩到已失效的 next 指针。
    IntrusiveList expired;
    expired.splice(slots_[now_slot_]);
    while (Session* s = expired.pop_front()) on_timeout(*s);
  }
};
keepalive_sec * 3 / 2 有可能超过 128：MQTT 允许 keepalive 最大 65535 秒。设备如果协商了一个很长的 keepalive，槽号回绕后会被提前判超时。两种处理：在 CONNECT 时就把 keepalive 钳制到协议允许的范围内（服务端可以在 CONNACK 里回一个更小的值，MQTT 5.0 的 Server Keep Alive 属性专门干这个），或者做成分层时间轮（秒轮 + 分钟轮）。前者更简单，而且对 IoT 来说钳制 keepalive 本来就是必要的——§7.2 会说明为什么心跳周期不能由设备单方面决定。

6.3 handler 热路径上的堆分配

异步框架的每一个 async_read(sock, buf, handler) 都要把 handler 存到某个地方，等 IO 完成后再取出来执行。Asio 通过 associated_allocator 拿分配器，默认走 operator new。于是每一帧消息至少一次 malloc + 一次 free；如果代码里还用了 std::function 包装回调，捕获超出小对象优化容量时又是一次。

1.33 万 msg/s 下这是 2.7 万次/s 的分配，峰值 24 万次/s。tcmalloc/jemalloc 的小对象分配在 thread cache 命中时只有几十纳秒，听起来不多，但要注意它落在200 ns 的处理预算里，而且 malloc 的元数据访问会污染刚才好不容易攒下的 cache 局部性。三档对策，按侵入性排序：

6.4 伪共享：一个计数器吃掉一成吞吐

最后一个是最隐蔽的，因为它的代码看起来完全无害：

为了做监控，我们需要统计每秒处理了多少条消息。自然的写法是一个全局 std::atomic<uint64_t> g_msg_count，每处理一帧自增一次。在 32 个核上，这意味着同一条 cache line 每秒被 32 个核抢 1.33 万次（峰值 12 万次）。每次抢夺都是一次 RFO，跨 NUMA socket 时更贵。实测中这样一个计数器吃掉 10% 以上吞吐是常事，而且 perf top 只会告诉你「时间花在那条 lock add 指令上」，不会告诉你原因是争用。

对策是 per-core 计数，采集时求和。真正需要注意的是三个细节：

  • 对齐的对象是数组元素，不是数组。uint64_t counters[64] 会把 8 个计数器塞进一条 line，问题一点没解决。要写 struct alignas(64) Counter { uint64_t v; }; Counter counters[64];。
  • 数组的邻居也会伪共享。如果这个数组是某个结构体的成员，它前后的成员可能和第一个/最后一个计数器落在同一条 line 上。放成独立的 static，或者前后各加一条 line 的 padding。
  • line 大小不一定是 64。std::hardware_destructive_interference_size 在 x86-64 上通常给 64，但 Intel 的 adjacent-cache-line prefetch 会成对拉取，有效粒度接近 128；部分 ARM 平台的 line 本身就是 128。跨平台代码保守取 128。

发现这类问题只有一个可靠工具：perf c2c record / report，它直接报告哪条 cache line 上发生了多少次跨核的 HITM（从别的核的缓存里命中），并且能定位到具体的变量和源码行。凡是多核服务，上线前跑一次 perf c2c 应该和跑一次压测一样是标准动作——它经常能找出几个谁都没想到的共享变量，比如一个用来打日志限速的时间戳。

7.1 三种死连接，第三种最贵

「连接断了」有三种形态，它们对服务端的成本完全不同：

第三种为什么贵，有两笔账。资源账：日均断连 6 次/设备里绝大多数是这一类，如果回收窗口是 75 秒，那么任意时刻都有 40万 × 6 / 86400 × 75 ≈ 2083 条半开连接在占资源——这个数字不大，可以忍。正确性账要严重得多：在被回收之前，网关认为这台设备在线，控制面下发的指令会被投给它，SSL_write 成功返回（数据只是进了内核发送缓冲），业务侧收到「下发成功」。设备再也不会响应，这条指令就静默丢失了。

为什么 TCP keepalive 不够用？它能探测半开连接，但默认参数是 tcp_keepalive_time = 7200 秒（2 小时）才发第一个探针。而运营商 NAT 的空闲连接回收通常是 5 分钟——也就是说在 TCP 探针发出之前，NAT 早就把映射删了，探针发出去也回不来。把 tcp_keepalive_time 调小到 60 秒是可行的，但它的粒度是 socket 选项、和 MQTT 的 keepalive 语义脱节、而且探针包不携带任何业务信息。结论是应用层心跳必须有，TCP keepalive 只作为兜底（防止应用层逻辑本身出 bug 导致连接永久泄漏）。

绝对不能用「写超时」判活。SSL_write 或 send 返回成功只说明数据进了内核发送缓冲；在弱网下，数据可能在缓冲里排队几十秒才发出，或者永远发不出去（对端不存在，重传到上限才报错，那要几分钟）。唯一可靠的活性证据是「收到了对端的字节」——所以判定逻辑挂在读路径上（§6.2 的 touch() 由任何一次成功读取触发），而不是写路径上。

7.2 四个超时必须满足的不等式

这套系统里有四个超时值，分别由四个不同的角色控制，而它们之间有强耦合。任何一个配错，症状都是「设备莫名掉线」或者「设备明明死了还显示在线」，而且很难归因——因为你只能看到自己那一个参数。

设 K = 设备 MQTT keepalive 周期（设备提出，服务端可钳制）
　 R = 网关读超时（我们定，即 §6.2 的时间轮窗口）
　 N = 运营商 NAT 空闲映射回收时间（不可控，只能测量）
　 L = 中间有状态设备的空闲超时（LB / 防火墙，ADR-001 已尽量绕开）

① K < N否则 NAT 先删映射，设备以为连接还在，实际已经不通
② K < L同理。这条是选 L4 DSR 而非 L7 代理的又一个理由——DSR 无状态，没有 L
③ R ≥ 1.5 K + JJ 是弱网抖动余量。允许丢一个心跳，否则一次丢包就误杀一台正常设备

第 ④ 条需要单独说，因为它是把两个 SLA 解耦的关键。如果下行流程是「查会话 → 找到连接 → 写过去 → 等 ACK 超时才知道设备已死」，那么一台半开连接的设备会让指令等到 R = 75 s 才失败——远超「下行 P99 < 2 s」的要求。做法是把活性判定从下行关键路径上摘掉：

  • 控制面下发时先读设备影子里的 last_seen。这个值由网关每隔几秒批量同步，精度够。超过一个心跳周期没更新就直接按「离线」处理，走离线指令队列（§10.2），不去尝试实时下发。
  • 确实认为在线的，下发后设 1.5 s 的指令层 ACK 超时（MQTT QoS1 的 PUBACK 或业务层回执）。超时就立刻标记为可疑并转入离线队列，同时通知网关提前判死这条连接——这条通知能把半开连接的回收从 75 s 提前到 1.5 s。
这就是「用一个宽松的判据保证不误杀，再用一个严格的判据保证不误信」。R = 75 s 负责「不冤枉正常设备」，指令层 1.5 s 超时负责「不欺骗业务方」，两者服务不同的质量属性（可靠性 vs 时延），所以必须是两个不同的数字。把它们合成一个，无论取哪个值都会牺牲另一边——这是超时设计里最常见的错误。

7.3 重连风暴：服务端一个人解决不了

一个区域的基站故障恢复，10 万台设备同时发现网络可用。如果固件写的是「断线就立即重连，失败就再立即重连」，这 10 万台会在几秒内全部涌向网关：

10 万台在 5 s 内重连 = 2 万次握手/s。按 §8.1 的 1.1 ms CPU/握手，需要 22 个核纯做握手——超过单实例 32 核的三分之二，上行处理被挤到几乎停摆。
更糟的是正反馈：握手排队 → 设备等到超时 → 断开重试 → 队列里那次握手的 CPU 白花了，因为对端已经走了 → 有效吞吐进一步下降 → 更多设备超时。这是一个典型的重试放大导致的正反馈，它不会自己停下来。

服务端能做的三件事都是必要的，但都不够：

accept 限速

握手线程池的入口限速到集群能承受的速率（§8.2）。超出的连接尽早拒绝而不是排队——排不完的队等于用 CPU 去服务已经放弃的客户。

会话复用优先

重连的设备如果能命中会话票据，握手成本从 1.1 ms 降到约 0.05 ms（§8.3），20 倍差距，把 22 个核变成 1 个核。

队列宁短勿长

somaxconn 不要设成很大的值。队列长度应该约等于「握手池 1–2 秒能排空的量」，剩下的靠 SYN 丢弃让设备退避。

但这三件事都改变不了一个事实：到达率是设备决定的。如果 10 万台设备坚持每 1 秒重试一次，服务端无论怎么限速，收到的 SYN 都是 10 万/s，光是处理和丢弃这些 SYN 就会吃掉可观的软中断 CPU。真正的解法必须在设备侧：

8.2 握手必须有独立的执行资源

从图 12 能看出，握手的 CPU 需求在正常和异常之间差 700 倍。如果握手和上行处理跑在同一批线程上（也就是 §4 方案 B 的朴素实现——新连接落在哪个核就在哪个核握手），那么一次重连洪峰会直接偷走上行的 CPU：正常设备的遥测开始延迟、PUBACK 变慢、攒批超时触发、上行吞吐下降——一个只该影响「正在重连的设备」的事件，变成了影响全部 40 万台设备的故障。

这就是 隔离与爆炸半径那一章的舱壁模式，落在这个系统上的具体形态是：

  • 独立的握手线程池，固定 4–6 个线程并 pin 在专门的核上。它的容量决定了集群的握手上限（4 线程 × 900 = 3600 次/s），也就是 §11.3 和 §3.2 里那个「速率」的来源。
  • 入口有界排队 + 尽早拒绝。队列长度按「1–2 秒能排空」定；满了就直接关闭连接，不进队列。被拒的设备会退避重试（§7.3），这比让它在队列里等到超时要好——超时的握手是纯浪费。
  • 握手完成后把 fd 交给某个 worker 核。这一步和 SO_REUSEPORT 的内核分流并不冲突：内核决定 fd 落在哪个监听 socket，握手池负责把它推进 TLS 就绪状态，然后由该 socket 所属的核接管。也可以反过来，由握手池按连接数主动选核——这就吸收了 §4.1 方案 C 的优点（分配可控）。
「握手池的线程数」和「worker 核数」是两个独立的容量维度，不要混在一个配置项里。前者按最坏重连速率定，后者按稳态消息率定。把它们绑在一起（比如「每个核既做 worker 又做握手」）会导致：为了扛住重连洪峰而超配核数，绝大部分时间这些核在空转。

8.3 会话复用与它的前向安全折损

TLS 1.3 的会话恢复（PSK / session ticket）跳过全部非对称运算，握手成本从 1.1 ms 降到约 0.05 ms——图 12 最后一行那 20 倍。对一个「设备日均断连 6 次、恢复时会有洪峰」的系统来说，这不是优化，它是让 §7.3 那个场景从「雪崩」变成「可控」的唯一手段。

但会话票据有一个跟架构直接冲突的性质：票据是用某个密钥加密的，而这个密钥默认是每个进程自己生成的。于是设备重连时如果被负载均衡分到了另一个实例，票据解不开，只能退回完整握手——而重连洪峰恰恰是最需要复用、又最可能换实例的时候（因为 §3.2 的再平衡、或者因为原实例正在重启）。命中率会低到没有意义。

这个决策值得记录的地方在于它明确地拿安全性换了可用性，而且给出了折损的边界（12 小时）而不是含糊地说「影响不大」。这类决策最怕的不是选错，而是没人知道它被做过——三年后一次安全审计发现「票据密钥居然是共享的」，如果没有 ADR，唯一的结论会是「这是个漏洞」，然后有人把它改回去，接着某次故障恢复时集群被握手打死。ADR 那一章讲的「记录被否决的候选和它们的代价」，这里是一个非常具体的用例。

8.4 五百万张证书怎么吊销

一机一证意味着 500 万张证书，而其中总会有需要作废的：设备被盗、私钥泄露、设备退役。标准手段在这个规模下都不太好用：

CRL 不可行

吊销列表要包含所有被吊销证书的序列号。假设 1% 被吊销就是 5 万条，几 MB 的文件，网关每次更新都要重新解析全表，而且它永远在增长。

OCSP 引入外部依赖

每次握手向 CA 查一次，等于在连接建立的关键路径上加了一次网络往返和一个可能挂掉的外部依赖。洪峰时 5000 次/s 的 OCSP 查询会把 CA 打死。

短有效期 + 本地黑名单

证书有效期设成 7–30 天，由设备在到期前自动续签（用当前证书换新证书）。吊销就是不给它续签——最长 30 天自动失效，不需要任何吊销机制。

短有效期把「吊销」这个难题转化成了「续签」这个例行问题，代价是必须建一套可靠的自动续签链路（而且它自己不能依赖设备在线——离线太久的设备证书会过期，需要一条带外的恢复路径，通常是一个有效期很长的「注册凭证」）。对于需要立即生效的吊销（设备被盗），再加一层网关本地的布隆过滤器：控制面把吊销的设备 ID 推送给所有实例，握手完成后查一次布隆过滤器，命中就断开。布隆过滤器 5 万条目在 1% 误判率下只要约 60 KB，可以常驻内存；误判的代价是一台正常设备被拒绝一次，用一个精确的小集合做二次确认即可。

8.5 ADR-003 决策记录

ADR-003握手用独立线程池并限速；会话票据密钥集群共享、6 小时轮换；证书用短有效期替代吊销列表已接受
背景
mTLS 完整握手约 1.1 ms CPU。稳态重连 28 次/s 可忽略，但实例重启会产生 5000 次/s（5.6 核），无退避的重连风暴可达 2 万次/s（22 核）。同时 500 万张设备证书需要可行的吊销方案。
决策
① 握手在 4–6 个专用线程上执行并 pin 核，入口有界排队、满即拒绝；② 会话票据密钥由控制面统一下发，6 h 轮换、保留前一轮用于解密，不落盘；③ 证书有效期 30 天 + 自动续签，吊销 = 停止续签；需要立即生效时用控制面推送的布隆过滤器黑名单。
后果
得到：重连洪峰不再抢占上行 CPU（爆炸半径限定在「正在重连的设备」）；洪峰时握手成本降低 20 倍；吊销问题被转化为续签问题，无需维护增长无界的 CRL。
付出：票据密钥共享带来最长 12 小时的前向安全折损窗口（已量化并接受）；必须建设并维护一条自动续签链路，以及一条设备长期离线后的带外恢复路径；握手池的线程数成为一个需要独立容量规划的参数。
依赖
本决策的③依赖设备固件支持自动续签。存量设备若不支持，需保留一套长有效期证书并单独维护 CRL——这是已知的技术债，随固件升级逐步收敛（§12.3）。

  sleep(30);            // ← 上报相位由「上电时刻」决定，此后永久锁定
}

相位由上电时刻决定，而设备的上电时刻不是随机的：一个小区停电恢复，几千台设备在同一秒上电；一批新设备现场安装，装完统一通电；一次大规模固件升级，重启时刻集中。每一次这样的事件都会造出一个「相位簇」，而这个簇永远不会自己散开——sleep(30) 是精确的，几千台设备会一起在第 0 秒、第 30 秒、第 60 秒上报，年复一年。

解法是服务端下发随机相位偏移：设备连上来时，网关在 CONNACK 里（MQTT 5.0 用 User Property，3.1.1 用一条专门的配置 topic）带一个 0–29 秒的随机值，设备把它存进 flash，之后的上报循环变成 sleep(30) 加上首次的 sleep(offset)。因为偏移是持久化的，重启后相位保持散开。

这件事最值得学的是为什么用架构手段而不是改固件。改固件当然更"正确"（把 sleep(30) 改成 sleep(30 + rand()%30)），但固件升级要经过灰度、现场覆盖率爬升、还有一批设备永远升不上来——按经验，让一批现网设备的固件覆盖率到 90% 要按季度计。而下发相位偏移当天生效、对老固件同样有效（只要它支持配置 topic）。

这就是架构师和工程师视角的一个典型分别：面对一个「本该由别人修」的缺陷，架构师要评估的是「等他修」和「我在自己这一侧抵消掉」哪个总成本更低，而不是判断谁的责任。这里九分之八的容量差，答案很明显。

9.2 PUBACK 的时机决定了架构

MQTT QoS1 承诺「至少一次」：服务端回了 PUBACK，设备就丢弃本地副本；没回，设备会重传。所以「什么时候回 PUBACK」等价于「什么时候我们承诺不会丢这条数据」——这是一个纯粹的架构决策，不是实现细节。三个候选：

方案 ② 和 ③ 之间还有一个很容易被选中的中间态：网关写本地 WAL，落盘后就回 PUBACK，再异步推给下游。它的延迟比 ③ 更低（本地 fsync 比一次网络往返快），看起来很有吸引力。但顺着它往下推一步就会发现问题：本地 WAL 只在进程崩溃时管用，机器整体故障（磁盘坏、节点下线）时 WAL 里的数据一样丢。要让它真正可靠，WAL 必须复制到别的节点——而「一个被复制的 WAL」正是 Kafka 的定义。自己实现它，等于自己写一个 Kafka，还得处理副本同步、故障切换、以及网关重启后的恢复流程（在这期间它不能接受新连接）。

更关键的是，本地 WAL 会让网关变成有状态的，而这一条会连带否掉前面的好几个决策：Pod 需要 PVC（不能随意调度）、优雅下线时要等 WAL 排空（§11 的排空时间被拉长）、扩缩容要迁移数据。「网关无状态」不是一个洁癖，它是 §11 那套滚动升级方案的前提。

这也是为什么这个决策要写进 ADR：单看「本地 WAL vs Kafka」，前者延迟更低、依赖更少，是个挺合理的选择；只有把它和「网关必须能随意重启」这个约束放在一起看，才知道它不行。

9.3 攒批的三个触发条件

选了方案 ③，Kafka produce 就在上行的关键路径上，必须攒批——1.33 万 msg/s 逐条 produce 会产生 1.33 万次网络往返。攒批有三个触发条件，缺一个都会出问题：

触发条件取值它防的是什么
条数达到 batch.size500 条保证批次不会太小，摊薄每批的固定开销
字节达到上限64 KB防止「条数没到但字节爆了」。IoT 帧长基本固定，但一旦有设备开始上传诊断日志，单条可能几十 KB——只按条数攒批的系统会在这时候突然发出巨大的请求
linger.ms 超时10 ms兜底。低谷期（比如凌晨）到达率可能只有几百/s，攒 500 条要好几秒——而这几秒里设备在等 PUBACK。超时是三个条件里唯一保证延迟上界的那个，绝不能省

攒批和 QoS1 的交互有两个必须处理的地方：

一、PUBACK 必须等整批的 ack。一批 500 条对应 500 台设备，Kafka 回 ack 之后才能给这 500 台各发一个 PUBACK。所以 linger.ms 直接进入上行延迟，10 ms 对秒级 SLA 完全无感。要注意的是失败也是整批的：produce 失败时这 500 条都不能回 PUBACK，设备会重传——这是正确行为，但要确保网关不会在重传到来时因为「已经处理过」而误 ACK。

二、按设备分区保证顺序。Kafka 只在分区内保序，所以同一台设备的消息必须进同一个分区（用 deviceId 做 partition key）。同时 max.in.flight.requests.per.connection 要设成 1，否则前一批失败重试、后一批已经成功，同一设备的两帧就乱序了。WAL 与崩溃恢复那一章讨论的顺序保证，在这里是同一个约束。

9.4 存储抖动时的三种选择

Kafka 或时序库出现抖动（扩容、compaction、网络分区），上行链路开始堵。这时候必须提前决定怎么办——如果不决定，默认行为就是「无界排队直到 OOM」，也就是 §5.4 那个雪崩的翻版：

选择做法后果链适用
① 不回 PUBACK 让设备自己保存并重传 设备 inflight 窗口是 1，于是它会停止后续上报，数据积压在设备的 flash 里。恢复后有一波补传洪峰，必须限速否则二次打死存储。数据不丢。 告警、计费
② 网关本地缓冲 写本地磁盘等恢复 网关变有状态（§9.2 已否）；而且磁盘也会满，满了之后还是要在 ① 和 ③ 之间选——它只是把决策推迟了，没有消除它 不采用

决策是按消息类别分级：topic 前缀决定它走哪条路。这正是 §1.1 第四轮追问的价值——因为提前问清了「遥测可丢、告警不可丢」，这里才能做出一个不需要妥协的选择：95% 的流量走 ③（不积压、无洪峰），5% 走 ①（不丢、可控的补传）。

① 那条路的恢复限速是最容易漏掉的一环。存储恢复的瞬间，所有积压的设备会同时开始补传，到达率可以是稳态的几十倍——这和 §7.3 的重连风暴是同一个数学问题，也需要同样的解法（设备侧抖动 + 服务端坡道式放开）。凡是「攒着等恢复」的设计，都必须同时设计恢复时的节奏，否则故障恢复本身会成为第二次故障。

10.1 三级寻址与会话注册中心

控制面拿到一个 deviceId，要找到它的连接。§4 的 shared-nothing 模型让这个地址变成三级：哪个实例 → 哪个核 → 哪个槽位，加上 gen 一共四个字段、16 字节。

会话注册中心存这份映射。它的选型有个反直觉的地方：这里只需要最终一致，所以不要用共识系统。理由是「寻址错了的代价极低」——

  • 读到过期的地址 → 投递到错误的实例 → 那个实例发现 gen 不匹配（§4.3）→ 返回「不在我这」→ 控制面重查一次。总成本是一次多余的往返，几毫秒。
  • 读到的地址是空 → 按离线处理，进离线指令队列（§10.2）。设备下次连上来会收到。
对比一下写入压力：40 万连接、日均断连 6 次，就是 40万 × 6 / 86400 ≈ 28 次注册变更/s 稳态；实例重启时 30 万条要在几分钟内全部更新，瞬时可达数千/s。
这个写入量对分片 Redis 来说毫无压力，但对一个 Raft 集群来说是每一次写都要过一轮多数派复制——用 etcd 存这个会在实例重启时被写入吞吐直接打死。分布式协调那一章的判据在这里很直接：需要「谁是主」这类唯一性裁决时用共识系统，需要「东西在哪」这类可重试的查找时用 KV 缓存。

具体做法：Redis Cluster 按 deviceId 哈希分片，键是 deviceId、值是那 16 字节地址，TTL 设成 2 倍读超时（150 s），由网关每 60 s 批量续期。TTL 的作用是兜底：网关被 kill -9 时来不及清理注册表，TTL 会在 150 s 内自动收敛。批量续期很重要——30 万个键逐个 EXPIRE 是 30 万次往返，要用 pipeline 按分片攒批。

10.2 离线指令、幂等与过期

设备不在线时的指令要排队，而排队立刻带来三个必须回答的问题：

队列多深

按设备限深（比如 32 条）。一台离线三个月的设备不该攒下几万条指令——它上线时会被一次性灌爆，而且那些指令早就没意义了。队列满时丢最老的，因为控制指令的价值随时间衰减。

什么时候过期

每条指令带 deadline。「把阀门关到 30%」这种指令过了两小时再执行可能是危险的。过期的判断必须在设备侧也做一遍——网关投递和设备执行之间还有弱网延迟。

怎么保证不重复执行

每条指令一个幂等键（幂等设计）。重传、重连、控制面重试都可能导致同一条指令到达两次，设备侧必须按键去重——服务端做不到，因为它不知道设备到底执行了没有。

第三点值得强调：QoS1 是「至少一次」，所以重复投递是协议保证的一部分，不是 bug。想要「恰好一次」只能靠幂等，而幂等的最终责任方是执行侧（设备）。服务端能做的是把幂等键设计好：用「指令 ID + 目标状态」而不是「递增序号」，这样即使设备的去重表被重启清空，重复执行一次「把阀门设为 30%」也是无害的。把指令设计成幂等的（声明目标状态）而不是增量的（「再关 10%」），是这一层最有效的一个约定。

10.3 ADR-004 OTA 必须走控制面 / 数据面分离

OTA 是这个系统里唯一的大流量场景，也是最容易把架构毁掉的一个需求。先算账：

一批 5 万台设备 × 8 MB 固件 = 400 GB。
如果从网关下发：假设希望 1 小时内完成，需要 400 GB / 3600 s ≈ 111 MB/s ≈ 0.9 Gbps——单看带宽 10 GbE 撑得住。但内存撑不住：按 §5.4，每条连接的写缓冲上限 256 KB，5 万台同时下载意味着网关要持有 5 万 × 数百 KB 的在途数据，而且弱网设备收得慢、缓冲会一直贴着上限。再叠加 §5.2 那个已经调到 2 KB 的 TLS record，8 MB 固件要切成 4000 个 record，每个都要走一次加密——CPU 也被吃掉一大块。

更根本的问题是：这个流量和网关的职责毫无关系。网关的价值在于维护 40 万条长连接的活性和身份，搬运固件字节流不需要长连接、不需要设备身份（一个签名的固件包谁下载都无害）、也不需要 MQTT。让它经过网关，唯一的效果是让最难重启的那个组件承担最大的流量。

ADR-004OTA 固件实体不经过网关，网关只下发预签名 URL 与放行令牌已接受
背景
单批 OTA 为 5 万台 × 8 MB = 400 GB。若经网关下发，需要网关同时持有 5 万份在途写缓冲，并把已调至 2 KB 的 TLS record 切成 4000 段逐段加密，内存与 CPU 都会被这一个非核心职责挤占。
决策
网关只走控制面：一条约 300 B 的 MQTT 通知，含目标版本、对象存储的预签名 URL（限时有效）、以及固件的签名与哈希。设备用普通 HTTPS + Range 请求直接从 CDN 下载，支持断点续传（弱网下必需）。下载与校验完成后经网关上报结果，供 OTA 控制器做灰度判断。
后果
得到：网关流量从 400 GB 降到 15 MB；固件分发的带宽成本转移到 CDN 并可独立扩容；断点续传天然支持（HTTP Range），弱网设备不必从头再来；固件包的完整性由签名保证，不依赖传输通道的机密性。
付出：多一个外部依赖（对象存储 / CDN）与一套预签名 URL 的签发和过期管理；设备固件必须实现 HTTPS 客户端与断点续传（对资源受限的 MCU 是真实负担）；下载进度不再经过网关，可观测性要靠设备上报或 CDN 日志补。
何时重议
若将来接入一批完全没有 HTTP 栈的极简设备，需要为它们保留一条经网关的分块下发通道——但那应该是一个独立的、可限流的下发服务，而不是把逻辑加回长连接网关。

10.4 分批放行与自动暂停

就算固件不过网关，「5 万台同时下载」本身也是个问题：CDN 会被打出带宽尖峰（还可能触发计费告警），而且如果这批固件有 bug，5 万台会一起变砖。所以 OTA 控制器要做两件事：

分批放行。通知不是一次全发，而是按批次发（1% → 5% → 20% → 100%），每批之间留观察窗口。放行的粒度还要考虑地理和电网分布——不要让同一个变电站下的设备在同一批里，否则那一批集体变砖会导致一个区域的数据全断。

自动暂停。每批的成功率、平均下载时长、升级后的重连率都要有阈值，任一项超限就自动停止后续放行并告警。注意「升级后的重连率」这个指标：如果新固件有个会导致偶发崩溃的 bug，设备会反复重启重连——这在成功率上看不出来（升级本身成功了），只能靠重连率发现。灰度的观察指标必须包含「升级之后设备的行为」，而不只是「升级过程的成功率」。

分批放行的实现有一个便宜的做法：不需要控制器主动推送，而是让设备在自己的心跳里询问「有没有我的升级任务」，控制器按当前放行窗口决定回不回。这样放行速率完全由控制器一侧的一个数字决定，暂停就是把这个数字改成 0——比取消已发出的通知简单得多。把「推送」改成「受控的拉取」，是控制大规模下发节奏最省事的手法，同样适用于配置变更和证书续签（§8.4）。

发布与容量：三十万连接怎么滚动升级

11.1 直接杀 Pod 的代价

无状态 HTTP 服务的滚动升级是个非事件：摘流量、等在途请求（几百毫秒）、杀进程。长连接网关不是——一个实例承载 13–17 万连接，直接杀掉意味着这些设备同时断连，然后：

17 万台设备断连，即使固件带了正确的退避与抖动（§7.3），它们也会在 1–5 分钟内全部回来。取 60 s 集中期，就是 2833 次握手/s；如果退避的抖动窗口小，可以短到 20 s，那是 8500 次握手/s——超过握手池 3600 次/s 的容量（§8.2），开始排队和拒绝。
而这些连接要被剩下的两个实例接住，也就是它们各自要在几分钟内新增 8.5 万连接、承担一半的握手洪峰。§5 那个「单实例上限 30 万」的余量，就是为这一刻准备的。

顺着往下推，这里还有一个隐藏的连锁：新连接会被均衡器分给「连接数最少」的实例——而正在启动的新版本 Pod 连接数是 0，于是 §3.2 的 least-conn 尖峰问题在滚动升级时必然出现。这就是为什么 §3.2 的慢启动和本节的排空必须同时存在：一个控制流出，一个控制流入，只做一半会把洪峰从一处挪到另一处。

11.2 优雅下线四步

目标是把「17 万连接瞬间断开」摊成「按可控速率逐步迁走」。四个步骤，顺序不能变：

步动作为什么是这个顺序
1 停止接收新连接：readiness 探针开始失败，从均衡器的 real server 列表里摘除；进程仍然存活并继续服务存量连接 必须最先做。否则一边排空一边进新连接，永远排不完
2 按速率主动断连：每秒挑 N 条连接，发 MQTT 5.0 DISCONNECT + reason 0x9C + Server Reference，然后关闭 带 0x9C 的设备立即重连且不退避，迁移最快；不支持 5.0 的老设备会走退避，所以要按协议版本分开统计速率
3 等残余：还剩少量连接（比如已经半开、或者设备正好在弱网中）时不再等待，直接关闭 半开连接（§7.1）不会响应 DISCONNECT，也不会主动断开。等它们等于等满一个读超时 R = 75 s，没有意义
4 flush 在途的上行：等 Kafka 把已收下但还没 ack 的批次确认完，再退出进程 这一步保证了 §9.2 的 QoS1 承诺：已经回过 PUBACK 的数据必须已经落进 Kafka。因为网关无状态，这一步只有几十毫秒

11.3 断连速率由握手预算反推

「每秒断多少条」不能拍脑袋，它由 §8.1 的握手预算决定。把这段逻辑写成代码，顺便把 §3.2 的再平衡也用同一条公式——它们在物理上是同一件事：

// 排空速率与再平衡速率是同一个公式：都受「集群还剩多少握手能力」约束。
// 只有触发原因不同（发布 / 倾斜），所以实现成一个函数，避免两处各调一套参数。
uint32_t drain_rate_per_sec(const ClusterState& c) {
  // 1. 集群理论握手能力：健康实例数 × 每实例握手线程数 × 单线程 900 次/s
  uint32_t capacity = c.healthy_instances * c.handshake_threads * 900;

  // 2. 扣掉稳态自然重连（§1.2 的 28 次/s，取实测的 P95 而不是均值）
  uint32_t headroom = capacity > c.natural_reconnect_p95
                        ? capacity - c.natural_reconnect_p95 : 0;

  // 3. 只用掉余量的一半：另一半留给「排空期间恰好发生一次区域故障」。
  //    发布窗口里出故障不是假设，它比平时更容易 —— 集群正处于降级状态。
  headroom /= 2;

  // 4. 老协议设备断开后会走退避，重连不是立刻发生，对瞬时握手压力贡献低；
  //    MQTT 5.0 带 0x9C 的设备会立即重连，1 条断开 ≈ 1 次即时握手。
  double immediate = c.mqtt5_ratio * 1.0 + (1.0 - c.mqtt5_ratio) * 0.3;
  uint32_t rate = static_cast<uint32_t>(headroom / immediate);

  // 5. 上界：排空必须在 terminationGracePeriodSeconds 内完成，否则被 SIGKILL；
  //    下界：太慢会让发布窗口长到没人愿意发版，那样就没人升级了 —— 这也是风险。
  return std::clamp(rate, 50u, 2000u);
}
代入本例：3 实例 × 4 线程 × 900 = 10800 次/s 理论能力。但排空时被摘掉一个实例，只剩 2 个 → 7200。扣掉稳态重连 P95（约 60 次/s）→ 7140，取一半 → 3570。假设 MQTT 5.0 占比 40%：immediate = 0.4 + 0.6 × 0.3 = 0.58，得到 6155 次/s。
这个数远大于图 16 里用的 200 条/s——为什么？因为还有一个更紧的约束：那 17 万连接要被剩下 2 个实例接住，而它们各自还要处理自己原有的连接。真正的限制往往不是握手，而是「接收方的 CPU 和内存增长速率」。所以实际速率是取所有约束里最小的那个，而这段代码只算了其中一条——这也是它必须写成一个能加约束的函数、而不是一个配置项的原因。

反推出速率之后，K8s 的两个参数就有了依据，而不是抄默认值：terminationGracePeriodSeconds 要 ≥ 最大连接数 / 排空速率 + 余量（17 万 / 200 ≈ 850 s，取 1200 s）；preStop 钩子负责触发排空并阻塞到完成。注意 preStop 的超时和 grace period 是同一个计时器——如果 preStop 还在跑但 grace period 到了，进程照样被 SIGKILL，前面的努力全部作废。这是这套方案最常见的落地失败原因。

11.4 SLI / SLO 与告警

99.9% 可用性等于每月 43 分钟的不可用预算，而按 §11.2，一次滚动升级要 14 分钟 × 3 个实例。所以发布本身必须不消耗可用性预算——这要求排空期间被迁移的设备始终有实例可连，也就是 §5 那个「单实例上限 30 万」的余量。发布不是「消耗预算的动作」，它是「必须设计成不消耗预算的动作」。

指标定义上，这个系统有几个和普通服务不一样的地方。直方图与分位数那一章讲了怎么正确聚合分位数，这里只说选哪些指标：

12.3 演进路线与触发信号

本文写的是 v2。不要一上来就做 v2——它的复杂度只在特定规模下才划算。三个阶段和它们之间的迁移触发信号：

v1 · ≤ 5 万连接

单 io_context + 线程池、shared_ptr<Session>、每连接一个 steady_timer、直接写时序库。这些「错误做法」在这个规模下完全正确，而且开发速度快一个档。三个月能上线。

v2 · 5 万 → 50 万

本文。触发信号是可测量的，不是感觉：perf 里锁等待或原子操作占 CPU > 15%；内存使用率 > 60% 且主要在用户态缓冲；一次发布的窗口拉长到 20 min 以上；一次区域故障恢复导致过全站上行抖动。

v3 · 多机房 / 300 万

设备按地理就近接入 + 跨机房会话路由 + 区域自治（单机房失联时本地仍能收数据）。新问题：设备跟着基站漂移导致机房间反复抖动，需要连接亲和性与滞回阈值。

顺便说一下技术债怎么管。本文留了两笔明确的债：MQTT 3.1.1 设备无法用 0x9C 重定向（让 §3.2 的再平衡和 §11.2 的排空效率打折），以及 老固件不支持证书自动续签（ADR-003 的依赖项）。这两笔都写进了 ADR，并且都有同一个收敛路径：随固件升级逐步减少。关键是给它们定一个可观测的指标——「MQTT 5.0 设备占比」和「支持自动续签的设备占比」应该出现在架构看板上，否则「随固件升级逐步收敛」就只是一句安慰话。

12.4 这套架构什么时候不适用

这一节比前面十一章都重要，因为架构文档最大的危害是被套用到不该用的地方。五条反向判据：

如果……那么本文的哪个决策会失效该怎么做
连接数 < 5 万 ADR-002 的收益（省掉锁）小于它的成本（自建跨核通道 + 裸指针的生命周期风险） 回到 v1：共享 io_context，shared_ptr，per-connection timer
下行成为主导（视频回传、指令流） shared-nothing 的每一条下行都要过跨核队列，跨核成本从「偶尔」变成「常态」，会超过省掉的锁 改回共享模型，或者按「设备」而非「连接」分片，让下行的产生方和连接落在同一个核
平均消息 > 4 KB §4.2 的核心论证（处理时间 ≈ 锁争用时间）不再成立，锁开销占比降到 1% 以下 选简单的模型，把精力放在零拷贝和缓冲管理上（零拷贝那一章）
需要强一致（金融交易、工控闭环） ADR-005 的「至少一次 + 幂等」、§10.1 的「寻址错了就重试」全部建立在最终一致上 这不是网关的问题，是整条链路的问题。需要端到端的事务或共识（Raft），代价是吞吐下降一到两个数量级
要在网关里做业务计算 §2.2 的「网关最薄」被破坏，于是业务的变更频率乘上网关的发布代价（§11 的 14 分钟 × 3） 把计算放到 Kafka 下游的流处理里。网关的发布代价高，所以它承载的变化必须少——这条约束是物理的，不是风格偏好
把这五条读一遍会发现一个规律：失效的判据几乎都指向同一个数字——单条消息的处理时间与一次跨核同步开销的比值。这个比值大（消息大、逻辑重），共享模型就够；比值接近 1（消息小、逻辑薄、量大），才需要 shared-nothing。

一份好的架构文档不只说「我选了什么」，还要说清「这个选择依赖哪个量级关系」。因为规模会变、需求会变，而唯一能让后来者判断「现在还该不该这么做」的东西，就是当初那个量级关系还成立不成立。

高频面试题 · 高并发接入网关

12 道，按难度分三档

点击每道题展开参考答案（先自测，再对照）。

13.1 基础（必答）

  1. 基础「单机支持 30 万长连接」，最先撞到的上限是什么？

    不是 CPU，不是带宽，也不是 fs.nr_open——那些是人为上限，改个配置就没了。真正的物理上限是每连接的常驻内存，而它的绝大部分是我们自己申请的（§5.1）。

    典型错答
    「调 tcp_rmem 和 tcp_mem」。tcp_rmem 的默认值是收发队列的上限，不是每连接预留；空闲连接的内核侧常驻只有 struct sock + tcp_sock 约 2.3 KB，占总预算不到 2%。
    该怎么答
    逐项列出预算：用户态读缓冲（如果常驻 64 KB，30 万就是 19.2 GB）、OpenSSL 的 SSL 对象加双向 16 KB BIO（约 40 KB/连接 = 12 GB）、用户态写缓冲、Session 对象、内核 sock、epoll item。然后指出前两项占了九成，而它们都可以靠池化和 SSL_MODE_RELEASE_BUFFERS 消掉。
    加分
    补一句「所以我会先算这张表，再决定单机放多少连接，而不是反过来先定目标再优化」。
  2. 基础为什么长连接场景下负载均衡器的轮询和最少连接策略都不够用？

    因为均衡器只能作用于新建连接这个导数，而连接寿命以天计，存量分布它管不着（§3.2）。

    • 轮询：重启后连接数归零的实例只能分到 1/N 的新建连接，按稳态 28 次/s 的新建速率，补齐 10 万连接要几个小时。这期间其它实例持续超载。
    • 最少连接：反过来把所有新建都送给它，如果恰好赶上一次重连洪峰，5000 次/s 的握手全砸在一个实例上，它需要 5.6 个核纯做握手，直接排队崩掉。
    正确组合
    新实例慢启动（递增权重，削掉 least-conn 的尖峰）+ 主动再平衡（网关上报连接数，偏高的实例按速率主动断连，用 MQTT 5.0 的 0x9C 让设备不退避地立刻重连）。前者管流入，后者管流出。
  3. 基础怎么判断一条连接背后的设备还活着？为什么不能用写操作判断？

    唯一可靠的证据是最近收到过对端的字节。判活逻辑必须挂在读路径上。

    写操作不行
    send / SSL_write 返回成功只说明数据进了内核发送缓冲。弱网下它可能排队几十秒；对端已经不存在时，要等 TCP 重传到上限（几分钟）才会报错。「写成功」和「对端收到」之间没有任何关系。
    TCP keepalive 只能兜底
    默认 tcp_keepalive_time = 7200 秒，而运营商 NAT 的空闲回收常见 5 分钟甚至 60 秒——探针还没发，映射早删了。可以调小，但它和 MQTT keepalive 语义脱节、探针不带业务信息，所以只作为「应用层逻辑出 bug 导致连接泄漏」的最后防线。
    正解
    应用层心跳（MQTT keepalive）+ 服务端读超时，超时判定用时间轮做到 O(1)（§6.2）。窗口取 1.5 倍心跳周期加抖动余量。
  4. 基础MQTT QoS1 的 PUBACK 应该在什么时候发？

    这不是实现细节，它定义了系统承诺在哪一刻起不会丢这条数据（§9.2）。三个候选各有代价：

    时机代价
    收到就回进程崩溃 / 被 OOM Kill 时内存里那批数据无声消失
    落终态存储后回上行吞吐 = 存储写入吞吐；存储的每次抖动都变成一次上行故障
    写进复制型日志（Kafka acks=all）后回上行 +5~15 ms，多一个强依赖
    推荐第三种
    它同时满足「不丢」和「网关无状态」。而「网关无状态」是滚动升级方案（§11）的前提。
    为什么不写本地 WAL
    本地 WAL 只防进程崩溃，防不了机器故障；要防就得复制，而「被复制的 WAL」就是 Kafka。更要命的是它让网关变成有状态的，连带否掉「可随意重启」这个前提。

13.2 中级（区分熟练度）

  1. 中级什么时候该选 shared-nothing（每核一份）线程模型，什么时候不该？给出可量化的判据。

    判据是一个比值：单条消息的处理时间 ÷ 一次跨核同步开销（§4.2、§12.4）。

    • 一次实际发生争用的跨核锁或原子操作，成本在 100–200 ns 量级（cache line 的 RFO 迁移，跨 socket 更贵）。
    • 处理一帧 200 B 的 MQTT 报文大约几百纳秒。比值接近 1，锁不是「开销」而是主要成本 → 选 shared-nothing。
    • 处理一条 64 KB 的消息要几十微秒，比值是 100 以上，锁占比不到 1% → 共享模型完全够用，还省掉全部跨核复杂度。
    要主动说出代价
    跨核下发必须自建通道（有界队列 + 聚合唤醒，有丢唤醒风险）；核间存量倾斜不自愈；SO_REUSEPORT 组内 socket 数量要固定；Session 变成裸指针，生命周期靠约定而非类型系统保证。只说好处不说代价，是这道题最常见的失分点。
  2. 中级shared-nothing 下，别的线程要给某条连接发数据，怎么做？

    关键约束是连接只能被它所属的核触碰，这是模型的立身之本。所以需要一条跨核通道，三个设计点（§4.3）：

    传什么
    定长 POD，只放 (slot, gen) 弱句柄 + 指令编号。不能传指针，更不能传 shared_ptr——后者的原子引用计数就是我们想消除的东西。gen（槽位代号）负责防 ABA：槽被复用后 gen 不同，迟到的投递自然失效。
    怎么背压
    有界队列（比如 8192），写满就如实返回失败，让调用方告诉上游「设备忙」。这是下行链路唯一的背压点。如果这里阻塞或者无界扩容，压力会往上游漂，最终以一个完全无关的形态（控制面 API 超时）暴露。
    怎么唤醒
    eventfd 注册在目标核的 epoll 上，但只在队列「空 → 非空」时写一次，后面的消息搭同一趟车。给 5 万台设备发通知可能只产生几十次系统调用。顺序有硬约束：消费侧必须先清 armed 标志再读队列头，颠倒了会丢唤醒——表现为「偶尔有指令延迟几十秒」，只在高并发下发时出现。
    为什么不用 asio::post
    它无界（背压消失）、每次 post 一次 std::function 堆分配、且无条件唤醒。批量下发时会产生和消息数一样多的系统调用与线程唤醒。
  3. 中级三十万个心跳定时器怎么管？为什么 asio::steady_timer 不合适？

    io_context 的定时器队列是堆，插入和取消都是 O(log n)。真正的问题在于重置频率：心跳不是每 45 秒重置一次，而是每收到一帧就重置一次——1.33 万 msg/s × (cancel + rearm) = 2.7 万次 O(log 30万) 堆操作/秒，峰值 24 万次/秒，每次还伴随一个 handler 的堆分配（§6.2）。

    时间轮
    128 槽 × 1 s（2 的幂，取模变位与；覆盖窗口 128 s 要大于读超时 75 s）。每槽一条侵入式双向链表——链表节点就是 Session 自己，零额外分配。重置 = 从旧槽摘下 + 挂到新槽 = 两次指针写，O(1)。每秒只扫一个槽（约 30万/128 ≈ 2344 条）。
    为什么可以这么做
    因为MQTT keepalive 本来就允许 1.5 倍宽限，±1 秒的精度损失完全无害。这是拿精度换复杂度，前提是业务允许——是架构判断，不是优化技巧。
    两个坑
    ① tick() 里要先把整条链摘下来再逐个回调，因为回调会关连接从而把自己从链表里删掉，边遍历边删会踩到失效的 next 指针。② MQTT 允许 keepalive 最大 65535 秒，乘 1.5 会超出槽数导致提前误判超时；要么在 CONNACK 里用 Server Keep Alive 钳制，要么做分层时间轮。
  4. 中级发布一个承载 17 万连接的网关实例，怎么做才不引发雪崩？

    直接杀掉的后果：17 万台设备在 20–60 秒内集中重连，即 2833–8500 次握手/s，而握手池容量只有 3600 次/s（§11.1）。超载 → 排队 → 设备超时 → 重试 → 排队里那次握手的 CPU 白花 → 正反馈。

    优雅下线四步，顺序不能变
    ① readiness 失败、从均衡器摘除，但进程继续服务存量（必须最先做，否则一边排空一边进新连接）；② 按速率主动断连，带 MQTT 5.0 DISCONNECT + 0x9C + Server Reference，设备会立即重连且不退避；③ 残余（半开连接、正在弱网中的）不再等待，直接关；④ flush 在途上行，等 Kafka 确认完再退出，兑现已发出的 PUBACK 承诺。
    速率怎么定
    取所有约束里最小的那个：集群剩余握手能力（要扣掉稳态重连、再留一半给「排空期间恰好出故障」）、以及接收方实例的 CPU/内存增长速率。本例是 200 条/s，排空 14 分钟。
    最常见的落地失败
    terminationGracePeriodSeconds 忘了按 连接数 ÷ 速率 反推（默认 30 s，需要 1200 s）。preStop 和 grace period 共用同一个计时器，超时照样 SIGKILL，前面全部作废。
    还要注意
    新版本 Pod 连接数为 0，least-conn 会把洪峰全给它——所以排空和慢启动必须同时存在，只做一半是把洪峰从一处挪到另一处。

13.3 高级（体现深度）

  1. 高级系统里有四个超时值分别由四方控制，它们之间有什么约束？

    设 K = 设备心跳周期、R = 网关读超时、N = 运营商 NAT 空闲回收、L = 中间有状态设备的空闲超时（§7.2）：

    K < N
    否则 NAT 先删映射，设备以为连接还在、实际已经不通。N 不可控，只能拿真机测——4G 常见 5 min，部分省份的 NB-IoT 低到 60–90 s。
    K < L
    同理。选无状态 L4 DSR 而不是 L7 代理的一个附带收益就是 L 根本不存在，这条约束自动满足。
    R ≥ 1.5 K + 抖动
    允许丢一个心跳，否则弱网下一次丢包就误杀正常设备。本例 K = 45 s → R = 75 s。
    R 必须离开下行关键路径
    这是最容易漏的一条。如果下行靠「写过去等超时」判活，一台半开连接的设备会让指令等 75 s 才失败，远超「下行 P99 < 2 s」。做法是下发前先读设备影子的 last_seen，并对确认在线的设置 1.5 s 的指令层 ACK 超时，超时立刻转离线队列并通知网关提前判死。
    背后的原则
    R = 75 s 负责「不冤枉正常设备」，1.5 s 负责「不欺骗业务方」。两者服务不同的质量属性（可靠性 vs 时延），所以必须是两个数字；合成一个，无论取哪个值都会牺牲另一边。
  2. 高级一次区域基站故障恢复，10 万台设备同时回来。服务端能扛住吗？

    先算：10 万台在 5 秒内回来 = 2 万次握手/s。mTLS 完整握手约 1.1 ms CPU（两次 ECDSA 验签是 mTLS 比单向 TLS 多出来的部分），2 万次/s 需要 22 个核，占单实例 32 核的 68%——上行处理基本停摆（§7.3、§8.1）。

    而且它不会自己停下来
    握手排队 → 设备等到超时 → 断开重试 → 队列里那次握手的 CPU 白花了（对端已经走了） → 有效吞吐进一步下降 → 更多设备超时。典型的重试放大正反馈。
    服务端能做的三件（都必要，都不够）
    ① 握手独立线程池 + 入口限速，超出尽早拒绝而不是排队（排不完的队等于用 CPU 服务已经放弃的客户）；② 会话票据复用，把握手从 1.1 ms 降到 0.05 ms，22 核变 1 核；③ somaxconn 宁短勿长。
    真正的解法在设备侧
    到达率是设备决定的。必须是指数退避 + 随机抖动 + 上限：min(cap, base × 2^n) × rand(0.5, 1.5)。只加退避不加抖动是个陷阱——所有设备的退避序列一模一样，它们永远保持同相，一个大尖峰只是变成一串小尖峰，总量没变。
    现网已有不带抖动的老固件怎么办
    让恢复本身变慢：故障恢复后按坡道逐步提升 accept 限速。被拒绝的设备会自然错开重试时刻，几轮之后相位就散了。用服务端的准入节奏，替设备补上它缺失的抖动。
    架构层面的结论
    设备固件的重连策略是这个系统的架构决策，即使代码不在你的仓库里。它必须写进 ADR 和设备接入规范，并在准入测试里抓包验证退避序列。
  3. 高级加核之后吞吐不升反降，怎么定位？

    「单核压测更快、加核变慢」是伪共享或缓存行争用的典型签名（§6.4）。定位工具只有一个可靠：

    perf c2c
    perf c2c record / report 直接报告哪条 cache line 上发生了多少次跨核 HITM（从别的核的缓存里命中），并定位到具体变量和源码行。其它工具（perf top、火焰图）只能告诉你时间花在某条 lock add 指令上，不会告诉你原因是争用。
    常见的三个源头
    ① 全局统计计数器 std::atomic<uint64_t>——32 个核每秒抢同一条 line 上万次，实测能吃掉 10% 以上吞吐；② shared_ptr 的控制块；③ 意想不到的共享变量，比如日志限速用的时间戳。
    对齐的三个细节
    ① 对齐的对象是数组元素：uint64_t c[64] 把 8 个计数器塞一条 line，等于没改，要写 struct alignas(64) Counter { uint64_t v; }；② 数组的邻居也会伪共享——如果它是某结构体的成员，前后成员可能和首尾计数器同 line，要 padding 或独立 static；③ line 不一定是 64 字节：Intel 的 adjacent-line prefetch 让有效粒度接近 128，部分 ARM 平台本身就是 128，跨平台保守取 128。
    流程上的建议
    perf c2c 应该和压测一样是上线前的标准动作。它经常能揪出几个谁都没想到的共享变量。
  4. 高级五百万台设备一机一证，怎么做证书吊销？

    标准手段在这个规模下都不太好用（§8.4）：

    • CRL：假设 1% 被吊销就是 5 万条序列号、几 MB 的文件，网关每次更新都要重新解析，而且它永远只增不减。
    • OCSP：在连接建立的关键路径上加一次网络往返和一个可能挂掉的外部依赖。重连洪峰时 5000 次/s 的查询会把 CA 打死。OCSP stapling 解决的是服务端证书，帮不了客户端证书。
    把吊销转化成续签
    证书有效期设 7–30 天，设备用当前证书自动换新证书。吊销 = 停止给它续签，最长 30 天自动失效，不需要任何吊销机制。这是用「短生命周期」换掉「撤销机制」的经典手法（和 SPIFFE / 短期 token 的思路一致）。
    代价要说清
    必须建一套可靠的自动续签链路，而且它不能只依赖设备在线——离线太久的设备证书会过期，需要一条带外恢复路径（通常是一个有效期很长的注册凭证）。另外老固件可能不支持续签，那就是一笔明确的技术债，要有可观测的收敛指标。
    需要立即生效的吊销
    设备被盗这类场景等不了 30 天。加一层网关本地的布隆过滤器：控制面推送吊销的设备 ID，握手完成后查一次，命中就断开。5 万条目在 1% 误判率下约 60 KB，可以常驻内存；误判的代价只是一台正常设备被拒一次，用一个精确的小集合做二次确认即可。
