01

系统背景与业务目标

案例是一套车端数据采集与遥测系统。本文只讲决策怎么做出来，方法论本身见 质量属性与权衡、ADR 写法与安全关键系统的架构特殊性。

1.1 背景

从 CAN-FD / Automotive Ethernet 采信号，按 OTA 下发的规则触发式录制（TTC < 2s 存前后 30s），本地缓冲后选择性上传。它不控制车辆，但与 ADAS 同处一颗 SoC，所以要过 ASIL-B。

业务需求本身不是架构驱动力：只有翻译成可测量的质量属性、且「优先级高 + 实现难」的那几条才值得改结构。

1.2 利益相关者（Stakeholders）地图

Stakeholder关心什么推出哪个 QA
ADAS 算法团队数据完整性、触发准确性可靠性、时序精度
嵌入式 BSP 团队资源占用、WCET 可预测实时性、确定性
功能安全团队ASIL-B 合规、FFI故障隔离、故障检测
数据保护团队记录了什么、加密、GDPR信息安全、隐私

平台架构师（我）模块边界、ABI 稳定可维护性、可演进性

1.3 核心约束

硬约束（必须满足）

  • NVIDIA Orin（Cortex-A78 + 16GB）· QNX Hypervisor + 双 Guest
  • 1TB NVMe，每天最多写 50GB · C++17
  • 过 ISO 26262 Part 6 audit（ASIL-B）· 规则与软件都要支持 OTA

软约束（需要权衡）

  • 6 人 C++ + 2 DevOps + 1 安全 · 季度里程碑，1.5 年上线
  • 上行 4G/LTE 均 10 Mbps，流量费敏感
  • Flash：50GB/天 × 5 年 = 91.25 TB 写入，须匹配 NVMe TBW

「QNX Hypervisor + 两个 Guest」决定了故障域的形状：遥测最坏也只炸掉 Linux Guest。这既是 FFI 论证的落点，也是「为什么拆 4 个进程」的前提。

Flash 寿命和上行带宽是两道会否决方案的算术题。算到底，结论直接产出了 ADR-002 的压缩与保留策略：

2.2 架构关键点识别

把 11 条场景铺进「优先级 × 难度」矩阵，只有右上角那 4 条值得写 ADR；为其余的提前设计结构即过度设计。

🔴 Risk（做不到就崩）

  • P99 ≤ 10ms：同步 IPC 达不到 → 无锁共享内存
  • RPO = 0：重启即丢 → WAL
  • FFI：可能污染 ADAS 内存 → 进程隔离 + hypervisor 保护

🟠 Tradeoff（两头都想要）

  • 低延迟 vs 隔离：共享内存快但隔离弱 → ADR-001
  • 加密 vs 写速：AES-256 有 CPU 开销 → 下沉到 NVMe 硬件加密
  • 热更新 vs 确定性 → ADR-006 只更新数据、不加载代码

ADR-001：进程间通信选型

延迟 vs 隔离 vs 资源占用

ADR-001

选择无锁共享内存环形缓冲区作为信号流 IPC

Accepted
日期：2025-09-15 决策人：平台架构师 + 嵌入式负责人
Context · 上下文

信号流要跨三个进程。约束：P99 ≤ 10ms、崩溃隔离，可用 4 核 / 8GB。

Decision Drivers · 决策驱动因素
  • P99 ≤ 10ms（来自 [H,H] 质量属性场景）
  • 进程崩溃隔离
  • < 5MB IPC 内存占用
  • 零第三方 broker 进程
Considered Options · 候选方案
  1. POSIX 共享内存 + 无锁环形缓冲（自研）
  2. SOME/IP ara::com · 3. ZeroMQ · 4. NATS local broker
Decision · 决策
选择方案 1：POSIX 共享内存 + 无锁环形缓冲（自研）。
Justification · 论证
方案P99 延迟隔离资源成熟度
1. 共享内存（选）~5µs ✅进程隔离 ✅<1MB ✅自研
2. ara::com~100µs完整 ✅10MB+重 ❌
3. ZeroMQ~50µs进程隔离5MBOK
4. NATS~1msbroker 独立15MB ❌OK

淘汰其余三个的不是延迟，是资源：ara::com 与 NATS 都要多一个常驻进程 / 10MB+；ZeroMQ 够快，但它只省下 500 行自研成本，团队已有 lock-free 经验时不值。

Negative Consequences · 负面后果
  • 自研 → 并发正确性只能靠 TSan + 长时压测兜底
  • 写者崩溃会留下不一致的 head/tail → 启动时 sanity check 后重置
  • 无内建背压：写满即覆盖最旧数据，见下
背压语义与降级链

选"写满覆盖"而不是背压，因为阻塞采集会让 P99 直接崩；代价是风险变成"丢了却不知道"，所以必须配一条可观测的降级链（通用形态见 负载脱落与自适应限流）：

Follow-ups · 后续行动
  • 水位 > 80% 自动告警；v2 评估是否换成支持优先级的 POSIX MQ

ADR-002：数据存储选型

写密集 vs Flash 寿命

ADR-002

使用 RocksDB 作为本地时序数据存储

Accepted
日期：2025-09-20
Context · 上下文

本地存储要求：写密集（峰值 500MB/s）、按时间范围读、断电安全、受 NVMe TBW 约束。

Considered Options · 候选方案
  1. RocksDB（LSM-Tree）
  2. SQLite WAL · 3. 本地 InfluxDB · 4. 自研二进制追加文件
Decision · 决策
选择方案 1：RocksDB + FIFO Compaction + Snappy 压缩。
Justification · 论证
方案写性能空间效率成熟度复杂度
RocksDB（选）优（LSM）高（Snappy）成熟 ✅中
SQLite中（B-Tree）中成熟 ✅低
InfluxDB优（TSM）高重 ❌高
自研文件优自定义—高（维护）

决定性的一条是 FIFO Compaction：直接丢整个 SST、不做写放大，§1.3 那道 TBW 题因此从 91 TB 降到 22.8 TB。B-Tree 就地更新反复重写页，恰好相反。

数据流与选型落点

存储不是"选一个数据库"，而是四段路径各选一次：

RocksDB 关键配置
compaction_style                   = kFIFO
max_total_wal_size                 = 1 GB
compression                        = kSnappyCompression
write_buffer_size                  = 64 MB
level0_file_num_compaction_trigger = 4
Negative Consequences · 负面后果
  • Compaction 带宽必须限流，否则抢掉前台峰值写
  • RocksDB 在目标工具链上的可移植性要在 Phase 1 验证——整条决策唯一可能被推翻的前提
  • 读写放大取舍见 存储与数据架构

ADR-003：ABI 边界设计

跨供应商、跨编译器的插件契约

ADR-003

插件接口使用 C ABI + Opaque Handle 模式

Accepted
日期：2025-10-01
Context · 上下文

适配器覆盖 CAN-FD / SOME-IP / ROS2，来自不同供应商、用不同编译器编译，且要能不重启加载。

Decision · 决策
适配器插件接口使用 C ABI（extern "C" + 纯 C 函数表），内部实现用 C++ + Pimpl。
接口定义
// signal_adapter_api.h — 这是唯一的 ABI 合约
typedef struct SignalAdapterDescriptor {
    uint32_t    api_version;    // Must == SIGNAL_ADAPTER_API_VERSION
    const char* name;           // e.g., "can-fd-adapter"
    const char* version;        // semver
    void (*destroy)(struct SignalAdapterDescriptor*);
    int  (*init)(struct SignalAdapterDescriptor*, const char* config_json);
    int  (*subscribe)(struct SignalAdapterDescriptor*,
                      const char** signal_ids, size_t count,
                      SignalCallback callback, void* userdata);
    void (*unsubscribe)(struct SignalAdapterDescriptor*, const char** ids, size_t count);
} SignalAdapterDescriptor;

typedef SignalAdapterDescriptor* (*AdapterCreateFn)(void);
Positive Consequences · 正面后果
  • 供应商只需实现这张函数表，内部用什么语言都无关；适配器因此能独立 OTA
  • api_version 是唯一防线：字段只能往末尾加并递增版本，绝不改既有字段的顺序和宽度
Negative Consequences · 负面后果
  • C ABI 没有 RAII 也没有异常 → 要包一层 RAII wrapper，错误走返回码 + out-param
  • 三种 ABI 稳定模式的取舍见 Pimpl 与稳定 ABI 与 插件化架构

ADR-005：C++ 子集与工具链

ADR-005

采用 AUTOSAR C++14 子集 + C++17 非违规扩展

Accepted
日期：2025-10-15
Decision · 决策
  • 基准：AUTOSAR C++14 Guidelines（源自 MISRA C++）
  • 扩展：C++17 的 std::optional / std::variant / if constexpr（已审查无违规）
  • 禁止：运行期 new/delete / 异常 / RTTI / 非 constexpr 递归
  • 工具链：GCC 12.3 交叉编译 + Clang 16 分析 + Coverity 合规扫描
内存管理策略
阶段策略
启动期允许分配：建资源池、规则缓存
运行期零分配，一律从预分配池取（etl::pool<T,N>）
Positive Consequences · 正面后果
  • 关键收益只有一条：运行期零分配 → WCET 可计算，这是过 ASIL-B Clause 8 的前提，合规检查也因此能自动化
Negative Consequences · 负面后果
  • 标准容器全部出局，所有 API 返回 etl::expected<T,E>——签名风格与站外 C++ 割裂
  • "启动期可分配、运行期不可"只能靠机器守，见 §14.1

ADR-006：插件化与规则热更新

零停机更新配置

ADR-006

规则配置 OTA 更新采用原子替换 + 双缓冲策略

Accepted
日期：2025-11-01
Context · 上下文

OTA 更新规则时不允许服务中断。规则是版本化的 Protobuf 文件。

Decision · 决策
使用原子文件替换 + 双缓冲 Rule Cache。
为什么不用 dlopen
  • 规则是数据不是代码；dlopen 会引入无法验证的代码执行路径，ASIL-B 下过不了
Negative Consequences · 负面后果
  • 两份规则内存都要在启动时按 MAX_RULES 预留满（运行期零分配所迫）——常驻内存翻倍
  • inotify 有 100–500 ms 抖动，SLO 只能写"≤ 5 分钟"，不能承诺秒级
  • 指针交换的内存序必须在目标 aarch64 上实测：弱内存模型下 release/acquire 配错，规则内容可能比指针后到

核心模块边界与接口

11.1 Signal Adapter 接口（C++ 内部）

ADR-003 定对外的 C ABI，这里定对内的 Port。两者刻意不同：对外跨编译器只能退化成 C 函数表，对内则用类型把约束写死。

// 信号采集上下文的 Port 接口（依赖倒置）
// domain/ports/i_signal_source.hpp
class ISignalSource {
public:
    virtual ~ISignalSource() = default;
    virtual etl::expected<void, SignalError>
        subscribe(const etl::string_view& signal_id,
                  std::function<void(const SignalSample&)>) = 0;
    virtual etl::expected<void, SignalError>
        unsubscribe(const etl::string_view& signal_id) = 0;
    virtual etl::optional<SignalSample>
        get_latest(const etl::string_view& signal_id) const noexcept = 0;
};

// 核心领域对象（值对象）
struct SignalSample {
    SignalId  id;           // strong typedef
    Timestamp timestamp;   // 高精度，纳秒级
    SignalValue value;     // std::variant<bool, int32_t, float, double, etl::string<64>>
    Quality quality;       // GOOD / DEGRADED / BAD (故障诊断用)
};

实现类 CanFdSignalSource 就是 §4.1 那条 ACL 边：把 signal_id 翻成「CAN message ID + bit offset」。Vendor 概念到这层为止。

11.2 Rule Engine 接口

两个约束落进了类型：evaluate 必须 const noexcept 且零 IO，否则进不了实时路径；仓储接口在 domain 声明、infra 实现，否则 Protobuf 会渗进 domain。

class TriggerRule {  // Aggregate Root
    RuleId        id_;
    RuleVersion   version_;
    ConditionExpr condition_;  // AST 预编译，不是每次重新解析
    TriggerAction action_;     // 命中后录多久
    RuleStatus    status_ = RuleStatus::Active;
public:
    // 纯逻辑、零 IO、不抛异常 —— 才可能进 10ms 预算
    etl::optional<TriggerDecision> evaluate(const MatchContext&) const noexcept;
    // 不变量：Active 的规则必须有有效 ConditionExpr
    bool is_active() const noexcept { return status_ == RuleStatus::Active; }
};

// Domain 层声明，Infrastructure 层实现（依赖倒置的落点）
class IRuleRepository {
public:
    virtual ~IRuleRepository() = default;
    virtual etl::expected<etl::vector<TriggerRule, MAX_RULES>, LoadError>
        load_all() noexcept = 0;
    virtual RuleVersion current_version() const noexcept = 0;
};

11.3 CMake 模块依赖图

接口只是意图，守不守得住取决于构建图允许谁 link 谁：PRIVATE 与 PUBLIC 一字之差，就是「RocksDB 头文件会不会传染到 application 层」。传播规则见 现代 CMake。

DDD 战术设计

12.1 信号采集上下文的核心 Aggregate

RecordingSession 之所以是聚合根，是因为下图那几条不变量必须在同一个边界内成立；散在 Recorder 的过程代码里，第一次并发重入就会破掉（Entity / VO / Aggregate 的划分见 DDD 战术设计）。

两处刻意设计：只存 TriggerEventId 不持有规则对象（否则两个聚合生命周期绑死）；channels_ 定容 etl::vector<SignalId, 256>，上限进类型、运行期不分配。

12.2 Domain Event 流

三个事件把四个进程串起来，走另一条 ring buffer——低频控制流混进高频信号流会被淹没。负载只放 ID 和位置。

事件发 → 收负载丢了会怎样
TriggerFired Rule Engine → Recorder event_id / rule_id / fired_at / 触发信号与取值 整段录制没发生。唯一不可丢的事件，发送方带重试
RecordingCompleted Recorder → Uploader session_id / 起止时间 / location / bytes_written 数据仍在本地，只是没排进上传队列；扫库可补偿
UploadRequested Uploader 内部编排 session_id / priority / location 下一轮扫描自然重排，天然幂等
最后一列才是设计产出：只有 TriggerFired 需要投递保证，另两个靠扫状态重建即可补偿——不必给整条总线上事务，那会吃光 50 ms 预算。

14.1 依赖方向检查

没有检查的原则只活在文档里。四条检查各对应一条决策和一种会静默发生的失效；「判据」必须是机器能算真假的量，"代码要清晰"写不成检查。

检查守哪条决策不检查会怎样判据
依赖方向 §11.3 分层 某次赶工在 domain 里 #include <rocksdb/db.h>，分层名存实亡 domain 测试不 link 任何第三方库即可编过
ABI 兼容 ADR-003 结构体中间插了字段，已发布的适配器全部错位读内存 abi-compliance-checker 对比基线，任何 break 即失败
性能基线 P99 ≤ 10 ms 一次涨 0.5 ms，二十次提交后超标，但查不出是哪一次 QEMU 注入 10k 样本，p99 > 10 ms 即失败
运行期零分配 ADR-005 某库在热路径偷偷 new，WCET 不可算，ASIL-B 论证作废 替换全局 operator new，run phase 命中即报

前三条有现成工具，只有最后一条要自己写——"运行期"不是编译期概念：

// 全局替换 operator new：把「阶段」这件事变成可检测的
namespace { std::atomic<bool> run_phase{false}; }

void* operator new(std::size_t n) {
    if (run_phase.load(std::memory_order_relaxed)) {
        // 测试构建：直接 abort，让 CI 变红并留下 core
        // 生产构建：降级为 DLT critical，不能因监控而杀掉遥测
        report_illegal_alloc(n);
    }
    return std::malloc(n);
}

真实项目对比：车端遥测 vs 分布式 RPC 代理

拿一个真实的电信网元管理代理做对照：同一套方法论换个领域，会得出什么不同的结论。
想看第三个领域的对照，读 IoT 接入网关架构设计：那是一个由量化 SLA 驱动的高并发服务端案例（30 万长连接、内存与握手 CPU 预算、shared-nothing 线程模型、滚动升级速率反推）。
和本篇的分工很清楚：本篇的约束来自「安全等级与确定性」，那篇的约束来自「规模与常驻资源」。同一套 C4 + ADR 方法论，前者推向静态分配与形式化，后者推向容量核算与背压——把两篇放在一起看，最能看出方法论在不同约束下会长成什么形状。

Mock 系统设计面试题

高级架构师 / Principal 面试的核心环节——45 分钟系统设计题。下面给出 3 道典型题 + 标准解答框架。点击题目展开答案
FRAMEWORK 系统设计题的标准 5 步框架（先记住这个，再做题）
速记所有系统设计题通用
STEP 1
需求澄清（5-7 分钟）

别急着画图，先问：核心用例与读写比 / 规模（QPS、数据量、保留期）/ 质量属性（P99、SLA、一致性）/ 约束（地域、预算、团队）。

STEP 2
容量估算（3-5 分钟）

BOTE：峰值 QPS = DAU × 人均请求 / 86400 × 峰值倍数；存储 = QPS × 单条大小 × 保留秒数。面试官想看你用数字思考。

STEP 3
高层设计（10-15 分钟）

画 C4 L2：客户端 → Gateway → Service → DB / Cache / MQ。从最简单的方案起步，先单体再分布式。

STEP 4
深入设计（10-15 分钟）

面试官会挑一个组件追问："怎么扩展 / 怎么分片 / 缓存怎么一致"。

STEP 5
权衡与演进（5-10 分钟）

主动说出瓶颈在哪、怎么从 1k QPS 演进到 100k、什么时候该重新设计。

MOCK-1 设计一个分布式限流系统（Distributed Rate Limiter），支持 1M QPS、跨数据中心、精确到用户维度
P0主题：分布式系统常见公司：Cloudflare/Stripe/AWS
STEP 1 · 澄清问题
  • 限什么？(1) 用户级（user_id）；(2) IP 级；(3) API 级
  • 限流算法？(1) 固定窗口；(2) 滑动窗口；(3) Token Bucket；(4) Leaky Bucket
  • 容忍误差？（精确 vs 近似）
  • 跨数据中心一致性要求？
STEP 2 · 容量估算

1M QPS，每次限流检查 1ms → 需要 1000 个工作单元；用户量 100M，活跃 10M → 状态存储 ~1GB

STEP 3 · 高层设计

核心方案：Token Bucket 算法 + Redis 集群 + 本地缓存

Client → API Gateway → Rate Limit Service → Redis Cluster
                              ↓
                     Local LRU Cache (减少 Redis 调用)
                              ↓
                     Decision: ALLOW / REJECT
STEP 4 · 关键设计点
  1. 算法选 Token Bucket：支持突发流量，比固定窗口更精确
  2. Redis 用 Lua 脚本 原子地"取 token + 扣减 + 返回剩余"，避免竞态
  3. 分片：按 user_id hash 分布到 Redis 集群，单点 QPS 受限于 Redis 上限（10W QPS / 节点 × N 节点）
  4. 本地缓存：每个网关节点本地 LRU 缓存最近用户的 token 余量，异步同步到 Redis——牺牲精度换性能
  5. 跨数据中心：每个 DC 有独立 Redis Cluster + 局部限流；全局限流通过 异步聚合 实现（接受秒级延迟）
STEP 5 · 权衡
  • 瓶颈：Redis QPS、网络延迟（每次 1ms × 1M = 1000 CPU 秒）
  • 精度 vs 性能：本地缓存会让用户多用 1-2% 配额，但 QPS 翻 10x
  • 演进：> 10M QPS 时考虑 cell-based 架构（按用户分租户，每个租户独立 Redis）
面试加分

提到 Cloudflare 的"Sliding Window Counter"——结合固定窗口的简单性和滑动窗口的精度，用加权平均近似。这是工业界常用的实用算法。

MOCK-2 设计一个类似 Kafka 的分布式消息队列：百万 QPS、至少一次语义、可重放
P0主题：分布式 + 存储常见公司：LinkedIn/Confluent/字节跳动
STEP 1 · 澄清
  • 消息保留多久？（影响存储设计）
  • 需要顺序保证吗？（影响分区设计）
  • Exactly-Once 还是 At-Least-Once？
  • Consumer 类型？（Push vs Pull）
STEP 3 · 高层设计（Kafka 思路）
Producer → Broker (Leader Partition) ──→ Followers (副本)
                    ↓                          ↑
              Local Log (append-only)    Replication
                    ↑
            Consumer (Pull) - Offset
            Consumer Group - Auto Rebalance
STEP 4 · 关键设计点
  1. Topic 分区：每个 Topic 多个 Partition；写入按 key hash 路由到 Partition；同 key 顺序保证，不同 key 并行
  2. 顺序写日志：每个 Partition 是 append-only 日志，顺序 IO 让单节点支撑 1GB/s 写入（SSD 顺序写极快）
  3. 副本机制：每个 Partition 有 N 个副本，Leader 负责读写，Follower 拉取复制；ISR（in-sync replicas）管理同步副本集
  4. At-Least-Once：Producer acks=all 等所有 ISR 写入；Consumer 提交 offset 在处理之后（消息可能重处理）
  5. 可重放：消息按时间保留（不删除），Consumer 可以从任意 offset 重读
  6. 水平扩展：加 Broker → 新建 Partition / 迁移 Partition
STEP 5 · 权衡
  • Partition 数量：太少 → 并行度不够；太多 → 元数据爆炸 + Rebalance 时间长。典型 100-1000 个
  • 副本数：3 副本是平衡点（容错 1 节点失败 + 不浪费）
  • 磁盘 vs 内存：消息持久化到磁盘，利用 OS Page Cache 加速读取（不用应用层缓存）
面试加分

提到 Pulsar 的分层存储（热数据 BookKeeper + 冷数据 S3）——比 Kafka 更现代的设计。或者讨论 Kafka KRaft 模式（去 ZooKeeper）的演进。

MOCK-3 设计一个高频交易系统的订单匹配引擎：P99 < 100µs、确定性、高可靠
P0主题：低延迟 C++ 系统常见公司：HFT 公司、券商技术、Citadel
STEP 1 · 澄清
  • 多少符号（symbols）？每秒订单数？
  • 需要支持哪些订单类型？（限价/市价/止损）
  • 是否需要 wire-to-wire 延迟保证？
STEP 3 · 高层设计
Network NIC (DPDK / Solarflare) → Decoder
                                       ↓
                              Order Book (per symbol)
                                       ↓
                                Matching Engine
                                       ↓
                              Trade Output / WAL
                                       ↓
                                  Risk Check
                                       ↓
                              Market Data Publisher
STEP 4 · 关键设计点（低延迟 C++ 核心）
  1. Kernel bypass：DPDK / Solarflare OpenOnload，绕过内核 TCP/IP 栈，从 NIC 直接到应用，延迟从 50µs 降到 2µs
  2. Single-threaded matching engine per symbol：避免锁，单线程跑完整个匹配；多个符号并行多线程
  3. Lock-free 数据结构：SPSC ring buffer 在 IO 线程和 matching 线程之间传递订单
  4. Order book 数据结构：通常用跳表或自研价格层级数组，根据典型订单簿深度优化
  5. CPU pinning + isolation：matching 线程绑定特定 CPU 核（isolcpus），关中断，关 NUMA balancing
  6. 预分配内存：避免运行时 malloc；用对象池
  7. WAL 写日志：每笔成交先写到磁盘的内存映射文件（mmap），崩溃后可恢复
STEP 5 · 权衡
  • 延迟 vs 可靠性：完全的 WAL fsync 增加延迟；HFT 通常用异步 WAL + 主备热备方案
  • 性能 vs 可维护性：极致优化代码极难维护，必须有专门团队
  • FPGA 加速：> 10M orders/s 时，把市场数据解码下沉到 FPGA
常见陷阱

不要说"用微服务"或"用 Kafka"——HFT 系统的设计哲学是"单进程极致优化 + 简单冗余"，加任何网络跳数都不可接受。

面试加分

能引用具体的延迟分布：典型 wire-to-wire 2-10µs（kernel bypass），50ns（FPGA）。能讨论 LMAX Disruptor 的设计思想（环形缓冲 + 单写者模型）。
