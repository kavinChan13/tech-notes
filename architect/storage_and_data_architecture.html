WAL 与崩溃恢复

为什么需要 WAL · WAL 的基本结构 · 崩溃恢复流程（ARIES 算法简化版） · Checkpoint 机制 · Double Write Buffer（InnoDB 特有）

所有持久化引擎都靠同一招：改数据之前先把"我要做什么"写进日志，崩溃后重放。

4.1 为什么需要 WAL

一次 B+Tree 更新可能牵动多个页（分裂、合并），而磁盘的原子写单位是 512B 扇区、页是 16KB——没有任何办法把这组修改原子地落盘。写到一半断电，结构就烂了。

解法：先把"我要做什么"顺序追加进日志，再慢慢改数据页。于是"提交成功"等价于日志落盘，而不是数据页落盘——后面所有恢复逻辑都建在这一句上。

4.2 WAL 的基本结构

每条 record 记「哪个表空间、哪个页、改成什么」，头上带一个单调递增的 LSN。关键在于每个数据页里也存了一份 Page LSN（这页最后被哪条 record 改过），两者一比就知道这条 redo 要不要重放。幂等由此而来：重放两遍和一遍结果相同，所以恢复过程自己再崩一次也不会错。

4.4 Checkpoint 机制

Checkpoint 就是把"已经安全落盘"的水位往前推（三件事与频率权衡见上图），它同时决定恢复时间与redo 文件大小。所以"崩溃后多久能起来"这个 SLA，本质上是在配 Checkpoint 频率，而不是在配 CPU。

MVCC 与隔离级别

MVCC 的基本思想 · InnoDB 的 MVCC 实现 · 四大隔离级别与读现象 · Undo Log 的两个用途

MVCC 让读不阻塞写、写不阻塞读，代价是旧版本得留着。隔离级别的全部差别只在快照何时建。

5.1 MVCC 的基本思想

写操作不覆盖旧数据，而是把旧值挪进 Undo Log、新值留在原位，串成一条从新到旧的版本链。读操作不加锁，只是沿链回溯，挑一个"对我可见"的版本。所以读写互不阻塞——代价是旧版本要一直留着，直到确认没人再需要它。

5.2 InnoDB 的 MVCC 实现

基石是每行两个隐藏列：DB_TRX_ID（最后改这行的事务 ID，6B）和 DB_ROLL_PTR（指向 Undo Log 里的上一版本，7B）。前者回答"这个版本是谁写的"，后者把版本串成链。

-- 事务 180 沿 roll_ptr 回溯，对每个版本问同一组判据（rv = 自己的 Read View）
for v in chain(v3 -> v2 -> v1):
    if v.trx_id == self.trx_id:   return v   # 自己刚改的，一定看得见
    if v.trx_id <  rv.min_trx_id: return v   # 建快照前就提交了
    if v.trx_id >= rv.max_trx_id: continue   # 比我晚开始，当它不存在
    if v.trx_id in rv.m_ids:     continue   # 建快照时还活着 = 未提交
    return v                                 # 已提交，就是它

5.3 四大隔离级别与读现象

5.4 Undo Log 的两个用途

Undo Log 兼两份工：回滚（ROLLBACK 就是逆向跑一遍）和给 MVCC 供货（版本链上的旧版本都住这儿）。两份工共用一份数据，所以清理时机取决于"还有没有人可能读它"，而不是"事务提交了没有"。

索引设计深入

索引选择性（Selectivity） · 联合索引的最左前缀原则 · 覆盖索引（Covering Index） · 索引失效的常见场景 · 分页查询优化

6.1 索引选择性（Selectivity）

选择性 = 不重复值数 / 总行数，一句 SQL 就能量：SELECT COUNT(DISTINCT col) / COUNT(*) FROM t。

email 通常接近 1.0，很适合建索引；status 只有几个取值，往往低到 0.003，单独建了优化器也不会走——它只有和高选择性列组成联合索引才有价值。

6.2 联合索引的最左前缀原则

INDEX(a,b,c) 是按 (a,b,c) 字典序排的一棵树：a 定住了 b 才有序，a、b 都定住了 c 才有序。所以"能不能用上"取决于前缀是否连续、且前面全是等值：

-- INDEX(a, b, c)：能用到几列
WHERE a=1                  -- ✓ a
WHERE a=1 AND b=2 AND c=3  -- ✓ a,b,c 全用上
WHERE a=1 AND b>2          -- ✓ a 等值定位 + b 范围扫，c 用不上了
WHERE b=2                  -- ✗ 跳过 a，整棵树无序，只能全表
WHERE a=1 AND c=3          -- ✗ 中间断了，c 只能在 a=1 的范围里逐行过滤
WHERE a>1 AND b=2          -- ✗ a 是范围，其后的 b 已经无序
推论：等值条件放前面，范围条件放最后。同一组列换个顺序，结论完全不同。

6.3 覆盖索引（Covering Index）

把 SELECT 要的列也塞进索引，回表就消失了：SELECT name … WHERE email=? 在 INDEX(email) 下要两次树查找，换成 INDEX(email, name) 只需一次，实测快 5–10 倍，EXPLAIN 出现 Using index 即生效。代价是索引更宽、写入更慢，只给热查询做。

6.4 索引失效的常见场景

场景原因解决
WHERE YEAR(created_at)=2024列上有函数改成 BETWEEN '2024-01-01' AND '2024-12-31'
WHERE age + 1 = 30列上有计算把计算搬到右边：age = 29
LIKE '%alice%'前缀通配 B+Tree 无从定位全文索引 / Elasticsearch
WHERE phone = 188…varchar 列传数字 → 隐式转换参数类型对齐列类型

6.5 分页查询优化

OFFSET 的代价是"扫过去再丢掉"：前 100000 行要真的读出来、回表、再扔掉，所以页码越大越慢，且是线性变慢。

-- ❌ 扫 100020 行，丢掉前 100000 行
SELECT * FROM orders ORDER BY id LIMIT 100000, 20;

-- ✅ 游标改写：把"第几页"换成"从哪个 id 之后开始"
SELECT * FROM orders WHERE id > :last_id ORDER BY id LIMIT 20;
-- 一次树定位 + 顺着叶子链表读 20 行，与页码无关

代价是不能跳页，前端得记住上一页最后一个 id。真要跳页就退一步：子查询在覆盖索引里先取这 20 个主键（不回表），再 JOIN 回主表做 20 次点查——快一个量级，但仍是 O(offset)。

多级缓存体系

缓存的五种模式 · 缓存一致性策略 · 进程内缓存（L1） · 多级缓存分层架构

本章按请求路径从外到内编号：L0 CDN → L1 进程内 → L2 本地 Redis → L3 分布式 Redis → DB。⚠️ CPU 的 L1/L2/L3 Cache 是硬件层、应用无法失效，不在此编号内——下文的「L1」一律指进程内缓存。

7.1 缓存的五种模式

五种模式只差两件事：miss 时谁回源、写时谁先落地。

模式机制代价与适用
Cache-Aside应用自己回源回填；写时先 DB 再删缓存默认选它；miss 瞬间 DB 压力大
Read-Through应用只跟缓存说话，缓存自己回源省掉重复代码，但缓存层要懂 DB
Write-Through同步写缓存 + DB写延迟是两次之和，冷数据白占内存
Write-Behind只写缓存，异步刷 DB快但会丢；只用于计数器一类
Refresh-Ahead快过期时后台重载，本次仍返回旧值天然防击穿；要能预测热点

7.2 缓存一致性策略

四种写法只有一种能用，理由全在竞态上：

写法会发生什么
❌ 先写缓存，再写 DB写完缓存就挂 → DB 还是旧值，缓存成了唯一"真相"
❌ 先写 DB，再更新缓存并发写的落地顺序可能反过来，慢的那个覆盖回旧值
❌ 先删缓存，再写 DB中间来一次读，把旧值重新加载回缓存
✅ 先写 DB，再删缓存最坏只是删失败 → 旧值留到 TTL 过期，不一致有界
删除比更新安全，因为删除没有顺序问题。删失败就重试，或者别在业务代码里删：用 CDC（Canal / Debezium）监听 binlog 触发失效。要再收窄窗口就延迟双删，中间隔 100–500 ms。

7.3 进程内缓存（L1）

L1 命中就是一次内存访问，10–100 ns，连序列化都省了。实现没有玄机：带容量上限的 LRU 加 TTL。

L1 的难点全在失效：它散落在每个实例的堆里，没有任何 API 能删掉别人进程那一份。所以它只配放"错一会儿也不要紧"的数据——配置、字典、权限表。要多实例强一致的东西不要进 L1。

7.4 多级缓存分层架构

命中率是乘法：0.2 × 0.2 × 0.1 = 0.4%。反过来，任何一层掉一截，下游承受的都是成倍放大——所以容量按"缓存全灭时 DB 扛不扛得住"算，不是按稳态流量算。

8.4 Redis 主从复制与 Cluster

主从复制

Slave PSYNC → Master BGSAVE → Slave 加载 RDB → 增量 Replication Buffer → 持续命令同步

第一次连上是全量：Master BGSAVE 出 RDB 发过去，期间的新写由 Replication Buffer 补发。断线重连看 offset 还在不在 backlog 里——在就只补差量，不在就退化成全量。所以 repl-backlog-size 设太小是隐形炸弹：一次抖动就能引发全量同步风暴，而全量同步又要 fork。

缓存三大问题与对策

缓存穿透（Cache Penetration） · 缓存击穿（Cache Breakdown） · 缓存雪崩（Cache Avalanche） · 一致性哈希（Consistent Hashing）

9.1 缓存穿透（Cache Penetration）

穿透两种对策各有边界：缓存空值最简单，但换个 key 就能塞满垃圾，所以 TTL 要短（60s 左右）；布隆过滤器用 1 MB 覆盖亿级 key、假阳性约 1%，但它不支持删除，key 集合会变就得定期重建。

9.2 缓存击穿（Cache Breakdown）

击穿的本质是同一个 key 的重建被并发了 N 遍。对策不是"别让它过期"，而是把 N 次重建收敛成 1 次：

// 只有抢到锁的那个请求去查 DB，其余人短暂等待后重读缓存
val = cache.get(key)
if val != nil: return val
if redis.SetNX("lock:"+key, 1, 3*time.Second):   // 锁必须带超时，否则持锁者崩了就死锁
    defer redis.Del("lock:"+key)
    val = db.Load(key); cache.Set(key, val, ttl+jitter())
    return val
time.Sleep(50 * time.Millisecond)      // 不要 spin，等一手再读，通常已命中
return cache.get(key)

另一条路是逻辑过期：不设真 TTL，把过期时刻写进 value，读到已过期就返回旧值并异步重载。用一点一致性换零等待。

9.3 缓存雪崩（Cache Avalanche）

雪崩有两种成因，别混：一批 key 同时过期（预热全用同一个 TTL）靠 TTL = base + random(0, base/10) 打散即可；Redis 整体挂了和 TTL 无关，只能靠 Sentinel / Cluster 自动切换，再加一道熔断降级——返回默认值也比让 DB 陪葬好。

判据：预热和限流都按"缓存全空时 DB 能扛多少"定。如果这个数字连稳态流量的 10% 都不到，你的系统其实没有降级能力，只有一个还没触发的事故。

车端按时效性分三层，越往上越快、越下越久：

⚡ L1 · 内存环形缓冲

只留最近 100–1000 ms 的信号，满了覆盖写、不落盘。无锁队列，采样线程绝不阻塞。

↓ 只在触发事件（急刹 / 碰撞）时转存

💾 L2 · 本地 Flash

二进制时序文件按小时分块，1–4 GB 保留 7 天。过期删整块——逐条删是在磨 Flash。

↓ 选择性上传

☁️ L3 · 云端

只传事件片段 + 统计聚合，断线续传。

四个决定必须写进 ADR，因为后期都改不动：数据格式（自研二进制最省也最难解析）、持久化触发策略（决定 Flash 还能活几年）、上传策略（实时流 vs 批量，账单差一个量级）、OTA 期间的数据保护。

12.2 索引设计速查

  • 选择性 → 高的优先建（email、phone、order_no）
  • 联合索引 → 等值列在前、范围列在后；跳前缀等于没建
  • 覆盖索引 → EXPLAIN 见 Using index 才算生效
  • 主键 → AUTO_INCREMENT 或 UUID v7
  • 深分页 → 游标替代 OFFSET；列上套函数即失效

12.3 Redis 使用速查

  • TTL 一律加抖动；大 Key（value > 10KB / hash > 5000 field）必须拆
  • maxmemory + allkeys-lru 必配，否则 OOM 时行为不可预测
  • 批量走 Pipeline；要原子性走 Lua（服务端一次执行完）
  • 单实例内存别超 10–20 GB —— BGSAVE 的 fork 会卡住你

12.4 MVCC 与隔离级别速查

  • DB_TRX_ID + DB_ROLL_PTR 串成版本链，Read View 决定看哪一节
  • RC 每次 SELECT 重建快照，RR 全事务只建一次——差别就这一句
  • 快照读走 MVCC，当前读走锁；混用就可能见幻象
  • 长事务同时锁住行和整条版本链，60 秒就该告警

Q1 B+ Tree 和 LSM-Tree 各自的适用场景？为什么 RocksDB 用 LSM？
P0主题：存储引擎难度：⭐⭐⭐
核心答案：读写权衡
维度B+ Tree（InnoDB）LSM-Tree（RocksDB）
写性能中（随机 IO）优（顺序写）
读性能优（点查 1-3 次 IO）中（多层查找 + Bloom）
空间中（碎片）高（压缩 4:1）
写放大低高（Compaction）
读放大低中
RocksDB 选 LSM 的原因
  • SSD 顺序写比随机写快 10x，LSM 把所有写变成顺序写
  • 典型 KV 场景：写多读少（如时序数据、日志）
  • 需要高压缩率（Snappy 4:1）
追问：什么是三大放大因子？
  • 写放大（WA） = 实际写 IO / 用户写量。LSM 高（Compaction 重写）
  • 读放大（RA） = 实际读 IO / 用户读量。LSM 中（多层）
  • 空间放大（SA） = 存储 / 用户数据。LSM 中（旧版本暂存）

三者不可能同时优，选型就是选哪个最重要。

Q2 InnoDB 的 RR 隔离级别能不能完全防幻读？解释 MVCC 怎么实现的。
P0主题：MVCC + 隔离级别难度：⭐⭐⭐⭐必考
核心答案：不完全防

InnoDB 的 RR 通过两种机制防幻读，但有边界条件：

  • 快照读（普通 SELECT）：MVCC 保证看到的是事务开始时的快照，能防幻读
  • 当前读（SELECT FOR UPDATE / UPDATE / DELETE）：用 Next-Key Lock（行锁 + Gap Lock）防幻读
  • 混用：先快照读，再当前读，可能看到幻象（快照里没有，但当前读看到了别的事务插入的行）
MVCC 实现机制
  1. 每行有两个隐藏列：DB_TRX_ID（最后修改事务 ID）+ DB_ROLL_PTR（指向 Undo Log 旧版本）
  2. 更新操作不覆盖，而是把旧版本写入 Undo Log，新版本写到当前位置，形成版本链
  3. 事务开始时创建 Read View = {m_ids（活跃事务集合）, min_trx_id, max_trx_id}
  4. 读时遍历版本链，找到第一个对当前 Read View "可见"的版本
可见性规则
if (trx_id < min_trx_id):    可见（已提交的旧事务）
elif (trx_id >= max_trx_id): 不可见（比我晚的事务）
elif (trx_id in m_ids):     不可见（创建时还活跃，未提交）
else:                       可见（已提交）
陷阱：长事务的杀伤力

有任何活跃事务存在，它能看到的所有历史版本就不能被 Purge 线程清理。一个 10 小时不提交的事务 → Undo Log 积累 10 小时的所有写入 → ibdata1 暴涨、磁盘满。必须监控 information_schema.innodb_trx，禁止 > 60s 的事务。

Q3 缓存更新策略：先更新 DB 还是先删缓存？为什么不是先更新缓存？
P0主题：缓存一致性难度：⭐⭐⭐高频
核心答案：先更 DB，再删缓存

这是 Cache-Aside 模式的标准做法。原因是"删除"比"更新"更安全——删除后下一次读会 miss 然后从 DB 加载新值；更新缓存则有竞态：

// 反例：先更新 DB 再更新缓存的竞态
T1: UPDATE DB to V2
T2: UPDATE DB to V3 (T2 比 T1 晚)
T2: SET cache to V3
T1: SET cache to V2 ← T1 较慢，覆盖了 T2
// 结果：缓存里是 V2（旧），DB 里是 V3 → 不一致
为什么不是"先删缓存再更 DB"
T1: DELETE cache
T2: GET cache (miss) → 从 DB 读到旧值 V1 → SET cache = V1
T1: UPDATE DB to V2
// 结果：缓存 V1（旧），DB V2 → 不一致

所以正确顺序是：先更 DB，再删缓存。最坏情况是删缓存失败，缓存里有旧值，直到 TTL 过期或下次更新——是有界的不一致。

面试加分：延迟双删

"我们用延迟双删：更新 DB 前删一次缓存（防止读到旧值后写回），sleep 一段时间（典型 100-500ms，覆盖未完成的读操作），再删一次。这能进一步缩短不一致窗口。"

追问：如果删缓存失败怎么办？

常见方案：(1) 重试机制，失败后入消息队列重试；(2) 用 CDC（Debezium）监听 DB binlog，自动触发缓存删除——这是最可靠的方案，业务代码完全无感。

Q4 Redis 为什么用跳表实现 ZSet，而不是红黑树？
P0主题：Redis 内部难度：⭐⭐⭐
核心原因（Antirez 解释过）
  1. 实现简单：跳表不需要复杂的旋转/平衡操作，~200 行代码搞定；红黑树要 500+ 行且容易出 bug
  2. 范围查询友好：跳表的 L1 链表天然支持有序遍历（ZRANGE 性能极高），红黑树需要中序遍历
  3. 缓存友好：跳表的内存访问模式更线性，CPU 缓存命中率高
  4. 更易扩展：跳表的层数可调，可在内存和速度间权衡
跳表的时间复杂度
  • 查找/插入/删除：O(log N) 平均（与红黑树相同）
  • 范围查询：O(log N + M)，M 是结果数
追问：ZSet 内部小数据怎么存？

Redis 7+ 用 listpack（小数据：< 128 元素且 member < 64B），紧凑连续内存，省内存；超过阈值才转为 skiplist + hashtable（双索引）。

面试加分：跳表的级数随机化

跳表的每个节点层数是随机决定的（概率 p = 0.5），不需要重平衡——这是它实现简单的核心。期望层数 = log_{1/p}(N)，对 10^9 节点也只有 ~30 层。

Q5 索引失效的常见场景有哪些？深分页 LIMIT 10000, 10 怎么优化？
P1主题：索引优化难度：⭐⭐⭐
索引失效六大场景
  1. 列上有函数/计算：WHERE YEAR(created_at) = 2024 → 改为 BETWEEN '2024-01-01' AND '2024-12-31'
  2. LIKE 前缀通配符：LIKE '%alice%' → 全文索引 / Elasticsearch
  3. 隐式类型转换：WHERE phone = 18888888888（phone 是 varchar，触发转换）
  4. OR 连接不同列：优化器放弃索引 → 改 UNION
  5. 跳过联合索引最左前缀：INDEX(a,b,c) 用 WHERE b=2 不走
  6. 不等号 / NOT IN：通常走全表
深分页优化（核心）

问题：SELECT * FROM t ORDER BY id LIMIT 1000000, 10 扫描 1000010 行丢弃前 1M。

// 方案 1：游标分页（推荐）
SELECT * FROM t WHERE id > last_id ORDER BY id LIMIT 10;
// 必须记住"上一页的最后一个 id"，前端配合

// 方案 2：覆盖索引 + JOIN 主键
SELECT * FROM t o
JOIN (SELECT id FROM t ORDER BY id LIMIT 1000000, 10) p ON o.id=p.id;
// 子查询只扫覆盖索引（无回表），主查询只 10 次点查
面试加分：覆盖索引

"我会优先考虑覆盖索引——把 SELECT 列都放进索引，EXPLAIN 显示 Using index，完全避免回表，性能提升 5-10x。"

"对穿透问题，我会用 Redis 的 BloomFilter 模块，启动时把所有合法 key 加载进去。查询时先过 Filter，不在的直接拒绝，连 Redis 缓存都不查。False Positive 率可调（典型 1%），用 1MB 内存能撑亿级 key。"

追问：互斥锁怎么实现？

缓存 miss 时先 SETNX 加分布式锁，获锁者去查 DB 并回填缓存，其他请求等待 50-100ms 重试（避免轮询 spinning）。等待者第二次 GET 缓存通常命中。
