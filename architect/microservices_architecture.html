01

单体 vs 微服务：不是越微越好

微服务是组织与规模问题的解，不是技术时髦

微服务把一个大应用拆成一组围绕业务能力、独立部署、独立数据、通过网络通信的小服务。它的核心收益是团队自治与独立演进——不同团队能各自开发、部署、扩容而互不阻塞。但它把「函数调用」换成了「网络调用」，引入了分布式系统的全部复杂性。

先把「网络调用」这四个字换成数字，后面所有取舍才有依据。

进程内函数调用：约 1–10 ns，不会失败，参数不用序列化，天然在同一个事务里。
同机房 gRPC 调用：约 0.3–1 ms（序列化 + 内核栈 + 网络 + 反序列化），会失败、会超时、会重复，没有事务。

差 10 万倍。一次业务操作如果原来调 20 个内部函数，拆成 20 个服务之后就是 20 次网络往返——延迟从微秒级变成十几毫秒，而且任意一次失败整个操作就失败（§1.3 会算这个可用性）。拆分的粒度直接由这个数字约束。

1.1 三个维度的对比

维度单体（Monolith）微服务（Microservices）
开发/部署简单，一个仓库一次部署独立部署，团队自治，但需 CI/CD 基建
调用进程内函数调用（快、可靠、事务简单）网络调用（有延迟、会失败、需分布式事务）
扩展整体扩（浪费）按服务独立扩（精准）
技术栈统一可异构（也可能失控）
故障隔离一处崩全崩可隔离（若设计得当）
调试/排障简单（一处日志）难（跨服务链路追踪）

1.2 什么时候该上微服务

🧭 判据
  • 团队规模：一个团队维护不动一个大单体、部署互相阻塞时（康威定律：架构映射组织）。
  • 业务复杂度：不同模块有截然不同的扩展/迭代节奏。
  • 反过来：初创/小团队/需求不清时，先单体（Modular Monolith），边界稳定后再拆——「Monolith First」是行业共识。
「团队规模」这条经常被当成一句正确的废话，其实它有一个可观察的触发信号：「我要发版，但得等隔壁组的改动一起上」这句话出现的频率。

微服务真正买到的东西是独立部署——它让「发版」从一次需要协调 N 个团队的活动，变成每个团队自己的事。如果你的团队现在并不为发版协调发愁，那么拆分买到的最大那件东西你用不上，剩下的全是成本。
先问「我们现在为什么疼」，再看微服务治的是不是这个疼。治不了的话，Modular Monolith（一个部署单元，内部有清晰模块边界）能拿到大部分代码组织上的收益，而不用付分布式的账。

1.3 拆分对可用性的影响：它是乘法

有一个常被忽略的算术：串行依赖的可用性是相乘的。拆得越细，同步依赖链越长，整体可用性越低——而且是指数级下降。

每个服务 99.9%（月不可用 43 分钟），串联 20 个同步强依赖：0.999²⁰ = 98.02%，月不可用 14.3 小时——比单体差一个数量级。

要把它拉回 99.9%，两条路：① 每个服务做到 99.995%（成本极高）；② 让大部分依赖变成「可降级」的——它挂了整体还能用，于是它不进这个乘法。
② 才是现实的路，而这意味着每一个依赖都要设计降级方案。这是拆分的隐藏账单，通常没人在拆分决策时算它。
生活类比：大厨房 vs 美食广场

单体像一个大厨房：所有菜一个团队做，沟通快、协调易，但人一多就挤、一个灶台坏影响出所有菜。微服务像美食广场：每个档口（服务）独立经营、各自扩张、互不干扰，但顾客要凑齐一顿饭得跑好几个窗口（跨服务调用），且需要统一的收银/找位（网关/服务发现）。档口分得太细，顾客就累了——这就是过度拆分。

映射：档口=服务 · 跑多个窗口=跨服务调用 · 统一收银=API 网关 · 分太细=过度拆分
02

拆分边界：最难也最关键

DDD 限界上下文

微服务成败 80% 取决于边界划得对不对。划错了会得到「分布式单体」——服务间高度耦合、改一个要动一串、还多了网络开销，比单体更糟。领域驱动设计（DDD）的限界上下文（Bounded Context）是划分边界的主流方法论。

📐 划分原则
  • 按业务能力，不按技术分层：拆成「订单服务/库存服务/支付服务」，而不是「DAO 服务/逻辑服务」。
  • 高内聚低耦合：一个业务变更尽量只落在一个服务内（避免跨服务改动）。
  • 限界上下文：同一个词在不同上下文含义不同（「商品」在售卖上下文 vs 仓储上下文关注点完全不同）——沿这些语义边界切。
  • 数据自治：服务应拥有自己的数据，不共享库（见 §4）。
  • 合适的粒度：不是越小越好；一个服务应能被一个小团队完整拥有（two-pizza team）。
怎么找边界

用 Event Storming（事件风暴）：把业务里发生的领域事件（「订单已创建」「已支付」「已发货」）贴满墙，观察哪些事件、命令、数据天然聚在一起——聚成团的就是一个限界上下文，团与团之间的稀疏连接就是服务边界。边界应落在业务耦合最弱的地方。

2.1 「按 DDD 划」不是判据，这三个维度才是

「按限界上下文拆」这句话的问题在于：它没告诉你两个候选方案哪个更好。真正能拿来打分的是三个维度，而且它们经常互相冲突——冲突时的取舍才是架构工作：

维度问什么划错的症状
① 变化频率 这两块东西是不是总是一起改？翻半年的提交记录，统计「同一个 PR 同时改了 A 和 B」的比例。 比例 > 30% 却把它们拆开了 → 每个需求都要跨两个服务、两次发版、两轮联调
② 数据所有权 这份数据的唯一写入方是谁？一个数据只能有一个主人。 两个服务都写同一张表 → 不管代码怎么拆，它们在数据层是一个整体
③ 团队边界 谁被叫起来处理它的告警？一个服务必须有唯一的负责团队。 一个服务两个团队共同维护 → 变更要协调，独立部署的收益归零
第一个维度有一个很实用的落地方式：用提交历史反推边界。跑一遍 git log，统计文件的共同变更频率，把「总是一起改」的文件聚成团——这些团就是候选的服务边界，而且它是从真实的变更行为里量出来的，不是从想象的领域模型里推的。

这个方法的价值在于它能证伪：如果你设想的边界和历史上的共同变更模式完全对不上，那要么是边界错了，要么是过去的代码组织有问题——两种情况都值得在拆之前搞清楚，而不是拆完之后才发现每个需求都跨三个服务。

2.2 冲突时怎么办

三个维度对不齐是常态。最典型的冲突：「变化频率」说该合，「团队边界」说该拆——两个团队各管一块，但业务上它们总是一起变。

❌ 按团队硬拆

得到两个高度耦合的服务，每个需求跨两边、要两次发版、要联调。这就是分布式单体——它比单体更糟，因为多了网络的不可靠，却没换来独立部署。

✅ 先改组织

康威定律反过来用（「逆康威操作」）：既然架构会映射组织，那就先把组织调成你想要的架构的样子。把这两块合并给一个团队，或者重新划分职责让它们真的解耦。

这里最常见的错误决策是「先拆开，以后再解耦」。不会有以后——拆开之后，跨服务的耦合会被网络调用固化下来，重新合并的成本比当初不拆高得多。
判据很简单：如果你无法说清「拆开之后，这两个服务各自能独立发版吗」，那就先别拆。

更完整的领域建模与战略/战术设计见 架构方法论。

03

服务间通信：同步还是异步

通信方式决定耦合度
维度同步（REST / gRPC）异步（消息 / 事件）
模式请求-响应，调用方等结果发消息即返回，解耦时间
耦合时间耦合（下游必须在线）时间解耦（下游可稍后处理）
一致性易做强一致但易级联失败最终一致，天然削峰抗峰
复杂度低，易调试高（顺序/重复/顺序性/可观测）
适用需即时结果的查询/命令事件通知、解耦、削峰、跨服务数据同步
🔗 实践建议
  • 查询/需即时反馈：同步（内部 gRPC，对外 REST，详见 API 设计）。
  • 状态变更通知/解耦：异步事件（Kafka/RabbitMQ）——「订单已创建」事件让库存、积分、通知服务各自订阅处理。
  • 少用同步链式调用：A→B→C→D 同步串联，延迟累加、任一挂全挂。能异步/并行就别串。
  • 事件驱动：发布领域事件而非直接命令下游，降低耦合（发布者不需知道谁在消费）。
同步像打电话，异步像发短信

同步调用像打电话：对方必须此刻接听，你得一直等；对方不在你就办不成事。异步消息像发短信：发出去就能干别的，对方有空再处理、也能积压慢慢消化。前者及时但脆弱耦合，后者解耦抗峰但要接受「稍后才处理」。

3.1 同步长链为什么是最糟的形态

选同步还是异步，有一个比「耦合度」更好用的判据：调用方需不需要用下游的结果来决定自己的返回值？

需要（查库存够不够才能决定下单成不成） → 同步，没得选。
不需要（下单成功后要发通知、加积分、更新推荐） → 这些都不该是同步的，它们的失败不该导致下单失败。

按这个判据过一遍，通常会发现一条同步长链里真正必须同步的只有前两跳，后面挂着的都是「顺便做的事」——它们被写成同步只是因为当初这么写最省事。把它们改成事件，链长从 4 降到 2，可用性从 99.7% 回到 99.8%，延迟从 100 ms 回到 40 ms。
04

数据管理：每服务一库

Database per Service

微服务最重要也最反直觉的原则之一：每个服务独占自己的数据库，其它服务不能直接访问。共享数据库会让服务在数据层紧耦合——改个表结构影响一片，等于没拆。

🗄️ 原则与代价
  • 数据私有：只能通过对方的 API/事件访问其数据，不能直连它的库。
  • 好处：服务可独立选型（订单用 MySQL、搜索用 ES）、独立演进 schema、独立扩展。
  • 代价：没有跨库 JOIN 和跨库事务了——这是微服务数据的核心难题。
难题解法
跨服务查询（原来一个 JOIN）API 组合（网关/BFF 聚合多服务）或 CQRS（构建只读物化视图）
数据同步/冗余订阅领域事件维护本地副本（如订单服务冗余商品名快照）
跨服务一致性Saga / 事件驱动最终一致（见 §5）
报表/分析CDC 汇聚到数仓统一分析，不在线上跨库查
05

分布式事务：Saga 与最终一致

放弃 2PC，拥抱补偿

「下单」要跨订单、库存、支付三个服务改数据——没有跨库事务怎么保证一致？传统 2PC（两阶段提交）强一致但会阻塞、可用性差、协调者是单点，互联网基本不用。主流是Saga：把一个大事务拆成一串本地事务 + 失败时的补偿操作，换取最终一致。

方案一致性特点
2PC / XA强一致阻塞、协调者单点、可用性差——不推荐
TCC（Try-Confirm-Cancel）较强业务侵入大（每步写三个方法），资金类可用
Saga最终一致本地事务 + 补偿；编排（Orchestration）/ 协同（Choreography）两种风格
本地消息表 / 事务消息最终一致保证「本地事务 + 发消息」原子，配 Saga 用
🎭 Saga 两种风格
  • 编排式（Orchestration）：一个中心协调器按步骤调各服务，失败则反向调补偿。逻辑集中、易理解易监控，但协调器是重点。
  • 协同式（Choreography）：各服务订阅事件、自主反应，无中心。松耦合，但流程分散、难追踪（易变「事件意大利面」）。
  • 补偿要幂等：补偿可能重试，须幂等；且要处理「补偿也失败」（告警 + 人工兜底）。
  • 注意 Saga 没有隔离性：中间态对外可见，需业务上处理（如订单「处理中」状态）。

5.1 Saga 真正难的是补偿，不是编排

讲 Saga 的材料大多把重点放在「编排 vs 协同」上，但那是形式问题。真正会让项目翻车的是补偿这件事本身在业务上往往做不到：

正向操作理论上的补偿现实
扣库存加回库存可以，这是 Saga 最理想的场景
扣款退款可以，但不是「撤销」而是一笔新交易——对账、手续费、用户账单上都会留下两条记录
发了通知短信？撤不回来。只能再发一条「刚才那条作废」，而这本身就是很差的体验
调用了外部支付网关依赖对方提供撤销接口对方可能不提供，或者有时间窗口限制
由此得到 Saga 设计的一条实操原则：把「不可补偿」的步骤排到最后。

下单流程如果是「发通知 → 扣库存 → 扣款」，那么扣款失败时你已经发了通知、还得补发一条撤销通知。改成「扣库存 → 扣款 → 发通知」，前两步都可补偿，最后一步执行时前面已经全部成功，永远不需要撤销它。

这个排序不是优化，它决定了 Saga 能不能真的工作。而它经常和「哪一步最快返回」的直觉相反——发通知最快，所以很容易被放在前面。
另一个必须提前想清楚的：补偿本身失败了怎么办？它不能再补偿（那会无限递归）。唯一的出路是重试到成功 + 超过阈值后告警转人工，这意味着：① 补偿操作必须幂等（会被重试）；② 必须有一个「卡住的 Saga」列表和处理它们的运维流程。
没有这个人工兜底流程的 Saga 实现是不完整的——而它通常是最后才被想起来的部分。

5.2 Saga 没有隔离性，这是个业务问题

ACID 里的 I（隔离性）在 Saga 里完全不存在：中间状态对外可见。库存已扣、款还没付的那几百毫秒里，别人查到的库存是少的，而这单可能最终会失败。

三种处理，都是业务层面的：

语义锁

给记录加一个「处理中」状态，其它操作看到就等待或拒绝。本质是自己实现了一个业务级的锁——要处理锁超时和死锁。

把中间态设计成合法状态

订单就是有「待支付」这个状态，它对用户可见且有意义。这是最好的做法：不是掩盖中间态，而是承认它是业务的一部分。

预留而非扣减

库存分「可用」和「已预留」两个字段，Saga 期间只动预留。这样中间态在数据模型上是自洽的，查询方能看到正确的语义。

分布式一致性、共识与故障模型的底层原理见 分布式基础；幂等设计是补偿可重试的前提。

06

API 网关：统一入口

把横切关注点从服务里抽出来

客户端不该直接调几十个后端服务（要处理服务地址、认证、协议差异）。API 网关作为统一入口，把横切关注点集中处理。

🚪 网关职责
  • 路由：把请求转发到对应后端服务。
  • 认证鉴权：统一校验身份，后端服务信任网关。
  • 限流熔断：入口过载保护（见 限流熔断降级）。
  • 协议转换：对外 REST/GraphQL，对内 gRPC。
  • 聚合：一次请求聚合多服务结果（BFF）。
  • 其它：日志、监控埋点、灰度、缓存、请求整形。
BFF：给每类前端定制网关

BFF（Backend For Frontend）是网关的一种：为 Web / App / 第三方各配一个专属聚合层，各自按需裁剪与聚合数据。就像酒店的前台——客人不用直接找客房部、餐饮部、保洁部，前台统一接待并协调各部门，还能针对散客/团客/VIP 提供不同服务。

映射：前台=网关 · 各部门=后端服务 · VIP 专属接待=BFF

⚠️ 注意别把网关做成新的「单体」——业务逻辑不该塞进网关，它只做编排与横切。

07

服务发现与服务网格

服务多了怎么找、怎么治理

服务实例会动态扩缩、重启、迁移，IP 不固定。服务发现解决「A 怎么找到 B 的实例」：

  • 注册中心：服务启动时注册到 etcd / Consul / Nacos / Eureka，调用方查询可用实例 + 健康检查剔除坏节点。
  • 客户端发现 vs 服务端发现：前者调用方自己拿列表 + 负载均衡；后者经 LB/网关转发。
  • K8s：内置 Service + DNS + kube-proxy 做服务发现与负载均衡，是云原生事实标准。
🕸️ 服务网格（Service Mesh）

当服务治理逻辑（重试、熔断、mTLS、流量灰度、追踪）散落在各语言的 SDK 里难以统一时，Service Mesh（如 Istio/Linkerd）把这些下沉到Sidecar 代理（与业务容器并列的 Envoy）：

  • 数据面：Sidecar 拦截所有进出流量，做负载均衡、mTLS、重试、熔断、指标。
  • 控制面：统一下发策略与配置。
  • 收益：治理与业务解耦、跨语言统一、零侵入。代价：每个 Pod 多一跳延迟 + 资源开销 + 运维复杂度。
  • 权衡：中小规模用 SDK/网关够了；服务数量大、多语言、需精细流量治理时上 Mesh。
08

可观测与弹性：微服务的生存基建

拆了就必须能看清、扛得住

单体的一个 bug 看一处日志就行；微服务一个请求跨 5 个服务，没有可观测就是盲人摸象。这些是微服务的必备基建，不是可选项：

  • 分布式追踪：全链路 trace_id 串起跨服务调用（OpenTelemetry / Jaeger），定位是哪一跳慢/错。
  • 集中日志：各服务日志汇聚 + trace_id 关联检索。
  • 指标监控：RED（Rate/Error/Duration）+ 饱和度，每服务 + 全链路。
  • 弹性：超时、重试、熔断、降级、隔离——防级联失败（详见 限流熔断降级）。

完整的可观测三支柱（Trace/Log/Metric）与实践见 可观测性工程。

反模式与迁移策略

别掉进这些坑
🚫 常见反模式
  • 分布式单体：拆了但服务间强耦合、必须一起部署——最糟结果，边界划错的标志。
  • 共享数据库：多服务连同一个库，数据层耦合，等于没拆。
  • 过度拆分（纳米服务）：拆太细，网络开销 + 运维成本压垮收益。
  • 同步长链：A→B→C→D→E 串行同步调用，延迟累加、脆弱。
  • 缺基建就上微服务：没有 CI/CD、可观测、自动化，微服务运维会失控。
🪓 迁移：绞杀者模式（Strangler Fig）

把单体改造成微服务不要「大爆炸重写」（风险极高）。用绞杀者模式：在单体前放一层路由，逐个把功能剥离成新服务、把流量慢慢切过去，老单体功能逐步「被绞杀」直至下线。每步可回滚、风险可控。

9.1 拆的顺序，以及最难的那一步

先拆叶子节点——被别人依赖少、自己依赖别人也少的（通知、报表这类）。它们剥离后对主流程影响最小，而且能让团队先把基建（服务模板、CI/CD、追踪、部署流程）跑通。不要一上来就拆核心域，那时你既不熟悉流程也没有基建。

真正难的是数据怎么迁。它有四步，每一步都可回滚：

共享数据库的耦合仍然存在，只是没人再看它； 下一次有人改老表结构，会莫名其妙地影响到某个已经「迁走了」的服务。迁移的完成标志是老表被删掉，不是新库上线。

三条 ADR 与反向判据

最后一节比前面九节都重要

10.1 三条 ADR

ADR-001先做 Modular Monolith，只在出现「跨团队发版协调」时才拆出服务已接受
背景
拆分的主要收益是独立部署，而当前团队规模下发版并不需要跨团队协调；同时按 §1.3 的算术，每增加一个同步强依赖都会拉低整体可用性，并要求配一套降级方案。
决策
单一部署单元，内部按限界上下文划模块，模块之间只能通过显式接口调用，用构建期依赖检查强制（禁止跨模块直接访问对方的数据访问层）。当某个模块出现「因为发版协调而阻塞」的实际证据时，再把它拆出去——此时边界已经被验证过了。
后果
得到：拿到代码组织上的绝大部分收益，不付分布式的账；边界划错时改回来只是一次重构，不是一次迁移。
付出：无法按模块独立扩容（整体扩，浪费资源）；技术栈必须统一；模块边界靠工具强制，一旦检查失效就会悄悄腐化——这条要有 CI 门禁。
何时重议
出现以下任一信号即重新评估：发版需要协调 3 个以上团队；某个模块的扩容需求与其它模块差一个数量级；某个模块的迭代速度被整体发版节奏拖慢。
ADR-002同步调用链深度上限为 2；超出的一律改为事件驱动已接受
背景
同步链的延迟累加、可用性相乘（§1.3、§3.1）。而按「调用方需不需要用下游结果决定自己的返回值」这个判据，长链里真正必须同步的通常只有前两跳。
决策
定一条硬规则：一次外部请求引发的同步调用链不得超过 2 跳，由链路追踪自动检测并在超标时告警。第 3 跳及以后的工作改为发布领域事件、由消费者异步处理。
后果
得到：延迟与可用性都有了可预测的上界；「顺便做的事」的失败不再拖垮主流程。
付出：这些工作变成最终一致——用户下单后积分可能几秒后才到，产品侧必须接受并在 UI 上表达；多了一套消息基建及其运维；调试一个业务流程要跨同步和异步两种视图，链路追踪必须能串起事件。
ADR-003暂不引入 Service Mesh，治理能力放在共享库 + 网关已接受
背景
Mesh 解决的是「治理逻辑散落在各语言 SDK 里难以统一」，而当前只有两种语言、十几个服务。Mesh 的代价是每个 Pod 多一个 sidecar（资源、一跳延迟、升级与调试复杂度）。
决策
治理能力（重试、熔断、超时、追踪埋点）放在一个共享库里，两种语言各维护一份；南北向流量的横切关注点放网关。但服务间身份用 SPIFFE/mTLS 独立建设（见 安全架构 §5）——这样将来接入 Mesh 时身份体系不用重做。
后果
得到：省掉 sidecar 的资源与运维成本；调试时抓包能看到明文。
付出：共享库的版本升级需要推动所有服务发版——这是 Mesh 想解决的核心问题，我们把它转成了一个组织问题；语言数量增加时成本线性上升。
重议信号：出现第三种语言，或共享库的一次安全修复推了一个月还没覆盖到所有服务。

10.2 什么时候不该用微服务

如果……为什么不该拆
团队少于 3 个、发版不需要跨团队协调 微服务买到的最大那件东西（独立部署）你用不上，剩下的全是成本
业务边界还在快速变化 边界会划错，而改服务边界比改模块边界贵一个数量级（要迁数据、要改调用方、要双写过渡）
没有 CI/CD、链路追踪、集中日志 这些是微服务的前置条件不是配套。缺了它们，十个服务的运维负担会压垮团队
核心流程需要强一致 Saga 只能给最终一致，且很多步骤业务上无法补偿（§5.1）。这类场景应该让相关数据留在同一个服务里
拆分后两个服务仍然「总是一起改」 这就是分布式单体的定义。先改组织或重新划边界，不要先拆再说（§2.2）

10.3 一页速记

🎯 关键结论
  • 函数调用和网络调用差 10 万倍，且后者会失败——拆分粒度直接受这个数字约束。
  • 可用性是乘法：20 个 99.9% 的同步强依赖串起来是 98%（月不可用 14 小时）。把依赖做成可降级的，它才不进这个乘法。
  • 边界的判据是变化频率 × 数据所有权 × 团队边界三个维度；冲突时先改组织，不要先拆再说。可以用 git 的共同变更频率反推候选边界。
  • 判断同步还是异步：调用方需不需要用下游结果决定自己的返回值？不需要的一律改事件。
  • Saga 难在补偿不在编排：把不可补偿的步骤排到最后；补偿必须幂等；必须有人工兜底流程。
  • Saga 没有隔离性，中间态对外可见——最好的处理是把它设计成一个合法的业务状态（「待支付」）。
  • 拆分的隐藏账单是降级方案的数量，通常没人在决策时算它。

高频面试题 · 微服务架构

12 道，按难度分三档

点击每道题展开参考答案（先自测，再对照）。

11.1 基础（必答）

  1. 基础什么时候该上微服务？什么时候不该？

    微服务真正买到的东西是独立部署——让「发版」从一次需要协调 N 个团队的活动，变成每个团队自己的事。

    一个可观察的触发信号
    「我要发版，但得等隔壁组的改动一起上」这句话出现的频率。如果团队现在不为发版协调发愁，那么拆分买到的最大那件东西你用不上，剩下的全是成本。
    不该拆的情况
    团队少于 3 个；业务边界还在快速变化（会划错，而改服务边界比改模块边界贵一个数量级）；没有 CI/CD、链路追踪、集中日志（这些是前置条件不是配套）；核心流程需要强一致。
    中间选项
    Modular Monolith：一个部署单元，内部按限界上下文划模块，模块间只能走显式接口（用构建期依赖检查强制）。能拿到代码组织上的大部分收益而不付分布式的账，边界划错时改回来只是一次重构。
  2. 基础什么是分布式单体？怎么识别？

    拆成了多个服务，但它们之间高度耦合、必须一起部署——付了分布式的全部成本，却没换来独立部署这个唯一的核心收益。它比单体更糟。

    识别信号
    ① 一个需求的实现总是要改 2 个以上服务；② 发版必须按特定顺序、几个服务一起上；③ 联调是常态；④ 两个服务共享数据库；⑤ 改一个服务的接口要通知一串调用方。
    量化的判据
    翻半年的提交记录，统计「同一个 PR 同时改了 A 和 B」的比例。超过 30% 却把它们拆开了，就是划错了。这个方法的好处是它从真实的变更行为里量出来，不是从想象的领域模型里推的。
    最常见的成因
    按团队硬拆，而两个团队负责的东西在业务上总是一起变。正确做法是逆康威操作——既然架构会映射组织，就先把组织调成你想要的架构的样子，而不是「先拆开，以后再解耦」（不会有以后）。
  3. 基础为什么强调「每服务一库」？代价是什么？

    共享数据库会让服务在数据层紧耦合：改个表结构影响一片，等于没拆。数据私有之后，服务才能独立选型、独立演进 schema、独立扩展。

    代价：没有跨库 JOIN 和跨库事务了
    这是微服务数据层的核心难题，所有麻烦都从这里来。
    四类替代方案
    跨服务查询 → API 组合（网关/BFF 聚合）或 CQRS（构建只读物化视图）；数据冗余 → 订阅领域事件维护本地副本（如订单冗余商品名快照）；跨服务一致性 → Saga；报表分析 → CDC 汇到数仓，不在线上跨库查。
    加分：冗余副本的取舍
    「订单冗余一份商品名快照」不只是为了避免 JOIN，它还有语义价值——订单要记录的是「下单那一刻的商品名」，商品后来改名了也不该影响历史订单。很多所谓的「数据冗余」其实是正确的领域建模，不是妥协。
  4. 基础服务间通信选同步还是异步？
    判据比「耦合度」更具体
    调用方需不需要用下游的结果来决定自己的返回值？
    需要（查库存够不够才能决定下单成不成）→ 同步，没得选。
    不需要（下单成功后发通知、加积分、更新推荐）→ 这些都不该是同步的，它们的失败不该导致下单失败。
    按这个判据过一遍会发现
    一条同步长链里真正必须同步的通常只有前两跳，后面挂着的都是「顺便做的事」——写成同步只是因为当初这么写最省事。改成事件后，链长从 4 降到 2，延迟从 100 ms 回到 40 ms，可用性从 99.7% 回到 99.8%。
    异步不是免费的
    换来的是最终一致：用户下单后积分可能几秒才到，产品侧必须接受并在 UI 上表达。还要多一套消息基建，以及调试要跨同步和异步两种视图——链路追踪必须能串起事件。

11.2 中级（区分熟练度）

  1. 中级拆成 20 个微服务之后，整体可用性会怎样？

    可用性是乘法。每个服务 99.9%（月不可用 43 分钟），20 个同步强依赖串起来：0.999²⁰ = 98.02%，月不可用 14.3 小时——比单体差一个数量级。

    两条出路
    ① 每个服务做到 99.995%（成本极高，而且它自己也依赖别人）；② 让大部分依赖变成「可降级」的——它挂了整体还能用，于是它不进这个乘法。②才是现实的路。
    推论：拆分的隐藏账单
    ②意味着每一个依赖都要设计降级方案。所以「拆多细」不只是延迟问题，它直接决定了你要在多少个地方做降级——而这笔账通常没人在拆分决策时算。
    并行扇出也不是免费的
    把串行改并行能把延迟从累加变成取最大值，但尾延迟被放大：三个下游都要等，「至少一个慢」的概率是单个的三倍（容量篇 §6.1）。扇出越大，整体的中位数越接近单个下游的 P99。
  2. 中级怎么划服务边界？「按 DDD 限界上下文」之外还有什么可操作的？

    「按限界上下文拆」的问题是它没法告诉你两个候选方案哪个更好。三个能打分的维度：

    ① 变化频率
    这两块是不是总是一起改？用 git log 统计共同变更频率。超过 30% 还拆开，每个需求都要跨两个服务、两次发版、两轮联调。
    ② 数据所有权
    这份数据的唯一写入方是谁？一个数据只能有一个主人。两个服务都写同一张表，那它们在数据层就是一个整体，代码怎么拆都没用。
    ③ 团队边界
    谁被叫起来处理它的告警？一个服务必须有唯一的负责团队，否则变更要协调，独立部署的收益归零。
    冲突时怎么办才是真问题
    最典型：变化频率说该合，团队边界说该拆。正确做法是先改组织（逆康威操作），把这两块合给一个团队或重新划职责。
    错误做法是「先拆开，以后再解耦」——拆开之后耦合会被网络调用固化，重新合并比当初不拆贵得多。判据：说不清「拆开后这两个服务能各自独立发版吗」，就先别拆。
  3. 中级Saga 的编排式和协同式怎么选？
    编排式（Orchestration）
    一个中心协调器按步骤调各服务，失败则反向调补偿。逻辑集中、流程可见、易监控和调试，代价是协调器成为一个需要维护的组件，且它知道所有业务流程（某种程度的耦合）。
    协同式（Choreography）
    各服务订阅事件、自主反应，无中心。松耦合、加新参与者不用改别人，代价是流程分散在各处——没有任何一个地方能看到完整流程，容易变成「事件意大利面」。
    判据
    步骤多（> 4）、流程复杂、需要清晰的状态跟踪和运维介入 → 编排式。步骤少、参与方会频繁增减、各方职责独立 → 协同式。
    实践中混合很常见：核心交易流程用编排（要能看清、能人工干预），外围的通知/统计用协同。
    但这其实不是最重要的选择
    形式问题远没有补偿在业务上做不做得到重要——见下一题。
  4. 中级要不要上 Service Mesh？

    Mesh 解决的是一个很具体的问题：治理逻辑（重试、熔断、mTLS、灰度、追踪）散落在各语言的 SDK 里，难以统一升级。先确认你有没有这个问题。

    代价是实打实的
    每个 Pod 多一个 sidecar：内存与 CPU 开销、每次调用多一跳延迟（进出各一次代理）、升级 Mesh 要滚动所有 Pod、抓包看不到明文导致调试变难、以及一整套新的故障模式。
    判据
    服务数量大（几十以上）、多语言、需要精细的流量治理（金丝雀按比例、故障注入、镜像流量）→ 值得。
    十几个服务、一两种语言 → 共享库 + 网关就够了。
    不上 Mesh 时的一个重要例外
    服务间身份（mTLS / SPIFFE）值得独立建设，不要等 Mesh。它挡的是横向移动（一个服务被攻破后能以任意服务身份调用任何接口），价值和 Mesh 的其它功能不在一个量级上；而且先建好身份体系，将来接入 Mesh 时不用重做。
    不上 Mesh 的代价要写下来
    共享库的版本升级需要推动所有服务发版——这正是 Mesh 想解决的问题，你把它转成了一个组织问题。重议信号：出现第三种语言，或一次安全修复推了一个月还没覆盖所有服务。

11.3 高级（体现深度）

  1. 高级Saga 里最难的是什么？

    不是编排形式，是补偿这件事在业务上往往做不到。

    补偿的可行性分三档
    能真正撤销：扣库存 → 加回库存。只能用一笔新操作抵消：扣款 → 退款——这不是「撤销」，对账、手续费、用户账单上都会留下两条记录。根本撤不回来：已经发出去的通知短信、已经调用的外部支付网关（对方可能不提供撤销接口，或有时间窗限制）。
    由此得到一条实操原则
    把不可补偿的步骤排到最后。「发通知 → 扣库存 → 扣款」改成「扣库存 → 扣款 → 发通知」：前两步可补偿，最后一步执行时前面已全部成功，永远不需要撤销它。
    这个排序不是优化，它决定了 Saga 能不能工作，而它经常和「哪一步最快返回」的直觉相反。
    补偿失败了怎么办
    不能再补偿（无限递归）。唯一出路是重试到成功 + 超过阈值转人工。这意味着补偿必须幂等，且必须有一个「卡住的 Saga」列表和处理它们的运维流程——没有这个人工兜底的 Saga 实现是不完整的。
    还有隔离性
    ACID 的 I 在 Saga 里完全不存在，中间态对外可见。三种处理都是业务层面的：语义锁（自己实现业务级锁，要处理超时）、把中间态设计成合法状态（订单就是有「待支付」——这是最好的做法）、或预留而非扣减（库存分「可用」和「已预留」）。
  2. 高级怎么把一个单体安全地拆成微服务？

    绞杀者模式（Strangler Fig）：在单体前放一层路由，逐个把功能剥离成新服务、把流量慢慢切过去，老单体功能逐步被「绞杀」直至下线。绝不做大爆炸重写。

    拆的顺序很重要
    先拆叶子节点——被别人依赖少、自己依赖别人也少的那些（比如通知、报表）。它们剥离后对主流程影响最小，而且能让团队先把基建（服务模板、CI/CD、追踪、部署流程）跑通。不要一上来就拆核心域，那时你既不熟悉流程也没有基建。
    数据怎么迁
    这是最难的一步，通常要经历：① 新服务读老库（先只拆代码不拆数据）→ ② 双写（新老库同时写，对账）→ ③ 切读到新库 → ④ 停写老库、删表。每一步都可回滚，②③之间要跑足够长时间的对账。
    最容易被跳过的一步：④
    很多迁移停在③——新库在用了，老表还留着「以防万一」。结果是共享数据库的耦合仍然存在，只是没人再看它。要有明确的删除计划和负责人。
    判断拆分成功的标志
    不是「服务跑起来了」，而是「这个服务能独立发版，且发版不需要通知任何人」。做不到就说明耦合还在，只是从代码层挪到了别处。
  3. 高级微服务下怎么排查一个「某些请求偶发慢」的问题？

    单体看一处日志就行，微服务一个请求跨 5 个服务——没有链路追踪就是盲人摸象。

    第一步：确认追踪是完整的
    trace_id 必须贯穿同步调用和异步事件。很多系统的追踪在消息队列那里断掉了——事件被消费时开了一条新的 trace，于是「下单慢」和「积分服务慢」看起来毫无关系。这是 ADR-002 那个「异步化」决策的配套成本。
    第二步：分清是排队还是服务时间
    每一跳都要分开打点「在队列里的时间」和「实际处理的时间」。两者的解法完全不同：排队靠降利用率或加容量，服务时间的长尾只能靠隔离或让慢的变快（容量篇 §3）。
    第三步：注意扇出放大
    如果这一跳是并行调用多个下游，那么「偶发慢」可能不是任何一个下游变慢了，而是扇出本身在放大尾部：每个下游 P99 是 100 ms，扇出 10 个时「至少一个慢」的概率是 9.6%，扇出 100 个是 63%。这时优化任何单个下游的平均延迟都没用，要么降扇出，要么对下游提 P99.9 的 SLO，要么上对冲请求。
    一个常见的误诊
    看到「A 调 B 花了 200 ms，但 B 自己记录只花了 20 ms」，直觉是网络问题。更常见的原因是 B 的线程池排队（请求到了但没被处理）或客户端连接池耗尽（请求还没发出去）。两者都在「B 的处理时间」之外，但也不是网络。
  4. 高级如果让你重新评估一个已经拆成 40 个服务的系统，你看什么？

    核心问题只有一个：这 40 个服务，有多少个是真的能独立发版的？数出来的那个比例，就是这次拆分的实际收益率。

    要量的几个数
    ① 跨服务 PR 比例（同一个需求改了几个服务）——高说明边界错了；② 同步调用链的深度分布——长链是延迟和可用性的双重杀手；③ 每个服务的负责团队数——大于 1 就等于没有独立部署；④ 共享数据库的表——一张都不该有；⑤ 没有降级方案的强依赖数——它们都在可用性的乘法里。
    合并也是一种正确的演进
    这一点常被忽略：如果两个服务总是一起改、总是一起发版、由同一个团队负责，那就把它们合了。「服务数量减少」不是失败，是修正。反而「服务数只增不减」说明没有人在做架构维护。
    最有价值的一个观察角度
    看组织图和服务依赖图对不对得上。康威定律说架构会映射组织，反过来说：如果两张图差异很大，那么差异的地方就是持续摩擦的来源——要么改架构去贴组织，要么改组织去贴架构，但不能让它们长期不一致。
