01

可观测性 vs 监控：思维方式的根本差异

为什么监控不够用了 · 可观测性的三个维度 · 架构师的可观测性 KPI

监控回答「我预想到的那几个灯红了没」。可观测回答「灯红了之后，我能不能从输出反推出内部状态」——包括从没见过的故障。

1.1 为什么监控不够用了

「You build it, you run it.」可观测性是每个服务的基础设施，不是事后加的 Dashboard。

1.2 可观测性的三个维度

控制理论里还有可控性（外部输入能否改内部状态）和可调试性（出事能否定位）。本文只做可观测：Traces / Metrics / Logs / Profiles 四类信号。

1.3 架构师的可观测性 KPI

每个服务至少定义：黄金信号（延迟 / 吞吐 / 错误率 / 饱和度）、请求侧 RED、资源侧 USE、以及 SLI + Error Budget——告警跟预算走，不跟拍脑袋阈值走。

OpenTelemetry 的价值是同一套数据模型 + SDK：一次埋点，四种信号都能带上关联键。2026 年它是事实标准，新项目不要再接各家私有 SDK。

Tracing 深入：Span 模型与语义约定

Trace 与 Span 的精确定义 · Trace 结构可视化 · Span 命名最佳实践 · OTel Semantic Conventions（语义约定）

Trace 是一棵 Span 树：同一 trace_id，父子靠 parent_span_id。

3.1 Trace 与 Span 的精确定义

Trace：一次端到端请求的执行路径。Span：树上一个有起止时间的操作（函数、DB、HTTP）。
字段作用坑
trace_id 128-bit整棵树共享丢了就拼不回链路
span_id / parent_span_id本节点 / 父节点根 Span 的 parent 为空
name + SpanKind操作名；INTERNAL / SERVER / CLIENT / PRODUCER / CONSUMERname 禁止拼 user_id、具体 URL
Attributes / Events / Links维度、时间点事件、跨 Trace 关联（MQ）高基数放 Attribute，不放 name
statusUNSET / OK / ERRORERROR 是尾采样的保留信号

3.2 Trace 结构可视化

3.3 Span 命名最佳实践

低基数模板：GET /users/{id}、SELECT users、grpc.UserService/GetProfile。user_id 与具体 URL 进 Attribute。query 这种名字等于没埋。

3.4 OTel Semantic Conventions（语义约定）

标准 Attribute 名让 Grafana / Jaeger 能认出 HTTP / DB / RPC，不要自创 http_method 这种近义词。

场景关键 Attributes
HTTP 服务端http.request.method, http.route, http.response.status_code, network.peer.address
HTTP 客户端http.request.method, url.full, server.address, server.port
数据库db.system, db.name, db.statement, db.operation.name
消息系统messaging.system, messaging.destination.name, messaging.operation.type
gRPCrpc.system=grpc, rpc.service, rpc.method, rpc.grpc.status_code
异常exception.type, exception.message, exception.stacktrace
服务标识service.name, service.version, service.namespace
04

Context Propagation：跨进程传递 Trace ID

为什么需要 Propagation · W3C TraceContext 标准 · Baggage：跨服务传递业务数据

4.1 为什么需要 Propagation

进程内靠 TLS 隐式传 Context。跨进程（HTTP / gRPC / 消息）必须显式 Inject 到载体、对端 Extract，否则链路在边界断裂。

4.2 W3C TraceContext 标准

propagator.Inject(HttpHeaderCarrier{req.headers}, RuntimeContext::GetCurrent());
auto ctx = propagator.Extract(HttpHeaderCarrier{req.headers},
                              RuntimeContext::GetCurrent());
auto span = tracer->StartSpan("handle", StartSpanOptions{.parent = ctx});

4.3 Baggage：跨服务传递业务数据

Baggage 可随 Trace 带少量业务键（tenant_id、feature_flag）。它会传到所有下游——禁止放 token / 密码，体积也要克制。

14.2 PromQL 高频公式速查

QPS：rate(http_requests_total[5m])。错误率：5xx 的 rate 除以总 rate。P99：§8.2 那条 histogram_quantile。饱和度：1 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m]))。其余模式见上方表格。

14.3 核心总结

  • 监控看已知未知；可观测回答未知未知。
  • 四支柱钉在同一 trace_id；OTel 统一模型，不统一后端。
  • 跨进程必须 Inject/Extract；错误+超 SLO 全采，其余抽稀。
  • 延迟用 Histogram；bucket 围着 SLO 加密；label 禁止高基数。
  • 日志 event 受控；spdlog 细节见实践篇。车端走漏斗，不要把云上管道原样搬上车。

高频面试题 · 可观测性

SRE / Platform / 高级后端架构师面试必考。点击题目展开答案
Q1 监控（Monitoring）和可观测性（Observability）有什么本质区别？
P0主题：概念难度：⭐⭐
核心答案（一句话区分）
  • 监控："我知道什么会出错，所以我去看那些指标"。针对 known unknowns（已知会出问题的地方）。
  • 可观测性："无论出什么问题，我都能通过系统输出找到原因"。针对 unknown unknowns（前所未见的问题）。
实践层面的差异
维度监控可观测性
数据类型预定义指标高维数据 + 任意切片
问题类型"CPU 高""哪个用户的哪类请求让哪段代码 CPU 高"
告警阈值告警SLO + Error Budget
排查看预设 Dashboard从 Metric→Trace→Log→Profile 钻取
面试加分：可观测性的"control theory" 起源

提到这个术语来自控制理论（Rudolf E. Kálmán, 1960）——一个系统是 observable 的当且仅当能从外部输出推断出内部状态。这把可观测性从"工具集"提升到"系统属性"。

Q2 Metric 的 Histogram 和 Summary 有什么区别？多副本聚合时该选哪个？
P0主题：Metric难度：⭐⭐⭐
核心区别
维度HistogramSummary
分位数计算服务端（PromQL histogram_quantile）客户端（采集时预计算）
精度受 Bucket 划分影响高（精确分位数）
多副本聚合✅ 可聚合❌ 不可聚合（数学上不能合并各实例 P99）
客户端开销低（只计数）高（维护 t-digest 等数据结构）
多副本场景选 Histogram

关键原因：P99 不可聚合。三个实例各自的 P99 是 50ms / 60ms / 70ms，整体 P99 ≠ avg(50,60,70) = 60ms，也不是 max = 70ms。要正确计算，必须有原始数据。

Histogram 在每个实例只存 bucket 计数（如 le=50ms: 100 次，le=100ms: 150 次），计数可以加，加起来后用 histogram_quantile() 估算整体分位数。

面试加分：Bucket 设计

"Bucket 划分要覆盖实际值的分布。如果 SLO 是 P99 ≤ 100ms，必须在 100ms 附近有足够密集的 Bucket（比如 50/75/100/150/200ms），否则 P99 估算有大误差（线性插值假设）。"

Q3 分布式 Tracing 的 Head 采样和 Tail 采样区别？生产环境怎么选？
P0主题：Tracing难度：⭐⭐⭐
核心区别
维度Head 采样Tail 采样
决策时机Trace 起点Trace 完成后
能识别"有趣 Trace"❌ 不能✅ 能（错误/慢）
开销极低高（需要缓存全部）
典型采样率1-10%错误 100% + 其他 1%
生产推荐：组合采样

用 OTel Collector 的 tail_sampling 处理器：

  1. 错误 Trace（status_code = ERROR）→ 100% 保留
  2. 慢 Trace（latency > SLO）→ 100% 保留
  3. 其他 → 1% 均匀采样
  4. 速率上限：1000 spans/s（防爆炸）
陷阱：决定性采样（Deterministic）的价值

同一 Trace ID 在所有服务必须做出相同的采样决定，否则会出现"断裂的 Trace"——只有部分服务的 Span，链路不完整。OTel 用 TraceIdRatioBasedSampler 对 TraceID 哈希做决策保证一致性。

Q4 Trace ID 是如何跨服务传播的？讲一下 W3C TraceContext 标准。
P0主题：Tracing难度：⭐⭐⭐
核心答案

跨进程传播必须把 Trace 上下文显式注入到载体（HTTP header / 消息属性）。

W3C TraceContext 是 2020 年成为 W3C Recommendation 的标准：

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ^  ^                                ^                ^
             |  Trace ID (128 bit hex)           Span ID (64 bit) Flags
             version=00                                            01=sampled
Inject / Extract 流程
  1. 客户端发请求前：从当前 Context 取 Trace 信息，Inject 到 HTTP headers
  2. 服务端收请求：从 headers Extract 出来，作为父 Span 上下文创建新 Span
  3. 新 Span 的 parent_span_id = 客户端的 Span ID，trace_id 不变
追问：Baggage 是什么？

除了 traceparent，Baggage（W3C 也定义了）可以传递任意 key-value（user_id、tenant_id），跟随 Trace 传播。陷阱：Baggage 会传到所有下游，不能放敏感信息（token / 密码）。

面试加分：多种传播格式

"在迁移期间可能要支持多种格式：W3C TraceContext（标准）、B3（Zipkin/Jaeger）、Datadog。OTel 用 CompositePropagator 串联多个，兼容老系统。"

Q5 如何把 Metric、Trace、Log 三个信号关联起来？给一个真实的故障排查流程。
P1主题：综合实战难度：⭐⭐⭐⭐
关联机制
  • Trace ↔ Log：日志带 trace_id 字段；查询日志时可按 trace_id 过滤
  • Metric ↔ Trace：用 Exemplar（Histogram 数据点附带 trace_id 示例），从 P99 直接跳到具体 Trace
  • Trace ↔ Profile：Profile 数据带 trace_id（pprof labels），找到慢 span 对应的火焰图
典型故障排查流程
  1. 告警（Metric）："订单服务 P99 延迟 > 500ms"
  2. 下钻 Trace：点击 P99 数据点的 Exemplar → 跳到 Jaeger，看到这条 Trace 的完整 Span 树
  3. 定位慢 Span：发现 SQL 查询占 90% 时间
  4. 查 Log：用 trace_id 过滤日志，看到查询参数 + 慢 SQL 文本
  5. 看 Profile：（可选）看那段时间的 CPU profile，确认是数据库 driver 在等待

这就是"3+1 支柱串联调试"，是 OpenTelemetry 的终极价值。

面试加分：Service-level Objectives (SLO)

"告警阈值不应该手动设——应该基于 SLO（如可用性 99.9%）和 Error Budget。当 Error Budget 消耗速率超过预期 → 触发告警。这比"P99 > 500ms"这种硬阈值更合理，避免告警疲劳。"
