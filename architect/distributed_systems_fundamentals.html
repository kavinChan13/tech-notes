分布式系统的根本问题：为什么这么难

"分布式计算的八大谬误"（Peter Deutsch, Sun Microsystems 1994） · 分布式系统的三大不可能 · 分布式系统的时间问题 · 部分失败（Partial Failure）

分布式系统的复杂性都根源于两个物理现实：节点会故障、网络会延迟丢包和分区。承认这两点，大量"单机上天经地义"的假设就全部崩塌。

1.1 "分布式计算的八大谬误"（Peter Deutsch, Sun Microsystems 1994）

还要补两条 1994 年没写、今天更常踩的：进程会被暂停（GC、swap、容器迁移，几百毫秒到几十秒），以及时钟不同步（§1.3）。

1.2 分布式系统的三大不可能

不可能结论精确说法工程判据（你要据此做什么）
FLP（1985）异步网络中只要有一个节点可能故障，就不存在确定性共识算法共识实现全靠超时 + 随机化换 liveness，给选举失败留重试与告警
CAP（2000）网络分区时 C 与 A 只能取一逐份数据回答"分区时能不能返回旧值"（§2.1）
拜占庭容错节点可能撒谎时，容忍 f 个故障需要 3f+1 个节点内部系统按 crash-fault 设计即可；只有开放网络才值得付 BFT 的代价

1.3 分布式系统的时间问题

永远不要用物理时钟决定分布式事件的先后。NTP 误差常态 1–50ms，VM 迁移、休眠、管理员调时还会让时钟整段跳跃；两个节点读到的"现在"差上几百毫秒是常态。

判据：只要"谁先发生"用 Lamport，要区分"并发 vs 因果"（冲突检测、多副本合并）必须上向量时钟。比较函数就是全部：

// Lamport：只能给出一个全序，无法回答"是否并发"
void on_send(int& c)            { ++c; }
void on_recv(int& c, int msg_c) { c = std::max(c, msg_c) + 1; }

// 向量时钟：≤ 全维成立且至少一维严格小 = 真的 happens-before
enum class Ord { Before, After, Concurrent, Equal };

Ord compare(const VC& a, const VC& b) {
    bool le = true, ge = true;
    for (size_t i = 0; i < a.size(); ++i) {
        if (a[i] > b[i]) le = false;
        if (a[i] < b[i]) ge = false;
    }
    if (le && ge) return Ord::Equal;
    if (le)       return Ord::Before;      // a → b
    if (ge)       return Ord::After;
    return Ord::Concurrent;              // 冲突，交给应用层 merge
}

混合逻辑时钟（HLC）物理时钟在高位、逻辑计数在低位，既对得上真实时间又保留 happens-before，CockroachDB 用的就是它。更多见进阶篇 §5。

1.4 部分失败（Partial Failure）

单机故障是全或无，分布式故障是部分失败：

思维转变："你永远不知道一个操作是否成功，只知道它可能成功了"——所以要先定清楚是"至少一次"还是"至多一次"，再让重试无害。
02

CAP / PACELC / BASE：正确理解，避免常见误读

CAP 定理精确含义 · PACELC：CAP 的改进版 · BASE：AP 系统的设计哲学

2.1 CAP 定理精确含义

三个字母的精确含义：C = Linearizability（每次读返回最新写或报错，不是 ACID 的 C）；A = 每次请求都得到非错误响应（允许是旧数据）；P = 分区时系统继续运行。P 是物理现实、不是选项。

三个要现场纠正的误读：①「选 AP 就没有一致性」——AP 系统无分区时照样强一致；②「关系数据库是 CA」——不存在 CA，不容忍分区的那是单机；③「CAP 的 C = ACID 的 C」——前者是 Linearizability，后者是"事务后仍满足业务约束"，毫无关系。

2.2 PACELC：CAP 的改进版

PACELC（Abadi, 2012）：If Partition, choose A or C; Else, choose Latency or Consistency.

它补上了 CAP 缺的那一半：没有分区时也在做取舍。强一致要求写等多数派确认，那是实打实的额外 RTT——这才是系统 99.9% 时间里真正在付的账。

系统PartitionElse说明
DynamoDBPAEL可用性优先，最终一致
CassandraPAEL可调一致性（默认 EL）
ZooKeeperPCEC强一致，分区时停服
etcdPCECRaft，强一致
CockroachDBPCEL/EC默认 EC，可配置
MySQL（单主）PCEC强一致，但非分布式

2.3 BASE：AP 系统的设计哲学

ACID 的反面：Basically Available（可降级、可返回旧值，但不能不响应）、Soft State（没有新写入时状态也会自己变，后台复制还在跑）、Eventually Consistent（停写后副本终将收敛，典型是秒级）。

BASE 不是"放弃一致性"，而是"接受短暂不一致换取高可用"。落到工作上只有三件事：
  1. 逐份数据判定允许最终一致（头像、点赞数）还是必须强一致（余额、库存、唯一性约束）
  2. 给前者定收敛 SLA（如"99.9% 在 5 秒内"），否则"最终"就是永远的借口
  3. 为它选定冲突解决策略：LWW / version vector / CRDT，见 §3.3

3.2 Linearizability 的精确定义

每个操作表现得好像在 invocation 与 completion 之间的某一瞬间原子生效。这个定义是可测的——找不到一种生效点排法能解释所有返回值，这段历史就违反了线性一致。

3.3 最终一致性的陷阱

"最终一致"不是"随便不一致"的借口。收敛 SLA 与冲突策略见 §2.3，这里再补一问：用户读到旧值那一刻看到的是什么？点赞数少一个无所谓，余额少一笔就是事故。

Raft 共识算法完整讲解

Raft 基础：三种角色 · Term（任期）：Raft 的逻辑时钟 · Leader 选举：完整流程 · 日志复制：AppendEntries RPC · 安全性：为什么不会产生脑裂 · …

Raft 的设计目标就是"能被读懂并正确实现"，如今是 etcd、CockroachDB、TiKV 的共识内核。它把共识拆成三件事：选主、日志复制、安全性。Multi-Raft、ReadIndex 证明等边角见进阶篇 §3。

4.3 Leader 选举：完整流程

投票只有两个条件：candidate.term >= currentTerm，且 candidate 的日志不落后于自己（同一 term 内先到先得）。第二个条件是整个 Raft 安全性的支点，它的全部实现就是这个比较函数：

bool candidate_log_up_to_date(
    int candidate_last_term, int candidate_last_index,
    int my_last_term,         int my_last_index) {
    if (candidate_last_term != my_last_term)
        return candidate_last_term > my_last_term;
    return candidate_last_index >= my_last_index;
}

4.4 日志复制：AppendEntries RPC

Log Matching：每条 AppendEntries 都带上前一条的 (prevLogIndex, prevLogTerm)，Follower 对不上就拒绝，Leader 回退一格重试，直到找到双方最后一个共同点再强制覆盖之后的日志。这条归纳式检查换来一个很强的性质：两份日志只要某个位置的 term 相同，此前的全部内容就一定相同。

4.5 安全性：为什么不会产生脑裂

不变量只有一句：已提交的日志永远不会被覆盖。它靠"多数派提交 + 选举时查日志"两条规则夹出来：

反直觉的一条：Leader 不能靠"已在多数节点上"来提交旧 term 的日志。那条日志此后仍可能被另一个 term 的 Leader 覆盖，"已提交"的东西就丢了。所以 Raft 规定只对 currentTerm 的日志计票，旧条目靠"新 term 条目提交时顺带生效"。这是论文里最容易写错的一处。

4.6 成员变更（Membership Change）

风险是新旧配置各自选出一个 Leader。解法是让新旧多数派始终有交集：单步变更一次只动一个节点，新配置作为一条日志提交后才生效，两侧多数派必然相交；一次替换多台才需要联合共识过渡。细节见进阶篇 §3。

4.7 日志压缩（Log Compaction）与快照

状态机在 index=N 做快照 → 丢弃 index ≤ N 的日志 → 保留 lastIncludedIndex / Term → 落后 Follower 收 InstallSnapshot

InstallSnapshot RPC 比逐条日志回放更高效。

5.2 ZAB（ZooKeeper Atomic Broadcast）

ZAB 早于 Raft，骨架却几乎一样，差别只在措辞：epoch 就是 term，Discovery / Synchronization / Broadcast 三段就是选举 + 追日志 + 正常复制，保证叫FIFO 全序广播而不是"日志顺序"。

需要共识服务就直接用 etcd 或 ZooKeeper，不要自己实现。一个细节偏差（比如上面那条"只提交 currentTerm"）就是静默丢数据，而且只在故障切换时才暴露。
06

分布式事务：2PC / 3PC / TCC

为什么不能直接用数据库事务 · 两阶段提交（2PC） · 三阶段提交（3PC） · TCC（Try-Confirm-Cancel）

"让多个服务的操作要么全成功要么全回滚"没有完美方案，每一种都在一致性、可用性、复杂度之间做取舍。

6.1 为什么不能直接用数据库事务

"Database per Service"之后，一次业务操作要落进多个互不相识的数据库，单库的 BEGIN…COMMIT 包不住它。而跨库协调的代价是数量级的——锁要跨网络持有，吞吐掉 10–100 倍。所以下面四个方案，本质都在回答同一个问题：这份不一致能容忍多久。

6.2 两阶段提交（2PC）

Phase 1 让参与者锁住资源回答 YES/NO，Phase 2 由协调者广播 COMMIT 或 ABORT。问题全在两个阶段之间那一小段：

问题后果
协调者单点：Phase 2 前宕机事务悬挂（in-doubt），锁不释放，需人工介入
阻塞性：prepared 期间必须持锁高并发下锁竞争急剧恶化，吞吐塌陷
同步木桶：要等最慢的参与者整个事务延迟 = 最慢节点延迟
2 个 RTT：Prepare + Commit跨机房时延迟直接翻倍

6.3 三阶段提交（3PC）

在两阶段中间插入 PreCommit，让参与者在协调者失联后能自主推断决议，不再无限阻塞；代价是网络分区时可能出现不一致提交。用"可能出错"换"不阻塞"多数场景并不划算，所以几乎没有生产系统用纯 3PC。

6.4 TCC（Try-Confirm-Cancel）

TCC 把两阶段搬到业务层：Try 冻结 10 件库存但不减总量，Confirm 把冻结转成真实扣减，Cancel 解冻归还。数据库锁在每一步内部就释放了，跨服务期间只剩一个业务状态字段，并发能力因此远好于 2PC。

TCC 的复杂度全在三个方法都要抗住重试和乱序：Try / Confirm / Cancel 各自幂等；空回滚——根本没 Try 过就收到 Cancel，也要能安全返回成功；防悬挂——Cancel 之后姗姗来迟的 Try 必须被拒绝，否则冻结的资源再没人释放。落地统一靠一张记 (xid, branch_id, state) 的分支状态表，三个方法都先查表。
维度2PCTCC
锁DB 行锁，prepared 期间一直持有业务字段冻结，不占 DB 锁
代价实现简单（框架代劳），但阻塞、吞吐差每个接口要写 3 个方法，侵入业务
适用同库 / XA跨服务、高并发资金类
07

Saga / Outbox / Event Sourcing：最终一致性事务

Saga 模式 · Outbox 模式：可靠地发布事件 · Event Sourcing：事件溯源

7.1 Saga 模式

Saga：把分布式事务拆成一串本地事务，每步配一个补偿事务。就像订旅行——租车没订上不会"原子回滚"，而是退机票、退酒店。Saga 没有回滚，只有一串"撤销操作"。

判据很直接：步骤 ≤ 3 且天然事件驱动用编舞，超过 3 步或要人工介入 / 超时重试 / 看进度就用编排。订单类流程最后基本都会走向编排。

三个陷阱全都出在"它不是事务"：①补偿本身会失败——补偿也要幂等 + 持久化重试队列，不能写成一个 try/catch；②脏读——跑到一半时别人读得到中间态，得靠语义锁（订单标 PROCESSING，其他流程见到就避让）；③无隔离性——两个并发 Saga 会互相踩，得用版本号做乐观并发。

7.2 Outbox 模式：可靠地发布事件

Outbox 模式：业务数据与"待发布事件"写进同一个事务，再由后台进程把 outbox 表里的事件投到消息队列——两者要么都发生，要么都不发生。
生活类比——餐厅小票：点单和小票一起落到收银台，传菜员再照着小票通知后厨。他临时走开也不要紧，小票还在——绝不会"钱收了但后厨不知道要做菜"。
轮询实现简单但有秒级延迟、给主库加负载；CDC 让 Debezium 直接读数据库 WAL 把变更投到 Kafka，亚秒级且业务代码一行不改，代价是多一套组件要运维。Outbox + CDC 是事件驱动微服务最可靠的发布方案。

at-least-once 的代价：幂等键与去重

Outbox 投递、Kafka 重投、客户端重试给出的都是 at-least-once（§1.4 的四种超时无法区分）。整条链路的正确性因此全押在消费端能否安全地重复处理同一条消息上：

// 幂等键必须来自业务自然键：同一次点击重试多少遍都得算出同一个键。
// 用随机 UUID 等于没有幂等——每次重试都成了"新请求"。
std::string idem_key(const Request& r) {
    return r.tenant_id + ":" + r.order_id + ":" + r.op;  // "t7:ORD-1001:charge"
}

Result handle(const Request& r) {
    auto key = idem_key(r);
    Txn tx = db_.begin();
    // 去重表在 key 上有 UNIQUE 索引；插不进去 = 这次请求以前处理过
    if (!tx.try_insert_dedup(key))          // INSERT ... ON CONFLICT DO NOTHING
        return tx.load_saved_result(key);   // 回放旧结果，不重复执行副作用

    auto res = apply_business_effect(tx, r);  // 扣款 / 减库存 / 建单
    tx.save_result(key, res);
    tx.commit();   // ← 去重记录与业务副作用同一事务提交，这是全部关键
    return res;
}
判据一句话：能用数据库唯一约束表达的幂等，就别写代码去查重。UNIQUE(idem_key) 让并发重试里恰好一个成功、其余撞冲突；"先 SELECT 再 INSERT"中间那一瞬间就是双写窗口。

7.3 Event Sourcing（事件溯源）

Event Sourcing：不存"当前状态"，而是把改变状态的那一串事件本身当作唯一真相持久化，当前状态由重放事件算出。也就是银行流水——存的是每一笔进出，余额随时能算回来，而且历史完整、可审计。

传统状态存储 vs 事件溯源

❌ 传统：只存当前状态

UPDATE account SET balance = 1000

问题：覆盖式更新，历史丢失——答不出"上周三余额是多少"。

✅ 事件溯源：存事件序列

Deposited(+1500) → Withdrawn(-500) → …

优点：全历史可查、可审计、可重建任意时间点状态。

快照优化：事件多了从头重放很慢，每 N 个事件存一次快照，重建时"最近快照 + 之后的少量事件"即可。
不是银弹：事件写入后不可变，schema 演进很棘手；查"当前状态"也不如传统表直接，得配 CQRS 读模型（订阅事件投影出的物化视图）。只在真正需要完整历史与审计的领域（金融、账务）才值得引入。

分布式锁：Redis / etcd / ZooKeeper

分布式锁的需求 · Redis 分布式锁（SET NX） · etcd / ZooKeeper 分布式锁（更强保证）

9.1 分布式锁的需求

生活类比——会议室钥匙：std::mutex 是把钥匙挂在自己办公室的墙上，别的楼层（别的进程、别的机器）看不到那面墙，于是另配一把，两拨人同时进屋。分布式锁就是把钥匙挪到所有人都够得着的公共前台（Redis / etcd / ZooKeeper）。

典型场景：同一个定时任务不能被多个实例同时跑、集群级别的限流串行化、共享设备与文件的互斥访问。

9.2 Redis 分布式锁（SET NX）

一条命令逐字拆解：SET lock_key <UUID> NX PX 30000 三部分缺一不可——NX 让"判断不存在 + 写入"成为一条原子命令（拆成 GET 再 SET 就有竞态，两个客户端会同时以为自己抢到了）；PX 是崩溃兜底，持锁进程死了锁也会过期；value 用随机 UUID 证明"这把锁是我加的"。
释放必须走 Lua。"核对 value 再删"若拆成 GET + DEL 两步就有这个窗口：你刚确认是自己的锁，它恰好过期并被别人抢走，你的 DEL 删掉的是别人的锁。Lua 把检查与删除合成一个原子操作。 
class RedisDistLock {
    RedisClient& redis_;
    std::string  key_;
    std::string  token_;      // 唯一标识符
    std::chrono::milliseconds ttl_;
public:
    bool try_acquire() {
        token_ = generate_uuid();
        auto result = redis_.set(key_, token_,
            SetOptions{.nx=true, .px=ttl_.count()});
        return result == "OK";
    }
    void release() {
        static const char* lua = R"""(
            if redis.call('get',KEYS[1])==ARGV[1]
            then return redis.call('del',KEYS[1])
            else return 0 end
        )""";
        redis_.eval(lua, {key_}, {token_});
    }
};

三个安全问题，同一个形状

GC 停顿（暂停几十秒，锁超时被别人拿走）、主从延迟（主节点写锁后崩溃，从节点没复制到，新主上没这把锁）、网络分区（持锁方与 Redis 失联，锁被人抢走）——三者同形：持锁进程"以为"自己还持锁，其实早已不是。

Fencing Token：让"迟到的写"失效

锁本身治不了，就让过期锁的写入在下游被拒绝：发锁时附一个单调递增编号，下游记住见过的最大值，只收更大的。这正是 Martin Kleppmann 那篇著名批评的落点——正确性不该由锁来保证。

9.3 etcd / ZooKeeper 分布式锁（更强保证）

生活类比——银行取号排队：取一张顺序递增的号票，只盯着前一号，前面那位办完就轮到你。etcd / ZooKeeper 锁就是这样：各自创建顺序编号的临时节点，最小者持锁，其余只 watch 紧邻自己的前一个——既FIFO 公平不饿死，又避开了惊群。
为什么比 Redis 锁更强？① 底层是 Raft/ZAB，写锁要多数派确认，不存在主从异步复制丢锁；② 锁绑定在 Lease / 临时节点上，客户端崩溃或断连会话即过期，锁自动释放，不必靠猜一个 TTL。代价是走共识、延迟更高，所以只在"绝对互斥"的关键路径上用。
建 Lease→ 挂 Lease 建 key→ revision 最小？是 → 获锁否 → watch 前一个 key
方案一致性延迟可用性适用
Redis 单节点弱低中限流、防重复（容忍偶发失效）
RedLock中（有争议）中中比单节点更强，仍有边角 case
etcd强（Raft）中中关键资源互斥、Leader 选举

一句话决策：
  1. 先问能不能不用锁——唯一约束 / 乐观锁版本号 / 幂等设计能顶就别用。
  2. 限流、防重复点击这类可容忍偶发失效 → Redis SET NX。
  3. 扣库存、选主这类绝对互斥 → etcd / ZooKeeper。
  4. 无论哪种，下游怕双写就加 fencing token 兜底。

消息中间件：Kafka 深入

Kafka 核心概念 · ISR（In-Sync Replicas）机制 · Producer 的 acks 配置 · Exactly-Once 语义（EOS） · 消费者组 Rebalance · …

Kafka 是分布式消息队列的事实标准。它的机制里真正会影响架构决策的，是"消息到底什么时候算写成功、消费者什么时候能看见"这一条线：ISR、HW、acks、EOS 说的都是它。

10.1 Kafka 核心概念

概念含义
PartitionTopic 的物理分片，本身是一个只追加的有序日志；顺序保证只在分区内成立
Offset消息在分区内的位置，单调递增，由消费者自己记
Consumer Group同一 Group 内一个分区只被一个消费者吃——所以并发度上限就是分区数
Leader / Follower每个分区一个 Leader 负责读写，Follower 从它拉数据；Broker 是承载这些分区的节点

10.2 ISR（In-Sync Replicas）机制

ISR：与 Leader "足够同步"的副本集合。判据是最近 replica.lag.time.max.ms（默认 30s）内发过 fetch，且落后量没超过阈值。

HW（High Watermark）：消费者可见的最高偏移量

10.3 Producer 的 acks 配置

acks 值含义消息丢失风险延迟
acks=0不等确认，fire-and-forget高最低
acks=1Leader 写入即返回（Follower 未必写入）中（Leader 挂则丢）中
acks=-1 (all)等所有 ISR 成员写入低（ISR 都挂才丢）高

10.4 Exactly-Once 语义（EOS）

Kafka 0.11+ 的 Exactly-Once 由两个机制拼成：

幂等 Producer

开 enable.idempotence=true，每个 Producer 带 PID + Seq，Broker 拒收重复的 (PID, Partition, Seq)，保证单分区内恰好一次。

事务 API

initTransactions / beginTransaction / commitTransaction 让跨多个分区的写变成原子的；Consumer 侧配 isolation.level=read_committed 只读已提交的消息。

10.5 消费者组 Rebalance

成员加入 / 退出 / 崩溃都会触发 Rebalance，代价是期间所有消费者停止消费。调大 session.timeout.ms 与 max.poll.interval.ms 可避免"处理慢"被误判成掉线；Kafka 2.4+ 换 CooperativeStickyAssignor 后重分配变成渐进式，不再 STW。

11.1 服务发现的两种模式

Client-Side Discovery

客户端自己查注册中心、自己做负载均衡（Eureka + Ribbon）。

取舍：策略可以很灵活（版本感知、区域感知），代价是客户端与注册中心耦合，每种语言都要实现一遍。

Server-Side Discovery

请求先到 LB / 网关，由它查注册中心再转发（K8s Service、Envoy）。

取舍：客户端无感、与语言无关，代价是多一跳，而且 LB 自己要做高可用。

高频面试题 · 分布式系统

所有公司架构师面试的必考点：CAP、Raft、分布式事务、Kafka。点击题目展开答案
Q1 请准确解释 CAP 定理。它的 C 和 ACID 的 C 一样吗？
P0主题：CAP 基础难度：⭐⭐⭐必问题
核心答案（先纠正常见误读）

CAP 的精确表述：分布式系统在网络分区时，只能在一致性（C）和可用性（A）之间二选一。不是任何时候都二选一——没有分区时 C 和 A 都能拿到。

  • C = Linearizability：每次读都返回最新写入值，或者错误。所有节点表现如同一台机器。
  • A：每次请求都得到非错误响应（可能是旧数据）。
  • P：网络分区时系统继续工作（节点间消息可丢失/延迟）。

CAP 的 C ≠ ACID 的 C：

  • CAP 的 C：操作的"原子可见性"（Linearizability）
  • ACID 的 C：事务后数据满足约束（业务规则不被破坏）
陷阱 1：选 "CA" 系统

"我用关系数据库，它是 CA 系统" — 错。CA 系统不存在，因为分布式系统必须容忍网络分区。"传统单机 RDBMS" 严格说不是分布式系统。

陷阱 2：选 AP 就没有一致性

错。AP 系统在没有分区时可以提供强一致；只是在分区发生时优先返回（可能是旧的）数据。

追问：PACELC 是什么？

If Partition, A or C; Else, Latency or Consistency. — 即使没有分区，强一致性（Linearizability）也需要额外同步开销（更高延迟）。这是 CAP 没说清的一半。DynamoDB 是 PA/EL，etcd 是 PC/EC。

Q2 讲一下 Raft 的 Leader 选举过程。为什么 candidate 必须"日志最新"才能当选？
P0主题：共识算法难度：⭐⭐⭐⭐
选举过程
  1. Follower 选举超时（150-300ms 随机），自增 currentTerm，变 Candidate
  2. 给所有节点发 RequestVote(term, lastLogIndex, lastLogTerm)
  3. 每个 Follower 在同一 term 内只投一票（先到先得），且要求 candidate 日志 ≥ 自己
  4. Candidate 获得多数派（> N/2）选票 → 成为 Leader
  5. 立即发心跳（AppendEntries 空 entries）宣告权威，其他节点退回 Follower
为什么必须"日志最新"才能当选（核心问题）

Raft 的最关键不变量：已经提交的日志永远不能被覆盖/丢失。

已提交 = 多数节点写入。新 Leader 一定也来自多数派，所以多数派的交集里至少有一个节点拥有所有已提交日志。投票规则保证只有"拥有所有已提交日志"的节点才能当选 Leader——这样新 Leader 不会回滚已提交的日志。

日志"更新"的比较规则
  1. 先比 lastLogTerm（最后一条日志的 term），大的更新
  2. term 相同，再比 lastLogIndex（日志长度），长的更新
追问：为什么选举超时要随机化？

避免多个 Follower 同时超时同时发起选举导致 split vote（没人能拿到多数票）。随机化让一个节点通常比其他节点早一点超时，能先获得多数票。

面试加分：Pre-Vote 优化

不稳定网络下，孤立节点会反复自增 term 发起选举，term 涨得很快。当它重新加入集群时会扰乱当前 Leader。Pre-Vote 是先用"试探票"问 majority 自己有没有机会当选，有才正式发起选举。这是面试加分点。

Q3 2PC、Saga、TCC、Outbox 这四个分布式事务方案怎么选？
P0主题：分布式事务难度：⭐⭐⭐⭐
核心答案 · 决策矩阵
方案一致性性能实现复杂度典型适用
2PC强差低同 DB 内（XA），不适合微服务
Saga最终好中跨服务长流程（订单/物流/支付）
TCC最终好高（每接口 3 个方法）高并发资金类（账户冻结）
Outbox最终好低业务写 + 事件发布原子保证
选型关键问题
  • 能接受最终一致吗？不能 → 2PC；能 → Saga/TCC/Outbox
  • 需要事务-事件双写一致？→ Outbox（最常用的"小事务"）
  • 有金融级别的并发要求？→ TCC（资源预留比锁更高效）
  • 长流程跨服务编排？→ Saga（编舞或编排）
陷阱：Saga 没有隔离性

Saga 执行中，其他事务可能读到"中间态"数据。必须在应用层处理：语义锁（状态字段标记"处理中"）、乐观并发（版本号）、补偿事务幂等性。

面试加分：Outbox 实战

"我们用 Debezium 监听 PostgreSQL 的 WAL，自动把 outbox 表的变更发到 Kafka——这样应用层只需把事件写到同一事务的 outbox 表，发布完全异步且零业务代码改动。" 这是 CDC + Outbox 的标准组合。

Q4 Kafka 怎么实现 Exactly-Once Semantics？需要什么配合？
P0主题：消息中间件难度：⭐⭐⭐⭐
核心答案

Kafka EOS 由两个机制组成：

  1. 幂等 Producer（enable.idempotence=true）：每个 Producer 有 PID + Sequence Number，Broker 拒绝重复 (PID, Partition, Seq)。保证单分区内恰好一次。
  2. 事务 API（initTransactions / beginTransaction / commitTransaction）：跨分区原子写。Consumer 设置 isolation.level=read_committed 只读已提交。
EOS 的完整链路
initTransactions → poll → beginTransaction → process + send → sendOffsetsToTransaction → commitTransaction
陷阱：EOS 不是端到端的

Kafka EOS 只保证从 Producer 到 Broker，再从 Broker 到 Consumer 的处理过程。如果 Consumer 处理后写入下游系统（DB / 另一个 MQ），那段链路Kafka 管不了，需要业务自己保证幂等。

追问：性能代价多大？

开启 EOS 大约 10-20% 吞吐下降。对绝大多数业务可接受。但极致性能场景（如百万 TPS 实时管道）可能用 At-Least-Once + 业务幂等。

Q5 Snowflake 算法的核心是什么？时钟回拨怎么处理？
P1主题：分布式 ID难度：⭐⭐⭐
核心结构（64-bit）
1 bit符号 0
41 bit时间戳
10 bitworkerId
12 bit序列号

吞吐上限 ≈ 4B ID/s（1024 × 4096 / ms）

时钟回拨处理（三种策略）
  1. 小回拨（< 10ms）：等待时钟追上再生成 ID
  2. 大回拨：拒绝生成 ID，抛异常 + 触发告警，等运维介入
  3. 预防性：用 NTP slew 模式（缓慢调整）而不是 step 模式（瞬间跳跃）
面试加分：推荐 UUID v7 替代

"如果是新系统，我会用 UUID v7（2023 RFC 9562 标准）替代 Snowflake——它毫秒时间戳前缀，趋势递增对 B+ Tree 索引友好；标准 UUID 格式（128 bit）所有工具都支持；不需要分配 workerId，无中心化。"

Q6 用 Redis 做分布式锁，可能有什么问题？怎么解决？
P0主题：分布式锁难度：⭐⭐⭐⭐
Redis 锁的三大问题（Martin Kleppmann 的著名分析）
  1. GC/STW 暂停导致锁过期：客户端获锁后 GC 暂停 30 秒，锁过期被另一客户端拿到，两者同时认为自己持锁 → 双写。
  2. 主从延迟丢锁：客户端在主节点写锁后主节点崩溃，从节点未复制成功 → 新主节点不知道这个锁 → 另一客户端再获锁。
  3. 网络分区：持锁方与 Redis 分区，锁超时被释放，另一方获锁，但持锁方继续操作。
解决方案
  • Fencing Token（推荐）：锁返回单调递增 token，每次写资源带 token，资源系统拒绝旧 token。即使两个客户端"以为"自己持锁，资源系统只接受新 token。
  • RedLock：写到 N/2+1 个独立 Redis 实例才算成功。降低主从延迟问题，但有时钟假设争议。
  • 选 etcd/ZK：基于 Raft/ZAB 强一致，不存在主从延迟。
什么时候用什么
  • 容忍偶发失效（限流、防重复点击）→ Redis 单实例足够
  • 绝对互斥（库存扣减、Leader 选举）→ etcd / ZooKeeper
  • 需要 fencing token → 锁服务返回单调递增版本号，下游资源校验
面试加分：正确的 Redis 锁实现

三个关键点：(1) SET NX PX 原子获锁 + 超时；(2) value 是唯一 UUID 防止误释放；(3) Lua 保证"检查+删除"原子性。
