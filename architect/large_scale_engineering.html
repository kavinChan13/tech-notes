01

什么是 ABI，为什么比 API 难十倍

API vs ABI：层次对比 · ABI 的六个组成部分 · 为什么 C++ ABI 问题比 C 严重 10 倍 · ABI 问题在工程中的真实场景

API 是源码约定，破坏立刻编译失败；ABI 是二进制约定，破坏表现为运行时崩溃或静默写坏内存。同一份 API 可以对应无数种 ABI——C++ 标准不规定 ABI，工程上必须自己钉死边界。

1.1 API vs ABI：层次对比

API 改参数类型，编译器拦住你。ABI 改的是已经烤进旧 .o 的偏移、槽位、符号编码——新库装上去，旧调用方照旧跑，直到某次访问踩错字节。

1.2 ABI 的六个组成部分

块破坏时
Manglingundefined symbol
Calling convention栈 / 寄存器脏
Layoutoff-by-N 读写
vtable虚调用跳错地址
Exception跨 so 无法 unwind
LifecycleA new / B delete 堆损坏

1.3 为什么 C++ ABI 问题比 C 严重 10 倍

C 只有签名和 struct。C++ 再叠加 mangling、vtable、异常表、模板实例化、标准库布局。void foo(int) 在 GCC 是 _Z3fooi、MSVC 是 ?foo@@YAXH@Z——所以跨编译器只能走 C 接口。GCC 5 的 std::string COW→SSO 是历史上最大的一次布局切换。

1.4 ABI 问题在工程中的真实场景

现场根因判据
换了 .so 不重编应用sizeof 变大，旧栈/堆按旧尺寸分配无关位置 heap corruption
插件边界传 std::string两边 string ABI 不同（COW vs SSO）只在短/长串交界崩
跨 so 虚调用槽位按各自版本算调 A 却跑进 B
A new / B delete两边 CRT / allocator 不同MSVC Debug/Release 混链最典型
ABI 的危险在于：同一套二进制换一条 .so 搜索路径就可能崩。边界要在设计时钉死，不要等 valgrind 来救火。

Itanium C++ ABI 详解：Name Mangling、vtable、Exception

Name Mangling：函数名如何变成符号 · 虚函数表（vtable）的真实内存布局 · 对象内存布局与 ABI · 异常 ABI：LSDA 与 personality routine · Itanium ABI …

Linux/macOS 上 GCC 与 Clang 共同遵守 Itanium C++ ABI。改「看起来私有」的东西为什么会炸，答案都在 mangling、vtable、对象布局和异常表里。编码细节见 Name Mangling 与 vtable / RTTI。

2.1 Name Mangling：函数名如何变成符号

重载、模板、命名空间迫使编译器把完整签名编进符号。Itanium 用 _Z 前缀，MSVC 用 ?——两边符号表对不上，不能直链。c++filt / undname 只是解码器，不是兼容层。

2.2 虚函数表（vtable）的真实内存布局

Itanium：对象头是 vptr；表里先是 offset-to-top 和 typeinfo，再是虚函数槽。槽位是源码声明顺序。只准在末尾追加；插到中间，旧调用方仍走老 slot。

2.3 对象内存布局与 ABI

调用方按编译期算好的偏移取字段。公开头里多一个 int，哪怕是 private，旧代码的 offset 全错。

操作ABI
加/改/重排任何数据成员（含 private）Break
改对齐 / pack / 基类Break
中间插入虚函数 / 删虚函数Break
加 static 成员、加非虚方法Safe
单一继承、vtable 末尾加虚函数Safe*

* 多重继承要单独评估 thunk / offset-to-top。

2.4 异常 ABI：LSDA 与 personality routine

抛异常不是 goto，是查三张表：每函数一份 LSDA（try/catch/cleanup）、每帧一份 unwind CFI、以及 __gxx_personality_v0 决定这一帧接不接。跨 so 时两边必须是同一份 libstdc++/libc++。

跨编译器二进制边界只有一种稳法：C ABI。边界上出现 std::string / std::vector 等于没隔离。包装手法见 C ABI wrapper。
03

ABI 兼容性：如何守护、如何检测、如何发布

防线一：设计时——ABI 稳定的设计原则 · 防线二：检测工具 · 防线三：版本管理策略

三道防线：设计时不把实现泄漏进公开布局；工具在 PR 里拦住 break；发布时用 SONAME / 符号版本让新旧库并存。

3.1 防线一：设计时——ABI 稳定的设计原则

✅ 安全✗ Break
加非虚方法、static 成员、新类、新重载改任何数据成员 / sizeof / 对齐 / pack
单一继承、vtable 末尾加虚函数中间插 / 删虚函数，改基类
改 .cpp 里的非 inline 实现改公开签名、改 inline 行为、改枚举数值、改 noexcept

头文件里的 inline getter 由调用方编译。你后来在前面加字段，旧 .o 仍按旧偏移读。对策：公开头不 inline 访问成员，或直接 Pimpl。

3.2 防线二：检测工具

人工 review 看不住偏移。把比较两个 .so 做成 PR 必过项：有 break 要么修回去，要么升 MAJOR。

命令目的判据
abi-dumper + abi-compliance-checkerdump 再出 HTML 报告0 break 才合
abidiff libfoo.so.1 libfoo.so.2直接比两份二进制exit 0
abipkgdiff a.rpm b.rpm比发行包包级无回归
CI 相对 main 编两份再比拦住静默 break故意 break 必须升 MAJOR

3.3 防线三：版本管理策略

Linux 三级名字：libfoo.so（链接器用的符号链接）→ libfoo.so.1（SONAME）→ libfoo.so.1.2.3（真实文件）。ABI break 换 SONAME，旧 .so.1 留下，两个 major 可共存。

变更版本SONAME
修 bug，ABI 兼容1.2.3 → 1.2.4不变
只加符号1.2.3 → 1.3.0不变
改/删 ABI→ 2.0.0libfoo.so.2

CMake：VERSION 1.2.3 + SOVERSION 1。Windows：__declspec(dllexport) + .def 白名单，不要靠碰巧没导出内部符号。

Pimpl 与稳定 ABI 的设计模式

Pimpl 惯用法（Pointer to Implementation） · Opaque Handle（不透明句柄）模式 · 抽象接口 + 工厂（virtual 稳定接口） · 三种模式对比选型

被动守护不够：用设计把实现从公开头里拿掉，ABI 表面积只剩一个指针或一组 C 函数。三种稳法——Pimpl、opaque C handle、抽象工厂——选型见表，代码只示范 Pimpl（它是 C++ 库最常用的那一种）。成本与反模式见 PIMPL 与 ABI 稳定性。

4.1 Pimpl 惯用法（Pointer to Implementation）

公开头只留 incomplete type + 析构声明。析构必须在看到完整 Impl 的 .cpp 里定义，否则 unique_ptr 对不完整类型 delete 是 UB。

// widget.hpp — 公开头：incomplete type + 析构声明
class Widget {
public:
    Widget();
    ~Widget();                 // 必须声明，在 .cpp 定义
    void draw();
private:
    class Impl;
    std::unique_ptr<Impl> pimpl_;
};
// widget.cpp
class Widget::Impl { int w; /* 随便加字段 */ };
Widget::Widget() : pimpl_(std::make_unique<Impl>()) {}
Widget::~Widget() = default;
void Widget::draw() { /* pimpl_->… */ }

Impl 里加字段、换私有依赖，Widget 的 ABI 不动。仍会 break 的：给 Widget 本身加数据成员、改虚函数、改公开签名。堆分配是代价；热路径可用固定 buffer + static_assert(sizeof(Impl) <= N)，细节见上面那篇成本链。

4.2 Opaque Handle（不透明句柄）模式

比 Pimpl 更彻底：对外没有 C++ 类，只有 typedef struct Widget_opaque* Handle 和一组 extern "C" 函数。任何语言都能 FFI；代价是没有 RAII，调用方必须 destroy，内存必须在同一模块分配/释放。

4.3 抽象接口 + 工厂（virtual 稳定接口）

IWidget 只含虚函数，工厂返回 unique_ptr<IWidget>。实现类随便改。规则与 vtable 章相同：只在末尾追加虚函数，析构必须 virtual。适合同编译器的插件/策略替换，不适合跨 GCC/MSVC。

4.4 三种模式对比选型

模式跨语言性能选它当
Pimpl仅 C++一次堆分配库的默认稳 ABI
Opaque Handle所有一次堆分配FFI / 跨编译器
抽象工厂仅 C++虚调用同工具链插件
车规：Adaptive 常用 Pimpl（堆要可控就配 PMR）；Classic↔Adaptive 走 C handle；ASIL-D 禁虚函数时用 CRTP，不要硬套工厂。

++20 Modules 深入：原理、迁移策略与工程实战

#include 的四大顽疾 · Modules 的工作原理 · Module 的四种文件类型 · 渐进迁移策略：Header Units 和 Shim 层 · CMake 3.28+ 的 Modules 支持 · …

Modules 用语义导入替代文本展开：宏不外泄，符号不泄漏，头文件不再被解析 N 次。生态 2026 年仍不齐，新项目可 POC，车规先别上。

5.1 #include 的四大顽疾

顽疾后果
重复解析100 个 .cpp include <string> = 解析 100 次；PCH 只是绕路
宏污染windows.h 的 min/max 跟着 include 走进每个 TU
符号泄漏A include 了 B，你「没用 B」却编过；A 改 include 才爆
顺序依赖include 顺序不同 → 宏不同 → 不可重现行为

5.2 Modules 的工作原理

import 读的是 BMI（GCC .gcm / Clang .pcm / MSVC .ifc），不是再扫一遍源码。未 export 的名字和宏都出不去。

export module math;
import <cmath>;              // 不传染调用方
export namespace math {
    double sqrt(double x);
}
double helper(double);       // 未 export，外面看不见
#define INTERNAL 42          // 宏不传出模块

5.3 Module 的四种文件类型

类型声明扩展名
主接口export module name;.cppm / .ixx
实现单元module name;.cpp
分片接口export module name:part;.cppm
分片实现module name:part;.cpp

大模块用主接口 export import :point; 聚合分片，调用方只 import geometry。

5.4 渐进迁移策略：Header Units 和 Shim 层

阶段做什么
1 工具链GCC 14+ / Clang 16+ / MSVC 17.4+
2 Header Unit调用方 import <vector>;，老头文件不动
3 Shimexport module x; export { #include "old.hpp" }

5.5 CMake 3.28+ 的 Modules 支持

CMake 3.28 起用 FILE_SET CXX_MODULES 声明 .cppm。工程骨架、install 规则见 现代 CMake · 真实项目走读。

现代 CMake 工程化实战：Target-Centric 思维

现代 CMake 的核心哲学 · PUBLIC / PRIVATE / INTERFACE 传播规则 · 大型项目的 CMake 结构 · 生成器表达式（Generator Expressions） · CMake Pa…

现代 CMake = 属性挂在 target 上，用 PUBLIC / PRIVATE / INTERFACE 决定漏不漏给使用方。工程树、Config 包、warnings 接口库见 真实项目走读 与 依赖四方案。

6.1 现代 CMake 的核心哲学

不要 include_directories / add_definitions / set(CMAKE_CXX_FLAGS)——它们污染所有 target。每个库自己 target_include_directories / target_compile_options，关键字写清传播。

6.2 PUBLIC / PRIVATE / INTERFACE 传播规则

判据只有一句：你的公开头里有没有 #include 它。有 → PUBLIC；只在 .cpp 里 → PRIVATE；自己是 header-only → INTERFACE。

target_link_libraries(lib PUBLIC  domain)      # 自己用 + 漏给使用方
target_link_libraries(lib PRIVATE spdlog::spdlog) # 只自己用
target_link_libraries(hdr INTERFACE baz)       # 自己不用，只漏给使用方

6.3 大型项目的 CMake 结构

根 CMakeLists.txt 只做 project()、选项、add_subdirectory；每个库一份自己的 lists。工具链、sanitizer、install 规则丢进 cmake/。GLOB 收集源文件是 anti-pattern——新 .cpp 不会触发重新 configure。

6.4 生成器表达式（Generator Expressions）

属性按配置/编译器分支：$<$<CONFIG:Debug>:-fsanitize=address>、$<$<CXX_COMPILER_ID:GNU,Clang>:-Wall>。安装路径用 $<BUILD_INTERFACE:...> / $<INSTALL_INTERFACE:include>，不要把构建机绝对路径写进 exported target。

6.5 CMake Package Config（让你的库可被 find_package 发现）

下游要的是 Foo::foo imported target，不是一堆 -I。install(TARGETS … EXPORT) → FooConfig.cmake → 用户 find_package(Foo)。完整 Config 模板见 CMake 走读。

6.6 常见 CMake 踩坑

坑表现解决
set(CMAKE_CXX_FLAGS ...) 全局污染，覆盖 toolchain 设置 用 target_compile_options
include_directories 全局 include 路径，传染所有 target 用 target_include_directories
GLOB 收集源文件 新增文件不触发 CMake 重新生成 显式列出源文件，或用 configure_file 做触发
没有 INTERFACE 目标的 header-only 库 include 路径不传播 add_library(mylib INTERFACE)
target_link_libraries 不写关键字 CMake 3.x 默认 PUBLIC，可能意外传播 永远写 PUBLIC/PRIVATE/INTERFACE
BUILD_INTERFACE 路径硬编码 install 后 find_package 路径错误 用 $<BUILD_INTERFACE:...> / $<INSTALL_INTERFACE:...>

依赖管理：Conan、vcpkg、Bazel 与 FetchContent

四种方案对比 · Conan 2.x 实战 · vcpkg 实战 · FetchContent（轻量场景） · 私有 Conan 仓库：Artifactory / Nexus

C++ 依赖管理是工程化最大的痛点——历史上没有标准包管理器，"从源码编译所有依赖"是常态。本章深入比较主流方案，给出选型建议，以及在大型项目中落地的关键决策。

7.1 四种方案对比

方案模型优势缺点适用场景
Conan 2.x 二进制 + 源码包管理 最强大；支持多 profile；中心化仓库（conan-center-index）；与 CMake 深度集成 学习曲线陡；概念多（recipe/profile/settings/options） 大型跨平台项目；嵌入式交叉编译
vcpkg 源码编译 上手简单；与 MSVC/VS 无缝集成；CMake toolchain 文件简单 定制能力弱；没有 Conan 灵活的 profile；二进制缓存不如 Conan Windows 项目；VS 用户；快速 POC
Bazel 构建系统（含依赖） Hermetic build（可重现）；分布式缓存；超大规模 monorepo 学习成本极高；与 CMake 生态不兼容；嵌入式工具链支持差 Google/Meta 规模 monorepo；要求严格可重现构建
CMake FetchContent 下载 + 源码编译 无需额外工具；与 CMake 原生集成 每次 configure 联网；没有版本锁定；冲突难解 小项目；依赖少；不想引入额外工具链

7.2 Conan 2.x 实战

三件套：Profile 描述 OS/编译器/arch（交叉编译用 host+build 两个）；Recipe 写依赖和怎么编；Generator 吐出 CMakeDeps/CMakeToolchain。流程是 conan install . --build=missing 再 cmake -DCMAKE_TOOLCHAIN_FILE=…。

7.3 vcpkg 实战

Manifest 模式：仓库根放 vcpkg.json，CMake 传入 vcpkg toolchain，然后照常 find_package。适合 VS / Windows；二进制缓存和交叉 profile 不如 Conan 细。

7.4 FetchContent（轻量场景）

零额外工具，但没有 lock。必须钉 commit hash，禁止跟踪 branch。依赖一多、要离线或交叉编译，就换 Conan/vcpkg。详见 依赖四方案。

7.5 私有 Conan 仓库：Artifactory / Nexus

内网 conan remote add + conan upload。车规/工厂环境还要：vendor tarball 自己写 recipe、完全离线镜像、profile 锁编译器版本、lockfile 出 SBOM。

插件化架构设计：接口、隔离、生命周期

插件系统的四大设计目标 · 插件系统的核心接口设计 · 插件端的实现 · 版本兼容性策略 · 错误隔离：进程隔离 vs 线程隔离

插件要跨编译器、能版本握手、崩了别带塌主程序。边界钉成 C ABI + 版本号 + 模块内 free。

8.1 插件系统的四大设计目标

目标做法
ABI 隔离C 结构 + 函数指针表，不传 C++ 对象
版本握手第一字段 api_version，对不上就拒绝加载
错误隔离可信插件可同进程；不可信走子进程 + IPC
生命周期先 destroy 再 dlclose；内存在分配它的 .so 里释放

8.2 插件系统的核心接口设计

// plugin_api.h — 永久稳定的 C 结构 + 版本号
#ifdef __cplusplus
extern "C" {
#endif
#define PLUGIN_API_VERSION 2
typedef struct PluginDescriptor {
    unsigned api_version;
    const char* name;
    void (*destroy)(struct PluginDescriptor*);
    int  (*process)(struct PluginDescriptor*, const void*, size_t,
                    void**, size_t*);
    void (*free_output)(void*);   // 必须在本 .so 里 free
} PluginDescriptor;
typedef PluginDescriptor* (*PluginCreateFn)(void);
#ifdef __cplusplus
}
#endif

加载：dlopen(…, RTLD_NOW|RTLD_LOCAL) → dlsym("plugin_create") → 检查 api_version。卸载：先 destroy 再 dlclose。

8.3 插件端的实现

插件 .so 填充 PluginDescriptor 函数表，导出 extern "C" plugin_create。输出缓冲在本模块 malloc，由 free_output 配对释放。用 version-script 只导出入口，其余符号 local: *。

8.4 版本兼容性策略

向后兼容（新主程序加载旧插件）才是默认承诺：只在结构末尾追加字段；api_version >= 2 才调新函数。向前兼容要新插件还能装进旧主程序，通常不做——能力用 capability flags，不要在中间插槽。

8.5 错误隔离：进程隔离 vs 线程隔离

方式隔离程度性能适用
同进程 dlopen 低（崩溃=主程序崩溃） 最高 可信插件、追求性能
独立进程 + IPC 高（崩溃=子进程） 中（IPC 开销） 不可信插件、安全性要求高
沙盒进程（seccomp） 最高（系统调用受限） 低（沙盒 + IPC） 第三方不可信代码
嵌入式插件化注意事项：
  • 传统嵌入式（MCU）没有 MMU → 不能动态加载 .so，用静态插件注册表（函数指针数组，编译期确定）
  • AUTOSAR Adaptive 支持动态部署，但受 Execution Management 管控，不是传统 dlopen
  • Linux 嵌入式（高端 SoC）可以用 dlopen，但注意对 MMU/flash 的约束
  • 静态注册表示例：REGISTER_PLUGIN(my_plugin, &create_fn) 宏展开成 linker section 里的指针

动态加载深入：dlopen / LoadLibrary 的坑与最佳实践

dlopen 的关键标志 · RTLD_LOCAL 与 self-contained 插件 · static 变量的 unload 陷阱 · Windows 上的 LoadLibrary 对应关系

9.1 dlopen 的关键标志

标志目的判据
RTLD_NOW立刻解析全部符号缺符号当场失败，不要拖到第一次调用
RTLD_LOCAL符号不进全局表两个插件都能有自己的 foo
RTLD_GLOBAL符号进全局表几乎不用；后加载会覆盖先加载
RTLD_NODELETEdlclose 不卸载映像热卸载做不到时保命，等于泄漏这份 .so

生产默认 RTLD_NOW | RTLD_LOCAL。C ABI wrapper 细节见 ABI 兼容指南 §7。

9.2 RTLD_LOCAL 与 self-contained 插件

LOCAL 之后插件调不到主程序的全局 log()。把 log / alloc 做成 PluginContext 函数表，plugin_create(ctx) 注入——自包含，不靠全局符号。

9.3 static 变量的 unload 陷阱

dlclose 会跑 .so 里 static 对象析构。还有线程握着里面的函数指针 → 立刻 UAF。先停线程，再 destroy，再 dlclose；热卸载做不到就 RTLD_NODELETE；别在插件里放 static std::string。

9.4 Windows 上的 LoadLibrary 对应关系

12.1 ABI 稳定性检查清单

每次发布库的新版本前，逐项检查：

  1. 所有公开类的 sizeof 是否变化？（static_assert(sizeof(Foo) == N)）
  2. 是否在已有虚函数之间插入了新虚函数？
  3. 是否改变了任何公开 struct/class 的成员变量？
  4. 是否改变了函数签名（参数类型、返回类型）？
  5. 是否改变了inline 函数的行为（而不只是修复 bug）？
  6. 是否改变了枚举值的数值？
  7. 是否改变了基类（加/删/改）？
  8. abi-compliance-checker 或 abidiff 是否通过？
  9. 如果有 break → 是否提升了 MAJOR 版本？

高频面试题 · 大型 C++ 工程化

C++ 架构师专属题——ABI、Modules、CMake、插件化的核心考点。点击题目展开答案
Q1 为什么改了一个类的私有成员会导致 ABI break？它和 API break 有什么本质区别？
P0主题：ABI 基础难度：⭐⭐⭐
核心答案

因为类的私有成员影响 sizeof 和成员偏移——这些数值被编码进了已编译的调用方代码。新版本库的对象布局变了，旧代码按旧偏移读写，访问到错误地址 / 写超界，触发 heap corruption。

API vs ABI 的本质区别：

  • API = 源码层约定（函数签名、类的接口）。破坏 API → 编译报错（立刻可知）。
  • ABI = 二进制层约定（符号名、调用约定、内存布局、vtable、异常表）。破坏 ABI → 运行时崩溃或静默数据损坏（最难找）。
追问：如何检测 ABI break？

用 abi-compliance-checker 或 libabigail 的 abidiff。比较两个 .so，生成 HTML 报告。CI 里把它作为 PR 必过项——任何 ABI break 都必须显式提升 MAJOR 版本号。

面试加分

提到 GCC 5 的 std::string ABI 切换（COW → SSO）——这是历史上最大规模的一次 ABI break，影响了所有 Linux 发行版。可以引出 _GLIBCXX_USE_CXX11_ABI 编译开关的话题。

Q2 设计一个跨编译器（GCC + MSVC）共用的 C++ 插件系统，你的接口怎么定义？
P0主题：插件化 + ABI难度：⭐⭐⭐⭐
核心答案

必须用 C ABI，因为 GCC 和 MSVC 的 C++ name mangling、虚表布局、异常机制完全不兼容。具体做法：

  1. 头文件 extern "C" 包裹接口
  2. 结构体只用 C 类型（不能放 std::string / std::vector）
  3. 对象用 opaque handle（typedef struct Foo* FooHandle），所有操作走函数指针表
  4. 内存分配/释放必须在同一模块内配对（提供 free_xxx 函数）
  5. 错误处理用返回码（不抛异常，异常无法跨 ABI 边界）
  6. 第一字段是 api_version，加载时握手校验
陷阱：在边界传 std::string

"我用了 extern "C" 就跨 ABI 安全了？"——错。如果函数签名里有 std::string 参数，std::string 本身就是 C++ 类型，跨编译器布局不同（COW vs SSO）。extern "C" 不能让 C++ 对象跨 ABI 安全，只能让函数符号名稳定。

追问：你怎么实现版本兼容（v2 主程序加载 v1 插件）？

在 PluginDescriptor 结构体的末尾追加新字段。主程序先检查 api_version，如果是 v1 就不访问新字段。绝对不能在中间插入字段，那会破坏整个 ABI。

Q3 现代 CMake 里 PUBLIC、PRIVATE、INTERFACE 的区别是什么？给个具体例子。
P0主题：CMake难度：⭐⭐
核心答案（一句话记法）

影响"自己"还是"消费方"：

  • PRIVATE：只影响自己（消费方不传播）— 实现细节
  • PUBLIC：影响自己 + 传播给消费方 — API 依赖
  • INTERFACE：不影响自己，只传播给消费方 — header-only 库
具体例子：判断依据是看头文件
target_link_libraries(my_lib
    PUBLIC  boost::asio    # my_lib.hpp 里 #include <boost/asio.hpp>
                           # → 消费方编译时也需要看到 asio 头文件
    PRIVATE spdlog::spdlog # 只在 my_lib.cpp 里 #include <spdlog/spdlog.h>
                           # → 消费方不需要 spdlog
)
追问：为什么 header-only 库要用 INTERFACE？

因为 header-only 库没有可编译的 .cpp 文件——它本身不需要任何编译选项，但消费方在使用时需要 include 路径和编译特性。INTERFACE 表达的正是这个意思：" 我自己什么都不做，但消费方需要这些"。

陷阱：不写关键字

CMake 老风格 target_link_libraries(my_lib boost) 不带关键字，CMake 3.x 默认按 PUBLIC 处理，会意外传播。规则：永远写关键字。

Q4 C++20 Modules 解决了什么 #include 的痛点？2026 年应该开始用 Modules 吗？
P1主题：Modules难度：⭐⭐⭐
核心答案：#include 的四大顽疾
  1. 重复解析：100 个 .cpp 都 #include <string>，解析 100 次
  2. 宏污染：windows.h 的 min/max 宏污染整个翻译单元
  3. 符号泄漏：A include 了 B 内部 include 的 C，意外能用 C
  4. 顺序依赖：include 顺序不同，宏定义不同，行为可能不同

Modules 用语义导入而非文本替换，彻底解决这些问题。BMI（编译产物）可被多个 .cpp 共享，编译速度提升 40-80%。

2026 年用 Modules 的判断
  • 新绿地项目：可以试，但要做 POC
  • 生产大型项目：暂缓，等工具链更稳定（CMake 3.28+、GCC 14+ / Clang 16+ / MSVC 17.4+ 才可用）
  • 嵌入式/车规：禁用——嵌入式编译器（IAR、Green Hills）大多还在 C++14/17
渐进迁移策略

Phase 1: 切到支持 Modules 的编译器 → Phase 2: 新代码用 Modules，老代码用 Header Unit (import <vector>;) → Phase 3: 内部 utility 库改 Module → Phase 4: 公开 API 改 Module。不要一次性切。
