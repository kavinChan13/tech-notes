安全架构

安全不是在设计完之后加的一层，它是一组会改变系统形状的约束。这一篇讲架构师真正要做的决策：威胁建模怎么在评审里跑起来、认证与授权的边界为什么必须分开、服务间身份怎么自举、密钥的三个生命周期问题、纵深防御每一层各自能挡住什么，以及这些防护什么时候不值得加。

核心难度 ★★★★☆ 架构师必备 阅读时长 ~60 min 前置 分布式基础 · HTTP
01

安全为什么是架构问题

如果它只是「加个鉴权中间件」，那它确实不是架构问题

1.1 「安全」不是一个非功能需求

性能、可用性这些非功能需求有一个共同点：它们可以在系统建好之后被测量和改善。慢了就优化，不够可用就加副本，改动通常是局部的。安全不是这样：

它不可测量

你可以测出 P99 是 200 ms，但没有任何指标能告诉你「本系统的安全性是 99.9%」。没有漏洞被发现，和没有漏洞，是两件事。

它改的是结构

「服务间要互相认证」会改变部署拓扑、发布流程、故障模式。这不是加一个中间件，是给每个工作负载引入一个身份的生命周期。

它的失败是离散的

性能退化是连续的（慢一点、再慢一点）。安全的失败是阶跃：要么没事，要么整个数据库被拖走。中间没有过渡态。

第三条决定了安全设计的基本方法论和性能设计完全不同。性能可以「先做出来再优化」，因为中间态是可用的；安全不能「先做出来再加固」，因为在加固之前系统是完全敞开的，而且你不知道那段时间里有没有人进来过。

这也是为什么安全必须在架构阶段做决策：认证方式、信任边界、密钥怎么到达进程——这几件事一旦定了，后面几年都很难改。而它们恰好都是架构决策，不是编码细节。

1.2 场景：一个多租户 SaaS

全篇用一个具体系统做锚点，否则所有讨论都会飘：

业务

面向企业的多租户数据分析 SaaS。3000 家客户，最大的一家有 8000 个用户。客户上传自己的业务数据，在平台上做分析、配置报表、通过 API 拉结果。

技术

12 个微服务跑在 Kubernetes 上，共用一套 PostgreSQL（按 tenant_id 逻辑隔离）与对象存储。有 Web 前端、移动端、以及给客户系统调用的 OpenAPI。

这个场景的选择不是随意的：多租户 + 客户数据 + 开放 API 这三条凑在一起，把安全架构里最难的几个问题全都逼出来了——租户之间怎么隔离、令牌怎么撤销、服务之间凭什么互相信任、以及一个服务被攻破之后能波及多远。

1.3 四个必须先回答的问题

在画任何图之前，先把这四个问题的答案写下来。它们的答案会决定后面每一章的选择，而且它们在项目后期几乎改不动：

问题本例的答案它决定了什么
要防谁？ ① 外部攻击者 ② 其它租户（最重要）③ 内部误操作 ④ 被攻破的自家服务 第②条把「租户隔离」提到了和外部防护同等的位置——这是多租户系统与单租户系统最大的分野
最坏能损失什么？ 客户的业务数据被跨租户读取；一次泄露会同时影响 3000 家客户 决定了纵深防御要做到几层（§7），以及审计日志的保留要求（§9）
信任边界在哪？ 不在网络边界上——集群内部的服务之间也不互相信任（§5） 这一条就是「零信任」的实际含义，它会改变部署拓扑
合规要求？ 客户会做安全问卷；数据要能按租户导出与删除；审计日志留存 1 年 「能按租户删除」这条会反向约束数据模型——这是最容易在后期发现改不动的一条
第一个问题里「防谁」的顺序值得注意。多数团队默认把「外部攻击者」排第一，但在多租户 SaaS 里，最现实的攻击路径是一个合法租户：他有合法账号、能调所有 API、能反复试探，而且他的每一次请求在日志里都看起来正常。外部攻击者要先突破认证，合法租户已经在里面了。
所以「租户 A 能不能看到租户 B 的数据」这个问题，比「怎么防 SQL 注入」更值得花时间。
02

威胁建模：让它在评审里真的跑起来

大多数威胁建模的产出是一份没人看的表格，这一章讲怎么避免

2.1 从数据流图开始，不是从清单开始

威胁建模最常见的错误做法是：拿一份 OWASP Top 10 清单，逐条问「我们有没有这个问题」。这样做的产出永远是「都考虑过了」，因为清单是通用的，而威胁是具体的。

正确的起点是数据流图 + 信任边界：画出数据从哪来、经过谁、存到哪，然后在每一条跨越信任边界的箭头上问 STRIDE 六个问题。跨边界的箭头才是威胁的所在，边界内部的调用不用逐个建模。

2.2 STRIDE 与它对应的控制

STRIDE 是六类威胁的首字母。它的价值不在于分类本身，而在于每一类都对应一组已知的控制手段——问完六个问题，该做什么基本就清楚了：

S

Spoofing · 冒充

攻击者假装成另一个用户或另一个服务。

→ 认证：用户侧 OIDC，服务侧 mTLS（§3、§5）

T

Tampering · 篡改

请求、数据或代码在传输/存储中被改。

→ TLS、签名、只追加的审计日志、镜像签名（§8、§9）

R

Repudiation · 抵赖

做了操作但事后否认，而你无法证明。

→ 审计日志：谁、何时、对什么、结果（§9.1）

I

Info Disclosure · 信息泄露

本例最要命的一类：跨租户读取。

→ 授权 + 数据层兜底（§4.3）、加密、最小返回字段

D

DoS · 拒绝服务

把资源耗尽让别人用不了。

→ 限流、配额、隔离——见 弹性与过载保护

E

Elevation · 提权

普通用户拿到管理员能力，或服务拿到不该有的权限。

→ 最小权限、授权集中决策、容器能力裁剪（§7.3）

把这六个问题套到图 1 的九条跨界箭头上，会得到几十条候选威胁。这时候不要急着全部处理——下一节是定级。

2.3 定级：不是所有威胁都要处理

威胁建模的产出如果是「四十条待办」，那它一定不会被执行。必须定级，而定级的两个维度是可能性和影响：

威胁（本例节选）可能性影响处置
租户 A 通过构造 tenant_id 参数读到租户 B 的数据 高——合法租户就能试 灾难性——3000 家客户信任崩塌 缓解：授权 + 数据层强制过滤双保险（§4.3）
导入服务解析客户上传的文件时被 RCE 中——解析器是常见漏洞源 高——能横向移动到数据区 缓解：解析放沙箱进程 + 该服务的数据库凭据只读且限租户
API 长期凭据泄露（客户把它提交到公开仓库） 高——这几乎必然会发生 中——限于该租户 缓解：凭据带前缀便于扫描器识别；支持一键轮换；异常来源告警
攻击者暴力破解用户密码 高 低——有 MFA 和限速 接受（已有控制足够），继续监控
内部运维直接查生产库看到客户数据 中 中 转移：走审批 + 全程录屏，把技术问题转成流程与责任问题
国家级攻击者的 0day 供应链攻击 极低 灾难性 接受——不在本系统的防御能力范围内，明确写下来
最后一行的「接受」是威胁建模里最被低估的一个动作。把「我们不防这个」显式写下来，比假装能防更负责任：它让后来者知道这是一个已知的、有意识的选择，而不是遗漏；出事时复盘也有据可查。

四种处置只有这四种——缓解、转移、接受、消除（消除 = 干脆不做这个功能）。任何一条威胁如果最后既没缓解也没明确接受，就是悬着的。

2.4 为什么大多数威胁建模会流于形式

三个高频原因，每一个都有对应的做法：

① 做得太晚

系统已经上线才做，产出的每一条都意味着重构，于是全部变成「排期待定」。
做法：在写第一行代码之前做一次粗的，之后每次信任边界发生变化时补一次——加一个外部集成、开一个新 API、引入一个新的数据存储。

② 由安全团队单独做

安全团队不了解业务细节，产出的是通用清单；开发团队没参与，不认可结论。
做法：由设计这个系统的人主持，安全的人参与提问。威胁建模是一次设计评审，不是一次审计。

③ 没有产出可执行的东西

产出一份 Word 表格，然后归档。
做法：每条「缓解」都必须变成一张工单或一条 ADR；每条「接受」都写进 ADR 的「后果」一栏。ADR 那一章讲的记录方式在这里正好适用。

03

认证与授权：边界必须分开

把它们混在一起，是这一层最常见也最贵的错误

3.1 两个问题，两套机制

认证 Authentication授权 Authorization
回答的问题你是谁你能对这个东西做这件事吗
输入凭据（密码、证书、令牌）身份 + 资源 + 动作 + 上下文
结果一个身份，或者失败允许 / 拒绝
变化频率低——登录方式几年不变高——每加一个功能就多一条规则
能在哪做边缘（网关）就够，做一次即可必须靠近资源，因为只有资源持有者知道它属于谁

最后两行是把它们分开的理由。认证的结论是全局的（「这是租户 42 的用户 7」在任何地方都成立），所以在网关做一次、往下游传结论，是对的。授权的结论是局部的（「用户 7 能不能看报表 993」取决于报表 993 属于谁），网关不知道报表 993 属于谁，它做不了这个判断。

上图那种漏洞在 OWASP 里叫 IDOR（Insecure Direct Object Reference），至今是 API 安全里被利用最多的一类——因为它不需要任何技巧，改一个 URL 里的数字就行。它也特别难被测试发现：功能测试用的是自己的数据，永远不会构造出「访问别人的 ID」这种用例。
对应的测试必须显式写：用租户 A 的凭据去访问租户 B 的资源 ID，断言 403。这条测试要覆盖每一个暴露资源 ID 的接口。

3.2 JWT 当 session 用会怎样

JWT 的卖点是「无状态」：令牌自带签名，任何服务本地验签就能确认身份，不用查中心。这个特性在服务间调用里非常好用；但把它直接用作用户会话，会撞上一个结构性问题——

签发出去的 JWT 在过期之前无法撤销。用户改了密码、管理员踢了他、账号被停用、权限被回收——这些都改不了已经在攻击者手里的那个令牌。它会一直有效到 exp。
如果 exp 设成 24 小时（很常见，因为要少让用户登录），那么一次令牌泄露就是24 小时的完全访问权，而且这段时间里你在服务端做任何操作都没用。

常见的三种「解决」方式，前两种其实没解决问题：

做法实际效果
缩短过期时间到 15 分钟把窗口从 24 小时缩到 15 分钟，但没有消除窗口；而且要配 refresh token，于是 refresh token 成了新的长期凭据，问题被搬了个家
每次请求查一下黑名单这时候它已经不是无状态的了——每次都要查中心，那 JWT 相比一个随机 session id 就只剩下「体积更大」这个缺点
分场景用不同机制见下面的 ADR-001。用户会话用不透明令牌 + 中心校验，服务间调用用短寿命 JWT
第二行值得展开，因为它是一个很常见的思维陷阱：为了保留「无状态」这个卖点，人们会去掉撤销能力；发现不行之后加回中心校验，却仍然坚持用 JWT。此时 JWT 相比一个 128 位随机串已经没有任何优势——体积大了十几倍、有一堆解析和算法混淆的坑（alg: none、HS256/RS256 混淆）、而无状态的好处一个都没了。

选技术时要盯住「我为什么选它」那个理由是否还成立。理由被自己的后续决策抵消掉了，就该换回更简单的方案。

3.3 令牌撤销的三种做法

不透明令牌 + 中心校验

令牌就是一个随机串，本身不含信息。网关拿它去身份服务换身份，撤销 = 删一条记录，立即生效。
代价：每次请求一次中心查询——但可以在网关侧缓存几秒，撤销延迟就是缓存 TTL。

短寿命 JWT + 刷新

access token 5 分钟，refresh token 在中心可撤销。撤销延迟 ≤ 5 分钟。
代价：refresh 流程本身的复杂度（并发刷新、轮转、重放检测），以及那 5 分钟窗口。

JWT + 撤销位图

令牌带一个递增的 sid，服务本地缓存一份「已撤销 sid」的布隆过滤器，由中心推送。
适合服务间场景：撤销量小、推送可控。用户会话场景下位图会长得很快。

3.4 ADR-001 会话与令牌的选型

ADR-001用户会话用不透明令牌 + 网关侧 5 秒缓存；服务间调用用 5 分钟 JWT已接受
背景
多租户 SaaS 必须支持「立即踢出用户 / 停用账号 / 回收权限」，而 JWT 在过期前无法撤销。同时服务间调用量大（内部 QPS 是外部的十几倍），每次都查中心不现实。
候选
① 全部用长寿命 JWT ② 全部用不透明令牌 + 中心校验 ③ 分场景：用户侧不透明、服务间 JWT
决策
选 ③。用户会话用 128 位随机不透明令牌，网关换取身份并缓存 5 秒——撤销延迟上界就是这 5 秒，且可解释给客户。服务间调用用 5 分钟有效期的 JWT，由工作负载身份签发（§5），不需要撤销机制——过期就没了。
后果
得到：用户侧撤销 5 秒内生效，满足「停用账号立即失效」的合规要求；服务间调用零中心依赖，身份服务不在关键路径上。
付出：两套机制、两份文档、两个可能出 bug 的地方；网关的令牌缓存是一个新的状态（要处理多网关实例间的不一致——5 秒 TTL 让这个不一致有界，可接受）。
何时重议
若外部请求量涨到身份服务扛不住，缓存 TTL 要放宽，撤销延迟随之变大——那时需要引入主动推送的撤销通道，而不是简单调大 TTL。
04

授权模型：ACL / RBAC / ABAC / ReBAC

选模型就是在选「规则会长成什么样」

4.1 四种模型与它们的成本

模型规则形态擅长会在什么地方崩
ACL 访问控制表 每个资源挂一张「谁能做什么」的表 资源少、规则简单 资源多了之后表本身成为数据量问题；「给所有新员工加只读权限」要遍历全部资源
RBAC 基于角色 用户 → 角色 → 权限 组织结构稳定、权限粒度粗。绝大多数系统的起点 角色爆炸：为了表达「华东区的销售经理能看华东区的报表」，要造出「华东区销售经理」这个角色，于是角色数 = 维度的笛卡尔积
ABAC 基于属性 规则是表达式：user.region == resource.region && user.level >= 3 多维度条件、动态上下文（时间、IP、设备） 规则可读性差、难以回答「谁能访问 X」这个反向问题；调试困难
ReBAC 基于关系 图：user 是 folder 的 editor，权限沿关系继承 层级资源与共享（文档、文件夹、项目）。Google Zanzibar 是代表 要维护一个关系图并保证查询快；一致性问题（权限刚撤销，缓存里还是旧的）
实践中的答案通常是混合，而且演进路径很固定：先 RBAC 管粗粒度（「这个人是管理员还是普通用户」），遇到角色爆炸时给关键维度加 ABAC 条件（不要把租户维度做成角色——那是角色爆炸最常见的起因），有共享/层级需求时再局部引入 ReBAC。

真正要早做的决策不是选哪个模型，而是把授权判断收拢到一个地方（下一节）。模型可以换，散落在几十个 if 里的判断换不动。

4.2 授权决策放在哪一层

业界的标准分法是把授权拆成两个角色，这个拆分很有用，因为它把「策略」和「执行点」解耦了：

4.3 多租户的隔离必须在数据层兜底

回到 §1.3 那个最重要的威胁：租户 A 读到租户 B 的数据。授权层能挡住它，但授权层是代码，代码会有 bug——一个新写的查询忘了加租户条件，就是一次跨租户泄露。

所以租户隔离不能只有一层。三层防护，从弱到强：

层做法强度
① 应用层过滤 每个查询手动加 WHERE tenant_id = ? 最弱。取决于每一个写查询的人都没忘，而这是概率问题，不是设计问题
② ORM / 数据访问层强制注入 在数据访问层统一注入租户条件，业务代码拿不到「不带租户」的查询入口 好很多。但绕过路径仍然存在：原生 SQL、批处理任务、运维脚本
③ 数据库强制（RLS） PostgreSQL 的 Row Level Security：连接上设置 app.tenant_id，数据库自己过滤，绕不过去 最强。即使应用层完全写错，数据库也不会返回别人的行
这三层的关系不是「选一个」，而是②做主、③兜底、①禁止。为什么还要留②：RLS 每行都要跑一遍策略判断，在大表全扫时有可观开销，而②能让绝大多数查询在到达数据库之前就已经带上了索引友好的租户条件。②管性能，③管正确性。

更重要的是，③把「租户隔离」从一个需要靠纪律维持的属性，变成了一个结构上成立的属性。这是安全设计里最值钱的一种转换：凡是靠「每个人都别忘了」维持的安全属性，迟早会失效——把它下沉到一个不需要人记得的地方。
RLS 有一个必须堵住的口子：建表者和超级用户默认绕过 RLS。如果应用连的是表的 owner 或带 BYPASSRLS 的角色，策略形同虚设——而「应用用 owner 账号连库」恰恰是最常见的默认配置。 
-- ① 应用用一个专门的、非 owner 的低权限角色。这一步最容易被跳过，
--    而跳过它之后下面所有配置都不生效 —— owner 默认绕过 RLS。
CREATE ROLE app_rw LOGIN;                -- 注意：不给 BYPASSRLS，也不是表的 owner
GRANT SELECT, INSERT, UPDATE, DELETE ON reports TO app_rw;

-- ② 开启并「强制」。只写 ENABLE 的话 owner 仍然绕过；FORCE 才是对所有人生效。
ALTER TABLE reports ENABLE ROW LEVEL SECURITY;
ALTER TABLE reports FORCE ROW LEVEL SECURITY;

-- ③ 策略：租户 id 从连接级的运行时参数读，不从 SQL 参数读。
--    这一点是关键 —— 业务 SQL 里根本没有 tenant_id 这个可以被写错或遗漏的地方。
CREATE POLICY tenant_isolation ON reports
  USING       (tenant_id = current_setting('app.tenant_id')::uuid)   -- 读
  WITH CHECK  (tenant_id = current_setting('app.tenant_id')::uuid);  -- 写，防止写进别人的租户

-- ④ 应用侧：从连接池取出连接后、执行业务 SQL 前设置。
--    用 set_config(..., true) 让它随事务结束自动清除，
--    否则连接归还池子后残留的 tenant_id 会被下一个请求用上 —— 这是最危险的一种 bug。
SELECT set_config('app.tenant_id', $1, true);
第 ③ 步是这套配置里最值钱的设计：租户条件不再是业务 SQL 的一部分。写查询的人根本没有「忘记加 tenant_id」这个选项——他写不写都一样。这就是 §4.3 开头说的那个转换：把靠纪律维持的属性，变成结构上成立的属性。

第 ④ 步的 true（事务级）不能漏。用连接级设置的话，连接归还连接池后 app.tenant_id 还在，下一个请求如果因为某条代码路径没设置就直接查，它会用上一个租户的身份——这个 bug 只在高并发下偶发，几乎不可能靠人工测试发现。

配完之后必须写一个测试来验证它真的生效：用租户 A 的连接去查租户 B 的行，断言返回 0 条。没有这个测试，你不知道 RLS 是不是在某次迁移中被关掉了——ALTER TABLE 加字段、重建表、或者一次 pg_dump 还原，都可能把策略丢掉，而且丢掉之后系统功能完全正常。

05

服务间身份：从共享密钥到 SPIFFE

「集群内部是可信的」这个假设，是横向移动的全部前提

5.1 三代做法与各自的失效点

12 个服务互相调用，凭什么相信对方是它声称的那个服务？

代做法失效点
0 代 不认证。「都在集群里，内网是安全的」 任何一个服务被攻破（比如 §2.3 那个解析器 RCE），攻击者就能以任意服务的身份调用任何接口。这就是横向移动，也是绝大多数大型泄露事件的中间步骤
1 代 共享密钥 / API key：每个服务配一个静态密钥 密钥在配置里、在环境变量里、在镜像里、在有人的笔记本上。轮换需要同时改所有调用方，于是从来不轮换。而且它只证明「持有密钥」，不证明「是那个服务」
2 代 mTLS + 短寿命证书：每个工作负载一张证书，双向验证 强。身份绑定到工作负载而非密钥文件，证书短寿命（小时级）自动轮换，泄露窗口有界

SPIFFE 是 2 代做法的标准化：它定义了一种身份格式（spiffe://example.org/ns/prod/sa/report-svc）和一套签发流程（SPIRE 是它的实现，Istio 的身份体系也遵循它）。价值在于身份是可移植的——跨集群、跨云、跨 K8s 与虚拟机，用同一套身份语义。

5.2 身份的自举问题

这是整章最有意思的一个问题，也是最容易被跳过的：一个刚启动的 Pod，凭什么向签发方证明「我是 report-svc」，从而拿到它的第一张证书？

如果答案是「它带着一个密钥去换证书」，那问题只是被推了一层——那个密钥怎么安全地到达它？这就是秘密的零号问题（secret zero）：你总需要一个初始凭据，而它不能用同一套机制来保护。

可行的答案都依赖一个比应用更可信的东西来做见证：

平台见证

K8s 的 Projected ServiceAccount Token：kubelet 给 Pod 挂一个短寿命、带受众限制的 JWT，由 API Server 签名。签发方验它，就知道「这确实是 ns/prod 里 sa/report-svc 起的 Pod」。
信任根是控制平面。

云厂商见证

实例元数据服务（IMDS）签发的身份文档。信任根是云平台。
注意 IMDS 本身要防 SSRF——v1 版本能被一个 SSRF 漏洞直接读走，必须用 IMDSv2。

硬件见证

TPM / 安全芯片做远程证明。信任根是硬件，最强，但只在自有物理机上可行。

这三种的共同结构值得记住：把「证明我是谁」这件事，委托给一个已经知道答案的、更底层的组件。kubelet 知道它启动的是哪个 Pod，云平台知道这台机器是谁的，TPM 知道跑的是不是被篡改过的镜像。

反过来说，如果你的架构里找不到这样一个「更底层的见证者」，那服务身份就只能退回到静态密钥——这时候不要假装自己做了零信任。识别出这一点，比部署一套 mTLS 更重要。

5.3 ADR-002 工作负载身份

ADR-002服务间用 mTLS，身份由 SPIRE 签发，自举依赖 K8s Projected SA Token已接受
背景
§2.3 已把「导入服务被 RCE」列为需要缓解的威胁，其影响之所以是「高」，正是因为当前内部调用不做认证，一个服务被攻破即可横向移动到全部服务与数据。
候选
① 维持内网信任 ② 每服务一个静态 API key ③ SPIRE + mTLS ④ 服务网格（Istio）自带的 mTLS
决策
选 ③。证书有效期 1 小时、自动轮换；身份自举用 K8s 的 Projected ServiceAccount Token（受众限定为 SPIRE，有效期 10 分钟）。没有选 ④ 是因为团队暂时不打算引入服务网格的完整复杂度（sidecar 的资源、升级、调试成本），而 SPIRE 可以先单独用起来，将来接入网格时身份体系不用重做。
后果
得到：横向移动的门槛从「攻破任一服务」提高到「攻破任一服务并在 1 小时内利用其身份」，且每次调用都留下可归因的身份；静态密钥从代码库和配置里彻底消失。
付出：SPIRE 本身成为一个必须高可用的关键依赖（它挂了新 Pod 起不来，但已有连接不受影响——这个失败模式要写进运维手册）；调试变难，抓包看不到明文；本地开发需要一套绕过机制，而这个绕过机制本身是个风险，必须保证它无法在生产启用。
依赖
本决策依赖运行在 K8s 上。若将来有工作负载跑到 K8s 之外（虚拟机、边缘节点），需要为它们配置另一种自举方式（云 IMDS 或 join token），这是已知的扩展点而非遗漏。
06

密钥：三个生命周期问题

「放进环境变量」不是答案，它只是换了个地方放

系统里的密钥远比想象中多：数据库口令、对象存储凭据、第三方 API key、加密数据用的主密钥、签 JWT 的私钥、TLS 证书私钥。每一个都要回答三个问题——从哪来、怎么换、泄了怎么办。

6.1 从哪来：不能是配置文件

方式问题
代码里硬编码进了 git 历史就永远在那里。删掉那一行不算修复，必须轮换。
配置文件 + 部署时注入密钥落在磁盘上、进了镜像层、出现在 CI 日志里；谁有部署权限谁就有全部密钥
环境变量比文件好一点，但 /proc/<pid>/environ 可读、崩溃转储里有、很多框架会把整个 env 打进启动日志
K8s Secret默认只是 base64，不是加密；etcd 里明文存储（除非开了 encryption at rest）；有 namespace 读权限的人能看到全部
密钥管理服务 + 工作负载身份换取进程启动时用 §5 的身份去 Vault / KMS 换一个短寿命凭据。密钥不落盘、不进镜像、不进 CI，且每次获取都有审计记录
最后一行之所以成立，是因为 §5 已经解决了自举问题。工作负载身份是密钥管理的前置条件——没有可信的服务身份，密钥管理服务就无法判断「谁在申请这个密钥」，只能退回到用另一个密钥来认证，回到原点。
这也是 ADR-002 的一个附带价值：它不只是防横向移动，它还让「密钥不落盘」成为可能。两个安全决策互相支撑，单独做任何一个价值都会打折。

更进一步的做法是动态凭据：应用不再持有固定的数据库口令，而是每次启动时向 Vault 申请一个为它临时创建的数据库账号，有效期几小时，到期自动删除。这样「数据库口令泄露」这个威胁基本消失了——泄露的是一个几小时后就不存在的账号。代价是数据库要能承受频繁的建号删号，以及连接池的生命周期要和凭据对齐。

6.2 怎么轮换：双密钥窗口

轮换的难点从来不是「生成一个新密钥」，而是切换的那一刻不能有请求失败。所有轮换方案的核心都是同一个结构：

把它落成代码，关键是验证方要同时接受一组密钥，而签发方只用其中一个：

// 验证侧：接受一组密钥；签发侧：只用 active 那个。
// 这个不对称是双密钥窗口的全部实现 —— 图 3 的四个阶段就是这两个集合的四种组合。
class KeyRing {
  std::string active_kid_;                       // 当前用于签发的 key id
  std::unordered_map<std::string, Key> verify_;  // 所有仍被接受的密钥

 public:
  // 令牌里必须带 kid，否则验证方要逐个试 —— 那会把「多密钥」变成一个计时侧信道，
  // 而且密钥多了之后每次验证的开销随之上升。
  bool verify(std::string_view kid, std::span<const uint8_t> msg,
              std::span<const uint8_t> sig) const {
    auto it = verify_.find(std::string(kid));
    if (it == verify_.end()) return false;
    // 必须用恒定时间比较：普通 memcmp 在第一个不同字节就返回，
    // 攻击者可以按字节爆破签名。这是密码学代码里最经典的一个疏漏。
    return verify_constant_time(it->second, msg, sig);
  }

  Signature sign(std::span<const uint8_t> msg) const {
    return do_sign(verify_.at(active_kid_), msg, active_kid_);
  }

  // 阶段 ② ：只加进验证集，不动 active。全部实例都执行完这一步，才能进入阶段 ③。
  void stage_new(std::string kid, Key k) { verify_.emplace(std::move(kid), std::move(k)); }
  // 阶段 ③ ：切换签发方。旧密钥仍在 verify_ 里，在途令牌不受影响。
  void promote(std::string kid) { active_kid_ = std::move(kid); }
  // 阶段 ④ ：确认旧 kid 的验证计数已归零后，才移除。
  void retire(std::string_view kid) { verify_.erase(std::string(kid)); }
};
代码里有个容易忽略的运维要求：要按 kid 打点统计验证次数，否则阶段 ④ 就只能靠估算「应该没人用旧的了吧」。有了这个指标，退役就变成一个有明确判据的动作——旧 kid 的计数连续 N 分钟为 0 才移除。
「怎么知道可以安全地删掉它」这个问题，在设计的时候就要想好怎么回答；否则轮换永远停在阶段 ③，密钥集合只增不减。

6.3 泄露了怎么办

这一节的前提是：假设它一定会泄露。那么设计时要保证的是三件事：

能发现

给密钥加可识别前缀（如 tsk_live_），GitHub 的 secret scanning 和各类扫描器就能自动识别并通知你。这是成本极低、收益极高的一步。

能快速换掉

如果轮换需要停机或改二十处配置，那么泄露时你会犹豫——而犹豫就是延长暴露。轮换必须是一个演练过的、几分钟的常规操作。

爆炸半径有界

一个密钥不该能做所有事。按用途和租户拆分：导入服务的数据库凭据应当只读、只能访问导入相关的表。这样它泄露的后果是有限且可描述的。

6.4 ADR-003 密钥分发与轮换

ADR-003密钥一律由工作负载身份向 Vault 换取，不落盘；签名密钥走双密钥窗口，90 天轮换已接受
背景
当前密钥分散在 K8s Secret、CI 变量与部署配置里，无法回答「谁在什么时候拿过这个密钥」，也无法在不停机的情况下轮换。ADR-002 提供的工作负载身份使得更好的方案成为可能。
决策
① 应用启动时用 SPIFFE 身份向 Vault 换取凭据，全部在内存中，不写文件、不进环境变量；② 数据库凭据用 Vault 的动态凭据（临时账号，4 小时有效）；③ JWT 签名密钥走双密钥窗口，90 天轮换，按 kid 打点以判断何时可以退役旧密钥；④ 所有外发的长期凭据（客户的 API key）带 tsk_live_ 前缀便于扫描器识别。
后果
得到：密钥不再出现在磁盘、镜像、CI 日志和 git 历史里；每次获取都有审计记录；数据库凭据泄露的价值降到「4 小时内的一个受限账号」。
付出：Vault 成为启动路径上的强依赖（它挂了新 Pod 起不来——与 SPIRE 是同一类失败模式，要一起写进运维手册）；数据库要承受频繁建号删号；连接池的生命周期必须与凭据有效期对齐，这一条最容易被漏掉，表现是凭据过期后连接池里的老连接开始报错。
07

纵深防御：每一层能挡住什么

「多加几层」不是纵深防御，能说清每层挡什么才是

7.1 攻击链与防线的对应

纵深防御容易被做成「层数竞赛」——加 WAF、加扫描、加审计，但说不清哪一层在挡什么。更有用的做法是沿着一条真实的攻击链排布防线，然后逐段确认：这一段被突破时，下一段能不能兜住。

7.2 「零信任」到底改变了什么

这个词被用滥了，但它有一个精确的含义，就是否定一条具体的假设：

传统边界模型

「网络位置 = 信任级别」。内网可信、外网不可信，防线集中在边界（防火墙、VPN）。
失效方式：一旦有人进到内网——通过 VPN 凭据泄露、供应链、或者一个 SSRF——他就获得了内网的全部信任。

零信任

「网络位置不提供任何信任」。每次访问都要重新验证身份与授权，无论请求来自哪里。
实际改变的三件事：服务间要互相认证（§5）、授权要在每个资源处判断（§4.2）、以及网络策略默认拒绝而非默认允许。

值得澄清的是：零信任不等于不要网络边界。防火墙和网络策略仍然有价值——它们是纵深防御的一层，只是不再是唯一的那层。

判断一个系统有没有真的做到零信任，有一个很简单的检验：如果攻击者已经在集群里拿到了一个 Pod 的代码执行，他能做的事情比外部攻击者多多少？如果答案是「多很多」，那不管部署了什么产品，信任仍然建立在网络位置上。

7.3 爆炸半径与最小权限的量化

「最小权限」是句正确的废话，除非能量化。可操作的方法是对每个主体列出它被攻破后能做什么，然后逐条问「这是必要的吗」：

主体当前能做什么其中不必要的收紧后的爆炸半径
导入服务 读写全部表、访问对象存储全部 bucket、出网无限制 它只需要：写 import_* 表、读自己那个 bucket 前缀、完全不需要出网 从「全库 + 全部文件 + 可外传」收到「几张表 + 一个前缀 + 出不去网」
报表服务 读写全部表 它只读不写 降级为只读账号，且受 RLS 约束
CI 流水线 部署到生产、读全部密钥 构建阶段不需要生产密钥；部署应当是一个需要审批的独立主体 构建与部署拆成两个主体，构建产物签名后由部署主体验证
第一行里「不需要出网」这条最值得强调，因为它是投入产出比最高的一条：绝大多数攻击在拿到代码执行之后，下一步都是回连 C2 或者把数据传出去。一条默认拒绝的出网策略（NetworkPolicy egress deny + 需要出网的服务显式放行到具体域名）能把「RCE」和「数据外泄」之间切断。

而它的成本几乎为零——大多数内部服务本来就不需要访问互联网。但默认配置是允许出网的，所以它需要被显式地做一次。这类「成本极低、默认关闭、需要有人想起来打开」的控制，正是安全评审清单存在的意义。

8.1 依赖是最大的攻击面

供应链的风险有三种形态，防法完全不同：

形态例子防法
已知漏洞依赖的某个版本有 CVE相对好办：扫描 + 及时升级。难点是噪音——大量 CVE 其实不影响你的调用路径
恶意包抢注（typosquatting）、维护者账号被盗后发布带后门的版本钉版本 + 锁文件 + 新依赖需人工评审；不要自动升级到最新
构建过程被污染CI 被攻破，产出的镜像和源码对不上最难：需要可复现构建 + 产物签名 + 部署时验签（SLSA 框架讲的就是这一层）
第二行里「维护者账号被盗」是近年最现实的一类：攻击者不需要找漏洞，只需要拿到一个流行小库的 npm/PyPI 账号，发一个补丁版本，几小时内就会被成千上万个项目自动拉取。「自动升级到最新的补丁版本」这个看起来负责任的做法，恰恰是这条攻击链的传送带。
这就是「及时升级修 CVE」与「不要自动升级防投毒」之间的真实张力——它没有两全的答案，只有一个取舍点（见 ADR-004）。

8.2 SBOM 解决什么、不解决什么

SBOM（软件物料清单）就是一份「这个产物里到底有什么」的机器可读清单。它常被当成一个合规勾选项，但它真正的价值在一个具体场景：

✅ 它解决「我受影响吗」

某个库爆出高危漏洞，问题是「我们的哪些服务、哪些版本用了它」。没有 SBOM，这个问题要靠人翻代码库，要几小时到几天；有 SBOM，是一次查询。
而这几小时正是攻击者的窗口。

❌ 它不解决「我安全吗」

SBOM 只是清单，不是评估。它不会告诉你哪个依赖有漏洞、漏洞是否可达、也不会阻止任何东西被引入。
把 SBOM 当成安全措施是个常见误解——它是应急响应的基础设施，价值在事故发生那一刻兑现。

与之配套的是可达性分析：一个 CVE 在依赖里，但你的代码是否真的调到了那个函数？工具（如 Go 的 govulncheck、部分 SCA 产品）能做这个判断，它通常能把「需要处理的 CVE」数量降一个数量级——而降噪本身就是安全价值，因为一份两千条的告警列表等于没有告警列表。

8.3 ADR-004 依赖钉版与准入

ADR-004依赖全部钉版并提交锁文件；升级走定期批量 + 安全补丁快速通道；镜像签名后部署时验签已接受
背景
「及时升级修 CVE」与「不自动升级防投毒」直接冲突（§8.1）。需要一个显式的取舍点，而不是让两种做法在不同项目里各行其是。
决策
① 依赖钉到精确版本，锁文件进版本库，CI 用 --frozen-lockfile 构建；② 常规升级每两周批量做一次，有人 review 变更集；③ 安全补丁走快速通道，但仍需一次人工确认（看 diff、看维护者是否变更），不设全自动合并；④ 新增依赖需评审，看维护活跃度、下载量、维护者数量；⑤ 构建产物用 cosign 签名，K8s 侧用准入控制器拒绝未签名镜像。
后果
得到：投毒版本不会在无人察觉时进入生产；产物可追溯到具体的构建；「我们受影响吗」有确定答案。
付出：CVE 的平均修复时间比全自动升级长（两周窗口，安全补丁除外）——这是一个明确接受的取舍；两周一次的批量升级需要有人固定负责，没人负责它就会积压成一次几百个包的大升级，那时风险更高。
何时重议
若出现一次因为「升级不及时」导致的实际入侵，需要重新评估两周这个窗口；反之若可达性分析成熟到能自动判断「这个 CVE 对我们无影响」，人工确认的负担可以下降，快速通道能覆盖更多情况。

检测与响应：假设已经被攻破

前面八章都在防；这一章的前提是防线已经失败了

入侵的平均发现时间以周为单位，而且很多是被外部通报的。所以设计时必须假设「已经有人在里面」，然后问：我能发现吗？能知道他动了什么吗？能证明哪些租户受影响吗？最后一个问题在多租户 SaaS 里是合规通报的前提——答不出来，就只能按最坏情况通知全部 3000 家客户。

9.1 审计日志的三条硬要求

① 只能追加，攻击者删不掉

如果审计日志和应用写在同一个地方、用同一套凭据，那么拿到应用权限的人可以把自己的痕迹擦掉。
做法：单向写入——应用只有 append 权限，没有 delete/update；日志实时推到另一个信任域（不同账号、不同集群）。

② 内容要能回答四个 W

谁（主体身份，不是 IP）、何时、对什么（资源 ID + 租户 ID）、结果（成功/拒绝）。
拒绝也要记——一连串被拒绝的访问，正是探测行为的特征，而只记成功就完全看不到。

③ 和业务日志分开

业务日志会因为降噪、成本、格式变更而被随意调整；审计日志有留存期要求，不能一起被砍掉。
而且业务日志里常常混进敏感数据，两者的访问权限要求不同。

有一个常被忽略的问题：审计日志本身可能泄露敏感数据。记录「谁查了什么」时，很容易把查询参数整个记下来——里面可能有客户的业务数据、手机号、甚至凭据。审计日志的访问权限通常比业务库宽（安全团队、合规、运维都要看），于是它成了一个新的泄露点。
做法是记资源标识而不是资源内容：记 report:993，不记这个报表返回了什么。

9.2 该告警什么

安全告警最容易犯的错是告警太多——一天几百条，然后所有人都不看了。有效的告警集中在「正常业务不会产生」的模式上：

信号为什么它有效
跨租户访问被拒绝正常业务永远不会触发这个。一次都不该有——所以它是零噪音、高置信度的信号，出现即调查
单租户读取量突增（10 倍以上）数据外泄的直接特征。要按租户各自的基线比，不是全局阈值
服务发起了预期之外的出网连接配合 §7.3 的默认拒绝出网，被拒绝的出网尝试同样是零噪音信号
凭据从异常地理位置/ASN 使用凭据泄露的常见特征。对 API key 尤其有效——它们通常只从固定几个 IP 用
权限变更（授予管理员、改角色）低频、高影响，适合逐条人工确认
容器内启动了 shell / 包管理器配合 §7.1 的无 shell 镜像，这个信号几乎没有误报。前提是运行时检测（如 Falco）
这张表里最好的信号有一个共同特征：它们在正常运行时的发生次数是零。「跨租户访问被拒绝」「被拒绝的出网」「容器里起了 shell」——这些不是「超过阈值才告警」，而是出现一次就该看。

找这类信号的方法是问：「有没有哪个事件，在系统健康时永远不会发生？」这样的事件不需要调阈值、不会随流量增长而误报、也不会因为扩容而失效。相比之下，「错误率超过 5%」这种阈值型告警，既要不断调参又容易被淹没。

9.3 ADR-005 审计日志的独立性

ADR-005审计日志写入独立信任域，应用只有追加权限；记资源标识不记资源内容，留存 1 年已接受
背景
§1.3 的合规要求是审计留存 1 年；而 §2.3 已识别出「服务被 RCE」是需要缓解的威胁——如果审计日志与应用共用凭据与存储，攻击者可以擦掉痕迹，事后无法界定受影响的租户范围。
决策
审计事件经独立通道写入另一个云账号下的只追加存储，应用侧的凭据只有 PutObject 权限、无删除无覆盖；事件内容为「主体身份 + 时间 + 租户 ID + 资源标识 + 动作 + 结果」，不含请求体与响应体；成功与拒绝都记录。
后果
得到：即使应用被完全攻破，历史审计记录仍然可信；能按租户回答「他的数据被谁在什么时候访问过」，把合规通报的范围从「全部 3000 家」缩小到实际受影响的那几家。
付出：跨账号写入的可用性要单独保障（写失败时是阻塞业务还是丢日志？——本例选择本地有界缓冲 + 缓冲满则阻塞，因为审计缺失在合规上不可接受）；1 年留存的存储成本；排查问题时要同时看两套日志。
权衡说明
「缓冲满则阻塞」是一个把可用性让给合规的选择，和 弹性篇的反向判据正好相反。之所以在这里成立，是因为审计缺失的后果（无法界定泄露范围）比短暂不可用更严重——这个前提如果不成立，就该改成丢弃 + 告警。

10.3 什么时候不该加这层安全

安全措施不是免费的，它的成本体现在开发速度、调试难度、故障模式和运维负担上。加错地方会同时损失效率和可靠性，而并不换来安全：

如果……那么哪条不值得理由
单租户、内部工具、用户就是同事 ADR-002 的 mTLS、§4.3 的 RLS 它们的收益来自「防范同一系统内的其它主体」，而这个场景里没有这类主体。付出的是启动依赖与调试难度
数据本身是公开的 大部分机密性控制 该保护的是完整性与可用性（别被篡改、别被打挂），投在加密与隔离上是错配
团队没有能力运维它 SPIRE、Vault、服务网格 这是最重要的一条：一个没人会调、出问题只能整体重启的安全组件，会同时降低安全性和可用性——它成了新的故障源，而且没人敢碰
威胁模型里没有这个威胁 对应的控制 「别人都在做」不是理由。每一条控制都应该能指回 §2 的某条具体威胁
它会被绕过 那条控制 比如加了 WAF 但内网可以直连服务、要求代码评审但有紧急发布通道。有绕过路径的控制提供的是虚假的安心，比没有更危险
最后一行值得展开。安全里最危险的状态不是「没有防护」，而是「以为有防护」——前者会让人保持警惕并在决策时考虑风险，后者会让人把风险从心里划掉。

所以每加一条控制，都要配一个问题：「怎么绕过它？」答不上来说明还没想清楚；答得上来就要么堵住那条路径，要么把它记进 ADR 的「后果」一栏——让后来者知道这条防线的边界在哪，而不是以为它是密不透风的。

11.1 基础（必答）

  1. 基础认证和授权有什么区别？为什么不能都放在网关做？

    认证回答「你是谁」，授权回答「你能对这个东西做这件事吗」。

    关键差别在于结论的作用域
    认证的结论是全局的——「这是租户 42 的用户 7」在任何地方都成立，所以在网关做一次、往下游传结论是对的。授权的结论是局部的——「用户 7 能不能看报表 993」取决于报表 993 属于谁，而网关不知道报表 993 属于谁，它做不了这个判断。
    硬放在网关的后果：IDOR
    网关只能按 URL 模式配规则（/api/reports/* → 需要 report:read），于是任何持有该权限的人都能访问任何报表，包括别的租户的。这类漏洞不需要任何技巧，改一下 URL 里的数字就行，至今是 API 安全里被利用最多的一类。
    正确结构
    PEP（执行点）分散在每个服务里、靠近资源；PDP（决策点）集中管策略。这样策略可以集中审计和变更，而判断发生在知道资源归属的地方。
  2. 基础用 JWT 做用户会话有什么问题？

    签发出去的 JWT 在过期之前无法撤销。用户改密码、管理员踢人、账号停用、权限回收——这些都改不了已经在攻击者手里的那个令牌，它会一直有效到 exp。

    两种常见的「解决」其实没解决
    ① 缩短过期时间：窗口从 24 小时缩到 15 分钟，但没消除；而且要配 refresh token，refresh token 又成了新的长期凭据，问题搬了个家。② 每次查黑名单：这时它已经不是无状态的了，而无状态正是选 JWT 的唯一理由——此时它相比一个 128 位随机串只剩下体积大十几倍和一堆解析坑（alg: none、HS256/RS256 混淆）。
    合理做法：分场景
    用户会话用不透明令牌 + 中心校验（网关缓存几秒，撤销延迟就是缓存 TTL）；服务间调用用短寿命 JWT（几分钟，过期就没了，不需要撤销机制）。
    背后的通用原则
    选技术时要盯住「我为什么选它」那个理由是否还成立。理由被自己的后续决策抵消掉了，就该换回更简单的方案。
  3. 基础多租户系统怎么保证租户 A 看不到租户 B 的数据？

    关键是不能只有一层。授权层能挡住它，但授权层是代码，代码会有 bug——一个新写的查询忘了加租户条件就是一次跨租户泄露。三层，强度递增：

    ① 应用层手动加 WHERE tenant_id
    最弱。它取决于每一个写查询的人都没忘，这是概率问题不是设计问题。
    ② 数据访问层强制注入
    业务代码拿不到「不带租户条件」的查询入口。好很多，但绕过路径仍在：原生 SQL、批处理任务、运维脚本。
    ③ 数据库强制（PostgreSQL RLS）
    连接上设 app.tenant_id，数据库自己过滤。即使应用层完全写错，也不会返回别人的行。
    三者的关系是「②做主、③兜底、①禁止」
    ②管性能（让查询带上索引友好的条件），③管正确性。③把租户隔离从靠纪律维持变成结构上成立——这是安全设计里最值钱的一种转换。
    RLS 的坑
    建表者和超级用户默认绕过 RLS。应用必须用非 owner 的低权限角色连接，并给表加 FORCE ROW LEVEL SECURITY。配完要写一个测试：用租户 A 的连接查租户 B 的行，断言返回 0 条——否则你不知道它是不是在某次迁移里被关掉了。
  4. 基础密钥应该放在哪？环境变量行不行？

    环境变量比配置文件好一点，但仍然不行：/proc/<pid>/environ 可读、崩溃转储里有、很多框架会把整个 env 打进启动日志。

    各种做法的问题
    硬编码：进了 git 历史就永远在（删掉那一行不算修复，必须轮换）。K8s Secret：默认只是 base64 不是加密，etcd 里明文（除非开了 encryption at rest），有 namespace 读权限的人能看到全部。
    正解：工作负载身份 + 密钥管理服务
    进程启动时用自己的服务身份去 Vault/KMS 换一个短寿命凭据。密钥不落盘、不进镜像、不进 CI，且每次获取都有审计记录。更进一步是动态凭据——每次启动申请一个临时数据库账号，几小时后自动删除，「口令泄露」这个威胁基本消失。
    前提条件
    这套做法依赖可信的服务身份。没有它，密钥服务无法判断「谁在申请」，只能用另一个密钥来认证，回到原点。所以工作负载身份是密钥管理的前置条件，两个决策互相支撑。

11.2 中级（区分熟练度）

  1. 中级怎么做威胁建模才不流于形式？
    从数据流图开始，不是从清单开始
    拿 OWASP Top 10 逐条自问「我们有没有这个问题」，产出永远是「都考虑过了」——因为清单是通用的，威胁是具体的。
    正确起点：画数据流图 + 标出信任边界，然后只对跨越边界的箭头问 STRIDE 六个问题。边界内部的调用不用逐个建模。
    STRIDE 的价值在于每类对应一组控制
    Spoofing→认证、Tampering→TLS/签名/只追加日志、Repudiation→审计、Info Disclosure→授权+数据层兜底、DoS→限流隔离、Elevation→最小权限。问完六个问题，该做什么基本就清楚了。
    必须定级，处置只有四种
    缓解 / 转移 / 接受 / 消除。产出四十条待办等于不会执行。「接受」是最被低估的动作——把「我们不防国家级 0day」显式写下来，比假装能防更负责任：后来者知道这是有意识的选择而不是遗漏。
    三个让它流于形式的原因
    ① 做得太晚（上线后做，每条都要重构）→ 在写第一行代码前做粗的，之后每次信任边界变化时补；② 由安全团队单独做（不了解业务、开发不认可）→ 由设计这个系统的人主持，安全的人参与提问；③ 产出一份归档的表格 → 每条缓解变成工单，每条接受写进 ADR。
  2. 中级服务间调用要不要认证？怎么做？

    要。不做认证意味着任何一个服务被攻破，攻击者就能以任意服务的身份调用任何接口——这就是横向移动，是绝大多数大型泄露事件的中间步骤。

    静态 API key 不算解决
    密钥在配置里、环境变量里、镜像里、有人的笔记本上；轮换需要同时改所有调用方，于是从来不轮换；而且它只证明「持有密钥」，不证明「是那个服务」。
    mTLS + 短寿命证书
    每个工作负载一张证书，双向验证，有效期小时级自动轮换。身份绑定到工作负载而非密钥文件，泄露窗口有界。SPIFFE 是这套做法的标准化，好处是身份可移植（跨集群、跨云、跨 K8s 与虚机）。
    真正的难点：身份自举
    一个刚启动的 Pod 凭什么证明「我是 report-svc」从而拿到第一张证书？如果答案是「带一个密钥去换」，问题只是被推了一层——这就是秘密的零号问题。
    可行答案都依赖一个比应用更可信的见证者：K8s 的 Projected SA Token（信任根是控制平面）、云厂商 IMDS（信任根是云平台，注意要用 v2 防 SSRF）、TPM 远程证明（信任根是硬件）。
    如果架构里找不到这样的见证者，那就只能退回静态密钥——这时不要假装做了零信任。
  3. 中级怎么在不中断服务的情况下轮换一个签名密钥？

    双密钥窗口，四个阶段，顺序不能变：

    ① 只有旧密钥 → ② 新密钥「可验证」
    把新密钥加进验证集，但签发仍用旧的。必须等全部实例都完成这一步才能进入 ③。
    ③ 新密钥「用于签发」 → ④ 移除旧密钥
    切换签发方，旧密钥仍在验证集里，在途令牌不受影响。等旧密钥的验证流量归零后才移除。
    顺序反了会怎样
    先切签发再让验证方认识新密钥 = 一次全站鉴权失败。这是最常见的事故形态。
    实现要点
    验证方接受一组密钥、签发方只用其中一个——这个不对称就是双密钥窗口的全部实现。令牌里必须带 kid，否则验证方要逐个试，既是计时侧信道又让开销随密钥数上升。
    最容易漏的一步
    按 kid 打点统计验证次数，否则阶段 ④ 只能靠估算「应该没人用旧的了吧」。有了这个指标，退役才有明确判据。「怎么知道可以安全地删掉它」这个问题，设计时就要想好怎么回答，否则轮换永远停在阶段 ③，密钥集合只增不减。
    还有一处
    签名比较必须用恒定时间。普通 memcmp 在第一个不同字节就返回，攻击者可以按字节爆破。
  4. 中级RBAC 不够用了怎么办？

    RBAC 的典型崩塌是角色爆炸：为了表达「华东区的销售经理能看华东区的报表」，要造出「华东区销售经理」这个角色，于是角色数 = 各维度的笛卡尔积。

    三条演进路径
    ABAC（基于属性）：规则写成表达式 user.region == resource.region && user.level >= 3，擅长多维度与动态上下文；代价是可读性差、难以回答「谁能访问 X」这个反向问题。
    ReBAC（基于关系）：权限沿关系图继承（Google Zanzibar），擅长层级资源与共享；代价是要维护关系图并保证查询快，以及权限撤销后的缓存一致性。
    混合：实践中的常见答案。
    固定的演进顺序
    先 RBAC 管粗粒度 → 遇到角色爆炸时给关键维度加 ABAC 条件 → 有共享/层级需求时局部引入 ReBAC。特别注意不要把租户维度做成角色，那是角色爆炸最常见的起因。
    但真正要早做的不是选模型
    而是把授权判断收拢到一个地方（PEP/PDP 分离）。模型可以换，散落在几十个 if 里的判断换不动。

11.3 高级（体现深度）

  1. 高级「零信任」到底改变了什么？怎么判断一个系统真的做到了？

    它精确地否定一条假设：「网络位置 = 信任级别」。传统边界模型里内网可信、防线集中在边界；一旦有人进到内网（VPN 凭据泄露、供应链、SSRF），他就获得了内网的全部信任。

    实际改变的三件事
    ① 服务间要互相认证（mTLS + 工作负载身份）；② 授权要在每个资源处判断，不能只在边缘；③ 网络策略默认拒绝而非默认允许。
    澄清
    零信任不等于不要网络边界。防火墙和网络策略仍然是纵深防御的一层，只是不再是唯一的那层。
    一个很实用的检验
    「如果攻击者已经在集群里拿到了一个 Pod 的代码执行，他能做的事情比外部攻击者多多少？」如果答案是「多很多」，那不管部署了什么产品，信任仍然建立在网络位置上。
    投入产出比最高的一条
    默认拒绝出网。绝大多数攻击拿到代码执行后，下一步都是回连 C2 或外传数据；一条 egress deny 策略就能把「RCE」和「数据外泄」切断。成本几乎为零（多数内部服务本来就不需要访问互联网），但默认配置是允许的，需要有人显式做一次。
  2. 高级供应链安全怎么做？SBOM 有什么用？

    先认清规模：一个典型镜像里自研代码通常不到 5%，其余是运行时、框架、传递依赖和基础镜像里的系统包。花在自研代码上的全部安全投入，覆盖的是攻击面的 5%。

    三种形态，防法不同
    已知漏洞（CVE）：扫描 + 升级，难点是噪音——大量 CVE 其实不在你的调用路径上。恶意包（抢注、维护者账号被盗）：钉版 + 锁文件 + 新依赖人工评审。构建过程被污染：最难，需要可复现构建 + 产物签名 + 部署验签（SLSA）。
    一个真实的张力
    「及时升级修 CVE」与「不自动升级防投毒」直接冲突。「自动升级到最新补丁版本」这个看起来负责任的做法，恰恰是投毒攻击的传送带——攻击者拿到一个流行小库的账号，发个补丁版本，几小时内被成千上万项目自动拉取。
    没有两全的答案，只有一个显式的取舍点：常规升级定期批量做（有人 review），安全补丁走快速通道但仍需一次人工确认。
    SBOM 解决什么
    它解决「我受影响吗」：某库爆漏洞时，「我们哪些服务、哪些版本用了它」是一次查询而不是几小时翻代码——而这几小时正是攻击者的窗口。
    SBOM 不解决什么
    它不是安全措施，只是清单：不评估漏洞、不判断可达性、不阻止任何东西被引入。把它当安全措施是常见误解——它是应急响应的基础设施，价值在事故发生那一刻兑现。配套要做可达性分析，它通常能把需要处理的 CVE 降一个数量级，而降噪本身就是安全价值。
  3. 高级假设系统已经被攻破，你的设计要保证什么？

    入侵的平均发现时间以周计，很多还是被外部通报的。所以要能回答三个问题：我能发现吗？能知道他动了什么吗？能证明哪些租户受影响吗？最后一个在多租户 SaaS 里是合规通报的前提——答不出来就只能按最坏情况通知全部客户。

    审计日志的三条硬要求
    ① 只能追加，攻击者删不掉：应用只有 append 权限，日志实时推到另一个信任域（不同账号、不同集群）。② 能回答四个 W：谁（主体身份不是 IP）、何时、对什么（资源 ID + 租户 ID）、结果。拒绝也要记——一连串被拒绝的访问正是探测行为的特征。③ 和业务日志分开：留存期要求不同，访问权限要求也不同。
    一个反直觉的风险
    审计日志本身可能泄露敏感数据。记「谁查了什么」时很容易把查询参数整个记下来，而审计日志的访问权限通常比业务库更宽（安全、合规、运维都要看），于是它成了新的泄露点。记资源标识，不记资源内容。
    怎么选告警信号
    问一个问题：「有没有哪个事件，在系统健康时永远不会发生？」跨租户访问被拒绝、被拒绝的出网连接、容器里起了 shell——这些是零噪音、出现一次就该看的信号，不需要调阈值、不随流量增长误报、不因扩容失效。
    相比之下「错误率超过 5%」这类阈值告警既要不断调参又容易被淹没。安全告警最容易犯的错是告警太多，然后所有人都不看了。
  4. 高级什么时候不该加安全措施？

    安全措施的成本体现在开发速度、调试难度、故障模式和运维负担上。加错地方会同时损失效率和可靠性，而并不换来安全。

    五条反向判据
    ① 单租户、内部工具：mTLS 与 RLS 的收益来自「防范同一系统内的其它主体」，这个场景里没有这类主体。② 数据本身公开：该保护的是完整性与可用性，投在机密性上是错配。③ 威胁模型里没有这个威胁：「别人都在做」不是理由，每条控制都应能指回一条具体威胁。④ 它会被绕过：加了 WAF 但内网能直连、要求代码评审但有紧急发布通道。
    ⑤ 最重要的一条：团队没有能力运维它
    一个没人会调、出问题只能整体重启的安全组件（SPIRE、Vault、服务网格），会同时降低安全性和可用性——它成了新的故障源，而且没人敢碰。
    最危险的状态
    不是「没有防护」，而是「以为有防护」。前者会让人保持警惕、在决策时考虑风险；后者会让人把风险从心里划掉。
    所以每加一条控制都要配一个问题：「怎么绕过它？」答不上来说明还没想清楚；答得上来就要么堵住那条路径，要么把它写进 ADR 的「后果」一栏——让后来者知道这条防线的边界在哪。
