API 设计

API 的难点不在写接口，在它发出去之后就改不动了。这一篇按「一个改动会波及多少调用方」来组织：错误模型为什么也是契约、幂等键的四个边界、翻页期间数据变了会怎样、以及最难的那件事——怎么下线一个老版本。含 3 条 ADR。

核心难度 ★★★★☆ 应用层架构 阅读时长 ~40 min 前置 HTTP / 分布式基础
01

API 是契约，不是实现细节

一旦发布就很难改——设计时就要考虑演进

API（Application Programming Interface）是服务对外暴露的契约：调用方依赖它编程，一旦有人在用，你就不能随意破坏它。好的 API 设计追求四个目标：易用、一致、可演进、难以误用。坏 API 的代价是长期的——它会渗透进所有调用方的代码，改一个字段可能要协调几十个团队。

生活类比：餐厅菜单

API 就像餐厅的菜单：顾客（调用方）照着菜单点菜，不关心后厨（实现）怎么做。菜单要命名清晰（「宫保鸡丁」而非「菜品 A」）、分类合理、价格明确（返回结构稳定）。后厨可以换厨师、改工艺（重构实现），但只要菜单不变，顾客就无感知。一旦你把「宫保鸡丁」下架或改成别的味道，所有习惯点它的老顾客都会投诉——这就是破坏性变更。

映射：菜单=接口契约 · 后厨=实现 · 换厨师=重构 · 下架菜品=breaking change
🧭 设计原则（贯穿全文）
  • 面向调用方：以业务语义而非数据库表结构组织接口。
  • 一致性：命名、分页、错误格式全局统一，降低学习成本。
  • 最小惊讶：行为符合直觉，GET 不产生副作用，DELETE 幂等。
  • 为演进而设计：预留扩展、只做加法、破坏性变更走版本。

1.1 场景与它的三类消费者

全篇用一个具体系统做锚点：一个面向企业客户的订单开放 API。它有三类消费者，而这三类的差别决定了后面几乎所有取舍：

消费者规模你能让它改代码吗它约束了什么
自家 Web 前端1 个能，和你同一次发版基本不构成约束
自家移动端2 个（iOS / Android）能改，但老版本 App 会存活 1–2 年版本至少要兼容两年
客户的服务器800 家企业客户不能。你只能通知，改不改是他们的事这一类定义了「契约」这个词的全部分量

1.2 改一个字段的真实代价

把订单金额字段 amount 的类型从整数（分）改成字符串（避免大数精度问题）。这是一个「小改动」。

· 自家前端：改一行，下次发版带上。成本约等于零。
· 移动端：改代码 + 发版 + 等用户升级。按经验，老版本覆盖率降到 5% 以下要 6–12 个月。
· 800 家客户：每一家都要排期、改代码、测试、上线。按 30% 的客户在 3 个月内响应算，要彻底完成需要 1–2 年，而且总有几十家永远不动。

这就是「API 是契约」的量化含义：一个字段的类型，一旦发布，你要为它维护一到两年的双轨。
由此得到一条贯穿全篇的判据：设计 API 时，每一个决定都要问「如果这个决定错了，改回来要多久」。

字段名、类型、错误码、分页方式、幂等语义——这些一旦有 800 家客户在用，纠错成本就是以年计的。相比之下，实现层面的决定（用什么数据库、怎么缓存）随时可以改。把有限的设计时间投在「改不动的那部分」上，这是 API 设计和内部重构最大的区别。
02

风格选型：REST / gRPC / GraphQL

没有银弹，看场景

三种主流风格解决不同问题。选型的第一问是：谁在调用？浏览器/第三方 → REST 或 GraphQL；内部服务间高性能调用 → gRPC。

维度REST (HTTP+JSON)gRPC (HTTP/2+Protobuf)GraphQL
数据形态资源为中心方法/RPC 为中心查询为中心
传输/编码HTTP/1.1 + 文本 JSONHTTP/2 + 二进制 Protobuf（紧凑快）HTTP + JSON
性能一般高（二进制 + 多路复用 + 流式）一般（解析复杂）
浏览器友好✓ 原生✗ 需 gRPC-Web✓
取数灵活易过度/不足获取固定按需取字段，解决 over/under-fetch
典型场景公开 API / CRUD内部微服务、低延迟聚合多源、前端驱动
⚖️ 决策要点
  • 对外公开 API：REST 生态最成熟、调试最方便、缓存友好（走 HTTP 语义）。
  • 内部服务间：gRPC——强类型契约（.proto）、代码生成、高性能、支持流式。
  • 前端聚合多后端：GraphQL——一次请求取全所需、避免 N 次往返；代价是缓存与限流更难、有 N+1 查询陷阱。
  • 三者可共存：内部 gRPC + 对外 REST/GraphQL 网关转换。
03

RESTful 设计规范

资源 + 动词 + 状态码

REST 的核心是用 URL 表达资源（名词），用 HTTP 方法表达动作（动词）。把动词塞进 URL（/getUser?id=1）是最常见的反模式。

操作坏例 ❌好例 ✅
查用户GET /getUser?id=1GET /users/1
建用户POST /createUserPOST /users
改用户POST /updateUserPUT /users/1（全量）/ PATCH /users/1（部分）
删用户GET /deleteUser?id=1DELETE /users/1
子资源GET /getUserOrders?uid=1GET /users/1/orders
📐 方法语义（安全性 / 幂等性）
  • GET：只读，安全（无副作用）+ 幂等，可缓存。
  • PUT：全量替换，幂等（重复调用结果一致）。
  • DELETE：删除，幂等（删已删的返回 204/404，不报错重复删）。
  • POST：创建/触发，非幂等（重复会创建多条）——见下一节幂等设计。
  • PATCH：部分更新，是否幂等取决于语义（如 increment 就不幂等）。

命名约定：资源用复数名词（/users）、小写 + 连字符、层级不超过 2-3 层；非 CRUD 的动作型接口可用子资源表达（POST /orders/1/refund）。

04

错误处理与状态码

让调用方能程序化处理错误

正确使用 HTTP 状态码 + 结构化错误体，是专业 API 的分水岭。不要 200 里塞 {"code": 500}——让 HTTP 层就能区分成功失败。

类别码含义
2xx 成功200 / 201 / 204OK / 已创建 / 无内容
4xx 客户端错400 / 401 / 403 / 404 / 409 / 422 / 429参数错 / 未认证 / 无权限 / 不存在 / 冲突 / 语义校验失败 / 限流
5xx 服务端错500 / 502 / 503 / 504内部错 / 网关错 / 不可用 / 超时

结构化错误体应包含机器可读的 code + 人类可读的 message + 可选的字段级细节 + trace_id（便于排障）：

{
  "error": {
    "code": "ORDER_ALREADY_PAID",
    "message": "订单已支付，无法重复支付",
    "details": [{ "field": "order_id", "issue": "state conflict" }],
    "trace_id": "a1b2c3d4"
  }
}
⚠️ 常见坑
  • 4xx vs 5xx 混淆：客户端传错参数是 400，别返回 500（会误触发告警/重试）。
  • 错误码要稳定：code 是契约的一部分，调用方按它分支；message 可随时改文案。
  • 不泄露内部信息：5xx 别把堆栈/SQL 返回给外部。

4.1 错误也是契约

最常见的做法是：成功路径认真设计，错误路径「返回个 500 加一句 message 就行」。但调用方的代码里，处理错误的分支往往比处理成功的分支还多。message 是给人看的，如果它是唯一的信息来源，调用方就只能解析 message 字符串来判断该怎么办——而你下次改文案就会把他们全部搞挂。

所以错误响应的三个字段各有明确分工，其中只有 code 是契约：

字段给谁看能不能改
code（稳定枚举串）程序——调用方按它分支不能改。它和字段名一样是契约
message人——日志、报错弹窗随时改，改文案、改语言都行
details / trace_id排障可加不可减

4.2 三类错误：调用方靠什么分支

调用方拿到一个错误，只需要回答一个问题：接下来该干什么。而答案只有三种，所以错误码的设计应当让这三种一眼可分：

退避后重试 429 必须带 Retry-After， 否则调用方只能猜退避多久 ② 不可重试 400 参数错、401、403、404、422 动作：直接失败，别重试 这类错误是确定性的—— 重试一万次结果一样 ③ 需要用户介入 余额不足、库存不够、状态冲突 动作：把信息透传给用户 技术上「成功」了， 只是业务上不允许 为什么不能只靠 HTTP 状态码分类 500 大多可重试，但「服务端遇到了一个确定性 bug」也是 500——重试没用。409 冲突有时该重试（乐观锁）， 有时不该（订单已支付）。状态码表达的是「错在哪一层」，而调用方需要的是「接下来该干什么」——这是两个不同的维度。 做法：在错误体里显式给一个 retryable: true/false，或者让 code 的命名规约自带这个信息。别让调用方去猜。
「显式给 retryable」这个建议看起来很小，但它把一个判断从调用方挪到了服务方——而只有服务方知道这个错误到底是不是暂时的。

不这么做的后果在重试放大那里会成倍出现：调用方不确定能不能重试，保守起见就都重试；三层各重试 3 次就是 27 倍，而其中大部分是重试一万次也不会成功的确定性错误。这些无效重试恰好在系统过载时最密集。
05

幂等性设计

网络会重试，你的写接口扛得住吗

分布式环境下，请求超时不等于失败——可能服务端已处理，只是响应丢了。客户端重试就会导致重复下单、重复扣款。幂等性保证「同一操作执行一次和多次效果相同」。

生活类比：电梯按钮

电梯的楼层按钮是幂等的：你焦急地按 10 次「5 楼」，电梯也只去一次 5 楼。而「加 1」这种操作不幂等——按 10 次就加了 10。写 API 要设计成电梯按钮，而不是计数器。

映射：按 5 楼=幂等写 · 按 10 次仍去一次=重试安全
🔑 实现方式
  • 幂等键（Idempotency-Key）：客户端为每次业务操作生成唯一 key 放请求头；服务端用「唯一约束 / 去重表」记录已处理的 key，重复请求直接返回首次结果。Stripe 就是这么做的。
  • 业务唯一约束：如订单号唯一索引，重复插入直接冲突返回既有订单。
  • 状态机：只允许合法状态流转（待支付→已支付），重复支付命中「已支付」直接返回成功。
  • 乐观锁 / 版本号：UPDATE ... WHERE version = N，防并发覆盖。

补充：GET/PUT/DELETE 天然幂等，重点是给 POST 加幂等键。

5.1 幂等键的四个边界

「用幂等键去重」这句话说起来简单，真正实现时有四个必须回答的问题。每一个答错都会在并发下出问题：

第一次还在处理时第二次请求到达，它会发现「没有记录」于是当成首次请求—— 两次并发执行，幂等失效。占位必须发生在处理之前，而不是完成之后。
问题正确做法答错的后果
① 谁生成 key 客户端生成（UUID），并在重试时复用同一个 服务端生成毫无意义——重试时客户端拿不到上次那个；客户端每次重试换新 key 也一样，等于没有幂等
② 什么时候占位 处理之前，用唯一索引原子占位 处理完再记录 → 第一次还在跑时第二次到达，两次并发执行（见图 2）
③ 同 key 不同参数 返回 422 冲突，不要返回旧结果 返回旧结果 = 调用方以为「下单 200 元成功了」，实际系统里是上次那笔 100 元的
④ key 存多久 覆盖调用方最长的重试窗口，24 小时是常见值 太短：迟到的重试变成新请求。太长：去重表无限增长——所以要有 TTL 和清理
第 ③ 条容易被当成小细节，但它是幂等键最危险的失效方式。「同 key 不同参数」意味着调用方的代码有 bug（复用了 key 但改了内容），此时返回旧结果会让这个 bug 变得不可见——调用方以为新请求成功了，而系统里根本没有这笔。
做法是把请求体的哈希一起存进去，不匹配就报 422。这样调用方的 bug 会立刻暴露，而不是变成一笔对不上的账。
最后再退一步：能设计成天然幂等的操作，就不需要幂等键。「把订单状态设为已支付」重复执行无害，「给余额加 100」不行。
图片流水线那篇把这一点做到了极致：产物路径由内容哈希决定，同一张图处理 100 次产出逐字节相同的结果，「重复」在下游根本不可观测——去重需要状态，幂等不需要。设计接口时先问一句「能不能做成声明目标状态而不是增量」，能的话整套去重机制都省了。
06

分页 / 过滤 / 排序

列表接口的三个必答题

任何返回列表的接口都必须分页——否则数据一多就拖垮服务与网络。分页有两种主流方案：

方案Offset 分页游标（Cursor / Keyset）分页
形式?page=3&size=20 / ?offset=40&limit=20?cursor=xxx&limit=20
实现LIMIT 20 OFFSET 40WHERE id > last_id LIMIT 20
深翻性能✗ 差（OFFSET 越大越慢，要扫过前面所有行）✓ 稳定（走索引定位）
数据漂移✗ 会重复/漏（翻页间有增删）✓ 稳定
能否跳页✓ 可跳到第 N 页✗ 只能上下翻
📌 选型
  • 后台管理/需要跳页：Offset（数据量可控时）。
  • 信息流/大数据量/无限滚动：游标分页（性能与一致性都更好）——大厂列表接口标配。
  • 过滤/排序：白名单允许的字段（防注入 + 防扫全表），如 ?status=paid&sort=-created_at。

6.1 翻页期间数据变了会怎样

表里那行「数据漂移」是两种分页最本质的差别，值得画出来——它不是性能问题，是正确性问题：

上一页的最后一条被重复返回。 反过来如果是删除，就会漏掉一条——而且没人会发现。 ✅ 游标分页：WHERE id < last_id 第 1 页读到 [A B C D]，游标 = D 的 id A B C D ← 游标记住它 同样插入 X X A B C D 第 2 页 = 「id 小于 D」的下一批，不受 X 影响 既不重复也不遗漏。代价是不能跳到第 N 页—— 因为「第 5 页」这个概念本身就依赖一个稳定的快照。 深分页的性能差异（OFFSET 100000 要扫过前十万行）是附带的；上面这个正确性差异才是选游标的主要理由。
「不能跳页」常被当成游标分页的缺点，但换个角度看它是诚实：在一个持续变化的列表上，「第 5 页」本来就不是一个有确定含义的概念。offset 分页给了你一个跳页按钮，代价是这个按钮返回的内容取决于你什么时候点它。

所以判据不是「要不要跳页功能」，而是「这个列表在用户翻页期间会不会变」。后台管理里查历史订单（数据基本不动）→ offset 没问题；信息流、消息列表、实时榜单 → 必须游标。
07

版本演进与向后兼容

改 API 的艺术：只做加法

API 会持续演进，但你不能随时打断存量调用方。核心原则：兼容变更直接改，破坏变更走新版本。

兼容变更（可直接做）✅破坏变更（需新版本）❌
新增可选字段 / 新增接口删除或重命名字段
新增枚举值（调用方需容忍未知值）改字段类型 / 语义
放宽输入校验收紧校验 / 新增必填参数
新增可选响应改错误码 / 状态码含义
🔢 版本化策略
  • URL 版本：/v1/users → /v2/users。最直观、缓存/路由友好，最常用。
  • Header 版本：Accept: application/vnd.api.v2+json。URL 干净但调试不直观。
  • 灰度与下线：新旧版本并行 → 引导迁移（Deprecation 头 + 文档）→ 监控旧版流量归零 → 下线。切忌硬切。
Protobuf 的兼容智慧

gRPC 用 Protobuf，天生为演进设计：字段靠编号（field number）而非名字识别。只要不复用已删字段的编号、不改类型，加字段、删字段（保留编号 reserved）都向后兼容。这是「只做加法」原则的工程化体现。

映射：field number=稳定标识 · reserved=防编号复用 · 新增字段=安全

7.1 难的不是发新版本，是下线老版本

「破坏变更走新版本」这条建议只解决了一半问题。发一个 v2 很容易——加一套路由的事。真正的难点是：v1 怎么办？
如果没有下线机制，结果是 v1、v2、v3 同时在线，每个新需求都要实现三遍，每个 bug 要修三遍。几年后维护成本会压垮团队，而这时候你已经不敢下线任何一个了——因为不知道还有谁在用。

下线一个版本需要四步，而第一步决定了后面三步能不能做：

步做什么没做会怎样
① 能看见谁在用 按 版本 × 调用方 打点。每个客户一个可识别的凭据（§8），日志里能聚合出「哪 37 家客户还在调 v1」 这一步没做，后面全做不了。你只能看到「v1 还有 3% 流量」，但不知道是谁——于是永远不敢关
② 明确宣告 响应里带 Deprecation 和 Sunset 头（RFC 8594），文档标注，并且主动联系那 37 家 只发邮件不带响应头 → 对方的技术人员根本收不到
③ 制造压力 逐步降级：先是响应变慢一点，再是每天固定时段返回错误（brownout），最后才彻底关 直接从「正常」跳到「关闭」，会在关闭那一刻集中爆发
④ 关闭并保留回滚 关掉后保留一段时间的快速恢复能力 关了发现漏了一个大客户，只能手忙脚乱
第 ③ 步的 brownout（计划性短时不可用）值得单独说，它是 Google 和一些大平台的实际做法：在下线前的几周里，每天挑一个时段让老版本返回错误，时长逐周递增（1 分钟 → 10 分钟 → 1 小时）。

它的作用不是技术上的，是组织上的：一封「v1 将于三个月后下线」的邮件会被归档，而一次真实的、可预告的故障会让对方的技术团队立刻排上期。而且因为是预告过的、短时的，它造成的损失可控，比真正下线时的集中爆发小得多。

更一般的原则：迁移的推力不来自通知，来自「不迁移会有代价」。
回到 ①。它解释了为什么每个调用方都要有独立可识别的凭据——这不只是安全需求，它是 API 能够演进的前提。所有客户共用一个 key，或者根本不区分调用方，那么「谁还在用 v1」这个问题就永远没有答案，你的 API 就再也下不了线。
同理，契约测试的契约仓库回答的是同一类问题：「我这个字段还有谁在用」。可演进性的本质是可观测性——你只能安全地改动那些你知道谁在依赖的东西。
08

认证 / 授权 / 限流

安全与稳定的入口防线
  • 认证（你是谁）：API Key（简单，服务间）、OAuth2 / JWT（用户态，无状态可扩展）、mTLS（服务间强身份）。
  • 授权（你能做什么）：RBAC（角色）/ ABAC（属性）/ scope（OAuth 细粒度）。在网关或服务入口统一校验。
  • 限流：按 key/用户/IP 限速，返回 429 + Retry-After + X-RateLimit-* 头，保护后端。详见 限流熔断降级。
  • 其它：全站 HTTPS、输入校验防注入、CORS、请求大小限制、幂等键防重放。
🧱 分层拦截

典型链路：API 网关做统一认证 + 限流 + 路由 → 服务做业务授权 + 参数校验。把横切关注点（认证/限流/日志/熔断）下沉到网关，业务服务保持轻量。

09

gRPC 深入

内部微服务的高性能选择

gRPC = Protobuf（IDL + 序列化）+ HTTP/2（传输）+ 代码生成（多语言 stub）。为什么内部服务间它比 REST 强：

  • 强契约：.proto 定义即契约，编译期生成客户端/服务端代码，避免手写解析与字段拼错。
  • 性能：二进制编码比 JSON 小且快；HTTP/2 多路复用（一连接跑多请求，避免队头阻塞）+ 头压缩。
  • 四种调用：一元（Unary）、服务端流、客户端流、双向流——原生支持流式（如实时推送、大文件分块）。
  • 拦截器：统一做认证、日志、重试、超时（deadline 传播）。
代价 / 权衡说明
浏览器支持需 gRPC-Web + 代理转换，不如 REST 直接。
可调试性二进制不可肉眼读，需 grpcurl / 反射；REST 用 curl 即可。
基础设施负载均衡需 L7（HTTP/2 感知），传统 L4 LB 会把多路复用打到单实例。

实践：内部 gRPC + 边缘 REST/GraphQL 网关兼得性能与开放性——这是主流微服务栈的标准姿势。参见 微服务架构。

10

WebService · SOAP · WSDL

你以为它死了，但工业、金融、政务系统里到处都是

如果只做互联网业务，你可能一辈子碰不到 SOAP。但一旦接触工业设备管理、银行核心、保险、电信 BOSS、政务对接、老 ERP，几乎必然要对接 WebService——这些系统的对外接口十年前定下来，现在也不会改。它不是「过时技术」，而是「存量技术」，这两者对工程师的意义完全不同。

生活类比：公文 vs 微信消息

REST 像发微信：想说什么直接说，格式随意，对方看懂就行，快。SOAP 像走公文流程：必须用红头文件模板（Envelope），有固定的抬头（Header）和正文（Body），要盖章（WS-Security），还要事先把公文格式手册（WSDL）发给对方，对方照着手册就能自动生成填表工具。啰嗦、慢，但格式严格、可机器校验、有法律效力级的强契约——这正是金融和政务系统喜欢它的原因。

映射：公文模板=SOAP Envelope · 格式手册=WSDL · 盖章=WS-Security · 档案室目录=UDDI（已基本废弃）
📚 三个术语先分清
  • WebService：一个宽泛的概念——「通过网络暴露的、可被程序调用的服务」。狭义语境下（尤其在国内招聘和老项目里）特指 SOAP + WSDL 这一套。
  • SOAP（Simple Object Access Protocol）：消息格式规范。规定消息必须是一个 XML Envelope，内含可选的 Header（放认证、事务、路由等元数据）和必需的 Body（放实际参数或 Fault 错误）。它与传输层无关——最常见跑在 HTTP POST 上，但也能跑在 SMTP、JMS 上。
  • WSDL（Web Services Description Language）：接口描述文件，本身也是 XML。它精确定义了有哪些操作、每个操作的入参出参的 XML Schema、绑定到什么传输协议、服务地址在哪。它的价值在于可以直接生成客户端代码——这是 SOAP 最强的一点，比「读文档手写 HTTP 请求」可靠得多。

一次典型的 SOAP 调用长这样（工业设备查询状态）：

POST /DeviceService HTTP/1.1
Host: mes.factory.local
Content-Type: text/xml; charset=utf-8
SOAPAction: "http://factory.local/GetDeviceStatus"     <!-- ★ 老式绑定靠这个头路由 -->

<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Header>
    <wsse:Security><wsse:UsernameToken>
      <wsse:Username>mes</wsse:Username>
      <wsse:Password>***</wsse:Password>
    </wsse:UsernameToken></wsse:Security>
  </soap:Header>
  <soap:Body>
    <GetDeviceStatus xmlns="http://factory.local/">
      <deviceId>LINE3-CAM01</deviceId>
    </GetDeviceStatus>
  </soap:Body>
</soap:Envelope>

<!-- 出错时 Body 里返回 Fault，HTTP 状态码是 500 -->
<soap:Body><soap:Fault>
  <faultcode>soap:Client</faultcode>
  <faultstring>Unknown deviceId</faultstring>
</soap:Fault></soap:Body>
维度SOAP / WebServiceREST
契约WSDL 强契约，机器可读、可生成代码、可自动校验OpenAPI 是可选的约定，且描述与实现容易脱节
消息格式只能 XML，Envelope 固定结构通常 JSON，格式自由
报文体积大（XML 标签冗余，常是等价 JSON 的 2–5 倍）小
错误表达<soap:Fault>，HTTP 状态码固定 500直接用 HTTP 状态码语义
传输层与传输无关（HTTP / SMTP / JMS 均可）绑定 HTTP
缓存✗ 全是 POST，HTTP 缓存完全用不上✓ GET 天然可缓存
安全 / 事务WS-Security / WS-AtomicTransaction 等成套规范，支持消息级签名与加密（可穿越中间节点）靠 TLS（传输级）+ OAuth2，消息级安全要自己做
调试需专用工具（SoapUI）；肉眼读 XML 很累curl 即可
今天该选只在对接存量系统时新项目默认
🛠 C++ / Qt 侧怎么对接
  • gSOAP：C/C++ 领域事实上的标准工具。wsdl2h 把 WSDL 转成头文件，soapcpp2 生成客户端/服务端桩代码，之后就像调本地函数。工业与嵌入式场景（ONVIF 摄像机、部分 PLC 网关）几乎都用它。注意它是 GPL / 商业双许可，闭源产品要买授权。
  • 手工拼 XML + HTTP POST：接口只有两三个、结构简单时，用 QNetworkAccessManager 或 libcurl 直接 POST 一段模板化的 XML，再用 QXmlStreamReader 解析响应，比引入整套 gSOAP 轻得多。但一定要用 XML 库解析，不要用字符串查找——命名空间前缀、属性顺序、自闭合标签都会让手写解析崩掉。
  • ONVIF 是最常遇到的一个：网络摄像机的行业标准，底层就是 SOAP + WSDL。做视觉/安防相关的上位机，几乎一定会碰到设备发现（WS-Discovery，走 UDP 组播）、取流地址、云台控制这几组 SOAP 调用。
⚠️ 对接老 WebService 的六个高频坑
  • WSDL 里的地址是内网地址：生成的桩代码会去连一个连不通的 host。要在运行时覆盖 endpoint，别改生成的代码。
  • 命名空间必须完全一致：少一个 xmlns 或前缀对不上，服务端直接返回 Fault 且错误信息通常毫无帮助（「无法反序列化」）。
  • SOAPAction 头：SOAP 1.1 常靠它路由，漏了会 404 或 500；SOAP 1.2 改用 Content-Type 里的 action 参数——两个版本混用是最常见的对接失败原因。
  • 字符编码：老系统常是 GBK，而 XML 声明里写 UTF-8。中文乱码时先确认实际编码，别急着改自己这边。
  • HTTP 500 不代表服务器出错：SOAP 的业务错误（参数非法、无权限）也返回 500 + Fault。不能按状态码做重试判断，必须解析 Body 里的 faultcode——soap:Client 是你的错（别重试），soap:Server 才可能值得重试。
  • 没有超时就等于挂死：老系统响应慢是常态，客户端必须自己设连接和读取超时，并且整个调用要能被取消，否则 UI 线程一卡就是几十秒。

相关阅读：HTTP 层面的报文、状态码与调试见 HTTP / HTTPS 协议完全指南；Qt 侧的网络请求与超时处理见 Qt 网络与本机 IPC。

11

take-aways 与反向判据

🎯 一页速记
  • API 是契约：一个字段类型改动，800 家客户要一到两年才能收敛。把设计时间投在「改不动的那部分」上。
  • 选型：对外 REST、内部 gRPC、前端聚合 GraphQL；可共存。
  • REST：资源做名词、方法做动词、状态码用对。
  • 错误也是契约：只有 code 不能改，message 随便改。按「调用方接下来该干什么」分成可重试 / 不可重试 / 需用户介入三类，并显式给 retryable——别让调用方去猜。
  • 幂等键四个边界：客户端生成并在重试时复用、处理之前原子占位（不是完成之后）、同 key 不同参数报 422、TTL 覆盖最长重试窗口。能做成天然幂等就不需要键。
  • 分页：游标 vs offset 的差别首先是正确性（翻页期间数据变化会重复或遗漏，且不报错、测试发现不了），性能只是附带。
  • 演进「只做加法」；但难的不是发新版本，是下线老版本——前提是「能看见谁在用」，否则你永远不敢关。
  • SOAP/WSDL 不是新项目的选项，但对接工业、金融、政务存量系统时绕不开——C++ 侧用 gSOAP 生成桩代码，注意 HTTP 500 也可能是业务错误。

11.1 什么时候不必这么讲究

如果……哪条可以放松理由
只有自家前端在调，且和后端同一次发版 版本化、下线机制 「契约」的分量来自你改不动的那些调用方。全都能一起改时，直接改就是了——加一套 v2 只是纯成本
内部服务间，团队之间沟通顺畅 严格的 REST 语义 gRPC 的方法风格更直接。把动作硬套成资源（POST /orders/1/cancellations）经常比 CancelOrder 更难懂
接口是只读查询 幂等键 GET 天然幂等，加键是纯开销
列表数据基本不变（历史归档、配置项） 游标分页 offset 的正确性问题不会出现，而跳页对后台管理很有用
但如果有第三方在调 以上全都不能放松 哪怕现在只有 3 家。API 的成本不是按调用量算的，是按「有多少你改不动的调用方」算的

三条 ADR

每一条都写清了付出什么
ADR-001对外 REST + 对内 gRPC，边缘网关做协议转换已接受
背景
三类消费者的诉求相反（§1.1）：800 家客户的服务器需要最低的接入门槛和最好的可调试性；内部 12 个服务之间要的是强类型契约和低延迟。
决策
对外只提供 REST + JSON（生态成熟、curl 就能调、缓存走 HTTP 语义）；内部服务间用 gRPC（.proto 即契约、代码生成、deadline 原生传播）；由边缘网关做转换。
后果
得到：客户接入成本最低；内部拿到强契约与性能；.proto 的字段编号机制让内部接口天然向后兼容。
付出：同一个概念要维护两套定义（proto 与对外的 JSON schema），转换层是一个必须同步演进的地方；网关成为所有对外流量的必经点，它的可用性就是 API 的可用性。
ADR-002错误用稳定的字符串枚举码，并显式给出 retryable已接受
背景
HTTP 状态码表达的是「错在哪一层」，而调用方需要的是「接下来该干什么」（§4.2）。两者不是一个维度，硬用状态码表达会导致调用方去解析 message 字符串。
决策
错误体固定为 {code, message, details, trace_id, retryable}。code 是全局唯一的大写下划线串（ORDER_ALREADY_PAID），纳入契约管理，只增不改；retryable 由服务端判断并显式给出。HTTP 状态码仍然正确使用，但它只是粗分类。
后果
得到：调用方能可靠地分支；retryable 把「能不能重试」这个只有服务端知道的判断放在了服务端，减少了无效重试放大。
付出：错误码成为一份需要治理的清单（防止各团队随意新增、语义重叠）；码一旦发布就不能改语义，改了等同于破坏性变更——需要评审流程。
ADR-003每个调用方独立凭据；版本下线走「可观测 → 宣告 → brownout → 关闭」四步已接受
背景
发新版本容易，下线老版本难。而下线的前提是「能看见谁在用」——共用凭据或不区分调用方，这个问题就永远没有答案，API 再也下不了线（§7.1）。
决策
① 每个客户一套独立凭据，网关按 版本 × 调用方 打点；② 下线前带 Deprecation / Sunset 响应头并主动联系仍在用的客户；③ 关闭前几周做 brownout（每天固定时段返回错误，时长逐周递增）；④ 关闭后保留一段快速恢复能力。
后果
得到：老版本能真的被下线，避免 v1/v2/v3 并存导致每个需求实现三遍；独立凭据同时满足安全侧的审计与限流需求。
付出：凭据管理与轮换的运维成本；brownout 是一次有意制造的故障，需要事先和客户沟通并承担关系成本——它换来的是「不迁移会有代价」这个推力，但用错场合会损害信任。

高频面试题 · API 设计

12 道，按难度分三档

点击每道题展开参考答案（先自测，再对照）。

13.1 基础（必答）

  1. 基础REST、gRPC、GraphQL 怎么选？

    第一问是谁在调用，不是「哪个性能好」。

    对外公开 API → REST
    生态最成熟、curl 就能调、缓存走 HTTP 语义、第三方接入成本最低。对 800 家客户来说，接入门槛比性能重要得多。
    内部服务间 → gRPC
    .proto 即契约、编译期生成 stub、二进制编码 + HTTP/2 多路复用、原生支持流式与 deadline 传播。
    前端聚合多后端 → GraphQL
    一次请求取全所需，避免 over/under-fetch。代价是缓存与限流更难（每个查询都不一样）、有 N+1 陷阱、以及查询复杂度攻击（一个深嵌套查询能打死服务，需要复杂度上限）。
    三者可共存
    典型是内部 gRPC + 边缘网关转 REST/GraphQL。代价是同一个概念要维护两套定义，转换层必须同步演进。
  2. 基础为什么说「API 是契约」？改一个字段有多贵？

    关键不在「有人在用」，在「有多少调用方是你改不动的」。

    算一笔账
    把金额字段从整数改成字符串：自家前端成本约等于零（同一次发版）；移动端要 6–12 个月等老版本覆盖率降下来；800 家客户要 1–2 年，而且总有几十家永远不动。
    推论
    设计 API 时每个决定都要问「如果错了，改回来要多久」。字段名、类型、错误码、分页方式、幂等语义是以年计的；而实现层面的决定（数据库、缓存）随时可以改。把有限的设计时间投在改不动的那部分上。
    反过来
    如果只有自家前端在调、且能一起发版，那么版本化和下线机制都是纯成本。API 的成本不按调用量算，按「有多少你改不动的调用方」算。
  3. 基础什么是幂等？哪些 HTTP 方法天然幂等？

    同一操作执行一次和多次效果相同。它之所以必须，是因为分布式环境下请求超时不等于失败——可能服务端已处理，只是响应丢了，客户端重试就会重复下单、重复扣款。

    天然幂等的
    GET（安全 + 幂等）、PUT（全量替换）、DELETE（删已删的返回 204/404，不报错）。POST 不幂等——重点是给它加幂等键。
    PATCH 看语义：设置字段值幂等，increment 不幂等。
    四种实现
    幂等键（客户端生成 UUID，服务端去重）、业务唯一约束（订单号唯一索引）、状态机（重复支付命中「已支付」直接返回成功）、乐观锁版本号。
    加分
    能设计成天然幂等的操作就不需要幂等键。「把状态设为已支付」重复执行无害，「余额加 100」不行。设计接口时先问「能不能做成声明目标状态而不是增量」。
  4. 基础列表接口的分页怎么做？
    Offset 分页
    LIMIT 20 OFFSET 40。能跳到第 N 页，但深翻性能差（要扫过前面所有行），且翻页期间数据变化会重复或遗漏。
    游标分页
    WHERE id < last_id LIMIT 20。走索引定位，性能与页码无关；翻页期间插入删除都不影响。代价是不能跳页。
    重点不是性能，是正确性
    翻页期间有新记录插到列表头部，offset 的第 2 页会重复返回上一页的最后一条；删除则会漏掉一条。
    这两种都不报错，而且测试环境发现不了——测试数据是静止的。
    判据
    不是「要不要跳页功能」，而是「这个列表在用户翻页期间会不会变」。后台查历史订单 → offset 够；信息流、消息列表、实时榜单 → 必须游标。
    另外过滤和排序字段一定要白名单（防注入 + 防扫全表）。

13.2 中级（区分熟练度）

  1. 中级错误响应该怎么设计？

    先认识到错误也是契约：调用方代码里处理错误的分支往往比处理成功的还多。三个字段分工明确，只有 code 是契约：code 给程序分支（不能改），message 给人看（随时改文案），details / trace_id 给排障。

    最常见的错误
    只给 message。调用方只能解析 message 字符串来判断该怎么办，你下次改文案就把他们全搞挂了。
    另一个是「200 里塞 {"code": 500}」——让 HTTP 层就能区分成功失败，否则所有中间件（网关、监控、重试）都失效。
    按「调用方接下来该干什么」分三类
    可重试（超时、503、429 → 退避后重试，429 必须带 Retry-After）、不可重试（400、401、403、404、422 → 直接失败）、需要用户介入（余额不足、库存不够 → 透传给用户）。
    为什么不能只靠状态码分类
    500 大多可重试，但「服务端遇到确定性 bug」也是 500；409 有时该重试（乐观锁）有时不该（订单已支付）。
    状态码表达「错在哪一层」，调用方需要的是「接下来该干什么」——两个维度。做法是显式给一个 retryable 字段，把这个只有服务端知道的判断放在服务端。
  2. 中级幂等键怎么实现？有哪些坑？

    四个边界，每个答错都会在并发下出问题：

    ① 谁生成
    客户端生成，并在重试时复用同一个。服务端生成没有意义（重试时客户端拿不到上次那个）；客户端每次重试换新 key 也等于没有幂等。
    ② 什么时候占位 —— 最关键
    处理之前，用唯一索引原子占位（不能先查后插）。
    如果只在处理完成后记录结果，那么第一次还在处理时第二次请求到达，它会发现没记录于是当成首次请求——两次并发执行，幂等完全失效。所以状态里必须有「处理中」这一档，命中它就返回 409。
    ③ 同 key 不同参数
    返回 422 冲突，不要返回旧结果。这种情况说明调用方复用了 key 但改了内容（它自己的 bug），返回旧结果会让这个 bug 变得不可见——调用方以为「下单 200 元成功了」，实际系统里是上次那笔 100 元的。
    做法是把请求体哈希一起存进去比对。
    ④ 存多久
    覆盖调用方最长的重试窗口，24 小时常见。太短则迟到的重试变成新请求；太长则去重表无限增长，要有 TTL 和清理。
  3. 中级哪些 API 变更是破坏性的？怎么判断？

    判据是「一个按旧契约写的调用方，会不会因为这个改动而出错」。

    兼容（可直接做）
    新增可选字段、新增接口、新增枚举值（前提是调用方能容忍未知值——这一条要写进文档）、放宽输入校验、新增可选响应字段。
    破坏（需新版本）
    删除或重命名字段、改字段类型、改语义、收紧校验、新增必填参数、改错误码或状态码的含义。
    最阴险的一类：改语义
    字段 amount 的单位从「元」改成「分」——类型没变、字段还在、契约测试完全通过，但所有调用方的金额都错了 100 倍。
    没有工具能挡住它，只能靠命名（amount_cents）、评审和生产对账。
    Protobuf 的做法值得学
    字段靠编号而非名字识别，只要不复用已删字段的编号（用 reserved 占住）、不改类型，加删字段都向后兼容。这是「只做加法」的工程化体现。
  4. 中级gRPC 在什么场景下不如 REST？
    浏览器
    浏览器不能直接发 gRPC，需要 gRPC-Web + 代理转换。对外的公开 API 用 gRPC 等于给每个客户增加接入成本。
    可调试性
    二进制不可肉眼读，要 grpcurl + 服务端反射；REST 用 curl 就行，抓包也能直接看。排障时这个差别很实在——尤其是和外部团队一起排障时。
    基础设施：最容易踩的一条
    gRPC 走 HTTP/2 多路复用，一条连接上跑多个请求。传统 L4 负载均衡按连接分发，结果是一个客户端的所有请求都打到同一个实例上——负载完全不均。
    必须用 L7（HTTP/2 感知）的负载均衡，或者客户端侧做负载均衡。
    还有
    HTTP 缓存语义用不上（REST 的 GET 可以被 CDN、浏览器、反代缓存）；生态工具（Postman、日志分析、WAF）对 REST 的支持更成熟。

13.3 高级（体现深度）

  1. 高级怎么下线一个已经有几百家客户在用的 API 版本？

    先认识到：发新版本容易，下线老版本难。没有下线机制的结果是 v1/v2/v3 并存，每个需求实现三遍、每个 bug 修三遍，几年后维护成本压垮团队——而这时你已经不敢关任何一个，因为不知道还有谁在用。

    ① 能看见谁在用 —— 这一步决定后面能不能做
    按 版本 × 调用方 打点，每个客户一套独立凭据。没有这一步，你只能看到「v1 还有 3% 流量」，不知道是谁，于是永远不敢关。
    ② 明确宣告
    响应里带 Deprecation 和 Sunset 头（RFC 8594），文档标注，并主动联系仍在用的那几十家。只发邮件不带响应头，对方的技术人员根本收不到。
    ③ brownout：制造压力
    关闭前几周，每天挑一个时段让老版本返回错误，时长逐周递增（1 分钟 → 10 分钟 → 1 小时）。
    它的作用是组织上的：一封「三个月后下线」的邮件会被归档，而一次真实的、预告过的故障会让对方立刻排期。因为可控且预告过，损失远小于真正下线时的集中爆发。
    更一般的原则：迁移的推力不来自通知，来自「不迁移会有代价」。
    ④ 关闭并保留快速恢复能力
    关了发现漏了一个大客户，要能立刻恢复。
    背后的原则
    可演进性的本质是可观测性——你只能安全地改动那些你知道谁在依赖的东西。这也是为什么每个调用方要有独立凭据、以及契约仓库为什么有价值（它回答「这个字段还有谁在用」）。
  2. 高级一个「小改动」上线后大量客户报错，怎么复盘？

    先分清是哪一类，四类的成因和防法完全不同：

    ① 判成了兼容变更，其实是破坏变更
    最常见的是新增枚举值——理论上兼容，但如果调用方用的是严格枚举解析（很多强类型语言的默认行为），新值会直接抛异常。
    防法：把「必须容忍未知枚举值」写进文档和 SDK；或者干脆不新增枚举值，用一个可扩展的字符串。
    ② 改了语义没改结构
    单位变了、默认值变了、排序变了、时区变了。契约测试全过，因为类型和字段都没动。这类只能靠命名和评审。
    ③ 收紧了校验
    以前宽松接受的脏数据现在报 400。而客户一直在发脏数据，只是之前你没管。防法：先加一个「本次请求在未来版本会被拒绝」的告警响应头，观察一段时间再真的收紧。
    ④ 错误码或状态码含义变了
    调用方按 code 分支，你改了 code 的语义，他们的分支就走错了。code 一旦发布就不能改语义，要新增就新增一个。
    复盘的产出
    不该只是「以后小心」。应该是：把这类变更加进破坏性变更判定清单、在 CI 里加一条对应的契约检查、以及（如果适用）加一个能自动重跑的验证。
  3. 高级API 的限流配额怎么设计并表达给客户？

    限流算法本身见弹性篇 §2，这里只说 API 层特有的部分——核心是配额必须对客户「可预期」。

    响应头是契约的一部分
    返回 X-RateLimit-Limit / Remaining / Reset，让客户能主动控制自己的节奏而不是撞墙后才知道。被限流时返回 429 + Retry-After——没有 Retry-After，客户端只能猜退避多久，通常会猜得太激进。
    维度要和计费/合同对齐
    按客户、按接口、按操作成本（一次批量导出显然不该和一次查询算同样的额度）。如果配额维度和客户签的合同对不上，客服会天天收到质疑。
    突发额度要显式给
    令牌桶的桶容量决定了客户能不能攒一批一起发。这个值应该写进文档——不写的话客户会按最坏情况自己限速，白白浪费容量；或者按最好情况发，然后频繁撞限流。
    限流器故障时的行为也要想好
    fail-open（放行）还是 fail-close（拒绝）？对保护性限流选 fail-open——限流是保护措施，不该比被保护的东西还脆弱。但对有合规要求的配额（计费、外部 API 转售）必须 fail-close。这是个二选一，没有中间答案，必须显式决定。
  4. 高级如果让你评审一个已经上线的开放 API，你看什么？

    按「改不动的程度」从高到低看，因为那才是纠错成本最高的地方：

    ① 能不能回答「谁在用哪个版本、哪个字段」
    答不出来，这个 API 就再也演进不了——不敢删字段、不敢下线版本。这是最优先要补的能力，比任何设计问题都紧急。
    ② 错误模型
    有没有稳定的机器可读 code？调用方是不是在解析 message？可重试与否是显式的还是靠猜？这三条决定了整条链路的重试行为是否可控。
    ③ 写接口的幂等
    有没有幂等键？占位是在处理之前还是完成之后（后者在并发下失效）？同 key 不同参数怎么处理？
    ④ 列表接口的分页
    有没有分页（没有的话迟早出事）？数据会变的列表用的是 offset 还是游标？
    ⑤ 最后看一致性
    同一套 API 里，分页参数名统一吗？错误格式统一吗？时间格式统一吗？命名风格统一吗？
    不一致本身就是成本——它让每个接口都要单独读文档，而且这种成本是按调用方数量乘出来的。
    评审的产出
    区分「现在能改的」和「已经改不动的」。改不动的那些要写进 ADR 作为已知债务，并给出下一个大版本时的收敛方案——而不是留在评审纪要里。
