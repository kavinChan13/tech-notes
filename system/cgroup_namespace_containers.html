01

容器不是虚拟机

没有 Guest OS，只有被「框住」的进程

最大的误解是把容器当「轻量虚拟机」。虚拟机虚拟的是硬件：每个 VM 跑一整套自己的内核与 OS，靠 Hypervisor 隔离。容器不虚拟硬件，所有容器共享宿主机的同一个内核，只是被内核的隔离机制「框」起来。

这不是比喻，是可以当场验证的事实：容器里那个「PID 1」的 nginx，在宿主的 ps 里就明晃晃地躺着（父进程是 containerd-shim），宿主上 ls /proc/<pid>/root/etc/nginx/ 能直接翻它的文件系统。容器就是宿主上的一个普通进程——这一句是后面八章的全部前提。

🖥 虚拟机

虚拟硬件 + 独立内核/OS；隔离强、启动秒级到分钟级，内存开销以百 MB 计（要养一整套 OS）。

📦 容器

共享宿主内核，隔离靠 namespace + cgroup；毫秒启动，除应用本身几乎无额外内存开销，密度高一个数量级。

⚖️ 取舍

省资源、快，但共享内核 → 内核漏洞就是逃逸。强隔离场景用轻量 VM（Kata / Firecracker）或用户态内核（gVisor）。

这条取舍的另一半在 虚拟化与虚机 I/O：容器的攻击面是整个宿主内核（几千万行）+ 全部系统调用，虚机是 hypervisor（几十万行）。判据不是「谁更快」而是「你需要防谁」——跑自己团队的代码容器完全够，跑不受信任的第三方代码（多租户 FaaS、CI runner）就该看那一篇的轻量 VM 一节。那篇也讲清了虚机为什么「跑计算不慢、跑 I/O 慢」。
生活类比：独栋别墅 vs 合租公寓

虚拟机像独栋别墅：每家独立水电煤（内核/OS），互不影响但盖房贵。容器像一栋楼里的合租单间：共用整栋楼的水电主管道（宿主内核），每间房有独立门锁与视野（namespace），物业还限制每间的用电额度（cgroup）。便宜灵活，但主管道出问题会影响所有人。

映射：整栋楼水电=宿主内核 · 独立房间视野=namespace · 用电限额=cgroup · 合租便宜=轻量高密度

内核里根本没有「容器」这个对象

翻遍 Linux 源码找不到 struct container。内核只知道 struct task_struct 里挂着几个指针，「造一个容器」就是把这几个指针一次性指向新建的实例：

task_struct 里的字段指向什么谁负责换掉它换掉之后的效果
nsproxy一个包含 mnt / uts / ipc / net / pid / cgroup / time namespace 指针的小结构体clone() 带 CLONE_NEW*，或 unshare() / setns()看到的挂载点、主机名、网卡、进程号全都换了一套
cgroups（css_set）该任务在 cgroup 树上所属节点的一组控制器状态往 cgroup.procs 里写 PIDCPU / 内存 / IO 用量开始被计入并受限
fs（fs_struct）该任务的根目录（root）与当前目录（pwd）pivot_root() / chroot()路径解析的起点变成容器 rootfs
creduid/gid、四五个 capability 集合、所属的 user namespacesetuid / capset / CLONE_NEWUSER权限收敛；容器内 root 可以是宿主上的普通用户
seccomp挂在任务上的 BPF 过滤器链seccomp(SECCOMP_SET_MODE_FILTER, ...)白名单外的系统调用直接返回 EPERM 或杀进程
securityLSM（SELinux / AppArmor）挂的标签指针运行时写 /proc/self/attr/*MAC 策略开始约束它能碰哪些客体
三大支柱：namespace 管「看得见什么」、cgroup 管「能用多少」、镜像 / OverlayFS 管「根文件系统长什么样」。Docker、containerd、K8s 都只是把这三件事编排起来的工具。

Namespace：隔离视图

让进程以为自己独占系统

Namespace 把某类全局系统资源包装起来，让不同 namespace 里的进程看到各自独立的实例。造容器就是把一个进程放进一组新建的 namespace。

Namespaceclone 标志隔离什么没隔离什么 / 注意
PIDCLONE_NEWPID进程号空间——容器内 PID 1 是宿主上的某个大 PID宿主仍能看到并 kill 容器内进程；PID 嵌套，父 ns 永远可见子 ns
Mount (mnt)CLONE_NEWNS挂载点视图——容器有自己的根文件系统传播类型配错会把容器的挂载漏回宿主
Network (net)CLONE_NEWNET网卡、IP、路由表、iptables 规则、端口空间创建开销最大（要初始化整套协议栈实例）
UTSCLONE_NEWUTS主机名与 NIS 域名就这两样，最简单的一种
IPCCLONE_NEWIPCSystem V IPC、POSIX 消息队列跨容器共享内存得显式挂同一个 /dev/shm
UserCLONE_NEWUSERUID/GID 映射——容器内 root 可映射为宿主普通用户唯一能被非特权用户创建的；rootless 的基石，也是 CVE 高发区
CgroupCLONE_NEWCGROUP隐藏宿主 cgroup 层级，只看到自己那棵子树的根只改视图，不改限额

三个相关系统调用

  • clone()：创建新进程时带 CLONE_NEW*，子进程直接诞生在新 namespace 里。runc 用的是这个。
  • unshare()：让当前进程脱离并进入新 namespace。PID namespace 特殊——当前进程不换 PID，要它的子进程才进新 PID ns，所以 unshare --pid 必须配 --fork。
  • setns()：加入一个已存在的 namespace，docker exec 与 nsenter 就是它。

两个非直觉之处（图里画不下的细节）

  • setns 进 PID namespace 后当前进程的 PID 不变，只有此后 fork 的子进程才在新 ns 里分配 PID——这是 nsenter -t PID -p 之后 echo $$ 看起来「不对」的原因。
  • user 与 pid namespace 有嵌套深度上限（当前内核 32 层），嵌套容器套太深会直接失败。

namespace 靠什么活着——以及泄漏怎么查

  • namespace 是引用计数对象，最后一个引用消失时才销毁。引用只有三类：① 还有任务的 nsproxy 指着它；② 有人持有 /proc/PID/ns/X 的打开的 fd；③ 它被 bind mount 到了别处（ip netns add 就是这么让一个空 ns 活着的）。
  • 所以「netns 泄漏」必是这三条之一没断，排查按三条来：findmnt -t nsfs 找对不上活容器的死条目（最常见，umount 即释放）；ls -l /proc/*/fd | grep 'net:\[' 找谁忘了 close；lsns -t net 看有没有进程留在里面。
  • NPROCS=0 却还存在的 net namespace 就是泄漏（见过一台机器攒到近两千个，根因是 CNI 插件退出路径没清干净），后果是 ip netns 操作与 Pod 删除越来越慢——net ns 的销毁由单个工作队列串行处理，还要等 RCU 宽限期。

PID namespace 的三条特殊规则，以及可复现的验证

PID 1 的怪脾气不是 Docker 的实现细节，而是内核对 PID namespace 里 init 进程的明文规定——规则说清了，「容器里 kill 不掉进程」和「docker stop 要等 10 秒」就是同一件事的两面。

规则内核行为在容器上表现为
同 ns 内发给 PID 1 的信号只有 PID 1 自己安装了处理函数的信号才会被送达，其余一律丢弃——包括特权进程发的，也包括 SIGKILL容器内 kill -9 1 毫无反应；「容器里 kill 不掉主进程」
祖先 ns 发给 PID 1 的信号同样要求有处理函数，唯独 SIGKILL / SIGSTOP 例外——这两个从祖先 ns 发出时强制送达且不可捕获docker stop 的 SIGTERM 被静默丢弃 → 干等 10 秒 → SIGKILL 生效。「优雅退出逻辑从来没跑过」
PID 1 退出该 namespace 里所有其余进程被内核 SIGKILL，namespace 随之销毁主进程一退，容器整个没了，别的进程来不及善后
孤儿进程重新归属父进程先死的孤儿，被过继给本 namespace 的 PID 1（不是宿主 init）PID 1 不 wait() 就攒僵尸，攒满 pids.max 后 fork 全部失败
PID 是嵌套的同一个任务在每一层 namespace 里各有一个编号，父 ns 永远能看到子 ns 的全部进程宿主上能 kill 容器里任何进程；/proc/PID/status 的 NSpid 行把各层编号列出来
僵尸的具体危害是吃 pids.max 的额度：撞上限之后 fork 返回 EAGAIN，容器里执行任何命令都报 Resource temporarily unavailable，而 CPU 与内存指标全都正常。证据在 pids.current 与 pids.events 的 max 计数。
❌ 信号收不到

ENTRYPOINT 脚本末行写 ./myapp：shell 一直是 PID 1，SIGTERM 发给了 shell，myapp 什么都收不到。

✅ exec 让出 PID 1

末行改成 exec ./myapp：myapp 替换掉 shell、自己成为 PID 1，能收到 SIGTERM（前提是注册了 handler）。

判断「要不要 --init」只需两问：① PID 1 会不会 fork 出可能变孤儿的子进程？② 它有没有正确处理 SIGTERM？两个都是「是」才可以不要——实践中只有 nginx、PostgreSQL 这类天生的进程管理者真做到了。

Mount namespace 与挂载传播：容器最容易漏出去的一环

新建 mount namespace 时内核复制一份当前挂载树，但两棵树不是彻底断开——每个挂载点带一个传播类型，决定挂载 / 卸载事件怎么在两棵树之间流动。这是容器隔离里最容易配错、也最容易让宿主受害的一处。

传播类型mount 选项事件流向典型用途
shared--make-shared / --make-rshared双向：同一 peer group 内互相传播挂载与卸载宿主 / 的默认（systemd 设成 rshared）；CSI 插件要把卷「推」给别的容器时用
private--make-private / --make-rprivate不传播，两边完全独立最强隔离；代价是宿主后来新挂的东西容器里永远看不见
slave--make-slave / --make-rslave单向：从 master（宿主）收，但自己的挂载不回传★ 容器运行时的常用选择，理由见下
unbindable--make-unbindableprivate，且禁止被 bind mount防止「递归 bind 包含自身的子树」导致挂载点指数爆炸，多用于运行时内部的中间挂载点

为什么 rslave 是容器运行时的常用选择

  • 要「从宿主收」：宿主后来挂进来的东西（新 attach 的云盘、CSI 刚 publish 的卷）必须能出现在容器里，private 做不到。
  • 不能「往宿主漏」：容器内部会挂一大堆 /proc、tmpfs、secret 卷，shared 下全部传播到宿主挂载树上，而挂载操作的开销与挂载点总数相关。更严重的是卸载会反向生效：容器里 umount /data 会把宿主那个 bind 源也卸掉。
  • K8s 的 Bidirectional（rshared）要求容器特权，只该给 CSI 这类必须往宿主推挂载的组件。

事故 · 宿主 df 输出上万行，节点上所有 mount 操作变慢

现象：一台跑了几十个 Pod 的节点，df 要好几秒才返回、输出上万行；kubelet 日志里大量 mount 超时，新 Pod 卡在 ContainerCreating。

根因：为了让一个特权存储组件能把卷推给别的容器，运维给一批不相干的容器都加了 mountPropagation: Bidirectional。于是它们内部每一次挂载都传播回宿主挂载树，而容器反复重启、传播过来的那份没人负责卸载。现场数据：/proc/mounts 一万一千多行、4310 条 overlay 是 shared，活容器只有 38 个。

处方：Bidirectional 只留给 CSI node 插件，其余一律 None 或 HostToContainer；按路径批量 umount -l 清残留；把 wc -l /proc/mounts 当节点级指标，超过几百条就告警。

User namespace 与 ID 映射：容器内是 root，宿主上是普通用户

User namespace 隔离的是 UID/GID 的解释方式，翻译表就是 /proc/PID/uid_map 与 gid_map。它还兼任其它 namespace 的「所有者」——能不能对一个 net ns 做特权操作，看的是你在它的所有者 user ns 里有没有 CAP_NET_ADMIN。

映射算术：uid_map 每行三个数（inside、outside、length），换算公式 宿主 uid = outside + (容器内 uid − inside)。没有落进任何一行的 uid 是「不可映射」的：内核把这类文件的属主显示成 overflowuid（通常 65534 / nobody），你在容器内对它没有任何权限——哪怕你是容器内的 root。
# 这两行就是 rootless 容器的全部秘密
$ cat /proc/<pid>/uid_map
         0       1000          1     # 容器内 root ← 宿主 uid 1000，长度 1
         1     100000      65536     # 容器内 1..65536 ← 宿主 100000..165535

# 非特权用户想写多行 → 必须借 setuid 帮助程序（它按 /etc/subuid 授权）
$ newuidmap $PID 0 1000 1 1 100000 65536
# 写 gid_map 之前还有一道前置条件，顺序反了直接 EPERM：
$ echo deny > /proc/$PID/setgroups && newgidmap $PID 0 1000 1 1 100000 65536

uid_map 的写入规则（踩过就会记住）

  • 只能写一次，写成功后文件变只读、再写返回 EPERM。映射必须一次性写全，不能增量追加。
  • 写多行区间要求写入者在父 user ns 里持有 CAP_SETUID。非特权用户只有一个例外：写单独一行把自己的 eUID 映射进去（unshare -r 干的就是这件事）——这也是 newuidmap / newgidmap 这两个 setuid 帮助程序存在的理由。
  • 非特权场景写 gid_map 前必须先往 setgroups 写 deny（堵住一类「丢掉附加组反而获得权限」的历史提权漏洞），写了之后该 ns 里就永久不能调 setgroups()。
rootless 容器的代价原因常见对策
不能绑定 1024 以下的端口在宿主的初始 net namespace 里没有 CAP_NET_BIND_SERVICE调 net.ipv4.ip_unprivileged_port_start，或在宿主侧做端口转发
网络吞吐明显低于 root 模式没有 CAP_NET_ADMIN，无法把 veth 一头插进宿主网桥，只能用用户态 TCP/IP 栈（slirp4netns / pasta）中转能接受时改用宿主网络；或用带内核加速路径的较新实现
早期内核上挂不了 overlayfs在 user namespace 内挂 overlay 需要内核支持（较新的内核，约 5.11 起才允许）退回用户态的 fuse-overlayfs，元数据操作更慢；或升级内核
cgroup 限额可能失效普通用户对 cgroup 树没有写权限靠 systemd 的 Delegate= 把一棵子树授权给用户会话（见 systemd 与 cgroup）
chown / 包管理器可能失败目标 uid 没落进映射区间确保 /etc/subuid 给了足够大的连续段（通常 65536）

剩下四种：小，但各有一个非直觉之处

cgroup namespace 只改「根在哪」：没开它时 cat /proc/self/cgroup 会吐出自己在宿主 cgroup 树上的完整路径（信息泄露，且让「读自己的路径找限额文件」在容器内外行为不一致）；开了之后只看到 0::/。它只改视图不改限额。time namespace 只偏移单调时钟与 boottime，主要给 CRIU 用（进程恢复后单调时钟不能倒退），别指望用它给容器「改时间」。

uts namespace 只有主机名与域名两个字段。ipc namespace 隔离了 System V IPC，但 POSIX 共享内存走 /dev/shm 这个 tmpfs、不受它管：跨容器共享必须挂同一个 tmpfs，而单容器的 /dev/shm 默认只有 64 MB——「PyTorch 报 Bus error」几乎都是这 64 MB 的锅。

Cgroup v2：资源限制与统计

namespace 管隔离，cgroup 管配额

Namespace 让容器「看不见别人」，但不限制它「用多少」——一个容器仍能吃满宿主 CPU 与内存。Cgroup负责限制、统计、隔离一组进程的资源用量。

cgroup v2 的统一层级（unified hierarchy）：所有控制器挂在同一棵树上，进程只属于一个节点；v1 则是每个控制器各一棵独立目录树，同一进程可以分属不同组。

手工造一个「有限额的进程组」

不用 Docker，几条 echo 就能拿到 cgroup 的全部限制能力——这一段能彻底祛魅：

# v2 的判据：根下有 cgroup.controllers
$ cat /sys/fs/cgroup/cgroup.controllers
cpuset cpu io memory hugetlb pids rdma misc

# ① 父组先「下放」控制器，子组目录里才会冒出 cpu.max / memory.max 这些文件
$ echo "+cpu +memory +pids" | sudo tee /sys/fs/cgroup/cgroup.subtree_control

# ② 建组就是 mkdir，控制文件由内核自动生成
$ sudo mkdir /sys/fs/cgroup/demo

# ③ 设限额：每 100ms 最多用 20ms CPU（=0.2 核）/ 内存 100M / 最多 50 个进程
$ echo "20000 100000" | sudo tee /sys/fs/cgroup/demo/cpu.max
$ echo "100M"         | sudo tee /sys/fs/cgroup/demo/memory.max
$ echo "50"           | sudo tee /sys/fs/cgroup/demo/pids.max

# ④ 把当前 shell 丢进去（写 PID 到 cgroup.procs，子进程自动继承）
$ echo $$ | sudo tee /sys/fs/cgroup/demo/cgroup.procs

# ⑤ 观察生效：这个死循环只能吃到 20% 的一个核
$ while :; do :; done &
$ top -p $!                  # %CPU 稳定在 20 左右，而不是 100

# ⑥ 顺手撞一下「无内部进程」约束
$ echo "+cpu" | sudo tee /sys/fs/cgroup/demo/cgroup.subtree_control
tee: .../cgroup.subtree_control: Device or resource busy   # ★ EBUSY
#   demo 里已经有进程了，不能再变成「分配节点」。
#   正解：建 demo/leaf 装进程，demo 只做分配 —— 这就是 slice/service 的形状。

# ⑦ 删除用 rmdir（不是 rm -rf），且必须先空掉
$ sudo rmdir /sys/fs/cgroup/demo

cgroup.controllers 和 cgroup.subtree_control 的区别（最常被搞混的一对）

  • cgroup.controllers 只读，回答「本组自己能用哪些控制器」，内容由父组的 subtree_control 决定；cgroup.subtree_control 可写，回答「我要把哪些控制器下放给子组」。
  • 所以「mkdir 了一个组但里面没有 cpu.max」的原因永远是父组没把 cpu 写进自己的 subtree_control。这条链要从根一路开到你那一层，漏一级就断。
  • 另两个值得盯的观察文件：cgroup.events 的 populated（可 inotify 它等子树进程归零）、cgroup.stat 的 nr_dying_descendants（见下）。
nr_dying_descendants 值得单独盯一眼：一个 cgroup 被 rmdir 后若名下还有未回收的 page cache，内核不会立刻释放它，而是让它进入「dying」状态等回收。频繁起停容器的节点上这个数字能攒到几万，表现为内核内存只增不减、遍历 cgroup 树的操作（systemctl status、cAdvisor 采集）越来越慢。缓解手段是给容器设 memory.max 让 page cache 有上界。

CPU 的两种限法：cpu.weight 和 cpu.max 完全不是一回事

这两个文件常被混为一谈，但语义、失效方式、对延迟的影响截然不同。选错的代价通常表现为「限了之后延迟毛刺变多，吞吐并没提上去」。

格式上 cpu.max 是「QUOTA PERIOD」两个微秒值，"max 100000" 表示不限。「2 核配额」不等于「绑 2 个核」：20 个线程可以在 100 个核上各跑 2 ms，一样把配额用光。真要绑核用 cpuset.cpus。

节流尖刺：「CPU 用量没到上限，延迟却很高」的成因

这是容器时代最常见也最反直觉的困惑：面板上利用率 40%、离 limit 还差一大截，但 P99 是 P50 的十几倍。原因是利用率和配额根本不在同一个时间尺度上。

生活类比：每小时限量的自助饮水机

cpu.max 不是「水龙头开小一点」，而是「每小时给你 12 分钟的用水额度，用完就断到下个整点」。你可能前 12 分钟就把水用完（一次接满 20 个杯子），剩下 48 分钟一滴都没有——按小时统计「用水率」只有 20%，但第 15 分钟来接水的人要干等 45 分钟。

记住这条不等式：「利用率低」不等于「没被限流」。线程数越多、请求越突发，两者差距越大——并行度高的应用反而更容易在低利用率下被节流，因为它能在周期头几毫秒里就把额度花光。唯一可信的证据是 cpu.stat 的 nr_throttled。

判读 cpu.stat 与 memory.events：容器排障的两个核心文件

cpu.stat 给三个关键数：nr_periods（经历了多少配额周期）、nr_throttled（多少个被限流）、throttled_usec（累计冻结时长）；memory.events 给 low / high（触发软限被加压回收）/ max（撞硬上限）/ oom_kill（真的杀了几个进程）四行。

这两个文件里的数字全部是自 cgroup 创建以来的累计值，看绝对值毫无意义，必须采两次取差再算比例。经验阈值：nr_throttled/nr_periods 小于 1% 基本无影响，1%–5% 延迟敏感服务已能看出毛刺，超过 10% 一定要处理。throttled_usec 的增量可以超过墙上时间，它是各 CPU 上冻结时长之和。另外定内存 limit 要看 memory.peak 而不是 memory.current。
处方怎么做代价 / 适用条件
把线程数降到配额量级工作线程数 ≈ 配额核数（而不是宿主核数），见第 8 章事故 3几乎总是对的第一步，没有副作用；很多情况下只做这一步限流就消失了
放宽或去掉 limit只留 requests（cpu.weight），靠权重做优先级失去硬隔离：邻居忙时你变慢，容量规划变难；多租户环境不适用
调小 period配额等比缩小，如 "20000 10000" 仍是 2 核，周期从 100 ms 降到 10 ms最坏停顿从 90 ms 压到 9 ms；代价是记账开销上升、更容易在短突发上撞线。周期有取值范围限制
启用 burst较新内核的 cpu.max.burst，把周期内没用完的配额攒起来供突发使用治「平均不高但有突发」，对「持续超配额」无效；削弱硬隔离的确定性
换成绑核cpuset.cpus 做硬亲和，配合 K8s 的 static CPU manager policy彻底没有 throttle，缓存亲和更好；代价是失去弹性、碎片化、只对整数核有效
升级内核较早的内核里 CFS 带宽控制有「本地配额切片过期后被白白扣掉」的缺陷，多核多线程下造成远超预期的限流，5.4 前后修掉先确认手上内核版本与发行版回合情况；「利用率极低却限流极重」时这是重点怀疑对象

PSI：比利用率更能反映「有没有被卡住」

  • v2 提供 cpu.pressure / memory.pressure / io.pressure。读法：some avg10=42.18 是「最近 10 秒里有 42% 的时间至少有一个任务在等 CPU」；full=（memory / io 才有）是所有任务都被卡住的比例，更严重。
  • 利用率 100% 未必是问题（就是跑满了），而 some avg10 高才真正说明有人在等。
最常见的容器性能坑：应用感知不到 cgroup 限额——/proc 不是 namespace 化的，老程序读 nproc 拿到宿主全部核数，于是在 2 核配额里开 64 个工作线程，自己给自己制造上下文切换与限流。完整案例见第 8 章事故 3。

CPU 权重与配额如何影响调度、throttling 的完整案例见 进程调度；内存 cgroup 的回收路径、memory.min/low 的保护语义与 OOM killer 的打分逻辑见 NUMA 与高级内存。

在现代发行版上，这棵 cgroup 树的所有者是 systemd，不是容器运行时：运行时要在自己下面建 cgroup 必须靠 Delegate=yes 拿到授权。「普通服务怎么限资源」「为什么 systemctl stop 能干净地杀掉全部子进程」，答案都在 Linux 启动流程与 systemd——同一套机制，入口换成 unit 文件里的 CPUQuota= / MemoryMax=。

OverlayFS：镜像分层

为什么 docker pull 能秒级、镜像能共享

容器镜像是只读层的叠加。OverlayFS 把多个目录「合并」成一个视图：底下是若干只读镜像层（lowerdir），最上面是可写层（upperdir），容器看到的是合并后的统一文件系统。

「可写层随容器销毁」是「容器无状态」的物理原因，不是一种设计倡议。而「删文件」在这里也不省空间：只读层的原件动不了（别人还在共享），upper 层还多一个 whiteout 标记占一个 inode。

workdir 那两条约束不是实现细节，而是原子性的要求：copy-up 与创建 whiteout 必须「要么完全没做，要么完整做好」，唯一能保证原子的办法是 rename()，而它不能跨文件系统——所以 workdir 必须和 upperdir 同盘；而它不能是 upperdir 的子目录，因为 workdir 里的临时文件会出现在 merged 视图里。搞错时 mount 返回 EINVAL，dmesg 里会留一行明确原因。

写时复制的粒度：整个文件

这句话平淡，却是容器存储上最大的一颗雷：copy-up 不是按块、不是按页，而是把整个文件从 lower 完整复制到 upper，哪怕只改一个字节。可以当场量出来：对一个 1 GB 的 lower 层文件用 dd 改第一个字节，耗时约 2.3 秒、upper 目录从 0 涨到 1.0 G；第二次改同一文件只要 3 毫秒。更反直觉的是只改元数据也同样触发整文件复制——除非开了 metacopy=on。

推论一条比一条严重：① 数据库文件放可写层，第一次写入就是「整库复制」级别的停顿；② 日志的第一次追加写同样触发全量 copy-up；③ 最隐蔽的是 CI 场景：镜像里预置了 node_modules 或 .git，改动它们会逐个 copy-up 成千上万个小文件，写入量是改动量的几十倍。规则很简单：所有会被写的路径一律挂 volume 绕开 overlay。这不只是防丢数据，更是性能问题。

opaque 挡住 lower 的同名目录是为了符合 POSIX 语义——「删了目录再重建，里面就该是空的」。rootless 容器用不了 trusted.*（写它需要 CAP_SYS_ADMIN），较新内核提供 userxattr 改用 user.overlay.* 存这些标记。

inode：两个让人困惑的现象

现象一：同一个文件在容器内和宿主上 inode 号不同。overlay 是「合成」文件系统，文件其实住在 lower 或 upper 的真实文件系统上。早期实现直接把底层 inode 号透出来，让 tar、rsync、find -samefile 这类依赖 (st_dev, st_ino) 判重的工具误判；后来引入 xino 把层号编码进 inode 号高位。这是合成层的必然结果。

现象二（更会咬人）：copy-up 之后，之前打开的 fd 看不到新内容。copy-up 在 upper 层创建了一个新 inode，而之前打开的只读 fd 仍指向 lower 层的旧 inode，会一直读到旧内容直到关闭重开；inotify 监视的也是旧 inode。这是 overlayfs 明确列出的非 POSIX 行为，表现就是「运维改了配置，进程重读却拿到旧值」。

还有一个必查项：inode 耗尽。df -h 说空间还剩很多、df -i 却已 100%，此时 touch 报的是 ENOSPC，极易误判成「磁盘满」——两个命令必须都看。典型元凶是 node_modules（十万个小文件，每层各存一份）。通用排查见 文件系统与存储栈 §7。

层数：为什么「合并 RUN 指令」真的有用

overlay 的路径查找是自上而下逐层试的，而「文件不存在」最贵——必须把每一层都查完才能确定，Python 的 import、Node 的模块解析恰恰产生大量「查不到」的探测。量过一组数：同一份代码，37 层镜像里 python -c "import pandas" 冷启动 3.42 s，压到 6 层后 1.18 s；strace -c 显示这次导入做了 48210 次 newfstatat，其中 41337 次失败，每次都把 37 层全查了一遍。这才是「合并 RUN 指令」的真实收益，省磁盘只是顺带。

容器如何启动（OCI / runc）

从 docker run 到进程诞生

Docker / K8s 只是上层。真正「造容器」的是符合 OCI 规范的低层运行时（如 runc）：它读一份 config.json，把前面三件事（namespace / cgroup / rootfs）依次做掉，然后自己退出。

启动六步

  • ① 准备根文件系统：OverlayFS 挂镜像各层 + 可写层，得到容器 rootfs。
  • ② 创建 namespace：clone() 带各 CLONE_NEW*，子进程诞生在隔离视图里。
  • ③ 加入 cgroup：把新进程写进配好限额的 cgroup.procs。
  • ④ 切换根：pivot_root 切到容器 rootfs，然后卸载旧根。
  • ⑤ 收敛权限：drop caps、装 seccomp 过滤器、打 LSM 标签、设 no_new_privs，必须在 exec 之前全部做完。
  • ⑥ exec 用户进程：execve 运行 ENTRYPOINT，容器「活」了。

为什么用 pivot_root 而不是 chroot：chroot 只改根目录指针，旧的根文件系统仍然挂载着、仍然可达；pivot_root 把旧根整个从挂载树上摘下来并卸载。用挂载点条数当场验证：容器里 wc -l /proc/mounts 只有二十来条，chroot 出来的环境里宿主那一百多条一条不少。

chroot 为什么能被逃出去：把原理拆开看

chroot(path) 只做一件事：把 task_struct→fs→root 换成 path 的 dentry。它不改 pwd，也不动挂载树，于是留下几个洞：

三条经典逃逸路径（都不需要漏洞）

  • ① pwd 落在新根之外。内核解析 .. 的规则是「到了本进程的 root 就停」，但若 chroot 之后没紧跟 chdir("/")，pwd 已在 root 之外，这个条件永远不成立，chdir("..") 一路走到真正的根。
  • ② 造一个「更深的根」。即使规范地 chdir("/") 了，只要还持有 CAP_SYS_CHROOT：mkdir("x") → chroot("x")（pwd 留在父目录，正好落在新 root 之外）→ 回到 ①。十几行 C 代码，用的全是正常语义。
  • ③ 一个 chroot 之前打开的目录 fd。fchdir(fd) 直接把 pwd 设到外面，同样回到 ①。
  • 所以 chroot 从来不是安全边界，手册页自己就这么写着。

runc 的做法是：mount("", "/", MS_SLAVE|MS_REC) 断开向宿主的传播 → 把 rootfs bind 成挂载点 → chdir(rootfs) → pivot_root(".", ".")（两个参数传同一个 "."，旧根叠在新根同一位置，省掉在镜像里预留 /old_root）→ umount2(".", MNT_DETACH) 把叠着的旧根整棵摘掉。

runc 为什么要分三个阶段：Go 语言撞上内核限制

两个绕不过去的坑

  • 多线程进程不能 unshare/setns user namespace。而 Go runtime 一启动就创建多个 OS 线程且无法变回单线程，所以这段逻辑必须在 Go runtime 初始化之前跑完——只有 C 的 constructor（nsexec.c）能拿到这个窗口。
  • uid_map 必须由 namespace 外面的进程写。写多行映射要在父 user ns 里持有 CAP_SETUID，而新建 user ns 的进程自己在里面反而没有，只能两个进程配合。
  • 第三个理由更简单：unshare(CLONE_NEWPID) 不把调用者放进新 PID ns，必须再 fork 一次才有 PID 1。
create 与 start 分离不是多余的抽象。容器进程必须先存在（才有 PID、才有 net namespace 可以插 veth、才能写进 cgroup），但业务代码不能在网络和限额就绪前跑起来。「先造好、卡在最后一步、由外部按下发令枪」正好解决这个矛盾。created 状态下 cat /proc/<pid>/cmdline 看到的还是 /proc/self/exe init。

容器网络

独立网络栈怎么连出去

每个容器有独立的 network namespace（自己的网卡、IP、路由表、iptables 规则）。它怎么和宿主 / 外网通信？答案全部由几个虚拟设备拼出来，没有任何魔法。

模式做法性能适用
bridge（默认）宿主建虚拟网桥 docker0，每容器一对 veth 插上去，出外网靠 NAT有 NAT 与网桥转发开销通用；单机多容器互通
host不建 net namespace，直接用宿主网络栈零开销高性能网络服务；代价是端口冲突与零隔离
none只有 loopback—完全不需要网络，或自己用 CNI 配
container:<id>共用另一个容器的 net namespace同 hostK8s Pod 内多容器共享网络就是这个（靠 pause 容器持有 ns）
macvlan / ipvlan直接从物理网卡派生子接口，容器有独立 MAC/IP接近裸机需要容器在二层网络里像独立主机一样存在

手工搭一个 bridge 网络：Docker 到底做了什么

docker0 没有任何神秘之处，几条 ip 命令就能复现：ip netns add c1 造一个「容器」；ip link add veth-host type veth peer name eth0 造一对虚拟网线，ip link set eth0 netns c1 把一头塞进去；宿主侧建网桥并把另一头 master br-demo 插上；容器侧配 IP、把网桥设成默认网关；最后开 ip_forward 加一条 iptables -t nat -A POSTROUTING -s 172.30.0.0/24 ! -o br-demo -j MASQUERADE——这条 SNAT 规则就是能出外网的全部原因。

veth 与 bridge 的开销来自哪里

  • veth 不是网卡的模拟，而是一根「内存里的短路线」：一端的发送函数直接把 skb 交给另一端的接收路径，不经过硬件队列、没有 DMA（所以默认 qdisc noqueue）。开销主要是多走一遍协议栈，而不是数据拷贝。
  • bridge 模式的开销是叠加的：图上每一跳都不贵，但加起来足以在小包高 PPS 场景下成为瓶颈。
  • 内核侧 veth / bridge / netfilter 的实现细节、以及 XDP 与 eBPF 怎么压短这条路径，见 内核网络栈 §5 与 §3 netfilter 与 conntrack。

NAT 的两个真实上限：conntrack 表与端口

第一道硬墙是 conntrack 表（nf_conntrack_max 是容量、nf_conntrack_count 是用量）。表满时包被直接丢弃，dmesg 里有明确一行 nf_conntrack: table full——但业务侧看到的是「随机超时」，而 CPU、内存、带宽全都正常，日志里像是对端的问题。按状态分类通常会发现大头是 TIME_WAIT（表项要挂 120 秒）。

第二道墙是 SNAT 可用的源端口：ip_local_port_range 默认约 2.8 万个。严格说这是「每个 (目的 IP, 目的端口) 组合」下的可用量，但所有容器都连同一个下游 VIP 时，它就是实打实的全局上限。

症状根因处方
随机超时，dmesg 有 table fullconntrack 表满调大 nf_conntrack_max（每条目约几百字节）+ 缩短 TIME_WAIT 超时 + 改用长连接
连同一个下游时出现 EADDRNOTAVAILSNAT 源端口耗尽放宽 ip_local_port_range；给下游加多个 VIP；或让该服务走 host 网络绕开 SNAT
小包正常、大包卡住或超时MTU 不匹配：overlay 封装要留头部空间，容器网卡 MTU 必须相应减小；中间设备丢掉 ICMP 后路径 MTU 发现失效，大包被静默黑洞显式让容器 MTU 与网桥一致；用 ping -M do -s <size> 二分找出真实可用 MTU
UDP（尤其 DNS）偶发丢包后重试才成功多线程对同一五元组做 SNAT/DNAT 时 conntrack 表项插入存在竞争窗口，冲突的那个包被丢弃用连接池 / 本地 DNS 缓存减少并发新建；给 MASQUERADE 加 --random-fully；或调 ndots 减少查询
规则数量大后转发延迟明显上升iptables 规则链线性匹配，Service 多时每个包要过很长的链切到 nftables 实现，或用 eBPF 数据面（Cilium）绕开 iptables

--net=host 的取舍

维度bridge（默认）--net=host

端口容器内可以随便用 80、和别的容器重名与宿主及其它 host 容器共享端口空间，会冲突；配置里不能写死端口

--net=host 最容易被低估的是安全影响而不是端口冲突。很多服务把「只监听 127.0.0.1 就是安全的」当前提（Redis、Etcd、各种 admin 端口、云元数据服务都这样），而一个 host 网络的容器眼里的 127.0.0.1 就是宿主的。所以开 host 网络前先问一句「这台机器的 loopback 上有什么」。见 Linux 安全模型 §6。

端口映射（-p 8080:80）到底是什么

  • 本质是一条 DNAT 规则：进宿主 8080 的包，目的地址被改写成容器 IP 的 80，然后正常路由过去。iptables -t nat -L DOCKER -n 里那条 DNAT tcp dpt:8080 to:172.17.0.2:80 就是它。
  • Docker 还会起一个 docker-proxy 占住宿主端口，处理 DNAT 覆盖不到的情况（如从宿主自己 127.0.0.1:8080 访问）。它是「端口明明没人用却说被占用」的常见元凶。
  • 大流量下 NAT 会消耗 conntrack 表项，表满直接丢包；跑高连接数服务时考虑 host 网络或 macvlan。

K8s 里跨节点 Pod 通信由 CNI 插件（Calico / Cilium / Flannel）实现，Cilium 用 eBPF 替掉 iptables、规则多时优势明显。内核侧的收发包路径见 内核网络栈与流量治理；用户态 socket 编程见 网络编程。

容器安全

共享内核 = 隔离没有 VM 强

容器的隔离是内核提供的，所以隔离强度的上限就是内核的正确性。这句话有两层含义：内核有漏洞时容器逃逸是现实威胁；而更常见的是——大多数逃逸根本不需要漏洞，只需要一个错误的配置。

纵深防御的五层

  • Capabilities：把 root 拆成细粒度能力，容器默认只留一小部分。绝不要 --privileged，也别随手加 CAP_SYS_ADMIN——那一项基本等于 root。
  • Seccomp：系统调用白名单，把攻击面从 300+ 个 syscall 缩到几十个。K8s 里要显式设 seccompProfile: RuntimeDefault 才启用。
  • User namespace（rootless）：容器内 root 映射成宿主普通用户，即使逃逸也不是宿主 root。
  • 只读根 + no_new_privs：根只读、禁止 setuid 提权，可写目录单独挂 tmpfs。
  • 强隔离场景：多租户 / 跑不可信代码用 gVisor 或 Kata / Firecracker，用一点性能换 VM 级隔离。

三条自查一分钟能做完：{{.HostConfig.Privileged}} 必须是 false；.HostConfig.Binds 里有没有挂 docker.sock、/、/proc；容器内用 capsh --decode=$(grep CapEff /proc/self/status | cut -f2) 展开实际能力，出现 cap_sys_admin / cap_sys_module / cap_sys_ptrace 就要警惕。顺带确认 grep Seccomp /proc/self/status 是 2 而不是 0。

隔离边界的真实形状：哪些东西根本没有被 namespace 化

讨论容器安全时最有用的清单不是「有哪些逃逸手法」，而是「内核里有哪些资源压根没有 namespace 化」——这些是隔离边界上天然的缺口，不需要漏洞就能观察到。

资源被隔离了吗容器里看到 / 影响到什么后果与应对
内核版本与编译配置否uname -r 永远是宿主内核；/proc/config.gz 也是宿主的「镜像里装了另一个发行版」不等于换了内核。依赖特定内核特性的程序必须检查宿主内核
CPU / 内存的硬件信息否/proc/cpuinfo、/proc/meminfo、/proc/loadavg 全是宿主的第 8 章事故 3 的根源。要么让应用读 cgroup，要么挂 lxcfs 伪装
绝大多数 sysctl否vm.*、fs.file-max、kernel.pid_max 等都是全局的容器里改要么被拒，要么影响整机。只有 net.*、kernel.hostname、System V IPC 与 fs.mqueue.* 这几类是命名空间化的，运行时也只允许改这几类
墙上时钟否time namespace 只偏移单调时钟；改 CLOCK_REALTIME 影响整机需要「改时间」的测试用用户态方案，不要给 CAP_SYS_TIME
内核模块否insmod 加载的模块对全机生效CAP_SYS_MODULE 等价于宿主 root，绝不能给
内核日志环否dmesg 能读到宿主全部内核消息（含别的容器的 OOM）设 kernel.dmesg_restrict=1，并 drop CAP_SYSLOG
页缓存否（只记账到 cgroup）一个容器大量读文件会挤掉别人的缓存；卷共享时能通过缓存命中时间推断别人读过什么用 memory.max 给 page cache 上界；高敏场景用独立卷
CPU 的微架构状态否共享缓存、TLB、分支预测器、SMT 兄弟核侧信道攻击的物理基础。多租户要么禁 SMT + 独占核，要么上轻量 VM
PID 空间是（但嵌套）宿主永远能看到并操作容器内进程，反之不行设计如此，不是缺陷；也是 nsenter 排障能成立的前提
cgroup 限额本身只隔离视图开了 cgroup ns 也只是看不见宿主路径，限额一模一样不要把 cgroup ns 当安全机制
这张表就是「容器隔离弱于 VM」的具体内容：不是「namespace 不够严密」，而是「namespace 只覆盖了内核资源的一部分」。剩下这些是共享的，共享就意味着可观测、可干扰、可作为攻击面。所以判断一个负载能不能进普通容器，问题应该是「它会不会碰到这张表里的东西」，而不是「我有没有把 capability drop 干净」。
本篇到此为止。安全维度再往下属于另一篇的范围，这里不重复：capabilities 五个集合的语义与提权计算 → Linux 安全模型 §3；seccomp-bpf 过滤器怎么写、怎么排查被拦的调用 → §4；SELinux / AppArmor 的标签模型与 audit2allow 排障 → §5；namespace 作为安全边界的形式化分析 → §6；逃逸链完整拆解（docker.sock、core_pattern、release_agent）→ §7；加固基线 → §8。

三个生产事故 + checklist

从现象到根因

事故 1 · 退出码 137，但容器内存监控只有 60%

现象：Java 服务容器每隔几小时被杀一次，docker inspect 显示 ExitCode: 137、OOMKilled: true，但 Prometheus 上的 JVM 堆内存曲线一直平稳在 60%。

关键认知：cgroup 统计的是整个容器的内存，不只是 JVM 堆——memory.max 管的是 RSS + page cache + 内核栈 + 直接内存 + metaspace + 线程栈的总和。这个服务用了大量 NIO 直接内存，堆外增长完全没被堆监控覆盖。

# 退出码 137 = 128 + 9，即被 SIGKILL —— 但谁杀的？先看内核怎么说
$ dmesg -T | grep -i 'killed process'
[Wed Sep  3 04:12:08] Memory cgroup out of memory: Killed process 84213 (java)
  total-vm:9821044kB, anon-rss:2048112kB, file-rss:18224kB
#   ★ "Memory cgroup out of memory" = 容器自己超了 memory.max
#     若是 "Out of memory: Killed process"（不带 cgroup 字样）= 整机内存不足，
#     那是宿主超卖，和这个容器的 limit 无关 —— 两者处方完全不同。

# 分解容器内存的真实构成 —— 不要只信应用自己的监控
$ cat /sys/fs/cgroup/<path>/memory.stat | head -6
anon 2097152000          # 匿名页：堆 + 直接内存 + 线程栈 ← 大头在这
file 184320000            # page cache（读写文件带来的，可回收）
kernel_stack 8388608
slab 41943040
sock 2097152

$ cat /sys/fs/cgroup/<path>/memory.events
high 2841                # 触发 memory.high 软限、被加压回收的次数（提前告警信号）
max 193                 # 撞到 memory.max 硬上限的次数
oom_kill 7              # ★ 已经被杀 7 次了
memory.stat 字段是什么能不能回收它变大通常意味着
anon匿名页：堆、线程栈、malloc 拿到的内存、JVM 的直接内存不能（只能换出到 swap，容器里通常禁 swap）真的在用或者漏了。这是 OOM 的主要贡献者
filepage cache：读写文件带进来的能（干净页直接丢，脏页先回写）大量顺序 I/O。它计入 memory.current，所以「内存快满了」经常只是缓存多
shmemtmpfs / POSIX 共享内存（/dev/shm）不能——它长得像 file，行为像 anon最容易误判的一项：往 /dev/shm 或 emptyDir: memory 写文件会直接吃内存额度
slab / slab_reclaimable内核对象：dentry、inode 缓存等部分能大量小文件操作（npm install）；容器里也算在自己头上
kernel_stack每个线程 8–16 KB 的内核栈不能线程数失控。上千线程时这一项能到几十 MB
socksocket 缓冲区不能连接数暴涨或对端不读导致发送队列堆积
percpuper-CPU 分配的内核结构不能核数多 + cgroup 多时不可忽略

判读顺序：先看 anon + shmem + kernel_stack 之和——这是「杀了也回收不出来」的部分，接近 memory.max 就一定会 OOM；file 高不用慌。本例中 anon 占 2 GB 而堆监控只覆盖其中一部分，差值就是直接内存。

处方：① -XX:MaxDirectMemorySize 显式限制直接内存，让 JVM 自己先报错而不是被内核 kill；② -XX:MaxRAMPercentage 让堆按容器 limit 定；③ memory.high 设在 max 的 85% 左右，换一段「先变慢、后被杀」的缓冲带；④ 监控口径改成「anon + shmem 对 memory.max 的占比」。见 NUMA 与高级内存 §7。

事故 2 · 宿主磁盘被吃满，但每个容器看着都很小

现象：节点 /var/lib/docker 所在分区 100%，新 Pod 全部 ImagePullBackOff。逐个进容器 du -sh /，加起来远小于实际占用。

三个来源都在容器外面：① 已停止容器的可写层没清；② 悬空镜像；③ 日志文件——stdout/stderr 由 json-file 驱动写在宿主上，默认不限大小、不轮转，一个话痨服务几天就能写出几十 GB。

怎么定位：docker system df -v 看三类的 RECLAIMABLE 占比（现场是镜像 82 GB 里 74% 可回收、卷 31 GB 里 91%）；日志单独查 du -sh /var/lib/docker/containers/*/*-json.log，本例最大一个 14 GB。别忘了 df -i。

处方：daemon 级配置日志轮转（log-opts 的 max-size / max-file）；定期 docker system prune；给 /var/lib/docker 独立分区，别让它撑爆根分区把整个节点带下去。见 文件系统与存储栈。

事故 3 · 容器里 nproc 说 96 核，实际只有 2 核配额

现象：把服务从物理机搬进容器后 QPS 反而降了 40%，CPU 限流严重，火焰图里大量时间花在锁竞争和上下文切换上。

/proc 不是 namespace 化的——nproc、/proc/cpuinfo、/proc/meminfo 看到的都是宿主的真实硬件（docker run --cpus=2 alpine nproc 老老实实回答 96），于是所有「按核数自动配置」的默认值全错。正确读法是直接读 /sys/fs/cgroup/cpu.max。

处方：① 升级 runtime（JVM 的 UseContainerSupport、较新 Go 的 cgroup 感知、automaxprocs）；② 显式设置线程数环境变量，不依赖 auto；③ 平台侧挂 lxcfs 伪装 /proc。

容器排障 / 加固速查

  • 容器「无故变慢」→ 先看 cpu.stat 的 nr_throttled / throttled_usec，别只看利用率曲线；而且要采两次取差，里面全是累计值。
  • 退出码 137 → 被 SIGKILL，通常是 cgroup OOM。查 dmesg、memory.events 的 oom_kill、memory.stat 的 anon，注意堆外内存也算数。
  • 退出码 139 → SIGSEGV，应用自己崩了，去看 core dump，参考 崩溃调试。
  • 线程池 / GC 线程开太大 → 程序没感知 cgroup 限额，读的是宿主核数；升级 runtime 或显式配置。
  • 僵尸堆积、docker stop 等满 10 秒 → PID 1 问题。用 --init，ENTRYPOINT 用 exec 形式。
  • 数据丢失 → 写在可写层（删容器即丢）。持久化必须挂 volume；大文件小改动也必须挂，否则每次写都整文件 CoW。
  • 宿主磁盘满 → docker system df -v，重点查容器日志与悬空镜像；顺手 df -i 看 inode。
  • 容器里没有排查工具 → nsenter -t <宿主PID> -n 从宿主进它的 namespace，或 kubectl debug 起临时容器。
  • 安全 → 非 root、drop 全部 caps 再按需加、seccomp、只读根、绝不 --privileged、绝不挂 docker.sock。
  • 节点上 mount 变慢、df 输出上万行 → 挂载传播配成了 rshared。把 wc -l /proc/mounts 当节点级指标。
  • Pod 删除变慢、ip netns 卡顿 → netns 泄漏。lsns -t net 找 NPROCS=0，findmnt -t nsfs 找残留 bind mount。
  • 「磁盘还有空间却创建不了文件」→ inode 耗尽，df -h 和 df -i 永远一起看。
  • 随机超时但 CPU / 内存 / 带宽都正常 → 看 dmesg 有没有 nf_conntrack: table full，再看 SNAT 源端口是否耗尽。
  • 「配置改了但进程读到旧值」→ copy-up 换了 inode，老 fd 还指着 lower 层旧文件。重开文件，或把配置挂成 volume。
  • 共享内存不足、Bus error → /dev/shm 默认只有 64 MB，调 --shm-size。
  • 频繁起停容器的节点内核内存只增不减 → 看 cgroup.stat 的 nr_dying_descendants。
排障时永远记得：它就是宿主上的一个进程，宿主上所有工具都能用在它身上。

面试题（12 道）

分层自测

9.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础容器和虚拟机的本质区别是什么？

    虚拟机虚拟的是硬件，里面跑完整的 Guest OS 与独立内核；容器不虚拟任何硬件，所有容器共享宿主的同一个内核，只是被 namespace 限制视野、被 cgroup 限制用量，进程在宿主的 ps 里就能看到。

    由此推出的三条差异：

    • 开销：容器没有 Guest OS，额外内存接近 0、启动毫秒级；VM 要几百 MB 和数秒。
    • 隔离强度：VM 有 Hypervisor 挡一层；容器共享内核，内核漏洞直接等于逃逸。
    • 能力边界：VM 里可以改内核参数、加载模块；容器不能。

    能加分的一句：内核里根本没有 struct container，「造容器」只是换掉 task_struct 的 nsproxy / cgroups / fs / cred；正因为它不是内核对象，这几样才能拆开单用。选型判据是「这个负载会不会碰到共享内核这条边界」。

  2. 基础namespace 和 cgroup 分别解决什么问题？只有其中一个会怎样？

    namespace 管「看得见什么」——隔离进程号、挂载点、网络栈、主机名、IPC、用户 ID 的视图；cgroup 管「能用多少」——限制并统计 CPU、内存、I/O、进程数。

    缺一个的后果：

    • 只有 namespace 没有 cgroup：容器看不到别人，但能吃满宿主全部 CPU 与内存，把邻居饿死。
    • 只有 cgroup 没有 namespace：用量限住了，但能看到宿主所有进程、挂载、网卡，毫无隔离。

    加上第三样——OverlayFS 提供的分层根文件系统——才构成一个完整的容器。

    两者的实现风格也不同：namespace 是「换指针」，代价一次性付在创建时（net ns 最贵），运行期几乎零开销；cgroup 是「持续记账」，开销分摊在整个生命周期。它们都被单独用过，所以「容器」是约定而不是内核机制。

  3. 基础为什么容器删掉后数据就没了？怎么持久化？

    因为写入落在 OverlayFS 的可写层（upperdir）上，这一层随容器生命周期创建销毁；镜像的只读层则共享且不可改。

    持久化的三种方式：

    • volume：由 Docker/K8s 管理的独立存储，生命周期与容器解耦，推荐。
    • bind mount：把宿主某个目录挂进容器，简单但把容器和宿主路径绑死了。
    • tmpfs：用于不需要持久化但需要可写的场景（只读根 + 可写 /tmp）。

    加分点：除了「会丢」，还有性能理由——CoW 的粒度是整个文件，所以「所有会被写的路径一律挂 volume」是硬性规则。另一个 overlay 独有的坑：copy-up 会创建新 inode，之前打开的只读 fd 仍指着旧 inode，表现是「配置改了，进程重读却拿到旧值」。

  4. 基础容器退出码 137 和 139 分别意味着什么？

    Shell 约定：被信号杀死的进程退出码是 128 + 信号编号。

    • 137 = 128 + 9（SIGKILL）：最常见的是 cgroup 内存超限被 OOM killer 杀，也可能是 docker stop 超时后的强杀。
    • 139 = 128 + 11（SIGSEGV）：应用自己段错误，和容器机制无关。
    • 143 = 128 + 15（SIGTERM）：正常收到停止信号退出。docker stop 后拿到 143 说明优雅退出链路是通的，拿到 137 说明 SIGTERM 没被处理。
    • 134 = 128 + 6（SIGABRT）：断言失败、未捕获异常、glibc 检测到堆破坏。

    另外三个由运行时而非内核产生的码：125 = 运行时自己出错（容器压根没启动）；126 = 命令不可执行；127 = 命令不存在，多半是动态链接了镜像里没有的 .so。

    确认 137 是谁干的，三个证据一起看：① State.OOMKilled；② dmesg 里 Memory cgroup out of memory 是容器超了自己的 memory.max，不带 cgroup 字样的则是整机内存不足；③ memory.events 的 oom_kill 在不在涨。

    陷阱
    cgroup OOM killer 杀的是该 cgroup 里得分最高的任务，不一定是 PID 1。所以完全可能「容器还在跑、退出码也没变，但某个工作进程悄悄消失了」，业务表现为部分功能失效而不是崩溃重启。只能靠 oom_kill 计数发现。

9.2 中级（区分熟练度）

  1. 中级容器内的 PID 1 有什么特殊之处？为什么建议用 --init？

    PID namespace 的 1 号进程扮演 init 角色，内核对它有两条特殊规则：

    • 孤儿进程都过继给它，必须调 wait() 回收，否则僵尸堆积、耗尽 PID。
    • 它不会响应自己没装处理函数的默认信号。这本是内核防止误杀 init 的保护机制，用在容器上就成了坑：docker stop 的 SIGTERM 被忽略，等 10 秒超时后 SIGKILL 硬杀。

    把规则说精确能明显区分层次：同 ns 内发给 PID 1 的信号只有装了 handler 的才送达，连 SIGKILL 都丢；从祖先 ns发来时规则相同，唯独 SIGKILL / SIGSTOP 例外。第三条：PID 1 一退出，该 ns 里其余进程全被内核 SIGKILL。

    --init 注入一个极小的 init（tini）当 PID 1，回收僵尸并转发信号。判断要不要它只需两问：PID 1 会不会 fork 出可能变孤儿的子进程？它有没有正确处理 SIGTERM？两个都是「是」才可以不要。

  2. 中级容器 CPU 利用率只有 40%，服务却明显变慢。怎么定位？

    首先怀疑 cpu.max 的突发限流：配额是「每个 period 内最多用多少 CPU 时间」，突发负载会提前耗尽配额，剩余时间整段被冻结。按秒平均后利用率不高，但请求就卡在被冻结的那几十毫秒里。

    证据在 cpu.stat：

    nr_periods 41022
nr_throttled 18847     # 限流命中率 46%
throttled_usec 982114000

    但这三个数是累计值，看绝对值没有意义。必须采两次取差算比例：< 1% 基本无影响，1%–5% 已能看出毛刺，> 10% 一定要处理。

    为什么利用率会「骗人」：它的分母是「墙上时间 × 全部核数」，配额的分母是「一个 period」，并行度越高、越突发，两者差距越大；更好的指标是 cpu.pressure 的 some avg10。处方按性价比排序：先把线程数降到配额量级（常常只做这一步限流就消失），再考虑调小 period、改用 cpu.weight、或用 cpuset.cpus 绑核。

  3. 中级为什么用 pivot_root 而不是 chroot 切换容器根目录？

    chroot 只是改变进程的根目录指针，旧的根文件系统仍然挂载着、在挂载树上仍然存在。这带来两个问题：

    • 只要还有 CAP_SYS_CHROOT，可以再 chroot 到一个更深的目录，然后利用当前工作目录还在外面的特性 cd .. 一路走回真正的根。
    • 任何在 chroot 之前打开的、指向外部的文件描述符仍然可用，fchdir() 就能出去。

    原理值得说清：chroot 只改 task_struct→fs→root，不改 pwd。内核解析 .. 的规则是「到了本进程的 root 就停」，可一旦 pwd 落在 root 之外，这个条件永远不成立——逃逸代码不需要任何漏洞。而 pivot_root 把旧根整个从挂载树上摘下来再 umount，容器的挂载 namespace 里根本不存在通往宿主的路径。

    能报出 runc 的实际写法会加分（pivot_root(".", ".") 两个参数传同一个 "."，再 umount2(".", MNT_DETACH)）。验证很直接：容器里 wc -l /proc/mounts 只有二十来条，chroot 环境里宿主那一百多条一条不少。

  4. 中级容器里 nproc 显示 96 核，为什么？会造成什么后果？

    因为 /proc 不是 namespace 化的，读到的都是宿主机的真实硬件；cgroup 的配额是另一套东西，放在 /sys/fs/cgroup 下，两者互不相通。受害者是所有「按核数自动配置」的默认值：JVM 的 GC 线程数与 ForkJoinPool 并行度、Go 的 GOMAXPROCS、Nginx 的 worker_processes auto、C++ 的 hardware_concurrency()。

    后果不是「稍微浪费一点」，而是比不加限制还差：线程数远超配额核数 → 大量上下文切换与锁竞争 → 头几毫秒就把周期配额花光 → 剩下几十毫秒整组被冻结。也就是说线程开太多还放大了 CFS 节流。

    值得一并指出：这不止是核数的问题。/proc/meminfo 同样是宿主的，「按可用内存的 1/4 设堆」也全错；/proc/loadavg 让容器内的自适应限流读到不相干的负载。

    三种解法：升级到能感知 cgroup 的 runtime；显式设置线程数环境变量（最保险）；平台侧挂 lxcfs 伪装这几个 /proc 文件。正确读法始终是直接读 cpu.max 与 memory.max。

9.3 高级（体现深度）

  1. 高级cgroup v2 相比 v1 改了什么？为什么要改？

    v1 的核心问题是每个控制器一棵独立的层级树：一个进程可以同时在 cpu 树的 /A、memory 树的 /B、blkio 树的 /C。三个麻烦：

    • 语义混乱，很难回答「这个进程到底被谁限制着」。
    • 控制器无法协同——内存回收会产生 I/O，但 memory 控制器不知道按哪个 blkio 组的权重限速。
    • 没有统一的委派模型，容器运行时和 systemd 争抢 cgroup 树的所有权。

    v2 的改动：

    • 统一层级：只有一棵树，进程只属于一个节点，所有控制器作用在同一结构上。
    • 显式下放：父组要写 cgroup.subtree_control，子组里才有那些控制文件。
    • 「无内部进程」约束：非根的非叶子节点不能直接放进程。
    • 更好的内存控制：memory.high（软限，加压回收并对分配方限速而不是杀进程）与 memory.min（保护下限）。
    • PSI 压力指标：给出「有多少时间有任务在等这个资源」，比利用率更真实。
  2. 高级OverlayFS 的写时复制有什么性能陷阱？工程上怎么规避？

    两个陷阱：

    ① 写放大：CoW 的粒度是整个文件，不是块。对来自只读层的 2 GB 文件改 1 个字节，OverlayFS 先把 2 GB 完整复制到可写层才让你改（chmod 同样触发，除非开 metacopy=on）。

    ② 层数过多拖慢元数据操作。每次 open 要自上而下逐层查找，而「文件不存在」必须把每一层都查完；Python 的 import 恰恰产生大量「查不到」的探测。这才是「合并 RUN 指令」的真实理由。

    规避：

    • 所有会被写的数据一律挂 volume 或 bind mount 绕开 overlay。
    • 控制层数，多阶段构建，把频繁变动的层放最上面以利用缓存。
    • I/O 敏感的负载考虑其它 storage driver，或干脆挂独立块设备。
  3. 高级容器逃逸有哪些常见路径？分别怎么自查？

    绝大多数逃逸不需要内核 0day，只需要一个错误配置：

    • --privileged：全部 capability 加设备访问，可以直接挂宿主磁盘读写任意文件。自查 {{.HostConfig.Privileged}} 必须为 false。
    • 挂载 /var/run/docker.sock：等于交出宿主 root——容器里能调 Docker API 造一个特权容器并挂宿主根目录。
    • CAP_SYS_ADMIN：能挂文件系统、操作 cgroup，是多条逃逸链的起点。自查 capsh --decode=$(grep CapEff /proc/self/status | cut -f2)。
    • 挂宿主 /proc、/sys 为可写：能通过 core_pattern 这类可写入口在宿主上执行命令。
    • hostPID / hostNetwork：能看到并操作宿主全部进程、直接访问宿主本地服务，横向移动能力极强。
    • 内核漏洞：共享内核意味着任何本地提权漏洞都可能成为逃逸漏洞。

    系统性的防御是纵深的：非 root 运行 + user namespace remap + drop 全部 caps + seccomp + 只读根 + no_new_privs + 及时打内核补丁。详见 Linux 安全模型。

  4. 高级K8s Pod 里的多个容器是怎么共享网络和存储的？pause 容器起什么作用？

    Pod 是「一组共享部分 namespace 的容器」。具体共享哪些：

    • network namespace：共享同一个 IP 与端口空间，可以用 localhost 互通——也意味着同一 Pod 内不能监听同一个端口。
    • IPC namespace：可以用 System V IPC / POSIX 消息队列互通。UTS：共享主机名。
    • 存储：不是共享 namespace，而是把同一个 volume 分别挂进各容器的挂载点。
    • PID namespace 默认不共享，要显式设 shareProcessNamespace: true。
    • mount namespace 各自独立——所以每个容器有自己的根文件系统和镜像。

    pause 容器的作用是持有这些共享的 namespace：它第一个启动并创建 network/IPC/UTS namespace，业务容器用 setns 加入。价值在于业务容器可以随意崩溃重启，而 Pod 的 IP 由 pause 持有、始终不变。这是「用一个最小的、绝不崩溃的进程锚定共享状态」的经典设计，和 containerd-shim 持有容器 stdio 一脉相承。
