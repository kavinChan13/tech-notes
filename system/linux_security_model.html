Linux 安全模型

同一台机器上，内核凭什么决定「这个进程能不能做这件事」？这篇把答案拆成五层—— seccomp 收窄系统调用面、DAC 看属主与权限位、capabilities 把 root 切成碎片、LSM 让策略压过属主、namespace 划出可见范围—— 再用它们去解释「容器到底隔离了什么、又漏了什么」。
与另一篇的分工：C++ 安全加固指南讲的是代码层面的安全（内存漏洞、编译期硬化、sanitizer、供应链）； 本篇讲操作系统层面的安全模型——即使你的代码被攻破，攻击者能拿到什么，由这一层决定。
对位读者：需要为服务设计最小权限、或需要回答「容器到底隔离了什么」的后端与平台工程师。

01

权限检查发生在哪

一次 open() 要连过五道关卡

一次 open("/etc/shadow", O_RDONLY) 要过五道独立关卡，任何一道拒绝就失败——它们是「与」不是「或」。「我 chmod 777 了为什么还是 Permission denied」的答案几乎永远是：你只打开了 DAC 那一道门。

进公司大楼要过五道关：门禁闸机（seccomp——你这张卡根本没被允许刷这台机器）、工位归属（DAC——这个抽屉是不是你的）、职级牌（capabilities——你有没有「可以开别人抽屉」的特权）、公司红头文件（MAC——就算抽屉是你的，制度规定研发不得带出财务资料）、楼层可见性（namespace——你的门禁卡只能到 3 楼，其他楼层对你来说根本不存在）。五道全过才进得去；任意一道不过就是「Permission denied」，而且错误码通常长得一模一样，这正是排障最难的地方。

为什么要这么多层

每一层都在补上一层的洞：

层它补的洞它自己的短板引入时间
DAC（uid/gid + mode）最基本的多用户隔离粒度太粗：只有「属主/组/其他」三档；而且属主可以随意放宽，一个 chmod 777 就把防线拆了Unix 诞生起
capabilitiesroot 是全有全无：一个只想绑 80 端口的进程被迫拿到格式化磁盘的能力拆分粒度仍然不均，CAP_SYS_ADMIN 成了新的垃圾桶（约等于 root）Linux 2.2（1999）
seccomp系统调用面太宽：内核有 300+ 个入口，你的进程可能只用 40 个，其余全是白送的攻击面只能看系统调用号和寄存器里的标量参数，看不到指针指向的内容（TOCTOU）2.6.12 strict / 3.5 filter
LSM / MACDAC 归属主管，属主自己会犯错；需要一套属主也改不了的策略策略编写与维护成本高，出问题时排查链路长Linux 2.6（2003）
namespace前四层都在「同一个世界」里做判断，缺少看不见这个更强的隔离共享同一个内核——内核漏洞面完全没有被隔离2.4.19 起逐步加入，3.8 补齐 user ns
一句话：seccomp 决定「能敲哪些门」，DAC 决定「门是不是你家的」，capabilities 决定「有没有万能钥匙」，LSM 决定「制度允不允许开」，namespace 决定「你在哪一栋楼」。
顺序与翻盘：① seccomp 在系统调用入口，拒绝时是 SIGSYS 或指定 errno，不是 EACCES；② DAC 拒绝后 capabilities 还能翻盘（CAP_DAC_OVERRIDE）；③ LSM 拒绝没有任何东西能翻盘，连 root 都不行——这就是 MAC 相对 DAC 的本质差别。
本篇是操作系统层。代码层的内存漏洞、编译器硬化、供应链见 C++ 安全加固指南。两者是纵深的两端：代码层降低「被攻破」的概率，系统层降低「被攻破之后的损失」。
02

传统 DAC：属主说了算

看似人人都懂，细节处处是坑

DAC（Discretionary Access Control，自主访问控制）：访问权限由客体的属主自行决定。你的文件，你想给谁看就给谁看，内核不干涉这个决定。「自主」这个词是关键——它同时是 DAC 的便利之处和它的根本弱点。

2.1 权限位：目录的 r 和 x 完全是两回事

文件的 rwx 很直观，目录的 rwx 才是考点：

位对普通文件对目录没有它会怎样
r读内容列出目录里有哪些名字（readdir）ls 失败，但已知名字仍能访问
x执行穿越——按名字解析进去（stat/open/cd）整棵子树全部不可达，连 stat 都是 EACCES
w写内容增删改名目录项（须同时有 x）无法创建/删除——删文件看的是目录的 w，不是文件自己

这就是家目录常见的 711：外人列不出你有哪些文件，但你可以把 ~/public_html/index.html 这种约定路径告诉别人。路径上每一级都要 x——文件本身 644 却读不了，多半断在上层某级目录。反过来，共享盘给了 r 忘了 x，ls 热闹、打开全是 EACCES。

2.2 umask：新文件权限的减法

umask 不是默认权限，而是要减掉的位：内核用 mode & ~umask。普通文件 open 常传 0666，目录 0777。

umask普通文件结果典型场景
00220644systemd 服务默认；组不可写
00020664交互 shell 常见；「本地好好的、线上全组可写」多半是这个差
00770600只有自己能读
umask 只能减不能加，且是进程属性、被子进程继承。精确权限用 open(…, 0600) 再按需 fchmod——先关紧再开门。临时改 umask 不是线程安全的。

2.3 setuid / setgid / sticky：三个特殊位

位八进制对可执行文件对目录看起来像
setuid4000以文件属主的身份运行（典型 passwd 需要写 /etc/shadow）Linux 上忽略-rws r-x r-x
setgid2000以文件属组的身份运行新建文件继承目录的属组（团队共享目录靠它）drwx r-s r-x
sticky1000现代内核忽略只有文件属主（或目录属主、或有 CAP_FOWNER）能删除/改名drwx rwx rwt
/tmp 为什么是 1777：777 让所有人能建临时文件；前面的 1（sticky）堵住「目录 w = 能删别人文件」。sticky 只管删除，不管创建——固定文件名的 symlink / TOCTOU 仍在。对策：mkstemp() 或 O_CREAT|O_EXCL|O_NOFOLLOW，服务再叠 PrivateTmp=yes；内核兜底 fs.protected_symlinks=1 / fs.protected_hardlinks=1。

2.4 进程的三套 uid：real / effective / saved

每个进程有三个 user ID（gid 同理还有三个），外加 Linux 特有的第四个 fsuid：
  • real uid（ruid）：你是谁——登录时确定，代表进程的真实归属，决定谁能给它发信号。
  • effective uid（euid）：你现在以谁的身份行事——所有权限检查用的都是它。
  • saved set-user-ID（suid）：execve 时保存的一份「备份」，让进程能在特权与非特权之间来回切而不丢失恢复能力。
  • fsuid：仅用于文件系统访问检查，通常自动跟随 euid。历史上给 NFS 服务器用，普通程序不必碰。
三套 id 像「员工卡 + 临时授权牌 + 存在前台的原卡」：real 证明你是谁；门禁只认 effective；saved 让你还能换回来。
❌ 先 setuid 再 setgid，还不检查返回值

setuid(uid) 之后已经不是 root，setgid 静默 EPERM，gid 仍是 0；附加组也没清——docker 组还在，等价于没降权。

✅ setgroups → setresgid → setresuid，每步检查，事后复查

三套 id 全部显式写成目标值；getresuid 核对；再试 setuid(0)，成功就说明没降干净。

2.5 为什么现代做法是尽量不用 setuid 二进制

setuid 程序是「用户任意控制输入、却以 root 身份跑」的攻击面——环境变量、已打开 fd、cwd、rlimit 全由调用者控制。动态链接器会忽略 LD_PRELOAD，但你自己 system() 出去的子进程不会。权限还是全量的：passwd 只想改一个文件，却拿到完整 root。

三种替代：① 文件 capability（setcap）只给这一位；② systemd socket activation，特权进程绑好端口把 fd 传过去；③ 特权 helper 经 Unix 域套接字暴露极窄接口，用 SO_PEERCRED 验身份。镜像里 setuid 二进制应趋近于零：find / -xdev -perm -4000 -type f 定期 diff。

挂载选项也是 DAC 的一部分：对 /tmp、/dev/shm、用户可写挂载点，nosuid,nodev 应是默认——即使放得进 setuid-root 文件也执行不出特权。findmnt -o TARGET,OPTIONS 一次看全。
03

capabilities：把 root 拆开

四十多把小钥匙，替代一把万能钥匙

传统 Unix 只有 uid 0（内核跳过绝大多数检查）和其他。一个只想 bind(80) 的进程被迫拥有加载模块、格式化磁盘的能力。capabilities 把 root 切成 40 多个独立位，按需授予。

从万能钥匙换成按需门禁卡。丢一张保洁卡损失停在走廊；但若图省事发了「除机房外全部楼层」，那就和万能钥匙没区别——这就是 CAP_SYS_ADMIN。

3.1 常用 capability 一览

capability能干什么典型使用者风险
CAP_NET_BIND_SERVICE绑定 1024 以下的特权端口Web / DNS 服务低——这是最典型的「只需要这一个」场景
CAP_NET_ADMIN配置网络：网卡、路由、iptables、netns、抓包接口CNI 插件、VPN、网关中高——能改路由就能做中间人
CAP_NET_RAW创建 RAW / PACKET socket（ping、抓包、伪造源地址）ping、tcpdump中——可嗅探同网段流量、做 ARP 欺骗；容器里建议 drop
CAP_DAC_OVERRIDE绕过所有文件读写权限检查备份工具高——等于对所有文件有读写权
CAP_DAC_READ_SEARCH绕过读与目录穿越检查；还能用 open_by_handle_at索引/备份高——open_by_handle_at 是经典逃逸原语
CAP_CHOWN改任意文件的属主包管理、解压工具高——可把关键文件改成自己的再改内容
CAP_FOWNER绕过「必须是属主」的检查（chmod、删 sticky 目录里别人的文件）包管理高
CAP_SETUID / CAP_SETGID任意切换 uid / gidlogin、容器运行时极高——等价于可以变成任何用户
CAP_SYS_PTRACEptrace 任意进程、读写其内存调试器、profiler极高——能注入代码到更高权限的进程
CAP_SYS_MODULE加载/卸载内核模块驱动安装极高——直接就是内核态代码执行
CAP_SYS_ADMINmount、pivot_root、setns、swapon、部分 bpf、改 hostname…一百多个不相干的操作容器运行时约等于 root，见下方警告
CAP_BPF加载大部分 eBPF 程序（5.8 起从 SYS_ADMIN 拆出）可观测性 agent高——常需与 CAP_PERFMON 配合
CAP_PERFMONperf_event_open 等性能监控（5.8 起从 SYS_ADMIN 拆出）perf、profiler中高——可侧信道观测其他进程
CAP_SYS_CHROOTchroot沙箱工具中——单独看不算高，但配合其他能力是逃逸拼图的一块
CAP_SYSLOG读内核环形缓冲（dmesg）日志采集中——泄漏内核地址，破坏 KASLR
CAP_SYS_ADMIN 约等于 root：历史上的垃圾桶，一百多个不相干操作，其中挂载、setns、cgroup v1 写 release_agent 都能换成完整 root。听到「容器需要 --cap-add=SYS_ADMIN」，正确反应是追问它到底要哪一个操作——十有八九能换成更窄的位，或宿主侧预先备好资源再挂进去。

3.2 五个集合与 execve 的计算规则

这是 capabilities 里最容易讲糊涂、也最容易被追问的部分。每个进程有五个集合，每个带文件 capability 的可执行文件有三个集合。

集合缩写含义一句话记忆
PermittedCapPrm进程被允许持有的能力上限，可以随时从这里往 Effective 里加「钱包里有多少钱」
EffectiveCapEff内核当下真正检查的集合——只有在这里的能力才生效「手里正拿着多少钱」
InheritableCapInh与文件的 Inheritable 求交后可以跨 execve 保留「需要对方也同意才能传下去」
BoundingCapBnd天花板：这里没有的，任何途径都拿不到。只能减不能加，且不可逆「这辈子最多能有多少」
AmbientCapAmb（4.3 起）能无条件跨过 execve 的集合，专为「非 root 且目标文件没有文件 cap」设计「随身带过去，不需要对方配合」
① 检查只看 Effective；② Bounding 是硬天花板，丢掉不可逆；③ Inheritable 要「进程和文件双方都标了这一位」才能传下去，普通脚本没有文件 cap——Ambient（4.3+）就是补这个洞（文件带 setuid / 文件 cap 时会被清空，防止污染特权程序）。

3.5 在代码里主动降权

#include <sys/capability.h>   // libcap，编译加 -lcap
#include <sys/prctl.h>
#include <linux/capability.h>

// 启动早期（还是 root 时）绑好端口，然后把特权降到只剩必要的一位
static bool drop_to_minimal(uid_t uid, gid_t gid) {
    // ★① 保住 Permitted 集，否则 setuid 到非 0 时内核会清空所有 cap
    if (prctl(PR_SET_KEEPCAPS, 1, 0, 0, 0) != 0) return false;

    // ★② 顺序不能反：附加组 → gid → uid
    if (setgroups(0, nullptr) != 0)      return false;
    if (setresgid(gid, gid, gid) != 0)  return false;
    if (setresuid(uid, uid, uid) != 0)  return false;

    // ★③ 只保留 CAP_NET_BIND_SERVICE，其余全部清掉
    cap_t caps = cap_init();                       // 全空的集合
    cap_value_t keep[] = { CAP_NET_BIND_SERVICE };
    cap_set_flag(caps, CAP_PERMITTED, 1, keep, CAP_SET);
    cap_set_flag(caps, CAP_EFFECTIVE, 1, keep, CAP_SET);
    int rc = cap_set_proc(caps);                   // 应用到当前进程
    cap_free(caps);
    if (rc != 0) return false;

    // ★④ 收 Bounding 天花板 —— 这一步不可逆，之后连 exec 也拿不回来
    for (int c = 0; c <= CAP_LAST_CAP; ++c) {
        if (c == CAP_NET_BIND_SERVICE) continue;
        prctl(PR_CAPBSET_DROP, c, 0, 0, 0);   // 已经 drop 的返回 EINVAL，忽略即可
    }

    // ★⑤ 关死「execve 提权」这条路（详见 §4）
    return prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0) == 0;
}
忘了 PR_SET_KEEPCAPS 是这段最常见的 bug。euid 从 0 变成非 0 时内核默认清空 Permitted / Effective。必须先 KEEPCAPS 保住钱包，降完 uid 再挑要留的。它只保护「本进程降 uid」这一刻，execve 时自动清零。
容器里通常不用自己写：--cap-drop=ALL --cap-add=NET_BIND_SERVICE --user 1000，或 K8s 的 securityContext.capabilities。自己写降权的价值是不依赖部署方配置正确。两者叠加最好。
04

seccomp-bpf：收窄系统调用面

用不到的门，直接砌死

DAC 和 capabilities 回答的是「你能不能操作这个对象」。seccomp 回答的是一个完全不同的问题：「你能不能调用这个系统调用」——不管对象是谁。它是纵深防御里非常划算的一层，因为内核提供了 300 多个系统调用入口，而一个具体的服务进程通常只用到其中 40～60 个，剩下 250 个纯粹是白送给攻击者的攻击面。

一栋楼有三百扇门，你的部门日常只走其中四十扇。seccomp 就是把剩下那二百六十扇直接砌死——不是加锁（加锁还有配钥匙、撬锁、内鬼的可能），是砌墙。哪怕攻击者拿到了你的员工卡（RCE 拿到了进程控制权），他也没法从那些门出去。代价是：万一你哪天真的需要走某扇被砌死的门，程序不是失败，而是当场被打死（SIGSYS）——所以「砌哪些门」这份名单必须建立在真实数据上。
seccomp（SECure COMPuting）：进程自愿给自己安装一份系统调用过滤器，之后不可撤销，且被所有子进程和 execve 出来的程序继承。「自愿 + 不可撤销 + 可继承」这三个性质合起来，让它成为沙箱的理想基石——沙箱在做危险事情之前先把自己关起来，之后就算被完全控制也出不去。

4.3 no_new_privs：装过滤器的前提

no_new_privs：一旦置位无法清除、被子进程继承。置位后 execve 不再因 setuid 或文件 cap 提升权限。

装 filter 必须先置这个位（除非有 CAP_SYS_ADMIN）。否则普通用户能构造混淆代理人：过滤器会被 execve 继承，而即将变成 setuid-root 的那个程序会在扭曲的系统调用语义下跑——典型手法是让 setgroups 返回成功却不真正清附加组，特权程序以为自己降干净了。

no_new_privs 是装 seccomp 的前提，否则普通用户能绕。置位之后再 exec 那个 setuid 二进制，它拿不到额外特权，过滤器坑到的只剩自己。K8s 的 allowPrivilegeEscalation: false、Docker 的 --security-opt no-new-privileges 设的就是这个位——它同时关掉 setuid 和文件 cap 两条提权路，所以和 seccomp 是一对，不要只装过滤器忘了它。

4.4 用 libseccomp 写一个白名单过滤器

手写 cBPF 指令既痛苦又容易错（还要自己处理架构判断），生产上一律用 libseccomp。下面是一个「只做 JSON 解析、除必需 IO 外什么都不许干」的沙箱子进程的完整过滤器：

#include <seccomp.h>      // libseccomp-dev，编译加 -lseccomp
#include <sys/prctl.h>
#include <sys/socket.h>

static bool install_sandbox(int in_fd, int out_fd) {
    // ★① 先置 no_new_privs（libseccomp 的 load 也会做，显式写出来更清楚）
    if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0) != 0) return false;

    // ★② 默认动作 = 杀进程。白名单模式，宁可误杀不可漏放。
    //     调试期可临时换成 SCMP_ACT_LOG 或 SCMP_ACT_ERRNO(EPERM)。
    scmp_filter_ctx ctx = seccomp_init(SCMP_ACT_KILL_PROCESS);
    if (!ctx) return false;

    // ★③ 显式声明目标架构。不加这句，过滤器只覆盖本机原生架构，
    //     x86-64 上仍可通过 int 0x80 走 i386 ABI 用【不同的调用号】绕过。
    seccomp_arch_add(ctx, SCMP_ARCH_X86);        // 32 位兼容 ABI
    seccomp_arch_add(ctx, SCMP_ARCH_X32);        // x32 ABI

    // ── 必需：进程收尾。少一个都会在退出时被自己的过滤器打死 ──
    int always[] = { SCMP_SYS(exit), SCMP_SYS(exit_group),
                     SCMP_SYS(rt_sigreturn), SCMP_SYS(rt_sigprocmask),
                     SCMP_SYS(rt_sigaction) };
    for (int nr : always) seccomp_rule_add(ctx, SCMP_ACT_ALLOW, nr, 0);

    // ── 必需：glibc 内部会用到的内存与线程原语 ──
    //    ⚠ 这几个是「你自己代码里一次都没写、但少了必挂」的典型
    int mem[] = { SCMP_SYS(brk), SCMP_SYS(mmap), SCMP_SYS(munmap),
                  SCMP_SYS(mprotect), SCMP_SYS(mremap),
                  SCMP_SYS(futex), SCMP_SYS(getrandom),
                  SCMP_SYS(clock_gettime), SCMP_SYS(gettimeofday) };
    for (int nr : mem) seccomp_rule_add(ctx, SCMP_ACT_ALLOW, nr, 0);

    // ── 业务：只允许读写【这两个已经打开的 fd】，其他 fd 一律拒绝 ──
    //    第 4 个参数 1 = 附加 1 个参数条件；A0 是第一个参数（fd）
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(read),  1,
                     SCMP_A0(SCMP_CMP_EQ, (scmp_datum_t)in_fd));
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 1,
                     SCMP_A0(SCMP_CMP_EQ, (scmp_datum_t)out_fd));
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(close), 0);

    // ── 明确拒绝但不杀：让程序看到 EPERM 走降级分支 ──
    //    比直接 KILL 友好，适合「有也行没有更好」的能力
    seccomp_rule_add(ctx, SCMP_ACT_ERRNO(EPERM), SCMP_SYS(socket), 0);

    // ★④ 加载。加载之后【永不可撤销】，且 fork/exec 出来的都继承。
    int rc = seccomp_load(ctx);
    seccomp_release(ctx);            // 释放的只是用户态上下文，过滤器已在内核里
    return rc == 0;
}

4.5 四个真实的工程陷阱

① 拦到了 libc 内部用的调用 → 莫名其妙崩溃

  • 代码没写 futex，std::mutex / 惰性初始化会调；没写 getrandom，glibc malloc 和栈保护会调。
  • clock_gettime 有 vDSO 时不走系统调用，换一台没配好的机器就走了——同样二进制 A 机正常、B 机 SIGSYS。
  • 症状：进程无预警消失，dmesg 里 seccomp ... syscall=228。用 ausyscall 228 把号翻出来。

② 调用号是架构相关的，白名单不可跨架构复用

  • x86-64 上 read=0，aarch64 上 =63。必须用 SCMP_SYS() 宏，不要字面量。
  • x86-64 还有 i386 / x32 ABI。不显式 seccomp_arch_add 就等于留了后门。
  • glibc 会把 open 换成 openat。升级基础镜像后必须重新采集。

③ 先用 LOG 跑一轮，用数据生成白名单

  • 默认动作临时 SCMP_ACT_LOG，跑完整功能与压测（含错误分支、重连、优雅退出）。
  • ausearch -m SECCOMP 捞实际调用；没有 auditd 时用 strace -c 起步。
  • 采集到的是「跑过的」不是「需要的」。看到 ptrace / mount / init_module 先问为什么。
  • 灰度：LOG → ERRNO(EPERM) → KILL_PROCESS。

④ Docker 默认 profile 屏蔽了什么

  • 白名单式（默认 SCMP_ACT_ERRNO），挡住的是「业务用不到、对攻击者很有用」的几十个调用：
  • 内核模块：init_module / finit_module / delete_module——直接的内核代码执行。
  • 挂载与根切换：mount / umount2 / pivot_root——逃逸的核心原语。
  • namespace：setns、带 CLONE_NEW* 的 unshare（依配置）。
  • 整机状态：reboot / kexec_load / clock_settime。
  • 密钥环与句柄：keyctl（keyring 没有完全 namespace 化）、open_by_handle_at（配合 CAP_DAC_READ_SEARCH 是经典逃逸手法）。
  • 观测：bpf / perf_event_open——容器里跑 eBPF 探针默认不行。
  • ⚠ --privileged 会连同 seccomp profile 一起关掉（变成 unconfined），不只是加满 capabilities。
  • K8s 对应 seccompProfile.type: RuntimeDefault。它不是默认值——不写这一行，很多集群是 Unconfined。这是最便宜的一条加固。

LSM 与 MAC：SELinux / AppArmor

策略说了算，属主也改不了

MAC：规则由系统级策略规定，属主无权修改。DAC 是「我的文件我做主」，MAC 是「制度说不行就是不行，属主和 root 都不例外」。
DAC 像家门锁，钥匙你配。MAC 像公司涉密制度：文件是你写的，但不能带出研发区，签字权不在你手上。Web 被打穿后，DAC 下攻击者能碰所有 apache 能碰的；MAC 下他锁在 httpd_t，策略没写 allow 的一律拒绝。

5.1 LSM：内核里的钩子框架

LSM 不是策略，而是遍布内核的钩子：打开文件、创建 socket、exec、ptrace… 具体模块挂上去判断。位置永远在 DAC 和 capabilities 之后。

5.2 SELinux 的模型：一切皆 label

每个主体和客体都贴四段 label：user:role:type:level。Type Enforcement 是核心：策略写「哪个 source type 能对哪个 target type 做哪种操作」，默认拒绝。服务器场景出问题几乎总是 type 对不上。

模式行为何时用
Enforcing拒绝 + 记日志生产
Permissive不拒绝但照样记调试：setenforce 0（重启失效）
Disabled完全关闭，停止维护 label几乎永远不该用

看 label：文件 ls -Z，进程 ps -Z，身份 id -Z，socket ss -Z。

关掉 SELinux 是最糟的解决方案。SELINUX=disabled 后内核停止维护文件 label，期间新建的文件没有正确 type。再开启只能全盘 restorecon -R /——TB 级文件系统是几小时停机。临时手段永远是 Permissive：业务先跑，同时拿到「要放开哪些」清单。

5.3 实操：从 AVC denied 到修好

  1. ausearch -m AVC,USER_AVC -ts recent -i 确认是 MAC 拦的，不是 DAC。
  2. 逐字段读：denied { read }、scontext（谁，如 httpd_t）、tcontext（对谁）、tclass、permissive=0 表示真拒了。
  3. 90% 是 label 不对。头号成因：mv 保留 label，cp 按目标路径重打——从家目录 mv 网页到 /var/www 必然出问题。
  4. 修复优先级：matchpathcon + restorecon → setsebool -P 开现成开关 → semanage fcontext/port 登记非默认路径/端口 → 最后才 audit2allow，且先只打印、逐条审掉 sys_admin / unlabeled_t。

端口也有 label：nginx 听 8888 要先 semanage port -a -t http_port_t -p tcp 8888。反向代理先查 httpd_can_network_connect 这个 boolean，90% 常见场景社区已预留开关。

❌ 无脑 audit2allow -M 然后 semodule -i

生成的规则可能含 allow httpd_t self:capability sys_admin，等于把约束拆掉大半，还留下没人敢动的自定义模块。

✅ 先 audit2allow 只打印，再 audit2why

restorecon → setsebool → semanage → 写策略。真要写也审掉过宽规则。

5.4 AppArmor：按路径而不是按 label

不给文件贴 label，profile 里直接写路径通配。入门成本低——一份可读文本。代价是 bind mount 与路径别名会让规则对不上；SELinux 跟的是 inode 上的 type，搬文件只要 label 跟着走。排障路径因此完全不同：AppArmor 先对路径，SELinux 先对 type。

规则含义
capability net_bind_service,只允许这一个 capability
/etc/myserver/** r,配置只读
/var/lib/myserver/** rw,数据读写
deny /home/** rwx,显式拒绝（比默认拒绝优先级更高）
network inet stream,只允许 TCP/IPv4
deny network raw,禁掉 raw socket

常用命令：aa-status / aa-complain（只记录不拦截）/ aa-enforce / aa-logprof（读日志交互补规则）/ apparmor_parser -r 重载。被拒日志直接写缺哪条路径，比 AVC 好读。

维度SELinuxAppArmor
约束对象inode 上的 label（跟着文件走）路径字符串（跟着位置走）
覆盖范围全系统默认约束，未打标的落到 unlabeled_t；进程、文件、端口、socket、IPC、设备全都管只约束显式写了 profile 的程序，没写 profile 的完全不受限
上手成本高——要理解 label / type / boolean / 策略模块，出错信息晦涩低——一份文本 profile，日志直接说缺哪条路径
表达能力更强：MLS/MCS 多级安全、类型转换、精细的 class/permission较弱：以文件路径 + 少量网络/capability 规则为主
硬链接 / 绑定挂载不受影响——label 在 inode 上，换多少条路径指过去都一样是弱点：同一个 inode 从另一条路径访问就绕过了规则；bind mount、符号链接、容器内重映射都要小心
重命名 / 移动文件mv 保留 label（反倒是常见坑，见上文）路径变了规则自然跟着变，符合直觉

怎么选？跟着发行版走。主流内核只允许一个 major LSM，默认策略、软件包 profile、社区经验都围着它。真正要决策的是「用不用」和「约束到什么粒度」，不是用哪个。

隔离了什么，更重要的是没隔离什么

前五层回答「能不能做」。namespace 回答「能看见什么」。看不见的自然操作不了，所以常被当成隔离——但它不是为安全设计的，初衷是资源视图虚拟化。机制原理见 cgroup / namespace 与容器原理，这里只谈安全边界。

6.2 user namespace：唯一非特权可创建的那个

user namespace：唯一普通用户无需特权就能创建的 namespace。新 ns 里可以是 uid 0 并拥有该 ns 内全套 capability——但只对同属这个 ns 的资源有效。它是 rootless 的基石，也是争议最大的一块。
像剧组里的国王：片场内对布景道具有绝对权威，走出摄影棚就是普通人。为了戏演得像，内核给了他不少过去只有 root 才走得到的代码路径——这些路径审计远不充分，大量 userns CVE 就来自这里。

6.4 两面性：rootless 的基石，也是提权的温床

user ns 同时是 rootless 的基石，也是本地提权的温床——这两件事经常被混成一句「userns 危险」，必须拆开看。

❌ 它扩大了攻击面

创建 user ns 后，普通用户能触达大量过去只有 root 才走得到的内核路径（挂载解析、netns、cgroup、setns）。这些路径历史上按「反正只有 root 能走」来审计，于是出现一批以「非特权 userns」为前置的本地提权 CVE。发行版用三套旋钮收：Debian / 部分内核的 kernel.unprivileged_userns_clone=0、通用的 user.max_user_namespaces、较新 Ubuntu 的 kernel.apparmor_restrict_unprivileged_userns（配合 AppArmor 限制能在 userns 里干什么）。关掉非特权克隆并不等于不能跑 rootless 容器——运行时可以用一个有限特权的 helper 代为创建。

✅ 它也是最有效的容器加固

没有 user ns 时，容器 root 就是宿主 root（uid 都是 0），任何碰到宿主文件的路径都是完整沦陷。开了之后逃逸收益从「宿主 root」降成「uid 100000 的陌生人」。给容器开 user ns 是加固；允许宿主上任意用户随便创建是风险。合理配置：运行时用它，sysctl / AppArmor 限制滥用。

Docker userns-remap 与 --privileged / --pid=host / --net=host 及部分卷不兼容，已有卷属主会对不上（宿主看是 100000）。适合新集群从一开始就开；中途切换要做迁移评估。写 gid_map 前必须先 echo deny > /proc/PID/setgroups，否则返回 EPERM——不禁掉 setgroups 的话进程可以丢掉某个附加组，绕过「deny 某组」类的负权限规则。

容器逃逸的真实路径

绝大多数不是内核 0day，是配置错误

下面讲原理、成因和自查判据，不提供可运行的攻击脚本。真实逃逸绝大多数不是内核 0day，是写得太宽松的部署配置。前两条加起来覆盖大部分事故。

7.1 --privileged：等于没有容器

--privileged 等于没有容器。它一次性做了五件事，很多人只记得第一件：

  1. capability 全给——包括 SYS_ADMIN / SYS_MODULE / SYS_PTRACE / DAC_READ_SEARCH。
  2. seccomp profile 换成 unconfined——§4.5 那张白名单整表作废。
  3. AppArmor / SELinux 约束解除——MAC 层不再挡路径。
  4. /sys 变可写——cgroup、uevent、内核参数重新暴露。
  5. 宿主所有设备节点在 /dev 下可见——块设备可以直接 mount。

有了这些，容器里的 root 能直接看到宿主块设备并挂载它——改 /etc/passwd、写 authorized_keys、投个 cron 都是顺手的事。剩下的只有 namespace 提供的「视图隔离」，对一个能挂载宿主磁盘的进程毫无意义。

自查三条对上就是特权容器：CapEff 满 f（如 0000003fffffffff）+ Seccomp: 0 + ls /dev 上百项且能看到 /dev/sda。唯一合理用途是系统组件（CNI、存储驱动、节点 agent）——它们本来就等于节点上的 root。常见借口与收窄：「要 DinD」换 Kaniko / buildah；「要设 sysctl」用运行时的 --sysctl；「要挂 fuse / GPU」用 --device + 对应 cap，不要一把梭。

7.2 挂载 /var/run/docker.sock：把宿主 root 交出去

比 privileged 更隐蔽：看起来只是挂了一个文件，CI runner、监控面板的官方文档里到处都是这个写法。推理链只有三步：这个 socket 是 Docker 守护进程的完整控制 API → 通过它可以创建新容器且参数由你指定 → 于是可以创建一个 privileged、把宿主 / 挂进去的容器。不需要任何漏洞，这就是 API 的正常功能。

能访问 docker.sock = 拥有宿主 root。containerd.sock / crio.sock / 宿主 docker 组成员，完全同理。自查：ls -l /var/run/docker.sock、mount | grep sock、以及 id 看在不在 docker 组。集群侧用准入控制把挂了 /var/run 的 hostPath 全捞一遍。

修：CI 换 rootless 构建器（buildah / Kaniko）；监控用只读 API 代理，不要把 socket 递进业务 Pod。绕不开就把这个工作负载按与宿主同等信任级别治理——它已经不是「一个容器」了。

7.3 CAP_SYS_ADMIN + cgroup v1 的 release_agent

cgroup v1 有一个「最后一个进程退出时通知」机制：某个 cgroup 的进程数掉到 0 时，内核会执行该 cgroup 的 release_agent 字段里写的路径。执行发生在宿主根 namespace、root 凭据——不是容器里那个进程的上下文。攻击链因此变成：在容器里挂上 cgroupfs（需要 CAP_SYS_ADMIN）→ 给某个子 cgroup 写 release_agent=/恶意程序 → 把自己放进去再立刻退出 → 内核在宿主上帮你跑那个程序。

前置条件三件套：容器有 CAP_SYS_ADMIN、宿主仍是 cgroup v1、进程处于初始 user ns（ns 内的 SYS_ADMIN 打不到宿主的 cgroupfs）。自查：stat -fc %T /sys/fs/cgroup 是 cgroup2fs 则这条路径不存在；/proc/self/uid_map 若是 0 0 4294967295 表示没做 uid 重映射，逃逸收益仍是宿主 root。

CVE-2022-0492 漏掉了对「必须在初始 user ns」的校验，连 CAP_SYS_ADMIN 都不再需要——非特权容器也能走到这条路径。「需要某 cap 才能利用」不是可靠防线：漏一个检查，整条假设就塌。切到 cgroup v2 是结构性修复——v2 改用 cgroup.events + inotify，不在内核里执行用户指定的程序。

7.4 可写的 /proc 与 /sys

路径可写的后果正常状态
/proc/sys/kernel/core_pattern写成 |/path/to/prog 后，任意进程崩溃都会在宿主上 root 执行它容器内只读（运行时会把 /proc/sys 挂成 ro）
/proc/sys/kernel/modprobe内核在需要自动加载模块时会执行这个路径只读
/proc/sysrq-trigger可触发宿主重启、OOM kill、Magic SysRq被 mask 掉（指向 /dev/null）
/proc/kcore、/proc/kallsyms读内核内存 / 泄漏内核符号地址，破坏 KASLR被 mask 或权限受限

7.5 hostPID / hostNetwork / hostIPC

hostPID: true

  • 看到宿主完整进程表。/proc/<pid>/environ 里常躺着 token。配合 CAP_SYS_PTRACE 能注入；/proc/<pid>/root/ 能穿透到那个进程的 mount ns。
  • 自查：正常容器 ps 是个位数；几百个进程就是共享了宿主 PID ns。

hostNetwork: true

  • NetworkPolicy 对它无效。能访问只听 127.0.0.1、往往没做认证的服务（kubelet 只读端口、本地 Redis、云元数据代理）。
  • 自查：ip addr 看到宿主全部网卡而不是一张 eth0。

hostIPC 与云元数据

  • hostIPC 可读宿主 System V 共享内存。公有云 169.254.169.254 默认对节点上所有 Pod 可达——强制 IMDSv2 + 网络策略拦截。这条在真实入侵链里比内核漏洞更常见。

7.6 内核漏洞：共享内核意味着内核漏洞就是逃逸漏洞

这一条没有「检测配置」，只有版本管理。Dirty COW、Dirty Pipe 都能在容器内直接利用，无需特殊配置——因为容器和宿主跑的是同一份内核代码。runC 的 CVE-2019-5736 用 /proc/self/exe 覆盖宿主 runc，说明运行时本身也是攻击面：容器进程看到的「自己」其实是宿主上那个特权二进制。

无法靠配置消除，只能三件事管理：① 补丁节奏（能量出集群最旧的内核，而不是只看「最新那台」）；② 开 user ns，降低利用价值；③ 不可信负载换 gVisor / Kata。「容器不是安全边界」指的就是这一条——对配置良好的自有服务不成立，对隔离敌意代码则完全成立。前五条是配置错误，这一条才是架构税。

8.3 第三层：换掉共享内核

维度普通容器（runc）gVisor（runsc）Kata Containers

8.4 两个较新的机制

Landlock（5.13+）：非特权进程给自己上锁

  • 普通进程无需特权就能给自己加文件系统规则（后续版本扩到网络、作用域），规则不可撤销、exec 后继承。正好补上 seccomp 看不见路径的洞：你可以允许 open，但只允许打开 /etc/myapp.conf 和自己的数据目录。
  • 它是「进程自愿收紧」，不是管理员强制：适合解释器、插件宿主、处理不可信文件的工具在进入危险阶段前把自己锁死。它挡不住已经拿到的 fd，也替代不了 LSM——对「别的进程能不能碰我」没有发言权。
  • 能力随内核版本递增（ABI 用 landlock_create_ruleset 的 attr 探测），代码里必须做探测并降级。生态还在成长期，发行版默认策略里几乎看不到它。

eBPF LSM（5.7+）

  • eBPF 程序挂到同一套 LSM 钩子上，可热更新、能表达「这个进程刚才做过什么」这类运行时状态——SELinux 策略是静态标签，eBPF LSM 可以按 cgroup / 容器 ID / 执行历史做动态判决。Tetragon 建立在它上面。
  • 加载仍需要 CAP_BPF / CAP_SYS_ADMIN 量级的特权，而且要过 verifier。目前更多是安全产品的底座，不是应用团队直接写 hook 的东西。生产上要管好谁能 bpf()：容器默认 seccomp 已经把它挡掉，不要为了「观测」把这条豁口重新打开给业务 Pod。

9.3 服务上线前的安全 checklist

身份与权限

  • 进程不以 root 运行；镜像里显式 USER，K8s 里 runAsNonRoot: true（两处都写，防止镜像被换）。
  • --cap-drop=ALL，需要的 capability 逐个列出并写清理由；清单里没有 SYS_ADMIN。
  • no_new_privs / allowPrivilegeEscalation: false 已开。
  • 镜像里没有 setuid/setgid 二进制（构建时 find / -xdev -perm -4000 -type f -exec chmod u-s {} +）。
  • 代码里如果自己降权：setgroups → setgid → setuid 顺序正确、每一步检查返回值、事后 getresuid 复验。

隔离与文件系统

  • 根文件系统只读，可写目录用 tmpfs / 卷显式列出，并带 noexec,nosuid。
  • 没有 privileged、hostPID、hostNetwork、hostIPC。
  • 没有挂载 docker.sock / containerd.sock / 宿主 / / /etc / /var/run。
  • 必须挂的 hostPath 全部 readOnly: true，且路径尽可能具体（不要挂目录的父级）。
  • 已评估 user namespace 重映射（新集群建议直接开）。

系统调用与 MAC

  • seccompProfile: RuntimeDefault 已显式写上（不写就是 Unconfined）；高价值服务再上自定义白名单。
  • 自定义 seccomp profile 经过 LOG → ERRNO → KILL 三阶段灰度，且覆盖了错误分支与优雅退出路径。
  • SELinux 处于 Enforcing（或 AppArmor profile 处于 enforce），没有人为 disable。
  • 换基础镜像 / 升级 libc 后重新验证过 seccomp 白名单。

可观测与应急

  • auditd 规则已加载（auditctl -s 里 lost = 0），日志实时转发到集群外。
  • 运行时检测（Falco / Tetragon）已部署，至少一条规则做过端到端演练——不要等真出事才发现告警通道是断的。
  • 内核与容器运行时纳入常规补丁节奏，能回答「集群里最旧的内核是哪台、落后多少」。
  • 准入控制（Pod Security Standards / OPA / Kyverno）在集群侧兜底，不依赖每个团队自觉。
  • 云环境已强制 IMDSv2 并用网络策略拦住 169.254.169.254。
这份 checklist 的排序不是随意的：越靠前的越便宜、收益越大。如果只能做三件事，选非 root 运行、cap-drop ALL、只读根文件系统——这三条加起来改不了十行 YAML，却能让绝大多数「拿到 RCE 之后」的常规操作（装工具、落 webshell、改二进制、提权）全部失败。安全预算永远有限，先把这种投入产出比的事做完。

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础DAC 和 MAC 有什么区别？为什么有了 DAC 还要 MAC？

    DAC（自主访问控制）：权限由客体的属主自行决定——你的文件你想给谁看就给谁看，内核不干涉这个决定。Linux 的 uid/gid + 权限位就是 DAC。

    MAC（强制访问控制）：权限由系统级策略规定，属主无权修改，root 也不例外。SELinux、AppArmor 通过 LSM 框架实现。

    为什么需要 MAC，两个 DAC 补不上的洞：

    • 「自主」本身就是弱点：一个 chmod 777 就把防线拆了，而这可能是运维手滑，也可能是被攻陷的进程主动做的。
    • 粒度太粗：DAC 只认「属主 / 组 / 其他」三档。Web 服务被打穿后，攻击者以 apache 身份运行，DAC 下他能碰所有 apache 能碰的东西——包括其他站点的数据、日志、临时目录。MAC 下他被锁在 httpd_t 这个 type 里，策略没写 allow 的一律拒绝。
    一句话总结
    DAC 防的是「用户之间互相看」，MAC 防的是「一个被攻陷的进程能做多少事」。前者假设用户是善意的，后者不做这个假设。
    顺序很重要
    LSM 钩子在 DAC 和 capabilities 检查之后。所以 MAC 只能收紧不能放宽——DAC 已经拒绝的请求根本走不到 LSM。这个单调性保证了「加上 SELinux 最坏是把服务搞挂，不会悄悄开出一个洞」。
  2. 基础目录的 x 权限是什么含义？和 r 有什么区别？
    • r = 列出目录里有哪些名字（readdir）。没有它，ls 失败，但已经知道名字的文件仍然能访问。
    • x = 穿越——按名字把路径解析下去（stat、open、cd）。没有它，整棵子树完全不可达，连 stat 一个已知文件名都是 EACCES。
    • w（须配合 x）= 增删改名目录项。删除一个文件看的是它所在目录的 w，不是文件自己的权限——这一点最反直觉。

    所以 chmod 711 /home/alice 是一个有意义的配置：别人列不出你有哪些文件，但你可以把某个具体路径告诉他让他访问。

    最实用的推论
    路径解析要求路径上每一级目录都有 x。「文件明明是 644 却读不了」的头号原因就在上层某个目录。排查一条命令搞定：namei -l /path/to/file，它把每一级的权限和属主一行行列出来，断在哪一目了然。
    延伸
    /tmp 的 1777 里那个 1 是 sticky 位，正是为了堵住「目录 w = 能删别人文件」这个洞：加上它之后，只有文件属主（或目录属主、或有 CAP_FOWNER）才能删除。
  3. 基础进程为什么有三套 uid？setuid 程序里它们是怎么变化的？
    • real uid：你是谁，代表进程的真实归属，决定谁能给它发信号。
    • effective uid：你现在以谁的身份行事——所有权限检查用的都是它。
    • saved set-user-ID：execve 时保存的备份，让进程能在特权与非特权之间来回切而不丢失恢复能力。

    执行一个 setuid-root 程序（属主 root、模式 4755）时：ruid = 调用者的 uid（如 1000），euid = 文件属主 = 0，suid = euid = 0。之后 seteuid(1000) 可以临时放弃特权，因为 suid 还是 0，随时能 seteuid(0) 切回来。

    必须记住的铁律
    永久降权时顺序是 setgroups(0,NULL) → setgid → setuid，绝对不能反。因为 setuid() 在 euid==0 时会把三套 uid 一次性全设成目标值，这一步之后你不再是 root，后面的 setgid 会返回 EPERM。而绝大多数代码不检查这两个函数的返回值，于是进程以「uid 降了、gid 还是 0」的状态继续跑——特权只降了一半，是教科书级的提权漏洞模式。
    更好的写法
    用 setresuid / setresgid，三个值全部显式写出来。setuid 的语义取决于当前 euid 是不是 0（是则改三套，否则只改 euid），这种「行为随上下文变化」的 API 是漏洞温床。降完还要用 getresuid 复验，并试着 setuid(0)——能成功就说明没降干净。
  4. 基础capabilities 解决了什么问题？举两个常用的例子。

    它解决的是 root 全有全无的问题。传统 Unix 只有两类进程：uid 0 的（内核跳过绝大多数检查）和其他的。一个只需要 bind(80) 的 Web 服务器，为了那一个动作被迫拥有格式化磁盘、加载内核模块、读任意进程内存的能力——任何一个内存漏洞的收益都被放大到最大。

    capabilities 把 root 的特权切成 40 多个独立的位，按需授予。两个典型：

    • CAP_NET_BIND_SERVICE——绑定 1024 以下端口。最经典的「只需要这一个」场景，用 setcap 'cap_net_bind_service=+ep' ./myserver 就能替代整个 setuid-root。
    • CAP_NET_RAW——创建 RAW/PACKET socket，ping 和 tcpdump 需要它。反过来说，普通业务容器应该 drop 掉它，因为它能嗅探同网段流量、做 ARP 欺骗。
    必须一起说的一句
    CAP_SYS_ADMIN 约等于 root。它是历史上的垃圾桶，新特权操作找不到分类就往里塞，累积到今天覆盖一百多个操作，其中好几条（挂载文件系统、setns、cgroup v1 写 release_agent）可以直接换成完整 root。所以「只给它 SYS_ADMIN」不算最小权限。
    怎么看
    getcap 看文件、capsh --print 看当前进程、grep Cap /proc/PID/status 加 capsh --decode=<hex> 看某个正在跑的服务。

10.2 中级（区分熟练度）

  1. 中级capabilities 的五个集合分别是什么？execve 时怎么计算？
    集合含义
    Permitted被允许持有的上限，可随时往 Effective 里加（「钱包里有多少钱」）
    Effective内核当下真正检查的集合（「手里正拿着多少」）
    Inheritable与文件的 Inheritable 求交后可跨 execve 保留（需要「对方也同意」）
    Bounding天花板：这里没有的任何途径都拿不到；只减不增且不可逆
    Ambient（4.3+）能无条件跨过 execve，专为「非 root 且目标文件没有文件 cap」设计

    execve 后的计算（不含 root / setuid 特例）：

    P′(ambient)     = 文件带特权(setuid 或文件 cap) ? 0 : P(ambient)
P′(permitted)   = (P(inheritable) & F(inheritable))
                | (F(permitted)   & P(bounding))
                | P′(ambient)
P′(effective)   = F(effective) ? P′(permitted) : P′(ambient)
P′(inheritable) = P(inheritable)      P′(bounding) = P(bounding)
    三条足够用的结论
    ① 权限检查只看 Effective；② Bounding 是硬天花板，PR_CAPBSET_DROP 掉的位再也回不来——这正是它作为安全边界的价值；③ Inheritable 要传下去必须进程和文件双方都标了这一位，而普通脚本和解释器根本没有文件 cap，所以 Ambient 出现之前非 root 进程无法把能力传给自己 exec 的子程序，Ambient 就是补这个洞。
    高频实战坑
    代码里降权时忘了 prctl(PR_SET_KEEPCAPS, 1, …)。默认情况下 euid 从 0 变成非 0 时内核会清空 Permitted 和 Effective，所以必须先 KEEPCAPS 保住钱包，降完 uid 再从 Permitted 里挑要留的，否则 cap_set_proc 直接 EPERM。另外文件 cap 存在扩展属性里，cp 默认不保留——「本地好好的、打进镜像就绑不了端口」多半是这个。
  2. 中级seccomp 为什么必须先设置 no_new_privs？

    因为不这么要求的话，普通用户可以发起一次混淆代理人（confused deputy）攻击。关键在于 seccomp 过滤器会被 execve 继承：

    1. 攻击者（普通用户）先给自己装一个过滤器，让 setgroups() 静默返回成功（SECCOMP_RET_ERRNO(0)）。
    2. 然后 execve 一个 setuid-root 的程序。
    3. 那个特权程序按标准写法降权：setgroups(0,NULL)「成功」了（其实没生效）、setuid(user) 真的降了。
    4. 结果：uid 降了，但附加组还留着 root 的——特权程序在毫不知情的情况下被诱导留下了一个提权缺口。

    no_new_privs 是一个一旦置位就无法清除、且被子进程继承的标志，置位后 execve 不再因 setuid 位或文件 capability 提升权限。于是攻击者无论怎么扭曲系统调用语义，被坑的只有自己。所以内核的规则是：装 filter 要么有 CAP_SYS_ADMIN，要么 no_new_privs 已置位。

    怎么验证
    grep -E 'NoNewPrivs|Seccomp' /proc/self/status：NoNewPrivs: 1 且 Seccomp: 2（2 = filter 模式）。K8s 的 allowPrivilegeEscalation: false 设的就是这个位，systemd 里对应 NoNewPrivileges=yes。
    延伸
    这个设计体现了一条通用原则：「让低权限主体去影响高权限主体的行为」是所有权限模型都要堵的洞。LD_PRELOAD 对 setuid 程序失效、sudo 清洗环境变量、动态链接器对特权进程忽略某些路径，全是同一个模式的不同表现。
  3. 中级写 seccomp 白名单时最容易踩哪些坑？
    ① 拦到了 libc 内部用的调用
    你代码里一次都没写 futex，但只要用了 std::mutex 或某些惰性初始化就会调它；getrandom 被 glibc 的 malloc 和栈保护初始化用到；clock_gettime 在有 vDSO 时不走系统调用，换一台没配好 vDSO 的机器就走了——「同样的二进制在 A 机器好好的、B 机器一起来就 SIGSYS」。症状是进程无预警消失，dmesg 里一行 seccomp ... syscall=228，用 ausyscall 228 把号翻出来。
    ② 系统调用号是架构相关的
    x86-64 上 read=0，aarch64 上 read=63，直接搬数字等于随机放行。必须用 libseccomp 的 SCMP_SYS() 宏。更隐蔽的是 x86-64 上还有 i386 兼容 ABI 和 x32 ABI，调用号完全是另一套——不显式 seccomp_arch_add 就等于留了后门，这是历史上被多次利用的绕过手法。systemd 里对应 SystemCallArchitectures=native。
    ③ libc / 基础镜像升级后白名单失效
    glibc 在不同版本里可能把 open 换成 openat、stat 换成 newfstatat、poll 换成 ppoll。「什么都没改，换个基础镜像就挂」的常见根因，所以换基础镜像必须重新采集。
    正确流程
    先把默认动作设成 SCMP_ACT_LOG（放行 + 记日志），跑完整的功能与压测，包括错误分支、重连、优雅退出；用 ausearch -m SECCOMP 把实际用到的调用捞出来；人工审阅一遍（采集到的是「跑过的」不是「需要的」，看到 ptrace/mount 要先问为什么）；然后按 LOG → ERRNO(EPERM) → KILL_PROCESS 灰度。直接上 KILL 是拿线上做测试。
    还要知道的一条局限
    seccomp 只能看标量参数，不能解引用指针——这是刻意设计（否则有 TOCTOU：过滤器检查完之后另一个线程可以改掉那块内存）。所以「只允许打开某个路径」seccomp 做不到，那是 LSM 和 Landlock 的活。
  4. 中级SELinux 报 AVC denied，你的排查流程是什么？为什么不能直接关掉？

    排查流程（按顺序走）：

    1. ausearch -m AVC,USER_AVC -ts recent -i 找到那条记录。
    2. 逐字段读：denied { read } 是被拒的操作，scontext 是谁（进程的 type，如 httpd_t），tcontext 是对谁（客体的 type），tclass 是客体类别，permissive=0 表示真的拒了。
    3. audit2why 看内核给的解释——它会告诉你是不是有现成的 boolean 可以开。
    4. 按优先级处理：① matchpathcon 确认「应有的 label」，restorecon -Rv 修复；② getsebool -a 找现成开关，setsebool -P 打开；③ 非默认路径/端口用 semanage fcontext / semanage port 登记；④ 实在没有才用 audit2allow 写策略，而且先只打印不安装，逐条审掉 sys_admin、unlabeled_t 这类过宽规则。
    最常见的根因
    label 不对，而 label 不对的头号成因是用了 mv 而不是 cp：mv 在同一文件系统内只改目录项，label 原样跟着走；cp 创建新 inode，按目标路径规则打新标签。所以「从家目录 mv 一个网页到 /var/www」必然出问题。这也是「权限明明 777 却还是 Permission denied」的标准答案。
    为什么不能 disabled
    SELINUX=disabled 之后内核停止维护文件 label，期间新建和修改的文件全都没有正确 type。等哪天要重新开启（比如一次合规检查），整个文件系统的 label 已经烂了，开机后大量服务起不来，只能全盘 restorecon -R /——TB 级文件系统上这是几小时的停机。临时手段永远用 setenforce 0（Permissive）：不拦截但照常记录，label 继续维护，你既能让业务先跑，又拿到了完整的「要放开哪些」清单。

10.3 高级（体现深度）

  1. 高级namespace 到底没有隔离什么？这对容器安全意味着什么？

    先说最重要的一条：namespace 不隔离内核。宿主和所有容器共用同一份内核代码、同一份内核数据结构、同一张系统调用表。除此之外还有一批共享项：

    • 大部分 sysctl 是全局的。只有 net.*（netns）、kernel.hostname（utsns）、System V IPC 与 fs.mqueue.*（ipcns）等少数被命名空间化了。vm.max_map_count、fs.file-max、kernel.pid_max、kernel.core_pattern 全是全局的——所以 Elasticsearch 容器要求你在宿主上改 vm.max_map_count。
    • 内核 keyring只部分隔离；/sys/kernel、内核模块列表、硬件与 CPU 微架构状态（Spectre/Meltdown 类侧信道）完全共享。
    • time namespace（5.6+）只虚拟化 CLOCK_MONOTONIC / CLOCK_BOOTTIME 的偏移，墙上时间不隔离。
    • 物理资源：CPU 缓存、内存带宽、磁盘 IOPS、网卡队列——cgroup 能限额，但不能消除互相干扰。
    最直接的后果
    任何内核提权漏洞都直接是容器逃逸漏洞。Dirty COW（CVE-2016-5195）、Dirty Pipe（CVE-2022-0847）在容器里打和在宿主上打没有区别，不需要任何特殊配置。这就是「容器不是安全边界」这句话的真实含义——它对配置良好的自有工作负载不成立，对「拿容器隔离敌意代码」的场景则完全成立。
    怎么应对
    三条，按成本递增：① 补丁节奏——把内核与运行时纳入常规更新，并能度量「集群里最旧的内核是哪台」；② 开 user namespace，让逃逸拿到的是 uid 100000 而不是 root，降低利用价值；③ 对真正不可信的负载换 gVisor 或 Kata，把内核攻击面本身换掉。
  2. 高级user namespace 为什么既是加固手段又是攻击面？

    它是唯一一个普通用户无需特权就能创建的 namespace。在新的 user ns 里进程可以是 uid 0 并拥有该 namespace 内的全套 capability，但这些 capability 只对同属这个 namespace 的资源有效——内核做检查时会把「ns 内 root」翻译回宿主 uid。

    加固的一面：没有 user ns 时，容器里的 root 就是宿主的 root（uid 都是 0），只要有任何一条路径碰到宿主文件就是完整沦陷。开了之后容器 root 在宿主上只是 uid 100000，逃逸收益从「宿主 root」降级成「一个没有任何权限的陌生用户」。这是 Podman rootless、rootless Docker、K8s hostUsers: false 的核心价值。

    攻击面的一面：为了让「ns 内 root」这件事成立，普通用户获得了触达大量过去只有 root 才走得到的内核代码路径的能力——文件系统挂载解析、网络栈配置、cgroup 操作、setns…这些路径历史上的审计强度远低于常规路径（假设「反正只有 root 能走」），于是过去十年出现了相当数量以「非特权用户创建 user ns」为前置条件的本地提权 CVE。所以不少发行版做了限制：user.max_user_namespaces、Debian 的 kernel.unprivileged_userns_clone、较新 Ubuntu 的 kernel.apparmor_restrict_unprivileged_userns。

    这两件事经常被混为一谈，要分开看
    「给容器开 user ns」是明确的加固；「允许宿主上任意用户随便创建 user ns」是明确的风险。合理配置是两者兼顾：容器运行时用它，同时用 sysctl / AppArmor 限制普通用户滥用。
    落地代价
    Docker 的 userns-remap 与 --privileged、--pid=host、--net=host 以及部分卷挂载场景不兼容，已有卷的文件属主也会对不上（宿主看是 100000）。新集群从一开始就开最省事，中途切换要做迁移评估。另外写 gid_map 前必须先 echo deny > /proc/PID/setgroups，否则返回 EPERM——原因是不禁掉 setgroups 的话进程可以丢掉某个附加组，绕过「deny 某组」类的负权限规则。
  3. 高级为什么说 --privileged 容器等于没有容器？挂 docker.sock 的风险呢？

    --privileged 一次性做了五件事：capability 全给、seccomp profile 换成 unconfined（很多人只知道前半句）、AppArmor/SELinux 约束解除、/sys 变可写、宿主所有设备节点在 /dev 下可见。有了这些，容器里的 root 能直接看到宿主块设备并挂载它——宿主根文件系统就在眼前，写 authorized_keys 或投个 cron 都是顺手的事。剩下的只有 namespace 提供的「视图隔离」，而视图隔离对一个能挂载宿主磁盘的进程毫无意义。

    挂 docker.sock 比它更隐蔽，因为看起来「只是挂了一个文件」，而且 CI runner、监控面板的官方文档里到处都是这个写法。推理链只有三步：这个 socket 是 Docker 守护进程的完整控制 API → 通过它可以创建新容器且参数由你指定 → 于是可以创建一个 privileged 的、把宿主 / 挂进去的容器。不需要任何漏洞，这就是 API 的正常功能。containerd.sock、crio.sock、宿主上的 docker 组成员身份，全都等价于宿主 root。

    自查命令
    grep CapEff /proc/self/status 看到满值（如 0000003fffffffff）+ Seccomp: 0 + ls /dev 有上百项且能看到 /dev/sda —— 三条对上就是特权容器。socket 用 ls -l /var/run/docker.sock 和 mount | grep sock；顺带 id 看看在不在 docker 组。集群侧用 kubectl get pods -A -o json | jq 把 privileged=true 和挂了 /var/run 的 hostPath 全捞一遍。
    怎么修
    DinD 场景换 Kaniko / buildah / BuildKit rootless（不需要守护进程）；监控日志场景用只放行只读接口的 API 代理而不是把裸 socket 递进去；「我要设 sysctl / 挂 fuse / 用某个设备」这类需求几乎总能收窄到 --sysctl、--device、或宿主侧预备资源再挂进来。集群侧用 Pod Security Standards 的 restricted 档在准入时直接拒绝，别依赖每个团队自觉。
  4. 高级什么情况下需要 gVisor 或 Kata？它们各自的原理和代价是什么？

    先说判据，因为这是最容易答偏的地方：需不需要它们，取决于你是否要在同一台机器上运行「你不信任的代码」——用户提交的构建脚本、多租户函数计算、来路不明的第三方镜像。对「跑自己写的服务」的团队，把非 root、cap-drop ALL、只读根文件系统、RuntimeDefault seccomp 这几条落实到位，收益远大于换运行时且不用付性能账。

    gVisor（runsc）Kata Containers
    原理用户态内核：Sentry 进程用 Go 重新实现了大部分 Linux 系统调用语义，容器的调用先被拦到 Sentry；Sentry 自己再套一层很窄的 seccomp，宿主内核只剩几十个调用暴露给它每个 Pod 一个轻量 VM（Firecracker / QEMU），里面跑独立的 guest 内核，边界由硬件虚拟化强制
    攻击面宿主内核只对 Sentry 暴露一小部分；但 Sentry 自己是新代码，也有自己的漏洞面只暴露 hypervisor 接口，最小，且是硬件边界
    主要代价系统调用开销明显更高（多一层用户态转发），I/O 与 syscall 密集负载受影响大；兼容性不完整——冷门系统调用、部分 /proc /sys 项、某些 ioctl 不支持，上线前必须真跑一遍内存开销大（每 Pod 一份 guest 内核 + rootfs，上百 MB 起）、启动慢、I/O 要过 virtio；需要硬件虚拟化支持，嵌套虚拟化环境可能不可用
    适合多租户 SaaS、跑用户提交的代码、函数计算——负载偏计算、系统调用不密集时性价比最好强合规、强多租户、需要硬件级隔离保证；也更适合「必须完整内核兼容性」的负载
    共同的取舍本质
    两者都是在用性能和运维复杂度换一个更小的内核攻击面。gVisor 换的是「更少的宿主内核代码被触达」，Kata 换的是「一道硬件强制的边界」。K8s 里用 RuntimeClass 按工作负载选择，不必全集群一刀切——把不可信负载调度到 gVisor/Kata 节点池，可信负载留在 runc 上，是常见且合理的混合方案。
    别忘了它们不解决什么
    它们只解决「内核共享」这一条。挂了 docker.sock、把宿主目录挂进去、凭据写在环境变量里——这些问题换什么运行时都一样存在。先把配置层做对，再谈换运行时。
