Linux 安全模型

同一台机器上，内核凭什么决定「这个进程能不能做这件事」？这篇把答案拆成五层—— seccomp 收窄系统调用面、DAC 看属主与权限位、capabilities 把 root 切成碎片、LSM 让策略压过属主、namespace 划出可见范围—— 再用它们去解释「容器到底隔离了什么、又漏了什么」。
与另一篇的分工：C++ 安全加固指南讲的是代码层面的安全（内存漏洞、编译期硬化、sanitizer、供应链）； 本篇讲操作系统层面的安全模型——即使你的代码被攻破，攻击者能拿到什么，由这一层决定。
对位读者：需要为服务设计最小权限、或需要回答「容器到底隔离了什么」的后端与平台工程师。

01

权限检查发生在哪

一次 open() 要连过五道关卡

大多数人对 Linux 权限的理解停留在 chmod 644。但真实内核里，一次普通的 open("/etc/shadow", O_RDONLY) 要依次通过五道独立的关卡，任何一道拒绝，系统调用就失败——它们是「与」的关系，不是「或」。这一点必须先建立，否则后面所有排障都会走偏：「我 chmod 777 了为什么还是 Permission denied」这个经典问题，答案永远是「你只打开了第二道门」。

进公司大楼要过五道关：门禁闸机（seccomp——你这张卡根本没被允许刷这台机器）、工位归属（DAC——这个抽屉是不是你的）、职级牌（capabilities——你有没有「可以开别人抽屉」的特权）、公司红头文件（MAC——就算抽屉是你的，制度规定研发不得带出财务资料）、楼层可见性（namespace——你的门禁卡只能到 3 楼，其他楼层对你来说根本不存在）。五道全过才进得去；任意一道不过就是「Permission denied」，而且错误码通常长得一模一样，这正是排障最难的地方。

为什么要这么多层

每一层的出现都是为了补上一层的洞，这个演化顺序值得记住：

层它补的洞它自己的短板引入时间
DAC（uid/gid + mode）最基本的多用户隔离粒度太粗：只有「属主/组/其他」三档；而且属主可以随意放宽，一个 chmod 777 就把防线拆了Unix 诞生起
capabilitiesroot 是全有全无：一个只想绑 80 端口的进程被迫拿到格式化磁盘的能力拆分粒度仍然不均，CAP_SYS_ADMIN 成了新的垃圾桶（约等于 root）Linux 2.2（1999）
seccomp系统调用面太宽：内核有 300+ 个入口，你的进程可能只用 40 个，其余全是白送的攻击面只能看系统调用号和寄存器里的标量参数，看不到指针指向的内容（TOCTOU）2.6.12 strict / 3.5 filter
LSM / MACDAC 归属主管，属主自己会犯错；需要一套属主也改不了的策略策略编写与维护成本高，出问题时排查链路长Linux 2.6（2003）
namespace前四层都在「同一个世界」里做判断，缺少看不见这个更强的隔离共享同一个内核——内核漏洞面完全没有被隔离2.4.19 起逐步加入，3.8 补齐 user ns
五层的心智模型可以压成一句话：seccomp 决定「你能敲哪些门」，DAC 决定「门是不是你家的」，capabilities 决定「你有没有万能钥匙」，LSM 决定「制度允不允许你开这扇门」，namespace 决定「你在哪一栋楼里」。面试里能把这五句说清楚，基本就赢了一半。
面试加分点：被问「Linux 权限体系」时，绝大多数人只会答 DAC 和 root。真正区分度在于说清顺序与关系——① seccomp 在系统调用入口，比一切都早，所以它拒绝时你连 EACCES 都拿不到，而是 SIGSYS 或指定的 errno；② DAC 拒绝后 capabilities 还能翻盘（这正是 CAP_DAC_OVERRIDE 的定义）；③ 但 LSM 拒绝没有任何东西能翻盘，连 root 都不行——这就是 MAC 相对 DAC 的本质差别。
本篇的定位是操作系统层。如果你关心的是「怎么让 C++ 代码本身不出内存漏洞、怎么开编译器硬化选项、怎么管依赖供应链」，那是另一篇的范围：C++ 安全加固指南。两者是纵深防御的两端——代码层降低「被攻破」的概率，系统层降低「被攻破之后的损失」。真实事故里后者往往更值钱：漏洞永远修不完，但一个跑在 nobody + 空 capability 集 + seccomp 白名单里的进程，即使被 RCE 也基本什么都干不了。
02

传统 DAC：属主说了算

看似人人都懂，细节处处是坑

DAC（Discretionary Access Control，自主访问控制）：访问权限由客体的属主自行决定。你的文件，你想给谁看就给谁看，内核不干涉这个决定。「自主」这个词是关键——它同时是 DAC 的便利之处和它的根本弱点。

2.1 权限位：目录的 r 和 x 完全是两回事

文件的 rwx 很直观，目录的 rwx 才是真正的考点，也是生产上最常见的误解来源：

位对普通文件对目录没有它会怎样
r读内容列出目录里有哪些名字（readdir）ls 失败，但已知名字仍能访问
x执行穿越——按名字解析进去（stat/open/cd）整棵子树全部不可达，连 stat 都是 EACCES
w写内容增删改名目录项（必须同时有 x）无法创建/删除文件——注意：删文件看的是目录的 w，不是文件自己的权限
 
# 只给 x 不给 r —— 经典的「知道名字才进得去」目录
$ chmod 711 /home/alice
$ sudo -u bob ls /home/alice
ls: cannot open directory '/home/alice': Permission denied   # 缺 r，列不出来
$ sudo -u bob cat /home/alice/public.txt
hello                                                        # 有 x，知道名字就能穿越进去

# 反过来：只给 r 不给 x —— 看得见名字，什么都打不开
$ chmod 744 /home/alice
$ sudo -u bob ls /home/alice
ls: cannot access '/home/alice/public.txt': Permission denied
public.txt                                                   # 名字列得出，stat 全失败
路径解析要求路径上每一级目录都有 x。这是「文件明明 644 却读不了」的头号原因——问题不在文件，在它上面某一层目录。排查手法：namei -l /path/to/file 会把每一级的权限、属主一行行列出来，一眼就能看到断在哪。别再一层层 ls -ld 手动看了。
$ namei -l /srv/app/data/config.yaml
f: /srv/app/data/config.yaml
 drwxr-xr-x root root /
 drwxr-xr-x root root srv
 drwxr-x--- root deploy app        # ← 就是这一级：other 没有 x
 drwxr-xr-x deploy deploy data
 -rw-r--r-- deploy deploy config.yaml

2.2 umask：新文件权限的减法

umask 不是「默认权限」，而是要减掉的权限位。内核创建文件时用 mode & ~umask。程序传给 open 的 mode 通常是 0666（普通文件）或 0777（目录/可执行），umask 再从中扣掉：

$ umask
0022
$ touch a.txt && ls -l a.txt
-rw-r--r--  # 0666 & ~0022 = 0644

$ umask 0077 && touch b.txt && ls -l b.txt
-rw-------  # 0666 & ~0077 = 0600，只有自己能读

# ⚠ umask 是进程属性，会被子进程继承。守护进程务必自己显式设置，
#   不要指望继承来的值 —— systemd 启动的服务默认 umask 是 0022，
#   而从交互 shell 手动跑可能是 0002，同一份代码在两种环境下产出的
#   文件权限不同，是「本地好好的、线上文件全组可写」的常见成因。
umask 只能减不能加。所以 open(path, O_CREAT, 0777) 在 umask 022 下拿到的是 0755——想要精确的权限，必须 open 之后再 fchmod，或者临时改 umask（记得改回来，而且它不是线程安全的）。更稳的做法是 open 时就用 0600 这种保守值，需要放宽再显式 fchmod——先关紧再开门，永远比先敞开再关门安全，因为后者中间有一个别人能抢进来的时间窗。

2.3 setuid / setgid / sticky：三个特殊位

位八进制对可执行文件对目录看起来像
setuid4000以文件属主的身份运行（典型 passwd 需要写 /etc/shadow）Linux 上忽略-rws r-x r-x
setgid2000以文件属组的身份运行新建文件继承目录的属组（团队共享目录靠它）drwx r-s r-x
sticky1000现代内核忽略只有文件属主（或目录属主、或有 CAP_FOWNER）能删除/改名drwx rwx rwt
/tmp 为什么是 1777：777 是因为所有人都要能在里面建自己的临时文件；前面那个 1（sticky）是为了堵住随之而来的洞——没有它，「所有人可写的目录」意味着任何用户都能删掉别人的文件（删除权看的是目录的 w）。sticky 位把删除权收窄回「只能删自己的」。ls -ld /tmp 看到的那个 t 就是它。
/tmp 依然是危险区。sticky 位只管删除，不管创建。攻击者可以抢先创建一个你的程序即将使用的固定文件名（或指向敏感文件的符号链接），你的程序 open(O_CREAT) 时就写进了攻击者控制的位置——这就是经典的 symlink attack / TOCTOU。对策：一律用 mkstemp()（内核保证原子创建且 0600）或 O_CREAT|O_EXCL|O_NOFOLLOW，永远不要用固定的临时文件名；服务级别再叠一层 systemd 的 PrivateTmp=yes，让这个进程看到的 /tmp 是它专属的。内核侧还有 fs.protected_symlinks=1 / fs.protected_hardlinks=1（现代发行版默认开启）作为兜底。

2.4 进程的三套 uid：real / effective / saved

每个进程有三个 user ID（gid 同理还有三个），外加 Linux 特有的第四个 fsuid：
  • real uid（ruid）：你是谁——登录时确定，代表进程的真实归属，决定谁能给它发信号。
  • effective uid（euid）：你现在以谁的身份行事——所有权限检查用的都是它。
  • saved set-user-ID（suid）：execve 时保存的一份「备份」，让进程能在特权与非特权之间来回切而不丢失恢复能力。
  • fsuid：仅用于文件系统访问检查，通常自动跟随 euid。历史上给 NFS 服务器用，普通程序不必碰。
三套 id 像「员工卡 + 临时授权牌 + 存在前台的原卡」：员工卡（real）证明你是张三；干某件事时前台发你一块「代行主管职权」的牌子（effective），门禁只认这块牌；原来那张主管牌存在前台（saved），你随时可以换回来。setuid 系列调用干的就是换牌这件事，而「换完还能不能换回来」，取决于前台那张还在不在。
// 执行一个 setuid-root 程序（属主 root，模式 4755）时，内核这样设置：
//   ruid = 调用者的 uid（比如 1000）
//   euid = 文件属主的 uid（0）      ← 权限检查看这个
//   suid = euid = 0                 ← 备份，用于来回切换

// ── 临时放弃特权（还能拿回来）─────────────────────
seteuid(ruid);        // euid: 0 → 1000，suid 仍是 0
// …干不需要特权的活…
seteuid(0);          // 因为 suid == 0，允许切回来

// ── 永久放弃特权（不可逆）─────────────────────────
if (setuid(0) == 0) { /* 确认自己确实是 root */ }
setgroups(0, nullptr);   // ★① 先清空附加组，否则 wheel/docker 组还留着
setgid(target_gid);       // ★② 再降 gid
setuid(target_uid);       // ★③ 最后降 uid —— 顺序绝对不能变
「先 setgid 后 setuid」是一条铁律，搞反了是教科书级的提权漏洞。setgid() 需要特权才能改成任意组；而 setuid() 在 euid==0 时会把三套 uid 一次性全设成目标值，这一步之后你不再是 root。所以如果先 setuid(1000) 再 setgid(1000)，第二步会直接失败返回 EPERM——而绝大多数代码不检查这两个函数的返回值，于是进程就以「uid=1000 但 gid 还是 0」的状态继续跑。gid=0 意味着它对所有 root 组可写的文件仍有写权限，特权只降了一半。同样的道理，setgroups(0, NULL) 必须排在最前面：附加组列表也只有特权进程能清空。
❌ 顺序错 + 不检查返回值
setuid(uid);          // 已经不是 root 了
setgid(gid);          // 静默失败，gid 还是 0
// 附加组也没清，docker 组还在 →
// 等价于没降权（能连 docker.sock）
run_untrusted_code();
✅ 顺序对 + 一律校验 + 事后复查
if (setgroups(0, nullptr) != 0) abort();
if (setresgid(gid, gid, gid) != 0) abort();
if (setresuid(uid, uid, uid) != 0) abort();

// ★ 事后主动验证降权真的生效了
uid_t r, e, s;
getresuid(&r, &e, &s);
if (r != uid || e != uid || s != uid) abort();
// 再试着切回 root，成功就说明没降干净
if (setuid(0) == 0) abort();
用 setresuid / setresgid 而不是 setuid / setgid。后者的语义取决于当前 euid 是不是 0——euid==0 时改三套，否则只改 euid。这种「行为随上下文变化」的 API 是漏洞温床。setresuid(r, e, s) 把三个值全部显式写出来，读代码的人一眼就知道结果是什么，不需要在脑子里推演当前特权状态。

2.5 为什么现代做法是尽量不用 setuid 二进制

setuid 程序是一个用户可以任意控制输入、却以 root 身份运行的攻击面，而且这个攻击面比想象中大得多——不只是命令行参数：

继承来的一切都不可信

环境变量（LD_PRELOAD、PATH、IFS、locale）、已打开的 fd、当前工作目录、rlimit、umask、信号处置——全部由调用者控制。动态链接器对 setuid 程序会忽略 LD_PRELOAD，但你自己 system() 出去的子进程可不会。

权限是全量的

passwd 只想改一个文件，却拿到了完整 root。任何一个内存漏洞的收益都被放大到最大。

三种更好的替代

① 文件 capability（setcap）——只给这一个具体能力；② systemd socket activation——特权进程绑好端口把 fd 传过去；③ 特权 helper 守护进程——通过 Unix 域套接字暴露极窄的接口，用 SO_PEERCRED 验身份。

# 盘一遍系统上所有 setuid/setgid 二进制 —— 每一个都是一份攻击面预算
$ find / -xdev \( -perm -4000 -o -perm -2000 \) -type f -printf '%M %u %g %p\n' 2>/dev/null
-rwsr-xr-x root root /usr/bin/sudo
-rwsr-xr-x root root /usr/bin/passwd
-rwsr-xr-x root root /usr/bin/mount
-rwsr-xr-x root root /usr/bin/su
-rwxr-sr-x root shadow /usr/bin/chage
# 定期 diff 这个列表：突然多出来一个，要么是包更新，要么是有人留了后门。
# 自己的镜像里应该趋近于零 —— Dockerfile 里可以直接：
#   RUN find / -xdev -perm -4000 -type f -exec chmod u-s {} +
挂载选项也是 DAC 的一部分，而且经常被忘掉：nosuid 让该文件系统上的 setuid 位失效，nodev 让设备节点失效，noexec 禁止执行。对 /tmp、/dev/shm、所有用户可写的挂载点，nosuid,nodev 应该是默认配置——即使攻击者能往里面放一个 setuid-root 文件，也执行不出特权。findmnt -o TARGET,OPTIONS 一次看全。
03

capabilities：把 root 拆开

四十多把小钥匙，替代一把万能钥匙

传统 Unix 只有两种进程：uid 0 的（想干什么干什么，内核对它跳过绝大多数检查）和其他的。这个二分法在现代服务里非常别扭——一个只需要 bind(80) 的 Web 服务器，为了那一个动作被迫拥有「加载内核模块」「格式化磁盘」「读任意进程内存」的能力。capabilities 把 root 的特权切成了 40 多个独立的位，每个位单独授予。

从「一把开遍全公司的万能钥匙」换成「一串按需配发的门禁权限」：保洁只有「所有楼层的走廊 + 卫生间」，网管只有「机房」，财务只有「档案室」。丢一把万能钥匙等于整栋楼失守；丢一张保洁卡，损失被限制在走廊。但前提是权限真的被切细了——如果有人图省事发了一张「除机房外全部楼层」的卡，那和万能钥匙没多大区别，这就是下面要说的 CAP_SYS_ADMIN。

CAP_SYS_CHROOTchroot沙箱工具中——单独看不算高，但配合其他能力是逃逸拼图的一块
CAP_SYSLOG读内核环形缓冲（dmesg）日志采集中——泄漏内核地址，破坏 KASLR
CAP_SYS_ADMIN 约等于 root，任何「只给它 SYS_ADMIN」的方案都不是最小权限。它是历史上的垃圾桶：新加的特权操作找不到合适分类就往里塞，累积到今天覆盖了一百多个不相干的操作，其中好几条可以直接换成完整 root——比如挂载文件系统（把宿主根目录挂进来）、setns（进入别的 namespace）、以及 cgroup v1 下写 release_agent。听到「这个容器需要 --cap-add=SYS_ADMIN 才能跑」，正确的反应不是批准，而是追问它到底要做哪一个操作——十有八九能换成一个更窄的 capability，或者换成宿主侧预先准备好资源再挂进去。

3.2 五个集合与 execve 的计算规则

这是 capabilities 里最容易讲糊涂、也最容易被追问的部分。每个进程有五个集合，每个带文件 capability 的可执行文件有三个集合。

集合缩写含义一句话记忆
PermittedCapPrm进程被允许持有的能力上限，可以随时从这里往 Effective 里加「钱包里有多少钱」
EffectiveCapEff内核当下真正检查的集合——只有在这里的能力才生效「手里正拿着多少钱」
InheritableCapInh与文件的 Inheritable 求交后可以跨 execve 保留「需要对方也同意才能传下去」
BoundingCapBnd天花板：这里没有的，任何途径都拿不到。只能减不能加，且不可逆「这辈子最多能有多少」
AmbientCapAmb（4.3 起）能无条件跨过 execve 的集合，专为「非 root 且目标文件没有文件 cap」设计「随身带过去，不需要对方配合」
三条足够应付面试的结论：① 检查权限时内核只看 Effective；② Permitted 是 Effective 的取值上限，Bounding 又是 Permitted 的取值上限，丢掉 Bounding 位不可逆——这正是它作为安全边界的价值；③ Inheritable 要传下去必须「进程和文件双方都标了这一位」，而绝大多数文件根本没有文件 cap，所以在 Ambient 出现之前，非 root 进程无法把能力传给自己 exec 出来的子程序——Ambient 就是为了补这个洞（代价是它会在文件带 setuid 位或文件 cap 时被清空，防止被用来污染特权程序）。

3.3 文件 capability：setuid 的现代替代

# 传统做法：整个二进制 setuid-root，为了绑一个端口拿到全部特权
$ sudo chown root:root ./myserver && sudo chmod 4755 ./myserver   # ❌

# 现代做法：只给它真正需要的那一位
$ sudo setcap 'cap_net_bind_service=+ep' ./myserver
$ getcap ./myserver
./myserver cap_net_bind_service=ep
#                                ^^ e = 放进 Effective（程序不用自己调 capset）
#                                 p = 放进 Permitted

# 撤销
$ sudo setcap -r ./myserver
文件 capability 存在 security.capability 这个扩展属性里，有三个常被忽略的后果：① cp 默认不保留（要 cp --preserve=xattr 或 --preserve=all），所以「本地跑得好好的，打进镜像就绑不了端口」十有八九是这个；② 挂载了 nosuid 的文件系统上文件 cap 同样失效；③ 很多网络文件系统和 tar 的默认参数不带 xattr。把 getcap 检查写进部署脚本或容器健康检查，别等到服务起不来才查。

3.5 在代码里主动降权

#include <sys/capability.h>   // libcap，编译加 -lcap
#include <sys/prctl.h>
#include <linux/capability.h>

// 启动早期（还是 root 时）绑好端口，然后把特权降到只剩必要的一位
static bool drop_to_minimal(uid_t uid, gid_t gid) {
    // ★① 保住 Permitted 集，否则 setuid 到非 0 时内核会清空所有 cap
    if (prctl(PR_SET_KEEPCAPS, 1, 0, 0, 0) != 0) return false;

    // ★② 顺序不能反：附加组 → gid → uid
    if (setgroups(0, nullptr) != 0)      return false;
    if (setresgid(gid, gid, gid) != 0)  return false;
    if (setresuid(uid, uid, uid) != 0)  return false;

    // ★③ 只保留 CAP_NET_BIND_SERVICE，其余全部清掉
    cap_t caps = cap_init();                       // 全空的集合
    cap_value_t keep[] = { CAP_NET_BIND_SERVICE };
    cap_set_flag(caps, CAP_PERMITTED, 1, keep, CAP_SET);
    cap_set_flag(caps, CAP_EFFECTIVE, 1, keep, CAP_SET);
    int rc = cap_set_proc(caps);                   // 应用到当前进程
    cap_free(caps);
    if (rc != 0) return false;

    // ★④ 收 Bounding 天花板 —— 这一步不可逆，之后连 exec 也拿不回来
    for (int c = 0; c <= CAP_LAST_CAP; ++c) {
        if (c == CAP_NET_BIND_SERVICE) continue;
        prctl(PR_CAPBSET_DROP, c, 0, 0, 0);   // 已经 drop 的返回 EINVAL，忽略即可
    }

    // ★⑤ 关死「execve 提权」这条路（详见 §4）
    return prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0) == 0;
}
忘了 PR_SET_KEEPCAPS 是这段代码最常见的 bug。默认情况下，当进程的 euid 从 0 变成非 0 时，内核会清空 Permitted 和 Effective（这是个安全默认值，防止降权不彻底）。所以如果你先 setresuid 再想 cap_set_proc 加回 CAP_NET_BIND_SERVICE，会拿到 EPERM——钱包已经空了，加不回来。必须先 PR_SET_KEEPCAPS 保住 Permitted，降完 uid 再从 Permitted 里挑要留的。注意 PR_SET_KEEPCAPS 会在 execve 时自动清零，它只保护「本进程降 uid」这一个时刻。
容器场景下这些通常不需要自己写代码：docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE --user 1000:1000，或者 K8s 的 securityContext.capabilities.{drop:[ALL], add:[NET_BIND_SERVICE]}，运行时会替你做完全套。自己写代码降权的价值在于「不依赖部署方配置正确」——服务自己保证「我跑起来之后一定没有多余特权」，这在被别人部署、或部署配置不由你控制时非常重要。两者叠加最好。
04

seccomp-bpf：收窄系统调用面

用不到的门，直接砌死

DAC 和 capabilities 回答的是「你能不能操作这个对象」。seccomp 回答的是一个完全不同的问题：「你能不能调用这个系统调用」——不管对象是谁。它是纵深防御里非常划算的一层，因为内核提供了 300 多个系统调用入口，而一个具体的服务进程通常只用到其中 40～60 个，剩下 250 个纯粹是白送给攻击者的攻击面。

一栋楼有三百扇门，你的部门日常只走其中四十扇。seccomp 就是把剩下那二百六十扇直接砌死——不是加锁（加锁还有配钥匙、撬锁、内鬼的可能），是砌墙。哪怕攻击者拿到了你的员工卡（RCE 拿到了进程控制权），他也没法从那些门出去。代价是：万一你哪天真的需要走某扇被砌死的门，程序不是失败，而是当场被打死（SIGSYS）——所以「砌哪些门」这份名单必须建立在真实数据上。
seccomp（SECure COMPuting）：进程自愿给自己安装一份系统调用过滤器，之后不可撤销，且被所有子进程和 execve 出来的程序继承。「自愿 + 不可撤销 + 可继承」这三个性质合起来，让它成为沙箱的理想基石——沙箱在做危险事情之前先把自己关起来，之后就算被完全控制也出不去。

4.1 两种模式

模式允许的系统调用怎么启用实际用途
strict（2.6.12）只有 read、write、_exit、sigreturn 四个prctl(PR_SET_SECCOMP, SECCOMP_MODE_STRICT)几乎没人用——连 close 和 mmap 都没有，只适合「已经把 fd 准备好、纯做计算」的极端场景
filter（3.5，即 seccomp-bpf）由你写的 cBPF 程序逐次决定seccomp(SECCOMP_SET_MODE_FILTER, …) 或 libseccomp所有实际场景：容器运行时、浏览器渲染进程、systemd 单元、各类沙箱

过滤器用的是 cBPF（classic BPF，就是 tcpdump 那套指令集），不是现代的 eBPF。它在系统调用入口被执行，输入是一个 struct seccomp_data：

struct seccomp_data {
    int   nr;                     // 系统调用号（★ 与架构强绑定！）
    __u32 arch;                  // AUDIT_ARCH_X86_64 / AUDIT_ARCH_AARCH64 …
    __u64 instruction_pointer;   // 触发这次调用的用户态 IP
    __u64 args[6];                // 六个寄存器参数的【原始值】
};
seccomp 看不见指针指向的内容，这是它的根本局限。args[] 里如果是一个指针，过滤器只能看到那个地址数值，不能解引用。这不是实现偷懒，而是刻意的设计：如果允许过滤器读用户内存，攻击者可以在过滤器检查完之后、内核真正读取参数之前，用另一个线程把内存改掉——经典的 TOCTOU（检查与使用之间的时间差）。所以「只允许 open("/etc/myapp.conf")」这种基于路径的规则 seccomp 根本做不到；路径级的控制是 LSM（§5）和 Landlock 的职责。seccomp 能过滤的只有标量参数：系统调用号、fd 编号、flags 位、domain/protocol 之类的枚举值。

4.2 动作语义

返回动作发生什么调用方看到什么时候用
SECCOMP_RET_KILL_PROCESS杀死整个进程（4.14 起）进程消失，dmesg 有记录生产默认——违规即终止，不给攻击者重试机会
SECCOMP_RET_KILL_THREAD只杀当前线程（老名字就是 KILL）多线程程序会剩下半死不活的状态历史遗留，新代码不要用——留下的进程状态难以推理
SECCOMP_RET_TRAP投递 SIGSYS，可被捕获si_syscall 里有系统调用号调试：打一条精确日志再退出；或做用户态兼容层
SECCOMP_RET_ERRNO(n)不执行，直接返回指定 errno就像这个调用失败了兼容性最好：返回 EPERM/ENOSYS 让程序走降级分支，而不是崩溃
SECCOMP_RET_LOG放行，但记一条审计日志（4.14 起）无感知采集阶段的主力——先跑一轮收集真实调用集
SECCOMP_RET_TRACE通知 ptrace 追踪者裁决取决于追踪者需要复杂裁决逻辑时；性能代价大
SECCOMP_RET_USER_NOTIF把调用转交给另一个用户态进程裁决（5.0 起）由监督者决定现代方案：rootless 容器用它让特权 helper 代做 mount 等操作
SECCOMP_RET_ALLOW放行正常执行白名单里的调用
可以给同一个进程叠加多个过滤器（后装的先跑，全部都跑），最终生效的是最严格的那个动作——所以过滤器只能越叠越紧，无法通过再装一个来放宽。这个「单调收紧」的性质是 seccomp 安全性的基础：容器运行时装的 profile，应用自己再装一层也不可能把它撑开。代价是每个系统调用都要跑完所有过滤器，层数多了会有可测量的开销（cBPF 很快，但系统调用密集型负载叠十几层是能看出来的），生产上一般控制在两三层以内。

4.3 no_new_privs：装过滤器的前提

no_new_privs（prctl(PR_SET_NO_NEW_PRIVS, 1, …)）：一个一旦置位就无法清除、且被子进程继承的标志。置位后，execve 不再因为 setuid 位或文件 capability 而提升权限——你 exec 一个 setuid-root 程序，它仍然以你的身份运行。

为什么装 seccomp 过滤器必须先置这个位（除非你有 CAP_SYS_ADMIN）？因为不这么要求的话，普通用户可以构造一次混淆代理人攻击：

❌ 没有 no_new_privs 会发生什么
// 攻击者（普通用户）：
// 1. 装一个过滤器，让 setgroups()
//    静默返回成功（RET_ERRNO(0)）
install_filter(setgroups => ERRNO(0));

// 2. exec 一个 setuid-root 的程序
execve("/usr/bin/some-setuid-tool", ...);

// 3. 那个程序照常降权：
//    setgroups(0,NULL) → 「成功」但没生效
//    setuid(user)      → 真的降了
// 结果：uid 降了，但附加组还留着 root 的，
// 特权程序在自己毫不知情的情况下被诱导
// 留下了一个提权缺口。
✅ no_new_privs 从根上堵死
prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);
// 之后再 exec 那个 setuid 程序：
// 它【不会】拿到 root，就是个普通进程。
// 攻击者能欺骗的只有自己的权限。

// 所以内核的规则是：
//   装 filter 需要 CAP_SYS_ADMIN
//              或 no_new_privs 已置位
seccomp(SECCOMP_SET_MODE_FILTER, 0, &prog);

// 验证：
//   grep -E 'NoNewPrivs|Seccomp' /proc/self/status
//   NoNewPrivs: 1
//   Seccomp:    2      ← 2 = filter 模式
面试加分点：「为什么 seccomp 需要 no_new_privs」是个很好的区分题。标准答案不是「因为内核要求」，而是要讲清混淆代理人这条攻击链：seccomp 过滤器会被 execve 继承，如果不限制，低权限进程就能给一个即将变成高权限的进程预埋一套扭曲的系统调用语义——让本该失败的调用「成功」、本该成功的调用失败，诱导特权程序走进它自己没预料到的分支。no_new_privs 保证「我 exec 出来的东西权限不会比我高」，于是无论我怎么扭曲语义，被坑的只有我自己。K8s 的 allowPrivilegeEscalation: false 设的就是这个位。

4.4 用 libseccomp 写一个白名单过滤器

手写 cBPF 指令既痛苦又容易错（还要自己处理架构判断），生产上一律用 libseccomp。下面是一个「只做 JSON 解析、除必需 IO 外什么都不许干」的沙箱子进程的完整过滤器：

#include <seccomp.h>      // libseccomp-dev，编译加 -lseccomp
#include <sys/prctl.h>
#include <sys/socket.h>

static bool install_sandbox(int in_fd, int out_fd) {
    // ★① 先置 no_new_privs（libseccomp 的 load 也会做，显式写出来更清楚）
    if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0) != 0) return false;

    // ★② 默认动作 = 杀进程。白名单模式，宁可误杀不可漏放。
    //     调试期可临时换成 SCMP_ACT_LOG 或 SCMP_ACT_ERRNO(EPERM)。
    scmp_filter_ctx ctx = seccomp_init(SCMP_ACT_KILL_PROCESS);
    if (!ctx) return false;

    // ★③ 显式声明目标架构。不加这句，过滤器只覆盖本机原生架构，
    //     x86-64 上仍可通过 int 0x80 走 i386 ABI 用【不同的调用号】绕过。
    seccomp_arch_add(ctx, SCMP_ARCH_X86);        // 32 位兼容 ABI
    seccomp_arch_add(ctx, SCMP_ARCH_X32);        // x32 ABI

    // ── 必需：进程收尾。少一个都会在退出时被自己的过滤器打死 ──
    int always[] = { SCMP_SYS(exit), SCMP_SYS(exit_group),
                     SCMP_SYS(rt_sigreturn), SCMP_SYS(rt_sigprocmask),
                     SCMP_SYS(rt_sigaction) };
    for (int nr : always) seccomp_rule_add(ctx, SCMP_ACT_ALLOW, nr, 0);

    // ── 必需：glibc 内部会用到的内存与线程原语 ──
    //    ⚠ 这几个是「你自己代码里一次都没写、但少了必挂」的典型
    int mem[] = { SCMP_SYS(brk), SCMP_SYS(mmap), SCMP_SYS(munmap),
                  SCMP_SYS(mprotect), SCMP_SYS(mremap),
                  SCMP_SYS(futex), SCMP_SYS(getrandom),
                  SCMP_SYS(clock_gettime), SCMP_SYS(gettimeofday) };
    for (int nr : mem) seccomp_rule_add(ctx, SCMP_ACT_ALLOW, nr, 0);

    // ── 业务：只允许读写【这两个已经打开的 fd】，其他 fd 一律拒绝 ──
    //    第 4 个参数 1 = 附加 1 个参数条件；A0 是第一个参数（fd）
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(read),  1,
                     SCMP_A0(SCMP_CMP_EQ, (scmp_datum_t)in_fd));
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 1,
                     SCMP_A0(SCMP_CMP_EQ, (scmp_datum_t)out_fd));
    seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(close), 0);

    // ── 明确拒绝但不杀：让程序看到 EPERM 走降级分支 ──
    //    比直接 KILL 友好，适合「有也行没有更好」的能力
    seccomp_rule_add(ctx, SCMP_ACT_ERRNO(EPERM), SCMP_SYS(socket), 0);

    // ★④ 加载。加载之后【永不可撤销】，且 fork/exec 出来的都继承。
    int rc = seccomp_load(ctx);
    seccomp_release(ctx);            // 释放的只是用户态上下文，过滤器已在内核里
    return rc == 0;
}

4.5 四个真实的工程陷阱

① 拦到了 libc 内部用的调用 → 莫名其妙的崩溃

  • 你的代码里一次都没写 futex，但只要用了 std::mutex、std::once_flag、甚至 glibc 的某些惰性初始化，它就会被调用。
  • 没写过 getrandom，但 glibc 2.25+ 的 malloc 和栈保护初始化会调它。
  • 没写过 clock_gettime？在有 vDSO 的机器上它不走系统调用，换一台没配好 vDSO 的机器就走了——于是「同样的二进制在 A 机器好好的，在 B 机器一起来就 SIGSYS」。
  • 症状：进程无预警消失，dmesg 里一行 audit: seccomp ... syscall=228。把这个号翻出来：ausyscall 228 或 grep 228 /usr/include/asm/unistd_64.h。

② 系统调用号是架构相关的，白名单不可跨架构复用

  • x86-64 上 read=0、write=1；aarch64 上 read=63、write=64。直接搬数字过去等于随机放行。libseccomp 的 SCMP_SYS() 宏会做映射，所以一定要用宏而不是字面量。
  • x86-64 还有 i386 兼容 ABI 和 x32 ABI，调用号完全是另一套。不显式 seccomp_arch_add 就等于留了后门——这是历史上多次被利用的绕过手法。
  • libc 版本也会变：glibc 在不同版本里可能把 open 换成 openat、把 stat 换成 newfstatat、把 poll 换成 ppoll。升级基础镜像后必须重新采集一遍，这是「什么都没改，换个基础镜像就挂」的常见根因。

③ 正确的做法：先用 LOG 跑一轮，用数据生成白名单

# A) 把默认动作临时设成 SCMP_ACT_LOG（放行 + 记日志），跑完整的功能与压测
#    注意：一定要跑到【所有代码路径】，包括错误分支、重连、优雅退出

# B) 从 audit 日志里把实际用到的调用捞出来
$ sudo ausearch -m SECCOMP -ts today --raw | grep -oP 'syscall=\K\d+' \
    | sort -un | while read n; do ausyscall "$n"; done | sort -u
brk
close
epoll_wait
futex
...

# C) 没有 auditd 时退而求其次，用 strace 统计（覆盖不如 audit 全，但够起步）
$ strace -f -c -U name ./myserver --run-test-suite 2>&1 | tail -n +3 | awk '{print $NF}'
  • 把采集结果与人工审阅结合：采集到的是「跑过的」，不是「需要的」。看到 ptrace、process_vm_readv、mount、init_module 出现在列表里，先问清楚为什么，别无脑加进白名单。
  • 灰度顺序：LOG → ERRNO(EPERM)（观察业务是否报错）→ KILL_PROCESS。直接上 KILL 是在拿线上做测试。

④ Docker / containerd 的默认 profile 屏蔽了什么

  • 默认 profile 是白名单式的（默认 SCMP_ACT_ERRNO，放行绝大多数常用调用），屏蔽掉的是几十个「容器里正常业务绝对用不到、但对攻击者很有用」的调用，大致分为几类：
  • 内核模块：init_module / finit_module / delete_module——直接的内核代码执行。
  • 挂载与根切换：mount / umount2 / pivot_root / chroot（部分）——逃逸的核心原语。
  • namespace 操作：setns、带 CLONE_NEW* 的 clone/unshare（依配置）。
  • 整机状态：reboot / kexec_load / swapon / settimeofday / clock_settime / sethostname。
  • 密钥环与文件句柄：add_key / request_key / keyctl（内核 keyring 是没有完全 namespace 化的）、open_by_handle_at（配合 CAP_DAC_READ_SEARCH 是经典逃逸手法）。
  • 观测类：bpf / perf_event_open——所以「在容器里跑 eBPF 探针」默认是不行的，需要显式放开。
  • ⚠ --privileged 会连同 seccomp profile 一起关掉（变成 unconfined），而不只是加满 capabilities。很多人只知道前半句。
  • K8s 侧对应 securityContext.seccompProfile.type: RuntimeDefault。它不是默认值——不写这一行，很多集群里 Pod 跑的是 Unconfined。这是最便宜的一条加固。
05

LSM 与 MAC：SELinux / AppArmor

策略说了算，属主也改不了

MAC（Mandatory Access Control，强制访问控制）：访问规则由系统级策略规定，客体的属主无权修改。与 DAC 的差别只有一句话——DAC 是「我的文件我做主」，MAC 是「制度说不行就是不行，你是属主也不行，你是 root 也不行」。
DAC 像你家的门锁：你想给谁配钥匙就给谁，物业不管。MAC 像公司的涉密管理制度：这份文件虽然是你写的、存在你的电脑上，但制度规定它不能带出研发区——你自己也没有「同意带出」的权限，因为签字权根本不在你手上。MAC 存在的意义就是「防止你自己犯错」以及「防止拿到你身份的攻击者为所欲为」：Web 服务被打穿了，攻击者以 apache 身份执行代码，DAC 下他能读所有 apache 能读的东西；MAC 下他被锁在 httpd_t 这个 type 里，策略没写允许的一律拒绝，连读 /home 都不行。

5.1 LSM：内核里的钩子框架

LSM（Linux Security Module）本身不是一个安全策略，而是内核里遍布各处的一套钩子点。内核在每个安全相关的决策点（打开文件、创建 socket、执行程序、发信号、ptrace…）留下一个回调，具体的安全模块挂上去做判断。它的位置永远在 DAC 和 capabilities 检查之后——这是设计上的刻意安排：

LSM 只能收紧，不能放宽。DAC 已经拒绝的请求根本走不到 LSM 钩子。所以「装了 SELinux 之后某个原本能访问的文件不能访问了」是可能的，「装了 SELinux 之后原本不能访问的能访问了」不可能。这个单调性让 MAC 可以安全地叠加在既有系统上——最坏情况是把事情搞砸（服务起不来），不会悄悄开出一个洞。
# 看当前内核启用了哪些 LSM 以及顺序
$ cat /sys/kernel/security/lsm
lockdown,capability,landlock,yama,bpf,selinux

# capability 也是一个 LSM（历史原因）；yama 管 ptrace 范围；
# selinux / apparmor 是所谓「major LSM」—— 目前主流发行版上二者【只能启用一个】。
# RHEL / Fedora / CentOS 系默认 SELinux；Ubuntu / Debian / SUSE 系默认 AppArmor。

# yama 顺带一提：限制谁能 ptrace 谁，容器与桌面都很有用
$ cat /proc/sys/kernel/yama/ptrace_scope

      # 2=只有 CAP_SYS_PTRACE 3=完全禁止(不可逆)

5.2 SELinux 的模型：一切皆 label

SELinux 给系统里每一个主体（进程）和每一个客体（文件、端口、socket、设备…）都贴一个 label，格式是四段：

system_u : system_r : httpd_t : s0
   ↑         ↑          ↑        ↑
 user      role       type    level(MLS/MCS)
 SELinux    角色     ★核心★    多级安全，容器用它做互隔离
 用户身份  （RBAC）  类型强制    如 s0:c123,c456
Type Enforcement（类型强制）：SELinux 的核心机制，也是 99% 日常问题的所在。策略里写的是「哪个 source type 可以对哪个 target type 做哪种操作」，例如 allow httpd_t httpd_sys_content_t : file { read getattr open };。规则是默认拒绝——策略里没有明确 allow 的组合，一律拒绝。user 和 role 那两段在服务器场景下基本是摆设，出问题几乎总是 type 对不上。

「关掉 SELinux」是最常见也最糟的解决方案。它不只是「少一层防护」这么简单：SELINUX=disabled 之后内核停止维护文件 label，期间新建和修改的文件全都没有正确的 type。等哪天你（或者一次合规检查）想重新开启，整个文件系统的 label 已经烂了，开机后大量服务起不来，只能全盘 restorecon -R / 重打标签——在 TB 级文件系统上这是几个小时的停机。正确的临时手段永远是 setenforce 0（Permissive）：它照常记录所有本该拒绝的操作，label 也继续维护，你既能让业务先跑起来，又拿到了完整的「要放开哪些」清单，修完 setenforce 1 立刻恢复。

5.4 AppArmor：按路径而不是按 label

AppArmor 的模型完全不同：它不给文件贴 label，而是在 profile 里直接写路径通配规则。这让它的入门成本低得多——一份 profile 就是一个人类可读的文本文件。

# /etc/apparmor.d/usr.local.bin.myserver
#include <tunables/global>

/usr/local/bin/myserver {
  #include <abstractions/base>
  #include <abstractions/nameservice>

  capability net_bind_service,          # 只允许这一个 capability

  /etc/myserver/**        r,             # 配置：只读
  /var/lib/myserver/**    rw,            # 数据：读写
  /var/log/myserver/*.log w,             # 日志：只写
  /usr/local/bin/myserver r,             # 自己：可读（动态链接需要）
  /proc/sys/kernel/random/uuid r,

  deny /home/**           rwx,           # 显式拒绝（比默认拒绝优先级更高）
  deny /etc/shadow        r,

  network inet stream,                   # 只允许 TCP/IPv4
  deny network raw,                      # 明确禁掉 raw socket
}
# 常用命令
$ sudo aa-status                        # 看有哪些 profile、各自什么模式
$ sudo aa-complain /usr/local/bin/myserver   # 切「只记录不拦截」（相当于 Permissive）
$ sudo aa-enforce  /usr/local/bin/myserver   # 切强制模式
$ sudo aa-logprof                       # 交互式：读日志，逐条问你要不要加进 profile
$ sudo apparmor_parser -r /etc/apparmor.d/usr.local.bin.myserver   # 重载

# 被拒时日志长这样（比 AVC 好读很多）
$ sudo dmesg | grep DENIED

06

namespace 的安全边界

隔离了什么，更重要的是没隔离什么

前面五层都在回答「能不能做」。namespace 回答的是另一个问题：「你能看见什么」。看不见的东西自然也操作不了，所以它常被当成隔离手段——但它不是为安全设计的，它的初衷是资源视图虚拟化。理解这句话是理解容器安全的起点。详细的机制原理见 cgroup / namespace 与容器原理，这里只谈安全边界。

namespace隔离了什么没有隔离什么
mnt挂载点视图底层块设备本身；宿主传进来的 bind mount 内容是真实共享的，容器写进去宿主立刻可见
pid进程号视图（容器内看不到宿主进程）宿主能看见并 kill 容器内的进程；/proc 里非进程的部分（/proc/sys、/proc/kcore…）
net网卡、路由表、iptables、端口空间物理带宽与网卡队列；宿主侧的 veth 另一端；大部分 net.* sysctl 是 netns 化的，但不是全部
utshostname、domainname—
ipcSystem V IPC、POSIX 消息队列基于文件的共享内存（/dev/shm 若被共享）
useruid/gid 映射与 capability 的作用域宿主上的真实 uid（容器内的 root 在宿主上就是某个普通 uid）
cgroupcgroup 层级的根视图实际的资源限制值（限制仍由宿主设定）
time（5.6+）只有 CLOCK_MONOTONIC / CLOCK_BOOTTIME 的偏移墙上时间不隔离——改系统时间是全局的
最重要的一条：namespace 不隔离内核。宿主和所有容器共用同一份内核代码、同一份内核数据结构、同一张系统调用表。这意味着：① 任何一个内核提权漏洞都直接是容器逃逸漏洞——Dirty COW（CVE-2016-5195）、Dirty Pipe（CVE-2022-0847）这类漏洞在容器里打和在宿主上打没有区别；② 没有被 namespace 化的内核全局状态是共享的，典型的有：/proc/sys/kernel/* 与 /proc/sys/vm/* 下的绝大多数 sysctl、内核模块列表、/sys/kernel、内核 keyring（只部分隔离）、CPU 微架构状态（Spectre/Meltdown 类侧信道）、以及硬件本身。这就是 gVisor 和 Kata 存在的全部理由（§8）。

6.1 哪些 sysctl 是 namespace 化的

# 容器里能安全设置的 sysctl 是【有限的白名单】，因为其余的是全局的
#   ✅ netns 化：net.ipv4.* / net.core.* 的大部分（每个 netns 一份）
#   ✅ ipcns 化：kernel.msgmax / kernel.shmmax / kernel.sem / fs.mqueue.*
#   ✅ utsns 化：kernel.hostname / kernel.domainname
#   ❌ 全局：vm.max_map_count / vm.swappiness / fs.file-max /
#            kernel.pid_max / kernel.core_pattern / kernel.dmesg_restrict …

# 所以这条在容器里是【改宿主】，而不是「改我自己」：
$ docker run --sysctl vm.max_map_count=262144 ...
Error: sysctl "vm.max_map_count" is not in a separate kernel namespace
# Docker 会直接拒绝 —— 这个报错本身就是一份很好的 namespace 边界文档。
# Elasticsearch 容器要求先在【宿主】上 sysctl -w vm.max_map_count=262144，
# 原因就在这里。

# kernel.core_pattern 是没被隔离的典型危险项：容器内进程崩溃时，
# 内核会按【宿主的】core_pattern 在【宿主上下文】执行处理程序。
# 能写它 = 能在宿主上执行命令，所以它必须是只读的。
$ cat /proc/sys/kernel/core_pattern     # 容器里应该只能读，不能写

6.2 user namespace：唯一非特权可创建的那个

user namespace：唯一一个普通用户无需任何特权就能创建的 namespace。在新的 user ns 里，进程可以是 uid 0 并拥有该 namespace 内的全套 capability——但这些 capability 只对同样属于这个 namespace 的资源有效。它是 rootless 容器的基石，也是 Linux 安全模型里争议最大的一块。
user namespace 像「剧组里的国王」：在片场里他是国王，对布景、道具、群演有绝对权威（namespace 内的 capability 全开）。但一走出摄影棚，他就是个普通人，对真实世界的银行账户和政府机关毫无权力（对宿主资源没有任何额外特权）。问题在于：为了让这场戏演得像，剧组得给他开放不少原本闭着的通道——他能布景、能调灯光、能改道具（能创建其他 namespace、能挂载部分文件系统）。这些通道通向的是真实的内核代码，而这些代码路径过去只有 root 走过、审计得远没那么充分。这正是历史上大量 userns 相关 CVE 的来源。
# 手动体验：普通用户创建 user ns + mount ns
$ id -u
1000
$ unshare --user --map-root-user --mount --pid --fork bash
# 现在在新 namespace 里 ——
# id -u
0                                    # 「我是 root」
# cat /proc/self/uid_map
         0       1000          1     # ns 内 uid 0 ↔ 宿主 uid 1000
# capsh --print | head -2
Current: =ep                         # 在这个 ns 里全套 capability
# touch /etc/shadow_test
touch: cannot touch '/etc/shadow_test': Permission denied
#  ↑ 但对宿主的文件毫无办法：内核检查时会把「ns 内 root」翻译回宿主 uid 1000，
#    而 /etc 属于宿主的 uid 0。capability 只在【拥有该文件系统的 user ns】里生效。

6.3 UID 映射的写法

# uid_map / gid_map 的格式：每行三个数
#   <ns 内起始 ID>  <父 ns 内起始 ID>  <长度>
$ cat /proc/self/uid_map
         0     100000      65536
# 读作：容器内的 uid 0..65535  映射到  宿主的 100000..165535
# 于是容器里的 root(0) 在宿主上看就是 100000 —— 一个什么都不是的普通用户。

# 写映射的规则（容易踩坑的三条）：
#  ① 每个 map 文件【只能写一次】，之后就固定了；
#  ② 非特权进程只能映射【自己的那一个 uid】；要映射一段连续区间，
#     需要父 ns 里的 CAP_SETUID/CAP_SETGID，或者借助 setuid 的
#     newuidmap/newgidmap 工具（它们读 /etc/subuid、/etc/subgid 授权）；
#  ③ ★ 非特权情形下，写 gid_map 之前必须先：
$ echo deny > /proc/$PID/setgroups
#     否则 gid_map 写入返回 EPERM。原因：不禁掉 setgroups 的话，
#     进程可以【丢掉】某个附加组，从而绕过「deny 某组访问」类的负权限规则。

# 发行版给非 root 用户预留的映射区间
$ cat /etc/subuid
alice:100000:65536
$ cat /etc/subgid
alice:100000:65536
# Podman / rootless Docker / buildah 全部依赖这两个文件。

6.4 两面性：rootless 的基石，也是提权的温床

❌ 它扩大了攻击面

创建 user ns 后，普通用户获得了在这个 ns 内使用 capability 的能力，从而能触达大量过去只有 root 才走得到的内核代码路径：文件系统挂载解析、网络协议栈配置、cgroup 操作、setns…

这些路径的安全审计强度历史上远低于常规路径（假设「反正只有 root 能走」），于是过去十年里出现了相当数量的、以「非特权用户创建 user ns 后触发」为前置条件的本地提权 CVE。

所以不少发行版默认限制或加了额外约束：Debian 曾用 kernel.unprivileged_userns_clone；RHEL 系用 user.max_user_namespaces；较新的 Ubuntu 引入了 kernel.apparmor_restrict_unprivileged_userns，用 AppArmor 限制非特权 userns 的使用。

✅ 它也是最有效的容器加固手段

没有 user ns 时，容器里的 root 就是宿主的 root（uid 都是 0）。只要有任何一条路径让它碰到宿主的文件（一次错误的 bind mount、一个内核漏洞），那就是完整的宿主 root。

开了 user ns 之后，容器 root 在宿主上只是 uid 100000。逃逸的收益从「宿主 root」降级成「一个没有任何权限的陌生用户」——这是数量级的差别，也是 Podman rootless、rootless Docker、K8s 的 UserNamespacesSupport 的核心价值。

净收益判断：给容器开 user ns 是明确的加固；允许宿主上任意用户随便创建 user ns 是明确的风险。两件事经常被混为一谈。合理配置是：容器运行时用它，同时通过 sysctl / AppArmor 限制普通用户滥用。

# 检查本机对非特权 user ns 的限制
$ cat /proc/sys/user/max_user_namespaces
15000                       # 0 表示完全禁止非特权创建
$ sysctl kernel.unprivileged_userns_clone 2>/dev/null   # Debian 系可能有这一项
$ sysctl kernel.apparmor_restrict_unprivileged_userns 2>/dev/null  # 较新 Ubuntu

# Docker 侧启用 userns-remap（/etc/docker/daemon.json）
{ "userns-remap": "default" }
# 重启 dockerd 后会自动建 dockremap 用户并写 /etc/subuid、/etc/subgid。
# ⚠ 代价要提前知道：与 --privileged、--pid=host、--net=host 以及部分
#   卷挂载场景不兼容；已有卷的文件属主会对不上（宿主看是 100000）。
#   所以它适合新集群从一开始就开，中途切换要做迁移评估。

容器逃逸的真实路径

绝大多数不是内核 0day，是配置错误

本章的写法说明：下面讲的是原理、成因和自查方法，目的是让你能判断自己的环境有没有这些问题、以及怎么修。不提供可直接运行的完整攻击脚本——那对防守方没有增量价值，每一条给出的都是「怎么检测」和「怎么修」。

真实世界里的容器逃逸，绝大多数不是靠内核 0day，而是靠一份写得太宽松的部署配置。下面六条按「实际遇到的频率 × 危害」排序，前两条加起来能覆盖大部分事故。

7.1 --privileged：等于没有容器

--privileged 一次性做了这些事：capability 全给、seccomp profile 换成 unconfined、AppArmor/SELinux 约束解除、/sys 变为可写、宿主的所有设备节点在 /dev 下可见。有了这些，容器里的 root 可以直接看到宿主的块设备并把它挂载起来——宿主根文件系统就在眼前，改 /etc/passwd、写 authorized_keys、投个 cron 任务都是顺手的事。

# 自查：我现在是不是在特权容器里？
$ grep CapEff /proc/self/status
CapEff:	0000003fffffffff              # 满值 → 特权容器（具体位数随内核版本变）
$ capsh --decode=0000003fffffffff | tr ',' '\n' | grep -E 'sys_admin|sys_module'
cap_sys_admin
cap_sys_module                        # 这两个一起出现基本就是 privileged

$ grep Seccomp /proc/self/status
Seccomp:	0                         # 0 = 没有过滤器 → profile 被关掉了

$ ls /dev | wc -l
180                                   # 普通容器只有十来个；上百个 = 宿主设备全暴露
$ ls /dev/sd* /dev/nvme* 2>/dev/null
/dev/sda  /dev/sda1  /dev/nvme0n1     # ← 看到宿主块设备就已经输了

# 宿主侧盘点：哪些容器是特权的
$ docker ps -q | xargs -r docker inspect \
    --format '{{.Name}} privileged={{.HostConfig.Privileged}} caps={{.HostConfig.CapAdd}}'

# K8s 侧盘点
$ kubectl get pods -A -o jsonpath='{range .items[*]}{.metadata.namespace}{"/"}{.metadata.name}{"\t"}{.spec.containers[*].securityContext.privileged}{"\n"}{end}' | grep true
--privileged 唯一合理的用途是「这个容器就是系统组件」——CNI 插件、存储驱动、节点上的监控 agent。业务容器要它，永远是设计问题。最常见的两个借口：「我要在容器里跑 docker（DinD）」——用 Kaniko / buildah 这类无守护进程的构建方案替代；「我要设 sysctl / 挂 fuse / 用某个设备」——用 --sysctl、--device=/dev/fuse + --cap-add=SYS_ADMIN、或宿主侧预先准备好资源再挂进来，几乎总能收窄到具体的一两项。

7.2 挂载 /var/run/docker.sock：把宿主 root 交出去

这一条比 --privileged 更隐蔽，因为它看起来「只是挂了一个文件」，而且 CI runner、监控面板、日志采集器的官方文档里到处都是这个写法。

能访问 docker.sock = 拥有宿主 root。推理链只有三步：这个 socket 是 Docker 守护进程的完整控制 API → 通过它可以创建新容器，而新容器的参数由你指定 → 于是可以创建一个 privileged 的、把宿主 / 挂到 /host 的容器。不需要任何漏洞，这就是 API 的正常功能。containerd.sock、crio.sock、以及 K8s 里挂 hostPath: /var/run/ 完全同理。
# 自查：容器里有没有这个 socket
$ ls -l /var/run/docker.sock /run/containerd/containerd.sock 2>/dev/null
srw-rw---- 1 root docker 0 Jun  1 10:00 /var/run/docker.sock   # ← 有就是高危
$ mount | grep -E 'docker\.sock|containerd\.sock|crio\.sock'

# 顺带查一下自己在不在 docker 组 —— 宿主上这同样等价于 root
$ id
uid=1000(ci) gid=1000(ci) groups=1000(ci),998(docker)   # ← 998(docker) 就是 root

# 宿主侧盘点：谁挂了它
$ docker ps -q | xargs -r docker inspect \
    --format '{{.Name}} {{range .Mounts}}{{.Source}} {{end}}' | grep -i sock

# K8s 侧：找所有挂了 /var/run 的 hostPath
$ kubectl get pods -A -o json | jq -r '.items[] | select(.spec.volumes[]?.hostPath.path // "" | test("^/var/run|^/run")) | "\(.metadata.namespace)/\(.metadata.name)"'
怎么修：① CI 场景换成 rootless 构建器（Kaniko、buildah、BuildKit rootless）——它们不需要守护进程；② 监控/日志场景改用只读的、经过收窄的 API 代理（如 socket-proxy 之类只放行 GET /containers/json 的中间层），而不是把裸 socket 递进去；③ 实在绕不开时，至少把这个容器当成与宿主同等信任级别来治理：单独节点、单独网络策略、严格的镜像来源审计。

7.3 CAP_SYS_ADMIN + cgroup v1 的 release_agent

这是被写进无数演讲稿的经典手法，值得理解原理——因为它完美展示了「一个看起来无害的内核特性 + 一个过宽的 capability」如何组合成逃逸。

release_agent（仅 cgroup v1）：cgroup v1 提供的一个回调机制——当某个 cgroup 里最后一个进程退出时（且该 cgroup 的 notify_on_release 为 1），内核会在宿主的根 namespace 上下文里执行 release_agent 文件指定的那个程序。注意「宿主上下文」这五个字——这就是整条链的关键。

攻击成立需要同时满足几个条件：容器有 CAP_SYS_ADMIN（才能 mount cgroupfs）、宿主用的是 cgroup v1、以及容器处于初始 user namespace（没开 userns-remap）。满足之后，逃逸者要做的就是：把一个 cgroup 层级挂进容器、往 release_agent 里写一条指向容器内某个脚本的宿主可见路径（容器的 rootfs 在宿主上是有真实路径的，可以从 /etc/mtab 或 /proc/self/mountinfo 里读出来）、然后制造一次「cgroup 变空」事件。内核就会在宿主上以 root 身份执行那个脚本。

# ── 自查（不是攻击）：这台机器/这个容器是否具备上述前置条件 ──

# ① cgroup 版本：v2 (unified) 没有 release_agent 这个机制，这条路径不存在
$ stat -fc %T /sys/fs/cgroup
cgroup2fs        # ✅ v2，安全
tmpfs            # ⚠ v1（或混合模式），需要继续查

# ② 我有没有 CAP_SYS_ADMIN
$ grep CapEff /proc/self/status | awk '{print $2}' | xargs capsh --decode | grep sys_admin

# ③ 容器内能不能挂载 cgroupfs（有 SYS_ADMIN 且 seccomp 没拦 mount 就能）
$ grep -E '^(Seccomp|NoNewPrivs)' /proc/self/status
Seccomp:	2        # 2 = 有过滤器；Docker 默认 profile 会拦 mount

# ④ 我在不在初始 user namespace（开了 userns-remap 就不在）
$ cat /proc/self/uid_map
         0          0 4294967295      # ⚠ 这行表示【没有】做 uid 重映射
         0     100000      65536      # ✅ 做了重映射，容器 root 在宿主上是 100000

# ⑤ 宿主侧：release_agent 是否被写过（正常应为空）
$ find /sys/fs/cgroup -maxdepth 2 -name release_agent -exec sh -c \
    'printf "%s: " "$1"; cat "$1"' _ {} \; 2>/dev/null
面试加分点：这条链在 2022 年还引出过一个纯内核侧的变种——CVE-2022-0492：内核在检查「谁有权写 release_agent」时漏掉了对初始 user namespace 的验证，导致在自己创建的 user ns 里就能写它，于是连 CAP_SYS_ADMIN 都不再需要。这个案例说明两件事：① 「需要 CAP_SYS_ADMIN 才能利用」不是一个可靠的防线，因为漏洞可能正好出在权限检查本身；② 切到 cgroup v2 是一劳永逸的结构性修复，因为 v2 根本没有这个机制（它改用 cgroup.events + inotify 通知，不在内核里执行任何用户指定的程序）。现代发行版默认已是 v2 unified 层级。

7.4 可写的 /proc 与 /sys

路径可写的后果正常状态
/proc/sys/kernel/core_pattern写成 |/path/to/prog 后，任意进程崩溃都会在宿主上 root 执行它容器内只读（运行时会把 /proc/sys 挂成 ro）
/proc/sys/kernel/modprobe内核在需要自动加载模块时会执行这个路径只读
/proc/sysrq-trigger可触发宿主重启、OOM kill、Magic SysRq被 mask 掉（指向 /dev/null）
/proc/kcore、/proc/kallsyms读内核内存 / 泄漏内核符号地址，破坏 KASLR被 mask 或权限受限
/sys/kernel/uevent_helper与 core_pattern 同理，内核会在宿主上执行它/sys 整体只读
/sys/fs/cgroup/** 可写见 §7.3；另外可改自己的资源限制只读挂载
宿主 / 或 /etc 被 bind mount 进来直接改宿主配置，连逃逸都不用不应该存在

$ for p in /proc/sys/kernel/core_pattern /proc/sys/kernel/modprobe \

    if [ -w "$p" ]; then echo "WRITABLE  $p"; else echo "ok        $p"; fi
  done

$ findmnt -o TARGET,SOURCE,OPTIONS | grep -E '/proc/sys|/sys '

# 看有没有把宿主目录挂进来（最直接的问题，也最容易被忽略）
$ grep -E ' / | /etc | /root | /var/lib/kubelet ' /proc/self/mountinfo

7.5 hostPID / hostNetwork / hostIPC

hostPID: true（docker run --pid=host）

  • 容器看到宿主的完整进程表。/proc/<pid>/cmdline 和 /proc/<pid>/environ 里经常躺着命令行传入的密码和环境变量里的 token——这是最省事的凭据收集途径。
  • 配合 CAP_SYS_PTRACE 就能 ptrace 宿主进程，往里注入代码；即使没有 ptrace 权限，/proc/<pid>/root/ 也能穿透到那个进程的 mount namespace去读文件。
  • 自查：ps aux | wc -l 在正常容器里是个位数；看到几百个进程就是共享了宿主 PID ns。或直接 readlink /proc/1/ns/pid 与宿主对比。

hostNetwork: true（--net=host）

  • 直接使用宿主网络栈：网络策略（NetworkPolicy）对它完全无效，因为策略作用在 Pod 网络上。
  • 能访问只监听 127.0.0.1 的服务——这类服务往往因为「只有本机能连」而没做认证：kubelet 的只读端口、各种 admin 接口、本地 Redis、云厂商的元数据服务代理。这是横向移动最肥的一块地。
  • 可以 bind 宿主端口、可以抓宿主流量（若同时有 CAP_NET_RAW）。
  • 自查：ip addr 看到的是宿主全部网卡而不是一张 eth0；ss -tlnp 能看到宿主上其他服务的监听。

hostIPC: true 与云元数据服务

  • hostIPC 让容器能访问宿主的 System V 共享内存段——可以读到别的进程放在共享内存里的数据（数据库缓冲池、行情快照…）。相对少见但危害实在。
  • 顺带一条不属于 namespace 但同样致命的：公有云上的元数据服务（169.254.169.254）默认对节点上所有 Pod 可达，能取到节点角色的临时凭据。对策是强制 IMDSv2（需要 PUT 取 token 且限制跳数）+ 网络策略拦截该地址。这条在真实的云上入侵链里出现的频率比内核漏洞高得多。

7.6 内核漏洞：共享内核意味着内核漏洞就是逃逸漏洞

# 这一条没有「检测配置」可言，只有版本管理
$ uname -r
5.15.0-91-generic
$ cat /etc/os-release | grep VERSION=

# 有代表性的两个例子（都能在容器内直接利用，无需任何特殊配置）：
#   Dirty COW  CVE-2016-5195  —— 写时复制的竞态，可写只读文件，覆盖 setuid 二进制
#   Dirty Pipe CVE-2022-0847  —— 管道缓冲区标志未初始化，可覆盖任意只读文件内容
#                                 影响 5.8 起的内核，在 5.16.11/5.15.25/5.10.102 修复
# 另有一类是运行时自身的漏洞，例如 runC 的 CVE-2019-5736：
#   利用 /proc/self/exe 覆盖宿主上的 runc 二进制，下一次 exec 就在宿主上执行。
#   它提醒我们：容器运行时本身也是攻击面，不只是内核。
这一条无法靠配置消除，只能靠三件事管理：① 补丁节奏——把内核与容器运行时纳入常规更新，并有能力度量「集群里最旧的内核是哪台」；② 降低利用价值——开 user namespace，让逃逸拿到的是 uid 100000 而不是 root（§6.4）；③ 换更强的隔离——对真正不可信的工作负载（多租户、跑用户提交的代码），用 gVisor 或 Kata 把内核攻击面本身换掉（§8）。「容器不是安全边界」这句常被引用的话，指的就是这一条；它对配置良好的容器不成立，对「拿它隔离敌意代码」的场景则完全成立。

8.3 第三层：换掉共享内核

前两层都在「配置得更严」，但 §7.6 那条——共享内核——是配置改不动的。要动它只有两条路：

维度普通容器（runc）gVisor（runsc）Kata Containers
隔离原理namespace + cgroup + seccomp，直接调宿主内核用户态内核：Sentry 进程用 Go 重新实现了大部分 Linux 系统调用语义，容器的调用先被拦到 Sentry每个 Pod 一个轻量 VM（Firecracker / QEMU），里面跑一个独立的 guest 内核
内核攻击面完整的 300+ 系统调用直达宿主内核宿主内核只暴露给 Sentry，且 Sentry 自己再套一层很窄的 seccomp（宿主侧只剩几十个调用）只暴露 hypervisor 接口——攻击面最小，且是硬件强制的边界
启动延迟~50–200 ms比 runc 略慢，同量级较慢（Firecracker 约百毫秒级，QEMU 更久）
内存开销近乎为零每容器一个 Sentry 进程（几十 MB）每 Pod 一份 guest 内核 + rootfs，上百 MB 起
系统调用开销原生明显更高——每次调用多一层用户态转发；syscall 密集与 I/O 密集负载受影响大较低（VM 内是原生调用），但 I/O 要过 virtio，网络与存储有额外延迟
兼容性完整不完整：部分冷门系统调用、部分 /proc /sys 项、某些 ioctl 不支持。上线前必须真跑一遍接近完整（就是个真内核），但需要硬件虚拟化支持，嵌套虚拟化环境下可能不可用
适合可信的自有工作负载（配好 §8.1 就够）多租户 SaaS、跑用户提交的代码、函数计算强合规、强多租户、需要硬件级隔离保证的场景
不要把 gVisor / Kata 当成默认选项。对绝大多数「跑自己写的服务」的团队，把 §8.1 那张表落实到位的收益远大于换运行时，而且不用付性能账。真正需要它们的判据只有一个：你要在同一台机器上运行「你不信任的代码」——用户提交的构建脚本、多租户的函数计算、跑不认识的第三方镜像。这时候「容器不是安全边界」才真正咬人，才值得为一层用户态内核或一个 VM 付出代价。K8s 里通过 RuntimeClass 按工作负载选择，不必全集群一刀切。

8.4 两个较新的机制

Landlock（5.13+）：非特权进程给自己上锁

  • 过去的 MAC 都需要管理员写全局策略。Landlock 让普通进程无需任何特权就能给自己加一套文件系统访问规则——「我接下来只读 /etc/myapp，只写 /var/lib/myapp，别的一律拒绝」。
  • 规则和 seccomp 一样不可撤销、可被子进程继承，所以适合放在程序初始化的最后一步。它正好补上了 seccomp 做不到的那块（§4.1）：seccomp 看不见路径，Landlock 就是按路径来的。
  • 能力随内核版本递增（5.13 起是文件系统，后续版本加入了 TCP bind/connect 等），所以代码里要做能力探测并优雅降级，不能假定目标内核支持某个 ABI 版本。
  • 典型用户：Chromium、systemd（ExecPaths= 等）、一些沙箱库。值得关注，但生态还在成长期。

eBPF LSM（5.7+）：用 eBPF 程序挂到 LSM 钩子上

  • 把 eBPF 程序附加到 LSM 钩子，返回 0 放行、返回负 errno 拒绝。相当于可动态加载、可热更新的 MAC 策略，不用编译内核模块，也不用重启。
  • 相比 SELinux 的静态策略，它能表达依赖运行时状态的规则（结合 map 做计数、按容器 ID 区分、与可观测性数据联动）。Tetragon 这类工具就建立在它上面。
  • 门槛：需要 CONFIG_BPF_LSM=y 且在 lsm= 启动参数里启用，写起来也不轻松。目前更多是安全产品的底座，而不是应用团队直接用的东西。

防不住的，至少要看得见

前面所有措施都是预防。但预防总有漏网的，所以还需要第二个问题的答案：「出事了我能不能发现、能不能还原过程」。这一章讲两条互补的路线——内核自带的 auditd（全、重、离线分析）与基于 eBPF 的运行时检测（轻、快、在线告警）。

9.1 auditd：内核自带的审计子系统

Linux Audit：内核里独立于 LSM 的一套记录框架。它把「谁在什么时间对什么做了什么、结果如何」写进 /var/log/audit/audit.log。SELinux 的 AVC denied 记录也是通过它输出的——所以 §5.3 用的 ausearch 其实就是在查 audit 日志。
# 规则写在 /etc/audit/rules.d/*.rules，用 augenrules --load 或 auditctl 加载

# ① 监控敏感文件的写与属性变更（-p wa：write + attribute change）
-w /etc/shadow      -p wa -k identity
-w /etc/passwd      -p wa -k identity
-w /etc/sudoers     -p wa -k identity
-w /etc/sudoers.d/  -p wa -k identity
-w /root/.ssh/      -p wa -k ssh_keys

# ② 监控提权类系统调用（arch 必须显式写，b64/b32 各来一条）
-a always,exit -F arch=b64 -S setuid -S setreuid -S setresuid -k privesc
-a always,exit -F arch=b64 -S setgid -S setregid -S setresgid -k privesc

# ③ 监控内核模块加载 —— 正常业务机器上这个应该几乎不响
-a always,exit -F arch=b64 -S init_module -S finit_module -S delete_module -k modules

# ④ 监控执行：信息量最大，也【最贵】，见下方警告
-a always,exit -F arch=b64 -S execve -F auid>=1000 -F auid!=4294967295 -k exec
#   auid（登录用户 id）>=1000 过滤掉系统服务，只看真人操作，
#   auid!=4294967295（-1）排除掉没有登录会话的进程。这两个条件能砍掉绝大部分噪声。

# ⑤ 最后一行：锁定规则集，之后要改必须重启（防止攻击者关审计）
-e 2
# ── 查询 ──
$ sudo ausearch -k identity -ts today          # 按 key 查
$ sudo ausearch -m AVC -ts recent -i           # -i 把数字翻译成名字，可读性大增
$ sudo ausearch -ua 1000 -ts '06/01/2026 09:00:00'  # 按登录用户 + 时间窗

# ── 汇总报表 ──
$ sudo aureport --summary                      # 总览：各类事件计数
$ sudo aureport -au --summary -i               # 认证事件（失败登录尖峰一眼看出）
$ sudo aureport -x --summary -i | head         # 执行过的程序 Top N
$ sudo aureport -m --summary                   # 账户变更

# ── 健康检查（最容易被忽略的一步）──
$ sudo auditctl -s
enabled 2  failure 1  pid 1234  rate_limit 0  backlog_limit 8192
lost 0  backlog 0
#   lost > 0  → 【正在丢事件】，你的审计日志是不完整的
#   backlog 持续接近 backlog_limit → 队列快满了，赶紧调大或减规则
$ sudo auditctl -b 16384      # 调大队列
$ sudo auditctl -r 2000       # 限速，超出部分丢弃（保护系统别被审计拖垮）
审计量爆炸是真实的生产事故，不是理论风险。无条件审计 execve 在一台跑 CI 或大量 shell 脚本的机器上，每秒能产生上万条记录——磁盘被日志打满、审计队列溢出（lost 疯涨）、内核在审计路径上自旋导致整机变慢。更凶险的是 failure 参数：设成 2（panic）时审计失败会直接 panic 内核，设成 1（printk）会刷屏 dmesg。正确做法：① 只审计你会真的去看的事件，写不出「这条告警响了我做什么」就别加这条规则；② 用 -F auid>=1000、-F exe=、-F dir= 这类条件把范围收窄；③ 用 -r 限速、把 -b 调大；④ 上线前在压测环境量一遍 EPS，别在生产上试。
审计对象值不值得说明
敏感文件写（/etc/shadow、sudoers、SSH key）✅ 必做事件量极小，信噪比极高，改动几乎必然是可疑的
提权调用（setuid 家族）✅ 值得量可控；配合白名单（已知的 login/su/容器运行时）后剩下的都要看
模块加载✅ 值得业务机器上正常情况下几乎为零，一响就是大事
execve（全量）⚠️ 谨慎信息量最大也最贵；必须加 auid 过滤，否则容易压垮机器
所有文件访问（open/read）❌ 不要量是天文数字，且几乎没有可操作的信号。要做文件级监控请用 LSM 或 eBPF
网络连接⚠️ 换工具auditd 做这个又贵又难用，用 conntrack / eBPF / 服务网格更合适

9.2 基于 eBPF 的运行时检测

auditd 的模型是「记录一切、事后查询」。eBPF 类工具的模型是「在内核里就地做规则判断，只把命中的事件送上来」——数据量小几个数量级，而且能实时告警。eBPF 本身的机制见 eBPF 与可观测性。

工具挂载点能做什么取舍
Falco系统调用（eBPF 或内核模块驱动）一套 YAML 规则语言，社区维护了大量开箱规则（「容器内起了 shell」「有人读了 /etc/shadow」「写了 /usr/bin」「连了非预期的外网」）规则易读、生态成熟；高系统调用速率下有可观测的开销，需要调采样与规则范围
Tetragon系统调用 + LSM 钩子不只观测，还能直接阻断（在钩子里返回拒绝、或同步杀进程）；带完整的 K8s 元数据（Pod / 容器 / 服务）能力更强、开销更低；需要较新内核，配置复杂度高
自写 bpftrace 脚本tracepoint / kprobe临时排查、验证某个具体假设，几行就能出结果不适合常驻；但排障时极其好用
 
# Falco 规则的样子（YAML，可读性是它的卖点）
- rule: Terminal shell in container
  desc: 容器里出现交互式 shell —— 正常业务镜像不该有这种行为
  condition: >
    spawned_process and container
    and shell_procs and proc.tty != 0
    and container_entrypoint
  output: >
    Shell spawned in container (user=%user.name container=%container.name
    shell=%proc.name parent=%proc.pname cmdline=%proc.cmdline)
  priority: NOTICE
  tags: [container, shell, mitre_execution]

# 临时排查：谁在读敏感文件（bpftrace 一行流）
$ sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat
  /str(args->filename) == "/etc/shadow"/
  { printf("%s pid=%d uid=%d comm=%s\n", strftime("%H:%M:%S", nsecs),
           pid, uid, comm); }'

# 临时排查：容器内所有 execve（比开全量 auditd 便宜得多）
$ sudo bpftrace -e 'tracepoint:syscalls:sys_enter_execve
  { printf("%d %s -> %s\n", pid, comm, str(args->filename)); }'
面试加分点：auditd 和 Falco 不是二选一，它们回答不同的问题。auditd 是「取证」——它的价值在于完整、可信、合规认可，事后要还原「三天前 14:20 到底谁改了这个文件」时只有它靠谱，代价是量大、只能离线查。Falco / Tetragon 是「告警」——价值在于实时、低噪、可操作，「现在有个容器里冒出了 shell」这种事必须几秒内知道。成熟的方案是两者都有并分工：auditd 收窄到少数高价值规则、日志转发到 SIEM 长期留存；eBPF 工具承担实时行为检测、告警接入 on-call。中间用统一的容器/Pod 标识把两边的事件关联起来，这样告警响了能立刻去 SIEM 里拉出完整上下文。
与日志/SIEM 的衔接有三个容易踩的点：① 日志必须离开这台机器——攻击者拿到 root 后第一件事往往是清日志，本地日志在事后取证里可信度为零，要实时转发（audisp-remote、rsyslog、Vector、Fluent Bit）；② 时间必须同步，多机取证时时钟漂移会让事件顺序完全错乱，NTP 是安全基础设施而不只是运维细节；③ 身份要能对上——容器里的 pid、uid 与宿主上的不是一回事，转发时要带上容器 ID / Pod 名，否则 SIEM 里看到的是一堆无法归属的 uid=100000。

9.3 服务上线前的安全 checklist

身份与权限

  • 进程不以 root 运行；镜像里显式 USER，K8s 里 runAsNonRoot: true（两处都写，防止镜像被换）。
  • --cap-drop=ALL，需要的 capability 逐个列出并写清理由；清单里没有 SYS_ADMIN。
  • no_new_privs / allowPrivilegeEscalation: false 已开。
  • 镜像里没有 setuid/setgid 二进制（构建时 find / -xdev -perm -4000 -type f -exec chmod u-s {} +）。
  • 代码里如果自己降权：setgroups → setgid → setuid 顺序正确、每一步检查返回值、事后 getresuid 复验。

隔离与文件系统

  • 根文件系统只读，可写目录用 tmpfs / 卷显式列出，并带 noexec,nosuid。
  • 没有 privileged、hostPID、hostNetwork、hostIPC。
  • 没有挂载 docker.sock / containerd.sock / 宿主 / / /etc / /var/run。
  • 必须挂的 hostPath 全部 readOnly: true，且路径尽可能具体（不要挂目录的父级）。
  • 已评估 user namespace 重映射（新集群建议直接开）。

系统调用与 MAC

  • seccompProfile: RuntimeDefault 已显式写上（不写就是 Unconfined）；高价值服务再上自定义白名单。
  • 自定义 seccomp profile 经过 LOG → ERRNO → KILL 三阶段灰度，且覆盖了错误分支与优雅退出路径。
  • SELinux 处于 Enforcing（或 AppArmor profile 处于 enforce），没有人为 disable。
  • 换基础镜像 / 升级 libc 后重新验证过 seccomp 白名单。

可观测与应急

  • auditd 规则已加载（auditctl -s 里 lost = 0），日志实时转发到集群外。
  • 运行时检测（Falco / Tetragon）已部署，至少一条规则做过端到端演练——不要等真出事才发现告警通道是断的。
  • 内核与容器运行时纳入常规补丁节奏，能回答「集群里最旧的内核是哪台、落后多少」。
  • 准入控制（Pod Security Standards / OPA / Kyverno）在集群侧兜底，不依赖每个团队自觉。
  • 云环境已强制 IMDSv2 并用网络策略拦住 169.254.169.254。
这份 checklist 的排序不是随意的：越靠前的越便宜、收益越大。如果只能做三件事，选非 root 运行、cap-drop ALL、只读根文件系统——这三条加起来改不了十行 YAML，却能让绝大多数「拿到 RCE 之后」的常规操作（装工具、落 webshell、改二进制、提权）全部失败。安全预算永远有限，先把这种投入产出比的事做完。

  1. 基础DAC 和 MAC 有什么区别？为什么有了 DAC 还要 MAC？

    DAC（自主访问控制）：权限由客体的属主自行决定——你的文件你想给谁看就给谁看，内核不干涉这个决定。Linux 的 uid/gid + 权限位就是 DAC。

    MAC（强制访问控制）：权限由系统级策略规定，属主无权修改，root 也不例外。SELinux、AppArmor 通过 LSM 框架实现。

    为什么需要 MAC，两个 DAC 补不上的洞：

    • 「自主」本身就是弱点：一个 chmod 777 就把防线拆了，而这可能是运维手滑，也可能是被攻陷的进程主动做的。
    • 粒度太粗：DAC 只认「属主 / 组 / 其他」三档。Web 服务被打穿后，攻击者以 apache 身份运行，DAC 下他能碰所有 apache 能碰的东西——包括其他站点的数据、日志、临时目录。MAC 下他被锁在 httpd_t 这个 type 里，策略没写 allow 的一律拒绝。
    一句话总结
    DAC 防的是「用户之间互相看」，MAC 防的是「一个被攻陷的进程能做多少事」。前者假设用户是善意的，后者不做这个假设。
    顺序很重要
    LSM 钩子在 DAC 和 capabilities 检查之后。所以 MAC 只能收紧不能放宽——DAC 已经拒绝的请求根本走不到 LSM。这个单调性保证了「加上 SELinux 最坏是把服务搞挂，不会悄悄开出一个洞」。
  2. 基础目录的 x 权限是什么含义？和 r 有什么区别？
    • r = 列出目录里有哪些名字（readdir）。没有它，ls 失败，但已经知道名字的文件仍然能访问。
    • x = 穿越——按名字把路径解析下去（stat、open、cd）。没有它，整棵子树完全不可达，连 stat 一个已知文件名都是 EACCES。
    • w（须配合 x）= 增删改名目录项。删除一个文件看的是它所在目录的 w，不是文件自己的权限——这一点最反直觉。

    所以 chmod 711 /home/alice 是一个有意义的配置：别人列不出你有哪些文件，但你可以把某个具体路径告诉他让他访问。

    最实用的推论
    路径解析要求路径上每一级目录都有 x。「文件明明是 644 却读不了」的头号原因就在上层某个目录。排查一条命令搞定：namei -l /path/to/file，它把每一级的权限和属主一行行列出来，断在哪一目了然。
    延伸
    /tmp 的 1777 里那个 1 是 sticky 位，正是为了堵住「目录 w = 能删别人文件」这个洞：加上它之后，只有文件属主（或目录属主、或有 CAP_FOWNER）才能删除。
  3. 基础进程为什么有三套 uid？setuid 程序里它们是怎么变化的？
    • real uid：你是谁，代表进程的真实归属，决定谁能给它发信号。
    • effective uid：你现在以谁的身份行事——所有权限检查用的都是它。
    • saved set-user-ID：execve 时保存的备份，让进程能在特权与非特权之间来回切而不丢失恢复能力。

    执行一个 setuid-root 程序（属主 root、模式 4755）时：ruid = 调用者的 uid（如 1000），euid = 文件属主 = 0，suid = euid = 0。之后 seteuid(1000) 可以临时放弃特权，因为 suid 还是 0，随时能 seteuid(0) 切回来。

    必须记住的铁律
    永久降权时顺序是 setgroups(0,NULL) → setgid → setuid，绝对不能反。因为 setuid() 在 euid==0 时会把三套 uid 一次性全设成目标值，这一步之后你不再是 root，后面的 setgid 会返回 EPERM。而绝大多数代码不检查这两个函数的返回值，于是进程以「uid 降了、gid 还是 0」的状态继续跑——特权只降了一半，是教科书级的提权漏洞模式。
    更好的写法
    用 setresuid / setresgid，三个值全部显式写出来。setuid 的语义取决于当前 euid 是不是 0（是则改三套，否则只改 euid），这种「行为随上下文变化」的 API 是漏洞温床。降完还要用 getresuid 复验，并试着 setuid(0)——能成功就说明没降干净。
  4. 基础capabilities 解决了什么问题？举两个常用的例子。

    它解决的是 root 全有全无的问题。传统 Unix 只有两类进程：uid 0 的（内核跳过绝大多数检查）和其他的。一个只需要 bind(80) 的 Web 服务器，为了那一个动作被迫拥有格式化磁盘、加载内核模块、读任意进程内存的能力——任何一个内存漏洞的收益都被放大到最大。

    capabilities 把 root 的特权切成 40 多个独立的位，按需授予。两个典型：

    • CAP_NET_BIND_SERVICE——绑定 1024 以下端口。最经典的「只需要这一个」场景，用 setcap 'cap_net_bind_service=+ep' ./myserver 就能替代整个 setuid-root。
    • CAP_NET_RAW——创建 RAW/PACKET socket，ping 和 tcpdump 需要它。反过来说，普通业务容器应该 drop 掉它，因为它能嗅探同网段流量、做 ARP 欺骗。
    必须一起说的一句
    CAP_SYS_ADMIN 约等于 root。它是历史上的垃圾桶，新特权操作找不到分类就往里塞，累积到今天覆盖一百多个操作，其中好几条（挂载文件系统、setns、cgroup v1 写 release_agent）可以直接换成完整 root。所以「只给它 SYS_ADMIN」不算最小权限。
    怎么看
    getcap 看文件、capsh --print 看当前进程、grep Cap /proc/PID/status 加 capsh --decode=<hex> 看某个正在跑的服务。

10.2 中级（区分熟练度）

  1. 中级capabilities 的五个集合分别是什么？execve 时怎么计算？
    集合含义
    Permitted被允许持有的上限，可随时往 Effective 里加（「钱包里有多少钱」）
    Effective内核当下真正检查的集合（「手里正拿着多少」）
    Inheritable与文件的 Inheritable 求交后可跨 execve 保留（需要「对方也同意」）
    Bounding天花板：这里没有的任何途径都拿不到；只减不增且不可逆
    Ambient（4.3+）能无条件跨过 execve，专为「非 root 且目标文件没有文件 cap」设计

    execve 后的计算（不含 root / setuid 特例）：

    P′(ambient)     = 文件带特权(setuid 或文件 cap) ? 0 : P(ambient)
P′(permitted)   = (P(inheritable) & F(inheritable))
                | (F(permitted)   & P(bounding))
                | P′(ambient)
P′(effective)   = F(effective) ? P′(permitted) : P′(ambient)
P′(inheritable) = P(inheritable)      P′(bounding) = P(bounding)
    三条足够用的结论
    ① 权限检查只看 Effective；② Bounding 是硬天花板，PR_CAPBSET_DROP 掉的位再也回不来——这正是它作为安全边界的价值；③ Inheritable 要传下去必须进程和文件双方都标了这一位，而普通脚本和解释器根本没有文件 cap，所以 Ambient 出现之前非 root 进程无法把能力传给自己 exec 的子程序，Ambient 就是补这个洞。
    高频实战坑
    代码里降权时忘了 prctl(PR_SET_KEEPCAPS, 1, …)。默认情况下 euid 从 0 变成非 0 时内核会清空 Permitted 和 Effective，所以必须先 KEEPCAPS 保住钱包，降完 uid 再从 Permitted 里挑要留的，否则 cap_set_proc 直接 EPERM。另外文件 cap 存在扩展属性里，cp 默认不保留——「本地好好的、打进镜像就绑不了端口」多半是这个。
  2. 中级seccomp 为什么必须先设置 no_new_privs？

    因为不这么要求的话，普通用户可以发起一次混淆代理人（confused deputy）攻击。关键在于 seccomp 过滤器会被 execve 继承：

    1. 攻击者（普通用户）先给自己装一个过滤器，让 setgroups() 静默返回成功（SECCOMP_RET_ERRNO(0)）。
    2. 然后 execve 一个 setuid-root 的程序。
    3. 那个特权程序按标准写法降权：setgroups(0,NULL)「成功」了（其实没生效）、setuid(user) 真的降了。
    4. 结果：uid 降了，但附加组还留着 root 的——特权程序在毫不知情的情况下被诱导留下了一个提权缺口。

    no_new_privs 是一个一旦置位就无法清除、且被子进程继承的标志，置位后 execve 不再因 setuid 位或文件 capability 提升权限。于是攻击者无论怎么扭曲系统调用语义，被坑的只有自己。所以内核的规则是：装 filter 要么有 CAP_SYS_ADMIN，要么 no_new_privs 已置位。

    怎么验证
    grep -E 'NoNewPrivs|Seccomp' /proc/self/status：NoNewPrivs: 1 且 Seccomp: 2（2 = filter 模式）。K8s 的 allowPrivilegeEscalation: false 设的就是这个位，systemd 里对应 NoNewPrivileges=yes。
    延伸
    这个设计体现了一条通用原则：「让低权限主体去影响高权限主体的行为」是所有权限模型都要堵的洞。LD_PRELOAD 对 setuid 程序失效、sudo 清洗环境变量、动态链接器对特权进程忽略某些路径，全是同一个模式的不同表现。
  3. 中级写 seccomp 白名单时最容易踩哪些坑？
    ① 拦到了 libc 内部用的调用
    你代码里一次都没写 futex，但只要用了 std::mutex 或某些惰性初始化就会调它；getrandom 被 glibc 的 malloc 和栈保护初始化用到；clock_gettime 在有 vDSO 时不走系统调用，换一台没配好 vDSO 的机器就走了——「同样的二进制在 A 机器好好的、B 机器一起来就 SIGSYS」。症状是进程无预警消失，dmesg 里一行 seccomp ... syscall=228，用 ausyscall 228 把号翻出来。
    ② 系统调用号是架构相关的
    x86-64 上 read=0，aarch64 上 read=63，直接搬数字等于随机放行。必须用 libseccomp 的 SCMP_SYS() 宏。更隐蔽的是 x86-64 上还有 i386 兼容 ABI 和 x32 ABI，调用号完全是另一套——不显式 seccomp_arch_add 就等于留了后门，这是历史上被多次利用的绕过手法。systemd 里对应 SystemCallArchitectures=native。
    ③ libc / 基础镜像升级后白名单失效
    glibc 在不同版本里可能把 open 换成 openat、stat 换成 newfstatat、poll 换成 ppoll。「什么都没改，换个基础镜像就挂」的常见根因，所以换基础镜像必须重新采集。
    正确流程
    先把默认动作设成 SCMP_ACT_LOG（放行 + 记日志），跑完整的功能与压测，包括错误分支、重连、优雅退出；用 ausearch -m SECCOMP 把实际用到的调用捞出来；人工审阅一遍（采集到的是「跑过的」不是「需要的」，看到 ptrace/mount 要先问为什么）；然后按 LOG → ERRNO(EPERM) → KILL_PROCESS 灰度。直接上 KILL 是拿线上做测试。
    还要知道的一条局限
    seccomp 只能看标量参数，不能解引用指针——这是刻意设计（否则有 TOCTOU：过滤器检查完之后另一个线程可以改掉那块内存）。所以「只允许打开某个路径」seccomp 做不到，那是 LSM 和 Landlock 的活。
  4. 中级SELinux 报 AVC denied，你的排查流程是什么？为什么不能直接关掉？

    排查流程（按顺序走）：

    1. ausearch -m AVC,USER_AVC -ts recent -i 找到那条记录。
    2. 逐字段读：denied { read } 是被拒的操作，scontext 是谁（进程的 type，如 httpd_t），tcontext 是对谁（客体的 type），tclass 是客体类别，permissive=0 表示真的拒了。
    3. audit2why 看内核给的解释——它会告诉你是不是有现成的 boolean 可以开。
    4. 按优先级处理：① matchpathcon 确认「应有的 label」，restorecon -Rv 修复；② getsebool -a 找现成开关，setsebool -P 打开；③ 非默认路径/端口用 semanage fcontext / semanage port 登记；④ 实在没有才用 audit2allow 写策略，而且先只打印不安装，逐条审掉 sys_admin、unlabeled_t 这类过宽规则。
    最常见的根因
    label 不对，而 label 不对的头号成因是用了 mv 而不是 cp：mv 在同一文件系统内只改目录项，label 原样跟着走；cp 创建新 inode，按目标路径规则打新标签。所以「从家目录 mv 一个网页到 /var/www」必然出问题。这也是「权限明明 777 却还是 Permission denied」的标准答案。
    为什么不能 disabled
    SELINUX=disabled 之后内核停止维护文件 label，期间新建和修改的文件全都没有正确 type。等哪天要重新开启（比如一次合规检查），整个文件系统的 label 已经烂了，开机后大量服务起不来，只能全盘 restorecon -R /——TB 级文件系统上这是几小时的停机。临时手段永远用 setenforce 0（Permissive）：不拦截但照常记录，label 继续维护，你既能让业务先跑，又拿到了完整的「要放开哪些」清单。

10.3 高级（体现深度）

  1. 高级namespace 到底没有隔离什么？这对容器安全意味着什么？

    先说最重要的一条：namespace 不隔离内核。宿主和所有容器共用同一份内核代码、同一份内核数据结构、同一张系统调用表。除此之外还有一批共享项：

    • 大部分 sysctl 是全局的。只有 net.*（netns）、kernel.hostname（utsns）、System V IPC 与 fs.mqueue.*（ipcns）等少数被命名空间化了。vm.max_map_count、fs.file-max、kernel.pid_max、kernel.core_pattern 全是全局的——所以 Elasticsearch 容器要求你在宿主上改 vm.max_map_count。
    • 内核 keyring只部分隔离；/sys/kernel、内核模块列表、硬件与 CPU 微架构状态（Spectre/Meltdown 类侧信道）完全共享。
    • time namespace（5.6+）只虚拟化 CLOCK_MONOTONIC / CLOCK_BOOTTIME 的偏移，墙上时间不隔离。
    • 物理资源：CPU 缓存、内存带宽、磁盘 IOPS、网卡队列——cgroup 能限额，但不能消除互相干扰。
    最直接的后果
    任何内核提权漏洞都直接是容器逃逸漏洞。Dirty COW（CVE-2016-5195）、Dirty Pipe（CVE-2022-0847）在容器里打和在宿主上打没有区别，不需要任何特殊配置。这就是「容器不是安全边界」这句话的真实含义——它对配置良好的自有工作负载不成立，对「拿容器隔离敌意代码」的场景则完全成立。
    怎么应对
    三条，按成本递增：① 补丁节奏——把内核与运行时纳入常规更新，并能度量「集群里最旧的内核是哪台」；② 开 user namespace，让逃逸拿到的是 uid 100000 而不是 root，降低利用价值；③ 对真正不可信的负载换 gVisor 或 Kata，把内核攻击面本身换掉。
  2. 高级user namespace 为什么既是加固手段又是攻击面？

    它是唯一一个普通用户无需特权就能创建的 namespace。在新的 user ns 里进程可以是 uid 0 并拥有该 namespace 内的全套 capability，但这些 capability 只对同属这个 namespace 的资源有效——内核做检查时会把「ns 内 root」翻译回宿主 uid。

    加固的一面：没有 user ns 时，容器里的 root 就是宿主的 root（uid 都是 0），只要有任何一条路径碰到宿主文件就是完整沦陷。开了之后容器 root 在宿主上只是 uid 100000，逃逸收益从「宿主 root」降级成「一个没有任何权限的陌生用户」。这是 Podman rootless、rootless Docker、K8s hostUsers: false 的核心价值。

    攻击面的一面：为了让「ns 内 root」这件事成立，普通用户获得了触达大量过去只有 root 才走得到的内核代码路径的能力——文件系统挂载解析、网络栈配置、cgroup 操作、setns…这些路径历史上的审计强度远低于常规路径（假设「反正只有 root 能走」），于是过去十年出现了相当数量以「非特权用户创建 user ns」为前置条件的本地提权 CVE。所以不少发行版做了限制：user.max_user_namespaces、Debian 的 kernel.unprivileged_userns_clone、较新 Ubuntu 的 kernel.apparmor_restrict_unprivileged_userns。

    这两件事经常被混为一谈，要分开看
    「给容器开 user ns」是明确的加固；「允许宿主上任意用户随便创建 user ns」是明确的风险。合理配置是两者兼顾：容器运行时用它，同时用 sysctl / AppArmor 限制普通用户滥用。
    落地代价
    Docker 的 userns-remap 与 --privileged、--pid=host、--net=host 以及部分卷挂载场景不兼容，已有卷的文件属主也会对不上（宿主看是 100000）。新集群从一开始就开最省事，中途切换要做迁移评估。另外写 gid_map 前必须先 echo deny > /proc/PID/setgroups，否则返回 EPERM——原因是不禁掉 setgroups 的话进程可以丢掉某个附加组，绕过「deny 某组」类的负权限规则。
  3. 高级为什么说 --privileged 容器等于没有容器？挂 docker.sock 的风险呢？

    --privileged 一次性做了五件事：capability 全给、seccomp profile 换成 unconfined（很多人只知道前半句）、AppArmor/SELinux 约束解除、/sys 变可写、宿主所有设备节点在 /dev 下可见。有了这些，容器里的 root 能直接看到宿主块设备并挂载它——宿主根文件系统就在眼前，写 authorized_keys 或投个 cron 都是顺手的事。剩下的只有 namespace 提供的「视图隔离」，而视图隔离对一个能挂载宿主磁盘的进程毫无意义。

    挂 docker.sock 比它更隐蔽，因为看起来「只是挂了一个文件」，而且 CI runner、监控面板的官方文档里到处都是这个写法。推理链只有三步：这个 socket 是 Docker 守护进程的完整控制 API → 通过它可以创建新容器且参数由你指定 → 于是可以创建一个 privileged 的、把宿主 / 挂进去的容器。不需要任何漏洞，这就是 API 的正常功能。containerd.sock、crio.sock、宿主上的 docker 组成员身份，全都等价于宿主 root。

    自查命令
    grep CapEff /proc/self/status 看到满值（如 0000003fffffffff）+ Seccomp: 0 + ls /dev 有上百项且能看到 /dev/sda —— 三条对上就是特权容器。socket 用 ls -l /var/run/docker.sock 和 mount | grep sock；顺带 id 看看在不在 docker 组。集群侧用 kubectl get pods -A -o json | jq 把 privileged=true 和挂了 /var/run 的 hostPath 全捞一遍。
    怎么修
    DinD 场景换 Kaniko / buildah / BuildKit rootless（不需要守护进程）；监控日志场景用只放行只读接口的 API 代理而不是把裸 socket 递进去；「我要设 sysctl / 挂 fuse / 用某个设备」这类需求几乎总能收窄到 --sysctl、--device、或宿主侧预备资源再挂进来。集群侧用 Pod Security Standards 的 restricted 档在准入时直接拒绝，别依赖每个团队自觉。
  4. 高级什么情况下需要 gVisor 或 Kata？它们各自的原理和代价是什么？

    先说判据，因为这是最容易答偏的地方：需不需要它们，取决于你是否要在同一台机器上运行「你不信任的代码」——用户提交的构建脚本、多租户函数计算、来路不明的第三方镜像。对「跑自己写的服务」的团队，把非 root、cap-drop ALL、只读根文件系统、RuntimeDefault seccomp 这几条落实到位，收益远大于换运行时且不用付性能账。

    gVisor（runsc）Kata Containers
    原理用户态内核：Sentry 进程用 Go 重新实现了大部分 Linux 系统调用语义，容器的调用先被拦到 Sentry；Sentry 自己再套一层很窄的 seccomp，宿主内核只剩几十个调用暴露给它每个 Pod 一个轻量 VM（Firecracker / QEMU），里面跑独立的 guest 内核，边界由硬件虚拟化强制
    攻击面宿主内核只对 Sentry 暴露一小部分；但 Sentry 自己是新代码，也有自己的漏洞面只暴露 hypervisor 接口，最小，且是硬件边界
    主要代价系统调用开销明显更高（多一层用户态转发），I/O 与 syscall 密集负载受影响大；兼容性不完整——冷门系统调用、部分 /proc /sys 项、某些 ioctl 不支持，上线前必须真跑一遍内存开销大（每 Pod 一份 guest 内核 + rootfs，上百 MB 起）、启动慢、I/O 要过 virtio；需要硬件虚拟化支持，嵌套虚拟化环境可能不可用
    适合多租户 SaaS、跑用户提交的代码、函数计算——负载偏计算、系统调用不密集时性价比最好强合规、强多租户、需要硬件级隔离保证；也更适合「必须完整内核兼容性」的负载
    共同的取舍本质
    两者都是在用性能和运维复杂度换一个更小的内核攻击面。gVisor 换的是「更少的宿主内核代码被触达」，Kata 换的是「一道硬件强制的边界」。K8s 里用 RuntimeClass 按工作负载选择，不必全集群一刀切——把不可信负载调度到 gVisor/Kata 节点池，可信负载留在 runc 上，是常见且合理的混合方案。
    别忘了它们不解决什么
    它们只解决「内核共享」这一条。挂了 docker.sock、把宿主目录挂进去、凭据写在环境变量里——这些问题换什么运行时都一样存在。先把配置层做对，再谈换运行时。
