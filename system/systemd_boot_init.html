01

从按下电源到 shell

五次交接，每一次都可能卡住

开机不是一件事，是一条接力链：固件把控制权交给引导器，引导器交给内核，内核交给 initramfs 里的 /init，/init 挂好真正的根后交给 /sbin/init（也就是 systemd），systemd 再把 default.target 依赖的所有服务拉起来。「开不了机」这句话毫无信息量——真正有用的第一步永远是判断它卡在哪一棒。

生活类比：接力赛的交接棒

固件是发令员，只负责把棒交到第一个人手里，它不关心后面跑什么。引导器是第一棒，任务是把「今天跑哪条赛道」（哪个内核、什么参数）定下来。内核是第二棒，但它出发时手里工具不全——真正的根文件系统可能在加密盘或网络存储上，它打不开。于是有了 initramfs 这个临时工具箱：第三棒背着工具箱把门撬开，然后把工具箱扔掉（switch_root 会释放这块内存），换真正的根接着跑。最后交给 systemd，由它同时派出几百个人去干活。

映射：赛道选择=内核与 cmdline · 临时工具箱=initramfs · 扔掉工具箱=switch_root · 同时派几百人=systemd 并行启动

UEFI 与传统 BIOS 的实质差别

这不是「新旧」的差别，而是「固件能不能读文件系统」的差别。传统 BIOS 只会做一件事：把磁盘第一个扇区（MBR，512 字节）读进内存并跳过去执行。512 字节写不下任何有意义的引导逻辑，所以 GRUB 不得不把自己拆成 stage1 / stage1.5 / stage2，其中 stage1.5 还得塞在 MBR 之后那段「保留间隙」里——一个纯粹为了绕开 512 字节限制而存在的历史包袱。

UEFI 固件自己就能读 FAT32，于是引导器可以是一个普通的可执行文件躺在 ESP 分区上，固件直接加载它。启动项也不再靠「哪块盘的第一个扇区」，而是记在主板 NVRAM 里的一张有序列表。

维度传统 BIOSUEFI
引导器存放MBR 512 字节 + 磁盘间隙ESP 分区（FAT32）里的 .efi 文件
分区表MBR，最多 4 主分区、2 TB 上限GPT，无实际数量限制
启动项管理只能选「从哪块盘启动」NVRAM 里的有序列表，用 efibootmgr 增删改
Secure Boot无校验引导器与内核签名；自编内核要签名或关掉它
典型故障装了新盘后 MBR 没写、间隙被覆盖ESP 没挂载 / 被格式化、NVRAM 启动项丢失

02

initramfs 到底做什么

一个为了解决「鸡生蛋」而存在的临时根
initramfs（initial RAM filesystem）：一个被打包成 cpio 归档、随内核一起加载进内存的临时根文件系统。内核挂载它、执行里面的 /init，由这个用户态程序完成「找到并挂载真正的根」，然后切换过去。

为什么非要它不可

这是个典型的鸡生蛋问题：内核要挂载根文件系统，但根文件系统可能在——

需要驱动的设备上

NVMe、RAID 卡、SAS HBA。驱动通常编译成模块（.ko），而模块存在根文件系统里——它还没挂上。

需要用户态工具组装的卷上

LVM 要 lvm 扫描并激活、软 RAID 要 mdadm 组阵列、LUKS 加密卷要 cryptsetup 和一次密码输入。这些都是用户态程序。

网络的另一端

iSCSI、NFS 根。得先配好网卡、拿到 IP、建立会话，才谈得上挂载。

把所有驱动和这些工具都编进内核？内核会膨胀到无法接受，而且发行版没法用一个通用内核适配所有硬件。于是把「打开门所需的最小工具集」单独打一个包，先让内核用它把门撬开。

hostonly：省空间，也埋雷

  • 发行版默认用 hostonly 模式生成 initramfs：只打包这台机器当前用得上的驱动和模块，体积从几百 MB 降到几十 MB。
  • 代价是它和当前硬件/存储布局强绑定。把系统盘拔到另一台机器、换了 RAID 卡、把根从 ext4 迁到 XFS、给根加了 LVM——只要 initramfs 没重建，开机就会停在「找不到根设备」。
  • 制作可迁移的镜像（云镜像、装机母盘）时要显式关掉：dracut 用 --no-hostonly，Debian 侧在 /etc/initramfs-tools/initramfs.conf 里设 MODULES=most。

经典故障 · Cannot open root device

现象：屏幕停在 Warning: /dev/mapper/vg0-root does not exist，几十秒后掉进 dracut 的 emergency shell（提示符是 dracut:/#）。

这条信息的含义非常明确：内核和 initramfs 都起来了（否则不会有这个 shell），只是 /init 没能把根设备变出来。九成是驱动或用户态工具缺失。在这个 shell 里可以直接查：

dracut:/# cat /proc/cmdline           # ① 确认 root= 参数本身对不对
root=/dev/mapper/vg0-root ro quiet

dracut:/# ls /dev/disk/by-uuid/       # ② 内核到底看见了哪些块设备
# 什么都没有 → 磁盘控制器驱动没打进 initramfs

dracut:/# lvm vgscan && lvm vgchange -ay   # ③ 手工激活 LVM 试试
  1 logical volume(s) in volume group "vg0" now active
dracut:/# ls /dev/mapper/
control  vg0-root                    ← 出来了！说明是 LVM 没被自动激活

dracut:/# exit                        # ④ 退出 shell，启动流程会继续往下走

处方：先用上面第 ③ 步把系统救进去，进系统后立刻 dracut -f 重建 initramfs 并确认包含了 lvm / dm 模块。如果 ls /dev/disk/by-uuid/ 完全为空，那就是控制器驱动的问题——要么用 --add-drivers 显式加入，要么关掉 hostonly 重建。

03

systemd 的心智模型

依赖有两个正交的维度，这是最大的坑

它到底解决了 SysV init 的什么问题

「systemd 太复杂」是常见抱怨，但它复杂是因为它接手的问题本来就复杂。SysV init 有三个结构性缺陷，不是靠写更好的 shell 脚本能绕过去的：

SysV init 的问题为什么脚本解决不了systemd 的做法
启动是串行的，靠 S01–S99 数字前缀排序脚本无法表达「A 和 B 互不相关，可以同时跑」，只能一个个等显式声明依赖，无依赖关系的 unit 全部并行；再用 socket 激活打破剩下的串行（§5）
追踪不住服务的进程守护进程双 fork 后与父进程脱离，PID 文件可能过期、可能被抢占、可能压根没写每个服务放进独立 cgroup，内核层面保证「这个服务的所有后代」可枚举、可一次性 kill（§6）
没有统一的状态模型「服务是否健康」靠每个脚本自己实现 status，行为千奇百怪统一的 active/failed/activating 状态机，配合 Restart= 与看门狗
Unit 类型管什么典型例子
.service一个服务进程nginx.service
.socket一个监听套接字，可按需拉起对应 servicesshd.socket
.target一组 unit 的同步点，取代 runlevelmulti-user.target
.timer定时触发，取代 cronlogrotate.timer
.mount / .automount挂载点（由 /etc/fstab 自动生成）data.mount
.path监视文件/目录变化并触发cups.path
.slicecgroup 层级里的一个资源分组节点system.slice
.scope不是 systemd 启动、但被它接管的外部进程组用户会话、容器运行时创建的进程

依赖的两个维度：需求 ≠ 顺序

这是 systemd 最反直觉、也最容易写错的一点：Requires= 只说「必须一起启动」，完全不管先后。如果你只写 Requires=postgresql.service，systemd 会同时启动数据库和你的应用——应用大概率先连上一个还没监听的端口然后失败退出。

维度指令含义
需求
（要不要一起启动 / 停止）		Requires=强依赖：对方启动失败或被停止，本 unit 也停。不含顺序
Wants=弱依赖：尝试一起启动，对方失败也不影响自己。绝大多数场景应该用它
BindsTo=比 Requires 更强：对方无论以何种方式进入非活动状态（包括设备被拔掉），本 unit 立刻停
Requisite=要求对方已经启动；没启动就直接失败，不会去拉它
Conflicts=互斥：启动本 unit 会先停掉对方
顺序
（谁先谁后）		After=本 unit 要等对方启动完成之后才开始。不含需求——如果对方压根没被启动，这条等于没写
Before=反向的 After
❌ 只写需求，不写顺序
[Unit]
Description=My API
Requires=postgresql.service

# 两者被同时启动，API 启动时
# 数据库可能还在做崩溃恢复
# → connection refused，服务反复重启
✅ 两个维度都写
[Unit]
Description=My API
Wants=postgresql.service
After=postgresql.service network-online.target
Requires=network-online.target

# 用 Wants 而不是 Requires：数据库偶发
# 重启不该把 API 一起拖下水，交给
# Restart= 和应用自己的重连逻辑处理
After=network.target 几乎总是不是你想要的。network.target 只表示「网络管理服务已经启动」，不表示网卡拿到了 IP。要等真正可用的网络得用 network-online.target，并且必须同时 Wants=network-online.target——因为这个 target 默认不会被拉起，只写 After= 的话它根本不在启动集合里，那条 After 就是一句空话。这是「服务开机起不来、手动 restart 却好」这个经典现象的头号原因。

覆盖优先级与 drop-in

同名 unit 可能出现在三个地方，后者整体覆盖前者：

路径归谁优先级
/usr/lib/systemd/system/发行版软件包最低
/run/systemd/system/运行时动态生成，重启即失中
/etc/systemd/system/管理员最高

但整体覆盖意味着你得把整个文件抄一份，之后上游改了什么你都收不到。正确做法是 drop-in：在 /etc/systemd/system/<unit>.d/ 下放一个 .conf 片段，只写要改的那几行。

# 用 systemctl edit 自动创建 drop-in（推荐，它会帮你建目录、改完自动 daemon-reload）
$ sudo systemctl edit nginx.service
# 编辑器里只写要覆盖的部分：
[Service]
LimitNOFILE=65535
Restart=always

# 落到这里：
$ cat /etc/systemd/system/nginx.service.d/override.conf

# 看「最终生效」的完整配置（含所有 drop-in 合并后的结果）
$ systemctl cat nginx.service
# /usr/lib/systemd/system/nginx.service
...原始内容...
# /etc/systemd/system/nginx.service.d/override.conf
[Service]
LimitNOFILE=65535

# 查某个具体属性的最终值——比读文件可靠，它是问 systemd 要的运行时值
$ systemctl show nginx.service -p LimitNOFILE -p Restart
LimitNOFILE=65535
Restart=always

列表类指令的覆盖有个陷阱

  • ExecStart=、Environment= 这类可以出现多次的指令，drop-in 里再写一条是追加而不是替换。ExecStart 出现两次会直接报错（Type=oneshot 除外）。
  • 要替换必须先用空值清空：ExecStart=（等号后什么都不写）另起一行再写新的。这条规则不知道的人几乎必踩。
  • 改完任何 unit 文件都要 systemctl daemon-reload，否则 systemd 用的还是内存里的旧版本。systemctl edit 会自动做，手工改文件不会。
04

service unit 详解

Type= 和 Restart= 是两个最常配错的地方

Type=：「服务算启动完成」的判定时刻

Type= 唯一的作用就是回答一个问题：systemd 在什么时刻认为这个服务「起来了」，可以去启动依赖它的下一个服务？选错的后果不是服务跑不起来，而是依赖顺序全乱或者systemd 认为服务挂了。

Type=何时算「启动完成」用在什么程序上
simple（默认）fork() 一执行完就算——不等程序真的初始化好前台运行、不 daemonize 的程序。绝大多数现代服务
exec等到 execve() 成功返回。比 simple 严一点，能捕获「二进制不存在」这类错误同 simple，能用就优先用它
forking父进程退出时算完成，systemd 去追踪 fork 出来的子进程传统的自我 daemonize 程序。必须配 PIDFile=
oneshot进程执行完退出才算完成。默认状态是 inactive 而非 active一次性初始化脚本。配 RemainAfterExit=yes 可让它保持 active
notify程序自己调 sd_notify(READY=1) 时才算最准确。程序真正加载完配置、监听好端口后才通知
dbus在 D-Bus 上拿到指定 name 时算完成D-Bus 服务
idle等其它 job 都派发完再启动，避免刷屏只是为了控制台输出好看，不要用它做依赖控制
❌ 程序自己 daemonize，却写 simple
[Service]
Type=simple
ExecStart=/usr/sbin/myd    # 内部 fork 后父进程退出

# systemd 看到「主进程」退出了 →
# 认为服务失败 → 按 Restart= 又拉一次
# → 无限重启，而真正的 daemon
#   每次都残留在后台，越堆越多
✅ 让它别 daemonize
[Service]
Type=exec
ExecStart=/usr/sbin/myd --foreground

# 现代程序基本都有 --foreground /
# --no-daemon / -D 之类的开关。
# 优先用前台模式，把进程管理彻底
# 交给 systemd，而不是用 forking
# 去迁就一个过时的守护化习惯。

Restart= 与那个让人抓狂的限流

Restart=什么情况下重启
no（默认）从不
on-failure非零退出码、被信号杀死、超时、看门狗触发。最常用
on-abnormal只在被信号杀死 / 超时 / 看门狗时；正常的非零退出不重启
on-abort只在收到未捕获信号时
always无论怎么退出都重启，包括 exit 0。会让 systemctl stop 之外的一切退出都被拉起
最经典的坑：服务崩溃后重启了几次，然后再也不起来了，systemctl start 报 start request repeated too quickly。这是 StartLimitBurst（默认 5 次）/ StartLimitIntervalSec（默认 10 秒）在起作用——设计意图是防止一个必然失败的服务把机器 CPU 打满，但它常常被误认为「systemd 坏了」。清除计数用 systemctl reset-failed <unit>，不是 daemon-reload。如果服务确实需要频繁重启，把 RestartSec 调大（比如 5s）比放宽限流更合理——那才是在治因。
$ sudo systemctl start myapi
Job for myapi.service failed.
See "systemctl status myapi.service" and "journalctl -xeu myapi.service" for details.

$ systemctl status myapi
     Loaded: loaded (/etc/systemd/system/myapi.service; enabled)
     Active: failed (Result: start-limit-hit) since Thu 2026-09-03 18:22:41 CST
#                            ↑ 关键词：不是程序失败，是被限流挡住了

$ sudo systemctl reset-failed myapi     # 清掉计数
$ sudo systemctl start myapi            # 现在能起了

# 想调整阈值（注意：这两个指令在 [Unit] 段，不是 [Service]）

sd_notify 与看门狗

Type=notify 让程序自己说「我准备好了」，这比 systemd 靠 fork 时刻瞎猜准确得多。配合 WatchdogSec= 还能让程序定期报平安，超时没报就被判定为卡死并重启——这能抓住「进程还在、但已经死锁不干活」这类用退出码发现不了的故障。

#include <systemd/sd-daemon.h>   // 链接 libsystemd

int main(void) {
    load_config();
    bind_and_listen();                      // 真正准备好之后……
    sd_notify(0, "READY=1");              // ……才通知 systemd

    // 看门狗：从环境变量 WATCHDOG_USEC 读出周期，按一半的间隔喂狗
    uint64_t usec = 0;
    int wd = sd_watchdog_enabled(0, &usec);

    while (running) {
        serve_one_round();
        if (wd > 0) sd_notify(0, "WATCHDOG=1");   // 喂狗
    }

    sd_notify(0, "STOPPING=1");           // 优雅退出时告知，让 systemd 别当成崩溃
    return 0;
}
// ⚠ 喂狗必须放在真正的工作循环里。放在一个独立线程里定时喂 —— 那只能证明
//    "喂狗线程还活着"，主逻辑早就卡死了你也发现不了，等于自欺欺人。

05

socket 激活与并行启动

systemd 打破启动串行的核心武器

并行启动最难的部分不是「同时跑」，而是依赖：客户端要等服务端监听好端口。传统做法只能串行等待。systemd 的洞见是：让 systemd 自己先把所有监听套接字建好，然后所有服务同时启动——客户端连过去的连接会静静躺在内核的 accept 队列里，等服务端起来了再取走。连接不会被拒绝，只会被延迟，于是依赖顺序凭空消失了。

生活类比：先装信箱，再搬进来

传统做法是「等 A 搬完家、装好信箱，B 才敢往那儿寄信」，一家一家串行。socket 激活相当于物业先把整栋楼的信箱全装好，然后所有住户同时搬家。B 现在就能寄信——信投进信箱躺着，A 搬完了自己去取。谁先搬完不重要，信一封都不会丢。

映射：信箱=监听 socket · 物业统一安装=systemd 提前 bind/listen · 信躺在信箱里=内核 accept 队列 · 不丢信=连接不被 refuse

同一个机制顺带解决了另外两件事：按需启动（第一个连接到来时才拉起服务，机器上几十个低频服务可以都不常驻）和零停机重启（监听 socket 由 systemd 持有，服务进程重启期间它一直开着，新连接照样排队）。

#include <systemd/sd-daemon.h>

// 并通过环境变量 LISTEN_FDS 告诉你有几个、LISTEN_PID 防止 fd 被子进程误用。
int n = sd_listen_fds(1);        // 参数 1 = 用完后清掉这些环境变量
if (n < 0) { /* 出错 */ }

    listen_fd = create_listen_socket(8080);

    listen_fd = SD_LISTEN_FDS_START;   // == 3
    // 校验一下类型对不对，别把 socket 当成别的 fd 用

// 之后正常 accept 即可。★ 保留"没有 fd 就自己 bind"这条分支很重要，
//    否则程序脱离 systemd 就跑不起来，本地开发和容器里都会很难受。

fd 是怎么跨进程继承过来的、为什么 3 号是第一个可用编号，见 文件描述符深入；用 Unix 域套接字主动传 fd 的做法见 多进程与 IPC。

用它做零停机重启

  • systemctl restart myapi.service（不带 .socket）：socket unit 保持 active，监听 fd 一直由 systemd 持有，服务进程重建期间新连接在 accept 队列里排队。客户端感知到的只是一次几百毫秒的延迟，不是 connection refused。
  • 如果误敲了 systemctl restart myapi.socket，监听 fd 会被关闭重建，那就真的会短暂拒连了。
  • 要看 socket 当前状态：systemctl status myapi.socket 会显示 Listen: 0.0.0.0:8080 (Stream) 和已接受的连接数。

systemd 与 cgroup

它是 cgroup v2 层级的唯一管理者

systemd 把每个服务放进独立的 cgroup，这不只是为了限资源——更根本的价值是「可靠地知道一个服务包含哪些进程」。PID 文件会过期、会被抢占、双 fork 后追踪不到；而 cgroup 是内核维护的、进程无法逃逸的成员关系。「一个服务的所有后代」这件事第一次变得可枚举、可一次性 kill。

systemd 指令对应的 cgroup v2 接口说明
CPUQuota=200%cpu.max200% = 2 个核。超额被 throttle，不是被杀
CPUWeight=（1–10000，默认 100）cpu.weight相对权重，只在 CPU 争用时起作用。比 Quota 更适合大多数场景
MemoryMax=4Gmemory.max硬上限，超了先回收、回收不出来就 OOM kill
MemoryHigh=3Gmemory.high软限，超了持续加压回收但不杀。配合 Max 使用能把硬杀变成先预警
IOWeight=io.weight块设备 I/O 相对权重
TasksMax=pids.max进程/线程数上限，防 fork 炸弹
AllowedCPUs=cpuset.cpus绑核。新线程自动继承，比 taskset 可靠
Delegate=yes把子树交给服务自己管容器运行时必须开，否则它没法在自己下面建 cgroup

unit 级安全加固

不改一行代码就能收窄攻击面

这一章可能是整篇性价比最高的部分：在 unit 文件里加十几行，就能把一个服务被攻破后的杀伤范围压缩一个数量级。底层用的是 namespace、capabilities、seccomp、LSM 那一套（原理见 Linux 安全模型），但 systemd 把它们包装成了声明式指令，不需要改代码、不需要写 seccomp 过滤器。

指令效果注意
NoNewPrivileges=yes禁止通过 setuid 二进制提权几乎所有服务都该开。它也是 seccomp 生效的前提
ProtectSystem=strict整个文件系统只读，只有 /dev、/proc、/sys 例外必须配 ReadWritePaths= 放出真正要写的目录
ProtectHome=yes/home、/root、/run/user 不可见系统服务基本都该开
PrivateTmp=yes独立的 /tmp 与 /var/tmp顺带消灭了一整类 /tmp 竞态漏洞
PrivateDevices=yes只给一组伪设备，看不到真实块设备需要访问硬件的服务不能开
ProtectKernelTunables=yes/proc/sys、/sys 只读防止服务改内核参数
ProtectKernelModules=yes禁止加载/卸载内核模块—
ProtectControlGroups=yes/sys/fs/cgroup 只读挡住经典的 cgroup 逃逸路径
CapabilityBoundingSet=限定能持有的 capability 上界留空即全部丢弃；只保留真正需要的那一两个
RestrictAddressFamilies=只允许指定的 socket 协议族不用 AF_NETLINK、AF_PACKET 的服务应显式排除
SystemCallFilter=@system-serviceseccomp 白名单，用预定义集合比手写过滤器省事得多；配 SystemCallErrorNumber=EPERM 让被拦的调用返回错误而不是直接杀进程

journald 日志

二进制格式换来的和失去的

journald 把日志存成带索引的二进制文件，而不是纯文本。这个选择让很多老 Linux 用户不适应，但取舍是清楚的：

换来了失去了
每条日志带结构化字段（_SYSTEMD_UNIT、_PID、_UID、_BOOT_ID、PRIORITY…），可以精确过滤而不是 grep 猜不能直接 cat / grep / tail，必须通过 journalctl
按 unit、按启动轮次、按优先级、按时间范围检索都是索引查询，不是全文扫描文件损坏时比文本更难抢救（有 journalctl --verify）
自动附加不可伪造的元数据（进程真实 UID、cgroup 路径），日志无法被应用冒名常规的文本工具链（logrotate、awk 管道）要改用 -o cat 或转发到 rsyslog
自带轮转与容量控制，不需要额外的 logrotate 配置默认不持久化，重启就没了——这是最常见的踩坑

systemd.unit=emergency.target只挂了根（而且是只读），几乎没有服务rescue 都进不去时用。改文件前要先 mount -o remount,rw /
init=/bin/bash完全不启动 systemd，内核直接 exec 一个 shell最后手段：systemd 本身坏了、或要改 /etc/fstab 里的致命错误。此时没有任何服务、根是只读、不能用 reboot（要 sync 后 echo b > /proc/sysrq-trigger）

典型场景 · 加了一行 fstab 之后机器起不来了

现象：给 /etc/fstab 加了一个数据盘挂载，重启后卡在 A start job is running for /data，倒计时 1 分 30 秒后掉进 emergency 模式。

原因是 systemd 会把 /etc/fstab 的每一行生成成一个 .mount unit，并让 local-fs.target 依赖它们。设备不存在（拔了、UUID 写错、盘符变了）时，这个 mount job 会一直等到 DefaultTimeoutStartSec（默认 90 秒）超时，然后整个 local-fs.target 失败，启动中断。

# 救援：GRUB 里加 init=/bin/bash，进去后
bash-5.1# mount -o remount,rw /
bash-5.1# vi /etc/fstab              # 注释掉那一行，或加上 nofail
bash-5.1# sync
bash-5.1# echo b > /proc/sysrq-trigger    # 强制重启（此时 reboot 命令不可用）

# 正确的写法：非关键挂载一律加 nofail，最好再给一个短超时
UUID=8f3c-...  /data  ext4  defaults,nofail,x-systemd.device-timeout=10s  0 2
#                                  ↑ 设备不在就跳过，不阻塞开机
#   改完 fstab 后一定要先 systemctl daemon-reload && mount -a 验证一遍，
#   千万别改完直接 reboot —— 这是最容易把远程机器搞到失联的操作之一。

启动与服务排障速查

  • 先分清卡在哪一棒：屏幕最后一条信息属于固件 / GRUB / 内核 / initramfs / systemd 中的哪一段（§1）。
  • 服务起不来 → systemctl status 看 Result:，再 journalctl -xeu <unit> -b。
  • 报 start-limit-hit → systemctl reset-failed，然后去查它为什么一直崩，别只放宽阈值。
  • 手动能起、开机不能起 → 八成是缺 Wants=network-online.target + After=，只写 After=network.target 无效。
  • 改了配置没生效 → systemctl daemon-reload；用 systemctl cat 确认最终合并结果，用 systemctl show -p X 确认运行时值。
  • 覆盖列表类指令（ExecStart、Environment）→ 先写一行空值清空再写新值。
  • 优化开机速度 → 只看 critical-chain，不要按 blame 排序砍服务。
  • 改 /etc/fstab → 非关键挂载加 nofail；改完先 daemon-reload && mount -a 验证再重启。
  • 生产机器 → 开 journald 持久化、配串口控制台，这两件事必须在出事之前做好。
  • 新服务上线 → 跑一次 systemd-analyze security，把 exposure 压到 5 以下。

面试题（12 道）

分层自测

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础为什么需要 initramfs？没有它行不行？

    因为存在一个鸡生蛋的问题：内核要挂载根文件系统，但挂载它所需的东西又在根文件系统里。具体分三类：

    • 需要驱动：NVMe、RAID 卡、SAS HBA 的驱动通常是模块（.ko），而模块存在还没挂上的根里。
    • 需要用户态工具：LVM 要 lvm 激活、软 RAID 要 mdadm 组阵列、LUKS 要 cryptsetup 和一次密码输入——这些都是用户态程序，内核自己做不了。
    • 需要网络：iSCSI / NFS 根要先配好网卡拿到 IP。

    行不行？行，但有前提：如果把所需驱动全部编译进内核（=y 而非 =m），且根文件系统是简单分区（没有 LVM / RAID / 加密），就可以不用 initramfs 直接 root=/dev/sda2 启动。嵌入式系统经常这么做。发行版不能这么做，是因为它要用一个通用内核适配千奇百怪的硬件，全编进去内核会大到不可接受。

  2. 基础Requires= 和 After= 有什么区别？只写一个会怎样？

    它们是两个正交的维度，这是 systemd 最容易被搞混的地方：

    • Requires= 管需求：「必须一起启动，对方失败/停止我也停」。完全不管先后顺序。
    • After= 管顺序：「要等对方启动完成我才开始」。完全不管对方要不要被启动。

    各自漏写的后果：

    • 只写 Requires=：两者被同时启动，你的服务大概率在数据库还没监听时就去连接，然后失败退出。
    • 只写 After=：如果对方压根不在本次启动的集合里，这条 After 等于一句空话——没有人会去启动它，你也就"等"了个寂寞。network-online.target 就是最典型的例子。

    实践上推荐 Wants= + After= 的组合：既保证顺序，又不会因为依赖偶发故障而把自己一起拖下水，重连交给应用自己和 Restart= 处理。

  3. 基础服务日志重启后就没了，为什么？

    因为 journald 默认把日志写在 /run/log/journal，而 /run 是 tmpfs（内存文件系统），重启即清空。这是发行版为了不预设「你想留日志」而做的保守默认，但对生产机器来说恰恰最要命——机器意外重启后，你最想看的那段日志正好没了。

    开持久化只要让 /var/log/journal 目录存在即可（journald 检测到它就自动改用持久存储），或者在 /etc/systemd/journald.conf 里显式写 Storage=persistent：

    sudo mkdir -p /var/log/journal
sudo systemd-tmpfiles --create --prefix /var/log/journal
sudo systemctl restart systemd-journald

    开完记得配容量上限（SystemMaxUse=），否则日志可能把 /var 撑满。查历史用 journalctl -b -1 看上一次启动，这是排查「机器为什么重启」的关键入口。

  4. 基础改了 unit 文件为什么没生效？

    三个层层递进的原因，按顺序排查：

    1. 忘了 systemctl daemon-reload。systemd 把 unit 配置缓存在内存里，不重新加载就还是旧的。systemctl edit 会自动 reload，手工改文件不会。
    2. 改错了文件。/etc/systemd/system/ 下的同名文件会整体覆盖 /usr/lib/systemd/system/ 里的——你改了后者，前者还在那儿挡着。用 systemctl cat <unit> 看真正生效的是哪几个文件。
    3. 改了但语义不对。列表类指令（ExecStart、Environment）在 drop-in 里再写一条是追加不是替换，要先写一行空值（ExecStart=）清空再写新的。

    最终确认手段是 systemctl show <unit> -p <属性>——它返回的是 systemd 运行时真正持有的值，比读任何文件都可靠。

10.2 中级（区分熟练度）

  1. 中级Type=simple 和 Type=forking 分别在什么时刻算「启动完成」？选错会怎样？

    Type= 唯一的作用是回答「systemd 什么时候认为服务起来了、可以去启动下一个」：

    • simple：fork() 一执行完就算完成，不等程序真正初始化。
    • forking：父进程退出时才算完成，systemd 转而追踪 fork 出来的子进程（需要 PIDFile= 帮它确认主进程）。

    两种选错方式：

    • 程序会自我 daemonize，却写了 simple：systemd 看到"主进程"退出，判定服务失败，按 Restart= 又拉一次——无限重启，而真正的 daemon 每轮都残留在后台越堆越多。
    • 程序是前台的，却写了 forking：systemd 一直等父进程退出，等到 TimeoutStartSec 超时，判定启动失败并把它杀掉——尽管服务其实跑得好好的。

    最佳实践是都别用：现代程序基本都有 --foreground 之类的开关，用 Type=exec（比 simple 严格，能捕获 execve 失败）；如果程序支持 sd_notify，用 Type=notify 最准确——它保证依赖它的服务启动时，端口是真的已经在监听了。

  2. 中级socket 激活的价值是什么？为什么它能打破启动依赖？

    核心洞见：依赖的本质是「客户端要等服务端监听好端口」，而这个 bind/listen 可以由 systemd 提前统一做掉。

    systemd 在启动任何服务之前，先把所有 .socket unit 声明的监听套接字全部建好，然后所有服务同时启动。此时客户端连过去，连接会静静躺在内核的 accept 队列里，等服务端起来后再取走。连接不会被拒绝，只会被延迟——依赖顺序就凭空消失了。

    顺带解决另外两件事：

    • 按需启动：第一个连接到来时才拉起服务，机器上几十个低频服务可以都不常驻。
    • 零停机重启：监听 fd 由 systemd 持有，systemctl restart myapi.service（不带 .socket）期间 socket 一直开着，客户端感知到的只是几百毫秒延迟而不是 connection refused。

    程序侧改动很小：用 sd_listen_fds() 拿继承来的 fd（从 SD_LISTEN_FDS_START 即 3 号开始），代替自己的 bind/listen。要保留"没有继承 fd 就自己 bind"的分支，否则脱离 systemd 就跑不起来，本地调试和容器里都很难受。

  3. 中级systemd 和 cgroup 是什么关系？为什么说它比 PID 文件可靠？

    systemd 是 cgroup v2 层级的唯一管理者：它把整棵树切成 system.slice（系统服务）/ user.slice（登录会话）/ machine.slice（虚拟机与容器），每个服务在下面有自己的 cgroup 节点。

    相比 PID 文件的优势不在于"限资源"，而在于可靠地知道一个服务包含哪些进程：

    • PID 文件可能过期（进程死了文件还在）、可能被抢占（PID 复用后指向了别人）、可能压根没写；双 fork 之后更是完全追踪不到。
    • cgroup 的成员关系由内核维护，进程无法逃逸——fork 出来的所有后代自动属于同一个 cgroup。于是"停止服务"可以真正做到把整组进程一次性干净地终结，不留孤儿。

    资源限制是附带收益：CPUQuota= / MemoryMax= / TasksMax= 这些指令直接映射到 cpu.max / memory.max / pids.max。限额加在 .slice 上对整组生效，加在 .service 上只作用于单个服务。

    相关的还有 KillMode=：默认 control-group 会把 SIGTERM 发给 cgroup 内所有进程；mixed 只给主进程（适合 nginx 这类自己编排子进程退出顺序的）；process 不管子进程，几乎不该用。

  4. 中级服务手动 start 能起来，开机却起不来。怎么查？

    手动能起说明程序和配置本身没问题，差别只在「环境」——开机时某些东西还没准备好。按这个顺序查：

    1. journalctl -u <unit> -b 看开机那次的实际报错，这是唯一的一手证据。
    2. 最常见的原因是网络依赖写错了。After=network.target 只表示"网络管理服务已启动"，不表示网卡拿到了 IP。要等真正可用的网络必须用 network-online.target，而且要同时写 Wants=network-online.target——这个 target 默认不会被拉起，只写 After= 的话它根本不在启动集合里，那条 After 形同虚设。
    3. 其它依赖没就绪：数据库还在崩溃恢复、要写的目录所在的挂载点还没挂上（应显式 After=<path>.mount）、DNS 还不可用。
    4. 环境变量差异：你手动 start 时继承的是 root shell 的环境，开机时没有。用 EnvironmentFile= 显式提供，别依赖 PATH 里有什么。
    5. 确认真的 enable 了：systemctl is-enabled <unit>。没有 [Install] 段的 unit 执行 enable 会报错，而那个错误常常没人看。

10.3 高级（体现深度）

  1. 高级systemd-analyze blame 排第一的服务，砍掉它开机就会变快吗？

    不一定，多数情况下不会。blame 给的是「每个 unit 各自花了多久」，不是「它拖慢了开机多久」。这两者只有在串行启动的世界里才等价，而 systemd 的核心特性恰恰是并行。

    • 一个耗时 20 秒、但和所有人并行、谁都不等它的服务，对开机总时长的贡献是 0。
    • 一个只花 200 毫秒、却卡在关键链条中间的服务，可能让它后面几十个服务全部排队。

    要优化开机速度必须看 systemd-analyze critical-chain——它输出的是真正的串行关键路径，每一行的 @ 是这个 unit 变为 active 的绝对时刻，+ 是它自己花的时间。只有压缩这条链上的节点才有意义。

    再往上一层：systemd-analyze 的总览会把时间分成 firmware / loader / kernel / initrd / userspace 五段。如果大头在 firmware（BIOS 自检、RAID 卡扫盘）或 loader（GRUB 超时），那和 systemd 一点关系都没有，去调 BIOS 设置和 GRUB_TIMEOUT 才对。

    systemd-analyze plot > boot.svg 能生成完整的甘特图，最直观地看出谁在等谁。

  2. 高级rescue.target、emergency.target 和 init=/bin/bash 分别在什么情况下用？

    三者的差别是系统被恢复到了哪一步，按「能力从多到少」排列，原则是能用温和的就别用激烈的：

    • systemd.unit=rescue.target：根已挂载且可写，基础服务已启动，只是没有网络和图形。systemctl、journalctl 都能用——绝大多数配置错误在这里就能修完。首选。
    • systemd.unit=emergency.target：只挂了根，而且是只读的，几乎没有任何服务。rescue 都进不去时才用（比如某个 local-fs.target 依赖的挂载失败导致 rescue 也起不来）。改文件前必须先 mount -o remount,rw /。
    • init=/bin/bash：完全绕过 systemd，内核挂上根之后直接 exec 一个 shell。用于 systemd 自身损坏、或 /etc/fstab 里有致命错误导致连 emergency 都进不去。此时环境极其原始：没有任何服务、根是只读、reboot 命令不可用（它要跟 systemd 通信）。改完要 sync 然后 echo b > /proc/sysrq-trigger 强制重启。

    加分点：说清为什么会需要救援比背命令更重要。最高频的触发场景是改 /etc/fstab——systemd 会把每一行生成成 .mount unit 并让 local-fs.target 依赖它，设备不存在时会阻塞到超时（默认 90 秒）然后整个启动中断。正确做法是非关键挂载一律加 nofail 和 x-systemd.device-timeout=10s，并且改完先 daemon-reload && mount -a 验证再重启，不要直接 reboot 远程机器。

  3. 高级为什么容器里 PID 1 常常收不到 SIGTERM？这和 systemd 作为 PID 1 有什么共同点？

    内核对 PID 1 有一条特殊规则：它不会响应自己没有安装处理函数的默认信号。普通进程收到 SIGTERM 而没装 handler 时会被默认终止，PID 1 则会直接忽略。这是内核的保护机制——防止一次误发的信号把 init 干掉、导致内核 panic。

    用在容器上就成了坑：业务进程直接当 PID 1 却没显式处理 SIGTERM，docker stop 发的信号石沉大海，等 10 秒超时后被 SIGKILL 硬杀——优雅退出逻辑一次都没跑过。还有个变体：ENTRYPOINT 是 shell 脚本且写成 ./app 而非 exec ./app，此时 PID 1 是 shell，信号根本传不到 app。

    PID 1 的另一项职责是回收孤儿进程：所有失去父进程的进程都会被过继给它，它必须调 wait() 收尸，否则僵尸堆积耗尽 PID。

    共同点：systemd 和 tini 本质上在做同一件事——当一个称职的 init。两者都显式安装信号处理函数并做转发，都负责回收所有过继来的孤儿。区别只是规模：tini 是几百行的极简版，systemd 还额外承担了服务编排、cgroup 管理、日志、socket 激活。所以容器里的解法要么 docker run --init 注入 tini，要么在 ENTRYPOINT 里用 exec 让业务进程成为 PID 1 并自己处理 SIGTERM。相关内容见 容器底层原理。

  4. 高级不改一行代码，怎么把一个服务被攻破后的杀伤范围压到最小？

    用 systemd 的 unit 级沙箱指令。它们底层就是 namespace、capabilities、seccomp、mount 只读那一套，但被包装成了声明式配置，不需要改代码、不需要手写 seccomp 过滤器。按收益排序：

    • User= 非 root 运行——这一条的收益超过后面所有条加起来。
    • NoNewPrivileges=yes：禁止通过 setuid 二进制提权，同时也是 seccomp 生效的前提。
    • ProtectSystem=strict + ReadWritePaths=：整个文件系统只读，只放开真正要写的几个目录。攻击者拿到 RCE 也改不了任何二进制或配置。
    • PrivateTmp=yes：独立 /tmp，顺带消灭一整类 /tmp 竞态漏洞。
    • CapabilityBoundingSet=：留空即全部丢弃，只加回真正需要的（比如绑定低端口只需要 CAP_NET_BIND_SERVICE）。
    • SystemCallFilter=@system-service + SystemCallErrorNumber=EPERM：用预定义集合做 seccomp 白名单，被拦的调用返回错误而不是直接杀进程（便于排查）。
    • RestrictAddressFamilies=、ProtectKernelTunables=、ProtectKernelModules=、ProtectControlGroups=：分别挡住裸 socket、改内核参数、加载模块、cgroup 逃逸这几条路。

    验证手段是 systemd-analyze security <unit>，它会逐条打分并给一个 0–10 的 exposure 总分。什么都不配的默认 unit 通常在 9 分（UNSAFE），加完上述指令一般能降到 2–4。

    工程上的关键提醒：逐条加、每加一条重启验证一次。ProtectSystem=strict 和 SystemCallFilter= 最容易把服务搞挂——前者会让漏列的写路径失败，后者可能拦掉 libc 内部用的调用。一次性全加上，出问题时你根本不知道是哪条。被 seccomp 拦住时 journal 里有明确记录。
