01

从按下电源到 shell

五次交接，每一次都可能卡住

开机是五次交接。「开不了机」没有信息量——第一步永远是看屏幕最后一条信息属于哪一棒：往前的都已经成功。第 ①②④ 棒没有 journald，只能靠屏幕和串口；第 ⑤ 棒开始才有日志。

生活类比：接力赛的交接棒

固件发令；GRUB 选赛道（内核与 cmdline）；内核出发时工具不全，initramfs 是临时工具箱，撬开门后 switch_root 把它扔掉；systemd 再同时派出几百人。

映射：赛道=cmdline · 工具箱=initramfs · 扔掉=switch_root · 同时派人=并行启动

UEFI 与传统 BIOS 的实质差别

差别不是「新旧」，是固件能不能读文件系统。BIOS 只会把 MBR 头 512 字节读进内存再跳转，GRUB 才被迫拆成 stage1 / stage1.5 / stage2。UEFI 自己读 FAT32，引导器是 ESP 上一个普通 .efi，启动项记在 NVRAM。

维度传统 BIOSUEFI
引导器存放MBR 512 字节 + 磁盘间隙ESP 分区（FAT32）里的 .efi 文件
分区表MBR，最多 4 主分区、2 TB 上限GPT，无实际数量限制
启动项管理只能选「从哪块盘启动」NVRAM 里的有序列表，用 efibootmgr 增删改
Secure Boot无校验引导器与内核签名；自编内核要签名或关掉它
典型故障装了新盘后 MBR 没写、间隙被覆盖ESP 没挂载 / 被格式化、NVRAM 启动项丢失
命令目的判据
[ -d /sys/firmware/efi ]判断 UEFI / BIOS目录在就是 UEFI；没有就是传统 BIOS
efibootmgr -v看 NVRAM 启动项与顺序BootCurrent 是这次用的。装完系统进不去，十有八九是 BootOrder 被主板改了
cat /proc/cmdline确认本次内核参数排障第一个确认 root=、是否被 quiet 吞掉了关键信息
GRUB 菜单按 e，linux 行尾追加参数，Ctrl-X / F10临时改 cmdline（重启失效）systemd.unit=rescue.target、init=/bin/bash、systemd.debug-shell=1（tty9 免登录）
改 /etc/default/grub 的 GRUB_CMDLINE_LINUX，再 update-grub / grub2-mkconfig永久加参数永远不要手改 grub.cfg——内核升级会覆盖
永远不要手改 grub.cfg——它由 grub-mkconfig 生成，内核升级会覆盖。永久改只动 /etc/default/grub 再 update-grub / grub2-mkconfig。
服务器一定要配串口控制台（console=ttyS0,115200）。第 ①②④ 棒发生的一切都没有 journald 记录，只往控制台打印。没有串口（或 IPMI SOL）的机器一旦卡在这几棒，你连「它卡在哪」都看不到，只能去机房插显示器。
02

initramfs 到底做什么

一个为了解决「鸡生蛋」而存在的临时根
initramfs（initial RAM filesystem）：一个被打包成 cpio 归档、随内核一起加载进内存的临时根文件系统。内核挂载它、执行里面的 /init，由这个用户态程序完成「找到并挂载真正的根」，然后切换过去。
命令目的判据
lsinitrd /boot/initramfs-$(uname -r).img（Debian：unmkinitramfs）看里面装了什么应有存储驱动 + lvm / cryptsetup；最前面一段是 CPU 微码，必须不压缩
dracut -f --kver $(uname -r) / update-initramfs -u / mkinitcpio -P改了存储布局、加了模块、装了新内核之后重建ls -l /boot/initr* 时间戳必须变；没变就是命令没真正生成成功
dracut emergency 里 cat /proc/cmdline确认 root= 本身对不对能进这个 shell 说明内核和 initramfs 都起来了，只是根没变出来
ls /dev/disk/by-uuid/；空则再 lvm vgscan && lvm vgchange -ay区分「没驱动」和「LVM 没激活」UUID 全空 → 控制器驱动没打进 initramfs；vgchange 后 /dev/mapper 出现 → 缺 lvm 模块，救进去立刻 dracut -f

hostonly：省空间，也埋雷

  • 发行版默认只打包这台机器当前用得上的驱动。系统盘拔到另一台、换 RAID 卡、根从 ext4 迁到 XFS、给根加 LVM——initramfs 没重建就会停在「找不到根设备」。
  • 制作云镜像 / 装机母盘时显式关掉：dracut --no-hostonly，Debian 在 initramfs.conf 里设 MODULES=most。

经典故障 · Cannot open root device

屏幕停在 Warning: /dev/mapper/vg0-root does not exist，随后掉进 dracut:/#。

内核和 initramfs 都起来了，/init 没把根设备变出来。先按上表在 shell 里分流：没块设备就是驱动，有设备但没有 mapper 就是 LVM。救进去立刻重建，别只手工 vgchange 一次就当修好了。

03

systemd 的心智模型

依赖有两个正交的维度，这是最大的坑

它到底解决了 SysV init 的什么问题

SysV 三个脚本绕不过去的缺陷：S01–S99 只能串行；双 fork 后 PID 文件不可靠；「是否健康」每个脚本自己定义。systemd 用显式依赖 + 并行、每个服务一个 cgroup、统一的 active/failed 状态机来接。

Unit 类型管什么典型例子
.service一个服务进程nginx.service
.socket一个监听套接字，可按需拉起对应 servicesshd.socket
.target一组 unit 的同步点，取代 runlevelmulti-user.target
.timer定时触发，取代 cronlogrotate.timer
.mount / .automount挂载点（由 /etc/fstab 自动生成）data.mount
.path监视文件/目录变化并触发cups.path
.slicecgroup 层级里的一个资源分组节点system.slice
.scope不是 systemd 启动、但被它接管的外部进程组用户会话、容器运行时创建的进程

依赖的两个维度：需求 ≠ 顺序

Requires= 只说「必须一起启动」，完全不管先后。只写它，数据库和应用会被同时拉起——应用连上一个还没监听的端口然后失败。

指令含义
BindsTo=比 Requires 更强：对方无论怎么变成非活动（含设备拔掉），本 unit 立刻停
Requisite=要求对方已经在；没启动就直接失败，不会去拉它
Conflicts=互斥：启动自己会先停掉对方
Before=反向的 After；同样不含需求
❌ 只写 Requires=

两者同时启动 → 数据库还在崩溃恢复 → connection refused → 反复重启。

✅ Wants= + After=

有顺序，数据库偶发重启不拖垮 API。网络必须同时 Wants=network-online.target。

After=network.target 几乎总不是你想要的——它只表示网络管理服务已启动，不表示网卡有 IP。要等可用网络必须 Wants= + After=network-online.target（这个 target 默认不会被拉起，只写 After 等于没写）。这是「开机起不来、手动 restart 却好」的头号原因。

覆盖优先级与 drop-in

同名 unit 后者整体覆盖前者。整体覆盖意味着你得把整个文件抄一份，上游改了什么都收不到。正确做法是 drop-in：只写要改的那几行。

命令目的判据
systemctl edit nginx.service建 drop-in 并自动 daemon-reload落到 /etc/systemd/system/nginx.service.d/override.conf；编辑器里只写要覆盖的段
systemctl cat nginx.service看合并后的完整配置每个来源文件会标路径，确认你改的那份真的在栈顶
systemctl show nginx.service -p LimitNOFILE -p Restart问运行时最终值比读任何文件可靠；对不上就是没 reload 或被另一份 drop-in 挡住

列表类指令：追加不是替换

  • ExecStart= / Environment= 在 drop-in 里再写一条是追加。ExecStart 出现两次会报错（oneshot 除外）。
  • 要替换必须先空值清空：ExecStart= 再写新的。手工改文件后要 daemon-reload，systemctl edit 会自动做。
04

service unit 详解

Type= 和 Restart= 是两个最常配错的地方

Type=：「服务算启动完成」的判定时刻

Type= 只回答一件事：systemd 何时认为服务起来了，可以去启动下一个？选错的后果不是跑不起来，而是依赖顺序全乱，或 systemd 误判服务挂了。

Type=完成判定坑
simplefork 完就放行自我 daemonize → 假失败 + 残留堆积
execexecve 成功能抓住二进制不存在；能用就优先
forking父进程退出必须 PIDFile=；前台程序会等到超时
notifyREADY=1最准确；忘了通知会一直 activating
oneshot进程退出默认 inactive；配 RemainAfterExit=yes 保持 active
dbus / idle拿到 D-Bus name / 等其它 job 派发完idle 只为控制台好看，别拿它做依赖控制

Restart= 与那个让人抓狂的限流

Restart=什么情况下重启
no（默认）从不
on-failure非零退出码、被信号杀死、超时、看门狗触发。最常用
on-abnormal只在被信号杀死 / 超时 / 看门狗时；正常的非零退出不重启
on-abort只在收到未捕获信号时
always无论怎么退出都重启，包括 exit 0。会让 systemctl stop 之外的一切退出都被拉起
撞墙后报 start request repeated too quickly，status 里是 start-limit-hit。reset-failed 清计数，不是 daemon-reload。真要频繁重启，把 RestartSec 调到 5s，比放宽 Burst 更合理。

sd_notify 与看门狗

Type=notify 让程序自己说「我准备好了」。配合 WatchdogSec= 还能定期报平安，抓住「进程还在、已经死锁」这种退出码发现不了的故障。喂狗必须放在真正的工作循环里——独立线程定时喂只能证明喂狗线程活着。

#include <systemd/sd-daemon.h>   // 链接 libsystemd

int main(void) {
    load_config();
    bind_and_listen();                      // 真正准备好之后……
    sd_notify(0, "READY=1");              // ……才通知 systemd

    // 看门狗：从环境变量 WATCHDOG_USEC 读出周期，按一半的间隔喂狗
    uint64_t usec = 0;
    int wd = sd_watchdog_enabled(0, &usec);

    while (running) {
        serve_one_round();
        if (wd > 0) sd_notify(0, "WATCHDOG=1");   // 喂狗
    }

    sd_notify(0, "STOPPING=1");           // 优雅退出时告知，让 systemd 别当成崩溃
    return 0;
}
// ⚠ 喂狗必须放在真正的工作循环里。放在一个独立线程里定时喂 —— 那只能证明
//    "喂狗线程还活着"，主逻辑早就卡死了你也发现不了，等于自欺欺人。

一份生产可用的 service 文件

[Unit]
Description=Order API
Documentation=https://wiki.internal/order-api
# 两个维度都写全；用 Wants 让依赖故障不至于级联
Wants=network-online.target postgresql.service
After=network-online.target postgresql.service
# 崩溃循环的阈值放宽一点，配合下面 5 秒的重启间隔
StartLimitIntervalSec=300

[Service]
Type=notify                       # 程序会调 sd_notify(READY=1)
User=orderapi                     # ★ 绝不用 root 跑业务

ExecReload=/bin/kill -HUP $MAINPID

Restart=on-failure
RestartSec=5s                     # 别用默认的 100ms，那是在制造惊群
TimeoutStartSec=60s
TimeoutStopSec=30s                # 给优雅退出留时间，超时才 SIGKILL
KillMode=mixed                    # SIGTERM 只给主进程，SIGKILL 给整个 cgroup
WatchdogSec=30s

# 资源上限（见 §6）
LimitNOFILE=65535
MemoryMax=4G
CPUQuota=200%

# 沙箱（见 §7）——这几行不改一行代码就能收窄攻击面
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=yes
ReadWritePaths=/var/lib/order-api /var/log/order-api
ProtectKernelTunables=yes

05

socket 激活与并行启动

systemd 打破启动串行的核心武器

并行启动最难的是依赖：客户端要等服务端监听好端口。systemd 自己先把所有监听套接字建好，然后所有服务同时启动——连接躺在 accept 队列里，不会被拒绝，只会被延迟。顺带还能按需启动（第一个连接才拉起服务）和零停机重启。

生活类比：先装信箱，再搬进来

物业先把整栋楼信箱装好，住户同时搬家。信投进信箱躺着，谁先搬完不重要，一封都不会丢。

映射：信箱=监听 socket · 物业安装=systemd bind/listen · 信躺着=accept 队列
unit 字段目的判据
ListenStream=0.0.0.0:8080 + WantedBy=sockets.target让 systemd 先 listensystemctl status myapi.socket 显示 Listen: 即已接管
service 写 Requires=/After=myapi.socket，不要 [Install]服务由 socket 触发，自己不再 bind程序用下面这段 C 取 fd 3；没继承到就走自己 bind 的分支
 
#include <systemd/sd-daemon.h>

// systemd 把监听 fd 从 3 号开始依次传给你（SD_LISTEN_FDS_START == 3），
// 并通过环境变量 LISTEN_FDS 告诉你有几个、LISTEN_PID 防止 fd 被子进程误用。
int n = sd_listen_fds(1);        // 参数 1 = 用完后清掉这些环境变量
if (n < 0) { /* 出错 */ }

int listen_fd;
if (n == 0) {
    // 没有继承来的 fd —— 说明是直接运行的（比如本地调试），自己 bind
    listen_fd = create_listen_socket(8080);
} else {
    listen_fd = SD_LISTEN_FDS_START;   // == 3
    // 校验一下类型对不对，别把 socket 当成别的 fd 用
    if (sd_is_socket_inet(listen_fd, AF_UNSPEC, SOCK_STREAM, 1, 8080) <= 0)
        die("inherited fd is not the socket we expect");
}
// 之后正常 accept 即可。★ 保留"没有 fd 就自己 bind"这条分支很重要，
//    否则程序脱离 systemd 就跑不起来，本地开发和容器里都会很难受。

fd 是怎么跨进程继承过来的、为什么 3 号是第一个可用编号，见 文件描述符深入；用 Unix 域套接字主动传 fd 的做法见 多进程与 IPC。

用它做零停机重启

  • 只 restart myapi.service：socket 保持 active，客户端只有几百毫秒延迟。
  • 误 restart myapi.socket：监听 fd 关闭重建，会短暂拒连。
这种零停机只对短连接成立：请求在 accept 队列里多等几百毫秒，客户端察觉不到。长连接不吃这一套——连接握在旧进程手里，重启就是断连，而且断的那一刻所有客户端会同时回来重连。几十万条长连接怎么滚动升级（分批断连、重连打散、握手 CPU 会不会被打爆）见 IoT 接入网关架构设计 · 发布与容量。判据：连接寿命远小于发布间隔，本节这套就够；连接一挂就是几小时几天，发布流程本身要按那一篇设计。
06

systemd 与 cgroup

它是 cgroup v2 层级的唯一管理者

每个服务一个 cgroup，根本价值是「可靠地知道一个服务包含哪些进程」。PID 文件会过期、被抢占、双 fork 后追踪不到；cgroup 由内核维护，进程无法逃逸。「一个服务的所有后代」第一次可枚举、可一次性 kill。

systemd 指令对应的 cgroup v2 接口说明
CPUQuota=200%cpu.max200% = 2 个核。超额被 throttle，不是被杀
CPUWeight=（1–10000，默认 100）cpu.weight相对权重，只在 CPU 争用时起作用。比 Quota 更适合大多数场景
MemoryMax=4Gmemory.max硬上限，超了先回收、回收不出来就 OOM kill
MemoryHigh=3Gmemory.high软限，超了持续加压回收但不杀。配合 Max 使用能把硬杀变成先预警
IOWeight=io.weight块设备 I/O 相对权重
TasksMax=pids.max进程/线程数上限，防 fork 炸弹
AllowedCPUs=cpuset.cpus绑核。新线程自动继承，比 taskset 可靠
Delegate=yes把子树交给服务自己管容器运行时必须开，否则它没法在自己下面建 cgroup
命令目的判据
systemd-cgls看整棵树，每个服务含哪些进程helper 脚本、worker 都应挂在对应 .service 下，不在就说明逃出了 cgroup
systemd-cgtop按 cgroup 看实时 CPU / 内存比 top 更能回答「是哪个服务在吃」
systemd-run --scope -p MemoryMax=500M ./batch_job不写 unit，临时给一条命令加限额怀疑脚本吃内存时先框住再观察
KillMode=停止服务时的行为什么时候用
control-group（默认）SIGTERM 发给 cgroup 内所有进程大多数服务。子进程也能收到通知
mixedSIGTERM 只给主进程；超时后的 SIGKILL 给所有进程主进程需要自己编排子进程退出顺序时（如 nginx master）
process只处理主进程，子进程不管几乎不要用——留下的孤儿会一直堆积
none什么信号都不发危险，基本只用于特殊的迁移场景

cgroup v2 的接口语义、cpu.stat 与 memory.events 的判读见 容器底层原理；CPU 配额如何影响调度延迟见 进程调度器。

07

unit 级安全加固

不改一行代码就能收窄攻击面

unit 里加十几行，就能把被攻破后的杀伤范围压一个数量级。底层是 namespace / capabilities / seccomp（见 Linux 安全模型），systemd 把它们收成声明式指令。

指令注意
ProtectHome= / PrivateTmp= / PrivateDevices=藏家目录、独立 /tmp、假设备。访问硬件的不要开 PrivateDevices
ProtectKernelTunables/Modules/ControlGroups=yes挡住改 sysctl、装模块、cgroup 逃逸
RestrictAddressFamilies=不用的 AF_NETLINK / AF_PACKET 显式排除
SystemCallFilter=@system-service配 SystemCallErrorNumber=EPERM，被拦返回错误而不是杀进程
命令目的判据
systemd-analyze security myapi.service给这个 unit 打分默认常 9.x UNSAFE；上表加完一般 2–4 OK。exposure 先压到 5 以下
systemd-analyze security | sort -k2 -rn | head全机找出最敞开的服务先修排前面的，不要平均用力
逐条加、每加一条重启验证。ProtectSystem=strict 漏列写路径会失败；seccomp 可能拦 libc 内部调用。journal 里搜 seccomp 能看到被拦记录。
08

journald 日志

二进制格式换来的和失去的

journald 存带索引的二进制：换来结构化字段（_SYSTEMD_UNIT / _PID / _UID）和按 unit、boot 检索，丢掉 cat/grep。元数据由内核填，应用冒不了名。默认还不持久化。

命令目的判据
journalctl -xeu myapi -b本次启动、带解释、跳到末尾报错时官方推荐组合；-b -1 看上次启动
journalctl -u myapi -f / -p err / -k跟随 / 只看 error / 内核消息-k 等价 dmesg 但有历史
journalctl _UID=1000 _COMM=python3；-o json-pretty按结构化字段过滤这是二进制格式的真正价值，不是拿它当 grep 后端
journalctl --list-boots列出启动轮次配合 -b -N 定位「上次是怎么挂的」
mkdir -p /var/log/journal 后 systemctl restart systemd-journald开持久化目录在就自动改用磁盘；再配 SystemMaxUse=
journalctl --disk-usage；--vacuum-size=500M看占用、手工压容量RateLimitBurst 打满时日志会丢，先查限速再查服务
默认写在 /run/log/journal（tmpfs），重启即丢。生产必须让 /var/log/journal 存在，或设 Storage=persistent。这一步没做，前面所有排查手段都无从谈起。
要进 ELK / Loki 不必二选一：ForwardToSyslog=yes，或 journalctl -o json -f 喂采集器。-o cat 输出纯消息体。

启动性能与故障排查

blame 的时间不是关键路径

systemd-analyze 的正确读法

blame 是各 unit 自己花了多久，不是拖慢开机多久。耗时 20 秒但完全并行的服务贡献是 0；200ms 卡在关键链上可能让后面全排队。只看 critical-chain。
现象先看什么常见原因
服务启动失败systemctl status <unit> 的 Active: 那一行括号里的 Result:exit-code=程序自己退了；timeout=Type 选错或真的慢；start-limit-hit=被限流（§4）
手动 start 能起、开机起不来journalctl -u <unit> -b 里的时序依赖没写全，尤其 network-online.target（§3）；或依赖的挂载点还没好
改了 unit 文件没生效systemctl cat <unit> 与 systemctl show忘了 daemon-reload；或被 /etc 下的旧覆盖文件挡住
开机卡住不动systemctl list-jobs某个 job 处于 running 状态迟迟不完成，常见于等设备或等网络
启动时报依赖环journalctl -b | grep -i "ordering cycle"systemd 会自己打破环——但它删掉的是它选中的那条边，结果往往不是你想要的
服务是 active 但功能不正常systemctl show -p MainPID + systemd-cglsType=simple 只保证 fork 成功，不保证程序初始化完成——换 Type=notify

进不了系统时的三种救援

典型场景 · 加了一行 fstab 之后机器起不来了

卡在 A start job is running for /data，90 秒后进 emergency。

systemd 把 fstab 每行生成 .mount，local-fs.target 依赖它们。设备不在就等到 DefaultTimeoutStartSec 超时，启动中断。非关键挂载写 defaults,nofail,x-systemd.device-timeout=10s。救援：init=/bin/bash → mount -o remount,rw / → 改 fstab → sync → echo b > /proc/sysrq-trigger。远程机器改完先 daemon-reload && mount -a，不要直接 reboot。

启动与服务排障速查

  • 先分清卡在哪一棒（§1）。服务起不来看 Result: 再 journalctl -xeu -b。
  • start-limit-hit → reset-failed，去查为什么一直崩。
  • 手动能起、开机不能 → 缺 Wants=network-online.target + After=。
  • 改了没生效 → daemon-reload；列表类指令先空值再写新值。
  • 优化开机只看 critical-chain。生产先开 journal 持久化、配串口。

面试题（12 道）

分层自测

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础为什么需要 initramfs？没有它行不行？

    因为存在一个鸡生蛋的问题：内核要挂载根文件系统，但挂载它所需的东西又在根文件系统里。具体分三类：

    • 需要驱动：NVMe、RAID 卡、SAS HBA 的驱动通常是模块（.ko），而模块存在还没挂上的根里。
    • 需要用户态工具：LVM 要 lvm 激活、软 RAID 要 mdadm 组阵列、LUKS 要 cryptsetup 和一次密码输入——这些都是用户态程序，内核自己做不了。
    • 需要网络：iSCSI / NFS 根要先配好网卡拿到 IP。

    行不行？行，但有前提：如果把所需驱动全部编译进内核（=y 而非 =m），且根文件系统是简单分区（没有 LVM / RAID / 加密），就可以不用 initramfs 直接 root=/dev/sda2 启动。嵌入式系统经常这么做。发行版不能这么做，是因为它要用一个通用内核适配千奇百怪的硬件，全编进去内核会大到不可接受。

  2. 基础Requires= 和 After= 有什么区别？只写一个会怎样？

    它们是两个正交的维度，这是 systemd 最容易被搞混的地方：

    • Requires= 管需求：「必须一起启动，对方失败/停止我也停」。完全不管先后顺序。
    • After= 管顺序：「要等对方启动完成我才开始」。完全不管对方要不要被启动。

    各自漏写的后果：

    • 只写 Requires=：两者被同时启动，你的服务大概率在数据库还没监听时就去连接，然后失败退出。
    • 只写 After=：如果对方压根不在本次启动的集合里，这条 After 等于一句空话——没有人会去启动它，你也就"等"了个寂寞。network-online.target 就是最典型的例子。

    实践上推荐 Wants= + After= 的组合：既保证顺序，又不会因为依赖偶发故障而把自己一起拖下水，重连交给应用自己和 Restart= 处理。

  3. 基础服务日志重启后就没了，为什么？

    因为 journald 默认把日志写在 /run/log/journal，而 /run 是 tmpfs（内存文件系统），重启即清空。这是发行版为了不预设「你想留日志」而做的保守默认，但对生产机器来说恰恰最要命——机器意外重启后，你最想看的那段日志正好没了。

    开持久化只要让 /var/log/journal 目录存在即可（journald 检测到它就自动改用持久存储），或者在 /etc/systemd/journald.conf 里显式写 Storage=persistent：

    sudo mkdir -p /var/log/journal
sudo systemd-tmpfiles --create --prefix /var/log/journal
sudo systemctl restart systemd-journald

    开完记得配容量上限（SystemMaxUse=），否则日志可能把 /var 撑满。查历史用 journalctl -b -1 看上一次启动，这是排查「机器为什么重启」的关键入口。

  4. 基础改了 unit 文件为什么没生效？

    三个层层递进的原因，按顺序排查：

    1. 忘了 systemctl daemon-reload。systemd 把 unit 配置缓存在内存里，不重新加载就还是旧的。systemctl edit 会自动 reload，手工改文件不会。
    2. 改错了文件。/etc/systemd/system/ 下的同名文件会整体覆盖 /usr/lib/systemd/system/ 里的——你改了后者，前者还在那儿挡着。用 systemctl cat <unit> 看真正生效的是哪几个文件。
    3. 改了但语义不对。列表类指令（ExecStart、Environment）在 drop-in 里再写一条是追加不是替换，要先写一行空值（ExecStart=）清空再写新的。

    最终确认手段是 systemctl show <unit> -p <属性>——它返回的是 systemd 运行时真正持有的值，比读任何文件都可靠。

10.2 中级（区分熟练度）

  1. 中级Type=simple 和 Type=forking 分别在什么时刻算「启动完成」？选错会怎样？

    Type= 唯一的作用是回答「systemd 什么时候认为服务起来了、可以去启动下一个」：

    • simple：fork() 一执行完就算完成，不等程序真正初始化。
    • forking：父进程退出时才算完成，systemd 转而追踪 fork 出来的子进程（需要 PIDFile= 帮它确认主进程）。

    两种选错方式：

    • 程序会自我 daemonize，却写了 simple：systemd 看到"主进程"退出，判定服务失败，按 Restart= 又拉一次——无限重启，而真正的 daemon 每轮都残留在后台越堆越多。
    • 程序是前台的，却写了 forking：systemd 一直等父进程退出，等到 TimeoutStartSec 超时，判定启动失败并把它杀掉——尽管服务其实跑得好好的。

    最佳实践是都别用：现代程序基本都有 --foreground 之类的开关，用 Type=exec（比 simple 严格，能捕获 execve 失败）；如果程序支持 sd_notify，用 Type=notify 最准确——它保证依赖它的服务启动时，端口是真的已经在监听了。

  2. 中级socket 激活的价值是什么？为什么它能打破启动依赖？

    核心洞见：依赖的本质是「客户端要等服务端监听好端口」，而这个 bind/listen 可以由 systemd 提前统一做掉。

    systemd 在启动任何服务之前，先把所有 .socket unit 声明的监听套接字全部建好，然后所有服务同时启动。此时客户端连过去，连接会静静躺在内核的 accept 队列里，等服务端起来后再取走。连接不会被拒绝，只会被延迟——依赖顺序就凭空消失了。

    顺带解决另外两件事：

    • 按需启动：第一个连接到来时才拉起服务，机器上几十个低频服务可以都不常驻。
    • 零停机重启：监听 fd 由 systemd 持有，systemctl restart myapi.service（不带 .socket）期间 socket 一直开着，客户端感知到的只是几百毫秒延迟而不是 connection refused。

    程序侧改动很小：用 sd_listen_fds() 拿继承来的 fd（从 SD_LISTEN_FDS_START 即 3 号开始），代替自己的 bind/listen。要保留"没有继承 fd 就自己 bind"的分支，否则脱离 systemd 就跑不起来，本地调试和容器里都很难受。

  3. 中级systemd 和 cgroup 是什么关系？为什么说它比 PID 文件可靠？

    systemd 是 cgroup v2 层级的唯一管理者：它把整棵树切成 system.slice（系统服务）/ user.slice（登录会话）/ machine.slice（虚拟机与容器），每个服务在下面有自己的 cgroup 节点。

    相比 PID 文件的优势不在于"限资源"，而在于可靠地知道一个服务包含哪些进程：

    • PID 文件可能过期（进程死了文件还在）、可能被抢占（PID 复用后指向了别人）、可能压根没写；双 fork 之后更是完全追踪不到。
    • cgroup 的成员关系由内核维护，进程无法逃逸——fork 出来的所有后代自动属于同一个 cgroup。于是"停止服务"可以真正做到把整组进程一次性干净地终结，不留孤儿。

    资源限制是附带收益：CPUQuota= / MemoryMax= / TasksMax= 这些指令直接映射到 cpu.max / memory.max / pids.max。限额加在 .slice 上对整组生效，加在 .service 上只作用于单个服务。

    相关的还有 KillMode=：默认 control-group 会把 SIGTERM 发给 cgroup 内所有进程；mixed 只给主进程（适合 nginx 这类自己编排子进程退出顺序的）；process 不管子进程，几乎不该用。

  4. 中级服务手动 start 能起来，开机却起不来。怎么查？

    手动能起说明程序和配置本身没问题，差别只在「环境」——开机时某些东西还没准备好。按这个顺序查：

    1. journalctl -u <unit> -b 看开机那次的实际报错，这是唯一的一手证据。
    2. 最常见的原因是网络依赖写错了。After=network.target 只表示"网络管理服务已启动"，不表示网卡拿到了 IP。要等真正可用的网络必须用 network-online.target，而且要同时写 Wants=network-online.target——这个 target 默认不会被拉起，只写 After= 的话它根本不在启动集合里，那条 After 形同虚设。
    3. 其它依赖没就绪：数据库还在崩溃恢复、要写的目录所在的挂载点还没挂上（应显式 After=<path>.mount）、DNS 还不可用。
    4. 环境变量差异：你手动 start 时继承的是 root shell 的环境，开机时没有。用 EnvironmentFile= 显式提供，别依赖 PATH 里有什么。
    5. 确认真的 enable 了：systemctl is-enabled <unit>。没有 [Install] 段的 unit 执行 enable 会报错，而那个错误常常没人看。

10.3 高级（体现深度）

  1. 高级systemd-analyze blame 排第一的服务，砍掉它开机就会变快吗？

    不一定，多数情况下不会。blame 给的是「每个 unit 各自花了多久」，不是「它拖慢了开机多久」。这两者只有在串行启动的世界里才等价，而 systemd 的核心特性恰恰是并行。

    • 一个耗时 20 秒、但和所有人并行、谁都不等它的服务，对开机总时长的贡献是 0。
    • 一个只花 200 毫秒、却卡在关键链条中间的服务，可能让它后面几十个服务全部排队。

    要优化开机速度必须看 systemd-analyze critical-chain——它输出的是真正的串行关键路径，每一行的 @ 是这个 unit 变为 active 的绝对时刻，+ 是它自己花的时间。只有压缩这条链上的节点才有意义。

    再往上一层：systemd-analyze 的总览会把时间分成 firmware / loader / kernel / initrd / userspace 五段。如果大头在 firmware（BIOS 自检、RAID 卡扫盘）或 loader（GRUB 超时），那和 systemd 一点关系都没有，去调 BIOS 设置和 GRUB_TIMEOUT 才对。

    systemd-analyze plot > boot.svg 能生成完整的甘特图，最直观地看出谁在等谁。

  2. 高级rescue.target、emergency.target 和 init=/bin/bash 分别在什么情况下用？

    三者的差别是系统被恢复到了哪一步，按「能力从多到少」排列，原则是能用温和的就别用激烈的：

    • systemd.unit=rescue.target：根已挂载且可写，基础服务已启动，只是没有网络和图形。systemctl、journalctl 都能用——绝大多数配置错误在这里就能修完。首选。
    • systemd.unit=emergency.target：只挂了根，而且是只读的，几乎没有任何服务。rescue 都进不去时才用（比如某个 local-fs.target 依赖的挂载失败导致 rescue 也起不来）。改文件前必须先 mount -o remount,rw /。
    • init=/bin/bash：完全绕过 systemd，内核挂上根之后直接 exec 一个 shell。用于 systemd 自身损坏、或 /etc/fstab 里有致命错误导致连 emergency 都进不去。此时环境极其原始：没有任何服务、根是只读、reboot 命令不可用（它要跟 systemd 通信）。改完要 sync 然后 echo b > /proc/sysrq-trigger 强制重启。

    加分点：说清为什么会需要救援比背命令更重要。最高频的触发场景是改 /etc/fstab——systemd 会把每一行生成成 .mount unit 并让 local-fs.target 依赖它，设备不存在时会阻塞到超时（默认 90 秒）然后整个启动中断。正确做法是非关键挂载一律加 nofail 和 x-systemd.device-timeout=10s，并且改完先 daemon-reload && mount -a 验证再重启，不要直接 reboot 远程机器。

  3. 高级为什么容器里 PID 1 常常收不到 SIGTERM？这和 systemd 作为 PID 1 有什么共同点？

    内核对 PID 1 有一条特殊规则：它不会响应自己没有安装处理函数的默认信号。普通进程收到 SIGTERM 而没装 handler 时会被默认终止，PID 1 则会直接忽略。这是内核的保护机制——防止一次误发的信号把 init 干掉、导致内核 panic。

    用在容器上就成了坑：业务进程直接当 PID 1 却没显式处理 SIGTERM，docker stop 发的信号石沉大海，等 10 秒超时后被 SIGKILL 硬杀——优雅退出逻辑一次都没跑过。还有个变体：ENTRYPOINT 是 shell 脚本且写成 ./app 而非 exec ./app，此时 PID 1 是 shell，信号根本传不到 app。

    PID 1 的另一项职责是回收孤儿进程：所有失去父进程的进程都会被过继给它，它必须调 wait() 收尸，否则僵尸堆积耗尽 PID。

    共同点：systemd 和 tini 本质上在做同一件事——当一个称职的 init。两者都显式安装信号处理函数并做转发，都负责回收所有过继来的孤儿。区别只是规模：tini 是几百行的极简版，systemd 还额外承担了服务编排、cgroup 管理、日志、socket 激活。所以容器里的解法要么 docker run --init 注入 tini，要么在 ENTRYPOINT 里用 exec 让业务进程成为 PID 1 并自己处理 SIGTERM。相关内容见 容器底层原理。

  4. 高级不改一行代码，怎么把一个服务被攻破后的杀伤范围压到最小？

    用 systemd 的 unit 级沙箱指令。它们底层就是 namespace、capabilities、seccomp、mount 只读那一套，但被包装成了声明式配置，不需要改代码、不需要手写 seccomp 过滤器。按收益排序：

    • User= 非 root 运行——这一条的收益超过后面所有条加起来。
    • NoNewPrivileges=yes：禁止通过 setuid 二进制提权，同时也是 seccomp 生效的前提。
    • ProtectSystem=strict + ReadWritePaths=：整个文件系统只读，只放开真正要写的几个目录。攻击者拿到 RCE 也改不了任何二进制或配置。
    • PrivateTmp=yes：独立 /tmp，顺带消灭一整类 /tmp 竞态漏洞。
    • CapabilityBoundingSet=：留空即全部丢弃，只加回真正需要的（比如绑定低端口只需要 CAP_NET_BIND_SERVICE）。
    • SystemCallFilter=@system-service + SystemCallErrorNumber=EPERM：用预定义集合做 seccomp 白名单，被拦的调用返回错误而不是直接杀进程（便于排查）。
    • RestrictAddressFamilies=、ProtectKernelTunables=、ProtectKernelModules=、ProtectControlGroups=：分别挡住裸 socket、改内核参数、加载模块、cgroup 逃逸这几条路。

    验证手段是 systemd-analyze security <unit>，它会逐条打分并给一个 0–10 的 exposure 总分。什么都不配的默认 unit 通常在 9 分（UNSAFE），加完上述指令一般能降到 2–4。

    工程上的关键提醒：逐条加、每加一条重启验证一次。ProtectSystem=strict 和 SystemCallFilter= 最容易把服务搞挂——前者会让漏列的写路径失败，后者可能拦掉 libc 内部用的调用。一次性全加上，出问题时你根本不知道是哪条。被 seccomp 拦住时 journal 里有明确记录。
