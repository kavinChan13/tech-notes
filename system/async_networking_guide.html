四种交付风格对照；生产只写协程

4.1 Callback 风格（经典）

handler 必须捕获 shared_from_this()，否则 start() 返回后 Session 已析构。读写拆成两个成员、错误路径写两遍，是回调的税。

4.2 协程风格（推荐）

asio::awaitable<void> echo_session(tcp::socket sock) {
    try {
        std::array<char, 8192> buf;
        for (;;) {
            size_t n = co_await sock.async_read_some(
                asio::buffer(buf), asio::use_awaitable);
            co_await asio::async_write(sock,
                asio::buffer(buf, n), asio::use_awaitable);
        }
    } catch (std::system_error& e) { /* 连接断 */ }
}

asio::awaitable<void> listener() {
    auto ex = co_await asio::this_coro::executor;
    tcp::acceptor acc(ex, {tcp::v4(), 8080});
    for (;;) {
        tcp::socket sock = co_await acc.async_accept(asio::use_awaitable);
        asio::co_spawn(ex, echo_session(std::move(sock)), asio::detached);
    }
}

int main() {
    asio::io_context io;
    asio::co_spawn(io, listener(), asio::detached);
    io.run();
}

4.3 future 风格（少用，仅展示）

use_future + .get() 每个 session 占一条线程，只适合接到同步测试里。

4.4 Sender/Receiver 风格 (asio 1.30+ experimental)

use_sender 返回可组合 sender，是接 stdexec 的桥，不是默认写法。超时 / 取消见 §5。

05

Asio 协程进阶

超时是读与定时器竞争；取消必须等两边都落地

5.1 co_spawn / detached / use_awaitable / awaitable<T>

awaitable<T> 是 Asio 的 Task。co_spawn(ex, coro, token) 把 executor 钉死，之后每个恢复点都 dispatch 回去——§6.4 整段会话无并发靠的就是这个。detached 是 fire-and-forget。

5.2 超时模式

asio::awaitable<void> read_with_timeout(tcp::socket& sock, std::chrono::milliseconds t) {
    asio::steady_timer timer(co_await asio::this_coro::executor);
    timer.expires_after(t);

    // awaitable_operators 提供 || 和 &&
    using namespace asio::experimental::awaitable_operators;

    auto result = co_await (
        sock.async_read_some(asio::buffer(buf), asio::use_awaitable)
        ||
        timer.async_wait(asio::use_awaitable)
    );

    if (result.index() == 1) {
        throw std::runtime_error("timeout");
    }
    // result 是 variant<size_t, monostate>
}

5.3 并发请求 (when_all / when_any)

&& = when_all（结果 tuple），|| = when_any（赢家取消其余）。co_await (fetch(a) && fetch(b)) 把两次 RTT 压成一次。套了超时还要让 cancellation 往下传，否则内层会跑完。

5.4 取消 (cancellation slot)

cancellation_signal + bind_cancellation_slot，emit(terminal) 沿 await 链向下。emit 不是同步的：未决操作以 operation_aborted 稍后回来，回来之前 buffer 仍被占用。手写「等两边收敛」漏了，就是超时功能上线后的偶发崩溃。

06

Strand —— Asio 的并发解药

排队代替互斥：同一 session 的 handler 永不并发

6.1 问题：多线程 io_context 上的 handler 可能并发

共享 context 时同一 Session 的读写完成可能并发。加锁会卡住整个 worker。

6.2 Strand：序列化执行器

strand = 队列 +「是否有人在跑」：空闲则当前线程接手，否则入队。FIFO，用排队代替互斥。

6.3 每 Session 一个 strand 模式（推荐）

class Session : public std::enable_shared_from_this<Session> {
    tcp::socket sock_;
    asio::strand<asio::any_io_executor> strand_;     // ★ 每 Session 自己一个
public:
    Session(asio::io_context& io, tcp::socket s)
        : sock_(std::move(s))
        , strand_(asio::make_strand(io)) {}

    void start() {
        sock_.async_read_some(asio::buffer(buf_),
            asio::bind_executor(strand_,           // ★ handler 绑到 strand
                [self = shared_from_this()](auto, auto n) {
                    // 此 callback 一定在 strand 上跑 → 单 session 内无并发
                }));
    }
};

6.4 协程 + strand

co_spawn(make_strand(io), session(...), detached) 后每个 co_await 都回到该 strand。连接极多而每连接极轻时，每核一个单线程 io_context 更省。

07

Boost.Beast — Asio 上的 HTTP / WebSocket

协议解析器，不是框架；HTTP/WS 都坐在 Asio 上

7.1 Beast 定位

Boost.Beast 是 Asio 之上的 HTTP/1.1 + WebSocket 协议解析器，不是带 router 的框架。IO、超时、strand 全部复用 Asio。

7.2 最小 HTTP server

循环：http::async_read → 组 response → async_write；keep_alive 为假则退出。flat_buffer 同样要活到本次 read 完成。

7.3 WebSocket 升级

websocket::stream 包住 tcp_stream，async_accept 后读写帧。超时 / 取消 / strand 与裸 socket 同一套。

7.4 Beast 的优劣

跟 Asio 零阻抗、HTTP/1.1 与 WS 解析正确；没有内置 router / HTTP/2 / HTTP/3，Boost 编译慢。上层用 Crow / Drogon / uWebSockets。

7.5 上层框架

  • Crow — 类 Flask 路由，header-only
  • Oat++ — 完整 Web 框架，含 ORM
  • Drogon — 高性能（自带 HTTP/2 + WS）
  • uWebSockets — 极致性能 WS

Sender/Receiver 网络栈 — 未来的方向

惰性描述 + 结构化取消；今天是桥，明天才是默认

8.1 概念示例 — 用 sender 组合网络操作

stdexec / mvfst 把请求写成 just(url) | dns | connect | tls | send | read | upon_error。超时、重试是 stop_when / retry_when，stop_token 沿链走。

8.2 Asio 1.30+ 的 sender 适配

use_sender 返回 sender，可丢进 stdexec 管线。C++26 标准化的是执行框架，网络还没进标准。

8.3 为什么 Sender 路线是未来

  • 结构化并发：取消 / 超时 / 错误沿链走
  • CPU / GPU / IO 同一套 scheduler
  • 编译期状态机，运行时无虚调用；C++26 对齐生态
2026：生产用 Asio 协程；S/R 是未来五年。提前布局，别 all-in。
09

gRPC 完整剖析 ⭐

HTTP/2 stream 上的四种消息形状；跨语言事实标准

gRPC 是 Google 开源的跨语言 RPC 框架。基于 HTTP/2 + Protobuf，C++ 实现性能/功能最完整。

9.1 gRPC 核心架构

HTTP/2 上每 RPC 一条 stream；四种调用模型只是 stub 形状，协议都是 HEADERS + DATA + trailer。

9.2 第一个 gRPC 服务

proto 生成同步 Service 与 CallbackService。同步覆盖 Echo(ctx, req, res) 再 Wait()——简单，但每在途 RPC 占一条线程。

9.3 gRPC 性能数据

同机房 Unary P50 约 50–100 μs。同步 10–30k QPS（每 RPC 占线程）；异步 + 多核 100–500k。差距在「等」占不占线程，不是单次 RPC 更快。

9.4 同步 vs 异步 API

同步适合低并发原型；老 CQ+tag 难写对；Callback API 是现代推荐；协程走第三方（asio-grpc）。

gRPC 异步 API 实战

Callback API 把线程从「等」里放走；流要自己做背压

10.1 Callback API (现代推荐)

继承 CallbackService，填 res 后 DefaultReactor()->Finish(OK)。handler 可先返回、稍后 Finish。reactor 活到 OnDone；callback 线程里禁止阻塞，否则卡住整个 EventEngine。

10.2 客户端流（client → server 流式发送）

ClientWriteReactor：StartWrite → OnWriteDone 再写下一块；结束 StartWritesDone。pending 必须有上限，否则慢消费者顶爆内存。

10.3 服务端流（一请求多响应）

ServerWriteReactor 在 OnWriteDone 里决定下一则还是 Finish。长命 stream 会被 idle timeout 掐断，keepalive 并把重连当正常路径。

10.4 与协程整合（社区）

asio-grpc 把 Async 调用变成 co_await agrpc::request(...)，生命周期回到作用域。

QUIC / HTTP/3 实战

12.2 msquic 最小客户端

MsQuicOpen2 → ConnectionStart → 每条逻辑流 StreamOpen / StreamSend。流互不阻塞。msquic 自带 Asio adapter。

12.3 QUIC 的关键优势复习

队头阻塞下沉到 stream；建连 1-RTT / 恢复 0-RTT；Connection ID 支持迁移；拥塞控制在用户态。代价是 UDP 被限、CPU 更高、0-RTT 可重放。

12.4 HTTP/3 部署

先用 HTTP/1.1 或 2 建连，带 Alt-Svc: h3=":443" 让浏览器下次试 QUIC。UDP 常被限速，回落不是可选项。0-RTT 只放幂等请求。

12.5 真实生产数据

Cloudflare：H3 占 25%+，移动延迟降 30%。YouTube：QUIC 占 70%+，buffering 降 9–20%。收益几乎全在高丢包 / 移动网；机房内部东西向通常不划算。

服务网格 (Envoy) 视角

sidecar 换来统一策略，代价是每 hop 0.5–2 ms

Envoy 是 Service Mesh 事实数据平面（Istio / Consul / AWS App Mesh），C++14。

14.1 Envoy 架构亮点

每线程一个事件循环；Listener / Filter chain 可插拔；xDS（gRPC streaming）热更新；HTTP/1.1/2/3；WASM filter 避免给每个扩展编 C++。

14.2 Envoy 的"为什么 C++"

选 C++：ms 级 P99、内存可预测、跟 BoringSSL / gRPC 同语言。门槛靠 WASM / Lua filter 对外放开。

14.3 Envoy 与你自家 C++ 服务的关系

  • Envoy 作为 sidecar 反向代理 → 你的 C++ 服务只需关心业务逻辑
  • Envoy 处理 mTLS / 限流 / 熔断 / 重试 / 灰度 → 减少自家代码
  • 但增加一层 latency（~0.5-2 ms / hop）

17.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础Reactor、Proactor、Sender/Receiver 三种范式的本质区别是什么？

    结论先行：三者回答的不是同一个问题。Reactor 和 Proactor 回答的是「操作系统在哪个时刻通知我」，属于 IO 通知模型；Sender/Receiver 回答的是「异步操作如何被描述和组合」，属于异步编程的代数模型，可以架在前两者之上。把它们并列比较本身就是个陷阱。

    • Reactor：epoll_wait 返回「fd 就绪」，用户自己在回调里 read/write。buffer 归用户，什么时候分配自己说了算。epoll / kqueue，libevent / Nginx / Redis / Linux 上的 Asio。
    • Proactor：用户提交「读 N 字节到这块 buffer」，内核完成后才通知，回调拿到的是已经填好的数据。buffer 在提交那一刻就交给了内核，完成之前不能释放或搬家。IOCP、io_uring、Windows 上的 Asio。
    • Sender/Receiver：async_read 不再「立刻发起」，而是返回一个描述子（sender）；要 connect 到 receiver 并 start 才真正执行。then / let_value / when_all 在编译期把整条链拼成一个状态机，取消与错误沿链结构化传播。

    机制上的关键差异是「buffer 的所有权在谁手里」：Reactor 下 buffer 全程归你，所以可以用共享读缓冲池、按需借还（百万连接省内存的关键）；Proactor 下每个在途操作都得钉住一块自己的 buffer，省了一次内核到用户的拷贝，但把生命周期难度顶到了脸上。

    工程视角：Asio 对上层永远暴露「完成回调」这套 Proactor 风格的接口，在 Linux 上其实是用 epoll 模拟出来的——就绪之后由 Asio 替你 read。所以在 Linux 上你享受不到 Proactor 真正的收益（少一次拷贝、批量提交），只是接口长得像。真正的收益要等 io_uring 后端。而 io_uring 的代价也很实在：提交后 vector 扩容或析构就是 UAF，而且是内核在写，ASAN 未必抓得住。

    S/R 不替代前两者，它替代的是「回调地狱 + 手写取消」。一句话口径：Reactor 通知「能读了」，Proactor 通知「读完了」，Sender/Receiver 管的是「这堆异步步骤怎么拼起来、怎么一起取消」。

  2. 基础gRPC 的四种调用模型分别是什么？它们在协议层面有区别吗？

    结论：Unary / Server-streaming / Client-streaming / Bidirectional-streaming，本质是「请求消息数 × 响应消息数」取 1 或 N 的四种组合。协议层面它们是同一件事——都是一条 HTTP/2 stream 上的 HEADERS + 若干 DATA 帧 + trailer HEADERS（携带 grpc-status）。四种模型只是 stub 生成代码的形状差别，不是四套协议。

    模型请求响应典型用途
    Unary11普通 RPC，占实际用量九成
    Server streaming1N订阅推送、大结果集分批、xDS 配置下发
    Client streamingN1大文件上传、批量打点，服务端最后汇总
    Bidi streamingNN聊天、行情、长连接双向通道

    「流」不是 gRPC 发明的，是 HTTP/2 stream 本来就支持双向多帧。半关闭由 DATA 帧的 END_STREAM 标志表达——client streaming 里的 StartWritesDone() 就是发这么一个标志。

    生产上真正会翻车的三点：

    • 流控与背压。HTTP/2 有 stream 级和 connection 级窗口，对端读得慢，你的 StartWrite 就会一直挂着不回 OnWriteDone。§10.2 里那个 pending_ 队列是最小可用版本，生产里必须加长度上限，超限就丢消息或断流，否则内存会被慢消费者顶爆。
    • 长命 stream 会被静默掐断。LB、NAT、Envoy 的 idle timeout 默认往往比你以为的短。必须配 GRPC_ARG_KEEPALIVE_TIME_MS 并把重连做成正常路径而不是异常路径。
    • 连接倾斜。一条 TCP 连接上的所有 stream 只会落到一个后端实例，L4 负载均衡下长连接会长期不均。这正是服务网格里 gRPC 必须走 L7 LB 或客户端侧 LB 的原因。
  3. 基础QUIC 解决了 HTTP/2 的什么痛点？代价是什么？

    结论：HTTP/2 在应用层做了多路复用，但它跑在一条 TCP 连接上，而 TCP 的可靠有序交付是整条连接级别的——丢一个包，内核不会把后面已经到达的字节交给用户，于是所有 stream 一起卡住。这是 TCP 层的队头阻塞，HTTP/2 靠自己无解。QUIC 把「可靠有序」的粒度从连接下沉到 stream。

    1. 队头阻塞：QUIC 在 UDP 上自己实现可靠传输，每个 stream 独立重组，丢包只阻塞受影响的那个 stream。
    2. 建连 RTT：TCP 握手 + TLS1.3 至少 2 个 RTT；QUIC 把传输握手和 TLS 握手合成一次，1-RTT；会话恢复 0-RTT。
    3. 连接迁移：连接由 Connection ID 标识而非四元组，手机从 Wi-Fi 切 5G，IP 变了连接不断——移动场景的杀手锏。
    4. 拥塞控制在用户态：随版本发布 BBR，不用等内核升级，也便于按业务定制。

    代价必须主动说出来，否则答案是不完整的：

    • UDP 在不少企业网和运营商那里被限速甚至封禁，必须保留 TCP 回落——§12.4 的 Alt-Svc 头就是干这个的，先用 HTTP/1.1 或 2 建连，再告诉浏览器「下次可以试 h3」。
    • 包处理和加解密全在用户态，CPU 开销明显高于 TCP（内核有 GSO / GRO / TSO 卸载）。大流量场景必须靠 UDP GSO、GRO 和 sendmmsg 才追得上，否则单机吞吐反而下降。
    • 0-RTT 数据可被重放，只能放幂等请求。
    • 全链路加密到连 ACK 都看不见，中间设备失去可观测性，排障只能靠端上的 qlog。

    §12.5 的数据能佐证收益的分布：Cloudflare 移动场景延迟降 30%、YouTube buffering 降 9–20%——收益几乎全出现在高丢包 / 移动网络。机房内部万兆低丢包的东西向流量，上 QUIC 通常不划算。

  4. 基础SO_REUSEPORT 在多 worker 架构里起什么作用？

    结论：它允许 N 个 worker 各自 bind / listen 同一个 <IP, port>，内核对每个新连接按四元组哈希，直接投递到其中一个 listen socket 的 accept 队列。它把「连接分发」从用户态挪进内核，消掉了单 accept 点的锁竞争和惊群。

    和另外两种做法比：

    • 单线程 accept 再分发：accept 线程是单点瓶颈，而且要跨线程传 fd，后续读写不在同一个核上，CPU 亲和性直接破功。
    • 多线程共享一个 listen fd：EPOLLEXCLUSIVE 之前是惊群，之后仍然是所有 worker 抢同一把 accept 队列锁，而且谁抢到是随机的。
    • SO_REUSEPORT：每 worker 一个 listen fd、一个独立 accept 队列，从 accept 到后续读写全程在同一个核。配合 §3.4 的「每核一个 io_context + pin」，整条路径无跨核。

    三个真实的坑：

    • 分流是静态哈希，不看负载。它不像 accept 竞争那样天然「谁空谁抢」。长连接场景下一旦某些连接特别重，负载会长期不均，而且自己不会恢复——需要应用层做连接迁移或重平衡。
    • worker 数变化会重哈希。滚动重启时加入或摘掉一个 listen socket，内核的分发表就变了，正在三次握手中的连接可能被投到已经关闭的队列而收到 RST。正确做法是用 SO_ATTACH_REUSEPORT_EBPF 自己控制分发，退出前先把本 socket 从 BPF map 里摘掉、等存量连接排空再 close。
    • 必须每个 worker 在自己线程里完整走一遍 socket → setsockopt(SO_REUSEPORT) → bind → listen。先 bind 再 fork 共享同一个 fd 不是 REUSEPORT，那还是共享队列。另外 Linux 要求同 uid 才能加入同一个组，否则就是端口劫持漏洞。
  5. 基础Asio 的 strand 是什么？它比「每连接一把锁」好在哪？

    结论：strand 是一个序列化执行器——投递到同一个 strand 的 handler 保证不会并发执行，并且满足 FIFO 和 happens-before。它用「排队」代替「互斥」，把并发问题在调度层解决掉，而不是在数据层加锁。

    机制：strand 内部是一个队列加一个「当前是否有线程正在跑本 strand」的标记。post 时若无人在跑，就由当前 IO 线程直接接手；否则挂进队列。跑完一个 handler 后同一线程继续取下一个——这一点很关键，它天然做了批处理，省掉了大量线程唤醒。

    相对每连接一锁的四个优势：

    • 不阻塞线程。抢不到执行权的 handler 是被排队，不是让 IO 线程 block 住。而一把锁会把整个 worker 线程连同它上面的几万条连接一起卡住——这是「每连接一锁」在事件驱动模型里最致命的问题。
    • 无锁竞争与 cacheline 争用。无竞争路径基本就是一次原子操作。
    • 不会死锁。strand 之间不存在「持有并等待」的关系（前提是你不在 strand 里同步等另一个 strand）。
    • 组合性。协程 co_spawn 到 strand 上之后，整个会话内所有 co_await 恢复点都自动回到该 strand（§6.4），不需要在每个成员函数里「记得加锁」。漏加锁才是线上最常见的 bug 源，strand 从结构上消灭了这一类。

    边界要讲清楚（这是加分项）：strand 只保证同一个 strand 内串行，跨 session 共享的路由表、全局统计仍然需要自己的同步手段；strand 会引入排队延迟，一个慢 handler 会拖住同一连接的后续所有事件，所以 strand 上绝不能做阻塞调用或重计算，要 post 到 thread_pool；连接极多而每连接极轻时，「每核一个单线程 io_context」比每连接一 strand 更省——那种场景 strand 是多余开销。

17.2 中级（区分熟练度）

  1. 中级Asio 的 completion token 机制怎么工作？为什么说它是这个库最强的设计？

    结论：completion token 把「操作本身」和「结果如何交付」正交解耦。async_xxx 的最后一个参数不是回调，而是一个选择交付方式的类型标签；库通过 async_result<Token, Signature> 特化，在编译期把标签改写成具体的完成处理器，并顺带决定整个 async_xxx 的返回类型。

    三步机制：① 每个异步操作声明自己的完成签名，比如 void(error_code, size_t)；② 用户传入 token；③ async_initiate<Token, Sig>(initiation, token, args...) 找到对应的 async_result 特化，由它决定包装成什么 handler、返回什么给调用者。

    // 同一个 async_read_some，四种交付方式，返回类型各不相同
sock.async_read_some(buffer(b), [](std::error_code, size_t){});      // → void
std::future<size_t> f = sock.async_read_some(buffer(b), asio::use_future);
size_t n = co_await sock.async_read_some(buffer(b), asio::use_awaitable);
auto op = sock.async_read_some(buffer(b), asio::deferred);   // 未启动，可稍后组合

    更妙的是 token 可以互相装饰：as_tuple(use_awaitable) 把错误从异常改回返回值；redirect_error(use_awaitable, ec)；bind_cancellation_slot(slot, token)；bind_executor(strand, token)；cancel_after(5s, token)。「超时」「取消」「换执行上下文」这些横切关注点变成了可叠加的修饰词，而不是每个调用点重写一遍控制流。这才是它比「要么回调要么 future」的库强大的根源。

    自己写异步操作时也应该这么写，而不是硬编码 std::function 回调：

    template <typename Token>
auto async_my_op(asio::any_io_executor ex, Token&& token) {
    return asio::async_initiate<Token, void(std::error_code, int)>(
        [ex](auto handler) {                      // initiation：只写一次
            asio::post(ex, [h = std::move(handler)]() mutable {
                h(std::error_code{}, 42);           // 交付结果
            });
        }, token);
}
// 调用方从此可以用 callback / use_future / use_awaitable / use_sender 任意一种

    工程视角：库作者只写一次 initiation，Asio 从 2003 年的回调、2011 年的 future、2020 年的协程，到今天的 sender（§8.2），API 签名一个字没改——C++ 里少见的真正做到向未来兼容的设计。代价也要说：错误信息灾难级（token 类型层层嵌套）、编译时间长、调试符号巨大。团队里必须有人真读得懂 async_result，否则出了问题没人能查。硬编码 std::function 的自研库则会被彻底锁死——它既不能被 co_await，也接不进 parallel_group 和 awaitable_operators。

  2. 中级asio::awaitable<T> 协程的 executor 是怎么决定的？

    结论：由启动它的 co_spawn 的第一个参数决定，之后沿 await 链继承。协程一出生就带着这个 executor，此后每个 co_await 完成时，恢复都会被 dispatch 回它——所以协程体内的代码始终在同一个执行上下文里跑。

    • co_spawn(ex, coro(), token) 把 ex 记进协程帧；协程内 co_await asio::this_coro::executor 可以把它读出来（§4.2 的 listener 就是这么拿到 executor 去建 acceptor 的）。
    • 用 use_awaitable 发起的操作，其完成 handler 被绑到这个 executor。即便 IO 在别的线程上完成，恢复也会 post 回来。
    • co_await other_coro() 直接 await 另一个 awaitable 不会新建执行上下文，子协程继承父协程的 executor。
    • 想临时切换：co_await asio::dispatch(other_ex, asio::use_awaitable)，此后的代码就在 other_ex 上；或者 co_spawn(other_ex, sub(), asio::use_awaitable) 把子协程整个放到另一个 executor 上跑并等它回来。

    这就是 §6.4 那段代码成立的原理：co_spawn(make_strand(io), session(...), detached) 之所以能让整个会话无并发，不是某一次绑定的效果，而是整条协程的所有恢复点都被钉在了同一个 strand 上。

    最容易踩的坑：协程里用到的 socket / timer 必须用同一个 executor 创建。如果 socket 建在另一个 io_context 上，co_await 它的操作会在那个 io_context 的线程上完成、再 dispatch 回来——语义仍然正确，但白白多一次跨线程投递；更糟的是如果那个 io_context 压根没人 run()，协程会永远挂住，而且没有任何报错，表现为「某些连接莫名其妙不响应」。

    还有一个细节值得知道：dispatch 在「已经处于目标 executor」时会直接内联调用，而 post 一定排队。在循环里反复 co_await dispatch(自己的 executor) 可能造成递归深度增长；而且内联意味着不给同一线程上的其他 handler 机会，长循环会饿死别人。需要「让一让」的时候用 post。

  3. 中级用 Asio 协程实现「读 socket，5 秒没数据就超时」，怎么写才是对的？为什么不能 detach 一个定时器？

    结论：正确做法是把「读」和「等 5 秒」当作两个可取消的异步操作组合起来，谁先完成就取消另一个，并且等两个都真正落地后再返回。最简洁的是 awaitable_operators 的 ||。

    写法一（推荐，即 §5.2 的模式）：

    using namespace asio::experimental::awaitable_operators;

asio::awaitable<size_t> read_with_timeout(tcp::socket& sock,
                                          asio::mutable_buffer buf) {
    asio::steady_timer timer(co_await asio::this_coro::executor);
    timer.expires_after(5s);

    auto r = co_await (
        sock.async_read_some(buf, asio::use_awaitable)
        ||
        timer.async_wait(asio::use_awaitable));

    if (r.index() == 1)                 // 定时器先赢 = 超时
        throw std::system_error(asio::error::timed_out);
    co_return std::get<0>(r);
}

    || 的语义是关键：任一分支完成后，它会向另一分支发出 cancellation signal，并等待那一分支真正结束才返回。所以函数返回时两个操作都已落地，栈上的 timer 和 buf 可以安全析构。

    写法二（需要知道谁先完成的精确顺序，或不想引 awaitable_operators）：

    auto [order, ec_read, n, ec_timer] =
    co_await asio::experimental::make_parallel_group(
        sock.async_read_some(buf, asio::deferred),
        timer.async_wait(asio::deferred))
    .async_wait(asio::experimental::wait_for_one(),
                asio::use_awaitable);

if (order[0] == 1) { /* 定时器先到 → 超时 */ }

    写法三（Asio 1.30+ 的语法糖，最短）：cancel_after 本身就是一个 token 装饰器，语义与 || 一致，还省掉了显式的 timer 对象：

    size_t n = co_await sock.async_read_some(
    buf, asio::cancel_after(5s, asio::use_awaitable));

    写法四（回调风格老代码里最常见）：定时器回调里调 sock.cancel()，读回调里调 timer.cancel()，读回调拿到 operation_aborted 时再区分是超时还是主动关闭。注意 sock.cancel() 会取消该 socket 上所有未决操作（连同写），全双工场景要么改用 cancellation_slot 精确取消，要么接受这个粒度。

    为什么不能简单地 detach 一个定时器——这是这道题真正的考点，三个理由：

    生命周期
    detach 出去的定时器回调持有 &sock 和 &buf。如果读先完成、协程返回，栈上的 timer 和 buffer 就析构了；5 秒后回调触发，访问的是已销毁对象。就算把 timer 塞进 shared_ptr 保活，socket 也可能已经关闭而 fd 被复用，cancel() 会打到别人的 fd 上——这种 bug 表现为「随机某条无关连接被断开」，几乎无法复现。
    竞态
    即便两者都还活着，「读完成」和「定时器到期」是两个独立事件。你在超时回调里判断「读还没完成」的那一瞬间，读可能刚好完成。没有 strand 保护就是数据竞争；有 strand 也还需要一个「谁先赢」的原子标志——而这正是 || 和 parallel_group 内部替你做掉的事。
    取消不是同步的
    cancel() 只是一个请求。未决操作会以 operation_aborted 的形式稍后回来，在那之前 buffer 仍被 Asio（乃至内核）引用。所以必须等两边都完成才能释放资源。手写这段「等两边都收敛」的逻辑是最容易漏的一步，也是超时功能上线后偶发崩溃的经典来源。
  4. 中级gRPC 的同步 API 和异步 callback API 有什么区别？性能差多少？

    结论：同步 API 是「每个在途 RPC 占一个线程」的线程池模型；callback API 是「RPC 状态机挂在事件循环上，线程只在有事件时被借用」。差距体现在并发容量和尾延迟上，不体现在单次 RPC 的最优延迟上——低并发时同步 API 甚至更快，因为少一次跨线程投递。「异步一定快」是错的。

    • 同步：ServerBuilder 起一个动态线程池，请求进来占一个线程直到 handler 返回。handler 里调下游时，这个线程纯粹在等。并发上限就是线程数，线程一多，上下文切换和栈内存都成问题。
    • 老异步（CQ + tag）：手动管理 tag、自己排 Request → Read → Write → Finish 的状态转移。性能好，但正确性极难保证（尤其 stream 上「上一个 Write 未完成不能再 Write」这条约束）。
    • Callback API（§10.1，现代推荐）：继承 Reactor，靠 OnReadDone / OnWriteDone / OnDone 驱动，底层由 gRPC 的 EventEngine 线程池执行。handler 可以先返回、持有 reactor 指针稍后 Finish——这正是「下游还没回来就先把线程放走」的关键。

    性能差距要分情况说（数量级对齐 §9.3 的表）：

    • handler 是纯 CPU 且极短：两者差 2–3 倍，差距来源就是线程切换。
    • handler 里有 IO 等待（查 DB、调下游）：差一到两个数量级，因为同步模型的线程全被「等」占死了。这是 §9.3 里同步 10–30k QPS、异步 100–500k QPS 的真实来源。
    • 单条 RPC 的 P50：同步反而可能更低（callback 多一次队列投递）。异步换来的是同样线程数下容纳更多在途请求，不是单请求更快。

    生产视角：callback handler 里绝对不能阻塞——一次 sleep 或一把争用的锁就会占住 EventEngine 线程，整个服务卡死，而且现象是「所有接口一起变慢」，极难归因。要么全异步，要么显式扔到自己的线程池。第二个大坑是生命周期：reactor 必须活到 OnDone，OnDone 里 delete this 是标准写法但极易被「提前 Finish」打乱。所以生产上更推荐用 asio-grpc（§10.4）把它协程化，让生命周期回到作用域里去。

    迁移策略：不要一次全改。先把「会阻塞等下游」的接口改成 callback，纯内存计算的接口保持同步——收益风险比最好。

  5. 中级brpc 比 gRPC 强在哪？弱在哪？你会怎么选？

    结论：brpc 在单机 C++ 内部 RPC 的性能与可运维性上明显更强；gRPC 在跨语言生态、标准化、云原生集成上不可替代。选型不是比 benchmark 数字，是比「你的组织愿意在哪一侧付代价」。

    brpc 强在：

    • 线程模型：bthread 是 M:N 用户态协程 + work-stealing，代码写起来像同步、跑起来是异步。gRPC C++ 要么同步占线程，要么写 reactor 回调（见上一题），中间没有平滑档位。
    • 协议自动嗅探：一个端口同时认 baidu_std / HTTP / gRPC / Redis / Memcached / Thrift。迁移和联调时的价值远超想象——可以直接 curl 一个 protobuf 服务。
    • 可观测性是一等公民：内置 bvar 和 /vars /rpcz /flags /connections 等内置 HTTP 服务，线上直接看 P99 直方图、CPU / 锁竞争 profiler。gRPC C++ 这块要自己接 OpenTelemetry。
    • 长尾治理开箱即用：backup request（对付 P99 的杀手锏）、多种负载均衡策略、熔断、重试、服务发现都内置，且都是 C++ 版一等公民——而 gRPC 的这些能力长期是 Go / Java 版先行、C++ 版跟不上。

    brpc 弱在：

    • 基本只有 C++。跨语言必须走它的 HTTP / gRPC 兼容层，那时性能优势也就不存在了。
    • 社区与文档：Apache 孵化后活跃度不如 gRPC，issue 响应慢，文档以中文为主，跨国团队接受度低。
    • 云原生集成要自己补：Istio / Envoy / xDS、gRPC-Web、health checking、server reflection 这些事实标准都是围绕 gRPC 建的。
    • 依赖耦合：与 protobuf / gflags 等版本绑得较紧，在已有大型 monorepo 里落地的成本经常被低估。

    选型口径（对齐 §11.4 与 §16.1）：跨语言微服务用 gRPC；C++ 内部、对长尾延迟和线上可观测性要求高的核心链路用 brpc。两者可以共存——brpc 能直接对外提供 gRPC 协议，边界上不必二选一。真正需要避免的是「因为 benchmark 好看就全量换掉」，那笔账最后是被生态和运维吃掉的。

17.3 高级（体现深度）

  1. 高级设计一个百万连接的 Web 推送服务，单机内存怎么估算？为什么理论值和实测值总差一大截？

    结论先给数：推送类连接（绝大多数时间空闲、消息小）单机百万连接的现实目标是 16–32 GB。但如果按内核默认参数、每连接一个固定读写 buffer 去写，同样一百万连接要到 90–100 GB，机器直接 OOM。差别几乎全在「buffer 是常驻还是按需」这一件事上。

    项朴素写法 / 连接优化后 / 连接说明
    struct sock + tcp_sock + file/inode~3 KB~3 KB内核固定开销，砍不掉
    epoll 注册项~0.2 KB~0.2 KB—
    收 + 发缓冲~64 KB（按 §13.3）~8 KB自动调优的上限不等于占用

    TLS 那一项单独说：OpenSSL 的 SSL* 默认为每条连接常驻两个 16 KB 的 record buffer（TLS record 最大 16 KB），空闲连接也不释放。百万连接就是 32 GB 凭空消失。开 SSL_CTX_set_mode(ctx, SSL_MODE_RELEASE_BUFFERS) 后空闲时会归还，降到几 KB；能上 kTLS 就把 record 处理整个交给内核。这是百万连接 HTTPS/WSS 网关的第一个必调项，也是最常被漏掉的。

    能报得出名字的旋钮：net.ipv4.tcp_rmem / tcp_wmem 的最小值和默认值（不是 max——自动调优从 default 起步，降 default 立竿见影），tcp_moderate_rcvbuf=1 保持自动调优开启，net.ipv4.tcp_mem 全局水位（到 pressure 会强制收缩每连接 buffer），应用层读缓冲池 + 仅在 EPOLLIN 时借出（Nginx / Envoy 都这么做），写路径用 writev 避免为每连接常驻 out buffer，以及 §13.4 的 ulimit -n / fs.file-max / fs.nr_open 和 conntrack。

    为什么理论值和实测值总差一大截——这才是这道题的真正考点：

    1. 内核 buffer 是上限不是占用。tcp_rmem 的第三个值只是自动调优天花板，空闲连接实际只占已收到的 skb。按 max 算会严重高估。但反过来，一旦出现慢消费者，几万条连接同时把 wmem 涨到 MB 级，内存能在几秒内翻十倍。所以估算必须给稳态和最坏两套数，容量规划按最坏。
    2. skb 的真实开销远大于 payload。一个 1 字节的 TCP 段在内核里是 sk_buff + skb_shared_info + 一个页片段，truesize 常常是 768 B 到 4 KB。攻击者用大量小包就能把 rmem 打爆，而 payload 只有几 MB——这是「内存涨了但流量没涨」的经典成因。
    3. 分配器不把内存还给 OS。glibc malloc 的 arena、tcmalloc 的 page heap 在连接峰值过后不会 madvise 回去，RSS 只涨不跌。看着像内存泄漏，实际是碎片。对策是 MALLOC_ARENA_MAX、tcmalloc 的 ReleaseFreeMemory，或者干脆改用固定大小的 slab 池——百万连接场景下后者才是正解。
    4. 协程 frame 的大小由编译器决定，不是你写的局部变量之和。循环里一个 co_await 就可能把整个 8 KB 数组抬进 frame。百万协程时必须实测（heaptrack / 编译器的 frame size 诊断），不能拍脑袋按「1–2 KB」算。
    5. 还有一堆没人算的固定成本：一百万个 fd 的 file 表本身就是几百 MB；跨 NUMA node 分布的内核结构会放大访存延迟；cgroup 记账把 page cache 也算进来。

    验证方法（面试里给出这个比给数字更值钱）：/proc/net/sockstat 的 mem 列看内核 socket 内存总量，ss -m 看单连接的 skmem 明细，cgroup 的 memory.stat 分解 anon / file / slab，再用 heaptrack 或 tcmalloc 的 heap profiler 看应用侧。先量再调，不要先调再量。

  2. 高级RPC 的超时、重试、熔断怎么做对？应该写在业务代码里还是 sidecar 里？

    结论：没有「全放一边」的正确答案。能机械化、与业务语义无关的部分（连接超时、mTLS、指标、基于状态码的熔断、幂等方法的重试）下沉到 sidecar；需要业务语义才能判断的部分（整体 deadline 预算、幂等键、这次失败到底能不能重试、降级返回什么）必须留在业务里。这是分层，不是二选一。

    先说三件事各自怎么做对。

    超时
    关键不是「设一个值」，而是 deadline propagation：入口处定一个绝对截止时间（不是相对超时），随请求透传（gRPC 的 grpc-timeout header / ClientContext::set_deadline），每一跳减去已花时间和网络裕量再往下传。这样最深层的服务才知道「我只剩 30 ms 了，别再重试了」。反模式是每层都写死 1 s：三层调用链上最外层早已超时返回，内层还在跑，白烧资源，还会造成「客户端记超时、服务端记成功」的排障噩梦。
    重试
    前提是幂等，代价是放大。只重试明确安全的错误（连接失败、UNAVAILABLE），DEADLINE_EXCEEDED 一般不该重试——预算已经花光了。必须带 jitter 的指数退避，且只在还有剩余 deadline 时才重试。最重要的是要有重试预算（如「重试量不超过总请求量的 10%」）而不是固定次数：N 层调用链每层重试 3 次，末端会看到 3N 倍流量——这就是重试风暴，是把局部抖动升级成全站雪崩的头号途径。很多团队只配了 numRetries 就上线，等于埋了一颗雷。非幂等写请求要么不重试，要么服务端用幂等键在窗口内去重——而这一步 sidecar 做不了，它不知道你的业务主键。
    熔断
    目的是快速失败以保护下游和自己。触发信号不能只看错误率——下游变慢但不报错时错误率是 0，队列却在爆。Envoy 的 circuit breaker 本质上是并发上限（max_connections / max_pending_requests / max_requests / max_retries），比经典的「闭合-半开」状态机更适合代理层，因为它直接约束了在途量。而熔断之后返回什么——缓存兜底、降级字段、还是直接报错——天然是业务决定。

    放 sidecar 的理由：多语言统一，Python / Java / C++ 服务不用各写一遍；策略由控制面（xDS）动态下发，改超时不用发版——这是最大的价值；与 mTLS、灰度、流量镜像、可观测性天然打包（§15.3 的做法）；策略正确性由一个团队维护，避免每个业务自己写出一个错误的退避。

    放 sidecar 的代价：每 hop 增加 0.5–2 ms 和一份 CPU / 内存（§14.3）——对 §15.1 那种 P99 要 2.3 ms 的行情链路根本不可接受；sidecar 看不见业务语义，无法判断这个 POST 是否幂等、无法在超时后给出有意义的降级结果；运维复杂度是真实故障源（注入、版本、启动顺序——应用比 sidecar 先起就连不上，优雅退出——sidecar 先死就是流量黑洞）；熔断状态是 per-sidecar 的局部视角，多副本下各自计数，整体行为不如集中式直观。

    我的实践口径：有服务网格时，连接级超时、mTLS、幂等方法的状态码重试、并发上限熔断放 Envoy；deadline 预算、幂等键、降级逻辑留业务；重试只在一层做（通常是最靠近用户的那层或 sidecar），严禁多层叠加。没有网格或延迟敏感时，用 brpc / gRPC 客户端自带的 retry policy + backup request + 熔断，超时用 §5.2 的 || 组合，并把策略收敛到一个 RPC 封装层——最坏的情况不是「放错了地方」，而是散落在几百个调用点上、谁也说不清线上真实的超时是多少。

  3. 高级跨数据中心的 RPC 怎么处理网络抖动？

    结论：跨 DC 的本质变化是 RTT 从 0.1 ms 变成 30–100 ms，而且抖动和丢包是常态而非异常。处理思路分三层：能不跨就不跨（架构）、跨了要抗抖（传输与调用策略）、抖了要能降级（业务）。单纯调重试次数解决不了问题，往往还会让问题更糟。

    架构层（收益最大，也最常被跳过）：

    • 单元化 / 就近读：强一致的写收敛到主 region，读走本地副本；把跨 DC 的同步 RPC 改成异步复制 + 本地读。一次跨洋 RPC 至少 150 ms，串行三次就是 450 ms，任何传输层调优都救不回来。
    • 批量化 + 并行化：必须跨的调用，要么用聚合接口把 N 次串行合成一次，要么用 when_all（§5.3 的 &&）并行发出，把 N×RTT 压成 1×RTT。这是投入产出比最高的一项改造。
    • 长连接常驻 + 预热：跨 DC 建连是 1 个 RTT（TCP）加 1 个 RTT（TLS1.3），冷连接的第一个请求会明显更慢。连接池要有最小空闲数和 keepalive，避免 NAT 静默超时后第一个请求踩 RST。

    传输层：

    • 拥塞控制换 BBR。跨 DC 是典型的「高带宽时延积 + 偶发随机丢包」，CUBIC 会把随机丢包当成拥塞信号而大幅降窗，吞吐塌陷。
    • tcp_rmem / tcp_wmem 上限要满足 BDP：100 ms × 1 Gbps ≈ 12.5 MB，窗口不够就永远跑不满带宽——注意这和上一题「百万连接要压小 buffer」是相反的方向，两类服务不能用同一套内核参数。
    • 移动或跨洋场景考虑 QUIC：0-RTT 恢复、每流独立重传、连接迁移（§12.3），在 1% 丢包的链路上比 TCP 稳得多。
    • 开 TCP_NODELAY。Nagle 与延迟 ACK 互等造成的 40 ms 级毛刺，在跨 DC 上极易被误诊为「网络抖动」，实际是自己造的。

    调用策略层：

    • hedged / backup request 是把 P99 拉回 P95 最有效的手段：请求发出后若 P95 时间内未返回，就向另一个副本再发一个，谁先回用谁。因为长尾的根因通常是个别节点或个别丢包，而不是整体变慢——重发一份大概率就绕开了。前提同样是幂等，且要有额外流量预算（控制在百分之几）。brpc 的 backup request、gRPC 的 hedging policy 都提供了。
    • 超时按 P99.9 + 裕量设，不要按均值。跨 DC 的超时必须比同城大一个量级，否则你会把正常请求判成失败然后重试，亲手制造雪崩。
    • 熔断按 region 维度独立统计，远端 DC 挂掉不应该污染本地调用的统计窗口。
    • 跨 DC 依赖不能是硬依赖，必须有降级路径：本地缓存、上一次快照，或明确标注的「部分结果」。

    定位方法：先分清是网络还是对端。同时看 TCP 层指标（ss -ti 的 rtt / rttvar / retrans、nstat 的 TcpRetransSegs）和服务端自身耗时：RTT 抖而服务端耗时平稳 = 网络；两者都平稳但客户端观测慢 = 排队（本端 backlog 或对端线程池）。端到端打点要带 trace id 且两侧都记时间戳，跨 DC 时钟不同步，只能用差值对齐，不能直接减绝对时间。

  4. 高级Envoy 为什么用 C++ 而不是 Go？换成今天你会怎么选？

    结论：因为 Envoy 是数据平面——每个请求都要穿过它，它的延迟直接加在所有服务的 P99 上。这类「每请求过一遍」的组件对尾延迟的确定性和内存的可预测性要求极高，而这恰恰是带 GC 的运行时最难保证的。但这不是「Go 不行」：Istio 的控制平面 istiod 就是 Go 写的。选型是按组件角色分的，不是按语言站队。

    选 C++ 的理由（对齐 §14.2 Lyft 的公开说法，并展开）：

    • P99 可控。Go 的 GC 已是并发标记、STW 亚毫秒，但 write barrier 有常驻开销，分配压力大时 mutator assist 会把标记工作摊给业务 goroutine，堆越大扫描越贵。而代理的内存里全是短命的 buffer 和 header——正是 GC 最不喜欢的形状。C++ 用确定性析构 + 对象池，延迟分布更平。
    • 内存可控。sidecar 常常只给 64–128 MB。Go 的 GOGC 模型天生要留出回收余量（不设 GOMEMLIMIT 时更明显），小配额下要么频繁 GC 要么被 OOMKill。
    • 生态在 C/C++ 这一侧：BoringSSL、nghttp2、gRPC C++、QUICHE 都是 C/C++；从 Go 走 cgo 调用要付栈切换成本并失去内联，反而更慢。
    • 内存布局控制：buffer 链、slice 引用、让 body 在多层 filter 间零拷贝流过——这些在 C++ 里是自然写法。

    选 Go 的理由也要给足，否则就成了站队：

    • 安全性。Envoy 历史 CVE 里相当一部分是内存安全和解析器问题，Go / Rust 能从语言层消掉一整类——对一个部署在所有流量路径上的组件来说，这个价值不小。
    • 开发效率。goroutine + channel 写 L7 逻辑远比 Envoy 的 filter 状态机好写。Envoy 的每线程事件循环模型（§14.1）要求所有 filter 严格非阻塞，扩展作者极容易写出一个阻塞调用把整个 worker 卡死。
    • 确有成功案例：Traefik、Caddy，以及蚂蚁用 Go 写的 MOSN——在其规模和场景下工作得很好。

    最有说服力的证据是 Envoy 自己的应对：正因为 C++ 门槛高、扩展迭代慢，它提供了 WASM filter SDK（可用 Rust / Go / TinyGo 写）和 Lua filter——核心热路径用 C++ 保性能，可变部分用高级语言隔离出去。这才是完整答案：不是「C++ 全面胜出」，而是分层用语言。

    今天重写会怎么选：多半会认真评估 Rust——同样无 GC，但内存安全。Cloudflare 的 Pingora 用 Rust 替换 NGINX 就是这个思路的实证，理由正是「想要 C 的性能和 Go 的安全」。真正的判据始终是那句：热路径上，延迟的方差比均值更重要；GC 恰恰是方差的来源。

  5. 高级为什么说 std::execution（Sender/Receiver）是异步 C++ 的未来？它今天能用吗？

    结论：因为它第一次给 C++ 的异步提供了一套可组合的代数和统一的取消 / 错误 / 调度语义，而不是又一个 future 或又一个协程库。协程解决的是「怎么写得像同步」，S/R 解决的是「怎么把异步操作当成值来传递、组合、装饰、取消」——这两件事正交，所以它们不是竞争关系，而且确实可以互操作。

    它修掉的是现有方案的结构性缺陷：

    • std::future：类型擦除 + 堆分配 + 没有取消 + .then 没进标准，shared state 的原子操作还实打实压在热路径上。
    • 裸回调（Asio callback 风格）：能做到零开销，但组合靠嵌套、取消要手写状态机、错误路径靠口头约定——上一档那道「读 + 5 秒超时」的三个坑，全部出自这里。
    • 协程：本身没有调度器、没有取消、没有「在哪跑」的概念。每个库自己发明一套（asio::awaitable、folly::coro、cppcoro）且互不相通；每个挂起点还可能有一次堆分配。

    四个关键性质：

    1. 惰性 + 静态组合。sender 只是描述；connect(sender, receiver) 产生 operation state，start 才执行。整条管线在编译期展开成一个状态机，operation state 可以放在调用者的栈或成员里——结构上允许零动态分配、零虚调用。
    2. 三通道完成。set_value / set_error / set_stopped 是框架级约定，取消不再伪装成一种错误码，错误也不再靠异常穿透。
    3. 结构化并发。when_all / let_value / sync_wait 的嵌套关系保证子操作生命周期不超过父作用域，stop_token 沿链自动向下传播、向上收敛。这从语言层面消灭了「手写取消 + 等两边收敛」的那一整类 bug。
    4. 调度与算法解耦。scheduler 是一个概念，同一段算法可以跑在线程池、io_uring、甚至 GPU 上——NVIDIA 推动 stdexec 的动机正在于此。这是 future 和协程都给不了的。

    直观差别看 §8.1：超时、重试、熔断变成了装饰算子——| stop_when(timer(5s))、| retry_when(backoff)，而不是在每个调用点重写一遍控制流。这和 completion token 的可装饰性是同一个思想，只是做到了跨库通用。

    保留意见必须给，否则不像做过生产：编译期成本和错误信息是真实痛点，一个类型不匹配能刷几百行，调试器里看到的是一坨模板生成的状态机；生态没跟上——C++26 只标准化了执行框架本身，网络还没进标准，Asio 的 use_sender（§8.2）是桥接不是原生；心智负担高，团队里能正确写自定义 sender 的人不会多，多数人只应该「用算子」。

    所以现实路线（也是 §8.3 那个提示框的意思）：今天生产用 Asio + 协程，同时保证协程与 sender 可互通（awaitable 能从 sender 构造，反之亦然），等标准和库成熟后再迁移热路径。提前布局，别提前 all-in——这是对「未来」这个词最负责任的用法。
