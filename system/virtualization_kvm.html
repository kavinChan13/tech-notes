虚拟化与虚机 I/O

容器底层那一篇把 namespace 和 cgroup 讲透了，虚机这一侧一直是空白。这一篇补上：KVM 的开销到底在哪（不在「执行」，在「退出」）、virtio 凭什么比模拟设备快三个数量级、SR-IOV 直通换走了什么、以及在虚机上跑低延迟服务必须处理的那几件事。

核心难度 ★★★★☆ 系统底层 阅读时长 ~30 min 前置 内存管理 · 中断 · 容器
01

虚拟化到底虚拟了什么

三样东西，难度和开销完全不同

1.1 三样东西：CPU、内存、设备

要虚拟的难在哪硬件怎么帮忙剩下多少开销
CPU 客户机以为自己有特权，但不能真的碰硬件 VT-x / AMD-V：给 CPU 加一个「客户机模式」，普通指令原生执行，只有特权操作才陷出 纯计算几乎为零（< 2%）
内存 客户机的「物理地址」其实是宿主的虚拟地址，要翻译两次 EPT / NPT：硬件做两层页表走查 TLB 命中时为零；miss 时页表走查从 4 次变 24 次（§3.1）
设备 网卡、磁盘是真实存在的，一份要给多个客户机用 没有通用的硬件方案——这是全部开销的所在 从 3 个数量级到接近零，取决于用哪一档方案（§4）
这张表的结论决定了整篇文章的重心：CPU 和内存的虚拟化已经被硬件解决得很好了，虚机慢，慢在 I/O。所以 §4 是全篇最长的一章，而「虚机性能调优」这件事，九成的工作是在选对设备虚拟化方案。

1.2 执行几乎免费，退出才要钱

KVM 的模型很简单：宿主上的 qemu 进程通过 /dev/kvm 请求内核把某个线程切换到客户机模式去跑。切进去之后，客户机的代码直接在物理 CPU 上执行——不是解释，不是翻译，就是原生指令。

执行是免费的，开销全在这个退出—处理—返回的循环上。要优化虚机性能，就是要减少退出次数。
02

VM Exit：所有开销的来源

把它当成一次「特别贵的系统调用」来理解

2.1 一次退出的成本

一次 VM Exit + Entry 的往返，硬件部分（保存/恢复客户机状态、切页表根、刷新部分 TLB）大约 1000–2000 个周期，也就是 0.3–0.7 μs。再加上处理逻辑：

· KVM 内核里就能处理完（比如访问虚拟 APIC）：合计约 1–3 μs；
· 要退到 QEMU 用户态处理（比如模拟一次 PIO 读）：还要再加一次内核到用户态的往返和设备模拟逻辑，合计 数微秒到数十微秒。

对比：一次普通系统调用约 0.1–0.6 μs。退到 QEMU 的那种退出，比系统调用贵一到两个数量级。

把这个单价乘上频率就知道问题在哪了。一个模拟的 e1000 网卡，收发一个包要访问好几次寄存器，每次都是一个 PIO/MMIO 退出——单包成本几十微秒，于是万兆网卡在虚机里只能跑出几万 pps。这就是 §4 存在的全部理由。

2.2 哪些操作会触发退出

触发原因频率能不能消除
访问模拟设备的寄存器（PIO / MMIO）极高——每个 I/O 操作几次能：换 virtio（批量化）或 SR-IOV（直通，完全不退出）
EPT violation（客户机物理页还没建立映射）启动时密集，之后收敛能：预分配内存 + 大页（§3.2）
外部中断（网卡、定时器）中高部分：中断合并、APICv/posted interrupt 让中断直接投递给客户机不退出
HLT（客户机空闲）取决于负载可调：halt_poll_ns 让 vCPU 先自旋一会儿再真退出
CPUID、访问某些 MSR低不用管
自旋锁的 PLE（Pause-Loop Exiting）vCPU 超卖时很高这是特性不是 bug：客户机在自旋等一把锁，而持锁的 vCPU 没被调度，退出让宿主去调度它（§6.1）
最后一行值得展开，它是虚机上一个非常隐蔽的性能问题的根源：客户机内核的自旋锁假设「持锁者正在另一个 CPU 上跑」，所以自旋等待是划算的。但在虚机里，持锁的那个 vCPU 可能根本没有被宿主调度——它在 runqueue 里排队。此时其它 vCPU 的自旋是纯粹的浪费，而且它们还占着宿主的 CPU，让持锁者更难被调度到。

这就是 Lock Holder Preemption，vCPU 超卖时它会让性能断崖式下跌。缓解手段是 PLE（自旋太久就退出，把 CPU 让给宿主去调度持锁者）和准虚拟化自旋锁（客户机知道自己在虚机里，自旋一会儿就直接让出而不是死等）。
但最有效的还是不超卖 vCPU——这也是低延迟场景要独占物理核的原因之一（§6）。

2.3 怎么观测

命令看什么
kvm_stat / perf kvm stat live最直接：按原因分类的退出次数与耗时。先看 exits 的绝对值和 top 原因
perf kvm --host --guest record同时采样宿主和客户机，看时间花在哪一侧
cat /sys/kernel/debug/kvm/*各类计数器的原始值
客户机里 vmstat 1 的 st 列steal time——从客户机视角看「我被抢走了多少」（§6.1）
03

内存虚拟化：两层页表

TLB 命中时零开销，miss 时成本是原来的六倍

3.1 EPT 与两维页表走查

客户机以为自己在操作物理内存，其实它的「物理地址」（GPA）还要再翻译一次才能得到宿主的物理地址（HPA）。硬件用 EPT（Intel）/ NPT（AMD）来做这层翻译，客户机的页表照常用，两层都由硬件走查。

代价在 TLB miss 时暴露。裸机上一次四级页表走查是 4 次内存访问。
虚机里，客户机页表的每一级都存在客户机物理地址里，而每一个 GPA 又都要过一遍 EPT 的四级走查：
(4 + 1) × 4 = 20~24 次内存访问——大约 6 倍。

TLB 命中时这些全都不发生，所以对工作集小的负载完全无感；但对随机访问大内存的负载（数据库、大图、稀疏矩阵），TLB miss 频繁，这 6 倍就实实在在地出现了。

3.2 为什么虚机里更该用大页

NUMA 与高级内存管理那篇讲过大页减少 TLB miss 的道理。在虚机里这个收益被放大了，因为每一次 miss 的代价是裸机的 6 倍：

客户机内用大页

减少客户机页表的层数与 TLB 压力。收益和裸机一样。

宿主给客户机内存用大页（更重要）

让 EPT 那一层也用大页，把 (4+1)×4 里的第二个 4 降下来。
做法是宿主侧用 hugetlbfs 预分配客户机内存。顺带还消除了 EPT violation 的启动尖峰，因为内存是预先分配好的。

「宿主用大页」还有一个附带好处，对低延迟场景很关键：预分配的大页不会被换出、不会被 KSM 合并、也不会触发 THP 的 khugepaged 后台整理。这三样都是延迟毛刺的来源。
代价是这块内存被这台虚机独占了，宿主不能再超卖——这正是下一节的取舍。

3.3 内存超卖的三种手段与代价

手段怎么做代价
Ballooning 客户机里装一个「气球」驱动，宿主让它申请内存并归还给宿主 需要客户机配合；回收速度慢，救不了突发；客户机会以为自己内存变少了
KSM（同页合并） 宿主扫描内存，把内容相同的页合并成一份写时复制 扫描本身耗 CPU；写入时触发 CoW 造成延迟毛刺；而且它是一条已知的侧信道（通过写入延迟能推断别的虚机有没有同样的页）
Swap 宿主把客户机内存换出 最糟：客户机完全不知道，它以为自己在访问「物理内存」。一次访问从纳秒变成毫秒，而客户机内部的所有调度和超时判断都没考虑这种可能
宿主 swap 客户机内存是虚机性能问题里最难查的一类：客户机内部看不到任何异常——它的内存使用率正常、没有 swap、CPU 也不高，只是所有操作都莫名其妙地慢，而且慢得毫无规律。
只有在宿主侧看 vmstat 的 si/so 才能发现。所以「虚机很慢但客户机内部什么都看不出来」时，第一个要问的是宿主的内存有没有超卖。
04

设备虚拟化：从模拟到直通

虚机性能调优九成的工作在这一章

4.1 四档方案与它们省掉了什么

4.2 virtio 快在哪

virtio 的核心思路只有一句：放弃「假装自己是一块真网卡」。全模拟之所以慢，是因为客户机驱动以为在操作硬件寄存器，而每一次寄存器访问都是一次 VM Exit。virtio 让客户机知道自己在虚机里，于是可以用一个专为虚拟化设计的接口：

共享内存环形队列

客户机和后端共享一块内存，里面是描述符环（vring）。放一个请求进去 = 一次内存写，不需要退出。

批量化 + 通知抑制

攒一批再敲一次门（kick），N 个包共享一次退出。而且队列非空时后端可以关掉通知（类似 NAPI 的思路），进一步减少 kick。

零拷贝的可能

描述符里放的是客户机物理地址，后端可以直接 DMA，不必逐字节搬运。

「批量化 + 通知抑制」这个组合眼熟吗？它和内核网络栈的 NAPI（中断来了就关中断转轮询，处理完一批再开）是同一个模式，也和接入网关那篇的 eventfd 聚合唤醒（只在队列由空变非空时通知一次）是同一个模式。

三个完全不同的场景，收敛到同一个解法：当「通知」比「数据」还贵时，就把通知摊薄到一批数据上。这是系统设计里复用率极高的一条模式，值得单独记住。

4.3 vhost 与 vhost-user

用了 virtio 之后，剩下的开销主要是「从 KVM 退到 QEMU 用户态」那一跳——每处理一批数据都要走一次内核到用户态的往返。vhost 就是把后端搬走：

方案后端在哪省掉了适合
virtio + QEMU 后端QEMU 用户态—通用，默认
vhost-net / vhost-scsi宿主内核线程到 QEMU 的那次用户态往返大多数生产虚机的默认选择
vhost-user另一个用户态进程（通常是 DPDK 或 OVS-DPDK）内核网络栈整个跳过NFV、高性能虚拟交换
vhost-user 有一个容易被忽略的前提：它需要客户机内存对后端进程可见。所以客户机内存必须是共享的（-object memory-backend-file,share=on），通常配 hugetlbfs。
这也意味着后端进程能读写整个客户机内存——它是一个信任边界上的组件，和 QEMU 同级，不是一个普通的用户态程序。

4.4 SR-IOV 的代价是失去迁移

SR-IOV 让一块物理网卡在硬件上呈现出多个「虚拟功能」（VF），每个 VF 可以直通给一台虚机。客户机用原生驱动直接操作它，数据路径完全不经过宿主软件栈，性能接近裸机。

但它换走的东西很实在：

失去什么为什么
热迁移虚机直接持有一个物理设备的状态，宿主不知道也复制不了。这通常是决定性的否决理由——失去迁移意味着宿主打补丁要停机
硬件无关性客户机装的是厂商驱动，换机型可能要换驱动
灵活的网络策略流量不过宿主，宿主上的安全组、流量镜像、QoS 都失效——这些要挪到网卡硬件里做（如果它支持）
密度VF 数量由硬件决定（常见几十到上百个），比软件方案少得多
近年出现的中间路线值得知道：vDPA（virtio Data Path Acceleration）。它让硬件直接实现 virtio 的数据面（所以性能接近 SR-IOV），但控制面仍然由宿主软件管——于是热迁移又回来了，因为迁移时可以把数据面从硬件切回软件 virtio。

这是一个很典型的架构演进模式：把「快」和「可管理」拆到数据面和控制面两边，各取所长。和 OTA 那个控制面/数据面分离是同一个思路，只是发生在硬件层。
05

裸金属 vs 虚机 vs 容器

它们不是三个档位，是两个维度

5.1 隔离强度与性能对照

裸金属虚机容器
隔离边界物理硬件虚拟化 + 独立内核共享宿主内核，靠 namespace + cgroup
攻击面—hypervisor（小，几十万行）整个宿主内核（几千万行）+ 全部系统调用
启动时间分钟秒级（轻量 VM 可到百毫秒）百毫秒
内存开销0每台一个内核 + QEMU，约 100–200 MB接近 0
计算性能100%98%+~100%
I/O 性能100%virtio+vhost 约 80–90%，SR-IOV 接近 100%~100%
能跑别的内核 / 内核模块能能不能
密度1几十几百
这张表里最重要的一行是「攻击面」。容器的隔离本质上是「同一个内核里的权限划分」——所有容器共享那几千万行内核代码，一个内核提权漏洞就能横穿全部容器。虚机的隔离是「不同的内核 + 硬件强制的地址空间隔离」，要突破得先攻破 hypervisor。

所以判据不是「谁更快」，而是「你需要防谁」：跑自己团队的代码 → 容器完全够；跑不受信任的第三方代码（多租户 FaaS、CI runner、在线代码执行）→ 容器的隔离强度不够，这正是下一节那些东西出现的原因。

5.2 轻量 VM 为什么出现

上面那张表暴露了一个空档：需要虚机的隔离强度，但受不了它的启动时间和内存开销。典型场景是 FaaS——每个函数调用起一个沙箱，要求百毫秒级启动、每个几十 MB。

Firecracker

把 QEMU 换成一个只有几万行、只支持极少设备（virtio-net / virtio-block / 串口）的 VMM。启动 ~125 ms，内存开销 < 5 MB。
做法是砍功能：不支持 PCI 热插拔、不支持图形、不支持 BIOS。

Kata Containers

保持容器的接口（OCI、K8s 里像普通 Pod 一样用），但每个 Pod 跑在自己的轻量虚机里。
它换的是「容器的易用性 + 虚机的隔离」，代价是启动慢一些、内存多一些。

gVisor

另一条路：不用硬件虚拟化，而是在用户态实现一个内核，拦截容器的系统调用。
攻击面小了（不直接碰宿主内核），但系统调用密集的负载会明显变慢，且部分冷门系统调用不支持。

三者的差别可以归结为「在哪一层重新实现内核语义」：Firecracker 和 Kata 用真内核 + 精简的 VMM（兼容性最好），gVisor 在用户态重写内核（兼容性打折，但不依赖硬件虚拟化，嵌套虚拟化环境里也能用）。

选择的判据是兼容性要求：跑标准的 Linux 负载 → 前两者；跑受控的、系统调用面窄的负载 → gVisor 的开销可以接受。

5.3 怎么选

如果……选
跑自己团队的代码，追求密度和启动速度容器
跑不受信任的第三方代码轻量 VM（Firecracker / Kata）
需要不同的内核版本、或要加载内核模块虚机（容器做不到）
需要把整台机器交给一个租户 / 极致性能裸金属
需要热迁移来做宿主维护虚机，且不能用 SR-IOV（§4.4）
低延迟、抖动敏感裸金属优先；必须用虚机的话看 §6
06

在虚机上做低延迟

默认配置下虚机的抖动比裸机大一个数量级

6.1 steal time：看不见的抢占

宿主把 CPU 分给了别的虚机，你的 vCPU 有一段时间根本没在跑。但客户机的时钟继续走——于是表现为「明明什么都没做，测出来花了 20 ms」。

这类问题在客户机内部几乎无法归因：CPU 使用率不高、没有 IO 等待、代码逻辑也没问题。唯一的线索是 vmstat 的 st 列，而很多监控面板压根不采集这一列。

它对性能分析的破坏性在于：它让「墙上时间」和「实际执行时间」脱钩。用 CLOCK_MONOTONIC 测出一段代码 20 ms，可能 18 ms 是 vCPU 被抢走了。区分方法是同时测 CLOCK_PROCESS_CPUTIME_ID（只算本进程真正占用的 CPU），两者差得多就说明时间花在等待上——详见时间与时钟 · 虚机的时钟问题。

消除它只有一个办法：不超卖，且把 vCPU 钉在专属的物理核上（CPU pinning）。这也顺带解决了 §2.2 那个 Lock Holder Preemption。

6.2 NUMA 拓扑必须穿透

6.3 一张调优清单

#做什么解决什么
1vCPU pinning，不超卖steal time、Lock Holder Preemption、调度抖动
2宿主侧 isolcpus / cpuset 把这些核隔离出来，别让宿主的其它任务用邻居干扰
3宿主用 hugetlbfs 预分配客户机内存EPT 走查开销、启动尖峰、换出、KSM 毛刺（§3.2）

6确认 clocksource 是 kvm-clock迁移后时间跳变（时间与时钟 §7.3）
7中断亲和性：把 VF / vhost 的中断绑到 vCPU 所在的核跨核收包
8调 halt_poll_ns空闲 vCPU 唤醒延迟（用一点 CPU 换低延迟）
9把 steal time 纳入监控不是优化，是让这类问题可归因——成本最低、最该先做的一条
这九条里 1–4 是一组：它们本质上都是「放弃超卖，换确定性」。虚拟化的核心卖点是资源复用，而低延迟场景要的恰恰是不复用——所以「在虚机上做低延迟」多少有点自相矛盾，做到最后你会发现这台虚机独占了它的核和内存，除了多一层 hypervisor 之外和裸金属没什么区别。

这时候值得回头问一句：还留着虚拟化是为了什么？如果答案是「热迁移」「统一的管理接口」「快速重建」，那它是划算的；如果答案是「因为公司只有虚机」，那就该去争取裸金属。

面试题（12 道）

按难度分三档

点击每道题展开参考答案（先自测，再对照）。

8.1 基础

  1. 基础KVM 的虚拟化开销主要在哪？

    不在「执行」，在「退出」。客户机代码进入客户机模式后是原生在物理 CPU 上执行的——不是解释，不是二进制翻译。所以纯计算负载的开销 < 2%。

    开销全在 VM Exit
    遇到特权操作、外部中断、EPT 缺页时会切回宿主处理。一次往返硬件部分约 1000–2000 周期（0.3–0.7 μs）；KVM 内核里处理完约 1–3 μs，要退到 QEMU 用户态的则是数微秒到数十微秒——比一次普通系统调用贵一到两个数量级。
    推论
    所有虚机优化手段（virtio、vhost、SR-IOV、大页）本质上都是同一个目标的不同做法：减少退出次数。
    怎么观测
    perf kvm stat live 或 kvm_stat，看按原因分类的退出次数与耗时。
  2. 基础virtio 比模拟网卡快在哪？

    核心思路一句话：放弃「假装自己是一块真网卡」。

    全模拟为什么慢
    客户机驱动以为在操作硬件寄存器，每一次寄存器访问都是一次 VM Exit。收发一个包要访问好几次，单包成本几十微秒——万兆网卡在虚机里只能跑几万 pps。
    virtio 的三件事
    ① 共享内存环形队列：放一个请求 = 一次内存写，不退出；② 批量化 + 通知抑制：攒一批敲一次门，N 个包共享一次退出，队列非空时后端还能关掉通知；③ 描述符里放客户机物理地址，后端可以直接 DMA。
    加分：这个模式眼熟
    「批量化 + 通知抑制」和内核网络栈的 NAPI（中断来了关中断转轮询）是同一个模式。当「通知」比「数据」还贵时，就把通知摊薄到一批数据上——这是系统设计里复用率极高的一条模式。
  3. 基础虚机和容器的隔离差在哪？该怎么选？
    本质差别是攻击面
    容器共享宿主内核，隔离是「同一个内核里的权限划分」——攻击面是整个宿主内核（几千万行）+ 全部系统调用，一个内核提权漏洞就能横穿所有容器。
    虚机是「不同的内核 + 硬件强制的地址空间隔离」，攻击面是 hypervisor（几十万行），要突破得先攻破它。
    判据不是「谁更快」，是「你需要防谁」
    跑自己团队的代码 → 容器完全够。跑不受信任的第三方代码（多租户 FaaS、CI runner、在线代码执行）→ 容器的隔离强度不够。
    其它维度
    容器启动百毫秒、内存开销接近零、密度几百；虚机启动秒级、每台多 100–200 MB（内核 + QEMU）、密度几十。但虚机能跑不同内核版本、能加载内核模块，容器不能。
  4. 基础什么是 steal time？为什么它难查？

    宿主把 CPU 分给了别的虚机，你的 vCPU 有一段时间根本没在跑，但客户机的时钟继续走——表现为「明明什么都没做，测出来花了 20 ms」。

    为什么难查
    在客户机内部几乎无法归因：CPU 使用率不高、没有 IO 等待、代码逻辑也没问题。唯一的线索是 vmstat 的 st 列，而很多监控面板压根不采集这一列。
    它对性能分析的破坏性
    它让墙上时间和实际执行时间脱钩。用 CLOCK_MONOTONIC 测出一段代码 20 ms，可能 18 ms 是 vCPU 被抢走了。
    区分方法：同时测 CLOCK_PROCESS_CPUTIME_ID（只算本进程真正占用的 CPU），两者差得多说明时间花在等待上。
    消除它只有一个办法
    不超卖 + vCPU pinning。但最该先做的是把 steal time 纳入监控——那不是优化，是让这类问题可归因，成本几乎为零。

8.2 中级

  1. 中级为什么虚机里 TLB miss 的代价特别高？

    因为要走两层页表。客户机以为自己在操作物理内存，但它的「物理地址」（GPA）还要经 EPT 再翻译一次才得到宿主物理地址（HPA）。

    算一下
    裸机一次四级页表走查是 4 次内存访问。虚机里，客户机页表的每一级都存在 GPA 里，每个 GPA 又要过一遍 EPT 的四级走查：(4+1)×4 = 20~24 次，约 6 倍。
    对策：两层都用大页
    客户机内用大页（收益和裸机一样）+ 宿主用 hugetlbfs 预分配客户机内存（让 EPT 那一层也用大页，把公式里第二个 4 降下来）。
    后者更重要，而且顺带消除了 EPT violation 的启动尖峰。
    预分配大页的附带好处
    它不会被换出、不会被 KSM 合并、不会触发 THP 的 khugepaged 整理——这三样都是延迟毛刺的来源。代价是这块内存被这台虚机独占，宿主不能再超卖。
    注意适用范围
    TLB 命中时这些全都不发生。所以对工作集小的负载完全无感，只有随机访问大内存的负载（数据库、大图、稀疏矩阵）才会真的感受到这 6 倍。
  2. 中级vhost 和 vhost-user 分别省掉了什么？

    用了 virtio 之后，剩下的主要开销是「从 KVM 退到 QEMU 用户态」那一跳——每处理一批数据都要走一次内核到用户态的往返。vhost 就是把后端搬走。

    vhost-net / vhost-scsi
    后端搬进宿主内核线程，省掉到 QEMU 的那次用户态往返。这是大多数生产虚机的默认选择。
    vhost-user
    后端搬到另一个用户态进程（通常是 DPDK 或 OVS-DPDK），整个宿主内核网络栈都跳过。适合 NFV 和高性能虚拟交换。
    vhost-user 的一个前提容易被忽略
    它需要客户机内存对后端进程可见，所以客户机内存必须共享（memory-backend-file,share=on，通常配 hugetlbfs）。
    这也意味着后端进程能读写整个客户机内存——它是信任边界上的组件，和 QEMU 同级，不是普通的用户态程序。
  3. 中级SR-IOV 性能最好，为什么不都用它？

    因为它换走的东西很实在，其中一条通常是决定性的。

    失去热迁移（通常是否决理由）
    虚机直接持有一个物理设备的状态，宿主不知道也复制不了。失去迁移意味着宿主打补丁要停机——对大规模运维来说这个代价往往超过性能收益。
    其它三项
    硬件相关：客户机装厂商驱动，换机型可能要换驱动；网络策略失效：流量不过宿主，安全组、流量镜像、QoS 都要挪到网卡硬件里做（如果它支持）；密度低：VF 数量由硬件决定，常见几十到上百个。
    加分：中间路线 vDPA
    硬件直接实现 virtio 的数据面（性能接近 SR-IOV），控制面仍由宿主软件管——于是热迁移又回来了，迁移时可以把数据面从硬件切回软件 virtio。
    这是一个典型的架构模式：把「快」和「可管理」拆到数据面和控制面两边。
  4. 中级虚机的内存超卖有哪几种手段？各自的代价？
    Ballooning
    客户机装气球驱动，宿主让它申请内存并归还。需要客户机配合，回收速度慢救不了突发，且客户机会以为自己内存变少了。
    KSM（同页合并）
    宿主扫描内存合并相同页为写时复制。代价：扫描耗 CPU、写入时触发 CoW 造成延迟毛刺、而且它是一条已知的侧信道——通过写入延迟能推断别的虚机有没有同样的页。
    Swap（最糟）
    宿主把客户机内存换出。客户机完全不知道，它以为自己在访问物理内存，一次访问从纳秒变成毫秒，而客户机内部所有的调度和超时判断都没考虑这种可能。
    为什么 swap 那条最难查
    客户机内部看不到任何异常：内存使用率正常、没有 swap、CPU 不高，只是所有操作莫名其妙地慢且毫无规律。只有在宿主侧看 vmstat 的 si/so 才能发现。
    「虚机很慢但客户机内部什么都看不出来」时，第一个要问的就是宿主内存有没有超卖。

8.3 高级

  1. 高级为什么给虚机加 vCPU 反而可能变慢？

    Lock Holder Preemption。客户机内核的自旋锁假设「持锁者正在另一个 CPU 上跑」，所以自旋等待是划算的。

    但在虚机里这个假设不成立
    持锁的那个 vCPU 可能根本没有被宿主调度——它在宿主的 runqueue 里排队。此时其它 vCPU 的自旋是纯粹的浪费，而且它们还占着宿主的 CPU，让持锁者更难被调度到——这是一个正反馈。vCPU 超卖时性能会断崖式下跌。
    缓解手段
    PLE（Pause-Loop Exiting）：自旋太久就 VM Exit，把 CPU 让给宿主去调度持锁者。准虚拟化自旋锁：客户机知道自己在虚机里，自旋一会儿就直接让出而不是死等。
    但最有效的还是不超卖
    vCPU pinning + 不超卖，从根上消除这个问题。这也是低延迟场景要独占物理核的原因之一。
    怎么确认是这个问题
    kvm_stat 里看 PLE 相关的退出次数；以及宿主的 vCPU 超卖比。症状很有辨识度：vCPU 数量增加而吞吐下降，且宿主 CPU 使用率很高但都是「自旋」。
  2. 高级在虚机上跑低延迟服务要做什么？

    默认配置下虚机的抖动比裸机大一个数量级。九条清单，前四条是一组：

    1–4：放弃超卖，换确定性
    ① vCPU pinning 不超卖（消除 steal time 和 Lock Holder Preemption）；② 宿主 isolcpus / cpuset 隔离这些核（消除邻居干扰）；③ 宿主 hugetlbfs 预分配内存（EPT 开销、启动尖峰、换出、KSM 毛刺一起解决）；④ 配 vNUMA 并与宿主拓扑一一对应。
    5–8：路径与时钟
    ⑤ 网络用 vhost 或 SR-IOV；⑥ 确认 clocksource 是 kvm-clock；⑦ 中断亲和性绑到 vCPU 所在的核；⑧ 调 halt_poll_ns（用一点 CPU 换唤醒延迟）。
    ④ 为什么关键：客户机会被骗
    默认配置下客户机看到一个平坦的单 NUMA 节点，而它的 vCPU 和内存实际散落在宿主两个 socket 上。
    最坏的不是「跨 socket 慢」，而是客户机以为内存是均匀的——于是所有 first-touch、绑核、本地分配的优化都建立在错误前提上，做了还不如不做，因为它会自信地把线程和内存放到错误的地方。
    做完之后该回头问一句
    1–4 本质上都是「放弃资源复用」。而虚拟化的核心卖点就是复用——做到最后这台虚机独占了它的核和内存，除了多一层 hypervisor 之外和裸金属没什么区别。
    此时要问：还留着虚拟化是为了什么？如果是热迁移、统一管理接口、快速重建，那划算；如果是「因为公司只有虚机」，那就该去争取裸金属。
  3. 高级Firecracker、Kata、gVisor 各解决什么问题？

    它们填的是同一个空档：需要虚机的隔离强度，但受不了它的启动时间和内存开销。典型场景是 FaaS——每次调用起一个沙箱，要百毫秒启动、几十 MB。

    Firecracker
    把 QEMU 换成一个只有几万行、只支持极少设备（virtio-net / virtio-block / 串口）的 VMM。启动 ~125 ms，内存开销 < 5 MB。做法是砍功能：不支持 PCI 热插拔、图形、BIOS。
    Kata Containers
    保持容器的接口（OCI、在 K8s 里像普通 Pod 一样用），但每个 Pod 跑在自己的轻量虚机里。换的是「容器的易用性 + 虚机的隔离」。
    gVisor（另一条路）
    不用硬件虚拟化，在用户态实现一个内核，拦截容器的系统调用。攻击面小了（不直接碰宿主内核），但系统调用密集的负载会明显变慢，且部分冷门系统调用不支持。
    归纳：在哪一层重新实现内核语义
    Firecracker / Kata 用真内核 + 精简 VMM（兼容性最好）；gVisor 在用户态重写内核（兼容性打折，但不依赖硬件虚拟化，嵌套虚拟化环境里也能用）。
    判据是兼容性要求：跑标准 Linux 负载选前两者，跑受控的、系统调用面窄的负载可以接受 gVisor 的开销。
  4. 高级一台虚机的网络吞吐上不去，怎么系统地排查？

    按数据路径从上到下走一遍，每一层都有明确的判据：

    ① 先确认用的是哪一档方案
    客户机里 lspci / ethtool -i eth0 看驱动名。如果是 e1000 之类的模拟设备，别的都不用查了——单包几十微秒，几万 pps 就是上限。换 virtio 能快 100 倍。
    ② 确认后端是不是 vhost
    宿主上看有没有 vhost-$pid 内核线程。没有的话数据要绕一次 QEMU 用户态。
    ③ 看 VM Exit 分布
    perf kvm stat live。如果退出次数和包数是同一个量级，说明批量化没生效（可能是队列太小，或者中断合并没配）。
    ④ 看中断与核的对应
    VF / vhost 的中断有没有绑到 vCPU 所在的核。没绑的话每个包都要跨核，对小包场景影响很大。
    ⑤ 最后才是「是不是被抢了」
    客户机 vmstat 的 st 列 + 宿主的超卖比。这一步放最后，是因为前四步的问题更常见、更容易确认、修起来收益也更大。
    排查顺序本身是有讲究的
    按「单项收益 × 确认成本」排序，不是按「从底层往上」排。①一条命令确认、修好快 100 倍，所以它必须第一个；⑤要跨宿主和客户机两侧看，且修起来涉及资源规划，所以放最后。
