内核崩溃分析

本站 崩溃调试指南讲的是用户态进程崩溃——有 core dump，有 GDB，可以慢慢看。这一篇讲内核崩溃：整机挂掉，没有 core，没有 GDB，进程连同它的调试器一起消失了。你手上只有一段抢救出来的 dmesg，或者一个几 GB 的 vmcore。本文要解决的是「怎么从这两样东西里把根因挖出来」。

01

内核出问题的几种形态

先分类，再取证——走错路会浪费一整天

「机器挂了」在内核视角下不是一件事，而是至少八种性质完全不同的事。它们的共同点只有一个：日志出现在 dmesg 里而不是应用日志里。它们的排查路径、取证手段、甚至「该不该去看代码」的答案都不一样。排障的第一步永远是分类——把一个 OOM 当成驱动 bug 去追，或者把一次 ECC 内存故障当成竞态去 review 代码，是最常见的时间浪费。

用户态崩溃像一个租户在自己屋里把杯子摔了：物业（内核）会给你留一份现场照片（core dump），你可以慢慢看，整栋楼照常运转。内核崩溃像大楼的承重结构出问题：没有第三方能替你拍照，因为「能拍照的那个人」也在这栋楼里。所以内核必须提前把相机和胶卷藏在一块谁也动不了的角落（这就是 kdump 预留内存），出事那一刻自己抢救自己。

用一句话区分：内核还能不能继续跑

这是所有分类的主轴。Oops 是「内核检测到了一个本不该发生的异常，杀掉肇事的那个上下文，然后试图继续跑」；panic 是「走不下去了，停机」。lockup / hung task / RCU stall 则完全是另一类：内核逻辑上没错，只是某个东西不动了，是检测器主动报出来的，本身不改变系统状态。OOM killer 更是「系统按设计正常工作」——它只是杀了个进程，属于容量问题而不是缺陷。

Oops：内核在自己的地址空间里踩到了不该踩的东西（最常见是解引用空指针或非法地址），CPU 抛出异常，内核的异常处理路径发现「这是内核态发生的、且没有 fixup 表项能救」，于是打印一份现场快照，把当前进程杀掉，然后返回主循环继续调度。名字来自那句无奈的 "Oops"——内核自己也知道这不该发生。
「Oops 之后系统还活着」是一种危险的错觉。被杀掉的那个上下文可能正持有自旋锁、正持有 mutex、正在改一个内核链表改到一半、刚从某个 slab 分配了对象还没登记。内核没有回滚机制，这些资源永远泄漏、这些锁永远不会被释放。所以一次 Oops 之后：后续访问同一子系统的任务会一个个卡死在 D 状态，几分钟后 hung task 报警，再过一会儿可能整机雪崩。Oops 之后的任何现象都不可信，只有第一次 Oops 的堆栈才是真相——这也是 [#1] 那个计数器存在的意义：[#2] [#3] 的堆栈通常是第一次的次生灾害，不要去追。

为什么 hard lockup 那条信息还能打印出来？这正是它的精妙之处：普通时钟中断已经进不去了（中断被关着），但 NMI（不可屏蔽中断）不受 cli 影响，硬件依然能把它送进 CPU。内核在 NMI 处理函数里发现「这个 CPU 的时钟中断计数已经很久没涨了」，于是在 NMI 上下文里把栈打出来。能看到 hard lockup 报告，说明 NMI 通路是好的；如果连这条都没有、机器直接静默复位，那多半是硬件看门狗或掉电，不是内核软件问题。

要不要自动重启：一组 sysctl 决定你能不能拿到现场

默认配置下，很多发行版不会在 Oops 时 panic，也不会在 panic 后重启——机器就那么静静地挂在那里，屏幕上一堆看不清的栈。这在服务器上通常是最糟糕的选择：既没有服务，也没有落盘的 vmcore。

参数含义生产建议
kernel.panicpanic 后等 N 秒自动重启；0 = 永远挂着不重启集群节点设 10~30；留几秒让 kdump 落盘和控制台输出刷完
kernel.panic_on_oopsOops 直接升级成 panic建议开（1）：Oops 后系统已不可信，与其带病运行不如立刻收现场
kernel.panic_on_warn连 WARN 都升级成 panic只在专门抓某个偶发 WARN 的调试期开，平时开了会天天重启
kernel.softlockup_panicsoft lockup 时 panic物理机可开；虚拟机慎开（宿主超卖会误报，见 §7）
kernel.hardlockup_panic / nmi_watchdog=panichard lockup 时 panic建议开——hard lockup 基本没有自愈可能
kernel.hung_task_panichung task 时 panic默认关。存储抖动一次就 panic 太激进，只在追死锁时临时开
kernel.panic_on_rcu_stallRCU stall 时 panic默认关；追 stall 根因时临时开，能拿到「卡住那一刻」的现场
vm.panic_on_oomOOM 时 panic 而不是杀进程几乎不用。OOM 是容量问题，panic 只会把局部故障放大成整机故障

$ sysctl kernel.panic kernel.panic_on_oops kernel.softlockup_panic
kernel.panic = 0
kernel.panic_on_oops = 1
kernel.softlockup_panic = 0

# 典型的服务器崩溃取证配置
$ cat /etc/sysctl.d/99-crash.conf
kernel.panic = 20            # panic 后 20 秒重启，别永远挂着
kernel.panic_on_oops = 1     # Oops 即 panic，立刻收现场
kernel.hardlockup_panic = 1
kernel.sysrq = 1             # 允许 magic SysRq（见 §6）
面试加分点：被问「panic_on_oops 该不该开」时，标准答案不是「开」或「不开」，而是取决于这台机器有没有冗余。集群里的一个节点、K8s 的一个 worker——立刻 panic 收 vmcore 是对的，反正流量会飘走，而带病运行的节点会返回错误结果污染上游。反过来，单点的工控设备、车载 ECU、机房里唯一那台采集机——panic 意味着业务中断，宁可保住 WARN 后的降级运行，靠外部硬件看门狗兜底。「拿现场」和「保可用」是真实的取舍，能说清这一层就说明真做过决策而不是背参数。
这一篇讲的是「已经出事之后怎么办」。事故的组织流程侧（谁来定责、怎么止血、复盘怎么写）在 故障处理手册；崩溃发生在你自己写的驱动里时，代码侧的规范见 Linux 设备驱动。

第一段：出了什么事、在哪个地址

address: 0000...0000 / CR2
x86 上 CR2 寄存器保存触发缺页的那个线性地址，第一行的 address: 就是它。这是整份 Oops 里最有用的一个数字：接近 0 的小地址 = 空指针解引用；而且那个小偏移往往就是结构体成员的偏移——0x8 表示访问了某结构体第 8 字节处的字段，0x18 表示第 0x18 字节处。配合 pahole 打印该结构体的布局，常常一眼就知道是哪个成员。
#PF: error_code(0x0002)
缺页错误码的位域：bit0 = 页是否存在（0=不存在），bit1 = 读还是写（1=写），bit2 = 用户态还是内核态（0=内核），bit3 = 保留位违规，bit4 = 取指。所以 0x0002 = 「内核态、写、页不存在」。现代内核会把它翻译成人话直接打在下一行（supervisor write access in kernel mode），不用自己算，但知道位含义有助于看老内核的日志。
Oops: 0002 [#1]
前面那个 0002 就是同一个错误码。[#1] 是本次启动以来的第几次 Oops。如果你看到 [#3]，说明前面还有两次，去日志里往上翻找 [#1]——第一次才是真凶，后面的通常是第一次留下的烂摊子引发的次生崩溃。SMP PTI 是内核配置标记（多处理器、开启了页表隔离）。

第二段：RIP —— 全场最关键的一行

RIP: 0010:mydev_write+0x2a/0x60 [mydev] 的读法：0010 是代码段选择子（内核态固定值，没有信息量，忽略）；mydev_write 是出错指令所在的函数；+0x2a 是出错指令相对函数入口的字节偏移；/0x60 是这个函数的总字节长度；[mydev] 表示这个函数来自名为 mydev 的可加载模块，没有方括号则来自内核本体（vmlinux）。
+0x2a/0x60 这种「偏移/长度」格式不是内核在卖弄，而是为了对抗 KASLR。开启地址随机化后，每次启动 mydev_write 的绝对地址都不一样，把绝对地址贴到 bug 报告里对别人毫无用处；而「函数名 + 函数内偏移」在同一份编译产物里是永远稳定的。同时 /0x60 这个总长度还是个校验：如果你手上的 .ko 里 mydev_write 长度不是 0x60，说明你拿错了版本，别浪费时间往下查。

Code: 那一行是 RIP 附近的原始机器码字节，其中被尖括号包住的那个字节（<c7>）就是出错指令的第一个字节。当你手头没有匹配的 .ko 时，这行是最后的救命稻草——内核源码树里的 scripts/decodecode 可以把它反汇编出来：

$ echo 'Code: 0f 1f 44 00 00 55 48 89 e5 41 54 49 89 fc 48 8b 47 18 48 85 c0 74 08 <c7> 00 2a 00' \

结合寄存器转储里的 RAX: 0000000000000000——结论已经完整了：从某结构体偏移 0x18 处取出的指针是 NULL，代码却直接往它指向的位置写了个值。剩下的只是去源码里找那个 0x18 是哪个字段。

第三段：Call Trace 与那些 ?

Call Trace 里的 ? 前缀：表示这一帧不可靠。x86_64 内核通常不保留帧指针（-fomit-frame-pointer），栈回溯靠 ORC 元数据推导；推导不出来的部分，内核会退化成「扫描栈内存，凡是看起来像内核代码地址的值都列出来」。这些值可能是之前某次调用留在栈上的残渣，跟当前调用链毫无关系。带 ? 的帧仅供参考，不带 ? 的才是可信调用链。
带 ? 的栈帧像白板上没擦干净的旧字迹：这块白板（内核栈）反复被不同的人用过，新写的内容只覆盖了一部分，残留的旧笔画混在里面。有经验的人一眼能分辨哪些是这次会议写的、哪些是上次留下的；没经验的人会把上次的结论当成这次的。

上面那段栈读下来就是：用户进程 cat 调 write(2) → entry_SYSCALL_64 → do_syscall_64 → ksys_write → vfs_write → 通过 file_operations 表调到了 mydev_write。注意 mydev_write 本身不在 Call Trace 里，它在 RIP 那一行——Call Trace 列的是「谁调用了当前函数」，当前函数在 RIP。这是初学者最常见的误读。

第四段：Tainted —— 决定社区理不理你

Taint（污染）标记：内核用一串字母记录「这个内核在崩溃之前已经处于什么非标准状态」。它的用途是快速判断这份报告值不值得信——如果内核里塞了闭源驱动、或者之前已经崩过一次，那么这次崩溃的现场很可能不是内核自己的问题。Tainted: G OE 中每个位置对应一个固定的标记位，G 在第一位表示「没有专有模块」，后面的空格表示该位未置位。
字母含义对排障的影响
G / PG = 所有已加载模块都声明了 GPL 兼容许可；P = 加载了专有（proprietary）模块P 基本等于社区不受理——闭源模块的代码没人能看，NVIDIA、某些 RAID 卡驱动会置这个位
O加载了 out-of-tree（树外）模块，即不在内核源码树里的模块你自己写的驱动、DKMS 编出来的模块都会置 O。社区看到 O 的第一反应是「先卸掉你的模块再复现一次」
E加载了未签名模块（unsigned module）说明关闭了模块签名校验或用了自签。安全相关，本身不代表 bug
D本次启动以来已经发生过 Oops / BUG（die）极其重要：看到 D 就意味着眼前这份不是第一现场，往前翻日志找 [#1]
W之前触发过 WARN_ON()同上，往前翻，那条 WARN 常常就是根因的早期信号
F / R模块被强制加载（insmod -f）/ 强制卸载强制加载意味着版本魔数不匹配也硬上，任何崩溃都不奇怪
M / B发生过机器检查异常（MCE） / 检测到坏页硬件信号。看到这两个先去查内存和 CPU，别追代码（见 §5）
C加载了 staging 驱动（内核里尚未成熟的孵化区）staging 驱动质量本就不保证，优先怀疑它
L之前发生过 soft lockup说明系统之前就有 CPU 卡顿史
K内核被 live patch 过运行中的代码和你手上的 vmlinux 不完全一致，符号偏移可能对不上
为什么社区看到 O 就不太接 bug？不是傲慢，是成本问题。树外模块可以做任何事：改内核数据结构、用未导出的内部接口、假设了某个已经变了的行为。当 Oops 的 RIP 落在内核本体的某个函数里、而 Tainted 有 O 时，最常见的真相是你的模块把内核的数据结构写坏了，内核只是在后来的某个时刻踩到了坏数据。维护者没有你的代码，无从判断。所以给上游报 bug 之前的标准动作是：卸载所有树外模块（或者干脆用发行版原装内核）复现一次；能在纯净内核上复现，报告才有价值。

decode_stacktrace.sh源码树 + vmlinux + 模块目录一次把整段 Call Trace 翻成文件:行号，报 bug 时贴这个路径参数容易配错，模块要单独指目录

03

kdump / kexec 机制

怎么在内核已经死掉的机器上，把内核的尸体拍下来

§2 那段 Oops 是幸运情况：控制台还能打印，日志还能进 journald。真实生产里更常见的是——机器直接重启了，dmesg 里干干净净什么都没有，因为重启把内存清了，环形缓冲区里的日志一起没了。要拿到现场，必须在「崩溃」和「重启」之间插进一个步骤。这就是 kdump。

kexec：一个能让正在运行的内核直接跳进另一个内核的机制，跳过固件（BIOS/UEFI）和引导加载器的整个自检与初始化流程。本来是为了加快服务器重启（省掉几十秒的 POST）而设计的。kdump 则是它的一个特化用法：预先把一个「捕获内核」加载进内存待命，等第一个内核 panic 的时候用 kexec 跳过去，让捕获内核把第一个内核残留在内存里的一切写成一个文件。
正常重启像火灾后先把楼推平再重建：现场什么都不剩，事后只能靠幸存者回忆（也就是那几行来不及刷出去的日志）。kdump 像在楼里预留了一间独立的消防指挥室：这间房日常锁着不让任何人用（预留内存），出事时消防队从这间房直接接管（kexec 跳进捕获内核），全楼断电但建筑结构原封不动（第一内核的内存不被清），指挥队从容地把整栋楼扫描一遍拍成档案（vmcore），然后才允许推倒重建。

为什么这样能拿到现场

关键在于两点，缺一不可：

① 捕获内核跑在一块「别人从来没碰过」的内存里
开机时通过 crashkernel= 参数从物理内存里划走一块，生产内核从此看不见这块内存（free 里的总量会少掉这么多）。捕获内核只在这块内存里活动，因此它的运行不会覆盖第一内核的任何一个字节。这也是为什么预留必须提前在启动时做——运行时再想找一块「肯定没人用」的连续物理内存，做不到。
② kexec 不走固件，内存不被清
正常重启会经过固件复位流程，很多平台会做内存训练、清零或至少让 DRAM 掉电刷新中断——现场就没了。kexec 是纯软件跳转：设置好新内核的入口、页表和参数，然后直接 jmp 过去，DRAM 从头到尾一直在正常刷新。第一内核的每一个数据结构、每一个 task_struct、每一段 printk 环形缓冲，全都完整地躺在那里等着被读。

配置实操

三件事：预留内存、装好服务、验证能落盘。第三步最容易被跳过，也最容易在真出事时发现根本没生效。

# ── ① 预留内存：改内核命令行 ─────────────────────────────
# 固定大小（最直白）
crashkernel=512M

# 按总内存分档（推荐：一份配置适配不同规格的机器）
# 语法 起始-结束:大小，可以串多段；"1T-" 表示 1T 以上
crashkernel=2G-64G:256M,64G-1T:512M,1T-:1G

# x86_64 大内存机器：预留区可以放到 4G 以上，另外在 4G 以下留一小块给需要低端 DMA 的设备

# 改完 GRUB 后必须重启才生效（预留只能在启动早期做）

$ dmesg | grep -i 'crashkernel\|Reserving'
[    0.000000] Reserving 512MB of memory at 3072MB for crashkernel
/sys/kernel/kexec_crash_size 为 0 是最常见的「以为配了其实没配」。典型原因：① 内存碎片化导致内核找不到一块足够大的连续物理区域（尤其在没写 ,high 的大内存机上）；② 改了 /etc/default/grub 但没重新生成 grub.cfg；③ 用了云厂商镜像，内核命令行由 metadata 覆盖。这个值必须非零，并且和你写的数字一致，才算配好了第一步。

makedumpfile 的 dump level：为什么几百 GB 能压成几 GB

一台 512 GB 内存的机器，原样 dump 就是 512 GB 的文件——写盘要几十分钟，存储放不下，传输更别想。makedumpfile 的核心工作是「按页类型裁剪」：绝大多数物理页对排查内核崩溃毫无价值，直接扔掉。

bit值裁掉的页类型丢了会影响什么
01全零页什么都不影响，无脑开
12非私有的 page cache（干净的文件缓存）看不到「某个文件当时被缓存的内容」，排查内核崩溃基本用不上
24私有的 page cache同上
38用户进程的数据页看不到用户态内存内容与用户栈；顺带解决了大半的脱敏问题（见 §8）
416空闲页（在 buddy 空闲链表上的）看不到「刚被释放的对象里还残留什么」——追 UAF 时偶尔会想要，但代价太大
—31以上全部（1+2+4+8+16）生产默认值。保留的是内核代码、内核数据、slab、页表、task 结构——排查内核问题需要的全在这里
 
# 常用组合：-d 31 裁页 + -l/-c/-p 压缩，通常能把 512G 压到个位数 GB
$ makedumpfile -l --message-level 1 -d 31 /proc/vmcore /var/crash/vmcore

#   -d 31   裁掉零页 / page cache / 用户页 / 空闲页
#   -c      zlib 压缩（压缩率高，CPU 慢）
#   -l      lzo  压缩（速度快，压缩率中等，常用默认）
#   -p      snappy 压缩（最快）
#   -F      输出到 stdout（配合 ssh 落远端时用）
#   -d 1    只裁零页 —— 追 UAF、想看已释放对象残留时用，但文件会大很多

# 事后还能对已有的 vmcore 再裁一遍（比如为了脱敏后外发）
$ makedumpfile -d 31 -c vmcore vmcore.stripped

# 看一个 vmcore 的头部信息（版本、页数、是否压缩）
$ makedumpfile --dump-dmesg /var/crash/.../vmcore dmesg.txt   # 只把内核日志抠出来，秒级
makedumpfile --dump-dmesg 是被严重低估的一条命令。vmcore 有 8 GB、crash 工具还要装匹配的 debuginfo，但你现在只想知道「崩之前最后打印了什么」——这条命令几秒钟就能把崩溃瞬间的完整内核日志抠成一个文本文件，不需要任何调试符号。很多事故到这一步就已经破案了（比如日志里明明白白写着某个磁盘 IO error 刷屏），根本用不着开 crash。拿到 vmcore 的第一件事就该是它。

生产陷阱

预留内存不够 → 捕获内核自己挂
捕获内核要跑一个 initramfs，里面有存储驱动、网络驱动（落 NFS/ssh 时）、makedumpfile。预留不够时它会在启动过程中 OOM 或 panic，而这次 panic 是没人接的——机器直接重启，你什么都拿不到，而且现象和「kdump 根本没开」一模一样。经验值：256 MB 是下限，带复杂存储栈或要走网络落盘的建议 512 MB 起，超大内存机器（TB 级）因为 makedumpfile 要维护页位图，需求还会再涨。
Secure Boot 下 kexec 受限
开启 Secure Boot 后，内核不允许加载未经签名的镜像——kexec_load 这个老系统调用会被直接拒绝（lockdown 机制）。必须改用 kexec_file_load（kexec -s），由内核自己校验镜像签名。发行版的 kdump 服务通常已经处理好了，但自编内核 + Secure Boot 的组合几乎必然踩坑：你的内核没有厂商签名，捕获内核加载不上。要么给自己的内核签名并把证书注册进 MOK，要么在这类机器上接受「只能靠串口日志」。
内存太大导致 dump 超时
几 TB 内存的机器即便裁到 -d 31，vmcore 仍可能有几十 GB，写盘几十分钟。这段时间机器完全不提供服务，而且很多监控/云平台会因为「节点长时间无心跳」触发自动重装或强制重启，把 dump 打断。对策：用更快的压缩（-p snappy）、落到本地 NVMe 而不是网络、把自动化平台的失联超时调长，或者在超大内存机上干脆放弃全量 dump，改成只保留 vmcore-dmesg.txt。
预留内存是永久成本
那 512 MB 从开机起就不可用，free -m 里直接少掉。在几百 GB 的机器上无所谓，在 2 GB 内存的嵌入式设备上就是 25%——这类设备通常不上 kdump，改用持久化的 pstore（把 panic 日志写进 UEFI 变量区、ACPI ERST 或一块专门的 RAM 区），重启后从 /sys/fs/pstore/ 读回来。拿不到完整内存镜像，但至少保住了最后那几 KB 的日志。

crash 工具实战

把 vmcore 当成一个「冻结的内核」来 debug

crash：内核崩溃分析的标准工具，本质是一个把 gdb 包在里面、并且懂内核数据结构的解释器。它读入 vmcore（内存快照）加上 vmlinux（符号与类型信息），把整个内核的状态还原出来——所有进程、所有 CPU 的栈、slab 分配情况、网络连接、文件表，都能像在活系统上一样查询。关键区别是它只读、且时间是冻结的：你看到的永远是崩溃那一瞬间的样子。
crash 像法医的解剖台。GDB 是给活人做体检——能让病人抬手、能问「现在哪里疼」（下断点、单步、改变量）。crash 面对的是一具尸体：什么都问不了，只能看。但正因为一切都静止了，你可以从容地把每一个器官（进程、锁、内存池）逐一翻查，而且不用担心状态在你眼皮底下变化——这在调试并发问题时反而是巨大的优势。

打开一个 vmcore 需要什么

两样东西，缺一不可：vmcore 本身，和版本严格匹配、带调试符号的 vmlinux。后者就是绝大多数人卡住的地方。

为什么空指针在内核里比在用户态危险得多。用户态解引用 NULL 只是 SIGSEGV，操作系统兜底。内核态没有兜底：一次空指针写就是一次 Oops，而 Oops 之后锁和资源的状态是不确定的（见 §1）。更麻烦的是写类型的空指针——如果偏移足够大（比如访问 ptr->field 而 field 在很深的位置），落到的地址可能已经不是「零页」而是某块真实存在的内存，那就不会 Oops，而是静默地把别人的数据改了，几分钟后在完全不相干的地方崩掉。这也是为什么内核会保留低地址不可映射（mmap_min_addr）——尽量让空指针早点、响亮地崩。

② UAF 与 slab poison：认毒值

Slab poison（毒化）：开启调试后，内核在对象被释放时用固定字节填满它，在分配时用另一个固定字节填未初始化区域。这样一来，一旦有人访问已释放的对象，读到的就是这些扎眼的固定模式而不是随机垃圾——把「静默的数据损坏」变成「一眼能认出的证据」。
毒化像退房后酒店在房间里铺满荧光标记的床单。正常情况下没人会看见它们；但如果某个客人拿着过期房卡溜回来，他身上会沾满荧光粉——你不需要看监控，只要看到荧光就知道有人用了不该用的房间。0x6b（ASCII 的 k，取 "kfree"）就是这层荧光粉。
看到的值含义指向的问题
0x6b6b6b6b6b6b6b6b（字节 0x6b，最后一字节常为 0xa5）已释放对象的填充（POISON_FREE / POISON_END）use-after-free：对象已 kfree，代码还在读它的字段
0x5a5a5a5a5a5a5a5a（字节 0x5a）刚分配、尚未初始化的区域（POISON_INUSE）忘了初始化就用；或越界读到了对象的 padding
0xbb / 0xcc 填充的红区SLUB 在对象前后加的 red zone红区被改写 = 缓冲区越界（写越了对象边界）
0xdead000000000100 / 0xdead000000000122list_del 之后写进 next/prev 的链表毒值重复 list_del，或使用了已摘链的节点
0x10 这样的极小非零值ZERO_SIZE_PTR：kmalloc(0) 的返回值长度计算成了 0，却当正常指针用了

③ 内核栈溢出：只有十几 KB，不是几 MB

内核栈：每个内核线程（以及每个进入内核态的用户线程）都有一个独立的内核栈，x86_64 上常见大小是 16 KB（4 个 4 KB 页），很多 32 位平台是 8 KB。这个值在编译时由 THREAD_SIZE 决定，运行时不可增长——它和用户态那个默认 8 MB、还能自动扩展的栈完全不是一回事。
为什么内核栈这么小？因为它是按线程数量线性乘出来的常驻开销：一台机器上万个任务，每个 16 KB 就是 160 MB 物理内存，而且这些页必须常驻、不能换出（换出的话缺页处理本身又需要栈，会死循环）。同时内核栈需要是物理连续的（在 CONFIG_VMAP_STACK 之前），大块连续内存本身就稀缺。所以「小」不是疏忽，是必须付出的设计代价——代价转嫁给了内核开发者：不许递归，不许在栈上放大数组。

④ 原子上下文里睡眠

原子上下文：不允许被调度出去的执行环境——持有自旋锁期间、关中断期间、软中断/硬中断处理函数里、RCU 读侧临界区里。在这些地方调用任何可能睡眠的函数（mutex_lock、msleep、copy_to_user、kmalloc(GFP_KERNEL)）都是严重错误：调度器会试图切走当前任务，而这个任务手里攥着别人正在自旋等待的锁——轻则性能崩溃，重则整机死锁。

不崩溃时的内核调试手段

大多数内核问题不会好心地给你一个 vmcore

vmcore 的边界前面说过：它有结果，没有过程。而现实中更多的情况是「没崩，但不对」——驱动偶尔丢一帧、某个 ioctl 返回了 -EINVAL 但不知道走的哪个分支、某个路径明明不该被调用却被调用了。这时候你需要的是观测，不是尸检。

printk / dmesg

最原始也最可靠。代价是要重编模块或重启，而且高频调用会淹没日志、拖慢系统。适合固定的关键路径。

dynamic_debug

把 pr_debug 变成运行时可按文件/函数/行开关的日志。不重编、不重启，随开随关。驱动调试的首选。

ftrace / bpftrace

不改一行代码就能追任意内核函数的调用、参数、返回值、耗时。开销可控，能上生产。探索未知路径时最强。

printk 的日志级别与 dmesg 的正确用法

内核日志有 8 个级别（0 最紧急，7 最啰嗦）。级别不只是分类，它直接决定「这条消息会不会打到物理控制台」——这一点在串口调试时至关重要，因为往串口打日志是同步的、极慢的，级别设错能让一台机器慢到不可用。

级别宏语义什么时候该用
0pr_emerg系统不可用panic 前的最后一句
1pr_alert必须立即处理数据结构损坏这类
2pr_crit严重错误硬件失效、关键路径失败
3pr_err错误驱动里报错的默认选择
4pr_warn警告可恢复的异常、降级
5pr_notice值得注意的正常事件设备上下线
6pr_info一般信息模块加载、参数打印
7pr_debug调试默认不输出，由 dynamic_debug 控制

dmesg -T 的时间戳不能全信。内核环形缓冲里存的是单调时钟的相对秒数；-T 是用「当前墙上时间 − 当前单调时间」反推出来的。所以只要机器挂起过（suspend）、调过系统时钟、或者 NTP 做过大幅校正，换算出来的绝对时间就是错的，误差可能达到小时级。跨机器对时间线时，用 journalctl -k（journald 记录的是真实墙钟）更可靠；或者干脆用相对时间戳自己算差值。

dynamic_debug：不重编内核就能开关 pr_debug

dynamic_debug（CONFIG_DYNAMIC_DEBUG）：内核把每一条 pr_debug / dev_dbg 的位置（模块、文件、函数、行号、格式串）都登记在一张表里，运行时可以按任意维度精确开关。未开启的调试语句用 static key 实现，关闭状态下的运行时开销接近零——所以发行版内核可以放心地把成千上万条 pr_debug 全部编进去。
dynamic_debug 像整栋楼预先布好了线的射灯：灯全装好了但都关着，不费电；你想看哪个房间，在总控面板上按一下就亮。传统做法（改代码加 printk 再重编）相当于每次想照亮一个角落就要重新拉一次电线——而在内核里「重新拉线」意味着重编模块、卸载重载，很多时候现场根本不允许。

hung task detector：为什么只看 D 状态

khungtaskd 是一个普通的内核线程，周期性地遍历全部任务，做一件很朴素的事：「这个任务处在 TASK_UNINTERRUPTIBLE（D）状态，而且它的自愿+非自愿上下文切换总数和我上次看时一模一样——说明它这段时间一次都没被调度过，纯粹在睡。」连续这样超过阈值，就打印它的栈。

为什么 S（TASK_INTERRUPTIBLE，可中断睡眠）不算：S 状态是「正常等待」的常态——一个 sshd 等新连接可以等三个月，一个 epoll_wait 空转的服务器进程一天里 99.99% 的时间都在 S。把 S 纳入检测，等于给每台机器每两分钟刷屏几百条误报。而 D 状态的语义完全不同：它表示「正在等待一个不可被信号打断的事件」，通常是块设备 IO、页面回写、某些内核互斥锁。这类等待按设计就应该在毫秒到秒级返回——等满两分钟只有两种可能：底层设备真的挂了，或者出现了死锁。两种都值得报警。
这就像公司里区分「在会议室开会」和「在洗手间反锁了两小时」。前者（S 状态）你不会去敲门——人家本来就该在那待着，待多久都正常。后者（D 状态）你一定会去敲门，因为那个隔间设计上就不该被占用两小时，要么里面的人出事了，要么门锁坏了。hung task detector 就是那个负责去敲门的人。

soft / hard lockup detector：一对互补的看门狗

这两者共用一套基础设施，但检测的层次完全不同。理解它们的关键是问一句：「报警本身是怎么被打印出来的？」

soft lockup —— 中断还活着
每个 CPU 上有一个高精度定时器周期性触发（周期约为 watchdog_thresh/5，默认下是几秒一次），它的工作是检查该 CPU 上的 watchdog 内核线程有没有被调度到并更新时间戳。如果超过 2×watchdog_thresh（默认约 20 余秒）还没更新，说明这个 CPU 一直在跑某段不让出的代码。注意定时器中断本身是能进来的——所以这个 CPU 只是「不调度」，不是「完全失联」，报警可以在中断上下文里正常打印出来。典型元凶：内核态 while 死循环、遍历一个成环的链表、在关抢占的临界区里干太久。
hard lockup —— 连中断都进不来
如果连时钟中断都被挡在门外（local_irq_disable() 之后死循环、或者自旋锁死锁在关中断的临界区里），上面那套基于 hrtimer 的机制整个失效——定时器根本不会触发。于是内核祭出NMI：不可屏蔽中断不受 cli 影响，硬件强行把它送进 CPU。NMI 处理函数检查「这个 CPU 的普通时钟中断计数是不是很久没涨了」，是则判定 hard lockup 并在 NMI 上下文里打栈。x86 上 NMI 通常由 PMU 性能计数器产生；虚拟机里没有虚拟 PMU 时这套机制会直接不可用（dmesg 里会有 perf event 创建失败的提示），新一些的内核提供了「CPU 之间互相检查」的 buddy 方案作为替代。

RCU stall

RCU 静止态（quiescent state）：RCU 的核心假设是「只要每个 CPU 都经历过一次上下文切换 / 进入过用户态 / 进过 idle，那么此前所有的 RCU 读侧临界区都已经结束了」。这些时刻就叫静止态。所有 CPU 都报告过静止态，一个宽限期（grace period）才算结束，被延迟释放的内存才能真正回收。如果某个 CPU 长时间一次静止态都没有——它在内核态死循环、长时间关抢占、或者关着中断——宽限期就永远结束不了，待释放的内存不断堆积，最终可能拖垮整个系统。RCU stall detector 就是来报这件事的。

虚拟机上的误报：这是最常被问、也最容易搞错的一点

物理机上的 watchdog 像老板每隔 20 秒来工位看一眼：人不在就记一笔。虚拟机上的 vCPU 则像一个被派去别处开会的员工——他不是在偷懒，是被更高一层的调度者（宿主机）整个人调走了 20 秒。可这位老板（guest 内核）看不见宿主机那一层，它只知道「工位空了 20 秒」，于是照样记一笔 soft lockup。问题从来不在这个员工身上。
误报的机制
宿主机 CPU 超卖时，guest 的 vCPU 只是宿主上的一个普通线程，随时可能被抢占几十毫秒甚至几秒。在 guest 内核看来，「时间凭空跳了过去」和「某个 CPU 卡了这么久」是完全无法区分的两件事。此外，存储抖动（虚拟磁盘后端阻塞）会让整个 vCPU 卡在 IO 上，热迁移（live migration）的最后停机阶段更是会让整台 guest 暂停数百毫秒到数秒。
内核已有的缓解
KVM 提供了 steal time 和「宿主曾暂停过本 guest」的标志位，guest 内核在报 lockup 之前会检查这个标志，若发现刚被宿主暂停过则跳过这次报警。这能挡掉大部分热迁移和明显暂停导致的误报，但挡不住「持续性的中度超卖」——每次只被抢 3 秒、连续抢 7 次，标志位不一定被置上，累计却超过了阈值。
怎么判断是不是误报
先看 steal time。top / vmstat 1 里的 st 列、/proc/stat 的第 8 个字段，如果明显非零（持续 > 5%~10%），基本可以确定是宿主争抢而不是 guest 内的问题。再看栈：真实的 soft lockup 会稳定地卡在同一个内核函数上（那个死循环）；误报的栈往往每次都不一样，甚至栈顶是 native_safe_halt（本来在 idle）这种荒谬的位置。「栈没有形状」= 误报，这和 §5 里判断硬件问题的逻辑是一样的。

kernel.softlockup_panic = 0        # ★ 绝对不要在超卖的虚拟机上开这个
kernel.hardlockup_panic = 1        # hard lockup 极少误报，可以保留
# 同时把 steal time 纳入监控告警 —— 它才是这类问题的真实指标

panic 收现场 vs 仅告警：怎么选

场景建议理由
集群里的一台无状态 worker（K8s 节点、Web 前端）倾向 panic：panic_on_oops=1 + hardlockup_panic=1有冗余，流量会飘走。带病节点返回错误结果的危害大于短暂少一台机器
数据库主节点 / 有状态服务谨慎：先确认有可靠的自动切主，再开 panicpanic 会触发切主，切主本身有风险；但带着损坏的内核状态继续写数据更危险
CPU 超卖的虚拟机 / 云主机关 softlockup_panic，保留 hard lockupsoft lockup 误报率高，开了会变成随机重启
单点工控机 / 车载 / 医疗设备不 panic，靠 WARN + 外部硬件看门狗停机就是事故。用外部看门狗兜底「真死机」，软件层尽量维持降级运行
正在追某个偶发问题的调试期全开：panic_on_warn、hung_task_panic、panic_on_rcu_stall目标是拿到第一现场。调试期就该激进，但记得事后关掉
这个取舍的本质是「现场的价值」对比「可用性的代价」。有冗余时，现场几乎是免费的（流量飘走，用户无感），那就该拿。没有冗余时，现场的价格是一次真实的业务中断——这时候更划算的做法是降低对现场的依赖：把 dynamic_debug 和 ftrace 常态化埋点、把 pstore 配好（至少保住最后几 KB 日志）、在测试环境用 KASAN 提前发现问题。「拿不到 vmcore」不等于「查不出来」，只是需要在事前多花功夫。

生产落地

从「偶尔手工看一次」到「每次重启都可归因」

前面七章讲的是一个人在一台机器上怎么查。规模上去之后问题变了：一千台机器，上个月有 17 次非计划重启，其中几次是内核崩溃？分别是什么原因？有没有重复的？——如果这些问题回答不了，那么单机排障技能再强也只是在救火。

vmcore 自动收集与归档流水线

kdump 只负责把 vmcore 写到本地磁盘。剩下的事情必须自动化，因为「机器重启后有人记得去 /var/crash 看一眼」这件事在生产上不会发生。

# 开机时检查是否有新的 vmcore，有就打包上传并告警
# /etc/systemd/system/vmcore-upload.service
[Unit]
Description=Upload kdump vmcore if present
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/vmcore-upload.sh

[Install]
WantedBy=multi-user.target

# vmcore-upload.sh 至少要收集这些东西 —— 光有 vmcore 是不够的
#   vmcore                     内存镜像
#   vmcore-dmesg.txt           崩溃瞬间的内核日志（先看这个）
#   uname -a / /proc/cmdline   内核版本与启动参数
#   包版本清单（rpm -qa / dpkg -l）与自研模块的 build id
#   lspci -nnk / dmidecode     硬件与固件版本
#   journalctl -k -b -1        上一次启动的完整内核日志
#   /sys/kernel/kexec_crash_size / _loaded  证明 kdump 当时是生效的

# 上传后本地保留策略：至少留一份最近的，磁盘满了先删旧的
# 千万别让 /var/crash 把根分区撑满 —— 那会导致下一次崩溃根本落不了盘
最讽刺的失败模式：/var/crash 把磁盘写满，导致后续所有崩溃都没有 vmcore。一个 vmcore 动辄几个 GB，连续崩三次就能填满一块小系统盘。必须配保留策略（/etc/kdump.conf 里可以设，或者用 systemd-tmpfiles / 上传脚本自己管），并且把 /var/crash 的剩余空间纳入监控。同理，落 NFS 时要考虑「一百台机器同时崩溃同时往一个 NFS 写几 GB」的场景。

体积与脱敏：vmcore 里有什么不能外传的东西

vmcore 是一份完整的内存镜像——它包含崩溃那一刻内存里的一切。用户的明文密码（刚从 HTTP 请求里解出来还没清零的缓冲区）、TLS 会话密钥、数据库连接串、用户的业务数据、page cache 里缓存的文件内容。把 vmcore 发给硬件厂商、上传到公有云工单系统、或者放进一个全公司可读的对象存储桶，都是实打实的数据泄露。
措施做法代价
裁掉用户页makedumpfile -d 31（bit 3 就是用户数据页，bit 1/2 是 page cache）看不到用户态内存和被缓存的文件内容；排查内核问题基本不受影响
限制访问vmcore 目录 0600；归档存储按团队做 ACL；下载留审计日志流程成本
传输加密落远端走 ssh 而不是 NFS 明文；对象存储开服务端加密捕获内核里要配密钥，增加 initramfs 复杂度
外发前评审给厂商/上游之前走一次数据合规审批，能只发 vmcore-dmesg.txt 就别发全量响应变慢；但这是必要的
能不发就不发先自己 crash 分析，把结论 + 脱敏后的栈发过去需要本方有分析能力——这正是学这一章的意义
-d 31 是一个「性能优化顺便解决了合规问题」的经典例子。它最初的目的是压缩体积（几百 GB → 几 GB），但因为裁掉的正好是用户数据页和 page cache，它同时把绝大部分敏感数据挡在了外面。反过来提醒一件事：如果你为了追某个用户态相关的问题把 dump level 调低（比如 -d 1 只裁零页），那份 vmcore 的敏感级别就完全不同了，不能按常规流程流转。

调试符号管理：崩溃发生时才找 vmlinux 就晚了

这是自研内核 / 自研驱动团队最常见的翻车点：三个月前发布的版本崩了，而当时的 vmlinux 谁也找不到了。vmcore 拿在手里却打不开，等于没有。

符号管理的四条硬规矩

  • CI 必须归档未 strip 的 vmlinux 和所有 .ko，和二进制版本号（或 build id）一一绑定，保留期 ≥ 你的最长支持周期。/boot/vmlinuz-* 是压缩过的引导镜像，不能拿来给 crash 用。
  • 用 build id 而不是版本号做主键：readelf -n vmlinux | grep 'Build ID'。版本号会重复（同一个版本重编一次符号就变了），build id 不会。
  • 部署 debuginfod：设置 DEBUGINFOD_URLS 后，gdb、crash、perf 能按 build id 自动拉取匹配的调试信息，彻底告别「翻遍制品库找符号」。发行版通常也有公共 debuginfod 服务。
  • 把符号可用性纳入发布检查项：发版时顺手验证一次「用归档的 vmlinux 能不能打开一个测试 vmcore」，比事故当天才发现强得多。
# build id 是符号与二进制配对的唯一可靠依据
$ readelf -n vmlinux | grep -A1 'Build ID'
    Build ID: 3f2a91c0b4e7d81a9c5f2e03b71d4a6c8e09f512

# 配好 debuginfod 之后，gdb / crash 会自动去拉符号
$ export DEBUGINFOD_URLS="https://debuginfod.example.com/"
$ crash /var/crash/.../vmcore          # 不用手工指定 vmlinux 了

# 自研模块也要留档，并记下它对应的内核 vermagic
$ modinfo mydev.ko | grep -E 'vermagic|srcversion'
vermagic:    6.1.0-18-amd64 SMP preempt mod_unload modversions
srcversion:  A3F91C0B4E7D81A9C5F2E03

把「机器重启」变成可归因事件

这是整章最有价值的一节。「这台机器昨晚重启了」不是一个事件，是一个待分类的信号——它可能是内核 panic、可能是掉电、可能是硬件看门狗、可能是运维手滑、可能是云平台的实例迁移。五种原因的处理方式完全不同，而区分它们只需要三条命令。

# ── ① 上一次是怎么停的：正常关机还是崩溃 ────────────────
$ last -x reboot shutdown | head
reboot   system boot  6.1.0-18-amd64   Thu Sep  3 10:12   still running
reboot   system boot  6.1.0-18-amd64   Wed Sep  2 03:41 - 10:11 (1+06:30)
# 注意：只有 reboot 没有对应的 shutdown 记录 = 【非正常关机】
# 正常 shutdown 会留下 "shutdown system down" 一行

# ── ② 上一次启动的内核日志里有没有临终遗言 ──────────────
$ journalctl --list-boots
 -2 8f3a... Mon 2026-09-01 09:02:11 — Wed 2026-09-02 03:40:55
 -1 b71d... Wed 2026-09-02 03:41:20 — Thu 2026-09-03 10:11:47
  0 3f2a... Thu 2026-09-03 10:12:05 — ...
$ journalctl -k -b -1 | tail -50
# 看最后几行：
#   有 "Kernel panic - not syncing"    → 内核崩溃，去找 vmcore
#   有 "systemd-shutdown: Rebooting"    → 正常重启，去查是谁下的命令
#   什么都没有，日志【戛然而止】        → 掉电 / 硬件复位 / 宿主机杀掉了 VM

# ── ③ kdump 当时到底有没有生效 ──────────────────────────
$ ls -lt /var/crash/ | head              # 有没有对应时间点的目录
$ systemctl status kdump
$ cat /sys/kernel/kexec_crash_loaded     # 现在是 1，那当时呢？要看历史监控

# ── ④ 硬件侧的证据（前三条都指向「无声重启」时看这个）──
$ ipmitool sel list | tail -20           # BMC 事件日志：掉电、温度、看门狗超时
$ ras-mc-ctl --summary                   # 内存 ECC 统计
证据组合结论下一步
last 无 shutdown + 上次日志末尾有 panic + /var/crash 有新目录内核崩溃，且现场拿到了按 §4 分析 vmcore
last 无 shutdown + 上次日志末尾有 panic + 没有 vmcore内核崩溃，但 kdump 没生效先修 kdump（§3 的四步验收），同时用日志里那段 Oops 按 §2 分析
last 无 shutdown + 日志戛然而止无任何异常掉电 / 硬件复位 / hard lockup 且 NMI 也没起来查 BMC 事件日志、机房电源、硬件看门狗配置
有 shutdown 记录正常重启查 journalctl -b -1 里是谁发起的（运维脚本？自动更新？云平台？）
云上实例，日志末尾正常但重启时间对不上宿主机维护 / 实例迁移查云厂商的实例事件记录，不是你的问题
面试加分点：被问「线上机器无故重启怎么排查」，从「先看 dmesg」开始答就落了下乘——重启之后 dmesg 里全是新启动的日志，上一次的早没了。正确的第一句是：「先确定这是不是内核问题。last -x 看有没有配对的 shutdown 记录，journalctl -k -b -1 看上一次启动的日志是怎么结束的，/var/crash 看有没有 vmcore。三条命令就能把五种原因分开，分错了后面全白干。」这一句就说明你真的处理过这类事故。

什么时候该升级内核，而不是继续查

自己 bisect 一个内核 bug 的成本很高（每轮编译 + 复现动辄几小时，而很多问题几天才复现一次）。下面这几种情况，升级的期望收益远高于继续查：

① 崩溃点在内核通用子系统里，且你的模块是干净的
RIP 落在 mm/、fs/、net/ 里，Tainted 没有 O/P——这种 bug 大概率已经有人踩过并修了。把关键函数名 + 报错首行拿去搜内核 git log、stable 分支的补丁列表、发行版的 bug 追踪系统，命中率相当高。
② 你的内核已经 EOL 或落后很多个稳定版
stable 分支每周都在合入修复。跑着一年前的内核去查一个内存管理的偶发崩溃，很可能你查的东西半年前就被修了。先升到当前 stable 的最新点版本再看还复不复现，这个动作的成本远低于一次 bisect。
③ 但不要盲目升级
升级会引入新的回归，而且「升级后不复现」不等于「问题解决了」——也可能只是时序变了把它藏起来了。真正的判据是找到对应的上游补丁：能指出「就是这个 commit 修的、原因是 XXX」，才算结案。找不到补丁的「升级后好了」，要在复盘里明确标注为未定位。

给上游报 bug 要附什么

一份会被认真对待的内核 bug 报告

  • 完整的 dmesg，从开机第一行开始，不是只截 Oops 那十行——维护者需要看到硬件、固件、启动参数和崩溃前的上下文。
  • uname -a 和 /proc/cmdline，以及发行版和内核包的确切版本。
  • 用 scripts/decode_stacktrace.sh 处理过的调用栈（带文件:行号），比裸地址友好一个数量级。
  • Tainted 的解释：如果有 O 或 P，必须先在卸掉树外模块的纯净内核上复现一次，否则报告基本会被搁置。
  • 能否在最新 mainline 上复现——这是维护者最先问的问题，先自己回答掉。
  • 复现步骤，越小越好；能给出一个几十行的复现程序，处理速度会完全不同。
  • 硬件信息：lspci -nnk、dmidecode（尤其是 BIOS 版本，很多问题是固件的）。
  • 用 scripts/get_maintainer.pl 找到对应子系统的维护者和邮件列表，发给正确的人而不是群发。

决策树与 checklist

机器挂了 / 重启了，从零开始怎么查

把前八章压缩成一条可执行的路径。五个阶段：确认 → 分类 → 取证 → 定位 → 止血。顺序不能乱——最常见的错误是跳过「确认」直接进「定位」，结果花三天查代码，最后发现是一根内存条坏了。

① 确认（3 分钟内做完）

  • last -x reboot shutdown —— 有没有配对的 shutdown？没有就是非正常关机。
  • journalctl -k -b -1 | tail -50 —— 上一次启动的内核日志是怎么结束的？
  • ls -lt /var/crash/ —— 有没有对应时间点的 vmcore？
  • ipmitool sel list / ras-mc-ctl --summary —— 硬件侧有没有告警？这一条最容易被跳过，也最容易白省。
  • 云主机额外看一眼厂商的实例事件记录，排除宿主机维护。

② 分类（对着 §1 那张表）

  • 在日志里 grep 这几个关键词：Oops、kernel BUG at、WARNING:、soft lockup、hard LOCKUP、blocked for more than、rcu.*stall、oom-killer、Hardware Error。
  • 找到时间最早的那一条，不要看雪崩之后的一堆。看 [#N] 计数器，只信 [#1]。
  • 看 Tainted：有 D/W 就往前翻找第一次；有 M/B 立刻转硬件方向；有 O/P 优先怀疑那个模块。

③ 取证

  • 有 vmcore → makedumpfile --dump-dmesg 先秒出日志，再上 crash。
  • 没 vmcore 但机器还活着（卡死）→ echo w、echo l 到 /proc/sysrq-trigger；配了 kdump 就 echo c 主动收现场。
  • 没 vmcore 且已经重启 → 只能用 journalctl -k -b -1 里那段 Oops，同时立刻去修 kdump（§3 四步验收），保证下次能拿到。
  • 可复现的问题 → 上 dynamic_debug / ftrace / bpftrace 抓过程；测试环境上 KASAN + lockdep。
  • 取证阶段不要开始推理。先把所有能拿的数据拿全，再统一分析——边取证边猜会让你只去找支持当前猜想的证据。

④ 定位

  • 校验符号版本：函数长度对得上吗？vermagic 一致吗？版本不对的分析结果是有害的，不是无用的。
  • faddr2line / crash dis -l 把 RIP 变成文件:行号。
  • 多 CPU 场景先 bt -a + foreach UN bt，划掉所有在等锁的，剩下的是凶手。
  • 看毒值：6b6b…（UAF）、5a5a…（未初始化）、dead0000…（链表毒值）。
  • 用 struct -o 把出错偏移对应到结构体成员，验证假设而不是停在假设。

⑤ 止血与收尾

  • 先止血再修根因：隔离故障机 / 回滚上一次变更 / 卸载可疑模块 / 临时调大阈值。
  • 找到上游补丁的，评估升级路径；找不到补丁的「升级后好了」，复盘里标注为未定位。
  • 硬件问题走报修，别让它在集群里飘着继续崩别的业务。
  • 复盘必答三题：下次还会不会发生？下次能不能拿到现场？告警会不会更早响？——第二题答不上，说明 kdump / 日志留存有缺口，这本身就是一个待办。
  • 把这次的判据（比如「mydev 相关的 Oops」）加进监控规则，让下次是告警发现而不是用户发现。流程侧见 故障处理手册。
整套流程里最反直觉、也最值钱的一条：「拿不到现场」本身就是一个必须立刻修复的缺陷，优先级不低于那个崩溃本身。一次没有 vmcore 的崩溃，你能做的只有猜；而只要修好了取证链路，同一个问题下次复现时你会在半小时内定位它。很多团队反复被同一个内核问题折磨几个月，根因不是问题太难，而是从来没有一次拿到过完整现场。

按难度分层，先自测再对照

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础Oops 和 panic 有什么区别？Oops 之后系统还能正常用吗？

    Oops：内核检测到一个本不该发生的异常（最常见是解引用空指针或非法地址），打印一份现场快照，杀掉当前进程，然后返回调度器继续跑。panic：内核判定走不下去了，停机——按 kernel.panic 的秒数自动重启，为 0 则永远挂着。

    什么时候 Oops 会变成 panic：① 异常发生在中断上下文里（没有「当前进程」可杀，只能停机）；② 被杀的是 init（PID 1）；③ 显式设置了 kernel.panic_on_oops=1。

    「Oops 之后还能用」是危险的错觉
    被杀掉的那个上下文可能正持有自旋锁、正改内核链表改到一半、刚分配的资源还没登记。内核没有回滚机制，这些锁永远不会释放、这些资源永远泄漏。结果是：后续访问同一子系统的任务会一个个卡进 D 状态，几分钟后 hung task 刷屏，最终整机雪崩。
    实践结论
    有冗余的集群节点建议开 panic_on_oops=1——与其带病运行返回错误结果污染上游，不如立刻 panic 收 vmcore 让流量飘走。另外 Oops 输出里的 [#N] 是本次启动的第几次 Oops，只有 [#1] 是真相，后面的都是次生灾害。
  2. 基础RIP: 0010:my_func+0x2a/0x60 [mymod] 这一行怎么读？为什么用偏移而不是绝对地址？
    • 0010：代码段选择子，内核态的固定值，没有信息量。
    • my_func：出错指令所在的函数名。
    • +0x2a：出错指令相对函数入口的字节偏移。
    • /0x60：这个函数的总字节长度。
    • [mymod]：函数来自名为 mymod 的可加载模块；没有方括号则来自内核本体。
    为什么用偏移
    开启 KASLR 后每次启动内核代码的绝对地址都不同，贴绝对地址到 bug 报告里对别人毫无用处；而「函数名 + 函数内偏移」在同一份编译产物里永远稳定。附带好处：/0x60 这个长度是个免费的版本校验——如果你手上目标文件里该函数长度不是 0x60，说明拿错了版本，别浪费时间往下查。
    怎么变成源码行
    ./scripts/faddr2line mymod.ko my_func+0x2a/0x60（最推荐，能处理内联）；或 gdb -batch -ex 'list *(my_func+0x2a)' mymod.ko；或 objdump -dS 看上下文。三者都要求是同一次编译的产物——编译器版本、.config、优化等级任何一项不同，都会给出一个语法合理但内容完全错误的行号。
  3. 基础Oops 里的 Tainted: 是什么意思？为什么社区看到 O 就不太愿意接 bug？

    Taint（污染）标记记录「这个内核在崩溃之前已经处于什么非标准状态」，用一串字母表示。它的作用是快速判断这份报告值不值得信。

    • P：加载了专有（闭源）模块——社区基本不受理。
    • O：加载了 out-of-tree（树外）模块，即不在内核源码树里的模块。
    • E：加载了未签名模块。
    • D：本次启动已经 Oops 过——看到它就往前翻找 [#1]。
    • W：之前触发过 WARN_ON；M/B：发生过 MCE / 坏页（硬件信号）；F/R：模块被强制加载/卸载。
    为什么 O 让人却步
    不是傲慢，是成本。树外模块能做任何事：改内核数据结构、用未导出的内部接口、假设了已经变了的行为。当 RIP 落在内核本体某个函数上而 Tainted 有 O 时，最常见的真相是「你的模块把内核数据写坏了，内核只是在后来某个时刻踩到了坏数据」。维护者没有你的代码，无从判断。所以报 bug 前的标准动作是：卸掉所有树外模块（或用发行版原装内核）复现一次。
  4. 基础kdump 为什么能在内核已经死掉的机器上把内存现场保住？

    靠两件事，缺一不可：

    ① 提前预留一块「谁都不许碰」的内存
    开机时通过 crashkernel= 从物理内存里划走一块，生产内核从此看不见它（free 里会少掉这么多）。捕获内核只在这块内存里活动，因此它的运行不会覆盖第一内核的任何一个字节。预留必须在启动早期做——运行时再想找一块「肯定没人用」的连续物理内存，做不到。
    ② kexec 跳转不经过固件
    正常重启会经过固件复位流程，很多平台会做内存训练或让 DRAM 掉电——现场就没了。kexec 是纯软件跳转：设好新内核的入口、页表和参数直接跳过去，DRAM 一直在正常刷新。于是第一内核的每一个 task_struct、每一段 slab、整个 printk 环形缓冲，全都完好地躺在那里。

    捕获内核起来后通过 /proc/vmcore 读取旧内存，用 makedumpfile 裁剪压缩后落盘，落盘完成才真正重启。

    配了不等于生效
    必检两个文件：/sys/kernel/kexec_crash_size（预留字节数，为 0 就是没预留成功）和 /sys/kernel/kexec_crash_loaded（捕获内核是否已装载，必须是 1）。然后 echo c > /proc/sysrq-trigger 真触发一次，确认 /var/crash 里有文件落地。

10.2 中级（区分熟练度）

  1. 中级crashkernel 该预留多大？预留不够会出现什么现象？

    预留区要装下一个完整的捕获内核 + initramfs（含存储驱动、落远端时还要网络驱动）+ makedumpfile 的运行内存。经验值：256 MB 是下限；带复杂存储栈或走网络落盘的建议 512 MB 起；TB 级内存的机器因为 makedumpfile 要维护页位图，需求还会再涨。

    # 固定值
crashkernel=512M
# 按总内存分档（一份配置适配不同规格）
crashkernel=2G-64G:256M,64G-1T:512M,1T-:1G
# x86_64 大内存机：主体放 4G 以上，另留一小块低端内存给需要低 DMA 的设备
crashkernel=1G,high crashkernel=256M,low
    预留不够的现象非常有迷惑性
    panic 后机器直接重启，/var/crash 空空如也——因为捕获内核自己在启动过程中 OOM 或挂了，而这次崩溃是没人接的。现象和「kdump 根本没开」一模一样，很容易被误判成 kdump 配错了。控制台上通常能一闪而过地看到 OOM 或 initramfs 挂载失败。
    另外两个高频坑
    ① 预留失败：内存碎片化导致找不到连续区域（大内存机不写 ,high 时尤其常见）、grub 改了没重新生成、云镜像的命令行被 metadata 覆盖——所以必须查 /sys/kernel/kexec_crash_size 而不是只看 grub 配置。② 落盘目标不可用：path 指向的目录挂在 iSCSI / 复杂多路径存储上，而捕获内核的极简 initramfs 里没有对应驱动。
  2. 中级makedumpfile -d 31 里的 31 是什么意思？为什么它能把几百 GB 压到几 GB？

    -d 的参数是一个位掩码，每一位对应一类「可以扔掉的物理页」：

    bit值裁掉
    01全零页
    12非私有的 page cache
    24私有的 page cache
    38用户进程数据页
    416空闲页（在 buddy 空闲链表上的）

    31 = 1+2+4+8+16，即五类全裁。一台 512 GB 的机器里，绝大部分内存是 page cache、用户进程数据和空闲页——这些对排查内核崩溃毫无价值。保留下来的是内核代码、内核数据、slab、页表、task 结构，通常只有几个 GB，再叠加压缩（-l lzo / -c zlib / -p snappy）就更小了。

    顺带解决了合规问题
    bit 3 裁掉的正好是用户数据页，bit 1/2 裁掉 page cache——vmcore 里最敏感的东西（明文密码、密钥、用户数据、被缓存的文件内容）大部分就此消失了。这是「性能优化顺便解决安全问题」的经典案例。反过来说：如果为了追某个用户态相关的问题改用 -d 1，那份 vmcore 的敏感级别完全不同，不能按常规流程流转。
    被低估的一条命令
    makedumpfile --dump-dmesg vmcore out.txt——几秒钟就能把崩溃瞬间的完整内核日志抠成文本，不需要任何调试符号。很多事故到这一步就破案了，根本用不着开 crash。拿到 vmcore 的第一件事就该是它。
  3. 中级hung task detector 为什么只检测 D 状态的任务，S 状态不算？

    因为两种睡眠的语义完全不同。

    S（TASK_INTERRUPTIBLE，可中断睡眠）是「正常等待」的常态：sshd 等新连接可以等三个月，空闲服务器上 99.99% 的进程都在 S。把它纳入检测等于每两分钟刷屏几百条误报。

    D（TASK_UNINTERRUPTIBLE）表示「正在等待一个不可被信号打断的事件」，通常是块设备 IO、页回写、某些内核互斥锁。这类等待按设计就应该在毫秒到秒级返回——等满两分钟只有两种可能：底层设备真挂了，或者死锁了。两种都值得报警。

    检测机制
    khungtaskd 内核线程周期扫描全部任务，找「处于 D 状态且自愿+非自愿上下文切换计数与上次扫描时完全相同」的——说明这段时间它一次都没被调度过。超过 hung_task_timeout_secs（常见默认 120 秒）就打印它的栈。
    一个坑：hung_task_warnings
    默认只报 10 次就不再报了。长时间运行的机器上，「没再报了」很容易被误读成「问题好了」，其实只是配额用完。排查期间记得 sysctl -w kernel.hung_task_warnings=100。
    不等检测器的手工版
    ps -eo pid,stat,wchan:32,comm | awk '$2 ~ /^D/' —— wchan 列直接告诉你它睡在哪个内核函数上，常常一眼就够；再不够就 cat /proc/<pid>/stack 或 echo w > /proc/sysrq-trigger。
  4. 中级系统已经卡到 SSH 连不上、shell 敲不动，但键盘还有反应。你会怎么做？

    不要直接按电源键——那等于亲手销毁唯一的现场。用 magic SysRq，它在极高优先级的中断路径上直接处理，绕过用户态、调度器和文件系统，系统半死时通常仍然有效。

    1. Alt+SysRq+w：打印所有 D 状态任务的栈——这是取证的第一条命令。
    2. Alt+SysRq+l：通过 NMI 打印所有 CPU 当前的栈——找「谁在占着 CPU 不放」。
    3. Alt+SysRq+m：内存统计（怀疑 OOM 或内核内存泄漏时）。
    4. 配了 kdump 就 Alt+SysRq+c：主动 panic，拿一份完整 vmcore。
    5. 实在不行走 R-E-I-S-U-B：夺回键盘 → 终止进程 → 杀死进程 → 同步磁盘 → 只读重挂 → 重启。每步之间等几秒，比断电安全得多（不丢数据、不烂文件系统）。

    还能登进去时用 echo w | sudo tee /proc/sysrq-trigger，输出都进 dmesg。需要先启用：sysctl -w kernel.sysrq=1。

    为什么 SysRq 在系统卡死时还能工作
    它不依赖任何用户态进程、不依赖调度器（不需要「调度到某个处理程序」）、也不写文件系统（结果直接进内核环形缓冲）。唯一的前提是中断还能进来——所以 soft lockup 时它有效，而彻底 hard lockup 的那个 CPU 是响应不了的（那种情况只能靠 NMI 自动打出来的那段，或者靠 kdump）。

10.3 高级（体现深度）

  1. 高级拿到一个多核死锁的 vmcore，怎么在一堆 CPU 里找出真凶？

    核心思路一句话：找「不在等」的那个。

    bt 只能看到崩溃的那个任务，而它通常是受害者——比如 CPU 3 自旋等一把锁等到 hard lockup，真正拿着锁不放的是 CPU 5。所以要用 bt -a（每个 CPU 上正在跑的任务）配合 foreach UN bt（所有 D 状态任务）。

    判读方法
    受害者的栈顶是等待函数：queued_spin_lock_slowpath、osq_lock、__mutex_lock、rwsem_down_*、io_schedule。凶手的特征恰恰是「栈顶是正常的业务函数」——它拿着锁在干一件永远干不完的事（死循环、遍历成环的链表、等一个不会来的硬件应答、在临界区里睡眠）。所以做法是：先把所有「在等锁」的 CPU 划掉，剩下的一两个就是答案。
    辅助手段
    foreach bt | grep -c <func> 看聚集——「37 个任务同时卡在 mydev_ioctl」这个数字本身就是结论。ps 里行首的 > 标记正在占 CPU 的任务，UN 就是 D 状态。
    别把殡仪馆当案发现场
    bt 输出最上面几帧（machine_kexec / __crash_kexec / oops_end / exc_page_fault）是内核处理崩溃本身的代码，不是死因。真正的现场是 [exception RIP: ...] 那一行及其下面的帧。另外别忘了 mod -s mymod /path/mymod.ko 给自研模块加载符号，否则 dis 只有裸地址。
  2. 高级在内核崩溃现场看到 0x6b6b6b6b6b6b6b6b、0x5a5a5a5a、0xdead000000000100，各说明什么？

    这些是毒值（poison）——内核在特定时刻用固定字节填充内存，把「静默的数据损坏」变成「一眼能认出的证据」。

    • 0x6b 反复填充（最后一字节常为 0xa5）：已释放对象的填充。看到它 = use-after-free，对象已 kfree 但代码还在用。0x6b 是 ASCII 的 k，取 "kfree"。
    • 0x5a 反复填充：刚分配、尚未初始化的区域。看到它 = 忘了初始化就用，或越界读到了对象 padding。
    • 0xbb / 0xcc 填充的红区（red zone）：SLUB 在对象前后加的哨兵。红区被改写 = 缓冲区越界写。
    • 0xdead000000000100 / 0xdead000000000122：list_del 之后写进 next/prev 的链表毒值。看到它 = 重复 list_del，或使用了已摘链的节点。
    • 极小的非零值如 0x10：ZERO_SIZE_PTR，kmalloc(0) 的返回值——长度算成了 0 却当正常指针用。
    怎么开、怎么用
    启动参数 slub_debug=FZPU（F=一致性检查 Z=红区 P=毒化 U=记录分配/释放调用栈），或只对单个 cache 开 slub_debug=FZPU,kmalloc-256 以降低开销。U 是最值钱的一个 flag：报告会直接给出「Allocated in … / Freed in …」两段调用栈，几乎不用再推理。生产上只在追具体 bug 时对单个 cache 开。
    和 KASAN 的分工
    slub_debug 是事后发现毒值被改——知道被踩了，但不一定知道是谁在什么时候踩的。KASAN 是插桩检测，在越界/UAF 发生的那一瞬间就报，栈是精确的，而且报告直接给「踩的人 / 分配的人 / 释放的人」三段栈。代价是要重编内核、内存和 CPU 开销都是数倍级——测试环境用 KASAN，生产环境用 slub_debug。
  3. 高级虚拟机上频繁报 soft lockup，怎么判断是真问题还是误报？

    先理解误报的机制。soft lockup 的判据是「某 CPU 上的 watchdog 线程超过 2×watchdog_thresh（默认约 20 余秒）没被调度到」。但在虚拟机里，vCPU 只是宿主上的一个普通线程——宿主超卖时它可能被整个抢走几秒到几十秒。在 guest 内核看来，「时间凭空跳过去了」和「某个 CPU 卡了这么久」完全无法区分。此外热迁移的停机阶段、虚拟磁盘后端阻塞，都会造成同样的效果。

    两条判据
    ① 看 steal time。vmstat 1 的 st 列、top 里的 st、/proc/stat 第 8 个字段。持续明显非零（> 5%~10%）基本就能确定是宿主争抢。② 看栈有没有「形状」。真实的 soft lockup 会稳定地卡在同一个内核函数上（那个死循环）；误报的栈每次都不一样，甚至栈顶是 native_safe_halt（本来在 idle）这种荒谬的位置。「栈没有形状」= 误报——这和判断硬件问题的逻辑是同一个。
    内核已有的缓解及其局限
    KVM 提供 steal time 和「宿主曾暂停过本 guest」的标志，guest 内核报警前会检查它，若刚被暂停过就跳过这次报警。这能挡掉大部分热迁移和明显暂停导致的误报，但挡不住持续性的中度超卖——每次只被抢 3 秒、连抢 7 次，标志不一定被置上，累计却超了阈值。
    务实配置
    虚拟机上把 watchdog_thresh 放宽到 30，并且绝对不要开 softlockup_panic（否则会变成随机重启）；hardlockup_panic 可以保留，它极少误报。同时把 steal time 纳入监控告警——它才是这类问题的真实指标。注意反面风险：把阈值调到永远不报，问题还在，只是你看不见了。
  4. 高级内核栈为什么只有十几 KB？这对写内核代码有什么约束？

    每个内核线程（以及每个进入内核态的用户线程）都有独立的内核栈，x86_64 上常见是 16 KB（4 个页），不少 32 位平台是 8 KB。大小在编译时由 THREAD_SIZE 决定，运行时不可增长——和用户态那个默认 8 MB、还能自动扩展的栈完全不是一回事。

    为什么必须这么小
    ① 它是按线程数线性乘出来的常驻开销：一万个任务 × 16 KB = 160 MB 物理内存。② 这些页必须常驻、不能换出——换出的话，缺页处理本身又需要栈，会死循环。③ 历史上还要求物理连续（CONFIG_VMAP_STACK 之前），大块连续内存本身就稀缺。所以「小」不是疏忽，是必须付出的设计代价——代价转嫁给了内核开发者。
    三条硬约束
    ① 不许在栈上放 KB 级缓冲区：char buf[4096] 一口气吃掉四分之一。要用 kmalloc / per-CPU 缓冲 / 预分配池。② 不许无界递归：如果递归深度由外部输入决定（解析嵌套结构、遍历树），那就是一个可被远程触发的内核崩溃；必须改迭代或硬限深度。③ 注意隐式深度：文件系统嵌套（loop 设备上的 fs 上的 fs）、块设备栈叠（LVM over MD over dm-crypt）会让调用链比你想的深得多。
    怎么发现
    编译期：-Wframe-larger-than=（CONFIG_FRAME_WARN，默认阈值在 1~2 KB 量级）会对超标的栈帧告警，这能拦住一大半。运行期：开启 CONFIG_VMAP_STACK 后栈末尾有不可访问的守护页，溢出会立刻报 BUG: stack guard page was hit；没有它的老内核则表现为栈回溯完全乱码或静默踩坏相邻内存——后者是最难查的一类问题，因为崩溃点和真凶完全无关。
