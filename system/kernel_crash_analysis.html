内核崩溃分析

本站 崩溃调试指南讲的是用户态进程崩溃——有 core dump，有 GDB，可以慢慢看。这一篇讲内核崩溃：整机挂掉，没有 core，没有 GDB，进程连同它的调试器一起消失了。你手上只有一段抢救出来的 dmesg，或者一个几 GB 的 vmcore。本文要解决的是「怎么从这两样东西里把根因挖出来」。

内核出问题的几种形态

先分类，再取证——走错路会浪费一整天

「机器挂了」不是一件事。排障第一步永远是分类：OOM 当驱动 bug 追、ECC 当竞态去 review，是最常见的时间浪费。主轴只有一句——内核还能不能继续跑。

用户态崩溃像租户自己屋里摔了杯子：物业（内核）给你留现场照片（core dump），整栋楼照常运转。内核崩溃像承重结构出问题：能拍照的人也在楼里。所以必须提前把相机藏进谁也动不了的角落（kdump 预留内存），出事时自己抢救自己。没有这间「消防指挥室」，panic 后立刻 reboot 就把环形缓冲一起清掉——这就是「自动重启会丢现场」的技术含义，不是运维口号。

用一句话区分：内核还能不能继续跑

Oops 杀掉肇事上下文后试图继续；panic 停机。lockup / hung task / RCU stall 是检测器报「某个东西不动了」，本身不改系统状态。OOM 是设计行为，容量问题不是缺陷。

Oops：内核态踩到不该踩的地址（最常见空指针），没有 fixup 能救，于是打印现场快照、杀掉当前进程、返回调度器。
「Oops 之后系统还活着」是危险错觉。被杀的上下文可能正持有自旋锁或改链表改到一半。内核没有回滚，这些锁永远不释放。后续任务卡进 D 状态，几分钟后 hung task，再过一会儿雪崩。只有第一次 Oops 的堆栈是真相——[#2] [#3] 通常是次生灾害，不要追。

Oops 变成 panic 的三个条件：异常发生在中断上下文（没有「当前进程」可杀）、被杀的是 init、或显式 panic_on_oops=1。自动重启会丢现场：kernel.panic=0 永远挂着，没有服务也没有 vmcore；设成 1 秒又没配 kdump，环形缓冲来不及刷就被清掉——这是生产上「配了自动重启却永远查不出原因」的最常见组合。集群节点立刻 panic 收现场是对的：流量会飘走，带病节点返回错误结果会污染上游。单点工控、车载、机房里唯一那台采集机则相反：停机就是事故，宁可 WARN 后降级运行，靠外部硬件看门狗兜底。hard lockup 还能打印，是因为 NMI 不受 cli 影响；连这条都没有、机器静默复位，去查硬件看门狗或掉电，不要在软件里找死循环。

OOM killer 是设计行为：内核在内存耗尽时按分数杀用户进程以自保。把它当驱动 bug 去追，是最常见的分类错误。真正的内核泄漏会表现为 kmem -i 里 SLAB 长期涨、用户进程 RSS 却不高；那种情况杀进程救不了，只能 panic 收现场或重启。WARN 是最好的早期信号——它还没把锁拿死，此时开 panic_on_warn 能抓到第一现场，平时开了会天天重启，只在追某个偶发 WARN 的调试期用。看到 WARN 就当没看见，等它升级成 Oops，是把最好的取证窗口自己关上了。

要不要自动重启：一组 sysctl 决定你能不能拿到现场

很多发行版默认 Oops 不 panic、panic 后也不重启——既没有服务，也没有 vmcore。集群节点应立刻收现场让流量飘走；单点工控/采集机宁可降级运行、靠外部硬件看门狗兜底。「拿现场」和「保可用」是真实取舍：有冗余时现场几乎免费；没有冗余时，更划算的是事前把 dynamic_debug、pstore、KASAN 测试机配好，降低对「崩那一次的 vmcore」的依赖。参数表在下面，场景表在 §7。

address / CR2触发缺页的线性地址。接近 0 = 空指针；0x8/0x18 往往是结构体成员偏移，配合 pahole / struct -o 对上（见 §5）

RIP 一行的完整读法：0010 是内核态代码段选择子，没有信息量；mydev_write 是出错指令所在函数；+0x2a 是相对函数入口的字节偏移；/0x60 是这个函数的总字节长度；方括号 [mydev] 表示来自可加载模块，没有方括号则来自内核本体。+0x2a/0x60 不是卖弄——开启 KASLR 后每次启动绝对地址都不同，贴绝对地址对别人毫无用处；同一份编译产物里「函数名 + 函数内偏移」永远稳定，总长度还是免费的版本校验。Code 行被尖括号包住的字节是出错指令的第一个字节；手头没有匹配的 .ko 时，源码树里的 scripts/decodecode 是最后的救命稻草。

+0x2a/0x60 对抗的是 KASLR。开启地址随机化后每次启动绝对地址都不同，贴到 bug 报告里对别人毫无用处；「函数名 + 函数内偏移」在同一份编译产物里永远稳定。/0x60 还是免费的版本校验——长度对不上就停。带 ? 的栈帧像白板上没擦干净的旧字迹：内核栈反复被不同调用占用，ORC 推不出就扫描「看起来像代码地址」的残渣。只信不带问号的链；当前函数在 RIP 那一行，不在 Call Trace 里。

Tainted —— 决定社区理不理你

一串字母记录崩溃前的非标准状态，用来快速判断报告值不值得信——如果塞了闭源驱动、或者之前已经崩过一次，这次现场很可能不是内核自己的问题。Tainted: G OE 里每个位置对应一个固定标记位，G 在第一位表示没有专有模块，空格表示该位未置位。

字母含义对排障的影响

O / E树外模块 / 未签名自研驱动、DKMS 会置 O。上游第一反应是「先卸掉再复现」

RIP 落在内核本体、Tainted 却有 O 时，最常见真相是你的模块把内核数据写坏了，内核后来才踩到。报 bug 前：卸掉树外模块或用发行版原装内核复现一次。

社区看到 O 却步不是傲慢，是成本。树外模块能改内核数据结构、用未导出接口、假设已经变了的行为。RIP 落在内核本体而 Tainted 有 O 时，最常见真相是你的模块把数据写坏了，内核后来才踩到。维护者没有你的代码，无从判断。能在纯净内核上复现，报告才有价值。NVIDIA、某些 RAID 卡驱动会置 P，那基本等于社区不受理——不是歧视厂商，是闭源代码没人能看，任何「内核本体 Oops」都可能是闭源模块先写坏了页表。

03

kdump / kexec 机制

怎么在内核已经死掉的机器上，把内核的尸体拍下来

§2 那段 Oops 是幸运情况。生产里更常见：机器直接重启，环形缓冲一起没了。要在「崩溃」和「重启」之间插一步——kdump。

kexec：正在运行的内核直接跳进另一个内核，跳过固件。kdump 是它的特化：预先把捕获内核加载进预留内存，生产内核 panic 时跳过去，把第一内核残留的内存写成文件。
正常重启像火灾后把楼推平再重建，现场什么都不剩，事后只能靠幸存者回忆（来不及刷出去的那几行日志）。kdump 像预留一间独立消防指挥室：日常锁着（预留内存），出事时从这间房接管，建筑结构原封不动，拍完档案（vmcore）才允许推倒。

为什么这样能拿到现场

两点缺一不可：① crashkernel= 开机时划走一块物理内存，生产内核看不见它，捕获内核只在这块里跑，不会覆盖第一内核任何一个字节。这也是为什么预留必须提前在启动时做——运行中再找连续物理区做不到。② kexec 是纯软件跳转，不走固件复位/内存训练，DRAM 一直刷新。正常重启会经过固件，很多平台会做内存训练、清零或至少让 DRAM 掉电刷新中断——现场就没了。kexec 设置好新内核的入口、页表和参数，然后直接 jmp 过去。

预留必须在启动早期做——运行时再找一块「肯定没人用」的连续物理内存做不到。free 里会少掉这么多，这是永久成本。捕获内核起来后通过 /proc/vmcore 读旧内存，makedumpfile 裁剪压缩后落盘，落盘完成才真正 reboot。配了不等于生效：必检 kexec_crash_size（为 0 就是没预留成功）和 kexec_crash_loaded（必须是 1），再真触发一次确认 /var/crash 有文件。第一内核的每一个 task_struct、每一段 printk 环形缓冲、每一张页表，全都完整地躺在那里等着被读。

上线前四步验收

  • kexec_crash_size 非 0，且和 grub 里写的量级一致。
  • kexec_crash_loaded 为 1。systemctl is-enabled kdump 为 enabled 只说明开机要装，不说明现在已经装进预留区。
  • 维护窗口主动 echo c 一次：重启后 /var/crash 必须有带时间戳的目录，里面有 vmcore 或至少 vmcore-dmesg.txt。
  • 用匹配的 vmlinux 打开这份测试 vmcore，能看到 PANIC:。内核或 kdump 包升级后这四步重跑——新内核的捕获镜像没签上、预留策略变了，都是静默失效。
预留太小 → 捕获内核自己挂
捕获内核要跑 initramfs（存储驱动、落 NFS 时还要网卡）和 makedumpfile。预留不够它会在启动过程中 OOM，而这次 panic 没人接——机器直接重启，/var/crash 空空如也，现象和「kdump 根本没开」一模一样。经验值：256 MB 下限，复杂存储或网络落盘 512 MB 起；TB 级机器因为页位图还会再涨。256M 写在 grub 里但 kexec_crash_size 为 0，多半是大内存机没写 ,high 找不到连续区。

makedumpfile：几百 GB 为什么能压成几 GB

-d 是位掩码，按页类型裁剪。生产默认 -d 31（上表）+ -l zlib / -c gzip / -p snappy。--dump-dmesg 被严重低估：vmcore 有 8 GB、debuginfo 还没装，这条命令几秒就能把崩溃瞬间的完整内核日志抠成文本，不需要任何符号。很多事故到这一步已经结案（磁盘 IO error 刷屏），根本用不着开 crash。拿到 vmcore 的第一件事就该是它。

kexec_crash_size 为 0 的典型原因：内存碎片化找不到足够大的连续物理区（大内存机没写 ,high）、改了 grub 没重生 cfg、云镜像用 metadata 覆盖了内核命令行。这个值必须非零且和你写的数字一致。Secure Boot 下老 kexec_load 会被 lockdown 拒绝，必须 kexec_file_load（kexec -s）；自编内核没有厂商签名时，要么进 MOK 注册证书，要么接受「只能靠串口」。嵌入式那 512 MB 是 25% 成本，通常改用 pstore（写进 UEFI 变量 / ACPI ERST / 专用 RAM），重启后从 /sys/fs/pstore/ 读——拿不到完整镜像，但能保住最后几 KB 日志。

#0 不是案发点。下面的帧才是真实调用链；末尾若还有一组 RIP/RSP，那是用户态上下文，能告诉你这次内核执行是由哪个用户态调用触发的。bt -f 把栈上的原始字一起打出来，手工辨认被 ? 掩盖的帧时用——ORC 推不出时，你有时能在原始数据里认出一个被漏掉的返回地址。不要把殡仪馆那几帧（machine_kexec / __crash_kexec / oops_end / exc_page_fault）当成调用者去 faddr2line。

lockup / 死锁里，崩溃那个 CPU 往往是受害者：CPU 3 自旋等到 hard lockup，拿着锁不放的是 CPU 5 上陷入死循环的任务。bt 只能看到受害者。bt -a 的读法不是从上往下逐个看，而是先划掉所有栈顶是等待函数的 CPU（queued_spin_lock_slowpath / osq_lock / __mutex_lock / io_schedule / rwsem_down_*），剩下那一两个栈顶是业务函数、却永远不返回的，才是凶手——死循环、成环链表、临界区里睡眠、等一个不会来的硬件应答。面试里问「怎么找真凶 CPU」，标准回答就是「看谁不在等」。

kmem -i 里 SLAB 占到百分之几十是明确的内核泄漏（正常个位数）。kmem -s 能告诉你哪个 cache 涨了，不能告诉你谁分配的——那是过程，vmcore 里通常没有。要分配点，去能复现的环境开 slub_debug=U（记录每个对象的分配/释放栈）、/sys/kernel/debug/kmemleak（CONFIG_DEBUG_KMEMLEAK）或 bpftrace 在 kmem:kmalloc 上按栈聚合。这是 vmcore 分析的固有边界，也是 §6 那些「不崩溃时的手段」同样重要的原因。

一次真实走查的缩小范围，而不是随机敲命令：log 看见崩前几秒的 device removed → bt 跳过殡仪馆落到 mydev_write+0x2a → mod -s mydev 让 dis -l 给出文件:行号 → struct -o mydev_ctx 把 Oops 的 address: 0x18 对上 cursor 字段 → 假设被验证。UPTIME 是「开机就崩」还是「跑了 12 天才崩」直接决定方向：前者像初始化/参数，后者更像泄漏或极低概率竞态。

crash 走查通用套路

  • 永远从 log 开始；崩前几秒的 "device removed" 这类日志经常直接点破。
  • bt 只给受害者，bt -a + foreach UN bt 才给全场。
  • 自研模块务必 mod -s；用 struct -o 把 Oops 的 address: 0x18 对上字段。
  • 不要在 vmcore 里找过程。输出用 > file 存下来。

② UAF 与 slab poison：认毒值

Slab poison：调试开启后，释放时用固定字节填对象、分配时填未初始化区——把静默损坏变成一眼能认出的证据。

slub_debug=FZPU：F 健全性检查、Z 红区、P 毒化、U 记录分配/释放栈。U 最值钱——报告直接给 Allocated in / Freed in。生产只对单个 cache 开（slub_debug=U,kmalloc-256），全开会让分配路径慢一个数量级、内存涨一截。slub_debug 是事后发现毒值被改；KASAN 是插桩，越界/UAF 当下就报。测试用 KASAN，生产用定点 slub_debug。看见毒值被改成别的花纹，说明对象已经被重新分配给别人——那是 use-after-realloc，比「还没被复用的 UAF」更难追，必须靠 U 的两次栈。

list_del 在调试配置下会把 next/prev 写成 LIST_POISON1/2（0xdead000000000100 / 0xdead000000000122）。再次 list_del 或遍历已摘链节点，Oops 的 address 就会带 dead。这比「随机野指针」好查得多：直接去找哪条路径把同一个节点删了两次，或模块卸载后工作队列还握着那条链表。

KASAN 报告的三段式读法
第一行给「什么类型的错误 + 在哪个函数」（slab-use-after-free / slab-out-of-bounds / stack-out-of-bounds / global-out-of-bounds / double-free），三段调用栈分别给「踩的人 / 分配的人 / 释放的人」。UAF 类问题看到这三段基本就结案了——「释放的人」和「踩的人」之间缺一道同步，把它补上就是修复。最下面的影子内存转储里，00 表示这 8 字节完全可访问，非 00 的值编码了不可访问的原因（部分可访问、红区、已释放），^ 精确指到出错字节；日常排查通常不需要逐字节解读它。
❌ 引用计数缺失 → UAF

mydev_release 里直接 kfree(ctx)，但 ctx 还挂在定时器 / 工作队列上。mydev_timer_fn 稍后 ctx->seq++ —— 读到 0x6b6b… 或踩坏别人。release 与 timer 之间没有任何同步，不是「可能出问题」，是迟早出问题。

✅ 引用计数 + 同步取消
static void ctx_free(struct kref *k)
{
    struct mydev_ctx *ctx = container_of(k, struct mydev_ctx, ref);
    kfree(ctx->buf);

③ 内核栈溢出：只有十几 KB

④ 原子上下文里睡眠

持自旋锁、关中断、软/硬中断、RCU 读侧里调用可能睡眠的函数（mutex_lock、kmalloc(GFP_KERNEL)、copy_to_user）——调度器想切走当前任务，而它攥着别人正在自旋等的锁。轻则性能崩溃，重则整机死锁。报告形态：scheduling while atomic 或 sleeping function called from invalid context（in_atomic(): 1）。

ABBA 死锁的经典形状：进程上下文拿 A 再拿 B，中断上下文拿 B 再拿 A。进程被中断打断时两把锁互相等，soft lockup 和 hung task 会一起响。lockdep 在测试机第一次走出这个顺序就会报 circular locking dependency，不必真等到死锁。生产上看到「ioctl 卡住 + 中断处理函数也卡住同一把锁」，先画等待环，不要先调 hung_task 阈值。

防线在编译/测试期：CONFIG_DEBUG_ATOMIC_SLEEP、CONFIG_PROVE_LOCKING（lockdep 在第一次 A→B 再 B→A 时就报 circular locking，不必真死锁）、CONFIG_DEBUG_SPINLOCK。生产内核通常关这些，所以「线上没报 lockdep」不证明没有死锁，只证明你没在测试机开证明器。

用户态空指针只是 SIGSEGV；内核态一次空指针写就是 Oops，锁和资源状态不确定（见 §1）。偏移很大时可能落到真实内存 → 不 Oops，静默改别人的数据。mmap_min_addr 就是为了让空指针早点、响亮地崩，而不是悄悄写到低地址映射里。极小非零如 0x10 可能是 kmalloc(0) 返回的 ZERO_SIZE_PTR，不是「差不多是 NULL」——当成空指针修会修错地方。

「一堆任务在等锁」时，持锁者往往不在 D 状态：它可能正在 CPU 上跑（ps 的 >），或者卡在另一个不可中断等待里。只打阻塞栈会漏掉真凶。两类混在一起时先解释 IO 那一支——底层设备 error 经常是表象，锁死是被 IO 卡住之后的连锁。

⑤ 锁死：拿到全部阻塞栈

「一堆任务在等锁」时要找的是持锁者，而它往往不在 D 状态。活系统：echo w（阻塞栈）+ echo l（全 CPU 栈）；vmcore：foreach UN bt + bt -a。栈顶 io_schedule → 查设备/IO error；栈顶 __mutex_lock → 找持锁者。两类混在一起时先解释 IO 那一支。

⑥ 硬件与固件：不要去追代码

特征：崩溃位置随机、栈毫无规律、换机器不复现。软件 bug 几乎总有稳定形状。

检测器原理与调参

四个告警都在问「某个东西是不是不动了」，但盯的对象不同。不理解原理就调参数，最常见的结果是阈值调到永远不报——问题还在，只是你看不见了。

hung task 检测器区分的是「在会议室开会」和「在洗手间反锁了两小时」。前者（S 状态）待多久都正常；后者（D 状态）隔间设计上不该被占用两小时——要么人出事了，要么门锁坏了。khungtaskd 就是那个负责敲门的人。

khungtaskd 是一个普通内核线程，周期遍历全部任务，做一件很朴素的事：这个任务处在 TASK_UNINTERRUPTIBLE（D），而且自愿+非自愿上下文切换总数和上次看时一模一样——说明这段时间一次都没被调度过，纯粹在睡。连续超过阈值就打印它的栈。

S（可中断睡眠）是正常等待的常态：sshd 可以等三个月，epoll_wait 空转的服务器一天里 99.99% 的时间都在 S。纳入检测等于每两分钟刷屏几百条误报。D 表示正在等待一个不可被信号打断的事件（块设备 IO、页回写、某些内核互斥锁），按设计应在毫秒到秒级返回——等满两分钟只有两种可能：底层设备真挂了，或死锁了。hung_task_warnings 默认只报 10 次就静默，「没再报了」很容易被误读成好了。要追一个持续存在的 hung，把这个计数调到 -1（不限次数），查完改回去。

soft lockup 的检测靠每 CPU 的 hrtimer（周期约 watchdog_thresh/5）检查 watchdog 线程有没有被调度到并更新时间戳——定时器中断本身进得来，所以这个 CPU 只是不让出，不是完全失联，报警可以在中断上下文里正常打印。建议开 softlockup_all_cpu_backtrace，否则只看到一个核。hard lockup 是 local_irq_disable() 之后死循环，hrtimer 整套失效，只能靠 NMI：不可屏蔽中断不受 cli 影响。x86 上 NMI 通常由 PMU 产生；虚拟机没有虚拟 PMU 时这套机制可能直接不可用（dmesg 里会有 perf event 创建失败），新内核提供 CPU 之间互相检查的 buddy 方案作替代。

RCU 的核心假设是：每个 CPU 都经历过一次上下文切换 / 进过用户态 / 进过 idle（静止态）之后，此前所有读侧临界区都已结束，被延迟释放的内存才能回收。某个 CPU 长时间一次静止态都没有，宽限期永远结束不了，待释放内存不断堆积，最终可能拖垮整机。RCU stall 和 soft lockup 经常同时出现且指向同一个死循环：看两条日志点名的 CPU 编号是不是同一个，是就当一个问题查，不要当成两件事分别调两个阈值。

物理机上的 watchdog 像老板每隔 20 秒来工位看一眼：人不在就记一笔。虚拟机的 vCPU 像被派去别处开会的员工——他不是在偷懒，是被更高一层的调度者整个人调走了 20 秒。可这位老板（guest 内核）看不见宿主机那一层，只知道「工位空了 20 秒」，于是照样记一笔 soft lockup。问题从来不在这个员工身上。

误报的机制：vCPU 只是宿主上的一个普通线程，超卖时被抢走几秒到几十秒。在 guest 看来，「时间凭空跳了」和「某个 CPU 卡了这么久」无法区分。热迁移的停机阶段、虚拟磁盘后端阻塞会造成同样效果。KVM 的 steal time 标志能挡掉大部分明显暂停，但挡不住「每次抢 3 秒、连抢 7 次」这种中度超卖。真实 soft lockup 会稳定卡在同一个内核函数；误报的栈每次都不一样，甚至栈顶是 native_safe_halt（本来在 idle）。「栈没有形状」= 误报——这和判断硬件问题是同一个逻辑。先看 vmstat 1 / top 的 st 列或 /proc/stat 第 8 字段：持续 >5%–10% 基本就是宿主争抢。虚拟机把 watchdog_thresh 调到 30，绝对不要开 softlockup_panic（会变成随机重启）；hard lockup 仍可 panic。反面风险：阈值调到永远不报，问题还在——把 steal time 纳入监控，而不是把检测器掐死。

这个取舍的本质是「现场的价值」对比「可用性的代价」。有冗余时现场几乎免费（流量飘走），那就该拿。没有冗余时，现场的价格是一次真实中断——更划算的是降低对 vmcore 的依赖：dynamic_debug / ftrace 常态化埋点、配好 pstore、测试环境用 KASAN。「拿不到 vmcore」不等于查不出来，只是需要事前多花功夫。

符号管理的四条硬规矩

  • CI 必须归档未 strip 的 vmlinux 和所有 .ko，和 build id 绑定，保留期 ≥ 最长支持周期。/boot/vmlinuz-* 是压缩引导镜像，不能给 crash 用。

  • 部署 debuginfod：设 DEBUGINFOD_URLS 后 gdb / crash / perf 能按 id 自动拉符号，彻底告别翻遍制品库。发行版通常也有公共 debuginfod。
  • 发版时验证一次「用归档的 vmlinux 能否打开测试 vmcore」，比事故当天才发现强得多。

一份会被认真对待的上游报告：完整 dmesg（从开机第一行，不是只截 Oops 十行）、uname -a 与 /proc/cmdline、decode_stacktrace.sh 处理过的栈、Tainted 有 O/P 必须先在纯净内核上复现、能否在最新 mainline 复现、最小复现步骤、lspci -nnk 与 BIOS 版本、scripts/get_maintainer.pl 发给正确的人而不是群发。能只发 vmcore-dmesg.txt 就别发全量；-d 1 只裁零页时敏感级别完全不同，不能按常规流程流转。

决策树与 checklist

机器挂了 / 重启了，从零开始怎么查

五个阶段：确认 → 分类 → 取证 → 定位 → 止血。最常见的错误是跳过「确认」直接进「定位」，花三天查代码最后发现是一根内存条。

① 确认（3 分钟）

  • last -x · journalctl -k -b -1 · ls /var/crash · ipmitool sel / ras-mc-ctl --summary。硬件这一条最容易被跳过——随机崩溃先排除内存条，再 review 代码。
  • 云主机额外看实例事件，排除宿主机维护、热迁移、hypervisor 重启。日志末尾正常但墙上时间对不上，优先查云厂商事件，不是内核。

② 分类（对着 §1）

  • grep 最早一条：Oops / BUG at / lockup / blocked for / stall / oom-killer / Hardware Error。只信 [#1]。
  • Tainted：D/W 往前翻；M/B 转硬件；O/P 优先怀疑那个模块。

③ 取证

  • 有 vmcore → --dump-dmesg 先秒出日志，再上 crash。没 vmcore 但还活着 → SysRq w/l，配了 kdump 就 c。系统卡死但键盘还有反应时，不要按电源键。
  • 已经重启 → 只用 journalctl -k -b -1 里那段 Oops，同时立刻修 kdump。取证阶段不要开始推理。

④ 定位 / ⑤ 止血

  • 函数长度和 vermagic 对得上吗？版本不对的分析结果是有害的。多 CPU 划掉等锁的。毒值 6b/5a/dead。用 struct -o 验证偏移。
  • 先止血：隔离 / 回滚 / 卸模块。复盘必答：下次还会发生吗？下次能不能拿到现场？告警会不会更早响？流程侧见 故障处理手册。
  • 硬件这一条最容易被跳过：ras-mc-ctl、BMC SEL、温度、电源。随机地址 + 换机器不复现，先把内存条换掉再 review 代码。

线上「无故重启」从「先看 dmesg」开始答就落了下乘——重启之后 dmesg 里全是新启动的日志，上一次早没了。正确第一句是：先确定这是不是内核问题。last -x 看有没有配对的 shutdown，journalctl -k -b -1 看上次启动怎么结束，/var/crash 看有没有 vmcore。三条命令把五种原因分开，分错了后面全白干。

「拿不到现场」本身就是必须立刻修复的缺陷，优先级不低于那个崩溃。很多团队被同一个内核问题折磨几个月，根因不是问题太难，而是从来没有一次拿到过完整现场。

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础Oops 和 panic 有什么区别？Oops 之后系统还能正常用吗？

    Oops：内核检测到一个本不该发生的异常（最常见是解引用空指针或非法地址），打印一份现场快照，杀掉当前进程，然后返回调度器继续跑。panic：内核判定走不下去了，停机——按 kernel.panic 的秒数自动重启，为 0 则永远挂着。

    什么时候 Oops 会变成 panic：① 异常发生在中断上下文里（没有「当前进程」可杀，只能停机）；② 被杀的是 init（PID 1）；③ 显式设置了 kernel.panic_on_oops=1。

    「Oops 之后还能用」是危险的错觉
    被杀掉的那个上下文可能正持有自旋锁、正改内核链表改到一半、刚分配的资源还没登记。内核没有回滚机制，这些锁永远不会释放、这些资源永远泄漏。结果是：后续访问同一子系统的任务会一个个卡进 D 状态，几分钟后 hung task 刷屏，最终整机雪崩。
    实践结论
    有冗余的集群节点建议开 panic_on_oops=1——与其带病运行返回错误结果污染上游，不如立刻 panic 收 vmcore 让流量飘走。另外 Oops 输出里的 [#N] 是本次启动的第几次 Oops，只有 [#1] 是真相，后面的都是次生灾害。
  2. 基础RIP: 0010:my_func+0x2a/0x60 [mymod] 这一行怎么读？为什么用偏移而不是绝对地址？
    • 0010：代码段选择子，内核态的固定值，没有信息量。
    • my_func：出错指令所在的函数名。
    • +0x2a：出错指令相对函数入口的字节偏移。
    • /0x60：这个函数的总字节长度。
    • [mymod]：函数来自名为 mymod 的可加载模块；没有方括号则来自内核本体。
    为什么用偏移
    开启 KASLR 后每次启动内核代码的绝对地址都不同，贴绝对地址到 bug 报告里对别人毫无用处；而「函数名 + 函数内偏移」在同一份编译产物里永远稳定。附带好处：/0x60 这个长度是个免费的版本校验——如果你手上目标文件里该函数长度不是 0x60，说明拿错了版本，别浪费时间往下查。
    怎么变成源码行
    ./scripts/faddr2line mymod.ko my_func+0x2a/0x60（最推荐，能处理内联）；或 gdb -batch -ex 'list *(my_func+0x2a)' mymod.ko；或 objdump -dS 看上下文。三者都要求是同一次编译的产物——编译器版本、.config、优化等级任何一项不同，都会给出一个语法合理但内容完全错误的行号。
  3. 基础Oops 里的 Tainted: 是什么意思？为什么社区看到 O 就不太愿意接 bug？

    Taint（污染）标记记录「这个内核在崩溃之前已经处于什么非标准状态」，用一串字母表示。它的作用是快速判断这份报告值不值得信。

    • P：加载了专有（闭源）模块——社区基本不受理。
    • O：加载了 out-of-tree（树外）模块，即不在内核源码树里的模块。
    • E：加载了未签名模块。
    • D：本次启动已经 Oops 过——看到它就往前翻找 [#1]。
    • W：之前触发过 WARN_ON；M/B：发生过 MCE / 坏页（硬件信号）；F/R：模块被强制加载/卸载。
    为什么 O 让人却步
    不是傲慢，是成本。树外模块能做任何事：改内核数据结构、用未导出的内部接口、假设了已经变了的行为。当 RIP 落在内核本体某个函数上而 Tainted 有 O 时，最常见的真相是「你的模块把内核数据写坏了，内核只是在后来某个时刻踩到了坏数据」。维护者没有你的代码，无从判断。所以报 bug 前的标准动作是：卸掉所有树外模块（或用发行版原装内核）复现一次。
  4. 基础kdump 为什么能在内核已经死掉的机器上把内存现场保住？

    靠两件事，缺一不可：

    ① 提前预留一块「谁都不许碰」的内存
    开机时通过 crashkernel= 从物理内存里划走一块，生产内核从此看不见它（free 里会少掉这么多）。捕获内核只在这块内存里活动，因此它的运行不会覆盖第一内核的任何一个字节。预留必须在启动早期做——运行时再想找一块「肯定没人用」的连续物理内存，做不到。
    ② kexec 跳转不经过固件
    正常重启会经过固件复位流程，很多平台会做内存训练或让 DRAM 掉电——现场就没了。kexec 是纯软件跳转：设好新内核的入口、页表和参数直接跳过去，DRAM 一直在正常刷新。于是第一内核的每一个 task_struct、每一段 slab、整个 printk 环形缓冲，全都完好地躺在那里。

    捕获内核起来后通过 /proc/vmcore 读取旧内存，用 makedumpfile 裁剪压缩后落盘，落盘完成才真正重启。

    配了不等于生效
    必检两个文件：/sys/kernel/kexec_crash_size（预留字节数，为 0 就是没预留成功）和 /sys/kernel/kexec_crash_loaded（捕获内核是否已装载，必须是 1）。然后 echo c > /proc/sysrq-trigger 真触发一次，确认 /var/crash 里有文件落地。

10.2 中级（区分熟练度）

  1. 中级crashkernel 该预留多大？预留不够会出现什么现象？

    预留区要装下一个完整的捕获内核 + initramfs（含存储驱动、落远端时还要网络驱动）+ makedumpfile 的运行内存。经验值：256 MB 是下限；带复杂存储栈或走网络落盘的建议 512 MB 起；TB 级内存的机器因为 makedumpfile 要维护页位图，需求还会再涨。

    # 固定值
crashkernel=512M
# 按总内存分档（一份配置适配不同规格）
crashkernel=2G-64G:256M,64G-1T:512M,1T-:1G
# x86_64 大内存机：主体放 4G 以上，另留一小块低端内存给需要低 DMA 的设备
crashkernel=1G,high crashkernel=256M,low
    预留不够的现象非常有迷惑性
    panic 后机器直接重启，/var/crash 空空如也——因为捕获内核自己在启动过程中 OOM 或挂了，而这次崩溃是没人接的。现象和「kdump 根本没开」一模一样，很容易被误判成 kdump 配错了。控制台上通常能一闪而过地看到 OOM 或 initramfs 挂载失败。
    另外两个高频坑
    ① 预留失败：内存碎片化导致找不到连续区域（大内存机不写 ,high 时尤其常见）、grub 改了没重新生成、云镜像的命令行被 metadata 覆盖——所以必须查 /sys/kernel/kexec_crash_size 而不是只看 grub 配置。② 落盘目标不可用：path 指向的目录挂在 iSCSI / 复杂多路径存储上，而捕获内核的极简 initramfs 里没有对应驱动。
  2. 中级makedumpfile -d 31 里的 31 是什么意思？为什么它能把几百 GB 压到几 GB？

    -d 的参数是一个位掩码，每一位对应一类「可以扔掉的物理页」：

    bit值裁掉
    01全零页
    12非私有的 page cache
    24私有的 page cache
    38用户进程数据页
    416空闲页（在 buddy 空闲链表上的）

    31 = 1+2+4+8+16，即五类全裁。一台 512 GB 的机器里，绝大部分内存是 page cache、用户进程数据和空闲页——这些对排查内核崩溃毫无价值。保留下来的是内核代码、内核数据、slab、页表、task 结构，通常只有几个 GB，再叠加压缩（-l lzo / -c zlib / -p snappy）就更小了。

    顺带解决了合规问题
    bit 3 裁掉的正好是用户数据页，bit 1/2 裁掉 page cache——vmcore 里最敏感的东西（明文密码、密钥、用户数据、被缓存的文件内容）大部分就此消失了。这是「性能优化顺便解决安全问题」的经典案例。反过来说：如果为了追某个用户态相关的问题改用 -d 1，那份 vmcore 的敏感级别完全不同，不能按常规流程流转。
    被低估的一条命令
    makedumpfile --dump-dmesg vmcore out.txt——几秒钟就能把崩溃瞬间的完整内核日志抠成文本，不需要任何调试符号。很多事故到这一步就破案了，根本用不着开 crash。拿到 vmcore 的第一件事就该是它。
  3. 中级hung task detector 为什么只检测 D 状态的任务，S 状态不算？

    因为两种睡眠的语义完全不同。

    S（TASK_INTERRUPTIBLE，可中断睡眠）是「正常等待」的常态：sshd 等新连接可以等三个月，空闲服务器上 99.99% 的进程都在 S。把它纳入检测等于每两分钟刷屏几百条误报。

    D（TASK_UNINTERRUPTIBLE）表示「正在等待一个不可被信号打断的事件」，通常是块设备 IO、页回写、某些内核互斥锁。这类等待按设计就应该在毫秒到秒级返回——等满两分钟只有两种可能：底层设备真挂了，或者死锁了。两种都值得报警。

    检测机制
    khungtaskd 内核线程周期扫描全部任务，找「处于 D 状态且自愿+非自愿上下文切换计数与上次扫描时完全相同」的——说明这段时间它一次都没被调度过。超过 hung_task_timeout_secs（常见默认 120 秒）就打印它的栈。
    一个坑：hung_task_warnings
    默认只报 10 次就不再报了。长时间运行的机器上，「没再报了」很容易被误读成「问题好了」，其实只是配额用完。排查期间记得 sysctl -w kernel.hung_task_warnings=100。
    不等检测器的手工版
    ps -eo pid,stat,wchan:32,comm | awk '$2 ~ /^D/' —— wchan 列直接告诉你它睡在哪个内核函数上，常常一眼就够；再不够就 cat /proc/<pid>/stack 或 echo w > /proc/sysrq-trigger。
  4. 中级系统已经卡到 SSH 连不上、shell 敲不动，但键盘还有反应。你会怎么做？

    不要直接按电源键——那等于亲手销毁唯一的现场。用 magic SysRq，它在极高优先级的中断路径上直接处理，绕过用户态、调度器和文件系统，系统半死时通常仍然有效。

    1. Alt+SysRq+w：打印所有 D 状态任务的栈——这是取证的第一条命令。
    2. Alt+SysRq+l：通过 NMI 打印所有 CPU 当前的栈——找「谁在占着 CPU 不放」。
    3. Alt+SysRq+m：内存统计（怀疑 OOM 或内核内存泄漏时）。
    4. 配了 kdump 就 Alt+SysRq+c：主动 panic，拿一份完整 vmcore。
    5. 实在不行走 R-E-I-S-U-B：夺回键盘 → 终止进程 → 杀死进程 → 同步磁盘 → 只读重挂 → 重启。每步之间等几秒，比断电安全得多（不丢数据、不烂文件系统）。

    还能登进去时用 echo w | sudo tee /proc/sysrq-trigger，输出都进 dmesg。需要先启用：sysctl -w kernel.sysrq=1。

    为什么 SysRq 在系统卡死时还能工作
    它不依赖任何用户态进程、不依赖调度器（不需要「调度到某个处理程序」）、也不写文件系统（结果直接进内核环形缓冲）。唯一的前提是中断还能进来——所以 soft lockup 时它有效，而彻底 hard lockup 的那个 CPU 是响应不了的（那种情况只能靠 NMI 自动打出来的那段，或者靠 kdump）。

10.3 高级（体现深度）

  1. 高级拿到一个多核死锁的 vmcore，怎么在一堆 CPU 里找出真凶？

    核心思路一句话：找「不在等」的那个。

    bt 只能看到崩溃的那个任务，而它通常是受害者——比如 CPU 3 自旋等一把锁等到 hard lockup，真正拿着锁不放的是 CPU 5。所以要用 bt -a（每个 CPU 上正在跑的任务）配合 foreach UN bt（所有 D 状态任务）。

    判读方法
    受害者的栈顶是等待函数：queued_spin_lock_slowpath、osq_lock、__mutex_lock、rwsem_down_*、io_schedule。凶手的特征恰恰是「栈顶是正常的业务函数」——它拿着锁在干一件永远干不完的事（死循环、遍历成环的链表、等一个不会来的硬件应答、在临界区里睡眠）。所以做法是：先把所有「在等锁」的 CPU 划掉，剩下的一两个就是答案。
    辅助手段
    foreach bt | grep -c <func> 看聚集——「37 个任务同时卡在 mydev_ioctl」这个数字本身就是结论。ps 里行首的 > 标记正在占 CPU 的任务，UN 就是 D 状态。
    别把殡仪馆当案发现场
    bt 输出最上面几帧（machine_kexec / __crash_kexec / oops_end / exc_page_fault）是内核处理崩溃本身的代码，不是死因。真正的现场是 [exception RIP: ...] 那一行及其下面的帧。另外别忘了 mod -s mymod /path/mymod.ko 给自研模块加载符号，否则 dis 只有裸地址。
  2. 高级在内核崩溃现场看到 0x6b6b6b6b6b6b6b6b、0x5a5a5a5a、0xdead000000000100，各说明什么？

    这些是毒值（poison）——内核在特定时刻用固定字节填充内存，把「静默的数据损坏」变成「一眼能认出的证据」。

    • 0x6b 反复填充（最后一字节常为 0xa5）：已释放对象的填充。看到它 = use-after-free，对象已 kfree 但代码还在用。0x6b 是 ASCII 的 k，取 "kfree"。
    • 0x5a 反复填充：刚分配、尚未初始化的区域。看到它 = 忘了初始化就用，或越界读到了对象 padding。
    • 0xbb / 0xcc 填充的红区（red zone）：SLUB 在对象前后加的哨兵。红区被改写 = 缓冲区越界写。
    • 0xdead000000000100 / 0xdead000000000122：list_del 之后写进 next/prev 的链表毒值。看到它 = 重复 list_del，或使用了已摘链的节点。
    • 极小的非零值如 0x10：ZERO_SIZE_PTR，kmalloc(0) 的返回值——长度算成了 0 却当正常指针用。
    怎么开、怎么用
    启动参数 slub_debug=FZPU（F=一致性检查 Z=红区 P=毒化 U=记录分配/释放调用栈），或只对单个 cache 开 slub_debug=FZPU,kmalloc-256 以降低开销。U 是最值钱的一个 flag：报告会直接给出「Allocated in … / Freed in …」两段调用栈，几乎不用再推理。生产上只在追具体 bug 时对单个 cache 开。
    和 KASAN 的分工
    slub_debug 是事后发现毒值被改——知道被踩了，但不一定知道是谁在什么时候踩的。KASAN 是插桩检测，在越界/UAF 发生的那一瞬间就报，栈是精确的，而且报告直接给「踩的人 / 分配的人 / 释放的人」三段栈。代价是要重编内核、内存和 CPU 开销都是数倍级——测试环境用 KASAN，生产环境用 slub_debug。
  3. 高级虚拟机上频繁报 soft lockup，怎么判断是真问题还是误报？

    先理解误报的机制。soft lockup 的判据是「某 CPU 上的 watchdog 线程超过 2×watchdog_thresh（默认约 20 余秒）没被调度到」。但在虚拟机里，vCPU 只是宿主上的一个普通线程——宿主超卖时它可能被整个抢走几秒到几十秒。在 guest 内核看来，「时间凭空跳过去了」和「某个 CPU 卡了这么久」完全无法区分。此外热迁移的停机阶段、虚拟磁盘后端阻塞，都会造成同样的效果。

    两条判据
    ① 看 steal time。vmstat 1 的 st 列、top 里的 st、/proc/stat 第 8 个字段。持续明显非零（> 5%~10%）基本就能确定是宿主争抢。② 看栈有没有「形状」。真实的 soft lockup 会稳定地卡在同一个内核函数上（那个死循环）；误报的栈每次都不一样，甚至栈顶是 native_safe_halt（本来在 idle）这种荒谬的位置。「栈没有形状」= 误报——这和判断硬件问题的逻辑是同一个。
    内核已有的缓解及其局限
    KVM 提供 steal time 和「宿主曾暂停过本 guest」的标志，guest 内核报警前会检查它，若刚被暂停过就跳过这次报警。这能挡掉大部分热迁移和明显暂停导致的误报，但挡不住持续性的中度超卖——每次只被抢 3 秒、连抢 7 次，标志不一定被置上，累计却超了阈值。
    务实配置
    虚拟机上把 watchdog_thresh 放宽到 30，并且绝对不要开 softlockup_panic（否则会变成随机重启）；hardlockup_panic 可以保留，它极少误报。同时把 steal time 纳入监控告警——它才是这类问题的真实指标。注意反面风险：把阈值调到永远不报，问题还在，只是你看不见了。
  4. 高级内核栈为什么只有十几 KB？这对写内核代码有什么约束？

    每个内核线程（以及每个进入内核态的用户线程）都有独立的内核栈，x86_64 上常见是 16 KB（4 个页），不少 32 位平台是 8 KB。大小在编译时由 THREAD_SIZE 决定，运行时不可增长——和用户态那个默认 8 MB、还能自动扩展的栈完全不是一回事。

    为什么必须这么小
    ① 它是按线程数线性乘出来的常驻开销：一万个任务 × 16 KB = 160 MB 物理内存。② 这些页必须常驻、不能换出——换出的话，缺页处理本身又需要栈，会死循环。③ 历史上还要求物理连续（CONFIG_VMAP_STACK 之前），大块连续内存本身就稀缺。所以「小」不是疏忽，是必须付出的设计代价——代价转嫁给了内核开发者。
    三条硬约束
    ① 不许在栈上放 KB 级缓冲区：char buf[4096] 一口气吃掉四分之一。要用 kmalloc / per-CPU 缓冲 / 预分配池。② 不许无界递归：如果递归深度由外部输入决定（解析嵌套结构、遍历树），那就是一个可被远程触发的内核崩溃；必须改迭代或硬限深度。③ 注意隐式深度：文件系统嵌套（loop 设备上的 fs 上的 fs）、块设备栈叠（LVM over MD over dm-crypt）会让调用链比你想的深得多。
    怎么发现
    编译期：-Wframe-larger-than=（CONFIG_FRAME_WARN，默认阈值在 1~2 KB 量级）会对超标的栈帧告警，这能拦住一大半。运行期：开启 CONFIG_VMAP_STACK 后栈末尾有不可访问的守护页，溢出会立刻报 BUG: stack guard page was hit；没有它的老内核则表现为栈回溯完全乱码或静默踩坏相邻内存——后者是最难查的一类问题，因为崩溃点和真凶完全无关。
