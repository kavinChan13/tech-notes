01

驱动在哪：用户态 vs 内核态

你写的 open/read 最终落到谁身上

在用户态你调用 open("/dev/mydev")、read(fd, buf, n)、ioctl(fd, CMD, arg)。驱动就是内核里接住这些调用的一段代码：把「一次系统调用」翻译成「对某个硬件寄存器的读写 / 对某块内存的搬运」，再把结果交回用户态。换句话说，文件描述符那篇讲的 struct file::f_op 函数表，表里的函数指针正是驱动要填的坑。

生活类比：餐厅的后厨与传菜口

用户态程序是顾客，只能在传菜口（系统调用界面）点单；后厨（内核）不让顾客进——怕碰坏设备、也怕看到别桌的菜。驱动就是后厨里对接某台设备的专职厨师：顾客说"烤箱调 200 度"（ioctl），厨师去按物理旋钮（写寄存器）。顾客永远碰不到旋钮。

映射：顾客=用户进程 · 传菜口=syscall / VFS · 厨师=驱动 · 物理旋钮=MMIO 寄存器 · 不让进后厨=用户/内核地址空间隔离

1.1 内核态代码的五条铁律

进入内核态，用户态的很多"常识"立刻失效。这不是风格问题，而是硬约束。

约束为什么后果 / 替代
没有 libc / STL / printf内核不链接用户态 C 库用 printk、kmalloc、内核链表 list_head
栈极小且不可增长每个任务的内核栈固定几页（x86_64 一般 16 KB，32 位 ARM 一般 8 KB）禁止大数组 / 深递归，大缓冲一律 kmalloc；开 CONFIG_VMAP_STACK 后溢出会撞 guard page 变成 oops，而不是静默踩坏隔壁任务的栈
不能随意用浮点 / SIMD内核默认不在上下文切换时保存 FPU 状态，以省掉切换开销需要时显式 kernel_fpu_begin/end()（中间不能睡）；常规做法是改用定点 / 移位运算
错误必须用负 errno 返回内核没有异常，也没有 errno 这个全局变量失败 return -EINVAL;，成功返回 0 或正的字节数；返回指针的函数用 ERR_PTR() / IS_ERR()
一个 bug = 整机崩没有进程边界保护你空指针 → oops / panic，而不是 SIGSEGV

翻译成"肌肉记忆要改哪些"：左边是用户态张手就写的，右边是内核里的对应物。

用户态习惯内核里的写法关键差别

printfpr_info / dev_dbg写进内核日志环形缓冲，不是 stdout；有级别、要限速（见第 9 章）
std::vector / maplist_head、rb_root、xarray、hlist侵入式容器：节点内嵌在你的结构体里，挂链不额外分配内存
pthread_mutexmutex / spinlock_t / rw_semaphore选哪个取决于上下文能不能睡（见 1.3 与第 7 章）
assertWARN_ON_ONCE() / BUG_ON()WARN 打栈但继续跑；BUG_ON 直接 oops——能恢复的路径永远选 WARN
sleep(1)msleep()（可睡）/ udelay()（忙等）忙等版本白烧 CPU，只用于微秒级且确实不能睡的场合
浮点算比例整数 / 定点，div_u64()、DIV_ROUND_UP64 位除法在 32 位平台要用专门 helper，直接写 / 可能链接失败
名词：内核空间 / 用户空间指针

内核代码里裸指针分两种世界：内核指针（可直接解引用）和用户指针（标注 __user，绝不能直接解引用）。后者必须走 copy_from_user() 这类带检查的搬运函数，这是内核安全的第一道闸。

1.2 一次 read() 的完整时序

read 陷入内核后，VFS 靠 f_op 函数表分发到你的驱动；驱动读硬件、再 copy_to_user 回填，最后把字节数一路返回
图里最该带走的一点：驱动不是"程序"，而是一堆"回调"。内核在需要时调用你注册的函数，你几乎从不主动"运行"。心智模型是事件驱动 + 被内核调用，不是 main() 里的顺序流程。

1.3 全篇最该背下来的一张表：当前上下文能不能睡

驱动里九成的"偶发死机"都是同一个问题：在不能睡眠的上下文里调了会睡眠的函数。它经常不当场崩——只有恰好抢不到锁、恰好缺页时才真睡下去，于是压测两天没事、客户现场三小时就 hang。所以写每一行前先问："我现在在哪个上下文？"

上下文怎么进来的能否睡眠内存分配能用的锁copy_*_user
进程上下文（可抢占） 系统调用落到 read/write/ioctl；probe()；模块 init/exit；kthread 可以 GFP_KERNEL（可回收、可等待，成功率高） 全部：mutex / rwsem / spinlock / 完成量 可以
进程上下文但持自旋锁 / 关了抢占或中断 spin_lock() / preempt_disable() / local_irq_save() 之后 不可以 GFP_ATOMIC（不睡、只吃紧急保留池，更容易失败） 只能 spinlock / 原子操作；不能 mutex 不可以（可能缺页 → 睡）
软中断 / tasklet / NAPI poll 硬中断退出时或 ksoftirqd 里执行下半部 不可以 GFP_ATOMIC spin_lock()（同类软中断本核不重入，但可在别的核并行，锁还是要） 不可以
硬中断上半部（ISR） request_irq() 注册的那个函数被硬件触发 不可以 GFP_ATOMIC，且最好一个都不分配（buffer 在 probe 阶段预分配） spin_lock()（本核中断已关，无须再 irqsave） 不可以
threaded IRQ 线程 / workqueue request_threaded_irq() 的下半部；schedule_work() 可以 GFP_KERNEL 全部，包括 mutex 不可以——它是内核线程，没有用户地址空间
NMI（不可屏蔽中断） watchdog、perf 采样、硬件错误 不可以 不要分配 连普通 spin_lock 都不能拿（本核可能正持着它），只能用 NMI 安全的无锁结构 不可以
最容易被忽略的是最后两列的那一行差异：threaded IRQ 与 workqueue 能睡，但不能 copy_to_user——它拷的是 current->mm 指向的地址空间，而内核线程的 mm 是 NULL。数据必须先落到驱动自己的 kfifo，再由用户进程的 read() 拷出去。"谁调用的 read，就在谁的上下文里拷"，这是字符驱动数据通路的基本骨架。

1.4 别靠猜——让内核告诉你会不会睡

内核在每个可能睡眠的函数入口都埋了 might_sleep()，平时被编译掉，打开 CONFIG_DEBUG_ATOMIC_SLEEP 后就会在原子上下文里调用可睡函数的那一刻打出 BUG: sleeping function called from invalid context 和完整调用栈。判读三步：in_atomic(): 1 说明 preempt_count 非零（持自旋锁或关了抢占）；irqs_disabled(): 1 说明是关中断导致的；栈里第一个带 [模块名] 的帧才是你的锅。

不要用 in_atomic() / in_interrupt() 去做逻辑分支（"在中断里就用 GFP_ATOMIC，否则 GFP_KERNEL"）：preempt_count 在某些配置下并不总能反映真实情况，这样写等于把"我不知道自己在什么上下文"变成永久技术债。正确做法是在函数注释里规定调用上下文，并加一个 gfp_t 参数由调用者传下来。

1.5 错误处理：负 errno 与 ERR_PTR

规矩只有一条：返回 int 的函数失败给负 errno、成功给 0 或有意义的正值；返回指针的函数不能返回 -EINVAL，要用 ERR_PTR(-ENOMEM) 把错误码编进指针，调用侧用 IS_ERR() 判断、PTR_ERR() 取回。这个负值最终一路传回 VFS，变成用户态的 errno。

名词：ERR_PTR / IS_ERR / PTR_ERR

内核把地址空间最高的一小段（最后 4096 个地址）预留出来当"错误指针"：ERR_PTR(-ENOMEM) 就是 (void *)-12，永远不会是合法的内核对象。好处是一个返回值同时携带"成功的指针"和"失败的原因"。陷阱：错误指针不是 NULL——只写 if (!p) 会把错误当成功放过去，下一行解引用 0xfffffffffffffff4 直接 oops。

错误码的语义在内核里是有约定的，随手乱选会让用户态无法正确处理：

错误码什么时候返回用户态看到什么
-EINVAL参数值不合法Invalid argument
-ENOTTY未知的 ioctl 命令号（不要用 EINVAL）Inappropriate ioctl for device——用户态据此判断"设备不支持该命令"并回退到旧接口
-EFAULTcopy_*_user / get_user 失败，即用户给了坏指针Bad address
-EAGAIN设置了 O_NONBLOCK 且当前无数据可读Resource temporarily unavailable，配合 poll/epoll 重试
-ERESTARTSYS等待被信号打断，希望系统调用被自动重启看不到这个值：内核会重新执行系统调用，或转成 EINTR
-ENODEV / -ENXIO设备已被移除 / 该 minor 不存在No such device
-EPROBE_DEFER只在 probe() 里用：依赖的时钟 / GPIO / regulator 还没就绪用户看不到，内核把设备放回 deferred 队列（见第 5 章）
02

第一个内核模块

insmod / rmmod / dmesg 的最小闭环

驱动通常以可加载内核模块（LKM，.ko）的形式存在：编译成独立文件，运行时 insmod 装进内核、rmmod 卸载，不用重编内核也不用重启。骨架只有三件事：module_init() 注册加载入口（返回非 0 则模块不驻留）、module_exit() 注册卸载入口、MODULE_LICENSE("GPL") 声明许可（非 GPL 会 taint 内核，还用不了以 EXPORT_SYMBOL_GPL 导出的核心 API）。第 3 章的骨架就是把这三件事和 cdev 注册拼在一起。

模块不能用普通 gcc 编译——它必须针对特定内核版本的头文件和配置构建，靠内核源码树的 Kbuild：Makefile 里写 obj-m += mydev.o，再 make -C /lib/modules/$(uname -r)/build M=$PWD modules。

"编过了"不等于"能用"。下面每一条命令都对应一个必须确认的事实，按顺序走一遍，出问题时立刻知道断在哪一环：

步骤命令要确认什么
① 编译make产物不只 .ko：还有内核自动生成的 .mod.o 胶水与 Module.symvers
② 查身份modinfo mydev.ko加载前就能发现的问题都在这里：vermagic 必须与运行内核逐字一致，license 必须是 GPL
③ 加载sudo insmod mydev.ko无输出即成功；报错要配合下面的对照表去 dmesg 找真因
④ 确认驻留lsmod | grep mydev第三列 Used by 是引用计数，为 0 才能 rmmod
⑤ 看日志sudo dmesg -wH持续刷新 + 人类可读；调驱动时开一个专门的终端挂着它
⑥ 查内核视角ls /sys/module/mydev/refcnt 同 lsmod 第三列；holders/ 是"谁依赖我"；sections/ 给段地址，算 oops 偏移要用

2.3 模块参数：不重编就能调

module_param(buf_kb, int, 0644) + MODULE_PARM_DESC() 就能让 insmod mydev.ko buf_kb=64 生效，并在 /sys/module/mydev/parameters/ 下暴露成文件。

权限位不是随便填的：0644 意味着这个参数可以在运行期被 root 改掉，代码必须能承受它随时变化。像 buf_kb 这种"只在 init 时决定分配多大"的参数改了并不会重新分配缓冲，反而会让后续逻辑按新值访问旧缓冲、直接越界——它应该写 0444（只读）。适合 0644 的是 verbose 这类每次使用时才读一次的开关。
名词：交叉编译（Cross-Compile）

嵌入式几乎从不在目标板上编译。你在 x86 主机上用 ARM 工具链编出 ARM 的 .ko：make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -C $KDIR M=$PWD modules，其中 $KDIR 指向目标板同版本的内核源码/头。版本或配置（vermagic）对不上，insmod 会直接拒绝加载。工程细节见 Modern CMake 的 Cross-Compile。

字符设备三件套

设备号 + cdev + file_operations

Linux 把设备分三类，差别不只是"接口不同"，而是内核为它们准备的整条软件栈都不同——认清要写的是哪一类，才不会抄错模板：

三类设备的分工：字符设备最"裸"，块设备与网络设备各自站在一整套内核子系统之上

本文聚焦最常写的字符设备：让 /dev/mydev 能 open/read/write，需要三样东西对齐。

3.1 设备号、cdev 与 fops 的注册关系

主设备号定位驱动、次设备号区分实例；cdev_add 把号段登记到 cdev，cdev 再指向你的 fops——open() 就是沿这条链走一趟
用 alloc_chrdev_region 动态申请设备号而不是写死 major，是现代驱动的规矩：写死的 major 会和别的驱动冲突。用户态需要的映射交给 udev / /proc/devices 解决。

3.2 最小可用的字符设备骨架

下面这一块是全篇唯一需要通读的代码：把「模块入口 → 占设备号 → 绑 fops → 挂进内核 → 让 udev 建节点」这条链一次走完，并示范错误路径必须逆序回滚。后面各章的 ioctl / 中断 / DMA 都是往这个骨架上挂东西。

#include <linux/module.h>
#include <linux/fs.h>        // file_operations, alloc_chrdev_region
#include <linux/cdev.h>
#include <linux/uaccess.h>   // copy_to/from_user
#include <linux/device.h>    // class_create → udev 建节点

#define BUF_SZ 1024

struct mydev {
    struct cdev  cdev;      // 内嵌，靠 container_of 反查外层
    struct mutex lock;      // 保护 buf/len，见第 7 章
    char   buf[BUF_SZ];
    size_t len;
};

static dev_t          dev_num;   // major:minor
static struct class *cls;
static struct mydev *g;

// ── 回调 ①：每次 open() 都会进来，把私有对象挂到 file 上 ──────────
static int mydev_open(struct inode *ino, struct file *f)
{
    f->private_data = container_of(ino->i_cdev, struct mydev, cdev);
    return 0;
}

// ── 回调 ②：返回值是「实际字节数」，0 表示 EOF，负数才是错误 ──────
static ssize_t mydev_read(struct file *f, char __user *ubuf,
                          size_t n, loff_t *ppos)
{
    struct mydev *d = f->private_data;
    ssize_t ret;

    mutex_lock(&d->lock);
    if (*ppos >= d->len) { ret = 0; goto out; }        // EOF：cat 靠它退出
    n = min_t(size_t, n, d->len - *ppos);              // 允许短读
    if (copy_to_user(ubuf, d->buf + *ppos, n)) { ret = -EFAULT; goto out; }
    *ppos += n;
    ret = n;
out:
    mutex_unlock(&d->lock);
    return ret;
}

static const struct file_operations fops = {
    .owner   = THIS_MODULE,   // 有人 open 着就挡住 rmmod，见第 10 章
    .open    = mydev_open,
    .read    = mydev_read,
    .write   = mydev_write,   // 对称实现，copy_from_user
    .unlocked_ioctl = mydev_ioctl,   // 见第 4 章
    .llseek  = default_llseek,
};

// ── 注册：三层依次上线，「让设备可见」必须是最后一步 ──────────────
static int __init mydev_init(void)
{
    int ret;

    // ① 上户口：动态申请设备号，别写死 major
    ret = alloc_chrdev_region(&dev_num, 0, 1, "mydev");
    if (ret)
        return ret;

    g = kzalloc(sizeof(*g), GFP_KERNEL);
    if (!g) { ret = -ENOMEM; goto err_region; }
    mutex_init(&g->lock);      // 锁与缓冲要在设备可见之前就绪

    // ② 安电话：绑 fops，挂进字符设备映射表。这一步之后 open 就能进来了
    cdev_init(&g->cdev, &fops);
    g->cdev.owner = THIS_MODULE;
    ret = cdev_add(&g->cdev, dev_num, 1);
    if (ret) goto err_free;

    // ③ 挂门牌：发 uevent，udev 据此创建 /dev/mydev
    cls = class_create("mydev_class");
    if (IS_ERR(cls)) { ret = PTR_ERR(cls); goto err_cdev; }
    device_create(cls, NULL, dev_num, NULL, "mydev");

    pr_info("mydev: major=%d minor=%d\n", MAJOR(dev_num), MINOR(dev_num));
    return 0;

// 错误路径逆序回滚 —— 内核编程的必修课，漏一步就泄漏。
// devm_* / dmam_* 系列存在的意义就是把这段手写代码消灭掉（见第 5 章）。
err_cdev:   cdev_del(&g->cdev);
err_free:   kfree(g);
err_region: unregister_chrdev_region(dev_num, 1);
    return ret;
}

static void __exit mydev_exit(void)
{
    // 严格逆序：第一步就让设备不可见，最后才放号
    device_destroy(cls, dev_num);
    class_destroy(cls);
    cdev_del(&g->cdev);
    kfree(g);
    unregister_chrdev_region(dev_num, 1);
}

module_init(mydev_init);
module_exit(mydev_exit);
MODULE_LICENSE("GPL");
解释 container_of(ino->i_cdev, struct mydev, cdev)。它是内核实现"面向对象"的核心宏：已知内嵌成员 cdev 的地址，用编译期 offsetof 反算出外层结构体的首地址，零运行时开销。不用全局变量、天然支持多实例的关键就是它 + file::private_data——上面的骨架为了短才用了一个全局 g，真实驱动应当每个实例一份。

3.3 三层注册各管什么，漏一层什么症状

这三个调用常被当成"抄下来的样板"，但漏掉任何一层的症状都不一样，而且都很有迷惑性：

调用做的事漏了它的症状
alloc_chrdev_region() 向内核申请一段 (major, minor) 号并登记名字。此时只是"占号"，还没有任何行为 后面 cdev_add 用了一个没申请的号：可能和别的驱动撞车、互相覆盖，表现为"open 到了别人的设备"
cdev_init() + cdev_add() 把 fops 绑到 cdev，再把 cdev 挂进内核的字符设备映射表。这一步之后"设备号 → 你的回调"才通 节点存在、ls 看得见，但 open() 返回 ENXIO——号占了、没人认领
class_create() + device_create() 在 sysfs 里建出设备对象并发一个 uevent，udev 收到后在 /dev 下创建节点文件 驱动完全可用，但 /dev/mydev 不存在，只能自己 mknod 手建——这正是老教材里为什么总让你手动 mknod
一句话记住分工：alloc_chrdev_region 是"上户口"，cdev_add 是"安电话"，device_create 是"挂门牌"。前两个是内核内部的事，门牌才是用户态能看见的。所以"节点不存在"和"节点打不开"是两类完全不同的故障，先用 grep mydev /proc/devices 区分：能看到名字说明前两步没问题，问题在 udev / 权限。

3.4 file_operations 各方法的语义

file_operations 有几十个成员，字符驱动常填的就这几个。语义写错比不填更糟——不填时内核有合理的默认行为，写错则会让上层的 read 循环、poll 事件全部错乱：

方法被谁触发返回值语义（最容易写错的地方）
.open每一次 open()0 成功、负 errno 失败。会被调多次，不要在这里做"只该做一次"的初始化
.release最后一个引用消失时返回值基本被忽略。关键是 fork() / dup() 让多个 fd 共享同一个 struct file，此时 close() 只减引用计数、release 不会被调用；想"每次 close 都做点事"要用 .flush
.readread() / pread()返回实际拷贝的字节数；0 表示 EOF（用户态 while(read()>0) 靠它退出）；负 errno 表示失败。允许返回比请求少，这叫短读
.writewrite()返回实际写入字节数。返回 0 很危险：用户态的写循环会变成死循环。没空间且非阻塞应返回 -EAGAIN
.unlocked_ioctlioctl()未知命令必须返回 -ENOTTY。名字里的 unlocked 指"不再持全局 BKL"，不是"不需要加锁"
.pollselect / poll / epoll必须先 poll_wait() 挂等待队列，再检查状态。顺序反了会丢事件，进程永久阻塞
.llseeklseek()不实现时用内核默认行为。串口、传感器这类"流式"设备应显式设 no_llseek
.mmapmmap()只负责建立映射，之后的访问不再经过驱动。见第 4 章

3.5 验证：用 shell 当 fuzzer

加载后先用 grep mydev /proc/devices 确认内核侧注册成功，再 ls -l /dev/mydev 确认节点到位（第一个字符必须是 c；是 b 就说明你照着块设备模板抄了）。功能验证则不要只用自己写的测试程序。

解释为什么 echo / cat 比自己写的测试程序更能发现问题。cat 会反复 read 直到返回 0：如果 read 忘了推进 *ppos、永远返回同样的数据，cat 就无限刷屏——新手驱动最经典的现象，而"读一次就退出"的测试程序完全发现不了。同理 echo 多带一个换行、tee 可能分多次写，能暴露"假设一次 write 就是一条完整消息"。用 shell 当 fuzzer，成本极低、收益极高。
节点权限别用 chmod 666 糊过去，正式做法是写一条 udev 规则（KERNEL=="mydev", MODE="0660", GROUP="plugdev"）再把需要访问的用户加进该组。ioctl 通常等价于"任意写寄存器"，权限给宽了就是一个本地提权面。见 Linux 安全模型。
04

与用户态的数据通道

copy_*_user / ioctl / mmap 三种流派

驱动和用户态之间搬数据有三条路，选错会要么慢、要么不安全。

通道方向 / 语义开销适用
read/write + copy_*_user字节流，有拷贝每次一次内核↔用户拷贝常规数据流（串口、传感器采样）
ioctl带外控制命令 + 小结构体一次拷贝小数据配置寄存器、查询状态、模式切换
mmap把设备内存/缓冲映射进用户地址空间建立映射后零拷贝帧缓冲、大块 DMA 缓冲、高吞吐

4.1 copy_*_user 多做了什么，不做会怎样

用户指针永远不可信：它可能非法、可能指向已被换出的页、可能是攻击构造的内核地址。把 memcpy 和 copy_to_user 拆开看，后者多做的每一件事都对应一类真实事故：

copy_*_user 多做的事不做会怎样
① 地址空间校验（access_ok()）：确认地址落在用户空间范围内 用户把内核地址当 buffer 传进来，read() 就变成"把任意内核内存读给我"、write() 变成"往任意内核内存写"。最经典的本地提权原语
② 缺页兜底：拷贝指令登记在异常表（__ex_table）里，访问非法页时由 fixup 接管 用户传一个未映射的地址，内核取页失败——没有 fixup 就是 oops，整机崩溃，而不是杀掉这个进程
③ 临时解除硬件保护：x86 的 SMAP、ARM 的 PAN 在硬件层面禁止内核态直接访问用户页 在这类 CPU 上 memcpy 碰到用户地址会直接触发保护故障。好消息是新硬件上当场暴露；坏消息是老平台上它静默地"看起来能用"，等换了新 SoC 才集体崩
④ 可能睡眠：缺页时要等页换入 反过来说，它们不能在中断上下文或持自旋锁时调用（见 1.3 的表）

所以搬运用户数据只有三个合法入口，按数据形态选：

API用在什么数据上返回值语义
copy_to_user / copy_from_user任意长度的缓冲、结构体剩余未拷字节数，0 才是成功
get_user / put_user单个标量（int / 指针 / u64）0 或 -EFAULT，语义更直白，实现上是单条指令 + fixup，比走通用路径快
__copy_*_user_inatomic原子上下文里的"尽力一试"同上，但必须先 pagefault_disable()，且调用方要有失败重试路径

4.2 返回值语义：它不是错误码

这是全篇最容易写错、而且写错了还能跑的一处。它返回的是还没拷完的字节数：0 表示全部拷完，非 0 表示"有这么多字节没拷成"。

// ❌ 三种真实见过的错法
ret = copy_to_user(ubuf, kbuf, n);
if (ret < 0) return ret;      // 返回类型是 unsigned long，永远 >= 0，此判断恒不成立

return copy_to_user(ubuf, kbuf, n);  // 成功时返回 0 → 上层当成「读到 0 字节 = EOF」

copy_from_user(&req, uarg, sizeof(req));  // 压根不判返回值
do_something(req.len);                    // req 里可能是没被覆盖的内核栈残留

// ✅ 正确写法：只判「是否为 0」，字节数自己算
static ssize_t mydev_read(struct file *f, char __user *ubuf,
                          size_t n, loff_t *ppos)
{
    struct mydev *d = f->private_data;

    n = min_t(size_t, n, d->len - *ppos);
    if (copy_to_user(ubuf, d->buf + *ppos, n))
        return -EFAULT;          // 非 0 一律折叠成 -EFAULT
    *ppos += n;
    return n;                    // 返回自己算出来的字节数
}

// ✅ 回传给用户的结构体必须先清零：编译器插入的 padding 不会被
//    任何赋值语句覆盖，直接拷出去就是内核栈信息泄漏（大量 CVE 的模式）
static long mydev_get_stats(struct mydev *d, void __user *uarg)
{
    struct mydev_stats s = { };      // 或 memset(&s, 0, sizeof(s))

    s.nr_irq = d->nr_irq;
    s.bytes  = d->bytes;
    return copy_to_user(uarg, &s, sizeof(s)) ? -EFAULT : 0;
}

// ✅ 小标量用 get_user / put_user：语义是 0 或 -EFAULT，反而更直白
if (get_user(hz, (int __user *)arg))
    return -EFAULT;
if (hz < 1 || hz > 100000)     // 校验永远基于内核里的这份副本
    return -EINVAL;
"不判返回值"的危害比想象中大：copy_from_user 可能拷了一半才失败，目标缓冲的内容是不确定的。如果它是栈上结构体，里面就是上一次调用留下的内核栈数据，你接着把它当参数写进寄存器，行为完全随机。

4.3 ioctl：设备的"控制面"

read/write 是数据面，ioctl 是控制面。.unlocked_ioctl（不是老的 .ioctl）是现代接口，实现上就是一个 switch (cmd)：每个 case 里取参、严格校验、再动硬件；default 必须 return -ENOTTY。命令号不能随手取整数，要用内核宏把四个字段打包进一个 32 位数，这样不同驱动的命令不会撞车：

命令号 = 方向 + 参数大小 + 幻数 + 序号。因为 size 参与编码，参数类型一变命令号就变，内核 switch 自然匹配不上——这是特性不是缺陷

拆字段的宏是 _IOC_DIR/_IOC_TYPE/_IOC_NR/_IOC_SIZE。推荐的入口校验：先用 _IOC_TYPE(cmd) != MYDEV_MAGIC 挡掉不属于本驱动的命令，再进 switch。

解释"为什么方向反着看"。_IOR 里的 R 是 用户态在 read，所以内核是写方，驱动里要 copy_to_user；_IOW 是用户写、内核读，驱动里 copy_from_user。判断方法：把 ioctl(fd, CMD, &arg) 想成一次 read/write，方向和它一致。还要注意 dir 和 size 字段并不会被内核强制执行——它们只是"自描述的元数据"，实际校验仍然要靠你的 copy_*_user。

4.4 32/64 位混用：最难查的一类 ioctl 故障

典型场景：64 位内核跑一个 32 位编译的老用户态程序（嵌入式里非常常见——内核先升到 arm64，应用还是 armhf）。同一份头文件，两边算出来的命令号不一样：

结构体里的写法32 位用户态64 位内核后果
long / unsigned long4 字节8 字节_IOC_SIZE 不同 → 命令号不同 → switch 落到 default → 用户拿到 ENOTTY，看起来像"内核不支持这个命令"
结构体里含指针4 字节8 字节同上；即使命令号侥幸相同，指针值也要 compat_ptr() 转换
time_t / struct timeval随 libc 而变8 字节布局漂移，而且这个坑会随发行版升级突然出现
__u64 成员在 __u32 之后i386 上按 4 对齐，结构更紧凑按 8 对齐，中间多 4 字节 paddingsizeof 不同；即使强行对齐，字段偏移也错位，读到的值是移位后的垃圾

解决办法分两层，而第一层能让第二层的代码完全不必写：

✅ 第一层：把 UAPI 设计成两边一样

  • 共享头文件里只用固定宽度类型 __u32 / __u64
  • 8 字节成员放在 8 字节边界上，尾部用 __u32 __pad 显式补齐
  • 不放指针、不放 long / size_t / time_t、不放位域
  • 布局真的一致时 .compat_ioctl = compat_ptr_ioctl 一行搞定

❌ 第二层：ABI 已定型只能写 compat

  • 为 32 位布局单独定义一份 struct mydev_req32 和对应命令号
  • .compat_ioctl 里拷 32 位版本，再逐字段手工搬到 64 位结构
  • 结构体内的用户指针要过 compat_ptr()
  • 不填 .compat_ioctl：32 位程序的 ioctl 全部返回 ENOTTY
排查第一步：在 default: 分支里打一句 pr_warn_ratelimited("unknown ioctl cmd=%#x size=%u\n", cmd, _IOC_SIZE(cmd))，把用户态实际发来的 size 和你期望的 sizeof 一比，位宽问题立刻现形。

4.5 mmap：零拷贝的代价与用途

当吞吐是瓶颈（摄像头帧、GPU、采集卡），逐字节 copy_to_user 太贵。.mmap 回调把设备内存或内核缓冲映射进用户地址空间，之后用户读写就是访存，不再有系统调用、也不再经过驱动。实现上只有两句要紧的：用 pgprot_noncached(vma->vm_page_prot) 改页属性，再用 remap_pfn_range() 把物理页帧号铺进 vma。

映射设备寄存器一定要用 pgprot_noncached（或 write-combining）：走普通可缓存映射，CPU 会把对寄存器的写攒在 cache 里、把读命中旧值，硬件行为完全错乱。代价也要认清：零拷贝的另一面是"内核失去了每次访问的插手点"，同步、越界、生命周期都得靠约定（通常再加一个 ioctl 做"提交 / 归还 buffer"的握手）。
05

设备树与 platform_driver

别再把板级信息写死进 C 代码

x86 有 PCI/ACPI 能自动枚举硬件，但 ARM/RISC-V SoC 上大量外设（I²C 控制器、SPI、GPIO、UART、传感器）挂在片上总线，硬件无法自我描述——寄存器基址、中断号、时钟在哪，CPU 不知道。历史上这些信息硬编码在内核的 board file 里，几千个 board file 让 ARM 内核树臃肿不堪。设备树就是把它们从代码里抽出来，变成一份独立的数据文件。

生活类比：装修图纸 vs 把家具焊死在墙上

旧做法（board file）像把家具焊死在墙上：换个户型就得砸墙重焊（改内核重编）。设备树像一份可替换的装修图纸：墙体（内核 + 驱动）不动，只换图纸（.dtb）就能描述"这块板子上，UART 在地址 0x..、用中断 32、接 24MHz 时钟"。

映射：墙体=内核/驱动逻辑 · 图纸=设备树 dts/dtb · 家具位置=reg/interrupts/clocks · 换户型不砸墙=同内核多板复用

5.1 一个节点 + 一次匹配

节点描述硬件，驱动声明自己认哪个 compatible，内核负责撮合。这两半必须一起看才有意义，所以放在同一块里：

/* ── board.dts：描述「板子上有什么」，不描述「怎么驱动它」 ────────── */
myperiph@40001000 {
    compatible = "acme,myperiph-v1";      // ← 匹配键，惯例是「厂商,型号」
    reg = <0x40001000 0x1000>;            // 寄存器基址 + 长度
    interrupts = <GIC_SPI 42 IRQ_TYPE_LEVEL_HIGH>;
    clocks = <&clk_periph>;               // 引用时钟控制器提供的时钟
    acme,sample-rate-hz = <48000>;        // 自定义属性必须带厂商前缀
    status = "okay";                      // SoC 的 .dtsi 常默认 disabled！
};

/* ── 驱动侧：probe 里把上面每一项取出来 ───────────────────────── */
static int myperiph_probe(struct platform_device *pdev)
{
    struct device *dev = &pdev->dev;
    struct myperiph *p;
    int ret;

    // devm_ 前缀：probe 失败或设备移除时内核自动逆序释放，
    // 第 3 章那种手写 goto 回滚就不需要了
    p = devm_kzalloc(dev, sizeof(*p), GFP_KERNEL);
    if (!p)
        return -ENOMEM;

    // ① reg → ioremap 后的虚拟地址，只能交给 readl/writel
    p->regs = devm_platform_ioremap_resource(pdev, 0);
    if (IS_ERR(p->regs))
        return PTR_ERR(p->regs);

    // ② interrupts → Linux 中断号（不等于 dts 里写的硬件号）
    p->irq = platform_get_irq(pdev, 0);
    if (p->irq < 0)
        return p->irq;

    // ③ 自定义属性。读不到就保留代码里的默认值，别直接失败
    of_property_read_u32(dev->of_node, "acme,sample-rate-hz", &p->sample_rate);

    // ④ clocks → 依赖资源。时钟驱动可能比你晚初始化，此时返回 -EPROBE_DEFER，
    //    必须原样往上传；dev_err_probe 会对 defer 自动降级成 debug 日志
    p->clk = devm_clk_get(dev, NULL);
    if (IS_ERR(p->clk))
        return dev_err_probe(dev, PTR_ERR(p->clk), "failed to get clock\n");
    ret = clk_prepare_enable(p->clk);   // 拿到还不够，得真的打开
    if (ret)
        return ret;

    platform_set_drvdata(pdev, p);
    dev_info(dev, "probed, rate=%u irq=%d\n", p->sample_rate, p->irq);
    return 0;
}

// 匹配表：.data 挂型号差异表，一个驱动就能支持多个型号
static const struct of_device_id myperiph_of[] = {
    { .compatible = "acme,myperiph-v1", .data = &cfg_v1 },
    { .compatible = "acme,myperiph-v2", .data = &cfg_v2 },
    { }
};
MODULE_DEVICE_TABLE(of, myperiph_of);   // 让 modprobe 能按 compatible 自动装

static struct platform_driver myperiph_drv = {
    .probe  = myperiph_probe,
    .driver = { .name = "myperiph", .of_match_table = myperiph_of },
};
module_platform_driver(myperiph_drv);   // 展开 init/exit，省样板
of_device_get_match_data() 能把命中的那条 .data 取回来，这是一个驱动支持多个型号的标准做法：把型号差异（寄存器偏移、FIFO 深度、有无 DMA）做成常量表挂上去，probe 里读出来存进私有结构，代码里就不需要 if (是 v1) ... else if (是 v2) 这种会越写越长的分支。

compatible 还可以写一串并从具体到通用排列（如 "ti,am3352-uart", "ti,omap4-uart"），内核按顺序找第一个有驱动的。这个顺序有实际意义：

情况结果为什么这样设计
有专门的 ti,am3352-uart 驱动用它，可以启用这颗芯片特有的功能精确匹配优先
只有通用的 ti,omap4-uart 驱动降级用通用驱动，功能少一点但能工作硬件兼容性的降级机制：新芯片在旧内核上也能跑起来
两个都没有节点在设备树里，但没有驱动认领，probe 永远不被调用不是错误：一块板上很多节点本来就不需要驱动

5.2 从上电到 probe：匹配链与 defer 回路

匹配链的五环各有一个可直接查看的证据；probe 的三种返回值分别走向「绑定成功 / 回延迟队列 / 永久放弃」
名词：EPROBE_DEFER（延迟探测）

probe 常常依赖别的子系统：时钟、regulator、GPIO 控制器、PHY。而设备的初始化顺序并不受你控制——你的 probe 可能在时钟驱动之前就跑了。这时 devm_clk_get() 返回 -EPROBE_DEFER，正确做法是原样往上返回。两个典型错误：当普通错误打一条 dev_err（启动期刷出一堆吓人的假错误，应该用 dev_err_probe()）；改写成 -ENODEV 返回——设备就永久不会再被探测，症状是"冷启动偶尔起不来、重启一次又好了"。

5.3 排查："probe 到底跑了没有"

按图里 ①→⑤ 的顺序逐层缩小，每一环对应一条命令：ls /proc/device-tree/（节点在不在）→ cat .../compatible（字符串对不对；数值属性是大端二进制要 hexdump -C，或干脆 dtc -I fs -O dts /proc/device-tree 反编译整棵树）→ ls /sys/bus/platform/devices/ → ls /sys/bus/platform/drivers/myperiph/（出现设备名的符号链接才算绑定成功）→ cat /sys/kernel/debug/devices_deferred。

命中率从高到低：① 板子上刷的还是旧 dtb（改了 dts 没重新部署，占一半以上）；② 节点写了 status = "disabled"——很多 SoC 厂商的 .dtsi 默认把外设全关掉，板级 dts 必须显式 status = "okay"；③ compatible 差一个字符；④ 驱动压根没加载；⑤ 卡在 EPROBE_DEFER 等一个永不出现的依赖。提效技巧：往 drivers/myperiph/unbind 再 bind 写设备名，可以重走一遍 probe，不用重启板子。
06

中断：上半部与下半部

为什么中断处理要"拆两半"

硬件事件（数据到了、传输完成、按键按下）通过中断异步通知 CPU，CPU 立刻暂停当前工作跳去执行中断服务程序（ISR）。问题在于：中断处理期间通常关着同优先级中断，处理越久，系统对其它事件越迟钝、延迟抖动越大。所以内核把中断处理拆成两半。

名词：中断上下文（interrupt context）

ISR 运行在"中断上下文"里——不属于任何进程、不能睡眠。它借用被打断者的内核栈运行，却没有自己的 task_struct，也就没有"稍后被唤醒继续执行"的载体，一旦睡眠就再也回不来。这是内核编程最容易踩的红线。

6.1 拆两半，以及四种下半部的取舍

上半部只做"必须马上做"的三件事；下半部四种机制沿"能否睡眠 × 延迟可控性"这条轴排开，新驱动默认落在 threaded IRQ
图里最反直觉的一条：softirq 延迟最小，但普通驱动根本选不到它——它的类型是编译期静态枚举的，外部模块无法新增，只能借用网络 / 块层已有的那几个。所以现实中的选择其实只在 threaded IRQ 与 workqueue 之间。网卡驱动的收包路径为什么长成那样，见 内核网络栈 · 网卡与驱动层。

6.2 现代写法：threaded IRQ

与其手动管理 tasklet/workqueue，现代驱动直接用线程化中断：一个函数做上半部（quick check），一个函数做下半部（跑在专属内核线程，可以睡眠）。这也是 PREEMPT_RT 让中断可抢占、压低延迟的基础。上半部的返回值直接决定内核接下来做什么：

返回 irqreturn_t含义不这样返回的后果
IRQ_NONE"这次中断不是我的"，让内核继续问同一条线上的其它 handler无条件返回 HANDLED 会掩盖同线上别的设备的故障，内核的 nobody-cared 保护永远不触发
IRQ_HANDLED已经处理完，不需要下半部—
IRQ_WAKE_THREAD已应答硬件，唤醒 thread_fn 去做耗时的活只在 request_threaded_irq 注册了线程时有效；没注册就等于没人处理
 
// ── 上半部：中断上下文。只做三件事，然后立刻返回 ──────────────────
static irqreturn_t myperiph_isr(int irq, void *data)
{
    struct myperiph *p = data;
    u32 st = readl(p->regs + REG_STATUS);

    // ① 认领。共享中断线上少了这一句，会掩盖同线上别的设备的故障：
    //    你声称「处理了」，内核的 nobody-cared 保护就永远不触发。
    if (!(st & INT_PENDING))
        return IRQ_NONE;

    // ② 清中断标志。电平触发下不清，中断线一直有效 → 中断风暴。
    //    读/清的先后顺序按硬件手册来，有些控制器要求「先读后清」。
    writel(INT_PENDING, p->regs + REG_ACK);

    // ③ 交给下半部线程。绝不在这里 mutex_lock / msleep /
    //    kmalloc(GFP_KERNEL) / copy_to_user——它们都可能睡。
    return IRQ_WAKE_THREAD;
}

// ── 下半部：内核线程上下文，可以睡眠 / 拿 mutex / 走 I²C ──────────
static irqreturn_t myperiph_thread(int irq, void *data)
{
    struct myperiph *p = data;

    // 搬运并解析数据、写入 kfifo，最后唤醒阻塞在 read() 上的进程。
    // 注意这里「能睡」但仍然「不能 copy_to_user」：内核线程没有
    // 用户地址空间（current->mm == NULL），见 1.3 那张表。
    kfifo_in(&p->fifo, p->hw_buf, len);
    wake_up_interruptible(&p->wq);   // 顺序必须是「先放数据，后唤醒」
    return IRQ_HANDLED;
}

// ── probe 里注册。devm_ 版本会在设备移除时自动 free_irq ──────────
ret = devm_request_threaded_irq(dev, p->irq,
                                myperiph_isr,      // 上半部，可为 NULL
                                myperiph_thread,   // 下半部线程
                                IRQF_ONESHOT,      // 上半部为 NULL 时是强制要求
                                "myperiph",        // 显示在 /proc/interrupts 末列
                                p);                // dev_id：传给 handler，也是 free_irq 的凭据

6.3 request_irq 的 flags

flag含义什么时候必须加
IRQF_SHARED允许多个驱动共享同一条中断线PCI 等中断线紧张的场景。加了它，handler 必须先认领、不是自己的返回 IRQ_NONE，且 dev_id 不能为 NULL（free_irq 靠它区分注册者）
IRQF_ONESHOT直到线程处理函数返回，中断线一直屏蔽用 request_threaded_irq 且上半部传 NULL 时是强制要求（否则注册返回 -EINVAL）：电平触发的中断在标志被清掉前一直有效，没人清又不屏蔽就会在线程跑起来前无限重入
IRQF_TRIGGER_RISING 等指定边沿 / 电平触发方式通常不要在代码里写——触发方式是板级属性，该由 dts 的 interrupts 描述，写死会和 dts 冲突并打 warning
IRQF_NO_SUSPEND系统挂起期间仍保持使能唤醒源、时钟中断。普通外设不要加，会妨碍系统进入低功耗
IRQF_PERCPU该中断是每 CPU 一份的本地定时器、per-CPU 的 IPI；用了就不能再指望 smp_affinity
IRQF_NOBALANCING不参与 irqbalance 的自动迁移需要把中断钉在特定核上时

这是中断问题的第一现场。每一行从左到右是：Linux 中断号、每个 CPU 上的累计次数、中断控制器（如 GICv3）、硬件中断号、触发方式（Level / Edge）、以及你 request_irq 时给的 devname。末尾几行 IPI* 是核间中断，不属于任何设备。

观察到的现象含义 / 该查什么
找不到自己的 devnamerequest_irq 没成功，或 probe 没跑到那一步。回到 5.3 查绑定

生产案例：某 SoC 的采集卡驱动压测半小时后整机变慢，%hi（硬中断时间）接近 40%，而 /proc/interrupts 显示中断每秒涨约 90 万次、实际数据率只有每秒 3000 帧。根因是这颗芯片的 ACK 寄存器写 1 清零且要求写入前先读一次，代码少了那次读、标志没被真正清掉。修复只有一行，关键在于把"中断次数"和"业务事件次数"对上，发现差了 300 倍——这个比值是判断中断风暴最直接的证据，比看 CPU 占用有效得多。
07

内核并发与竞态

选错锁 = 死锁或数据损坏

内核天生高度并发：多核同时进你的驱动、中断随时打断进程上下文、抢占让内核代码中途被换出。共享数据（缓冲、计数、寄存器影子值）必须保护。

这一节只讲最常用的那几把锁。完整的内核同步体系——READ_ONCE 为什么不能用 volatile 替代、内存屏障为什么必须成对、seqlock 与 per-CPU 变量、RCU 的宽限期原理与陷阱——见 内核同步原语与 RCU。写驱动而不理解屏障与 RCU，写出来的竞态往往要到量产才暴露。

7.1 三个并发来源，各配一把锁

抽象地讲"要加锁"没有用。驱动里的并发只有三个来源，认出来就知道该用什么：

三个来源决定锁的种类：只有进程上下文 → mutex；中断也要访问 → spin_lock_irqsave；SMP 是"为什么必须有锁"本身
口诀：临界区会睡就用 mutex；不能睡（或中断里）就用 spinlock，且临界区越短越好。自旋锁持有期间睡眠是内核头号 bug——持锁者被换出、别的核死等，直接 hang。还要记住 spinlock 顺手关掉了抢占：持锁期间不能睡眠、不能触发缺页、不能 copy_*_user、不能 kmalloc(GFP_KERNEL)，持锁时长要用微秒衡量。
场景用哪把锁
只在进程上下文、临界区可能睡眠mutex
只在进程上下文、临界区极短不睡spin_lock
数据被硬中断处理也访问spin_lock_irqsave
数据只被 softirq / tasklet 访问spin_lock_bh
读多写极少（配置表、设备列表）RCU / seqlock（读者近乎无锁）
纯计数器atomic_t / per-CPU 变量（累加后读时求和，往往快一个数量级）

四个 spin_lock 变体的差别只在"额外关掉了什么"，选错的后果各不相同：

变体额外做的事什么时候用 / 不用
spin_lock只关抢占数据不被任何中断路径访问时。被硬中断访问就是自死锁
spin_lock_irqsave关本核中断，并保存 / 恢复原中断状态库与驱动代码一律用它——它不假设调用者原本开着中断
spin_lock_irq关中断，解锁时无条件开中断❌ 少用：调用者本来关着中断的话，它会悄悄破坏调用者的前提
spin_lock_bh只关软中断数据被 softirq / tasklet 访问、但不被硬中断访问
PREEMPT_RT 会改变这套直觉。RT 内核里 spinlock_t 被换成可睡眠的 rt_mutex（带优先级继承），真正忙等的只剩 raw_spinlock_t，要兼容 RT 的驱动不能再假设"spinlock 临界区一定是原子的"。另一件必须做的事是打开 CONFIG_PROVE_LOCKING（lockdep）跑测试——它能自动发现锁序反转、irq-safe 与 irq-unsafe 混用，这类问题靠人工评审几乎抓不住。

7.2 唤醒丢失：阻塞读为什么必须用 wait_event

还有一类竞态不涉及数据损坏，而是让进程永久睡死。它是阻塞读的骨架必须照抄的原因：

wait_event_interruptible 的价值全在"挂队列 → 判条件 → 才睡"这个原子序列上；永远不要自己手写 set_current_state + schedule

落到代码上只有四行要紧的：if (f->f_flags & O_NONBLOCK) return -EAGAIN;；wait_event_interruptible(d->wq, !kfifo_is_empty(&d->fifo))；它返回非 0 说明被信号打断，此时 return -ERESTARTSYS；最后 kfifo_to_user() 拷给用户（内部调 copy_to_user，只能在进程上下文用——而 read() 正是）。

被信号打断时要返回 -ERESTARTSYS 而不是 -EINTR：前者让内核在信号处理完后自动重新执行这次系统调用，后者会把 EINTR 扔给用户态，逼着每个调用方都写重试循环。用 _interruptible 版本同样重要——否则 Ctrl+C 杀不掉卡在你驱动里的进程。

竞态来源具体场景手段
移除 / 卸载时仍在使用 rmmod 或热插拔时，还有进程阻塞在 read 里，还有 work 排在队列里，中断还没 free .owner = THIS_MODULE 只挡住"有人 open 着"；异步引用靠 exit 路径逆序拆除并用 *_sync 版本（见第 10 章）

MMIO 与内存的顺序 填好 DMA 描述符再写寄存器"敲门铃"；或先写地址寄存器再写启动寄存器 寄存器访问一律 readl() / writel()（含该架构所需屏障）；描述符在普通内存里，和后面那次 writel 之间没有天然顺序，中间必须加 dma_wmb()

08

DMA 与一致性内存

让外设自己搬数据，但小心 cache

DMA（直接内存访问）让外设绕过 CPU 直接读写内存：网卡收包、摄像头写帧、磁盘控制器搬扇区都靠它。CPU 只需"告诉外设缓冲在哪、多大"，然后去干别的，传输完外设发中断。它是高吞吐外设的命脉，但引出两个硬核问题：地址与cache 一致性，而两者的根源都是同一件事——CPU 和设备走的不是同一条路。

8.1 两条数据路径：MMIO 与 DMA

MMIO 是 CPU 主动去戳寄存器（绕过 cache）；DMA 是设备直接读写物理内存（绕过 CPU 的 cache）——一致性问题正诞生于这个"各走一边"
名词：总线地址 vs 物理地址 vs 虚拟地址

CPU 用虚拟地址，经 MMU 转成物理地址；但外设看到的是总线 / DMA 地址——有 IOMMU 或地址偏移时它和物理地址并不相等。所以既不能把 kmalloc 的内核虚拟地址直接给外设，也不能自己 virt_to_phys，必须用 DMA API 拿到 dma_addr_t。

8.2 一致性映射 vs 流式映射

一致性（coherent）映射

  • dma_alloc_coherent() / dmam_alloc_coherent()
  • 映射成 uncached，双方看到的永远一致，免手动同步
  • 适合小而被双方频繁访问的控制结构：描述符环、状态字
  • 代价：CPU 访问很慢，拿它当大数据缓冲是常见的性能事故
  • 大量小块别反复调它（按页分配，几十字节的描述符浪费整页），改用 dma_pool_*

流式（streaming）映射

  • dma_map_single() / dma_map_sg()，用完即 unmap
  • 保留 cache、性能好；但要声明方向并遵守所有权规则
  • 适合一次性大块传输（网络包、磁盘 IO、采集帧）
  • buffer 必须物理连续可 DMA：vmalloc 内存和栈上数组都不行
  • dma_map_sg() 之后只能用 sg_dma_address/len() 读地址长度——有 IOMMU 时内核会合并段，nents 比传入的少

方向不是文档注释，而是告诉内核在什么时机做 clean 还是 invalidate。写反了在无一致性硬件的平台上就是偶发数据损坏，而且往往只在特定 cache 状态下出现：

方向语义内核在什么时机做什么
DMA_TO_DEVICE发送：CPU 填好、设备来读map 时 clean——把脏 cache 行写回内存，否则设备读到旧值
DMA_FROM_DEVICE接收：设备写入、CPU 来读unmap 时 invalidate——丢弃可能过期的 cache 行，否则 CPU 命中旧行
DMA_BIDIRECTIONAL双向（原地改写）两头都做，最贵。别图省事默认选它

8.3 流式映射的所有权规则

流式映射最容易违反的不是"方向"而是所有权：映射期间这块 buffer 属于设备，CPU 不许碰。画成时间轴就很清楚：

map / unmap 是所有权的交接点，也正是内核做 cache 维护的时机；在"设备拥有"区间里访问 buffer 是流式 DMA 最常见的错误
还有两条配套规则一样会咬人。第一，dma_map_single() 的返回值必须用 dma_mapping_error() 判断，不能只判 0——某些平台上 0 是合法的 DMA 地址。第二，probe 里要先 dma_set_mask_and_coherent() 声明本设备的寻址能力再做任何映射，否则内核按默认处理，可能给你一个设备地址线根本够不到的高地址。

8.4 IOMMU 与 swiotlb

名词：IOMMU / SMMU

给设备用的 MMU：设备发出的地址先经它翻译，才落到物理内存。ARM 上叫 SMMU，Intel 叫 VT-d，AMD 叫 AMD-Vi。有了它，dma_addr_t 就是纯粹的设备侧虚拟地址，和物理地址毫无关系。

IOMMU 带来的具体价值代价
隔离与保护有 bug 或被攻破的设备无法 DMA 到任意物理内存。这是把设备直通给虚拟机（VFIO / SR-IOV）的前提——没有 IOMMU，直通等于把整台机器的内存交给客户机每次映射都要建 / 拆页表项
分散内存的聚合物理上零散的多个页可映射成设备看到的一段连续地址，不支持 scatter-gather 的老设备也能传大块数据—
突破地址位宽限制32 位设备也能访问 4 GB 以上的内存，不必再 bounce—
——IOTLB 失效开销：解除映射要刷 IOTLB，高频小映射时开销可观。iommu.strict=0（延迟批量失效）在安全性和吞吐之间取舍
没有 IOMMU、设备地址位宽又不够时，内核会启用 swiotlb（bounce buffer）：先把数据拷进一块低地址的保留内存，再让设备访问它。它是正确性的兜底，但每次传输多一次拷贝，症状是"功能正常但吞吐上不去"。判断方法是看启动日志里的 software IO TLB: mapped，以及压力下出现 swiotlb buffer is full（bounce 区被打满、传输开始失败）。修法是把 dma_set_mask 声明正确、或改用支持 scatter-gather 的传输方式，而不是一味调大 swiotlb=。

8.5 这类 bug 怎么查

DMA 错误的画像非常一致：只在高压力下偶发、损坏位置随机、加一行 printk 就复现不了（时序和 cache 状态都变了）。所以不要靠加日志，要靠内核自带的校验：

手段能抓到什么
CONFIG_DMA_API_DEBUG内核记录每一次 map/unmap 并校验：unmap 时的地址长度方向是否和 map 时一致、有没有泄漏未 unmap 的映射、有没有重复映射、有没有映射栈内存。开发期应常开，它是这一整类问题最有效的单一工具
ARCH_DMA_MINALIGN 对齐检查DMA buffer 必须独占 cache line。kmalloc 对足够大的请求已保证对齐，但把 buffer 作为结构体成员时要自己加 ____cacheline_aligned
把描述符环 dump 出来在完成中断里检查 OWN 位是否已被硬件清掉。CPU 看到的 OWN 还是 1 而硬件已报完成，就是缺屏障或缺 dma_rmb()
先在一致性映射上跑一遍把流式映射临时换成 dma_alloc_coherent，问题消失就基本确认是 cache 同步 / 所有权问题而非逻辑错误。这是最快的二分法
生产案例：某 ARM64 板的 SPI 采集驱动低速正常，采样率提到上限后每隔几分钟出现一帧的前 32 字节是上一帧的内容。CONFIG_DMA_API_DEBUG 没报错（map/unmap 配对），最终定位是接收 buffer 前面紧跟着一个每帧都更新的计数器，两者落在同一条 64 字节 cache line 上：dma_unmap 的 invalidate 丢掉了 CPU 刚写的计数器，反过来计数器的回写又覆盖了 DMA 写入的前 32 字节。加 ____cacheline_aligned 即可。"前 N 字节固定出错、N 恰好小于一条 cache line"就是对齐问题的指纹。

9.1 printk 的级别，以及为什么必须限速

printk 有 8 个级别。日志全部进内核环形缓冲（dmesg 都能看到），但只有级别数值小于 console_loglevel 的才会往控制台（串口 / VGA）输出——这是嵌入式"看不到 log"的头号排查点。门槛看 /proc/sys/kernel/printk 的第一个数，临时提高就往它 echo 8，或用启动参数 ignore_loglevel。

级别宏什么时候用
0–2 EMERG / ALERT / CRITpr_emerg / pr_alert / pr_crit系统即将不可用、或需要立即处理的严重故障。驱动里基本用不到
3 KERN_ERRpr_err / dev_err真正的错误：probe 失败、硬件不响应、DMA 映射失败
4 KERN_WARNINGpr_warn / dev_warn不正常但能继续（丢了一帧、参数被夹到合法范围）。多数发行版控制台的默认门槛
5–6 NOTICE / INFOpr_notice / pr_info正常的里程碑：probe 成功、协商到了什么速率。一次加载只该有一两条
7 KERN_DEBUGpr_debug / dev_dbg调试细节。默认编译后不产生任何代码，除非开了 CONFIG_DYNAMIC_DEBUG（见 9.2）
日志会淹掉系统，这不是夸张而是能算出来的。串口控制台按 115200 波特算约 11 KB/s，一条 80 字节的日志就要 约 7 ms，而且 printk 往控制台输出的那一段是同步的。中断处理里每次都打一条、中断每秒来 1000 次，光输出日志就要 7 秒——CPU 被彻底堵死，接着是 soft lockup，然后整机重启。而这个故障看起来完全不像日志导致的，很多人会去查中断处理逻辑。

所以高频路径上有三种正确写法：限速 dev_err_ratelimited()（默认约"每 5 秒最多 10 条"）；只打一次 dev_warn_once() / WARN_ONCE()，适合"这个条件成立说明配置有问题"的一次性告警；完全不走控制台 trace_printk()，写进 ftrace 环形缓冲，开销低一个数量级以上、中断上下文可用（但它会在 dmesg 里打一大段警告横幅，提醒你别留在正式代码里）。

选级别有一条实用判据：如果这条日志会因为"外部输入不合法"而被触发，它就不能是 pr_err，也不能不限速。用户态可以循环调一个非法 ioctl，每次都打 error 就等于给了任何本地用户一个刷满内核日志、把真正重要的信息挤出环形缓冲的手段。这类路径要么 ratelimited，要么降到 dev_dbg。

9.2 动态调试：不重编就能打开某几行日志

pr_debug / dev_dbg 在开了 CONFIG_DYNAMIC_DEBUG 的内核上是可以逐条开关的——每个调用点在内存里有一个开关位，默认关闭、开销接近于零。往控制文件 /sys/kernel/debug/dynamic_debug/control 里写一行「选择器 + 标志」即可：

写进 control 的内容作用
module mydev +p打开整个模块的所有 dev_dbg；把 + 换成 - 就是关掉
file mydev.c line 120-150 +p精确到文件的某一段行号，排查热点路径时很有用
func mydev_read +p / format "rx overflow" +p按函数名 / 按格式串匹配
module mydev +pmfl额外在每条日志前加模块名（m）、函数名（f）、行号（l），省得自己写进格式串；t 是线程 ID
读这个文件第一列是文件:行，末尾 =p 表示已打开、=_ 表示关闭
probe 阶段的 dev_dbg 用 echo 是打不开的——控制文件要等模块加载后才有对应条目，而那时 probe 已经跑完了。要用 insmod mydev.ko dyndbg=+p（内建驱动用启动参数 mydev.dyndbg=+p）才能抓到启动期的输出。这是"为什么我加了日志却什么都看不到"最常见的原因之一，另一个是级别没过 console_loglevel。

9.3 ftrace：问题是"慢"而不是"崩"的时候

在 /sys/kernel/debug/tracing 下操作，不需要额外工具：先 echo 'mydev_*' > set_ftrace_filter 只跟踪自己的函数（否则输出量大到没法看），再 echo function_graph > current_tracer、echo 1 > tracing_on，触发一次业务操作后 cat trace。判读要点：缩进给出调用层次，DURATION 是该函数含子调用的总耗时，所以要找"某一层远大于其所有子调用之和"的地方。行首的 + / ! 是内核加的耗时标记（超过 10 µs 和 100 µs），扫一眼就能定位可疑行。

要回答的问题用什么

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础设备树（Device Tree）解决了什么问题？compatible、reg、interrupts 分别是什么？

    它把易变的板级硬件描述从内核代码里剥离成独立的数据文件，让同一个内核镜像配不同 dtb 支持不同板子，终结了 ARM 内核里泛滥成灾的 board file。三个属性：compatible 是匹配键（写「厂商,型号」，可给一串并从具体到通用排列，内核用第一个有驱动的，这是硬件兼容性的降级机制）；reg 是寄存器区间，用 devm_platform_ioremap_resource 取；interrupts 是中断描述，用 platform_get_irq 取。

    必须说清的细节：reg 和 interrupts 里那串数字本身没有固定含义——前者的解释取决于父节点的 #address-cells / #size-cells，后者取决于 interrupt-parent 那个中断控制器的 #interrupt-cells。所以同一串 <0 32 4> 在 GIC 下是「SPI 32 号、高电平触发」，换个控制器就完全是另一回事。抄别人的 dts 最容易在这里翻车。

    边界也要交代：设备树只描述「硬件是什么、在哪里」，不描述「怎么驱动它」；可自枚举的总线不需要它——PCI / USB 自带 ID 与配置空间，x86 则走 ACPI。

  2. 基础container_of 是怎么工作的？为什么驱动里到处都是它？

    已知结构体某个内嵌成员的地址，减去编译期常量 offsetof(type, member)，反算出外层结构体的首地址。offsetof 在编译期就算完了，所以这个宏零运行时开销，本质只是一次指针减法；内核版本还用 typeof 做了成员类型校验，成员名写错编译期就报错。

    为什么驱动里到处都是：内核回调只会把内核对象的指针交给你（work_struct *、timer_list *、cdev *、notifier_block *），而你的私有状态（缓冲、锁、寄存器基址、实例编号）在自己的结构体里。把内核对象内嵌进私有结构，回调里一次 container_of 就找回全部上下文——第 3 章骨架里 mydev_open() 那一行就是标准写法。真正价值是让驱动天然支持多实例：不需要全局变量，也不需要「设备号 → 私有数据」的查表。list_head 的侵入式链表是同一套思路，挂链不额外分配节点，一个对象还能同时挂在多条链上。

    陷阱：成员必须按值内嵌而非指针；嵌了两个同类型成员时只能靠成员名区分，写错了类型照样匹配、算出来的地址却是错的，而且没有任何运行时检查——只会表现为遥远的内存损坏。

  3. 基础copy_to_user 和 memcpy 有什么区别？为什么不能直接解引用用户指针？

    用户传进来的指针可能非法、可能指向已被换出的页、也可能被恶意构造成内核地址。直接 memcpy 的后果分别是 oops、缺页无人处理，以及最严重的——把任意内核内存读给用户、或让用户写进内核，这是最经典的提权原语。

    copy_*_user 做了三件 memcpy 不做的事：① access_ok() 校验地址确实落在用户空间；② 拷贝指令登记在异常表里，缺页时由 fixup 接管、返回「未拷贝字节数」而不是 oops；③ 在支持 SMAP / PAN 的硬件上临时打开内核访问用户页的开关。

    四个容易丢分的细节：

    • 返回值是剩余字节数，0 才是成功，类型还是 unsigned long——if (ret < 0) 恒不成立。不判返回值就会把没填满的内核栈缓冲当有效数据用。
    • 它可能睡眠，所以不能在中断上下文或持 spinlock 时调用。
    • 回传的结构体要先清零。编译器插入的 padding 不会被赋值语句覆盖，拷出去就是内核栈信息泄漏。
    • 校验必须基于内核副本。「先校验用户内存里的长度字段，再按它去拷」是典型 TOCTOU。

    一句话总结：它不是「带检查的 memcpy」，而是用户 / 内核隔离的强制闸门，绕过它等于取消整套地址空间隔离。

  4. 基础让 /dev/mydev 能被 open，需要哪几步注册？每一步各自负责什么，漏一步会看到什么症状？

    三层，分别对应「上户口 → 安电话 → 挂门牌」：

    • alloc_chrdev_region()：申请一段 (major, minor) 并登记名字。此刻只是占号，没有任何行为绑上去。动态申请而不是写死 major，写死会和别的驱动撞车。
    • cdev_init() + cdev_add()：把 file_operations 绑到 cdev，再把 cdev 挂进字符设备映射表。这一步之后「设备号 → 你的回调」才真正连通。
    • class_create() + device_create()：在 sysfs 建出设备对象并发一个 uevent，udev 收到后才创建节点文件。内核自己不创建 /dev 节点。

    漏掉不同层的症状完全不同，这是这道题真正想问的：

    漏 cdev_add
    /dev/mydev 存在、ls 看得见，但 open() 返回 ENXIO——号占了却没人认领。
    漏 device_create
    驱动完全可用，但 /dev/mydev 不存在。这就是老教材里为什么总让你手动 mknod /dev/mydev c <major> 0。

    所以「节点不存在」和「节点打不开」是两类故障，先用 grep mydev /proc/devices 区分：能看到名字说明前两层没问题，问题在 udev / 权限。

    还有一个顺序上的讲究：「让设备可见」必须是注册的最后一步——cdev_add() 一返回用户态立刻就可能 open，私有结构还没初始化完就会解引用半成品；移除时完全反过来。手写这条路径必须逐层 goto 逆序回滚，devm_* 存在的意义就是把它交给内核自动做。

10.2 中级（区分熟练度）

  1. 中级中断处理函数里为什么不能睡眠？如果非要做耗时/阻塞的活怎么办？

    根因是中断上下文不绑定任何进程：它借用被打断者的内核栈运行，但没有属于自己的 task_struct，也就没有「稍后被唤醒继续执行」的载体。一旦睡眠，调度器把 CPU 交给别人之后再也没有办法回到这段中断处理——轻则该 CPU hang，重则 panic。而且上半部通常关着中断，睡在里面会直接拉高全系统的中断延迟。

    内核的判据是 preempt_count：硬中断、软中断、关抢占、持 spinlock 都会把它加起来，非零就是原子上下文。可能睡眠的函数入口都埋了 might_sleep()，开 CONFIG_DEBUG_ATOMIC_SLEEP 会直接打出 BUG: sleeping function called from invalid context 并附调用栈。

    具体禁忌：不能 mutex_lock / wait_event / msleep，不能 copy_*_user（会缺页），kmalloc 必须带 GFP_ATOMIC（失败率更高，所以关键 buffer 应在 probe 阶段预分配），也别用大栈数组——内核栈只有 8–16 KB，还和被打断的进程共用。

    正确做法是拆上半部 / 下半部：上半部只做「认领中断、清硬件标志、记录状态、调度下半部」然后立刻返回；下半部在 threaded IRQ / workqueue / softirq / tasklet 里四选一，新代码默认 threaded IRQ。

    取舍：拆下半部换来「上半部极短」，代价是下半部的执行时刻不确定。硬实时路径宁可让上半部多做一点确定性的工作，也不要把关键动作排进 workqueue 去赌调度；反之吞吐型设备该把几乎所有处理都推到下半部，甚至再做 NAPI 式批量轮询摊薄中断本身的开销。

  2. 中级DMA 的 cache 一致性问题是什么？一致性映射和流式映射怎么选？

    本质是两个访问者走了不同的路径：CPU 经过 cache，DMA 引擎直接改物理内存。于是有两种翻车方向——外设写完内存后 CPU 命中旧 cache 行，读到过期数据；或者 CPU 写的数据还躺在 cache 里没回写，外设读到旧值。x86 由硬件保证一致性，很多 ARM SoC 不保证，必须由软件 clean / invalidate。

    选择的判据是访问模式而不是大小：dma_alloc_coherent() 映射成 uncached、双方看到的永远一致、不需要手动同步，但 CPU 访问很慢，所以只适合小而被双方频繁访问的控制结构（描述符环、状态字）——拿它当大数据缓冲是常见的性能事故；dma_map_single() 保留 cache、性能好，适合一次性大块传输，代价是要声明方向、并遵守所有权规则（映射期间 buffer 属于设备，CPU 不得访问；非要看就 dma_sync_single_for_cpu() → 看 → for_device() 交还）。方向写反了在无一致性平台上就是偶发数据损坏：TO_DEVICE 在 map 时 clean、FROM_DEVICE 在 unmap 时 invalidate。

    另外三条同样会咬人：dma_addr_t 不是物理地址（经 IOMMU 后与物理地址完全无关，自己 virt_to_phys 算是错的）；buffer 必须物理连续可 DMA（vmalloc 内存和栈上数组都不行）；要按 cache line 对齐，否则一次 invalidate 会连带丢掉同一行上相邻变量的修改。这类 bug 只在高压力下偶发、位置随机、加一行 printk 就复现不了，所以排查靠 CONFIG_DMA_API_DEBUG 校验配对与方向，而不是继续加日志。

  3. 中级softirq / tasklet / workqueue / threaded IRQ 四种下半部怎么选？各自的延迟量级如何？

    按顺序问四个问题，答案基本唯一：①下半部要睡眠吗（拿 mutex、GFP_KERNEL 分配、走 I²C/SPI 这类会等的总线）——要，就只剩 threaded IRQ 和 workqueue；②是「每次中断对应一次处理」还是「零散的异步任务」——一一对应选 threaded IRQ；③需要可控的优先级 / 绑核吗——需要选 threaded IRQ，它有独立 task_struct，能 chrt 调优先级、taskset 绑核，而 workqueue 用共享线程池做不到这么细；④是不是每秒几十万次且完全不需要睡眠——才轮到 softirq。

    延迟量级（数量级参考，强烈依赖 CPU、CONFIG_PREEMPT* 与负载，必须在自己的板子上实测）：softirq 最小，多数情况下在硬中断返回前就地执行，亚微秒到数微秒，但积压过多时会被推给 ksoftirqd、退化到受调度器影响的毫秒量级，而且同一类型可在多核并行、共享数据仍要加锁；tasklet 建在 softirq 之上、延迟相同，特点是同一实例不会并行（这是它当年流行的原因），但已是老接口、新代码不要用；threaded IRQ 是一次线程唤醒 + 一次调度，微秒到几十微秒；workqueue 最不确定，几十微秒到毫秒都可能，不适合有延迟要求的路径。

    softirq 还有一条硬限制常被忽略：它的类型是编译期静态枚举的，外部模块无法新增，所以普通驱动根本选不到它。

  4. 中级模块加载成功，但 platform_driver 的 probe 从来没被调用，怎么定位？

    不要猜，沿着「dts → device_node → platform_device → 驱动 → 绑定」逐层缩小，每一层都有一个能直接看的证据：ls /proc/device-tree/（看不到就是 dtb 的问题，根本没到驱动这一层）→ cat .../compatible 和驱动里 of_match_table 的字符串逐字符比 → ls /sys/bus/platform/devices/ → ls /sys/bus/platform/drivers/myperiph/（出现设备名的符号链接才算绑定成功）→ cat /sys/kernel/debug/devices_deferred。

    按经验，命中率从高到低是：板子上刷的还是旧 dtb（占一半以上）；节点写了 status = "disabled"——很多 SoC 厂商的 .dtsi 默认把外设全关掉；compatible 差一个字符；驱动压根没加载；卡在 -EPROBE_DEFER 等一个永远不会出现的依赖。

    最后一条值得展开：时钟、regulator、GPIO、PHY 这些子系统可能比你晚初始化，此时 devm_clk_get() 返回 -EPROBE_DEFER，必须原样往上返回让内核稍后重试。两个典型错误：当普通错误打一条 dev_err（启动期刷出一堆假错误，应该用 dev_err_probe()，它对 defer 自动降级为 debug）；或改写成 -ENODEV 返回——设备就永久不会再被探测，症状是「冷启动偶尔起不来、重启一次又好了」。

10.3 高级（体现深度）

  1. 高级spinlock 和 mutex 怎么选？spin_lock 和 spin_lock_irqsave 的区别？

    第一个判据是「临界区会不会睡眠」：会睡（或临界区较长）→ mutex，拿不到锁就让出 CPU；不能睡或身处中断上下文 → spinlock，忙等，临界区必须极短。

    更关键的是知道 spinlock 顺手做了什么：它会关抢占，即使不关中断。所以持锁期间 CPU 不会被调度走，临界区里不能睡眠、不能触发缺页、不能 copy_*_user、不能 kmalloc(GFP_KERNEL)；持锁时长要用微秒衡量。

    spin_lock 与 spin_lock_irqsave 的区别就落在那个自死锁上：

    自死锁
    进程上下文拿了普通 spinlock，本核中断到来，中断处理去拿同一把锁 → 它忙等一个永远不会被释放的锁，因为持有者正被自己打断在同一个 CPU 上。这是硬死锁，多核也救不了。所以只要这份数据也会被中断处理访问，进程侧就必须用 spin_lock_irqsave。

    三个变体不要混：spin_lock_irqsave 保存原状态，库与驱动代码一律用它；spin_lock_irq 解锁时无条件开中断，若调用者本来就关着中断，它会悄悄破坏调用者的前提；spin_lock_bh 只关软中断，用于「数据被 softirq / tasklet 访问但不被硬中断访问」。

    再往上还有更合适的原语，能选对才说明真的理解并发：读多写极少用 RCU（读端零开销不阻塞，代价是写端要走「复制—替换—等 grace period—释放」，释放被推迟且读端可能看到旧快照）；很小的统计量用 seqlock（读端靠序号重试、无 cacheline 争用，但临界区不能有副作用）；rwlock 基本不推荐；只是计数就别上锁。

    两件工程上必须做的事：打开 CONFIG_PROVE_LOCKING（lockdep）跑测试，它能自动发现锁序反转与 irq-safe / irq-unsafe 混用；以及记住 PREEMPT_RT 会改变这套直觉——RT 内核里 spinlock_t 被换成可睡眠的 rt_mutex，真正忙等的只剩 raw_spinlock_t。

  2. 高级.owner = THIS_MODULE 有什么用？不写会怎样？

    它让内核在设备被使用时对模块加引用计数：VFS 在 open 时按 file_operations::owner 调 try_module_get()、release 时 module_put()；rmmod 发现计数非零就返回 EBUSY。

    不写的后果很具体：正有进程 open 着 /dev/mydev 时模块被卸载，回调所在的代码页被释放，下一次 read 就跳进一个已经不存在的地址——Oops 里的 PC 是查不到符号的野地址，这种现场几乎无法反推原因。

    但这道题真正的深度在于：引用计数只挡住「有人正 open 着」这一种情况。模块里所有异步引用它都管不了，而它们同样会在卸载后回调进已释放的代码：还排在队列里或正在执行的 work_struct；已经 armed 的 timer_list / hrtimer；还没 free_irq 的中断与 threaded IRQ 线程；注册进链表的 notifier_block、sysfs / debugfs 节点、还在跑的 kthread；以及被别的模块通过导出符号拿走的函数指针——只有最后这一类才是 module_get 计数真正保护的对象。

    所以 module_exit 必须和注册严格逆序地拆干净，而且要用会「等已经在跑的那一次跑完」的 *_sync 版本；具体顺序与两个反例见下一题。查引用的入口：lsmod 第三列、/sys/module/<name>/refcnt，以及 holders/ 看谁在依赖它。

    生产视角：卸载路径的竞态又多又难测，所以很多产品干脆把驱动编进内核（built-in），从根上消掉这一整类问题；确实需要热插拔时，就必须把反复 insmod / rmmod 当成正式压测用例并配合 KASAN 跑。

  3. 高级现场反馈：rmmod 成功返回、过几秒机器 panic，栈里的地址查不到任何符号。怎么排？

    「rmmod 返回了，几秒后才崩，且 PC 是野地址」这三个特征放在一起，几乎唯一指向一件事：模块的代码页已经被释放，但还有一个异步回调在此之后被触发，跳进了那段不再存在的内存。符号查不到正是因为负责翻译地址的那个模块已经不在 /proc/modules 里了。

    取证——先固定证据再谈修复：

    • 看 Oops 里的 PC / RIP 是否落在已卸载模块曾占用的地址区间（卸载前 cat /sys/module/mydev/sections/.text 记下来）。落在里面就已经定案。
    • 崩溃路径通常带着凶手的名字：栈上出现 call_timer_fn / process_one_work / irq_thread / notifier_call_chain，分别说明是定时器、工作队列、中断线程、通知链在回调一个已消失的函数。
    • 开 KASAN 复现，它能把「谁分配的、谁释放的、谁在释放后访问的」三段栈一起打出来。
    • 写压测脚本反复「边用边卸」：while :; do insmod mydev.ko; ./stress & sleep 0.3; rmmod mydev; done。卸载竞态几乎只能这样压出来，正常测试流程永远碰不到。

    修复——exit 路径必须和注册严格逆序，而且要用会等「已经在跑的那一次」跑完的 *_sync 版本：

    free_irq(irq, dev);            /* ① 先断源头，别让新工作再排进来 */
cancel_work_sync(&dev->work);  /* cancel_work 只摘队列，不等在跑的那次 */
del_timer_sync(&dev->timer);   /* 注意：回调里若又 mod_timer，sync 也救不了 */
destroy_workqueue(dev->wq);
device_destroy(cls, devno);
cdev_del(&dev->cdev);          /* ② 最后才让设备不可见 */
unregister_chrdev_region(devno, 1);

    两个反例：顺序反了照样出事——先 cancel_work_sync 再 free_irq，中断可能在这中间又排一次 work 进来；会自我续期的定时器（回调里再调 mod_timer）是另一个专门的坑——del_timer_sync 只保证「当前这次跑完」，不保证它没重新武装自己，必须先置一个 going_away 标志让回调不再续期，再 sync。

    工程结论：尽量用 devm_* / dmam_*，把释放顺序交给内核按注册顺序自动逆序回滚，比人工维护 exit 路径可靠得多。崩溃现场的完整取证方法（Oops 字段逐个解读、kdump、crash 工具）见 内核崩溃分析。

  4. 高级访问设备寄存器为什么必须用 readl/writel，不能把基址转成 volatile 指针直接解引用？

    volatile 只约束编译器：它保证每次访问都真的产生一条访存指令、不被优化掉、不被合并。但它对 CPU 和总线的重排毫无约束，而寄存器访问的顺序往往有硬件含义——「先写地址寄存器、再写触发寄存器」写反了，硬件就按上一个地址启动了传输。readl() / writel() 除了访问本身，还包含了该架构所需的屏障与编译器约束。

    它们还做了另外三件 volatile 指针做不到的事：字节序转换（writel 的语义是「写一个小端 32 位值」，大端 CPU 上会自动转换，裸指针赋值不会——代码在小端平台正常、移植到大端就全乱）；访问宽度确定（很多外设要求整字访问，字节访问是未定义行为，而裸指针的宽度取决于编译器选了哪条指令）；可移植性（某些架构的 I/O 空间根本不能用普通 load/store 访问，这些宏会展开成正确形式）。

    配套两点也常一起问：__iomem 指针只能交给这些访问器，不能 memcpy、不能直接解引用（sparse 会检查，这也是 devm_platform_ioremap_resource() 返回 void __iomem * 的原因）；ioremap 的映射默认不可缓存——走可缓存映射会让 CPU 把写攒在 cache 里、把读命中旧值。

    最后一个容易漏的点：writel 保证的是对同一设备的 MMIO 之间有序，它不保证「普通内存的写」和「后面这次 MMIO 写」之间有序。所以填完 DMA 描述符再敲门铃，中间必须显式加 dma_wmb()。完整原理见 内核同步原语 · 内存屏障。

11

checklist 与小结

写字符 + 平台驱动的自检清单

  • 设备号动态申请，别写死 major；私有状态挂 struct + container_of，支持多实例。
  • 资源优先 devm_*；手写路径逆序释放，「让设备可见」放最后一步。
  • 写每一行前先问「当前上下文能不能睡」（1.3 那张表）。
  • 用户指针一律 copy_*_user / get_user；只判返回值是否为 0；回传的结构体先清零。
  • ioctl 入参严格校验，未知命令返回 -ENOTTY；UAPI 只用固定宽度类型 + 显式补齐。
  • 阻塞读用 wait_event_interruptible，被打断返回 -ERESTARTSYS；中断侧先放数据、后唤醒。
  • 高频路径的日志一律 *_ratelimited 或 trace_printk——串口上一条约 7 ms，无限打印直接触发 soft lockup。
  • 板级信息走设备树；-EPROBE_DEFER 原样往上返回。
  • 中断拆两半：上半部认领 + 清标志 + 立刻返回，耗时的放 threaded IRQ。
  • 选对锁：睡→mutex，不睡→spinlock，被中断访问→spin_lock_irqsave，临界区极短。
  • DMA 先声明 dma_set_mask_and_coherent，流式映射声明方向、遵守所有权、按 cache line 对齐。
  • MMIO / mmap 寄存器用 pgprot_noncached；通知硬件之前加 dma_wmb()。
  • 开发期开 KASAN + lockdep + CONFIG_DEBUG_ATOMIC_SLEEP + CONFIG_DMA_API_DEBUG，并备好串口控制台。
一句话总结：驱动是内核里被"回调"的一堆函数——把 fops 填对、资源用 devm 管好、中断拆成两半、锁和 cache 一致性想清楚，一个能上真实 SoC 的驱动就成了。
