🚨 N08 本文

讲production incident · "出问题 5 分钟内怎么定位"。按问题分类组织 · runbook 风格。

Playbook 的核心价值：incident 发生时 you don't think · you execute。提前把"症状 → 工具 → 步骤"沉淀成肌肉记忆 · 5 分钟定位 vs 30 分钟摸索 · 这是 Senior SRE 的护城河。建议把本文 7 个 playbook 打印贴在桌前 · 1 个月内值班用 3 次就成肌肉记忆。
PB1
🔥 CPU 100% · 服务响应慢 / load avg 飙

典型症状

  • load average 远超 CPU 核数（4 核机器 load 30+）
  • 某个 / 多个进程 CPU% 接近 100% / 多核累加 > 100%
  • 请求 P99 latency 飙 · throughput 反而下降

① 快速分类

$ top                  # 找 top 进程 (按 P 排 CPU 顺序)
$ uptime               # load avg 历史
$ vmstat 1 5           # us/sy/id/wa/st 分布
  • us 高 (user CPU) → 应用代码热 → 走 ② 看应用
  • sy 高 (kernel) → syscall / context switch 多 → 走 ③ 看内核
  • wa 高 (IO wait) → 看似 CPU 高其实 IO 慢 → 跳 PB3
  • st 高 (steal time) → 虚拟机宿主在偷 CPU · 跟云厂商联系

② 应用级深入 (us 高)

$ sudo perf top -p <pid>          # 实时看哪个函数热
$ sudo perf record -F 99 -p <pid> -g -- sleep 30
$ sudo perf script | ./stackcollapse-perf.pl | ./flamegraph.pl > flame.svg
  • 看火焰图 · 平顶函数 = 热点 · 平宽函数 = 调用很多次
  • 典型场景：① 死循环（某 condition 没退出）② 正则 / hash 碰撞 ③ JSON parse 整大文档 ④ GC 风暴（Java）

③ 内核级深入 (sy 高)

$ sudo perf top -e cycles --cpu 0,1,2,3   # 看内核热点
$ pidstat -w 1                            # 进程上下文切换频率
$ sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* { @[probe] = count(); }'   # 哪个 syscall 频繁
  • 典型：① 频繁 read/write（小 buffer + 大循环）② 频繁 futex（lock 抢）③ 内核 spinlock 抢（high core count 严重）

④ 缓解 + 修复模式

  • 立刻：限流（nginx limit_req / 网关）· 切流 · 重启该实例
  • 短期：扩容（K8s replicas + 1）· 升 CPU 配置
  • 修复：定位热点后 ① 算法优化 ② 加 cache ③ 异步化 ④ 退化策略（降级一些 feature）
某服务突然 CPU 100% · perf top 显示 90% 在 regex::match · 火焰图发现一个 user input 走到了 regex backtracking 路径（ReDoS · catastrophic backtracking）· 修复：用 RE2 替代 std::regex / 加 input length 上限 / 加 timeout。
PB2
💥 内存涨 / OOM kill · process 突然消失

典型症状

  • RSS 缓慢上涨 (每天 +X MB) · 不释放 = 泄漏
  • RSS 突然飙到 limit → OOM kill · dmesg | grep OOM 有记录
  • swap 使用率高 · 系统响应慢
  • 容器内 OOM 但 memory.current 看似没满 → cgroup memory 计入了 page cache

① 快速分类

$ free -h                          # 总体看 used / free / available
$ ps aux --sort=-%mem | head -10   # top 10 内存进程
$ cat /proc/<pid>/status | grep VmRSS
$ cat /proc/meminfo                # 细分 anon / cached / slab
$ dmesg | grep -i "killed process"  # OOM 历史

② 区分 4 种内存涨

  • AnonPages 涨（用户态 heap）→ 应用泄漏 · 走 ③
  • Cached / Buffers 涨（page cache）→ 正常 · OS 会自动 reclaim · 不是问题
  • Slab 涨（内核 cache）→ inode / dentry cache 多 · 看 slabtop
  • HugePages reserved 多（预留但没用）→ 计入 used 但应用没用

③ 应用泄漏定位

# Production 友好 (开销 < 5%)
$ sudo memleak-bpfcc -p <pid>            # 抓 outstanding alloc + stack trace

# C++ heap profiling (tcmalloc)
$ HEAPPROFILE=/tmp/myapp.heap LD_PRELOAD=/usr/lib/libtcmalloc.so ./myapp
$ pprof --text /tmp/myapp.heap.0001

# Java heap dump
$ jcmd <pid> GC.heap_dump /tmp/heap.hprof
$ jhat / VisualVM 分析

# Python heap (objgraph / tracemalloc)

④ OOM 调查

$ dmesg | grep -i oom -A 20    # 看被杀进程的 RSS / oom_score

# 常驻 OOM 监控 (推荐!)
$ sudo bpftrace -e '
  kprobe:oom_kill_process {
    printf("[%H:%M:%S] OOM kill: pid=%d comm=%s\n", pid, comm);
  }' | tee -a /var/log/oom.log

⑤ 缓解 + 修复模式

  • 立刻：定期 restart（cron）· 升 memory limit · K8s replicas + 1
  • 修复：① 修代码泄漏（最常见：cache 没 LRU、event listener 没 unregister）② 加 cgroup memory.high 让 throttle 不 OOM ③ 调 oom_score_adj 让关键进程不被杀
  • 预防：上线 memleak-bpfcc 持续监控 + 内存涨 alert（每日 RSS > 1.2x baseline）
某 Node.js 服务 RSS 每天涨 100MB · memleak-bpfcc 跑 24h 抓到 stack trace 在 EventEmitter · 发现某 socket disconnect 没 removeAllListeners() · 修后稳定。详见 N07 §7 cgroup memory 配置。
PB3
🐌 IO wait 高 · 服务慢但 CPU 不高

典型症状

  • vmstat 看 wa 列持续 > 20% (单核 wa > 50% 严重)
  • top 看进程 D 状态多（uninterruptible sleep · 等 IO）
  • 磁盘 util% 接近 100%

① 快速分类

$ vmstat 1 5            # wa 列
$ iostat -x 1 5         # 看 util% / await / svctm / r_await / w_await
$ iotop -o              # 哪个进程 IO 多 (-o 只显示有 IO 的)
$ ps aux | awk '$8 == "D"'   # 哪些进程在 D 状态
  • util% 接近 100% → 磁盘饱和 · 看 await
  • await > 100ms → 磁盘慢（SSD 正常 < 5ms · HDD 正常 < 30ms）
  • r/s + w/s 极高 → 应用产生 IO 太多 · 看 iotop 找进程

② 应用级 IO 模式分析

$ sudo biosnoop-bpfcc           # 实时看每个 IO 详细 (process, size, latency)
$ sudo biolatency-bpfcc 10 6    # IO 延迟直方图
$ sudo bpftrace -e 'tracepoint:block:block_rq_issue {
  @[comm, args->rwbs] = count();
}'   # 哪个进程 + 读/写 量

# 跟踪 syscall 模式 (大量小 IO vs 少量大 IO)
$ sudo strace -p <pid> -e read,write -c
  • 常见反模式：① 大量小 IO（buf 太小 / 没 fwrite buffer）② fsync 太频繁（DB 每条 commit fsync）③ 随机 IO（大文件 seek）

③ 文件系统 / 块层调查

$ cat /sys/block/sda/queue/scheduler    # 看 IO scheduler (mq-deadline / kyber / bfq / none)
$ cat /proc/diskstats                   # 详细统计
$ sudo blktrace -d /dev/sda             # Block 层 trace (高级)

④ 缓解 + 修复模式

  • 立刻：限流 / 关闭非核心 IO 任务
  • 云上：升级到 io2 / 高 IOPS volume · 或 local NVMe
  • 应用：① 合并小 IO（用 buffered IO 或 io_uring batching）② 减 fsync（用 fdatasync / batched commit）③ 大文件用 sequential read + readahead ④ 切换 Direct IO 绕过 cache（DB 类）
  • 系统：调 IO scheduler / readahead size / dirty page ratio · 详见 N01 §11
云服务 P99 偶尔 2 秒 spike · iostat 显示 sda util 偶尔 100% · biolatency 显示 P99 = 1.5s · 查云厂商 EBS volume 共享被限流 · 切 io2 高 IOPS volume + 加 IO batching · spike 消失。
PB4
📡 网络丢包 / 延迟高 / 连接异常

典型症状

  • TCP 重传率高 / ESTABLISHED 状态长 / TIME_WAIT 满
  • 用户感知慢 · ping 正常 · 但 HTTP / gRPC 慢
  • 偶发 connection refused / connect timeout

① 快速分类

$ ss -s                          # socket 总览 (TCP/UDP/SYN_RECV 等数量)
$ ss -tan state established | wc -l     # ESTABLISHED 连接数
$ ss -tan state time-wait | wc -l       # TIME_WAIT 数
$ netstat -s | grep -i retrans          # 重传数 (TCPRetrans / RTO)
$ ip -s link show                       # 网卡 RX/TX dropped + errors
$ ifconfig / ethtool -S <iface>

② 实时观测包级

$ sudo tcpdump -i any -w /tmp/dump.pcap host x.x.x.x and port 8080
$ wireshark /tmp/dump.pcap         # 离线分析

# eBPF 实时看内核 drop 原因 (神器!)
$ sudo tcpdrop-bpfcc

# 看重传 (按 src/dst 聚合)
$ sudo tcpretrans-bpfcc

# 看 TCP 连接建立 / 关闭
$ sudo tcpconnect-bpfcc

③ 常见根因

  • backlog 满（tcpdrop 看到 LISTENOVERFLOWS）→ net.core.somaxconn + listen() backlog 调大
  • TIME_WAIT 满（连接数被卡）→ net.ipv4.tcp_tw_reuse=1（client 侧）/ SO_LINGER
  • conntrack 表满（NAT 场景）→ net.netfilter.nf_conntrack_max 调大
  • 网卡 drop（ip -s 看 RX dropped）→ irq affinity / RPS / RFS 调优
  • buffer 不够（rmem/wmem 默认小）→ net.core.rmem_max + tcp_rmem

④ 缓解 + 修复模式

  • 立刻：限流 · 重启 · 加节点（横向扩容）
  • 修复：① 调 sysctl（参考下表 5 个最常用）② 上 BBR 拥塞控制 ③ SO_REUSEPORT 多 listener load balance
sysctl默认推荐含义
net.core.somaxconn1284096listen backlog 上限
net.ipv4.tcp_max_syn_backlog1288192SYN_RECV 队列
net.ipv4.tcp_tw_reuse01TIME_WAIT 复用 (client 侧)
net.ipv4.tcp_fin_timeout6015FIN_WAIT2 超时
net.ipv4.tcp_congestion_controlcubicbbr (Linux 4.9+)拥塞控制算法 · BBR 长肥管道好
电商大促 · 5xx 错误飙升 · tcpdrop-bpfcc 显示大量 LISTENOVERFLOWS drop · listen backlog 写死 128 满了 · 改成 4096 + 调 somaxconn · 错误立刻消失。详见 N04 网络编程。
PB5
📂 fd 泄漏 · "Too many open files"

典型症状

  • 报错 EMFILE: Too many open files · accept() 失败
  • /proc/<pid>/fd/ 文件越来越多
  • 服务跑几天后 socket / file 操作开始失败

① 快速分类

$ ls /proc/<pid>/fd | wc -l        # 当前 fd 数
$ cat /proc/<pid>/limits | grep "Max open files"
$ lsof -p <pid> | head -50         # 看打开了哪些
$ lsof -p <pid> | awk '{print $5}' | sort | uniq -c | sort -rn   # 按类型聚合

# 系统级
$ cat /proc/sys/fs/file-nr         # 系统 fd 总用量
  • 看 lsof 输出按类型聚合 (REG / SOCKET / pipe / FIFO 等) · 哪类多 = 哪类泄漏

② 确认是否真泄漏 (不是流量自然涨)

# 监控 fd 趋势 (每 30 秒)
$ while true; do
    echo "$(date +%s) $(ls /proc/<pid>/fd | wc -l)"
    sleep 30
  done | tee fd_trend.log
  • 稳定上涨 / 不下降 = 泄漏 · 涨跌平衡 = 正常波动

③ 定位代码源头

# bpftrace 抓 open 没对应 close 的 stack
$ sudo bpftrace -e '
  tracepoint:syscalls:sys_enter_openat /pid == TARGET/ {
    @opens[ustack] = count();
  }'

# strace 简单粗暴
$ sudo strace -p <pid> -e trace=open,openat,close 2>&1 | head -100

④ 缓解 + 修复模式

  • 立刻：临时调 ulimit (prlimit --pid X --nofile=65536) + 重启
  • 修复：① 检查 C++: RAII (智能指针 / unique_fd wrapper) ② Python: with 语句 ③ Java: try-with-resources ④ Go: defer close()
  • 常见原因：socket disconnect 没 close · HTTP client 没复用 (每次创建新 conn) · 临时文件没 unlink
某 Python 服务每周必崩一次 (EMFILE) · lsof 看到 30000 个 TIME_WAIT socket · 代码用 requests 没 Session 复用 · 改用 requests.Session() + connection pool · 问题解决。
PB6
🔒 死锁 / hang · 服务不响应但没崩

典型症状

  • HTTP / gRPC 不响应 · 连接 hang
  • thread 卡在某 lock / read · CPU 几乎 0%
  • kill TERM 没用 · 必须 kill -9

① 快速分类

$ ps -eLf | grep <process> | head    # 看线程数 + 状态
$ ps -L -p <pid> -o tid,state,cmd     # 每个线程状态

# 看哪些线程在等 (state = D 或 S)
$ cat /proc/<pid>/task/<tid>/wchan    # 在哪个内核函数等
$ cat /proc/<pid>/task/<tid>/stack    # 内核调用栈
  • D 状态（uninterruptible）= 等 IO / 等内核锁
  • S 状态（interruptible）+ wchan = futex_wait = 等 mutex / cond var
  • 大量同样 wchan = 怀疑死锁或同时等同一资源

② 获取 user-space 调用栈

# C++ - gdb attach
$ sudo gdb -p <pid>
(gdb) thread apply all bt        # 所有线程 backtrace
(gdb) info threads               # 看哪些线程
(gdb) thread <N> bt              # 看某线程

# Java - jstack
$ jstack -l <pid> > /tmp/jstack.log
# 看 BLOCKED / WAITING / 是否有 "Found one Java-level deadlock"

# Python - py-spy
$ sudo py-spy dump --pid <pid>

# Go - pprof goroutine
$ curl http://localhost:6060/debug/pprof/goroutine?debug=2

③ 死锁模式识别

  • 循环等待：T1 持 A 等 B · T2 持 B 等 A → 经典死锁
  • 同一 mutex 大量等：可能是 contention 严重 · 不是死锁但效果类似
  • IO 死锁：所有线程都在等同一文件 read / write
  • 外部依赖 hang：等下游 DB / Redis / 外部 API 永不返回

④ 缓解 + 修复模式

  • 立刻：保留 stack trace + core dump → 再 kill -9 重启
  • 修复死锁：① 全局加锁顺序约定（lock ordering）② 用 std::scoped_lock 多 mutex 一起锁 ③ 用 timeout 锁 try_lock_for ④ 减少锁粒度（细锁 / 无锁结构）
  • 修复外部 hang：所有外部调用必须有 timeout · 加 circuit breaker
  • 预防：dev 阶段用 ThreadSanitizer (-fsanitize=thread) 找潜在死锁
C++ 服务突然 hang · gdb thread apply all bt 看到 2 个线程互相 waiting on different mutex · classic ABBA 死锁 · 修复：约定全局 lock order（A 永远在 B 前）+ 用 std::scoped_lock。
PB7
GC stall / Latency spike · 偶发 200ms+ 延迟

典型症状

  • P50 / P95 正常 · P99 / P99.9 突然 spike 200-2000ms
  • 无规律 · 应用代码看不出原因
  • JVM / Go / Node.js / 任何 managed runtime 都可能
  • C++ 也可能：malloc fragmentation / page fault / 内核 RT throttle

① 快速分类 — 是 GC 还是别的

# JVM GC log (强烈推荐生产开启)
$ jvm flag: -Xlog:gc*:file=/var/log/gc.log

# Go GC trace
$ GODEBUG=gctrace=1 ./myapp

# 通用：跟应用 latency spike 时序对齐 page fault / context switch
$ sudo bpftrace -e '
  software:page-faults:1 /pid == TARGET/ { @[comm] = count(); }
  interval:s:1 { print(@); clear(@); }'

② 4 类可能元凶

  • GC pause（Java / Go）→ GC log 看 STW 时间
  • Page fault 风暴 → memory pressure / THP collapse · 看 /proc/vmstat thp_collapse
  • 调度延迟（cgroup throttle / CPU 抢）→ runqlat-bpfcc 看 runqueue 等
  • JIT compile spike（JVM / V8）→ JIT 编译期间慢
  • swap（page 被换出再被换入）→ vmstat 看 si/so
  • 外部依赖偶发慢（DB / Redis spike）→ trace 上下游

③ JVM GC 调优速查

  • GC 选型：JDK 17+ ZGC / Shenandoah（low-pause < 10ms）· JDK 11+ G1（balance）
  • 典型反模式：Old gen 用 Parallel GC + 大 heap → Full GC stall 多秒
  • 关键 flag：-Xms = -Xmx（避免动态 resize stall）· 启用 -XX:+AlwaysPreTouch 避免 page fault spike

④ 缓解 + 修复模式

  • 立刻：扩容（更多实例分担流量）· 限流 P99 用户
  • 修复：① 换 GC（ZGC / Shenandoah）② 调小 heap（更频繁但更短的 GC）③ 减分配（对象复用 / pool）④ 关 THP（DB / GC heavy 服务）⑤ mlockall + HugePage 避免 swap / page fault
  • 诊断流程：用 spike 时间戳跟 GC log + vmstat + runqlat 时序对齐 · 找元凶
Java service 偶有 1.5s spike · GC log 显示 ZGC pause 都 < 5ms · 排除 GC · bpftrace page-faults 显示 spike 时thp_collapse_alloc 频率高 · THP 在合并 page 导致 stall · 关 THP 后 spike 消失。详见 N07 §4 THP。

面试题（12 道）

SRE / Tech Lead 视角 · 分层自测

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础故障发生时，先止血还是先定位？

    先止血。 incident 的第一目标是恢复服务，不是理解问题——理解问题是复盘阶段的目标。用户在流血的时候，你花在"想搞清楚为什么"上的每一分钟都在累加影响面。

    但这句话有个必要的前提，不说清就变成了教条：止血之前要先保存现场。回滚、重启、扩容都会破坏证据，一旦重启完问题消失，你就永远查不出根因，下次它会以同样的方式回来。所以标准动作是用一两分钟做"低成本快照"再动手：

    • hang / 死锁 → gdb -p 的 thread apply all bt、jstack、py-spy dump，或直接 gcore；
    • 内存问题 → 记下 /proc/<pid>/smaps_rollup、free -h、dmesg 尾部；
    • CPU 问题 → perf record -F 99 -p <pid> -g -- sleep 10，十秒就够；
    • 多实例故障 → 留一个坏实例摘掉流量但不重启，其余全部恢复。这是最优解：既止了血，又留了完整现场。

    另一个前提是止血手段本身必须是低风险的。回滚到已知良好版本、摘流量、限流、扩容都属于可预测的动作；而"改一行配置试试看"、"手动改数据库数据"不是止血而是在故障中引入第二个变量——这类操作在 incident 里造成的次生故障，比原始故障更常见也更难查。

    唯一"先定位"的例外：你不知道止血动作会不会让事情更糟。比如数据可能已经写坏了，此时重启会让脏数据继续扩散；或者怀疑是级联过载，盲目重启会引发惊群把下游彻底打死。这种情况下先花几分钟确认影响面和数据一致性，是对的。

  2. 基础怎么在 5 分钟内判断故障域是应用、依赖还是基础设施？

    核心思路是做切分实验而不是逐个排查——每一步都应该把可能性砍掉一半，而不是从头到尾看一遍监控。

    1. 看影响面的形状（60 秒），这一步信息量最大：
      • 只有一个实例坏 → 几乎必然是那台机器（磁盘、内存、网卡、邻居干扰）。直接摘掉，问题就结束了。
      • 同一可用区 / 同一机架全坏 → 基础设施（网络、存储、电源）。
      • 所有实例同时坏 → 要么刚发布，要么共享依赖挂了。这两个方向下一步分别验证。
      • 只有某类请求坏（某个接口、某个租户、某个地域）→ 应用逻辑或数据相关。
    2. 问"刚才改了什么"（30 秒）。发布、配置变更、feature flag、灰度扩量、DNS / 证书变更、定时任务、依赖方发版——绝大多数故障都能追到一次变更。这一步的成本几乎为零而命中率极高，应该是条件反射，不该排在监控之后。
    3. 切分应用与依赖（2 分钟）。看错误的类型而不是数量：超时和连接失败指向依赖或网络；5xx 加异常栈指向应用自身；4xx 突增指向上游或客户端。再对比自身延迟与依赖调用延迟：如果服务总延迟 2 秒而对下游的调用就占了 1.9 秒，问题不在你这儿。绕过应用直接打依赖（redis-cli --latency、直连 DB 跑一条简单查询）能一击定性。
    4. 排除基础设施（1 分钟）：vmstat 1 的 st（宿主偷 CPU）、ip -s link 的 drop / error、dmesg -T | tail（磁盘 IO error、网卡 reset、OOM）、以及云厂商的状态页。

    生产视角：能不能在 5 分钟内做完这套，取决于平时有没有把这几个信号做成一屏——按实例/可用区维度切分的错误率、自身延迟 vs 依赖延迟的分解、以及一条部署时间轴叠加在指标图上。最后这一项收益最高：变更与指标拐点的对齐关系，往往一眼就能定位，比任何工具都快。

  3. 基础CPU 100% 的分层排查顺序是什么？

    顺序上先分类再深入，因为 "CPU 100%" 是四类完全不同问题的共同症状，走错方向会浪费掉最宝贵的十分钟。

    第一步：用 vmstat 1 的时间构成分类（这一步决定后面走哪条路）：

    $ vmstat 1 5
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
18  0      0 1024000  ...                                       78  8  0  0  0
 ^                                                              ^  ^      ^  ^
 runqueue                                                      us sy     wa st
    • us 高 → 应用代码在算。走应用侧：perf top -p <pid> 看热点函数，再 perf record -g 出火焰图。常见根因：死循环 / 退出条件失效、正则回溯（ReDoS）、把大 JSON 反复解析、加密或压缩没走硬件指令、以及 GC 风暴。
    • sy 高 → 时间花在内核。走内核侧：pidstat -w 1 看上下文切换，bpftrace -e 'tracepoint:syscalls:sys_enter_* { @[probe] = count(); }' 看哪个 syscall 被刷爆。常见根因：小 buffer 大循环的 read/write、锁竞争导致 futex 风暴、epoll 空转、以及线程数远超核数造成的切换开销。
    • wa 高 → 根本不是 CPU 问题，是在等 IO。转去查存储，别在 CPU 上纠缠。
    • st 高 → 宿主机在偷 CPU（同机邻居或超卖）。你在客户机里做任何优化都无效，该找云厂商或迁移实例。

    第二步：确认是"变忙"还是"变慢"。这个区分很容易被跳过但极关键：QPS 同步上涨 → 是容量问题，扩容或限流；QPS 没变而 CPU 翻倍 → 是效率退化，必然对应一次变更（新版本、配置、数据分布变化如缓存击穿、某个大 key），扩容只是掩盖它。

    第三步：区分"热点函数"和"调用太多次"。火焰图上宽而平顶的是单函数自身耗时，优化实现；宽而下面还很深的是调用量大，要减少调用次数——两者的修法完全相反，看错了会做无用功。

    止血手段按代价排序：限流（保住大部分用户）→ 摘掉异常实例 → 扩容 → 关掉可疑的 feature flag / 降级非核心功能 → 回滚。

  4. 基础load average 很高但 CPU 基本空闲，怎么解释？

    因为 Linux 的 load average 不是"CPU 使用率"，而是 R 状态 + D 状态任务数的指数移动平均。D 是不可中断睡眠——通常在等块设备、等 NFS、等某些内核锁。传统 Unix 的 load 只算可运行任务，Linux 特意把 D 算进来是想表达"系统里有多少工作被卡住"，代价就是这个数字不再等价于 CPU 压力。

    所以 load 30 而 CPU 空闲，最常见的解释是一堆线程卡在 IO 上：一块盘退化、一个 NFS mount 挂了、云上的网络存储被限流。极端情况下一个坏盘就能把 load 顶到几十，而 CPU 完全闲着。

    怎么确认，一分钟内可以走完：

    $ vmstat 1 5          # r = 可运行（CPU 挤）；b = 不可中断阻塞（IO 堵）
$ ps -eo state,pid,comm | awk '$1 ~ /^D/'    # 谁在 D 状态
$ cat /proc/<pid>/stack                      # 卡在哪个内核函数
$ iostat -x 1                                # await / util% 定性存储

    b 列持续不为 0、ps 里一片 D 状态、/proc/<pid>/stack 都停在同一个内核函数上，基本就定了。/proc/<pid>/stack 这一步很有价值——它能直接告诉你是等块设备、等网络文件系统还是等某个内核锁。

    其他几种能造成"load 高 CPU 闲"的情况也要能说出来：

    • 不可中断的挂载点：hard mount 的 NFS 不可达，访问它的进程全部进 D 且 kill -9 都杀不掉。
    • 大量线程刚被唤醒：唤醒风暴瞬间抬高 R 计数，但每个线程只跑一点点，CPU 平均下来不高。这种 load 是尖峰而非持续。
    • 容器里的 load 是宿主机的：/proc/loadavg 不做 cgroup 隔离，容器里看到的是整台机器的 load。在容器里用 load 判断自己的负载是错的，应该看 cpu.stat 的 usage_usec 和 nr_throttled。

    方法论上的收获：load average 只适合当"有事发生"的粗糙信号，不能作为诊断依据。它把两种性质完全不同的排队（等 CPU、等 IO）加在一个数里，注定无法区分。真正该看的是 r / b 两列，或者更好——按饱和度设计的 PSI 指标（/proc/pressure/{cpu,io,memory}），它直接给出"有多少时间有任务因为该资源而卡住"，正是 load 想表达却表达不清的东西。

10.2 中级（区分熟练度）

  1. 中级服务被 OOM kill 了，怎么区分是内存泄漏还是 limit 配得太小？

    判据是形状，不是数值：泄漏是"与流量无关的单调上涨"，配置过小是"峰值超了但会回落"。

    把 RSS（容器里看 cgroup 的 memory.current 或 memory.stat 的 anon）按时间画出来，对着三个问题看：

    • 增长与流量相关吗？ 流量翻倍内存翻倍、夜间低峰回落 → 是水位问题，limit 偏小。内存曲线跟 QPS 曲线毫无关系、只跟运行时长相关 → 泄漏。
    • 重启后回到 baseline 再重新爬升吗？ 每次重启都从 300 MB 开始、几天后到 4 GB → 典型泄漏。
    • 有平台期吗？ 涨到某个值就稳住不动 → 那是缓存 / 连接池 / 分配器持有的内存达到稳态，不是泄漏。真泄漏没有上界。

    确认之后再看构成，把三类"假泄漏"排掉——这是最容易误判的地方：

    # 容器场景看构成，别看总量
$ cat /sys/fs/cgroup/<path>/memory.stat | head -5
anon 5033164800        # 只有这部分难回收，是判断依据
file 1073741824        # page cache，可回收，贴住上限完全正常
slab 218103808

$ dmesg | grep -i -A 20 "killed process"   # 看被杀时的 RSS 和 oom_score
    • page cache 被算进来：memory.current 包含 cache，它长期贴着上限是正常现象，不是即将 OOM 的信号。
    • 分配器没归还给内核：glibc / jemalloc 释放后可能只是 MADV_FREE 标记或留在 arena 里，应用侧已经 free 了但 RSS 不降。用 malloc_info / jemalloc 的 stats 对比"应用视角的活跃字节"与 RSS，差值大就是这一类，调 decay 参数即可，不用改代码。
    • 堆外内存：JVM 的 metaspace / direct buffer / 线程栈、Go 的 mmap 区、连接池里每连接的 buffer。"堆 dump 看起来很干净但 RSS 一直涨"几乎都是这一类，要看 smaps_rollup 和 NMT 而不是堆分析器。

    确认是真泄漏后定位：生产上用 memleak-bpfcc -p <pid>（开销约 5%，直接给出未释放分配的调用栈），托管运行时用各自的 heap dump。最常见的四个根因：无上界的缓存（没有 LRU / TTL）、事件监听或回调注册了没注销、连接/会话对象被全局容器持有、以及日志或指标标签基数爆炸（每个请求造一个新的 label 组合）。

    生产视角：两条路径通常都要走。 先把 limit 调到能撑过修复周期（并配上定时重启作为临时兜底），同时排查泄漏。只调 limit 是把爆炸推迟；只查泄漏则会在修好之前一直被 OOM。另外要检查 limit 是不是本来就没给堆外和 page cache 留余量——按 JVM -Xmx 直接设容器 limit 是很常见的配置错误，那必然 OOM。

  2. 中级fd 泄漏怎么定位？怎么做兜底？

    定位分三步：确认是泄漏 → 确认泄漏的是哪一类 fd → 定位到代码。

    ① 确认趋势。绝对值没有意义（一个网关有几万个连接很正常），要看它是否单调不降：

    $ while :; do echo "$(date +%s) $(ls /proc/<pid>/fd | wc -l)"; sleep 30; done | tee fd.log
$ cat /proc/<pid>/limits | grep "open files"    # 距离上限还有多远

    ② 按类型聚合，这一步基本就指明了方向：

    $ lsof -p <pid> | awk '{print $5}' | sort | uniq -c | sort -rn
  28417 sock      # socket 泄漏 → 连接没关或没复用
    312 REG       # 普通文件
     44 FIFO

    sock 占绝大多数时再看状态分布：ss -tanp | grep <pid>，大量 CLOSE_WAIT 是决定性证据——它意味着对端已经关了连接、内核也通知了你，但你的代码从来没调用 close()。这是 fd 泄漏最经典的指纹。大量 TIME_WAIT 则相反，那是你在主动关且没有复用连接，属于连接池缺失而不是漏 close。

    ③ 定位代码。ls -l /proc/<pid>/fd/ 直接看 symlink 指向什么（哪个文件、哪个对端地址），往往一眼就能对应到某个模块。要栈就用 bpftrace 抓 open 而不抓 close 的调用栈：

    $ sudo bpftrace -e '
  tracepoint:syscalls:sys_exit_openat /pid == TARGET && args->ret > 0/ {
    @open[args->ret] = ustack;
  }
  tracepoint:syscalls:sys_enter_close /pid == TARGET/ {
    delete(@open[args->fd]);
  }
  interval:s:60 { print(@open); }'    /* 60 秒后还留在表里的就是没关的 */

    兜底与预防，按有效性排序：

    • 语言层面消除手动 close：C++ 用 RAII 包装（unique_fd），Python 用 with，Java 用 try-with-resources，Go 用 defer。这是唯一的根本解——只要还依赖"记得调 close"，异常路径上就一定会漏。
    • 所有出站连接走连接池并设上限：既避免每次新建，也让泄漏从"耗尽 fd"退化为"池满等待"，故障面小得多。HTTP client 不复用 Session 是最高频的一类原因。
    • 把 fd 使用率做成告警：告 已用 / 上限 > 70% 而不是等 EMFILE。fd 泄漏是少数能被完美提前预测的故障，斜率稳定，能算出还有几天撞墙——不该等它崩。
    • ulimit 调大只是买时间：prlimit --pid X --nofile=65536 可以在线改，但它把每周崩一次变成每月崩一次，不解决问题；同时要注意系统级的 fs.file-max 和内存开销。
    • 连接必须有超时和空闲回收：很多"fd 泄漏"其实是对端消失后连接永远挂着，配上 TCP keepalive 或应用层 idle timeout 就自愈了。
  3. 中级服务不响应了，怎么判断是死锁还是"只是慢"？

    一句话判据：死锁是"永远不会好"，慢是"最终会好"。 所以最有效的手段是隔一段时间采两次栈做对比——这比任何单次快照都可靠。

    # 间隔 30 秒采两次
$ for i in 1 2; do gdb -p <pid> -batch -ex "thread apply all bt" > bt.$i; sleep 30; done
$ diff bt.1 bt.2
# Java: jstack -l <pid>   Python: py-spy dump   Go: /debug/pprof/goroutine?debug=2

    判读：

    • 栈完全一样、同样的线程卡在同样的位置 → 真卡住了（死锁、或等一个永不返回的外部调用）。
    • 栈在变、只是都很忙 / 都在同一个锁上排队 → 是慢，不是死。

    再看几个正交信号，能快速定性：

    • CPU 使用率：死锁时 CPU 几乎为 0（大家都在睡）。CPU 打满而不响应通常是活锁、忙等或 GC 风暴。
    • 线程状态：ps -L -p <pid> -o tid,stat,wchan。全是 S + futex_wait → 等用户态锁；D 状态 → 等 IO 或内核锁（这一类"卡死"其实是存储问题）；大量线程同一个 wchan → 强烈怀疑同一个资源。
    • 吞吐是否为零：完全零请求完成 = 死锁；还有少量请求在完成 = 严重排队/饱和。这个区别决定了止血手段完全不同。
    • 是不是线程池耗尽：这是最容易被误判成死锁的一类。所有 worker 都在等同一个慢下游，新请求根本拿不到线程，从外部看和死锁一模一样——但根因在下游超时没设或设得太长。栈上会看到一堆线程停在网络读上，而不是停在锁上。

    真死锁的确认要找环：T1 持 A 等 B，T2 持 B 等 A。JVM 的 jstack 会直接打印 "Found one Java-level deadlock" 并给出环；C++ 得自己从 thread apply all bt 里配对（谁在 pthread_mutex_lock，锁的 owner 又在等谁）。

    生产视角：止血一律是保留现场后 kill -9 重启（TERM 通常没用，因为处理信号的线程也卡着）。修复方向差别很大——真死锁靠全局加锁顺序约定、std::scoped_lock 一次锁多个、以及 try_lock_for 超时兜底，开发期用 ThreadSanitizer 提前发现；而"假死锁"（线程池耗尽 / 下游 hang）靠的是给所有外部调用设超时 + 熔断 + 隔离舱（不同下游用不同线程池）。后者在生产里出现的频率远高于前者，所以"任何跨进程调用都必须有超时"这条纪律，比任何死锁检测工具都值钱。

  4. 中级灰度和回滚的决策依据是什么？

    灰度的目的不是"稳一点"，而是把变更的影响面控制在可承受范围内，并且让坏结果在造成大规模伤害之前被指标发现。 所以设计灰度要回答三个量化问题，而不是凭感觉分批：

    • 爆炸半径：这一批影响多少用户 / 多少流量？第一批应该小到"全错了也不构成 incident"（常见是 1% 或单实例，内部流量优先）。
    • 观察窗口：这个变更的坏结果需要多久才会显现？CPU 和错误率是秒级；内存泄漏、fd 泄漏、缓存命中率退化、慢查询积累是小时甚至天级。观察窗口小于问题显现时间的灰度是假灰度——五分钟就全量的内存泄漏变更，灰度等于没做。
    • 判据（放行 / 中止的指标阈值）：必须在发布前写下来。事前定阈值和事后看图，结论经常相反——因为人在压力下会倾向于把噪音解释成"应该没事"。

    判据要选灰度组与对照组的对比而不是绝对值：错误率、P99、以及至少一个业务指标（下单成功率、消息投递率）。只看技术指标会漏掉最危险的一类问题——服务健康但业务逻辑错了：接口 200、延迟正常，但返回的数据是错的。这类故障纯靠技术指标永远发现不了。

    回滚的决策依据（同样应该事先约定）：

    • 默认动作是回滚，不是继续查。 只要故障时间线与某次变更对得上，回滚是最快、最可预测、可逆的止血手段。"再看五分钟说不定会自己好"是 incident 里最贵的一句话。
    • 回滚的前提是回滚本身安全。这需要提前设计：数据库 schema 变更必须先加后用、向后兼容、分两次发布（先上兼容新旧的 schema，再上用新字段的代码），否则回滚代码会撞上已经迁移过的数据。不可回滚的变更是架构缺陷，不是"这次特殊"。
    • 数据面变更（消息格式、缓存 key、存储编码）比代码更难回滚，因为脏数据已经写出去了。这类变更要用双写 + 影子读来灰度，回滚计划里必须包含数据修复方案。

    最后一条纪律：回滚决策要设时间上限而不是靠判断力。约定"影响面超过 X% 且 10 分钟内没有明确根因就回滚"，把决策从"当事人的判断"变成"团队的规则"——在压力下人的判断力是最不可靠的那个环节，而规则不会因为你觉得"就快查到了"而动摇。

10.3 高级（体现深度）

  1. 高级什么样的故障必须立刻回滚，而不是继续排查？

    先给判据，再给例外。只要满足"影响在扩大" + "存在可回滚的近期变更"，就立刻回滚，不管你觉得离根因有多近。理由很简单：排查时间是不可预测的，回滚时间是可预测的；在影响面持续累加时，你没有权利用用户的代价去赌自己的判断。

    四类必须无条件回滚的情况：

    • 数据正在被写坏。这是唯一一类"每多一秒都在增加不可逆损失"的故障——错误的写入、错误的删除、格式不兼容的消息进了队列。此时不但要回滚，还要先切断写入路径（关写、停消费者）。可用性可以事后恢复，数据一致性破坏了往往只能靠备份和人工对账。
    • 影响面在扩大且尚未见顶。错误率还在爬、故障从一个实例扩散到一片、下游开始跟着报警。级联失败的特征是指数扩散，等你查明白时已经是全站故障了。
    • 安全问题：权限校验被绕过、数据越权可见、密钥泄漏。这类"服务完全健康"的故障不能用可用性权衡，必须立即止损。
    • 你已经不理解系统状态了。多个变更叠加、监控自身也在报错、不同指标互相矛盾。回滚到一个"已知良好状态"的价值恰恰在于消除未知——在不理解现状的情况下继续操作，制造次生故障的概率极高。

    反过来，不该立刻回滚的情况也要能说清，否则就变成了另一种教条：

    • 回滚不安全：schema 已经迁移、数据格式已经变了，回滚旧代码会读不懂新数据。此时正确动作是向前修复（hotfix）或关掉 feature flag。这也说明了为什么"任何变更都要设计成可回滚"是硬要求。
    • 故障与变更无关：依赖方挂了、硬件坏了、流量突增。回滚不但无效，还会额外引入一次发布风险和一次流量抖动。
    • 已经止血且影响已被隔离：坏实例摘掉了、流量切走了。此时保留现场慢慢查是对的——事实上应该刻意留一个坏实例。
    • 回滚会引发惊群：过载场景下重启全部实例，冷缓存 + 连接重建可能比原故障更糟。这时要先限流再灰度重启。

    一个常被忽略的点：feature flag 关闭优于代码回滚。它秒级生效、粒度更细、不需要重新部署、不引入新的二进制。所以"高风险变更必须挂 flag"应该是架构约定——它把回滚决策的成本从"一次发布"降到"一次配置变更"，从而让人们真的敢在早期回滚。

  2. 高级一份合格的 postmortem 应该写什么？

    先明确目的：postmortem 的产出是"系统性的改进项"，不是"事故记录"。 判断一份复盘写得好不好，看它有没有回答"下次同类问题会不会被更早发现、影响会不会更小"，而不是看它写得多详细。

    必须有的几块：

    • 影响（放在最前面，用业务语言量化）：持续多久、多少用户/请求受影响、有没有数据损失、有没有资金或合规影响。不写影响的复盘无法排优先级——所有改进项都要和这个数字比才知道值不值得做。
    • 时间线：从"变更引入"而不是"告警触发"开始，一直到恢复。每个条目带时间戳和"谁做了什么、看到了什么"。时间线的价值在于暴露三个关键间隔：故障开始→告警（检测差距）、告警→有人响应（响应差距）、响应→止血（缓解差距）。这三个数字直接指出该改进哪一环，比任何主观总结都有用。
    • 根因分析：追到"为什么这个缺陷能进到生产"，而不是停在"某函数有个空指针"。至少往下问三层：代码为什么错 → 为什么测试/评审没拦住 → 为什么灰度没发现。停在技术层面的根因只能修一个 bug，往上追才能修一类 bug。
    • 做对了什么（不是客套）：哪个监控起作用了、哪个 runbook 有效、哪次决策正确。这些是要刻意保留和复制的资产，只写问题会让好的实践悄悄流失。
    • 改进项：每条必须有明确责任人、截止日期、可验证的完成标准，并且进入正常的排期系统而不是留在文档里。没有 owner 的 action item 等于没写。
    • 触发条件与预警信号：事后回看，有哪个指标其实提前几小时就异常了？这一项直接转化成新的告警规则。

    改进项的质量分层，这是资深与否的分水岭：

    弱
    "以后发布更小心"、"加强 code review"——依赖人的注意力，不可执行、不可验证，等于没做。
    中
    补一条告警、补一条 runbook、加一个测试用例。有效但只覆盖这一个场景。
    强
    让这类问题在结构上不可能发生或必然被更早拦住：加类型约束或静态检查、把危险操作做成需要二次确认、给所有外部调用加默认超时、把配置项收敛到有校验的模板、把手工步骤自动化。好的改进项减少的是"依赖人正确"的地方。

    还有两个实践细节：复盘要在 24–48 小时内写完初稿（记忆和上下文衰减很快，日志还没轮转掉）；以及应该有一个"是否需要复盘"的客观触发标准（如超过 X 分钟的用户可见故障、任何数据损失、任何安全事件），而不是由当事人自行判断——否则最该复盘的那些会被"这个不算大事"跳过。

  3. 高级为什么复盘要坚持"无指责"（blameless）？这不会变成没人负责吗？

    无指责的理由不是"对人友善"，而是指责会破坏你唯一的信息来源，从而让复盘失去价值。这是一个工程决策，不是文化偏好。

    机制上，指责导致三件必然发生的事：

    • 信息隐藏。故障最关键的细节往往只有当事人知道——他当时看到了什么、为什么那样判断、执行了哪条没记录的命令。一旦说出真相意味着被追责，人的理性选择就是模糊化、只说能自证清白的部分。而你无法修复一个你不知道真实经过的故障。
    • 抑制上报。人会倾向于自己悄悄修掉、不上报小问题。于是团队失去了"故障前的预警信号"，只能等它长成大事故。航空业和医疗业的安全体系正是靠"上报免责"才拿到了真实的近失事件数据。
    • 停在错误的根因上。"某人误操作"是一个让人满意的结论，因为它有出口（批评、罚款、换人）。但它同时终止了追问：为什么这条危险命令没有二次确认？为什么生产和测试环境的操作方式一样？为什么一个人就能造成全局影响？把根因定位到人，等于放弃了修复系统的机会——换个人上去，同样的坑还在那里。

    这里有个必须讲清的前提：无指责的立场是"人的行为在当时的信息和约束下是合理的"。这几乎总是成立的——没人早上起来打算搞坏生产。既然行为合理却导致了坏结果，那么问题在于信息不足、工具危险、流程有陷阱，这些都是可以被工程手段修复的。

    关于"会不会变成没人负责"，这是最常见的误解，要正面回答：无指责 ≠ 无责任（accountable but not blamed）。区别在于责任的形式：

    • 不做：把故障归因到个人、写进绩效、公开批评、要求道歉。
    • 要做：每个改进项有明确 owner 和期限；当事人通常是最适合主导复盘和落实改进的人（他理解上下文最深）；对反复发生的同类问题追问"为什么上次的 action item 没落地"——追责的对象是"改进没有执行"，而不是"故障发生了"。

    边界也要说清楚，否则会被当成免责牌：无指责适用于善意的失误。故意绕过安全流程、隐瞒故障、伪造数据不属于此列，那是纪律问题而不是工程问题。另外，无指责不等于不能说"这个设计很糟"——对事的批评要够狠，对人的评判要够克制。

    一句话总结这个取舍：你可以选择让人害怕犯错，也可以选择让系统不怕犯错，但只有后者会随时间变得更可靠。

  4. 高级怎么设计告警才不会被噪音淹没？症状告警和原因告警怎么选？

    核心原则一句话：页面告警（page，会把人叫起来的那种）只能基于"用户正在受影响"，其余一切都是仪表盘或工单。

    为什么要这么严：告警系统的真正约束不是技术，是人的注意力。一旦准确率低于某个水平，工程师就会开始无视告警——这时你不是"多了一些噪音"，而是整个告警系统失效了，包括那条真正重要的。噪音的代价是非线性的。

    症状告警（symptom-based）
    直接测量用户体验：错误率、P99 延迟、成功率、队列积压、数据新鲜度。覆盖面完整——不管根因是磁盘、代码、依赖还是配置，只要用户受影响就一定会触发。数量少、必然有意义，应该是 page 的唯一来源。
    原因告警（cause-based）
    测量内部状态：CPU > 80%、磁盘 > 85%、某队列长度、主从延迟。问题是既漏又吵：CPU 80% 可能完全健康（批处理正在跑），而 CPU 40% 也可能因为锁竞争已经不可用了。它的正确用途是加速定位（作为仪表盘和排障线索）以及预测性容量告警。

    原因告警只有两种情况值得升级为 page：

    • 该指标即将导致不可恢复的后果，且症状出现时已经太晚。磁盘写满、fd 耗尽、证书过期、license 到期、备份连续失败——这些有明确的斜率，可以算出"还有多久撞墙"，应该按剩余时间而不是阈值告警（"按当前速度 4 小时后写满"远比"已用 85%"有用）。
    • 它是无声故障：数据管道停了但接口全是 200、消费者 lag 在涨但没有报错。这类必须靠原因/数据面指标发现。

    降噪的具体手段，按收益排序：

    • 用 SLO 和错误预算燃烧率代替固定阈值。这是最有效的一招：同时看短窗口（如 5 分钟，抓急性故障）和长窗口（如 6 小时，抓慢性劣化），只有两个窗口同时超才 page。这天然过滤掉了瞬时抖动，又不会漏掉"每小时错 1% 持续一周"这种缓慢消耗预算的问题。
    • 加持续时间和最小样本量条件：错误率 > 5% 持续 5 分钟，且请求数 > N。低流量下的比率指标极不稳定，一个请求失败就是 100% 错误率。
    • 告警要有依赖抑制：数据库挂了就不要同时发出它上游二十个服务的告警。一次故障应该只叫醒一个人。
    • 每条 page 必须回答三个问题：影响是什么、第一步做什么（runbook 链接）、以及如果我不管会怎样。第三个问题最能筛掉伪告警——答案是"没什么"的，就不该 page。
    • 定期审计：统计每条告警的触发次数与"实际需要人工干预"的比例。命中率低于 50% 的规则要么修要么删。同时统计每次 on-call 的告警数量，超过几条就说明系统在消耗人而不是保护人。
    • 能自动处理的不要叫人：单实例故障应该由健康检查自动摘除并重建，只有"自动处理失败"或"故障实例比例过高"才升级为 page。

    最后一个容易忽略的方向：告警系统本身要有心跳（dead man's switch）。最危险的不是误报，是漏报——采集挂了、规则被误删、通道不通，此时一切安静，而故障正在发生。用一条"预期必然定期触发"的告警来反向验证链路通畅，是低成本高价值的保险。
