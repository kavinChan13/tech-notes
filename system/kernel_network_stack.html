01

收包与发包的完整路径

从网卡 DMA 到 socket 缓冲区

绝大多数后端工程师对网络的认知止步于 socket() / bind() / listen() / accept() / read()。这套 API 之下，一个以太网帧要经过硬件、中断、软中断、协议栈、socket 队列五个截然不同的执行环境才能到达你的 read()。搞不清这条路径，排障时就只能猜——「丢包了」这三个字，在这条路径上至少有八个含义完全不同的位置。

收包路径像机场到你家的国际快递。货机落地（网卡收到帧），包裹先卸到货站的固定格口（RX ring buffer，格口数量有限，装满了后面的货只能扔）；货站给分拣中心打一个电话说「有货了」（硬中断），但不会每来一件货打一次电话——那样接线员会被打崩，所以是「打一次电话，然后分拣员自己过来一次搬走一批」（NAPI 轮询）。分拣员把同一个收件人的十个小包合并成一个大箱（GRO）省得后面重复走流程，再依次过海关（netfilter）、查地址簿决定是本市派送还是转运（路由），最后放进你家楼下的快递柜（sk_receive_queue）。你什么时候下楼取（recv()）是你的事——但快递柜满了，后来的包裹就退回了。
struct sk_buff（skb）：内核里表示「一个网络包」的核心数据结构。它不是数据本身，而是一份描述数据在哪里、各层协议头偏移多少、归属哪个 socket 和设备的元信息。整条协议栈传递的都是 struct sk_buff * 这一个指针，真实的字节尽量原地不动——这是内核网络栈能跑到几十 Gbps 的前提。

1.1 收包：五种执行上下文的接力

这条路径不在一个执行上下文里跑完：DMA 不占 CPU，硬中断必须极短，软中断优先于普通进程，recv() 才是你的线程。跨上下文意味着每一段都有自己的排队点和丢弃计数器。

硬件 DMA 完全不占 CPU：描述符补不上，网卡只能在硬件层丢掉后续帧（rx_missed_errors）。硬中断几乎什么都不干——关本队列中断、napi_schedule()、触发 NET_RX_SOFTIRQ，立刻返回。软中断超 netdev_budget / netdev_budget_usecs 就把剩下的活推给 ksoftirqd/N，同时 time_squeeze 加一。大流量机器上它吃满一个核是溢出通道，不是异常本身。

驱动 poll() 把 DMA 页挂进 skb 的 frags[]，不拷字节。GRO 把同流连续小包合成一个大 skb，后面 IP / TCP / netfilter / 唤醒全都只走一遍——内核栈能扛 10G 小包，代价是抓包看到的不是线上真实的包（§9）。netif_receive_skb() 先喂 tcpdump tap 和 tc ingress，再 ip_rcv()：PREROUTING → 路由（本机 ip_local_deliver / 转发 ip_forward）→ tcp_v4_rcv 四元组查 socket。

入队有个关键分支：用户进程正持锁时，软中断不能动接收队列，skb 只能进 sk_backlog；否则直接进 sk_receive_queue。backlog 也受 sk_rcvbuf 约束，溢出记 TcpExtTCPBacklogDrop。

这一分支解释了一个很多人踩过的现象：应用越慢，丢包越多，而且丢的位置会变。应用读得慢 → sk_receive_queue 堆积 → 触及 sk_rcvbuf 上限 → 新包在软中断里被丢（TCPRcvQDrop）；同时应用长时间持锁 → 软中断只能走 backlog → backlog 也满 → TCPBacklogDrop。两个计数器指向的都是「应用侧慢」，但很多人只盯着网卡计数器，怎么调 ring size 都没用。

1.2 sk_buff：为什么整条路径尽量不拷贝

1500 字节的包若每层都拷一次，10Gbps 就是每秒几 GB 额外内存带宽。skb 的约束是：数据只在「网卡 DMA 进来」和「拷给用户态」两端各碰一次，中间全靠指针腾挪。

1.3 发包：对称，但不完全对称

发送侧看起来是收包的镜像，但有三个会在生产里咬人的差异。

① 有一次不可避免的拷贝。 send() 的用户态缓冲内核必须拷进 skb——TCP 要留副本重传，用户可能立刻改 buffer。想跳过用 MSG_ZEROCOPY（页被 pin，完成通知走 MSG_ERRQUEUE），或源头本就在页缓存里的 sendfile() / splice()。

② 多一层 qdisc。 dev_queue_xmit() 先选 TX 队列（XPS 按 CPU，否则按 skb hash），再交给 qdisc：立刻发（noqueue）、排队（fq_codel / htb）、或直接丢（队列满）。这是内核主动丢你自己的包的唯一地方，见 §6。

③ 一个 skb ≠ 一个包。 开 TSO 后内核可把最大 64KB 的巨型 skb 交给网卡，由硬件按 MSS 切帧、填 TCP 头和校验和。网卡不支持时内核用软件做同样的事，叫 GSO。

02

网卡与驱动层

ring buffer、中断合并、多队列与 RSS/RPS/RFS/XPS

这一层的问题有个共同特征：应用层完全无感，只表现为「偶尔丢包」「延迟毛刺」「某个核 si 打满」。而且它的计数器和内核栈的计数器分别在两个地方，不知道去哪看就永远查不出来。

2.1 RX ring 满了会怎样：两个容易混淆的计数器

RX ring buffer：网卡与驱动约定的描述符环形数组，每个描述符指向一块预分配的内存。它的大小（ethtool -g 里的 RX 值）不是「能缓存多少字节」，而是「CPU 来不及处理时，能积压多少个包」。它是一个吸收突发的水桶，不是提升吞吐的手段。
计数器来源含义该怎么办
rx_missed_errors网卡硬件计数器（ethtool -S）网卡收到了帧，但没有可用的 RX 描述符或内部 FIFO 溢出，硬件直接丢弃加大 ring（ethtool -G）、开多队列、检查软中断是否被饿死
rx_fifo_errors网卡硬件PCIe 带宽或内部 FIFO 跟不上，帧还没 DMA 出去就被覆盖多半是 PCIe 插槽位宽 / NUMA 跨节点问题
rx_dropped（/proc/net/dev）内核软件侧包已经进了内核，但被软件丢弃：未知协议、netns 无对应设备、VLAN 不匹配、backlog 满等看具体原因，跟 ring size 无关
rx_errors网卡硬件CRC 错、长度错、对齐错的总和物理层问题：网线、光模块、协商速率
rx_over_errors / 驱动私有的
rx_no_buffer_count		驱动私有不同驱动叫法不同，语义接近「没缓冲区」以驱动自己的 ethtool -S 为准
别把 ip -s link 的 dropped 当 ring 满。 那是软件侧 rx_dropped；ring 满通常在 rx_missed_errors 或 ethtool -S 私有计数。永远先看驱动原生计数。

2.2 中断合并：用延迟换 CPU

网卡每收到一个包就中断一次，10Gbps 小包场景下就是每秒上千万次中断——CPU 全部时间都在做上下文保存与恢复。中断合并（interrupt coalescing）让网卡「攒够 N 个包或等够 T 微秒再中断一次」。

命令目的判据
ethtool -c eth0看合并参数rx-usecs / Adaptive；被人改过要对照基线
ethtool -C … adaptive-rx off rx-usecs 8低延迟档金融 / RPC 短包；关自适应，中断绑到同 NUMA 不同物理核
ethtool -C … rx-usecs 200 rx-frames 64吞吐档批量传输；改完同时看延迟直方图和 si 占比
❌ rx-usecs=0

中断风暴，ksoftirqd 抢业务线程，p99 反而暴涨。低延迟 ≠ 零合并。

✅ 按业务分档

短包 8~20μs + 关自适应；批量 100~300μs。改完同时看延迟直方图和 si。

2.4 /proc/net/softnet_stat：最被低估的一个文件

每 CPU 一行、全是十六进制、没有表头。第 2 列只统计 enqueue_to_backlog() 因队列满而丢的包——物理网卡走 NAPI 直通，ring 满不会记在这里。

列字段含义不为零意味着什么
1processed本 CPU 处理过的包数看各 CPU 是否均衡；只有一两个 CPU 有值 = 中断没打散
2droppedper-CPU backlog 队列满而丢弃的包只有走 backlog 的路径才会计数（RPS、veth、loopback、非 NAPI 驱动）。物理网卡走 NAPI 直通，ring 满不会记在这里——这是最大的误区

2.5 多队列与 RSS：让多个核一起收包

RSS（Receive Side Scaling）：网卡硬件对每个包的四元组（或二元组）做 Toeplitz 哈希，按哈希值把包投递到 N 个 RX 队列中的一个，每个队列有独立的中断向量，可以绑到不同 CPU。同一条流永远落到同一个队列——这保证了单流的包序，也意味着单流的吞吐上限就是单核的处理能力。

03

netfilter 与 conntrack

五个 hook、表与链的优先级、连接跟踪表打满

netfilter 是内核网络栈里唯一一个「可以任意插手每个包」的框架：防火墙、NAT、负载均衡（IPVS）、容器网络（Docker、kube-proxy 的 iptables 模式）全都建在它上面。它的能力有多强，踩坑的花样就有多多——生产环境里最难查的一类网络故障，往往就藏在某条没人记得是谁加的规则里，或者藏在 conntrack 表里。

3.1 五个 hook 点与包的走向

netfilter hook：内核在 IP 层的五个固定位置埋下的回调点。每个 hook 上挂着一串按优先级数字从小到大排序的处理函数，iptables 的每张「表」其实就是注册在某几个 hook 上、拥有特定优先级的一组回调。「表」决定优先级，「链」决定挂在哪个 hook 上。

3.3 连接跟踪：状态机与它的代价

conntrack（连接跟踪）：内核为每一条「流」维护一个条目，记录五元组、双向的转换关系、状态和超时时间。它是有状态防火墙和 NAT 的基础——没有它，就无法表达「只允许我主动发起的连接的回包进来」。代价是：每条流占一个哈希表条目（约 300 字节量级）和一次哈希查找，而且它是全局共享的有限资源。

conntrack 的状态和 TCP 自身的状态不是一回事，面试里经常被混淆：

conntrack 状态含义典型规则用法
NEW该方向第一个包，尚未看到回包-m conntrack --ctstate NEW -j ACCEPT 放行主动连接
ESTABLISHED双向都见过包了有状态防火墙的第一条规则永远是放行它
RELATED与已有连接关联的新连接（FTP 数据通道、ICMP 差错报文）需要对应的 helper 模块识别
INVALID无法归入任何连接（乱序到达的 RST、超时后姗姗来迟的包）通常直接 DROP；但在非对称路由下会误杀正常流量
UNTRACKED被 raw 表 -j NOTRACK 显式排除跟踪高 pps 的 DNS / 日志上报流量

此外 TCP 连接在 conntrack 内部还有自己的一套子状态机（SYN_SENT / SYN_RECV / ESTABLISHED / FIN_WAIT / CLOSE_WAIT / LAST_ACK / TIME_WAIT / CLOSE），每个子状态有独立的超时时间。其中 nf_conntrack_tcp_timeout_established 默认是 432000 秒（5 天）——这个值大得离谱，是很多表满事故的根源。

3.4 conntrack 表打满：现象、定位与止血

conntrack -S 字段含义非零说明什么
insert_failed插入新条目失败典型是 NAT 端口分配冲突（多个连接想用同一个转换后的源端口）或表满
drop因为无法建条目而丢包表满的直接证据
early_drop表满时，强行踢掉一个尚未 ESTABLISHED 的旧条目腾位置已经在拆东墙补西墙了
invalid被判为 INVALID 的包数大量出现要怀疑非对称路由或 conntrack 超时过短
search_restart查找过程中哈希桶被并发修改，重来一次少量正常；暴涨说明桶太少、冲突严重
chaintoolong哈希桶链过长（较新内核）提高 nf_conntrack_buckets
命令目的判据
iptables -t raw -A PREROUTING -p udp --dport 53 -j NOTRACK（OUTPUT 对称一条）DNS 等短连接不跟踪两个方向都要写；nft：udp dport 53 notrack

超时调太短也会出事。 空闲长连接条目被删后，后续数据包被判 INVALID——「看着通，空闲一会儿卡死」。keepalive 必须小于该值。
上面这几档都是在保留 conntrack 的前提下省着用。业务连接数本身就是几十万量级的接入型服务，调参只能拖延——真正的出路是让这条转发路径根本不产生条目。IoT 接入网关架构设计 · ADR-001 记录的就是这个决策：外部 L4 DSR + hostNetwork，整条路径不过 kube-proxy，conntrack 归零。判据：表满是「某一类短连接异常多」造成的，按本节分类对症；是「连接数天生就超过表容量」造成的，那是接入层选型问题，参数改不动它。

3.5 NAT 端口耗尽

SNAT / MASQUERADE 要给每条出向连接分配一个「源 IP + 源端口」的组合，使回包能被唯一还原。一个源 IP 大约只有 2.8 万到 6 万个可用端口（受 net.ipv4.ip_local_port_range 约束）。当大量容器共用一个宿主机 IP 访问同一个目的 IP:Port（比如所有 Pod 都连同一个 Redis 或同一个外部 API）时，可用组合会被迅速耗尽。

命令目的判据
sysctl net.ipv4.ip_local_port_range看可用源端口默认 32768–60999，约 2.8 万
conntrack -S 看 insert_failedNAT 端口争用 / 表满快速增长 + 应用连超时
conntrack -L | grep 'dst=… dport=6379' | wc -l同一目的的 NAT 条数贴着端口上限就是耗尽

NAT 端口耗尽的四种解法（按优先级）

  • 减少连接数：客户端上连接池复用，别每次请求新建连接。这是根治，其它都是缓解。
  • 扩大源 IP 池：-j SNAT --to-source 10.0.0.10-10.0.0.20，N 个 IP 就是 N 倍的端口空间。云上对应 NAT 网关多绑几个弹性 IP。
  • 放宽端口范围：sysctl -w net.ipv4.ip_local_port_range="10240 65535"，注意不要与监听端口冲突（配合 ip_local_reserved_ports）。
  • 绕开 NAT：容器直接用可路由 IP（underlay / IPvlan L3 / 云 VPC CNI），从根上不需要 SNAT。
MASQUERADE 下两个 CPU 可能抢同一个转换端口，insert_failed++，偶发万分之一的 SYN 丢失要等 1 秒重传。加 --random-fully 降低碰撞。
04

路由与邻居

FIB 查找、策略路由、rp_filter 三档、ARP 表老化

路由决定包往哪个接口发、下一跳是谁；邻居子系统（ARP / NDP）解决「知道了下一跳的 IP，可它的 MAC 是多少」。这两层平时透明得让人忘了它们存在，一旦机器有多张网卡、或者进了容器 / VPN / 双栈环境，它们就是故障率最高的地方。

4.1 路由查找：三张表、一棵 trie

FIB（Forwarding Information Base）：内核里真正用于查找的转发表，按最长前缀匹配组织成压缩前缀树（fib_trie）。早期内核在 FIB 之前还有一层「路由缓存」（routing cache），因为容易被哈希碰撞攻击且在多核上争抢严重，已在 Linux 3.6 移除；现在每个包直接查 trie，配合 per-CPU 的 dst_entry 引用来摊薄开销。

系统默认三张表，按 ip rule 优先级依次查：local（本机地址与广播，内核自动维护）→ main（平时 ip route add 进这张）→ default（通常空）。排障最有用的不是 ip route show，而是 ip route get——让内核真的跑一遍查找。

命令目的判据
ip rule show看查表顺序0 local / 32766 main / 32767 default；策略规则插在中间
ip route get 8.8.8.8真实查找结果含 src、dev、via；指定 from 诊断多网卡回包
ip route get 192.168.1.23 from 1.2.3.4 iif eth1模拟入向（含 rp_filter）Invalid cross-device link = 被 rp_filter 拒了
ip route get 10.20.30.40 mark 0x64带 fwmark 的策略表确认分流规则真的命中

4.2 策略路由：源地址、mark 与多张表

普通路由只看目的地址。策略路由按源地址、入接口、fwmark、TOS 选不同表——多线路出口、VPN 分流、容器多网卡的标准工具。

4.3 rp_filter：三个取值，一条容易被忽略的合并规则

反向路径过滤（Reverse Path Filtering，RFC 3704）：收到一个包时，内核用它的源地址反查路由表——「如果我要给这个源地址发包，会从哪个接口出去？」如果答案不是这个包进来的接口，就认为源地址被伪造，丢弃。它是防 IP 欺骗的基础手段，也是非对称路由环境下最常见的「莫名其妙丢包」元凶。
取值名称行为适用场景
0关闭不做任何反向路径检查路由器、需要非对称路由的多线出口、某些 VPN / anycast 场景
1严格模式反查结果必须正好是收包接口，否则丢弃单出口的普通服务器；安全性最高
2松散模式只要源地址在任意一个接口上可达就放行，不要求接口一致多网卡 / 非对称路由但仍想挡掉完全不可路由的伪造源地址
最容易踩的一条：all 与接口值取的是「较严格的那个」。 内核实际生效的值是 net.ipv4.conf.all.rp_filter 与 net.ipv4.conf.<iface>.rp_filter 两者的最大值。所以只把 eth1.rp_filter 设成 0，而 all.rp_filter 还是 1，结果依然是严格模式——「我明明关了啊」就是这么来的。要真正关闭必须两个都改，而且 all 的改动不会自动同步到已存在的接口上，新建接口则继承 default 的值。
命令目的判据
sysctl -a | grep '\.rp_filter'一次看清 all / default / 各接口别只看 all；接口 0 而 all=1 仍然是严格模式
nstat -az | grep -i ReversePathFilter证明是 rp_filter 在丢名字带 Tcp，实际统计 IP 层所有被丢的包
sysctl -w net.ipv4.conf.all.log_martians=1临时看具体哪些包dmesg 的 martian source；很吵，查完关
TcpExtIPReversePathFilter 名字带 Tcp，实际统计 IP 层所有被 rp_filter 丢的包。「部分客户端连不上」先看它是否在涨。

与 rp_filter 同一族、经常一起出问题的还有 arp_ignore 和 arp_announce：当多张网卡在同一个二层网段时，Linux 默认会用任意一张网卡回应对所有本机 IP 的 ARP 请求（所谓 ARP flux），导致 MAC 学习混乱。LVS 的 DR 模式必须在真实服务器上设 arp_ignore=1（只回应目标 IP 配置在本接口上的 ARP 请求）和 arp_announce=2（发 ARP 请求时使用最合适的本地地址），否则 VIP 会被真实服务器抢答。

4.4 邻居表：ARP 缓存与 gc_thresh

邻居表就像小区门口的门牌-住户对照本。你要给「3 栋 502」送东西，得先知道那家人叫什么（IP → MAC）。对照本容量有限，久不联系的条目会被划掉（老化）。小区住户特别多的时候（大二层网络、几千台机器同网段），对照本被塞爆，快递员每次都得重新去问一遍——这就是 neighbour table overflow 的现场。
命令目的判据
ip -s neigh show条目数与状态FAILED 多、或 wc -l 接近 gc_thresh3
dmesg | grep -i neighbour表满现场neighbor table overflow
sysctl net.ipv4.neigh.default.gc_thresh{1,2,3}水位：不回收 / 强制回收 / 硬上限默认 128 / 512 / 1024；K8s 大二层常需上调一个量级
邻居状态含义下一步
INCOMPLETE已发出 ARP 请求，还没收到应答包被暂存，超时未答则丢弃并转 FAILED
REACHABLE最近确认过可达可达时间到期后转 STALE
STALE条目还在，但久未确认下次要用时转 DELAY，仍可先按旧 MAC 发包
DELAY / PROBE正在后台重新探测探测成功回 REACHABLE，失败转 FAILED
FAILED探测失败会被回收；发往该地址的包直接失败
PERMANENT手工静态添加（ip neigh add ... nud permanent）永不老化，也永不自动纠错
NOARP该设备不需要 ARP（如点对点隧道、lo）—
邻居表满在Kubernetes 大集群里格外常见：几千个 Pod 全在一个大二层网段，加上 Service 的虚拟 IP，条目数轻松破万，而 gc_thresh3 默认才 1024。症状是集群里随机的、间歇性的 Pod 间连接失败，抓包看不到任何 TCP 层异常（因为包根本没发出去），只有 dmesg 里那一行 overflow。这是「先看 dmesg」这条老规矩至今仍然有效的原因之一。

网络命名空间与虚拟设备

netns / veth / bridge / macvlan / ipvlan / tun-tap

容器网络听起来很复杂，其实只是几个内核原语的组合。把这几个原语单独拆开理解一遍，再看 Docker、CNI、Service Mesh 的网络方案，会发现它们都是同一套积木的不同搭法。

5.1 netns：一整套独立的网络栈

network namespace：内核把「网络」相关的全部全局状态做了一次复制隔离。每个 netns 有独立的：网络接口列表、IP 地址、路由表与 ip rule、ARP/邻居表、netfilter 规则与 conntrack 表、/proc/net 下的全部统计、以及端口号空间。因此两个 netns 里可以各自有一个进程监听 80 端口，互不冲突。
netns 像同一栋写字楼里的两家公司：共用大楼的电力和电梯（同一个内核、同一份 CPU 和内存），但各自有独立的前台、内部分机号、门禁名单和收发室。A 公司的 8080 分机和 B 公司的 8080 分机是两个完全不同的号码；要互相联系，得走大楼的走廊（veth pair）或者总机（bridge）。

流量控制 tc

qdisc 分类、bufferbloat 与 fq_codel、netem 与 htb

tc（traffic control）是内核里被严重低估的一个子系统。大多数人只知道它能限速，其实它同时是延迟治理工具（fq_codel 治 bufferbloat）、故障注入工具（netem 造延迟丢包）和eBPF 挂载点（clsact，见 §7）。而且它有个特点：默认配置在很多机器上就是错的，只是没人去看。

6.1 qdisc 是什么，它在路径的哪一段

qdisc（queueing discipline，排队规则）：挂在网络设备发送方向上的调度器。dev_queue_xmit() 把 skb 交给 qdisc，qdisc 决定「下一个发哪个包、什么时候发、要不要丢」。它是内核里唯一会主动丢弃你自己发出的包的地方——发送缓冲区满了 send() 会阻塞或返回 EAGAIN，而 qdisc 队列满了是静悄悄地丢。
qdisc 像高速公路收费站。车（包）到了收费站不是立刻放行，而是按某种规则排队：先到先得（pfifo）、按车道分优先级（prio）、每条车道轮流放一辆（fq_codel）、每小时最多放 N 辆（tbf/htb）。收费站的停车场大小就是队列深度：太小，车流一波动就把车赶走（丢包）；太大，最后一辆车要在场里等半小时——车没丢，但迟到了。bufferbloat 说的就是「停车场造得太大」这件事。

6.2 bufferbloat：包没丢，但延迟涨了十倍

bufferbloat：为了「不丢包」把缓冲配太大，TCP 感知不到拥塞，把队列填满并维持（standing queue）。带宽跑满，每个包却多等几百毫秒。

典型症状：「一开始下载，别的什么都用不了了」。空闲 ping 20ms，一有大流量变成 800ms——这个差值就是量化指标。

6.5 限速：tbf 与 htb

命令目的判据
tc qdisc add … tbf rate 100mbit burst 32kbit latency 400ms整机出向令牌桶最简单的限速
htb：根 1G，1:10/20/30 保证 400/400/200、ceil 各异，叶子挂 fq_codel多业务分带宽很多教程漏掉叶子 AQM
tc filter … u32 match ip dport 443 或 fw mark分类tc -s class show 看 lended / borrowed
htb 概念含义调错了会怎样
rate该类的保证带宽，任何时候都能拿到所有子类 rate 之和超过父类 rate → 保证形同虚设
ceil该类的上限，空闲时可借用兄弟的带宽借到这个数ceil == rate = 完全隔离、不共享；ceil 太大 = 隔离失效

quantum一次轮到该类时可以发多少字节，影响类间公平性由 r2q 推导，太小会 quantum is too small 报警
lended / borrowed借出 / 借入的包数观察带宽共享是否真的在发生
giants超过 MTU 的包数非零多半是 TSO/GSO 的大 skb 进了 qdisc，会让限速精度变差
限速与 TSO 的相互干扰：开了 TSO/GSO 之后，进 qdisc 的是一个最大 64KB 的巨型 skb。htb 按「包」调度，一个 64KB 的包一次就发出去了，导致短时间尺度上速率剧烈抖动，限速曲线不平滑。要求精确限速时可以关掉 TSO/GSO（代价是 CPU 上升），或者改用支持 tc 层分段的方案。这也是为什么用 fq 做 pacing 通常比用 htb 限速更平滑——fq 是按时间给每个包排发送时刻的。
07

XDP 与 eBPF 数据面

三种运行模式、AF_XDP、tc-bpf 与内核旁路的取舍

前面六章讲的都是「内核给你什么，你怎么配」。XDP 和 tc-bpf 换了一个思路：把你自己的代码塞进内核的收发路径里，在包还没被加工成 skb 之前就做出决策。这是过去十年 Linux 网络栈最大的一次能力扩张。

7.1 XDP 在路径上的位置决定了它的价值

XDP（eXpress Data Path）：在驱动的收包函数里、分配 sk_buff 之前执行的 eBPF 程序。它拿到的是一块裸内存（xdp_md 里的 data / data_end 指针），返回一个动作码决定这个包的命运。因为跳过了 skb 分配、GRO、netfilter、路由的全部开销，单核可以做到千万级 pps 的丢弃或转发。
运行模式在哪执行性能要求用途
native（driver 模式）驱动的 poll() 里，skb 分配之前最高，单核可达千万 pps 级别驱动实现了 XDP 支持（主流万兆网卡驱动大多支持）生产环境的默认选择
offload网卡固件里，包根本不进主机不占主机 CPU少数 SmartNIC（历史上 Netronome NFP 系列）超大规模 DDoS 清洗；硬件生态很窄
generic（skb 模式）netif_receive_skb 附近，skb 已经分配好了最低，比 tc-bpf 还慢任何设备都能用只用于开发调试，别在生产上用它跑高性能路径
「上了 XDP 没提速」多半跑在 generic。 加载后 ip link show 必须是 xdp 不是 xdpgeneric。virtio-net / veth 也支持 XDP，但语义不完全一样（veth 上 XDP_TX 发回对端）。

7.2 XDP 的动作码

返回值含义典型场景
XDP_PASS交给正常内核栈继续处理默认放行
XDP_DROP就地丢弃，连 skb 都不分配DDoS 清洗、ACL。这是 XDP 最经典也最有性价比的用法
XDP_TX改完包从同一张网卡原路发回去L4 负载均衡的 DSR 回程、ICMP 应答、ARP 应答
XDP_REDIRECT转发到另一个设备，或投递到 AF_XDP socket、CPUMAP软件路由器、把包甩给用户态处理
XDP_ABORTED出错丢弃，并触发 xdp:xdp_exception tracepoint程序内部错误路径；生产上应该监控这个 tracepoint
 
#include <linux/bpf.h>
#include <linux/if_ether.h>
#include <linux/ip.h>
#include <linux/udp.h>
#include <bpf/bpf_helpers.h>

/* 一个 per-CPU 数组做统计：[0]=通过 [1]=丢弃。用 per-CPU 避免多核原子争抢 */
struct {
    __uint(type,        BPF_MAP_TYPE_PERCPU_ARRAY);
    __uint(max_entries, 2);
    __type(key,   __u32);
    __type(value, __u64);
} stats SEC(".maps");

static __always_inline void bump(__u32 idx) {
    __u64 *v = bpf_map_lookup_elem(&stats, &idx);
    if (v) (*v)++;
}

SEC("xdp")
int xdp_drop_dns_flood(struct xdp_md *ctx)
{
    void *data     = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;

    /* 每一次解引用前都必须做边界检查，否则 verifier 直接拒绝加载。
       这不是防御式编程的建议，是硬性要求——内核不信任你的算术。 */
    struct ethhdr *eth = data;
    if ((void *)(eth + 1) > data_end)
        return XDP_PASS;
    if (eth->h_proto != bpf_htons(ETH_P_IP))
        return XDP_PASS;

    struct iphdr *ip = (void *)(eth + 1);
    if ((void *)(ip + 1) > data_end)
        return XDP_PASS;
    if (ip->protocol != IPPROTO_UDP)
        return XDP_PASS;

    /* IP 头是变长的（ihl 以 4 字节为单位），不能假定 20 字节 */
    if (ip->ihl < 5)
        return XDP_PASS;
    struct udphdr *udp = (void *)ip + ip->ihl * 4;
    if ((void *)(udp + 1) > data_end)
        return XDP_PASS;

    /* 丢掉打向本机 53 端口的 UDP：本机不是 DNS 服务器，这些都是反射攻击 */
    if (udp->dest == bpf_htons(53)) {
        bump(1);
        return XDP_DROP;          /* 到此为止：不分配 skb，不进协议栈 */
    }

    bump(0);
    return XDP_PASS;
}

7.5 什么时候值得放弃内核栈

方案性能量级（单核，64B 小包）你要付出什么适用
普通内核栈 + socket百万 pps 量级什么都不用付99% 的业务
tc-bpf数百万 pps写 eBPF、过 verifierService 转发、策略、可观测
XDP native千万 pps 量级（丢弃/转发）受限的编程模型，调试困难DDoS 清洗、L4 LB、软件路由
AF_XDP接近线速自己处理协议，但网卡仍归内核管需要用户态处理但不想独占网卡
DPDK / 内核旁路线速网卡被独占、CPU 核 100% 空转轮询、自带一套 TCP/IP 栈、失去所有内核工具（tcpdump、ss、iptables 全部失效）、运维体系要重建专用网元：NFV、防火墙、交换机、行情网关
XDP vs DPDK 的答案在运维成本，不在 pps。 DPDK 独占网卡：没有 ip/tcpdump/ss，协议栈自己实现，核永远 100%。只适合整机就是为了转发。XDP 是内核路径上的快速通道，剩下的照常走栈。机器上还跑着需要正常网络栈的业务，就选 XDP。
eBPF 的完整体系（verifier、map 类型、CO-RE、bpftrace / bcc 的使用、可观测性程序的写法）见 eBPF 与可观测性。本章只覆盖它在数据面转发上的那一小块。
08

协议栈调优

两个 backlog 队列、TIME_WAIT、缓冲区自动调优、BBR

先说结论，再讲细节：不要抄网上的 sysctl 大礼包。 那些「Linux 网络优化必备 30 条」的清单里，通常有三分之一在现代内核上已是默认值（改了等于没改）、三分之一在你的场景下没有意义（比如给一台内网 RPC 服务器调 BBR）、还有几条是有害的（tcp_tw_recycle、盲目 SO_RCVBUF、把 tcp_mem 拉到天上）。每一个参数都应该能回答三个问题：什么症状让我要改它？改完我看哪个指标验证？它的副作用是什么？ 答不上来就别改。

8.1 两个队列：SYN queue 与 accept queue

listen() 之后内核维护两个队列，很多人只知道一个。

# LISTEN 行特殊语义：Recv-Q=当前排队，Send-Q=上限
$ ss -lnt
State   Recv-Q  Send-Q  Local Address:Port
LISTEN  128     128           0.0.0.0:8080
        ^^^ 满了：当前=上限，应用没在 accept
只调 somaxconn 未必有用。 实际大小是 min(listen backlog, somaxconn)。应用写死 listen(fd, 128) 时 Send-Q 仍是 128。两边都要改。5.4 前默认就是 128。
❌ 一看到溢出就调大队列

队列变大只是让排队的连接更多、等得更久。如果应用每秒只能 accept 1000 个而进来 5000 个，队列从 128 加到 8192 只是把「立刻失败」变成「等 8 秒后失败」，用户体验反而更差，而且内存里挂着一堆已完成握手的连接。

✅ 队列是缓冲，不是产能

队列只该用来吸收突发。持续溢出说明产能不足，要看的是：accept 线程是不是在做本该异步的事？accept() 后有没有阻塞的 DNS 反查 / 鉴权调用？要不要上 SO_REUSEPORT 多进程分担？先把 accept 循环做成「只接连接、立刻交给工作线程」，再谈队列大小。

tcp_abort_on_overflow 默认 0 = 队列满时静默丢 ACK，客户端以为连上了、几秒后才超时。设 1 立刻 RST。快速失败对有重试的客户端更友好，瞬时突发也会被硬拒。

8.2 TIME_WAIT：被误解最深的状态

TIME_WAIT：主动关闭连接的那一端，在发出最后一个 ACK 后进入的状态，持续 2×MSL（Linux 里写死为 60 秒，TCP_TIMEWAIT_LEN，没有 sysctl 可以改）。它存在的两个理由缺一不可：① 保证最后那个 ACK 丢失时，对方重传的 FIN 还能被正确响应，否则对方会收到 RST；② 让网络中该连接的迟到报文自然消亡，防止被相同四元组的新连接错误接收。
TIME_WAIT 像退租后押金的观察期。你搬走了，但房东要留 60 天：万一还有你的快递寄到这个地址，得有人签收退回；也防止下一位租客收到本该给你的信。觉得「几万个 TIME_WAIT 是资源泄漏」的人，是把观察期当成了占用。 事实上一个 TIME_WAIT 只占一个很小的 tcp_timewait_sock（远小于完整 socket），几万个也就几 MB 内存。
常见说法真相
「TIME_WAIT 太多会把内存吃光」每个约几百字节，10 万个不到 100MB。tcp_max_tw_buckets 是硬上限，超了会直接销毁并打印告警，不会 OOM
「服务端 TIME_WAIT 多说明有问题」说明是服务端在主动关闭。HTTP 短连接、服务端主动 close 就是这样。真要减少，应该改成长连接 / keep-alive，而不是调内核参数
「TIME_WAIT 导致端口耗尽」只对主动发起连接的一方成立（客户端 / 做反向代理的网关）。服务端监听固定端口，TIME_WAIT 不占用新端口
「开 tcp_tw_recycle 就好了」这个参数已在 Linux 4.12 被移除。它按「对端 IP」维度记录 PAWS 时间戳，在客户端处于 NAT 之后时会把时间戳更小的那些客户端的 SYN 全部丢掉——症状是「同一个出口 IP 后面的部分用户随机连不上」，是历史上最著名的坑之一
真正要处理 TIME_WAIT 的只有一种情况：本机当客户端/代理，向同一目的海量短连接，端口 60 秒内被占满，报 EADDRNOTAVAIL。顺序：连接池 → 扩大 ip_local_port_range → tcp_tw_reuse=1 → 增加目的地址。绝不要用 tcp_max_tw_buckets 去「压制」。

8.3 缓冲区：自动调优，以及怎么把它关坏

TCP 接收缓冲默认按 BDP 在 tcp_rmem 的 min/max 之间伸缩。rmem_max 只约束显式 setsockopt；tcp_mem 是全系统页数水位，超 pressure 会压缩并记 TCPMemoryPressures。ss -tm 的 rb/tb/d 是单连接实况。

❌ 应用里显式 setsockopt(SO_RCVBUF)

一旦显式设置，内核永久关闭这个 socket 的自动调优，缓冲区钉死。长肥管道 256KB 可能远远不够（100ms × 1Gbps ≈ 12MB），短 RTT 又白占内存。内核会把你给的值翻倍记账，getsockopt 读回来容易以为设错了。

✅ 让内核自己调，只调上限

高 BDP 把 tcp_rmem / tcp_wmem 的 max 抬高；应用侧什么都不做。自动调优需要时长到上限，不需要时保持很小。只有明确知道流量特征、默认策略确实不合适时（多租户限单连接内存）才该显式设置。

8.4 拥塞控制：cubic 与 BBR 的边界

cubic（默认）BBR
拥塞信号丢包。丢包即降窗模型：持续测量瓶颈带宽（BtlBw）与最小 RTT（RTprop），按二者乘积定发送速率
擅长常规网络；与其它 cubic 流公平共存；行为可预测有随机丢包的长距离链路（跨国、卫星、劣质无线）——丢包不再意味着降速
不擅长长肥管道上随机丢包会严重压低吞吐；深队列下会把缓冲区填满（加剧 bufferbloat）与 cubic 共享浅缓冲区链路时可能抢占过多带宽（公平性争议）；ACK 聚合严重的链路上带宽估计会偏高
对队列的影响倾向于填满瓶颈队列主动把在途数据量控制在 BDP 附近，队列更浅、延迟更低
配套无特殊要求建议配 fq qdisc：BBR 依赖精确 pacing

切 BBR 必须同时把 qdisc 换成 fq。灰度用 setsockopt(TCP_CONGESTION, "bbr")。判据只有一句：链路上有没有与拥塞无关的丢包。有（跨洲 / 移动 / 劣质公网）才值得切；内网亚毫秒丢包近 0 基本没收益——那是抄大礼包。

8.5 SO_REUSEPORT：多进程共享监听端口

传统的多进程服务器有两种做法，都有问题：父进程 listen() 后 fork，所有子进程在同一个 fd 上 accept()（惊群：一个连接到来唤醒所有进程，只有一个成功）；或者用 epoll 监听同一个 listen fd（epoll 惊群，需要 EPOLLEXCLUSIVE 缓解）。

SO_REUSEPORT 让多个 socket 绑定同一个「IP:Port」，内核在收到 SYN 时按四元组哈希直接选中其中一个，只唤醒那一个进程。每个 socket 有自己独立的 accept 队列。

int fd = socket(AF_INET, SOCK_STREAM, 0);
int on = 1;
/* 必须在 bind() 之前设置；每一个想共享端口的 socket 都要设 */
setsockopt(fd, SOL_SOCKET, SO_REUSEPORT, &on, sizeof(on));
bind(fd, (struct sockaddr *)&addr, sizeof(addr));
listen(fd, 8192);
/* 每个工作进程/线程独立走一遍上面四步，各自有独立的 accept 队列 */
SO_REUSEPORT 两个坑。 ① 关闭某个 listen socket 时，已哈希到它、还在 accept 队列里的连接会被 RST，组重新哈希可能让握手中的 SYN 丢归属。关掉前先停 accept、排干队列。② 内核按连接哈希不是按请求，长连接生命周期差大会严重不均。

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础描述一个 TCP 数据包从网卡到达应用 recv() 的完整路径，并说明每一段在什么执行上下文里跑。

    分五个执行上下文接力：

    • 硬件 DMA：网卡把帧直接写进驱动预分配的 RX ring 缓冲区，不占 CPU。
    • 硬中断（hardirq）：驱动的中断处理函数只做三件事——关掉本队列中断、napi_schedule() 把 NAPI 结构挂上本 CPU 轮询链表、触发 NET_RX_SOFTIRQ，然后立刻返回。这段是关中断的，必须极短。
    • 软中断（softirq / ksoftirqd）：net_rx_action() 调用驱动的 poll()，为每个包构造 sk_buff（数据页直接挂进 frags，不拷贝），经 napi_gro_receive() 做 GRO 聚合，再进 netif_receive_skb()——这里会先喂 AF_PACKET tap（tcpdump）、过 tc ingress，然后按协议分发到 ip_rcv()。
    • 仍在软中断：IP 层过 netfilter PREROUTING（含 conntrack、DNAT），做路由判定；目的是本机则 ip_local_deliver() 过 LOCAL_IN，交给 tcp_v4_rcv() 用四元组查 socket。
    • 入队分支：若此刻没有用户进程持有该 socket 的锁，直接放进 sk_receive_queue 并唤醒等待者；若有进程正持锁，则放进 sk_backlog，由该进程释放锁时处理。
    • 用户上下文：recv() → tcp_recvmsg() 把数据拷到用户缓冲区。

    发送侧对称但有三点不同：必须有一次用户态到内核的拷贝（TCP 要留副本重传）；多一层 qdisc 排队（唯一会主动丢弃自己发出的包的地方）；TSO 让一个 skb 对应多个真实的线上帧。

  2. 基础NAPI 是什么？它为什么能避免中断风暴？ksoftirqd 吃满一个核是不是故障？

    NAPI 是「中断 + 轮询」的混合收包框架。 空闲时靠中断唤醒（省 CPU），一旦收到第一个包就关掉该队列的中断、切换到轮询模式批量取包，取空之后才重新打开中断。类比是「门铃响一次，我就守在门口一直收货，直到没货了才回屋等下一次门铃」。

    它避免中断风暴的关键在于：大流量下中断被主动关闭，一次中断可以摊薄到成百上千个包上，中断频率不再随 pps 线性增长。

    两级预算限制单次轮询的时长：每个 NAPI 实例的 weight（通常 64）、以及一轮 net_rx_action() 的 net.core.netdev_budget（默认 300 包）和 netdev_budget_usecs（默认 2000μs）。

    ksoftirqd 占满一个核不一定是故障：当软中断在中断返回路径上跑超了预算，剩余工作会被推给 ksoftirqd/N 内核线程，同时 /proc/net/softnet_stat 第 3 列 time_squeeze 加一。这是设计好的溢出通道，作用是防止软中断无限期霸占 CPU 饿死普通进程。真正要判断的是：它是否伴随丢包（rx_missed_errors / softnet 第 2 列增长）、以及软中断负载是否只集中在一两个核上（那说明中断没打散，该看 RSS / RPS / smp_affinity）。

  3. 基础TIME_WAIT 为什么必须存在？服务器上几万个 TIME_WAIT 需要处理吗？

    TIME_WAIT 是主动关闭方在发出最后一个 ACK 后进入的状态，持续 2×MSL（Linux 固定 60 秒，TCP_TIMEWAIT_LEN，没有 sysctl 能改）。两个理由缺一不可：

    • 保证最后的 ACK 可靠送达：如果这个 ACK 丢了，对方会重传 FIN，本端还在 TIME_WAIT 才能正确回应；否则对方收到的是 RST，会认为连接异常终止。
    • 让旧连接的迟到报文消亡：防止延迟到达的报文被相同四元组的新连接误收。

    大多数情况不需要处理。 每个 TIME_WAIT 只占一个精简的 tcp_timewait_sock（几百字节量级），10 万个也就几十 MB。服务端 TIME_WAIT 多，只说明是服务端在主动关闭（典型是 HTTP 短连接），根治办法是改用 keep-alive 长连接，而不是调内核参数。

    唯一真正需要处理的场景：本机作为客户端或反向代理，向同一个目的 IP:Port 发起海量短连接，端口在 60 秒内被占满，新连接报 EADDRNOTAVAIL。处理顺序是：连接池复用 → 扩大 ip_local_port_range → 开 tcp_tw_reuse=1（依赖 tcp_timestamps=1，只影响主动发起的连接） → 增加目的地址。

    绝对不要用 tcp_tw_recycle：它按对端 IP 维度做 PAWS 时间戳校验，在客户端处于 NAT 之后时会误丢部分客户端的 SYN，症状是「同一出口 IP 后面的部分用户随机连不上」。它已在 Linux 4.12 被移除，今天写这个参数只会得到「No such file or directory」。

  4. 基础客户端偶发连接超时，服务端 CPU 和内存都很闲。怎么判断是不是 accept 队列溢出？

    三条命令定性：

    ss -lnt                                        # LISTEN 行：Recv-Q=当前排队数，Send-Q=队列上限
nstat -az | grep -E 'ListenOverflows|ListenDrops'
netstat -s | grep -i 'listen queue'            # "times the listen queue of a socket overflowed"

    ss -lnt 对 LISTEN 状态的 socket 有特殊语义：Recv-Q 是 accept 队列当前排了多少已完成握手的连接，Send-Q 是它的上限。两者相等就是满了。ListenOverflows 只要非零就是问题。

    为什么表现为「超时」而不是「拒绝」：默认 tcp_abort_on_overflow=0，队列满时内核静默丢弃客户端的 ACK。客户端已经收到 SYN+ACK，认为连接建立了，会重传 ACK 甚至直接发数据，几秒后才超时。设成 1 会立刻回 RST（快速失败），但瞬时突发也会被硬拒。

    修复要点：accept 队列大小是 min(listen() 的 backlog 参数, net.core.somaxconn)，两边都要改才有效——只调 somaxconn 而应用写死 listen(fd,128) 是没用的。但更重要的判断是：队列是缓冲，不是产能。持续溢出说明 accept() 速度跟不上，要看 accept 循环里是不是混进了阻塞操作，或者上 SO_REUSEPORT 多进程分担。

conntrack -L | grep -oP 'dport=\d+' | sort | uniq -c | sort -rn | head   # 谁占的

    按占用者分类对症，而不是一律调大 max：

    • 海量短连接（DNS、探针、日志上报） → raw 表 -j NOTRACK 直接不跟踪。注意 NOTRACK 的流量无法被 --ctstate 匹配也无法做 NAT，且两个方向都要写规则。
    • ESTABLISHED 条目堆积 → nf_conntrack_tcp_timeout_established 默认是 432000 秒（5 天），这是最常见的元凶，可调到 1200~3600。
    • 哈希冲突严重（search_restart / chaintoolong 在涨） → 调 nf_conntrack_buckets，通常设为 max/4~max/2。
    • 确实就是连接多 → 再调 nf_conntrack_max，并评估内存（每条约几百字节）。

    调短超时的副作用必须一起说：空闲长连接（连接池、gRPC、SSH）的 conntrack 条目被提前删除后，服务端后续发来的数据包在网关上会被判为 INVALID 而丢弃，症状是「连接看着通，空闲一段时间后突然卡死」。所以调短超时必须确保应用侧 keepalive 间隔小于这个值。

    加分项：提到 insert_failed 增长往往不是表满而是 NAT 端口分配竞争，可以用 MASQUERADE --random-fully 显著降低碰撞率——这个偶发万分之一的 SYN 丢失会造成 1 秒的 SYN 重传，在 p99 敏感的服务上很刺眼。

  2. 中级rp_filter 的三个取值分别是什么语义？为什么有人「明明关了却还是被丢包」？

    反向路径过滤：收包时用源地址反查路由表，看「我要回这个源地址会从哪个接口出去」。

    • 0 = 关闭，不检查。适用于路由器、多线非对称路由、anycast。
    • 1 = 严格模式（RFC 3704 strict），反查出的接口必须正好是收包接口，否则丢弃。单出口服务器的推荐值。
    • 2 = 松散模式，只要源地址在任意接口上可达就放行。多网卡但仍想挡掉完全不可路由的伪造源地址时用它。

    「关了还被丢」的原因：实际生效值是 net.ipv4.conf.all.rp_filter 与 net.ipv4.conf.<iface>.rp_filter 的最大值。只把某个接口设成 0 而 all 还是 1，结果依然是严格模式。必须两个都改；另外 all 的改动不会自动同步到已存在的接口，新建接口继承的是 default。

    怎么证明是它干的：nstat -az | grep -i ReversePathFilter，TcpExtIPReversePathFilter 在涨就实锤了（这个计数器名字带 Tcp，实际统计 IP 层所有被 rp_filter 丢的包）。想看具体包可以临时 sysctl -w net.ipv4.conf.all.log_martians=1，dmesg 里会打印 martian source。

    更根本的解法通常是策略路由：双网卡回包走错网卡是根因，用 ip rule add from <本接口IP> lookup <独立表> 把回包钉回它进来的那张网卡，比关掉 rp_filter 更安全。

  3. 中级不用 Docker，用 ip 命令手工搭一套容器网络并能访问外网，需要哪几步？每一步解决什么问题？

    七步，每一步对应一个必须解决的问题：

    ip netns add ns1                                    # ① 独立的网络栈（接口/路由/iptables/端口空间全独立）
ip link add veth0 type veth peer name ceth0         # ② 一根「虚拟网线」把两个 netns 连起来
ip link set ceth0 netns ns1
ip link add br0 type bridge                         # ③ 软件交换机，让多个容器能互通
ip link set veth0 master br0
ip addr add 172.18.0.1/24 dev br0                   #    网桥自己带 IP，同时当容器的网关
ip link set br0 up; ip link set veth0 up
ip netns exec ns1 ip addr add 172.18.0.2/24 dev ceth0   # ④ 容器侧配地址
ip netns exec ns1 ip link set ceth0 up
ip netns exec ns1 ip link set lo up
ip netns exec ns1 ip route add default via 172.18.0.1   #    默认路由指向网桥
sysctl -w net.ipv4.ip_forward=1                     # ⑤ 允许转发，否则「不是给我的包」直接丢
iptables -t nat -A POSTROUTING -s 172.18.0.0/24 ! -o br0 -j MASQUERADE   # ⑥ 私网地址换成宿主机地址
iptables -A FORWARD -i br0 -j ACCEPT                # ⑦ 很多发行版 FORWARD 默认 DROP

    关键理解点：

    • veth 的对端要走一遍完整的接收路径——从 ceth0 发出的帧进入 veth0 的 RX 路径，会再过一次 netif_receive_skb、GRO、netfilter。这既是容器网络 pps 开销高的原因，也是「在宿主机上 tcpdump -i vethXXX 能抓到容器全部流量」的原理。
    • 容器流量走 FORWARD 链，不走 INPUT/OUTPUT。在宿主机上写 INPUT 规则拦不住容器流量。
    • 回包靠 conntrack 还原：SNAT 只在首包时决策，结果记进 conntrack，反向包自动还原目的地址。
    • ! -o br0 是为了不把容器之间的互访也 NAT 掉。

    这套东西就是 Docker bridge 模式（docker0）和 Kubernetes 大多数 CNI（cni0）在内核层面做的事。加分项：提到 br_netfilter 与 bridge-nf-call-iptables——打开后二层桥接流量也会进 iptables 三层链，k8s 要求打开，但会让同网桥内的 Pod 互访也过一遍 conntrack。

  4. 中级抓包看到 TCP 段有 65160 字节、而且校验和全是 incorrect，是网卡坏了还是 MTU 配错了？

    两个都不是，是卸载（offload）特性造成的观测偏差。

    • 出向的巨帧：出向 tcpdump 的 tap 在 dev_hard_start_xmit() 里，也就是在驱动之前、TSO 分段之前。内核交给网卡的是一个最多 64KB 的巨型 skb，网卡才会按 MSS 切成几十个真实的以太网帧。所以你抓到的「一个包」在线上其实是几十个包。
    • 校验和错误：开了 TX checksum offload 时，内核只填了伪首部，真正的校验和由网卡计算。抓包点在网卡之前，自然看到的是「错的」。这是假告警。
    • 入向对应的是 GRO：入向 tap 在 netif_receive_skb() 里，GRO 已经把同流的多个小包合并了，所以抓到的入向包也可能远大于 MTU。

    怎么确认与规避：

    ethtool -k eth0 | grep -E 'segmentation|receive-offload|checksum'
ethtool -K eth0 gro off gso off tso off lro off   # 会瞬断、CPU 上升，只在抓包窗口内做
tcpdump -i eth0 -nn -s 96 -c 2000 -w /tmp/cap.pcap ...
ethtool -K eth0 gro on gso on tso on              # 立刻恢复

    什么时候必须关掉再抓：排查 MSS/MTU 协商、分段行为、乱序、重传时序、以及真实的校验和错误时。排查连通性、防火墙、握手行为时完全不用关。

    另外两个相关的坑：LRO 在转发场景必须关掉（硬件合并后无法还原成原包，转发出去就是错的，GRO 因为保留了足够信息可以重新分段所以没这个问题）；抓包结束一定要看 packets dropped by kernel，不为零说明 tcpdump 自己漏了包，基于这份 pcap 得出的「丢包」结论要打折。

10.3 高级（体现深度）

  1. 高级什么是 bufferbloat？CoDel 凭什么能治它，而单纯「把队列改小」不行？

    bufferbloat：设备为了「不丢包」配了过大的缓冲区，拥塞时包不是被丢弃而是长时间排队。TCP 靠丢包感知拥塞，队列不丢包它就持续加速，最终把大队列填满并稳定维持在满状态（standing queue）。结果是带宽跑满、但每个包的排队延迟涨到几百毫秒——「一下载东西，SSH 就卡得敲不了字」。

    为什么不能简单把队列改小：队列该多大取决于带宽和 RTT（BDP），而这两者是动态变化的——同一个值在 100Mbps 短 RTT 下太大、在 1Gbps 长 RTT 下又太小。不存在一个普适的队列长度。改小了还会伤害突发吞吐：正常的流量突发会被直接丢弃。

    CoDel 的洞见是换了度量维度：不看队列有多长（长度没有普适阈值），而看每个包在队列里待了多久（sojourn time）。规则是：在一个 interval（100ms）的观察窗口内，如果队列的最小驻留时间始终超过 target（5ms），判定为 standing queue，开始丢弃队首包，且丢弃频率随持续时间递增，直到延迟回落。

    用「最小值」是精髓：突发流量会让队列瞬间变长但很快排空，最小驻留时间不会超标，所以突发不被惩罚；只有持续的、排不空的队列才会触发。这就区分开了「好队列」（吸收突发）和「坏队列」（制造延迟）。

    fq_codel = 公平排队 + CoDel：先按五元组哈希把流分到 1024 个子队列，每个独立跑 CoDel，用赤字轮询调度并给新流优先权。效果是大象流被 CoDel 压住，而一个刚发起的 DNS 查询落在自己的空队列里几乎零排队。

    实操：sysctl net.core.default_qdisc=fq_codel（现代发行版已是默认，但被人手工 replace 过就会退回 pfifo_fast，做延迟优化第一件事是 tc qdisc show 确认）。判读 tc -s qdisc show 时重点看 backlog（瞬时积压，持续非零 = 正在制造延迟），注意 overlimits 对 htb/tbf 表示「限速在生效」而不是错误。用 BBR 时要配 fq 而不是 fq_codel（BBR 依赖精确 pacing）。

  2. 高级XDP 和 DPDK 都能做高性能包处理，怎么选？为什么说这道题的答案不在性能数字上？

    核心差异是「是否放弃内核栈」，而不是快多少。

    XDPDPDK
    网卡归属仍归内核驱动管被独占（vfio-pci 绑定），内核看不见它
    CPU按需处理，空闲不占轮询模式，核永远 100% 空转
    协议栈处理不了的包 XDP_PASS 交给内核栈没有内核栈，TCP/IP 全要自己实现或引入用户态栈
    运维工具ip / ss / tcpdump / iptables 全部继续可用全部失效，可观测性要重建
    部署热加载 / 卸载，不中断改配置基本要重启进程

    判据：只要这台机器上还跑着需要正常网络栈的业务（哪怕只是 SSH 和监控 agent），就应该选 XDP——它是「在内核路径上插一段快速通道」。只有当整台机器的存在意义就是转发（NFV 网元、专用防火墙、行情网关、软件交换机）时，DPDK 独占网卡的代价才划算。

    中间选项是 AF_XDP：XDP 程序用 XDP_REDIRECT 把包投进 XSKMAP，用户态通过 UMEM 共享内存和四个环（FILL / RX / TX / COMPLETION）收发，零拷贝、无系统调用，但网卡仍是标准内核驱动，不需要它的流量继续走内核栈。

    关于 XDP 本身的两个深度点：① 三种模式里只有 native 有意义，generic（skb 模式）在 skb 分配之后才跑，比 tc-bpf 还慢，只用于调试——很多「上了 XDP 没提速」的案例就是跑在了 generic 上，要用 ip link show 确认显示的是 xdp 而不是 xdpgeneric。② 不要把所有逻辑都塞进 XDP：XDP 只有裸包，没有 skb 元数据、没有 conntrack、不能挂 egress。Cilium 的分工很有代表性——XDP 只做 DDoS 丢包和 NodePort 首跳，Service 转发、NetworkPolicy、可观测性全在 tc-bpf（clsact）层，因为那里能读到 __sk_buff 的完整上下文。

  3. 高级有人建议「全公司统一切 BBR，吞吐能翻倍」。你怎么评估这个提议？

    先问一个问题：这些链路上存在与拥塞无关的丢包吗？ 这是 BBR 是否有收益的唯一判据。

    原理层面的差异：cubic 把丢包当拥塞信号，丢一个包就降窗；BBR 是模型驱动的，持续测量瓶颈带宽（BtlBw）和最小 RTT（RTprop），按二者的乘积决定在途数据量，丢包不再直接触发降速。

    有收益的场景：跨洲传输、CDN 回源、移动 / 无线网络、质量不稳定的公网出口——这些链路的丢包很大比例来自误码或中间设备的随机丢弃而非真拥塞，cubic 会被反复打压到远低于可用带宽，BBR 常能带来数倍提升。另外 BBR 把在途数据控制在 BDP 附近，队列更浅，延迟明显更低，对 bufferbloat 严重的链路是双重收益。

    没收益甚至有风险的场景：机房内网（RTT 亚毫秒、丢包率近 0）换 BBR 基本没有提升，只是引入了新的行为模式和排查复杂度。已知的风险点包括：与 cubic 共享浅缓冲区链路时可能占用超过公平份额（公平性一直有争议）；ACK 聚合严重的链路（部分无线、部分虚拟化环境）上带宽估计会偏高。

    所以对这个提议的回答是：不接受「全公司统一切」。正确做法是——

    • 先分类链路：内网 / 公网出口 / 跨地域，分别量当前的重传率（nstat 的 TcpRetransSegs/TcpOutSegs）和 ss -ti 的 delivery_rate。
    • 灰度：用 setsockopt(fd, IPPROTO_TCP, TCP_CONGESTION, "bbr", 3) 对部分连接开，而不是全局 sysctl。同一台机器上可以对比。
    • 配套：BBR 依赖精确 pacing，qdisc 应该配 fq（net.core.default_qdisc=fq），不是 fq_codel。
    • 验证指标：不只看吞吐，还要看 p99 延迟和重传率；只看一个必然误判。

    这道题真正考的是「不抄 sysctl 大礼包」的判断力：每个参数都要能回答「什么症状让我改它 / 改完看什么验证 / 副作用是什么」。

  4. 高级线上服务报「偶发丢包」，给你一台机器和十分钟，你的排查顺序是什么？说出每一步的判据。

    核心原则：「丢包」不是结论而是现象类别，内核路径上至少有九个丢包点，每一层都有专属计数器。策略是先用两三条命令把范围缩到某一层，再深入。全程看速率不看绝对值。

    • 0 分钟 —— dmesg -T | tail -50。nf_conntrack: table full、neighbour table overflow、TCP: time wait bucket table overflow 这类问题一行日志就结案，不看白不看。
    • 1 分钟 —— nstat -n; sleep 10; nstat。先清零再看这 10 秒里哪些计数器动了，这是性价比最高的一步。重点：ListenOverflows（accept 队列）、TCPBacklogDrop / TCPRcvQDrop（socket 层）、UdpRcvbufErrors、IPReversePathFilter、TcpRetransSegs/TcpOutSegs 算重传率（内网 > 0.05%、公网 > 1% 就该查）。
    • 3 分钟 —— 硬件与软中断层。ethtool -S eth0 采样两次做差，看 rx_missed_errors、各 rx_queue_N_drops（只有一两个队列在丢 = 哈希不均，不是容量不够）；/proc/net/softnet_stat 看第 3 列 time_squeeze；mpstat -P ALL 1 看 %soft 是否集中在个别核。
    • 5 分钟 —— 连接与队列。ss -lnt 看 accept 队列；ss -ti 抽查连接，用 rwnd_limited（对端读得慢）/ sndbuf_limited（本端缓冲不够）/ cwnd 小（拥塞控制在压）三个信号区分「吞吐上不去」的三种完全不同的原因；tc -s qdisc show 看发送侧 backlog 和 dropped。
    • 7 分钟 —— netfilter。iptables -L -n -v 看 DROP 规则的包计数是否在涨（这是最直接的证据）；conntrack -S。
    • 10 分钟 —— 抓包做二分或追内核栈。在服务端网卡抓：能抓到 SYN = 包到了机器，问题在本机（继续往协议栈里查，注意 tcpdump 的 tap 在 netfilter 之前，所以被 iptables DROP 的包照样能抓到——「抓到 SYN 但应用没反应」头号嫌疑就是防火墙）；抓不到 SYN = 包没到，去查网络路径 / 安全组 / 客户端。还定位不了就 bpftrace -e 'tracepoint:skb:kfree_skb { @[kstack(6)] = count(); }' 按内核栈聚合看内核在哪一行丢的（5.17+ 还能直接读 args->reason）。

    几个能体现经验的细节：① softnet_stat 第 2 列只统计 per-CPU backlog 溢出，物理网卡走 NAPI 不经过 backlog，所以它为 0 不代表内核没丢包；② ip -s link 的 dropped 是软件侧丢弃，和 ring 大小无关，别看到它就去 ethtool -G；③ 抓包前想清楚要不要关 GRO/TSO；④ 抓完看 packets dropped by kernel，不为零则这份 pcap 本身不完整。
