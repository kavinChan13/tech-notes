为什么需要调度器

几千个线程抢几十个核

现代机器有几十个 CPU 核，但同时有成千上万个可运行的线程。调度器决定「下一刻哪个线程在哪个核上跑、跑多久」。它要同时兼顾几个互相冲突的目标：公平（谁都别饿死）、吞吐（少切换多干活）、响应性（交互任务要快）、确定性（实时任务不能被拖）。这些目标无法同时最优——调度就是一门取舍的艺术。

生活类比：医院分诊台

CPU 核是医生，线程是病人。分诊台（调度器）不能简单先到先看：急诊（实时任务）要插队，普通门诊（普通任务）按公平排，但也不能让谁一直排不上（防饿死）。医生频繁换病人（上下文切换）会浪费时间在「重新了解病情」（刷新 cache / TLB），所以也不能切太勤。调度器就是这个既要公平、又要救急、还要高效的分诊台。

映射：医生=CPU 核 · 病人=线程 · 急诊插队=实时优先级 · 换病人成本=上下文切换

调度器只回答三个问题

① 选谁跑

从本 CPU 的运行队列里挑下一个任务（pick_next_task）。这是调度算法的核心，CFS 与 EEVDF 的差别就在这里。

② 跑多久

时间片 / 虚拟截止时间决定它能连续跑多久。太短则切换开销吃掉吞吐，太长则别人等太久。

③ 在哪跑

负载均衡决定任务落在哪个核。迁移能填平负载，但会丢 cache 热度、可能跨 NUMA。

先厘清「可运行」到底指什么

调度器只关心可运行（TASK_RUNNING）的任务，它包含两类：正在某个核上跑的，和在运行队列里排队等着跑的。睡眠中的任务根本不在调度器的候选集里。这一点直接决定了下面几个观测量该怎么读。

状态含义是否参与调度是否计入 load average
R可运行：正在跑，或在 runqueue 里等是是
S可中断睡眠：等 I/O、等锁、等事件，可被信号唤醒否否
D不可中断睡眠：通常在等磁盘 / NFS，连信号都打不断否是
T / t被 SIGSTOP 停住 / 被 ptrace 停住否否
Z僵尸：已退出但父进程没回收否否

最常见的误读：load average 不是 CPU 利用率

  • Linux 的 load average 统计的是 R 状态 + D 状态 任务数的指数移动平均。这是 Linux 特有的，传统 Unix 只算 R。
  • 所以一台 8 核机器 load 飙到 50，可能一点 CPU 都没跑满——只是有 50 个进程卡在 D 状态等一块挂掉的磁盘。这时候去调 nice、加核、扩容全是白费。
  • 判断到底是 CPU 挤还是 I/O 堵：看 vmstat 的 r（可运行队列长度）和 b（不可中断阻塞数）两列，比 load 精确得多。

调度器的核心难题是「公平」和「响应性」的矛盾：交互任务（键盘、鼠标）需要立刻响应但只占很少 CPU；批处理任务（编译、渲染）想吃满 CPU。好的调度器让交互任务感觉「秒响应」，同时批任务照样跑满——CFS/EEVDF 就是为此设计的。

调度类与优先级空间

Linux 有多套调度策略叠在一起

Linux 不是只有一个调度算法，而是分层的调度类（scheduling class），按优先级从高到低依次挑选：Stop → Deadline → RT → CFS/EEVDF → Idle。高优先级类里只要还有可运行任务，就轮不到低优先级类——注意这是严格的类间优先，不是加权，所以一个失控的 RT 任务真的能把整台机器的普通任务全饿死。

调度类策略用途
Stop（内核内部，无用户接口）CPU 热插拔、任务迁移这类必须立刻执行的内核操作
DeadlineSCHED_DEADLINEEDF，按截止时间调度，用户可用的最高优先级，硬实时
Real-TimeSCHED_FIFO / SCHED_RR固定优先级（1-99），实时任务
公平（CFS/EEVDF）SCHED_OTHER / SCHED_BATCH / SCHED_IDLE绝大多数进程，靠 nice 值调权重
Idle（内核内部）没别的可跑时才跑的 idle 任务，负责进入省电状态

一张图看懂优先级数值的三套坐标系

「优先级」这个词在 Linux 里至少有三种数值表示，混用是面试和排障时最容易翻车的地方：内核内部的 prio（0–139，越小越高）、实时优先级 rtprio（1–99，越大越高）、以及普通任务的 nice（−20–19，越小越"不谦让"）。

nice 值：普通任务的「谦让度」

  • 范围 -20（最不谦让，占更多 CPU）到 +19（最谦让）。默认 0。
  • nice 不是「百分比」——内核用一张 sched_prio_to_weight[] 权重表做映射，每差 1 级权重约变化 1.25 倍。nice 0 的权重定为 1024，nice 1 是 820，nice 5 是 335，nice 19 只有 15。
  • 由此可推：nice 0 与 nice 5 的两个 CPU 密集任务抢一个核，CPU 时间比约为 1024 : 335 ≈ 75% : 25%。这个「1.25 倍」的设计意图是让每差 1 级带来约 10% 的相对变化，方便渐进调节。
  • 普通用户只能调高 nice（更谦让）；调低需要 CAP_SYS_NICE。
  • SCHED_BATCH：告诉调度器「我是批处理，别为我做唤醒抢占优化」，减少切换、提升吞吐。SCHED_IDLE：权重极低（相当于 nice 20 之外），只在系统真没别的事做时跑，适合后台索引、日志压缩。
# 启动时指定 nice；对已有进程用 renice
$ nice -n 10 ./batch_job
$ renice -n 5 -p 4890
$ renice -n -5 -u www-data            # 按用户批量调整（需要权限）

# 把一个后台任务丢进 SCHED_IDLE，几乎不会干扰前台
$ chrt --idle 0 ./nightly_reindex

# 查看某进程当前的调度策略与优先级
$ chrt -p 3271
pid 3271's current scheduling policy: SCHED_FIFO
pid 3271's current scheduling priority: 50
优先级反转（priority inversion）陷阱：高优先级 RT 任务等一个被低优先级任务持有的锁，而低优先级任务又被中优先级任务抢占永远跑不完——高优先级被间接饿死。1997 年火星探路者号的反复重启就是这个原因。解法：优先级继承（PI mutex），让持锁的低优先级任务临时继承高优先级。§5 给出代码。

CFS：完全公平调度

2007–2023 的默认调度器

CFS（Completely Fair Scheduler）的核心思想：让每个任务获得「理想公平份额」的 CPU 时间。它用 虚拟运行时间（vruntime） 追踪每个任务已经跑了多久（按权重加权），永远挑 vruntime 最小的任务跑——即「最亏欠的先跑」。

vruntime（虚拟运行时间）：任务实际消耗的 CPU 时间，按权重缩放后的结果。递推关系是 Δvruntime = Δ实际运行时间 × (1024 / 本任务权重)。nice 0 的权重正好是 1024，所以对它来说 vruntime 就等于真实时间；nice −5（权重 3121）的任务跑 1 秒只记 0.33 秒，于是它能被反复选中，实际拿到更多 CPU。

核心机制

  • 红黑树：所有可运行任务按 vruntime 排序，取最左（最小）节点。插入 / 删除 O(log n)，而"取最左"因为缓存了指针是 O(1)。
  • 没有固定时间片：CFS 有一个调度周期（目标是让所有可运行任务在这段时间内各跑一次）。任务越多，每个分到的越短；但有下限 min_granularity，任务多到一定程度后周期就随任务数线性拉长，避免切换过频。
  • 唤醒补偿：任务睡醒后 vruntime 会被拉到接近当前队列最小值（但不允许倒退太多），让刚醒的交互任务能立刻抢到 CPU——这就是"响应性"的来源。
  • 唤醒抢占：被唤醒的任务如果 vruntime 比当前运行者小到超过 wakeup_granularity，会立刻触发抢占，而不是等时间片用完。
vruntime 像记账

把 CPU 时间想成公司发的「工时」。CFS 给每人记账：谁领的工时最少（vruntime 最小），下一份活就先给谁。nice 低的是「VIP 员工」，同样干 1 小时只记 0.33 小时账，所以能领到更多活。这样长期看每人按权重公平分配，短期又能让「刚来的人（唤醒任务）」马上有活干。

映射：记账本=红黑树 · 已领工时=vruntime · VIP 折扣率=nice 权重 · 先给最少的人=取最左节点

组调度：为什么容器里的 CPU 份额是分层的

如果公平只在"任务"这一层做，那么一个开了 200 个线程的容器就能把只有 2 个线程的容器挤死。CFS 的组调度（group scheduling）让公平在 cgroup 层级上先分配一次：先按 cpu.weight 在各个 cgroup 之间分 CPU，每个 cgroup 拿到的份额再在它内部的任务之间按 vruntime 分。

读懂 /proc/PID/sched

这是排查单个任务调度行为最直接的入口，比任何监控面板都准确。

$ cat /proc/4412/sched

se.statistics.wait_sum           :         9917.442100   # ★ 累计在队列里干等的时间（ms）
se.statistics.wait_max           :           42.118000   # ★ 单次最久等了 42ms —— 延迟毛刺的直接证据
se.statistics.iowait_sum         :          812.330000
nr_switches                      :             1284471
nr_voluntary_switches            :             1279904   # 自己让出（等 I/O、等锁）

三个字段就能定性

  • wait_sum / (wait_sum + sum_exec_runtime) ≈ 这个任务有多少时间是在排队而不是干活。超过 10% 就说明 CPU 供给不足或被同核任务挤。
  • wait_max 直接给出最坏一次调度延迟。低延迟服务的 P99 毛刺往往就等于这个数。
  • nr_involuntary_switches 占 nr_switches 的比例高 → 被反复抢占；比例低而总数巨大 → 是自己在频繁阻塞（I/O 或锁），那是另一类问题。

EEVDF：CFS 的继任者

Linux 6.6（2023）起的默认调度器

CFS 在「延迟敏感任务」上有个结构性短板：它只保证长期公平，任务无法表达「我只要一点点 CPU，但我要马上拿到」。想降延迟只能调 nice，而 nice 同时改变了份额——你为了让一个心跳线程及时唤醒，被迫让它拿走了不该拿的 CPU 份额。EEVDF（Earliest Eligible Virtual Deadline First）把「份额」和「延迟」拆成两个独立维度，2023 年合入内核 6.6 取代 CFS。

三个关键概念

  • lag（亏欠）：任务「应得的」减去「实得的」CPU 时间。lag > 0 表示系统欠它，lag < 0 表示它超支了。
  • eligible（合格）：只有 lag ≥ 0 的任务才有资格被选中。这一条保证了长期公平——超支的任务必须先等回来。
  • virtual deadline（虚拟截止）：由任务请求的时间片长度推出：虚拟截止 = 变得合格的时刻 + 请求的时间片 / 权重。请求的时间片越小，截止越早，越优先被挑中。

选择规则一句话：在所有 eligible 的任务里，挑虚拟截止时间最早的那个。

生活类比：食堂窗口的两条规则

CFS 只有一条规则：谁打的饭最少谁先来。于是一个只想拿包餐巾纸的人，也得和端着餐盘的人一起排队。EEVDF 加了第二条：先看你有没有超额（lag ≥ 0 才能排队），在没超额的人里，谁说"我只要 10 秒"谁先上。于是拿餐巾纸的人立刻被放行，而他也确实只占用 10 秒——既没破坏公平，又救了延迟。

映射：打饭总量=CPU 份额 · 超额者先等=lag 检查 · 我只要 10 秒=请求小时间片 · 放行顺序=虚拟截止

能否单独表达"低延迟"不能，只能调 nice（连份额一起改）能，请求更小的时间片即可

较新的内核（6.12 起）允许普通任务通过 sched_setattr() 的 sched_runtime 字段为自己请求一个自定义时间片，从而在不改 nice 的前提下换取更低的调度延迟。代价是切换更频繁——你是在用吞吐买延迟：

#define _GNU_SOURCE
#include <linux/sched/types.h>
#include <sys/syscall.h>
#include <unistd.h>

struct sched_attr attr = {0};
attr.size           = sizeof(attr);
attr.sched_policy   = SCHED_OTHER;      // 仍然是普通任务，份额不变
attr.sched_nice     = 0;
attr.sched_runtime  = 300000;          // 请求 0.3 ms 的时间片（默认 3 ms）

if (syscall(SYS_sched_setattr, 0, &attr, 0) < 0)
    perror("sched_setattr");       // 内核不支持时返回 EINVAL，要能优雅降级
// 效果：这个线程被唤醒后能更快抢到 CPU，但每次只跑 0.3 ms 就可能被换下。
// 适合心跳 / 控制面线程；千万别给计算密集线程用，切换开销会吃掉吞吐。
面试官想听的是「EEVDF 解决了 CFS 的什么问题」而不是算法细节。标准答案：CFS 把"份额"和"延迟"耦合在 nice 这一个旋钮上，EEVDF 用 lag 管公平、用请求时间片管延迟，把两者解耦了。能再补一句「所以低延迟服务不再需要靠调低 nice 来蹭响应速度」就很到位。

实时调度与 PREEMPT_RT

当「公平」不够，你要「确定」

普通调度追求平均表现；实时任务追求最坏情况可控（bounded latency）——宁可平均慢一点，也要保证「绝不超过 X 微秒」。注意这里的"实时"不是"快"，而是可预测。

策略行为典型用途
SCHED_FIFO同优先级先到先跑，一直跑到主动让出 / 阻塞 / 被更高优先级抢占，无时间片周期性控制环、音频回调
SCHED_RR同优先级之间轮转（有时间片，见 sched_rr_get_interval），其余同 FIFO多个同等重要的实时任务
SCHED_DEADLINE指定 (runtime, deadline, period)，内核用 EDF 调度并做准入控制有明确周期与预算的任务

把一个线程变成实时线程

#include <pthread.h>
#include <sched.h>
#include <sys/mman.h>

void make_realtime(int prio) {
    // ① 先锁内存：实时线程绝不能在关键路径上触发缺页，那是毫秒级的不确定性
    mlockall(MCL_CURRENT | MCL_FUTURE);

    struct sched_param p = { .sched_priority = prio };   // 1..99
    if (pthread_setschedparam(pthread_self(), SCHED_FIFO, &p) != 0)
        perror("pthread_setschedparam");   // 无 CAP_SYS_NICE 时返回 EPERM
}

// ② 优先级继承锁：这是防止优先级反转的唯一正解，不是可选项
pthread_mutexattr_t ma;
pthread_mutexattr_init(&ma);
pthread_mutexattr_setprotocol(&ma, PTHREAD_PRIO_INHERIT);
pthread_mutex_init(&lock, &ma);
// 现在低优先级线程持有 lock 期间，会临时继承等待者的优先级，
// 保证它能尽快跑完并释放锁，而不会被中优先级线程无限期挤掉。
# 命令行等价物：chrt
$ sudo chrt -f 50 ./control_loop          # SCHED_FIFO 优先级 50
$ sudo chrt -r 20 ./worker                # SCHED_RR 优先级 20
$ chrt -m                                 # 查看各策略的优先级取值范围
SCHED_OTHER min/max priority        : 0/0
SCHED_FIFO min/max priority         : 1/99
SCHED_RR min/max priority           : 1/99
SCHED_BATCH min/max priority        : 0/0
SCHED_IDLE min/max priority         : 0/0
SCHED_DEADLINE min/max priority     : 0/0    # DEADLINE 不用静态优先级

# 不需要 root 也想跑实时？给二进制加 capability，比整个进程 root 安全得多
$ sudo setcap cap_sys_nice+ep ./control_loop

SCHED_DEADLINE 与准入控制

FIFO 的优先级是相对的——你只知道谁比谁高，不知道系统整体是否还扛得住。DEADLINE 让你直接声明"我每 10 ms 需要 2 ms 的 CPU"，内核据此做准入控制：所有 DEADLINE 任务的 runtime / period 之和超过系统容量时，sched_setattr 直接返回 EBUSY 拒绝你——宁可不让你跑，也不让已经承诺的任务违约。这是它比 FIFO 更"硬"的地方。

struct sched_attr attr = {0};
attr.size            = sizeof(attr);
attr.sched_policy    = SCHED_DEADLINE;
attr.sched_runtime   =   2 * 1000 * 1000;   // 每周期最多用 2 ms CPU
attr.sched_deadline  =   8 * 1000 * 1000;   // 必须在 8 ms 内用完
attr.sched_period    =  10 * 1000 * 1000;   // 周期 10 ms
// 约束：runtime <= deadline <= period

if (syscall(SYS_sched_setattr, 0, &attr, 0) < 0) {
    if (errno == EBUSY)   // ★ 准入被拒：系统已承诺的实时负载放不下你了
        fprintf(stderr, "admission control rejected: 系统实时带宽不足\n");
}
// 用完 runtime 还没结束？任务会被 throttle 到下个周期，而不是拖垮别人。

用 RT 调度的四个坑

  • 饿死整机：一个死循环的 SCHED_FIFO 任务会独占 CPU，连内核线程都跑不了。内核有 RT throttling 兜底：默认每 1 秒周期里最多给 RT 类 0.95 秒（sched_rt_period_us / sched_rt_runtime_us），超了就强制让给普通任务，并在 dmesg 打印 sched: RT throttling activated。看到这条日志就说明有 RT 任务失控了。
  • 优先级选得太高：把业务线程设成 99，会压过 migration/、watchdog/ 这些内核线程，后果是系统行为异常甚至 hard lockup。业务实时线程一般落在 10–60 这个区间，把高位留给内核。
  • 忘了 mlockall：一次缺页中断可能是几百微秒到毫秒级，足以毁掉所有实时保证。实时进程启动时就要锁定内存并预热栈。
  • 容器里的 RT：cgroup v2 默认不给子组分配 RT 带宽，容器内 chrt -f 常常直接 EPERM 或 EINVAL。要跑实时容器得单独配置，或者干脆别用容器。
# 观测 RT throttling 是否发生过
$ dmesg | grep -i 'rt throttling'
[ 4213.882145] sched: RT throttling activated

# 当前的 RT 带宽配置（默认 1s 周期里给 0.95s）
$ cat /proc/sys/kernel/sched_rt_period_us    /proc/sys/kernel/sched_rt_runtime_us
1000000

# ⚠ 设成 -1 可以完全关掉限流。只有在你 100% 确信 RT 任务不会失控、
#   且有硬件看门狗兜底时才这么做——否则一个 bug 就是整机失联。

PREEMPT_RT 是另一件事：它不改调度策略，而是把内核自身改造成几乎处处可抢占——大部分自旋锁变成可睡眠的 RT mutex、中断处理下半部线程化、临界区大幅缩短，把最坏调度延迟从毫秒级压到微秒级。这套补丁在 2024 年（内核 6.12）合入主线。详见 PREEMPT_RT 深入。

多核负载均衡

调度器是 per-CPU 的

为避免全局锁成为瓶颈，Linux 给每个 CPU 一个运行队列（runqueue），各自独立调度。这带来新问题：负载可能不均（一个核挤爆、另一个闲着）。负载均衡器在三个时机把任务在核之间搬动。

时机触发条件行为
周期性均衡时钟中断里按调度域的 balance_interval 检查从最忙的组往本组拉任务，层级越高检查越稀疏
idle 均衡某个核发现自己没活干，准备进 idle立刻去别的核"偷"任务，这是最积极的一档
唤醒时放置任务被唤醒，要决定放哪个核（select_task_rq）倾向放回唤醒者附近（wake affine，共享 cache），或找个 idle 核

调度域：按硬件拓扑分层，越近越先均衡

  • 层级从近到远：SMT（同物理核的两个超线程）→ MC（共享 LLC 的核）→ NUMA 节点内 → 跨 NUMA。
  • 迁移代价随层级指数上升：同 SMT 几乎免费；跨 LLC 要重建 L2/L3 热度；跨 NUMA 还要付远端访存的代价（延迟约 1.5–2 倍）。所以越高层的均衡门槛越高、频率越低。
  • sched_migration_cost_ns 是个"阻尼"：刚跑过不久的任务被认为 cache 还热，不轻易迁走。
  • NUMA balancing（/proc/sys/kernel/numa_balancing）是另一套机制：它周期性地取消页表映射制造缺页，借此观察谁在访问哪块内存，然后把任务和它的内存挪到一起。对访存模式稳定的服务是好事，对大内存随机访问的负载反而是纯开销——数据库类应用常常主动关掉它。

抢占与上下文切换

切换不是免费的

抢占的判定其实很朴素：内核在若干"检查点"看一眼 TIF_NEED_RESCHED 标志，置位了就调用 schedule()。这些检查点包括：系统调用返回用户态时、中断返回时、内核里显式的 cond_resched()、以及（在可抢占内核上）持锁计数归零时。标志则由「更高优先级任务被唤醒」「时间片/虚拟截止到期」这类事件置上。

抢占模型内核态可抢占性最坏延迟量级典型场景
PREEMPT_NONE只在返回用户态时切数十毫秒吞吐优先的服务器、批处理
PREEMPT_VOLUNTARY额外在显式 might_sleep() 点让出毫秒级通用发行版默认
PREEMPT内核态除临界区外处处可抢占亚毫秒桌面、低延迟服务
PREEMPT_RT连大部分自旋锁临界区也可抢占微秒级工业控制、音频、机器人

# 括号里的是当前模式
$ echo full | sudo tee /sys/kernel/debug/sched/preempt

切换到底花多少钱

直接成本

保存/恢复寄存器、切页表、更新调度统计。数量级在几百纳秒到 1–2 微秒，同进程内的线程切换比跨进程便宜（不换页表）。

间接成本（大头）

L1/L2 cache 与 TLB 被新任务冲掉，切回来时要重新预热。工作集大的任务，这部分可以达到几十微秒，是直接成本的十几倍。

所以

优化方向不是"让切换更快"，而是让切换更少：减少线程数、批量处理、用协程在用户态切、绑核保住 cache。

怎么读这两个数

  • 自愿切换极高、被抢占很低：任务大部分时间在等（I/O 或锁）。别去调度器上找答案，去看 I/O 或锁竞争——参考 死锁与锁竞争调试。
  • 被抢占占比高（比如超过总数的 20%）：CPU 真的挤。要么减少可运行线程数（线程池开太大是最常见原因），要么提优先级 / 绑核。
  • 两者都低但延迟高：可能是被同核的中断或内核线程打断，走 §6 的隔离路线，或者根本不是调度问题。
协程/异步之所以快，正是因为它在用户态做「切换」（只换栈和几个寄存器，纳秒级、无内核参与、不丢 TLB），而线程切换要陷入内核。这是 协程 相对线程的核心优势——但它换不来抢占式的公平，一个不让出的协程会卡死整个线程。

三个真实案例 + checklist

从现象到根因

案例 1 · CPU 用不满，服务却变慢

现象：K8s 里某 Java 服务 P99 从 30 ms 涨到 800 ms，但监控上容器 CPU 使用率只有 45%，宿主机也不忙。

「CPU 没满」这个观测把大家往错误方向带了整整两天。真相是 cgroup CPU 配额的突发限流：cpu.max 设的是「每 100 ms 周期最多用 200 ms CPU」，而这个服务是突发型的——某几个 10 ms 窗口内它想用 8 个核，配额瞬间耗尽，剩下的 80 ms 被硬生生 throttle 掉。平均到 1 秒的利用率当然不高，但请求就卡在那 80 ms 里。

$ cat /sys/fs/cgroup/kubepods/.../cpu.max
200000 100000                 # quota 200ms / period 100ms → 相当于 2 核

$ cat /sys/fs/cgroup/kubepods/.../cpu.stat
usage_usec 84120334
nr_periods 41022
nr_throttled 18847          # ★ 46% 的周期被限流过
throttled_usec 982114000     # ★ 累计被冻结 982 秒

处方：① 把 limit 调高或直接去掉 limit 只留 request（改用 cpu.weight 做相对分配）；② 让应用感知配额——老版本 JVM 读 /proc/cpuinfo 看到宿主 64 核就开了 64 个 GC 线程，配额只有 2 核，等于自己把自己限流，新版本 JVM 与 Go runtime 已能识别 cgroup 限额。详见 容器底层原理。

案例 2 · 实时线程每隔几秒抖一次

现象：SCHED_FIFO 优先级 50 的控制线程，99.9% 的周期都在 50 μs 内完成，但每几秒会出现一次 300 μs 的尖峰。

用 perf sched timehist 抓到尖峰那一刻，发现控制线程被换下时，上 CPU 的是同一个核上的 kworker 和网卡软中断。它虽然优先级 50 高于普通任务，但硬中断和软中断不受调度器优先级约束——中断来了就是打断你。

# 确认中断落在哪些核上
$ cat /proc/interrupts | grep -E 'eth0|CPU6'
      CPU5  CPU6  CPU7
 129: 84102 91882  2114   IR-PCI-MSI  eth0-rx-2   ← 中断正打在核 6

# 把这个中断挪走
$ echo 0-3 | sudo tee /proc/irq/129/smp_affinity_list

# 顺手确认核 6 上还剩什么
$ ps -eLo psr,pid,tid,cls,rtprio,comm | awk '$1==6'
  6  3271  3271  FF  50 control_loop
  6   118   118  TS   - kworker/6:1H

处方：isolcpus=6 + nohz_full=6 + rcu_nocbs=6 + 中断亲和避开核 6。尖峰降到 60 μs 以内。

案例 3 · 同样的压测，吞吐每次差 20%

现象：一个 32 线程的计算服务，每次压测吞吐在 8 万到 10 万 QPS 之间随机波动，代码和数据完全一样。

这是跨 NUMA 迁移的经典表现。进程启动时内存在 node 0 上分配好了，但线程被负载均衡陆续搬到 node 1 的核上，之后每次访存都要走 QPI/UPI 到远端节点。哪些线程被搬走是随机的，于是每轮压测的"远端访存比例"不同，吞吐就飘。

$ numastat -p 4412
                           Node 0          Node 1           Total
Private                  12882.31         4021.88        16904.19
# 内存基本都在 node 0

$ ps -eLo psr,tid,comm | awk '$3=="worker"' | awk '{print $1}' | sort -n | uniq -c
     18 0-15 范围内            # node 0 的核
     14 16-31 范围内           # ★ 一半线程跑在 node 1，访存全是远端

# 处方：把进程整体钉在一个 NUMA 节点上
$ numactl --cpunodebind=0 --membind=0 ./service
# 吞吐稳定在 10.2 万 QPS，波动 < 2%

如果单节点放不下，就按节点分片：每个 NUMA 节点跑一个独立实例，各自绑定本地内存，用前端做分发。这比让调度器"自己看着办"可靠得多。

调度相关排障 / 调优速查

  • 先分清是不是调度问题：vmstat 1 看 r 和 b；b 高是 I/O，r 高才是 CPU 挤。load 高但两者都不高 → 去查 D 状态进程。
  • 关键线程延迟抖动大 → perf sched latency 找出 Max delay，再用 timehist 看那一刻是谁抢的。
  • 抖动来自中断 / 内核线程 → isolcpus + nohz_full + rcu_nocbs + 中断亲和，四件套一起上。
  • 需要确定性延迟 → SCHED_FIFO（相对优先级）或 SCHED_DEADLINE（有准入控制）+ PI mutex + mlockall，必要时上 PREEMPT_RT。
  • RT 任务卡住其它任务 → dmesg | grep 'RT throttling'；检查是不是死循环独占，别急着关限流。
  • 非自愿上下文切换高 → 线程数是不是开太多了（常见：线程池按宿主核数开，但容器只给 2 核）。
  • 容器 CPU「没满却慢」→ 一定要看 cpu.stat 的 nr_throttled，不要只看利用率曲线。
  • 吞吐随机波动 → numastat -p 看内存和线程是否跨节点，用 numactl 或 cpuset.mems 钉住。
  • 动 sched_* 参数永远是最后一步，而且一次只动一个并测量。
一句话记忆：普通任务靠 CFS/EEVDF 求公平，实时任务靠 RT/Deadline 求确定，低延迟靠绑核 + 隔离 + 中断避让 + PREEMPT_RT 消抖动。而 90% 的「调度问题」最后都被证明不是调度问题。

面试题（12 道）

分层自测

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础load average 高就说明 CPU 不够用吗？

    不是。Linux 的 load average 统计的是 R 状态 + D 状态任务数的指数移动平均，而 D 状态是不可中断睡眠（通常在等磁盘或 NFS）。所以一块坏盘就能让 load 飙到几十，而 CPU 完全空闲。

    正确做法是看 vmstat 1 的两列：r 是可运行队列长度（CPU 挤的信号），b 是不可中断阻塞数（I/O 堵的信号）。再配合 %wa 和 iostat 定性。

    补充加分：传统 Unix 的 load 只算 R 状态，Linux 特意把 D 算进来是为了反映"系统整体有多少工作被卡住"，代价就是这个指标不再等价于 CPU 压力。

  2. 基础nice 值到底怎么影响 CPU 分配？差 1 级差多少？

    nice 通过一张权重表映射成调度权重，每差 1 级权重约变化 1.25 倍。nice 0 的权重定为 1024，nice 1 是 820，nice 5 约 335，nice 19 只有 15。

    两个 CPU 密集任务抢一个核时，拿到的 CPU 时间比 = 权重比。nice 0 与 nice 5 的比例约 1024 : 335，即 75% 对 25%。

    三个常见误区：① nice 不是百分比，也不是绝对保证；② 只有在 CPU 真的不够分时才起作用，空闲时谁都跑满；③ nice 永远抢不过任何一个实时任务，因为调度类之间是严格优先，不是加权。

  3. 基础SCHED_FIFO 和 SCHED_RR 有什么区别？什么时候用哪个？

    两者都是固定优先级的实时策略，高优先级永远抢占低优先级。唯一区别在同优先级任务之间：

    • SCHED_FIFO：没有时间片，一旦上 CPU 就一直跑，直到自己阻塞、主动 sched_yield()、或被更高优先级抢占。
    • SCHED_RR：同优先级之间按时间片轮转（可用 sched_rr_get_interval() 查询）。

    选择：如果同一优先级只有一个任务（常见的控制环、音频线程），用 FIFO，行为最可预测；如果有多个地位相同的实时任务需要共享 CPU，用 RR 避免其中一个独占。

  4. 基础上下文切换的开销主要花在哪？为什么协程比线程快？

    分两块：

    • 直接成本：保存/恢复寄存器、切换页表（跨进程时）、更新调度统计。几百纳秒到 1–2 微秒。
    • 间接成本（大头）：L1/L2 cache 和 TLB 被新任务冲掉，切回来要重新预热。工作集大的任务可达几十微秒。

    协程的切换发生在用户态：只换栈指针和少量寄存器，不陷入内核、不切页表、不丢 TLB，所以是纳秒级。

    但要说清代价：协程是协作式的，一个不主动让出的协程会卡死整个载体线程，也拿不到抢占式调度的公平性和隔离性。

10.2 中级（区分熟练度）

  1. 中级解释 vruntime。为什么 CFS 选 vruntime 最小的任务就能实现公平？

    vruntime 是「按权重缩放后的已运行时间」：Δvruntime = Δ真实运行时间 × 1024 / 权重。权重越高（nice 越低），同样的真实时间记账越少。

    CFS 每次挑 vruntime 最小的任务跑，等价于「让所有任务的 vruntime 尽量追平」。而 vruntime 相等 ⟺ 真实运行时间之比等于权重之比 ⟹ 按权重公平。

    几个要点：① 用红黑树维护有序集合，取最左节点；② vruntime 是每个运行队列的相对值，跨 CPU 不可直接比较，任务迁移时要做归一化；③ 睡眠任务醒来时 vruntime 会被拉到接近队列最小值——否则它睡了 10 分钟，醒来后会独占 CPU 10 分钟去"追平"，这既不公平也很危险。

  2. 中级什么是优先级反转？为什么 PI mutex 能解决？

    场景：高优先级任务 H 等一把被低优先级任务 L 持有的锁。本来 L 跑完释放锁就好，但一个中优先级任务 M 抢占了 L——M 不需要锁，却因为优先级比 L 高而一直占着 CPU。结果是 H 被 M 间接饿死，虽然 M 的优先级明明比 H 低。1997 年火星探路者号的反复重启就是这个问题。

    优先级继承（PI）：当 H 阻塞在 L 持有的锁上时，内核临时把 L 的优先级提升到 H 的水平。这样 M 就抢不走 L 的 CPU，L 得以尽快跑完并释放锁。锁释放后 L 的优先级恢复原值。

    用法是 pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT)。另一个方案是优先级天花板（PRIO_PROTECT），持锁即提升到预设上限，开销更小但需要静态分析出天花板值。

    补充：这也是 PREEMPT_RT 的关键机制——它把内核里的自旋锁换成可睡眠的 RT mutex，正是因为 RT mutex 支持优先级继承。

  3. 中级容器 CPU 使用率只有 40%，但接口 P99 暴涨。怎么查？

    首先怀疑 cgroup CPU 配额的突发限流。cpu.max 是「每个 period 内最多用多少 CPU 时间」，突发负载会在周期内提前耗尽配额，剩余时间被整段冻结。平均利用率被拉平后看着不高，但请求就卡在被冻结的那几十毫秒里。

    证据：

    cat /sys/fs/cgroup/<path>/cpu.stat
nr_periods 41022
nr_throttled 18847        # 被限流的周期数
throttled_usec 982114000  # 累计冻结时长

    nr_throttled / nr_periods 就是限流命中率，超过百分之几就值得处理。

    处方：① 放宽或去掉 limit，改用 cpu.weight 做相对分配；② 缩短 period（有些场景可行）让配额更平滑；③ 检查应用是否感知配额——老 JVM/Go 按 /proc/cpuinfo 的宿主核数开线程池和 GC 线程，在 2 核配额下等于自己给自己制造争用。

  4. 中级taskset 绑核之后，为什么延迟毛刺还在？

    因为 taskset 只约束了「我不被搬走」，没约束「别人不搬过来」，更管不了中断。绑核后这个核上仍然可能有：

    • 被负载均衡放过来的普通任务；
    • 硬中断与软中断（网卡、定时器）——它们不受调度优先级约束，来了就打断；
    • 每 tick 一次的时钟中断；
    • kworker、RCU 回调等内核线程。

    要真正独占一个核，需要四件套配合：isolcpus= 把核从负载均衡里摘出来、nohz_full= 免掉周期时钟中断、rcu_nocbs= 把 RCU 回调挪走、irqaffinity= 或 /proc/irq/N/smp_affinity_list 把中断赶到别的核。在容器里则用 cgroup 的 cpuset.cpus，它比 taskset 可靠——新创建的线程会自动继承约束。

10.3 高级（体现深度）

  1. 高级EEVDF 相比 CFS 解决了什么根本问题？

    CFS 把「CPU 份额」和「调度延迟」耦合在 nice 这一个旋钮上。一个只需要极少 CPU 但要求快速响应的任务（心跳、控制面），在 CFS 下只能靠调低 nice 来蹭响应速度，而这会连带给它更多份额——你为了延迟被迫牺牲了公平。

    EEVDF 把两者拆开：

    • lag（应得减实得）负责公平：只有 lag ≥ 0 的任务才 eligible，超支的必须先等回来。
    • 虚拟截止时间负责延迟：由任务请求的时间片长度推出，请求越小的时间片截止越早、越优先被选中，但相应地每次也只跑那么短。

    于是「我只要一点点 CPU，但请让我马上拿到」第一次可以被直接表达。较新内核（6.12 起）可通过 sched_setattr() 的 sched_runtime 请求自定义时间片。

    代价要说清：小时间片意味着更频繁的上下文切换，是拿吞吐换延迟，不能给计算密集线程滥用。

  2. 高级SCHED_DEADLINE 的准入控制是什么？它比 SCHED_FIFO 强在哪？

    DEADLINE 任务声明三元组 (runtime, deadline, period)：每 period 内需要 runtime 的 CPU，且必须在 deadline 前完成。内核用 EDF（最早截止优先）调度，并在 sched_setattr() 时做准入控制：检查所有 DEADLINE 任务的带宽之和 Σ(runtime/period) 是否超出系统容量，超了就返回 EBUSY 拒绝新任务。

    相对 FIFO 的三点优势：

    • 优先级是"绝对"的而不是"相对"的：FIFO 只告诉你谁比谁高，无法回答"系统整体还扛不扛得住"；DEADLINE 直接把这个问题变成可计算的带宽约束。
    • 有资源隔离：任务用完 runtime 还没结束会被 throttle 到下个周期，不会像失控的 FIFO 那样拖垮整机。
    • 不需要人工排优先级：多个周期任务的相对紧急程度由截止时间自动决定，避免了"到底谁该是 50 谁该是 51"这种拍脑袋。

    代价：必须能给出可靠的 WCET（最坏执行时间）估计，runtime 估小了会被 throttle，估大了浪费带宽还挤掉别人的准入。所以它适合真正周期化、行为可测的任务，不适合请求驱动的服务。

  3. 高级为什么 Linux 用 per-CPU runqueue 而不是一个全局队列？代价是什么？

    全局队列的问题是可扩展性：每次调度决策都要拿同一把锁，几十上百个核在同一条 cacheline 上争用，锁本身就成了瓶颈；而且这条 cacheline 会在所有核之间不停弹跳（cacheline bouncing）。

    per-CPU runqueue 让常规路径完全本地化：选下一个任务只碰本核的数据结构，无跨核同步，随核数线性扩展。

    代价与补偿机制：

    • 负载可能不均——需要额外的负载均衡器（周期性均衡、idle 时偷任务、唤醒时择核）。
    • 均衡本身有成本——迁移会丢 cache 热度，跨 NUMA 还要付远端访存代价。所以内核按硬件拓扑分层建立调度域，越"远"的层级均衡门槛越高、频率越低，并用 migration_cost 做阻尼。
    • 公平只在队列内部严格成立——vruntime 是每队列的相对值，跨队列比较无意义，迁移时要做归一化。全局公平只能靠均衡近似达成。

    这是典型的「用局部最优 + 周期性纠偏，换取可扩展性」的系统设计取舍，和内存分配器的 per-CPU cache、网络栈的 RSS 多队列是同一个思路。

  4. 高级一个低延迟服务的 P99 有 15 ms 毛刺，怎么系统性定位是不是调度导致的？

    按「先证伪再深挖」的顺序，不要一上来就调参数：

    1. 先排除非调度因素：vmstat 1 看 r / b；b 高就是 I/O，先去查存储。GC / 缺页 / 锁竞争也要先排掉。
    2. 拿到直接证据：cat /proc/<pid>/sched 看 se.statistics.wait_max。如果它就在 15 ms 量级，那毛刺确实等于调度延迟；如果它只有几十微秒，说明时间花在别处，调度是清白的。
    3. 定位是谁抢的：perf sched record + perf sched latency --sort=max 找出最大延迟属于哪个任务，再用 perf sched timehist 看那一时刻 CPU 上跑的是什么。
    4. 看分布而不是均值：用 bpftrace 的 runqlat 直方图确认长尾的量级和频率，均值几乎总是骗人的。
    5. 分类处方：被普通任务抢 → 绑核 + isolcpus，或提优先级；被中断/内核线程抢 → 中断亲和 + nohz_full + rcu_nocbs；被 cgroup 限流 → 看 cpu.stat 的 nr_throttled；跨 NUMA 抖动 → numastat -p 加 numactl 钉住。
    6. 最后才考虑内核参数或 PREEMPT_RT，且一次只改一项并测量。

    加分点：说清「平均延迟正常、最坏延迟爆炸」是实时性问题的典型signature，所以从一开始就要用 max / 分位数而不是均值来衡量。
