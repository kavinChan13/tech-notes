01

为什么需要调度器

几千个线程抢几十个核

几十个核、成千上万可运行线程。调度器要同时满足公平（别饿死）、吞吐（少切换）、响应（交互要快）、确定（实时不能拖）——无法同时最优。

生活类比：医院分诊台

CPU 核是医生，线程是病人。急诊（实时）插队，普通门诊按公平排，还不能让谁永远排不上。医生频繁换病人会浪费在「重新了解病情」（刷新 cache / TLB）。

映射：医生=CPU 核 · 病人=线程 · 急诊插队=实时优先级 · 换病人成本=上下文切换

先厘清「可运行」到底指什么

调度器只看 TASK_RUNNING：正在跑的 + 在 runqueue 里等的。睡眠任务不在候选集，这直接决定 load / vmstat 该怎么读。

状态含义是否参与调度是否计入 load average
R可运行：正在跑，或在 runqueue 里等是是
S可中断睡眠：等 I/O、等锁、等事件，可被信号唤醒否否
D不可中断睡眠：通常在等磁盘 / NFS，连信号都打不断否是
T / t被 SIGSTOP 停住 / 被 ptrace 停住否否
Z僵尸：已退出但父进程没回收否否

最常见的误读：load average 不是 CPU 利用率

  • Linux load 是 R + D 的指数平均（传统 Unix 只算 R）。8 核 load 50 可能 CPU 全闲——50 个进程卡在坏盘的 D。
  • 判据用 vmstat 的 r（可运行队列）和 b（不可中断阻塞），比 load 准。这时候去调 nice、加核全是白费。
命令目的判据
cat /proc/loadavg1/5/15 分钟均值第 4 列是「正在跑 / 总任务」；高 load 不能直接当 CPU 挤
vmstat 1区分 CPU 挤还是 I/O 堵r 高才是 CPU 挤；r 低、b 高、wa 高 → 磁盘/NFS，调度旋钮一个都别动
调度器的核心难题是「公平」和「响应性」的矛盾：交互任务（键盘、鼠标）需要立刻响应但只占很少 CPU；批处理任务（编译、渲染）想吃满 CPU。好的调度器让交互任务感觉「秒响应」，同时批任务照样跑满——CFS/EEVDF 就是为此设计的。
02

调度类与优先级空间

Linux 有多套调度策略叠在一起

Linux 不是一个算法，而是分层的调度类，按优先级从高到低：Stop → Deadline → RT → CFS/EEVDF → Idle。高优先级类里只要还有可运行任务，低优先级类一轮都轮不到——类间是严格优先，不是加权，所以一个失控的 RT 真能把普通任务全饿死。

调度类策略用途
Stop（内核内部，无用户接口）CPU 热插拔、任务迁移这类必须立刻执行的内核操作
DeadlineSCHED_DEADLINEEDF，按截止时间调度，用户可用的最高优先级，硬实时
Real-TimeSCHED_FIFO / SCHED_RR固定优先级（1-99），实时任务
公平（CFS/EEVDF）SCHED_OTHER / SCHED_BATCH / SCHED_IDLE绝大多数进程，靠 nice 值调权重
Idle（内核内部）没别的可跑时才跑的 idle 任务，负责进入省电状态

一张图看懂优先级数值的三套坐标系

「优先级」至少有三种数值：内核 prio（0–139，越小越高）、实时 rtprio（1–99，越大越高）、普通任务 nice（−20–19）。混用是面试和排障最容易翻车的地方。

nice 值：普通任务的「谦让度」

  • −20（最不谦让）到 +19（最谦让），默认 0。内核用 sched_prio_to_weight[]，每差 1 级权重约 1.25 倍：nice 0 = 1024，nice 5 ≈ 335，nice 19 = 15。
  • 两个 CPU 密集任务抢一个核：nice 0 vs 5 ≈ 1024 : 335 ≈ 75% : 25%。空闲时谁都跑满，nice 不起作用。
  • 普通用户只能调高 nice；调低要 CAP_SYS_NICE。SCHED_BATCH 不做唤醒抢占优化；SCHED_IDLE 权重极低，适合后台索引。
命令目的判据
ps -eo pid,cls,rtprio,ni,pri,psr,comm --sort=-rtprio看策略 / 实时优先级 / 所在核FF/RR/DLN 排在 TS 前面；注意 ps 的 PRI = 139 − prio，和内核方向相反，原始值看 /proc/PID/stat 第 18 字段
nice -n 10 ./job / renice -n 5 -p PID启动或事后改谦让度只在 CPU 不够分时改变份额
chrt -p PID / chrt --idle 0 ./reindex查策略；丢进 SCHED_IDLEFIFO 会打印 priority 1–99；OTHER/BATCH/IDLE 的 priority 恒为 0
优先级反转：高优先级 RT 等一把被低优先级持有的锁，中优先级再抢走低优先级的 CPU——高优先级被间接饿死。1997 年火星探路者号反复重启就是这个。解法：优先级继承（PI mutex），持锁者临时继承等待者的优先级。§5 给出用法。
03

CFS：完全公平调度

2007–2023 的默认调度器

CFS 的核心：让每个任务获得理想公平份额。用 vruntime 记账（按权重加权），永远挑最小的那个跑——最亏欠的先跑。

vruntime：实际 CPU 时间按权重缩放。Δvruntime = Δ真实时间 × (1024 / 权重)。nice 0 权重正好 1024，vruntime 等于真实时间；nice −5（权重 3121）跑 1 秒只记 0.33 秒，于是被反复选中。
vruntime 像记账

CPU 时间是「工时」。谁领得最少，下一份活先给谁。nice 低的是 VIP：干 1 小时只记 0.33 小时，所以能领到更多活。

映射：记账本=红黑树 · 已领工时=vruntime · VIP 折扣=nice 权重 · 先给最少的人=取最左
命令目的判据
ls /sys/kernel/debug/sched/看当前旋钮（约 5.13 起从 sysctl 搬到 debugfs）EEVDF 内核以 base_slice_ns 为主；老内核还有 sched_latency_ns / min_granularity_ns
sysctl -a | grep sched_老内核的 latency / granularity / migration_cost值随核数 tunable_scaling 自动放大，8 核机上看到的不是 4 核机的值

组调度：为什么容器里的 CPU 份额是分层的

公平只做在任务层，开 200 个线程的容器就能挤死只有 2 个线程的容器。组调度先按 cpu.weight 在 cgroup 之间切一刀，再在组内按 vruntime 分。

读懂 /proc/PID/sched

单任务调度行为最直接的入口。三个字段就能定性：

命令 / 字段目的判据
cat /proc/PID/sched单任务记账vruntime 只在本 CPU 队列内可比
wait_sum / sum_exec_runtime排队 vs 干活排队占比 > 10% → CPU 供给不足或同核被挤
wait_max最坏一次调度延迟低延迟服务的 P99 毛刺往往就等于这个数
nr_involuntary_switches被抢占次数占 nr_switches 高 → CPU 争用；低但总数巨大 → 自己在频繁阻塞
nr_migrations换核次数高说明 cache 热度反复丢失

EEVDF：CFS 的继任者

Linux 6.6（2023）起的默认调度器

CFS 只保证长期公平，任务无法表达「我只要一点点 CPU，但要马上拿到」。想降延迟只能调 nice，而 nice 同时改了份额。EEVDF（内核 6.6 起默认）把「份额」和「延迟」拆成两个维度。

生活类比：食堂窗口的两条规则

CFS 只有一条：谁打的饭最少谁先来，拿餐巾纸的人也得跟端餐盘的一起排。EEVDF 加了第二条：超额者先等；没超额的人里，谁说「我只要 10 秒」谁先上。

映射：打饭总量=CPU 份额 · 超额者先等=lag · 我只要 10 秒=小时间片 · 放行顺序=虚拟截止
维度CFSEEVDF
选择依据vruntime 最小eligible 中虚拟截止最早
公平的保证方式vruntime 单调追平lag ≥ 0 的准入条件
能否单独表达"低延迟"不能，只能调 nice（连份额一起改）能，请求更小的时间片即可
时间片由调度周期 ÷ 任务数推出任务可自行请求（默认由 base_slice_ns 给）
唤醒抢占靠 wakeup_granularity 这类启发式由 lag 与截止时间自然推出，启发式更少
睡眠任务的份额唤醒时把 vruntime 拉近最小值，规则较 ad-hoclag 在睡眠期间被保留，语义更一致
命令目的判据
cat /sys/kernel/debug/sched/base_slice_nsEEVDF 默认时间片（取代旧 latency/granularity）常见 3 ms；改小等于全局用吞吐买延迟
grep PLACE_LAG /sys/kernel/debug/sched/features确认当前是不是 EEVDF出现 PLACE_LAG / RUN_TO_PARITY 即是

6.12 起普通任务可用 sched_setattr() 的 sched_runtime 请求自定义时间片（仍是 SCHED_OTHER，份额不变）。心跳 / 控制面线程可以要 0.3 ms；计算密集线程别用——切换会吃掉吞吐。内核不支持时返回 EINVAL，要能降级。

面试官想听的是「EEVDF 解决了 CFS 的什么问题」而不是算法细节。标准答案：CFS 把"份额"和"延迟"耦合在 nice 这一个旋钮上，EEVDF 用 lag 管公平、用请求时间片管延迟，把两者解耦了。能再补一句「所以低延迟服务不再需要靠调低 nice 来蹭响应速度」就很到位。
05

实时调度与 PREEMPT_RT

当「公平」不够，你要「确定」

普通调度追求平均；实时追求最坏情况可控——不是「快」，是可预测。

策略行为典型用途
SCHED_FIFO同优先级先到先跑，一直跑到主动让出 / 阻塞 / 被更高优先级抢占，无时间片周期性控制环、音频回调
SCHED_RR同优先级之间轮转（有时间片，见 sched_rr_get_interval），其余同 FIFO多个同等重要的实时任务
SCHED_DEADLINE指定 (runtime, deadline, period)，内核用 EDF 调度并做准入控制有明确周期与预算的任务

把一个线程变成实时线程

三件套缺一不可：mlockall(MCL_CURRENT | MCL_FUTURE)（关键路径上缺页是毫秒级不确定性）、pthread_setschedparam(..., SCHED_FIFO, ...)（无 CAP_SYS_NICE 会 EPERM）、PTHREAD_PRIO_INHERIT 的 mutex（防优先级反转，不是可选项）。业务实时优先级落在 10–60，99 会压过 migration/ 和 watchdog/。

命令目的判据
chrt -f 50 ./loop / chrt -r 20 ./wFIFO / RR 启动需要特权；给二进制 setcap cap_sys_nice+ep 比整进程 root 安全
chrt -m / chrt -p PID看取值范围 / 当前策略FIFO/RR 是 1–99；DEADLINE 不用静态优先级

SCHED_DEADLINE 与准入控制

FIFO 的优先级是相对的——只知道谁比谁高，不知道系统还扛不扛得住。DEADLINE 直接声明「每 10 ms 需要 2 ms CPU」，内核做准入控制：所有 DEADLINE 的 runtime / period 之和超容量，sched_setattr 返回 EBUSY——宁可不让你跑，也不让已承诺的任务违约。

struct sched_attr attr = {0};
attr.size            = sizeof(attr);
attr.sched_policy    = SCHED_DEADLINE;
attr.sched_runtime   =   2 * 1000 * 1000;   // 每周期最多用 2 ms CPU
attr.sched_deadline  =   8 * 1000 * 1000;   // 必须在 8 ms 内用完
attr.sched_period    =  10 * 1000 * 1000;   // 周期 10 ms
// 约束：runtime <= deadline <= period

if (syscall(SYS_sched_setattr, 0, &attr, 0) < 0) {
    if (errno == EBUSY)   // ★ 准入被拒：系统已承诺的实时负载放不下你了
        fprintf(stderr, "admission control rejected: 系统实时带宽不足\n");
}
// 用完 runtime 还没结束？任务会被 throttle 到下个周期，而不是拖垮别人。

用 RT 调度的另外三个坑

  • 优先级选得太高：业务别用 99，会压过内核迁移 / watchdog，甚至 hard lockup。
  • 忘了 mlockall：一次缺页足以毁掉所有实时保证；启动时锁定并预热栈。
  • 容器里的 RT：要单独配 RT 带宽，否则干脆别用容器跑硬实时。
命令目的判据
dmesg | grep -i 'rt throttling'实时类是否被墙过出现 RT throttling activated → 有 FIFO/RR 死循环或预算估小了
cat /proc/sys/kernel/sched_rt_{period,runtime}_us看 / 改这堵墙默认 1000000 / 950000；runtime=-1 关掉限流

PREEMPT_RT 不改调度策略，而是把内核改成几乎处处可抢占——自旋锁变 RT mutex、中断下半部线程化，最坏延迟从毫秒压到微秒。2024 年合入主线（6.12）。详见 PREEMPT_RT 深入。

06

多核负载均衡

调度器是 per-CPU 的

每个 CPU 一个 runqueue，避免全局锁。代价是负载可能不均。负载均衡器在三个时机搬任务。

调度延迟还有一个不那么显眼的下游影响：它才是「定时器不准」的主要来源。定时器到期只是把线程放进 runqueue，什么时候真正跑起来由这一章讲的调度决定——空闲时几微秒，繁忙时可达毫秒级，远大于定时器硬件本身的误差。所以「提高定时器精度」这个需求，大部分时候要在这一章解决，而不是去调定时器。展开见 时间与时钟 · 精度的损耗链。
时机触发条件行为
周期性均衡时钟中断里按调度域的 balance_interval 检查从最忙的组往本组拉任务，层级越高检查越稀疏
idle 均衡某个核发现自己没活干，准备进 idle立刻去别的核"偷"任务，这是最积极的一档
唤醒时放置任务被唤醒，要决定放哪个核（select_task_rq）倾向放回唤醒者附近（wake affine，共享 cache），或找个 idle 核

NUMA balancing 是另一套机制

  • 周期性取消页表映射制造缺页，观察谁在访问哪块内存，再把任务和页挪到一起。
  • 访存模式稳定的服务是好事；大内存随机访问（很多数据库）是纯开销——hint_faults 巨大而 pages_migrated 很小就该关 kernel.numa_balancing。
命令目的判据
cat /sys/kernel/debug/sched/domains/cpu0/domain*/name看本机调度域层级常见 SMT / MC / NUMA；没有 SMT 说明没开超线程
head /proc/schedstat每 CPU 运行 / 等待 / 切换格式随内核变，看列的相对大小
grep numa_ /proc/vmstatNUMA balancing 是否白花numa_hint_faults ≫ numa_pages_migrated → 考虑关掉
本章讲的是调度器怎么把线程摊到核上。如果看到的现象是「加了核，吞吐反而降了」，先别怀疑均衡器：更常见的原因是共享资源的串行段加上跨核一致性开销，两者合起来就是那条会掉头向下的 USL 曲线，怎么压几个并发度点把两个系数拟合出来、进而判断该纵向加核还是横向扩机器，见 容量估算与背压 · USL。判据：perf sched / runqlat 显示线程在等 CPU，是本章的调度问题；没人等 CPU、但每核吞吐随核数增加而下降，是争用问题，加机器也一样不涨。

默认不可控、可以绑核

调度对象是线程不是进程。默认 soft affinity：尽量留原核保热缓存，该核忙了就 migrate。对应用是黑盒——这次核 2、下次核 5，false sharing / 多核内存序 bug 会时有时无。

#define _GNU_SOURCE
#include <pthread.h>
#include <sched.h>

// 把当前线程钉在 CPU 6 上
cpu_set_t set;
CPU_ZERO(&set);
CPU_SET(6, &set);
int rc = pthread_setaffinity_np(pthread_self(), sizeof(set), &set);
if (rc != 0) fprintf(stderr, "setaffinity: %s\n", strerror(rc));

// 回读确认——写进去不代表生效，cpuset 或容器可能已经限制了可用核集合
CPU_ZERO(&set);
pthread_getaffinity_np(pthread_self(), sizeof(set), &set);
for (int i = 0; i < CPU_SETSIZE; i++)
    if (CPU_ISSET(i, &set)) printf("allowed: cpu%d\n", i);
命令目的判据
taskset -c 2,3 ./w / taskset -cp 6,7 PID启动或事后绑核只约束「我不被搬走」，挡不住别人搬过来；新线程不一定继承，cgroup cpuset.cpus 更可靠
ps -eLo pid,tid,psr,comm看每个线程实际在哪个核PSR 列；绑了却飘 → cpuset / 容器把集合裁过了
echo 6-7 > .../cpuset.cpus服务级绑核 + 可顺带 cpuset.mems后代线程自动继承
隔离手段作用范围能挡住什么挡不住什么
taskset / sched_setaffinity指定线程自己被迁走别的任务跑到这个核上来
cgroup cpuset.cpus一组进程及其后代组内外互相越界内核线程、中断
isolcpus=（启动参数）整机普通任务被均衡过来显式绑上来的任务、中断
nohz_full=（启动参数）整机核上只剩一个任务时的周期性时钟中断其它中断、IPI
irqaffinity= / /proc/irq/N/smp_affinity_list整机 / 单个中断硬中断落在关键核上NMI、IPI
❌ 只绑核

taskset -c 6 ./app 之后核上仍有被均衡过来的任务、irqbalance 送来的网卡中断、每 tick 时钟中断。P99 照样抖。

✅ 成套隔离

启动参数 isolcpus=6,7 nohz_full=6,7 rcu_nocbs=6,7 irqaffinity=0-5，运行时 taskset -c 6 chrt -f 50 ./app。核上只剩你的线程和极少数 IPI。

好处副作用
绑核可复现、保热缓存、隔离干扰不能借闲核，可能饿死；负载不均
不绑（默认）调度器借闲核，吞吐更好核号不可控，多核 bug 难复现
绑核不取消数据竞争：只改变「跑在哪」，不改变「要不要锁 / atomic」。单核绑死仍会交错（见 OS 基础 · 单核不是一进程、内存模型 §8.1）。

NUMA 感知调度与内存本地性见 NUMA + 高级内存。

抢占与上下文切换

切换不是免费的

抢占判定很朴素：内核在检查点看 TIF_NEED_RESCHED，置位了就 schedule()。检查点包括系统调用返回用户态、中断返回、显式 cond_resched()、以及可抢占内核上持锁计数归零。标志由「更高优先级被唤醒」或「时间片 / 虚拟截止到期」置上。

抢占模型内核态可抢占性最坏延迟量级典型场景
PREEMPT_NONE只在返回用户态时切数十毫秒吞吐优先的服务器、批处理
PREEMPT_VOLUNTARY额外在显式 might_sleep() 点让出毫秒级通用发行版默认
PREEMPT内核态除临界区外处处可抢占亚毫秒桌面、低延迟服务
PREEMPT_RT连大部分自旋锁临界区也可抢占微秒级工业控制、音频、机器人
命令目的判据
cat /sys/kernel/debug/sched/preempt看当前抢占模型括号里的是正在用的；echo full 可运行时切换

切换到底花多少钱

命令目的判据
perf stat -e context-switches,cpu-migrations ./w量化切换与迁移每秒上万次切换通常偏高；迁移多说明 cache 热度保不住
grep ctxt /proc/PID/status / pidstat -w -p PID 1区分自愿 vs 被抢占自愿高、被抢低 → 等 I/O/锁（见 死锁与锁竞争调试）；被抢占 > 20% → 线程池开太大或该提优先级

两者都低但延迟高

可能是同核中断或内核线程打断，走 §6 隔离，或者根本不是调度问题。

协程/异步之所以快，正是因为它在用户态做「切换」（只换栈和几个寄存器，纳秒级、无内核参与、不丢 TLB），而线程切换要陷入内核。这是 协程 相对线程的核心优势——但它换不来抢占式的公平，一个不让出的协程会卡死整个线程。

案例 1 · CPU 用不满，服务却变慢

K8s 里 Java 服务 P99 从 30 ms 涨到 800 ms，容器 CPU 45%，宿主机也不忙。

案例 2 · 实时线程每隔几秒抖一次

SCHED_FIFO 50 的控制线程，99.9% 周期 < 50 μs，每几秒一次 300 μs 尖峰。

perf sched timehist 抓到尖峰时上 CPU 的是同核 kworker 和网卡软中断。硬中断 / 软中断不受调度器优先级约束——来了就打断你。处方：§6 四件套，把 IRQ 赶到别的核。

命令目的判据
cat /proc/interrupts中断落在哪些核关键核上 eth0 计数在涨 → 挪走 smp_affinity_list
ps -eLo psr,cls,rtprio,comm该核还剩谁除了你的 FIFO 还应只剩极少数内核线程

案例 3 · 同样的压测，吞吐每次差 20%

32 线程计算服务，8 万到 10 万 QPS 随机波动，代码和数据完全一样。

跨 NUMA 迁移：内存在 node 0，线程被均衡到 node 1，访存走 UPI。搬走哪些线程是随机的，远端比例不同，吞吐就飘。单节点放不下就按节点分片，比让调度器「自己看着办」可靠。NUMA 细节见 NUMA + 高级内存。

命令目的判据
numastat -p PID内存落在哪个节点Private 几乎全在 node 0，线程却一半在 node 1 核上 → 远端访存
numactl --cpunodebind=0 --membind=0进程钉在一个节点吞吐应稳住；或用 cpuset.mems

调度相关排障速查

  • 先分清是不是调度：vmstat 的 r / b；b 高是 I/O。
  • 延迟抖动 → wait_max 对上 P99 再用 perf sched timehist 看谁抢的。
  • 中断 / 内核线程 → §6 四件套；确定性 → FIFO 或 DEADLINE + PI mutex + mlockall，必要时 PREEMPT_RT。
  • RT 卡住别人 → dmesg | grep 'RT throttling'，别急着关限流。
  • 非自愿切换高 → 线程池按宿主核数开、容器只给 2 核是最常见原因。
  • 容器「没满却慢」→ cpu.stat 的 nr_throttled。吞吐乱飘 → numastat -p。
  • 动 sched_* 永远是最后一步，一次只动一个。
一句话记忆：普通任务靠 CFS/EEVDF 求公平，实时任务靠 RT/Deadline 求确定，低延迟靠绑核 + 隔离 + 中断避让 + PREEMPT_RT 消抖动。而 90% 的「调度问题」最后都被证明不是调度问题。
10

面试题（12 道）

分层自测

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础load average 高就说明 CPU 不够用吗？

    不是。Linux 的 load average 统计的是 R 状态 + D 状态任务数的指数移动平均，而 D 状态是不可中断睡眠（通常在等磁盘或 NFS）。所以一块坏盘就能让 load 飙到几十，而 CPU 完全空闲。

    正确做法是看 vmstat 1 的两列：r 是可运行队列长度（CPU 挤的信号），b 是不可中断阻塞数（I/O 堵的信号）。再配合 %wa 和 iostat 定性。

    补充加分：传统 Unix 的 load 只算 R 状态，Linux 特意把 D 算进来是为了反映"系统整体有多少工作被卡住"，代价就是这个指标不再等价于 CPU 压力。

  2. 基础nice 值到底怎么影响 CPU 分配？差 1 级差多少？

    nice 通过一张权重表映射成调度权重，每差 1 级权重约变化 1.25 倍。nice 0 的权重定为 1024，nice 1 是 820，nice 5 约 335，nice 19 只有 15。

    两个 CPU 密集任务抢一个核时，拿到的 CPU 时间比 = 权重比。nice 0 与 nice 5 的比例约 1024 : 335，即 75% 对 25%。

    三个常见误区：① nice 不是百分比，也不是绝对保证；② 只有在 CPU 真的不够分时才起作用，空闲时谁都跑满；③ nice 永远抢不过任何一个实时任务，因为调度类之间是严格优先，不是加权。

  3. 基础SCHED_FIFO 和 SCHED_RR 有什么区别？什么时候用哪个？

    两者都是固定优先级的实时策略，高优先级永远抢占低优先级。唯一区别在同优先级任务之间：

    • SCHED_FIFO：没有时间片，一旦上 CPU 就一直跑，直到自己阻塞、主动 sched_yield()、或被更高优先级抢占。
    • SCHED_RR：同优先级之间按时间片轮转（可用 sched_rr_get_interval() 查询）。

    选择：如果同一优先级只有一个任务（常见的控制环、音频线程），用 FIFO，行为最可预测；如果有多个地位相同的实时任务需要共享 CPU，用 RR 避免其中一个独占。

  4. 基础上下文切换的开销主要花在哪？为什么协程比线程快？

    分两块：

    • 直接成本：保存/恢复寄存器、切换页表（跨进程时）、更新调度统计。几百纳秒到 1–2 微秒。
    • 间接成本（大头）：L1/L2 cache 和 TLB 被新任务冲掉，切回来要重新预热。工作集大的任务可达几十微秒。

    协程的切换发生在用户态：只换栈指针和少量寄存器，不陷入内核、不切页表、不丢 TLB，所以是纳秒级。

    但要说清代价：协程是协作式的，一个不主动让出的协程会卡死整个载体线程，也拿不到抢占式调度的公平性和隔离性。

10.2 中级（区分熟练度）

  1. 中级解释 vruntime。为什么 CFS 选 vruntime 最小的任务就能实现公平？

    vruntime 是「按权重缩放后的已运行时间」：Δvruntime = Δ真实运行时间 × 1024 / 权重。权重越高（nice 越低），同样的真实时间记账越少。

    CFS 每次挑 vruntime 最小的任务跑，等价于「让所有任务的 vruntime 尽量追平」。而 vruntime 相等 ⟺ 真实运行时间之比等于权重之比 ⟹ 按权重公平。

    几个要点：① 用红黑树维护有序集合，取最左节点；② vruntime 是每个运行队列的相对值，跨 CPU 不可直接比较，任务迁移时要做归一化；③ 睡眠任务醒来时 vruntime 会被拉到接近队列最小值——否则它睡了 10 分钟，醒来后会独占 CPU 10 分钟去"追平"，这既不公平也很危险。

  2. 中级什么是优先级反转？为什么 PI mutex 能解决？

    场景：高优先级任务 H 等一把被低优先级任务 L 持有的锁。本来 L 跑完释放锁就好，但一个中优先级任务 M 抢占了 L——M 不需要锁，却因为优先级比 L 高而一直占着 CPU。结果是 H 被 M 间接饿死，虽然 M 的优先级明明比 H 低。1997 年火星探路者号的反复重启就是这个问题。

    优先级继承（PI）：当 H 阻塞在 L 持有的锁上时，内核临时把 L 的优先级提升到 H 的水平。这样 M 就抢不走 L 的 CPU，L 得以尽快跑完并释放锁。锁释放后 L 的优先级恢复原值。

    用法是 pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT)。另一个方案是优先级天花板（PRIO_PROTECT），持锁即提升到预设上限，开销更小但需要静态分析出天花板值。

    补充：这也是 PREEMPT_RT 的关键机制——它把内核里的自旋锁换成可睡眠的 RT mutex，正是因为 RT mutex 支持优先级继承。

  3. 中级容器 CPU 使用率只有 40%，但接口 P99 暴涨。怎么查？

    首先怀疑 cgroup CPU 配额的突发限流。cpu.max 是「每个 period 内最多用多少 CPU 时间」，突发负载会在周期内提前耗尽配额，剩余时间被整段冻结。平均利用率被拉平后看着不高，但请求就卡在被冻结的那几十毫秒里。

    证据：

    cat /sys/fs/cgroup/<path>/cpu.stat
nr_periods 41022
nr_throttled 18847        # 被限流的周期数
throttled_usec 982114000  # 累计冻结时长

    nr_throttled / nr_periods 就是限流命中率，超过百分之几就值得处理。

    处方：① 放宽或去掉 limit，改用 cpu.weight 做相对分配；② 缩短 period（有些场景可行）让配额更平滑；③ 检查应用是否感知配额——老 JVM/Go 按 /proc/cpuinfo 的宿主核数开线程池和 GC 线程，在 2 核配额下等于自己给自己制造争用。

  4. 中级taskset 绑核之后，为什么延迟毛刺还在？

    因为 taskset 只约束了「我不被搬走」，没约束「别人不搬过来」，更管不了中断。绑核后这个核上仍然可能有：

    • 被负载均衡放过来的普通任务；
    • 硬中断与软中断（网卡、定时器）——它们不受调度优先级约束，来了就打断；
    • 每 tick 一次的时钟中断；
    • kworker、RCU 回调等内核线程。

    要真正独占一个核，需要四件套配合：isolcpus= 把核从负载均衡里摘出来、nohz_full= 免掉周期时钟中断、rcu_nocbs= 把 RCU 回调挪走、irqaffinity= 或 /proc/irq/N/smp_affinity_list 把中断赶到别的核。在容器里则用 cgroup 的 cpuset.cpus，它比 taskset 可靠——新创建的线程会自动继承约束。

10.3 高级（体现深度）

  1. 高级EEVDF 相比 CFS 解决了什么根本问题？

    CFS 把「CPU 份额」和「调度延迟」耦合在 nice 这一个旋钮上。一个只需要极少 CPU 但要求快速响应的任务（心跳、控制面），在 CFS 下只能靠调低 nice 来蹭响应速度，而这会连带给它更多份额——你为了延迟被迫牺牲了公平。

    EEVDF 把两者拆开：

    • lag（应得减实得）负责公平：只有 lag ≥ 0 的任务才 eligible，超支的必须先等回来。
    • 虚拟截止时间负责延迟：由任务请求的时间片长度推出，请求越小的时间片截止越早、越优先被选中，但相应地每次也只跑那么短。

    于是「我只要一点点 CPU，但请让我马上拿到」第一次可以被直接表达。较新内核（6.12 起）可通过 sched_setattr() 的 sched_runtime 请求自定义时间片。

    代价要说清：小时间片意味着更频繁的上下文切换，是拿吞吐换延迟，不能给计算密集线程滥用。

  2. 高级SCHED_DEADLINE 的准入控制是什么？它比 SCHED_FIFO 强在哪？

    DEADLINE 任务声明三元组 (runtime, deadline, period)：每 period 内需要 runtime 的 CPU，且必须在 deadline 前完成。内核用 EDF（最早截止优先）调度，并在 sched_setattr() 时做准入控制：检查所有 DEADLINE 任务的带宽之和 Σ(runtime/period) 是否超出系统容量，超了就返回 EBUSY 拒绝新任务。

    相对 FIFO 的三点优势：

    • 优先级是"绝对"的而不是"相对"的：FIFO 只告诉你谁比谁高，无法回答"系统整体还扛不扛得住"；DEADLINE 直接把这个问题变成可计算的带宽约束。
    • 有资源隔离：任务用完 runtime 还没结束会被 throttle 到下个周期，不会像失控的 FIFO 那样拖垮整机。
    • 不需要人工排优先级：多个周期任务的相对紧急程度由截止时间自动决定，避免了"到底谁该是 50 谁该是 51"这种拍脑袋。

    代价：必须能给出可靠的 WCET（最坏执行时间）估计，runtime 估小了会被 throttle，估大了浪费带宽还挤掉别人的准入。所以它适合真正周期化、行为可测的任务，不适合请求驱动的服务。

  3. 高级为什么 Linux 用 per-CPU runqueue 而不是一个全局队列？代价是什么？

    全局队列的问题是可扩展性：每次调度决策都要拿同一把锁，几十上百个核在同一条 cacheline 上争用，锁本身就成了瓶颈；而且这条 cacheline 会在所有核之间不停弹跳（cacheline bouncing）。

    per-CPU runqueue 让常规路径完全本地化：选下一个任务只碰本核的数据结构，无跨核同步，随核数线性扩展。

    代价与补偿机制：

    • 负载可能不均——需要额外的负载均衡器（周期性均衡、idle 时偷任务、唤醒时择核）。
    • 均衡本身有成本——迁移会丢 cache 热度，跨 NUMA 还要付远端访存代价。所以内核按硬件拓扑分层建立调度域，越"远"的层级均衡门槛越高、频率越低，并用 migration_cost 做阻尼。
    • 公平只在队列内部严格成立——vruntime 是每队列的相对值，跨队列比较无意义，迁移时要做归一化。全局公平只能靠均衡近似达成。

    这是典型的「用局部最优 + 周期性纠偏，换取可扩展性」的系统设计取舍，和内存分配器的 per-CPU cache、网络栈的 RSS 多队列是同一个思路。

  4. 高级一个低延迟服务的 P99 有 15 ms 毛刺，怎么系统性定位是不是调度导致的？

    按「先证伪再深挖」的顺序，不要一上来就调参数：

    1. 先排除非调度因素：vmstat 1 看 r / b；b 高就是 I/O，先去查存储。GC / 缺页 / 锁竞争也要先排掉。
    2. 拿到直接证据：cat /proc/<pid>/sched 看 se.statistics.wait_max。如果它就在 15 ms 量级，那毛刺确实等于调度延迟；如果它只有几十微秒，说明时间花在别处，调度是清白的。
    3. 定位是谁抢的：perf sched record + perf sched latency --sort=max 找出最大延迟属于哪个任务，再用 perf sched timehist 看那一时刻 CPU 上跑的是什么。
    4. 看分布而不是均值：用 bpftrace 的 runqlat 直方图确认长尾的量级和频率，均值几乎总是骗人的。
    5. 分类处方：被普通任务抢 → 绑核 + isolcpus，或提优先级；被中断/内核线程抢 → 中断亲和 + nohz_full + rcu_nocbs；被 cgroup 限流 → 看 cpu.stat 的 nr_throttled；跨 NUMA 抖动 → numastat -p 加 numactl 钉住。
    6. 最后才考虑内核参数或 PREEMPT_RT，且一次只改一项并测量。

    加分点：说清「平均延迟正常、最坏延迟爆炸」是实时性问题的典型signature，所以从一开始就要用 max / 分位数而不是均值来衡量。
