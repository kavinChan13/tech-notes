1.1 从用户视角看 fd

用户空间里 fd 是非负小整数，三条铁律：0/1/2 预留给 stdin/stdout/stderr；open/socket/pipe 返回当前进程最小可用号；进程私有——A 的 fd=5 与 B 的 fd=5 无关。

int fd1 = open("/etc/hosts", O_RDONLY);   // 3（最小可用）
int fd2 = open("/etc/passwd", O_RDONLY);  // 4
close(fd1);                              // 3 立刻可被复用
int fd3 = open("/etc/group", O_RDONLY);   // 3，与 fd1 毫无关系
close(conn->fd);                         // 线程 A 关掉连接
write(conn->fd, buf, n);                 // 若 accept 抢到同号：静默写进别人的连接

1.2 为什么内核不直接返回指针？

✓安全隔离

内核指针进用户态等于拆掉 KASLR。int 是进程局部句柄，无法凭它越权。

✓引用计数

dup / fork 让多个 fd 指向同一内核对象；句柄让生命周期可数。

✓ABI 稳定

结构体布局可以演化，open() 返回 int 这个契约不变。

✓表索引即句柄

fd 就是 fd_array[] 下标，查找 O(1)。

「查表」本身还是一道检查点：吃 fd 的系统调用先 fdget()/fget()，一步做三件事——查号是否越 max_fds、查位图这一位是否置位（否则 -EBADF）、取指针的同时递增引用计数。

1.3 「最小可用」这条规定的代价

POSIX 强制返回当前最小空闲号，shell 才能在 dup2 出现前预测 stdout。代价有二：

一是分配不能简单自增：next_fd 记住上次分配到哪，close 更小的号时要回拨，位图之上还有 full_fds_bits 避免 50 万 fd 时扫 50 万位。二是号被立即复用。

✗ 提前 close 是最难查的一类 bug

号还空着 → EBADF，好查；已被 open/accept 抢走 → 读写打到无关对象、返回值一切正常，只表现为「偶尔有用户收到别人的响应」。只能靠所有权解决：先扣着号不放，现象消失即确诊。

1.4 fd 号不是「资源量」的好指标

ls /proc/<pid>/fd | wc -l 数的是表项，不是打开了多少文件，也不是内核内存。

你想知道的该看的数字为什么不能互相替代
这个进程占了多少 fd 配额ls /proc/<pid>/fd | wc -l受 RLIMIT_NOFILE 约束；dup 出来的每个号单独计一次
系统里有多少个打开状态/proc/sys/fs/file-nr 第一列数 struct file。dup/fork 不增加，两次 open 才增加
有多少个文件实体在被引用lsof 去重后的路径 / inode多个 struct file 可指向同一 inode
为此付了多少内核内存slabtop 的 filp / dentry / inode_cachestruct file 本身二三百字节，大头往往是 socket 缓冲

四个数字的结论方向完全不同：「fd 三万但 file-nr 只涨三千」＝多数来自 dup/fork，泄漏在句柄管理；「fd 正常但内存持续涨」＝每连接缓冲太大，与 fd 无关。

三级表详解

2.1 三层映射全景

这张图是整篇的地基：dup、fork、O_APPEND、「文件删了空间没释放」，答案都落在某一条箭头上。共享只可能发生在第 ② 层——① 进程私有、③ 全系统唯一，而偏移量恰好放在 ②。

三级表像酒店的房卡系统。房卡是 fd（① 层），入住记录是 struct file（② 层，记着谁在住、押金多少），房间是 inode（③ 层）。于是：多配一张卡（dup）不产生新记录、两卡共享押金；两次分别办入住是两条独立记录；把房间从客房表划掉（unlink）不赶走还在住的人。

2.2 三层职责划分

层级作用域关键数据回答什么问题
① FD Table进程私有fd → struct file*；FD_CLOEXEC 只在这一层"我的 fd=3 指向哪个打开文件？"
② Open File Table系统全局f_pos / f_flags / f_count"这次打开的上下文是什么？"
③ Inode Table文件系统级大小、权限、数据块、类型"这个文件本身是什么？"

2.3 为什么是三层而不是两层？

▶ 设计动机

① 保证进程隔离，③ 必须系统唯一（否则硬链接无法共享元数据）。② 存在是因为两件相反的事要同时成立：每次 open() 各自 pos，而 dup/fork 共享偏移。

砍掉 ② 会怎样：f_pos 挪进 ①，2>&1 会让 stdout/stderr 互相覆盖；挪进 ③，两个进程分别 open 就共享偏移，两个 cat 各读一半。两种极端都不可用。它的正式名字是 open file description，和 file descriptor 只差一个词。

2.4 引用计数的两个层次：f_count 与 i_count

两个独立计数管两件事，分清了「删了空间没释放」就不是玄学。

2.5 两个经典现象，用两个计数就能解释

现象一：close 了，但文件还在（也可能反过来）

close 减 f_count、unlink 减 i_nlink，两件事无关。所以 rm 只摘掉目录项，已打开的 struct file 直指 inode，照样读写到底——这被大量利用：

用法怎么做为什么可行
自动清理的临时文件open 后立刻 unlink，继续用那个 fd进程怎么退（含 SIGKILL）内核关 fd 时空间自动回收。O_TMPFILE 是原子版，连中间名字都没有
原子替换配置写 a.conf.tmp → fsync → rename旧 inode 的 i_nlink 归零，已打开旧文件的进程仍读到完整旧内容
升级正在跑的程序rm 旧可执行文件再放新的运行中进程经 mmap 持有旧 inode（所以升级后必须重启才生效）
logrotate 的 copytruncate拷走内容后 truncate 原文件到 0反例：写日志的进程还持有旧 inode，不重开就会一直写进已改名的文件

现象二：磁盘满了，但 du 找不到大文件

生产上最高频的 fd 排障：df 100%、du -sh /* 只有一半。文件已被 rm（i_nlink=0，走目录树数不到），但进程还持有 fd（i_count>0），数据块一个没释放。典型是运维 rm 了 nginx access.log 却没发 SIGUSR1。

顺序动作命令 / 判据
1确认差额df -h / 与 du -sxh /（-x 限制在同一文件系统）
2找出 deleted 文件sudo lsof +L1：NLINK=0 即确诊；SIZE/OFF 是扣住的空间
3同 NODE 不重复加master/worker 经 fork 继承同一 struct file，只占一份磁盘
4首选：让持有者重开kill -USR1 <nginx> / systemctl reload rsyslog
5次选：原地截断sudo sh -c '> /proc/PID/fd/N'。必须重定向，不能 rm。对 O_APPEND 安全；普通 O_WRONLY 会留下稀疏空洞（f_pos 还停在 38G）
6末选 / 核对重启进程；然后 df -h / 且 lsof +L1 应清空
⚠ 逐列判读 + 「df 比 du 大」不只有这一个原因

+L1 = 链接数 < 1，SIZE/OFF 是 i_size，各行相加应对上差额（txt/mem/DEL 行是映像与被删的 .so，通常只有几 MB）。仍对不上就换方向：挂载点被盖住、ext4 给 root 留的 5%、稀疏文件、inode 耗尽（df -i 100%，报错同样是 ENOSPC）。见 filesystem_storage_stack.html §7。

内核数据结构源码

3.1 task_struct → files_struct · 3.2 files_struct 与 fdtable · 3.3 struct file —— 第二层的核心 · 3.4 struct inode —— 第三层 · 3.5 fd 表的扩容

3.1 task_struct → files_struct

task_struct 用 files 指针挂上整张 fd 世界。线程共享同一张表（files_struct.count++），fork 则复制表、共享下面的 struct file。

3.2 files_struct 与 fdtable

同时有 fdtable* fdt 和内嵌的 fdtable fdtab 不是冗余：绝大多数进程一辈子 < 64 个 fd，数组和位图直接躺在 files_struct 里，超 NR_OPEN_DEFAULT 才扩容。

3.3 struct file —— 第二层的核心

偏移、打开标志、引用计数都在这里。O_APPEND/O_NONBLOCK 改这一层，所以 dup 出的另一个 fd 一起变；FD_CLOEXEC 在上一层，不继承。f_op 是多态核心：ext4、socket、pipe、eventfd 各给一张函数表。

3.4 struct inode —— 第三层

i_nlink 对目录项，i_count 对内存引用。i_size 是逻辑长度（ls -l），i_blocks 是实际占用的 512 字节块数（du）——truncate -s 10G x 前者 10 GB、后者 0，这就是稀疏文件的判据，拷贝时不加 cp --sparse=always 会写满目标盘。

3.5 fd 表的扩容：为什么前 64 个 fd 特别便宜

路径做了什么加锁量级
fdget() / fget()范围 + 位图 + 取指针 + f_count++无锁（RCU 读侧）。单线程持有时连原子加都省几纳秒，L1 命中
get_unused_fd_flags()从 next_fd 扫位图、置位file_lock 自旋锁几十纳秒；极多时靠 full_fds_bits 保持 O(log n)
扩容（跨 64/256/1024）alloc_fdtable → 拷指针与三张位图 → rcu_assign_pointer 发布 → call_rcu 回收旧表持 file_lock；分配可能睡眠百万 fd 一次拷贝约 8 MB 指针数组，可达毫秒
fork 的 dup_fd()为子进程分配新表 + 逐项 get_file()持父进程 file_lock与 fd 数成正比

读路径无锁，所以扩容不能立刻 kfree 旧表——别的 CPU 可能正从旧 fd[] 取值，必须 call_rcu 延迟释放。这就是「前 64 个 fd 特别便宜」的另一半：读路径几乎只是一次数组取值。

✗ 连接数越多，起子进程越慢

某网关持有约 12 万长连接，每分钟 system() 采一次指标，p999 规律蹦到 200 ms+。热点在 dup_fd：复制 12 万指针并逐个原子递增，期间所有 open/accept/close 排队等 file_lock。改用 posix_spawn()。持有大量 fd 的进程不应该 fork。

dup/dup2/dup3 语义

4.1 三个 API 的差异 · 4.2 dup 的三级表变化 · 4.3 dup2 实现 Shell 重定向 · 4.4 编排顺序的坑

4.1 三个 API 的差异

API行为典型用法
dup(oldfd)返回最小空闲 fd，指向同一 struct file简单复制
dup2(oldfd, newfd)newfd 若已打开先 close，然后 newfd → oldfd 的 fileShell 重定向
dup3(oldfd, newfd, flags)同 dup2，支持 O_CLOEXEC；oldfd==newfd 时报错原子设置 CLOEXEC
fcntl(oldfd, F_DUPFD, base)返回 ≥ base 的最小空闲 fd挪到高号段，避开 0/1/2
fcntl(oldfd, F_DUPFD_CLOEXEC, base)同上，且新 fd 带 FD_CLOEXEC库代码里复制 fd 的正确写法
⚠ 三条容易记反的规则
  • dup2 是原子的，「先 close 再 dup」不是。内核持 file_lock 完成「关掉 new 上的旧 file + 装上 old 的 file」。手写两步会被抢走 new 号。
  • dup2(fd, fd) 空操作返回 fd；dup3(fd, fd, …) 返回 -EINVAL。dup3 的唯一用途是设标志，「什么都不做却要设标志」自相矛盾。
  • 新 fd 不继承 FD_CLOEXEC（① 层表项属性）。O_APPEND / O_NONBLOCK 在 ② 层，所以共享。「哪个标志在哪一层」是整章判据。

库代码复制 fd 用 fcntl(old, F_DUPFD_CLOEXEC, 0)，别 dup 再补 fcntl——后者有和 §6.4 同构的竞态窗口。要把 fd 挪出 0/1/2，用 F_DUPFD 指定下限。

4.2 dup 的三级表变化

4.3 dup2 实现 Shell 重定向

// 实现 `ls > output.txt`
int fd = open("output.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
dup2(fd, STDOUT_FILENO);  // fd=1 现在指向文件
close(fd);                // 原始 3 可关，stdout 仍持有引用
execvp("ls", argv);

第三步 close(3) 只把 f_count 从 2 减到 1，stdout 仍握着那份打开状态，所以 exec 后 ls 的输出进文件。漏掉它则多占一个同指向的 fd，没打 CLOEXEC 时会泄漏给下一层 exec。

4.4 编排顺序：一个几乎人人写错过的循环

同时搬好几个 fd 时（实现 shell、写 spawn 库、做进程沙箱），目标号可能恰好就是另一个源号。单独看 dup2 很简单，循环一写就翻车。

▶ 不要自己写这段编排

正确版本还要处理 exec 失败如何回报（O_CLOEXEC pipe 传 errno）、信号掩码重置、vfork 下哪些函数不能调。优先 posix_spawn()；自己写只有一个理由：需要 setns 这类它表达不了的动作。

5.1 fork 如何复制 FD Table

5.2 关键规则

  • fork() 复制 FD Table（子进程独立的 files_struct）
  • 每个指针指向的 struct file 不复制，只 f_count++ → 共享 pos
  • 子进程 close 只减自己的表项；归零才真正释放

5.3 验证实验

pos 推进是原子的，但大块 write 可能被拆分（管道 PIPE_BUF=4096 以内原子，普通文件取决于文件系统）。生产用 O_APPEND。

✗ 竞争条件：并发 write 到共享 fd

5.4 三种「共享程度」：fork / 线程 / vfork

5.5 经典事故：父子写同一个日志文件

两种写法只差一个 O_APPEND。因为共享 f_pos 且单次 write 受 f_pos_lock 保护，测试一万次都对——它在下面三种生产里立刻崩：

  • 有任何一方是独立 open 的（日志滚动后 worker 重开、旁路脚本也在写）→ 两个 struct file 各有 f_pos，互相覆盖，出现半行和一大段 \0。
  • 有人调了 lseek（含 fseek，或手写「先 SEEK_END 再 write」）→ 共享偏移被拽回去，覆盖已有内容。
  • 文件被 truncate（logrotate 的 copytruncate）→ f_pos 不回 0，下次写落在原偏移，凭空一个几十 GB 的稀疏文件（ls -l 40 GB，du 200 KB）。

O_APPEND 让这三种全部消失：每次 write 内部原子地「取当前 i_size + 写入」，不看 f_pos 历史值。边界（NFS、不能替代文件锁）在 §8.5。

5.6 另一半事故：用户态缓冲被复制

内核层之外：fork 会把用户态 stdio 缓冲一起复制走。

printf("start\n");  // 管道/文件是全缓冲，这 6 字节还在用户态
fork();             // 缓冲区连同那 6 字节被复制
// 父子退出各自 flush → 文件里两遍 "start"
// tty 是行缓冲，遇 \n 已刷出，所以「直接跑没事，加个 > log 就重复」
fflush(NULL);       // 修法：fork 前刷所有流
fork();

更稳的做法是多进程干脆不用 stdio 写日志，直接 write() 到 O_APPEND 的 fd。代价是每条一次系统调用，要省就在应用层自己攒批。三层缓冲见 io_linux_kernel_guide.html §4。

exec 与 FD_CLOEXEC

6.1 exec 默认行为：fd 保留 · 6.2 FD_CLOEXEC 标志 · 6.3 close_on_exec 位图在内核的位置 · 6.4 一步到位的接口 · 6.5 泄漏的两种真实后果 · 6.6 兜底与验收

6.1 exec 默认行为：fd 保留

与直觉相反，execve() 默认不关 fd——这是 Shell 重定向能工作的前提。当年单线程、fd 个位数、没有安全边界，「全部继承」是合理取舍；今天三个前提都不成立，正确默认值应该反过来，但它自己改不了：改一个字节全世界的 shell 停摆。

6.2 FD_CLOEXEC 标志

密钥、日志不该被子进程继承。标志在第 ① 层：dup 出的新 fd 不带，fork 复制整张位图后各自独立。只要还有一个没设 CLOEXEC 的 fd 指向同一个 struct file，它就会跟着 exec 走——所以要用 accept4(…, SOCK_CLOEXEC)。

6.3 close_on_exec 位图在内核的位置

每个 fdtable 一张位图，execve 末段 do_close_on_exec() 按位关闭——这就是「CLOEXEC 是表项属性而非 file 属性」的内核位置。

Shell Pipe 原理

7.1 创建匿名管道 · 7.2 fork + dup2 编排 · 7.3 最小实现 · 7.4 EOF、SIGPIPE 与背压都是引用计数

ls | grep foo 是 fd 操作的教科书：内核为管道分配读、写两个 struct file（缓冲默认 64 KB），pfd[0] 读、pfd[1] 写。

7.1 创建匿名管道

pipe(pfd) 之后父进程同时握着两端。EOF 的条件不是「子进程退出」，而是写端那一侧的引用归零，所以父进程自己也必须关写端。内核给管道分配的是读、写两个 struct file——和 dup 的「一个 file、两个 fd」正好相反。

7.2 fork + dup2 编排

写端全关、读端在读：read 返回 0。读端已关、写端还在写：内核发 SIGPIPE，忽略该信号则 write 返回 EPIPE。管道满时 write 阻塞（或 EAGAIN），这就是背压。

7.3 最小实现

// 实现: ls | grep foo
int pfd[2];
pipe(pfd);
if (fork() == 0) {              // ls
    close(pfd[0]);
    dup2(pfd[1], STDOUT_FILENO);
    close(pfd[1]);
    execlp("ls", "ls", NULL);
}
if (fork() == 0) {              // grep
    close(pfd[1]);
    dup2(pfd[0], STDIN_FILENO);
    close(pfd[0]);
    execlp("grep", "grep", "foo", NULL);
}
close(pfd[0]); close(pfd[1]);   // 父必须关，否则 EOF 永远不到
wait(nullptr); wait(nullptr);
▶ 为什么必须关闭不用的管道端？

更精确地说：管道 inode 上写端引用计数归零时，内核才唤醒读端并让 read 返回 0。任一进程忘了关写端，grep 就永远阻塞——shell/IPC 编程最经典的 bug。

7.4 管道把「fd 引用计数」变成了可观察的行为

现象引用计数视角
子进程都退出了，父进程 read 还挂着父自己也持有一份写端。进程退出关不掉别人的
yes | head -1 能正常结束head 退出 → 读端归零 → 上游 SIGPIPE（默认终止）。这是特性
忽略 SIGPIPE 后 write 返回 EPIPE同一条件的另一种通知。服务端一般 SIG_IGN 再按 EPIPE 处理
写一个没人读的管道会阻塞而不是报错读端 count > 0（哪怕对方没在 read），填满 64 KB 后阻塞 = 天然背压

缓冲可用 F_SETPIPE_SZ 调（上限 fs.pipe-max-size）。这是个常被误用的旋钮：它只能吸收更长的突发，提不了稳态吞吐。真正该调大的场景是下游有周期性长停顿，让缓冲刚好盖住那个窗口。管道家族其余部分见 ipc_guide.html §5。

▶ 工程启示：日志文件 append

多进程写同一日志不要自己 lseek + write（非原子，会互相覆盖），用 O_APPEND：内核保证每个 write 原子地定位到末尾再写。

8.4 shell 里的 > 与 >>：在内核层面差一个标志

shell 写法实际 open每次 write多进程同时写

cmd >> fO_WRONLY|O_CREAT|O_APPEND原子取当前 i_size安全不看 f_pos 历史值

✗ 只差两个字符，结果天差地别

输出量小时看不出来：stderr 20 字节盖掉 stdout 开头 20 字节，文件长度还是 200，只是开头「有点怪」。另外 2>&1 必须写在 > f 之后——顺序反了 stderr 仍留在终端。

8.5 O_APPEND 的原子性到底保证了什么

✓它保证的
  • 「定位 + 写」是一步：持 i_rwsem 取当时 i_size。
  • 无论多少进程、共享还是各自 open，数据都落在真正末尾。文件长度 = 所有写入之和。
  • 本地 fs（ext4/XFS/btrfs）上，单次 write() 不会被别人劈开。
  • lseek 被忽略。
✗它不保证的
  • 不保证跨 NFS。协议没有「追加」，客户端靠「先查大小再写偏移」模拟，两步无保护。共享日志放 NFS 上会互相覆盖。
  • 不能替代文件锁。管不了读—改—写。计数器 / JSON 必须 flock 或 F_SETLK。
  • 不保证多次 write 的连续性。一条日志必须一次 write 写完。
  • 超大单次写可能被拆（信号中断、部分写入）。单条控制在几 KB 内。
⚠ 多进程写同一个日志到底能不能用 O_APPEND

能，这就是标准答案——三条同时满足：本地文件系统、每条一次 write（不经 stdio 多次刷新）、单条几 KB 内。不适用的场景：读—改—写（用锁）、跨 NFS、单条很大、需要严格全局顺序。

还要分清：O_APPEND 的原子性是内存里的，与「掉电后还在不在」正交。写入先进页缓存，掉电会丢最后几秒。真的不能丢就 fsync，代价是吞吐掉到几百条每秒。

fd 传递 (SCM_RIGHTS)

10.1 传的是引用不是数字 · 10.2 可编译的收发端 · 10.3 cmsghdr 的四个坑 · 10.4 真实用途

10.1 传的是「对 struct file 的新引用」，不是那个整数

fd 号是每进程命名空间，把 3 这个整数发过去毫无意义。真正发生的是：

  1. 发送端 sendmsg 时内核在发送进程的 ① 层查出 struct file* 并立刻 get_file()——引用在这一刻建立，之后发送方 close 甚至退出，那个打开状态仍「在管道里飞着」。
  2. 接收端 recvmsg 时在接收进程表里分配一个可能完全不同的号，装上同一个 struct file*。

效果是跨进程的 dup：号可以不同，但共享 f_pos 与 f_flags，所以下面的示例用 pread。只在同一台机器、同一内核实例内有效。

10.2 完整可编译的收发端

cmsghdr 变长且有对齐要求，「缓冲区大小」和「数据长度」是两个不同的宏。下面用 socketpair + fork 自己跟自己传，易错点都标了号。

// passfd.c —— cc passfd.c -o passfd && ./passfd
#define _GNU_SOURCE
#include <sys/socket.h>
#include <sys/wait.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>
#include <stdio.h>
#include <errno.h>

/* ── 发送 n 个 fd ─────────────────────────────────────────── */
static int send_fds(int uds, const int* fds, int n) {
    /* ① 控制缓冲用 CMSG_SPACE（含头部与对齐填充），不是 CMSG_LEN */
    union {                          /* union 保证 cmsghdr 的对齐要求 */
        char buf[CMSG_SPACE(sizeof(int) * 8)];
        struct cmsghdr align;
    } u;
    memset(&u, 0, sizeof u);

    /* ② 必须捎带至少 1 字节普通数据：某些实现会丢掉纯控制消息 */
    char dummy = 'F';
    struct iovec iov = { .iov_base = &dummy, .iov_len = 1 };

    struct msghdr msg = {
        .msg_iov        = &iov,
        .msg_iovlen     = 1,
        .msg_control    = u.buf,
        .msg_controllen = CMSG_SPACE(sizeof(int) * n),   /* 只声明实际用到的 */
    };

    struct cmsghdr* cm = CMSG_FIRSTHDR(&msg);
    cm->cmsg_level = SOL_SOCKET;
    cm->cmsg_type  = SCM_RIGHTS;
    cm->cmsg_len   = CMSG_LEN(sizeof(int) * n);           /* ③ 这里是 CMSG_LEN */
    memcpy(CMSG_DATA(cm), fds, sizeof(int) * n);          /* ④ 用 memcpy，别强转指针 */

    ssize_t r;
    do { r = sendmsg(uds, &msg, 0); } while (r < 0 && errno == EINTR);
    return r < 0 ? -1 : 0;
}

/* ── 接收最多 max 个 fd，返回实际收到的个数 ───────────────── */
static int recv_fds(int uds, int* out, int max) {
    union {
        char buf[CMSG_SPACE(sizeof(int) * 8)];
        struct cmsghdr align;
    } u;
    char dummy;
    struct iovec iov = { .iov_base = &dummy, .iov_len = 1 };
    struct msghdr msg = {
        .msg_iov        = &iov,
        .msg_iovlen     = 1,
        .msg_control    = u.buf,
        .msg_controllen = sizeof u.buf,      /* 收侧给足，宁大勿小 */
    };

    ssize_t r;
    /* MSG_CMSG_CLOEXEC：收到的 fd 直接带上 CLOEXEC，避免竞态窗口 */
    do { r = recvmsg(uds, &msg, MSG_CMSG_CLOEXEC); }
    while (r < 0 && errno == EINTR);
    if (r <= 0) return -1;                 /* 0 = 对端关闭 */

    /* ⑤ 必查！控制缓冲不够时内核会【静默关闭】放不下的 fd */
    if (msg.msg_flags & MSG_CTRUNC) {
        fprintf(stderr, "MSG_CTRUNC: fd 被内核丢弃了\n");
        return -1;
    }

    /* ⑥ 必须遍历所有 cmsg 并核对 level/type，不能假定第一个就是 SCM_RIGHTS */
    for (struct cmsghdr* cm = CMSG_FIRSTHDR(&msg); cm; cm = CMSG_NXTHDR(&msg, cm)) {
        if (cm->cmsg_level != SOL_SOCKET || cm->cmsg_type != SCM_RIGHTS)
            continue;                     /* 可能是 SCM_CREDENTIALS 等 */
        /* ⑦ 个数是【算】出来的，不是约定的——对端可能只传了 1 个 */
        int n = (cm->cmsg_len - CMSG_LEN(0)) / sizeof(int);
        if (n > max) n = max;
        memcpy(out, CMSG_DATA(cm), sizeof(int) * n);
        return n;
    }
    return 0;                             /* 只有普通数据，没带 fd */
}

int main(void) {
    int sv[2];
    /* 必须是 AF_UNIX；SOCK_STREAM 或 SOCK_DGRAM 都可以传 fd */
    socketpair(AF_UNIX, SOCK_STREAM | SOCK_CLOEXEC, 0, sv);

    if (fork() == 0) {                  /* ── 子进程：接收方 ── */
        close(sv[0]);
        int got[8];
        int n = recv_fds(sv[1], got, 8);
        printf("[child] 收到 %d 个 fd，第一个是 %d\n", n, got[0]);

        char b[64] = {0};
        pread(got[0], b, sizeof b - 1, 0);   /* 用 pread 避免动共享的 f_pos */
        printf("[child] 读到内容: %s", b);
        _exit(0);
    }

    close(sv[1]);                       /* ── 父进程：发送方 ── */
    int fd = open("/etc/hostname", O_RDONLY | O_CLOEXEC);
    printf("[parent] 发送 fd %d\n", fd);
    send_fds(sv[0], &fd, 1);
    close(fd);                          /* 发完就能关：引用已经在内核里了 */
    wait(NULL);
    return 0;
}

父进程打印发送的 fd 号，子进程打印收到的号（相同与否纯属巧合）并能 pread 到内容；父进程 close(fd) 之后子进程照样读得到——引用在 sendmsg 那一刻就已经建立。

读这段代码盯四个宏：发送侧 msg_controllen 用 CMSG_SPACE（含对齐填充）、cmsg_len 用 CMSG_LEN；接收侧必查 MSG_CTRUNC，并用 CMSG_NXTHDR 遍历。

10.3 cmsghdr 的四个坑，全都不会给你明确报错

写法错在哪症状
msg_controllen = CMSG_LEN(sizeof(int))缓冲长度必须用 CMSG_SPACE（含尾部对齐），CMSG_LEN 只用于 cmsg_len64 位下两者碰巧都是 20 → 缓冲不足。接收端 MSG_CTRUNC
*(int*)CMSG_DATA(cm) = fd地址不保证按 int 对齐x86 没事，ARM / RISC-V 上 SIGBUS。一律 memcpy

✗ 接收方的 RLIMIT_NOFILE 是攻击面

新 fd 占接收进程配额；超限时内核装不下就直接 close 并置 MSG_CTRUNC，而不是让 recvmsg 失败重试。高频传 fd 必须调足限额并做流控。

10.4 真实用途：它解决的是「资源移交」这一类问题

1 特权分离

高权限小进程负责 open，低权限大进程负责处理——权限检查只在 open 时发生（§6.5 那条规律反过来当特性用）。Chrome 渲染进程、OpenSSH privsep 都是这个形状。

2 热升级：移交监听 socket

新进程不能自己 bind 同一端口（EADDRINUSE；SO_REUSEPORT 也救不了 accept 队列里已有的连接）。必须接过那个 struct file。nginx USR2、systemd socket activation、Envoy hot restart。

3 容器 runtime 与设备代理

runtime 在容器外打开 tty/GPU，把 fd 传进去。docker exec -it 的终端就是这样。Wayland 把帧放进 memfd 再传 fd；pidfd_getfd() 是反向「取」。

▶ 什么时候不该用它

三种误用：跨机器不可能；当成通用 IPC——对方有权限时告诉它路径更简单；跨命名空间要想清楚——fd 能穿过 PID/网络 NS，但 socket 仍活在发送方那个网络 NS 里。

▶ 限额怎么定

不要「反正调大点」。每个 fd 的真实成本差两个数量级：

  • struct file 本身：二三百字节，100 万 fd ≈ 200–300 MB，不可压缩。
  • fdtable 指针数组：8 字节 × 最大 fd 号（不是实际使用数），100 万 ≈ 8 MB，外加每 fd 3 bit 的三张位图。
  • TCP socket：大头。每条连接 struct socket + tcp_sock 约 1–2 KB，再加收发缓冲。100 万空闲约几 GB，100 万活跃能吃掉几十 GB。
  • 普通文件：本身便宜，但挂着的页缓存不便宜（可回收，不计入 RSS）。

顺序是：先估峰值连接 × 每连接内存，再把限额定在峰值的 2–3 倍。设成 infinity 的坏处是泄漏时没有刹车，故障从「报 EMFILE，可定位」变成「机器 OOM，全盘皆输」。

▶ 「每连接内存」这一项怎么估

本章列的是 fd 这一侧的成本。一条真实的长连接还要加上用户态读写缓冲、TLS 上下文、会话对象与定时器，几项加起来才决定单机能放多少连接。一份逐项列到字节、并反推出机器上限的预算表见 IoT 接入网关架构设计 · 每连接预算（那里把 124 KB/连接压到 10 KB 的过程也在同一章）。判据：报 EMFILE 说明限额没调够，看本章；限额够了却先 OOM，说明预算算错了，看那一篇。

✗ 每天凌晨 4 点 EMFILE，重启就好

订单同步服务每天 4:30 报 Too many open files，重启即恢复，运维加了「每天 4 点定时重启」跑了两个月。按顺序走：凌晨 2 点陡增；全是 socket:[]；97% CLOSE_WAIT；远端全指向内部对账接口。

根因：对账任务每批次新建一个 HTTP 客户端（各带连接池），只关了「本次请求」没关客户端。服务端断连发来 FIN，本地永久停在 CLOSE_WAIT——对象已无人引用，但 GC 不会替你关 socket。

  • fd_used / fd_limit 比例（不是绝对值），阈值 70%。
  • fd 数的一阶差分：每小时净增量持续为正就告警。
  • CLOSE_WAIT 连接数：正常接近 0。它是最常见那类泄漏的前置指标。

高频面试题

14.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础什么是文件描述符？它在内核中对应什么数据结构？

    fd 是进程级的非负小整数，本质是 files_struct::fdtable::fd[] 这个指针数组的下标。往下是三级表：

    • ① FD Table（进程私有，files_struct）：fd → struct file*，外加一张 close_on_exec 位图。
    • ② Open File Table（系统级，struct file）：保存 f_pos、f_flags、f_op 与引用计数 f_count。
    • ③ Inode（struct inode + dentry）：文件大小、权限、数据块位置与路径缓存。

    为什么是索引而不是内核指针：用户态永远拿不到内核地址，从根上堵住伪造；每次系统调用都要经 fget() 查表，天然获得合法性校验 + 引用计数的机会。

    由此直接推出：多个 fd 可指向同一个 struct file（dup/fork），共享偏移与打开标志；f_count 归零内核才真正关闭底层对象。号按「最小可用」分配、close 后立刻可复用——提前 close 一个别人还在用的 fd，后续 open 会抢到同号，读写静默打到别的对象上。

    排查入口：ls -l /proc/<pid>/fd、cat /proc/<pid>/fdinfo/<n>、lsof -p <pid>。

  2. 基础两次 open 同一个文件，和 dup 同一个 fd，有什么区别？

    差别就在三级表的第二层：

    • 两次 open：两个独立的 struct file，各有 f_pos 与 f_flags，只有第三层 inode 相同。一个 fd 读写不会移动另一个的位置。
    • dup(fd)：只在 FD Table 里加一个指针指向同一个 struct file，f_count++，两个 fd 共享 pos 与 flags，一个写入会推进共同的偏移量。

    共享 flags 常被漏掉：O_APPEND、O_NONBLOCK 都在 struct file 上，所以 fcntl(dup_fd, F_SETFL, O_NONBLOCK) 会连原 fd 一起改——很多「我明明只改了这个 fd」的源头。

    工程含义：2>&1 用 dup2 让两路共享偏移，才能顺序交错而不互相覆盖；要并行读同一文件的不同区域必须各自 open 或用 pread。

    dup2(old, new) 是原子的，「先 close 再 dup」有窗口期。dup 出的 fd 不继承 FD_CLOEXEC（① 层属性）。fork 复制 ① 层、共享 ② 层，所以「共享偏移」对 dup/fork/SCM_RIGHTS 都成立，只有「两次 open」不成立。

  3. 基础一个进程最多能打开多少个 fd？

    四层限制依次生效，任何一层都能先把你卡住：

    • 进程级软限制（RLIMIT_NOFILE）：ulimit -n，历史默认 1024，进程可以自己 setrlimit 提到硬限制。
    • 进程级硬限制：只有特权进程能抬高，常见 4096 或 1048576。
    • 系统级：fs.file-max（全系统 struct file 总数）与 fs.nr_open（单进程硬限制的天花板）。
    • 物理限制：每个 struct file 约 200–300 字节，加上指针数组与协议对象，100 万 fd 光内核内存就是几百 MB 起。

    两个容易踩的点：LimitNOFILE=infinity 会被截到 fs.nr_open，想过百万得两处一起调；软限制留在 1024 是为了保护用 select 的老程序。EMFILE 是本进程超了、ENFILE 是全系统超了，方向完全不同；/proc/PID/fd 数表项而 file-nr 数 struct file，前者涨后者不涨说明泄漏在句柄管理。

  4. 基础close(fd) 之后内核做了什么？为什么 rm 掉一个文件，磁盘空间可能没有释放？

    close 先在本进程 fd 表里清槽位与位图，再 fput() 减 f_count。只有减到 0 才调 f_op->release()（socket 这时才发 FIN、管道才产生 EOF）并递减 i_count。所以 close 一个被 dup 或 fork 继承过的 fd，实质性的事都不会发生。

    「rm 了但空间没释放」是这条规律的直接推论：unlink() 只减 i_nlink（磁盘目录项数），而 i_count（内存引用数）还大于 0，两者同时为 0 才 evict_inode()。诊断命令 lsof +L1，看 NLINK 列是不是 0。

    反过来被正面利用：open 之后立刻 unlink，得到「进程怎么死都会自动清理」的临时文件（O_TMPFILE 是原子版）；写临时文件 → fsync → rename，保证正在读旧文件的进程读到完整旧内容。

    两个容易漏的点：close 成功不代表已落盘；close 可能返回 EIO，但此时 fd 号已释放，绝不能重试——会关掉别的线程刚拿到的同号 fd。

14.2 中级（区分熟练度）

  1. 中级fork() 之后父子进程的 fd 是什么关系？

    fork 复制了 files_struct（第一层），但里面每个指针指向的 struct file（第二层）不复制，只做 f_count++。于是：

    • 父子的 FD Table 各自独立——子进程 close 或 dup2 不影响父进程。
    • 指向的 struct file 是共享的——共享 f_pos 与 f_flags。
    • 父子写同一个 fd 时偏移量累加不会互相覆盖，这正是 (cmd1; cmd2) > f 能顺序追加、以及管道能工作的原理。
    • 只有所有引用归零，内核才真正释放打开状态。

    和线程对照更清楚：clone(CLONE_FILES) 连第一层都共享，一个线程 close 立刻影响另一个。三种共享程度对应三类不同的 bug。

    缓冲重复
    fork 前没 fflush，用户态 stdio 缓冲被完整复制，父子各刷一次 → 同一段日志出现两遍。多进程模型里一律在 fork 前 flush，或干脆不用 stdio。
    管道端未关
    只要还有任何进程持有管道写端，读端就永远等不到 EOF。「子进程都退出了，父进程的 read 还在挂着」几乎总是因为父进程自己也留了一份写端。
    追加不原子
    共享 offset 只保证「不覆盖」，不保证「一条完整」。多进程写同一个日志必须用 O_APPEND，且单条控制在块边界内。

    性能：fd 多时 fork 变慢（要复制整张指针数组和位图）。高频起子进程用 posix_spawn，比 fork 后循环 close 几十万个划算得多。

  2. 中级为什么 socket、pipe、eventfd 都是 fd？这样设计有什么好处？

    Linux 把几乎所有可读写的内核对象收敛到 fd 这一个句柄类型，统一用 read/write/close/poll 操作。实现靠 struct file::f_op——本质是用 C 手写的虚函数表。

    好处：

    • 单一事件环：网络、timerfd、signalfd、pidfd、inotify、eventfd 全能注册进同一个 epoll。
    • 组合与传递：fd 可以 dup、可以经 SCM_RIGHTS 送给别的进程、可以被 splice 直接对接，这些能力对所有资源类型一致。
    • 生命周期统一：一套 close 语义，RAII 封一个句柄类就管住全部资源。
    • 可观测：/proc/<pid>/fd 与 fdinfo 让 SRE 用同一套工具排查网络、文件与 epoll 注册关系。

    边界才是加分项：「字节流」语义套到某些对象上很别扭——eventfd 必须读写恰好 8 字节，signalfd 读出固定结构体。也不是所有内核对象都赶上这班车：System V IPC 至今不是 fd，进不了 epoll。

  3. 中级C10K 问题为什么不能用一个进程 1024 个 fd 的 select 解决？

    三层障碍，层层递进：

    • fd 上限是 ABI 级的：FD_SETSIZE = 1024，大小写进了结构体布局，重新 #define 再编译并不安全——libc 内部按标准大小处理。
    • 每次调用的固定成本：每轮都要把整个 fd_set 拷进内核、O(n) 遍历全部 fd、再把结果拷回来；返回值只说「有几个就绪」，用户态还得自己扫一遍找是谁。
    • 通知方向不同：select/poll 是「内核被动挨个扫」，epoll 是「数据到达时协议栈回调把 fd 挂进就绪链表」，代价只和活跃连接数相关。

    thread-per-connection 同样不行——不是因为内存（栈是虚拟地址），而是调度与缓存：1 万个可运行线程让上下文切换和 cache 抖动成为主成本。

    标准答案：epoll + 非阻塞 I/O + 多 Reactor 绑核 + SO_REUSEPORT。再往上（C1M）瓶颈会从「如何等待」转移到内核每连接内存与定时器管理。

  4. 中级多进程写同一个日志文件，为什么 O_APPEND 可以而「lseek 到末尾再 write」不行？O_APPEND 的边界在哪？

    lseek(SEEK_END) + write() 是两次系统调用，中间有任意长的窗口：A 定位到 1000 还没写，B 抢先写了 50 字节，A 再从 1000 写下去就盖掉 B 的内容。

    O_APPEND 把两步合成一步：内核在 write 内部持 i_rwsem，取当时真正的 i_size 再写，不看 f_pos 的历史值，所以谁 lseek 过、有几个 struct file、文件被不被 truncate，都影响不到它。

    反直觉的是：fork 出来的父子共享同一个 f_pos，所以不加 O_APPEND 单次 write 也不会互相覆盖。「测起来是对的」正是这个坑最危险的地方——三种崩法见正文 §5.5。

    跨 NFS 失效
    NFS 协议里没有「追加」，客户端靠「先查大小再写偏移」模拟，两步毫无保护。共享日志放 NFS 上是反复被踩的坑。
    不能替代文件锁
    只保证单次 write 的原子性，管不了读—改—写。维护计数器、改 JSON，必须 flock 或 fcntl(F_SETLK)。
    一条日志必须一次 write
    两次 write 或 stdio 多次刷新之间，随时会插进别人的一整行。
    超大写可能被拆
    写入量很大或遇到信号中断时会返回部分写入。把单条控制在几 KB 内。

    结论：本地文件系统 + 每条一次 write + 单条几 KB 内，三条同时满足时多进程共写一个日志是标准做法。原子性只在内存中，掉电是否还在要看 fsync。

14.3 高级（体现深度）

  1. 高级为什么需要 FD_CLOEXEC？什么场景下必须用它？

    execve 默认保留所有 fd——shell 重定向正靠它工作。但在多线程、库化、容器化的今天这是个不安全的默认值：密钥、监听 socket、审计 fd 都不该被随手 exec 出来的子进程看到。

    后果很具体：子进程能通过 /proc/self/fd/N 读到本应隔离的内容（哪怕它对路径没权限）；泄漏的若是 listen fd，它甚至能 accept 抢走真实流量。

    必须用 O_CLOEXEC（打开时原子设置）而不是事后 fcntl：

    • 多线程程序：open 与 fcntl 之间有窗口。这个竞态无法用锁解决——fork 可能发生在任何第三方库里。
    • 库代码：库无从知道调用者是否多线程，所以打开的 fd 一律加 CLOEXEC。glibc、Go、Rust 标准库都已这样做。
    • 安全敏感 fd：凭证、私钥、token，以及任何指向宿主机资源的 fd（容器逃逸常见跳板）。

    不继承的坑：dup/dup2 的新 fd 不带 CLOEXEC，要用 F_DUPFD_CLOEXEC 或 dup3；accept 出来的连接也不继承，要用 accept4(…, SOCK_CLOEXEC)。

    兜底与验收：exec 前 close_range(3, ~0U, CLOSE_RANGE_CLOEXEC)（5.9+）一次性打标记；上线前在子进程里 ls -l /proc/self/fd，只应剩 0/1/2。

  2. 高级你怎么实现 Shell 的 "ls | grep foo | wc -l"？

    骨架是两次 pipe + 三次 fork + 正确的 dup2 编排：

    int p1[2], p2[2];
pipe(p1); pipe(p2);
if (fork() == 0) { dup2(p1[1], 1); /* close 全部原始端 */ execlp("ls", "ls", NULL); }
if (fork() == 0) { dup2(p1[0], 0); dup2(p2[1], 1); /* close 全部 */ execlp("grep", "grep", "foo", NULL); }
if (fork() == 0) { dup2(p2[0], 0); /* close 全部 */ execlp("wc", "wc", "-l", NULL); }
close(p1[0]); close(p1[1]); close(p2[0]); close(p2[1]);
while (wait(NULL) > 0) {}

    最核心的一点：每个进程（包括父进程）都必须关掉自己不用的所有管道端。EOF 的条件是「该管道所有写端引用归零」。症状是「命令跑完却不返回」，很难第一时间想到引用计数。

    • dup2 的顺序：p1[0] 恰好等于 0 或 1 时，先 close 再 dup2 会把源关掉。一律「先 dup2 完所有目标，再统一 close 原始 fd」，dup2(x, x) 是安全的空操作。
    • SIGPIPE：head 提前退出后上游继续写会被默认终止——这正是 yes | head -1 能结束的机制。要自己处理就 SIG_IGN 后看 EPIPE。
    • 进程组：三个子进程要 setpgid 进同一进程组，父 shell 用 tcsetpgrp 把终端交给它，否则 Ctrl-C 打不到整条流水线。
    • 退出码：管道取最后一个命令的退出码，中间失败会被吞掉——这就是脚本里要写 set -o pipefail 的原因。

    管道缓冲默认 64 KB（F_SETPIPE_SZ 可调），写满即阻塞，这就是天然的背压。

  3. 高级如何实现进程间传递一个已打开的 socket fd？

    用 Unix Domain Socket 的 SCM_RIGHTS 辅助消息。传的不是那个整数，而是它背后的 struct file 引用：内核在接收端新分配一个号指向同一个 struct file。所以两端此后共享 offset 与 flags，就是跨进程版的 dup。完整示例见正文 passfd.c。

    必须带普通数据
    iovlen = 0 的纯控制消息，某些实现会整个丢掉。惯例是捎带至少 1 字节。
    控制缓冲要给够
    msg_controllen 不足时内核置 MSG_CTRUNC 并直接关闭放不下的 fd——数据静默消失，而 recvmsg 返回值看起来完全正常。
    计入接收方限额
    新 fd 占接收进程的 RLIMIT_NOFILE，超限即丢弃；且不自动带 CLOEXEC，要 MSG_CMSG_CLOEXEC。拷贝一律 memcpy，不要对 CMSG_DATA 强转指针。

    能力边界：只能在同一台机器、同一内核实例内工作，不是 RPC 的替代品。典型应用：systemd socket activation、Nginx 平滑升级、Chrome 沙箱。UDS 建连与对端凭证见 ipc_guide.html §7。

  4. 高级线上告警根分区 100%，但 du -sxh / 加起来只有一半。怎么定位，怎么处理？

    第一反应：df 数的是文件系统的账，du 数的是目录树上能走到的文件。对不上说明有空间被占用却不在目录树上。最常见的就是引用计数：文件已被 rm（i_nlink=0）但还有进程持有 fd，数据块一个没释放。

    定位只需要一条命令，+L1 的意思是「只列链接数 < 1 的文件」：

    $ sudo lsof +L1
COMMAND  PID USER  FD  SIZE/OFF NLINK    NODE NAME
nginx   1893 www    9w  38G         0 1049203 /var/log/nginx/access.log (deleted)
nginx   1894 www    9w  38G         0 1049203 /var/log/nginx/access.log (deleted)

    逐列判读：NLINK 为 0 即确诊；SIZE/OFF 是被扣住的空间；NODE 相同的行只占一份空间——按 PID 把 38 GB 乘以 worker 数是最常见的误判。

    首选
    通知进程自己重开日志（kill -USR1 / systemctl reload）。旧 fd 一关，i_count 归零，空间立刻回收，服务零中断。
    次选
    原地截断：sudo sh -c '> /proc/1893/fd/9'。必须用重定向，不能 rm。对 O_APPEND 安全；普通 O_WRONLY 会留下稀疏空洞，因为 f_pos 还停在 38 GB 处。
    末选
    重启进程。一定有效但有中断，而且掩盖了根因。

    能拉开差距的是说出「这不是唯一成因」：总量对不上时还有四种——挂载点被盖住、ext4 的 5% 保留块、稀疏文件、inode 耗尽。根治：清日志一律交给 logrotate，禁止手工 rm 活跃日志。
