Linux 时间与时钟

时间是那种「以为自己懂了」的东西，直到一次 NTP 校时把全站超时逻辑打穿。这一篇把时钟源、五种 POSIX 时钟、vDSO、step 与 slew、定时器精度和容器里的时间视图逐个拆开——重点是选错会怎样，而不是 API 怎么调。

核心难度 ★★★★☆ 系统底层 阅读时长 ~35 min 前置 系统调用 · 调度
01

时间为什么是个系统问题

它的失效方式有一个共同点：日志里什么都看不出来

1.1 三类真实事故

① 超时集体失效

某一刻起全站请求同时超时，几秒后自动恢复，日志里没有任何异常。原因是一次 NTP 校时把系统时间往前跳了，而超时是用 CLOCK_REALTIME 算的——所有在途请求的 deadline 瞬间「已过期」。

② 服务莫名变慢一个数量级

没有发版、没有流量变化，但 P99 涨了十倍。原因是内核把 clocksource 从 tsc 降级到了 hpet，而这个服务每秒调几百万次 clock_gettime——单次从 25 ns 变成 1 μs。

③ 定时任务在笔记本合盖后不执行

「每 5 分钟上报一次」的逻辑，在设备休眠 3 小时后醒来只补了一次，而不是 36 次。因为用的是 CLOCK_MONOTONIC——它在挂起期间是停住的。

这三类事故的共同点：没有任何组件报错。CPU 正常、内存正常、网络正常、应用日志正常。它们之所以难查，是因为「时间」是所有测量的基准，而基准出问题时，所有的测量都会一起骗你——包括你用来排查的那些监控图。

1.2 「现在几点」没有单一答案

应用调一次 clock_gettime，背后是一条从晶振到用户态的链路，每一层都可能被调整、降级或虚拟化：

这张图里最需要记住的是第 ③ 层不是一个时钟，是五个。它们共享同一个底层计数器，但语义完全不同——被调整时的行为、挂起时的行为、是否单调，全都不一样。选错哪一个，就是 §1.1 那三类事故。

02

时钟源：从硬件到内核

一个你从不配置、但会突然变化的东西

2.1 三种硬件计时器

源读取成本怎么读问题
tsc ~5–10 ns 一条 RDTSC 指令，不出 CPU 历史上不可靠（变频、多核不同步、休眠后重置），需要满足 §2.3 的三个条件
hpet ~500–1000 ns MMIO 读，要走一趟总线到南桥 慢 100 倍。它是 TSC 不可用时的回退，不是替代
acpi_pm ~700 ns 端口 I/O 更慢，且只有 24 位、约 5 秒回绕一次，最后的兜底
kvm-clock / hyperv 接近 TSC 宿主通过共享内存页告诉客户机换算参数 虚机专用，解决迁移后 TSC 频率变化的问题（§7.3）

当前用的是哪个、有哪些可选，看两个文件：

命令看什么
cat /sys/devices/system/clocksource/clocksource0/current_clocksource当前源。不是 tsc 就要查为什么
cat .../available_clocksource可选项
dmesg | grep -i 'clocksource'关键：内核降级时会打日志，写明为什么切换

2.2 clocksource 掉档是 40 倍的性能悬崖

一个每秒调用 200 万次 clock_gettime 的服务（每请求打几个时间戳，很常见）：
TSC + vDSO：200 万 × 25 ns = 0.05 秒 CPU/秒，5% 的一个核，可以忽略。
HPET：200 万 × 1000 ns = 2 秒 CPU/秒——需要 2 个核持续满载，而且这 2 个核什么业务都没干。

而且 HPET 是全局共享的单一硬件：所有核读它都要串行走总线，核越多争抢越严重。在 64 核机器上这不是「慢 40 倍」，可能是「整机被一个计时器锁死」。
内核会在检测到 TSC 不稳定时自动降级，并打一行 Clocksource tsc unstable。这行日志出现在 dmesg 里，不会触发任何告警，服务也不会报错——它只是突然慢了一个数量级。
如果你的监控里没有 current_clocksource 这一项，这类故障基本无法归因：所有指标都指向「CPU 高」，但没有任何代码变更能解释它。把当前 clocksource 作为一个 gauge 指标上报，成本几乎为零。

2.3 TSC 可用的三个前提

TSC 曾经因为三个问题被认为不可靠，现代 CPU 用三个特性分别解决了它们。看 /proc/cpuinfo 的 flags 就能确认：

历史问题解决它的特性没有它会怎样
CPU 变频时 TSC 频率跟着变constant_tsc时间随负载快慢变化
进入深度 C-state 后 TSC 停走nonstop_tsc空闲时钟变慢
多核之间 TSC 不同步tsc_reliable / 内核启动时的同步校验线程迁移到另一个核后时间倒流——这会让「测量耗时」得到负数
第三条是自己用 RDTSC 做计时的最大陷阱。就算 TSC 在核间同步得很好，RDTSC 也是一条可以被乱序执行的指令——CPU 可能把它提前或推后，导致测出来的区间不是你想测的那段。要么用 RDTSCP（自带序列化并返回核 ID），要么在前后加 lfence。

但更实际的建议是：不要自己读 TSC。clock_gettime(CLOCK_MONOTONIC) 走 vDSO 时本来就是一条 RDTSC 加几次乘除（§4），只贵十几纳秒，却帮你处理了核间同步、频率换算、以及热插拔 CPU 这些边界情况。自己读 TSC 的收益很小，而它引入的正确性问题很难查。
03

五种 POSIX 时钟，选错就是事故

这一章是全篇最该记住的部分

3.1 对照表

时钟NTP 调整时系统挂起时起点用它来做什么
CLOCK_REALTIME 会跳、会变速、可能倒退 继续走（醒来后被校正） 1970-01-01 UTC 只用于「需要和外界对齐的绝对时刻」：日志时间戳、数据库的创建时间、证书有效期
CLOCK_MONOTONIC 不跳，但会被 NTP 调速率（±500 ppm） 停住 不确定（通常是开机） 测量时间间隔、算超时、限流、重试退避——默认就该用它
CLOCK_BOOTTIME 同 MONOTONIC 继续走 开机 需要「真实流逝的时间」时：会话过期、缓存 TTL、心跳（§3.3）
CLOCK_MONOTONIC_RAW 完全不受 NTP 影响，连速率都不调 停住 同 MONOTONIC 测量硬件性能、校准。不要用它算超时——它会随晶振漂移，长时间下不准
CLOCK_*_COARSE 跟随对应的时钟 同上 同上 精度只有一个时钟节拍（1–4 ms），但便宜一个数量级（§4.3）
CLOCK_PROCESS_CPUTIME_ID — — 进程启动 只统计本进程实际占用的 CPU 时间。用于区分「慢是因为在算」还是「慢是因为在等」
一句话记法：REALTIME 回答「现在几点」，MONOTONIC 回答「过了多久」。绝大多数代码想问的是后者，却习惯性地用了前者，因为 time() / System.currentTimeMillis() / time.time() 这些「默认」的 API 全都是 REALTIME。

3.2 用 REALTIME 算超时会怎样

更糟的是时间往回跳的情况：如果 NTP 把时间调慢，用 REALTIME 算出来的「已耗时」会是负数。代码里 if (elapsed > timeout) 不会触发，于是这个请求永远不会超时——它会一直占着连接和线程，直到进程重启。这比「全部超时」更难发现，因为它只影响那一小批请求。

// ❌ 常见写法：用挂钟算间隔。一次 NTP 校时就会让它给出错误答案（甚至负数）。
auto start = std::chrono::system_clock::now();          // ← system_clock 就是 CLOCK_REALTIME
// ... 干活 ...
auto elapsed = std::chrono::system_clock::now() - start;
if (elapsed > 500ms) timeout();

// ✅ 测间隔一律用 steady_clock（= CLOCK_MONOTONIC）。它的名字就是在提示这一点：
// C++ 标准要求 steady_clock 单调且步长恒定，system_clock 两条都不保证。
auto start = std::chrono::steady_clock::now();
auto elapsed = std::chrono::steady_clock::now() - start;

// ✅ 传 deadline 时也要传单调时钟的绝对时刻，不要传「剩余毫秒数」：
// 后者在每一跳都要重算，网络传输和排队的时间会被漏掉（越往下游误差越大）。
struct Deadline { std::chrono::steady_clock::time_point at; };

// ⚠️ 但跨进程/跨机器传 steady_clock 的值是没有意义的 —— 它的起点各机器不同。
// 跨边界只能传「剩余时长」，接收方立刻换算成自己的 steady_clock 绝对时刻。
// 这一步会漏掉网络单程延迟，所以接收方还要减去一个保守的估计值。
最后那段注释是个容易忽略的边界：CLOCK_MONOTONIC 的值只在本机内有意义，它的零点是任意的（通常是开机时刻）。所以「传绝对时刻」这条建议只适用于进程内；跨进程要传时长，跨机器还得考虑单程延迟。

这也是为什么 gRPC 的 deadline 在协议上传的是 grpc-timeout: 1500m（剩余时长）而不是绝对时刻——它必须跨机器。而在同一个进程里传递时，绝对时刻才是对的。两种做法各有各的适用边界，混用会引入难查的误差。

3.3 MONOTONIC 与 BOOTTIME：挂起的那段

两者唯一的差别是系统挂起（suspend / 休眠）期间是否继续走。这个差别在服务器上很少遇到，在笔记本、手机、边缘设备上是常态：

用途该用理由
测量一段代码的耗时MONOTONIC挂起不是「代码在跑」，不该算进去
网络请求超时MONOTONIC挂起期间连接早就断了，醒来重连即可
会话 / 令牌过期BOOTTIME安全语义要的是「真实流逝了多久」。用 MONOTONIC 的话，挂起 3 小时的设备醒来后令牌还没过期
缓存 TTL、心跳判活BOOTTIME同上，否则休眠后会拿着几小时前的缓存当新鲜的用
定时任务「每 N 分钟一次」看语义「至少每 N 分钟」用 BOOTTIME（醒来立刻补一次）；「CPU 忙了 N 分钟」用 MONOTONIC
timerfd 和 epoll_wait 的超时都基于 MONOTONIC，这意味着它们不会把设备唤醒，也不会在挂起期间计时。想让定时器把系统从挂起中唤醒，需要 CLOCK_REALTIME_ALARM / CLOCK_BOOTTIME_ALARM（要 CAP_WAKE_ALARM 权限）。
这就是「手机上定的闹钟能响，但 App 里的定时器不能」的底层原因——前者用的是 alarm 时钟，后者用的是普通定时器。

3.4 三个问题定一个时钟

问题一

要和外界对齐吗？
要（日志、证书、跨机器比较）→ REALTIME，并接受它会跳。
不要 → 继续问。

问题二

挂起的时间算数吗？
算（过期、TTL、判活）→ BOOTTIME。
不算（测耗时、超时）→ MONOTONIC。

问题三

需要多高精度？
毫秒够（日志、限流、粗粒度超时）→ 加 _COARSE，省一个数量级（§4.3）。
需要微秒/纳秒 → 用标准版。

04

vDSO：不进内核的系统调用

它让 clock_gettime 便宜了一个数量级，但它会悄悄失效

4.1 机制

读时间不需要修改任何内核状态，它只是读一个内核维护的数据结构。既然是只读，就没必要为它付一次特权级切换的钱。vDSO（virtual dynamic shared object）就是这个思路：内核把一小段代码和一个共享数据页映射进每个进程的地址空间，clock_gettime 直接在用户态执行完。

共享数据页里放的是「上次同步时的 TSC 值 + 对应的时间 + 换算系数」，内核在每次时间更新时写它，用户态只读。为了避免读到撕裂的数据，它用的是 seqlock——读者读之前和之后各取一次序号，不一致就重试。这正是 内核同步原语那篇讲的 seqlock 的经典用例：读多写少、读者不能阻塞写者。

4.2 它什么时候会失效

vDSO 只在能够在用户态完成换算时生效。以下情况会静默回落到真正的系统调用，性能差 20 倍而没有任何提示：

情况为什么怎么确认
clocksource 不是 tsc / kvm-clock HPET 要 MMIO 读，用户态做不到 current_clocksource（§2.1）
用了 CLOCK_MONOTONIC_RAW 之外的冷门时钟 vDSO 只实现了常用的几个 strace -c -e clock_gettime：如果能看到调用计数，说明它进内核了
seccomp 过滤器配置不当 某些沙箱会阻止 vDSO 页映射 同上
静态链接的老程序 / 某些语言运行时 没走 glibc 的封装，直接发 syscall 同上
strace 那一条是个很好用的判据：vDSO 生效时，strace 看不到 clock_gettime——因为它压根没进内核，strace 靠 ptrace 拦系统调用，拦不到。所以「strace 里能数出 clock_gettime 的调用次数」本身就说明 vDSO 没起作用。

4.3 更便宜的 COARSE 变体

就算走了 vDSO，25 ns 里大部分花在 RDTSC 和换算上。如果只需要毫秒级精度，CLOCK_MONOTONIC_COARSE 直接读共享页里内核上次更新的值——不读 TSC、不做换算，只有几纳秒。

CLOCK_MONOTONIC：~25 ns，精度纳秒级。
CLOCK_MONOTONIC_COARSE：~5 ns，精度一个时钟节拍（CONFIG_HZ=250 时是 4 ms，HZ=1000 时是 1 ms）。

对一个每秒调 200 万次的服务：0.05 s/s → 0.01 s/s。收益不如从 HPET 换回 TSC 那么戏剧化，但它是白拿的——前提是你的用途真的不需要那个精度。

什么用途适合 COARSE：日志时间戳、限流器的令牌补充（令牌桶那一节就是这么做的）、粗粒度的超时判定、周期性统计。什么不适合：测量单次操作的耗时（4 ms 的粒度会把大部分操作测成 0）、生成有序 ID、任何需要区分相邻两次调用的地方。

05

时间是怎么被调整的

两种调整方式，一个必须做的取舍

5.1 step 与 slew

本机晶振有误差（典型 ±10–50 ppm，也就是一天差 1–4 秒），所以必须定期和外部时间源对齐。对齐有两种做法，它们的取舍很清晰：

5.2 chrony 的默认行为

场景chrony 的默认动作要注意什么
偏差很小（< 几百 ms）slew，全程连续正常状态，不会有问题
偏差大（超过 makestep 阈值）step——直接跳这就是 §3.2 事故的触发时刻
刚开机、时钟差很多通常配 makestep 1.0 3：前 3 次更新允许 step这个配置是对的——开机时 step 是必要的，慢慢 slew 几小时不可接受
虚机从快照恢复 / 迁移后偏差可能是几分钟甚至几小时 → step这是生产环境里 step 最常见的触发原因（§7.3）
有人会想：把 makestep 关掉，永远只 slew，不就没有 §3.2 的问题了吗？

不行，而且危险。偏差 1 小时的话，按 500 ppm 追要 2000 小时（83 天）。在这期间机器的时间一直是错的，日志时间戳、证书校验、分布式系统里的时序判断全都不对。step 不是一个可以关掉的功能，它是「偏差太大时唯一能接受的选择」。

正确的应对不是禁止 step，而是让应用不怕 step——也就是 §3 那件事：所有间隔计算都用 MONOTONIC。做到这一点之后，step 就只影响日志时间戳（可接受），不再影响任何逻辑。

5.3 闰秒的三种处理

UTC 偶尔会插入一个闰秒，出现 23:59:60 这个 POSIX 时间戳表示不了的时刻。三种处理方式：

step 回退一秒

Linux 默认行为：把 23:59:59 重复一次。时间倒退 1 秒。
历史上多次引发事故（2012 年那次让大量 Java 服务 CPU 打满，因为 futex 的超时计算撞上了倒退）。

slew 一秒

用 500 ppm 慢慢追，需要 33 分钟。期间时间连续，但和标准时间有最多 1 秒的偏差。

smear（抹平）

Google / AWS 的做法：把这 1 秒摊到 24 小时里，每秒偷偷慢 ~11.6 μs。全程单调连续，偏差极小。
代价：这段时间内你的时间和标准 UTC 不一致，和用 step 的机器也不一致。

smear 的代价值得强调：抹平期间，抹平的机器和不抹平的机器之间最多差 0.5 秒。如果你的集群里一部分用云厂商的 NTP（smear）、一部分用公共 NTP 池（step），那么闰秒当天这两批机器的时间会不一致——跨机器的时序判断会出错。
所以关键不是选哪种，是全集群选同一种。而这条要求很容易被忽略，因为平时看不出任何区别。
06

定时器：精度被谁吃掉

你要求 1 ms，实际拿到 50 μs 的抖动，中间发生了什么

6.1 内核的两套定时器体系

timer wheel（低精度）hrtimer（高精度）
精度一个 tick（1–4 ms）理论纳秒，实际微秒
数据结构时间轮，插入/删除 O(1)红黑树，O(log n)
用于大量、会被取消的超时：TCP 重传、连接超时需要准点的场景：nanosleep、timerfd、POSIX 定时器
设计取舍牺牲精度换 O(1)。因为绝大多数超时定时器根本不会到期——它们在到期前就被取消了牺牲插入成本换准点
timer wheel 那一行的设计理由很值得琢磨：内核里绝大多数定时器是「超时」而不是「闹钟」——TCP 重传定时器几乎总是在数据被确认时取消，连接超时几乎总是在请求完成时取消。既然大部分定时器只被创建和取消、从不触发，那么优化的目标就该是插入和取消的成本，而不是触发的精度。

这正是 接入网关那篇用时间轮取代 30 万个 steady_timer 的同一个论证——用户态遇到的是同一个问题，解法也是同一个。内核在四十年前就做过这个取舍了。

6.2 用户态四种接口对比

接口怎么通知优点问题
sleep / nanosleep阻塞当前线程最简单阻塞；被信号打断要处理 EINTR 并自己续（clock_nanosleep 配 TIMER_ABSTIME 可以避免重新计算残余）
setitimer / POSIX timer发信号不阻塞信号处理器里只能调 async-signal-safe 函数；多线程下信号送给哪个线程不确定；基本不要用

epoll_wait 的 timeout 参数直接返回零额外开销只有一个超时值，多个定时器要自己算最近的那个；精度是毫秒

// 不用信号、不用单独的定时器线程、不用在每次 epoll_wait 前手算最近超时。
int tfd = timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK | TFD_CLOEXEC);
//                        ↑ 这里的时钟选择就是 §3.3 那个决策：
//                          MONOTONIC 挂起时停走，BOOTTIME 继续走，

struct itimerspec its{};
its.it_value.tv_sec    = 1;   // 首次触发
its.it_interval.tv_sec = 1;   // 之后每 1 秒。设为 0 就是一次性定时器
timerfd_settime(tfd, 0, &its, nullptr);

epoll_ctl(epfd, EPOLL_CTL_ADD, tfd, &ev);

// 读出来的是「自上次读以来错过了几次」。这一点很关键：
// 如果事件循环卡了 5 秒，expirations 会是 5，而不是「触发 5 次」。

uint64_t expirations;
read(tfd, &expirations, sizeof expirations);
if (expirations > 1) {
  // 落后了。对「周期性采样」应当只做一次并打点告警（补做会造成瞬时尖峰），
  // 对「必须每次都执行」的任务才补做。这是业务语义，不是技术细节。
}

6.4 tickless 与 nohz_full

传统内核每秒产生 HZ 次时钟中断（250 或 1000 次），即使 CPU 完全空闲。这既费电，又给每个核带来周期性的干扰。三种模式：

模式行为适合
CONFIG_HZ_PERIODIC始终周期性中断几乎没有场景
NO_HZ_IDLE（默认）CPU 空闲时停掉 tick通用。省电，且不影响忙碌的核
nohz_full=CPUs指定的核上只有一个可运行任务时也停 tick低延迟 / 实时：把干扰从「每毫秒一次」降到接近零
nohz_full 不是「配上就变快」。它有几个反直觉的代价：该核上必须只有一个可运行任务（多一个就退回有 tick）、进出内核的开销变大（每次都要重新计算记账）、而且需要把 RCU 回调、内核线程、中断亲和性都从这些核上赶走，否则干扰照旧。
配了 nohz_full 但没做后面这些的机器，实测经常比默认配置更慢。这类调优要么完整做，要么不做。
07

容器与虚机里的时间

两个「以为被隔离了、其实没有」的东西

7.1 容器里为什么改不了时间

在容器里 date -s 会失败，即使你是 root。原因是：系统时间长期以来根本没有被 namespace 化——它是全机器共享的一个全局状态。容器里的 root 之所以改不动，是因为它缺少 CAP_SYS_TIME（容器运行时默认 drop 掉了）。

如果给容器加上 --cap-add SYS_TIME，它就真的能改宿主机的时间——连带影响宿主上所有其它容器。这是一条常被忽略的容器逃逸相关风险：它不需要突破隔离，因为这里本来就没有隔离。
同理，容器里看到的 uptime 是宿主机的开机时长，不是容器的；/proc/uptime 也一样。很多「容器运行了多久」的监控其实测的是宿主。

7.2 time namespace

Linux 5.6 引入了 time namespace，但它只虚拟化两个时钟：CLOCK_MONOTONIC 和 CLOCK_BOOTTIME，方式是给它们加一个偏移量。

被虚拟化没有被虚拟化
CLOCK_MONOTONIC、CLOCK_BOOTTIME（各自一个可设的 offset） CLOCK_REALTIME——它仍然是全机器共享的

为什么只做这两个？因为它的设计目标很具体：让 checkpoint/restore（CRIU）能工作。一个进程被冻结、几天后在另一台机器上恢复，它读到的 CLOCK_MONOTONIC 不能突然倒退——time namespace 通过设置偏移量让它看起来连续。它不是为了「让容器有自己的时区/时间」而设计的，那个需求从来没被满足过。

所以「容器里的时间和宿主不一样」这个需求，至今没有干净的解法。常见的替代是 libfaketime（LD_PRELOAD 劫持时间函数），但它只对动态链接、且真的调用 libc 的程序有效——静态链接的 Go 程序、直接发 syscall 的代码，都绕过它。用它做测试可以，用它做生产隔离不行。

7.3 虚机的时钟问题

虚机比容器多两个麻烦，而且它们都会触发 §5 的 step：

① 迁移与快照恢复

虚机被暂停、迁移到另一台物理机、或从几小时前的快照恢复——恢复瞬间它的时间是旧的，且新宿主的 TSC 频率可能不同。NTP 会立刻 step 一大步，于是 §3.2 的事故在虚机上出现频率远高于物理机。

② steal time

宿主把 CPU 分给了别的虚机，你的 vCPU 有一段时间根本没在跑。这段时间里你的时钟继续走，但你的代码没执行——表现为「明明什么都没做，测出来花了 20 ms」。
vmstat 的 st 列、/proc/stat 的 steal 字段能看到。

对策是用 paravirtual 时钟（kvm-clock、Hyper-V 的 TSC page）：宿主通过一个共享内存页告诉客户机换算参数，迁移后宿主会更新这个页，客户机的时间自动连续。确认方法就是 §2.1 那个 current_clocksource——虚机里它应该是 kvm-clock 而不是 tsc 或 hpet。

steal time 那一条对性能分析的影响特别大：它让「墙上时间」和「实际执行时间」脱钩。你用 CLOCK_MONOTONIC 测出一段代码花了 20 ms，可能其中 18 ms 是 vCPU 被抢走了。
区分方法是同时测 CLOCK_PROCESS_CPUTIME_ID（只算本进程真正占用的 CPU）：两者差得多，说明时间花在等待上——而在虚机里，「等待」可能包括「等宿主把 CPU 还给我」这种你完全看不见的事。

面试题（12 道）

按难度分三档

点击每道题展开参考答案（先自测，再对照）。

9.1 基础

  1. 基础CLOCK_REALTIME 和 CLOCK_MONOTONIC 有什么区别？各用在什么地方？

    REALTIME 回答「现在几点」，MONOTONIC 回答「过了多久」。

    REALTIME
    墙上时间，从 1970 起算。会被 NTP 调整——会跳、会变速、可能倒退。只用于需要和外界对齐的绝对时刻：日志时间戳、数据库创建时间、证书有效期。
    MONOTONIC
    单调递增，不受时间调整影响（但会被 NTP 微调速率，±500 ppm）。测间隔、算超时、限流、重试退避一律用它。
    为什么容易搞错
    各语言「默认」的时间 API 全都是 REALTIME：time()、System.currentTimeMillis()、time.time()、C++ 的 system_clock。C++ 里 steady_clock 这个名字就是在提示区别——标准要求它单调且步长恒定，system_clock 两条都不保证。
  2. 基础用 CLOCK_REALTIME 算超时会发生什么？

    一次 NTP 校时就能打穿它，而且是两个方向都会出事：

    时间往前跳
    所有在途请求的 deadline 瞬间「已过期」，全部被判超时。表现是「某一刻全站超时，几秒后自动恢复，日志里什么异常都没有」——因为确实没有任何组件报错。
    时间往回跳（更阴险）
    算出来的「已耗时」是负数，if (elapsed > timeout) 永远不成立，这批请求永远不会超时，一直占着连接和线程直到进程重启。它只影响一小批请求，比全量超时更难发现。
    修法
    间隔计算一律用单调时钟。做到这一点之后，NTP step 就只影响日志时间戳（可接受），不影响任何逻辑。
    不能靠「禁止 step」绕过
    slew 的最大速率是 500 ppm，修正 1 秒要 33 分钟，修正 1 小时要 83 天。step 不是可以关掉的功能，正确做法是让应用不怕它。
  3. 基础clock_gettime 是系统调用吗？

    通常不是。它走 vDSO——内核把一小段代码和一个共享数据页映射进每个进程的地址空间，整个调用在用户态完成。

    为什么可以这样
    读时间不修改任何内核状态，只是读一个内核维护的数据结构。既然只读，就不必付特权级切换的钱。共享页里放的是「上次同步的 TSC 值 + 对应时间 + 换算系数」，用户态读它 + 一条 RDTSC + 几次乘除就够了。
    差多少
    系统调用 ~600 ns（Spectre 缓解的 KPTI 让它更贵），vDSO ~25 ns，24 倍。
    加分：怎么防止读到撕裂的数据
    共享页用 seqlock：读者读之前和之后各取一次序号，不一致就重试。这是 seqlock 的经典用例——读多写少、且读者不能阻塞写者。
    怎么确认它生效了
    strace 看不到 clock_gettime 才是正常的（它没进内核，ptrace 拦不到）。反过来，能在 strace -c 里数出调用次数，就说明 vDSO 没起作用。
  4. 基础怎么在事件循环里做定时器？
    timerfd
    把「时间」变成一个可读的 fd，扔进 epoll，和网络 IO 走同一套事件循环。不用信号、不阻塞、不需要单独的定时器线程。
    为什么不用信号（setitimer / POSIX timer）
    信号处理器里只能调 async-signal-safe 函数；多线程下信号送给哪个线程是不确定的。基本上不要用。
    epoll_wait 的 timeout 参数
    零额外开销，但只有一个超时值——多个定时器要自己算最近的那个，而且精度只有毫秒。定时器少时够用。
    timerfd 的一个关键细节
    read() 读出来的是「自上次读以来错过了几次」。如果事件循环卡了 5 秒，expirations 会是 5。补做 5 次还是只做 1 次，内核不替你决定——周期性采样应该只做一次并告警（补做会造成尖峰），必须每次执行的任务才补做。这是业务语义。

9.2 中级

  1. 中级服务没发版、流量没变，CPU 突然涨、P99 涨十倍。查什么？

    如果这个服务调时间很频繁（每请求打几个时间戳很常见），先查 clocksource 是不是被降级了。

    算一笔账
    每秒 200 万次 clock_gettime：TSC + vDSO 是 200万 × 25 ns = 0.05 秒 CPU/秒（5% 的一个核）；HPET 是 200万 × 1000 ns = 2 秒 CPU/秒，两个核持续满载，什么业务都没干。
    而且 HPET 更糟
    它是全局共享的单一硬件，要走总线到南桥，所有核读它都得串行。核越多争抢越严重——在 64 核机器上可能不是「慢 40 倍」而是「整机被一个计时器锁死」。
    怎么查
    cat /sys/devices/system/clocksource/clocksource0/current_clocksource，以及 dmesg | grep -i clocksource——内核降级时会打日志写明原因（Clocksource tsc unstable）。
    为什么这类故障难查
    没有任何组件报错，所有指标都指向「CPU 高」，但没有代码变更能解释它。把 current_clocksource 作为一个 gauge 指标上报，成本几乎为零，能把这类故障从「查一整天」变成「看一眼」。
  2. 中级CLOCK_MONOTONIC 和 CLOCK_BOOTTIME 什么区别？各用在哪？

    唯一差别：系统挂起（suspend）期间是否继续走。MONOTONIC 停住，BOOTTIME 继续。

    判据是一个问题
    挂起的时间算不算数？
    算数 → BOOTTIME
    会话/令牌过期、缓存 TTL、心跳判活。安全语义要的是「真实流逝了多久」——用 MONOTONIC 的话，挂起 3 小时的设备醒来后令牌还没过期，缓存还被当成新鲜的。
    不算数 → MONOTONIC
    测代码耗时（挂起不是「代码在跑」）、网络超时（挂起期间连接早断了）。
    相关的一个坑
    timerfd 和 epoll_wait 的超时基于 MONOTONIC，它们既不会把设备唤醒，也不在挂起期间计时。要唤醒系统得用 CLOCK_BOOTTIME_ALARM（需 CAP_WAKE_ALARM）——这就是「手机闹钟能响但 App 定时器不能」的原因。
  3. 中级NTP 校时有哪两种方式？各自的代价是什么？
    step：直接跳
    立即正确，但时间不连续、可能倒退。这一刻所有用 REALTIME 做的间隔计算全部出错。
    slew：调频率让它追上
    全程单调连续，但慢。最大速率 500 ppm（每秒追 0.5 ms）——修正 1 秒要 33 分钟。这个上限不是随便定的：再快的话「一秒」会明显不等于一秒，依赖时钟测速率的东西（音视频、采样）会失真。
    chrony 的默认
    偏差小 → slew；超过 makestep 阈值 → step。常见配置 makestep 1.0 3 表示前 3 次更新允许 step（开机时必要）。生产上 step 最常见的触发原因是虚机迁移或快照恢复。
    闰秒的三种处理
    step 回退（Linux 默认，2012 年那次让大量 Java 服务 CPU 打满）、slew（33 分钟追上）、smear 抹平（Google/AWS：摊到 24 小时，每秒偷偷慢 11.6 μs）。
    关键不是选哪种，是全集群选同一种——混用的话闰秒当天两批机器最多差 0.5 秒，跨机器时序判断会出错，而平时完全看不出区别。
  4. 中级容器里能不能有自己的时间？

    基本不能。系统时间长期以来没有被 namespace 化，它是全机器共享的全局状态。

    容器里改不了时间的原因
    不是因为被隔离了，而是因为容器运行时 drop 掉了 CAP_SYS_TIME。如果 --cap-add SYS_TIME，它就真的能改宿主机的时间，连带影响所有其它容器——这里本来就没有隔离。
    time namespace（5.6+）只做了一半
    它只虚拟化 CLOCK_MONOTONIC 和 CLOCK_BOOTTIME（各加一个偏移量），CLOCK_REALTIME 仍然全机器共享。
    因为它的设计目标很具体：让 CRIU 的 checkpoint/restore 能工作——进程被冻结几天后在另一台机器恢复，读到的单调时钟不能倒退。它不是为「容器要有自己的时间」设计的。
    两个附带的坑
    容器里的 uptime 和 /proc/uptime 是宿主机的；libfaketime 这类 LD_PRELOAD 方案只对动态链接且真的调 libc 的程序有效，静态链接的 Go 程序绕过它——测试可以用，生产隔离不行。

9.3 高级

  1. 高级为什么不建议自己用 RDTSC 计时？

    TSC 历史上有三个问题，现代 CPU 用三个特性分别解决：变频导致频率变化 → constant_tsc；深度 C-state 停走 → nonstop_tsc；多核不同步 → 内核启动时的同步校验。但即使这三个都满足，自己读仍有两个坑。

    ① RDTSC 可以被乱序执行
    CPU 可能把它提前或推后，测出来的区间不是你想测的那段。要么用 RDTSCP（自带序列化并返回核 ID），要么前后加 lfence。
    ② 线程迁移
    如果核间 TSC 没同步好，线程被调度到另一个核后时间会倒流——「测量耗时」得到负数。
    更实际的建议
    clock_gettime(CLOCK_MONOTONIC) 走 vDSO 时本来就是一条 RDTSC 加几次乘除，只贵十几纳秒，却帮你处理了核间同步、频率换算、CPU 热插拔这些边界情况。自己读 TSC 的收益很小，引入的正确性问题却很难查。
    如果确实需要更便宜
    用 CLOCK_MONOTONIC_COARSE：直接读共享页里内核上次更新的值，不读 TSC 不做换算，~5 ns，代价是精度只有一个 tick（1–4 ms）。适合日志时间戳、限流器令牌补充这类不需要高精度的高频调用。
  2. 高级要求 1 ms 的定时器，实际抖动几百微秒，为什么？

    四层损耗叠加，而主要来源和定时器本身无关：

    ① 硬件分辨率
    现代 APIC timer 纳秒级，可忽略。
    ② timer slack
    内核默认 50 μs，故意合并邻近定时器以省电。prctl(PR_SET_TIMERSLACK, 1) 可以去掉。
    ③ 中断到唤醒
    中断处理 + 加入运行队列，几微秒。
    ④ 等待调度 —— 这才是大头
    定时器到期只是把线程放进运行队列，什么时候真正跑起来由调度器决定。系统繁忙时前面排着一堆就绪线程。空闲时几微秒，繁忙时可达毫秒级。
    所以
    「提高定时器精度」这个问题，大部分时候其实是「降低调度延迟」的问题。对策是提高线程优先级（SCHED_FIFO）、绑核并隔离该核、用 PREEMPT_RT 内核。用 cyclictest 量的就是这个。
    nohz_full 不是银弹
    它要求该核上只有一个可运行任务（多一个就退回有 tick），进出内核的开销变大，还必须把 RCU 回调、内核线程、中断亲和性都从这些核赶走。配了但没做后面这些的机器，实测经常比默认配置更慢。要么完整做，要么不做。
  3. 高级内核为什么有两套定时器（timer wheel 和 hrtimer）？

    因为内核里的定时器有两类完全不同的用途，优化目标相反。

    timer wheel：为「超时」优化
    时间轮，插入/删除 O(1)，精度一个 tick（1–4 ms）。用于 TCP 重传、连接超时这类大量存在、且几乎总是会被取消的定时器。
    hrtimer：为「闹钟」优化
    红黑树，O(log n)，精度理论纳秒。用于 nanosleep、timerfd、POSIX 定时器这类确实要准点触发的。
    背后的洞见
    内核里绝大多数定时器是「超时」而不是「闹钟」——TCP 重传定时器几乎总在数据被确认时取消。既然大部分定时器只被创建和取消、从不触发，那优化目标就该是插入和取消的成本，而不是触发精度。
    同一个论证在用户态也成立
    三十万条长连接的心跳定时器是同样的形态：每收到一帧就要重置一次，绝大多数永远不会触发。所以用户态也该用时间轮而不是 per-connection 的高精度定时器——内核在四十年前就做过这个取舍了。
  4. 高级虚机上的时间有什么特殊问题？
    ① 迁移与快照恢复 → 频繁 step
    虚机被暂停、迁移到另一台物理机、或从几小时前的快照恢复，恢复瞬间时间是旧的，且新宿主的 TSC 频率可能不同。NTP 会立刻 step 一大步——所以「用 REALTIME 算超时」这类 bug 在虚机上暴露的频率远高于物理机。
    ② steal time：时钟走了但代码没跑
    宿主把 CPU 分给了别的虚机，你的 vCPU 有一段时间根本没执行。表现是「明明什么都没做，测出来花了 20 ms」。vmstat 的 st 列能看到。
    对策：paravirtual 时钟
    用 kvm-clock（或 Hyper-V 的 TSC page）：宿主通过共享内存页告诉客户机换算参数，迁移后更新这个页，客户机时间自动连续。确认方法就是看 current_clocksource —— 虚机里它应该是 kvm-clock，不是 tsc 或 hpet。
    steal time 对性能分析的影响
    它让墙上时间和实际执行时间脱钩。用 MONOTONIC 测出一段代码 20 ms，可能 18 ms 是 vCPU 被抢走了。
    区分方法是同时测 CLOCK_PROCESS_CPUTIME_ID（只算本进程真正占用的 CPU）：两者差得多说明时间花在等待上——而在虚机里，「等待」可能包括「等宿主把 CPU 还给我」这种你完全看不见的事。
