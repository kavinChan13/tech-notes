多进程与进程间通信完全指南

线程共享一切所以廉价，进程隔离一切所以可靠。这篇讲清什么时候值得付出隔离的代价、fork 到底复制了什么、六种 IPC 机制的真实取舍、为什么信号处理函数里连 printf 都不能调，以及多进程服务模型里的惊群问题。

01

为什么要多进程

隔离是要花钱买的

线程像合租室友：共用客厅厨房，沟通只需要喊一嗓子，成本极低；但一个人把厨房烧了，全屋一起完蛋。进程像各自独立的公寓：想给邻居送东西得走楼道（IPC），麻烦；但隔壁失火有防火墙挡着，你还能继续过日子。
维度多线程多进程
地址空间共享独立（写时复制 / 显式共享内存）
通信成本几乎为零（直接读写变量）需要 IPC，最快的共享内存也要考虑同步
创建开销低（约几十 μs）较高（fork 要复制页表，exec 要重新加载）
崩溃影响一个线程段错误，整个进程死一个进程死，其他进程活着，父进程可拉起
资源限制整个进程一份 rlimit可以给每个进程单独设 cgroup / rlimit
权限降级做不到（整个进程一个 uid）可以：解析用的子进程降到 nobody + seccomp
调试难度数据竞争难查状态分散在多个进程，需要跨进程追踪
第三方库要求库是线程安全的不安全的库也能用（每进程一份状态）
选多进程的四个真实理由（不是「因为它并行」——线程也并行）：① 故障隔离——Chrome 每个标签页一个进程，一个网页崩了不影响其他标签；② 权限隔离——处理不可信输入（解码图片、解析 PDF）的进程降权 + seccomp 沙箱，即使被 RCE 也拿不到什么；③ 绕开全局状态——某些库有全局单例或不可重入的状态（历史上的 OpenSSL、大量科学计算库），多进程是最省事的方案；④ 独立升级 / 重启——工作进程可以滚动重启而不中断服务。
工业上位机的典型架构：UI 进程 + 算法进程 + 采集进程。算法进程用了大量第三方视觉库，稳定性不可控；采集进程要实时抓相机数据不能被 GC 式的停顿影响；三者用共享内存传图像、用本机 socket 传控制指令。任何一个算法进程崩了，UI 还在，重新拉起即可——这就是隔离的价值。线程模型下的对应内容见 C++ 并发模式与 进程调度与上下文切换。
02

fork / exec / wait 全流程

一次调用，两次返回

fork()：复制当前进程，产生一个几乎一模一样的子进程。它调用一次，返回两次——在父进程里返回子进程的 pid，在子进程里返回 0，出错返回 -1。这是 Unix 里最反直觉也最优雅的设计之一。
#include <unistd.h>
#include <sys/wait.h>

pid_t pid = fork();
if (pid < 0) {
    perror("fork");                       // EAGAIN(进程数超限) / ENOMEM
} else if (pid == 0) {
    // ── 子进程 ──────────────────────────────
    close(listen_fd);                       // ★ 关掉继承来的、自己不需要的 fd
    dup2(pipe_fd[1], STDOUT_FILENO);       // 重定向标准输出到管道
    setgid(nobody_gid); setuid(nobody_uid); // ★ 顺序不能反：先 gid 后 uid
    execl("/usr/bin/worker", "worker", "--job", id, (char*)nullptr);
    _exit(127);                             // ★ exec 失败才会走到这，用 _exit 不是 exit
} else {
    // ── 父进程 ──────────────────────────────
    close(pipe_fd[1]);                     // ★ 必须关写端，否则永远读不到 EOF
    int st = 0;
    while (waitpid(pid, &st, 0) < 0 && errno == EINTR) {}   // ★ 处理信号打断
    if (WIFEXITED(st))        printf("exit %d\n", WEXITSTATUS(st));
    else if (WIFSIGNALED(st)) printf("killed by signal %d\n", WTERMSIG(st));
}

三个必须记住的细节

子进程用 _exit
exit() 会跑 atexit 注册的清理函数、刷新 stdio 缓冲区。子进程继承了父进程已有但未刷新的缓冲内容，exit() 会把它再输出一遍。_exit() 直接进内核，不做用户态清理。
先 setgid 后 setuid
反过来的话，setuid 之后你已经不是 root 了，setgid 会失败——权限还留着一半，是个经典的提权漏洞模式。
fd 泄漏到子进程
子进程继承所有没标 FD_CLOEXEC 的 fd。监听 socket 泄漏进去，会导致你 kill 了父进程但端口还被占着（子进程还持有引用）；密钥文件泄漏进去则是安全问题。习惯：所有 open/socket 都带 O_CLOEXEC/SOCK_CLOEXEC，这比事后 close 可靠得多。

写时复制（COW）到底复制了什么

fork 并不真的拷贝几百 MB 的内存。内核只复制页表，并把父子双方的所有页都标成只读；任一方尝试写入时触发缺页异常，内核这时才真正复制那一页。

COW 的代价不是零。页表复制本身对大内存进程就很贵——一个占 100 GB 的进程 fork，光复制页表就要几百毫秒。这就是 Redis 做 RDB 持久化时会有延迟毛刺的原因，也是为什么大内存服务更倾向用 posix_spawn 或 vfork+exec（内核不复制页表，直接换地址空间）。另一个坑：COW 意味着 fork 后父子同时写会导致内存用量翻倍，OOM 常常发生在 fork 之后而不是 fork 那一刻。
03

僵尸、孤儿与 fork 的雷区

进程管理的三个经典事故

僵尸进程（zombie）：子进程已经退出，但父进程还没 wait 回收它的退出状态。内核必须保留它的 PCB（进程描述符）来存这个状态，于是它以 Z 状态挂在进程表里——不占内存不占 CPU，但占一个 pid。pid 是有限资源（默认 32768），僵尸攒够了就 fork 失败。
僵尸进程像办完离职手续但档案没人签收：人已经走了，工位也腾了，但 HR 系统里那条记录一直挂着，占着编制。孤儿进程则是父母先走了的孩子——不会流落街头，会被 init（1 号进程）收养，将来由它负责签收档案。
❌ 三种会攒僵尸的写法
// 1) 根本不 wait
for (;;) { if (fork() == 0) handle(), _exit(0); }

// 2) SIGCHLD 处理函数里只 wait 一次
void on_child(int) { waitpid(-1, nullptr, 0); }
// 信号不排队！同时死 5 个子进程可能只递送 1 次
// SIGCHLD，剩下 4 个变僵尸

// 3) 主循环里 wait，但主循环阻塞在 accept 上
// 半天转不到 wait 那一句
✅ 两种可靠做法
// A) 明确表示「不关心退出状态」
signal(SIGCHLD, SIG_IGN);
// POSIX 规定：此时子进程退出直接被内核回收
// 代价是 wait() 再也拿不到状态了

// B) 需要退出状态时：循环 + WNOHANG 排干
void on_child(int) {
    int saved = errno;              // ★ 保存 errno
    while (waitpid(-1, nullptr, WNOHANG) > 0) {}
    errno = saved;
}
// 更好：用 signalfd 把 SIGCHLD 变成可读事件，
// 在事件循环里正常处理，彻底避开信号处理函数

容器里的 PID 1 问题

在容器里，你的应用往往就是 PID 1。PID 1 有两个特殊职责：收养孤儿进程并回收它们、转发信号给子进程。普通应用不会做这两件事，结果是——容器里僵尸越攒越多，docker stop 发的 SIGTERM 没人转发导致只能等超时被 SIGKILL。解决办法：用 tini / dumb-init 做 PID 1（docker run --init 就是干这个的），或者自己实现这两个职责。这是容器化时最容易忽略的一个细节，详见 cgroup / namespace 与容器原理。

多线程程序里 fork：最危险的组合

fork 只复制调用它的那个线程。其他线程在子进程里凭空消失——但它们持有的锁不会消失。如果某个线程在 fork 的瞬间正好持有 malloc 的内部锁，子进程继承了这把永远不会被释放的锁；子进程接下来任何一次 malloc 都会永久死锁。这不是理论风险：printf、new、std::string 构造、任何日志库，背后都可能 malloc。所以 POSIX 规定 fork 之后、exec 之前，只能调用 async-signal-safe 的函数——这个白名单里没有 malloc、没有 printf、没有几乎所有 C++ 标准库。
实践结论
多线程程序里 fork 之后立刻 exec，中间什么都别做（除了 close、dup2、setuid 这些 async-signal-safe 的调用）。如果需要「fork 出一个不 exec 的工作进程」，就在程序启动早期、创建任何线程之前先把这些进程 fork 出来。pthread_atfork 理论上能加锁保护，但实际上无法覆盖所有第三方库，不要指望它。更省事的方案是直接用 posix_spawn。
04

IPC 全景与选型

六种机制，一张表选完

机制数据模型典型延迟亲缘要求适合主要坑
匿名管道 pipe字节流，单向~5 μs需要亲缘（fork 继承）父子进程传数据、shell 管道没有消息边界；读端关闭后写会收 SIGPIPE
命名管道 FIFO字节流，单向~5 μs无无关进程间的简单单向流open 会阻塞到两端都打开
socketpair字节流/数据报，双向~5 μs需要亲缘父子进程双向通信、传 fd—（比 pipe 更好用，优先选它）
POSIX 消息队列带边界的消息 + 优先级~8 μs无任务分发、需要优先级的控制通道队列长度和消息大小有系统上限
共享内存裸内存~0.1 μs无大块数据：图像、行情、批量结果完全没有同步，必须自己配信号量/futex；崩溃可能留下不一致状态
Unix 域套接字流 / 数据报，双向~6 μs无通用首选；能传 fd 和凭证路径权限要设对；抽象命名空间是 Linux 专有
信号仅一个编号~2 μs无（要有权限）通知：退出、重载配置不排队、可打断系统调用、处理函数限制极严
eventfd64 位计数器~2 μs亲缘或传 fd纯唤醒通知，配合 epoll只能计数，不能传内容
选型口诀：控制信令走 Unix 域套接字（双向、有连接语义、能传 fd、能拿对端 uid，还能无缝换成 TCP 上远程）；大块数据走共享内存（一帧 5000×4000 的图 60 MB，走 socket 要拷两次，走共享内存是零拷贝）；两者配合用——共享内存放数据，socket 传「第几号缓冲区就绪了」这条几十字节的消息。这是所有高性能本机 IPC 的标准架构，Chrome、PostgreSQL、各类行情系统都是这个套路。
System V IPC（shmget/semget/msgget）不要在新代码里用了。它的标识符是全局整数 key 而不是文件路径，权限管理弱、命名容易冲突、进程崩溃后资源不自动回收（要靠 ipcrm 手动清，或者攒到系统上限后所有人一起挂）。POSIX 版本（shm_open/sem_open/mq_open）用文件路径命名、走 /dev/shm、支持 fd 语义、能配合 epoll，全面更优。存量 System V 代码不用急着改，但新写的一律用 POSIX。
05

管道家族

最简单，也最容易挂死

int fd[2];
pipe2(fd, O_CLOEXEC);        // fd[0] 读端，fd[1] 写端；pipe2 可以原子地设标志

if (fork() == 0) {
    close(fd[0]);            // ★ 子进程只写，立刻关读端
    write(fd[1], buf, n);
    close(fd[1]);
    _exit(0);
}
close(fd[1]);                // ★★ 父进程只读，必须关写端
char b[4096]; ssize_t n;
while ((n = read(fd[0], b, sizeof b)) > 0) consume(b, n);
// n == 0 表示 EOF —— 只有当【所有】写端都关闭时才会发生
「程序卡死在 read 上」的头号原因：忘了关自己那一端。管道的 EOF 条件是「所有写端的引用计数归零」。父进程如果保留着 fd[1] 不关，那么即使子进程退出了，写端引用计数仍然是 1，read 永远返回不了 0，父进程永久阻塞。反过来，写端在所有读端关闭后继续 write，会收到 SIGPIPE，默认行为是直接杀掉进程——服务程序必须 signal(SIGPIPE, SIG_IGN)，然后靠 write 返回 EPIPE 来处理。

管道容量与死锁

管道有固定容量（Linux 默认 64 KB，可用 fcntl(fd, F_SETPIPE_SZ, n) 调整）。写满之后 write 阻塞，读空之后 read 阻塞。这就埋下了一个经典死锁：

❌ 双管道同步读写 → 死锁
// 父：先把 10 MB 全写给子进程，再读结果
write_all(to_child, big_input, 10*MB);   // ← 卡在这
read_all(from_child, result);

// 子：先读完输入，再写结果
read_all(from_parent, input);
write_all(to_parent, big_output);
// 父写满 64 KB 后阻塞；子在读，本该没事——
// 但若子进程边读边写（如 grep），它的输出
// 也会写满 64 KB 然后阻塞，此时双方互等。
✅ 用 epoll 同时驱动两个方向
// 两个 fd 都设 O_NONBLOCK，一起丢进 epoll
set_nonblock(to_child); set_nonblock(from_child);
for (;;) {
    int n = epoll_wait(ep, evs, 2, -1);
    for (int i = 0; i < n; ++i) {
        if (evs[i].events & EPOLLOUT) pump_input();
        if (evs[i].events & EPOLLIN)  drain_output();
    }
    if (input_done && output_eof) break;
}
// 输入写完就 close(to_child)，让子进程读到 EOF
这个死锁在「用管道调用外部程序」的场景里极其常见——Python 的 subprocess 文档专门警告不要用 p.stdin.write() + p.stdout.read() 而要用 communicate()，就是为了这个。C++ 里没有现成的 communicate，得自己写事件循环，或者用临时文件绕开。

socketpair：比 pipe 更好的选择

int sv[2];
socketpair(AF_UNIX, SOCK_STREAM | SOCK_CLOEXEC, 0, sv);
// sv[0] 和 sv[1] 都是【双向】的，一个给父一个给子
// 相比 pipe 的优势：
//   1. 双向，不用开两个 pipe
//   2. 支持 shutdown() 单向半关闭
//   3. 支持 SCM_RIGHTS 传文件描述符（见 §7）
//   4. 可以用 SOCK_SEQPACKET 拿到消息边界
//   5. 支持 SO_RCVTIMEO 等 socket 选项
除非你就是要模拟 shell 的单向管道语义，父子进程通信一律用 socketpair 而不是 pipe。多写零行代码，多拿五项能力。
06

共享内存 + 信号量

最快的 IPC，也最需要自律

共享内存像公司的公共白板：谁都能直接看、直接写，不需要传纸条（拷贝），效率最高。但正因为没人管，两个人同时上去写就会覆盖对方——所以必须约定一套规矩：信号量就是白板旁边那支「谁拿着谁能写」的笔。
// ── 创建者 ─────────────────────────────────────────
int fd = shm_open("/frames", O_CREAT | O_RDWR, 0600);
ftruncate(fd, SIZE);                          // ★ 必须先定尺寸，否则访问会 SIGBUS
void* p = mmap(nullptr, SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
close(fd);                                    // mmap 之后 fd 就可以关了

// ── 控制头：放进程间可用的同步原语 ────────────────
struct Header {
    sem_t                 slots;              // 空位数（生产者等它）
    sem_t                 items;              // 已就绪数（消费者等它）
    std::atomic<uint32_t> head, tail;
    uint32_t              magic, version;     // ★ 版本校验，防止新旧程序混用
};
auto* h = new (p) Header{};                   // placement new
sem_init(&h->slots, 1, N_SLOTS);              // ★ 第二个参数 1 = 进程间共享
sem_init(&h->items, 1, 0);

// ── 生产者 ─────────────────────────────────────────
sem_wait(&h->slots);                          // 等一个空位
memcpy(slot_ptr(h->head), frame, FRAME_SZ);   // 相机可直接 DMA 到这里，连这次拷贝也省掉
h->head = (h->head + 1) % N_SLOTS;
sem_post(&h->items);                          // 通知消费者

四条硬规矩

① 里面绝不能放指针
两个进程把同一块内存映射到不同的虚拟地址。A 进程存的 0x7f1122334455 在 B 进程里指向别处（或直接段错误）。要引用共享内存内部的位置，存偏移量；要在里面放容器，用自定义分配器（Boost.Interprocess 的 offset_ptr 就是干这个的）。同理，虚函数表指针也不能跨进程——共享内存里的对象不能有虚函数。
② 同步原语必须声明为进程间共享
sem_init(&s, 1, n) 的第二个参数、pthread_mutexattr_setpshared(&a, PTHREAD_PROCESS_SHARED)——漏了这一步，锁在单进程内看起来完全正常，跨进程则完全不起作用，而且不会报错。这是最难查的一类 bug。
③ 持锁进程崩溃 = 全体卡死
进程 A 拿着共享 mutex 时段错误，锁永远不会释放。对策：pthread_mutexattr_setrobust(&a, PTHREAD_MUTEX_ROBUST)——之后其他进程 lock 会返回 EOWNERDEAD，你可以修复数据后调 pthread_mutex_consistent 接管。不用 robust 就必须有外部看门狗。
④ 生命周期与清理
shm_open 创建的对象在 /dev/shm/ 下持久存在，进程全退了它还在。要么由某个明确的 owner 在退出时 shm_unlink，要么在启动时用 magic + version 校验并主动重建。留着上一版程序的布局给新版程序用，是一类非常隐蔽的内存踩踏。
什么时候值得上共享内存？算一笔账：走 Unix 域套接字传 60 MB 的图像，需要「用户态→内核缓冲→用户态」两次拷贝，约 10–20 ms；共享内存是 0 次拷贝，只有一次几微秒的信号量操作。数据量大且频率高时差距是数量级的；反过来，如果每秒只传几十条几百字节的控制指令，共享内存带来的复杂度（同步、崩溃恢复、版本管理）完全不值得——直接用 socket。
07

Unix 域套接字与传 fd

本机 IPC 的通用答案

Unix 域套接字（UDS）用的是 socket API，但数据不经过网络协议栈——内核直接在两个 socket 的缓冲区之间搬运，没有 TCP 的分段、校验和、拥塞控制、Nagle 延迟。同样是本机通信，UDS 的吞吐通常是 TCP over loopback 的 1.5–2 倍，延迟约一半。

// 服务端
int s = socket(AF_UNIX, SOCK_STREAM | SOCK_CLOEXEC, 0);
sockaddr_un a{}; a.sun_family = AF_UNIX;
strcpy(a.sun_path, "/run/myapp/ctl.sock");
unlink(a.sun_path);                       // ★ 上次残留的文件会导致 bind 返回 EADDRINUSE
bind(s, (sockaddr*)&a, sizeof a);
chmod(a.sun_path, 0660);                 // ★ 权限靠文件系统控制，别用 0777
listen(s, 64);
SCM_RIGHTS：UDS 独有的能力——通过 sendmsg 的辅助数据把一个打开的文件描述符传给另一个进程。注意传的不是数字，而是内核里的文件表项引用：接收方拿到的 fd 编号可能不同，但指向同一个打开的文件/socket，共享同一个文件偏移量。
传 fd 不是「告诉对方房间号 305」，而是直接把 305 房间的钥匙复制一把递过去。对方的钥匙串上编号可能是第 7 把，但开的是同一扇门；而且你们共用同一个门锁计数——你把门关了（lseek 改了偏移），对方也会感知到。
// ── 发送方：把已 accept 的连接交给工作进程 ────────
void send_fd(int uds, int fd_to_send) {
    char dummy = 'x';                          // ★ 必须带至少 1 字节普通数据
    iovec  io { &dummy, 1 };
    char   ctl[CMSG_SPACE(sizeof(int))] = {};
    msghdr m{};
    m.msg_iov = &io; m.msg_iovlen = 1;
    m.msg_control = ctl; m.msg_controllen = sizeof ctl;

    cmsghdr* c = CMSG_FIRSTHDR(&m);
    c->cmsg_level = SOL_SOCKET;
    c->cmsg_type  = SCM_RIGHTS;
    c->cmsg_len   = CMSG_LEN(sizeof(int));
    memcpy(CMSG_DATA(c), &fd_to_send, sizeof(int));

    sendmsg(uds, &m, 0);
}
// 接收方用 recvmsg + CMSG_FIRSTHDR 取出，得到一个【本进程的】新 fd
// ★ 收完必须自己 close，否则泄漏；★ 忘记提供 msg_control 会导致 fd 被内核直接丢弃
用途做法谁在用
连接分发主进程 accept 后把连接 fd 发给最空闲的工作进程Nginx 的部分模式、各类自研网关
特权分离特权进程绑定 80 端口后把 listen fd 传给降权进程systemd socket activation
零拷贝传大数据传 memfd 或共享内存的 fd，对方自己 mmapWayland、Android Binder、Chrome
身份校验SO_PEERCRED 直接拿到对端的 pid/uid/gidD-Bus、各类本机守护进程
SO_PEERCRED 是 UDS 的另一个杀手锏：内核直接告诉你对端是谁，不需要任何密码或 token。本机守护进程做权限控制时，「调用方 uid 是不是 0 或者在某个组里」这个判断可以完全交给内核，比自己实现认证可靠得多。远程通信没有这个能力，这也是「本机 IPC 不要图省事直接上 HTTP」的一个理由。
08

信号：最容易写错的 IPC

异步、不排队、限制极严

信号像办公室的火警铃：只有「响了」这一个信息量，不能附带任何内容；连响三次和响一次听起来一样（不排队）；而且它会在你正在做任何事的时候突然打断你——包括你正在锁着保险柜的时候。所以火警响时的应急预案必须极其简单，复杂的事情要等回到正常流程再做。

动手感受：信号为什么会「丢」

左边模拟「处理函数很慢 + 信号不排队」：处理期间到达的同种信号会被合并成一次挂起，处理完只会再补一次。右边是正确做法：处理函数只置一个标志（或用 signalfd），主循环循环排干所有待处理事件。点击「同时来 5 个子进程退出」对比结果。

async-signal-safe：白名单有多短

信号处理函数可能在任意一条指令之间被插入执行——包括 malloc 正在改动堆链表的中途。如果你在处理函数里再调 malloc，它会看到一个不一致的堆，轻则数据损坏，重则死锁（glibc 的 malloc 锁不可重入）。POSIX 给出的安全函数白名单很短：write、read、_exit、signal、kill、sem_post 等约一百个系统调用级函数。不在名单里的包括：printf 全家、malloc/free/new/delete、std::string 的任何操作、几乎所有 C++ 标准库、所有日志库。「在信号处理函数里 printf 一条日志」是绝大多数人写过的错误代码。
❌ 处理函数里干活
void on_term(int) {
    log_info("shutting down...");   // malloc + 锁
    save_state_to_db();              // IO + 内存分配
    exit(0);                         // 跑 atexit，更多不安全操作
}
// 90% 的时候「能跑」，剩下 10% 是
// 现场无法复现的死锁或堆损坏
✅ 只置标志 / 用 signalfd
// 方案 A：只写一个原子标志
volatile sig_atomic_t g_quit = 0;

// 主循环每轮检查 g_quit —— 但阻塞在 epoll 上时
// 感知不到，需要 self-pipe 或下面的方案 B

// 方案 B（Linux 首选）：signalfd 把信号变成 fd 事件
sigset_t m; sigemptyset(&m);
sigaddset(&m, SIGTERM); sigaddset(&m, SIGCHLD);
sigprocmask(SIG_BLOCK, &m, nullptr);   // ★ 必须先屏蔽
int sfd = signalfd(-1, &m, SFD_CLOEXEC);
epoll_ctl(ep, EPOLL_CTL_ADD, sfd, &ev);
// 从此信号就是普通的可读事件，
// 在主循环里用任意代码处理，没有任何限制
陷阱说明对策
信号不排队同种信号在挂起期间重复到达只算一次处理时循环排干（while(waitpid(...WNOHANG)>0)）
打断系统调用read/accept 返回 -1 且 errno==EINTR循环重试；或用 sigaction 带 SA_RESTART（但不是所有调用都能自动重启）

多进程服务模型

从 prefork 到 SO_REUSEPORT

模型做法优点缺点
fork-per-connection每来一个连接 fork 一个进程实现最简单，隔离最彻底fork 开销大；C10K 完全不可行。仅适合 sshd 这类低并发高隔离场景
prefork + 共享 listen fd启动时 fork N 个进程，都在同一个 listen fd 上 accept无运行时 fork 开销惊群；负载不均
prefork + accept 互斥锁同上，但抢锁后才 accept消除惊群锁成为瓶颈；这是 Nginx 早期的 accept_mutex
SO_REUSEPORT每个进程各自 bind 同一端口，内核按四元组哈希分发内核层面负载均衡，无锁无惊群，扩展性最好Linux 3.9+；进程退出时它队列里的连接会被重置
主进程 accept + 传 fd主进程 accept，通过 UDS 把连接 fd 发给工作进程可以按真实负载智能分发主进程成为单点和瓶颈
惊群（thundering herd）：N 个进程都阻塞在同一个 listen fd 上等连接，来了一个连接却把全部 N 个都唤醒，最终只有一个 accept 成功，其余 N-1 个白白被调度一遍又睡回去。在高并发下这些无效唤醒会吃掉可观的 CPU。
惊群就像快递员在楼下喊一声「有快递」，整栋楼二十户全跑下来，结果只有一家有件，其余十九家白跑一趟。accept_mutex 相当于「约定每次只派一个人下去看」——不白跑了，但派人这件事本身要排队协调。SO_REUSEPORT 则是每户一个专属信箱，快递员按地址直接投递，谁都不用跑。
惊群问题在现代内核上已经部分解决：Linux 2.6 起，阻塞在 accept 上的多个进程只会唤醒一个。但如果你用的是 epoll 监听 listen fd（几乎所有现代服务都是），epoll_wait 层面的惊群仍然存在——除非用 EPOLLEXCLUSIVE（Linux 4.5+）。所以完整的现代方案是：SO_REUSEPORT 优先，退而求其次用 EPOLLEXCLUSIVE。

工程上还要处理的三件事

优雅重启
老进程收到 SIGTERM 后：停止 accept、处理完手上的请求、然后退出；主进程同时用新二进制拉起新工作进程。SO_REUSEPORT 下要注意老进程 accept 队列里未处理的连接会被内核重置，需要先 close listen fd 并留出排空时间。
崩溃自动拉起
主进程收 SIGCHLD 后判断退出原因：正常退出（滚动重启）不拉起，被信号杀死（崩溃）则重新 fork。必须加退避——如果因为配置错误导致子进程秒崩，无退避的拉起会变成 CPU 打满的死循环。指数退避 + 崩溃计数阈值是标配。
状态共享
多进程模型下，「连接计数」「限流令牌」「缓存」这些原本是进程内变量的东西全部要重新设计。要么放共享内存（快但要自己同步），要么放 Redis（慢但简单），要么接受每进程独立（限流阈值除以进程数）。第三种最常见也最省事，但要意识到它的精度损失。

面试题集（12 道）

按难度分层，先自测再对照

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础fork() 为什么会「返回两次」？父子进程共享什么、不共享什么？

    fork 调用一次，内核创建了两个进程，两个都从这条系统调用返回——父进程拿到子进程 pid，子进程拿到 0。用返回值区分身份，这是 Unix 的经典设计。

    不共享（各一份，写时复制）：地址空间（代码/数据/堆/栈）、pid、父 pid、资源使用统计、挂起的信号集、文件锁。

    共享：打开的文件描述符指向同一个文件表项——这意味着共享文件偏移量，父子同时写同一个文件会互相推进 offset。

    最常见的追问
    「fork 之后父子谁先执行？」——不确定，由调度器决定。任何依赖执行顺序的代码都是错的。要保证顺序必须显式同步（管道、信号量）。
  2. 基础什么是僵尸进程和孤儿进程？各自有什么危害？

    僵尸进程：子进程已退出，父进程还没 wait 回收它的退出状态。内核必须保留 PCB 存这个状态，所以它以 Z 状态挂在进程表里。不占内存不占 CPU，但占一个 pid；pid 是有限资源（默认上限 32768），攒满了整个系统都 fork 不出新进程。

    孤儿进程：父进程先退出，子进程还活着。没有危害——它会被 init（PID 1）收养，将来由 init 负责回收。

    怎么避免僵尸
    ① signal(SIGCHLD, SIG_IGN)——明确表示不关心退出状态，内核直接回收；② 在 SIGCHLD 处理里 while (waitpid(-1, nullptr, WNOHANG) > 0); 循环排干（因为信号不排队，同时死 5 个可能只送 1 次信号）；③ 最优雅的是用 signalfd 把 SIGCHLD 变成 epoll 里的可读事件。
  3. 基础常见的 IPC 方式有哪些？各自适合什么场景？
    • 管道 / FIFO：字节流单向，简单；父子进程或 shell 管道。
    • socketpair：双向字节流，父子进程首选（比 pipe 多五项能力）。
    • 消息队列：带边界、带优先级的消息；任务分发。
    • 共享内存：唯一的零拷贝方案，最快；大块数据（图像、行情）。
    • 信号量 / 互斥量：不传数据，只做同步，配合共享内存用。
    • Unix 域套接字：本机通信的通用首选，双向、能传 fd、能拿对端 uid。
    • 信号：只能传一个编号，用于通知（退出、重载配置）。
    选型口诀
    控制信令走 UDS，大块数据走共享内存，两者配合——共享内存放数据，UDS 传「几号槽位就绪」这条几十字节的消息。这是 Chrome、PostgreSQL、行情系统的通用架构。
  4. 基础用管道时程序卡死在 read 上不动，最可能是什么原因？

    忘了关闭自己不用的那一端写端。

    管道的 EOF 条件是「所有写端的引用计数归零」。fork 之后父子都持有 fd[1]，如果父进程只读却没有 close(fd[1])，那么即使子进程退出了，写端引用计数仍然是 1，read 永远等不到 0，永久阻塞。

    反方向的坑
    所有读端关闭后继续 write，进程会收到 SIGPIPE，默认行为是直接终止进程。服务程序必须 signal(SIGPIPE, SIG_IGN)，改为靠 write 返回 EPIPE 来判断。
    另一种卡死
    管道容量固定（默认 64 KB）。父进程「先写完全部输入再读输出」而子进程「边读边写」时，双方各自写满缓冲区后互相等待——经典死锁。正解是把两个 fd 都设非阻塞丢进 epoll，同时驱动两个方向。

10.2 中级（区分熟练度）

  1. 中级什么是写时复制？fork 一个占用 10 GB 内存的进程，开销大吗？

    COW：fork 时内核不复制物理内存，只复制页表，并把父子双方所有页标为只读。任一方写入时触发缺页异常，内核这时才复制那一页。

    开销并不是零，主要在两处：

    ① 页表复制
    10 GB 内存对应约 250 万个页表项（4 KB 页），复制它们本身就要几十毫秒。这就是 Redis 做 RDB fork 时出现延迟毛刺的原因。用大页（huge page）能减少页表项数量，但会让 COW 的粒度从 4 KB 变成 2 MB，写放大更严重。
    ② 后续的缺页与内存翻倍
    父子进程各自写入时会不断触发缺页复制。最坏情况内存用量翻倍——所以 OOM 经常发生在 fork 之后一段时间，而不是 fork 那一刻。给这类服务规划内存时要留出这份余量。

    如果 fork 后马上 exec，页表复制纯属浪费，应该用 posix_spawn 或 vfork+exec（内核跳过页表复制）。

  2. 中级为什么信号处理函数里不能调用 printf 或 malloc？正确的做法是什么？

    信号处理函数可能在任意两条指令之间被插入执行，包括 malloc 正在修改堆内部链表的中途。此时在处理函数里再调 malloc，它会看到一个不一致的堆——轻则数据损坏，重则死锁（glibc 的 malloc 锁不可重入，同一线程再次加锁直接卡死）。printf 内部会 malloc，还有自己的 stdio 锁，同理不安全。

    POSIX 给出的 async-signal-safe 白名单只有约一百个系统调用级函数（write、read、_exit、kill、sem_post…）。不在名单里的包括 printf 全家、malloc/new、std::string、几乎所有 C++ 标准库和日志库。

    正确做法
    ① 处理函数里只置一个 volatile sig_atomic_t 标志，真正的工作放主循环；② 主循环阻塞在 epoll 上时感知不到标志，用 self-pipe trick（处理函数里 write 一个字节到管道，管道读端在 epoll 里）；③ Linux 上最优解是 signalfd——先 sigprocmask 屏蔽信号，再把 signalfd 加进 epoll，信号就变成了普通可读事件，在主循环里用任意代码处理，完全没有限制。
    还要记得
    处理函数里调系统调用会改 errno，进函数时保存、出去前恢复；注册一律用 sigaction 而不是 signal（后者跨平台语义不一致）。
  3. 中级共享内存里为什么不能存指针？要在共享内存里放一个链表怎么办？

    因为两个进程把同一块物理内存 mmap 到各自地址空间的不同虚拟地址。进程 A 写入的指针 0x7f1122334455 是 A 的虚拟地址，B 进程读到这个值后解引用，指向的是 B 自己地址空间里一个完全无关的位置——运气好是段错误，运气不好是静默的数据损坏。

    解法
    存相对于共享内存基址的偏移量，用的时候 base + offset 还原。链表的 next 存成 uint32_t offset；Boost.Interprocess 的 offset_ptr 把这层封装成了指针的样子。
    同样的原因
    共享内存里的对象不能有虚函数——vptr 指向本进程的虚表，跨进程调用虚函数直接跳飞。也不能直接放 std::string、std::vector（它们内部有指针），要用自定义分配器版本。
    可以强行固定地址吗
    理论上可以用 mmap 的 MAP_FIXED 让所有进程映射到同一个虚拟地址，这样指针就能用了。但这在有 ASLR 的现代系统上很脆弱，而且一旦那个地址已被占用就直接失败。生产上不要这么干，老老实实用偏移量。
  4. 中级什么是惊群？SO_REUSEPORT 怎么解决它？

    惊群：N 个进程都阻塞在同一个 listen fd 上，来了一个连接却唤醒全部 N 个，只有一个 accept 成功，其余 N-1 个白白被调度一遍。高并发下这些无效唤醒是实打实的 CPU 浪费和调度抖动。

    SO_REUSEPORT（Linux 3.9+）让多个 socket 各自 bind 同一个端口，内核为每个 socket 维护独立的 accept 队列，新连接按四元组哈希直接投递到其中一个。只有那一个进程被唤醒——没有惊群，没有锁，扩展性随核数线性增长。

    重要细节
    现代内核上，阻塞在 accept 的惊群早就解决了（只唤醒一个）。但几乎所有真实服务用的是 epoll 监听 listen fd，epoll_wait 层面的惊群依然存在——需要 EPOLLEXCLUSIVE（Linux 4.5+）或 SO_REUSEPORT。这是面试里区分「背过八股」和「真做过」的一个点。
    SO_REUSEPORT 的代价
    哈希是按四元组算的，不感知实际负载——长连接场景下可能出现某个进程分到一堆重连接而另一个很闲。另外进程退出时它队列里排着的连接会被内核直接重置，优雅重启时要先 close listen fd 并留出排空时间。

10.3 高级（体现深度）

  1. 高级多线程程序里调用 fork() 有什么风险？为什么 POSIX 说之后只能调 async-signal-safe 函数？

    fork 只复制调用它的那一个线程，其他线程在子进程里凭空消失。但它们持有的锁不会消失——锁的状态是内存里的一个值，被原样复制到了子进程。

    如果某个线程在 fork 的瞬间正好持有 glibc malloc 的内部锁，子进程就继承了一把永远不会被释放的锁（那个线程在子进程里不存在，没人能解锁）。子进程接下来任何一次内存分配都会永久死锁。

    这不是理论风险
    printf、new、std::string 构造、任何日志库背后都是 malloc。而且这种死锁是概率性的——取决于 fork 的时刻另一个线程在做什么，本地测一万次都不复现，上线跑几天挂一次。
    实践结论
    fork 之后立刻 exec，中间只调 close/dup2/setuid 这类 async-signal-safe 的调用。如果需要不 exec 的工作进程，就在程序启动早期、创建任何线程之前把它们全 fork 出来。pthread_atfork 理论上能在 fork 前后加解锁，但你管不到第三方库内部的锁，不要指望它。最省事的是直接用 posix_spawn，它内部用 CLONE_VFORK 避开了整个问题。
  2. 高级SCM_RIGHTS 传文件描述符时，内核到底传了什么？有哪些实际用途？

    传的不是那个整数。fd 只是进程 fd 表的下标；内核实际做的是：在接收进程的 fd 表里分配一个新槽位，让它指向同一个内核 file 结构体，并把该结构体的引用计数加一。

    所以接收方拿到的 fd 编号通常不同，但指向同一个打开的文件/socket，共享同一个文件偏移量和状态标志。这跟 fork 继承 fd 是同一个机制，只是不需要亲缘关系。

    四类实际用途：

    连接分发
    主进程 accept 后按真实负载把连接 fd 发给最空闲的工作进程——比 SO_REUSEPORT 的哈希分发更智能。
    特权分离
    root 进程绑定 80 端口后把 listen fd 传给已降权的工作进程。systemd 的 socket activation 就是这个原理。
    零拷贝传大数据
    传 memfd_create 出来的匿名内存 fd，对方自己 mmap。Wayland 传帧缓冲、Android Binder、Chrome 的进程间图像传递都用这招。
    易错点
    ① 必须同时发送至少 1 字节普通数据，否则辅助数据可能不被处理；② 接收方如果没提供 msg_control 缓冲，内核会直接关掉那个 fd，静默丢失；③ 收到的 fd 属于接收进程，必须自己 close；④ 一次可以传多个 fd，缓冲区要按 CMSG_SPACE(n * sizeof(int)) 算。
  3. 高级设计一个「相机采集进程 + 算法进程 + UI 进程」的架构，进程间怎么通信？

    数据面走共享内存，控制面走 Unix 域套接字。

    数据面
    预分配 N 个槽位的共享内存环形缓冲（shm_open + mmap），每槽一帧。相机 SDK 直接 DMA 到槽内存，全程零拷贝。控制头里放两个进程间信号量（sem_init 第二参数为 1）做空位/满位计数，加原子的 head/tail 和 magic+version 校验。N 取 3–4：太少会因抖动丢帧，太多只是徒增内存与延迟。
    控制面
    UDS（SOCK_SEQPACKET 拿现成的消息边界）传「第 k 号槽位就绪，帧号 t，曝光参数 …」这几十字节，以及启停、参数下发、结果回传。用 SO_PEERCRED 校验对端身份，避免任意进程连上来发指令。
    失败处理（最容易被忽略的部分）
    ① 共享 mutex 用 robust 属性，算法进程崩溃时其他进程能拿到 EOWNERDEAD 并接管；② 每个槽位带一个「持有者 pid + 时间戳」，看门狗发现超时就强制回收；③ 主进程监听 SIGCHLD（走 signalfd）自动拉起崩溃的子进程，带指数退避防止秒崩死循环；④ 相机进程要能在算法进程重启期间丢帧而不是阻塞——实时采集不能被下游拖住。
    为什么不全用一个多线程进程
    算法侧依赖大量第三方视觉库，稳定性不可控；一个段错误会带走整个程序包括 UI。拆进程后算法崩了 UI 还在，用户看到「本次检测失败，正在恢复」而不是程序消失。这就是隔离的价值，代价是这套 IPC 复杂度。
  4. 高级容器里为什么需要 tini / --init？PID 1 有什么特殊之处？

    PID 1 在内核眼里有两个特殊性：

    ① 是所有孤儿进程的收养者
    父进程先死的进程会被重新挂到 PID 1 名下，PID 1 有义务 wait 回收它们。普通应用不会写这个逻辑，于是容器里僵尸越攒越多，最终 pid 耗尽。
    ② 默认信号处理被禁用
    内核不会对 PID 1 执行信号的默认动作。也就是说，如果你的应用没有显式注册 SIGTERM 处理函数，docker stop 发来的 SIGTERM 会被直接丢弃——不是「没处理」，是根本不生效。Docker 等 10 秒后只能上 SIGKILL，于是每次停容器都要卡 10 秒，而且没有任何优雅退出的机会。

    tini / dumb-init 做的就是这两件事：循环 waitpid 回收所有孤儿；把收到的信号转发给整个进程组。docker run --init 就是自动注入 tini。

    还有一个坑
    ENTRYPOINT 写成 shell 形式（CMD java -jar app.jar）时，PID 1 是 /bin/sh，你的应用是它的子进程——sh 不转发信号，结果一样。要用 exec 形式（CMD ["java","-jar","app.jar"]）或者在脚本里 exec java … 让应用顶替 shell 成为 PID 1。
