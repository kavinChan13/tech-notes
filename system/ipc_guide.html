为什么要多进程

隔离是要花钱买的

线程像合租室友：沟通只需喊一嗓子，成本极低；但一个人把厨房烧了，全屋一起完蛋。进程像各自独立的公寓：送东西得走楼道（IPC），麻烦；但隔壁失火有防火墙挡着。
维度多线程多进程
地址空间共享独立（写时复制 / 显式共享内存）
通信成本几乎为零（直接读写变量）需要 IPC，最快的共享内存也要考虑同步
创建开销低（约几十 μs）较高（fork 要复制页表，exec 要重新加载）
崩溃影响一个线程段错误，整个进程死一个进程死，其他进程活着，父进程可拉起
资源限制整个进程一份 rlimit可以给每个进程单独设 cgroup / rlimit
权限降级做不到（整个进程一个 uid）可以：解析用的子进程降到 nobody + seccomp
调试难度数据竞争难查状态分散在多个进程，需要跨进程追踪
第三方库要求库是线程安全的不安全的库也能用（每进程一份状态）
拆进程的理由必须是「隔离」，不能是「并行」——线程同样用满多核，还便宜一个数量级。值得付 IPC 代价的只有四种：故障隔离、权限隔离（解码不可信输入的进程降权 + seccomp）、绕开全局状态（库里有不可重入的单例）、独立升级重启。

内核眼里没有「进程」和「线程」，只有 task_struct

调度器调度的单位统一叫 task，每个 task 一个 task_struct。fork、pthread_create、容器运行时建沙箱，走的都是同一个 clone，区别只在于传了哪些 CLONE_*——也就是哪些资源共享而不是复制。

CLONE_* 标志置位后共享的东西fork线程不置位的后果 / 用途
CLONE_VMmm_struct：整个地址空间、页表否是不置位就走写时复制，这是「进程贵」的主要来源
CLONE_FILESfiles_struct：fd 表本身否是不置位时 fd 表被复制，但表项指向同一个 struct file——所以父子共享文件偏移量。见 fd 三级表 · fork 后的 fd 共享
CLONE_FScwd、root、umask否是不置位时子进程 chdir 不影响父进程——这正是 shell 的 cd 必须是内建命令的原因
CLONE_SIGHAND信号处理函数表否是不置位时 exec 会把已注册的 handler 全部重置为默认（SIG_IGN 保留）
CLONE_THREAD线程组（TGID）否是置位后 getpid() 返回组长的 pid，真正的 task id 要用 gettid()——ps -L 看到的 LWP 就是它
CLONE_NEWNS 等反过来：不共享某个 namespace否否容器的地基。详见 cgroup / namespace 与容器原理
CLONE_VFORK父进程阻塞等子进程 exec/_exit否否posix_spawn 内部就用它来跳过页表复制
这解释了一个常被问倒的现象：多线程程序里 getpid() 在所有线程返回相同值，而 /proc/<pid>/task/ 下却有一堆目录——CLONE_THREAD 让线程共用一个 TGID，getpid() 返回的就是它；每个线程自己的 id 要用 gettid()，那才是内核调度与 /proc 的主键，top -H、perf、gdb info threads 显示的都是 tid。

隔离的代价：一组可比较的量级

要谈开销就谈数量级。下表是一台普通 x86-64 服务器（内核 6.x、进程常驻约 50 MB、不跨 NUMA）上的量级观察：换硬件绝对值能差 2–3 倍，相对关系稳定。

操作量级主要成本在哪随什么增长
pthread_create + join~20–40 μs分配栈（默认 8 MB 虚拟地址，惰性提交）+ 一次 clone基本恒定
fork + _exit + wait~100–300 μs复制页表与各类内核结构随进程虚拟内存规模线性增长

UDS 一次往返（1 字节 ping-pong）~10–15 μs两次系统调用 + 两次进程唤醒基本恒定
TCP over loopback 一次往返~20–40 μsUDS 的成本 + 协议栈处理基本恒定

四种情况不该拆进程：① 需要频繁交换可变状态——序列化与生命周期管理的复杂度会吃掉全部收益；② 只是想「利用多核」；③ 短命任务——本身跑几百微秒，却要花 1–3 ms 去 spawn；④ 所有代码同属一个信任域，进程边界只带来调试成本。
本篇的边界是进程之间怎么通信。相邻三块在别处：进程/线程概念与 mmap 原理见 操作系统基础 · 进程 vs 线程与 同篇 · mmap 内存映射；fd 三级表见 文件描述符深入 · 三级表详解；同步原语见 内核同步原语与 RCU；线程侧见 C++ 并发模式与 进程调度与上下文切换。

fork / exec / wait 全流程

一次调用，两次返回

fork()：复制当前进程，产生一个几乎一模一样的子进程。它调用一次，返回两次——父进程里返回子进程 pid，子进程里返回 0，出错返回 -1。这是 Unix 里最反直觉也最优雅的设计之一。
// 唯一值得背下来的编排：建管道 → fork → 子进程改 fd 与身份 → exec → 父进程收尸
int pfd[2];
pipe2(pfd, O_CLOEXEC);                      // pfd[0] 读端，pfd[1] 写端

pid_t pid = fork();
if (pid < 0) {
    perror("fork");                       // EAGAIN(进程数超限) / ENOMEM
} else if (pid == 0) {
    // ── 子进程：exec 之前只能调 async-signal-safe 的函数 ──
    close(pfd[0]);                        // ★ 关掉继承来的、自己不需要的那一端
    dup2(pfd[1], STDOUT_FILENO);          // 标准输出重定向到管道写端
    close(pfd[1]);                        //   dup2 之后原 fd 就多余了
    setgid(nobody_gid); setuid(nobody_uid); // ★ 顺序不能反：先 gid 后 uid
    execl("/usr/bin/worker", "worker", "--job", id, (char*)nullptr);
    _exit(127);                            // ★ exec 失败才走到这，用 _exit 不是 exit
} else {
    // ── 父进程 ──
    close(pfd[1]);                        // ★★ 必须关写端，否则永远读不到 EOF
    char b[4096]; ssize_t n;
    while ((n = read(pfd[0], b, sizeof b)) > 0) consume(b, n);

    int st = 0;
    while (waitpid(pid, &st, 0) < 0 && errno == EINTR) {}  // ★ 处理信号打断
    if (WIFEXITED(st))        printf("exit %d\n", WEXITSTATUS(st));
    else if (WIFSIGNALED(st)) printf("killed by signal %d\n", WTERMSIG(st));
}

三个必须记住的细节

子进程用 _exit
exit() 会跑 atexit 回调、刷新 stdio 缓冲区。子进程继承了父进程已有但未刷新的缓冲内容，exit() 会把它再输出一遍。_exit() 直接进内核，不做用户态清理。
先 setgid 后 setuid
反过来的话，setuid 之后你已经不是 root，setgid 会失败——权限只降了一半，是个经典的提权漏洞模式。
fd 泄漏到子进程
子进程继承所有没标 FD_CLOEXEC 的 fd。监听 socket 泄漏进去，会导致你 kill 了父进程但端口还被占着；密钥文件泄漏进去则是安全问题。习惯：所有 open/socket/pipe2 都带 O_CLOEXEC，这比事后 close 可靠得多。

写时复制（COW）到底复制了什么

COW 像合同的复印件：双方共用锁在柜子里的同一份原件，谁都不许改；哪天甲方真要批注某一页，才把那一页复印出来改自己的副本。但柜子的索引目录（页表）是一开始就要抄一份的。

内核只复制页表，把双方私有可写页的 PTE 改成只读、物理页引用计数加一；任一方写入时触发缺页，才真正分配新页。页表不是 COW 的，它是实打实复制的——10 GB 匿名内存有约 262 万个 PTE，光最末级页表就 20 MB，再加各级目录、每个 VMA 的结构复制、对每张物理页的原子加一，几十毫秒跑不掉，而这段时间父进程完全停住。

Redis 的 BGSAVE 是这套机制最著名的现场。① fork 那一刻父进程卡住几十到几百毫秒，成为 P99 的一根尖刺（Redis 把它暴露成 latest_fork_usec，判读方式是「它应当和数据集大小大致成正比」）；② 之后父进程每改一个 key 就多占一张物理页，写入密集时最坏情况内存翻倍——所以「数据集 8 GB、机器 16 GB」不是宽裕，是刚好够。
OOM 常常发生在 fork 之后一段时间，而不是 fork 那一刻——真正的原因是 COW 分裂在持续吃内存。两个配套设置：vm.overcommit_memory=1（否则内核按「最坏要翻倍」直接拒绝 fork），以及关掉透明大页（开了之后 COW 粒度从 4 KB 变成 2 MB，写放大 512 倍）。

fork 的三种替代品：vfork / posix_spawn / 提前 fork

fork 之后马上 exec，刚复制的整套页表会在 execve 里被整个丢掉。vfork 当年就是为这个场景发明的，今天它的正确用法是不要自己用。

方式复制页表子进程能做什么危险性什么时候用
fork是（COW）任意（单线程程序里）低需要在子进程里跑逻辑而不 exec；进程内存不大
vfork否只能 _exit 或 execve。父进程被挂起，而且父子共用同一个栈——子进程里 return 或改局部变量会直接破坏父进程的栈帧极高❌ 不要在应用代码里直接用
posix_spawn否（glibc 内部走 CLONE_VM|CLONE_VFORK）通过 file_actions / attr 声明式地描述「开什么 fd、关什么 fd、设什么信号掩码」，由 libc 在安全的上下文里执行低✅ 「启动一个外部程序」的默认答案，尤其在多线程 / 大内存进程里
启动早期预先 fork是，但那时内存还很小任意低需要长期存在的工作进程时的最优解——把成本挪到内存只有几 MB 的时刻
posix_spawn 的真正价值不是快，是安全：它把那段危险窗口封进 libc，你只能通过 file_actions（adddup2 / addclose）和 attr（POSIX_SPAWN_SETSIGDEF / SETSIGMASK）这套受限接口描述意图，物理上没机会写错。代价是做不了 setuid 降权、chroot、装 seccomp。另注意它失败时返回错误码而不是设 errno。

fork 失败时的四个 errno

errno含义去哪儿确认处理
EAGAIN（用户进程数超限）该 uid 的进程/线程数超过 RLIMIT_NPROCulimit -u、cat /proc/<pid>/limits调高 limit；或先查是不是线程泄漏——这个上限统计的是线程数而不是进程数
EAGAIN（pid 耗尽）系统内 pid 分配不出来cat /proc/sys/kernel/pid_max；ps -eo stat | grep -c Z八成是僵尸堆积（见 §3），去修 wait 逻辑而不是调大 pid_max
ENOMEM内核分配不出 task_struct/页表，或 overcommit 策略拒绝/proc/meminfo、vm.overcommit_memory大内存进程配 overcommit_memory=1；或改用 posix_spawn

03

僵尸、孤儿与 fork 的雷区

进程管理的三个经典事故

僵尸进程（zombie）：子进程已退出，但父进程还没 wait 回收它的退出状态。内核必须保留它的 task_struct 来存这个状态，于是它以 Z 状态挂在进程表里。
僵尸像办完离职手续但档案没人签收：人走了、工位腾了，HR 系统里那条记录一直挂着，占着编制。孤儿则是父母先走了的孩子——不会流落街头，会被 reaper 收养，将来由它签收档案。

一次 SIGCHLD 可能对应 N 个已退出的子进程

根因几乎总是信号不排队：内核对每个未决的标准信号只维护一个挂起位，五个子进程同一瞬间退出，五次置位合并成一次递送。处理函数只 waitpid 一次，剩下四个就永远没人管，而且不会再有第二次 SIGCHLD 提醒你。

static void on_sigchld(int /*sig*/) {
    int saved = errno;                 // ★ ① waitpid 会改 errno，必须存起来——
                                       //     被打断的主流程可能正要读它
    while (waitpid(-1, nullptr, WNOHANG) > 0) { }
    // ★ ② 循环排干。三种结束方式都是正常的：
    //     返回 0                     → 还有活着的子进程，但没有待回收的
    //     返回 -1 且 errno == ECHILD → 一个子进程都没了
    //     返回 -1 且 errno == EINTR  → 被别的信号打断，直接结束也行
    errno = saved;                     // ★ ③ 恢复
}

void install_sigchld() {
    struct sigaction sa{};             // ★ 用 sigaction 而不是 signal，见 §8
    sa.sa_handler = on_sigchld;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART            // 自动重启可重启的慢系统调用
                | SA_NOCLDSTOP;         // ★ 子进程被 SIGSTOP 停住时不要发 SIGCHLD，
                                        //   否则调试子进程时主进程收到一堆无意义的信号
    sigaction(SIGCHLD, &sa, nullptr);
}
为什么必须是 WNOHANG
不加 WNOHANG 的循环在回收完所有已退出的子进程之后，会阻塞在还活着的那些子进程上——整个进程卡死在信号处理函数里，主流程再也回不去。
handler 里能调 waitpid 吗
能，它在 async-signal-safe 白名单里（就是一个系统调用，没有用户态状态）。但白名单里没有你的日志函数：想在回收时打日志，只能置个标志让主循环去打，或者用 signalfd（见 §8）把 SIGCHLD 变成 epoll 里的可读事件，彻底避开处理函数。

wait / waitpid / waitid：三个接口，语义差得很远

接口能等谁返回什么非阻塞默认会汇报的事件评价
wait(&st)任意一个子进程pid + 打包的状态整数不能退出、被信号杀死等价于 waitpid(-1, &st, 0)，只在最简单的场景用
waitpid(pid, &st, opt)>0 指定 pid；-1 任意；0 同进程组；<-1 指定进程组同上WNOHANG退出、被信号杀死；加 WUNTRACED 才报停止日常主力
waitid(idtype, id, &info, opt)P_PID / P_PGID / P_ALL / P_PIDFDsiginfo_t：si_pid、si_uid、si_code、si_statusWNOHANG必须显式指定 WEXITED / WSTOPPED / WCONTINUED语义最清晰；独有 WNOWAIT（查看但不回收，状态留着下次还能取）
waitid 的 si_code 比一堆 WIF* 宏干净得多：CLD_EXITED / CLD_KILLED / CLD_DUMPED / CLD_STOPPED / CLD_CONTINUED / CLD_TRAPPED 直接说明发生了什么；waitpid 那边同样的信息要靠下面这组宏拆一个打包的整数，而它的位布局是历史遗留，没有可移植性。WNOWAIT 还能做「查看但不消费」的健康检查。
状态宏为真时的含义配套取值宏易错点
WIFEXITED(st)正常 exit / _exit / main 返回WEXITSTATUS(st)只有低 8 位。exit(256) 传出去是 0，exit(-1) 是 255
WIFSIGNALED(st)被信号终止WTERMSIG(st)、WCOREDUMP(st)shell 里看到的 137 就是 128+9（SIGKILL），那是 shell 的编码约定，不是内核的
WIFSTOPPED(st)被 SIGSTOP/SIGTSTP 停住（没有退出）WSTOPSIG(st)默认不汇报，要加 WUNTRACED；调试器 ptrace 时才常用
WIFCONTINUED(st)被 SIGCONT 恢复—要加 WCONTINUED
pid 复用竞态与 pidfd。记下的 pid 4821 退出并被回收之后，系统可能把它分给一个无关的新进程，此时 kill(4821, SIGTERM) 会打到无辜的第三者身上。pidfd（CLONE_PIDFD 或 pidfd_open()）稳定引用某个具体进程实例，不受复用影响，还能丢进 epoll，进程退出时变为可读。

SIG_IGN 让内核自动回收：三个副作用

把 SIGCHLD 设成 SIG_IGN（或用 sigaction 设 SA_NOCLDWAIT，此时 sa_handler 要填 SIG_DFL）之后，POSIX 规定子进程退出直接被内核回收，不产生僵尸。最省事，但有代价：

① 退出状态全部丢失
正常退出还是段错误、退出码是几，一概拿不到。对「崩溃后要自动拉起、并区分正常与异常退出」的服务主进程，这等于把最关键的信息扔了——它只适合「发个通知就不管了」的场景。
② wait 的行为变了
wait()/waitpid(-1,…) 会一直阻塞到所有子进程都退出，然后返回 -1 且 errno == ECHILD。代码里残留的 wait 会给出完全不同的结果。
③ 会被 exec 继承
exec 把被捕获的信号恢复成默认，但被忽略的信号保持忽略。于是你 exec 起来的第三方程序从出生起就在一个「SIGCHLD 被忽略」的环境里，它自己的 wait 逻辑莫名失效。规矩：exec 之前把信号处理恢复默认（POSIX_SPAWN_SETSIGDEF）。
容器里你的应用往往就是 PID 1，而 PID 1 有两个特殊职责：收养并回收孤儿、把信号转发给子进程。普通应用不做，于是僵尸越攒越多、docker stop 的 SIGTERM 没人转发只能等超时被 SIGKILL。办法是用 tini / dumb-init 做 PID 1（docker run --init），细节见 §10 最后一题。

多线程程序里 fork：最危险的组合

fork 只复制调用它的那个线程。其他线程在子进程里凭空消失——但它们持有的锁不会。锁的状态就是内存里的一个值，被原样复制过去，而能解开它的线程已经不存在。所以 POSIX 规定 fork 之后、exec 之前只能调用 async-signal-safe 的函数。
为什么不能指望 pthread_atfork
它的套路是「prepare 里把锁全拿到手，fork 之后两边各自解开」。但：① 你管不到别人的锁——第三方库的 mutex、日志库的写锁、函数内静态局部变量的初始化保护（__cxa_guard_acquire）都不会帮你注册；② 只要一处漏网就会死锁，而你无法证明自己列全了；③ 它自己会引入死锁——prepare 按注册的逆序调用而 parent/child 按注册顺序，两者对不上时就死在父进程里。
「现代 glibc 给 malloc 打了补丁」这件事要说清。glibc 在 fork 内部会先锁住所有 malloc arena、之后再解开，所以教科书上那个例子在较新的 glibc 上不容易复现了。但这是实现细节，不是保证——换分配器、换 libc、升降一个版本结论就可能变，而且它只覆盖 glibc 自己的锁。
实践结论
fork 之后立刻 exec，中间只调 close/dup2/setuid 这类 async-signal-safe 的函数。需要「不 exec 的长期工作进程」，就在启动早期、创建任何线程之前把它们全 fork 出来——顺带避开了复制页表的成本。最省事的是直接用 posix_spawn（见 §2）。

「能不能进 epoll」这一列往往是决定性的
真实服务几乎都是单线程事件循环 + epoll。进不了就意味着要么额外开一个线程去阻塞等它（又得处理它与事件循环的同步），要么轮询。这就是共享内存从来不单独使用的根本原因——它快，但「不会说话」，必须配一个能进 epoll 的通道来传「数据准备好了」。

上面的时延口径都是一字节 ping-pong 往返除以二：同机、两个进程绑在同一 NUMA 节点的不同物理核、CPU 调频锁 performance。挤在同一个核上会因为每次往返都要等对方被调度而慢一倍以上，所以不绑核直接测的结果会在两个数之间随机跳，容易误判成「UDS 抖动很大」。也别拿它推算吞吐：时延要小包立即发、吞吐要攒批。

System V IPC（shmget/semget/msgget）不要在新代码里用了。标识符是全局整数 key 而不是文件路径，权限管理弱、命名容易冲突、进程崩溃后资源不自动回收（要靠 ipcrm 手动清）。POSIX 版本用文件路径命名、走 /dev/shm、支持 fd 语义、能配合 epoll，全面更优。
05

管道家族

最简单，也最容易挂死

管道的用法在 §2 那段编排里已经写全了。真正需要理解的不是 API，而是「什么时候会读到 EOF」这条规则——它是绝大多数管道事故的源头。

管道容量与死锁

管道容量固定（Linux 默认 16 个页 = 64 KB）。写满则 write 阻塞，读空则 read 阻塞。于是「用管道调用外部程序」这个最常见的场景里埋着一个经典死锁：

容量能查也能改，但别当解药
fcntl(fd, F_GETPIPE_SZ) 读、F_SETPIPE_SZ 改（内核向上取整到页大小的 2 的幂倍，缩小时不能小于已缓冲的数据量，否则 EBUSY），非特权上限是 /proc/sys/fs/pipe-max-size。调大的本质是用不可换出的内核页换调度次数；需要的缓冲一旦到几十 MB，就说明管道不是对的抽象。
一个非常难查的隐性上限
/proc/sys/fs/pipe-user-pages-soft 是每个用户所有管道占用的页数软上限（默认 16384 页 = 64 MB）。超过之后新建管道会被悄悄降级成一个页大小而不是报错——表现为「某天开始程序莫名变慢」。

PIPE_BUF：多个进程写同一个管道会不会交错

PIPE_BUF（Linux 上是 4096，POSIX 只保证至少 512）：不超过这个字节数的一次 write 是原子的——要么整块进入管道，要么一个字节都不进，绝不会和另一个写者的数据交织。超过之后内核可能写一部分、让别人插进来、再写剩下的。

这条规则支撑了一个很实用的模式：多个进程往同一个管道写日志，只要每条一次 write 且不超过 4 KB，就不需要任何锁。判据只有「单次 write 有没有超过 PIPE_BUF」：「我测了几次没交错」不能证明写法安全。

一次写的字节数阻塞模式（默认）O_NONBLOCK
≤ PIPE_BUF阻塞到有足够空间，然后原子地全部写入空间够 → 全部写入；空间不够 → 一个字节都不写，返回 -1/EAGAIN
> PIPE_BUF会写完全部数据，但可能被其它写者的数据打断分段有多少空间写多少，返回实际写入的字节数（部分写）；一点空间都没有才 EAGAIN
最常见的误用是「以为它适用于所有 fd」。PIPE_BUF 的原子性只针对管道和 FIFO。写普通文件的并发原子性来自另一套机制（O_APPEND 下内核在文件锁保护中「取偏移 + 写」）；写 socket 则完全没有这种保证——把日志从管道改成 socket 之后开始出现半行日志，就是这么来的。

FIFO：给没有亲缘关系的进程用的管道

FIFO（mkfifo）就是给管道起个文件系统里的名字，谁都能 open；行为和匿名管道完全一样（同一份内核实现），唯一需要额外理解的是 open 的阻塞语义。它是文件系统里的真实节点，谁创建谁负责 unlink。

打开方式没有对端时的行为用途
open(O_RDONLY)阻塞，直到有进程以写方式打开读端先起，等写端来接
open(O_WRONLY)阻塞，直到有进程以读方式打开写端先起，等读端来接
open(O_RDONLY | O_NONBLOCK)立刻成功，之后 read 返回 0（当前无写端）✅ 守护进程的常用写法
open(O_WRONLY | O_NONBLOCK)立刻失败，errno == ENXIO客户端用来探测「服务在不在」，探到之后再把 O_NONBLOCK 去掉走简单的阻塞写
open(O_RDWR)立刻成功（自己既是读端也是写端）服务侧的常用技巧：让读端自己也持有一个写端引用，read 就不会在所有外部写者退出时返回 EOF，fd 可以一直挂在 epoll 里，不必写重开逻辑
FIFO 今天只剩两个合理用途：给脚本提供一个运维友好的指令口子（echo reload > /run/myapp/cmd.fifo 谁都会用），以及在没法改造成 socket 的老程序之间搭桥。新写的双向本机通信直接上 UDS——FIFO 单向、没有连接概念、拿不到对端身份、也没法传 fd。

socketpair：比 pipe 更好的选择

除非你就是要模拟 shell 的单向管道语义，父子进程通信一律用 socketpair(AF_UNIX, SOCK_STREAM | SOCK_CLOEXEC, 0, sv) 而不是 pipe：多写零行代码，多拿五项能力——① 两端都是双向的，不用开两根管道；② 支持 shutdown() 单向半关闭；③ 支持 SCM_RIGHTS 传 fd（见 §7）；④ 换成 SOCK_SEQPACKET 就有了消息边界；⑤ 能用 SO_RCVTIMEO 这类 socket 选项。

共享内存 + 信号量

最快的 IPC，也最需要自律

共享内存像公司的公共白板：谁都能直接看、直接写，不需要传纸条（拷贝），效率最高。但正因为没人管，两个人同时上去写就会覆盖对方——所以必须约定规矩：信号量就是白板旁边那支「谁拿着谁能写」的笔。
// ── 建立：用 O_EXCL 明确区分「我是创建者」还是「我是后到的」 ──
int fd = shm_open("/frames", O_CREAT | O_EXCL | O_RDWR, 0600);
bool creator = (fd >= 0);
if (!creator && errno == EEXIST) fd = shm_open("/frames", O_RDWR, 0600);
if (creator) ftruncate(fd, RING_BYTES);  // ★ 不定尺寸就访问 = SIGBUS，不是段错误

void* p = mmap(nullptr, RING_BYTES, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
close(fd);                               // ★ 映射建立后 fd 就没用了，映射本身持有引用
Ring* r = static_cast<Ring*>(p);

if (creator) {
    r->version = RING_VERSION; r->n_slots = N_SLOTS;
    r->slot_sz = SLOT_SZ;      r->data_off = DATA_OFF;  // ★ 存【偏移】不存指针
    sem_init(&r->slots, 1, N_SLOTS);  // ★★ 第二个参数 1 = pshared，跨进程有效。
    sem_init(&r->items, 1, 0);        //     写 0 在单进程里测完全正常，跨进程静默失效
    r->magic.store(RING_MAGIC, std::memory_order_release);  // ★ magic 最后写
} else {
    while (r->magic.load(std::memory_order_acquire) != RING_MAGIC) usleep(1000);
    if (r->version != RING_VERSION) return -1;  // ★ 版本不匹配必须拒绝启动
}

// ── 生产者一轮：所有等待都带超时，消费者崩了也不会永久卡住 ──
timespec dl; clock_gettime(CLOCK_REALTIME, &dl); dl.tv_sec += 1;
if (sem_timedwait(&r->slots, &dl) < 0) {
    if (errno == ETIMEDOUT) { drop_frame(); return; }  // ★ 实时采集丢帧，不阻塞上游
    if (errno == EINTR)     return;
}
uint32_t i = r->head;
memcpy(slot_ptr(r, i), frame, FRAME_SZ);   // 相机可直接 DMA 到这里，连这次拷贝也省掉
r->meta[i] = SlotMeta{ seq, now_ns(), FRAME_SZ };

sem_post(&r->items);                       // 通知消费者（内含 release 语义）

//   return reinterpret_cast<uint8_t*>(r) + r->data_off + (size_t)i * r->slot_sz;

四条硬规矩

① 里面绝不能放指针
两个进程把同一块内存映射到不同的虚拟地址，A 存的 0x7f1122334455 在 B 里指向别处。要引用内部位置就存偏移量，要放容器就用自定义分配器（offset_ptr）。同理虚表指针也不能跨进程——共享内存里的对象不能有虚函数。
② 同步原语必须声明为进程间共享
sem_init(&s, 1, n) 的第二个参数、pthread_mutexattr_setpshared(&a, PTHREAD_PROCESS_SHARED)——漏了这一步，锁在单进程内完全正常，跨进程则不起作用而且不报错。pshared 决定内核用「虚拟地址」还是「物理页」作 futex 等待队列的键，不声明就等在两条不同的队列上。见 内核同步原语与 RCU。
③ 持锁进程崩溃 = 全体卡死
进程 A 拿着共享 mutex 时段错误，锁永远不会释放。对策是 pthread_mutexattr_setrobust(&a, PTHREAD_MUTEX_ROBUST)——之后其他进程 lock 返回 EOWNERDEAD，修好数据再调 pthread_mutex_consistent 接管。不用 robust 就必须有外部看门狗。
④ 生命周期与清理
shm_open 的对象在 /dev/shm/ 下持久存在（好处是能 ls、能 rm、能 df 看用量）。要么由明确的 owner 退出时 shm_unlink，要么启动时靠 magic + version 校验并重建——把上一版的布局给新版程序用，是一类非常隐蔽的内存踩踏。另外容器里 /dev/shm 常常只有 64 MB，空间不够时 ftruncate 会成功但写到某页时 SIGBUS——别查野指针，去看 df -h /dev/shm。

进程崩溃之后：卡死排查与三条兜底

共享内存最大的运维难题不是性能，是「有个进程死在临界区里了」。网络通信里对端挂掉会断连、read 返回 0，你至少知道出事了；共享内存里对端挂掉什么都不会发生，锁一直锁着，剩下的进程安静地卡死。

卡住时的三板斧
① cat /proc/<pid>/syscall，首个数字是 202（futex）就说明卡在锁或信号量上；② grep -l /dev/shm/frames /proc/*/maps 列出所有映射了这块内存的进程（比 lsof 快，也不要 root）——比预期的多，八成是上一代进程没退干净，这正是 magic + version 要防的；③ System V 侧看 ipcs -m 里 nattch=0 的泄漏段。
robust 覆盖不到的两块
① 条件变量没有 robust 版本：等在 pthread_cond_wait 里的进程不会因为「本该唤醒它的进程死了」而被唤醒。② sem_t 也没有：生产者在 sem_wait(slots) 和 sem_post(items) 之间崩溃，那个槽位就永久丢了，崩几次后流水线停摆且没有任何错误信息。还有一个终局状态：拿到 EOWNERDEAD 却没调 pthread_mutex_consistent 就解锁，之后所有 lock 返回 ENOTRECOVERABLE。
生产上真正的兜底是这三条叠加
① 所有等待都带超时（sem_timedwait / pthread_cond_timedwait / pthread_mutex_timedlock），至少能打日志、能告警；② 每个槽位记录「持有者 pid + 领用时间戳」，看门狗发现某槽被已不存在的 pid 占了超过 N 秒就强制回收——要连 pid 的启动时间一起记（/proc/<pid>/stat 第 22 个字段），否则 pid 复用会让你误判；③ 定义一条「整块重建」的路径。能自动重建的系统，比试图把每种不一致都修好的系统可靠得多。
什么时候值得上共享内存？照 §4 那张拷贝次数图算账就行。一条实用的判据：单条消息小于几十 KB，或者每秒不到一千条，就别上共享内存——同步、崩溃恢复、版本管理这些复杂度换不回那点拷贝开销。

Unix 域套接字与传 fd

本机 IPC 的通用答案

UDS 用的是 socket API，但数据不经过网络协议栈——内核直接在两个 socket 的缓冲区之间搬运。服务端的写法就是普通四步：socket(AF_UNIX, SOCK_STREAM | SOCK_CLOEXEC, 0) → 填 sockaddr_un.sun_path → unlink 掉上次残留的 socket 文件（否则 bind 直接 EADDRINUSE）→ bind + chmod 0660（权限靠文件系统控制）→ listen。真正独有的能力有两个：传 fd 和拿对端凭证。

SCM_RIGHTS：通过 sendmsg 的辅助数据把一个打开的文件描述符传给另一个进程。注意传的不是那个整数，而是内核里的文件表项引用。
传 fd 不是「告诉对方房间号 305」，而是直接把 305 房间的钥匙复制一把递过去。对方钥匙串上的编号可能是第 7 把，但开的是同一扇门；而且你们共用同一个门锁状态——你改了偏移量，对方也会感知到。
// ── 发送方：把一个已打开的 fd 交给对端 ────────────────────
void send_fd(int uds, int fd_to_send) {
    char dummy = 'x';                          // ★ 必须同时带至少 1 字节普通数据
    iovec  io { &dummy, 1 };
    char   ctl[CMSG_SPACE(sizeof(int))] = {}; // 传 n 个就是 CMSG_SPACE(n*sizeof(int))
    msghdr m{};
    m.msg_iov = &io; m.msg_iovlen = 1;
    m.msg_control = ctl; m.msg_controllen = sizeof ctl;

    cmsghdr* c = CMSG_FIRSTHDR(&m);
    c->cmsg_level = SOL_SOCKET;
    c->cmsg_type  = SCM_RIGHTS;
    c->cmsg_len   = CMSG_LEN(sizeof(int));
    memcpy(CMSG_DATA(c), &fd_to_send, sizeof(int));  // ★ 用 memcpy：
    sendmsg(uds, &m, 0);                             //   CMSG_DATA 不保证对齐
}

// ── 接收方：取出一个【属于本进程】的新 fd ─────────────────
int recv_fd(int uds) {
    char dummy = 0;
    iovec  io { &dummy, 1 };
    char   ctl[CMSG_SPACE(sizeof(int))] = {};
    msghdr m{};
    m.msg_iov = &io; m.msg_iovlen = 1;
    m.msg_control = ctl; m.msg_controllen = sizeof ctl;  // ★ 不提供这块缓冲，
                                                           //   内核会直接把 fd 关掉
    if (recvmsg(uds, &m, MSG_CMSG_CLOEXEC) <= 0) return -1;
    // ★ MSG_CMSG_CLOEXEC 原子地给收到的 fd 设上 FD_CLOEXEC；事后 fcntl 有竞态窗口
    if (m.msg_flags & MSG_CTRUNC) return -1;
    // ★ MSG_CTRUNC = 控制数据被截断，说明缓冲开小了，对应的 fd 已被内核丢弃。
    //   不检查的话表现是「对方说发了但我没收到」，极难定位。

    for (cmsghdr* c = CMSG_FIRSTHDR(&m); c; c = CMSG_NXTHDR(&m, c))
        if (c->cmsg_level == SOL_SOCKET && c->cmsg_type == SCM_RIGHTS) {
            int fd; memcpy(&fd, CMSG_DATA(c), sizeof fd);
            return fd;      // ★ 它属于本进程，用完必须自己 close ——
        }                    //   不会随连接关闭而消失
    return -1;
}

信号：最容易写错的 IPC

异步、不排队、限制极严

信号像办公室的火警铃：只有「响了」这一个信息量；连响三次和响一次听起来一样（不排队）；而且它会在你做任何事的时候突然打断你——包括你正锁着保险柜的时候。所以应急预案必须极其简单，复杂的事留到回正常流程再做。

动手感受：信号为什么会「丢」

左边模拟「处理函数很慢 + 信号不排队」：处理期间到达的同种信号会被合并成一次挂起。右边是正确做法：处理函数只置一个标志（或用 signalfd），主循环循环排干所有待处理事件。

async-signal-safe：白名单有多短

信号处理函数可能在任意一条指令之间被插入执行——包括 malloc 正在改动堆链表的中途。此时再调 malloc，它会看到一个不一致的堆，轻则数据损坏，重则死锁。POSIX 的安全白名单只有约一百个系统调用级函数（write、read、_exit、kill、waitpid、sem_post 等），名单外包括 printf 全家、malloc/new、std::string、几乎所有 C++ 标准库和日志库。

SA_RESTART 给了很多人一种错觉：加上它就不用管 EINTR 了。不是的——有一批调用无论如何都会返回 EINTR，恰恰是事件循环里最核心的那几个：

类别典型调用加了 SA_RESTART 会怎样
永远不重启epoll_wait、poll、select、nanosleep、clock_nanosleep、sigtimedwait、io_getevents照样返回 EINTR。因为它们带超时——自动重启会把超时重新计满，语义就错了

把信号纳入事件循环：self-pipe 与 signalfd

只置标志的方案有一个无法用标志本身解决的竞态，根治思路只有一个：让信号变成一个 fd 上的可读事件，和其它 IO 事件走同一条路，竞态自然消失。

#include <sys/signalfd.h>

int setup_signalfd(int ep) {
    sigset_t m; sigemptyset(&m);
    sigaddset(&m, SIGTERM); sigaddset(&m, SIGINT);
    sigaddset(&m, SIGHUP);  sigaddset(&m, SIGCHLD);

    // ★★ 必须先屏蔽！否则信号仍然走默认处理（SIGTERM 直接杀进程），
    //     signalfd 根本没机会拿到它 —— 这是最常见的一处写错。
    // ★  多线程程序用 pthread_sigmask，而且要【在创建线程之前】设，
    //     这样所有线程都继承这个掩码，信号只会落到 signalfd 上。
    if (pthread_sigmask(SIG_BLOCK, &m, nullptr) != 0) return -1;

    int sfd = signalfd(-1, &m, SFD_NONBLOCK | SFD_CLOEXEC);
    if (sfd < 0) return -1;
    epoll_event ev{}; ev.events = EPOLLIN; ev.data.fd = sfd;
    epoll_ctl(ep, EPOLL_CTL_ADD, sfd, &ev);
    return sfd;
}

void on_signalfd_readable(int sfd) {
    signalfd_siginfo si;
    // ★ 循环读干净：一次 read 可以返回多个 signalfd_siginfo
    while (read(sfd, &si, sizeof si) == (ssize_t)sizeof si) {
        switch (si.ssi_signo) {
        case SIGTERM: case SIGINT:
            log_info("shutdown by pid=%u uid=%u", si.ssi_pid, si.ssi_uid);
            begin_graceful_shutdown();      // ★ 普通函数，随便调
            break;
        case SIGHUP: reload_config(); break;
        case SIGCHLD:
            // ⚠ signalfd 【不改变】标准信号不排队的事实：一次事件仍然可能
            //   对应多个已退出的子进程，所以这里照样要循环排干
            while (waitpid(-1, nullptr, WNOHANG) > 0) { }
            break;
        }
    }
}

signalfd 最隐蔽的坑：信号屏蔽字会跨 exec 继承。信号处理函数在 exec 后恢复默认，但屏蔽字不会。于是服务屏蔽了 SIGTERM 走 signalfd，某天它 exec 起一个辅助脚本，那个脚本从出生起 SIGTERM 就是被屏蔽的，怎么都 kill 不掉。确认方式是看 /proc/<pid>/status 的 SigBlk（十六进制位图，第 n 位对应信号 n）。别误判：走 signalfd 的程序本来就该有非零的 SigBlk，该警惕的是它 exec 起来的子程序也有同样的值。规矩：exec 之前清空掩码。

多进程服务模型

从 prefork 到 SO_REUSEPORT

模型做法优点缺点
fork-per-connection每来一个连接 fork 一个进程实现最简单，隔离最彻底fork 开销大；C10K 完全不可行。仅适合 sshd 这类低并发高隔离场景
prefork + 共享 listen fd启动时 fork N 个进程，都在同一个 listen fd 上 accept无运行时 fork 开销惊群；负载不均
prefork + accept 互斥锁同上，但抢锁后才 accept消除惊群锁成为瓶颈；这是 Nginx 早期的 accept_mutex
SO_REUSEPORT每个进程各自 bind 同一端口，内核按四元组哈希分发内核层面负载均衡，无锁无惊群，扩展性最好Linux 3.9+；进程退出时它队列里的连接会被重置
主进程 accept + 传 fd主进程 accept，通过 UDS 把连接 fd 发给工作进程可以按真实负载智能分发主进程成为单点和瓶颈
惊群（thundering herd）：N 个进程都在等同一个 listen fd，来了一个连接却把全部 N 个都唤醒，最终只有一个 accept 成功，其余 N-1 个白白被调度一遍又睡回去。高并发下这些无效唤醒会吃掉可观的 CPU。
惊群就像快递员在楼下喊一声「有快递」，整栋楼二十户全跑下来，只有一家有件。accept_mutex 相当于「约定每次只派一个人下去看」——不白跑了，但派人本身要排队协调。SO_REUSEPORT 则是每户一个专属信箱，按地址直接投递。
「Linux 早就没有惊群了」这句话只对了一半。阻塞在 accept 上的惊群从 2.6 起就解决了（走独占等待队列）；但现代服务用的是 epoll 监听 listen fd，epoll_wait 层面的惊群依然存在——除非用 EPOLLEXCLUSIVE（4.5+，只能在 EPOLL_CTL_ADD 时设，且只保证「不唤醒全部」）。完整方案是 SO_REUSEPORT 优先，其次 EPOLLEXCLUSIVE。

工程上还要处理的三件事

优雅重启
老进程收到 SIGTERM 后停止 accept、处理完手上的请求再退出；主进程同时用新二进制拉起新 worker。SO_REUSEPORT 下注意老进程 accept 队列里未处理的连接会被内核重置，要先 close listen fd 并留出排空时间。
崩溃自动拉起：退避是必需品，不是优化
主进程收 SIGCHLD（走 signalfd）后循环排干，正常退出不拉起、被信号杀死则重新 fork，并必须带指数退避——配置写错导致 worker 秒崩时，没有退避的主进程会变成一个 CPU 打满的 fork 死循环。可用参数：delay = min(100ms << min(n, 8), 30s)，连续崩 10 次放弃并告警，退避靠定时器而不要在回收路径里 sleep。最容易漏的是「活过 N 秒就重置崩溃计数」——否则每 5 分钟才 OOM 一次的 worker 会一路累加到「放弃拉起」，服务在没人注意的情况下容量减半；N 取「正常启动耗时的 10 倍」。
状态共享
「连接计数」「限流令牌」「缓存」这些原本是进程内变量的东西全要重新设计：放共享内存（快但要自己同步）、放 Redis（慢但简单）、或接受每进程独立（限流阈值除以进程数）。第三种最省事，但有精度损失。

SO_REUSEPORT 的写法与三个约束

每个 worker 各自创建 socket：socket → setsockopt(SO_REUSEPORT)（必须在 bind 之前） → bind → listen，之后主循环里就是最普通的 accept4(s, nullptr, nullptr, SOCK_NONBLOCK | SOCK_CLOEXEC)。错误分支里有一个要单独处理：EMFILE 时不能简单 continue，否则「连接还排在队列里、每次 accept 都失败」会变成 100% CPU 忙循环；经典做法是预留一个 fd，EMFILE 时关掉它、accept 一个、立刻 close、再重开。

约束说明写错的表现
必须在 bind 之前设内核在 bind 时决定要不要加入 reuseport 组bind 返回 EADDRINUSE——第二个 worker 起不来
组内所有 socket 的 euid 必须相同内核的防劫持检查：否则任何用户都能往别人的端口上「插」一个 socket 分走一半流量降权之后新起的 worker bind 失败。要么全部在降权后 bind，要么全部在降权前
不要和「继承 listen fd」混用一个进程如果既继承了父进程的 listen fd、又自己 bind 了一个，它会出现在同一端口的两个分发路径上负载严重不均，且很难想明白为什么
SO_REUSEADDR ≠ SO_REUSEPORT前者是「允许 bind 处于 TIME_WAIT 的地址」，和负载分发毫无关系以为设了就有多进程分发，实际还是第一个进程独占
SO_REUSEPORT 在长连接下的失衡
哈希按四元组算，只保证「同一个连接总落到同一个 worker」，不感知实际负载。短连接靠大数定律抹平；长连接则可能出现「worker 2 分到 3 个高频客户端 CPU 100%，其它三个各 20%」。缓解：给 reuseport 组挂 eBPF（SO_ATTACH_REUSEPORT_EBPF）自定义选择逻辑，或回到「主进程 accept + SCM_RIGHTS 传 fd」按真实负载分发。
优雅重启时的连接丢失
worker 退出时，已完成三次握手、排在它队列里但还没被 accept 的连接会被内核重置——客户端看到 connection reset 而不是干脆的连接失败，没法安全重试。稳妥的顺序：先让新 worker 加入 reuseport 组；老 worker 收到 SIGTERM 后 close listen fd 把自己摘出分发组，但先把队列里已有的连接 accept 干净；处理完存量请求再退出。

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础fork() 为什么会「返回两次」？父子进程共享什么、不共享什么？

    调用一次，内核创建了两个进程，两个都从这条系统调用返回——父进程拿到子进程 pid，子进程拿到 0。

    内核做了什么：copy_process 复制 task_struct、页表（标只读做 COW）、fd 表，然后把子进程「系统调用返回值寄存器」直接写成 0。两边都从同一条 syscall 的下一条继续执行，只是寄存器里的值不同。

    不共享：地址空间（COW）、pid、CPU 时间与资源统计、未决信号集（子进程被清空）、fcntl 记录锁、定时器、mlock、以及其它线程。

    共享：打开的 fd 指向同一个 struct file——fd 表本身是复制的（子进程 close 不影响父进程），但表项指向同一个内核对象，因此共享文件偏移量与状态标志。另外还共享内存映射的物理页（直到写入）与 MAP_SHARED 映射。见 fd 深入 · fork 后的 fd 共享。

    最常见的追问
    「fork 之后父子谁先执行？」——不确定，由调度器决定，任何依赖执行顺序的代码都是错的。历史上 Linux 曾倾向让子进程先跑（减少 COW 分裂），但那从来不是承诺。
    加分回答
    「一次调用两次返回」今天更像历史包袱：它把「创建进程」和「配置进程」硬绑在一起，代价是那段危险窗口、大内存进程的页表复制、以及和多线程的根本冲突。后来的系统给了不同答案：CreateProcess、posix_spawn、clone3 与 pidfd。说出「fork 的优雅是有代价的」比背返回值规则更能体现深度。
  2. 基础什么是僵尸进程和孤儿进程？各自有什么危害？

    僵尸进程：子进程已退出，父进程还没 wait 回收退出状态，内核必须保留 task_struct 存它，于是它以 Z 挂在进程表里。地址空间、打开的文件、栈在退出时就已释放——所以「不占内存」是对的，占的是一个条目和一个 pid。

    孤儿进程：父进程先退出，子进程还活着，本身没有危害，会被「最近的 reaper」收养并回收。reaper 不一定是 PID 1：进程可用 prctl(PR_SET_CHILD_SUBREAPER, 1) 声明自己是子树的收养者；PID namespace 里则是该 ns 的 1 号进程。

    怎么避免僵尸
    ① SIG_IGN / SA_NOCLDWAIT 让内核直接回收，代价是退出码全部丢失；② SIGCHLD 里 while (waitpid(-1, nullptr, WNOHANG) > 0); 循环排干——标准信号不排队，同时死 5 个只递送 1 次；③ 最优雅的是 signalfd / pidfd，变成 epoll 里的可读事件。
    怎么排查
    ps -eo pid,ppid,stat,comm | awk '$3 ~ /^Z/'，重点看 PPID——那才是要改代码的程序。判据是趋势而不是绝对值。另一个常见误操作是 kill -9 掉僵尸，它已经死了，信号无效。
    危害的量级
    pid 上限由 pid_max 决定（传统默认 32768），容器里还受 cgroup pids.max 限制。攒满之后整个系统或容器都 fork 不出新进程——连 ssh 都登不上、bash 执行任何外部命令都报 fork: Resource temporarily unavailable。
  3. 基础常见的 IPC 方式有哪些？各自适合什么场景？
    • 管道 / FIFO：字节流单向，简单；父子进程或 shell 管道。
    • socketpair：双向字节流，父子进程首选。
    • 消息队列：带边界、带优先级的消息；任务分发。
    • 共享内存：唯一的零拷贝方案；大块数据（图像、行情）。
    • 信号量 / 互斥量：不传数据，只做同步，配合共享内存用。
    • Unix 域套接字：本机通信的通用首选，双向、能传 fd、能拿对端 uid。
    • 信号：只能传一个编号，用于通知（退出、重载配置）。
    • eventfd：64 位计数器，最轻量，天然能进 epoll，共享内存的最佳搭档。
    • mmap 普通文件：既共享又持久化，适合多进程读同一份大只读数据（词典、模型权重、索引）。
    选型时问自己四个问题
    ①「要不要保留消息边界？」——要就划掉 SOCK_STREAM 和裸管道。②「能不能进 epoll？」——进不了就得多开线程阻塞等或轮询；共享内存正因这一条而从不单独使用。③「进程崩了会留下什么？」——fd 型由内核按引用计数回收，其余会留残留。④「将来要不要跨主机？」——要就从一开始用 UDS。
    选型口诀
    控制信令走 UDS，大块数据走共享内存，两者配合。分界线：单条消息小于几十 KB、或每秒不到一千条，就别上共享内存。
  4. 基础用管道时程序卡死在 read 上不动，最可能是什么原因？

    忘了关闭自己不用的那一端写端。管道的 EOF 条件是「所有写端的引用计数归零」，父进程只读却没 close(fd[1])，即使子进程退出了写端计数仍然是 1，read 永远等不到 0。

    反方向的坑
    所有读端关闭后继续 write，进程收到 SIGPIPE，默认直接终止进程。服务程序必须忽略它，改为靠 write 返回 EPIPE 判断。
    另一种卡死
    父进程「先写完全部输入再读输出」而子进程「边读边写」时，两根管道的 64 KB 缓冲都填满并互相等待——这正是 Python subprocess 文档反复警告要用 communicate() 的原因。正解是两个 fd 都设非阻塞丢进 epoll，同时驱动两个方向。
    怎么现场确认
    ① cat /proc/<pid>/syscall，首个数字是当前阻塞在哪个系统调用上（0 = read、202 = futex）；② ls -l /proc/<pid>/fd/ 拿到 pipe:[12345] 的 inode；③ 用它 grep 所有进程的 fd，列出来的就是所有还持有这根管道的进程。比 lsof 快，也不需要 root。

10.2 中级（区分熟练度）

  1. 中级什么是写时复制？fork 一个占用 10 GB 内存的进程，开销大吗？

    COW：fork 时内核不复制物理内存，只复制页表并把双方所有页标为只读；任一方写入时触发缺页异常，这时才复制那一页。

    开销并不是零，主要在两处：

    ① 页表复制
    10 GB 对应约 250 万个页表项，复制它们本身就要几十毫秒——这就是 Redis 做 RDB fork 时那根延迟毛刺。用大页能减少页表项数量，但会让 COW 粒度从 4 KB 变成 2 MB，写放大更严重。
    ② 后续的缺页与内存翻倍
    父子各自写入时不断触发缺页复制，最坏情况内存用量翻倍——所以 OOM 经常发生在 fork 之后一段时间，而不是 fork 那一刻。

    如果 fork 后马上 exec，页表复制纯属浪费，应该用 posix_spawn（内部走 CLONE_VM|CLONE_VFORK）。

  2. 中级为什么信号处理函数里不能调用 printf 或 malloc？正确的做法是什么？

    处理函数可能在任意两条指令之间被插入执行，包括 malloc 正在修改堆内部链表的中途。此时再调 malloc，它会看到不一致的堆——轻则数据损坏，重则死锁（glibc 的 malloc 锁不可重入）。printf 内部会 malloc，还有自己的 stdio 锁，同理不安全。

    POSIX 的 async-signal-safe 白名单只有约一百个系统调用级函数，名单外包括 printf 全家、malloc/new、std::string、几乎所有 C++ 标准库和日志库。

    正确做法
    ① 处理函数里只置一个 volatile sig_atomic_t 标志，工作放主循环；② 主循环阻塞在 epoll 上时感知不到标志（有竞态窗口），用 self-pipe trick；③ Linux 上最优解是 signalfd——先屏蔽信号再加进 epoll，信号成了普通可读事件，处理逻辑完全没有限制。
    还要记得
    处理函数里调系统调用会改 errno，进函数保存、出去前恢复；注册一律用 sigaction 而不是 signal。
  3. 中级共享内存里为什么不能存指针？要在共享内存里放一个链表怎么办？

    因为两个进程把同一块物理内存 mmap 到各自地址空间的不同虚拟地址。A 写入的 0x7f1122334455 是 A 的虚拟地址，B 解引用它指向的是自己地址空间里一个完全无关的位置——运气好是段错误，运气不好是静默的数据损坏。

    解法
    存相对于基址的偏移量，用的时候 base + offset 还原。链表的 next 存成 uint32_t offset；Boost.Interprocess 的 offset_ptr 把这层封装成了指针的样子。
    同样的原因
    共享内存里的对象不能有虚函数——vptr 指向本进程的虚表，跨进程调用直接跳飞。也不能直接放 std::string、std::vector，要用自定义分配器版本。
    可以强行固定地址吗
    理论上可以用 MAP_FIXED 让所有进程映射到同一虚拟地址，指针就能用了。但它在有 ASLR 的系统上很脆弱，地址一旦被占就直接失败。生产上不要这么干。
  4. 中级什么是惊群？SO_REUSEPORT 怎么解决它？

    惊群：N 个进程都在等同一个 listen fd，来了一个连接却唤醒全部 N 个，只有一个 accept 成功，其余白白被调度一遍。高并发下这些无效唤醒是实打实的 CPU 浪费和调度抖动。

    SO_REUSEPORT（Linux 3.9+）让多个 socket 各自 bind 同一端口，内核为每个 socket 维护独立的 accept 队列，新连接按四元组哈希直接投递，只有那一个进程被唤醒——没有惊群，没有锁，扩展性随核数线性增长。

    重要细节
    现代内核上，阻塞在 accept 的惊群早就解决了。但真实服务用的是 epoll 监听 listen fd，epoll_wait 层面的惊群依然存在——需要 EPOLLEXCLUSIVE（4.5+）或 SO_REUSEPORT。这是区分「背过八股」和「真做过」的一个点。
    SO_REUSEPORT 的代价
    哈希按四元组算，不感知实际负载——长连接下可能一个进程分到一堆重连接而另一个很闲。另外进程退出时它队列里排着的连接会被内核重置，优雅重启要先 close listen fd 并留出排空时间。

10.3 高级（体现深度）

  1. 高级多线程程序里调用 fork() 有什么风险？为什么 POSIX 说之后只能调 async-signal-safe 函数？

    fork 只复制调用它的那一个线程，其他线程在子进程里凭空消失，但它们持有的锁不会消失——锁的状态是内存里的一个值，被原样复制过去了。

    如果某个线程在 fork 瞬间正好持有 glibc malloc 的内部锁，子进程就继承了一把永远不会被释放的锁（那个线程在子进程里不存在），接下来任何一次内存分配都会永久死锁。

    这不是理论风险
    printf、new、std::string 构造、任何日志库背后都是 malloc。而且这种死锁是概率性的——本地测一万次不复现，上线跑几天挂一次。
    实践结论
    fork 之后立刻 exec，中间只调 close/dup2/setuid 这类 async-signal-safe 的调用。需要不 exec 的工作进程，就在启动早期、创建任何线程之前把它们全 fork 出来。pthread_atfork 管不到第三方库内部的锁，不要指望它。最省事的是直接用 posix_spawn。
  2. 高级SCM_RIGHTS 传文件描述符时，内核到底传了什么？有哪些实际用途？

    传的不是那个整数。fd 只是 fd 表的下标；内核实际做的是在接收进程的 fd 表里分配一个新槽位，指向同一个内核 file 结构体并把引用计数加一。所以接收方的 fd 编号通常不同，但共享同一个文件偏移量和状态标志。

    四类实际用途：

    连接分发
    主进程 accept 后按真实负载把连接 fd 发给最空闲的工作进程——比 SO_REUSEPORT 的哈希更智能。
    特权分离
    root 进程绑定 80 端口后把 listen fd 传给已降权的工作进程，systemd 的 socket activation 就是这个原理。
    零拷贝传大数据
    传 memfd_create 出来的匿名内存 fd，对方自己 mmap。Wayland 传帧缓冲、Android Binder、Chrome 的进程间图像传递都用这招。
    易错点
    ① 必须同时发送至少 1 字节普通数据；② 接收方没提供 msg_control 缓冲时内核会直接关掉那个 fd；③ 收到的 fd 属于接收进程，必须自己 close；④ 一次可传多个，缓冲要按 CMSG_SPACE(n * sizeof(int)) 算，开小了会拿到 MSG_CTRUNC。
  3. 高级设计一个「相机采集进程 + 算法进程 + UI 进程」的架构，进程间怎么通信？

    数据面走共享内存，控制面走 Unix 域套接字。

    数据面
    预分配 N 个槽位的共享内存环形缓冲，每槽一帧，相机 SDK 直接 DMA 到槽内存，全程零拷贝。控制头放两个进程间信号量做空位/满位计数，加 head/tail 与 magic+version 校验。N 取 3–4：太少会因抖动丢帧，太多只是徒增内存与延迟。
    控制面
    UDS（SOCK_SEQPACKET 拿现成的消息边界）传「第 k 号槽位就绪，帧号 t，曝光参数 …」这几十字节，以及启停、参数下发、结果回传，用 SO_PEERCRED 校验对端身份。
    失败处理（最容易被忽略的部分）
    ① 共享 mutex 用 robust 属性，算法进程崩溃时别人能拿到 EOWNERDEAD 并接管；② 每个槽位带「持有者 pid + 时间戳」，看门狗超时强制回收；③ 主进程走 signalfd 自动拉起，带指数退避；④ 相机进程要能丢帧而不是阻塞。
    为什么不全用一个多线程进程
    算法侧依赖大量第三方视觉库，一个段错误会带走整个程序包括 UI。拆进程后算法崩了 UI 还在，用户看到「本次检测失败，正在恢复」而不是程序消失。这就是隔离的价值。
  4. 高级容器里为什么需要 tini / --init？PID 1 有什么特殊之处？

    PID 1 在内核眼里有两个特殊性：

    ① 是所有孤儿进程的收养者
    父进程先死的进程会被挂到 PID 1 名下，PID 1 有义务 wait 回收。普通应用不写这个逻辑，于是容器里僵尸越攒越多，最终 pid 耗尽。
    ② 默认信号处理被禁用
    内核不会对 PID 1 执行信号的默认动作。应用没有显式注册 SIGTERM 处理时，docker stop 发来的 SIGTERM 会被直接丢弃——不是「没处理」，是根本不生效。Docker 等 10 秒后只能上 SIGKILL。

    tini / dumb-init 做的就是这两件事：循环 waitpid 回收孤儿；把收到的信号转发给整个进程组。docker run --init 就是自动注入 tini。

    还有一个坑
    ENTRYPOINT 写成 shell 形式（CMD java -jar app.jar）时 PID 1 是 /bin/sh，你的应用是它的子进程——sh 不转发信号，结果一样。要用 exec 形式，或在脚本里 exec java … 让应用顶替 shell 成为 PID 1。
