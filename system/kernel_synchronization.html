内核同步原语与 RCU

本站的 C++ 内存模型与 并发深入讲的是用户态的内存序与并发，Linux 设备驱动里只用一小节点到了驱动里的竞态。这篇讲内核态的同步——它和用户态的根本差别在于：你的代码可能跑在中断上下文（绝对不能睡眠）、可能被内核抢占打断、要面对 SMP 真并行与 CPU 乱序，而且一个死锁不是进程挂了，是整机 hang。

01

内核并发从哪来

四个并发源，决定了锁的种类

用户态并发只需要 mutex + atomic，前提是永远可以睡眠。内核这个前提不成立：同一函数可能跑在进程上下文（可睡）、硬中断（绝不能睡）、或已经持着自旋锁（原子上下文，一睡整机 hang）。锁的种类多，不是喜欢造轮子——四个并发源必须用不同手段挡住。

用户态像办公室协作：等打印机可以去喝咖啡。内核像急诊值班：救护车随时把你从病历夹边叫走。拿着病历夹去睡觉，下一个找夹子的人只能干等到天亮——还堵着电梯（自旋烧 CPU）。

1.1 四个并发源

上下文：这段代码跑在什么身份。进程上下文有 current，可睡；中断上下文借当前任务栈，不能睡（睡了就把无关任务永久挂起）；原子上下文是 preempt_count != 0 的任何时刻（持自旋锁、关中断/抢占、在中断里），同样不能睡。
preempt_count：把抢占/软中断禁用层数、硬中断/NMI 嵌套压在同一个 32 位数里。in_atomic() / might_sleep() 都读它。能不能睡，本质是问这个数是不是 0。

1.2 谁能打断谁

选锁只有一句：先问「这份数据会被谁访问」，能打断就必须挡住它。关中断挡不住另一个 CPU——那是新手最常犯的错。

1.3 中断与进程共享队列

驱动最常见的结构：ISR 把包挂进链表，read() 取走。进程侧只用 spin_lock 时，同 CPU 上的硬中断再抢同一把锁就是死锁——持锁者被挂起、永远回不去解锁。

PREEMPT_RT 会改变这里的部分规则。在实时内核上，spinlock_t 被换成了可睡眠的 rt_mutex，持有它不再禁止抢占；真正的「关抢占自旋锁」变成了 raw_spinlock_t。中断处理程序默认也被线程化。所以 RT 上「持 spinlock_t 时能不能 kmalloc(GFP_KERNEL)」的答案和主线内核相反。写通用驱动时按主线内核的严格规则写（不睡眠、临界区短），在 RT 上一定是安全的；反过来不成立。详见 PREEMPT_RT 深入。
02

原子操作与 READ_ONCE / WRITE_ONCE

最便宜的同步，和编译器的一场博弈

共享的只是计数器或标志位时，一条 CPU 指令就能原子改完，加锁是浪费。内核给两套：atomic_t，以及比锁更基础、评审里最常被抓的 READ_ONCE() / WRITE_ONCE()。

2.1 atomic_t 与常用 API

atomic_t：包了一层结构体的 int，故意让你没法 ++、必须走 atomic_*()。32 位有符号；64 位用 atomic64_t。引用计数不要手搓——用 refcount_t，溢出和「从 0 复活」会 WARN 并饱和，atomic_t 上这两种是静默 UAF。

无返回值 RMWatomic_inc / set_bit是无序。要序就配 smp_mb__before_atomic() / _after_atomic()

2.2 READ_ONCE / WRITE_ONCE：不是「再读一次」

READ_ONCE 禁止的是撕裂和编译器优化，不是「提醒你再读一遍」。普通变量轮询在 C 抽象机里，循环体内没人改 ready，编译器有权把多次读提成一次——数据竞争是 UB，它有权假设不存在。

❌ 普通变量轮询

while (!ready); → 编译器可提成 if (!ready) for (;;);

这不是编译器 bug。给变量加 volatile 更糟：不产生 CPU 屏障（ARM 上 ready==1 但 data 仍旧）、把锁内本可进寄存器的访问也关掉、掩盖「哪一次才必须真读」。合法用途基本只剩 jiffies 和 MMIO（后者用 readl/writel）。

✅ 访问点表达意图
static int ready;

void wait_for_peer(void)
{
    while (!READ_ONCE(ready))
        cpu_relax();      /* 超线程让路；勿依赖它的 memory clobber */
    smp_rmb();            /* ★ 还要屏障，见 §3 */
    consume();
}

void peer_done(void)
{
    fill_data();
    smp_wmb();
    WRITE_ONCE(ready, 1);
}

加分：READ_ONCE 是访问点标记，volatile 是类型属性。追问「能替代屏障吗？」——不能。齐全但缺 smp_rmb() 的代码在 x86（TSO）上能跑一万年，换 ARM64 立刻炸。
03

内存屏障

屏障永远成对出现

乱序有两层：编译器（挡它的是 barrier()，不产生指令）和 CPU（store buffer、推测执行；挡它的是 mfence/dmb）。x86-64 是 TSO，只允许「写→读」重排，所以 smp_rmb()/smp_wmb() 在 x86 上是纯编译器屏障、零指令——缺屏障的 bug 到 ARM64 / POWER 才炸。

屏障像快递「先封箱再贴单」。仓库为了效率会打乱工序；下游按面单取货，单子贴了箱子还空着就会拿到空箱。写侧 release = 封好才能贴单；读侧 acquire = 看到单才能开箱。只管仓库不管取货方，推测执行照样偷看。

3.1 内核屏障 API

3.2 铁律：屏障总是成对出现

一个屏障单独存在几乎总是 bug。写侧 release 必须对上读侧 acquire。看到孤零零的 smp_mb()，第一反应是「它的对儿在哪」。

最经典的成对是发布—订阅：先填对象再发指针。RCU、延迟初始化、模块加载都是它。图已经画清两侧缺一的后果，下面只留配对写法：

/* 写侧：发布一个新的配置对象 */
struct cfg *newc = kzalloc(sizeof(*newc), GFP_KERNEL);
if (!newc)
    return -ENOMEM;
newc->timeout = 500;
newc->retries = 3;
smp_store_release(&dev->cfg, newc);   /* ★ 发布：内容先于指针可见 */

/* 读侧：热路径取配置 */
struct cfg *c = smp_load_acquire(&dev->cfg);  /* ★ 订阅 */
if (c && now - start > c->timeout)
    handle_timeout(c->retries);
/* 老写法：smp_wmb()+WRITE_ONCE / READ_ONCE+smp_rmb()，弱序架构上更贵 */
控制依赖不可靠。「有 if (q) 就不会提前读 q->len」——会。分支预测把 load 先发出去。读侧控制依赖对 load 不构成顺序保证。别用它，用 acquire。地址依赖由 READ_ONCE/rcu_dereference 保证；Alpha 退场后 smp_read_barrier_depends() 已删。

04

spinlock 家族

忙等的锁，和「绝不能睡」这条红线

自旋锁：拿不到就不睡、不让出 CPU，循环直到拿到。意义是省掉睡眠-唤醒两次切换（几微秒），代价是等待时 CPU 空转。只适合极短临界区，也是中断上下文里唯一能用的锁。
mutex 像银行取号：可以去买咖啡。自旋锁像等自动门——对方两秒就出来，去买咖啡更慢。里面的人睡午觉，门口整层楼堵死。

4.1 持锁期间绝不能睡眠

为什么持自旋锁不能睡

  • 别人在烧 CPU 等你。自旋锁的前提是等待极短；睡眠直接摧毁它。
  • 同 CPU 真死锁。spin_lock() 含 preempt_disable()。强行 schedule() 后，同核另一个要这把锁的任务自旋，持锁者又需要这个 CPU 才能醒。互等，这个核死了。
  • 中断上下文没有「睡眠」这个概念。ISR 借无关任务的栈，不是可调度实体。让它睡 = 把那个任务永久挂起。内核直接 BUG。

CONFIG_DEBUG_ATOMIC_SLEEP 下，might_sleep() 在 preempt_count != 0 时立刻打 BUG: sleeping function called from invalid context；没开则更晚看到 scheduling while atomic，末尾十六进制就是 preempt_count。

临界区里这些函数会睡，一律不能出现在 spin_lock 内

  • kmalloc(..., GFP_KERNEL) / vmalloc() → 换成 GFP_ATOMIC（能不在锁里分配就别分配）
  • copy_to_user / copy_from_user、 mutex_lock / down / wait_event / synchronize_rcu、 msleep / cond_resched
  • printk 洪水（不睡，但临界区拖到毫秒级）；以及没读过实现的第三方内核函数

4.2 变体：和谁竞争，就关谁

❌ spin_unlock_irq 破坏调用方

inner() 里 spin_lock_irq / spin_unlock_irq；outer() 已 local_irq_save 再调 inner()——回来时中断被无条件打开。两个函数各自正确，组合起来错，且零警告。

✅ inner 一律 irqsave

spin_lock_irqsave(&dev->lock, flags); … spin_unlock_irqrestore(&dev->lock, flags); 恢复到进来时的状态，任意上下文可调。代价一条读标志寄存器。驱动里不要用 _irq。

flags 必须是局部变量。见过有人把它放进结构体里「共享」——那就成了两个 CPU 互相覆盖对方保存的中断状态，恢复出来的值完全随机。同理，flags 不能跨函数传递给另一个上下文去 restore。它就是一个纯粹的栈上临时值。

4.3 实现演进：MCS 排队，别贴实现

自旋锁史是一部公平性 vs cacheline 争用的斗争史。

qspinlock：x86 从 4.2 起的默认 spinlock_t。基于 MCS——每人把 per-CPU 本地节点挂到队尾，只自旋在自己那条缓存行上；释放只写下一个节点。无争用与 test-and-set 一样快，高争用是 O(1) 且 FIFO。

4.4 临界区要短

无争用 lock+unlock ~10–20 ns；争用一次传递 50–200 ns（跨 socket 再乘 2–5）；上下文切换 1–5 μs。自旋只要低于切换就划算。争用是超线性放大的：临界区拉长 10 倍，撞锁概率也涨约 10 倍，核数越多吞吐掉得越狠。把一次 kfree 移出锁外，不是抠 100 ns，是掐掉会随核数爆炸的争用点。

缩短临界区

  • 分配/释放挪锁外：锁内只挂链/摘链
  • 锁内只搬指针；拆锁（哈希桶 / 每队列 / per-CPU），多锁必须定死顺序
  • 读多写少换 seqlock / RCU；只是计数换 per-CPU。把锁优化到极致不如把锁去掉。
rwlock_t 基本弃用：读侧也要写读者计数（仍争一条 cacheline），写者可能饿死，中断里再读会死锁。读多写少用 RCU 或 seqlock。
05

可睡眠锁：mutex / rwsem / semaphore

临界区长的时候，让出 CPU 才是对的

临界区可能长于一次上下文切换（微秒）时，睡下去把 CPU 让出才划算。硬条件：只能在进程上下文用。

5.1 mutex：能用就用它

乐观自旋：mutex_lock 拿不到时不立刻睡。owner 正在另一个 CPU 上跑，就先自旋一会儿（自旋者自己排 MCS 队列）；owner 被切走或自旋太久才睡。短临界区接近自旋锁，长临界区保留睡眠语义。

系统调用路径优先 mutex_lock_interruptible（可被 Ctrl-C 打断）。不可递归、必须持有者本人解锁、中断里用 = BUG。

判据选 spinlock选 mutex
调用上下文任意（中断里只能选它）只能进程上下文
临界区里会不会睡绝对不能可以：GFP_KERNEL、copy_to_user
临界区长度< 1 μs 级可能超过微秒，或长度不可控
死锁形态整机 hang，靠 lockdep任务卡在 D 状态，hung task 打栈
默认怎么选必须在中断/原子上下文才被迫用能用 mutex 就用 mutex
第一判据是上下文，不是长短。数据会被中断访问 → 无论多长只能 spinlock（并做短）；临界区必须 copy_to_user → 无论多短只能 mutex。长短只在两者都合法时才轮到。

5.2 rwsem / semaphore / completion

down_read 多读者并发，down_write 独占。典型用户：mmap_lock、文件系统 i_rwsem。「读多、写少、临界区可能很长」。5.x 加了 handoff（写者等太久就预定锁，新读者不能插队），饥饿压到可接受。仍不适合写侧也有一定频率的热点。

读写锁在「读多」时可能比互斥更慢：读侧也要原子改读者计数，32 核就是 32 次争同一条 cacheline。临界区工作量必须显著大于一次 cacheline 迁移，读写锁才有意义。

要互斥

mutex。有 owner、能乐观自旋、lockdep 全支持。99% 的场景。

要等一个事件

completion（一次性，complete() 可在中断里调）或 wait_event_interruptible()。都要考虑超时和信号。

要限制并发为 N

struct semaphore 几乎只剩这个用途。互斥不要再用它：无 owner、不能乐观自旋、lockdep 弱。

06

seqlock 与 per-CPU 变量

两种把读侧成本压到接近零的思路

§4 的结论：读写锁在读侧极热时是负优化（读侧也要写 cacheline）。两条绕开的路：seqlock 读侧一个字都不写，靠版本号重试；per-CPU 让每个 CPU 有自己的一份，从根上消灭共享。

6.1 seqlock：读侧无锁重试

seqlock：序号 + 自旋锁。写者拿锁并把序号加一（变奇数），改完再加一（变偶数）。读者完全不写：读序号 → 读数据 → 再读序号；两次不同或第一次是奇数就整段重读。
seqlock 最典型的一个生产用例就在你每次调 clock_gettime 时跑：vDSO 的共享数据页（内核写、所有进程读）正是用 seqlock 保护的——读多写少、且读者绝对不能阻塞写者（否则内核更新时间就会被用户态卡住）。展开见 时间与时钟 · vDSO。
seqlock 像抄翻页车次牌：先看「更新中」灯，抄完再看灯有没有闪过。没闪就是一致的一屏；闪过就整屏重抄。抄的人从不碰牌子，一百人同时抄也不互相干扰。

写侧：write_seqlock / write_sequnlock（中断里用 _irqsave）。读侧：do { seq = read_seqbegin(); 拷到局部; } while (read_seqretry());——循环内可能读到撕裂态，只能拷贝，绝不能决策或解引用。

seqlock 的使用边界（每一条都是踩过的坑）

  • 读侧必须可安全重跑：无副作用。循环内数据可能撕裂，只能拷到局部，通过后再用。
  • 绝不能读到指针就解引用——可能是半新半旧野值，oops 发生在 read_seqretry 有机会说话之前。含指针的结构用 RCU。
  • 写极少（读者几乎撞不上）；拷贝字段越多重试越频。写侧自带自旋锁，不能睡。
甜点是 timekeeping：clock_gettime 每秒可能百万次，写侧只在时钟中断里更新。读侧零写入，几十个核互不影响。

6.2 per-CPU：无锁是因为根本不共享

per-CPU 变量：每个 CPU 一份副本，各自只碰自己的。不需要锁、原子、屏障——唯一要防的是访问期间被抢占/迁移到别的 CPU。不是把锁做快，是把共享消灭掉。
per-CPU 像每个收银员自己的钱箱：收钱零争用；店长要总额必须挨个箱子数，而且永远是近似值。

三个代价：① 内存放大（256 核 = 256 份）；② 汇总不便宜（监控每秒采一次 = 每秒 256 次跨 NUMA miss）；③ 拿不到一致快照。「精确总数等于 0 才能释放」别用它。
「不是把锁做快，是把共享消灭掉」在用户态是同一本账。高并发服务里最典型的三个跨核弹跳点——shared_ptr 的引用计数、被多个 worker 共享的连接表、挤在同一条 cache line 上的统计计数器——以及 shared-nothing 分片之后它们怎么整个消失，见 IoT 接入网关架构设计 §6。判据：代码跑在内核态（驱动、模块、内核路径）用本篇的原语；跑在用户态的服务端程序，那边讲的是同一个硬件效应在 C++ 侧的形态与代价。

RCU 原理

读侧零开销，代价全给写侧

RCU 解决「读极热、写极少、读侧还常在不能睡的上下文」：路由表、模块列表、fd 表、SELinux 策略。rwsem 不能进中断，rwlock 读侧要写 cacheline，seqlock 不能保护含指针的结构。

RCU 的核心交易是：让读者永远不阻塞、不重试、甚至一条同步指令都不执行；把全部代价转移给写者——写者必须做拷贝，还必须等待一段「宽限期」才能释放旧数据。读写比例是 1000:1 时，这笔交易划算得离谱。
RCU 像换公告板：旁边做好新通知，箭头一挪（原子指针替换）。正在看旧通知的人不受影响；新来的人看到新的。旧通知不能立刻撕掉——等到「换箭头前就开始看的人都走了」，这段等待就是宽限期。

7.1 读侧为什么能做到零开销

rcu_read_lock() 不是一把锁：不互斥、不失败、不阻塞。它只标记「我正在读」，好让写者判断宽限期结束了没有。非抢占内核里展开成 preempt_disable()，某些配置下几乎零指令。抢占式内核可读侧被抢占，要记账嵌套计数，但对使用者行为一致：不阻塞、不失败、不能主动睡眠。读侧：rcu_read_lock(); c = rcu_dereference(p); use(c->field); rcu_read_unlock();——只能把值带出临界区。

宽限期：从指针替换到「所有在替换前已进入读侧的读者都退出」。之后再也没有任何路径能拿到旧指针。它不等新读者，也不需要知道有哪些读者——这才是读侧零开销的原因。
静止状态：一个 CPU 此刻肯定不在任何 RCU 读侧临界区。非抢占内核里，上下文切换 / idle / 返回用户态即证明。宽限期 = 等每个 CPU 都经过一次。内核死循环不让出 → RCU stall（§8）。

7.2 三件套：发布、订阅、宽限期

动作API它保证什么对应 §3 的什么
发布rcu_assign_pointer(p, v)把新对象的内容先于指针发布出去。读者一旦看到新指针，就一定能看到完整初始化的对象写侧 smp_store_release()
订阅rcu_dereference(p)取指针，并保证后续通过这个指针的解引用不会被提前到取指针之前（地址依赖序）；同时带 lockdep 检查「你真的在读侧临界区里吗」读侧的地址依赖 + READ_ONCE()

7.3 写侧模式与完整代码

「Read-Copy-Update」这个名字就是写侧的流程：拷贝一份 → 改副本 → 原子替换指针 → 等宽限期 → 释放旧的。注意 RCU 不解决写者之间的互斥——多个写者并发时仍然需要一把普通的锁（spinlock 或 mutex）把它们串起来。

/* ══ 模式一：整体替换一个配置对象 ═══════════════════ */
static struct cfg __rcu *g_cfg;
static DEFINE_MUTEX(cfg_mutex);          /* ★ 写者之间的互斥，RCU 不管这个 */

static int cfg_set_timeout(u32 t)
{
    struct cfg *old, *new;

    new = kmalloc(sizeof(*new), GFP_KERNEL);
    if (!new)
        return -ENOMEM;

    mutex_lock(&cfg_mutex);
    old = rcu_dereference_protected(g_cfg, mutex_is_locked(&cfg_mutex));
    *new = *old;                          /* ① Copy */
    new->timeout = t;                     /* ② Update（改副本，读者看不见）*/
    rcu_assign_pointer(g_cfg, new);       /* ③ 原子发布，含 release 语义 */
    mutex_unlock(&cfg_mutex);

    synchronize_rcu();                    /* ④ 等宽限期（会睡！只能在进程上下文）*/
    kfree(old);                           /* ⑤ 现在没人能引用 old 了 */
    return 0;
}

/* 读侧（可以在软中断、可以在 NAPI poll 里）： */
static u32 cfg_timeout(void)
{
    struct cfg *c;
    u32 t;

    rcu_read_lock();
    c = rcu_dereference(g_cfg);
    t = c ? c->timeout : DEFAULT_TIMEOUT;
    rcu_read_unlock();
    return t;                             /* ★ 只能把【值】带出去，绝不能把 c 带出去 */
}

7.4 synchronize / call_rcu / kfree_rcu

API行为上下文用它的时候
synchronize_rcu()阻塞等宽限期只能进程上下文；不能在读侧调低频配置变更、模块卸载。可能阻塞毫秒到几十毫秒
call_rcu立刻返回，宽限期后回调几乎任何上下文写侧不能睡；释放逻辑不只是 kfree。回调在软中断，不能睡；模块 exit 前必须 rcu_barrier()
kfree_rcu宽限期后自动 kfree同 call_rcu释放就是一次 kfree 时的首选，不需要 rcu_barrier
rcu_barrier()等已排队回调跑完进程上下文模块 exit。不等于 synchronize_rcu
synchronize_rcu_expedited()IPI 催静止状态进程上下文真等不了才用；会打扰所有 CPU，别随便开
能用 kfree_rcu 就用它；逻辑复杂用 call_rcu；必须确认旧对象彻底没人用才 synchronize。第三种远比想象的少。
RCU 保护查找，引用计数保护使用：临界区里 refcount_inc_not_zero() 再出临界区。必须用 _not_zero，计数已是 0 不能复活。
08

RCU 的边界与陷阱

它不是万能的，而且失效方式很隐蔽

8.1 适用与不适用

✅ 三个前提，缺一不可
  • 读远多于写（至少 10:1，理想 100:1）。写侧拷贝 + 等宽限期，比加锁贵。
  • 能容忍稍旧的数据（路由表、配置、回调列表晚几毫秒无害）。
  • 对象可以延迟释放。宽限期毫秒级，对象大或持稀缺资源会耗尽。
❌ 不要用 RCU
  • 必须看到最新值（权限策略收紧后不能还用旧策略放行）。
  • 写侧也很热（计数器、队列头尾每次都改）。
  • 要立刻确认生效→ 只能 synchronize_rcu，付阻塞代价。
  • 读侧要睡眠→ SRCU，见下。

8.2 陷阱一：读侧睡眠是核弹

普通 RCU 读侧不能主动睡眠：mutex_lock、GFP_KERNEL、copy_to_user、synchronize_rcu 一律禁止。

SRCU 不只是「能睡」。普通 RCU 全局：任一 CPU 长时间不让出，拖长所有人的宽限期。每个 srcu_struct 是独立域——读侧临界区可能很长，也是选它的理由。代价：读侧不再零开销。

8.3 陷阱二：call_rcu 洪水导致 OOM

call_rcu() 立刻返回，释放进队列。回调产生快于宽限期推进时，队列无限涨——内存被一堆「已经没人用、还没被释放」的对象吃光。OOM killer 杀谁都救不回来：内存不在任何进程账上。

❌ 每条都 call_rcu

清空百万级 conntrack / 路由表时循环 list_del_rcu + call_rcu。内核 qhimark（默认 10000）会加速宽限期——缓解不是解决：从必定 OOM 变成 CPU 尖峰 + 延迟抖动。

✅ 一批只等一次宽限期

先把整批摘到本地 dead 链表（或 list_splice_init_rcu），一次 synchronize_rcu()，再统一 kfree。观测：rcudata 的 qlen 稳定在几万就是确诊。低延迟用 rcu_nocbs= 把回调卸到 rcuo 线程。

8.4 陷阱三：读懂 RCU stall 报错

宽限期超过阈值（默认 21 秒，rcupdate.rcu_cpu_stall_timeout）会打 stall。生产里很常见，它报的往往不是 RCU 的 bug，而是「有人在内核里赖着不走」。

09

死锁排查与竞态检测

别靠压测和运气

同步 bug 概率极低、后果极重、现场难留。工程实践不是「写完压测」，而是打开运行时验证，让 bug 第一次跑到就暴露。

9.1 lockdep：不需要真死锁就能发现死锁

lockdep（CONFIG_PROVE_LOCKING）：不检测「现在死锁了」，而是检测「这套加锁模式在某种时序下可能死锁」。每个锁归一个锁类，运行时记录「持有 A 时获取 B」的有向图；新边成环立刻报警。同时记录上下文（硬中断 / 开中断），抓 §1.3 那种不一致。
真死锁要两个 CPU 恰好交错；lockdep 只要两条路径各自跑过一次。概率性 bug 变成覆盖率问题。

9.2 读 lockdep 报告：循环依赖

报告里看什么含义

9.3 KCSAN：找出「没有锁保护」的访问

lockdep 查锁对不对，KCSAN 查这个变量到底有没有被保护：编译器插桩 + 采样 watchpoint，无同步的并发访问就报。修法不一定是加锁——统计计数器用 READ_ONCE/WRITE_ONCE 即可，那是给人和工具看的意图声明；KCSAN 把它们和 atomic_* 当作已标注，不再报警。

KCSAN / KASAN / lockdep 分工

  • lockdep：锁的顺序与上下文 → 死锁风险。
  • KCSAN：缺同步的并发访问 → 数据竞争。lockdep 看不见「压根没加锁」。
  • KASAN：越界 / UAF / double-free，带分配栈+释放栈。RCU 延迟释放让 UAF 推迟很久才暴露——调 RCU 相关 UAF，KASAN 几乎是唯一有效手段。
  • 三者可同开，都很慢，不上生产。

前面几样都需要提前编译进内核。生产内核上默认开着的是三个「兜底」检测器，它们不告诉你原因，但会在系统已经出问题时保住现场。

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础为什么持有自旋锁期间绝对不能睡眠？

    三层理由，从「性能差」到「必然死锁」：

    ① 别人在烧 CPU 等你
    自旋锁的等待者不睡觉，就在循环里空转。你睡 5 ms，其他等锁的 CPU 就空转 5 ms——几百万条无用指令，还伴随持续的 cacheline 争用。自旋锁的全部前提是「等待极短」，睡眠直接摧毁这个前提。
    ② 同 CPU 上会真死锁
    spin_lock() 在主线内核里包含 preempt_disable()，睡眠会强行 schedule()。调度器可能选中同一个 CPU 上另一个也要这把锁的任务——它拿不到锁（持锁者在睡）于是自旋，而持锁者需要这个 CPU 才能醒过来继续跑。互等，这个 CPU 死了。
    ③ 中断上下文没有「睡眠」这个概念
    中断处理程序借用某个无关任务的内核栈，它不是可调度实体。让它睡 = 把那个倒霉任务永久挂起，而且没有任何人会来唤醒「这个中断」。
    怎么被发现
    开 CONFIG_DEBUG_ATOMIC_SLEEP，可能睡眠的函数入口的 might_sleep() 会在 preempt_count != 0 时打印 BUG: sleeping function called from invalid context。不开的话你看到的会是更晚更难懂的 BUG: scheduling while atomic——那行末尾的十六进制数就是 preempt_count。
    最容易踩的几个「隐形睡眠」
    kmalloc(GFP_KERNEL)（要换 GFP_ATOMIC）、copy_to_user（可能缺页）、mutex_lock、synchronize_rcu、msleep。以及任何你没读过实现的第三方内核函数——这是最现实的一条。
  2. 基础spin_lock / spin_lock_bh / spin_lock_irq / spin_lock_irqsave 怎么选？为什么 irqsave 比 irq 更安全？

    选择依据只有一句：和谁竞争，就关谁。先把所有会访问这份数据的代码路径列出来，看它们跑在什么上下文：

    • 只有进程上下文（多 CPU 的系统调用/内核线程）→ spin_lock()（只需挡住其他 CPU + 本 CPU 抢占）
    • 还会被软中断 / tasklet / NAPI 访问 → 进程侧 spin_lock_bh()
    • 还会被硬中断处理程序访问 → 进程侧 spin_lock_irqsave()
    • ISR 自己那一侧用 spin_lock() 就够——它已经在关中断的状态下运行
    irqsave vs irq
    spin_unlock_irq() 是无条件打开中断；spin_unlock_irqrestore() 是恢复到进来时的状态。差别在于「函数被谁调用」：如果上层调用者本来特意关了中断，你用 _irq 版本就会在返回时把中断悄悄打开，破坏上层的保护——而且不产生任何警告，只表现为极低概率的数据损坏。
    结论
    irqsave 的代价只有一条读标志寄存器的指令，换来的是「这个函数可以被任何上下文安全调用」这个可组合性。驱动里一律用 irqsave。spin_lock_irq() 只在「能确定调用者一定是开着中断的顶层路径」时才合法，内核核心代码里有这种用法是因为那里的调用关系被严格审过。
    容易漏的一条
    同一种软中断在同一个 CPU 上不会重入，但在不同 CPU 上可以并发。所以多队列 NAPI 的 poll 函数之间访问共享数据，仍然需要 spin_lock()——「都是软中断所以不用锁」是错的。
  3. 基础READ_ONCE() / WRITE_ONCE() 为什么必须存在？直接用 volatile 不行吗？

    因为编译器对普通内存访问的优化权力比大多数人想象的大，而这些优化在单线程语义下全都合法。最经典的例子：

    while (!ready)      /* ready 由另一个 CPU 置 1 */
    ;
/* 编译器可以合法地变成：
     if (!ready) for (;;) ;     ← 永久死循环
   因为循环体内没有任何东西修改 ready，
   「每次重新读」是可以省掉的。 */

    除了这种合并读，编译器还会做：合并/删除写（状态机丢一步）、读撕裂（把 64 位读拆成两个 32 位读，拼出一个从未被写过的值）、写撕裂、凭空多读（寄存器不够用时把值丢掉重读一遍，导致「先检查后使用」两次读到不同值）。READ_ONCE/WRITE_ONCE 的本质就是一次带 volatile 语义的访问，用来禁止这一类变换。

    为什么不用 volatile 变量
    ① 解决不了真正的问题——volatile 不产生任何 CPU 屏障，在 ARM 上照样会读到 ready==1 但数据是旧的；② 把优化全面关掉——这个变量的所有访问都变 volatile，包括已经在锁里、本可以放寄存器的那些；③ 掩盖意图——看代码的人无法知道哪次访问是「真的要求每次都读」。内核文档 volatile-considered-harmful.rst 明确不建议这么做。
    必须记住的一条
    READ_ONCE 不是屏障。它只挡编译器，不挡 CPU 乱序。「READ_ONCE 齐全但没有 smp_rmb()」的代码在 x86 上（TSO，读读不重排）能跑一万年不出错，换到 ARM64 上立刻炸。这是国产 ARM 服务器普及后大量存量代码暴露出的真实问题。
    反过来也要注意
    已经在锁保护下的访问不需要 READ_ONCE——锁的 acquire/release 已经包含编译器屏障。滥用它会让评审者误以为「这里有无锁并发」。
  4. 基础RCU 里的「宽限期」是什么？为什么需要它？

    宽限期（grace period）：从「写者完成指针替换」这一刻算起，到「所有在替换之前就已经进入读侧临界区的读者都退出」为止的这段时间。

    为什么需要它：RCU 的读者不加锁、不阻塞，所以写者替换指针的那一刻，可能有一堆读者手里正拿着指向旧对象的指针在读。写者不能立刻 kfree 旧对象——那就是 use-after-free。它必须等到「确信再也没有人能引用旧对象」为止，这个等待就是宽限期。

    关键：它不需要等谁
    宽限期只需要等「跨越了替换点」的那些读者。替换之后新进入的读者只能看到新指针，本来就拿不到旧对象，不必等。而且写者完全不需要知道到底有哪些读者——正是这一点让读侧可以做到零记账、零开销。
    怎么判断宽限期结束
    靠静止状态（quiescent state）——一个 CPU「此刻肯定不在任何 RCU 读侧临界区里」的可判定时刻。非抢占内核里读侧临界区是关抢占的，所以一次上下文切换、进入 idle、返回用户态都足以证明。宽限期的实现就是等每个 CPU 都至少经过一次静止状态。
    由此推出两个实用结论
    ① 宽限期是毫秒量级（要等所有 CPU 都过一次静止状态），所以 synchronize_rcu() 不能放在热路径上；② 「有 CPU 一直在内核里不让出」会让宽限期永远结束不了——这就是 RCU stall 报错的来源，也是为什么长循环里要插 cond_resched()。

10.2 中级（区分熟练度）

  1. 中级为什么说「内存屏障总是成对出现」？只在写侧加屏障会怎样？

    因为屏障约束的只是「同一个 CPU 上，我自己的访问之间的顺序」。写侧的 smp_wmb() 保证「我发出去的写，对外可见的顺序是 A 先于 B」；但它管不到读侧的 CPU——读侧的 CPU 完全可以推测执行，提前把 B 读了，之后才去读 A。那么读侧看到的仍然是「B 新 A 旧」，写侧的努力白费。

    标准的成对模式是发布-订阅：

    /* 写侧 */
p->len = 4096;
p->data = buf;
smp_store_release(&gp, p);   /* ① 保证内容先于指针可见 */

/* 读侧 */
q = smp_load_acquire(&gp);   /* ② 保证拿到指针后才读内容 */
if (q)
    use(q->len, q->data);

    只有 ① 没有 ②：读侧 CPU 提前读了 q->len（旧值/垃圾），之后才确认 gp。只有 ② 没有 ①：写侧的 gp 先落地，p->len 还在 store buffer 里，读者拿到指针读到未初始化的内容。两种情况的结果一样糟。

    配对关系
    smp_store_release ↔ smp_load_acquire；smp_wmb ↔ smp_rmb；rcu_assign_pointer ↔ rcu_dereference（RCU 就是这个模式的一个特化）。看到代码里一个孤零零的 smp_mb()，第一反应应该是「它的对儿在哪」。
    不要指望控制依赖
    「读侧有 if (q) 判断，CPU 总不能在不知道 q 是否为 NULL 时就读 q->len 吧？」——它真能。分支预测 + 推测执行会先把 load 发出去，预测错才回滚。控制依赖对后续的 load 完全不构成顺序保证。（地址依赖是另一回事，那个由 READ_ONCE/rcu_dereference 保证。）
    为什么在 x86 上测不出来
    x86-64 是 TSO，只允许「写→读」这一种重排。所以 smp_rmb()/smp_wmb() 在 x86 上编译成纯编译器屏障、零指令——少写一个完全没影响。到 ARM64 / POWER 上立刻暴露。写内核同步代码必须按最弱的内存模型思考，不能按测试平台。内核有形式化模型和 tools/memory-model/ 下的验证工具可以帮你判断。
  2. 中级seqlock 的读侧有哪些限制？为什么不能在读侧读到一个指针就解引用？

    seqlock 的读侧模型是「读序号 → 读数据 → 再读序号，不等就整段重试」。它的所有限制都来自这个模型的两个事实：读侧临界区可能被执行多次，而且期间读到的数据可能是撕裂的、互相矛盾的。

    • 必须可以安全地重跑：不能有副作用——不能改全局状态、不能 printk、不能分配/释放内存、不能唤醒任务。
    • 只能把数据原样拷到局部变量，等 read_seqretry() 通过之后再用。在重试循环里做判断、算下标、做除法（可能除零）都是 bug——那些计算是基于可能矛盾的数据做的。
    • 写者会饿死读者：写侧持续不断时读者可能一直重试。所以它要求「写少到读者几乎撞不上」，不只是「写比读少」。
    • 读侧不宜太长：拷贝的字段越多，撞上写窗口的概率越大。
    为什么绝不能解引用读到的指针
    因为那个指针值可能是半新半旧拼出来的野值（写者正在改它的时候你读了它）。解引用一个野指针 = 立刻 oops——而这发生在 read_seqretry() 有机会告诉你「数据不一致，重试」之前。重试机制只能在你读完之后才生效，它救不了一次已经执行了的非法访问。要保护含指针的结构，用 RCU，不要用 seqlock。
    它的甜点场景
    「一组必须彼此一致的标量，读极多写极少」。内核最著名的使用者是 timekeeping：clock_gettime() 要读「上次更新的时刻 + 周期数 + 乘数 + 移位」这一整组字段，调用频率每秒可能上百万次，写侧只在时钟中断里更新。读侧零写入 → 几十个核并发调用互不影响，这是 rwlock 做不到的。
    与 RCU 的分工
    seqlock 保护值（一组标量的一致快照），RCU 保护对象（可以安全解引用的指针）。seqlock 的写者原地改、不需要额外内存、不需要延迟释放；RCU 的写者要拷贝 + 等宽限期。所以「读一组计数器」用 seqlock，「读一张会增删条目的表」用 RCU。
  3. 中级per-CPU 变量为什么快？它的代价是什么？什么时候不该用？

    快的原因很朴素：它不共享，所以不需要任何同步。一份数据每个 CPU 一个副本，各自只碰自己那份——不需要锁、不需要原子指令、不需要屏障，this_cpu_inc() 在 x86 上就是一条带段前缀的普通 inc，约 1 ns 且零争用。对比一下：atomic64_inc 在多核同时写同一条 cacheline 时会退化到几十甚至上百纳秒，而且随核数恶化。

    唯一要防的不是「别的 CPU」，是「自己漂移到别的 CPU」：拿了 this_cpu_ptr() 之后如果被抢占并迁移，后面的操作就写到别人的副本上去了。所以要用 get_cpu_ptr()/put_cpu_ptr()（内含关/开抢占），或者确认自己已经在关抢占/关中断/持自旋锁的上下文里。

    三个代价
    ① 内存放大——256 核上就是 256 份，结构体里塞个 4 KB 缓冲就是 1 MB；② 汇总是 O(CPU 数) 且不便宜——某个 /proc 统计被监控系统每秒采一次，就是每秒 256 次跨 NUMA 的 cache miss，历史上多次成为大核数机器上的性能问题；③ 拿不到一致快照——遍历过程中前面的 CPU 还在改，总数永远是近似值。
    什么时候不该用
    ① 业务需要精确总数（比如「计数必须严格等于 0 才能释放资源」）——近似值不够，要么加额外的同步，要么别用 per-CPU；② 读侧也很热——读写都热的话 per-CPU 只是把开销搬了个地方；③ 数据本身很大——内存放大扛不住。这时可以退一步用 percpu_counter：本地累加，攒够 batch 才碰一次全局值，用「误差 ≤ batch × CPU 数」换 O(1) 的粗读。
    遍历要用 possible 而不是 online
    for_each_possible_cpu()，不是 for_each_online_cpu()。CPU 下线之后它的 per-CPU 副本还在，里面攒的数还算数；用 online 会在 CPU 热插拔后静默丢数据，表现为「统计值突然变小」。
    往上抽一层
    per-CPU 和 RCU 是同一个设计原则的两个方向：先判断读写比例，再把开销挪到频率低的那一侧。RCU 是「读多写少 → 开销全给写侧」，per-CPU 计数器是「写多读少 → 开销全给读侧」。能识别出这一点，比记住 API 更重要。
  4. 中级synchronize_rcu()、call_rcu()、kfree_rcu() 分别在什么时候用？
    API行为上下文用它的时候
    synchronize_rcu()阻塞到宽限期结束只能进程上下文（会睡）；不能在 RCU 读侧临界区里调（自己等自己，必死）低频操作：配置变更、模块卸载、设备移除。代码最直白，返回后可以放心 kfree
    call_rcu(&p->rcu, fn)立刻返回，宽限期后回调 fn几乎任何上下文，包括中断和原子上下文写侧不能阻塞时；释放逻辑不只是 kfree（要先 put 引用、解注册）
    kfree_rcu(p, rcu)宽限期后自动 kfree(p)同 call_rcu释放动作就是一次 kfree 时的首选，也就是绝大多数情况
    选择规则
    能用 kfree_rcu() 就用它；释放逻辑复杂用 call_rcu()；只有「我必须确认旧对象彻底没人用了才能往下走」才用 synchronize_rcu()。第三种情况远比想象的少——大多数写侧其实不关心旧对象何时真的被释放，只需要保证「最终会释放」。
    call_rcu 的三个坑
    ① 回调在软中断上下文执行，里面不能睡；② 模块卸载前必须 rcu_barrier()，否则回调函数所在的代码段已被卸载，调用时直接 oops（kfree_rcu 不需要，因为没有模块代码被调用）；③ 回调洪水会 OOM——见下。
    批量删除千万别每条都 call_rcu
    清空一张几百万条的表时逐条 call_rcu，回调队列会无限增长，内存被一堆「已经没人用但还没释放」的对象吃光。slabtop 里那个 slab 暴增，但代码逻辑上「都删掉了」。正确做法：把整批节点摘到本地链表，调一次 synchronize_rcu()，然后统一 kfree——一个宽限期解决 N 个对象。RCU 内部有回调洪水检测（rcutree.qhimark 默认 10000）会加速宽限期，但那只是缓解，代价是 CPU 尖峰和延迟抖动。
    rcu_barrier ≠ synchronize_rcu
    synchronize_rcu() 只等宽限期；rcu_barrier() 还要等所有已排队的回调真的执行完。两件事，别混。模块 exit 路径要的是后者。

10.3 高级（体现深度）

  1. 高级RCU 读侧为什么能做到「零开销」？这个开销去哪了？

    关键在于 rcu_read_lock() 不是一把锁。它不与任何人互斥（写者可以在你读的时候照样改）、不会失败、不会阻塞、不会重试、多个读者之间毫无交互。它做的唯一一件事是标记出「我正在读」这段区间，好让写者能判断宽限期结束了没有。

    而「标记一段区间」这件事，在非抢占内核里可以做得极其便宜：读侧临界区只要关抢占，那么「这个 CPU 发生了一次上下文切换」就自动证明了「它已经不在任何读侧临界区里」。于是 rcu_read_lock() 展开成 preempt_disable()——而在不需要抢占计数的配置下，这几乎不产生任何指令，只剩一个编译器屏障。这就是「零开销」的字面含义：没有原子指令、没有屏障指令、没有 cacheline 争用、没有任何写内存。

    抢占式内核里呢
    读侧临界区可以被抢占，所以「上下文切换」不再能证明「不在临界区里」。此时它需要在当前任务上维护一个嵌套计数，并在被抢占时把这个任务记录下来，让宽限期把它也等上。具体实现各版本有差异，但对使用者暴露的行为一致：读侧不阻塞、不失败、不能主动睡眠。开销比非抢占内核大，但仍然远低于任何一把真锁。
    开销去哪了：全给写侧
    ① 写侧必须拷贝一份对象（不能原地改，否则读者会看到半新半旧）；② 必须等一个宽限期（毫秒量级）才能释放旧对象；③ 期间旧对象一直占着内存；④ 写者之间还需要另一把普通锁来互斥（RCU 完全不管这个）。所以 RCU 的本质是一笔交易：用「写侧贵一个数量级」换「读侧便宜到接近零」。读写比 1000:1 时这笔交易划算得离谱，写比读多时是纯负优化。
    相应的硬约束
    零开销是有代价的——因为读侧不记账，所以指针的有效期严格限于 rcu_read_lock()/rcu_read_unlock() 之间，出了 unlock 立刻失效，不能存到全局、不能带出函数。要延长使用期，标准做法是在临界区里 refcount_inc_not_zero() 拿一个引用——RCU 保护「查找的过程」，引用计数保护「使用的过程」。get_task_struct()、socket 查找、dentry 查找都是这个套路。
  2. 高级什么场景下 RCU 是错误选择？举出至少三类并说明原因。

    RCU 有三个前提，缺一不可：读远多于写、能容忍读到稍旧的数据、对象可以延迟释放。任何一条不成立就要换方案。

    ① 读者必须看到最新值
    最典型的是权限/策略检查：不能允许「策略已经收紧了，但某些读者还在用旧策略放行」。RCU 只保证最终一致——写者替换指针后，读者可能在整个宽限期内继续看着旧版本。这类要求「立即生效」的语义只能用锁（或者用 synchronize_rcu() 阻塞到确认为止，但那就付了阻塞的代价，RCU 的优势也没了）。
    ② 写侧也很热
    计数器、队列的头尾指针这类每次操作都在改的数据。用 RCU 等于每次都要分配一个新对象、拷贝、等一个宽限期——比加锁贵几个数量级。经验阈值是读写比至少 10:1，理想 100:1 以上。这类数据的正确答案是 per-CPU（如果是计数）或普通自旋锁。
    ③ 需要立刻回收资源
    对象很大（几 MB 缓冲）、或者持有稀缺资源（文件描述符、DMA 通道、硬件寄存器窗口、许可证）。宽限期是毫秒量级，高频增删下延迟释放会累积成资源耗尽——而且这种 OOM 特别难查，因为内存不在任何进程账上，slabtop 才看得见。
    ④ 读侧要睡眠
    普通 RCU 的读侧临界区里不能睡（copy_to_user、mutex_lock、GFP_KERNEL 分配都不行）。这种情况要用 SRCU——它允许读侧睡眠，而且每个域独立（一个域里的慢读者不会拖累内核其他部分）。代价是读侧不再零开销（要维护 per-CPU 计数，有真实的原子操作与屏障），宽限期也可能更长。
    ⑤ 数据结构不适合「替换式更新」
    RCU 要求「读者要么看到旧版本、要么看到新版本，不能看到中间态」。能靠一次原子指针替换完成的更新（换一个对象、链表增删）最适合。反过来，需要同时改多个位置才能保持不变式的结构（比如平衡树的旋转、双向索引的同步更新）用 RCU 会非常别扭——要么设计成「重建整棵子树再替换」（写侧极贵），要么就得承认读者可能看到不一致的中间态。
    怎么答得更好
    不要只罗列场景，说出判断流程：先量读写比例（有没有到 10:1）→ 再问业务能不能容忍陈旧读 → 再问对象延迟几毫秒释放有没有问题 → 最后确认读侧不需要睡眠。四个都过了才上 RCU，否则老老实实用锁或 per-CPU。「知道什么时候不用某个技术」通常比「知道怎么用」更能体现工程判断力。
  3. 高级lockdep 能发现哪些「真死锁发现不了」的问题？它的盲区在哪？

    lockdep 的核心价值：它检测的不是「现在死锁了」，而是「这套加锁模式在某种时序下可能死锁」。原理是给每个锁归一个「锁类」，运行时记录每一对「持有 A 时获取 B」的先后关系，构建有向图，一旦出现环就报警。

    这带来一个质变
    真死锁需要「两个 CPU 恰好在特定时刻交错」——可能一年触发一次，触发时整机 hang、没有 dump。而 lockdep 只需要那两条代码路径【各自】被执行过一次（不需要同时、不需要交错），就能把环画出来并报警。这把概率性 bug 变成了确定性检测，从「靠运气发现」变成「靠覆盖率发现」。

    它能发现的几类，真死锁都很难自然触发到：

    • AB-BA 环（含 A→B→C→A 的多跳环）：两条路径可能分别在两个完全不同的业务流程里，正常运行时永远不交错。
    • 中断上下文不一致（inconsistent lock state）：同一把锁有时在开中断的进程上下文拿、有时在硬中断里拿。真死锁只在「中断恰好打断持锁者、且在同一个 CPU 上」时发生——多核机器上这个概率极低，可以潜伏数年。
    • RCU 用法错误（suspicious RCU usage）：rcu_dereference() 在读侧临界区之外被调用。这个错误永远不会「死锁」，只会在极偶然的时机产生 UAF——不靠工具几乎不可能发现。
    • 返回用户态时还持着锁：错误路径漏了 unlock。这往往只在某个罕见的 goto err 分支上，正常测试根本走不到。
    • 等待类型冲突（-{3:3} 那部分）：在 raw_spinlock 里拿 mutex——在主线内核上可能只是「不优雅」，在 PREEMPT_RT 上是必死。
    三个盲区（这才是区分深度的部分）
    ① 只看跑到过的路径——没被测试覆盖的加锁组合它一无所知，所以 lockdep 的有效性直接取决于测试覆盖率（包括错误注入、热插拔、模块反复加载卸载这些冷路径）。② 只认识内核的锁原语——你自己用原子标志 + 忙等搓的「土制锁」、用 completion 拼出的等待关系、内核等一个用户态守护进程回话形成的跨态依赖，它全都看不见，而这些恰恰是自研模块里死锁的重灾区。③ 不检测数据竞争——「这个变量根本没被任何锁保护」不在它职责内，那是 KCSAN 的活。
    两个实操细节
    ① lockdep 报过一次警就会把自己关掉（内部状态可能已不一致），所以第一份报告最珍贵，不要攒一批再看，看到 Tainted: ...W... 要往上翻找第一条。② 读报告先跳到最后的 Possible unsafe locking scenario 方框——lockdep 已经把「怎么死」画成了两栏时序图，那是信息密度最高的部分；再回头看 -> #1/-> #0 两段栈，它们分别是「历史上那条边」和「现在这条边」的完整调用路径，修复就是在这两条路径里选一条改掉。
    合法的「同类嵌套」要显式告知
    报 possible recursive locking 不一定是真递归——也可能是「同一个锁类的两个不同实例」的合法嵌套（比如同时锁父子 inode）。此时用 mutex_lock_nested() / spin_lock_nested() 把层级显式告诉 lockdep，而不是把警告关掉。报告里两个锁实例地址相同才是真递归。
  4. 高级内核的同步原语和 C++ 的 memory_order 怎么对应？从 C++ 转内核开发最容易踩什么？

    两套模型的底层机器语义是同一套（毕竟跑在同一个 CPU 上），差别在默认值和表达方式。

    Linux 内核C++ 等价物注意
    READ_ONCE(x)x.load(memory_order_relaxed)内核版额外保证地址依赖序
    WRITE_ONCE(x, v)x.store(v, memory_order_relaxed)基本一致
    smp_load_acquire / smp_store_releaseload(acquire) / store(release)语义一致，这是最好用的一对
    smp_mb()atomic_thread_fence(seq_cst)工程上按等价用
    smp_wmb() / smp_rmb()没有对应物C++ 只有 acquire/release/seq_cst 三档 fence，没有单向的读读/写写屏障。内核有，因为它要贴近硬件省开销
    barrier()atomic_signal_fence(seq_cst)都只约束编译器。C++ 里服务于信号处理函数，内核里服务于中断处理程序——是同一个问题
    rcu_dereference()无（memory_order_consume 是个死掉的设计）内核靠「编译器不许破坏地址依赖」这条工程约定实现，C++ 的标准化尝试失败了
    最大的坑：默认值反了
    C++ 的 std::atomic 默认 memory_order_seq_cst——不写就是最强序，所以 cnt++ 天然安全。内核的 atomic_inc() 默认最弱——原子但什么序都不保证。从 C++ 转过来的人最容易带着「原子操作自带同步」的直觉写内核代码，结果所有「没写序」的地方语义都反了。内核的规则是：无返回值的 RMW（atomic_inc、set_bit）无序；有返回值的 RMW（atomic_add_return、test_and_set_bit）是全屏障；cmpxchg 成功时全屏障、失败时无序。
    第二个坑：上下文这件事在 C++ 里不存在
    用户态所有代码都跑在「可以睡眠」的上下文里，所以 C++ 从来不需要区分「这段代码能不能阻塞」。内核里这是第一判据：会被中断访问的数据只能用自旋锁（无论临界区多长），临界区里要 copy_to_user 就只能用 mutex（无论多短）。把「长短」当成选锁的首要依据，是用户态思维的残留。
    第三个坑：失败的后果不一样
    用户态死锁 = 一个进程卡住，gdb 上去看栈，kill 掉重启。内核死锁 = 整机 hang，没有 dump、没有日志（可能连 console 都刷不出来）。所以内核的工程实践重心完全不同：不是「出问题了怎么调试」，而是「怎么让问题在第一次跑到时就被工具抓住」——lockdep、KCSAN、KASAN、DEBUG_ATOMIC_SLEEP 全开，配 kdump 兜底。
    可以带过去的经验
    发布-订阅（release/acquire 配对）的思维方式是完全通用的；「屏障成对」在两边都成立；「先判断读写比例，再把开销挪到频率低的那一侧」这个原则在两边都对（用户态的 seqlock 手法、读多写少的 hazard pointer / epoch-based reclamation 本质就是 RCU 的用户态版本）。而内核额外多给你的东西是：LKMM 有形式化模型和 tools/memory-model/ 下的验证工具，可以把你的同步模式在最弱架构上跑一遍判断是否成立——这比在 x86 上压测靠谱得多。
