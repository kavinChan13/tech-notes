内核同步原语与 RCU

本站的 C++ 内存模型与 并发深入讲的是用户态的内存序与并发，Linux 设备驱动里只用一小节点到了驱动里的竞态。这篇讲内核态的同步——它和用户态的根本差别在于：你的代码可能跑在中断上下文（绝对不能睡眠）、可能被内核抢占打断、要面对 SMP 真并行与 CPU 乱序，而且一个死锁不是进程挂了，是整机 hang。

内核并发从哪来

四个并发源，决定了锁的种类

用户态写并发，你需要担心的东西其实很少：几个线程、一把 std::mutex、必要时上 std::atomic 配好 memory_order。这三样东西之所以够用，是因为用户态有一个巨大的前提——你的代码永远运行在一个可以睡眠的上下文里。锁不到就阻塞，阻塞就让出 CPU，内核会在合适的时候把你唤醒。整个 C++ 并发模型都建立在这个前提上。

内核里这个前提不成立。同一段内核函数，可能被系统调用路径调用（进程上下文，可以睡眠），也可能被网卡中断处理程序调用（中断上下文，绝对不能睡眠）；可能在持有自旋锁的时候被调用（原子上下文，一旦睡眠整机卡死）。这就是为什么内核里锁的种类比用户态多这么多——不是内核开发者喜欢造轮子，是不同的并发源必须用不同的手段挡住。

用户态并发像几个同事在同一间办公室协作：谁要用打印机就等一下，等的人可以先去喝咖啡（睡眠），没有额外成本。内核并发像医院急诊科的值班室：你正在写病历（进程上下文），救护车随时会拉响警报把你叫走（中断），叫走时你手上可能正拿着唯一那份公用病历夹（临界区）。如果你在拿着病历夹的时候跑去休息室睡觉（持锁睡眠），下一个来找病历的人就只能站在门口干等到天亮——而且他站的那台电梯还堵着（自旋烧 CPU）。急诊科的规矩之所以又多又死，就是因为「被叫走」是常态。

1.1 四个并发源

① SMP 真并行

32 核机器上，32 段内核代码字面意义上同时在跑。两个 CPU 同时执行同一个函数、同时改同一个链表，这是最直观的并发源，也是唯一在单核机器上不存在的那个。

② 内核抢占

CONFIG_PREEMPT 下，进程上下文的内核代码可以在几乎任意一条指令处被更高优先级的任务抢走。哪怕只有一个 CPU，你的临界区也会被切成两半执行。

③ 中断 / 软中断

硬中断和软中断可以在同一个 CPU 上插到你的临界区中间，而且它们不是「另一个任务」——它们借用当前任务的内核栈，无法被调度器调走，只能等它跑完。

④ 主动睡眠让出

kmalloc(GFP_KERNEL)、copy_to_user、mutex_lock、msleep 都可能睡。睡眠 = 调用 schedule() = 别人开始跑你刚才那段代码。这是最隐蔽的一个源。

上下文（context）：内核用它描述「当前这段代码运行在什么身份下」，直接决定你能用哪些同步原语。进程上下文——由系统调用、内核线程进入，有 current，可以睡眠；中断上下文——硬中断处理程序、软中断/tasklet，借用当前任务的栈，不能睡眠（睡了就把一个无关的任务永久挂起，而且没人能唤醒中断）；原子上下文——广义概念，指 preempt_count != 0 的任何时刻，包括持有自旋锁、关中断、关抢占、在中断里，此时同样不能睡眠。
preempt_count：内核为每个任务维护的一个复合计数器，把「抢占禁用层数」「软中断禁用层数」「硬中断嵌套层数」「NMI 层数」压在同一个 32 位整数的不同位段里。preempt_disable()、local_bh_disable()、进入硬中断都会给对应位段加一。in_atomic()、in_interrupt()、might_sleep() 全部靠读它来判断。后面所有「能不能睡」的讨论，本质都是在问这个数是不是 0。

1.2 谁能打断谁

这张表是内核同步选型的唯一依据。选锁的过程其实就是：先问「我这段数据会被谁访问」，再从表里查「那个人能不能打断我」，能打断就必须挡住它。

打断者能打断不能打断要挡住它，你得
另一个 CPU（SMP） 所有上下文，包括对方关了中断的临界区 —（它是真并行，谈不上「打断」） 必须用真正的锁：spin_lock / mutex。单纯关中断、关抢占对它完全无效——这是新手最常犯的错
硬中断（hardirq） 本 CPU 上的进程上下文、软中断 同 CPU 的另一个硬中断（现代内核的中断处理程序默认在本 CPU 关中断的状态下运行，不嵌套） local_irq_save() 或 spin_lock_irqsave()
软中断 / tasklet 本 CPU 上的进程上下文 硬中断处理程序 local_bh_disable() 或 spin_lock_bh()
内核抢占 进程上下文里可抢占的区间 preempt_count != 0 的区间（持自旋锁 / 关中断 / 中断里） preempt_disable()；持有 spin_lock 时已经自动关了抢占
自己睡眠让出 你自己的临界区（醒来时世界已经变了） — 要么别在临界区里调可能睡的函数，要么改用可睡眠锁把整段保护起来
选锁的口诀只有一句：和谁竞争，就关谁。只跟别的 CPU 竞争 → spin_lock；还跟本 CPU 的软中断竞争 → spin_lock_bh；还跟硬中断竞争 → spin_lock_irqsave；临界区里要睡 → mutex。多关是性能损失（关中断会推高中断延迟），少关是随机崩溃。

1.3 一个经典竞态：中断与进程上下文共享队列

下面这段是驱动里最常见的结构：中断处理程序把收到的数据包挂进链表，进程上下文的 read() 从链表里取走。它看起来毫无问题，但在真机上会随机 panic。

❌ 只用了普通 spin_lock
/* 进程上下文：用户调 read() 走到这里 */
static ssize_t drv_read(...)
{
    struct pkt *p = NULL;

    spin_lock(&dev->rx_lock);      /* ← 只关了抢占 */
    if (!list_empty(&dev->rx_list)) {
        p = list_first_entry(&dev->rx_list,
                             struct pkt, node);
        list_del(&p->node);
    }
    spin_unlock(&dev->rx_lock);
    ...
}

/* 硬中断：网卡收包 */
static irqreturn_t drv_isr(int irq, void *arg)
{
    spin_lock(&dev->rx_lock);      /* ★ 死锁点 */
    list_add_tail(&pkt->node, &dev->rx_list);
    spin_unlock(&dev->rx_lock);
    return IRQ_HANDLED;
}

进程上下文在本 CPU 拿到锁，链表指针改了一半时网卡中断到来。ISR 在同一个 CPU 上尝试拿同一把锁——持锁者被中断挂着、永远回不去解锁，ISR 就在那儿自旋。这个 CPU 彻底卡死，几秒后 watchdog: BUG: soft lockup。

✅ 进程侧用 irqsave 挡住中断
static ssize_t drv_read(...)
{
    struct pkt *p = NULL;
    unsigned long flags;

    /* 关本 CPU 中断 + 拿锁，一步完成 */
    spin_lock_irqsave(&dev->rx_lock, flags);
    if (!list_empty(&dev->rx_list)) {
        p = list_first_entry(&dev->rx_list,
                             struct pkt, node);
        list_del(&p->node);
    }
    spin_unlock_irqrestore(&dev->rx_lock, flags);

    /* ★ 耗时操作放在临界区【外面】 */
    if (p) {
        copy_to_user(buf, p->data, p->len);  /* 可能睡 */
        kfree(p);
    }
    ...
}

/* ISR 侧保持 spin_lock 即可：
 * 它自己已经在关中断的上下文里跑 */

关键在于只有可能被中断打断的那一侧需要关中断。ISR 本身已经在关中断状态，再 irqsave 只是多几条指令、没有正确性收益（但也不算错，很多驱动为了统一写法都用 irqsave）。

面试加分点：这个 bug 的可怕之处在于它在单 CPU 上更容易复现，在多 CPU 上反而可能长期潜伏。多核时 ISR 有很大概率跑在另一个核上，那样只是正常的锁等待，一切正常；只有 ISR 恰好落在持锁的那个核上才死。所以「在 16 核开发机上压测一周没问题，客户 2 核虚拟机上十分钟就 hang」是这类 bug 的典型表现。能说出这一层，说明你真的理解了「自旋锁的死锁是本 CPU 问题，不是跨 CPU 问题」。
PREEMPT_RT 会改变这里的部分规则。在实时内核上，spinlock_t 被换成了可睡眠的 rt_mutex，持有它不再禁止抢占；真正的「关抢占自旋锁」变成了 raw_spinlock_t。中断处理程序默认也被线程化。所以 RT 上「持 spinlock_t 时能不能 kmalloc(GFP_KERNEL)」的答案和主线内核相反。写通用驱动时按主线内核的严格规则写（不睡眠、临界区短），在 RT 上一定是安全的；反过来不成立。详见 PREEMPT_RT 深入。

原子操作与 READ_ONCE / WRITE_ONCE

最便宜的同步，和编译器的一场博弈

不是所有共享数据都值得上锁。如果共享的只是一个计数器、一个标志位，用一条 CPU 指令就能原子地改完，那么加锁的开销（争用时的 cacheline 迁移、可能的睡眠唤醒）就完全是浪费。内核为此提供了两套东西：原子类型 atomic_t，以及比锁更基础、但极其容易被忽视的 READ_ONCE() / WRITE_ONCE()。

2.1 atomic_t 与常用 API

atomic_t：内核的原子整数类型，定义就是一个包了一层结构体的 int（typedef struct { int counter; } atomic_t;）。包这一层是刻意的——它让你没法对它做普通的 ++、没法直接赋值，必须走 atomic_*() 接口，于是所有访问在代码里都是显式可见的。它是 32 位有符号的；需要 64 位就用 atomic64_t，需要位宽无关的长整型用 atomic_long_t。
#include <linux/atomic.h>

static atomic_t   refcnt = ATOMIC_INIT(1);
static atomic64_t bytes_rx = ATOMIC64_INIT(0);

/* ── 读写：不是 RMW，没有任何内存序保证 ───────────── */
int v = atomic_read(&refcnt);        /* 内部就是 READ_ONCE() */
atomic_set(&refcnt, 1);              /* 内部就是 WRITE_ONCE() */

/* ── 无返回值的 RMW：原子，但【不带内存屏障】 ─────── */
atomic_inc(&refcnt);
atomic_dec(&refcnt);
atomic_add(4, &refcnt);

/* ── 有返回值的 RMW：原子 + 【全屏障】 ───────────── */
int now = atomic_add_return(1, &refcnt);
int old = atomic_fetch_add(1, &refcnt);
bool zero = atomic_dec_and_test(&refcnt); /* 减 1 后是否为 0 —— 引用计数的标准写法 */

/* ── 比较交换：成功时全屏障，失败时【无序】 ──────── */
int prev = atomic_cmpxchg(&refcnt, 2, 3);   /* 返回旧值 */
int exp = 2;
if (atomic_try_cmpxchg(&refcnt, &exp, 3))  /* 更省一条比较指令，新代码首选 */
    ...;

位操作是另一套，作用在 unsigned long 数组上，常用来实现标志位集合（dev->flags 这类）：

#include <linux/bitops.h>

enum { F_RUNNING = 0, F_STOPPING = 1, F_FAULT = 2 };
unsigned long flags;             /* 位图；>64 位就用数组 + DECLARE_BITMAP */

set_bit(F_RUNNING, &flags);        /* 原子置位，无返回值 → 不带屏障 */
clear_bit(F_RUNNING, &flags);
if (test_bit(F_FAULT, &flags))     /* 纯读，无屏障 */
    ...;

/* 有返回值 → 全屏障。这是内核里最常见的「无锁上锁」惯用法： */
if (test_and_set_bit(F_STOPPING, &flags))
    return;                        /* 已经有人在停了，我直接退出 */
/* 走到这里说明【只有我】把 F_STOPPING 从 0 改成了 1 */
do_stop(dev);

/* __ 前缀 = 非原子版本，只保证编译器不乱动，快但要自己配锁 */
__set_bit(F_RUNNING, &flags);      /* 已经在锁里了，用它省掉 lock 前缀 */
类别例子原子性内存序（LKMM 视角）
普通读写atomic_read / atomic_set / test_bit单次访问不撕裂无序。等价于 READ_ONCE/WRITE_ONCE，只挡编译器
无返回值 RMWatomic_inc / atomic_add / set_bit是无序。需要序就配 smp_mb__before_atomic() / smp_mb__after_atomic()
有返回值 RMWatomic_add_return / atomic_dec_and_test / test_and_set_bit / xchg是全屏障（前后都不会跨越）
条件 RMWatomic_cmpxchg / try_cmpxchg是成功时全屏障；失败时无序——这一条最容易踩
显式弱序变体atomic_add_return_relaxed / _acquire / _release是由后缀决定。热路径上用它省掉不需要的屏障
「原子」不等于「有序」，这是内核原子操作最反直觉的一点，也是和 C++ std::atomic 最大的体感差异。C++ 的 std::atomic 默认是 memory_order_seq_cst——不写就是最强序；内核的 atomic_inc() 默认是最弱的，什么序都不保证。原因很实在：内核里绝大多数原子操作就是纯计数（统计、引用计数），根本不需要序，默认给强序等于给所有人上税。所以内核代码里看到 atomic_t 时不能假设它顺带解决了可见性问题，屏障要自己写。
引用计数不要自己用 atomic_t 手搓。内核有专门的 refcount_t（refcount_inc / refcount_dec_and_test），它在计数溢出和「从 0 复活」时会 WARN 并饱和处理——这两种情况在 atomic_t 上是静默的 use-after-free，历史上被反复用来做提权。新代码一律用 refcount_t，atomic_t 留给真正的计数器。

2.2 READ_ONCE / WRITE_ONCE：为什么必须存在

这一节是整篇里最容易被跳过、也最容易在代码评审里被抓出来的部分。先看一段所有人都写过的代码：

❌ 普通变量轮询：可能永久死循环
static int ready;   /* 另一个 CPU 会置 1 */

void wait_for_peer(void)
{
    while (!ready)
        ;
    consume();
}

编译器完全有权把它变成：

/* 单线程语义下等价的合法优化 */
if (!ready)
    for (;;)
        ;       /* ★ 永久死循环 */

因为在 C 的抽象机里，循环体内没有任何东西修改 ready，所以「每次都重新读」是可以省掉的。这不是编译器 bug，是标准允许的行为——数据竞争在 C 里是未定义行为，编译器有权假设它不存在。

✅ 用 READ_ONCE 表达「每次都要真读」
static int ready;

void wait_for_peer(void)
{
    while (!READ_ONCE(ready))
        cpu_relax();      /* 给超线程让路 + 省电 */
    smp_rmb();            /* ★ 还需要屏障，见 §3 */
    consume();
}

/* 写侧同样要成对： */
void peer_done(void)
{
    fill_data();
    smp_wmb();
    WRITE_ONCE(ready, 1);
}

cpu_relax() 在 x86 上展开成 rep; nop（PAUSE 指令）并自带 "memory" clobber，所以它顺带也挡住了提升。但不要依赖这个副作用：一旦有人重构掉了 cpu_relax()，代码就静默地变错了。用 READ_ONCE 把意图写在读的那一点上，这才是可维护的。

编译器对普通内存访问的「权力」远比大多数人想象的大。内核文档里列举了一整套它可以做、而且在真实优化级别下真的做过的变换：

编译器行为它干了什么后果挡住它的
省略 / 合并读（load fusing）把循环里的多次读优化成一次，值缓存在寄存器轮询变死循环；「重新检查」检查了个寄存器READ_ONCE
省略 / 合并写（store fusing）x=1; ...; x=2; 里的第一次写被删掉对端永远看不到中间状态（状态机丢一步）WRITE_ONCE
读撕裂（load tearing）把一个 64 位读拆成两个 32 位读拼出一个从未被写入过的值（高半旧、低半新）READ_ONCE（且变量不超过机器字长）
写撕裂（store tearing）把 x = 0x0001DEAD; 拆成两条 16 位立即数写对端读到半个值WRITE_ONCE
凭空多读（invented load）寄存器不够用时，把已读到寄存器的值丢掉再重读一遍「先检查后使用」两次读到不同值，检查白做了READ_ONCE 一次读到局部变量后只用局部变量
凭空写（invented store）把 if (c) x = v; 优化成 x = c ? v : x;（无条件写回）把别人刚写进去的值覆盖回旧值WRITE_ONCE
重排在不改变单线程语义的前提下调整访问顺序发布顺序反了，见 §3屏障，READ_ONCE 挡不住这个
 
/* READ_ONCE 的本质（简化）—— 就是一次带 volatile 语义的访问 */
#define READ_ONCE(x)      (*(const volatile __unqual_scalar_typeof(x) *)&(x))
#define WRITE_ONCE(x, v)  (*(volatile __typeof__(x) *)&(x) = (v))

/* 关键点：
 *  1. 它只约束【这一次访问】，不改变变量的类型
 *  2. 它【不是】CPU 屏障 —— 只挡编译器，不挡处理器乱序
 *  3. 只对不超过机器字长的标量有效；对 struct 会编译报错
 *     （更大的对象撕裂无法用一次访问避免）
 *  4. READ_ONCE 顺带保证「地址依赖序」，这是 rcu_dereference 的基础
 */
❌ 拿 volatile 糊
static volatile int ready;   /* 别这样 */

while (!ready)
    ;
consume();
  • 解决不了真正的问题：volatile 不产生任何 CPU 屏障，上面这段在 ARM 上照样会读到 ready==1 但 data 是旧的。
  • 把优化全面关掉：变量的所有访问都变成 volatile，包括已经在锁里、本来完全可以放寄存器的那些。
  • 掩盖意图：看代码的人无法知道哪一次访问是「真的要求每次都读」，哪一次只是顺带。
  • 内核文档 volatile-considered-harmful.rst 明确不建议给变量加 volatile；合法用途基本只剩 jiffies 这类和内存映射 I/O（后者应该用 readl()/writel()）。
✅ 在访问点表达意图
static int ready;                /* 类型保持干净 */

/* 需要每次都读的地方显式标出来 */
while (!READ_ONCE(ready))
    cpu_relax();
smp_rmb();
consume();

/* 已经在锁保护下的地方，普通访问即可，
 * 编译器该怎么优化就怎么优化 */
spin_lock(&lk);
ready++;
spin_unlock(&lk);

「锁里面不需要 READ_ONCE」是另一个常见误区的反面：锁的 acquire/release 语义已经包含了编译器屏障，锁内的普通访问是安全的。滥用 READ_ONCE 会让评审者以为「这里有无锁并发」，制造误导。

面试加分点：被问到「READ_ONCE 和 volatile 有什么区别」时，标准答案是「READ_ONCE 是访问点的标记，volatile 是类型的属性」。但真正体现深度的追问是：「READ_ONCE 能替代屏障吗？」——不能。它只解决编译器层的问题，CPU 层的乱序要靠 §3 的屏障。一段代码里 READ_ONCE 齐全但没有 smp_rmb()，在 x86 上跑一万年都不出错（x86 是 TSO，读读不重排），换到 ARM64 服务器上立刻炸——这是国产 ARM 服务器普及之后大量存量代码暴露出的真实问题。
03

内存屏障

屏障永远成对出现

乱序有两层，必须分开想：

编译器层

为了减少访存、更好地用寄存器和流水线，编译器在不改变单线程可观测行为的前提下自由调整访问顺序。挡它的是 barrier()——一条不产生任何机器指令、只告诉编译器「这里之前之后的内存访问不能互穿」的空 asm。

CPU 层

写进 store buffer 还没落到 cache、读被推测执行提前拿了、cache 失效消息还在队列里排队。挡它的是真正的屏障指令（x86 的 mfence/lock 前缀、ARM 的 dmb/dsb）。

为什么 x86 上「没事」

x86-64 是 TSO：只允许「写 → 读」这一种重排。所以 smp_rmb()/smp_wmb() 在 x86 上编译成纯编译器屏障、零指令。缺屏障的 bug 在 x86 上几乎无法复现，到 ARM64 / POWER 上立刻暴露。

屏障像快递的「先包装后贴单」流程规定。仓库为了效率，会把「装箱」和「贴面单」这两道工序打乱着做（乱序执行）——反正最后箱子和单子都齐了。但如果下游是按面单来取货的，先贴了单、箱子还没装好，取货的人就会拿到一个空箱子。所以必须立一条规矩：面单只能在箱子彻底封好之后才贴（写侧 release）；同时取货方也要有规矩：看到面单才能开箱，看到之前不许提前偷看箱子（读侧 acquire）。两条规矩必须同时存在才有意义——只管好仓库不管取货方，取货方那边的「提前偷看」（推测执行）照样出问题。

3.1 内核屏障 API

3.2 铁律：屏障总是成对出现

一个屏障单独存在几乎总是 bug。屏障约束的是「同一个 CPU 上，我自己的访问之间的顺序」；要让另一个 CPU「看到正确的顺序」，对方必须也有一个屏障来保证它自己不提前读。写侧的 release 必须对上读侧的 acquire，写侧的 smp_wmb() 必须对上读侧的 smp_rmb()。看到代码里一个孤零零的 smp_mb()，第一反应应该是「它的对儿在哪」。

最经典的成对模式就是「发布 — 订阅」：写者先把一个对象填好，再把指向它的指针发布出去；读者先拿到指针，再读对象内容。这个模式在内核里出现的频率高到夸张——RCU 的整套机制、per-CPU 数据的延迟初始化、模块加载、驱动的 probe，全都是它。

/* ── 写侧：发布一个新的配置对象 ─────────────────── */
struct cfg *newc = kzalloc(sizeof(*newc), GFP_KERNEL);
if (!newc)
    return -ENOMEM;
newc->timeout = 500;
newc->retries = 3;

smp_store_release(&dev->cfg, newc);   /* ★ 发布点 */

/* ── 读侧：热路径上取配置 ───────────────────────── */
struct cfg *c = smp_load_acquire(&dev->cfg);   /* ★ 订阅点 */
if (c && now - start > c->timeout)             /* 保证读到 500 而不是 0 */
    handle_timeout(c->retries);

/* 等价但更啰嗦的老写法（在弱序架构上通常还更贵）：
 *   写侧： ...填内容...; smp_wmb(); WRITE_ONCE(dev->cfg, newc);
 *   读侧： c = READ_ONCE(dev->cfg); smp_rmb(); ...读内容...;
 * 新代码优先用 acquire/release：语义就写在名字里，
 * 而且 ARM64 有专门的 ldar/stlr 指令，比无条件 dmb 便宜。
 */
控制依赖不可靠。有人会想：「读侧有个 if (q) 判断，CPU 总不能在还不知道 q 是不是 NULL 的时候就去读 q->len 吧？」——它真能。这叫控制依赖（control dependency），而 CPU 的分支预测 + 推测执行会先按预测的分支把 load 发出去，只在预测错时回滚。读侧的控制依赖对 load 完全不构成顺序保证（对后续的 store 才勉强算，而且限制一堆）。内核文档 memory-barriers.txt 里专门有一大节讲控制依赖的坑，结论是：别用它，用 acquire。地址依赖（用读到的指针去解引用）是另一回事，那个在现代内核里由 READ_ONCE()/rcu_dereference() 保证——历史上唯一需要显式屏障的 Alpha 已经退场，smp_read_barrier_depends() 也早已从内核里删掉了。

04

spinlock 家族

忙等的锁，和「绝不能睡」这条红线

自旋锁（spinlock）：拿不到锁时不睡眠、不让出 CPU，而是在一个循环里反复尝试直到拿到。它的全部意义在于省掉睡眠-唤醒的两次上下文切换（合计几微秒），代价是等待期间这个 CPU 完全在做无用功。所以它只适合极短的临界区，而且是中断上下文里唯一能用的锁。
互斥锁像去银行取号排队：拿到号就可以坐下、甚至出去买杯咖啡，叫号了再回来（睡眠 + 唤醒）。自旋锁像在自动门前面等一个人先出来：你就站着盯着门，谁也不叫号——因为对方只需要两秒钟，去买咖啡的往返时间比等待本身长得多。但这也意味着：如果里面那个人进去睡了午觉，你就得一直站着，而且门口很快排起长队，全楼的人都堵在这儿。

4.1 持锁期间绝不能睡眠

这是内核里最硬的一条红线，理由有三层，从「性能差」到「必然死锁」：

为什么持自旋锁不能睡

  • ① 别人在烧 CPU 等你。你睡了几毫秒，其他等锁的 CPU 就在自旋几毫秒——那是几百万条无用指令，还伴随着持续的 cacheline 争用。自旋锁的全部前提是「等待时间极短」，睡眠直接摧毁这个前提。
  • ② 同一个 CPU 上会真死锁。spin_lock() 在主线内核里包含 preempt_disable()，本来就不允许在临界区里调度。但如果你调了一个会睡的函数，它会强行 schedule()。调度器可能选中同一个 CPU 上另一个也要拿这把锁的任务——它拿不到（持锁者在睡），于是自旋；而持锁者需要这个 CPU 才能被唤醒继续跑。互等，这个 CPU 死了。
  • ③ 中断上下文里根本没有「睡眠」这个概念。中断处理程序借用的是某个无关任务的内核栈，它不是一个可调度实体。让它睡，等于把那个倒霉任务永久挂起，而且没有任何人会来唤醒「这个中断」。内核会直接报 BUG。

内核有专门的检查来抓这件事。打开 CONFIG_DEBUG_ATOMIC_SLEEP 后，所有可能睡眠的函数入口处的 might_sleep() 会在 preempt_count != 0 时立刻打印：

struct mydev {

{

static void outer(struct mydev *dev)
{
    unsigned long f;
    local_irq_save(f);             /* 我特意关了中断 */
    ...
    inner(dev);                    /* ← 回来时中断已经【被打开了】 */

inner() 单独看完全正确，outer() 单独看也完全正确，组合起来错了。而且这个错误不会报任何警告，只表现为极低概率的数据损坏。函数被复用、调用链变长之后，谁也说不清「调用这个函数时中断是开还是关」。

✅ 一律用 irqsave
static void inner(struct mydev *dev)
{
    unsigned long flags;

    spin_lock_irqsave(&dev->lock, flags);
    dev->count++;
    spin_unlock_irqrestore(&dev->lock, flags);
    /* 恢复到【进来时】的状态：
     *   进来时中断开着 → 出去时开着
     *   进来时中断关着 → 出去时【还是关着】
     * 于是这个函数在任何上下文里都能安全调用。 */
}

代价只有一条读标志寄存器的指令（x86 上 pushf/popf，几个周期）。换来的是「函数可以被任意上下文调用」这个可组合性，在几万行的驱动里这远比几个周期值钱。

spin_lock_irq() 的合法用途只剩一种：你能确定这段代码的调用者一定是开着中断的顶层路径（比如就是某个 ioctl 的入口）。内核核心代码里有不少这种用法，因为那里的调用关系是被严格审过的；驱动里请一律用 irqsave。

flags 必须是局部变量。见过有人把它放进结构体里「共享」——那就成了两个 CPU 互相覆盖对方保存的中断状态，恢复出来的值完全随机。同理，flags 不能跨函数传递给另一个上下文去 restore。它就是一个纯粹的栈上临时值。

4.3 实现演进：从 test-and-set 到 qspinlock

自旋锁的实现史是一部「公平性和cacheline 争用的斗争史」。理解这段演进，能解释很多性能现象。

/* ── 第一代：test-and-set（最朴素） ─────────────────── */
void lock(int *l)   { while (xchg(l, 1) == 1) cpu_relax(); }
void unlock(int *l) { WRITE_ONCE(*l, 0); }
/* 问题 1（公平性）：谁抢到算谁的。释放时所有等待者一起冲，
 *   物理上离锁最近（同 core 的超线程、同 L3 的核）的赢面大得多。
 *   高争用下可能出现【某个 CPU 饿死几十毫秒】。
 * 问题 2（争用）：xchg 是带 lock 前缀的写操作，
 *   N 个等待者就是 N 个核【持续写同一条 cacheline】，
 *   每次都要把独占权从别的核抢过来 —— 锁还没拿到，
 *   总线/互联已经被打满了。
 */

/* ── 第二代：ticket lock（x86 从 2.6.25 用到 4.2 前后） ── */
struct tlock { u16 next, owner; };
void lock(struct tlock *l) {
    u16 my = xadd(&l->next, 1);          /* 取号，只做一次原子操作 */
    while (READ_ONCE(l->owner) != my)     /* 之后只【读】，不写 */
        cpu_relax();
}
void unlock(struct tlock *l) { l->owner++; }
/* ✅ 严格 FIFO，公平性解决了，不会饿死。
 * ❌ 但所有等待者还是【读同一条 cacheline】：
 *   owner 一变，N 个核的缓存副本全部失效，N 次一致性风暴，
 *   而其中只有一个核是真的该醒。核数越多越糟（O(N) 流量）。
 */
qspinlock（queued spinlock）：x86 上从 4.2 前后成为 spinlock_t 的默认实现。它基于 MCS 锁——每个等待者把一个per-CPU 的本地节点挂到队尾，然后只自旋在自己那个节点上；持锁者释放时只写「下一个节点」的标志，于是只有一条 cacheline 迁移、只唤醒一个核。为了让无争用的快路径仍然只有一条原子指令，内核把锁状态压进一个 32 位字（locked 字节 + pending 位 + 队尾 CPU 编号），只在真的开始排队时才动用 per-CPU 节点数组。结果是：单线程路径和 test-and-set 一样快，高争用路径是 O(1) 的争用流量并且严格 FIFO。

4.4 临界区要短：一笔可以算出来的账

「临界区要尽量短」这句话人人都会说，但很少有人给出量级。算一下就清楚了：

操作量级（同 NUMA 节点，供参考）含义
L1 命中的一次读~1 ns（约 4 周期）无争用时，一次原子操作的基准成本
无争用的 spin_lock+unlock~10–20 ns一条 lock cmpxchg，cacheline 已在本核独占状态
争用时的一次锁传递~50–200 nscacheline 要从另一个核迁过来。跨 socket 更贵，常见 2–5 倍
一次上下文切换~1–5 μs（含 cache/TLB 变冷的间接成本）这是自旋锁想省掉的东西——所以自旋时间只要低于它就划算
关键不是「自旋 100 ns 有多贵」，而是争用是超线性放大的。临界区从 50 ns 拉长到 500 ns，单看是慢了 10 倍；但持锁时间变长 10 倍意味着「后来者撞上锁」的概率也涨了约 10 倍，于是排队长度涨、每个人的等待时间也涨——吞吐可能掉一个数量级，而且是在核数越多时掉得越狠。这就是为什么内核里会为了把一次 kfree() 移到锁外面而专门发一个补丁：那不是抠 100 ns，那是把一个会随核数爆炸的争用点掐掉。

缩短临界区的四个标准手法

  • 分配 / 释放挪到锁外：先在锁外 kmalloc 好对象，进锁只做链表挂接；删除时在锁内摘链、锁外 kfree。这是内核里最高频的一个模式。
  • 锁内只搬指针，不搬数据：需要拷贝 4 KB 就在锁内把指针换出来，拷贝放锁外。
  • 拆锁：一把大锁 → 每个哈希桶一把锁 / 每个队列一把锁 / per-CPU 一把锁。代价是「需要同时锁多个」时要定死加锁顺序（否则 AB-BA 死锁，见 §9）。
  • 换机制：读远多于写就上 §6 的 seqlock 或 §7 的 RCU；只是计数就上 per-CPU 计数器。把锁优化到极致不如把锁去掉。
读写自旋锁（rwlock_t）基本已被弃用。它允许多个读者并发，看起来很美，但：① 读侧也要写 cacheline（改读者计数），所以「多读者并发」在硬件层面依然是全员争抢一条缓存行，读多的场景下性能常常不如普通 spin_lock；② 它是读者优先的，写者可能长时间饿死；③ 不能递归读（在中断里再读会与等待的写者形成死锁）。新代码里「读多写少」的正确答案是 RCU（§7）或 seqlock（§6），不是 rwlock_t。
05

可睡眠锁：mutex / rwsem / semaphore

临界区长的时候，让出 CPU 才是对的

自旋锁省的是上下文切换，代价是等待时烧 CPU。一旦临界区可能长于「一次上下文切换的成本」（微秒量级），这笔账就反了——此时应该睡下去把 CPU 让给别人。这就是可睡眠锁的存在意义。它们的前置条件只有一个但很硬：只能在进程上下文使用。

5.1 mutex：默认的第一选择

#include <linux/mutex.h>

static DEFINE_MUTEX(cfg_mutex);
/* 或结构体成员： */
mutex_init(&dev->lock);

/* ── 三种加锁方式 ───────────────────────────────── */
mutex_lock(&dev->lock);                    /* 不可中断地等 —— 会让任务进 D 状态 */
...
mutex_unlock(&dev->lock);

if (mutex_lock_interruptible(&dev->lock))  /* ★ 用户可 Ctrl-C 打断，返回 -EINTR */
    return -ERESTARTSYS;                   /* 系统调用路径上【应该】优先用这个 */

if (!mutex_trylock(&dev->lock))
    return -EBUSY;

/* ── 硬性限制 ───────────────────────────────────── */
/* ① 只能在进程上下文用，中断里用 = BUG
 * ② 不可递归：同一任务再次 mutex_lock 同一把锁 = 自死锁
 * ③ 必须由【持有者本人】解锁（不像 semaphore 可以别人 up）
 * ④ 持有 mutex 时不能退出进程、不能 kfree 掉这把锁所在的对象
 */
乐观自旋（optimistic spinning，CONFIG_MUTEX_SPIN_ON_OWNER）：mutex_lock 拿不到锁时不会立刻睡。它先看 mutex 里记录的 owner——如果 owner 此刻正在另一个 CPU 上运行，说明它很可能马上就会释放，那就先自旋一会儿；只有当 owner 被调度走了（或自旋太久、或有更高优先级任务要跑）才真的睡下去。为了避免自旋者互相争抢缓存行，这些自旋者自己排成一条 MCS 队列。效果是：短临界区拿到了自旋锁的性能，长临界区保留了睡眠锁的语义。这也是「现代内核里 mutex 通常比 semaphore 快」的主要原因。
乐观自旋像在便利店结账时看前面那个人：如果他已经在扫码、手在掏手机（owner 正在运行），你就站着等十秒钟，比走到隔壁自助机重新排队快；如果他忽然接了个电话走开了（owner 被调度走），你就该果断换队伍（睡眠让出 CPU）。关键信息是「前面那人现在到底在不在动」——这正是 mutex 记录 owner 的意义。
判据选 spinlock选 mutex
调用上下文任意（中断里只能选它）只能进程上下文
临界区里会不会睡绝对不能可以：kmalloc(GFP_KERNEL)、copy_to_user、读写文件都行
临界区长度< 1 μs 级（几十条指令、改几个字段）可能超过微秒，或长度不可控（依赖用户输入、I/O）
持锁期间会不会被抢占不会（关了抢占）——所以延迟可控会——所以不适合有延迟要求的路径
对中断延迟的影响irqsave 变体会推高中断延迟，临界区必须极短无影响
调试友好度死锁 = 整机 hang，只能靠 lockdep 提前发现死锁 = 任务卡在 D 状态，hung task 检测器会打出完整栈
默认怎么选—能用 mutex 就用 mutex；只有「必须在中断/原子上下文访问」才被迫用 spinlock
面试加分点：很多人会答「短临界区用 spinlock，长临界区用 mutex」，这只是判据之一，而且不是最重要的那条。真正的第一判据是上下文：如果这份数据会被中断处理程序访问，那么无论临界区多长你都只能用 spinlock（并且必须想办法把它做短）；反过来，如果临界区里必须调用可能睡眠的函数（copy_to_user 是最常见的），那么无论它多短你都只能用 mutex。长度判据只在「两者都合法」时才轮得到。能把这个优先级说清楚，比背长短更能体现你真写过内核代码。

5.2 rwsem：可睡眠的读写锁

#include <linux/rwsem.h>

static DECLARE_RWSEM(cfg_sem);
/* 或 init_rwsem(&dev->sem); */

down_read(&dev->sem);          /* 多个读者可以同时进 */
val = dev->cfg->timeout;
up_read(&dev->sem);

down_write(&dev->sem);         /* 写者独占 */
dev->cfg->timeout = 500;
up_write(&dev->sem);

/* 变体 */
if (down_read_trylock(&dev->sem)) { ... up_read(&dev->sem); }
if (down_write_killable(&dev->sem))   /* 可被 SIGKILL 打断，长等待路径应该用 */
    return -EINTR;
downgrade_write(&dev->sem);     /* 写锁降级为读锁，不释放中间窗口 */

/* 内核里的典型使用者：mmap_lock（原 mmap_sem）、
 * 文件系统的 i_rwsem、cgroup 的各种 rwsem —— 都是
 * 「读多、写少、且临界区可能很长（要访存/IO）」的场景。 */
写者饥饿是读写锁的原罪。如果实现是「有读者就让读者进」，那么在读者源源不断的场景下，写者可以永远拿不到锁——而且它还堵在那里，让后面的读者体验也变差。内核在 5.x 对 rwsem 做过一轮重写，引入了 handoff 机制（写者等太久之后会「预定」这把锁，此后新来的读者必须排队而不能插队）和读者侧的乐观自旋，把饥饿问题压到了可接受的程度。但设计层面的结论没变：rwsem 适合「写很少但必须能写进去」的配置类数据，不适合写侧也有一定频率的热点数据。
读写锁在「读多」场景下可能比互斥锁更慢，这是最反直觉的一点。原因是读侧也要写内存——获取读锁必须原子地修改读者计数，那是一次对同一条 cacheline 的写。于是 32 个核并发读，硬件层面就是 32 个核轮流争抢同一条缓存行的独占权，每次几十到几百纳秒。如果临界区里真正的工作只是「读一个 int」（几纳秒），那么99% 的开销都花在锁上，而这个开销随核数增长。此时 rwsem/rwlock_t 不但没帮上忙，反而比什么都不做（RCU）慢几十倍。判据：临界区里的工作量必须显著大于一次 cacheline 迁移，读写锁才有意义。

5.3 semaphore 与 completion

#include <linux/semaphore.h>
static DEFINE_SEMAPHORE(slots, 4);   /* 计数信号量：最多 4 个并发 */

down(&slots);        /* 拿一个配额，没了就睡 */
use_hw_channel();
up(&slots);          /* ★ 允许【别的任务】来 up —— 这既是特性也是坑 */

/* ── 一次性等待请用 completion，别拿 semaphore 凑 ──── */
#include <linux/completion.h>
struct completion done;
init_completion(&done);

/* 提交方 */
submit_dma(dev, &done);
if (!wait_for_completion_timeout(&done, msecs_to_jiffies(500)))
    return -ETIMEDOUT;      /* ★ 一定要带超时，硬件是会不回话的 */

/* 中断处理程序里 */
complete(&done);            /* ✅ complete() 可以在中断上下文调用 */
struct semaphore 在现代内核里基本是历史遗留。它出现得比 mutex 早（曾经内核里的互斥锁就是「计数为 1 的 semaphore」），但它没有 owner 字段，因此：不能做乐观自旋（不知道谁持有、对方是否在跑）、lockdep 支持弱、无法检测「不是持有者却解锁」。所以互斥用 mutex、一次性事件通知用 completion、需要「等一个条件成立」用 wait_event_*()。semaphore 只剩一个不可替代的用途：真正的计数信号量（限制并发数为 N > 1），而且这个用途本身也不常见。

要「互斥」

mutex。有 owner、能乐观自旋、lockdep 全支持、误用会被检测。这是 99% 的场景。

要「等一个事件」

completion（一次性，如等 DMA 完成）或 wait_event_interruptible()（等条件成立，如等队列非空）。都要考虑超时和信号打断。

要「限制并发为 N」

struct semaphore，或者更常见的做法：一个计数 + wait_event，或直接用工作队列的并发度限制。

06

seqlock 与 per-CPU 变量

两种把读侧成本压到接近零的思路

§4 末尾那个结论值得重复：读写锁在读侧极热时是负优化，因为读侧也要写 cacheline。内核给出了两条绕开它的路，思路完全不同但都极其有效：seqlock——读侧一个字都不写，靠版本号重试来保证一致性；per-CPU 变量——干脆让每个 CPU 有自己的一份，从根上消灭共享。

6.1 seqlock：读侧无锁重试

seqlock：一个「序号 + 自旋锁」的组合。写者拿自旋锁并把序号加一（变奇数），改完数据再加一（变偶数）。读者完全不写任何内存：先读序号，再读数据，再读一次序号；如果两次序号不同、或第一次读到的是奇数（说明读的时候有人在写），就整段重读。
seqlock 像看火车站那种翻页式的车次牌。牌子旁边挂着一块「正在更新中」的小灯。你要抄下一整屏车次：先看灯是不是亮的（序号是否为奇数），然后一行行抄，抄完再看一眼灯有没有闪过（序号有没有变）。只要灯全程没动，你抄到的就是一致的一屏；如果动过，说明中间有人翻页了，你抄的可能是半新半旧的——那就从头再抄一遍。你从头到尾没有碰过牌子，所以一百个人同时抄也不会互相干扰。
#include <linux/seqlock.h>

struct stats {
    u64 packets;
    u64 bytes;
    u64 drops;
};
static seqlock_t     st_lock;
static struct stats st;

seqlock_init(&st_lock);

/* ── 写侧：内含自旋锁，写者之间自动互斥 ────────────── */
static void account(u32 len, bool drop)
{
    write_seqlock(&st_lock);         /* 拿锁 + 序号++ （变奇数）*/
    if (drop) {
        st.drops++;
    } else {
        st.packets++;
        st.bytes += len;
    }
    write_sequnlock(&st_lock);       /* 序号++ （变偶数）+ 放锁 */
}
/* 如果写侧在中断里跑，用 write_seqlock_irqsave() */

/* ── 读侧：一个字都不写 ─────────────────────────── */
static void snapshot(struct stats *out)
{
    unsigned int seq;

    do {
        seq = read_seqbegin(&st_lock);   /* 读序号；奇数会在这里等 */

        /* ★ 这一段可能读到【撕裂的中间状态】，
         *   所以只能【拷贝到局部】，绝不能在这里做决策/解引用 */
        out->packets = st.packets;
        out->bytes   = st.bytes;
        out->drops   = st.drops;

    } while (read_seqretry(&st_lock, seq));   /* 序号变了 → 全部重来 */

    /* 走到这里，out 里的三个值一定来自【同一个瞬间】 */
}

seqlock 的使用边界（每一条都是踩过的坑）

  • 读侧临界区必须可以安全地重跑：不能有任何副作用——不能改全局状态、不能 printk、不能分配/释放内存、不能唤醒任务。因为它可能被执行 2 次、5 次。
  • 读侧读到的数据可能是撕裂的、互相矛盾的。所以只能原样拷贝到局部变量，等 read_seqretry() 通过之后再用。在重试循环内部做 if 判断、算下标、除法（可能除零！）都是 bug。
  • 绝对不能读到一个指针就立刻解引用。那个指针可能是半新半旧拼出来的野值，解引用直接 oops——而这发生在 read_seqretry() 有机会告诉你「重试」之前。要保护含指针的结构，用 RCU，不要用 seqlock。
  • 写者会饿死读者。写侧持续不断时，读者可能一直重试。所以它要求写极少——不是「写比读少」，是「写少到读者几乎撞不上」。
  • 读侧不适合放很长的临界区：拷贝的字段越多，撞上写窗口的概率越大，重试越频繁。
  • 写侧自带自旋锁（seqlock_t），所以写侧不能睡；如果你已经有别的锁来串行化写者，可以用更轻的裸 seqcount_t（write_seqcount_begin/end），但那时写者互斥要你自己保证。
内核里最著名的 seqlock 使用者是 timekeeping。clock_gettime() 这条路径要读「上次更新的时刻 + 周期数 + 乘数 + 移位」这一整组必须彼此一致的字段，而它的调用频率高到离谱（每秒可能几百万次），写侧则只在时钟中断里更新。这正是 seqlock 的完美场景：读侧零写入、零争用，几十个核并发调 clock_gettime() 互不影响。此外 dentry 的路径查找（RCU-walk 模式配合 rename_lock）、任务的 CPU 时间统计也都用它。

6.2 per-CPU 变量：最好的锁是没有锁

per-CPU 变量：一份数据，每个 CPU 有自己独立的一个副本，各自只访问自己那份。既然不共享，就不需要任何锁、任何原子操作、任何屏障——唯一要防的是「访问期间被抢占/迁移到了别的 CPU」。它是内核里最彻底的一种优化：不是把锁做快，是把共享消灭掉。
per-CPU 变量像给每个收银员一个自己的钱箱，而不是全店共用一个保险柜。收钱时谁也不用等谁（零争用），代价是店长想知道今天总营业额，必须挨个箱子去数（汇总是 O(核数)），而且数的过程中前面的箱子可能又收了钱，所以拿到的永远是个近似值。绝大多数时候这个取舍是极其划算的：收钱每秒几千次，看总额一天几次。
#include <linux/percpu.h>

/* ── 静态定义 ───────────────────────────────────── */
static DEFINE_PER_CPU(u64, rx_packets);
static DEFINE_PER_CPU(struct my_cache, cache);

/* ── 最简：this_cpu_* 系列，单条指令完成，抢占安全 ─── */
this_cpu_inc(rx_packets);              /* ✅ x86 上是一条带 %gs 段前缀的 inc */
this_cpu_add(rx_bytes, len);
u64 v = this_cpu_read(rx_packets);
/* 「抢占安全」的含义：它保证【读-改-写落在同一个 CPU 的副本上】，
 * 不会因为中途被抢占而把结果写到另一个 CPU 的副本里。
 * 它【不是】跨 CPU 原子的 —— 别指望它做同步。 */

/* ── 拿指针操作复杂结构：必须防止 CPU 漂移 ────────── */
struct my_cache *c = get_cpu_ptr(&cache);   /* preempt_disable() + this_cpu_ptr() */
c->head = c->items[--c->n];                 /* 这中间绝不会换 CPU */
put_cpu_ptr(&cache);                        /* preempt_enable() */

/* 已经在关抢占/关中断/持自旋锁的上下文里，直接用轻量版： */
struct my_cache *c2 = this_cpu_ptr(&cache);
/* ★ 在【可抢占】上下文里用 this_cpu_ptr 而不关抢占，
 *   开了 CONFIG_DEBUG_PREEMPT 会报：
 *   BUG: using smp_processor_id() in preemptible [00000000] code
 *   这个警告的意思是：你算出的 CPU 号可能下一刻就过期了。 */

/* ── 汇总：需要遍历所有【可能存在】的 CPU ──────────── */
u64 total = 0;
int cpu;
for_each_possible_cpu(cpu)             /* ★ possible 而不是 online：
                                        *   CPU 下线后它的副本还在，
                                        *   用 online 会丢数据 */
    total += per_cpu(rx_packets, cpu);

/* ── 动态分配 ───────────────────────────────────── */
struct my_stats __percpu *ps = alloc_percpu(struct my_stats);
if (!ps)
    return -ENOMEM;
this_cpu_ptr(ps)->n++;
free_percpu(ps);
方案写侧成本（每次）读侧成本精度适用
spin_lock + 普通变量争用时 50–200 ns，且随核数恶化同上精确写侧本来就不热，或者需要和其他数据一起原子更新
atomic64_inc无争用 ~10 ns；多核同时写同一条 cacheline 时急剧恶化一次读，很便宜精确写侧频率中等（每秒几万次以内），需要随时读到准确值
per-CPU 变量~1 ns（一条普通指令，零争用）O(CPU 数)，256 核要触碰 256 条 cacheline近似（汇总期间还在变）高频统计计数器——网络包数、字节数、各类 /proc 统计
percpu_counter~1 ns（本地累加），攒够 batch 才碰一次全局值_read() O(1) 但粗；_sum() O(CPU 数) 且要拿锁可控：误差 ≤ batch × CPU 数既要高频写、又要「大致准确」的量，如文件系统的空闲块数
per-CPU 的三个代价，别只看到零争用。① 内存放大：一个 per-CPU 结构在 256 核机器上就是 256 份；结构体里塞个 4 KB 缓冲，那就是 1 MB。② 汇总不便宜也不精确：/proc 里某个统计如果被监控系统每秒采集一次，而它需要遍历 256 个 CPU 的副本，那就是每秒 256 次跨 NUMA 的 cache miss——「读一个数」变成了一个实实在在的开销，历史上多次成为大核数机器上的性能问题。③ 拿不到一致快照：遍历过程中前面的 CPU 还在改，所以「总数」永远是个近似值；如果业务逻辑需要「精确的总数等于 0 才能释放资源」，per-CPU 就不适用（或者要额外配一个 seqlock/RCU 屏障来保证）。
面试加分点：被问「怎么优化一个高频计数器」时，除了说出 per-CPU，加上这一层会明显不同——「per-CPU 把成本从写侧转移到了读侧」。这和 §7 的 RCU 是同一种思维：先判断读写比例，然后把开销挪到频率低的那一侧。RCU 是「读多写少 → 开销全给写侧」，per-CPU 计数器是「写多读少 → 开销全给读侧」。能识别出这是同一个设计原则的两个方向，说明你抓住了内核同步设计的主线，而不是在背 API。
07

RCU 原理

读侧零开销，代价全给写侧

RCU（Read-Copy-Update）是内核同步里最有独创性的一项设计，也是面试里区分「读过书」和「读过代码」的分水岭。它解决的问题很具体：一份数据被极其频繁地读、极少被改（比如网络路由表、已加载模块列表、进程的文件描述符表、SELinux 策略），而读侧还常常在中断/软中断这种不能睡的上下文里。前面所有方案在这个场景下都不理想——rwsem 不能在中断里用，rwlock 的读侧要写 cacheline，seqlock 不能保护含指针的结构。

RCU 的核心交易是：让读者永远不阻塞、不重试、甚至一条同步指令都不执行；把全部代价转移给写者——写者必须做拷贝，还必须等待一段「宽限期」才能释放旧数据。读写比例是 1000:1 时，这笔交易划算得离谱。
RCU 像更换公告板上的通知。传统做法是把公告板锁上（加锁），撕下旧通知、贴上新的，期间所有人都在门外等。RCU 的做法是：在旁边先做好一张全新的通知（Copy + Update），然后把公告板上的「指向哪张通知」的箭头一挪（一次原子的指针替换）。挪箭头是瞬间的，正在看旧通知的人不受任何影响，可以慢慢看完；新来的人看到的自然是新通知。最后一步是关键：那张旧通知不能马上销毁——得等到「所有在换箭头之前就开始看的人都看完走了」，这段等待就是宽限期。

7.1 读侧为什么能做到零开销

/* 读侧的全部内容就这么多 */
rcu_read_lock();
struct cfg *c = rcu_dereference(dev->cfg);
if (c)
    use(c->timeout, c->retries);
rcu_read_unlock();

/* rcu_read_lock() 到底做了什么？关键在于它【不是一把锁】：
 *   · 它不与任何人互斥 —— 写者可以在你读的时候照样改
 *   · 它不会失败、不会阻塞、不会重试
 *   · 多个读者之间毫无交互，可以任意嵌套
 *   它做的唯一一件事是【标记出「我正在读」这段区间】，
 *   好让写者能判断「宽限期结束了没有」。
 *
 * 在 CONFIG_PREEMPT_NONE 的内核里，它展开成 preempt_disable()；
 * 而在不需要抢占计数的配置下，这几乎不产生任何指令 —— 只剩一个
 * 编译器屏障。这就是「读侧零开销」的字面含义。
 *
 * 在抢占式内核（CONFIG_PREEMPT / PREEMPT_RT）里，读侧临界区【可以被抢占】，
 * 所以它需要在当前任务上维护一个嵌套计数，并在被抢占时把这个任务
 * 记录下来，让宽限期把它也等上。实现细节各版本有差异，
 * 但【对使用者暴露的行为是一致的】：读侧不阻塞、不失败、不能睡眠。 */
宽限期（grace period）：从「写者完成指针替换」这一刻算起，到「所有在替换之前就已经进入读侧临界区的读者都退出」为止的这段时间。宽限期结束后可以断言：再也没有任何 CPU 能通过任何路径拿到旧对象的指针——因为新进入的读者只能看到新指针，而旧读者都走完了。此时才可以安全释放旧对象。注意它不需要等新进入的读者，也不需要知道到底有哪些读者——这正是它能做到读侧零开销的原因。
静止状态（quiescent state）：一个 CPU「此刻肯定不在任何 RCU 读侧临界区里」的可判定时刻。在非抢占内核里，读侧临界区是关抢占的，所以一次上下文切换、进入 idle、返回用户态都足以证明这一点。宽限期的实现就是等每个 CPU 都至少经过一次静止状态——这也解释了「为什么内核里的死循环会导致 RCU stall」（§8）：那个 CPU 一直不经过静止状态，宽限期就永远结束不了。

7.2 三件套：发布、订阅、宽限期

动作API它保证什么对应 §3 的什么
发布rcu_assign_pointer(p, v)把新对象的内容先于指针发布出去。读者一旦看到新指针，就一定能看到完整初始化的对象写侧 smp_store_release()
订阅rcu_dereference(p)取指针，并保证后续通过这个指针的解引用不会被提前到取指针之前（地址依赖序）；同时带 lockdep 检查「你真的在读侧临界区里吗」读侧的地址依赖 + READ_ONCE()
划界rcu_read_lock() / rcu_read_unlock()标记读侧临界区。指针的有效期只在这一对之间——出了 unlock，之前拿到的指针立刻失效—（RCU 特有）

7.3 写侧模式与完整代码

「Read-Copy-Update」这个名字就是写侧的流程：拷贝一份 → 改副本 → 原子替换指针 → 等宽限期 → 释放旧的。注意 RCU 不解决写者之间的互斥——多个写者并发时仍然需要一把普通的锁（spinlock 或 mutex）把它们串起来。

/* ══ 模式一：整体替换一个配置对象 ═══════════════════ */
static struct cfg __rcu *g_cfg;
static DEFINE_MUTEX(cfg_mutex);          /* ★ 写者之间的互斥，RCU 不管这个 */

static int cfg_set_timeout(u32 t)
{
    struct cfg *old, *new;

    new = kmalloc(sizeof(*new), GFP_KERNEL);
    if (!new)
        return -ENOMEM;

    mutex_lock(&cfg_mutex);
    old = rcu_dereference_protected(g_cfg, mutex_is_locked(&cfg_mutex));
    *new = *old;                          /* ① Copy */
    new->timeout = t;                     /* ② Update（改副本，读者看不见）*/
    rcu_assign_pointer(g_cfg, new);       /* ③ 原子发布，含 release 语义 */
    mutex_unlock(&cfg_mutex);

    synchronize_rcu();                    /* ④ 等宽限期（会睡！只能在进程上下文）*/
    kfree(old);                           /* ⑤ 现在没人能引用 old 了 */
    return 0;
}

/* 读侧（可以在软中断、可以在 NAPI poll 里）： */
static u32 cfg_timeout(void)
{
    struct cfg *c;
    u32 t;

    rcu_read_lock();
    c = rcu_dereference(g_cfg);
    t = c ? c->timeout : DEFAULT_TIMEOUT;
    rcu_read_unlock();
    return t;                             /* ★ 只能把【值】带出去，绝不能把 c 带出去 */
}
/* ══ 模式二：RCU 保护的链表（最常见的用法）═════════ */
#include <linux/rculist.h>

struct entry {
    struct list_head list;
    struct rcu_head  rcu;      /* ★ call_rcu 要用的回调头，嵌在对象里 */
    u32              key;
    u32              val;
};
static LIST_HEAD(entries);
static DEFINE_SPINLOCK(entries_lock);   /* 只保护写者之间 */

/* ── 读：不加任何锁，可以在中断上下文 ─────────────── */
static bool lookup(u32 key, u32 *out)
{
    struct entry *e;
    bool found = false;

    rcu_read_lock();
    list_for_each_entry_rcu(e, &entries, list) {   /* 内部用 rcu_dereference */
        if (e->key == key) {
            *out = e->val;                /* 取值出去，不带指针出去 */
            found = true;
            break;
        }
    }
    rcu_read_unlock();
    return found;
}

/* ── 增：先填好再挂链，list_add_rcu 内含发布语义 ──── */
static int insert(u32 key, u32 val)
{
    struct entry *e = kmalloc(sizeof(*e), GFP_KERNEL);

    if (!e)
        return -ENOMEM;
    e->key = key;
    e->val = val;                         /* ★ 挂链【之前】填完 */

    spin_lock(&entries_lock);
    list_add_rcu(&e->list, &entries);     /* 读者要么看不到它，要么看到完整的它 */
    spin_unlock(&entries_lock);
    return 0;
}

/* ── 删：摘链 + 延迟释放 ────────────────────────── */
static void entry_free_rcu(struct rcu_head *head)
{
    struct entry *e = container_of(head, struct entry, rcu);

    kfree(e);
}

static void remove(u32 key)
{
    struct entry *e;

    spin_lock(&entries_lock);
    list_for_each_entry(e, &entries, list) {   /* 写侧有锁，不必用 _rcu 版本 */
        if (e->key == key) {
            list_del_rcu(&e->list);       /* ★★ 不是 list_del()！见下 */
            spin_unlock(&entries_lock);
            call_rcu(&e->rcu, entry_free_rcu);  /* 异步等宽限期后释放 */
            return;
        }
    }
    spin_unlock(&entries_lock);
}

/* ── 改一个已存在的项：不能原地改（读者会看到半新半旧）── */
static int update(u32 key, u32 val)
{
    struct entry *old, *new;

    new = kmalloc(sizeof(*new), GFP_KERNEL);
    if (!new)
        return -ENOMEM;

    spin_lock(&entries_lock);
    old = find_locked(key);
    if (!old) { spin_unlock(&entries_lock); kfree(new); return -ENOENT; }
    *new = *old;
    new->val = val;
    list_replace_rcu(&old->list, &new->list);   /* 原子换节点 */
    spin_unlock(&entries_lock);

    kfree_rcu(old, rcu);                  /* 最省事：宽限期后自动 kfree */
    return 0;
}
必须用 list_del_rcu() 而不是 list_del()。普通的 list_del() 会把节点的 next 和 prev 都写成 LIST_POISON1/LIST_POISON2（一个故意非法的地址，用来让 use-after-free 立刻崩而不是静默损坏）。但 RCU 读者可能此刻正停在这个节点上，下一步要顺着 next 继续遍历——如果 next 被写成毒值，读者就跳到非法地址去了。list_del_rcu() 的差别就是保留 next 有效（只毒化 prev，因为 RCU 遍历总是单向的），让还在链上的读者能安全地走完剩下的节点。同理，绝不能在宽限期结束前 kfree 掉节点，哪怕它已经不在链上了。

7.4 synchronize_rcu / call_rcu / kfree_rcu 怎么选

API行为能在什么上下文调用它的时候坑
synchronize_rcu() 阻塞，直到宽限期结束才返回 只能进程上下文（它会睡）；绝不能在 RCU 读侧临界区里调（自己等自己，必死） 代码简单直白，之后可以放心 kfree；适合低频的配置变更、模块卸载、设备移除 可能阻塞很久——毫秒到几十毫秒是常态（要等所有 CPU 都过一次静止状态）。在热路径上调它会造成明显停顿；持锁时调它极易连环卡死
call_rcu(&p->rcu, fn) 立刻返回，宽限期后由内核在软中断（或专门的 rcuo 内核线程）里调用 fn 几乎任何上下文，包括中断和原子上下文 写侧不能阻塞时的标准选择；释放逻辑不只是 kfree（要先 put 引用、解注册）时用它 ① 回调函数在软中断上下文执行，里面不能睡；② 模块卸载前必须 rcu_barrier()，否则回调函数所在的代码段已被卸载，调用时直接 oops；③ 大量调用会积压，见 §8
kfree_rcu(p, rcu_field) 宽限期后自动 kfree(p) 同 call_rcu 释放动作就是一次 kfree 时的首选——绝大多数情况 不需要写回调函数，因此也不需要 rcu_barrier()（没有模块代码被调用）。内核对它做了批量优化，比手写 call_rcu(..., kfree_cb) 更省
rcu_barrier() 阻塞，等所有已排队的 call_rcu 回调都执行完 只能进程上下文 模块 exit 路径的必备动作 它不等于 synchronize_rcu()：后者只等宽限期，前者还要等回调真的跑完。两件事，别混
synchronize_rcu_expedited() 用 IPI 强行催各 CPU 尽快报告静止状态，宽限期缩到几十微秒 进程上下文 真的等不了的关键路径（内核里用得很谨慎） 会给所有 CPU 发 IPI——对实时性和低延迟业务是干扰源。rcupdate.rcu_expedited=1 会把全局都改成催促模式，不要随便开
选择规则很简单：能用 kfree_rcu() 就用它；释放逻辑复杂就用 call_rcu()；只有「我必须确认旧对象已经彻底没人用了才能继续往下走」时才用 synchronize_rcu()。第三种情况远比想象的少见——大多数写侧其实不关心旧对象什么时候真的被释放，只是需要保证「最终会释放」。
RCU 和引用计数不是互斥的，经常配合用。典型模式：读侧在 RCU 临界区里找到对象，然后 refcount_inc_not_zero() 拿一个引用，出临界区后靠引用计数继续安全使用。这解决了「RCU 指针出了 rcu_read_unlock() 就失效」这个限制——RCU 保护「查找的过程」，引用计数保护「使用的过程」。内核里 get_task_struct()、socket 查找、dentry 查找都是这个套路。注意必须用 _not_zero 版本：对象可能已经在被销毁的路上了，此时计数是 0，不能复活它。
08

RCU 的边界与陷阱

它不是万能的，而且失效方式很隐蔽

8.1 适用与不适用

✅ RCU 的三个前提，缺一不可
  • 读远多于写。写侧要做拷贝 + 等宽限期，比加锁贵得多。经验阈值是读写比至少 10:1，理想是 100:1 以上。写比读还多的场景用 RCU 是纯负优化。
  • 能容忍读到稍旧的数据。读者可能在宽限期内一直看着旧版本。对「路由表」「配置」「已注册的回调列表」这类数据，晚几毫秒生效完全无害。
  • 对象可以延迟释放。宽限期是毫秒量级，期间旧对象一直占着内存。对象小、数量可控时没问题。
❌ 这些场景不要用 RCU
  • 读者必须看到最新值。比如「检查权限」——不能允许「策略已经收紧了但某些读者还在用旧策略放行」。这类语义要求必须用锁。
  • 写侧也很热。计数器、队列头尾指针这种每次都在改的东西，用 RCU 等于每次操作都分配一个对象再等一个宽限期。
  • 需要立刻回收资源。对象很大（几 MB 的缓冲）、或持有稀缺资源（fd、DMA 通道、硬件寄存器窗口），延迟释放会累积成资源耗尽。
  • 需要「修改后立即生效并确认」的语义。RCU 只能保证「最终一致」，要立即确认就得 synchronize_rcu()，那你就付了阻塞的代价。
  • 读侧要睡眠。普通 RCU 的读侧临界区里睡眠是明确的错误——要用 SRCU。

8.2 陷阱一：读侧临界区里睡眠

普通 RCU 的读侧临界区里不能睡眠（非抢占内核里它就是关抢占；抢占式内核里虽然可以被抢占，但仍然不允许主动阻塞）。这意味着一整类操作在读侧被禁止：mutex_lock、kmalloc(GFP_KERNEL)、copy_to_user、synchronize_rcu。

/* ❌ 典型错误：想在 RCU 读侧把数据拷给用户 */
rcu_read_lock();
e = find_entry_rcu(key);
copy_to_user(buf, e->data, e->len);   /* ★ 可能缺页 → 睡眠 → BUG */
rcu_read_unlock();

/* ✅ 方案 A：在临界区里只拿引用，出去之后再慢慢用 */
rcu_read_lock();
e = find_entry_rcu(key);
if (e && !refcount_inc_not_zero(&e->ref))
    e = NULL;
rcu_read_unlock();
if (e) {
    copy_to_user(buf, e->data, e->len);   /* 有引用兜底，可以睡 */
    entry_put(e);
}

/* ✅ 方案 B：在临界区里把需要的数据拷到内核栈/临时缓冲 */
rcu_read_lock();
e = find_entry_rcu(key);
if (e) { len = min(e->len, sizeof tmp); memcpy(tmp, e->data, len); }
rcu_read_unlock();
if (len) copy_to_user(buf, tmp, len);

/* ✅ 方案 C：确实需要在读侧睡眠 → 用 SRCU（Sleepable RCU）*/
static struct srcu_struct my_srcu;
init_srcu_struct(&my_srcu);           /* 每个「域」一个，互不影响 */

int idx = srcu_read_lock(&my_srcu);   /* ★ 返回一个 idx，解锁时必须带回来 */
e = srcu_dereference(g_entry, &my_srcu);
copy_to_user(buf, e->data, e->len);   /* ✅ 这里可以睡 */
srcu_read_unlock(&my_srcu, idx);

/* 写侧对应用 synchronize_srcu(&my_srcu) / call_srcu(...) */
/* SRCU 的代价：读侧【不再是零开销】—— 它要维护 per-CPU 的计数，
 * 读侧有真实的原子操作与屏障；宽限期也可能更长。
 * 换来的是「读侧可以睡」和「每个域独立，一个域卡住不影响别人」。 */
SRCU 的「域隔离」是它另一个被低估的优点。普通 RCU 是全局的：任何一个 CPU 上的长时间不让出，都会拖长所有人的宽限期。SRCU 每个 srcu_struct 是独立的域——你的模块里有个读者卡了 10 秒，只会拖累你自己这个域的 synchronize_srcu()，不会影响内核其他部分。所以「读侧临界区可能很长」也是选 SRCU 的理由，不只是「要睡眠」。

8.3 陷阱二：call_rcu 洪水导致 OOM

call_rcu() 是「立刻返回」的，这很爽，但它意味着释放动作被放进了一个队列。如果你产生回调的速度持续快于宽限期推进的速度，这个队列就会无限增长——内存被一堆「已经没人用、但还没被释放」的对象吃光。

典型触发场景与表现

  • 场景：一个循环里高速删除表项（清空一张几百万条的连接跟踪表、卸载一个巨大的路由表、压测里疯狂增删），每条都 call_rcu。
  • 表现：内存持续上涨，slabtop 能看到对应的 slab 缓存暴增，但代码逻辑上「这些对象都已经删掉了」。严重时直接 OOM，而 OOM killer 杀谁都救不回来（内存不在任何进程账上）。
  • 内核的自我保护：RCU 有回调洪水检测——当某个 CPU 上待处理回调数超过阈值（rcutree.qhimark，默认 10000）时，它会切到更激进的模式加速宽限期、并提高单次处理的回调数上限。这是缓解，不是解决：它只是让你从「必定 OOM」变成「可能撑住，但会有明显的 CPU 尖峰和延迟抖动」。
  • 正确做法：批量删除路径上不要每条都 call_rcu。要么先把整批节点摘下来、调一次 synchronize_rcu()、再统一 kfree 整批（一个宽限期解决 N 个对象）；要么在循环里定期检查并主动限速。内核自己在很多批量销毁路径上就是这么做的。
/* ❌ 一百万次 call_rcu */
list_for_each_entry_safe(e, tmp, &huge_list, list) {
    list_del_rcu(&e->list);
    call_rcu(&e->rcu, entry_free_rcu);   /* 队列爆炸 */
}

/* ✅ 一个宽限期解决全部 */
LIST_HEAD(dead);

spin_lock(&lock);
list_splice_init_rcu(&huge_list, &dead, synchronize_rcu);
/* 或者手工：把节点全部摘到本地 dead 链表 */
spin_unlock(&lock);

synchronize_rcu();                        /* ★ 只等【一次】宽限期 */
list_for_each_entry_safe(e, tmp, &dead, list)
    kfree(e);                             /* 直接释放，不用 RCU */
相关的一个观测点：/sys/kernel/debug/rcu/rcudata（需要 CONFIG_RCU_TRACE 与 debugfs）能看到每个 CPU 的待处理回调数（qlen）。怀疑回调积压时先看这个数——如果它稳定在几万甚至几十万，那就确诊了。另外 rcu_nocbs= 内核参数可以把指定 CPU 的回调处理卸载到专门的 rcuo 内核线程，这是低延迟/实时场景的标配（避免 RCU 回调在软中断里抢你的关键线程），代价是多了一批内核线程需要绑核安置。

面试加分点：能讲出 RCU flavor 合并这段历史，是很强的信号。要点是为什么当初要分、以及为什么后来能合：分是因为不同场景对「静止状态」的定义不同（软中断里的读者、关抢占的读者），三套各自维护自己的宽限期；合是因为统一实现让宽限期同时满足所有几种读侧临界区的要求——代价是宽限期可能略长，收益是少了三分之二的记账开销、以及消灭了「用错 flavor 导致的静默 bug」这一整类问题。这个取舍本身就是内核工程哲学的好例子：宁可付一点确定的性能，也要消灭一类不确定的正确性风险。
09

死锁排查与竞态检测

别靠压测和运气

内核同步的 bug 有一个共同特征：概率极低、后果极重、现场极难保留。一个 AB-BA 锁序问题可能一年触发一次，触发时整机 hang，没有 core dump，只有一屏烧在 console 上的栈。所以内核同步的工程实践不是「写完压测」，而是把一整套运行时验证工具打开，让 bug 在第一次跑到的时候就暴露。

9.1 lockdep：不需要真死锁就能发现死锁

lockdep（CONFIG_PROVE_LOCKING）：内核内置的锁正确性验证器。它不检测「现在死锁了」，而是检测「这套加锁模式在某种时序下可能死锁」。原理是：给每个锁归一个「锁类」（同一行代码初始化出的所有锁实例算同一类），运行时记录每一对「持有 A 时获取 B」的先后关系，构建一张有向图；一旦新加入的边让图出现环，就立刻报警。此外它还记录每个锁类在什么上下文下被获取过（是否在硬中断里、是否开着中断），据此发现中断相关的不一致。
lockdep 像建筑图纸的单向通道审查。它不需要等到真的有两队人在走廊里对头堵死，才说「这里设计有问题」；它只要在图纸上发现「A 房间的门只能通向 B，而 B 房间又有一条只能通向 A 的路」，就直接判定这个布局迟早会堵。关键优势是：只要这两条路各自被走过一次（不需要同时走），环就画出来了。
这就是 lockdep 最重要的价值：它把「需要两个 CPU 恰好在特定时刻交错」的概率性 bug，变成了「只要两条代码路径各自被执行过一次」的确定性检测。真死锁需要天时地利，lockdep 只需要你的测试跑到过那两行代码。这是从「靠运气发现」到「靠覆盖率发现」的质变。

  • 先跳到最后那个 Possible unsafe locking scenario 方框。lockdep 已经把「怎么死」画成了两栏时序图，这是整份报告里信息密度最高的部分。上面这例的意思是：CPU0 按 rx→tx 的顺序拿，CPU1 按 tx→rx 的顺序拿，两个各拿到第一把之后互等——经典 AB-BA。

lockdep 的三个盲区，必须知道。① 它只看跑到过的路径——测试没覆盖到的加锁组合它一无所知，所以 lockdep 的有效性直接取决于你的测试覆盖率。② 它只认识内核的锁原语——你自己用原子标志 + 忙等搓的「土制锁」、用 completion 拼出的等待关系、跨内核-用户态的依赖（比如内核等一个用户态守护进程回话），它全都看不见，而这些恰恰是自研模块里死锁的重灾区。③ 它不检测数据竞争——「这个变量根本没被任何锁保护」不在它的职责范围内，那是 KCSAN 的活。另外它开销很大（每次加锁都要查图、记账），只用于开发和测试内核，生产内核不开。
lockdep 一旦报过一次警，就会把自己关掉（后续报告不再产生），因为它的内部状态已经可能不一致了。所以第一份报告最珍贵——不要在看到一条警告后继续跑，指望攒一批再看。同理，看到 Tainted: 里有 W（曾经 WARN 过）时要往上翻日志找第一条。

  • lockdep：锁的顺序与上下文用错 → 死锁风险。看的是「锁之间的关系」。
  • KCSAN：缺少同步的并发访问 → 数据竞争。看的是「访问与访问之间有没有同步」。它能发现 lockdep 完全看不到的「这里压根没加锁」。
  • KASAN：内存错误——越界、use-after-free、double-free。它和本篇的关系比看起来紧密：RCU 的延迟释放会让 UAF 推迟很久才暴露，等到崩溃时早已看不出是谁释放的。KASAN 用影子内存记录每块内存的状态，并在报错时同时打出分配栈和释放栈——「谁 kfree 的」这个关键问题它能直接回答。调 RCU 相关的 UAF，KASAN 基本是唯一有效手段。
  • 三者独立、可同时开（开发内核里推荐全开）。共同点是都很慢：KASAN 约 2–3 倍开销，KCSAN 视采样率而定，lockdep 在锁密集路径上也能有几倍。它们都属于「开发/CI 内核」，不上生产。

  • 所有错误分支都释放了锁——用统一的 goto unlock; 收口，别每个分支各写一遍。

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础为什么持有自旋锁期间绝对不能睡眠？

    三层理由，从「性能差」到「必然死锁」：

    ① 别人在烧 CPU 等你
    自旋锁的等待者不睡觉，就在循环里空转。你睡 5 ms，其他等锁的 CPU 就空转 5 ms——几百万条无用指令，还伴随持续的 cacheline 争用。自旋锁的全部前提是「等待极短」，睡眠直接摧毁这个前提。
    ② 同 CPU 上会真死锁
    spin_lock() 在主线内核里包含 preempt_disable()，睡眠会强行 schedule()。调度器可能选中同一个 CPU 上另一个也要这把锁的任务——它拿不到锁（持锁者在睡）于是自旋，而持锁者需要这个 CPU 才能醒过来继续跑。互等，这个 CPU 死了。
    ③ 中断上下文没有「睡眠」这个概念
    中断处理程序借用某个无关任务的内核栈，它不是可调度实体。让它睡 = 把那个倒霉任务永久挂起，而且没有任何人会来唤醒「这个中断」。
    怎么被发现
    开 CONFIG_DEBUG_ATOMIC_SLEEP，可能睡眠的函数入口的 might_sleep() 会在 preempt_count != 0 时打印 BUG: sleeping function called from invalid context。不开的话你看到的会是更晚更难懂的 BUG: scheduling while atomic——那行末尾的十六进制数就是 preempt_count。
    最容易踩的几个「隐形睡眠」
    kmalloc(GFP_KERNEL)（要换 GFP_ATOMIC）、copy_to_user（可能缺页）、mutex_lock、synchronize_rcu、msleep。以及任何你没读过实现的第三方内核函数——这是最现实的一条。
  2. 基础spin_lock / spin_lock_bh / spin_lock_irq / spin_lock_irqsave 怎么选？为什么 irqsave 比 irq 更安全？

    选择依据只有一句：和谁竞争，就关谁。先把所有会访问这份数据的代码路径列出来，看它们跑在什么上下文：

    • 只有进程上下文（多 CPU 的系统调用/内核线程）→ spin_lock()（只需挡住其他 CPU + 本 CPU 抢占）
    • 还会被软中断 / tasklet / NAPI 访问 → 进程侧 spin_lock_bh()
    • 还会被硬中断处理程序访问 → 进程侧 spin_lock_irqsave()
    • ISR 自己那一侧用 spin_lock() 就够——它已经在关中断的状态下运行
    irqsave vs irq
    spin_unlock_irq() 是无条件打开中断；spin_unlock_irqrestore() 是恢复到进来时的状态。差别在于「函数被谁调用」：如果上层调用者本来特意关了中断，你用 _irq 版本就会在返回时把中断悄悄打开，破坏上层的保护——而且不产生任何警告，只表现为极低概率的数据损坏。
    结论
    irqsave 的代价只有一条读标志寄存器的指令，换来的是「这个函数可以被任何上下文安全调用」这个可组合性。驱动里一律用 irqsave。spin_lock_irq() 只在「能确定调用者一定是开着中断的顶层路径」时才合法，内核核心代码里有这种用法是因为那里的调用关系被严格审过。
    容易漏的一条
    同一种软中断在同一个 CPU 上不会重入，但在不同 CPU 上可以并发。所以多队列 NAPI 的 poll 函数之间访问共享数据，仍然需要 spin_lock()——「都是软中断所以不用锁」是错的。
  3. 基础READ_ONCE() / WRITE_ONCE() 为什么必须存在？直接用 volatile 不行吗？

    因为编译器对普通内存访问的优化权力比大多数人想象的大，而这些优化在单线程语义下全都合法。最经典的例子：

    while (!ready)      /* ready 由另一个 CPU 置 1 */
    ;
/* 编译器可以合法地变成：
     if (!ready) for (;;) ;     ← 永久死循环
   因为循环体内没有任何东西修改 ready，
   「每次重新读」是可以省掉的。 */

    除了这种合并读，编译器还会做：合并/删除写（状态机丢一步）、读撕裂（把 64 位读拆成两个 32 位读，拼出一个从未被写过的值）、写撕裂、凭空多读（寄存器不够用时把值丢掉重读一遍，导致「先检查后使用」两次读到不同值）。READ_ONCE/WRITE_ONCE 的本质就是一次带 volatile 语义的访问，用来禁止这一类变换。

    为什么不用 volatile 变量
    ① 解决不了真正的问题——volatile 不产生任何 CPU 屏障，在 ARM 上照样会读到 ready==1 但数据是旧的；② 把优化全面关掉——这个变量的所有访问都变 volatile，包括已经在锁里、本可以放寄存器的那些；③ 掩盖意图——看代码的人无法知道哪次访问是「真的要求每次都读」。内核文档 volatile-considered-harmful.rst 明确不建议这么做。
    必须记住的一条
    READ_ONCE 不是屏障。它只挡编译器，不挡 CPU 乱序。「READ_ONCE 齐全但没有 smp_rmb()」的代码在 x86 上（TSO，读读不重排）能跑一万年不出错，换到 ARM64 上立刻炸。这是国产 ARM 服务器普及后大量存量代码暴露出的真实问题。
    反过来也要注意
    已经在锁保护下的访问不需要 READ_ONCE——锁的 acquire/release 已经包含编译器屏障。滥用它会让评审者误以为「这里有无锁并发」。
  4. 基础RCU 里的「宽限期」是什么？为什么需要它？

    宽限期（grace period）：从「写者完成指针替换」这一刻算起，到「所有在替换之前就已经进入读侧临界区的读者都退出」为止的这段时间。

    为什么需要它：RCU 的读者不加锁、不阻塞，所以写者替换指针的那一刻，可能有一堆读者手里正拿着指向旧对象的指针在读。写者不能立刻 kfree 旧对象——那就是 use-after-free。它必须等到「确信再也没有人能引用旧对象」为止，这个等待就是宽限期。

    关键：它不需要等谁
    宽限期只需要等「跨越了替换点」的那些读者。替换之后新进入的读者只能看到新指针，本来就拿不到旧对象，不必等。而且写者完全不需要知道到底有哪些读者——正是这一点让读侧可以做到零记账、零开销。
    怎么判断宽限期结束
    靠静止状态（quiescent state）——一个 CPU「此刻肯定不在任何 RCU 读侧临界区里」的可判定时刻。非抢占内核里读侧临界区是关抢占的，所以一次上下文切换、进入 idle、返回用户态都足以证明。宽限期的实现就是等每个 CPU 都至少经过一次静止状态。
    由此推出两个实用结论
    ① 宽限期是毫秒量级（要等所有 CPU 都过一次静止状态），所以 synchronize_rcu() 不能放在热路径上；② 「有 CPU 一直在内核里不让出」会让宽限期永远结束不了——这就是 RCU stall 报错的来源，也是为什么长循环里要插 cond_resched()。

10.2 中级（区分熟练度）

  1. 中级为什么说「内存屏障总是成对出现」？只在写侧加屏障会怎样？

    因为屏障约束的只是「同一个 CPU 上，我自己的访问之间的顺序」。写侧的 smp_wmb() 保证「我发出去的写，对外可见的顺序是 A 先于 B」；但它管不到读侧的 CPU——读侧的 CPU 完全可以推测执行，提前把 B 读了，之后才去读 A。那么读侧看到的仍然是「B 新 A 旧」，写侧的努力白费。

    标准的成对模式是发布-订阅：

    /* 写侧 */
p->len = 4096;
p->data = buf;
smp_store_release(&gp, p);   /* ① 保证内容先于指针可见 */

/* 读侧 */
q = smp_load_acquire(&gp);   /* ② 保证拿到指针后才读内容 */
if (q)
    use(q->len, q->data);

    只有 ① 没有 ②：读侧 CPU 提前读了 q->len（旧值/垃圾），之后才确认 gp。只有 ② 没有 ①：写侧的 gp 先落地，p->len 还在 store buffer 里，读者拿到指针读到未初始化的内容。两种情况的结果一样糟。

    配对关系
    smp_store_release ↔ smp_load_acquire；smp_wmb ↔ smp_rmb；rcu_assign_pointer ↔ rcu_dereference（RCU 就是这个模式的一个特化）。看到代码里一个孤零零的 smp_mb()，第一反应应该是「它的对儿在哪」。
    不要指望控制依赖
    「读侧有 if (q) 判断，CPU 总不能在不知道 q 是否为 NULL 时就读 q->len 吧？」——它真能。分支预测 + 推测执行会先把 load 发出去，预测错才回滚。控制依赖对后续的 load 完全不构成顺序保证。（地址依赖是另一回事，那个由 READ_ONCE/rcu_dereference 保证。）
    为什么在 x86 上测不出来
    x86-64 是 TSO，只允许「写→读」这一种重排。所以 smp_rmb()/smp_wmb() 在 x86 上编译成纯编译器屏障、零指令——少写一个完全没影响。到 ARM64 / POWER 上立刻暴露。写内核同步代码必须按最弱的内存模型思考，不能按测试平台。内核有形式化模型和 tools/memory-model/ 下的验证工具可以帮你判断。
  2. 中级seqlock 的读侧有哪些限制？为什么不能在读侧读到一个指针就解引用？

    seqlock 的读侧模型是「读序号 → 读数据 → 再读序号，不等就整段重试」。它的所有限制都来自这个模型的两个事实：读侧临界区可能被执行多次，而且期间读到的数据可能是撕裂的、互相矛盾的。

    • 必须可以安全地重跑：不能有副作用——不能改全局状态、不能 printk、不能分配/释放内存、不能唤醒任务。
    • 只能把数据原样拷到局部变量，等 read_seqretry() 通过之后再用。在重试循环里做判断、算下标、做除法（可能除零）都是 bug——那些计算是基于可能矛盾的数据做的。
    • 写者会饿死读者：写侧持续不断时读者可能一直重试。所以它要求「写少到读者几乎撞不上」，不只是「写比读少」。
    • 读侧不宜太长：拷贝的字段越多，撞上写窗口的概率越大。
    为什么绝不能解引用读到的指针
    因为那个指针值可能是半新半旧拼出来的野值（写者正在改它的时候你读了它）。解引用一个野指针 = 立刻 oops——而这发生在 read_seqretry() 有机会告诉你「数据不一致，重试」之前。重试机制只能在你读完之后才生效，它救不了一次已经执行了的非法访问。要保护含指针的结构，用 RCU，不要用 seqlock。
    它的甜点场景
    「一组必须彼此一致的标量，读极多写极少」。内核最著名的使用者是 timekeeping：clock_gettime() 要读「上次更新的时刻 + 周期数 + 乘数 + 移位」这一整组字段，调用频率每秒可能上百万次，写侧只在时钟中断里更新。读侧零写入 → 几十个核并发调用互不影响，这是 rwlock 做不到的。
    与 RCU 的分工
    seqlock 保护值（一组标量的一致快照），RCU 保护对象（可以安全解引用的指针）。seqlock 的写者原地改、不需要额外内存、不需要延迟释放；RCU 的写者要拷贝 + 等宽限期。所以「读一组计数器」用 seqlock，「读一张会增删条目的表」用 RCU。
  3. 中级per-CPU 变量为什么快？它的代价是什么？什么时候不该用？

    快的原因很朴素：它不共享，所以不需要任何同步。一份数据每个 CPU 一个副本，各自只碰自己那份——不需要锁、不需要原子指令、不需要屏障，this_cpu_inc() 在 x86 上就是一条带段前缀的普通 inc，约 1 ns 且零争用。对比一下：atomic64_inc 在多核同时写同一条 cacheline 时会退化到几十甚至上百纳秒，而且随核数恶化。

    唯一要防的不是「别的 CPU」，是「自己漂移到别的 CPU」：拿了 this_cpu_ptr() 之后如果被抢占并迁移，后面的操作就写到别人的副本上去了。所以要用 get_cpu_ptr()/put_cpu_ptr()（内含关/开抢占），或者确认自己已经在关抢占/关中断/持自旋锁的上下文里。

    三个代价
    ① 内存放大——256 核上就是 256 份，结构体里塞个 4 KB 缓冲就是 1 MB；② 汇总是 O(CPU 数) 且不便宜——某个 /proc 统计被监控系统每秒采一次，就是每秒 256 次跨 NUMA 的 cache miss，历史上多次成为大核数机器上的性能问题；③ 拿不到一致快照——遍历过程中前面的 CPU 还在改，总数永远是近似值。
    什么时候不该用
    ① 业务需要精确总数（比如「计数必须严格等于 0 才能释放资源」）——近似值不够，要么加额外的同步，要么别用 per-CPU；② 读侧也很热——读写都热的话 per-CPU 只是把开销搬了个地方；③ 数据本身很大——内存放大扛不住。这时可以退一步用 percpu_counter：本地累加，攒够 batch 才碰一次全局值，用「误差 ≤ batch × CPU 数」换 O(1) 的粗读。
    遍历要用 possible 而不是 online
    for_each_possible_cpu()，不是 for_each_online_cpu()。CPU 下线之后它的 per-CPU 副本还在，里面攒的数还算数；用 online 会在 CPU 热插拔后静默丢数据，表现为「统计值突然变小」。
    往上抽一层
    per-CPU 和 RCU 是同一个设计原则的两个方向：先判断读写比例，再把开销挪到频率低的那一侧。RCU 是「读多写少 → 开销全给写侧」，per-CPU 计数器是「写多读少 → 开销全给读侧」。能识别出这一点，比记住 API 更重要。
  4. 中级synchronize_rcu()、call_rcu()、kfree_rcu() 分别在什么时候用？
    API行为上下文用它的时候
    synchronize_rcu()阻塞到宽限期结束只能进程上下文（会睡）；不能在 RCU 读侧临界区里调（自己等自己，必死）低频操作：配置变更、模块卸载、设备移除。代码最直白，返回后可以放心 kfree
    call_rcu(&p->rcu, fn)立刻返回，宽限期后回调 fn几乎任何上下文，包括中断和原子上下文写侧不能阻塞时；释放逻辑不只是 kfree（要先 put 引用、解注册）
    kfree_rcu(p, rcu)宽限期后自动 kfree(p)同 call_rcu释放动作就是一次 kfree 时的首选，也就是绝大多数情况
    选择规则
    能用 kfree_rcu() 就用它；释放逻辑复杂用 call_rcu()；只有「我必须确认旧对象彻底没人用了才能往下走」才用 synchronize_rcu()。第三种情况远比想象的少——大多数写侧其实不关心旧对象何时真的被释放，只需要保证「最终会释放」。
    call_rcu 的三个坑
    ① 回调在软中断上下文执行，里面不能睡；② 模块卸载前必须 rcu_barrier()，否则回调函数所在的代码段已被卸载，调用时直接 oops（kfree_rcu 不需要，因为没有模块代码被调用）；③ 回调洪水会 OOM——见下。
    批量删除千万别每条都 call_rcu
    清空一张几百万条的表时逐条 call_rcu，回调队列会无限增长，内存被一堆「已经没人用但还没释放」的对象吃光。slabtop 里那个 slab 暴增，但代码逻辑上「都删掉了」。正确做法：把整批节点摘到本地链表，调一次 synchronize_rcu()，然后统一 kfree——一个宽限期解决 N 个对象。RCU 内部有回调洪水检测（rcutree.qhimark 默认 10000）会加速宽限期，但那只是缓解，代价是 CPU 尖峰和延迟抖动。
    rcu_barrier ≠ synchronize_rcu
    synchronize_rcu() 只等宽限期；rcu_barrier() 还要等所有已排队的回调真的执行完。两件事，别混。模块 exit 路径要的是后者。

10.3 高级（体现深度）

  1. 高级RCU 读侧为什么能做到「零开销」？这个开销去哪了？

    关键在于 rcu_read_lock() 不是一把锁。它不与任何人互斥（写者可以在你读的时候照样改）、不会失败、不会阻塞、不会重试、多个读者之间毫无交互。它做的唯一一件事是标记出「我正在读」这段区间，好让写者能判断宽限期结束了没有。

    而「标记一段区间」这件事，在非抢占内核里可以做得极其便宜：读侧临界区只要关抢占，那么「这个 CPU 发生了一次上下文切换」就自动证明了「它已经不在任何读侧临界区里」。于是 rcu_read_lock() 展开成 preempt_disable()——而在不需要抢占计数的配置下，这几乎不产生任何指令，只剩一个编译器屏障。这就是「零开销」的字面含义：没有原子指令、没有屏障指令、没有 cacheline 争用、没有任何写内存。

    抢占式内核里呢
    读侧临界区可以被抢占，所以「上下文切换」不再能证明「不在临界区里」。此时它需要在当前任务上维护一个嵌套计数，并在被抢占时把这个任务记录下来，让宽限期把它也等上。具体实现各版本有差异，但对使用者暴露的行为一致：读侧不阻塞、不失败、不能主动睡眠。开销比非抢占内核大，但仍然远低于任何一把真锁。
    开销去哪了：全给写侧
    ① 写侧必须拷贝一份对象（不能原地改，否则读者会看到半新半旧）；② 必须等一个宽限期（毫秒量级）才能释放旧对象；③ 期间旧对象一直占着内存；④ 写者之间还需要另一把普通锁来互斥（RCU 完全不管这个）。所以 RCU 的本质是一笔交易：用「写侧贵一个数量级」换「读侧便宜到接近零」。读写比 1000:1 时这笔交易划算得离谱，写比读多时是纯负优化。
    相应的硬约束
    零开销是有代价的——因为读侧不记账，所以指针的有效期严格限于 rcu_read_lock()/rcu_read_unlock() 之间，出了 unlock 立刻失效，不能存到全局、不能带出函数。要延长使用期，标准做法是在临界区里 refcount_inc_not_zero() 拿一个引用——RCU 保护「查找的过程」，引用计数保护「使用的过程」。get_task_struct()、socket 查找、dentry 查找都是这个套路。
  2. 高级什么场景下 RCU 是错误选择？举出至少三类并说明原因。

    RCU 有三个前提，缺一不可：读远多于写、能容忍读到稍旧的数据、对象可以延迟释放。任何一条不成立就要换方案。

    ① 读者必须看到最新值
    最典型的是权限/策略检查：不能允许「策略已经收紧了，但某些读者还在用旧策略放行」。RCU 只保证最终一致——写者替换指针后，读者可能在整个宽限期内继续看着旧版本。这类要求「立即生效」的语义只能用锁（或者用 synchronize_rcu() 阻塞到确认为止，但那就付了阻塞的代价，RCU 的优势也没了）。
    ② 写侧也很热
    计数器、队列的头尾指针这类每次操作都在改的数据。用 RCU 等于每次都要分配一个新对象、拷贝、等一个宽限期——比加锁贵几个数量级。经验阈值是读写比至少 10:1，理想 100:1 以上。这类数据的正确答案是 per-CPU（如果是计数）或普通自旋锁。
    ③ 需要立刻回收资源
    对象很大（几 MB 缓冲）、或者持有稀缺资源（文件描述符、DMA 通道、硬件寄存器窗口、许可证）。宽限期是毫秒量级，高频增删下延迟释放会累积成资源耗尽——而且这种 OOM 特别难查，因为内存不在任何进程账上，slabtop 才看得见。
    ④ 读侧要睡眠
    普通 RCU 的读侧临界区里不能睡（copy_to_user、mutex_lock、GFP_KERNEL 分配都不行）。这种情况要用 SRCU——它允许读侧睡眠，而且每个域独立（一个域里的慢读者不会拖累内核其他部分）。代价是读侧不再零开销（要维护 per-CPU 计数，有真实的原子操作与屏障），宽限期也可能更长。
    ⑤ 数据结构不适合「替换式更新」
    RCU 要求「读者要么看到旧版本、要么看到新版本，不能看到中间态」。能靠一次原子指针替换完成的更新（换一个对象、链表增删）最适合。反过来，需要同时改多个位置才能保持不变式的结构（比如平衡树的旋转、双向索引的同步更新）用 RCU 会非常别扭——要么设计成「重建整棵子树再替换」（写侧极贵），要么就得承认读者可能看到不一致的中间态。
    怎么答得更好
    不要只罗列场景，说出判断流程：先量读写比例（有没有到 10:1）→ 再问业务能不能容忍陈旧读 → 再问对象延迟几毫秒释放有没有问题 → 最后确认读侧不需要睡眠。四个都过了才上 RCU，否则老老实实用锁或 per-CPU。「知道什么时候不用某个技术」通常比「知道怎么用」更能体现工程判断力。
  3. 高级lockdep 能发现哪些「真死锁发现不了」的问题？它的盲区在哪？

    lockdep 的核心价值：它检测的不是「现在死锁了」，而是「这套加锁模式在某种时序下可能死锁」。原理是给每个锁归一个「锁类」，运行时记录每一对「持有 A 时获取 B」的先后关系，构建有向图，一旦出现环就报警。

    这带来一个质变
    真死锁需要「两个 CPU 恰好在特定时刻交错」——可能一年触发一次，触发时整机 hang、没有 dump。而 lockdep 只需要那两条代码路径【各自】被执行过一次（不需要同时、不需要交错），就能把环画出来并报警。这把概率性 bug 变成了确定性检测，从「靠运气发现」变成「靠覆盖率发现」。

    它能发现的几类，真死锁都很难自然触发到：

    • AB-BA 环（含 A→B→C→A 的多跳环）：两条路径可能分别在两个完全不同的业务流程里，正常运行时永远不交错。
    • 中断上下文不一致（inconsistent lock state）：同一把锁有时在开中断的进程上下文拿、有时在硬中断里拿。真死锁只在「中断恰好打断持锁者、且在同一个 CPU 上」时发生——多核机器上这个概率极低，可以潜伏数年。
    • RCU 用法错误（suspicious RCU usage）：rcu_dereference() 在读侧临界区之外被调用。这个错误永远不会「死锁」，只会在极偶然的时机产生 UAF——不靠工具几乎不可能发现。
    • 返回用户态时还持着锁：错误路径漏了 unlock。这往往只在某个罕见的 goto err 分支上，正常测试根本走不到。
    • 等待类型冲突（-{3:3} 那部分）：在 raw_spinlock 里拿 mutex——在主线内核上可能只是「不优雅」，在 PREEMPT_RT 上是必死。
    三个盲区（这才是区分深度的部分）
    ① 只看跑到过的路径——没被测试覆盖的加锁组合它一无所知，所以 lockdep 的有效性直接取决于测试覆盖率（包括错误注入、热插拔、模块反复加载卸载这些冷路径）。② 只认识内核的锁原语——你自己用原子标志 + 忙等搓的「土制锁」、用 completion 拼出的等待关系、内核等一个用户态守护进程回话形成的跨态依赖，它全都看不见，而这些恰恰是自研模块里死锁的重灾区。③ 不检测数据竞争——「这个变量根本没被任何锁保护」不在它职责内，那是 KCSAN 的活。
    两个实操细节
    ① lockdep 报过一次警就会把自己关掉（内部状态可能已不一致），所以第一份报告最珍贵，不要攒一批再看，看到 Tainted: ...W... 要往上翻找第一条。② 读报告先跳到最后的 Possible unsafe locking scenario 方框——lockdep 已经把「怎么死」画成了两栏时序图，那是信息密度最高的部分；再回头看 -> #1/-> #0 两段栈，它们分别是「历史上那条边」和「现在这条边」的完整调用路径，修复就是在这两条路径里选一条改掉。
    合法的「同类嵌套」要显式告知
    报 possible recursive locking 不一定是真递归——也可能是「同一个锁类的两个不同实例」的合法嵌套（比如同时锁父子 inode）。此时用 mutex_lock_nested() / spin_lock_nested() 把层级显式告诉 lockdep，而不是把警告关掉。报告里两个锁实例地址相同才是真递归。
  4. 高级内核的同步原语和 C++ 的 memory_order 怎么对应？从 C++ 转内核开发最容易踩什么？

    两套模型的底层机器语义是同一套（毕竟跑在同一个 CPU 上），差别在默认值和表达方式。

    Linux 内核C++ 等价物注意
    READ_ONCE(x)x.load(memory_order_relaxed)内核版额外保证地址依赖序
    WRITE_ONCE(x, v)x.store(v, memory_order_relaxed)基本一致
    smp_load_acquire / smp_store_releaseload(acquire) / store(release)语义一致，这是最好用的一对
    smp_mb()atomic_thread_fence(seq_cst)工程上按等价用
    smp_wmb() / smp_rmb()没有对应物C++ 只有 acquire/release/seq_cst 三档 fence，没有单向的读读/写写屏障。内核有，因为它要贴近硬件省开销
    barrier()atomic_signal_fence(seq_cst)都只约束编译器。C++ 里服务于信号处理函数，内核里服务于中断处理程序——是同一个问题
    rcu_dereference()无（memory_order_consume 是个死掉的设计）内核靠「编译器不许破坏地址依赖」这条工程约定实现，C++ 的标准化尝试失败了
    最大的坑：默认值反了
    C++ 的 std::atomic 默认 memory_order_seq_cst——不写就是最强序，所以 cnt++ 天然安全。内核的 atomic_inc() 默认最弱——原子但什么序都不保证。从 C++ 转过来的人最容易带着「原子操作自带同步」的直觉写内核代码，结果所有「没写序」的地方语义都反了。内核的规则是：无返回值的 RMW（atomic_inc、set_bit）无序；有返回值的 RMW（atomic_add_return、test_and_set_bit）是全屏障；cmpxchg 成功时全屏障、失败时无序。
    第二个坑：上下文这件事在 C++ 里不存在
    用户态所有代码都跑在「可以睡眠」的上下文里，所以 C++ 从来不需要区分「这段代码能不能阻塞」。内核里这是第一判据：会被中断访问的数据只能用自旋锁（无论临界区多长），临界区里要 copy_to_user 就只能用 mutex（无论多短）。把「长短」当成选锁的首要依据，是用户态思维的残留。
    第三个坑：失败的后果不一样
    用户态死锁 = 一个进程卡住，gdb 上去看栈，kill 掉重启。内核死锁 = 整机 hang，没有 dump、没有日志（可能连 console 都刷不出来）。所以内核的工程实践重心完全不同：不是「出问题了怎么调试」，而是「怎么让问题在第一次跑到时就被工具抓住」——lockdep、KCSAN、KASAN、DEBUG_ATOMIC_SLEEP 全开，配 kdump 兜底。
    可以带过去的经验
    发布-订阅（release/acquire 配对）的思维方式是完全通用的；「屏障成对」在两边都成立；「先判断读写比例，再把开销挪到频率低的那一侧」这个原则在两边都对（用户态的 seqlock 手法、读多写少的 hazard pointer / epoch-based reclamation 本质就是 RCU 的用户态版本）。而内核额外多给你的东西是：LKMM 有形式化模型和 tools/memory-model/ 下的验证工具，可以把你的同步模式在最弱架构上跑一遍判断是否成立——这比在 x86 上压测靠谱得多。
