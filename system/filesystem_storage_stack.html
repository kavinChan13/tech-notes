一次 write() 的完整旅程

每一层都有一个缓存，每个缓存都是一个丢数据的机会

write() 返回成功，只表示数据进了某一层缓存。到盘片要穿过四个独立缓存，失效场景完全不同：进程崩溃、内核 panic、机器掉电、设备固件谎报。下图每一层标了「谁丢什么」。

把写文件想成寄一份合同。你把文件塞进办公室的出件篮（glibc 缓冲区）——你走了，篮子里的东西没人管；行政每小时来收一次，放进公司的待寄堆（页缓存）——公司着火，还是没了；快递员每天来取，装上车（设备写缓存）——车翻了也没了；只有对方签收那一刻，合同才算真的送到。write() 返回成功，只等于「塞进出件篮了」。

先把「谁丢什么」分清楚

失效场景会丢什么怎么防
进程被 SIGKILL / 段错误只丢 glibc stdio 缓冲区里的内容用裸 write()，或 fflush()。数据一旦进内核就与进程生死无关
内核 panic / 机器掉电页缓存里所有脏页（默认可以攒到 30 秒 + 内存的 20%）fsync() / fdatasync()，或 O_DSYNC
掉电，但文件系统挂了 nobarrier设备写缓存里的内容，即使 fsync 返回成功不要关 barrier；或者用带掉电保护电容的企业级盘
掉电，廉价 SSD / U 盘谎报 FLUSH 完成同上，而且你无法从软件侧发现选盘。这是硬件采购问题，不是代码问题
只 fsync 了文件、没 fsync 父目录文件内容在，但文件名可能不存在fsync 父目录的 fd（见 §5）

四层缓存的失效彼此独立：stdio 只怕进程死；页缓存怕掉电和 panic；设备写缓存怕掉电且没 FLUSH；盘片才怕介质损坏。所以「加一个 fsync」挡不住 fwrite 没 fflush，也挡不住 nobarrier，更挡不住廉价 SSD 谎报 FLUSH。每一层要用那一层的原语去推。

stdio：终端 vs 文件

fwrite 不到 4 KB 或不遇到换行，根本不会进内核。日志少了最后几百行，八成停在用户态。

输出目标缓冲write() 次数kill -9 会丢
终端行缓冲每行一次当前未换行的那一行
重定向到文件全缓冲 4 KB攒满才发最后不满 4 KB 的那一批
写日志绕开 stdio。裸 write()（常规文件加 O_APPEND）或 setvbuf(..., _IOLBF, 0)。信号杀死时 atexit 不跑；fork 后子进程 exit() 还会把父进程缓冲区再吐一遍（见 多进程与 IPC）。fsync 管不到 glibc 缓冲区——fwrite 之后不 fflush，fsync 的是空的内核缓冲，用户态那批字节崩溃时照样消失。这是「我明明 fsync 了怎么还丢」的第一号误诊。

02

VFS 的四个核心对象

文件名不在 inode 里——这一句能解释一大半疑问

Linux 支持几十种文件系统，但应用只见到一套 open/read/write/stat。中间这层抽象叫 VFS（Virtual File System），它定义了四个核心对象和一组函数指针表（super_operations、inode_operations、file_operations、dentry_operations）。具体文件系统只要填这些表，就能挂到 VFS 上。理解这四个对象的分工，是读懂后面所有内容的前提。

对象内核结构体代表什么生命周期存不存在磁盘上
superblockstruct super_block一个已挂载的文件系统实例：块大小、inode 总数、空闲计数、日志位置、特性标志挂载到卸载是（且 ext4 在每个 block group 留了备份）
inodestruct inode一个文件本体：类型、权限、uid/gid、大小、三个时间戳、链接数、数据块映射被引用期间常驻内存，之后回收是（ext4 默认 256 字节一个）
dentrystruct dentry一个名字到 inode 的绑定，以及它在目录树里的位置（父子关系）纯缓存，可随时回收重建否——磁盘上是目录文件里的目录项记录
filestruct file一次打开：当前偏移 f_pos、打开标志、引用计数open 到最后一个引用 close否，纯运行时状态
inode：index node 的缩写。它是文件的全部元数据加数据块索引，唯一标识是「superblock + inode 号」。inode 里没有文件名——名字存在目录里。目录本身也只是一个特殊类型的文件，它的数据内容就是一串「名字 → inode 号」的记录。

两个进程打开同一个文件，是两个 struct file、两份 f_pos。lseek 互不影响。dup / fork 才共享同一个 struct file（fork 后父子的偏移会一起走）。「打开」和「文件」不是一回事：这是 O_APPEND 必须由内核在每次 write 时取文件末尾、而不能靠用户态 lseek 的原因。

硬链接、符号链接、unlink 仍占空间

硬链接不是快捷方式，是给同一个 inode 再起一个平等的名字。rm 是 unlink：只拆掉「名字 → inode」，空间要等 i_nlink == 0 且 i_count == 0 才释放。

维度硬链接 ln符号链接 ln -s
本质目录项里多一条指向同一个 inode 的记录一个独立的 inode，其数据内容是一段路径字符串
占 inode不占（只多一条目录项）占一个（ext4 里路径 ≤ 约 60 字节时直接存在 inode 的 i_block 区，不额外占数据块，称为 fast symlink）
能跨文件系统不能——inode 号只在自己的 superblock 内唯一，跨挂载点没有意义，ln 直接返回 EXDEV能——它存的是路径字符串，指向哪都行，甚至可以指向不存在的路径
能指向目录不能（EPERM），只有内核自己维护的 . 和 .. 是例外能
目标被删后照常可用，链接数减一而已变成悬空链接，访问返回 ENOENT
解析成本零，就是一次普通查找每次访问都要读出内容再重新走一遍路径解析（内核限制递归深度，超了返回 ELOOP）
权限位就是 inode 的权限符号链接自己的权限位无意义（永远显示 777），实际检查的是目标
「visited inode 集合」挡不住目录硬链接成的环。合法的文件硬链接本来就会让同一个 inode 出现两次，遍历工具不能见重复就停。环会让 find/du 无法停机；「..」有多个父目录；引用计数收不回环。所以内核直接 EPERM。符号链接不进 nlink，默认不跟随。

i_nlink 是磁盘上的名字数，i_count 是内存里的打开数。运维只看见名字（ls、du），内核还看见打开（lsof）。两个计数对不上时，空间账就对不上。备份工具也可能把硬链接展开成两份数据：容量规划前先 find -links +1 看有没有大量共享 inode，否则「备份后体积翻倍」会吓一跳。硬链接不能跨文件系统（inode 号只在本 superblock 内唯一），ln 跨设备直接 EXDEV；符号链接存的是路径字符串，指向哪都行，也可以指向还不存在的目标，访问时才再走一遍路径解析。

dentry cache：slabtop 里几个 GB 不是泄漏

路径解析走 dcache（父 dentry + 名字 → 子 dentry）。否定结果也缓存：negative dentry 加速反复 stat 不存在的路径，也能让乱扫路径的程序把内存吃满。

命令目的判据
slabtop -o -s c看谁占 slabdentry（约 192 B × 百万级）和 ext4_inode_cache（约 1 KB）是大户
cat /proc/sys/vm/vfs_cache_pressure回收倾向100 默认；调大更激进收 dentry/inode；调小更倾向保留
这块算进 free 的 buff/cache，内存紧时会自动还。病态是压力已经很大 slab 还在涨。不要靠 drop_caches（§6）。动态链接器搜 .so、Python 找模块会反复 stat 不存在的路径——negative dentry 正是为此加速。反过来，乱扫随机路径能把 dcache 喂满；回收时路径解析会突然变慢，表现为「偶发 open 变卡」而不是泄漏告警。

rename() 原子性 ≠ 崩溃持久性

rename(old, new)：同一文件系统内，别人看到的要么是完整旧文件、要么是完整新文件，不会「不存在」或「半新半旧」。目标已存在则原子替换。
原地改文件像当众改一份正在被阅读的合同；rename 是旁边誊好再一把换掉。任何时刻看到的要么是完整旧版，要么是完整新版——这只保证别人看不见中间态。
原子性是命名空间可见性，不是掉电后还在。改名本身也只是页缓存里的元数据。「写临时文件 + rename」只解决并发可见，要持久必须 fsync(临时文件) + fsync(父目录)。完整写法在 §5。ext4 的 data=ordered 帮不上这个忙：它不保证新内容与新名字一起出现（§3）。

03

ext4 的磁盘布局

block group、extent、延迟分配、以及被误解最深的 data=ordered

ext4 是 Linux 上最保守也最普及的选择：它从 ext2 一路演进而来，兼容层厚、工具链成熟、故障案例库最全。理解它的磁盘布局有直接的实用价值——mkfs 时定错一个参数，可能要等到半年后文件系统「明明还有 40 GB 空间却创建不了文件」时才暴露。

block group：把整块盘切成小区

4 KB 块位图有 32768 位 → 每个 group 128 MiB。分配优先落在「inode 所在的 group」，元数据和数据挨着。

分配数据块时优先落在 inode 所在 group：机械盘少寻道，SSD 少读元数据页。ext4 的 group 只是位图分片，分配路径仍有全局串行点；XFS 的 AG 才是并发单元（§4）。sparse_super 只在 0、1 和 3/5/7 的幂次 group 备份 superblock；主 SB 坏了用 fsck -b 指定备份（BG1 总是有）。metadata_csum 只保护元数据，数据块位翻转 ext4 看不见——要端到端校验得上 Btrfs/ZFS。

命令目的判据
tune2fs -l看 mkfs 定下的全局参数Inode count 无法事后增加；state 不是 clean = 没正常卸载；Reserved 默认 5% 只给 root；Lifetime writes 看磨损
dumpe2fs看每个 group 的块号Reserved GDT 给 resize_inode 扩容；备份 super 在 BG1 等；INODE_UNINIT 表示该 group 的 inode 表还没真正初始化

inode 数量在 mkfs 时就定死了

ext4 inode 表预分配，格式化后无法增加。默认每 16 KB 配一个 inode（100 GiB ≈ 655 万）。海量 200 字节小文件会在空间只用 2% 时 ENOSPC，df -h 仍 98% free。没有事后补救，只能备份重 mkfs。XFS 动态分配（§4）。inode 耗尽时 creat 的 errno 和「盘真的满了」相同。监控如果只采 df -h 的 Use%，会在 inode 打满那天才第一次报警。数据盘必须同时采 df -i。

delayed allocation：write() 只在页缓存记账，物理块推迟到回写那一刻才挑——内核已经知道总长度，能拿一段连续空间。
ENOSPC 迟到

auto_da_alloc 检测到「rename 覆盖」和「truncate 到 0 再 close」会提前分配，不发 FLUSH、不管父目录。正确代码仍然自己 fsync。ext3 的 ordered 日志每 5 秒提交时，常常顺带把数据刷下去，坏代码侥幸没出事；ext4 延迟分配让数据待更久，元数据操作反而先落盘。POSIX 从没承诺不 fsync 能活过掉电。

jbd2：data=ordered 保证什么、不保证什么

日志：先把即将做的元数据顺序追加并提交，再改原地。崩溃后重放，不用全盘 fsck。解决的是「inode 说占了这块、位图说空闲」这种矛盾。
模式日志里记什么崩溃后保证写放大适用
data=journal 元数据 + 数据都进日志 最强：元数据一致，且已提交的数据本身也能从日志重放恢复 数据写两遍；且与延迟分配、O_DIRECT 不兼容 极少用。日志放在独立的快速设备上时才有意义
data=ordered
（默认）		 只有元数据；但强制数据块先落盘，再提交引用它的元数据 元数据一致，且不会读到别人的旧数据。但不保证你的数据不丢 正常（数据写一遍） 99% 的场景
data=writeback 只有元数据，且不约束顺序 元数据一致，但文件长度可能已更新而数据还没写 → 读到磁盘上残留的陈旧内容 最低 只写临时数据、且能容忍垃圾内容的场景。有信息泄露风险
data=ordered 保证元数据一致、不读到别人的旧数据，不保证你写的数据不丢。没 fsync 的文件崩溃后完全可能是空的或半截。想不丢，只能自己 fsync。
data=ordered 也不保证文件内容与 rename 原子。它只约束「提交引用这些块的元数据之前，数据块已经落盘」。rename 是另一次元数据操作，完全可以先于你刚写入、还在页缓存里的新内容提交。崩溃后：名字已经切到新文件，内容却是空的或半截——这就是 2009 年那批 0 字节配置。想「要么完整旧版要么完整新版」活过掉电，只能自己 fsync 临时文件再 rename 再 fsync 父目录（§5）。挂载选项替代不了。

04

XFS 与文件系统选型

allocation group 的并发红利，与「不能缩容」这道硬伤

ext4 从 ext3 稳妥演进；XFS 从第一天为大文件、大容量、高并发服务。2014 年起是 RHEL 默认。本质差别在分配器的并发结构。

allocation group：把「分配」并行化

AG：每个 AG 自带空闲空间 B+ 树、inode B+ 树和各自的锁。两个 CPU 上的线程可以同时在不同 AG 里分配，互不争抢。

agcount 按容量自动定，也可 mkfs.xfs -d agcount=N。线程数远大于 agcount 时加大可能有收益；盲目加大增加元数据开销。某个 AG 的空闲树先耗尽时，分配要跨 AG 重试——卷「看起来还有空间」但这个目录所在 AG 满了，创建变慢甚至 ENOSPC。这是 XFS 特有的「局部满」。xfs_info 还要看：crc=1 仍无数据块校验和、finobt、reflink、sunit/swidth（RAID 条带对齐）。

动态 inode：只要有空间就能建文件

XFS 不预分配 inode 表，按 64 个一组在需要时分配，inobt 索引。imaxpct 只是占用比例上限（xfs_growfs -m 可在线调），不是预留。查 inode 要走 B+ 树而不是算术，finobt 基本抹平了找空槽的开销。

延迟日志

往同一目录连建一万个文件，会把那个 B+ 节点改一万次。延迟日志在内存合并，只把最终结果写进日志，流量降一到两个数量级（2.6.39 起默认，现为唯一行为）。代价：崩溃可能丢更多「已经返回成功」的元数据操作——仍自洽，但 mkdir 成功后目录可能不在。需要持久的元数据，同样必须 fsync 父目录。reflink 拷贝只增加引用，第一次写入才真正 CoW；备份工具用它很快，但空间账要按「写满后」来算，和稀疏文件是同一类超卖。

两道硬伤

XFS 不能缩容，永远。不是没实现，是 AG 结构让在线搬迁极复杂。LVM 分大了想收回，只能备份重建。规划要保守：先给小，再扩（挂载状态下就能扩）。ext4 可缩，但必须先卸载。
早期崩溃后的 NULL 文件与 §3 的 0 字节同源：size 元数据先落盘、数据还在页缓存。现代内核已在提交 size 之前先刷数据。拿它当「XFS 不安全」过时了；真正的教训仍是——没有 fsync，任何文件系统都不承诺活过掉电。

持久化语义

全篇最重要的一章：数据到底什么时候真的落盘

测试环境不掉电，持久化 bug 只在机房断电、panic、云主机被强杀时爆发。每个 API 的语义必须精确。应用事故几乎都是把下一层的承诺当成了上一层：日志框架用 fwrite 当「崩溃不丢」；配置写入用 rename 当「掉电还在」；数据库用 O_DIRECT 当「已经进介质」。

你以为防住了实际只承诺到还要补什么
进程崩溃数据进了内核裸 write / fflush，不要停在 stdio
机器掉电页缓存不够，要进介质fsync / fdatasync，且不要 nobarrier
重启后还能按名字打开文件 fd 不够，要刷目录fsync(dirfd)

fdatasync 到底省了什么

fsync 还要提交 inode 全部元数据（含 mtime）——多一次日志事务 + 一次 FLUSH。fdatasync 只提交「读回数据所必需的」：原地覆盖、size 没变，就一条元数据都不用写。

WAL 为什么要预分配。每次追加都让文件变长，fdatasync 仍得写 size。PostgreSQL / MySQL 把 WAL 段预分配成定长（如 16 MB）再原地覆盖，每次提交从 3–4 次 I/O 降到 1–2 次。面试能讲到这一层，比背「fdatasync 不刷元数据」有说服力。
O_DIRECT 不等于持久。它只绕过页缓存，数据仍停在设备写缓存，元数据也没处理。之后照样要 fdatasync（或 O_DSYNC）。

不是每次 write 都该 fsync。日志、指标、可重建的中间结果：丢几秒可以接受，每条 fsync 会把吞吐打成设备 IOPS 上限。配置、WAL、已向用户 ack 的订单：必须 fsync。判据是「丢了能不能从别处重建，以及用户是否已经收到成功」。把日志当 WAL 刷，是把在线服务写成了每秒几十次 FLUSH 的单线程。

坑一：新建文件必须 fsync 父目录

unlink / rmdir 同样改目录项。做「先 rename 到 .trash 再异步删」的回收站，如果漏了 fsync 父目录，掉电后文件可能以旧名字复活，或者 .trash 里出现无名孤儿。持久化的是「目录树的这一刀」，不是「某个 inode 的内容」。

坑二：设备自己的写缓存

易失写缓存：几乎所有盘内部都有 DRAM，数据进 DRAM 就向主机报完成。掉电这块全没。要进介质，主机必须发 REQ_PREFLUSH（先刷缓存再处理）或 REQ_FUA（本请求穿透缓存）。这才是 fsync「贵」的原因：FLUSH 近似串行。

一次普通 write 进设备缓存只要几十微秒；一次 FLUSH 要把缓存里未落盘的都推到介质，机械盘数毫秒到几十毫秒，消费级 SSD 也常是毫秒级，而且近似串行——这就是数据库「每个事务一次 fdatasync」成为 TPS 上限的原因。WAL 预分配的意义是：能少一次 FLUSH 就少一次。

命令目的判据
hdparm -WSATA 写缓存1 = 开（掉电有风险）；0 = 关（延迟大涨）；重启失效，要写 udev
sdparm --get=WCESCSI/SASWCE=1 同写缓存开

不要为了性能挂 nobarrier。文件系统不再发 FLUSH/FUA，掉电时连日志提交顺序都没了。唯一可考虑：存储有电池/电容（BBWC / PLP）。看采购文档，不要猜。
廉价 SSD / U 盘收到 FLUSH 立即返回、实际没写完——软件无法检测。需要真持久性就上带 PLP 的企业级盘。消费级盘跑数据库，代码写得再对也挡不住。

坑三：fsync 失败之后数据在哪？（fsyncgate）

2018 年 PostgreSQL 披露的不是某个 bug，是被普遍误解的错误报告语义：

① 错误只报一次，之后 fsync 返回成功
回写失败时内核记下错误，同时清掉 dirty 标记。第一次 EIO，按「重试」思路再调，第二次返回 0——脏页没了，内核认为无事可做。应用于是截断 WAL，而数据已经不存在。
② 错误可能被别的进程吃掉
更早实现把错误记在 address_space 上，谁先 fsync 谁拿到。checkpointer 可能拿到一次干净的成功。
内核侧的改进
4.13 起 errseq_t：错误带序列号记在 file 上，每个 fd 至少看到一次打开之后的错误。修好了「谁拿到」。修不好「数据去哪了」——脏页已被丢弃。
把 fsync 失败当不可恢复的致命错误。不要重试、不要忽略。磁盘上是你无法观测的混合状态——哪些页写成功了、哪些被丢掉，内核不会给你一张清单。PostgreSQL 选择 panic 并从 WAL 重放。代码里 if (fsync(fd) < 0) { log_warn(...); } 然后继续跑，是定时炸弹。
close 返回值
延迟分配让 ENOSPC 迟到。write 成功、没调 fsync 时，错误可能在 close 才出现。忽略 close 等于丢掉最后一次报错机会。
写路径失败和读路径失败性质不同：读失败系统状态没变；写失败进入你无法观测的状态。有状态服务该停下来，从一个已知持久点重建。见 线上故障处置手册。持久化没法靠「跑一遍单测」证明：虚拟机里 write 之后 echo b > /proc/sysrq-trigger 模拟 panic；用 dm-flakey 注入写失败，看应用是 panic 还是重试 fsync。测试环境不掉电，是这类 bug 能活到生产的原因。

写文件的正确姿势：完整代码

#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <stdio.h>

// 原子且持久地把 buf 写成 dir/name。返回 0 成功，-1 失败（errno 有效）。
int write_file_durably(const char* dir, const char* name,
                       const void* buf, size_t len)
{
    char tmp[4096], dst[4096];
    snprintf(tmp, sizeof tmp, "%s/.%s.tmp.%d", dir, name, (int)getpid());
    snprintf(dst, sizeof dst, "%s/%s", dir, name);

    int fd = open(tmp, O_WRONLY | O_CREAT | O_EXCL | O_CLOEXEC, 0644);
    if (fd < 0) return -1;

    // ① write 可能【短写】，必须循环；EINTR 要重试
    const char* p = (const char*)buf;
    size_t left = len;
    while (left > 0) {
        ssize_t n = write(fd, p, left);
        if (n < 0) { if (errno == EINTR) continue; goto fail; }
        p += n; left -= (size_t)n;
    }

    // ② 数据 + 必要元数据落盘。新文件 size 变了，fdatasync 会连 size 一起写。
    //    ★ 失败就直接放弃，【绝对不要重试 fsync】——见 fsyncgate
    if (fdatasync(fd) != 0) goto fail;

    // ③ close 的返回值同样要检查：延迟分配的 ENOSPC 可能在这里才浮现
    if (close(fd) != 0) { fd = -1; goto fail; }
    fd = -1;

    // ④ 原子替换：读者看到的要么是完整旧版，要么是完整新版
    if (rename(tmp, dst) != 0) goto fail;

    // ⑤ ★★ 最容易漏的一步：让「这个名字存在」也持久化
    int dfd = open(dir, O_RDONLY | O_DIRECTORY | O_CLOEXEC);
    if (dfd < 0) return -1;
    if (fsync(dfd) != 0) { int e = errno; close(dfd); errno = e; return -1; }
    if (close(dfd) != 0) return -1;
    return 0;

fail:
    { int e = errno;
      if (fd >= 0) close(fd);
      unlink(tmp);                 // 不留 .tmp 垃圾
      errno = e; }
    return -1;
}
❌ 天真写法（绝大多数代码的样子）

fopen(..., "w") + fwrite + fclose，相信返回值。四种真实事故：① "w" 立刻截断到 0，别人读到空配置；② 数据停在 stdio 缓冲，进程被 kill → 文件永久 0 字节；③ 没 fsync，掉电后半截 JSON；④ 没检查 fclose，盘满错误被吞掉。

✅ 临时文件 → fsync → rename → fsync 目录

调用上面的 write_file_durably()。五道防线：临时文件（原文件始终完整）→ 裸 write 循环（无用户态缓冲）→ fdatasync（穿过页缓存和设备缓存）→ rename（原子切换）→ fsync(父目录)（名字也持久）。任一步失败返回 -1。解析失败不要覆盖已有配置——持久化正确 ≠ 内容合法。

短写不是异常：普通文件在被信号打断或磁盘将满时都可能 n < left。循环 + EINTR 是 write 的正确用法。失败路径必须 unlink 临时文件，否则堆 .tmp.pid。rename 成功但 fsync(dirfd) 失败时，读者已经能看到新文件——并发可见有了，持久性还没有，调用方必须当失败。父目录 fd 要用 O_DIRECTORY；跨目录 rename 两个父目录都要 fsync，漏一个比「两边都没有」更难查。

持久化自检清单

  • 写日志/数据用裸 write()，不用 fwrite；非要用就 setvbuf 改行缓冲。
  • write() 一律循环处理短写与 EINTR。
  • 需要持久的地方调 fsync/fdatasync，并检查返回值；失败当致命错误处理。
  • 新建文件、rename、unlink 之后 fsync 父目录；跨目录 rename 要 fsync 两个。
  • 检查 close() 的返回值——延迟分配的 ENOSPC 常常在这里才出现。
  • 需要「要么完全生效要么完全不生效」时用临时文件 + rename，绝不原地截断重写。
  • 不要挂 nobarrier，除非存储侧确实有电池/电容保护。
  • 不要把 O_DIRECT 当持久化手段。
  • 预分配定长 WAL 段文件，让 fdatasync 真正省掉元数据写。

页缓存与回写调优

脏页攒得越多吞吐越好，直到写者被一把按住

页缓存让重复读免费、写入可合并；脏页攒到阈值时，内核会把正在写的进程按住。这是「平时 p99 5 ms、每隔几分钟蹦到 2 秒」的常见根因。

脏页的三条回写路径

确认手法：循环打 Dirty，看是不是「缓慢攒高 → 与毛刺同时骤降」的锯齿。没有锯齿就不要调 dirty_*，去 §9。有锯齿再改 dirty_bytes。预算很具体：dirty_bytes ≈ 设备顺序写带宽 × 1～2 秒。调小 = 偶发大毛刺换成持续小开销。

fsync 很勤的服务（数据库）几乎不靠这套阈值，脏页活不过一次提交；毛刺更常出现在「吞吐型写入 + 大内存 + 很少 fsync」：日志聚合、备份、对象存储网关。cgroup 的 memory.high 会缩小 dirtyable 集合，容器里同样的 ratio 对应的绝对字节数比宿主小，表现为「同样代码在容器里更早被按住」。

参数默认语义与调优要点
vm.dirty_background_ratio10脏页占「可回收内存」的百分比超过它 → 后台回写启动，不阻塞写者
vm.dirty_ratio20超过它 → 写者在 balance_dirty_pages 里被同步限速。毛刺的直接来源
vm.dirty_background_bytes
vm.dirty_bytes		0（未启用）设成非零字节数会覆盖对应的 ratio。大内存机器强烈建议用 bytes：512 GB 内存上 20% 是 100 GB 脏页，一次回写风暴能把服务打死
vm.dirty_expire_centisecs3000（30 s）脏页「变老」的门槛，超过就在下一轮回写里被写出。它决定了「掉电最多丢多久的数据」的量级

vm.vfs_cache_pressure100回收 dentry/inode 缓存的倾向。调大更激进（省内存、路径解析变慢），调小更倾向保留
vm.swappiness60不直接管页缓存，但影响「回收匿名页还是文件页」的偏好。数据库主机通常调到 1–10

Dirty 是「还在内存、承诺要写但没写」；Writeback 是「已经交给块层、还没完成」。Dirty 高而 Writeback 接近 0：设备跟得上，只是阈值太松。两者都高：设备已经在吐，还是赶不上产量。只看 Dirty 会误判。

同一台机器，空闲内存多时 dirtyable 大，ratio 对应的绝对字节数也大——刚启动后的空闲期格外容易攒出一次超级风暴。这是「重启之后第一个备份任务把延迟打穿」的常见原因，不是备份脚本变了。

readahead 与 posix_fadvise

顺序读命中就加倍窗口，默认上限 128 KB。/sys/block/*/queue/read_ahead_kb 可调。随机读场景预读是纯浪费——看 /proc/PID/io 的 read_bytes 是否远大于文件本身。

posix_fadvise / madvise

  • SEQUENTIAL 加大预读；RANDOM 关掉；WILLNEED 立刻异步预读。
  • DONTNEED 丢掉干净页。⚠️ 不会先刷脏页。正确：先 sync_file_range(...WAIT_BEFORE|WRITE|WAIT_AFTER) 再 DONTNEED。
  • MADV_DONTNEED 用在匿名内存是「下次读到全 0」，不是「换出去」。
// 流式扫 100 GB：加大预读，每 64 MB 丢掉已处理的干净页，免得冲光别人的热缓存
posix_fadvise(fd, 0, 0, POSIX_FADV_SEQUENTIAL);
posix_fadvise(fd, 0, done - 8*MB, POSIX_FADV_DONTNEED);  /* 留 8 MB 余量 */

流式扫描如果不用 DONTNEED，100 GB 会把别人的热缓存挤光，扫完以后在线请求全 miss。留 8 MB 余量是因为预读窗口还在往后取，切太干净会把正在用的页丢掉、变成同步读。DONTNEED 不会先刷脏页——边扫边写同一文件时，要先 sync_file_range。

O_DIRECT：把缓存决策权交给应用

该用
应用自己有更好的缓存（InnoDB innodb_flush_method=O_DIRECT），或一次性顺序流（备份）。双重缓存等于浪费一半内存。
约束
缓冲区、偏移、长度按逻辑块对齐，否则 EINVAL。statx(STATX_DIOALIGN) 查准确值，别硬编码 512/4096。
误用
当持久化（见 §5）；在小 I/O 上用——失去合并与预读，随机小读写可能差几倍。

数据库 buffer pool 已经按页管理了，再走页缓存等于同一份数据两份内存，而且两次缓存的失效策略还不一致（内核 LRU vs InnoDB flush list）。O_DIRECT 把决策权交回去。代价是对齐和失去内核合并——4 KB 随机直写往往比走页缓存更慢，所以「所有程序都 O_DIRECT」是错的。

free 的 buff/cache 与 drop_caches

free 列很低是健康的（空闲被拿去做缓存）。只看 available：不触发换出就能拿到的量。available 持续接近 0 才是告急。

不要在生产 echo 3 > /proc/sys/vm/drop_caches。立刻丢掉全部可回收页缓存和 slab：① 热数据重新打满磁盘；② 大内存机器上遍历可能卡住几秒到几十秒；③ 解决不了泄漏。唯一正当用途是性能测试的冷缓存基线。它也丢不掉脏页——Dirty 还在，只是干净缓存没了，于是下一次读更慢、写路径没被修好。
周期性延迟毛刺 → 先看 Dirty 锯齿。有，往 dirty_bytes 调；没有，去 §9。kswapd 回收文件页和写者被 balance_dirty_pages 按住会叠在一起：内存紧时既要腾干净页给新读，又要把脏页写下去。表现为「读也慢、写也慢、iowait 不高」（CPU 在做回收）。这时先看 PSI memory，不要只当 I/O 问题处理。

空间与 inode 事故

线上最高频的一类问题，几乎全是「看错了数字」

「磁盘满」最多。棘手的不是满了怎么办，是你以为满了其实没满，或以为没满已经写不进去。

现象定位命令根因
df 说满了，du 加起来对不上lsof +L1文件被 rm 了但还有进程持有 fd，空间未释放（§2）
同上，但 lsof 什么都没查到mount --bind / /mnt 后 du /mnt/<path>挂载点被覆盖：挂载前写进去的文件还占着底层空间，但被上层挂载遮住了
df 100%，但 root 还能写tune2fs -l | grep -i reservedext4 默认保留 5% 只给 root（df 的百分比按普通用户可用算）
有大把空间却 ENOSPCdf -iinode 耗尽——海量小文件（§3）
ls -l 显示 10 GB，du 只有 200 MBdu --apparent-size、filefrag -v稀疏文件：中间大量空洞没有实际分配块
du 比 ls 之和小很多find -links +1硬链接被 du 只计一次（备份工具常大量使用硬链接）
读写变慢，容量却没变化filefrag、xfs_bmap碎片化，extent 数量爆炸
某个目录下 ls 要等好几秒ls -f \| wc -l、tune2fs -l \| grep dir_index单目录文件数过多

df 与 du 为什么对不上

df 问 superblock「还有多少空闲块」；du 从目录遍历能通过路径访问到的文件。占着块但没有路径的，df 看得见、du 看不见。

典型事故：新机器服务先起、往 /data 写，过几天才把数据盘挂到 /data。上层遮住了底层那批文件，du /data 看不见，df 仍记账。mount --bind / /mnt 再 du /mnt/data 才能揭开。

命令目的判据
df -h vs du -sxh /对账差额就是「有块无路径」
lsof +L1已删仍打开SIZE 最大的那条
mount --bind / /mnt 再 du /mnt/data揭开被遮的挂载点底下藏着初始化时写下的数据
tune2fs -m 1数据盘保留块调到 1%留一点让 root 在盘满时还能登录清理

inode 耗尽

df -i 的 IUse% 到 100%，df -h 可能只用了 7%。ext4 上 resize2fs 不能增加 inode 总数。救：删文件 / 打成 tar / 备份重建 / 换 XFS。定位按文件数统计目录（ls -U 不排序，大目录比 ls 快几十倍）。预防：凡是海量小文件的用途一律选 XFS；非要用 ext4 就在 mkfs 时把密度提上来，并算清 inode 表本身要占的空间。

稀疏文件与 fallocate

稀疏文件：逻辑长度里有从未写过的空洞，不占物理块。ls -l 看 i_size，du 看 st_blocks，可以差几个数量级。
命令目的判据
dd … seek=10G / ls -lh vs du -h造/识别稀疏文件逻辑 11G、实际 4K；du --apparent-size 跟 ls
filefrag -v看空洞分布只有最后一个块有映射
fallocate -d / cp --sparse=always / tar --sparse打洞、复制、打包时保持稀疏默认 cp/tar 可能把空洞展开成真实零
fallocate -l 16G瞬间预分配（unwritten extent，不写零）对比 dd if=/dev/zero 要真写 16G
fallocate(FALLOC_FL_KEEP_SIZE)预留空间不改 i_sizeposix_fallocate 在不支持的 FS 上会真写零
稀疏文件是文件层超卖：30 个「10 GB」镜像可能只占 800 MB × 30，直到客户机写满。监控看 df，规划按 du --apparent-size。

fallocate 造的是 unwritten extent：元数据说「这些块是你的」，介质上还没写零。第一次读返回零，第一次写才真正占用介质带宽。这就是为什么预分配「瞬间完成」——它几乎只改元数据。posix_fallocate 在不支持的 FS 上会真写零，启动时间差两个数量级。

预分配的两个理由
① 把 ENOSPC 提前到启动时；② 一次性拿到连续空间，降低碎片。最好的碎片对策是 fallocate，不是事后 defrag。

碎片化与单目录文件数

SSD 上碎片的代价不是寻道，是 extent 树变深和请求放大。filefrag 一个 10 GB 文件 200 条 extent 健康，18 万条该处理（e4defrag / xfs_fsr，低峰做）。

ext4 dir_index（HTree）让「open 一个已知名字」在 300 万文件的目录里仍然快。慢的是遍历：readdir 是哈希序，inode 是创建序，ls -l/du 变成对 inode 表的随机访问。SSD 上这表现为「元数据 IOPS 打满、数据盘很闲」。工程上单目录控制在几万，用两级十六进制分片（ab/cd/abcdef.jpg）。面试能说出「慢的是遍历不是查找」，比说「文件太多要分目录」深一层。

卷管理与冗余：LVM / RAID / 多路径

五层叠在一起，每层解决一个问题，也各有一个故障域

文件系统底下往往不是一块物理盘，而是一叠设备映射层。搞不清这一叠，排障时会问出「盘坏了为什么服务还活着」或者反过来「明明做了 RAID 为什么数据没了」这类问题。每一层的存在都有明确理由，也各自有一个明确的失效边界。

排障口诀：服务还活着但某个文件没了 → 文件系统；一块盘灯红了但卷还在 → RAID；所有卷同时只读 → thin pool；I/O 全部卡住 kill -9 无效 → 多路径 queue_if_no_path 或盘全挂。层找错了，工具全白费。

命令目的判据
lsblk一眼看整棵栈NAME 缩进 = 层级；同一 mpath 下多块盘 = 多路径
cat /proc/mdstatRAID 健康[UUUUU] 全在线；出现 _ 掉盘；有 recovery 行 = 正在重建
lvs -o +data_percent,metadata_percentthin pool两个百分比都要看；VG 没余量则自动扩容无效

RAID 级别：容量、性能、风险的三角

级别可用容量一次随机写的底层 I/O可容忍故障重建代价适合
RAID 0N1 次写0 块无法重建纯临时数据、可随时从别处重算的中间结果
RAID 1N/22 次写（两块都写）每个镜像组 1 块只读镜像伙伴，最快最安全系统盘、小容量关键数据
RAID 5N−14 次（读旧数据 + 读旧校验 + 写数据 + 写校验）1 块要读遍所有剩余盘——最危险大盘时代已不推荐（见下）
RAID 6N−26 次（双校验）2 块同样要读遍剩余盘，但能扛重建期二次故障大容量归档、以读为主的数据湖
RAID 10N/22 次写每个镜像组 1 块只读镜像伙伴，快且低风险数据库、随机写重的负载
大盘时代不要 RAID 5。16 TB 重建按 150 MB/s 也要约 30 小时，期间读遍剩余盘，URE 概率撞上重建窗口；同批盘故障相关，不是独立事件。「重建中彻底失效」反复发生。大容量用 RAID 6 或 RAID 10；哪种都不能替代备份。URE 按厂商 1014 比特一遇估算，读完 16 TB × (N−1) 块盘，窗口里撞上不可恢复读错误并不稀罕。RAID 6 能扛重建期二次故障，RAID 10 重建只读镜像伙伴、窗口短得多。
写洞：RAID 5/6 条带的数据块和校验块在不同盘上，无法原子更新。「数据已写、校验未写」时掉电，校验是错的而 RAID 不知道。平时读不走校验；真要重建时得到静默错误数据。
命令目的判据
mdadm --grow --consistency-policy=ppl部分校验日志（仅 RAID 5）/sys/block/md0/md/consistency_policy = ppl
--write-journal独立日志设备，最彻底最好带掉电保护
echo check > …/sync_action巡检mismatch_cnt 非 0 = 潜伏坏块。不巡检会拖到重建才暴露

write-intent bitmap 只能缩短重建时间，不能补上「数据已写、校验未写」的那一个条带。PPL / 独立 journal 才针对写洞。巡检会把每个条带的校验再算一遍：mismatch_cnt 非 0 说明平时已经有静默错误，拖到重建才发现就晚了。

LVM 快照：两种「写满」后果完全不同

传统快照：不复制数据，只留 COW 区。原卷每次写入未复制过的块，先把旧内容拷到 COW 再写。做快照瞬间，之后每次修改变贵。
传统快照像「复印一份档案后，每次改某一页之前先把原页复印到副本」。快照瞬间免费，之后每次修改都多一次读+一次写。COW 区用完，副本作废，原件还在。thin pool 则是整栋楼共用一个水箱：水箱空了，所有住户同时停水。
传统快照 COW 满：快照失效，原卷继续工作。thin pool 满：池上所有卷一起 I/O 错误，文件系统通常变只读。更隐蔽的是 metadata_percent——容量小、更容易满。监控两个百分比，且 VG 必须有空闲 PE，否则 autoextend 无效。
命令目的判据
lvm.conf thin_pool_autoextend_*80% 自动扩 20%前提是 vgs 的 VFree > 0
lvs … data_percent,metadata_percent用量Attr 出现 I = 传统快照已 invalid

在线扩容：顺序反了会丢数据

lvextend -r 会自动调 resize2fs / xfs_growfs，少一次人肉顺序错误。XFS 的扩参是挂载点不是设备名。缩容仅 ext4，且必须卸载 + e2fsck -f；lvreduce -f 拦不住你先砍 LV。分区表扩完还要通知内核（partprobe），否则文件系统看到的还是旧大小。

多路径：queue_if_no_path 会把机器挂死

dm-multipath 保护的是链路不是盘。所有路径都断时，queue_if_no_path 把 I/O 无限排队 → 进程永久 D 状态，kill -9 无效，往往只能硬重启。生产配 no_path_retry N，有界等待后向上报错。路径抖动时「failed faulty」先查线缆、交换机端口、HBA，不要先换盘。active/passive 阵列如果策略配成 round-robin，会把 I/O 打到 standby 路径上，表现为周期性几百毫秒毛刺。

命令目的判据
multipath -ll路径状态failed faulty 查线缆/端口；features 里不要长期留着 queue_if_no_path
NVMe 原生多队列，blk-mq 每 CPU 一个软件队列，提交不再跨核争抢——所以 NVMe 默认调度器常是 none。这也是 %util 失效的原因（§9）。细节见 Linux I/O 与内核 I/O 栈。

I/O 排障工作流

先判断「是不是 I/O」，再判断「是哪一层」

「看到 %wa 高就换盘」是答错最多的路径。先用两个便宜判据分层，再上对应工具。

NVMe 上不要看 %util。它的定义是「采样周期内至少有一个请求在飞」的时间占比，隐含「设备一次只能干一件事」。机械盘一个磁头时 100% 约等于饱和；NVMe 内部几十上百个并行队列，98% 只表示「没闲着」，await 仍可能是 0.3 ms。饱和度看 await 是否随 aqu-sz 恶化，以及设备公布的 QD 上限。

iowait 高只说明「有 CPU 闲着在等 I/O」：空闲机器拷文件可以 90%，盘可能很好；64 核上一根线程卡死最多贡献约 1.5%。业务被 I/O 拖死而 iowait 0.3% 是常态，因为别人在跑用户态，这笔账记到 %user。用 PSI 和 D 状态，不要用 iowait 当开关。

周期性毛刺先排除 §6 的 Dirty 锯齿，再排除容器 overlay copy-up 和 io.max。这三件都表现为「盘不忙但应用卡」，工具却完全不同：meminfo、du 容器可写层、cgroup io.stat。拿着 iostat 死盯 %util 会三件都漏掉。

工具怎么用：命令 → 目的 → 判据

字段含义怎么用 / 注意什么

aqu-sz平均队列深度（老版本叫 avgqu-sz）配合 await 区分「排队」还是「单请求慢」——这是决策树里的第二个判据

  • 周期性毛刺先看 Dirty 锯齿（§6）。容器先确认没落 overlay 可写层（§4），再看 io.max。

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础硬链接和软链接有什么区别？为什么硬链接不能跨文件系统、也不能指向目录？

    硬链接是在目录里多加一条指向同一个 inode 的记录——两个名字完全平等，没有主次。ls -i 会看到相同的 inode 号，inode 的 i_nlink 是 2。软链接（符号链接）是一个独立的 inode，它的数据内容就是一段路径字符串。

    核心认知：文件名不在 inode 里，在目录项里。inode 只存元数据和数据块映射。理解这一句，两种链接的所有差异都能自己推出来。

    为什么不能跨文件系统
    硬链接记的是 inode 号，而 inode 号只在自己的 superblock 范围内唯一。跨挂载点写下一个 inode 号毫无意义——目标文件系统里那个号是别的文件。所以 ln 跨设备直接返回 EXDEV。软链接存的是路径字符串，指向哪都行，甚至可以指向还不存在的路径。
    为什么不能指向目录
    会产生目录环，后果有三层：① find/du/备份这类遍历工具陷入无限循环，而且没法用「访问过的 inode 集合」简单判环——合法的硬链接文件本来就会重复出现；② .. 变得歧义，一个目录有多个父目录，cd .. 不知道该去哪；③ 引用计数无法回收环状结构，删掉外部引用后环内部还互相引用着，空间永久泄漏（引用计数式回收的经典缺陷）。内核选择直接禁止，把复杂度挡在门外。软链接没这个问题，因为它不参与引用计数，遍历工具默认也不跟随它。
    常见追问
    「删掉原文件会怎样？」——硬链接照常可用（数据块还在，链接数减一）；软链接变成悬空链接，访问返回 ENOENT。另外软链接自己的权限位是无意义的（永远显示 777），实际检查的是目标的权限。
  2. 基础rm 了一个 30 GB 的日志文件，df 显示空间一点没降，为什么？怎么处理？

    因为还有进程持有指向它的打开文件描述符。rm 实际调用的是 unlink，它只删掉「名字 → inode」的绑定并把 i_nlink 减一。真正释放数据块需要两个条件同时满足：i_nlink == 0（没有任何名字指向它）并且 i_count == 0（没有任何进程打开它）。

    此时文件已经从目录树里消失（du 遍历不到它，所以 du 和 df 会对不上），但它仍然活着，而且写日志的进程还在继续往里写、还在继续变大。

    定位
    sudo lsof +L1——+L1 的意思是「只列出链接数小于 1 的打开文件」，输出里 NLINK 列为 0、名字带 (deleted) 的就是它。
    处理，按优雅程度排序
    ① 让进程重新打开日志文件（kill -USR1 给 nginx、服务自己的 reload）；② truncate -s 0 /proc/<pid>/fd/<n> 立刻还空间且不用重启进程；③ 重启进程。
    方式 ② 的陷阱
    如果那个 fd 不是 O_APPEND 打开的，进程内部的写偏移不会归零，它会继续在 30 GB 那个位置写，文件立刻变成前面全是空洞的稀疏文件。所以正确的日志轮转是 copytruncate 或让进程配合 reopen，而不是 rm + truncate。
    反过来用是个好技巧
    「open 之后立刻 unlink」能造出一个真正的临时文件：没有名字，别人无法通过路径访问，进程一退出（哪怕是 SIGKILL）内核自动回收，永远不留垃圾。tmpfile() 就是这么实现的，更现代的写法是 O_TMPFILE + linkat。
  3. 基础write() 返回成功，数据就安全了吗？fsync 和 fdatasync 有什么区别？

    不安全。write() 返回只保证「数据进了页缓存，其他进程读得到」。此时数据在内核内存里：进程崩溃不会丢（内核持有），但内核 panic 或机器掉电就全丢。默认配置下脏页可以在内存里待 30 秒（dirty_expire_centisecs）。

    更靠前还有一层：如果用的是 fwrite，数据可能连内核都还没进——它还在 glibc 的 stdio 缓冲区里，进程被 kill 就没了。重定向到文件时 stdio 是全缓冲（4 KB），这是「崩溃后日志少了最后几百行」最常见的原因。

    fsync(fd)
    把该文件的全部脏页推下去，写全部元数据（包括 mtime 这种没人关心的字段），并向设备发 FLUSH 让写缓存进介质。
    fdatasync(fd)
    同样刷数据和发 FLUSH，但只写「为了把数据读回来所必需」的元数据。如果这次写没有改变文件大小（在文件内部原地覆盖），那就一条元数据都不用写——省掉一次日志事务提交和一次额外的 FLUSH。
    这个区别的实际价值
    解释了为什么数据库要预分配定长 WAL 段文件：预分配之后每次写日志都是原地覆盖，fdatasync 才真正省掉元数据写，把每次事务提交的 I/O 从 3–4 次降到 1–2 次。在「提交延迟决定 TPS 上限」的负载里这是数量级差别。
    两个常见误解
    O_DIRECT 不等于持久——它只绕过页缓存，数据仍停在设备写缓存里，元数据也完全没处理，之后照样要 fdatasync。sync_file_range() 也不是持久化原语——它只发起/等待页回写，不写元数据、不发 FLUSH，man 手册明确警告过。
  4. 基础df 说磁盘满了，但 du -sh 加起来差了几十 GB。有哪几种可能？

    先搞清两者在数什么：df 问的是文件系统的 superblock「一共多少块、还剩多少空闲块」；du 是从某个目录遍历，把每个能通过路径访问到的文件的占用块数加起来。所以凡是「占着块但没有路径」的东西，df 看得见、du 看不见。

    • 被删未关闭的文件（最常见）：lsof +L1。见上一题。
    • 挂载点被覆盖：挂载之前就写进那个目录的文件仍占着底层文件系统的空间，但被上层挂载遮住了，任何常规命令都看不到。用 mount --bind / /mnt 把上层「揭开」再 du。典型触发路径：新机器先起了服务往 /data 写，之后才把数据盘挂到 /data。
    • 保留块：ext4 默认留 5% 只给 root，df 的 Avail 已经扣掉了。tune2fs -l | grep -i reserved 确认，大数据盘可以 tune2fs -m 1 调小（但不要调成 0）。
    • 硬链接：du 对同一个 inode 只计一次，备份工具大量使用硬链接时差异会很明显。
    • 稀疏文件：这个方向相反——du 反而比 ls -l 小很多（空洞不占块）。
    • 用错了参数：du 不加 -x 会跨文件系统，把 /proc、其他挂载点算进来；不加 sudo 会漏掉没权限进入的目录（而且错误信息被 2>/dev/null 吞了）。
    还有一种
    df -h 空间明明够，但写文件报 ENOSPC——那不是空间问题，是 inode 耗尽，用 df -i 才看得到。

10.2 中级（区分熟练度）

  1. 中级ext4 的 data=journal / ordered / writeback 有什么区别？默认的 ordered 到底保证了什么？

    日志（jbd2）的作用是保证元数据的原子性：把即将进行的修改先顺序追加到日志区并提交，再改真正的位置，崩溃后重放即可，不用全盘 fsck。三种模式的差别在于「数据要不要也进日志、以及数据和元数据的先后顺序」。

    • data=journal：元数据和数据都进日志。一致性最强（已提交的数据能从日志重放恢复），但数据要写两遍，而且与延迟分配、O_DIRECT 不兼容。实际很少用。
    • data=ordered（默认）：只有元数据进日志，但强制数据块先落盘，再提交引用它的元数据。
    • data=writeback：只有元数据进日志，且不约束顺序。文件长度可能已经更新而数据还没写，崩溃后读到那块磁盘上残留的陈旧内容——可能是别人已删除文件的字节，这是实打实的信息泄露面。
    最常见的误解，必须答对
    data=ordered 保证的是「元数据一致」和「不会读到别人的旧数据」，不是「你写的数据不会丢」。崩溃后一个没 fsync 的文件完全可能是空的或只有前半段。「ordered」约束的是顺序（数据在元数据之前落盘），不是时机（什么时候落盘）。想要不丢，只能靠应用自己 fsync——挂载模式怎么调都替代不了它。
    再深一层
    日志也不能替代 fsck 和备份。它挡不住：位翻转与介质错误（ext4 的 metadata_csum 只校验元数据，数据块根本没有校验和，要端到端校验必须上 Btrfs/ZFS）；磁盘谎报 FLUSH 导致日志自己的提交顺序被破坏（此时重放可能让情况更糟）；以及逻辑错误——rm -rf 是一次完全一致的元数据操作。所以 Filesystem state: clean 只说明上次正常卸载过，不说明数据是对的。
  2. 中级什么是延迟分配（delayed allocation）？它带来什么好处，以及那个「崩溃后 0 字节文件」是怎么回事？

    延迟分配：write() 时 ext4 只在页缓存里记账（预留配额，标记为待分配），并不决定这些数据落在哪些物理块上。真正的块分配推迟到回写那一刻——此时内核已经知道这个文件总共要写多少字节，可以一次性挑一段足够长的连续空间。

    好处：extent 数量大幅减少，碎片和写放大都下降。一个 512 MiB 的文件常常只要 4 条 extent（每条顶格 128 MiB）。

    副作用一：ENOSPC 迟到
    块分配被推迟了，所以 write() 可能返回成功，直到真正分配时才发现盘满。这个错误只在后续的 fsync、close 或异步回写时才浮现。这是「必须检查 close() 返回值」的硬理由，不是教科书洁癖。
    副作用二：2009 年那批 0 字节文件
    ext4 刚普及时，用户发现崩溃后一批配置文件变成 0 字节。原因是那些应用把保存写成了「truncate 到 0 再重写」或「写临时文件再 rename 但不 fsync」。在 ext3 的 data=ordered 下，日志提交会顺带把数据刷下去（默认 5 秒一次），这类代码侥幸一直没出事；换到 ext4，延迟分配让数据能在页缓存里待更久，而元数据操作（truncate/rename）反而先通过日志落盘了——重启后就得到一个「已截断到 0 或已改名成功、但内容没写下去」的文件。
    责任划分与现代内核的行为（这一层是加分项）
    严格说那些应用本来就是错的：POSIX 从没承诺不 fsync 的数据能活过掉电，ext3 的行为只是不受保证的巧合。但「技术上正确」解决不了用户丢配置，所以 ext4 在 2.6.30 前后加了启发式补救：检测到「rename 覆盖已存在文件」和「truncate 到 0 后重写再 close」这两种模式时，自动触发延迟分配块的分配与回写（可用 noauto_da_alloc 关掉）。但这只是给坏代码兜底，不是可依赖的语义——它不发设备 FLUSH，也不管父目录，跨文件系统更不通用。正确的代码依然必须自己 fsync。
  3. 中级为什么新建文件后还要 fsync 父目录？rename() 的原子性到底保证了什么？

    因为文件名不在 inode 里，在父目录的数据块里。fsync(fd) 只管这个 inode 和它的数据块；「final.bin 这个名字指向 inode #131074」这条信息属于父目录这个文件的内容，它的修改同样先进页缓存。

    于是掉电后可能出现这个诡异组合：inode 和数据都完好地在磁盘上，但没有任何名字指向它。文件系统检查时发现一个链接数为 0 却还占着块的 inode，就把它当孤儿回收——数据消失了，而你的 fsync 明明返回了成功。

    需要 fsync 父目录的操作：所有会改目录项的——open(O_CREAT)、rename、link、unlink、mkdir、rmdir。纯粹改已存在文件的内容不需要。rename 跨了两个目录，两个父目录都要 fsync。

    rename 的原子性，最容易答偏的一点
    POSIX 保证：同一个文件系统内，其他进程通过目标路径看到的要么是完整旧文件、要么是完整新文件，绝不会出现「不存在」或「半新半旧」。但这是「命名空间可见性」的原子性，不是「崩溃持久性」。它保证其他进程看不到中间态，完全不保证掉电后你能看到新文件——甚至不保证还能看到旧文件，因为这次改名本身也只是页缓存里的元数据修改。「写临时文件 + rename」只解决并发可见性，没解决持久性。
    完整的正确写法
    ① 写临时文件（裸 write 循环处理短写）→ ② fdatasync 临时文件 → ③ 检查 close 的返回值 → ④ rename 到目标名 → ⑤ fsync 父目录的 fd。任意一步失败都要清理临时文件并向调用方报错。
    值得一提的两个能力
    renameat2（3.15+）的 RENAME_NOREPLACE（目标存在就失败，避免 access+rename 的 TOCTOU 竞态）和 RENAME_EXCHANGE（原子交换两个路径，是「灰度切换整个目录再一键回滚」的利器）。
  4. 中级磁盘还有 90% 空间，但创建文件报 ENOSPC。怎么确认、怎么救、怎么预防？

    inode 耗尽。df -h 看空间，df -i 看 inode——后者 IUse% 到 100% 时，即使空间只用了 7%，也创建不了任何新文件。

    根因：ext4 的 inode 表是预分配的，总数在 mkfs 时按 inode_ratio（默认段通常是 16384，即每 16 KB 空间配一个 inode）算好并写进 superblock 和 group descriptor。这个比例假设文件平均 16 KB——一旦负载是「几千万个 200 字节的小文件」（缩略图、邮件队列、监控碎片），inode 会在空间用掉不到 2% 时就耗尽。

    定位是谁生产的
    按文件数而不是大小统计：find /data -xdev -type d -exec sh -c 'echo "$(ls -U "$1" | wc -l) $1"' _ {} \; | sort -rn | head。ls -U 不排序，在几百万条目的目录里比 ls 快几十倍——排查时这个细节很重要。粗筛也可以看目录文件自身的大小（find -type d -size +1M），它反映目录项数量。
    救：ext4 上没有在线办法
    resize2fs 能扩块数，但不能增加 inode 总数。可选项只有：① 删文件（治标）；② 把海量小文件打包成归档（几百万个文件变成一个 tar，inode 从几百万降到 1）；③ 备份 + mkfs.ext4 -i 4096 或 -N 重建 + 恢复；④ 换 XFS。
    预防
    XFS 不预分配 inode，按 chunk 动态分配、用 B+ 树索引，只要有空间就能建文件（imaxpct 只是占用比例上限，不是预留，还能在线调）。凡是会产生海量小文件的用途，一律选 XFS；非要用 ext4 就在格式化时把 inode 密度提上来，并算清 inode 表本身的空间成本（2000 万 × 256 字节 ≈ 5.1 GB）。

10.3 高级（体现深度）

  1. 高级fsync() 返回错误之后，那些数据在哪里？应用应该怎么处理？

    这是 2018 年 PostgreSQL 社区披露的 fsyncgate。它的核心不是某个 bug，而是一个长期存在、被普遍误解的错误报告语义。

    问题一：错误只报一次，重试会返回成功
    回写失败时，内核记下错误，同时清掉这些页的 dirty 标记（认为「重试也没用，别把内存占死」）。应用第一次 fsync 拿到 EIO，如果按常规思路重试一次，第二次会返回 0——脏页已经没了，内核认为无事可做。应用于是确信数据已落盘，继续推进检查点、截断 WAL，而那些数据已经彻底不存在。
    问题二：错误可能被别的进程吃掉
    更早的实现把错误记在 address_space 上，谁先 fsync 谁拿到，之后就清了。PostgreSQL 的 checkpointer 负责 fsync，但错误可能被另一个恰好也 fsync 了同一个文件的进程先取走，checkpointer 得到干干净净的成功。
    内核侧的改进
    4.13 起引入 errseq_t：错误带序列号记在 struct file 上，每个 fd 至少会看到一次它打开之后发生的错误，不会再被别人抢走（各文件系统的适配在随后几个版本陆续完成）。这修好了「谁拿到」。但没有、也无法修好「数据去哪了」——脏页已被丢弃，内核手上确实没有那份数据了。
    应用侧唯一正确的处理
    把 fsync 失败当作不可恢复的致命错误：不重试、不忽略、更不能假装成功。因为你无法知道哪些页写成功了、哪些没有，也无法把它们要回来——磁盘上现在是一个你不知道内容的混合状态。PostgreSQL 现在的选择是直接 panic 并进入崩溃恢复，从 WAL 重放到一个已知一致的点。看着暴力，但它是唯一诚实的做法。if (fsync(fd) < 0) { log_warn(...); } 然后继续跑，是一颗定时炸弹。
    该学到的一般结论
    「写路径的错误」和「读路径的错误」性质完全不同。读失败可以重试、降级、返回错误，系统状态没变；写失败之后系统进入了一个你无法观测的状态，继续运行等于在未知之上叠加更多未知。所以有状态服务的写路径失败，正确反应是停下来，从一个已知的持久点重建，而不是原地修复。
  2. 高级服务平时 p99 是 5 ms，每隔几分钟蹦到 2 秒。磁盘不忙，怎么定位？

    典型的脏页回写风暴。先看一分钟就能确认的判据：

    $ while :; do grep -E '^(Dirty|Writeback):' /proc/meminfo | tr '\n' ' '; echo; sleep 1; done
# Dirty 呈现「缓慢攒高 → 骤降」的锯齿形状，且骤降时刻与毛刺时刻吻合 = 就是它

    机制：脏页有三条回写触发路径。① 周期性（每 dirty_writeback_centisecs=5 s 唤醒，写出老于 dirty_expire_centisecs=30 s 的页）；② 超过 dirty_background_ratio（默认 10%）启动后台回写，不阻塞写者；③ 超过 dirty_ratio（默认 20%）时，内核在 balance_dirty_pages 里让产生脏页的那个进程自己去等——它必须帮着把脏页写下去才能继续。第三条就是毛刺。

    为什么大内存机器上特别严重
    比例的分母是可脏化内存（大致是空闲内存 + 可回收文件页）。512 GB 内存的机器上，20% 意味着可以攒到上百 GB 脏页；一旦触线，那一次要写下去的量远超设备几秒的吞吐，被罚站的进程就卡了好几秒。毛刺不是因为设备慢，而是因为允许攒的窗口太大。
    处理
    把上界从「百分比」换成确定的字节数：vm.dirty_bytes / vm.dirty_background_bytes，目标是「一次要写的量在设备 1–2 秒能吐完的范围内」。注意 *_bytes 与 *_ratio 互斥，设了一个另一个自动归零。更根本的做法是让应用自己有节奏地分批推（写一段就 sync_file_range(...WRITE)），主动把大峰摊平，而不是等内核来罚站。
    这是个取舍，不是免费的
    调小脏页窗口 = 合并机会变少、写放大上升、总吞吐下降。延迟敏感的在线服务该调小；批处理和数据导入反而该调大，让内核有更大的合并窗口。没有一组适用于所有场景的值。
    如果 Dirty 没有锯齿
    那就换方向：看 D 状态进程的 wchan。jbd2_log_wait_commit 说明卡在 ext4 日志提交上（fsync 太频繁，用 biosnoop 会看到满屏 jbd2 线程的 4 KB 写）；也要排查 RAID 是否在重建、多路径是否在切换、cgroup 的 io.max 是否在周期性限流。
  3. 高级为什么大容量盘时代不推荐 RAID 5？什么是写洞？

    RAID 5 用单份分布式校验换容量（可用 N−1），能容忍 1 块盘故障。它在小容量盘时代是很好的取舍，但三个因素叠加之后不再成立：

    ① 重建窗口极长
    一块 16 TB 的盘，即便能以 150 MB/s 持续重建也要约 30 小时；生产环境还要和业务 I/O 争带宽，实际常常是几天。这几天里阵列是没有冗余的。
    ② 重建必须读遍所有剩余盘
    恢复一块盘的数据要读全部其他盘的对应条带。此时任何一块盘出现不可恢复读错误（URE），重建就中断——而消费级盘的 URE 指标量级是「每读 1014–1015 位出现一次」，重建要读的总量恰好落在这个量级附近。
    ③ 故障是相关的，不是独立的
    同批采购、同批上架、同样的温度和振动环境，盘的失效时间正相关。第一块坏了之后，第二块坏的条件概率显著高于基础故障率。拿独立事件的概率去算「两块同时坏的可能性极小」是错的。
    写洞（write hole）
    一个条带的数据块和校验块分布在不同物理盘上，无法原子地一起更新。在「数据已写、校验未写」的瞬间掉电，这个条带的校验就是错的——而 RAID 层不知道它错了。危险在于：平时读数据不走校验，一切正常；等到某块盘真的坏了、需要用校验重建时，重建出来的是静默错误的数据。Linux md 的缓解手段是 --consistency-policy=ppl（部分校验日志，开销小，仅 RAID 5）或 --write-journal（独立的日志设备，最彻底但要额外盘）。
    结论与运维要求
    大容量盘上用 RAID 6（能扛重建期二次故障）或 RAID 10（重建只读镜像伙伴，又快又低风险，随机写还便宜——RAID 5 一次随机写要 4 次底层 I/O，RAID 6 要 6 次，RAID 10 只要 2 次）。另外必须开定期巡检（echo check > /sys/block/md0/md/sync_action，看 mismatch_cnt）——不巡检的话坏块会一直潜伏到重建那一刻才暴露。而无论哪种 RAID 都不能替代备份：它防的是盘坏，防不了 rm -rf、勒索软件和机房事故。
  4. 高级top 里 %wa 高就说明磁盘慢吗？给出你判断「应用慢是不是 I/O 导致」的完整路径。

    不能这么判断。%iowait 的定义是「该 CPU 处于空闲状态、且此刻至少有一个 I/O 在飞」的时间占比——它是一个关于 CPU 空闲的指标，不是关于磁盘的指标。两个方向都会误导：

    高 iowait 不代表磁盘有问题
    一台 CPU 完全空闲的机器上跑一个正常的批量拷贝，iowait 可以是 90%。这只说明「CPU 没别的事干而且在等 I/O」，盘可能好得很。
    低 iowait 不代表磁盘没问题
    64 核机器上一个线程被慢盘卡死，iowait 最多贡献 1/64 ≈ 1.5%；更极端的是——只要 CPU 上还有别的可运行任务，那段时间就被记成 %user/%sys 而不是 %iowait。业务被 I/O 拖死而 iowait 是 0.3%，在繁忙机器上是常态。

    正确的判断路径，分两步：

    第一步：先证明是 I/O
    看 /proc/pressure/io（PSI，4.20+）的 full 那一行——它统计的是任务的停顿而非 CPU 的空闲，不受核数和其他负载稀释；cgroup v2 里还有 per-cgroup 的 io.pressure。再看 D 状态进程的 wchan（ps -eo state,pid,comm,wchan:32），wait_on_page_writeback / jbd2_log_wait_commit 这类值信息量极大。
    第二步：分成三类，各走各的路
    用 iostat -x 1 的 r_await/w_await（必须分开看，合并会掩盖「读快写慢」）配 aqu-sz：① await 低 + 队列浅 → 瓶颈不在设备（fsync 太频繁、队列深度只有 1、cgroup io.max 限流、页缓存命中率掉了）；② await 高 + 队列深 → 排队，用 iotop/pidstat -d 找出压 I/O 的进程；③ await 高 + 队列浅 → 单请求本身慢，查 dmesg/smartctl、RAID 重建、多路径切换。
    顺带纠正两个过时的指标
    %util 在 NVMe / RAID / 多队列设备上基本无意义——它只表示「至少有一个请求在飞」的时间占比，这些设备内部并行度很高，100% 不代表到极限了。不要拿它当饱和度。而 svctm 已经从新版 sysstat 里删掉了，因为它的计算方式在多队列设备上根本不成立；看到老文档教你看 svctm，那份文档过时了。
    要精确拆解耗时就上 blktrace
    blktrace + btt 把单个 I/O 拆成 Q2G（分配 request）、G2I（插入队列）、I2D（内核侧排队）、D2C（设备真实服务时间）。如果 Q2C 平均 44 ms 而其中 I2D 占 42 ms、D2C 只有 2 ms，那么换更快的盘毫无用处——时间全花在内核排队上，该做的是降并发、调调度器、或查限流。同理，ext4slower 报大量慢操作但 biolatency 显示块层很快，说明问题在文件系统层或以上，不在盘上。
