01

一次 write() 的完整旅程

每一层都有一个缓存，每个缓存都是一个丢数据的机会

「我调了 write()，它返回了写入的字节数，所以数据写进磁盘了」——这句话在几乎每一层上都是错的。从应用调用 write() 到字节真正被记录在盘片的磁性介质或闪存单元里，中间要穿过至少四个独立的缓存，每个缓存都对应一类不同的失效场景：进程崩溃、内核 panic、机器掉电、乃至设备固件谎报。搞不清这条链，就写不出正确的持久化代码，也读不懂线上「重启后配置文件变成 0 字节」这类故障。

把写文件想成寄一份合同。你把文件塞进办公室的出件篮（glibc 缓冲区）——你走了，篮子里的东西没人管；行政每小时来收一次，放进公司的待寄堆（页缓存）——公司着火，还是没了；快递员每天来取，装上车（设备写缓存）——车翻了也没了；只有对方签收那一刻，合同才算真的送到。write() 返回成功，只等于「塞进出件篮了」。

先把「谁丢什么」分清楚

失效场景会丢什么怎么防
进程被 SIGKILL / 段错误只丢 glibc stdio 缓冲区里的内容用裸 write()，或 fflush()。数据一旦进内核就与进程生死无关
内核 panic / 机器掉电页缓存里所有脏页（默认可以攒到 30 秒 + 内存的 20%）fsync() / fdatasync()，或 O_DSYNC
掉电，但文件系统挂了 nobarrier设备写缓存里的内容，即使 fsync 返回成功不要关 barrier；或者用带掉电保护电容的企业级盘
掉电，廉价 SSD / U 盘谎报 FLUSH 完成同上，而且你无法从软件侧发现选盘。这是硬件采购问题，不是代码问题

用 strace 看清 ① 和 ② 的区别

最容易踩的第一步其实在用户态：C 标准库的 fwrite/fprintf 有自己的缓冲区，不到 4 KB 或不遇到换行（终端下是行缓冲，重定向到文件时是全缓冲）根本不会发起系统调用。日志写不全、崩溃后最后几百行丢失，八成是这个原因，跟内核和磁盘毫无关系。

# 同一段代码，输出到终端 vs 重定向到文件，系统调用次数差一个数量级
$ strace -e trace=write ./logger > /tmp/out.txt
write(1, "line 0\nline 1\nline 2\n...line 60\n", 4096) = 4096   # 攒满 4 KB 才发一次
write(1, "line 61\n...line 121\n", 4096) = 4096
...
# 进程此刻被 kill -9：最后不满 4 KB 的那一批永久消失

$ strace -e trace=write ./logger        # 直接输出到终端
write(1, "line 0\n", 7) = 7                # 行缓冲，每行一次系统调用
write(1, "line 1\n", 7) = 7
写日志的正确姿势：绕开 stdio。要么用裸 write()（一次系统调用写一整条，天然是原子的——只要不超过 PIPE_BUF 或用 O_APPEND 打开常规文件），要么显式 setvbuf(fp, nullptr, _IOLBF, 0) 改成行缓冲并接受性能损失。不要指望 exit() 帮你 fflush——被信号杀死时 atexit 根本不会执行，而 fork 之后子进程用 exit() 还会把父进程遗留的缓冲区再输出一遍（这一点在 多进程与 IPC 里详细讲过）。

02

VFS 的四个核心对象

文件名不在 inode 里——这一句能解释一大半疑问

Linux 支持几十种文件系统，但应用只见到一套 open/read/write/stat。中间这层抽象叫 VFS（Virtual File System），它定义了四个核心对象和一组函数指针表（super_operations、inode_operations、file_operations、dentry_operations）。具体文件系统只要填这些表，就能挂到 VFS 上。理解这四个对象的分工，是读懂后面所有内容的前提。

对象内核结构体代表什么生命周期存不存在磁盘上
superblockstruct super_block一个已挂载的文件系统实例：块大小、inode 总数、空闲计数、日志位置、特性标志挂载到卸载是（且 ext4 在每个 block group 留了备份）
inodestruct inode一个文件本体：类型、权限、uid/gid、大小、三个时间戳、链接数、数据块映射被引用期间常驻内存，之后回收是（ext4 默认 256 字节一个）
dentrystruct dentry一个名字到 inode 的绑定，以及它在目录树里的位置（父子关系）纯缓存，可随时回收重建否——磁盘上是目录文件里的目录项记录
filestruct file一次打开：当前偏移 f_pos、打开标志、引用计数open 到最后一个引用 close否，纯运行时状态
inode：index node 的缩写。它是文件的全部元数据加数据块索引，唯一标识是「superblock + inode 号」。inode 里没有文件名——名字存在目录里。目录本身也只是一个特殊类型的文件，它的数据内容就是一串「名字 → inode 号」的记录。

硬链接：同一个 inode 的多个名字

硬链接不是「快捷方式」，而是给同一个文件本体再起一个名字。两个名字完全平等，没有「原件」和「副本」之分——ls -i 会显示它们的 inode 号相同，stat 显示 Links: 2。

$ echo hello > a.txt
$ ln a.txt b.txt              # 硬链接，不加 -s
$ ln -s a.txt s.link          # 符号链接

$ ls -li
131074 -rw-r--r--. 2 kavin kavin 6 Sep  3 10:12 a.txt   # ← 链接数 2
131074 -rw-r--r--. 2 kavin kavin 6 Sep  3 10:12 b.txt   # ← 同一个 inode 号
131099 lrwxrwxrwx. 1 kavin kavin 5 Sep  3 10:12 s.link -> a.txt

$ rm a.txt                    # 删掉「原件」
$ cat b.txt
hello                         # ✅ 硬链接照常工作，文件本体还在
$ cat s.link
cat: s.link: No such file or directory   # ❌ 符号链接断了：路径解析失败
$ stat -c '%h' b.txt
1                             # 链接数从 2 减到 1
维度硬链接 ln符号链接 ln -s
本质目录项里多一条指向同一个 inode 的记录一个独立的 inode，其数据内容是一段路径字符串
占 inode不占（只多一条目录项）占一个（ext4 里路径 ≤ 约 60 字节时直接存在 inode 的 i_block 区，不额外占数据块，称为 fast symlink）
能跨文件系统不能——inode 号只在自己的 superblock 内唯一，跨挂载点没有意义，ln 直接返回 EXDEV能——它存的是路径字符串，指向哪都行，甚至可以指向不存在的路径
能指向目录不能（EPERM），只有内核自己维护的 . 和 .. 是例外能
目标被删后照常可用，链接数减一而已变成悬空链接，访问返回 ENOENT
解析成本零，就是一次普通查找每次访问都要读出内容再重新走一遍路径解析（内核限制递归深度，超了返回 ELOOP）
权限位就是 inode 的权限符号链接自己的权限位无意义（永远显示 777），实际检查的是目标
「为什么硬链接不能指向目录」是个好问题。如果允许，目录树就可能出现环：/a/b 硬链接到 /a，那么 /a/b/b/b/... 无限有效。后果是三重的：① find、du、备份程序这类要遍历整棵树的工具会陷入无限循环，而且无法用「访问过的 inode 集合」简单判环，因为合法的硬链接文件本来就会重复出现；② .. 变得歧义——一个目录有多个父目录，cd .. 该去哪？③ 引用计数无法回收环状结构，删掉外部的所有引用后环内部还互相引用着，成了永久泄漏的空间（这正是引用计数式 GC 的经典缺陷）。所以内核直接禁止，把复杂度挡在门外。符号链接没有这个问题，因为它不参与引用计数，遍历工具默认不跟随它。

rm 其实是 unlink：删了但空间没释放

rm 调用的系统调用叫 unlink，名字本身就说明了它做什么：删掉一条名字与 inode 的绑定，并把 inode 的链接数 i_nlink 减一。真正释放数据块，需要两个条件同时满足：

条件一
i_nlink == 0——磁盘上再没有任何名字指向它。
条件二
i_count == 0——内存里再没有任何进程持有指向它的打开文件（struct file）。

这就是那个经典事故的全部原因：运维 rm 掉了一个 30 GB 的日志文件，df 显示空间一点没降。因为写日志的进程还开着那个 fd，条件二不满足，内核必须保留数据块——文件从目录树里消失了，但它还活着，而且还在继续变大。

# 定位：+L1 = 只列出「链接数小于 1」的打开文件
$ sudo lsof +L1
COMMAND    PID USER   FD   TYPE DEVICE     SIZE/OFF NLINK   NODE NAME
java     21877  app    5w   REG  253,1  32212254720     0 131074 /var/log/app/app.log (deleted)
nginx     3312  www   12w   REG  253,1   1073741824     0 131552 /var/log/nginx/access.log (deleted)
#                                        ↑ 30 GB      ↑ NLINK=0 就是它

# 三种处理方式，按优雅程度排序：
# ① 让进程重开日志文件（最优）
$ kill -USR1 3312                    # nginx 的 reopen 信号
$ systemctl reload app               # 或者服务自己的 reload

# ② 通过 /proc 把文件截断，立刻还空间，进程不用重启
$ sudo truncate -s 0 /proc/21877/fd/5   # fd 5 就是上面 lsof 里那个

# ③ 重启进程（最粗暴，但有时是唯一选择）
方式 ② 有个陷阱：如果那个 fd 不是 O_APPEND 打开的，进程内部的写偏移量不会跟着归零。它会继续在 32 GB 那个位置写，于是文件立刻变成一个前 32 GB 全是空洞的稀疏文件——ls -l 看着还是 32 GB，但 du 只算实际占用的那几 KB。看起来空间是还回来了，实际上是把问题换了个形式（见 §7 的稀疏文件）。所以正确的日志轮转方式是 copytruncate 或者让进程配合 reopen，而不是 rm + truncate。这也是为什么 logrotate 默认要给服务发信号。

反过来，这个机制也是一个实用技巧：「打开后立刻 unlink」可以创建一个真正的临时文件——它没有名字，任何人都无法通过路径访问，进程一退出（不管是正常退出还是被 SIGKILL）内核自动回收空间，永远不会留下垃圾。tmpfile() 就是这么实现的，更现代的方式是 open(..., O_TMPFILE)，甚至可以之后用 linkat 给它补一个名字——这是「原子地生成一个文件」的另一条路径。

// O_TMPFILE：先造一个无名文件，写完再给它命名
int fd = open("/data", O_TMPFILE | O_RDWR | O_CLOEXEC, 0600);
write_all(fd, buf, len);
fsync(fd);                                     // 先把内容做实
char proc[64];
snprintf(proc, sizeof proc, "/proc/self/fd/%d", fd);
linkat(AT_FDCWD, proc, AT_FDCWD, "/data/final.bin", AT_SYMLINK_FOLLOW);
// 在 linkat 成功之前，这个文件对整个系统不可见；
// 崩溃了也不会留下 .tmp 垃圾，比 mkstemp + rename 更干净。
// 注意：linkat 只是让名字出现，父目录的持久化仍然需要 fsync(dirfd)，见 §5。

dentry cache：为什么 slabtop 里它能吃掉几个 GB

路径解析（把 /var/log/app/app.log 变成一个 inode）需要逐级读目录、逐级比对名字。如果每次 open 都真去读磁盘，性能不可接受。所以内核用 dentry cache（dcache） 把「父 dentry + 名字 → 子 dentry」的映射缓存在一张哈希表里，配合 inode cache，让热路径的解析完全不碰磁盘。

dcache 还缓存否定结果：查一个不存在的名字，内核会建一个 negative dentry 记住「这里没有东西」。这对反复 stat 不存在文件的程序（动态链接器搜索 .so、Python 找模块）是巨大的加速，但也意味着一个疯狂访问随机不存在路径的程序能把内存吃满。

「服务器可用内存只剩几百 MB，但应用只用了 20 GB」——先看 slabtop 再慌。海量小文件的场景（构建服务器、邮件队列、对象存储网关）里 dentry + inode cache 占几个 GB 是正常的，它不是泄漏，是缓存，内存压力上来会自动还。真正的病态情况是 vfs_cache_pressure 被人调到很低、或者出现了带 slab 泄漏的内核 bug——判据是「内存压力已经很大了但 slab 还在涨」。不要靠 drop_caches 解决（原因见 §6）。

rename() 的原子性：「写临时文件再替换」这个模式的基石

rename(old, new) 的原子性：POSIX 要求，在同一个文件系统内，其他进程通过 new 这个路径看到的，要么是原来的旧文件、要么是完整的新文件，绝不会出现「文件不存在」或「内容半新半旧」的中间态。如果 new 已存在，它被原子地替换掉，旧 inode 的链接数减一。
直接原地改文件像在会议上当众修改一份正在被大家阅读的合同——你划掉第三条的瞬间，有人正好读到第三条，看到的是残缺内容。rename 的做法是：在旁边桌上重新誊抄一份完整的新合同，然后一把换掉。任何时刻抬头看的人，手里要么是完整的旧版，要么是完整的新版。

这就是几乎所有配置文件、数据库快照、包管理器更新文件的标准做法，也是 vim、git、dpkg 内部的实现。但这里有一个极其常见的误解需要立刻澄清：

rename 的原子性是「命名空间可见性」的原子性，不是「崩溃持久性」。它保证的是其他进程看不到中间态；它完全不保证掉电之后你能看到新文件——甚至不保证你还能看到旧文件。因为这次改名本身也只是页缓存里的元数据修改，需要日志提交并落盘才算数。「写临时文件 + rename」只解决了并发可见性，没解决持久性；要持久，必须补上 fsync(临时文件) 和 fsync(父目录)。完整的正确写法在 §5。

另外两个值得知道的能力，来自 renameat2（Linux 3.15+）：

RENAME_NOREPLACE
目标已存在就失败，而不是覆盖。用来实现「原子地占位」——比用 access() 检查再 rename 可靠，后者是典型的 TOCTOU 竞态。
RENAME_EXCHANGE
原子地交换两个路径，两边都必须存在。这是「灰度切换整个目录」的利器：把 current 和 next 一把对调，回滚时再对调回来，中间没有任何时刻是不可用的。注意它不是所有文件系统都支持（ext4、XFS、Btrfs 支持，overlayfs 上有限制）。
这一章的四个对象，后面每一章都会用到：§3 讲 inode 表和目录项在 ext4 磁盘上的具体形态；§5 的「fsync 父目录」本质上就是「dentry 所在的那个目录文件的数据块要落盘」；§7 的 df/du 不一致全部源于「inode 还活着但名字没了」。把「名字 / 本体 / 打开状态」三者分开想，绝大多数疑问会自动消解。关于 struct file 与 fd 三级表的细节，见 文件描述符三级表。
03

ext4 的磁盘布局

block group、extent、延迟分配、以及被误解最深的 data=ordered

ext4 是 Linux 上最保守也最普及的选择：它从 ext2 一路演进而来，兼容层厚、工具链成熟、故障案例库最全。理解它的磁盘布局有直接的实用价值——mkfs 时定错一个参数，可能要等到半年后文件系统「明明还有 40 GB 空间却创建不了文件」时才暴露。

block group：把整块盘切成小区

ext4 把整个分区切成若干 block group，每个 group 内部自带一套完整的管理结构：块位图、inode 位图、inode 表、数据块。为什么这么切？因为一个块的位图能管的块数是有限的——4 KB 的块位图有 4096 × 8 = 32768 位，正好管 32768 个块，也就是 128 MiB。这个数字不是拍出来的，它是「用一个块做位图」这个约束直接推导出来的。

block group 像把一座大仓库分成若干个区，每个区门口挂一张自己的库位表。找空位只看本区的表，不用翻遍整个仓库的总账；同一批货尽量放在同一个区，取货时不用满仓跑。ext4 分配数据块时会优先放在「该文件 inode 所在的那个 group」，正是为了让元数据和数据在盘上挨着——在机械盘时代这直接减少寻道，在 SSD 时代仍然能减少要读的元数据页数。

flex_bg：把元数据聚到一起

  • 特性列表里那个 flex_bg 表示：连续若干个 group（默认 16 个）的块位图、inode 位图、inode 表集中放在第一个 group 里，而不是各自散在自己的 group 中间。
  • 好处是元数据连续、可以一次大 I/O 读完（fsck 和大目录遍历明显变快），并且给大文件留出了更长的连续数据区。
  • 代价是元数据集中——这块区域坏了影响面更大，所以 metadata_csum（元数据校验和）几乎总是一起启用。

inode 数量在 mkfs 时就定死了

ext4 的 inode 表是预分配的，总数在格式化时确定，之后无法增加。mke2fs 默认按 inode_ratio（/etc/mke2fs.conf 里 default 段通常是 16384）来算，也就是每 16 KB 空间配一个 inode。100 GiB 的分区因此得到约 655 万个 inode。这个比例假设文件平均大小 16 KB——一旦你的负载是「几千万个 200 字节的小文件」（缩略图、邮件队列、监控指标碎片），inode 会在空间用掉不到 2% 的时候就耗尽，然后 creat 返回 ENOSPC，而 df -h 还美滋滋地显示 98% free。这个坑没有事后补救的办法，只能备份数据重新 mkfs。
# 预知会有海量小文件时，格式化就要把 inode 密度提上来
$ sudo mkfs.ext4 -i 4096 /dev/sdb1        # 每 4 KB 一个 inode，inode 数 ×4
$ sudo mkfs.ext4 -N 20000000 /dev/sdb1    # 或者直接指定总数
$ sudo mkfs.ext4 -T small /dev/sdb1        # 用 mke2fs.conf 里的 small 档预设

# 代价要算清楚：inode 表本身要占空间
#   2000 万 × 256 字节 = 5.1 GB 的 inode 表，一开始就没了
# 想彻底不操心 inode 数量 → 用 XFS，它是动态分配的（见 §4）

extent：用「区间」取代「一个块一个指针」

ext2/ext3 的块映射是间接块方案：inode 里放 12 个直接指针，然后是一级、二级、三级间接块。一个 1 GB 的文件需要 262144 个块指针，光索引就要读好几个间接块，而且这些指针分散在盘上。更糟的是删除大文件时要遍历整棵间接块树把每个块逐个还回位图，rm 一个几十 GB 的文件能卡好几秒——这在 ext3 时代是真实的运维痛点。

ext4 换成 extent（区段）：一条记录描述「从逻辑块 X 开始的连续 N 个块，映射到物理块 Y」。一个 12 字节的 extent 最多可以表达 32768 个连续块，也就是 128 MiB。inode 的 i_block 区（60 字节）能内联放一个 12 字节的头加 4 条 extent；超过 4 条就升级成 extent B+ 树，树根仍留在 inode 里。

延迟分配（delayed allocation）：性能收益与那个著名的副作用

delayed allocation：write() 时 ext4 只在页缓存里记账（预留配额，标记为「待分配」），并不真的决定这些数据落在哪些物理块上。真正的块分配推迟到回写发生的那一刻——此时内核已经知道这个文件总共有多少字节要写，于是可以一次性挑一段足够长的连续空间。
这就像搬家前先把所有箱子在客厅堆好，再一次性决定谁上货车的哪个位置；而不是每打包好一个箱子就立刻搬上车，最后发现大件放不下、车厢里到处是缝。前者能装得整整齐齐（低碎片），代价是「你以为已经上车了的东西，其实还在客厅」。

收益很实在：连续写产生的 extent 数量大幅减少，写放大和后续读的寻道都下降。但代价有两个，第二个曾经引发过一场著名风波。

代价一：ENOSPC 迟到
因为块分配被推迟了，write() 可能返回成功，但真正分配空间时才发现盘满了。这个错误只能在后续的 fsync、close、或者异步回写时才浮现——如果程序不检查 fsync 和 close 的返回值（很多程序不检查），错误就被静默吞掉了。这是「必须检查 close() 返回值」的一个硬理由，不只是教科书洁癖。
代价二：崩溃后的 0 字节文件（2009 年那场风波）
ext4 刚成为主流时，用户发现崩溃或掉电后，一批配置文件变成了 0 字节——KDE 之类的桌面环境把配置文件的保存写成了「truncate 到 0 再重写」或者「写临时文件再 rename 但不 fsync」。在 ext3 的 data=ordered 下，日志提交会顺带把数据也刷下去（提交间隔默认 5 秒），这类代码侥幸一直没出事；换到 ext4，延迟分配让数据可以在页缓存里待更久，而元数据操作（truncate、rename）反而先通过日志落盘了——重启后于是得到一个「已经被截断到 0、或者已经改名成功、但内容还没写下去」的文件。
这件事的责任划分很重要，面试里问的往往是这一层。严格说，那些应用程序本来就是错的——POSIX 从来没承诺过「不 fsync 的数据能活过掉电」，ext3 的行为只是一个不受保证的幸运巧合。但「技术上正确」不能解决用户丢配置的现实问题，所以 ext4 在 2.6.30 前后加了启发式补救：检测到「rename 覆盖一个已存在的文件」和「truncate 到 0 后重写再 close」这两种模式时，自动触发对延迟分配块的分配与回写。这个行为可以用 noauto_da_alloc 挂载选项关掉。但这只是给坏代码兜底，不是可以依赖的语义——它不发设备 FLUSH，也不管父目录，跨文件系统更不通用。正确的代码依然必须自己 fsync。

jbd2 日志：data=ordered 到底保证了什么

日志（journal / jbd2）：把「即将进行的元数据修改」先顺序追加写到一块专用区域并提交，然后才去修改真正的位置。崩溃后重放日志即可，不用扫全盘。它解决的是元数据一致性——不会出现「inode 说自己占了这个块，但块位图说这个块是空闲的」这种能让 fsck 跑几个小时的矛盾。
日志就是记账本上的「先写流水，再改余额」。改余额的过程中断电了，凭流水可以重算出正确余额；如果没有流水，只有一堆半改完的余额，就只能盘点全部库存（fsck 全盘扫描）。注意流水记的是「哪几个账户的余额要改」，不是「这笔钱本身」——这正是 data=ordered 与 data=journal 的区别所在。
模式日志里记什么崩溃后保证写放大适用
data=journal 元数据 + 数据都进日志 最强：元数据一致，且已提交的数据本身也能从日志重放恢复 数据写两遍；且与延迟分配、O_DIRECT 不兼容 极少用。日志放在独立的快速设备上时才有意义
data=ordered
（默认）		 只有元数据；但强制数据块先落盘，再提交引用它的元数据 元数据一致，且不会读到别人的旧数据。但不保证你的数据不丢 正常（数据写一遍） 99% 的场景
data=writeback 只有元数据，且不约束顺序 元数据一致，但文件长度可能已更新而数据还没写 → 读到磁盘上残留的陈旧内容 最低 只写临时数据、且能容忍垃圾内容的场景。有信息泄露风险
这是全篇最常见的误解，请读三遍：data=ordered 保证的是「元数据一致」和「不读到别人的旧数据」，不是「你写的数据不会丢」。崩溃之后，一个刚写完但没 fsync 的文件完全可能是空的、或者只有前半段。ordered 里那个「ordered」约束的是顺序（数据在元数据之前落盘），而不是时机（什么时候落盘）。想要「不丢」，唯一的办法是应用自己调 fsync——文件系统模式怎么挂都替代不了它。反过来说，data=writeback 之所以危险，也不是因为「更容易丢你的数据」，而是因为它可能让你读到本该属于别人的、已删除文件的残留字节，这是个实打实的信息泄露面。

04

XFS 与文件系统选型

allocation group 的并发红利，与「不能缩容」这道硬伤

如果 ext4 的设计目标是「稳妥地从 ext3 演进过来」，XFS 的设计目标是「从第一天起就为大文件、大容量、高并发服务」。它出自 SGI 的 IRIX，1990 年代就在处理视频流和科学计算数据集，2014 年起成为 RHEL 7+ 的默认文件系统。它和 ext4 最本质的差别不在功能列表上，而在分配器的并发结构。

allocation group：把「分配」这件事本身并行化

allocation group（AG）：XFS 把整个文件系统切成若干个几乎完全独立的 AG，每个 AG 自带一套完整的空闲空间 B+ 树和 inode B+ 树，并且有各自的锁。两个 CPU 上的两个线程可以同时在不同 AG 里分配空间，互不争抢。

这一点和 ext4 的 block group 长得像，但性质完全不同：ext4 的 block group 只是位图的分片，分配路径上仍有全局性的串行点；XFS 的 AG 是并发单元。这就是为什么在「几十个线程同时创建/追加文件」的负载下（构建集群、日志聚合、数据库多表空间），XFS 的元数据吞吐能明显甩开 ext4，而单线程顺序写两者差别不大。

ext4 的 block group 像一个仓库分了很多区，但只有一个管理员拿着钥匙串挨个开门；XFS 的 AG 像每个区配一个自己的管理员——十个人来提货可以同时办，但你得先被分到某个区去。代价也在这里：AG 划分好之后，某个 AG 里的空间紧张时，不会自动去别的 AG 借，需要分配器跨 AG 重试，这在文件系统接近写满时会明显变慢。

动态 inode 分配：从此不必担心 inode 耗尽

XFS 不预分配 inode 表。inode 按 64 个一组（chunk）在需要时才分配，位置由 inode B+ 树（inobt）索引。这直接消灭了 ext4 那个最恶心的坑：只要还有空间，就能创建文件。imaxpct 只是给 inode 设了一个占用比例的上限（可以用 xfs_growfs -m 在线调整），不是预留。

代价是「查一个 inode 号在哪」需要走 B+ 树而不是简单的算术（ext4 里由 inode 号直接算出它在第几个 group 的第几个槽位）。在 inode 极多时，inobt 的深度会带来额外的元数据读——但 finobt 的引入基本抹平了这部分开销。

延迟日志（delayed logging）

元数据修改有极强的重复性：往同一个目录里连续创建一万个文件，会把这个目录的 B+ 树节点改一万次。早期 XFS 老老实实把每次修改都写进日志，日志设备成了瓶颈。延迟日志把这些修改在内存里累积、合并，只把最终结果写进日志，元数据密集负载下的日志流量能降一到两个数量级。它在 2.6.39 起成为默认并在后来变成唯一行为（delaylog 挂载选项已经消失）。

代价是崩溃时可能丢失更多「已经完成」的元数据操作——它们还在内存里等着合并。这不违反一致性（重放后仍是一个自洽的文件系统），但意味着「mkdir 返回成功了，掉电后目录不在了」。凡是需要持久的元数据操作，同样必须 fsync 父目录——这条在 XFS 上和在 ext4 上一样重要。

两道必须知道的硬伤

① XFS 不能缩容，永远。xfs_growfs 只有 grow，没有 shrink，而且这不是「还没实现」，是设计上的取舍——AG 结构和元数据分布让在线搬迁数据的复杂度极高，社区多年来一直没有把它列为优先项。后果很现实：LVM 卷分大了想收回一点，只能备份、重建、恢复。所以在 XFS 上做容量规划要保守：先给小，需要时再扩（扩容非常容易，甚至可以在挂载状态下做）。ext4 可以缩，但必须先卸载。
② 早期崩溃后的 NULL 文件。历史上 XFS 曾以「崩溃后文件变成 0 长度或被 NULL 填充」出名，机制和 §3 那个 ext4 的 0 字节文件问题同源：日志把「文件大小已更新」这条元数据落盘了，而数据块还在页缓存里。后来通过「在提交改变文件大小的事务之前先把数据刷下去」修正了这个行为，现代内核上已不是问题。如实说明这一点很重要：它常被拿来当「XFS 不安全」的证据，但真正的教训是同一条——没有 fsync，任何文件系统都不承诺你的数据能活过掉电。

Btrfs 中CoW 导致随机写碎片化好 可在线扩缩 原生、秒级、可写数据 + 元数据 单盘/RAID1 可用；RAID5/6 不建议生产 需要快照与子卷的系统盘、容器主机
ZFS 强好好 池可扩，vdev 移除受限 原生 + send/recv 增量复制端到端，自愈 非常高，但不在内核主线（许可证） 存储服务器、备份目标、要求数据完整性的场景
tmpfs —受内存限制极快 改 size= 即时生效 无不适用 高 /dev/shm、/run、构建中间产物、绝不落盘的临时文件
overlayfs —（转发给底层）首次写触发整文件 copy-up差（写路径要遍历各层） 随底层 靠镜像层随底层 高（容器标配） 容器根文件系统；有写压力的数据一律挂卷绕开它
不纠结的默认选择：系统盘 ext4 或 XFS 都行（想留缩容余地就 ext4）；数据盘、数据库、日志盘一律 XFS；需要文件级快照和数据校验和才上 Btrfs / ZFS，并且要认真评估它们的运维复杂度和内存需求；tmpfs 用来放「绝对不需要活过重启」的东西——注意它会被换出到 swap，不等于「一定不落盘」，放敏感数据时要留意。

overlayfs：容器为什么「写文件特别慢」

  • 它把只读的 lowerdir（镜像的各层）和可写的 upperdir 叠起来，呈现为一个 merged 视图。删除下层文件靠在上层放一个 whiteout 标记，而不是真的删。
  • copy-up：第一次写一个来自下层的文件时，overlayfs 要把整个文件先复制到上层再写。改一个 2 GB 镜像文件里的 4 字节，代价是复制 2 GB。这是容器里「同样的程序慢十倍」最常见的原因。
  • 层数越多，路径解析要逐层查找的开销越大；readdir 需要合并各层结果并去重。
  • 所以规则很简单：数据库、日志、任何有持续写压力的目录，都要用 volume / bind mount 直接落到宿主的 XFS/ext4 上，不要留在容器可写层里。容器的分层与命名空间机制见 cgroup / namespace 与容器原理。

持久化语义

全篇最重要的一章：数据到底什么时候真的落盘

前面四章讲的是「数据放在哪」，这一章讲「数据什么时候安全」。这是所有存储相关 bug 里最隐蔽的一类：代码在测试环境跑一万次都对，因为测试环境不掉电。故障只在机房断电、内核 panic、云主机被强制重启那一刻集中爆发，而那时你已经没有现场了。所以这一章的每个 API 都要精确理解，不能凭感觉。

fdatasync 到底省了什么

fsync 除了刷数据，还要把 inode 的全部元数据变更提交到日志——包括 mtime 这种「谁也不关心」的字段。这在文件系统层面意味着一次额外的日志事务提交 + 一次额外的设备 FLUSH。fdatasync 只提交「为了能把数据读回来所必需的元数据」：如果这次写没有改变文件大小（也就是在文件内部原地覆盖），那就一条元数据都不用写。

这解释了一个数据库设计上的经典细节：为什么 WAL 文件要预分配。如果每次追加日志都让文件变长，fdatasync 就必须写 size，省不下什么。所以 PostgreSQL、MySQL 这类系统会预先把 WAL 段文件按固定大小（如 16 MB）分配好并填满，之后每次写日志都是在已有长度内原地覆盖——此时 fdatasync 真正做到只发一次数据 + 一次 FLUSH，把每次事务提交的 I/O 从 3–4 次降到 1–2 次。在「提交延迟就是 TPS 上限」的负载里，这是数量级的差别。面试时能讲到这一层，比背出「fdatasync 不刷元数据」有说服力得多。
O_DIRECT 不等于持久。很多人以为「绕过页缓存就是直写磁盘」——它绕过的只是页缓存，数据仍然会停在设备的写缓存里，而且元数据变更完全没被处理。O_DIRECT 之后依然需要 fdatasync（或者同时带上 O_DSYNC）才有持久性。把 O_DIRECT 当持久化手段，是一个真实存在且后果严重的误用。

坑一：新建文件后必须 fsync 父目录

fsync(fd) 只管这个 inode 和它的数据块。可是「final.bin 这个名字指向 inode #131074」这条信息不在 inode 里，在父目录的数据块里（§2 讲过：文件名住在目录项）。父目录也是一个普通文件，它的修改同样先进页缓存。

于是掉电后完全可能出现这个诡异组合：inode 和数据都完好地在磁盘上，但没有任何名字指向它。文件系统检查时发现一个链接数为 0 却还占着块的 inode，把它当孤儿回收——你的数据就这么消失了，而 fsync 明明返回了成功。

这就像把货物完好地入库并贴好条码，但忘了在库位登记本上写下「这批货在 A3 货架」。货物真实存在，可是没人找得到它，盘库时它就被当成来源不明的东西清掉了。fsync(dirfd) 就是把登记本这一页也按下去。
哪些操作需要 fsync 父目录？所有会修改目录项的操作：creat/open(O_CREAT) 新建、rename、link、unlink、mkdir、rmdir、linkat。纯粹修改已存在文件的内容不需要——目录项没变。rename 如果跨了两个目录，两个父目录都要 fsync。

坑二：设备自己的写缓存

易失写缓存（volatile write cache）：几乎所有硬盘和 SSD 内部都有一块 DRAM，写命令数据进了这块 DRAM 就向主机报告「完成」。这让写延迟从毫秒/百微秒级降到微秒级，代价是掉电时这块 DRAM 里的内容全部消失。要让它真正进介质，主机必须显式发命令。

内核为此在 bio 上有两个标志：REQ_PREFLUSH（先把设备缓存里已有的全部刷进介质，再处理这个请求）和 REQ_FUA（Force Unit Access，这个请求必须绕过/穿透缓存直达介质）。文件系统在提交日志和处理 fsync 时会发这些标志——这才是 fsync 真正「贵」的地方：FLUSH 是一个近似串行化的操作，它要等设备把队列里所有东西都落下去。

不要为了性能挂 nobarrier。这个选项让文件系统不再发 FLUSH/FUA，fsync 会瞬间返回，跑分非常漂亮——代价是掉电时连日志本身的提交顺序都失去了保证，重放日志可能把文件系统弄得比不重放更糟。唯一可以考虑它的情况是：存储侧有电池或超级电容保护的写缓存（企业级 RAID 卡的 BBWC/FBWC、带掉电保护的企业级 SSD），此时设备承诺「已确认的写一定不丢」，FLUSH 变成了纯粹的浪费。怎么判断？看采购文档里有没有 PLP（Power Loss Protection），不要靠猜。
关于「廉价 SSD 谎报 FLUSH」：这是真实存在的，而且软件侧无法检测。一些消费级 SSD 和几乎所有 U 盘 / SD 卡的固件收到 FLUSH 后立即返回成功，实际并没有把 DRAM 里的内容写完。学术界和存储厂商做过多轮掉电测试，都能复现出「明明 fsync 成功、掉电后数据丢失甚至文件系统损坏」的结果。结论是采购结论，不是代码结论：任何需要真持久性的数据，都要跑在带 PLP 的企业级设备上。用消费级盘做数据库存储，代码写得再对也挡不住。

坑三：fsync 失败之后，数据在哪里？（fsyncgate）

2018 年 PostgreSQL 社区披露了一个让所有数据库开发者后背发凉的问题，后来被称为 fsyncgate。它的核心不是某个 bug，而是一个长期存在、被普遍误解的错误报告语义：

① 错误只报一次，之后 fsync 返回成功
回写失败时，Linux（以及当时的多个操作系统）会记下错误，但同时清掉这些页的 dirty 标记——因为内核认为「重试也没用，别把内存占死」。应用第一次 fsync 拿到 EIO，如果它按常规思路「重试一次」，第二次 fsync 会返回 0：脏页已经没有了，内核认为无事可做。应用于是确信数据已经落盘，继续推进检查点、截断 WAL——而那些数据已经彻底不存在了。
② 错误可能被别的进程「吃掉」
更早的实现把错误记在 address_space 上，谁先 fsync 谁拿到，之后就清了。PostgreSQL 的 checkpointer 进程负责 fsync，但错误可能被另一个恰好也 fsync 了同一个文件的进程先取走——checkpointer 得到的是干干净净的成功。
内核侧的改进
4.13 起引入 errseq_t：错误带序列号记在 file 上，每个打开的 fd 至少会看到一次它打开之后发生的错误，不会再被别的进程抢走（相关的文件系统适配在随后的几个版本里陆续完成）。这修好了「谁拿到」的问题。但没有、也无法修好「数据去哪了」——脏页已经被丢弃，内核手上确实没有那份数据了。
应用侧唯一正确的处理：把 fsync 失败当作不可恢复的致命错误。不要重试、不要忽略、更不要假装成功。因为你无法知道「哪些页写成功了、哪些没有」，也无法把它们从内核那里要回来——磁盘上现在是一个你不知道内容的混合状态。PostgreSQL 现在的选择就是直接 panic 并进入崩溃恢复，从 WAL 重放到一个已知一致的点。这看起来很暴力，但它是唯一诚实的做法。如果你的代码里有 if (fsync(fd) < 0) { log_warn(...); } 然后继续往下跑，那是一颗定时炸弹。
从 fsyncgate 该学到的一般结论：「写路径上的错误」和「读路径上的错误」性质完全不同。读失败你可以重试、可以降级、可以返回错误给调用方，系统状态没变。写失败之后系统进入了一个你无法观测的状态——继续运行等于在未知的基础上叠加更多未知。所以有状态服务的写路径失败，正确反应通常是停下来，从一个已知的持久点重建，而不是尝试原地修复。这个思路在 线上故障处置手册 里还会再遇到。

写文件的正确姿势：完整代码

#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <stdio.h>

// 原子且持久地把 buf 写成 dir/name。返回 0 成功，-1 失败（errno 有效）。
int write_file_durably(const char* dir, const char* name,
                       const void* buf, size_t len)
{
    char tmp[4096], dst[4096];
    snprintf(tmp, sizeof tmp, "%s/.%s.tmp.%d", dir, name, (int)getpid());
    snprintf(dst, sizeof dst, "%s/%s", dir, name);

    int fd = open(tmp, O_WRONLY | O_CREAT | O_EXCL | O_CLOEXEC, 0644);
    if (fd < 0) return -1;

    // ① write 可能【短写】，必须循环；EINTR 要重试
    const char* p = (const char*)buf;
    size_t left = len;
    while (left > 0) {
        ssize_t n = write(fd, p, left);
        if (n < 0) { if (errno == EINTR) continue; goto fail; }
        p += n; left -= (size_t)n;
    }

    // ② 数据 + 必要元数据落盘。新文件 size 变了，fdatasync 会连 size 一起写。
    //    ★ 失败就直接放弃，【绝对不要重试 fsync】——见 fsyncgate
    if (fdatasync(fd) != 0) goto fail;

    // ③ close 的返回值同样要检查：延迟分配的 ENOSPC 可能在这里才浮现
    if (close(fd) != 0) { fd = -1; goto fail; }
    fd = -1;

    // ④ 原子替换：读者看到的要么是完整旧版，要么是完整新版
    if (rename(tmp, dst) != 0) goto fail;

    // ⑤ ★★ 最容易漏的一步：让「这个名字存在」也持久化
    int dfd = open(dir, O_RDONLY | O_DIRECTORY | O_CLOEXEC);
    if (dfd < 0) return -1;
    if (fsync(dfd) != 0) { int e = errno; close(dfd); errno = e; return -1; }
    if (close(dfd) != 0) return -1;
    return 0;

fail:
    { int e = errno;
      if (fd >= 0) close(fd);
      unlink(tmp);                 // 不留 .tmp 垃圾
      errno = e; }
    return -1;
}

持久化自检清单

  • 写日志/数据用裸 write()，不用 fwrite；非要用就 setvbuf 改行缓冲。
  • write() 一律循环处理短写与 EINTR。
  • 需要持久的地方调 fsync/fdatasync，并检查返回值；失败当致命错误处理。
  • 新建文件、rename、unlink 之后 fsync 父目录；跨目录 rename 要 fsync 两个。
  • 检查 close() 的返回值——延迟分配的 ENOSPC 常常在这里才出现。
  • 需要「要么完全生效要么完全不生效」时用临时文件 + rename，绝不原地截断重写。
  • 不要挂 nobarrier，除非存储侧确实有电池/电容保护。
  • 不要把 O_DIRECT 当持久化手段。
  • 预分配定长 WAL 段文件，让 fdatasync 真正省掉元数据写。

页缓存与回写调优

脏页攒得越多吞吐越好，直到写者被一把按住

页缓存是 Linux 内存管理里最赚钱的一块——它让重复读免费、让写入可以批量化和合并。但它同时是延迟毛刺的头号来源：脏页攒到阈值时，内核会直接把正在写的进程按住，直到回写追上来。理解这套阈值机制，是解释「服务平时 p99 是 5 ms，每隔几分钟蹦到 2 秒」这类现象的关键。

脏页的三条回写触发路径

① 周期性

每 dirty_writeback_centisecs（默认 500，即 5 秒）唤醒一次回写工作线程，把「变老超过 dirty_expire_centisecs（默认 3000，即 30 秒）」的脏页写出去。这是常态路径，对应用完全透明。

② 超过后台阈值

脏页量超过 dirty_background_ratio（默认 10%）时，立刻启动回写，但不阻塞写者。这是「加大力度追赶」阶段，应用还感觉不到。

③ 超过硬阈值

超过 dirty_ratio（默认 20%）时，内核在 balance_dirty_pages 里让产生脏页的那个进程自己去等——它必须先帮着把脏页写下去才能继续。这就是毛刺。

页缓存像厨房的洗碗池。脏盘子丢进池子（write()）比洗掉快得多，所以大家都往里丢，效率很高。水位到一半（dirty_background_ratio）时后厨加派人手来洗，客人无感；水位到八成（dirty_ratio）时店里的规矩是「谁再丢盘子，谁先站在这洗一会儿」——于是服务员突然消失两秒。毛刺不是因为洗得慢，而是因为池子太大：允许攒的越多，一次被罚站的时间就越长。
参数默认语义与调优要点

vm.dirty_ratio20超过它 → 写者在 balance_dirty_pages 里被同步限速。毛刺的直接来源

调小 dirty_ratio 是把「偶发的大毛刺」换成「持续的小开销」，不是免费的。脏页窗口变小意味着合并机会变少、写放大上升、总吞吐下降。这个取舍取决于你的 SLO：延迟敏感的在线服务宁可牺牲一点吞吐换平滑（调小，或者干脆让应用自己有节奏地 sync_file_range 主动分批推）；批处理和数据导入反而应该调大，让内核有更大的合并窗口。没有一组适用于所有场景的值。

readahead：顺序读的免费加速，随机读的纯浪费

内核检测到顺序读模式时会预读后面的页。窗口从小开始，命中就翻倍增长，遇到不连续的访问就缩回去。默认上限 128 KB，可以按块设备调。

$ cat /sys/block/nvme0n1/queue/read_ahead_kb
128
$ sudo blockdev --setra 512 /dev/nvme0n1     # 单位是 512 字节扇区 → 256 KB

# 判断预读是否有效：读放大。读了 1 GB 文件，块层实际读了多少？
$ cat /proc/$$/io | grep read_bytes
read_bytes: 1207959552        # 比文件本身大 15% → 预读多拉了一些，顺序读通常划算
# 随机读场景下这个数字可能是文件大小的好几倍 —— 那就是纯浪费

用 posix_fadvise / madvise 告诉内核你的访问模式

  • POSIX_FADV_SEQUENTIAL：加大预读窗口。备份、全表扫描、大文件校验时值得加。
  • POSIX_FADV_RANDOM：关掉预读。数据库索引页这种「每次读 4 KB、位置无规律」的负载，预读只会白白占带宽和内存。
  • POSIX_FADV_WILLNEED：立刻发起异步预读。已知马上要读的场景很有用（例如启动时预热索引文件）。
  • POSIX_FADV_DONTNEED：把该范围的干净页从页缓存丢掉。⚠️ 它不会先帮你把脏页写下去——脏页会被跳过，调用看起来成功但什么也没释放。正确用法是先 sync_file_range(...WAIT_BEFORE|WRITE|WAIT_AFTER) 把范围刷干净，再 DONTNEED。
  • madvise 是 mmap 区域的对应物，语义类似。⚠️ 但 MADV_DONTNEED 用在匿名内存上是「直接丢弃内容，下次访问读到全 0」，不是「换出去」——用错会静默丢数据。
// 典型用法：流式处理一个 100 GB 的大文件，不让它把页缓存冲光
// 不加这段的话，扫一遍大文件会把其他服务的热数据全部挤出缓存
int fd = open(path, O_RDONLY);
posix_fadvise(fd, 0, 0, POSIX_FADV_SEQUENTIAL);   // 0,0 = 整个文件

off_t done = 0;
while ((n = read(fd, buf, CHUNK)) > 0) {
    process(buf, n);
    done += n;
    if (done > 64*MB) {                          // 每处理 64 MB 回收一次
        posix_fadvise(fd, 0, done - 8*MB,
                      POSIX_FADV_DONTNEED);        // 留 8 MB 余量，别把还要用的丢了
    }
}
// ★ 写场景要先刷再丢，否则 DONTNEED 对脏页无效：
//   sync_file_range(fd, off, len, SYNC_FILE_RANGE_WRITE);
//   sync_file_range(fd, off, len, SYNC_FILE_RANGE_WAIT_AFTER);
//   posix_fadvise(fd, off, len, POSIX_FADV_DONTNEED);
//   （这三步只是「回收内存」，不构成持久化保证 —— 见 §5 的表）

O_DIRECT：什么时候真该绕开页缓存

O_DIRECT 让 I/O 在用户缓冲区和设备之间直接 DMA，不经过页缓存。它不是「更快的 I/O」，而是「把缓存决策权交给应用」。

该用的场景
应用自己有更好的缓存——数据库知道哪些索引页热、知道 LRU 该怎么做、知道什么时候该批量刷脏，它不需要内核再猜一遍（双重缓存等于浪费一半内存）。MySQL 的 innodb_flush_method=O_DIRECT 就是这个道理。另一类是一次性顺序流（备份、大文件校验），数据读完就不再用，进页缓存纯属污染。
约束
对齐要求：缓冲区地址、文件偏移、长度都必须按设备的逻辑块大小对齐（用 posix_memalign 分配缓冲区）。对齐不对直接返回 EINVAL，而且不同设备的要求不一样——现代内核可以用 statx 查询 STATX_DIOALIGN 拿到准确值，而不是硬编码 512 或 4096。
最常见的误用
以为它等于持久化（见 §5），以及在小 I/O 上用它——绕过页缓存意味着失去了合并与预读，随机小读写的性能可能反而差几倍。O_DIRECT 只在「应用自己做了批量化和缓存」的前提下才有正收益。

Mem:           125Gi        18Gi       1.2Gi       0.5Gi       106Gi       105Gi
Swap:          8.0Gi          0B       8.0Gi

# 怎么读这一行：
#   free = 1.2 Gi   ← 【不要看这个】。Linux 会主动把空闲内存拿去做缓存，
#                      free 很低是【正常且健康】的，不是内存不够。
#   buff/cache      ← 页缓存 + slab 里可回收的部分（dentry/inode cache 等）
#   available       ← ★ 唯一该看的数字：不触发换出就能拿到的内存
#                      available 持续接近 0 才是真的内存告急
不要在生产环境用 echo 3 > /proc/sys/vm/drop_caches。它做的事是「把整台机器所有可回收的页缓存和 slab 缓存立刻同步丢掉」，后果是三重的：① 全部热数据要重新从磁盘读回来，之后几分钟里 I/O 打满、延迟飙升，等于自己给自己制造了一次故障；② 丢缓存的过程本身持有锁并遍历大量数据结构，在大内存机器上可能卡住几秒到几十秒，期间新的内存分配都在等；③ 它解决不了任何真实问题——如果你觉得「内存不够，清一下缓存好了」，那说明你在看 free 那一列而不是 available；如果是真的内存泄漏，缓存被丢掉之后泄漏依然在涨。它唯一的正当用途是性能测试时构造冷缓存基线。
这一章的排障心法：看到周期性延迟毛刺，先看 /proc/meminfo 的 Dirty 有没有「攒到很高再骤降」的锯齿形状。有，就是回写风暴，往 dirty_bytes 方向调；没有，再去 §9 的流程里找。这个判断只要一分钟，能省掉半小时的乱猜。

df 与 du 为什么会不一致

先搞清它们各自在数什么，不一致就不奇怪了：df 问的是文件系统的 superblock：「你一共有多少块，还剩多少空闲块」；du 做的是从某个目录开始遍历，把每个能通过路径访问到的文件的占用块数加起来。所以任何「占着块但没有路径」的东西，df 看得见、du 看不见。

# 场景：df 说 / 用了 95%，du 只数出来 40 GB
$ df -h /
Filesystem      Size  Used Avail Use% Mounted on
/dev/vda1        98G   90G  3.2G  97% /
$ sudo du -sxh / 2>/dev/null
41G     /
#            ↑ 差了 49 GB。-x 很重要：不跨文件系统，否则会把 /proc /sys 之类算进来

# ① 第一嫌疑：被删未关闭的文件
$ sudo lsof +L1 | sort -k7 -n -r | head -5
COMMAND    PID USER  FD  TYPE DEVICE    SIZE/OFF NLINK   NODE NAME
java     21877  app   5w  REG  253,1 48318382080     0 131074 /var/log/app/gc.log (deleted)
#                                     ↑ 45 GB，就是它

# ② 如果 lsof 没查到，检查挂载点是否被覆盖
#    比如有人往 /data 写了 50 GB，之后才把新盘挂到 /data 上 ——
#    那 50 GB 还在根分区里，但被遮住了，任何 du /data 都看不到它
$ sudo mkdir -p /mnt/root-real
$ sudo mount --bind / /mnt/root-real     # 把根「原样」再挂一份，不带子挂载
$ sudo du -sh /mnt/root-real/data
49G     /mnt/root-real/data              # ★ 找到了：藏在挂载点底下
$ sudo umount /mnt/root-real

# ③ 保留块：df 的 Avail 已经扣掉了这 5%
$ sudo tune2fs -l /dev/vda1 | grep -i 'reserved block count'
Reserved block count:     1284915          # × 4 KiB ≈ 4.9 GB 只给 root
# 大数据盘上 5% 太浪费，可以调小（但【不要调成 0】：
# 留一点余量能让 root 在盘满时还有办法登录和清理，也能缓解碎片化）
$ sudo tune2fs -m 1 /dev/vdb1               # 数据盘调到 1%
「挂载点被覆盖」这个坑值得单独记住，因为它完全反直觉。目录里原有的文件在挂载之后并没有消失，只是被新的挂载遮住了——它们照旧占着底层文件系统的空间，而且没有任何常规命令能看到它们。典型触发路径：新机器初始化时先启动了服务（往 /data 写了一堆），之后才把数据盘挂到 /data。半年后根分区莫名满了，怎么找都找不到。用 mount --bind 把上层挂载「揭开」是唯一可靠的排查方法。

稀疏文件：ls 和 du 打架

稀疏文件（sparse file）：文件的逻辑长度里存在空洞（hole）——那些区间从来没被写过，文件系统也就没有为它们分配任何物理块。读空洞返回全 0，但不占空间。ls -l 显示的是逻辑长度（i_size），du 显示的是实际分配的块数（st_blocks），两者可以差几个数量级。
# 造一个稀疏文件：seek 到 10 GB 处写一个字节
$ dd if=/dev/zero of=sparse.img bs=1 count=1 seek=10G 2>/dev/null
$ ls -lh sparse.img
-rw-r--r--. 1 kavin kavin 11G Sep  3 11:02 sparse.img     # ← 逻辑 10 GiB
$ du -h sparse.img
4.0K    sparse.img                                        # ← 实际 4 KB
$ du -h --apparent-size sparse.img
11G     sparse.img                                        # 让 du 也按逻辑长度算

# 看空洞的具体分布
$ filefrag -v sparse.img
 ext: logical_offset: physical_offset: length: expected: flags:
   0: 2621440..2621440: 4718592..4718592:      1:          last,eof
#     ↑ 只有最后一个块有映射，前面 2621440 个逻辑块全是空洞

# 把一个已有文件里的全 0 区间「打回」空洞（回收空间）
$ fallocate -d bigfile.img            # -d = dig holes，punch hole

# 复制稀疏文件时要小心：默认可能把空洞展开成真实的零
$ cp --sparse=always src.img dst.img  # 保持稀疏
$ rsync -S src.img host:/dst/         # rsync 的 -S 同理
$ tar --sparse -cf a.tar sparse.img   # tar 需要显式 --sparse，否则打出 11 GB
稀疏文件在容量规划上是个陷阱：一个「10 GB」的虚拟机镜像可能实际只占 800 MB，于是在一个 100 GB 的卷上放了 30 个——直到虚拟机把自己的盘写满，30 × 10 GB 的账要真的还。这本质上就是超卖，和 §8 的 thin provisioning 是同一类风险，只是发生在文件层。监控要看 df（真实占用），容量规划要按 du --apparent-size（最坏情况）。

fallocate：预分配的两个理由

ext4 和 XFS 都支持 unwritten extent：预分配的区间在元数据里标记为「已分配但未写过」，读它返回 0，不需要真的写零。所以 fallocate 一个 100 GB 的文件是瞬间完成的元数据操作，而 dd if=/dev/zero 要真写 100 GB。

理由一：把 ENOSPC 提前到启动时
数据库、消息队列在启动时预分配好数据文件，空间不够就立刻启动失败——而不是在半夜业务高峰写到一半时才 ENOSPC，那时的处理成本高得多。「让错误尽早发生」在存储上尤其值钱。
理由二：降低碎片
一次性拿到一大段连续空间，比让文件随机增长几万次要连续得多。用 FALLOC_FL_KEEP_SIZE 可以只预留空间而不改变 i_size（适合「预留但按需暴露长度」的追加型文件）。
# 命令行
$ fallocate -l 16G /data/pg/wal_prealloc     # 瞬间完成，不写一个字节的零
$ time dd if=/dev/zero of=/data/x bs=1M count=16384   # 对比：要真写 16 GB

// 代码里
#include <fcntl.h>
// 预留 16 MiB，且【不改变】文件当前长度
fallocate(fd, FALLOC_FL_KEEP_SIZE, 0, 16*1024*1024);
// 在中间挖一个空洞，把这段空间还给文件系统（长度不变）
fallocate(fd, FALLOC_FL_PUNCH_HOLE | FALLOC_FL_KEEP_SIZE, off, len);
// ★ posix_fallocate() 是可移植版本，但在不支持的文件系统上会【真的写零】,
//   在大文件上可能慢到无法接受。明确只跑 Linux 时用 fallocate()。

碎片化：什么时候真的要管

$ filefrag /data/db/table1.ibd
/data/db/table1.ibd: 184203 extents found
#                     ↑ 18 万条 extent。健康的大文件应该是几十到几百条。
#   后果不是「寻道」（SSD 上没这回事），而是：
#   ① extent B+ 树变深，每次读都要多走几层元数据；
#   ② 单次 I/O 能覆盖的连续区间变短，请求数量上升，队列变长。

# ext4 在线整理（会产生大量 I/O，安排在低峰）
$ sudo e4defrag -v /data/db/table1.ibd
# 整个文件系统的碎片率概览
$ sudo e4defrag -c /data

# XFS 侧
$ sudo xfs_bmap -vp /data/db/table1.ibd | tail -3
$ sudo xfs_fsr /data                  # 在线重组
SSD 时代碎片化依然重要，但重要的原因变了。机械盘时代是寻道；SSD 上寻道成本近似为零，真正的代价变成元数据开销（extent 树更深、每次映射查找更贵）和请求放大（连续区间短 → 一次 I/O 覆盖的数据少 → 请求数量多 → 队列深度和延迟上升）。判据不是「有没有碎片」而是「extent 数量与文件大小的比例是否离谱」：一个 10 GB 的文件有 200 条 extent 完全健康，有 18 万条就该处理了。最好的对策还是 fallocate 预分配，而不是事后 defrag。

单目录文件数过多

ext4 的 dir_index 特性（默认开启）用 HTree——一棵以文件名哈希为键的浅树——把目录查找从 O(n) 线性扫描变成近似 O(1)。所以「在一个有 300 万文件的目录里 open 一个已知名字」其实很快。真正慢的是另外三件事：

① readdir + stat 的顺序灾难
readdir 返回的顺序是哈希顺序，而 inode 在磁盘上是按创建顺序排的。于是「遍历目录并 stat 每个文件」（ls -l、du、备份、find 都是这个模式）变成了对 inode 表的纯随机访问。这是「ls 卡住十几秒」的真正原因，不是查找慢。缓解办法是先把 readdir 的结果按 inode 号排序再 stat——某些备份工具就是这么优化的。
② 删除整个大目录极慢
要逐个 unlink，每次都改目录项和位图。几百万文件的目录 rm -rf 跑几十分钟很常见，而且期间产生大量元数据 I/O 影响其他业务。
③ ls 本身要排序和缓冲
ls 默认要把全部条目读进内存排序。用 ls -U（不排序）或 ls -f 能快几十倍——排查时务必用这个。
工程结论：单目录条目数控制在几万以内，用两级十六进制分片。把 abcdef123.jpg 存成 ab/cd/abcdef123.jpg，两级各 256 个子目录，就能把 1600 万个文件均匀摊成每个目录 244 个。这不是「因为文件系统查得慢」（HTree 不慢），而是为了让 readdir+stat 的遍历、备份、删除、以及人工排查都保持在可操作的规模。所有内容寻址的存储系统（Git 的 objects/ab/cdef…、各类图片站、Docker 的 layer 目录）都是这个结构，理由完全一样。面试里能说出「慢的是遍历而不是查找」，比说「文件太多要分目录」深一层。

RAID 级别：容量、性能、风险的三角

级别可用容量一次随机写的底层 I/O可容忍故障重建代价适合
RAID 0N1 次写0 块无法重建纯临时数据、可随时从别处重算的中间结果
RAID 1N/22 次写（两块都写）每个镜像组 1 块只读镜像伙伴，最快最安全系统盘、小容量关键数据
RAID 5N−14 次（读旧数据 + 读旧校验 + 写数据 + 写校验）1 块要读遍所有剩余盘——最危险大盘时代已不推荐（见下）
RAID 6N−26 次（双校验）2 块同样要读遍剩余盘，但能扛重建期二次故障大容量归档、以读为主的数据湖
RAID 10N/22 次写每个镜像组 1 块只读镜像伙伴，快且低风险数据库、随机写重的负载
为什么 RAID 5 在大盘时代不该用了——这是一道很好的面试题。三个因素叠加：① 重建窗口极长。一块 16 TB 的盘，即便能以 150 MB/s 持续重建也要约 30 小时；生产环境上还要和业务 I/O 争带宽，实际常常是几天。② 重建期间读遍所有剩余盘。RAID 5 恢复一块盘的数据必须读全部其他盘的对应条带。这时任何一块盘出现不可恢复读错误（URE），重建就中断——而消费级盘的 URE 指标量级在「每读 1014–1015 位出现一次」，重建时要读的总量恰好就落在这个量级附近，撞上一次并非小概率事件。③ 故障相关性。同批采购、同批上架、同样的温度和振动环境，盘的失效时间是正相关的，不是独立事件——第一块坏了之后，第二块坏的条件概率显著高于基础故障率。三者相乘，「RAID 5 阵列在重建过程中彻底失效」是一个真实且反复发生的事故模式。结论：大容量盘上用 RAID 6 或 RAID 10，并且无论哪种都不能替代备份。
写洞（write hole）：RAID 5/6 的一个条带包含数据块和校验块，它们分布在不同物理盘上，无法原子地一起更新。如果在「数据已写、校验未写」的瞬间掉电，这个条带的校验就是错的——而 RAID 层不知道它是错的。危险之处在于：平时读数据不走校验，一切正常；等到某块盘真的坏了、需要用校验去重建时，重建出来的是静默错误的数据。

LVM 快照：CoW 的代价，以及两种「写满」的不同后果

传统 LVM 快照：创建时不复制任何数据，只分配一块异常存储区（COW 区）。之后每次向原卷写入一个尚未被复制过的块时，dm 层要先把该块的旧内容复制到 COW 区，再执行写入。读快照时，被改过的块从 COW 区读，没改过的直接读原卷。
这就像给一本正在被人涂改的书做快照：不复印整本书，只在每次有人要涂改某一页之前，先把那一页原样复印一份存起来。做快照本身是瞬间的，但之后每一次修改都变贵了（一次读 + 一次额外写 + 一次原写入）。而且复印纸是有限的——用完了，这份快照就再也拼不出完整的旧版本了。
「快照写满」的后果取决于是哪种快照，这个区别很重要，别记混：

传统快照（lvcreate -s -L 分配固定 COW 区）：COW 区用满时，快照自己失效（lvs 的 Attr 里出现 I 表示 invalid），无法再读；原卷不受影响，继续正常工作。损失是备份没了，业务还在。

thin pool（lvcreate --thinpool，原卷和快照共享一个超卖的池）：池写满时整个池上的所有卷一起出问题——写入返回 I/O 错误，文件系统通常会立刻转成只读或直接报错。这才是「原卷不可用」的那种情况，而且因为 thin pool 常常同时承载多个卷，影响面是整台机器级别的。更隐蔽的是元数据池：metadata_percent 满了后果同样严重，而它容量小得多、更容易被忽略，监控时两个百分比都要看。

在线扩容：顺序反了就会丢数据

操作正确顺序为什么
扩容① 先扩块设备（lvextend）→ ② 再扩文件系统文件系统不能超出底层设备的边界。反了会立刻失败（幸运情况）

XFS 缩容不存在XFS 没有 shrink，只能备份 + 重建 + 恢复（§4）
 
# ── 扩容：ext4 和 XFS 都能在【挂载状态下】完成 ──────────────
$ sudo lvextend -L +500G /dev/vg0/data          # ① 先把 LV 扩大
$ sudo resize2fs /dev/vg0/data                  # ② ext4：不带尺寸 = 用满设备
$ sudo xfs_growfs /data                         # ② XFS：★ 参数是【挂载点】不是设备

# 更省事：-r / --resizefs 让 lvextend 自动调用对应的文件系统工具
$ sudo lvextend -r -L +500G /dev/vg0/data

# ── 缩容（只有 ext4 可以，且必须卸载）───────────────────────
$ sudo umount /data
$ sudo e2fsck -f /dev/vg0/data                  # ★ resize2fs 缩容前强制要求先 fsck
$ sudo resize2fs /dev/vg0/data 2T               # ① 先把文件系统缩到 2T
$ sudo lvreduce -L 2T /dev/vg0/data             # ② 再缩 LV，尺寸必须 ≥ 上一步
$ sudo mount /data
# ★★ 把 ① ② 顺序写反 = 数据永久损坏。lvreduce 会警告，但它拦不住 -f。

多路径：冗余带来的一个新故障模式

dm-multipath 把同一个 LUN 的多条物理链路（多个 HBA、多个交换机、存储的多个控制器口）合成一个设备，任一条路径故障时自动切换。它保护的是链路，不是盘——存储阵列本身坏了，多路径救不了。

queue_if_no_path 是多路径最著名的坑。它的语义是「所有路径都断了时，把 I/O 无限期排队而不是报错」——设计意图是让短暂的全路径抖动（交换机重启）对应用透明。但如果链路是真的长时间断了，后果是：所有访问该设备的进程永久卡在 D 状态（不可中断睡眠），kill -9 也杀不掉，umount 挂住，最后往往只能硬重启整台机器。生产上应该配 no_path_retry <N>（重试 N 个周期后放弃并向上报错），把「无限等待」换成「有界等待后失败」——让上层有机会做决策，永远好过让它挂死。

NVMe 与 blk-mq 一句话：传统 SATA/SAS 只有一个硬件队列，内核也只有一个带全局锁的请求队列，几十个核一起提交 I/O 时那把锁就是瓶颈。NVMe 协议原生支持大量硬件队列，内核的 blk-mq 因此做成每 CPU 一个软件队列、映射到硬件队列，提交路径上不再有跨核争抢——这也是为什么 NVMe 设备默认的 I/O 调度器常常是 none（设备内部并行度已经很高，内核再排序只是添乱）。多队列的结构细节、各调度器的策略、以及它对 %util 这个指标的破坏（见 §9），在 Linux I/O 与内核 I/O 栈 里展开。

I/O 排障工作流

先判断「是不是 I/O」，再判断「是哪一层」

「应用变慢了，是不是磁盘的问题」——这个问题被答错的频率极高，最常见的错误路径是「看到 top 里 %wa 高，就断定磁盘慢，然后去换盘」。下面这张决策树的价值在于，它先用两个便宜的判据把问题定位到某一层，再针对那一层上工具，而不是一上来就 iostat 猜。

第一步：先证明这真的是 I/O 问题

「iowait 高就是磁盘慢」是这一章要打掉的头号误判。%iowait 的定义是：该 CPU 处于空闲状态、且此刻至少有一个 I/O 请求在飞的时间占比。注意它是一个关于 CPU 空闲的指标，不是关于磁盘的指标。两个方向都会误导你：

① 高 iowait 不代表磁盘有问题。一台 CPU 完全空闲的机器上跑一个正常的批量拷贝，iowait 可以是 90%——这只说明「CPU 没别的事干，而且在等 I/O」，磁盘可能好得很。

② 低 iowait 不代表磁盘没问题。64 核的机器上，一个线程被慢盘卡死，iowait 最多贡献 1/64 ≈ 1.5%，几乎看不见；更极端的是——只要 CPU 上还有别的可运行任务，那段时间就被记成 %user/%sys 而不是 %iowait。业务被 I/O 拖死，而 iowait 是 0.3%，这在繁忙的机器上是常态。

所以 iowait 只适合当一个粗糙的旁证。真正该看的是下面两个直接指标。

# ① PSI（Pressure Stall Information，4.20+）—— 直接回答「有多少时间因 I/O 卡住」

r_await / w_await请求从进入内核队列到完成的平均总耗时（含排队）最重要的两个字段，而且必须分开看。合并成一个 await 会把「读快写慢」这类问题彻底掩盖

%util「至少有一个请求在飞」的时间占比在 NVMe / RAID / 多队列设备上基本无意义。这些设备内部并行度很高，100% 只表示「没闲着」，不表示「到极限了」。不要拿它当饱和度指标
rareq-sz / wareq-sz平均请求大小（KB）持续很小（4–8 KB）说明是随机小 I/O，或者上层没做批量化；预期是顺序大 I/O 却看到小值 → 查预读和 O_DIRECT 用法
rrqm/s / %rrqm被合并掉的请求数与比例合并率高说明访问是顺序的，块层在帮你省 I/O。O_DIRECT 下通常接近 0
svctm旧版本里的「服务时间」已经从新版 sysstat 里删除了，因为在多队列设备上它的计算方式根本不成立。看到老文档教你看 svctm，那份文档过时了

I/O 排障速查

  • 先证明是 I/O：/proc/pressure/io 的 full + D 状态进程的 wchan。别用 iowait 下结论。
  • 再分三类：r_await/w_await 与 aqu-sz 的组合（见决策树）。忽略 %util。
  • 不在设备 → 查 fsync 频率（biosnoop 里满屏 jbd2 就是证据）、队列深度、io.max 限流、页缓存命中率。
  • 排队 → iotop/pidstat -d 找出压 I/O 的进程，限流、错峰或扩容。
  • 单请求慢 → dmesg + smartctl 确认硬件；btt 看 D2C 是否占大头；检查 RAID 是否在重建、多路径是否在切换。
  • 周期性毛刺 → 先看 /proc/meminfo 的 Dirty 锯齿（§6），再看日志提交（jbd2_log_wait_commit）。
  • 容器里慢 → 先确认数据没落在 overlayfs 可写层（§4），再看 cgroup 的 io.max 与 io.pressure。
整套流程的核心是「先分层，再上工具」。I/O 问题的工具特别多，容易变成「把所有命令都跑一遍然后盯着一屏数字发呆」。决策树的价值不在于它给出答案，而在于它先把可能性砍成三分之一——每一类后续用的工具、能得出的结论、能采取的行动都完全不同。故障时的流程化处置见 线上故障处置手册；持续压测与性能基线方法见 性能工程全景。

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础硬链接和软链接有什么区别？为什么硬链接不能跨文件系统、也不能指向目录？

    硬链接是在目录里多加一条指向同一个 inode 的记录——两个名字完全平等，没有主次。ls -i 会看到相同的 inode 号，inode 的 i_nlink 是 2。软链接（符号链接）是一个独立的 inode，它的数据内容就是一段路径字符串。

    核心认知：文件名不在 inode 里，在目录项里。inode 只存元数据和数据块映射。理解这一句，两种链接的所有差异都能自己推出来。

    为什么不能跨文件系统
    硬链接记的是 inode 号，而 inode 号只在自己的 superblock 范围内唯一。跨挂载点写下一个 inode 号毫无意义——目标文件系统里那个号是别的文件。所以 ln 跨设备直接返回 EXDEV。软链接存的是路径字符串，指向哪都行，甚至可以指向还不存在的路径。
    为什么不能指向目录
    会产生目录环，后果有三层：① find/du/备份这类遍历工具陷入无限循环，而且没法用「访问过的 inode 集合」简单判环——合法的硬链接文件本来就会重复出现；② .. 变得歧义，一个目录有多个父目录，cd .. 不知道该去哪；③ 引用计数无法回收环状结构，删掉外部引用后环内部还互相引用着，空间永久泄漏（引用计数式回收的经典缺陷）。内核选择直接禁止，把复杂度挡在门外。软链接没这个问题，因为它不参与引用计数，遍历工具默认也不跟随它。
    常见追问
    「删掉原文件会怎样？」——硬链接照常可用（数据块还在，链接数减一）；软链接变成悬空链接，访问返回 ENOENT。另外软链接自己的权限位是无意义的（永远显示 777），实际检查的是目标的权限。
  2. 基础rm 了一个 30 GB 的日志文件，df 显示空间一点没降，为什么？怎么处理？

    因为还有进程持有指向它的打开文件描述符。rm 实际调用的是 unlink，它只删掉「名字 → inode」的绑定并把 i_nlink 减一。真正释放数据块需要两个条件同时满足：i_nlink == 0（没有任何名字指向它）并且 i_count == 0（没有任何进程打开它）。

    此时文件已经从目录树里消失（du 遍历不到它，所以 du 和 df 会对不上），但它仍然活着，而且写日志的进程还在继续往里写、还在继续变大。

    定位
    sudo lsof +L1——+L1 的意思是「只列出链接数小于 1 的打开文件」，输出里 NLINK 列为 0、名字带 (deleted) 的就是它。
    处理，按优雅程度排序
    ① 让进程重新打开日志文件（kill -USR1 给 nginx、服务自己的 reload）；② truncate -s 0 /proc/<pid>/fd/<n> 立刻还空间且不用重启进程；③ 重启进程。
    方式 ② 的陷阱
    如果那个 fd 不是 O_APPEND 打开的，进程内部的写偏移不会归零，它会继续在 30 GB 那个位置写，文件立刻变成前面全是空洞的稀疏文件。所以正确的日志轮转是 copytruncate 或让进程配合 reopen，而不是 rm + truncate。
    反过来用是个好技巧
    「open 之后立刻 unlink」能造出一个真正的临时文件：没有名字，别人无法通过路径访问，进程一退出（哪怕是 SIGKILL）内核自动回收，永远不留垃圾。tmpfile() 就是这么实现的，更现代的写法是 O_TMPFILE + linkat。
  3. 基础write() 返回成功，数据就安全了吗？fsync 和 fdatasync 有什么区别？

    不安全。write() 返回只保证「数据进了页缓存，其他进程读得到」。此时数据在内核内存里：进程崩溃不会丢（内核持有），但内核 panic 或机器掉电就全丢。默认配置下脏页可以在内存里待 30 秒（dirty_expire_centisecs）。

    更靠前还有一层：如果用的是 fwrite，数据可能连内核都还没进——它还在 glibc 的 stdio 缓冲区里，进程被 kill 就没了。重定向到文件时 stdio 是全缓冲（4 KB），这是「崩溃后日志少了最后几百行」最常见的原因。

    fsync(fd)
    把该文件的全部脏页推下去，写全部元数据（包括 mtime 这种没人关心的字段），并向设备发 FLUSH 让写缓存进介质。
    fdatasync(fd)
    同样刷数据和发 FLUSH，但只写「为了把数据读回来所必需」的元数据。如果这次写没有改变文件大小（在文件内部原地覆盖），那就一条元数据都不用写——省掉一次日志事务提交和一次额外的 FLUSH。
    这个区别的实际价值
    解释了为什么数据库要预分配定长 WAL 段文件：预分配之后每次写日志都是原地覆盖，fdatasync 才真正省掉元数据写，把每次事务提交的 I/O 从 3–4 次降到 1–2 次。在「提交延迟决定 TPS 上限」的负载里这是数量级差别。
    两个常见误解
    O_DIRECT 不等于持久——它只绕过页缓存，数据仍停在设备写缓存里，元数据也完全没处理，之后照样要 fdatasync。sync_file_range() 也不是持久化原语——它只发起/等待页回写，不写元数据、不发 FLUSH，man 手册明确警告过。
  4. 基础df 说磁盘满了，但 du -sh 加起来差了几十 GB。有哪几种可能？

    先搞清两者在数什么：df 问的是文件系统的 superblock「一共多少块、还剩多少空闲块」；du 是从某个目录遍历，把每个能通过路径访问到的文件的占用块数加起来。所以凡是「占着块但没有路径」的东西，df 看得见、du 看不见。

    • 被删未关闭的文件（最常见）：lsof +L1。见上一题。
    • 挂载点被覆盖：挂载之前就写进那个目录的文件仍占着底层文件系统的空间，但被上层挂载遮住了，任何常规命令都看不到。用 mount --bind / /mnt 把上层「揭开」再 du。典型触发路径：新机器先起了服务往 /data 写，之后才把数据盘挂到 /data。
    • 保留块：ext4 默认留 5% 只给 root，df 的 Avail 已经扣掉了。tune2fs -l | grep -i reserved 确认，大数据盘可以 tune2fs -m 1 调小（但不要调成 0）。
    • 硬链接：du 对同一个 inode 只计一次，备份工具大量使用硬链接时差异会很明显。
    • 稀疏文件：这个方向相反——du 反而比 ls -l 小很多（空洞不占块）。
    • 用错了参数：du 不加 -x 会跨文件系统，把 /proc、其他挂载点算进来；不加 sudo 会漏掉没权限进入的目录（而且错误信息被 2>/dev/null 吞了）。
    还有一种
    df -h 空间明明够，但写文件报 ENOSPC——那不是空间问题，是 inode 耗尽，用 df -i 才看得到。

10.2 中级（区分熟练度）

  1. 中级ext4 的 data=journal / ordered / writeback 有什么区别？默认的 ordered 到底保证了什么？

    日志（jbd2）的作用是保证元数据的原子性：把即将进行的修改先顺序追加到日志区并提交，再改真正的位置，崩溃后重放即可，不用全盘 fsck。三种模式的差别在于「数据要不要也进日志、以及数据和元数据的先后顺序」。

    • data=journal：元数据和数据都进日志。一致性最强（已提交的数据能从日志重放恢复），但数据要写两遍，而且与延迟分配、O_DIRECT 不兼容。实际很少用。
    • data=ordered（默认）：只有元数据进日志，但强制数据块先落盘，再提交引用它的元数据。
    • data=writeback：只有元数据进日志，且不约束顺序。文件长度可能已经更新而数据还没写，崩溃后读到那块磁盘上残留的陈旧内容——可能是别人已删除文件的字节，这是实打实的信息泄露面。
    最常见的误解，必须答对
    data=ordered 保证的是「元数据一致」和「不会读到别人的旧数据」，不是「你写的数据不会丢」。崩溃后一个没 fsync 的文件完全可能是空的或只有前半段。「ordered」约束的是顺序（数据在元数据之前落盘），不是时机（什么时候落盘）。想要不丢，只能靠应用自己 fsync——挂载模式怎么调都替代不了它。
    再深一层
    日志也不能替代 fsck 和备份。它挡不住：位翻转与介质错误（ext4 的 metadata_csum 只校验元数据，数据块根本没有校验和，要端到端校验必须上 Btrfs/ZFS）；磁盘谎报 FLUSH 导致日志自己的提交顺序被破坏（此时重放可能让情况更糟）；以及逻辑错误——rm -rf 是一次完全一致的元数据操作。所以 Filesystem state: clean 只说明上次正常卸载过，不说明数据是对的。
  2. 中级什么是延迟分配（delayed allocation）？它带来什么好处，以及那个「崩溃后 0 字节文件」是怎么回事？

    延迟分配：write() 时 ext4 只在页缓存里记账（预留配额，标记为待分配），并不决定这些数据落在哪些物理块上。真正的块分配推迟到回写那一刻——此时内核已经知道这个文件总共要写多少字节，可以一次性挑一段足够长的连续空间。

    好处：extent 数量大幅减少，碎片和写放大都下降。一个 512 MiB 的文件常常只要 4 条 extent（每条顶格 128 MiB）。

    副作用一：ENOSPC 迟到
    块分配被推迟了，所以 write() 可能返回成功，直到真正分配时才发现盘满。这个错误只在后续的 fsync、close 或异步回写时才浮现。这是「必须检查 close() 返回值」的硬理由，不是教科书洁癖。
    副作用二：2009 年那批 0 字节文件
    ext4 刚普及时，用户发现崩溃后一批配置文件变成 0 字节。原因是那些应用把保存写成了「truncate 到 0 再重写」或「写临时文件再 rename 但不 fsync」。在 ext3 的 data=ordered 下，日志提交会顺带把数据刷下去（默认 5 秒一次），这类代码侥幸一直没出事；换到 ext4，延迟分配让数据能在页缓存里待更久，而元数据操作（truncate/rename）反而先通过日志落盘了——重启后就得到一个「已截断到 0 或已改名成功、但内容没写下去」的文件。
    责任划分与现代内核的行为（这一层是加分项）
    严格说那些应用本来就是错的：POSIX 从没承诺不 fsync 的数据能活过掉电，ext3 的行为只是不受保证的巧合。但「技术上正确」解决不了用户丢配置，所以 ext4 在 2.6.30 前后加了启发式补救：检测到「rename 覆盖已存在文件」和「truncate 到 0 后重写再 close」这两种模式时，自动触发延迟分配块的分配与回写（可用 noauto_da_alloc 关掉）。但这只是给坏代码兜底，不是可依赖的语义——它不发设备 FLUSH，也不管父目录，跨文件系统更不通用。正确的代码依然必须自己 fsync。
  3. 中级为什么新建文件后还要 fsync 父目录？rename() 的原子性到底保证了什么？

    因为文件名不在 inode 里，在父目录的数据块里。fsync(fd) 只管这个 inode 和它的数据块；「final.bin 这个名字指向 inode #131074」这条信息属于父目录这个文件的内容，它的修改同样先进页缓存。

    于是掉电后可能出现这个诡异组合：inode 和数据都完好地在磁盘上，但没有任何名字指向它。文件系统检查时发现一个链接数为 0 却还占着块的 inode，就把它当孤儿回收——数据消失了，而你的 fsync 明明返回了成功。

    需要 fsync 父目录的操作：所有会改目录项的——open(O_CREAT)、rename、link、unlink、mkdir、rmdir。纯粹改已存在文件的内容不需要。rename 跨了两个目录，两个父目录都要 fsync。

    rename 的原子性，最容易答偏的一点
    POSIX 保证：同一个文件系统内，其他进程通过目标路径看到的要么是完整旧文件、要么是完整新文件，绝不会出现「不存在」或「半新半旧」。但这是「命名空间可见性」的原子性，不是「崩溃持久性」。它保证其他进程看不到中间态，完全不保证掉电后你能看到新文件——甚至不保证还能看到旧文件，因为这次改名本身也只是页缓存里的元数据修改。「写临时文件 + rename」只解决并发可见性，没解决持久性。
    完整的正确写法
    ① 写临时文件（裸 write 循环处理短写）→ ② fdatasync 临时文件 → ③ 检查 close 的返回值 → ④ rename 到目标名 → ⑤ fsync 父目录的 fd。任意一步失败都要清理临时文件并向调用方报错。
    值得一提的两个能力
    renameat2（3.15+）的 RENAME_NOREPLACE（目标存在就失败，避免 access+rename 的 TOCTOU 竞态）和 RENAME_EXCHANGE（原子交换两个路径，是「灰度切换整个目录再一键回滚」的利器）。
  4. 中级磁盘还有 90% 空间，但创建文件报 ENOSPC。怎么确认、怎么救、怎么预防？

    inode 耗尽。df -h 看空间，df -i 看 inode——后者 IUse% 到 100% 时，即使空间只用了 7%，也创建不了任何新文件。

    根因：ext4 的 inode 表是预分配的，总数在 mkfs 时按 inode_ratio（默认段通常是 16384，即每 16 KB 空间配一个 inode）算好并写进 superblock 和 group descriptor。这个比例假设文件平均 16 KB——一旦负载是「几千万个 200 字节的小文件」（缩略图、邮件队列、监控碎片），inode 会在空间用掉不到 2% 时就耗尽。

    定位是谁生产的
    按文件数而不是大小统计：find /data -xdev -type d -exec sh -c 'echo "$(ls -U "$1" | wc -l) $1"' _ {} \; | sort -rn | head。ls -U 不排序，在几百万条目的目录里比 ls 快几十倍——排查时这个细节很重要。粗筛也可以看目录文件自身的大小（find -type d -size +1M），它反映目录项数量。
    救：ext4 上没有在线办法
    resize2fs 能扩块数，但不能增加 inode 总数。可选项只有：① 删文件（治标）；② 把海量小文件打包成归档（几百万个文件变成一个 tar，inode 从几百万降到 1）；③ 备份 + mkfs.ext4 -i 4096 或 -N 重建 + 恢复；④ 换 XFS。
    预防
    XFS 不预分配 inode，按 chunk 动态分配、用 B+ 树索引，只要有空间就能建文件（imaxpct 只是占用比例上限，不是预留，还能在线调）。凡是会产生海量小文件的用途，一律选 XFS；非要用 ext4 就在格式化时把 inode 密度提上来，并算清 inode 表本身的空间成本（2000 万 × 256 字节 ≈ 5.1 GB）。

10.3 高级（体现深度）

  1. 高级fsync() 返回错误之后，那些数据在哪里？应用应该怎么处理？

    这是 2018 年 PostgreSQL 社区披露的 fsyncgate。它的核心不是某个 bug，而是一个长期存在、被普遍误解的错误报告语义。

    问题一：错误只报一次，重试会返回成功
    回写失败时，内核记下错误，同时清掉这些页的 dirty 标记（认为「重试也没用，别把内存占死」）。应用第一次 fsync 拿到 EIO，如果按常规思路重试一次，第二次会返回 0——脏页已经没了，内核认为无事可做。应用于是确信数据已落盘，继续推进检查点、截断 WAL，而那些数据已经彻底不存在。
    问题二：错误可能被别的进程吃掉
    更早的实现把错误记在 address_space 上，谁先 fsync 谁拿到，之后就清了。PostgreSQL 的 checkpointer 负责 fsync，但错误可能被另一个恰好也 fsync 了同一个文件的进程先取走，checkpointer 得到干干净净的成功。
    内核侧的改进
    4.13 起引入 errseq_t：错误带序列号记在 struct file 上，每个 fd 至少会看到一次它打开之后发生的错误，不会再被别人抢走（各文件系统的适配在随后几个版本陆续完成）。这修好了「谁拿到」。但没有、也无法修好「数据去哪了」——脏页已被丢弃，内核手上确实没有那份数据了。
    应用侧唯一正确的处理
    把 fsync 失败当作不可恢复的致命错误：不重试、不忽略、更不能假装成功。因为你无法知道哪些页写成功了、哪些没有，也无法把它们要回来——磁盘上现在是一个你不知道内容的混合状态。PostgreSQL 现在的选择是直接 panic 并进入崩溃恢复，从 WAL 重放到一个已知一致的点。看着暴力，但它是唯一诚实的做法。if (fsync(fd) < 0) { log_warn(...); } 然后继续跑，是一颗定时炸弹。
    该学到的一般结论
    「写路径的错误」和「读路径的错误」性质完全不同。读失败可以重试、降级、返回错误，系统状态没变；写失败之后系统进入了一个你无法观测的状态，继续运行等于在未知之上叠加更多未知。所以有状态服务的写路径失败，正确反应是停下来，从一个已知的持久点重建，而不是原地修复。
  2. 高级服务平时 p99 是 5 ms，每隔几分钟蹦到 2 秒。磁盘不忙，怎么定位？

    典型的脏页回写风暴。先看一分钟就能确认的判据：

    $ while :; do grep -E '^(Dirty|Writeback):' /proc/meminfo | tr '\n' ' '; echo; sleep 1; done
# Dirty 呈现「缓慢攒高 → 骤降」的锯齿形状，且骤降时刻与毛刺时刻吻合 = 就是它

    机制：脏页有三条回写触发路径。① 周期性（每 dirty_writeback_centisecs=5 s 唤醒，写出老于 dirty_expire_centisecs=30 s 的页）；② 超过 dirty_background_ratio（默认 10%）启动后台回写，不阻塞写者；③ 超过 dirty_ratio（默认 20%）时，内核在 balance_dirty_pages 里让产生脏页的那个进程自己去等——它必须帮着把脏页写下去才能继续。第三条就是毛刺。

    为什么大内存机器上特别严重
    比例的分母是可脏化内存（大致是空闲内存 + 可回收文件页）。512 GB 内存的机器上，20% 意味着可以攒到上百 GB 脏页；一旦触线，那一次要写下去的量远超设备几秒的吞吐，被罚站的进程就卡了好几秒。毛刺不是因为设备慢，而是因为允许攒的窗口太大。
    处理
    把上界从「百分比」换成确定的字节数：vm.dirty_bytes / vm.dirty_background_bytes，目标是「一次要写的量在设备 1–2 秒能吐完的范围内」。注意 *_bytes 与 *_ratio 互斥，设了一个另一个自动归零。更根本的做法是让应用自己有节奏地分批推（写一段就 sync_file_range(...WRITE)），主动把大峰摊平，而不是等内核来罚站。
    这是个取舍，不是免费的
    调小脏页窗口 = 合并机会变少、写放大上升、总吞吐下降。延迟敏感的在线服务该调小；批处理和数据导入反而该调大，让内核有更大的合并窗口。没有一组适用于所有场景的值。
    如果 Dirty 没有锯齿
    那就换方向：看 D 状态进程的 wchan。jbd2_log_wait_commit 说明卡在 ext4 日志提交上（fsync 太频繁，用 biosnoop 会看到满屏 jbd2 线程的 4 KB 写）；也要排查 RAID 是否在重建、多路径是否在切换、cgroup 的 io.max 是否在周期性限流。
  3. 高级为什么大容量盘时代不推荐 RAID 5？什么是写洞？

    RAID 5 用单份分布式校验换容量（可用 N−1），能容忍 1 块盘故障。它在小容量盘时代是很好的取舍，但三个因素叠加之后不再成立：

    ① 重建窗口极长
    一块 16 TB 的盘，即便能以 150 MB/s 持续重建也要约 30 小时；生产环境还要和业务 I/O 争带宽，实际常常是几天。这几天里阵列是没有冗余的。
    ② 重建必须读遍所有剩余盘
    恢复一块盘的数据要读全部其他盘的对应条带。此时任何一块盘出现不可恢复读错误（URE），重建就中断——而消费级盘的 URE 指标量级是「每读 1014–1015 位出现一次」，重建要读的总量恰好落在这个量级附近。
    ③ 故障是相关的，不是独立的
    同批采购、同批上架、同样的温度和振动环境，盘的失效时间正相关。第一块坏了之后，第二块坏的条件概率显著高于基础故障率。拿独立事件的概率去算「两块同时坏的可能性极小」是错的。
    写洞（write hole）
    一个条带的数据块和校验块分布在不同物理盘上，无法原子地一起更新。在「数据已写、校验未写」的瞬间掉电，这个条带的校验就是错的——而 RAID 层不知道它错了。危险在于：平时读数据不走校验，一切正常；等到某块盘真的坏了、需要用校验重建时，重建出来的是静默错误的数据。Linux md 的缓解手段是 --consistency-policy=ppl（部分校验日志，开销小，仅 RAID 5）或 --write-journal（独立的日志设备，最彻底但要额外盘）。
    结论与运维要求
    大容量盘上用 RAID 6（能扛重建期二次故障）或 RAID 10（重建只读镜像伙伴，又快又低风险，随机写还便宜——RAID 5 一次随机写要 4 次底层 I/O，RAID 6 要 6 次，RAID 10 只要 2 次）。另外必须开定期巡检（echo check > /sys/block/md0/md/sync_action，看 mismatch_cnt）——不巡检的话坏块会一直潜伏到重建那一刻才暴露。而无论哪种 RAID 都不能替代备份：它防的是盘坏，防不了 rm -rf、勒索软件和机房事故。
  4. 高级top 里 %wa 高就说明磁盘慢吗？给出你判断「应用慢是不是 I/O 导致」的完整路径。

    不能这么判断。%iowait 的定义是「该 CPU 处于空闲状态、且此刻至少有一个 I/O 在飞」的时间占比——它是一个关于 CPU 空闲的指标，不是关于磁盘的指标。两个方向都会误导：

    高 iowait 不代表磁盘有问题
    一台 CPU 完全空闲的机器上跑一个正常的批量拷贝，iowait 可以是 90%。这只说明「CPU 没别的事干而且在等 I/O」，盘可能好得很。
    低 iowait 不代表磁盘没问题
    64 核机器上一个线程被慢盘卡死，iowait 最多贡献 1/64 ≈ 1.5%；更极端的是——只要 CPU 上还有别的可运行任务，那段时间就被记成 %user/%sys 而不是 %iowait。业务被 I/O 拖死而 iowait 是 0.3%，在繁忙机器上是常态。

    正确的判断路径，分两步：

    第一步：先证明是 I/O
    看 /proc/pressure/io（PSI，4.20+）的 full 那一行——它统计的是任务的停顿而非 CPU 的空闲，不受核数和其他负载稀释；cgroup v2 里还有 per-cgroup 的 io.pressure。再看 D 状态进程的 wchan（ps -eo state,pid,comm,wchan:32），wait_on_page_writeback / jbd2_log_wait_commit 这类值信息量极大。
    第二步：分成三类，各走各的路
    用 iostat -x 1 的 r_await/w_await（必须分开看，合并会掩盖「读快写慢」）配 aqu-sz：① await 低 + 队列浅 → 瓶颈不在设备（fsync 太频繁、队列深度只有 1、cgroup io.max 限流、页缓存命中率掉了）；② await 高 + 队列深 → 排队，用 iotop/pidstat -d 找出压 I/O 的进程；③ await 高 + 队列浅 → 单请求本身慢，查 dmesg/smartctl、RAID 重建、多路径切换。
    顺带纠正两个过时的指标
    %util 在 NVMe / RAID / 多队列设备上基本无意义——它只表示「至少有一个请求在飞」的时间占比，这些设备内部并行度很高，100% 不代表到极限了。不要拿它当饱和度。而 svctm 已经从新版 sysstat 里删掉了，因为它的计算方式在多队列设备上根本不成立；看到老文档教你看 svctm，那份文档过时了。
    要精确拆解耗时就上 blktrace
    blktrace + btt 把单个 I/O 拆成 Q2G（分配 request）、G2I（插入队列）、I2D（内核侧排队）、D2C（设备真实服务时间）。如果 Q2C 平均 44 ms 而其中 I2D 占 42 ms、D2C 只有 2 ms，那么换更快的盘毫无用处——时间全花在内核排队上，该做的是降并发、调调度器、或查限流。同理，ext4slower 报大量慢操作但 biolatency 显示块层很快，说明问题在文件系统层或以上，不在盘上。
