API行为坑

⚠ iostream 的性能陷阱

6.3 LT vs ET (水平触发 vs 边缘触发)

LT水平触发 (Level Trigger)

只要可读/可写就持续通知。默认模式，编程简单；兼容阻塞 fd。

ET边缘触发 (Edge Trigger)

状态变化时才通知。必须非阻塞 fd，且循环 read 直到 EAGAIN。Nginx/Redis 标配。

// ET 模式的正确用法：必须读尽数据
epoll_event ev{.events = EPOLLIN | EPOLLET, .data.fd = fd};
fcntl(fd, F_SETFL, O_NONBLOCK);
epoll_ctl(ep, EPOLL_CTL_ADD, fd, &ev);

while (true) {
    int n = epoll_wait(ep, events, 64, -1);
    for (int i = 0; i < n; ++i) {
        int cfd = events[i].data.fd;
        // ET 模式下必须 while 循环读尽
        while (true) {
            ssize_t r = read(cfd, buf, sizeof(buf));
            if (r > 0) /* 处理 */;
            else if (r == 0) { close(cfd); break; }  // EOF
            else if (errno == EAGAIN) break;   // 读完了
            else { perror("read"); close(cfd); break; }
        }
    }
}
⚠ epoll 惊群

多进程 epoll_wait 同一个 listen fd，来连接时全被唤醒。解法：Linux 4.5+ EPOLLEXCLUSIVE、SO_REUSEPORT，或 Nginx accept mutex。

⚠ mmap 的陷阱

  • TLB miss：随机扫大文件可能比 read 慢
  • 小文件不划算：建 VMA + 页表有固定开销，<4KB 用 read
  • MAP_SHARED：必须 msync / munmap 才保证落盘

// sendfile 实现高性能 HTTP 文件服务
int serve_file(int client_sock, const char* path) {
    int fd = open(path, O_RDONLY);
    struct stat st;
    fstat(fd, &st);

    // HTTP 头
    std::string hdr = std::format(
        "HTTP/1.1 200 OK\r\nContent-Length: {}\r\n\r\n", st.st_size);
    write(client_sock, hdr.data(), hdr.size());

    // 零拷贝发送文件主体
    off_t offset = 0;
    while (offset < st.st_size) {
        ssize_t sent = sendfile(client_sock, fd, &offset,
                                  st.st_size - offset);
        if (sent <= 0) break;
    }
    close(fd);
    return 0;
}

9.3 Direct I/O (O_DIRECT)

绕过 Page Cache，用户 buf 与磁盘直 DMA。自己管缓存时避免双重缓存，延迟更可预测。约束：buf / offset / size 必须按块对齐（512B 或 4KB），用 posix_memalign；小 I/O 没有缓存聚合，更慢。

// Direct I/O 的正确用法 (数据库/日志系统)
constexpr size_t BLOCK = 4096;

int fd = open("data.bin", O_RDWR | O_DIRECT | O_CREAT, 0644);

void* buf = nullptr;
posix_memalign(&buf, BLOCK, BLOCK * 256);  // 必须对齐

read(fd, buf, BLOCK * 256);   // 直接 DMA 到 buf
write(fd, buf, BLOCK);        // 绕过 page cache 直接写盘

free(buf);
close(fd);
▶ 谁在用 Direct I/O

自己管缓存才划算：InnoDB Buffer Pool、RocksDB 的 SST（WAL 仍普通 I/O + fsync）、Ceph / ScyllaDB（稳定延迟，常配 io_uring）。

▶ 它们为什么宁可自己管缓存

因为存储引擎知道内核不知道的事：哪些页是索引内节点必须常驻、哪些是马上会被覆盖的 WAL、哪些扫完一次就不会再用。B+Tree 与 LSM-Tree 各自的页 / SST 组织，以及由此决定的读写放大，见 存储与数据架构 · InnoDB 的 B+Tree 与 RocksDB 的 LSM-Tree。判据：问「O_DIRECT 怎么用、为什么 EINVAL、和 page cache 谁快」看本章；问「这个负载该选 B+Tree 还是 LSM、compaction 怎么调」看那一篇。

10.6 提交和收割的主循环模板

// 典型的 io_uring 事件循环 — 一边提交、一边收割 (batched)
void eventLoop(io_uring& ring) {
    while (!stop) {
        // 1) 填 SQE — 尽量一次填多个 (来自应用任务队列)
        while (auto task = taskQueue.try_pop()) {
            auto* sqe = io_uring_get_sqe(&ring);
            if (!sqe) break;                // SQ 满, 下轮再试
            task->prep(sqe);                  // prep_read / prep_write ...
            io_uring_sqe_set_data(sqe, task); // 回传指针当 user_data
        }

        // 2) 一次 syscall 提交 N 个, 并顺便 wait 至少 1 个完成
        io_uring_submit_and_wait(&ring, 1);

        // 3) 批量收割 CQE — 无系统调用, 直接读环形队列
        io_uring_cqe* cqe;
        unsigned head, count = 0;
        io_uring_for_each_cqe(&ring, head, cqe) {
            auto* task = static_cast<Task*>(io_uring_cqe_get_data(cqe));
            task->complete(cqe->res);      // 回调业务层
            ++count;
        }
        io_uring_cq_advance(&ring, count);  // 告诉内核这些 CQE 已消费
    }
}

15.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础用户态和内核态有什么区别？为什么需要这种隔离？

    这条边界是硬件划的，不是软件约定：x86 用 Ring 0 / Ring 3，ARM 用 EL1 / EL0。内核态可以执行特权指令（改 CR3 换页表、读写 I/O 端口、开关中断）并访问内核地址空间；用户态一旦尝试，CPU 直接抛 #GP，落到进程身上就是 SIGSEGV。

    跨越边界只能走受控入口：syscall 指令、中断、异常。内核在入口处切换栈（用户栈 → 内核栈）、保存寄存器、按调用号查 sys_call_table 分发，返回时再逆过来。这套仪式就是隔离的成本所在。

    三点必要性：① 保护内核完整性，应用的野指针写不坏调度器；② 进程之间隔离，页表由内核独占管理；③ 资源仲裁——只有内核有全局视角去记账 fd、内存与 CPU 时间。

    代价与工程应对：一次系统调用现在约 50–100 ns，Meltdown 之后开启 KPTI，进出内核要额外切一次页表，某些负载上开销翻倍。所以 I/O 优化的主线始终是减少陷入次数：stdio 的用户态缓冲、epoll_wait 一次返回多个事件、io_uring 批量提交与 SQPOLL 稳态零系统调用，以及 vDSO 把 clock_gettime 做成纯用户态读取——它们本质上都在回答同一个问题。

  2. 基础文件描述符是什么？它在内核中对应什么数据结构？

    fd 是进程级的小整数，本质是 task_struct->files->fdt->fd[] 这个指针数组的下标。往下是三层：

    • fd 数组（per-process）：只存指针，所以同一个 fd 号在不同进程之间毫无关系。
    • struct file（打开实例，system-wide）：持有读写位置 f_pos、打开标志 f_flags、操作表 f_op 和引用计数。
    • struct inode（文件本体元数据）+ dentry（路径名缓存）。

    几乎所有"奇怪"的 fd 语义都能从这张图直接推出来：

    • dup / dup2 让两个 fd 指向同一个 struct file，共享 offset；而两次 open 同一个文件得到两个 struct file，offset 各自独立。
    • fork 复制 fd 数组但只给 struct file 引用计数 +1，所以父子进程共享 offset——shell 里 (cmd1; cmd2) > f 能顺序追加而不是互相覆盖，靠的就是这个。
    • 管道两端与 socket 也都是 struct file，只是 f_op 不同，这才有了"一切皆文件"。

    生产陷阱：fd 号的分配规则是"当前最小可用"，close 之后马上会被复用。多线程程序里如果 A 线程 close 了一个 B 线程还在用的 fd，随后的 open / accept 很可能拿到同一个号，B 的读写就静默打到了别的文件上。这类 fd 复用竞态几乎无法从日志里看出来，正确做法是用引用计数或 RAII 句柄管住生命周期，而不是靠"记得别提前 close"。

    排查手段：ls -l /proc/<pid>/fd 看每个 fd 指向什么，cat /proc/<pid>/limits 看上限，lsof -p <pid> 定位泄漏。

  3. 基础stdio 的 fwrite 和系统调用 write 有什么区别？

    fwrite 是 libc 层的带缓冲流（FILE*），默认全缓冲（BUFSIZ，多为 4 KB），输出到终端时退化为行缓冲；write 是系统调用，直接陷入内核。

    性能差距来自陷入次数：一万次 4 字节的 write 就是一万次系统调用（约 1 ms 的纯开销），同样的写法走 fwrite 会攒满 4 KB 才发一次，系统调用降到十几次。

    但缓冲带来两个必须讲清的语义差异：

    • 丢数据的窗口不同：数据还在用户态缓冲里时，进程被 kill -9 就没了；write 返回意味着数据已进 page cache，进程崩溃不丢，只怕断电。
    • fork / exec 会出事：fork 前不 fflush，缓冲区被完整复制，父子各自 flush 一次 → 同一段输出出现两遍。这就是"为什么我的日志重复了"的标准答案。

    要真正落盘，两层都得推一遍，且顺序不能反：

    fflush(fp);              /* 用户态缓冲 -> page cache */
fdatasync(fileno(fp));   /* page cache -> 介质 */

    另外 stdio 每次调用都会对 FILE 加锁以保证线程安全，热路径可用 flockfile + fwrite_unlocked 自己管。而真正追求可控延迟的场景（日志库、数据库）通常干脆绕开 stdio——自己攒缓冲再用 writev 批量提交，因为 stdio 的刷盘时机你说不准。

  4. 基础write() 返回后数据在哪里？如何保证数据落盘？

    write 返回只代表数据被拷进了 page cache 的 dirty 页，等着回写。所以它保证"进程崩了不丢"，不保证"断电不丢"。

    回写由内核 writeback 线程按三个条件触发：脏页年龄超过 dirty_expire_centisecs（默认 30 s）、脏页占比超过 dirty_background_ratio（后台异步刷）、超过 dirty_ratio（前台同步刷——此时应用的 write 会被拖住去帮忙回写，表现为毫秒甚至秒级的突发长尾；很多"莫名的写延迟毛刺"就是它）。

    强制落盘的几个档位：

    • fsync(fd)：数据 + 元数据，最强也最慢。
    • fdatasync(fd)：只保证数据与"读取所必需的元数据"。文件大小没变时能省掉一次 inode 写，通常快 20%–50%，是日志追加型负载的默认选择。
    • O_SYNC / O_DSYNC：每次 write 隐含一次 sync，省了一次系统调用但失去了批量的机会。
    • sync_file_range()：只发起回写、不等元数据，适合"边写边把脏页推下去、最后统一 fsync"的流水线写法。

    还有一层常被忽略：设备自己的易失写缓存。fsync 会向块层下发 FLUSH/FUA 请求，但如果 RAID 卡开了 write-back 而 BBU / 电容失效，或者虚拟化层没把 flush 透传下去，fsync 返回成功依然可能丢数据。所以存储型服务上线前要做真实拔电测试，而不是相信文档。

    工程做法是 Group Commit：一批事务共用一次 fsync，把这个固定成本摊薄——MySQL 的 innodb_flush_log_at_trx_commit、PostgreSQL 的 commit_delay 都是同一个旋钮。最后一条红线：fsync 返回错误时不要重试，Linux 4.13 之前失败会清掉页上的 error 标记，第二次 fsync 会"成功"但数据早已丢失（著名的 fsyncgate）；正确响应是 fail-fast 并走恢复流程。

15.2 中级（区分熟练度）

  1. 中级select / poll / epoll 的区别？为什么 epoll 更快？

    三点关键差异：

    • 数据结构：select 用固定位图（FD_SETSIZE 编译期 1024），poll 用变长数组，epoll 在内核里维护一棵红黑树（注册集）加一条就绪链表。
    • 拷贝：select / poll 每次调用都要把整个 fd 集合拷进内核再拷回来；epoll 的注册（epoll_ctl）只做一次，之后 epoll_wait 只带回就绪的那几个事件。
    • 复杂度：select / poll 是"每次挨个问一遍"，内核 O(n) 遍历；epoll 是"注册一次 + 内核回调"——数据到达时协议栈调 ep_poll_callback 把 fd 挂上就绪链表，epoll_wait 直接摘链表，代价只和活跃连接数相关。

    顺手纠一个流传很广的说法：epoll 并没有用 mmap 和用户态共享就绪队列，epoll_wait 依然要 copy_to_user。它省掉的是"每次把全部 fd 重新交代一遍"这件事。这一点面试官很爱追问。

    所以 epoll 的优势本质上取决于 总连接数 / 活跃连接数 这个比值：10 万连接里只有几百个活跃（典型长连接推送）时它是碾压级的；如果 1000 个 fd 每轮全都活跃，epoll 甚至可能因为多一次 epoll_ctl 和链表维护而略慢于 poll。

    select 剩下的用处：fd 极少且短命、需要跨平台（含 Windows）、或需要 timeval 的微秒级超时。但要记住它的红线——fd 号 > 1024 时 FD_SET 会直接越界写栈，这是真实出现过的漏洞类别，不是理论风险。

  2. 中级epoll 的 LT 和 ET 模式有什么区别？各自适用什么场景？

    LT（水平触发）关注的是"状态"：只要缓冲区还有数据可读，每次 epoll_wait 都会继续报。ET（边缘触发）关注的是"变化"：只在不可读 → 可读的跳变时报一次。

    ET 有两条硬性配套：fd 必须是非阻塞的；必须循环 read 直到返回 EAGAIN，否则剩下的数据再也不会被通知，连接就静默僵死。写方向同理，EPOLLOUT 在 ET 下只在"不可写 → 可写"时来一次。

    但"读到 EAGAIN 为止"又引入公平性问题：一个持续灌数据的连接会把线程霸占住，饿死同一个 epoll 上的其他连接。生产写法是给单次读取加一个字节数或轮次上限，没读完就把这个 fd 记进自己的"待续处理"队列下一轮继续——相当于在用户态补一层调度。

    LT 也有自己的坑：如果一直关注 EPOLLOUT，在没有待发数据时会被反复唤醒变成 busy loop，所以 LT 下的 EPOLLOUT 必须按"发送缓冲非空"动态开关。

    选择：ET 的收益是更少的唤醒与系统调用，Nginx 默认 ET；LT 的编程容错高得多，Redis、libevent 默认 LT，绝大多数业务用 LT 完全够。多线程共享同一个 epfd 时两者都要处理惊群——LT 下更严重，需要 EPOLLEXCLUSIVE 或 EPOLLONESHOT；更干净的做法是每线程一个 epfd 配 SO_REUSEPORT，从根上避免多个线程盯同一个 fd。

  3. 中级什么是零拷贝？sendfile 和 splice 的区别？

    零拷贝指减少或消除 CPU 参与的数据搬运（DMA 那两次躲不掉）。传统 read + send 发一个文件要 4 次拷贝、4 次用户/内核切换：磁盘 →（DMA）page cache →（CPU）用户 buffer →（CPU）socket buffer →（DMA）网卡。

    • sendfile(out_fd, in_fd, ...)：数据不出内核，page cache 直接喂给 socket，只剩 1 次内核内 CPU 拷贝；网卡支持 SG-DMA + checksum offload 时连这次也省掉，只传描述符。限制是出端必须是 socket，而且用户态碰不到数据——所以做不了压缩和 TLS，除非用 kTLS 把加密下沉到内核或网卡。
    • splice()：借一个 pipe 的内核缓冲做中转，移动的是 page 引用而不是内容，两端可以是任意支持 splice 的 fd（socket↔socket、file↔socket）。代价是必须额外准备 pipe、代码更绕。代理与转发类应用用它，正因为 sendfile 的 in_fd 不能是 socket。

    同族还有：mmap + write（省一次拷贝但引入缺页开销）、copy_file_range()（文件到文件，btrfs / XFS 上还能退化成 reflink，连数据都不动）、以及 MSG_ZEROCOPY 与 io_uring 的 SEND_ZC（用户 buffer 直接给网卡 DMA，但完成通知是异步的，buffer 生命周期得自己扛）。

    取舍必须说清：零拷贝省的是 CPU 周期和内存带宽，不省磁盘与网络时间。小文件下它常常不划算——一次 sendfile 的固定开销比省下的拷贝还多，还丢掉了在用户态合并小包的机会。更根本的限制是"数据不经过用户态"等价于"不能改数据"，所以 Kafka 能大量用 sendfile，前提正是消息在磁盘上就已经是要发出去的格式。

  4. 中级mmap 和 read 读文件哪个更快？

    没有普适答案，因为两者的开销结构不同：read 付的是系统调用 + 一次拷贝，可以一次搬 1 MB 把成本摊薄；mmap 付的是缺页异常，粒度固定在页（4 KB），首次访问每页都要陷一次内核（minor fault 约 1 μs 量级）。

    所以顺序读大文件时 read / pread 常常反而更快，除非用 MAP_POPULATE 预先填页表、或 madvise(MADV_SEQUENTIAL | MADV_WILLNEED) 让内核激进预读。

    mmap 真正的赢点在三处：随机访问（免掉 offset 计算与整块拷贝）、多进程共享同一份 page cache（省内存也省拷贝）、以及需要指针语义的数据结构——数据库的 B+Tree、索引文件可以直接在映射区上遍历，不必先读进 buffer 再解析。

    陷阱清单：

    • 文件被 truncate 后访问已映射区域会收到 SIGBUS（而 read 只是返回 0）。映射不可信文件必须装 handler，否则一次误操作就是进程崩溃。
    • 写映射的落盘要 msync，且脏页回写时机由内核决定，比 write + fsync 难控。
    • 映射面积大会推高页表与 TLB 压力，可用大页缓解；32 位地址空间根本放不下大文件。
    • 低延迟场景要慎用：一次 major fault（真去读盘）就是不可预测的毫秒级停顿，而它恰好落在 P99 上。

    一句话结论：一次性流式处理选 read，长期驻留 + 随机访问 + 跨进程共享选 mmap，延迟敏感路径优先 read / Direct I/O 换确定性。

  5. 中级一次磁盘写入，从 write() 到数据真正落盘经过哪些层？

    整条链路：

    用户 write()
  -> glibc        走 stdio 时先进用户态缓冲
  -> 系统调用      陷入内核
  -> VFS          vfs_write / 通用写入路径
  -> 文件系统      ext4_file_write_iter（分配块、写 journal）
  -> Page Cache   写入页并标记 dirty   <-- write() 到这里就返回了
  -> writeback    内核线程按阈值 / 年龄触发回写
  -> bio 层       构造 bio，按段映射到设备
  -> blk-mq       每 CPU 软队列 -> 硬件队列
  -> I/O 调度器    mq-deadline / kyber / none
  -> 设备驱动      NVMe 提交到 SQ 并敲门铃
  -> 介质         DMA 落盘，完成后中断或轮询回收

    两个关键理解：write 的返回点在 page cache，后半段完全是异步的；fsync 做的事就是把后半段同步等完，还要额外下发一次 FLUSH 让设备把自己的易失缓存也刷掉。所以 fsync 延迟 = 排队 + 介质写入 + 缓存刷新，NVMe 上几十到几百微秒，SATA SSD 或带 journal 的文件系统上可以到毫秒。

    O_DIRECT 只绕过 page cache，并不绕过块层——依然要过 blk-mq 与调度器，而且要求 buffer 地址、偏移、长度都按逻辑块大小对齐，否则直接 EINVAL。

    分层定位瓶颈的工具也是分层的：iostat -x 1 看设备侧 await / %util；biolatency（bcc）看块层延迟直方图；blktrace + blkparse 看单个请求在各阶段的时间戳；bpftrace 挂 block:block_rq_issue / block_rq_complete 做自定义统计。如果块层很快而应用觉得慢，八成卡在 writeback 限流或 journal 上，而不是设备本身。

15.3 高级（体现深度）

  1. 高级io_uring 相比 epoll 有什么优势？为什么说它是"真正的"异步 I/O？

    范式不同：epoll 是 Reactor / 就绪通知——内核告诉你"可以读了"，读还是你自己去读，而这一步本身可能阻塞；io_uring 是 Proactor / 完成通知——你把"读这段"交给内核，内核干完把结果写回来。

    这也解释了 epoll 对普通文件为什么没用：常规文件的 poll 实现永远返回可读可写，真正的阻塞发生在 read 内部。所以 epoll 时代的文件 I/O 只能丢给线程池假装异步，而 io_uring 是第一个把文件 I/O 真正异步化的通用接口。

    机制：用户与内核共享两个环形队列（SQ / CQ），靠内存屏障同步。填好 N 个 SQE 后一次 io_uring_enter 提交，把"每次 I/O 一次系统调用"变成"一批 I/O 一次系统调用"；开 SQPOLL 后内核线程主动轮询 SQ，稳态下连这一次都没有；IORING_SETUP_IOPOLL 对 NVMe 走轮询完成，把中断开销也去掉。再加上注册 fd / buffer 省掉每次的引用查找与映射校验、链式 SQE 直接表达依赖（读完自动写），高 IOPS 场景相比 libaio 能有数倍差距。

    生产视角的代价比优势更值得说：

    • 内核版本敏感：5.1 起有、5.6+ 才好用、6.x 才算成熟，可用 op 与标志随版本变。代码里必须做能力探测（io_uring_probe）并保留 epoll 退路。
    • 安全面积大：它把大量内核路径暴露给了一个新的提交通道，CVE 密集。Google 在 ChromeOS / Android 上直接禁用，Docker 默认 seccomp 也拦。上线前先确认宿主策略，否则写完跑不起来。
    • 编程模型难：buffer 必须活到 CQE 到达，取消（ASYNC_CANCEL）与超时语义复杂，错误码散在 CQE 的 res 字段里而不是 errno。
    • 低队列深度收益有限：它赢在批量与深队列，一次只发一个请求时和 epoll 差不多。

    结论：网络 I/O 现阶段 epoll 仍是更可控的默认选择；存储密集型系统（数据库、对象存储、日志引擎）才是 io_uring 收益最大、也最值得吃掉这些复杂度的场景。

  2. 高级如何实现一个高性能的日志库？

    核心原则一句话：前台线程只做"捕获参数 + 入队"，格式化和 I/O 全部后移。前台每多做一件事，都会按调用频率乘回到业务延迟上。

    • 格式化后移：用 std::format / fmtlib 而不是 iostream，日志点只把参数按值拷进 buffer。NanoLog 更激进——编译期把格式串抽成静态字典，运行时只写二进制参数，落盘后离线还原，前台开销压到 10 ns 以内。
    • 队列选型：per-thread SPSC 环形缓冲 + 后台线程轮询收集，比一个全局 MPSC 队列少一半争用；每个 ring 的 head / tail 要 alignas(64) 分开，否则 false sharing 会把无锁队列的收益吃光。
    • 双缓冲与批量刷盘：前台写 A，后台 flush B，攒到 N 条或 T 毫秒触发一次 writev（多条一次系统调用）。要崩溃安全就得 fdatasync，但那是毫秒级——所以必须给调用方显式选择：默认异步（崩溃丢最后几毫秒）vs 关键日志同步。
    • 时间戳：clock_gettime 即便走 vDSO 也要 20 ns 上下，热路径用 rdtsc 记原始计数，后台再按校准过的频率换算成墙钟。

    三个真正会在生产上咬人的问题：

    队列满
    阻塞前台等于让日志拖慢业务，违背整个设计初衷；丢弃则必须暴露丢弃计数指标，否则排障时你会以为"那一刻什么都没发生"。实际做法是按级别分流：error 宁可阻塞，debug 直接丢。
    page cache 污染
    日志是纯顺序写且几乎不再读，却会挤占 page cache、驱逐业务数据。刷盘后用 sync_file_range 把脏页推下去，再 posix_fadvise(POSIX_FADV_DONTNEED) 主动释放。
    轮转与多写者
    文件轮转的 rename / open 绝不能在前台线程做（一次 open 可能几十微秒）；多进程写同一文件要靠 O_APPEND 的原子性，且单条长度不越过块边界才安全。

    必备的自我观测：前台入队延迟直方图、队列水位、丢弃计数。没有这三个指标的日志库，出问题时你没法证明它自己不是凶手。参考实现：spdlog（async 模式，易用）、NanoLog / Quill（低延迟档）、Boost.Log（功能全但重）。

  3. 高级TCP 连接 accept 后，如何设计线程模型处理请求？

    四种主流模型，按并发能力递增：

    • 单 Reactor 单线程：Redis 风格。无锁、无同步、行为完全可预测，前提是业务 CPU 极轻且没有任何阻塞调用。
    • 单 Reactor + worker 线程池：I/O 线程只做读写与协议解析，业务丢线程池。适合业务重、连接数中等。
    • 主从 Reactor：muduo / Netty 风格。主 Reactor 只 accept，把连接按轮询或最小负载分给 sub-Reactor 池，每个 sub 独占一个 epfd。这是通用场景的默认答案。
    • 多进程各自 listen：Nginx 风格，SO_REUSEPORT 让内核按四元组哈希直接分发，进程之间零共享，故障隔离最好。

    选型的三个判据：单连接内是否要求严格顺序处理？业务里有没有阻塞调用（数据库、磁盘、下游 RPC）？跨连接共享状态多不多（多则倾向线程而非进程）？

    比模型选择更容易翻车的是这几个细节：

    • 不要在 I/O 线程里阻塞。一个慢查询就会卡住同一个 sub-Reactor 上的几千个连接，症状是"一部分用户全挂、另一部分完全正常"，极具误导性。
    • 连接必须有唯一 owner 线程。fd 被两个线程同时 epoll 或读写，任何锁都救不了顺序问题；跨线程要发数据就投递任务回 owner 线程执行。
    • SO_REUSEPORT 是哈希不是负载均衡。长连接场景下一旦分布不均就会长期不均（连接不会自己迁移），需要每 worker 连接数上限 + 主动拒绝，或定期重建 listen fd。
    • 惊群：多线程共享 listen fd 时用 EPOLLEXCLUSIVE，或干脆单线程 accept；Nginx 的 accept_mutex 是同一问题的老式解法。

    推荐组合：主从 Reactor + 每 sub-Reactor 绑核 + 网卡中断亲和分散（RSS / RPS）+ 重业务走独立线程池并用无锁队列回传结果。

  4. 高级设计一个能处理 100 万并发长连接的服务器，怎么做？

    这题的关键不是背参数，而是先算账，再定架构。

    内存是第一约束：每条连接内核侧的 socket + tcp_sock 约 3–4 KB，加上收发缓冲（tcp_rmem / tcp_wmem 会自动调节，但最小值也得算进去），100 万连接光内核就要 4–10 GB。用户态必须把 per-connection 状态压到几百字节级——"每连接预分配 64 KB 读写 buffer"是最常见的 OOM 原因，正确做法是读缓冲共享或按需分配、写缓冲只在有积压时才存在。

    架构：SO_REUSEPORT 多进程（或多线程）各自 epoll，worker 绑核，网卡多队列中断分散到对应核，避免跨核唤醒与 cacheline 弹跳。协议层用固定长度头携带 body 长度，一次 read 就能拿完整包；开 TCP_NODELAY，但推送类业务要在应用层自己合并小包，否则省下的延迟被系统调用和小包开销吃掉。

    要调的旋钮（大致按被打爆的先后顺序）：

    ulimit -n 1048576              # 进程 fd 上限
fs.nr_open / fs.file-max       # 系统 fd 上限
net.core.somaxconn             # accept 队列
net.ipv4.tcp_max_syn_backlog   # 半连接队列
net.ipv4.tcp_mem               # TCP 内存页数上限（最容易被忽略）
net.netfilter.nf_conntrack_max # 有 iptables 时通常是它先爆

    心跳与超时才是真正的难点：100 万连接不能一人一个定时器。用时间轮或分桶（把连接散到 60 个桶，每秒只扫一个桶），否则定时器管理本身就成了瓶颈。同时要区分"TCP 还连着"和"对端还活着"——只有应用层心跳能发现半开连接，而 tcp_keepalive 默认 2 小时才探测，等不起。

    观测：ss -s 看连接状态分布，nstat 的 ListenOverflows / ListenDrops 直接指认 accept 队列打满，每核 softirq 占比看中断是否倾斜，再加 epoll_wait 单次返回事件数的分布判断有没有事件风暴。

    最后一个实战提醒：压测端往往先挂。单机主动发起连接受本地端口数（约 28 K）限制，需要多 IP、IP_BIND_ADDRESS_NO_PORT 或多台压测机——很多"服务端到不了 100 万"的结论其实是客户端的锅。
