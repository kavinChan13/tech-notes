1.4 fork() 的 Copy-on-Write 机制

Copy-on-Write：fork 后共享只读物理页，某方真写入才复制该页。fork 本身很快，代价摊到后续每一次首写。

1.5 单核是不是只有一个进程？

不是。核、进程、线程不是一对一：

  • 核 = 硬件执行单元（能同时取指/执行的物理或逻辑 CPU）。
  • 进程 = 资源容器（地址空间、fd、信号量……）。
  • 线程 = 调度实体（内核眼里真正被排上某个核的那条执行流）。

单核同一时刻通常只有一条指令流，靠时间片并发；多核才真并行。进程数可以远大于核数；某一瞬间 Running 大约等于逻辑核数。

单核多核
同时刻指令流通常 1 条= 逻辑核数
争的资源这一颗核 + DRAMDRAM / 共享 L3
主要「税」本核 L1 / TLB 被冲刷带宽争用 + MESI

调度细节见 进程调度器。单核照样会有数据竞争——见 内存模型。

4.5 mmap 实战

文件映射：建好即可 close(fd)，按指针读，用完 munmap。匿名两种见下表。

#include <sys/mman.h>
#include <fcntl.h>
#include <sys/stat.h>
#include <unistd.h>

int fd = open("large_file.dat", O_RDONLY);
struct stat sb; fstat(fd, &sb);
void* p = mmap(nullptr, sb.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
close(fd);                              // 映射建立后即可关 fd
auto* data = static_cast<const char*>(p);
// data[0] … data[sb.st_size-1] 像内存一样读
munmap(p, sb.st_size);

7.1 用户态 vs 内核态切换代价

syscall 比函数调用贵两个数量级，但比进程切换便宜。账面 50–100 ns，真正的税往往是 KPTI 换 CR3 和 cache 被内核路径挤冷。同机网络往返大约 50 μs，所以“再加一次 syscall”通常比“再打一趟网”便宜。

切换类型量级主要开销
函数调用~1 ns栈帧
用户/内核~50–100 nssyscall、权限、KPTI
线程 / 进程~1–5 μs / ~3–10 μs进程额外换页表

7.2 同步原语全景对比

原语场景阻塞方式开销C++ API
Atomic无锁计数、标志位不阻塞（CAS 重试）最低（< 10ns）std::atomic<T>
Spinlock极短临界区、中断环境忙等（占满 CPU）低（但空转耗电）std::atomic_flag 自行实现
Mutex通用互斥让出 CPU，内核调度中（~100ns-1μs）std::mutex
RWLock读多写少读共享、写互斥中高std::shared_mutex (C++17)
Condvar生产者/消费者等待阻塞直到被唤醒中std::condition_variable
Semaphore资源计数（连接池）阻塞或超时中std::counting_semaphore (C++20)
Barrier/Latch批量等待点阻塞到所有就绪中std::barrier/latch (C++20)
Futex无竞争时零系统调用有竞争才进内核极低Linux 内部实现，mutex 基础

选：单变量 → atomic；<1μs 且 CPU 闲 → spinlock；其余 mutex；读多写少 → shared_mutex。无竞争时 futex 不进内核，这是 mutex 快的原因。

7.3 C++11 内存模型 & Memory Order 高级难点

CPU 会乱序、重排。C++11 内存模型管的是可见性与顺序，不是“原子就不会坏”。单例发布：acquire 读指针，确认空后再在 mutex 里 new，release 写回。

Memory Order语义性能典型用法
memory_order_relaxed无任何同步/顺序约束，仅原子性最快统计计数器
memory_order_consume数据依赖顺序（实践中少用，退化为 acquire）—避免使用
memory_order_acquireload：后续读写不能提前到此 load 之前快读取锁、指针
memory_order_releasestore：之前的读写不能延后到此 store 之后快写入锁、发布对象
memory_order_acq_rel读-改-写操作同时具备 acquire + release中CAS 操作
memory_order_seq_cst全局顺序一致（默认）最慢简单且对

默认 seq_cst。只有 profiler 指着这行、且你能写出 happens-before 时才放宽。

7.7 高频面试题 Q&A

12 道题按难度分三档，覆盖本章的进程模型、同步原语、内存序、cache 行为与信号处理。建议先合上答案自己讲一遍，再展开对照——面试考的是能不能说清楚机制和取舍，不是能不能背出结论。

7.7.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础fork() 之后 malloc 的内存是否被复制？copy-on-write 是怎么做到的？

    不复制内容，只复制页表。fork 采用写时复制（COW）：子进程初始与父进程共享全部物理页，双方的页表项都被内核改成只读，同时物理页的引用计数加一。任一方写入时触发写保护缺页异常，内核在异常处理里分配新页、拷贝内容、把发起写的那一方的 PTE 改回可写。

    所以 fork 本身很快（O(页表大小)，不是 O(内存大小)），但代价被推迟并分散到后续的每一次首写上。这带来两个真实的生产问题：

    • 延迟尖刺：Redis 做 RDB/AOF 重写时 fork 出子进程，如果主进程写入压力大，大量页在短时间内被 COW 拆分，既产生缺页开销，又让实际内存占用逼近 2 倍（最坏情况）。
    • fork 本身也不是免费的：几十 GB 的进程页表可以有几百 MB，复制它就要几十到几百毫秒。透明大页（THP）会让这个问题更糟——一次 COW 要拷 2 MB 而不是 4 KB，所以数据库类服务通常建议关掉 THP。

    另外要说清一个常见误区：多线程程序 fork 之后只有调用 fork 的那个线程存在于子进程。别的线程持有的锁会永远保持在"已加锁"状态，子进程里再调 malloc 就可能直接死锁。这就是 POSIX 只允许在 fork 与 exec 之间调用 async-signal-safe 函数的原因，也是 pthread_atfork() 存在的理由。

  2. 基础线程栈多大？能无限创建线程吗？

    Linux 默认线程栈 8 MB（ulimit -s 查看）。但要注意这 8 MB 是虚拟地址空间的预留，不是立刻占用的物理内存——栈是按页惰性分配的，只碰到的页才会真正占 RSS。所以"1000 个线程 = 8 GB 内存"这个说法在 64 位下是错的，真实物理开销通常是每线程几十 KB。

    限制来自三处：

    • 虚拟地址空间：32 位进程只有 3 GB 用户空间，8 MB 一个栈 ⇒ 上限约 380 个线程。64 位基本不受此限。
    • 内核对象：每个线程有 task_struct + 内核栈（16 KB），受 /proc/sys/kernel/threads-max 与 cgroup pids.max 约束。
    • 调度成本：线程多了，可运行队列变长、上下文切换与 cache 抖动加剧，吞吐反而下降。

    工程做法：用 pthread_attr_setstacksize() 把栈调到 256 KB–1 MB（前提是没有深递归和大的栈上数组）；I/O 密集场景改用固定大小线程池 + 事件循环，或用 C++20 协程（每个协程帧只有几十到几百字节），把并发数和线程数解耦。

  3. 基础volatile 能用于多线程同步吗？

    不能。 C++ 的 volatile 只对编译器说"这个变量的读写不能被优化掉、不能被缓存进寄存器、不能被合并"，它不提供：

    • 原子性：v++ 依然是 load-modify-store 三步，两个线程照样丢更新；
    • 顺序性：不会生成任何内存屏障，CPU 仍可乱序，别的线程看到的写入顺序可能和源码不同；
    • 可见性保证：它不 flush cache（cache 一致性本来就由 MESI 硬件保证），但也不阻止写缓冲区里的写延迟到达。

    多线程同步必须用 std::atomic 或 mutex。volatile 在 C++ 里只剩两个正当用途：① 内存映射 I/O（读写硬件寄存器，每次访问都必须真的发生）；② 信号处理函数与主流程共享的标志（配合 volatile sig_atomic_t，或更好的 std::atomic<bool> 且 is_lock_free()）。

    常见混淆：Java / C# 的 volatile 带 acquire-release 语义，约等于 C++ 的 std::atomic；跨语言经验直接套过来必错。x86 上写 volatile "看起来能跑"是因为 x86 的内存模型本身很强（TSO），换到 ARM / POWER 上立刻暴露。

  4. 基础死锁的四个必要条件是什么？工程上怎么预防？

    Coffman 四条件（必须同时成立）：① 互斥；② 持有并等待；③ 不可剥夺；④ 循环等待。打破任意一条即可，但工程上真正可操作的只有后两条。

    • 统一加锁顺序（破坏循环等待，最实用）：全局约定一个偏序，比如按锁对象地址升序加锁。代码评审时"这个函数会同时持有哪几把锁、顺序是什么"应该是可回答的。
    • std::scoped_lock(m1, m2)（C++17）/ std::lock()：内部用 try-and-back-off 算法一次性拿多把锁，顺序无关也不会死锁。
    • try_lock + 超时回退（破坏不可剥夺）：拿不到就释放已持有的锁、退避重试。要注意活锁，退避需要随机化。
    • 减少同时持锁数量：能用无锁结构、能把临界区拆小、能用消息传递代替共享状态，就不会有死锁。
    • RAII（lock_guard / unique_lock / scoped_lock）：保证异常路径也释放，避免"死锁"其实是"忘了解锁"。

    怎么发现：ThreadSanitizer（-fsanitize=thread）能报出锁顺序反转（lock-order-inversion），即使这次没真的死锁；线上已经卡死时用 gdb -p <pid> 加 thread apply all bt，看哪几个线程停在 __lll_lock_wait 上，互相等谁一目了然。pthread_mutex 还可以设 PTHREAD_MUTEX_ERRORCHECK 在自我重入时直接报错。

7.7.2 中级（区分熟练度）

  1. 中级为什么 malloc 不总是向内核要内存？tcmalloc / jemalloc 的优势在哪？

    因为系统调用太贵（~50–100 ns，还会污染 cache），而典型程序每秒可能分配上百万次小对象。所以 allocator 的基本策略是批发-零售：用 brk（堆顶推进）或 mmap（大块，glibc 默认 ≥128 KB 走 mmap）一次向内核要一大片，然后在用户态切成小块分配；free 时也不还给内核，挂进 free list / bin 等着复用。

    glibc 的 ptmalloc 用多 arena 缓解锁竞争（arena 数 ≈ 8×核数），但同一 arena 内仍是一把大锁，线程多时争用明显。

    • tcmalloc（Google）：每线程一个 thread-local cache，小对象分配/释放在无锁的本地链表上完成，只有 cache 空了或满了才去中央堆搬运。高并发小对象场景比 ptmalloc 快 2–5 倍。
    • jemalloc（Facebook）：按 size class 精细分桶 + arena 绑定 + 主动 decay 归还，碎片率明显更低，长时间运行的大内存服务（MongoDB、Redis、Rust 运行时）更青睐它。

    选型不是"谁更快"，而是看瓶颈：分配频率高 → tcmalloc；常驻内存大、怕碎片、怕 RSS 只涨不跌 → jemalloc；单线程或分配很少 → 换了也没用。

    验证成本很低，不用改代码：

    LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libtcmalloc_minimal.so ./prog
# jemalloc 还能直接吐出统计
MALLOC_CONF=stats_print:true ./prog

    另一个常被忽略的点："内存没还给操作系统"不等于泄漏。RSS 高位不降往往只是 allocator 在缓存；jemalloc 的 dirty_decay_ms / glibc 的 malloc_trim() 可以主动归还。判断真泄漏要看是否持续单调增长，用 heaptrack / ASan 抓分配栈。

  2. 中级为什么进程切换比线程切换慢？慢的到底是哪一部分？

    同进程内的线程切换只需保存/恢复通用寄存器、栈指针、PC、FPU/SIMD 状态和少量 TLS 指针，地址空间不变。

    进程切换额外要做：

    • 切换页表（写 CR3） → 这是大头。没有 PCID 时整个 TLB 被清空，切回来后每一次内存访问都要重走页表（4 级页表 = 最多 4 次额外访存）。现代 x86 有 PCID/ASID 可以给不同地址空间打标签、避免全刷，但 Meltdown 之后的 KPTI 又把内核/用户页表拆成两份，一次系统调用就要换一次 CR3，代价被重新拉高。
    • 切换 mm_struct、文件描述符表、信号处理表等资源指针。

    量级：线程切换 1–5 μs，进程切换 3–10 μs。但真正的成本往往不在这两个数字里——是切换后的 cache 冷却：L1/L2/LLC 里的热数据被新任务挤掉，切回来要重新预热，工作集大的服务可以损失几十微秒。所以优化方向从来不是"让切换更快"，而是让切换更少：绑核减少迁移、用线程池代替频繁创建、用事件循环代替一连接一线程、用批量 I/O（epoll / io_uring）减少阻塞点。

    观测：perf stat -e context-switches,cpu-migrations 看总量，pidstat -w 1 区分自愿（cswch/s，等锁等 I/O）与非自愿（nvcswch/s，被抢占）切换——前者说明阻塞太多，后者说明 CPU 超卖。

  3. 中级协程和线程的本质区别？C++20 coroutine 是怎么实现的？

    线程：内核调度实体，抢占式，栈固定（默认 8 MB 虚拟空间），切换要陷入内核。协程：用户态调度，协作式（只在显式挂起点让出），切换是普通的函数返回 + 跳转，纳秒级。

    C++20 的 co_await / co_yield / co_return 是无栈协程：编译器把函数体重写成一个状态机，把跨挂起点存活的局部变量、参数、挂起点编号打包进一个 coroutine frame（通常堆分配，编译器可做 HALO 优化省掉）。挂起时只是保存"下一步从哪个 case 继续"，恢复时调 frame.resume()。所以它不需要独立的栈，一个协程可能只占几十到几百字节。

    代价与边界要讲清：

    • 无栈的限制：只能在协程函数体内直接 co_await，不能在被它调用的普通函数深处挂起（有栈协程如 boost.context、Go 的 goroutine 可以）。
    • 协作式的风险：一个不让出的协程会独占整个载体线程，CPU 密集任务必须自己切出去或丢给线程池。
    • C++20 只给了语言机制，没给调度器：promise_type、awaiter 都得自己写或用库（folly::coro、cppcoro、Asio、Seastar）。

    适用判断：协程赢在高并发 I/O 等待（几十万连接各自阻塞在网络上），不赢在计算。计算密集仍然是"线程数 ≈ 核数"最优。

  4. 中级什么是 false sharing？怎么确认它真的发生了，又怎么消除？

    CPU 的缓存一致性（MESI）以 cache line（x86_64 通常 64 字节）为单位。两个线程各自只写自己的变量，但这两个变量落在同一条 cache line 上时，每一次写都会让对方核上的那条 line 失效，数据在核间来回弹（cache line ping-pong）。逻辑上没有共享，硬件上却在疯狂同步——这就是伪共享，典型代价是 10–100 倍的性能塌陷。

    怎么确认（别靠猜，伪共享和普通的内存瓶颈从火焰图上看不出区别）：

    perf c2c record -- ./prog
perf c2c report          # 直接列出发生 HITM 的 cache line 及命中它的源码行
# 粗筛也可以看这个事件是否异常高
perf stat -e cache-misses,LLC-load-misses,mem_load_l3_hit_retired.xsnp_hitm ./prog

    perf c2c 的 HITM（load 命中了另一个核处于 Modified 状态的 line）就是伪共享的直接证据。

    怎么消除：

    • 给热点字段做 padding / 对齐：alignas(std::hardware_destructive_interference_size)（x86_64 = 64，Apple M1 = 128）。
    • 改数据布局：把"每线程一份的计数器数组"改成每元素独占一条 line，或干脆改成 thread_local 累加、最后再汇总——这一招通常比 padding 更好，因为它连一致性流量都没有。
    • 只读数据和频繁写的数据分开放：把 hot 的 std::atomic 计数器从只读配置结构体里搬出去。

    反过来也要注意别过度 padding：每个计数器占满 64 字节会让数组撑大 8 倍，反而恶化 cache 命中率和预取效果。只对被多个核并发写的字段做隔离。

7.7.3 高级（体现深度）

  1. 高级relaxed / acquire-release / seq_cst 各自保证了什么？什么时候敢用 relaxed？

    先分清两件事：原子性（这次读写不会被撕裂）所有 memory order 都保证；顺序性（它与周围其它内存操作的相对顺序）才是 memory order 在管的东西。

    • relaxed：只有原子性。编译器和 CPU 可以随意把它与前后的访存重排。同一个原子变量上的修改顺序（modification order）仍然全局一致，但你无法用它来"发布"别的数据。
    • acquire（load）/ release（store）：构成同步-于关系。若线程 B 的 acquire-load 读到了线程 A 的 release-store 写的值，那么 A 在 release 之前的所有写，对 B 在 acquire 之后都可见。这正是"发布一个构造好的对象"所需要的最小保证。
    • seq_cst：在 acquire-release 之上，额外要求所有 seq_cst 操作存在一个全局单一顺序，且所有线程看到的这个顺序一致。它能解决 acq-rel 解决不了的经典反例——两个线程各写一个标志再读对方的标志，acq-rel 下可能双方都读到旧值（Dekker 模式），seq_cst 不会。

    代价：x86 上 acquire-load / release-store 几乎免费（TSO 天然满足，只需编译屏障），但 seq_cst 的 store 要 xchg 或 mfence，是真实开销。ARM / POWER 是弱内存模型，acquire/release 会生成 ldar/stlr，seq_cst 更贵。这就是为什么"x86 上测不出差别"不能作为放宽的依据。

    什么时候敢用 relaxed：只有当这个原子变量的值不用于给其它数据排序时。最典型的两个安全场景：① 纯统计计数器（counter.fetch_add(1, relaxed)，只在最后读一次汇总）；② shared_ptr 式引用计数的增加（增加时对象必然还活着，无需同步），但减少必须是 acq_rel——最后一个减到 0 的线程要能看到其它线程之前的所有写，才能安全析构。

    工程建议照页面正文说的：默认写 seq_cst，只在 profiler 指着这行说它是热点、且你能写出"谁 happens-before 谁"的论证时才放宽，并用 TSan + 在真实的 ARM 机器上验证。放错的后果是只在高负载、特定机型上偶发的数据损坏，比崩溃难查得多。

  2. 高级系统调用为什么慢？除了 syscall 指令本身还有什么代价？如何减少？

    一次系统调用的裸开销约 50–100 ns，但这只是账面数字，真实成本分四层：

    • 特权级切换本身：syscall 指令切 ring、换栈（用户栈 → 内核栈）、保存恢复寄存器。
    • KPTI（Meltdown 缓解）：内核与用户使用两套页表，进出内核各要写一次 CR3。没有 PCID 的老 CPU 上等于每次系统调用都刷 TLB，开销可以翻好几倍——这就是 2018 年之后很多 I/O 密集服务性能掉 10–30% 的原因。
    • Spectre 缓解：retpoline、IBPB/STIBP 等会让间接跳转与分支预测器失效，进一步加码。
    • cache / 分支预测器污染：内核代码路径把你的 L1i、L1d、BTB 挤掉，返回用户态后前几百条指令都跑在冷 cache 上。这一项最难量化，也常常最大。

    减少办法，按收益排序：

    • 批量化：一次调用干多件事。epoll_wait 一次返回一批事件、writev/sendmmsg 合并多段数据、io_uring 把提交队列和完成队列放在用户-内核共享内存里，可以做到"提交一千个 I/O，零次或一次系统调用"。
    • vDSO：clock_gettime、gettimeofday 这类纯读内核数据的调用被映射到用户空间执行，根本不进内核。高频打时间戳时务必确认走的是 vDSO（strace 里看不到就是走了）。
    • 共享内存：绕过 copy_to_user，进程间大块数据传递用 mmap 共享而不是 pipe/socket。
    • 内核旁路：极端低延迟场景用 DPDK / SPDK / AF_XDP，把网卡或 NVMe 直接映射到用户态轮询，代价是丢掉内核提供的一切（协议栈、隔离、可观测性）并且要烧掉一整个核。

    诊断入口：strace -c -f ./prog 看哪个 syscall 次数最多，perf stat -e raw_syscalls:sys_enter 看总频率。每秒几十万次系统调用就该考虑批量化了。

  3. 高级为什么信号处理函数里不能调 malloc / printf？正确的工程做法是什么？

    因为信号是异步打断：它可能恰好打断本线程正在执行的 malloc，此时 allocator 的内部锁已被本线程持有、free list 处于中间状态。handler 里再调 malloc 就会去拿同一把（非递归的）锁 → 自己和自己死锁，或者更糟，看到半更新的链表把堆搞坏。printf 同理（stdio 有自己的锁和缓冲区），std::mutex、STL 容器、抛异常也都是禁区。

    POSIX 给出的白名单是 async-signal-safe 函数（man 7 signal-safety）：write、_exit、kill、sigaction、大多数直接的 syscall 包装，以及对 volatile sig_atomic_t 的读写。注意是 write 不是 printf，是 _exit 不是 exit（后者会跑 atexit handler 和刷 stdio 缓冲）。

    三种正确做法：

    • self-pipe trick：handler 里只做一件事——write(pipefd[1], "x", 1)；真正的逻辑放在主事件循环里，从管道另一端读到字节后处理。这样信号被"降级"成一个普通的可 epoll 事件。
    • signalfd()：Linux 特有，把信号直接变成一个可 epoll 的 fd，读出来是结构化的 signalfd_siginfo。比 self-pipe 更干净，前提是先用 pthread_sigmask 把信号 block 掉，否则默认处理会先跑。
    • 只置标志：volatile sig_atomic_t g_stop = 1;（或 std::atomic<bool> 且 lock-free），主循环每轮检查。最简单，适合优雅退出。
    // signalfd：把 SIGTERM/SIGINT 变成事件循环里的一个 fd
sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGTERM);
sigaddset(&mask, SIGINT);
pthread_sigmask(SIG_BLOCK, &mask, nullptr);   // 必须先 block
int sfd = signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC);
// 之后把 sfd 加进 epoll，可读时 read() 出 signalfd_siginfo

    还有两个容易被追问的细节：① 信号掩码是每线程的，多线程程序应该在创建其它线程之前统一 block，再由一个专职线程处理，否则信号会被随机投递给某个"没 block 该信号"的线程；② 崩溃类信号（SIGSEGV / SIGABRT）的 handler 里想打栈，backtrace_symbols() 会 malloc——正确做法是用 backtrace() + backtrace_symbols_fd() 直接写 fd，或干脆让它 core dump 事后分析。

  4. 高级如何系统性地定位一个 Linux 服务的性能瓶颈？

    方法论先于工具：先分类，再深挖。第一步只回答一个问题——瓶颈是 CPU、内存、I/O 还是锁/等待？用 vmstat 1 的 r（可运行队列）和 b（不可中断阻塞）就能把方向定下来，再用 USE 方法（每个资源看 Utilization / Saturation / Errors）逐项排查。分类错了，后面所有的调优都是白干。

手写一个最小容器（不到 60 行 C++）

// minimal-container.cpp —— 演示 namespace + cgroup 隔离
// 编译: g++ -std=c++20 minimal-container.cpp -o mc
// 运行: sudo ./mc /bin/bash
#include <sched.h>           // clone, CLONE_NEW*
#include <sys/mount.h>       // mount, MS_*
#include <sys/wait.h>
#include <unistd.h>
#include <cstdio>
#include <cstring>

static int child_fn(void* arg) {
    char** argv = static_cast<char**>(arg);
    // 隔离 mnt 后必须重新挂 /proc，否则 ps 看到的还是宿主机
    sethostname("container01", 11);
    mount("proc", "/proc", "proc", 0, nullptr);
    execvp(argv[0], argv);                // 把 PID=1 让给用户进程
    return 127;
}

int main(int argc, char** argv) {
    static char stack[1 << 20];          // 子进程栈
    int flags = CLONE_NEWPID | CLONE_NEWNS | CLONE_NEWUTS
              | CLONE_NEWIPC | CLONE_NEWNET | SIGCHLD;
    pid_t pid = clone(child_fn, stack + sizeof(stack),
                       flags, argv + 1);
    waitpid(pid, nullptr, 0);
    // 解除挂载留待父进程，避免污染宿主 /proc
}

跑起来：容器内 PID=1、hostname=container01、网络只有 lo。隔离 mnt 后必须重挂 /proc，否则 ps 看到的还是宿主机。Docker 再加 cgroup、rootfs、镜像层。

容器里三件容易踩的

  1. hardware_concurrency() 读的是宿主机核数。线程池按它开、cgroup 只给 2 核 → throttle。自己解析 cpu.max（max 表示不限额，否则 ceil(quota/period)）。
  2. OOM 在 cgroup 内挑 oom_score 最高的杀，未必是闯祸的那个。看 memory.events 与 dmesg。
  3. memory.high 不杀进程，只回收+节流——服务变慢但没崩。看 memory.pressure。

8.4 capabilities —— 把 root 切成 40 块

Linux 把 root 拆成 40+ 个 CAP_*。容器默认约 14 个；CAP_SYS_ADMIN（“新 root”）通常丢掉。

低延时常见：CAP_SYS_NICE、CAP_IPC_LOCK、CAP_NET_ADMIN。K8s 用 SecurityContext.capabilities 授予。

8.5 seccomp-bpf —— 拦截 syscall 的最后一道闸

seccomp 用 BPF 过滤 syscall。Docker 默认拦约 44 个危险调用。升级 glibc 后新 syscall（clone3 / statx）不在旧白名单 → 莫名 EPERM：升级 Docker 20.10.10+ / runc 1.0.3+，或自定义 profile。

8.6 高级工程师视角：容器内 C++ 服务排障清单

点击每道题展开参考答案（先自测，再对照）。

  1. 高级服务在容器里 CPU 已经 100% 了，throughput 却上不去，怎么查？

    先分清两种"100%"：是真的把配额跑满了，还是被 CFS 周期性冻结。后者在监控上表现为平均 CPU 利用率不高（甚至只有 40%），但 P99 惨不忍睹——因为时间都花在被冻结的那几十毫秒里。

    cat /sys/fs/cgroup/cpu.stat
nr_periods 41022
nr_throttled 18847        # 被限流的周期数
throttled_usec 982114000  # 累计冻结时长

    nr_throttled / nr_periods 就是限流命中率，超过几个百分点就值得处理。常见根因：

    • 线程数与配额不匹配：线程池按 std::thread::hardware_concurrency() 开线程，读到的是宿主机核数（比如 96），而 cpu.max 只给了 2 核。96 个线程在每个 100 ms 周期的前几毫秒就把 200 ms 配额烧光，剩下的时间整体冻结。修复见 §8.3：从 cpu.max 推算有效核数来定线程池大小。
    • 突发型负载：请求到达是尖峰的，平均值远低于 limit 但瞬时超了。可以调短 period（cpu.cfs_period_us 从 100 ms 降到 5–20 ms）让配额更平滑，或改用 cpu.weight（相对份额，不设硬顶）代替 cpu.max。
    • 被忽略的后台线程：GC、日志刷盘、指标上报线程也吃配额，容量规划时经常漏算。

    如果确认没有 throttle，那 100% 就是真的算不过来，回到常规的 CPU 剖析：perf record -g 找热点，perf stat -d 看是不是 cache miss / 伪共享导致 IPC 过低。

  2. 中级容器 OOM 了，但被杀的不是我的进程，为什么？

    因为 OOM 的作用域是 cgroup 而不是进程。当某个 memory cgroup 的用量触到 memory.max 且回收不出来，内核会在这个 cgroup 内部挑 oom_score 最高的任务杀——通常就是占内存最多的那个，未必是"闯祸"的那个。

    取证三件套：

    cat /sys/fs/cgroup/<path>/memory.events   # oom / oom_kill 计数
cat /sys/fs/cgroup/<path>/memory.max      # 硬上限
dmesg -T | grep -i "killed process"       # 谁被杀、当时 RSS 多少

    典型场景是主服务和 sidecar / agent 共处一个 cgroup：sidecar 内存泄漏把整体顶到上限，但主服务 RSS 更大，于是主服务先死。解法按优先级：① 每个进程/容器独立 cgroup 与独立 limit（K8s 里就是拆成不同 container 并各自设 limit）；② 用 oom_score_adj 显式表达"谁更该活"（越小越不容易被杀，-1000 为免杀）；③ 打开 memory.oom.group=1，让整个 cgroup 一起被杀，避免留下半死不活的状态。

    另外注意 memory.max 与 memory.high 的区别：前者是硬墙（超了就 OOM），后者是软阈值（超了会被强制回收并节流分配，进程会变慢但不死）。给 memory.high 留一段缓冲带，往往比直接撞硬墙更容易发现问题。

  3. 中级程序在容器里读到的 /proc/meminfo、/proc/cpuinfo 为什么是宿主机的？

    因为 /proc 的这些文件不是 namespace 化的。PID namespace 只隔离了 /proc/<pid> 这一层，全局统计文件（meminfo、cpuinfo、stat、loadavg）依旧来自宿主机内核的全局视图。容器不是虚拟机，没有自己的内核。

    后果很实际：JVM 老版本按 /proc/cpuinfo 定 GC 线程数和 ForkJoinPool 大小，Go 按核数设 GOMAXPROCS，C++ 用 hardware_concurrency() 开线程池——在 2 核配额的容器里全都会开出几十上百个线程，自己给自己制造争用和 throttle。

    解决方案（按可靠性排序）：

    • 直接读 cgroup 文件，这是唯一权威的来源：cpu.max（形如 200000 100000，即 2 核）、memory.max、memory.current。自己封一个 effective_cpus() 在启动时算一次。
    • lxcfs：用户态 FUSE 文件系统，把 /proc/meminfo 等按 cgroup 视图重写后 bind-mount 进容器，对应用完全透明——适合改不动的老程序。
    • 运行时自带的适配：JDK 10+ 的 UseContainerSupport（默认开）、Go 用 automaxprocs 库，都是在做同一件事。

    还要区分 cpu.max（配额，时间片）和 cpuset.cpus（绑定到哪几个物理核）：前者决定"能用多少 CPU 时间"，后者决定"能在哪些核上跑"。低延迟服务应该用后者做独占，用前者只会引入周期性冻结。

  4. 基础容器里调 mlockall() 返回 EPERM，怎么办？

    两个独立原因，都要排查：

    • 缺 CAP_IPC_LOCK：Docker 默认不给。docker run --cap-add=IPC_LOCK；K8s 里写 securityContext.capabilities.add: ["IPC_LOCK"]。
    • RLIMIT_MEMLOCK 太小：很多发行版默认只有 64 KB。docker run --ulimit memlock=-1:-1，或在程序里用 setrlimit() 抬高（需要 CAP_SYS_RESOURCE）。用 cat /proc/self/limits | grep locked 确认当前值。

    补充一点判断力：先问要不要 mlockall。它的用途是防止关键页被换出到 swap 造成毫秒级抖动，只有低延迟/实时服务才真正需要。而容器环境通常本来就关了 swap（K8s 早期甚至强制要求 swapoff），这时 mlockall 的收益接近于零，却会让内存无法被回收、更容易触发 OOM。要用就用 MCL_CURRENT | MCL_FUTURE，并确认 memory.max 留足了余量。

  5. 基础容器内跑 gdb / strace 失败，可能卡在哪几道关？

    按从外到内的顺序有三道闸，任意一道都会让 ptrace 失败：

    • capability：Docker 默认丢弃 CAP_SYS_PTRACE。加 --cap-add=SYS_PTRACE。
    • Yama LSM：/proc/sys/kernel/yama/ptrace_scope 为 1 时只允许调试自己的直接子进程（这是宿主机级别的内核参数，容器内改不了）。设为 0 放开，或用 gdb ./prog 直接启动而不是 attach。
    • seccomp：Docker 默认 profile 在旧版本里直接拒 ptrace（20.10 之后已放行）。用 --security-opt seccomp=unconfined 排除这一项。

    三条一起加就是调试镜像的标准姿势：

    docker run --cap-add=SYS_PTRACE --security-opt seccomp=unconfined ...

    生产环境不该长期这么跑。更好的做法是用 ephemeral container（K8s kubectl debug）临时注入一个带工具链的容器，共享目标 Pod 的 PID namespace；或者干脆用 eBPF 类工具（bpftrace、perf）从宿主机侧观测——它们不需要 ptrace，对目标进程零侵入、无停顿。

  6. 中级为什么 K8s 推荐 Pod 内多容器，而不是一个容器里跑多个进程？

    核心理由是让平台的管理粒度和故障粒度对齐。K8s 的一切控制面能力——资源 limit、liveness/readiness probe、restart policy、镜像版本、日志采集——都是容器粒度的。把两个进程塞进一个容器，平台就看不见它们的区别了：

    • 资源限额只能整体设，一个进程泄漏会拖死另一个（见前面的 OOM 问题）；
    • probe 只能探一个端点，sidecar 挂了平台不知道；重启也只能整体重启；
    • 镜像被迫耦合，升级 agent 要重新构建业务镜像；
    • 你得自己在容器里塞一个 init/supervisor 来做进程管理和僵尸回收——等于在容器里重新实现一遍 K8s。

    而同 Pod 的多个容器共享 network namespace（同一个 IP 和端口空间，可以走 localhost 通信）、共享 IPC namespace 和 volume，所以拆开的协作成本很低，sidecar 用 UDS 或 loopback 与主容器通信即可。这正是 Istio/Envoy、日志收集、配置热更新这些 sidecar 模式成立的前提。

    什么时候例外：两个进程有强父子关系且生命周期必须完全一致（比如一个薄壳 wrapper 起真正的业务进程），拆开反而增加复杂度；这时也要记得让 PID 1 正确转发信号并回收僵尸进程（用 tini / --init），否则 kubectl delete 会一直等到超时被 SIGKILL。
