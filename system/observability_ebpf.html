读前定位 · 为什么 Observability 是第三支柱

log + metric + trace 之后还缺一层：内核级 observability，也就是 eBPF / perf / bpftrace 这条链路。它专门回答那类「应用日志和指标全都正常，但请求就是慢」的问题。

0.2 四种观测手段各答什么问题

「装了一堆工具还是查不出来」，根源多半是拿一种手段去回答它答不了的问题——用指标去归因、用日志去看分布、用链路去找热点函数。

落到内核观测里，能拿到的数据形态只有三种，工具选型全由它决定：

形态它能回答它答不了成本量级代表
① 计数（counter） 「发生了多少次」「有没有在涨」 不知道是谁、慢多少 几乎为零，可常驻 /proc、nstat、ethtool -S、BPF percpu map 累加
② 分布（histogram） 「尾巴多长」「P99 落在哪个数量级」 不知道是哪一次、栈是什么 低，内核里聚合，输出量恒定 biolatency、runqlat、bpftrace 的 hist()
③ 事件流（event / trace） 「那一次发生了什么，栈与时间戳」 量大时自己就是瓶颈，还会丢事件 高，每条都要出内核 strace、opensnoop、bpftrace 的 printf()、ftrace trace_pipe
正确的顺序永远是 ①→②→③：先用计数确认「问题真的存在且在这一层」，再用分布确认「长尾量级对不对得上」，最后只对超过阈值的那几次抓事件流。一上来就 strace -f 全量抓既慢又淹在噪声里——在已经过载的机器上，第 ③ 类观测本身就可能是最后一根稻草。

0.3 什么场景必须用本文这套

  • 「哪个 syscall 慢」「内核锁卡住了」——应用日志只记业务耗时；内核自旋锁与 rwsem 的竞争在用户态 profiler 眼里只是一段「不知道在干嘛的时间」（机制见 内核同步与 RCU）。
  • 「哪些进程在抢同一块磁盘」——biolatency -F / biosnoop 能按进程、设备、IO 类型切；iostat 只给一个聚合数字。
  • 「生产不能装 valgrind」——valgrind 慢 10–100 倍且要重启进程；eBPF 挂上去就能观测已经在跑的进程。
  • 「延迟 spike 一秒，不知道哪里慢」——只能靠「内核里做阈值过滤 + 命中时抓栈」，§8 给完整套路。

0.4 什么时候不该用 eBPF

❌ 已经有现成计数器

TCP 重传、softirq 挤压、页回收次数，内核本来就在 nstat / /proc/net/softnet_stat / /proc/vmstat 里数着，读一个文件的成本是零。

❌ 问题在业务语义层

「哪个租户慢」「哪条 SQL 拖垮了连接池」内核看不见，属于 日志 / 指标 / 链路。硬用 uprobe hook 业务函数，会得到一个又贵又脆的方案。

❌ 需要长期跨版本稳定

想把某个内核内部指标常驻接进 Prometheus，先问「挂的是 tracepoint 还是 kprobe」。挂 kprobe 的常驻监控会在某次内核升级后静默失效或静默出错数（§4.5、§7.3）。

eBPF 的核心价值：不改代码、不重启服务、实时观测内核与所有进程，失败了也带不走内核。但它不是免费的——「安全」和「便宜」是两件事，§4.7 专门讲这个区别。

1.1 先分层，再选工具：USE 与 RED

拿到「系统慢」的报障，第一步不是打开工具而是决定要在哪一层找。USE（资源视角：利用率 / 饱和度 / 错误）面向 CPU、内存、磁盘、网卡这些有限资源，是本文的主场；RED（请求视角：速率 / 错误率 / 时延分布）面向服务对外提供的请求，属于 应用层可观测性，本文只在它指向内核时接手。

饱和度比利用率重要得多。 CPU 利用率 60% 完全可能同时存在严重排队——负载集中在少数几个核上，或者被 cgroup 限流。利用率是「有没有在干活」，饱和度是「有多少人在门口排队」。runqlat、biolatency 之所以值钱，就是它们直接量饱和度，而 top 永远量不到。PSI（/proc/pressure/*）是内核自己给出的饱和度指标，成本为零，值得先看一眼。

这一节刻意做薄。 perf 全景 已经讲透了 PMU 采样原理、16 个子命令、FP / DWARF / LBR 三种栈回溯、符号化与 [unknown]、Top-Down。本节只留「够用的速查」和「火焰图怎么读」——后者是 eBPF 侧 profile、offcputime 共用的判读能力。

2.1 五分钟速查

我想知道命令一句话说明
现在哪个函数最热perf top -p <pid>实时刷新，默认按 CPU 周期采样

全文唯一需要背下来的 perf 命令：on-CPU / off-CPU 两张火焰图
# on-CPU：99 Hz 采样 30 秒 → 火焰图
sudo perf record -F 99 -g -p $(pgrep -f myapp) -- sleep 30 \
  && sudo perf script | stackcollapse-perf.pl | flamegraph.pl > oncpu.svg

# off-CPU：只记阻塞 > 1 ms 的栈，限 PID、限 30 秒（不限就是故障源）
sudo offcputime-bpfcc -df -p $(pgrep -f myapp) --min-block-us 1000 30 > out.stacks
flamegraph.pl --color=io --title="Off-CPU Time" --countname=us out.stacks > offcpu.svg
99 Hz × 30 s ≈ 3000 个样本。样本数要心里有数：占比 1% 的分支只有 30 个样本，统计上已经很不可靠，别对着这么窄的火苗下结论。

2.2 on-CPU 与 off-CPU 回答的是两个问题

一次请求的墙上时间只能拆成两段：线程在 CPU 上执行与不在 CPU 上。两种火焰图各覆盖一半，只看一种必然漏掉另一半——这是「CPU 才 20% 但接口就是慢」的根源。

on-CPU 火焰图off-CPU 火焰图
回答什么「CPU 忙的时候在干什么」「不忙的时候在等什么」
采集方式采样：固定频率（如 99 Hz）中断，记录当前栈事件驱动：在 sched_switch 记下离开 CPU 的时刻与栈，被唤醒时算出阻塞时长
横轴宽度被采到的样本数 ∝ 占用 CPU 的时长累计阻塞时长（单位是微秒，不是样本数）
开销与护栏低且可预测（频率固定与负载无关）；只需确认样本数够高且随负载放大——每秒几十万次上下文切换都要抓栈，所以必须限 PID、限时长、设最小阻塞阈值，否则观测本身就是故障源

2.3 火焰图怎么读：横轴不是时间轴

这是火焰图被误解最多的一点，误解之后会做出完全相反的判断。

如果图里出现大量 [unknown] 或栈只有一两层，说明缺少 frame pointer、符号被 strip、或者是 JIT 代码——此时图的形状就是错的。原因分类与修法见 perf 全景 §9 符号化。
03

ftrace · 内核函数追踪

ftrace 是内核内置的追踪框架：不装任何东西、不需要编译器与 BTF，echo 几个文件就能跑。它比 eBPF 老得多，但至今仍是「看内核函数调用图与逐层耗时」最快的路径，也是连 bpftrace 都装不上的老旧生产机上唯一还能用的手段。

3.1 机制：为什么它关着的时候几乎不要钱

内核编译时带 -pg -mfentry，编译器在每个函数入口插一条对 __fentry__ 的调用。每次调用都真跳一趟内核会慢到不能用，所以 CONFIG_DYNAMIC_FTRACE 在启动时把这些 call 全部原地改写成 NOP，并把地址记进一张表。

像在每间办公室门口都预先钻好装摄像头的孔，平时孔里塞着一块和墙同色的塞子（NOP）。要装摄像头时照着施工图（那张地址表）走到指定的几个孔前换掉塞子。关键在于只装需要的那几个——这正是 set_ftrace_filter 存在的意义。

3.2 tracefs：先认路

控制面就是一个文件系统，较新内核挂在 /sys/kernel/tracing（老一点在 /sys/kernel/debug/tracing，内容一样）。只需要认识这几个：

3.3 function_graph：带耗时的调用树

这是 ftrace 最有价值的 tracer：同时挂函数入口和返回，输出缩进的调用树 + 每层实际耗时，粒度比 strace 细一整个层级。开法是三条 echo：function_graph 写进 current_tracer、目标函数写进 set_graph_function、阈值写进 tracing_thresh，然后读 trace。

三个必踩的坑。 ① 不设 tracing_thresh 和 max_graph_depth，输出会瞬间把缓冲区冲掉，看到的是最后几毫秒的碎片。② 默认 buffer_size_kb 偏小，长时间追踪要调大或改用 trace_pipe。③ set_graph_function 是「从这个函数开始追整棵子树」，set_ftrace_filter 是「只追这些函数本身」。

3.4 事件追踪：比函数追踪更该优先用

events/ 下是内核所有静态 tracepoint。能用 tracepoint 就别用 function tracer：参数结构化、相对稳定、开销更低。固定流程：

步骤操作（以 block:block_rq_issue 为例）为什么
① 看字段cat events/block/block_rq_issue/format写过滤条件全靠它。这个事件给的是 dev/sector/nr_sector/bytes/rwbs/comm
② 设过滤echo "bytes > 262144" > .../filter过滤在内核里发生，不匹配的事件压根不进缓冲区
③ 开 + 读，用完 一定要关echo 1 > .../enable → cat trace_pipe → echo 0 > .../enabletrace_pipe 流式消费，长跟不会被冲掉；忘关它会一直往缓冲区写
再往上一层是 hist trigger：往 events/<子系统>/<事件>/trigger 写一行 hist:key=comm:val=bytes:sort=bytes.descending，读同目录的 hist 就能拿到「按进程名聚合的写入字节数」，全程在内核里算完、不外送任何事件（前面加 ! 关掉）。它是「穷人版 bpftrace」——能聚合、求和、做 log2 直方图、用 onmatch 关联两个事件算延迟，限制是只能用已有的 tracepoint 字段。在装不了 bpftrace、也没有 BTF 的老机器上，它经常是唯一的选择。

04

eBPF 概念 · BPF map / probes / JIT / Verifier

eBPF = 「在内核里跑 sandboxed 程序」：你写一段 BPF 字节码（受限 C 或 bpftrace DSL），内核 verifier 检查安全后 JIT 成原生码运行。这是 Linux 过去十年最大的内核创新。

① 挂载点（§4.5）

在哪里 hook：kprobe / fentry · tracepoint · uprobe / USDT · perf_event · XDP / tc · LSM。

② BPF map（§4.3）

唯一的持久化存储，也是内核 ↔ 用户态的通道。能不能在内核里聚合完全看 map 选得对不对——eBPF 便宜的根本原因。

③ Verifier（§4.2）

加载时的静态证明器。不是「运行时保护」，而是「不合格就根本进不来」。

④ JIT

字节码 → 本机指令，x86-64 / arm64 默认开启。走解释器慢一个数量级以上。

4.1 eBPF 为什么可行：三个前提缺一不可

「让用户提供一段代码，在内核态、在中断上下文里、以完全的内核权限同步执行」——听起来就不该被允许。它成立靠三件事同时到位：

① 受限的指令集——刻意设计得容易被机器分析的 RISC 风格虚拟 ISA：11 个 64 位寄存器（r0 返回值、r1–r5 传参、r6–r9 被调用者保存、r10 是只读栈帧指针）、定长指令、栈只有 512 字节、只能调 helper 白名单与 kfunc、没有动态内存分配。② Verifier 的静态检查（§4.2）。③ JIT——让一个「读几个字段、更新一次 map」的探针落在几十到几百纳秒。安全和便宜必须同时成立。

三个使用层级，按需求选。 ① 直接用现成的 BCC / libbpf-tools，一行命令，不用懂 eBPF；② 写 bpftrace 一行脚本，学一小时，覆盖八成临时排障；③ 写 libbpf + CO-RE 的 C 程序，学一周，用于长期常驻的基础设施。绝大多数人停在 ② 就够了，但 §4.2–§4.7 的原理即使只用 ①② 也必须懂——否则你不知道为什么脚本报错、为什么数字不准、为什么它把机器拖慢了。

4.2 Verifier 讲透：它到底拒绝什么

Verifier 干的事一句话：加载时把所有可能的执行路径都走一遍，对每个寄存器推导出「可能是什么类型、取值落在什么范围」，然后证明每次内存访问都合法、且程序必然终止。 这是静态证明而非运行时检查——通不过就是加载失败，通过了运行时就没有额外开销。

把它想成机场安检而不是机上的保安：每件行李摊开确认，不能确认就不让上飞机；代价是排队慢、有些无害的东西也被拦下，好处是飞机上不需要再配保安。你遇到的大多数 verifier 报错，本质是「我写的东西是安全的，但我没有把这件事证明给它看」。

报错日志格式固定：先给出触发问题那条指令的上下文（带源码行注释），再给一行判决。例如 r7 = r0（bpf_map_lookup_elem 的返回值）之后紧接 r1 = *(u64 *)(r7 +0)，判决就是 R7 invalid mem access 'map_value_or_null'——补一个 if (!s) return 0; 让类型在这个分支里收窄成 map_value 就过了。

三个实用技巧：① 把日志级别开到最大（libbpf 设 log_level = 2，或 bpftool prog load -d），能看到每条指令后各寄存器的推导范围，R2_w=inv(umin=0,umax=4294967295) 直接告诉你「verifier 认为它可能有多大」；② 从报错指令往上游读，定位「范围从哪一步开始不确定」；③ 末尾的 processed N insns 是复杂度体检表，接近上限说明该用 tail call 拆程序。

Verifier 是学习曲线上最陡的一段，心智模型却很简单：「你必须把安全性证明给一个不会推理业务逻辑的机器看」。人类觉得显然的「这个 map 里肯定有值」「这个索引不可能越界」，对它都不成立。养成三个习惯——map 查找后判空、变量当下标前夹范围、要外送的结构体先清零——八成的报错根本不会出现。

4.3 BPF map：类型选择决定了工具准不准

map 是 BPF 程序唯一的持久化存储，也是它和用户态之间的通道。没有 map，探针只能触发一次打印一行——等于把全部聚合推给用户态，事件量一大先被自己压垮。

类型并发与内存陷阱
HASH / ARRAY 桶级自旋锁，单次 update/delete 原子，但 *v += 1 不是；默认预分配 max_entries 项 满了之后 update 直接失败、静默丢数据；ARRAY 的索引必须让 verifier 能证明不越界
PERCPU_HASH / PERCPU_ARRAY 写入完全无锁无竞争（内核做 cache line 对齐）；内存 nr_cpus × value_size 用户态读出来要自己把各核相加；读到的瞬间不是严格一致的快照（统计用途可接受）
LRU_HASH / STACK_TRACE 同 HASH；STACK_TRACE 按 max_entries × 栈深 LRU 淘汰是近似的（per-CPU 局部），极端情况会淘汰掉还在用的项，表现为「少数事件的延迟算不出来」；栈 id 会哈希碰撞，且解析时进程可能已退出
PERF_EVENT_ARRAY / RINGBUF 前者每核独占无锁、内存随核数增长；后者 reserve 时取锁、只占一份 ringbuf 在极高事件率下多核争同一把锁，反而不如 per-CPU 的 perf buffer（§4.4）
共享 map 上写 (*v)++ 是最隐蔽的一类错误。 这条语句是「读—改—写」三步、不是原子操作，多核并发会丢更新；而且所有核更新同一个 value 就是在争同一条 cache line，让探针本身成为系统里竞争最激烈的地方。退一步的 __sync_fetch_and_add(v, 1) 数对了，但仍在争那条 cache line。高频路径的正解只有一个：换成 per-CPU map，然后普通自增。

4.4 ringbuf 相比 perf buffer 改进了什么

当你确实需要把每一条事件送到用户态（比如 execsnoop 要打印每次 exec 的命令行），就需要一个内核到用户态的高速通道。历史上是 perf buffer，5.8 之后有了 ringbuf。

ringbuf 解决的不只是「省内存」，更重要的是顺序性。用 perf buffer 做「A 之后是否总跟着 B」这类因果分析会踩到跨 CPU 乱序的坑——你看到 B 在 A 前面，怀疑了半天代码逻辑，其实只是两个 CPU 的缓冲区被消费的先后不同。要做事件关联就优先 ringbuf。

位置与开销图里已经给全，这张表只补「用的时候容易被咬一口的地方」：

挂载点典型用途要注意什么
tracepoint 长期监控的首选：sched_switch、block_rq_*、syscalls:sys_enter_* 字段以命名形式给出，社区当作面向用户空间的接口对待；raw_tracepoint 更快但参数是内部结构，更脆
fentry / fexit（5.5+） 要挂内核函数时的优先选择；fexit 能同时拿参数和返回值 依赖 BTF；挂的仍是函数名，函数改名照样失效

tracepoint 稳定而 kprobe 不稳定，这一点必须讲清楚。 kprobe 挂的是内核的内部实现细节，社区从不提供兼容性承诺。三种失效方式，危险程度递增：
① 函数消失（内联 / 合并 / 改名，如 do_sys_open 在 5.6 后变成 do_sys_openat2）——还算好的，因为它会报错。
② 参数重排——函数还在、脚本还能加载、图表还在出数，但第三个参数从「字节数」变成了「标志位」，数字全错却没有任何告警。
③ 结构体字段挪位——依赖字段偏移的写法会读到别的内容；这一类能用 CO-RE 解决（§4.6），前两类不能。
所以用了 kprobe 就要把「探针健康度」当成告警项——一个静默失效的监控比没有监控更危险。

4.6 CO-RE 与 BTF：eBPF 工程化最关键的一步

BPF 程序经常要读内核结构体的字段（比如从 struct sock 里取目的 IP），编译出来是一条 load [r1 + 40]——偏移量 40 是编译时写死的常量。而 结构体布局随内核版本、随 CONFIG_ 组合而变：同一个字段在 5.4 上偏移 40，5.15 上可能是 48。拿着写死 40 的程序去跑，读到的是隔壁字段——不会崩，只会给你错数据。

BCC 的解法简单粗暴：把 C 源码随工具发出去，运行时在目标机上现场调 clang 编译。代价很实在：每台机器要装 clang/LLVM + 匹配的内核头文件（容器镜像里通常两者都没有，这是「在 Pod 里跑 BCC 失败」最常见的原因）；启动要几秒钟；编译期内存峰值可达几百 MB——在一台已经因内存问题在排查的机器上，工具自己把它推过了 OOM 线，这不是段子。

BTF（BPF Type Format）：一种极其紧凑的类型描述格式，记录内核里每个结构体有哪些字段、各在什么偏移、什么类型。内核编译时开 CONFIG_DEBUG_INFO_BTF=y 就会把它嵌进内核镜像自身，运行时通过 /sys/kernel/btf/vmlinux 暴露。它只有几 MB，比完整 DWARF 小一到两个数量级，所以发行版愿意默认打开。

CO-RE（Compile Once – Run Everywhere）反过来解：既然偏移量是唯一会变的东西，那就别在编译时写死，留一个待填的空。① 编译时 clang 遇到 BPF_CORE_READ(sk, __sk_common.skc_daddr) 会额外生成一条重定位记录；② 加载时 libbpf 读目标机器的 BTF 查出真实偏移，就地改写字节码里的立即数；③ 字段在老内核上不存在也有办法——bpf_core_field_exists() 让两条分支都编译进去，加载时由重定位决定走哪条。

下面是最小 CO-RE 骨架，把前面几节的纪律落在一处：vmlinux.h 拿类型、per-CPU map 聚合、LRU map 存无界键、查找后判空、存了就删。

// mytrace.bpf.c —— 测 fsync 耗时分布，编译一次跨内核可跑
// vmlinux.h 由 bpftool btf dump file /sys/kernel/btf/vmlinux format c > vmlinux.h 生成
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_core_read.h>
#include <bpf/bpf_tracing.h>

char LICENSE[] SEC("license") = "GPL";

// 键空间无界（按线程），必须用 LRU：普通 HASH 满了会静默丢数据
struct {
    __uint(type, BPF_MAP_TYPE_LRU_HASH);
    __uint(max_entries, 8192);
    __type(key, u32);            // tid
    __type(value, u64);          // 进入时的时间戳
} start SEC(".maps");

// 高频路径上的直方图：per-CPU，写入无锁无争用，用户态读出后各核相加
struct {
    __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
    __uint(max_entries, 64);     // log2 分桶
    __type(key, u32);
    __type(value, u64);
} hist SEC(".maps");

// fentry 优于 kprobe：参数带类型、由 verifier 校验、无异常路径
SEC("fentry/vfs_fsync_range")
int BPF_PROG(on_fsync_enter, struct file *file)
{
    u32 tid = (u32)bpf_get_current_pid_tgid();
    u64 ts  = bpf_ktime_get_ns();
    bpf_map_update_elem(&start, &tid, &ts, BPF_ANY);
    return 0;
}

SEC("fexit/vfs_fsync_range")
int BPF_PROG(on_fsync_exit, struct file *file, loff_t s, loff_t e, int datasync, int ret)
{
    u32 tid = (u32)bpf_get_current_pid_tgid();

    u64 *tsp = bpf_map_lookup_elem(&start, &tid);
    if (!tsp)                    // ← 必须判空，否则 verifier 直接拒绝加载
        return 0;

    u64 us = (bpf_ktime_get_ns() - *tsp) / 1000;
    bpf_map_delete_elem(&start, &tid);   // 存了就要删，否则 map 涨满

    // CO-RE：字段偏移在加载时按目标机 BTF 重定位，不是编译时写死
    u32 dev = BPF_CORE_READ(file, f_inode, i_sb, s_dev);
    if (dev == 0)
        return 0;

    u32 slot = 0;
    for (u32 i = 0; i < 63 && (us >> i); i++)   // 编译期常量上界，verifier 才认
        slot = i;

    u64 *cnt = bpf_map_lookup_elem(&hist, &slot);
    if (cnt)
        (*cnt)++;                // per-CPU 副本，普通自增即可，不需要原子
    return 0;
}

启动时间 / 内存峰值数秒 / 几百 MB毫秒级 / 几 MB
跨内核 / 容器化靠现场编译「碰巧」适配；镜像臃肿同一个二进制跨版本可用，DaemonSet 挂一个 BTF 目录即可
CO-RE 是「eBPF 工具」变成「eBPF 基础设施」的分界线。 Cilium、Pixie、Parca 以及 libbpf-tools/ 全都走这条路，原因就是上表最后两行。实践上记两件事：① 先确认目标内核有没有 /sys/kernel/btf/vmlinux，没有 BTF 就没有 CO-RE；② 老内核可从社区的 BTF 归档站拿到对应文件，libbpf 支持从外部加载。

4.7 开销与安全边界：安全 ≠ 便宜

这是生产使用 eBPF 时唯一一条真正会伤到你的认知差：Verifier 保证的是内存安全和终止性，完全不保证你不会给一条每秒执行千万次的路径加上一段代码。

开销来源量级什么时候会失控怎么控
探针执行本身 tracepoint / fentry + 一次 map 更新，几十到几百纳秒 __schedule 每秒数十万次尚可接受；网络收包路径、malloc、自旋锁实现 上就是灾难 先用 funccount 估「每秒被调多少次」，一分钟给答案
栈回溯 单项最贵，比一次 map 更新贵一到两个数量级 off-CPU profiling：每次上下文切换都抓栈 限 PID、限时长、设最小阻塞阈值（--min-block-us）
事件外送 比内核内聚合贵几个数量级 用 printf() 而不是 hist()；消费不及时还会丢事件 能聚合就绝不外送；必须外送时先在内核里做阈值过滤
uprobe 的陷入 比 kprobe 高一个数量级 挂用户态热点函数，作用域是整个文件 见 §7.2 的真实教训
内核内存 map 预分配 + JIT 代码，不可回收 max_entries 设太大；per-CPU map × 128 核 算清 max_entries × (key+value)（per-CPU 再 × 核数）。5.11 后计入 cgroup 内核内存

安全边界上还有三条约束：探针不能睡眠，也不能调用任意内核函数（helper 是白名单）；递归风险真实存在——在分配路径或锁实现上挂探针而探针自己又触发同一条路径，内核用 per-CPU 递归保护挡住，代价是丢掉那些事件；加载能力本身就是攻击面——能加载 BPF 基本等价于能读任意内核内存，所以发行版默认 kernel.unprivileged_bpf_disabled=1。

生产使用 eBPF 的四条纪律。
① 先在压测环境量开销：挂探针前后各跑一次，对比业务 P99 和 perf stat 的 IPC。
② 限范围、限时长：能限 PID 就限 PID，能只跑 30 秒就别常驻，临时脚本永远带 timeout。
③ 常驻监控只用最便宜的形态：tracepoint（或 fentry）+ per-CPU map 聚合 + 定期读取。
④ 把观测工具自身的开销当成一个要被监控的指标。 在一个已经过载的系统上贸然挂高频探针，是把一次性能事件升级成一次故障的经典方式。

5.1 三分钟语法

# 完整可跑的短脚本：read 系统调用的延迟直方图（微秒）
# 三段式在这里体现为：两个 tracepoint 配对 + /@s[tid]/ 过滤掉没有配上的 exit + hist() 在内核里分桶
sudo bpftrace -e '

  tracepoint:syscalls:sys_exit_read /@s[tid]/ {

5.4 写脚本的四条纪律

  • 先 bpftrace -lv 确认字段，别照着博客抄。 网上脚本大量挂在已改名或已内联的 kprobe 上，字段名也跨版本变过。
  • 能用 key 聚合就不要 printf。 把本来想打印的东西当成 @[...] 的键（第 ② 条就是这么做的）。
  • 存了就要删。 @start[tid] = nsecs 之后若某条路径没走到 delete()，map 会一直涨到满，然后静默丢新数据。最典型的漏删场景是「进入了但出错提前返回，没有对应的 exit 事件」。
  • 临时脚本一律加时限。 timeout 30 bpftrace -e '...' 或写 interval:s:30 { exit(); }。忘在生产上跑了一夜的高频探针是常见的自伤方式。
把这些脚本沉淀成团队的 runbook——不是存命令，而是存「命令 + 一份正常输出的样例」。排障最耗时的从来不是敲命令，而是判断「我看到的这个数字算不算异常」。有一份健康基线，这个判断从十分钟缩到十秒。

USDT / kprobes / uprobes · 应用层 hook

§4.5 给了挂载点全景，这一章补上机制细节——kprobe 怎么在运行中的内核上插入断点、uprobe 为什么明显更贵、以及一条用血换来的纪律：在高频路径上挂探针能把一台健康的机器打垮。

先把「谁能挂在哪」钉死。 内核函数（__schedule、vfs_fsync_range）只能挂 kprobe/kretprobe 或 fentry/fexit；uprobe/uretprobe 只能挂用户态二进制里的函数。 两者不能互换——不存在「给 __schedule 挂 uprobe」这个选项，也不存在「给 malloc 挂 kprobe」。看到脚本里写反了，那份脚本就是错的。

7.1 kprobe：在跑着的内核上改指令

内核做的事很直接：把目标地址的指令保存下来，那里改成一条断点指令（x86 上是单字节 int3）。CPU 执行到这里触发异常，内核认出这是一个 kprobe、调用你的处理函数，然后把被覆盖的那条指令搬到别处单步执行，最后跳回去继续。

像在一条正在通车的高速路上装测速点：把某段路面换成岔道口（int3），车被引到旁边小房间登记（处理函数），再把原本这段路补跑一遍，然后回主路。登记本身不慢，慢的是「下高速再上高速」。优化版不挖岔道口，而在原地放一块跳板（int3 换成 5 字节 jmp），省掉异常处理那一趟。
  • 优化版 kprobe（CONFIG_OPTPROBES）：条件允许时内核自动把断点换成跳转，绕开异常路径。不是每个 kprobe 都能被优化——同一行脚本挂在不同函数上开销可能差好几倍。
  • kretprobe 的实例池：要在返回时触发，得在入口处把返回地址换成蹦床地址，真地址存进一个「实例」。实例数由 maxactive 限定，并发线程数超过实例数时多出来的直接不记录，表现为「调用次数比实际少」且没有任何提示。
  • 有 fexit 就别用 kretprobe：fentry/fexit 基于 BPF trampoline（5.5+，依赖 BTF），从 ftrace 预留的入口 NOP 处调过来，没有异常、没有实例池、参数带类型，还能同时拿到入参和返回值。

7.2 uprobe：为什么比 kprobe 贵一个数量级

uprobe 表面上是同一件事——把用户态二进制某个偏移处的指令换成断点。但有三个额外代价叠加：

代价说明与后果
每次命中要两次陷入内核 断点触发陷入一次，执行完处理函数后原指令要在「异地执行」区域里单步跑完再陷回来。这是 uprobe 比优化过的 kprobe 慢一个数量级的主因——后者连一次异常都没有
破坏页共享 改写用户态代码页会触发写时复制，这个页从「共享的 page cache 页」变成该进程私有的副本；目标若是被上百个进程共用的共享库，多出的内存占用会被放大
作用域是「文件 + 偏移」，
不是「进程」		 uprobe 注册在 inode 上。挂到 libc.so 的 malloc，全机所有用这个 libc 的进程都会触发，哪怕你按 PID 过滤——过滤发生在陷入之后，代价已经付了。最容易被低估的一条：你以为只在观测一个服务，实际上给整台机器上了税
Case 0 · 一条探针把一台健康的机器变成不可用

两种典型翻车方式，本质相同：低估了目标路径的调用频率。

[翻车 A] 想知道「上下文切换多频繁、都是谁在切」，于是给内核函数 __schedule 挂 kprobe（内核函数只有这一类选择）并逐条 printf。 → 这个函数在繁忙的多核机器上每秒被调数十万次； → 每次都外送一条事件，用户态消费不过来、内核缓冲区打满； → 探针执行本身发生在调度路径上，拖慢了调度器本身； → 负载飙升，ssh 都开始卡，只能等脚本超时或者硬重启。 [翻车 B] 想抓内存分配热点，给共享 libc 里的 malloc / free 挂 uprobe （用户态函数只有这一类选择）。 → uprobe 挂在 inode 上，全机所有进程的每次 malloc 都陷入内核两次； → 单次约 1–2 微秒，而一个普通服务每秒 malloc 几十万次； → 整机吞吐掉一大截，被观测的进程慢了一个数量级。 [正确做法] 动手前先花一分钟量频率： $ sudo funccount-bpfcc -d 10 '__schedule' # 内核函数 $ sudo funccount-bpfcc -d 10 'c:malloc' # 用户态函数 → 看到「每秒几十万次」就换方案：改用采样（profile:hz:99）、 用 hist() 在内核里聚合而不是 printf、或挂到更低频的上游函数。
挂探针前必须先回答一个问题：这个函数每秒被调用多少次？ 一万次以内随便挂；十万次量级要确保只做 map 聚合、绝不外送；百万次量级基本只能采样。「Verifier 通过了」只说明它不会崩内核，完全不说明它不会拖垮内核。

7.4 给自己的 C++ 服务埋 USDT 探针

USDT 是「把可观测性设计进代码里」最轻的做法。关键性质：没有人观测时，那里只是一条 NOP——不是「开销很小」，是真的没有开销。所以可以在生产二进制里长期保留埋点，不用在「信息量」和「性能」之间取舍。

埋点 → 确认 → 挂载：一条完整链路

// 1. 埋点（Debian/Ubuntu: apt install systemtap-sdt-dev）
#include <sys/sdt.h>

void process_order(int order_id, int amount) {
  DTRACE_PROBE2(myapp, order_start, order_id, amount);
  // ... 业务逻辑 ...
  DTRACE_PROBE2(myapp, order_done, order_id, latency_us);
}

# 2. 编译后确认探针真的进了二进制（找 .note.stapsdt 段）
$ readelf -n ./myapp | grep -A 2 stapsdt
  stapsdt              0x00000045       NT_STAPSDT (SystemTap probe descriptors)
    Provider: myapp   Name: order_start   Args: -4@%edi -4@%esi
    Provider: myapp   Name: order_done    Args: -4@%edi -4@%esi

# 或者直接问 bpftrace / tplist（也可用来查第三方组件内置了哪些探针）
$ sudo bpftrace -l 'usdt:/opt/myapp/myapp:*'
$ sudo tplist-bpfcc -p $(pgrep myapp)

# 3. 挂上去用：算每个订单的处理耗时分布
$ sudo bpftrace -e '
  usdt:/opt/myapp/myapp:order_start { @s[arg0] = nsecs; }

  usdt:/opt/myapp/myapp:order_done /@s[arg0]/ {
    @us = hist((nsecs - @s[arg0]) / 1000);
    delete(@s[arg0]);
  }'
  • 埋在哪：请求进入 / 离开、跨组件边界、重试与降级分支、缓存命中与否。埋「状态转换」而不是「函数调用」——后者用 uprobe 也能挂，前者只有你自己知道。
  • 参数要能当聚合的 key：租户 ID、请求类型、错误码这类低基数字段最有价值；传指针进去没什么用。参数需要现算（比如拼字符串）时，用带信号量的探针形态，让「没人观测时连参数都不算」。
日志是「无条件写出，事后筛选」，USDT 是「默认不写，需要时才开」。前者的成本恒定发生（格式化、加锁、落盘、传输、存储），后者只在观测窗口内发生。所以那些「很想记但记不起」的高频细节，正是 USDT 的用武之地。

5 个真实诊断 case

五个 case 都按同一条链条组织：现象 → 列出所有假设 → 用哪个探针去排除假设 → 结论与修复。这个顺序比任何具体结论都重要——排障效率不取决于你会多少工具，而取决于能不能每一步都砍掉一半可能性。

Case 1 · 服务 P99 从 50 ms 跳到 2 秒，日志里看不出任何异常

现象：P50 稳定 50 ms，P99 每隔几分钟有一批到 2 秒。业务日志记的「处理耗时」也是 2 秒，但那是从进 handler 到返回的总时长，内部没有分段。CPU、内存、网络监控全平稳。
假设：① 下游依赖偶发慢；② 锁竞争；③ 调度延迟；④ 某个 syscall 偶发慢；⑤ GC 或分配器停顿。

[排除 ③] 先跑最便宜的：runqlat-bpfcc 10 1 → P99 = 380 微秒。和 2 秒差三个数量级，调度清白；cpu.stat 的 nr_throttled = 0。 [缩小范围] 不知道是哪个 syscall，用 raw_syscalls 先看全景（短时间跑）： $ bpftrace -e 'tracepoint:raw_syscalls:sys_enter /pid==$PID/ { @s[tid]=nsecs; } tracepoint:raw_syscalls:sys_exit /@s[tid]/ { @us=hist((nsecs-@s[tid])/1000); delete(@s[tid]); }' → 明显双峰：主体几微秒，另有几十个样本落在 1–2 秒的桶里。 [定位到具体 syscall] 在内核里做阈值过滤，只抓超时那几次 + 用户栈 （脚本形态见 §10.3 最后一题）： → 09:41:22 fsync 1832 ms，栈指向写审计日志的那条路径。 [验证根因] 问题在应用还是设备？biolatency-bpfcc 10 3 → 同步写（WS）最大桶落在 [1s, 2s)：块设备真的慢，不是应用发太多 fsync。 [结论] 审计日志与数据文件在同一块共享云盘上，云盘按 IOPS 配额限流； 批量任务把配额耗光后，同步写就排到秒级。 [修复] ① 审计日志换独立卷；② 按时间窗批量落盘合并 fsync； ③ 给 biolatency 长尾加告警。[结果] P99 2000 ms → 80 ms。
真正省时间的是第一步：花 10 秒跑 runqlat 排除调度，就砍掉了「是不是 CPU 不够」这个最容易被无限追查的方向。「量级对不对得上」是排除假设最快的判据。另外注意最后一步：定位到 fsync 慢之后还要再问一次「是谁的问题」，否则很容易得出「减少 fsync」这个治标的结论。
Case 2 · RSS 每天涨 200 MB，但 valgrind 上不了生产

现象：RSS 单调上涨，一周后触发容器内存上限被杀；重启就好，然后重新开始涨。valgrind 慢 10 倍以上且要重启进程，测试环境复现不出来（流量模式不同）。
假设：① 真泄漏；② 假泄漏——分配器持有空闲内存不还给 OS；③ 涨的不是堆而是别的段（mmap、线程栈）；④ 内核侧对象泄漏。

[先分段，别急着抓栈] 涨的到底是哪一段？ $ cat /proc/$PID/smaps_rollup # 全部映射的汇总 $ grep -E 'VmRSS|VmData|Threads' /proc/$PID/status → VmData（堆 + 匿名映射）在涨，线程数稳定。排除 ③。 [区分真假泄漏] 判据：让分配器把空闲内存还回去，看降不降。 → 一直不降则倾向真泄漏；若是碎片型「假泄漏」，该转向 arena 数量与分配模式，而不是去找哪一行没 free。 [抓分配栈] memleak-bpfcc 可以直接在生产上跑，但要压成本： $ sudo memleak-bpfcc -p $PID --sample-rate 100 -a 300 60 → --sample-rate 100 = 每 100 次分配采样一次， 这个参数是能不能上生产的分界线（不加就是 §7.2 的翻车 B）； → -a 300 只报存活超过 300 秒的分配，滤掉正常的短命对象； → 输出按「未释放字节数」排序，栈顶指向一处回调注册。 [结论] 某个事件回调在异常分支上提前 return 跳过了注销；正常路径会注销， 测试环境因此跑不出来。[修复] 改成 RAII guard，注销放进析构。
① memleak 不加采样率就别在生产上跑——它底层是 uprobe 挂分配函数，全量抓的开销足以让服务不可用。② 先分清真假泄漏再抓栈：如果是分配器碎片，你会拿到一堆完全正常的分配栈然后怀疑人生。「RSS 在涨」和「有内存泄漏」是两件事。
Case 3 · CPU 利用率只有 60%，响应却在变慢

现象：CPU 60%、内存充足、磁盘和网络都闲，但 P99 从 50 ms 涨到 200 ms，且与流量不成比例——流量涨 20%，延迟涨 4 倍。
假设：① 负载不均，60% 是平均值而某几个核已满；② cgroup CPU 配额限流；③ 锁竞争；④ 缓存/内存带宽饱和。

[量饱和度，不是利用率] runqlat-bpfcc 10 1 → P99 = 48 毫秒。与 200 ms 的 P99 量级相符，方向对了。 [排除 ①] mpstat -P ALL 1 看每核 → 都在 55%–65%，没有单核打满。 [验证 ②] cgroup v2 的限流计数器是决定性证据： $ cat /sys/fs/cgroup/<service-path>/cpu.stat nr_periods 184203 nr_throttled 91847 <- 一半的周期都被限流了 throttled_usec 4128390215 → 不是机器没 CPU，是配额不让用。 [为什么「60%」会被限流] CFS 配额按周期（默认 100 ms）发放，而服务是多线程的： 几个线程在周期开头并行跑，很快把整个周期的配额一次性用光， 剩下几十毫秒整个 cgroup 全部被冻住——平均利用率确实只有 60%， 延迟却已经被打成了锯齿。 [修复] ① 提高 quota；② 或缩短 period 让配额发放更平滑； ③ 更根本的是让线程数与配额匹配（配额 2 核就别开 32 个工作线程）。
「CPU 利用率不高」是最容易骗人的指标。 利用率是平均值，延迟由饱和度决定。这个 case 里三个指标同时存在：利用率 60%（看起来健康）、runqueue 等待 48 ms（严重排队）、限流一半周期（根因）。多线程服务 + CFS 配额是这类「平均值健康、尾延迟灾难」的经典组合。机制见 进程调度 §3 CFS。
Case 4 · 高峰期客户端大量连接超时，网卡计数器却干干净净

现象：每天两个高峰时段客户端报连接超时和偶发 RST，重试后大多成功。服务端 ethtool -S 无丢包、CPU 与内存正常、应用日志里根本没有这些连接（连 accept 都没到）。
假设：① 中间网络丢包；② 网卡 ring buffer 丢包；③ conntrack 表满；④ 半连接队列溢出；⑤ 全连接队列溢出——应用 accept 太慢。

[先看内核自己的计数器，成本为零] $ nstat -az | grep -Ei 'listen|overflow|syn|drop' TcpExtListenOverflows 18402 0.0 TcpExtListenDrops 18402 0.0 TcpExtTCPReqQFullDrop 0 0.0 → ListenOverflows 在涨 = 全连接队列满，排除 ①②③④，直接命中 ⑤。 这一步花了 5 秒。 [量化队列] ss 的 Recv-Q / Send-Q 在 LISTEN 状态下语义不同： $ ss -lnt 'sport = :8080' State Recv-Q Send-Q Local Address:Port LISTEN 129 128 0.0.0.0:8080 → Send-Q = 队列容量，Recv-Q = 已握手完但还没被 accept 走的连接数。 129 > 128，队列已经溢出。 [找出是谁在设 128] 队列容量 = min(listen() 的 backlog, somaxconn) $ sysctl net.core.somaxconn # 4096，不是它 $ bpftrace -e 'tracepoint:syscalls:sys_enter_listen { printf("%s backlog=%d\n", comm, args->backlog); }' myapp backlog=128 # 应用代码里写死的 [但队列为什么会满] 队列小只是放大器，根因是 accept 跟不上：offcputime 显示 accept 线程阻塞在一次同步的鉴权 RPC 上，高峰期该 RPC 变慢。 [修复] ① backlog 提到 4096（争取缓冲时间）；② 鉴权移出 accept 循环， 改成连接建立后异步做（真正的修复）；③ 给 ListenOverflows 加告警。
① 先读计数器再上探针——nstat 一条命令把五个假设砍到一个，这就是「计数 → 分布 → 事件流」顺序的价值。② 队列满的根因几乎永远在队列之外：调大 backlog 只是给了更多缓冲，真正的问题是消费者慢。只改 backlog 就宣布修复，下一次高峰它会带着更大的队列再来一次。 各层丢包计数器对照见 内核网络栈 §9。
Case 5 · 服务被 OOM 杀掉，但事后完全查不出是谁涨的内存

现象：凌晨三点服务被杀重启，dmesg 里有 OOM 记录。但监控是 30 秒一个采样点，被杀前一个采样点还是正常的——涨得比采样间隔还快，现场已经没了。
假设：① 主服务自己突然分配了大量内存；② 同一 cgroup 里别的进程（定时任务、sidecar）挤爆了配额；③ page cache 顶到上限；④ 内核对象占用。注意：被杀的进程不一定是导致内存不足的那个——内核按 oom_score 挑「杀了最划算」的，通常就是最大的那个。

[承认现场没了，先把网撒下去] 关键不是「怎么查」，而是「下次有没有证据」： → 常驻 OOM 探针（§5.3 第 ⑫ 条），开销约等于零，输出接 logger； → 每 5 秒记一次 cgroup 的 memory.current 与 memory.events； → execsnoop 常驻，记录所有短命进程（这一条是关键）。 [第 5 天再次发生] 三份证据对齐时间戳： → oom-watch：触发者 = batch-importer，不是被杀的主服务； → execsnoop：03:41:02 有一个 cron 起的 batch-importer； → memory.current：03:41:02 之后 12 秒内从 2.1G 涨到 3.9G。 → 三条线索指向同一个进程，因果链闭合。 [根因] 定时任务把一个逐日增长的文件整体读进内存做转换， 而它和主服务在同一个 cgroup 里共用内存配额。 [修复] ① 转换改成流式；② 定时任务放进独立 cgroup 单独限额， 让它自己 OOM 而不拖死主服务；③ 给 memory.events 的 oom_kill 加告警。
核心不是某个工具，而是「常驻的廉价探针」这个模式。低频、高损失、且现场易失的事件——OOM、内核 Oops、短命进程、连接队列溢出——必须提前布网，事后查不出来。 机器整个失联（不是进程被杀）属于 内核崩溃分析 的范畴。

常驻监控临时排障

数据形态
与频率		只做内核内聚合（per-CPU map + 定期读），绝不逐条外送；低频事件优先（OOM、Oops、连接队列溢出、exec）可以外送，但要先在内核里做阈值过滤；高频也行，但限 PID、限时长

10.1 基础（必答）

  1. 基础eBPF 是什么？为什么它能在生产环境上跑，而内核模块不敢？

    eBPF 是在内核里跑一段受限的、经过静态验证的沙箱程序的机制。你把程序编成 BPF 字节码通过 bpf() 系统调用加载，内核 verifier 逐条检查安全性，通过后 JIT 成本机指令，再挂到某个 hook 点（kprobe / tracepoint / XDP / socket filter 等）上，事件发生时同步执行。

    内核模块能做同样的事，但它是完全信任的原生代码：一个空指针解引用就是内核 panic，一个死循环就是整机挂死，一次忘记释放就是内核内存泄漏。而 eBPF 程序在加载阶段就被证明了几件事：

    • 控制流有界：verifier 做的是路径穷举（带剪枝）。早期直接禁止任何反向跳转，5.3 之后允许有界循环（编译期能证明迭代次数上界），后来又加了 bpf_loop() 这类辅助函数把循环交给内核侧执行。目的始终一致——保证程序必然终止，且总指令数有上限（早期 4096，现在放宽到百万级但仍有界）。
    • 内存访问合法：每个指针都有类型和范围，读包数据、读 map 值都必须先做边界检查，verifier 会跟踪寄存器的取值区间，检查不通过就拒绝加载。访问任意内核内存必须走 bpf_probe_read_kernel() 这类可能失败的辅助函数，而不是裸解引用。
    • 资源不会泄漏：map 有生命周期管理，程序不能自己分配任意内存，helper 函数是白名单。

    所以取舍很清楚：eBPF 用"能表达的东西变少"换来了"失败也不会带走内核"。这就是它能在几万台生产机器上常驻的根本原因——加载失败是 bpf_load 返回错误 + 一段 verifier 日志，而不是一次故障。代价是写起来受限（早期连字符串处理都很痛苦），以及 verifier 的报错信息经常很难读。

  2. 基础BPF map 是干什么的？常见类型有哪些，各自适合什么场景？

    map 是 BPF 程序唯一的持久化存储，同时是内核态与用户态之间的共享通道。没有它，探针只能在触发时 printf 一行——那等于把聚合工作全推给用户态，事件量一大就先被自己压垮。有了 map，你可以在内核里就完成聚合，只把结果搬出来，这是 eBPF 开销低的关键设计。

    常见类型与用途：

    • BPF_MAP_TYPE_HASH / ARRAY：最基础的键值对与定长数组。@[comm] = count() 这类按维度聚合就是 hash。
    • PERCPU_HASH / PERCPU_ARRAY：每个 CPU 一份副本，写入无锁无竞争，读取时用户态把各核相加。高频计数器必须用它，否则多核同时更新同一个 map 项会在一条 cacheline 上激烈争用，探针本身就成了瓶颈。
    • LRU_HASH：容量满时自动淘汰最久未用的项。跟踪"每个 socket / 每个请求的开始时间"这类无界键空间时必须用，普通 hash 满了之后 bpf_map_update_elem 直接失败，你会静默丢事件。
    • STACK_TRACE：内核帮你把调用栈存起来并返回一个 id，程序里只需要把 id 当键聚合。这是火焰图和 memleak 的实现基础。
    • PERF_EVENT_ARRAY / RINGBUF：向用户态推送事件流。5.8 之后优先用 ringbuf——它是全局共享的环形缓冲，能保证事件顺序、内存占用不随核数线性膨胀，还支持预留-提交模式减少一次拷贝；perf buffer 是 per-CPU 的，跨核事件顺序无保证。
    • bpftrace 里的 hist() / lhist() 底层也是 map，只是把分桶逻辑封装好了。

    生产视角：选错 map 类型是 eBPF 工具"数据不准"的头号原因——用普通 hash 存 per-request 状态会因为满了而丢数据；用非 percpu 的 map 做高频计数会丢更新（BPF 的 map 更新不是原子读改写，需要 __sync_fetch_and_add 或 percpu）。另外要给 map 设合理的 max_entries：它是预分配的（除非设 BPF_F_NO_PREALLOC），把 max_entries 随手写成一百万会当场吃掉几百 MB 内核内存。

  3. 基础火焰图怎么读？横轴是时间吗？

    横轴不是时间轴，这是最常见的误读。火焰图的横轴是把同一层的相同栈帧合并后按名字排序的结果，所以左右相邻只代表字典序相邻，不代表先后发生。

    正确的读法：

    • 宽度 = 该栈帧在所有采样里出现的比例，也就是"占了多少量"。on-CPU 图里等价于 CPU 时间占比。
    • 高度 = 调用栈深度，自底向上是 caller → callee。
    • 看顶部的平顶：一个宽而平的顶说明 CPU 真的耗在这个函数自身（self time），这是优化的直接目标。
    • 看宽而不平的中间层：说明这个函数自己不慢，但它下面的调用总量很大——通常是"调用次数太多"而不是"单次太慢"，优化方向是减少调用而不是优化实现。
    • 颜色默认无语义（随机暖色，只为区分相邻块）。只有在特意生成的着色方案里才有含义，比如把内核态染成一种颜色、JIT 代码染成另一种。

    要看"什么时候发生"就不能用火焰图，得用 perf sched timehist、Perfetto 这类真正带时间轴的 timeline 视图。这也是火焰图的天生局限：它把整段采样期压平成一张统计图，无法表达偶发毛刺——一个 1% 时间发生的 2 秒卡顿，在 30 秒的火焰图里只有 1% 宽度，很容易被忽略。查毛刺要先用直方图或 timeline 定位时间窗口，再对那个窗口单独采样。

    生产视角：给别人看火焰图时一定要说清采样对象和时长（-F 99 -- sleep 30 意味着约 3000 个样本），样本太少的图不要下结论；差分火焰图（differential flame graph）在做前后对比时比两张图并排看有效得多。

  4. 基础kprobe / uprobe / tracepoint / USDT 四者有什么区别？

    两个维度就能分清：在内核还是用户态，以及动态插入还是静态预埋。

    内核态用户态
    静态预埋tracepointUSDT
    动态插入kprobe / kretprobeuprobe / uretprobe

    机制上：

    • kprobe：在任意内核函数（甚至任意指令地址）上打断点——实现是把目标指令替换成断点或跳转（optimized kprobe 用 jmp 更快），执行到时跳去运行你的程序。能力最强：几乎任何内核函数都能挂，参数从寄存器里读。kretprobe 在返回时触发，用来测函数耗时，但它要劫持返回地址、需要预分配实例（maxactive），并发高时会丢事件。
    • tracepoint：内核开发者在源码里预先埋好的静态点（trace_sched_switch() 之类），关闭时几乎零开销（nop 打桩），开启时参数以结构化的 args 提供。
    • uprobe：同样是断点，但打在用户态二进制的某个偏移上。触发时会有一次用户态到内核态的陷入，所以开销明显高于 kprobe；挂在 malloc 这种超高频函数上足以让程序慢一个数量级。
    • USDT：应用自己用 DTRACE_PROBE 宏预埋的静态点，编译后是一条 nop，探针未启用时开销为零，启用时由 uprobe 机制接管那条 nop。Postgres / MySQL / JVM / Python / Node.js 都内置了，tplist -p <pid> 可以列出来。

    稳定性的取舍是重点：静态点是"契约"，动态点是"实现细节"。tracepoint 和 USDT 由维护者承诺相对稳定；kprobe 挂的是内联可能消失、可能被改名、参数可能重排的内部函数，内核一升级你的工具就可能静默失效或读到错误的参数。uprobe 更脆——符号被 strip、函数被内联、编译器换个版本都会挂。

    所以选择顺序是：有 tracepoint 用 tracepoint，有 USDT 用 USDT，都没有才退到 kprobe / uprobe，并且要意识到后者是"临时排障工具"而不是"长期监控依赖"。

10.2 中级（区分熟练度）

  1. 中级为什么长期运行的监控应该依赖 tracepoint 而不是 kprobe？

    因为kprobe 挂的是内核内部实现，而内部实现没有兼容性承诺。三种失效方式，都很难在上线时发现：

    • 函数消失：被内联、被合并、被重构改名。blk_account_io_start 就是典型——它在若干版本里改过签名也改过是否 inline，一堆抄来的 bpftrace 脚本在新内核上直接加载失败。
    • 参数重排：这最危险。函数还在、加载还成功，但第三个参数从"字节数"变成了"标志位"，你的监控图表依然在出数，只是数字全错。
    • 结构体布局变化：脚本里 ((struct sock *)arg0)->__sk_common.skc_daddr 这种写法依赖字段偏移，字段一挪就读到别的内容。

    tracepoint 的差别在于它是有意暴露的接口：参数以命名字段的形式给出（args->prev_comm），内核社区把它当作面向用户空间的 ABI 来对待，改动会谨慎得多。同时它开启前是 nop，开销也更低。

    如果确实只能用 kprobe，工程上要做三件事把风险降下来：

    • 用 CO-RE 而不是运行时编译：libbpf + BTF 的 BPF_CORE_READ() 会在加载时按目标内核的 BTF 信息重定位字段偏移，所以结构体挪字段不会让你读错——这解决了上面第三类问题，也让一个二进制能跑在不同内核上（不用像早期 BCC 那样在每台机器上带一个 clang 现场编译内核头文件）。
    • 优先挂 fentry/fexit（5.5+，基于 BPF trampoline）：比 kprobe/kretprobe 快得多，且能直接拿到带类型的参数和返回值，验证器还会帮你检查类型。
    • 加"探针健康度"监控：把加载失败、事件计数长期为 0 当成告警条件。一个静默失效的监控比没有监控更危险，因为它会让你在故障时误以为某条链路是干净的。
  2. 中级on-CPU 火焰图和 off-CPU 火焰图分别回答什么问题？

    一个回答"CPU 忙的时候在干什么"，一个回答"不忙的时候在等什么"。任何一次请求的墙上时间 = on-CPU 时间 + off-CPU 时间，只看一半必然漏掉一半问题。

    on-CPU
    按固定频率（如 99 Hz）采样，每次记录当前正在执行的调用栈。采样对象是"时间"，被采到的概率正比于占用 CPU 的时长。适合 CPU 打满、吞吐上不去、算法热点这类问题。工具：perf record -F 99 -g 或 profile-bpfcc、bpftrace -e 'profile:hz:99 { @[ustack] = count(); }'。
    off-CPU
    不是采样而是事件驱动：在 sched_switch 时记下线程离开 CPU 的时刻与当时的栈，在被唤醒回到 CPU 时算出阻塞时长，把这个时长累加到那个栈上。所以横轴宽度是阻塞时间而不是 CPU 时间。适合"CPU 只有 20% 但接口很慢"——等锁、等 IO、等下游、等 runqueue 全在这里。工具：offcputime-bpfcc，或直接用 bpftrace 挂 sched:sched_switch + sched:sched_wakeup。

    关键取舍：off-CPU 的开销远高于 on-CPU。采样是固定频率、成本可预测；off-CPU 是每次上下文切换都要记一次栈，而一台繁忙机器每秒有几十万次切换，栈回溯又是这里面最贵的操作。所以生产上 off-CPU 要限制范围（-p <pid>）、限制时长、并设最小阻塞阈值（只记超过 1 ms 的），否则观测本身就会造成可观的性能下降。

    还有一个坑：off-CPU 图告诉你"我在等 futex"，但没告诉你在等谁。要补上这一步需要 wakeup 火焰图（记录唤醒者的栈）甚至 chain graph（把阻塞栈与唤醒栈拼起来），这才能回答"谁持有那把锁"。生产实践里更常见的组合是：先用 runqlat 排掉调度延迟、用 biolatency 排掉 IO，剩下的再上 off-CPU 定位锁竞争。

  3. 中级perf 采样为什么用 99 Hz 而不是 100 Hz？FP / DWARF / LBR 三种栈回溯怎么选？

    99 Hz 是为了避开锁步（lock-step）。系统里有大量周期性活动本身就是整数频率——内核时钟中断（100 / 250 / 1000 Hz）、定时器、每秒一次的统计任务、应用自己的 1 秒心跳。如果你也用 100 Hz 采样，采样点会稳定地落在这些周期性事件的同一相位上，结果是系统性偏差：要么每次都采到时钟中断处理函数（凭空多出一个热点），要么每次都恰好错过它（一个真实负载完全隐身）。取 99 这个质数让采样相位持续漂移，长期看等于均匀覆盖所有相位。同理，多个采样工具同时跑也应该错开成 97 / 99 / 101。

    栈回溯三种方式：

    FP（frame pointer）
    --call-graph fp，靠 %rbp 链表逐帧回溯。开销最低、栈深度不限，但要求整条调用链都保留了帧指针。问题是 -O2 默认带 -fomit-frame-pointer，发行版的系统库长期是这么编的，于是栈会断在第一个没有 FP 的帧上。解法是自己的代码和关键依赖用 -fno-omit-frame-pointer 编译（成本约 1% 性能，换来永久可 profile 的能力，绝大多数场景很值——Fedora/Ubuntu 近年已经默认打开）。
    DWARF
    --call-graph dwarf，采样时把一段栈内存原样拷出来（默认 8 KB），事后用 .eh_frame 调试信息在用户态展开。优点是不需要 FP，任何二进制都能回溯。代价很大：perf.data 体积暴涨（每个样本几 KB）、perf script 展开极慢、且栈超过拷贝大小就会被截断（深递归、深模板调用栈很容易触发，要调 --call-graph dwarf,65528）。适合一次性深挖，不适合长期采集。
    LBR
    --call-graph lbr，用 Intel 的 Last Branch Record 硬件寄存器。开销极小、精度高，但栈深受硬件限制（通常 16–32 层），深栈会被截。还能顺便做分支/路径分析。适合关注叶子附近的热点，或做 perf record -b 精确定位。

    生产建议：默认目标是让 FP 可用——编译加 -fno-omit-frame-pointer，一劳永逸；临时排查第三方二进制用 DWARF，接受它慢；对采样开销极度敏感的低延迟服务用 LBR。JIT 运行时（JVM / V8）还需要额外的 perf-map agent 把动态生成的代码地址翻译成符号，否则栈里全是十六进制地址。

  4. 中级栈里出现大量 [unknown] 是什么原因？怎么排？

    [unknown] 意味着拿到了地址但翻译不出符号，或者压根没拿到完整的栈。按出现位置分类排查：

    • 内核栈全是 unknown：/proc/sys/kernel/kptr_restrict 不为 0（非 root 看不到内核地址），或者 perf_event_paranoid 太严。设 kptr_restrict=0 并用 root 跑。另一种是内核没带符号表，需要 /proc/kallsyms 可读或安装 kernel-debuginfo。
    • 用户栈只有一两帧然后 unknown：典型的缺失 frame pointer。回溯在第一个 -fomit-frame-pointer 编译的帧断掉。改用 --call-graph dwarf 确认，长期解法是重编带 FP。
    • 符号被 strip：生产二进制常被 strip 以减小体积。装对应的 -debuginfo 包，或保留 .symtab（可以用 separate debug file + debuglink，兼顾体积与可调试性）。静态链接的二进制若 strip 得干净，事后基本无法恢复。
    • 容器 / 进程已退出：这是很容易踩的一类。符号解析发生在 perf report 阶段，而不是采样阶段——如果采样时的进程已经退出，或者二进制在容器的另一个 mount namespace 里（宿主机路径上不存在），就找不到文件了。解法是采样后立刻在同一环境跑 perf script，或用 perf buildid-cache 把二进制归档，或直接在容器的 namespace 里解析。
    • JIT 代码：JVM / V8 / .NET 动态生成的代码没有 ELF 符号表。需要 perf-map-agent（JVM）或 --perf-basic-prof（Node.js）生成 /tmp/perf-<pid>.map，perf 会读它来翻译。
    • PLT / 尾调用优化：函数被尾调用优化后帧不复存在，栈看起来"跳过"了一层，虽然不显示 unknown 但同样会误导。

    生产视角：可观测性是要提前设计的，不是出事时才想起来。让服务在故障时可 profile 需要三件事在构建期就做好——带 frame pointer 编译、保留或归档 debug 符号（按 build-id 存档）、JIT 运行时挂好 map agent。等到 P99 炸了才发现栈全是 unknown，那次故障基本只能靠猜。

10.3 高级（体现深度）

  1. 高级在容器 / K8s 里跑 eBPF 需要哪些权限？为什么在 Pod 里跑 bpftrace 常常失败？

    因为 eBPF 观测的是整个内核，而容器的全部设计目标是让你只看见自己——两者天然冲突，所以需要一串显式授权。

    需要的权限，按依赖顺序：

    • capability：传统上要 CAP_SYS_ADMIN（等于半个 root）。5.8 之后拆细为 CAP_BPF（加载程序、操作 map）+ CAP_PERFMON（perf / tracing 类探针）+ CAP_NET_ADMIN（网络类如 XDP / tc），最小权限方案应该用这三个而不是 privileged: true。
    • sysctl：kernel.perf_event_paranoid 需要 ≤ 1（采样）甚至 -1，kernel.kptr_restrict=0（看内核符号）。这两个是宿主机级别的，Pod 里改不了。
    • 挂载点：bpftrace / BCC 需要 /sys/kernel/debug（tracefs，取 tracepoint 定义）和 /sys/fs/bpf（bpffs，pin map）。容器默认不挂 debugfs，这是"命令报错找不到 tracefs"的最常见原因。
    • 内核头文件或 BTF：BCC 的老式工作方式要在目标机上现场编译，因此依赖 /lib/modules/$(uname -r)/build——容器里这个路径通常不存在。这也正是为什么要用 CO-RE：有 /sys/kernel/btf/vmlinux 就不需要头文件，一个二进制跨内核可用，容器化部署才现实。
    • seccomp / AppArmor：bpf() 系统调用在很多默认 seccomp profile 里是被禁的，即使 capability 给足了也会 EPERM。

    还有两个语义陷阱，比权限更难发现：

    • PID namespace：探针拿到的 pid 是宿主机（init namespace）的 PID，跟你在容器里 ps 看到的完全不是一套编号。按 PID 过滤时必须先换算，否则条件永远不成立。
    • 符号解析跨 namespace：目标进程的二进制在它自己的 mount namespace 里，你的探针进程看不到那个路径，于是栈解析全 unknown（上一题的最后一类）。

    工程实践：把观测工具做成DaemonSet + hostPID + 最小 capability，共享宿主 PID namespace 从根本上绕开编号换算问题；不要让业务 Pod 自己带 privileged 的调试工具（那等于给每个业务容器开了逃逸面）。Cilium、Pixie、Parca 这些生产级方案都是这个形态。

  2. 高级观测本身的开销和安全边界在哪？怎么保证"查问题不会制造新问题"？

    先说结论：eBPF 安全（不会崩内核）不等于便宜（不会拖慢系统）。verifier 保证的是内存安全和终止性，它完全不保证你不会给一条每秒执行千万次的路径加上一段代码。

    开销来自三处，量级差别很大：

    • 探针本身的执行成本：一次 kprobe + 简单 map 更新在几十到几百纳秒量级。挂在 sched_switch（每秒数十万次）上还能接受；挂在网络收包路径或 malloc 上就是灾难。uprobe 尤其贵，因为每次触发要陷入内核再回来，把 malloc/free 全 hook 住能让程序慢一个数量级——这也是 memleak-bpfcc 要靠采样率来控制成本的原因。
    • 栈回溯：这是单项最贵的操作，尤其 DWARF 方式要拷整段栈内存。off-CPU profiling 之所以危险，就是它在每次上下文切换都做这件事。
    • 事件外送：per-event 推到用户态（ringbuf / perf buffer）比在内核里聚合贵几个数量级，而且用户态消费不及时会丢事件（丢事件本身还会造成误判——你以为问题消失了，其实是数据没上来）。能在内核聚合就绝不外送：用 hist()、count() 而不是 printf()。

    安全边界方面，除了 verifier 的保证，还有几条实际约束要知道：

    • 探针上下文不能睡眠（除了少数 sleepable BPF 场景），也不能调用任意内核函数——helper 是白名单。
    • 递归与死锁风险确实存在：在内存分配路径或锁实现上挂探针，而探针自己又触发了同一路径，内核用 per-CPU 的递归保护挡住（代价是丢事件），但把探针挂在这类核心路径上仍然要极其谨慎。
    • eBPF 的 map 和 JIT 代码占用不可回收的内核内存，早期算在 RLIMIT_MEMLOCK，5.11 之后计入 cgroup 的内核内存。map 开太大会真的把内存吃掉。
    • 加载能力本身是攻击面：能加载 BPF 程序基本等价于能读任意内核内存，历史上也出过 verifier 绕过的 CVE。所以生产上不应该让普通服务账号有 CAP_BPF。

    操作纪律：永远先在预发环境量一遍开销（跑探针前后对比 perf stat 的 IPC 和业务 P99）；生产上探针限定 PID、限定时长、设阈值过滤（只记 > 1 ms 的阻塞）；常驻的监控只用最便宜的形态（tracepoint + percpu map 聚合，比如 OOM 监控这种低频事件）；把"观测工具自身的开销"当成一个需要被监控的指标。在一个已经过载的系统上贸然挂高频探针，是把一次性能事件升级成一次故障的经典方式。

  3. 高级什么时候用 bpftrace，什么时候该上 BCC / libbpf？

    判据是"这段观测逻辑的寿命有多长"，而不是"问题有多复杂"。

    bpftrace · 探索期
    DSL 极简，一行就能出直方图，改一次条件重跑只要几秒。它的价值在迭代速度——排障本质是"假设-验证"的循环，你需要在十分钟里换二十个角度看数据。适合：临时排障、验证某个猜想、把 @[comm] = count() 这类聚合快速做出来。缺点是每次运行都要现场编译（依赖 clang / LLVM，二进制几十 MB）、无法做复杂数据结构、无法长期常驻输出到监控系统。
    BCC · 现成工具 + 中等复杂度
    60+ 个久经考验的工具（biolatency / runqlat / memleak）应该作为第一选择直接用，别自己写。写 BCC 的 Python + C 混合形态适合中等复杂度的一次性工具。但它的运行时模型有硬伤：在目标机上现场编译 BPF 程序，需要内核头文件、启动要几秒、内存占用高，容器化部署很别扭。
    libbpf + CO-RE · 产品化
    要把观测变成长期跑的基础设施就得走这条路：编译期一次性生成 BPF 字节码，借 BTF 做字段重定位，产出一个几百 KB 的静态二进制，无运行时依赖，跨内核版本可用，启动毫秒级。Cilium、Parca、Pixie、以及现在的 bcc/libbpf-tools 都是这个形态。代价是要写 C、要处理 skeleton 和构建链，开发成本明显更高。

    典型的演进路径也印证这个判据：bpftrace 一行验证思路 → 确认这个指标长期有用 → 用 libbpf 重写成常驻 exporter 接进 Prometheus。反过来，一开始就用 libbpf 写一个只跑一次的排查工具，等你编译通过故障早就过去了；而把 bpftrace 脚本塞进生产常驻（还带着 LLVM 依赖和现场编译）迟早会因为内核升级或依赖缺失挂掉。

    补充加分：是否有 BTF 往往是决定性约束。目标机内核带 /sys/kernel/btf/vmlinux（4.18+ 的发行版内核基本都有）才能走 CO-RE；老内核只能退回 BCC 的现场编译模式，这时"能不能产品化"就不是技术选择而是环境限制了。

  4. 高级一个服务 P50 正常但 P99 偶发 2 秒，怎么用这套工具链在一小时内定位？

    方法论优先："偶发的尾延迟" 意味着均值类指标和火焰图都会骗你（1% 的时间在 30 秒采样里只有 1% 宽度）。所以整个流程围绕两件事：先缩小时间窗口，再在窗口内做归因；而且每一步都要用分布而不是均值。

    1. 先分解墙上时间，而不是先猜（5 分钟）。请求慢只有三种可能：在 CPU 上算得慢、在等某个资源、根本没被调度上 CPU。vmstat 1 看 r（runqueue 挤）和 b（不可中断阻塞）；如果 CPU 利用率不高，就基本排除"算得慢"，重点转向后两类。
    2. 用直方图定性，确认量级对得上（10 分钟）。runqlat-bpfcc 看调度延迟、biolatency-bpfcc 看块设备延迟。关键是看长尾桶的量级是否和 2 秒同阶——如果 runqlat 的最大值只有几毫秒，调度就是清白的，别再往那查。同时看 cpu.stat 的 nr_throttled 排除 cgroup 限流。
    3. 抓住"慢的那一次"的现场（15 分钟）。这一步是核心：用 bpftrace 在内核里做阈值过滤，只在超时发生时打印，把事件量从每秒十万降到每小时几条。
    sudo bpftrace -e '
  tracepoint:syscalls:sys_enter_fsync /pid == TARGET/ { @s[tid] = nsecs; }
  tracepoint:syscalls:sys_exit_fsync  /@s[tid]/ {
    $d = nsecs - @s[tid];
    if ($d > 500000000) {                 /* 只关心 > 500ms 的那几次 */
      printf("%s slow fsync %d ms tid=%d\n", strftime("%H:%M:%S", nsecs), $d/1000000, tid);
      print(ustack);
    }
    delete(@s[tid]);
  }'

    把 fsync 换成怀疑的任何 syscall；不确定是哪个就先用 @[probe] = hist(...) 把所有 syscall 的耗时分布打出来，看哪一类有 秒级 的桶。拿到带时间戳的慢事件 + 当时的用户栈，问题基本就定位了。

    1. 如果 syscall 都不慢，就是 off-CPU 或外部依赖（15 分钟）。offcputime-bpfcc -p <pid> --min-block-us 100000 只看阻塞超 100 ms 的栈——等锁、等条件变量、等下游会直接现形。同时用 page-faults / /proc/vmstat 的 thp_collapse_alloc、compact_stall 排掉内存侧的停顿（THP 合并造成秒级 spike 是真实存在的一类）。
    2. 时序对齐做最终确认（10 分钟）。把慢请求的时间戳与 GC 日志、vmstat 采样、探针输出摆在同一条时间轴上。能对齐才叫定位，只是"相关"不叫根因。

    两个容易犯的错值得点出来：一是直接上 off-CPU profiling——它开销大，在一个已经不健康的系统上可能把问题放大；应该先用便宜的直方图排除法。二是拿 30 秒火焰图找偶发毛刺，方向从一开始就错了，火焰图适合回答"整体时间花在哪"，不适合回答"那一次为什么慢"。
