01

NUMA · 是什么 + 为什么重要

NUMA = Non-Uniform Memory Access。简言之：不同 CPU 访问不同内存条速度不一样。

1.1 类比 · 办公室的座位

两个团队（node 0 / node 1）共享一间办公室：各自有本地文件柜，取一次 5 秒；也都能去对方的柜子拿，15 秒。地址空间是统一的——所有人都能访问任何柜子，只是慢 3 倍。这个「慢的那一份」就是 NUMA penalty。

坑 · 云上看到的 NUMA 拓扑可能是假的

  • 客户机里 numactl -H 显示的是 hypervisor 呈现给你的视图：宿主上跨 socket 的两段内存可能被合并成一个 node（你「看不到 NUMA」，却实实在在吃着远端延迟）；也可能被呈现成多 node，但 vCPU 被宿主搬来搬去，绑了等于没绑。
  • 判据只有一条：用 numactl --membind 逐个组合跑同一个微基准，看数字分不分层。拓扑文件是「声明」，延迟是「事实」——只信后者。

怎么测。延迟要用指针追逐：顺序遍历会被硬件预取器完全掩盖，量到的是带宽不是延迟；必须让下一次访存的地址来自上一次的返回值，形成串行依赖链。再把同一个程序放进 numactl 的四种组合各跑一遍——这张 2×2 的表就是本机真实的 NUMA 代价矩阵：

三个不注意就量出噪声的点：① 工作集要远大于 LLC，否则测的是 cache；② 必须用 --membind 而非 --preferred（后者会悄悄回落，把「远端」测成本地）；③ 先关掉 AutoNUMA（3.7），否则内核会在测量过程中把页搬回来。测带宽换多线程流式读写，或直接用 Intel mlc——一条命令打印完整的 node×node 延迟与带宽矩阵。

判据而不是数字：「本地 / 远端」分层明显（≥1.5×）就值得管 NUMA；分层不明显（<1.2×，常见于 SNC 或被压平的虚拟机），绑核绑内存收益有限，优先去查别的瓶颈。先量代价矩阵再决定要不要优化——顺序反了就会出现「照着博客绑了核，性能反而掉了」。

2.2 numastat 的全局计数器 · numa_miss 与 numa_foreign

不带参数的 numastat 打印的是另一套东西：每个 node 自开机以来的分配计数器。它是判断「NUMA 有没有出问题」最直接的一手证据，但六个字段的语义相当绕，绕错了会得出完全反向的结论。

字段（记在 node N 上）严格含义它在告诉你什么
numa_hit打算在 N 上分配，并且成功了正常路径。它应该占绝对多数
numa_miss原本打算在别的 node 上分配，最后落在了 N 上N 替别人背了锅。说明别的 node 内存吃紧，被迫溢出到 N
numa_foreign原本打算在 N 上分配，最后落到了别处N 自己不够用了。这一列高的那个 node 才是问题所在
interleave_hitinterleave 策略下打算在 N 分配且成功只有用了 --interleave 才会动。它是预期行为，不是问题
local_node跑在 N 上的进程，从 N 拿到了内存「访存本地化」的正面指标
other_node跑在 N 上的进程，从别的 node 拿到了内存跨节点分配。注意它不区分原因——可能是内存不够，也可能是策略要求的

三条判读要点，缺一条就会误判

  • ① numa_miss 与 numa_foreign 是同一件事的两面。一次「本地分配失败、溢出到远端」会同时记两笔：在原本想去的 node 记 numa_foreign，在实际落到的 node 记 numa_miss。推论：要定位「谁不够用」，看 numa_foreign 最大的那个 node——很多人会读反成「记了 miss 的那个有问题」。
  • ② 这些是自开机累计值，不是当前状态。跑了半年的机器 numa_miss 有几亿完全正常。正确用法是看速率并换算成比例：numa_foreign / (numa_hit + numa_foreign) 就是本地分配失败率。经验阈值：稳态持续 < 1% 基本无害；持续 > 5% 且在增长，说明某个 node 容量已不足，光靠绑核解决不了。
  • ③ other_node 高 ≠ 内存不够。它高而 numa_foreign 几乎不动，说明跨节点分配是策略造成的（自己开了 --interleave=all，或线程被搬走后继续访问旧页），属预期行为；两者都高才是真的容量不足，这时加内存或缩小实例才是解。

2.3 精确到 VMA · /proc/<pid>/numa_maps

numastat -p 是按段类型汇总的粗粒度视图。要精确回答「哪一段虚拟内存落在哪个 node、用了什么策略」，只有 numa_maps，每行形如 7f2a90000000 bind:1 anon=262144 dirty=262144 N1=262144 kernelpagesize_kB=4。

  • 第 2 列的策略名（default / bind:1 / interleave:0-1）是全系统唯一能直接看到「策略真的挂上去了」的地方，验证 mbind() / numactl 生效就靠它。
  • N0= / N1= 的单位是页而不是字节：上例 262144 × 4 KB = 1 GB 全在 node1。带 huge 且 kernelpagesize_kB=2048 的段是 hugetlb 大页。
  • 最实用的速查：grep -c 'N1=' /proc/<pid>/numa_maps —— --membind=0 之后这个数应该是 0，不是 0 就说明有内存漏到了 node1（常见于绑定前已分配的启动期内存）。

2.4 别忘了设备也有 NUMA 归属

NUMA 亲和性不只关系到 CPU 和内存：PCIe 设备（网卡、NVMe、GPU）也挂在某一个 socket 的 root complex 上，DMA 读写它的环形缓冲区同样有本地 / 远端之分——ring buffer 在 node0 而网卡挂在 node1，收发包路径上每个描述符都要跨互联。

查归属的四个入口 · 判读与陷阱

  • 入口：/sys/class/net/eth0/device/numa_node（网卡）、/sys/block/nvme0n1/device/device/numa_node（NVMe）、nvidia-smi topo -m 的 NUMA Affinity 列（GPU）、/proc/irq/<irq>/smp_affinity_list（中断打在哪些核上）。
  • 返回 -1 表示固件没提供该设备的亲和信息（虚拟机和消费级主板很常见），这时只能实测，不要假设是 node0。
  • 网卡中断的 CPU 亲和、收包队列的内存、处理线程，三者落在同一个 node 才算对齐（机制见 内核网络栈）。多网卡 / 多 NVMe 的服务，正确做法通常是按 node 切成对称的两组实例，而不是起一个大实例再去 interleave。

2.5 一个 myth · "我没绑核 = 没 NUMA 问题"

错。默认的 first-touch 会导致一条几乎必然发生的退化路径：进程单线程启动，init 内存全落 node0 → 随后 spawn 出的一半 worker 被调度到 node1 → 这一半线程此后每一次访存都跨 node。全程不报错、不出现在任何曲线上，只表现为「吞吐比预期低 20–40%」。这就是无意识 NUMA 退化，三条解法（--interleave=all、numa_alloc_local()、让 worker 自己 first-touch）分别在 3.1、3.3、3.5 展开。

NUMA 感知编程

3.1 四种内存策略 · 语义与适用

内核对「一次匿名页分配落在哪个 node」的决定全部收敛到一个叫 mempolicy 的对象上。它只有四种模式，把语义分清，NUMA 编程一半的问题就没了。下图是同一个「要 12 个页、node0 只装得下 8 个」的场景，四种策略各自的落点：

模式 / numactl语义补充（图上没说的）✅ 适用❌ 不适用
MPOL_DEFAULT
不加参数		 严格说是「撤销显式策略、回退系统默认」，溢出按 zonelist 顺序 单 node 装得下、线程与数据天然对齐 主线程预热、线程后建的程序（2.5 的退化路径）
MPOL_BIND
--membind=0		 OOM 之前会先在允许的 node 内触发回收 / 换出 延迟确定性优先、容量已经算清的服务 内存用量会突增的服务——你把「变慢」换成了「被杀」
MPOL_PREFERRED
--preferred=0		 只指定一个首选 node，其余按 zonelist 大多数生产服务的稳妥默认 ⚠️ NUMA 微基准——静默回落会把「远端」测成本地
MPOL_INTERLEAVE
--interleave=all		 匿名内存按虚拟地址轮转、文件 / 共享内存按 offset 轮转，因此可复现 工作集大于单 node、或要吃满整机带宽（大堆 JVM、大模型权重） 延迟敏感的小工作集——把「一半快一半慢」变成「全部中等」

另有 MPOL_LOCAL（Linux 3.8+）是「显式的本地优先」，不会被上层作用域的策略覆盖；较新内核还有「优先多个 node」和为 CXL 分层内存设计的带权轮转，可用性看发行版内核版本。

选择口诀：装得下就 --membind；装不下或要吃满带宽就 --interleave；拿不准就 --preferred（不会把性能问题升级成可用性问题）。唯一不该有的选择是「什么都不设，期待默认策略帮你做对」——它只保证「本地优先」，保证不了线程和数据在同一个 node。

3.2 set_mempolicy 与 mbind 的区别

策略有两个挂载点，这是最容易混淆的一处。对应两个系统调用——一个绑线程，一个绑地址区间：

#include <numaif.h>
unsigned long mask = 1UL << 0;      /* nodemask：只用 node 0 */

/* ① 绑「调用线程」：此后该线程发起的所有匿名分配都走这个策略 */
set_mempolicy(MPOL_BIND, &mask, 8);

/* ② 绑「一段 VMA」：只影响这段地址，与哪个线程访问无关；优先级高于 ① */
mbind(p, SZ, MPOL_INTERLEAVE, &mask2, 8, MPOL_MF_MOVE);
/*                                        ★ 不加这个 flag 就只管未来的分配 */
set_mempolicy(mode, nodemask, maxnode)mbind(addr, len, mode, nodemask, maxnode, flags)
作用对象调用线程本身（task policy）一段虚拟地址区间（VMA policy）
影响范围此后该线程发起的所有匿名分配只影响这段地址，与哪个线程访问无关
生命周期跟线程走，新线程继承创建者的策略跟 VMA 走，fork 后子进程继承，munmap 后消失
优先级低高——VMA 策略存在时压过 task 策略
能否迁移已有页不能，只影响未来的分配默认也不能；要迁移必须显式加 MPOL_MF_MOVE
典型用法worker 启动时设一次，之后所有分配自动本地化对某个大数组单独指定 interleave，其余保持本地

优先级链是 VMA 策略 > 线程策略 > 系统默认。numactl 本质上就是「先 set_mempolicy，再 exec」——它对整个进程生效，也因此无法给不同线程设不同策略。

坑 · mbind 默认不搬已经分配的页

  • malloc + memset 之后再 mbind(..., 0)，这段代码什么都没改变：memset 时物理页已按 first-touch 落定，不带 flag 的 mbind 只约束「以后」。这是新手最常写错的一处，而且它不报错。
  • 要真的搬就加 MPOL_MF_MOVE（只搬独占页）或 MPOL_MF_MOVE_ALL（连共享页，需 CAP_SYS_NICE）；MPOL_MF_STRICT 能让「有页不符合策略」变成显式报错。另外两条路是 migrate_pages(2) 和 move_pages(2)（后者也是查询页所在 node 的标准 API）。
  • 迁移不是免费的：每页都要 unmap、拷贝、重建映射、刷 TLB。正确做法永远是一开始就分对，迁移只是救火手段。

3.5 First-touch 原则 · NUMA 编程最反直觉的一条

如果这一页你只记一件事，就记这条：决定物理页落在哪个 node 的，不是「谁调用了 malloc」，而是「谁第一次写了这个页」。

malloc / mmap 返回的只是一段虚拟地址区间。物理页要等到第一次访问触发缺页时才分配，走的是「当前 CPU 的本地 node 优先」。分配动作和放置决定被解耦到两个时间点、两个可能不同的线程上——这是所有「无意识 NUMA 退化」的总根源。

严格说是 first-write-touch。对匿名私有内存，第一次读只把页表项指向内核的全局零页，不分配物理页也不产生 node 归属；只有第一次写才触发写时复制、真正落定 node。所以大块 calloc 不会 touch（直接走 mmap，本来就是零），malloc + memset 会全部 touch。文件页 / 共享内存不同：第一次读就在读者所在 node 上分配 page cache 页。

不要相信推理，直接测。下面这个程序把上图钉死：同一块 buffer 由两个绑在不同 node 的线程各写一半，再用 move_pages(2) 逐页查询真实落点。

/* firsttouch.c —— gcc -O2 -pthread firsttouch.c -lnuma -o firsttouch */
#define _GNU_SOURCE
#include <numaif.h>
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#define PGSZ  4096
#define NPAGE 8                       /* 前 4 页给线程 A，后 4 页给线程 B */

static char *buf;
struct arg { int cpu, from, to; };

/* nodes 传 NULL 时 move_pages 不迁移，只把每页当前所在 node 写回 status[] */
static int node_of(void *p)
{
    void *pg[1] = { p };  int st[1] = { -1 };
    move_pages(0, 1, pg, NULL, st, 0);
    return st[0];
}

static void *toucher(void *a)
{
    struct arg *g = a;
    cpu_set_t set;  CPU_ZERO(&set);  CPU_SET(g->cpu, &set);
    pthread_setaffinity_np(pthread_self(), sizeof(set), &set);
    for (int i = g->from; i < g->to; i++)
        buf[(size_t)i * PGSZ] = 1;    /* ★ 第一次写 → 缺页 → 落定 node */
    return NULL;
}

int main(void)                        /* 跑之前先 sysctl -w kernel.numa_balancing=0 */
{
    buf = aligned_alloc(PGSZ, (size_t)NPAGE * PGSZ);   /* 一个字节都别碰！ */

    /* cpu 号按 numactl -H 的输出改：a 取 node0 的核，b 取 node1 的核 */
    struct arg a = { .cpu = 0, .from = 0, .to = 4 };
    struct arg b = { .cpu = 8, .from = 4, .to = 8 };
    pthread_t ta, tb;
    pthread_create(&ta, NULL, toucher, &a);  pthread_join(ta, NULL);
    pthread_create(&tb, NULL, toucher, &b);  pthread_join(tb, NULL);

    for (int i = 0; i < NPAGE; i++)
        printf("page %d -> node %d\n", i, node_of(&buf[(size_t)i * PGSZ]));
    return 0;
}

对照实验就是全部结论：加一行看起来无害的 memset（或任何「预热」「清零」），整块内存的 node 归属就被主线程一次性决定了。生产里这一行常常不是你写的——它藏在容器基类的构造函数里、arena 初始化里、框架的 --pretouch 选项里。

陷阱 · 透明大页会把 first-touch 的粒度放大到 2 MB

THP 开启时，一次缺页决定整个 2 MB 的归属。分片边界没按 2 MB 对齐，边界那个大页就整块落到「先到的线程」那边。症状是「明明做了 first-touch，numa_maps 里还有一小部分页在对面」。修法：分片起止按大页尺寸对齐，或对该区域 madvise(MADV_NOHUGEPAGE) 换取放置精度。

3.6 正确的多线程 init 模式

把「谁先碰」交给真正要用它的那个线程

  • ❌ 反模式：data = malloc(LARGE); memset(data, 0, LARGE); spawn_workers(data); —— 所有页 touch 在主线程的 node 上，一半 worker 全程远端。
  • ✅ 正确：malloc 之后一个字节都不碰，让每个 worker 在自己的线程里 memset(data + my_start, 0, my_len) 清零属于它的那一段。这是 OpenMP / TBB / 自研线程池的性能优化第一原则。
  • ⚠️ 前提是后续访问的分片和 first-touch 的分片一致。运行期用 work-stealing 时线程会去偷别人的分片，first-touch 的努力被抵消一部分——这种场景 --interleave=all 反而更稳。

3.7 AutoNUMA · 内核替你搬页和搬线程

first-touch 只在「分配时就知道谁会用」的前提下有效，真实负载常常不满足。于是内核内置了一套运行期自动纠偏机制 AutoNUMA（NUMA balancing）——它默认开启，很多人不知道自己一直在用它。

AutoNUMA 像办公室里一个勤快的行政：他定期溜一圈，看到你老去对面团队的柜子取文件就把那批文件搬到你旁边；搬文件不划算（太多、好几个人都在用）就干脆把你的工位挪过去。问题是他溜一圈和搬东西时，你得停下手上的活让路。

  • 关它的判据是两条同时成立：① 已用 --membind / cpuset.mems 显式绑定（此时 AutoNUMA 只剩采样开销）；② 你关心的是 P99 而不是均值。

HugePages · 大页内存

HugePages = 用 2MB / 1GB 替代默认 4KB page · 减 TLB miss · 大内存程序的标配优化。

4.1 为什么需要大页

TLB（Translation Lookaside Buffer）是 CPU 缓存「虚拟页 → 物理页」翻译结果的地方，容量硬件写死：现代 x86-64 大致是 L1 dTLB 几十项（4 KB 与 2 MB 各有独立项）、L2 统一 TLB（STLB）约 1500–2000 项，1 GB 页往往只有十几个专用项。具体数字每代都不同，用 cpuid 或厂商优化手册确认，别照抄。

关键不是「页变大了」，而是同样多的 TLB 项能覆盖多少内存——以及一次 miss 要走几级页表：

大页的收益不取决于内存有多大，取决于「工作集 / TLB 覆盖范围」这个比值。工作集 4 MB 的服务在 4 KB 页下 TLB 已全覆盖，上大页毫无收益、只多担碎片和抖动的风险。判据：perf stat -e dTLB-load-misses,dTLB-load-misses.walk_duration 看走页表花了多少周期，超过总周期 5% 才值得动手。

4.3 两种模式 · 显式 vs 透明

Explicit HugePages（hugetlb）由管理员提前预留一个池，应用用 mmap(MAP_HUGETLB) / hugetlbfs 显式取用，稳定可控但要 reserve、不够时分配失败；Transparent HugePages（THP）由内核自动尝试给 2 MB 页，应用无感知，但有 collapse 带来的性能尖刺。

「一个自动一个手动」这种概括不够用——两者在可换出性、记账方式、失败模式上是完全不同的东西，选错了会在生产上表现成两类截然不同的故障。

/proc/meminfo 那组字段要分清：HugePages_Total 是池里一共几个、_Free 是还没被 fault 进来的、_Rsvd 是已被 mmap 承诺但还没 fault 的、_Surp 是临时借的。Hugetlb不在 MemAvailable 里；AnonHugePages 则是 THP 的用量，和 hugetlb 池毫无关系——这两个最容易被混着看。

应用侧取用三条路：① mmap(..., MAP_PRIVATE|MAP_ANONYMOUS|MAP_HUGETLB, -1, 0)，长度必须是大页尺寸的整数倍，返回 MAP_FAILED（ENOMEM）就是池不够，必须写回落到 4 KB 的分支；② 默认尺寸不是 1 GB 时显式加 MAP_HUGE_1GB；③ open("/mnt/huge/pool") 后普通 mmap(MAP_SHARED)，可跨进程共享。

验证「进程真的用上了」—— 这一步最容易被跳过

  • hugetlb 不计入 RSS，只在 status 的 HugetlbPages 和全局 meminfo 看得到——VmRSS: 512 MB 而 HugetlbPages: 2 GB 完全正常。THP 用量看 smaps_rollup 里 AnonHugePages 占 Rss 的比例。
  • Free 不降但 Rsvd 涨说明「已预定、还没开始用」，内核先扣配额保证以后 fault 不 SIGBUS，不是配置没生效。Free - Rsvd 才是「真正还能给新进程用的量」。
  • 容器里走 hugetlb controller，K8s 对应 hugepages-2Mi。Pod 不声明这个资源就拿不到大页，哪怕宿主机预留了一大池。

4.6 坑 · 大页分配失败会静默回落到 4 KB

这是 THP 最需要警惕的一条：它失败的时候什么都不说。凑不出连续块（或 defrag 不允许就地规整）就直接退回 512 个 4 KB 页——程序照跑、日志干净、监控无告警，唯一的变化是你以为拿到的那 20% 吞吐提升根本不存在。跑了几周的机器必然碎片化，「开机命中率 95%、两周后掉到 40%」是典型曲线。

验证方法只有一个：数分配与回落的比例——grep thp_ /proc/vmstat，命中率 = thp_fault_alloc / (thp_fault_alloc + thp_fault_fallback)；回落数是成功数的 3 倍，命中率就只有 25%，进程侧 AnonHugePages / Rss 应该和它对得上。

三种「看起来配了其实没用上」

  • THP 静默回落：enabled=always 但 AnonHugePages 远小于 Rss，根因是碎片。缓解是提高 vm.min_free_kbytes 给规整留空间，或改用 explicit HugePages 开机把内存拿到手。
  • THP 设成 madvise，但应用没调 madvise：最容易发生的「人为静默」——改了 sysfs 就以为生效，其实没有任何一段内存符合条件。看 thp_fault_alloc 几乎不动即可确认。
  • hugetlb 预留了但对不上 node：预留的 2048 个全落在 node0，服务却绑 node1，mmap(MAP_HUGETLB) 返回 ENOMEM——更糟的是程序没检查返回值。hugetlb 按 node 满足，池的分布必须和绑定一致。

更凶的一种：SIGBUS 而不是回落

  • hugetlbfs 映射（或 MAP_HUGETLB | MAP_NORESERVE）在 mmap 时可能不扣配额，等写入触发 fault 才去池里取。池空 → 没有 4 KB 可以回落（这段 VMA 的页尺寸就是 2 MB，语义上不允许降级）→ 只能发 SIGBUS。症状是「服务跑得好好的，某次写入直接崩，dmesg 什么都没有」。
  • 预防：不要用 MAP_NORESERVE，让内核在 mmap 时就扣住配额（体现为 HugePages_Rsvd 上涨），把失败提前到启动阶段。同一机制也解释了 hugetlb + fork 的风险——子进程 COW 要新大页，池空同样 SIGBUS。

4.7 khugepaged 的时延尖峰 · 讲透这一条

「关 THP 因为 khugepaged 会 stall 应用」到处都能看到，但它把三种不同的停顿混成了一种。要在面试和排障里分清，必须知道停顿发生在哪把锁上。

khugepaged 周期性醒来扫一批页，把「某个 2 MB 对齐区间内已有足够多 4 KB 页在用」的地方合并（collapse）成大页：分配 2 MB 连续块（可能触发规整甚至回收）→ 取该进程 mm 的写锁 → 拷贝 512 个页 → 建 PMD 映射、刷 TLB → 释放旧页。第二步最狠：mmap_lock 写锁会阻塞这个进程里所有需要读锁的线程，而缺页处理、mmap / madvise 全都要读锁——collapse 期间只要碰到一次缺页就得排队。所以「THP 停顿」实际是三种：

停顿类型发生在哪观测计数器处方
① 缺页路径上的同步规整 业务线程自己的缺页处理里，内核在当前上下文就地做 compaction compact_stall defrag 改成 defer：拿不到就立刻回落 4 KB，规整丢给后台 kcompactd
② khugepaged 合并停顿 被 mmap_lock 写锁挡住，或被 TLB shootdown 的 IPI 打断 thp_collapse_alloc pages_to_scan 调小、scan_sleep_millisecs 调大；彻底解决就 enabled=madvise
③ 拆分（split）停顿 内存压力下要换出、或 COW 需要更细粒度时拆回 4 KB thp_split_pmd 本质是「内存不够了」，处方是降水位或缩小工作集，不是调 THP 参数

/sys/kernel/mm/transparent_hugepage/ 下是两组正交的旋钮，很多人只知道 enabled，其实 defrag 往往才是尾延迟的关键：

参数含义调大 / 调小的后果
enabledalways / madvise（仅 MADV_HUGEPAGE 区域）/ never生产稳妥值是 madvise——保留能力，交出决定权
defrag缺页拿不到大页时，是否在当前上下文同步规整always = 最高命中率 + 最差尾延迟；defer = 立刻回落、后台补齐，低延迟服务的正确选择
khugepaged/pages_to_scan每轮扫多少个页调大 → 收敛快、单次持锁久；调小 → 尖峰变矮变密
khugepaged/scan_sleep_millisecs两轮扫描之间睡多久调大 → 干扰变少，但已碎片化的区域长期拿不到大页
khugepaged/alloc_sleep_millisecs分配失败后退避多久再试调大 → 碎片严重时不再反复做无用的规整尝试，排障时很有用
khugepaged/max_ptes_none一个 2 MB 区间里最多允许多少「空洞」还愿意合并调大 → 稀疏区域也被合并，内存放大严重（只用几十 KB 却占 2 MB）
khugepaged/max_ptes_swap区间里最多允许多少页已被换出调大 → 合并时要先换回来，把 IO 拉进关键路径

什么时候关 THP · 以及「关」的正确含义

  • DB / Redis / 交易系统的推荐配置就两行：enabled=madvise + defrag=defer。持久化写成 systemd unit 或 tuned profile，不要放 rc.local——它在部分发行版上的执行时机晚于业务服务启动，等于没设。验证同样是看计数器停止增长，不是看开关。
  • Postgres / MongoDB / Redis / Cassandra / Oracle 都建议不要用 always：它们自己管理 buffer pool，访问模式稀疏，THP 的内存放大和停顿收益比很差。
  • 「关 THP」不等于「放弃大页」，这是最常见的误解。正确表述是把决定权从内核手里拿回来：需要的那几段自己 madvise(MADV_HUGEPAGE)，或用 explicit HugePages 开机把连续内存拿到手。
  • 反面场景：HPC、批处理、大堆 JVM 这类「吞吐优先、用量稳定」的负载，always 才是对的。同一台机器跑数据库该关、跑计算该开——取决于你优化均值还是分位数。
  • Redis 的 fork：THP 下写一个 4 KB 页要复制整个 2 MB，单靠调 khugepaged 参数解决不了，必须 never 或 madvise。

slab / buddy / vmalloc · 内核内存分配器

用户态 malloc 底层是 brk / mmap。内核态自己有 3 个分配器 — 知道这些能更好理解 /proc/slabinfo 等观测数据。

5.1 3 个分配器对比

三者严格分层，不是三个并列选项：buddy 分配大块连续物理页（4 KB ~ 4 MB，2 的幂）是唯一的物理页来源；slab / SLUB 从它批发页再切成小对象（dentry / inode / task_struct 等）；vmalloc 也从它逐页拿，映射成虚拟连续但物理不连续的大块——慢且占 TLB，能不用就不用。

5.2 看 slab 占用 · 从 slabtop 到泄漏定位

⚠️ drop_caches 是调试手段，不是修复手段

sudo slabtop -o -s c 按占用排序，最常见的是 dentry 与 ext4_inode_cache 涨到几百 MB 到 GB 级——系统说「内存紧张」，实际上是 cache。此时 drop_caches 会把热元数据一次清空，换来一波缺页与重读风暴；它唯一的正当用途是做基准测试前对齐初始状态。要长期压低元数据缓存，调 vm.vfs_cache_pressure。

排障时直接读 /proc/slabinfo 更有用，因为它给出每个 cache 的对象尺寸和打包密度——那才是判断「对象太多还是单个对象太大」的依据：

5.3 slab 泄漏的排查路径

「slab 涨爆」有三种，第一步必须先分清，否则方向全错：

✅ 多数情况 · 可回收的缓存

SReclaimable 在涨，主角是 dentry / *_inode_cache。内核在正常缓存文件元数据，压力一来自动回收。涨到几 GB 也不是故障。

🔥 真问题 · 不可回收的对象

SUnreclaim 单调上涨，或某个具体 cache（kmalloc-*、skbuff_*）持续增长且重启业务后不降。这才是内核对象泄漏。

⚠️ 记账到了容器头上

slab 按 cgroup 记账，某容器的元数据缓存把自己顶到 memory.max。进程 RSS 很小却被 OOM，见下。

四步定位，以及不重启也能查的两条路

  • ① 分类：grep -E '^(Slab|SReclaimable|SUnreclaim)' /proc/meminfo，只盯 SUnreclaim 的趋势。② 找元凶：slabtop -o -s c。③ 看明细：/sys/kernel/slab/<cache>/ 下的 objects / slabs / partial。
  • ④ 打开 SLUB 分配点追踪（最有用、最少人知道的一步）：启动参数加 slub_debug=U,<cache名>，重启后读 alloc_calls 与 free_calls，两边一减就知道「哪个调用点分配了却没人释放」。不重启就用 kmem:kmem_cache_alloc/free 两个 tracepoint 按栈聚合做差。
  • 按业务动作二分：最有效的往往不是工具而是对照实验——停掉某个定时任务 / 探针 / 某类请求，看 SUnreclaim 斜率变不变。内核对象泄漏几乎总能对应到一个具体的用户态行为（频繁 mount、频繁建销 cgroup、大量短命 socket、遍历海量小文件）。

容器场景的一个真陷阱：slab 会计入 cgroup

较新内核里内核对象按 cgroup 记账。一个只用 500 MB 堆的容器，可能因为遍历几百万个小文件把 dentry cache 堆到几 GB，撞上 memory.max 被 OOM——症状极具误导性：进程 RSS 很小，容器却被杀。缓解：调高 vm.vfs_cache_pressure、减少不必要的路径遍历、或给 limit 留余量。drop_caches 是全机生效的，多租户宿主上别用它救单个容器。

5.4 buddy 与外部碎片 · 水位和 order

slab 涨爆是「用得多」，buddy 的问题是「凑不出连续块」——空闲内存总量可能很充足，但没有一个 2 MB 对齐的连续区间。这直接决定了 THP 能不能用上、驱动的高阶 DMA 缓冲能不能申请到。

  • 可用总量要自己算：Σ (count × 2^order × 4 KB)。上图 order 0 那 18422 个页 ≈ 72 MB 全是零散的，加总可能有几百 MB「空闲」，却一个 2 MB 块都拿不出来。这就是「内存够但分配失败」的全部含义。
  • 更细的视图是 /proc/pagetypeinfo，按迁移类型分开列。Unmovable 的块散布在各个 order 上，说明碎片是「结构性」的——compaction 搬不动它们。
  • 分配失败的现场在 dmesg：page allocation failure: order:4, mode:0x40cc0(GFP_KERNEL|__GFP_COMP)。GFP_KERNEL 说明它可以睡、做过回收和规整还是失败，碎片是真严重；换成 GFP_ATOMIC 含义完全不同——不允许睡眠，失败往往只是瞬时水位不足。
  • 水位在 /proc/zoneinfo：free 跌破 low → 唤醒 kswapd 后台回收（便宜）；跌破 min → 分配线程自己做直接回收，那就是同步停顿。

三个旋钮和它们的真实作用

  • vm.min_free_kbytes 抬高 min 水位。价值不在「多留点空闲」，而在于给 compaction 留腾挪空间、给原子分配（网卡收包就在用 GFP_ATOMIC）留储备。大内存机器默认值常偏小。
  • echo 1 > /proc/sys/vm/compact_memory 手动触发全局规整。它本身会造成停顿，别放业务高峰或定时任务。
  • vm.vfs_cache_pressure / vm.swappiness 影响回收时「先丢元数据、页缓存还是换出匿名页」。改之前先确认瓶颈真在回收侧——大部分「内存问题」其实是容量问题。

5.5 vmalloc · 为什么"能不用就不用"

vmalloc 的存在只为一件事：你需要一大块连续的虚拟地址，但系统已经凑不出同样大的连续物理内存。它逐页向 buddy 要 order-0 页（这部分几乎总能成功），然后在内核的 vmalloc 地址区间里找一段空洞，逐页建立页表映射。

  • 观测入口是 /proc/vmallocinfo，每行都带调用者符号（如 xfs_buf_alloc+0x1d1/0x3a0 pages=512 vmalloc N0=512）——某个模块泄漏时这里会出现同一符号的大量条目。总量看 VmallocUsed。
  • 为什么慢：逐页分配 + 逐页建页表，成本与大小成正比；释放要 TLB flush；而且 vmalloc 区只能 4 KB 映射，内核线性映射区通常已被大页覆盖——所以它额外消耗 TLB 项，比同样大小的 kmalloc 内存更容易 miss。
  • 绝对不能用于 DMA：物理不连续，设备看到的是不连续的物理地址。需要 DMA 走 dma_alloc_coherent()。
  • 一个容易忽略的日常用户：内核栈。开了 CONFIG_VMAP_STACK 的内核用 vmalloc 分配每线程的内核栈（栈溢出会撞守护页立刻 panic 而不是静默踩坏邻居）。所以线程极多的系统里 VmallocUsed 线性上涨是正常的。

5.7 RSS 不等于真实占用

这一节讲的是全站最高频的一类误判：拿 top 里的 RSS 当作"这个进程占了多少内存"，然后基于它做容量规划、判断泄漏、设置容器 limit。三件事全会错。

RSS 的严格定义是「当前映射在该进程页表里的物理页总量」。这句话里埋了两个坑：① 一个物理页被 N 个进程映射，就在 N 份 RSS 里各算一次；② 没映射进页表的内存（未 mmap 的 page cache、hugetlb 大页、内核替它分配的对象）一个字节都不算。所以 RSS 既会重复计数也会漏计，两个方向的误差同时存在。
指标定义共享页怎么算适合回答什么问题
RSS 页表里映射的物理页总量 每个进程全额算一遍 「这个进程能直接访问多少物理内存」。❌ 不能跨进程相加
PSS（Proportional） 私有页全算 + 共享页按共享进程数摊分 按份数平摊 唯一可跨进程求和的指标。容量规划、算「每个实例真实成本」用它
USS（Unique） Private_Clean + Private_Dirty，只算独占的页 不算共享页 「杀掉它能立刻收回多少」。OOM 决策与容器瘦身用它
Private_Dirty 独占 且已被写过的页 不算共享页，也不算只读文件页 最接近「这个进程自己造出来的内存」。查泄漏看它的趋势
Shared_Clean 与别人共享、未修改（共享库代码段、只读文件映射） — RSS 虚高的主要来源，也是内存压力下最先被丢弃、代价最低的部分

拿数据最快的方式是 /proc/<pid>/smaps_rollup——一次给出全进程汇总，不用解析上千段 smaps。除了 Rss / Pss，还有 Shared_Clean、Private_Dirty、LazyFree（MADV_FREE 标记但还没被回收，见第 6 章）、AnonHugePages、SwapPss（换出部分也要摊分）。排序找大户直接用 sudo smem -k -s pss -r。

误判 ① 共享库导致的重复计数 —— 最常见的一种

16 个 worker 各自 RSS = 800 MB，加起来 12.8 GB，机器只有 8 GB 却跑得很好。不是监控坏了：一份 libstdc++、一份模型权重、fork 后尚未写过的 COW 页，在每个进程的 RSS 里都被完整算了一遍。推论：按 RSS 设 limit 会浪费掉一大半预算，按 RSS 判断「谁该杀」会选错对象——该看 USS。

误判 ② 不在 RSS 里的那些内存

「所有进程 RSS 加起来对不上 MemTotal - MemAvailable」，差额通常藏在：

  • explicit HugePages：完全不计入 RSS，只在 HugetlbPages / 全局 Hugetlb 里；预留了就占住，哪怕没人在用。最大的一个「隐形黑洞」。
  • 页表本身（PageTables，见 4.2）、内核替进程分配的对象（每线程约 16 KB 内核栈、task_struct、socket 缓冲区）。
  • tmpfs / /dev/shm（记在 Shmem，只有 mmap 进来的部分才进 RSS）、read() 产生的 page cache、GPU / DMA pinned 内存，三者都不体现在任何进程的 RSS 里。

误判 ③ RSS 不降 ≠ 泄漏

  • 两个常见原因：MADV_FREE 标记的页在没有压力时一直留着（LazyFree，jemalloc / tcmalloc 默认就这么干）；或分配器把内存留在自己的 arena 里没还给内核。先用 malloc_stats() / jemalloc 的 stats.* 区分二者——前者调 decay 参数，后者改代码。
  • 判泄漏要看趋势不看快照：把 Private_Dirty（或 cgroup 的 anon）按天画曲线。稳定上涨且与流量无关才是泄漏；随流量涨跌只是水位；file / cache 贴住上限完全正常。

陷阱 · 高频采集 smaps 本身就是性能问题

读 smaps 要持 mmap_lock 遍历全部 VMA 并逐页统计；对一个几万映射段、几十 GB 的进程，一次读取可能几百毫秒，期间该进程所有缺页处理都在排队。真实事故：监控 agent 每 10 秒采一遍，业务 P99 出现规律的 10 秒周期毛刺——观测本身成了干扰源。做法：改用 smaps_rollup，采集周期放到分钟级，容器里优先读 memory.stat。

三句话记住选哪个：算成本用 PSS（可相加），查泄漏用 Private_Dirty（趋势），决定杀谁用 USS（真能收回）。RSS 只适合回答「这个进程现在映射着多少物理页」这一个字面问题——而这个问题在生产上其实很少有人真正想问。

madvise(addr, len, advice) = 告诉内核"我打算怎么用这段内存"·内核根据 advice 优化（preread / 提前 swap / 用大页 / 不要 swap 等）。

  • 「我明明 free() 了，为什么 RSS 不降？」——大概率是分配器用了 MADV_FREE，内存已可回收、只是没人来收。jemalloc 可调 dirty_decay_ms / muzzy_decay_ms 控制归还节奏。

6.2 mlock / mlockall · 锁定物理内存不被 swap

接口只有三个：mlock(addr, size) 锁一段、mlockall(MCL_CURRENT | MCL_FUTURE) 锁当前与未来的全部内存、munlock() 解锁。典型场景是实时系统 / 金融交易——不能容忍 swap 带来的延迟 spike。前置条件是 RLIMIT_MEMLOCK 默认极小，要 ulimit -l unlimited 或给二进制 CAP_IPC_LOCK；而且锁太多内存等于系统可分配的变少，反而可能 OOM 掉别的进程。

6.3 优先用 MCL_ONFAULT · 以及 mlock 的四层代价

mlockall(MCL_CURRENT | MCL_FUTURE) 是很多低延迟教程的标配写法，但代价常被低估：

  • 启动被拉长、RSS 立刻打满：MCL_FUTURE 意味着后续每次 mmap 都要在返回前把页真正分配并填充，「按需分配」的省内存效果全部消失。
  • 被 RLIMIT_MEMLOCK 卡住：不放开直接 ENOMEM；容器里还要确认 runtime 透传了这个 limit，这一步经常漏。
  • 锁住的页对整机不可回收也不可迁移：同时加剧外部碎片并抬高别人被 OOM kill 的概率——你为自己买了确定性，代价摊给同机的其他进程。
  • fork 会放大：子进程继承锁定，锁定量可能瞬间翻倍。

更好的默认：MCL_ONFAULT

  • Linux 4.4+ 的 MCL_ONFAULT（单段用 mlock2(..., MLOCK_ONFAULT)）语义是：不预先填充，但一旦某页被 touch 进来就再也不会被换出——保留按需分配的省内存特性，同时拿到「已在内存里的页不走 swap」这个真正想要的保证。
  • 很多场景根本不需要 mlock：vm.swappiness=1 加上不配 swap 已能解决九成换出问题，成本低得多。真要用的场景一般还会同时配 explicit HugePages + 绑核 + 中断隔离——它是一整套确定性方案里的一环，单独上收益有限。

OOM killer + cgroup v2 memory

7.1 OOM killer 工作机制

物理内存 + swap 都满、且回收无效时，内核遍历所有进程算 oom_score，选最高的 SIGKILL，并在 dmesg 留下完整现场。评分函数 oom_badness() 比想象的简单——基础分几乎就是「你占了多少内存」：points = rss + swap_entries + pgtables_bytes/PAGE_SIZE + oom_score_adj × totalpages / 1000（前三项单位都是页）。

  • 所以 oom_score_adj 的单位是「整机（或 cgroup）内存的千分之几」，-1000 被特殊处理成「必然为 0」，等价于豁免。
  • 它不看进程活了多久，也不看 nice、不看是不是 root（老内核曾按 nice 和 root 身份调整，早已移除）。纯粹「谁胖谁死」。
  • pgtables 被计入是个容易忽略的细节：映射了巨量 4 KB 页的进程，光页表就能让它显著更容易被选中（见 4.2）。
  • 杀的粒度是整个 thread group，之后由 oom_reaper 异步回收地址空间，所以「被杀了但内存没马上回来」是正常的。

用 systemd 设置 memory limit（最常用）

  • unit 里四行就够：MemoryMax=4G（硬上限）、MemoryHigh=3G（软上限，开始 throttle）、MemoryLow=2G（系统紧张时保护）、OOMScoreAdjust=-500，然后 systemctl daemon-reload && systemctl restart。

7.5 max / high / low / min 的行为差异

上面那张表列的是文件名，真正会踩坑的是「超过之后内核具体做什么」——四个旋钮里只有一个会杀进程：

memory.max · 硬上限 会（cgroup OOM） 按峰值 + 余量。它是「最后一道墙」，不是日常工作点
memory.high · 节流阀 永不杀 设在 max 之下留缓冲（如 80%），让内核先把内存压回去、给告警留窗口

7.6 memory.pressure（PSI）· 唯一能量化"内存压力"的指标

利用率类指标（memory.current、MemAvailable）回答的是「用了多少」，回答不了「这件事有没有在伤害我的延迟」。PSI（Pressure Stall Information）就是为这个问题设计的：它直接统计任务因为等内存而停下来的时间比例。读 <cgroup>/memory.pressure（全局版本是 /proc/pressure/memory，格式相同），拿到的是两行 some / full，各带 avg10 / avg60 / avg300 / total：

字段含义判读
some至少有一个任务因内存压力被阻塞的时间百分比「有没有压力」的灵敏指示器。持续 > 10% 说明它已经在吃你的延迟
full所有非空闲任务都被阻塞——整个 cgroup 完全停摆持续 > 0 就已经很糟：有整段时间这个 cgroup 一点活都没干
avg10 / avg60 / avg300最近 10 / 60 / 300 秒的滑动平均avg10 抓尖峰、avg300 判趋势，告警用 avg60 不容易抖
total累计阻塞微秒数做差算速率接进时序监控

PSI 的价值在于把「内存不足」翻译成了时间成本，可以直接和延迟 SLO 对齐：memory.current 长期贴着上限但 PSI 几乎为零的容器是健康的（cache 贴满而已）；用量只到 60% 但 some avg60 常年 20% 的容器是有病的。（需要 CONFIG_PSI，部分发行版还要加启动参数 psi=1。）

7.7 "内存没满却疯狂回收"的六个成因

这是容器化环境里最常见的一类疑难：memory.current 离 memory.max 还有距离，甚至 top 里进程 RSS 很小，但服务延迟劣化、IO 暴涨、PSI 高企。先用两个文件定性，再对号入座。

  • memory.events 给出四个累计事件计数：high / max / oom / oom_kill。high 巨大而 oom_kill 为 0 = 一直在被节流，没被杀。
  • memory.stat 挑六个字段：anon / file / slab 看构成；pgscan 与 pgsteal 看回收效率（扫 8.9 亿页只回收到 1200 万页 = 1.4%，纯属做无用功）；workingset_refault_file 持续增长说明刚回收掉又被读回来，回收错了对象。

这两个信号加上 PSI，构成「疯狂回收」的完整证据链。六个常见成因：

成因特征 / 判读处方
① memory.high 比工作集低
最常见的一个		 一越过就在每次返回用户态前插入回收 + 睡眠惩罚，进入「贴着 high 反复被节流」的稳态。high 计数巨大而 oom_kill 为 0 把 high 抬到工作集之上，或不设只留 max。别把节流阀当成「目标用量」
② limit 只按 anon 峰值算 memory.current 包含 page cache，limit 卡在匿名峰值上 cache 就待不住。「内存没超但 IO 暴涨」，workingset_refault_file 飞涨 limit = anon 峰值 + 依赖的 cache 量。cache 顶到贴住上限是正常的，别为此告警
③ slab 按 cgroup 记账 遍历海量小文件把元数据缓存堆到 GB 级（见 5.3）。进程 RSS 很小，容器却在回收甚至被杀 看 slab_reclaimable；调 vm.vfs_cache_pressure 或给 limit 留余量

⑤ 没设 memory.low 宿主紧张时全局回收按比例索取，没保护的容器和跑批任务平等受压。回收与自身负载无关，却和别的容器同步 memory.low ≈ 常驻工作集
⑥ tmpfs / /dev/shm 不可丢弃 Shmem 计入 memory.current 却没有后备文件，只能换出；禁了 swap 就完全不可回收 看 memory.stat 的 shmem 与 OOM 日志的 shmem-rss；中间结果改落磁盘
排查这一类问题的固定顺序：memory.events（是节流还是被杀）→ memory.pressure（有没有真的伤到延迟）→ memory.stat 的构成（anon / file / slab / shmem 谁在涨）→ pgscan 与 workingset_refault（回收是否在做无用功）。看总量曲线永远得不出结论，因为 memory.current 把可回收和不可回收的东西加在了一起。

5 个真实优化 case

Case 1 · Java 服务 NUMA 优化 · 吞吐 +35%

背景：双 socket Xeon · 32 GB heap JVM · 默认部署 · 吞吐不达预期。

[Day 1] numastat -p <jvm-pid>: → 内存 18 GB on Node 0, 14 GB on Node 1 [Day 1] bpftrace 看 GC thread 跑哪： → 8 个 GC thread 一半在 Node 0, 一半在 Node 1 [修复] systemd: ExecStart=numactl --interleave=all /usr/bin/java ... [结果] 吞吐 +35% · GC pause -20%

根因：32 GB heap 装得进单 node，理论最优是全本地绑定；但这是吞吐型服务，钉死单 node 等于只用一半的核。所以 --interleave=all 才是正解——把「一半线程全程远端」换成「所有线程各有一半远端」，牺牲均值换掉长尾。GC pause 改善得比吞吐更明显：GC 线程要遍历整个 heap，原先总有几个在扫远端 region，而 STW 时长由最慢的那个决定。

两个 JVM 特有的坑：① -XX:+AlwaysPreTouch 启动时把整个 heap 写一遍，正是 3.5 的 first-touch 陷阱，必须和 numactl 策略一起考虑；② 部分 GC 有自己的 NUMA 感知选项（按 node 切 eden），和外部的 --interleave 互相抵消，同时开等于让 JVM 和内核抢方向盘。

Case 2 · Postgres 性能 spike · 元凶 THP

背景：Postgres P99 偶有 500ms spike · DB 自身 metric 正常。

[Day 1] bpftrace 看哪个 syscall 慢: → spike 时 mmap / madvise 慢 [Day 1] 看 /proc/vmstat: → thp_collapse_alloc 频率高 (kcompactd 在合并 page) [修复] echo madvise > /sys/kernel/mm/transparent_hugepage/enabled echo defer > /sys/kernel/mm/transparent_hugepage/defrag [结果] P99 spike 消失

根因分辨：4.7 讲的两种停顿这里都在，但主犯是缺页路径上的同步 compaction而不是 khugepaged——判据是 compact_stall 的增长速率与 P99 毛刺时序完全对齐，而 thp_collapse_alloc 量级小一个数量级。这个区分重要在处方不同：同步规整靠 defrag=defer 解决，khugepaged 停顿靠 enabled=madvise 解决。两条都改了，真正起作用的是前者。

复盘：改 madvise 而不是 never，是因为 Postgres 的共享内存本身能受益于大页；更彻底的做法是给 shared_buffers 配 explicit HugePages。另外compact_stall 之所以那么高，前提是这台机器已经跑了几周、高度碎片化——同样的配置在刚重启的机器上复现不出来，这正是这类问题难查的根本原因。

Case 3 · 推理服务 (vLLM) NUMA 退化

背景：LLM serving (70B INT4 在 4 张 H100) · throughput 比官方 benchmark 低 30%。

[Day 1] numactl --hardware: → 4 张 H100 分 Node 0 (GPU 0,1) + Node 1 (GPU 2,3) [Day 1] nvidia-smi topo -m: → 显示 GPU 跟 NUMA 关系 [Day 2] 跟踪 model loading: → CPU 内存全在 Node 0 · GPU 2/3 的 DMA 跨 node [修复] 分两个 worker process · 各 numactl --cpunodebind 各自 node [结果] throughput +28% 接近 benchmark

根因：GPU 是 PCIe 设备，挂在某个 socket 的 root complex 下（见 2.4）。H2D 传输走 DMA，源地址是 CPU 侧的 pinned 内存——内存在 node0 而 GPU 挂在 node1，每次权重加载、每批 token 的 KV 搬运都要先跨 UPI 再上 PCIe，而互联本来就是最窄的一环，于是 H2D 带宽先饱和、GPU 反而在等数据。确认方式：nvidia-smi topo -m 的 NUMA Affinity 列对上 numastat -p 的内存分布，两边不一致就是问题。

复盘：关键决策是「拆成两个进程」而不是「加 --interleave」——interleave 会让两张卡都变成「一半本地一半远端」，把好的一半和坏的一半平均掉；按 node 拆成对称两组，每组的 CPU、内存、GPU 全部本地，才是这类「设备也有归属」场景的通解。多 GPU / 多网卡的服务，实例划分粒度应该跟着硬件拓扑走，而不是跟着 CPU 核数走。

Case 4 · 容器 OOM 但监控里 memory.current 只有 6/8 GB

背景：K8s Pod 设 limits.memory=8Gi · Grafana 上 memory.current 稳定在 6 GB · 每天凌晨被 OOMKilled 一两次（退出码 137）。

[Day 1] dmesg 看 constraint: → CONSTRAINT_MEMCG · 整机还有 40 GB 空闲 → 不是全局 OOM [Day 1] memory.events: high = 0 · max = 1841 · oom_kill = 3 → 没设 memory.high = 完全没有节流缓冲带，一超限直奔硬墙 [Day 1] memory.stat 看构成（不要看总量！）: → anon 2.1G · file 0.7G · shmem 3.2G · slab 0.2G → shmem 是 /dev/shm 的中间结果，无后备文件 → 只能换出 → 而 memory.swap.max = 0 → 这 3.2 G 完全不可回收 [Day 2] 采集周期 30s 降到 1s 重跑: → 凌晨批量任务期间 尖峰到 8.0 G，持续约 4 秒，30s 采样抓不到 [根因] 可回收的只有 0.7 G file cache，批量任务让 anon 短时涨 3 G [修复] /dev/shm 中间结果改落磁盘 · memory.high=6.5G + 告警 · 监控改采 memory.events 计数（事件不会被采样漏掉）

它同时踩了三个常见误判：① 把 memory.current 当容量指标——可回收的 file 和不可回收的 anon / shmem 被加在一起；② 用采样指标监控瞬时事件——OOM 由几秒的尖峰触发，正确做法是监控累计事件计数；③ 以为 /dev/shm 和写文件差不多——禁了 swap 就等于把 tmpfs 变成永久占用。

Case 5 · 高频交易系统 · 锁定内存 + 大页 + 隔核

背景：交易延迟敏感 · 不能容忍 page fault / TLB miss / 调度抖动。

[组合优化] ① mlockall(MCL_CURRENT | MCL_FUTURE) → 永不 swap ② mmap with MAP_HUGETLB (1GB hugepage) → TLB miss → 0 ③ isolcpus=2,3 内核启动参数 → CPU 2,3 不参与调度 ④ sched_setaffinity 绑 worker 到 CPU 2,3 ⑤ numactl --membind 匹配 CPU 的 NUMA node [结果] 延迟 P99 从 200us → 12us · 抖动 -95%

为什么必须是「一整套」：P99 由最慢的那条路径决定，只要还剩一个抖动源，前面消掉的都白费。五项各堵一个——mlockall 堵 swap-in（毫秒级）、大页堵 TLB miss 与缺页（微秒级）、isolcpus 堵调度抢占（数十微秒）、绑核堵核间迁移的 cache 冷启动、--membind 堵远端访存。做四项拿不到 80% 收益，只能拿到「最差那一项决定的」收益——这是延迟优化和吞吐优化最本质的差别。

还得补两件事：关 AutoNUMA（已显式绑定，它只剩采样开销和迁移抖动）、关 THP 或设 madvise（都用上 1 GB 大页了，khugepaged 后台合并只会引入 mmap_lock 争抢）。另外 isolcpus 只挡普通任务，中断要单独赶到非隔离核，否则一个网卡中断就能打穿 12 µs 的预算。

代价：这台机器基本变成单用途设备——1 GB 大页预留后其他进程一律用不到，mlockall 的内存不可回收不可迁移还加剧碎片，隔离核对整机利用率是净损失。只有当延迟本身就是产品价值时，这笔账才算得过来。

分层自测

10.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础什么是 NUMA？Linux 默认的 first-touch 策略为什么会让多线程程序"无意识退化"？

    NUMA 指的是内存控制器挂在 CPU 上而不是挂在一条共享总线上：每个 socket（node）有直连的内存通道，访问别的 node 要过 UPI 再由对方的内存控制器代取。地址空间仍然统一，程序不改也能跑——只是慢。

    关键在于物理页是缺页时才分配的，而默认策略是 first-touch：哪个 CPU 触发缺页，页就落在那个 CPU 所属的 node。典型退化路径：主线程 malloc 大 buffer 并 memset 清零，此时只有主线程在跑，页全落 node0 → 随后 spawn 出的 worker 一半被放到 node1 → 这一半线程访问的每个字节都在对面。

    这类退化不报错、不出现在任何利用率曲线上，只表现为「吞吐比预期低 20–40%」。修法要么让 worker 自己 first-touch 属于它的那一段，要么启动时 --interleave=all 摊平。malloc 只返回虚拟地址，正是这一点让 first-touch 优化成为可能。

  2. 基础拿到一台陌生机器，怎么用 numactl 和 numastat 判断有没有 NUMA 问题？

    numactl --hardware 看拓扑，重点是 node distances：对角线固定 10，非对角线是相对代价（21/10 = 2.1 即远端约慢一倍），四路机器会出现 10 / 21 / 31 的多级距离。同时记住哪些 CPU 号属于哪个 node，超线程的兄弟核号通常跨了一大段。

    numastat -p <pid> 看落点，判读方式是把内存分布和线程分布对着看：内存 88% 在 node1、而 ps -Lo psr 显示线程大量在 node0 的核上，才是明确的跨节点访存。要精确到哪一段 VMA 就读 numa_maps。

    还有一个容易忽略的信号：不带参数的 numastat 里 numa_foreign 持续增长，说明本地分配已失败并被迫落到远端——通常意味着某个 node 内存被占满，光靠绑核解决不了。

  3. 基础跨节点访存的代价到底有多大？为什么 top 和利用率曲线看不出来？

    同一代 Xeon 大致是：L1 约 1 ns、L3 约 10 ns、本地 DRAM 约 80 ns、远端 150–200 ns。加分点是把延迟与带宽分开说：延迟只慢 1.6–2.2 倍，但多线程压满时远端带宽可能只剩本地的 25–35%，这解释了「单线程微基准才慢 1.7 倍、上线压测却掉 40%」。

    看不出来是因为「等内存」在 CPU 记账上算作忙：核没让出，流水线只是在等 load 返回，top 照样 100%。利用率是「占用时间」不是「有效工作量」。要证据就看 perf stat 的 insn per cycle——IPC < 1 基本可定性为 memory-bound，再用 node-load-misses 拿远端访存比例。

    所以「CPU 打满但加机器无效」必须先排 NUMA——你加的是 CPU，缺的是本地带宽。测的时候要用多线程基准 + --membind（--preferred 会静默回落，把远端测成本地）。

  4. 基础HugePages 和 THP 有什么区别？各自适合什么场景？

    目标一样——用 2 MB / 1 GB 页替代 4 KB，减少页表层级和 TLB 表项数；获取方式完全不同。100 GB 工作集用 4 KB 是 2500 万个页，TLB 必然崩；2 MB 页只有 5 万个，TLB miss 率能从 5–15% 降到 1% 以内，吞吐 +10–30%。

    Explicit HugePages
    按 node 预留一块连续物理内存池，用 mmap(MAP_HUGETLB) 或 hugetlbfs 显式取用。特点是确定：拿到就永远是大页，不会被拆、不会被换出、不参与 reclaim。代价是预留的内存别人一律用不了，拿不到时分配直接失败（必须处理这个错误路径）。1 GB 大页只能开机预留。
    Transparent HugePages
    内核缺页时尝试给 2 MB 页，或由 khugepaged 后台合并（collapse）已有的 4 KB 页，应用零改动。代价是不确定：合并、以及为合并腾地方的 compaction 都可能在关键路径上引入停顿，还有内存放大（只用 8 KB 也占住 2 MB）。

    选择：吞吐优先、用量稳定（HPC、批处理、JVM 大堆）→ THP always 最省事；延迟敏感或分配模式碎片化（数据库、Redis、交易系统）→ THP 设 madvise，需要大页的地方用 explicit HugePages 精确拿。注意「关 THP」不等于「放弃大页」。

10.2 中级（区分熟练度）

  1. 中级为什么 Postgres / MongoDB / Redis 都建议关掉透明大页？

    因为 THP 把一件本来可以后台慢慢做的事塞进了应用的关键路径，而数据库对尾延迟零容忍。三条机制：

    • 分配路径上的同步 compaction：缺页时要 2 MB 对齐的连续块，碎片化的机器上内核会在缺页上下文里做规整——这就是 compact_stall，一次普通的写内存变成几十甚至几百毫秒。
    • khugepaged 的合并停顿：后台 collapse 要取 mmap_lock 写锁、迁移数据、刷 TLB，对应 thp_collapse_alloc。
    • COW 放大：Redis 靠 fork 做 RDB，父进程写一个 4 KB 页在 THP 下要复制整个 2 MB——写放大 512 倍。

    判读证据是 grep -E 'thp_|compact_' /proc/vmstat：compact_stall 持续增长 + P99 毛刺基本可定性。处方是 enabled=madvise + defrag=defer（而不是一律 never）。加分点：这不是「THP 不好」，而是吞吐优化与尾延迟的经典冲突——同一台机器跑 HPC 该开、跑数据库该关。

  2. 中级buddy 和 slab 分配器的分工是什么？内存碎片和 compaction 又是怎么回事？

    分工是两级：buddy 管页，slab 管页里的小对象。

    buddy allocator
    内核唯一的物理页来源，按 2^order 个连续页分配。要 order-3 而没有现成的，就把 order-4 块劈成两半（互为 buddy），释放时若 buddy 也空闲就合并回去。这个「劈-合」结构天然抗外部碎片，但只在页粒度上有效。
    slab / SLUB
    task_struct、dentry、skb 只有几十到几百字节，每个都去 buddy 要一整页就浪费到荒谬。SLUB 从 buddy 批发页、切成同尺寸对象缓存，并做 per-CPU 无锁 fast path，兼顾内部碎片与 cache 局部性。

    外部碎片指「空闲页总量够，但凑不出连续的高阶块」，看 /proc/buddyinfo 的高阶列是否全为 0。后果不只是 THP 用不上：网卡的 jumbo frame 缓冲、驱动要的 order-4 DMA 缓冲都会失败，dmesg 留下 page allocation failure: order:4。

    compaction 是解法：把 MIGRATE_MOVABLE 的页从 zone 一端往另一端搬，腾出连续空洞。这也解释了内核为什么按可移动性给页分组——内核数据结构和 slab 页搬不动，混在中间就永久破坏连续性。它有 kcompactd 后台（便宜）和分配路径同步（compact_stall，很贵）两条路径，主动 compact_memory 本身也会造成停顿，别放业务高峰；长期方案是提高 vm.min_free_kbytes 给规整留空间。

  3. 中级madvise 常用的建议值有哪些？MADV_DONTNEED 和 MADV_FREE 的区别是什么？

    madvise 是把应用掌握、内核猜不到的访问模式告诉内核。常用几档：MADV_SEQUENTIAL / MADV_RANDOM 调 readahead 窗口；MADV_WILLNEED 异步预取用于预热；MADV_HUGEPAGE / NOHUGEPAGE 在 THP 设为 madvise 时精确控制哪段用大页；MADV_COLD / MADV_PAGEOUT 把一段标成冷数据。

    DONTNEED 是立即的、语义可见的：马上解开页表映射、释放物理页，RSS 当场下降；匿名内存下一次读拿到全零页——数据真的没了，它是语义操作而不是建议。FREE 是延迟的、语义不可见的：只打个标记说「内容我不要了，地址还归我」，有压力时内核直接丢弃（不写 swap，很便宜），没压力时页一直留着，读到的仍是原来的数据。

    取舍：FREE 省掉「释放-再缺页」的来回，分配释放高频时快得多，这是 jemalloc / tcmalloc 默认偏好它的原因。代价是 RSS 不会立刻下降，造成经典误判「我明明 free() 了，为什么 RSS 不降？」。另一个坑：在 cgroup 里 FREE 的页仍计入 memory.current，曲线一直贴着上限，但逼近 memory.max 时会先被回收、不导致 OOM。

  4. 中级mlockall 的代价是什么？什么情况下才值得用？

    mlockall(MCL_CURRENT | MCL_FUTURE) 把进程所有页锁在物理内存里，买到的是确定性：消除 swap-in 的毫秒级停顿和首次访问的 major fault。但代价有四层，面试要能全部说出来：

    • 启动被拉长、RSS 立刻打满：MCL_FUTURE 意味着每次 mmap 都要在返回前把页真正分配并填充，「按需分配」的省内存效果全部消失。
    • 被 RLIMIT_MEMLOCK 卡住：默认极小，不放开就 ENOMEM；容器里还要看 runtime 是否透传。
    • 锁住的页对整机不可回收也不可迁移：加剧外部碎片并抬高别人被 OOM kill 的概率——你为自己买了确定性，代价摊给同机的其他进程。
    • fork 放大：子进程继承锁定，锁定量可能瞬间翻倍。

    生产做法：优先 MCL_ONFAULT（Linux 4.4+）——只锁实际被访问过的页，保留按需分配的省内存特性。而且很多场景根本不需要 mlock：vm.swappiness=1 + 不配 swap 已能解决九成换出问题。真要 mlock 的场景一般还会同时配 explicit HugePages + 绑核 + 中断隔离——它是一整套确定性方案里的一环，单独上收益有限。

10.3 高级（体现深度）

  1. 高级OOM killer 是怎么打分选受害者的？oom_score 和 oom_score_adj 什么关系？

    核心函数 oom_badness() 比想象的简单：基础分几乎就是「你占了多少内存」——points = rss + swap + pgtables + oom_score_adj × totalpages / 1000。所以 oom_score_adj 的单位是「整机内存的千分之几」，-1000 被特殊处理成分数必然为 0，等价于豁免。注意它不看进程运行多久、也不看 nice（老内核曾按 nice 和 root 身份调整，早已移除）——纯粹「谁胖谁死」。

    三个必须说清的细节：杀的粒度是整个 thread group（cgroup v2 可设 memory.oom.group=1 把整组一起杀）；oom_score_adj 会被子进程继承（服务设了 -900，它 fork 出的批处理任务也免死）；选中后由 oom_reaper 异步回收地址空间，「被杀了但内存没马上回来」是正常的。

    陷阱：不要给所有重要服务都设 -1000。全局 OOM 时内核找不到可杀的候选，结果不是「大家都活着」，而是整机进入 reclaim livelock，事实上死机。正确做法是分层：只给运维通道设 -500 ~ -900 保住「还能登上去看一眼」，业务进程靠 cgroup 隔离把问题限制在自己的 cgroup 里。

  2. 高级cgroup 的 memory.max 触发的 OOM 和全局 OOM 有什么区别？memory.high 又是什么行为？

    三件事完全不同，混在一起讲就会得出「容器明明没满却被杀」这种错误结论。

    全局 OOM
    物理内存 + swap 真的不够，受害者从全机进程里按 oom_badness 挑——你的服务可能因为邻居失控而被杀。dmesg 里有完整的 zone 快照，constraint=CONSTRAINT_NONE。
    memory.max（硬上限）
    cgroup 内部的局部事件：先只在这个 cgroup 内回收，回收不出来才在该 cgroup 范围内选进程杀——整机可能内存充裕、其他容器毫无感知。K8s 的 limits.memory 映射到这里，退出码 137。
    memory.high（软上限）
    永不杀进程。超过后内核在返回用户态之前插入正比于超额量的主动回收 + 睡眠惩罚。表现是「CPU 没打满、没有 OOM 记录，但延迟整体劣化」——很难查，因为常规指标都正常。

    判读入口是 memory.events（high 上万而 oom_kill 为 0 就是被节流）和 memory.stat 的构成。关于「memory.current 看着没满却被 OOM」：它包含可回收的 page cache，贴着上限跑本身正常，真正决定生死的是 anon + 不可回收的 slab / shmem；反过来把 limit 卡在 anon 峰值上，会让 cache 被反复回收，出现「内存没超但 IO 暴涨」。

    工程建议：memory.high 设在 max 的 80% 留缓冲，让内核先 throttle 把内存压回去、给监控留告警窗口；memory.min / low 则反向使用，保护必须留住工作集的服务。

  3. 高级如何定位一个服务的内存到底花在哪？RSS / PSS / page cache / slab 怎么分？

    方法是自外向内逐层收敛，每层先回答「是不是这一层的问题」再往下钻，不要一上来就挂 profiler。

    1. 整机层 /proc/meminfo：看 MemAvailable 而不是 MemFree。AnonPages 大 → 用户态堆；Cached 大 → page cache，通常无害；Slab 大 → 看 SReclaimable / SUnreclaim；Committed_AS 远超物理内存 → overcommit 风险。
    2. cgroup 层 memory.stat：容器化环境下这才是权威口径，它按 cgroup 归属重新算了一遍 anon / file / slab / sock。
    3. 进程层 smaps_rollup：一次读出全进程汇总，比逐段解析 smaps 快很多，也不会因为持 mmap_lock 拖慢业务。

    关键区别：RSS 把共享页在每个进程里都算一遍，一堆 worker 的 RSS 加起来会远超实际用量；PSS 按份数摊开，是唯一能跨进程求和的指标。查「到底是谁占的」用 Private_Dirty——它排除了共享库和文件映射的干净页。

    再往里分类深挖：堆内用 jemalloc 的 prof / memleak-bpfcc（生产友好，开销约 5%），但要先确认是「分配器持有未归还」还是「应用真的没释放」；内核对象用 slabtop -o 找具体 cache；不在 RSS 里的部分最容易漏——explicit HugePages、PageTables、GPU pinned / DMA 内存、Shmem、socket buffer、MADV_FREE 未回收的页。

    判泄漏要看趋势而不是快照：把 Private_Dirty 或 cgroup 的 anon 按天画曲线，稳定上涨且与流量无关才是泄漏。

  4. 高级要在一台双路机器上部署常驻 100 GB 内存的服务，你会怎么配置，又怎么验证配置生效了？

    先做一个决策，再落五项配置，最后用四条证据验证。顺序不能反——先量拓扑，别照抄别人的参数。

    决策：能不能装进单个 node。能装下就「钉死一个 node」（--cpunodebind=0 --membind=0），再起第二个实例钉 node1，天然对称；装不下（或要吃满整机带宽）就 --interleave=all，牺牲一半访存换确定的平均带宽——「稳定的中等」优于「运气决定的好或极差」。

    五项配置：

    • 内存策略 + 绑核一起给：只绑核不绑内存等于没做。容器里用 cpuset.cpus + cpuset.mems，比 taskset 可靠，新线程自动继承。
    • 大页：100 GB / 4 KB = 2500 万页，必须上。按 node 预留而不是全局预留；1 GB 大页只能开机参数配。
    • THP 设 madvise，需要的地方用 MADV_HUGEPAGE，避免同步 compaction 打进关键路径。
    • cgroup 限制：memory.max 按峰值 + 余量，memory.high 设其 80%；memory.swap.max=0 或 vm.swappiness=1。
    • 失败面控制：运维通道设 OOMScoreAdjust=-500，业务进程不滥设豁免；开 memory.oom.group 让多进程服务整体重建。

    四条验证证据（「配了」≠「生效了」）：① numastat -p + grep -c 'N1=' numa_maps（membind=0 时应为 0）；② HugePages_Free 明显下降 + 进程 AnonHugePages 有量；③ perf stat -e node-loads,node-load-misses,instructions,cycles——远端访存比例与 IPC 是唯一能证明「NUMA 优化有效」的硬指标；④ memory.events 无隐性节流、compact_stall 不增长。

    收尾方法论：一次只改一项，压测对比，留下数字。三组参数互相影响（预留大页会加剧碎片，进而影响 THP），一起改完只会得到「好像快了」这种无法复现的结论。上线后把 numastat -p 与 memory.events 纳入例行巡检——扩容、内核升级、邻居变化都可能让配置悄悄失效。
