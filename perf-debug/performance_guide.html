01

引言

性能优化方法论金字塔

性能优化不是堆 trick。真正的性能工程是分层：先测量，再从算法往下走到微架构；编译器是最后一层免费加速。

1.1 几个思维误区

  1. 凭感觉优化 — 直觉热点与真实热点重叠率通常 < 30%
  2. 优化所有热点 — 真热点只有 1–3 个
  3. trick 总是更好 — 循环展开、手写 SIMD，现代编译器经常已经做了
  4. STL 总是慢 — 多数场景 vector / unordered_map 已经够快；慢在用法
  5. 汇编最赚 — 给好数据布局 + -O2 -flto，比内联汇编更稳

1.2 本章涵盖什么

  • 测量 → 建模 → 定位 → 优化 → 验证
  • CPU / 缓存 / 分支 / 分配器 / 锁 / 编译器
  • perf 与火焰图；5 个生产案例只留模式，不复述代码
02

测量先行

性能优化的三大法则

2.1 三大法则

法则 1: 测量, 不要猜

没有 profiling 数据就不要优化。「你以为的热点」与真实热点重叠率常常 < 30%。

法则 2: 优化前定基线

改前记一笔，改后再比。看不到 ≥ 5% 改进就回退——那是噪音。

法则 3: 优化用户感知的指标

p99 / QPS / 资源，而不是单次 nanosecond。30 ms 用户感觉不到，100 ms → 1 s 才是体验悬崖。

法则 4: 20/80

20% 代码吃 80% CPU。只打这 20%；其余慢 10× 也无所谓。

2.2 标准优化流程

  1. 定义目标：p99 < 50 ms / QPS > 10000 / 内存 < 1 GB
  2. 基线：当前值 + 测试条件
  3. profiling：perf record → 火焰图，只盯 top 3
  4. 假设 + 单变量实验 → 对比基线 → 提交或回退 → 上线监控

2.3 微基准 — Google Benchmark

Google Benchmark 自动找稳定迭代、用 DoNotOptimize 防 DCE、报告均值/标准差。完整文件和十坑见 §15；这里不贴样板工程。

2.4 容易被忽略的测量原则

  • warm-up：第一次有冷缓存，先 burn-in
  • 固定频率：关 turbo，governor = performance
  • 测分布：单次 ±20% 噪音正常；小样本不可信
  • 防 DCE：DoNotOptimize / ClobberMemory

缓存层次 · L1/L2/L3 与缓存友好编程

Cache line · 时间/空间局部性 · 行优先 vs 列优先

5.1 缓存层次（典型 Intel Skylake）

5.2 Cache Line

Cache line：缓存与 DRAM 之间的基本搬运单位，x86/ARM 主流 64 字节。读 1 字节也会拉整行。

5.3 缓存友好的两个原则

① 时间局部性

刚用过的还会再用。处理完一块再切下一块，不要东一榔头西一棒。

② 空间局部性

相邻地址一起访问。连续容器（vector），别用链表；访问模式顺序化。

5.4 经典例子：行优先 vs 列优先

C 数组按行存放：外 i 内 j 是顺序；外 j 内 i 每次跳一整行（N=4096 时步长 16 KB，远超一条 line）。图画完了，不必再贴两层循环。

5.5 Cache 友好的容器

容器友好度原因
vector / array★★★★★单块连续
deque★★★分段连续
list / map★ / ★★节点散落
unordered_map / absl::flat_hash_map★★ / ★★★★拉链 vs 开址连续
规则：默认 vector。N < 1000 时几乎总是赢过 list / set——缓存比大 O 更先说话。
06

False Sharing 假共享 ★ (并发性能杀手)

Cache line ping-pong · alignas(64) · padding

6.1 问题

两个变量被不同核写，却落在同一 cache line → MESI 让这一行在核间来回作废。逻辑上无共享，物理上在打架。

两人合住一间房：你只改自己的抽屉，室友也得把整间房腾空重装——因为「房间」才是搬运单位。

6.2 重现

逻辑上各写各的 counter，多线程却比单线程还慢——典型假共享。

6.3 解决：cache line 对齐

❌ 两个 counter 挤一条 line
struct Counters { std::atomic<long> a, b; };
Counters g;                    // 通常同一 64B
// Core0 写 g.a，Core1 写 g.b
✅ alignas / hardware_destructive_interference_size
struct Padded {
    alignas(std::hardware_destructive_interference_size)
    std::atomic<long> v;
};
Padded a, b;                   // 各独占一行

4 线程 100M 自增：挤一行 ~3 s，padding ~0.4 s（约 8×）。细节与 MESI 状态机见 内存模型 · false sharing。

6.4 易触发场景

  • per-worker stats / vector<atomic<T>> / spinlock 数组紧挨着
  • RingBuffer 的 head/tail 没分到两行

6.5 检测工具

perf c2c record/report 看 hot line + 多核写；加速比远小于线程数也是信号。VTune 能直接标 false sharing。

数据布局优化

SoA vs AoS · 对齐 · padding

7.1 SoA vs AoS

struct Particle { float x,y,z, vx,vy,vz; int id; };   // AoS
for (auto& p : ps) p.x += dt * p.vx;                   // 跳整对象

struct Particles { std::vector<float> x, vx; };        // SoA
for (size_t i = 0; i < ps.x.size(); ++i)
    ps.x[i] += dt * ps.vx[i];                          // 顺序 + 易 SIMD

7.2 内存对齐与 padding

手法做什么何时

08

分支预测 · likely/unlikely · branchless

Branch predictor · [[likely]] · 无分支编程

8.1 分支预测器原理

CPU 在条件跳转之前就预测路径并提前执行。猜错 → 流水线 flush → ~10–20 周期。

8.2 经典实验：sort 数据后变快

同一段 if (x > 128) sum += x，数据排序后快约 4×。不是算法变了，是分支从随机变成两段偏置。

8.3 [[likely]] / [[unlikely]] (C++20)

编译器把 likely 放 fallthrough，给预测器和 i-cache 一个好起点。gcc 老写法是 __builtin_expect。

8.4 Branchless (无分支) 编程

if (rc > 0) [[likely]] { handle_ok(rc); }
else [[unlikely]] { handle_err(rc); }     // 热路径 fallthrough

int mx = (a > b) ? a : b;                 // 常被编成 cmov
int mx2 = lut[static_cast<unsigned>(i)];  // 数据相关：查表更稳
高度可预测的分支不要硬改成 branchless——可能两条路径都算一遍，更慢。先看 branch-misses。

内存分配优化

malloc 真实成本 · reserve · pmr · jemalloc/tcmalloc · SBO

9.1 malloc 的真实成本

场景开销
小块 malloc/free（无竞争）~50–100 ns
多线程竞争 / brk·mmap / page fault / >128KBµs 级

glibc 内部见 内存泄漏 · Arena。

9.2 优化思路

预分配 · 对象池 · arena · SSO/SBO · 替换 malloc（jemalloc / tcmalloc / mimalloc）· std::pmr。

9.3 reserve 的威力

1M 次 push_back 不 reserve 约 20 次 2× 扩容；reserve(N) 一次分配。实测约 3–4×。

9.4 std::pmr (C++17)

#include <memory_resource>
char buf[8192];
std::pmr::monotonic_buffer_resource pool{buf, sizeof(buf)};
std::pmr::vector<int> v{&pool};
for (int i = 0; i < 1000; ++i) v.push_back(i);   // 不碰堆

请求结束 pool 整块释放。用法与限制见 低延迟 · pmr。

9.5 替代 allocator

分配器特点适用
jemalloc / tcmalloc / mimalloc多线程、碎片、自带 profile服务端；LD_PRELOAD 即可换
scudo安全优先安全敏感

9.6 SBO

std::string SSO 约 15/22 字节。small_vector 标准库没有，boost/folly 有。热路径短字符串不要无故越过 SSO 阈值。

inline 与函数调用开销

调用约定 · inline 误区 · LTO inline · devirtualization

11.1 函数调用真实成本

调用开销
已 inline / 未 inline / 虚函数0 / ~1–2 ns / ~1–3 ns
函数指针 / std::function / PLT~1–2 / 5–10 / +5 ns
syscall~50–200 ns

11.2 inline 关键字 ≠ 强制 inline

inline 今天主要是 ODR；编译器自己决定是否内联。真要强制：always_inline / __forceinline。默认别瞎标。

11.3 LTO 后链接器也能 inline

没 LTO，跨 .o 看不见对方函数体。开 LTO 才有跨 TU inline / DCE。这是生产开 -flto 的真正原因，不只是「再快几个 percent」。

11.4 虚函数与 devirtualization

派生类标 final，在已知静态类型的调用点可以去虚化甚至再 inline。模板代码天然可见定义，不必虚。规则：让编译器决定 inline；热点多态用 final 或改成模板。

12

编译器优化 · O3 · LTO · PGO

-O 级别 · LTO · PGO · 自动向量化 · 生产编译选项

12.1 优化级别

级别行为典型加速
-O0 / -Og无优化 / 调试友好基线 · 开发
-O2全部安全优化3–5× · 生产默认
-O3 / -Ofast更激进向量化 / 放松 IEEE偶发回退；-Ofast 改语义
-Os优化大小嵌入式

生产常用 -O2 -flto -DNDEBUG -fno-omit-frame-pointer（后者为了 perf 栈）。别把旗标墙当方法论。

12.2 LTO

把 IR 留到链接，跨 TU inline / DCE。大型项目 5–15%，编译慢 1.5–3×。建议开。

12.3 PGO

用真实负载告诉编译器哪条热、哪个分支常走。收益 5–20%。插桩 vs 生产采样 vs 二进制重排见 §16c 的分层图。

12.4 自动向量化

顺序、无别名、无循环携带依赖、POD 类型，编译器才愿意 SIMD。提示：__restrict__、alignas、-fopt-info-vec。三档策略见 §16b。

12.5 推荐的生产编译选项

先 LTO，再 AutoFDO，binary 很大再 BOLT。每一档单独上线、单独测。完整流水见 §16c。

锁的性能优化

锁开销层次 · 分片 · lock-free · thread_local

13.1 锁的开销层次

原语无竞争有竞争
atomic / spinlock~5 / 10 ns行乒乓 / 忙等烧核
mutex / shared_mutex / CV~25 / 50 / 100+ nssyscall + 调度

13.2 锁优化的几个方向

只锁数据不锁 IO；按 hash 分片；读多写少用 shared_mutex / COW；能 TLS 就不要全局 atomic；batch 减少加锁次数。

13.3 分片示例

array<Shard,16>，每片自带 mutex + map；shard_for(id) 取模。不同 session 无锁竞争。

13.4 Lock-Free 计数

全局 atomic<long> 在多核上是假共享+行乒乓。改成 thread_local 累加、定时 fetch_add 到全局，4 线程 100M 可从 ~1 s 降到 ~50 ms。先测争用，再写 CAS 循环。

    18.30%     2.10%  myapp    libc           [.] malloc

14.2 火焰图阅读

x 轴是采样占比（不是墙钟），宽 = 该函数占用的 CPU 比例；y 轴是栈深，向上是被调用者。颜色无语义。顶部最宽的平台就是该打的叶子。

16B

SIMD / 向量化深度

从自动向量化到 intrinsics ⭐

SIMD 一条指令处理多个数据。x86 AVX2 一次 8×float。用对了数值循环 4–16×；用错了先被自动向量化打脸。

16b.1 三档实现策略

策略难度性能可移植
自动向量化★~50–90%✅ 第一选择
pragma / restrict / 对齐提示★★~70–95%✅
Highway / xsimd / std::simd★★★95%+✅ 生产首选跨平台
intrinsics / 手写汇编★★★★100%❌ 最后才碰

16b.2 让自动向量化生效 —— 6 个前提

边界可分析 · 无别名（__restrict__）· 循环体无未内联调用 · 对齐 · 无循环携带依赖 · 无早退分支。

16b.3 自动向量化诊断

g++ -O3 -fopt-info-vec-all / Clang -Rpass=loop-vectorize。汇编里要看到 ymm/zmm，否则只是「以为向量化了」。

16b.4 三个立刻生效的提示

__restrict__ 否认重叠；alignas(64) + assume_aligned；#pragma omp simd / GCC ivdep。别一上来写 _mm256_*。

16b.5 实例：dot product

n=4096、AVX2：朴素 -O0 ~12 µs；-O3 自动向量化 ~1.1 µs；std::simd ~1.0；手写 FMA ~0.85。从 -O0 到 -O3 已经 10×，intrinsics 只再抠 20%。不要为这 20% 放弃可移植。

16b.6 跨平台库

Highway（Chromium）· xsimd · ISPC · C++26 std::simd。

16b.7 SIMD 反模式

  • 盲目 intrinsics，寄存器/cache 更差
  • 横向 hadd/permute（10+ cycles）
  • 分支密集循环；先 partition 让数据同质
  • 未对齐 AVX-512、以及部分 Intel 上 AVX-512 降频拖垮整核
流程：写清楚的 C++ → 看 vec remarks → restrict/对齐 → 库 → 最后才 intrinsics。绝大多数停在第三步。
16C

PGO / AutoFDO / BOLT

用 profile 优化二进制 ⭐

编译器默认是静态启发式。PGO 把真实热路径喂回去：inline、函数布局、分支、去虚化。生产 C++ 服务常见 5–15%。

16c.1 PGO 经典三段

插桩编 → 跑代表性负载落 profile → 带 profile 重编。Clang 用 -fprofile-instr-generate + llvm-profdata merge。

16c.2 PGO 帮编译器做对哪些决策

优化无 PGO有 PGO
inline / 函数排序按大小、链接顺序按真实频次，热函数聚簇
分支布局 / 展开likely 提示按真实分布
indirect call无法去虚看到 95% 同一 target 就直调

16c.3 AutoFDO

插桩版不能上线、代表性负载难造。AutoFDO 用生产 perf record（开销 < 1%）转成编译器能吃的 sample profile。Google / Meta 的闭环：每周拉最近 24h 采样当下次发版输入。

16c.4 BOLT

Meta 的 post-link 工具：成品 ELF + perf → 重排基本块。Clang 自身 / HHVM 公开数据约 +15–20%（在 AutoFDO 之上再叠）。

16c.5 三者关系总览

上图即总览。Instrumented 准但贵；AutoFDO 便宜可持续；BOLT 吃的是已经链完的布局。

16c.6 ThinLTO + AutoFDO + BOLT

大型服务的标准流水：-flto=thin -fprofile-sample-use=… -Wl,--emit-relocs 再 llvm-bolt。每层单独基准，不要一次全开。

16c.7 常见坑

  • gdb 栈不连续 → 保留 -g + 单独 debug 包
  • 流量模式变了旧 profile 会变慢 → 定期重采
  • cold 第一次走暴 icache miss → 可能伤 p999
  • 生产采样要 perf_event_paranoid / CAP_PERFMON

17.4 速答示范（第 4 题）

问：什么是 cache line? 典型大小?

答：

  • Cache line = 缓存的基本传输单位，CPU 在 cache 与 DRAM 之间一次只搬这么多字节
  • 典型 64 字节（x86/ARM 主流）；某些 ARM 是 128 字节
  • 读 1 字节也会加载整个 64 字节 → 顺序访问 8 个相邻 int 几乎免费
  • 查看：cat /sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size
  • C++17：std::hardware_destructive_interference_size (避免假共享) / hardware_constructive_interference_size (主动共享)

面试官可能追问："cache line 概念怎么影响数据结构设计?" — 答：① 数据布局紧凑（同时访问的字段放一起）；② 多线程 atomic 数组要对齐到 cache line（防假共享）；③ 优先用连续容器（vector / array）。
