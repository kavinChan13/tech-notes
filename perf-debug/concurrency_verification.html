并发正确性验证方法论

TSan 报了绿灯，说明的只有一件事：它这次跑过的那个交错里没有数据竞争。而并发 bug 恰恰住在没跑到的那些交错里。本文讲的是 TSan 之外的那半边——把缺陷分类、承认动态工具的天花板、用模型检查穷举核心几十行、用 litmus test 十分钟结掉一个内存序争论，最后把这些拼成一套能进 CI 的分层策略。

核心难度 ★★★★★ 漏检代价 极高 阅读时长 ~35 min 前置 内存模型 · TSan · 无锁编程
缺陷分类与覆盖矩阵 GenMC / CDSChecker / Relacy herd7 litmus test 交错放大与多架构矩阵
01

TSan 绿灯不等于正确

动态分析的观测对象是「这一次执行」，而不是「这段程序」

一个团队把并发验证做到了这一步：CI 里跑 TSan，全绿；本地压测循环跑十万次，不复现；code review 两个人签字。三周后线上出现一次十分钟的数据错乱，事后定位是一个 memory_order_relaxed 用错了地方。

这不是执行不到位，是方法论上本来就有一个洞。TSan 是动态分析：它在程序真实跑的时候插桩每一次内存访问，然后判断有没有两次访问落在同一地址上、彼此之间又没有 happens-before 关系。它的观测对象是这一次执行——线程被调度成什么样、每个分支走了哪边、每个 CAS 第几次成功，全都是这一次的具体取值。

交错（interleaving）：多个线程的指令序列在一次具体执行中被排成的那一个全序。n 个线程各 k 步，可能的交错数是 (nk)! / (k!)ⁿ——两个线程各 10 步就是 184756 种。而弱内存模型下还要再乘上「每个 load 从哪个 store 读」的选择，数量级又往上翻。

1.1 一条执行路径 vs 全部交错

这张图里最该记住的是颜色的不对称：TSan 报错几乎没有假阳性——它报了就是真的有竞争，值得立刻修；但 TSan 不报错，提供的信息量非常有限。把一个只有存在性能力的工具当成全称证明用，是并发验证里最常见的方法论错误。

1.2 「跑了一万次」值多少钱

压测报告里的「循环运行 10000 次无异常」几乎总是被高估。要看清它值多少钱，得同时算两件事：单次命中概率，以及这一万次之间是否独立。

竞争窗口的典型宽度是几个到几十个纳秒——从写完 payload 到发布指针之间也许就三条指令。而一次线程抢占的时间粒度是毫秒级，主动切换（futex、yield）是微秒级。要让另一个线程恰好挤进那几纳秒，概率量级在 10⁻⁶ 到 10⁻⁹。跑一万次，检出概率也就千分之一量级。

更要命的是第二件事：这一万次不是一万个独立样本。同一个二进制、同一台机器、同样的 cache 预热状态、同样的线程创建顺序，操作系统调度器会收敛到高度重复的模式。实测中经常出现「跑十万次，用调度指纹去重后只覆盖了三四种不同交错」的情形。次数和交错覆盖率之间根本不成正比，而报告里写的偏偏是次数。

你要证明一条山路上没有落石，于是开车走了一万趟——但每次都是同一个时间出发、同一个车速、走同一条车道。这一万趟真正采样到的路况变化，可能还不如换三个不同时段各走一趟。压测的价值来自「交错的多样性」，不来自「循环的次数」；而多样性得靠主动设计（§6），不会自己出现。
02

把验证目标拆成五类

不分类就会拿一把工具去打五种钉子，然后以为都打完了

「并发 bug」不是一类缺陷，是至少五类，各自的定义域、发现手段、修复方式都不一样。混在一起谈，就必然出现「TSan 全绿所以并发是对的」这种推理。

2.1 五类并发缺陷

类别定义最小例子为什么 TSan 未必看得见
数据竞争两次访问同一地址、至少一个是写、至少一个非原子、彼此无 happens-before两个线程同时 ++counter（普通 int）看得见，而且这是它唯一真正强的一类
死锁 / 活锁线程互相等待，或反复重试却谁也不前进ABBA 锁序反转；两个 CAS 循环互相打断它是 happens-before 检测器，不是等待图检测器
原子性违反每次访问都同步了，但该在一个临界区里的操作被拆成了两个if (m.count(k)) use(m[k]); 两句各自加锁每次访问都有锁保护，按定义就不是竞争
顺序违反依赖「A 一定在 B 之前」，但没有任何机制保证后台线程在 init() 完成前就开始用配置同上：如果两侧都加了锁，只是顺序错了，无竞争可报
内存序错误原子操作用了过弱的 memory_order，导致别的线程读到不该读到的值发布指针用 relaxed 而不是 releasepayload 非原子时能报；全部是 atomic 时它按定义不报

加上第六类活性问题（饥饿、丢通知、优先级反转、假唤醒），它属于「程序没坏、只是不往前走」，任何以「检测非法状态」为原理的工具都拍不到——它要靠超时、看门狗和等待图。

这张表里最值得盯的是原子性违反那一行。它是生产环境里占比很高、而工具覆盖率最低的一类：所有访问都规规矩矩加了锁，静态检查满意，TSan 满意，唯一的问题是临界区的边界划错了。这类缺陷只能靠「不变量」来抓——你得先能写出「什么状态是非法的」，才有东西可检查。

03

动态工具的天花板

你在 x86 上测的不是你的代码，是「你的代码 + 一台几乎不重排的机器」

3.1 x86 TSO 掩盖了什么

「x86 上跑了半年都好好的，移植到 ARM 服务器第二天就崩」——这是内存序错误的标准剧本，而它的原因完全不神秘：x86 的硬件内存模型强到掩盖了你的大部分错误。

x86-TSO：x86 的内存模型只允许一种重排——store → load（后面的 load 可以越过前面还在 store buffer 里的 store）。load→load、load→store、store→store 一律不允许。相比之下 ARMv8 四种都允许，POWER 还额外不保证 multi-copy atomicity（不同线程可以对同一组写观察到不同顺序）。

把这件事说到底：内存序错误在 x86 上不是「概率低」，很多时候是概率为零——编译器生成的指令与正确写法完全相同，硬件也不会做那种重排。这类 bug 在 x86 上跑一亿次仍然是零命中，它不是被压测漏掉的，是压测在这台机器上根本无法命中。所以再多的 x86 长跑都不能替代一台弱序机器（§6.2）。

3.2 TSan 建模的是 happens-before

还有一层更细的天花板：TSan 并不模拟硬件重排。它拦截原子操作、按 memory_order 维护 vector clock，判断的是C++ 抽象机层面的 happens-before 关系。这带来一个需要分情况看的结论。

✅ payload 是非原子的 → TSan 有戏
buf[t] = v;                       // 非原子写
tail.store(t+1, relaxed);         // ❌ 该 release

// 消费者
if (tail.load(relaxed) > t)       // ❌ 该 acquire
    use(buf[t]);                  // 非原子读

relaxed 不建立 happens-before，于是 buf[t] 上的写与读在 TSan 眼里就是一对无序访问 → 报竞争。而且它不要求两次访问在时间上重叠，所以在 x86 上也能报出来。

❌ 全部是 atomic → TSan 按定义沉默
// Dekker 的核心：没有一个非原子访问
want[me].store(1, relaxed);       // ❌ 该 seq_cst
if (want[other].load(relaxed) == 0)
    enter_critical_section();     // 两个线程可能同时进来

数据竞争的定义要求至少一个非原子访问。这里全是原子操作，无论内存序多弱都不构成竞争——TSan 不是漏报，是这件事不在它的定义域里。

这个区分很实用：它告诉你什么时候还能指望 TSan，什么时候必须换工具。凡是「算法的正确性依赖原子操作之间的顺序」的代码——无锁队列的 head/tail 协议、引用计数的最后一次递减、状态机的 CAS 转换、自旋锁本身——TSan 一格都覆盖不到，那正是 §4 和 §5 存在的理由。

3.3 重复执行不是采样

§1.2 已经算过概率。这里补一个容易被忽略的工程推论：既然重复执行的样本不独立，那么压测的正确指标不是执行次数，而是覆盖到的不同交错数。这个数得自己测量——在关键点上记录一个全局递增序号，把一次执行经过的序号序列拼成「调度指纹」，然后统计去重后有多少种。

第一次这么量的团队通常会被结果吓一跳：十万次执行，去重后三到五种指纹。而这也直接给出了改进方向——不是把一万次加到一百万次，而是让每一次都不一样（§6.1）。

04

穷举与模型检查

唯一能把「没找到 bug」升级成「没有 bug」的手段，代价是范围极小

动态工具是在交错空间里随机撞，模型检查是系统地走完。走完之后得到的结论性质完全不同：不再是「这次没撞到」，而是「在这个规模内不存在违反」。这是并发验证里唯一能给出全称结论的工具类别。

4.1 有界 vs 无状态

工具路线接入方式能表达的内存模型适合
GenMC无状态 + DPOR直接编译 C/C++ 源码运行，无需改写类型RC11、IMM、LKMM 可选默认首选；核心算法 30–80 行
CDSChecker无状态链接它的 libmodel，用 C11 atomics 写测试C/C++11 公理模型需要精确控制 fence 语义的实验
Relacy无状态 + 模拟弱序头文件库，rl::atomic 替换 std::atomic自建的 relaxed 可见性模拟不想装工具链、想直接写单测
Nidhugg无状态（LLVM IR）编译到 IR 后分析SC / TSO / PSO只关心 TSO 层面的问题
CBMC有界（SAT/SMT）把源码编码成公式SC / TSO / PSO输入组合也要覆盖时

4.2 写一个可穷举的测试

模型检查的门槛不在工具，在把代码改造成可被穷举的形状。约束很硬：线程数 2–3、每线程操作 2–4 步、没有外部输入、没有系统调用、循环必须有界。下面这个测试正好落在 §3.2 提到的「TSan 完全盲」那一类——全部是原子操作，只有一条断言。

/* mutex_probe.c —— 两线程互斥协议：全是 atomic，TSan 按定义不报任何竞争
 * $ genmc --unroll=2 -- -std=c11 mutex_probe.c                              */
#include <stdatomic.h>
#include <assert.h>
#include <pthread.h>
#include <stdint.h>

static atomic_int want[2];   /* 我要进临界区 */
static atomic_int inside;    /* 临界区内人数 —— 不变量：任何时刻 <= 1 */

static void *worker(void *arg) {
    intptr_t me = (intptr_t)arg;
    atomic_store_explicit(&want[me], 1, memory_order_relaxed);            /* 疑点 A */
    if (atomic_load_explicit(&want[1 - me], memory_order_relaxed) == 0) { /* 疑点 B */
        int n = atomic_fetch_add_explicit(&inside, 1, memory_order_relaxed);
        assert(n == 0);          /* ← 整个测试就为了这一行：不变量被打破了吗 */
        atomic_fetch_sub_explicit(&inside, 1, memory_order_relaxed);
    }
    atomic_store_explicit(&want[me], 0, memory_order_relaxed);
    return NULL;
}

int main(void) {
    pthread_t t[2];
    for (intptr_t i = 0; i < 2; i++) pthread_create(&t[i], NULL, worker, (void *)i);
    for (int i = 0; i < 2; i++)      pthread_join(t[i], NULL);
    return 0;
}

GenMC 在秒级给出反例：两个 relaxed store 都还没对彼此可见，两个 load 各自读到 0，两个线程一起进临界区，inside 变成 2。把 A、B 都改成 memory_order_seq_cst 后再跑，它报「探索完毕、无违反」——注意这句话的分量：不是「这次没撞到」，而是这个规模内的执行已经走完了。

四个改造要点，每一个都是从「必须能穷举」推出来的：

要点怎么做不这么做会怎样
规模压到最小2 个线程，每个 3–4 个原子操作；CAP 之类的常量取 1 或 24 线程 × 5 步就是 1.2e10 条路径，跑不完
把正确性写成不变量assert 一个状态断言（人数 ≤ 1、值不为 0、顺序不倒置）没有断言的穷举只能发现崩溃和死锁，逻辑错误照样漏
循环必须有界CAS 重试循环加 --unroll=N，或改写成「最多重试两次」无界重试在无状态模型检查下产生无限执行，工具挂住
切断外部世界不 malloc、不 IO、不读时间、不用 random；输入写成固定常量每个不确定来源都乘进状态空间，或者让工具直接放弃

第二条最容易做砸。断言的质量决定了整件事的价值：穷举一遍只跑出「没崩」的结论，那这几天工作换来的信息量还不如一次 code review。写断言的正确姿势是先回答「这个结构的不变量是什么」——队列不丢不重不乱序、引用计数归零时无人持有、状态机不出现非法转换——写不出来这句话，说明还没想清楚要验证什么。

4.3 状态空间爆炸的边界

指数增长是这条路线的硬边界，也是它的使用说明书：模型检查验证的是「核心几十行」，不是你的程序。它的合理用法是把无锁数据结构的 push/pop、引用计数的增减、状态机的转换单独摘出来做成上面那种探针，而不是指望它跑通业务代码。

DPOR（动态偏序归约）的作用是把「交换两个互不相干的操作得到的交错」认成同一条，从而把可行规模往上推几个数量级——但它降的是底数，不是指数。所以规划工作量时的现实预期是：写一个够小、够封闭、断言够狠的探针，通常比写实现本身更花时间。这个成本正是 §8.2 那些判据的来源。

Relacy、CDSChecker、GenMC、perf c2c 这几个名字在 C++ 内存模型 §14 里被点到过，但那里没有展开怎么用；反过来，本文不重复内存模型本身（happens-before、memory_order 六档语义、fence 的作用域），需要补的话看那一篇。
05

litmus test 与 herd7

回答「这两个 relaxed 之间要不要加 fence」最快的方式，十分钟就有结论

内存序的争论在 code review 里最难收场：一方说「这里 relaxed 就够，反正有依赖」，另一方说「不加 release 迟早出事」，两边都举不出证据，最后按资历或按嗓门决定。litmus test 的意义就是把这种争论变成一条可执行的命令。

litmus test：一个只有几行、多线程、无循环无输入的最小程序，加上一个关于最终状态的断言。herd7 拿一份形式化的内存模型（.cat 文件）去穷举它在该模型下的所有允许结果；litmus7 则把同一个测试编译成真程序，在真机上跑几百万次看实际能不能出现。前者回答「标准允许吗」，后者回答「这颗 CPU 干不干」。

5.1 一个 litmus 长什么样

用最经典的 message passing（MP）：一个线程写数据再置标志，另一个线程看到标志后读数据。问题是——标志用 relaxed 行不行？

C MP-relaxed
{ }
P0 (atomic_int *x, atomic_int *y) {
  atomic_store_explicit(x, 1, memory_order_relaxed);      // 写数据
  atomic_store_explicit(y, 1, memory_order_relaxed);      // 置标志 ← 疑点
}
P1 (atomic_int *x, atomic_int *y) {
  int r0 = atomic_load_explicit(y, memory_order_relaxed); // 看标志 ← 疑点
  int r1 = atomic_load_explicit(x, memory_order_relaxed); // 读数据
}
exists (1:r0=1 /\ 1:r1=0)      /* 看见标志却读到旧数据 —— 这可能发生吗？ */

$ herd7 -model rc11.cat MP-relaxed.litmus

5.2 它回答什么、不回答什么

输出含义你该怎么办
Never 0 N该模型下不可能出现，任何符合标准的实现都不会这个内存序够用，不必加 fence——省下的开销是有依据的
Sometimes k N标准允许出现就是 bug，跟「x86 上测不出来」无关（§3.1）
Always N 0断言在所有执行下都成立通常说明断言写反了，检查一下 exists
litmus7 实测 0 次命中这颗 CPU 这次没做这种重排不能推出安全——换代 CPU、换编译器、加个循环都可能变

最后一行是关键判断：herd7（模型穷举）和 litmus7（真机实测）给出的结论强度差一个量级。标准说 Sometimes 就按 bug 处理，不要拿真机测不出来当挡箭牌——那只是复现了一遍 §3.1 的错误。反过来，如果 litmus7 在某颗 CPU 上真跑出来了，那就是一个铁证，可以直接结束争论。

litmus test 的适用面很窄但很锋利：它只回答「几个原子操作之间的顺序关系」这一类问题——两个 relaxed 之间要不要 fence、seq_cst 能不能降成 acq_rel、这个 fence 该放在 CAS 前还是后。它答不了「我这个队列在满的时候会不会丢元素」，那是 §4 的活。CppMem 是同一件事的网页版，针对 C++11 模型，能把候选执行连同 happens-before 边画出来，讲解和自学时比命令行更直观。

06

压测怎么设计才有效

目标从「跑很多次」换成「每次都不一样，且失败能复现」

模型检查只覆盖核心几十行，其余部分仍然要靠压测兜底。但压测必须重新设计——按 §1.2 的算法，默认写法的效率低到接近于零。三个方向：放大交错、换弱序机器、让失败可复现。

6.1 交错放大

注入点的位置必须由知道协议的人来标，这是这套做法能不能奏效的分水岭。一个 tn_interleave(site) 应该恰好插在「payload 写完、还没发布」「CAS 读到旧值、还没写回」「解锁了、还没通知」这些真正的窗口里；均匀撒在每个函数入口，效果基本等于零。

// ---- stress_harness.hpp：整段只在 -DTN_STRESS 的测试构建里有代码 ----
inline uint64_t tn_seed() {                 // 全进程唯一随机源，失败时靠它复现
    static const uint64_t s = [] {
        const char *e = std::getenv("TN_SEED");
        uint64_t v = e ? std::strtoull(e, nullptr, 10)
                       : std::chrono::steady_clock::now().time_since_epoch().count();
        std::fprintf(stderr, "TN_SEED=%llu\n", (unsigned long long)v);  // 日志第一行
        return v;
    }();
    return s;
}

#ifdef TN_STRESS
inline void tn_interleave(int site) {
    thread_local std::minstd_rand rng{ (uint32_t)(tn_seed()
        ^ std::hash<std::thread::id>{}(std::this_thread::get_id())) };
    switch (rng() % 4) {                    // 四种强度，让每次执行都不一样
    case 0: break;                                           // 什么都不做
    case 1: std::this_thread::yield(); break;                // 让出一次
    case 2: for (int i = rng() % 64; i--;) tn_cpu_relax(); break;   // 忙等几十周期
    case 3: std::this_thread::sleep_for(
                std::chrono::microseconds(rng() % 50)); break;      // 撑开窗口
    }
    tn_schedule_fingerprint(site);          // 记指纹，用来统计覆盖了多少种交错
}
#else
inline void tn_interleave(int) {}           // 生产构建里彻底消失
#endif

// 用法：撒在协议的窗口里，而不是撒在每个函数入口
buf[t % CAP] = v;
tn_interleave(/*site=*/7);   // ← 消费者若能在此刻插进来，发布顺序错误就暴露了
tail.store(t + 1, std::memory_order_release);

#else 那个空实现不是形式主义：注入点会散落在最热的代码路径上，必须保证它在生产构建里连一条指令都不剩。同理，注入用的随机数只能从 tn_seed() 派生——一旦有人图方便用了 std::random_device 或当前时间，整套复现机制就失效了，而且这种失效是静默的。

6.2 多架构矩阵

§3.1 已经论证了 x86 单架构压测在内存序问题上的能力接近于零，所以矩阵里必须有一台弱序机器。这里有一个反直觉的坑：QEMU 模拟的 aarch64 不算。

环境能不能暴露内存序错误说明
x86-64 真机只有 store→load 一类Dekker / store buffering 那类能碰到，MP / LB 那类碰不到
aarch64 真机能，四种重排都真实发生云上 ARM 实例、Apple Silicon、国产 ARM 服务器都可以；矩阵里必须有一台
QEMU 用户态模拟 aarch64基本不能翻译执行时访存顺序由宿主机决定，宿主是 x86 就得到 x86 的顺序——绿灯毫无意义
POWER / RISC-V 真机能，且更弱POWER 不保证 multi-copy atomicity，能抓到 ARM 都抓不到的 IRIW 类问题
Rosetta / 二进制翻译层不可预期翻译层通常会补强内存序以保证兼容，等于又盖了一层

还有两个成本很低、收益却经常被低估的维度：用 taskset 把线程压到 1–2 个核上（抢占频率大幅上升，锁的交接路径完全不同）；用背景负载压满调度器（让线程在任意点被抢走，而不是总在系统调用处让出）。这两条不需要新硬件，只改运行方式，往往在夜间长跑里第一次抓到东西。

6.3 可复现与覆盖度

并发压测最贵的浪费是：抓到了一次失败，但没法再抓到第二次。日志里只有一行断言失败，重跑不复现，两天后这个 issue 被标成 flaky test 关掉——真 bug 就这样被扔了。避免它只需要三条纪律：

纪律具体做法它救的是什么
单一随机源所有随机（延迟、操作序列、线程数、数据）都从一个 TN_SEED 派生；禁用 random_device 与读时间让 TN_SEED=12345 ./stress 能重走同一条路
种子写在日志第一行进程启动就打印，不等到失败时才打失败时进程可能已经被 abort / OOM kill 了
用指纹量覆盖度tn_schedule_fingerprint() 把经过的注入点序列哈希起来，统计去重后的种数把「跑了 N 次」换成「覆盖了 M 种交错」，才知道调参有没有用

第三条是唯一能让压测调优脱离玄学的东西。加了一档 sleep、换了个注入点、限了核——覆盖度是从 4 种涨到 900 种还是原地不动？有这个数字，压测就变成一个可以优化的工程问题；没有它，只能凭「感觉这样更容易出问题」。

07

确定性回放的位置

它不负责发现问题，它负责把已经出现过一次的问题变成可以反复调试的

把 rr 放在验证体系里的哪个位置，是个容易搞错的问题。它的价值不在发现——在于把「三周出现一次」变成「随时能重放一次，而且每次一模一样」。抓到之后可以反向执行，从断言失败处倒着走回那个写坏了值的地方，这在并发问题上是量级上的效率差别。

性质含义推论
录制时把线程串行到单核靠记录调度切换点实现确定性只能探索单核可达的交错；真并行才出现的问题录不到
不模拟弱内存模型录制回放的是实际发生的那一次执行ARM 上的重排问题，rr 帮不上（矩阵里的 §6.2 才行）
串行化改变了时序线程不再真正并行不能用来诊断性能问题：真伪共享、锁竞争的数据全变了
--chaos 随机化调度随机化线程优先级与时间片专为让并发 bug 更容易出现而设计，是它唯一带一点「发现」能力的地方
开销 1.2–2×远低于 TSan 的 5–15×可以在夜间长跑里默认开着录，出事时手上就有录像

最后一行是最实用的一条部署建议：让夜间压测在 rr record --chaos 下跑。开销低到可以承受，而一旦哪次断言失败了，手上直接就有一份能确定性回放的录像，省掉「先想办法复现」这个通常最耗时的环节。这也解释了为什么 §2.2 的矩阵里 rr 那一列写的是「可复现」而不是「覆盖」——它改变的是调试成本，不是检出能力。

rr 的安装、record / replay 的具体用法、反向执行与 --chaos 的参数，在 崩溃排查 里已有展开，本文只讨论它在验证体系中的定位与边界。

分层验证策略

每层各自便宜、各自有洞，叠起来才有覆盖；最上面那一层是「别写它」

8.1 七层各花多少时间

层手段覆盖什么成本频率
L0 设计能不能不写这段无锁代码从源头消除整片风险一次讨论每次设计评审
L1 模型检查GenMC / CDSChecker 穷举核心 30–80 行五类缺陷全覆盖，含弱内存下的 reads-from2–5 人日（写探针比写实现久）算法改动时
L2 litmusherd7 / CppMem 结掉一个具体内存序问题原子操作之间的顺序关系10–30 分钟每次有争论
L3 TSanCI 上每个 PR 跑单测 + 集成测试数据竞争，且只在跑到的交错上CI 时间 ×5–15每个 PR
L4 压测矩阵x86 + ARM 真机、延迟注入、限核、长跑概率性地捞漏网的，尤其内存序一套夜间流水线每晚
L5 rr 回放rr record --chaos 常开不增加检出，把复现成本降到零开销 1.2–2×随 L4 一起

这张表最反直觉的一格是 L1 的成本：2–5 人日，而且是每次算法改动都要付一遍。正因为这么贵，它不能作为默认要求——L1 只用在「自己手写的无锁结构」和「跨线程状态机」上。用 std::mutex 的普通并发代码，L3 + L4 就是合适的投入。

另一个容易被跳过的是 L2 只要十分钟。它的性价比在整张表里最高，却最常被省掉——因为「争论」在团队里不被当成一个需要工具的场合。把 herd7 装上、在仓库里存几个 .litmus 模板，可能是这七层里最容易拿到的收益。

09

面试题集（12 道）

按难度分三档，先自测再对照

点击每道题展开参考答案（先自测，再对照）。

9.1 基础（必答）

  1. 基础TSan 报了绿灯，能说明什么、不能说明什么？

    能说明的只有一句：在它这次（或这几万次）实际跑过的交错上，没有找到数据竞争。TSan 是动态分析，观测对象是「这一次执行」——线程被调度成什么样、每个分支走了哪边，全是这一次的具体取值。

    不能说明的是「这段代码没有并发缺陷」。两个线程各 10 步就有 184756 种交错，它采到的是其中一条。TSan 是存在性证据（报了就一定是真 bug，几乎无假阳性），不是全称证明。把它当全称证明用，是并发验证里最常见的方法论错误。

  2. 基础并发缺陷至少分成哪几类？为什么必须先分类？

    五类加一类活性：数据竞争（无同步的并发访问）、死锁 / 活锁、原子性违反（每次访问都同步了，但该在一个临界区里的操作被拆成两个）、顺序违反（依赖 A 在 B 之前但无机制保证）、内存序错误（memory_order 用得过弱）、以及活性问题（饥饿、丢通知、假唤醒）。

    必须分类是因为工具的定义域各不相同。TSan 只在第一类上强；后三类里它有大片盲区。不分类就会出现「TSan 全绿所以并发是对的」这种推理——把一把工具的结论套到五种缺陷上。

  3. 基础「压测循环跑了一万次没问题」这个结论值多少钱？

    比直觉低得多，原因有两层。第一层是概率：竞争窗口典型宽度是几到几十纳秒，而线程切换的粒度是微秒到毫秒，单次命中概率量级在 10⁻⁶–10⁻⁹，一万次的检出概率也就千分之一。

    第二层更关键：这一万次不是一万个独立样本。同一个二进制、同一台机器、同样的预热状态，调度器会收敛到高度重复的模式，用调度指纹去重后常常只有三五种不同交错。压测的价值来自交错的多样性，不来自循环次数，而多样性必须主动设计（注入延迟、限核、换架构），不会自己出现。

  4. 基础什么是 litmus test？它和普通单元测试的区别在哪？

    litmus test 是一个只有几行、多线程、无循环无输入的最小程序，加上一条关于最终状态的断言（exists (1:r0=1 /\ 1:r1=0)）。herd7 拿一份形式化的内存模型去穷举它在该模型下的所有允许结果，输出 Never / Sometimes / Always。

    区别在结论的性质：单元测试跑一次得到「这次通过」，litmus + herd7 得到「标准允许 / 禁止这个结果」。所以它能直接结束「这两个 relaxed 之间要不要加 fence」这类争论——十几行文件、十分钟，比在 review 里争半小时便宜。

9.2 中级（区分熟练度）

  1. 中级为什么同一段代码在 x86 上跑半年没事，换到 ARM 服务器第二天就崩？

    因为 x86-TSO 只允许 store→load 一种重排，load→load、load→store、store→store 都不允许；ARMv8 四种全部允许。更直接的证据在指令层面：x86 上 relaxed 与 acquire 的 load 都编译成普通 mov，relaxed 与 release 的 store 也都是 mov——写错内存序，机器码完全一样。ARM64 上则分别是 ldr / ldar、str / stlr，写错了硬件真的会重排。

    推论很硬：这类 bug 在 x86 上往往不是「概率低」而是概率为零，跑一亿次仍然零命中。所以「在 x86 上测不出来」这件事本身不携带任何关于正确性的信息，再多 x86 长跑也替代不了一台弱序真机。

  2. 中级什么情况下 TSan 能发现内存序错误，什么情况下按定义就发现不了？

    分水岭是有没有非原子访问参与。TSan 拦截原子操作、按 memory_order 维护 vector clock，判断的是 C++ 抽象机层面的 happens-before。

    能发现：payload 是非原子的。比如 buf[t] = v; 之后用 relaxed 发布 tail，消费者用 relaxed 读 tail 后读 buf[t]——relaxed 不建立 happens-before，buf[t] 上就是一对无序访问，TSan 报竞争。而且它不要求两次访问在时间上重叠，x86 上也能报。

    按定义发现不了：全部是原子操作。数据竞争的定义要求至少一个非原子访问，所以像 Dekker 那样两个线程各自 want[me].store(1, relaxed) 再读对方标志，无论内存序多弱都不构成竞争。凡是「正确性依赖原子操作之间顺序」的代码——无锁队列的 head/tail 协议、引用计数的最后一次递减、CAS 状态机、自旋锁本身——TSan 一格都覆盖不到。

  3. 中级什么是原子性违反？为什么它是覆盖率最低的一类？

    每次访问都正确加了锁，但临界区的边界划错了：本该在一个临界区里完成的若干操作被拆成了两个，中间被第三方修改插了进来。经典形态是 check-then-act：if (m.count(k)) use(m[k]); 两句各自加锁，中间 k 被别的线程删了。

    覆盖率低是因为它同时躲过了两类工具：所有访问都有同步，TSan 按定义不报；语法上完全合法，静态检查也满意。唯一能抓它的是「不变量」——你得先能写出「什么状态是非法的」，才有东西可以检查。这也是模型检查那一列能覆盖它的原因：穷举执行加上一条状态断言。

  4. 中级设计一个并发压测，你会加哪些机制让它比「循环一万次」有效？

    三个方向。放大交错：在协议的真实窗口里（payload 写完还没发布、CAS 读到旧值还没写回、解锁了还没通知）插入注入点，随机执行 yield / 忙等 / 微秒级 sleep，把几纳秒的窗口撑到几十微秒。注入点必须由知道协议的人标注——全局无脑撒点会拖慢十倍却一个都落不进关键窗口，而且整段要用 #ifdef 保证生产构建里连一条指令都不剩。

    换机器：矩阵里必须有一台 aarch64 真机（QEMU 用户态模拟不算——访存顺序由宿主决定，宿主是 x86 就得到 x86 的顺序）；另外 taskset 限核和背景负载压调度器成本极低、收益常被低估。

    可复现：所有随机从一个 TN_SEED 派生、禁用 random_device 和读时间，种子在启动时就打印在日志第一行（失败时进程可能已被 abort）。再加一条：用调度指纹统计去重后覆盖了多少种交错，把「跑了 N 次」换成「覆盖了 M 种」——这是压测调优能脱离玄学的唯一办法。

9.3 高级（体现深度）

  1. 高级有界模型检查与无状态模型检查的区别是什么？各自的边界在哪？

    有界模型检查（BMC，如 CBMC）把程序展开到 N 步，编码成一个逻辑公式交给 SAT/SMT 求解器。强项是输入可以是符号变量——不必给具体测试值就能覆盖全部取值组合；弱项是展开界限之外的行为完全看不见，公式规模也会爆。

    无状态模型检查（SMC，如 GenMC / CDSChecker / Nidhugg）不保存状态集合，而是反复真实执行，每次系统地更换一个调度决策和一组 reads-from 关系（弱内存模型下必须枚举「这个 load 从哪个 store 读」，光枚举交错不够），配合 DPOR 把等价交错折叠成一条。强项是直接跑真实代码、不需要抽象；弱项是测试必须封闭、确定、有界。

    共同边界是组合数学：交错数 (nk)!/(k!)ⁿ，2 线程 × 5 步是 252，3 × 5 是 7.6×10⁵，4 × 5 超过 10¹⁰。DPOR 降的是底数不是指数。所以这类工具验证的永远是核心几十行，不是你的程序。

  2. 高级要把一个无锁队列改造成可被 GenMC 穷举的测试，你会做哪些取舍？

    四条，每条都是从「必须能穷举」推出来的。规模压到最小：2 个线程、每个 3–4 个原子操作，容量常量取 1 或 2（4 线程 × 5 步就是 10¹⁰ 条路径）。把正确性写成不变量断言：不丢不重不乱序、人数 ≤ 1、未发布的槽位读出来必须是初始值——没有断言的穷举只能发现崩溃和死锁。循环必须有界：CAS 重试循环在无状态模型检查下会产生无限执行，要用 --unroll=N 或改写成「最多重试两次」。切断外部世界：不 malloc、不 IO、不读时间、不用随机，输入写成固定常量。

    最容易做砸的是第二条。断言的质量决定了整件事的价值——穷举一遍只得到「没崩」，信息量还不如一次 code review。写断言前要先能用一句话说出「这个结构的不变量是什么」；说不出来，说明还没想清楚要验证什么。

    还要有成本预期：写一个够小、够封闭、断言够狠的探针，通常比写实现本身更花时间，2–5 人日是常态，而且每次算法改动都要付一遍。

  3. 高级rr 在并发验证体系里应该放在什么位置？它的三个边界是什么？

    位置是定位而非发现：它把「三周出现一次」变成「随时能重放，每次一模一样」，还能反向执行，从断言失败处倒推到那个写坏值的地方。它改变的是调试成本，不是检出能力。

    三个边界都源于「录制时把线程串行到单核、靠记录调度切换点实现确定性」：① 只能探索单核可达的交错，真并行才出现的问题录不到；② 不模拟弱内存模型，ARM 上的重排问题它帮不上，那要靠多架构矩阵；③ 串行化改变了时序，不能用来诊断性能问题——伪共享、锁竞争的数据全变了。

    最实用的部署方式是让夜间压测在 rr record --chaos 下跑：--chaos 随机化线程优先级与时间片，是它唯一带一点发现能力的地方；开销 1.2–2×（远低于 TSan 的 5–15×），低到可以常开，一旦断言失败手上直接就有录像，省掉最耗时的「先想办法复现」。

  4. 高级什么时候你会在评审里直接否掉一段无锁实现，让作者改用 std::mutex？

    三条判据，任一不满足就否。①核心超过 80 行，或结构还会持续演进——这两半是同一个门槛：一个正确的无锁结构如果每季度都加功能，模型检查的成本就永远摊不薄，每次改动都得重写探针、重新论证内存序，最后探针慢慢过期，变成一个绿灯的装饰。②团队里没人能维护那个穷举测试——只有原作者读得懂的算法，等于一个人一离职就无法安全修改的模块。③实测收益不到 2×——低竞争下 std::mutex 几乎免费，快路径就是一次 CAS、压根不进内核，很多无锁改造的真实收益只有 10%–30%。

    三个「否」指向同一个出口：改用 mutex 或成熟的无锁库。这不是保守，是把长期维护成本算进了正确性预算。分层策略里成本最低的一层是 L0「能不能不写它」，因为省掉的验证工作是唯一不会出错的验证工作。

    反过来，三条都满足时就该认真付这笔钱：写 GenMC 探针进 CI、用 litmus 把每个 memory_order 的选择钉死，并把「改这段代码必须重跑探针」写进 README——否则下一个人只会看到一段没有注释的 relaxed。
