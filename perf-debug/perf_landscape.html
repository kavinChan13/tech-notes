01

perf 是什么 · 工具谱系定位

一句话定位 · 和 valgrind / ASan / eBPF / VTune 的分工 · 本文覆盖范围与阅读顺序

先把最容易混淆的一点说清楚：perf 不是"一个测速工具"，而是 Linux 内核 perf_event 子系统的官方前端。内核负责采集，perf 负责下发配置、收数据、符号化、出报告。理解这条分界线，后面所有"为什么它能做 X 却做不了 Y"的问题都会自然有答案。

1.1 一句话定位

perf基于硬件性能计数器（PMU）+ 内核事件的采样式剖析器。它不改你的二进制、不重启你的进程，用统计抽样的方式回答"CPU 时间花在哪、为什么慢"。
🎬 生活类比 · 人口普查 vs 抽样调查 Valgrind / Callgrind 像全员普查：每条指令都过一遍，数据绝对完整，但整个城市停摆（慢 10-30 倍）。
perf 像抽样调查：每秒随机拦下 99 个人问"你现在在干什么"，跑 30 秒就有 3000 个样本。它永远说不出"第 12345 次调用发生了什么"，但能非常准确地告诉你"70% 的人都堵在同一个路口"。
性能优化要的恰好是后者——你要找的是热点分布，不是完整流水账。

1.2 和 valgrind / ASan / eBPF / VTune 的分工

这几个工具经常被摆在一起比较，但它们的坐标其实差得很远。横轴是观测层次（只看自己进程 → 看整个内核），纵轴是运行时开销（决定了能不能上生产）：

图 1.1 · perf 占据的是"低开销 + 覆盖内核"这个象限，这正是生产环境唯一能站的位置。
工具核心机制擅长回答不擅长
perfPMU 计数 / 中断采样"CPU 时间在哪、微架构瓶颈是什么""第 N 次调用为什么错"、精确调用次数
Valgrind动态二进制翻译"指令级完整计数、可重现 cache 模拟"生产、长跑、墙钟时间
Sanitizers / 崩溃调试编译期插桩 / core + GDB"有没有内存 / 并发 正确性 bug"、进程为何死性能剖析（它本身就慢）
eBPF / bpftrace内核可编程探针"自定义条件下的延迟分布、跨进程因果"微架构指标（PMU 那套还是 perf 更顺）
VTunePMU + 自家模型"inner loop 的端口占用、内存带宽建模"轻量、免装、脚本化流水线
perf 与 eBPF 不是替代关系：perf 强在"标准化的 PMU 指标 + 采样剖析"，eBPF 强在"可编程的条件过滤与聚合"。实际排查里常常是 perf top 先定位方向，再用 bpftrace 精确验证假设。

02

采样原理 · PMU 与 perf_event_open

计数模式 vs 采样模式 · 一次采样中断到底发生了什么 · 四类事件源 · 为什么开销能压到 1% 以内

2.1 计数模式 vs 采样模式

所有子命令都是这两种模式的包装：精确计数不知道发生在哪行；溢出采样能定位代码，但是统计值。

图 2.0 · 左栏是精确账本，右栏是抽样调查。日常先 stat 判断大类，再 record 落到函数。
period / frequency-c 1000000 固定周期；-F 99 固定频率（内核调 period 去逼近）。日常用 -F；跨机器要比绝对计数才用 -c。

2.2 一次采样中断到底发生了什么

图 2.1 · 采样链路五步。注意第 ⑤ 步：perf.data 里存的是裸地址，符号化发生在 perf report 阶段——这就是第 9 章所有符号问题的根源。
面试常问"perf 会不会漏样本"。会。两处会漏：① ring buffer 打满（提高 -m 缓冲页数、降低频率）；② 内核限流——单次采样处理超时，内核会打印 "perf interrupt took too long, lowering kernel.perf_event_max_sample_rate" 并主动降频，这时你的 -F 4000 已经悄悄不生效了。

2.3 四类事件源

类别由谁提供例子关键约束
Hardware eventCPU 的 PMUcycles instructions branch-misses cache-misses计数器个数有限；虚拟机里常不可用
Software event内核自己的计数器cpu-clock task-clock page-faults context-switches永远可用，没 PMU 时的兜底
Tracepoint内核里的静态埋点sched:sched_switch syscalls:sys_enter_write数量巨大但位置固定，改不了
Dynamic probekprobe / uprobeperf probe 现场加的探针灵活；取变量值要 debuginfo
没 PMU 也能干活：云上虚拟机常常拿不到 cycles，但 cpu-clock 这个 software event 一定有。perf record -e cpu-clock -F 99 -g 依然能出一张可用的 on-CPU 火焰图，只是没法看 IPC / cache miss。这是很多人在 EC2 上"perf 完全用不了"的误判来源。

2.4 为什么开销能压到 1% 以内

计数免费
PMU 累加是硬件行为，不插指令——这是它和 Valgrind / ASan 的根本区别。
中断稀疏
-F 99 每核每秒只打断 99 次；样本走 mmap ring buffer，不走 syscall。
但会变贵
--call-graph dwarf 每样本拷几 KB；-F 10000 抬两个数量级；高频 sched:* 在忙机器上每秒几十万条。"很轻"只对默认配置成立。
03

权限模型 · 容器与生产环境

perf_event_paranoid 四档语义 · CAP_PERFMON · 容器 / K8s 里怎么跑 · 虚拟机里 PMU 常常根本不存在

"在自己机器上好使，上了生产 / 容器就报 Permission denied" —— 这是 perf 第一大门槛。它不是配置繁琐，而是性能计数器天然是侧信道：能观测别的进程执行细节，等于能推断它的秘密。所以内核默认收得很紧。

3.1 perf_event_paranoid 四档语义

性能计数器是侧信道，内核默认收得很紧。读 /proc/sys/kernel/perf_event_paranoid，多数发行版是 2。

图 3.1 · 档位越高越看不见。默认 2 下火焰图底部一大片 [unknown] 常常是权限，不是符号。
值非特权用户能做什么典型场景
-1几乎全放开，含 raw tracepoint专用性能实验机；生产别这么设
0可做系统级（-a）采集，禁 raw tracepoint需要整机火焰图的性能环境
1禁系统级 / per-cpu 采集，自己的进程可以共享开发机
2再禁内核态采样，只剩用户态多数发行版默认
3+非特权用户彻底禁用（Debian/Ubuntu 的额外补丁档）加固过的系统
paranoid=2 下你依然能剖析自己的进程，只是栈会在进入内核的地方断掉——火焰图底部一大片 [unknown]，看起来像"符号有问题"，其实是权限问题。想看到 __do_sys_write → ext4_file_write_iter 这类内核帧，至少要 paranoid ≤ 1，并且 kptr_restrict=0（见 §9.1）。

3.2 CAP_PERFMON —— 别再给 root

Linux 5.8 起用细粒度 CAP_PERFMON，不要为了看火焰图给 CAP_SYS_ADMIN。setcap cap_perfmon,cap_sys_ptrace,cap_syslog=ep $(which perf)，或在 Pod 里 capabilities.add: ["PERFMON"]。

CAP_PERFMON
访问 perf_event 子系统。
CAP_SYS_PTRACE
读 /proc/<pid>/maps 与内存，符号化和 DWARF 回溯需要。
CAP_SYSLOG
读 /proc/kallsyms（受 kptr_restrict 影响）。

3.3 容器 / K8s 里怎么跑

容器里采不到，通常不是一条命令写错，而是三层权限各卡一层：

图 3.2 · Permission denied、栈在进内核处断、全是 [unknown] 经常是这三格，不是 perf 坏了。符号化细节见 §9.4。

3.4 虚拟机里 PMU 常常根本不存在

很多云实例不暴露 PMU：cycles / instructions 显示 <not supported>。先换 software event（cpu-clock / task-clock）做时间分布；要真实微架构指标再换裸金属或开了 vPMU 的机型。KVM 可给 guest -cpu host,pmu=on。不要把云上测出的 IPC / cache-miss 当可信基准。

05

事件命名 · perf list 与计数器复用

三层事件名 · 跨平台差异 · 计数器复用与缩放外推 · 读懂 <not counted> 与 <not supported>

5.1 三层事件名：通用 / 原生 / raw

层级写法可移植性什么时候用
通用事件（generalized）cycles instructions cache-misses高，跨架构可用默认首选
原生事件（native / PMU）MEM_LOAD_RETIRED.L3_MISS、l2d_cache_refill绑定具体微架构通用事件太粗，要精确语义
raw 事件r04c5、cpu/event=0xc5,umask=0x0/绑定到具体型号手册里有、perf 还没收录的事件
cache-misses 是最容易被误解的事件名。它在多数 Intel 微架构上映射到 LLC（末级缓存）miss，不是"所有层级的 cache miss"。想区分 L1 / L2 / LLC 必须用 L1-dcache-load-misses、LLC-load-misses 这类更明确的名字，或者直接上原生事件。看到"cache-miss 率 3%，很健康"这种结论，先问一句：哪一级？

5.2 跨平台：x86 与 ARM 的事件名不通用

换到 ARM 服务器（Graviton / 鲲鹏 / Ampere）上，perf 命令行完全一样，但一旦用了原生事件就全部失效：

想测x86 (Intel)ARM (aarch64)
LLC 读 missLLC-load-misses / MEM_LOAD_RETIRED.L3_MISSll_cache_miss_rd / l2d_cache_refill（随核型号变）
精确访存采样PEBS（:pp 修饰符）ARM SPE：perf record -e arm_spe//
分支栈LBR（-b / --call-graph lbr）BRBE（较新核）或退化到 FP/DWARF
换机器第一条命令永远是 perf list（配合 perf list cache / perf list pmu 过滤）。ARM 的 PMU 可编程计数器通常只有 6 个（x86 常见 4 通用 + 3 固定），一次订阅太多事件更容易触发复用。ARM 平台的更多差异见 ARM 平台通信实战。

5.3 计数器复用 (multiplexing) 与缩放外推

multiplexing订阅事件超过物理计数器时，内核轮流调度；每个事件只统计一部分时间，再按启用占比线性外推。
图 5.1 · 规避：每次只订 2–4 个事件；-M 用官方 metric group；需要同时性时 -e '{cycles,instructions}' 绑成一组。

5.4 读懂 <not counted> 与 <not supported>

not supported
这台机器/这个 PMU 没有这个事件。常见于虚拟机，或把 x86 原生名搬到了 ARM。
not counted
事件存在，但整段测量一次都没排上计数器（复用极端），或程序跑得太短。加长时间、减少订阅。
06

perf stat 判读 · 从数字到结论

默认输出逐行拆解 · 常用开关 · 三条健康线与它们的例外 · 别把比率当结论

6.1 默认输出逐行拆解

$ perf stat ./bench

     1,842.55 msec task-clock  # 0.998 CPUs utilized  ← ≈1 核纯算；0.2=在等
     6,231,882,104 cycles      # 3.382 GHz            ← 远低于标称=降频
     9,884,120,377 instructions# 1.59 insn per cycle  ← IPC；<1 流水线空转
        21,338,772 cache-misses# 3.42% of all cache   ← 多数平台是 LLC miss
       1.845821194 seconds time elapsed
task-clock
CPUs utilized ≈ task-clock / elapsed，是判断「单线程还是并行、有没有在等」的第一眼指标。0.998 = 纯 CPU 单线程；0.2 = 大部分在等（IO / 锁 / 睡眠）；3.6 ≈ 用了 3.6 个核。sys 占比高说明时间花在内核，该看 perf trace 而不是继续优化用户态算法。
insn per cycle
现代乱序核理论上限 4–6；实测 > 2 算舒展，< 1 说明大量空转。spin-wait 的 IPC 可以接近 4 却毫无产出。
cache-miss
别把比率当结论，工业界用 MPKI（1000 × misses / instructions）。cache-misses 在多数 Intel 上是 LLC miss，不是所有层级。

6.2 常用开关：-d / -r / --per-core / -M

命令目的判据
perf stat -d ./prog加一组常用细节事件-dd/-ddd 更容易触发复用
perf stat -r 10 ./bench10 次均值 ± 标准差抖动 > 5% 时「优化了 3%」是噪声
perf stat -a -- sleep 10整机一段时间看系统级，不绑到单个进程
perf stat -a --per-core …核间是否均衡单核打满 vs 平均看起来还好
perf stat -M IPC,L1MPKI官方 metric group让 perf 自己挑能同时上的组合
perf stat --delay 2000跳过启动预热只统计稳态

6.3 三条健康线与它们的例外

指标粗略健康线不达标最可能的原因例外 / 陷阱
IPC> 1.5访存等待、分支误预测、依赖链过长spin-wait 的 IPC 极高但纯属浪费；SIMD 代码 IPC 低但吞吐很好
branch-miss 率< 1-2%数据相关分支、虚函数分派、解释器循环分支总数很小时百分比抖动大
LLC-miss 率< 5-10%数据布局差、工作集超 LLC、指针追逐流式处理（如 memcpy 大块）本来就该 miss，看的是带宽不是命中率
IPC 高 ≠ 程序好。忙等自旋锁 IPC 可以接近 4。唯一的最终指标是墙钟时间 / 吞吐 / P99，微架构指标只解释"为什么"。

6.4 别把比率当结论

同一段代码可以靠"多跑廉价指令"把 miss 率 压下来，绝对次数没少。用 MPKI = 1000 × misses / instructions。L1D MPKI > 30 或 LLC MPKI > 5 就值得做数据布局（见 内存优化指南）。

07

Top-Down 微架构分析法

为什么"cache-miss 率"不够用 · 四象限 · perf stat --topdown 与 toplev · 逐层下钻

7.1 为什么"cache-miss 率"不够用

传统做法是盯着一堆孤立事件（cache-miss、branch-miss、TLB-miss……）逐个猜。问题是这些事件会互相掩盖：乱序执行可以把一次 L3 miss 藏在其他指令后面，此时 miss 数很高但根本不影响性能；反过来，一个不起眼的依赖链可能才是真正的瓶颈。

Intel 提出的 Top-Down Microarchitecture Analysis (TMA) 换了个思路：不数事件，而是做流水线槽位的会计。每个 cycle 的流水线有固定数量的 issue slot（比如 4 个），每个 slot 的命运只有四种可能，加起来必然是 100%。这就把"猜"变成了"分账"。

🎬 生活类比 · 餐厅上菜为什么慢 你只统计"厨房出错次数"没法定位问题。Top-Down 的做法是盯着每一个上菜窗口位问它空着的原因：
· 菜正常端走了 → Retiring（有效产出）
· 端出去发现点错了、倒掉重做 → Bad Speculation（分支预测失败）
· 窗口空着因为服务员没来取 → Frontend Bound（取指 / 译码供不上）
· 窗口空着因为厨房堵了 → Backend Bound（访存或计算资源不够）
四类加起来 100%，最大那一类就是你该优化的方向——不用再猜。

7.2 四象限：流水线槽位去哪了

图 7.1 · TMA Level-1 四象限。先看哪一格最大，再只往那一格下钻——这是 Top-Down 名字的含义，也是它比"逐个事件猜"高效的原因。

7.3 perf stat --topdown 与 toplev

命令目的判据
perf stat --topdown -a -- sleep 5Level-1 四象限较新内核 + Intel Skylake+
perf stat --topdown --td-level=2硬件直接到 Level-2Ice Lake+
perf stat -M TopdownL1同一套指标的 metric 写法和 --topdown 等价入口
toplev.py --level 3 -- ./prog自动下钻到 Level-4Intel pmu-tools；会处理复用
前提
依赖 slots 等固定计数器。虚拟机里基本别想（见 §3.4）。AMD / ARM 各有一套，不能照搬 Intel 公式。

7.4 逐层下钻的正确姿势

① 只追最大项
四格里挑占比最大的那格下钻。不要平均用力——Frontend 占 8% 时，把它优化到 0 也只提升 8%。
② 一层一层
Level-1 定方向 → Level-2 定子类（如 Backend → Memory Bound → L3 Bound）→ 到这一步才去看具体事件和代码。
③ 和火焰图交叉
Top-Down 告诉你"什么类型的瓶颈"，火焰图告诉你"哪个函数"。两者交叉才能定位到"哪个函数的哪类瓶颈"——单看任何一个都容易改错地方。
④ 别在噪声上下钻
负载不稳定时四象限占比会大幅漂移。先用 perf stat -r 确认可重复，再做 Top-Down。
08

perf record · 三种栈回溯的取舍

FP · DWARF · LBR · 三者对比与选型 · 采样频率：为什么是 99 而不是 100

"火焰图只有一层"、"栈里全是 [unknown]"、"perf.data 一分钟 2GB" 都出自同一个选择：-g 用哪种方式回溯。

8.1 FP · 快但要重编

默认 -g 即 FP：顺 rbp 链走，几乎免费。致命前提是 -O2 默认 -fomit-frame-pointer——链是断的。你的代码要加 -fno-omit-frame-pointer；系统库（libc / libstdc++）不是你能控制的，栈走到那里就断。Fedora 38 / Ubuntu 24.04 已把发行版重编为保留 FP，理由正是「可剖析性比省一个寄存器值钱」。保留 FP 通常约 1% 代价，对绝大多数服务这个交换值：换来生产随时能出可信火焰图。

8.2 DWARF · 准但数据暴涨

perf record --call-graph dwarf,16384 -F 99 -p <pid> -- sleep 30

中断时拷一段栈，事后用 .eh_frame 展开。不用重编，能穿过没有 frame pointer 的库，但每个样本多带 8–16 KB：-F 99 × 32 核 × 30 秒大约十万样本，perf.data 能到 GB 级，写盘本身变成新瓶颈。超过拷贝上限就底部断层，深递归要显式加大第二个参数。

8.3 LBR · 免费但很浅

读硬件 Last Branch Record，不碰内存。只有十几层，主场是 perf record -b 喂 AutoFDO / BOLT（§14.2），不是深栈火焰图。

图 8.1 · 能控制构建 → 全线 FP；临时查已发布二进制 → DWARF 并降频；只要分支热度 → LBR + -b（见 §14.2）。

8.4 三者对比与选型

FPDWARFLBR
需要重编目标要（-fno-omit-frame-pointer）不要不要
运行时开销极低中～高极低
perf.data 体积小大 10-50×小
栈深度完整完整（受拷贝上限）仅十几层
穿越无 FP 的库不行行行
硬件要求无无Intel（ARM 需 BRBE）
实战选型：① 能控制构建 → 全线加 -fno-omit-frame-pointer，用 FP，这是长期最省事的方案，也是生产常驻采集的唯一现实选择；② 临时排查第三方 / 已发布的二进制 → DWARF，但把频率降到 -F 49、时间缩到 10 秒；③ 只要"哪些分支热" → LBR + -b。

8.5 采样频率：为什么是 99 而不是 100

内核周期性活动常是 100 / 250 / 1000 Hz。-F 100 会锁相，火焰图凭空多一根宽柱。取质数 99 打破同步。不写 -F 时默认 4000 Hz，生产偏高。超过 perf_event_max_sample_rate 时内核会降频并在 dmesg 留言——跨机器对比会得出错结论。

report / annotate / diff

perf report 的四个必会开关 · perf annotate 与 skid / PEBS · perf diff

10.1 perf report 的四个必会开关

perf record -F 99 -g -p <pid> -- sleep 30
perf report --stdio --no-children
perf report -g graph,0.5,caller
perf report --sort dso
Children vs Self默认按 Children 排序，榜首往往是 main。--no-children 看 Self 才是叶子热点。Self 告诉你改哪个函数，Children 告诉你是谁在调它。--sort dso 一眼分清战场在自己代码、libc 还是第三方库——见过太多优化三天自己的代码，结果 60% 在 libssl。

10.2 perf annotate 与 skid / PEBS

skidPMU 溢出到中断真正打断之间隔了若干 cycle，记下的地址往往落在真正的"罪犯"之后几条，尤其是长延迟 load 的下一条。精确事件：Intel PEBS（-e cycles:pp，:ppp 为零 skid）、AMD IBS、ARM SPE。即便零 skid，乱序核上「哪条指令负责这次停顿」本身就是模糊概念。annotate 定位到"这个循环 / 这次访存"，不要精确到"就是这一条指令"。

10.3 perf diff · 优化前后对比

两份 perf.data 用 perf diff before.data after.data。价值在于让"开销搬家"无法藏起来——parse_header 降了 18%，却转移到 memmove。CI 里把它自动化。带调用上下文的图形对比见 差分火焰图。

访存与并发 · mem / c2c / lock / sched

12.1 perf mem · 这次 load 从哪一级拿到的

perf mem 用精确访存采样（PEBS / IBS / SPE）：热点那次 load 从哪一级拿到、等了多少 cycle。stat 只告诉你 miss 了多少次，mem 告诉你哪一行。

12.2 perf c2c · 假共享定位

HITMHit in Modified：一次读命中了另一个核 cache 里处于 Modified 状态的行，必须走一致性协议把脏行搬过来。perf c2c 按 cache line 排 HITM，并给出行内偏移——不只说「有假共享」，还指出是结构体里偏移 0 和 8 的两个字段在打架。
图 12.1 · 机制见 内存模型 · MESI；修法见 性能指南 §6 / 内存优化 §2.2。

12.3 perf lock · 锁竞争

次数和累计等待时长要分开看。次数多但短可接受；单次很长说明临界区里干了重活。锁优化见 性能指南 §13。

12.4 perf sched · 调度延迟

从「可运行」到真正上 CPU 的等待，完全不出现在 on-CPU 火焰图里，却是延迟敏感服务 P99 毛刺的头号嫌疑之一。忙机器上 sched record 几秒就能几百 MB，先短采。实时内核见 PREEMPT_RT 深入。

命令目的判据

perf c2c record -a -- sleep 10按 cache line 排 HITM高 HITM 的行内偏移就是假共享现场
perf lock contention -a -b锁等待（BPF，6.x+）次数多但短可接受；单次很长 = 临界区太重。死锁见 死锁调试
perf sched latency --sort max可运行到上 CPU 的等待毫秒级 → 超卖 / cgroup 限流 / 线程过多。调度细节见 进程调度，低延迟见 低延时实战

14.1 常驻采集 · continuous profiling

出问题再登机器：现场没了，也没有基线。做法是常驻低频：perf record -F 49 -g --call-graph fp -a -- sleep 10，每 5 分钟一次。必须用 FP（§8.4）。folded / pprof 入库；优先评估 Parca / Pyroscope（可观测性 §12）。收益是事后可追溯、版本间自动差分、跨实例横向对比，以及给容量规划一份「CPU 花在哪个模块」的真实数据。

14.2 喂给 AutoFDO / BOLT

生产分支 profile 能换 3–20% 的免费性能。这两个工具要的是 LBR 分支轨迹（-b / -j）而不是调用栈（§8.3）。收益来自热代码聚拢、降 icache miss，即 Frontend Bound。完整对比见 性能指南 §16c。

面试题（12 道分层）

基础（必答） · 中级（区分熟练度） · 高级（体现深度）

15.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础perf 和 Valgrind、ASan 有什么本质区别？

    三者解决的不是同一类问题：

    perf
    基于 PMU 的采样式性能剖析，不改二进制、开销 < 1%、能看到内核态，答"CPU 时间花在哪"。代价是统计性质，说不出精确调用次数。
    Valgrind
    动态二进制翻译，指令级完整计数，慢 10-30×。答"精确的指令数 / 可重现的 cache 模拟"，不能上生产。
    Sanitizers
    编译期插桩，查正确性（内存错误、data race），不是性能工具。
    一句话
    perf 是"抽样调查"，Valgrind 是"全员普查"，Sanitizer 是"体检"。
  2. 基础perf stat 你会重点看哪几个数字？怎么判断"CPU 用得健康"？
    四个数字
    ① CPUs utilized（task-clock / elapsed）判断是 CPU 密集还是在等；② IPC，> 1.5 算舒展、< 1 说明流水线大量空转；③ branch-miss 率，< 1-2%；④ LLC-miss 率 / MPKI，miss 高说明访存受限。再加上 user vs sys 比例判断时间是否花在内核。
    但要补一句
    这三条线只是启发式。IPC 高不等于程序好——自旋等待的 IPC 接近 4 却毫无产出。最终指标永远是墙钟时间 / 吞吐 / P99，微架构指标只用来解释原因。
    加分
    提到 cache-misses 在多数 Intel 平台上其实是 LLC miss 而不是"所有 cache miss"，以及用 MPKI 代替百分比来避免分母骗人。
  3. 基础给一个正在生产跑的服务出火焰图，完整命令是什么？每一步在做什么？ 
    sudo perf record -F 99 -g -p $(pgrep myapp) -- sleep 30
sudo perf script > out.perf
./stackcollapse-perf.pl out.perf | ./flamegraph.pl > flame.svg
    逐步
    record 以 99Hz 带调用栈采样 30 秒 → script 把二进制数据摊成文本栈 → stackcollapse 把相同栈合并成一行计数 → flamegraph.pl 画 SVG。
    为什么 99
    避免和内核 100/250/1000 Hz 的周期性活动锁相产生采样别名。
    读图注意
    横轴是样本占比且按字母序排，不是时间轴；要找的是宽而平的顶部平台；这只是 on-CPU，等锁 / 等 IO 的时间不会出现。
  4. 基础为什么 perf 的开销能低到 1% 以内？什么情况下会不止 1%？
    为什么低
    ① PMU 计数是硬件行为，不插一条指令；② -F 99 每核每秒只中断 99 次，单次几微秒；③ 样本走 mmap ring buffer 给用户态，不走 syscall。
    什么时候变贵
    ① --call-graph dwarf 每样本拷几 KB 栈；② 频率抬到几千 Hz；③ 订阅高频 tracepoint（sched:*）；④ 用 uprobe 挂热函数——那已经是每次触发都陷内核，不是采样了。

15.2 中级（区分熟练度）

  1. 中级火焰图只有一两层，或者栈里全是 [unknown]。怎么定位原因？
    先分类
    层数少 = 栈回溯断了；层数够但名字是地址 = 符号化失败。这是两条完全不同的排查路径，先分清能省一半时间。
    栈断
    ① 默认 -g 走 frame pointer，而 -O2 默认 -fomit-frame-pointer → 加 -fno-omit-frame-pointer 重编，或改用 --call-graph dwarf；② DWARF 模式下栈拷贝上限默认 8KB，深栈被截断 → dwarf,32768；③ LBR 只有十几层深度；④ perf_event_paranoid=2 时内核帧被禁，栈在进内核处断掉。
    符号化失败
    ① 二进制被 strip → 用 build-id 关联单独的 debuginfo 或配 DEBUGINFOD_URLS；② 分析用的二进制和采集时不是同一份（build-id 不匹配）；③ 内核符号看不到 → kptr_restrict=0；④ 容器 / 跨机分析路径找不到 → --symfs 或 perf archive；⑤ JIT 代码 → /tmp/perf-<pid>.map 或 perf inject --jit。
    加分
    提到 Fedora 38 / Ubuntu 24.04 已经把发行版整体重编为保留 frame pointer，正是因为"可剖析性 > 省一个寄存器"这个权衡在服务端成立。
  2. 中级perf record -g 的三种栈回溯方式怎么选？
    FP
    顺 frame pointer 链走。开销极低、数据量小、栈完整，但要求目标和依赖库都保留 frame pointer。
    DWARF
    中断时拷一段栈内存，事后用 .eh_frame CFI 离线展开。不用重编、能穿无 FP 的库，代价是数据量涨 10-50 倍、后处理很慢、深栈会被截断。
    LBR
    读硬件分支寄存器反推。零内存拷贝、几乎免费，但只有十几层深度、一般只覆盖用户态、依赖 Intel（ARM 需 BRBE）。
    选型
    能控制构建 → 全线 FP（生产常驻采集唯一现实选择）；临时查第三方二进制 → DWARF 但降频缩时长；只要分支热度（AutoFDO / BOLT）→ LBR + -b。
  3. 中级perf stat 输出里每行后面的 (62.13%) 是什么意思？会带来什么风险？
    是什么
    计数器复用（multiplexing）的启用时间占比。订阅的事件数超过物理计数器数量时，内核轮流把事件调度到计数器上，每个事件只在部分时间被真实统计，最后按占比线性外推。
    风险
    外推假设"负载在整段时间里是均匀的"。负载有相位（如启动 / 稳态 / GC）时这个假设不成立，误差可以很大。表现为荒谬的派生指标——branch-misses 比 branches 多、IPC 算出 12。占比低于 50% 时基本只能看数量级。
    怎么办
    ① 拆成多次跑，每次只订阅 2-4 个事件；② 用 {cycles,instructions} 事件组语法保证组内始终一起被调度；③ 用 -M 让 perf 按官方 metric group 挑组合；④ ARM 计数器更少（常见 6 个），更容易触发。
  4. 中级服务 CPU 只用了 15%，但 P99 延迟很高。用 perf 怎么查？
    第一判断
    瓶颈在 off-CPU。on-CPU 火焰图在这种场景下几乎无用——程序在睡觉的时间一个样本都不会被采到。
    路径
    ① perf sched latency --sort max 看调度延迟，毫秒级说明 CPU 超卖 / cgroup 限流 / 线程数超配；② perf lock contention -a -b 看锁等待，重点看"单次等待时长"而不只是次数；③ perf trace -s 看是否堵在某类 syscall；④ perf record --off-cpu 或 bpftrace 的 offcputime 出一张 off-CPU 火焰图。
    方法论
    on-CPU 图回答"在算什么"，off-CPU 图回答"在等什么"，两张宽度加起来才是墙钟时间。只看前者是"优化半天 P99 没动"的最常见原因。

15.3 高级（体现深度）

  1. 高级什么是 Top-Down 微架构分析法？它比"逐个看 cache-miss / branch-miss"强在哪？
    核心思想
    不数孤立事件，而是给流水线 issue slot 做会计。每个 slot 的归属只有四种：Retiring（有效产出）/ Bad Speculation（预测错白干）/ Frontend Bound（取指译码供不上）/ Backend Bound（后端堵住），四者合计 100%。先看哪格最大，再只往那格下钻。
    强在哪
    孤立事件会互相掩盖：乱序执行能把一次 L3 miss 藏在其他指令后面，此时 miss 数很高却不影响性能；反之一个不显眼的依赖链才是真瓶颈。Top-Down 直接量化"损失了多少执行带宽"，把猜变成分账。
    怎么跑
    perf stat --topdown（Skylake+），--td-level=2（Ice Lake+ 硬件支持），或 Intel pmu-tools 的 toplev.py --level 3 自动逐层下钻。
    边界
    依赖 slots 等固定计数器和精确事件，虚拟机里通常不可用；AMD / ARM 各有自己一套指标，不能直接照搬 Intel 的公式。负载不稳定时四象限占比会大幅漂移，要先确认可重复。
  2. 高级perf annotate 显示 70% 的开销压在一条 mov 上，能直接断定是这条指令慢吗？
    不能
    存在 skid：PMU 计数器溢出到中断真正打断执行之间隔了若干 cycle，记下的指令地址往往落在真正的"罪犯"之后几条。热点常常显示在长延迟 load 的下一条指令上。
    缓解
    用精确事件：Intel PEBS（-e cycles:pp，:ppp 为零 skid，硬件在事件发生点直接写现场）、AMD IBS、ARM SPE（-e arm_spe//）。perf mem / perf c2c 底层依赖的正是这套精确采样。
    更深一层
    即使零 skid，在乱序超标量核上"哪条指令负责这次停顿"本身就是模糊概念——多条指令并行在飞，停顿是资源竞争的结果。所以 annotate 的正确用法是定位到"这个循环 / 这次访存"，而不是"就是这一条指令"。要判断瓶颈类型该上 Top-Down。
  3. 高级要给公司几千个 C++ 服务实例上"常驻性能剖析"，你怎么设计？
    ① 采集
    perf record -F 49 -g --call-graph fp -a -- sleep 10，每实例每 5 分钟一次。必须用 FP 不能用 DWARF——DWARF 的数据量和后处理成本在这个规模上不可持续。前置条件是推动全公司构建加 -fno-omit-frame-pointer（约 1% 性能代价，换来永久可剖析性）。
    ② 符号
    这是真正的分水岭，比命令行技巧重要得多。CI 构建时：stripped 二进制进镜像，.debug 按 build-id 上传内部 debuginfod。这样生产镜像不变大，任何分析机都能完整符号化。
    ③ 权限
    给采集容器 CAP_PERFMON 而不是 privileged（内核 < 5.8 才退化到 CAP_SYS_ADMIN）；宿主机统一 perf_event_paranoid=1 + kptr_restrict=0，并评估侧信道风险后做取舍。
    ④ 存储与查询
    perf script → folded / pprof 格式，按 服务 × 版本 × 实例 × 时间 打标入库。核心能力是差分：版本间、实例间、时间段间。优先评估 Parca / Pyroscope 而不是自建。
    ⑤ 闭环
    不止给人看：把分支 profile 接到 AutoFDO，让生产 profile 反馈进编译流水线，形成"跑得越多编得越好"的循环。这才是常驻采集 ROI 最高的部分。
    要主动提的风险
    ① PMU 在虚拟机上可能不可用，需要区分实例类型；② 性能计数器是侧信道，多租户环境要评估；③ 采集本身的开销要有熔断（比如目标机负载过高时跳过本轮）；④ 符号服务器挂了会让所有历史数据变成一堆地址，它是关键依赖而不是附属设施。
  4. 高级同一份代码在 x86 上测得很好，搬到 ARM 服务器上 perf 结论完全对不上。可能是什么原因？
    ① 事件名不通用
    命令一样但原生事件名完全不同：x86 的 LLC-load-misses 在 ARM 上要用 ll_cache_miss_rd / l2d_cache_refill 之类，还随核型号变。换机器第一件事是 perf list。
    ② 计数器更少
    ARM 常见 6 个可编程计数器（x86 常见 4 通用 + 3 固定），同样的 -e 列表在 ARM 上更容易触发复用外推，数字可信度下降。
    ③ 精确采样机制不同
    没有 PEBS，对应的是 ARM SPE（-e arm_spe//），行为和字段都不一样；LBR 对应 BRBE 且只有较新核才有，--call-graph lbr 往往直接不可用。
    ④ 微架构差异本身
    cache 层次与容量、cache line 大小（ARM 上可能是 128B，影响 alignas(64) 的假共享修复是否够）、内存序模型更弱（seq_cst 代价显著更高）、SIMD 是 NEON/SVE 而非 AVX。结论对不上很可能是真的不一样，不是测错了。
    正确做法
    不要移植"事件列表"，要移植"问题"。先用跨平台通用的 cycles / instructions / task-clock 建立 IPC 与时间分布，确认瓶颈类型；再按目标平台手册挑该平台的原生事件下钻。跨平台的更多差异见 ARM 平台通信实战。

16.2 动手清单

  1. 在自己的服务上跑一遍 perf stat -d，把 IPC / branch-miss / LLC-miss 记下来当基线。
  2. 给项目加 -fno-omit-frame-pointer 重编，对比加之前 / 之后火焰图的层数差异——亲眼看到栈断是怎么回事。
  3. 故意写一段假共享代码（两个线程各自 ++ 相邻的 counter），用 perf c2c 把它抓出来，再 alignas(64) 修掉，记录加速比。
  4. 把服务的二进制 strip 后再分析一次，走通"build-id + 单独 debuginfo"的符号化链路。
  5. 做一次 perf diff：随便优化一处，验证"开销是不是只是搬家了"。
  6. 如果有裸金属机器，跑一次 perf stat --topdown，判断你的服务是 Frontend 还是 Backend 受限，再决定下一步优化方向。
