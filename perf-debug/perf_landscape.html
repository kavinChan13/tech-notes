01

perf 是什么 · 工具谱系定位

一句话定位 · 和 valgrind / ASan / eBPF / VTune 的分工 · 本文覆盖范围与阅读顺序

先把最容易混淆的一点说清楚：perf 不是"一个测速工具"，而是 Linux 内核 perf_event 子系统的官方前端。内核负责采集，perf 负责下发配置、收数据、符号化、出报告。理解这条分界线，后面所有"为什么它能做 X 却做不了 Y"的问题都会自然有答案。

1.1 一句话定位

perf基于硬件性能计数器（PMU）+ 内核事件的采样式剖析器。它不改你的二进制、不重启你的进程，用统计抽样的方式回答"CPU 时间花在哪、为什么慢"。
🎬 生活类比 · 人口普查 vs 抽样调查 Valgrind / Callgrind 像全员普查：每条指令都过一遍，数据绝对完整，但整个城市停摆（慢 10-30 倍）。
perf 像抽样调查：每秒随机拦下 99 个人问"你现在在干什么"，跑 30 秒就有 3000 个样本。它永远说不出"第 12345 次调用发生了什么"，但能非常准确地告诉你"70% 的人都堵在同一个路口"。
性能优化要的恰好是后者——你要找的是热点分布，不是完整流水账。

这几个工具经常被摆在一起比较，但它们的坐标其实差得很远。横轴是观测层次（只看自己进程 → 看整个内核），纵轴是运行时开销（决定了能不能上生产）：

02

采样原理 · PMU 与 perf_event_open

计数模式 vs 采样模式 · 一次采样中断到底发生了什么 · 四类事件源 · 为什么开销能压到 1% 以内

2.1 计数模式 vs 采样模式

整个 perf 只有两种工作模式，所有子命令都是这两种的包装：

计数模式 (counting)

让 PMU 从 0 开始纯累加，程序跑完读一次结果。产出的是"这段时间一共发生了 N 次"。

代表 perf stat

特点几乎零开销（就是几条寄存器读写）、数字精确、但完全不知道发生在哪行代码。

采样模式 (sampling)

给计数器预设一个溢出阈值，每溢出一次就触发中断，内核趁机记下"当前指令地址 + 调用栈 + pid/tid/cpu/时间戳"。

代表 perf record / perf top

特点能定位到函数甚至指令，但结果是统计意义上的——样本太少就会失真。

period / frequency采样密度的两种表达。-c 1000000 是"每 100 万个事件采一次"（固定周期，period）；-F 99 是"每秒采 99 次"（固定频率，frequency，内核自动动态调整 period 去逼近这个频率）。日常用 -F，需要跨机器可比的绝对计数时才用 -c。

2.2 一次采样中断到底发生了什么

图 2.1 · 采样链路五步。注意第 ⑤ 步：perf.data 里存的是裸地址，符号化发生在 perf report 阶段——这就是第 9 章所有符号问题的根源。
面试常问"perf 会不会漏样本"。会。两处会漏：① ring buffer 打满（提高 -m 缓冲页数、降低频率）；② 内核限流——单次采样处理超时，内核会打印 "perf interrupt took too long, lowering kernel.perf_event_max_sample_rate" 并主动降频，这时你的 -F 4000 已经悄悄不生效了。

2.3 四类事件源

类别由谁提供例子关键约束
Hardware eventCPU 的 PMUcycles instructions branch-misses cache-misses计数器个数有限；虚拟机里常不可用
Software event内核自己的计数器cpu-clock task-clock page-faults context-switches永远可用，没 PMU 时的兜底
Tracepoint内核里的静态埋点sched:sched_switch syscalls:sys_enter_write数量巨大但位置固定，改不了
Dynamic probekprobe / uprobeperf probe 现场加的探针灵活；取变量值要 debuginfo
没 PMU 也能干活：云上虚拟机常常拿不到 cycles，但 cpu-clock 这个 software event 一定有。perf record -e cpu-clock -F 99 -g 依然能出一张可用的 on-CPU 火焰图，只是没法看 IPC / cache miss。这是很多人在 EC2 上"perf 完全用不了"的误判来源。

2.4 为什么开销能压到 1% 以内

计数免费
PMU 累加是硬件行为，程序照原速跑，不插一条指令。这一点是它和 Valgrind / ASan 的根本区别。
中断稀疏
-F 99 意味着每核每秒只被打断 99 次。单次中断处理约几微秒，算下来 CPU 占用在千分之几量级。
无 syscall
样本经 mmap 共享的 ring buffer 交给用户态，不走 read/write，避免了每样本一次系统调用。
但会变贵
开销主要来自你自己的选择：--call-graph dwarf 每个样本都要拷贝几 KB 栈内存（数据量能涨 10-50 倍）；-F 10000 把中断频率抬两个数量级；订阅高频 tracepoint（如 sched:*）在忙机器上每秒几十万条。"perf 很轻"是默认配置下的结论，不是无条件的。
03

权限模型 · 容器与生产环境

perf_event_paranoid 四档语义 · CAP_PERFMON · 容器 / K8s 里怎么跑 · 虚拟机里 PMU 常常根本不存在

"在自己机器上好使，上了生产 / 容器就报 Permission denied" —— 这是 perf 第一大门槛。它不是配置繁琐，而是性能计数器天然是侧信道：能观测别的进程执行细节，等于能推断它的秘密。所以内核默认收得很紧。

3.1 perf_event_paranoid 四档语义

$ cat /proc/sys/kernel/perf_event_paranoid
2
值非特权用户能做什么典型场景
-1几乎全放开，含 raw tracepoint专用性能实验机；生产别这么设
0可做系统级（-a）采集，禁 raw tracepoint需要整机火焰图的性能环境
1禁系统级 / per-cpu 采集，自己的进程可以共享开发机
2再禁内核态采样，只剩用户态多数发行版默认
3+非特权用户彻底禁用（Debian/Ubuntu 的额外补丁档）加固过的系统
paranoid=2 下你依然能剖析自己的进程，只是栈会在进入内核的地方断掉——火焰图底部一大片 [unknown]，看起来像"符号有问题"，其实是权限问题。想看到 __do_sys_write → ext4_file_write_iter 这类内核帧，至少要 paranoid ≤ 1，并且 kptr_restrict=0（见 §9.1）。

3.2 CAP_PERFMON —— 别再给 root

Linux 5.8 之前，"让 CI 里的采集脚本能跑 perf"通常靠 sudo 或 CAP_SYS_ADMIN——而 CAP_SYS_ADMIN 几乎等于 root，为了看个火焰图付出的代价太大。5.8 引入了细粒度的 CAP_PERFMON：

# 只给 perf 观测能力，不给挂载 / 改内核参数等一揽子权限
$ sudo setcap cap_perfmon,cap_sys_ptrace,cap_syslog=ep $(which perf)

# 或者在容器 / systemd 单元里声明
securityContext:
  capabilities:
    add: ["PERFMON"]
CAP_PERFMON
访问 perf_event 子系统。
CAP_SYS_PTRACE
读目标进程的 /proc/<pid>/maps 与内存，符号化和 DWARF 回溯需要。
CAP_SYSLOG
读 /proc/kallsyms 里的内核符号地址（受 kptr_restrict 影响）。

3.3 容器 / K8s 里怎么跑

容器里的 perf 有三个独立的坑，必须分开解决：

① 权限
perf_event_paranoid 是宿主机内核的全局参数，容器内改不了（/proc/sys 只读）。要么调宿主机，要么给 Pod 加 CAP_PERFMON（老内核只能 privileged）。
② PID 视角
在宿主机上 perf record -p <宿主 pid> 采到的样本，地址属于容器里的二进制。最省事的做法是在宿主机采集、在宿主机符号化，通过 --symfs 指到容器 rootfs（见 §9.4）；在容器内采集则需要 hostPID: true 才能看到别的进程。
③ 符号
生产镜像通常 strip 过。要么构建时把 .debug 单独产物存进符号服务器（配 debuginfod），要么保留 build-id 后期匹配。先把这件事做好，再谈采集——否则你会拿到一堆地址。

3.4 虚拟机里 PMU 常常根本不存在

这一点在云上排查时极容易误判。虚拟化环境是否暴露 PMU 取决于 hypervisor 配置，很多实例类型直接不给：

$ perf stat -e cycles,instructions ./bench

 Performance counter stats for './bench':

   <not supported>      cycles
   <not supported>      instructions
看到 <not supported> 先别怀疑自己：① 换 software event（cpu-clock / task-clock）继续做时间分布剖析；② 需要真实微架构指标时，换 裸金属实例或开了 vPMU 的实例类型；③ KVM 宿主机可以给 guest 开 -cpu host,pmu=on。不要把云上测出的 IPC / cache-miss 当作可信基准。

05

事件命名 · perf list 与计数器复用

三层事件名 · 跨平台差异 · 计数器复用与缩放外推 · 读懂 <not counted> 与 <not supported>

5.1 三层事件名：通用 / 原生 / raw

层级写法可移植性什么时候用
通用事件（generalized）cycles instructions cache-misses高，跨架构可用默认首选
原生事件（native / PMU）MEM_LOAD_RETIRED.L3_MISS、l2d_cache_refill绑定具体微架构通用事件太粗，要精确语义
raw 事件r04c5、cpu/event=0xc5,umask=0x0/绑定到具体型号手册里有、perf 还没收录的事件
cache-misses 是最容易被误解的事件名。它在多数 Intel 微架构上映射到 LLC（末级缓存）miss，不是"所有层级的 cache miss"。想区分 L1 / L2 / LLC 必须用 L1-dcache-load-misses、LLC-load-misses 这类更明确的名字，或者直接上原生事件。看到"cache-miss 率 3%，很健康"这种结论，先问一句：哪一级？

5.2 跨平台：x86 与 ARM 的事件名不通用

换到 ARM 服务器（Graviton / 鲲鹏 / Ampere）上，perf 命令行完全一样，但一旦用了原生事件就全部失效：

想测x86 (Intel)ARM (aarch64)
LLC 读 missLLC-load-misses / MEM_LOAD_RETIRED.L3_MISSll_cache_miss_rd / l2d_cache_refill（随核型号变）
精确访存采样PEBS（:pp 修饰符）ARM SPE：perf record -e arm_spe//
分支栈LBR（-b / --call-graph lbr）BRBE（较新核）或退化到 FP/DWARF
换机器第一条命令永远是 perf list（配合 perf list cache / perf list pmu 过滤）。ARM 的 PMU 可编程计数器通常只有 6 个（x86 常见 4 通用 + 3 固定），一次订阅太多事件更容易触发复用。ARM 平台的更多差异见 ARM 平台通信实战。

5.3 计数器复用 (multiplexing) 与缩放外推

multiplexing当你订阅的事件数超过物理计数器数量时，内核会轮流把它们调度到计数器上，每个事件只在部分时间被真实统计，最后按"实际启用时间占比"线性外推成完整值。
$ perf stat -e cycles,instructions,cache-references,cache-misses,\
branches,branch-misses,L1-dcache-loads,L1-dcache-load-misses ./bench

     3,214,556,102      cycles                    # (74.85%)  ← 只统计了 74.85% 的时间
     5,102,338,914      instructions              # (74.91%)
       182,441,203      cache-references          # (62.13%)
        21,338,772      cache-misses              # (49.77%)  ← 外推自不到一半的样本
怎么识别
输出行尾出现 (xx.xx%) 就是发生了复用。百分比越低，数字越不可信；低于 50% 时基本只能看数量级。
怎么规避
① 拆成多次跑，每次只订阅 2-4 个事件；② 用 -M 指定官方 metric group，perf 会自动挑能同时上的组合；③ 需要严格同时性时，用 {} 声明事件组：-e '{cycles,instructions}'，保证组内事件始终一起被调度。
最坑的表现
外推会产生非整数或明显不合理的派生指标——比如 branch-misses 比 branches 还多、IPC 算出来 12。看到荒谬的比率，先怀疑复用，而不是怀疑 CPU。

5.4 读懂 <not counted> 与 <not supported>

not supported
这台机器/这个 PMU 压根没有这个事件。常见于虚拟机（没暴露 PMU）、或把 x86 原生事件名搬到了 ARM 上。
not counted
事件存在，但整个测量期间一次都没被调度到计数器上（复用调度的极端情况），或者程序跑得太短。加长运行时间、减少订阅事件数。

cycles / GHz
算出的实际频率。明显低于标称频率说明有降频（散热、governor、AVX 频率墙），基准测试前必须先排除。
insn per cycle

context-switches

切换多 → 线程数超配 / 锁竞争；迁移多 → 没绑核，cache 局部性被反复打掉。低延迟场景这两个要接近 0。
user vs sys
sys 占比高说明时间花在内核——syscall 太频、page fault 太多、网络栈开销大。这时该看的是 perf trace 而不是继续优化用户态算法。

6.2 常用开关：-d / -r / --per-core / -M

# -d 加一组常用细节事件；-dd / -ddd 更细（注意会触发复用）
perf stat -d ./prog

# -r 10 跑 10 次，输出均值 ± 标准差 —— 微基准必用
perf stat -r 10 ./bench

# 只测某段时间的整机情况
perf stat -a -- sleep 10

# 看负载在核间是否均衡 / 有没有单核打满
perf stat -a --per-core -e cycles,instructions -- sleep 5

# 用官方 metric group，让 perf 自己挑事件组合并算派生指标
perf stat -M IPC,L1MPKI --metric-only ./prog

# 只统计某个阶段：用信号或 --delay 跳过启动预热
perf stat --delay 2000 -- ./prog
perf stat -r 10 输出的 标准差比均值更有价值。抖动 > 5% 时任何"优化了 3%"的结论都是噪声。这是"优化被 review 打回"最常见的原因。

指标粗略健康线不达标最可能的原因例外 / 陷阱
IPC> 1.5访存等待、分支误预测、依赖链过长spin-wait 的 IPC 极高但纯属浪费；SIMD 代码 IPC 低但吞吐很好
branch-miss 率< 1-2%数据相关分支、虚函数分派、解释器循环分支总数很小时百分比抖动大
LLC-miss 率< 5-10%数据布局差、工作集超 LLC、指针追逐流式处理（如 memcpy 大块）本来就该 miss，看的是带宽不是命中率
IPC 高 ≠ 程序好。一个忙等自旋锁的循环 IPC 可以接近 4，但它一件有用的事都没干。同理，"优化后 IPC 从 0.8 涨到 2.0 但墙钟时间没变"是常见幻觉——你可能只是把工作换成了更廉价但更多的指令。唯一的最终指标永远是墙钟时间 / 吞吐 / P99，微架构指标只用来解释"为什么"。

6.4 别把比率当结论

比率的分母会骗人。同一段代码，你可以通过"多执行一些廉价指令"把 miss 率 压下来，而 miss 的绝对次数一点没少。工业界更常用 MPKI（Misses Per Kilo-Instructions）来消掉这个歧义：

MPKI1000 × misses / instructions。以"每千条指令 miss 多少次"衡量，不受"指令总数变化"干扰。经验尺度：L1D MPKI > 30 或 LLC MPKI > 5 就值得专门做数据布局优化（见 内存优化指南）。

Top-Down 微架构分析法

为什么"cache-miss 率"不够用 · 四象限 · perf stat --topdown 与 toplev · 逐层下钻

7.1 为什么"cache-miss 率"不够用

传统做法是盯着一堆孤立事件（cache-miss、branch-miss、TLB-miss……）逐个猜。问题是这些事件会互相掩盖：乱序执行可以把一次 L3 miss 藏在其他指令后面，此时 miss 数很高但根本不影响性能；反过来，一个不起眼的依赖链可能才是真正的瓶颈。

Intel 提出的 Top-Down Microarchitecture Analysis (TMA) 换了个思路：不数事件，而是做流水线槽位的会计。每个 cycle 的流水线有固定数量的 issue slot（比如 4 个），每个 slot 的命运只有四种可能，加起来必然是 100%。这就把"猜"变成了"分账"。

🎬 生活类比 · 餐厅上菜为什么慢 你只统计"厨房出错次数"没法定位问题。Top-Down 的做法是盯着每一个上菜窗口位问它空着的原因：
· 菜正常端走了 → Retiring（有效产出）
· 端出去发现点错了、倒掉重做 → Bad Speculation（分支预测失败）
· 窗口空着因为服务员没来取 → Frontend Bound（取指 / 译码供不上）
· 窗口空着因为厨房堵了 → Backend Bound（访存或计算资源不够）
四类加起来 100%，最大那一类就是你该优化的方向——不用再猜。

7.2 四象限：流水线槽位去哪了

图 7.1 · TMA Level-1 四象限。先看哪一格最大，再只往那一格下钻——这是 Top-Down 名字的含义，也是它比"逐个事件猜"高效的原因。

7.3 perf stat --topdown 与 toplev

# 较新内核 + Intel Skylake 以后的核，perf 直接给 Level-1 分解
$ perf stat --topdown -a -- sleep 5

# 指定层级（Ice Lake 之后硬件直接支持到 Level-2）
$ perf stat --topdown --td-level=2 ./prog

# 用 metric group 的方式取同样的指标
$ perf stat -M TopdownL1 ./prog

# 更完整的实现：Intel pmu-tools 的 toplev，能自动逐层下钻到 Level-4
$ toplev.py --level 3 -- ./prog
perf 原生
够用、零依赖，但层级和覆盖的微架构有限。AMD 有自己的一套（-M 下的 pipeline utilization 指标），ARM 通常要靠厂商工具或自己按手册组事件。
toplev
Intel 官方 pmu-tools 里的脚本，内置各代微架构的完整 TMA 公式树，会自动处理计数器复用与多次运行。做微架构级优化时值得装。
前提
Top-Down 依赖 slots 之类的固定计数器和精确事件。虚拟机里基本别想（见 §3.4），要裸金属。

7.4 逐层下钻的正确姿势

① 只追最大项
四格里挑占比最大的那格下钻。不要平均用力——Frontend 占 8% 时，把它优化到 0 也只提升 8%。
② 一层一层
Level-1 定方向 → Level-2 定子类（如 Backend → Memory Bound → L3 Bound）→ 到这一步才去看具体事件和代码。
③ 和火焰图交叉
Top-Down 告诉你"什么类型的瓶颈"，火焰图告诉你"哪个函数"。两者交叉才能定位到"哪个函数的哪类瓶颈"——单看任何一个都容易改错地方。
④ 别在噪声上下钻
负载不稳定时四象限占比会大幅漂移。先用 perf stat -r 确认可重复，再做 Top-Down。

perf record · 三种栈回溯的取舍

FP · DWARF · LBR · 三者对比与选型 · 采样频率：为什么是 99 而不是 100

这一章是 perf 使用者最容易翻车、也最能体现深度的地方。"火焰图只有一层"、"栈里全是 [unknown]"、"perf.data 一分钟 2GB" —— 三个症状都出自同一个选择：-g 到底用哪种方式回溯调用栈。

8.1 FP · 快但要重编

默认方式（-g 等价于 --call-graph fp）。依赖 frame pointer 链：每个栈帧的 rbp 指向上一帧的 rbp，内核只要顺着这条链走几步就能拿到整个栈——快到几乎免费。

致命前提
编译器默认开 -fomit-frame-pointer（-O2 起就省掉了 rbp 当通用寄存器用），链子是断的。你的代码要加 -fno-omit-frame-pointer；而系统库（libc / libstdc++）不是你能控制的——栈走到 libc 就断。
好消息
Fedora 38（2023）和 Ubuntu 24.04 LTS 已经把发行版全量重编为保留 frame pointer，理由正是"可剖析性比省一个寄存器值钱"。在这些系统上 FP 回溯的可用性大幅提升。
代价
保留 frame pointer 的性能损失通常在 1% 量级（个别热点小函数更明显）。对绝大多数服务，这个交换是值的：换来的是生产环境随时能出可信火焰图。

8.2 DWARF · 准但数据暴涨

perf record --call-graph dwarf,16384 -F 99 -p <pid> -- sleep 30

不依赖 frame pointer，而是在中断时把栈内存原样拷一份（默认 8192 字节，可调），事后用二进制里的 DWARF CFI（.eh_frame）信息离线展开。

优点
不用重编目标程序，能穿过没有 frame pointer 的库；深栈也能完整拿到（只要没被截断）。
代价一：体积
每个样本多带 8-16KB。-F 99 × 32 核 × 30 秒 ≈ 十万样本 ≈ GB 级 perf.data。写盘本身就可能成为新的瓶颈。
代价二：后处理
展开发生在 perf report/script 阶段，大文件解析要几分钟到几十分钟，内存占用也高。
代价三：截断
栈超过拷贝上限就被切掉，表现为火焰图底部莫名断层。深递归 / 深模板嵌套要显式加大第二个参数。

8.3 LBR · 免费但很浅

perf record --call-graph lbr -F 99 -p <pid> -- sleep 30
LBRLast Branch Record，Intel CPU 里一组硬件环形寄存器，自动记录最近若干次分支的源/目标地址。perf 从其中的 call 记录反推调用栈，完全不用碰内存。
优点
不需要 frame pointer，不需要拷栈，开销和数据量都极小。
硬限制
寄存器深度有限（常见 16 / 32 条），只能拿到最近十几层调用。深栈的 C++ 服务通常不够。而且一般只覆盖用户态。
真正的主场
LBR 的分支栈（perf record -b）是 AutoFDO 与 BOLT 的输入格式——它们要的不是完整调用栈，而是"哪些分支被走到了"，正好对上。见 §14.2。

8.4 三者对比与选型

FPDWARFLBR
需要重编目标要（-fno-omit-frame-pointer）不要不要
运行时开销极低中～高极低
perf.data 体积小大 10-50×小
栈深度完整完整（受拷贝上限）仅十几层
穿越无 FP 的库不行行行
硬件要求无无Intel（ARM 需 BRBE）
实战选型：① 能控制构建 → 全线加 -fno-omit-frame-pointer，用 FP，这是长期最省事的方案，也是生产常驻采集的唯一现实选择；② 临时排查第三方 / 已发布的二进制 → DWARF，但把频率降到 -F 49、时间缩到 10 秒；③ 只要"哪些分支热" → LBR + -b。

8.5 采样频率：为什么是 99 而不是 100

几乎所有教程都写 -F 99，原因不是玄学：内核的周期性活动（timer tick、各种定时任务）往往正好是 100 / 250 / 1000 Hz。用整数 100 采样会和它们锁相，导致你总在同一个相位上采到样本，火焰图里凭空出现一根不该那么宽的柱子（采样别名 / aliasing）。取质数 99 打破这种同步。

99 / 97
生产默认。30 秒能拿到约 3000 样本 × 核数，对定位 top 热点足够。
999
短事务、需要更细分辨率时用，注意开销和数据量都涨 10 倍。
不写 -F
perf record 默认频率是 4000 Hz，对生产偏高。忘记写 -F 是新手最常见的开销来源。
被内核降频
超过 kernel.perf_event_max_sample_rate 时内核会强制降频并在 dmesg 留言。这时你以为的采样率和实际的不一致，跨机器对比会得出错误结论。

符号化 · 为什么栈里全是 [unknown]

六种典型原因 · build-id 与 debuginfod · JIT / 解释型代码 · 容器：--symfs 与 buildid-cache

回忆 §2.2：perf.data 里存的是裸地址。把地址翻成 MyClass::process(Request&) 这一步叫符号化，发生在 report 阶段，需要"地址 → 二进制 → 符号表"三段链路都对上。任何一段断了，你就看到 [unknown] 或 0x00007f2a3c1b4e20。

9.1 六种典型原因

①
二进制被 strip 了。生产镜像常规操作。→ 构建时把符号单独产出（objcopy --only-keep-debug），并在分析机上通过 build-id 关联回来。
②
分析时用的二进制和采集时不是同一个（重新编译过、版本不同）。build-id 不匹配，perf 会警告但很多人忽略。→ 认 build-id，别认路径。
③
栈本身就是断的，不是符号问题。见 第 8 章：FP 被优化掉、DWARF 栈被截断、LBR 深度不够。先分清"栈断"还是"名字翻不出来"——前者表现为层数少，后者表现为层数够但名字是地址。
④
内核符号不可见。kptr_restrict=1/2 时 /proc/kallsyms 里的地址全是 0，内核帧显示为 [unknown]。→ sysctl kernel.kptr_restrict=0（并保证 perf_event_paranoid ≤ 1）。
⑤
代码是运行时生成的（JIT、动态生成的 trampoline）。地址不属于任何磁盘文件。→ 见 §9.3。
⑥
在容器 / 另一台机器上分析，perf 按 perf.data 里记录的绝对路径去找文件，找不到。→ 见 §9.4。

9.2 build-id 与 debuginfod

build-id链接器写进 ELF 的一段唯一哈希（.note.gnu.build-id）。它是"这份二进制"的身份证，perf 用它而不是文件路径来判断符号文件是否匹配。readelf -n ./myapp | grep -i build 可以看到。
# 采集机：把二进制 + 调试信息塞进本地缓存（~/.debug）
$ perf buildid-cache -a ./myapp

# 看这份 perf.data 依赖哪些 build-id，缺哪个一目了然
$ perf buildid-list -i perf.data

# 让 perf 自动去符号服务器拉 debuginfo（现代发行版都提供）
$ export DEBUGINFOD_URLS="https://debuginfod.elfutils.org/"
$ perf report
工程化建议：CI 构建时把 stripped 二进制发布、把 .debug 按 build-id 上传到内部符号服务器（自建 debuginfod 即可）。这样生产采集的 perf.data 拿到任何一台分析机上都能完整符号化，而生产镜像不必因为要保留符号而变大。这是"能不能在生产用 perf"的真正分水岭，比任何命令行技巧重要。

9.3 JIT / 解释型代码

纯 C++ 服务通常不涉及，但只要进程里嵌了 JIT（LuaJIT、V8、JVM、某些 SQL 引擎的表达式编译、PyTorch inductor 生成的 kernel），就会遇到"一大片地址翻不出来"。两种机制：

perf-PID.map
最简单的约定：运行时进程自己往 /tmp/perf-<pid>.map 追加 起始地址 长度 符号名 三列文本，perf report 会自动读取。很多运行时有开关或第三方 agent 来生成。
jitdump + inject
更完整的方案：运行时写 /tmp/jit-<pid>.dump（含代码字节和调试行号），采集后跑 perf inject --jit -i perf.data -o jit.data，perf 会把 JIT 代码物化成一堆小 ELF 并重写样本，之后连 perf annotate 都能用。
注意时序
map 文件必须在 report 时仍然存在，而且进程重启后 pid 复用会串味。容器里 /tmp 是容器内的，宿主机 perf 看不到——需要挂出来。

9.4 容器：--symfs 与 buildid-cache

# 场景：在宿主机采集容器里的进程，在宿主机分析

# 1) 找到容器的 rootfs（或直接用 /proc/<pid>/root）
$ perf report --symfs /proc/12345/root -i perf.data

# 2) 或者把容器里的二进制先导出来入缓存
$ docker cp mysvc:/usr/local/bin/myapp /tmp/myapp
$ perf buildid-cache -a /tmp/myapp
$ perf report -i perf.data

# 3) 跨机分析：打包时带上依赖的二进制与符号

10.1 perf report 的四个必会开关

# ① 文本输出，可以塞进 CI 日志 / diff
perf report --stdio

# ② 调用图方向与阈值：caller 视角、只展开占比 > 0.5% 的分支
perf report -g graph,0.5,caller

# ③ 关掉"把子函数开销累加到父函数"，只看自身开销
perf report --no-children

Children vs Selfperf report 默认按 Children（含所有被调用者）排序，所以榜首往往是 main / 事件循环——正确但没用。--no-children 切到 Self（只算函数自己那几条指令），才能看到"真正在烧 CPU 的叶子函数"。两个视角都要看：Self 告诉你改哪个函数，Children 告诉你是谁在调它。
--sort dso 是个被严重低估的开关。它一眼告诉你"CPU 花在自己代码、libc、还是某个第三方库上"。见过太多"优化了三天自己的代码"，结果 --sort dso 显示 60% 在 libssl 里。先分清战场，再冲锋。

10.2 perf annotate 与 skid / PEBS

$ perf annotate -s hot_func --stdio

       │     for (size_t i = 0; i < n; ++i) {
  1.20 │ 40:   add    $0x8,%rax
       │       sum += data[idx[i]];
 71.40 │       mov    (%rcx,%rdx,8),%rdx     ← 71% 集中在这条 load
  3.10 │       add    %rdx,%rsi

看到 71% 压在一条 mov 上，直觉是"这条指令很慢"。但要小心归因误差：

skidPMU 溢出到中断真正打断执行之间隔了若干个 cycle，记录下来的指令地址往往落在真正的"罪犯"之后几条。这就是为什么热点常常显示在一条无辜的指令上，尤其是在长延迟 load 的下一条指令上。
解法：精确事件
Intel 的 PEBS 让硬件在事件发生时直接写下精确现场。用修饰符开启：-e cycles:pp（:p 越多越精确，:ppp 为零 skid）。AMD 对应 IBS，ARM 对应 SPE。
仍要留心
即便精确采样，乱序执行也让"哪条指令负责这次停顿"本身就是模糊概念。annotate 用来定位到"这个循环 / 这次访存"，不要精确到"就是这一条指令"。

10.3 perf diff · 优化前后对比

$ perf record -o before.data -F 99 -g ./prog_v1
$ perf record -o after.data  -F 99 -g ./prog_v2
$ perf diff before.data after.data

# Baseline  Delta      Shared Object     Symbol
# ........  .........  ................  ...............................
    31.20%    -18.40%  myapp             [.] parse_header
     4.10%     +6.80%  libc.so.6         [.] __memmove_avx_unaligned
     2.30%     +3.10%  myapp             [.] Buffer::grow
上面这份 diff 讲了一个典型故事：parse_header 确实降了 18%，但开销转移到了 memmove 和 Buffer::grow——很可能优化引入了额外拷贝。perf diff 的价值就在于让"开销搬家"这件事无法藏起来，而单看两张火焰图很容易漏掉。CI 里跑基准时把它自动化，回归会自己浮出来。

火焰图 · on-CPU / off-CPU / 差分

11.1 生成管线与每一步在做什么

$ git clone https://github.com/brendangregg/FlameGraph

$ sudo perf record -F 99 -g -p $(pgrep myapp) -- sleep 30
$ sudo perf script > out.perf
$ ./FlameGraph/stackcollapse-perf.pl out.perf > out.folded
$ ./FlameGraph/flamegraph.pl out.folded > flame.svg
perf script
把二进制 perf.data 摊成"一个样本一段文本栈"。这是唯一的出口，接 pprof / 自研工具也走这里。
stackcollapse
把每个样本的多行栈压成一行 a;b;c 1，并把相同栈合并计数。这一步之后就没有时间信息了——这解释了下一节的"宽度不是时间轴"。
flamegraph.pl
按字母序递归排布成 SVG。颜色默认只是随机区分，没有语义（除非用 --color=java/js 之类的调色板）。

11.2 怎么读：宽度是量，不是时间轴

纵轴
调用栈深度。上面的函数被下面的函数调用。
横轴
样本数占比，按字母序排列，不是时间顺序。左右相邻没有先后关系。想看时序要用 perf script 原始输出或 perfetto 之类的时序视图。
看什么
找宽而平的顶部平台——那是真正在消耗 CPU 的叶子函数。一根又高又窄的塔通常无害（只是调用链深）。
常见误读
① 把"某函数很宽"当成"它自己慢"，其实可能是它的子调用宽；② 用样本占比反推绝对耗时（要乘上总 CPU 时间才有意义）；③ 忘了这只是 on-CPU：程序在睡觉、等锁、等 IO 的时间，一个样本都不会出现在图里。

11.3 off-CPU 火焰图

上一条的第 ③ 点很关键：如果你的服务"CPU 只用了 20% 但 P99 就是高"，on-CPU 火焰图会几乎空白——瓶颈全在 off-CPU。三种做法：

perf 内建
较新内核支持 perf record --off-cpu（底层用 BPF 记录调度切换时的栈），直接产出可以做 off-CPU 火焰图的数据。最省事。
sched 事件
perf record -e sched:sched_switch -g -a，从"线程被换下 CPU 时的栈"聚合出"在哪里睡着了"。数据量大，忙机器上慎用。
bpftrace / BCC
offcputime 这类工具直接在内核里聚合"阻塞时长 × 栈"，开销和数据量都最低。见 系统观测 / eBPF。
完整的判断姿势是两张图一起看：on-CPU 图回答"在算什么"，off-CPU 图回答"在等什么"。两张图的宽度加起来才是墙钟时间。只看 on-CPU 是绝大多数"优化了半天 P99 没动"的原因。

11.4 差分火焰图

# 采两份（v1 / v2 或 优化前/后）
$ ./stackcollapse-perf.pl before.perf > before.folded
$ ./stackcollapse-perf.pl after.perf  > after.folded

# 红 = 变多了，蓝 = 变少了
$ ./difffolded.pl before.folded after.folded | ./flamegraph.pl > diff.svg
差分火焰图和 perf diff 是互补的：perf diff 给的是按函数排序的表格（精确、易自动化），差分火焰图给的是带调用上下文的图形（一眼看出"是哪条路径上的这个函数变多了"）。做性能回归排查时两个都值得跑。

访存与并发 · mem / c2c / lock / sched

perf mem · perf c2c · perf lock · perf sched

12.1 perf mem · 这次 load 从哪一级拿到的

$ sudo perf mem record ./prog
$ sudo perf mem report --stdio

# 输出里最有价值的一列是 "Data Src"：
#   L1 hit / LFB / L2 hit / L3 hit / Local RAM / Remote RAM / Remote Cache

perf mem 底层用的就是精确访存采样（Intel PEBS load-latency、AMD IBS、ARM SPE）。它回答的问题很具体：热点代码里的那次 load，数据实际是从哪一级拿到的、等了多少 cycle。

最有价值的信号
看到大量 Remote RAM / Remote Cache → NUMA 跨节点访存，该考虑绑核 + 本地分配（见 NUMA 与内存进阶）。看到大量 Local RAM（即 LLC miss 到内存）→ 工作集超了 LLC，该改数据布局或分块。
和 perf stat 的区别
perf stat -e LLC-load-misses 只告诉你"总共 miss 了多少次"；perf mem 告诉你"哪一行代码的 load 在 miss、miss 到了哪一层"。前者判断有没有问题，后者定位在哪。

12.2 perf c2c · 假共享定位

$ sudo perf c2c record -a -- sleep 10
$ sudo perf c2c report --stdio
HITMHit in Modified —— 一次读命中了另一个核 cache 里处于 Modified 状态的行，必须走缓存一致性协议把数据从那个核搬过来。perf c2c 报告按 cache line 排序 HITM 次数，HITM 高的那几条 line 就是假共享现场。

报告会给出每条热点 cache line 的行内偏移以及参与读写的指令地址与线程。这一点非常关键：它不只说"有假共享"，还直接告诉你"是这个结构体里偏移 0 和偏移 8 的两个字段在打架"，对应修复就是 alignas(64) 拆开或改成 per-thread 局部累加。

机制层面（为什么写 A 会让另一个核的 B 失效、为什么单核几乎无感）见 内存模型 · MESI；修复手法与实测数据见 性能指南 §6 False Sharing 和 内存优化 §2.2。本页只负责"用哪条命令看到它"。

12.3 perf lock · 锁竞争

# 老方式：基于 lock tracepoint，需要内核开 CONFIG_LOCK_STAT，开销较大
$ sudo perf lock record ./prog
$ sudo perf lock report

# 新方式（Linux 6.x+）：BPF 内核内聚合，开销低得多，可以 -a 整机跑
$ sudo perf lock contention -a -b -- sleep 10
$ sudo perf lock contention -a -b -t -- sleep 10   # 按线程聚合
看什么
竞争次数和累计等待时长要分开看。次数多但每次很短 → 可以接受；次数不多但单次等待很长 → 临界区里干了重活（可能有 IO 或分配），是更严重的问题。
配套
死锁与更系统的锁问题排查见 死锁调试指南；锁优化手法（分片、读写分离、无锁）见 性能指南 §13。

12.4 perf sched · 调度延迟

$ sudo perf sched record -- sleep 5
$ sudo perf sched latency --sort max     # 按最大延迟排序，抓毛刺
$ sudo perf sched timehist               # 逐事件时序，做对齐分析
$ sudo perf sched map                    # 可视化线程在核上的分布
调度延迟线程从"进入可运行状态（被唤醒）"到"真正拿到 CPU 开始跑"之间的等待时间。它完全不出现在 on-CPU 火焰图里，却是延迟敏感服务 P99 毛刺的头号嫌疑之一。
数据量
perf sched record 订阅高频 sched tracepoint，忙机器上几秒就能产生几百 MB。先短时间试采，确认量级再放长。
典型结论
最大延迟到了毫秒级 → 检查 CPU 超卖、cgroup CPU 配额被限流（throttling）、有没有邻居噪声、线程数是否远超核数。低延迟场景的完整清单见 低延时实战，实时内核见 PREEMPT_RT 深入。

动态探针 · perf probe / perf trace

perf probe 给内核函数临时加埋点 · uprobe 探自己的 C++ 函数 · perf trace

13.1 perf probe · 给内核函数临时加埋点

tracepoint 是内核开发者预先埋好的固定观测点，位置改不了。当你需要的点位没有 tracepoint 时，perf probe 可以用 kprobe 现场"钻一个孔"——不用改内核、不用重启。

# 在内核函数入口加探针
$ sudo perf probe --add tcp_sendmsg
Added new event: probe:tcp_sendmsg

# 看这个函数在当前内核上能取到哪些变量（需要 kernel debuginfo）
$ sudo perf probe --vars tcp_sendmsg

# 带参数：抓 size 这个入参
$ sudo perf probe --add 'tcp_sendmsg size'

# 像普通事件一样采集
$ sudo perf record -e probe:tcp_sendmsg -a -- sleep 10

# 用完记得清理，探针是持久注册的
$ sudo perf probe -l
$ sudo perf probe -d probe:tcp_sendmsg

13.2 uprobe · 探自己的 C++ 函数

# -x 指定用户态二进制。C++ 要用 mangled 名或加引号的完整签名
$ sudo perf probe -x /usr/local/bin/myapp --add 'RequestHandler::handle'

# 函数返回处（%return）+ 取返回值
$ sudo perf probe -x ./myapp --add 'handle%return $retval'

# 然后就能统计调用次数 / 做调用栈采样
$ sudo perf stat -e probe_myapp:handle -a -- sleep 10
前提
取变量值需要 DWARF debuginfo；只挂函数入口/出口不需要。被内联掉的函数找不到符号也挂不上——这是探自己代码时最常见的失败原因。
开销
uprobe 每次触发都要陷入内核（int3 → 内核处理 → 返回），单次约微秒量级。挂在每秒调用几百万次的热函数上会显著拖慢程序——这和 perf 的采样模式完全不同，别用同一套"开销 < 1%"的直觉。
更好的选择
需要复杂过滤、聚合成直方图、或长期常驻时，用 bpftrace / BCC 更合适——它能在内核里就把数据聚合掉，不用把每次事件都送到用户态。perf probe 的定位是"临时、一次性、不想写脚本"。

13.3 perf trace · 比 strace 轻的 syscall 观测

$ sudo perf trace -p $(pgrep myapp)
$ sudo perf trace -s -p <pid> -- sleep 10       # 汇总统计
$ sudo perf trace -e 'syscalls:sys_enter_mmap,syscalls:sys_enter_brk' ./myapp
straceperf trace
机制ptrace，每个 syscall 两次进程停顿tracepoint，内核内记录
开销可达数十倍到上百倍通常个位数百分比
生产可用基本不行可以（注意数据量）
参数解码最详尽较好但不如 strace
永远不要在生产进程上直接 strace。ptrace 的停-启机制会把 syscall 密集的服务拖慢一两个数量级，足以直接触发上游超时和雪崩。要在生产看 syscall，用 perf trace 或 eBPF。

生产实践与十个陷阱

常驻采集 · 喂给 AutoFDO / BOLT · 十个陷阱清单

14.1 常驻采集 · continuous profiling

"出问题了再去登机器拉 perf"有两个致命缺陷：现场可能已经没了，而且你没有可对比的基线。成熟做法是常驻低频采集：每个实例每隔几分钟采 10 秒，落到中心存储，永远有历史可查。

采集参数
perf record -F 49 -g --call-graph fp -a -- sleep 10，每 5 分钟一次。折算下来平均 CPU 占用在千分之几。关键是用 FP 而不是 DWARF（见 §8.4），否则数据量和后处理成本都不可持续。
存储格式
perf script | stackcollapse 后的 folded 文本压缩率极高（同栈已合并），或直接转 pprof 格式接现成的后端：perf script | go tool pprof -http=:8080 -。
现成方案
Parca / Pyroscope / Grafana Phlare 这类系统已经把"eBPF 采集 + 存储 + 差分 UI"做好了，自建流水线前先评估。落地细节见 可观测性指南 §12。
收益
① 事后可追溯，不用复现；② 版本间自动差分，回归无处可藏；③ 跨实例横向对比能揪出"就那台机器慢"；④ 给容量规划提供"CPU 花在哪个业务模块"的真实数据。

14.2 喂给 AutoFDO / BOLT

perf 除了给人看，还能直接喂给编译器和链接器。这是 perf 最被低估的用途：生产采集的分支 profile 可以转化成 3-20% 的免费性能提升。

# AutoFDO：生产环境采分支样本 → 转成编译器能吃的 profile
$ sudo perf record -b -e br_inst_retired.near_taken:pp -- ./myapp prod_workload
$ create_llvm_prof --binary=./myapp --profile=perf.data --out=myapp.afdo
$ clang++ -O2 -fprofile-sample-use=myapp.afdo ...

# BOLT：拿成品二进制 + perf profile 重排函数与基本块（post-link）
$ sudo perf record -e cycles:u -j any,u -- ./myapp prod_workload
$ perf2bolt -p perf.data -o myapp.fdata ./myapp
$ llvm-bolt ./myapp -o myapp.bolt -data=myapp.fdata -reorder-blocks=ext-tsp \
    -reorder-functions=hfsort -split-functions -split-all-cold
为什么要 -b / -j
这两个工具要的不是调用栈，而是分支执行轨迹（LBR 分支栈）。所以用 -b / -j any,u 而不是 -g。这也是 LBR 在 §8.3 里"很浅但很有用"的真正原因。
收益来自哪
本质是把热代码聚到一起，降低 icache / iTLB miss —— 也就是 Top-Down 里的 Frontend Bound。所以先跑 Top-Down 看 Frontend 占比，就能预判 BOLT 能不能给你带来收益。
完整对比
PGO / AutoFDO / BOLT / ThinLTO 的关系、收益量级与常见坑，见 性能指南 §16c。

14.3 十个陷阱清单

1
忘写 -F。默认 4000 Hz，生产上偏高，还容易被内核限流。
2
直接用 --call-graph dwarf 上生产。数据量能大 10-50 倍，写盘本身变成新瓶颈。
3
只看 on-CPU 火焰图。CPU 不高但很慢的问题，图上什么都看不到（§11.3）。
4
把复用外推的数字当精确值。看到行尾 (48.5%) 就该警觉（§5.3）。
5
在虚拟机上测 IPC / cache-miss 并当作基准。PMU 可能根本没暴露，或被 hypervisor 干扰（§3.4）。
6
把栈断当成符号问题（或反过来）。层数少 = 回溯方式问题；层数够但名字是地址 = 符号问题（§9.1）。
7
用不匹配的二进制符号化。build-id 不一致时，你看到的函数名可能是完全错的——比看不到名字更危险。
8
只看 Children 视图。榜首永远是 main，得加 --no-children 看 Self（§10.1）。
9
没固定测量环境就下结论。频率漂移、turbo、邻居噪声、cgroup 限流都能造出 ±15% 的假差异。先 perf stat -r 10 看标准差。
10
把 perf probe 挂在热函数上。uprobe 是每次触发都陷内核，和采样完全不是一个开销模型（§13.2）。

面试题（12 道分层）

基础（必答） · 中级（区分熟练度） · 高级（体现深度）

15.1 基础（必答）

点击每道题展开参考答案（先自测，再对照）。

  1. 基础perf 和 Valgrind、ASan 有什么本质区别？

    三者解决的不是同一类问题：

    perf
    基于 PMU 的采样式性能剖析，不改二进制、开销 < 1%、能看到内核态，答"CPU 时间花在哪"。代价是统计性质，说不出精确调用次数。
    Valgrind
    动态二进制翻译，指令级完整计数，慢 10-30×。答"精确的指令数 / 可重现的 cache 模拟"，不能上生产。
    Sanitizers
    编译期插桩，查正确性（内存错误、data race），不是性能工具。
    一句话
    perf 是"抽样调查"，Valgrind 是"全员普查"，Sanitizer 是"体检"。
  2. 基础perf stat 你会重点看哪几个数字？怎么判断"CPU 用得健康"？
    四个数字
    ① CPUs utilized（task-clock / elapsed）判断是 CPU 密集还是在等；② IPC，> 1.5 算舒展、< 1 说明流水线大量空转；③ branch-miss 率，< 1-2%；④ LLC-miss 率 / MPKI，miss 高说明访存受限。再加上 user vs sys 比例判断时间是否花在内核。
    但要补一句
    这三条线只是启发式。IPC 高不等于程序好——自旋等待的 IPC 接近 4 却毫无产出。最终指标永远是墙钟时间 / 吞吐 / P99，微架构指标只用来解释原因。
    加分
    提到 cache-misses 在多数 Intel 平台上其实是 LLC miss 而不是"所有 cache miss"，以及用 MPKI 代替百分比来避免分母骗人。
  3. 基础给一个正在生产跑的服务出火焰图，完整命令是什么？每一步在做什么？ 
    sudo perf record -F 99 -g -p $(pgrep myapp) -- sleep 30
sudo perf script > out.perf
./stackcollapse-perf.pl out.perf | ./flamegraph.pl > flame.svg
    逐步
    record 以 99Hz 带调用栈采样 30 秒 → script 把二进制数据摊成文本栈 → stackcollapse 把相同栈合并成一行计数 → flamegraph.pl 画 SVG。
    为什么 99
    避免和内核 100/250/1000 Hz 的周期性活动锁相产生采样别名。
    读图注意
    横轴是样本占比且按字母序排，不是时间轴；要找的是宽而平的顶部平台；这只是 on-CPU，等锁 / 等 IO 的时间不会出现。
  4. 基础为什么 perf 的开销能低到 1% 以内？什么情况下会不止 1%？
    为什么低
    ① PMU 计数是硬件行为，不插一条指令；② -F 99 每核每秒只中断 99 次，单次几微秒；③ 样本走 mmap ring buffer 给用户态，不走 syscall。
    什么时候变贵
    ① --call-graph dwarf 每样本拷几 KB 栈；② 频率抬到几千 Hz；③ 订阅高频 tracepoint（sched:*）；④ 用 uprobe 挂热函数——那已经是每次触发都陷内核，不是采样了。

15.2 中级（区分熟练度）

  1. 中级火焰图只有一两层，或者栈里全是 [unknown]。怎么定位原因？
    先分类
    层数少 = 栈回溯断了；层数够但名字是地址 = 符号化失败。这是两条完全不同的排查路径，先分清能省一半时间。
    栈断
    ① 默认 -g 走 frame pointer，而 -O2 默认 -fomit-frame-pointer → 加 -fno-omit-frame-pointer 重编，或改用 --call-graph dwarf；② DWARF 模式下栈拷贝上限默认 8KB，深栈被截断 → dwarf,32768；③ LBR 只有十几层深度；④ perf_event_paranoid=2 时内核帧被禁，栈在进内核处断掉。
    符号化失败
    ① 二进制被 strip → 用 build-id 关联单独的 debuginfo 或配 DEBUGINFOD_URLS；② 分析用的二进制和采集时不是同一份（build-id 不匹配）；③ 内核符号看不到 → kptr_restrict=0；④ 容器 / 跨机分析路径找不到 → --symfs 或 perf archive；⑤ JIT 代码 → /tmp/perf-<pid>.map 或 perf inject --jit。
    加分
    提到 Fedora 38 / Ubuntu 24.04 已经把发行版整体重编为保留 frame pointer，正是因为"可剖析性 > 省一个寄存器"这个权衡在服务端成立。
  2. 中级perf record -g 的三种栈回溯方式怎么选？
    FP
    顺 frame pointer 链走。开销极低、数据量小、栈完整，但要求目标和依赖库都保留 frame pointer。
    DWARF
    中断时拷一段栈内存，事后用 .eh_frame CFI 离线展开。不用重编、能穿无 FP 的库，代价是数据量涨 10-50 倍、后处理很慢、深栈会被截断。
    LBR
    读硬件分支寄存器反推。零内存拷贝、几乎免费，但只有十几层深度、一般只覆盖用户态、依赖 Intel（ARM 需 BRBE）。
    选型
    能控制构建 → 全线 FP（生产常驻采集唯一现实选择）；临时查第三方二进制 → DWARF 但降频缩时长；只要分支热度（AutoFDO / BOLT）→ LBR + -b。
  3. 中级perf stat 输出里每行后面的 (62.13%) 是什么意思？会带来什么风险？
    是什么
    计数器复用（multiplexing）的启用时间占比。订阅的事件数超过物理计数器数量时，内核轮流把事件调度到计数器上，每个事件只在部分时间被真实统计，最后按占比线性外推。
    风险
    外推假设"负载在整段时间里是均匀的"。负载有相位（如启动 / 稳态 / GC）时这个假设不成立，误差可以很大。表现为荒谬的派生指标——branch-misses 比 branches 多、IPC 算出 12。占比低于 50% 时基本只能看数量级。
    怎么办
    ① 拆成多次跑，每次只订阅 2-4 个事件；② 用 {cycles,instructions} 事件组语法保证组内始终一起被调度；③ 用 -M 让 perf 按官方 metric group 挑组合；④ ARM 计数器更少（常见 6 个），更容易触发。
  4. 中级服务 CPU 只用了 15%，但 P99 延迟很高。用 perf 怎么查？
    第一判断
    瓶颈在 off-CPU。on-CPU 火焰图在这种场景下几乎无用——程序在睡觉的时间一个样本都不会被采到。
    路径
    ① perf sched latency --sort max 看调度延迟，毫秒级说明 CPU 超卖 / cgroup 限流 / 线程数超配；② perf lock contention -a -b 看锁等待，重点看"单次等待时长"而不只是次数；③ perf trace -s 看是否堵在某类 syscall；④ perf record --off-cpu 或 bpftrace 的 offcputime 出一张 off-CPU 火焰图。
    方法论
    on-CPU 图回答"在算什么"，off-CPU 图回答"在等什么"，两张宽度加起来才是墙钟时间。只看前者是"优化半天 P99 没动"的最常见原因。

15.3 高级（体现深度）

  1. 高级什么是 Top-Down 微架构分析法？它比"逐个看 cache-miss / branch-miss"强在哪？
    核心思想
    不数孤立事件，而是给流水线 issue slot 做会计。每个 slot 的归属只有四种：Retiring（有效产出）/ Bad Speculation（预测错白干）/ Frontend Bound（取指译码供不上）/ Backend Bound（后端堵住），四者合计 100%。先看哪格最大，再只往那格下钻。
    强在哪
    孤立事件会互相掩盖：乱序执行能把一次 L3 miss 藏在其他指令后面，此时 miss 数很高却不影响性能；反之一个不显眼的依赖链才是真瓶颈。Top-Down 直接量化"损失了多少执行带宽"，把猜变成分账。
    怎么跑
    perf stat --topdown（Skylake+），--td-level=2（Ice Lake+ 硬件支持），或 Intel pmu-tools 的 toplev.py --level 3 自动逐层下钻。
    边界
    依赖 slots 等固定计数器和精确事件，虚拟机里通常不可用；AMD / ARM 各有自己一套指标，不能直接照搬 Intel 的公式。负载不稳定时四象限占比会大幅漂移，要先确认可重复。
  2. 高级perf annotate 显示 70% 的开销压在一条 mov 上，能直接断定是这条指令慢吗？
    不能
    存在 skid：PMU 计数器溢出到中断真正打断执行之间隔了若干 cycle，记下的指令地址往往落在真正的"罪犯"之后几条。热点常常显示在长延迟 load 的下一条指令上。
    缓解
    用精确事件：Intel PEBS（-e cycles:pp，:ppp 为零 skid，硬件在事件发生点直接写现场）、AMD IBS、ARM SPE（-e arm_spe//）。perf mem / perf c2c 底层依赖的正是这套精确采样。
    更深一层
    即使零 skid，在乱序超标量核上"哪条指令负责这次停顿"本身就是模糊概念——多条指令并行在飞，停顿是资源竞争的结果。所以 annotate 的正确用法是定位到"这个循环 / 这次访存"，而不是"就是这一条指令"。要判断瓶颈类型该上 Top-Down。
  3. 高级要给公司几千个 C++ 服务实例上"常驻性能剖析"，你怎么设计？
    ① 采集
    perf record -F 49 -g --call-graph fp -a -- sleep 10，每实例每 5 分钟一次。必须用 FP 不能用 DWARF——DWARF 的数据量和后处理成本在这个规模上不可持续。前置条件是推动全公司构建加 -fno-omit-frame-pointer（约 1% 性能代价，换来永久可剖析性）。
    ② 符号
    这是真正的分水岭，比命令行技巧重要得多。CI 构建时：stripped 二进制进镜像，.debug 按 build-id 上传内部 debuginfod。这样生产镜像不变大，任何分析机都能完整符号化。
    ③ 权限
    给采集容器 CAP_PERFMON 而不是 privileged（内核 < 5.8 才退化到 CAP_SYS_ADMIN）；宿主机统一 perf_event_paranoid=1 + kptr_restrict=0，并评估侧信道风险后做取舍。
    ④ 存储与查询
    perf script → folded / pprof 格式，按 服务 × 版本 × 实例 × 时间 打标入库。核心能力是差分：版本间、实例间、时间段间。优先评估 Parca / Pyroscope 而不是自建。
    ⑤ 闭环
    不止给人看：把分支 profile 接到 AutoFDO，让生产 profile 反馈进编译流水线，形成"跑得越多编得越好"的循环。这才是常驻采集 ROI 最高的部分。
    要主动提的风险
    ① PMU 在虚拟机上可能不可用，需要区分实例类型；② 性能计数器是侧信道，多租户环境要评估；③ 采集本身的开销要有熔断（比如目标机负载过高时跳过本轮）；④ 符号服务器挂了会让所有历史数据变成一堆地址，它是关键依赖而不是附属设施。
  4. 高级同一份代码在 x86 上测得很好，搬到 ARM 服务器上 perf 结论完全对不上。可能是什么原因？
    ① 事件名不通用
    命令一样但原生事件名完全不同：x86 的 LLC-load-misses 在 ARM 上要用 ll_cache_miss_rd / l2d_cache_refill 之类，还随核型号变。换机器第一件事是 perf list。
    ② 计数器更少
    ARM 常见 6 个可编程计数器（x86 常见 4 通用 + 3 固定），同样的 -e 列表在 ARM 上更容易触发复用外推，数字可信度下降。
    ③ 精确采样机制不同
    没有 PEBS，对应的是 ARM SPE（-e arm_spe//），行为和字段都不一样；LBR 对应 BRBE 且只有较新核才有，--call-graph lbr 往往直接不可用。
    ④ 微架构差异本身
    cache 层次与容量、cache line 大小（ARM 上可能是 128B，影响 alignas(64) 的假共享修复是否够）、内存序模型更弱（seq_cst 代价显著更高）、SIMD 是 NEON/SVE 而非 AVX。结论对不上很可能是真的不一样，不是测错了。
    正确做法
    不要移植"事件列表"，要移植"问题"。先用跨平台通用的 cycles / instructions / task-clock 建立 IPC 与时间分布，确认瓶颈类型；再按目标平台手册挑该平台的原生事件下钻。跨平台的更多差异见 ARM 平台通信实战。

16.1 一页速查

## 体检（先跑这个）
perf stat -d ./prog                       # 整体计数器 + 细节
perf stat -r 10 ./bench                    # 跑 10 次看均值 ± 标准差
perf stat -a --per-core -e cycles -- sleep 5  # 核间是否均衡
perf stat --topdown -a -- sleep 5           # 四象限定瓶颈类型

## 找热点
perf top -p <pid>                         # 实时
perf record -F 99 -g -p <pid> -- sleep 30  # 离线采样（FP 回溯）
perf report --stdio --no-children         # 看 Self 榜
perf report --sort dso                    # CPU 花在哪个库
perf annotate -s hot_func                 # 下钻到指令

## 火焰图
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg
perf record --off-cpu -g -a -- sleep 10    # off-CPU（新内核）

## 访存 / 并发
perf mem record ./prog && perf mem report     # 命中层级与延迟
perf c2c record -a -- sleep 10 && perf c2c report  # 假共享
perf lock contention -a -b -- sleep 10     # 锁竞争（BPF 模式）
perf sched record -- sleep 5 && perf sched latency --sort max

## 对比 / 探针
perf diff before.data after.data
perf probe -x ./myapp --add 'Handler::handle'
perf trace -s -p <pid> -- sleep 10

## 环境与符号（出问题先查这些）
perf list | less                          # 这台机器支持什么事件
cat /proc/sys/kernel/perf_event_paranoid  # 权限档位
cat /proc/sys/kernel/kptr_restrict        # 内核符号可见性
perf buildid-list -i perf.data            # 缺哪个 build-id
perf report --symfs /proc/<pid>/root      # 容器符号
perf archive perf.data                    # 打包给别人分析

16.2 动手清单

  1. 在自己的服务上跑一遍 perf stat -d，把 IPC / branch-miss / LLC-miss 记下来当基线。
  2. 给项目加 -fno-omit-frame-pointer 重编，对比加之前 / 之后火焰图的层数差异——亲眼看到栈断是怎么回事。
  3. 故意写一段假共享代码（两个线程各自 ++ 相邻的 counter），用 perf c2c 把它抓出来，再 alignas(64) 修掉，记录加速比。
  4. 把服务的二进制 strip 后再分析一次，走通"build-id + 单独 debuginfo"的符号化链路。
  5. 做一次 perf diff：随便优化一处，验证"开销是不是只是搬家了"。
  6. 如果有裸金属机器，跑一次 perf stat --topdown，判断你的服务是 Frontend 还是 Backend 受限，再决定下一步优化方向。
