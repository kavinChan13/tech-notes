死锁的四个必要条件 (Coffman, 1971)

四条同时成立 ⇔ 死锁；破任意一条即可

死锁：进展永久为零。自死锁（同线程再锁非递归 mutex）也算。
条件含义怎么破
1. 互斥同时只能一人占RCU / 不可变 / 读写锁
2. 持有并等待握着 A 再要 Bscoped_lock 一次拿齐
3. 不可抢占只能自己放try_lock + 随机退避
4. 循环等待等待图有环全局锁序

常见死锁形态

ABBA · 自死锁 · 丢 notify · 读升写 · fork 后锁 · 锁内回调 · 优先级反转

形态现场解法
ABBA 两个 wait，owner 互换 scoped_lock / 全局锁序
自死锁 一个 wait，owner = 自己 抽出 Locked 私有函数
丢 notify cond_wait，无人 signal wait(pred)；状态锁内改
读升写 多人等写锁，读计数下不去 先释放再独占 + double-check
fork 后锁 子进程 lock，owner 是父 tid；malloc 也会 pthread_atfork 或只 exec
锁内回调 栈上 execute 套在 lock_guard 里 copy-out 再回调
优先级反转 H 在 wait，L 可运行却不被调度（无环） PI mutex，见 进程调度 §5
裸 lock + 异常 之后全员等这把锁 永远 RAII

2.1 ABBA 锁序反转 最常见

窄桥两头各来一辆车，都占着自己这头不退——这就是 ABBA。

void t1() { std::lock_guard a(mA); std::lock_guard b(mB); }
void t2() { std::lock_guard b(mB); std::lock_guard a(mA); }  // ABBA

03

检测：GDB / TSan / Helgrind

两次 bt 差分定性进展；TSan 只看本轮观测到的锁序

3.1 两次 thread apply all bt 差分

死锁 = 进展为零。GDB attach 会冻住所有线程，差分必须两次 -batch，中间放跑。

步骤做什么看什么
t0 gdb -p PID -batch -ex 'thread apply all bt' → /tmp/bt1 各 LWP 顶帧 + mutex 地址
间隔 5–10s 进程在跑（不要停在交互 gdb 里） 给持锁者把 IO 做完的机会
t1 同样命令 → /tmp/bt2，diff 顶帧全同且 futex_wait → 死锁候选；有人换帧 → 还活着
画环 p mutex.__data.__owner LWP 成环才定性；owner 不在 wait → 去看它（锁内 IO）
Thread 1: #0 __lll_lock_wait  #1 pthread_mutex_lock(mB)  #2 t1()   // 持 mA
Thread 2: #0 __lll_lock_wait  #1 pthread_mutex_lock(mA)  #2 t2()   // 持 mB  → 环
__owner 是 LWP/TID，不是 gdb 的 thread id。glibc 里 __lock：0 空闲，1 锁定，≥2 有等待者。

3.2 Core 与 mutex owner

做法目的判据
gcore -o /tmp/hang PID 不杀进程取 dump 然后 gdb ./bin /tmp/hang.PID
kill -ABRT PID 进程已经没救，交给 systemd-coredump coredumpctl debug PID
p mu.__data.__owner 持有者 LWP 成环 = 死锁；指向自己 = 自死锁
__count / __kind 递归计数；0=NORMAL 1=RECURSIVE 2=ERRORCHECK NORMAL 上看到 count>0 不该发生

3.3 TSan 能抓什么、抓不到什么

只进 CI（5×–15×）。官方建议 -O1：-O0 太慢，-O2 可能优化掉同步。

3.4 Helgrind / DRD

工具命令抓什么漏什么 / 开销
Helgrind valgrind --tool=helgrind --history-level=full ./bin 锁序反转、pthread API 误用、data race 与 TSan 同一类盲区；20×–30×
DRD valgrind --tool=drd ./bin 同类，对 condition_variable 更严 20×–50×；适合补 TSan 看不到的 cv 误用
TSan -fsanitize=thread 编译期插桩，同样是锁序图 比 Valgrind 快一个数量级；生产不能开

Helgrind 句式 lock order "A before B" violated，后面两段栈就是 ABBA 两边。

3.5 不 attach gdb 时的内核视角

命令判据
ps -L -p PID TIME 几乎不动 + 进程仍在 → 死锁/hang，不是活锁
cat /proc/PID/task/*/wchan 全 futex_wait_queue_me → mutex/cv；有 io_schedule → hang
strace -f -e futex -p PID 只有 WAIT 无 WAKE，val=2 → 锁没人放
top -H -p PID 全 0%：死锁或 hang；有 100%：活锁 / 自旋

05

防御：锁序与 scoped_lock

两把以上锁禁止手写嵌套 lock_guard；临界区禁止回调和 IO

5.1 统一锁序

每把锁一个 level，进程内只允许一个方向。用 thread_local 记已持最高 level；标准库没有现成实现，debug 构建自检，Clang GUARDED_BY 编译期拦。

约定违了
锁名带层级（l1_config_mu_） review 看不出 ABBA
A 持锁调 B，B 不得再锁 A 隐式 ABBA；TSan 两条路径都跑到才报
level 检查只开 debug 构建 别把 throw 当线上恢复

5.2 std::scoped_lock：一次拿多把

std::scoped_lock lk(mA, mB);           // C++17：顺序无关
std::unique_lock l1(mA, std::defer_lock);
std::unique_lock l2(mB, std::defer_lock);
std::lock(l1, l2);                     // C++14 等价
自己写 try_lock 循环必须加随机睡眠；std::lock 会换起点，一般够用。

5.3 try_lock + 退避（破不可抢占）

拿不到第二把就放下第一把再试。双 try_lock 不加 jitter 会活锁。try_lock_for 超时后当「没进临界区」恢复。

5.4 缩小临界区 / copy-out

锁内禁止改法
用户回调 / 虚函数 swap 出来再调
IO、日志、网络、大块 new 锁内只改内存
再申请不知层级的锁 改消息队列 / Dispatcher

5.5 RAII

  • 禁止裸 lock()/unlock()：异常、早退、goto 都会漏 unlock，后续全员死等。
  • 默认 lock_guard；要手控解锁或配 cv 才用 unique_lock；≥2 把用 scoped_lock。
  • cv 必须配 unique_lock（wait 期间要放锁）。

5.6 架构上消灭共享锁

模式适用
MPSC / Dispatcher事件、日志；本工作区就是这样
Actor会话、连接
Sharding连接池、cache
不可变 + 引用计数配置热更新
RCU读多写极少的路由表

C++ 标准库锁机制对比

选型看死锁风险，不看名字好不好听

类型 语义 适用 死锁风险 关键陷阱
std::mutex 独占，非递归 默认选择 中 同线程二次 lock = 自死锁
std::recursive_mutex 同线程可重入 旧代码权宜 低 慢 ~2×；掩盖锁粒度过大。配 cv 要用 condition_variable_any
std::timed_mutex try_lock_for/_until 超时退避 低 超时后没进临界区，调用方自己恢复
std::shared_mutex 读共享写独占 读写比 >10:1 高 读升写死锁；写者饥饿。无原子升级
std::lock_guard RAII，不可动 单锁临界区 低 不能手动 unlock；不能配 cv
std::unique_lock 可 unlock / 可移动 cv、defer_lock 低 比 lock_guard 多一个 bool
std::shared_lock 读锁 RAII 读路径 中 多读者同时升级 → 互相死锁
std::scoped_lock 一次锁多把，内部规避 ≥ 2 把锁 极低 不防自死锁、不防锁内回调；锁集合变化仍可能成环
std::condition_variable 基于 mutex 的通知 生产消费 高 无谓词 wait；锁外改状态 → lost signal
std::call_once 一次性初始化 单例 中 初始化函数抛异常会重置 flag，再试一次
atomic_flag 自旋 用户态打转 临界区 < 1µs 中 临界区一长 CPU 100%；不能在里面睡
07

面试高频问题与解答

Coffman 四条件 · 锁层级 · 条件变量谓词 · 线上死锁定位 · 无锁语义

点击每道题展开参考答案（建议先自己复述一遍，再对照）。

  1. 基础死锁的四个必要条件是什么？打破任意一个的具体做法？
    • 互斥：用无锁数据结构（lock-free queue）、不可变对象 (immutable)、RCU；读多写少改用 shared_mutex。
    • 持有并等待：std::lock / std::scoped_lock 一次性原子获取所有锁。
    • 不可抢占：try_lock + 随机退避；timed_mutex::try_lock_for 超时返回。
    • 循环等待：建立全局锁层级 (Lock Hierarchy)，规定从低到高单调申请。
  2. 中级std::lock 是怎么避免死锁的？

    它实现的是“try-and-back-off”算法：先 lock() 第一个 mutex，然后对其余的 try_lock()。 若任何一个 try 失败，就把已经持有的全部 unlock()，等一个非常短的随机时间后重新选起点。 直到一次能把所有 mutex 都获取成功才返回。这相当于“原子获取多锁”的语义，无论多个线程以什么顺序调用 std::lock(mA, mB) 都不会死锁。

  3. 基础lock_guard 和 unique_lock 有什么区别？什么时候用哪个？
    lock_guardunique_lock
    构造时自动 lock是可选 (defer/try/adopt)
    析构时自动 unlock是是
    可手动 unlock/lock否是
    可移动否是
    性能开销极低多一个 bool 状态
    能配 cv 用否是 (cv 需要 unlock 等待)

    默认用 lock_guard；需要手控解锁、配合 cv、或与 std::lock+defer_lock 配合时改用 unique_lock；需要锁多个 mutex 用 scoped_lock。

  4. 中级std::recursive_mutex 解决什么问题？为什么不推荐？

    解决“同一线程在持锁期间需要再次进入加锁路径”的问题（典型如递归算法、回调）。 不推荐的原因：
    ① 性能比普通 mutex 慢 ~1.5× ~ 2×（要维护 owner 和 count）；
    ② 掩盖设计问题——通常说明加锁粒度过大、或者公私接口没有分离；
    ③ 让“到底持锁多少次”变得不可读，不利于审查；
    ④ 与 condition_variable 配合复杂（必须用 condition_variable_any）。
    更好做法：把临界区抽成 fooLocked() 私有版本（无锁），公开 foo() 加锁后调用 fooLocked()。

  5. 基础死锁和活锁 (Livelock) / 饥饿 (Starvation) 的区别？
    • 死锁：线程都不动了，CPU 0%，互相等待，永久阻塞。
    • 活锁：线程都在动，CPU 100%，但不断互相让步、永远完不成工作。典型：朴素 try_lock 循环、TCP 电梯效应。解：随机退避。
    • 饥饿：某些线程永远轮不上锁，但其他线程在正常工作。典型：写者在大量读者中拿不到 shared_mutex 的写锁。解：公平队列锁、写者优先策略。
  6. 高级在生产环境怎么定位一个线上死锁？
    1. 监控报警：心跳超时 / RPS 跌零；top -H 看线程是否全部 D/S 状态。
    2. 取现场：sudo gcore -o /tmp/core $PID，不杀进程。如果服务无法继续，kill -SIGABRT $PID 触发 systemd-coredump。
    3. 下载符号：把 .so 调试符号、core、二进制本身一起 sync 到分析机。
    4. GDB 分析：thread apply all bt full，p mutex.__data.__owner 画 wait-for 图。
    5. 修复：调整锁序、改 scoped_lock、缩小临界区、或拆模块用消息队列。
    6. 预防：CI 跑 TSan；引入 lock hierarchy；上线前压测。
  7. 中级条件变量为什么必须配合谓词使用？什么是虚假唤醒 (Spurious Wakeup)？

    虚假唤醒：POSIX 标准规定 pthread_cond_wait 可能在没有任何 signal/broadcast 的情况下返回——这是底层为了实现简单（futex 可能因信号、超时、被错误唤醒）。
    因此必须用 while 循环检查条件，而不是 if：

    // ✗ 错
if (!ready) cv.wait(lk);

// ✓ 对（手写循环）
while (!ready) cv.wait(lk);

// ✓ 推荐（lambda 谓词版本，标准库内部就是 while）
cv.wait(lk, []{ return ready; });

    另外，谓词还能防止 lost signal：如果 producer 在 consumer 进入 wait() 前就 notify_one()，没谓词就会丢失信号；带谓词时 consumer 进 wait 前先检查谓词，已满足就直接跳过等待。

  8. 中级怎么在编码阶段就预防死锁？
    • 规范：约定全局锁序文档，锁名带层级前缀（如 l1_config_mu_）。
    • 禁手写：禁用裸 lock()/unlock()，code review 自动拒绝。
    • scoped_lock 优先：但凡 ≥ 2 把锁，强制 std::scoped_lock。
    • 临界区原则：① 不在锁内做 I/O；② 不在锁内回调用户函数；③ 不在锁内发送消息或申请其他锁。
    • 不变量审查：每个共享数据结构标注 “guarded by mutex_xxx”（GCC __attribute__((guarded_by(mu))) 或 Clang Thread Safety Analysis）。
    • 测试：CI 跑 TSan，发版前压测 24h+。
  9. 高级什么是 Lock-free / Wait-free / Obstruction-free？
    • Obstruction-free：任意线程在没有竞争时能在有限步内完成。最弱保证，不能保证整体进度。
    • Lock-free：系统整体能在有限步内取得进度，但单个线程可能永远饥饿。例如 CAS 循环算法。
    • Wait-free：每个线程都能在有限步内完成。最强保证，工程实现极难。

    从 Lock-free 到死锁免疫并不等同——lock-free 不会死锁，但可能 livelock（无限重试）。

  10. 高级shared_mutex 为什么容易死锁？

    三种典型陷阱：

    1. 读升写死锁：N 个线程持读锁后同时申请写锁——所有人都等其他人释放读锁。
    2. 写者饥饿：读者源源不断进入，写者永远拿不到写锁。需要公平队列锁实现 (gcc 11+ 已部分修复)。
    3. 嵌套读读死锁：某些 shared_mutex 实现不允许同线程递归 lock_shared()，会死锁；规范未严格定义。

    建议：除非读写比 > 10:1 且临界区耗时 > 1µs，否则 std::mutex 已足够；性能更易预测。

  11. 高级Linux 下 mutex 是怎么实现的？为什么死锁时 CPU 占用是 0？

    glibc 的 pthread_mutex 基于 futex (fast userspace mutex)：

    • 无竞争时，lock() 仅是一次 cmpxchg（原子指令），完全在用户态完成，开销 ~10ns。
    • 有竞争时，调用 futex(FUTEX_WAIT) 系统调用让线程进入内核睡眠队列。
    • 持有者 unlock() 时调 futex(FUTEX_WAKE) 唤醒一个等待者。

    因此死锁时所有线程都阻塞在内核 futex_wait_queue_me，CPU 调度器给它们 0 时间片——表现为 CPU 0%、进程仍存活。这也是为什么 strace -e futex 是诊断利器。

  12. 高级用 C++ 实现一个简单的 DeadlockDetector 思路？

    核心：维护一张全局 有向图「线程 → 等待的锁 → 锁的持有者 → ...」，每次 lock() 加边、检查是否成环。

    class DeadlockDetectingMutex {
    std::mutex internal_;
    std::atomic<std::thread::id> owner_{};
public:
    void lock() {
        auto me = std::this_thread::get_id();
        Graph::registerWait(me, this);    // 加边
        if (Graph::hasCycle())               // DFS / Tarjan
            throw std::system_error(...);
        internal_.lock();
        owner_.store(me);
        Graph::registerHold(me, this);    // 改边
    }
    void unlock() {
        Graph::unregister(std::this_thread::get_id(), this);
        owner_.store({});
        internal_.unlock();
    }
};

    真实库：Boost.Thread 的实验性 strict_lock、Abseil 的 Mutex 自带死锁检测、Folly 的 folly::SharedMutex。

PR 审查清单

打勾才合并

  • ☐ RAII：无裸 lock()/unlock()。
  • ☐ 多锁：≥2 把必须 scoped_lock / std::lock，或符合文档里的全局锁序。
  • ☐ 临界区：锁内只碰内存。禁止 IO、网络、日志、大块分配。
  • ☐ 无锁内回调：禁止持锁调 functor / observer / 虚函数；必须则先 swap 出来。
  • ☐ cv：wait 带谓词；状态锁内改；notify 可锁外。
  • ☐ shared_mutex：禁止读锁内升写；读写比不够就用 mutex。
  • ☐ 递归：避免 recursive_mutex；公开加锁、私有 Locked 版本。
  • ☐ fork：持锁期间不 fork；子进程只 exec 或走 pthread_atfork。
  • ☐ RT：实时线程的 mutex 必须 PI，见 进程调度 §5。
  • ☐ 静态：Clang -Wthread-safety + GUARDED_BY。
  • ☐ 动态：CI 跑 TSan（绿了仍可能有自死锁 / 丢 notify）。
  • ☐ 监控：长寿线程接心跳；超时 abort 收 core。Watchdog 自己不抢业务锁。
