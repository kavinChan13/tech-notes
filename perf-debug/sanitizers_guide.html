引言

本章目标 · 本章与已有资料的关系

Sanitizer 是 C++ 工程师必备

C++ 三类 bug 在测试期常常不崩，上线才随机炸。Sanitizer 是把它们提前暴露的标准插桩：内存错误 → ASan / LSan；未定义行为 → UBSan；数据竞争 → TSan。未初始化读另开 MSan（仅 clang）。

ASan 是堆上的警戒带，TSan 是进出时间戳，UBSan 是运算前口算——后两者不改堆布局。

本章与已有资料的关系

  • cpp/sanitizer_internals.html 讲编译器 / runtime 内部（shadow layout、FastTrack、LLVM Pass、完整局限表）
  • crash_debugging_guide.html 讲用户态崩溃现场：GDB、core、以及怎么读一份 ASan UAF 报告（三栈 + shadow bytes）
  • 本章讲各 sanitizer 做什么、怎么编、假阳性从哪来；不贴完整 UAF 复现墙
内部机制跳 sanitizer_internals.html。ASan 报告读法见 崩溃调试指南 §5.1。

ASan 原理速览 ⭐

三件套 · 性能与基本局限（实战视角）

三件套 · 性能与基本局限（实战视角）
面试速答级摘要。shadow 编码、fake stack、quarantine、插桩汇编见 sanitizer_internals.html §2。

4.1 三件套

  1. 编译期插桩：每条 load/store 前查 shadow
  2. Shadow memory：8 字节应用内存 → 1 字节影子（shadow = (addr >> 3) + offset）
  3. Redzone + Quarantine：alloc 前后红区 poison；free 进隔离队列、shadow 标已释放，UAF 在隔离期内能抓到

4.2 性能与基本局限（实战视角）

  • CPU ~2×、内存 ~3–4×；不上生产（HWASan / GWP-ASan 见 §14b）
  • 远距离越界、intra-object overflow、quarantine 挤出后的老 UAF：漏检
  • 不查未初始化读（MSan）、不查 race（TSan）

完整局限根因表见 internals §2。

UBSan · UndefinedBehaviorSanitizer

能检测什么 · 用法 · 经典报告 · UBSan 默认是"trap" · 性能与用法

能检测什么 · 用法 · 经典报告

5.1 能检测什么

C++ 标准里 UB 两百多种，UBSan 覆盖常见约 30 种。不申请 shadow、不换分配器，故可与 ASan / TSan / MSan 同编。堆上动态越界不管；float-divide-by-zero 默认关。常见项：signed-overflow、shift、div0、null、vptr、bounds、alignment、return、bool、enum。

5.2 用法

目的旗标
全家桶（推荐与 ASan 一起）-fsanitize=undefined 或 address,undefined
只开几项-fsanitize=signed-integer-overflow,null
排除一项-fno-sanitize=alignment
触发即停（CI 必加）-fno-sanitize-recover=all

5.3 经典报告

代码报告要点
INT_MAX + 1signed integer overflow
int* p = nullptr; *p;load of null pointer
1 << 32shift exponent too large
把 Base* 当 Derived* 调虚函数member call … does not point to 'Derived'

5.4 UBSan 默认是"trap"

更准确：默认是打印后继续（recover），进程退出码经常仍是 0。ASan 相反，halt_on_error 默认就是 1。

TSan · ThreadSanitizer 数据竞争检测

能检测什么 · 经典 data race 例子 · TSan 抓得到的几类问题 · TSan 能识别的同步原语 · TSan 不能识别的 · …

能检测什么 · 经典 data race 例子 · TSan 抓得到的几类问题

6.1 能检测什么

  • Data race：同一地址、两线程冲突访问（至少一个写）、中间没有 happens-before
  • 部分 lock 顺序异常、unlocked unlock、对已销毁同步原语的使用

6.2 经典 data race 例子

int g;
void w() { g = 1; }
void r() { if (g) {} }   // 无锁读写 → data race
// g++ -O1 -g -fsanitize=thread   （不能与 ASan 同编）

报告给写栈和读栈各一份。只修一边，另一边下次还会报。

6.3 TSan 抓得到的几类问题

形态为何是 race
无锁 g++; / g--;两边都是写
一边 lock_guard、另一边裸写漏锁，没有 HB 边
payload 用 relaxed atomic 当发布relaxed 不建立 happens-before，payload 仍是 race

6.4 TSan 能识别的同步原语

标准库 mutex / shared_mutex / atomic（带正确 memory order）/ condition_variable / thread::join / future-promise / pthread 互斥与条件变量 / POSIX semaphore。

6.5 TSan 不能识别的

自绘 spinlock（需 __tsan_acquire / __tsan_release）、跨进程共享内存 + futex、仅靠 fence 拼出来的 HB。这些不是「TSan 误报」，是它看不见你的同步。

6.6 用法

TSAN_OPTIONS作用
halt_on_error=1第一发 race 就退出
second_deadlock_stack=1死锁报告带两条栈
history_size=7访问历史更长，内存更贵

6.7 性能与限制

5–15× CPU、5–10× 内存，与 ASan 互斥。只能报告这次跑到的 race，要多次跑、换负载。长时间跑可能把访问历史撑爆。

07

TSan 原理速览 ⭐

核心：vector clock + happens-before · FastTrack 的关键优化 · 性能开销来源（实战视角）

核心：vector clock… · FastTrack 的关键优化 · 性能开销来源（实战视角）
FastTrack、shadow word、为何 5–10× 见 sanitizer_internals.html §3。

7.1 核心：vector clock + happens-before

每线程一份 vector clock。mutex unlock→lock、atomic release→acquire、cv notify→wait、join 会合并双方时钟，画出 happens-before 边。新访问拿 shadow 里「上次访问的时钟」和当前比：对得上就安全，比不了就是 race。

7.2 FastTrack 的关键优化

每次访问都存完整 N 元 VC 会到 100×。FastTrack：多读不构成 race，读只记一个 epoch，写才存完整时钟，所以落到 5–10×。

7.3 性能开销来源（实战视角）

每次内存访问更新并比对 shadow；VC 随线程数涨；访问历史窗口加长则漏报少、内存爆。

MSan · MemorySanitizer 未初始化内存读

检测什么 · 用法 · 报告 · 原理速览 · MSan 难用的原因（实战视角） · …

检测什么 · 用法 · 报告

8.1 检测什么

读未初始化内存。ASan 看不见这一类：影子只管「这块能不能碰」，不管「值从哪来」。

struct S { int x, y; };
void f() {
    S s; s.x = 1;
    if (s.y > 0) {}   // y 未初始化 → use-of-uninitialized-value
}
// clang++ -O1 -g -fsanitize=memory   （仅 clang；依赖必须同样重编）

8.2 用法

gcc 没有 MSan。要链一条用 MSan 编过的 libc++ / 第三方库，否则未插桩代码一读栈上垃圾就假阳。

8.3 报告

第一行 use-of-uninitialized-value。开 origin tracking（-fsanitize-memory-track-origins=2）后，会多出「值在哪次分配产生、中间哪次 store 传过来」。

8.4 原理速览

编码与 trade-off 见 internals §4 MSan。

8.5 MSan 难用的原因（实战视角）

  • 仅 clang
  • 依赖必须全部 MSan 重编（含标准库），否则误报
  • 普通团队成本高；替代是 Valgrind Memcheck + -Wuninitialized

8.6 何时用 MSan

全 clang、能控制全部依赖、或 OSS-Fuzz 已提供 MSan sysroot 时才值得。关键数据处理可单独编一份。

LSan · LeakSanitizer 内存泄漏

工作方式 · 报告 · 检测原理 · 抑制误报 · LSan vs Valgrind 对比

工作方式 · 报告 · 检测原理

9.1 工作方式

Linux 上 LSan 嵌在 ASan 里，detect_leaks 默认 1。也可以 -fsanitize=leak 单独编，不做地址检查、开销更小。

9.2 报告

字段含义
Direct leak of N byte(s)根上无人指向，典型忘了 delete
Indirect leak挂在 Direct leak 对象上的连锁块
allocated from分配栈，不是「泄漏发生点」

9.3 检测原理

退出时停线程，从栈 / 全局 / 寄存器 / TLS 当根做可达性，标不到的就是泄漏。不是引用计数。

9.4 抑制误报

退出不释放的缓存、第三方 init，用 leak: 规则。每条抑制都是债，见 §11 片段。

9.5 LSan vs Valgrind 对比

对照图在 §10.3。一句话：能重编就 ASan+LSan；不能重编或要查未初始化，才上 Memcheck。

选项含义

范围写法

12.3 CMake 集成模板

不要只改 CMAKE_CXX_FLAGS。option 打开时 add_compile_options(-fsanitize=…) 与 add_link_options(-fsanitize=…) 成对，见 §2.3。ASan 与 TSan 做成互斥 option，配错直接 message(FATAL_ERROR)。

12.4 处理已知误报

抑制文件进仓库（如 tools/sanitizer_suppressions/），每条带 issue 与截止日期，CI 加载，季度 review。新增抑制要 reviewer 批。ASan/UBSan/TSan 必须 0 错误才 merge。

HWASan + GWP-ASan

14b.1 全家桶位置定位 · 14b.2 HWASan — 硬件辅助的轻量 ASan · 14b.3 GWP-ASan — 采样型生产 ASan · 14b.4 三档 Sanitizer 部署矩阵 · 14b…

让 Sanitizer 真的能上生产 ⭐

普通 ASan 因约 2× CPU、3–4× 内存不上生产。能上线的是硬件标签（HWASan）或采样（GWP-ASan）。

14b.1 全家桶位置定位

开销架构定位
ASan2× CPU / 3× 内存x86 / ARM开发 / CI
HWASan明显低于 ASan（ARM TBI/MTE）ARMv8.5+ 为主Android / ARM 预发布
GWP-ASan采样，平均接近 0任意大规模生产
kASan / kHWASAN内核插桩内核syzkaller 等

14b.2 HWASan — 硬件辅助的轻量 ASan

ARM Top-Byte Ignore：指针高 8 位放 tag，与 16 字节内存上的 4-bit tag 比对。ARMv8.5+ MTE 由 CPU 比对。x86 没有同等 TBI，HWASan 基本是 ARM 的戏。4-bit 碰撞会漏检（约 1/16），不是误报。

细节见 internals §6。

14b.3 GWP-ASan — 采样型生产 ASan

每 N 次 malloc 抽一次放到带 guard page 的槽（N 常见数千量级）。越界 / UAF 直接 SEGV，报告仍是 alloc / free / use 三栈。其余走普通分配器。单实例几乎抓不到，靠机群。Chrome PartitionAlloc、Android Scudo 都有实现。局限见 internals §7。

14b.4 三档 Sanitizer 部署矩阵

阶段开什么
本地 / CI 单测ASan + UBSan；并发 job 开 TSan
CI FuzzlibFuzzer + ASan + UBSan
ARM 预发布HWASan
全量生产GWP-ASan 采样，不开完整 ASan

14b.5 真实部署案例

Chrome、Android 公开用过 GWP-ASan / HWASan；内核侧是 syzkaller + kASan。这不是「所有生产都必须上」，而是「完整 ASan 上不了生产时的退路」。

15.1 一句话局限速记

ASan 远跳/过期 UAF 漏；TSan 只报本次交错；MSan 依赖未插桩就假阳；UBSan 只覆盖常见 UB；LSan 默认退出才扫；HWASan 碰撞漏检；GWP 靠机群。根因表见 internals。

15.2 行为差异

插桩改分配器、改时序、涨内存。race 可能开了 ASan 反而不现；也可能 OOM。这不是「ASan 修了 bug」，是布局变了。

16.4 速答示范（第 4 题）

TSan 怎么知道两次访问没有 happens-before？

每线程一份 vector clock，mutex unlock→lock / atomic release→acquire 会合并时钟。访问时拿 shadow 里上次的时钟和当前比：对得上有 HB，比不了就是 race。只报这次跑到的交错；自绘锁要注解，否则当漏同步。开销 5–15×，与 ASan 互斥。图见 §7。
