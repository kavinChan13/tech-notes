C++ 测试工程

C++ 的测试困难不在于缺工具——GoogleTest 已经二十年了。真正的困难有两条：一段代码能不能被测，在写它的时候就决定了；以及 C++ 的缺陷有很大一部分（越界、data race、UB）不是靠断言发现的，而是靠在不同的构建配置下重跑同一批用例。所以本文的重心是判断——什么该测、测在哪一层、什么时候该停手。

01

金字塔在 C++ 里多两层

别的语言分四层，C++ 底下还垫着编译期，侧面还挂着 sanitizer 重跑

测试金字塔的原始主张很简单：底层测试要多、要快、要稳；顶层测试要少。理由不是审美，而是一个很实际的算术——一个缺陷从「测试红了」到「我知道该改哪一行」的距离，随着层级上升迅速拉长。单元测试失败时你已经知道是哪个函数；端到端测试失败时你只知道「下单流程坏了」，接下来是两小时的排查。

这就像工厂的质检布点。最便宜的检验放在每个零件出车床的那一刻——卡尺一量，三秒钟，不合格立刻知道是哪台机器出了问题。最贵的检验是整车下线路试：能发现零件级检验发现不了的问题（异响、共振），但一旦发现，「到底是哪个零件」还得拆开来找。没有哪家工厂会只做路试，也没有哪家会只量零件。

1.2 C++ 独有的两层

标准的金字塔到这里就结束了，但 C++ 有两层别的语言不需要、或者根本没有。

地基：编译期测试。 C++ 的类型系统和模板系统本身就是一套可以出错的程序，而它出的错——布局假设不成立、模板被错误实例化、本该编不过的用法编过了——是运行期测试永远抓不到的。这类断言的成本近乎为零：不进可执行文件，不占运行时间，编译通过就是通过。

// 编译期测试：不进可执行文件，不占运行时间，编译通过即通过
static_assert(sizeof(Header) == 16, "Header 上了线就不能改大小");
static_assert(std::is_trivially_copyable_v<Header>);   // memcpy 安全
static_assert(alignof(RingSlot) == 64, "必须独占一条 cache line");

// 编译期可算的函数，直接在编译期对拍已知向量
constexpr std::uint32_t crc32(std::string_view s);
static_assert(crc32("123456789") == 0xCBF43926u);

// 「这段代码必须编不过」也是一种断言，用 concept + requires 表达
template <class T>
concept Serializable = requires(const T& t, Writer& w) { t.write(w); };

static_assert(Serializable<OrderMsg>);
static_assert(!Serializable<std::mutex>);   // 别人不许把锁塞进消息体

最后两行是一个容易被忽略的用法：static_assert(!Concept<T>) 是在测试「误用会被拒绝」。接口的正确性一半在于它接受什么，一半在于它拒绝什么，而后者通常没人测。

侧面：同一批用例在多个构建下重跑。 这是 C++ 测试里性价比最高的一笔投资，因为它不需要写任何新用例。越界读写、use-after-free、data race、未初始化读、整数溢出这些缺陷，你的断言几乎抓不到——它们要么恰好不影响这次的结果，要么表现为几小时后另一个位置的崩溃。而把同一批测试在 ASan / UBSan / TSan 下再跑一遍，插桩会在缺陷发生的那一刻报出来。

这五种 sanitizer 各自的原理、开关、误报抑制与符号化，在 Sanitizer 全家桶 里有系统展开；本文只负责回答「它们在测试体系里占哪个位置」——答案是不是新的一层，而是已有层的一个构建维度。

1.3 倒过来的金字塔

实践中最常见的形态不是金字塔，而是「冰淇淋锥」：底下几个单元测试，上面一大堆端到端测试，再上面是一层手工点检。它不是被设计出来的，而是长出来的——因为写端到端测试不需要改动生产代码，写单元测试往往需要。于是每次赶工，都选那条不用改代码的路。

症状真实原因修法
「这块逻辑没法写单元测试」它和 I/O、时钟、单例长在一起，没有接缝§2：把决策逻辑和副作用分开，不是加测试而是改设计
单测套件要跑 8 分钟里面混进了真文件、真端口、sleep把它们重新归类到集成层，单元层只留纯计算
改一行代码，红 40 个测试过度 mock，测试断言的是实现细节（§4.3）把交互断言换成状态断言，mock 换 fake
测试常年有 3 个是红的，大家习惯了flaky 没人治，红色失去了信号意义§7.2：隔离 + 限期修复 + 到期删除，红必须意味着坏

最后一行值得单独强调：一套允许长期存在红色的测试等于没有测试。测试的全部价值在于「红 = 有问题」这个映射是可信的，一旦不可信，后面所有投入都白费。

02

可测性是设计出来的

「这段代码没法测」几乎总是在说「这段代码耦合得不对」

一个被测对象要能测，需要满足三件事：能构造出来、能把输入喂给它、能把结果观察到。这三件事任何一件做不到，测试就写不出来——而做不到的原因一般不是测试框架不够强，是被测代码把不该固定的东西固定住了。

2.1 接缝在哪里

接缝（seam）：程序里一个不修改该处源码就能改变其行为的点。虚函数调用、模板参数、函数指针、链接期符号替换都是接缝；而直接写死的 std::chrono::system_clock::now() 或 Logger::instance() 不是——要换掉它们，只能改这一行代码本身。单元测试就是在接缝处插入替身。

所以「这个类能不能测」这个问题，可以精确地改写成：它的每一个不可控依赖，是不是都落在某个接缝上。不可控依赖只有几类，一眼就能数完：时间、随机数、文件系统、网络、进程环境、线程调度、以及别人的单例。

图里那条不对称性是这一节的要点：可测性不是可以叠加的分数，而是一条链。四个依赖里注入了三个，剩下一个是真时钟，那么所有涉及超时的用例就只能靠 sleep 去撞——而 sleep 慢、在负载高的 CI 机器上还会 flaky。这条链上任何一环没打通，收益就基本归零。

2.2 依赖注入的三种做法

Java 世界里依赖注入基本只有虚接口一种形态，C++ 有三种，而且它们的取舍差别很大——不是风格问题，是性能与编译期开销的真实差别。

// 甲 · 虚接口：运行期可换，最灵活；代价是间接调用 + 常常要堆分配
struct IClock {
    virtual ~IClock() = default;
    virtual TimePoint now() const = 0;
};
class Session {
    IClock& clock_;                              // 引用，不持有
public:
    explicit Session(IClock& c) : clock_(c) {}
};

// 乙 · 模板参数：零开销、可内联；代价是实现进了头文件、编译期膨胀
template <class Clock = SystemClock>
class SessionT {
    Clock clock_;                                // 值语义，可能是空类
public:
    TimePoint now() const { return clock_.now(); }   // 直接内联，无虚表
};
using ProdSession = SessionT<>;                  // 生产
using TestSession = SessionT<FakeClock>;         // 测试

// 丙 · 函数对象：只需要替换「一个动作」时最轻，不必为此造一个接口
class SessionF {
    std::function<TimePoint()> now_;             // 想零开销就模板化这个 Fn
public:
    explicit SessionF(std::function<TimePoint()> now =
                          [] { return SystemClock::now(); })
        : now_(std::move(now)) {}
};
甲 · 虚接口乙 · 模板参数丙 · 函数对象
运行期开销虚调用，不可内联零，空类还能被 EBO 消掉std::function 有间接与可能的堆；模板化后为零
编译期开销低——实现可以留在 .cpp高——实现必须在头文件，每个实例化各编一遍低（用 std::function）
能否运行期切换能（读配置决定用哪个实现）不能，编译期定死能
被测类型是否变不变变：测试里是另一个类型，不能塞进同一个容器不变
适合数量少、切换频率低的粗粒度依赖（存储、网络、时钟）热路径上的策略（分配器、哈希、比较器、时钟）只有一两个回调点的场景；也适合渐进式改造已有代码
别用在每秒调百万次的内层循环需要 ABI 稳定、或想缩短编译时间的模块边界依赖有多个方法、需要成组替换时

选择顺序我一般是：先问这个依赖在不在热路径上。不在（绝大多数情况）就用甲，因为它对编译时间最友好，实现能藏在 .cpp 里，改实现不会引起全量重编。在热路径上才用乙，并接受它带来的编译期代价。丙用在两种时候：只需要替换一个动作（「怎么取当前时间」），或者在一份不敢大改的老代码里先凿出一个接缝——加一个带默认值的构造参数，是改动最小、且对现有调用方完全兼容的做法。

还有第四种在 C++ 里独有、但要谨慎的做法：链接期替换。测试的可执行文件不链接真实的 net_send.o，而链接一个同名符号的假实现。它不需要改一行生产代码，所以在处理遗留代码时有奇效；代价是接缝在构建系统里而不在源码里，读代码的人完全看不到它的存在，而且一个可执行文件只能有一个版本的替身，同一个套件里没法给不同用例用不同的假实现。作为过渡手段可以，别当默认方案。

2.3 为什么不测私有函数

这条规则常被当成教条，其实理由很具体：私有函数不是契约，是你今天恰好选择的实现路径。给它写测试，等于把一个随时可能改的内部决策变成了一份合同——下次重构把三个私有函数合并成一个，生产行为完全没变，测试全红。这就是 §4.3 那个反模式的另一副面孔。

而绕过访问控制的手段，无论哪一种，都在向你发出同一个信号：

做法问题
#define private public 后 include 头文件ODR 违规 + ABI 不一致（访问说明符影响布局排序），是真正的 UB，不只是难看
FRIEND_TEST / 手写 friend class XxxTest;生产头文件里出现测试类名，生产代码开始知道测试的存在
把成员改成 protected，测试里继承出来为了测试放宽了封装；子类还可能改变基类不变量
整个测试文件 #include "impl.cpp"能跑，但符号会和正常构建冲突，且链接期替换等手段全部失效

信号是：那个私有函数已经足够复杂到需要独立测试了，说明它其实是另一个概念，应该被提取成独立的类或自由函数——提出来之后它自然是公开的，测它天经地义，也不再需要任何 hack。这里唯一的例外是纯粹的实现细节助手（一个复杂的位运算、一个解析子步骤），把它放进匿名命名空间或 detail 命名空间的自由函数，然后光明正大地测：它不在公开 API 里，但对同一个翻译单元的测试可见。

2.4 全局状态是头号敌人

单例和全局变量之所以是测试的头号敌人，不是因为「难替换」——那只是麻烦。真正的问题是它在本来相互独立的测试之间建立了隐藏的通信通道，于是测试结果开始依赖执行顺序。

要注意，被污染的不只是显式的单例。static 局部变量的缓存、进程级的信号处理器与 locale、被改过的环境变量、std::rand() 的全局种子、全局分配器统计、线程池里残留的任务——都是同一类问题。它们的共同特征是「活得比一个测试长」。

一个能立刻落地的判据：如果把用例顺序打乱、或者把整个套件并行跑，结果会变，那就一定存在共享状态。所以 --gtest_shuffle 和 ctest -j 不是可选的加速项，而是这类耦合的检测器。不能并行的单元套件，往往是因为它有全局状态，而不是因为它「本来就不能并行」。

现实里不可能一次消灭所有单例。折中做法是给它加一个仅供测试的重置或替换入口——Config::ResetForTest()、或者把单例改成「持有一个可替换的 unique_ptr 实例」，fixture 的 SetUp 里换成干净的一份、TearDown 里换回去。这不优雅，但它把「顺序相关」这件事从隐式变成了显式，是通往彻底去单例的中间站。

03

GoogleTest 的关键武器

值得记的不是宏表，是那几处语义上会咬人的地方

GoogleTest 的 API 文档很全，这里不重复。值得专门讲的是四处：fixture 的生命周期（决定了什么能共享）、参数化与类型参数化（决定了模板代码怎么测）、死亡测试（有一套独立的进程语义）、以及 EXPECT 与 ASSERT 的差别（很多人以为只是「要不要继续」）。

GoogleTest / Catch2 / doctest 的选型对比见 现代 C++ 库全景 §13；用 CMake + CTest 把它接进构建与覆盖率报告的完整配置见 CMake 与 CI 工程化 §10。本章只讲怎么写测试。

3.1 fixture 的生命周期

最常被误解的一点：TEST_F 的 fixture 对象不是共享的，每个测试都会新构造一个。所以在 SetUp 里准备一份重量级资源（起一个数据库、编译一个正则、加载一个模型），会在每个测试里重复付一遍成本。

图里最后那条判据是实践中真正用得上的：构造昂贵且不可变的东西放 suite 级，任何可变状态放 per-test 级。把可变状态提到 suite 级去「优化速度」，等于亲手造出 §2.4 的顺序依赖，而且因为它藏在 fixture 里，比全局变量更难发现。

3.2 参数化与类型参数化

TEST_P（值参数化）解决的问题不是「少写几行」，而是失败信息的精度。在一个测试里写 for 循环跑 20 组输入，失败时你看到的是「期望 true 实际 false」，还要自己回去数是第几次迭代；参数化之后每组输入是一个独立用例，失败时名字里直接带着参数，而且其余 19 组仍然会跑完——你一次就知道是全挂还是只挂边界那一组。

TYPED_TEST（类型参数化）则是测模板代码的正道。模板只有被实例化才会真正编译和执行，所以「我测了 MyVector<int>」并不能说明 MyVector<std::string> 或 MyVector<NonCopyable> 也对。正确的做法是把不变量写一遍，让它跑遍所有实例化。

// 值参数化：失败时打印的是具体参数，而不是「第 7 次循环」
struct ParseCase { std::string_view in; bool ok; std::int64_t want; };

class ParseTest : public testing::TestWithParam<ParseCase> {};

TEST_P(ParseTest, MatchesSpec) {
    const auto& c = GetParam();
    std::int64_t got{};
    EXPECT_EQ(parse(c.in, got), c.ok);
    if (c.ok) EXPECT_EQ(got, c.want);            // 失败也继续，见 §3.4
}
INSTANTIATE_TEST_SUITE_P(Boundaries, ParseTest, testing::ValuesIn(kCases),
    [](const auto& info) { return std::string{info.param.in}; });   // 用例名带上输入

// 类型参数化：同一份不变量跑遍所有实例化 —— 测模板代码的正道
template <class Queue> class QueueTest : public testing::Test {};
using Impls = testing::Types<SpscQueue<int>, MpmcQueue<int>, LockedDeque<int>>;
TYPED_TEST_SUITE(QueueTest, Impls);

TYPED_TEST(QueueTest, PopSeesWhatPushPut) {
    TypeParam q;                                 // 当前被测类型
    ASSERT_TRUE(q.push(42));                     // 前置不成立就没必要继续
    int v{};
    ASSERT_TRUE(q.pop(v));
    EXPECT_EQ(v, 42);
    EXPECT_FALSE(q.pop(v));                      // 空了就该失败
}

类型参数化还有一个副作用常被当成主要收益：它把「什么是这个抽象的契约」写成了可执行的形式。上面那个 QueueTest 实际上是「队列」这个概念的定义。将来有人新写一个实现，把类型加进 Impls 就得到了一整套一致性检查——这比任何文档都可靠。对自定义容器、分配器、序列化后端、策略类，这是默认该用的形态。

两个实践细节：一是 INSTANTIATE_TEST_SUITE_P 一定要传名字生成器，否则用例叫 Boundaries/ParseTest.MatchesSpec/7，那个 7 对排查毫无帮助；名字里只能用字母数字和下划线，所以生成器里要把输入里的特殊字符处理掉。二是参数化用例的数量会乘进每一轮 sanitizer 构建，一个 500 组的参数化在 TSan 下可能就是十几分钟——参数组要挑得有代表性（边界、越界、空、最大值、已知回归样本），而不是把所有组合都枚举一遍，那是 §6 的 fuzz 该做的事。

3.3 死亡测试与 fork 语义

死亡测试用来验证「非法输入会让程序确定地死掉」——契约违约、不变量被破坏、配置非法。它是断言型防御（assert、CHECK、std::abort）唯一的测试手段。但它的实现方式决定了一套完全不同的语义：EXPECT_DEATH 会 fork 出一个子进程来执行那条语句。

// 多线程程序里这一行几乎是必须的：fork 后重新 exec，不继承别的线程的锁
int main(int argc, char** argv) {
    testing::InitGoogleTest(&argc, argv);
    GTEST_FLAG_SET(death_test_style, "threadsafe");
    return RUN_ALL_TESTS();
}

TEST(RingBufferDeathTest, RejectsNonPowerOfTwo) {
    EXPECT_DEATH(RingBuffer(48), "power of two");
    //           ^ 在子进程里执行   ^ 是 stderr 的正则「部分匹配」，不是全串相等
}

// 想区分「怎么死的」，用 EXPECT_EXIT
EXPECT_EXIT(flush_and_quit(), testing::ExitedWithCode(2), "flush failed");

// ❌ 典型误用：在父进程里断言子进程的副作用
TEST(Bad, ChecksSideEffect) {
    std::vector<int> v;
    EXPECT_DEATH({ v.push_back(1); die(); }, "");
    EXPECT_EQ(v.size(), 1u);   // 永远失败：push_back 发生在子进程，v 在父进程仍是空的
}

还有一条工程上的注意：死亡测试和 sanitizer 相处得不好。ASan 与 LSan 在子进程异常退出时可能报出泄漏（因为进程是被 abort 掉的，没走正常清理），TSan 对 fork 本身也有限制。实践中的做法是把死亡测试的套件名统一以 DeathTest 结尾（GoogleTest 会保证这类套件先运行），并在 sanitizer 轮次里用 --gtest_filter=-*DeathTest* 排掉——它们验证的是控制流，不是内存安全，在那一轮里没有信息增量。

3.4 EXPECT / ASSERT 与匹配器

EXPECT_* 失败后继续执行本测试，ASSERT_* 失败后 return。这是大家都知道的部分。下面几条才是真正会咬人的：

要点说明
怎么选后续断言还有意义就用 EXPECT，没意义就用 ASSERT。指针非空、容器非空、解析成功这类前置条件用 ASSERT——否则下一行就是解引用空指针，测试从「失败」变成「崩溃」，还带走了同进程里剩下的所有用例
ASSERT 只能在返回 void 的函数里它的实现就是 return;。写在返回值的辅助函数里编不过；辅助函数里想断言，就把它改成 void f(..., bool* ok) 或者用 testing::AssertionResult
辅助函数里的 ASSERT 不会终止测试它只 return 出那个辅助函数，调用者继续往下跑。要在调用点加 ASSERT_NO_FATAL_FAILURE(helper())，这是最常见的一处误判
一个测试里堆十个 EXPECT不是错，但失败信息会变得难读。更好的做法是用一个 EXPECT_THAT 描述整个期望结构（见下），一次给出完整差异
浮点永远不用 EXPECT_EQ，用 EXPECT_DOUBLE_EQ（4 ULP 以内）或 EXPECT_NEAR（自己给容差）。涉及累加误差时容差要自己算，不要抄一个 1e-6
自定义类型给它写 PrintTo 或 operator<<。否则失败信息是一串十六进制字节，等于没有信息

匹配器（EXPECT_THAT + gMock matchers）是 GoogleTest 里最被低估的部分，因为它把断言从「逐个字段比」变成「描述期望的形状」。EXPECT_THAT(orders, UnorderedElementsAre(Field(&Order::id, 7), Field(&Order::id, 9))) 这一行，失败时会打印实际容器的完整内容和它与期望的差异；等价的手写循环只会告诉你 size() != 2。

值得掌握的是自定义匹配器：当同一个领域概念在多处被断言时（「这个响应是合法的」「这两棵树等价」「这个时间戳在窗口内」），用 MATCHER_P 定义一次，就同时获得了复用和可读的失败信息——匹配器的描述字符串会直接出现在失败输出里。判据很简单：同一组断言在三个地方出现过，就该变成一个匹配器；而一个匹配器如果需要解释才能看懂它在断言什么，说明它包了太多东西。

04

gMock：用得少才用得对

它是个好工具，但它解决的问题比大多数人以为的窄得多

4.1 mock / stub / fake / spy

这四个词常被混用，但它们的区别决定了测试的耐久度。

替身做什么断言什么什么时候用
stub按脚本返回固定值，不关心被怎么调不断言（只是让代码能跑下去）被测逻辑需要一个输入源，而这个源本身不是测试重点
fake真实现，只是简化版——内存版仓储、内存版文件系统、假时钟断言最终状态默认选择。 依赖有状态、会被反复调用、多个用例都要用它
mock预先声明期望（次数、参数、顺序），不满足就失败断言交互本身交互就是被测的行为：重试了几次、超时后有没有发退订、失败时有没有上报
spy记录被怎么调了，事后由测试自己检查事后断言交互，但不预设脚本想断言交互又不想被「顺序 / 次数」绑死时，比 mock 松

选择的关键是问一句：我要断言的是「结果对不对」，还是「它是怎么做到的」。绝大多数时候是前者，而前者应该用 fake + 状态断言。只有当「怎么做到的」本身就是需求——「网络抖动时必须重试且只重试一次」「关闭时必须发一条退订」——mock 才是对的工具，因为这时候「调用了什么」确实是可观察的对外行为。

// mock 用在对的地方：「失败后恰好重试一次」本身就是需求，不是实现细节
class MockPriceFeed : public IPriceFeed {
public:
    MOCK_METHOD(std::optional<Price>, fetch, (SymbolId), (const, override));
};

TEST(SettleTest, RetriesExactlyOnceOnTransientFailure) {
    testing::NiceMock<MockPriceFeed> feed;       // 没设期望的其它调用不刷警告
    EXPECT_CALL(feed, fetch(kBTC))
        .WillOnce(testing::Return(std::nullopt))          // 第一次瞬时失败
        .WillOnce(testing::Return(Price{42}));            // 重试成功
    // 第三次调用会因为没有可用的 action 而失败 —— 「只重试一次」被真正断言了

    EXPECT_EQ(settle(feed, kBTC), Price{42});
}

写 fake 要额外写代码，这是它唯一的成本——一个内存版仓储可能是两百行。但这两百行会被几十个用例共享，而且它本身可以被测试（用 §3.2 的 TYPED_TEST 让真实现和 fake 跑同一套契约测试，保证 fake 没有偏离语义）。这是 fake 相比 mock 最被低估的优势：fake 的正确性是可验证的，而每个 EXPECT_CALL 里对依赖行为的假设，没有任何东西在检查它是否还符合真实现。依赖升级后 mock 的假设悄悄失效、测试依然全绿，这种情况非常常见。

4.2 Naggy / Nice / Strict

gMock 的裸 MockFoo 是「naggy」的：任何没被 EXPECT_CALL 覆盖的调用都会打印一条 Uninteresting mock function call 警告，但不算失败。三种包装的差别就在这里：

未预期的调用后果用在
MockFoo（naggy）打警告日志噪音大，重要失败被淹没基本别直接用
NiceMock<MockFoo>安静接受，返回默认值测试只关心自己声明的那几个交互默认选这个。 尤其是依赖有 log() 这类无关方法时
StrictMock<MockFoo>直接失败「不该发生的调用」也被测到了需要断言「没有多余副作用」时，例如「缓存命中时绝不碰数据库」

默认用 NiceMock 的理由是耐久度：StrictMock 让测试对被测代码的任何新增调用都敏感，哪怕新增的是一行日志。这种敏感度只在你真的想断言「什么都没多做」时才有价值，其余时候它只是让每次无害改动都伴随一批测试失败。反过来，NiceMock 的代价是会掩盖「返回了默认值而你没注意」——所以关键方法仍然要显式 EXPECT_CALL 或 ON_CALL 设好返回。

另外两个容易踩的点：EXPECT_CALL 必须写在被测动作之前（它是「注册期望」，不是「事后检查」）；以及 EXPECT_CALL 里的期望在 mock 对象析构时才校验，所以 mock 的生命周期要覆盖到断言之后——把 mock 定义在一个提前结束的作用域里，会让「次数不符」的失败报在一个莫名其妙的行号上。

4.3 测试锁死实现

这是 mock 的经典代价，值得单独讲，因为它的症状很有误导性：一次不改变任何外部行为的重构，让几十个测试变红。大多数人的反应是「测试真有用，帮我发现了重构的问题」，但这里并没有问题——测试红了只是因为它断言的是实现路径。

过度 mock 还有两个不那么明显的代价。其一，它让测试失去了发现真实集成问题的能力：如果所有依赖都是 mock，那么被测代码和依赖之间的契约误解（参数单位、空值语义、错误码含义）永远测不出来，因为 mock 就是按你的误解写的。其二，InSequence 是最脆的一种断言——它把调用顺序也变成了契约，而顺序在绝大多数情况下并不是需求的一部分。真的需要断言顺序时，用 After() 或显式的 Sequence 只约束那两个确实有依赖关系的调用，而不是给整个测试套上 InSequence。

05

覆盖率的正用与误用

它是一个很好的「哪里没测」的定位工具，和一个很坏的考核指标

5.1 行 / 分支 / MC/DC

「覆盖率 85%」这句话如果不说清是哪种覆盖率，基本没有信息量——三种口径对同一段代码给出的数字可以差一倍。

C++ 还有两个别的语言没有的口径问题。一是模板： 覆盖率工具看到的是实例化后的代码，所以 Foo<int> 被完整测过、Foo<std::string> 从未实例化时，后者要么根本不出现在报告里（显得覆盖率很高），要么算成 0%——取决于工具和是否显式实例化。这正是 §3.2 用 TYPED_TEST 的另一个理由。二是头文件里的内联函数： 它们会在多个目标文件里各有一份，合并规则不同的工具给出的数字会不一样。所以跨工具、跨项目比较覆盖率数字基本没有意义，只有同一套配置下的趋势才可比。

5.2 llvm-cov 实操

clang 的 source-based coverage（-fprofile-instr-generate -fcoverage-mapping）比 gcov 更准，因为它的计数器挂在源码结构上而不是行号上，能正确处理模板、内联和宏。完整流程只有五步：

# 1. 插桩构建（clang 专属；注意用 -O1 而非 -O0，插桩本身已经很慢了）
clang++ -O1 -g -fprofile-instr-generate -fcoverage-mapping \
        -o build/tests test/*.cc src/*.cc -lgtest_main -lgtest

# 2. 跑测试；%p 展开成 pid，避免并行用例互相覆盖同一个文件
LLVM_PROFILE_FILE='cov/%p.profraw' ctest --test-dir build -j"$(nproc)"

# 3. 合并（-sparse 让没执行过的函数不占空间，大项目上差别很大）
llvm-profdata merge -sparse cov/*.profraw -o cov/all.profdata

# 4. 看分支而不是行，并且把测试代码和三方库本身排除掉
llvm-cov report build/tests -instr-profile=cov/all.profdata \
        -ignore-filename-regex='(test|third_party)/' \
        -show-branch-summary

# 5. 真正有用的一步：把未走过的分支标红，逐个问「这条路径为什么进不去」
llvm-cov show build/tests -instr-profile=cov/all.profdata \
        -show-branches=percent -format=html -output-dir=cov/html

第 4 步那个 -ignore-filename-regex 不是美化报告：测试代码自身的覆盖率永远接近 100%（它就是被执行的那部分），把它算进去会系统性地虚高总数，而且虚高的幅度取决于测试代码的占比——于是「多写测试」和「多测生产代码」在数字上变得无法区分。

第 5 步是覆盖率唯一真正的用法：不看总百分比，看未覆盖的清单。逐个问「这条分支为什么进不去」，答案通常落在三类里——(a) 这是个真实但没测的场景，补用例；(b) 这条路径实际上不可达（死代码、防御性的 default: 分支），删掉或标注；(c) 它需要很难构造的条件（malloc 失败、write 返回 EINTR），这时候要么注入一个可失败的分配器/系统调用包装，要么明确承认不测。这三类答案都是有价值的产出，而总百分比不是。

用 CMake 把插桩构建做成一个独立的构建类型、在 CI 里生成并上传 lcov / llvm-cov 报告的具体配置，见 CMake 与 CI 工程化 §10，这里不重复。

5.3 一旦指标化就失效

「覆盖率必须 ≥ 80% 才能合入」这条规则，几乎总是会产出下面这种测试：

❌ 为覆盖率而写

调一遍所有公开方法，不写断言，或者只写 EXPECT_NO_THROW。行覆盖漂亮地涨上去，而这些测试唯一能发现的缺陷是崩溃——它们对返回值是否正确一无所知。更糟的是它们永远不会红，于是给人一种「这块有测试」的错觉，真正的缺陷反而更难被注意到。

✅ 把覆盖率当定位工具

不设总数门槛，改成两条：新增代码的分支覆盖不低于某个值（增量门槛，防止新债），以及核心模块的未覆盖分支清单要在评审里逐条有说法。前者可自动化，后者靠人——但它问的是「这条路径为什么不用测」，而这个问题无法用无断言的测试糊弄过去。

这是古德哈特定律在测试上的标准案例：一项指标一旦成为考核目标，它就不再是好的度量。根本原因在 §5.1 那张图的最后一行——覆盖率度量的是「执行到了」，而我们想要的是「验证过了」，两者之间没有任何机制保证关联。真正能防住无断言测试的手段是变异测试（mutation testing）：故意改动生产代码（把 < 改成 <=、把返回值改成常量），看有没有测试因此变红。C++ 的变异测试工具链（mull 一类）还不够成熟、成本也高，但它的思路值得借用——评审测试时可以手动做一次：如果我把这个函数的返回值改成固定值，有哪个测试会红？ 答不出来，那些测试就没在测什么。

06

属性测试与 fuzz 的位置

用例测「这些输入」，属性测试和 fuzz 测「所有输入」

例子化的测试（example-based，也就是我们写的绝大多数用例）有一个结构性的上限：它只能覆盖作者想到的输入。而缺陷恰恰集中在作者没想到的地方。属性测试和 fuzz 都是在突破这个上限，区别在于它们各自替你回答的问题不同。

属性测试（property-based testing）：不写「输入 X 应得到 Y」，而写一条对所有合法输入都成立的性质，由框架生成大量随机输入去反驳它；一旦找到反例，框架会自动收缩（shrink）成最小的那个。C++ 侧的实现是 RapidCheck（GoogleTest 集成最顺）等。

「收缩」是属性测试相比手写随机测试的核心价值，也是它和 fuzz 最大的体验差别：框架报给你的不是一个 4KB 的随机数组，而是「{0, -1} 这两个元素就能让你的排序出错」。一个能直接粘进新用例的最小反例，和一个需要花两小时缩小的崩溃输入，排查成本差一个量级。

但属性测试不是万能的——它只在你能说出一条性质时才有用，而这恰好把它的适用范围限定得很清楚：

适合的形态性质长什么样C++ 里的典型对象
可逆运算（往返）decode(encode(x)) == x序列化、压缩、协议编解码、字符集转换、URL / base64
参考实现对拍fast(x) == naive(x)SIMD 优化版 vs 朴素版、无锁容器 vs 加锁版、缓存版 vs 直算版
不变量任意操作序列后，结构自检仍通过红黑树 / 跳表 / 分配器 / 状态机 —— 随机生成操作序列，每步后调一遍 check_invariants()
代数性质幂等 f(f(x))==f(x)、交换、结合、单调归一化函数、集合运算、区间合并、比较器（严格弱序！std::sort 的前提）
元变形关系输入这样变，输出应那样变「多加一条订单，总额只增不减」「打乱输入顺序，结果不变」

反过来，写不出性质的地方就别硬套。业务规则「VIP 用户满 300 减 50」没有任何数学性质可言，用属性测试去写只会得到一个把业务规则抄了两遍的测试——而这正是 §4.3 那个反模式的变体。

fuzz 则是同一条路上更靠前的一步：它不需要你说出性质，只需要一个「不该发生的事」的判据（崩溃、sanitizer 报错、断言失败、超时），然后由覆盖率反馈引导变异去找触发它的输入。所以三者的关系可以这样排：

输入从哪来判据（oracle）一次运行多久跑在哪一档
例子化用例人写的精确的期望值毫秒每次提交
属性测试框架按类型生成 + 收缩一条性质秒级（默认 100 组）每次提交（组数调小）
fuzz覆盖率引导的变异 + 语料库只有「不该崩」分钟到小时nightly / 持续

三者的判据强度是递减的，而覆盖输入的能力是递增的——所以它们不互相替代。一个实践上的连接点：fuzz 或属性测试找到的每一个反例，都要变成一个固定的例子化用例提交进去。否则下一次随机不一定还能撞到它，修复就没有回归保护。这是把随机测试的成果沉淀成资产的唯一方式。

还有一个常被忽略的组合：属性测试和 sanitizer 是乘法关系。属性测试负责把代码推到奇怪的状态，sanitizer 负责在那里发现内存与并发问题——把属性测试放进 ASan 轮次，比在 Debug 轮次里跑十倍的组数更有价值。

CI 分层与 flaky 治理

测试体系的实际形状，是由「开发者愿意等多久」决定的

7.1 五档流水线

§1.2 说过一遍 sanitizer 会带来 2–15 倍的减速，再乘上多平台、多编译器、多标准版本，「全都跑」的总时长很容易到小时级。而反馈时长有一条硬的心理边界：超过十分钟，开发者就会开始想办法绕过它——本地跳过钩子、盯着 CI 只看第一个失败、或者干脆合了再说。所以分层的目标不是「跑得全」，而是在十分钟的预算里把信噪比做到最高。

几个排布上的判断值得说明。ASan + UBSan 放在 PR 档而 TSan 不放：前者 2–3 倍还在预算内，而且发现的是最常见的一类缺陷；TSan 的 5–15 倍放不进十分钟，而且 data race 通常不是「这次改动刚引入」，nightly 的延迟可以接受。Release 构建必须在 PR 档：很多 UB 只在 -O2 下才改变行为，只跑 Debug 等于放过了一整类问题。--gtest_shuffle 放在 PR 档：它不花时间，但能持续把 §2.4 的顺序耦合逼出来。性能基线放 nightly 而不是 PR：共享 CI 机器上的性能数字噪声太大，放进 PR 只会制造 flaky。

还有一条与分层同等重要、但常被忽略：越靠右的档位越需要明确的负责人。nightly 和 weekly 天然没人盯，而一旦它连红三天没人管，它就永久失去了信号意义——这和 §1.3 最后那条是同一个道理。有效的做法是让失败自动创建一张有 owner 的工单，而不是发一封谁都不会点开的邮件。

7.2 flaky 测试治理

flaky（同一份代码，有时红有时绿）是测试体系里破坏力最大的东西，因为它攻击的是测试的信任度。一旦团队养成了「红了先重跑一次」的习惯，真实的回归也会被这个习惯吃掉。

成因典型形态根治手段
真实时间sleep(100ms) 等一个异步结果；CI 机器一忙就超时注入假时钟手动推进（§2.2）；或改成条件变量 / future 等待事件而不是等时长
顺序依赖单跑绿、全跑红，或 shuffle 后随机红（§2.4）消除共享状态；--gtest_shuffle 常开，让它必然暴露
并发非确定性多线程用例偶尔断言失败TSan 跑一轮，多半能定位到真实 race——这类 flaky 通常是真 bug，不是测试问题
未初始化 / UAF换编译器、换机器就变；加一行打印就好了ASan / MSan。「加打印就好了」是内存问题的经典签名
外部资源写死的端口被占、共享测试库被别人改、域名解析抖动端口用 0 让内核分配；每个用例独立的临时目录；集成测试用容器起自己的依赖
哈希 / 指针序断言依赖了 unordered_map 的遍历顺序或指针地址断言改成无序匹配（UnorderedElementsAre）；别让指针值进断言

治理流程比清单更重要，三步：测量 → 隔离 → 限期。测量是 nightly 里把套件重跑 20 遍统计通过率，把 flaky 从「大家的印象」变成一份有数字的清单——没有这一步，讨论永远停留在「我觉得那个测试不太稳」。隔离是把确认的 flaky 移出阻塞门禁（标记而不是删除），让主干的红色重新变得可信。限期是关键的一条：每个被隔离的用例必须有 owner 和到期日，到期未修就删掉。

「到期就删」听起来激进，但它背后的账是清楚的：一个被隔离的测试不提供任何保护（它的失败不再阻塞任何东西），却持续消耗 CI 时间和每个看到它的人的注意力。把它留在那里唯一的作用是让「我们有测试覆盖」这句话继续成立——这比没有测试更危险。删掉它至少让缺口变得可见。

最后一条经验，和上面的表格第三行相关但值得单独强调：不要默认 flaky 是测试的问题。并发类的 flaky 里有相当比例是生产代码里真实的 data race，只是在测试环境下的调度更容易撞上。把它当测试问题去「稳定化」（加重试、加 sleep、放宽断言），等于亲手把一个已经被发现的线上事故埋回去。判断方法很直接：先在 TSan 下跑一轮，让工具告诉你是谁的问题。

8.1 基础（必答）

  1. 基础EXPECT_* 和 ASSERT_* 的区别是什么？怎么选？

    EXPECT 失败后继续执行本测试，ASSERT 失败后立刻 return。选择判据是后续断言还有没有意义：指针非空、容器非空、解析成功这类前置条件用 ASSERT，否则下一行就是解引用空指针，测试从「失败」变成「崩溃」，还会带走同进程里剩下的所有用例；相互独立的多个字段检查用 EXPECT，一次能看到全部差异。

    两个常被忽略的细节：ASSERT 的实现是 return;，所以它只能写在返回 void 的函数里；而写在辅助函数里时它只 return 出那个辅助函数，不会终止测试——调用点需要 ASSERT_NO_FATAL_FAILURE(helper())。

  2. 基础TEST_F 的 fixture 对象是多个测试共享的吗？SetUp() 和构造函数该用哪个？

    不共享，每个 TEST_F 都会新构造一个 fixture，顺序是：构造函数 → SetUp() → 测试体 → TearDown() → 析构函数。只有 static 的 SetUpTestSuite() / TearDownTestSuite() 是整套一次。

    SetUp() 存在的理由是构造函数里不能用 ASSERT_*（它展开成 return;，构造函数没有返回值），也不能调用虚函数；TearDown() 的理由是析构函数里断言失败会在栈展开时出问题，而 TearDown 里可以正常断言「资源清干净了」。

    由此得到一条判据：构造昂贵且只读的东西放 suite 级，任何可变状态放 per-test 级。把可变状态提到 suite 级去省时间，就是亲手造出测试间的顺序依赖。

  3. 基础为什么不该给私有函数写测试？如果它确实复杂到需要单独测呢？

    因为私有函数不是契约，而是今天恰好选择的实现路径。给它写测试等于把一个随时会改的内部决策变成了合同：下次重构把三个私有函数合成一个，对外行为完全没变，测试却全红。

    而绕过访问控制的手段都在发同一个信号：#define private public 是 ODR 违规加布局不一致，属于真 UB；FRIEND_TEST 让生产头文件开始知道测试类的名字；改 protected 再继承是为测试放宽封装。

    正解是提取：它复杂到需要独立测试，说明它其实是另一个概念，提成独立的类或自由函数之后它自然是公开的。纯实现细节的助手（一段位运算、一个解析子步骤）可以放进 detail 或匿名命名空间的自由函数，光明正大地测。

  4. 基础「代码覆盖率 90%」这句话，为什么信息量很低？

    两个层面。第一，没说是哪种口径：行覆盖只要求这一行执行过，if (a && b) 一个用例就 100%；分支覆盖要求判断真假各一次；MC/DC 要求每个子条件都独立决定过结果（N 个条件要 N+1 个用例）。同一段代码三个数字能差一倍。

    第二，也是更根本的：三种口径都只知道「代码被执行了」，不知道「结果被验证了」。一个只调函数、不写任何断言的测试能把行覆盖刷满。所以它是很好的「哪里没测」定位工具，是很坏的考核指标。

    C++ 还多两个坑：模板只有被实例化才计入（所以 Foo<int> 测透了不代表 Foo<std::string> 也测了），头文件内联函数在不同工具下的合并规则不同。跨项目比数字没有意义，只有同一套配置下的趋势可比。

8.2 中级（区分熟练度）

  1. 中级C++ 里依赖注入有哪几种做法？各自的取舍是什么？

    三种。虚接口：运行期可换，实现能留在 .cpp 里（编译期友好），代价是虚调用不可内联。模板参数：零运行期开销、可内联、空类还能被 EBO 消掉，代价是实现必须进头文件、每个实例化各编一遍，而且被测类型本身变了（生产和测试是两个类型，不能塞进同一个容器）。函数对象：只替换「一个动作」时最轻，不必为此造接口；用 std::function 有间接与可能的堆分配，模板化后为零。

    选择顺序：先问这个依赖在不在热路径上。不在（绝大多数情况）就用虚接口，因为编译时间最友好；在热路径上（分配器、哈希、比较器、时钟）才用模板参数。函数对象用在只有一两个回调点、或者要在不敢大改的老代码里先凿出一个接缝时——加一个带默认值的构造参数，对现有调用方完全兼容。

    C++ 还有第四种：链接期替换（测试二进制链一个同名符号的假实现）。处理遗留代码时有奇效，但接缝在构建系统里而不在源码里，读代码的人看不见，而且一个二进制只能有一份替身。作为过渡手段可以，别当默认。

  2. 中级EXPECT_DEATH 是怎么实现的？由此带来哪些坑？

    它 fork() 出一个子进程执行那条语句，父进程 waitpid 收集退出状态，并用正则部分匹配子进程的 stderr。正是因为真正死掉的是子进程，父进程才能继续跑后面的用例。

    三个坑。副作用看不见：子进程里 push_back、改全局、改成员，父进程一概观察不到，所以在 EXPECT_DEATH 之后断言这些修改永远失败。多线程下 fork 极易死锁：fork 后只有调用线程存活，其它线程持有的锁永远不会释放，子进程卡死，表现为超时而不是失败——所以多线程程序要设 death_test_style = "threadsafe"（改成 fork + 重新 exec 测试二进制，慢但不继承那些锁）。「死」的定义很宽：abort 和 SIGSEGV 都算死，想区分「以错误码 2 退出」要用 EXPECT_EXIT + ExitedWithCode。

    工程上还要注意它和 sanitizer 相处不好（子进程被 abort 掉没走清理，LSan 可能报泄漏），实践中把套件名以 DeathTest 结尾，并在 sanitizer 轮次里 --gtest_filter=-*DeathTest* 排掉。

  3. 中级什么时候该用 gMock，什么时候 fake 更好？

    判据是一句话：我要断言的是「结果对不对」，还是「它是怎么做到的」。前者（绝大多数情况）用 fake + 状态断言；只有当「调用了什么」本身就是对外可观察的需求时才用 mock——「网络瞬时失败必须重试且只重试一次」「关闭时必须发一条退订」「失败必须上报告警」，这时候交互就是行为。

    fake 的代价是要写代码（一个内存版仓储可能两百行），但它被几十个用例共享，而且它本身可以被测试：用 TYPED_TEST 让真实现和 fake 跑同一套契约测试，保证 fake 没有偏离语义。这是最被低估的一点——fake 的正确性可验证，而每个 EXPECT_CALL 里对依赖行为的假设，没有任何东西在检查它是否还符合真实现。依赖升级后 mock 的假设悄悄失效、测试依然全绿，很常见。

    用 mock 时默认包 NiceMock（未预期的调用安静接受）；只有确实要断言「什么都没多做」时才用 StrictMock，因为它对被测代码的任何新增调用都敏感，哪怕只是加了一行日志。

  4. 中级一个测试单跑通过、和别人一起跑就失败，怎么定位？为什么 CI 该默认开 --gtest_shuffle？

    这是共享状态的确诊症状：某个活得比单个测试更长的东西被前面的用例改过了。范围比「单例」宽得多——static 局部变量的缓存、进程级信号处理器与 locale、环境变量、std::rand() 的全局种子、线程池里残留的任务、提到 SetUpTestSuite 的可变 fixture 状态，共同特征是「活得比一个测试长」。

    定位手段：用 --gtest_filter 二分，找出「加上哪个用例就会红」的那一个，两者之间共享的状态就是嫌疑。

    --gtest_shuffle 该常开，是因为它不花时间，却是把这类隐藏耦合逼出来的唯一手段——固定顺序下这种耦合可以潜伏几年，直到某天有人加了一个新用例。同理，ctest -j 也不只是加速：不能并行的单元套件，往往是因为有全局状态，而不是「本来就不能并行」。

8.3 高级（体现深度）

  1. 高级一次不改变任何对外行为的重构让 40 个测试变红，这说明什么？

    说明测试的问题，不是重构的问题。判据很干净：如果对外可观察行为没变，那么任何变红的断言，断言的都是实现细节。

    最常见的成因是过度 mock：EXPECT_CALL(repo, save(_)).Times(3) 把「调了三次 save」写成了合同，于是把三次 save 合并成一次 saveAll() 就全红了。次常见的是测私有函数、以及给整个测试套 InSequence（顺序在绝大多数场景并不是需求的一部分）。

    过度 mock 还有两个更隐蔽的代价：它让测试失去发现真实集成问题的能力——依赖全是 mock 时，参数单位、空值语义、错误码含义这类契约误解永远测不出来，因为 mock 就是按你的误解写的；以及它让测试变成实现的一份复印件，重构成本翻倍，最终团队会选择不重构。

    修法是把交互断言换成状态断言：用 fake 跑完整流程，断言最终状态（EXPECT_THAT(repo.all(), UnorderedElementsAreArray(...))）。真的需要断言顺序时，用 After() 或局部 Sequence 只约束那两个确有依赖的调用。

  2. 高级团队定了「覆盖率必须 ≥ 80% 才能合入」，会发生什么？你会怎么设门槛？

    会得到一批无断言测试：把所有公开方法调一遍，不写断言或只写 EXPECT_NO_THROW。行覆盖漂亮地涨上去，而这些测试唯一能发现的缺陷是崩溃。更糟的是它们永远不会红，于是制造出「这块有覆盖」的错觉，真实缺陷反而更难被注意到。这是古德哈特定律的标准案例：指标一旦成为目标就不再是好的度量。根源在于覆盖率度量「执行到了」，我们想要的是「验证过了」，两者之间没有任何机制保证关联。

    我会改成两条：增量门槛——新增/改动代码的分支覆盖不低于某个值（防止新债，可自动化，且把测试代码和三方库从统计里排除，否则测试代码自身接近 100% 会系统性虚高总数）；清单评审——核心模块的未覆盖分支要逐条有说法。答案通常落在三类：真实但没测的场景（补用例）、实际不可达（删或标注）、难构造的条件如 malloc 失败 / EINTR（注入可失败的包装，或明确承认不测）。这三类答案都是产出，而总百分比不是。

    真正能防住无断言测试的是变异测试：改动生产代码（< 改 <=、返回值改常量），看有没有测试变红。C++ 工具链还不成熟，但思路可以手动用在代码评审里：「如果我把这个函数的返回值改成固定值，哪个测试会红？」 答不出来，那些测试就没在测什么。

  3. 高级设计一套 CI 分层：哪些每次提交跑、哪些 nightly 跑？sanitizer 慢 5–15 倍怎么安排？

    先定约束：「每次都跑」那一档的预算必须钉死在 10 分钟以内。超过这个数，开发者就会开始绕过它（本地 --no-verify、只看第一个失败、合了再说），于是分层再完美也不生效。其余测试按「发现缺陷的概率 ÷ 耗时」往后排。

    五档：本地 pre-commit（< 30 s）格式 + 编译期测试 + 受影响单测；PR 每次推送（≤ 10 min）全量单测 Debug 与 Release 双构建 + 组件测试 + ASan/UBSan + 增量覆盖率 + --gtest_shuffle；合入主干（≤ 30 min）集成测试 + 三编译器矩阵 + 全量覆盖率报告；nightly TSan / MSan 全量 + 端到端 + 性能基线 + fuzz + 套件重跑 20 遍抓 flaky；weekly 长时 fuzz / soak + 全平台全标准矩阵 + MC/DC。

    几个具体判断：ASan + UBSan 放 PR 档，因为 2–3 倍还在预算内、发现的又是最常见一类缺陷；TSan 的 5–15 倍放不进十分钟，而且 data race 通常不是「这次改动刚引入」，nightly 的延迟可接受。Release 构建必须在 PR 档——很多 UB 只在 -O2 下才改变行为。性能基线放 nightly，因为共享 CI 机器上的性能噪声会制造 flaky。

    最后一条常被忽略：越靠右的档位越需要明确负责人。nightly 天然没人盯，连红三天没人管就永久失去信号意义——失败要自动创建带 owner 的工单，而不是发邮件。

  4. 高级属性测试适合什么、不适合什么？和 fuzz、例子化用例怎么分工？

    属性测试写的是「对所有合法输入都成立的性质」，由框架生成随机输入去反驳，并把反例收缩（shrink）成最小形态——这是它相比手写随机测试的核心价值：报给你的是「{0, -1} 就能让排序出错」，而不是一个 4KB 的随机数组，排查成本差一个量级。

    适合的形态都能写出一条性质：可逆运算（decode(encode(x)) == x：序列化、压缩、协议编解码、base64）；参考实现对拍（SIMD 版 vs 朴素版、无锁容器 vs 加锁版）；不变量（随机生成操作序列，每步后调 check_invariants()——红黑树、跳表、分配器、状态机）；代数性质（幂等、交换、结合、单调；比较器的严格弱序尤其值得测，它是 std::sort 的前提，违反了是 UB）；元变形关系（「多加一条订单总额只增不减」）。

    不适合的是写不出性质的地方——「VIP 满 300 减 50」这类业务规则硬套属性测试，只会得到一个把规则抄两遍的测试，正是「测试锁死实现」的变体。

    三者的分工可以按判据强度排：例子化用例的判据最强（精确期望值）但输入最少；属性测试判据是一条性质，输入由框架生成；fuzz 判据最弱（只有「不该崩」），但输入覆盖最广。判据强度递减、覆盖能力递增，所以不互相替代。两个连接点：fuzz 或属性测试找到的每个反例都要沉淀成固定的例子化用例，否则下次随机撞不到就没有回归保护；以及属性测试和 sanitizer 是乘法关系——把属性测试放进 ASan 轮次，比在 Debug 轮次里跑十倍组数更有价值。
