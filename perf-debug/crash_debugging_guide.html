01

Crash 信号分类

信号产生的内核流程示意 · 哪些信号会产生 core dump?

本文讲的是用户态进程崩溃：有信号、有 core dump、有 GDB，可以事后慢慢看。如果挂掉的是内核本身——整机失联、自动重启、dmesg 里只留下一段 Oops——那是另一套完全不同的取证方法（kdump 保住现场、crash 工具读 vmcore、从 RIP 偏移定位源码行、KASAN 与 slab poison 的读法），见 内核崩溃分析。判据很简单：进程没了但机器还在 → 看本文；机器没了 → 看那一篇。

进程异常退出几乎都是内核或运行时把一次 signal 投递给了某个线程。认信号比立刻开 gdb 更重要：同步信号（SEGV/BUS/ILL/FPE/ABRT）贴在肇事线程上；KILL/TERM 是别人要你死。

日志关键字先分流：Abort signal received 多半是外部 kill / 资源耗尽，不是这段代码自己踩内存；Shutdown in progress 是关机副作用，往上找真正的复位；多域二进制用 c++filt 分诊即可，不必先下 NotStripped 包。详见第九章。
信号典型场景判据core
SIGSEGV 11空指针、野指针、写只读、栈溢到 guard pagesi_addr 近 0 或越界；dmesg error bit0=页不存在会
SIGBUS 7mmap 文件被 truncate、ARM 未对齐、磁盘满的 mmapVMA 在，物理页给不出会
SIGABRT 6assert / terminate / glibc 堆检测栈顶在 abort / __libc_message会
SIGILL 4函数指针坏、ret 到数据段、老 CPU 跑 AVXx/i $rip 不是合法指令会
SIGFPE 8整数除 0、INT_MIN/-1默认浮点不发信号，除非 feenableexcept会
SIGPIPE 13对端 RST 后还 write长连接常见；默认退出不留 core否
SIGKILL 9OOM / kill -9 / cgroup无 core；查 dmesg oom-killer否
SIGTERM 15systemd / 正常停机通常不算 crash否

还会写 core：QUIT / SYS / TRAP / XCPU / XFSZ。同步信号是线程局部的——多线程 core 必须 thread apply all bt，主线程停在 abort 往往只是收尸。

2.4 Core 文件格式 (ELF NOTE)

core 是 ET_CORE：PT_NOTE 是元数据，PT_LOAD 是按 coredump_filter 裁过的内存。gdb 读栈靠 NOTE 里的寄存器 + LOAD 里的栈页。

段 / 笔记里面有什么排障时看它
NT_PRSTATUS通用寄存器 + 信号info registers 的来源
NT_SIGINFOsiginfo_tsi_addr = 出错地址
NT_FILEmmap 文件表对上 so 路径与 build-id
NT_PRPSINFO / AUXV / FPREGSET进程名、辅助向量、浮点寄存器确认 exe / argv
PT_LOAD每线程栈、堆、匿名 mmap；.text 常被裁缺代码段时用磁盘上的二进制补
filter 位含义判据
0x33 默认匿名私有+共享 + ELF header + 巨页私有cat /proc/self/coredump_filter
0xFF连共享文件映射都写体积爆炸，生产禁止
验证file core / readelf -n / readelf -l能看到 ET_CORE 与 NOTE

2.5 生产环境 core dump 收集策略

  • 命名带 %e.%p.%t.%h；debug 副本按 build-id 索引（见 §3 / §5.4）。
  • 容器：pattern 在宿主机生效，容器内仍要 LimitCORE。

3.4 调试 -O2 优化代码的技巧

-O2 会把局部变量优化进寄存器或直接消掉，gdb 打 <optimized out>。按 System V ABI 看前六个参数寄存器；内联和尾调用会让行号跳，用 disas /m 对照。生产建议 -O2 -g -fno-omit-frame-pointer，strip 只剥发布副本，debug 按 build-id 另存。

根因 → 信号速查表 · 空指针 / 野指针 SIGSEGV · Use-After-Free / Double Free SIGSEGV SIGABRT · Buffer Overflow SIGSEGV SIGABR…

空指针 / 野指针 · Stack Overflow · 未处理异常 / std::te…

崩在 malloc 里几乎从来不是 malloc 的 bug——更早的溢写已经把 chunk 头毁掉了，这次分配只是引爆点。

根因信号现场判据
空 / 野指针SEGVthis=0x0 或 si_addr 近 0
UAFSEGV 或沉默ASan 给出 alloc / free / use 三栈
double-freeABRTstderr：double free or corruption
buffer overflowSEGV / ABRTcanary → __stack_chk_fail；堆元数据坏 → 下次 malloc

4.1 空指针 / 野指针 SIGSEGV

写法下场判据 / 修法
入口裸指针不判this=0 或 si_addr 近 0API 边界判空；内部能用引用就别用指针
ctx.get() 后 reset() 还用 raw野指针，崩点可远离释放点不要把 raw 活得比所有者长
构造时判了 session当时不崩 ≠ 之后 session_ 仍有效每次使用边界保证生命周期，或持有 shared/weak

4.2 Use-After-Free / Double Free SIGSEGV SIGABRT

最短复现：同一块堆先 UAF 写、再二次释放。ASan 会在第一处就停；没插桩时 glibc 常在第二次 delete 才 abort。

struct Foo { int x; };
int main() {
    Foo* p = new Foo{1};
    Foo* q = p;
    delete p;     // 堆块进 tcache
    q->x = 2;     // UAF 写：可能静默
    delete q;     // double-free → SIGABRT
}

UAF 写常常不立刻崩：块还在 tcache 里，地址仍可写。二次释放时 glibc 发现 fd/key 对不上才 abort。所以 ABRT 现场的栈顶是检测器，真正的释放点在更早那条 free 栈上——这正是 ASan 三条栈要一起看的原因。

形态典型写法判据修法
异步 UAF线程池 [&w] 捕获局部对象ASan：use 栈 vs free 栈shared_ptr / shared_from_this 捕获
双计数两个 shared_ptr<T>(raw)double free or corruption只 make_shared 一次，其余拷贝

glibc 在 free 时查 prev_inuse / fastbin fd / tcache key，不对就 __libc_message → abort。栈顶这条链是检测器，不是根因。

4.3 Buffer Overflow SIGSEGV SIGABRT

形态坏法当场 / 延后修法
栈strcpy 不限长盖返回地址 → SEGV；开 canary → __stack_chk_fail ABRTstring_view + 有界拷贝；-fstack-protector-strong -D_FORTIFY_SOURCE=2
堆off-by-one 写 chunk 头下次 malloc/free 才 ABRTvector / 先 size 后写

4.4 Data Race (并发竞争) SIGSEGV SIGABRT SIGBUS

信号不固定：破坏的是指针就 SEGV，破坏的是堆元数据就 ABRT，ARM 未对齐就 BUS。TSan 看 happens-before，不要用崩点当根因。

写法后果修法
无锁 ++n_撕寄存器、偶发错值或崩atomic 或把计数放进已有锁
改 running_ 不持锁就 notifylost wakeup持锁改谓词，解锁后再 notify
外层 RPC 锁套内层数据锁内层若在内核阻塞，stop() 拿不到外层 → 死锁分层：外层只串行化语义，阻塞前必须放下内层

4.5 Stack Overflow SIGSEGV

无终止递归、8MB 栈上的 10MB 数组、lambda 按值拷大容器。core 里：si_addr 贴 rsp、栈极深且函数名重复、info proc mappings 顶到 PROT_NONE guard。

4.6 未处理异常 / std::terminate SIGABRT

触发修法
析构里抛、栈展开再抛析构 noexcept，内部 catch 只打日志
线程函数未捕获线程入口 try/catch；否则 join 路径 terminate
noexcept 函数真抛了不展开、析构也不跑，直接 abort
构造/析构中调纯虚vtable 还是基类；__cxa_pure_virtual

生产可 set_terminate 打当前异常后 abort 留 core，不要静默吞。

5.1 AddressSanitizer (ASan)

编译插桩 + shadow：每 8 字节应用内存对应 1 字节影子。CI 必开（约 2–3×）；ASan / TSan / MSan 不能同时编。生产关掉。

    #0 ... in main uaf.cpp:7

    #0 ... operator delete
previously allocated by thread T0 here:        ← 谁分配
    #0 ... operator new
Shadow bytes: fa fa [fd] fd fa fa              ← fd = freed poison

5.2 ThreadSanitizer (TSan)

动态 happens-before：同一地址上两个线程冲突访问，且中间没有同步。报告给读栈和写栈各一份，并列出缺失的锁或 atomic。只修其中一处，另一边下次还会报。开销 5–15×，与 ASan 互斥，多线程模块单独编一份。

防御性编程实践

6.1 RAII 一切资源

内存、fd、锁、定时器都绑到对象析构。C 句柄用 unique_ptr + deleter。自定义 guard：拷贝删除，移动把源置空（exchange(fd, -1)），析构 noexcept。

6.2 智能指针策略

场景选择说明
独占unique_ptr默认；零开销
真共享shared_ptr原子计数；同一 raw 只能 make 一次
观察weak_ptr破环
异步 thisshared_from_this必须先被 shared_ptr 管着
同一个 raw 不能既给 unique 又给 shared，更不能给两个独立 shared。

6.3 断言与 Contract

工具何时死判据
assert仅调试；-DNDEBUG 蒸发不变量，不是错误处理
自写 CHECK / abort发布也死，留 core违反前置条件比带着脏数据跑更可查

6.4 Defensive nullptr Check 的边界

API 边界必须判；内部能引用就引用。shared_ptr 也能存空，仍要在解引用前想清楚。不变量用类型（GSL not_null）表达，比注释可靠。

6.5 线程安全设计模式

模式要点
线程封闭 / 不可变无共享就不锁
scoped_lock一次锁多个，内部 std::lock 防死锁
cv + 谓词持锁改标志；wait 带 lambda 防虚假唤醒
分层锁外层语义、内层数据；阻塞前放下内层

面试高频问题与解答

信号辨析 · core 取证 · 多线程定位肇事线程 · 偶发 crash 的系统化排查

点击每道题展开参考答案（建议先自己复述一遍，再对照）。

  1. 基础SIGSEGV 和 SIGBUS 有什么区别？

    SIGSEGV：访问的虚拟地址没有合法的 VMA 映射，或访问权限不符（如写只读段）。最常见就是空指针/野指针解引用。

    SIGBUS：虚拟地址有合法 VMA，但物理上无法满足。典型场景：
      1) mmap 文件后文件被 truncate，再访问超出文件长度的页面；
      2) 在 ARM/SPARC 等严格对齐架构上未对齐访问 (load 一个未 4 字节对齐的 int)；
      3) 写入磁盘已满的 mmap。

  2. 基础Core dump 文件里有哪些关键信息？为什么有时调试看到 ?? ??

    Core 文件是 ELF Core 类型，包含 PT_NOTE（NT_PRSTATUS 寄存器、NT_PRPSINFO 进程信息、NT_SIGINFO 出错地址、NT_FILE mmap 表、NT_AUXV 辅助向量、NT_FPREGSET 浮点寄存器）和 PT_LOAD（按 coredump_filter 选择的内存段：栈、堆、数据、可选的代码段）。

    看到 ?? ?? 通常因为：
      1) 二进制 / .so 不带调试符号（被 strip）；
      2) build-id 不匹配；
      3) 栈被破坏，回溯失败（bt 找不到 frame）；
      4) JIT / 动态生成代码（如 V8、JVM）。

  3. 中级怎么区分 "double free" 和 "use-after-free"？

    都触发 SIGABRT，但报错文案不同：

    • double free：glibc 报 double free or corruption，在 free() 检查 fastbin/tcache 链表时发现刚刚释放过的 chunk。
    • use-after-free：glibc 不一定报错；表现为 SIGSEGV（地址被 unmap）、随机崩溃、数据错乱。要靠 ASan / Valgrind 才能精确定位。

    定位首选 ASan：-fsanitize=address，会同时给出"分配栈 / 释放栈 / 访问栈"三条调用栈。

  4. 中级在多线程程序里 GDB 看到 main 线程在 abort，怎么找真正的肇事线程？

    步骤：

    1. info threads 列所有线程
    2. thread apply all bt 拿到所有线程栈快照
    3. 在所有栈里搜：__cxa_throw、std::terminate、__assert_fail、__stack_chk_fail、raise、__libc_message、应用层 panic 函数
    4. 找到栈顶位于这些"陷阱函数"的线程，那就是肇事者
    5. 切过去 thread N，沿 frame 向上看业务代码

    注意：很多场景肇事线程触发同步信号后异步通知了主线程 / signal handler 线程，主线程上看到的 abort 不是真正的源头。

  5. 中级std::shared_ptr 是线程安全的吗？

    分两层：

    • 控制块（引用计数）：线程安全。多个线程对不同 shared_ptr 实例但指向同一对象的拷贝/赋值/析构是安全的。
    • 同一个 shared_ptr 实例：不是线程安全。两个线程同时对同一个对象 reset/赋值，需要外部同步，或者使用 std::atomic<std::shared_ptr<T>> (C++20) / std::atomic_load/store (旧)。
    • 指向的对象：和普通对象一样，需要业务自己保证线程安全。
  6. 中级noexcept 的真正含义是什么？写错有什么后果？

    noexcept 是承诺该函数不会抛异常。如果违反：

    • 编译器可生成更优代码（不需要异常清理路径，move 操作可被容器优先选择）
    • 真抛了：直接调用 std::terminate → SIGABRT，不进行栈展开，析构函数也不跑

    典型规则：

    • 析构函数默认 noexcept(true)，绝不要在析构里抛
    • 移动构造 / 移动赋值标 noexcept（否则 vector 扩容时会退化为 copy）
    • swap / 简单 getter 标 noexcept
  7. 高级Stack Overflow 在 Linux 上是怎么被检测到的？

    Linux 在每个线程栈的最低端放一个或多个 guard page（PROT_NONE）。当栈增长触到这页：

    1. CPU 触发 page fault
    2. 内核 do_page_fault 检查 VMA 是 PROT_NONE
    3. 对栈段还会判断 expand_stack 是否能扩展；若已到上限则发 SIGSEGV

    编译器加 -fstack-protector-strong 后，函数 prologue 在栈上放 canary，epilogue 检查；被破坏则调用 __stack_chk_fail → SIGABRT。

    线程栈大小通过 pthread_attr_setstacksize 或 ulimit -s 调整。

  8. 中级什么时候应该用 std::atomic 而不是 mutex？
    • 单一标志位 / 计数器：用 atomic（如 running_、refcount）
    • 读多写少 / 单生产单消费：atomic 配合正确的 memory_order，无锁队列
    • 多字段需要保持一致：必须用 mutex，原子操作只能是单一变量
    • 需要等待事件：condition_variable + mutex；atomic 配 wait() (C++20) 也可以

    误区：以为 atomic 一定比 mutex 快。实际上：高竞争下 mutex 让线程睡眠节省 CPU；atomic 自旋反而浪费。 总线锁 (LOCK 前缀) 也不便宜，约 10-100ns。

  9. 中级condition_variable 的 spurious wakeup 怎么处理？

    POSIX 允许 pthread_cond_wait 在没有 notify 时也唤醒。所以必须在 while 循环中检查谓词：

    std::unique_lock lk(m);
cv.wait(lk, [&]{ return ready; });   // 等价 while (!ready) cv.wait(lk);

    另一个常见 bug：notify 之前没在持锁状态下修改谓词，导致 notify 在 wait 之前发生（lost wakeup）。正确做法：

    {
    std::lock_guard lk(m);
    ready = true;          // 持锁修改
}
cv.notify_one();           // 释放锁后通知（可优化等待者唤醒后立刻拿锁）
  10. 高级生产环境进程偶发 crash，如何系统化排查？
    1. 取证：保存 core 文件 + 二进制 + 所有 .so + dmesg + journalctl + 业务日志（同一时间窗）
    2. 初判：file core、readelf -n core | grep PRSTATUS 看信号；dmesg 看 segfault 行
    3. 定栈：gdb + thread apply all bt；用 build-id 对齐符号；区分崩溃线程
    4. 分类：根据信号 + 栈顶函数划归 4.x 节中的某一类（空指针 / UAF / 越界 / race / 栈溢 / 异常）
    5. 复现：在测试机用 ASan/TSan 重新编译；输入回放 / fuzz / 压测
    6. 修复：明确根因后改代码；写回归用例
    7. 加固：在该路径加 contract 检查、metric、超时；添加 sanitizer CI；把 core_pattern + ulimit 检查加进部署 healthcheck
