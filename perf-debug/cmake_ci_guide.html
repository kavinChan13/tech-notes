L6 Engineering · CMake · Modern CI/CD

现代 CMake + 包管理 + CI 完全指南

target-based 哲学 · vcpkg / conan · clang-tidy/sanitizer 集成 · GitHub Actions 模板

核心难度: ★★★ 工程必备 阅读时长: ~15 min 前置: cpp_compilation_guide
01

引言

陷阱 · 包管理 · sanitizer · CI

为什么 CMake 仍是 C++ 工程首选
还没建立「CMake 是元构建系统、两阶段构建、target 是什么」的心智模型时，先读 CMake 是什么。本文从现代写法、包管理与 CI 模板往下走。

CMake 仍是首选，因为它是生成器：一份 CMakeLists.txt 产出 Ninja / VS / Xcode，再交给真正的编译器。跨平台、IDE、vcpkg/conan 都吃这一套。两阶段细节见 cmake_modern；下面只钉一句：configure 不编译，build 才编译。

02

现代 CMake 哲学 vs 老式

target 一等公民 · 禁全局变量 · 3.20 基线

五大原则

2.1 老式 CMake (CMake 2.x 时代)

目录级命令是全局开关：include_directories / add_definitions / link_directories / 拼接 CMAKE_CXX_FLAGS。一个 add_subdirectory 就能改整个树的 include 与宏，子项目互相踩。

2.2 现代 CMake (3.5+ 起，3.15+ 推荐)

属性挂在 target 上：target_include_directories / target_link_libraries / target_compile_options。传递性用 PUBLIC / PRIVATE / INTERFACE 钉死。好例见 §3 那份最小 Lists。

2.3 现代 CMake 五大原则

原则含义
Treat CMake as code当代码写，不当 ini 拼
Targets are everything设置挂 target，禁全局变量
PUBLIC / PRIVATE / INTERFACE传递性显式，避免泄漏
target_xxx 替代 add_xxxinclude_directories 等已过时
3.20 基线Presets + FetchContent 才齐

2.4 推荐版本要求

团队统一 cmake_minimum_required(VERSION 3.20)。3.15 才算现代 CMake 真正可用；3.20 起 Presets / FetchContent 行为稳定。C++ 标准用 target_compile_features(... PUBLIC cxx_std_20)，少拼 CMAKE_CXX_FLAGS。

03

CMakeLists 基础结构

最小 target-based 写法 · 目录约定

库 + 可执行文件

3.1 最简单的可执行文件

单文件 add_executable(hello main.cpp) 见 cmake_modern。工程起点永远是「库 + 可执行文件」，不要从 hello 再抄第二份 Lists。

3.2 库 + 可执行文件

这是本页唯一一份完整 Lists：PUBLIC 头给消费者，PRIVATE 实现细节，链接同样拆开。别名让 FetchContent 与 find_package 用户写同一句。

cmake_minimum_required(VERSION 3.20)
project(myapp LANGUAGES CXX VERSION 1.0)

add_library(mylib STATIC src/foo.cpp src/bar.cpp)
add_library(mylib::mylib ALIAS mylib)

target_compile_features(mylib PUBLIC cxx_std_20)
target_include_directories(mylib
    PUBLIC  ${CMAKE_CURRENT_SOURCE_DIR}/include
    PRIVATE ${CMAKE_CURRENT_SOURCE_DIR}/src
)
target_link_libraries(mylib
    PUBLIC  fmt::fmt          # 头文件暴露类型
    PRIVATE spdlog::spdlog    # 仅 .cpp 用
)

add_executable(myapp src/main.cpp)
target_link_libraries(myapp PRIVATE mylib::mylib)

3.3 推荐目录结构

路径放什么
CMakeLists.txt / CMakePresets.json顶层 + 预设
include/<proj>/公开头（PUBLIC）
src/实现 + 内部头（PRIVATE）
cmake/Sanitizers / Warnings module
tests/ · .github/workflows/CTest · CI

3.4 顶层选项

顶层只留 option 与 add_subdirectory，不要再贴一份 80 行模板。常用开关：BUILD_TESTS / ENABLE_ASAN / ENABLE_TSAN / ENABLE_COVERAGE。单配置生成器才设 CMAKE_BUILD_TYPE；多配置（VS）走 generator expression。

04

Targets

七种 target · INTERFACE / ALIAS / OBJECT

一切以 target 为中心

4.1 三种 target 类型

类型命令用途
可执行文件add_executable(name srcs...)程序入口
静态库add_library(name STATIC srcs...)编译时链接
动态库add_library(name SHARED srcs...)运行时加载
对象库add_library(name OBJECT srcs...)不打包，仅 .o 集合（共享中间产物）
接口库add_library(name INTERFACE)纯头文件库 / 仅传递设置
导入库add_library(name STATIC IMPORTED)引用预编译的库
别名add_library(ns::name ALIAS name)命名空间风格

4.2 INTERFACE 库 — 纯头文件库

没有 .cpp，只传递 include / 特性 / 宏。属性必须写 INTERFACE（没有 PRIVATE 可挂）。消费者 target_link_libraries(app PRIVATE header_only) 即继承。

4.3 别名 target — 命名空间风格

对外一律 add_library(mylib::mylib ALIAS mylib)。FetchContent 换成 find_package 时用户代码不用改；链接错误也是 mylib::mylib 一眼能搜。

4.4 OBJECT 库 — 共享中间产物

同一份 .cpp 要打进 STATIC 和 SHARED 时用 OBJECT，再用 $<TARGET_OBJECTS:core> 拼，避免编两遍。OBJECT 本身不进 install。

05

PUBLIC / PRIVATE / INTERFACE 传递性

自用 × 暴露 · 头文件同样规则

三个关键字 · 决策法则

现代 CMake 的核心：属性挂在 target 上之后，传不传给下游由这三个关键字决定。

5.1 三个关键字的含义

关键字本 target 用下游用
PRIVATE是否
INTERFACE否是
PUBLIC是是

5.2 决策法则（Daniel Pfeifer 的经典口诀）

对属性 X 只问两句：① 我的 .cpp 需要吗？② 我的头文件暴露了吗？

自用头文件暴露用
是否PRIVATE
否是INTERFACE
是是PUBLIC

5.3 实例分析

target_link_libraries(mylib
    PRIVATE spdlog::spdlog    # .cpp 用，头文件不暴露
    PUBLIC  fmt::fmt          # mylib.h 里出现 fmt 类型
)
add_library(json_helper INTERFACE)
target_link_libraries(json_helper INTERFACE nlohmann_json::nlohmann_json)

5.4 头文件路径同样规则

include/ → PUBLIC；src/ 内部头 → PRIVATE。安装后路径用 $<BUILD_INTERFACE:...> / $<INSTALL_INTERFACE:include>，见 §9 图。

5.5 编译选项 / 定义同样规则

警告 -Wall、内部宏 → PRIVATE。头文件依赖的宏、符号可见性（-fvisibility=hidden）→ PUBLIC。别把 sanitizer 旗标只打在测试 target 上，见 §15。

06

头文件 / 编译选项 / 链接

API 对照 · 警告封装

target API

6.1 头文件路径

target_include_directories：公开 API 用 PUBLIC，内部头 PRIVATE。第三方头加 SYSTEM 压警告。安装路径拆 BUILD/INSTALL 见 §9。

6.2 编译特性

用 target_compile_features(mylib PUBLIC cxx_std_20) 替代手写 -std=c++20，跨 gcc/clang/MSVC 才一致。

6.3 编译选项

警告、sanitizer 一律 target_compile_options(... PRIVATE ...)。全局 CMAKE_CXX_FLAGS 拼接是 §2 的反面教材。

6.4 编译器警告 module 化

写成 set_project_warnings(target)：MSVC /W4 /permissive-，Clang/GCC -Wall -Wextra -Wpedantic。每个 target 调一次，别复制 40 行 flags。

6.5 链接库

只链 imported target：fmt::fmt、Threads::Threads。禁止 link_directories + 裸库名。

6.6 链接选项

裁死代码用 target_link_options(... PRIVATE -Wl,--gc-sections)（MSVC 对应 /OPT:REF）。和编译选项一样挂 target，不挂目录。

07

子目录 · FetchContent · ExternalProject

何时 FetchContent / find_package / vcpkg

选型决策

7.1 add_subdirectory — 同仓库子模块

本仓的 src/、tests/ 用它。vendoring 进 third_party/ 也走这条。依赖会进你的构建图，选项名容易撞车。

7.2 FetchContent — 在线拉取并构建

钉 GIT_TAG + GIT_SHALLOW，FetchContent_MakeAvailable 之后当子目录用。适合小库、测试框架。干净构建每次拉源码并编译，版本冲突要自己扛。

7.3 ExternalProject — 高级版本控制

单独一套 build pipeline，不进本工程 DAG。FetchContent 能覆盖的场景不要用它。

08

find_package

Config vs Module · 标准 target 名

系统库查找

8.1 基本用法

find_package(fmt 10.0 REQUIRED) 然后链 fmt::fmt。永远链 imported target，不要链变量里的 ${FMT_LIBRARIES}。

8.2 两种模式

模式查找文件谁提供
ConfigXXXConfig.cmake库自己（现代默认先搜这个）
ModuleFindXXX.cmakeCMake 自带或你写

8.3 PkgConfig 兜底

没有 Config 也没有 Find 模块时：pkg_check_modules(... IMPORTED_TARGET)，链 PkgConfig::NAME。

8.4 常用库的标准 target 名

库target
fmt / spdlog / nlohmann_jsonfmt::fmt · spdlog::spdlog · nlohmann_json::nlohmann_json
Boost / OpenSSL / Protobuf / gRPCBoost::filesystem · OpenSSL::SSL · protobuf::libprotobuf · gRPC::grpc++
GTest / benchmark / Threads / OpenMPGTest::gtest · benchmark::benchmark · Threads::Threads · OpenMP::OpenMP_CXX
09

install / export

本树 vs 安装树 · find_dependency

本树 vs 安装树

给别人用的库必须能 find_package(mylib)。缺 export 时，别人只能拷你的源码当子目录。

9.1 完整流程

步骤做什么
include 拆路径BUILD_INTERFACE / INSTALL_INTERFACE
install(TARGETS … EXPORT)产出 mylibTargets.cmake，带 NAMESPACE mylib::
Config + Version 文件configure_package_config_file + write_basic_package_version_file

9.2 mylibConfig.cmake.in

@PACKAGE_INIT@ 之后对每个 PUBLIC 依赖 find_dependency(fmt)，再 include(...Targets.cmake)。漏 find_dependency，下游 configure 直接找不到 fmt::fmt。

9.3 用户使用

装完之后就是 find_package(mylib 1.0 REQUIRED) + target_link_libraries(app PRIVATE mylib::mylib)。用户代码应与 FetchContent 时同一句。

10

测试

CTest · GTest / Catch2 · coverage

CTest + GoogleTest

10.1 启用 CTest

顶层 include(CTest)（含 enable_testing()）。没这行，ctest 是空的。

10.2 GoogleTest 集成

FetchContent 拉 GTest，测例链 GTest::gtest_main，用 gtest_discover_tests 注册——比手写 add_test 少漏用例。测例必须和库同一套 sanitizer 旗标，见 §15。

10.3 跑测试

ctest --test-dir build --output-on-failure -j。过滤 -R，失败重跑 --rerun-failed。CI 里用 test preset，见 §16 / §17。

10.4 集成 Catch2

链 Catch2::Catch2WithMain + catch_discover_tests。和 GTest 二选一，不要两个框架并存。

10.5 Coverage 集成

--coverage -O0 -g 打在被测库和测例上，再 lcov / llvm-cov。只给测例加 coverage、库是 Release，覆盖率是假的。

11

vcpkg 包管理

manifest · toolchain · 二进制缓存

manifest 模式

CMake 集成最顺：Lists 里仍是 find_package，toolchain 交给 preset。

11.1 安装 vcpkg

clone + bootstrap-vcpkg，导出 VCPKG_ROOT。CI 用 lukka/run-vcpkg 钉 commit，不要每次拉最新。

11.2 manifest 模式（推荐）

{
  "name": "myproject",
  "version": "1.0.0",
  "dependencies": [
    "fmt",
    "spdlog",
    { "name": "protobuf", "features": ["zlib"] }
  ]
}

11.3 与 CMake 集成

preset 设 toolchainFile 后，Lists 里 find_package(fmt CONFIG REQUIRED) 即可。不要每人记一条超长 -DCMAKE_TOOLCHAIN_FILE=。

11.4 优劣

库多、集成顺；默认源码构建偏慢，靠 binary cache 补。版本锁定不如 conan 细，但纯 CMake 项目够用。

12

conan 包管理

预编译包 · 与 vcpkg 对照

vcpkg vs conan

亮点是预编译 binary。Lists 侧同样 find_package，toolchain 来自 conan install 生成的 conan_toolchain.cmake。

12.1 安装与配置

pip install conan 后 conan profile detect。profile 决定 compiler / libcxx / build_type，和 sanitizer 一样：库和测例必须同一 profile。

12.2 conanfile.txt

[requires] 钉版本，[generators] CMakeDeps CMakeToolchain。复杂选项再升 conanfile.py，简单项目不必。

12.3 安装 + 集成

conan install . --output-folder=build --build=missing，再 cmake -DCMAKE_TOOLCHAIN_FILE=build/conan_toolchain.cmake。把这条写进 preset，不要散落 wiki。

12.4 vcpkg vs conan

维度vcpkgconan
主导MicrosoftJFrog
产物默认源码编译 + binary cache预编译包更成熟
CMaketoolchain 一行同样 toolchain
私有仓有Artifactory 更顺
怎么选纯 CMake 团队多构建系统 / 内部包多
13

ccache

命中路径 · CI 缓存键

编译加速

把 CMAKE_CXX_COMPILER_LAUNCHER 设成 ccache。跨机命中靠 hash_dir = false + 同一编译器/旗标。

13.1 安装与启用

find_program(CCACHE ccache) 后设 launcher。包管理器装即可，不要手拷二进制。

13.2 配置

max_size 给足（10G 起）；sloppiness 含 pch_defines,time_macros。PCH / sanitizer 旗标变了，hash 必变，这是特性不是 bug。

13.3 CI 缓存

缓存 ~/.ccache，key 带 os + compiler + preset，restore-keys 前缀回退。具体 YAML 见 §17，不要再复制一份。

13.4 效果

14

clang-tidy / clang-format / cppcheck

PR 门禁 · compile_commands

静态分析组合

14.1 clang-format

根目录一份 .clang-format。CI 只跑 clang-format --dry-run --Werror，不要在 CI 里 -i 改文件。

14.2 clang-tidy

根目录 .clang-tidy 开 bugprone-* / modernize-*，关掉噪声项。需要 CMAKE_EXPORT_COMPILE_COMMANDS=ON（preset 里开）。

14.3 CMake 集成

CXX_CLANG_TIDY 挂 target 后每次编译都跑，本地会痛。默认关，CI 的 static-analysis job 单独开 ENABLE_CLANG_TIDY。

14.4 cppcheck

互补、可选。CMAKE_CXX_CPPCHECK 同样只在 CI 打开。

14.5 推荐组合

工具定位必要性
clang-format格式PR 必需
-Wall -Wextra编译期第一道必需
clang-tidy现代化 + bugCI 推荐
ASan / UBSan / TSan运行时必需，见 §15
cppcheck互补可选
15

Sanitizer + Coverage 在 CMake 中的集成

同一旗标编库和测 · TSan 不能混 ASan

库和测例同一选项

15.1 Sanitizers.cmake

一个 enable_sanitizers(target)：按 ENABLE_ASAN / UBSAN / TSAN 往该 target 打 -fsanitize= + 对应 target_link_options。TSan 与 ASan/MSan 互斥，CMake 里直接 FATAL_ERROR。机制细节见 Sanitizer 工具。

option编译 + 链接注意
ENABLE_ASAN-fsanitize=address可与 UBSan 组合
ENABLE_UBSAN-fsanitize=undefined建议和 ASan 一起
ENABLE_TSAN-fsanitize=thread单独 job，禁止混 ASan

15.2 Coverage.cmake

-O0 -g --coverage 打在被测库 + 测例。不要和 Release / 高优化混用。

15.3 在 CI 中使用

cmake --preset asan 然后 ctest --preset asan。环境变量放在 workflow 里，见 §17。

16

CMakePresets.json 与 IDE 集成

generator · cacheVariables · inherits

声明式配置

把 generator、toolchain、sanitizer 开关写进 JSON。本地、IDE、CI 都 cmake --preset asan。个人差异放 CMakeUserPresets.json（gitignore）。

{
  "version": 6,
  "configurePresets": [
    {
      "name": "asan",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/${presetName}",
      "toolchainFile": "$env{VCPKG_ROOT}/scripts/buildsystems/vcpkg.cmake",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "ENABLE_ASAN": "ON",
        "ENABLE_UBSAN": "ON",
        "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"
      }
    }
  ],
  "buildPresets": [{ "name": "asan", "configurePreset": "asan" }],
  "testPresets": [{ "name": "asan", "configurePreset": "asan" }]
}
17

CI · GitHub Actions 完整模板

compiler × sanitizer × os · ccache

推荐 CI 矩阵
# .github/workflows/ci.yml
name: CI
on: { push: { branches: [main] }, pull_request: {} }
jobs:
  build-test:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-22.04, macos-latest]
        preset: [debug, release, asan]
        include: [{ os: ubuntu-22.04, preset: tsan }]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: lukka/run-vcpkg@v11
      - uses: actions/cache@v4
        with:
          path: ~/.ccache
          key: ccache-${{ matrix.os }}-${{ matrix.preset }}-${{ github.sha }}
          restore-keys: ccache-${{ matrix.os }}-${{ matrix.preset }}-
      - run: cmake --preset ${{ matrix.preset }}
      - run: cmake --build --preset ${{ matrix.preset }} -j
      - name: Test
        env:
          ASAN_OPTIONS: "halt_on_error=1:detect_leaks=1"
          UBSAN_OPTIONS: "halt_on_error=1:print_stacktrace=1"
          TSAN_OPTIONS: "halt_on_error=1"
        run: ctest --preset ${{ matrix.preset }} --output-on-failure -j

18B

构建系统全景

CMake 生成 Ninja/VS · 加速清单

Ninja · ccache · Bazel 何时上

CMake 是生成器，不是编译器。加速靠后端（Ninja）和缓存（ccache），不靠把 Lists 写得更长。

18b.1 主流构建系统横向对比

系统角色何时用
CMake + Ninja元构建 + 快速后端默认。本文其余章节都假设这对
Make遗留执行器只维护，新项目不要
Bazel / Buck2密封 + 远程缓存/执行百万行 monorepo、多语言
Meson更短的 DSLGNOME 系；C++ 库生态仍是 CMake

18b.2 Ninja —— CMake 的最佳后端

CMake 写出 build.ninja，Ninja 跑 DAG。启动比 Make 快一个数量级。preset 里写 "generator": "Ninja"，CI 不要再用 Unix Makefiles。

18b.3 Unity / Jumbo Build

UNITY_BUILD ON 把多个 .cpp 合成一个 TU，全量能砍模板/头文件重复解析。副作用：匿名命名空间冲突、增量变差。CI 全量可开，本地默认关。

18b.4 Precompiled Headers

target_precompile_headers 钉 <vector> 等重头。debug / release / sanitizer 各一份 PCH，旗标变了必须重建。

18b.5 ccache / sccache

命中路径见 §13。跨机用 sccache + S3。launcher 写成 ccache;distcc 时先查缓存再分发。

18b.6 distcc / icecream

把编译任务分到机器池，本地做预处理和链接。没有缓存时才有意义；有 ccache 命中率之后收益骤降。

18b.7 Bazel

密封构建图 + 远程缓存 + RBE。和 CMake 生态（vcpkg / find_package）互通成本高：< 50 万行、依赖多 → 留下 CMake + Ninja + ccache；百万行 monorepo 多语言再评估 Bazel / Buck2。

18b.8 C++20 Modules

BMI 一次编译、多次导入，避免每个 TU 重解析 <vector>。CMake 3.28+ FILE_SET CXX_MODULES 可用。既有项目全量迁移成本大：新叶子库试水，公共头先留传统 include。

18b.9 编译时间侦测

Clang -ftime-trace 出每 TU 火焰图；ClangBuildAnalyzer 聚合最贵的头和模板；IWYU 删多余 include。先量再开 Unity / PCH。

18b.10 加速 checklist

Ninja → ccache（CI 带远程后端）→ PCH → 必要时 Unity（仅 CI）→ IWYU。性价比最高的是前三件，零代码侵入。

易错点速查（10 个高频陷阱）

传递性 · 全局变量 · export
  1. PUBLIC 却不 find_dependency — Config.cmake 漏了传递依赖，下游 configure 挂。
  2. include_directories 全局污染 — 改用 target_include_directories。
  3. 拼接 CMAKE_CXX_FLAGS — 改用 target_compile_options。
  4. ALIAS 缺命名空间 — 必须是 mylib::mylib。
  5. install 忘了 EXPORT — 没有 Targets.cmake 就没有 find_package。
  6. FetchContent 不打 GIT_SHALLOW — 干净构建拉整仓。
  7. Presets 缺 version — "version": 6 不能省。
  8. 没导出 compile_commands — tidy / clangd 都要。
  9. cmake_minimum_required 过低 — 基线 3.20。
  10. sanitizer 只打测例 — 库和测必须同一 preset，见 §15。
