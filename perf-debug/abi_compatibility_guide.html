源码兼容 vs 二进制兼容

ABI 是什么，为什么大型 C++ 项目绕不开

1.1 ABI vs API

API 管「客户重编译能不能过」；ABI 管「旧二进制不重编、直接换新 .so 会不会崩」。C++ 难在后者：mangling、vtable、padding、异常、RTTI 全是二进制契约，库作者改一行头文件就可能毁掉它。

谁定库作者编译器 + 平台（Itanium / MSVC）

1.3 为什么 ABI 对 Tech Lead 是关键

核心 .so 一升，几百个二进制若都要重编，发版从一天变一周。线上「string 长度变怪 / dynamic_cast 失败 / 随机崩」十有八九是 ABI 不一致，不是逻辑 bug。

选型 Boost / Folly / Abseil 先问 ABI 策略；pybind11 / cxx-rs / JNI 全是 ABI 边界。对策四件套：PIMPL、inline namespace、visibility + version script、C ABI 包装。

Name Mangling

符号怎么编码 · c++filt · 稳定承诺 · extern "C"

函数名怎么变成符号

3.1 为什么需要 mangling

链接器只认字符串。C++ 要把重载、命名空间、模板编码进唯一符号，否则 foo(int) 和 foo(double) 会撞名。

3.2 Itanium mangling 范例

声明mangled
void foo()_Z3foov
void foo(int)_Z3fooi
namespace ns { void bar(); }_ZN2ns3barEv
template<> void f<int>()_Z1fIiEvv

3.3 反 mangling 工具

# 一对符号：普通函数 vs Dual ABI 的 string 构造
$ c++filt _ZN2ns3barEv
ns::bar()
$ c++filt _ZNSt7__cxx1112basic_stringIcSt11char_traitsIcESaIcEEC1Ev
std::__cxx11::basic_string<char, ...>::basic_string()

整表用 nm libfoo.so | c++filt；LLVM 侧是 llvm-cxxfilt。

3.4 mangling 的"稳定"承诺

声明不变，mangled 永不改——这是 ABI 兼容的基石。改参数类型 → 老二进制 undefined reference。C++17 起 noexcept 进函数类型，函数指针 mangling 会变。

3.5 extern "C" 抑制 mangling

extern "C" void my_api(int); 符号就是 my_api。不能重载、不能引用、不能模板、不能是成员函数；函数体仍是 C++。跨语言 / 跨编译器的公开面必须走 C ABI（extern "C" + POD），C++ 类型留在 .so 内部。

6.1 GCC 5 的"切换"

GCC 5 把 std::string 从 COW 换成 SSO：C++11 要求 data() 返回不可写指针，COW 违规。旧二进制不能直接换布局，所以同一份 libstdc++.so.6 里必须两套并存。

6.3 如何检查 / 选择

# 默认 1；强制旧 ABI 用 -D_GLIBCXX_USE_CXX11_ABI=0
g++ -E -dM -x c++ - < /dev/null | grep _GLIBCXX_USE_CXX11_ABI
# nm | c++filt | grep __cxx11  → 有就是新 string
std::string s;   // ABI=1 时实际是 std::__cxx11::string

6.4 Dual ABI 的隐藏陷阱

跨 .so 传 std::string 必须同一宏；新代码链旧库会报 get_name[abi:cxx11]() undefined。企业内部锁死一个值，禁止混编。机制细节见 对象模型 §14.9。

7.3 解决方案：C ABI 层 wrapper

❌ 跨 .so 按值传 std::string
std::string get_name();

// Dual ABI / 两套 malloc / Debug CRT 任一不一致就崩

Monorepo 路线：统一 toolchain，静态链 libstdc++ + visibility=hidden，根本不让 STL 跨 so。代价是体积和享受不到系统 libstdc++ 的安全补丁。

8.4 标准库自己的用法

std::__cxx11 是 Dual ABI；std::literals 用嵌套 inline 控制粒度。两 TU 不能把同一名字丢进不同 inline namespace（ODR）。

PIMPL 与 ABI 稳定性

PIMPL 的 ABI 收益 · PIMPL 的成本 · PIMPL 的最佳实践 · 何时不该用 PIMPL

PIMPL 的 ABI 收益 · PIMPL 的成本 · PIMPL 的最佳实践

9.1 PIMPL 的 ABI 收益

// widget.h — 只前向声明
class Widget {
    struct Impl;
    std::unique_ptr<Impl> p_;
public:
    Widget();
    ~Widget();                 // 不能在头里 =default：Impl 还不完整
};
// widget.cpp
struct Widget::Impl { int a; std::string b; };
Widget::~Widget() = default;   // 析构必须在 .cpp

9.2 PIMPL 的成本

一次堆分配 + 每次多一次解引用；公开函数没法在头里 inline。析构必须在 .cpp，否则 unique_ptr 对不完整类型 sizeof 失败——见 智能指针 §3.7。

9.3 PIMPL 的最佳实践

现代写法做成 move-only（拷贝 = delete，移动在 .cpp）。Fast PIMPL 用头里预留 buffer 躲堆分配，但改 Impl 大小会破坏 ABI，预留不够就前功尽弃。

9.4 何时不该用 PIMPL

热路径小对象、必须 inline 的头文件 API、没有跨 so 边界的内部模块、以及模板类（PIMPL 救不了模板）。

10.3 Version Script —— 更精细的导出 + 版本化

新 API 进新 version 节，老 API 永远留在老节。客户看到 mylib_call@@LIBMYLIB_1.0。这是 glibc 几十年 ABI 稳定的办法。

10.4 versioned symbol 实战：替换实现但保留旧符号

.symver foo_v1,foo@LIB_1.0 绑旧实现，foo_v2,foo@@LIB_2.0（两个 @）是默认新实现。老二进制继续跑 v1，新编译的走 v2。

12.3 "C4251" 警告 — 跨 DLL 传 STL 的官方告警
