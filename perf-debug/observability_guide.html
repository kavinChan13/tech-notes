引言

已知症状 vs 未知故障

可观测性 vs 监控

1.1 关键区别

项监控 (Monitoring)可观测性 (Observability)
问题已知症状（CPU > 80%）未知故障（为何 P99 突涨）
方法预定义指标 + 阈值从输出反推内部状态
工具Zabbix / NagiosOTel / Prometheus / Tempo
关注系统是否健康不健康时慢在哪一步

监控回答「已知仪表有没有亮」；可观测性让你对没写过仪表的故障也能追问。百万 QPS 的 C++ 服务两者都要，而且采集本身必须 < 1% 开销。

1.2 为什么 C++ 工程师必须关心可观测性

  • QPS 大，日志失控就是磁盘和账单
  • 热路径同步 log 直接抬 P99
  • 和 Go / Python 混部必须 OTLP

三大支柱 + SLO / 告警怎么在 C++ 落地。OTel 只留 span；eBPF 脚本见 N06。

三大支柱：Logs / Metrics / Traces

三者正交，谁也替代不了谁

Logs / Metrics / Traces

2.1 三者的定位

2.2 三者的关系（不可替代）

「有 Traces 就不需要日志/指标」是错的。Metrics 看趋势，Traces 看慢路径，Logs 看那一次失败的字段。同一 trace_id 把三者钉在一起，而不是互相替代。

2.3 现代趋势：Observability 3.0

支柱之外再加：持续 Profiling（火焰图常态化，见 §12）、eBPF（内核侧无侵入，见 §13 / N06）。崩溃上报（Sentry / Crashpad）是用户态进程的事，见 崩溃调试；整机没了走 内核崩溃分析。

2.4 OpenTelemetry —— 统一三大支柱的标准

OpenTelemetry 用同一套 SDK + OTLP出 logs/metrics/traces，后端可换。2026 新项目不要再接各家私有 SDK。span 用法见 §10，采集链路见 §16。

03

结构化日志 ⭐

一行 JSON，event 基数受控

现代 C++ 日志的基础

3.1 文本日志 vs 结构化日志

文本行给人 grep，机器却要写一堆正则。生产一律 JSON / logfmt：字段有类型，可按 event 聚合。

3.2 结构化日志的关键设计

3.3 spdlog 写结构化日志

pattern 出 JSON；变量走 fmt 参数，不要拼进句子。nlohmann::json 组装也可以，键集合必须和上图一致。

// {"ts":"2026-03-15T10:23:01.123Z","level":"info","event":"user_login","user_id":12345,"trace_id":"abc"}
spdlog::set_pattern(
    "{\"ts\":\"%Y-%m-%dT%H:%M:%S.%eZ\",\"level\":\"%l\",\"msg\":\"%v\"}");
spdlog::info("user_login user_id={} ip={} trace_id={}", uid, ip, tid);

3.4 用 nlohmann::json 直接组装（最干净）

把 ts / level / event / user_id / trace_id 写成对象再 dump() 进 spdlog。键名稳定，比纯 pattern 更容易加字段。

3.5 关键："event" 字段是基数受控的

反模式：msg 含动态变量会撑爆索引。正确：event 枚举，变量独立成键。

3.6 日志级别使用规则

级别用法生产
TRACE / DEBUG细节编译排除或 ≤1% 采样
INFO正常业务事件按业务 1–100%
WARN可恢复异常100%
ERROR / FATAL失败 / 即将退出100% + 告警

3.7 trace_id / span_id 是头等公民

thread_local 存当前请求的 trace/span，用自定义 formatter 自动带上。没有这两个字段，日志和链路永远对不上。

5.1 三件套设计

5.2 关键技术：延迟格式化

前台只塞：rdtsc 时间戳、级别、编译期 format 指针、参数的二进制打包。后台才 fmt + write。这就是 quill 快的原因，不是「换个更快的 fprintf」。

5.3 时间戳：rdtsc 比 clock_gettime 快

clock_gettime ~30ns + syscall；rdtsc ~10ns。cycle 要标定成 ns，且依赖 invariant TSC，跨核才可信。

5.4 quill 风格 — 已经做好的版本

6.2 Prometheus 拉模型 vs 推模型

07

prometheus-cpp 实战

最短 counter + histogram

label 基数陷阱

7.1 安装与最小示例

vcpkg install prometheus-cpp[core,pull]。热路径 Increment / Observe，进程里起 Exposer 拉 /metrics。

auto registry = std::make_shared<Registry>();
auto& reqs = BuildCounter().Name("http_requests_total").Register(*registry);
reqs.Add({{"method","GET"},{"status","200"}}).Increment();

auto& lat = BuildHistogram().Name("http_request_duration_seconds").Register(*registry);
auto& h = lat.Add({{"path","/api"}}, Histogram::BucketBoundaries{0.005, 0.01, 0.025, 0.1, 0.5, 1, 5});
h.Observe(elapsed_sec);
Exposer{"0.0.0.0:9090"}.RegisterCollectable(registry);

7.2 Histogram + label 完整示例

上块已含 histogram。桶在 P99 附近加密；label 只用 method / path 模板 / status。

7.3 高性能：原子计数器封装

Counter 内部有锁。极热路径才每核 atomic，scrape 时再 sum。

7.4 label 基数 (cardinality) 警告

label 禁止 user_id / order_id。每个组合一条时序，百万用户就是百万 series。总数控制在约 10k；高基数放日志 / trace。
08

HDR Histogram —— 比 Summary 更准的百分位

百分位必须能跨实例合并

Histogram vs HDR

8.1 为什么 Summary 类型不好

客户端算出的 P99 不能跨实例相加。10 个实例各报一个 P99，得不到全局 P99。

8.2 Histogram 的做法

只上报桶计数，服务端 sum 后再 histogram_quantile（§6.4）。可聚合，但桶选差误差大。

8.3 HDR Histogram —— 高精度直方图

热路径 hdr_record_value；窗口结束序列化后 hdr_add merge。不要再贴一份完整 init。

8.4 周期 dump HDR + 集中聚合

每 10s dump 当前窗口到 Kafka / 日志，reset 后再采。后端 merge 所有 instance 得到全局百分位。

8.5 协调遗漏 (Coordinated Omission)

压测若「发完等响应再发下一条」，等待时间没被记进去，P99 会低一到两个数量级。HDR 的 record_corrected_value 按预期间隔补点。

Distributed Tracing ⭐

父子 span + W3C 传播

跨服务调用链

9.1 解决什么问题

「这个请求慢了 2 秒，卡在哪？」Logs 对不上请求，Metrics 没有 request id。给每个请求一个 trace_id，跨服务钉成一棵树。

9.2 核心概念

Trace 是整棵树；Span 是一段操作（start/end/parent/attributes）。Baggage 只放真正要穿透的业务字段（tenant），不要把整个 user profile 塞进去。

9.3 W3C Trace Context — 跨语言标准

跨语言只认 traceparent：00-{32hex trace}-{16hex span}-{flags}。厂商扩展走 tracestate。出站 Inject、入站 Extract，下游 span 自动挂到同一棵树。

10

OpenTelemetry C++ SDK

只留 start / 错误属性 / end

不要初始化墙

10.1 为什么用 OpenTelemetry

同一 SDK + OTLP 出三大支柱，后端可换，C++ / Go / Python 共用 trace_id。新项目不要再接各家私有 SDK。

10.2 安装

vcpkg install opentelemetry-cpp[otlp-grpc,otlp-http]。Collector 地址用环境变量，不要在每个服务里写死 exporter 全家桶。

10.3 最小 Tracing 例子

初始化（exporter / processor / provider）做一次即可，不要在每个请求里建。热路径只留 start / 属性 / 错误 / end：

auto span = tracer->StartSpan("handle_request");
auto scope = trace_api::Tracer::WithActiveSpan(span);
span->SetAttribute("http.method", "GET");
if (err) {
    span->SetStatus(trace_api::StatusCode::kError, err);
    span->SetAttribute("exception.message", err);
}
span->End();

10.4 跨服务上下文传播

出站 Inject traceparent，入站 Extract 再 Attach。之后 StartSpan 即为子 span。

10.5 Metrics 与 Logs 一起

span 会把 trace_id 注入 log。Metrics 仍走 prometheus-cpp；高基数不要当 attribute 当 label 用。

14.2 怎么定 SLO（防"拍脑袋"）

先看当前真实 P99，再问业务能忍多久。核心 API 一档、非核心一档。99.9% ≈ 月停 43 分钟。比现状严太多的 SLO 只会训练团队忽略告警。

14.3 Error Budget 政策（"消耗了 50% 怎么办"）

14 天窗口：<50% 正常发版；50–100% 限制冒险变更；花光则功能冻结。1 小时烧掉月预算的 14% → P1。

14.4 Multi-window Multi-burn-rate 告警

短窗（5min）抓真火，长窗（1h）滤毛刺：两窗都超才 page。单窗 PromQL 见 §15 表，不在这里贴墙。
