01

内存泄漏的本质再定义

三视角分歧 — VSZ / RSS / PSS / USS · 三视角下的"泄漏"定义 · 六种 RSS/USS 增长形态

为什么"泄漏"这个词在工程语境下是多义的？三视角分歧带来 80% 误诊

教科书的泄漏是「不可达的已分配」。生产告警看的是 USS 单调涨且不回落。free 了但 arena 不还内核时，两者会打架。先看斜率，再争论定义——多数线上事故是假泄漏被当成真漏，不要反过来。

1.1 三视角分歧 — VSZ / RSS / PSS / USS

看错指标等于误诊。关系永远是 USS ≤ PSS ≤ RSS ≤ VSZ。

指标来源用途陷阱
VSZVmSize是否撞 ulimit -vmalloc 不写页也会涨
RSSVmRSS单进程粗看共享库重复计算
PSSsmaps Pss容器内存账单共享页按引用数均摊
USSPrivate_*泄漏斜率只算本进程独占
命令目的判据
cat /proc/$PID/smaps_rollup单进程 USSPrivate_Clean + Private_Dirty 单调涨
awk '/Pss/{s+=$2} END{print s}' /proc/$PID/smaps容器账单PSS 之和才是 cgroup 口径

四个进程同 binary 时，把 RSS 相加会把 libc 算四遍。K8s 限额看 PSS / memory.current。

1.2 三视角下的"泄漏"定义

视角定义工具会漏掉
教科书分配后没有 freeValgrind / LSancache、单例、capacity
运行时对象不可达LSan 引用图shared_ptr 环：可达但不释
OS / 运维USS 单调涨不回落smaps / 大盘allocator cache 被当成漏
本文默认 OS 视角：会告警、会 OOM 的那种。初始化少 free 一次且体积不涨，线上通常不是问题。

1.3 六种 RSS/USS 增长形态

形态曲线含义下一步
A单调直线每个请求残留固定字节heap diff，对请求路径
B阶梯批次结束留下一块对批次日志，不是对单次 RPC
C锯齿、中线上移碎片或缓存缓慢失控先 trim / 切 jemalloc
DS 曲线后平台warm-up、连接池填满收敛就结案
E脉冲回落批处理、定时全量任务结案；看峰值是否撞 limit
F突然跳高单次大对象 / 恶意输入查当时请求，不要开 Valgrind

D / E 先结案。A / B / F 才上 profile。停流量一小时仍涨，去查心跳和定时器，不是入口 handler。

glibc malloc 内部全景 — 为什么 free 不立即归还内存？

Arena — 多线程下的并发分配单元 · Bins 与 tcache — free 后内存去哪了？ · chunk 布局 — 堆里每一个对象长什么样？ · M_MMAP_THRESHOLD / malloc_trim …

深入 ptmalloc2：arena × bins × tcache × chunk × top chunk × mmap threshold

glibc 把 free 的块放进 bin / tcache，不立刻 brk 收缩。RSS 不降多半是这件事，不是忘了 free。别去贴 malloc.c——看图。

2.1 Arena — 多线程下的并发分配单元

仓库退货：货从货架拿下来（free）不等于退回厂家（brk/munmap）。货还在本仓货架上，占地面积（RSS）不变。

2.2 Bins 与 tcache — free 后内存去哪了？

free 按 size 进不同桶，物理页仍算 RSS。只有 mmap 大块和 trim 堆顶会还内核。

桶何时还内核判据
tcache / fastbin否，且不合并小对象、多线程 → RSS 虚高
small / large / unsorted否（除非并进 top 再 trim）fordblks 大而 RSS 不降
top chunk超过 trim 阈值才 brk 收缩中间有 in-use 就锁死
mmap ≥ 128KBfree 立刻 munmapRSS 跟着业务降

默认 M_MMAP_THRESHOLD 是 128KB。业务里大量 64–100KB 对象会进 largebin，free 之后页仍算 RSS。把它调到 64KB，这些块改走 mmap，释放才会立刻反映到曲线上。代价是 mmap/munmap 更勤、虚拟地址更碎——这是「RSS 真实性」和「分配延迟」的权衡，不是开关。

tcache 每线程一份，别的线程拿不到。缓解：GLIBC_TUNABLES=glibc.malloc.tcache_count=0 或调小 mmap_threshold。线程池很大时优先砍 arena_max，否则 maps 里会铺满 64MB 的 PROT_NONE 预留段。

2.3 chunk 布局 — 堆里每一个对象长什么样？

chunk header：malloc 返回值前面约 16 字节（prev_size + size|A|M|P）。free 后用户区被复用成 fd/bk。fastbin/tcache 不合并，所以小块碎一地凑不出大块。不要贴 malloc.c。

2.4 M_MMAP_THRESHOLD / malloc_trim / 为什么 RSS 不下降

四条按优先级：bins 仍占页 → top 不够大或不在堆顶 → 中间 in-use 锁住 brk → 只有 mmap 块立刻还。区分真泄漏和假泄漏，看这两个字段：

/* mallinfo2 / malloc_info 关键字段 */
arena     /* 主堆 brk 总字节（含空闲） */
uordblks  /* 正在用 */
fordblks  /* 空闲但仍在 arena：free 了 RSS 仍算 */
hblks     /* mmap 块个数 */
hblkhd    /* mmap 总字节：free 立刻 munmap */
keepcost  /* 堆顶可 trim 的字节 */
/* fordblks 大 + keepcost 小 → 碎片锁堆，不是漏 */
/* malloc_trim(0) 后 RSS 降 >30% → 假泄漏 */
命令目的判据
mallopt(M_MMAP_THRESHOLD, 65536)中等对象走 mmapfree 后 RSS 立刻降
malloc_trim(0)强制还能还的页降 >30% → allocator cache
GLIBC_TUNABLES=glibc.malloc.arena_max=2限制线程 arenamaps 里 64MB anon 段变少
LD_PRELOAD=libjemalloc.so更激进归还峰值掉一大截则是 ptmalloc 碎片

4.1 三层泄漏分类

层形态工具

为什么用了智能指针和 RAII，"现代 C++ 服务仍然大量泄漏"？

智能指针是工具不是设计。边界写清楚，泄漏会少一个数量级。

裸 new · 异常路径就漏
void add(Conn* c) {  // 谁 delete？
  if (!ready()) return;
  items_.push_back(c);
}
char* p = new char[n];
parse(p);  // throw 则漏
delete[] p;
unique_ptr / vector 包边界
void add(unique_ptr<Conn> c) {
  items_.push_back(std::move(c));
}
vector<char> buf(n);
parse(buf.data());  // 析构必还
// 清容量：vector<T>{}.swap(v)

7.1 pmap / smaps / smaps_rollup — 零成本快查

零插桩、零损耗。先分清 [heap]、线程 arena 的 64MB anon、file-backed mmap。落到代码再换下面的工具。thread arena 常见写法是先 mmap(64MB, PROT_NONE) 再逐段 mprotect：maps 里出现一串 64MB 倍数、文件名空的段，个数约等于工作线程数。线程池开太大，RSS 会按 arena 一份份虚高，这不是泄漏。

命令目的判据
pmap -x $PID | tail -1总 RSS / mapped第一眼量级
pmap -x $PID | grep '\[heap\]'主 arena（brk）连续 anon 是否独大
cat /proc/$PID/smaps 按 Private_Dirty 排序谁真正占物理页脏独占页 Top
maps 里 30–70MB 的空名 anon数 thread arena每多一段 RSS 虚高一块

7.2 heaptrack — 强力 diff 工具

预发 attach，不重启。杀手锏是两个时间点 diff：t2 仍未 free、t1 没有的调用栈，几乎就是泄漏源。磁盘可能到 GB 级；采样用 HEAPTRACK_TRACE_INTERVAL。

# 预发 attach（也可启动时 heaptrack ./my_service）
heaptrack --pid $PID
# 产出 /tmp/heaptrack.my_service.PID.gz
heaptrack_print -d t1.gz > base.txt
heaptrack_print -d t2.gz > now.txt
# GUI: heaptrack_gui *.gz  ·  Bottom-Up / Memory Leaks / Flame
同类 Bytehound 也是 LD_PRELOAD 堆画像，带 Web UI。命令见 Valgrind 篇 §5.4。两者都不替代 ASan 查越界。

7.3 jemalloc profile — 生产首选

采样记录 in-use 调用栈，损耗通常 <2%，可以一直开。横向宽度 = 仍未 free 的字节；必须 diff 才能去掉长寿对象。

export MALLOC_CONF="prof:true,prof_active:true,lg_prof_sample:19,prof_prefix:/tmp/jeprof.out"
kill -USR1 $PID
jeprof --base=/tmp/jeprof.out.PID.0.heap \
        --svg ./my_service /tmp/jeprof.out.PID.5.heap > diff.svg
# lg_prof_sample:19 ≈ 每 50 万次分配采一次；mallctl("prof.dump") 也可触发

7.4 ASan / LSan — CI 必备

编译插桩，2–3×；Valgrind 是整程序翻译，10–30×。报告怎么读、抑制文件、选项矩阵见 ASan §3 / LSan §9。这里只记「何时开」。

命令目的判据
g++ -O1 -g -fsanitize=addressCI：越界 + 泄漏必须能重编；不要编进生产
g++ -fsanitize=leak只要泄漏损耗更低，无 redzone
ASAN_OPTIONS=detect_leaks=1:atexit=1退出时扫一遍definitely lost 才当 L1
LSAN_OPTIONS=suppressions=lsan.supp忽略 leaky 单例抑制项要评审，别当垃圾桶
__lsan_do_recoverable_leak_check()长稳进程中途 dump不必退出

7.5 eBPF / uprobe / bpftrace — 不重启抓调用栈

不能重编、不能重启、不能 Valgrind 时用。要 debuginfo 才能符号化。自研 LD_PRELOAD hook 是后门：hook 内禁止再 malloc；多线程 unwind 可能死锁。

命令目的判据
bpftrace 挂 uprobe:libc:malloc按 ustack 聚合 size几分钟热点，不是全量泄漏图
memleak -p $PID 30 5bcc：窗口内未 free连续 5 次仍在的栈才跟
tracepoint:sys_enter_brk看谁在撑 arenabrk 频繁而业务空闲 = 碎片
dlsym(RTLD_NEXT,"malloc")自研 hook日志用 write(2)；fork 后状态要重置
08

内核视角 · OOM Killer 与 cgroup memory

RSS 上涨 → Page Cache 受压 → reclaim → OOM 的完整链路 · cgroup v2 memory 子系统五个关键文件 · Transparent Huge Page (THP) 与"内存膨胀…

"泄漏不一定 OOM · OOM 不一定泄漏" —— 完整理解二者的因果链

泄漏不一定 OOM：有 swap、cgroup memory.high、overcommit。OOM 不一定泄漏：突发大对象、THP 膨胀、同机别人抢内存。打分与 dmesg 字段见 NUMA 高级内存 §7；memory.max 梯度见 cgroup §3。

宿舍限电：整栋楼还亮着（宿主 free 充足），某一间跳闸（memory.max）——不是物业没电，是这间自己超了。OOM killer 像宿管：不一定赶最占面积的人，谁「麻烦分」高谁走。

oom_score 大致随 RSS 占比走，再叠加 oom_score_adj（−1000…+1000）。−1000 近似免疫，+1000 优先当祭品。同 cgroup 里比的是组内得分，所以「我不是最肥却被杀」先查 adj，再查同组还有谁。

8.1 从 malloc 到 SIGKILL

写入才 page fault，RSS 才涨。free 列表不够 → kswapd / direct reclaim（先 page cache，再 swap anon）→ 仍不够才 OOM。容器走 memcg 记账，宿主水位可以还很健康。overcommit 打开时，VSZ 可以先吹起来，真正写页时才爆——所以「malloc 成功了」不等于物理内存够。

命令目的判据
cat /proc/$PID/oom_score谁更容易被杀越大越先死
echo -1000 > /proc/$PID/oom_score_adj保护关键进程−1000 近似免疫；+1000 优先祭品
dmesg | grep -i 'out of memory'全局还是 memcg栈含 try_charge = 容器；alloc_pages = 整机
cat /sys/fs/cgroup/memory.events本 cgroup 是否杀过oom_kill > 0
cat memory.current; cat memory.max账单 vs 硬限current 贴 max = 自己撑爆
kubectl describe podK8s 确认lastState reason=OOMKilled

8.2 cgroup v2 memory 五个文件

文件含义判据
memory.current当前账单含 page cache，不只堆
memory.max硬上限超了回收失败就 cgroup OOM
memory.high软上限先 throttle，不立刻杀
memory.low保护下限系统回收时优先留着
memory.statanon/file/slabanon 贴 max 才是真危险

8.3 THP 与 NUMA

现象原因判据 / 动作
RSS 比对象总和大约 30%–100%THP 把 1KB 写成 2MB 页madvise 模式；Redis 类服务常关 THP
某 socket RSS 独高first-touch：谁先写页落谁numastat -p $PID；泄漏线程亲和性会印在该 node

THP 还会在 fork 时把 2MB 巨页拆成 4KB，copy-on-write 延迟尖刺。内存敏感服务（Redis 一类）官方文档倾向关掉它。NUMA 上 first-touch 让「哪个线程先写」决定页落在哪颗 socket；泄漏排查时某 node 独高，优先怀疑绑在那颗上的线程。

真实案例库 — 6 个生产线泄漏排障复盘

每个案例：现象 → 信息收集 → 假设 → 验证 → 修复 → 复盘
案例 1 · IM 网关 RSS 每天涨 1G · arena 碎片化 假泄漏
现象
线上 IM 网关服务，处理 200 万长连接。重启后 RSS 8GB，每天上涨 1G，一周后 OOM。Valgrind 跑不动（线下重放性能不够），ASan 报告 0 leak。
初判
RSS 形态：稳定线性（形态 A）。但是 LSan/Valgrind 都不报泄漏。怀疑：① 真泄漏 L2（可达但永生）② allocator 碎片。
关键操作
① 触发 malloc_trim(0) → RSS 下降 1.5GB（说明大量空闲未还）
② 看 /proc/PID/maps → 数到 32 个 thread arena（线程池 32 个）
③ MALLOC_ARENA_MAX=2 重启 → RSS 稳定在 4GB，每天涨 200MB（仍涨但慢）
④ 切 jemalloc → RSS 稳定 3.5GB，不再增长
真相
不是泄漏，是 glibc ptmalloc2 在多线程 + 频繁小对象分配 + 跨线程 free 的模式下产生大量碎片。每个 arena 独立、tcache per-thread 让对象"分散到各处"，碎片永久无法回收。
修复
① 切 jemalloc（最低风险，LD_PRELOAD）② 业务上把热点对象池化（slab）。
教训
RSS 涨 ≠ 泄漏。先做 malloc_trim 实验，3 秒判断是不是 allocator 问题。
案例 2 · 长稳测试夜间增长 · shared_ptr 循环 真泄漏 L2
现象
72 小时长稳测试，前 48 小时正常，48 小时后 RSS 突然加速增长。LSan 报告 0 个 leak。
初判
形态：突变后线性（形态 A 变种）。可达但永生 → 怀疑 shared_ptr 循环。
关键操作
① jemalloc profile diff 出"OrderBook 对象"和"SubscriberList"是 top 增长
② gdb attach + info shared_ptr (pretty printer) 看 use_count
③ 发现一个 shared_ptr<Subscriber> 持有 shared_ptr<OrderBook>，OrderBook 又持有该 Subscriber → 循环
④ 触发条件：业务在 48h 后某条件成立才加入这个订阅关系
修复
Subscriber 持 OrderBook 改为 weak_ptr。CI 加入静态分析 + 单元测试主动构造循环场景。
教训
循环引用是 L2 泄漏典型，LSan 报不出。稳定性测试必须 > 业务最长周期（48h 才暴露）。jemalloc profile diff 是看 L2 的金手段。
案例 3 · thread cache 误诊 · 切 tcmalloc "更糟" 误诊
现象
团队怀疑 ptmalloc 慢，切 tcmalloc，RSS 涨幅增大了。
初判
tcmalloc 的 thread cache 默认大于 glibc tcache，cache 池更大 = RSS 更大。
关键操作
① MallocExtension::GetStats 输出 → 看到 thread cache 占 800MB
② 调 TCMALLOC_MAX_TOTAL_THREAD_CACHE_BYTES=64MB
③ 再次部署，RSS 回到正常区间
真相
不是 allocator 问题，是 默认配置不合适。tcmalloc 默认 thread cache 64MB × N 线程 = 几 GB。在 RSS 受限容器内必须调小。
教训
切 allocator 不是无脑动作，必须调参。jemalloc 也类似（dirty_decay_ms）。
案例 4 · async lambda 持 this · 连接泄漏 真泄漏 L1+L2
现象
WebSocket 服务，客户端断开后服务端 RSS 不下降。同时 /proc/PID/fd 数量持续上涨。
关键操作
① fd 上涨 → 复习 FileDescriptor_DeepDive.html §11.2 fd 泄漏检测
② 抓 core dump → gdb 看 info threads → 大量 worker 在 epoll_wait
② info shared_ptr 显示 Connection 对象 use_count=2 → 一份在 active 表，一份在 timer 回调里
③ 看代码：timer_.async_wait([conn=shared](...){ conn->poke(); }) 没设取消
真相
断开时 active 表移除连接，但 timer 里的 lambda 仍持有 shared_ptr。timer 未取消，定期触发，conn 永生。fd 也跟着 conn 永生。
修复
① 改 weak_ptr 捕获 ② 断开时显式 cancel timer ③ CI 加入"每次 async lambda 必须 weak 捕获"的 lint。
教训
fd 泄漏 + 内存泄漏经常同源。资源都挂在同一个对象图上。
案例 5 · coroutine task 未 await · 帧泄漏 L1（工具盲区）
现象
C++20 协程改造后的 RPC 服务，RSS 缓慢线性增长。ASan/LSan/heaptrack 都报 0 leak。
关键操作
① jemalloc profile 显示 top 增长是"operator new(N)"，size 集中在 240-280 字节 → 像协程帧
② 在 promise 的 ctor/dtor 加全局原子计数，active_frames 缓慢上涨
③ grep 全代码：发现 spawnTask(...) 返回值被丢弃（fire-and-forget）
④ 丢弃后 task 没人 co_await，coroutine_handle 永远悬挂，frame 永生
修复
① 提供 detach() 接口显式断开，析构时 destroy frame
② 默认 task 析构时若未 done 则 destroy frame（带告警日志）
教训
协程是 工具盲区。在自己的 task type 里嵌入计数器是唯一可靠方法。
案例 6 · observer 没注销 · 单例事件总线 L2 业务
现象
每次用户登录创建一个 Session，Session 注册到全局 EventBus。Session 退出时没注销。EventBus 持有 shared_ptr<Session>。10 万用户来过之后，10 万 Session 全活着。
关键操作
① jeprof diff → top 是 Session::Session
② Session 数量 vs 当前在线人数差 100×
③ 看 EventBus::subscribers_.size() = 100,000 而当前在线只有 1000
修复
① EventBus 改用 weak_ptr 储存订阅者，分发时 lock，失败则 erase
② Session 析构时主动 unsubscribe（兜底）
③ 监控告警：subscribers.size() / online_user_count 比例
教训
"谁拥有谁"必须显式。EventBus 不应该拥有 Session，应该弱引用。

10.1 初级（5 题）— P5/L4 校招新人门槛

点击每道题展开参考答案（先自测，再对照）。

  1. L4 初级new 之后忘了 delete 是不是泄漏？
    答案
    是。但只是 L1（definitely lost）。如果你 new 之后保留了指针在某个全局，那是 L2（still reachable）。要区分。
    考察
    能否区分 "无人持有" 和 "有人持有但永不释放"
    追问
    如果是单例 leaky 设计呢？→ 答："故意不 delete 由 OS 回收，这不算 bug"
  2. L4 初级unique_ptr 和 shared_ptr 区别？
    答案
    ① unique_ptr 独占所有权，只能 move 转移；shared_ptr 引用计数，可共享。② unique_ptr 零开销（等价于裸指针 + RAII）；shared_ptr 有控制块 + 原子计数。③ 默认 80% 应该用 unique_ptr。
    考察
    是否知道性能差异（不只是语义差异）
    常见错误
    说 "都行随便用一个" → 大扣分
  3. L4 初级什么是 RAII？
    答案
    Resource Acquisition Is Initialization。在对象构造时获取资源，析构时释放。利用栈展开保证异常安全下也能释放。
    深挖
    ① 为什么 C 语言做不到？→ 没有析构函数
    ② Java 的 try-with-resources 是 RAII 吗？→ 不完全是（无栈对象，无确定性时机）
    ③ Go 的 defer 呢？→ 函数级，不是对象级
  4. L4 初级怎么用 Valgrind 查泄漏？
    答案
    valgrind --tool=memcheck --leak-check=full --show-leak-kinds=all ./prog
    关注 "definitely lost"，"still reachable" 通常忽略。
    深挖
    Valgrind 太慢怎么办？→ ASan/LSan。原理差异 = 编译插桩 vs 运行时翻译。性能 2-3× vs 10-30×
  5. L4 初级栈对象需要 delete 吗？
    答案
    不需要。栈对象自动析构。delete 栈对象会 crash（错误的 free 给了 allocator 一个非堆地址）。
    常见错误
    说 "delete 栈对象不会有问题，反正会被忽略" → 完全错

10.2 中级（6 题）— P6/L5 一线工程师

  1. L5 中级shared_ptr 为什么会循环引用？怎么解决？
    答案
    A 持 shared<B>，B 持 shared<A>，引用计数永远 ≥ 1。解决：把其中一边改 weak_ptr。规则：后向引用 / 通知方 用 weak。
    深挖
    ① weak_ptr 内部怎么实现？→ 控制块里的 weak_count，可独立于 strong_count。
    ② weak_ptr.lock() 是无锁的吗？→ 是 CAS 循环（lock-free）。
    ③ make_shared 和 shared_ptr(new) 在内存布局上有什么区别？→ 前者合并 T 和控制块；后者两次分配。前者更省、cache 友好，但 weak 还在时 T 也不能释放。
    常见错误
    只说"改 weak_ptr"不解释哪一边改 → 中等扣分
  2. L5 中级malloc 为什么不立即归还内存给内核？
    答案
    ① 性能：归还后下次 malloc 又要 syscall。② brk 只能从堆顶动，中间空闲还不了。③ free 后进入 bins（fastbin/smallbin/largebin/unsorted/tcache）等待复用。④ 仅 ≥128KB 的 mmap 块 free 时立刻 munmap。
    深挖
    ① M_MMAP_THRESHOLD 是什么？默认值？怎么调？→ 128KB，mallopt 或 GLIBC_TUNABLES
    ② malloc_trim 做什么？→ 扫描堆顶，把 top chunk 中可还的部分通过 brk(-N) 还给内核
    ③ tcache 为什么独立 per-thread？→ 无锁分配，配合 fastbin 形成两级 cache。glibc 2.26 引入。
  3. L5 中级RSS 不下降怎么办？
    答案
    四步排查：① malloc_trim(0) 试试 ② 切 jemalloc 试试 ③ jemalloc/tcmalloc heap profile diff ④ 排查是否容器 capacity 没收缩（vector::clear 不缩容）。
    深挖
    有没有可能 free 了 RSS 仍上升？→ 有。free 进 fastbin，但下一次 malloc 走了不同 size，反而又申请新页。这是典型碎片场景。
  4. L5 中级ASan 为什么比 Valgrind 快这么多？
    答案
    ① ASan 编译期插桩，每条访存前查 shadow byte。② Valgrind 是整程序动态翻译，每条原始 inst 翻成多条 IR 在合成 CPU 跑。③ ASan 损耗 2-3×，Valgrind 10-30×。
    深挖
    ① ASan 的 shadow memory 怎么映射？→ 每 8 字节用户内存 → 1 字节 shadow，固定偏移（shadow = (mem >> 3) + 0x7FFF_8000）
    ② ASan 能查未初始化内存吗？→ 不能，那是 MSan
    ③ ASan 能查越界但 Valgrind 漏报吗？→ 能。ASan 的 redzone 设计；Valgrind 看不到栈/全局变量越界（只看 heap）
  5. L5 中级allocator 如何减少锁竞争？
    答案
    三级 cache：① per-thread tcache（无锁）② per-arena fastbin（同 arena 内一把锁）③ 多 arena（不同线程分散到不同 arena）。tcmalloc/jemalloc 类似但更激进。
    深挖
    ① jemalloc 的 size class 设计？→ 几何级数，约 200 个 class
    ② tcmalloc 的 page heap 锁颗粒？→ 每个 size class 一把
    ③ 为什么不能完全无锁？→ 跨线程 free 必然要锁（dest arena）
  6. L5 中级vector::clear 之后内存会还吗？
    答案
    不会。capacity 不变。clear 只析构对象，buffer 还在。要真释放：vector<T>{}.swap(v) 或 v.shrink_to_fit()（后者标准上不强制）。
    同理 unordered_map::clear 不缩 bucket 数组。

10.3 高级（6 题）— P7/L6 资深 / Staff

  1. L6 高级线上不能重启，怎么定位泄漏？
    答案
    三个手段（按优先级）：① 如果用了 jemalloc/tcmalloc，它们的 profile 模式开了就在跑，直接 SIGUSR dump → jeprof diff。② attach heaptrack --pid（10-20% 损耗，10 分钟够定位）。③ bpftrace / eBPF memleak（采样最低损耗）。不能用 Valgrind/ASan（需重启 + 高损耗）。
    深挖
    ① 没开 prof 怎么办？→ 切流量到一个 canary 实例，重启它开 prof
    ② 容器内连 bpftrace 都装不了？→ ssh 到宿主跑 sidecar，用 cgroup 路径过滤
  2. L6 高级为什么"泄漏不一定 OOM，OOM 不一定泄漏"？
    答案
    泄漏 ↛ OOM：① 速度极慢 / 服务进程会 cycle ② swap 兜底 ③ cgroup 没设 hard limit ④ overcommit + 写得稀疏，未必触发 page fault。
    OOM ↛ 泄漏：① 一次性 alloc 大对象（输入恶意）② 业务突发峰值 ③ 同宿主其它进程偷内存 ④ 内存膨胀 (THP/碎片) ⑤ allocator cache 失控
  3. L6 高级delete this 为什么危险？
    答案
    ① this 之后任何成员访问 = UAF ② 编译器可能在调用 delete 后仍访问 vptr（虚函数解析） ③ 你必须保证 this 是 new 出来的（栈对象 / 数组 / 静态对象都 crash）④ 异常安全断裂。
    正确做法：不要 delete this。用 shared_from_this 或外部生命周期管理。
    深挖
    什么场景必须 delete this？→ 极少。比如 COM 风格的 AddRef/Release 模式，Release==0 时 delete this。但现代 C++ 用 intrusive_ptr 替代。
  4. L6 高级weak_ptr 的内部实现？
    答案
    weak_ptr 持有 同一个控制块 的指针，不增加 strong_count，但增加 weak_count。
    strong→0 时调 ~T()，但控制块不释放（因为 weak_ptr 还可能查询）。
    weak→0 时才释放控制块。
    lock() 是 CAS 循环："读 strong_count，若 >0 则 +1，否则失败"。
    深挖
    ① make_shared 时控制块和 T 合并，那 strong=0、weak>0 时，T 已析构但内存不能释放，相当于浪费？→ 是的。这是 make_shared 的缺点。
    ② 为什么 use_count() 不线程安全？→ 读了立刻就过期，应该用 expired() 替代逻辑判断
    ③ enable_shared_from_this 怎么工作？→ 内部有个 weak_ptr<T> _Wptr，shared_from_this() 就是 _Wptr.lock()
  5. L6 高级你怎么设计一个长稳服务的内存治理体系？
    答案（架构题）
    四道防线：
    ① 静态防御：clang-tidy + cppcoreguidelines + 自研 lint（强制 weak 捕获 / 限制 shared_ptr 边界）
    ② CI 防御：每个 PR 跑 ASan/LSan + 长稳模拟 30 分钟
    ③ 运行时观测：jemalloc profile 常开 + USS 监控 + slope alarm（24h 斜率 > 阈值告警）
    ④ 应急工具链：jeprof / heaptrack / bpftrace 在标准基础镜像里，SOP 文档化
    考察
    是否能从单点工具上升到"体系"的视角
  6. L6 高级怎么实现一个 malloc hook？两个坑？
    答案
    ① LD_PRELOAD + dlsym(RTLD_NEXT, "malloc") 接管。② 或 glibc 的 __malloc_hook（已废弃但能用）。③ 或 jemalloc 的 extent_hooks（最优雅）。
    坑 1 · 递归
    hook 内不能调 printf/malloc → 死循环。用 syscall 直写 fd。
    坑 2 · backtrace 不安全
    多线程下 unwind 可能死锁（信号 + dl_iterate_phdr 持锁）。用 frame pointer 自己走或 libunwind cache。

10.4 专家级（5 题）— P8+ Staff/Principal

  1. L7+ 专家ptmalloc 的 chunk header 布局？P 位用来做什么？
    答案
    每个 chunk 头 16 字节（64 位）：prev_size | size+flags。
    flag 低 3 位：P (PREV_INUSE)、M (IS_MMAPPED)、A (NON_MAIN_ARENA)。
    P 位：标记前一个 chunk 是否在使用。free 时检查下一块的 P 位决定是否合并。如果前一块也 free，本块 prev_size 字段才有效（指向前块起始）。
    深挖
    off-by-one 改 P 位为什么导致漏洞？→ 攻击者改 size 字段的 P 位，glibc 误判可合并，把用户数据当 free chunk 链表处理，链表操作 unlink 改写指定地址 → write-what-where。这是 heap fengshui 攻击的基础。
  2. L7+ 专家在 NUMA 系统上发现某 socket RSS 远高于其它 socket，怎么排查？
    答案
    ① numastat -p $PID 看分布
    ② 检查线程亲和性 (taskset/numactl)：是不是有线程绑到该 socket 但跨 socket alloc？
    ③ first-touch policy：哪个 CPU 写，页落在哪 node。负载分配不均可能导致"hot socket"
    ④ 检查 NUMA-aware allocator 配置（jemalloc 有 percpu arenas）
    ⑤ 如果是泄漏，泄漏的线程亲和性会反映在某 node 上
  3. L7+ 专家C++20 协程的 frame 在哪？怎么排查协程泄漏？
    答案
    frame 由 operator new 在堆上分配（编译器可优化成栈，需 HALO 启用）。包含：所有局部变量、promise、suspended state。
    排查：① 在 promise 的 ctor/dtor 嵌全局原子计数 ② handle 在 final_suspend 后是否被 destroy
    ③ jeprof / heaptrack 看 operator new 的 size 分布，frame 通常是个小固定值
    深挖
    HALO 是什么？→ Heap Allocation eLision Optimization，编译器在 inline 后能证明 frame 不逃逸时把它栈分配。需要 -O2+ 且 await 表达式都内联。
  4. L7+ 专家容器里的 OOMKilled 但宿主机 free 内存很多，可能原因？
    答案
    cgroup memory.max 触发了。看 memory.events.oom_kill。原因：
    ① cgroup limit 设得太低
    ② 单进程实际 USS 已达 limit（不是宿主总量）
    ③ Java/Go 等运行时未感知 cgroup（C++ 通常无此问题）
    ④ kernel memcg "reparenting" 后 LRU 评估异常（罕见）
    ⑤ 进程 oom_score_adj 太高被优先选中
  5. L7+ 专家设计：如何在不重编不重启的前提下，给一个跑了 3 天的服务挂上"分配热点追踪"？
    答案（开放设计题）
    不重编不重启 + 不重启 + 低损耗 → 唯一选项是 eBPF / uprobe。具体：
    ① bpftrace 挂 uprobe:libc:malloc 采集调用栈+size
    ② per-stack 聚合存到 BPF map
    ③ user-space 周期性 read map → 输出火焰图
    ④ 配 / arg0 > threshold / 过滤大对象
    ⑤ 与 free 配对（uretprobe + 自己维护 map）做 diff
    缺点：① 符号化需要 debuginfo ② 跨 PID 时间窗口短
    替代方案：如果允许装 sidecar，可以用 ssh 到宿主跑 memleak -p PID（bcc）
    考察
    是否能在多约束下做工程权衡，是否真用过 eBPF
