01

引言

只给机制，不给 Task

为什么需要协程

1.1 异步代码的"四代演进"

回调嵌套、future 链式 .then、协程线性 co_await、C++26 Sender/Receiver 代数 —— 四代解决的是同一件事：别把异步控制流写成回调地狱。协程这一代的卖点只有一句：异步代码长得像同步，try/catch 和局部变量寿命都按顺序走。

1.2 协程的"标准只提供机制"特性

C++20 只给三样：三个关键字、状态机模板、coroutine_handle + promise_type 钩子。不给可用的 Task / Generator —— hello world 要先写几十行框架，各家 Task 互不 co_await。这是「零开销 + 不绑死调度模型」的代价。C++23 补了 std::generator，标准化 Task 要等到 C++26 std::execution。

1.3 本指南的覆盖范围

三件套（promise / handle / awaiter）讲到能画关系图；Task 一次性 vs Generator 惰性；对称转移和 HALO 为什么能称「零开销」；调度、异常、泄漏的工程坑。生产 IO 协程写法见 异步网络 §4.2。

1.4 与其他章节的关系

  • 并发模式 §12 是入门，本文是机制深度

02

协程的核心机制

函数变成带 PC 的状态机

编译器到底做了什么

2.1 "什么样的函数是协程"

函数体出现 co_await / co_yield / co_return 任一，整个函数就是协程。返回类型叫 Task 但体内是普通 return 的，仍是普通函数。见 §1.2 那张三关键字图。

2.2 协程的 5 个阶段

2.3 协程帧 (coroutine frame) — 协程的"栈"

普通函数的局部变量在调用栈上，返回即释放。协程能挂起后再恢复，状态必须放进帧——默认在堆上（HALO 见 §10）。

字段说明
promise_type promise用户定义的行为对象
形参副本按值传入的；引用参数不复制所指对象
跨挂起点的局部变量恢复后还要用的
state / PC状态机当前 case
resume / destroy 入口编译器生成
引用参数不会被拷进帧。临时对象作实参、协程一挂起就悬空 —— 最常见的 UB。见 §15。

2.4 状态机翻译 —— 协程的"灵魂"

编译器把函数改写成带 PC 的 switch：挂起 = 写 state 后 return；恢复 = 进对应 case 接着跑。这就是无栈协程。

03

promise_type 完全剖析 ⭐

六个钩子决定协程行为

promise_type 定义协程的全部行为：何时挂起、co_return 怎么收、异常怎么记。编译器通过 Task::promise_type 找到它。

3.1 promise_type 的 6 个必需钩子

钩子必需作用
get_return_object()✅返回给调用方的 Task / Generator
initial_suspend()✅never 立刻跑；always 懒启动
final_suspend() noexcept✅通常 always，让外部取结果再 destroy
unhandled_exception()✅主体未捕获异常；通常存 exception_ptr
return_value(T) 或 return_void()二选一对应 co_return v / co_return，不能同时有
yield_value(T)仅 generator对应 co_yield

3.2 一个最小 promise_type

句柄没有析构函数：final_suspend = always 时必须由 Task 析构 destroy()，否则帧泄漏。

#include <coroutine>

struct SimpleTask {
    struct promise_type {
        SimpleTask get_return_object() {
            return SimpleTask{std::coroutine_handle<promise_type>::from_promise(*this)};
        }
        std::suspend_always initial_suspend() noexcept { return {}; }
        std::suspend_always final_suspend()   noexcept { return {}; }
        void return_void() {}
        void unhandled_exception() { std::terminate(); }
    };
    std::coroutine_handle<promise_type> h_;
    explicit SimpleTask(std::coroutine_handle<promise_type> h) : h_(h) {}
    ~SimpleTask() { if (h_) h_.destroy(); }
    SimpleTask(const SimpleTask&) = delete;
    SimpleTask(SimpleTask&& o) noexcept : h_(std::exchange(o.h_, {})) {}
    void resume() { if (h_ && !h_.done()) h_.resume(); }
};

3.3 initial_suspend / final_suspend 的关键选择

组合语义用在
never + never立刻跑，结束自毁fire-and-forget
never + always立刻跑，结束等外部 destroyeager 且要拿结果
always + always手动 resume；结束等外部Task / 懒求值（默认）
always + never懒启动 + 结束自毁少用
final_suspend 几乎总是 always 且 noexcept：结果还在 promise 里；对称转移要在这里把控制权交还给等待者。fire-and-forget 才用 never 让帧自毁。

3.4 return_value vs return_void

Task<T> 定义 return_value(T)；Task<void> 定义 return_void()。不能同时有，否则编译失败。

3.5 unhandled_exception —— 必须实现

主体未捕获异常不会弹回调用方，只调这个钩子。标准做法：存 exception_ptr，等待者 await_resume 时 rethrow。图见 §11。

3.6 进阶钩子（可选）

钩子作用
await_transform(T&&)拦截 / 禁止某些 await（可 = delete 掉 std::future）
operator new / delete自定义帧分配（池、PMR）
get_return_object_on_allocation_failure分配失败兜底

3.7 await_transform 的妙用 —— 强制类型化

只给允许的 awaitable 写 overload，其它类型没有匹配就会编译失败。libunifex / stdexec 用它把 sender 翻成 awaiter。

04

coroutine_handle —— 协程的"句柄"

指向帧的遥控器，没有析构

4.1 它是什么

std::coroutine_handle<P> 是指向帧的类型擦除指针：resume() / destroy() / done() / promise()（仅 typed）/from_promise / from_address。

4.2 typed vs untyped (void)

typed 能 promise()；隐式转成 coroutine_handle<> 后只能 resume / destroy / done。awaiter 常接 untyped，需要字段时用 from_address 转回 typed。

4.3 from_promise — 在 promise 里反向拿到自己的 handle

get_return_object 里 from_promise(*this) 是约定：promise 在帧开头，反向偏移算出帧地址。骨架见 §3.2。

4.4 资源管理 — handle 是 raw owner

handle 没有析构。未 resume 的懒 Task 若丢掉且不 destroy，帧在堆上永生。§3.2 的析构就是在堵这个洞。
05

awaiter 三件套

ready / suspend / resume

让"等什么"可定制

5.1 awaiter / awaitable 区别

awaitable 是能被 co_await 的表达式；awaiter 才真正定义「等什么」，必须有三方法。解析顺序：promise 的 await_transform → 对象自身 → operator co_await → 否则它就是 awaiter。

5.2 awaiter 的三个方法

struct MyAwaiter {
    bool await_ready() const noexcept;   // true → 跳过挂起
    void              await_suspend(std::coroutine_handle<> h);          // 必然挂起
    bool              await_suspend(std::coroutine_handle<> h);          // true 挂 / false 不挂
    std::coroutine_handle<> await_suspend(std::coroutine_handle<> h);    // 对称转移 §9
    T await_resume();                    // 返回值 = co_await 的值
};

5.3 标准库提供的两个 trivial awaiter

suspend_never：ready=true。suspend_always：ready=false，suspend 空实现。promise 的 initial/final 几乎只用这两个。

5.4 第一个真实 awaiter：等定时器

ready 看延时是否已到零；suspend 把 h.resume 交给调度器的 timer；resume 返回 void。IO 完成 awaiter 同一骨架：把 handle 塞进完成队列，CQE 回调里 resume。

5.5 await_suspend 的三种返回类型

返回语义
void无条件挂起，等外部 resume
booltrue 挂 / false 立刻续跑
coroutine_handle<>对称转移：尾调用恢复返回的那个协程

5.6 await_resume 的返回值就是 co_await 的"值"

返回 int 则 int x = co_await e；返回 void 则单独一条 co_await e。

5.7 让任意类型可 await：operator co_await

给类型写 Awaiter operator co_await()，co_await fut 就变成 co_await fut.operator co_await()。Asio 的 use_awaitable 走的是同一条路。

06

编译器对 co_await 的精确翻译

五步控制流，不是又一份伪代码

auto val = co_await expr; 被编译成五步。伪代码墙见过一次就够，这里只留控制流。

步骤做什么
1 找 awaiterawait_transform 或 operator co_await 或 expr 自身
2 ready?true → 跳到 5
3 保存状态写 PC、保住跨挂起点的局部变量
4 suspendvoid：return 给调用方；bool：false 则不挂；handle：尾调用那个协程
5 resumeval = awaiter.await_resume()

6.1 三种 co_* 的翻译要点

表达式翻译为
co_await e上面 5 步
co_yield eco_await promise.yield_value(e)
co_return epromise.return_value(e); goto FINAL
co_return;promise.return_void(); goto FINAL
FINALco_await promise.final_suspend()

08

手写 Generator<T>

拉一下，才产一个

Generator 是 co_yield 的接收端：每次 yield 挂起，外部 ++ 再 resume。比 Task 简单——没有 continuation 链。

Generator<int> naturals(int n) {
    for (int i = 0; i < n; ++i) co_yield i;
}
for (int x : naturals(5)) std::print("{} ", x);   // 0 1 2 3 4

8.1 比较 std::generator (C++23 标准化版)

用户视角与上例相同，实现多了递归 yield 和 range 协议。详见 §16。

09

Symmetric Transfer

换协程，不涨栈

尾调用转移控制权

9.1 问题：朴素实现导致栈无限增长

A await B await C … 若 await_suspend 里直接 other.resume()，每次都是普通函数调用，链一深就爆栈。

9.2 解决：await_suspend 返回 coroutine_handle

std::coroutine_handle<> await_suspend(
    std::coroutine_handle<promise_type> me) noexcept {
    auto a = me.promise().awaiter_;
    return a ? a : std::noop_coroutine();
}

编译器对返回的 handle 做尾调用 resume：当前协程栈帧释放，新协程顶上来。

9.3 std::noop_coroutine — "空协程"哨兵

顶层 Task 没有等待者。返回空 handle 会崩；noop_coroutine() 的 resume 是空操作。

9.4 为什么这是"零开销"的关键

没有它就必须把恢复塞进队列、靠外部循环 dispatch，无法 inline。有了它，A→B→C 像普通调用链，还能尾调用消除。

10

HALO

别赌编译器一定 elide

堆 / 栈 / 池

10.1 协程帧的"默认"分配

每次创建协程默认 operator new 分配帧 —— 这是主开销，大约一次 alloc + free。

10.2 HALO 的优化条件

Heap Allocation eLision：把帧提升到调用者栈上。要同时满足：生命周期被调用者包含、帧大小静态可知、handle 不逃逸。

10.3 典型可以 HALO 的场景

co_return co_await inner() 这种立刻消费，编译器看得到寿命。把 Task 存变量再 submit_to_queue 则必须堆分配。

10.4 验证 HALO 是否生效

看 IR 里的 new 调用，或反汇编里 inner 是否被 inline 到 outer 的栈上。O0/O1 基本没有 HALO。

10.5 自定义 frame 分配器（避免堆分配）

在 promise 里写 operator new/delete 走 thread-local 池。编译器创建帧时会调它们，不依赖 HALO。

11

异常在协程中的传递

throw 进 promise，不进原调用栈

11.1 协程主体抛异常会怎样

未捕获异常走 promise.unhandled_exception()，不会弹到启动协程的那个调用栈。必须自己接住。

11.2 标准范式：保存到 exception_ptr，await 时 rethrow

钩子存指针；等待者取值前检查。骨架已在 §3.2 / §7 图里。

11.3 跨协程异常链

C await B await A，A throw 仍能在 C.get() 的 catch 里拿到原始 runtime_error。

11.4 fire-and-forget 协程的异常

无人 await 则异常无处可去。至少在 unhandled_exception 里 log / 交错误队列，禁止裸 spawn。

11.5 协程的"两阶段"异常

  • 主体抛 → unhandled_exception
  • promise 构造 / 分配失败 → 传给调用方
  • get_return_object / await_resume 抛 → 传给当时的调用方
  • final_suspend 抛 → terminate
12

调度器与 Reactor 对接

恢复点之后线程可能换了

12.1 协程的"调度"问题

协程不知道 1 秒后谁来 resume。co_await 只负责挂起；定时器、IO 完成、线程池都是用户提供的 executor。

12.2 三个抽象

抽象职责
Executor在哪跑：线程池 / IO 线程
Scheduler何时跑：定时器、完成通知
Reactor事件循环（epoll / io_uring）

12.3 让协程跑在指定 executor 上 — schedule awaiter

await_ready=false，suspend 里 ex.post([h]{ h.resume(); })。恢复点之后的代码跑在目标线程。

12.4 IO 完成 awaiter（与 io_uring 对接）

suspend 时把 handle 地址塞进 SQE user_data；CQE 回调取出并 resume()。await_resume 返回字节数。面试骨架在 §17。完整 Reactor 见 异步网络 §2.4。

12.5 Asio coroutine 支持

不要在本页再抄一份 echo。asio::awaitable + use_awaitable + co_spawn 的线性读写见 异步网络 §4.2 和 §5.1。生产网络服务用 Asio，不要手撸 awaiter。

协程调试技巧

bt 上看不见谁 await 谁

14.1 协程帧不在栈上的痛苦

gdb bt 只看见当前状态机那一帧。谁 await 谁散落在各帧的 awaiter_ 里，不在调用栈上。

14.2 GDB / LLDB 的协程支持现状

  • GDB 13+：基础 coroutine 命令
  • LLDB / VS：能看 promise 字段（MSVC natvis 较成熟）
  • folly::coro 有 GDB pretty-printer 画等待链

14.3 手写"逻辑栈回溯"工具

promise 里留 awaiter_ + source_location，从当前 handle 沿等待者走下去打印文件:行。typed handle 才能碰 promise。

14.4 用 std::source_location 自动标记协程函数名

promise 构造函数默认参数 source_location::current()，每个协程帧自动带上创建点。

14.5 抓 fire-and-forget 协程

自定义 operator new/delete 统计活帧，定期 dump「活着但很久没 resume」的。配合 ASan 看泄漏栈。

15

协程内存泄漏排查

未 destroy 的帧留在堆上

15.1 协程"泄漏"的典型模式

模式表现
丢 handle帧永生，无人 destroy
等待链断裂父被销毁，子挂在 awaiter_ 上没人 resume
引用悬空不是泄漏，症状像踩内存
跨调度器互等两方 continuation 永远不跑

15.2 案例 1：引用参数 + 临时对象 → UB

形参是 const string& 时，帧里只有引用。临时实参在第一次挂起后销毁。面试题 §17 有完整 UB 示例。修复：按值传。

15.3 案例 2：fire-and-forget 丢 handle

用 supervisor 管寿命，或专用类型：final_suspend=never + unhandled_exception 必处理。记录所有 spawn 到全局表。

15.4 排查工具

heaptrack / jemalloc 按固定帧大小聚合；自定义分配器 dump 长期不动的活帧。详见 内存泄漏指南。

16

C++23 std::generator —— 标准化的 Generator

惰性序列进标准库

C++23 把 Generator 放进 <generator>，避免人人造轮子。用法与 §8 短例相同，下面只补标准库多出来的能力。

16.1 基本用法

std::generator<int> fib() 里 co_yield，再 fib() | views::take(10)。创建时一个数都还没算，见 §8 惰性图。

16.2 递归 yield —— std::generator 的杀手特性

co_yield std::ranges::elements_of(walk(child)) 展开子生成器，每元素 O(1)，手写转发是 O(depth)。

16.3 与 ranges 互通

它是 input_range，可直接 fold_left / take / filter。

16.4 性能

每次 yield 约 10–20 ns。比填 vector 慢，但内存恒定 O(1)，无限序列只能走这条路。

面试题集（20 道分层）

点击每道题展开参考答案（先自测，再对照）。

17.1 基础（必答）

  1. 基础协程与线程的本质区别？无栈协程 vs 有栈协程？
    vs 线程
    协程是用户态可挂起 / 恢复的函数，协作式调度、无内核切换；线程由 OS 抢占调度。
    无栈/有栈
    C++20 是无栈协程：只把必要状态存进堆上的协程帧，不保存整个调用栈；有栈协程（ucontext / boost.context）保存完整栈，可在任意深度挂起但切换更重。
  2. 基础C++20 给了哪三个关键字？编译器看到这些做了什么？
    关键字
    co_await / co_yield / co_return，函数含任一即为协程。
    改写
    编译器把函数改写成状态机：分配协程帧、创建 promise、在挂起点保存 / 恢复状态，并按 promise 钩子织入逻辑。
  3. 基础协程帧里存哪些东西？为什么不在栈上？
    存
    promise 对象、形参拷贝、跨挂起点存活的局部变量、挂起点编号 / 恢复地址。
    为何在堆
    挂起后调用者栈帧会销毁，状态必须存在堆（或 HALO 优化后的调用者帧）才能在恢复时仍有效。
  4. 基础promise_type 的 6 个必需钩子是什么？
    钩子
    get_return_object、initial_suspend、final_suspend(noexcept)、unhandled_exception、return_void 或 return_value，以及（generator 需）yield_value。
  5. 基础initial_suspend / final_suspend 通常应该返回什么？为什么？
    initial
    Task 常 suspend_always（懒启动）；eager 任务用 suspend_never。
    final
    几乎总 suspend_always 且 noexcept —— 让帧在结束后保留，便于取结果 / symmetric transfer 唤醒等待者，再由外部 destroy。

17.2 中级

  1. 中级awaiter 的三个方法 await_ready / await_suspend / await_resume 各自语义？
    ready
    是否已就绪，true 则跳过挂起。
    suspend(h)
    挂起时调用，决定挂起 / 恢复 / 转移。
    resume
    恢复后调用，返回值即 co_await 表达式的值。
  2. 中级await_suspend 的三种返回类型（void / bool / coroutine_handle）有什么区别？
    void
    无条件挂起，控制权回到 resume 的调用者。
    bool
    true 挂起；false 不挂起、立即继续本协程。
    handle
    symmetric transfer：尾调用恢复返回的那个协程，栈深度不增。
  3. 中级什么是 Symmetric Transfer？为什么它是 C++ 协程"零开销"的关键？
    机制
    await_suspend 返回另一协程 handle，编译器翻译成尾调用，当前栈帧立即释放，链式恢复栈深度恒定，避免深嵌套 / 循环 yield 栈溢出。完整解析见 §17.4。
  4. 中级HALO 是什么？满足什么条件才能生效？
    HALO
    Heap Allocation eLision Optimization：编译器省略协程帧的堆分配，放进调用者栈帧。
    条件
    协程生命周期完全被调用者包含（不逃逸）且编译器能看到全部信息（通常需内联）。属"可做"优化，不保证。
  5. 中级协程主体抛异常会怎样？怎么传给等待者？
    捕获
    未捕获异常触发 promise.unhandled_exception()，通常 exc_ = std::current_exception() 存到 promise。
    透传
    await_resume() 时检查并 rethrow_exception，从而传给 co_await 它的等待者。
  6. 中级co_yield / co_return 在编译器层面分别被翻译成什么？
    co_yield e
    → co_await promise.yield_value(e)。
    co_return e
    → promise.return_value(e) 后跳到 final_suspend（无值则 return_void）。
  7. 中级什么是 std::noop_coroutine？什么时候用？
    作用
    返回一个"什么都不做"的 coroutine_handle。
    场景
    symmetric transfer 链的终点：final_suspend 在没有等待者时返回 noop_coroutine() 安全结束、把控制权交回调度器，而不是返回无效 handle。

17.3 高级（体现深度）

  1. 高级手写一个 Task<T> 支持 co_await + 异常透传，至少要哪些核心代码？
    promise
    get_return_object / initial_suspend=suspend_always / final_suspend 返回唤醒 continuation 的 awaiter / unhandled_exception 存 exception_ptr / return_value。
    Task
    持有 coroutine_handle；operator co_await 返回 awaiter（await_suspend 记录 continuation 并 symmetric transfer 启动本协程，await_resume 重抛异常并取值）；析构 destroy。
  2. 高级为什么协程函数不能用引用参数？给一个 UB 示例
    原因
    形参按值拷贝进协程帧，但引用 / 指针参数只拷贝引用本身、不延长被引用对象寿命。
    UB 示例
    Task f(const std::string& s) {
    co_await something();   // 挂起后临时实参已销毁
    use(s);                // 悬空引用 → UB
}
f(std::string("tmp"));     // 临时只活到第一次挂起
    应按值传参。
  3. 高级fire-and-forget 协程的异常去哪了？怎么正确处理？
    陷阱
    detached 协程无人 co_await，unhandled_exception 里若 rethrow 会 terminate。
    正确
    在 unhandled_exception 内 catch / 记日志，或设计成不分离、由 supervisor 持有并取异常。
  4. 高级std::generator 比手写 generator 强在哪？（提示：elements_of）
    优势
    标准、正确处理异常与提前结束，且支持递归 yield：co_yield std::elements_of(subrange) 高效展开嵌套生成器（递归生成器每元素 O(1)，避免手写转发的 O(depth) 开销）。
  5. 高级跨调度器的协程链可能死锁吗？怎么避免？
    风险
    continuation 在错误线程 / 持锁时恢复，或两调度器互等线程 → 死锁 / 饥饿。
    避免
    明确 continuation 恢复到哪个 executor（如 asio strand）、避免持锁 co_await、用 symmetric transfer + 调度器边界显式 schedule。
  6. 高级协程怎么和 io_uring / Reactor 对接？写一个 read awaiter 骨架
    骨架
    struct ReadAwaiter {
    int fd; void* buf; size_t len; ssize_t result;
    bool await_ready() { return false; }
    void await_suspend(std::coroutine_handle<> h) {
        // 提交 io_uring SQE，user_data = h.address()
    }
    ssize_t await_resume() { return result; }
};
    完成队列(CQE)回调里取出 handle 并 resume()。
  7. 高级协程 frame 能不堆分配吗？答出 HALO 之外还有什么手段
    手段
    HALO（内联使逃逸分析成功）、自定义 promise 的 operator new 用内存池 / 栈缓冲、generator 的栈分配实现、保证不逃逸下的 -O2 优化 —— 本质都是消除 / 复用那次 operator new。
  8. 高级解释为什么 final_suspend 必须 noexcept，且通常返回 suspend_always
    noexcept
    final_suspend 在协程结束清理阶段调用，此时若抛异常无处可逃 → terminate，标准强制 noexcept。
    suspend_always
    让帧在结束后保留，等待者 / 调用者能安全取结果、读异常、再手动 destroy；若 suspend_never 帧会自毁，外部访问就悬空。

17.4 速答示范（第 8 题：Symmetric Transfer）

答：朴素协程链 A→B→C 的恢复，如果 await_suspend 内部调 h.resume()，会让栈每嵌套一层加一帧。深嵌套或循环 yield 直接栈溢出。
Symmetric Transfer 通过 await_suspend 返回 std::coroutine_handle<>，编译器把"切换到那个协程"翻译成尾调用（间接跳转），当前栈帧立即释放。整个协程链不论多深，栈深度恒定。
Final suspend 返回"父协程的 handle"就是这个机制：Task 结束时把控制权 symmetric transfer 给等我的人。这是 C++ 协程相比 Go / Lua 协程能宣称零开销的核心理由。
