constexpr 与编译期编程

大多数人把 constexpr 当成「一个让编译器提前算好的优化提示」。这个理解会让你错过它真正的价值：编译期求值是编译器内部一台抽象机在解释执行你的代码，而那台抽象机看得见未定义行为。于是越界、溢出、读未初始化这些运行期查不出来的问题，在这里会变成一条编译错误。constexpr 最被低估的好处从来不是快，而是它让一段代码变成可证明的。

01

常量表达式的求值模型

不是优化，是编译器里另一台机器在跑你的代码

先纠正一个普遍的心智模型。很多人以为 constexpr 的工作方式是「编译器看到常量参数，就顺手把结果折叠掉」——那是常量折叠（constant folding），一种自古就有的优化，跟 constexpr 没关系，而且开不开优化都可能变。

constexpr 是另一回事：它在语言语义层面定义了一台求值器。标准规定了这台求值器认识哪些操作、遇到什么情况必须放弃，而这些规定与优化级别无关——同一段代码在 -O0 和 -O3 下，能不能常量求值的答案必须一致，否则 static_assert 的行为就会随编译选项变化。

core constant expression：标准对「这个表达式能不能被常量求值器算出来」给出的判定。它的定义方式是反向的——不是列出允许什么，而是列出一张「出现下列任一情况即不是常量表达式」的清单。这个反向定义很关键：它意味着语言的默认态度是「能解释的都解释」，每次版本更新只是从清单里删掉几条。
常量折叠像超市收银员心算「三瓶五块的水等于十五」——他只是碰巧算得快，换个人可能就不算了。constexpr 求值器像审计：它不只算，还要求每一步都能追溯到合法凭证。你说「从这个数组的第 4 格取值」，它会先翻一下这个数组到底有几格；数组只有 4 格（下标 0–3），它不会随便给你一个数字，而是拒绝出账并开一张单据。运行期那个收银员不会拒绝——他会顺手抓旁边货架上的东西塞给你。

1.1 抽象机拒绝什么

那张「不许做」的清单看着杂乱，其实只有两个来源：抽象机没有外部世界，以及抽象机不容许未定义行为。把每一条归到这两类里，就不需要背了。

被拒绝的操作来源为什么必然如此
IO、系统调用、取当前时间、读环境变量没有外部世界编译期不存在「文件」「时钟」「进程」这些东西，而且必须可重现——同一份源码两次编译要给同一个答案
调用非 constexpr 函数没有外部世界它的定义可能在另一个 TU、在一个只有二进制的库里、或者就是一条汇编指令。抽象机没有可解释的东西
读非 constexpr 的全局变量没有外部世界它的值要到运行期初始化后才确定
volatile 读写、内联汇编没有外部世界volatile 的语义就是「值可能被抽象机看不见的东西改动」，两者定义上冲突
reinterpret_cast、把整数当指针不容许 UB抽象机里没有「一片可以任意解释的字节」——每块存储都带着类型与对象身份。C++20 的 std::bit_cast 是被批准的替代品
越界下标、解引用空指针 / 悬垂指针不容许 UB抽象机知道每个数组有多长、每个对象是否还活着，所以它必须拒绝
有符号溢出、除以零、移位位数越界不容许 UB同上。运行期靠 UBSan 才能抓到的东西，这里是硬性诊断
读未初始化的对象、访问 union 的非活跃成员不容许 UB抽象机逐字段跟踪初始化状态与 union 的活跃成员

第二类的存在方式值得多说一句。标准并不是专门为 constexpr 写了一套「安全检查」，而是说：只要求值过程中出现了会导致 UB 的操作，这个表达式就不是常量表达式。所以这不是编译器厂商的良心实现，而是一条符合性要求——任何合格的编译器都必须诊断它。

1.2 UB 变成编译错误

这是本文最想让你带走的一句话，所以值得看一段最小的代码。

constexpr int at(const int (&a)[4], int i) { return a[i]; }

constexpr int arr[4] = {1, 2, 3, 4};

constexpr int ok  = at(arr, 3);   // 4，编译期算出，进 .rodata
constexpr int bad = at(arr, 4);   // ❌ error: read of out-of-bounds
                                  //    array element at index 4

int leak(int i) {
    return at(arr, i);            // 同一个函数，运行期调用。
}                                 // i == 4 时读到 arr 后面的字节，
                                  // 没有任何人提醒你

constexpr int twice(int x) { return x * 2; }
static_assert(twice(2'000'000'000) == 4'000'000'000);
// ❌ error: overflow in constant expression
//    有符号溢出是 UB，抽象机看得见，于是拒绝出账

注意 at 只写了一遍。同一个函数体，在常量求值上下文里是一个被审计的表达式，在运行期是一段普通机器码。这带来一个非常实用的技术：把核心逻辑写成 constexpr，然后为它写一批 static_assert 覆盖边界输入。这些 static_assert 不只是单元测试——它们同时是对那条执行路径上不存在 UB 的证明，而且证明是编译器做的，零运行开销、不需要跑测试、不依赖 sanitizer 是否编进了这次构建。

这条性质有一个边界要记清：它只证明你实际求值过的那些输入。static_assert(f(3) == 9) 不能保证 f(-1) 没有 UB。所以它是「路径级的证明」，不是「函数级的验证」——真正想覆盖全部输入还是要靠 fuzzing 和 sanitizer。

1.3 「可以但不保证」

constexpr 函数最常被误解的一点：它不是「这个函数在编译期执行」的声明，而是「这个函数有可能在编译期执行」的许可。真正决定的是调用点——上下文需不需要一个常量。

调用点所处的上下文是否强制编译期求值求不出来时的后果
需要常量表达式的位置：数组长度、模板实参、static_assert、枚举值、case 标签、位域宽度、constexpr 变量的初始化器强制编译错误，并且错误信息会告诉你卡在哪一步
constinit 变量的初始化器强制（要求常量初始化）编译错误。注意它只约束初始化，不约束变量本身是常量
consteval 函数的调用强制编译错误：立即函数的调用必须自身是常量表达式
普通表达式里调用 constexpr 函数，实参恰好都是常量不强制编译器可以求值，也可以生成一次真正的函数调用。-O0 下常见后者
实参含运行期值不强制就是一次普通调用，和没有 constexpr 一样

这个设计是刻意的，而且是 constexpr 得以普及的关键。假设 constexpr 意味着「必须编译期」，那么标准库里所有想支持编译期用法的函数都得写两份——一份 constexpr、一份普通版，调用方还得自己选。「可以但不保证」让一份实现服务两个世界，这就是为什么 C++20 之后标准库能大规模地给既有函数补上 constexpr 而不破坏任何东西。

代价是：你无法从源码上看出某次调用到底在哪跑。这个不确定性催生了 §6 那一整套诊断手段，也是 consteval 存在的理由。

02

三个关键字的分工

它们约束的是三件不同的事，混用是因为名字长得太像

constexpr / consteval / constinit 读起来像同一个东西的三种强度，其实它们回答的是三个不相干的问题：能不能在编译期算、必须不必须在编译期算、值什么时候就位。

2.1 一张判定流程

2.2 constinit 与 SIOF

constinit 是三个里最少被用、也最被误解的一个。它常被当成「弱化版 constexpr」，但它其实在解决一个完全不同的问题——一个 C++ 里最古老、也最难调的问题之一。

静态初始化顺序问题（SIOF, Static Initialization Order Fiasco）：具有静态存储期的对象分两批初始化。静态初始化（零初始化 + 常量初始化）在程序开始执行前就完成，值直接躺在 .bss / .data / .rodata 里；动态初始化要在运行期真的调用构造函数。同一个翻译单元内的动态初始化按定义顺序进行，但跨翻译单元的相对顺序是未指定的。于是 A.cpp 的全局对象构造时用到 B.cpp 的全局对象，而后者可能还没构造。

SIOF 的经典解法是 Meyers singleton（函数内 static 局部对象，首次调用时构造），它确实正确，但代价是每次访问都要过一次线程安全的 guard 变量检查，而且把问题从「顺序」变成了「析构顺序也未定义」。constinit 提供的是另一条路：让这个对象根本不需要动态初始化。

// ---- 坏：动态初始化，跨 TU 顺序未指定 ----
// registry.cpp
std::map<std::string, Handler> g_registry = build_registry();

// plugin.cpp
static bool g_ok = (g_registry.emplace("foo", &foo_handler), true);
//                   ^^^^^^^^^^ 可能读到还没构造的 map → SIOF

// ---- 好：值在编译期就算好，程序跑之前已经在段里躺着 ----
struct Entry { std::string_view name; Handler fn; };

constexpr Entry kTable[] = {          // 常量初始化 → .rodata
    {"foo", &foo_handler},
    {"bar", &bar_handler},
};

// ---- 需要「启动前就位，但之后要能改」时，用 constinit ----
constinit Counter g_stats{0};         // 保证静态初始化；之后 ++ 它完全合法
// constexpr Counter g_stats{0};      // ❌ 隐含 const，再也改不了
// const     Counter g_stats{0};      // ⚠️ 编译得过，但不保证是静态初始化
//                                    //    构造函数一旦不是 constexpr，
//                                    //    它就悄悄滑回动态初始化那一栏

最后那三行注释是这一节的全部重点。const 和 constinit 在源码上只差一个词，但前者是「希望它是静态初始化」，后者是「要求编译器证明它是」。区别在什么时候暴露：用 const 时，有人把 Counter 的构造函数改成非 constexpr，代码照样编译通过，只是这个变量默默搬到了动态初始化那一栏——SIOF 的引信在一次无关的重构里被装上了。用 constinit，那次重构会在编译期停下来。

这就是 constinit 真正的定位：它不是为了「更快」，而是把一个原本只存在于程序员脑子里的假设变成编译器强制的约束。和 §1.2 那条一样，它的价值在于把错误的发现时机往前搬。常见陷阱与风格里有全局状态相关的更多反模式。

2.3 四者对照

关键字约束的是保证启动前就位之后可修改能用在需要常量表达式的位置
const（变量）只是「不能通过它修改」❌ 不保证❌仅当是整型 / 枚举且初始化器本身是常量表达式
constexpr（变量）值必须是常量表达式✅❌（隐含 const）✅
constinit（变量）初始化器必须是常量表达式✅✅❌（变量本身不是常量）
constexpr（函数）「有可能」被常量求值——取决于调用点（见 §1.3）
consteval（函数）「必须」被常量求值——✅，而且只能用在那里

constinit 那一行的两个 ✅ 和一个 ❌ 组合起来，正好是别的关键字给不出的语义：值确定得很早，但值本身不是常量。全局计数器、全局互斥量、预分配的内存池句柄都属于这一类——它们必须在任何人碰它之前就可用，但它们的整个存在意义就是被修改。

这三个关键字的语法与最小示例在 现代 C++ 特性速览里各有一张 slide，本文不重复；if constexpr 在模板里怎么裁掉死分支，见 模板编程 §5.1。
03

constexpr 函数的边界

每次放宽，都是那台抽象机又多实现了一块语言语义

3.1 一路放宽的十二年

C++11 刚引入 constexpr 时，函数体只能是一条 return 语句。这个限制严苛到近乎无用——想写循环只能靠递归，想分支只能靠三元运算符，一个简单的求和函数写出来像 Lisp。此后每一个标准版本都在放宽它。

C++23 那一条（P2242）值得单独理解，因为它改变的是判定的粒度。在它之前，只要函数体里出现了一个不可能常量求值的构造（比如一个 static 局部变量），整个函数就不能标 constexpr——哪怕那条路径在编译期永远走不到。这让渐进迁移几乎不可能：你必须把一个函数的所有内部实现细节一次性清理干净。C++23 把判定推迟到实际求值：函数照样可以标 constexpr，只是一旦某次常量求值真的走到了那条分支，这次求值失败。

3.2 至今仍然不行的

放宽了这么多轮之后，还剩下的限制基本都是「永久的」——它们不是编译器实现没跟上，而是与编译期求值的定义相冲突。

限制性质该怎么做
IO、文件、网络、当前时间、随机数永久这些属于构建期而不是编译期：写一个小程序生成 .cpp，见 §7
reinterpret_cast、指针与整数互转永久std::bit_cast（C++20，在 constexpr 里可用，前提是两边都是可平凡复制且大小相同）
把 new 出来的内存带到运行期永久（瞬态分配）见 §4：先算大小，再填进 std::array
真的抛出并让异常逃出常量求值永久try / catch 自 C++20 可以写，但异常真的抛到求值边界外就让这次求值失败。编译期错误处理用返回值或 static_assert
volatile 读写、内联汇编、intrinsic永久if consteval 分两条实现：编译期走朴素算法，运行期走 intrinsic（§6）
读一个非 constexpr 的运行期变量永久没有绕法——这是「常量」二字的定义
static / thread_local 局部变量C++23 已放宽C++20 及之前用「返回 std::array 的 constexpr 函数」替代静态表
goto、带标签的语句C++23 已放宽—

把这张表和 §1.1 那张放在一起看会发现它们是同一件事的两个侧面：凡是抽象机无法解释或无法保证可重现的，就永远不会被允许。这也给了一个很好用的预判方法——遇到一个新特性想知道它能不能进 constexpr，不用去查标准，先问「这件事能在一台没有操作系统、没有内存地址、必须两次给同一答案的机器上做吗」。

04

constexpr 容器与瞬态分配

vector 只能当算草稿的工具，不能当交付物

C++20 给 std::vector 和 std::string 补上了 constexpr，这是一个非常大的可用性提升——终于可以在编译期写「筛法」「分词」「建图」这类需要动态容器的算法了。但随之来了一条极容易踩的限制，而且它的错误信息初看很费解。

瞬态分配（transient allocation）：常量求值期间用 new / allocator 分配的存储，必须在同一次常量求值结束之前释放。换句话说，编译期的堆是随这次求值一起诞生、一起消失的，任何还活着的分配都会让这次求值失败。

4.1 生命周期窗口

这条规则的一个直接推论是：constexpr std::string 作为全局常量永远写不出来。很多人第一次用 C++20 的 constexpr string 都是从这里被拦下的。想要一个编译期就绪的字符串常量，用的还是 constexpr std::string_view（指向字符串字面量，字面量本身是静态存储期）或者 constexpr std::array<char, N>。

4.2 先算大小再填 array

知道了限制，绕法也就清楚了：把一次求值拆成两趟。第一趟用 vector 随便算，但只把「结果有多大」这个整数带出来；第二趟用这个整数当 std::array 的长度，再算一遍并填进去。std::array 不分配，所以它可以离开求值。

// 第一趟：只算「有多少个」—— 返回 size_t，不含指针，可以带出求值
consteval std::size_t count_primes(int n) {
    std::vector<char> sieve(n + 1, 1);        // 瞬态分配
    std::size_t k = 0;
    for (int i = 2; i <= n; ++i)
        if (sieve[i]) {
            ++k;
            for (int j = i * i; j <= n; j += i) sieve[j] = 0;
        }
    return k;
}   // vector 在这里析构 —— 求值结束时堆是空的，合法

// 第二趟：用第一趟的结果当长度，把值填进不分配的容器
template <int N>
consteval auto primes_up_to() {
    std::array<int, count_primes(N)> out{};   // 长度是常量表达式
    std::vector<char> sieve(N + 1, 1);
    std::size_t k = 0;
    for (int i = 2; i <= N; ++i)
        if (sieve[i]) {
            out[k++] = i;
            for (int j = i * i; j <= N; j += i) sieve[j] = 0;
        }
    return out;                               // array 无分配 → 可以带出去
}

constexpr auto kPrimes = primes_up_to<1000>();   // 躺在 .rodata
static_assert(kPrimes.size() == 168);
static_assert(kPrimes.back() == 997);

代价是算了两遍。对小表无所谓，对大表就要算一算 §7 那笔账了——这也是「两段式」这个模式最真实的成本，而不只是写起来啰嗦。

值得注意的是这里用了 consteval 而不是 constexpr。原因很具体：count_primes 里有 std::vector，如果它被运行期调用，就会真的在运行期做一次堆分配。标成 consteval 明确表示「这个函数只服务编译期」，编译器会拒绝任何运行期调用，也就不会为它生成机器码。这是 consteval 最实用的场景：不是为了「保证快」，而是为了把一个只在编译期成立的实现约束变成编译错误。

把查表算在编译期、结果直接进只读段，在资源受限的场景下收益最直接（省 RAM、省启动时间、还能进 Flash）。嵌入式 C++ 里有这条路线的完整实践；通信协议里 constexpr 表驱动 opcode 分发的实战见 通信软件中的现代 C++ §3。
05

编译期字符串处理

让「写错一个字符串」从运行期崩溃变成编译不过

字符串在编译期编程里地位特殊，因为大量配置是以字符串形式写在代码里的：格式串、SQL、正则、协议字段定义、路由表、单位符号。这些串在编译时就已经完全确定，却传统上要到运行期才会被解析——于是一个打错的字符就是一个线上故障。编译期字符串处理就是把这个解析动作往前搬。

5.1 字面量进模板参数

做法可用版本能做到 / 做不到
字符逐个进模板参数包 template<char... Cs>C++11能把内容编进类型，但调用处写法极丑，且受模板参数个数上限限制
constexpr 函数 + std::string_view 操作字面量C++17能解析、能校验、能算长度；做不到让串的内容成为类型的一部分
结构化类型作非类型模板参数（fixed_string）C++20字面量直接写进模板实参列表；内容相同的两个串是同一个类型，可以特化、可以做类型级分发
constexpr std::string 参与求值C++20求值内部随便用，但结果带不出去（§4）
static_assert 的消息本身由常量求值产出C++26报错信息终于能拼出「你写的是 X，合法取值是 Y」，而不再是一句写死的话

C++20 这一行是质变。它的门槛是结构化类型（structural type）：所有成员都是 public 且本身是结构化类型、没有私有或受保护的非静态数据成员、没有可变引用成员。这个要求看起来很严，但理由很硬——非类型模板参数需要模板等价性判定：编译器必须能回答「Schema<"a"> 和另一处的 Schema<"a"> 是不是同一个类型」。只有当值的全部状态都可见、可逐成员比较时，这个判定才是良定义的。一旦允许私有状态或自定义 operator==，「相同」的含义就由用户代码决定，而类型标识不能依赖用户代码的执行结果。

// 结构化类型：成员全 public、无私有状态 → 可以当非类型模板参数
template <std::size_t N>
struct fixed_string {
    char data[N]{};
    constexpr fixed_string(const char (&s)[N]) {
        for (std::size_t i = 0; i < N; ++i) data[i] = s[i];
    }
    constexpr std::string_view view() const { return {data, N - 1}; }
};

// 编译期校验协议字段串，形如 "u8:id,u16:len,bytes:payload"
consteval bool valid_schema(std::string_view s) {
    while (!s.empty()) {
        auto comma = s.find(',');
        auto field = s.substr(0, comma);
        auto colon = field.find(':');
        if (colon == std::string_view::npos) return false;   // 缺类型名
        auto type = field.substr(0, colon);
        if (type != "u8" && type != "u16" &&
            type != "u32" && type != "bytes") return false;  // 类型名非法
        if (colon + 1 >= field.size()) return false;         // 缺字段名
        if (comma == std::string_view::npos) break;
        s = s.substr(comma + 1);
    }
    return true;
}

template <fixed_string S>
struct Schema {
    static_assert(valid_schema(S.view()),
        "协议字段串非法。正确形如 \"u8:id,u16:len\"："
        "每个字段必须是 类型:名字，类型只能取 u8 / u16 / u32 / bytes");
    /* ... 由 S 推导出偏移表、生成 encode/decode ... */
};

using Hdr = Schema<"u8:id,u16:len">;    // ✅
// using Bad = Schema<"u9:id">;         // ❌ 编译失败，且信息说清了合法取值

这段代码的价值不在于技巧，而在于它把一类错误彻底消灭了。协议字段串写错，原本要到那条消息第一次被收到时才暴露——可能是上线三周后的某个凌晨。现在它是一条编译错误，而且是在写下那个字符的几秒钟之后。

5.2 为什么 format 能查格式串

这里有一个很值得学的设计手法：std::format 的第一个参数类型不是 std::string_view，而是 std::format_string<Args...>——一个模板类，带着实参类型，并且有一个 consteval 的转换构造函数。于是「校验」这件事被塞进了参数的隐式转换里，调用者的写法一个字都不用改。

值得留意的是它报错的机制：不匹配时并不是调用 static_assert（那时还拿不到具体信息），而是在 consteval 上下文里执行一个不是常量表达式的操作（例如抛异常）。由于身处立即函数，「求值失败」就直接等于「编译失败」。这是编译期错误上报的一个通用套路——代价是错误信息往往指向标准库内部，读起来不如手写的 static_assert 友好，这也正是 C++26 允许动态生成 static_assert 消息要解决的问题。

06

怎么确认它真在编译期跑

「我加了 constexpr」不是证据，编译器的拒绝才是

§1.3 说过，constexpr 只是许可不是保证。所以「这段代码到底在哪跑」是一个必须能被验证的问题，否则你可能维护着一个自以为零开销、实际上每次调用都在算的函数。

手段能回答什么局限
static_assert(expr)最强的证据：编译通过就说明 expr 确实被常量求值了只适用于本身能写成常量表达式的东西
constexpr auto x = f(...);同上，而且顺手把结果固化进只读段变量随之变成 const
constinit「这个全局变量有没有偷偷滑进动态初始化」只管初始化这一刻，不管之后
把函数标成 consteval「是不是所有调用点都在编译期」——有一个不是就编译失败会连带拒绝那些本来合理的运行期调用
std::is_constant_evaluated()C++20：在函数内分出编译期 / 运行期两条实现极易误用，见下
if constevalC++23：同上，但语法上排除了那种误用需要 C++23
objdump -s -j .rodata / 看反汇编最终裁判：表到底在不在只读段、调用有没有被真的生成读起来费劲，且受优化级别影响
nm -C 找 _GLOBAL__sub_I_ 符号这个 TU 还有没有残留的动态初始化符号命名与平台 / 工具链相关
 
// ① 最强的证据：编译不过，就说明它没在编译期跑
static_assert(kPrimes.size() == 168);
static_assert(kPrimes.back() == 997);

// ② 全局变量真的没有动态初始化？让编译器保证，别自己猜
constinit Registry g_reg = make_registry();   // 不是常量初始化 → 编译失败

// ③ 同一个函数两条实现：编译期走朴素算法，运行期走 intrinsic
constexpr int popcount(std::uint64_t x) {
    if consteval { return naive_popcount(x); }         // C++23
    else         { return __builtin_popcountll(x); }   // 抽象机不认识它
}

// ④ 最后的裁判：看产物
//   objdump -s -j .rodata a.out        表真的在只读段里？
//   nm -C a.out | grep _GLOBAL__sub_I  这个 TU 还有动态初始化残留？

std::is_constant_evaluated() 那个误用值得单独警告，因为它不报错、只静默地永远走错分支：把它写进 if constexpr。

if constexpr (std::is_constant_evaluated()) 里，条件表达式本身处在一个「显然被常量求值」的位置，所以它恒为 true——编译器会把 else 分支整个丢掉，于是运行期调用也走了编译期那条实现。这个 bug 的症状是「性能没有变好」或者「运行期结果不对」，而代码读起来完全合理。if consteval（C++23）就是为了消灭这个坑：它是语法结构而不是函数调用，写不出这种形式。所以规则很简单：用 if，不要用 if constexpr；有 C++23 就直接用 if consteval。

6.1 static_assert 的信息怎么写

编译期校验的价值完全取决于那条错误信息有没有用。把 static_assert 的消息写成「assertion failed」和写成一句能直接照着改的话，差别是「五分钟」和「半小时翻标准」。

三条经验。第一，说清楚合法取值，而不是只说非法：「类型名只能取 u8 / u16 / u32 / bytes」比「非法的类型名」有用得多，因为读者的下一个动作就是改。第二，把违反的约束翻译成用户的语言：不要写 "!std::is_pointer_v<T>"，写「这个接口不接受裸指针，请传 span 或引用——裸指针无法表达长度」。第三，把约束拆细：一个 static_assert 检查五个条件，报错时你还是不知道是哪一个错了；五个各自带消息的 static_assert 会精确地告诉你。concept 在这件事上天然更好，因为编译器会逐个原子约束报告哪一条没满足。

07

代价与取舍

编译期计算没有消灭工作量，只是把账单换了个人付

关于 constexpr 的讨论经常停在「运行期开销为零」就结束了，这是不完整的。那些计算并没有凭空消失——它们被搬到了编译器里，而编译器是一台解释器：它逐节点走 AST、为每个中间对象维护值与生命周期记录，速度比 -O2 编出来的机器码慢几个数量级。更关键的是，这笔开销每次编译都要重付一遍，而编译发生的次数远比你想的多。

把第三条路单独拎出来讲，因为它常常是最优解，却因为「不够 C++」而被忽略。

时机成本落在哪适合什么不适合什么
constexpr / consteval 求值每次编译，每个包含它的 TU 各付一次小表；结果要参与类型系统（当数组长度、模板实参、concept 约束）大表；求值本身耗时长——它还会被多个 TU 各算一遍
构建期生成 .cpp（脚本或小程序）一次生成，结果进版本库或构建缓存几万项的大表；生成逻辑本身很复杂；需要读外部文件（.proto、IDL、CSV）结果需要参与编译期类型推导的场合
运行期启动时建表每次进程启动；表在 RAM 里表依赖运行期配置或环境；表大到不想放进二进制启动延迟敏感的场景；内存紧张的嵌入式设备

第一行那个「每个 TU 各付一次」值得警惕，它是编译期计算最隐蔽的放大器。常量求值的结果不会跨翻译单元缓存：一个放在头文件里的重量级 consteval 表，被 80 个 .cpp 包含，就要被算 80 遍。单次 0.4 秒看着无害，乘完是 32 秒，再乘上 CI 里的 4 个构建配置就是两分钟——而这两分钟会出现在每一个 PR 上。

所以最后给一个可操作的判据，而不是「适度使用」这种废话：先量。用 -ftime-trace（Clang）或 -ftime-report（GCC）看常量求值在总编译时间里的占比；改动前后各量一次全量构建。如果一张表让全量构建慢了 10% 以上，它就该搬去构建期生成——那时你换到的是一份可读、可 diff、增量编译友好的 .cpp，而不是一段每次都要重新解释的模板。

反过来，有一类编译期计算无论多贵都值得：它换到的不是运行期性能，而是一类错误的消失。§5 的协议串校验、§2.2 的 constinit、§1.2 的 UB 诊断都属于这一类——它们的收益不体现在 benchmark 上，而体现在「这个 bug 从此不可能被写出来」。拿编译时间换运行期几纳秒通常不划算，拿编译时间换一整类线上故障几乎总是划算。这两者经常被混在一起讨论，而它们的成本收益结构完全不同。

面试题集（12 道）

按难度分三档，先自测再对照

点击每道题展开参考答案（先自测，再对照）。

8.1 基础（必答）

  1. 基础constexpr 变量和 const 变量的区别是什么？

    const 只说「不能通过它修改」，对初始化时机没有任何要求：const int n = read_config(); 完全合法，它的值要到运行期才有。

    constexpr 要求初始化器本身就是常量表达式，值在编译期算出，因此能用在需要常量的位置（数组长度、模板实参、static_assert）。它同时隐含 const。

    一个容易混的历史细节：const int（整型 / 枚举，且初始化器是常量表达式）在 C++98 起就能当数组长度用，这让很多人以为 const 就等于编译期常量。但这个待遇只给整型和枚举，换成 const double 或 const MyClass 就不成立。

  2. 基础一个 constexpr 函数，一定在编译期执行吗？

    不一定。constexpr 是「有可能在编译期求值」的许可，不是保证。真正决定的是调用点：处在需要常量表达式的位置（数组长度、模板实参、static_assert、constexpr 变量的初始化器）时才强制；否则编译器可以求值，也可以生成一次普通调用，-O0 下后者很常见。

    这个「不保证」是刻意设计，也是 constexpr 能大规模普及的原因：一份实现同时服务编译期和运行期，标准库才能在 C++20 给大批既有函数补 constexpr 而不破坏任何调用方。要强制编译期就用 consteval。

  3. 基础consteval 和 constexpr 的区别？什么时候该用 consteval？

    consteval 标记的是「立即函数」：每一次调用都必须自身是常量表达式，运行期调用直接编译错误。constexpr 是「可以但不保证」。

    实用场景不是「保证快」，而是把一个只在编译期成立的实现约束变成编译错误。比如 §4.2 那个用 std::vector 做筛法的函数：如果它被运行期调用，就会真的在运行期堆分配一次，这不是设计意图。标成 consteval 之后，任何运行期调用都在编译期被拦下，编译器也不必为它生成机器码。

  4. 基础为什么数组越界在 constexpr 上下文里是编译错误，而在运行期只是 UB？

    因为常量求值是一台抽象机在解释执行，它知道每个数组有多长、每个对象是否还活着、每个字段有没有初始化过。标准规定：求值过程中一旦出现会导致 UB 的操作，这个表达式就不是常量表达式——于是编译器必须诊断。

    运行期是真实 CPU 执行机器码，没有任何人携带这些元信息，越界读就是老老实实去读那个地址。所以同一个函数体在两条路径上待遇完全不同。

    推论是一个很实用的技术：把核心逻辑写成 constexpr，再用一批 static_assert 覆盖边界输入——这些断言同时是「这条执行路径上没有 UB」的编译器证明，零运行开销、不依赖 sanitizer。注意它只覆盖你真的求值过的输入。

8.2 中级（区分熟练度）

  1. 中级constinit 解决什么问题？为什么 const 或 constexpr 替代不了？

    它解决静态初始化顺序问题（SIOF）。静态存储期对象分两批初始化：静态初始化（零初始化 + 常量初始化）在程序跑之前完成、不存在顺序问题；动态初始化在运行期 main 之前进行，跨翻译单元的相对顺序未指定。constinit 要求编译器证明这个变量属于前者，证明不了就编译失败。

    constexpr 替代不了，因为它隐含 const——而全局计数器、全局互斥量、内存池句柄的整个存在意义就是被修改。constinit 提供的正是别人给不出的组合：值确定得很早，但值本身不是常量。

    const 替代不了，因为它只是希望是静态初始化。区别在什么时候暴露：有人把构造函数从 constexpr 改成普通函数，const 版本照样编译通过，只是这个变量默默滑进了动态初始化那一栏——SIOF 的引信在一次无关的重构里被装上，而且没有任何人收到通知。constinit 会让那次重构在编译期停下来。

  2. 中级C++20 起 constexpr 里能用 std::vector 了，为什么不能把算出来的 vector 直接当全局常量？

    因为瞬态分配规则：常量求值期间的分配必须在同一次求值结束前释放。constexpr std::vector<int> v = make(); 要求那块堆活到运行期，直接编译错误。

    根本原因是编译期的「堆」只是编译器内部的一张对象表，没有任何机制把它序列化进目标文件——真要支持，编译器得在 .data 里重建整套指针关系并让重定位配合，是另一个数量级的复杂度。同理，constexpr std::string 作为全局常量也永远写不出来，要用 constexpr std::string_view（指向字面量）或 constexpr std::array<char, N>。

    常用绕法是两段式：第一趟用 vector 随便算，只把「结果有多大」这个整数带出来；第二趟用它当 std::array 的长度，再算一遍填进去。array 不分配，所以能离开求值。代价是同一份逻辑算了两遍，大表上这个成本要算进 §7 那笔账。

  3. 中级std::is_constant_evaluated() 最常见的误用是什么？为什么 if consteval 更好？

    最常见的误用是把它写进 if constexpr：if constexpr (std::is_constant_evaluated())。此时条件表达式本身处在一个显然被常量求值的位置，所以它恒为 true，else 分支被整个丢弃——运行期调用也走了编译期那条实现。

    这个 bug 特别阴险，因为它不报错也不崩溃，症状只是「性能没变好」或「运行期结果不对」，而代码读起来完全合理。正确写法是普通的 if。

    if consteval（C++23）更好的地方是它是语法结构而不是函数调用，从形式上就写不出那种误用；而且在 if consteval 的 true 分支里可以调用 consteval 函数，这是普通 if + is_constant_evaluated() 做不到的。

  4. 中级为什么 std::format 能在编译期检查格式串？运行期拼出来的格式串怎么办？

    关键在参数类型：std::format 的第一个参数不是 std::string_view，而是 std::format_string<Args...>——一个带着实参类型的模板类，它有一个 consteval 的转换构造函数。于是校验被塞进了参数的隐式转换里，调用方写法一个字都不用改。构造过程中拿 Args 的类型逐个核对占位符，不匹配就执行一个非常量操作（抛异常）；因为身处立即函数，求值失败就直接等于编译失败。

    所以前提是格式串是字面量。运行期拼出来的串用 std::vformat + std::make_format_args（C++26 也可以用 std::runtime_format 包一层），此时检查退回运行期，错了抛 std::format_error。

    顺带一个可迁移的经验：这种「在 consteval 里做一个非常量操作来报错」是编译期错误上报的通用套路，代价是错误信息指向标准库内部、读起来不如手写的 static_assert 友好——这正是 C++26 允许动态生成 static_assert 消息要解决的问题。

8.3 高级（体现深度）

  1. 高级什么是 core constant expression？这套抽象机模型带来哪些必然的限制？

    它是标准对「这个表达式能不能被常量求值器算出来」的判定，定义方式是反向的——不列举允许什么，而是给一张「出现下列任一情况即不是常量表达式」的清单。这个反向定义很重要：语言的默认态度是「能解释的都解释」，每个新版本只是从清单里删掉几条。

    限制只有两个来源，归类之后就不用背了。一，抽象机没有外部世界：IO、系统调用、时间、随机数、volatile、内联汇编、调用没有可解释定义的函数、读运行期变量——除了「做不到」，还有一条更硬的要求是可重现，同一份源码两次编译必须给同一个答案。二，抽象机不容许 UB：越界、空指针 / 悬垂指针解引用、有符号溢出、除零、移位越界、读未初始化、访问 union 非活跃成员、reinterpret_cast。

    第二类不是编译器厂商的良心实现，而是符合性要求：标准直接规定「求值中出现会导致 UB 的操作则不是常量表达式」，任何合格编译器都必须诊断。

    这套归类还能用来预判：遇到一个新特性想知道能不能进 constexpr，先问「这件事能在一台没有操作系统、没有真实地址、必须两次给同一答案的机器上做吗」，基本不用翻标准。

  2. 高级字符串字面量怎么成为非类型模板参数的？为什么要求「结构化类型」这么严？

    做法是包一层：定义 template <std::size_t N> struct fixed_string { char data[N]; constexpr fixed_string(const char (&)[N]); };，配合类模板实参推导，就能写 Schema<"u8:id">。C++20 起允许「结构化类型」的字面量类作非类型模板参数，这条路才通。

    结构化类型的要求是：所有非静态数据成员都是 public 且本身是结构化类型、没有私有或受保护的非静态数据成员、没有可变引用成员。

    理由很硬：非类型模板参数需要模板等价性判定——编译器必须能回答「这里的 Schema<"a"> 和另一个 TU 里的 Schema<"a"> 是不是同一个类型」。只有当值的全部状态都可见、可以逐成员比较时，这个判定才是良定义的。一旦允许私有状态或用户自定义的相等语义，「相同」的含义就由用户代码决定了，而类型标识不能依赖用户代码的执行结果——否则 ODR、符号名修饰、跨 TU 的类型同一性全都失去基础。

    这也解释了为什么 std::string 永远不可能直接当模板参数：它有私有指针成员，而且那个指针的值还随分配位置变化。

  3. 高级要一张 64K 项的查表，你用 consteval 算，还是构建期生成 .cpp？怎么判断？

    64K 项这个规模基本就是构建期生成的地盘，判断依据有三条，而且都能量。

    一，常量求值的结果不跨 TU 缓存。这是最容易被忽略的放大器：一张放在头文件里的重量级 consteval 表，被 80 个 .cpp 包含就要被算 80 遍。单次 0.4 秒看着无害，乘完 32 秒，再乘 CI 上 4 个构建配置就是两分钟，而这两分钟出现在每一个 PR 上。

    二，编译器是解释器。同样的筛法，解释执行比 -O2 的机器码慢几个数量级；构建期那个小程序是编译好的原生代码，可能快上百倍，而且只跑一次、结果还能进构建缓存。

    三，看结果要不要参与类型系统。只有当表的内容需要当数组长度、模板实参或 concept 约束时，才必须在编译期算；如果它只是一份数据，生成的 .cpp 完全等价，而且可读、可 diff、增量编译友好。

    操作上：用 -ftime-trace（Clang）/ -ftime-report（GCC）量常量求值在总编译时间里的占比，改动前后各量一次全量构建。超过 10% 就搬走。反过来，小表（几百项）、逻辑纯、又想顺手拿 static_assert 校验不变量的，留在 consteval 里更好——省掉一整套代码生成的构建依赖。

  4. 高级if constexpr、if consteval、std::is_constant_evaluated() 三者在语义上有什么本质差异？

    它们问的是三个不同的问题，混起来用就会写出恒真恒假的分支。

    if constexpr 问的是类型层面的问题，在模板实例化时判定，未选中的分支不被实例化（但仍要语法正确、非依赖名仍要能查到）。它的用途是按类型裁剪代码，与「在哪执行」毫无关系。

    if consteval（C++23）问的是当前这次求值是否处在常量求值中。两个分支都会被编译，选哪条由这次求值的性质决定；true 分支里还可以调用 consteval 函数，这是它独有的能力。

    std::is_constant_evaluated()（C++20）回答同一个问题，但它是函数调用而不是语法结构，于是留下了那个著名的坑：写进 if constexpr 里恒为 true，else 分支被静默丢弃，运行期调用也走了编译期实现。

    所以结论是：按类型分叉用 if constexpr；按执行时机分叉，有 C++23 就用 if consteval，没有就用普通 if + is_constant_evaluated()，绝不要用 if constexpr 包它。典型场景是给同一个函数写两条实现：编译期走朴素算法（抽象机不认识 intrinsic），运行期走 __builtin_* 或 SIMD。
