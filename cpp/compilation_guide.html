② 阶段 2：编译（Compilation）

2.1 词法分析（Lexical Analysis / Tokenization） · 2.2 语法分析（Syntax Analysis / Parsing） · 2.3 语义分析（Semantic Analysis） · 2.4 中间…

工具：cc1plus / clang
输入：.ii
输出：.s

编译器内部六步：词法 → 语法 → 语义（含模板实例化）→ IR → 优化 → 出汇编。日常排障只需要记住：类型/重载/模板错误出在语义分析；-O2 才开始认真内联。

1词法字符 → Token
2语法Token → AST
3语义类型 / 模板
4IR平台无关
5优化-O0 … -O3
6代码生成IR → .s

2.1 词法分析

int count = 42; 被切成关键字 / 标识符 / 运算符 / 字面量 / 分号。拼写错误多半死在这一层。

2.2 语法分析

Token 流长成 AST。模板在树上只是「带类型参数的函数」，此刻还不生成机器码。

2.3 语义分析

检查失败长什么样
类型 / const / 访问控制int + string、const 对象被改、碰 private
名称查找 / 重载决议找不到声明，或 9 个重载对不上
模板实例化用到的那组参数才生成代码；没看到定义 → 链接期 undefined reference

模板：每个 TU 各自实例化一份

2.4 中间代码

AST 变成 LLVM IR / GIMPLE：与 CPU 无关、SSA 形式，后面的优化都在这层做。LTO 就是把这份 IR 留到链接期再优化。

2.5 优化

旗标目的判据
-O0不优化，好调试每个局部变量都能在 gdb 里看到
-O2日常发布内联 / 循环优化；体积尚可
-O3 / -Ofast再挤性能向量化；-Ofast 放松 IEEE
-Os体积优先嵌入式 / 下载包

2.6 目标代码生成

IR → 目标平台汇编。C++ 符号被 name mangling 编进参数类型（c++filt 还原）。GCC 5+ 双 ABI 会让 mangled 名对不上，表现为 undefined reference——细节见下文面试专题。

③ 阶段 3：汇编（Assembly）

目标文件的段结构 · 目标文件中的符号类型

工具：as
输入：.s
输出：.o

汇编器把助记符变成机器码，并写下符号表 / 重定位项。链接器稍后只看这些表，不再回头读源码。D 是已初始化全局量，B 是 BSS；排障时先分清 U 和 T 就够。

目标文件的段

段内容
.text / .rodata机器码、字符串常量
.data / .bss已初始化 / 未初始化全局量（bss 不占文件空间）
.symtab / .rel.text符号；需要链接器回填的调用点

用 nm 看 U 与 T

T = 本文件已定义的函数；U = 引用了但本文件没有，等别的 .o / 库来给。

④ 阶段 4：链接（Linking）

4.1 符号解析（Symbol Resolution） · 4.2 重定位（Relocation） · 4.3 段合并（Section Merging） · 4.4 库链接

工具：链接器（ld / lld / gold）
输入：多个 .o + 库文件
输出：可执行文件或共享库

4.1 符号解析

链接器把各 .o 的符号表并在一起：每个 U 必须找到恰好一个定义（T / D）。找不到 → undefined reference；找到多份强符号 → multiple definition（ODR）。静态库里「没人点名」的 .o 整份丢弃，靠全局 ctor 自注册的插件要用 --whole-archive（见面试题）。

动手玩：点击「开始解析」看链接器如何把每个未定义符号 U 连到某处的定义 T，并填入真实地址（重定位）。

待解析 (含未定义符号)
main.o

Tmain本地
提供定义 (符号来源)
YangAdapter.o
TsetWithXml0x4012
libm.so
Tsqrt0x7f3a
2 个未定义符号等待解析…

4.2 重定位

每个 .o 里的 call 先写占位。符号解析成功后，链接器把真实地址填回去——这就是重定位。段合并只是把各文件的 .text / .data 首尾相接。

4.3 段合并

最终映像 = 所有被选中的 .text + .data + .rodata。没被引用的静态库成员根本不会进来。

4.4 静态库只抽用到的 .o

类型何时解析体积 / 升级
静态库 .a链接期按成员抽取打进 exe；升级要重链
动态库 .so运行时 ld.so（默认可延迟）exe 小；替换 so（SONAME 兼容）

关键概念总结

概念一句话
翻译单元一个 .cpp 预处理后的完整内容，独立编译
ODR非 inline 符号全程序只能有一份定义

// a.cpp / b.cpp 都 #include "util.hpp"
// 链接：multiple definition of next_id()

面试深度专题 ⭐ — 编译链接进阶

1. ODR — One Definition Rule（单一定义规则） · 2. LTO / ThinLTO — 链接时优化 · 3. inline / constexpr / 模板 的链接行为 · 4. 静态库 vs 动态库 深度对…

站在高级 C++ 工程师视角，编译/链接的深度考点集中在：ODR、LTO、内联/模板的链接行为、动/静态库对比、Name Mangling 与 ABI 稳定性、常见链接错误诊断。

1. ODR — One Definition Rule（单一定义规则）

C++ 最基础也最易违反的规则：

  • 一个翻译单元内：每个变量/函数/类/模板/枚举 定义 只能出现一次
  • 整个程序：非 inline 函数和全局变量 定义 只能出现一次
  • 多个 TU 中：类、inline 函数、模板可重复定义，但必须逐 token 相同

违反 ODR 的典型场景（UB，链接器不一定报错）

// foo.hpp
struct Foo { int x; };

// a.cpp
#define DEBUG
#include "foo.hpp"   // 假设 hpp 里有 #ifdef DEBUG 改变布局

// b.cpp
#include "foo.hpp"   // 未定义 DEBUG —— Foo 在 a/b 中布局不同！UB

隐形 ODR 违反：-D 宏不一致、不同版本头文件、匿名命名空间 vs static、static library 版本混用。

检测：gold --detect-odr-violations、clang -fsanitize=odr、ThinLTO 偶发报告。

2. LTO / ThinLTO — 链接时优化

传统编译以单个翻译单元为优化边界：跨 .cpp 的函数无法内联、无法常量传播、无法死代码消除。

.cpp × N
→
编译器发 LLVM IR / GIMPLE-flto
→
链接器全程序优化跨 TU 内联 / DCE
选项作用代价
-flto (Full LTO)全程序合并成一个大 IR 再优化链接时间/内存暴涨，大项目不可用
-flto=thin (ThinLTO)每个 TU 独立 IR + 轻量跨 TU 导入增量/并行友好，Clang/LLD 推荐
-fuse-linker-pluginGCC LTO 需配合 gold/lld—

典型收益：纯 C++ 后台服务 5-15% 加速，包含大量模板/小函数的代码收益更高（跨 TU 内联）。

3. inline / constexpr / 模板 的链接行为

声明定义可在头文件？符号类型说明
void f();❌ 头只声明external定义必须在 .cpp，否则链接报 multiple def
inline void f(){}✅弱符号 (COMDAT)链接器按签名合并，任选一份保留
constexpr f(){}✅隐式 inline等同 inline
template<> T f(){}✅COMDAT 弱符号每个实例化按需合并
static void f(){}✅internal linkage每 TU 独立副本（代码膨胀）
namespace { void f(); }✅internal匿名命名空间等同 static（但支持模板）
C++17 inline 变量✅COMDAT全局单例不再需要 .cpp 放定义

关键点：inline 的链接语义比展开优化更重要——它告诉链接器允许多定义并合并。没有 inline 的函数放头文件会 multiple definition。

4. 静态库 vs 动态库 深度对比

维度静态库 (.a)动态库 (.so)
链接时机链接时复制进可执行文件运行时 ld.so 加载
符号解析按归档成员按需抽取（未引用不链入）整个 so 全载入
符号顺序⚠️ 依赖顺序敏感：-lA -lB，A 引用 B不敏感
可执行体积大（打包所有依赖）小（共享）
ABI 升级重编译全程序替换 .so 即可（若 SONAME 兼容）
符号冲突链接期报错按加载顺序解析，可能静默覆盖（LD_PRELOAD 原理）
初始化/析构随进程启停__attribute__((constructor))/dlopen 时机

动态库的隐形坑：

  • SONAME vs filename：libfoo.so.1 是 SONAME（ABI 版本），libfoo.so.1.2.3 是实际文件，libfoo.so 是 devel 软链
  • 全局符号污染：默认所有 extern 符号可见，应显式 -fvisibility=hidden + __attribute__((visibility("default")))
  • C++ 静态对象析构顺序跨 so 不保证，易 crash

5. Name Mangling 与 ABI 稳定性

C++ 函数重载、模板、命名空间都通过 name mangling 编码进符号名。GCC/Clang 使用 Itanium C++ ABI。

// 源代码
namespace ns { int foo(int, const std::string&); }

// mangled
_ZN2ns3fooEiRKSs            // GCC < 5, old ABI
_ZN2ns3fooEiRKNSt7__cxx1112basic_stringIcSt11char_traitsIcESaIcEEE  // GCC ≥ 5, C++11 ABI

// 还原
c++filt _ZN2ns3fooEiRKSs   // → ns::foo(int, std::string const&)

GCC 5+ Dual ABI — 经典坑

GCC 5 为了支持 C++11 的 std::string/std::list 标准（SSO、O(1) size），引入 双 ABI：

  • _GLIBCXX_USE_CXX11_ABI=1（默认）：新 ABI，命名空间 std::__cxx11
  • _GLIBCXX_USE_CXX11_ABI=0：旧 ABI，兼容 GCC 4

两种 ABI 编译的 .o 链接会 undefined reference——因为 mangled 名不同。解决：统一宏；或 extern "C" 接口隔离。

为什么 C 没有这些问题：C 无重载、无模板，函数名直接就是符号名，ABI 极其稳定（几十年不变）。

7. 高频面试题 Q&A

点击每道题展开参考答案（先自测，再对照）。

  1. 基础#pragma once vs #ifndef 头文件保护？

    功能等价。#pragma once 更简洁、避免 macro 重名，但依赖编译器识别同一物理文件（符号链接/同一文件不同路径可能失败）。#ifndef 标准但 macro 可能冲突。现代项目优先 #pragma once，所有主流编译器都支持。

  2. 基础为什么模板的定义必须放在头文件？

    模板不是代码，是代码生成器。编译器在实例化点才知道具体类型，需要看到完整定义。若模板定义在 a.cpp，b.cpp 想用 Foo<int>，b.cpp 的编译器根本看不到定义，链接器也不会生成——会 undefined reference。

    例外：显式实例化 template class Foo<int>; 放 a.cpp，此时 a.o 会生成该符号，b.cpp 声明 extern template class Foo<int>; 避免重复实例化。

  3. 基础extern "C" 的真正作用？

    告诉 C++ 编译器对这块声明禁用 name mangling，使用 C 风格符号名。用途：

    • C++ 写库给 C 调用（.so 导出符号）
    • C++ 调 C 库的头文件（extern "C" { #include <pthread.h> }，C 头通常自带 #ifdef __cplusplus 包裹）
    • 绕过 ABI 不稳问题（C ABI 超级稳定）

    限制：extern "C" 函数不能重载（同名 mangling 冲突）、不能是成员函数、不能是模板。

  4. 高级静态库里的全局对象构造函数不被调用？

    经典坑。链接器对静态库按需抽取——某 .o 里的符号如果主程序没引用，该 .o 整个不被链入，连带它的全局对象构造也消失。

    场景：注册模式（全局对象构造时调 Factory::Register(...)），静态库里没人直接 new 这个类 → 被优化掉。

    解决：

    # 强制链入整个归档
g++ main.o -Wl,--whole-archive -lplugin -Wl,--no-whole-archive
# 或 clang
clang++ main.o -Wl,-force_load,libplugin.a
  5. 中级为什么要用 -fvisibility=hidden？

    Linux .so 默认导出所有 extern 符号——产生三大问题：

    1. 符号冲突：多个 .so 里同名 inline 函数，加载时首个 so 的版本赢（ODR 幽灵违反）
    2. 加载慢：ld.so 要解析巨量符号
    3. 二进制体积：symbol table 膨胀

    最佳实践：

    g++ -fvisibility=hidden -fvisibility-inlines-hidden ...

// 需要导出的 API 显式标记
#define API_EXPORT __attribute__((visibility("default")))
API_EXPORT void publicFunc();
  6. 中级什么是弱符号 / strong symbol？

    ELF 符号有强度：

    • 强符号：普通函数、已初始化的全局变量
    • 弱符号：inline 函数、模板实例（COMDAT 组）、未初始化全局变量（C 老语义）、__attribute__((weak))

    规则：多强符号冲突 → 报错；强弱冲突 → 强胜；多弱冲突 → 任选。这是 inline 函数可以出现在多个 TU 的底层机制。

  7. 高级RTTI 与 exception 跨 so 有什么坑？

    RTTI 的 typeid 和 dynamic_cast 跨 so 比较的是 type_info 的指针（旧）或 mangled name 字符串（新）。若：

    • 两个 so 都静态链 libstdc++ → 各自有独立 type_info 拷贝 → dynamic_cast 失败
    • 异常抛出后跨 so 边界 catch → 若 type_info 不同，catch 不到

    解决：动态链 libstdc++（默认），或导出关键类型的 RTTI 符号（-fvisibility=default for typeinfo）。

  8. 中级为什么 precompiled header (PCH) 能加速编译？

    C++ 编译慢的主因是头文件重复解析。典型项目：<vector>、<string>、Boost、自家公共头——每个 .cpp 都要重新解析一遍，展开数十万行。

    PCH 把这些公共头预先编译成二进制 AST，每个 .cpp 编译时直接加载，跳过词法/语法/语义分析前端。大型项目可加速 20-50%。

    配合技巧：

    • CMake 3.16+：target_precompile_headers(tgt PRIVATE <string> <vector>)
    • Unity Build（把多个 .cpp 合并编译）进一步加速，但影响调试和增量编译
    • ccache：编译结果缓存，CI 环境命中率可达 90%+

L2. Symbol Visibility

档导出？用途
default是，可被覆盖公共 API（Linux 默认）

g++ -fvisibility=hidden -fvisibility-inlines-hidden -c api.cpp

API void public_api();   // 进 .dynsym
void impl();              // 不导出。判据：nm -D lib.so

开 hidden 是为了三件事：同名 inline 不再被先加载的 so 抢走、ld.so 少解析几千个符号、编译器敢对内部函数做更狠的内联。nm -D 只该看到 API。更细的版本化导出用 --version-script（glibc / OpenSSL）；CMake 对应 CXX_VISIBILITY_PRESET，见 CMake。

L3. 弱符号

inline / 模板是自动弱符号（COMDAT）：多 TU 各生成一份，链接器留一份。未初始化全局变量在 C 里也是弱的，C++ 不要靠这个。

L4. 链接器优化开关

常用项已收进 §8 旗标表。--gc-sections 会误删「没人引用、只靠全局 ctor 注册」的对象——用 __attribute__((used)) 或 linker script KEEP()。

L5. 全局对象初始化顺序

同一 TU：声明序构造、逆序析构。跨 TU / 跨 .so：标准不保证（SIOF）。修法：函数内 static（Meyers Singleton，C++11 起线程安全），不要在别的全局 ctor 里碰它。

典型事故：libplugin.so 的全局对象在 ctor 里写 libcore.so 的 Logger，但链接顺序让 plugin 先初始化 → Logger 还是零页 → 段错误。Debug 碰巧顺序对，Release 才炸。跨 so 只能靠按需构造，init_priority 只管同一 so。

L8. 服务端的二进制体积治理

「体积只有嵌入式才在乎」是个过时的印象。服务端一个 800 MB 的二进制会在三个地方收费：容器镜像分发（每次发版乘以节点数）、动态链接启动耗时（符号表越大重定位越久，对滚动升级的 P99 直接可见）、调试符号的存储。而且它通常不是一次长上去的，是几年里每次多链一个库堆出来的。

手段典型收益代价 / 注意
-fvisibility=hidden + -fvisibility-inlines-hidden动态符号表常能砍掉一大半，连带加快启动要导出的符号必须显式标 __attribute__((visibility("default")))，漏标就是运行期 undefined symbol
version script（--version-script）精确控制导出面，比 visibility 更细需要维护一份符号清单，但这本来就是稳定 ABI 的应有之义
-ffunction-sections -fdata-sections + --gc-sections删掉未引用的函数与数据见 L4：靠全局 ctor 注册的对象会被误删，要 KEEP() 或 used
拆分调试信息（objcopy --only-keep-debug + --add-gnu-debuglink）发布件瘦身最显著的一招，且不损失可调试性要建符号服务器，崩溃分析时按 build-id 取回
-Os / -Oz（仅冷代码）冷路径体积换性能别全局开；热路径仍要 -O2/-O3
模板实例化收敛（extern template）去掉 N 个 TU 里的重复实例见 模板 §7.1
静态库改动态、或反过来取决于部署形态多进程共享同一 .so 才省；单体容器里静态链接反而更省事

诊断顺序建议固定成这三步：size -A 看段分布（先确认到底是代码段大还是调试信息大，这一步能排掉一半的误判）→ nm --size-sort -S 找最大的那些符号 → bloaty 按编译单元和模板归因。先归因再动手，否则很容易花一天开了一堆旗标、只减了 2%。

这一节讲的是「发布件为什么这么大、怎么砍」。让构建过程本身变快是另一件事（IWYU、PCH、ccache、Unity Build、-ftime-trace），见 大型 C++ 工程化 §11；跨语言边界上导出面怎么设计，见 跨语言互操作。
