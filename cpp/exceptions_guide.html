throw / try / catch 基础

三段式语法 · catch 匹配规则 · 重新抛出 · 嵌套异常 (C++11)

2.1 三段式语法

try 包可能失败的操作；catch 从上到下取第一个匹配（不是虚函数那种最具体）。派生类写上面，catch (...) 垫底。

2.2 catch 匹配规则

写法匹配坑
catch (const T&)T 及其派生，零拷贝推荐
catch (T)按值拷贝切片，丢多态
基类引用派生对象也能进基类写前面 → 派生 catch 死代码
catch (...)任意类型拿不到 what()；不重抛等于吞错

匹配不做用户定义转换。顺序错了编译器会警告，别靠警告当设计。

2.3 重新抛出与切片

throw; 重抛当前异常对象，动态类型还在。throw e; 按静态类型再构造一份 → 派生字段全部丢掉。

2.4 嵌套异常 (C++11)

API作用判据
throw_with_nested(E)把当前异常包进新异常再抛模块边界加上下文（路径、请求号）
rethrow_if_nested(e)若 e 带 nested 则再抛内层顶层打印完整链
nested_exception混入类，持有 exception_ptr标准异常都能套

栈展开 (Stack Unwinding) 机制详解 ⭐

概念 · 完整流程图 · 关键点：异常对象在哪里？ · ABI 层面：Itanium C++ ABI · throw + 栈展开的简化伪代码

4.1 概念

抛出后运行时沿调用栈回退，直到匹配的 catch。每一帧的局部对象按构造逆序析构——这就是 RAII 能在「你什么都不写」时仍释放锁和内存的原因。裸 new / 手动 lock() 没有对象可析构，展开等于泄漏。

4.2 栈展开与析构

▶ 交互式演示：异常抛出后，栈如何"逐帧展开"
h() 抛出异常，运行时沿调用栈回退，逐帧析构每个局部 RAII 对象，直到 main() 的 catch 接住它。生活化类比：像下楼时逐层关灯锁门（析构），一直退到有人接应（catch）的楼层。

try { ... } catch (std::exception& e)

~Logger()

~lock_guard()

步骤 0 / 6

4.3 关键点：异常对象在哪里？

不能放普通栈——展开会把它拆掉。libstdc++ / libc++ 放在线程局部异常区（动态分配）；MSVC 拷到 catch 旁的临时区。所以异常类拷贝构造必须 noexcept：分配完再抛，只能 terminate。

4.4 ABI：Itanium 与跨 .so 边界

组件作用
__cxa_throw分配 header + 对象，调 unwind
_Unwind_RaiseException真正走栈
.eh_frame每函数 DWARF CFI
.gcc_except_table (LSDA)PC 范围 → 析构 / catch
__cxa_begin_catch / end_catch进出 catch

「零开销」的关键：析构点写在表里，不在每个入口埋 setjmp。

4.5 throw 之后若没人接

__cxa_throw 在 unwind 返回时（没有 landing pad）直接 std::terminate()。默认 abort()。安装 set_terminate 只能记日志，不能恢复——进程已经没契约了。

异常对象的生命周期

时间轴 · std::current_exception / rethrow_exception

5.1 时间轴：拷贝还是移动

5.2 std::current_exception / rethrow_exception

C++11 起可以把异常对象存成引用计数指针，跨线程或延迟处理。std::async / future::get 内部就是这个。

// 工作线程把异常带到主线程
std::exception_ptr g_eptr;

void worker() {
    try {
        do_work();
    } catch (...) {
        g_eptr = std::current_exception();    // 抓住异常
    }
}

void main_check() {
    if (g_eptr) {
        try { std::rethrow_exception(g_eptr); }
        catch (const std::exception& e) {
            LOG_ERROR("worker failed: {}", e.what());
        }
    }
}

// std::async / std::future 内部就是这种实现
auto fut = std::async([]{ throw std::runtime_error{"x"}; });
try { fut.get(); }                          // 重新抛出
catch (const std::exception& e) { /* ... */ }
std::exception_ptr 是引用计数的 → 拷贝便宜，多个线程可共享。是跨线程异常传递的标准方式。

异常安全 3 级保证 ⭐⭐⭐ (面试必答)

basic guarantee 示例 · strong guarantee 示例 — copy-and-swap 惯用法 · nothrow guarantee — swap / 移动构造的责任 · 经典案例对比

异常安全说的不是「会不会抛」，而是抛了之后对象留在什么状态。

▶ 交互式演示：同一个 s = newValue; 赋值，为什么"写法顺序"决定异常安全级别
左边是朴素写法（先删旧再分配新），右边是 copy-and-swap（先在旁边备好新的，再一步交换）。打开下面的开关注入异常，单步对比两者的差别。
💥 注入异常：内存分配 new 失败（抛 bad_alloc）—— 当前：关
❌ 朴素写法（basic 都难保证）
delete[] data_; data_ = new char[n]; ...
✅ copy-and-swap（strong 强保证）
Buffer& operator=(Buffer rhs){ swap(rhs); return *this; }
步骤 0

6.1 每种保证一份对照

档写法要点抛了之后
无保证先 delete[] data_ 再 new悬空指针，析构 double-free
basicunique_ptr 持有新节点再链接不泄漏；容器长度可能已变
strong先在旁边构造完整副本，再 noexcept swap*this 一个字节都没动
nothrowswap / 移动构造标 noexcept不允许失败；说谎就 terminate

6.2 strong — copy-and-swap

class Buffer {
    char* data_;  size_t size_;
public:
    void swap(Buffer& o) noexcept {
        using std::swap;
        swap(data_, o.data_); swap(size_, o.size_);
    }

    // strong guarantee: copy-and-swap
    Buffer& operator=(Buffer rhs) {        // ① 按值收 — 拷贝在参数构造时发生
        swap(rhs);                              // ② 不抛 — 真正"提交"
        return *this;
        // ③ rhs 出作用域析构旧的资源
    }
};
// ✅ 如果 ① 抛异常 → *this 完全不变
// ✅ ② noexcept → 一旦走到这里，操作必然成功

6.3 nothrow — swap / 移动构造

容器扩容用 move_if_noexcept：移动构造是 noexcept 才敢掏空旧元素。否则退化为拷贝——慢，但旧缓冲始终完好。说谎标 noexcept 再抛，vector 无法回滚，直接 terminate。见图 §8。

6.4 把 basic 升到 strong

operator+= 若先改 *this 再分配，失败就是 basic 甚至无保证。正确顺序：新缓冲全部就绪（拷贝旧数据 + 追加），最后才 delete[] 旧指针——所有抛点都在修改前。copy-and-swap 把这个顺序固化成惯用法。

RAII —— 异常安全的基石

RAII 三件套 · 经典对比 · 自定义 RAII guard（scope guard 模式）

Resource Acquisition Is Initialization：资源生命周期绑到对象生命周期。展开会调析构，所以锁和文件在异常路径上自动释放。

7.1 RAII 三件套

资源RAII 类
动态内存unique_ptr / shared_ptr
互斥锁lock_guard / unique_lock / scoped_lock
文件fstream / ofstream
fd / 句柄自己写包装，析构 noexcept 里 close

7.2 经典对比

// ❌ 不用 RAII — 异常会泄漏锁 + 内存
void bad() {
    mu.lock();
    auto* p = new Foo;
    do_something(p);    // 抛异常 → mu 没解锁 + p 没 delete
    delete p;
    mu.unlock();
}

// ✅ RAII — 异常自动释放
void good() {
    std::lock_guard lk{mu};
    auto p = std::make_unique<Foo>();
    do_something(p.get());
    // 离开作用域 (正常或异常): p 析构 → delete; lk 析构 → unlock
}

7.3 scope guard

需求做法坑
作用域结束必做一事析构里调回调（ScopeExit / C++23 scope_exit）回调必须 noexcept 或内部吞异常
事务回滚先登记 rollback，成功再 dismiss()rollback 自己不能抛
手动 try/finallyC++ 没有 finally漏一条路径就泄漏

所有「离开作用域必须发生」的事（解锁、close、回滚）都交给对象，不要手写对称的 lock/unlock。

noexcept 关键字

两个含义 · 哪些函数应该是 noexcept · 哪些场景受益 · 抛了 noexcept 函数会怎样 · noexcept 与函数指针

8.1 两个含义

形态意思违反
说明符 void f() noexcept承诺不抛运行时 terminate，不展开
noexcept(true/false)条件承诺同左
运算符 noexcept(expr)编译期查询声明查的是声明不是实现

条件写法：noexcept(noexcept(T(std::move(a))) && noexcept(a = std::move(b))) —— swap 只在 T 的移动也不抛时才标不抛。

8.2 哪些函数应该是 noexcept

析构（默认就是）、移动构造/赋值、swap、平凡 getter。不要给「内部会 new / 会调用户代码」的函数随手贴。

8.3 noexcept 如何毁掉强保证

vector 扩容要保强保证：搬一半失败时旧缓冲必须还能用。若移动可能抛，它只能拷贝（旧的完好）。你把移动标成 noexcept，它就敢掏空旧槽——此时再抛，两边都是残骸，只能 terminate。

09

构造 / 析构中的异常

构造函数抛异常 · function-try-block — 构造函数初始化列表的异常 · 析构函数中的异常 — 几乎一律不抛 · 正确的析构错误处理

9.1 构造函数抛异常

对象没构造完 → 自身析构不调用。已构造的成员和基类按逆序析构。因此构造里拿到的资源必须立刻交给成员 RAII，不能先裸 new 再在函数体里塞进指针。

struct A { A() { LOG("A"); } ~A() { LOG("~A"); } };
struct B { B() { LOG("B"); throw 1; } ~B() { LOG("~B"); } };
struct C { C() { LOG("C"); } ~C() { LOG("~C"); } };

struct X {
    A a;
    B b;        // 抛
    C c;
};

// X x;
// 输出: A B ~A — c 没构造，X 析构没执行

9.2 function-try-block

普通函数体里的 try 抓不到初始化列表里的异常。构造函数要写成 X(int v) try : a_(v), b_(v) { } catch (...) { throw; }。

9.3 析构几乎一律不抛

C++11 起析构默认 noexcept。栈展开时再抛 → 两个异常 → terminate。要抛必须显式 noexcept(false)，生产代码不要走这条。

9.4 析构里的错误

做法对不对原因
析构里 throw 表示 flush 失败❌展开中再抛 terminate
公开 flush() 抛异常；析构尽力 fflush + 记日志✅调用方能处理；析构只兜底
析构 catch (...) 吞掉后 close✅永不逸出

异常 vs 错误码 vs std::expected

三种风格对比 · 经验法则 (Google C++ Style 的做法很激进，C++ 社区分歧) · 反模式：用异常做控制流

怎么选

10.1 三种风格

10.2 经验法则 (Google C++ Style 的做法很激进，C++ 社区分歧)

用异常

  • 真正的异常情况（罕见 + 严重）— 内存不足 / 配置错 / 网络致命错
  • 构造函数失败（构造没法返错误码）
  • 跨多层调用栈传递错误
  • 错误是少数路径，主路径希望干净

用错误码 / expected

  • 可预期的失败（"缓存 miss" "key 不存在"）— 正常控制流
  • 性能敏感的热路径
  • 嵌入式 / 关闭异常的环境 (-fno-exceptions)
  • 与 C API 边界
  • 调用方必然要做错误处理

10.3 反模式：用异常做控制流

在树里 throw node 当 break：慢、难读、展开表为「正常路径」付体积。查找 miss、缓存 miss、解析失败都是预期结果，用返回值 / optional / expected。

10.4 第四类：契约违约根本不是「错误」

上面三种风格争的都是「怎么传递错误」。但有一类情况不该传递——调用方违反了函数的前置条件。vector::operator[] 越界、传了空指针给一个文档写明「不接受 null」的参数，这些不是运行期的意外，是代码里有 bug。把它包装成 expected 返回给调用方，等于让一个已经写错的程序继续跑下去。

类别例子谁的责任该用什么
预期结果查找 miss、缓存未命中、可选字段缺失没人错optional / 返回值
可恢复错误文件打不开、网络超时、解析失败环境expected 或异常
契约违约越界下标、空指针实参、未满足的不变量调用方的 bugassert / contracts，不要 catch
不可恢复内存耗尽、栈溢出、关键不变量已损坏无解terminate，尽快死

把第三类和第二类混在一起，是错误处理设计里最常见的一个结构性错误：它让「有 bug」和「环境不好」走同一条恢复路径，于是真正的 bug 被 catch 吞掉、记一条日志、继续跑——而程序此刻的状态已经不可信了。

assert 作为契约工具有三个真实缺陷。其一，NDEBUG 下它整个消失，包括里面表达式的副作用——assert(pop() == 3) 在 Release 下连 pop() 都不会执行，这是经典事故。其二，不能分级：便宜的检查和昂贵的检查只有「全开」和「全关」两档，而生产环境往往想保留前者。其三，违约行为写死为 abort，无法统一改成「记录遥测再退出」。

C++26 的 Contracts（P2900）正是冲这三条来的。它把前置条件、后置条件、断言变成声明的一部分：

int at(const std::vector<int>& v, std::size_t i)
    pre (i < v.size())            // 前置条件：属于接口，调用方可见
    post(r: r == v[i])            // 后置条件：可以引用返回值
{
    contract_assert(!v.empty());  // 函数体内的断言
    return v[i];
}

关键不在语法，而在它解决了上面三条：

  • 求值语义是编译期可选的三档——ignore（不检查）、observe（检查、报告、继续执行）、enforce（检查、报告、终止）。observe 这一档是 assert 从来没有的：可以在生产环境先「只观察不杀进程」，收集真实违约率，再决定是否收紧。
  • 违约处理器可替换，能接到自己的遥测/日志系统，而不是硬编码 abort。
  • 前置条件写在声明上，所以它是接口的一部分而不是实现细节，调用方和文档工具都能看到。
但有一条纪律必须说清：契约违约不是异常，不要试图 catch 它来「恢复」。违约意味着程序已经处于设计时认为不可能的状态，继续执行的每一步都建立在错误假设上。observe 模式允许继续执行，那是为了灰度期收集数据，不是一种恢复策略——它的正确用法是「先观察两周，确认没有误报，再切到 enforce」。

在 C++26 落地之前，能立刻做的是：把 assert 分成两个宏（廉价的在 Release 保留、昂贵的只在 Debug 开），并且永远不要在 assert 的表达式里放副作用。

REAL真实工程 · 5 个实战

platform agent 启动 — 异常分层处理 · schema解析 — nested exception 链 · RPC 处理 — 用 expected 而不是异常 (热路径) · 资源管理 — 完整 RAII …

13.1 platform agent 启动

main 只 catch：配置错误返回 2，其余 exception 返回 1，... 垫底。业务异常在事件循环内部消化，不要漏到进程顶。

13.2 schema 解析 — nested 链

底层 IO/语法错用 throw_with_nested 包成带路径的外层异常。顶层递归 rethrow_if_nested 打出完整链：外层有路径，内层有行号。

13.3 RPC 热路径用 expected

Timeout / Refused / BadRequest 是请求级预期失败，不要 throw。返回 expected<Reply, RpcErr>，调用方按有值/有错分别回包。

13.4 资源类

C API 半打开（sqlite3_open 失败仍可能返回 handle）要在 throw 前手动 close，成功后再交给 unique_ptr。事务：BEGIN → scope guard ROLLBACK → 成功再 COMMIT + dismiss。

13.5 跨线程

worker 的异常经 future::get 重抛。多个 future 收集 exception_ptr，一个直接 rethrow，多个合成聚合错误。线程入口本身仍要 catch，防止漏网 terminate。代码见 §5.2。

15

面试题集（20 道分层）

基础 · 中级 · 高级 · 速答示范（第 7 题）

点击每道题展开参考答案（先自测，再对照）。

15.1 基础

  1. 基础throw / try / catch 工作流程?
    流程
    throw 构造异常对象并开始栈展开：从抛出点向外逐层析构已构造的局部对象，沿调用栈寻找类型匹配的 catch；找到则执行处理器，全程无匹配则 std::terminate。
  2. 基础std::exception 类层次? 常用派生类?
    基类
    std::exception（提供 what()）。
    两大支
    logic_error（invalid_argument / out_of_range / length_error / domain_error）、runtime_error（range_error / overflow_error / system_error）；另有 bad_alloc / bad_cast 等。
  3. 基础什么是栈展开?
    定义
    异常传播时，从抛出点到捕获点之间已完成构造的自动对象按逆序析构、栈帧释放。这正是 RAII 生效的底层机制。
  4. 基础异常对象的生命周期?
    周期
    在 throw 处构造（存于实现保留的安全区域），传播期间存活，直到对应 catch 块结束（或 rethrow）才销毁。catch (const E&) 引用的就是它本身。
  5. 基础throw vs throw e 区别?
    throw;
    在 catch 内重新抛出当前异常，保留动态类型（多态）。
    throw e;
    抛出 e 的拷贝，发生切片，丢失派生类型。
  6. 基础catch by value vs by reference?
    by value
    拷贝 + 可能切片，丢多态。
    by reference
    const E&：无拷贝、保留多态类型，推荐。

15.2 中级

  1. 中级异常安全 3 级保证分别是什么? 举例。
    basic
    即使抛异常也不泄漏资源，对象处于合法但未指定状态（如 vector::push_back 失败）。
    strong
    事务性：要么成功，要么状态完全不变（copy-and-swap 实现的 operator=）。
    nothrow
    标 noexcept 承诺不抛（swap、析构、移动构造）。完整示范见 §15.4。
  2. 中级什么是 RAII? 与异常安全什么关系?
    RAII
    资源获取即初始化，析构自动释放。
    关系
    栈展开会自动调析构 → RAII 是实现异常安全（basic 保证）的根本手段，免去手写 try/catch 清理。
  3. 中级noexcept 的两个含义?
    说明符
    声明函数不抛（违反则 terminate）。
    运算符
    编译期查询表达式是否 noexcept，用于条件 noexcept(...) 与 move_if_noexcept。
  4. 中级构造函数抛异常 → 析构会被调用吗?
    自身
    该对象自己的析构不调用（未构造完成）。
    成员
    已构造完成的成员 / 基类会被逆序析构。因此构造中获取的资源应交给成员 RAII 管理。
  5. 中级析构函数能抛异常吗? 后果?
    后果
    析构默认 noexcept；若在栈展开期间再抛 → std::terminate。
    规则
    析构绝不让异常逸出（内部 try/catch 吞掉或记录）。
  6. 中级copy-and-swap 惯用法如何实现强异常安全?
    机制
    operator=(T rhs) 按值收参（拷贝可能抛，但发生在改 *this 之前），再 noexcept swap。任何抛异常都在原对象被修改前 → 原对象完好 = 强保证，且天然自赋值安全。

15.3 高级

  1. 高级异常的"零开销"是什么意思? 真的零开销吗?
    含义
    指不抛异常时正常路径无运行时开销（table-based 模型，无标志位查询）。
    代价
    转移到抛出时（解析展开表，很慢）+ 二进制体积（展开表）。所以"正常路径零开销、抛出路径昂贵"。
  2. 高级异常是怎么实现的 (ABI 层面)?
    Itanium EH
    编译器为每个函数生成 LSDA + unwind table（.eh_frame / .gcc_except_table）。
    抛出时
    libunwind + personality routine 解析表，逐帧执行 landing pad（析构局部对象）并匹配 catch。抛出前无任何运行时栈成本。
  3. 高级std::move_if_noexcept 怎么工作?
    逻辑
    若 T 的移动构造为 noexcept → 返回 T&&（移动）；否则返回 const T&（拷贝）。vector 扩容靠它在"移动可能抛"时退回拷贝以保强异常安全。
  4. 高级std::exception_ptr 用在什么场景?
    用途
    用 current_exception() 捕获并存储 / 转移异常，跨线程、跨边界传播（promise::set_exception / async），延后用 rethrow_exception 重抛。
  5. 高级std::expected vs 异常 — 怎么选?
    expected
    可预期、高频失败（解析、查找）：无展开开销、显式体现在返回类型，适合热路径 / 禁异常环境。
    异常
    真正异常情形、构造失败、需穿越深调用栈时。
  6. 高级function-try-block 与普通 try 区别?
    区别
    function-try-block 把整个函数体（含构造函数初始化列表）包进 try，能捕获成员 / 基类初始化时抛出的异常 —— 普通 try 覆盖不到初始化列表。
    约束
    构造函数的 function-try 中必须重抛（不能吞掉）。
  7. 高级跨线程怎么传递异常?
    做法
    工作线程 catch 后用 current_exception() 存入 exception_ptr（或 promise 的共享状态），主线程 rethrow_exception 重抛。std::async / future 自动做这件事。
  8. 高级为什么 vector::push_back 强异常安全保证依赖移动构造 noexcept?
    原因
    扩容需把旧元素搬到新缓冲区。移动若可能抛、搬到一半抛 → 旧缓冲区已被破坏、无法回滚。只有移动 noexcept 才用移动且仍保强保证，否则退化为拷贝（旧数据完好）。

15.4 速答示范（第 7 题）

问：异常安全 3 级保证分别是什么? 举例。

答：

  • basic guarantee (基本保证)：即使抛异常，不泄漏资源，对象处于合法但未指定状态。例如 std::vector::push_back 在 T 拷贝构造抛异常时：vector 长度可能改变，但不崩、不泄漏。
  • strong guarantee (强保证)：操作具事务性 — 要么成功，要么状态完全不变（rollback）。例如copy-and-swap 实现的 operator=：先拷贝构造，再 noexcept swap，任何抛异常都发生在 swap 之前 → 原对象不受影响。
  • nothrow guarantee (不抛保证)：函数标 noexcept，承诺不抛。例如 swap、所有析构、移动构造（应该）。

"无保证" = 反模式，避免。

实战中：所有公开接口至少 basic 保证；关键事务性操作 strong；析构和 swap nothrow。
