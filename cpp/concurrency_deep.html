01

线程 vs 协程

内核调度的执行流，对用户态状态机

操作系统线程有独立栈，由内核调度、可被抢占；C++20 协程是编译器生成的状态机，co_await 只切这台状态机，不进内核。不要把 std::jthread 和 coroutine 当成同一种「轻线程」。能并行的是核，不是你 new 出来的线程数。用户态调度见 协程。

默认栈在 Linux 常是 8 MiB，按请求数 new thread 会先把虚拟地址和调度器打满。任务多就用线程池复用 worker。std::thread 若 detach，生命周期和栈上对象脱钩，bug 从析构 terminate 变成 use-after-return。需要用户态让出而不占核，才是协程的场景。

线程像雇来的工人：每人一套工具箱（栈），工头（内核）决定谁上工位（CPU）。协程像同一人手里的多份待办清单：做不下去就夹个书签换下一份，人没换、工位没换。

std::thread 析构时若仍 joinable，直接 std::terminate。C++20 jthread 把 join 做成 RAII，并带上停止通道：

std::jthread worker([](std::stop_token st) {
  while (!st.stop_requested()) do_work();
});  // 析构：request_stop() + join()，不再 terminate

1.1 一条线程的真实成本账

「线程贵」贵在哪、贵多少，决定了你该在多细的粒度上并行。账分三段：创建一次的、一直占着的、每次切换的。

成本项量级（x86-64 Linux）备注
创建 / 销毁10–30 μsclone + task_struct + 调度器入队
用户栈默认 8 MiB 虚拟预留按页 fault 进来，但一万条线程就是 80 GiB 地址空间
内核栈16 KiB 真实物理内存不会因为「没用到」而省掉
上下文切换直接成本 1–3 μs存寄存器 + 切页表 + TLB 失效
切换的余波常是直接成本的几倍L1/L2 被新线程冲刷，切回来全是 cold miss，profiler 里看不见

判据：单个任务的执行时间要远大于一次上下文切换，经验上是百微秒量级。这就是「一请求一线程」在 QPS 上万时必崩的原因——请求本身只要 20 μs CPU，线程数却跟着请求数走。上界则看线程在等什么：CPU 密集取核数，阻塞 IO 密集可超配几倍，天花板是内存而不是 CPU。

1.2 协程省掉的是哪一部分

协程不是「更便宜的线程」，而是有选择地省掉上面几项。一次 co_await 挂起 = 把活跃变量存进 coroutine frame 加一次间接跳转，几十纳秒，不进内核、不切页表，cache 还是热的。

维度OS 线程C++20 协程
切换μs 级，含 syscall 与 TLB 失效ns 级，一次返回加跳转
栈独立栈，MiB 级虚拟预留帧在堆上，只存活跃变量，百字节级
谁决定下一个跑谁内核，可抢占你写的调度器，不可抢占
能否吃多核能不能，仍要分发到多条线程上
撞上阻塞 syscall本线程睡，其它照跑整条载体线程卡住，上面所有协程陪葬
最后一行是协程最常见的翻车点：协程里调了同步 read()，它不会「只让当前协程等」，而是把整个 event loop 线程钉住。这个「栈上不许阻塞」的约束会传染给你依赖的每一个库。
02

数据竞争

无同步的共享写是 UB，不是「偶尔读到旧值」

数据竞争 = 两个线程访问同一内存、至少一个写、中间没有 happens-before。C++ 把它定义为 UB：优化器可以假设它永不发生，于是把后面的代码一并优化没。单核也会——抢占就够。闸门是 TSan，不是多跑几次单测。

x++ 看起来是一句话，机器上是 load-add-store 三步，中间任意点可被抢占。volatile 只挡编译器优化，不建立 happens-before，不能当锁。TSan 报的是「缺少同步关系」，不必真撞上那一拍——这是它比「多跑几次」值钱的原因。

内存序是「如何建立 happens-before」。六档语义、MESI、false sharing、CAS / ABA / RCU 见 内存模型（从 单核数据竞争、MESI、无锁回收 进）。本页不贴 memory_order_* 代码墙。

2.1 数据竞争 ≠ 竞态条件

中文都叫「竞争」，层次却不同。数据竞争是语言层的机械判定（同一地址、至少一写、无 happens-before），后果是 UB；竞态条件是逻辑错误，指结果依赖执行时序，标准对它没有任何意见。两者可以各自单独出现。

有数据竞争无数据竞争
有竞态条件最常见：两线程裸 x++，既 UB 又丢更新「查了再用」：if (!m.count(k)) m.insert(k, v); 每步都持锁，两个线程却都能通过检查
无竞态条件两线程写同一个值——标准照样判 UB，不认「反正值一样」目标状态

右上角那格最难查：TSan 一声不吭，因为确实每次访问都持锁了。错在不变量的边界画错了——「检查」和「使用」被拆进两个临界区，只能靠人推理。左下角那格则提醒反面：别用「反正只是个统计计数器」给裸共享写开脱，标准不承认「良性竞争」。

2.2 编译器凭什么敢把你的循环优化没

「无数据竞争」不是道德要求，而是优化器的输入假设。既然标准保证它不会发生，编译器就能断定：非原子变量在两个同步点之间不可能被别人改。于是重复的 load 被提到循环外，值留在寄存器里。

// 源码：等别人置位。done 非原子、中间没有任何同步
bool done = false;
while (!done) { }

// 编译器眼里的合法等价变换（前提：不可能有数据竞争）
if (!done) for (;;) { }   // load 一次 → 永远出不来

后果不是「读到旧值」那么温和：这条线程永远看不到变化，因为内存根本不再被访问。同一份代码 -O0 能跑、-O2 死循环，于是 bug 被归因成「优化器有问题」。同类变换还有把一次写撕成两次、把条件写变成无条件写（x = c ? 1 : x; 会凭空覆盖别人）。竞争的后果不是「结果不确定」，是任意。

把 volatile 当同步用是这里最常见的错解。它只要求编译器不省略这一次访问，既不阻止 CPU 乱序，也不建立 happens-before，更不保证原子。修上面那个死循环要用 std::atomic<bool>。
03

mutex 锁的是数据

保护不变量，不是「这段函数」

mutex 保护的是数据上的不变量，不是某段代码。同一对象的所有读写必须持同一把锁；两把锁锁两段函数、数据却共享，等于没锁。lock / unlock 在异常和早退上会漏；lock_guard 用析构保证释放。临界区只放碰共享状态的语句——持锁做 I/O 是把延迟摊给所有等待者。

需要中途手动释放才用 unique_lock；一次拿多把用 scoped_lock（内部有死锁避免）。recursive_mutex 把「谁持锁」从类型系统抹掉，优先拆对象或拆锁。锁的粒度跟对象走：一把锁罩整棵树，争用会把并行打回串行。

// ❌ 早退 / 抛异常都会把锁带走
mtx.lock();
use(shared);
mtx.unlock();

// ✅ 锁绑在数据上，析构必 unlock
{
  std::lock_guard<std::mutex> lk(mtx);
  use(shared);
}

3.1 粒度：粗锁与细锁各付什么代价

确定「一把锁对应一组不变量」之后，下一问是这组不变量画多大。两头的坑性质不同：粗锁的代价是性能，可以量；细锁的代价是正确性。

一把大锁多把小锁
主要代价争用：并行被打回串行死锁与锁序；两把锁之间的瞬间不变量不成立
失败形态吞吐上不去，但结果是对的平时正常，压测或换机器后偶发挂死
可观测性好：futex 等待时间直接看得到差：要靠 TSan 和死锁现场的全线程栈

默认选粗，有 profile 证明这把锁是瓶颈了再拆。拆的时候优先拆数据而不是拆锁：把大容器切成 N 个分片、每片自带一把锁、key 决定落哪片——一次操作永远只碰一把锁，环路无从产生。

3.2 四个 guard 怎么选

类型能力什么时候用
lock_guard构造 lock、析构 unlock，没别的默认选它：一把锁，进出即整段临界区
unique_lock可延迟加锁、中途 unlock、可移动、可交给 cv.wait配条件变量（硬性要求）；中途要放锁做慢操作；要把所有权交出去。代价是多一个持有状态标记
scoped_lock一次锁住 N 把，内部走免死锁算法确实要同时持有多把锁时；N=1 时与 lock_guard 等价
shared_lock取 shared_mutex 的读侧见 §7，判据很窄

还有一条低级但真实的坑：guard 必须有名字。std::lock_guard lk(mtx); 是临界区；std::lock_guard{mtx}; 构造的是临时量，在分号处就析构，临界区长度为零。

3.3 把内部引用漏出去，锁就白加了

最隐蔽的破锁方式不是忘了加锁，而是在锁内把被保护数据的引用、指针或迭代器交出去。调用者在锁外使用它，类型上看不出任何异常，而 guard 早就析构了。

class Registry {
  std::mutex m_;
  std::vector<Item> items_;
public:
  // ❌ 引用逃出临界区：调用者拿到它时锁已经放了
  const std::vector<Item>& all() {
    std::lock_guard lk(m_);
    return items_;
  }

  // ✅ 要么给拷贝，要么把操作送进来执行
  std::vector<Item> snapshot() {
    std::lock_guard lk(m_);
    return items_;
  }
  template<class F> auto with_lock(F&& f) {
    std::lock_guard lk(m_);
    return f(items_);   // 前提：f 不把引用存下来
  }
};

同一个漏洞有好几副面孔：返回 T& 或 T*、返回迭代器、把 &data_ 存进别的成员，以及在锁内调用外部回调并把数据递给它。最后一种最难防：回调可能把引用存下来，也可能反手调你另一个加锁方法造成自锁。正确姿势是让数据不出临界区——给拷贝或快照，或把操作送进去执行。

04

cv 与虚假唤醒

wait 必须 while 谓词——这是这一课

condition_variable::wait 会虚假唤醒（POSIX 允许），也会丢唤醒（notify 发生在对方进入 wait 之前）。唯一正确形态：持 unique_lock，while 谓词为假才 wait。wait(lock, pred) 就是这层循环的语法糖。谓词读的条件必须由同一把锁保护，否则谓词本身就是数据竞争。

wait 的前置条件是已经持锁。它睡之前 unlock、醒之后再 lock，所以谓词求值始终在锁内——「看纸条」和「改纸条」互斥。notify 可以不持锁，但持着发能避免「更新谓词」和「通知」被拆开。普通 condition_variable 只接受 unique_lock<mutex>；要跟 stop_token 一起等，换 condition_variable_any。

条件变量像门铃 + 门口的纸条。门铃会误响（假醒），也可能在你贴纸条「有货了」之后客人才趴到门上（丢唤醒）。所以每次被叫醒都要先看纸条：货还没有，继续等。
std::unique_lock<std::mutex> lk(m);
while (!ready) {           // 假醒 + 先 notify 后 wait，都靠谓词
  cv.wait(lk);             // 内部 unlock；被唤醒后重新 lock
}
// 此时持锁，且 ready == true

4.1 那把 mutex 保护的是「检查 + 睡下」这一步

既然 wait 内部会 unlock，为什么还非得先持锁？去掉锁推演一遍：消费者在「谓词为假」和「真正挂进等待队列」之间必然有一个窗口；生产者恰好在窗口里改了条件并 notify——通知打在空气上，因为队列里还没有人。等消费者挂上去，条件早已满足，它却要睡到下一次通知。

所以 wait 的契约是：「放锁」和「入队」对外必须是原子的一步。生产者拿不到锁就改不了条件，窗口不存在。这是 mutex 在这里的全部作用，跟「保护谓词读到的变量」是两件事，只是顺带也做到了。

推论：谓词涉及的状态必须由交给 wait 的那把 mutex 保护。用一个 atomic 当谓词、再锁另一把 mutex 去 wait，窗口就又回来了——原子性保证的是单个变量，不是「检查 + 睡」这个复合动作。

4.2 notify_one、notify_all 与惊群

notify_one 省，但只在等待者完全等价时才安全。一旦它们在等不同谓词（典型是有界队列上消费者和生产者共用一个 cv），唤醒可能发给一个谓词仍为假的线程，它看一眼又睡回去，这次通知就此丢失。

场景选择理由
等待者同质，一次通知只让一个能前进notify_one叫醒 N 个只有 1 个能干活，其余白跑
等待者在等不同谓词，或共用一个 cvnotify_all唯一不丢唤醒的做法；更好的是拆成两个 cv
等待者上百却只有一个能干活notify_one + 拆 cv此处 notify_all 就是惊群

持锁 notify 还是解锁后 notify：两者都正确，区别只在性能。持锁时 notify，被唤醒者发现锁还在通知者手上，只能再睡一次；解锁后少这一跳，但前提是cv 所属的对象此刻还活着。生命周期有一点不确定，就老实在锁内 notify。

面试只问「wait 要不要 while」：答「假醒是规范允许的，丢唤醒是时序问题，谓词一次收掉两件」。再往下才是内存序，带到 内存模型。
05

future / async

promise 写、future 读；async 默认可以不启线程

promise 是写端，future 是读端，中间一块 shared state。set_value happens-before get 返回，结果传递不必再加锁。get 只能一次；多人等用 shared_future。std::async 的默认 launch 是 async | deferred——实现可以选延后：看起来起了任务，其实 get() 才在调用者线程跑。要真有工作线程，写 launch::async。async 的 future 析构会 join，容易在意料外的地方卡住。

promise 析构时还没 set，shared state 会留下 broken_promise，get 抛异常。async 造出的 future 带「这是 async」标志，析构即 join；packaged_task 或手写 promise 没有这层隐式等待。不要丢弃 std::async 的返回值——那等于在这条语句上同步等完。

auto f = std::async(std::launch::async, []{ return work(); });
use(f.get());   // 真有工作线程；get 阻塞到完成

auto g = std::async(std::launch::deferred, []{ return work(); });
use(g.get());   // 延后：get 才在本线程跑

5.1 它是标准里唯一会在析构时阻塞的 future

std::future 的析构函数通常什么都不做。唯一的例外是由 std::async 创建、且真起了线程的那一个：它的 shared state 带着「最后一个引用析构时要 join」的标记。这是为了堵住「线程还在跑而 main 已退出」打的补丁，代价是让一次析构变成可能阻塞任意久的操作。

// ❌ 丢弃返回值 = 这一行就同步等完，两个任务纯串行
std::async(std::launch::async, taskA);   // 临时 future 在分号处析构 → join
std::async(std::launch::async, taskB);   // A 跑完才轮到 B

// ✅ 先全部启动，再统一收结果
auto fa = std::async(std::launch::async, taskA);
auto fb = std::async(std::launch::async, taskB);
use(fa.get(), fb.get());

丢弃返回值时，临时 future 在分号处就析构，整句退化成同步调用——看起来开了并发，实际一条都没并行。而 packaged_task、手写 promise、deferred 的 future 都没有这层隐式等待：同样一行析构，行为取决于它是怎么来的。对偶的陷阱是 promise 析构时还没 set，等在那边的 get() 收到 broken_promise 异常而不是永久阻塞。

5.2 为什么工程上几乎不用 std::async

std::async线程池 + packaged_task
线程从哪来实现决定，不要求复用；libstdc++ 每次新开一条固定 worker，创建成本只付一次
并发度不可控，一千次调用可能就是一千条线程由池大小决定，能跟核数对齐
背压没有，来多少开多少队列满了可阻塞、丢弃或拒绝，是个策略点
析构语义future 析构可能阻塞（见 §5.1）普通 future，析构不阻塞
线程属性名字、亲和性、优先级、栈大小都无从设置建池时一次设好，top 里也认得出是谁

std::async 真正合适的只剩一次性、数量可数的后台任务（启动时并行加载三个配置文件）。任务数量由输入规模决定的地方，都该换成「有界队列 + 固定 worker + packaged_task 产出 future」。C++26 的 std::execution 要解决的正是这件事：把「在哪执行」从「怎么表达异步」里拆出来。

06

死锁四条件

四条同时成立才会套住；破任意一条

死锁不是「锁太多」，是四条同时成立：互斥、持有并等待、不可剥夺、环路等待。工程上破「环路」最便宜——多把锁按固定地址序，或一次 scoped_lock(m1, m2)。持锁调别人的回调，等于把未知锁序引进来。排查见 死锁调试。

活锁是大家都在让，看起来有进展，谁也完不成。锁顺序要用对象身份（地址）而不是业务名字——两个模块会把「先 A 后 B」写成反的。try_lock 超时退避能破环，但会把死锁变成延迟，要有预算。持锁做日志 / RPC 是把四条件里的「持有并等待」主动延长。

6.1 四条件各自怎么破

条件C++ 里的破法代价
① 互斥无锁结构；不可变数据 + 写时拷贝；每线程一份副本最后归并多数可变共享状态做不到
② 持有并等待std::scoped_lock(m1, m2) 一次拿齐；或先拷出数据、放锁、再干活「要拿哪些锁」有时运行时才知道
③ 不可剥夺try_lock 失败就把手上的全放掉、退避、重来把死锁换成活锁风险和不确定的延迟
④ 环路等待按 std::mutex* 的地址排序；或给每把锁一个层级号几乎没有，还能静态检查

①②③ 都在改变程序结构，④ 只是加一条约定，所以默认从 ④ 下手。

6.2 锁序怎么形式化，scoped_lock 又是怎么免死锁的

「先 A 后 B」写在注释里撑不住：两个模块各自的 A、B 不是同一对对象，一重构顺序就反。要让它可执行，得把顺序变成可比较的数值：

  • 地址序：if (&a < &b) { lock(a); lock(b); } else { lock(b); lock(a); }。不需要注册，对同类型的任意两个对象天然成立，典型场景是两账户转账；缺点是顺序没有语义。
  • 层级锁：给每把锁一个层级号，线程在 thread_local 里记住当前持有的最低层级，加锁时断言新锁层级严格更低，于是第一次违规就抛异常，不必等环路形成。

std::lock 与 std::scoped_lock 走第三条路，对应破条件 ③：先阻塞式锁住第一把，其余用 try_lock；任何一把失败就把已拿到的全部释放，再以失败的那把重来。它在等的时候手上一把锁都没有，条件 ② 不成立，所以不会死锁；但它不保证公平，高争用下会反复 try-release。

顺带分开三种失败模式：死锁所有人都停着；活锁所有人都在动却谁也不前进；饥饿整体在前进、只有某个线程排不上。

07

读写锁

读共享、写独占；写者可能饿

shared_mutex：读者共享、写者独占。读多写少且临界区短才值得；写者可能饿死在一串读者后面。没有「持 shared 再升级 unique」的合法 API，自己写容易死锁。多数业务一把普通 mutex 更简单。

读多写少的典型是配置快照、路由表。写很少却延迟敏感时，双缓冲或 RCU 可能比读写锁更合适，那是 内存模型 §14 的领地。shared_lock 不要试图升级成独占——没有合法升级路径，自己写就是死锁。

7.1 为什么没有「锁升级」这个操作

「持着 shared 读完了，发现要改，就地升级成 unique」——这个想法自然到几乎人人会提，却在原理上无法安全实现：两个读者同时想升级，各自都要求对方先退出，A 等 B 放、B 等 A 放。这个环只要两线程同时尝试就必然出现，不是概率问题，所以标准干脆不提供这个 API。能做的只有放掉读锁、重新取写锁、再重新检查——窗口里别人可能已经改过，这一步就是 §2.1 说的 check-then-act。

另一个反直觉点：短临界区下 shared_mutex 常比普通 mutex 更慢——读侧要维护共享计数器，多核在同一条 cache line 上弹跳，代价可能超过省下的并行，实测见 并发模式 §4.2。判据：读临界区长到微秒级、且读写比悬殊，它才开始赢；写极少而延迟敏感时，双缓冲或 RCU 更合适。

08

thread_local

同名不同存储，不是「静态但加了锁」

thread_local 每线程一份，适合 errno、随机数状态、per-thread 缓存。把该对象的指针交给别的线程，原线程退出后就是悬空。构造发生在该线程首次 odr-use，不要假设 main 里已经构造完。

函数里的 thread_local 静态对象按线程惰性初始化：该线程第一次 odr-use 才构造，析构在线程退出时。它不是「带锁的全局变量」。用它缓存指向共享堆的裸指针，等于把所有权藏进你看不见的地方。

8.1 构造、析构与动态库卸载

时机规则坑
构造常量初始化的在线程启动前就绪；动态初始化的在该线程首次 odr-use 时惰性构造「启动时统一初始化完」是错觉；每次访问背后可能藏着一次「构造了吗」的检查
析构线程退出时按构造的逆序销毁本线程那一份析构里又访问另一个 thread_local，可能把已析构的那个重新构造出来
dlclose库卸载时，其它活着的线程里那一份的析构代码可能已不在内存里退出时段错误，栈回溯指向已 unmap 的地址；插件架构的高发故障
detach 的线程进程退出不等它，析构可能根本不跑靠析构做 flush 的（日志缓冲、统计上报）丢数据

由此得出一条收缩原则：thread_local 对象尽量做成平凡可析构的。一旦析构有副作用，上表里多半都会变成真实风险。

8.2 线程池里的 thread_local 会串味

这是本章唯一的高频线上事故。thread_local 绑的是线程，而线程池里任务和线程不是一一对应的：同一条 worker 先后跑成千上万个不相关的任务，A 留下的东西会被后来的 B 原样读到。

最经典的载体是「请求上下文」：trace id、租户 id、事务句柄——天生适合放 thread_local，不用一层层传参。换成线程池后就是两种表现：日志串号，B 的日志打着 A 的 trace id；权限泄漏，A 设过「当前租户 = 甲」，B 忘了设直接读，于是以甲的身份查了乙的数据。QPS 低时复用率低、几乎不复现，一上量才开始串。

它不是数据竞争，而是纯粹的生命周期错配，任何并发检测工具都发现不了。

对策：不要用 thread_local 存请求态，把上下文做成随任务走的对象；非用不可就在任务边界上 RAII 强制清理，进任务时存旧值设新值，出任务时（含抛异常的路径）无条件恢复。

09

停止 token

合作式退出；C++ 没有可移植的杀线程

停线程必须合作。jthread 析构 request_stop() 再 join。工作循环要自己查 stop_requested()，或把 token 下传到 condition_variable_any。只设 atomic<bool> 也可以，但别忘了 join——主线程退出时 worker 还在碰已销毁的栈对象。§1 的 jthread 短例就是这条通道。

循环里只查 token 不够：线程若卡在 cv.wait 或阻塞 syscall 里，token 置位也看不见。要么用带 stop_token 的 wait 重载，要么 notify 一下把人叫醒，让谓词看到「该停了」。强制杀线程在标准 C++ 里不存在。

9.1 叫不醒的三种线程

合作式取消的前提是被取消方会回来看。线程停在一个不检查 token 的地方，request_stop() 就只是置了个标志位，join 一直卡着——而卡住的往往是进程退出路径。

卡在哪为什么醒不了怎么办
cv.wait(lk, pred)谓词里不含停止状态，没人 notify 就不会醒用 condition_variable_any 带 stop_token 的重载；或把 st.stop_requested() 并进谓词，再在 stop_callback 里唤醒
阻塞的 read / accept线程在内核里睡，用户态的标志它看不见把 fd 纳入 epoll，另加 eventfd 作唤醒通道；或设收发超时
第三方库的同步调用你进不去它的循环只能用它自己的 cancel 接口；没有就隔离到独立进程，用杀进程代替

轮询周期本身也是取舍：短则空转耗电，长则退出慢，常见折中是 100 ms 量级的超时加一条真正的唤醒通道。再往下就是边界了——标准 C++ 里不存在强制终止线程的办法，pthread_cancel 只在特定取消点生效，还会让栈上对象的析构变成实现定义行为。这是设计结论：线程被强杀时手上可能正持着锁。

9.2 stop_callback 在哪条线程上跑

std::stop_callback 的执行线程不固定：注册时尚未请求停止，回调就在将来调 request_stop() 的那条线程上同步执行，且 request_stop() 要等所有回调跑完才返回；注册时已经请求过，回调就在注册的那条线程上立即跑完。

所以回调里碰的东西都得能承受「被任意线程、在任意时刻调用」，还要避开两个坑：不要在回调里做耗时或阻塞的事，它会拖住调 request_stop() 的线程，而那常常正是在析构 jthread 的那条；不要在回调里 join 被停止的线程，那可能是自 join 死锁。

析构同样带同步语义：返回之后回调不会再被调用，若此刻回调正在别的线程上跑，析构会等它跑完——这正是它被设计成 RAII 对象的原因。典型用法只有一行：在等待循环外层建一个 stop_callback，内容是 cv.notify_all()，把「停止请求」翻译成「条件变量事件」。

10

落到 futex

无争用是用户态 atomic；有人睡才进内核

Linux 上 std::mutex 无争用时是用户态 atomic（uncontended fast path）；有人要睡才 futex 进内核等待队列。所以「锁很贵」描述的是争用，不是每次 lock_guard。atomic::wait / notify 也是同一条系统调用。验证用 TSan；设计期把 happens-before 画出来再写代码。无锁队列、Hazard Pointer、RCU 见 内存模型 §14 与 并发模式；要看完整可编译的 SPSC 环与 ABA 解法，去 高性能通信 §2–§3。

实时线程才值得开优先级继承（PI futex）：持锁的低优先级会被临时抬到等待者的优先级，避免反转。用户态先自旋再睡（adaptive mutex）赌的是临界区极短，只改 P99，不改正确性。TSan 慢 5–15 倍，CI 必开，生产别开。形式化小例子用 cppmem，现场复现用 rr。

10.1 自旋多久才划算

「先自旋一会儿再睡」（adaptive mutex）赌的是持锁方马上就放。睡下去再被唤醒是两次系统调用加一次上下文切换，1–3 μs；自旋每次 pause 几十纳秒。

临界区的剩余执行时间明显小于一次「睡 + 醒」时，自旋赢；否则既没省下切换，还白占了一个本可以让持锁方更早放锁的核。
情形该不该自旋原因
临界区几十条指令，线程数 ≤ 核数自旋几十到几百次持锁方正在别的核上跑，很快就放；glibc 自适应锁就这么假设
线程数 > 核数，或容器 CPU 有配额不要自旋持锁方可能已被调度走，自旋到时间片耗尽它都回不来

真要手写，形态是 test-and-test-and-set：先用普通 load 自旋（裸 CAS 会让这条 cache line 一直被争抢），看到可能空闲了再发 CAS。但更常见的答案是不要手写。
