01

线程 vs 协程

内核调度的执行流，对用户态状态机

操作系统线程有独立栈，由内核调度、可被抢占；C++20 协程是编译器生成的状态机，co_await 只切这台状态机，不进内核。不要把 std::jthread 和 coroutine 当成同一种「轻线程」。能并行的是核，不是你 new 出来的线程数。用户态调度见 协程。

默认栈在 Linux 常是 8 MiB，按请求数 new thread 会先把虚拟地址和调度器打满。任务多就用线程池复用 worker。std::thread 若 detach，生命周期和栈上对象脱钩，bug 从析构 terminate 变成 use-after-return。需要用户态让出而不占核，才是协程的场景。

线程像雇来的工人：每人一套工具箱（栈），工头（内核）决定谁上工位（CPU）。协程像同一人手里的多份待办清单：做不下去就夹个书签换下一份，人没换、工位没换。

std::thread 析构时若仍 joinable，直接 std::terminate。C++20 jthread 把 join 做成 RAII，并带上停止通道：

std::jthread worker([](std::stop_token st) {
  while (!st.stop_requested()) do_work();
});  // 析构：request_stop() + join()，不再 terminate
02

数据竞争

无同步的共享写是 UB，不是「偶尔读到旧值」

数据竞争 = 两个线程访问同一内存、至少一个写、中间没有 happens-before。C++ 把它定义为 UB：优化器可以假设它永不发生，于是把后面的代码一并优化没。单核也会——抢占就够。闸门是 TSan，不是多跑几次单测。

x++ 看起来是一句话，机器上是 load-add-store 三步，中间任意点可被抢占。volatile 只挡编译器优化，不建立 happens-before，不能当锁。TSan 报的是「缺少同步关系」，不必真撞上那一拍——这是它比「多跑几次」值钱的原因。

内存序是「如何建立 happens-before」。六档语义、MESI、false sharing、CAS / ABA / RCU 见 内存模型（从 单核数据竞争、MESI、无锁回收 进）。本页不贴 memory_order_* 代码墙。

03

mutex 锁的是数据

保护不变量，不是「这段函数」

mutex 保护的是数据上的不变量，不是某段代码。同一对象的所有读写必须持同一把锁；两把锁锁两段函数、数据却共享，等于没锁。lock / unlock 在异常和早退上会漏；lock_guard 用析构保证释放。临界区只放碰共享状态的语句——持锁做 I/O 是把延迟摊给所有等待者。

需要中途手动释放才用 unique_lock；一次拿多把用 scoped_lock（内部有死锁避免）。recursive_mutex 把「谁持锁」从类型系统抹掉，优先拆对象或拆锁。锁的粒度跟对象走：一把锁罩整棵树，争用会把并行打回串行。

// ❌ 早退 / 抛异常都会把锁带走
mtx.lock();
use(shared);
mtx.unlock();

// ✅ 锁绑在数据上，析构必 unlock
{
  std::lock_guard<std::mutex> lk(mtx);
  use(shared);
}
04

cv 与虚假唤醒

wait 必须 while 谓词——这是这一课

condition_variable::wait 会虚假唤醒（POSIX 允许），也会丢唤醒（notify 发生在对方进入 wait 之前）。唯一正确形态：持 unique_lock，while 谓词为假才 wait。wait(lock, pred) 就是这层循环的语法糖。谓词读的条件必须由同一把锁保护，否则谓词本身就是数据竞争。

wait 的前置条件是已经持锁。它睡之前 unlock、醒之后再 lock，所以谓词求值始终在锁内——「看纸条」和「改纸条」互斥。notify 可以不持锁，但持着发能避免「更新谓词」和「通知」被拆开。普通 condition_variable 只接受 unique_lock<mutex>；要跟 stop_token 一起等，换 condition_variable_any。

条件变量像门铃 + 门口的纸条。门铃会误响（假醒），也可能在你贴纸条「有货了」之后客人才趴到门上（丢唤醒）。所以每次被叫醒都要先看纸条：货还没有，继续等。
std::unique_lock<std::mutex> lk(m);
while (!ready) {           // 假醒 + 先 notify 后 wait，都靠谓词
  cv.wait(lk);             // 内部 unlock；被唤醒后重新 lock
}
// 此时持锁，且 ready == true
面试只问「wait 要不要 while」：答「假醒是规范允许的，丢唤醒是时序问题，谓词一次收掉两件」。再往下才是内存序，带到 内存模型。
05

future / async

promise 写、future 读；async 默认可以不启线程

promise 是写端，future 是读端，中间一块 shared state。set_value happens-before get 返回，结果传递不必再加锁。get 只能一次；多人等用 shared_future。std::async 的默认 launch 是 async | deferred——实现可以选延后：看起来起了任务，其实 get() 才在调用者线程跑。要真有工作线程，写 launch::async。async 的 future 析构会 join，容易在意料外的地方卡住。

promise 析构时还没 set，shared state 会留下 broken_promise，get 抛异常。async 造出的 future 带「这是 async」标志，析构即 join；packaged_task 或手写 promise 没有这层隐式等待。不要丢弃 std::async 的返回值——那等于在这条语句上同步等完。

auto f = std::async(std::launch::async, []{ return work(); });
use(f.get());   // 真有工作线程；get 阻塞到完成

auto g = std::async(std::launch::deferred, []{ return work(); });
use(g.get());   // 延后：get 才在本线程跑
06

死锁四条件

四条同时成立才会套住；破任意一条

死锁不是「锁太多」，是四条同时成立：互斥、持有并等待、不可剥夺、环路等待。工程上破「环路」最便宜——多把锁按固定地址序，或一次 scoped_lock(m1, m2)。持锁调别人的回调，等于把未知锁序引进来。排查见 死锁调试。

活锁是大家都在让，看起来有进展，谁也完不成。锁顺序要用对象身份（地址）而不是业务名字——两个模块会把「先 A 后 B」写成反的。try_lock 超时退避能破环，但会把死锁变成延迟，要有预算。持锁做日志 / RPC 是把四条件里的「持有并等待」主动延长。

07

读写锁

读共享、写独占；写者可能饿

shared_mutex：读者共享、写者独占。读多写少且临界区短才值得；写者可能饿死在一串读者后面。没有「持 shared 再升级 unique」的合法 API，自己写容易死锁。多数业务一把普通 mutex 更简单。

读多写少的典型是配置快照、路由表。写很少却延迟敏感时，双缓冲或 RCU 可能比读写锁更合适，那是 内存模型 §14 的领地。shared_lock 不要试图升级成独占——没有合法升级路径，自己写就是死锁。

08

thread_local

同名不同存储，不是「静态但加了锁」

thread_local 每线程一份，适合 errno、随机数状态、per-thread 缓存。把该对象的指针交给别的线程，原线程退出后就是悬空。构造发生在该线程首次 odr-use，不要假设 main 里已经构造完。

函数里的 thread_local 静态对象按线程惰性初始化：该线程第一次 odr-use 才构造，析构在线程退出时。它不是「带锁的全局变量」。用它缓存指向共享堆的裸指针，等于把所有权藏进你看不见的地方。

09

停止 token

合作式退出；C++ 没有可移植的杀线程

停线程必须合作。jthread 析构 request_stop() 再 join。工作循环要自己查 stop_requested()，或把 token 下传到 condition_variable_any。只设 atomic<bool> 也可以，但别忘了 join——主线程退出时 worker 还在碰已销毁的栈对象。§1 的 jthread 短例就是这条通道。

循环里只查 token 不够：线程若卡在 cv.wait 或阻塞 syscall 里，token 置位也看不见。要么用带 stop_token 的 wait 重载，要么 notify 一下把人叫醒，让谓词看到「该停了」。强制杀线程在标准 C++ 里不存在。

10

落到 futex

无争用是用户态 atomic；有人睡才进内核

Linux 上 std::mutex 无争用时是用户态 atomic（uncontended fast path）；有人要睡才 futex 进内核等待队列。所以「锁很贵」描述的是争用，不是每次 lock_guard。atomic::wait / notify 也是同一条系统调用。验证用 TSan；设计期把 happens-before 画出来再写代码。无锁队列、Hazard Pointer、RCU 见 内存模型 §14 与 并发模式。

实时线程才值得开优先级继承（PI futex）：持锁的低优先级会被临时抬到等待者的优先级，避免反转。用户态先自旋再睡（adaptive mutex）赌的是临界区极短，只改 P99，不改正确性。TSan 慢 5–15 倍，CI 必开，生产别开。形式化小例子用 cppmem，现场复现用 rr。

原语保护什么典型坑
jthread生命周期 + 停止普通 thread 析构时 joinable → terminate
mutex数据不变量锁代码不锁数据；裸 lock/unlock
condition_variable「条件成立」不用 while 谓词
future / async一次性结果默认 deferred；析构 join
thread_local每线程一份状态把指针交给别的线程
