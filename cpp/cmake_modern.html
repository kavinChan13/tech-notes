01

CMake 是什么

它不是编译器，也不是 Make —— 它是「写菜谱的人」

打开一个 C++ 仓库，根目录几乎总能看到 CMakeLists.txt。很多人的第一反应是「这就是编译命令」。这个印象差了一层：CMake 自己并不编译任何代码。

CMake（Cross Platform Make）是一个元构建系统（meta-build system）。你写一份与平台无关的「菜谱」CMakeLists.txt，它先探测这台机器上有什么编译器、什么库，再生成这份机器真正能执行的构建文件（Ninja、Makefile、Visual Studio 解决方案……）。真正去调 g++ / clang++ / cl.exe 的，是后面那个原生构建工具。
把它想成餐厅后厨。食材是源码，炉灶是编译器，厨师是 Ninja / Make / MSBuild（真正炒菜的人）。CMake 是主厨写工单：同一份菜谱，到了中餐灶写一份、西餐灶另写一份——Linux 生成 Ninja，Windows 生成 .sln。你不会让主厨亲自颠勺，也不会给每间厨房各抄一份完全不同的菜谱。

四样东西经常被混为一谈，职责其实完全不同：

角色典型名字干什么不干什么
编译器g++ / clang++ / cl.exe把一个 .cpp 变成 .o不管「这个项目有 200 个文件、该以什么顺序编」
链接器ld / lld / link.exe把一堆 .o 和库收成可执行文件 / 动态库不管「哪些文件属于哪个库」
原生构建工具Ninja / Make / MSBuild按依赖图并行、增量地调用编译器和链接器不管跨平台差异；一份 Makefile 通常绑死 Unix
CMakecmake 可执行文件读 CMakeLists.txt，生成上面那种原生构建文件不编译代码；也不是包管理器（Conan / vcpkg 才是）

所以「用 CMake 编译」这句话，精确说是两步：先配置（configure / generate），再构建（build）。下一节讲为什么不能省掉 CMake，直接敲 g++。

02

为什么需要它

单文件够用 g++；项目一大，决策就会爆炸

一个文件的玩具程序，CMake 是多余的：

g++ -std=c++20 -O2 hello.cpp -o hello

真实项目要同时记住的事情会立刻炸开：哪些 .cpp 编进哪个库、头文件在哪、Boost / OpenSSL 装在哪、Debug 加 -g -O0 而 Release 加 -O3 -DNDEBUG、Linux 链 -ldl 而 Windows 链 ws2_32、你用 VS Code + Ninja、同事用 Visual Studio、CI 用 Ubuntu 容器。每一维都是乘法。下一节的配置代理把这个乘法具象成：三个模块 × 本机/交叉编译 × 产品二进制/UT/MT × 是否开 sanitizer。

CMake 要解决的，不是「能不能编译」，而是这四件事：

  1. 跨平台、跨 IDE。 一份描述，生成 Ninja、Makefile 或 Visual Studio 工程。CLion / VS Code / Visual Studio 都认 CMake。
  2. 依赖图与增量。 改一个头文件，只重编真正依赖它的翻译单元。这是 Ninja 的强项，CMake 负责把图建对。
  3. 把「这个库需要什么」写成可传递的属性。 下游 target_link_libraries(app PRIVATE foo) 之后，include 路径、宏、链接库自动跟上——这就是后文的 Target 模型。
  4. 可复现。 新人、CI、发布机器敲同一组命令，而不是「问张三他本机那个神秘脚本」。
C++ 没有像 cargo / go build 那样「语言自带构建 + 包管理」的标准工具链。生态在 2010 年代收敛到 CMake：开源库几乎都提供 CMake config，vcpkg / Conan 也以它为集成面。选 CMake 不是因为语法优美，而是别人都用它——你的依赖、你的 IDE、你的招聘市场都认这一份。

一次构建实际发生了什么

配置 ≠ 编译 · 源码外构建 · 最小可运行项目

两阶段：configure 然后 build

① 配置 Configure读 CMakeLists.txt
找编译器 / 库
→
② 生成 Generate写出 build.ninja
或 Makefile / .sln
→
③ 构建 BuildNinja 调 g++
产出二进制
→
④ 安装 Install可选：拷到前缀
生成 Config.cmake

日常你只敲两句。它们对应上面完全不同的阶段：

命令阶段产物什么时候要重跑
cmake -S . -B build① + ②build/ 里的原生构建文件、CMakeCache.txt改了 CMakeLists.txt、换编译器、改 cache 变量
cmake --build build③.o、可执行文件、库改了源码（CMake 会按需只重编脏文件）
cmake --install build④安装前缀下的 include / lib / cmake要给别的项目 find_package 时
源码外构建（out-of-source build）：-B build 把所有生成物丢进单独目录，源码树保持干净，也方便删掉重来。build/ 进 .gitignore。绝对不要在源码目录里直接 cmake .——生成文件会和源码缠在一起，清不掉。

单配置 vs 多配置：为什么会有 generator expression

这里有个后面会反复撞上的坑。Ninja / Makefile 是单配置生成器：配置时就要选定 CMAKE_BUILD_TYPE=Debug|Release。Visual Studio / Xcode 是多配置生成器：一份工程里同时带着 Debug 和 Release，真正编译时才选。所以你不能在 CMakeLists.txt 里写死 -O0——配置 VS 工程的那一刻，两种配置都还在。CMake 用 $<CONFIG:Debug> 这种生成器表达式，把「到生成 / 构建时再求值」的逻辑写进属性。§6 会用到。

最小可运行项目

myapp/
├── CMakeLists.txt ← 菜谱，进 git
├── src/
│   └── main.cpp
└── build/ ← cmake -B 生成，不进 git 
# CMakeLists.txt —— 一个可执行文件所需的最少声明
cmake_minimum_required(VERSION 3.25)
project(MyApp VERSION 1.0.0 LANGUAGES CXX)

add_executable(myapp src/main.cpp)
target_compile_features(myapp PRIVATE cxx_std_20)

然后：

cmake -S . -B build && cmake --build build && ./build/myapp

这三行各自的含义：-S 是源码根（CMakeLists.txt 所在处），-B 是构建目录；第二句让 Ninja/Make 去编译；第三句跑产物。指定生成器用 -G Ninja（推荐，增量远快于 Make）。指定 Debug：-DCMAKE_BUILD_TYPE=Debug（仅单配置生成器）。

上面刻意没写 set(CMAKE_CXX_STANDARD 20) 这种目录级变量，而是 target_compile_features(myapp PRIVATE cxx_std_20)。效果类似，但属性挂在 target 上，不会污染后来 add_subdirectory 进来的别的项目。真实仓库很少这么干净——下一节用一个配置代理工程，看「能跑的老菜谱」长什么样。
04

真实项目走读：配置代理

把「菜谱 / 厨师 / 炉灶」钉到一个会交叉编译的 C++ 进程上

前面三节用玩具项目讲概念。下面用一个设备侧 NETCONF 配置代理（文中二进制叫 agent）把同一套概念落到目录上。这个进程干的事很具体：对上走 NETCONF/YANG（开源栈 libnetconf2 + libyang + SSH），对下改设备里的配置、性能、故障、账号。CMake 要解决的不是「怎么编译一个 main.cpp」，而是：几百个 .cpp、十几个平台库、本机和交叉编译、产品二进制和两套测试，共用同一份菜谱。

文中的模块名、平台库名、板卡代号、安装前缀都做了脱敏：开源协议栈保留真名（否则讲不清这个进程是干什么的）；内部运行时、硬件 API、板型换成角色名。结构、OBJECT 库拼法、pkg-config 找库、Yocto sysroot 交叉编译，都按真实工程来。

仓库目录就是构建图

agent/ ← 源码根，这里有顶层 CMakeLists.txt
├── CMakeLists.txt 项目、编译选项、找依赖、add_subdirectory
├── src/
│   ├── CMakeLists.txt 把三块 OBJECT 库 + main 链成 agent
│   ├── main.cpp
│   ├── Core/ 平台胶水：日志、清单、PM、账号
│   ├── Controller/ 把 NETCONF 请求编排成内部动作
│   └── Agent/ YANG 场景：会话、通知、各配置用例
├── Protos/ .proto → 生成 .cc / .h，打成静态库
├── test/
│   ├── ut/ 单元测试二进制 agent_UT
│   └── mt/ 模块测试二进制 agent_MT
├── Make/cmake/ SDK / 交叉编译辅助，不当作业务代码读
└── build-host/ 本机构建目录，不进 git

九份 CMakeLists.txt 不是重复，是一张图拆开写：顶层管「项目有什么约束」，src/ 管「怎么拼出可执行文件」，子目录各管一块 OBJECT 库，test/ 管测试怎么链同一批 .o。

文件它在图上的职责
顶层 CMakeLists.txtproject(agent)、拼全局 flag、用 pkg-config 找库、按 ARCH 决定要不要硬件 API、再 add_subdirectory
Protos/CMakeLists.txt找到 .proto，调用 protoc 生成源，打成 agent-protos 静态库
src/Core|Controller|Agent各做一份 OBJECT 库；测试再包一层 SHARED 方便去链
src/CMakeLists.txtadd_executable(agent …)：把三块 OBJECT + main + 生成参数 链在一起
test/ut · test/mt另两个可执行文件，链的是同一批 OBJECT，不要产品 main.cpp

配置阶段在找什么

你敲 cmake -S . -B build-host 时，CMake 还不编译任何业务代码。它在做三件事：读菜谱、探测这台机器 / sysroot 里有什么、写出 Makefile 或 Ninja 文件。对这个代理来说，「有什么」分两桶：

桶例子（脱敏后）谁提供找不到会怎样
开源协议栈libyang、libnetconf2、libssh、protobuf、openssl、zlib、Boost开发机包管理器，或 Yocto sysroot配置直接失败：没有 YANG/NETCONF 就没有这个进程
平台运行时plat-runtime（进程框架/日志）、inventory（设备清单）、pm-lib / fm-lib、oam-lib、hw-api几乎一定在 SDK / sysroot 里，用 *.pc（pkg-config）描述 include 和 -l同样配置失败；这就是嵌入式 CMake 看起来「一长串 pkg_check_modules」的原因

pkg_check_modules(LIBYANG REQUIRED libyang) 等价于问 pkg-config：「libyang.pc 在哪？头文件路径、链接参数、额外宏是什么？」然后把答案塞进 LIBYANG_INCLUDE_DIRS / LIBYANG_LIBRARIES 这类变量。这是 Linux 嵌入式的主流找库方式，和 find_package(OpenSSL) 是亲戚：都在配置期解析，不在编译期现找。

ARCH 是这份菜谱的「哪间厨房」开关。本机 x86_64 编开发/测试；arm / aarch64 / mips 走交叉工具链；还有一种纯软件部署（文中叫 vdu）不链硬件 API，并加一个 IS_VDU 宏让源码 #ifdef 掉单板路径。CMake 在这里的作用就是：同一份源码，按 ARCH 换依赖集合和编译器，而不是维护三份工程文件。

OBJECT 库如何拼出二进制

这个仓库最容易让人懵的一句是：add_library(agent-Core OBJECT …)。它不生成 .a / .so，只是给这批 .cpp 起个名字，编译成一堆 .o，供后面多次引用。原因：产品二进制要 main.cpp，UT/MT 不要产品 main，但要同一批业务 .o。先做成 OBJECT，再按需组装，比把几百个文件名抄进两个 add_executable 少出错。

# src/CMakeLists.txt 的结构（脱敏、删掉具体库名）
add_library(agent-main OBJECT main.cpp)

add_executable(agent
  $<TARGET_OBJECTS:gen-params>
  $<TARGET_OBJECTS:agent-main>
  $<TARGET_OBJECTS:agent-Core>
  $<TARGET_OBJECTS:agent-Controller>
  $<TARGET_OBJECTS:agent-Agent>
)

target_link_libraries(agent
  pthread yang netconf2 ssh ssl crypto protobuf
  plat-runtime inventory pm-lib fm-lib oam-lib
  agent-protos
)

配置成功之后，CMake 已经把这张图写成了 Ninja/Make 的边。cmake --build 只是让厨师按图炒菜：每个 .cpp 一次 g++ -c，最后一次链接。具体命令长什么样，见 编译步骤 §6。

产品构建还有一步后处理：用 objcopy 把调试符号剥到 agent.debug，二进制本身 strip 掉，再写上 debuglink。设备上跑的是瘦的，出了崩溃拿 .debug 回来对。这不是 CMake 语言的功能，是 add_custom_command(… POST_BUILD) 在链接成功后插的壳命令。

你敲的命令对应哪一步

开发机（已经 source 过 SDK，pkg-config 能看见 sysroot 里的 .pc）：

你敲的CMake / 厨师在干什么
cmake -S . -B build-host -DARCH=x86_64 -DBUILD_TESTS=ON配置：找编译器、扫全部 .pc、生成测试目标、写出 build-host/ 里的原生构建文件
cmake --build build-host --target agent构建产品：只编 agent 及其依赖的 .o
cmake --build build-host --target ut编出 agent_UT（EXCLUDE_FROM_ALL，默认 all 不会带上它）
cmake --build build-host --target ut-run跑 ctest，按 shard 切 8 片 GoogleTest
cmake -S . -B build-arm -DCMAKE_TOOLCHAIN_FILE=… -DARCH=arm另一份构建目录、另一套编译器；源码树仍然只有一份
为什么要两个 -B 目录？ 本机 Debug+测试 和 交叉 Release 的 cache（编译器路径、是否 IS_VDU、有没有 hw-api）完全不同。混在一个 build/ 里，换 ARCH 就要删 cache 重配。源码外构建的真正好处在这里：厨房可以并排几间，菜谱还是那一份。

对照：为什么这份菜谱难读

能跑 ≠ 好读。这个工程是典型的「2010 年代嵌入式 CMake」：CMake 3.0 底线、目录级 include、变量拼 flag。它能工作，是因为整个团队约定了同一套 sysroot 和 ARCH 取值；外人打开会觉得咒语很多。对照下一节的 Modern 原则，这份菜谱踩中的坑几乎是清单原句：

仓库里实际的写法它在干什么读的人为什么晕
cmake_minimum_required(VERSION 3.0.x) + 拼接 CMAKE_CXX_FLAGS所有 target 共用一串 -Wall -Werror -std=c++17 -Os看不出哪个库不该吃 -fno-exceptions；多配置生成器上 CMAKE_BUILD_TYPE 还是空的
include_directories(…) 二三十条、link_directories(…)当前目录及子目录的所有 target 都能看见这些 -I / -LUT 和产品二进制被同一坨路径污染；缺了谁要全局翻
file(GLOB_RECURSE *.cpp)配置时扫磁盘收源文件你新加一个 .cpp，不重新 cmake，Ninja 根本不知道它存在
${Boost_LIBRARIES} 一类变量，而不是 Boost::system只拿到库文件名，传递依赖靠人肉再写一遍漏一个传递库就链接失败，报错离「谁该链它」很远
用构建目录路径是否匹配 arm/… 判断是不是发布构建历史妥协：CI 的 -B 命名即策略换个目录名，链接 flag（--gc-sections）悄悄变了

所以：不是 CMake 本身难，是这份菜谱把「全局变量 + 目录作用域 + 环境约定」叠在一起。 下一节的 Modern CMake，就是把同一张图改写成「每个 target 自己带着 include / 链接 / 宏」。你不必立刻改这个仓库；先能在脑子里画出上面那张 OBJECT 图，就已经能回答「CMake 在这个项目里干什么」。

05

为什么难用 · "Modern CMake" 是什么

20 年三种写法并存 · 四条原则 · 版本底线

CMake 1999 年诞生，补丁和功能叠了二十多年，三种范式同时活在文档和 Stack Overflow 上。上一节的配置代理是第一种的活标本：能编过，但全局 flag 和 include_directories 让图看不清。

  • 变量时代（2.x）：include_directories / link_libraries / 拼 CMAKE_CXX_FLAGS，作用域是「当前目录及子目录」，一个 target 的设置会漏到所有邻居。
  • Target 时代（约 2014 起，Daniel Pfeifer 在 CppCon 的 Effective CMake）：一切属性挂在 target 上，用 PUBLIC / PRIVATE / INTERFACE 声明传递性。这就是「Modern CMake」。
  • 工程化时代（3.19+）：CMakePresets.json、更好的 FILE_SET、C++20 Modules（3.28+）。

新人搜到的答案经常是第一种。命令还在，能跑，但在中型以上项目里会把 include 路径和宏污染成一团。本文后面只讲第二种以后。

Modern CMake 4 原则
  1. Everything is a target. 可执行文件、静态/动态库、纯头文件库，都是图上的一个节点。
  2. PUBLIC / PRIVATE / INTERFACE 写清传递性——下游链接你时，该看见的属性自动跟上，不该看见的不要漏出去。
  3. 不改 CMAKE_CXX_FLAGS。用 target_compile_options + 生成器表达式。
  4. 不写 directory-scoped 命令。include_directories / link_libraries / add_definitions 都是遗留。

版本底线

2026 写新项目用 CMake ≥ 3.25。理由不是「越新越好」，而是这几个能力已经默认该有：完整的生成器表达式、3.21+ 的 FILE_SET、3.19+ 的 Presets。要 C++20 Modules 再升到 3.28+，并配 Ninja 1.11+。

cmake_minimum_required(VERSION 3.25) 会把政策（policy）切到该版本的行为。写低了，新命令在老 CMake 上会以奇怪方式退化；写高了，老发行版的包管理器装不到。对开源项目这是一道真实的兼容门槛。

06

Target 心智模型

三种 target · 属性怎么传 · 生成器表达式

Modern CMake 的全部技巧可以收成一句：你在描述一张图。节点是 target，边是 target_link_libraries，边上标注「这条边上哪些属性要跟着走」。

类型命令磁盘上有没有二进制典型用途
可执行文件add_executable(myapp ...)有程序入口
库 STATIC / SHARED / OBJECTadd_library(foo STATIC|SHARED|OBJECT ...)有（OBJECT 是一堆 .o）可复用代码。§4.3 的配置代理就是靠 OBJECT 把产品和测试拼在同一批 .o 上
INTERFACE 库add_library(foo INTERFACE)无，只传递属性header-only（如大量 header-only 的 Boost 组件）

PUBLIC / PRIVATE / INTERFACE

每个 target_include_directories / target_link_libraries / target_compile_definitions 都要标可见性。规则只有三句：

  • PRIVATE：只给本 target 编译自己时用，不传给链接我的人。
  • INTERFACE：本 target 自己编译时不用（通常因为没有 .cpp），但链接我的人要用。
  • PUBLIC = PRIVATE + INTERFACE：自己用，下游也用。
把库当成一家公司。PUBLIC 是写在对外合同里的供应商——客户拿到你的产品，也必须能找到这家供应商。PRIVATE 是公司内部用的办公软件，客户不必、也不该安装。INTERFACE 是纯中介：自己不生产，只规定下游必须带上某份头文件或某个链接项。
沙盒：拨动可见性，看属性怎么传给下游
改变 foo 链接两个依赖的可见性，观察消费者 myapp 能看见什么。PUBLIC = 自己用也转交；PRIVATE = 只自己用；INTERFACE = 自己不用、只转交。
foo 链接fmt::fmt
foo 链接spdlog::spdlog
foo 自己（编译 foo.cpp 时）
fmt::fmt
spdlog::spdlog
→
myapp（target_link_libraries(myapp PRIVATE foo)）
fmt::fmt
spdlog::spdlog

判断规则（不必背，问自己两个问题）

  1. 这个依赖是否出现在我的公开头文件里（#include，或作为公开 API 的参数 / 返回值 / 成员类型）？是 → PUBLIC。
  2. 只在 .cpp 里用？→ PRIVATE。

标错的代价不对称：该 PRIVATE 标成 PUBLIC，下游会多链一个库、多一份 include——能编过，但依赖膨胀、有时 ABI 泄漏。该 PUBLIC 标成 PRIVATE，下游编译到你的头文件时会报找不到头 / 未定义类型——立刻失败。拿不准时先 PRIVATE，公开头编译不过再改 PUBLIC。

# 一个库 + 一个可执行文件。注意可见性与 BUILD/INSTALL 两套 include
add_library(foo SHARED src/foo.cpp)

target_include_directories(foo
  PUBLIC
    $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
    $<INSTALL_INTERFACE:include>
  PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/src
)
target_link_libraries(foo
  PUBLIC  fmt::fmt          # foo.hpp 里 #include <fmt/format.h>
  PRIVATE spdlog::spdlog    # 只在 foo.cpp 打日志
)
target_compile_features(foo PUBLIC cxx_std_20)

add_executable(myapp main.cpp)
target_link_libraries(myapp PRIVATE foo)
# myapp 自动获得 foo 的 PUBLIC include 和 fmt；看不到 src/ 和 spdlog

$<BUILD_INTERFACE:…> 只在本树构建时生效，指向源码里的 include/；$<INSTALL_INTERFACE:include> 在安装之后生效，指向安装前缀。同一条 PUBLIC include 因此能同时服务「开发自己」和「别人 find_package」。漏掉这一对，是开源库「本机能编、装完别人编不过」的头号原因。

生成器表达式

$<…> 在生成原生构建文件时（多配置生成器则更晚）才求值，所以同一份 CMakeLists.txt 能表达「Debug 加这个宏、GCC 加这组警告、MSVC 加那组」：

  • $<$<CONFIG:Debug>:FOO_DEBUG> —— 仅 Debug 定义宏
  • $<$<CXX_COMPILER_ID:GNU,Clang>:-Wall;-Wextra> —— 按编译器选 flag（注意列表用 ; 分隔）
  • $<BUILD_INTERFACE:…> / $<INSTALL_INTERFACE:…> —— 上面那对路径

不要在配置阶段用 if(CMAKE_BUILD_TYPE STREQUAL "Debug") 去改编译选项：多配置生成器上 CMAKE_BUILD_TYPE 是空的，这段 if 永远不进。一律走生成器表达式或 target_compile_options 的 per-config 形式。

依赖管理 4 方案

CMake 找库，不等于 CMake 是包管理器

CMake 能声明「我需要这个库」并接到 target 图上，但默认不负责下载、缓存、二进制复用。四条路的差别在「库从哪来」。

find_package（系统里已经有的大库）

在系统 / 指定前缀里找已安装的包，得到 imported target（如 OpenSSL::SSL、Boost::thread）。这是现代写法；老代码里的 ${Boost_LIBRARIES} 变量不要再用——变量不会带着 include 路径和传递依赖走。

适合：OpenSSL、Boost、Qt、CUDA、ROS，以及发行版已经打包好的一切。嵌入式 / Yocto 交叉编译也走这条：sysroot 里有什么就 find 什么。配置代理 §4.2 里那一长串是 pkg_check_modules，机制相同，只是查询的是 *.pc 而不是 CMake Config 文件。

FetchContent（构建时拉源码，适合小库）

配置阶段 clone 指定 tag，当子项目 add_subdirectory 进来。适合 fmt、nlohmann/json、Catch2、spdlog 这种小库或 header-only。缺点：首次配置要联网、大库会把你的构建时间拖垮、版本冲突要自己解。开源项目常写成「先 find_package，找不到再 FetchContent」给发行版用户一条退路。

include(FetchContent)
FetchContent_Declare(fmt
  GIT_REPOSITORY https://github.com/fmtlib/fmt.git
  GIT_TAG        10.2.1
  GIT_SHALLOW    TRUE)
FetchContent_MakeAvailable(fmt)
target_link_libraries(myapp PRIVATE fmt::fmt)

Conan 与 vcpkg（真正的包管理器）

两者都在 CMake 之外解决「下载 + 按 triplet 预编译 + 缓存」，再通过 toolchain file 把 imported target 喂给 CMake。你的 CMakeLists.txt 仍然只写 find_package + target_link_libraries。

场景推荐原因
小项目，依赖 < 10 个小库FetchContent零额外工具，clone 即编
开源，希望发行版用户轻松编find_package + FetchContent 回退能吃系统包就吃系统包
企业内部，要二进制缓存和严格版本Conan 2Artifactory / 私有 remote 成熟
Windows / Microsoft 生态vcpkg manifest 模式与 VS、GitHub Actions 集成顺
Linux 发行版、嵌入式 sysrootfind_package库已经在镜像或 SDK 里
vcpkg 的 vcpkg.json、Conan 的 conanfile.txt、CI 矩阵和完整模板，见 CMake & CI 实战。本页只把「四选一」的判据讲清，避免在菜谱里再塞一本包管理手册。

CMakePresets.json

把「怎么配置」从口口相传变成仓库里的一份 JSON

CMake 3.19+ 的 Presets 解决的是这种对话：「你本地到底加了哪些 -D？用的 Ninja 还是 Make？构建目录叫 build 还是 out？」把常用配置写成声明，IDE（VS Code / CLion / Visual Studio）和 CI 读同一份文件。

{
  "version": 6,
  "cmakeMinimumRequired": { "major": 3, "minor": 25 },
  "configurePresets": [
    {
      "name": "default",
      "binaryDir": "${sourceDir}/build/${presetName}",
      "generator": "Ninja",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Release",
        "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"
      }
    },
    {
      "name": "dev",
      "inherits": "default",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "ENABLE_SANITIZERS": "ON"
      }
    }
  ],
  "buildPresets": [
    { "name": "default", "configurePreset": "default", "jobs": 8 },
    { "name": "dev", "configurePreset": "dev", "jobs": 8 }
  ]
}
命令作用
cmake --preset dev按 dev 做 configure + generate
cmake --build --preset dev构建
ctest --preset default跑测试（需另写 testPresets）
cmake --list-presets列出仓库里的预设

个人习惯（本机路径、额外开关）放 CMakeUserPresets.json 并 gitignore。仓库里只留团队公约。CI 用同一个 preset 名，开发机和流水线不会各写一套 -D。

CMAKE_EXPORT_COMPILE_COMMANDS=ON 会在构建目录生成 compile_commands.json。clangd / clang-tidy 靠它知道每个文件的真实编译参数；这是「IDE 能跳转、能报对警告」的地基，新项目默认打开。

跨平台与交叉编译

本机三平台用 if；跨架构用 toolchain file，不要把编译器写进 CMakeLists

本机多平台差异（Linux 链 dl、Darwin 链框架、Windows 定义 NOMINMAX）用 CMAKE_SYSTEM_NAME / WIN32 分支，并且仍然挂在 target 上，不要改全局 flag。

交叉编译（在 x86 上为 ARM 单板、Android、WebAssembly 出包）不要在 CMakeLists.txt 里写死 arm-linux-gnueabihf-g++。单独做一份 toolchain file，配置时传入：

cmake -S . -B build-arm -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/arm-linux-gnueabihf.cmake

文件里只放「这是什么系统、编译器叫什么、sysroot 在哪、find 只在 sysroot 里找」。这样同一份菜谱可以：本机编一份、ARM 编一份、CI 再编一份，互不污染。配置代理 用 -B build-host 和 -B build-arm 两套目录，正是这个意思；ARCH 只换依赖集合，不换源码树。

目标Toolchain 从哪来
通用 ARM Linux自己写，或发行版交叉工具链文档里的示例
AndroidNDK 自带 android.toolchain.cmake
iOS常用第三方 ios-cmake
WebAssemblyEmscripten 的 emcmake 包装
YoctoSDK 里已经生成好 toolchain file

工程化：Sanitizer / LTO / 安装 / CI

开关挂 option · 安装是为了被别人 find_package · CI 复用 preset

Sanitizer 与 LTO

ASan / TSan / UBSan 是编译器功能，CMake 只负责把 flag 挂到指定 target。要点：

  • 用 option(ENABLE_ASAN …) 控制，默认 OFF；preset dev / asan 再打开。
  • ASan 与 TSan 不能同时开。编译和链接两侧都要加 -fsanitize=…，只加一边会链失败或漏报。
  • 只给 GNU/Clang 加；MSVC 有自己的 sanitizer 开关，不要混写。

LTO（链接时优化）：check_ipo_supported 探测后再 set_target_properties(… INTERPROCEDURAL_OPTIMIZATION TRUE)，通常仅 Release。PGO 是「先插桩跑一趟代表性负载，再用 profile 重编」，CMake 没有一等公民封装，用两套构建目录 + 编译器自己的 -fprofile-generate / -fprofile-use 即可。细节与原理见 Sanitizer 内部、工具链全景。

C++20 Modules

CMake 3.28 + Ninja 1.11 + GCC 14 / Clang 17 / MSVC 19.30 可以工作：用 target_sources(… FILE_SET CXX_MODULES FILES math.cppm) 声明模块接口。跨库 import、标准库 import std;、Conan/vcpkg 仍有边角。新玩具项目可以试；生产大库建议再等一等，不要为了 Modules 把构建图赌进去。

install / export：让别人 find_package 到你

安装不是「把二进制拷走」这么简单。下游要的是一个 imported target Foo::foo，带着正确的 include 和链接接口。流程是：install(TARGETS foo EXPORT FooTargets …) → install(EXPORT FooTargets FILE FooTargets.cmake NAMESPACE Foo:: …) → 再配一份 FooConfig.cmake。用户侧就变成 find_package(Foo 1.0) + target_link_libraries(app PRIVATE Foo::foo)。

CPack 可以在此之上打 TGZ / DEB / RPM，命令是 cmake --build build --target package。包格式是发行问题；Config 文件对不对，才是 CMake 问题。

CI

矩阵 = 操作系统 × preset。步骤就是仓库里开发者敲的那两句：cmake --preset X 然后 cmake --build --preset X，再 ctest。Windows 上排除 ASan preset 这类互斥组合。完整 GitHub Actions 模板见 CMake & CI 实战。

构建性能与调试

Ninja + ccache 是默认组合；编不过时先看真实命令

工具 / 命令干什么什么时候用
Ninja替代 Make，增量与并行更狠新项目默认 -G Ninja
ccache / sccache按编译命令缓存 .o切分支、干净构建反复发生时
CMAKE_EXPORT_COMPILE_COMMANDS生成 compile_commands.jsonclangd、clang-tidy
cmake --build build --verbose打印真实编译命令行「头文件找不到」却怀疑 CMake 没传 -I
cmake --graphviz=deps.dot导出 target 依赖图PUBLIC 传多了、环依赖
cmake --trace-expand展开后的 CMake 语言逐行跟踪宏 / function 把变量弄丢了
Unity Build / PCH合并翻译单元 / 预编译头模板重、头文件巨兽；先测再开，可能掩盖 ODR

ccache 的接法是把启动器设到编译器前面：找到 ccache 可执行文件后 set(CMAKE_CXX_COMPILER_LAUNCHER …)。不要去改 CMAKE_CXX_COMPILER 本身。

构建慢时先分清是配置慢（FetchContent clone、feature test）还是编译慢（模板、没有增量）。前者减网络依赖、钉死 tag；后者 Ninja + ccache + 少在公开头里塞实现。编译器内部在干什么，见 编译步骤。

10 大反模式

能跑不等于现代；这些写法在中型项目里会反噬

#反模式实际伤害改成
1include_directories(...)当前目录所有 target 都被污染target_include_directories
2link_libraries(...)同上，链接接口无法按库裁剪target_link_libraries(target …)
3拼接 CMAKE_CXX_FLAGS多配置生成器失效；子项目中招target_compile_options + $<…>
4file(GLOB …) 收源文件新增 .cpp 时 CMake 不知道，要手动重配显式列出源文件
5不写 PUBLIC / PRIVATE属性乱传或漏传每个 target_* 都显式标
6${Boost_LIBRARIES} 一类变量没有传递依赖、没有 includeimported target Boost::system
7硬编码 /opt/foo/include别人的机器、CI、交叉编译全挂CMAKE_CURRENT_* + find / FetchContent
8不写 cmake_minimum_required政策默认值随 CMake 版本漂移钉死最低版本
9add_definitions(-DFOO)目录级宏泄漏target_compile_definitions
10公开头路径不拆 BUILD / INSTALL本机能编，find_package 之后路径错BUILD_INTERFACE / INSTALL_INTERFACE
老写法（能跑，别学）
include_directories(include)
link_directories(/opt/lib)
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -Wall")
add_definitions(-DFOO=1)
file(GLOB SRC src/*.cpp)
add_library(foo ${SRC})
target_link_libraries(foo boost_system)
同一意图的现代写法
add_library(foo src/foo.cpp src/bar.cpp)
target_include_directories(foo PUBLIC
  $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
  $<INSTALL_INTERFACE:include>)
target_compile_options(foo PRIVATE -Wall)
target_compile_definitions(foo PRIVATE FOO=1)
target_link_libraries(foo PRIVATE Boost::system)
可以带走的几句话
  • CMake 是元构建：翻译菜谱，不炒菜。编译器怎么工作见 编译步骤。
  • 需要它，是因为平台 × 生成器 × 配置 × 依赖是乘法；一份 CMakeLists.txt 覆盖整张表。
  • 日常两句：cmake -S . -B build（配置）和 cmake --build build（构建）。
  • 配置代理：配置期用 pkg-config 找两桶库；OBJECT 库让产品和 UT/MT 共用 .o；ARCH 换厨房。
  • Modern = 一切属性在 target 上；PUBLIC / PRIVATE 问的是「公开头里有没有用到它」。
  • 包管理另选工具；Presets 让人和 CI 敲同一组命令。
