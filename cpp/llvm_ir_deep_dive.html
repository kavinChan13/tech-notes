LLVM IR 深入

LLVM IR 是类汇编 + 强类型 + SSA 的编译器中枢：Clang 编进来，opt 在上面跑 Pass，后端降到机器码。这篇用图讲清 SSA / phi / alloca / LTO，再用最短 IR 把指令语义钉死——面向静态分析、插桩、自定义优化。

01

为什么是 LLVM IR

跨语言 / 跨平台的中枢 · 三种形态等价

LLVM IR 夹在源码和机器码之间：类汇编、强类型、SSA。C / Rust / Swift 编到同一 IR；x86 / ARM / RISC-V / WASM / GPU 后端吃同一 IR；AOT、JIT、静态分析、sanitizer 插桩也在这一层做。和 GCC GIMPLE 不同，外部工具能直接 emit / parse / transform。

三地址码 + SSA + 强类型：三个选择，各解决一个问题

IR 长成这样不是审美偏好，每一条都在为「优化器好写、好验证」让路。

设计选择不这么做会怎样买到了什么
三地址码
%r = add i32 %a, %b		表达式树或栈式字节码：中间结果没有名字「这个乘法的结果被谁用了」从「递归遍历子树」变成一次查表
SSA
一个名字只被定义一次		可重复赋值的虚拟寄存器：要沿控制流回溯才知道用的是哪次赋值use → def 是一条确定的边（§3.1）
强类型
每个 value 都带类型		只记 bit 宽度的字节码：什么都能通过Verifier 能在每个 pass 之后重新校验（§4.1）

为什么会收敛到 IR 这个腰部

M 种语言、N 种架构。如果每个前端各自直奔机器码，「循环不变量外提」这种和语言、架构都无关的优化得重复实现 M×N 遍。插一层 IR 之后账变成 M 个前端 + 一套优化器 + N 个后端。

数量只是表面，真正的收益在于谁受益：Rust 从第一天起就拿到了为 C 打磨十年的 LICM、GVN、向量化，它的编译器团队一行优化代码都没写；反过来一个新架构只要写完后端，立刻拥有全部这些语言。GCC 的 GIMPLE 处在类似位置却没长出这种生态，差别不在技术——它没有稳定的对外格式，而 LLVM 把 IR 当成公开接口维护。

同一份 IR 的三种形态

形态扩展名用途
Textual IR.ll人读 · godbolt · 调试
Bitcode.bc紧凑；LTO 时塞进 .o
In-memory—llvm::Module，跑 pass 时

三者是同一份 IR 的三种序列化，llvm-as / llvm-dis 无损互转，语义完全一致，区别只在读写成本和「谁来读」：.ll 是唯一人能读的形态，也是 LLVM 自己的测试格式（llvm/test/ 下几万个 .ll 配 FileCheck 就是整个优化器的回归测试网）；.bc 紧凑，而且有向后兼容承诺——新版能读旧 bitcode，LTO 时它被塞进 .o 的一个 section（§6.3）；而内存里的 Module 才是 pass 真正操作的对象。

推论：生产管线里不要把 IR 落成文本再读回来——那是白付一次 parse，而 bitcode 正是为这个场景存在的。
02

IR 解剖学

最短函数 · 指令表 · alloca / load-store · O0 vs O2 · CFG

嵌套四层：Module（一个翻译单元）⊃ Function ⊃ BasicBlock（直通指令序列，只能末尾跳转）⊃ Instruction。

四层容器的边界，以及谁在哪一层干活

层级对应源码里的什么典型 pass
Module一个翻译单元（.cpp 加它展开出的所有头文件）Inliner · GlobalOpt · LTO
Function一个函数。模板每个实例化、每个 lambda 各算一个SROA · GVN · SimplifyCFG
BasicBlock一段没有分支的直通代码局部 CSE · InstCombine
Instruction一次运算 / 访存 / 跳转—

层级决定一个 pass 能看多远：Function pass 看不见别的函数，只能保守假设「这个调用可能写了我的内存」——这正是内联能带来那么多连带收益的原因（§7.1）。

最短函数：alloca / store / load / ret

O0 把局部变量放栈上。吐 IR：clang -S -emit-llvm -O0 inc.c -o inc.ll。

; int inc(int a) { int x = a; x = x + 1; return x; }
define i32 @inc(i32 %a) {
entry:
  %x = alloca i32, align 4     ; 栈槽；放 entry 才能 mem2reg
  store i32 %a, ptr %x         ; 写入
  %0 = load i32, ptr %x        ; 读出
  %1 = add i32 %0, 1
  store i32 %1, ptr %x
  %2 = load i32, ptr %x
  ret i32 %2
}
指令语义
alloca开栈槽，返回 ptr；仅 entry 且不逃逸可 mem2reg
store / load类型写在指令上，不在指针上
ret / br返回 / 跳转（带 i1 则条件）
icmp / fcmp比较 → i1
add / mul / …新 SSA 名，从不改旧名
phi / select按前驱选值 / 无跳转二选一
call / getelementptr按 calling conv 传参 / 只算地址

基本块「只能从头进、只能从尾出」

严格说：一个基本块里只有第一条指令能是跳转目标，只有最后一条能是 terminator（br / switch / ret / invoke）。中间既不许跳进来，也不许跳出去。

这条约束把「分析一段代码」拆成两个难度完全不同的问题：块内指令严格顺序执行，「这个值在这里是多少」从块顶往下扫一遍就行，完全不用考虑控制流；块间的复杂度全被挤到 CFG 这一张图上，变成支配关系、循环识别这些和指令语义无关的纯图算法。允许从块中间跳进来，前一半立刻失效——所以源码里看着像跳进中间的写法（switch 的 fallthrough、&& 的短路）Clang 都会把落点切成一个新的基本块。

alloca 为什么总在 entry 块

alloca 没有配套的释放指令——它开的栈要等函数返回才随栈帧一起回收，所以这条指令执行几次栈就长几块。放在 entry 块它整个函数只执行一次；一旦落进循环体，转一百万次就是一百万张槽，直接爆栈（C 的 VLA 和 alloca() 在循环里危险就是这个原因）。

第二个理由才是重点：mem2reg 只认 entry 块里的静态 alloca。循环里的 alloca 每圈是一张不同的槽，「这个槽里现在是什么值」没有唯一答案，映射不到单个 SSA 名。所以位置放错不只是栈的问题，而是这个变量永远走内存、进不了寄存器——代价见 §3.3。

03

SSA 与 Phi 节点

只赋值一次 · phi 在块顶

SSA：每个名字只赋值一次。def-use 变成一张图上的唯一边，GVN / LICM / DCE 都靠这个前提。源码里「同一个 x 写两次」，IR 里必须换成 %1、%2。
SSA 像快递单号——每个包裹只贴一次。phi 是分拣口：看货从哪条传送带来，就取那条边上的值。
; 源码：x = 1;  x = x + 1;   —— 两次赋值，SSA 禁止改旧名
%1 = add i32 0, 1      ; 第一次赋值 → %1
%2 = add i32 %1, 1     ; 再写 x 必须换 %2；%1 永远不变
ret i32 %2

SSA 真正买到了什么：use-def 链直接可查

在可重复赋值的 IR 上，问「这条 add 的第一个操作数是哪来的」没有唯一答案：得沿所有可能的控制流路径往回找最近的那次赋值，有分支时还要在汇合点把多个答案合起来——这套东西叫数据流分析，每个优化都得自己做一遍。

SSA 把这个问题整个删掉：名字只被定义一次，所以「定义在哪」是名字自带的属性。在 LLVM 的对象模型里这就是 Value 与 User——一条 Instruction 既是 Value（它产生的结果）又是 User（它用到的操作数），「谁用了我」和「我用了谁」都是 O(1) 查询。几个经典优化因此塌成几行：DCE 是「没有 use 且无副作用就删」，常量传播是「def 是常量就 replaceAllUsesWith」，GVN 是「运算和操作数名字都相同 → 结果必然相同」。

最后一条是关键：在可重复赋值的 IR 上，x + y 出现两次不代表结果一样。SSA 把「语法相同」升级成「语义相同」——这是 GVN 能存在的全部前提。

汇合点：phi 为什么必须在块顶

两条前驱都给 x 赋值时，merge 块顶用 phi：按进来的那条边选值。phi 只能出现在块顶。

entry:
  br i1 %cond, label %T, label %F
T:
  br label %M
F:
  br label %M
M:
  %x = phi i32 [ 1, %T ], [ 2, %F ]
  ret i32 %x

phi 长得像指令，执行模型却不一样。它必须在块顶，因为它的含义是「这个块刚被进入时这个值是多少」，依赖的信息是「从哪条边进来的」——而这个信息在块里执行了任何一条真正的指令之后就不再有意义，放到块中间语义无法定义。同一块顶的所有 phi 还是并行求值的：循环里交换两个变量（t=a; a=b; b=t;）在 mem2reg 之后是两个互相引用的 phi，按顺序一条条算的话，第二条会读到第一条刚更新的值，两个变量最后变成同一个。

它也不是真正的指令——没有哪个 CPU 有 phi。寄存器分配前的 PHI elimination 把每个 phi 拆成若干条 mov、插到各前驱块的末尾，上面那个并行赋值的麻烦在这一步原样重现（lost-copy / swap problem）。

SSA 只管函数内的寄存器值。逃逸对象、global、heap 仍是内存；跨函数要 IPA / LTO。

mem2reg：几乎所有后续优化的前提

如果整个 LLVM 只让你记住一个 pass，就是它。-O0 的 IR 里每个局部变量是一个 alloca 加一堆 store / load，而几乎所有优化都只看 SSA 名之间的关系，看不进内存。

为什么看不进：load i32, ptr %x 的结果取决于「上一次写 %x 写进了什么」，这要靠别名分析回答，而它只能保守——中间只要有一次看不见函数体的 call，就必须假设 %x 已经被改了。于是 GVN 不敢合并两个 load，LICM 不敢外提循环里的 load，常量传播不敢把 store 的值代入后面的 load。mem2reg 把这些栈槽整个删掉、改成 SSA 名，并在需要汇合处补上 phi——每一条「不敢」于是都变成「显然」，因为不再有内存，只剩名字。

这解释了 -O0 和 -O1 之间那道台阶为什么这么陡。常见说法是「-O1 打开了几十个优化」，真实情况更集中：-O0 是唯一一个连 mem2reg 都不跑的档位，后面那几十个优化全部空转。经验上 -O0 → -O1 常见 3–10 倍差距，-O1 → -O3 往往只有几十个百分点——第一级解决的是「优化器能不能开始工作」。

别拿 -O0 的数字当性能基准。它不是「没优化的版本」，而是一个连虚拟寄存器都基本不用的形态——用它测出来的热点分布经常是假的。
别让局部变量的地址逃逸。一旦对局部变量取地址、传给一个编译器看不见定义的函数（跨 TU 的函数、虚函数、std::function），它就被钉在栈上，本节列出的优化全部失效。这就是「noinline 的 getter」「跨 TU 的引用传参」在热点上产生可测量开销的机制层原因，也是 LTO 能提速的同一个理由。
04

类型系统

强类型 · opaque ptr · poison · inbounds GEP

每个 value 都有类型，对不上就是非法 IR。整数无符号性不在类型上，而在 add vs add nsw / udiv vs sdiv 这些算子上。

类型含义
i1 … i128 / iN定宽整数；符号由指令决定
half / float / double浮点
ptrLLVM 16+ 唯一指针类型（opaque）
{i32, double} / [10 x i32] / <4 x float>结构 / 数组 / SIMD 向量
i32 (i32, ptr)函数类型
label / token / void块标签 · 协程/异常令牌 · 无返回

为什么 IR 要强类型，以及符号性去哪了

一个只记 bit 宽度的 IR（多数字节码就是这样）也能跑，但它让「这段 IR 合法吗」变成没法回答的问题。强类型换来的是：Verifier 能抓住改坏 IR 的那个 pass——类型不匹配、terminator 不在块尾、phi 的前驱个数和 CFG 对不上，都能在线性时间里查出来。开发时加 -verify-each，坏在哪一步立刻定位；否则表现是「后端某处崩溃或默默生成错码」，现场离出错点隔着几十个 pass。

有意思的是符号性不在类型里：i32 既不是 signed 也不是 unsigned。原因很实在——二进制补码下加、减、乘的位模式与符号无关，只有除法、右移、比较、扩展需要区分，于是区分放到了指令上（sdiv/udiv、ashr/lshr、icmp slt/icmp ult），恰好落在真正需要区分的地方。

同一条思路解释了「有符号溢出为什么是 UB」：它在 IR 层是 add nsw，而 nsw 是前端给优化器的一句保证——真溢出时结果是 poison，于是「把 i32 归纳变量提升成 i64 省掉每圈一次符号扩展」这类推导才成立。

opaque pointer：LLVM 15 起指针不再带指向类型

LLVM 15 之前，指针类型自己记着指向什么：i8*、i32*、%struct.Foo*。15 起全部塌成一个 ptr，pointee 类型只写在真正访问它的指令上。这是近十年 IR 最大的一次变化，动机可以压缩成一句：指向类型对优化毫无用处，却制造了海量的 bitcast。

优化器真正关心的是「这次访问读写了几个字节、对齐多少、和另一次访问会不会重叠」，这些信息全在 load / store / getelementptr 上，从来不在指针类型里。而 C 和 C++ 本来就允许同一块内存按不同类型访问（malloc 的返回值、memcpy 的 void*、union、placement new、基类与派生类指针互转），每次转换在旧 IR 里都要插一条 bitcast——这些指令语义上什么都不做，却要被搬运、被反复消除、被每一处模式匹配跳过（于是 pass 里到处是 stripPointerCasts()，漏一处优化就静默失效）。

源码层没有变化，但看到 i32* 加一堆 bitcast 的 IR 片段，就知道那是 LLVM 14 及更早的旧教程。

05

Metadata + Attribute

TBAA · function attributes · calling conv

指令旁边可以挂 metadata；函数/参数/返回值可以挂 attribute。两者都是给优化器的保证，写错等于撒谎，会生成错码。

!dbg：行号能活下来，变量常常活不下来

!dbg 挂在指令上，指向一条 DILocation（文件、行、列、内联链）。行号能活下来，因为它只是个标签，指令搬到哪儿它跟到哪儿——内联之后 DILocation 还会带一条链（「这行在 foo 里，而 foo 被内联到 bar 的第 42 行」），调试器靠它重建出已经不存在的栈帧。

变量就没这么幸运。它的位置靠 #dbg_value 记录（「变量 x 此刻住在这个 SSA 值 / 栈槽 / 寄存器里」），而优化会让它根本不存在：

优化做了什么变量去哪了调试器里看到
DCE 删掉只服务于它的那串计算彻底消失，连一个位置都没有<optimized out>
GVN 合并两个等价表达式两个源码变量共用同一个值改一个像是「同时改了另一个」
寄存器分配不同区间住不同寄存器，有的区间压根没有只在部分行可见

-O2 -g 下调试体验差，根因不是「调试信息丢了」，而是被问的那个变量在那一刻真的不存在——这也是 -Og 的存在理由：只开不破坏变量可见性的优化。

!tbaa：严格别名规则就是这样传给优化器的

C++ 的严格别名规则——「不得通过与对象动态类型不兼容的左值访问该对象」——在编译器内部的落地形态，就是每条访存指令上挂的 !tbaa。

Clang 给每条 load / store 标注「这次访问的是什么类型」，类型组织成上图那棵树。判据是：两个访问的节点不在同一条祖先链上，就断定它们永不重叠（char 是所有类型的祖先，所以 char* 能别名一切）。

❌ 类型双关 · 违反了合同
float f = 1.0f;
int   i = *(int*)&f;   // 用 int 左值访问 float 对象
✅ 编译器认得这个模式，一样快
int i;
std::memcpy(&i, &f, sizeof i);
// 或 C++20：i = std::bit_cast<int>(f);

左边那段里 store float 挂 float 节点、load i32 挂 int 节点，两者不同链，于是优化器断定这次 load 读的不是刚写进去的那块内存，它因此可以重排这两条指令、或者把那次 store 当死代码删掉。因果要说清楚，因为这件事经常被说反：优化器没有「生成错误的代码」，是你给了它一个假前提。打开 -fstrict-aliasing（-O2 默认）等于签一份合同——「我不会用不兼容的类型访问同一块内存」。违反之后，它基于合同的每一步推导都对，只是结论错了。症状也极难查：只在 -O2 出现、换个编译器版本就变、加一句 printf 就好了。

合法写法只有三条：memcpy（编译器认得这个模式，会折成一条 mov）、std::bit_cast、union。-fno-strict-aliasing 是最后手段，代价是整棵 TBAA 树失效。

属性从哪来，又值多少钱

函数与参数上的 attribute 是契约的另一半，大部分是源码写法直接翻译过来的：

IR 属性C++ 里什么写法产生它优化器因此敢做什么撒谎的后果
noalias__restrict__ 参数；new 的返回值两个指针参数当作不重叠 → 敢向量化、敢重排访存真传了重叠的指针 → 静默算错
nonnull dereferenceable(N)引用参数 T&：不能为空，且至少 N 字节可读删掉空指针检查；把 load 提到分支之前语言层已保证
memory(read)（旧名 readonly）不是 const 成员函数给的，靠 FunctionAttrs 从函数体推重复调用可以合并，可以从循环里外提偷偷写了 → 调用被合并掉
nounwindnoexcept删掉 invoke 的异常边，整个 landing pad 消失真抛了 → 直接 std::terminate
willreturn能被证明一定会返回的函数没人用它的结果时，整个调用可以删掉死循环被优化掉
引用参数比裸指针快，不是因为「引用没有解引用开销」——IR 层两者都是同一个 ptr。差别在于引用带着 nonnull dereferenceable，优化器因此敢把 load 提前、敢删掉隐含的空检查。但 const T& 不给任何别名保证：const 只说「我不通过这个引用改它」，没说「别人不会改它」，所以循环里通过 const int& 读到的值每圈都得重新 load。想要那个保证只能写 __restrict__，或在循环外拷一份到局部变量。
06

Pass 流水线深入

NewPM 嵌套 · LTO · 常用命令

每个 pass 只干一件事。-O2 大约 150 个，-O3 再多二三十。Transform 改 IR，Analysis 只产信息（DominatorTree / LoopInfo / AA）；LICM 这类 transform 靠后面那批分析。

LLVM 13+ 默认 NewPM（CRTP，比 legacy 虚调用快一截，支持嵌套管线）。自己写 pass 就继承 PassInfoMixin<T> 实现 run()。和 legacy PM 的区别一句话：legacy 靠虚函数加全局注册表、pass 之间用字符串声明依赖，NewPM 是模板加显式嵌套的四层 PassManager，分析结果由 AnalysisManager 缓存，整条管线还能用一个字符串描述（-passes='default<O2>'）。

analysis 与 transform：分工在「有没有结果要被别人拿走」

Analysis pass 不改 IR，产出一个可查询的对象：DominatorTree（谁支配谁）、LoopInfo（循环嵌套结构）、AAResults（两个指针会不会重叠）、ScalarEvolution（循环里的表达式关于迭代变量的闭式），结果由 AnalysisManager 惰性缓存。Transform pass 改 IR，然后返回一个 PreservedAnalyses，声明「我改完之后哪些分析还有效」。

这个声明是整套机制的关键，也是写 pass 最容易出错的地方：改了 CFG 却声称保留了 DominatorTree，后面的 pass 就会拿着一棵过期的支配树做决策。所以拿不准就返回 PreservedAnalyses::none()——代价是重算，不是错。

为什么同一个 pass 要跑很多遍

-O2 的管线里 InstCombine 出现十几次，SimplifyCFG、GVN、SROA 也都不止一次。这不是配置冗余，而是因为优化之间在互相喂饭：内联搬进来的常量实参让常量传播有了活干；常量传播把一个条件变成常量，SimplifyCFG 于是能删掉一整个分支；分支删掉后两个基本块合并，块内的 InstCombine 又冒出新模式；块合并可能让某个聚合不再逃逸，SROA 能再拆一次、mem2reg 再提升一批。

理想的优化器应该「跑到不动点为止」，现实做不到：这个过程不保证收敛，而编译时间有预算。LLVM 的做法是手排一个固定顺序、在关键位置重复几个便宜且收益高的 pass，然后接受「有些机会就是被错过了」——这也解释了为什么同一份源码在不同 LLVM 版本上性能会有差异。

LTO：把链接也搬到 IR 层

普通编译在 .o 这一层链接，机器码已经定型，跨 .cpp 的内联和 DCE 无从谈起。LTO 把每个 TU 的 bitcode 塞进 .o，链接器认出来、合回 IR 再优化一轮——这也是 §3.3 那条「别让地址逃逸」的救济手段。

常用命令

命令用途
clang -S -emit-llvm -O0 a.c -o a.ll吐 textual IR
clang -c -emit-llvm a.c -o a.bc吐 bitcode（LTO 进 .o）
opt -passes='mem2reg,instcombine' -S a.ll跑指定 pass
opt -passes='default<O2>' -print-pipeline-passes列出 -O2 管线
opt -O2 -print-after=gvn看某 pass 之后的 IR
opt -O2 -opt-bisect-limit=N二分定位引入 bug 的 pass
opt -time-passes哪个 pass 慢
opt -load-pass-plugin=… -passes=call-counter跑自己的插件

7 个关键优化 Pass 内部

Inliner · mem2reg · GVN · LICM · SROA · Vectorize · InstCombine

真正拉开 -O0 和 -O2 的是这七个；其余上百个多半是清理工。

Pass干什么卡点
Inliner函数体替换 call小函数 / 常量实参；后续优化前提
mem2regentry 不逃逸 alloca → SSA没它 GVN/LICM 空转；见 §3
GVN等价表达式同一编号MemorySSA + AA 还能消 load
LICM循环不变量外提AA 说重叠就停
SROA聚合拆 scalar 再 mem2reg没它小对象全走栈
LoopVectorize无依赖循环 → SIMD要 noalias、可数迭代
InstCombine局部 peephole每个 transform 后都跑

下面每一节先给一句「它在源码层面对应什么写法」：知道自己写的哪种代码在喂哪个 pass，比知道它怎么实现有用得多。

7.1 Inliner — 函数体替代 call

源码层对应：所有小函数——getter、operator[]、lambda、模板里的一行辅助函数、<algorithm> 里几乎每个算法的内层。

它本身只省下一条 call，真正的收益是把两个函数的 IR 放进同一个作用域：实参的常量传得进去、返回值的常量传得出来、两边的访存能一起做别名分析。所以它是优化的使能器，加速多半要记在它后面那几十个 pass 的账上。决策靠 cost（被调函数指令数，可简化的部分打折）与 threshold（-O2 基线 225）比大小。

inline 关键字和内联基本无关，它管的是链接。真正起作用的是 always_inline（绕过 cost 模型，套在大函数上会让体积膨胀、I-cache 变差）、noinline（把冷路径隔出去，让热函数更容易被调用者内联），以及 LTO——别的 .cpp 里的函数当前 Module 没有它的 IR，内联无从谈起。

7.2 mem2reg — 栈槽提升到 SSA

只提升 entry 块里、地址不逃逸、且被整体 load / store 的槽。源码层对应：所有局部变量；你唯一能做的配合是「别让地址逃逸」，见 §3.3。

7.3 GVN — 等价表达式编号

GVN 前 · 算了两遍
%a = add i32 %x, %y
%b = add i32 %x, %y
%c = mul i32 %a, %b
GVN 后 · 公共子表达式删掉
%a = add i32 %x, %y
%c = mul i32 %a, %a      ; %b 消失

源码层对应：重复计算——同一表达式在相邻几行写了两遍、v.size() 在循环条件和循环体里各调一次、同一个数组元素被 load 两次。配上 MemorySSA 它还能消冗余的 load，但成败取决于别名分析：中间夹一个看不见函数体的 call，这次 load 就消不掉。

所以「手工把重复表达式提到临时变量」多半是白做的（GVN 做得比你全）。但「把 load 提到循环外」经常真有用，因为你知道那块内存没人改、而编译器不知道。

7.4 LICM — 循环不变量外提

源码层对应：循环里每圈算出同一结果的东西——a[i] = b[i] * scale * 2 里的 scale * 2、写在循环条件里的 strlen(s)、循环体里的 obj.config().timeout()。

外提除了要求「值不变」，还要求外提本身安全：被提的指令若可能出错（除法、load）而循环可能一次都不执行，外提就等于凭空执行了一条本不会执行的指令。

7.5 SROA — 聚合拆标量

源码层对应：小结构体传参与返回、std::pair / std::optional、聚合初始化的临时对象、按值捕获的 lambda 闭包。它先按字段把整块内存切成独立的 alloca，再各自交给 mem2reg。

这是 C++ 零成本抽象在 IR 层的兑现点。std::optional<int> 在内存里是 4 字节加一个标志位加 padding，SROA 之后就是一个 i32 加一个 i1，和手写「一个 int 加一个 bool」完全一样；返回小结构体、string_view 按值传也都不比传两个裸标量贵。失效条件和 mem2reg 一样：地址逃逸，或整块 memcpy。

7.6 Loop Vectorizer

源码层对应：对连续内存做同一件事的循环——数组求和、逐元素乘加、找最大值。它把 N 圈标量循环改成 N/W 圈向量循环（<8 x float>）加一个处理尾巴的 remainder 循环。条件很硬，缺一条就整个放弃：迭代次数要能写成关于循环变量的表达式（while (*p++) 基本没戏）、迭代间无依赖、访存无别名冲突。而 sum += a[i] 这种规约要重排浮点加法，而浮点加法不满足结合律，所以默认不做。

实操：循环体内不调不透明函数、用连续索引访问、指针加 __restrict__。成没成不要靠猜，用 §9.1 那条 -Rpass 直接问编译器。

7.7 InstCombine

源码层对应：没有。它匹配的模式绝大多数不是人写出来的，而是前面的 pass 产生的——内联展开后的冗余、常量传播留下的 x * 1。它做 x + x → x << 1 这类局部重写，单看都省不了几个周期，真正的作用是把 IR 归一化：同一语义的十种写法收敛成一种，后面 GVN 和向量化才匹配得上——这就是它要跑十几次的原因（§6.2）。

所以不用手写位运算技巧。无符号数上 x / 2 和 x >> 1、x % 16 和 x & 15 生成的代码完全一样；反过来手写在有符号数上会算错（-7 / 2 是 -3，-7 >> 1 是 -4）。
08

写自己的 Pass

NewPM 插件 · IRBuilder 插桩

最快的理解路径：写一个 NewPM 插件。分析 pass 返回 PreservedAnalyses::all()；改 IR 的返回 none()，逼着 PM 重算分析。

API作用
PassInfoMixin<T>NewPM 插件基类（CRTP）
run(Function&, FAM&)每个函数调一次；循环两层 BB → Instruction
isa<CallInst> / dyn_cast识别 / 转型指令
llvmGetPassPluginInfo动态库入口，用 -passes=名字 挂上
IRBuilder<>在某条指令前插入新 IR
Module::getOrInsertFunction声明运行时钩子（__asan_report 那一类）

Sanitizer、coverage、profiler 的核心就是最后两行：在 call 前 IRBuilder 再插一个 call @__my_log。编译：opt -load-pass-plugin=libMyPass.so -passes=call-counter。细节见 Sanitizer 内部。

不用真写插件也能用上这套机制——opt -passes= 接受一个管线描述串，语法和 NewPM 的嵌套层级一一对应：'mem2reg,instcombine' 顺序跑两个 function pass，'require<loops>,loop(licm)' 先要分析再在 loop 层跑 transform，'default<O2>' 则是 clang 用的那一整条。它的价值在于隔离：只跑那一个 pass、看前后 IR，不让其余一百多个一起插手（§9.1）。

09

调试 Pass

print-after · opt-bisect · FileCheck

命令已收进 §6 那张表。这里只补判据：

  • -print-after=gvn 看某一个 pass 之后的 IR；-print-after-all 会炸日志。
  • -opt-bisect-limit=N：bug 还在就降 N，没了就升 N，锁定那个引入回归的 pass。
  • 单测用 llvm-lit + FileCheck：; RUN: opt -passes=instcombine -S %s | FileCheck %s，然后 ; CHECK-NEXT: 钉住改写后的 IR。测的是「(x+x)+(x+x) 变成 x*4」这类局部契约。

对普通 C++ 工程师最有用的那一条：确认优化到底有没有发生

调性能时最常见的判断失误，是假设某个优化发生了——「这函数这么小，肯定被内联了」「这循环这么规整，肯定向量化了」。这两句都能用一条命令验证，而且不需要读汇编：

想确认什么怎么问看什么
抽象有没有被拆开clang -O2 -S -emit-llvm -o - a.cpp热函数里还剩几个 alloca；一个不剩说明 SROA + mem2reg 全做完了
某个调用有没有被内联同上，或 -Rpass=inlineIR 里还有没有那条 call
循环有没有向量化-Rpass=loop-vectorize 加 -Rpass-missed=…编译器一句话给出结论和失败原因
到底是哪个 pass 做的opt -passes='sroa' -S x.ll只跑它、前后对比，不受别的 pass 干扰
哪些 pass 真改动了 IRopt -passes='default<O2>' -print-changed -S只打印真有改动的那些

顺序上先用 -Rpass* 系列问「成了没有、为什么没成」，这一组输出是专门为最终用户设计的；只有需要精确到指令时才去看 IR。

看 IR 时务必用和生产一致的优化等级与目标平台：-march=native 会改变可用指令和向量宽度，直接改变向量化的成败——godbolt 上那份漂亮的输出，有时只是因为它默认开了一个你生产里没开的 -march。
