GDB 调试 C++ · 系列 05 / 06

Multi-thread Debugging：C++ 多线程程序如何用 GDB

多线程 bug 是 C++ 里最折磨人的一类：程序不崩，只是卡住；或者某个线程悄悄占满 CPU；或者偶发地算错数。这一篇教你用 GDB 把一个「卡死」的多线程进程就地冻结、逐线程验尸：info threads 看全景、thread apply all bt 一次拿到每个线程在哪、再顺着锁的等待关系找出死锁。最后用一个经典双 mutex 死锁案例完整走一遍。

重难点 阅读 ~15 min 前置：本系列 01–03 pthread / std::thread
info threads / thread thread apply all bt 死锁 / mutex 等待 单文件 · 无 CDN 依赖
01 GDB 是什么 02 断点与执行控制 03 栈 / 帧 / 变量 04 内存 / 寄存器 / 汇编 05 多线程调试 06 Crash 实战
编译多线程程序记得链接 pthread

本篇示例用 std::thread，Linux 下编译需要：g++ -g -O0 demo.cpp -o demo -pthread。少了 -pthread 可能链接失败或运行异常。

01

多线程为什么更难调

bug 从「崩溃」变成「卡住」和「偶发」

单线程程序出错，通常直接崩，bt 一看就知道。多线程的麻烦在于：

  • 不崩，只卡：死锁时所有相关线程都在「等」，程序像睡着了，没有任何报错；
  • 偶发、难复现：数据竞争依赖线程调度时序，跑 100 次可能只错 1 次；
  • 现场分散：问题不在「某一行」，而在「若干线程此刻各自的状态与它们持有/等待的资源」之间的关系。
多线程调试的核心思路转变

单线程调试问「执行到哪了」；多线程调试问「每个线程分别在哪、在等什么、谁持有它想要的东西」。所以第一动作不是单步，而是冻结全场 + 给所有线程拍一张「集体照」—— 这正是 thread apply all bt 的用途。

用一段能直接运行的多线程程序作背景：

// threads.cpp — g++ -g -O0 threads.cpp -o threads -pthread
#include <thread>
#include <mutex>
#include <condition_variable>
#include <chrono>

std::mutex mtx;
std::condition_variable cv;
bool ready = false;

void worker() {                       // 忙等，吃 CPU
    volatile long x = 0;
    while (true) ++x;
}
void waiter() {                       // 等条件变量，睡着
    std::unique_lock<std::mutex> lk(mtx);
    cv.wait(lk, []{ return ready; });
}
int main() {
    std::thread t1(worker);
    std::thread t2(waiter);
    std::this_thread::sleep_for(std::chrono::hours(1));  // 主线程也在睡
    t1.join(); t2.join();
}
02

info threads：一眼看全所有线程

先点名，再问话

程序跑起来后（或用 gdb -p <pid> attach 到一个卡住的进程），先 Ctrl+C 让 GDB 冻结全部线程，然后：

(gdb) info threads
  Id   Target Id                     Frame
* 1    Thread ... "threads" (main)   0x... in nanosleep ()          # 主线程在 sleep
  2    Thread ... "threads"          0x... in worker ()             # t1 在忙等
  3    Thread ... "threads"          0x... in ...cv wait...         # t2 在等条件变量
列含义
*GDB 当前所在线程（命令默认作用于它）
IdGDB 给的线程编号（1,2,3…），后续用它切换
Target Id操作系统线程标识（LWP / pthread id）
Frame该线程此刻正停在哪个函数 —— 最有信息量的一列
Frame 列就是「体检报告首页」

光看 Frame 列往往就能猜到问题：停在 nanosleep = 在睡；停在 __lll_lock_wait / pthread_mutex_lock = 卡在抢锁；停在 futex / cv wait = 在等条件变量；停在自己的业务函数且 CPU 高 = 忙等或死循环。看到多个线程都卡在 lock，就要高度怀疑死锁。

03

thread / thread apply：切换与批量操作

点名某个线程，或让所有线程一起报告

命令作用
thread 3 / t 3切换到 3 号线程，之后 bt/p 都作用于它
thread apply 2 3 bt只对 2、3 号线程执行 bt
thread apply all bt对所有线程执行 bt（最常用）
thread apply all -- p errno对所有线程执行任意命令
 
(gdb) thread 3           # 切到等条件变量的线程
[Switching to thread 3 ...]
(gdb) bt                 # 看它的调用栈：waiter → cv.wait → futex
(gdb) info locals        # 看它本地状态（ready 是否为 true 等）
切换线程 = 切换整个观察上下文

thread N 之后，你在第 03 篇学的 bt / frame / info locals / p 全都作用在这个线程的栈上。多线程调试本质就是「在多个线程之间反复切上下文」，逐个盘问它们的调用栈和局部状态。

04

thread apply all bt：核心杀招

一条命令，拿到全体线程的调用栈快照

这是多线程调试的「一键验尸」：把每个线程当前的完整调用栈一次性全打出来。分析卡死/死锁时，你几乎总是先敲它。

(gdb) thread apply all bt

Thread 3 (Thread ... "threads"):
#0  futex_wait (...)
#1  ... in std::condition_variable::wait(...)
#2  waiter () at threads.cpp:16
#3  ...

Thread 2 (Thread ... "threads"):
#0  worker () at threads.cpp:12        # 停在 while(true) ++x

Thread 1 (Thread ... "threads"):
#0  nanosleep (...)
#1  main () at threads.cpp:22
为什么它是杀招

它把「散落在各线程里的现场」压缩成一屏可对比的信息。你不再需要一个个 thread N; bt，而是一眼扫过去找规律：哪些线程卡在同一个锁 / 同一个函数？谁在等、谁在跑？死锁的两个线程会双双停在 pthread_mutex_lock，一比对就现形。生产上 attach 到卡死进程后，thread apply all bt 的输出往往就是提交给团队的第一手「病历」。

小技巧

线程很多时，用 set logging on 把输出存到文件再慢慢看；或 thread apply all bt 5 只看每个线程最里面 5 层，减少噪音。

05

10 个线程各自卡在哪里

把「一堆线程」变成「一张清晰的状态表」

面对一个有 10 个线程的服务进程「怎么快速知道每个线程现在在哪」？答案就是 thread apply all bt，然后把输出归纳成一张表。比如一个典型服务器可能长这样：

Thread 1
 └── main()                    # 主线程，epoll_wait 等事件
Thread 2
 └── worker()                  # 业务线程，处理任务
Thread 3
 └── network_loop()            # IO 线程，recv 阻塞
Thread 4
 └── mutex_wait()              # 卡在抢某把锁 ← 可疑
从「集体照」提炼三类信号
  • 正常阻塞：停在 epoll_wait/recv/accept/cv.wait —— 在等活干，健康；
  • 可疑等待：多个线程停在 pthread_mutex_lock —— 可能锁竞争严重或死锁；
  • 异常忙碌：停在业务函数、且反复 continue 后位置不变或在小范围打转、CPU 100% —— 忙等/死循环。
诊断「某线程 CPU 占用异常」

如果 top -H -p <pid> 显示某个 LWP 占满一个核，把它的 LWP 对到 GDB 的线程号（info threads 的 Target Id 里有 LWP），thread N 切过去，反复 continue 再 Ctrl+C 几次看它总停在哪 —— 若总在某个循环里，就是它在空转。这种「多次采样看落点」的手法，是穷人版的 profiler（真要做统计性能分析该用 perf，见第 06 篇工具对比）。

06

死锁 / 卡住 / 等待的现场分析

GDB 观察的是「结果」，你来推「因果」

症状GDB 里的表现下一步
死锁≥2 个线程停在 pthread_mutex_lock，互不前进看各自 bt，找「谁持有、谁在等」的环
线程卡住停在某阻塞调用，continue 后不动看它等的是锁、cv 还是 IO
mutex 等待bt 里有 __lll_lock_wait找持有该 mutex 的线程
条件变量等待停在 condition_variable::wait/futex检查唤醒条件（谓词、notify 是否发生）
某线程 CPU 高多次采样总落在同一循环看循环退出条件为何不满足
某线程异常退出info threads 里少了它为其入口设断点，看它怎么结束/崩
找「谁持有锁」的实用技巧

Linux 的 std::mutex 底层是 futex，其内部字段常记录持有者的线程 ID（TID）。当线程卡在 pthread_mutex_lock 时，可以 frame 到锁相关帧、p mutex（或查看 __data.__owner 字段）看当前 owner 的 TID，再回 info threads 找到那个持有者线程，看它为什么迟迟不释放。适用条件：具体字段名依赖 glibc/实现版本，未必稳定； 更通用的做法是靠调用栈的等待关系推断。

07

案例 3：两个 mutex 的经典死锁

加锁顺序不一致 → 抱死。用 GDB 完整定位一遍

CASE 3 · Deadlock

两个线程、两把锁，加锁顺序相反 —— 教科书级死锁：

// deadlock.cpp — g++ -g -O0 deadlock.cpp -o deadlock -pthread
#include <thread>
#include <mutex>
std::mutex A, B;

void threadA() {
    std::lock_guard<std::mutex> la(A);   // 先锁 A
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    std::lock_guard<std::mutex> lb(B);   // 再要 B ← 卡在这
}
void threadB() {
    std::lock_guard<std::mutex> lb(B);   // 先锁 B
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    std::lock_guard<std::mutex> la(A);   // 再要 A ← 卡在这
}
int main() {
    std::thread t1(threadA), t2(threadB);
    t1.join(); t2.join();               // 永远 join 不完
}

第一步：程序卡死后 attach / Ctrl+C，看全景

$ gdb ./deadlock
(gdb) run
... 程序挂起不动，按 Ctrl+C ...
(gdb) info threads
  Id   Frame
* 1    ... pthread_join ...            # main 在等 join
  2    ... __lll_lock_wait ...  threadA # 卡在锁
  3    ... __lll_lock_wait ...  threadB # 也卡在锁 ← 两个都卡！

第二步：thread apply all bt，看两个线程各卡在哪把锁

(gdb) thread apply all bt

Thread 2 (threadA):
#0  __lll_lock_wait
#1  pthread_mutex_lock
#2  ... std::mutex::lock (this=&B)   # A 线程：已持 A，正等 B
#3  threadA () at deadlock.cpp:11

Thread 3 (threadB):
#0  __lll_lock_wait
#1  pthread_mutex_lock
#2  ... std::mutex::lock (this=&A)   # B 线程：已持 B，正等 A
#3  threadB () at deadlock.cpp:18

第三步：拼出等待环 → 死锁定案

Thread A（线程 2）

已持有 A
正在等待 → B

Thread B（线程 3）

已持有 B
正在等待 → A

A 等 B，B 等 A —— 环形等待，谁也不放手
怎么从 GDB 输出「读」出死锁

关键信息在 #2 那帧的 this=&A / this=&B：它告诉你每个线程正想锁哪一把。线程 2 想要 B、线程 3 想要 A；再结合代码知道它们各自已持有 A、B —— 两条「持有→等待」的边首尾相接成环，就是死锁的充要现场。根因是加锁顺序不一致；修复方法是全局统一加锁顺序（都先 A 后 B），或用 std::scoped_lock(A, B) 一次性按避免死锁的算法同时上锁。

08

GDB 不是 TSan：工具边界

GDB 擅长看「卡死的静态现场」，不擅长抓「一闪而过的竞态」

关键边界

GDB 可以帮助观察现场，但它本身不是 ThreadSanitizer 的替代品。死锁、卡住这种「稳定停住」的问题，GDB 一冻结就看得清清楚楚。但数据竞争（data race）是「两个线程没同步地访问同一变量」，往往稍纵即逝、只在特定调度下发生 —— GDB 断点还会改变时序（观察者效应），越调越不复现。这类问题应交给 TSan。

问题类型首选工具原因
死锁 / 卡住 / 等待GDB状态稳定，冻结即可逐线程分析
数据竞争 Data RaceTSan需要全程监控内存访问的先后关系
内存越界 / UAFASan插桩检测非法访问
内存泄漏 / 非法访问Valgrind运行时动态检查

完整的工具对比（GDB / ASan / TSan / Valgrind / Core Dump / perf）在 第 06 篇集中展开。记住原则：真实项目从不是「只用 GDB」，而是多工具组合。

09

核心结论 + 常见误区

  • 多线程调试先冻结全场（Ctrl+C / attach），再逐线程验尸，而不是急着单步。
  • info threads 看全景，Frame 列就是每个线程「卡在哪」的第一手线索。
  • thread N 切上下文，thread apply all bt 一键拿全体调用栈快照。
  • 死锁 = 环形等待：从各线程「已持有 / 正等待哪把锁」拼出环即定案。
  • GDB 抓死锁，不抓竞态：data race 交给 TSan，工具要组合用。

❌ 多线程问题都能用 GDB 定位。 死锁/卡住可以；数据竞争这种时序敏感、稍纵即逝的问题该用 TSan，GDB 断点还会改变时序掩盖问题。

❌ 断点只影响当前线程。 默认 GDB 命中断点会停整个进程的所有线程（all-stop 模式）；如需只停一个线程要用 non-stop 模式，行为差异很大。

❌ 线程编号（Id）等于系统 TID。 GDB 的 Id 是它自己的编号，系统线程标识在 Target Id（LWP）里，排查 CPU 高线程要用 LWP 对应。

❌ 看到线程停在 lock 就是死锁。 也可能只是正常的锁竞争在排队；死锁的判据是存在环形等待且不再推进。

10

面试问题

点击每道题展开参考答案（先自测，再对照）。

  1. 基础如何查看某个线程的调用栈？

    先 info threads 找到目标线程编号，thread N 切过去，再 bt 看它的调用栈；或直接 thread apply N bt 一步到位。

  2. 基础thread apply all bt 有什么用途？

    对所有线程一次性执行 bt，得到全体线程当前调用栈的快照。用于快速判断每个线程卡在哪里、是否有多个线程堵在同一把锁上，是分析卡死/死锁的第一动作。

  3. 基础一个进程 10 个线程，怎么快速知道每个线程在哪？

    info threads 看 Frame 列速览，再 thread apply all bt 拿完整栈，把结果归纳成「线程→函数/等待对象」的表，识别出正常阻塞、可疑锁等待、异常忙碌三类。

  4. 原理如何用 GDB 分析死锁？

    程序卡死后 attach 或 Ctrl+C 冻结，thread apply all bt 查看所有线程栈；找出停在 pthread_mutex_lock 的线程，通过栈帧参数（如 this=&某mutex）看每个线程已持有哪把、正等哪把锁，若形成环形等待即为死锁，根因通常是加锁顺序不一致。

  5. 原理GDB 命中断点会停一个线程还是所有线程？

    默认 all-stop 模式：任一断点命中会暂停整个进程的所有线程，便于观察一致的全局快照。也可切到 non-stop 模式让其他线程继续跑、只停命中的线程，适合调试长时间运行的服务，但分析更复杂。

  6. 进阶GDB 和 TSan 有什么区别？多线程 bug 该怎么选？

    GDB 是交互式调试器，擅长「稳定停住」的问题（死锁、卡死），冻结后逐线程分析。TSan 是编译期插桩的检测器，全程监控内存访问的先后关系，专门发现数据竞争这种时序敏感、偶发的问题。死锁用 GDB，data race 用 TSan。

  7. 进阶某个线程 CPU 占用 100%，怎么用 GDB 定位它在空转什么？

    用 top -H -p pid 找到占核的 LWP，映射到 GDB 线程号并 thread N 切过去；多次 continue + Ctrl+C 采样，若总落在同一循环，就检查该循环的退出条件为何不满足。要做统计性能剖析则应改用 perf。
