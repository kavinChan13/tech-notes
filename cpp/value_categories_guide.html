03

引用类型与「引用折叠」规则

三种引用 · 万能引用 (Universal / Forwarding Reference) · 引用折叠规则（Reference Collapsing）· 何时该用 & / && / const& / 按值：接口设计决策

3.1 三种引用

引用能绑哪些用途
T&仅 lvalue（非 const）修改原对象
const T&所有（lvalue / xvalue / prvalue）只读不复制（万能只读参数）
T&& (具体类型)仅 rvalue（xvalue / prvalue）移动构造、移动赋值
T&& (模板参数)万能引用，看实参完美转发
int x = 42;
int&       a = x;            // ✅ lvalue → T&
int&       b = 42;           // ❌ rvalue 不能绑非 const T&
const int& c = 42;           // ✅ const T& 万能只读
int&&      d = 42;           // ✅ rvalue → T&&
int&&      e = x;            // ❌ lvalue 不能绑 T&&
int&&      f = std::move(x); // ✅ xvalue → T&&
一旦 T&& d = 42; 成立后，d 本身是 lvalue（因为它有名字、可取地址）！
"右值引用变量是 lvalue" — 这是绕过最多人的一个点。

具名 T&& 只约束「怎么进来」，不改变「进去之后是左值」

类型 int&& 只约束调用时必须传入右值。函数体内的形参有名字 → 表达式是 lvalue → 重载决议走左值那条。

void f(int&);     // ① 左值
void f(int&&);    // ② 右值
void g(int&& x) {
    f(x);            // 调 ①：x 有名字 → lvalue → int&
    f(std::move(x)); // 调 ②：cast 成 xvalue → int&&
}
设计原因：若具名 && 自动当右值，g 里写两次 consume(x) 会悄悄把对象掏空第二次——第一次已经移走，第二次读的是 moved-from。语言选择「默认安全：有名字就当左值，要交出去必须显式 std::move」。
🏷️
生活类比：门禁 vs 工牌
int&& 是门禁——进门必须是「即将搬走的货」。进门之后货架上贴了工牌（有名字），仓库默认当库存，不会自动装车。要出库必须再开一张调拨单（std::move）。

3.2 万能引用 (Universal / Forwarding Reference)

仅当 T&& 出现在模板参数推导上下文，T 是要推导的模板参数，且不带 const/volatile 修饰时，它才是万能引用，能绑任何值类别。

template<class T>
void universal(T&& arg);    // ✅ 万能引用

template<class T>
void notUniversal(const T&& arg);  // ❌ 有 const，是普通右值引用

template<class T>
void notUniversal2(std::vector<T>&& arg);  // ❌ T 不是直接参数

auto&& x = expr;             // ✅ auto&& 也是万能引用

3.3 引用折叠规则（Reference Collapsing）

当模板推导出 T = int&，那 T&& 等于什么？引用的引用语法上不允许，所以 C++ 定义了折叠规则：

原始折叠后
T& &T&
T& &&T&
T&& &T&
T&& &&T&&

口诀："一个 lvalue ref 进来，结果就是 lvalue ref；两个 rvalue ref 才是 rvalue ref"。

template<class T>
void f(T&& arg);

int x = 1;
f(x);     // 实参是 lvalue → T 推导为 int& → T&& = int& && = int&
f(42);    // 实参是 prvalue → T 推导为 int → T&& = int&&
f(std::move(x));  // xvalue → T 推导为 int → int&&

这就是为什么万能引用能同时绑左值和右值 — 通过推导规则 + 折叠规则联合实现。

3.3.1 「引用的引用」到底是从哪冒出来的

你手写 int& & r; 一定编译错 —— 折叠规则不是给人写代码用的，而是给类型推导系统兜底的。只有下面这几条「间接」路径会在编译器内部合成出引用的引用：

来源例子中间类型折叠为

int x; f(x);		 T = int& → 形参 int& &&int&
② auto&&int x; auto&& r = x; auto = int& → int& &&int&
③ 类型别名 typedef/usingusing LR = int&; LR&& r = x; int& &&int&
④ decltypedecltype(e)&& r = ...;（e 本身已是引用） 视 e 而定按表折叠
🏷️
生活类比 · 转租链上的一张「拆迁通知」
& 像「屋里还住着人」的标签，&& 像「已挂拆迁牌，东西随便搬」的标签。 一条转租链上只要出现过一次「还住着人」，整条链就只能按「有人住 → 不许搬东西」处理， 这就是折叠表里 三行都得到 & 的直觉来源；只有从头到尾全是拆迁牌（&& &&），才允许搬。

3.3.2 完整链路：推导规则 + 折叠规则「接力」

万能引用能同吃左右值，靠的不是折叠一条规则，而是两条规则接力：

规则 A（特殊推导，仅在 forwarding reference 上下文生效）：实参是左值 → T 推导为 U&（把引用编进 T）；实参是右值 → T 推导为 U（不带引用）。
规则 B（引用折叠）：把 T&& 代入后出现的「引用的引用」按上表压平。

把两步一起走完，才能看懂 std::forward 为什么能工作：

3.3.4 折叠规则到底带来什么好处：消灭「重载组合爆炸」

折叠规则本身只是个类型运算，它的价值全在于让「一个模板」替代「2ⁿ 个重载」。假设你要写一个把参数原封不动传给 T 构造函数的工厂，且不许损失值类别：

// ❌ 没有万能引用 + 折叠时，只能穷举每个参数的「左值 / 右值」组合
void emplace(const A& a, const B& b);
void emplace(const A& a, B&&      b);
void emplace(A&&      a, const B& b);
void emplace(A&&      a, B&&      b);   // 2 个参数 → 4 个重载
// 3 个参数 → 8 个；4 个 → 16 个；参数个数不定（emplace_back）→ 根本写不出来
// 还没算上 const / volatile 组合

// ✅ 万能引用 + 折叠 + forward：一个函数覆盖所有组合
template<class... Args>
T& emplace_back(Args&&... args) {
    ::new (end_) T(std::forward<Args>(args)...);
    return *end_++;
}

① 一份代码覆盖 2ⁿ 组合

make_unique / make_shared / emplace_back / emplace / std::thread / std::invoke / std::bind_front / std::apply 全部建立在这条规则上。没有折叠，就没有现代 STL 的工厂族。

② 零额外拷贝

右值实参从调用点一路保持右值，最终落到移动构造 / 原地构造。中间每一层包装都不产生临时对象 —— 这是"零成本抽象"在库层的具体体现。

③ const 正确性自动传递

const 被一起编进 T（见 3.3.2 第 2 行），所以不需要手写 const 重载。传 const 对象进去，内层收到的就是 const。

④ 按需实例化，二进制不虚胖

模板只为真实出现过的值类别组合生成代码。手写 4 个重载是「无论用不用都编进二进制」，模板是「用几个生成几个」。

3.4 什么时候该用 &、&&、const&、还是按值 —— 接口设计决策

前面讲的是「规则是什么」，这一节回答工程上真正要做的决定：写函数签名时到底选哪个。

📚
生活类比 · 借书的四种方式
const T& = 借你看，不许在上面写字（只读、零拷贝、什么书都能借）。
T& = 借你看，允许你批注，改动我这边也看得见（in-out 参数）。
T&& = 「这本书我不要了，撕页拆封都行」（可窃取资源）。
按值 T = 复印一份给你；如果我说「这份归你」（std::move），复印就省了。

3.4.1 参数传递决策表（背这一张就够）

你的需求推荐签名理由与代价
只读，类型小且平凡（int / double / 枚举 / 指针 / string_view / span / 迭代器） 按值 T一两个寄存器就传完；取引用反而多一次间接寻址，还妨碍编译器做寄存器分配
只读，类型大或有资源（string / vector / 自定义类） const T&零拷贝、能吃 lvalue/xvalue/prvalue 全部值类别。缺点：拿不到所有权，要存起来就必须拷贝
要修改调用方的对象（in-out） T&语义直接；缺点：调用点 f(a) 看不出 a 会被改 → 能用返回值就别用输出参数
接管 / 存起来（sink：setter、构造函数、push、任务提交） 按值 T + 函数内 std::move一份代码同吃左右值。右值：1 次移动；左值：1 次拷贝 + 1 次廉价移动
接管，且要「一次多余移动都不能有」 const T& + T&& 双重载代价最优但代码翻倍；参数一多就 2ⁿ 爆炸。标准库热点（vector::push_back）才这么写
泛型包装 / 转发（不知道调用方会给什么，也不该替它决定） 模板 T&& + std::forward<T>完美转发。缺点：必须进头文件、报错信息长、容易抢占其它重载（§12 第 6 条）
工厂 / 原地构造 变参模板 Args&&... + forwardemplace_back / make_unique 的标准做法，连临时对象都省掉
只读且只需要看内容、不关心容器 std::string_view / std::span比 const std::string& 更好：字面量、vector<char>、子串都能传进来且零构造。⚠ 不得存起来（无所有权）

3.4.2 实例：同一个 setter 的 4 种写法，数清每一次构造

// ① const&：经典 C++03 写法
struct W1 { std::string s;
    void set(const std::string& v) { s = v; } };

// ② 按值 + move：现代默认写法（Sutter 的 "sink parameter"）
struct W2 { std::string s;
    void set(std::string v)        { s = std::move(v); } };

// ③ 双重载：代价最优，代码最多
struct W3 { std::string s;
    void set(const std::string& v) { s = v; }
    void set(std::string&& v)      { s = std::move(v); } };

// ④ 完美转发：连「转成 string」这一步都能省
struct W4 { std::string s;
    template<class T>
    void set(T&& v)               { s = std::forward<T>(v); } };

三种典型调用下的实际代价（lv 是已有的 std::string 左值）：

写法w.set(lv)w.set(std::move(lv))w.set("literal")
① const& 1 次拷贝赋值
✔ 可复用 s 已有 buffer，常常不分配		 1 次拷贝赋值
✘ 右值性被浪费		 1 次临时 string 构造（分配）+ 1 次拷贝赋值
② 按值 + move 1 次拷贝构造（必然分配）+ 1 次移动赋值 1 次移动构造 + 1 次移动赋值（都是 O(1)） 形参直接由字面量构造（1 次分配）+ 1 次移动赋值
③ 双重载 1 次拷贝赋值（同 ①，可复用 buffer） 1 次移动赋值 — 最优 1 次临时构造 + 1 次移动赋值
④ 转发 1 次拷贝赋值（同 ①） 1 次移动赋值（同 ③） 0 个临时对象 — 直接命中 string::operator=(const char*)
选择建议（按优先级）
① 默认写法 ②（按值 + move）：一行代码，右值路径最优，左值路径只比最优多一次廉价移动。
② 但热路径上反复 set 同一个对象时改用 ①：② 的拷贝构造每次都要分配新内存，而 ① 的拷贝赋值能复用目标已有的 buffer。 「for (auto& row : rows) w.set(row.name);」这种循环里，① 往往比 ② 快。
③ 移动本身不便宜的类型（如 std::array<BigPOD, 64>、内部要逐个搬小对象、或干脆不可移动）→ 不要用 ②。
④ 库级 API、参数种类多、想省掉隐式转换的临时对象 → ④；对外只暴露 const&+&& 双重载（③）则给二进制兼容留了余地。
② 的隐藏风险：按值形参一旦被 std::move 掉，后面就不能再用它。 如果函数里要用参数两次（先校验再存），写成 if (!valid(v)) return; s = std::move(v); 是对的， 但 s = std::move(v); log(v); 就成了「读已移动对象」。

3.4.3 成员函数上的 & / &&（ref-qualifier）：给 *this 也分个值类别

const 限定了 *this 「能不能改」，ref-qualifier 限定 *this「是左值还是右值」。它有两个非常实用的用途。

用途 A：临时对象上取值时，自动升级为移动

class Config {
    std::string data_;
public:
    const std::string& str() const &  { return data_; }              // 左值调用 → 借出去
    std::string        str() &&       { return std::move(data_); }   // 右值调用 → 直接给
};

Config c = load();
auto a = c.str();              // c 还要继续用 → 拷贝（安全）
auto b = load().str();         // ✅ 临时对象反正要销毁 → 直接掏空，零拷贝

std::optional::value()、std::variant 的 get、流式 Builder 的 build() && 都是这个套路（C++23 起可以用 deducing this 一个函数搞定，见 §10b）。

用途 B：= delete 掉右值重载，把悬垂 bug 从运行期挪到编译期

class Owner {
    std::string buf_;
public:
    std::string_view view() const &  { return buf_; }
    std::string_view view() const && = delete;   // ★ 临时对象上取 view 必悬垂 → 直接禁掉
};

Owner o;
auto v1 = o.view();           // ✅ o 活着，view 安全
auto v2 = Owner{}.view();     // ❌ 编译期报错 — 而不是运行期读野内存
这是 && 的一个「反直觉」用法：用右值重载来禁止某类调用，而不是为了移动。 标准库里 std::regex_iterator、range 适配器对临时容器的限制（viewable_range 概念）都用了同一思路。 能主动提到「用 ref-qualifier + = delete 防悬垂」，比只会背折叠表更能体现工程视角。

3.4.4 什么时候不该用 &&

const T&& 作参数：能绑右值，却因为 const 而不能窃取 —— 几乎没有正当用途。唯一常见场景是 = delete 掉右值调用（如上面的 view() const && = delete）。
避免
返回 T&&：极易悬垂。std::string&& f() { std::string s; return std::move(s); } —— 返回时 s 已析构，调用方拿到野引用。返回值就按值返回，交给 RVO（§9）。
危险
小平凡类型的 && 重载（int&& / double&&）：没有资源可偷，移动 == 拷贝，纯粹增加重载集和编译时间。
无收益
把成员声明成 T&&：右值引用成员不延长所绑对象的生命周期（除了「临时量绑到构造函数引用形参」那种一次性延长），对象活过构造表达式就悬垂。要持有就按值持有。
危险
万能引用 T&& 和普通重载并存：万能引用是「完美匹配」，会抢走本该走隐式转换的重载，连拷贝构造都能抢（§12 第 6 条 / §13 第 16 题）。要用就配 requires / enable_if 约束。
需约束
该用的时候：① 移动构造 / 移动赋值；② sink 函数的性能关键重载；③ 泛型转发（配 forward）；④ ref-qualifier 区分「借 / 给」。
✅

4.1 std::move 不移动任何东西

它只是个 cast：把表达式无条件转换为右值引用（xvalue）。是否真正发生移动，由接收方决定。

// 标准库实现（简化）
template<class T>
constexpr std::remove_reference_t<T>&& move(T&& arg) noexcept {
    return static_cast<std::remove_reference_t<T>&&>(arg);
}

作用：把 arg（可能是 lvalue 或 rvalue）强制转为 xvalue → 之后调用 T(...) 时优先匹配移动构造。

误区：「std::move(x) 之后 x 就被销毁了」— 错。x 仍然存在，但状态变成「合法但未指定」。你可以给 x 重新赋值或析构，但不应该读它的值（除非你看了具体类型的文档）。 
std::string s = "hello";
std::string s2 = std::move(s);    // s2 拿走 s 的字符

s.size();    // 合法（不是 UB），但值未指定（通常是 0）
s = "world";  // 完全合法 — 重新赋值
// 但不要 assert(s == "hello") — 行为取决于实现

那「真正的移动」发生在哪？在移动构造函数体里。下图是 std::string 拷贝与移动的内存差别 —— std::move 的全部作用，只是让重载决议选中右边那条路：

对 int 写 std::move 几乎没意义

int x = 1; std::move(x); 如果丢掉结果（不接到任何接收方），x 仍是 1。std::move 只是 cast，真正的「移」发生在接收方的移动构造 / 移动赋值里。

int x = 1;
std::move(x);          // 结果丢掉 → x 仍是 1，什么都没发生
int y = std::move(x);  // y = 1，x 仍是 1：int 没有外置资源可偷
类型移动实际做什么相对拷贝
int / double / 指针本身按位复制寄存器宽度的值；源不必清空等于拷贝
string / vector / unique_ptr交出堆指针（或 buffer 指针），源置空O(1) vs O(n)
口诀：move 是授权，接收方才动手。标量没有可交的外置资源，授权了也只是一次拷贝。

4.2 为什么必须显式写 std::move：6 个真实场景

光知道「move 比 copy 快」不够用。真正要回答的是：在哪些代码位置，不写 std::move 就是 bug 或明确的性能损失？下面 6 个场景覆盖了工程里 95% 的 std::move 用法。

场景 ① 把对象塞进容器（最常见的性能漏点）

std::vector<std::string> lines;
std::string line;
while (std::getline(in, line)) {
    lines.push_back(line);              // ❌ 每行一次堆分配 + 一次 memcpy
    lines.push_back(std::move(line));   // ✅ 只搬 3 个指针
}
这里 std::move(line) 之后 line 处于「合法但未指定」状态，而下一轮 getline 会先清空再写入（它对内容没有前置要求）—— 所以这个写法是完全安全的，而且是读大文件时最典型的加速手段。
对 100 万行、每行 100 字节的文件：前者约 100 万次 malloc + 100 MB 的 memcpy；后者零次额外分配。

场景 ② 转移独占所有权 —— 不写 move 根本编译不过

auto conn = std::make_unique<Connection>(fd, peer);
pool_.push_back(conn);              // ❌ 编译错：unique_ptr 的拷贝构造 = delete
pool_.push_back(std::move(conn));   // ✅ 唯一出路

std::thread t(worker, std::move(payload));   // thread 只接受可移动构造的参数
std::promise<Result> p;
deliver(std::move(p));                        // promise / packaged_task / future 均 move-only
std::unique_lock lk(mu_);
handoff(std::move(lk));                       // 把「已持有的锁」交给别人释放
这一类的收益不是性能，而是语义：std::move 在调用点明确写出「所有权从这里转走了」。 配合 move-only 类型（unique_ptr / FileHandle / thread / promise），编译器会在你不小心想拷贝时直接报错 —— 这是 C++ 用类型系统表达资源所有权的核心手法。

场景 ③ 构造函数 / 成员初始化（新人最常漏的一处）

class User {
    std::string name_;
    std::vector<Order> orders_;
public:
    // ❌ 参数已经是一份本地副本了，再拷一次 = 白花两次分配
    User(std::string name, std::vector<Order> orders)
        : name_(name), orders_(orders) {}

    // ✅ 副本直接搬进成员
    User(std::string name, std::vector<Order> orders)
        : name_(std::move(name)), orders_(std::move(orders)) {}
};
这个漏点编译器不会警告，代码看起来完全正常，只是每次构造多两次堆分配 + 两次 memcpy。 开 clang-tidy 的 performance-unnecessary-value-param 和 performance-move-const-arg 可以自动查出来 —— 值得加进 CI。

场景 ④ 把资源移进 lambda / 协程闭包（异步编程必用）

auto buf = std::make_unique<char[]>(1 << 20);

io_.post([buf]{ ... });                   // ❌ 按值捕获 = 拷贝 → unique_ptr 不可拷贝 → 编译错
io_.post([&buf]{ ... });                  // ❌ 引用捕获 → 函数返回后 buf 已析构 → 悬垂

io_.post([buf = std::move(buf)]() mutable {  // ✅ C++14 初始化捕获：把资源搬进闭包
    process(buf.get());
});

任务要晚于当前函数执行时（线程池、事件循环、协程），「引用捕获」几乎一定悬垂，「拷贝捕获」对 move-only 类型不可行 —— [x = std::move(x)] 是唯一正确解。

场景 ⑤ 把成员「取出来」交给调用方

class Response {
    std::string body_;
public:
    const std::string& body() const & { return body_; }          // 借
    std::string        body() &&      { return std::move(body_); }  // 给（仅右值调用）
};

std::string s = fetch().body();   // ✅ 临时 Response 反正要销毁 → 零拷贝拿到 body

成员变量永远是 lvalue（它有名字），所以「把成员搬出去」必须显式 std::move，编译器不会替你做（§9.5 规则 ③）。

场景 ⑥ swap 与容器搬移 —— C++11 让存量代码免费变快的地方

template<class T>
void swap(T& a, T& b) {
    T tmp = std::move(a);   // C++03 这里是 3 次深拷贝（还可能抛 bad_alloc）
    a     = std::move(b);   // C++11 起是 3 次 O(1) 指针搬移，且可 noexcept
    b     = std::move(tmp);
}

std::swap、std::sort（元素交换）、std::rotate、vector 扩容、map 节点重排全部因此变快 —— 你不改一行代码，只要升到 C++11 且类型有移动构造，就白拿这些收益。这也解释了为什么 §10 强调移动构造必须 noexcept。

差距相差约 3 个数量级，且移动不会失败（可 noexcept，不触发 allocator）从「不可能」到「可行」
移动比拷贝快的真正原因不是「少复制字节」，而是「不碰 allocator」。堆分配要走全局/线程缓存、可能加锁、可能触发 mmap、还会污染 cache 并制造内存碎片；移动只动几个栈上标量。 所以移动的收益在高并发场景往往比单线程 benchmark 显示的更大 —— 它顺带消除了分配器上的竞争点。

4.3 那为什么编译器不能替我们自动 move？

既然 lines.push_back(line); 之后 line 明显不再被使用，编译器为什么不自动优化成移动？这是理解 std::move 存在意义的关键一问，答案有三层。

① 值类别是语法属性，不是数据流分析结论

重载决议在编译前端按表达式的静态值类别进行：line 有名字 → 一律 lvalue。要「自动 move」，编译器必须先证明「此处之后不会再读 line」，而这需要跨函数、跨翻译单元的别名与生命周期分析：line 可能被别处的指针 / 引用 / 另一个线程盯着。C++ 的分离编译模型 + 任意别名规则让这种证明无法可靠完成。

② 猜错的代价不对称

漏一次 move = 慢一点；错一次 move = 静默的逻辑 bug（调用方的对象被掏空，还不报错）。在「可能错」与「可能慢」之间，语言只能选默认安全：默认拷贝，移动必须由程序员显式授权。std::move 的本质就是这句授权：「我保证之后不再依赖它的值」。

③ 能证明的地方，标准确实自动做了

return 语句是唯一「语言层面能静态保证对象即将离开作用域」的场合，所以那里有隐式移动（甚至直接 copy elision）：

std::string f() {
    std::string s = "x";
    return s;   // 自动当 rvalue，甚至 NRVO 掉
}

④ 这个「自动」范围还在扩大

C++20 P1825 放宽了隐式移动的条件（返回按值形参、返回类型可转换等）；C++23 P2266 让 return 一个右值引用形参也能隐式移动。方向是：凡是编译器能证明的，都不再要求你写 std::move（这也是 §9 里「return std::move(local) 是反模式」的由来）。

「为什么 C++ 需要 std::move，别的语言（Rust）不需要？」
参考答案：Rust 默认就是移动语义，并用借用检查器在编译期保证 moved-from 对象不会再被使用 —— 它有能力做这个证明，因为语言从一开始就禁止了任意别名。 C++ 为了兼容既有语义（赋值 = 拷贝）和允许任意别名，只能反过来：默认拷贝 + 显式 std::move 授权 + moved-from 状态定义为「合法但未指定」，代价是这份安全性要靠程序员和工具（clang-tidy bugprone-use-after-move）来保证。

4.4 std::forward 完美转发

它根据模板参数 T 是否带引用，决定到底"做 move 还是不做"。专门给万能引用场景用。

// 标准库简化
template<class T>
constexpr T&& forward(std::remove_reference_t<T>& arg) noexcept {
    return static_cast<T&&>(arg);
}

关键：依赖引用折叠。如果 T 是 int&，T&& 折叠为 int&（不 move）；如果 T 是 int，T&& 是 int&&（move）。

template<class T>
void wrapper(T&& arg) {
    backend(std::forward<T>(arg));     // ✅ 完美转发
}

int x = 1;
wrapper(x);             // T = int& → forward 返回 int& → backend 收到 lvalue
wrapper(42);            // T = int → forward 返回 int&& → backend 收到 rvalue (能 move)
记忆口诀：
· std::move = 我确定要移动 → 无条件转 rvalue
· std::forward = 别人怎么传给我，我就怎么传出去 → 条件转

4.5 为什么需要 std::forward：包装函数的 5 种写法

std::forward 只在一个场景里出现：你写的函数是个「中间层」 —— 工厂、装饰器、线程池 submit、日志包装、emplace。这类函数不该替调用方决定「要不要移动」，只该把实参原样端到下一层。下面用同一个需求把 5 种写法全试一遍。

// 两个「按值接收 = 会把参数存起来」的 sink
void sink(std::string s);
void sink(std::unique_ptr<Frame> p);      // move-only 类型

// ① const T&：内层拿到的是 const& → 存起来必须拷贝，右值实参的移动机会白丢
template<class T> void w1(const T& x) { sink(x); }

// ② 按值：包装层自己先复制一份，纯浪费（中间层并不需要副本）
template<class T> void w2(T x)         { sink(std::move(x)); }

// ③ T&& 但直接传：x 有名字 → 它自己是 lvalue → 内层永远拷贝（§3.3.2 第 5 列）
template<class T> void w3(T&& x)       { sink(x); }

// ④ T&& + 无条件 move：把调用方的左值掏空 —— 真实事故，见下
template<class T> void w4(T&& x)       { sink(std::move(x)); }

// ⑤ T&& + forward：唯一正确解 ✅

REAL完整实例：线程池 submit

template<class F, class... Args>
auto ThreadPool::submit(F&& f, Args&&... args)
    -> std::future<std::invoke_result_t<F, Args...>>
{
    using R = std::invoke_result_t<F, Args...>;

    // ★ 任务要在「别的线程、稍后」执行 → 必须把实参搬进闭包（值语义），不能留引用
    auto task = std::make_shared<std::packaged_task<R()>>(
        [f   = std::forward<F>(f),                          // 右值可调用体 → 移动进闭包
         tup = std::make_tuple(std::forward<Args>(args)...)]() mutable {
            return std::apply(std::move(f), std::move(tup));  // 闭包只跑一次 → 这里可以 move
        });

    std::future<R> fut = task->get_future();
    {
        std::lock_guard lk(mu_);
        q_.emplace([task]{ (*task)(); });
    }
    cv_.notify_one();
    return fut;
}

4.6 实现细节：为什么 forward 的 <T> 不能省

// 标准库的两个重载（简化）
template<class T>
constexpr T&& forward(std::remove_reference_t<T>&  t) noexcept { return static_cast<T&&>(t); }
template<class T>
constexpr T&& forward(std::remove_reference_t<T>&& t) noexcept { return static_cast<T&&>(t); }

这个签名里有两个刻意的设计，都指向同一件事 —— 见 §3.3.2 的结论：实参的值类别信息只剩在 T 里。

① 形参写 remove_reference_t<T>& 而不是 T&&，是为了让 T 处于「非推导位置」。
假如写成 forward(T&& t)，T 就会从实参推导；而实参 arg（有名字）永远是 lvalue → 永远推出 T = U& → 永远折叠成 U& → forward 就变成「永远什么都不做」，彻底失效。 所以必须由调用者把 T 手动喂进去，编译器无从推导 —— 这不是 API 设计得啰嗦，而是唯一可行的方案。
② 真正的「条件」全在 static_cast<T&&> 这一句里，由引用折叠完成。
T = U&（调用方传的是左值）→ U& && 折叠为 U& → 转发成 lvalue，不移动；
T = U（调用方传的是右值）→ U&& → 转发成 xvalue，可移动。
也就是说 std::forward 全部魔法 = 「把 T 的形状原样翻译回值类别」，它自己一行运行时代码都没有。

④ moved-from 对象：什么能做，什么不能做

✅ 安全

  • 析构它
  • 给它重新赋值 / getline 写入
  • 调用无前置条件的成员：clear()、size()、empty()、reset()
  • 标准库容器/string 保证 moved-from 处于「合法但值未指定」状态

❌ 不安全

  • 断言/依赖它的内容（assert(s == "hello")）
  • 调用有前置条件的成员：front()、back()、operator[]、*it、对 moved-from unique_ptr 解引用（这些是真正的 UB）
  • 假设它一定为空 —— 小字符串优化（SSO）下短串移动后源可能仍有内容
自己写移动构造时，请把源对象置成明确的空状态（指针 nullptr、size 0），不要只留「反正没人会用」的心态 —— 这样 moved-from 对象既可安全析构，也可安全重新赋值，还便于调试定位。 工具面：clang-tidy bugprone-use-after-move + -fsanitize=address 能覆盖绝大多数 use-after-move。

Rule of 0 / 3 / 5（最重要的设计准则）

Rule of 0 的好处（举例） · Rule of 5 完整模板

Rule of 0（首选）

"不写任何特殊成员，让编译器全部默认生成"。

前提：所有成员都是已经管好资源的类型（vector、string、unique_ptr、shared_ptr）— 称为 RAII 友好。

这是现代 C++ 的金标准。

Rule of 3（C++03 时代）

如果你需要写任意一个： 析构、拷贝构造、拷贝赋值，三个都要写。

原因：之所以需要写其中之一，说明类有独占资源（裸 new/file fd）。析构要释放，拷贝要深复制，三者必须一致。

Rule of 5（C++11 起）

有了移动语义，三个变成五个：析构、拷贝构造、拷贝赋值、移动构造、移动赋值。

不一致就是 bug 的温床。

Rule of 5 的工程现实

真实代码里写 5 个成员是很麻烦的。策略：把"独占资源"封装进 RAII 类（如 unique_ptr 自定义 deleter），外层类回归 Rule of 0。

6.2 Rule of 5 完整模板

class Buffer {
    char* data_ = nullptr;
    size_t size_ = 0;
public:
    // 1. 默认构造
    Buffer() = default;

    // 自定义构造
    explicit Buffer(size_t n)
        : data_(new char[n]), size_(n) {}

    // 2. 析构
    ~Buffer() { delete[] data_; }

    // 3. 拷贝构造
    Buffer(const Buffer& other)
        : data_(new char[other.size_]), size_(other.size_) {
        std::memcpy(data_, other.data_, size_);
    }

    // 4. 拷贝赋值（copy-and-swap 惯用法 — 异常安全）
    Buffer& operator=(Buffer other) noexcept {     // ✅ 按值收（拷贝或移动）
        swap(other);
        return *this;
    }
    // ↑ 一个赋值搞定 拷贝赋值 + 移动赋值（编译器选择实参传递方式）

    // 5. 移动构造
    Buffer(Buffer&& other) noexcept
        : data_(other.data_), size_(other.size_) {
        other.data_ = nullptr;
        other.size_ = 0;
    }

    // 友元 swap
    void swap(Buffer& other) noexcept {
        using std::swap;
        swap(data_, other.data_);
        swap(size_, other.size_);
    }
};
copy-and-swap 惯用法 = 一个 operator=(Buffer)（按值收）+ swap = 同时实现拷贝赋值和移动赋值，且强异常安全保证。

    ~A() { LOG("destroying"); }       // 仅声明析构
};

// 因为 ~A 声明导致 移动操作不再自动生成

// 修复：显式 = default
struct B {
    std::vector<int> data;
    ~B() { LOG("destroying"); }
    B() = default;
    B(const B&) = default;
    B& operator=(const B&) = default;
    B(B&&) noexcept = default;       // ✅ 显式恢复
    B& operator=(B&&) noexcept = default;
};

9.1 三个术语梳理

术语含义C++17 强制?
RVO (Return Value Optimization)函数返回临时对象（prvalue）时，省略拷贝/移动✅ 强制（C++17 起）
NRVO (Named RVO)返回具名局部对象时省略拷贝/移动❌ 仍是允许但不强制
Copy Elision统称：编译器允许在某些场合省略拷贝/移动构造—

9.2 RVO（强制）

Buffer make_buffer(size_t n) {
    return Buffer(n);            // 临时 prvalue
}

Buffer b = make_buffer(1024);
// C++17 起：保证零拷贝。Buffer 直接在 b 的地址上构造。
// 这意味着即便 Buffer 不可拷贝/移动也能这么写。

9.3 NRVO（编译器自由选择）

Buffer make_buffer(size_t n) {
    Buffer b(n);                 // 具名
    b.init();
    return b;                    // NRVO 可能优化掉拷贝/移动
}
// 主流编译器都会优化，但标准不强制
千万不要写 return std::move(b);
这会阻止 NRVO（因为返回类型变了：本应 prvalue → 现在是 xvalue）。手动 move 让你失去零拷贝，反而强制做移动构造，比编译器优化差。

9.4 Copy Elision 的精确条件

必须满足下列全部条件之一，编译器才能 elide：

  1. return 语句返回与函数返回类型同类型（去 cv）的非 volatile 非函数参数的局部对象 → NRVO
  2. return 语句返回与函数返回类型同类型的临时对象（prvalue） → RVO（C++17 强制）
  3. throw 表达式抛出与 catch 类型同的局部对象 → 类似 NRVO
  4. 临时对象传给函数的by-value 参数（C++17 强制）

9.5 Copy Elision vs Move 对比

场景无优化有 RVO/NRVO
Buffer b = make_buffer();构造 + 拷贝/移动 + 析构 临时仅一次构造 — 直接在 b 地址
v.push_back(make_buffer())临时 + 移动到 vector直接在 vector 内构造（等价 emplace）
规则：
① 返回局部对象 → 直接 return obj;，不要 std::move
② 返回函数参数 → 必须 std::move（参数有具名→不能 NRVO）
③ 返回成员 → 必须 std::move（成员是 lvalue，不会被自动当 rvalue） 
struct Foo {
    Buffer buf;
    Buffer extract() {
        return std::move(buf);     // ✅ 成员是 lvalue，必须 move 才能移动构造返回
    }
};

Buffer forward_arg(Buffer b) {
    return std::move(b);          // ✅ 参数有名字，NRVO 不适用，需要 move
}

10.1 STL 容器的「强异常安全保证」

std::vector::push_back 在扩容时承诺：操作要么成功，要么 vector 状态完全不变（强保证）。

问题：扩容要把元素从旧 buffer 转到新 buffer。如果 T 的移动构造可能抛异常，转移过程中失败 → 旧 buffer 数据已经被破坏 → 无法回滚。

10.2 解决方案：std::move_if_noexcept

STL 在扩容时检查：noexcept(T(std::move(t))) 是否为 true？

  • true：用移动构造（快）
  • false：退化为拷贝构造（慢但安全；旧 buffer 可保留作回滚）

10.3 实测对比

10b.1 老问题 — *this 的值类别要写 4 个重载 · 10b.2 C++23 写法 — 一个函数搞定 · 10b.3 语法细节 · 10b…

*this 的值类别终于显式可推导 ⭐

P0847R7 引入"explicit object parameter"，允许成员函数把 this 写成第一个显式参数，从而：① 通过模板推导 *this 的值类别（const / & / &&）；② 一个函数代替原来 4 个重载；③ CRTP 不再需要 derived cast；④ Lambda 可以递归调用自身。这是 C++23 最影响日常代码风格的特性之一。

10b.1 老问题 — *this 的值类别要写 4 个重载

// 这就是 std::optional 的 value() 在标准里的真实重载数
template<class T>
class optional {
    T storage_;
public:
    T&                value() &       { return storage_; }                          // lvalue
    const T&          value() const & { return storage_; }                          // const lvalue
    T&&               value() &&      { return std::move(storage_); }              // rvalue
    const T&&         value() const &&{ return std::move(storage_); }              // const rvalue
};
四个函数体几乎一样，只是返回类型和 *this 值类别不同。维护成本高、易写错、模板化时还要写一堆 const_cast / static_cast。

10b.2 C++23 写法 — 一个函数搞定

template<class T>
class optional {
    T storage_;
public:
    template<class Self>
    auto&& value(this Self&& self) {              // ★ this 是第一个显式参数
        return std::forward<Self>(self).storage_;     // 自动 forward *this
    }
};

// 调用
optional<Big> o = ...;
auto&        a = o.value();                // Self = optional&        → 返回 Big&
auto&&       b = std::move(o).value();     // Self = optional&&       → 返回 Big&& (可移动!)
const auto& c = std::as_const(o).value();  // Self = const optional& → 返回 const Big&
核心收益：① 1 个模板代替 4 个重载；② 通过引用折叠 + perfect forwarding 自动给出正确的值类别；③ 维护成本骤降。

10b.3 语法细节

形式含义类比传统重载
void f(this Self&& self)forwarding reference 模板，Self 推导出 value category四组重载 + 引用折叠
void f(this Self self)by-value：拷贝/移动当前对象（罕用，Builder 模式有用）—
void f(this const C& self)固定类型，仅 const lvalue 调用等价 void f() const &
void f(this C&& self)固定类型，仅 rvalue 调用等价 void f() &&
规则：① 函数体内不能再用 this 指针，必须通过 self；② 不能与同名的非 explicit-object-parameter 成员函数共存；③ 不能用于虚函数、构造/析构函数。

10b.4 杀手级应用 ① — CRTP 不再需要 static_cast

// 旧 CRTP — 派生类调用要 static_cast 取回真实类型
template<class D>
struct Counted {
    int id() const {
        return static_cast<const D&>(*this).compute_id();
    }
};
struct User : Counted<User> {
    int compute_id() const { return 42; }
};

// 新写法 — 完全消除 CRTP 模板基类
struct User {
    int compute_id() const { return 42; }
    template<class Self>
    int id(this const Self& self) {
        return self.compute_id();         // Self 已是 User，无需 cast
    }
};

影响：大量库（CRTP 风格的 expression templates、流式 builder、smart pointer 基类）可以彻底重写。cpp-coro / Eigen / Boost.Hana 都开始迁移。

10b.5 杀手级应用 ② — 递归 lambda（不再需要 std::function 或 Y-combinator）

// C++20 及之前 — 递归 lambda 是地狱
auto fact = [](int n) {
    return n <= 1 ? 1 : n * fact(n - 1);   // ❌ fact 在自己内部不可见
};
// 老的 workaround: std::function 类型擦除（性能差），或写 Y-combinator

// C++23 — 通过 deducing this 自然递归
auto fact = [](this auto& self, int n) -> int {
    return n <= 1 ? 1 : n * self(n - 1);   // ✅ self 就是 lambda 闭包对象
};

std::cout << fact(10);   // 3628800

编译器对 lambda 自动调用 operator() 时把 lambda 闭包对象作为 self 传入。零开销—— 没有 std::function 虚调用、没有堆分配。

11.1 FileHandle — POSIX 文件描述符 RAII

class FileHandle {
    int fd_ = -1;
public:
    FileHandle() noexcept = default;
    explicit FileHandle(int fd) noexcept : fd_(fd) {}

    ~FileHandle() noexcept {
        if (fd_ >= 0) ::close(fd_);
    }

    // 禁拷贝（fd 是独占资源）
    FileHandle(const FileHandle&)            = delete;
    FileHandle& operator=(const FileHandle&) = delete;

    // 移动 = 转移 fd
    FileHandle(FileHandle&& o) noexcept : fd_(o.fd_) {
        o.fd_ = -1;
    }
    FileHandle& operator=(FileHandle&& o) noexcept {
        if (this != &o) {
            if (fd_ >= 0) ::close(fd_);    // 释放原资源
            fd_ = o.fd_;
            o.fd_ = -1;
        }
        return *this;
    }

    int get() const noexcept { return fd_; }
    int release() noexcept { int tmp = fd_; fd_ = -1; return tmp; }
    explicit operator bool() const noexcept { return fd_ >= 0; }
};

13.1 基础（必答）

  1. 基础什么是 lvalue / rvalue / xvalue / prvalue?

    用「有无身份(identity，可取地址) × 能否移动(movable)」两维度划分：

    • lvalue：有身份、不可被移动。有名变量、*p、返回 T& 的函数。
    • prvalue：无身份、可移动。字面量 42、表达式 a+b、返回 T（按值）的函数。
    • xvalue（将亡值）：有身份、可移动。std::move(x)、返回 T&& 的函数。
    • glvalue = lvalue ∪ xvalue（都有身份）；rvalue = prvalue ∪ xvalue（都可移动）。
  2. 基础std::move 做了什么? 它真的"移动"吗?

    它不移动任何东西，只是一个 static_cast<remove_reference_t<T>&&>，把表达式无条件转换成 xvalue（右值）。

    • 编译后零运行时开销，只改变值类别，使重载决议命中移动构造 / 移动赋值。
    • 真正的资源转移发生在移动构造 / 移动赋值的函数体里，而非 std::move 本身。
  3. 基础什么是 Rule of 3 / 5 / 0?
    • Rule of 3：若需自定义「析构 / 拷贝构造 / 拷贝赋值」之一，通常三者都要（管理资源时一致性）。
    • Rule of 5：C++11 起再加「移动构造 / 移动赋值」共五个。
    • Rule of 0：不写任何特殊成员，用 RAII 成员（智能指针、容器）让编译器全自动生成 —— 最推荐。
  4. 基础移动构造与拷贝构造的关键区别?
    • 拷贝构造 T(const T&)：深拷贝资源，源对象不变，开销 O(n)。
    • 移动构造 T(T&&)：窃取源对象的资源指针并把源置空，O(1)；源对象之后仍需保持可析构、可赋值的有效状态。
  5. 基础什么时候编译器自动生成移动构造?

    当类没有声明任何「拷贝构造 / 拷贝赋值 / 移动赋值 / 析构」，且所有非静态成员与基类都可移动时，编译器隐式生成移动构造。

    反之：声明了析构或任一拷贝操作 → 移动构造 / 移动赋值不再自动生成（见 §14.3 "X 抑制 Y" 表）。

  6. 基础为什么 std::vector 的元素需要可移动?

    扩容（reserve / push_back 触发 reallocation）时，需要把旧缓冲区元素搬到新内存：

    • 可移动 → O(1) 转移资源；否则只能逐个深拷贝。
    • 实际用 std::move_if_noexcept：移动构造非 noexcept 时退化为拷贝，以保证强异常安全。
  7. 基础为什么 int&& x 在函数里是 lvalue？

    类型 int&& 只约束调用 g 时必须传入右值。函数体内 x 有名字、可取地址 → 表达式是 lvalue。所以 void f(int&); void f(int&&); void g(int&& x){ f(x); } 走的是 f(int&)；要走右值重载必须 f(std::move(x))。

    设计原因：若具名 && 自动当右值，g 里 consume(x) 两次会悄悄掏空。默认安全 = 有名字就当左值，交出去必须显式授权。

  8. 基础为什么对 int 写 std::move 没意义？

    std::move 只是 cast，真正的移发生在接收方的移动构造 / 赋值。int x=1; std::move(x); 丢掉结果则 x 仍是 1。int 没有外置资源，移动 = 拷贝；string / vector / unique_ptr 移动才是交指针。

13.2 中级（区分熟练度）

  1. 中级引用折叠规则? 用一个例子说明万能引用怎么工作。

    折叠规则：只要有一个左值引用，结果就是左值引用 —— & &→&，& &&→&，&& &→&，&& &&→&&。

    万能引用 T&&（T 为待推导模板参数）：

    template<class T> void f(T&& x);
int i = 1;
f(i);   // 传左值 → T 推成 int&，int& && 折叠为 int&
f(42);  // 传右值 → T 推成 int，int && 即 int&&

    于是同一个 T&& 既能接左值也能接右值，再配合 std::forward 保持原值类别。

  2. 中级std::forward 与 std::move 区别? 各用什么场景?
    • std::move：无条件转右值。用于"我确定不再用这个对象，可窃取它"，如具名右值、转移成员。
    • std::forward：有条件转换 —— 左值仍转为左值、右值仍转为右值，保持原值类别。只用于万能引用 T&& 的完美转发。

    口诀：拿到具名右值用 move；转发模板形参用 forward。

  3. 中级RVO / NRVO 区别? C++17 强制了哪个?
    • RVO：返回无名临时（return T(...);）→ C++17 起强制省略，prvalue 直接在目标位置构造，连可拷贝 / 可移动都不要求。
    • NRVO：返回具名局部变量（return obj;）→ 编译器可选优化，C++17 也未强制。
  4. 中级为什么写 return std::move(local) 是反模式?
    • 它把返回表达式变成 xvalue，阻止了 NRVO（具名变量本可被 copy elision），强行多走一次移动构造，反而更慢。
    • 对 return local; 编译器已会把局部变量当右值处理（隐式移动），所以正确写法就是 return local;。
  5. 中级为什么自定义类的移动构造要标 noexcept?

    容器（如 std::vector）扩容时用 std::move_if_noexcept：

    • 移动构造标了 noexcept → 扩容用移动（高效）。
    • 未标 noexcept（可能抛）→ 退回拷贝以保证强异常安全 → 性能损失。
  6. 中级const T& 与 T&& 哪个更通用?
    • const T& 更通用：能绑左值、右值、const、临时，几乎一切；但只读、无法移动。
    • T&&（具体类型）只绑右值。
    • 若要"既通用又能转移"，用万能引用 T&&（模板）+ forward；纯只读则 const T&。

13.3 高级（体现深度）

  1. 高级给一个含 std::mutex 的类，编译器为什么生成不出拷贝构造?

    std::mutex 的拷贝构造被 = delete（且不可移动）。编译器隐式生成的拷贝构造要逐成员拷贝，遇到不可拷贝的 mutex 成员 → 整个拷贝构造被定义为 deleted。

    解决：自己实现拷贝控制，不拷贝 mutex 本身，只在持锁状态下拷贝被保护的数据。

    T(const T& o) {
    std::lock_guard lk(o.mtx_);   // 锁源，不拷 mtx_
    data_ = o.data_;
}
  2. 高级copy-and-swap 惯用法的 4 个好处?
    1. 一份代码两用：按值传参的 operator=(T rhs) 同时实现拷贝赋值与移动赋值。
    2. 强异常安全：先构造副本（可能抛在此处，但 *this 未动），再 swap（通常 noexcept）。
    3. 天然自赋值安全：操作的是独立副本，无需手写 if(this != &rhs)。
    4. 少重复：复用已有的拷贝 / 移动构造与析构逻辑。
  3. 高级std::move_if_noexcept 在 vector::push_back 中如何工作?

    扩容需把旧元素转移到新内存：

    • 元素移动构造为 noexcept → 返回右值引用 → 移动（高效）。
    • 移动可能抛 → 返回 const 左值引用 → 拷贝。因为移动到一半抛异常会让旧缓冲区元素已被破坏、无法回滚，违反强异常安全；拷贝则旧数据完好。
  4. 高级给一个万能引用 + 普通引用重载的二义性例子，并修复。

    典型坑：万能引用构造抢占了拷贝构造。

    struct Widget {
    template<class T> Widget(T&& x);     // (A) 万能引用
    Widget(const Widget&);              // (B) 拷贝构造
};
Widget w1;
Widget w2 = w1;   // ⚠️ w1 是非 const 左值，(A) T=Widget& 比 (B) const& 更匹配 → 调到 (A)!

    修复：用约束排除自身类型。

    template<class T>
    requires (!std::same_as<std::decay_t<T>, Widget>)
Widget(T&& x);   // C++20 concept；C++17 用 enable_if
  5. 高级下列代码有几次构造、几次拷贝、几次移动?
    std::vector<std::string> v; v.reserve(10); v.push_back("hello");

    1 次构造 + 1 次移动构造（无拷贝）：

    • "hello"（const char[6]）先构造一个临时 std::string → 1 次构造。
    • 临时是右值，命中 push_back(string&&) → 1 次移动构造进 vector。
    • 已 reserve(10) → 不扩容，无额外搬移。
    • 优化：v.emplace_back("hello") → 仅 1 次原地构造，连临时都省。

    详细分解见 §13.4 速答示范。

  6. 高级解释为什么 auto&& 是万能引用但 const auto&& 不是。
    • 万能引用的前提是：一个裸的、待推导的 T&& / auto&&，依赖引用折叠才能在接左值时折叠成左值引用。
    • const auto&& 加了 const 限定，破坏了"推导成左值引用"的可能 —— 它只能绑 const 右值，是一个普通右值引用，不再万能。
  7. 高级函数模板 template<class T> void f(std::vector<T>&& v); — 这是不是万能引用?

    不是。万能引用要求形参恰好是裸的 T&&（T 被直接推导）。这里外层类型是确定的 std::vector<T>&&，T 仅在 vector 内部被推导，所以它是一个普通右值引用，只接受 vector 的右值实参。

  8. 高级为什么字符串字面量 "hello" 是 lvalue 而不是 prvalue?
    • "hello" 的类型是 const char[6]，是一个存放在静态存储区、有地址的数组对象，可以 &"hello" 取址 → 有身份 → lvalue。
    • 对比：42、true 等内置标量字面量没有持久存储，是 prvalue。数组字面量因为需要实际存储而成为 lvalue。

13.4 速答示范（第 17 题）

问：std::vector<std::string> v; v.reserve(10); v.push_back("hello"); 几次构造、拷贝、移动? 
// 步骤分解：
// 1. "hello" 是 const char[6]，先转换为临时 std::string  → 1 次构造
// 2. push_back 接收 const string& 重载 → 把临时拷贝到 vector  → 1 次拷贝构造
