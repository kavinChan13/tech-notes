五种值类别全景（C++11 起）

文氏图：3 个底层 + 2 个聚合 · 三个底层类别的精确定义 · 两个聚合类别（更高层视角） · 实战识别

C++03 只有 lvalue / rvalue。C++11 把 rvalue 拆开后，用有无身份 × 能否移动两维看：三个底层类别，两个聚合类别是它们的并集。

2.1 文氏图：3 个底层 + 2 个聚合

2.2 三个底层类别的精确定义

类别口语含义判定标准典型例子
lvalue
(left-value)		 "有身份的值，且不能被偷" 有名字、可取地址，且不是 xvalue x、arr[0]、*ptr、字符串字面量 "abc"、返回 T& 的函数
prvalue
(pure rvalue)		 "纯临时，没有持久身份" 表达式的结果本身，不和任何对象关联 42、1+2、foo()（按值返回）、this、lambda 表达式
xvalue
(eXpiring value)		 "将亡值，可被偷的有身份对象" 有身份（有地址），但即将销毁，资源可被窃取 std::move(x)、返回 T&& 的函数、static_cast<T&&>(x)

2.3 两个聚合类别（更高层视角）

聚合类别定义用一句话记
glvaluelvalue ∪ xvalue"有身份（地址）的值"
rvaluexvalue ∪ prvalue"可被移动的值"
判断流程（背下来）：拿到一个表达式 →
① 它有名字或能 &e 取地址吗? 能 → glvalue；不能 → prvalue
② 如果是 glvalue：它是不是 std::move(...) 或返回 T&& 的结果? 是 → xvalue；否 → lvalue
🔍 交互式判定器：点一个表达式，走一遍决策树
选一个表达式，下面两道判定题会自动作答并给出值类别。生活化类比：lvalue 是"有户口的房子"（有地址、长住）；prvalue 是"路边临时摊"（没身份、用完即走）；xvalue 是"挂牌待拆的房子"（有地址但资源随时可搬走）。
① 有名字 / 能取地址 &e？ —
② 是 std::move 或返回 T&&（将亡）？ —

2.4 实战识别

一个函数里三种底层类别同时出现：

void classify(int& lv) {
    lv;                    // lvalue：有名、可取址
    std::move(lv);         // xvalue：有身份，标记为可偷
    42;                    // prvalue：纯临时，无身份
    getRRef();             // 返回 T&& → xvalue
    getVal();              // 按值返回 → prvalue
}
易错点：字符串字面量 "hello" 是 lvalue（类型 const char[6]），不是 prvalue！这是与其他字面量（int / true / nullptr）唯一的不同点 — 因为它们有静态存储，能取地址。
回答"什么是 xvalue?"时不要只说"std::move 的结果" — 标准定义是有身份且即将销毁、资源可被窃取的值。"将亡值" 是中文意译，要能讲出英文 eXpiring 的含义。
03

引用类型与「引用折叠」规则

三种引用 · 万能引用 (Universal / Forwarding Reference) · 引用折叠规则（Reference Collapsing）· 何时该用 & / && / const& / 按值：接口设计决策

3.1 三种引用

引用能绑哪些用途
T&仅 lvalue（非 const）修改原对象
const T&所有（lvalue / xvalue / prvalue）只读、零拷贝；绑临时会延长生命周期
T&&（具体类型）仅 rvalue移动构造 / 移动赋值
T&&（模板参数）万能引用，看实参完美转发，见 §3.2

具名 T&& 只约束「怎么进来」，不改变「进去之后是左值」

类型 int&& 只约束调用时必须传入右值。函数体内形参有名字 → 表达式是 lvalue → 重载决议走左值那条。

设计原因：语言选择「默认安全」——有名字就当左值，要交出去必须显式 std::move。
🏷️
生活类比：门禁 vs 工牌
int&& 是门禁——进门必须是「即将搬走的货」。进门之后贴了工牌（有名字），仓库默认当库存。要出库必须再开调拨单（std::move）。

3.2 万能引用 (Universal / Forwarding Reference)

仅当 T&& 出现在模板参数推导上下文，T 是要推导的模板参数，且不带 cv时，才是万能引用。

3.3 引用折叠规则（Reference Collapsing）

手写 int& & 非法。折叠只发生在推导 / auto&& / 别名 / decltype 内部：

原始折叠后
T& &T&
T& &&T&
T&& &T&
T&& &&T&&

口诀：出现过一次左值引用，结果就是左值引用；两个右值引用才是右值引用。

template<class T>
void wrapper(T&& arg) {                 // 万能引用：T 从实参推导
    backend(std::forward<T>(arg));      // T=U& → 不 move；T=U → move
}

3.3.1 折叠从哪来 · 一条模板代替 2ⁿ 重载

折叠不是给人手写 int& & 的，只出现在推导 / auto&& / 别名 / decltype。emplace_back(Args&&...) 一个函数覆盖所有左右值组合；没有折叠就没有 make_unique / std::thread 这类工厂。

调用T 推导为折叠后形参forward<T>
f(x) 左值U&U&lvalue（不 move）
f(42) / f(std::move(x))UU&&xvalue
f(std::move(cx)) const 右值const Uconst U&&绑不到移动重载，静默拷贝

函数体里 arg 永远是 lvalue；线索只在 T 里，所以 forward 必须写 <T>。

3.4 什么时候该用 &、&&、const&、还是按值 —— 接口设计决策

前面讲的是「规则是什么」，这一节回答工程上真正要做的决定：写函数签名时到底选哪个。

📚
生活类比 · 借书的四种方式
const T& = 借你看，不许在上面写字（只读、零拷贝、什么书都能借）。
T& = 借你看，允许你批注，改动我这边也看得见（in-out 参数）。
T&& = 「这本书我不要了，撕页拆封都行」（可窃取资源）。
按值 T = 复印一份给你；如果我说「这份归你」（std::move），复印就省了。

3.4.1 参数传递决策表（背这一张就够）

你的需求推荐签名理由与代价
只读，类型小且平凡（int / double / 枚举 / 指针 / string_view / span / 迭代器） 按值 T一两个寄存器就传完；取引用反而多一次间接寻址，还妨碍编译器做寄存器分配
只读，类型大或有资源（string / vector / 自定义类） const T&零拷贝、能吃 lvalue/xvalue/prvalue 全部值类别。缺点：拿不到所有权，要存起来就必须拷贝
要修改调用方的对象（in-out） T&语义直接；缺点：调用点 f(a) 看不出 a 会被改 → 能用返回值就别用输出参数
接管 / 存起来（sink：setter、构造函数、push、任务提交） 按值 T + 函数内 std::move一份代码同吃左右值。右值：1 次移动；左值：1 次拷贝 + 1 次廉价移动
接管，且要「一次多余移动都不能有」 const T& + T&& 双重载代价最优但代码翻倍；参数一多就 2ⁿ 爆炸。标准库热点（vector::push_back）才这么写
泛型包装 / 转发（不知道调用方会给什么，也不该替它决定） 模板 T&& + std::forward<T>完美转发。缺点：必须进头文件、报错信息长、容易抢占其它重载（§12 第 6 条）
工厂 / 原地构造 变参模板 Args&&... + forwardemplace_back / make_unique 的标准做法，连临时对象都省掉
只读且只需要看内容、不关心容器 std::string_view / std::span比 const std::string& 更好：字面量、vector<char>、子串都能传进来且零构造。⚠ 不得存起来（无所有权）

3.4.2 setter 四种写法：数清每一次构造

写法set(lv)set(std::move(lv))set("lit")
① const T&拷贝赋值（可复用 buffer）仍拷贝，右值浪费临时构造 + 拷贝赋值
② 按值 + move拷贝构造（必分配）+ 移动赋值两次 O(1) 移动形参直接构造 + 移动赋值
③ const& + &&同 ①一次移动赋值（最优）临时 + 移动赋值
④ 转发 T&&同 ①同 ③0 临时，直接 operator=(const char*)

默认用 ②；热路径反复 set 同一对象用 ①（赋值能复用容量）；库级 API 才上 ③/④。按值形参 move 掉之后不能再读。

3.4.3 ref-qualifier：给 *this 分左值 / 右值

写法作用
str() const & / str() &&左值借出，右值把成员 move 出去（optional::value）
view() const && = delete临时上取 view 必悬垂 → 编译期禁掉

C++23 可用 deducing this 一个函数代替四组重载，见 §10b。

3.4.4 什么时候不该用 &&

形态为什么不行
const T&& 作参数能绑右值却不能偷；只适合 = delete 掉右值调用
返回 T&&局部销毁后悬垂；按值返回，交给 RVO
int&& 这类平凡类型重载没有资源可偷
成员写成 T&&不延长寿命，构造完就悬垂
万能引用与普通重载并存完美匹配会抢走拷贝构造，必须 requires 约束
04

std::move / std::forward 真相

std::move 不移动任何东西 · 为什么必须显式写 move（6 个真实场景） · 为什么编译器不能替你 move · std::forward 完美转发 · 为什么需要 forward（包装函数的 5 种写法） · forward 的实现细节 · 易错对比 · 决策速查

4.1 std::move 不移动任何东西

它只是 cast：无条件转成 xvalue。真正搬资源的是接收方的移动构造 / 赋值。

template<class T>
constexpr std::remove_reference_t<T>&& move(T&& x) noexcept {
    return static_cast<std::remove_reference_t<T>&&>(x);  // 就是这一句
}
std::string s = "hi";
std::string t = std::move(s);   // t 偷走 buffer
s.size();                       // ❌ 合法但未指定，别依赖内容
s = "ok";                       // ✅ 重新赋值 / 析构都可以

真正的移动发生在移动构造函数体里。std::move 只让重载决议选中右边那条路：

对 int 写 std::move 几乎没意义

丢掉结果则什么都不发生；int 没有外置资源，移动等于拷贝。

类型移动实际做什么相对拷贝
int / 指针本身按位复制；源不必清空等于拷贝
string / vector / unique_ptr交指针，源置空O(1) vs O(n)

4.2 为什么必须显式写 std::move：6 个真实场景

场景不写会怎样正确写法
塞进容器push_back(line) 每行一次分配push_back(std::move(line))（下一轮 getline 会覆盖）
独占所有权unique_ptr / thread / promise 拷贝直接编译错必须 move
成员初始化按值形参再拷一次，编译器不警告: name_(std::move(name))
移进 lambda拷贝捕获 move-only 编不过；引用捕获悬垂[x = std::move(x)]
取出成员成员永远是 lvalue，会拷贝return std::move(body_)（仅右值 *this）
swap / 扩容C++03 三次深拷贝三次 O(1) 搬指针；移动构造要 noexcept

std::swap 的收益真正来自「不碰 allocator」。漏一次 move 只是慢；错一次 move 是静默掏空。所以默认拷贝，移动必须显式授权。Rust 反过来：默认移动，借用检查器禁止再用移后源。

4.3 那为什么编译器不能替我们自动 move？

层原因
值类别是语法属性有名字就是 lvalue。证明「之后不再读」需要跨 TU 的别名分析，C++ 做不到
猜错不对称漏 move 只是慢；错 move 是逻辑 bug
能证明的地方已经自动了return 局部对象：隐式移动甚至 NRVO。C++20/23 还在放宽。所以 return std::move(local) 是反模式
「Rust 为什么不需要 std::move？」默认就是移动，借用检查器禁止再用移后源。C++ 默认拷贝 + 显式授权，是为了兼容任意别名。

4.4 std::forward 完美转发

按 T 带不带 & 决定要不要转成右值。最短模板见 §3.3。口诀：move = 我确定要移动；forward = 别人怎么给我，我就怎么传出去。

4.5 为什么需要 std::forward：包装函数的 5 种写法

写法左值右值move-only判定
① const T&拷贝仍拷贝编不过丢移动
② 按值拷贝+移动两次移动两次移动能用，每层白搭一次
③ T&& 直传拷贝仍拷贝编不过右值性丢失
④ T&& + move掏空调用方移动移动正确性 BUG
⑤ T&& + forward拷贝移动移动唯一正确

转发参数只能 forward 一次，且在最后一次使用点。若日志包装里对同一参数先 move 进 logger 再 move 进 transport，调用方的左值被掏空，线上只剩空串。延迟执行（线程池）必须把实参 forward 进闭包按值持有，不能把引用塞进队列——submit 返回后临时对象已经析构。这正是 std::thread 要对参数做 decay-copy、以及 std::ref 必须显式写出的原因。

4.6 实现细节：为什么 forward 的 <T> 不能省

形参写成 remove_reference_t<T>&，让 T 处于非推导位置。若写成 forward(T&&)，实参 arg 永远是 lvalue → T 永远带 & → 转发失效。std::move 则相反：它无条件转换，不需要知道调用方的值类别，所以可以推导。forward 的条件全在 static_cast<T&&> 的折叠里，自己一行运行时代码都没有。

写法结论
std::forward<T>(arg)标准
std::forward<decltype(x)>(x)泛型 lambda 没有 T 时
std::forward(arg)编译错
forward<decay_t<T>> / 转发参数上 move连左值也强制右值

Rule of 0 / 3 / 5（最重要的设计准则）

Rule of 0 的好处（举例） · Rule of 5 完整模板

6.1 Rule of 0 的好处（举例）

Rule of 0 不是「这个类没有特殊成员」，而是「六个特殊成员全部交给编译器，且因为成员自己是 RAII，生成出来的拷贝 / 移动 / 析构都正确」。好处有三：改字段不用回头改五件套；异常安全跟着成员走；移动语义免费获得。一旦出现裸 new、fd、mmap，外层立刻掉进 Rule of 5——这时优先把裸资源封进 unique_ptr / 自定义 RAII，再让业务类回到 Rule of 0，而不是到处手写五件套。

6.2 Rule of 5 完整模板

Rule of 0
class User {
    std::string name;
    std::vector<Order> orders;
    std::unique_ptr<Profile> p;
};  // 6 个特殊成员全默认且正确
Rule of 5（裸指针）
class Buffer {
    char* data_{};
    size_t n_{};
public:
    explicit Buffer(size_t n)
        : data_(new char[n]), n_(n) {}
    ~Buffer() { delete[] data_; }
    Buffer(const Buffer& o)
        : Buffer(o.n_) { std::memcpy(data_, o.data_, n_); }
    Buffer(Buffer&& o) noexcept
        : data_(o.data_), n_(o.n_) { o.data_ = nullptr; o.n_ = 0; }
    Buffer& operator=(Buffer o) noexcept {
        std::swap(data_, o.data_); std::swap(n_, o.n_);
        return *this;
    }
};

copy-and-swap：operator=(Buffer) 按值收 + swap = 拷贝/移动赋值一份代码，且强异常安全。按值形参先完成拷贝或移动（失败时 *this 未动），再交换指针，自赋值也安全。

Rule of 0 的前提是成员已经管好资源（容器、智能指针）。一旦自己 new / 持 fd，就必须五件套对齐，否则析构释放、拷贝浅拷、移动没置空会叠出 double-free。

8.1 显式声明 = default 的价值

  • 恢复被其它声明抑制掉的默认行为
  • 表达「请生成合成版本」，并可单独控制访问级别（例如 protected 的拷贝）

显式 = default 和「干脆不写」不是一回事。不写可能被别的声明抑制掉；写了是在告诉编译器和读者：我知道被抑制了，请按合成语义生成。注意：析构写 = default 仍算「声明了析构」，移动照样不生成——只 default 析构却忘了 default 移动，是把 Rule of 3 升级到 5 时最常见的漏项。

9.1 三个术语梳理

术语含义C++17 强制?
RVO (Return Value Optimization)函数返回临时对象（prvalue）时，省略拷贝/移动✅ 强制（C++17 起）
NRVO (Named RVO)返回具名局部对象时省略拷贝/移动❌ 仍是允许但不强制
Copy Elision统称：编译器允许在某些场合省略拷贝/移动构造—

9.2 RVO（强制）

Buffer make(size_t n) {
    return Buffer(n);   // prvalue → C++17 强制省略
}
Buffer b = make(1024);  // 直接在 b 上构造；不可移动的类型也能这么返回

9.3 NRVO（编译器自由选择）

C++17 起，return 一个 prvalue 时直接在调用方对象上构造，连移动构造都可以没有——所以不可移动类型也能按值返回临时。NRVO 面对的是具名对象：编译器要证明所有 return 路径返回同一个变量，因此不是强制优化。写 return std::move(local) 把表达式变成 xvalue，省略规则不再适用，于是亲手关掉可能的零次构造，只剩一次移动。参数和成员本来就不能 NRVO（它们不是这个函数的局部对象），那种情况才必须 move。

9.4 Copy Elision 的精确条件

  1. return 同类型的非参数局部对象 → NRVO
  2. return 同类型临时 → RVO（C++17 强制）
  3. throw 同类型局部对象；以及临时传给 by-value 参数（C++17 强制）

9.5 Copy Elision vs Move 对比

场景正确写法

noexcept 与移动构造的关系

STL 容器的「强异常安全保证」 · 解决方案：std::move_if_noexcept · 实测对比 · noexcept 的影响范围 · 例外：何时不能 noexcept

10.1 STL 容器的「强异常安全保证」

std::vector::push_back 在扩容时承诺：操作要么成功，要么 vector 状态完全不变（强保证）。

问题：扩容要把元素从旧 buffer 转到新 buffer。如果 T 的移动构造可能抛异常，转移过程中失败 → 旧 buffer 数据已经被破坏 → 无法回滚。

10.2 解决方案：std::move_if_noexcept

STL 在扩容时检查：noexcept(T(std::move(t))) 是否为 true？这不是「快就用移动」的启发式，而是强保证下唯一安全的编译期分支。

  • true：用移动构造（快）
  • false：退化为拷贝构造（慢但安全；旧 buffer 可保留作回滚）

10.4 noexcept 的影响范围

扩容路径（push_back / resize）、move_if_noexcept、以及编译器少生成异常展开代码。

10.5 例外：何时不能 noexcept

移动构造里如果可能抛，就不要标 noexcept 去骗容器。典型是 pmr 容器跨 arena 搬元素时可能分配；分配失败抛 bad_alloc，若你标了 noexcept，vector 以为可以拆旧槽，失败就 terminate。只搬指针 / fd 的资源句柄类默认都该标。

11.1 FileHandle — POSIX 文件描述符 RAII

POSIX fd 是整数句柄，拷贝等于两个对象关同一个 fd。必须：析构 close；拷贝 = delete；移动把 fd 转走并把源置成 -1（或一个不会被 close 的哨兵）。移后源仍要能析构。不要在移动赋值里先 close 再偷——自赋值会把自己关了。

11.2 Buffer — 用 unique_ptr 实现 Rule of 0

堆内存交给 unique_ptr<char[]>，析构 / 移动自动正确。若还要拷贝，就显式深拷一份，或干脆拷贝 = delete。这是「Rule of 0 优先」的标准答案：业务类不碰 new。对照 §6.2 那个裸指针 Buffer——同样的语义，五件套可以整段删掉。

11.3 Connection — 持有 fd + Buffer + 状态

同时持有 fd、缓冲区和 atomic 状态时，成员里只要有一个不可移动（atomic），整个类的移动就被删除。不要强行手写移动去搬 atomic——地址稳定性才是连接对象的不变量。外包一层 unique_ptr<Connection> 再放进容器。

11.4 Session — 含锁，不可移动的"门面"

含锁 / atomic 的类不可移动是常态。策略：对象用 unique_ptr<T> 包起来——让指针可移动，对象本身保持稳定地址。把 Session 直接推进 vector 会编不过，这是特性不是缺陷：锁不能搬，门面必须钉在固定地址上。

13.1 基础（必答）

  1. 基础什么是 lvalue / rvalue / xvalue / prvalue?

    用「有无身份(identity，可取地址) × 能否移动(movable)」两维度划分：

    • lvalue：有身份、不可被移动。有名变量、*p、返回 T& 的函数。
    • prvalue：无身份、可移动。字面量 42、表达式 a+b、返回 T（按值）的函数。
    • xvalue（将亡值）：有身份、可移动。std::move(x)、返回 T&& 的函数。
    • glvalue = lvalue ∪ xvalue（都有身份）；rvalue = prvalue ∪ xvalue（都可移动）。
  2. 基础std::move 做了什么? 它真的"移动"吗?

    它不移动任何东西，只是一个 static_cast<remove_reference_t<T>&&>，把表达式无条件转换成 xvalue（右值）。

    • 编译后零运行时开销，只改变值类别，使重载决议命中移动构造 / 移动赋值。
    • 真正的资源转移发生在移动构造 / 移动赋值的函数体里，而非 std::move 本身。
  3. 基础什么是 Rule of 3 / 5 / 0?
    • Rule of 3：若需自定义「析构 / 拷贝构造 / 拷贝赋值」之一，通常三者都要（管理资源时一致性）。
    • Rule of 5：C++11 起再加「移动构造 / 移动赋值」共五个。
    • Rule of 0：不写任何特殊成员，用 RAII 成员（智能指针、容器）让编译器全自动生成 —— 最推荐。
  4. 基础移动构造与拷贝构造的关键区别?
    • 拷贝构造 T(const T&)：深拷贝资源，源对象不变，开销 O(n)。
    • 移动构造 T(T&&)：窃取源对象的资源指针并把源置空，O(1)；源对象之后仍需保持可析构、可赋值的有效状态。
  5. 基础什么时候编译器自动生成移动构造?

    当类没有声明任何「拷贝构造 / 拷贝赋值 / 移动赋值 / 析构」，且所有非静态成员与基类都可移动时，编译器隐式生成移动构造。

    反之：声明了析构或任一拷贝操作 → 移动构造 / 移动赋值不再自动生成（见 §14.3 "X 抑制 Y" 表）。

  6. 基础为什么 std::vector 的元素需要可移动?

    扩容（reserve / push_back 触发 reallocation）时，需要把旧缓冲区元素搬到新内存：

    • 可移动 → O(1) 转移资源；否则只能逐个深拷贝。
    • 实际用 std::move_if_noexcept：移动构造非 noexcept 时退化为拷贝，以保证强异常安全。
  7. 基础为什么 int&& x 在函数里是 lvalue？

    类型 int&& 只约束调用 g 时必须传入右值。函数体内 x 有名字、可取地址 → 表达式是 lvalue。所以 void f(int&); void f(int&&); void g(int&& x){ f(x); } 走的是 f(int&)；要走右值重载必须 f(std::move(x))。

    设计原因：若具名 && 自动当右值，g 里 consume(x) 两次会悄悄掏空。默认安全 = 有名字就当左值，交出去必须显式授权。

  8. 基础为什么对 int 写 std::move 没意义？

    std::move 只是 cast，真正的移发生在接收方的移动构造 / 赋值。int x=1; std::move(x); 丢掉结果则 x 仍是 1。int 没有外置资源，移动 = 拷贝；string / vector / unique_ptr 移动才是交指针。

13.2 中级（区分熟练度）

  1. 中级引用折叠规则? 用一个例子说明万能引用怎么工作。

    折叠规则：只要有一个左值引用，结果就是左值引用 —— & &→&，& &&→&，&& &→&，&& &&→&&。

    万能引用 T&&（T 为待推导模板参数）：

    template<class T> void f(T&& x);
int i = 1;
f(i);   // 传左值 → T 推成 int&，int& && 折叠为 int&
f(42);  // 传右值 → T 推成 int，int && 即 int&&

    于是同一个 T&& 既能接左值也能接右值，再配合 std::forward 保持原值类别。

  2. 中级std::forward 与 std::move 区别? 各用什么场景?
    • std::move：无条件转右值。用于"我确定不再用这个对象，可窃取它"，如具名右值、转移成员。
    • std::forward：有条件转换 —— 左值仍转为左值、右值仍转为右值，保持原值类别。只用于万能引用 T&& 的完美转发。

    口诀：拿到具名右值用 move；转发模板形参用 forward。

  3. 中级RVO / NRVO 区别? C++17 强制了哪个?
    • RVO：返回无名临时（return T(...);）→ C++17 起强制省略，prvalue 直接在目标位置构造，连可拷贝 / 可移动都不要求。
    • NRVO：返回具名局部变量（return obj;）→ 编译器可选优化，C++17 也未强制。
  4. 中级为什么写 return std::move(local) 是反模式?
    • 它把返回表达式变成 xvalue，阻止了 NRVO（具名变量本可被 copy elision），强行多走一次移动构造，反而更慢。
    • 对 return local; 编译器已会把局部变量当右值处理（隐式移动），所以正确写法就是 return local;。
  5. 中级为什么自定义类的移动构造要标 noexcept?

    容器（如 std::vector）扩容时用 std::move_if_noexcept：

    • 移动构造标了 noexcept → 扩容用移动（高效）。
    • 未标 noexcept（可能抛）→ 退回拷贝以保证强异常安全 → 性能损失。
  6. 中级const T& 与 T&& 哪个更通用?
    • const T& 更通用：能绑左值、右值、const、临时，几乎一切；但只读、无法移动。
    • T&&（具体类型）只绑右值。
    • 若要"既通用又能转移"，用万能引用 T&&（模板）+ forward；纯只读则 const T&。

13.3 高级（体现深度）

  1. 高级给一个含 std::mutex 的类，编译器为什么生成不出拷贝构造?

    std::mutex 的拷贝构造被 = delete（且不可移动）。编译器隐式生成的拷贝构造要逐成员拷贝，遇到不可拷贝的 mutex 成员 → 整个拷贝构造被定义为 deleted。

    解决：自己实现拷贝控制，不拷贝 mutex 本身，只在持锁状态下拷贝被保护的数据。

    T(const T& o) {
    std::lock_guard lk(o.mtx_);   // 锁源，不拷 mtx_
    data_ = o.data_;
}
  2. 高级copy-and-swap 惯用法的 4 个好处?
    1. 一份代码两用：按值传参的 operator=(T rhs) 同时实现拷贝赋值与移动赋值。
    2. 强异常安全：先构造副本（可能抛在此处，但 *this 未动），再 swap（通常 noexcept）。
    3. 天然自赋值安全：操作的是独立副本，无需手写 if(this != &rhs)。
    4. 少重复：复用已有的拷贝 / 移动构造与析构逻辑。
  3. 高级std::move_if_noexcept 在 vector::push_back 中如何工作?

    扩容需把旧元素转移到新内存：

    • 元素移动构造为 noexcept → 返回右值引用 → 移动（高效）。
    • 移动可能抛 → 返回 const 左值引用 → 拷贝。因为移动到一半抛异常会让旧缓冲区元素已被破坏、无法回滚，违反强异常安全；拷贝则旧数据完好。
  4. 高级给一个万能引用 + 普通引用重载的二义性例子，并修复。

    典型坑：万能引用构造抢占了拷贝构造。

    struct Widget {
    template<class T> Widget(T&& x);     // (A) 万能引用
    Widget(const Widget&);              // (B) 拷贝构造
};
Widget w1;
Widget w2 = w1;   // ⚠️ w1 是非 const 左值，(A) T=Widget& 比 (B) const& 更匹配 → 调到 (A)!

    修复：用约束排除自身类型。

    template<class T>
    requires (!std::same_as<std::decay_t<T>, Widget>)
Widget(T&& x);   // C++20 concept；C++17 用 enable_if
  5. 高级下列代码有几次构造、几次拷贝、几次移动?
    std::vector<std::string> v; v.reserve(10); v.push_back("hello");

    1 次构造 + 1 次移动构造（无拷贝）：

    • "hello"（const char[6]）先构造一个临时 std::string → 1 次构造。
    • 临时是右值，命中 push_back(string&&) → 1 次移动构造进 vector。
    • 已 reserve(10) → 不扩容，无额外搬移。
    • 优化：v.emplace_back("hello") → 仅 1 次原地构造，连临时都省。

    详细分解见 §13.4 速答示范。

  6. 高级解释为什么 auto&& 是万能引用但 const auto&& 不是。
    • 万能引用的前提是：一个裸的、待推导的 T&& / auto&&，依赖引用折叠才能在接左值时折叠成左值引用。
    • const auto&& 加了 const 限定，破坏了"推导成左值引用"的可能 —— 它只能绑 const 右值，是一个普通右值引用，不再万能。
  7. 高级函数模板 template<class T> void f(std::vector<T>&& v); — 这是不是万能引用?

    不是。万能引用要求形参恰好是裸的 T&&（T 被直接推导）。这里外层类型是确定的 std::vector<T>&&，T 仅在 vector 内部被推导，所以它是一个普通右值引用，只接受 vector 的右值实参。

  8. 高级为什么字符串字面量 "hello" 是 lvalue 而不是 prvalue?
    • "hello" 的类型是 const char[6]，是一个存放在静态存储区、有地址的数组对象，可以 &"hello" 取址 → 有身份 → lvalue。
    • 对比：42、true 等内置标量字面量没有持久存储，是 prvalue。数组字面量因为需要实际存储而成为 lvalue。

13.4 速答示范（第 17 题）

问：std::vector<std::string> v; v.reserve(10); v.push_back("hello"); 几次构造、拷贝、移动?
步骤发生什么
1"hello" 是 const char[6]，构造临时 string → 1 次构造
2临时是右值，命中 push_back(string&&) → 1 次移动构造
3已 reserve(10) → 不扩容
优化emplace_back("hello") → 仅 1 次原地构造
要拿满分，必须分清"有 reserve" → 不会扩容 → 只看 push_back 本身的构造代价。如果没 reserve，扩容时还可能移动之前的元素。
