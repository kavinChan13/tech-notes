01

崩溃到底发生了什么：信号

「程序崩了」在操作系统层面，是内核给它发了一个信号

C++ 程序「突然崩溃」并不是凭空消失，而是它做了非法操作，内核给它发了一个信号，默认动作是终止进程（并可能产生 core dump）。GDB 的价值就在于：在信号把进程杀死的那一刻把它冻住，让现场原封不动地留给你分析。

信号触发原因C++ 里的典型来源
SIGSEGVSegmentation fault：访问了不该访问的内存空指针、野指针、悬垂指针、数组越界
SIGABRTabort()：程序主动放弃未捕获异常、assert 失败、std::terminate、glibc 检测到堆损坏
SIGFPE算术异常整数除以 0、INT_MIN / -1 溢出
SIGBUS总线错误：地址对齐/映射问题未对齐访问、mmap 越界
SIGILL非法指令跳到了数据区、函数指针被写坏
信号是崩溃分析的「第一个线索」

GDB 停下来时第一行就告诉你是哪个信号：SIGSEGV → 往「非法内存访问（指针）」方向查；SIGABRT → 往「主动终止（异常/assert/堆损坏）」方向查；SIGFPE → 往「除零/溢出」方向查。信号类型直接决定你的假设方向，这就是 Debug Mindset 的起点（见第 09 节）。

02

拿到现场：run 崩溃 / core dump

现场有两种来源：现场复现，或事后 core

方式 A：直接在 GDB 里复现

$ g++ -g -O0 crash.cpp -o crash
$ gdb ./crash
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
0x... in foo () at crash.cpp:8       # GDB 直接停在出事那一刻
8           *ptr = 10;

GDB 会在崩溃点冻结，此时所有寄存器、栈、变量都是崩溃瞬间的真实状态 —— 立即 bt 就能看链。

方式 B：用 core dump 离线复盘

线上程序崩了，你不在现场，但系统留下了「案发时的内存快照」——core dump。事后用 GDB 加载它，就像回到崩溃那一刻：

# 先允许生成 core（很多系统默认 0，即不生成）
$ ulimit -c unlimited
$ ./crash                 # 崩溃后生成 core 文件（路径见 /proc/sys/kernel/core_pattern）

# 用「可执行文件 + core」一起加载
$ gdb ./crash core
(gdb) bt                # 直接看崩溃调用栈，无需复现！
Core Dump vs 直接调试 —— 关键区别

直接 run：程序在你控制下活着，你可以继续单步、改变量、调函数、动态观察 —— 但需要能复现。Core dump：是崩溃瞬间的静态内存快照，进程已死，你不能继续执行（不能 next/continue），只能查看当时的栈、变量、内存 —— 但它解决了「线上偶发、无法复现」的致命问题。生产事故排查几乎都靠 core。

03

七阶段崩溃分析路径

一套可复用、从粗到细的固定套路

1
拿到现场 —— run（复现）或 gdb ./app core（离线）。先看是哪个信号。
2
看调用栈 —— bt。崩在哪个函数？经由怎样的调用链？#0 是崩溃点。
3
查看当前帧 —— frame / info frame / info args / info locals。这一层的参数和变量是否已经不对？
4
看代码 —— list。崩溃那一行到底在做什么操作？
5
查看变量 —— p ptr / p *ptr。是不是 nullptr / 野指针 / 悬垂指针？
6
看寄存器 —— info registers，重点 RIP / RSP / RBP。RIP 合理吗？栈被破坏了吗？
7
看内存 / 汇编 —— x/… / disassemble。变量层看不清时，下探到字节和指令确认根因。
Crash
Signal（哪种信号 → 假设方向）
Backtrace（崩在哪、怎么来的）
Frame（当前上下文）
Source Code（这行在做什么）
Variables（哪个值异常）
Memory / Registers / Assembly（底层确认）
Root Cause
核心心法

这条路径是「从粗到细、逐步收窄」：大多数崩溃走到第 5 步（看变量）就定位了，只有栈损坏、优化干扰这类硬骨头才需要下探到 6、7。不要一上来就 disassemble —— 先用最省力的 bt 收窄范围。

04

案例 1：空指针解引用

最常见的 SIGSEGV，用来把七阶段走通

CASE 1 · Null Pointer 
// null.cpp — g++ -g -O0 null.cpp -o null
void writeIt(int* ptr) {
    *ptr = 10;              // ← 崩在这
}
int main() {
    int* p = nullptr;
    writeIt(p);
}
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
0x... in writeIt (ptr=0x0) at null.cpp:3         # ① 信号 SIGSEGV，ptr=0x0 已经很可疑
3           *ptr = 10;

(gdb) bt                                       # ② 调用栈
#0  writeIt (ptr=0x0) at null.cpp:3
#1  main () at null.cpp:8

(gdb) frame 0                                  # ③ 当前帧
(gdb) info args
ptr = (int *) 0x0

(gdb) list                                     # ④ 看代码
2   void writeIt(int* ptr) {
3       *ptr = 10;

(gdb) p ptr                                     # ⑤ 查变量
$1 = (int *) 0x0                                 # 地址是 0 → 空指针！
(gdb) p *ptr
Cannot access memory at address 0x0              # 解引用 0x0 就是崩因

(gdb) info registers rip                       # ⑥ 底层佐证
rip = 0x... <writeIt+..>                          # RIP 正常，说明是数据访问非法而非控制流跑飞
SIGSEGV → bt → frame → p ptr=0x0 → nullptr 解引用
如何区分 nullptr / 野指针 / 悬垂指针
  • nullptr：p ptr 显示 0x0（或很小的地址如 0x8，是空指针 + 成员偏移）；
  • 野指针（wild）：从未初始化，p ptr 是一个看起来随机、离谱的地址（如 0x7f... 之外的怪值）；
  • 悬垂指针（dangling / UAF）：地址看起来正常，但 p *ptr 出来的内容是垃圾或已被改写 —— 见案例 2。

根因：main 把 nullptr 传进 writeIt；真正的 bug 不在崩溃点 #0，而在 #1（调用者传了空指针）。崩溃点常是「受害者」，根因在调用链上游 —— 这就是为什么要看整条 bt。

05

案例 2：Use-After-Free

最阴险的一类 —— 有时崩、有时不崩

CASE 2 · Use-After-Free 
// uaf.cpp — g++ -g -O0 uaf.cpp -o uaf
#include <iostream>
int main() {
    int* ptr = new int(10);
    delete ptr;                 // 释放
    std::cout << *ptr << "\n";    // ← 访问已释放内存（UAF）
}
(gdb) break 6
(gdb) run
(gdb) p ptr
$1 = (int *) 0x5555555592c0        # 地址看起来完全正常！
(gdb) p *ptr
$2 = 10                            # 有时还能读到旧值 10——这才可怕
# 也可能是垃圾值，甚至此刻不崩、后面某处才崩
为什么 UAF 有时不立即崩溃？

delete 只是把这块内存「还给分配器」，并不会立刻清零，也不会立刻还给操作系统。所以紧接着读它，物理上那块内存往往还在、旧值还没被覆盖 —— 于是 *ptr 读出 10，程序「看起来正常」。真正的崩溃发生在那块内存被后续分配复用、内容被改写之后，此时读到的是别人的数据，或者结构体里的指针成了垃圾，间接触发 SIGSEGV。崩溃点和真正的错误（那次 delete 后仍持有指针）在时间和空间上都是错位的 —— 这正是 UAF 极难用 GDB 定位的根源。

为什么 Debug / Release 行为可能不同

UAF 属于未定义行为（UB）。-O0 下内存布局、分配复用节奏是一种样子；-O2 下变量可能被优化、内存复用时机改变，甚至编译器基于「UB 不会发生」的假设重排代码 —— 于是同一份 UAF，Debug 可能默默跑过、Release 却崩，或反过来。「换个优化级别行为就变」本身就是 UB 的强烈信号。

为什么 ASan 更适合抓 UAF

GDB 只能看「崩溃那一刻」的现场，而 UAF 的现场早已错位，你看到的往往是「受害者」而非「凶手」。AddressSanitizer（ASan）不同：它给每块内存维护「影子状态」，delete 后把该区域标记为「隔离/中毒（quarantine）」，只要之后任何一次访问它，ASan 立刻在第一现场报错，并同时打印「分配栈 + 释放栈 + 当前访问栈」三条调用链 —— 直接把「谁分配的、谁释放的、谁又访问了」摊开给你看。所以：UAF / 越界这类问题，先上 ASan；GDB 用来对 ASan 指出的点做进一步动态确认。

$ g++ -g -O1 -fsanitize=address uaf.cpp -o uaf
$ ./uaf
==ERROR: AddressSanitizer: heap-use-after-free ...
  READ of size 4 ...
  freed by thread T0 here: ... main uaf.cpp:5     # 释放点
  previously allocated by thread T0 here: ... :4  # 分配点

案例 3 回顾：多线程死锁

在第 05 篇已完整演示，这里放进统一的思维框架

死锁不产生信号、不崩溃，只是永久卡住。它的分析路径与崩溃不同，但思维一致 —— 先拿全场快照，再拼因果：

程序卡死 → Ctrl+C / attach 冻结
info threads → 多个线程停在 lock？
thread apply all bt → 每个线程「持有/等待哪把锁」
拼出环形等待 → 死锁根因：加锁顺序不一致

完整代码与逐步演示见 第 05 篇 · 案例 3。修复思路：全局统一加锁顺序，或 std::scoped_lock 同时上多把锁。

工具对比：GDB / ASan / TSan / Valgrind / Core / perf

真实项目从不是「只用 GDB」，而是多个工具各就各位

工具主要用途擅长发现典型代价 / 特点
GDB交互式调试、断点、调用栈、变量、内存崩溃定位、死锁、逻辑错误、按需观察现场需复现或 core；不自动发现问题
ASan地址消毒器（编译期插桩）堆/栈越界、Use-After-Free、重复释放~2× 变慢、内存翻倍；第一现场报错
TSan线程消毒器（编译期插桩）数据竞争 Data Race~5–15× 变慢、内存暴涨；抓时序问题
Valgrind动态二进制插桩（memcheck 等）内存泄漏、未初始化读、非法访问~10–50× 极慢；无需重编译
Core Dump崩溃后的离线现场快照线上偶发、无法复现的崩溃静态快照，配合 GDB 事后分析
perf基于采样的性能剖析CPU 热点、哪段代码耗时低开销；解决「慢」而非「错」
怎么组合使用（工程经验）
  • 崩了、能复现 → GDB run + 七阶段；
  • 崩了、线上偶发 → 开 core dump，事后 gdb ./app core；
  • 怀疑内存越界 / UAF → 先跑 ASan 定位第一现场，再用 GDB 确认；
  • 偶发算错 / 多线程诡异 → TSan 抓数据竞争；
  • 内存一直涨 → Valgrind / ASan-leak 查泄漏（GDB 查不了）；
  • 不崩但慢 → perf 找热点。

可与站内 Sanitizer 内部实现、性能与崩溃排查目录交叉阅读。

09

C++ Debugging Mindset：调试思维框架

整个系列最重要的一节 —— 命令是术，思维是道

先纠正一个起点

不要从「我应该输入哪个 GDB 命令？」开始。
而要从「我现在掌握了什么现场信息？下一步需要验证什么假设？」开始。
GDB 命令只是验证假设的手段，不是调试的目的。把顺序搞反，就会陷入「乱敲命令、看一堆输出却不知所云」。

通用调试循环

现象（崩溃 / 卡死 / 算错）
建立假设（可能是什么原因？）
获取现场（run / core / attach）
缩小范围（bt → frame → 变量，逐层收窄）
验证假设（p / x / watch / set var 求证）
定位根因（找到真正的错误来源，而非崩溃点）
修复 → 验证（改完再复现一遍确认）

把框架套到「程序 Crash」上

程序 Crash
    ↓ 是不是 SIGSEGV？          → 是 → 假设「非法内存访问（指针）」
看 bt
    ↓ Crash 在哪个函数？         → #0 是现场，但根因可能在上游帧
查看 frame + info args/locals
    ↓ 哪个指针 / 参数异常？       → 缩小到某个变量
查看变量 p ptr / p *ptr
    ↓ 是不是 nullptr？           → 验证假设
沿 bt 继续向上追踪调用链
    ↓ 这个坏值是从哪一层传进来的？  → 逐帧 up，找数据变坏的分界
找到错误来源（Root Cause）        → 往往不在崩溃行，而在若干层之上
三条贯穿全系列的心法
  1. GDB 是验证假设的工具，不是「看代码工具」。每敲一条命令前，先问「我想验证什么？」。
  2. 崩溃点 ≠ 根因。#0 常是受害者，真正的错误（传了空指针、提前 delete、加锁顺序错）在调用链上游或时间上更早处。
  3. 先粗后细、能省则省。先信号 → bt → 变量，能定位就停；栈损坏/优化干扰才下探到内存和汇编。
从这里，把整个知识体系串起来

你现在应该能独立走完：编译 Debug 版 → 启动 GDB → 设断点 → 运行 → 单步 → 看变量 → 看调用栈 → 切 Frame → 看内存 → 看寄存器 → 看汇编 → 切线程 → 分析 Crash / Deadlock → 定位 Root Cause。并且理解这条底层链条：
C++ 代码 → 编译器 → 机器码 → CPU → 寄存器 → Stack → Stack Frame → CALL/RET → GDB 观察运行现场。
想把「原理」那一半补齐，回到姊妹系列：函数调用 · 栈帧 · CALL/RET · ABI。

10

常见误区（全系列汇总）

❌ 有 -g 就一定能完整调试。 同时开 -O2 会让行号跳、变量 <optimized out>、函数因内联消失。

❌ GDB 能解决所有内存问题。 越界/UAF 常在错位的时间地点才崩，GDB 只看崩溃现场；泄漏更是完全看不出。

❌ GDB 可以替代 ASan。 ASan 在第一现场报错并给出分配/释放/访问三条栈，GDB 做不到；两者互补。

❌ bt 一定能拿到完整调用栈。 内联、缺帧指针、栈被溢出覆盖、尾调用优化，都可能让 bt 不完整或错乱。

❌ Release 程序不能使用 GDB。 能用，只是受优化与 strip 限制；生产常用 -O2 -g + 分离符号 + core dump。

❌ 优化后的程序变量一定能正常查看。 常显示 <optimized out>，因为变量被消除或只短暂存在于寄存器。

❌ p 出来的变量一定是真实当前值。 优化后 GDB 可能给出过期/近似值；崩溃在库函数、寄存器被覆盖时也未必准。

❌ 多线程问题都可以通过 GDB 定位。 死锁/卡住可以；数据竞争这类时序敏感问题该用 TSan，GDB 断点还会改变时序。

❌ 崩溃行就是 bug 所在。 崩溃点常是受害者，根因多在调用链上游或更早的错误操作（空指针来源、提前释放处）。

11

面试问题

点击每道题展开参考答案（先自测，再对照）。

  1. 基础GDB 如何定位 Segmentation Fault？

    用 run 复现或 gdb ./app core 加载 core，GDB 会停在崩溃点。然后 bt 看调用链、frame/info args/info locals 看当前上下文、list 看崩溃行、p ptr/p *ptr 判断是空/野/悬垂指针，必要时 info registers（看 RIP）与 x 下探内存确认根因，并沿 bt 向上找坏值来源。

  2. 基础Core Dump 和直接使用 GDB 有什么区别？

    直接 run 是程序活着、可继续执行和动态观察，但需要能复现。Core dump 是崩溃瞬间的静态内存快照，进程已死不能再执行，只能查看当时状态；它解决了线上偶发、无法复现的问题，是生产事故排查的主要手段。

  3. 原理为什么 Use-After-Free 有时不立即崩溃？Debug/Release 为何可能不同？

    delete 只是把内存还给分配器，不立即清零或归还系统，旧值常还在，紧接着访问可能「看似正常」，直到内存被复用改写才崩，崩溃点与错误点错位。UAF 是 UB，不同优化级别下内存布局、复用时机、代码重排都不同，导致 Debug 与 Release 行为不一致——「换优化级别行为就变」本身就是 UB 信号。

  4. 原理为什么 Release 版本变量常显示 <optimized out>？

    优化会把中间变量折叠消除、或让变量只短暂存在于某寄存器，运行时没有对应存储，GDB 无从读取，只能报告被优化掉。这是 -O2 的正常现象，与 -g 是否存在无关。

  5. 原理什么情况下 backtrace 不完整？

    函数被内联（栈里没有独立帧）、编译时省略帧指针且缺 DWARF CFI、栈被缓冲区溢出覆盖导致返回地址损坏、尾调用优化复用栈帧、以及崩在无符号的第三方库里，都会让 bt 不完整或错乱。

  6. 工程GDB 能不能定位内存泄漏？为什么？

    基本不能。泄漏是「该释放而未释放」，程序照常运行、不产生异常现场，GDB 这种「按需暂停看现场」的工具无从发现。应使用 Valgrind memcheck 或 ASan 的 leak 检测，它们跟踪每次分配/释放并在结束时报告未回收的块及其分配栈。

  7. 进阶GDB 与 ASan、TSan 分别有什么区别？

    GDB 是交互式调试器，按需暂停观察单点现场，擅长崩溃定位与死锁。ASan 是编译期插桩的内存错误检测器，在第一现场抓越界/UAF 并给出分配/释放/访问三条栈。TSan 是编译期插桩的线程检测器，全程监控内存访问先后关系以发现数据竞争。三者是「观察」与「自动检测」的分工，工程上组合使用。

  8. 进阶你的 C++ 崩溃排查思维流程是怎样的？

    从现象出发建立假设（看信号定方向），获取现场（run/core/attach），用 bt→frame→变量逐层缩小范围，用 p/x/watch 验证假设，沿调用链找到真正的根因（崩溃点常是受害者），修复后再复现验证。核心是把 GDB 当作验证假设的工具，而不是漫无目的地看代码。
