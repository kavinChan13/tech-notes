01

引言

先建模所有权，再谈 API

智能指针把裸 new/delete 的重复释放、漏释放、UAF、异常泄漏收进类型系统。会写 make_shared<T>() 不够——还要能画出控制块、分清「计数原子」和「对象本身线程安全」、并在循环引用 / 异步回调 / 热更新里选对 weak_ptr 与 atomic<shared_ptr>。

房子钥匙：unique_ptr 只有一把，转交必须交钥匙；shared_ptr 配多把钥匙（强计数），最后一把交回才拆房；weak_ptr 只记门牌号，进门前要 lock() 问「房还在吗」。

  • 值类别与拷贝控制 —— Rule of 0/3/5，是写智能指针的前置
  • 内存模型 §14.8 —— atomic shared_ptr / hazard pointer / RCU 三种无锁回收

2.3 选型决策树（背下来）

选 unique_ptr 当...

  • 资源独占（fd、连接、锁）
  • 工厂返回
  • 所有权可移动转移
  • PIMPL 实现

03

unique_ptr 完全剖析

独占 · EBO · 自定义 deleter · 单向升级

3.1 模板签名与典型大小

template<class T, class Deleter = std::default_delete<T>> class unique_ptr; —— deleter 是类型的一部分，直接进 sizeof。

类型sizeof（64-bit）原因
unique_ptr<int>8默认 deleter 空类，EBO 吃掉
unique_ptr<int, FileCloser>8空 struct 同样 EBO
unique_ptr<int, void(*)(int*)>16函数指针占 8B，无法 EBO
unique_ptr<int, function<void(int*)>>40+类型擦除 + SBO，别这样写

3.2 EBO 让"空 deleter 不占空间"

libstdc++ 把 T* 和 D 塞进可 EBO 的 tuple：空类 D 占 0 字节，所以默认 unique_ptr 和裸指针一样大。有状态的 deleter（函数指针、捕获了东西的 lambda）才会把 sizeof 撑开。

3.3 自定义 deleter 的 3 种正确写法

// 空类 deleter：EBO，sizeof 仍是 8；可作 API 上的稳定类型
struct FileCloser {
    void operator()(FILE* f) const noexcept { if (f) fclose(f); }
};
std::unique_ptr<FILE, FileCloser> f{fopen("x", "r")};
// lambda 无捕获同样 EBO；函数指针 deleter 会让 sizeof 变成 16
别用 std::function 当 unique deleter——SBO 把指针从 8 撑到 40+。PIMPL 的析构/移动必须放到 .cpp（Impl 完整后）再 = default，否则头文件里 default_delete<Impl> 对不完整类型删不了。

3.5 release / reset / swap —— 三件套语义

操作所有权旧对象
release()交回裸指针，自身变空不删，调用方负责
reset(p)接管 p先用 deleter 删旧
reset()变空删旧
swap(q)互换都不删

3.6 从 unique 到 shared 的"单向升级"

工厂返回 unique_ptr：默认零开销，调用方按需 move 升级。一开始就返回 shared_ptr 等于强迫所有人付计数。

3.7 unique_ptr 与 PIMPL

头文件只前向声明 struct Impl + unique_ptr<Impl>。析构和移动必须在 .cpp 里（Impl 完整之后）写成 = default。写在头文件会在 Impl 不完整时实例化 default_delete，编译失败。

shared_ptr 控制块完整布局 ⭐

对象指针 + 控制块；强计数管对象，弱计数管控制块

shared_ptr 的全部语义都在控制块：use_count→0 析构 T；weak_count→0 释放控制块。下面这张图比任何 API 列表都重要。

use_count→0 拆房（析构 T）；两个计数都→0 才注销门牌（释放控制块）。

4.2 控制块字段解释

字段语义
use_countshared_ptr 个数；0 → 析构 T
weak_countweak 个数 +「还有 strong」这一份虚引用；0 → 释放控制块
deleter / allocator类型擦除；所以 shared_ptr<T> 不含 D，多态转换才成立

deleter 不能进类型：否则 shared_ptr<Base> = make_shared<Derived>() 和 shared_ptr<FILE>(fp, fclose) 都做不到。代价是析构多一次虚调用——unique 没有这笔开销。

4.4 控制块的 3 种实现策略

策略触发布局
分离shared_ptr(new T) / 自定义 deleter对象、控制块各 alloc 一次
一体make_shared控制块 + T 一次 alloc
内嵌 weakenable_shared_from_this对象里藏 weak_this，构造 shared 时回填

4.5 看真实 libstdc++ 源码（简化）

基类 _Sp_counted_base 只放两个 _Atomic_word（32-bit，不是 long）和虚函数 _M_dispose（析构 T）/_M_destroy（释放控制块）。_Sp_counted_deleter 走分离式；_Sp_counted_ptr_inplace 把 T 嵌在控制块里——这就是 make_shared。

05

make_shared vs shared_ptr(new T)

一次分配 vs 两次；weak 拖住整块内存

5.1 两种构造方式的内存布局对比

❌ 两次分配
T* p = new T;          // alloc 1：对象
shared_ptr<T> sp(p);   // alloc 2：控制块
✅ 一次分配
// 一块：[控制块 | T]
auto sp = std::make_shared<T>();

5.2 性能基准（典型机器，对象 32B）

方式耗时分配
shared_ptr(new T)~120 ns2
make_shared~50 ns1
allocate_shared + PMR pool~20 ns1（池）

5.3 make_shared 的"陷阱" —— 内存不立刻还给 OS

大对象 + 长寿命 weak_ptr（缓存窥视）不要 make_shared：对象已析构，KB/MB 级空间仍被控制块拖着。改用分离分配，T 死立刻还内存。

5.4 异常安全 —— make_shared 的另一胜场

C++14 前 f(shared_ptr(new A), g()) 可能先 new A 再 g() 抛异常，shared 还没接管 → 泄漏。C++17 修了求值顺序，但 make_shared 仍更好（一次分配）。

5.5 make_shared 不能用的场景

场景改用
自定义 deletershared_ptr(p, deleter)
构造函数 private友元工厂，或 shared_ptr(new T)
大对象 + 长 weak分离分配（§5.3）

低延时路径用 allocate_shared + 每请求 monotonic pool：控制块和 T 都从池出，请求结束整池丢掉。

weak_ptr 与循环引用

强环泄漏；弱引用观察；lock() 原子升级

6.1 循环引用导致的内存泄漏

struct Node {
    std::shared_ptr<Node> next;   // 强：主所有权
    std::shared_ptr<Node> prev;   // ❌ 强环：a↔b 离开后 use 仍为 1
};
// ✅ prev 改 weak_ptr<Node> — 不增加对方 use_count

6.2 用 weak_ptr 打破循环

树/链表：「主方向」shared，「反向/观察」weak。不要两边都强。

6.3 weak_ptr 的核心 API

从 shared 构造；lock() 原子升级；expired() 只是快照，有竞态。真用就 lock 判返回值。

6.4 lock() 的内部原子操作

lock() 内部是对 use_count 的 CAS 循环：读到 0 直接空；否则尝试 +1。不要自己先 expired() 再 lock。

6.5 weak_ptr 的典型用法 — 观察者模式

6.6 weak_ptr 与缓存模式

模式存什么要点
观察者vector<weak_ptr<Obs>>notify 时 lock；失败就 erase。观察者析构不必 detach
缓存map<K, weak_ptr<V>>get 时 lock 命中才返回；失败当 miss。缓存不延长寿命
07

Aliasing Constructor

get() 指向子对象，控制块仍管父对象

7.1 签名与语义

shared_ptr<T>(other, raw)：与 other 共享控制块，get() 返回 raw。把「引用计数」和「当前指针」拆开。

7.2 经典用例：指向 vector 内某个元素，但持有 vector 所有权

shared_ptr<int> elem{vec, &vec->at(2)}：elem 活着，整个 vector 就不释放。别返回裸 &vec[i]。

7.3 经典用例：返回内部子对象，但延长父对象生命周期

工厂返回 shared_ptr<Child>{self, &self->child_}。调用方只拿得到 Child，Parent 由控制块保活。

7.4 C++17 与 aliasing 的 move 版本

rvalue 重载把控制块「偷」过来，少一次原子 +1/-1。能 move 就 move。

7.5 真实使用：CRTP 风格的子视图、Protobuf 子消息

Protobuf：shared_ptr<Header> h{msg, msg->mutable_header()}，异步队列只传 Header 视图，整包 Message 跟着活。没有 aliasing 就得拷整包。

08

enable_shared_from_this

对象里藏 weak_this；必须先被 shared_ptr 管住

8.1 解决什么问题

异步回调捕获裸 this 不延长寿命。需要「把自己活到回调跑完」——从对象内部拿出自己的 shared_ptr 再捕获。

8.2 用法

类公开继承 enable_shared_from_this<T>，且对象必须由 shared_ptr 创建。回调里 auto self = shared_from_this() 再捕获 self。

8.3 内部机制 —— 内嵌一个 weak_this

8.4 关键问题：weak_this 何时被赋值？

struct Foo : std::enable_shared_from_this<Foo> {
    Foo() { shared_from_this(); }   // ❌ 抛 bad_weak_ptr：ctor 时还没回填
    void start() { auto self = shared_from_this(); }
};
auto p = std::make_shared<Foo>();   // 构造返回后才注入 weak_this
p->start();                         // ✅ post-ctor

C++17 weak_from_this() 直接拿 weak，未管理时返回 expired，不抛。Asio session：每次 async_* 捕获 self = shared_from_this()，回调跑完前连接对象不死。

8.6 真实使用范式 —— Asio / Beast 的 strand-based session

链式 do_read 里用 init-capture [self = shared_from_this()]。外部 reset 最后一个 shared 也不影响已入队的回调。

09

std::atomic<std::shared_ptr<T>> (C++20)

控制块原子 ≠ 指针变量本身原子

9.1 问题：shared_ptr 变量本身的并发修改是 race

9.2 C++11/17 的临时方案 — 自由函数 atomic_load / atomic_store

atomic_load(&g) / atomic_store：C++20 弃用、C++26 移除。库多用全局锁池，别在热路径上用。

9.3 C++20 正式入标：std::atomic<std::shared_ptr<T>>

load 拿当前快照，store 原子替换。读端握着旧 shared，写端换新配置，两边都不 UAF。

9.4 实现内部 — 不是真的"无锁"

is_always_lock_free 不是 true。libstdc++ 早期 mutex 池；新实现 split lock / HP；Folly 才接近 lock-free 读。

9.5 性能基准

操作无竞争4 线程读
裸拷贝~5 ns—
atomic<shared_ptr>.load~30 ns~80–150 ns
folly::atomic_shared_ptr~10 ns~20–30 ns

不热 → 标准 atomic；读极重 → Folly 或 hazard pointer / RCU。

10

多线程下的 shared_ptr 真相

三档安全：计数原子、变量不原子、对象你自己管

10.1 三档安全等级

场景安全？
不同实例指向同对象，各自拷贝/析构✅
多线程只读同一实例（const）✅
多线程写同一实例❌ data race
并发改 T❌ 用户负责

10.2 反例与正例

两个线程对同一 sp 做 = / reset 是 UB。先 auto copy = sp（单线程）再把 copy 按值进线程；或者用 §9 的 atomic。

10.3 引用计数的内存序

+1 用 relaxed（已持有合法引用，只把计数变大）。-1 用 release；最后一个再 acquire fence 后才析构，保证其他线程对 T 的写 happens-before 析构。详见 内存模型 与 §14.4。

10.4 跨 .so 边界的陷阱

两边必须同一份控制块定义：都动态链同一 libstdc++ 才行。静态链、混 libc++、混 MSVC CRT 都会把计数打到两份副本上。公共 API 三选一：统一 toolchain、改 C ABI、或 intrusive_ptr（§11）。

11

intrusive_ptr 与替代方案

计数进对象；sizeof 一半，但要改类型

11.1 intrusive_ptr 是什么

对象提供 intrusive_ptr_add_ref / release（COM 的 AddRef/Release 就是这个）。Boost 包装成 RAII。

11.2 intrusive vs std::shared_ptr 对比

项shared_ptrintrusive_ptr
sizeof168
分配1 或 21（计数已在对象内）
裸指针重建危险安全
weak有无
改类型否是

11.3 什么时候选 intrusive_ptr

性能敏感、C 层来回传、跨 .so 不想绑 STL、或包装 COM。对象池把 release 改成还池而不是 delete。

11.4 其他智能指针替代方案

类型用途
out_ptr / inout_ptr (C++23)接 C API 的 T**
observer_ptr / T*显式非拥有
function_ref (C++26)callable 非拥有视图

11.5 反模式：用 raw pointer + 自己管引用计数

不要手写 retain/release（接 COM 除外）。用 intrusive_ptr 包一层，让析构帮你减计数。

14.1 基础（必答）

  1. 基础unique_ptr / shared_ptr / weak_ptr 各自语义？
    unique
    独占所有权，不可拷贝、可移动，零开销（等价裸指针）。
    shared
    共享所有权，原子引用计数，最后一个析构时释放对象。
    weak
    不增加强引用的观察者，用于打破循环；通过 lock() 临时提升为 shared_ptr。
  2. 基础sizeof(unique_ptr) 多少？sizeof(shared_ptr) 多少？
    unique
    默认 1 个指针大小（8B），无状态 deleter 经 EBO 不占空间；带状态 deleter 会变大。
    shared
    2 个指针（16B）：对象指针 + 控制块指针。
  3. 基础make_shared 比 shared_ptr(new T) 好在哪？至少 3 点
    ① 单次分配
    控制块 + 对象合并成一块，减少一次 malloc + 提升缓存局部性。
    ② 异常安全
    避免 f(shared_ptr(new T), g()) 求值顺序导致的泄漏。
    ③ 简洁
    不写裸 new，代码更短。
    代价
    只要还有 weak_ptr 存活，整块内存（含大对象空间）不释放。
  4. 基础shared_ptr 的引用计数线程安全吗？对象本身呢？
    计数
    控制块引用计数是原子的、线程安全：多个 shared_ptr 各自拷贝 / 析构安全。
    对象
    不安全：并发改同一对象需自行加锁；多线程读写同一个 shared_ptr 实例需 atomic<shared_ptr>。
  5. 基础循环引用怎么产生？怎么解？
    产生
    两对象互相用 shared_ptr 持有 → 计数永不归零 → 内存泄漏。
    解
    把其中一方改 weak_ptr（典型：父→子用 shared，子→父用 weak）。

14.2 中级

  1. 中级控制块里有哪些字段？为什么 weak_count 初值是 1？
    字段
    strong count、weak count、删除器、分配器，以及（make_shared 时）内联的对象存储。
    weak=1
    所有 strong 引用合起来算"一个 weak 持有者"。strong 归零时减掉这个 1，使控制块在最后一个 weak 也消失时才释放 —— 保证 expired() 等查询期间控制块仍有效。
  2. 中级enable_shared_from_this 内部怎么工作？为什么必须先用 shared_ptr 创建对象？
    机制
    基类内藏一个 weak_ptr；shared_ptr 构造时检测到该基类并回填这个 weak。shared_from_this() 即 weak.lock()。
    前提
    若对象不是被 shared_ptr 管理（栈对象 / 裸 new），weak 未初始化 → C++17 起抛 bad_weak_ptr（旧标准 UB）。
  3. 中级shared_ptr 拷贝时引用计数 +1 用什么 memory_order？为什么？
    +1
    relaxed。增加引用不改变对象可见性 —— 调用前我已持有合法引用，仅让计数变大，无需 happens-before。
    -1
    acq_rel（或 release + 末次 acquire fence），保证其他线程对对象的所有写 happens-before 析构。详见 §14.4。
  4. 中级weak_ptr.lock() 内部做了什么？
    实现
    原子检查 strong count 是否 > 0，是则用 CAS 把 strong+1 并返回 shared_ptr，否则返回空。本质是一个无锁 CAS 循环。
  5. 中级aliasing constructor 是什么？给一个真实使用场景
    定义
    shared_ptr<T>(other_sp, raw_ptr)：共享 other 的控制块（计数），但 get() 返回另一个指针。
    场景
    持有结构体某个成员的 shared_ptr，同时让整个结构体保持存活（计数挂在父对象上）。
  6. 中级shared_ptr<Base>{new Derived} 在 Base 析构非 virtual 时为何安全？
    原因
    shared_ptr 构造时把删除器类型擦除为 delete (Derived*) 并存进控制块，析构时调用记录的删除器删真实类型 Derived，不依赖 Base 虚析构。
    对比
    unique_ptr 无此保护 —— 多态删除仍需虚析构。
  7. 中级shared_ptr 和 std::function 都做类型擦除，开销分别在哪？
    shared_ptr
    擦除"如何删除"（删除器），开销在控制块一次分配 + 原子计数。
    function
    擦除"如何调用"，开销在可能的堆分配（超过 SBO 时）+ 一次间接调用。

14.3 高级（体现深度）

  1. 高级std::atomic<std::shared_ptr<T>> 内部是真无锁吗？
    不保证
    is_lock_free() 多为 false。多数实现用 spinlock / 锁分段保护控制块的原子换出 —— 逻辑上无锁语义，物理上常有锁。
  2. 高级make_shared 创建大对象 + weak_ptr 长期持有，会有什么问题？
    问题
    对象与控制块同一块内存；strong 归零对象析构，但只要 weak 还在，整块内存（含大对象空间）不释放 → 内存浪费。
    对策
    大对象 + 长 weak 改用 shared_ptr(new T) 分离分配。
  3. 高级shared_ptr 跨 .so 边界传递有什么 ABI 坑？怎么规避？
    坑
    不同编译器 / STL 版本控制块布局不同；删除器与分配器跨边界；可能跨不同堆。
    规避
    边界用 C 接口，或保证两侧同一套 ABI / 运行时；删除器在创建侧定义。
  4. 高级boost::intrusive_ptr 比 std::shared_ptr 强在哪？弱在哪？
    强
    计数嵌入对象内 → 单次分配、sizeof=1 指针、可从裸指针重建。
    弱
    侵入式需改对象、无内建 weak、需手写 add_ref / release。
  5. 高级设计一个"对象池版" shared_ptr（释放时回池，不 delete），怎么做？
    做法
    用自定义删除器归还池而非 delete： 
    std::shared_ptr<T> p(pool.alloc(),
    [&pool](T* q){ pool.recycle(q); });
    注意
    池的生命周期必须 > 所有指针；删除器捕获的引用 / 指针不能悬空。
  6. 高级shared_ptr 持有 const T 与持有 mutable T 的语义区别？
    const T
    只读共享：不能改对象，但能 reset 指针本身。多读者天然安全。
    mutable T
    允许改对象，多写者需自行同步。
  7. 高级从一个 shared_ptr<Derived> 转成 shared_ptr<Base> 是什么成本？反过来呢？
    上行
    static_pointer_cast，共享控制块，原子 +1，O(1) 无检查。
    下行
    dynamic_pointer_cast，含 RTTI 运行时检查，更贵且可能失败返回空。
  8. 高级设计一个 LRU cache，key→value 是 weak_ptr，怎么避免 cache 自己延长对象生命周期？
    做法
    value 存 weak_ptr，get 时 lock()：命中且 lock 成功才返回；失败说明对象已被外部释放 → 当作 miss 并清理该 entry。
    效果
    cache 不持 strong 引用、不延长寿命；可配合定期清理过期 entry。

14.4 速答示范（第 8 题：shared_ptr 拷贝的 memory_order）

答：拷贝时 fetch_add(1, memory_order_relaxed)。原因是"增加引用"这个动作不会让对象的可见性变化 —— 我执行这条之前已经持有合法引用，增加只是让计数变大，无需任何 happens-before 关系。
析构时 fetch_sub(1, memory_order_release)，最后一个释放后插入 acquire fence，然后才析构对象。这是为了让其他线程在该对象上的所有写都 happens-before 析构 —— 否则可能读到不完整的状态。
这一题是检验"你是真懂 memory_order 还是背了 acquire/release"的金标准。
