01

一、简单对象的内存布局

C++ 中最基本的对象就是一个无虚函数

无虚函数、无继承的 struct/class：编译器按声明顺序铺数据成员；对齐不够就插 padding。成员函数在 .text，不占 sizeof。

02

二、内存对齐与 Padding

对齐规则 · 未优化 vs 优化布局 · 常见类型的对齐要求

CPU 按自然对齐取数。编译器在成员之间和结构体尾部插 padding。上图 Bad 就是 char 卡住 double 的 8 字节边界。

对齐规则

  • 每个成员起始地址必须是其 alignof 的倍数
  • 结构体总大小必须是最大成员 alignof 的倍数

常见类型的对齐要求

类型大小对齐 (alignof)
char11
short22
int / float44
long4（Win LLP64）/ 8（Linux LP64）同大小
double / long long / pointer88
long double (x86)12 / 164 / 16

long 的大小是跨平台陷阱：Windows 64 位 LLP64 上仍是 4 字节。宽度与 INT_MAX / LONG_MAX 详见 类型转换 · 整型宽度。

03

三、this 指针与成员访问

成员函数被编译器隐式传递一个 this 指针

成员函数被编译器改写成普通函数，多一个隐藏的 this：成员访问就是「对象基址 + 编译期偏移」。x86-64 System V 用 rdi 传 this，Windows x64 用 rcx。多继承里这个指针还会被调（见 §6 / §14.2）。

04

四、虚函数表 (vtable) 与 vptr

当类含有 virtual 函数时

有 virtual 时，每个对象塞一个 vptr（通常在首部），指向该类唯一的 vtable（.rodata，所有实例共享）。

struct Animal {
    virtual void speak();   // vtable[0]
    int age;
};
// 对象: [ vptr 8B | age 4B | pad 4B ]   vptr → Animal::vtable[0]
05

五、单继承对象模型

单继承：派生对象 = 基类子对象（含那个 vptr）+ 自己的成员。Itanium 把 vptr 放首部，所以 Base* 与 Derived* 是同一地址，向上转型零成本。

06

六、多重继承对象模型

两个带虚函数的基类 → 对象里两份 vptr。转成第二基类要把指针加上子对象偏移；reinterpret_cast 不做这件事，是 UB。thunk 见 §14.2。

多继承里 static_cast 会调整指针；reinterpret_cast 不会——拿它在多继承层次里转是 UB。
07

七、虚继承与菱形继承

菱形继承问题

菱形继承若不声明 virtual public，最底类会有两份虚基类数据。虚继承把那份挪到对象尾部，中间用 vbptr / vbase offset 间接找。

class Mammal       : virtual public Animal { int fur; };
class WingedAnimal : virtual public Animal { int wingspan; };
class Bat : public Mammal, public WingedAnimal { int sonar; };
08

八、RTTI 与 type_info

RTTI (Run-Time Type Information) 使程序在运行时可以查询对象的真实类型

RTTI 挂在 vtable 负槽：typeid 是一次解引用；dynamic_cast 还要用 offset_to_top 走 __dynamic_cast，可能随继承深度变慢。-fno-rtti 能瘦二进制，但这两样都不能用。

09

九、构造与析构顺序

构造顺序（从内到外）

构造从内到外；析构完全反过来。每一层进函数体前，vptr 被写成这一层的表——所以构造/析构里调虚函数看不到最终派生类。

10

十、对象切片 (Object Slicing)

将派生类对象按值赋给基类变量时

按值赋给基类：派生数据丢掉，vptr 改成基类表，多态没了。要用指针或引用。

11

十一、空基类优化 (EBO)

C++ 标准要求每个对象至少占 1 字节（以保证不同对象有不同地址）

独立空对象必须 ≥ 1 字节（地址要能区分）。作为基类可以变成 0 字节，这就是 EBO。C++20 成员也能用 [[no_unique_address]] 拿到同样效果。MSVC 默认关 EBO，要 __declspec(empty_bases)。

struct Empty {};
struct Comp { Empty e; int x; };                       // 8：1B + pad 3
struct Ebo : Empty { int x; };                            // 4：空基类占 0
struct NoUa { [[no_unique_address]] Empty e; int x; };   // 4，不必继承
12

十二、POD、Standard Layout 与 Trivial 类型

C++11 将旧的 POD 概念拆分为两个正交属性：Trivial 和 Standard Layout

C++11 把旧 POD 拆成正交的两轴：Trivial（可以按字节搬）和 Standard Layout（布局可预测，offsetof 合法）。交集才是历史上的 POD。

struct Ok  { char a; int b; };                 // standard-layout
static_assert(offsetof(Ok, b) == 4);
struct Bad { private: int x; public: int y; };  // 访问级别混用 → 不是
// offsetof(Bad, y) 未定义

14.1 Itanium C++ ABI — vtable 的真实布局

GCC / Clang 走 Itanium C++ ABI。槽位已经画在 §4：vptr 指向 [0]，不是表头。typeid 是 *(vptr-1)；dynamic_cast 还要 offset_to_top。GDB：info vtbl obj。两个析构槽分别是 complete 与 deleting。

14.2 多继承与 vcall Thunk（this 指针调整）

通过第二基类的指针调已被覆盖的虚函数时，那一槽指向 thunk：先把 this 减回完整对象，再跳真正的实现。热路径应避开钻石 / 多继承。

14.3 空基类优化 (EBO) 与 [[no_unique_address]]

布局与短例见 §11。这里只补工程点：allocator / deleter / compare 走 EBO 是为了「策略对象零开销」；MSVC 要显式 __declspec(empty_bases)。两个同类型空基类不能都优化成 0（地址仍要能区分）。

14.4 Trivially Copyable 与 memcpy 合法性

见 §12 的两轴图。这里只钉「谁能 memcpy」：

类别可 memcpy可 memset(0)

含 std::string 的 struct 拷字节 = 共享堆缓冲，析构 double-free。

14.5 SBO / SSO — 标准库的小对象优化

小值塞进对象自己，避免堆分配。阈值因库而异，别写死。

类型优化常见阈值
std::stringSSOlibstdc++ 15B / libc++ 22B / MSVC 15B
std::functionSBO约 16–24B，超了就堆 + 虚调用
std::anySBO约 1–2 个指针
std::variant按最大 alternative无堆

lambda 捕获过大塞进 std::function，每次拷贝都是 new。热路径用模板或 function_ref。

14.6 位域 (Bit-field) 与 Flexible Array Member

位域把多个字段塞进同一个字；位序 implementation-defined，大端/小端还可能排反。解析网络头用移位掩码，不要 reinterpret_cast 成位域结构体。

14.7 std::launder 与对象重启

同一块 storage 上 placement new 之后，编译器仍可能按旧对象身份做常量折叠（const / 引用 / 旧 vptr）。std::launder 只是切断这个假设，不能凭空造对象。新指针本身已是新身份，不必 launder。optional / variant / any 内部都在用。

状态能做什么
已分配未构造搬字节、取地址
构造中 / 析构中this 可用；虚调用走当前层表
存活成员、方法、多态
已销毁、storage 还在placement new；不能再读成员
storage 已释放什么都不能
launder 不是 reinterpret_cast。内存里没有那个类型的活对象，launder 之后仍是 UB。

规则在上一张图里。写无锁结构 / 对象池 / union-variant 时，默认用新指针；只有「从裸字节重新解释旧名字」才请 launder。

14.9 inline namespace — ABI 版本演化的关键武器

inline namespace：对用户看起来在父命名空间里，mangled name 却带着版本前缀。GCC 5 的 Dual ABI 靠它让 COW string 和 SSO string 同在 libstdc++.so.6 里，-D_GLIBCXX_USE_CXX11_ABI 决定你链哪一套。

用法做什么判据
版本通道inline namespace v2 + 留下 v1nm 里是 myapi::v2::init，不是 myapi::init
Dual ABI两套 std::string 共存mangled 不同，不会「链接上了运行崩」
自家库MYAPI_LEGACY 切 inline 目标用户源码不用改
std::literals嵌套 inline 控制粒度可只开 string 或 chrono

两个 TU 不能把同一名字放进不同 inline namespace（ODR）。特化要进正确那一层。extern "C++" 跨不过 inline 边界。公共库第一天就规划 v1，五年后加 v2 并把 v1 的 inline 拿掉。

14.10 高频面试 Q&A

点击每道题展开参考答案（先自测，再对照）。

  1. 基础sizeof 空类为什么是 1 不是 0？

    C++ 要求不同对象有不同地址。如果 sizeof(Empty) == 0，数组 Empty a[10] 里所有元素地址相同、指针算术失效。作为基类时不受此限制，故有 EBO。

  2. 中级vptr 放对象首部还是尾部？为什么？

    放首部（Itanium ABI）。原因：

    • 单继承时 Base* 和 Derived* 指同一地址——指针零调整，性能好
    • 派生类增加成员只影响尾部，不改 vptr 位置
    • 但多继承下，非 primary base 的 vptr 必然在对象中间
  3. 基础为什么构造函数中调虚函数不触发多态？

    每层构造函数执行时，vptr 正被设置为该层自己的 vtable。若基类构造中调虚函数，此时派生类对象的派生部分还没构造，vptr 指向基类 vtable，调用的是基类版本。析构同理（反方向）。
    推论：永远不要在构造/析构中调虚函数，改用两阶段初始化。

  4. 中级虚函数有多少运行时开销？现代 CPU 能优化吗？
    • 每次调用：一次内存读（vptr）+ 一次内存读（vtable 项）+ 一次间接跳转
    • 间接跳转对 CPU 分支预测不友好，但现代 CPU 的 indirect branch predictor 对稳定类型能预测准确
    • 编译器的去虚化 (devirtualization) 可消除：final 类/方法、LTO 能看到唯一派生、constexpr 等场景

    实测：热路径 virtual 调用比直接调用慢 10-30%，冷路径几乎看不出。

  5. 中级final 关键字对性能有影响吗？

    ✅ 有。final 告诉编译器该类/方法不会再被继承/覆盖，编译器可以静态解析虚调用为直接调用（devirtualization），避免 vtable 查找。LTO 下效果更好。

    class Impl final : public Interface { ... };
Interface* p = new Impl;
p->foo();   // 编译器可直接调 Impl::foo，无 vtable
  6. 基础为什么基类析构函数一般要 virtual？什么时候可以不 virtual？

    通过基类指针 delete 派生对象时，若 ~Base 非 virtual 则只调 Base 析构 → 派生部分资源泄漏。
    可以不 virtual 的情况：

    • 基类设计为永不被 delete by pointer（如 CRTP 静态多态的基类）
    • 通过 protected 析构 + 禁止派生类 delete 的方式控制
    • 标准库的 std::enable_shared_from_this 等
  7. 基础struct 和 class 有区别吗？

    语法层面仅 2 点：① 默认访问权限（struct=public, class=private）；② 默认继承权限同上。
    内存布局、虚函数、模板参数推导等完全相同。惯例：纯数据用 struct，有不变式 / 封装的用 class。

  8. 中级如何查看一个类的真实内存布局？
    • Clang: clang -Xclang -fdump-record-layouts -c foo.cpp — 最友好
    • GCC: g++ -fdump-lang-class foo.cpp 产出 .class 文件
    • MSVC: /d1 reportSingleClassLayoutClassName
    • pahole（依赖 DWARF）：pahole -C MyClass a.out，直接显示 offset、hole、padding
    • GDB：ptype /o MyClass（新版支持）或 print &obj.member - (char*)&obj
  9. 中级为什么 std::vector<bool> 被视为设计失误？

    标准规定它为节省空间特化为位打包——每个 bool 占 1 bit。但带来：

    • operator[] 返回代理对象而非 bool&，auto& b = v[0]; 不是你想的
    • 不能取 &v[0] 作为 bool*
    • 非 thread-safe：并发修改相邻 bool 会冲突写同一 byte（word tearing）
    • 违反 Container concept

    替代：std::vector<char>、std::bitset、boost::dynamic_bitset。

  10. 高级什么是 layout-compatible？有什么用？

    两个 struct 如果成员序列的类型一一对应兼容，它们是 layout-compatible。可以通过 union 共同访问或 reinterpret_cast 合法转换——C++ 标准特别允许此时读共同初始序列不是 UB。

    struct Base   { int tag; };
struct Msg1   { int tag; int payload; };
struct Msg2   { int tag; double payload; };
// 通过读 tag 决定用哪个类型 — C 风格 tagged union
union U { Msg1 m1; Msg2 m2; } u;
if (u.m1.tag == 0) ...   // 合法：Msg1 和 Msg2 的初始公共序列是 { int tag; }
