一、简单对象的内存布局

C++ 中最基本的对象就是一个无虚函数

无虚函数、无继承的 struct/class：编译器按声明顺序铺数据成员；对齐不够就插 padding。成员函数在 .text，不占 sizeof。

02

二、内存对齐与 Padding

对齐规则 · 未优化 vs 优化布局 · 常见类型的对齐要求

CPU 按自然对齐取数。编译器在成员之间和结构体尾部插 padding。上图 Bad 就是 char 卡住 double 的 8 字节边界。

性能之外还有一条没得商量：只有自然对齐的访问才保证不被撕裂，这就是 std::atomic<T> 会把自己的 alignof 提到 sizeof 的原因。

对齐规则

  • 每个成员起始地址必须是其 alignof 的倍数
  • 结构体总大小必须是最大成员 alignof 的倍数

第二条是为数组服务的：&a[1] 就是 &a[0] + sizeof(T)，尺寸不是对齐的倍数，从第二个元素起就全歪了。

重排能省多少：一个算得出来的例子

编译器不会替你重排成员（C 互操作与 offsetof 都建立在「按声明序」之上），这笔账得自己算：

成员大小 / 对齐声明序偏移按对齐降序重排后
bool active1 / 10（其后填 7）21
double last_rtt8 / 880
int fd4 / 41616
char state1 / 120（其后填 3）20
void* ctx8 / 8248
sizeof有效数据 22B32（浪费 10B / 31%）24（浪费 2B / 8%）

只改声明顺序，对象就从 32 字节降到 24。孤立看这 8 字节没意义，但连接表里有 100 万个对象时它是 8 MB，而且一条 64 字节 cache line 从装 2 个变成装 2.67 个——遍历时命中率的提升往往比省下的内存值钱。规律是 padding 只来自「小成员卡在大成员前面」，按 alignof 降序声明填充必定最小。不用手算，pahole 会列出每个洞。

降序声明是默认动作而非铁律：热结构更该做冷热分离。反过来有时要主动扩大对齐（alignas(64) 独占一条 cache line 以消除伪共享），但堆上能否兑现取决于分配器，见 低延迟 · over-aligned new。

常见类型的对齐要求

类型大小对齐 (alignof)
char11
short22
int / float44
long4（Win LLP64）/ 8（Linux LP64）同大小
double / long long / pointer88
long double (x86)12 / 164 / 16

long 的大小是跨平台陷阱：Windows 64 位 LLP64 上仍是 4 字节。宽度与 INT_MAX / LONG_MAX 详见 类型转换 · 整型宽度。

三、this 指针与成员访问

成员函数被编译器隐式传递一个 this 指针

成员函数被编译器改写成普通函数，多一个隐藏的 this：成员访问就是「对象基址 + 编译期偏移」。x86-64 System V 用 rdi 传 this，Windows x64 用 rcx。多继承里这个指针还会被调整（见 §6 / §14.2）。

这一条改写解释了对象模型里一大半「为什么」：成员函数不占 sizeof（代码在 .text、全类共享）；非虚调用是纯静态的，调用点编译期就知道跳哪个符号，这是它能被内联的前提；static 成员函数没有 this，所以它能当 C 风格回调传给 pthread_create，普通成员函数不行——签名对不上的那一个参数就是 this。

04

四、虚函数表 (vtable) 与 vptr

当类含有 virtual 函数时

有 virtual 时，每个对象塞一个 vptr（通常在首部），指向该类唯一的 vtable（.rodata，所有实例共享）。

struct Animal {
    virtual void speak();   // vtable[0]
    int age;
};
// 对象: [ vptr 8B | age 4B | pad 4B ]   vptr → Animal::vtable[0]

vptr 为什么在对象最前面

标准没规定 vptr 的位置，这是 ABI 的选择。Itanium 把它放在偏移 0，理由只有一条但很硬：单继承下 Base* 与 Derived* 是同一个地址值，向上转型不需要任何指令。若放尾部，派生类一加成员 vptr 就换位置，每次转型都得先读一次「vptr 在哪」——先有鸡还是先有蛋。代价也随之锁死，而且都不在性能上：

后果工程上什么时候咬人
第一个数据成员不再在偏移 0，类不再 standard-layout给一个和 C 结构体对拷的类加一个虚析构，offsetof 失效、序列化静默错位
对象至少胖一个指针struct{int,int} 从 8B 变 24B；百万级小对象数组内存与 cache 一起翻三倍
构造函数必须写 vptr，不再 trivially default constructible失去 memset 批量初始化、静态对象进 .bss
虚函数声明顺序决定槽号，布局成了 ABI 的一部分在已发布头文件的虚函数列表中间插一个，老二进制全部调错槽——所以只能往末尾追加
调试时崩在一个不存在的地址、或 info vtbl 打出乱码，几乎总是内存被破坏而不是「虚函数出 bug」：vptr 就在对象首部 8 字节，越界写与 use-after-free 第一个踩坏的就是它，症状却要等下次虚调用才出现。

虚调用到底贵在哪

教科书式的拆解是「取 vptr + 查表 + 间接调用」，三步都真实存在，但它们几乎不是开销的主要来源：vptr 在对象首部、vtable 在 .rodata 且一类一张，两者热路径上基本常驻，合计 ~1–4 周期还常被乱序执行掩盖。真正收费的是无法内联（常常是数量级）和间接分支误预测（每次 15–20 周期）。

无法内联才是决定性的。 编译器看不见函数体，就无法常量传播、无法把循环不变量提出去、无法向量化整个循环，还必须假设这次调用可能改写任意可达内存。虚调用真正的成本不在调用点，而在它周围那一圈被切断的优化——这解释了为什么 microbenchmark 里只慢几个周期的东西放进真实循环能慢一倍。

分支预测则解释了为什么「按类型分桶、每桶批量处理」几乎总快于「一个混合数组挨个虚调用」：BTB 对单态调用点准确率接近 100%，一旦在几种类型之间来回跳就按次收费。

去虚化（devirtualization）

编译器只要能证明调用点的动态类型唯一，就能换成直接调用，进而恢复内联。能不能证明，取决于你给了它多少信息：

手段编译器据此推断
final（类或成员函数）不会再被派生 / 覆盖；静态类型已 final 时调用点直接解析
局部对象、刚 new 出来的对象动态类型在本函数内可见
匿名 namespace 里的类派生集合在本翻译单元内封闭
LTO + -fwhole-program-vtables全程序只有一个实现；需配合 -fvisibility=hidden
PGO 引导的推测去虚化「95% 是这个类型」：插入类型判断，命中走内联版本，否则回退

「加个 final 就快了一截」之所以有时成立，不是省掉了查表的两次访存，而是去虚化把内联的大门重新打开了。提速因此极不均匀：热循环里的一行 getter 可能快好几倍，几百行的大函数毫无变化。只有热路径上的小虚函数值得为它标 final。

whole-program devirtualization 的前提是「没有别人会再派生」，而 dlopen 加载插件的程序违反这个前提——新 .so 可以再派生一个类，主程序却已按「唯一实现」编译完了。插件宿主要么不开这个开关，要么把可被派生的接口类排除在 hidden 可见性之外，见 Symbol Visibility。
05

五、单继承对象模型

单继承：派生对象 = 基类子对象（含那个 vptr）+ 自己的成员。Itanium 把 vptr 放首部，所以 Base* 与 Derived* 是同一地址，向上转型零成本。

覆盖 vs 隐藏，以及那个静态绑定的默认参数

派生类的 vtable 是复制基类的表、替换被覆盖的槽、把新虚函数追加到表尾得来的，槽号因此在整条继承链上一致。但只有函数名、参数列表、cv / 引用限定全部一致才构成覆盖；漏个 const 就变成隐藏——派生类另开一槽，Base* 调到基类版本、Derived* 调到派生版本，同一个对象两种行为。写 override 让编译器替你检查。

默认参数是静态绑定的。 基类声明 virtual void draw(int w = 1)、派生类写 void draw(int w = 5) override，basePtr->draw() 执行的是 Derived::draw 的函数体，传入的却是基类的默认值 1——函数体走动态派发，默认值在调用点由静态类型填入。这个组合没有任何合理用途：虚函数不要带默认参数。

六、多重继承对象模型

两个带虚函数的基类 → 对象里两份 vptr。转成第二基类要把指针加上子对象偏移；reinterpret_cast 不做这件事，是 UB。thunk 见 §14.2。

多继承里 static_cast 会调整指针；reinterpret_cast 不会——拿它在多继承层次里转是 UB。

「指针值会变」这件事的全部后果

单继承养成的直觉是「转型只是换个类型标签，地址不变」，多继承一来这个前提就没了：static_cast<B*>(pc) 会加上一个编译期常量偏移（并额外插一个判空，因为空指针不该被调整），由此产生一串反直觉的现象：

写法结果与原因
(void*)pc == (void*)(B*)pcfalse——B 子对象不在对象首部，两个地址真的不同
pc == (A*)pctrue——A 是 primary base，偏移 0
dynamic_cast<void*>(pb)完整对象首地址：走 offset_to_top 退回最派生对象，可用来做对象身份比较

最常踩的是void* 往返：把 C* 存进一张 void* 注册表或 C 回调的 user_data，取出来时转成 B*——指针值从没被调整过，B 的成员全部读在 A 的字段上，还往往一时半会儿不崩。规则是 void* 只能原样转回「当初转进去的那个类型」。delete 同理：delete pb 若 ~B 非虚，传给分配器的是「完整对象地址 + 16」，堆元数据当场损坏；有虚析构就没问题——deleting destructor 会先把 this 调回完整对象，这正是那两个析构槽存在的理由之一。

这些麻烦都来自「第二个基类带数据成员」。把多继承限制在纯接口（只有纯虚函数、无数据成员）后，每个额外基类只贡献一个 vptr，布局仍可预测——COM 与 Qt 插件用的都是这个形态。要看真实布局：clang -Xclang -fdump-record-layouts。

07

七、虚继承与菱形继承

菱形继承问题

菱形继承若不声明 virtual public，最底类会有两份虚基类数据。虚继承把那份挪到对象尾部，中间用 vbptr / vbase offset 间接找。

class Mammal       : virtual public Animal { int fur; };
class WingedAnimal : virtual public Animal { int wingspan; };
class Bat : public Mammal, public WingedAnimal { int sonar; };

为什么偏移必须留到运行时才知道

这是虚继承一切代价的根源：Mammal 的成员函数只有一份机器码，却要同时服务单独的 Mammal（Animal 紧跟在自己的成员之后）和作为 Bat 一部分的 Mammal 子对象（Animal 被挪到 Bat 末尾）。同一份代码、两个偏移，所以偏移不可能烧进指令，只能每次从 vbptr 指向的表里读。三个后果比「慢一点」重要：

后果细节
访问虚基类成员是两次串行依赖访存读 vbptr → 读 vbase offset → 才能算出地址。这条依赖链无法被乱序掩盖，和普通继承的一条常量加法不在一个量级
offsetof 不可用，类不是 standard-layout偏移在不同最派生类型下就是不同的值，「这个成员在第几字节」没有唯一答案；按固定偏移序列化的代码全部出局
从虚基类向下 static_cast 是编译错误编译器不知道该减多少。只能 dynamic_cast，它靠 offset_to_top 在运行时解决，因此还要求类是多态的、RTTI 没关

构造责任上移，以及什么时候才真该用虚继承

虚基类只有一份，由最派生类直接构造，跳过中间层。Mammal 初始化列表里写的 : Animal(42)，作为 Bat 的子对象时被完全忽略——否则两条路径会把它构造两次，所以虚基类最好提供默认构造函数。为了让中间类同时适配两种身份，编译器还会生成一张 VTT，并为很多类产出两个版本的构造函数（Itanium 的 C1 与 C2）。

判据因此很窄：只有当「共享状态必须唯一」是正确性要求时才用虚继承（典型是 std::basic_iostream 必须只有一份 basic_ios）。菱形若只是接口重复，各基类纯虚、无数据成员，根本不会二义，别顺手加 virtual。

08

八、RTTI 与 type_info

RTTI (Run-Time Type Information) 使程序在运行时可以查询对象的真实类型

RTTI 挂在 vtable 负槽：typeid 是一次解引用；dynamic_cast 还要用 offset_to_top 走 __dynamic_cast，可能随继承深度变慢。-fno-rtti 能瘦二进制，但这两样都不能用。

为什么 type_info 比较会在跨 .so 时失败

Itanium ABI 的设计是「一个类型在整个进程里只有一个 type_info 对象」，于是 typeid(a) == typeid(b) 能退化成一次指针比较。但这个「唯一」是动态链接器而非编译器保证的：编译器把 typeinfo 发射成弱符号，多个 .so 各带一份，加载时由全局符号表合并。任何一环断掉，同一个类就有了两个 type_info。

断链的原因为什么会断
-fvisibility=hidden 未给多态类开洞typeinfo 变 hidden，不进全局符号表，无从合并
dlopen 默认的 RTLD_LOCAL插件符号不参与全局解析，与宿主的同名 typeinfo 互不相认
同一个静态库被链进两个 .so两份定义各自被本模块内部解析掉，没机会合并

最阴险的症状不是 dynamic_cast 返回 nullptr，而是异常抓不住：catch (MyError&) 的匹配同样走 type_info 比较，从另一个 .so 抛出的 MyError 会穿过你写得好好的 catch 飞到 std::terminate。（libstdc++ 在指针不等时会退回比较 name 字符串，libc++ 默认只比指针，换个标准库就复现。）

修法都在链接层面：给跨边界的多态基类和异常类显式标 visibility("default")；让类有一个非内联的虚函数（通常是虚析构）作为 key function，使 vtable 与 typeinfo 只在那一个 TU 里发射。详见 编译链接 · 跨 .so 的 C++ 类型。

dynamic_cast 的代价量级与替代方案

typeid 很便宜：取 vptr、读负一槽、比一次指针。dynamic_cast 则要调 __dynamic_cast，先用 offset_to_top 退回完整对象，再遍历继承图找目标基类——多继承 / 虚继承下就是一次真正的图搜索，量级几十到上百纳秒，比一次虚调用贵一到两个数量级。

替代方案适用条件与代价
加一个虚函数操作能表达成「让对象自己做」时，一次虚调用；首选
自维护类型 tag + static_cast类型集合由你掌控，一次整数比较（LLVM 的 isa<> / dyn_cast<>）
std::variant + std::visit类型编译期封闭，一次跳转表派发，且编译器强制穷尽分支
访问者模式类型稳定而操作不断增加，代价是加新类型要改所有访问者

更有用的是把判断句反过来：写出 dynamic_cast 时，先怀疑接口是不是漏了一个虚函数——「如果它是 Dog 就让它叫」通常应该是「让它叫，Dog 自己知道怎么叫」。但也不必妖魔化：插件探测可选接口、反序列化还原类型、调试断言，这些场景它正当且不在热路径上。

09

九、构造与析构顺序

构造顺序（从内到外）

构造从内到外；析构完全反过来。每一层进函数体前，vptr 被写成这一层的表——所以构造/析构里调虚函数看不到最终派生类。

构造 / 析构期间调虚函数：一个跨语言的认知陷阱

规则本身不难记，难的是它和 Java / C# 正好相反：那两门语言在分配时就确定了完整方法表，基类构造函数里调虚方法会真的派发到子类重写，于是子类读到一堆还没初始化的字段；C++ 宁可不派发，也不让你碰到尚未构造的成员。所以从 Java 转过来的人写的「基类构造函数调 init()、子类重写 init()」在 C++ 里会静默失效：那段初始化从来没执行过。

  • 间接调用一样中招：构造函数调了个非虚 helper、helper 里再调虚函数，vptr 仍停在当前层，从构造函数那一行完全看不出来。
  • 纯虚函数会直接 abort（槽里是 __cxa_pure_virtual）。看到 pure virtual method called 先怀疑构造 / 析构期间的虚调用，或对象已析构却还有回调打进来。
  • 析构期更糟：派生类析构体跑完、成员销毁之后 vptr 才改回基类，这段窗口里另一线程持裸指针发起的虚调用访问的就是已销毁的成员。

解法按推荐顺序：把可变行为作为参数或策略对象传进构造函数；两阶段初始化（构造设私有，只许工厂「构造完再 init()」）；CRTP 静态多态，它不依赖 vptr。

虚析构：不是「泄漏」，是 UB

「基类析构非 virtual 就会泄漏派生部分」这个说法太仁慈了。标准规定这种情形直接是未定义行为，后果也常比泄漏严重：C++14 起编译器默认用 sized deallocation，把 sizeof(Base) 当真实大小传给 operator delete，分配器按错误尺寸归还，堆元数据当场损坏。

但「所有基类都加虚析构」也不是免费建议：加一个虚函数就是加一个 vptr，§4.1 那张表里的每一条都会兑现。判据应该是「这个基类会不会被多态地 delete」，而不是「它有没有别的虚函数」：

基类形态析构函数怎么写
多态接口，会被 delete basePtrpublic virtual ~Base() = default;——唯一安全的写法
Mixin / CRTP 基类，从不被多态删除protected ~Base() = default;：不付 vptr 的钱，同时让「通过基类指针 delete」编译不过
只做值语义的类不要继承它——std::string 的析构就不是虚的
一个常被误解的例外：shared_ptr<Base> p = make_shared<Derived>(); 即使 ~Base 非虚也能正确析构——控制块在构造时按实际类型捕获了删除器。unique_ptr 没有这个性质。
10

十、对象切片 (Object Slicing)

将派生类对象按值赋给基类变量时

按值赋给基类：派生数据丢掉，vptr 改成基类表，多态没了。要用指针或引用。

切片为什么不报错，以及怎么在编译期挡掉

切片危险恰恰因为它完全合法：Animal a = dog; 调的是 Animal 的拷贝构造函数，Dog 能隐式转成 const Animal&，每一步都符合规则（Clang 的 -Wslicing 能报一部分，GCC 没有对应开关）。按值收参和 vector<Animal> 这两个高发场景至少还状态自洽；真正严重的是 *basePtr = someDog;——它不是切片，而是「半个赋值」：Animal::operator= 只拷贝基类字段，而拷贝赋值运算符不改写 vptr，于是对象的动态类型仍是原来那个派生类、派生字段纹丝不动，状态被撕成两半。它照样能跑、照样多态，只是行为诡异，排查时几乎没人会怀疑到那一行赋值上。

最彻底的防线是让基类抽象：有纯虚函数就无法按值实例化，上面几种写法全部编译失败。基类必须可实例化时，就把拷贝构造与拷贝赋值设为 protected：派生类之间的拷贝不受影响，外部切片通不过编译。

十一、空基类优化 (EBO)

C++ 标准要求每个对象至少占 1 字节（以保证不同对象有不同地址）

独立空对象必须 ≥ 1 字节（地址要能区分）。作为基类可以变成 0 字节，这就是 EBO。C++20 成员也能用 [[no_unique_address]] 拿到同样效果。MSVC 默认关 EBO，要 __declspec(empty_bases)。

struct Empty {};
struct Comp { Empty e; int x; };                       // 8：1B + pad 3
struct Ebo : Empty { int x; };                            // 4：空基类占 0
struct NoUa { [[no_unique_address]] Empty e; int x; };   // 4，不必继承

EBO 撑起了「零开销策略对象」这条设计原则

它看着像抠字节的小聪明，其实是标准库泛型设计成立的前提。std::vector<T> 是三个指针共 24 字节外加一个 allocator；allocator 若作为普通成员，哪怕完全无状态也要占 1 字节、再被对齐撑到 8，vector 就从 24 变成 32。unique_ptr 更极端——它必须恰好等于一个裸指针才能无痛替换裸指针，却还得带一个 deleter。

MSVC 两处都不一样：多继承下要 __declspec(empty_bases) 才启用 EBO，而标准写法 [[no_unique_address]] 被有意忽略（为不破坏既有 ABI），得写 [[msvc::no_unique_address]]。也正因为它改变布局，给已发布的库类型补这个属性等同于 ABI 破坏。

十二、POD、Standard Layout 与 Trivial 类型

C++11 将旧的 POD 概念拆分为两个正交属性：Trivial 和 Standard Layout

C++11 把旧 POD 拆成正交的两轴：Trivial（可以按字节搬）和 Standard Layout（布局可预测，offsetof 合法）。交集才是历史上的 POD。

每个概念各自授予什么权利

记住定义没用，记住「满足它之后我能做什么、谁会破坏它」才有用：

属性授予的权利谁会破坏它
is_trivially_copyable按字节搬运合法：memcpy、写进网络包 / 共享内存、std::bit_cast用户提供的拷贝 / 移动构造、赋值、析构；虚函数；虚基类。含 std::string、vector 的类一律出局
is_trivially_default_constructible不做任何事就算构造完：静态对象进 .bss、大数组省掉逐个构造用户提供的默认构造函数；默认成员初始化器（写了 int x = 0; 就不再 trivial）
is_standard_layout布局可预测：offsetof 有定义、与同样声明的 C struct 一致、union 里读「公共初始序列」不是 UB虚函数、虚基类、成员分散在不同访问级别、多层基类各自带数据

三条轴互相独立：混用 public / private 的类能 memcpy 却 offsetof 未定义，写了自定义构造函数的类能当 C 结构体用却不能按字节拷贝。所以「是不是 POD」几乎从来不是你真正想问的问题。

struct Ok  { char a; int b; };                 // standard-layout
static_assert(offsetof(Ok, b) == 4);
struct Bad { private: int x; public: int y; };  // 访问级别混用 → 不是
// offsetof(Bad, y) 未定义

C++20 怎么查：把假设钉进编译期

std::is_pod 在 C++20 已被弃用，取而代之的是按「我想做什么」直接选 trait：

我想做的事该问的 trait
memcpy / 写进网络包 / 放进共享内存 / std::bit_caststd::is_trivially_copyable_v<T>
offsetof / 与 C 共用结构体定义 / 跨语言 FFIstd::is_standard_layout_v<T>
分配后不初始化、静态对象进 .bssstd::is_trivially_default_constructible_v<T>
放进 union 而不必手工管理生命周期std::is_trivially_destructible_v<T> 及对应的拷贝 / 移动 trait

最重要的建议：凡是依赖这些性质的地方就写一条 static_assert，把原本只活在注释里的假设变成编译期检查。将来有人加了个虚析构或塞进一个 std::string，构建立刻失败，而不是等生产环境出现数据错乱。

static_assert(std::is_trivially_copyable_v<Packet>);  // 才敢 memcpy 进发送缓冲
static_assert(std::is_standard_layout_v<Packet>);     // 才敢 offsetof / 与 C 共用头文件
static_assert(sizeof(Packet) == 16);                  // 布局假设一并钉死
is_trivially_copyable_v 为 true 只说明语言层面按字节拷贝良构，不代表语义上正确。含裸指针的结构体完全满足这个 trait，memcpy 出来的两个对象却指向同一块内存——浅拷贝、双重释放，编译器一声不吭。std::string 有用户提供的拷贝构造所以被拦下了，裸指针没人替你拦。

14.1 Itanium C++ ABI — vtable 的真实布局

GCC / Clang 走 Itanium C++ ABI。槽位已经画在 §4：vptr 指向 [0]，不是表头。typeid 是 *(vptr-1)；dynamic_cast 还要 offset_to_top。GDB：info vtbl obj。两个析构槽分别是 complete 与 deleting。

14.2 多继承与 vcall Thunk（this 指针调整）

通过第二基类的指针调已被覆盖的虚函数时，那一槽指向 thunk：先把 this 减回完整对象，再跳真正的实现。热路径应避开钻石 / 多继承。

14.3 空基类优化 (EBO) 与 [[no_unique_address]]

布局与短例见 §11。这里只补工程点：allocator / deleter / compare 走 EBO 是为了「策略对象零开销」；MSVC 要显式 __declspec(empty_bases)。两个同类型空基类不能都优化成 0（地址仍要能区分）。

14.4 Trivially Copyable 与 memcpy 合法性

见 §12 的两轴图。这里只钉「谁能 memcpy」：

类别可 memcpy可 memset(0)
Trivial✅✅
TriviallyCopyable（默认构造可非 trivial）✅看值
仅 StandardLayout❌❌

含 std::string 的 struct 拷字节 = 共享堆缓冲，析构 double-free。

14.5 SBO / SSO — 标准库的小对象优化

小值塞进对象自己，避免堆分配。阈值因库而异，别写死。

类型优化常见阈值
std::stringSSOlibstdc++ 15B / libc++ 22B / MSVC 15B
std::functionSBO约 16–24B，超了就堆 + 虚调用
std::anySBO约 1–2 个指针
std::variant按最大 alternative无堆

lambda 捕获过大塞进 std::function，每次拷贝都是 new。热路径用模板或 function_ref。

14.6 位域 (Bit-field) 与 Flexible Array Member

位域把多个字段塞进同一个字；位序 implementation-defined，大端/小端还可能排反。解析网络头用移位掩码，不要 reinterpret_cast 成位域结构体。

14.7 std::launder 与对象重启

同一块 storage 上 placement new 之后，编译器仍可能按旧对象身份做常量折叠（const / 引用 / 旧 vptr）。std::launder 只是切断这个假设，不能凭空造对象。新指针本身已是新身份，不必 launder。optional / variant / any 内部都在用。

状态能做什么
已分配未构造搬字节、取地址
构造中 / 析构中this 可用；虚调用走当前层表
存活成员、方法、多态
已销毁、storage 还在placement new；不能再读成员
storage 已释放什么都不能
launder 不是 reinterpret_cast。内存里没有那个类型的活对象，launder 之后仍是 UB。

14.8 对象生命周期与 reuse of storage

规则在上一张图里。写无锁结构 / 对象池 / union-variant 时，默认用新指针；只有「从裸字节重新解释旧名字」才请 launder。

14.9 inline namespace — ABI 版本演化的关键武器

inline namespace：对用户看起来在父命名空间里，mangled name 却带着版本前缀。GCC 5 的 Dual ABI 靠它让 COW string 和 SSO string 同在 libstdc++.so.6 里，-D_GLIBCXX_USE_CXX11_ABI 决定你链哪一套。

用法做什么判据
版本通道inline namespace v2 + 留下 v1nm 里是 myapi::v2::init，不是 myapi::init
Dual ABI两套 std::string 共存mangled 不同，不会「链接上了运行崩」

两个 TU 不能把同一名字放进不同 inline namespace（ODR）。特化要进正确那一层。extern "C++" 跨不过 inline 边界。公共库第一天就规划 v1，五年后加 v2 并把 v1 的 inline 拿掉。

14.10 高频面试 Q&A

点击每道题展开参考答案（先自测，再对照）。

  1. 基础sizeof 空类为什么是 1 不是 0？

    C++ 要求不同对象有不同地址。如果 sizeof(Empty) == 0，数组 Empty a[10] 里所有元素地址相同、指针算术失效。作为基类时不受此限制，故有 EBO。

  2. 中级vptr 放对象首部还是尾部？为什么？

    放首部（Itanium ABI）。原因：

    • 单继承时 Base* 和 Derived* 指同一地址——指针零调整，性能好
    • 派生类增加成员只影响尾部，不改 vptr 位置
    • 但多继承下，非 primary base 的 vptr 必然在对象中间
  3. 基础为什么构造函数中调虚函数不触发多态？

    每层构造函数执行时，vptr 正被设置为该层自己的 vtable。若基类构造中调虚函数，此时派生类对象的派生部分还没构造，vptr 指向基类 vtable，调用的是基类版本。析构同理（反方向）。
    推论：永远不要在构造/析构中调虚函数，改用两阶段初始化。

  4. 中级虚函数有多少运行时开销？现代 CPU 能优化吗？
    • 每次调用：一次内存读（vptr）+ 一次内存读（vtable 项）+ 一次间接跳转
    • 间接跳转对 CPU 分支预测不友好，但现代 CPU 的 indirect branch predictor 对稳定类型能预测准确
    • 编译器的去虚化 (devirtualization) 可消除：final 类/方法、LTO 能看到唯一派生、constexpr 等场景

    实测：热路径 virtual 调用比直接调用慢 10-30%，冷路径几乎看不出。

  5. 中级final 关键字对性能有影响吗？

    ✅ 有。final 告诉编译器该类/方法不会再被继承/覆盖，编译器可以静态解析虚调用为直接调用（devirtualization），避免 vtable 查找。LTO 下效果更好。

    class Impl final : public Interface { ... };
Interface* p = new Impl;
p->foo();   // 编译器可直接调 Impl::foo，无 vtable
  6. 基础为什么基类析构函数一般要 virtual？什么时候可以不 virtual？

    通过基类指针 delete 派生对象时，若 ~Base 非 virtual 则只调 Base 析构 → 派生部分资源泄漏。
    可以不 virtual 的情况：

    • 基类设计为永不被 delete by pointer（如 CRTP 静态多态的基类）
    • 通过 protected 析构 + 禁止派生类 delete 的方式控制
    • 标准库的 std::enable_shared_from_this 等
  7. 基础struct 和 class 有区别吗？

    语法层面仅 2 点：① 默认访问权限（struct=public, class=private）；② 默认继承权限同上。
    内存布局、虚函数、模板参数推导等完全相同。惯例：纯数据用 struct，有不变式 / 封装的用 class。

  8. 中级如何查看一个类的真实内存布局？
    • Clang: clang -Xclang -fdump-record-layouts -c foo.cpp — 最友好
    • GCC: g++ -fdump-lang-class foo.cpp 产出 .class 文件
    • MSVC: /d1 reportSingleClassLayoutClassName
    • pahole（依赖 DWARF）：pahole -C MyClass a.out，直接显示 offset、hole、padding
    • GDB：ptype /o MyClass（新版支持）或 print &obj.member - (char*)&obj
  9. 中级为什么 std::vector<bool> 被视为设计失误？

    标准规定它为节省空间特化为位打包——每个 bool 占 1 bit。但带来：

    • operator[] 返回代理对象而非 bool&，auto& b = v[0]; 不是你想的
    • 不能取 &v[0] 作为 bool*
    • 非 thread-safe：并发修改相邻 bool 会冲突写同一 byte（word tearing）
    • 违反 Container concept

    替代：std::vector<char>、std::bitset、boost::dynamic_bitset。

  10. 高级什么是 layout-compatible？有什么用？

    两个 struct 如果成员序列的类型一一对应兼容，它们是 layout-compatible。可以通过 union 共同访问或 reinterpret_cast 合法转换——C++ 标准特别允许此时读共同初始序列不是 UB。

    struct Base   { int tag; };
struct Msg1   { int tag; int payload; };
struct Msg2   { int tag; double payload; };
// 通过读 tag 决定用哪个类型 — C 风格 tagged union
union U { Msg1 m1; Msg2 m2; } u;
if (u.m1.tag == 0) ...   // 合法：Msg1 和 Msg2 的初始公共序列是 { int tag; }
