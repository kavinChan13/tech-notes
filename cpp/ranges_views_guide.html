Ranges 与 views 深入

Ranges 的教学材料几乎都停在「v | filter | transform 好漂亮」这一层。但真正决定你能不能在生产代码里用它的，是下面三件事：view 概念把复杂度写进了语义要求（于是 owning_view 要等两年才补上）；引用语义让一半的悬垂问题被 dangling 挡成编译错误、另一半照旧是 UB；惰性求值把一次遍历的代价重新分配了——有时更快，有时把同一个函数算了两遍。

01

概念层次：range 之上的那层约束

「什么东西能当 view」这个问题的答案，编译器其实检查不了

Ranges 库表面上是一堆 views::xxx，骨架却是四五个互相叠加的 concept。搞不清这几个 concept 的关系，后面所有的坑都会显得像是随机的：为什么这个能进管道那个不能、为什么 ranges::find 有时返回不了迭代器、为什么 const auto& 接一个 filter 就编译不过。

把容器想成一本相册，view 就是一副眼镜。眼镜不复制任何照片，只改变你翻这本相册的方式（跳过没对焦的、给每张加个滤镜）。所以眼镜必须轻——随手能递给别人、能装进口袋、能戴两副叠着看。一件「戴上要花十分钟、摘下还得再花十分钟」的东西，无论效果多好都不是眼镜。view 概念里那条复杂度要求，就是在给「轻」下一个可执行的定义。

1.1 range 只要求有 begin 和 end

range：std::ranges::range<T> 只要求 ranges::begin(t) 和 ranges::end(t) 合法，且前者返回迭代器、后者返回一个能与之比较的 sentinel。注意 end 返回的不必是同类型迭代器——这一条松动是 Ranges 相对旧 STL 最大的结构性改动，它让「以 '\0' 结尾」「以谓词结尾」这类无界序列第一次成为一等公民。

在 range 之上，标准又叠了几层。它们不是继承关系，而是各自加一条独立的要求：

concept加了什么典型满足者典型不满足者
range有 begin/end所有容器、C 数组、span裸指针（没有 end）
sized_rangesize() 是常数时间vector · span · iota_view（有界）forward_list · filter_view
common_rangebegin 与 end 同类型所有旧 STL 容器take_view 套无界 range
borrowed_range迭代器可以活得比 range 久string_view · span · subrange · iota_viewvector（右值）· filter_view · transform_view
view移动 / 析构的复杂度约束ref_view · filter_view · owning_viewvector · string（拷贝是 O(n)）

1.2 view 的那条复杂度约束

view：view<T> 的语法部分只有三项——range<T>、movable<T>、enable_view<T>。真正的门槛在语义要求：移动构造必须是 O(1)；如果可拷贝，拷贝构造也必须是 O(1)；从一个含 M 个元素的 view 复制/移动出 N 个对象，这 N 个对象的析构总代价是 O(N+M)。

为什么要把复杂度写进概念？因为管道的每一步都在按值传递并存储整条链：v | filter(p) | transform(f) 的结果是 transform_view<filter_view<ref_view<vector<int>>, P>, F>，外层持有内层的一份副本。如果某一层的拷贝是 O(n)，那么「拼一条管道」这个动作本身就变成了 O(n) —— 而它在源码里长得像零成本的语法糖。这条约束的存在，正是为了让「管道拼装是免费的」这句话在标准里有依据，而不只是一个惯例。

但编译器验证不了它。view<T> 里的 enable_view<T> 是一个变量模板，默认值是「T 是否派生自 view_base 或 view_interface」。也就是说，「我是一个 view」是作者宣称的，不是编译器测出来的。你完全可以让一个每次拷贝都要 memcpy 一兆内存的类型满足 view，编译器一句话都不会说，只是所有依赖「管道拼装免费」的代码都会静默变慢。这是整个 Ranges 设计里最需要靠自觉的一处。

顺带解释了一个很多人碰到过的历史现象：C++20 刚发布时 view 还要求 semiregular（可默认构造 + 可拷贝），于是所有 view 都被迫要有默认构造函数，捕获了引用的 lambda 就没法直接塞进 views::filter。后来 P2325 把要求降到 movable 并作为 C++20 的缺陷报告追溯生效——「view 必须能默认构造」从一开始就是个错误的要求，它是为了满足旧 STL 的 Iterator 传统而不是为了满足任何真实需要。

1.3 owning_view 为什么迟到

现在回头看那条复杂度要求，会发现它顺手禁掉了一整类东西：一个 view 不能拥有它的元素。因为析构 n 个元素的代价一定随 n 增长，而最初的措辞要求析构与元素个数无关。

后果是 C++20 刚定稿时，get_vector() | views::filter(pred) 这行代码根本编译不过——右值容器既不是 view（拷贝 O(n)），又不是 borrowed_range，于是不满足 viewable_range。这是一个刻意的编译错误：宁可拒绝，也不要生成一个指向已死临时对象的 view。

P2415（What is a view?）改的正是这一句：把析构那条要求松成「从一个含 M 个元素的 view 复制/移动出 N 个对象，这 N 个对象的析构总代价是 O(N+M)」。这句话读起来绕，意思其实很直白——允许有一个 view 真正拥有那 M 个元素，只要它的副本不各自再拥有一份。owning_view 于是成立：它 move-only（删掉了拷贝），所以永远只有一份所有权。

这套「概念 + 语义要求」的写法本身是 C++20 concepts 的典型用法。concepts 的语法、约束求解、以及它相比 SFINAE 改善了什么，见 模板与元编程 §9.2（SFINAE 的原始形态在 §9.1）。常用 views 的一览表与投影（projection）的用法见 STL 算法 · slide 11，本文不再重复。
02

引用语义与 dangling

一半的悬垂被挡成了编译错误，另一半照旧是 UB —— 分界线在哪很值得记住

「views 有悬垂风险」这句话流传很广，但流传的版本大多是错的。最常见的一个说法是「views::filter(get_vector(), pred) 很危险」——它在 C++20 的最初版本里确实有问题（编译不过），而 P2415 之后这一行反而是安全的：临时容器被移进了 owning_view，元素的所有权跟着视图走。

所以真正需要记住的不是某一行代码，而是那条分界线：视图究竟是「引用了别人的元素」还是「自己拥有元素」。前者才有悬垂风险，而它的三种典型形状如下。

2.1 三种持有方式，三种结局

#include <ranges>
#include <vector>
namespace rg = std::ranges;

std::vector<int> make_data();
constexpr auto pos = [](int x){ return x > 0; };

// ① 安全：临时容器被 move 进 owning_view，元素归视图所有
auto a = make_data() | std::views::filter(pos);
//   → filter_view<owning_view<std::vector<int>>, decltype(pos)>
static_assert(!std::copyable<decltype(a)>);        // 代价：move-only

// ② 悬垂：形参是引用 ⇒ ref_view，而形参可能绑在临时对象上
auto positives(const std::vector<int>& v) {
    return v | std::views::filter(pos);            // ref_view<const vector>
}
for (int x : positives(make_data())) { /* ☠️ 临时容器已析构，且无任何警告 */ }

// ③ 编译错误：vector 不是 borrowed_range，返回类型退化成 dangling
auto it = rg::find(make_data(), 42);
static_assert(std::same_as<decltype(it), rg::dangling>);
// *it;   // error: 'std::ranges::dangling' 没有 operator*

第 ② 种是实际项目里唯一真正常见的形状，而且它不是 Ranges 独有的问题——它和「返回指向局部对象的引用」是同一个 bug，只是被一层视图类型包住之后更难看出来。防御手段也和那个老问题一样：接受 range 的函数不要返回视图，要么返回容器，要么让调用方自己拼管道；实在要返回视图，就把参数改成按值收 R&& 再 views::all(std::forward<R>(r))，让右值走 owning_view 那一路。

2.2 borrowed_range 到底在断言什么

borrowed_range：range<T> && (T 是左值引用 || enable_borrowed_range<remove_cvref_t<T>>)。语义上它断言一件事——从这个 range 取出的迭代器，其有效性不依赖 range 对象本身是否还活着。左值自动满足（对象在调用方手里活着）；右值必须由类型作者显式特化 enable_borrowed_range 来开启。

判断某个类型该不该开这个开关，只需要问一句：它的迭代器里有没有指回视图对象自己的指针？

类型迭代器里存了什么borrowed?为什么
span · string_view · subrange指向外部缓冲的裸指针✅视图本身只是一对指针，析构它不影响缓冲
iota_view · empty_view一个计数值 / 什么都没有✅元素是算出来的，不存在「被谁持有」
ref_view<C>底层容器的迭代器✅迭代器指向容器，与 ref_view 无关
take_view · drop_view · reverse_view底层迭代器（+ 计数）条件成立底层 borrowed 就 borrowed，没有额外状态
filter_view底层迭代器 + 指回视图的指针❌递进时要读谓词，谓词存在视图里
transform_view底层迭代器 + 指回视图的指针❌解引用时要读函数对象，函数存在视图里
owning_view<C>底层容器的迭代器❌容器就在视图内部，视图死了元素也没了

这张表解释了一个让人意外的现象：filter_view 和 transform_view 明明可能只是引用了别人的元素，却不是 borrowed_range。原因不在元素上，在谓词/函数对象上——它们存在视图里，而迭代器必须能访问到它们，所以迭代器持有一个 parent_ 指针。视图一死，指针就悬垂，跟元素在哪毫无关系。

03

惰性求值的真实代价

惰性不是「免费」，是「把代价换了一种分配方式」

惰性求值的宣传语是「不产生中间容器」，这是真的。但它同时带来了三件很少被提起的事：begin() 可能不是 O(1)；同一个元素可能被算多次；以及为了让前两件事不太糟，标准往视图里塞了缓存，而缓存又带来了自己的怪毛病。

3.1 filter 的 begin() 是 O(n)

range 概念要求 begin() 是摊还常数时间。filter_view 天然做不到：第一个满足谓词的元素可能在最后，也可能压根不存在，找到它就是一次 find_if。标准的解法是缓存——第一次 begin() 扫一遍并把结果存进视图，后续调用直接返回。

左边那个现象在实际编码里出现频率极高：习惯性地写 const auto& r = v | views::filter(p);，然后 for (int x : r) 编译失败，报错还在 <ranges> 深处。原因就是 begin() 要改缓存所以不能是 const，于是 const filter_view& 不满足 range。

可以从中提炼出一条可推广的判据：凡是 begin() 需要先扫描再缓存的视图，都没有 const begin()。属于这一类的有 filter_view、drop_while_view、split_view、chunk_by_view，以及底层不是 common_range 时的 reverse_view。反过来 transform_view、take_view、elements_view 都是可 const 迭代的。

3.2 每次解引用都重算一遍

视图不缓存元素值。transform_view 的 operator* 就是 invoke(f, *base_it)，每次解引用都真的调一次 f。这在单趟遍历里是想要的行为（这才叫惰性），但只要谁在你背后多解引用了一次，代价就翻倍。

int calls = 0;
auto f = [&calls](int x){ ++calls; return x * x; };
std::vector<int> v{1,2,3,4,5,6,7,8};

// ❌ 先变换再筛：filter 递进时解引用 transform（调 f），用户再解引用一次（又调 f）
for (int y : v | std::views::transform(f)
               | std::views::filter([](int y){ return y % 2 == 0; }))
    (void)y;
// calls == 12   —— 8 次扫描 + 4 个通过元素各再算一遍

// ✅ 先筛再变换：谓词读原始值，f 只在输出时算一次
calls = 0;
for (int y : v | std::views::filter([](int x){ return x % 2 == 0; })
               | std::views::transform(f))
    (void)y;
// calls == 4

这就是为什么视图链里的函数对象必须是纯函数。带副作用的 transform（打日志、递增计数器、往队列里塞东西）在管道里的行为无法预测：调用次数取决于下游有几个 filter、你遍历了几趟、有没有算法在背后多解引用一次。ranges::max_element 就会对同一位置解引用多次；写成 ranges::max_element(v | views::transform(expensive))，那个 expensive 会被调用远超 n 次。

3.3 什么时候惰性反而更慢

场景惰性的表现该怎么办
要遍历多趟每趟把整条链重算一遍先 ranges::to<vector>() 落地，再多趟用
变换函数昂贵（解压、查表、算哈希）调用次数不可控，可能远超元素数落地成容器；或把结果 memo 在容器里
下游需要随机访问 / 排序类别退化后压根编译不过（§5）落地；或改成对原容器排序
元素很小、管道很长（≥4 段）调试构建里每个元素几十次函数调用合并成一次 transform；或写循环
filter 命中率极低每次 begin() 都可能是完整 O(n)注意别反复重建视图（缓存不随拷贝走）
数据本来就在内存里、只遍历一趟这是惰性真正赢的场景放心用，中间容器省下的分配是纯赚

把最后一行和前面五行放在一起看，结论就清楚了：惰性的收益是「省掉中间容器的分配与拷贝」，代价是「元素的求值次数不再由你直接掌握」。数据量大、只走一趟、函数便宜 → 收益压倒代价；反过来任何一项不成立，就要具体算一算。

协程 generator 是另一种惰性序列，它和 views 可以互通（generator | views::take(10)），代价结构却完全不同——generator 的每次 ++ 是一次协程恢复，有实打实的间接跳转，但它天然只能单趟、也天然不会重复求值。对照见 协程深入 §16.3。
04

管道是怎么拼起来的

整套机制只有两条规则，比看起来简单得多

4.1 adaptor 对象与 closure 对象

views::filter 这个名字下其实藏着两种可调用对象，区别只在于「参数够不够」：

range adaptor object：参数齐全时直接产出视图（views::filter(v, pred) → filter_view）。
range adaptor closure object：只给了除 range 之外的参数时，返回一个「等着 range」的可调用对象（views::filter(pred)）。operator| 只认识后者。

views::all、views::reverse、views::join 这类不需要额外参数的，本身就是 closure；views::filter、views::take、views::transform 则是「调用一次生成 closure」的工厂。理解这个二分之后，v | views::take(3) 就不再神秘：views::take(3) 先产出一个 closure，然后 | 把 v 喂给它。

4.2 operator| 只有两条规则

4.3 自己写一个 adaptor

C++20 有一个尴尬的空缺：标准描述了 | 对标准 adaptor 的行为，却没提供任何让用户类型接入 | 的机制。于是各家库（range-v3、libstdc++ 的内部实现）各写一套，用户想自定义就只能抄实现细节。C++23 的 std::ranges::range_adaptor_closure<D> 补上了这一块：CRTP 继承它，就自动获得 §4.2 的两条规则。

下面是一个完整骨架，功能是「跳过相邻的重复元素」。三个部件缺一不可：视图本体（继承 view_interface）、CTAD 推导指引（把容器包成 ref_view 或 owning_view）、closure 对象（接入 |）。

namespace rg = std::ranges;

// ① 视图本体。继承 view_interface 后，empty() / front() / operator bool /
//    （在满足条件时）size() / operator[] 都由基类从 begin()、end() 推导出来，
//    同时 enable_view 自动为 true —— 这是「宣称我是 view」的标准方式。
template<rg::forward_range V> requires rg::view<V>
class dedup_view : public rg::view_interface<dedup_view<V>> {
    V base_{};
public:
    dedup_view() requires std::default_initializable<V> = default;
    constexpr explicit dedup_view(V b) : base_(std::move(b)) {}

    class iterator {
        rg::iterator_t<V> cur_{}, end_{};
    public:
        using value_type      = rg::range_value_t<V>;
        using difference_type = rg::range_difference_t<V>;
        iterator() = default;
        constexpr iterator(rg::iterator_t<V> c, rg::iterator_t<V> e)
            : cur_(std::move(c)), end_(std::move(e)) {}
        constexpr decltype(auto) operator*() const { return *cur_; }
        // 前进要跳过重复 ⇒ 不是 O(1) ⇒ 这个视图最高只能是 forward（§5）
        constexpr iterator& operator++() {
            auto prev = cur_++;
            while (cur_ != end_ && *cur_ == *prev) ++cur_;
            return *this;
        }
        constexpr bool operator==(std::default_sentinel_t) const { return cur_ == end_; }
        // …后置 ++、operator==(iterator) 略
    };

    constexpr iterator begin() { return {rg::begin(base_), rg::end(base_)}; }
    constexpr std::default_sentinel_t end() const { return {}; }
};

// ② CTAD：左值容器 → ref_view，右值容器 → owning_view，已是 view → 原样（§1.3）
template<class R> dedup_view(R&&) -> dedup_view<std::views::all_t<R&&>>;

// ③ closure 对象：继承 range_adaptor_closure 即获得 operator| 的两条规则
struct dedup_fn : rg::range_adaptor_closure<dedup_fn> {
    template<rg::viewable_range R>
    constexpr auto operator()(R&& r) const { return dedup_view{std::forward<R>(r)}; }
};
inline constexpr dedup_fn dedup{};

// 用起来和标准 adaptor 没有区别，也能被规则二合成
auto r = v | std::views::filter(odd) | dedup | std::views::take(3);

迭代器类别的退化

管道每加一段，能力就可能掉一级，而算法约束是按级别写的

5.1 filter 为什么到不了 random_access

random_access_iterator 的语义要求里有一条：it + n 和 it2 - it1 必须是常数时间。对 filter_view 来说，「第 n 个满足谓词的元素在哪」除了从头数没有别的办法，it + n 注定是 O(n)。所以这不是实现偷懒，是「诚实地不宣称做不到的事」——如果 filter_view 谎称 random_access，所有基于「随机访问 ⇒ 可以做二分」的算法都会静默退化成 O(n) 甚至 O(n log n) 的扫描。

5.2 两套类别同时存在

还有一层容易混淆的东西：Ranges 的迭代器同时带着两个类别标签。

iterator_conceptiterator_category
服务对象C++20 的 ranges::* 算法与 concept旧 std::* 算法，通过 iterator_traits
判据看操作是否可用、复杂度是否达标额外要求 operator* 返回真引用
transform 返回 prvalue 时可以是 random_access退化成 input_iterator_tag

第三行是个真实会咬人的差异：一个返回值（而非引用）的 transform_view，在 ranges:: 算法眼里是随机访问的，在 std:: 算法眼里只是输入迭代器。所以 std::sort(sq.begin(), sq.end()) 和 ranges::sort(sq) 会因为完全不同的原因失败——前者是「类别不够」，后者是「元素不可写」。这也是「不要混用 std:: 和 ranges:: 算法」的一个具体理由。

5.3 这对算法意味着什么

namespace rg = std::ranges;
std::vector<int> v{5,3,8,1,9,2};
auto odd = v | std::views::filter([](int x){ return x % 2; });

static_assert(rg::bidirectional_range<decltype(odd)>);
static_assert(!rg::random_access_range<decltype(odd)>);

// rg::sort(odd);              // ❌ 约束不满足：sort 要 random_access_range
// rg::nth_element(odd, ...);  // ❌ 同理
// rg::shuffle(odd, gen);      // ❌ 同理

// 三条出路
rg::sort(v);                                       // 甲：先排容器再筛，顺序换一下就行
auto tmp = odd | rg::to<std::vector>(); rg::sort(tmp);   // 乙：C++23 落地后再排
auto mid = rg::stable_partition(v, [](int x){ return x % 2; });  // 丙：换个只要双向的算法

// 另一种退化：transform 返回 prvalue ⇒ 元素不可写
auto sq = v | std::views::transform([](int x){ return x * x; });
// rg::sort(sq);   // ❌ 这次不是类别问题，是 sortable 要求元素可交换

甲式往往被忽略，但它常常是最好的答案：要排序就排拥有元素的那个容器，视图只负责「怎么看」。乙式的成本要算清楚——它把「省掉中间容器」这个惰性最大的收益直接还回去了，所以只在确实需要一个独立结果时才用。丙式最考验对算法库的熟悉度：partition、rotate、unique 这些只要求双向甚至前向的算法，往往能替掉一次排序。

最后一段的失败是另一回事。ranges::sort 要求 sortable，其中包含「元素可交换」；而 transform_view 的 operator* 返回的是一个临时值，交换两个临时值毫无意义，所以约束不成立。这条规则可以推广：所有计算出元素的视图都是只读的，包括 transform、iota、repeat、zip_transform。反过来 filter、take、reverse、elements 转发的是底层的真引用，通过它们写回原容器是合法的。

工程代价

6.1 编译时间与报错长度

<ranges> 是标准库里最重的头文件之一：它拖进 <concepts>、<iterator>、<compare>，自己又定义了几十个类模板和成打的 concept。单纯 #include <ranges> 在一个空 TU 里就有可观的固定开销，而每写一段管道就要实例化一整串嵌套类型和它们的迭代器。

更麻烦的是报错。Concepts 确实改善了错误信息的开头——第一行会明确告诉你「约束 random_access_range<...> 不满足」，这比旧 STL 那种从模板深处爆出来的十几屏替换失败好得多。但紧接着打印的类型名是灾难级的：一条四段管道的完整类型能有几百个字符，而报错里往往要重复它五六次。

症状手段
不知道哪一段掉了级别逐段 static_assert(rg::random_access_range<decltype(r)>)，二分定位
报错刷屏GCC 用 -fconcepts-diagnostics-depth=2；Clang 的约束诊断通常更短，可以拿它复现一遍
不知道时间花在哪Clang -ftime-trace / MSVC /d1reportTime，看是不是某个 TU 的管道在吃编译时间
头文件扩散管道写在 .cpp 里，接口层暴露 span / vector 而不是视图类型
const auto& 接视图编译失败见 §3.1：改成 auto 或 auto&&

「接口层不暴露视图类型」这一条值得单独强调。视图类型名进了函数签名，就意味着它进了 mangled 符号名、进了每个包含该头文件的 TU、也进了链接器要处理的符号表。把管道当实现细节、在边界上落地成 span 或容器，是控制这笔账最有效的一招——顺带也解决了 §2.1 的悬垂问题。

C++23 的补充

补的不是花样，是 C++20 用起来最别扭的那几处

7.1 ranges::to：链条的终点

C++20 的 Ranges 有一个非常显眼的缺口：没有标准办法把视图变回容器。老写法 std::vector<int> out(r.begin(), r.end()) 对视图常常不成立，因为许多视图不是 common_range（begin 与 end 类型不同），而容器的迭代器对构造函数要求两者同类型。于是所有人都在自己项目里手写一个 to_vector。

std::ranges::to 把这件事标准化了，而且做了三件手写版本通常会漏掉的事：能问长度就先 reserve；支持递归转换（range<range<char>> → vector<string>）；能通过尾随参数转发给容器的构造函数（分配器、比较器）。它既能当函数调 rg::to<std::vector>(r)，也是一个 closure，可以写在管道末尾 r | rg::to<std::vector>()。

7.2 zip / enumerate / chunk / slide

namespace rg = std::ranges;
namespace rv = std::views;

std::vector<std::string> names{"ada","bob","cy"};
std::vector<int>         ages {36, 41, 29};

// zip：yield tuple<string&, int&>，长度取两者较短
for (auto&& [n, a] : rv::zip(names, ages)) std::print("{}={}\n", n, a);

// enumerate：i 是有符号的 difference_type，n 仍是原容器元素的引用
for (auto&& [i, n] : names | rv::enumerate) std::print("#{} {}\n", i, n);

// chunk vs slide：同样的输入、同样的 3，结果个数不同
auto blocks  = rv::iota(1, 8) | rv::chunk(3);   // [1,2,3] [4,5,6] [7]      → 3 块
auto windows = rv::iota(1, 8) | rv::slide(3);   // [1,2,3] [2,3,4] … [5,6,7] → 5 个窗口

// join_with：ranges 版的 string join，惰性，不建中间字符串
auto line = names | rv::join_with(',') | rg::to<std::string>();   // "ada,bob,cy"

7.3 join_with 与其余

views::join_with(sep) 补的是 join 的一个很常见的变体：把嵌套序列摊平的同时插入分隔符。它最实际的用途就是 string join——一个每种语言都有、C++ 却一直要么手写要么依赖第三方的操作。而且它是惰性的，直接接 rg::to<std::string>() 时只有一次分配。

面试题集（12 道）

按难度分三档，先自测再对照

点击每道题展开参考答案（先自测，再对照）。

8.1 基础（必答）

  1. 基础range 和 view 的区别是什么？

    range 只要求「有 begin() 和 end()」，end() 甚至可以返回一个不同类型的 sentinel。容器、C 数组、span 全是 range。

    view 是 range 的一个子集，额外要求 movable、enable_view，以及一组复杂度语义要求：移动构造 O(1)，可拷贝时拷贝构造也 O(1)。这条要求存在的理由是管道的每一层都按值持有下一层，如果某层拷贝是 O(n)，「拼装管道」这个看起来免费的动作就变成了 O(n)。

  2. 基础const auto& r = v | views::filter(p); 之后 for (int x : r) 编译失败，为什么？

    filter_view::begin() 需要扫描到第一个满足谓词的元素，并把结果缓存在视图内部（否则 begin() 无法满足 range 要求的摊还常数时间）。缓存是可变状态，所以 begin() 不能是 const 成员——于是 const filter_view& 压根不满足 range。

    可推广的判据：凡是 begin() 要先扫描再缓存的视图都没有 const begin()，包括 filter_view、drop_while_view、split_view、chunk_by_view。写 auto 或 auto&& 即可。

  3. 基础惰性求值到底省了什么？什么时候它不省反赔？

    省的是中间容器的分配与拷贝：v | filter | transform 全程不产生任何临时 vector，元素在被解引用的那一刻才算出来。数据量大、只遍历一趟时，这是纯赚。

    不省反赔有三种典型情形：要遍历多趟（每趟把整条链重算）；变换函数昂贵（调用次数不由你掌握，见 §3.2）；下游需要随机访问或排序（类别退化后压根编译不过）。这几种都该先 ranges::to 落地。

  4. 基础views::transform 产出的视图能不能写回原容器？views::filter 呢？

    transform 不能。它的 operator* 返回的是 invoke(f, *base_it)——一个计算出来的临时值，往它赋值没有意义，所以 ranges::sort 之类要求元素可交换的算法会直接约束不满足。

    filter 能。它只是转发底层的真引用，for (int& x : v | views::filter(p)) x = 0; 是合法的，会改到 v。

    一般规律：「计算出元素」的视图都是只读的（transform、iota、repeat、zip_transform）；「转发引用」的视图可写（filter、take、drop、reverse、elements）。

8.2 中级（区分熟练度）

  1. 中级ranges::find(get_vector(), 42) 返回什么？为什么这么设计？

    返回 std::ranges::dangling——一个空结构体，没有 operator*、没有 operator->、没有 ++。机制是每个返回迭代器的 ranges 算法都用 borrowed_iterator_t<R> 做返回类型：borrowed_range<R> 成立就是真迭代器，否则退化成 dangling。vector 的右值不是 borrowed_range，于是走后一路。

    设计意图是把运行期 UB 降级成编译期诊断：临时容器在语句末就析构了，返回真迭代器的话使用它就是 use-after-free，而这类 bug 往往在生产环境才暴露。现在失败点被搬回产生它的那一行，错误消息是「dangling 没有 operator*」。

    局限也要说清：dangling 只在单个表达式内看得见「实参是右值」。跨过函数边界之后，被调用方拿到的只是 const&，无从知道上游绑的是变量还是临时对象。

  2. 中级filter_view 明明可能只是引用别人的元素，为什么不是 borrowed_range？

    问题不在元素上，在谓词上。filter_view::iterator 递进时要调用谓词，而谓词存在视图对象里，所以迭代器必须持有一个指回视图的 parent_ 指针。视图一析构，这个指针就悬垂了——跟元素在哪毫无关系。transform_view 同理（解引用要读函数对象）。

    判据可以推广：迭代器里有没有指回视图自己的指针。没有的（ref_view、take_view、drop_view、reverse_view）可以是 borrowed；有的一定不行。owning_view 不是 borrowed 则是另一个理由——容器就在它内部。

  3. 中级v | transform(f) | filter(p) 和 v | filter(p') | transform(f) 在性能上有什么区别？

    前者会重复求值。filter 为了找到下一个满足元素，必须先解引用 transform（调一次 f）让谓词看到变换后的值；用户随后再解引用一次，又调一次 f。所以每个通过的元素 f 被调 2 次、每个被筛掉的调 1 次。8 个元素 4 个通过 → 12 次。

    后者只调 4 次：谓词读的是原始元素，f 只在用户解引用时算一次，而且只作用在通过筛选的元素上。

    所以通用规则是能先筛就先筛。只有当谓词必须看变换后的值时才被迫用前一种顺序；此时的解法是把 f 拆成「便宜的键 + 昂贵的主体」，让 filter 只依赖便宜的那半。这也是为什么视图链里的函数对象必须是纯函数——带副作用的话，调用次数取决于下游结构，无法预测。

  4. 中级ranges::sort(v | views::filter(pred)) 为什么编译不过？有哪几种解法？

    ranges::sort 要求 random_access_range，而 filter_view 最高只能到 bidirectional：「第 n 个满足谓词的元素在哪」除了从头数没有办法，it + n 注定是 O(n)，宣称 random_access 就是撒谎。

    三条解法：甲——先 ranges::sort(v) 再筛，把顺序换一下（通常是最好的答案，排序本来就该作用在拥有元素的容器上）；乙——ranges::to<vector>() 落地后再排（但这把惰性最大的收益还回去了）；丙——换成只要求双向/前向的算法，stable_partition、rotate、unique 常能替掉一次排序。

8.3 高级（体现深度）

  1. 高级owning_view 为什么不是 C++20 一开始就有的？它的加入改了什么规则？

    因为最初的 view 语义要求把析构的复杂度也写成了与元素个数无关，这直接禁掉了「视图拥有元素」这件事——析构 n 个元素的代价一定随 n 增长。后果是 get_vector() | views::filter(p) 在当时编译不过：右值容器既不是 view（拷贝 O(n)），又不是 borrowed_range，不满足 viewable_range。这是刻意的：宁可拒绝，也不要造出指向已死临时对象的视图。

    P2415（What is a view?）把那条改成「从一个含 M 个元素的 view 复制/移动出 N 个对象，这 N 个对象的析构总代价是 O(N+M)」。意思是允许有一份真正的所有权，只要副本不各自再拥有一份。owning_view 因此删掉了拷贝构造、只保留移动。

    连带的影响有两个：viewable_range 放开了可移动的右值容器（但显式排除右值 initializer_list，因为它的底层数组本身是临时对象，包起来照样悬垂）；以及以 owning_view 开头的整条管道都变成 move-only，塞不进要求可拷贝的接口。

  2. 高级「view 的操作必须是 O(1)」这条要求，编译器是怎么检查的？

    不检查。这是本题的全部要点。view<T> 的语法部分只有 range<T> && movable<T> && enable_view<T>，而 enable_view<T> 默认就是「T 是否派生自 view_base 或 view_interface」。也就是说「我是一个 view」是作者宣称的，不是编译器测出来的。

    你完全可以让一个每次拷贝都 memcpy 一兆内存的类型满足 view，编译器一句话都不会说，只是所有依赖「管道拼装免费」的代码都会静默变慢——而且慢在一个语法上看不出成本的位置。

    这是标准库里「语义要求」这一类条款的典型形态（std::less 要求严格弱序、hash 要求相等即同值也是同一类）：违反它不是 ill-formed，而是把契约打破后的行为交给你自己承担。自定义视图时，这条要靠 code review 而不是编译器。

  3. 高级要给团队写一个自定义 range adaptor，最小需要哪些部件？各自不写会怎样？

    三个部件（见 §4.3）。视图本体继承 view_interface<D>：这既让 enable_view 自动为真、从而满足 view 能出现在管道中间，又通过 CRTP 从你的 begin()/end() 白送 empty()/front()/operator bool/条件性的 size() 与 operator[]——全部零运行期成本，没有虚函数。

    CTAD 推导指引 template<class R> my_view(R&&) -> my_view<views::all_t<R&&>>;：不写的话 my_view{v} 会拿 vector 本身当模板参数，而 vector 不满足 view，直接编译失败。有了它，左值自动包成 ref_view、右值包成 owning_view。

    closure 对象继承 C++23 的 ranges::range_adaptor_closure<D>：这才是接入 | 的唯一标准途径，同时也让你的 adaptor 能被「closure | closure」规则合成进别人的管道片段。C++20 完全没有这个机制，这也是当年自定义 adaptor 只能抄标准库实现细节的原因。

    另外两个易漏点：迭代器要定义 difference_type（否则连 input_iterator 都不满足，报错会出现在很深的地方）；默认构造要加 requires std::default_initializable<V>，否则底层视图不可默认构造时会变成硬错误而不是被 SFINAE 掉。

  4. 高级团队要在一个百万行的 C++ 项目里引入 Ranges，你会定哪几条规则？

    一、管道是实现细节，不上接口。视图类型名进了函数签名，就进了 mangled 符号名、进了每个包含该头的 TU、也进了链接器的符号表。边界上落地成 span 或容器，顺带也消掉了 §2.1 那类悬垂（返回建立在引用形参之上的视图）。

    二、不返回视图，也不长期存储视图。视图是「一次遍历的计划」，不是数据结构。要跨作用域保存就 ranges::to 落地。

    三、函数对象必须是纯函数。调用次数取决于下游有几个 filter、遍历几趟、算法有没有多解引用，不可预测（§3.2）。

    四、管道长度设上限（比如 3 段），能先筛就先筛。前者是可调试性与调试构建性能，后者是重复求值。

    五、性能结论必须来自测量。-O2 下简单管道通常与手写循环持平，但调试构建的差距是真实的——跑 Debug 测试套件、开发态帧率都会被它拖住，而这一点在只看 Release benchmark 时完全看不见。

    六、先查编译器支持表再用 C++23 的部分。ranges::to、cartesian_product 这批在三大实现里到位得晚，「写完才发现 CI 上那台旧编译器不认」是最常见的返工来源。
