C++ Lambda 的本质

Lambda 不是运行期的新东西，它是一台造类机器：编译器为每个 lambda 表达式生成一个唯一的、没有名字的类，把捕获变成它的数据成员，再给它一个 operator()。理解这一点，捕获语义、类型唯一性、零开销、悬垂陷阱这四类问题就都变成了同一个问题的推论。

01

一句话本质

它是语法糖，糖的下面是一个普通的类

C++ 的 lambda 是纯粹的编译期语法糖。编译器看到一个 lambda 表达式时，会为它生成一个唯一的、没有名字的类，把捕获列表里的东西变成这个类的非静态数据成员，并给它一个 operator()；而 lambda 表达式本身求值出来的，是这个类的一个对象。

所以「lambda 是什么」的答案是：一个重载了 operator() 的仿函数对象，只不过类名由编译器起、构造函数由编译器写。运行期不存在「lambda」这种实体，只有一个普通的类对象和一次普通的成员函数调用。

闭包类型（closure type）：标准为 lambda 表达式生成的那个类。它是唯一的、未命名的、非联合体的类类型，声明在包含该 lambda 表达式的最小作用域里（块作用域 / 类作用域 / 命名空间作用域）。闭包对象（closure object）：lambda 表达式求值的结果，即该闭包类型的一个对象。你能拿到它、拷贝它、传递它，但写不出它的类型名——只能用 auto、decltype 或模板参数去接。
Lambda 像一个带背包出门的人。函数体是「他会做的事」，捕获列表是「出门前往背包里装什么」：装复印件（值捕获）还是装家门钥匙（引用捕获）。装什么在出门那一刻就定死了——这就是为什么捕获是编译期决定的成员，而不是运行期动态查找的环境。也正因为可以只装钥匙，家（栈帧）被拆了以后，钥匙还在背包里，但已经打不开任何东西了——那就是悬垂。

本文按这条主线展开：先把糖脱掉（§2），再用「成员」这一个概念解释全部捕获语义（§3）与类型行为（§4），然后回答「凭什么零开销」（§5）、语言版本给了 operator() 哪些进化（§6）、四种可调用体怎么选（§7），最后是真正会让线上崩溃的生命周期问题（§8）与工程惯用法（§9）。

02

脱糖：编译器生成了什么

把 lambda 手写回一个类，一切就都解释得通了

2.1 完整对照

下面这段代码，右边是编译器概念上生成的类（名字、成员顺序是实现细节，语义是标准规定的）：

你写的
int a = 1;
std::string s = "hi";

auto f = [a, &s](int n) {
    s += std::to_string(a + n);
    return a;
};

int r = f(41);
编译器生成的
class __lambda_4_10 {          // 唯一 · 无名
    int a;                        // 值捕获 → 副本成员
    std::string& s;               // 引用捕获 → 引用成员
public:
    __lambda_4_10(int a_, std::string& s_)
        : a(a_), s(s_) {}

    int operator()(int n) const {  // 默认 const!
        s += std::to_string(a + n);
        return a;
    }
};

auto f = __lambda_4_10{a, s};      // 构造一个对象

由这张图可以直接推出一串常被单独记忆的「规则」，其实它们都是同一件事的推论：

  • 捕获是成员，所以捕获列表决定了闭包对象的大小与内容。
  • 成员在构造时初始化，所以值捕获的拷贝发生在 lambda 创建的那一刻，与调用无关。
  • operator() 是普通成员函数、非虚，所以调用是静态分派，能被内联。
  • 类是唯一且无名的，所以两个长得一样的 lambda 类型不同，且只能用 auto 接。

2.2 mutable 的真相：它去掉的是 operator() 的 const

mutable 经常被误解成「让捕获的变量可变」。准确说法是：lambda 的 operator() 默认是 const 成员函数，mutable 把这个 const 去掉。

写法生成的 operator()能改值捕获的成员吗
[a](){ ... }R operator()() const❌ 成员经 const 路径访问
[a]() mutable { ... }R operator()()✅ 可以，且状态在两次调用间保留
注意区分「成员是 const」和「访问路径是 const」：值捕获的成员本身不是 const 成员，只是在 const 的 operator() 里看到的是 const int。这解释了一个看起来矛盾的现象——引用捕获不需要 mutable 也能改被引用的对象： 
int x = 0;
auto f = [&x] { x = 5; };   // ✅ 合法，没有 mutable
因为成员是 int&，const 修饰的是这个引用成员本身（引用本来就不可重绑定），而不是它指向的 x。同理 [this]{ member_ = 5; } 也不需要 mutable——成员是 C*，const 的是那根指针。

2.3 sizeof 与成员布局

既然捕获就是成员，闭包对象的大小就是「成员之和 + 对齐填充」。这也是判断「一个 lambda 能不能塞进 std::function 的小对象缓冲」的依据：

lambda成员x86-64 典型 sizeof
[]{}无 → 空类1（空类不能为 0）
[i]{}（int i）int4
[&i]{}int&（实现上一个指针）8
[this]{}C*8
[*this]{}C 的副本sizeof(C)
[v]{}（std::vector<int> v）std::vector<int> 副本24（libstdc++）
[a, &s]{}（int, string&）int + 引用16（含 4 字节 padding）
不要依赖布局。标准明确规定：成员的声明顺序未指定；引用捕获是否真的产生一个数据成员也未指定（实现上都存指针，但标准没承诺）。所以别对闭包对象做 reinterpret_cast、别按偏移读它的字段、别把它的二进制表示写进文件或网络包。

「空类 sizeof 为 1」正是无捕获 lambda 能被零成本当作模板参数的原因：std::unique_ptr<FILE, decltype(closer)> 里那个 deleter 会被空基类优化（EBO）吃掉，指针大小不变。细节见对象模型。

03

捕获：成员的六种形态

把「捕获语义」翻译成「成员是什么」，就不用背了

3.1 形态总表

写法成员实际是什么初始化时机主要风险
[x]T x; 一份副本创建时拷贝构造大对象无声深拷贝
[&x]T& x;（实现上是指针）创建时绑定悬垂（最高频事故）
[this]C* this;创建时存指针对象先死 → 悬垂
[*this]（C++17）C 的一份副本创建时拷贝整个对象拷贝成本；副本与原对象状态分叉
[y = expr]（C++14）由任意表达式初始化的新成员创建时求值 expr唯一能 move 进闭包的方式
[...xs = std::move(pack)]（C++20）一组成员（包展开）创建时逐个初始化可变参转发进闭包

默认捕获 [=] / [&] 不是第七种形态，它只是「凡是用到的都按这个方式捕获」的简写，展开后还是上表里的形态。

3.2 拷贝发生在创建点，不是调用点

这是值捕获最容易出错的一处直觉偏差。成员在构造函数里初始化，而构造发生在 lambda 表达式求值时：

int n = 1;
auto f = [n] { std::cout << n; };   // 此刻把 1 拷进成员
n = 99;
f();                                 // 输出 1，不是 99

auto g = [&n] { std::cout << n; };  // 存的是引用
n = 42;
g();                                 // 输出 42

mutable 让这个「成员」成为有状态的对象，于是 lambda 变成了一个小型状态机——这是它作为仿函数的本色：

auto counter = [i = 0]() mutable { return ++i; };
counter();   // 1
counter();   // 2   —— 状态存活在闭包对象里

auto copy = counter;   // ⚠️ 拷贝对象 = 拷贝状态，两者从此独立
copy();      // 3（它自己的 3）
counter();   // 3（原来那个的 3）
「拷贝闭包 = 分叉状态」这条在配合 std::function 时特别容易踩：std::function 按值持有可调用体，每次拷贝 std::function 都会拷贝一份闭包状态。把一个带 mutable 计数器的 lambda 装进 std::function 再到处传，计数就会各算各的。

3.3 引用捕获的内存图

引用捕获之所以危险，是因为它只在闭包里留了一个「地址」，而地址的有效性由别人的生命周期决定。闭包对象本身完全没有延长任何东西的能力：

❌ 返回引用捕获的闭包
auto make() {
    std::string s = "hi";
    return [&s] { return s.size(); };
}
auto f = make();
f();   // UAF：s 早就没了
✅ 把状态搬进闭包
auto make() {
    std::string s = "hi";
    return [s = std::move(s)] {
        return s.size();
    };
}
auto f = make();
f();   // OK：字符串就住在闭包里

3.4 看着捕获，其实没捕获

默认捕获 [=] / [&] 只捕获真正被 odr-use 的自动存储期变量。以下几类根本不需要捕获，写进捕获列表反而会报错或产生误导：

  • static / thread_local 变量：有静态存储期，直接按名字访问，不占闭包空间。
  • 全局变量、命名空间作用域变量：同上。
  • 编译期常量：constexpr int N = 8; 在 arr[N] 这种「只读其值」的位置不构成 odr-use，不会被捕获；但一旦你对它取地址或绑引用，就又需要捕获了。
  • 没用到的变量：即使写了 [=]，用不到的变量不会被拷贝——所以「[=] 会把整个作用域拷一份」是误解。
[=] 最大的坑：它不拷贝成员变量。在成员函数里写 [=] 并访问 member_，捕获的是 this（一个指针），成员是通过它间接访问的： 
void Widget::post() {
    pool.submit([=] { use(data_); });  // 等价于 [this]，data_ 没被拷贝!
}                                        // Widget 先析构 → 悬垂
C++20 把 [=] 隐式捕获 this 标为弃用，要显式写 [=, this]（想拷贝对象则写 [*this]）。这条弃用的意义正是逼你把「我到底捕了指针还是副本」写出来。

3.5 init-capture：唯一能 move 进闭包的写法

C++14 的 init-capture 让成员可以由任意表达式初始化，于是终于能把只移动类型搬进闭包：

auto up = std::make_unique<Session>();

// ❌ C++11 做不到：捕获列表只能写变量名，走的是拷贝构造
// auto f = [up] { up->run(); };            // unique_ptr 不可拷贝

auto f = [p = std::move(up)] { p->run(); };   // ✅ 成员由 move 构造

// 也可以「捕获一个计算结果」，避免每次调用都算
auto g = [key = hash_of(cfg)](const Req& r) { return r.key == key; };
[x = x] 是合法且常见的写法：等号左边是新成员的名字（在闭包作用域里），右边是外层作用域的表达式。因为 up 被 move 空了，如果外层之后还要用它就得小心——move 之后的 unique_ptr 是 nullptr，这是明确定义的状态，不是 UB。

C++20 进一步允许在 init-capture 里做包展开，这是把可变参完美转发进闭包的标准做法：

template <class F, class... Args>
auto defer(F f, Args&&... args) {
    return [f = std::move(f), ...xs = std::forward<Args>(args)]() mutable {
        return std::invoke(std::move(f), std::move(xs)...);
    };
}
面试里问「怎么把 unique_ptr 交给一个异步任务」，标准答案就是 init-capture + std::move。追问一层：这样得到的闭包不可拷贝，因此塞不进 std::function（它要求 CopyConstructible），需要 C++23 的 std::move_only_function，或 std::packaged_task，或自己写个类型擦除包装。能答到这一层，说明你真的理解「捕获 = 成员」。
04

类型系统里的闭包类

唯一、无名，以及 C++20 松开的两道口子

4.1 每个 lambda 表达式一个唯一类型

「唯一」是字面意思：源码里每出现一次 lambda 表达式，就多一个类型，哪怕两处代码一模一样。

auto p = [](int x) { return x * 2; };
auto q = [](int x) { return x * 2; };
static_assert(!std::is_same_v<decltype(p), decltype(q)>);   // 通过：类型不同

// 模板里每个实例化也各有一个：foo<int> 和 foo<double> 里的 lambda 类型不同
template <class T> auto foo() { return [](T v) { return v; }; }

直接后果是你没法写出这个类型，只能：

  • auto f = ...; —— 局部持有，首选。
  • decltype(f) —— 需要把类型交给模板参数时（比较器、deleter）。
  • 模板参数 template <class F> void algo(F f) —— 库接口的标准做法，也是零开销的关键（§5）。
  • std::function<...> / std::move_only_function<...> —— 需要统一类型时才用，有代价。

4.2 无捕获 lambda 到函数指针的隐式转换

闭包类型还带一个转换函数——但只有无捕获时才有：

auto g = [](int x) { return x * 2; };
int (*fp)(int) = g;              // ✅ 走编译器生成的「到 int(*)(int) 的转换函数」
::signal(SIGINT, [](int){ /* ... */ });   // ✅ 所以能塞进 C 接口

int k = 2;
auto h = [k](int x) { return x * k; };
// int (*bad)(int) = h;             // ❌ 有捕获，没有这个转换函数

原因很直白：函数指针里放不下状态。无捕获的闭包是空类，调用它不需要 this，编译器可以生成一个等价的自由函数并把地址给你；一旦有捕获，上下文必须随身携带，而 int(*)(int) 没有地方放。

这解释了 C 回调接口为什么都长成 void (*cb)(void* user_data, ...) 的样子：状态必须走单独的参数。带捕获的 lambda 要接到这种接口上，标准手法是「无捕获 lambda 当蹦床（trampoline）」： 
template <class F>
void register_cb(F& f) {          // f 的生命周期由调用方保证
    auto tramp = [](void* ud, int ev) {   // 无捕获 → 可转函数指针
        (*static_cast<F*>(ud))(ev);
    };
    c_api_set_callback(tramp, &f);       // 状态走 void*
}
另外有个小技巧：+[]{ ... } 前面加一个一元 + 可以强制触发到函数指针的转换（一元 + 对类类型没有意义，于是走隐式转换），偶尔用于消除重载歧义。

4.3 C++20 松开的两道口子

C++20 之前，闭包类型的默认构造函数被删除、拷贝赋值被删除，而且 lambda 不能出现在未求值上下文里。这两条限制合起来导致一个很别扭的结果：明明只想用一个无状态的比较器，却必须绕一圈。

C++17：必须传实例进去
auto cmp = [](int a, int b) { return a > b; };
std::set<int, decltype(cmp)> s(cmp);
// 闭包类型不可默认构造 → 必须把对象传给构造函数
// 也不能写 decltype([]{...})：未求值上下文不许有 lambda
C++20：直接写在类型里
std::set<int, decltype([](int a, int b){ return a > b; })> s;
// ① 无捕获闭包可默认构造、可赋值
// ② lambda 可以出现在未求值上下文
// 于是「比较器」变成纯类型信息，零成员、EBO 吃掉

注意放宽只针对无捕获的闭包：有捕获的仍然没有默认构造、拷贝赋值仍是 delete（拷贝构造一直是可用的，前提是所有成员可拷贝）。

「为什么 C++20 之前不能把 lambda 直接当 std::set 的比较器」是一道很好的分层题：表层答案是「不可默认构造」，中层是「还需要能在未求值上下文里写 lambda」，深层是「这两个限制原本是为了防止在类型系统里制造 ODR 与 mangling 上的麻烦，P0315 / P0624 把这块的规则理清后才敢放开」。
05

零开销从哪里来

lambda 快，不是因为它是 lambda，而是因为调用点知道它的具体类型

5.1 三种调用路径

同一个「把每个元素加起来」的逻辑，用三种可调用体写出来，生成的代码差别巨大。差别的根源只有一个：编译器在调用点能不能看见要调用的具体函数体。

把 lambda 交给模板时，F 被推导成那个具体的闭包类型，f(x) 是一次对已知函数的调用，编译器可以整体内联并继续做循环展开、向量化。这就是「std::sort 比 C 的 qsort 明显快」的原因——不是算法更好，而是比较逻辑被内联了，而 qsort 每次比较都要走一次不可预测的间接调用。

// -O2 下这段的循环体里没有任何 call
long sum = 0;
std::for_each(v.begin(), v.end(), [&sum](int x) { sum += x; });

// 甚至连闭包对象都不存在了：&sum 被寄存器化，operator() 消失
想亲眼确认可以看名字修饰。GCC 下 main 里第一个接受 int 的 lambda，其 operator() 的符号是 _ZZ4mainENKUliE_clEi，c++filt 后是 main::{lambda(int)#1}::operator()(int) const——「第 1 个 lambda」这个编号就是「唯一无名类型」在 ABI 层的样子。而在 -O2 的产物里，这个符号通常根本不出现，因为它被完全内联掉了。

5.2 std::function 的三重开销

std::function<R(Args...)> 做的是类型擦除：把「各不相同的闭包类型」抹平成一个统一类型。这个能力不免费：

开销细节能否避免
间接调用经函数指针 / 虚表跳到真实目标，调用点看不见函数体不能，这是类型擦除的定义
可能堆分配闭包超出小对象缓冲就 new 一份缩小捕获（少捕、捕指针 / shared_ptr）
难以内联连带丢掉循环展开、向量化、常量传播热路径改用模板参数
拷贝语义拷贝 function = 拷贝闭包（可能再分配一次）传 const&；或用 move_only_function
要求可拷贝捕获了 unique_ptr 的闭包装不进去C++23 std::move_only_function
小对象缓冲的大小不是标准约定，别当契约用。libstdc++ 的内联缓冲是两个指针（16 字节）且要求移动构造不抛异常，libc++ 与 MSVC 的阈值都不同。工程上正确的做法是：如果分配敏感（实时、低延迟），就别把 std::function 放在热路径上，而不是去卡那个字节数。

5.3 代价的另一面：模板膨胀

「唯一类型」在性能上是优势，在体积上是代价：每个 lambda 都会让接受它的模板实例化一份新代码。在有几百个回调点的大型工程里，这会实实在在地推高二进制体积和编译时间。

所以选型不是「lambda 永远更好」，而是一条清晰的分界：

  • 热路径、当场调用（算法、循环、内层回调）→ 模板参数接原生 lambda 类型，要的就是内联。
  • 冷路径、需要存储或跨边界（事件表、注册回调、跨 .so、虚接口）→ 类型擦除，要的是统一类型和编译解耦。
这个 trade-off 有个漂亮的中间解：只在最外层做一次类型擦除。比如线程池的 submit 用模板接收任意闭包（调用方零开销），内部再包装成一个 move_only_function 放进队列（存储需要统一类型）。既没有让每个调用点都吃到擦除的代价，也没有让队列被模板污染。

operator() 的进化

泛型 · constexpr · static · 递归，全都落在这一个成员函数上

把 lambda 理解成「一个类 + 一个 operator()」之后，各版本新增的能力就都有了统一解释：它们都在改那个 operator() 的声明。

版本能力本质上改了什么
C++11lambda 表达式、捕获列表、mutable造类 + operator()（const 或非 const）
C++14泛型 lambda [](auto x)；init-captureoperator() 变成模板；成员可由任意表达式初始化
C++17隐式 constexpr；[*this]operator() 满足条件时自动 constexpr；多一种成员形态
C++20显式模板参数 []<class T>；未求值上下文；无捕获可默认构造；包捕获；[=, this]模板参数写出来；闭包类型能进类型系统
C++23static operator()；this auto&& self（deducing this）；lambda 属性去掉隐含的 this 传参；让 operator() 能拿到自己

6.1 泛型 lambda 就是模板 operator()

// C++14：参数写 auto
auto print = [](auto&& x) { std::cout << x; };

// 脱糖后：
class __lambda {
public:
    template <class T>
    auto operator()(T&& x) const { std::cout << x; }   // ← 成员模板
};

// C++20：把模板参数显式写出来，才能对类型本身做操作
auto sum = []<class T>(const std::vector<T>& v) {
    return std::accumulate(v.begin(), v.end(), T{});   // 需要 T 本身
};

C++20 的显式模板参数解决的正是「auto 拿不到类型名字」的问题：以前要写 std::decay_t<decltype(v)>::value_type 绕一大圈，现在直接有 T。

6.2 constexpr 与 static

// C++17 起：满足 constexpr 函数要求就自动是 constexpr，不用写
constexpr auto square = [](int x) { return x * x; };
static_assert(square(4) == 16);

// C++23：无捕获时可以让 operator() 变成 static —— 省掉隐含的 this 参数
auto cmp = [](int a, int b) static { return a < b; };

static operator() 的收益在高频小回调上才看得出来：非 static 的 operator() 即使对象是空类，调用约定上也要传一个 this（占掉一个参数寄存器）。改成 static 后这个参数消失，寄存器压力更小、更容易内联。

6.3 递归 lambda 的三种写法

递归对 lambda 是个真问题：函数体里没法用 auto 变量自己的名字（初始化还没完成，类型未定）。三种解法，代价递减：

// ① std::function —— 能写但最贵：类型擦除 + 每层递归一次间接调用
std::function<int(int)> fib = [&](int n) {
    return n < 2 ? n : fib(n-1) + fib(n-2);   // 还引用捕获了自己，别 return 出去
};

// ② 自传参（Y 组合子风味）—— 零开销，但调用侧要多写一个参数
auto fib2 = [](auto&& self, int n) -> int {
    return n < 2 ? n : self(self, n-1) + self(self, n-2);
};
fib2(fib2, 10);

// ③ C++23 deducing this —— 零开销且调用侧干净
auto fib3 = [](this auto&& self, int n) -> int {
    return n < 2 ? n : self(n-1) + self(n-2);
};
fib3(10);
写法 ① 有两个叠加的坑：std::function 的间接调用让递归无法被优化成尾调用或内联，而 [&] 捕获的又是正在初始化的那个变量自己——一旦把它 return 出去或拷贝到别处，引用立刻悬垂。需要递归又要考虑性能时，直接上 ② 或 ③。
07

可调用体选型

五种载体，按「要不要统一类型」和「要不要存起来」两问决定

载体状态调用开销可存储 / 统一类型什么时候用
原生 lambda（模板参数接）有可内联，~0❌ 类型唯一算法、热路径、当场调用
函数指针❌ 无一次间接调用✅ 统一C 接口、无状态回调
手写 functor 类有可内联，~0❌ 但类型有名字要复用 / 要多个重载 / 要文档化
std::function有（需可拷贝）间接 + 可能堆✅ 统一事件表、注册式回调、编译解耦
std::move_only_function（C++23）有（可只移动）间接 + 可能堆✅ 统一任务队列里放 unique_ptr 类闭包

另有一类「只借用不持有」的轻量载体：C++26 方向的 std::function_ref（现在可用第三方实现），语义是「指向某个可调用体的非拥有引用」，两个指针大小、不分配、不拷贝。它适合只在函数调用期间用一下的回调参数——这也是最常见的场景，而这个场景过去被 std::function 滥用得最多。

最常见的一处无谓开销：函数参数写成 std::function，而这个回调只在函数体内被调用几次、根本不存起来。 
// ❌ 每次调用都可能构造 std::function（可能堆分配），且挡住内联
void each(const std::vector<int>& v, std::function<void(int)> cb);

// ✅ 模板参数：零开销、可内联
template <class F> void each(const std::vector<int>& v, F cb);
模板会把 each 拉进头文件、并让每个调用点各实例化一份，这是它的代价。如果就是要接口稳定、要放在 .cpp 里，那 std::function（或 function_ref）是正确的选择——关键是这个决定要是有意识的。
还有一条 ABI 纪律：不要让闭包类型出现在对外的头文件接口上。它没有名字、编号依赖源码顺序，稍微改一下同一个函数里 lambda 的先后就会变化。要跨 .so / 跨模块边界，用 std::function、函数指针 + void*，或者一个自己定义的抽象接口。
08

生命周期与并发陷阱

线上真正会崩的地方，几乎全在这一章

8.1 悬垂三连

闭包对象不延长任何东西的生命周期。凡是「闭包会离开当前作用域」的地方，都要逐个审查捕获：

形态典型写法为什么崩
捕获局部变量的引用return [&local]{...};函数返回，栈帧销毁
捕获 thistimer.on([this]{ tick(); });对象先于定时器析构
捕获绑到临时量的 const&const auto& s = f(); [&s]{...} 存起来临时量在语句结束时析构
这类 bug 的恶性之处在于它经常「看着是好的」：栈内存刚被释放时内容往往还没被覆盖，测试环境轻负载下读到的还是旧值，一到生产高并发就随机崩。唯一可靠的手段是把 ASan 挂进 CI（-fsanitize=address），它会明确报 stack-use-after-return / heap-use-after-free 并打出「谁分配、谁释放、谁在读」三段栈。排查方法见Sanitizers 指南。

8.2 异步任务的正确写法

「提交给线程池 / 事件循环 / 定时器」是悬垂的高发区，因为闭包的存活时间由调度器决定，而不是由你写代码的那个作用域决定。三种正确姿势：

// ① 强持有 —— 回调执行期间对象一定活着（代价：延长了生命周期）
pool.post([self = shared_from_this()] { self->work(); });

// ② 弱持有 —— 对象可能已经死了，执行前检查（推荐用于「取消即失效」的回调）
pool.post([w = weak_from_this()] {
    if (auto self = w.lock()) self->work();
});

// ③ 值搬运 —— 不需要对象，只需要数据：把数据 move 进闭包
pool.post([payload = std::move(buf)] { send(payload); });

选择标准很清楚：回调必须完成（写日志、释放资源、提交事务）→ ①；对象没了就该放弃（UI 刷新、缓存回填、已取消的请求）→ ②；只是搬数据 → ③，最省心也最快。

案例 · 网关偶发崩溃，栈顶是一个 lambda 引用捕获 + 超时重排

现象：某接入网关每天崩 1～2 次，core 里栈顶是 Session::onTimeout 内的一个 lambda，读到的 request_id 是垃圾值。改成 Debug 版跑一周不复现。

代码大意是这样：

void Session::send(const Request& req) {
    timer_.expires_after(3s);
    timer_.async_wait([&req, this](auto ec) {   // ← 两个都有问题
        if (!ec) log_timeout(req.id);
    });
}

两处问题叠加：req 是引用参数，send 返回后调用方那边的 Request 可能已经销毁；this 在连接被对端提前关闭时也可能先死。Release 下栈内存被下一次调用复用，于是读到垃圾；Debug 下栈布局宽松、时序也不同，就不复现。

为什么没被 review 抓到
因为 [&req, this] 在同步代码里是完全正确的写法。真正的问题不是捕获方式，而是「async_wait 之后这个闭包活到了本函数之外」这件事没有出现在阅读者的视野里。
修法
把需要的数据 move / copy 进闭包，把对象所有权用 weak 表达： 
timer_.async_wait([id = req.id, w = weak_from_this()](auto ec) {
    if (ec) return;
    if (auto self = w.lock()) self->log_timeout(id);
});
只捕获真正需要的 id（一个整数），闭包更小、也不再依赖调用方的对象。
工程结论
给团队定一条可执行的规则比讲原理有效：凡是把闭包交给「会在本函数返回之后执行它」的 API（async_* / post / submit / then / 定时器 / 信号槽），捕获列表里不允许出现 &，this 必须写成 weak_from_this() 或 shared_from_this()。这条能用 clang-tidy 的 bugprone-* 检查加自定义匹配部分覆盖，剩下的靠 review 清单，比「小心悬垂」这种叮嘱靠得住。

8.3 lambda 协程：一个隐蔽得多的悬垂

当 lambda 的函数体里出现 co_await / co_return 时，它变成了一个协程。这里有个非常容易踩的坑：协程帧不会延长闭包对象的生命周期。

❌ 临时闭包 + 协程
spawn([conn]() -> task<> {
    co_await conn->read();   // 第一次挂起后…
    conn->write();          // ← 闭包（含 conn 成员）可能已析构
});
// 闭包对象是个临时量：调用 operator() 得到协程句柄后
// 这个临时量在整个表达式结束时就销毁了，而协程还在挂起
✅ 参数化，让协程帧自己持有
// 需要的东西走参数：协程帧会保存参数的副本
auto body = [](std::shared_ptr<Conn> c) -> task<> {
    co_await c->read();
    c->write();
};
spawn(body(conn));   // c 在帧里，安全

规则可以记成：协程帧保存的是「参数」，不是「捕获」。所以协程 lambda 的捕获列表应当尽量为空，需要的状态一律走参数（按值），或者保证闭包对象本身活得比协程久。同样的道理适用于成员函数协程里的 this——详见协程。

8.4 mutable 状态 + 多线程

mutable 让闭包变成有状态对象，那么它就和任何有状态对象一样，需要考虑数据竞争：

// ❌ 同一个闭包对象被多线程调用 → 对成员 n 的竞争
auto tick = [n = 0]() mutable { return ++n; };
pool.post(tick); pool.post(tick);   // 这里是拷贝，各算各的（更隐蔽的 bug）
pool.post(std::ref(tick));            // 这里是共享，真竞争

// ✅ 要共享计数就用原子，并且明确表达共享意图
auto counter = std::make_shared<std::atomic<int>>(0);
auto tick2 = [counter] { return counter->fetch_add(1) + 1; };

注意上面两行的差别很典型：拷贝闭包不会报错，但会静默地让状态分叉——「计数总是偏小」这类 bug 就是这么来的，而它不会触发任何 sanitizer。相关内存序细节见内存模型。

工程惯用法

五个真正提高代码质量的用法，而不是「能写成一行」

9.1 IIFE：给 const 变量一段初始化逻辑

需要几行逻辑才能算出来的值，往常只能放弃 const 或者写个只用一次的函数。立即调用的 lambda 解决这个问题，同时把中间变量关在里面：

// ❌ 为了初始化而放弃 const，作用域里多出两个临时变量
Config cfg;
if (has_env()) cfg = from_env();
else            cfg = from_file("default.toml");

// ✅ const，且初始化逻辑就在定义处，中间状态不外泄
const Config cfg = [] {
    if (has_env()) return from_env();
    return from_file("default.toml");
}();

同样适用于构造函数初始化列表里的复杂成员初始化——它是把「必须可变才能初始化」的代码变回 const 的通用手法。

9.2 无状态 lambda 当类型参数：deleter 与比较器

// 自定义 deleter：无捕获闭包是空类，EBO 吃掉，unique_ptr 仍是一个指针大小
auto fclose_ = [](FILE* f) { if (f) std::fclose(f); };
std::unique_ptr<FILE, decltype(fclose_)> fp{std::fopen(path, "rb")};
static_assert(sizeof(fp) == sizeof(FILE*));   // 真的零开销

// C++20：比较器直接写在类型里，容器不需要携带任何函数对象
using MaxHeapSet = std::set<int, decltype([](int a, int b){ return a > b; })>;
对比 shared_ptr：它的 deleter 存在控制块里（类型擦除），所以不影响 shared_ptr 的类型和大小，但多一层间接调用。unique_ptr 的 deleter 是类型参数，所以能被内联、能 EBO，但会进类型签名。这正是 §5 那条分界在标准库里的体现，详见智能指针。

9.3 overloaded：用继承把多个 lambda 合成一个重载集

闭包类型是普通的非 final 类，所以可以被继承。这就是 std::visit 配套的经典惯用法：

template <class... Fs>
struct overloaded : Fs... { using Fs::operator()...; };
// C++17 需要这条推导指引；C++20 起聚合体 CTAD 让它可省略
template <class... Fs> overloaded(Fs...) -> overloaded<Fs...>;

std::variant<int, std::string, double> v = "hi";
std::visit(overloaded{
    [](int i)                { std::cout << "int "    << i; },
    [](const std::string& s) { std::cout << "string " << s; },
    [](double d)             { std::cout << "double " << d; },
}, v);

三个 lambda 成为三个基类，using Fs::operator()...; 把它们的 operator() 全部拉进派生类形成重载集，重载决议照常工作。整个过程没有虚函数、没有分配——因为它全在类型层面完成。

9.4 scope guard：RAII + lambda

template <class F>
struct ScopeExit {
    F f;
    bool active = true;
    ~ScopeExit() { if (active) f(); }        // 异常路径也会执行
    void dismiss() { active = false; }
};
template <class F> ScopeExit(F) -> ScopeExit<F>;

void handle() {
    int fd = ::open(path, O_RDONLY);
    ScopeExit closer{[&] { ::close(fd); }};   // 任何出口都会关
    parse(fd);                                // 抛异常也没事
}

这里的 [&] 是安全的——因为 ScopeExit 是栈对象，闭包不会离开这个作用域。这也说明「引用捕获危险」不是绝对的：危险的是闭包活得比被引用者久，而不是引用捕获本身。

9.5 一份可执行的 review 清单

检查项理由
闭包会离开当前作用域吗？会 → 捕获列表里禁止 &悬垂的唯一有效防线
成员函数里用了 [=] / [this]？改成 weak_from_this() 或 [*this][=] 不拷贝成员，只捕 this
显式列出捕获，少用默认捕获让「捕了什么、多大、多久」在代码里可见

面试题集（16 道分层）

基础（必答） · 中级（区分熟练度） · 高级（体现深度）

点击每道题展开参考答案（先自测，再对照）。

10.1 基础（必答）

  1. 基础C++ 的 lambda 本质是什么？编译器为它生成了什么？

    它是编译期语法糖。编译器为每个 lambda 表达式生成一个唯一的、未命名的类（闭包类型），把捕获变成它的非静态数据成员，并生成一个 operator()；lambda 表达式求值的结果是这个类的一个对象（闭包对象）。

    • operator() 默认是 const、非虚、隐式 inline；C++17 起满足条件时隐式 constexpr。
    • 闭包类型声明在包含该表达式的最小作用域里，无名字、不可显式写出。
    • 运行期没有「lambda」这种实体，只有一次普通的对象构造 + 一次普通的成员函数调用。
  2. 基础mutable 到底改变了什么？

    它去掉 operator() 的 const，而不是「让变量可变」。默认生成的是 R operator()(...) const，所以值捕获的成员在里面是按 const 访问的；加上 mutable 后签名变成非 const，才能修改成员、并让状态在多次调用间保留。

    推论一
    引用捕获不需要 mutable 就能改被引用的对象：const 修饰的是引用成员本身（引用本来就不能重绑定），不是它指向的对象。
    推论二
    [this] 也不需要 mutable 就能改成员变量：成员是 C*，const 的是那根指针。
  3. 基础值捕获的拷贝发生在什么时候？

    发生在 lambda 创建的那一刻（闭包对象的构造函数里），与什么时候调用无关。

    int n = 1;
auto f = [n] { return n; };   // 此刻把 1 拷进成员
n = 99;
f();                          // 1

    因为「捕获就是成员」，成员自然是在构造时初始化的。引用捕获同理：绑定发生在创建时，之后读到的是被引用对象的当前值。

  4. 基础在成员函数里写 [=]，成员变量会被拷贝吗？

    不会。[=] 捕获的是 this（一个指针），成员变量是通过它间接访问的。所以对象一旦先析构，闭包里访问成员就是悬垂——这是异步回调里最高频的一类崩溃。

    C++20 的动作
    [=] 隐式捕获 this 被弃用，要显式写 [=, this]；想真正拷贝对象则用 C++17 的 [*this]。这条弃用的目的就是逼你把「捕的是指针还是副本」写清楚。
    正确写法
    异步场景用 [self = shared_from_this()]（必须完成）或 [w = weak_from_this()]（对象没了就放弃），只需要数据时直接把数据 move 进闭包。
  5. 基础为什么无捕获的 lambda 能转成函数指针，有捕获的不行？

    因为无捕获的闭包是空类、无状态，调用它不需要任何上下文，标准规定这种闭包类型额外提供一个到函数指针的转换函数，编译器可以生成一个等价的自由函数把地址给你。有捕获时状态必须随身携带，而 R(*)(Args...) 里没有地方放状态，所以这个转换不存在。

    工程含义
    C 回调接口都长成 void(*cb)(void* user_data, ...) 就是这个原因——状态必须走单独的参数。带捕获的闭包接 C 接口的标准做法是用一个无捕获 lambda 当蹦床，把对象地址通过 void* 传进去再 static_cast 回来。
  6. 基础两个写得一模一样的 lambda，类型相同吗？怎么持有一个 lambda？

    不同。源码里每出现一次 lambda 表达式就多一个唯一类型，std::is_same_v 为 false。模板的每个实例化里也各有一个。

    所以持有方式只有四种：auto（局部持有，首选）、decltype(f)（把类型交给模板参数，如 deleter / 比较器）、模板参数 template <class F>（库接口，零开销）、std::function 之类的类型擦除容器（需要统一类型时，有代价）。

10.2 中级（区分熟练度）

  1. 中级sizeof 一个 lambda 等于多少？可以依赖这个布局吗？

    等于所有捕获成员之和加对齐填充。无捕获时是空类，sizeof == 1；[i]（int）是 4；[&i] 和 [this] 是 8；[*this] 是 sizeof(C)；[a, &s]（int + 引用）在 x86-64 上是 16（含 4 字节 padding）。

    不能依赖
    标准规定成员的声明顺序未指定，引用捕获是否产生数据成员也未指定。所以不要对闭包对象 reinterpret_cast、不要按偏移读字段、不要序列化它。
    为什么还要关心大小
    两个实际用途：判断能否落在 std::function 的小对象缓冲里（避免堆分配），以及确认无捕获闭包作为 unique_ptr 的 deleter 时被 EBO 吃掉（sizeof(unique_ptr) == sizeof(T*)）。
  2. 中级lambda 和 std::function 的区别与开销？什么时候必须用后者？

    lambda 是一个具体类型，std::function 是类型擦除容器。前者调用点知道目标、可完全内联；后者把不同闭包统一成一个类型，代价是间接调用、可能的堆分配、以及内联失效（连带丢掉循环展开和向量化）。

    必须用 std::function 的场景：需要把不同类型的可调用体放进同一个容器 / 成员 / 虚接口；需要接口稳定并把实现放在 .cpp 里（避免模板进头文件）；需要运行期替换回调。

    最常见的滥用
    函数参数写 std::function，而回调只在函数体内被调用几次、根本不存起来。这种应该用模板参数（零开销）或 function_ref（两个指针、不分配）。
    小对象缓冲
    不是标准约定，别当契约：libstdc++ 是两个指针（16 字节）且要求移动不抛，libc++ / MSVC 的阈值都不同。分配敏感的路径应该直接避开 std::function，而不是去卡字节数。
  3. 中级为什么 std::sort 传 lambda 比 C 的 qsort 传函数指针快？

    不是算法差异，是比较逻辑能不能被内联。std::sort 的比较器是模板参数，被推导成那个具体的闭包类型，比较代码可以直接内联进排序循环；qsort 收的是 int(*)(const void*, const void*)，每次比较都是一次目标未知的间接调用，既不能内联，还挡住了周边的优化，另外还要为 void* 做类型转换和解引用。

    再深一层
    这条推理反过来也成立：如果你把比较器写成 std::function 传给 std::sort，就主动放弃了这个优势，性能会退回到接近函数指针的水平。快的不是「lambda」，而是「调用点知道具体类型」。
  4. 中级怎么把 unique_ptr 交给一个 lambda？之后能放进 std::function 吗？

    用 C++14 的 init-capture：[p = std::move(up)] { p->run(); }。C++11 的捕获列表只能写变量名、走拷贝构造，对只移动类型不成立。

    不能放进 std::function：这样得到的闭包有一个不可拷贝的成员，因此闭包本身不可拷贝，而 std::function 要求可调用体 CopyConstructible。

    解法
    C++23 的 std::move_only_function；或 std::packaged_task；或把资源换成 shared_ptr（可拷贝，代价是引用计数）；或自己写一个只要求可移动的类型擦除包装。
  5. 中级C++20 之前为什么不能把 lambda 直接写成 std::set 的比较器类型？

    两条限制叠加：① C++20 前闭包类型的默认构造函数被删除，容器无法自己造一个比较器，必须把实例传进构造函数（std::set<int, decltype(cmp)> s(cmp);）；② lambda不允许出现在未求值上下文，所以连 decltype([]{...}) 都写不出来。

    C++20 同时放开了这两条（无捕获闭包可默认构造、可赋值；lambda 可用于未求值上下文），于是 std::set<int, decltype([](int a, int b){ return a > b; })> 成立，比较器变成纯类型信息、零成员、被 EBO 吃掉。

    注意边界
    放宽只针对无捕获闭包。有捕获的仍然不可默认构造、拷贝赋值仍是 delete（拷贝构造一直可用，前提是成员都可拷贝）。

10.3 高级（体现深度）

  1. 高级泛型 lambda 的本质是什么？C++20 的显式模板参数解决了什么问题？

    [](auto x){...} 的本质是把 operator() 变成成员模板：闭包类型里是 template <class T> auto operator()(T x) const。所以泛型 lambda 不是「一个能吃任意类型的函数」，而是「一个能按需实例化出多个 operator() 的对象」——每种实参类型生成一份代码。

    C++20 的 []<class T>(const std::vector<T>& v){...} 解决的是「auto 拿不到类型的名字」：以前要写 typename std::decay_t<decltype(v)>::value_type 这种一长串，现在直接有 T 可用，也能对 T 加约束（concept）。

    连带影响
    泛型 lambda 无捕获时，到函数指针的转换函数也变成模板，可以按需要的签名取出对应的函数指针。另外「一个泛型 lambda 对应多份实例化代码」是模板膨胀的又一来源，在回调点极多的工程里值得留意。
  2. 高级递归 lambda 有几种写法？各自的代价是什么？

    问题的根源是：函数体里用不了 auto 变量自己的名字，因为初始化还没完成、类型还没定下来。

    ① std::function
    std::function<int(int)> f = [&](int n){ ... f(n-1) ... };。能写，但最贵：每层递归一次间接调用、无法内联；而且 [&] 捕获的是正在初始化的变量自己，一旦把它 return 出去或拷贝走就悬垂。
    ② 自传参（Y 组合子风味）
    [](auto&& self, int n) -> int { ... self(self, n-1) ... }。零开销、可内联，代价是调用侧要多写一个参数，可读性稍差。
    ③ C++23 deducing this
    [](this auto&& self, int n) -> int { ... self(n-1) ... }。零开销且调用侧干净，是目前的首选写法。
    追问
    为什么需要显式写返回类型 -> int？因为返回类型推导要求在推导点看到完整的函数体，而递归调用出现在推导完成之前，形成循环依赖。显式给出返回类型就打破了这个循环。
  3. 高级lambda 协程为什么会悬垂？怎么修？

    关键事实：协程帧保存的是「参数」，不是「捕获」。协程帧不会延长闭包对象的生命周期。

    spawn([conn]() -> task<> {
    co_await conn->read();   // 挂起，返回调用方
    conn->write();          // 闭包临时量早已销毁 → 读 conn 成员是 UAF
});

    这里的闭包是个临时量：调用 operator() 拿到协程句柄后，这个临时量在整个表达式结束时就析构了，而协程还挂在半路。之后恢复执行时访问的 conn 成员已经不存在。

    修法
    把状态走参数按值传（协程帧会保存参数副本），捕获列表尽量留空：auto body = [](std::shared_ptr<Conn> c) -> task<> {...}; spawn(body(conn));。或者保证闭包对象本身活得比协程久（存成一个具名的、生命周期受控的对象）。
    同类问题
    成员函数协程里的 this 完全一样：帧里存的是 this 指针，对象先死就悬垂。需要 shared_from_this() 或由调用方保证存活。
  4. 高级线上服务用 [&] 提交异步任务导致偶发崩溃，你怎么定位和修复？

    定位——这类问题在 Debug 下通常不复现（栈布局宽松、时序不同），所以：

    ① 保留优化 + 开检测
    -O2 -g -fsanitize=address。ASan 会明确报 stack-use-after-return 或 heap-use-after-free，并打出「谁分配 / 谁释放 / 谁在读」三段栈——释放栈通常直指那个已经返回的函数。
    ② 看 core 的栈顶符号
    栈顶若是 Xxx::method::{lambda(...)#N}::operator()，直接定位到是哪个函数里第几个 lambda，然后逐个检查它的捕获列表。
    ③ 缩小怀疑面
    全仓库搜「异步 API + [&] / [=] / [this]」的组合：async_、post、submit、then、定时器、信号槽。事故几乎总在这个交集里。

    修复：数据 move 进闭包；对象所有权用 shared_from_this()（回调必须完成）或 weak_from_this()（对象没了就放弃）；只捕获真正需要的最小字段而不是整个对象。

    防止复发（这是真正的答案）
    光修一处没意义。要立三件事：① 一条可执行的规则——「交给会在本函数返回后执行的 API 的闭包，捕获列表不允许出现 &，this 必须写成 weak_from_this()」，进 review 清单；② ASan 常态化挂进 CI（跑集成测试而不只是单测，异步问题只在有真实调度时才暴露）；③ 让异步 API 自己表达约束——把 post 的参数类型收成只接受可移动的闭包、或提供 post(weak_ptr, F) 这类专用重载，用类型系统挡住错误写法，比靠人记住更可靠。
  5. 高级为什么不能把闭包类型暴露在对外的接口 / ABI 上？

    因为闭包类型没有名字，且身份依赖源码形态。它在 ABI 层的名字是「某个函数里第 N 个 lambda」这种编号（GCC 下形如 main::{lambda(int)#1}::operator()(int) const）——在同一个函数里调整两个 lambda 的先后顺序，编号就变了，符号也就变了。

    • 调用方写不出这个类型，只能 auto，所以它没法出现在稳定的头文件签名里。
    • 它没有稳定的 mangled name，跨 .so 边界的兼容性无从保证。
    • 它把实现细节（有几个 lambda、顺序如何）变成了接口的一部分，任何重构都可能破坏兼容。
    跨边界该用什么
    std::function（统一类型、可存储，代价是间接调用与可能的分配）、函数指针 + void* user_data（C ABI 友好）、或者自己定义一个抽象接口类。要点是：边界上必须有一个你能写出名字、并且承诺不变的类型。
    相关的一处细节
    写在头文件 inline 函数或模板里的 lambda，标准要求各翻译单元得到同一个闭包类型（否则违反 ODR）；这让「模板里用 lambda」是安全的。但这条保证是关于同一份源码的，它不保证你改动源码后新旧二进制还兼容——所以 ABI 纪律依然成立。
