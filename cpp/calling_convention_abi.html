Calling Convention 与 ABI：参数为什么不一定压栈？

前三篇里反复出现一句话：「这取决于 ABI」。本篇把这个决定一切的幕后规则讲透 —— 参数放哪、返回值怎么带回、哪些寄存器谁负责保存、栈怎么对齐。我们以 x86-64 Linux System V ABI 为主线，再横向对比 Windows x64 与 ARM64，让你彻底理解：同一段 C++，为何在不同平台生成完全不同的汇编。

01

Calling Convention 与 ABI 是什么

两个常被混用的词，先分清层级

概念范围规定的内容
Calling Convention（调用约定）较窄单次函数调用的规矩：参数放哪、返回值放哪、谁保存寄存器、栈如何清理
ABI（Application Binary Interface）较宽包含调用约定，还规定：数据类型大小/对齐、结构体布局、name mangling、目标文件/可执行文件格式、系统调用方式等

可以理解为：调用约定是 ABI 的一个子集。ABI 是「两段独立编译的二进制如何协作」的完整合同，调用约定则是其中关于「函数怎么调」的那一章。

最需要记住的一句

C++ 语言标准并不规定参数放哪个寄存器、返回值怎么传。这些完全由 ABI / Calling Convention / 编译器 / 平台决定。C++ 只保证「语义」（调用 add(10,20) 会得到 30），不保证「实现方式」。

02

为什么 ABI 如此重要

它是「分开编译、还能拼在一起运行」的前提

你的程序由许多独立编译的部分组成：你的 .o、第三方 .so、C 标准库、系统内核。它们可能由不同版本编译器、甚至不同语言产出。为什么它们能互相调用？因为大家遵守同一份 ABI：

  • 调用方按 ABI 把参数放进 RDI/RSI…，被调方也按 ABI 从那里取 —— 双方无需见过对方源码；
  • 数据类型大小、结构体布局一致，一方写的结构体另一方才能正确读；
  • ABI 稳定，就能只替换某个 .so 而不重编译整个程序。

ABI 不匹配的后果非常隐蔽：编译能过、链接能过，运行时却因为「一方以为参数在 RDI、另一方去 RCX 取」而读到垃圾值、栈错位、崩溃。跨语言（C/C++/Rust/Go）互调、跨平台移植时，ABI 是头号坑。稳定的 C ABI 正是各种 FFI（外部函数接口）的通用桥梁。

03

参数传递规则（System V x86-64）

Linux / macOS / 多数 Unix 使用的调用约定

整数 / 指针参数：6 个寄存器

RDI
第 1 个参数
RSI
第 2 个参数
RDX
第 3 个参数
RCX
第 4 个参数
R8
第 5 个参数
R9
第 6 个参数

浮点/向量参数走另一组 XMM0–XMM7（8 个），与整数寄存器独立计数。所以一个函数可以有 6 个整数 + 8 个浮点参数全部走寄存器。

long add(long a, long b) {
    return a + b;
}

# System V x86-64（-O2，Intel 语法）
add:
    lea     rax, [rdi + rsi]   # a 在 RDI，b 在 RSI
    ret                        # 返回值在 RAX

对应关系一目了然：a → RDI，b → RSI，返回值 → RAX。这就是「参数不一定压栈」最直接的证据 —— 这里根本没碰栈。

this 指针去哪了？

C++ 成员函数的隐藏 this 指针，在 System V 下作为第一个参数放进 RDI，真实参数依次后移到 RSI、RDX…。这解释了为什么成员函数汇编里第一个参数总是 this。

04

返回值规则

小的走寄存器，大的走隐藏指针

返回类型放在哪
整数 / 指针（≤ 64 位）RAX
128 位整数 / 两个字段的小结构体RAX + RDX
浮点 / doubleXMM0（+ XMM1）
大结构体（放不进寄存器）调用者预留内存，把其地址通过隐藏指针（RDI）传入，被调函数直接写进去；同时返回该地址
大对象返回 = sret（结构体返回优化）

返回一个大 struct 时，编译器改写函数签名：真实的第一个参数变成「结果对象的地址」（RDI），原来的参数后移。被调函数把结果直接构造在调用者给的内存里，避免一次多余拷贝。这也是 RVO / NRVO（返回值优化）的底层实现方式之一。

05

Caller-saved 与 Callee-saved

共用一套寄存器时，「谁负责保护谁」的分工

调用者和被调者共用同一套物理寄存器。ABI 把它们分成两类，约定各自的保护责任：

类别含义System V 寄存器
Caller-saved（易失 / volatile）被调函数可以随意覆盖。调用者若想在调用后还用它，调用前自己先存RAX, RCX, RDX, RSI, RDI, R8–R11, XMM0–15
Callee-saved（非易失 / non-volatile）被调函数若要用，必须先保存、返回前恢复原值，让调用者感觉没被动过RBX, RBP, R12–R15, RSP
 
# 被调函数若要用 callee-saved 的 rbx：
foo:
    push    rbx           # 先保存调用者的 rbx
    ...     # 自由使用 rbx
    pop     rbx           # 返回前恢复
    ret

# 调用者若在 call 前后要保留 caller-saved 的 rcx：
    mov     [rsp-8], rcx  # 自己先存
    call    bar
    mov     rcx, [rsp-8]  # 调用后自己恢复

这套分工的意义：不必在每次调用时保存全部 16 个寄存器。只保存「确实要跨调用存活」的那些，把开销降到最低。返回值寄存器 RAX 天然是 caller-saved（本来就要被结果覆盖）。

06

栈对齐（16 字节）

一个不遵守就可能崩溃的隐形规则

System V x86-64 规定：在执行 call 那一刻，RSP 必须 16 字节对齐。由于 call 会压入 8 字节返回地址，所以函数入口处 RSP % 16 == 8。编译器据此计算序言里 sub rsp, N 的 N，使调用下一层前重新对齐到 16。

为什么要对齐？

SSE/AVX 的对齐访存指令（如 movaps）要求操作数 16 字节对齐，否则触发 #GP 异常直接崩溃。若你手写汇编或在信号处理里破坏了对齐，常见症状就是「进某个用到 SIMD 的库函数就段错误」。ARM64 同样要求栈 16 字节对齐。

# 典型：为了对齐而多留 8 字节
foo:
    push    rbp           # RSP 从 ...8 变 ...0（对齐）
    mov     rbp, rsp
    sub     rsp, 16       # 保持 16 对齐后再调用别人
    call    bar
07

参数超过寄存器数量怎么办

寄存器不够，栈来兜底

当整数参数超过 6 个，第 7 个起从右向左压栈。看一个 8 参数的例子：

long f(long a,long b,long c,long d,long e,long g,long h,long i);
// a→RDI b→RSI c→RDX d→RCX e→R8 g→R9   h,i→压栈
高地址 ↑
第 8 个参数 i[rsp + 16]
第 7 个参数 h[rsp + 8]
返回地址[rsp + 0] ← call 压入
低地址 ↓（被调函数视角，进入时）

▲ 超出寄存器的参数由调用者压栈，被调函数用 [rsp+N] 读取

从右向左压栈，使得第 7 个参数离返回地址最近、编号越大越远。这也是 C 变参函数（printf）能工作的部分基础。结论：栈只是寄存器不够时的补充，绝非「参数的默认归宿」。

Linux vs Windows：最直观的差异

long add(long a, long b) { return a + b; }

# Linux System V：a→RDI, b→RSI
    lea     rax, [rdi + rsi]

# Windows x64：a→RCX, b→RDX
    lea     rax, [rcx + rdx]

完全相同的 C++，寄存器分配却不同。这就是为什么直接把 Linux 编译的 .o 拿去 Windows 链接会出问题 —— 二者 ABI 不兼容。

ARM64（AArch64）：嵌入式 / 移动开发

ARM64 用 X0–X7 传前 8 个整数参数，返回值在 X0。它有独立的链接寄存器 LR (X30) 保存返回地址（而非像 x86 那样压栈）—— 叶子函数因此常常连栈都不碰，非常适合低功耗场景。理解这点，看 Cortex-M / 手机 SoC 的反汇编就不再陌生。

核心洞见：调用约定是「平台的选择」，不是「语言的规定」。正因如此，C++ 才能在从 8 位单片机到超算的各种硬件上运行 —— 语义统一，实现各随其平台的 ABI。

09

核心结论

  • 调用约定 ⊂ ABI：前者管单次调用，后者管整套二进制协作合同。
  • System V x86-64：整数参数 RDI/RSI/RDX/RCX/R8/R9，返回值 RAX，浮点走 XMM。
  • Caller-saved 由调用者按需保存，Callee-saved 由被调函数保存并恢复。
  • call 时 RSP 必须 16 字节对齐，否则 SIMD 指令可能崩溃。
  • 参数超出寄存器才压栈；大返回值走隐藏指针（sret）。
  • Linux / Windows / ARM64 的约定各不相同；C++ 标准对此一律不管。
10

常见误区

❌ C++ 标准规定了寄存器传参规则。 完全没有。这是 ABI / 平台层面的事。

❌ 所有平台参数寄存器都一样。 Linux 用 RDI 系列、Windows 用 RCX 系列、ARM64 用 X0 系列。

❌ 返回值总在 RAX。 标量是，大对象走隐藏指针，浮点走 XMM0。

❌ 栈对齐无所谓。 破坏 16 字节对齐会让 SSE/AVX 对齐访存指令直接触发异常。

❌ 每次调用都要保存全部寄存器。 只有跨调用需存活的 callee-saved 才需保存，最小化开销。

11

面试问题

基础什么是 Calling Convention？什么是 ABI？两者关系？

调用约定规定单次函数调用的参数/返回值/寄存器保存/栈清理规则；ABI 是更大的二进制接口合同，包含调用约定、类型布局、mangling、文件格式等。调用约定是 ABI 的子集。

基础System V x86-64 前 6 个整数参数放哪？返回值放哪？

RDI、RSI、RDX、RCX、R8、R9；返回值放 RAX（大对象走隐藏指针）。

原理Caller-saved 和 Callee-saved 是什么？

Caller-saved（易失）可被被调函数覆盖，调用者需要就自己先存；Callee-saved（非易失）被调函数要用必须先保存、返回前恢复。目的是最小化保存开销。

原理为什么需要 16 字节栈对齐？违反会怎样？

SSE/AVX 对齐访存指令要求 16 字节对齐，违反触发 #GP。ABI 规定 call 时 RSP 16 字节对齐来保证这一点。

ABI参数超过寄存器数量后怎么传？

超出部分由调用者从右向左压栈，被调函数用相对 RSP/RBP 的偏移读取。

ABIC++ 成员函数的 this 指针怎么传？

System V 下作为隐藏的第一个参数放进 RDI，其余参数后移。

进阶为什么 Linux 编译的目标文件不能直接给 Windows 链接？

两者 ABI/调用约定不同（寄存器分配、shadow space、对象格式 ELF vs PE），二进制层面不兼容。

进阶返回一个大结构体时底层发生了什么？

编译器插入隐藏指针参数（RDI），指向调用者预留的结果内存，被调函数直接在那里构造结果，避免拷贝（RVO 的实现基础）。
