C++ 模板 & 泛型编程

模板是编译期代码生成器：写一份蓝图，编译器按用到的类型「印」出具体函数/类。本篇用图讲清特化、SFINAE、Concepts、CRTP 与实例化点，代码只留最短能跑通的那几块。

01

模板 & 泛型编程概览

蓝图不进二进制 · 三种模板参数 · 零运行时开销

模板让你写与类型无关的代码，由编译器在使用处按具体类型生成对应版本。模板定义本身不产生机器码；只有被实例化的版本才进二进制。

饼干模具（模板）本身不是饼干。换一种面团（类型 / 值 / 模板）压一次，才得到一块对应口味的饼干（实例）。模具可以反复用，但每种面团只压一次——用过的类型不会再生成一份。
实例化：编译器把模板蓝图 + 实参填成具体函数/类的过程。发生在实例化点（Point of Instantiation），见 §7。

模板的核心价值

特性一句话典型用法
代码复用一套蓝图，多种类型serialize<T>()、vector<T>
类型安全错配在编译期炸掉static_assert / Concepts
零抽象成本生成后可完全内联CRTP、表达式模板
策略抽象类型参数就是策略分配器、比较器、消息 Adapter
02

函数模板 (Function Template)

蓝图 + 调用处推导 · 与类模板对照

函数模板是一份函数蓝图：调用时按实参推导 T，再在该翻译单元的实例化点生成具体函数。类模板同理，只是参数化的是整个类型。

template <typename T>
T maxv(T a, T b) { return a > b ? a : b; }   // 函数模板

template <typename T>
class Box {                                      // 类模板
    T v_;
public:
    explicit Box(T v) : v_(std::move(v)) {}
    const T& get() const { return v_; }
};

auto m = maxv(3, 7);          // 推导 T=int → 生成 maxv<int>
Box<std::string> b{"ok"};     // 类模板通常要写实参（C++17 CTAD 可省）

工程里函数模板干什么

形态干什么注意
单参数 serialize<T>POD 按字节塞进 payload非平凡类型不要 memcpy
数值算法 linearInterpolate<T>一份代码覆盖 float/double/int整数除法会截断
多参数 MakeMsg<TReq,TResp>static_assert 钉死 Req/Resp 配对约束比注释可靠

推导规则（最短）

普通参数按实参类型推导；T&& 在函数模板里是万能引用（见 §9.13）。显式写 maxv<double>(1, 2) 会压过推导。

多模板参数

每个参数独立推导。需要两个类型「对得上」时，用 static_assert / concept，不要等到运行期。

03

类模板 (Class Template)

参数化整个类型 · 成员还可以再是函数模板

最短语法见 §2 的 Box<T>。STL 的 vector<T> / map<K,V> 都是类模板：数据布局和成员函数一起被参数化。成员函数可以再套一层函数模板（双重泛型）。

线程安全封装

ReadWriteLockedValue<T>：T value_ + shared_mutex；get/set 锁整值，read(Func) / write(Func) 把锁范围内的操作交给回调——Func 是成员函数模板参数。

消息适配器

Adapter<T> 继承 T，默认 memcpy 整对象；对变长/只需部分字段的消息做全特化换实现（§4）。这是「同一接口、按类型换算法」，不是运行时虚函数。

类模板参数化什么特化点
ReadWriteLockedValue<T>被保护的值类型一般不特化，Func 靠推导
Adapter<T>消息体 + 序列化策略变长消息全特化 to/from
vector<T, Alloc>元素 + 分配器vector<bool> 全特化是反面教材
04

模板特化 (Template Specialization)

全特化钉死类型 · 偏特化约束形态 · 函数模板只能重载

特化 = 给更特殊的实参形态换一份实现。编译器永远选最特殊的匹配：全特化 > 偏特化 > 主模板。

工程里的全特化

写法干什么判据
主模板只声明 struct MessageInfo;强制每种消息必须有全特化漏特化 → 不完整类型，编译失败
template<> struct Adapter<StopReq>变长消息只序列化必要字段默认 memcpy 不够用才特化
convertValue<uint8_t> 全特化uint8_t 会被当成 char，要先转 uint16 再范围检查类型有「表面相同、语义不同」时

Adapter 自定义序列化

默认 Adapter<T> 假设对象是平凡可拷贝的定长块；特化版只写 transactionId。同一套 to/from 接口，实现按类型分叉——这就是全特化，不是虚函数。

convertValue<uint8_t>

主模板 lexical_convert<T> 对 uint8_t 会走到 char 路径。全特化先转 uint16_t 再检查 0–255：换实现，不是提前实例化。

偏特化 vs 全特化（最短例）

template <typename T> struct is_ptr { static constexpr bool value = false; };
template <typename T> struct is_ptr<T*> { static constexpr bool value = true; }; // 偏特化
template <>           struct is_ptr<void*> { static constexpr bool value = true; }; // 全特化

template <typename T> void f(T);
template <typename T> void f(T*);   // 重载，不是偏特化
// template <typename T> void f<T*>(T*);  // ❌ 非法

全特化 ≠ 显式实例化

全特化（显式特化）显式实例化
语法template <> struct Foo<int> { … }template struct Foo<double>;
有 <>有，且通常有函数体/类体没有，以分号结尾
做什么给该类型换实现用主模板提前生成
改行为会不会

模板的编译模型 & 显式实例化

实例化点 · 惰性成员 · ODR/COMDAT · 头文件模型 vs modules

模板定义是蓝图，不进二进制。真正生成代码的地方叫实例化点（Point of Instantiation）：通常就在使用该特化的那个翻译单元里。

显式实例化什么时候用

场景做法代价
类型集合封闭（7 种整数）定义放 .cpp + template bool convert<int>(…);新类型要手写一行，否则链接失败
头文件已公开、只想少编几次头文件 extern template class vector<string>;必须有一个 TU 真正实例化
任意用户类型别显式实例化，定义必须可见重复实例化靠链接去重

隐式 vs 显式

隐式显式
定义位置必须在头文件可见可以藏进 .cpp
时机用到才生成（类还惰性到成员）你写那一行就生成
编译每个 TU 可能重复一个 TU 一次
灵活性任意类型只限列出的类型

两条潜规则

惰性：类模板只实例化被调用的成员。去重：同一特化在 N 个 TU 里是弱符号，链接留一份——这既是 ODR 能成立的原因，也是编译变慢的原因。

本节讲的是模板为什么让编译变慢。真要把一个大仓库的构建时间压下来，是一整套工程活： 用 -ftime-trace 定位瓶颈、IWYU 裁头文件、PCH、ccache/sccache、Unity Build，以及 Modules 到底能省多少—— 见 大型 C++ 工程化 §11 构建性能工程； Modules 的 BMI、partition、FILE_SET CXX_MODULES 与迁移策略在同篇 §5。

  • 类型集合封闭 → 定义进 .cpp + 显式实例化

9.1 SFINAE

Substitution Failure Is Not An Error：替换失败时该候选被默默丢掉，编译器换下一个重载。不是「报错再恢复」，是「根本没进集合」。

❌ enable_if 年代

template<typename T, enable_if_t<is_integral_v<T> && !is_same_v<T,bool>, int> = 0> T next(T x);

约束藏在默认模板实参里，失败时打印「no matching function」加几十行候选。

✅ concept

template<Integer T> T next(T x); 或 template<typename T> requires Integer<T> T next(T x);

约束是签名的一部分，失败停在调用点。

9.2 Concepts：把错误提前

concept 是具名谓词。检查发生在调用点，而不是实例化钻到 vector 内部第 30 层才爆。

template <typename T>
concept Integer = std::integral<T> && !std::same_as<T, bool>;

template <Integer T>
T next(T x) { return ++x; }

template <typename T>
  requires Integer<T>
T twice(T x) { return x + x; }

9.2b requires 表达式的四种要求

requires (形参) { ... } 花括号里的每一行叫一个要求（requirement），一共四种。区分它们不是语法洁癖——第四种写错了会静默恒真，是 concept 里最阴的一个坑。

形态写法检查什么
简单要求a + b;只检查这个表达式能不能通过编译，不求值、不管类型
类型要求typename T::value_type;这个类型名存在且有效
复合要求{ a + b } noexcept -> std::convertible_to<T>;表达式合法 + 不抛异常 + 返回类型满足给定 concept，三件事一起
嵌套要求requires Integer<typename T::value_type>;把里面当成布尔常量表达式求值，必须为 true
最容易踩的是第四种漏写 requires：写成 Integer<typename T::value_type>;（少了前导 requires）就退化成了简单要求——它只问「这个表达式合法吗」，而 Integer<X> 作为一个表达式当然合法，无论它求值是 true 还是 false。于是这条约束永远通过，你以为加了检查，其实什么都没检查。同理，sizeof(T) == 4; 作为简单要求也是恒真的。凡是想「求值一个布尔条件」，前面必须有 requires。

另外那个让人困惑的 requires requires 双写也就解释得通了：第一个是约束子句（引出一个布尔表达式），第二个是requires 表达式（那个布尔表达式本身）。写成具名 concept 就不需要双写——这也是推荐做法。

9.2c 约束的偏序：为什么你的重载没被选中

两个重载都满足约束时，编译器选更受约束的那个，这个过程叫 subsumption（包含）。它让「通用版 + 特化版」不用再靠 tag dispatch 来消歧。但它有一条极其反直觉的规则，不知道就会撞墙。

还有一条同样重要：std::enable_if 完全不参与偏序。它只是 SFINAE 的开关，编译器无从比较两个 enable_if 谁更严格，所以老代码里只能靠优先级 tag、int/... 形参这类技巧人为排序。这是从 SFINAE 迁到 concept 最实在的一个收益，也是迁移时不能只做文本替换的原因——换成 concept 之后重载决议的行为会真的改变。

SFINAE 老写法concept 新写法迁移时要当心
enable_if_t<is_integral_v<T>> 在返回类型里template <std::integral T>约束进了签名，函数指针类型和 ABI 可能随之改变
void_t 探测成员requires { t.foo(); } 复合要求void_t 只测「存在」，复合要求还能顺带约束返回类型
优先级 tag（overload<3>）人为排序concept refinement 自动偏序只有具名 concept 才有偏序，见上图
static_assert 在函数体里挡约束写在签名上static_assert 挡不住重载决议——它已经选中你了才报错

9.7 Two-Phase Name Lookup

名字查找分两阶段。MSVC 曾经不严格，GCC/Clang 上才爆的「找不到成员」几乎都栽在这儿。

9.8 ADL 与 Hidden Friend

规则会去哪些命名空间找
实参类型自身ns::Box → 找 ns
基类直接/间接基类所在命名空间
模板实参vector<ns::Box> 也找 ns
外围类嵌套类跟着外层走

std::cout << x 能工作，是因为 ADL 在 x 的命名空间找到了 operator<<。类内 friend 定义的运算符只能经 ADL 找到（Hidden Friend）：不污染命名空间、不参与无关重载决议、编译更快。禁用 ADL：(::std::move)(x)；惯用 swap：using std::swap; swap(a,b);。

9.8b 三个真实事故：查找规则是怎么咬人的

现象根因修法
某个命名空间里的模板劫持了全站调用在 ns 里写了无约束的 template <class T> void swap(T&, T&)。只要实参沾一点 ns，ADL 就把它拉进候选集，且因为完全泛化常常赢过 std::swap命名空间级的泛型函数必须加约束（concept 或 SFINAE）；能做成 hidden friend 就做成 hidden friend
给 enum 写的 operator<< 死活不被调用ADL 只看实参类型所属的命名空间。运算符定义在了别处（比如全局或某个 util 命名空间），而 enum 在 ns 里运算符跟着它操作的类型走，定义在同一个命名空间里
在 GCC/Clang 上一堆 error: 'init' was not declared，MSVC 上却一直编得过MSVC 历史上不做严格的两阶段查找，依赖基类的成员在第一阶段就能看见。GCC/Clang 严格按标准，看不见写 this->init() 或 Base<T>::init()；MSVC 上加 /permissive- 让它也严格，把问题提前暴露
第三行是跨平台项目里最高频的一类「只在某个编译器上炸」。它的麻烦之处在于方向是单向的：先在 MSVC 上开发、再移植到 GCC，会一次性冒出几十个错误；反过来则几乎无感。所以多编译器项目应当从第一天就打开 /permissive-，而不是等移植时集中还债。同理，typename 与 template 消歧关键字漏写也属于这一类。

再往下一层——名字查找、inline、链接性与 ODR 违规如何合起来制造「链接通过但运行期读到垃圾」——属于编译链接的范畴，见 编译与链接 · 面试深度专题（含符号可见性、弱符号与静态库链接顺序）。

9.13 高频面试题 Q&A

点击每道题展开参考答案（先自测，再对照）。

  1. 基础模板代码为什么必须放在头文件？

    编译器在实例化时需要看到模板的完整定义。C++ 编译是逐 TU 独立进行的，链接期不能再生成代码。如果定义放 .cpp 里，其他 TU 看不到就无法实例化 → 链接错误。

    例外：使用 explicit instantiation 在 .cpp 内预先实例化所有用到的类型，可以把定义留在 .cpp — 常用于减少编译依赖与编译时间。

  2. 基础typename 和 class 在模板参数里的区别？

    作为模板参数声明时，二者完全等价：template<class T> ≡ template<typename T>。

    但在模板体内，必须用 typename 指示"这是一个依赖类型"：

    template<typename T>
void f() {
    typename T::iterator it;  // 必须加 typename！
    // 否则编译器以为 T::iterator 是静态成员
}

    C++20 起，许多"明显是类型"的场合可省略 typename。

  3. 高级两阶段名字查找（Two-Phase Name Lookup）是什么？

    ① 第一阶段（模板定义时）：查找非依赖名字（与模板参数无关的）。
    ② 第二阶段（实例化时）：查找依赖名字（涉及模板参数的）——结合 ADL 参数依赖查找。

    template <typename T>
void f(T t) {
    g(42);    // 第一阶段：必须此时可见的 g
    g(t);     // 第二阶段：实例化时根据 T 的命名空间再查
}

    MSVC 传统上不严格实施两阶段查找（更宽容），导致跨编译器移植时会暴露问题 — 面试常考。

  4. 中级为什么函数模板不能偏特化？

    语言设计决定：函数偏特化会与函数重载冲突，二者的决议规则不同（偏特化按特殊性，重载按参数匹配）。标准委员会选择让函数重载承担这个角色。

    替代方案：

    • 用函数重载（最常见）
    • 用类模板偏特化 + 静态成员函数包装
    • 用 if constexpr (C++17) 在函数内分派
    • 用 Concepts 约束 (C++20)
  5. 中级万能引用（Forwarding Reference）与右值引用的区别？ 
    void f(T&& x);               // 右值引用：T 是具体类型
template<typename T>
void g(T&& x);               // 万能引用！因为 T 是模板参数

auto&& x = foo();             // 万能引用 (auto&&)

    关键是引用折叠规则：T& && → T&，T&& && → T&&。

    • 传左值 → T 被推导为 T& → 参数类型 T&
    • 传右值 → T 被推导为 T → 参数类型 T&&

    必须配合 std::forward<T>(x) 才能正确转发。用 std::move 转发万能引用会把左值变右值 — 高危错误！

  6. 中级std::vector<bool> 为什么被称为"C++ 的污点"？

    它是 vector 的全特化，为节省空间用位压缩（1 个 bit 存 1 个 bool）。代价：

    • operator[] 返回的是代理对象 reference，不是真正的 bool&
    • 无法取 bool* 地址：&v[0] 编译错误
    • 不满足 Container 接口概念 → 泛型代码失效

    替代：std::deque<bool>、std::vector<char>、std::bitset、std::array<bool, N>。

  7. 基础if constexpr 和普通 if 的区别？

    关键差异：if constexpr 在编译期选择分支，未选中的分支不参与模板实例化。

    template<typename T>
auto getValue(T t) {
    if constexpr (std::is_pointer_v<T>) {
        return *t;       // 非指针类型时此分支不编译
    } else {
        return t;
    }
}
// 普通 if 的话，两个分支都要编译 → *int 直接报错

    替代了 C++17 前的 tag dispatch 和 SFINAE 方案，代码可读性飞跃。

  8. 高级模板编译慢怎么办？（大厂面试重点）
    1. 前置声明 + PImpl — 减少头文件依赖
    2. extern template — 避免重复实例化
    3. 显式实例化 — 把模板定义搬进 .cpp
    4. 减少递归深度 — 用 fold expression、pack indexing 替代递归模板
    5. 预编译头 (PCH) — GCC -include、MSVC /Yc /Yu
    6. Module (C++20) — 取代头文件的未来方案
    7. 分布式编译 — distcc、icecream、sccache
    8. unity build — 合并多个 cpp 成一个编译单元
