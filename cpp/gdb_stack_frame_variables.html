GDB 调试 C++ · 系列 03 / 06

Stack / Frame / Variable：如何分析 C++ 调用过程

程序停下来之后，第一个要回答的问题往往不是「这里是什么」，而是「它是怎么走到这里的」。这一篇把 GDB 里最常用、也最能救命的一组能力讲透：用 bt 看调用链、用 frame/up/down 在栈帧间穿梭、用 print/info locals/info args 检查变量 —— 并专门处理 C++ 特有的指针、引用、STL 容器怎么在 GDB 里看清楚。

01

从「停在哪」到「怎么走到这的」

构造一条清晰的调用链

用一段能直接编译运行的递进调用来贯穿本篇：

// call_chain.cpp — g++ -g -O0 call_chain.cpp -o call_chain
#include <iostream>
#include <string>
#include <vector>
#include <memory>

struct User {
    int id;
    std::string name;
};

int baz(int n)            { return n * n; }
int bar(int n)            { return baz(n) + 1; }
int foo(int n)            { return bar(n) - 1; }

int main() {
    User u{7, "Kavin"};
    User* p = &u;
    std::vector<int> v{10, 20, 30};
    auto sp = std::make_shared<User>(User{99, "SP"});
    int r = foo(5);        // main → foo → bar → baz
    std::cout << r << " " << p->name << " " << v[0] << " " << sp->name << "\n";
}

在最深的 baz 打断点，让程序停在调用链最底部：

$ gdb ./call_chain
(gdb) break baz
(gdb) run
Breakpoint 1, baz (n=5) at call_chain.cpp:12
02

bt / backtrace：一眼看清调用链

调试里被敲得最多的命令，没有之一

bt（backtrace 的缩写，等价还有 where）打印当前线程从崩溃点/暂停点一路回溯到 main 的完整调用链。停在 baz 时：

(gdb) bt
#0  baz (n=5) at call_chain.cpp:12
#1  0x... in bar (n=5) at call_chain.cpp:13
#2  0x... in foo (n=5) at call_chain.cpp:14
#3  0x... in main () at call_chain.cpp:22

一行就还原了整个「谁调用了谁」：

main()
foo(5)
bar(5)
baz(5) ← 现在停在这里（#0）
常用变体
  • bt：完整调用栈；
  • bt 3：只看最里面 3 层（栈很深时）；
  • bt -3：只看最外面 3 层；
  • bt full：每一帧连同它的局部变量一起打印（信息量大，排查利器）。
看到 bt 之后该怎么分析

bt 回答两个关键问题：①「现在在哪个函数？」（看 #0）②「是经过怎样一条路径调过来的？」（看 #0 往下）。崩溃调试里，#0 是崩溃发生的现场，往下逐层是它的调用来源 —— 真正的 bug 未必在 #0，常常在某一层传进来的错误参数里。这条链就是你后面「逐帧排查」的路线图。

03

#0 #1 #2 到底是什么

这些编号不是「行号」，是「栈帧编号」

每一层函数调用在栈上都占一块栈帧（stack frame）。GDB 给它们编号，#0 永远是最内层（当前正在执行的那一帧），编号越大越靠近 main（越「外层/越早」）。

栈帧编号（frame number）
#0 baz最内层 · 当前帧
#1 barbaz 的调用者
#2 foobar 的调用者
#3 main最外层 · 起点
关键：编号是「层级」不是「时间」

很多人误以为 #0 是「最先执行的」。恰恰相反：#0 是最后进入、最内层、当前正在跑的那个函数；#3（main）才是最早开始的。这正是栈「后进先出」的体现 —— 最后压栈的帧编号最小、离栈顶最近。GDB 里所有「查看变量」的命令，默认都作用在#0 这一帧，除非你切换过去。

为什么栈能这样被逐层回溯出来？因为每一帧都保存了「返回地址」和上一帧的帧指针，GDB 顺着这条链一路往回爬 —— 底层机制见 CALL / RET 深入。

04

frame / up / down：在栈帧间穿梭

切到哪一帧，「当前上下文」就变成哪一帧

命令作用
frame 2 / f 2直接切到 #2 帧（foo）
up往「外层」走一帧（#0→#1→#2…，朝 main 方向）
up 2一次往外走 2 帧
down往「内层」走一帧（朝 #0 方向）
info frame打印当前帧的底层细节：帧地址、返回地址、保存的寄存器位置
 
(gdb) up                 # 从 baz(#0) 切到 bar(#1)
#1  0x... in bar (n=5) at call_chain.cpp:13
13      int bar(int n) { return baz(n) + 1; }
(gdb) frame 3            # 直接跳到 main
#3  main () at call_chain.cpp:22
(gdb) info args          # 现在看的是 main 的上下文
为什么要切帧

切换栈帧的意义在于：把「当前上下文」搬到你想检查的那一层。停在 baz 时想看 main 里那个 User u？必须先 frame 3，否则 p u 会因为「当前帧（baz）里没有 u」而报错。这是新手最常见的困惑 —— 变量明明存在却说找不到，多半是站错帧了。

info frame 展示的是这一帧的「解剖图」：帧基址（对应 RBP）、栈顶（RSP）、返回地址存在哪、哪些被调用者保存寄存器被压在这一帧里。这些字段与 02 篇栈帧里讲的一一对应，第 04 篇会结合寄存器进一步展开。

05

info locals / info args：看局部变量与参数

一次性把当前帧的「家底」倒出来

(gdb) frame 3            # 切到 main
(gdb) info args          # main 没参数，显示 No arguments.
(gdb) info locals        # main 的所有局部变量
u = {id = 7, name = "Kavin"}
p = 0x7fffffffe010
v = std::vector of length 3, capacity 3 = {10, 20, 30}
sp = std::shared_ptr<User> (use count 1, weak count 0) = {...}
r = 0
命令看什么什么时候用
info args当前帧的函数参数怀疑「是不是传进来的参数就错了」
info locals当前帧的所有局部变量快速扫一遍这个函数内部的状态
调试直觉

拿到崩溃现场后的高效动作：bt 看链 → 逐帧 up，每到一帧就 info args + info locals 扫一眼，找「哪一层的数据开始不对劲」。参数在这一层还是对的、到下一层就错了，问题就锁定在这两层之间。

06

print / display：查看任意表达式

不止看变量，还能算表达式、调函数、改值

(gdb) print n            # p n —— 查看变量 n
$1 = 5
(gdb) p n * n           # 直接算表达式
$2 = 25
(gdb) p/x 255           # 以十六进制显示：$3 = 0xff
(gdb) p sizeof(User)    # 甚至能算 sizeof
(gdb) set var n = 42    # 修改运行中的变量值

print 的表达式能力非常强：算术、比较、解引用、成员访问、数组下标、类型转换、甚至在被调试进程里调用一个函数（p some_func(3)）。p/FMT 可指定输出格式：/x 十六进制、/d 十进制、/t 二进制、/c 字符、/a 地址、/f 浮点。

display：每次停下来自动打印

(gdb) display n          # 之后每次暂停都自动显示 n
(gdb) display/x sum      # 带格式的自动显示
(gdb) info display       # 查看已注册的自动显示项
(gdb) undisplay 1        # 取消 1 号自动显示
print vs display

print 是「看一次」；display 是「盯着看」 —— 单步调试循环时，把关心的几个变量 display 出来，之后每走一步它们的最新值都自动刷新，省去反复敲 p。

07

C++ 对象、指针、引用怎么看

C++ 的间接层多，看变量要先想清楚「你在看指针还是它指向的东西」

(gdb) frame 3
(gdb) p u                # 整个对象
$1 = {id = 7, name = "Kavin"}
(gdb) p u.id             # 成员
$2 = 7
(gdb) p u.name
$3 = "Kavin"

(gdb) p p                # p 是指针 → 打印的是地址
$4 = (User *) 0x7fffffffe010
(gdb) p *p               # 解引用 → 打印指向的对象
$5 = {id = 7, name = "Kavin"}
(gdb) p p->name           # 通过指针访问成员
$6 = "Kavin"
指针调试的第一性原理

p ptr 给你的是地址，p *ptr 给你的是内容。崩溃排查时这两步缺一不可：先 p ptr 看地址是否是 0x0（空指针）或一个明显不合理的值（野指针）；地址看起来正常，再 p *ptr 看内容是否是垃圾（可能是悬垂指针指向已释放内存）。第 06 篇会把这套流程用在真实崩溃上。

数组与引用

(gdb) p arr[0]           # 数组下标
(gdb) p *arr@5           # 把 arr 起始的 5 个元素当数组打印（@ 语法）
(gdb) p ref              # 引用在 GDB 里透明：直接显示被引用对象

@ 是很实用的技巧：p *data@len 能把一段裸内存/动态数组按 len 个元素打印出来，弥补「指针不知道自己指向多少元素」的问题。

08

STL 容器调试：vector / string / 智能指针

现代 GDB 带 pretty-printer，STL 看起来很友好 —— 但要知道它靠什么

现代 GDB 通常随发行版附带一套 Python pretty-printer（libstdc++/libc++ 的打印插件），它把 STL 对象的内部结构翻译成人类可读形式：

(gdb) p v
$1 = std::vector of length 3, capacity 3 = {10, 20, 30}
(gdb) p v[1]             # 甚至支持下标
$2 = 20

(gdb) p str
$3 = "hello world"

(gdb) p up               # unique_ptr
$4 = std::unique_ptr<User> = {get() = 0x55...}
(gdb) p *up.get()        # 取出被管理的对象

(gdb) p sp               # shared_ptr：能看到引用计数
$5 = std::shared_ptr<User> (use count 1, weak count 0) = {get()=0x55...}
类型看什么技巧
std::string直接显示字符串内容乱码常意味着对象已损坏/越界
std::vectorlength / capacity / 元素p vec[i]、p *vec._M_impl._M_start@n
unique_ptr底层裸指针p *ptr 或 p *ptr.get()
shared_ptruse count / weak count排查循环引用、生命周期问题的关键
适用条件：pretty-printer 不一定总在

友好的 STL 显示依赖 pretty-printer 被正确加载。若你在精简容器、交叉编译目标、或标准库版本不匹配的环境里调试，pretty-printer 可能缺失，此时 p v 会暴露 std::vector 的原始内部字段（_M_start / _M_finish）。这时改用底层办法：p *v._M_impl._M_start@(v._M_impl._M_finish - v._M_impl._M_start) 手动展开。可用 info pretty-printer 查看是否加载。

shared_ptr 的 use count 是宝藏

排查「对象被提前释放」或「循环引用内存不降」时，p sp 显示的 use count 直接告诉你现在有几个 shared_ptr 持有它。计数异常偏高 → 可能循环引用；该释放却仍 > 0 → 有地方多持有了一份。配合 智能指针深度指南一起看。

09

核心结论 + 常见误区

  • bt 还原调用链：#0 是当前/最内层，编号越大越靠近 main。
  • frame/up/down 切换当前帧；看不到变量常因为「站错帧」。
  • info args / info locals 一次性倒出当前帧的参数与局部变量。
  • print 看一次、display 持续盯；p *ptr 看内容、p ptr 看地址。
  • STL 靠 pretty-printer 友好显示，缺失时需手动展开内部字段。

❌ #0 是最先执行的函数。 恰好相反，#0 是最内层、最后进入、当前正在跑的帧；main 编号最大。

❌ 变量查不到就是没这个变量。 多半是当前帧不对，frame N 切到定义它的那一层再看。

❌ p ptr 就能看到对象。 那只是地址；要看内容得 p *ptr。

❌ bt 一定能拿到完整调用栈。 优化内联、缺帧指针、栈被破坏时，bt 可能不完整或错乱（第 06 篇详述）。

10

面试问题

基础bt（backtrace）是什么？

打印当前线程从暂停/崩溃点回溯到 main 的完整调用链，每一层是一个栈帧。它回答「现在在哪个函数」以及「经由怎样的调用路径到达这里」，是崩溃排查的第一步。

基础bt 里的 #0 #1 #2 是什么意思？

栈帧编号。#0 是最内层、当前正在执行的帧，编号越大越靠外、越接近程序起点 main。它体现栈的 LIFO：最后压栈的帧编号最小。

基础如何查看当前函数的局部变量和参数？

info locals 看当前帧所有局部变量，info args 看函数参数；单个变量或表达式用 print/p。注意这些命令都作用在「当前帧」，必要时先用 frame N 切换。

原理停在最内层函数，怎么查看调用者里的变量？

用 up 或 frame N 切到调用者那一帧，「当前上下文」随之改变，再 info locals/p 变量 即可。不切帧直接看会报「找不到变量」，因为它不在当前帧作用域内。

原理p ptr 和 p *ptr 有什么区别？崩溃排查怎么用？

p ptr 打印指针本身（地址），p *ptr 打印它指向的内容。排查时先看地址是否为 0x0（空指针）或异常值（野指针），地址正常再看内容是否为垃圾（悬垂指针）。

进阶GDB 怎么把 std::vector 显示成可读形式？没有这种显示时怎么办？

靠标准库配套的 Python pretty-printer 把内部结构翻译成 length/capacity/元素。若 pretty-printer 缺失（交叉编译、版本不匹配等），需手动展开：p *v._M_impl._M_start@N。可用 info pretty-printer 确认是否加载。

进阶用 GDB 怎么排查 shared_ptr 循环引用或提前释放？

p sp 能看到 use count / weak count。use count 异常偏高、内存不释放，往往是循环引用（应改用 weak_ptr 打破环）；对象本应存活却 use count 归零导致悬垂，则说明持有关系设计有误。
