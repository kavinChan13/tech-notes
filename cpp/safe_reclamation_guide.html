用户态安全内存回收

写一个无锁链表，难的从来不是怎么把节点摘下来——一个 CAS 就够了。难的是摘下来之后什么时候才能 delete：此刻可能还有三个读者握着指向它的指针，而你无法询问它们，因为一问就不是无锁了。这个问题有专门的名字：安全内存回收（Safe Memory Reclamation, SMR），它是无锁数据结构从「能跑」到「敢上线」之间的全部距离。

01

摘下来之后，什么时候才能 delete

无锁算法的教科书章节通常在 CAS 成功那一行就结束了，而真正的工程问题从下一行开始

把一个节点从无锁链表里摘掉，代码大概是这样：head.compare_exchange_weak(p, p->next)。CAS 成功了，链表里再也找不到 p，从数据结构的角度它已经不存在。于是很自然地写下一行 delete p;——这一行就是 bug。

因为「链表里找不到它」和「没有人正在用它」是两件完全不同的事。另一个线程可能在你 CAS 之前的半纳秒读到了 head，此刻正握着同一个 p，准备解引用。它没有做错任何事：它读到的确实是当时的合法状态。

安全内存回收（SMR）：在无锁数据结构中，确定「一块已被逻辑移除的内存何时不再可能被任何线程访问」的机制。它必须自己是无锁的——如果靠加锁来判断，整个数据结构的无锁性就白费了。
图书馆把一本书从检索目录里划掉了，这一步瞬间完成、不影响任何人借书。但此刻阅览室里还有三个人正捧着这本书在读。管理员不能因为「目录里已经没有它」就把书扔进碎纸机——他得先知道最后一个读者什么时候放下它。而阅览室不允许广播喊话（那就是加锁），所以只剩两种办法：要读就在门口的登记板上写下书名（Hazard Pointer），或者按批次清场，只销毁上上一批之前就没人碰的书（Epoch / RCU）。本文就是这两种办法。

1.1 一条能复现的 UAF 时间线

先把竞态画清楚。下面只有两个线程、四个时刻，没有任何复杂结构，但它足以解释后面所有机制存在的理由。

1.2 摘除与回收是两个阶段

看清上图之后，结论几乎是被逼出来的：一次删除必须拆成两个在时间上分离的阶段。

阶段做什么完成的判据谁能做
① 摘除（unlink / retire）一次 CAS 让节点从数据结构里不可达；然后把它挂进一个「待回收」列表CAS 成功，此刻立即完成任何写者，无锁
② 回收（reclaim / free）真正调用 delete / free，把内存还给分配器所有在摘除之前就开始的读者都已结束需要 SMR 机制来判定

两个阶段之间的时间差，就是宽限期（grace period）。所有 SMR 方案的差别，本质上只有一句话：它用什么办法判断宽限期结束了。Hazard Pointer 让每个读者显式登记自己正在用哪几个指针，写者去查这张表；Epoch 和 RCU 则不查具体指针，而是判断「所有线程都已经离开过临界区一次」——后者粒度粗得多，但读者侧几乎不花钱。

还有一个必然推论：回收一定是延迟且批量的。每摘一个节点就去跑一次判定，开销会高到不可接受，所以所有实现都是攒一批再判一次。这直接决定了「内存用量会比逻辑用量高一截」，而这一截有没有上界，是 §5 选型表里最关键的一列。

1.3 它和 ABA 是两个问题

这两件事被混为一谈的频率高得惊人，面试里几乎每次都要澄清一遍。它们都出现在无锁代码里，都跟「节点被删了」有关，但性质完全不同。

ABA 本身的时间线推演与四种解法对照在 高性能通信编程 §3.2，那里还有 §3.1 的 Treiber 栈 + CAS 实现与 §2 逐行标注内存序的 SPSC 环；内存序的选择依据、三级进度保证与 Michael-Scott 队列的选型见 C++ 内存模型 §14。本文不重复这些内容，只处理它们之后剩下的那个问题：什么时候能 delete。
02

Hazard Pointer：让读者举手

最直接的思路——既然不能问读者，就让读者主动登记

Hazard Pointer（Maged Michael，2004）的想法朴素得几乎像作弊：既然写者无法询问读者「你在用哪些指针」，那就让每个读者把答案预先写在一块所有人都能读到的地方。写者要 delete 之前先扫一遍这块地方，名单上有的就跳过。

一个「地方」就是一个 hazard slot：一个单写多读的原子指针，归某个线程独占写、所有人可读。线程同时要保护几个指针，就占几个 slot——Michael-Scott 队列的出队最多同时保护 2 个，Harris 链表删除要 3 个。

2.1 读者侧的四步循环

读者要做的不是「读一个指针」，而是「读一个指针并确保它在我用完之前不会被释放」。这两件事无法一步完成，所以必然是一个循环。

// 读者：把 src 里的指针安全地取出来
// 四步缺一不可，第 ③ 步是整个算法的支点
template <class T>
T* protect(std::atomic<T*>& src, hazard_slot& hp) {
    T* p = src.load(std::memory_order_acquire);
    for (;;) {
        // ① publish：向全世界宣告「我要用 p，别删它」
        hp.ptr.store(p, std::memory_order_release);

        // ② 屏障：禁止把 ① 的写重排到 ③ 的读之后。
        //    x86 上这是唯一真正花钱的一条指令（约 20–40 周期）。
        //    去掉它，store-load 重排会让 ③ 的验证形同虚设。
        std::atomic_thread_fence(std::memory_order_seq_cst);

        // ③ 重新验证：src 还是 p 吗？
        T* p2 = src.load(std::memory_order_acquire);
        if (p2 == p) return p;   // 是 → p 此刻仍可达，写者的 scan 必然看得见 ①
        p = p2;                  // 否 → 可能已被摘除，丢掉重来
    }
}

// 使用方：hazard slot 必须在最后一次解引用之后才清
void consume(std::atomic<Node*>& head) {
    auto& hp = tls_slot(0);
    Node* p = protect(head, hp);
    if (p) do_work(p->payload);            // ④ 这段期间 p 一定活着
    hp.ptr.store(nullptr, std::memory_order_release);  // ⑤ clear，越早越好
}

2.2 少了重新验证就整个失效

上图下半部分值得再用文字说一遍，因为它是这套机制里唯一不直观的一步，也是自己动手实现时最常省掉的一步——省掉之后代码照样跑，测试照样过。

论证只有两句话。写者的顺序是固定的：先摘除（改 src），后 scan。那么读者在 publish 之后重读 src，只有两种结果：

  • 读到的还是 p：说明此刻摘除尚未发生。而摘除在 scan 之前，所以 scan 一定发生在这之后——读者的 publish 已经落在 scan 的可见范围内，p 会被跳过。安全。
  • 读到的不是 p：说明摘除可能已经发生，读者无法判断自己的 publish 有没有赶上，于是不赌，丢弃重来。

关键在于「先摘除后 scan」与「先 publish 后重读」这两组顺序必须都是真的。前者靠写者代码的书写顺序加上 release/acquire；后者就是 ② 那条 seq_cst 屏障——store 后面跟一个 load，恰好是 x86 TSO 唯一允许重排的组合。所以这条屏障不是可有可无的保险，它是本算法在 x86 上唯一必须付的那笔钱。在 ARM 这类弱序机器上更是如此。

这也是为什么不要自己手写 hazard pointer。去掉屏障、或把它写成 release，在 x86 上跑百亿次都可能不出事，换到 aarch64 服务器上第二天就崩。用 folly 或等 C++26（§6）。自己写的唯一正当理由是学习，而学习的产物不应该进生产。

2.3 写者侧：retire 与 scan

写者侧简单得多，只有一个设计决策：什么时候去 scan。答案是攒够一批再去，因为 scan 的成本与线程数成正比，而摘除的次数与业务量成正比。

// 摘除后不 delete，先进本线程的待回收列表
void retire(Node* p) {
    auto& bag = tls_retired();
    bag.push_back(p);
    if (bag.size() >= kThreshold)   // kThreshold 取 2H，H = 全局 slot 总数
        scan();
}

void scan() {
    // ① 快照全体 hazard slot —— 只读遍历，不需要任何锁
    std::vector<void*> guarded;
    for (hazard_slot* s = g_slots.load(std::memory_order_acquire); s; s = s->next)
        if (void* h = s->ptr.load(std::memory_order_acquire))
            guarded.push_back(h);
    std::sort(guarded.begin(), guarded.end());

    // ② 分流：名单上的留到下一轮，其余立刻释放
    auto& bag = tls_retired();
    std::vector<Node*> keep;
    for (Node* p : bag) {
        if (std::binary_search(guarded.begin(), guarded.end(), p)) keep.push_back(p);
        else delete p;                    // 此刻没有任何线程登记过它
    }
    bag.swap(keep);
}

注意 scan() 里没有任何同步原语：它只是把别人的 slot 读一遍。一个线程正好在这期间 publish 了某个指针也不要紧——若那个指针指向的节点已被摘除，该读者自己会在重新验证那一步放弃。整套机制的正确性全部压在 §2.2 那两句话上。

2.4 摊销复杂度与 slot 数量

阈值取 R = 2H 不是随手写的常数，它是让摊销成本降到 O(1) 的最小选择。一次 scan 的成本是 O(H) 收集加上 O(R) 查表；而由于 hazard slot 总共只有 H 个，最多护住 H 个节点，所以这一批 R 个里至少有 R − H = H 个会被真正释放。用 O(R) 的成本换至少 H 次释放，摊销到每个节点就是常数。

参数含义调大的后果调小的后果
K（每线程 slot 数）由算法决定，不是调优项——不够用就写不出正确代码：MS 队列出队要 2，Harris 链表删除要 3
H = N·K（全局 slot 总数）scan 要遍历的长度scan 变慢，内存上界抬高不可调，由线程数决定；线程池规模因此直接影响内存上界
R（触发阈值）攒多少个才 scanscan 更稀疏，内存峰值更高，但 CPU 更省小于 H 时可能整批都被护住，scan 空跑，退化成每次 retire 都 O(H)

实践中真正的性能问题不在 scan，而在读者侧：每一次解引用都要付一条 seq_cst 屏障。遍历一条 100 节点的链表就是 100 条屏障，在 x86 上大约几千个周期。这就是 Hazard Pointer 的定位——读延迟确定但不低，换来一个与运行时行为无关的内存上界。如果你的读路径是「查一次哈希桶、拿到值就走」，这个代价可以接受；如果是「长链表扫描」，它会主导整个开销，此时 EBR 或 RCU 明显更合适。

03

Epoch-Based Reclamation

不问「你在用哪个指针」，只问「你还在临界区里吗」

Hazard Pointer 的成本几乎全部来自精确性：它要逐个指针登记。EBR 走另一条路——把问题粗粒度化。它不关心你在用哪个节点，只关心你有没有处在「可能持有任何节点指针」的状态里。这样一来，读者只需要在临界区的进出两端各写一次本地变量，临界区内部解引用完全免费。

3.1 全局 epoch 与 pin / unpin

机制由三样东西构成：一个全局 epoch 计数器；每个线程一个 local epoch（未进入临界区时标记为「离线」）；每个 epoch 一条 limbo list（待回收袋子）。

constexpr uint64_t kOffline = ~0ull;
std::atomic<uint64_t> g_epoch{0};          // 只需要三个取值：mod 3

struct Local {
    std::atomic<uint64_t> epoch{kOffline};
    std::vector<Garbage>  limbo[3];        // 按 epoch mod 3 分袋
};

// 进入临界区：宣告「我在 epoch e 里活动」
void pin(Local& le) {
    uint64_t e = g_epoch.load(std::memory_order_acquire);
    le.epoch.store(e, std::memory_order_relaxed);
    // 临界区内的读不能提前到这条 store 之前，否则我还没登记就已经在读了
    std::atomic_thread_fence(std::memory_order_seq_cst);
}

// 离开临界区：一条 release store，仅此而已
void unpin(Local& le) {
    le.epoch.store(kOffline, std::memory_order_release);
}

// 回收方：只有确认「在线的线程全都已经到达当前 epoch」才能推进
bool try_advance() {
    uint64_t e = g_epoch.load(std::memory_order_acquire);
    for (Local* le : g_threads) {
        uint64_t x = le->epoch.load(std::memory_order_acquire);
        if (x != kOffline && x != e) return false;   // 有人还留在旧 epoch
    }
    if (!g_epoch.compare_exchange_strong(e, e + 1, std::memory_order_acq_rel))
        return false;
    // 推进成功 ⇒ (e+1) % 3 那条袋子里的垃圾，已经不可能被任何线程访问
    free_bag((e + 1) % 3);
    return true;
}

对比一下代价结构就能看出它和 HP 的分水岭：HP 的开销正比于解引用次数，EBR 的开销正比于临界区次数。一次 pin 之后遍历一万个节点，EBR 只付一条屏障，HP 要付一万条。这是数量级的差距，也是为什么读多写少的场景几乎都选 EBR 系。

3.2 为什么是三个 epoch

几乎每个 EBR 实现（crossbeam、Fraser 的原始版本、各种 C++ 移植）都用三个 epoch 轮转。两个为什么不行，是这一节唯一值得讲清楚的问题。

换个说法：在 epoch e 里 retire 的节点，可能被任何在 e 之前就 pin 住的线程访问。要确保这些线程全部离开，全局 epoch 必须推进两次——一次证明「所有人都已到达 e」，再一次证明「所有人都已离开 e」。两次推进期间，e 那条袋子必须原样保留，同时新的 e+1、e+2 又各自要有地方放新垃圾。三条，一条都不能少。

3.3 致命弱点：一个人卡住全场

现在来看 EBR 的代价，它非常尖锐：只要有一个线程 pin 住不 unpin，全局 epoch 就永远推进不了，所有线程的所有待回收内存无限堆积，直到 OOM。

而「pin 住不放」在真实系统里一点都不罕见——它不需要死锁，只需要一次倒霉：临界区里不小心调了一次 malloc 而恰好触发了 mmap；被操作系统抢占后调度器半天没轮到它；跑在一个超卖的容器里被 cgroup 限流；甚至只是有人在临界区里加了一行日志，而那行日志写的是慢速磁盘。

缓解手段存在但都不彻底：限制临界区长度（靠纪律，会漂移）；给 limbo list 设水位，超了就退化成阻塞等待甚至 abort（把内存问题换成可用性问题）；crossbeam 式的「pin 计数超过阈值就强制尝试推进」（只是提高推进频率，卡住的线程照样卡住）。真正的结论是：这个弱点不能被修掉，只能被接受或者换方案。

「回收开销无上界」这一点让 EBR 严格来说不是 lock-free——虽然读写路径都是无锁的，但内存回收这一步依赖所有线程的进展。这与 C++ 内存模型 §14 里讲的三级进度保证是同一套语言：一个算法可以在操作层面 lock-free，而在空间层面 blocking。评审无锁设计时，这两件事要分开问。
04

用户态 RCU（liburcu）

同一个思想，但静止点得自己造出来

RCU 和 EBR 是近亲：都不追踪具体指针，都靠「所有线程都已离开过临界区一次」来判定宽限期。差别在工程形态——RCU 把这件事做成了一个通用库，并且提供了一个 EBR 通常不给的接口：synchronize_rcu()，同步等待宽限期结束，让写者能写出「改完、等一下、再释放」这种线性的代码。

4.1 三种风格的取舍

liburcu 把同一套语义做成了几个链接期可选的变体。选哪个，取决于你愿不愿意改应用代码，以及内核给不给你 membarrier。

变体读侧代价写侧代价对应用的要求什么时候选
urcu-qsbr接近零：rcu_read_lock() 编译后基本什么都不剩等待所有线程报告静止点侵入：必须在主循环顶点周期性调 rcu_quiescent_state()，阻塞前调 rcu_thread_offline()自己的服务，能改主循环；追求极限读性能
urcu-memb（默认）一次本地 store + 编译器屏障调 sys_membarrier()，代内核替所有 CPU 执行屏障只要成对调用 lock / unlock绝大多数场景的默认选择；Linux 4.14+ 可用
urcu-signal同 memb，很轻给每个注册线程发信号，强制它执行屏障要交出一个信号编号，不能与应用冲突没有 sys_membarrier 的老内核 / 非 Linux
urcu-mb读侧一条真屏障，明显更贵无需系统调用无可移植兜底，性能垫底
urcu-bp较重（每次检查是否已注册）同 memb无需显式注册线程写库时用：你无法要求宿主程序配合注册

把 memb 和 signal 放在一起看就明白它们在解决同一个问题：读者侧不想付屏障，那这条屏障就得由写者想办法强加给读者所在的 CPU。sys_membarrier 是内核提供的正规途径，发信号是它出现之前的土办法。成本从高频的读路径转移到了低频的写路径——这正是 RCU 系方案的核心交易。

4.2 QSBR 的零成本与它的账单

QSBR 把这笔交易推到极致：读者侧一条指令都不加。代价是它不再能自己判断线程何时离开了临界区，只能要求应用主动汇报。

这个要求在实践中比听起来麻烦。「在主循环顶点调一次 rcu_quiescent_state()」对一个 while(true){ poll(); handle(); } 的事件循环很自然，但对一个线程池里跑任意用户回调的框架就很难——你不知道回调会不会一跑就是十分钟。更关键的是阻塞前必须 rcu_thread_offline()：要去做一次磁盘 IO、要在条件变量上等、要调一个第三方库，都得先把自己标记为离线，否则整个进程的回收全部停摆，症状与 §3.3 的图一模一样。

所以 QSBR 的真实判据不是「要不要极限性能」，而是「这个进程里所有会碰 RCU 的线程，是不是都归你管」。是，选 QSBR；不是，选 memb 少操心。

4.3 和内核 RCU 的对照

内核 RCU 的读侧同样几乎免费，但它的免费来源和用户态完全不同——而这个差别正是 liburcu 要费这么大劲搞出三种变体的原因。

内核 RCU 本身的机制——宽限期检测、call_rcu 的回调批处理、可抢占 RCU 与 RCU 陷阱——在 内核同步机制 里有两整章，本文不重复。这里只需要记住对照关系：算法是同一个，难的部分被挪到了不同的地方。

5.2 什么时候其实不该无锁

这一节是本文最重要的一节，因为前面四章很容易给人一个错误印象：无锁回收是高手的默认选项。它不是。它是一个需要被论证的选项，而绝大多数场景论证不出来。

❌ 常见的错误推理链

「这段路径在热点上 → 锁会阻塞 → 改成无锁链表 → 需要 SMR → 引入 EBR」。

每一步看起来都成立，但整条链从未被量过：锁真的是瓶颈吗？争用率多少？临界区多长？换成无锁之后，省下的锁开销有没有被 SMR 的屏障吃回去？

实际结果常常是吞吐没涨、p99 反而更差（重试与缓存行弹跳），外加一整类以前不存在的内存安全 bug，和一个只有作者看得懂的模块。

✅ 先把便宜的办法试完

1. 分片 + 普通锁。把一把大锁换成 64 把小锁，通常就能拿到无锁方案 80% 的收益，而复杂度几乎为零。争用是被分散掉的，不一定要被消除。

2. atomic<shared_ptr<T>>（C++20）。读多写少的配置表、路由表、特征表，这一个类型就够了：语义精确、无需宽限期、内存立刻回收。代价是每次读一次原子 RMW，且实现通常不是 lock-free。先量一下这个代价是否真的不可接受。

3. 写时整体替换。配置类数据几秒才更新一次时，「造一份新的、原子换指针、旧的交给 SMR 延迟释放」比任何精细的并发容器都简单，而且此时宽限期长一点完全无所谓。

4. 确认无锁不可替代之后，用现成库。folly、liburcu、或等 C++26（§6）。

判据可以写成一句可执行的话：如果你无法用一个数字说清「换成无锁之后哪个指标改善了多少」，那就不该换。另外还有一条硬性门槛——只有一个写者、或写频率极低时，很多 SMR 的复杂性可以直接绕开（单写者时 synchronize_rcu() 的成本完全可以忍）。先确认自己是不是这种情况，能省掉一大半工作。

验证：为什么 TSan 靠不住

「跑了一晚上压测没问题」在这个领域几乎不构成证据

7.1 窗口有多窄

§1.1 那条时间线要出事，需要两个线程的指令流在几十纳秒的精度上对齐。在一台空闲的开发机上，这个概率低到可以跑一整夜都不复现；而在生产环境里，请求速率高三个数量级、CPU 被超卖、还有 NUMA 跨节点延迟，它每天都会命中几次。

更糟的是三重掩盖：即使 UAF 真的发生了，那块内存多半还没被分配器交给别人，读到的仍是旧值，程序继续正常运行；就算被复用了，也可能只是某个字段读出脏数据，表现为一次业务逻辑异常而不是崩溃；等真的崩了，栈顶早已跑到几百微秒之后的某个无关代码里。

手段能抓到吗为什么
TSan不一定TSan 只报告实际发生过的交错，它不探索调度空间。而且它对 std::atomic_thread_fence 的建模是不完整的——SMR 恰恰重度依赖独立屏障，因此存在系统性的漏报
ASan（默认）较难只有当那块内存已经被 free 且还在 quarantine 里时才报。窗口一窄、quarantine 一满，就退化成静默
ASan + 大 quarantine能，推荐ASAN_OPTIONS=quarantine_size_mb=4096:max_redzone=2048，让释放的节点长时间不被复用，把「偶尔读到脏数据」变成「必然触发报告」
手工毒化能，最便宜真 delete 前把整块填 0xDD 并抹掉魔数；读者每次解引用先校验魔数。不依赖任何工具，生产的 debug 构建里也能开
模型检验（GenMC / CDSChecker / Relacy）能，而且是穷举的在弱内存模型下枚举所有合法交错。只能验证几十行的核心算法，但那恰好就是 SMR 的全部代码量——这是唯一能给出"证明"而不是"没测出来"的手段
换 aarch64 跑一遍能抓一大类x86 的 TSO 会掩盖所有缺失的 store-load 屏障（§2.2）。同一份代码在 ARM 上可能几分钟就崩

7.2 压力测试怎么设计

压测的目标不是「模拟生产负载」，而是主动把那个几十纳秒的窗口撑开。这是两种完全不同的设计思路，后者需要刻意制造在生产里罕见的条件。

有一类假阴性特别值得警惕：在压测里把线程数设得比核数少。这看起来更「贴近生产配置」，实际上大幅降低了抢占频率，而抢占正是 §3.3 与 §1.1 两类 bug 的触发条件。SMR 的压测应该故意超卖 CPU，越挤越好。

面试题集（12 道）

按难度分三档，先自测再对照

点击每道题展开参考答案（先自测，再对照）。

8.1 基础（必答）

  1. 基础无锁链表里 CAS 成功摘下一个节点后，为什么不能立刻 delete？

    因为「节点在数据结构里不可达」不等于「没有线程正在使用它」。另一个读者可能在 CAS 发生之前的一瞬间读到了同一个指针，此刻正握着它准备解引用——它没有做错任何事，读到的确实是当时的合法状态。

    所以删除必须拆成两个阶段：摘除（CAS，立即完成）与回收（真 delete，必须等所有在摘除之前就开始的读者结束）。两者之间的时间差叫宽限期，判断它何时结束正是 SMR 机制存在的全部理由。

  2. 基础ABA 问题和内存回收问题是一回事吗？

    不是，它们正交。ABA 是值的歧义：CAS 只比较值相等，无法区分「没变过」和「变成 B 又变回 A」，于是把陈旧的 next 写了回去。回收是生命周期问题：读者手里的指针指向已释放的内存，哪怕全程只有一个写者、零次 CAS 重试，照样 UAF。

    唯一的联系是单向的：SMR 让节点不被释放，地址就不会被复用成同一个值，因此顺带消掉了大部分 ABA。反过来不成立——tagged pointer 只保护了那一个原子字，对它指向的整块内存毫无作用。正确顺序是先选 SMR，再看剩下的 ABA 面。

  3. 基础用一句话说清 Hazard Pointer 和 EBR 的核心差别。

    HP 追踪「你在用哪几个指针」，EBR 只追踪「你还在临界区里吗」。

    由此推出全部差异：HP 的开销正比于解引用次数（每次一条 seq_cst 屏障），EBR 的开销正比于临界区次数（区内解引用免费）；HP 因为精确，所以内存有硬上界；EBR 因为粗粒度，一个线程卡在临界区里就让全体回收停摆，内存无上界。一个换来确定性，一个换来读性能。

  4. 基础retire() 和 delete 的区别是什么？为什么回收总是批量的？

    retire() 只是记账：把指针挂进本线程的待回收列表，不释放任何内存。真正的 delete 要等到一次判定（HP 的 scan、EBR 的 epoch 推进）确认没人可能访问它。

    批量是因为判定本身有固定成本——HP 的 scan 要遍历全部 hazard slot，EBR 的推进要扫所有线程的 local epoch，都是 O(线程数)。每摘一个节点就判一次，成本会高到不可接受。所以实现都设一个阈值攒够再判，代价是内存用量必然高于逻辑用量，这一截有没有上界正是选型的关键。

8.2 中级（区分熟练度）

  1. 中级Hazard Pointer 的读者侧为什么 publish 之后必须重新读一次源指针？去掉会怎样？

    因为 publish 和「确认这个指针还没被摘除」无法在一步里完成。去掉重新验证，就会出现这个交错：读者读到 p（还没 publish）→ 写者摘除 p → 写者 scan，名单里当然没有 p → 读者才 publish（晚了）→ 写者 delete p → 读者用 p，UAF。

    加上重新验证后，利用写者固定的「先摘除后 scan」顺序可以做完备论证：重读若仍等于 p，说明摘除尚未发生，而 scan 在摘除之后，所以 scan 一定看得见我的 publish，安全；重读若不等于 p，说明可能已被摘除，读者不赌，丢弃重来。没有第三种可能，这就是正确性证明的全部。

  2. 中级那条 seq_cst 屏障能不能换成 release？在 x86 上测不出问题说明什么？

    不能。需要挡住的是 publish 那个 store 与重新验证那个 load 之间的重排，而 release 语义管不到后续的 load。把 store 重排到 load 之后，验证就形同虚设——你在「确认完之后」才登记，正好回到上一题那个交错。

    x86 是 TSO：它只允许 store-load 这一种重排，而这恰恰就是本算法唯一怕的那一种。所以在 x86 上测不出问题恰恰是最危险的情形：屏障被写错时，x86 可能跑几百亿次都不出事，换到 aarch64（store-store、load-load 都可能重排）第二天就崩。验证这类代码必须在弱序机器上重跑，或者送进模型检验器。

  3. 中级EBR 为什么需要三个 epoch，两个为什么不行？

    在 epoch e 里 retire 的节点，可能被任何在 e 之前就 pin 住的线程访问。要确认这些线程全部离开，全局 epoch 必须推进两次：第一次证明「所有在线线程都已到达 e」，第二次证明「所有线程都已离开 e」。

    这两次推进期间，e 那条袋子必须原样冻结，而新产生的垃圾又得有地方放，于是需要三条：一条正在收集（当前 epoch）、一条冻结等待（上一个）、一条确认安全可整袋释放（上上个）。只有两条时，「正在被读的」和「正要被 free 的」会落到同一条上。

  4. 中级liburcu 的 QSBR 为什么读侧几乎零开销？它的代价在哪？

    因为它把「判断线程是否在临界区」这件事完全外包给了应用：读侧的 rcu_read_lock() 编译后基本什么都不剩，静止点靠应用在主循环顶点主动调 rcu_quiescent_state() 汇报。

    代价是侵入性和一个很容易踩的坑：任何可能阻塞的操作之前必须 rcu_thread_offline()——磁盘 IO、等条件变量、调第三方库都算。漏一处，那个线程就永远不报告静止点，整个进程的回收全部停摆，症状是内存线性上涨直到 OOM。所以 QSBR 的真实判据不是「要不要极限性能」，而是「进程里所有会碰 RCU 的线程是不是都归你管」；不是的话选 urcu-memb。

8.3 高级（体现深度）

  1. 高级一个算法可以是 lock-free 的，同时内存回收却是 blocking 的——怎么理解？

    进度保证是分维度的。EBR 的读写操作路径确实 lock-free：任一线程暂停都不会阻止其他线程完成操作。但空间维度不是：一个线程 pin 住不放，全局 epoch 就推进不了，所有线程的所有待回收内存无限堆积，最终 OOM——这在实践中和「被阻塞」没有区别，只是表现为内存而不是延迟。

    Hazard Pointer 在这一维上更强：一个卡住的线程只护住它手里那 K 个指针，其余照常释放，总量守在 O(N²K) 的常数上界。所以评审无锁设计时要问两个问题而不是一个：操作是不是 lock-free，以及内存有没有上界。只问前一个，就会在超卖的容器里被第二个问题教做人。

  2. 高级为什么 TSan 对这类 bug 有系统性漏报？该用什么替代？

    两个原因。其一，TSan 只分析实际发生过的交错，它不探索调度空间；而 SMR 的 UAF 窗口只有几十纳秒，空闲机器上跑一夜都未必命中一次。其二更本质：TSan 对独立的 std::atomic_thread_fence 建模不完整，而 SMR 恰恰重度依赖独立屏障（§2.1 的 ② 就是），于是产生的是系统性漏报而不是偶然漏报。

    替代方案要分层叠加：ASan 配大 quarantine（quarantine_size_mb=4096）让释放的节点不被复用，把静默读脏变成确定报告；手工毒化 + 魔数校验提高可观测性；在 aarch64 上重跑抓 x86 TSO 掩盖掉的缺失屏障；最后，核心算法只有几十行，送进 GenMC / CDSChecker 这类模型检验器穷举——那是唯一能给出"证明"而非"没测出来"的手段。压测本身也要反着设计：结构缩到 2～4 个节点、线程数超卖 4 倍、回收阈值设为 1、在 publish 与验证之间注入随机 yield。

  3. 高级做一个读多写极少的全局路由表，你会怎么选？请给出判据而不是答案。

    先问「要不要无锁」。读多写极少意味着读写锁的写侧几乎不争用，而写时整体替换（造一份新表、原子换指针、旧表延迟释放）往往就够了——此时宽限期长一点完全无所谓，甚至可以用最笨的方式等。能落在这一档就不要往下走。

    如果读侧确实被量出是瓶颈，再按三条判据往下：① 线程是否都归你管、临界区里有没有可能阻塞的调用——都归你管且临界区短小紧凑，选 RCU（QSBR 最快，否则 urcu-memb）；② 内存是否必须有硬上界（实时系统、嵌入式、多租户共享进程）——是则只能 Hazard Pointer，哪怕读延迟差一截；③ 读路径是长遍历还是单次查找——长遍历时 HP 每次解引用都要付屏障，会主导整个开销，这种形态基本排除 HP。

    还有一条容易被忽略的现实判据：std::atomic<std::shared_ptr<T>> 对「整表替换」这个形态是完美匹配的——语义精确、立即回收、零额外概念。它的问题是引用计数争用，但如果写频率极低、读者持有引用的时间极短，先量一遍再决定要不要上 SMR。

  4. 高级线上发现某服务内存缓慢线性上涨、GC 式的回收完全停滞，怎么定位到 SMR？

    「线性上涨 + 回收停滞」这个组合本身就是 EBR / RCU 的签名症状，它和普通内存泄漏的区别在于：泄漏通常与请求量成正比且持续，而这个是某一时刻突然开始、之后不再回落，且往往在重启某个无关线程后自行恢复。

    定位路径：① 导出所有线程的 local epoch / 静止点计数，找那个数值落后于全局 epoch 的线程——它就是元凶，一个就够；② 对该线程抓栈，看它卡在哪——常见是临界区里调了会阻塞的东西（一次 mmap、一次日志落盘、一个第三方库的锁），或者 QSBR 下漏了 rcu_thread_offline()；③ 确认 limbo list 长度是不是随时间单调增长。

    根治要分两层：短期把那个阻塞调用挪出临界区；长期要认识到这个弱点不能被修掉——如果业务上无法保证临界区永远不阻塞（比如里面会跑用户回调），就该换成 Hazard Pointer，用读延迟换内存上界。给 limbo 设水位然后 abort 只是把内存问题换成可用性问题，不是解法。
