C++ 函数调用到底发生了什么？

你写下 add(10, 20)，只是一行普通的 C++。但在 CPU 眼里，这一步要解决「参数放哪、返回地址记在哪、局部变量存在哪、执行完怎么回去」等一连串问题。本篇把这一行代码从源码一路拆到机器指令，建立整个系列的地基 —— 并从一开始就纠正那个最常见的误解：「函数参数都会压栈」。

01

一次函数调用的全景：源码 → 机器指令

「函数调用」是一个抽象概念，落到硬件上其实是一整套约定

什么是「函数调用」？

函数调用本质是：暂时中断当前代码流，跳到另一段代码执行，执行完再精确地回到原来的位置继续。这句话里藏着 CPU 必须解决的所有难题 —— 「跳过去」很简单（改一下指令指针即可），难的是「怎么原路回来、回来之后一切还和走之前一样」。

C++ 是一门编译型语言，你写的 add(10, 20) 不会被 CPU 直接理解。它要经过这样一条流水线（本系列 编译步骤一篇有完整展开）：

C++ 源码  add(10, 20)
编译器前端：词法 / 语法 / 语义分析 → IR 中间表示
编译器后端 + ABI 规则：决定参数放寄存器还是栈
汇编 / 机器码  mov / call / ret
CPU 执行：改 RIP、读写 寄存器 与 栈
一句话建立心智模型

C++ 函数调用 = 编译器 + CPU + ABI 三方共同完成的一套流程：编译器按 ABI 规则把参数摆到约定位置、生成 call；CPU 负责保存返回地址、跳转、执行；栈负责存放放不下寄存器的东西以及「回家的路」。C++ 语言标准本身几乎不规定这些细节。

03

贯穿全文的例子：add(10, 20)

整个系列都用这段最小代码，从直觉一路推到汇编

int add(int a, int b)
{
    int c = a + b;   // 一个局部变量
    return c;
}

int main()
{
    int result = add(10, 20);
}

当 main 执行到 add(10, 20) 时，会发生一连串步骤。先用「白话时序」建立直觉，后面再落到寄存器和栈：

main()
  │
  ├─ ① 准备参数        a=10 → EDI，b=20 → ESI   （寄存器，不是压栈！）
  │
  ├─ ② call add        把「下一条指令地址」压栈，跳到 add
  │        │
  │        ├─ ③ 进入 add，建立栈帧（如果需要）
  │        ├─ ④ 执行 c = a + b
  │        ├─ ⑤ 把返回值放进 EAX
  │        └─ ⑥ ret     从栈取回返回地址，跳回 main
  │
  └─ ⑦ 回到 main，从 EAX 取回 result
注意第 ① 步

很多教材会说「调用前把参数压栈」。在现代 64 位平台上，前几个整数/指针参数走寄存器，根本不碰栈。这不是编译器的自由发挥，而是 ABI（应用二进制接口）的硬性规定。下一节详细说明。

04

参数怎么传：寄存器优先，不是「都压栈」

这是初学者最大的认知误区，必须一开始就纠正

为什么优先用寄存器？因为寄存器就在 CPU 内部，访问是 0 延迟级别的；栈在内存里，即便命中 L1 缓存也要几个周期。函数调用极其频繁，用寄存器传参能显著降低开销。于是现代 ABI 都规定：前若干个参数用寄存器，超出的部分才落到栈上。

x86-64 Linux（System V ABI）整数/指针参数寄存器

参数序号第 1 个第 2 个第 3 个第 4 个第 5 个第 6 个第 7 个起
寄存器RDIRSIRDXRCXR8R9压栈

所以 add(10, 20) 里 a 走 RDI（32 位用其低半部 EDI），b 走 RSI/ESI。对应的 -O0 汇编大致是：

# main 中调用点（AT&T 语法，源操作数在前）
    mov     esi, 20      # 第二个参数 b = 20
    mov     edi, 10      # 第一个参数 a = 10
    call    add           # 调用
    # 返回后 add 的结果在 eax 里
超过寄存器数量怎么办？

假设一个函数有 9 个整数参数：前 6 个走 RDI…R9，第 7、8、9 个从右往左压栈。栈这时才登场，作为寄存器不够用时的「溢出容器」。浮点参数走另一组 XMM0–XMM7 寄存器，互不占用。

不同平台的寄存器分配完全不同（这正是 ABI 的意义），后面 04 篇会横向对比 Linux / Windows / ARM64。这里只需记住结论：

参数放哪，取决于 ABI / Calling Convention，而不是「一律压栈」。C++ 标准对此只字未提。

05

返回地址 / 返回值 / 局部变量放在哪

三样最容易混淆的东西，位置各不相同

返回地址：CPU「回家的路」

返回地址就是 call 指令下一条指令的地址。执行 call add 时，CPU 自动把这个地址压到栈上，然后跳进 add。add 结束时的 ret 再把它从栈弹出、跳回去。没有它，CPU 执行完 add 就「迷路」了 —— 不知道该回到哪。

返回值：一般放在 RAX

对于 int/long/指针 这类能塞进一个寄存器的返回值，约定放在 RAX（32 位是 EAX）。add 算完 c，会 mov eax, c 再 ret；main 回来后从 EAX 取走。较大的结构体返回值走另一套「隐藏指针」机制（04 篇细讲）。

局部变量：默认在栈帧，优化后未必

add 里的 c 是局部变量。在 -O0 下它有一块专属栈空间；但开了优化，编译器很可能发现「c 只是 a+b 的中转」，直接用寄存器完成、根本不给它栈空间，甚至把整个 add 内联进 main 后 c 彻底消失。

❌ 误解：局部变量一定在栈上。

✅ 正解：局部变量逻辑上属于栈帧，但物理上可能只存在于寄存器，甚至被优化掉。「在栈上」只是未优化时的默认实现。

06

栈与栈帧：为什么必须保存上下文

这里只建立概念，02 篇会把栈帧彻底拆开

什么是栈（Stack）？

栈是每个线程私有的一块连续内存，专门服务函数调用。它后进先出（LIFO），而且在 x86-64 上向低地址方向增长 —— 每调用一层函数，栈就往下「长」出一块；函数返回，这块又被回收。

生活类比：叠盘子

调用函数像往桌上叠一摞盘子：新调用放最上面一个盘子（新栈帧），返回就拿走最上面那个。永远只动最顶端，天然保证「谁最后进、谁最先出」，也天然支持嵌套和递归。

什么是栈帧（Stack Frame）？

一次函数调用在栈上占用的那一小块，就是它的栈帧（activation record）。它把这次调用需要的东西打包在一起：

高地址 ↑（栈底方向）
main 的栈帧调用者上下文
返回地址call 压入
保存的寄存器 / 旧 RBP序言保存
add 的局部变量 c← RSP 附近
低地址 ↓（栈顶方向，栈向此增长）

▲ add(10,20) 执行时的栈布局示意（-O0 未优化的典型形态）

为什么函数调用需要「保存上下文」？

因为 main 和 add 共用同一套 CPU 寄存器。如果 add 随手改了某个寄存器，而 main 待会儿还要用它，就会数据错乱。于是有了约定：

  • 返回地址必须保存 —— 否则回不去；
  • 某些寄存器由被调函数负责保存/恢复（callee-saved），用之前先存栈、返回前还原；
  • 另一些由调用者自己保护（caller-saved），调用前想留就自己先存。

这套「谁保存谁」的分工，就是 04 篇要讲的调用约定核心。保存上下文的本质，是在共享寄存器的前提下，让每一层调用都感觉自己独占 CPU。

08

核心结论

  • 函数调用 = 中断当前流 → 跳转 → 精确返回。难点在「回得来且状态不变」。
  • 参数优先走寄存器（x86-64：RDI/RSI/RDX/RCX/R8/R9），放不下才压栈。
  • 返回地址由 call 压栈，是 CPU 回到调用点的唯一凭证。
  • 返回值一般在 RAX；局部变量默认在栈帧，优化后可能只在寄存器或被消除。
  • 栈帧把一次调用需要的东西打包，栈的 LIFO 特性天然支持嵌套与递归。
  • 这一切由 编译器 + CPU + ABI 共同定义，C++ 标准不规定具体位置。
09

常见误区

❌ 所有参数都会压栈。 现代 64 位 ABI 前几个参数走寄存器，压栈只是寄存器不够时的补充。

❌ 所有局部变量都在栈上。 优化后很多变量只存在于寄存器，甚至被完全优化掉。

❌ 返回值靠「栈返回」。 标量返回值走 RAX；只有大对象才借助隐藏指针（涉及内存）。

❌ C++ 标准规定了参数怎么传。 完全没有。这属于 ABI / 调用约定 / 平台实现层面。

❌ 「栈是 LIFO 所以用栈」就是全部原理。 LIFO 只是表象；真正要解决的是返回地址保存、寄存器保护、上下文隔离。

10

面试问题

点击每道题展开参考答案（先自测，再对照）。

  1. 基础执行 add(10, 20) 时，从准备参数到返回，大致经历了哪几步？

    准备参数（写寄存器）→ call（压返回地址、跳转）→ 建立栈帧 → 执行函数体 → 返回值放 RAX → ret（恢复上下文、跳回）→ 调用者取回结果。

  2. 基础C++ 函数调用时参数一定会压栈吗？为什么？

    不一定。x86-64 前 6 个整数/指针参数走 RDI/RSI/RDX/RCX/R8/R9，因为寄存器访问远快于内存；超出部分才压栈。

  3. 原理什么是返回地址？它保存在哪、由谁保存？

    call 指令的下一条指令地址。由 call 自动压入栈，ret 自动弹出并跳回。它是回到调用点的唯一凭证。

  4. 原理为什么函数调用需要「保存上下文」？

    因为调用者和被调者共用同一套寄存器。若不保存返回地址与被覆盖的寄存器，返回后调用者的状态会被破坏。

  5. 原理返回值一般放在哪里？大对象呢？

    标量放 RAX。大到寄存器装不下的对象，调用者预留空间并把其地址通过隐藏指针（RDI）传入，被调函数直接写进去（RVO/sret）。

  6. ABIStack Frame 是 C++ 语言概念吗？

    严格说不是。它是编译器 + CPU + ABI + 运行时共同形成的底层执行机制，C++ 标准并未定义它。

  7. 进阶为什么同一段 C++ 代码，在 Linux 和 Windows 上生成的传参汇编不同？

    因为两者用不同的调用约定：Linux 用 System V ABI（RDI/RSI…），Windows x64 用 RCX/RDX/R8/R9，寄存器分配与栈影子空间都不同。详见 04 篇。
