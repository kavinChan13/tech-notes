三、C++ 对象内存布局

普通对象 · 含虚函数对象 · 多重继承 — vptr/vtable 透视

3.1 简单对象布局

无虚函数的 struct Point { int x, y; }：两个 4 字节成员紧挨着，sizeof = 8，无填充。

3.2 内存对齐与填充 (Padding)

按声明顺序对齐：char, int, char 会在中间和尾部各垫 3 字节（12B）；改成 int, char, char 只在尾部垫 2 字节（8B）。成员按大小从大到小排，padding 最少。

3.3 虚函数表 (vtable) 布局

含虚函数的对象前端有一个 vptr（64 位上 8B），指向该类共享的 vtable。虚调用 = 一次间接跳转。

四、C++11 内存模型 (核心：多线程与原子操作)

多线程语义 · 三层重排 · 线程 vs 进程 · 共享内存 — Why Memory Model

C++11 正式定义了多线程内存模型，解决了此前"未定义行为泛滥"的问题。核心概念如下：

4.1 为什么需要内存模型？

每个 CPU 核心有自己的缓存和 Store Buffer，写入不会立即对其他核心可见。C++ 内存模型通过 std::atomic 和内存序来控制这种可见性。

4.2 内存模型到底在「管」什么？

内存模型是一份契约：一个线程的写，何时、以何顺序被另一线程看见。单线程永远感觉不到重排（as-if-serial）；问题只在共享同一块内存的多个执行流上。

三层叠加让「源码顺序」≠「对方看见的顺序」：编译器重排、CPU 乱序、以及下图的 store buffer。x86 的 TSO 只允许这一种跨核重排（StoreLoad）；挡住它需要 seq_cst，见 §7。

编译器还能把无依赖的 x=1; r1=y; 调成先读后写；CPU 流水线也会让 load 先完成。防线分别是原子操作（编译器屏障）和 CPU fence。seq_cst 才能挡住 StoreLoad，见 §7 短例。

4.3 线程 vs 进程 —— 从内存视角看并发

线程像一家人住同一套房（共享地址空间，内存模型全程生效）；进程像各住各家（默认隔离，只有显式共享内存才需要同一套规则）。
维度线程进程
地址空间共享同一虚拟地址各自独立（同虚拟地址 ≠ 同物理页）
默认共享代码 / 全局 / 堆 / fd不共享（fork 后 CoW）
私有栈、寄存器、thread_local整个地址空间
通信共享变量 + atomic/锁IPC：共享内存、管道、消息、socket
内存模型全程生效仅显式共享内存区域
创建/切换低（共享页表）高（建页表、切地址空间）
隔离一线程野指针可搞崩进程崩溃被内核关在本进程
典型场景并行计算、工作线程、UI + 后台浏览器沙箱、Nginx worker、微服务

判据只有一句：有没有共享内存，不取决于用线程还是进程。

4.4 进程间共享内存，也要遵守内存模型

shm_open + mmap 映射到同一物理页后，Store Buffer / Cache / 乱序与跨线程完全一样。同步写法就是 §7 的 release/acquire 配对——把 atomic 放进共享区即可。

跨进程多几条坑：atomic<T> 必须 is_always_lock_free（非 lock-free 的内部锁在本进程私有堆上，对面看不见）；不能放普通 mutex（改 PTHREAD_PROCESS_SHARED）；不能存指针（两进程虚拟地址不同，存偏移）；两端布局必须同一份头文件。

陷阱原因正确做法
atomic 必须 lock-free非 lock-free 的内部锁在本进程私有堆上static_assert(is_always_lock_free)
不能直接放 std::mutex句柄绑定本进程PTHREAD_PROCESS_SHARED 或命名信号量
不能存指针 / 引用两进程虚拟地址不必相同存相对共享区基址的偏移
对象布局要一致不同编译器/对齐会错位两端同一份头文件 + 明确 alignas

五、Happens-Before 关系

程序顺序 · 同步操作 · 传递性 — 跨线程可见性的形式化基础

Happens-before：若 A happens-before B，则 A 的副作用对 B 可见。它是程序序 + synchronizes-with 的传递闭包。

①→② 程序序，②→③ 配对同步，③→④ 程序序，因此 ① happens-before ④。没有这条边，B 读到 ready==true 仍可能看见 data 的旧值——那不是「慢一点」，而是数据竞争或半成品。

来源建立的边工程含义
程序序同一线程里分号前后（sequenced-before）单线程 as-if-serial，对方看不见这层
release → acquire写 flag 与读到该值的 acquire 读（synchronizes-with）发布 payload 的标准写法，见 §7.2
mutexunlock happens-before 下一次 lock临界区内不必手写屏障
thread构造 happens-before 新线程首句；末尾 happens-before join 返回join 之后读对方写过的普通变量是安全的
seq_cst所有 seq_cst 操作另有一条全局总序比配对 RA 更强，挡住 StoreLoad / IRIW

六、六种内存序 (Memory Ordering)

relaxed / consume / acquire / release / acq_rel / seq_cst — 六档强度

六档 memory_order：越往右约束越强、越慢。工程上常用三档——relaxed / acquire-release / seq_cst。

档位保证不保证典型用法
relaxed单次读写不可撕裂与其它变量的顺序、跨线程可见性边计数器、统计、已有别的同步时的 ++
consume本意只约束数据依赖读实现几乎全部提升为 acquire不要用，直接写 acquire
acquire本读之后的访问不能提前到读之前本读之前的写不必对别人可见读 flag、进临界区、load 指针
release本写之前的访问不能延后到写之后本写之后的读不必立刻全局可见写 flag、出临界区、发布指针
acq_rel一次 RMW 同时带读写屏障全局总序自旋锁 TAS、fetch_sub 到零再析构
seq_cst所有 seq_cst 操作共享一条全局时间线—Dekker / Peterson、默认、尚未 profile

配对必须成对：一边 release 一边 relaxed，对面看不到 payload。RMW 默认 seq_cst；引用计数 ++ 可 relaxed，-- 到零析构必须 acq_rel，否则可能看见半成品对象。

七、实战代码示例

Relaxed 计数器 · Acquire-Release · Seq_Cst 总序 — 三份短例

7.1 Relaxed：只保证原子性

std::atomic<int> counter{0};
void inc() { for (int i = 0; i < 1000; ++i)
    counter.fetch_add(1, std::memory_order_relaxed); }
// 两线程 join 后 counter 一定是 2000；不要用它同步别的数据

join 之后读 counter 安全：线程结束 happens-before join 返回。relaxed 只保证「加出来的和是 2000」，不能拿这次 fetch_add 去发布旁边的 payload——那是 §7.2 的活。

7.2 Release / Acquire：生产者写 flag

std::atomic<bool> ready{false};
int data = 0;
void producer() { data = 42; ready.store(true, std::memory_order_release); }
void consumer() {
    while (!ready.load(std::memory_order_acquire)) {}
    assert(data == 42);   // release 之前的写全部可见
}

7.3 seq_cst 总序 vs 没有它

std::atomic<bool> x{false}, y{false};
int r1 = 0, r2 = 0;
// A: x.store(true);  r1 = y.load();     // 默认 seq_cst
// B: y.store(true);  r2 = x.load();
// seq_cst：r1==0 && r2==0 不可能
// 改 relaxed 或 release/acquire：可能（store buffer）

自旋锁就是 acquire 的 test_and_set + release 的 clear，临界区不会漏出锁范围。DCLP 见 §13.4。

八、数据竞争与未定义行为

Race Condition · UB · 编译器假设 — 不可调试的陷阱

C++ 标准的定义：当两个线程同时访问同一内存位置，且至少一个是写操作，且没有通过原子操作或同步原语（mutex等）建立 happens-before 关系时，就是数据竞争（data race），属于未定义行为（UB）。

8.1 单核也会有多线程 bug

「单核同时只能执行一条指令」不等于「一个 C++ 语句是原子的」。 count++ 在汇编里通常是 load → add → store 三步，中间随时可以被时钟中断抢走。

抢占交错；多核再加真并行和内存序。 单核就要锁 / atomic（防「换人」）；多核还要防同时写 + 可见性。
  • 单核：锁 / atomic 防止「做到一半被换人」，交错时间线照样能把两次 ++ 合成 1。
  • 多核：还要防止两个核同时写，以及 store buffer 导致的可见性问题（见 §13.1 MESI）。
「单核测过没问题」挡不住多核内存序 bug：x86 上偶然绿的无锁代码，搬到 ARM 可能直接崩。核数不是正确性的护身符。

九、内存序选择决策流程

何时用 relaxed / acquire-release / seq_cst — 决策树

问题选
不需要原子？mutex / 别碰共享
只要原子、不和其他变量同步？relaxed
读 / 写 / RMW，需要同步？acquire / release / acq_rel
所有线程必须看见同一全局序（Dekker）？seq_cst

黄金法则：先 seq_cst 保证正确，profile 出热点再降档。过早抠内存序是万恶之源。

十二、常见误区

volatile != atomic · happens-before != 时间先后 — 典型错误澄清

误区真相
volatile 可以替代 atomic volatile 只防止编译器优化（如不省略读写），但不保证原子性和跨线程可见性。Java 的 volatile 和 C++ 的不同！
int 读写天然是原子的 即使在 x86 上对齐的 int 读写不会被撕裂，但编译器可能重排指令。标准说：不用 atomic/mutex 就是 UB。
加了 mutex 就不需要 atomic 如果所有对变量的访问都在 mutex 保护下，确实不需要 atomic。但如果有无锁的"快速路径"就需要。
relaxed 没用 计数器 (shared_ptr 引用计数递增)、统计等只需要原子性不需要同步的场景，relaxed 最高效。
seq_cst 太慢，不要用 在 x86 上，acquire/release 的读写已经免费了，seq_cst 只在 store 上多一条 MFENCE。先保证正确，再优化。
happens-before 就是墙上时钟的先后 它是可见性边，不是物理时间。A 比 B 先执行，没有同步边，B 仍可能看不见 A 的写。
x86 测过就等于对 TSO 只挡 StoreLoad；ARM 几乎什么都能重排。无锁代码必须按标准写，并在弱序平台压测。

十三、面试深度专题 ⭐

站在高级 C++ 工程师视角，内存模型的深度考点集中在：Cache 一致性协议、x86 vs ARM 内存模型差异、无锁 / 等待自由 / ABA、编译器屏障 vs CPU 屏障、假共享与 alignas、DCL 单例、thread_local。

13.1 Cache 一致性 — MESI 协议

多核 CPU 每个核都有自己的 L1/L2，Cache line（通常 64B）通过 MESI 协议保持一致：

状态含义写操作代价
Modified本核独占、已脏（与内存不一致）直接写
Exclusive本核独占、干净直接写（转 M）
Shared多核共享、干净发 Invalidate，等所有副本失效
Invalid无效先发 Read-for-Ownership

写 Shared 行代价远高于写独占行。两个无关变量挤在同一 64B 行 → false sharing。

写先到本核，另一核先看自己的 L1

一次 store 通常先进入本核的 store buffer / L1，并不立刻出现在 DRAM 或别的核上。另一核读同一个变量时，先查自己的 L1。MESI 保证的是最终一致：不会永远读到互相矛盾的稳定值。它不保证立刻，也不保证源码顺序（store buffer、乱序执行）。这就是 C++ 需要 atomic / 锁（acquire-release）的原因：协议管缓存行，不管你的程序顺序。

「A 只改自己的 L1，为什么 B 的 L1 作废？」

B 可能已经有同一条 64B 行的 Shared 副本。A 要写之前必须独占这条行（Invalidate 或 Read-for-Ownership / RFO），B 上整行变成 I。否则 B 会继续读到旧的 count_a。

  • 作废的是 B 手里那份过期副本，不是「改了 B 自己的变量」。
  • 粒度是缓存行不是 C++ 变量 → 同一行上的 count_b 被连带作废 = false sharing。perf 里常见 HITM（Hit Modified，从别核脏行来的命中）。

False sharing 典型病理几乎只在多核

痛的是同一行在两套私有 L1 之间 ping-pong。单核上两个线程轮流用同一套 L1，没有核间一致性流量，所以几乎无感。超线程通常共享 L1，也不是经典乒乓。

数据竞争（正确性）False sharing（性能）
单核两线程有：count++ 可被交错（§8.1）几乎无：没有核间 HITM
多核有：交错 + 真并行 + 内存序有：行在 L1 间弹射

定位与 alignas(64) 修法见 性能指南 · False Sharing、内存优化 · 伪共享（perf c2c）。这里不重复长文。

13.2 x86 vs ARM — 不同架构的内存模型

架构内存模型实际重排acquire/release 成本seq_cst 成本

13.3 内存屏障 — 编译器屏障 vs CPU 屏障

独立 atomic_thread_fence 很少用；优先把 order 写在原子操作上。x86 上 acquire/release fence 往往只是编译器屏障，seq_cst fence 才生成 mfence。

13.4 DCL 双检锁单例 — 经典案例

C++11 之前 DCL 是反面教材（没有内存模型）。现在优先 Meyers Singleton（static 局部，语言保证线程安全），见 陷阱与风格 · 静态初始化顺序。

若必须手写 DCL：acquire 读指针、release 发指针，避免对面看到 inst != nullptr 但对象还没构造完。

ABA 问题（CAS 的经典陷阱）

T1 读到 head=A 准备 CAS(A→B)；T2 弹出 A、B 再把 A 推回去。T1 的 CAS 成功，但 A→next 已不是 B，链表损坏。解法：tagged pointer（版本号）、Hazard Pointer / RCU 延迟回收。细节见 §14。

13.6 thread_local 与 TLS 实现

thread_local 是第四种存储期：名字像全局变量，每个线程各持一份。全局是公用白板（要锁）；TLS 是每人一本笔记本。

存储期有几份活多久
automatic每次调用一份作用域结束
static进程 1 份整个进程
thread每线程 1 份该线程退出

用途：消除锁（per-thread 计数/缓冲）、隐式上下文（trace_id）、改造不可重入的全局状态。热路径统计用 TLS + 周期聚合，别让 16 核抢同一条 atomic 行。

场景不用 TLS 会怎样
per-thread 计数 / 分配缓存全局 atomic 或锁成为热点（tcmalloc tcache 就是这招）
trace_id / 租户上下文一路当参数穿栈，污染所有接口
不可重入的库缓冲多线程互踩（errno 本身就是 TLS；strtok 没做才不可重入）
每线程 RNG / 编解码 buffer共享必错或每次重建

Linux x86-64 上访问是 %fs 相对寻址，一条指令。陷阱：线程池会留下上一个任务的脏数据；协程换核后绑错线程；大数组 × 线程数吃内存；dlopen 的 so 慎用（static TLS 区有限）。&x 仍是普通指针，传给别的线程一样要遵守内存序。

陷阱怎么办
线程池脏数据（trace_id 串请求）任务边界 reset / RAII 清空
协程 / N:M 调度换核改用任务级上下文，不要绑线程
内存放大（大数组 × 线程数）TLS 只放指针，大块在堆上按需分配
析构时访问别的 TLS / 全局析构保持简单；fork 前 flush
动态初始化每次访问都有守卫能 constinit 就常量初始化

热路径统计的量级：全局 mutex 加是数百 ns～µs；全局 fetch_add(relaxed) 约 100–400 ns 且随核数恶化；TLS + 周期聚合约 1–3 ns、与核数无关。关键不是具体数字，是前两行随核数变差，第三行不变。TLS 副本用 store(load()+1) 而不是 fetch_add——只有本线程写，不必 lock 前缀；监控线程并发读，所以仍须 atomic（裸 uint64_t 写+并发读是 data race）。快照是逐线程读的，只保证近似一致。

TLS 模型适用访问代价
local-exec主程序自己的 thread_local最快：%fs + 立即数偏移，1 条指令
initial-exec启动即加载的 so多一次 GOT 读偏移
global-dynamic默认，含 dlopen 出来的 so可能每次走 __tls_get_addr

用 -ftls-model=initial-exec 可提速，但 so 必须占有限的静态 TLS 区；插件 dlopen 太多会报 cannot allocate memory in static TLS block。

13.7 std::atomic 的真相

类型is_lock_free说明
atomic<bool> / atomic<int> / atomic<T*>✅ 总是直接 CPU 原子指令
atomic<int64_t> on x64✅cmpxchg8b/lock
atomic<__int128>依赖平台x86-64 需 -mcx16 才有 cmpxchg16b
atomic<BigStruct>❌库内部用 自旋锁表（spinlock table）模拟

性能陷阱：atomic<LargeStruct> 看起来无锁，其实可能串行化——务必检查 is_lock_free() 或用 is_always_lock_free（编译期）。跨进程共享内存时这条是硬约束：内部自旋锁表在本进程私有堆上，对面进程看不见。共享内存里的 atomic<T> 必须 lock-free，否则同步语义直接垮掉。

13.8 高频面试 Q&A

点击每道题展开参考答案（先自测，再对照）。

  1. 基础volatile 能用来做多线程同步吗？

    ❌ 不能。volatile 只阻止编译器优化（缓存到寄存器、合并读写），不提供原子性、也不产生内存屏障。在 ARM 等弱序架构上必然出错。Java 的 volatile 才等同于 C++ 的 atomic。
    唯一正确用途：MMIO 内存映射寄存器、信号处理（sig_atomic_t）、setjmp/longjmp 保护的变量。

  2. 中级happens-before、synchronizes-with、sequenced-before 的关系？
    • sequenced-before：单线程内，分号前后的程序顺序
    • synchronizes-with：一个 release 的 store 与读到该值的 acquire load 之间
    • happens-before：上述二者的传递闭包——是内存可见性的"官方"定义

    若 A happens-before B，则 A 的所有副作用在 B 中可见。seq_cst 额外提供全局单一顺序。

  3. 高级memory_order_consume 为什么不推荐？

    consume 试图只保证数据依赖的顺序（比 acquire 更弱、更快，适合 RCU 指针发布）。但：

    • 编译器难以精确追踪数据依赖，几乎所有实现都把 consume 提升为 acquire
    • C++17 起标准建议"暂不使用"，C++26 可能重新设计
    • 想用的话直接写 acquire，清晰且性能差别微小
  4. 基础为什么读取未加锁的 non-atomic int 是未定义行为，即使只读？

    C++ 标准明确：非同步地并发访问同一非原子对象，且至少一方是写，就是 data race = UB。UB 意味着编译器可以假设不会发生，于是可能：

    • 把读的值缓存到寄存器永不刷新（无限循环）
    • 假设读到的值永远在某个范围内，做激进优化
    • 读撕裂（64 位值在 32 位系统上拆成两个 32 位读）

    即使你"肉眼"看代码没问题，编译器 + CPU 联合作用下就可能崩。

  5. 中级fetch_add(1, relaxed) 安全吗？

    安全——如果你只需要原子性而不需要跨线程可见性同步。典型例子：shared_ptr 的引用计数 ++ 可以 relaxed（因为拿到 shared_ptr 本身就已同步过），-- 必须 acq_rel（析构前需要看到所有之前线程的写）。

  6. 基础为什么 mutex 内部不需要用户写内存屏障？

    std::mutex::lock() 内部隐含 acquire 屏障，unlock() 隐含 release。临界区内的读写不能重排出去。所以只要"读写都在同一 mutex 保护下"，就不用关心内存序。

  7. 高级std::hardware_destructive_interference_size 和 std::hardware_constructive_interference_size 是什么？
    • destructive：避免假共享的最小对齐（通常 64 或 128B）——独立变量要分开
    • constructive：为了共享 cache line 的最大尺寸——相关数据放一起（如 key+value）

    在 Intel 新一代（如 Sapphire Rapids）由于邻近 prefetcher 存在，destructive 值可能是 128B（两条 line）。

  8. 高级生产环境如何定位内存序 Bug？
    • ThreadSanitizer (TSan)：-fsanitize=thread，检测 data race（最有效）
    • Relacy Race Detector：枚举所有可能的内存序交织，验证无锁算法
    • CppMem / Herd7：形式化工具，按 C++ 标准公理模拟所有合法执行
    • 压测 + 多平台：x86 上跑 OK 的代码必须在 ARM（如 graviton、M1）上压测
    • ThinkSanity：Meta 开源的内存模型 fuzzer
  9. 中级A 只改自己的 L1，为什么会 Invalidate B 的缓存？

    B 可能已有同一 64B 行的 Shared 副本。A 写前必须独占（Invalidate / RFO），否则 B 会读到旧值。作废的是过期副本，不是「改了 B 的数据」。粒度是行不是变量 → 同行的 count_b 被连带作废 = false sharing / HITM。

  10. 中级False sharing 为什么单核几乎无感？它和数据竞争是一类 bug 吗？

    典型病理是行在两套私有 L1 之间 ping-pong。单核两线程共用一套 L1，没有核间一致性流量；超线程通常也共享 L1。False sharing 是性能问题（MESI 流量），不是 C++ 数据竞争那种正确性 UB。单核仍会有数据竞争（count++ 交错），见 §8.1。

十四、无锁编程 (Lock-Free Programming) ⭐

CAS · ABA · 内存回收 · MPMC 队列 — 实战与陷阱

无锁编程是内存模型最深的应用。核心只有 CAS + 内存序，陷阱在回收与 ABA。绝大多数量 mutex 就够；热路径再 lock-free；实时/HFT 才值得 wait-free——过早追求 wait-free 往往单次更慢、总吞吐更差。

14.1 三级进度保证

工程选择：绝大多数场景 mutex 够用；热路径用 lock-free；实时系统（音频、内核、HFT）追求 wait-free。过早追求 wait-free 通常得不偿失——单次操作更慢，总吞吐反而降低。

14.2 CAS — 无锁编程的"汇编指令"

compare_exchange_weak 允许伪失败（ARM/POWER 的 LL/SC 被打断就会 SC 失败）。循环里用 weak；单次检查用 strong。失败时 expected 已被写成最新值，不要再 load。

T expected = v.load(std::memory_order_relaxed);
T desired;
do { desired = compute(expected); }
while (!v.compare_exchange_weak(expected, desired,
        std::memory_order_release, std::memory_order_relaxed));
变体差异用法
weak允许伪失败循环内首选（LL/SC 上更快）
strong不会伪失败单次 check，不在循环里

14.3 CAS vs FAA

方案竞争下何时用
CAS 循环 cas(x, x+1)平均 O(N) 重试，吞吐随核数掉新值依赖旧值的复杂计算
FAA fetch_add(1)硬件一次成功盲加、位或/位与优先 FAA / fetch_or

14.4–14.7 无锁结构怎么选

Treiber 栈是 CAS 换链表头；pop 时读 old->next 若节点已被回收就是 use-after-free，必须配 Hazard Pointer / RCU。ABA：指针值回到 A，但背后的世界已经变了——tagged pointer 防 ABA，回收方案防 UAF。链表版 Michael-Scott 正确但分配多；数组版 Vyukov 用槽位序号做同步，cache 更友好。SPSC 是最快的无锁结构：单产单消，两个 atomic 指针即可，完全不需要 CAS；音频回调、日志消费者是典型场景。

结构要点典型实现
MPMC 链表（Michael-Scott）教科书正确，new/delete + cache miss 多教学 / 无界队列
MPMC 环形（Vyukov）槽位 seq + CAS 推进，零分配moodycamel::ConcurrentQueue
SPSC 环单产单消，两个 atomic 指针即可，不用 CASDPDK / Disruptor / boost spsc

SPSC 热路径约 10–20 ns 量级；head/tail 必须各占一行，避免假共享。

ABA / UAF 解法原理代价
Tagged Pointer / DCAS指针 + 版本号一起 CASx86 需 cmpxchg16b；只防 ABA，不防 UAF
Hazard Pointer每线程声明正在用的指针，回收前扫描读端一次 store + fence
RCU / Epoch等所有读者退出临界区再 free读端可做到零开销（QSBR）
对象池 / arena不 delete，整体释放实现简单，内存峰值高

14.8 节点回收

无锁最大的坑不是 CAS，是何时 delete。三种延后回收本质相同：读者声明「我还在用」，写者等声明消失再释放。

RCU 实现grace period 怎么探测读端开销
Classic / sleepable等所有 CPU 经历一次上下文切换零（内核里禁抢占）
QSBR线程在静止点显式上报（如 epoll 返回后）零
Memory Barrier RCUlock/unlock 原子计数，写者等清零每临界区 2 次 store
方案读开销适用标准化
Hazard Pointer1 store + fence栈/队列/树，指针复杂C++26 std::hazard_pointer
RCU / QSBR0（要有静止点）读极重、写罕见（路由/配置）C++26 std::rcu
Epoch (EBR)1 load + 1 store折中folly / crossbeam
atomic<shared_ptr>原子 refcount非热路径、求简单C++20

C++26 落地前用 folly::hazptr / folly::rcu 或 liburcu。生产上优先成熟库，自己写无锁几乎必有 bug。

Hazard Pointer 的读端关键是双重检查：把指针写入本线程 hazard slot 之后，必须再 load 一次源指针，确认登记期间没被换走。RCU 写端用 synchronize_rcu() 阻塞等 grace period，或 call_rcu 把释放丢给后台。选型：读极重写罕见 → RCU；读写接近且指针复杂 → Hazard Pointer；非热路径 → atomic<shared_ptr>。

14.12 面试高频题

点击每道题展开参考答案（先自测，再对照）。

  1. 基础mutex 是无锁的吗？spinlock 是无锁的吗？

    都不是。lock-free 的定义是"任一线程在有限步内能让系统整体前进"——而持锁线程挂起后，其他线程无法前进。
    但 spinlock 比 mutex 轻量（不涉及内核切换），在极短临界区 + 多核时比 mutex 快。

  2. 中级为什么 CAS 循环要用 weak 不用 strong？

    ARM/POWER 用 LL/SC 实现原子操作，"LL 到 SC 之间被中断"就 SC 失败——这就是所谓伪失败（spurious fail）。compare_exchange_weak 允许伪失败，硬件不需要内部 retry；strong 需要库/硬件保证无伪失败，在 LL/SC 架构上就是内部循环。既然外层已经有循环，weak 更高效。

  3. 高级如何安全地在无锁栈里 delete 节点？

    必须解决 use-after-free：其他线程可能还持有指向该节点的指针（CAS 正在进行）。方案：

    1. Hazard Pointer：每线程声明当前访问的指针，free 前扫描
    2. RCU / Epoch：延迟到所有线程退出读临界区
    3. Tagged Pointer：不能防 use-after-free，只防 ABA——仍需上面任一机制回收
    4. 不 delete：用对象池/arena，整体释放
  4. 基础std::shared_ptr 的引用计数真的线程安全吗？

    ✅ 控制块的计数是 atomic 的，++/-- 安全。
    ❌ shared_ptr 对象本身的 =/reset() 不安全——多线程同写同一 shared_ptr 变量是 data race。
    若需要对 shared_ptr 变量的并发读写，C++20 提供 std::atomic<std::shared_ptr<T>>。

  5. 高级fetch_add 在 x86 和 ARM 上如何实现？
    • x86：lock xadd 单条指令，带 MFENCE 语义
    • ARMv8.1-A LSE：ldadd 单条指令（large system extension）
    • ARMv8 基础：ldaxr + stlxr 循环（LL/SC），relaxed 用 ldxr + stxr

    推论：ARM 老平台上 fetch_add 本质是 CAS 循环，并不比自己写 CAS 快；新平台(苹果 M1/M2/M3、AWS Graviton 3+) 已有 LSE，性能接近 x86。

  6. 中级为什么 LMAX Disruptor 号称比无锁队列更快？
    • 环形 buffer，预分配——无 malloc/free
    • sequence barrier 协议，读写各自 cache line 独立（零假共享）
    • batch 处理：消费者一次性处理多个 slot，分摊 cache miss
    • 对 JVM 还有对象复用避免 GC 压力（C++ 版本收益略小）

    本质是机械同情 (Mechanical Sympathy)：理解 CPU 硬件特性并顺从之。

  7. 高级如何证明一个无锁算法正确？
    1. 人工推理：对所有可能的操作交织，画出 happens-before 图
    2. Linearizability 证明：每个操作能找到一个"瞬时点"，等价于串行执行
    3. Relacy / CDSChecker：自动枚举所有合法内存序执行
    4. TSan + 多核多平台压测：发现 data race / ABA
    5. Formal proof：TLA+、Coq——仅关键算法值得投入

    实践建议：优先用成熟库（folly、concurrentqueue、liburcu），自己实现的无锁代码几乎肯定有 bug。

  8. 中级什么时候一定不要用无锁？
    • 临界区超过几百条指令（长临界区下 mutex 更优，reduce retry 消耗）
    • 团队能力不足、缺少压测/验证基础设施
    • 只跑在单核 / GIL 型语言环境
    • 性能瓶颈经 profile 不在同步（提前优化是万恶之源）
