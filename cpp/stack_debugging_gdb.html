01

递归为什么会 Stack Overflow

每层递归一个栈帧，栈只增不减就会撞墙

void foo() {
    foo();          // 无终止条件的递归
}

结合 03 篇的栈帧模型：每次 foo() 调用都压入一个新栈帧（返回地址 + 局部数据），而它永远不返回，栈只增不减：

高地址 ↑
foo frame #1
foo frame #2
foo frame #3
foo frame #4 …← 不断向下增长
低地址 ↓ 触及栈边界（guard page）→ SIGSEGV

▲ 栈持续向低地址生长，越过保护页即崩溃

Linux 主线程栈默认 8 MB。栈生长到边界会撞上一个不可访问的保护页（guard page），触发 SIGSEGV，程序崩溃。这就是 Stack Overflow 的物理真相。

影响递归深度的因素
  • 每帧大小：局部变量越多，单帧越大，能递归的层数越少；
  • 栈总大小：可用 ulimit -s 查看/调整，或线程创建时设置；
  • 尾调用优化：若写成尾递归且编译器优化（复用同一帧），可能不再溢出 —— 但不可默认依赖，C++ 不保证 TCO。

工程建议：深度不可控的递归应改写为显式栈的迭代（把递归转成循环 + 手动栈），从根本上避免栈溢出，也便于设置容量上限。

02

局部变量过大：栈 vs 堆

一个大数组就能瞬间压垮栈

void foo() {
    char buffer[1024 * 1024];   // 1 MB 局部数组，全在栈上！
    ...
}

局部数组分配在栈帧里。一个 1 MB 的 buffer 会让这一层栈帧直接 sub rsp, 1MB，几层就能耗尽 8 MB 的栈 —— 即使没有递归也会溢出。

维度栈（Stack）堆（Heap）
分配方式移动 RSP，几乎零成本malloc/new，需管理器记账
容量小（默认 ~8 MB）大（受物理/虚拟内存限制）
生命周期随函数返回自动回收手动 free/delete 或智能指针
速度极快较慢（可能加锁、碎片）
适合小而短命的局部对象大对象、生命周期跨函数

经验法则：大缓冲区、大容器、生命周期不确定的对象放堆（std::vector、new、智能指针）；小而短命的放栈。把 1 MB 数组换成 std::vector<char> buffer(1024*1024);，数据就搬到堆上，栈帧只留一个几十字节的 vector 头。

03

GDB 查看栈：bt / frame / info

把 03 篇的「返回地址链」变成看得见的命令

命令作用
bt / backtrace打印完整调用栈（每层一帧）
frame N / f N切换到第 N 层栈帧，查看它的局部/参数
info frame当前帧的细节：RBP/RSP、返回地址、保存的寄存器位置
info args / info locals当前帧的参数 / 局部变量
info registers / i r所有寄存器当前值（RIP/RSP/RBP/RDI…）

以 main → foo → bar → baz 为例，在 baz 里断下后 bt：

(gdb) bt
#0  baz () at demo.cpp:9
#1  bar () at demo.cpp:6
#2  foo () at demo.cpp:3
#3  main () at demo.cpp:13

(gdb) frame 1              # 跳到 bar 那一帧
#1  bar () at demo.cpp:6
(gdb) info frame          # 看这帧的 RBP、返回地址在哪
(gdb) info locals         # 看 bar 的局部变量

回顾 03 篇：这张 #0…#3 的表，正是 GDB 顺着栈上的返回地址链（有帧指针时用 RBP 链，否则用 DWARF CFI）逐层回溯、再用调试信息翻译出的结果。命令背后就是前面讲的机制。

04

用 disassemble 把源码/汇编/寄存器串起来

这是整个系列的「合流点」

(gdb) disassemble          # 反汇编当前函数，标出下一条要执行的指令(=>)
(gdb) disassemble /s       # 汇编与源码行交错显示，对照最直观
(gdb) x/4xg $rsp           # 以 16 进制查看栈顶 4 个 8 字节（看返回地址等）
(gdb) p $rip  p $rsp  p $rbp   # 打印关键寄存器
(gdb) si                   # 单步一条机器指令，观察 RSP/RBP 变化

把这些命令组合起来，就能亲眼见证前五篇讲的每一步：

C++ 源码 disassemble /s
↓
汇编指令 call / ret / sub rsp
↓
寄存器 info registers
↓
Stack Frame x/xg $rsp · info frame

操作流：在 call 处 si 步入，观察 RSP 减 8（压了返回地址，03 篇）；进入序言看 RBP 被建立（02 篇）；info args 看参数确实来自 RDI/RSI（04 篇）。至此，抽象模型与运行现场完全对上号。

05

AddressSanitizer 抓栈相关内存错误

很多栈问题不会立刻崩，ASan 让它们当场暴露

编译时加 -fsanitize=address -g，运行时 ASan 会在栈/堆对象周围插入红区（redzone）并监控访问，越界立刻报错并打印栈回溯。它擅长逮住三类栈相关问题：

错误类型含义典型代码
stack-buffer-overflow局部数组越界读写int a[4]; a[4]=1;
stack-use-after-scope用了已离开作用域的局部对象返回/保存了块内局部变量的指针
stack-use-after-return用了已返回函数的栈变量地址int* p = f(); *p;（f 返回局部地址）
 
# 编译并运行
g++ -fsanitize=address -g demo.cpp -o demo
./demo

# 典型报错（节选）
==12345==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x...
WRITE of size 4 at 0x... thread T0
    #0 0x... in foo() demo.cpp:5
    #1 0x... in main demo.cpp:12
  Address ... is located in stack of thread T0
为什么需要 ASan？

栈越界经常「碰巧不崩」—— 覆盖的是相邻变量或填充字节，程序继续跑，bug 潜伏很久。ASan 把「悄悄的破坏」变成「当场的报错 + 精确行号 + 栈回溯」，是排查栈内存问题的利器。代价是约 2× 运行变慢、内存增加，通常只在测试/CI 开启。

检测栈溢出（爆栈）本身，ASan 也能识别为 stack-overflow；配合 Sanitizer 原理一篇可深入其实现。

06

完整调试串联：一次实战

从崩溃到定位，用上整个系列的知识

  1. 复现并抓崩溃：ulimit -c unlimited 开 core dump，或直接 gdb ./demo 运行到崩溃。
  2. 看调用栈：bt。若打印出成百上千层同名帧 → 无限递归 / 栈溢出（§01）。
  3. 看某帧：frame N + info locals，发现某个巨大局部数组 → 大对象爆栈（§02）。
  4. 下探指令：disassemble /s + info registers，确认 RSP 已越界、或返回地址被写坏（§03/§04）。
  5. 上 ASan 复测：-fsanitize=address 重新编译，让越界/悬垂当场报出精确位置（§05）。
  6. 修复：大对象搬堆、递归改迭代、修正越界索引、避免返回局部地址。

回到系列开篇的那个问题 —— 「执行 foo(a,b) 时 CPU 到底发生了什么」：现在你能从参数进寄存器、call 压返回地址、建立栈帧、执行、返回值进 RAX、ret 恢复调用者，一路讲清；并能用 g++ -S、objdump、gdb、-O0/-O2、ASan 亲手观察与验证。底层认知模型就此闭环。

07

核心结论

  • 递归/大局部对象都会耗栈：每帧占空间、栈只增不减到边界即 SIGSEGV。
  • 大对象放堆、深递归改迭代，是避免栈溢出的根本手段。
  • bt / frame / info frame / info registers / disassemble 能把源码、汇编、寄存器、栈帧串成一条线。
  • GDB 回溯的本质是读栈上的返回地址链 + 调试信息，与前面机制一致。
  • ASan 把潜伏的栈越界/悬垂变成当场报错，是测试期利器。
08

常见误区

❌ 尾递归一定不会栈溢出。 只有编译器实施了 TCO 才复用栈帧，C++ 不保证，不能默认依赖。

❌ 局部数组多大都行。 局部对象在栈上，几 MB 就可能爆掉 8 MB 的栈。

❌ 没崩就说明没有栈越界。 越界常「碰巧不崩」，潜伏很久；需要 ASan 才能可靠暴露。

❌ 返回局部变量的指针/引用没问题。 函数返回后其栈帧被回收，该地址悬垂，是 use-after-return。

❌ GDB backtrace 靠猜。 它读取真实的返回地址链，再用 DWARF 调试信息翻译。

09

面试问题

点击每道题展开参考答案（先自测，再对照）。

  1. 基础为什么递归可能导致 Stack Overflow？

    每层递归压入一个栈帧且未返回，栈持续向低地址增长，触及线程栈边界的保护页即触发 SIGSEGV。

  2. 基础栈和堆有什么区别？大对象该放哪？

    栈：移动 RSP 分配、极快、容量小、随返回自动回收；堆：malloc/new、容量大、需手动或智能指针管理。大对象/长生命周期放堆。

  3. 原理为什么 GDB 可以 backtrace？

    调用栈上保存着每层返回地址，GDB 用帧指针链或 DWARF CFI 逐帧回溯，再用调试信息映射到函数名与源码行。

  4. 工具GDB 里哪些命令能看栈帧和寄存器？

    bt 看调用栈、frame N 切帧、info frame 看帧细节、info args/locals 看参数与局部、info registers 看寄存器、disassemble 反汇编。

  5. 工具如何把源码、汇编、寄存器、栈帧对应起来？

    disassemble /s 交错显示源码与汇编，info registers 看寄存器，x/xg $rsp 看栈内容，si 单步观察 RSP/RBP 变化。

  6. 实战ASan 能发现哪些栈相关问题？

    stack-buffer-overflow（局部数组越界）、stack-use-after-scope、stack-use-after-return，以及爆栈 stack-overflow，并给出精确位置与栈回溯。

  7. 进阶如何避免深度不可控的递归导致崩溃？

    改写为显式栈的迭代、限制递归深度、增大线程栈、或依赖可保证的尾调用优化（谨慎）。

  8. 进阶返回局部变量地址为什么危险？如何定位？

    函数返回后其栈帧被回收，指针悬垂，后续访问是未定义行为。用 ASan（use-after-return）或编译器 -Wreturn-local-addr 警告定位。
