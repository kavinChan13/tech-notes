Apache Kafka 核心

架构概念

概念含义类比
Topic消息的逻辑分类数据库表
PartitionTopic 的物理分片，有序不可变日志分区表
Producer发送消息到 Topic写入者
Consumer从 Topic 读取消息读取者
Consumer Group消费者组，组内分摊消费，组间独立订阅者组
BrokerKafka 服务节点服务器实例
Offset消息在 Partition 中的位置行号
Producer → Topic [P0|P1|P2] → Consumer Group A [C1|C2]
                                            → Consumer Group B [C3]

核心特性

  • 高吞吐：顺序写磁盘 + Page Cache + 零拷贝（sendfile），单 Broker 百万消息/秒
  • 持久化：消息持久化到磁盘日志文件，Retention 可配（时间/大小）
  • 水平扩展：增加 Partition 提升并行度，增加 Broker 扩展容量
  • 回溯消费：Consumer 可重置 Offset 重新消费历史消息
  • 副本机制：每个 Partition 有 Leader + ISR（In-Sync Replicas）

Kafka 配置要点

# Producer 关键配置
acks=all                    # 所有 ISR 副本确认（最安全）
retries=3                   # 自动重试
enable.idempotence=true     # 幂等生产（防止重复消息）

# Consumer 关键配置
group.id=my-group
auto.offset.reset=earliest  # 无 Offset 时从头消费
enable.auto.commit=false    # 手动提交 Offset（精确控制）
max.poll.records=500        # 单次拉取最大消息数
  • Kafka 高吞吐的三大支柱：顺序写磁盘、Page Cache、零拷贝
  • Partition 数 = Consumer Group 内最大并行度（1 Partition 只分配给 1 Consumer）
  • acks=all + enable.idempotence=true 是生产环境的推荐配置

流处理：Apache Flink

Flink 核心概念

概念含义
DataStream无界数据流（流处理）
DataSet有界数据集（批处理，Table API 统一后趋淡化）
Window将无界流切分为有限块进行计算
State算子本地状态（支持 Checkpoint 容错）
Checkpoint分布式快照，保证 Exactly-Once 语义
Watermark事件时间进度标记，处理乱序数据

窗口类型

窗口类型描述示例
Tumbling Window固定大小不重叠每 5 分钟计算一次
Sliding Window固定大小可重叠窗口 10 分钟，每 5 分钟滑动
Session Window按会话间隔划分10 分钟无活动则关闭窗口
Global Window全局窗口需自定义触发器自定义聚合
// Flink 实时统计每5分钟请求数
DataStream<Event> events = env.addSource(kafkaSource);

events
  .keyBy(Event::getUserId)
  .window(TumblingEventTimeWindows.of(Time.minutes(5)))
  .aggregate(new CountAggregator())
  .addSink(new ElasticsearchSink(...));

Checkpoint 与 Exactly-Once

  • 基于 Chandy-Lamport 分布式快照算法
  • Barrier 在数据流中传播，触发各算子快照
  • 快照存储到 State Backend（RocksDB / Memory / HDFS）
  • 故障恢复：从最近 Checkpoint 重新启动，源端重放数据
  • 端到端 Exactly-Once 需要 Source 可回放 + Sink 支持事务（如 Kafka 事务）
  • Flink 的 Checkpoint 机制（Chandy-Lamport + Barrier）是实现 Exactly-Once 的关键
  • Event Time vs Processing Time：Event Time 保证结果确定性但需处理 Watermark 和乱序
  • Flink 已成为流批一体的事实标准，逐步替代 Spark Streaming
03

批处理：Apache Spark

Spark 核心架构

  • Driver：提交 Job、创建 DAG、调度 Task
  • Executor：执行 Task、存储数据
  • RDD（Resilient Distributed Dataset）：不可变分布式数据集
  • DataFrame / Dataset：带 Schema 的结构化 API（推荐使用）
  • Catalyst 优化器：自动优化查询计划（谓词下推、列裁剪等）

Spark vs Flink

维度Apache SparkApache Flink
设计理念批处理优先（微批做流）流处理优先（流做批）
流处理延迟秒级（Structured Streaming）毫秒级（真正的事件驱动）
状态管理有限原生丰富（Keyed State / Operator State）
Exactly-Once端到端支持（微批）端到端支持（Checkpoint）
生态ML（MLlib）、图（GraphX）、SQL流处理最强、SQL、CEP
适用场景大规模 ETL / 数据分析 / ML实时事件处理 / 实时分析
  • Spark 是"微批"模拟流处理（延迟秒级），Flink 是真正的事件驱动流处理（延迟毫秒级）
  • Spark 在批处理和 ML 生态上仍占优势
  • 流批一体趋势：Flink 的 Table API 和 Spark 的 Structured Streaming 都在融合

CDC 与 Debezium

CDC 监听数据库的数据变更（INSERT/UPDATE/DELETE），实时同步到下游系统

变更数据捕获（CDC）

CDC 监听数据库的数据变更（INSERT/UPDATE/DELETE），实时同步到下游系统。

CDC 实现方式

方式原理优缺点
基于查询定时轮询（WHERE updated_at > last_sync）简单但有延迟、可能遗漏 DELETE
基于触发器数据库触发器写变更日志表实时但侵入性强、影响性能
基于日志解析数据库事务日志（Binlog/WAL）无侵入、实时、推荐方案

Debezium 架构

MySQL Binlog / PG WAL → Debezium Connector → Kafka Topic → 下游消费者
  • 支持 MySQL、PostgreSQL、MongoDB、SQL Server、Oracle 等
  • 作为 Kafka Connect 的 Source Connector 运行
  • 支持全量快照 + 增量 CDC 无缝衔接
  • 每条变更事件包含：before（旧值）、after（新值）、source（元数据）
// Debezium CDC 事件示例
{
  "before": {"id": 1, "name": "旧名称", "status": "active"},
  "after":  {"id": 1, "name": "新名称", "status": "active"},
  "source": {"db": "mydb", "table": "users", "ts_ms": 1700000000},
  "op": "u"  // c=create, u=update, d=delete, r=read(snapshot)
}
  • 基于日志的 CDC 是最推荐的方式 — 无侵入、低延迟、可靠
  • Debezium 的全量快照 + 增量 CDC 无缝衔接能力是生产必需
  • CDC 是构建实时数据管道的基石：DB → Kafka → 数仓/搜索/缓存
05

Lambda / Kappa 架构

融合数据湖 + 数据仓库的优点：

Lambda 架构

数据源 → Batch Layer（Spark / Hive → 全量精确结果）
数据源 → Speed Layer（Flink / Storm → 实时近似结果）

Serving Layer = Batch 结果 ∪ Speed 结果
  • Batch Layer：定期全量重算，结果精确但有延迟（小时级）
  • Speed Layer：实时增量计算，结果即时但可能不精确
  • Serving Layer：合并两层结果对外提供服务
  • 缺点：需要维护两套代码（批 + 流），逻辑一致性难保证

Kappa 架构

数据源 → Kafka（不可变日志） → Stream Processing（Flink） → Serving Layer
  • 只用一套流处理代码替代 Lambda 的两层
  • 需要重算时：从 Kafka 回溯消费重放
  • 前提：消息系统支持足够长的 Retention
  • 优势：代码单一、维护简单、逻辑一致
  • 劣势：极大历史数据重放成本高、依赖可回溯消息系统

现代选择：Lakehouse 架构

融合数据湖 + 数据仓库的优点：

  • 开放表格式（Iceberg / Delta Lake / Hudi）+ 计算引擎（Spark / Flink / Trino）
  • ACID 事务 + Schema 演进 + 时间旅行
  • 同时支持 ETL / BI / ML 工作负载
  • Lambda 的核心问题：两套代码（流+批）维护成本高 → Kappa 用流统一解决
  • Kappa 的核心前提：消息系统（Kafka）能存足够长时间的历史数据
  • Lakehouse 是当前数据架构的主流趋势（Iceberg / Delta Lake）
06

AI 特征管道与 Exactly-Once 语义

AI 特征管道

原始数据 → 特征计算（Flink/Spark） → Feature Store → 模型训练/推理
  • 离线特征：Spark 批处理计算历史特征（训练用）
  • 实时特征：Flink 流处理计算实时特征（推理用）
  • Feature Store：统一管理离线/在线特征（Feast / Tecton / Hopsworks）
  • 训练-推理一致性：确保训练时和推理时使用相同的特征计算逻辑

Exactly-Once 语义

语义级别含义实现难度
At-Most-Once消息最多处理一次（可能丢失）最低
At-Least-Once消息至少处理一次（可能重复）中等
Exactly-Once消息恰好处理一次（不丢不重）最高

端到端 Exactly-Once 实现

  • Source：可回放（Kafka 支持重置 Offset）
  • Processing：Flink Checkpoint（分布式快照）
  • Sink：幂等写入或事务写入（Kafka Transactions / 数据库 UPSERT）
Exactly-Once = 可回放 Source + Checkpoint + 幂等/事务 Sink
  • Exactly-Once 不是"只发一次"，而是"效果等同于只处理一次"
  • Feature Store 解决训练-推理数据偏差（Training-Serving Skew）
  • 端到端 Exactly-Once 需要 Source + Processing + Sink 三方协同

🎯 Q&A

分三个环节保证：① Producer ：设置 acks=all （所有 ISR 副本确认）+…
Q1：Kafka 如何保证消息不丢失？

分三个环节保证：① Producer：设置 acks=all（所有 ISR 副本确认）+ retries > 0 + enable.idempotence=true（幂等防重复），确保消息写入所有副本。② Broker：设置 min.insync.replicas >= 2（至少 2 个副本同步），配合 acks=all 保证数据在至少 2 个 Broker 上持久化；合理设置 Partition 副本数（通常 3 副本）。③ Consumer：关闭自动提交（enable.auto.commit=false），处理完消息后手动提交 Offset，避免消息未处理就被标记已消费。三者协同实现端到端的不丢失。但需注意：这会降低吞吐并增加延迟，需根据业务权衡。

Q2：Flink 的 Checkpoint 机制如何实现 Exactly-Once？

Flink 基于 Chandy-Lamport 分布式快照算法：① JobManager 定期向 Source 注入 Checkpoint Barrier（特殊标记）；② Barrier 随数据流向下游传播，每个算子收到 Barrier 后将本地 State 快照到 State Backend（RocksDB/HDFS）；③ 所有算子完成快照后，JobManager 标记此 Checkpoint 完成。故障恢复时：回滚到最近完成的 Checkpoint，Source 从对应 Offset 重新消费。这保证了处理层的 Exactly-Once。端到端还需：Source 可回放（Kafka 的 Offset 重置）+ Sink 幂等或事务（如 Kafka 的两阶段提交 TwoPhaseCommitSinkFunction）。

Q3：什么是 CDC？Debezium 如何工作？

CDC（Change Data Capture）是捕获数据库变更（INSERT/UPDATE/DELETE）并实时同步到下游的技术。Debezium 基于日志解析实现：① 对 MySQL 读取 Binlog，对 PostgreSQL 读取 WAL 逻辑解码；② 作为 Kafka Connect Source Connector 运行，将变更事件实时写入 Kafka Topic；③ 每条事件包含 before/after 值、操作类型（c/u/d/r）、源数据库元信息。首次启动时执行全量快照（Snapshot），之后进入增量 CDC 模式。优势：对源数据库无侵入（不改 Schema、不加触发器）、延迟低（毫秒级）、可靠（基于数据库原生日志）。

Q4：Lambda 架构和 Kappa 架构的核心区别是什么？

Lambda 架构将数据管道分为两层：Batch Layer（全量重算，精确但延迟高）和 Speed Layer（增量实时，低延迟但可能不精确），Serving Layer 合并两者结果。核心问题：需要维护两套逻辑（批处理代码 + 流处理代码），一致性难保证，开发维护成本高。Kappa 架构只保留流处理层，所有数据通过 Kafka 这样的可回溯日志系统流入单一的流处理引擎（如 Flink）。需要重算时直接从 Kafka 重放历史数据。优势是单一代码、逻辑一致。劣势是海量历史数据重放成本高。现代趋势是 Lakehouse 架构（Delta Lake/Iceberg），融合了批流一体 + 数据湖的优点。

Q5：数据湖表格式（Iceberg/Delta Lake/Hudi）解决了什么问题？

传统数据湖（HDFS/S3 + Parquet）的核心痛点：① 无 ACID 事务 — 并发写入可能数据损坏；② 无 Schema 演进 — 加列/改类型需全量重写；③ 无高效更新 — Parquet 文件不可变，UPSERT 需全量重写；④ 无时间旅行 — 无法查看历史版本。开放表格式解决这些问题：Iceberg：Snapshot 隔离 + 隐式分区 + 全功能 Schema 演进，社区最活跃；Delta Lake：Databricks 主导，与 Spark 深度集成，事务日志设计；Hudi：Uber 开源，CDC + 增量处理最强，Copy-on-Write/Merge-on-Read 两种表类型。三者都实现了 ACID + 时间旅行 + 高效 UPSERT，区别在生态和特性侧重。
