00

为什么一定要自己动手搭一套

看懂 ≠ 会用

大数据的门槛不在概念，而在组件多、要互相连、环境难搭。容器化把它变成一条命令，也让「弄坏了重来」的成本归零。

光看菜谱学不会火候。这里是一间灶台锅具都配齐的迷你厨房，照步骤做出「实时数据入湖」这道菜；坏了 down -v 重来。

0.1 先看机器扛不扛得住

Spark 与 Trino 是 JVM 大户。内存不够是本地搭栈失败的第一名，先核对再动手。

Docker 内存6 GB8–10 GBdocker info --format '{{.MemTotal}}'
空闲磁盘15 GB25 GBdocker system df
Composev2v2.20+docker compose version
系统Linux / macOS / WSL2PowerShell 续行用 `

一份 compose · 五个角色 · 几分钟就绪

1.1 拓扑：五个角色、七个端口

端口服务用途怎么确认它活着

9000minioS3 APIcurl -s localhost:9000/minio/health/live
9001minio控制台 admin/password能登录，有 warehouse 桶
8181iceberg-rest表指针 catalogcurl -s localhost:8181/v1/config 有 JSON
8888sparkJupyter页面能打开
8080sparkSpark UI有 Streaming Query
8088trinoSQL（容器内 8080）SHOW CATALOGS 有 iceberg

1.2 容器内外是两套地址

坑一半出在这里：同一个 Kafka，宿主机脚本写 localhost:9092，容器里的 Spark 写 kafka:9092——一个走端口映射，一个走 Compose 的 DNS。

1.3 docker-compose.yml（直接抄）

# docker-compose.yml —— 本地迷你数据栈（学习用，非生产配置）
services:
  kafka:                                # 单节点 KRaft 模式，免 ZooKeeper
    image: bitnami/kafka:3.7
    ports: ["9092:9092"]
    environment:
      KAFKA_CFG_NODE_ID: 0
      KAFKA_CFG_PROCESS_ROLES: controller,broker
      KAFKA_CFG_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093
      KAFKA_CFG_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092
      KAFKA_CFG_CONTROLLER_QUORUM_VOTERS: 0@kafka:9093
      KAFKA_CFG_CONTROLLER_LISTENER_NAMES: CONTROLLER
      ALLOW_PLAINTEXT_LISTENER: "yes"

  minio:                                # 对象存储（S3 兼容）
    image: minio/minio
    ports: ["9000:9000", "9001:9001"]   # 9001 是控制台
    environment:
      MINIO_ROOT_USER: admin
      MINIO_ROOT_PASSWORD: password
    command: server /data --console-address ":9001"

  mc:                                   # 启动后自动建 bucket
    image: minio/mc
    depends_on: [minio]
    entrypoint: >
      /bin/sh -c "
      until mc alias set m http://minio:9000 admin password; do sleep 2; done;
      mc mb -p m/warehouse; mc anonymous set public m/warehouse; "

  iceberg-rest:                         # Iceberg REST Catalog（保管表指针，D11）
    image: tabulario/iceberg-rest
    ports: ["8181:8181"]
    depends_on: [minio]
    environment:
      CATALOG_WAREHOUSE: s3://warehouse/
      CATALOG_IO__IMPL: org.apache.iceberg.aws.s3.S3FileIO
      CATALOG_S3_ENDPOINT: http://minio:9000
      AWS_ACCESS_KEY_ID: admin
      AWS_SECRET_ACCESS_KEY: password
      AWS_REGION: us-east-1

  spark:                                # Spark + Iceberg，用来跑入湖与查询
    image: tabulario/spark-iceberg
    depends_on: [iceberg-rest, minio]
    ports: ["8888:8888", "8080:8080"]   # 8888 Jupyter, 8080 Spark UI
    environment:
      AWS_ACCESS_KEY_ID: admin
      AWS_SECRET_ACCESS_KEY: password
      AWS_REGION: us-east-1

  trino:                                # 交互式 SQL 查询引擎（D07）
    image: trinodb/trino:latest
    ports: ["8088:8080"]
    depends_on: [iceberg-rest]

1.4 阶段一：准备 → 拉起 → 等就绪

整段可连续贴进终端。两个 until 是关键：Up 只说明进程活着，不代表能接请求——多数「连不上」都栽在这里。

# ── 准备：建目录，把上面那份 YAML 存成 ./docker-compose.yml ──
mkdir -p ~/bigdata-lab && cd ~/bigdata-lab
docker compose config -q            # 无输出 = YAML 语法没问题

# ── 拉起：首次要下 ~6GB 镜像，5~10 分钟 ──
docker compose up -d

# ── 等就绪：Up ≠ 能用，必须等到健康探针通过 ──
until curl -sf localhost:9000/minio/health/live; do sleep 2; done
until curl -sf localhost:8181/v1/config >/dev/null; do sleep 2; done
docker compose ps --format 'table {{.Service}}\t{{.Status}}'

# 期望输出：kafka / minio / iceberg-rest / spark / trino 五行都是 Up
# mc 这一行显示 Exited (0) 是正常的——它建完 bucket 就退出了
它和云上的「Iceberg on S3 + Trino/Spark」架构同构，只是缩到一台机器。存算分离见 存储与数据架构 · 存储分层。

① 造数据：源源不断写进 Kafka

模拟业务系统产生订单事件流

整条链路六段，每段都有一个「看到这个才算过」的判据，做完一步就回来对一次。

生产者模拟业务系统：每 0.3 秒造一条订单事件丢进 orders。

# producer.py —— 每 0.3 秒造一条订单事件丢进 Kafka
import json, time, random, datetime
from kafka import KafkaProducer   # pip install kafka-python

p = KafkaProducer(bootstrap_servers="localhost:9092",
                  value_serializer=lambda v: json.dumps(v).encode())
cities = ["BJ", "SH", "GZ", "SZ"]
oid = 0
while True:
    oid += 1
    evt = {
        "order_id": oid,
        "city": random.choice(cities),
        "amount": round(random.uniform(10, 500), 2),
        "event_time": datetime.datetime.now().isoformat(),
    }
    p.send("orders", evt)
    print("sent", evt)
    time.sleep(0.3)
# ── 阶段二：建 topic → 灌数据 → 立刻验证 ──
docker compose exec kafka kafka-topics.sh --create \
  --topic orders --bootstrap-server localhost:9092 \
  --partitions 3 --replication-factor 1

docker compose exec kafka kafka-topics.sh --describe \
  --topic orders --bootstrap-server localhost:9092
# 判据：输出里有 PartitionCount: 3

pip install kafka-python
python producer.py &                # 后台持续造数，终端会刷 sent {...}

# 另开一个终端，用控制台消费者确认数据真的进去了
docker compose exec kafka kafka-console-consumer.sh \
  --topic orders --bootstrap-server localhost:9092 \
  --from-beginning --max-messages 5
# 判据：打印出 5 条 JSON 就退出。看到 JSON = 摄取这一段通了
命令目的判据（看到什么才算过）
kafka-topics.sh --create建 topicCreated topic orders；报 already exists 也算过
kafka-topics.sh --describe确认分区数PartitionCount: 3
python producer.py持续造事件每 0.3 秒刷一行 sent，不报连接异常
kafka-console-consumer.sh独立验证打印 JSON 后退出；卡住 = 没写进去
--from-beginning 能倒回去重读，这正是「可重放 commit log」的价值：生产与消费彻底解耦。见 Topic / Partition / Offset。
03

② 流式入湖：Kafka → Iceberg 表

两种写法任选 · Spark Structured Streaming 或 Flink SQL

把订单流写进一张 Iceberg 表（文件落 MinIO）。两种写法的差别不在语法，而在何时提交新快照。

维度Spark Structured StreamingFlink SQL
执行模型微批：攒一批算一批连续流：来一条算一条
延迟秒 ~ 分钟（trigger 间隔）亚秒 ~ 秒
提交时机每个微批结束每次 checkpoint 完成
写法PySpark / Scala纯 SQL，一条 INSERT
本地代价镜像已预置 Iceberg另起 JobManager / TaskManager
选它当已有 Spark 批链路可复用延迟敏感的纯流场景

3.1 写法 A：Spark Structured Streaming

# ── 阶段三：进容器建表，再起一个流作业持续入湖 ──
docker compose exec spark spark-sql
# 镜像已预置 Iceberg 包与 REST catalog 配置，直接建表：

-- 隐藏分区按天：查询不必写 partition 列，Iceberg 自己裁剪
CREATE TABLE demo.db.orders (
  order_id BIGINT, city STRING, amount DOUBLE, event_time TIMESTAMP)
USING iceberg
PARTITIONED BY (days(event_time));
-- 判据：SHOW TABLES IN demo.db 能看到 orders

# 退出 spark-sql，改开 PySpark 起流作业：
# 从 Kafka 读流 → 解析 JSON → 追加写 Iceberg（微批）
from pyspark.sql.functions import from_json, col
from pyspark.sql.types import *

schema = "order_id LONG, city STRING, amount DOUBLE, event_time TIMESTAMP"
df = (spark.readStream.format("kafka")
        .option("kafka.bootstrap.servers", "kafka:9092")
        .option("subscribe", "orders")
        .load()
        .selectExpr("CAST(value AS STRING) AS j")
        .select(from_json("j", schema).alias("o")).select("o.*"))

(df.writeStream
   .format("iceberg")
   .outputMode("append")
   .option("checkpointLocation", "s3://warehouse/ckpt/orders")
   .toTable("demo.db.orders"))   # 持续把订单追加进 Iceberg 表

3.2 写法 B：Flink SQL（纯 SQL 也能起流作业）

-- Flink SQL Client 里：定义 Kafka 源表 + Iceberg 目标表，一条 INSERT 起流作业
CREATE TABLE k_orders (
  order_id BIGINT, city STRING, amount DOUBLE, event_time TIMESTAMP(3))
WITH ('connector'='kafka', 'topic'='orders',
      'properties.bootstrap.servers'='kafka:9092',
      'format'='json', 'scan.startup.mode'='earliest-offset');

INSERT INTO iceberg_catalog.db.orders SELECT * FROM k_orders;  -- 流式入湖
checkpointLocation 是流作业的命根子：它记录「读到哪个 offset、写了哪些文件」，重启靠它才谈得上不重不漏。想重来务必连它一起清。

③ 查询、聚合与时间旅行

用 Trino / Spark SQL 把湖仓表当数仓查

Trino 并不「打开这张表」：它先问 catalog 要当前快照，逐层裁剪出文件清单，最后才去 MinIO 拉那几个 Parquet。知道这条路径，才知道慢在哪一层。

# ── 阶段四：进 Trino，把湖仓表当数仓查 ──
docker compose exec trino trino

-- 1) 先确认 catalog 通了
SHOW CATALOGS;                        -- 判据：列表里有 iceberg

-- 2) 实时看各城市 GMV：数据还在流入，多查几次数字应该在涨
SELECT city, count(*) AS orders, round(sum(amount), 2) AS gmv
FROM iceberg.db.orders
GROUP BY city ORDER BY gmv DESC;

-- 3) 表有哪些快照？每提交一个微批就多一行
SELECT snapshot_id, committed_at, operation
FROM iceberg.db."orders$snapshots" ORDER BY committed_at;

-- 4) 时间旅行：查 5 分钟前那一版数据，行数应明显少于现在
SELECT count(*) FROM iceberg.db.orders
FOR TIMESTAMP AS OF (current_timestamp - interval '5' minute);

-- 5) 维护：流式写必然产生小文件，合并一次
ALTER TABLE iceberg.db.orders EXECUTE optimize;
-- 判据：再查 $files，行数应该明显变少
查询回答什么判据
SHOW CATALOGS认得这个湖仓吗含 iceberg，否则 catalog 没挂上
$snapshots作业在提交吗行数持续增加，不涨即作业挂了
EXECUTE optimize治理有效吗$files 行数明显下降
交互演示 · 端到端链路跟随
点「下一步」，跟随一条订单从产生到被查询。
至此你已复现了一条实时数仓的最小骨架。原理见 时间旅行与快照隔离 与 Compaction。

常见坑与排查清单

最容易卡住的几处

失败原因高度集中在几处。先按下图定位是哪一类，再查具体服务。

现象多半原因先跑哪条命令怎么解
容器一直重启内存不足 / 端口占用docker compose logs --tail=50 <svc>加内存；lsof -i :9092 后换端口
连不上 Kafka内外地址混用docker compose exec spark ping -c1 kafka容器内 kafka:9092，宿主机 localhost:9092
写 Iceberg 报 403凭证 / endpoint 不对docker compose logs mc核对 AWS_* 与 minio:9000
Trino 查不到表catalog 不同源SHOW CATALOGS指向 http://iceberg-rest:8181
越跑越慢小文件爆炸SELECT count(*) FROM …$filesEXECUTE optimize + expire_snapshots
重启后重复消费checkpoint 丢了看 warehouse/ckpt/checkpointLocation 要持久唯一
三条心法：看日志定位哪一环、分段验证、一次只改一个变量。面试时讲一个亲手排掉的坑，远胜背概念。

6.1 一页纸总结

① 一键全栈

docker-compose 拉起五个服务。

② 端到端链路

造数 → Kafka → 入湖 → Trino → 时间旅行。

③ 两种写法

Spark 微批 vs Flink 连续流。

④ 排错心法

日志 → 分段验证 → 一次一个变量。

6.2 别把本地的结论直接搬去生产

架构同构，但每一项可靠性设计都被拿掉了。左边这一列出现在生产 PR 里都该被打回。
