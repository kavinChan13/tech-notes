SQL 心智与逻辑执行顺序

SQL 是声明式的 · 搞懂"子句先后顺序"，一半的诡异 bug 就解释清了

SQL 是声明式的：你描述「要什么结果」，优化器决定怎么算。但它有固定的逻辑执行顺序，能解释一大票「为什么这么写就报错」。

像在餐厅点菜：你说「要川菜、不辣、按辣度排前 3 道」，厨房自己决定怎么下锅——但处理顺序是固定的：先看有哪些菜、筛掉不要的、分组、排序、取前几道。

这一张图立刻解释了几个高频困惑：

困惑原因（看执行顺序）
别名在 WHERE 里报错，在 ORDER BY 里却能用WHERE（②）早于 SELECT（⑤），那时别名还不存在；ORDER BY（⑦）在其后
WHERE 和 HAVING 的分工WHERE 在分组前滤原始行，HAVING 在分组后滤聚合结果
窗口函数不能写进 WHERE窗口到 ⑤ 才算，② 时还没有 → 要过滤窗口结果得套子查询或 QUALIFY
逻辑顺序 ≠ 物理顺序：执行时优化器会重排（谓词下推能让 WHERE 早于 JOIN），只要结果等价即可。逻辑顺序管写对，物理优化管跑快。

窗口函数：分析型 SQL 的皇冠

组内排名、同比环比、累计、移动平均——离开窗口函数寸步难行

1.1 窗口函数 vs GROUP BY

GROUP BY 像把全班合并成一行组汇总，个人没了；窗口函数像给每个同学贴一张便签，写上「你在组内排第 2」——行还在。
窗口函数（Window Function）的语法核心是 OVER 子句，四个部件各管一件事：

1.2 三类窗口函数

排名类

ROW_NUMBER / RANK / DENSE_RANK，外加 NTILE(n) 分桶。三者差别见下图。

取值类（偏移）

LAG / LEAD 取前后 N 行，FIRST_VALUE / LAST_VALUE / NTH_VALUE 取窗内定点。

聚合类（开窗）

SUM / AVG / COUNT / MAX / MIN OVER(...)。配 frame 可做累计（running total）和移动平均。

排名类三兄弟只在并列时才分道扬镳，面试问的就是这一格：

取值类是「隔着行拿数」——同比环比、差分都落在 LAG / LEAD 上：

三类共享同一个窗口定义，写进同一个查询更容易看出差别：

-- 同一份 emp、同一个窗口 w：三类窗口函数一次全出
-- Bob / Cid 工资都是 80（并列），排名三列在这里分道扬镳
SELECT name, dept, salary,
  -- ① 排名类：区别只在"并列怎么办"
  ROW_NUMBER() OVER w AS rn,        -- 90→1 80→2 80→3 70→4  硬给唯一序号
  RANK()       OVER w AS rnk,       -- 90→1 80→2 80→2 70→4  同号后跳号
  DENSE_RANK() OVER w AS drnk,      -- 90→1 80→2 80→2 70→3  同号后不跳
  -- ② 取值类：跨行拿数，同比环比与差分都靠它
  LAG(salary)  OVER w AS prev_sal,  -- 窗口内上一行，首行 NULL
  LEAD(salary) OVER w AS next_sal,  -- 窗口内下一行，末行 NULL
  salary - LAG(salary) OVER w AS gap,  -- 与上一名的差额；换成月份就是环比
  -- ③ 聚合类开窗：不写 frame 时覆盖整个分区，同一个值贴给组内每一行
  AVG(salary)  OVER (PARTITION BY dept) AS dept_avg
FROM emp
WINDOW w AS (PARTITION BY dept ORDER BY salary DESC);
-- WINDOW 子句给窗口起个名，省去重复七遍 OVER(...)；不支持的引擎原样展开即可

1.4 窗口帧（Frame）与滚动计算

窗口框架（Frame）限定「窗口里取哪几行」：ROWS 数物理行，RANGE 按 ORDER BY 的值——排序列一有并列两者就分叉。默认值各引擎不同，生产 SQL 一律写明。
-- 一条查询同时给出：滚动累计、ROWS 与 RANGE 的差别、3 日移动平均
SELECT day, amount,
  -- 从窗口第一行累计到当前行 = running total
  SUM(amount) OVER (ORDER BY day
       ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)  AS cum_rows,
  -- 同一句换成 RANGE：day 相同的行被视为一体，会一起看到同一个累计值
  SUM(amount) OVER (ORDER BY day
       RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cum_range,
  -- 当前行 + 前两行；头两天不满 3 行，算的是已有行的均值而不是 NULL
  AVG(amount) OVER (ORDER BY day
       ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)         AS ma3
FROM daily_sales;
QUALIFY 用来过滤窗口函数结果，之于窗口正如 HAVING 之于 GROUP BY，一行搞定「取每组第一」。Snowflake / BigQuery / DuckDB 支持，其余退回子查询 + WHERE（见 §6.4）。

1.5 方言差异与兼容写法

能力常见支持情况兼容策略
QUALIFY部分云数仓与分析引擎改写为子查询 + 外层 WHERE
窗口默认 frame各引擎细节有差异显式写 ROWS/RANGE BETWEEN ...

高级聚合：多维小计一把梭

报表常要"分项 + 小计 + 总计"——别再 UNION 一堆子查询了

2.1 GROUPING SETS / ROLLUP / CUBE

普通 GROUP BY a, b 只给「a×b 的明细」，报表还要各维度小计 + 总计。这三个扩展一次搞定，区别只在「生成哪几种分组组合」：

ROLLUP(a, b)

层级小计：(a,b) 明细 + 按 a 的小计 + 总计。适合有层级关系的维度（年→月、地区→城市）。

CUBE(a, b)

所有组合：(a,b) + 按 a + 按 b + 总计。维度无层级、要全交叉时用。

GROUPING SETS

最灵活：你指定要哪些分组组合。ROLLUP/CUBE 其实都是它的语法糖。

2.3 一条查询写全：分组组合 + 小计标签 + 条件聚合

生产里的报表 SQL 是三件事叠在一起：GROUPING SETS 决定出哪些行，GROUPING() 把小计行的 NULL 换成人话，FILTER 一次扫描给出多个口径。

-- 一条查询出「明细 + 各维度小计 + 总计」，顺带标好小计行、并给三个口径
SELECT
    CASE WHEN GROUPING(region)  = 1 THEN '全部地区' ELSE region  END AS region,
    CASE WHEN GROUPING(product) = 1 THEN '全部品类' ELSE product END AS product,
    SUM(amount)                                        AS amt,
    SUM(amount) FILTER (WHERE channel = 'online')     AS amt_online,
    COUNT(*)    FILTER (WHERE amount > 1000)          AS big_orders
FROM sales
GROUP BY GROUPING SETS ((region, product), (region), (product), ());
--   等价改写：ROLLUP(region,product) = ((region,product),(region),())
--             CUBE(region,product)   = 上面四种组合全要
-- 不支持 FILTER 的引擎退回 SUM(CASE WHEN channel='online' THEN amount END)
03

CTE 与递归查询

把"俄罗斯套娃式子查询"拆成可读的步骤 · 以及用 SQL 遍历层级

3.1 CTE：给子查询起名字

CTE（Common Table Expression）：用 WITH 名字 AS (子查询) 给一段查询命名，后面当表用——把深层嵌套拉平成自上而下的步骤，还能多次复用。
CTE 不一定被「物化」——多数引擎会内联展开后再优化，等价于直接写子查询。别假设它自带缓存；部分引擎支持 MATERIALIZED 强制复用。

3.2 递归 CTE：用 SQL 走层级 / 图

递归 CTE（WITH RECURSIVE）：能引用自身，用来走层级 / 树 / 图——组织架构、BOM 展开、评论树。结构固定为锚成员 UNION ALL 递归成员，直到某一轮不再产出新行。

放进同一条查询，正好演示 CTE 的三个用途：命名、递归、在下游被引用两次。

-- 组织架构展开：普通 CTE 先备料，递归 CTE 逐层往下走
WITH RECURSIVE
-- ① 普通 CTE：只是给「在职员工」起个名字，后面当表用
active AS (
    SELECT id, name, manager_id FROM emp WHERE left_date IS NULL
),
-- ② 递归 CTE：锚成员定起点，递归成员反复接上「下属的下属」
subordinates AS (
        SELECT id, name, manager_id, 1 AS lvl,
               CAST(name AS VARCHAR) AS path        -- 锚成员，只跑一次
        FROM active WHERE id = 1
    UNION ALL
        SELECT a.id, a.name, a.manager_id, s.lvl + 1,
               s.path || ' > ' || a.name                -- 递归成员，引用自身
        FROM active a JOIN subordinates s ON a.manager_id = s.id
        WHERE s.lvl < 10       -- 深度兜底：数据成环时不至于把集群跑死
)
-- ③ 同一个 CTE 在下游被引用两次：既列层级路径，又统计直属下属数
SELECT s.lvl, s.path, COUNT(c.id) AS direct_reports
FROM subordinates s
LEFT JOIN subordinates c ON c.manager_id = s.id
GROUP BY s.lvl, s.path
ORDER BY s.lvl, s.path;
大数据引擎对递归 CTE 的支持参差（Spark SQL 早期不支持），上生产前先确认。防环靠那句 WHERE s.lvl < 10，比「相信数据无环」可靠。

Join 进阶与子查询

semi / anti join、LATERAL、相关子查询、集合运算 · 还有 NULL 的坑

4.1 半连接 / 反连接（Semi / Anti Join）

半连接（Semi Join）只问「左表这行在右表有没有匹配」，用 EXISTS；反连接（Anti Join）要「右表没有匹配的那些」，用 NOT EXISTS。普通 JOIN 会因右表多条匹配而放大行数，它俩不会。

4.2 LATERAL / 相关子查询

LATERAL Join（SQL Server 叫 CROSS/OUTER APPLY）让右侧子查询能引用左表当前行的列，典型用途是「每个用户取最近 3 笔订单」。它和相关子查询本质相同：逻辑上逐行重算，表达力强但可能慢，优化器常改写成 join。

4.3 集合运算

运算含义去重？
UNION并集去重（慢）
UNION ALL并集，保留重复不去重（快，优先用）
INTERSECT交集去重
EXCEPT / MINUS差集（A 有 B 无）去重
能用 UNION ALL 就别用 UNION：后者要做一次全局去重，相当于一次 shuffle，数据一大代价就不小。

4.4 坏例 ❌ / 好例 ✅：NULL 安全与行数放大

报表最常翻车的两处：anti join 写法用错（结果静悄悄变空）与明细 join 明细（金额重复计数）。后者的解法是先各自聚合再 join。
-- ❌ 坏例 1：子查询里只要混进一个 NULL，整个结果就变成空集
SELECT * FROM users u
WHERE u.id NOT IN (SELECT user_id FROM orders);

-- ✅ 好例 1：anti join 一律写 NOT EXISTS，对 NULL 安全，优化器也更容易识别
SELECT * FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
--   想要「下过单的用户」把 NOT 去掉就是 semi join：存在即可，不关心下了几单

-- ❌ 坏例 2：明细 join 明细。一个订单三行商品，用户维度的金额就被算了三遍
SELECT u.level, SUM(oi.amount)
FROM order_items oi JOIN users u ON oi.user_id = u.id
GROUP BY u.level;

-- ✅ 好例 2：先把事实收敛到订单粒度，再关联维表——行数不放大，shuffle 也小
WITH fact AS (
  SELECT order_id, user_id, SUM(amount) AS amt
  FROM order_items GROUP BY order_id, user_id
)
SELECT u.level, SUM(f.amt)
FROM fact f LEFT JOIN users u ON f.user_id = u.id
GROUP BY u.level;

大数据 SQL 特色

复杂嵌套类型、数组炸裂、近似计算、采样——传统 OLTP SQL 里少见，大数据里天天用

5.1 复杂类型与数组炸裂

复杂类型（ARRAY / MAP / STRUCT）：一行用户带一个 tags ARRAY<string>、一个 profile STRUCT<age,city>——半结构化数据（D01 Variety）落到表里就长这样。
explode / LATERAL VIEW（数组炸裂）：把一行里的数组展开成多行，之后才能正常 group by。方言差异集中在这里：
动作Spark / HivePresto / Trino
取 struct 字段profile.city
取数组元素tags[0]（从 0 起）tags[1]（从 1 起）
取 Map 的键props['key']
数组炸成多行LATERAL VIEW explode(tags) t AS tagCROSS JOIN UNNEST(tags) AS t(tag)
下标越界、键不存在都返回 NULL 而不报错——跨引擎迁移时下标起点差 1，错位是静默的。

5.2 近似计算：用精度换速度

精确 COUNT(DISTINCT) 要把所有值 shuffle 到一起去重，海量数据上极贵；approx_count_distinct 用 HyperLogLog 以固定小内存换 ~1–2% 误差。「差不多准 + 快」常胜过「绝对准 + 慢」——这是和 OLTP 思维的分野。
需求精确写法近似 / 抽样写法判据
去重计数COUNT(DISTINCT user_id)approx_count_distinct(user_id)看板可以；对账结算不行
分位数percentile(x, 0.99)approx_percentile(x, 0.99)P99 本就在抖，近似够用
探索 / 调试直接全量扫TABLESAMPLE BERNOULLI(10)逻辑跑通了再上全量

执行顺序 · 性能 · 常见陷阱

写对只是及格 · 写"快"且"不踩坑"才是高级

6.1 让优化器帮上忙（呼应 D01 / D03）

  • 分区裁剪：WHERE dt='2026-06-25' 让引擎只扫那一个分区，海量表上是数量级差异。务必在分区列上加过滤。
  • 谓词下推 / 列裁剪：列存（Parquet）+ 只 SELECT 需要的列 + 尽早 WHERE。少写 SELECT *。
  • SARGable 条件：别在过滤 / JOIN 列上套任何东西，否则索引与分区裁剪一起失效。原则是让常量迁就列，四种形态如下图。
B+Tree 为什么只能按前缀定位，见 B01 · B+ Tree 索引原理 与 架构篇 · InnoDB 存储引擎内部。

6.2 大数据 SQL 的性能要点

问题表现对策
COUNT(DISTINCT)重 shuffle、慢可容忍误差就换 approx_count_distinct
Join key 倾斜个别 task 卡住（D03）加盐 / 开 AQE / 热点单独处理

6.3 容易翻车的陷阱清单

NULL 三值逻辑：NULL = NULL 得到的是 NULL 而非 true；SUM/AVG 与 COUNT(col) 忽略 NULL，COUNT(*) 不忽略。动手前先用 COALESCE / IS NULL 想清楚。
其他常见坑：① GROUP BY 后 SELECT 非聚合列；② 浮点数做等值比较；③ DATE 截断按哪个时区算——跨库对数时最常见的分歧点。

6.4 去重与每组 TopN：同一个模板的两种用法

日志回放、CDC 重试下的去重，和面试最爱问的「每组前 N 名」，其实是同一段 SQL，差别只在最后那个比较符。
SELECT * FROM (
  SELECT t.*,
         ROW_NUMBER() OVER (
           PARTITION BY biz_id                          -- 换成 dept 就是「每个部门」
           ORDER BY event_time DESC, ingest_time DESC   -- 换成 salary DESC 就是「工资最高」
         ) AS rn
  FROM fact_events t
) x
WHERE rn = 1;
--    rn = 1   → 每个 biz_id 只留最新一条：防重放、防重复入湖
--    rn <= 3  → 每组前 3 名：top-N per group 的标准答案
-- 排序键必须能定出唯一顺序，否则并列时留下哪条是随机的——所以这里补了 ingest_time
-- 支持 QUALIFY 的引擎（DuckDB / Snowflake / BigQuery）可以省掉整层子查询：
--    SELECT * FROM fact_events
--    QUALIFY ROW_NUMBER() OVER (PARTITION BY biz_id ORDER BY event_time DESC) = 1;

6.5 读懂执行计划：为什么它走了全表扫描

前面所有建议都要靠 EXPLAIN 确认「到底生效没有」。不必逐行看懂，问三个问题就能定位九成慢查询：

EXPLAIN ANALYZE
SELECT u.level, COUNT(*) FROM orders o JOIN users u ON o.user_id = u.id
WHERE date(o.created_at) = DATE '2026-06-01' GROUP BY u.level;

-- 输出里只有这几行需要看：
HashAggregate  (cost=1240..1250 rows=10)   (actual rows=4    loops=1)
  ->  Hash Join  (cost=380..1180 rows=98000) (actual rows=1203)
        ->  Seq Scan on orders o  (cost=0..820 rows=100000) (actual rows=100000)
              Filter: (date(created_at) = '2026-06-01'::date)
              Rows Removed by Filter: 98797
        ->  Hash  (rows=500)

-- 判据三条，对应上图的三个问题：
--   ① Seq Scan + Rows Removed by Filter 巨大 → 过滤没能下推，白读了 98797 行
--   ② Filter 里出现 date(created_at)         → 列被函数包裹，索引用不上（见 §6.1 图）
--   ③ 估算 rows=98000 vs 实际 1203          → 差两个数量级，统计信息过期，先 ANALYZE
各字段的完整含义、以及 MySQL EXPLAIN 的 type / key / Extra 怎么读，见 B01 · 查询优化器与 EXPLAIN。

把高级 SQL 收成肌肉记忆

一页纸总结

① 执行顺序

FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT

② 窗口函数

OVER(PARTITION BY … ORDER BY … frame)，不合并行；QUALIFY 过滤

③ 多维聚合

ROLLUP / CUBE / GROUPING SETS + FILTER 条件聚合

④ CTE / 递归

WITH 拉平嵌套；WITH RECURSIVE 锚成员 + 递归成员，设深度上限

⑤ Join / 子查询

EXISTS / NOT EXISTS 不放大行；UNION ALL 优先；NOT IN + NULL 坑

⑥ 特色与性能

explode；近似函数；分区裁剪 / SARGable；EXPLAIN 三问

面试自测（点击展开）

基础SQL 的逻辑执行顺序是什么？为什么 WHERE 里不能用 SELECT 的别名？
顺序FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT。
别名WHERE 在 SELECT 之前执行，那时别名还没生成，所以 WHERE 用不了；ORDER BY 在 SELECT 之后，能用。
核心窗口函数和 GROUP BY 的区别？怎么取"每个部门工资前 3"？
区别GROUP BY 合并行成聚合；窗口函数保留每一行、附加一列基于窗口的计算。
Top-NROW_NUMBER() OVER(PARTITION BY dept ORDER BY salary DESC) 编号，外层 WHERE rn≤3（或 QUALIFY）。
辨析ROW_NUMBER 唯一序号；RANK 并列跳号；DENSE_RANK 并列不跳。按需求选。
高频RANK、DENSE_RANK、ROW_NUMBER 有什么区别？
ROW_NUMBER严格唯一序号，并列也给不同号（1,2,3,4）。
RANK并列同号、跳号（1,2,2,4）。
DENSE_RANK并列同号、不跳号（1,2,2,3）。
实战为什么 NOT IN 有时返回空集？怎么避免？
原因子查询结果含 NULL 时，x NOT IN (…, NULL) 在三值逻辑下永不为 true → 整体空集。
避免改用 NOT EXISTS（anti join），它对 NULL 安全；或在子查询里过滤掉 NULL。
大数据大表上 COUNT(DISTINCT) 很慢，怎么优化？
原因精确去重要把所有值 shuffle 到一起，重 IO/网络。
优化能容忍 ~1% 误差就用 approx_count_distinct（HyperLogLog）；或预聚合、按维度预计算去重结果。
延伸若 distinct key 倾斜，配合加盐/AQE（D03）。
